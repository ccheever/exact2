## Cause and fix

**FU-1.** `QueuedControl.drag` (`composer-controls.contract`) reset `dragRun`, `dragFrom`, `dragDy` and `dragSeq` in a start
branch and then wrote `dragDy = dragDy + dy`, which reads the value from before the action (an action's writes land when
it ends), so a drag that started after an earlier one (another run, or the first move after a drop bumped
`queueDropSeq`) began at that drag's offset, and its insertion line and drop index (`dragInsert`) were shifted by it.
The reference's `onDragStart` sets a new `dragState` each time. Fixed in SW-1's shape: `let fresh = dragRun != id or
dragSeq != data.composer.queueDropSeq`; the start branch writes the run, origin and sequence; `dragDy = (fresh ? 0 :
dragDy) + dy`. `queued-drag.test.ts` runs the action and the component's derives with Contract's action semantics over
the client's own snapshot and drop (`cc:queued-drop`, `queuedDrop`): on the base, a drag of q3 after q1's 30-pt drag
gives `dy` 27 and the line under the last row for `-3` and 2, and q1 dragged again 5 pt after its drop gives `dy` 35
and `q1|3`, whose drop moves it to the end (2 of 3 fail); after, 3 pass. The interpreter `sidebar-sweep.test.ts` had is
shared as `contract-action-fixture.ts` (it still fails 3 of 3 on `fe0e39c91`'s sweep, as recorded for SW-1).

**FU-2.** First the reference (T3 Code Electron on this lane, PR #168): its Select All (Chromium's `selectAll`, what Edit ›
Select All runs) takes every commit row's title, sha, age and counts, with the selection drawn over them, as it takes every
button's text on the page; a pointer drag across two commit rows selects nothing; find in page finds the titles. So
"never selected" holds for a drag, not for Select All. On the Mac the clone's host makes button content unselectable
(LLP 1115 D8, `textSelectable`), so the row's texts, being the button's content, follow that rule, as the task asks.

The Mac host conflicts with it for the title (X82). Attempt 1 (the texts' row `user-select: none`): ⌘A / ⌘C took no
commit text, but every title was blank at rest. Cause, from the drive and `ensure` / `refreshVisibleText`: the detail
panel keeps its tabs mounted under `visibility: hidden`; showing the Timeline restyles every row at once, `ensure`
starts two replacements on its two workers and declines the rest, and only selectable texts are asked again (X82's pump).
Attempt 2 (the title also mounted afresh as the tab shows, so its first pixels are painted at once): drawn at rest and
when the tab is shown again, but after a 900-pt scroll the titles of the rows the scroll brought in were blank (prepared
off screen, never presented), except a short one under 16,384 device pixels. The sha, age and counts are too small to
raster and drew in both attempts. Built: the sha and age row and the counts row `user-select: none`; the title stays
selectable while X82 stands (the remount taken out); the stale comment ("the whole row is a button") rewritten; X82's row
in `EXACT2-GAPS.md` records both attempts. Not built: the title unselectable (Not done).

**FU-3.** `search-key-and-timeline-commit-title.test.ts`: the TC-1 guard also requires the button at the row's first
child's indent (a mutant with the button inside the additions row passes the base guard, fails this one); `needsSurface`
reads the `&&` tokens and drops a rule only for a positive surface token (`!composerFocus`, `!previewFocus` no longer drop
one; a case added; the 45 chords of `keybindingDefaults` are unchanged); the dead ternary is gone and `aria` takes `+` for
`mod++`, spelt `Meta+Plus` as `keyboard-dispatch.ts` spells it; the Swift list is the string literals between `let
referenceChords = [` and its matching `]` (escapes, brackets in a literal and comments read as Swift reads them; a case
added) and the count 45 is gone. `macos/tests/real-key-chords/main.swift`: exits 0 when `executionCount` equals the
suite's `testCaseCount`; its header says it is a coverage guard that passed on the modules from before #439. The stand-in's
claim: `ShortcutsMac.swift` `ShortcutHost.sync` (this branch and `origin/main`) claims by `sameChord` / `same`, the item's
key equivalent lowercased and its modifiers compared as they are, so the real sync does not read an uppercase key
equivalent as ⇧ (AppKit does). The stand-in now calls that comparison (`ShortcutHost.sameChord`), and a new test fails when
any bar item has an uppercase letter equivalent, the case the review raised; a mutant item "F" + ⌘ fails the old and the
new binary's chord tests (⇧⌘F reaches it) and the new test names it (Decision needed 2).
