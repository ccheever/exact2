# X39: Telemetry: product analytics, OTLP export and the host-telemetry pipes

## Summary

In T3 Code, "telemetry" is four separate things: the server sends product usage events to PostHog by default; the desktop and the server can export traces, metrics and logs over OTLP when configured;
both write local trace files; and the desktop feeds host power and Electron process data to the server over private pipes. The user excluded telemetry from the clone.
The shipped server still sends analytics unless told not to, and the clone embeds that server. The clone needs a recorded decision for each part: build it, keep it off, or close it. Ticket `20261005-telemetry` is blocked until then.

## Why this issue arose

### The T3 Code behavior
1. Product analytics (server, PostHog). On by default: `T3CODE_TELEMETRY_ENABLED` defaults to `true`; the host defaults to `https://us.i.posthog.com`; a project key is compiled in (`apps/server/src/telemetry/AnalyticsService.ts:69-80`).
   Events seen in the server code: `server.boot.heartbeat` with thread and project counts (`apps/server/src/serverRuntimeStartup.ts:171`), `client.connected` (`apps/server/src/ws.ts:3823`), `client.thread.started` and `client.turn.requested` (`ws.ts:1211,1989-1994`),
   `provider.turn.completed` (`apps/server/src/orchestration-v2/ProviderEventIngestor.ts:88,627`) and Codex sign-in events (`apps/server/src/provider/CodexChatGptAuth.ts:109-120`).
   Every event carries platform, architecture, T3 Code version, `clientType` (`desktop-app` when the server mode is `desktop`), server OS, architecture and mode, with `$process_person_profile: false` (`AnalyticsService.ts:170-200`).
   Batches flush every 1 s, hold at most 1,000 events (default), try up to 5 times, and back off from 2 s to 5 min (`:52-67,77-80`).
   The identifier is a SHA-256 hash of the first available source: `~/.codex/auth.json` `tokens.account_id`, then `~/.claude.json` `userID`, then an anonymous id the server writes to `~/.t3/telemetry/anonymous-id` (`apps/server/src/telemetry/Identify.ts:157-177,204,257-266`).
   The project documents it: events carry provider, model, reasoning effort, permission mode, turn result, duration and main-agent token totals, and no prompts, responses, file contents or tokens; the only switch is `T3CODE_TELEMETRY_ENABLED=false` in the server's environment (`docs/user/telemetry.md`).
   I found no telemetry toggle in the settings UI: a search of `apps/web/src` and `apps/desktop/src` for PostHog, analytics and product-usage terms matched only `CommandPalette.tsx` and `UsageProviderChart.tsx`.
2. OTLP export and trace files. Off unless configured. The desktop reads `T3CODE_OTLP_TRACES_URL`, `_METRICS_URL`, `_LOGS_URL`, `_EXPORT_INTERVAL_MS`, `_HEADERS` and `_PROTOCOL` (`apps/desktop/src/app/DesktopConfig.ts:48-55`), falls back to persisted observability settings, and
   hands the three URLs to every backend in the bootstrap envelope (`apps/desktop/src/backend/DesktopBackendConfiguration.ts:68-76,244-255,524-535`). The desktop writes a local `desktop.trace.ndjson` (10 MiB x 10 files) and the server writes `server.trace.ndjson`
   (`apps/desktop/src/app/DesktopObservability.ts:33-34,668-672`; `docs/operations/observability.md`). Settings → Diagnostics reads the server's trace diagnostics.
3. Host-telemetry pipes. The desktop starts the server with two extra inherited descriptors, `desktopTelemetryFd: 4` (desktop to server) and `desktopTelemetryControlFd: 5` (server to desktop) (`DesktopBackendConfiguration.ts:561-562`).
   `DesktopTelemetryPublisher` sends host power (locked, suspended, on battery, thermal state, speed limit, idle) and Electron process data. Its sampling constants are 1 s (live), 5 s (battery), 15 s (constrained), and host power at 30 s (active) and 2 min (idle)
   (`apps/desktop/src/telemetry/DesktopTelemetryPublisher.ts:21-28`). Electron process metrics run only on live demand, and power events and slow heartbeats continue with diagnostics closed (`docs/internals/resource-telemetry.md`). The server merges them with its own process counters, which come from a Rust helper, `t3-resource-monitor`, that the archive carries; "A missing or failed collector leaves the server running"
   and "Headless servers leave unavailable power data unknown" (`docs/internals/resource-telemetry.md`). The server starts with a stale, unknown host-power snapshot (`apps/server/src/background/HostPowerMonitor.ts:21-33`) and the background policy treats a stale snapshot as not constrained
   (`apps/server/src/background/BackgroundPolicy.ts:140-155`: `if (hostPower.stale) return false`). The control pipe carries `setDiagnosticsDemand`, `setHostPowerIntervals` (the two host-power intervals of the Background activity settings) and the desktop-update requests of issue X40
   (`packages/contracts/src/resourceTelemetry.ts:258-345`).
   Reference tests: `DesktopTelemetryPublisher.test.ts`, `DesktopObservability.test.ts`, `AnalyticsService.test.ts`, `Identify.test.ts`.

### What exact2 does today
- Not in `EXACT2-GAPS.md`. Bundled library (`20261005-platforms-v3`): telemetry, analytics and passing extra file descriptors to a child process are **not covered: unknown**.
- Observed in the clone on 2026-10-05: no analytics or OTLP code. `settings-a-telemetry.ts` implements the client side of Settings → Diagnostics resource telemetry (subscription `subscribeResourceTelemetry`, `server.getResourceTelemetryHistory`, `server.signalProcess`; header comment, lines 1-6).
  It has labels for the Electron categories (`electron-main`, `electron-renderer`, `electron-gpu`, `electron-utility`) that the clone's server cannot report.
  `settings-a-background.ts` (lines 10-26, 70-71, 106-107) already offers the Background activity profiles, the switches "Pause when host is locked", "Pause on host low power", "Pause on client low power" and "Pause on battery", and the two host-power intervals.
- The plan now turns telemetry off everywhere: `20261005-embedded-server-runtime` sets
  `T3CODE_TELEMETRY_ENABLED=false` (scope, row "Telemetry off"), and so do every lane server
  (`20261005-clone-on-exact2-main`) and the oracle (`20261005-desktop-oracle-and-trace`).

### Where the clone hits it
Part 1 reaches the clone through the official server archive: unless the child environment says otherwise, the server posts events to T3's PostHog from the user's machine. Production builds share `~/.t3` with the original app (user decision), so the server would
reuse the original's identity file `~/.t3/telemetry/anonymous-id`, or hash the same Codex or Claude account, and `clientType` would read `desktop-app` if the clone sends the same `mode: "desktop"` bootstrap as the reference. Parts 2 and 3 do not reach the clone: it sets no OTLP URL and passes no pipes.
Differences a user sees: none for parts 1 and 2 if analytics is switched off; for part 3, the server has no Electron process data (so Settings → Diagnostics has no Electron rows) and no host power data. With a stale snapshot the policy never treats the host as constrained, so the clone's switches "Pause when host is locked" and "Pause on battery", the thermal and sleep rules, and the host-power intervals change nothing on the embedded server. ("Pause on host low power" is inert in the reference too: its desktop snapshot always reports `lowPowerMode: "unknown"`, `DesktopTelemetryPublisher.ts` in `sampleOnce`.)
That is a visible difference in a settings page the clone already draws. (What the policy pauses was not traced beyond `isHostConstrained`.)

## Why it must be resolved
The goal is a full clone, but the user excluded telemetry, and part 1 sends data about the user to a third party. A silent default in either direction is wrong, so the plan needs an explicit decision per part:
- Part 1: keep off (the clone sets `T3CODE_TELEMETRY_ENABLED=false` in the server's environment and the plan proves it), or leave the server default (events go to T3's PostHog), or build the clone's own analytics (not proposed).
- Part 2: close (no OTLP; local trace files stay), or pass OTLP settings through if the user supplies a collector (a Settings or environment input; the reference has none beyond environment variables).
- Part 3: close (accept that Diagnostics has no Electron rows and that the host-pause switches and the host-power intervals have no effect), or build the pipes: the module opens two descriptors for the child and samples macOS power state. Part 3 is local only; no data leaves the machine.
`20261005-telemetry` (blocked) holds parts 2 and 3; `20261005-embedded-server-runtime` must carry the part 1 setting regardless of the decision, because "excluded" is only true if the server is told not to send. `20261005-app-update-feed` depends on part 3 for server-triggered desktop updates.

## Requested support
Part 1 and part 2: none. A server environment variable and a pass-through; no framework change.
Part 3, if built (to confirm at `issue-open`): spawn the child with descriptors 4 and 5 (Swift `posix_spawn` file actions; Foundation `Process` offers only standard streams, so this is app-side Swift, not a framework feature), read macOS power state (battery, thermal, idle, lock, sleep) with system APIs,
and encode the messages of `DesktopHostTelemetryMessage` (hello, snapshot, update status; `packages/contracts/src/resourceTelemetry.ts:258-345`). The snapshot's `power.source` must be one of the schema's literals (`packages/contracts/src/background.ts:23-30`: `unknown`, `node-macos-shell`, `node-macos-native`, `node-linux`, `node-windows`, `electron-main`); which one the clone sends is decided at `prepare`. Whether the module's child-process helper may inherit extra descriptors under the host's sandbox settings is **unknown**.
