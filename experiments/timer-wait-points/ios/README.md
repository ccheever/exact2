# iOS timer wait points probe

This probe measures the UIKit behavior that LLP 1147 (`llp/1147-timers-that-may-wait.rfc.md`, D2, D3 and D7's Apple rows) relies on for timers that wait for a frame, a UI update, a scroll's end or idle. It is a plain UIKit app with no Exact code, so what it records is the platform's behavior alone.

The app shows one tall `UITableView` of plain rows, mid-way down so no gesture reaches an edge, and a small box that it fades. It logs events with `CACurrentMediaTime()` timestamps into memory, each with the main run loop's mode and, when it happens inside a UI update, that update's `UIUpdateInfo.modelTime`. An XCUITest target performs real gestures: a held drag (`press(forDuration:thenDragTo:withVelocity:thenHoldForDuration:)`, which moves slowly, holds the finger still for 500 ms and lifts without velocity) and a fling (`swipeUp(velocity: .fast)`). The test and the app talk through Darwin notifications, so the test waits on events and never queries the app's accessibility tree while it measures, which would add main-thread work to the app. XCUITest's in-app agent still makes UI updates of its own on a still screen (four in the 2 s still window, and one as the test resumes after each wait), so `run.sh` also runs the `updateLink` script with no test attached, posting its signal with `simctl notify_post` and waiting for the log the app then writes itself; those files are named `control-updateLink-<repetition>.json`. When the test asks, the app writes `Documents/<scenario>-<repetition>.json` (environment and summary) and `<scenario>-<repetition>.events.json` (the raw log), which `run.sh` copies into `results/`.

Each launch first runs a script: 2 s with nothing happening, a 1 s `UIView.animate` opacity fade, 1 s still, a 1 s `UIViewPropertyAnimator` fade and 1 s still. In the `updateLink` scenario three firing segments follow, 500 ms apart, each ten callbacks 100 ms apart that change nothing on screen: a `Timer` that logs with `UIUpdateInfo.current(for:)`, a `Timer` that logs without it, and a chain of `DispatchQueue.main.asyncAfter` blocks. They show whether a timer firing, or asking UIKit for the update in progress, makes a UI update. The summary splits the log into phases (`still`, `animate`, `animate.tail`, `animator`, `animator.tail`, `segment.<name>`, and for each gesture its `moving`, `held`, `deceleration`, `tail` and, when the app went to the background, `background` phases) and counts each measured callback in each, with its rate, median interval and run-loop modes. A tail is the second after motion ends, before the next gesture.

## What each test establishes

Each test launches the app three times (`testScrollState` five) with one scenario. A scenario installs only its own instruments, because a `CADisplayLink` asks for a frame every vsync and a timer wakes the run loop, either of which would change what the others see.

- `testUpdateLink` measures a passive `UIUpdateLink` (`requiresContinuousUpdates` false) on the view controller's view, with actions in `afterUpdateScheduled`, `beforeEventDispatch`, `afterEventDispatch` and `afterUpdateComplete`. It establishes when the link is called (still screen, drag, held finger, deceleration, a render-server `UIView.animate` fade, a `UIViewPropertyAnimator`) and whether the calls stop when motion stops. The summary's `ordering` groups events by UI update and reports, within each update, whether `afterUpdateScheduled` came before the window's touch dispatch (`touch.*`, logged in `UIWindow.sendEvent`), the pan recognizer's action (`pan.*`) and `scrollViewDidScroll` (`scroll`).
- `testRunLoopModes` measures a `CFRunLoopObserver` for `beforeWaiting` in the default mode only, another in the common modes, and repeating 100 ms `Timer`s in the default and common modes. It establishes which of them run while a finger drags and while the table decelerates.
- `testScrollState` samples `isTracking`, `isDragging` and `isDecelerating` every 50 ms (a common-mode timer) and logs the scroll view's delegate callbacks across a held drag, a fling, a fling interrupted by a switch to Settings, and that again, since the switch takes 0.5 to 4 s on a loaded host and only sometimes reaches the background before a 2.4 s deceleration ends. A slower deceleration is not available: on iOS 27.1, `UIScrollView.decelerationRate`'s setter stores 0.99 (`.fast`) for any value below 0.994 and 0.998 (`.normal`) otherwise. The app asks for the switch as each of these flings starts to decelerate, and `run.sh` makes it from the host with `simctl launch`: XCUITest waits for the app to idle after a swipe, which is after the deceleration, and on the iOS 27.1 iPhone Duo simulator `XCUIDevice.shared.press(.home)` did not send the app to the background (in two runs) and once crashed SpringBoard. On entering the background the app holds a background task for 2 s so the sampler can see `isDecelerating` there; the test then reactivates the app and waits up to 15 s for the scroll to settle.
- `testDisplayLink` measures a `CADisplayLink` left at the default `preferredFrameRateRange` while still and during a fling. The simulated iPhone Duo reports a 60 Hz `maximumFramesPerSecond`, so its rates say nothing about a ProMotion device's.

## Running it

`run.sh` needs Xcode 27.1 (set `DEVELOPER_DIR` to use another) and `xcodegen`. It creates an iPhone Duo simulator on the iOS 27.1 runtime, generates the project from `project.yml`, runs the UI tests on that simulator alone, runs the control when `testUpdateLink` runs, copies the results into `results/` and deletes the simulator. Arguments name test methods; none runs all four.

```zsh
./run.sh                                # all four tests
./run.sh testUpdateLink testScrollState # some
bun summarize.mjs [scenario]            # counts per phase across repetitions, and background timelines
```

The build goes into the repository's ignored `target/timer-wait-points-ios/` (`PROBE_BUILD_DIR` overrides it), with the test log at `xcodebuild.log` and the result bundle at `results.xcresult` there. Only the JSON files land in `results/`.
