## 1. Decisions

### D1 — the two regressions

1. **A grouped row that holds a stack keeps the cell's margins.** A column of two or more parts
   that isn't the subtitle cell gets the sheet's 15 pt above and below, as a `column` row and a
   hand-built cell pinned to its margins do. Every host draws the sheet. Avatar rows, rows with
   authored padding and empty columns are unchanged.
   - Built: `6623877a9`.
   - Tests: a contract test and an XCTest; iOS 507/0.
2. **A scroller's content is laid out above its bottom inset.** This is native safe-area
   integration: a layout inset on the content box, not padding around the scroller, and not a
   CSS rule. When a route's scroller runs
   under the home indicator (LLP 1116 D2.1), its content box for layout excludes the bottom
   adjusted inset. So a button that ends the content, or content that fills the scroller's
   height, rests above the indicator. Scrolling content still passes under it. Tests:
   trivia-quiz's results layout, a filled-height column, and the white-band apps re-checked.
3. **A long conversation opens at its newest message.** `scroll-start="end"` with
   `scrollFollowEnd` lands one or two messages short of the end when rows are measured after
   the first scroll, as their estimated heights become real (chat-rooms). The host keeps the end
   pinned until the rows above have their real heights.

### D2 — the docs stop teaching the two bugs

1. **The save lifecycle, whole.**
   - A field clears, and a sheet or pushed form closes, in a `then` action, only when the reply
     is ok.
   - A refusal keeps the text and the form, and shows the reason where the person edits.
   - A stale error clears when the next attempt starts.
   - This covers the core example, `chat-thread`, `rest-backend` and `navigation-stack` (which
     today navigates back before the reply).
   - The `tests` recipe shows the refusal path, and a new `after-a-write` recipe holds the whole
     pattern.
2. **A multi-field create or edit is a sheet.** The core says it in one sentence after its
   example and points at `navigation-stack`. A one-field add, like the example's, stays on the
   list.
3. **The header pitfall is corrected.** start-here's pitfall still says a header's extra text
   is dropped and a count belongs in the content. Since LLP 1116 D2, the first text after the
   heading is the bar's subtitle.

### D3 — design the content, leave the controls

The core's "say less" section is rewritten to say both halves:

- **The platform answers what you omit.** Controls, chrome, navigation, type ramp, colours of
  controls, dark mode.
- **The app's own content is yours to design.** For example:
  - a summary or hero at the top of the main screen (today's total, the current temperature,
    the score);
  - a clear hierarchy in rows (a `-exact-headline` title, `-exact-secondary-label` metadata);
  - colour that carries meaning (the system greens and reds for state, a tinted card for the
    hero);
  - a chart or bars where numbers compare, using `progress` or boxes with role colours;
  - empty states that say what to do.

That instruction is a few lines of the core, not a duty to restyle every screen. The
framework adds three things:

1. **`exact:content`, an opt-in built-in library.**
   - `use SummaryCard, StatBar, EmptyState, RowText from "exact:content"`.
   - Contract components with good spacing, role colours, text styles, a sensible narrow and
     wide arrangement, and accessible labels.
   - They are compiled into the compiler, as `exact:motion` is (`contract/cli/src/resolve.rs`).
   - Authors pick what to use and pass props. The components draw content, never controls or
     chrome.
2. **Grouped-row text styles by default.** In a grouped row's stack, a text with no authored
   font or colour is drawn as UIKit's subtitle cell draws it. The first text takes the title
   style, and the texts after it take the secondary label style and colour. This is omitted
   presentation, which LLP 1115 gives the platform.
3. **A `content-design` recipe** shows the library and the rule: a content screen is not
   another settings list, and inset-grouped is for settings and forms. An adaptive list-and-detail
   composition replaces the web-look recipe's centred 640 px column, which contacts' grader called
   "a stretched phone UI".

The test is the graders' "native but plain" verdicts (weather, mood-journal, habit-tracker,
water-tracker, focus-timer), judged on screenshots of real screens, not only by compiling.

### D4 — the web: a back control and links that look like links

1. **A pushed route's app bar draws a Back button on the web.** It is the route's
   `navigationBack` control, or the router's back when none is named (LLP 1116 D6). This
   matches the system Back button iOS draws. Today a pushed screen on the web has no way back
   except the browser's own button (contacts).
2. **A block `link` draws as a link on the web:** the accent colour and a pointer cursor, as an
   inline run already does (`LinkText`). Today a `tel:`/`mailto:` link is black text with a
   default cursor.

### D5 — recipes for what builders still grep

Round 2 builders still grepped the long guides for:

- keyboard dismissal and focus (4 builds);
- what to do after a write succeeds or fails (3);
- standard functions such as `sort`, `split`, `slice`, `first`, `pow` (5);
- timers (5);
- files and grants (4).

New recipes, each under 80 lines:

- **`keyboard-and-focus`:** dismiss on submit, `blur`, the keyboard's return key,
  `enterkeyhint`.
- **`after-a-write`:** a mutation's reply, `then`, `failure`, clearing on success, and closing
  a form on success (D2.1).
- **`functions`:** a one-line index of the standard functions. For one function's signature,
  rules and an example, `bun exact.mjs contract vocab <function>` prints that function's entry,
  as `vocab` already does for tags and properties: precise retrieval instead of a catalogue.
  The core's lookup row points here, not at the grammar.
- **`timers`:** `task … every`, starting and stopping, a countdown.
- **`files-and-grants`:** the storage API and grant lines for collections, beside
  `persisted-setting` for settings.

The core's lookup lines point at them. No recipe is added for a question builders did not
repeat.

## 2. Not in scope

- **The comparison stacks' strengths that are a builder's choice.** For example, a custom serif
  header, or skeleton loaders.
- **The Snapback client track** (LLP 1116 §9).

## 3. Order of work

Four lanes in parallel:

1. **iOS:** D1 items 2 and 3, and D3's grouped-row text styles. Item 1 is built.
2. **Web:** D4.
3. **Compiler and library:** `exact:content`, and `contract vocab <function>`.
4. **Docs:** D2, D3's core rule and recipes (including the adaptive composition), and D5. Each
   recipe is compiled by the doc check and run as an app.

Each lane runs the five checks and its host's suites.

Round 3 re-runs the same 24 pairs. It reports per stack how often Exact2 is cheaper, faster and
preferred at once, with the backend pairs apart.
