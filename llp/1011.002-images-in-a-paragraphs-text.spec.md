## Summary

An `image` may be a child of a `text` paragraph, between its runs, as an
`<img>` is in a `<p>`: it takes a box in the line where it stands, lines
break around it, a line grows to hold it, and `vertical-align` places it
against the baseline. A screen reader reads its `aria-label` in the
paragraph's words, and a copy of the text carries the label in its place.

```text
text
  text "Ferris "
  image emoji.src width="1.375em" height="1.375em" object-fit="contain" vertical-align="middle" aria-label=":ferris:"
  text " approves."
```

## D1. Contract

An `image` is admitted as a paragraph's own child, through `if` and `for`
as runs are, and the kernel takes only such a child as a run; an image inside a nested `text` run is `lower-leaf-children`.
`vertical-align` is admitted on such an image alone (`lower-attr-tag`
elsewhere). It takes `baseline` (the initial value), `middle`, `text-top`,
`text-bottom` or a length (`-0.2em`, `3px`); `sub`, `super`, `top`,
`bottom`, `center` and percentages are `lower-css-shorthand`. A choice of
literals is admitted; the JS target refuses a computed one, which no
single CSS declaration expresses (D3). A literal percentage `width` or
`height` and the min and max sizes are `lower-attr-value` on such an image
(D2 reads lengths alone), and an image in a multi-column `text`
(`columns`, `column-count` or `column-width` on it) is `lower-attr-tag`.

## D2. The kernel

An image in a paragraph's text is no layout box of its own. Its paragraph's
runs hold it as one run whose text is U+FFFC (`INLINE_BOX_TEXT`) and whose
`inline` is the box to reserve (`InlineBox`): its margin box, from its rows
as CSS sizes an inline replaced element. A length `width` or `height` is
the content box's (the border box's under `box-sizing: border-box`); an
`auto` one follows the other by `aspect-ratio`, else the natural ratio,
else is the natural size, else zero, as an `<img>` is before it loads. A
`display: none` image is no run.

The measurer reserves the box where its run stands, breaks lines around it,
and grows the line box to hold it (CSS 2 §10.8). When the kernel publishes
the paragraph's frame it asks the measurer where each box went
(`TextMeasurer::inline_boxes`: each margin box's top left in content
coordinates, in run order, at the paragraph's content width) and gives the
image that frame, less its margins. A box on no line (one `line-clamp` cut)
is answered as not a number, and its image gets an empty frame; a measurer
that answers nothing leaves each image at the content box's origin. A new
natural size, a change to the image's rows, or an environment change its
size reads (`vw`, `env()`) measures the paragraph again.

## D3. `vertical-align`

CSS Inline 3 makes `vertical-align` a shorthand of `alignment-baseline`
and `baseline-shift`, and so do the rows: `vertical_align` (the keyword)
and `baseline_shift` (the length, which the kernel resolves from `em` as
any length row). The box's top stands this far above the baseline, by the
font of the image's parent, the paragraph (CSS 2 §10.8.1; its own `em`
lengths still read its own font), in the same arithmetic on every host
(`InlineBox::ascent`): its height for `baseline`; half its height plus half
the x-height for `middle`; the font's ascent for `text-top`; its height less
the font's descent for `text-bottom`; then raised by the length. The web writes the
two rows as one `vertical-align` declaration.

## D4. Reading and copying

The paragraph's text, as read, takes each image's `aria-label` in its run's
place (`NodeRef::read_runs`; empty without one), and the image is hidden as
an element of its own, so it is read once, in order. Where a host copies a
paragraph's selection (macOS and iOS), each U+FFFC in it is copied as that
label.

## How each host draws it

- **Web** (the JS and wasm targets). The browser lays the paragraph out:
  the image is its `<img>`, inline in the paragraph (the page's sheet makes
  a paragraph's `img` inline where every other is a block), its rows as CSS.
- **Apple.** The run is U+FFFC with a `CTRunDelegate` of the box's width,
  ascent and descent, and no ink; the line box includes the box
  (`InlineBox.lineBox`). The paragraph op carries the run's box
  (`inlineBox`), so what is painted is what was measured. The image is its
  own view, a subview of the paragraph's, at the frame the kernel placed:
  it loads, decodes, animates and fits as any image does (LLP 1011,
  LLP 1011.000). `exact_set_inline_boxes` answers D2's question from the
  paragraph the presenter paints.
- **Linux, Windows and Android.** The run is a Parley inline box (Parley
  patch 17 exposes a line's items in order, so the glyphs after a box are
  placed past it); the host's line box grows to hold it. The image paints in
  the tree walk at its frame. A remote emoji loads as any remote image does
  (LLP 1011 §2); a GIF one draws nothing on Linux and Windows, which decode
  no GIF.
- **Terminal.** The rows are not admitted in a terminal entry.

## Not built

- Percentages and the min and max sizes of an image in text; `zoom`.
- An image in a nested run (D1), in a content region (its frame is not
  placed), in text that flows around exclusions (where it went is not
  asked, so the image shows nothing; only Apple reserves its box there), or
  in a
  `text-fit` paragraph (its box keeps its size when the text shrinks).
- macOS's region reader (a paragraph of 64 KB or more, LLP 1072) measures
  the box's U+FFFC as a glyph.
- A computed percentage `width` or `height` (D1 refuses a literal one) is
  read as `auto` off the web.
- A paragraph that is a flex container whose free space moves its lines
  (`text_line_offset`): its images stay at the lines' unmoved place.
- `text-overflow: ellipsis` on one line: where the ellipsis is drawn over
  an image, the image still shows. On Linux, an image after a clamped
  line's last kept glyph goes with the glyphs its ellipsis replaced.
- A copy from a virtualized list on macOS takes an image's label in its
  place, but the selection's offsets there count it as one character.
