## Summary

`@exact/camera` shows the camera and takes a photo, on the web, iOS,
macOS and Android first, with every other target of LLP 1133 D8 a visible
`later` or `absent`. Its tier 1 is the web's: Media Capture's
`getUserMedia({video})` opens a camera and answers a stream of tracks, a
viewfinder shows a track as `<video srcObject>` does, and Image Capture's
`takePhoto` takes a still from it:

```
use getUserMedia, applyConstraints, stopTrack, MediaStream,
  MediaTrackConstraints from "@exact/media-capture"
use takePhoto, Photo from "@exact/camera"

state track = ""
state facing = "environment"
state photo = "assets/sample.jpg"
mutation opened as shape MediaStream then show
mutation shot as shape Photo then taken

action open
  send opened = getUserMedia(video=MediaTrackConstraints(facingMode=facing))
action show
  match opened
    case some(s)
      track = s.tracks[0].id
    case none
      track = ""
action flip
  applyConstraints(track=track, facingMode=(facing == "environment" ? "user" : "environment"))
  facing = (facing == "environment" ? "user" : "environment")
action shutter
  send shot = takePhoto(track=track, fillLightMode="auto")
action taken
  match shot
    case some(p)
      photo = p.path
      stopTrack(track=track)
    case none
      photo = photo
view
  exact-camera srcObject=track width="100%" flex=1
```

```ts
import { takePhoto } from "@exact/camera";

// `track` is the id the Contract opened and passed to this source.
const p = await takePhoto({ track, apple: { photoQualityPrioritization: "speed" } });
return fetch(`${api}/upload`, { method: "PUT", exactBodyFrom: p.path });
```

Tier 2 reaches AVFoundation's photo settings and device types and
CameraX's capture and flash modes. Tier 3 hands the app's Swift the
`AVCaptureSession` inside its configuration, the `AVCaptureDevice`, the
photo output and each capture's settings, and its Kotlin the CameraX use
cases before they are bound and the `Camera` after.

The camera is the first module to need four things, each decided here for
every module after it:

- **A package carries a view.** `exact-camera` is the package's, on each
  host, and reaches the same implementation instance as the package's
  calls (D8 item 1).
- **A video track is a capture graph, not a stream of frames.** On Apple
  and Android a preview and a photo are outputs attached to the platform's
  capture session, not consumers of buffers. The track table LLP
  1133.009 D3 gives packages carries, for a video track, the platform's
  way to attach one, and the physical outputs are the process's, shared
  by every session's leases (D3).
- **A camera with nothing to show stops.** A video track whose viewfinder
  is not displayed, by the rule `wakelock` already uses (LLP 1125 D11),
  and which nothing else consumes, releases its device and reads `muted`
  until one is displayed again (D3). An app that forgets to stop its
  track, or leaves its screen by a gesture no action hears, does not leave
  the camera on; and showing the viewfinder again is a capture start,
  which a tool or a wake cannot make (D6).
- **A module's Android code may need a Jetpack library.** CameraX is how
  Android recommends a camera be built; its AndroidX must be the one the
  host already resolves for Compose, so an implementation's Maven
  libraries join one locked, verified Gradle graph (D8 item 5).

The consumer is the photo editor (`apps/photo-editor`), which today edits
one fixed image through its own module. With this one it takes a photo and
then edits it: a standard module beside an app's own (§10).

## 1. What exists

**The photo editor** (LLP 1024) is one app native module, `<photo-editor>`,
on the web, macOS and iOS: UIKit and AppKit gesture recognizers and the
web's Pointer Events over one image, whose `photo` prop is a path under
the app's assets (`modules/apple/PhotoEditor.swift`, `loadPhoto`;
`modules/web/index.js`, `setPhoto`). It has no `app.ts`; its Rust data
crate answers nothing and grants nothing. It has no Android crate.

**Views in an app's module.** On Apple a view is a factory in the app's
`ExactModule.views` (`host/apple/modules/ExactNativeModule.swift`); the
build reads the roster from the compiled module (`host/apple/build.mjs`,
the roster probe) and puts a `firstFrame` tag in the first frame. On the
web the app's `modules/web/index.js` exports `roster` and its classes, and
the host defines the custom elements. On Android the app's
`modules/android` defines `exact.app.Modules` with a `NativeModules`
roster; a hosted view takes `performClick()` only: "native drags,
arbitrary pointer forwarding … are not implemented"
(`host/android/README.md`). A native view's props are strings, and its
events are `load`, `change`, `input`, `message` and `press`
(`docs/recipes/native-views.md`).

**The package seam** as geolocation built it and LLP 1133.004, 1133.006
and 1133.009 extend it: an Apple implementation is a class with
`init(changed:agent:log:)`, `later`, `call` and `release`, composed into
the app's module by an adapter the build writes, made once a session at
its first request (`ExactExtensions.swift`); an Android one subclasses
`ExactExtension`; a web one exports `implementation({changed})`. An
implementation's `exact.json` already has a `views` field (LLP 1133.001
D1), which nothing reads: `packages/geolocation` declares `"views": []`,
and the adapter has no views.

**Tracks.** LLP 1133.003 D2 made a video track a host-owned object named
by id, shown by `video srcObject=`. LLP 1133.009 D3 puts Media Capture's
surface in one interface,
`@exact/media-capture`, the only package that opens an input, with one
capture per device for the process, leases per session, tracks in a
per-session table every package reaches, and no re-export; it leaves the
video half to the camera. This RFC agrees with its names, shapes, leases,
table and grants, and adds what video needs (D1, D3).

**The grant** `device.camera` is a row of `runner/src/device.rs`, with
`NSCameraUsageDescription` on iOS and macOS, the hardened-runtime
entitlement `com.apple.security.device.camera` and `Permissions-Policy:
camera`; it has no Android column.

**`rules/DEFERRED.md`** moved "No camera anything" on 2026-10-02: a camera
is a native module with a preview and start, stop, capture and flip,
gated by `device.camera`, with an agent substitute, web, iOS and macOS
first; "not a built-in tag"; video recording and barcode or document
scanning stay out. `input capture` stays refused. This RFC is that entry,
as a standard package rather than an app's module (§14 question 7).

## 2. Tier 1

### D1 — Media Capture's video, Image Capture's photo, a viewfinder

The camera's names, and the shared surface's that it uses, which an app
imports from `@exact/media-capture` (LLP 1133.009 D1 and D3):

| Name | Declared by | Kind | Web | Contract |
|---|---|---|---|---|
| `getUserMedia(video=…)` | media-capture | send; a request | `navigator.mediaDevices.getUserMedia({video})` | `send s = getUserMedia(video=true)` |
| `applyConstraints(track=, …)` | media-capture (added here) | send, answers nothing | `track.applyConstraints(…)` | statement |
| `stopTrack(track=)` | media-capture | send, answers nothing | `track.stop()` | statement |
| `setTrackEnabled(track=, enabled=)` | media-capture | send, answers nothing | `track.enabled = …` | statement |
| `mediaStreamTrack(track=)` | media-capture | live source; a fact | the track's attributes, `getSettings()`, `getCapabilities()` | `resource t = mediaStreamTrack(track=id)` |
| `enumerateDevices()` | media-capture | live source; a fact | `enumerateDevices()`, re-read at `devicechange` | `resource d = enumerateDevices()` |
| `cameraStatus()` | media-capture | live source; a fact; `sync` | `"mediaDevices" in navigator`, `permissions.query({name: "camera"})` | `resource c = cameraStatus()` |
| `takePhoto(track=, …)` | camera | send | `new ImageCapture(track).takePhoto(settings)` | `send p = takePhoto(track=id)` |
| `getPhotoCapabilities(track=)` | camera | live source; a fact | `new ImageCapture(track).getPhotoCapabilities()` | `resource c = getPhotoCapabilities(track=id)` |
| `exact-camera srcObject=` | camera | a view | `<video srcObject autoplay playsinline muted>` | `exact-camera srcObject=track` |

Data code calls every name but the view through its generated binding, in
Promise form (LLP 1133 D6).

**Values.** The shared shapes are LLP 1133.009 D1's; video adds:

| Shape | Fields |
|---|---|
| `MediaTrackConstraints` (video members) | `deviceId`, `groupId`, `facingMode`, `width`, `height`, `aspectRatio`, `frameRate`, `resizeMode` (Media Capture §4.3.8); `zoom`, `torch` (Image Capture §10, the two of its constrainable properties a phone's camera commonly has; a camera without one lists none in its capabilities) |
| `MediaTrackSettings` (video members) | the same names, each what the track applied |
| `MediaStreamTrack` (added) | `capabilities: option<MediaTrackCapabilities>`, the ranges and lists `getCapabilities()` gives for the members above (`zoom` a `{min, max, step}`, `torch` a bool, `facingMode` a list); absent on an audio track. `muteReason` is LLP 1133.009 D1's one enum, `option<enum<idle|interrupted|background|silenced|in-use|multitasking|system-pressure>>`; a video track reads every value but `silenced` |
| `MediaDeviceInfo` (video) | `kind` `videoinput`, and `facingMode: option<string>`, folded from `InputDeviceInfo.getCapabilities()` |
| `CameraStatus` | `available`, `state` (`granted`, `prompt`, `denied`, `unknown`), `apple`, `android` |
| `PhotoCapabilities` | `redEyeReduction` (`never`, `always`, `controllable`), `imageWidth`, `imageHeight` (`{min, max, step}`), `fillLightMode` (a list of `auto`, `off`, `flash`) |
| `Photo` | `path`, `type`, `size` (bytes), `width`, `height` (as the image is shown, its orientation applied) |

`facingMode` takes Media Capture's `user`, `environment`, `left` and
`right` ([VideoFacingModeEnum](https://www.w3.org/TR/mediacapture-streams/#dom-videofacingmodeenum)).
`takePhoto`'s options are `PhotoSettings`' `fillLightMode`, `imageWidth`,
`imageHeight` and `redEyeReduction`
([PhotoSettings](https://w3c.github.io/mediacapture-image/#dictdef-photosettings)),
and `path`.

**Errors** are the specifications' `DOMException` names, as LLP 1133.009
D1 answers them: `NotAllowedError` (denied, or a caller the origin rule
refuses, with `message` `person-required`, §6), `NotFoundError` (no
camera, or a track id the session does not hold), `NotReadableError` (the
platform would not give the camera: another app holds it, the hardware
failed), `InvalidStateError` (`takePhoto` on a track that is ended,
muted or disabled, or that no viewfinder shows, as Image Capture rejects
a track that is not live), `NotSupportedError`
(a target without an implementation, a `kind` `audio` track given to a
camera name), `AbortError`, `UnknownError` (a capture the platform failed,
[takePhoto](https://w3c.github.io/mediacapture-image/#dom-imagecapture-takephoto)).

**Declared deviations,** each with its reason:

- **Objects are ids** (LLP 1133.009 D1): a stream and a track are named by
  id. There is no `ImageCapture` object: `takePhoto(track=)` is its
  constructor and `takePhoto()` in one call, as `startMediaRecorder` is.
- **A photo is a file, not a `Blob`.** `takePhoto` writes the image to an
  `app:/` path and answers it. With `path` written, the module writes
  there, admitted against the calling source's `fs.write` (LLP 1133.009
  D10 item 4), and adds the extension of the format it wrote. Omitted, it
  writes `app:/tmp/camera/<n>.<ext>`, as a picked file lands in
  `app:/tmp/picked/` with no grant (LLP 1069.010). The file then shows in
  an `img`, uploads with `exactBodyFrom`, shares and shrinks with
  `compressImage` by its path. Reason: a photo is megabytes, which
  neither a Contract value nor a native module request (4 MiB, LLP
  1133.006 D8) carries.
- **`applyConstraints` may change the camera.** Writing `deviceId` or
  `facingMode` moves the track to another camera under the same id,
  where a page stops its track and asks again. Reason: on Apple and
  Android a hand-built app flips by replacing the session's input, with no
  second prompt and no new stream; on the web the implementation stops the
  browser's track and opens the other camera, under the module's id (D3).
- **Constraints are bare values,** which Media Capture treats as `ideal`
  (LLP 1133.009 D1); `exact` and `OverconstrainedError` wait for a
  consumer.
- **A track with nothing to show is muted** (D3): `muteReason` `idle`.
  Media Capture leaves a track running until `stop()`.
- **`takePhoto` needs a track that is shown.** A muted track, `idle`
  included, rejects with `InvalidStateError`. Reason: the person sees what
  is taken, and the platform's exposure and focus have converged on the
  frames the viewfinder showed; a hidden capture is tier 3.
- **The viewfinder is a view of the package's, not `video srcObject=`.**
  On the web the two are one element. On Apple the viewfinder is an
  `AVCaptureVideoPreviewLayer` attached to the capture session
  ([AVCaptureVideoPreviewLayer](https://developer.apple.com/documentation/avfoundation/avcapturevideopreviewlayer)),
  and on Android CameraX's `PreviewView` bound as a `Preview` use case:
  zero-copy, rotated by the platform, mirrored for a front camera, and
  where the platform's own gestures attach. A `video` shows a track's
  frames, which LLP 1133.003's door would have to receive one by one; a
  camera track in `video srcObject=` waits for a consumer that needs its
  frames (effects, composition) and for that door to be public (§12).

`getUserMedia` with both `video=` and `audio=` opens one stream with a
track of each kind, asking both decisions as LLP 1133.009 D3 says. Its
audio track is that RFC's microphone capture, holding its audio-session
claim (LLP 1133.009 D7); the camera's capture session takes no audio
input. Recording that stream as video, and where its sound comes from,
wait for video recording (§12). A disabled video track
(`setTrackEnabled(enabled=false)`) shows black in its viewfinder and
keeps its lease, as on the web; `takePhoto` on it rejects
`InvalidStateError`.

A written `object-fit` maps to the preview layer's gravity (`contain`,
`cover`, `fill` to `resizeAspect`, `resizeAspectFill`, `resize`) and to
`PreviewView`'s scale type. The gestures are the viewfinder's words
`tapToFocus` and `pinchToZoom`, named after CameraX's `CameraController`
switches; an author who writes `false` turns one off (author > platform).
A pinch changes the track's `zoom`, which `mediaStreamTrack` reports.

Where a platform reports no position for a camera (most Mac cameras),
`facingMode` is absent from its settings, as a browser on a Mac reports
none.

## 3. Tracks and what consumes them

### D3 — One capture per camera, leased; outputs attached; the camera runs while it is shown

LLP 1133.009 D3 gives the shape: `@exact/media-capture` is the only
package that opens an input; it keeps one capture per device for the
process and gives each session **leases**; a track is a host-owned object
in a per-session table; the lease that opens a capture configures it. The
camera takes that shape whole and adds what video needs.

**A video consumer attaches an output; an audio one subscribes.** On
Apple and Android the preview and the photo are outputs of the platform's
capture graph, not readers of frames, so a video track's entry in the
table offers an attach point beside `subscribe(buffer:, muted:, unmuted:,
ended:)` (LLP 1133.009 D10 item 6):

- **Apple.** A capture is an `AVCaptureSession` (one for the process on
  iOS, one per open camera on macOS, below), with a serial queue it is
  configured and started on: `startRunning` blocks,
  and Apple says to "start the session on a serial dispatch queue so that
  you don't block the main queue"
  ([AVCaptureSession](https://developer.apple.com/documentation/avfoundation/avcapturesession)).
  The entry offers `configure { session in … }`, run on that queue between
  `beginConfiguration()` and `commitConfiguration()`, which adds and
  removes **inputs and outputs only**. A preview layer is a `CALayer` and
  is attached on the main thread by the viewfinder, outside `configure`;
  main never waits on the session queue. The session is made with
  `automaticallyConfiguresApplicationAudioSession` false, as LLP 1133.009
  D3 requires.
- **Android.** The capture is CameraX's `ProcessCameraProvider` with one
  lifecycle owner the implementation drives. A consumer adds and removes
  a use case (`Preview`, `ImageCapture`, a tier 3 `ImageAnalysis`), and the
  implementation binds the whole set in one `bindToLifecycle` call on the
  main thread, since CameraX binds use cases together and one lifecycle's
  set is what runs
  ([CameraX architecture](https://developer.android.com/media/camera/camerax/architecture)).
- **Web.** The entry is the page's `MediaStreamTrack`, which `<video>` and
  `ImageCapture` take as they are.

**Physical outputs are the process's, one per capture, multiplexed.** A
capture session takes one `AVCapturePhotoOutput`, and one lifecycle's
use-case set has one `ImageCapture` and one `Preview`. So the camera
package keeps, beside each session's instance, a process object: one
photo output (one `ImageCapture`) per capture, attached while any lease
on that capture is live, which takes every lease's `takePhoto` in the
order they arrive and returns each photo to the session that asked.
Viewfinders: on Apple each displayed viewfinder has its own
`AVCaptureVideoPreviewLayer` on its camera's session; on Android the one
`Preview` shows in the most recently displayed viewfinder, and another
displayed at the same time shows its empty box and is no consumer, a
declared difference (D10).

**Two objects, never one, and who keeps what.** Media-capture's
per-session table keeps the session's tracks and their leases (LLP
1133.009 D3). A session's camera instance (the adapter its views and calls
share, D8 item 1) keeps that session's viewfinders and photo requests.
The process objects (media-capture's captures, the camera's photo
outputs) are reached through the track table, never through a session's
instance, so the first session's end does not take a capture from the
second. At a session's end the host calls `destroy` on the session's
instances (LLP 1133.009 D10 item 1), which ends its tracks and so its
leases; a capture stops when no lease on it is live.

**Who consumes, and who only reads.** A video track's consumers are the
viewfinders whose `srcObject` names it while they are displayed (on
Android, the one showing the `Preview`), a `takePhoto` in flight, and an
output attached through a hatch that declares itself a consumer (D5). A
viewfinder is displayed by `wakelock`'s function
(`runner/src/wakelock.rs`, `displayed`): it is hidden when it or an
ancestor is `display: none`, when its host covers its slot whole, or when
its navigation root hides its route; a screen a sheet covers stays shown.
The fact sources (`mediaStreamTrack`, `enumerateDevices`, `cameraStatus`,
`getPhotoCapabilities`) are readers, not consumers: their last reader's
`release` (LLP 1133.002 D5) stops nothing and ends no track. A change of
consumers announces `mediaStreamTrack`, so its readers are asked again.

**A lease is held while the track has a consumer.** A track opened by
`getUserMedia` takes its lease when its first consumer appears and
releases it when its last goes, reading `live`, `muted`, `muteReason`
`idle` meanwhile (LLP 1133.009 D6 takes this rule for a microphone, and
the agreement at the end of this section says which consumer reopens an
idle track).
Releasing the last lease on a capture stops its camera: Apple removes
the input and stops the capture session; Android unbinds the set; the
web calls `stop()` on the browser's track, since `enabled = false` leaves
a browser free to keep the camera and its indicator on
([enabled](https://www.w3.org/TR/mediacapture-streams/#dom-mediastreamtrack-enabled)),
and opens the camera again under the module's id when a consumer returns.

Reasons, in order:

1. **The platform's practice.** A hand-built camera screen starts its
   capture session when it appears and stops it when it disappears, the
   pair UIKit's `viewWillAppear` and `viewWillDisappear` invite, and
   CameraX stops a camera when the lifecycle it is bound to stops. A
   camera left running behind another screen keeps the system's camera
   indicator on, which a person who knows the platform notices.
2. **Otherwise every way a screen leaves needs its own stop.** A sheet
   dismissed by a swipe, a tab switched, a screen popped by the system's
   back gesture, a window closed: an app that stops its track in actions
   must pair each with one, and one missed leaves the camera on. The
   runner already knows which nodes are displayed.
3. **A track keeps its grant and id.** The app's state does not change
   when the viewfinder hides; showing it again shows the camera again.

**Taking a lease is a capture start** (§6): it carries an origin, and a
tool's or a wake's is refused. The origin is that of the commit that made
the viewfinder a consumer, by displaying it or by binding its `srcObject`
to the track: the runner reports each change of either with the origin
of the commit that made it (D8 item 2), keeps that origin, and admits the
lease with it. A viewfinder displayed or rebound by a tool invocation's
or a wake's commit takes no lease, and its track stays `idle` until a
commit of a person's input or the app's own foreground code makes a
viewfinder of it a consumer. A lease taken later because another lease
ended (below) carries the kept origin.

**How many captures.** As LLP 1133.009 D3 rules, the lease that starts a
capture chooses its camera and constraints; a later lease on that camera
gets it as it is, and its `settings` say what applied.

- **iOS and Android: one capture for the process.** They run one camera
  at a time in one app
  ([AVCaptureMultiCamSession](https://developer.apple.com/documentation/avfoundation/avcapturemulticamsession)
  is the exception, §12). A lease that wants another camera while one is
  live waits: its track reads `muted`, `muteReason` `in-use`, and takes
  its lease when no other is live, if it still has a consumer. (A phone
  has several cameras and runs one, so a video track waits where LLP
  1133.009 D3 fails a second microphone with `NotReadableError`; §11.) A
  track's own `applyConstraints` that moves it to another camera
  reconfigures the capture when its lease is the only live one; otherwise
  the change is refused (`NotReadableError`, journaled, the settings
  unchanged).
- **macOS and the web: one capture per open camera,** each with its own
  photo output (on macOS its own `AVCaptureSession`), so two tracks on two
  cameras run at once there, where the browser and the device allow it
  (WebKit on iOS ends the first camera's track when a page opens another,
  [WebKit bug 264288](https://bugs.webkit.org/show_bug.cgi?id=264288#c2),
  which is the platform ending a track, below).

**Lifetimes.** As LLP 1133.009 D6: streams and tracks belong to the
session, outlive the answer that opened them, and end at `stopTrack`, when
the platform takes the camera away (`readyState` `ended`), and at session
end. A `takePhoto` in flight is a consumer, so its lease, and the capture
under it, stay until the photo returns, also through `destroy`, which
waits for it within LLP 1133.009 D10 item 1's bound. If the bound passes
first, the capture is abandoned, the send fails `AbortError`, and the
consumer is dropped so the lease can end: a still has no partial file.

**Agreement with recording.** This RFC and LLP 1133.009 agree on the
shared surface, `@exact/media-capture`: its names, imported from it with
no re-export and pinned exactly; the shapes, `muteReason` one enum; one
capture per device for the process, configured by the lease that opens
it; leases per session, held while a track has a consumer and taken with
the origin of the commit that made the consumer; one per-session track
table with `subscribe(buffer:, muted:, unmuted:, ended:)`; handles and
their disposal; the two grants, per name and per argument; capture starts
declared `"origin": "app"` and `"foreground": true`, refused to a tool
invocation and a wake in every state and to an app in the background; and
the audio session the host's, which no capture session configures. They
differ by kind where each says why: a second camera waits `in-use` where a
second microphone fails (above). One rule says what reopens an idle track:
a consumer that shows the capture. A viewfinder shown again, by the
person or by the app's own code, takes the camera back; that is a capture
start, admitted with the origin of the commit that displayed it. A
microphone has nothing on screen that shows it, so a level reader
arriving at an idle track opens nothing, and the microphone reopens only
at an explicit start, `startMediaRecorder` or
`setTrackEnabled(enabled=true)` (LLP 1133.009 D6). A tool invocation's or
a wake's commit reopens neither.

**Interruptions.** The platform's reason becomes `muteReason`: Apple's
`videoDeviceNotAvailableInBackground` is `background`,
`videoDeviceNotAvailableWithMultipleForegroundApps` is `multitasking`,
`videoDeviceInUseByAnotherClient` is `in-use`,
`videoDeviceNotAvailableDueToSystemPressure` is `system-pressure`, any
other `interrupted`
([InterruptionReason](https://developer.apple.com/documentation/avfoundation/avcapturesession/interruptionreason)).
For the background, Apple preserves a session's `startRunning` and runs
it again when the app returns to the foreground
([videoDeviceNotAvailableInBackground](https://developer.apple.com/documentation/avfoundation/avcapturesession/interruptionreason/videodevicenotavailableinbackground)),
which is the person returning to the app, so the implementation lets it;
after the other reasons it restarts the session at
`interruptionEndedNotification` only while a lease is live. Android's
lifecycle stop is `background`, and `CameraState`'s errors map the same
way. The web reports `muted` with no reason a page can read; the
implementation gives `interrupted`.

**Threads.** Every entry into a package is on the main thread (LLP
1067.000 D4). Inputs, outputs, `startRunning` and `stopRunning` are on the
session queue, which never waits on main; main never waits on it. A
photo's delegate callbacks arrive on the queue the platform chooses; the
implementation writes the file off the main thread and replies on main.

captures.

## 6. Permission

### D6 — LLP 1133.002 §4, with LLP 1133.009's rule for capture

**Declare.** `device.camera <purposeKey>`. The row gains its Android
column: `android.permission.CAMERA`, and `required="false"` features for
`android.hardware.camera.any`, `android.hardware.camera`,
`android.hardware.camera.autofocus` and `android.hardware.camera.flash`.
`CAMERA` implies the back camera and autofocus as required features,
which filters the app from a device without them; declaring each one
with `required="false"` undoes that
([uses-feature](https://developer.android.com/guide/topics/manifest/uses-feature-element#permissions)).
Derived otherwise: iOS and macOS `NSCameraUsageDescription`, whose text
the prompt shows (and without which "attempting to start a capture
session … raises an exception",
[requestAccess](https://developer.apple.com/documentation/avfoundation/avcapturedevice/requestaccess(for:completionhandler:)));
macOS `com.apple.security.device.camera`
([entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.device.camera));
the web's `Permissions-Policy: camera=(self)`. The grant is required per
name and per argument (LLP 1133.009 D10 item 9): `video=` and every name
of `@exact/camera` need `device.camera`, and a bake that finds one without
the line refuses (`grant-missing`).

**Read.** `cameraStatus().state`:

| Platform state | `state` |
|---|---|
| Apple `AVCaptureDevice.authorizationStatus(for: .video)` `notDetermined` | `prompt` |
| Apple `authorized` | `granted` |
| Apple `denied`, `restricted` | `denied` |
| Android `CAMERA`, by LLP 1133.002 D8's history | as geolocation's |
| web `permissions.query({name: "camera"})` | the same word; `unknown` where the browser rejects the name (Chrome 64, Firefox 132 and Safari 16 accept it, by MDN's compatibility data) |

The Android history moves from geolocation's implementation into the
host's `ExtensionContext`, so every module reads one (D8 item 7). Safari
asks again in a later visit by default, so its state reads `prompt` again;
that is the browser's, and the status says it.

**Ask.** `getUserMedia(video=…)` is the request. While `prompt` it asks
through `AVCaptureDevice.requestAccess(for: .video)`,
`Activity.requestPermissions`, or the browser's own. One request at a
time, through LLP 1133.002 D9's queue. Explain and recover as LLP
1133.002 D11 says, with `openURL("app-settings:")`. On the web a lease
taken again after `idle` reopens the browser's camera (D3); a browser
that kept the grant shows nothing, and one that did not asks again, so
taking a lease there is a request too, admitted as one.

**Who may capture.** LLP 1133.009 D9's rule, which LLP 1133 D6 rule 3
already names for capture: a capture start is refused to a tool
invocation and to a wake in every state, granted included
(`NotAllowedError`, `person-required`), and to an app in the background
(`NotAllowedError`). The capture starts are:

- `getUserMedia(video=…)`;
- `takePhoto`;
- a lease taken by a viewfinder, from `idle` or `in-use`, with the origin
  of the commit that made it a consumer (D3);
- `setTrackEnabled(enabled=true)` on a video track;
- `applyConstraints` that moves a track to another camera, since the next
  lease would capture through it.

Each is declared `"origin": "app", "foreground": true` (LLP 1133.009 D10
item 8). A tool may stop a track, disable it, change constraints that
keep the camera (`zoom`, `torch`, size) and read every fact. Any of the
app's own code in a foreground session may start a capture: a person's
press, or a `task` that counts down a self-timer.

Both are extensions (LLP 1133 D5): a camera is an object with a view and

roster put the camera in wave 1 (LLP 1133.000 §4). An app depends on both

is no re-export (LLP 1133.009 D3).

The camera's interface, abridged, in LLP 1133.002 D13's form with LLP
1133.009 D10's additions:

```json
{
  "kind": "interface", "name": "@exact/camera", "version": "1.0.0",
  "uses": "@exact/media-capture@1.0.0",
  "substitute": "implementation",
  "views": {
    "exact-camera": { "props": { "srcObject": { "type": "handle<track>", "binds": true },
      "object-fit": "option<string>", "tapToFocus": "option<bool>",
      "pinchToZoom": "option<bool>" },
      "events": ["load"], "displayed": true }
  },
  "names": [
    { "send": "takePhoto", "grants": ["device.camera"],
      "origin": "app", "foreground": true,
      "options": { "track": "handle<track>",
        "fillLightMode": "option<enum<auto|off|flash>>",

```

`load` fires when the viewfinder shows its track's first frame.

item 2). `picture` is a name only the agent sets (§9).

### D8 — Seam additions

Beside LLP 1133.009 D10's twelve, which this package uses as they are
(the orderly end, the foreground, a path to write, the track table,
origin and foreground admission, grants per argument, handles, preferred
values reaching an implementation, readers released by their arguments),
the camera needs these. Each is
general, and each is proved by the out-of-tree fixture before this
package uses it (LLP 1133.001 D8):

1. **A package carries a view, and the view reaches its session's
   instance.** An interface declares each tag, its props and events; an
   implementation serves it. Today a view factory receives the app's
   `ExactModule` (`host/apple/modules/ExactNativeModule.swift`), and the
   extension adapters are a separate per-session map
   (`ExactExtensions.swift`); on Android `Extensions.made` holds one
   `ExactExtension` per process and hosted views come from
   `exact.app.Modules`, another registry. So: on Apple the implementation
   class gains `views`, the adapter the build writes joins them to the
   roster the build probes (`host/apple/build.mjs`), and a package view's
   factory receives that session's adapter, made at the view's creation if
   no call made it first. On the web the implementation's module exports
   `roster` and the view's class, which receives the session's
   implementation. On Android the `ExactExtension` builds its own hosted
   views, given the session they belong to, and keeps its per-session
   state by session. A package view is never a first-frame tag: the
   package's code loads after first pixel (`rules/RULES.md`, the boot
   path). **Tags are declared, not imported.** A custom element's name is
   one per document on the web
   ([CustomElementRegistry](https://html.spec.whatwg.org/multipage/custom-elements.html#customelementregistry)),
   and a tag is not a Contract name `use` takes; the bake finds a tag in
   the interfaces the app depends on directly, as it finds the app's own
   in `app.json` `modules`, and refuses one declared twice
   (`bake-view-twice`, naming both packages) or by no one
   (`bake-view-unknown`, naming the line `exact add` writes).
2. **A view hears whether it is displayed, and who made it so.** For a
   view declared `"displayed": true`, the runner reports each instance's
   displayed state by `wakelock`'s function when it changes, and each
   change of a prop the declaration marks as binding a device
   (`"binds": true`; `srcObject` here), with the origin of the commit that made the change
   (LLP 1133.002 D12), through the instance (`displayed(view, shown,
   origin)`, `bound(view, prop, origin)`), on native hosts and in the web
   JS runtime. Today a prop change reaches a view with no origin
   (`setProps`). The runner keeps the origin it reported, and a device
   acquisition that follows (D3's lease) is admitted with that kept
   origin, never one the implementation passes back. A map that pauses its tiles and
   a decoder that pauses its work read the same report.
3. **A video track's attach point** (D3): the track table's entry for a
   video track exposes `configure` (inputs and outputs, on the session
   queue) on Apple, the use-case set on Android, the `MediaStreamTrack`
   on the web; a consumer count the lease follows; and process objects
   of a package (the camera's photo output) reached through the table.
4. **Writes to `app:/tmp/<extension>/` with no grant,** for a file the
   module makes and names, as the picker writes `app:/tmp/picked/`;
   announced with `changed("app:/tmp/…")` as `wrote` announces an app's
   write. A written `path` is LLP 1133.009 D10 item 4's.
5. **An Android implementation names Maven coordinates, and one Gradle
   graph resolves them.** CameraX is several artifacts whose dependencies
   (`androidx.lifecycle`, `androidx.core`, `androidx.appcompat`,
   `androidx.fragment`, Guava's `listenablefuture`, `kotlinx-coroutines`,
   Dagger) overlap Compose's
   ([camera-core 1.6.2](https://dl.google.com/android/maven2/androidx/camera/camera-core/1.6.2/camera-core-1.6.2.pom),
   [camera-view 1.6.2](https://dl.google.com/android/maven2/androidx/camera/camera-view/1.6.2/camera-view-1.6.2.pom)),
   and the Android project already resolves Compose through Gradle for
   any app with a date or time control (`host/android/app/build.gradle.kts`,
   `-Pcompose=1`). A pinned file closure beside that graph would carry
   two AndroidX, and an app with a camera and a date picker would not
   build. So the implementation's `exact.json` names coordinates on Google
   and Maven Central (`"maven": ["androidx.camera:camera-camera2:1.6.2",
   …]`), the one Android project resolves them with the host's own
   AndroidX in one graph, and the graph is held by Gradle's dependency
   locking and dependency verification (checksums), whose files the build
   keeps beside the app's other locks; the build refuses, by name, an
   artifact the lock or the verification file does not name.
   An implementation adds no repository and no plugin. This amends LLP
   1133.001 D9's "neither SwiftPM nor Gradle resolves anything for a
   module" for Android's Maven libraries, and leaves D9's pinned
   `artifacts` for a library that is not on those repositories (§14
   question 4).
6. **An Android hosted view takes touches.** The reader forwards a
   pointer sequence that lands on a hosted view and no exact2 gesture
   claims to that view, as UIKit and AppKit deliver to a native view's
   recognizers. The viewfinder's tap and pinch need it, as a map's pan
   will. Until it lands, Android's viewfinder has no gestures, recorded
   as a tell in D10.
7. **One Android permission history,** in the host's `ExtensionContext`
   rather than each implementation's preferences (D6).
8. **Hatches off the main thread** declare their thread in their type
   (D5), which LLP 1133 D3 amends: until now every hatch moment was on
   main.
9. **Under the agent, the runner admits and the implementation answers.**
   Today both runtimes bind nothing under the agent
   (`runner/src/runner/modules/bound.rs`; `host/web-js/modules.js`,
   `implementation()` returns null while `clock.agent`), so the
   declaration answers, and a bound call passes the runner without
   admission (`runner/src/runner/modules.rs`, "past this admission").
   For an interface declared `"substitute": "implementation"`, both
   runtimes bind the implementation under the agent too, told
   `agent: true`, and every call (and every lease a display takes) passes
   admission first: the grant, the origin and the foreground (LLP
   1133.009 D10 item 8), and the permission decision, which the runner
   holds as a ticket the agent answers before the call reaches the
   implementation. The implementation then answers as §9 says. It is
   given the runner's preferred values for its names when it is bound and
   whenever one changes, including names nothing reads (`camera.picture`),
   beside LLP 1133.009 D10 item 11's value carried on a call. Its
   objects reach `state.extensions` through a `state()` call the runner
   merges under the extension's name. This is the split LLP 1133.009 §10
   relies on; LLP 1133.006 D8 item 4, where the implementation replaces
   the declaration and no ticket exists, is a different one.

Each is apparatus under `rules/RULES.md` and lands with this ruling.

### D9 — Callers

Contract reads `mediaStreamTrack`, `enumerateDevices`, `cameraStatus` and
`getPhotoCapabilities` as sources, sends the rest from actions, and places
the viewfinder. Data code calls every name through its generated binding,
in Promise form; a binding call of `takePhoto` from data code takes a
track id it was given, since a track belongs to the session, not to an
answer. Requests: `getUserMedia`, and a lease a display takes on the web
(D6). `sync`: `cameraStatus`, on Apple through `call`; its synchronous
form elsewhere throws `NotSupportedError` (LLP 1133 D6 rule 4). Rust data
code gets the same names through LLP 1133.002 D13's generated binding.

An app that does not import the module links none of it, derives no

## 9. The substitute

**The implementation is its own substitute,** in D8 item 9's split, as
recording's is (LLP 1133.009 §10): under the agent the runner admits each
call and holds the permission ticket, and each implementation then runs,
told so, opens no camera, asks the OS for nothing and calls no hatch. The
declared `permission` (`camera`, the status `cameraStatus`, its field
`state`, the denial `NotAllowedError`) stays the runner's, so tickets,
`prefer permission.camera` and `--permission camera=…` work as
geolocation's do (LLP 1133.002 §6).

Under the agent, on every target with an implementation:

- **Two cameras,** "Agent back camera" (`environment`) and "Agent front
  camera" (`user`), whose ids a counter the session's seed fixes;
  `enumerateDevices` lists them once granted.
- **The picture** is `packages/camera/fixture/card.jpg`, a test card with
  its orientation marked, or the image a drive names with `prefer
  extension camera.picture="assets/sample.jpg"`, which reaches the
  implementation when it is set (D8 item 9).
  The viewfinder draws it as a plain image (a layer's contents on Apple, a
  canvas's `captureStream()` in the `<video>` on the web), mirrored for
  `user`, so a screenshot shows it and is the same on every host. The
  platform's preview layer is not in a view hierarchy's drawing
  (`drawHierarchy` draws none of it), which is why the real viewfinder
  cannot be screenshot the same way; with the real implementation bound,
  its snapshot is the module's placeholder naming the camera.
- **`takePhoto`** copies the picture's file to the path, unchanged, so
  its bytes and SHA-256 are the same on every host, and answers its
  size, type and dimensions. `fillLightMode` and the platform words are
  checked as in production and journaled.
- **States.** `getUserMedia` while `prompt` holds a `permission` ticket;
  `tap @t allow` opens the track. Leases follow D3 exactly, since
  displayed reports and admission are the runner's. `prefer extension
  media-capture.mediaStreamTrack={"muted":true,"muteReason":"in-use"}`
  mutes a track for a drive, read as an interruption begun;
  `{"readyState":"ended"}` ends it.

On a target with no implementation (Linux and Windows today) the declared
part answers under the agent (`cameraStatus`, `available` false) and every
other name fails `NotSupportedError`, as in production (LLP 1133.009 §10).

**Disclosure:** `state.extensions` lists the session's tracks with their
device, settings, consumers, lease and `muteReason`, each viewfinder's
displayed state and the origin that displayed it, each photo's path and
SHA-256, and each answer's origin.

**Production:** none of it.

## 12. What stays out

Each until a consumer asks:

- video recording (a recorder of a stream with a video track);
- a camera track in `video srcObject=`, and frames to data code or a GPU
  surface (LLP 1133.003's track door, made public);
- two cameras at once on iOS (`AVCaptureMultiCamSession`, which needs
  several inputs, its own format choice and an arbitration this RFC does
  not have);
- barcode and document scanning as tier 1 (the roster's `vision`);
- `exact` and `ideal` dictionaries and `OverconstrainedError`;
- a capture with no viewfinder shown, except through tier 3;
- RAW and ProRAW as words; output-wide photo switches as words (D4);
- zoom on the web, which Image Capture puts behind the `panTiltZoom`
  permission with pan and tilt
  ([zoom](https://www.w3.org/TR/image-capture/#dom-mediatrackcapabilities-zoom));
- the system camera UI, and `input capture` (`DEFERRED.md`);
- Windows, Linux, tvOS, visionOS and watchOS cells.
