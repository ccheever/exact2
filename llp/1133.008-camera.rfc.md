## Summary

`@exact/camera` shows the camera and takes a photo, on the web, iOS,
macOS and Android first, with every other target of LLP 1133 D8 a visible
`later` or `absent`. Its tier 1 is the web's: Media Capture's
`getUserMedia({video})` opens a camera and answers a stream of tracks, a
viewfinder shows a track as `<video srcObject>` does, and Image Capture's
`takePhoto` takes a still from it:

```
use getUserMedia, applyConstraints, stopTrack, takePhoto,
  MediaStream, MediaTrackConstraints, Photo from "@exact/camera"

state track = ""
state facing = "environment"
state photo = "assets/sample.jpg"
mutation opened as shape MediaStream then show
mutation shot as shape Photo then taken

action open
  send opened = getUserMedia(video=MediaTrackConstraints(facingMode=facing))
action show
  match opened
    case some(s)
      track = s.tracks[0].id
    case none
      track = ""
action flip
  applyConstraints(track=track, facingMode=(facing == "environment" ? "user" : "environment"))
  facing = (facing == "environment" ? "user" : "environment")
action shutter
  send shot = takePhoto(track=track, fillLightMode="auto")
action taken
  match shot
    case some(p)
      photo = p.path
      stopTrack(track=track)
    case none
      photo = photo
view
  exact-camera srcObject=track width="100%" flex=1
```

```ts
import { takePhoto } from "@exact/camera";

// `track` is the id the Contract opened and passed to this source.
const p = await takePhoto({ track, apple: { photoQualityPrioritization: "speed" } });
return fetch(`${api}/upload`, { method: "PUT", exactBodyFrom: p.path });
```

Tier 2 reaches AVFoundation's photo settings and device types and
CameraX's capture and flash modes. Tier 3 hands the app's Swift the
`AVCaptureSession` inside its configuration, the `AVCaptureDevice`, the
photo output and each capture's settings, and its Kotlin the CameraX use
cases before they are bound and the `Camera` after.

The camera is the first module to need four things, each decided here for
every module after it:

- **A package carries a view.** `exact-camera` is the package's, on each
  host, and reaches the same implementation instance as the package's
  calls (D8 item 1).
- **A video track is a capture graph, not a stream of frames.** On Apple
  and Android a preview and a photo are outputs attached to the platform's
  capture session, not consumers of buffers. The track table LLP
  1133.009 D3 gives packages carries, for a video track, the platform's
  way to attach one (D3).
- **A camera with nothing to show stops.** A video track whose viewfinder
  is not displayed, by the rule `wakelock` already uses (LLP 1125 D11),
  and which nothing else consumes, releases its device and reads `muted`
  until one is displayed again (D3). An app that forgets to stop its
  track, or leaves its screen by a gesture no action hears, does not leave
  the camera on.
- **A module's Android code may need a library.** CameraX is how Android
  recommends a camera be built, and is the first prebuilt closure an
  implementation pins (D8 item 5).

The consumer is the photo editor (`apps/photo-editor`), which today edits
one fixed image through its own module. With this one it takes a photo and
then edits it: a standard module beside an app's own (§10).

## 1. What exists

**The photo editor** (LLP 1024) is one app native module, `<photo-editor>`,
on the web, macOS and iOS: UIKit and AppKit gesture recognizers and the
web's Pointer Events over one image, whose `photo` prop is a path under
the app's assets (`modules/apple/PhotoEditor.swift`, `loadPhoto`;
`modules/web/index.js`, `setPhoto`). It has no `app.ts`; its Rust data
crate answers nothing and grants nothing. It has no Android crate.

**Views in an app's module.** On Apple a view is a factory in the app's
`ExactModule.views` (`host/apple/modules/ExactNativeModule.swift`); the
build reads the roster from the compiled module (`host/apple/build.mjs`,
the roster probe) and puts a `firstFrame` tag in the first frame. On the
web the app's `modules/web/index.js` exports `roster` and its classes, and
the host defines the custom elements. On Android the app's
`modules/android` defines `exact.app.Modules` with a `NativeModules`
roster; a hosted view takes `performClick()` only: "native drags,
arbitrary pointer forwarding … are not implemented"
(`host/android/README.md`). A native view's props are strings, and its
events are `load`, `change`, `input`, `message` and `press`
(`docs/recipes/native-views.md`).

**The package seam** as geolocation built it and LLP 1133.004, 1133.006
and 1133.009 extend it: an Apple implementation is a class with
`init(changed:agent:log:)`, `later`, `call` and `release`, composed into
the app's module by an adapter the build writes, made once a session at
its first request (`ExactExtensions.swift`); an Android one subclasses
`ExactExtension`; a web one exports `implementation({changed})`. An
implementation's `exact.json` already has a `views` field (LLP 1133.001
D1), which nothing reads: `packages/geolocation` declares `"views": []`,
and the adapter has no views.

**Tracks.** LLP 1133.003 D2 made a video track a host-owned object named
by id, shown by `video srcObject=`. LLP 1133.009 §3 (in review beside
this one) puts Media Capture's surface in one interface,
`@exact/media-capture`, with tracks in a per-session table every package
reaches, and says the camera builds its video half. This RFC agrees with
its names, shapes, table and grants, and adds what video needs (D1, D3).

**The grant** `device.camera` is a row of `runner/src/device.rs`, with
`NSCameraUsageDescription` on iOS and macOS, the hardened-runtime
entitlement `com.apple.security.device.camera` and `Permissions-Policy:
camera`; it has no Android column.

**`rules/DEFERRED.md`** moved "No camera anything" on 2026-10-02: a camera
is a native module with a preview and start, stop, capture and flip,
gated by `device.camera`, with an agent substitute, web, iOS and macOS
first; "not a built-in tag"; video recording and barcode or document
scanning stay out. `input capture` stays refused. This RFC is that entry,
as a standard package rather than an app's module (§14 question 7).

## 2. Tier 1

### D1 — Media Capture's video, Image Capture's photo, a viewfinder

The camera's names, and the shared surface's that it uses (LLP 1133.009
D1 and D3; the camera re-exports them, so one import serves):

| Name | Declared by | Kind | Web | Contract |
|---|---|---|---|---|
| `getUserMedia(video=…)` | media-capture | send; a request | `navigator.mediaDevices.getUserMedia({video})` | `send s = getUserMedia(video=true)` |
| `applyConstraints(track=, …)` | media-capture (added here) | send, answers nothing | `track.applyConstraints(…)` | statement |
| `stopTrack(track=)` | media-capture | send, answers nothing | `track.stop()` | statement |
| `mediaStreamTrack(track=)` | media-capture | live source; a fact | the track's attributes, `getSettings()`, `getCapabilities()` | `resource t = mediaStreamTrack(track=id)` |
| `enumerateDevices()` | media-capture | live source; a fact | `enumerateDevices()`, re-read at `devicechange` | `resource d = enumerateDevices()` |
| `cameraStatus()` | media-capture | live source; a fact; `sync` | `"mediaDevices" in navigator`, `permissions.query({name: "camera"})` | `resource c = cameraStatus()` |
| `takePhoto(track=, …)` | camera | send | `new ImageCapture(track).takePhoto(settings)` | `send p = takePhoto(track=id)` |
| `getPhotoCapabilities(track=)` | camera | live source; a fact | `new ImageCapture(track).getPhotoCapabilities()` | `resource c = getPhotoCapabilities(track=id)` |
| `exact-camera srcObject=` | camera | a view | `<video srcObject autoplay playsinline muted>` | `exact-camera srcObject=track` |

Data code calls every name but the view through its generated binding, in
Promise form (LLP 1133 D6).

**Values.** The shared shapes are LLP 1133.009 D1's; video adds:

| Shape | Fields |
|---|---|
| `MediaTrackConstraints` (video members) | `deviceId`, `groupId`, `facingMode`, `width`, `height`, `aspectRatio`, `frameRate`, `resizeMode` (Media Capture §4.3.8); `zoom`, `torch` (Image Capture §10, the two of its constrainable properties a phone's camera commonly has; a camera without one lists none in its capabilities) |
| `MediaTrackSettings` (video members) | the same names, each what the track applied |
| `MediaStreamTrack` (added) | `capabilities: option<MediaTrackCapabilities>`, the ranges and lists `getCapabilities()` gives for the members above (`zoom` a `{min, max, step}`, `torch` a bool, `facingMode` a list); `muteReason: option<enum<idle|in-use|background|multitasking|system-pressure|interrupted>>` |
| `MediaDeviceInfo` (video) | `kind` `videoinput`, and `facingMode: option<string>`, folded from `InputDeviceInfo.getCapabilities()` |
| `CameraStatus` | `available`, `state` (`granted`, `prompt`, `denied`, `unknown`), `apple`, `android` |
| `PhotoCapabilities` | `redEyeReduction` (`never`, `always`, `controllable`), `imageWidth`, `imageHeight` (`{min, max, step}`), `fillLightMode` (a list of `auto`, `off`, `flash`) |
| `Photo` | `path`, `type`, `size` (bytes), `width`, `height` (as the image is shown, its orientation applied) |

`facingMode` takes Media Capture's `user`, `environment`, `left` and
`right` ([VideoFacingModeEnum](https://www.w3.org/TR/mediacapture-streams/#dom-videofacingmodeenum)).
`takePhoto`'s options are `PhotoSettings`' `fillLightMode`, `imageWidth`,
`imageHeight` and `redEyeReduction`
([PhotoSettings](https://w3c.github.io/mediacapture-image/#dictdef-photosettings)),
and `path`.

**Errors** are the specifications' `DOMException` names, as LLP 1133.009
D1 answers them: `NotAllowedError` (denied, or a caller the origin rule
refuses, with `message` `person-required`, §6), `NotFoundError` (no
camera, or a track id the session does not hold), `NotReadableError` (the
platform would not give the camera: another app holds it, the hardware
failed), `InvalidStateError` (`takePhoto` on a track that is ended or
muted, as Image Capture rejects a track that is not live), `NotSupportedError`
(a target without an implementation, a `kind` `audio` track given to a
camera name), `AbortError`, `UnknownError` (a capture the platform failed,
[takePhoto](https://w3c.github.io/mediacapture-image/#dom-imagecapture-takephoto)).

**Declared deviations,** each with its reason:

- **Objects are ids** (LLP 1133.009 D1): a stream and a track are named by
  id. There is no `ImageCapture` object: `takePhoto(track=)` is its
  constructor and `takePhoto()` in one call, as `startMediaRecorder` is.
- **A photo is a file, not a `Blob`.** `takePhoto` writes the image to an
  `app:/` path and answers it. With `path` written, the module writes
  there, admitted against the calling source's `fs.write` (LLP 1133.009
  D10 item 4), and adds the extension of the format it wrote. Omitted, it
  writes `app:/tmp/camera/<n>.<ext>`, as a picked file lands in
  `app:/tmp/picked/` with no grant (LLP 1069.010). The file then shows in
  an `img`, uploads with `exactBodyFrom`, shares and shrinks with
  `compressImage` by its path. Reason: a photo is megabytes, which
  neither a Contract value nor a native module request (4 MiB, LLP
  1133.006 D8) carries.
- **`applyConstraints` may change the camera.** Writing `deviceId` or
  `facingMode` moves the track to another camera under the same id,
  where a page stops its track and asks again. Reason: on Apple and
  Android a hand-built app flips by replacing the session's input, with no
  second prompt and no new stream; on the web the implementation stops the
  browser's track and opens the other camera, under the module's id (D3).
- **Constraints are bare values,** which Media Capture treats as `ideal`
  (LLP 1133.009 D1); `exact` and `OverconstrainedError` wait for a
  consumer.
- **A track with nothing to show is muted** (D3): `muteReason` `idle`.
  Media Capture leaves a track running until `stop()`.
- **`takePhoto` needs a track that is shown.** A muted track, `idle`
  included, rejects with `InvalidStateError`. Reason: the person sees what
  is taken, and the platform's exposure and focus have converged on the
  frames the viewfinder showed; a hidden capture is tier 3.
- **The viewfinder is a view of the package's, not `video srcObject=`.**
  On the web the two are one element. On Apple the viewfinder is an
  `AVCaptureVideoPreviewLayer` attached to the capture session
  ([AVCaptureVideoPreviewLayer](https://developer.apple.com/documentation/avfoundation/avcapturevideopreviewlayer)),
  and on Android CameraX's `PreviewView` bound as a `Preview` use case:
  zero-copy, rotated by the platform, mirrored for a front camera, and
  where the platform's own gestures attach. A `video` shows a track's
  frames, which LLP 1133.003's door would have to receive one by one; a
  camera track in `video srcObject=` waits for a consumer that needs its
  frames (effects, composition) and for that door to be public (§12).

`getUserMedia` with `video=` and `audio=` both opens one stream with both
kinds of track where the target can (LLP 1133.009 D3); stage 1 of this
module takes `video=` alone, and the combined call is the video recording
§12 leaves out.

### D2 — Unsaid defaults are the platform's; written ones are the web's

LLP 1133 D4: what the author omits is what a hand-built app on the
platform has; what the author writes takes the web's meaning.

| What | Web | Apple | Android |
|---|---|---|---|

| the camera for `facingMode="environment"` on iOS | — | the back virtual device with the most constituents (`builtInTripleCamera`, else `builtInDualWideCamera`, else `builtInDualCamera`, else `builtInWideAngleCamera`), so a zoom below 1 reaches the ultra-wide, as the Camera app does | CameraX's back camera; where the device exposes a logical camera, a zoom ratio below 1 reaches its ultra-wide |

| shutter sound | none | the system's, which iOS plays and lets an app suppress except where law requires it ([isShutterSoundSuppressionSupported](https://developer.apple.com/documentation/avfoundation/avcapturephotooutput/isshuttersoundsuppressionsupported)) | `MediaActionSound.SHUTTER_CLICK` at each capture, the cue a camera app on the platform gives; Android "strongly recommend[s]" it wherever `MediaActionSound.mustPlayShutterSound()` is true ([MediaActionSound](https://developer.android.com/reference/android/media/MediaActionSound)) |
| mirroring | none (a page mirrors with CSS) | a front camera's preview mirrored by its connection's `automaticallyAdjustsVideoMirroring`; the photo not mirrored | `PreviewView` mirrors a front camera's preview; the photo not mirrored |
| `object-fit` omitted | `contain`, as `<video>` renders | `resizeAspect`, the preview layer's default ([videoGravity](https://developer.apple.com/documentation/avfoundation/avcapturevideopreviewlayer/videogravity)) | `FILL_CENTER`, `PreviewView`'s default |

A written `object-fit` maps to the preview layer's gravity (`contain`,
`cover`, `fill` to `resizeAspect`, `resizeAspectFill`, `resize`) and to
`PreviewView`'s scale type. The gestures are the viewfinder's words
`tapToFocus` and `pinchToZoom`, named after CameraX's `CameraController`
switches; an author who writes `false` turns one off (author > platform).
A pinch changes the track's `zoom`, which `mediaStreamTrack` reports.

Where a platform reports no position for a camera (most Mac cameras),
`facingMode` is absent from its settings, as a browser on a Mac reports
none.

## 3. Tracks and what consumes them

### D3 — A video track is a capture graph; the camera runs while it is shown

LLP 1133.009 D3 puts tracks in a per-session table the host keeps, which
a package reaches through its context, and says a consumer "looks it up
by id and subscribes to its buffers". For audio that is the whole
interface. For video on Apple and Android it is not, and building it so
would be a tell and a cost: the preview and the photo are outputs of the
platform's capture session, not readers of frames.

- **Apple.** `@exact/media-capture`'s implementation keeps one
  `AVCaptureSession` per process, a serial queue it configures and starts
  it on, and an `AVCaptureDeviceInput` for the camera in use. `startRunning`
  blocks, and Apple says to "start the session on a serial dispatch queue
  so that you don't block the main queue"
  ([AVCaptureSession](https://developer.apple.com/documentation/avfoundation/avcapturesession)).
  A video track's entry in the table offers `configure { session in … }`,
  run on that queue between `beginConfiguration()` and
  `commitConfiguration()`, through which a consumer adds and removes its
  output: the camera's `AVCapturePhotoOutput`, a viewfinder's preview
  layer connection, a tier 3 `AVCaptureMetadataOutput`.
- **Android.** The implementation keeps CameraX's `ProcessCameraProvider`
  and, per live track, the set of use cases bound for it. A consumer adds
  and removes a use case (`Preview`, `ImageCapture`, a tier 3
  `ImageAnalysis`), and the implementation binds the whole set in one
  `bindToLifecycle` call on the main thread, since CameraX binds use cases
  together ([CameraX architecture](https://developer.android.com/media/camera/camerax/architecture)).
- **Web.** The entry is the page's `MediaStreamTrack`, which `<video>` and
  `ImageCapture` take as they are.

So a video track's entry in LLP 1133.009's table has a platform-typed
attach point beside `subscribe(buffer:, ended:)`, and its consumers
attach outputs. A frame subscription for video (an `AVCaptureVideoDataOutput`
the host attaches for the consumer) is what a later consumer of frames
gets; nothing here uses it.

**One camera runs at a time per process.** iOS runs one camera in an
`AVCaptureSession`; several need `AVCaptureMultiCamSession`, which is iOS
and iPadOS only ([AVCaptureMultiCamSession](https://developer.apple.com/documentation/avfoundation/avcapturemulticamsession)).
A session that opens a video track while another track of the process
runs takes the camera; the other track stays `live`, `muted` with
`muteReason` `in-use`, and runs again when the taker's track is muted or
ends. That is what iOS does to another app's session
(`videoDeviceInUseByAnotherClient`), and it lets the sample host's two
sessions each hold a track. Two tracks on one camera share its input.

**Who consumes.** A video track's consumers are its viewfinders that are
displayed, a `takePhoto` in flight, and an output attached through the
hatch (D5) that says it consumes. A viewfinder is displayed by
`wakelock`'s rule (LLP 1125 D11, `runner/src/wakelock.rs` `displayed`):
mounted, neither it nor an ancestor `display: none` or wholly covered by
its host, and under no route its navigation root hides. The runner, which
computes that rule for `wakelock`, reports each package view's displayed
state to its implementation as it changes (D8 item 2).

**With no consumer, the camera stops.** The track releases its device
(Apple: its input leaves the capture session, which stops when no track
has a device; Android: its use cases are unbound; web: `enabled =
false`, after which a browser may release the camera, and resuming needs
no new prompt),
and reads `live`, `muted`, `muteReason` `idle`. When a consumer returns,
the device is taken again and the track unmutes. `stopTrack` ends it; the
session's end ends it.

Reasons, in order:

1. **The platform's practice.** A hand-built camera screen starts its
   capture session when it appears and stops it when it disappears, the
   pair UIKit's `viewWillAppear` and `viewWillDisappear` invite, and
   CameraX stops a camera when the lifecycle it is bound to stops. A camera left
   running behind another screen keeps the system's camera indicator on,
   which a person who knows the platform notices.
2. **Otherwise every way a screen leaves needs its own stop.** A sheet
   dismissed by a swipe, a tab switched, a screen popped by the system's
   back gesture, a window closed: an app that stops its track in actions
   must pair each with one, and one missed leaves the camera on. The
   runner already knows which nodes are displayed.
3. **A track still holds its grant and id.** The app's state does not
   change when the viewfinder hides; returning shows the camera again with
   no request.

Restarting costs what the platform's restart costs (a fraction of a
second on an iPhone); stage 2 measures it on an iPhone and records it in
D11. A viewfinder that shows a track another viewfinder already shows
shows nothing until that one is not displayed: one displayed viewfinder
per track, the most recently displayed, since a CameraX track binds one
`Preview`, and Apple keeps the same rule so the targets agree.

**Lifetimes.** As LLP 1133.009 D6: streams and tracks belong to the
session, outlive the answer that opened them, and end at `stopTrack`, when
the platform takes the camera away (`readyState` `ended`) and at session
end. The capture session is the process's; it is made at the first video
track and stopped when no track has a device.

**Interruptions.** The platform's reason becomes `muteReason`: Apple's
`videoDeviceNotAvailableInBackground` is `background`,
`videoDeviceNotAvailableWithMultipleForegroundApps` is `multitasking`,
`videoDeviceInUseByAnotherClient` is `in-use`,
`videoDeviceNotAvailableDueToSystemPressure` is `system-pressure`, any
other `interrupted`
([InterruptionReason](https://developer.apple.com/documentation/avfoundation/avcapturesession/interruptionreason)).
Apple's documentation does not say a session resumes by itself, so the
implementation restarts it at `interruptionEndedNotification` when the
track still has a consumer. Android's lifecycle stop is `background`, and
`CameraState`'s errors map the same way. The web reports `muted` with no
reason the page can read; the implementation gives `interrupted`.

**Threads.** Every entry into a package is on the main thread (LLP
1067.000 D4). Session configuration, `startRunning` and `stopRunning` are
on the session queue; nothing on it waits on main. A photo's delegate
callbacks arrive on the queue the platform chooses; the implementation
writes the file off the main thread and replies on main. A display change
that removes a consumer enqueues the release and returns.

## 4. Tier 2 and tier 3

### D4 — The platforms' words

**Apple** (`apple.…`; AVFoundation's names):

### D5 — Access hatches

The objects are two packages': the capture session and device are
`@exact/media-capture`'s, the photo output and the viewfinder are
`@exact/camera`'s. An app's Swift sets each hatch as it sets
`GeolocationModule.hatch` (LLP 1133.002 D4).

| Target | Object | Moment | Thread | The module owns | The app may |
|---|---|---|---|---|---|
| Apple | the class of capture session | before the process's session is made | main | — | answer `AVCaptureMultiCamSession` (iOS) |
| Apple | `AVCaptureSession` | inside each configuration, after the module's inputs and outputs | the session queue | its inputs, its outputs, `sessionPreset`, start and stop | add outputs (`AVCaptureMetadataOutput` for codes, `AVCaptureVideoDataOutput` for frames, `AVCaptureMovieFileOutput`), declaring each a consumer or not (D3) |
| Apple | `AVCaptureDevice` | after the module's constraints are applied, under `lockForConfiguration` | the session queue | the properties the track's constraints and words set | set any other: white balance, low-light boost, video stabilization of its own outputs |
| Apple | `AVCapturePhotoOutput` | after it is added, before the session commits | the session queue | its delegate per capture | set output-wide switches (D4's last paragraph), depth, Live Photo, Photographic Styles where supported |
| Apple | `AVCapturePhotoSettings` | before each capture, after the module's words | main | `format` when `codec` is written, `flashMode`, `maxPhotoDimensions` | set any other field |
| Apple | each capture's `AVCapturePhotoCaptureDelegate` calls | after the module's own handling | the platform's | the file it writes | read the `AVCapturePhoto` (depth data, a Live Photo's movie) |
| Apple | the viewfinder's `UIView` or `NSView` | when made | main | its preview layer and gestures | add an `AVCaptureEventInteraction` for the hardware buttons (iOS 17.2, [doc](https://developer.apple.com/documentation/avkit/avcaptureeventinteraction)) |
| Android | the track's use cases | before each bind, after the module's | main | `Preview`, `ImageCapture` | add an `ImageAnalysis` (codes, frames), declaring it a consumer or not |
| Android | `ImageCapture.Builder` | before build, after the module's words | main | flash, capture mode, rotation | set any other field, Camera2 interop included |
| Android | `Camera` | after each bind | main | the zoom and torch the track's constraints set | `CameraControl`'s focus and metering, `CameraInfo` |
| Web | `MediaStreamTrack` | after `getUserMedia` | main | `enabled`, `stop()` | `applyConstraints` with any constraint |

A hatch that runs off the main thread says so in its type, and its code
must not touch UI. Development builds compare what the module owns with
what it last wrote and name a change (LLP 1133 D3: detection, not
enforcement). Under the agent no session, device or output is made and no
hatch is called.

## 6. Permission

### D6 — LLP 1133.002 §4, with LLP 1133.009's rule for capture

**Declare.** `device.camera <purposeKey>`. The row gains its Android
column: `android.permission.CAMERA`, and `<uses-feature
android:name="android.hardware.camera.any" android:required="false"/>`,
because "the `CAMERA` permission implies that your app also uses
`android.hardware.camera`" and a back camera is then a required feature
([uses-feature](https://developer.android.com/guide/topics/manifest/uses-feature-element#permissions)),
which would hide the app from a device without one. Derived otherwise:
iOS and macOS `NSCameraUsageDescription`, whose text the prompt shows
(and without which "attempting to start a capture session … raises an
exception",
[requestAccess](https://developer.apple.com/documentation/avfoundation/avcapturedevice/requestaccess(for:completionhandler:)));
macOS `com.apple.security.device.camera`
([entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.device.camera));
the web's `Permissions-Policy: camera=(self)`. A bake that finds a camera
name without the line refuses (`grant-missing`).

**Read.** `cameraStatus().state`:

| Platform state | `state` |
|---|---|
| Apple `AVCaptureDevice.authorizationStatus(for: .video)` `notDetermined` | `prompt` |
| Apple `authorized` | `granted` |
| Apple `denied`, `restricted` | `denied` |
| Android `CAMERA`, by LLP 1133.002 D8's history | as geolocation's |
| web `permissions.query({name: "camera"})` | the same word; `unknown` where the browser rejects the name (Chrome 64, Firefox 132 and Safari 16 accept it, by MDN's compatibility data) |

The Android history moves from geolocation's implementation into the
host's `ExtensionContext`, so every module reads one (D8 item 7). Safari
asks again in a later visit by default, so its state reads `prompt` again;
that is the browser's, and the status says it.

**Ask.** `getUserMedia(video=…)` is the request. While `prompt` it asks
through `AVCaptureDevice.requestAccess(for: .video)`,
`Activity.requestPermissions`, or the browser's own. One request at a
time, through LLP 1133.002 D9's queue; `getUserMedia(audio=, video=)`
asks for both in one request where the platform does (LLP 1133.009 D3).
Explain and recover as LLP 1133.002 D11 says, with
`openURL("app-settings:")`.

**Who may capture.** LLP 1133.009 D9's rule, which LLP 1133 D6 rule 3
already names for capture: `getUserMedia(video=…)` and `takePhoto` are
refused to a tool invocation and to a wake in every state, granted
included (`NotAllowedError`, `person-required`), and declared
`"origin": "foreground"`. Any of the app's own code in a foreground
session may call them: a person's press, or a `task` that counts down a
self-timer. A tool may stop a track, change its constraints and read
every fact.

A viewfinder's display asks nothing: it shows a track the app already
opened. A displayed viewfinder whose track is muted `idle` takes the
camera again under the grant the track holds; if the grant was revoked
meanwhile, the track ends (`readyState` `ended`), as a browser ends a
track whose permission is revoked.

### D8 — Seam additions

Each is general, and each is proved by the out-of-tree fixture before
this package uses it (LLP 1133.001 D8):

1. **A package carries a view.** An interface declares each tag, its
   props and events; an implementation serves it. On Apple the
   implementation's class gains `views`, and the adapter the build writes
   joins them to the roster the build probes (`host/apple/build.mjs`);
   a view's factory receives the session's adapter, so the view and the
   calls reach one implementation instance (LLP 1133.001 D2 rule 3). On
   the web the implementation's module exports `roster` and the view's
   class, which receives the implementation. On Android the
   implementation's roster joins `exact.app.Modules`. A package view is
   never a first-frame tag: the package's code loads after first pixel
   (`rules/RULES.md`, the boot path). **Tags are declared, not imported.**
   A custom element's name is one per document on the web
   ([CustomElementRegistry](https://html.spec.whatwg.org/multipage/custom-elements.html#customelementregistry)),
   and a tag is not a Contract name `use` takes; the bake finds a tag in
   the interfaces the app depends on directly, as it finds the app's own
   in `app.json` `modules`, and refuses one declared twice
   (`bake-view-twice`, naming both packages) or by no one
   (`bake-view-unknown`, naming the line `exact add` writes).
2. **A view hears whether it is displayed.** For a view declared
   `"displayed": true`, the runner reports each instance's displayed
   state by `wakelock`'s rule when it changes, through the implementation
   (`displayed(view, bool)`), on native hosts and in the web JS runtime.
   A map that pauses its tiles, a video that pauses its decode, a camera
   that releases its device, all read this.
3. **A video track's attach point** (D3): the track table's entry for a
   video track exposes, per platform, `configure` on Apple, the use-case
   set on Android, the `MediaStreamTrack` on the web; and a consumer count
   the track's owner reads to mute and unmute it.
4. **Writes to `app:/tmp/<extension>/` with no grant,** for a file the
   module makes and names, as the picker writes `app:/tmp/picked/`;
   announced with `changed("app:/tmp/…")` as `wrote` announces an app's
   write. A written `path` is LLP 1133.009 D10 item 4's.
5. **An Android implementation's prebuilt libraries** (LLP 1133.001 D9's
   `artifacts`, built here). CameraX is several Maven artifacts with their
   own dependencies; the 1.6.2 `camera-core`, `camera-camera2`,
   `camera-lifecycle` and `camera-view` POMs name, among others,
   `androidx.lifecycle`, `androidx.core`, `androidx.appcompat`,
   `androidx.fragment`, Guava's `listenablefuture`, `kotlinx-coroutines`
   and Dagger ([camera-core
   1.6.2](https://dl.google.com/android/maven2/androidx/camera/camera-core/1.6.2/camera-core-1.6.2.pom),
   [camera-view
   1.6.2](https://dl.google.com/android/maven2/androidx/camera/camera-view/1.6.2/camera-view-1.6.2.pom)).
   As D9 rules, the implementation names its whole closure, each artifact
   `{url, sha256}`; the step that fetches locked Cargo sources fetches
   them into a cache keyed by hash; the Android project takes them as
   file dependencies, so Gradle resolves nothing. An app that also builds
   with Compose, whose AndroidX the Android project resolves through
   Gradle (`host/android/app/build.gradle.kts`), can meet one library
   twice: the build refuses a class supplied by both, by name
   (`bake-artifact-conflict`), rather than let the packager pick. §14
   question 4 asks whether this or a Gradle-resolved, verified lock is the
   rule.
6. **An Android hosted view takes touches.** The reader forwards a
   pointer sequence that lands on a hosted view and no exact2 gesture
   claims to that view, as UIKit and AppKit deliver to a native view's
   recognizers. The viewfinder's tap and pinch need it, as a map's pan
   will. Until it lands, Android's viewfinder has no gestures, recorded
   as a tell in D10.
7. **One Android permission history,** in the host's `ExtensionContext`
   rather than each implementation's preferences (D6).
8. **Hatches off the main thread** declare their thread in their type
   (D5), which LLP 1133 D3 amends: until now every hatch moment was on
   main.

Each is apparatus under `rules/RULES.md` and lands with this ruling.

### D9 — Callers

Contract reads `mediaStreamTrack`, `enumerateDevices`, `cameraStatus` and
`getPhotoCapabilities` as sources, sends the rest from actions, and places
the viewfinder. Data code calls every name through its generated binding,
in Promise form; a binding call of `takePhoto` from data code takes a
track id it was given, since a track belongs to the session, not to an
answer. Requests: `getUserMedia`. `sync`: `cameraStatus`, on Apple
through `call`; its synchronous form elsewhere throws `NotSupportedError`
(LLP 1133 D6 rule 4). Rust data code gets the same names through LLP
1133.002 D13's generated binding.

## 9. The substitute

**The implementation is its own substitute** (LLP 1133.006 D8 item 4),
as recording's is (LLP 1133.009 §10): under the agent each
implementation runs, told so, opens no camera, asks the OS for nothing
and calls no hatch. The declared `permission` (`camera`, the status
`cameraStatus`, its field `state`, the denial `NotAllowedError`) stays the
runner's, so tickets, `prefer permission.camera` and `--permission
camera=…` work as geolocation's do (LLP 1133.002 §6).

Under the agent, on every target alike:

- **Two cameras,** "Agent back camera" (`environment`) and "Agent front
  camera" (`user`), whose ids a counter the session's seed fixes;
  `enumerateDevices` lists them once granted.
- **The picture** is `packages/camera/fixture/card.jpg`, a test card with
  its orientation marked, or the image a drive names with `prefer
  extension camera.picture="assets/sample.jpg"`. The viewfinder draws it
  as a plain image (a layer's contents on Apple, a canvas's
  `captureStream()` in the `<video>` on the web), mirrored for `user`, so
  a screenshot shows it and is the same on every host. The platform's
  preview layer is not in a view hierarchy's drawing (`drawHierarchy`
  draws none of it), which is why the real viewfinder cannot be
  screenshot the same way; with the real implementation bound, its
  snapshot is the module's placeholder naming the camera.
- **`takePhoto`** copies the picture's file to the path, unchanged, so
  its bytes and SHA-256 are the same on every host, and answers its
  size, type and dimensions. `fillLightMode` and the platform words are
  checked as in production and journaled.
- **States.** `getUserMedia` while `prompt` holds a `permission` ticket;
  `tap @t allow` opens the track. A viewfinder not displayed mutes it
  `idle`, as in production, since the rule is the runner's. `prefer
  extension camera.mediaStreamTrack={"muted":true,"muteReason":"in-use"}`
  mutes it for a drive; `{"readyState":"ended"}` ends it.

**Disclosure:** `state.extensions` lists the session's tracks with their
device, settings, consumers and `muteReason`, each viewfinder's displayed
state, each photo's path and SHA-256, and each answer's origin.

**Production:** none of it.

## 10. The consumer: the photo editor

The photo editor gains:

- `"@exact/camera"` and `"@exact/media-capture"` in a `package.json` of
  its own (LLP 1133.001 D4), the grant `device.camera cameraPurpose` from
  its data crate's `grants()`, and a strings table for `cameraPurpose`
  (it has none);
- a **Take photo** button, shown while `cameraStatus().available` and not
  `denied`, whose action opens the camera (the Summary's `open`) when the
  app holds no live track, and shows a camera screen over the editor: the viewfinder, a shutter, a
  flip button shown while `enumerateDevices()` lists cameras of both
  facings, a torch button shown while the track's capabilities have one,
  and Cancel, which stops the track;
- the shutter's `taken` sets the editor's `photo` to the photo's `app:/`
  path and closes the camera screen;
- `<photo-editor>` loads an `app:/` path: on Apple from the module
  context's `temporary` or `data` directory, on the web through the
  host's `appURL`, as an `img` shows one;
- while `denied`, a line saying so and, on native targets, Open Settings.

The camera screen is a sheet over the editor. A swipe that dismisses it
hides the viewfinder whether or not an action stops the track: the track
mutes `idle` and the camera stops (D3); Take photo shows the same track
again.

**Acceptance drives,** on the web, macOS and the iOS simulator under the
agent (ticket ids from `state.pending`, `@p` here):

1. `--permission camera=prompt`; `tap take-photo`; `tap @p allow`;
   `clock settle`; `screenshot`: the agent's back camera card fills the
   viewfinder, the same on every host; `state.extensions` shows one track,
   `live`, unmuted, its viewfinder displayed.
2. `tap shutter`; `clock settle`: the editor shows the card, its `photo`
   is `app:/tmp/camera/1.jpg`, the file's SHA-256 is the card's; `tap
   rotate`: the edit reads rotation 90°; the track is `ended`.
3. `prefer extension camera.picture="assets/sample.jpg"`; take again: the
   photo's SHA-256 is the sample's.
4. Open the camera, `tap flip`: the settings read `user` and the card is
   mirrored in the viewfinder; take: the photo's bytes are the card's,
   not mirrored.
5. Open the camera and dismiss the sheet (`back`): the track is `muted`,
   `idle`, and `state.extensions` shows no device held; `tap take-photo`:
   the same track unmutes, with no ticket and no second `getUserMedia`.
6. `--permission camera=denied`: no ticket, the denied line, Open
   Settings on native targets.
7. In the conformance fixture: a tool invocation of its capture action
   fails `person-required` and opens no ticket (D6); `takePhoto` on a
   muted track fails `InvalidStateError`.
8. By a person, on an iPhone and an Android phone with the real
   implementations: a photo of the room edited and its edit shown; flip;
   flash `auto` in the dark; the shutter sound; pinch and tap on the
   iPhone; Control Center or a call while the camera shows mutes it with
   its reason and it returns; revoking in Settings shows the denied line
   on return.

The conformance suite (LLP 1133.001 D7) runs the real web implementation
in Chromium with its fake capture device (`--use-fake-device-for-media-stream`,
granted with `--use-fake-ui-for-media-stream`, the host's own means), in
Firefox with `media.navigator.streams.fake`, and in WebKit where
Playwright's build has a mock camera, else it records the absence; and
the real Apple implementation on a Mac with a camera, which a person
grants (as geolocation's `--ask` does). The iOS simulator has no camera,
so drive 8's iPhone is Apple's mobile evidence. On Android the suite and
drives 1–7 run in the fixture app on an emulator's virtual camera: the
photo editor's view has no Android implementation, and its gestures need
D8 item 6 (§14 question 5).

## 12. What stays out
