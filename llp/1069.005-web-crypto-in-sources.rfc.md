# LLP 1069.005: Web Crypto in data sources — digests freely, entropy as a read, P-256 for DPoP

**Type:** RFC
**Status:** Draft r2; Charlie's rulings folded 2026-09-27
**Systems:** TypeScript executor (`js/src/prelude.js`, `js/build.rs`'s prelude list, the host ops in `js/src/lib.rs`); ibex2's crypto (`vendor/ibex2/src/stdlib/crypto.rs`, `bindings/crypto.js`, boundary ops 70–71); web module realms (`host/web/module-glue.js`, `module-worker.js`); the store's read count (`runner/src/store.rs` `observe_external_read`); `exact-data` (Rust parity); bake
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-27
**Revised:** 2026-09-27, r2: rulings folded (entropy a counted read; a repeatable stream under the agent now; the DPoP key's home per host; `p256` or `ring` measured)
**Related:** LLP 1069 §5 #6 (the survey item this answers); LLP 1027.000 (explicit time and randomness: D1 inputs, D3 the ambient refusals, D4's last sentence, "seeds … do not replace secure entropy for credentials"); LLP 1027.000.000 (the launch `seed` on `exactTime`, as built 2026-09-26); LLP 1027.001 (language parity); LLP 1067 D4 (asking for `native` counts as an external read, the precedent); LLP 1069.006 (the auth session: PKCE needs 32 random bytes and SHA-256; DPoP needs ES256 keys and signatures, its D6 step 4); LLP 1069.007 §5 (the first slice, which carries D2b's agent stream); LLP 1069.009 D2a (entropy reads are recorded answers)

## Rulings (Charlie, 2026-09-27)

- **Q1: entropy is a counted device read (D2).**
- **Q2: agent sessions get a repeatable random stream now,** with LLP 1069.007's first slice. **This overrides the RFC's "wait for 1069.009".**
- **Q3: the DPoP key is a JWK under `secret.keep` first,** and a host-held key after a security review. On the web it is held as a non-extractable `CryptoKey` in IndexedDB from the first cut, because `secret.keep` there is `localStorage`.
- **Q4: `p256` or `ring`** is the implementer's measurement, open to revisit.

## Summary

A data source needs two things from Web Crypto that it doesn't have on every
executor today:

- a **digest**, such as SHA-256 for a PKCE challenge, a content address or
  a cache key;
- **secure random bytes**, for a PKCE verifier, a nonce, or a record id that
  must be globally unique and unguessable.

The two differ in kind. A digest is a pure function, so it can be installed
with no rule at all. Randomness is an input, and LLP 1027.000 requires
every input to be visible to bake and cache. This RFC keeps that rule and
changes how it is met: **entropy counts as an external read** (the marker
secrets, SQLite and `native` already use), not as a refused API. So:

- `crypto.subtle.digest` (SHA-256/384/512) is installed on every executor,
  unconditionally.
- ECDSA P-256 `generateKey`, `sign`, and `importKey`/`exportKey` as JWK are
  installed for DPoP (LLP 1069.006). Generating and signing are random, so
  they count as reads. Natively the key is kept as a JWK under
  `secret.keep`; on the web it is a non-extractable `CryptoKey` in
  IndexedDB; a host-held key follows a security review (D1b).
- `crypto.getRandomValues` and `crypto.randomUUID` are installed, draw from
  the OS's secure source, and mark the answer as reading the device. A bake
  that reaches one emits the placeholder a secret read emits. The host then
  asks again after first pixel, so no random value is ever compiled into a
  plan that every install shares.
- They refuse during module initialization. `Math.random` stays refused.
- Under the agent they draw a repeatable stream seeded by the launch seed,
  so two runs mint the same ids (D2b).
- The launch `seed` on `exactTime` stays, for ids that should repeat when
  the inputs repeat. It is 53 bits, drawn once per launch and readable in
  `state`, so it isn't for credentials (LLP 1027.000 D4).
- Rust sources get the same three functions in `exact-data`, under the same
  marker.

This also closes a parity hole found while reading for this RFC (by code,
not yet driven). Web module realms inherit the page's `crypto` unguarded,
while the native Hermes executor has no `crypto` at all. So a source that
calls `crypto.randomUUID()` works in the browser, throws `ReferenceError`
on macOS and iOS, and at bake throws in a way that reads like a bug rather
than a rule.

## Motivation

**What exists (2026-09-27, main at `c74615a3`):**

- `js/src/prelude.js` refuses `Date.now`, `new Date()`, `Math.random` and
  Intl's default-time formatting (LLP 1027.000 D3). It says nothing about
  `crypto`.
- `js/build.rs` builds the native prelude from `pure.js`, ibex2's `url.js`
  and `prelude.js`. ibex2's `bindings/crypto.js` is not in the list, so
  `crypto` is undefined on the native executor.
- ibex2 already implements `getRandomValues` (a 65,536-byte quota, and on
  entropy failure it clears the buffer and never falls back) and
  `randomUUID` (v4), at boundary ops 70 and 71, backed by `getrandom`. It has
  no `subtle`.
- The web realms (`module-glue.js` for the iframe, `module-worker.js` for a
  worker placement) disable `XMLHttpRequest`, `WebSocket`, `EventSource` and
  the timers before app code runs. `crypto` is left as the browser's: all of
  `getRandomValues`, `randomUUID` and `subtle`, with no read marked.
- The runner has a launch `seed`, drawn by the host from the platform's
  secure source (web, `host/web/navigation.js` `placeReporter`; Apple,
  `Session.swift`; Linux, `host/linux/src/zone.rs`, since 93546bef). It is
  read as `exactTime().seed`. LLP 1027.000.000 records it as "the explicit
  entropy a source mixes with the date and a counter for ids." Under the
  agent every host takes it from `--seed` (default 1).
- `exact-data` depends only on `exact-plan`, `exact-runner` and
  `serde_json`. Rust providers call whatever crate they like; `logic/`
  already links `sha2`.

**Who needs it:**

- **The auth session (LLP 1069.006).** RFC 7636 needs a verifier of 32
  random octets and its SHA-256, base64url-encoded. The launch seed can't be
  the verifier: it is 53 bits, the same for every sign-in in a launch, and
  visible to the agent.
- **Optimistic records** (Bluesky compose, Messages, Exact Live's crew
  chat) need a client id before the server answers. Any id scheme that
  won't collide across devices is either random or needs a device id, and
  exact2 offers neither.
- **DPoP (LLP 1069.006 D6 step 4).** Every Bluesky token and resource
  request needs an ES256-signed proof, from a P-256 key the client
  generates and keeps.
- **Content addressing and cache keys over bytes** (a picked image's
  digest, LLP 1069.002; a file's backup name). Today each app would
  hand-roll SHA-256 in TypeScript.

## Design

### D1 — Digests are pure; install them everywhere

`crypto.subtle.digest(algorithm, data)` with `SHA-256`, `SHA-384` and
`SHA-512` returns `Promise<ArrayBuffer>`, as on the web.

- **Native:** a new ibex2 op backed by `sha2`, already in the lockfile. A
  binding that installs `crypto.subtle` with only `digest`, and
  `SubtleCrypto` and `crypto` brands as `bindings/crypto.js` does for the
  rest.
- **Web:** the browser's own `crypto.subtle.digest` where the page is a
  secure context. The dev protocol serves module realms to LAN pages over
  plain HTTP, where `crypto.subtle` is undefined. Module integrity already
  meets this with a dev-supplied `exact.moduleDigest` (`module-glue.js`
  lines 18–22). The realm's `digest` falls back to that same implementation
  for SHA-256, and refuses SHA-384/512 by name outside a secure context
  unless the dev digest grows them. Static pages need HTTPS, as today.
- **Bake:** unaffected. A digest of constant input is constant.
- **Refused by name:** `SHA-1` (`NotSupportedError`, as the web spells an
  unknown algorithm), and every `subtle` member outside D1 and D1b. HMAC
  and AES-GCM come with their first consumer.

*Rejected: a JavaScript SHA-256 in the prelude.* It is about 1 KB of
bytecode on every source's load and slower than the host's, for no gain
where both executors already have a native one.

### D1b — ECDSA P-256, for DPoP: generate, sign, import and export as JWK

The AT Protocol's OAuth binds every token to a key the client holds. Each
token and resource request carries a DPoP proof, a JWT signed with ES256
(LLP 1069.006 D6 step 4). This subset is **in the first cut**, landing with
D1 and D2, because Bluesky's real login can't happen without it. So the
first signature consumer exists, and it
needs exactly this subset of `crypto.subtle`, with the web's names and
argument shapes:

| member | accepted | marker |
|---|---|---|
| `generateKey({name:"ECDSA", namedCurve:"P-256"}, extractable, ["sign","verify"])` | P-256 only | entropy: a read (D2) |
| `sign({name:"ECDSA", hash:"SHA-256"}, privateKey, data)` | ES256, raw `r‖s` (64 bytes, as WebCrypto and JWS both use) | entropy: a read (D2) |
| `exportKey("jwk", key)` | the public key always; a private key only if created `extractable` | pure |
| `importKey("jwk", jwk, {name:"ECDSA", namedCurve:"P-256"}, extractable, usages)` | P-256 JWK | pure |

Some notes on the table:

- **`sign` counts as a read.** WebCrypto's ECDSA uses a random nonce, so the
  same key and message give different signatures on the web. The native
  executor matches that rather than using RFC 6979's deterministic nonce.
  Otherwise the same proof would be a pure value on one executor and a
  device read on another.
- **A DPoP proof is never bakeable anyway.** It carries a fresh `jti` and
  the server's nonce, so marking it costs nothing.
- **`verify` is left out.** A client checks no DPoP proof. It comes with a
  consumer, as a pure function.
- **Other curves, `raw`/`pkcs8`/`spki` formats, and ECDH are refused by
  name.** An unknown algorithm is `NotSupportedError`, a disallowed usage is
  `InvalidAccessError`, and `exportKey` of a non-extractable key is also
  `InvalidAccessError`, as on the web.

On each executor:

- **Web:** the browser's own methods, wrapped for the read marker. They
  need a secure context. Unlike D1's digest, a dev LAN page over plain HTTP
  has no fallback: ECDSA refuses there by name. The dev server's own HTTPS
  (or `localhost`, which is a secure context) is how OAuth is developed.
  The OAuth callback needs HTTPS in any case.
- **Native:** a `CryptoKey`-shaped object whose handle is the key's bytes,
  held by ibex2 on the executor's side and never exposed to the JavaScript
  heap except through `exportKey`. The implementation is `ring`, already in
  the lockfile through rustls, or RustCrypto's `p256`. `ring` doesn't hand
  out the private scalar except inside PKCS#8, so a private JWK export
  means reading `d` out of that document; `p256` is a new dependency that
  does all four directly. The implementer measures which keeps the
  executor's binary smaller and picks it (ruled; open to revisit), held by
  the vectors below.
- **Rust (D5):** the same four functions in `exact-data::crypto`, under the
  same markers.

**Where the key lives** (ruled), per host:

| host | the key | protected by |
|---|---|---|
| Apple, Linux | generated extractable, exported as a JWK, kept with `secret.keep bluesky.dpop`; imported non-extractable for signing on the next launch | the Keychain on Apple (LLP 1018 D6); a 0600 file on Linux |
| web | generated **non-extractable**; the `CryptoKey` itself kept in the realm's IndexedDB under the secret's name, with only a handle string in `secret.keep` | the browser: the private bytes are never visible to script |

The web differs from the native hosts because `secret.keep` there is
`localStorage`, and a JWK in `localStorage` is readable by any script on
the origin. A structured-clone key doesn't fit `secret.keep`'s string
values (the runner carries secrets as strings, `glue.js:634-640`), hence
the handle. The source's four calls are the same on every host; how it
spells "keep this key" must be one form too, and is the spec's to pin
(LLP 1069 §7, Open after the pass).

**After a security review,** Apple gets a host-held key (the Secure
Enclave): `generateKey` and `sign` become requests to the host (LLP 1067
D1's shape) with an opaque handle in `secret.keep`. `exportKey` of the
private half then refuses, and the key can't move between hosts.

### D2 — Entropy is an external read, not a refused API

`crypto.getRandomValues(view)` and `crypto.randomUUID()` are installed on
every executor.

- **Native:** add ibex2's `bindings/crypto.js` to the prelude list, with its
  two host functions wired to ops 70 and 71.
- **Web:** wrap the browser's two methods in the realm before app code runs.
  `randomUUID` exists only in a secure context, so on a LAN dev page the
  wrapper forms the v4 UUID from `getRandomValues`, which exists in any
  context, using the same bits as ibex2's `format_uuid`.
- Each call returns OS entropy and calls the store's
  `observe_external_read`, the marker a secret read, a SQLite query or
  asking for `native` (LLP 1067 D4) already sets.

What follows from the marker is what LLP 1027.000 D4 asks of any input
(ruled: entropy is a counted device read):

- **Bake:** an answer that drew entropy isn't compiled. Bake emits the
  placeholder it emits for device reads, and the host asks again after
  first pixel. A random id is never baked into a plan every install shares.
- **Carry and kept answers:** unchanged. A random value inside an answer is
  part of that answer, like a server's reply. A carried or kept answer keeps
  its id, which is what a pending optimistic record needs.
- **Asking again:** entropy doesn't make a resource re-ask itself. Like a
  time argument, a fresh value needs a new request: new arguments, a
  refresh, or an action.

*Why not keep refusing, as D3 does for `Math.random`?* LLP 1027.000 D1 says
a randomized calculation "takes an explicit seed or a previously supplied
random value". Its D4 then says seeds "do not replace secure entropy for
credentials." Nothing supplies the latter, and a credential can't be a
source argument: it would sit in the plan's arguments and the agent's
`state`. The read marker is the existing way an answer says "this came from
the device". Entropy is from the device.

*Why `Math.random` stays refused:* it isn't secure, and libraries call it
casually at module scope. A second door would bring the same meaning with
worse bytes. Its refusal message gains one clause: "or use
`crypto.getRandomValues`".

### D2b — Under the agent, a repeatable stream

Two runs of the same drive should mint the same UUIDs and show the same
screenshots (ruled; it lands with LLP 1069.007's first slice, not with
1069.009). Under `?agent=1` / `EXACT_AGENT=1`:

- `getRandomValues` and `randomUUID` draw from a deterministic generator
  seeded by the launch seed (`--seed`, default 1). The native executor
  selects it at creation; the web realm's wrapper does the same.
- The read marker still moves, so bake behaviour is unchanged.
- It is host-side and agent-only: never in a bake, a release build, or a
  run without the agent flag. A test asserts a non-agent boot draws from
  the OS.
- ECDSA `generateKey` and `sign` stay non-repeatable on the web, where the
  browser draws its own nonce. Neither a key nor a proof reaches `state` or
  a screen, so nothing an agent compares differs.

### D3 — Not during module initialization

Both entropy functions refuse while the module is initializing, with LLP
1027.000's message form ("`crypto.randomUUID()` is unavailable during
module initialization; call it inside an answer"). A module-scope random
value would be one hidden input shared by every answer, with no read to
count. Digests are allowed anywhere.

### D4 — The seed stays, for ids that should repeat

`exactTime().seed` is kept, and its role narrows to what it is good at: ids
that must be distinct within a launch and **identical when the inputs are
identical**. Examples are client keys for rows the app creates and throws
away, or a shuffle. It is 53 bits, drawn once per launch, and set by the
agent or a test. LLP 1027.000 D1 still applies: the id scheme is the app's
pure function (epoch, seed, a counter in its store), not a runner stdlib
entry.

The rule an author reads, in the generated declarations' comment:

- `randomUUID` for anything that leaves the device or must not be guessed.
- The seed for anything a replay should reproduce.

### D5 — Rust parity

`exact-data` gains `crypto::{digest, random_bytes, random_uuid}`.
`random_*` take the store handle a source already holds and call
`observe_external_read`, so a Rust source's bake and re-ask behaviour
matches a TypeScript source's.

- **Native Rust:** `getrandom` and `sha2`, both in the lockfile.
- **A Wasm logic module (LLP 1029.000):** entropy through the engine's
  existing host-call path, since `getrandom` in a Wasm guest has no source
  of its own. Which import that is gets confirmed while building. The Rust
  side's behaviour (bytes, marker, refusal) is the contract.

The crate can't stop a Rust provider from calling `getrandom` directly (LLP
1027.000 D4: trusted Rust is not sandboxed). The helpers exist so the right
way is the short way.

### D6 — Contract gets nothing

No `randomUUID()` or `digest()` in Contract's stdlib. Ids belong to the data
layer that stores them, and a view that needs a key has the row's. A
Contract-only app that wants a throwaway key reads `exactTime().seed`.

## What an app writes

```ts
// PKCE, in the auth source (LLP 1069.006)
const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
const challenge = base64url(new Uint8Array(
  await crypto.subtle.digest("SHA-256", new TextEncoder().encode(verifier))));

// an optimistic post
const draft = { id: crypto.randomUUID(), text, pending: true };
```

## Landing

One change, every executor. Held by:

- **`js/tests/inputs.rs` extended.** Digest vectors (the empty string,
  `abc` and a 1 MiB input for each SHA-2 size) are equal on the native
  executor and in Chrome. SHA-1 and `encrypt` refuse by name.
  ECDSA P-256:
  - A key generated on either executor exports a JWK the other imports.
  - A signature from either verifies under the other's `verify`, in the
    test only.
  - A non-extractable private key refuses `exportKey`.
  - P-384 refuses by name.
  - `generateKey` and `sign` move the read count; `importKey` and
    `exportKey` don't.

  `getRandomValues` fills a view, refuses 65,537 bytes, and throws during
  initialization. After an answer calls it, the store's read count moved,
  and `contract::bake` emits the placeholder, not a value. Under the agent
  flag, two executors with seed 1 produce equal bytes; without it, not.
- **Rust:** a `data` test with the same vectors and the same bake result.
- **The web realms:** `crypto` is the wrapped object in both the iframe and
  the worker placement (by driving a source, not by reading the glue).

There is no new check, no new agent operation and no new grant: reading
entropy is not a capability an app declares, any more than `TextEncoder` is.

**The parity hole first.** Adding ibex2's `bindings/crypto.js` to the
native prelude (`js/build.rs:271-275` lists `pure.js`, `url.js` and
`prelude.js` only) and wrapping the web realms' `crypto` is QUEUE's "Web
and native sources disagree on `crypto`", and lands before the rest (LLP
1069 §7, Wave 0).

## Substitute

Entropy is a read, not a fact or a request (LLP 1069.007 D1 names this case
in its D6 table): its substitute is D2b's stream from `--seed`. No
`pending` entry, no answer.

## Decided

1. Entropy is a counted device read, not a refused API (D2).
2. Agent sessions get a repeatable stream now, with LLP 1069.007's first
   slice (D2b).
3. The DPoP key: a JWK under `secret.keep` natively; a non-extractable
   `CryptoKey` in IndexedDB on the web from the first cut; a host-held key
   after a security review (D1b).
4. `p256` or `ring` is the implementer's measurement (D1b).
