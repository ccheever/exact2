## Summary

Drive a finger-like interaction through the platform's own input path —
press, move, hold, inspect, reverse, release — and read the result, from
the existing driver, with no temporary pointer binary and no hand-mapped
Simulator offsets. A held sheet, a keyboard drag and a cancelled Back
become reproducible test input.

What exists: the web carrier sends real CDP mouse events; macOS sends real
`NSEvent`s through `NSWindow.sendEvent` and even accepts an undocumented
one-move `drag` that no driver code ever sends; iOS **synthesizes no
touch** — `tap` hit-tests through the window and activates the node, and
`contextmenu`/`dblclick` inject the already-recognized event
(`AgentIOS.swift:5-10`, `:160-171`, `:188-206`). What does not exist
anywhere in the tree or its history: the "pointer helper" the Messages
record mentions, any desktop pointer synthesis, any Simulator
window-to-device mapping, any scripted normal-mode drive. Every held-drag
claim in the record was produced by hand and cannot be repeated by a
script.

Decisions: **a contact is a sequence of `tap` forms with phases** (D1),
**every input reply names its delivery class, carrier and mode** (D2),
**capability is reported per carrier and unsupported is a reply, not a
substitute** (D3), **a held contact never blocks reads, and cleanup is
scoped to the run's contact** (D4), **two clocks: the runner's is seeked,
the platform's is bounded, and a launch may keep platform timing under
the agent carrier** (D5), **replay is a script from a fixture state, at
two placements** (D6), and **the driver never fakes an outcome** (D7). The
feasibility gate (§3) decides the Simulator backend.

## 1. Motivation — the input paths as they are

| carrier | `tap` today | real platform event? | file |
|---|---|---|---|
| web | CDP `Input.dispatchMouseEvent` pressed/released at the box centre; `wheel`, `hover`, `contextmenu`, `dblclick` likewise | yes (Chrome synthesizes the click) | `agent.mjs:200-216` |
| macOS | `NSWindow.sendEvent` mouse down/up; `drag: [x,y]` one `leftMouseDragged` between them (never sent by the driver); wheel as an in-process `CGEvent` to the hit view | yes, in-process | `AgentMac.swift:115-184` |
| iOS simulator / device | window hit-test → nearest `NodeView` → focus by the touch-up rule → `presenter.press(id)`; `contextmenu`/`dblclick` → the presenter's handler directly, `injected: true` | **no** | `AgentIOS.swift:151-207` |
| linux | `tap` + `wheel`, `type` + `text` only; `hover` falls through to a press, `type … key` to setting `""` | its own | `host/linux/src/agent.rs:82-98` |

Agent mode also changes what a gesture *could* show: iOS pushes, pops and
sheet presentations run `animated: false` and keyboard changes apply at
once (`NavigationIOS.swift:113`, `ModalIOS.swift:117,144`,
`PresenterIOS.swift:137`); the web freezes and seeks every animation
(`glue.js:661-672`). So an interactive UIKit transition — the thing
Messages needed to verify — is observable only in a launch without agent
mode, which today means no carrier at all. LLP 1008 §9 already says
"physical gesture verification must also run outside that mode."

The record's unexplained failures are the cost of the missing path: an
outside-dismiss tap at (390, 170) missed once in normal mode and passed
under the agent; the first inbox drive of a session missed its gesture and
another lost its row; physical taps in the leading action area appeared not to
reach the authored control while the agent's activation did; a badge
wrapper "regressed intermittently" under physical taps and was reverted.
These observations were not reproducible through the eight-operation driver.

**Evidence update, 2026-09-10:** a separate reaction investigation reproduced a
browser covering the Simulator. With the named window raised and foreground
checked before each input, temporary scripts now pass Read/Unread with actual
drags/taps, reversal, row switching and draft/history retention; an ordinary
launch also passes both actions. No runtime repair was needed. This removes the
leading action from the current unexplained failures without attributing every
old miss to that cause. The scripts still depend on a desktop-to-Simulator
mapping outside the driver, so D3/D6's supported delivery path remains owed.
Evidence: `apps/messages/README.md`, `/tmp/messages-leading-foreground/`.

## 2. Decisions

### D1 — A contact is a sequence of `tap` forms with explicit phases, in the viewport space

One contact per session in this slice. Forms (CLI and wire):

```
tap <target> down [at <x> <y>]      {"op":"tap","id":V,"phase":"down","x":X,"y":Y}
tap move <x> <y> [over <ms>]        {"op":"tap","phase":"move","x":X,"y":Y,"ms":M}
tap move by <dx> <dy> [over <ms>]   {"op":"tap","phase":"move","dx":DX,"dy":DY,"ms":M}
tap hold [<ms>]                     {"op":"tap","phase":"hold","ms":M}
tap up                              {"op":"tap","phase":"up"}
tap cancel                          {"op":"tap","phase":"cancel"}
```

`tap <target>` unchanged: down and up at the centre. Coordinates are the
viewport space of LLP 1012 §1 — the one `layout` reports — so a target
resolved from a fresh `layout` and a path written in points need no other
mapping; `at` is relative to the target's box, `move` absolute in the
viewport, `by` relative to the contact. A `move … over <ms>` is delivered
as a sequence of moves spaced by the carrier's frame interval (the platform
recognizes velocity from them). The driver keeps the contact's state (down
point, current point, carrier handle); a second `down` while one is held is
refused. The macOS `drag` shape is retired into these. One contact; a
second contact, multitouch and recording are outside this slice.

Before `down`, the driver revalidates the target against a fresh `tree`
(1035.002 D3's identity) and the window mapping (D3); a resize, a missing
target or a stale mapping refuses. Once down, the path is the declared
path — the driver does not chase a moving target.

### D2 — Every input reply names its delivery class, carrier and mode

`tap` and `type` replies gain:

```
delivery: "platform" | "recognized" | "activation" | "unsupported"
carrier:  "web" | "macos" | "ios-sim" | "ios-device" | "linux"
mode:     "agent" | "platform"          (D5)
```

`platform`: a real input event entered the platform's input path (CDP
mouse/touch, `sendEvent`, a desktop pointer into the Simulator);
`recognized`: an already-recognized event was injected (iOS `contextmenu`/
`dblclick` today); `activation`: a hit-test and a direct press (iOS `tap`
today). The transcript renders it (`tapped #12 [send] platform ios-sim
agent`). A screenshot taken after an `activation` in agent mode is
evidence of the action, never of a gesture; the reply says which.

### D3 — Capability is reported per carrier; unsupported is a reply, never a substitute

`open()` and `state` report `input: { contact: bool, hold: bool, delivery:
… }` per carrier. Expected after §3's proof:

- **web**: contact and hold — CDP `Input.dispatchMouseEvent` phases, and
  `Input.dispatchTouchEvent` (`touchStart`/`touchMove`/`touchEnd`/
  `touchCancel`) for a finger under touch emulation; both real.
- **macOS**: contact and hold — `sendEvent` `leftMouseDown` /
  `leftMouseDragged` / `leftMouseUp`, the state held across requests
  (AppKit tracking loops are not entered because `NodeView` handles its
  own mouse events; the proof checks a scroll view's pan too).
- **ios-sim**: the feasibility gate's backend (§3). The mapping — the
  Simulator window's frame from the window list, its device size and
  scale from `simctl` — lives in one place in the driver
  (`scripts/agent.mjs`, `phaseSim`) and nowhere in an app test.
- **ios-device**: `unsupported` for contacts until an XCTest bundle
  exists; `tap` stays an activation, labelled.
- **linux**: contact through evdev when that carrier lands (LLP 1015's
  lane); today `unsupported`, and the carrier's two silent fall-throughs
  (`hover` → press, `key` → `""`) become refusals in this slice.

A carrier that cannot hold, reverse or capture while down replies
`unsupported` and the case stays visibly unverified in the smoke's output.
Action dispatch is never substituted for a contact.

### D4 — A held contact blocks nothing, and cleanup releases only the run's contact

Every candidate backend injects from outside the app's main thread (CDP,
a posted desktop event, `sendEvent` from the agent's run-loop turn that
returns before the next request), so `layout`, `state` and `screenshot`
proceed while a contact is down; the proof asserts a `layout` reply
arrives within one frame interval while held. On failure, timeout or
disconnect the driver sends `up` or `cancel` for its own contact only; a
desktop backend restores the cursor and never exits with a button down;
nothing kills another process (`rules/RULES.md` §Fleet: only recorded
PIDs, and the Simulator is not one).

### D5 — Two clocks; the platform's is bounded, never seeked; a launch may keep platform timing under the agent carrier

The runner's clock and Exact motion are seeked (LLP 1002 D3, LLP 1012 §2).
UIKit's recognition and transitions run on the platform clock and cannot
be seeked; `clock settle` must not claim to advance a sheet, and a normal-
mode claim must not be tested with native animation frozen.

Two additions. **(a)** `EXACT_AGENT=1` keeps the carrier; a second launch
knob, `EXACT_AGENT_TIMING=platform` (`open({timing: 'platform'})`), leaves
UIKit's animations at their natural durations and the keyboard's own
curve while the driver still owns the runner's clock — the "ordinary app"
with a socket. Replies say `mode: "platform"`. **(b)** Under it, `clock
settle` also waits, bounded, for the host's `navigation.transition.phase`
(1035.002 D2) to return to `idle` and the keyboard's animation to end,
exactly as it waits for requests in flight (LLP 1016): `settled: false`
with `reason: "transition"` at the bound. Injection and observation carry
`observed.wall` beside `clock` so a sequence can be read against both.

### D6 — Replay is a script from a fixture state, at two placements

A gesture case is the CLI's argument list or a `test` block (LLP 1017.000
P7) run from a known state — the app's fixtures, an empty store, the
runner clock at zero — and checked at its checkpoints (`layout`,
`state`, `screenshot` after `hold`, after the reverse, after `up`). It is
run twice on the Simulator: with the window at a second desktop position
and at the other device scale (2× / 3×), and the checkpoints must agree.
This is reproducible input, not a recorder and not a promise of
bit-identical OS timing.

### D7 — The driver never fakes an outcome

No backend may emulate a drag by setting a scroll offset, invoking a Back
action, or calling a recognizer's handler. The app receives whatever the
platform delivers from the injected input, or the reply says
`unsupported`.

## 3. Feasibility gate and first slice

**Gate (before any Messages case):** one carrier holds a contact across
down / move / hold / reverse / up while `layout`, `state` and `screenshot`
answer, on the compose sheet: `tap compose-header down`, `tap move by 0
200 over 300`, `tap hold`, `layout new-message-sheet` (the sheet's
`window` box at y≈252, the composer beside the keyboard), `screenshot
held.png`, `tap move by 0 -200 over 300`, `tap up`, `state` (route
unchanged, draft intact). The web and macOS pass this on the paths named
in D3 first; they are the parity baseline.

**Simulator candidates**, evaluated against that exact requirement:

1. **Desktop pointer into the Simulator window** — the driver posts
   `CGEvent` mouse down/drag/up at the mapped screen point (Simulator
   window frame from `CGWindowListCopyWindowInfo`, device size from
   `simctl`, scale from the two). Needs Accessibility permission for the
   driver's process; no app code; the path the record used by hand
   (System Events). Risks: the window must be frontmost and unobscured;
   the mapping must exclude the window's chrome; a modal's sheet is in the
   same window so no second offset exists — the record's "another offset"
   was the hand mapping's, not the platform's.
2. **An XCTest UI bundle** — `XCUIApplication` coordinates with
   `press(forDuration:thenDragTo:withVelocity:thenHoldForDuration:)`
   for a scripted hold; interleaving reads while held needs a test that
   waits on the driver's socket mid-gesture. More machinery, real touches
   (HID through the runner), and the only route to a physical device.
3. **In-process touch synthesis** — refused: private API compiled into the
   production host.

Recommendation: prove 1 first (a day), then 2 only if 1 cannot hold or
cannot run headless on the fleet. The decision is Charlie's after the
numbers (LLP 1035 §6 item 2).

**Then the slice:** the phases in `agent.mjs` for web and macOS; the
Simulator backend chosen; the delivery/carrier/mode fields in every input
reply and the transcript fixture; D3's capability report; the Linux
carrier's fall-throughs turned into refusals; the macOS `drag` shape
removed. **Verified through it**: keyboard interactive dismissal and
reversal; empty-sheet dismissal; populated-sheet resistance; the
horizontal timestamp reveal and return; Back cancelled and completed with
a populated draft — each at rest, held, reversed and released, each at
two placements (D6), each with the reply's delivery class in the
transcript. The record's three unexplained normal-mode failures are
re-run through it and either reproduced or closed as the hand path's.

## 4. What this deliberately does not add

A ninth operation (`rules/NOT-DOING.md` §Agent API — a drag is a form of
`tap`, decided 2026-08-29); pointer coordinates or moves reaching the
runner (the platform recognizes; only the completed event enters
Contract, LLP 1005 §3); an Exact gesture arena or a second motion graph;
session record/replay; multitouch; private event synthesis in a shipped
host; a promise about physical-device gestures before a backend exists.

## 5. Open questions

- Should `move … over <ms>` be delivered on the carrier's real frame
  interval (platform timing) or as a burst with synthetic timestamps? The
  former is the only honest one for recognition thresholds; the latter is
  faster. Leaning: real interval, and the gate measures it.
- Does the web's touch emulation (`Emulation.setTouchEmulationEnabled`)
  need to be on for `dispatchTouchEvent`, and does it change Chrome's
  hover/click behaviour for the mouse forms? Checked at the gate.
