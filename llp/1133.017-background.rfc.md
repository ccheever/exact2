## Summary

Two modules let an app's own code run while the person is not using it:

- **`@exact/background`** runs a handler when the system wakes the app:
  once, at the next chance it gives the app to run while online
  (Background Sync's `sync`), or every so often (Periodic Background
  Sync's `periodicsync`).
- **`@exact/background-transfer`** hands an upload or a download to the
  system, which finishes it after the app has left the screen, been
  suspended or been terminated, and then tells the app (Background
  Fetch's `backgroundfetchsuccess` and its siblings).

Both take the WICG specifications' names on the web, iOS, macOS and
Android, with every other target of LLP 1133 D8 a visible `later` or
`absent`:

```
use registerSync, registerPeriodicSync, backgroundSyncStatus, sync, periodicsync,
  BackgroundSyncStatus, SyncEvent from "@exact/background"
use backgroundfetchsuccess, backgroundfetchfail, BackgroundFetchRegistration
  from "@exact/background-transfer"

resource background = backgroundSyncStatus() as shape BackgroundSyncStatus
action notifyWhileClosed
  registerPeriodicSync(tag="catch-up", minInterval=1800000)
action caughtUp(tag: string)
  send caught = catchUp(persona)
action flushed(tag: string, e: SyncEvent)
  send flushed = flushOutbox(tag)
action uploaded(id: string, r: BackgroundFetchRegistration)
  send attached = attachPhoto(r)
view
  column periodicsync=caughtUp sync=flushed backgroundfetchsuccess=uploaded
    …
```

```ts
import { registerSync } from "@exact/background";
import { backgroundFetch } from "@exact/background-transfer";

if (!round.ok) await registerSync({ tag: `outbox:${persona}` });   // a round failed: retry at the next chance
await backgroundFetch({ id: `photo:${local}`, title: "Sending photo",
  requests: [{ url: `${origin}/assets`, method: "POST", headers, bodyFrom: path }] });
```

Tier 2 reaches `BGProcessingTask`, iOS 26's `BGContinuedProcessingTask`,
WorkManager's constraints and expedited work,
`NSBackgroundActivityScheduler`'s tolerance and quality of service, and a
background `URLSession`'s network policy. Tier 3 hands the app's Swift
each `BGTaskRequest` before it is submitted and each `URLSessionTask`
before it starts, and its Kotlin each `WorkRequest.Builder`.

Most of this RFC is not about names. It decides what a **wake** is, for
these modules and every later one that needs the app to run while it is
closed (geofencing, Bluetooth restoration, a data-only push, HealthKit's
background delivery): a launch with no first pixel, run by the host's own
code at the moment the platform requires, booting the session with no
view, delivering one declared event per due registration as an invocation
that owns its work, ending when that work settles or its budget runs out,
and never opening anything a person must see (§4).

The consumer is Harmony (`apps/harmony`), the team chat, which today
loses all three: a message written offline waits in its outbox until the
app is opened again, nothing tells the person they were mentioned while
the app was closed, and it cannot send a photo at all. With these modules
the outbox flushes at the next chance the platform gives, a periodic catch-up
posts a notification for a new mention, and a photo finishes uploading and
is sent after the person has left the app (§11).

## 0. What is new here

Writing the two modules out shows six things the parent RFCs and LLP
1114.001's stage 2 did not settle, each decided below and ruled in §15.

1. **A wake is a launch that never draws.** The boot path's rule is that
   no app code runs before first pixel (`rules/RULES.md`), and LLP
   1133.004 D6 delivers an event that starts the app after first pixel. A
   wake launch never has a first pixel. The rule for it: the session boots
   with no view, the event is delivered after that boot, and a person who
   opens the app during the wake gets the first pixel from the session as
   it stands, never after the wake's work (D7).
2. **The platform's entry points are the host's, not the package's.**
   `BGTaskScheduler` requires every launch handler registered "before the
   end of `applicationDidFinishLaunching(_:)`"
   ([register](https://developer.apple.com/documentation/backgroundtasks/bgtaskscheduler/register(fortaskwithidentifier:using:launchhandler:))),
   and a background `URLSession` must be recreated during the launch the
   system makes for it. A package's code loads with the app's module after
   first pixel (LLP 1024 D3), too late for either. So the host registers
   the entry points and keeps the one refresh request iOS allows; a package
   asks the host for wakes and is dispatched to (D8), as LLP 1133.004 D7
   keeps the notification delegate in the host.
3. **A wake's lifetime is the work its events own.** Each due
   registration's event is an invocation with LLP 1113 D4's owner set; the
   wake ends when every set is empty and the storage they started has
   landed, or when the module's budget (30 seconds, the tightest
   platform's) or the platform's own expiry comes first (D6).
4. **The web's names replace LLP 1114.001 stage 2's `wake` mark.** Its
   `task inbox when signedIn wake` was chosen because `periodicsync` fires
   in a service worker on the browser's schedule, not as a page timer.
   Here it fires on the system's schedule in a session that boots with no
   page, which is a service worker's place, so the objection no longer
   holds, and LLP 1133 D1 asks for the web's names where the web has the
   capability (D1, Q1).
5. **A transfer outlives its session and its process.** Its record is
   durable before the platform is told it was handled, its downloaded
   files are moved inside the callback that hands them over, and its
   ending event is delivered again at each launch or wake until the app
   retires the registration, keyed by its id (D10).
6. **A transfer's credentials stay below the seam.** A request's headers
   carry the app's tokens (LLP 1018 D5), so a transfer is started from data
   code only, its headers and its URL's query never enter Contract, the
   journal or the agent's state, and a token that expires while the system
   holds the request fails the transfer for the app to retry (D3, D10).

## 2. Tier 1: `@exact/background`

### D1 — Background Sync's and Periodic Background Sync's names

| Name | Kind | The web's | Deviation |
|---|---|---|---|
| `registerSync(tag=)` | send, answers nothing | [`SyncManager.register(tag)`](https://wicg.github.io/background-sync/spec/#dom-syncmanager-register) | named for the module, since imported names share the app's namespace (as `requestNotificationPermission`, LLP 1133.004 D1) |
| `syncTags()` | live source, a fact | `SyncManager.getTags()` | a live source: re-asked when a tag is added or retired |
| `registerPeriodicSync(tag=, minInterval=)` | send, answers nothing | [`PeriodicSyncManager.register(tag, {minInterval})`](https://wicg.github.io/periodic-background-sync/#dom-periodicsyncmanager-register) | as `registerSync` |
| `unregisterPeriodicSync(tag=)` | send, answers nothing | `PeriodicSyncManager.unregister(tag)` | as `registerSync` |
| `periodicSyncTags()` | live source, a fact | `PeriodicSyncManager.getTags()` | as `syncTags` |
| `backgroundSyncStatus()` | live source, a fact | `permissions.query({name: "periodic-background-sync"})` and `{name: "background-sync"}` | one fact for both, in LLP 1133.002 D8's shape (D14) |
| `sync` | event, on the app's root, raised by a wake | the service worker's [`sync`](https://wicg.github.io/background-sync/spec/#sync), a `SyncEvent` with `tag` and `lastChance` | delivered to the root's handler in a session that may have no view, not to a service worker (D5) |
| `periodicsync` | event, on the app's root, raised by a wake | the service worker's [`periodicsync`](https://wicg.github.io/periodic-background-sync/#periodicsync-event), with `tag` | as `sync` |

**What a registration means.**

- A `sync` registration fires once, at the first chance the platform
  gives the app to run while online: at once if the app runs and is online
  ("If the user agent is currently online, fire a sync event for
  newRegistration", the spec's `register`); else when it next does, which
  on Android is when the network returns and on an iPhone is the next
  refresh wake or launch (D2). It is retired when its event's invocation
  completes.
- **Retrying.** A handler that registers its own tag again before its
  invocation completes keeps it pending, the spec's "re-registered while
  firing", which is how an app retries (the outbox is still not empty). Such
  a registration is not eligible again until a backoff has passed (5
  minutes, doubling each attempt, at most an hour; on Android a new
  `OneTimeWorkRequest` with that `setInitialDelay`, ordinary even where the
  first was expedited, since WorkManager refuses a delayed expedited
  request, the worker itself having returned `Result.success()`) and then
  fires at the next
  chance, never at once: the spec's failed event waits "a user agent defined
  length of time" before it is retried, and here the same holds for a
  handler that failed on its own terms, so a server that refuses while the
  radio is up cannot make the app spin.
- A `periodicsync` registration fires no sooner than `minInterval` after
  its last run, its first time no sooner than `minInterval` after it was
  registered, at a time the platform chooses, while online ("Wait until
  online", the spec's §7.1). The spec calls `minInterval` "a suggestion to
  the user agent"; here it is a floor every target keeps (D2 sets Android's
  flex so), and the platform may stretch it without bound: iOS may wait
  hours, or never come, in Low Power Mode or with Background App Refresh
  off.
- **The interval's floor is 15 minutes,** WorkManager's minimum ("The
  minimum repeat interval that can be defined is 15 minutes",
  [define work](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)).
  A literal below it is refused at bake (`background-interval`); a
  computed one is raised to it, with a journal line.
- **Tags are the app's.** A tag is a string of at most 64 bytes; a tag
  registered again replaces its options. A registration belongs to the
  session that made it, by the session's label, so an embedded host's two
  sessions keep two sets (LLP 1031), as LLP 1133.004 D7 routes a click by
  the posting session.
- **`lastChance`** is true on the third attempt in a row that did not
  retire the registration (one the handler registered again, one that
  expired, D6, or one superseded, D5). After that attempt the registration
  is retired unless its handler registered it again during it, which keeps
  it pending at the longest backoff and starts a new count: an app that
  keeps asking is retried hourly, never in a loop. The spec leaves the
  count to the user agent ("based on some user agent defined heuristics");
  three is exact2's, declared. An expiry before the event was delivered (a
  boot that used the budget) is not an attempt.

**Errors,** by the web's names: `NotSupportedError` where the target has no
such capability (§9); `NotAllowedError` while `backgroundSyncStatus().state`
is `denied` (the spec's "If the user has disabled background sync, reject
promise with an NotAllowedError"); `TypeError` for a bad tag or interval,
which the bake refuses first where the value is literal.

**Declared deviations,** each because the web's form does not fit Exact:

- the events go to the root's handler, imported with their shapes, as
  LLP 1133.004 D6's `notificationclick` does; there is no service worker
  and no `waitUntil` (the invocation's owned work is the extension, D6);
- `register` answers nothing and refuses rather than rejects a promise in
  Contract (a journal line, as an answerless send's refusal is, LLP
  1133.004 D5); data code's binding rejects;
- `register` may be called from a wake (the spec refuses a registration
  from a service worker, "If isBackground is true, reject promise with an
  InvalidAccessError"), because re-registering from the handler is how an
  app retries here.

**Values.** `syncTags()` and `periodicSyncTags()` answer a list of
`{tag, minInterval, lastRun}` (`minInterval` and `lastRun` `none` for a
one-shot), the agent-visible list the substitute keeps (§10).

### D2 — Unsaid defaults are the platform's

| Unsaid | Web | iOS | macOS | Android |

**The shared word means "at the next chance", not "the moment the
network returns".** iOS has no wake for the network coming back: a refresh
wake comes when the system chooses, and a processing task "run[s] only
when the device is idle"
([`BGProcessingTask`](https://developer.apple.com/documentation/backgroundtasks/bgprocessingtask)).
So on an iPhone a `sync` registered while offline fires at the next refresh
wake, overnight, or when the person opens the app; on Android it fires
when the network returns. That difference is the platforms', and the
module declares it rather than hide it (the recipe says it), and an app
whose bytes must leave promptly
hands them to a transfer (D3), which the system itself starts when the
network returns. Harmony's outbox is a sync round, not one request, so it
uses `sync` and says so (§11).

The budget is 30 seconds on every target because iOS gives a refresh wake
"up to 30 seconds of background runtime"
([choosing background strategies](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)),
and a handler written for one platform should finish on all of them. An
app that needs longer on iOS writes `apple.task="processing"` (D12).

A hand-built app shows nothing while it refreshes in the background, and
neither does this module. LLP 1133 D4's tell test holds: no indicator, no
notification of its own.

## 3. Tier 1: `@exact/background-transfer`

### D3 — Background Fetch's names

| Name | Kind | The web's | Deviation |
|---|---|---|---|
| `backgroundFetch(id=, requests=, title=, downloadTotal=)` | send, answers `BackgroundFetchRegistration`; data code only | [`BackgroundFetchManager.fetch(id, requests, options)`](https://wicg.github.io/background-fetch/#background-fetch-manager-fetch) | requests are records, a body is a file (below); `icons` is out |
| `backgroundFetchRegistration(id=)` | live source, a fact | `BackgroundFetchManager.get(id)` and the registration's `progress` event | a live source: re-asked as the transfer progresses, at most once a second |
| `backgroundFetchIds()` | live source, a fact | `getIds()` | — |
| `abortBackgroundFetch(id=)` | send, answers `bool` | `BackgroundFetchRegistration.abort()` | by id |
| `retireBackgroundFetch(id=)` | send, answers nothing | none: the web retires a registration when its event's `waitUntil` settles | the app's acknowledgement that it has kept what it needs; until then the event is delivered again (D10) |
| `backgroundFetchStatus()` | live source, a fact | `permissions.query({name: "background-fetch"})` | in LLP 1133.002 D8's shape (D14) |
| `backgroundfetchsuccess`, `backgroundfetchfail`, `backgroundfetchabort` | events, on the app's root, raised by a wake | the service worker's events of those names, a `BackgroundFetchUpdateUIEvent` with its `registration` | as `sync` (D1); `updateUI` is out |
| `backgroundfetchclick` | event, on the app's root, an activation (LLP 1133.004 D6) | the service worker's `backgroundfetchclick` | raised only where the platform shows the transfer (Android's notification, D4) |

**A request** is a record, not a `Request`: `{url, method, headers,
bodyFrom, saveTo}`.

- `bodyFrom` is an `app:/` file, sent as its bytes, admitted against the
  calling source's `fs.read`, as `fetch`'s `exactBodyFrom` is. There is no
  body in memory, because a background session takes "only upload tasks
  from a file (uploads from data instances or a stream fail after the app
  exits)"
  ([Apple](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background)).
  Before `backgroundFetch` answers, the host copies the file into its own
  transfer directory (a clone on APFS), so a body in `app:/tmp`, which the
  system may purge, is still there for a retry hours later. No size cap of
  exact2's own; the server's and `downloadTotal` bound it.
- **Every response body is a file,** an upload's as well as a download's,
  because the response may be large and arrives while no answer runs. With
  `saveTo`, it is that `app:/` file, admitted against the source's
  `fs.write`, and the app's from then on. Unsaid, it stays in the host's
  transfer directory, which is `app:/data/transfers/`, the durable root, not
  purgeable: the record's `path` is `app:/data/transfers/<id>/<index>`,
  readable by the session's data code with no grant (a read-only prefix,
  as `app:/tmp/<extension>/` is a writable one, LLP 1133.008 D8 item 4,
  and written only by the host) until the registration is retired (D10); a
  handler that keeps it copies it first. The upload copies and the record
  live there too.
- `url` is admitted against the source's `net.fetch` lines, as `fetch` is.
  Only `http` and `https`: a background session supports "only HTTP and
  HTTPS protocols", and it always follows redirects (Apple, the same page).
- `headers` are sent as written and are never shown (below). Where the
  carrier is the app's own process (Android, D4), a retry after the process
  died needs them again, so the host keeps the headers and the URL's query
  in the secret store `secret.keep` uses, readable after the first unlock,
  keyed by registration, and deletes them on retirement; never in the record.

**A registration** answers `{id, uploadTotal, uploaded, downloadTotal,
downloaded, result, failureReason, records}`, the web's fields, with
`result` `""`, `"success"` or `"failure"` and `failureReason` the web's
`""`, `"aborted"`, `"bad-status"`, `"fetch-error"`, `"quota-exceeded"`,
`"download-total-exceeded"`. Each **record** is `{index, url, status,
contentType, path}`: the request's position, its URL **without query or
fragment**, the response's status and `Content-Type`, and the file its
body is in. The web's `match()` and `matchAll()` answer `Response`
objects; here the record names a file (a declared deviation): a response
that arrived while the app was terminated has no stream to hand over.

**Why data code only.** A request carries the app's credentials (an
`Authorization` header, a signed URL), which never enter Contract (LLP 1018
D5), and its grants are a source's (`net.fetch`, `fs.read`, `fs.write`),
which a Contract action does not have. So `backgroundFetch` is declared
`"callers": ["data"]` (D15 item 6): the bake refuses a Contract `send` of it
(`contract-module-caller`), and data code calls it through its binding.
Contract reads the registration, hears the events and may abort.

**Disclosure.** The journal, `pending`, `state.extensions` and every
answer show a request's method, its URL's origin and path, the sizes and
the paths; never a header's value, a URL's query or fragment, or a body
(LLP 1069.007 D7 item 4: a credential shows its presence only).

**Errors:** `TypeError` for an `id` that an active registration already
has (the spec's), a bad request or an `http` URL the app's ATS policy
refuses; `NotAllowedError` for an ungranted URL or path, and while
`backgroundFetchStatus().state` is `denied`; `NotSupportedError` where the
target has none.

## 4. Wakes

### D5 — What a wake is

A **wake** is the platform running the app for a reason a module
declared, while the person may not be using it: a refresh window, a
processing window, a network condition met, a transfer's events. It
reaches the app as one or more **wake events**, module events (LLP
1133.004 D6) declared `"raised": "wake"`:

```json
{ "event": "periodicsync", "on": "root", "raised": "wake",
  "args": ["string"], "hold": 16, "budget": 30000 }
```

- **Origin.** A wake event's commit has origin `wake` (`CallOrigin::Wake`),
  and so does everything it causes, by LLP 1133.002 D12's causation rule:
  its mutations, the requests they make, the re-asks they cause, data
  code's calls under their answers. This holds whether or not the app is
  on screen: a `sync` that fires while the person is looking at the app is
  still not the person's act, as LLP 1133.004 D6 says of every event a
  package raises.
- **Invocation.** Each event is an invocation with LLP 1113 D4's owner
  set, as a tool call's is. Two due registrations are two invocations,
  each delivered once, in order, each its own commit, **one at a time**:
  the next is delivered when the one before has completed or expired, as
  LLP 1113 D4 serializes tool calls, so two owners never share a request.
- **Superseded.** A commit outside the invocation (the person's, or the
  app's own code in a view) that replaces or forgets work the invocation
  owns ends it `superseded`, by LLP 1113 D4's rule. A superseded `sync`
  stays pending and counts as an attempt (D1); a superseded `periodicsync`
  counts as run, since the work it asked for was done by the commit that
  replaced it; a superseded transfer event is delivered again (D10).
- **Wakes are serialized per session.** A platform callback that arrives
  while a wake runs (Android may start a periodic worker, a sync worker and
  a transfer job together) is queued, and its events are delivered when the
  running wake has ended. Each platform object is completed by its own wake;
  one that the platform expires while queued is completed unsuccessfully
  with nothing delivered.
- **Who raises it.** Only the host, at the platform's call (D8). A package
  asks for wakes and names which of its events a wake raises; it cannot
  make a wake-origin commit any other way, so no package can run app code
  in the background without the platform's consent and a grant line (D14).
- **Held, and bounded,** as LLP 1133.004 D6: an event that arrives before
  the root's handler is mounted is held up to `hold`, in order.

### D6 — What a wake may run, and when it is done

**Runs** in a commit the wake owns: every Contract construct; data code,
with `fetch`, `storage`, `secret.keep` and `crypto` under the app's
grants; module names whose declaration admits a wake (geolocation's
`watchPosition` answers `POSITION_UNAVAILABLE` there, LLP 1133.002 D12);
`showNotification` when `notificationStatus().state` is `granted` (LLP
1133.004 §6); `registerSync`, `registerPeriodicSync` and `backgroundFetch`.

**Refused,** into the journal (`<name>: refused: during a wake`), as LLP
1114.001 D4 says and LLP 1133.002 D12's table extends to every module:

- anything that opens system UI: `share`, the pickers, `saveFile`,
  `openURL`, `openAuthSession`, `copyText`, a permission request
  (`person-required`), and every module name declared `"origin": "app"`
  or `"person"` (a capture start, LLP 1133.009 D9; `authenticate` and
  `store.unlock`, LLP 1133.010 D12);
- `playSound` and every sequence: the app holds no audio session in a
  wake;
- **before the device's first unlock since it started**, the whole wake.
  The host's boot reads the Keychain snapshot first (LLP 1018), whose items
  are `AfterFirstUnlock` (§1); the host also keeps a marker item of its own
  with that class, so an app with no secrets can tell too. A read that
  fails `errSecInteractionNotAllowed` means the first unlock has not come,
  and the host completes the wake
  unsuccessfully without booting, so a wake never boots as if signed out
  (LLP 1114.001 D4). `UIApplication.isProtectedDataAvailable` is not the
  test: it is false whenever a protected device is locked
  ([Apple](https://developer.apple.com/documentation/uikit/uiapplication/isprotecteddataavailable)),
  which is when most wakes come. The app's files have iOS's default
  protection, `completeUntilFirstUserAuthentication`, readable then too.

**Does not fire:** no `mount`, `when` or `every` timer and no frame task,
for the length of a wake in a session with no view or a hidden one (LLP
1114.001 D3). Timers resume when a view becomes visible.

**Done.** A wake is done when every invocation it delivered has an empty
owned set and the process's storage queue has drained (the runner's
`background_operations`, LLP 1097 D10). The count is the whole
process's, so a wake also waits for storage it did not start, a boot's
included: storage cannot be attributed, so the wake waits for all of it,
inside the platform's time, rather than tell the platform it is done
with a write unlanded. LLP 1113 D4 refuses a tool call while a storage
ticket exists and fails one that starts one, since it cannot attribute
background storage to an owner; a wake's handler writes (Harmony's mark,
its message), so for a wake invocation that rule is amended: it may start
storage, and the wake, not the invocation, waits for the storage to land
(§12). Other work the wake did not start neither holds it open nor is
touched by it: a cold boot's re-asked requests (LLP 1027 D4's
`data_ready`), a person's unfinished requests in a warm session.

**A session the wake booted** opens no stream resource (an `exactStream`
fetch, Harmony's `live`) until a view attaches, since nobody reads a live
feed in the background and an open socket would outlive the wake. When the
wake is done and no view has attached, the host ends that session,
cancelling the boot's requests, before it tells the platform; the next
wake or launch boots again. Then the host tells the platform
(`setTaskCompleted(success: true)`, WorkManager's `Result.success()`,
`NSBackgroundActivityScheduler`'s `.finished`, a background session's
stored completion handler).

**Budget and expiry.** A wake has one deadline: the delivery of its first
event plus the largest `budget` among the events it raises (30 s for both
modules), or the platform's expiry, whichever comes first. The boot before
the first delivery spends the platform's time, not the budget, and an
expiry during it is not an attempt (D1). iOS's expiration handler
"may be called before the background process uses the full amount of its
allocated time"
([expirationHandler](https://developer.apple.com/documentation/backgroundtasks/bgtask/expirationhandler)),
and Android stops a worker past ten minutes or when its constraints no
longer hold
([manage work](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/manage-work)).
At the deadline the runner:

1. cancels the requests the wake's invocations own that are still in
   flight, each answering as a network failure would;
2. retires their held tickets and drops their `then`s not yet run;
3. ends each invocation `expired` (journal `wake <event> <tag>: expired`);
4. waits for storage already begun, inside the platform's remaining time;
5. completes unsuccessfully (`setTaskCompleted(success: false)`,
   `Result.retry()` for a `sync`, `.deferred` on macOS). A `sync`
   registration that expired stays pending and counts towards `lastChance`
   (D1).

An app that moves a cursor (Harmony's "mentions notified up to") moves it
only after what it guards has been done, so an expired wake at worst does
the work again (LLP 1114.001 §7).

### D7 — A session with no view, and the first pixel

Every native host can boot a session with no view: the plan, the kept
answers (LLP 1027 D4), the data module and the app's native module, at the
last screen size the host recorded, `exactPage().visibilityState`
`hidden`. Before the first event is delivered, the boot lays out and
publishes one frame at that size, which nothing presents, so a view that
attaches later has a frame to show at once, without waiting on the owner
thread (on Android the main thread only replays a published stream,
`host/android/canvas`'s `Owner`).

| Host | A wake with no session | A wake with a session |
|---|---|---|
| iOS, iPadOS, tvOS | the process is launched with no scene; the host's handler boots the session headless, as `EXACT_PLAN` boots one before its view, and loads the module at once, since no pixel waits | the suspended session is resumed and its timers stay stopped |
| macOS | none: a scheduler fires only in a running process, which has its sessions (a window, or none under `keepRunning`) | delivered to the live session |
| Android | the process is started for the host's worker with no activity; the host boots the session on the reader's owner thread with no view | delivered to the live session |
| web | none: the page is open or nothing runs | delivered while the page is open |

**The rule for an event that starts the app,** extending LLP 1133.004 D6
to a launch that draws nothing: *an event that starts the app with a view
is held from launch and delivered after first pixel; an event that starts
it with no view is delivered after the headless boot, which never
presents. In both, the boot executes no app code before its data module is
ready, and a view that arrives during a wake takes its first pixel from
the session as it stands: it never waits for the wake's work.* A wake
launch runs app code and never has a first pixel, so `rules/RULES.md`'s
row "App JS executed before first pixel: none" does not describe it; that
row and its `boot` check stay as they are for every launch with a view,
and the row names the wake launch as outside it (Q12). A wake's boot is
measured as the wake's own cost (D18).

**A view that arrives mid-wake.** A scene that connects on iOS, or an
activity that starts on Android, attaches to the booted session (iOS's
view already fits a session booted before it; Android's activity gains the
same, stage 3). The person's commits are theirs: origin `app`, unaffected
by the wake. The wake's invocations keep their origin and run to
completion or expiry. Timers resume when the view is visible.

**Which session.** A registration or a transfer belongs to the session
that made it, by label. A wake for a label boots that session; if the
label is gone (the embedded host no longer makes it), the app's first
session (LLP 1133.004 D7's rule for a click from a previous process).
Android has one session a process.

### D8 — The host keeps the entry points; packages ask and are dispatched

The platform's wake entry points must exist before a package's code
loads, and some are one per app. So the host keeps them, and the context
(LLP 1133.009 D10) gains a way to ask for a wake and a way to be told of
one:

| Platform | Entry point the host keeps | One per | A package asks |
|---|---|---|---|
| iOS, iPadOS, tvOS | `BGTaskScheduler` launch handlers for `<bundle id>.refresh` and, per class of constraints, `<bundle id>.processing.network` and `<bundle id>.processing.network-power` (a submit "for an unexecuted task that's already in the queue replaces the previous task request", so one identifier carries one pending request, multiplexed), registered in `application(_:didFinishLaunchingWithOptions:)` on the main queue, each identifier in `BGTaskSchedulerPermittedIdentifiers` only when a grant line derives it (D14) | app: "a total of 1 refresh task and 10 processing tasks scheduled at any time" ([submit](https://developer.apple.com/documentation/backgroundtasks/bgtaskscheduler/submit(_:))) | `context.wakes.request(kind:, at:, key:, network:, power:)`: the host keeps every package's requests in its own defaults and submits one `BGAppRefreshTaskRequest` whose `earliestBeginDate` is the soonest refresh request, and one `BGProcessingTaskRequest` per processing identifier, each due at its soonest request; it submits again on entering the background and at the end of each wake |
| iOS, macOS | the transfer carrier: two background `URLSession`s, `<bundle id>.transfers` (`isDiscretionary` set false explicitly; the system may still treat a transfer started in the background as discretionary) and `<bundle id>.transfers.discretionary`, and their delegate, ExactKit's own; on iOS the one a relaunch names is made synchronously inside `application(_:handleEventsForBackgroundURLSession:completionHandler:)`, and both after first pixel of a launch whose host recorded transfers, each from its fixed configuration (D13) | app | `context.transfers.start(registration)`, `abort`, `retire`; progress and endings reach the package through its session instance |
| macOS | none needed: `NSBackgroundActivityScheduler` and `NWPathMonitor` live in the running process | — | `context.wakes.request(…)`; the host makes one scheduler per request |
| Android | one worker class, `ExactWakeWorker`, compiled into every app that binds a package using wakes, which boots the session if there is none and dispatches by its input data (package, key) | — | `context.wakes.request(…)` enqueues unique work (`enqueueUniqueWork`, `enqueueUniquePeriodicWork`, by key) naming that worker, with the package's constraints |
| web | none | — | `context.wakes.request(…)` keeps `sync` for the page's `online` event; periodic requests refuse |

A wake reaches each package whose requests are due as
`woke(_ wake: ExactWake)` on its session instance, after the session has
booted. `ExactWake` names the kind, the due keys, the platform's own
object (the `BGTask`, the `WorkerParameters`), the deadline, and
`raise(event:, args:)`, which raises one declared wake event and hands the
package its outcome (`completed`, `expired`). The host completes the
platform's task when every package it woke has said it is done.

**One refresh window, shared.** The refresh wake also carries delivery's
owed update check (LLP 1030.003), as LLP 1114.001 D5 said: the check is
the host's own request beside the packages'. A wake's budget is shared by
everything it runs, which is a cost, not a saving.

**Why the transfer carrier is the host's.** A background session must be
made again, "using the same session identifier", "as part of your launch
time setup"
([Apple](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background)),
and its delegate must move a finished download before the callback
returns. Package Swift loads with the app's module, which a launch the
system makes for the session would have to load inside the app delegate's
call, and a package class the host made from a table would be a second
kind of package object. So the session, its delegate and the durable
records (D10) are ExactKit's, as the notification delegate is (LLP
1133.004 D7), and `@exact/background-transfer`'s Apple implementation is
the thin layer that admits a call and hands it to `context.transfers`. A
third party's transfer module reaches the same carrier the same way. On
Android the carrier is the host's job service and worker (D4), for the same
reason.

**Why not the package's own registration.** A package's Swift is compiled
into the app's module and loaded after first pixel, and on iOS
"registration of all launch handlers must be complete before the end of
`applicationDidFinishLaunching(_:)`"; a second registration of one
identifier kills the app (the same page). The host registering two fixed
identifiers, and multiplexing every package's requests through them, is
what the platform's one-refresh-request rule requires anyway, and it keeps
`Info.plist` fixed per binary: a bundle that adds a tag or a registration
changes nothing the binary declares (LLP 1114.001 D5's compatibility
argument).

### D9 — A rule for delivery while the app is closed

LLP 1069.007 D7 left "background or cold-start delivery" without a rule,
and LLP 1133.004 D6 gave the cold-start half. This is the background half,
and it amends both:

> **A module whose work must run while the app is closed declares wake
> events. The host alone raises them, at the platform's call, each as an
> invocation of origin `wake` that owns its work, under a declared budget
> the platform may cut. A wake never presents, never asks a person and
> fires no timer. It ends when its invocations' work settles or its budget
> ends, and the host then tells the platform.**

Every later module that wakes the app (geofencing's regions and visits,
Bluetooth's state restoration, a data-only push, HealthKit's background
delivery) declares its events this way and adds, where it needs one, an
entry point the host keeps (D8). An entry point is a change to the host
that a person accepts, as a builder is (LLP 1133.001 D5).

### D10 — A transfer that finishes while the app is gone

The record is the truth; the event is a notice of it.

**The record.** The host keeps one durable record per registration, in
its transfer directory under the app's support directory (not purgeable,
not the runner's store, since it must be readable before a session boots):
the id, the session's label, each request's method, its URL without query
or fragment, its paths, its progress and status, `result`,
`failureReason`, the records, and how many times its ending event has been
delivered. Never a header or a query (D3). Each change is written before
the platform is told it was handled.

**Retirement is the app's.** A registration whose transfer has ended stays
until the app calls `retireBackgroundFetch(id=)`, which deletes its record
and the response files the host kept (D3). Until then its ending event is
raised again at every later launch with a view, after first pixel, and in
at most three wakes, after which it waits for the next launch; it stays
listed in `backgroundFetchIds()`, ended, so an app may also reconcile at
boot (Harmony's does, §11). So an event whose handler's write failed, whose
invocation expired or was superseded, or whose storage had not landed when
the process died, is delivered again; and a handler that retires only after
its own write has been admitted (Harmony's, §11) loses nothing. The web
retires a registration when its event's `waitUntil` settles; here the
retirement is explicit, a declared deviation, because no commit can be
made atomic with another store's write.

**On iOS,** in order:

1. The system relaunches the app in the background and calls
   `application(_:handleEventsForBackgroundURLSession:completionHandler:)`.
   The host keeps the completion handler and, before the call returns,
   makes the session with the same identifier and configuration ("You must
   configure the other options of your URLSessionConfiguration object in
   the same way",
   [handleEventsForBackgroundURLSession](https://developer.apple.com/documentation/uikit/uiapplicationdelegate/application(_:handleeventsforbackgroundurlsession:completionhandler:))).
   No session boots yet.
2. The session's delegate calls arrive, on its own queue.
   `didFinishDownloadingTo` moves the file to its destination before it
   returns, since the file "will be available until your delegate method
   returns"; an upload task's response data is appended to its file as
   `didReceive` delivers it; `didCompleteWithError` sets the request's
   status and response headers. When every request of a registration has
   ended, its `result` and `failureReason` are set and the record written.
3. At `urlSessionDidFinishEvents(forBackgroundURLSession:)` the host starts
   a wake of kind `transfer`: it boots the record's session headless (D7),
   loading the module then, and raises `backgroundfetchsuccess`,
   `backgroundfetchfail` or `backgroundfetchabort` for each ended
   registration not yet retired, with its registration as the argument. The
   budget is 30 s, cut by `backgroundTimeRemaining`.
4. When the wake is done, the host calls the stored completion handler on
   the main queue. A registration the handler retired is gone; one it did
   not is delivered again (above).

**What a relaunch reliably carries** of an upload's response is left to
measurement, since Apple documents a download's file and every task's
completion but not, for an app the system terminated, an upload's response
body. Stage 2 measures it on an iPhone before it builds (§14). The record
always has the status and the response's headers (`Content-Type` and
`Location` among them, never `Set-Cookie` or an authorization). If the
body does not survive, the record's body file is absent and its `bodyLost`
is true, and an app that needs the server's answer names the result
itself: Harmony's upload sends a key it chose, so the asset is found by it
(§11).

**Before the first unlock,** the transfer directory, which has the app's
default protection, cannot be written; after the first unlock it can,
locked or not. So only then the delegate moves a finished download, and an
upload's status, response headers and body, into a staging directory of
class `none`, with a marker naming the record, and the host calls the
stored completion handler at that relaunch's `urlSessionDidFinishEvents`,
once the files are staged, without booting a session. At the first unlock
the host moves the staged files and writes the records from the markers,
and deletes the staging directory: those bytes are unprotected at rest
until then, a cost declared here. A record still in flight whose task the
reconnected session no longer has, after that session has delivered its
queued events at a later launch, and with no marker, ends failed,
`fetch-error`, `apple.reason` `"lost"`; a marker with a known status is
`bodyLost` at worst, never `lost`. Stage 2 measures the relaunch before the
first unlock and when the reconnected session's task list is complete. No
session boots before the first unlock (D6).

**At a launch with a view,** an ended, undelivered registration's event is
held from launch and delivered after first pixel (LLP 1133.004 D6), so a
person who opens the app before a wake came sees the result.

**A person's force-quit** cancels the transfers ("the system does not
automatically relaunch apps that were force quit by the user", Apple's
`background(withIdentifier:)`): at the next launch the recreated session
reports each task cancelled, and the registration ends
`backgroundfetchabort`, `failureReason` `"aborted"`, with
`apple.cancelledReason` naming why.

**On Android,** the HTTP runs in the job's or worker's own process, the
headers and query read back from the secret store (D3) on a retry; the
record is written as each request ends, and on the last the same job
raises the events in a headless wake (D7) before it finishes, so the
platform keeps the process for it. A process killed mid-transfer is
retried by the platform from the start of the unfinished request.

**On macOS,** the delegate calls arrive while the process runs and the
events are raised into the live session; after a quit, the next launch
makes the session again by its identifier, and whatever the system
finished is delivered as at a launch with a view.

**Credentials.** The carrier keeps a request's headers for as long as it
holds the request: iOS's `nsurlsessiond` may send an `Authorization`
header hours after the app wrote it, and Android's secret store keeps them
until retirement. A token that has expired by then
fails with the server's status (`bad-status`); the app writes a fresh
token and starts again. A server that issues upload URLs for one use
(Snapback's `/assets`, S3's presigned URLs) bounds that window. The
record never holds a header; `state.extensions` shows only that a request
had headers.

### D11 — How a wake reaches data code

- **Through Contract, always.** A wake event goes to the root's handler, a
  Contract action, which reaches data code as any action does: it sends a
  mutation (`send caught = catchUp(persona)`) or refreshes a resource
  (`refresh snapshot`). Data code never hears an event directly (LLP
  1133.004 §11). LLP 1114.001 rejected a data-module export the host calls
  with no plan (its option (d)): a source returns values and an action
  applies them, and that holds in the background too.
- **Under the wake's origin.** The answer the action's mutation or
  refresh starts is owned by the wake's invocation (LLP 1113 D4), and its
  async steps resume under it (LLP 1133.002 D14's context helper), so a
  binding call from inside it, a `showNotification` or a `registerSync`,
  is admitted as `wake`. Where the context helper cannot be sure, the
  least privileged origin applies, which is `wake` itself.
- **Data code may register and transfer.** `registerSync`,
  `registerPeriodicSync` and `backgroundFetch` are bindings like any
  module's, in Promise form, from any answer.
- **The cost of the boot is the app's to bound.** A cold wake asks every
  resource of the root component, as any boot does; those re-asks are not
  the wake's and do not hold it, but they spend its network and its 30
  seconds. An app with heavy sources reads `exactPage().visibilityState`
  where the source's work is only for a person looking (the recipe says
  so).

## 7. Permission

### D14 — LLP 1133.002 §4, where nothing asks

**Declare.** Three grant lines, background modes as LLP 1069.008 D4 ruled
they become rows, with no purpose key (no platform shows one):

| Line | iOS, tvOS | macOS | Android | web |
|---|---|---|---|---|
| `device.periodic-background-sync` | `UIBackgroundModes` `fetch`; `<bundle id>.refresh` in `BGTaskSchedulerPermittedIdentifiers` | nothing | nothing of its own (WorkManager's library manifest merges the permissions it uses) | nothing |
| `device.background-sync` | `UIBackgroundModes` `fetch` and `processing`; `<bundle id>.refresh`, `<bundle id>.processing.network` and `<bundle id>.processing.network-power` | nothing | nothing | nothing |
| `device.background-fetch` | nothing (a background session needs no mode) | nothing | `RUN_USER_INITIATED_JOBS`, `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_DATA_SYNC` (the long-running worker of API 31–33, type `dataSync`) | nothing |

A use of a module name without its line is refused at bake (`grant-missing`).
`apple.task="processing"` on a periodic registration needs
`device.background-sync`'s identifiers too, refused at bake without it. The
lines are in `grantCeiling`, so adding one is a binary change and a bundle
that relies on a line its binary lacks fails the classifier (LLP 1069.008
D5). LLP 1114.001 D4 called `periodic-background-sync` "the Permissions
Registry's name"; it is the WICG specification's, and the registry lists
none of the three. `host.ios.backgroundModes` keeps only `audio`, which its
own module converts (LLP 1114.001 Q6); `fetch` and `processing` there are
refused by name, so a mode has one way to be declared.

**Read.** `backgroundSyncStatus()` answers `{available, state, periodic,
sync}` and the platforms' words; `backgroundFetchStatus()` answers
`{available, state}`. `state` is never `prompt`, because no platform asks:

| Platform state | `state` |
|---|---|
| iOS `backgroundRefreshStatus` `available` | `granted` |
| iOS `denied` (the person turned Background App Refresh off) or `restricted` | `denied` |
| macOS | `granted` |
| Android, `isBackgroundRestricted()` false | `granted` (the standby bucket is tier 2: it changes how often, not whether) |
| Android, `isBackgroundRestricted()` true | `denied` |
| web, `periodic-background-sync` queried | the browser's word (`granted`, `denied`), and `periodic` false while the cell is `later` |
| web, no such permission | `unknown` |

`periodic` and `sync` say whether each kind can fire on this target at all
(false on the web for `periodic`). On iOS a refresh status that is `denied`
also stops background transfers' wakes from coming as often, but a
transfer still runs, so `backgroundFetchStatus()` stays `granted`. The state
is read again when the app returns to the foreground and, on iOS, at
`backgroundRefreshStatusDidChangeNotification`.

**Ask.** Nothing to ask. exact2 adds no pre-prompt and no request: a
hand-built app has none, so one would be a tell. The app explains in its
own UI while `denied` and recovers through `openURL("app-settings:")` (LLP
1133.002 D11), whose page on iOS holds the Background App Refresh switch.

**Origin.** Every call carries its origin (LLP 1133.002 D12):

| Origin | `registerSync`, `registerPeriodicSync`, `unregister…`, the reads, `abortBackgroundFetch` | `backgroundFetch` | `beginContinuedProcessing` |
|---|---|---|---|
| a person's input, foreground | proceeds | proceeds; a user-initiated job on Android 34 and later | proceeds |
| the app's own code, foreground | proceeds | proceeds, as ordinary work | refused `person-required` |
| a tool invocation | proceeds under the app's grant | proceeds, as ordinary work | refused `person-required` |
| a wake | proceeds | proceeds, as ordinary work, on the non-discretionary session unless `apple.isDiscretionary`, though the system decides when a background start runs (D4) | refused |
| the development agent | §10 | §10 | §10 |

A tool may register background work and start a transfer: neither shows
the person anything or reaches what the app could not reach in front, and
LLP 1133.002 D12's direction narrows it when delegation is written. Only
the form the platform shows the person (a user-initiated job's
notification, a Live Activity) is held to a person's act, because the
platform itself requires it.

### D15 — Two packages, both extensions, and what the seam gains

```
packages/background/

  exact.json          the interface: D1's names, the wake events, the substitute
  test/               the conformance suite: a fixture app and authored tests
```

Both are extensions (LLP 1133 D5's default). What only the host can do,
the entry points and the headless boot, is a seam every package reaches
through its context, not exact2's vocabulary: geofencing and a Bluetooth
module will be third parties' as often as exact2's (LLP 1133.001 D8).

The interface, abridged, in LLP 1133.002 D13's form with LLP 1133.004's
answerless sends and events:

```json
{
  "kind": "interface", "name": "@exact/background", "version": "1.0.0",
  "grants": ["device.background-sync", "device.periodic-background-sync"],
  "substitute": "declared",
  "names": [
    { "send": "registerSync", "answers": null, "grants": ["device.background-sync"],
      "options": { "tag": "string" },
      "substitute": { "list": { "state": "background", "key": "tag", "kind": "sync" },
                      "tap": { "event": "sync", "as": "wake" } } },
    { "send": "registerPeriodicSync", "answers": null,
      "grants": ["device.periodic-background-sync"],
      "options": { "tag": "string", "minInterval": "number" },
      "substitute": { "list": { "state": "background", "key": "tag", "kind": "periodicsync" },

    { "send": "unregisterPeriodicSync", "answers": null, "options": { "tag": "string" },

  ],
  "events": [
    { "event": "sync", "on": "root", "raised": "wake", "args": ["string", "SyncEvent"],
      "hold": 16, "budget": 30000 },

      "hold": 16, "budget": 30000 }

```

**The seam additions,** each general, each proved by an out-of-tree
fixture module before these packages use it (LLP 1133.001 D8):

1. **Wake events** (D5): `"raised": "wake"` with a `budget`, delivered as
   invocations of origin `wake`; the runner's deadline, cancellation and
   expiry (D6); the refusals of D6 for every host command and module name;
   no timer while a wake runs in a session with no view or a hidden one.
   It needs LLP 1113 D4's owner set, which stage 0 builds if it has not
   landed.
2. **Headless sessions** (D7) on iOS, macOS and Android, and a view or an
   activity that attaches to one.
3. **Entry points the host keeps** (D8): the `BGTaskScheduler`
   identifiers, the Android worker; `context.wakes.request` and
   `woke(_:)`; requests kept by the host across launches; wakes serialized
   per session and invocations one at a time, with `superseded` (D5).
4. **The transfer carrier** (D8, D10): the host's background session and
   its delegate on Apple, its job service and worker on Android, with the
   durable records, the body's custody, the kept headers, the bake-time
   configuration words in `app.json` (D13), and `context.transfers`.
5. **Retirement by the app** (D10): an ended registration's event is raised
   again at every later launch with a view and in at most three wakes,
   until the app retires it.
6. **Callers** (D3): `"callers": ["data"]` on a name, refused in Contract
   at bake (`contract-module-caller`), for a name whose arguments carry
   credentials or need a source's grants.
7. **Per-target availability of a kind** (D1, D14): `periodic` false on the
   web, so `registerPeriodicSync` refuses `NotSupportedError` there while
   `registerSync` works.
8. **The declarative tap as a wake** (§10): LLP 1133.004 §7's `"tap"` raises
   its event as an activation; `"as": "wake"` raises it as a wake, with
   `"due"` naming the option whose interval must have passed.

Each is apparatus under `rules/RULES.md` and lands with this ruling.

**Android's library.** WorkManager is AndroidX
(`androidx.work:work-runtime:2.12.0`, minimum SDK 24,
[releases](https://developer.android.com/jetpack/androidx/releases/work)),
so its coordinates join the one locked, verified Gradle graph LLP 1133.008
D8 item 5 made, beside CameraX and Compose. It is Android's own advice:
"In most cases, your best option for running background tasks is to use
WorkManager"
([background tasks](https://developer.android.com/develop/background-work/background-tasks)).
The platform's `JobScheduler`, which WorkManager is built on, needs no
library and is what a user-initiated job uses anyway ("There is currently
no Jetpack library that supports UIDT jobs"); Q4 ruled WorkManager.

### D16 — Callers

Contract reads `backgroundSyncStatus`, `syncTags`, `periodicSyncTags`,

An app that imports neither module links nothing of either: no

## 10. The substitute

Wakes are the system's choice, so under the agent **no wake ever fires by
itself**: not on `clock +N`, not at `clock settle`. A drive raises each one,
and everything else is the production path.

**Shape.** `backgroundSyncStatus`, `backgroundFetchStatus`, the tags, the
ids and a registration are facts; nothing is a request; a wake is the
third shape this RFC adds to LLP 1069.007 D1 (D9).

- **The facts.** `state` is set by `prefer permission.background-sync
  granted|denied` and the launch flag `--permission background-sync=…`;
  `prefer permission.background-fetch …` likewise. Defaults: `granted`,
  `available` true, `periodic` and `sync` true, except where the target
  restricts them (the web's `periodic` false), which holds under the agent
  as LLP 1133.002 D14 step 2 says.
- **Registrations** are listed in `state.background`, by the
  declaration's list form (LLP 1133.004 §7): `{tag, kind, minInterval,
  lastRun, due, ref, session}`, `due` computed on the agent clock.
- **A warm wake** is `tap @<ref>` on a registration: the host's wake path,
  from the dispatch on: the session is marked hidden, timers stop, the
  event is raised as a wake invocation, and the drive settles it with
  `clock settle`. `tap` on a periodic entry that is not `due`, or a `sync`
  entry while `exactPage().onLine` is false (`prefer online false`), is refused by name (`not due
  until <t>`; `offline`), since the system would not wake it either.
- **A cold wake** is the launch flag `--wake '<entry>'`, whose value is an
  entry as `state.background` printed it before the app ended. The host
  boots headless through the same handler a platform wake reaches
  (`EXACT_WAKE`, LLP 1114.001 D6), raises the event, and attaches the
  window only after the wake is done, so the drive sees what a wake sees.
  An operation that needs the view (`tree`, `screenshot`) waits for the
  wake to end or expire.
- **Expiry** is `clock +N` past the wake's deadline (its start plus the
  budget, 30 000 ms) with owned work still pending: D6's steps, and the
  journal's `wake sync outbox:ada: expired`.
- **`state.wake`** shows the current or last wake: `{kind, cold, started,
  deadline, invocations: [{event, tag, state}], outcome}`.
- **Transfers** go to the agent's network, as `fetch` does: the drive's
  local server answers them, `pending` lists them, `clock settle` waits for
  them, and the drive's `fail fetch` and `pass fetch` apply. Each request
  is a `fetch` the runner makes, under the transfer's admission, with its
  body read from the file and its response written to the record's path.
  `backgroundFetchRegistration` reports the bytes as the runner counts
  them; `prefer extension background-transfer.backgroundFetchRegistration=…`
  overlays progress fields (LLP 1133.009 D10 item 11). The completion event
  is raised as a warm wake when the last request ends.
- **A transfer that ended while the app was gone** is `--wake` with an
  entry that names the event and the registration, each record's body a
  file relative to the test file that the driver copies to the record's
  path in the agent's store. So a drive starts an upload, ends the app,
  and relaunches it with the finished entry, and the app sees what an iOS
  relaunch would give it.
- **Production:** none of it. `--bind background` runs the platform under
  the agent for the conformance suites (LLP 1133.002 §10 stage 2).

**Disclosure:** tags, intervals, run times, a registration's id, origins
and paths, sizes and statuses; never a header's value or a URL's query
(D3). **Lifetime:** a registration until retired (D1) or unregistered; a
transfer record until `retireBackgroundFetch`, its event delivered again
as D10 says.

**Declared, not built in** (LLP 1133.001 D8): every form above is in the
interfaces' `exact.json`, so a third party's wake module drives the same
way: `"tap": {"event", "as": "wake", "due"}` (D15 item 8), the budget on
the event, and `--wake` reading the declaration of the event it names.

## 11. The consumer: Harmony

Harmony (`apps/harmony`) is a team chat over Snapback4 on iOS, macOS and
the web. Its writes are local-first: a message shows at once as
`pending`, and the next read runs the sync round that delivers it
(`apps/harmony/app/app.ts`); `snapshot` answers `online: round.ok`. It has
no notifications and no photos. Three small features, each a common thing
a hand-built chat app does and each one module's acceptance:

**1. The outbox goes out at the next chance** (`sync`): on Android when
the network returns, on an iPhone at the next refresh wake or launch (D2),
which the README says.

- A grant, `device.background-sync`.
- In `snapshot`, when the round fails and the device still holds unsent
  writes, ``await registerSync({ tag: `outbox:${persona}` })``: one tag a
  persona, since each persona's writes wait in its own partition.
- The root's `sync=flushed`; `action flushed(tag: string, e: SyncEvent)`
  sends `flushOutbox(tag)`, whose data code runs one round in the
  partition the tag names and, if it fails, registers the tag again, which
  then waits out D1's backoff. Snapback opens one partition at a time and
  closes the open one to open another (`snapback4/ts/snapback.ts`,
  `switcher`), so a wake never closes the partition a view holds: in a
  session with a view, a tag for another persona is registered again, to
  run when that persona is open or in a wake with no view, where any
  persona's partition may be opened.
- The web: the same, while the page is open.

**2. A mention while Harmony is closed is a notification** (`periodicsync`).

- A grant, `device.periodic-background-sync`, and `@exact/notifications`
  (LLP 1133.004, stage 1 on these three targets).
- In You, a switch "Notify me of mentions", shown while
  `backgroundSyncStatus().periodic`. Turning it on calls
  `requestNotificationPermission()` from the person's tap, then
  `registerPeriodicSync(tag="catch-up", minInterval=1800000)`; off calls
  `unregisterPeriodicSync`.
- The root's `periodicsync=caughtUp`; `caughtUp` sends `send caught =
  catchUp(persona)`. Data code runs one sync round unless the boot's
  `snapshot` finished one in this wake (the device serves one answer at a
  time, so the boot's round comes first), never the `/live` stream, reads the messages
  that mention the persona since the mark it keeps in `storage.kv`, posts
  one `showNotification({ title, body, tag: room, data: room })` per room,
  and only then moves the mark.
- A click opens the room through the root's `notificationclick` (LLP
  1133.004 D6). The web hides the switch: its cell is `later`.
- On macOS, `"keepRunning": true`, as a Mac chat app stays running when
  its window closes, so the catch-up has a process to run in.

**3. A photo finishes sending after the person leaves** (`backgroundFetch`).

- A grant, `device.background-fetch`, and `fs.read app:/tmp` and
  `fs.write app:/cache` beside the existing `net.fetch` (Snapback's
  checklist names all three).
- The composer gains a photo button: `input type=file accept="image/*"`
  (LLP 1069.002), its file shrunk to `app:/tmp/` by `compressImage`.
  Sending first writes an **outgoing photo** to `storage.kv` under the id
  it is about to use, `photo:<local id>`: the persona, the room, the reply
  it answers. Then, in data code, `backgroundFetch({ id, title: "Sending
  photo", requests: [{ url: `${origin}/assets`, method: "POST", headers:
  persona headers, bodyFrom: path }] })`, Snapback's own upload route
  (`snapback4/README.md`, "upload"). The message is not written yet.
- While it runs, the room shows a pending photo row from
  `backgroundFetchRegistration(id)`'s `uploaded` and `uploadTotal`.
- The root's `backgroundfetchsuccess=uploaded`; `uploaded` sends
  `attachPhoto(r)`. Data code finds the outgoing photo by `r.id`, so the
  persona and room are the ones the person sent it from, whatever the view
  shows now; reads the asset from the response file; writes the message
  with `{ photo: { id } }` through that persona's partition, unless one
  with this registration's id is already there (the write only admits it
  to the device's outbox and starts no round, so it never waits on the
  boot's `snapshot`); registers `outbox:<persona>`, so feature 1 sends it;
  and only then calls `retireBackgroundFetch({ id })` and forgets the
  outgoing photo. A second delivery (D10) that finds the message written
  registers the tag again, which is harmless, and retires, so a process
  that died between the write and the registration loses nothing.
  The partition rule of feature 1 holds: a photo for a persona other than
  the open one, in a session with a view, waits unretired. A task at mount,
  `task reconcile mount`, sends `reconcilePhotos()`, which lists
  `backgroundFetchIds()` and attaches each ended, unretired photo whose
  persona may be opened, so a photo whose attach failed in every wake is
  sent at the next open; it runs from an action, never inside `snapshot`'s
  partition. `backgroundfetchfail` marks the row failed with a
  retry button, and retiring it is the retry's or the dismissal's.
- If stage 2 finds that an upload's response body can be lost after the
  system terminated the app (D10's `bodyLost`), Harmony's upload sends a key
  of its own and finds the asset by it, a Snapback change (`POST
  /assets?key=`) made then.
- The schema gains a `photo` file column on messages (`snapback/schema.q`),
  and a row shows it through Snapback's `download` into `app:/cache` and an
  `image`.
- The web: `backgroundFetchStatus().available` is false, and the composer
  uses Snapback's `upload(path)` in the foreground, as it would today.

**Why Harmony.** No app in the repository needs a wake today; the Brooks
port, outside it, does (§1). Harmony already has the two halves these
modules complete: an outbox that waits for the next open, and an upload
route on its server that is "online only and never retried". A periodic
catch-up that notifies is the Bluesky clone's whole stage 2 (LLP 1114.001
§7), here on an app in the repository with a server the drives can run.
Catching up is best effort, as LLP 1114.001 Q2 said: iOS may wake the app
hours apart or not at all, and timely mentions need push (the roster's
`push`), which the README says.

**Acceptance drives,** by the agent on the web, macOS and the iOS
simulator against a local `snapback4 dev --memory` (ticket ids are read
from `state.pending` and `state.background`):

1. **Outbox.** `fail fetch "backend"`; write a message: it shows pending,
   and `state.background` lists `sync outbox:ada`. `tap @<outbox>`: refused,
   `offline`, while `prefer online false`; then `pass fetch
   "backend"`, `prefer online true`, `tap @<outbox>`, `clock settle`:
   the message is delivered, `state.wake.outcome` is `completed`, and the
   entry is gone.
2. **Cold outbox.** As 1 as ada, switch to persona B, then end the app with the entry listed and
   relaunch with `--wake '<entry>'`: the journal says `wake sync outbox:ada:
   completed` before the window attaches, and ada's message is delivered
   though the view shows B.
3. **A mention.** Turn the switch on; `tap @<catch-up>`: refused, `not
   due`. `clock +1800000`. A second session (persona B) posts `@ada` in
   #general; in persona A's app, `tap @<catch-up>`: `state.notifications` holds one
   entry for #general with the message's text; `tap @<that entry>` opens
   the room. Tapping the catch-up again posts nothing, since the mark moved.
4. **An expired catch-up.** Point the catch-up at a stand-in server that
   never answers (how `docs/contract-for-agents.md` tests a timeout);
   `tap @<catch-up>`; `clock +30000`: `wake periodicsync catch-up:
   expired`, no notification, and the mark has not moved; the next tap posts
   it.
5. **A photo.** `pick "photo" "fixtures/dog.jpg"`, send: the pending row
   shows progress, `clock settle`, and the message carries the photo; the
   journal shows the transfer's origin and path, no header; the
   registration is retired.
6. **A photo that ended while Harmony was gone.** Start one in #general as
   ada, switch to persona B and to #random, end the app, relaunch with
   `--wake` naming `backgroundfetchsuccess` and a record whose body is
   `fixtures/asset.json`: the message is written once, as ada in #general,
   and a second session as persona B sees it arrive; the same `--wake`
   again writes nothing new and retires.
7. **An attach the process did not finish is delivered again.** As 6,
   ending the app while `attachPhoto` is held (`pending`), before its write
   is admitted: the registration is not retired; the next launch delivers
   it again, after first pixel, the message is written once and
   `state.background` lists `sync outbox:ada`.
8. **Refusals in a wake.** A fixture action that calls `share` and
   `requestNotificationPermission` from `caughtUp`: both refused into the
   journal, and the wake completes.
9. **By hand, on an iPhone** (not driven by the agent): a refresh wake
   launched from Xcode's debugger
   (`_simulateLaunchForTaskWithIdentifier:`, which "work[s] only on
   devices",
   [Apple](https://developer.apple.com/documentation/backgroundtasks/starting-and-terminating-tasks-during-development))
   posts a real mention's notification with the app not running; a photo
   sent, the app left, and the phone locked, arrives in the room on

## 12. What this amends

- **LLP 1114.001 stage 2:** replaced by this RFC, which keeps its D3 (one
  request, every due dispatch its own invocation, a scene arriving
  mid-wake), D4 (nothing that needs a person runs in a wake), D5's
  compatibility argument and D6's `EXACT_WAKE`, and drops D2's `wake` mark
  for the web's names (§0 item 4, Q1). Its D7 (APNs) is the roster's
  `push`.
- **LLP 1133.004 D6:** the rule for an event that starts the app gains its
  headless case (D7); `"raised"` gains `"wake"` (D5); the declarative tap
  gains `"as": "wake"` (D15 item 8).
- **LLP 1069.007 D1 and D7:** a third shape, the wake, and the rule for
  background delivery (D9).
- **LLP 1133.009 D10:** the context gains `wakes`, `woke(_:)` and
  `transfers` (D8).
- **LLP 1113 D4:** a wake's invocation may start storage; the wake waits
  for it to land (D6). Superseded wake work is dispositioned by kind (D5).
- **`rules/RULES.md`:** the boot path's row names the wake launch as
  outside it (D7), as ruled (Q12).
- **LLP 1133 D3:** a hatch on a request one host object carries for every
  package takes nothing of the app's own (D13).
- **LLP 1069.008 D4:** three background rows; `host.ios.backgroundModes`
  keeps `audio` alone (D14).
- **LLP 1133.000 §3.6:** both rows, with WorkManager and the iOS
  identifiers as built.
- **LLP 1030.003:** its refresh check rides the host's refresh request.

## 13. What stays out

- A runner hosted in a service worker on the web, and with it periodic
  sync and background fetch there.
- Push and a data-only push's wake: the roster's `push`, which declares a
  wake event by D9.
- Wakes for an app that is not running on macOS, Linux and Windows: a
  login item or the platform's task scheduler (the roster's `login-item`).
- Android's long-running workers and foreground services, but for a
  person-started transfer on API 31–33 (D4): the roster's
  `foreground-service`.
- Resuming an interrupted upload on Android (`Range` and resumable upload
  protocols), until a consumer's files are large enough to need it.
- An app's own `beginBackgroundTask`; the host's for storage stays.
- Background location, geofencing, Bluetooth restoration and HealthKit
  delivery: their modules, over this seam.
- `icons` and `updateUI` on Background Fetch: no native target shows them.
- Continued processing's GPU resource, until a consumer asks.
