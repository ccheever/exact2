## Summary

Speech is two capabilities the web puts in one specification: the device
speaks text aloud, and the device turns spoken audio into text. exact2 gives
each its own package, because they share no object, no permission and no
dependency (D1):

- **`@exact/speech-synthesis`** speaks: the Web Speech API's
  `speechSynthesis.speak(new SpeechSynthesisUtterance(…))`, `cancel`,
  `pause`, `resume`, `getVoices`, with each utterance's progress (the
  `boundary` event's `charIndex`) as a live value. Below it,
  `AVSpeechSynthesizer` and Android's `TextToSpeech`. It asks for no
  permission. Its sound is a claim on the host's one audio session, beside
  sounds (LLP 1096), players (LLP 1098) and captures (LLP 1133.009 D7).
- **`@exact/speech-recognition`** listens: the Web Speech API's
  `SpeechRecognition`, started on an audio track that `@exact/media-capture`
  opened (`start(audioTrack)`, the specification's own overload), or on a
  recorded file. Below it, the Speech framework (`SpeechAnalyzer` with
  `SpeechTranscriber` or `DictationTranscriber` on iOS and macOS 26 and
  later, `SFSpeechRecognizer` before) and Android's `SpeechRecognizer`.
  Its results are a live value that keeps every final result, so none is
  lost to coalescing.

```
use getUserMedia, MediaStream from "@exact/media-capture"
use startSpeechRecognition, stopSpeechRecognition, speechRecognitionState,
  SpeechRecognitionInfo, SpeechRecognitionState, SpeechRecognitionTranscript
  from "@exact/speech-recognition"

state trackId = ""
state recognitionId = ""
mutation opened as shape MediaStream then listen
mutation started as shape SpeechRecognitionInfo then begun
mutation heard as shape SpeechRecognitionTranscript then filed
resource words = speechRecognitionState(recognition=recognitionId)
  as shape SpeechRecognitionState else empty()

action open
  send opened = getUserMedia(audio=true)
action listen
  match opened
    case some(s)
      trackId = s.tracks[0].id
      send started = startSpeechRecognition(track=trackId, continuous=true,
        interimResults=true, apple.addsPunctuation=true)
    case none
      trackId = ""
action begun
  match started
    case some(r)
      recognitionId = r.id
    case none
      recognitionId = ""
action done
  send heard = stopSpeechRecognition(recognition=recognitionId)
```

```ts
import { speak } from "@exact/speech-synthesis";

// Queue a document's paragraphs; each answers its utterance's id at once.
const ids = [];
for (const text of paragraphs) ids.push((await speak({ text, audioSessionType: "playback" })).id);
return { ids };
```

Tier 2 reaches the Speech framework's engines, presets, punctuation and
custom language models, `AVSpeechSynthesizer`'s voices, Personal Voice and
markers; Android's on-device recognizer, biasing strings, segmented
sessions, and the TTS engine and its audio attributes. Tier 3 hands the
app's Swift the synthesizer, each utterance, and each recognition's request
or analyzer before it starts; its Kotlin the `TextToSpeech` after it
initializes and each `RecognizerIntent` before `startListening`.

Three things are decided here that reach beyond this module (D4, D6, D7):

- **Recognition never opens a microphone of its own.** It is one more
  consumer of a `@exact/media-capture` track, holding that track's lease
  like a recorder or a meter, so a recorder and a live transcript share
  one capture, one permission decision and one indicator. Where a
  platform's recognizer can only open the microphone itself (Safari, Chrome
  on Android, and an Android recognition service that ignores an audio
  source), the track's capture is **handed over** to it for the length of
  the recognition, and no other consumer can join the track meanwhile.
- **Spoken audio is a claim on the host's audio session** with a type
  named after the W3C Audio Session draft: `transient` (a spoken prompt
  that ducks other audio), `transient-solo` (one that pauses it), or
  `playback` (reading aloud, which interrupts other audio and may continue
  in the background). The host composes it with the other claims; on
  Android, where the host has no owner today, the owner is built here and
  takes the form of audio focus.
- **Results are a value, not events.** A recognition's state keeps its
  final results numbered and in order, the latest interim result beside
  them, and the full transcript once it ends, so a reader that skips
  answers loses no words (LLP 1133 D6 rule 7).

The consumers are two small features that apps in the repo lack and their
platforms' own apps have: the recorder shows a take's transcript as it
records and keeps it with the take, and transcribes an older take on
request; the Markdown reader reads a document aloud and marks the word
being spoken (§10).

## 1. What exists

**Nothing speaks or listens.** No host, runner command or app synthesises
or recognises speech. `rules/DEFERRED.md`'s LLP 1096 entry keeps
"synthesis" out of sounds; that is sound synthesis (oscillators, effects),
not speech, and this module moves nothing of it (§14 question 7).

**The grant exists.** `device.speech-recognition` is a row of
`runner/src/device.rs` (LLP 1069.008), deriving
`NSSpeechRecognitionUsageDescription` on iOS and macOS, with no web or
Android column; its comment records the web's deviation ("its speech API is
gated by `microphone`"). LLP 1069.008 names an app outside the repo (grnl)
that would declare it "if it transcribes".

**What this builds on.** LLP 1133.009 decides the microphone:
`@exact/media-capture` is the only package that opens an input, one capture
per device for the process, a session's tracks as leases on it held while
the track has a consumer (D3, D6); handles are provisional until the runner
delivers the answer that carries them (D6); the host's audio-session owner
composes claims and is reachable from every package's context (D7, D10 item
5); a capture start is refused to a tool invocation and a wake in every
state (D9); a polled live source sits outside the timer wheel (D10 item 7);
the runner tells an implementation when a source's argument group loses its
last reader (`release(name, args)`, D10 item 12). LLP 1133.008 decides that
a lease is taken at the first consumer with the origin of the commit that
made it one (D3), and that under the agent the runner admits and the
implementation answers (D8 item 9). This RFC uses all of it unchanged and
adds what speech needs (D12).

## 2. Two packages

### D1 — Synthesis and recognition are separate packages

The Web Speech API is one document with two interfaces that share nothing:
`SpeechSynthesis` is a window attribute with a queue, `SpeechRecognition` a
constructor whose instances take a track. Their platform frameworks are
different (AVFAudio and Speech; `android.speech.tts` and `android.speech`),
synthesis asks for no permission while recognition asks for two, and only
recognition depends on `@exact/media-capture`.

One package would make an app that only speaks (the Markdown reader) depend
directly on `@exact/media-capture`, since LLP 1133.001 D4 lets no transitive
package carry native code, and link the Speech framework and the capture's
engine code for nothing. Two packages keep an app's dependencies, binary
and permissions to what it uses (LLP 1047.001). The roster's one row
(LLP 1133.000 §3.5) names the module; this RFC amends it to name both
packages (§11).

## 3. Synthesis

### D2 — Tier 1: `speechSynthesis`'s names

| Name | Kind | Web | Contract | Data code |
|---|---|---|---|---|
| `speak(text=, …)` | send; answers at once | `speechSynthesis.speak(new SpeechSynthesisUtterance(text))` with its attributes | `send u = speak(text=…)` | `await speak({text})` |
| `cancelSpeech()` | send, answers nothing | `speechSynthesis.cancel()` | `cancelSpeech()` | `await cancelSpeech()` |
| `pauseSpeech()`, `resumeSpeech()` | sends, answer nothing | `pause()`, `resume()` | statements | `await pauseSpeech()` |
| `speechSynthesisState()` | live source; a fact; `sync` where the host has `call` | `speaking`, `pending`, `paused`, and the current utterance's events | `resource s = speechSynthesisState()` | `await speechSynthesisState()` |
| `speechSynthesisVoices()` | live source; a fact; `sync` where the host has `call` | `getVoices()`, read again at `voiceschanged` | `resource v = speechSynthesisVoices()` | `await speechSynthesisVoices()` |

`speak`'s options are `SpeechSynthesisUtterance`'s attributes: `text`,
`lang` (BCP 47), `voice` (a `voiceURI` from `speechSynthesisVoices()`),
`volume` (0 to 1), `rate` (1 is the voice's normal rate), `pitch` (0 to 2),
and one shared word, `audioSessionType` (D4).

**Values:**

| Shape | Fields |
|---|---|
| `SpeechSynthesisVoice` | `voiceURI`, `name`, `lang`, `localService`, `default`; `apple`, `android` result words (D5) |
| `SpeechUtteranceInfo` | `id` |
| `SpeechSynthesisState` | `available`; `speaking`, `pending`, `paused` as the specification defines them; `utterance: option<string>`, the id being spoken; `charIndex`, `charLength`, `name` (`word`, `sentence`, a mark's name, or `""`) and `elapsedTime` of its last `boundary` or `mark`; `queue: string[]`, the ids not yet spoken; `ended: SpeechUtteranceOutcome[]`, the last 20 utterances to end, newest last |
| `SpeechUtteranceOutcome` | `id`, `outcome` (`end`, `error`), `error: option<SpeechSynthesisErrorCode>` |

**Errors** are the specification's `SpeechSynthesisErrorCode`s, in an
outcome's `error` (`canceled`, `interrupted`, `audio-busy`,
`audio-hardware`, `network`, `synthesis-unavailable`, `synthesis-failed`,
`language-unavailable`, `voice-unavailable`, `text-too-long`,
`invalid-argument`, `not-allowed`). A send that cannot queue at all fails
with the `DOMException` name LLP 1133.006 D8 item 2 answers
(`NotSupportedError` where the target has no implementation,
`NotAllowedError` for D10's origin and foreground rules).

**Declared deviations,** each because an event is not a value:

- **An utterance is an id.** `speak` answers `{id}` once the utterance is
  queued, and its id is a handle (LLP 1133.009 D10 item 10): a reply the
  runner drops (a superseded mutation, the session ending) cancels that
  utterance, so a `speak` the app never received never speaks.
- **Events are the state's fields.** `start`, `end`, `pause`, `resume` and
  `error` are `speaking`, `paused`, `utterance` and `ended`; `boundary` and
  `mark` are `charIndex`, `charLength`, `name` and `elapsedTime`, the last
  one reached. A reader highlighting the word being spoken needs only the
  last boundary, so coalescing loses nothing it shows. An utterance's end
  is sticky in `ended` (its outcome kept among the last 20), so an app that
  waits for one cannot miss it; one that must know every outcome of a long
  queue reads `ended` often enough, or counts its own ids out of `queue`.
- **SSML** (the specification lets `text` be an SSML document) is not
  tier 1: browsers speak it as text or not at all, and the platforms take
  it only through their own entries (Apple's `AVSpeechUtterance(ssmlRepresentation:)`,
  iOS 16). `apple.ssml=true` is tier 2 (D5); everything else speaks `text`
  as plain text (§12).

### D4 — Spoken audio is a claim on the host's audio session

LLP 1096 D8 made one owner of the process's audio session, and LLP
1133.009 D7 made a capture one more claim the owner composes. Speech is a
third kind of claim, held from the queue's first utterance starting until
the queue is empty (or `cancelSpeech`), with a type the author may write on
`speak` as the shared word `audioSessionType`. Its values are the W3C Audio
Session draft's types for spoken output, whose meanings it takes:
`transient` ("such as a notification ping. They usually should play on top
of playback audio"), `transient-solo` ("such as driving directions",
which "pause/mute all other audio and play exclusively"), and `playback`
("podcasts, etc.", which "should not mix with other playback audio")
([Audio Session §3.1](https://w3c.github.io/audio-session/)). The draft sets
one type for a page; a claim per queue is a declared deviation, since a
reader that speaks a document and a game that speaks a prompt are different
uses in one app. Two queued utterances with different types change the
claim's type when the second starts.

| Type | Apple (iOS, tvOS) | Android | Web |
|---|---|---|---|
| `transient` | `.playback`, mode [`.voicePrompt`](https://developer.apple.com/documentation/avfaudio/avaudiosession/mode-swift.struct/voiceprompt), options `.duckOthers` and `.interruptSpokenAudioAndMixWithOthers` | focus `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`; `USAGE_ASSISTANCE_NAVIGATION_GUIDANCE`, `CONTENT_TYPE_SPEECH` | `navigator.audioSession.type = "transient"` where it exists |
| `transient-solo` | `.playback`, `.voicePrompt`, `.interruptSpokenAudioAndMixWithOthers` without `.duckOthers`, so other spoken audio pauses | `AUDIOFOCUS_GAIN_TRANSIENT`, the same attributes | `"transient-solo"` |
| `playback` | `.playback`, mode [`.spokenAudio`](https://developer.apple.com/documentation/avfaudio/avaudiosession/mode-swift.struct/spokenaudio), no options: other audio is interrupted | `AUDIOFOCUS_GAIN`, `USAGE_MEDIA`, `CONTENT_TYPE_SPEECH`; on losing focus the queue pauses rather than ducks | `"playback"` |

The Mac has no session: the queue plays. Android's audio-focus guide says
to "call `requestAudioFocus()` immediately before starting to play", and
that spoken content should pause rather than be ducked; the system's
automatic ducking spares `CONTENT_TYPE_SPEECH`
([Manage audio focus](https://developer.android.com/media/optimize/audio-focus)).
An app targeting API 35 "cannot request audio focus unless it's the top app
or running a foreground service" (the same page), which is D10's
foreground rule for starting speech.

**Composition with the other claims.** While a capture claim holds
`.playAndRecord` (LLP 1133.009 D7), speech plays under it, in its mode and
options, and changes nothing: a capture is never reconfigured under itself.
Otherwise the owner's rule takes the strongest of the claims present,
`playback` over `transient-solo` over `transient` over the app's own
`audio_session` for sounds; a sound or video started during speech plays
under the speech claim, as it plays under `.playAndRecord` during a take.
When the last speech claim ends, the session returns to what the other
claims want, and `.notifyOthersOnDeactivation` is passed when the session
is given up, so a podcast the prompt ducked or interrupted resumes.

**Interruptions** (a call, Siri) are the owner's to observe (LLP 1133.009
D7): the speaking utterance pauses, `paused` reads true, and the queue
resumes only by `resumeSpeech`, as a `playback` player resumes only when
the app asks. A route change that removes headphones pauses a `playback`
queue, as Apple asks of a player when the old route was headphones
([Responding to audio route changes](https://developer.apple.com/documentation/avfaudio/responding-to-audio-route-changes)).

**The background.** A `playback` claim with `audio` in
`host.ios.backgroundModes` keeps speaking when the app leaves the
foreground, through LLP 1133.009 D7's widened `playsInBackground`, which
gains this claim beside `.playback` and a background capture. A
`transient` or `transient-solo` queue is canceled at the background, each
utterance ending `interrupted`, since a prompt the person can no longer
see the reason for is a tell. Now Playing for a `playback` queue (LLP
1098's media session) is out until a consumer asks (§12).

**Who plays it.** On Apple the synthesizer plays with
[`usesApplicationAudioSession`](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer/usesapplicationaudiosession)
true, under the owner's claim; set false, "the system creates a separate
audio session to automatically manage speech, interruptions, and mixing and
ducking", which would put a second owner beside LLP 1096 D8's. Whether the
synthesizer activates the application's session by itself when it speaks
is not documented. Stage 2 measures it: if it does, the owner has already
activated the session for the claim before `speak` reaches the synthesizer,
and the owner treats a reactivation it did not make as harmless; if it
deactivates the session after speaking, the implementation reports it and
the measurement amends this paragraph. *Rejected:* rendering speech into
buffers (`write(_:toBufferCallback:toMarkerCallback:)`, iOS 17) and
playing them through the sound arm's engine. It would put every sound on
one engine, but a hand-built app speaks with `speak(_:)`, the platform's
own route handling (AirPlay, the call uplink, the watch) comes with it,
and the buffer path's interaction with Personal Voice and assistive
settings is not documented; it stays tier 2 for an app that wants the
buffers (D5).

### D6 — Objects and lifetimes for synthesis

- **One queue per session.** Each session has its own synthesizer and
  queue, as each document has its own `speechSynthesis`. Two sessions
  speaking at once are heard together, under one process claim of the
  stronger type (D4).
- **An utterance belongs to its session** once delivered (D2's handle
  rule), and to nothing narrower: it outlives the answer and the mutation
  that queued it. `cancelSpeech` and the session's end cancel the queue;
  each canceled utterance ends `canceled`, the speaking one `interrupted`.
- **`destroy`** (LLP 1133.009 D10 item 1) stops the synthesizer
  (`stopSpeaking(at: .immediate)`, `TextToSpeech.stop()` and, on the
  process's last session, `shutdown()`) and releases the claim.
- **Threads.** Every entry is on the main thread. Apple's delegate is
  called on the queue the synthesizer chooses; the implementation hops to
  main. Android's `UtteranceProgressListener` is called on a binder thread;
  the implementation posts to the main looper.

**Errors** are the specification's `SpeechRecognitionErrorCode`s in the

**Declared deviations:**

- **A track is required.** The specification's `start()` with no track
  "requests microphone permission, then starts recognition from the device
  microphone". In exact2 one package opens the microphone
  (`@exact/media-capture`, LLP 1133.009 D3), so recognition always names a
  track, and an app opens one with `getUserMedia(audio=true)` first: one
  permission decision, one capture, one indicator, shared with a recorder
  or a meter on the same track. `start(audioTrack)` "does not request
  microphone permission", which is the same split.
- **A file is a source.** The web has no transcription of a file (a page
  plays it into a track in real time); every native platform has one
  (`SFSpeechURLRecognitionRequest`, `SpeechAnalyzer(inputAudioFile:…)`,
  Android's `EXTRA_AUDIO_SOURCE` fed from the decoded file). `path=` is a
  shared word for it, in the specification's style.
- **Objects are ids,** and a recognition's id is a handle (LLP 1133.009 D10
  item 10): a reply the runner drops aborts the recognition.
- **Events are the state's fields.** `audiostart` … `audioend` are `audio`,
  `sound` and `speech`; `result` is `results`, `finalCount` and `interim`;
  `nomatch` is a final result with no alternatives; `error` and `end` are
  `error` and `state` `ended`, which is sticky until the session ends.
  Final results are numbered: a reader that sees `finalCount` 12 and
  `results` ending at index 11 has missed nothing, and one whose last read
  ended at index 3 and now sees the window starting at 5 knows it fell
  behind and reads `transcript` at the end. The window bounds what each
  re-ask carries; the full list is answered once, at the end. No event
  protocol is needed (LLP 1133 D6 rule 7).
- **`speechRecognitionAvailability`** is the static `available()` as a live
  source, re-asked when an install changes it.

### D8 — Recognition is a consumer of a track; where it cannot be, a handover

A recognition started on a track is one of that track's **consumers**, as
LLP 1133.009 D6 counts a recorder that is not inactive and a meter's
readers: it holds the track's lease, so a track whose only consumer is a
recognition keeps the microphone open, and its stop releases the lease at
the end of that commit. Starting one is a capture start (D10).

How the audio reaches the recognizer differs by platform:

| Target | The track's buffers reach the recognizer | Shares the capture |
|---|---|---|
| iOS, macOS 26 and later | as `AnalyzerInput`s on the `AsyncStream` a `SpeechAnalyzer` reads, converted with `AnalyzerInputConverter` to `bestAvailableAudioFormat(compatibleWith:)` ([SpeechAnalyzer](https://developer.apple.com/documentation/speech/speechanalyzer)) | yes |
| iOS, macOS before 26 | appended to an [`SFSpeechAudioBufferRecognitionRequest`](https://developer.apple.com/documentation/speech/sfspeechaudiobufferrecognitionrequest) | yes |
| web, Chrome 135 and later on the desktop | `start(audioTrack)` with the page's `MediaStreamTrack` (MDN: Chrome 135; not Chrome on Android, Safari or Firefox) | yes |
| Android 13 (API 33) and later, a service that reads it | PCM written to a pipe passed as [`EXTRA_AUDIO_SOURCE`](https://developer.android.com/reference/android/speech/RecognizerIntent#EXTRA_AUDIO_SOURCE) with its channel count, encoding and sample rate | yes |
| Safari, Chrome on Android; Android before 33, or a service that does not read the pipe | none: the recognizer opens the microphone itself | no: a **handover** |

**The handover.** Where the platform's recognizer opens the microphone
itself, two captures of one device would contend (on Android the capture
policy silences one of them, [Sharing audio
input](https://developer.android.com/media/platform/sharing-audio-input)),
and the track's own capture would hear nothing useful. So on such a target
a recognition on a track is a consumer that **holds the device itself**:

- it may start only while it would be the track's sole consumer; a track
  with a recorder or a meter fails it `NotReadableError`, and a recorder or
  meter arriving while it runs fails or answers silence the same way;
- `@exact/media-capture` stops its own capture of that device for the
  recognition's length, keeping the lease (so the permission, the origin
  and the indicator's accounting stand), and the track reads `muted`,
  `muteReason` `in-use`, for any other session's consumers;
- the platform recognizer opens the microphone under the same platform
  permission the track's `getUserMedia` obtained (the browser's
  `microphone`, Android's `RECORD_AUDIO`), and its end hands the device
  back: the capture reopens if a lease still has a consumer.

`speechRecognitionStatus().sharesCapture` says which this target is, so an
app chooses: the recorder shows a live transcript where it is true, and
transcribes the take's file after it stops where it is false (§10).

**Android's detection.** [`EXTRA_AUDIO_SOURCE`](https://developer.android.com/reference/android/speech/RecognizerIntent#EXTRA_AUDIO_SOURCE)
says: "If this extra is not set or the recognizer does not support this
feature, the recognizer will open the mic for audio", and no call reports
support beforehand. A service that ignores the pipe does not read it, so
the writer's pipe fills: the implementation writes without blocking, and a
pipe not drained within its first 500 ms of audio means the service opened
the microphone itself. It aborts that recognition, records the service's
package and version as one that hands over, and starts again as a handover
(failing `NotReadableError` if the track has other consumers), so the app
sees `sharesCapture` turn false and its recognition restarted once. Stage 4
measures what the common services do (Google's, Samsung's) and records it.

**On the web,** whether a page may hold a `getUserMedia` track while
Safari's or Chrome on Android's recognizer runs is the browser's; stage 1
measures it, and the handover stops the page's capture regardless, so the
answer changes only how quickly the track reopens.

### D10 — Who may start, and the foreground

LLP 1133.009 D9's rule, unchanged: a **capture start** is refused to a tool
invocation and to a wake in every permission state, granted included
(`NotAllowedError`, `person-required`), and refused to any caller while the
app is not in the foreground. For this module the capture starts are
`startSpeechRecognition(track=…)` (it takes the track's lease) and, on a
handover target, nothing else. They are declared `"origin": "app",
"foreground": true`. A tool may stop, abort and read; a tool's
`stopSpeechRecognition` answers the transcript to the tool, since the words
are the app's data once heard.

**A file is not a capture.** `startSpeechRecognition(path=…)` opens no
device, so it is admitted under LLP 1133.002 D12's table: a tool may
transcribe a take the app already has while the speech-recognition state
is `granted`, and fails `person-required` when it would prompt. It still
requires the foreground (`"foreground": true`): Android's recognizer runs
in another app's service bound from the activity, and a transcription that
outlives the foreground is background work (§12).

**Synthesis.** Speaking opens no device and shows no system UI, so any
origin may speak while the app is in the foreground, a tool's included,
under the claim's type. `speak` and `resumeSpeech` are declared
`"foreground": true`: a wake cannot start speech (iOS gives a background
app no new audio session without the background mode, and Android's API 35
refuses focus to an app that is not the top app), while a `playback` queue
already speaking continues in the background (D4).
`requestPersonalVoiceAuthorization` shows a system prompt and is a
request, admitted as LLP 1133.002 D12 says.

**Not delegable now.** As LLP 1133.009 D9 says of a capture, recognition
on a live track records the room; until LLP 1133.002 D12's delegation
exists and says otherwise, no agent may start one without the person. A
voice is not a presence check (LLP 1133.010 D12), and nothing here treats
recognised speech as proof of who spoke.

**Declare.** Recognition needs two lines on the platforms that ask for

| Platform state | `state` |
|---|---|
| Apple `SFSpeechRecognizer.authorizationStatus()` `notDetermined` | `prompt` |
| Apple `authorized` | `granted` |
| Apple `denied`, `restricted` | `denied` (`restricted` is tier 2, `apple.authorizationStatus`) |

**Whether `SpeechAnalyzer` needs the authorization** is not documented.
Apple's permission article says the server-bound process "only applies to
speech recognition using `SFSpeechRecognizer`. `SpeechAnalyzer` transcriber
modules don't send audio data of the user's voice to Apple's servers", and
does not say whether they need `requestAuthorization`. Until stage 2
measures it on iOS 26 and macOS 26, the Apple implementation asks for
authorization before any engine, so a recognition never fails for want of
it; if the measurement finds `SpeechAnalyzer` needs none, the state on 26
reads `granted` with no prompt for the transcribers, and `SFSpeechRecognizer`
alone asks. Either way the purpose string is in the bundle.

**Ask.** `startSpeechRecognition` while `prompt` asks through
`SFSpeechRecognizer.requestAuthorization`, in LLP 1133.002 D9's queue,
after the microphone's decision (which `getUserMedia` took earlier) or, for
a file, alone. Explain and recover as LLP 1133.002 D11 says, with
`openURL("app-settings:")`.

**Personal Voice** (synthesis, tier 2) is a permission of its own, read in
`apple.personalVoiceAuthorizationStatus` and asked by
`apple.requestPersonalVoiceAuthorization`; a Personal Voice is listed in
`speechSynthesisVoices()` only once authorized.

| Android | each `RecognizerIntent` | after the extras are set, before `startListening` | `EXTRA_AUDIO_SOURCE` and its format, `EXTRA_PARTIAL_RESULTS`, the listener | add extras the words lack |
| Web | none | — | — | — |

`requiresOnDeviceRecognition` and the engine are the module's on every
call: a hatch that turns server recognition back on under
`processLocally=true` is set back after it returns, as LLP 1133.010 D11
sets back a gate, since an author who wrote `processLocally=true` was
promised the audio stays on the device.

| Use of the frameworks | Tier |
|---|---|

| mark the word being spoken | 1 (`charIndex`, `charLength`) |

### D17 — Cost

An app that does not import a package links none of it: no Speech
framework, no `NSSpeechRecognitionUsageDescription`, no `<queries>`, no
page code (LLP 1047.001). The synthesis package links AVFAudio, which the
sound arm links already, and no Speech. Nothing is made before the first
name is asked, so nothing runs before first pixel. Stage 2 records each
Apple implementation's size; stage 4 what the two Android implementations
add to an APK.

**Commit rate.** Interim results arrive several times a second, and each
announcement re-asks the state's readers. The implementation coalesces
announcements to one per 100 ms of the session clock, which is below the
50 ms budget LLP 1133.009 D13 measures for a level, so its measurement
covers this. A boundary is announced once per word.

## 9. The substitute

**Each implementation is its own substitute** (LLP 1133.008 D8 item 9):
under the agent the runner admits each call and holds the permission
ticket, and the implementation runs, told so, speaks nothing, opens no
recognizer and calls no hatch. The declared `permission`
(`speech-recognition`) is the runner's, so `prefer
permission.speech-recognition`, `--permission speech-recognition=…` and
tickets work as geolocation's do. Its default is the target's (D11):
`prompt` on Apple, `granted` on Android and a sharing browser; the
target's restrictions hold under the agent (LLP 1133.002 D15).

**Synthesis, on the session clock.** An utterance is spoken at 170 words a
minute times `rate`: each whitespace-separated word takes
`60000 / (170 × rate)` ms, a `word` boundary is reached at each word's
start, and `end` after the last. So `clock +N` moves the highlight by a
known number of words on every host. Voices are two: "Agent voice"
(`en-US`, the default) and one for the app's base locale. `prefer extension
speech-synthesis.fail="synthesis-failed"` makes the next utterance end
with that error.

**Recognition, from a phrase.** The agent's track (LLP 1133.009 §10) is a
tone, which no recognizer could hear. So a recognition hears what a drive
says it hears: `prefer extension speech-recognition.heard="pick up milk"`
delivers, from the moment it is set, one word as an interim result every
300 ms of the session clock and a final result 500 ms after the last word,
with confidence 0.9 and times on the session clock. A non-continuous
recognition then ends; a continuous one waits for the next phrase. With no
phrase, a non-continuous recognition ends `no-speech` after 8 s. A
`path=` recognition answers the phrase preferred at its start as one final
result, at once. `prefer extension speech-recognition.speechRecognitionStatus={"sharesCapture":false}`
makes the target a handover one (D8), so a drive tests both branches on
one host.

**Disclosure:** `state.extensions` lists each session's queue, the claim
and its type, each recognition with its track or path, whether it shares
or holds the device, its results count and each answer's origin.

**Production:** none of it.

## 10. The consumers

Nothing in `apps/` or `examples/` speaks or listens today. Two small
features would, each a thing its platform's own app does and each testing
a different half of the design:

### The recorder: a transcript with each take

The recorder (LLP 1133.009 §11, after recording's stage 0 moves it to the
packages) gains:

- `"@exact/speech-recognition"` in its `package.json`, and the grant
  `device.speech-recognition purpose.transcribe` beside its
  `device.microphone`;
- **a live transcript while recording,** where
  `speechRecognitionStatus().sharesCapture`: `arm` starts a continuous
  recognition with interim results on the take's track, beside the
  recorder; the waveform has a line of the last final results and the
  interim one under it; `filed` stops it and passes the transcript to
  `app.ts`, which writes it beside the take (`take-3.json`, through
  `storage.fs`), so the take's row shows its first line;
- **a transcript after recording,** where `sharesCapture` is false (a
  handover target) or the take predates the feature: a "Transcribe" button
  on the take's row starts a `path=` recognition on its file;
- while the state is `denied`, takes record without transcripts and a line
  says so, with Open Settings on native targets.

It tests the deepest part of the design: a recorder and a recognition on
one track, one lease, one indicator; the handover branch; a file as a
source; two permission decisions in order.

**Drives,** on the web, macOS and the iOS simulator under the agent, and
Android when its stages land:

1. `--permission microphone=prompt --permission speech-recognition=prompt`;
   `tap toggle`; `tap @p allow` (the microphone); `tap @q allow` (speech
   recognition); `prefer extension speech-recognition.heard="pick up milk
   and eggs"`; `clock +3000`: the line shows "pick up milk and eggs" and
   the waveform's bars; `tap toggle`; `clock settle`: the take's row shows
   its transcript, and `state.extensions` shows one capture with no lease
   left.
2. The same with `--permission speech-recognition=denied`: no second
   ticket, the take records, no transcript, the denied line.
3. `prefer extension
   speech-recognition.speechRecognitionStatus={"sharesCapture":false}`; a
   take records with no live line; "Transcribe" on its row: its transcript
   is the preferred phrase.
4. A tool invocation of record: `person-required` (LLP 1133.009 D9); a
   tool invocation of "Transcribe" on a take while granted: the
   transcript; while `prompt`: `person-required`, no ticket.
5. `tap toggle`, then `tap toggle` again before `clock settle` while
   `startSpeechRecognition`'s answer is undelivered: the recognition is
   aborted (D7's handle rule), and `state.extensions` journals it.
6. By a person, on an iPhone (iOS 26), a Mac and an Android phone with the
   real implementations: a thirty-second take's live transcript reads as
   spoken; one take over a minute long on an iOS 17 simulator or device
   with `processLocally` unset shows the journaled seam (D9); on Android
   the status reports which branch the phone's service takes.

### The Markdown reader: Listen

`apps/markdown` gains a **Listen** button in its header: it reads the open
document aloud from the section shown, one utterance per paragraph,
marking the word being spoken, with Pause, Resume and Stop. Readers do
this (Safari's Reader, Books' Speak Screen), and it tests synthesis
whole: a queue from data code, boundaries as a value, a `playback` claim
that continues with the screen locked on iOS (the app gains `audio` in
`host.ios.backgroundModes`).

- `"@exact/speech-synthesis"` in a `package.json` of its own; no grant.
- `app.ts`'s `listen(section)` mutation queues the section's paragraphs
  with `speak({text, lang: doc.lang, audioSessionType: "playback"})` and
  answers their ids; Contract keeps them and, from
  `speechSynthesisState()`'s `utterance` and `charIndex`, marks the word in
  the paragraph whose id is speaking (a run with a background, as search
  hits are marked).
- Opening another document or tapping Stop calls `cancelSpeech()`.

**Drives:** `tap listen`; `clock +1000`; `screenshot`: the fourth word of
the first paragraph marked, on every host; `tap pause`; `clock +2000`: the
mark has not moved; `tap resume`; `clock +60000`: the last paragraph's
`ended` outcome is `end`; `tap listen` twice before `clock settle`: the
first queue's undelivered ids are canceled and only one queue speaks; by a
person on an iPhone: reading continues with the screen locked, a phone
call pauses it, and a podcast playing before Listen is interrupted and
resumes after Stop.

The conformance suites (LLP 1133.001 D7) run the web implementations in
Google Chrome, Firefox and WebKit (Playwright's Chromium is expected to
have no speech service, which stage 1 confirms), the Apple ones on macOS
and the iOS simulator granted by `xcrun simctl privacy grant`, each
recognising a known spoken file and a known track and speaking a known
text with its boundaries.

## 11. What this amends

- **LLP 1133.009 D3, D6:** a track's consumer may hold the device itself
  (D8, D12 item 4); a recognition is a consumer.
- **LLP 1133.009 D7 and LLP 1096 D8:** the owner composes speech claims of
  three types (D4); `playsInBackground` includes a `playback` speech
  claim; the Android host gains an owner, as audio focus (D12 item 2).
- **LLP 1133.009 D10 item 8:** an origin condition on an argument's
  presence (D12 item 5).
- **LLP 1069.008:** `device.speech-recognition` gains an Android column
  (`<queries>` for `RecognitionService`); a grant column may name queries
  (D12 item 3).
- **LLP 1133.000 §3.5:** the row names two packages,
  `SpeechAnalyzer`/`SpeechTranscriber` and `SFSpeechRecognizer`,
  `TextToSpeech` and `SpeechRecognizer`; its "tier 2 must reach" becomes
  "engines and presets, custom language models, Personal Voice, Android's
  services and segmented sessions", since on-device recognition, phrases
  and file transcription are tier 1 here.

## 12. What stays out

Each until a consumer asks:

- synthesis to a file or buffers as a tier 1 name, SSML as tier 1, and Now
  Playing for a `playback` queue;
- recognising while the app speaks without hearing itself (D15), and
  turn-taking for a voice assistant;
- recognition in the background, a file transcribed while the app is
  closed (background work, LLP 1133.000 §3.6), and keyword spotting while
  idle;
- speaker identification and diarization, and translation (the roster's
  `translation`);
- `boost` on Apple (no platform word), and grammars (the specification's
  `grammars` does nothing);
- the tvOS, visionOS, watchOS, Windows and Linux cells.

## 14. Questions for the ruling

1. **Two packages (D1),** `@exact/speech-synthesis` and
   `@exact/speech-recognition`, as the roster's one module "speech"?
   *Proposed: yes (80%). The alternative, one package, makes an app that
   only speaks depend on `@exact/media-capture` and link the Speech
   framework.*
2. **Recognition always on a track, with a handover where the platform's
   recognizer must own the microphone (D7, D8).** *Proposed: yes (75%).
   The alternative, the specification's bare `start()` opening a
   microphone of its own, puts a second capture beside LLP 1133.009 D3's
   one owner on every target, which contends with a recorder on Android
   and doubles permission and indicator accounting.*
3. **Spoken audio's claim types (D4),** the W3C Audio Session draft's
   `transient`, `transient-solo` and `playback`, unsaid from the app's
   `audio_session`, with an Android owner built here as audio focus.
   *Proposed: yes (75%).*
4. **Who may start (D10):** recognition on a track is a capture start,
   refused to tools and wakes in every state; recognition of a file and
   speaking are open to a tool in the foreground under the app's grant.
   *Proposed: yes (80%).*
5. **The unsaid engine may use a server (D9),** as the platform's default
   does, or exact2 defaults `processLocally` to true wherever the device
   can recognise the language locally. *Proposed: the platform's (60%),
   since on iOS 26 and later it is already on the device, and on Android
   and the web a local default would fail languages the server has; the
   recipe asks for `processLocally=true` for anything private. Charlie's
   call.*
6. **D12's five seam additions** as apparatus admitted with this ruling.
   *Proposed: yes.*
7. **`DEFERRED.md`:** an "Expanded" record admitting speech synthesis and
   recognition by these names, with §12 as its "Still out", and a note
   that the LLP 1096 entry's "synthesis" (sound synthesis) stays out. Take:
   none offered; a waiver, or Charlie names one.
