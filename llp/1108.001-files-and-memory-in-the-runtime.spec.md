## 1. Slice 2: `exactSaveTo` — a response body written to an app file by the host

`exactBodyFrom` (the request side) landed on 2026-10-08 (LLP 1108 D6, "Built
early"). This is the response side.

### 1.1 Surface

```ts
const r = await fetch(url, {
  headers: { range: "bytes=0-" },
  exactSaveTo: { path: "app:/cache/snapback4/p/s-7", when: { "accept-ranges": "bytes" } },
});
if (r.exactSaved) { /* { path, bytes }: the file is in place */ }
else { const why = await r.json(); /* a refusal, or a 2xx `when` did not admit */ }
```

- `exactSaveTo: "app:/…"` is shorthand for `{ path: "app:/…" }`.
- `when` (optional) maps header names to values. Every one must be present
  on the response. Its whole value must equal the given one, compared
  without ASCII case and surrounding whitespace. The whole value is what
  Fetch's `headers.get` returns, every occurrence joined with `, `. No
  list member is matched alone, so `accept-ranges: none, bytes` does not
  match `bytes`. A missing header fails. Natively the host joins repeated
  headers the same way before it compares.
- Rust sources: `Request::save_to(path)` and `Request::save_when(name, value)`.
  `Response::saved()` returns `Option<u64>`.

### 1.2 Admission: everything that can be known before the request is sent

Each of these is refused before the request is sent, as `exactBodyFrom`'s
refusals are: a `TypeError` in the prelude, or a `FetchError` of kind
`Refused` from the host, naming why.

- The path: `app:/`, at most 4096 bytes of UTF-8, no `.` or `..` segment, no NUL.
- Not with `exactStream`, a WebSocket, or a `HEAD` request.
- `when`: an object of string values, at most 16 entries.
- **The grant:** `fs.write` must cover the path. The request's own scope
  narrows the app's grants, as for every storage operation.
- **The parent directory must exist,** as for `writeFile`. A missing one is
  refused naming the path (`ENOENT`).
- A host with no app files (a drive with no scratch store) refuses with kind
  `Unsupported`, as `exactBodyFrom` does.
- A Rust module across the logic seam (LLP 1029.000) refuses it, as it refuses
  `exactBodyFrom` and a timeout.

Every executor does these checks before sending:

- natively, by creating the staging file;
- on the web, by authorizing the path and reading the parent's record.

The wasm realm's early fetch (`module-glue.js` `fetchEarly`) never takes a
request that names `exactSaveTo`.

### 1.3 The writing rule

The host decides once the status and headers have arrived, before it reads
any of the body. The body is **written** only when both hold:

- the status is `2xx` (`response.ok`);
- every `when` header matches.

Otherwise the body is the response's, read into memory as for any other
fetch, under the same limit. Nothing is created, replaced or removed at the
path. So a `416 E_ASSET_RANGE`, a `404` or a `200 {denied}` is read with
`json()` as usual. With `when: {"accept-ranges": "bytes"}`, a `200` that says
`accept-ranges: none` (a `once` asset delivered) is in memory, never on disk.
In slice 3 that reply can be shown at once with `response.blob()`, so its view
is not wasted.

### 1.4 Writing

- **Natively,** the body streams into a staging file beside the target,
  chunk by chunk, so it is never held whole in memory.
  - The staging file is Ibex patch 11's: `.exact-<16 hex>.partial`, from the
    OS's randomness, created with `O_CREAT | O_EXCL | O_NOFOLLOW` through the
    parent's directory handle.
  - When the body ends, the host checks that the request was not let go
    (aborted), syncs the file and renames it over the target (`renameat`
    within the pinned parent). The file appears only whole, replacing any
    file there.
- **On the web,** the body is read through a counting stream into a `Blob`.
  The browser holds the bytes, not the module's heap, and the stream stops at
  the bound.
  - The `Blob` becomes the file's entry in the page's store (`saveBody` in
    `storage-fs.js`). The write runs under the same mutation discipline every
    `storage.fs` write uses: the module's mutation queue, then Web Locks on
    the path and its ancestors (`mutate`). It is one IndexedDB transaction,
    so it is atomic. A path that a live SQLite handle holds, or whose parent
    another tab is moving, is refused as a `writeFile` there would be.
  - On the JS target, a save never passes through `within`, which reads a
    clone of every body. Its counting stream is the only reader.
- **Truncation is the transport's to detect.** A body cut off before its
  framing says it ended (`content-length`, chunked encoding) is a `Network`
  failure on every transport.
  - **Natively,** the host also compares the bytes written with
    `content-length`, but only when the response declares no content coding
    (no `content-encoding`, or `identity`). The native transports hand over
    the headers as received (URLSession's `allHeaderFields`), so a decoded
    body always arrives with its coding named, and the comparison is
    skipped.
  - **On the web,** no length is compared. A cross-origin response exposes
    `content-length` but hides `content-encoding` unless the server exposes
    it, so the page cannot tell an encoded length from a decoded one. The
    browser's own framing check is the truncation check.
  - The tests include a cross-origin gzip response whose coding is not in
    `Access-Control-Expose-Headers`.
- **Failure.** A deadline (`exactTimeout`), letting the answer go, the bound,
  a short body, a disk error or a vanished directory all fail the fetch with
  the usual kinds (`Timeout`, `Aborted`, `Refused`, `Network`). The staging
  file is removed and the target is untouched.
- **The bound** is `exactIndependentHttp.maxResponseBytes`, or 64 MiB. It is
  the same as for a response read into memory, so a large download costs
  disk, not memory.

### 1.5 The response

- `response.exactSaved` is `{ path, bytes }` when the body was written, else
  `null`. The browser's `Response` gets the same property on the JS target.
  Its `Headers` never see the count.
- On a written response, `text()`, `json()` and `arrayBuffer()` (and `blob()`
  from slice 3) reject with a `TypeError`: "the body was saved to <path>".
  `status`, `ok` and `headers` are as received.
- **The carriers.**
  - The runner's `Response` type does not change. The byte count travels in
    its header list as the pair `(":exact-saved", "<bytes>")`. No HTTP
    response can carry that name, because a header name has no colon.
    `Response::saved()` reads it for a Rust source.
  - The prelude removes the pair before it builds `Headers`.
  - The wasm host's page-to-runner reply is header *text*, one `name: value`
    per line (`host/web/src/host.rs` `outcome_from`). The page puts the count
    first, as the line `:exact-saved: <bytes>`. `outcome_from` reads a line
    that starts with a colon as a pseudo-header: it splits the rest at its
    first colon and keeps the leading colon on the name. A browser header
    name has no colon, so no server's line starts with one. `fulfill` and
    `fulfill_at` take nothing new.

### 1.6 Lifetime, abort, and the client's part

- **One publication decision.** The rename (on the web, the IndexedDB
  transaction) happens before the fetch resolves. Before it, the writer
  takes the request's publication lock and checks, under it, that the
  request has not been let go, aborted or timed out.
  - Natively the file is synced first and the decision comes after, so
    only the `renameat` call follows it. On the web the decision is the
    moment the transaction is submitted.
  - A let-go, abort or deadline that takes the lock before the decision
    publishes nothing, and the staging file is removed.
  - One that arrives after it finds the file in place. The fetch then
    settles as it would have, with the file.
  - Once published, the file stays, and a later fetch to the same path
    replaces it.
- **Letting go covers every save, whatever its method.** Today the native
  executor and the wasm host abort a request the runner let go only when it
  is safe to (`GET`, `HEAD`: `executor_core.rs` `safe()`, `glue.js`
  `forgettable`). A sent `POST` runs on, as a sent write must. A save is
  different: its *publication* is cancelled whenever its ticket is let go,
  whatever its method. The executor keeps a per-ticket "publish" flag that
  letting go clears. The network exchange of a non-safe request still
  completes, and its body goes nowhere.
- **The deadline covers the whole save.** On every executor, `exactTimeout`
  counts the admission checks before sending, the body, the waits for the
  mutation queue and Web Locks on the web, and the decision.
  - A deadline that passes before the decision fails the fetch `Timeout`
    and publishes nothing.
  - Filesystem work that stalls past it, such as a sync that does not
    return, loses the decision. The staging file is removed when that work
    ends.
- **`signal` is the fetch's, not the host's.** As for every Hermes fetch
  today, an aborted `signal` rejects the promise at once and the host's
  request runs on (`prelude.js`: "its reply is dropped"). So a save can land
  after its caller saw `AbortError`. It lands whole, at the path the caller
  named.
  - The web's own `fetch` cancels the download on abort. Hermes has no
    per-ticket cancellation from a data module. Adding it is a runner change
    beyond this spec (§6).
  - An app that cannot tolerate a late file names a unique path and publishes
    it itself, as the Snapback client does (below).
- **A crash** can leave a `.exact-*.partial` file. It never takes the
  target's name. A sweep that removes it is the app's, and the Snapback
  client's open sweep removes any file its manifest does not name.
- **The Snapback client** (LLP 1108 D2, slice 1's driver once it switches):
  - It saves into a unique staging path in the partition's cache directory,
    with `when: {"accept-ranges": "bytes"}`.
  - Written (`exactSaved`): it hands the core's `asset_reply` the
    `{status, headers, size}` arm, with `size` = `exactSaved.bytes`.
  - Not written, and the reply is JSON (a refusal: `416 E_ASSET_RANGE`, a
    `4xx`, `5xx`, or a `200 {denied}`): it hands the `{status, body}` arm,
    the body read with `json()`.
  - Not written, and the reply is not JSON (a `200` with `accept-ranges:
    none`, the once-view delivered): it hands `{status, headers}` with the
    four media headers and no body. The bytes never enter the core (parent
    D2). The core reads `accept-ranges: none` as the spent view
    (`E_ASSET_ONCE_UNSUPPORTED` until slice 3; in slice 3 the driver shows
    that body with `response.blob()`).
  - The driver never falls back to `arrayBuffer()` and `atomicWriteFile`.
  - In the media queue, it renames the staging file to the path the core
    names, or removes it if the core refuses or the exchange is stale.

  That is the reviewers' "unique staging files the media queue publishes
  after core approval". The runtime's part is only to write the file whole or
  not at all, and only when the headers allow it.

### 1.7 Compatibility

A bundle using `exactSaveTo` on a shell whose prelude predates it would read
the body into memory and write no file. `bake/src/compat.rs`'s
`TYPESCRIPT_RUNTIME` goes from 1 to 2 (the draft branch's comment assigns 2
to `exactSaveTo`). The classifier then refuses an older
cohort, as it does for `exactBodyFrom`.

## 2. Slice 3: `Blob`, `Response.blob()`, object URLs, and `blob:` sources

### 2.1 Surface

On every executor, a data module has the web's API:

- `new Blob(parts?, { type? })`: parts are strings (UTF-8), `ArrayBuffer`s,
  views and `Blob`s.
- `blob.size`, `blob.type`, `blob.arrayBuffer()`, `blob.bytes()`,
  `blob.text()` and `blob.slice(start?, end?, type?)`.
- `response.blob()`.
- A `Blob` as a `fetch` body. Its `type` is the `Content-Type` when no header
  names one, as Fetch does.
- `URL.createObjectURL(blob)` and `URL.revokeObjectURL(url)`.

What is left out: `blob.stream()` (a data module has no streams), `File` and
`FormData`. A `blob:` URL is a source for `image` and `video` on every host
(§2.6). It is not something `fetch` reads: a data module already holds the
`Blob`, and the web's `fetch(blobURL)` is outside the grants model.

### 2.2 On the web

The browser's own `Blob`, `URL.createObjectURL` and `Response` serve both web
executors.

- **The JS target** is the web's executor for apps (LLP 1071 §7). The
  module's `Response` is the browser's, and its `blob()` is the browser's.
  LLP 1108 D8's "`Response.blob()` never surfaces its bytes in JavaScript"
  is claimed there and on Hermes, the two executors D8 names.
- **The wasm host's module realm** (games and fixtures only on the web,
  LLP 1071 §7) receives every reply through its JSON carrier, as text and
  base64 (`js/web/src/lib.rs`). Its prelude's `Response.blob()` makes a
  browser `Blob` from those bytes. The bytes have crossed into that realm, as
  they do today for `text()`. This is declared, not fixed. Giving that
  carrier a side channel for bytes is work for a target the web no longer
  ships apps on.
  - **A `Blob` body** is read into bytes inside the realm
    (`blob.arrayBuffer()`, which the realm holds anyway). The prelude then
    sends it as a `BufferSource` body on the existing `body_base64` carrier.
    The prelude restores the calling answer (`currentCall`) around that
    send, as a continuation's fetch is claimed today. No object URL and no
    new `Request` field crosses the realm, the runner or the page. A body
    over the request's bound is refused before it is read.
- **Lifetime is the creating environment's.** An object URL lives until it is
  revoked or the environment that made it ends:
  - on the JS target, the page;
  - in the wasm realm, its iframe or worker. Disposing the realm ends its
    URLs while the page lives on.
- **The URL's form is the browser's** on the web, `blob:<page origin>/<uuid>`,
  and both web hosts pass it to `<img>` and `<video>` unchanged. The
  app-id form of §2.4 is Hermes's only.
- The browser's own memory limits apply, not §2.5's. That is the declared
  deviation.

### 2.3 On Hermes: bytes held by the host

- **The store.** A process-wide map in Rust (`exact_runner::blobs`) holds
  reference-counted byte buffers (`Arc<[u8]>`), behind one mutex.
  - A buffer is immutable once made. `new Blob` copies its parts out of the
    JavaScript buffers into a new one.
  - Each buffer is charged to its app id when it is made. The charge is
    released when its last reference drops (§2.5), from whichever thread
    drops it: the Hermes thread, a finalizer, a decoder, the video loader's
    queue.
  - `acquire` clones the `Arc` under the mutex. Nothing else needs the lock
    to read a buffer.
- **A `Blob`** is a JavaScript object carrying a JSI `NativeState`. The state
  holds one reference to a buffer, plus a range for `slice`.
  - The state reports the buffer's size to Hermes as external memory, so
    the collector runs when held bytes grow, not only when the heap does.
    The call is JSI's `Object::setExternalMemoryPressure` (declared in the
    linked lean Hermes's `jsi/jsi.h`). Where a Hermes lacks it, the
    collection before a refusal (§2.5) is the only pressure.
  - The reference drops when the collector finalizes the object.
  - Nothing is spooled to disk.
- **The door.** The shim (`js/src/shim.cc`) installs one more host function,
  `__exact_blob(op, …)`. It:
  - makes a `Blob` from a list of `ArrayBuffer`s and `Blob`s;
  - copies bytes out (`arrayBuffer`, and `text` as lossy UTF-8);
  - slices, makes and revokes URLs;
  - takes a response body;
  - names a body for a request.

  The prelude keeps it in a closure and deletes the global, as it does
  `__exact_host`. `Blob` is installed from a new Hermes-only file,
  `js/src/blob.js`, so the prelude stays under its line cap.
- **Response bodies are held too,** on the `__exact_fulfill` path. A reply's
  body no longer travels as base64 and text in the outcome JSON.
  - The engine charges it (§2.5) and sets it aside under a number; the
    outcome JSON names that number and the size. `__exact_fulfill` takes it
    into the new `Response`'s `NativeState`. A body nobody took (a ticket
    already let go) is dropped as soon as the call returns.
  - `text()`, `json()` and `arrayBuffer()` copy out when asked. `blob()`
    shares the held buffer without a copy, so a photo shown through an object
    URL never enters the JavaScript heap.
  - As today, a body can be read more than once. The web marks it used, and
    making it single-read is not this spec's change.
  - **The stream path** (`__exact_message`) still carries a non-event reply's
    text inline. That is a stream's refusal body, at most the stream's
    ceiling (1 MiB by default), read by the prelude as `data`.
- **A `Blob` body** rides the same side channel the other way. The prelude
  passes the `Blob` to `__exact_blob("body", ticket, blob)` before it calls
  `__exact_host(1, …)`. The request JSON then says `body_blob: true`.
  `wire.rs` takes the bytes from the engine's side table when it builds the
  `Request`, synchronously, inside that same door call. The bytes are copied
  once into the request, in Rust, never through base64.

### 2.4 Object URLs

- **The form** is `blob:<app id>/<uuid>`, after the web's form of an origin
  then a UUID. An app with no id (a fixture) uses `blob:exact/<uuid>`.
  - An app id is not a URL origin, so `new URL(url).origin` is `"null"`, an
    opaque origin, where the web's gives the page's. That is a declared
    deviation.
  - Hosts read the app id from the URL's path: everything between `blob:`
    and the last `/`.
- **The UUID.**
  - Normally it comes from the OS's randomness, as `crypto.randomUUID` does
    natively.
  - Under an agent drive, it is drawn from the engine's own repeatable
    stream (LLP 1069.005 D2b), as `crypto.randomUUID` is. That stream is
    per executor and starts over when the executor is made, so one drive
    replays its URLs.
  - Two engines with one seed would draw the same first UUID (Astra r1).
    So a draw that names a URL already in the process store is drawn
    again. The second engine's URLs then differ from the first's, the same
    way in every replay of the same drive.
  - A drive may assert that a source is a `blob:` URL of its app, not which
    UUID it has. Each draw shifts the app's later draws from that stream,
    as any `randomUUID` does.
- **Ownership and lifetime.** Each URL belongs to the engine that made it. It
  lives until `revokeObjectURL` or until that engine ends: an app reload, a
  session closed, the process ending. An engine's teardown revokes only its
  own URLs.
  - A URL keeps its buffer alive. A revoke drops the URL's reference.
  - **Sessions.** Two sessions of one app id in one process (the sample host)
    share the store and the bound, and each can resolve the other's URLs. On
    the web, two documents of one origin can do the same.
- **Not at bake.** A URL is a device fact. At bake, `createObjectURL` refuses
  with "object URLs are unavailable during bake", so an answer that asks is
  not compiled and is asked on the device, as for storage.
- **Not durable.** A kept answer (LLP 1018) holding a `blob:` URL shows
  nothing after a relaunch. On the web it shows nothing after a reload, for
  the same reason. The guide says so: keep a path, not a URL.

### 2.5 The bound: everything the host holds, per app

- **What counts.** Every buffer the store holds for an app counts toward one
  bound of **256 MiB**: a `Blob`'s bytes, an object URL's, a held response
  body, and a host's acquisition for a decode or a player (§2.6).
  - A buffer counts once, however many `Blob`s, slices, URLs or acquisitions
    share it.
  - It stops counting only when its last reference drops.
- **Over the bound,** the engine first runs one full garbage collection, so
  unreachable `Blob`s and responses release their buffers. Then it tries
  again. If it is still over:
  - `new Blob(...)` and `response.blob()` throw a `DOMException`-shaped error
    named `QuotaExceededError`: "object memory is over 256 MiB for this app;
    revoke object URLs you no longer show". (`blob()` shares, so it can only
    fail when its body was not yet charged; it was, at delivery, so in
    practice it does not.)
  - A reply whose body would pass the bound rejects its fetch with
    `FetchError` kind `Refused`, with the same words.

  A leak of URLs or retained responses fails loudly rather than growing.
- There is no knob until an app needs one (§6 of LLP 1108).

### 2.6 `blob:` in `image` and `video`

- **No layer upstream rejects a scheme.** The kernel, the runner and Contract
  check only `symbol:`. Each host branches on `blob:` before the rejections
  it has today:
  - `RasterInput.open`'s `http`/`https`-only guard;
  - `NodeView.resolveSource`;
  - Linux `image_input`'s `relative()`.
- **Acquisitions pin.** A host resolves a `blob:` source with
  `exact_blob_acquire(url, app id) → (pointer, length, type, handle)`. That
  takes its own reference to the buffer.
  - Neither `revokeObjectURL` nor the finalizer can free a buffer an
    acquisition holds. Only `exact_blob_release(handle)` drops it.
  - An unknown or revoked URL acquires nothing.
- **Each host resolves a `blob:` source from the store,** as it resolves an
  `app:/` source from the file roots:
  - **Web, both targets:** the browser's object URL, unchanged. The glue
    already passes `blob:` through (`glue.js` `localAssetURL`,
    `symbols.js`).
  - **Apple `image`:** `RasterInput` gets a memory-backed form.
    - `metadata()` and `bytes()` read the acquired buffer, wrapped as `Data`
      without a copy. Its deallocator is the one release.
    - The encoded cap (`RasterMetadata.encodedLimit`, 64 MiB) applies as for
      a file.
    - `CGImageSource` decodes from that `Data`. The `Data`, and with it the
      acquisition, lives until the `CGImageSource` and every image it made
      are gone.
    - **Animated images.** A GIF or WebP keeps decoding frames after the
      first: its animation owner reopens the source today
      (`RasterLoader.swift` passes `input.url`; `AnimatedRaster.swift`
      rereads the file). For a `blob:` source the owner holds the same
      `Data` instead and decodes later frames from it. The acquisition, and
      its charge (§2.5), last until the owner is released, so a revoke while
      a GIF plays does not stop it.
    - The bytes are never spooled to a file, as a `data:` source's are
      today.
    - **The loader's by-name cache.** `RasterLoader.acquire` returns a
      `byName` hit before it opens a source. For a `blob:` name, a hit is
      used only after the store confirms the URL still resolves, so a new
      load of a revoked URL fails.
  - **Apple `video`** lives in the on-demand video arm. AVKit stays out of
    ExactKit's link graph (LLP 1042).
    - **The bridge.** After loading the arm, `VideoModule` hands it
      `exact_blob_acquire` and `exact_blob_release` once, through an optional
      symbol, `exact_video_blobs(acquire, release)`. An older arm without it
      fails a `blob:` source as unsupported.
    - **The source.** ExactKit passes a `blob:` `src` through unchanged.
    - **Playback.** The arm acquires the buffer when it builds the item, and
      makes an `AVURLAsset` over the custom scheme `exact-blob:` with an
      `AVAssetResourceLoaderDelegate`. The delegate answers content
      information (the type as a UTI, the length, byte-range access) and
      each data request, on the loader's queue.
    - **Release.** The arm releases the buffer when the item is replaced or
      the arm destroyed.
    - **Revocation.** A playing video keeps playing after a revoke, as a
      browser's does once it has loaded. A new load of a revoked URL fails
      `src-not-supported`.
    - **`poster`.** It takes a `blob:` image through the same acquisition,
      decoded from `Data`, never read as a file.
  - **Linux `image`:** `ImageInput::Bytes` from an acquisition, released
    after decoding. Linux shows an animated image's first frame only, so
    nothing holds the buffer after that. Linux plays no `video` (LLP 1042), and `state.media` lists
    a `blob:` video as it lists any other.
- **Origins.** A host resolves only URLs whose origin is its own app id.
  Another app's URL is unknown.
- **Revoked or unknown.** Such a source is an `error`, "the object URL was
  revoked or never made (blob:…)". The web gives the browser's error, the
  fixed `IMAGE_ERROR` text.
- **The decoded-image cache is checked after the store.** A new load of a
  revoked URL fails even when its pixels are cached. A view already showing
  the picture keeps it, as a browser's `<img>` does.

### 2.7 Compatibility

`TYPESCRIPT_RUNTIME` goes to 3: an older prelude has no `Blob`.
