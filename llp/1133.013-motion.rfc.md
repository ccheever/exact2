## Summary

`@exact/motion` gives an app the device's acceleration, rotation, magnetic
field and orientation on the web, iOS and Android, with every other target
of LLP 1133 D8 a visible `later` or `absent` (a Mac has no motion sensors
an app can read: `CMMotionManager` is unavailable on macOS). Its tier 1 is
the web's two families: W3C Device Orientation and Motion's
`devicemotion` and `deviceorientation`, and the Generic Sensor API's
`Accelerometer`, `LinearAccelerationSensor`, `GravitySensor`, `Gyroscope`,
`Magnetometer`, `AbsoluteOrientationSensor` and
`RelativeOrientationSensor`, each a polled live source:

```
use requestMotionPermission, motionStatus, gravitySensor, startSensorInput,
  MotionStatus, GravitySensor from "@exact/motion"

resource motion = motionStatus() as shape MotionStatus
resource level = gravitySensor(frequency=30, referenceFrame="screen", interval=100)
  as shape GravitySensor else empty()

action enableTilt
  send asked = requestMotionPermission()
action tiltOn
  startSensorInput(surface="world", sensor="gravity", frequency=60, referenceFrame="screen")
```

```ts
import { accelerometer } from "@exact/motion";

// Every sample since this reader's last answer, in order, at most 64.
const a = await accelerometer({ frequency: 50, interval: 500, history: 64 });
const shakes = a.samples.filter(s => Math.hypot(s.x, s.y, s.z) > 25).length;
```

Tier 2 reaches Core Motion's attitude reference frames, its calibration
display and the heading it computes, the motion of AirPods and other
Apple headphones, and Android's sampling periods, hardware batching,
rotation-vector choice and uncalibrated sensors. Tier 3 hands the app's
Swift the module's one `CMMotionManager`, and its Kotlin the
`SensorManager`, each with every sample the module receives.

The question this module is the first to answer is **how a sample stream
reaches Contract and data code without flooding the runner** (LLP 1133
D6 rule 7: "a live value coalesces changes, so it cannot promise every
motion sample"). The answer is three paths over one acquisition (§3):

- **Contract and data code read a polled source** (LLP 1133.009's poll):
  the runner asks every `interval` (50 ms at the least), and each answer
  carries the latest reading and, when the reader asks for it, every
  sample since that reader's last delivered answer, up to `history`, with
  a count of what the bound dropped. The runner holds each reader's
  cursor, so an answer the runner discards loses no sample. A view that
  moves with the device moves by a CSS transition between polls, which
  the platform's animator runs at display rate.
- **A canvas takes samples as input** (LLP 1046.002 S1): a game or a map
  asks for a sensor on its surface, and the host hands the GPU module
  every sample, stamped, once per frame, below the runner, into the same
  input queue keys and pads reach. The engine reads it per tick, so a
  replay and a save carry it.
- **Tier 3** gets every sample on the platform's own thread.

The consumer is Beacons (`game/games/beacons`), which gains *Tilt to
move*: a toggle that asks on the web, a level the player sets in Contract,
and the tilt itself in the world's input (§10).

## 1. What exists

**Nothing reads a motion sensor.** No host, package or app calls
`CMMotionManager`, `SensorManager`, `devicemotion` or a Generic Sensor
class (a search of the tree finds none outside `llp/`). LLP 1124's spike
(§6) read `deviceorientation` on the web for an out-of-tree level app,
announced at most ten times a second and only past half a degree, and
recorded the lesson this RFC keeps: a live source is not an animation
channel.

**The seams this module builds on:**

| Seam | What it gives | Where |
|---|---|---|
| A polled live source | the runner asks again each period of a declared option, on the session clock, outside the plan's timer wheel; an answer covers the time since the last delivered; `clock +N` waits for the ask | LLP 1133.009 D1, D10 item 7 (accepted, not built) |
| The package context | `destroy`, `now()`, the foreground, `release(name, args)` | LLP 1133.009 D10 items 1–3, 12 |
| Admission | grant, origin, foreground and permission decision before any implementation, under the agent too | LLP 1133.002 D14; LLP 1133.008 D8 item 9 |
| A lease while displayed, with its commit's origin | a device runs while a view that consumes it is displayed; the origin of the commit that displayed it admits the lease | LLP 1133.008 D3, D8 item 2 |
| Raw input to a canvas | `Surface::wants_input` and `Surface::input(&InputEvent)`, stamped by the host in milliseconds, delivered by the presenter straight to the module (`gpu/src/lib.rs`, `gpu/src/input.rs`); the game engine queues events and folds them into ticks by their stamps (`game/engine/src/sim/queue.rs`) | LLP 1046.002 S1, as built |
| A runner-to-surface path | `postMessage(text, surface)` reaches a canvas as `InputEvent::Message`, in order, never coalesced (`host/web-js/commands.js`, `Session.swift`) | game engine, as built |
| The declared substitute | facts with `prefer` names, permission tickets, generic in the runner and the web runtime | LLP 1133.002 §6, as built |

**Grants:** `runner/src/device.rs` has no motion row, and a row's `web`
field holds one `Permissions-Policy` feature where motion needs up to
three.

**`rules/DEFERRED.md`** has no entry for sensors; its "Motion" entry is
CSS's transitions, which this module uses and does not change. A new
"Expanded" record is owed (§14 question 7).

**Options,** on every sensor source:

| Option | Meaning | From |
|---|---|---|
| `frequency` | samples per second the reader asks for: a hint, as Generic Sensor §8.1 makes it, which the platform may not meet | `SensorOptions.frequency` |
| `referenceFrame` | `device` (default) or `screen`: whether x and y follow the screen's orientation | `MotionSensorOptions.referenceFrame` ([Accelerometer §7.1](https://www.w3.org/TR/accelerometer/)) |
| `interval` | milliseconds between the runner's asks (default 100, at least 50) | LLP 1133.009's poll, D5 |
| `history` | the most samples one answer carries (default 0: the latest reading only; at most 1,024) | this module, D5 |

`deviceMotion` and `deviceOrientation` take `interval` and `history`, and
no `frequency` or `referenceFrame`, since their events have neither: they
fire at the browser's rate in the device's frame.

**Values,** one representation on every target, in the specifications'
units and frames:

| Shape | Fields |
|---|---|
| `Accelerometer`, `LinearAccelerationSensor`, `GravitySensor` | `x`, `y`, `z` in m/s²; `timestamp`; the batch fields |
| `Gyroscope` | `x`, `y`, `z` in rad/s, positive clockwise looking along the axis ([Gyroscope §6](https://www.w3.org/TR/gyroscope/)); `timestamp`; the batch fields |
| `Magnetometer` | `x`, `y`, `z` in µT; `timestamp`; the batch fields |
| `AbsoluteOrientationSensor`, `RelativeOrientationSensor` | `quaternion` (`[x, y, z, w]`, Orientation Sensor §6.1.1's order); `timestamp`; the batch fields |
| `DeviceMotionEvent` | `acceleration`, `accelerationIncludingGravity` (`x`, `y`, `z` in m/s², each `option`), `rotationRate` (`alpha`, `beta`, `gamma` in deg/s, `option`), `interval` (the sampling interval in ms), `timeStamp`; the batch fields |
| `DeviceOrientationEvent` | `alpha` in [0, 360), `beta` in [−180, 180), `gamma` in [−90, 90), degrees, each `option`; `absolute`; `timeStamp`; the batch fields |
| `MotionStatus` | `available`, `state` (`granted`, `prompt`, `denied`, `unknown`), `sensors` (one bool per sensor name), `apple`, `android` (D9) |
| the batch fields | `sequence` (the latest sample's number), `samples` (each a shape of the same name ending `Sample`, without the batch fields), `dropped` (samples the reader missed since its last answer), `interrupted` (acquisition paused since its last answer, D8) |

Each value is the specifications' frame (Device Orientation §3.1: x to
the right of the screen, y to its top, z out of it; the Earth frame of
Orientation Sensor §5.1 for absolute orientation: x east, y magnetic
north, z up). A device lying face up and at rest reads
`accelerationIncludingGravity` and `Accelerometer` z = +9.8 m/s² (Device
Orientation §1's example; Android's `TYPE_ACCELEROMETER` reads +9.81
there, by [Motion sensors](https://developer.android.com/develop/sensors-and-location/sensors/sensors_motion)).

**Errors** are the Generic Sensor API's `DOMException` names, as LLP
1133.006 D8 item 2 answers them (`{error, message}`; a `DOMException` in
TypeScript; `failure(…).code` in Contract): `NotAllowedError` (not
granted, or a caller the origin rule refuses, with `message`
`person-required`, D11), `NotReadableError` (the platform will not
deliver: the app is in the background, the sensor is busy), and
`NotSupportedError` (the device lacks the sensor, or the target has no
implementation). `SecurityError`, which the web throws when a frame's
Permissions Policy forbids the feature, does not arise: an Exact page is
never framed.

**Declared deviations,** each because a web form is an object or an
event a function cannot hold:

- **A sensor object and an event are live sources.** `new Accelerometer`
  and `start()` are a resource reading `accelerometer(…)`; `stop()` is
  the last reader's release (LLP 1133.002 D5); `onreading` is the
  runner's next ask; `onerror` is the source's failure. The class's
  attributes are the answer's fields, under the class's name as the
  shape, and `activated` and `hasReading` are whether the resource has
  answered. `populateMatrix` is not a field: an app that wants a matrix
  computes it from `quaternion` (Orientation Sensor §6.1.2 gives the
  formula), since a Contract value holds no method.
- **The answer is a batch,** not one event per reading (D5). A reader
  that asks for no history receives the latest reading, which is what a
  page's `onreading` handler sees when it reads the attributes.
- **One request for both events.** `requestMotionPermission` calls both
  web methods in one press and answers `MotionStatus`, not a
  `PermissionState`, as geolocation's `requestPreciseLocation` answers its
  status (LLP 1133.002 D10). WebKit keeps one decision per origin for
  motion and orientation together
  ([DeviceOrientationAndMotionAccessController.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/dom/DeviceOrientationAndMotionAccessController.cpp)),
  so the two are one decision where the web asks at all.
- **`startSensorInput`** has no web name: a web game reads a sensor in its
  own frame loop. Here a canvas's module is Rust or a GPU module the app
  does not script per frame, so the host delivers the samples to it (D6).
- **Two units for rotation.** `Gyroscope` is rad/s and
  `DeviceMotionEvent.rotationRate` is deg/s, as the two specifications
  define them; the module converts neither to the other's.

### D2 — Platform values, mapped to the web's

| Name | Apple (Core Motion) | Android (`SensorManager`) | Web |
|---|---|---|---|

| `linearAccelerationSensor` | `CMDeviceMotion.userAcceleration` × −9.80665 | `TYPE_LINEAR_ACCELERATION` | `LinearAccelerationSensor`, else `acceleration` |

| `gyroscope` | `CMGyroData.rotationRate` (rad/s) where `isGyroAvailable`; the bias-corrected `CMDeviceMotion.rotationRate` when the reader asks `apple.biasCorrected` | `TYPE_GYROSCOPE` | `Gyroscope`, else `rotationRate` in rad/s: x from `beta`, y from `gamma`, z from `alpha` (Device Orientation §3.2 names each rate's axis) |
| `magnetometer` | `CMMagnetometerData.magneticField` (µT) | `TYPE_MAGNETIC_FIELD` | `Magnetometer` where a browser ships it; none does by default ([Magnetometer](https://www.w3.org/TR/magnetometer/)), so `NotSupportedError` |
| `absoluteOrientationSensor` | `CMDeviceMotion.attitude.quaternion` under `xMagneticNorthZVertical`, turned from Core Motion's x-north frame to the W3C's y-north | `TYPE_ROTATION_VECTOR` | `AbsoluteOrientationSensor`, else `deviceorientationabsolute`, else `NotSupportedError` (stage 1 decides whether WebKit's `webkitCompassHeading` serves) |
| `relativeOrientationSensor` | the attitude under `xArbitraryZVertical` | `TYPE_GAME_ROTATION_VECTOR` | `RelativeOrientationSensor`, else `deviceorientation`'s angles as a quaternion |
| `deviceMotion` | `CMDeviceMotion`, as WebKit maps it, with the sign below | the three sensors above, at one rate | the event |
| `deviceOrientation` | the attitude as alpha, beta, gamma (`absolute`: `xMagneticNorthZVertical`) | `getRotationMatrixFromVector` and `getOrientation` over the rotation vectors | the event |

**The sign of gravity.** Core Motion reports acceleration in g
([Getting raw accelerometer events](https://developer.apple.com/documentation/coremotion/getting-raw-accelerometer-events):
"the value 1.0 representing an acceleration of 9.8 meters per second (per
second) in the given direction"), with gravity pointing toward the Earth,
so a device face up reads z = −1. The W3C and Android read +9.8 there. The
Apple implementation multiplies by −9.80665. WebKit multiplies by
+9.80665 with no change of sign (`kGravity` in
[WebCoreMotionManager.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/ios/WebCoreMotionManager.mm)),
so Safari on iOS reports the opposite sign to the specification and to
Chrome on Android; the web implementation detects it at the first reading
(z of `accelerationIncludingGravity` against `deviceorientation`'s `beta`
and `gamma`, which give gravity's direction) and negates, so one sign
reaches every caller. Stage 2 confirms Core Motion's sign on an iPhone and
stage 1 Safari's, each in the conformance suite.

**Timestamps** are milliseconds on the session clock (LLP 1133.009 D10
item 2's `now()`), so a sample lines up with `clock` under the agent and
with input events in a canvas. Each platform stamps a sample on its own
monotonic clock: Core Motion's `CMLogItem.timestamp` (seconds of system
uptime), Android's `SensorEvent.timestamp` ("nanoseconds … the same time
base as `SystemClock.elapsedRealtimeNanos()`",
[SensorEvent](https://developer.android.com/reference/android/hardware/SensorEvent#timestamp)),
the web's `DOMHighResTimeStamp`. The implementation keeps the offset
between that clock and the session clock, measured when acquisition
starts and again on each return to the foreground (Android's two clocks
part only across deep sleep, which a foreground app does not see). A
platform that batches in hardware (D9's `android.maxReportLatencyUs`)
keeps each sample's own time, so a batch's samples are stamped when they
happened, not when they arrived.

| Option | Web | Apple | Android |

| `frequency` written | the Generic Sensor's hint; on the event path the browser's rate | the stream's update interval, 1 / `frequency` s, capped by the hardware (usually at least 100 Hz, by the article above) | `samplingPeriodUs` = 10⁶ / `frequency`, a hint; above 200 Hz, D9's permission |
| `referenceFrame` omitted | `device` | `device` | `device` |

`deviceMotion` on Apple samples at 60 Hz whatever the reader asks, as
WebKit does, and on Android at `SENSOR_DELAY_GAME`.

Two unsaid behaviours are the platform's and noted for the recipe:
**calibration.** Core Motion shows its own calibration display only when
the app sets `showsDeviceMovementDisplay` (default NO, by the header), so
a north-referenced reading on an uncalibrated device reports nothing
special and is less accurate; a hand-built app sets the flag, and so does
this module when a reader asks for an absolute orientation, which is the
platform's answer to "the compass needs moving". **Rotation of the
screen** changes nothing in the device frame; an app that needs screen
axes says `referenceFrame="screen"`.

## 3. Samples: one acquisition, three paths

### D4 — One acquisition for the process, composed from every consumer

Apple's guidance is one manager per app ("Create only one
CMMotionManager object for your app. Multiple instances of this class can
affect the rate at which the system receives data from the accelerometer
and gyroscope", [CMMotionManager](https://developer.apple.com/documentation/coremotion/cmmotionmanager)),
and a sensor runs at one rate. So the implementation keeps, for the
process, one acquisition per platform stream (on Apple, one
`CMMotionManager` with its accelerometer, gyro, magnetometer and device
motion streams; on Android, one `SensorEventListener` registration per
sensor type; on the web, one `Sensor` object or event listener per name),
and gives each session its part, as LLP 1133.009 D3 holds one capture per
device. The sample host's two sessions read one gyroscope.

- **Consumers.** A stream runs while any session in the process has a
  consumer of it: a reader (D5) whose admission started or joined it, a
  canvas input (D6) whose surface is displayed, or a hatch that declares
  itself one (D10). A reader of `motionStatus` is not a consumer.
- **Rate.** A stream samples at the highest `frequency` among its
  consumers, and changes rate only when that maximum changes. Each
  consumer receives at most its own rate: the implementation thins the
  stream for it to the samples nearest its own grid of 1 / `frequency`,
  so what one reader receives never depends on another reader. A reader
  that asked 10 Hz beside a game at 60 Hz receives about ten samples a
  second.
- **Frames.** One stream serves both reference frames: the `screen` frame
  is a rotation of the `device` frame's sample by the orientation at its
  timestamp, applied per consumer.
- **The orientation streams differ by reference frame,** which Core Motion
  sets per start (`startDeviceMotionUpdatesUsingReferenceFrame:`) and
  Android per sensor type. Two consumers asking one device-motion stream
  for different attitude frames are served by the one that needs the
  magnetometer (an absolute frame), and the relative reading is computed
  from it by the yaw at the relative stream's start; a development build
  names the composition in the journal. Android needs no composition:
  each rotation vector is its own sensor.
- **Release.** `release(name, args)` (LLP 1133.009 D10 item 12) drops a
  reader's argument group; `release(name)` its last; a canvas input ends at
  `stopSensorInput`, when its surface unmounts, and at session end. The
  stream stops when the process has no consumer of it.

### D5 — Contract and data code: a polled reading with a batch, and the cursor is the runner's

Every sensor source and both event sources are polled live sources (LLP
1133.009 D10 item 7): the runner asks again each `interval` of the session
clock while a reader reads, outside the plan's timer wheel, with at most
one ask in flight, so a poll never stops a clock advance and `clock +N`
returns after the ask it crossed is answered and committed.

**Each answer carries:**

- the latest reading, as the shape's fields: what a view shows;
- when the reader asks for `history`, the **batch**: every sample (thinned
  to the reader's `frequency`, D4) taken after the reader's last delivered
  answer, oldest first, at most `history`; `dropped` counts those the bound
  left out, oldest first, so a reader that falls behind sees that it did,
  as LLP 1041 D2 asks of a bound ("never a silent drop");
- `sequence`, the number of the latest sample in the stream;
- `interrupted`, true when acquisition paused since the reader's last
  delivered answer (D8), so a gap in time is not read as stillness.

**The cursor is the runner's.** The implementation keeps a ring of recent
samples per stream, numbered, a second's worth or `history`'s at the
highest rate, whichever is longer, and answers an ask from the cursor the
ask carries, statelessly. The runner keeps each reader's cursor: the
`sequence` of the last answer it **delivered** to that reader, and sends
it as `after` on the reader's next ask. So an answer the runner discards
(a superseded generation, a reader released before delivery, a refused
commit) consumed nothing, and the next answer covers the same samples
again. A replaced answer hands its cursor to its replacement with its
reader, atomically (LLP 1133.002 D5). A reader's first ask carries no
cursor and gets the latest reading with an empty batch: a new reader is
not handed the past. The declaration names the field (`"cursor":
"sequence"`, D12), so the runner learns no motion.

**Why a batch, and not a stream of events.** LLP 1016.000 D1 makes each
message of a stream a settlement, a commit. A sensor at 100 Hz would be a
hundred commits a second per reader, each running derives, layout and
paint, where LLP 1133.009 D13 budgets 2 ms of main-thread time per update
at 20 updates a second. A poll bounds commits by the reader's `interval`
whatever the sensor's rate, and the batch keeps every sample for a reader
that needs them: one answer of 60 samples costs one commit. LLP 1016.000
D4's other answer, coalescing to the latest, is what a reader with no
history gets.

**The floor.** `interval` below 50 ms is refused at bake when literal and
clamped at admission when computed, journaled, so no reader asks the
runner for more than 20 commits a second. 50 ms is the rate at which LLP
1133.009 D13 measures the runner's cost; if that measurement passes at a
higher rate, the floor follows it, and if it fails at 20 the floor rises
to what passes. The same 50 ms applies to data code: a data-code reader
re-asks its answer on each poll, which is a settlement too.

**A view that moves with the device** (a level's bubble, a compass rose, a
card that tilts) reads a polled source at 50 to 100 ms and moves by a CSS
transition of the same length: `transform` with `transition: transform
100ms linear`, which the platform's animator runs at the display's rate
(Core Animation on Apple, `exact-motion` elsewhere, `rules/DEFERRED.md`
"Motion"), so the bubble glides between polls and the runner commits ten
times a second. The recipe says so. A view that must follow every frame
with the device (a camera-relative scene, a parallax at 120 Hz) is a
canvas (D6).

### D6 — A canvas takes samples as input, below the runner

`startSensorInput(surface=, sensor=, frequency=, referenceFrame=)` asks
the host to deliver a sensor's samples to the named canvas's GPU module,
as LLP 1046.002 S1 delivers keys, pointers and pads: "not state, …
device samples", stamped, never through the runner.

- **What arrives.** `gpu/src/input.rs` gains one variant, general for any
  sampled sensor:

  ```rust
  /// One sample of a sensor the app asked for on this canvas
  /// (`startSensorInput`), in the W3C's units and the frame it asked for.
  Sensor {
      /// The Generic Sensor name: "accelerometer", "gravity", "gyroscope", …
      sensor: SensorKind,
      /// x, y, z (and w for an orientation's quaternion).
      values: [f32; 4],
      /// Host clock in milliseconds, when the sample was taken.
      at_ms: f64,
  },
  ```

  `sensor` is any name of D1's seven, so a map that turns with heading
  takes `absoluteOrientation` the same way a game takes `gravity`.
- **Per frame, in order, every sample.** The implementation writes each
  sample into a per-surface single-producer ring on the platform's sensor
  thread; the host drains it once per display frame, before the frame's
  input is handed to the module, and delivers every sample since the last
  drain, stamped, oldest first. So a 100 Hz gyroscope reaches a 60 Hz
  frame as one or two samples, and none is coalesced. The ring holds a
  second; a module that falls a second behind loses the oldest, and the
  host delivers one `Sensor` sample with `values` of `NaN` and the time of
  the gap first, so the module knows (a `dropped` mark, as D5's count).
- **The engine reads it per tick,** as it reads pads: a tick's samples are
  those whose stamps fall in its window ("every window is world time",
  `game/README.md`). The engine gains `input.sensor(kind)` (the latest at
  the tick's end and the tick's samples) and one stick source,
  `Stick::or_tilt(Tilt { max_degrees, dead_zone })`, which maps gravity in
  the screen frame, relative to a neutral the game sets, to a stick. The
  samples sit in the input queue a save holds, so a replay and a restored
  save see the same tilt; a world that never asks for a sensor has no such
  event and its pins do not change.
- **A lease while displayed** (LLP 1133.008 D3's rule, LLP 1133.008 D8
  item 2's report). The input is a consumer only while its canvas is
  displayed, by `wakelock`'s function: a canvas under a screen pushed over
  it, or `display: none`, pauses its input and stops the stream if it was
  the last consumer; showing it again resumes. The send's admission (D11)
  records its origin, and a resumption carries that origin. A canvas that
  unmounts ends the input.
- **Who may start it:** the app's own foreground code and a person's input
  (`"origin": "app"`, `"foreground": true`, LLP 1133.009 D10 item 8). It
  is not a request: it never prompts. While `motionStatus().state` is not
  `granted` it fails `NotAllowedError`, and the app calls
  `requestMotionPermission` first, from a press (D11).
- **Under the agent** the runner's declared substitute synthesizes the
  samples (§9) and delivers them on the runner-to-surface path
  `postMessage` takes, as `InputEvent::Sensor`, for each interval a clock
  advance crosses, before the ticks of that interval run. So a game's proof
  sees the same samples at the same stamps on every host, Linux's
  GPU-less proof host included.

*Rejected:* the canvas reading a Contract source. The values would cross
the runner at its poll rate and reach the world one commit late, and a
gyroscope integrated for aim needs every sample.

*Rejected:* the game declaring the sensor in its Rust (`Stick::or_tilt`
starting acquisition by itself). Asking is the app's act (LLP 1133.002
D9), it needs a press on the web (D11), and the bake finds the module's
use in Contract and data code, not in a GPU crate (LLP 1133 D6 rule 6).

### D7 — The clock

Three clocks meet here, and each keeps its role:

- **The session clock** stamps every sample a caller sees (D2), so
  `timestamp`, `samples[i].timestamp` and a canvas's `at_ms` agree with
  `clock`, `now()` and input events. The canvas's `at_ms` is the host's
  input clock, which on every host is the session clock's live time
  (`game/README.md`: "`clock +N` and a 60 Hz panel fire the same ticks").
- **The poll's period** is the session clock's too (LLP 1133.009 D1), and
  never a plan timer: the agent's `clock +N` crosses `N / interval` periods
  and asks once, and the batch then covers every sample in the span, up
  to `history`.
- **The sensor's own clock** is converted at the implementation (D2) and
  never seen.

Under the agent the sensor is the substitute (§9), sampled on the
session clock's grid, so `clock +1000` with a 60 Hz reader and
`history=64` yields the same 60 samples on every host and every run.

### D8 — Foreground, lifetimes and threads

**Foreground only.** Android delivers no continuous-mode sensor events to
an app in the background ("Sensors that use the continuous reporting
mode, such as accelerometers and gyroscopes, don't receive events",
[Android 9 behaviour changes](https://developer.android.com/about/versions/pie/android-9.0-changes-all)),
iOS suspends a backgrounded app, and the web delivers only while the
document is visible (Device Orientation §6.1's significant-change steps;
Generic Sensor §4.2.4). So acquisition stops when the package context
reports the background (LLP 1133.009 D10 item 3) and resumes on return.
Readers and canvas inputs are kept; the next answer reads `interrupted`
true, and a canvas receives the gap mark of D6. A reader that asks while
the app is in the background answers its last reading, `interrupted`, and
no new samples; a first read there fails `NotReadableError`.

**Lifetimes.** Nothing here is a handle: a reader is its answer, and a
canvas input is named by its surface and sensor. So LLP 1133.009 D10 item
10's disposal has nothing to dispose of, and the session's end
(`destroy`) releases every consumer the session holds.

**Threads.** Every entry into the package is on the main thread (LLP
1067.000 D4). Samples arrive on the platform's thread: Core Motion's
handler on an `OperationQueue` the implementation owns (the header advises
"a queue that will not be used in other contexts"), Android's listener on
a `HandlerThread` the implementation passes to `registerListener`, the
web's events on the page's main thread. There the implementation writes
the sample into the stream's ring and into each canvas input's ring,
single-producer and lock-free, and never allocates, locks or waits. An
answer to a poll reads the ring on main. Nothing hops to main per sample.

without it is clamped to 200 Hz and journaled, never thrown.

poll's (D5); the hardware's is the platform's, letting the processor sleep
while the sensor samples. A reader that polls every second for a step
analysis may ask `android.maxReportLatencyUs=500000`, and the samples
arrive in bursts with their own timestamps (D2). It is inert while a canvas
input reads the stream, which needs samples each frame.

## 6. Permission

### D11 — LLP 1133.002 §4, where every native platform grants without asking

**Declare.** `device.motion <purposeKey>`, a declared deviation: the
Permissions Registry has three names, `accelerometer`, `gyroscope` and
`magnetometer`, and no platform asks for them apart (WebKit's one
decision covers motion and orientation, D1; iOS and Android ask nothing).
Derived:

| Target | Derived | Does a prompt show the purpose? |
|---|---|---|
| iOS | nothing for `CMMotionManager`, which needs no authorization and no usage key; `NSMotionUsageDescription` when the app uses `headphoneMotion` (without it "the system crashes your app when you start device-motion updates", [CMHeadphoneMotionManager](https://developer.apple.com/documentation/coremotion/cmheadphonemotionmanager)) | yes, for headphone motion |
| macOS | `NSMotionUsageDescription` when the app uses `headphoneMotion`; nothing otherwise | yes, for headphone motion |
| web | `Permissions-Policy: accelerometer=(self), gyroscope=(self)`, and `magnetometer=(self)` when the app uses `magnetometer`, `absoluteOrientationSensor` or `deviceOrientation(absolute=true)` (the policy features of Device Orientation §4 and Orientation Sensor §5) | no |
| Android | nothing: motion sensors need no runtime permission; `HIGH_SAMPLING_RATE_SENSORS` by D9's rule | — |

The row's `web` field becomes a list, and a feature in it may be derived
by the names and literal arguments the app uses (LLP 1133.009 D10 item
9's grants per name and argument, applied to derivation). An app that
uses a motion name without the line is refused at bake (`grant-missing`).
The line is required even where nothing prompts: it is where the purpose
lives when a prompt appears (Safari's, the headphones'), the source of
the web's policy, and the place a reader of the app learns it reads the
device's motion, which research has shown can infer what a person types
(the reason browsers gate it, Device Orientation's privacy considerations).

**Read.** `motionStatus().state`, one meaning on every target (LLP
1133.002 D8):

| Platform | `state` |
|---|---|
| iOS, Android | `granted`: nothing to ask. A device with no motion sensor reads `available` false |
| web, where `requestPermission` exists (WebKit) | `prompt` until the page's first answer, then the answer; WebKit keeps it per origin for the page (D1), and stage 1 records whether it survives a reload |
| web, where the Permissions API names the sensors (Chromium) | `permissions.query` for each feature the app's names need: `denied` if any is, `prompt` if any is, else `granted` |
| web, neither (Firefox) | `granted` while the events exist: the browser asks nothing |
| macOS | `available` false, `state` `unknown`, but for `apple.headphoneMotion` |

`apple.headphoneMotion` is tier 2's own state, with its own request.

**Ask.** `requestMotionPermission(absolute=)` is the request. On WebKit
it calls `DeviceMotionEvent.requestPermission()` and
`DeviceOrientationEvent.requestPermission(absolute)`, which prompt only
"if … processing a user gesture" (`UserGestureIndicator::processingUserGesture`
in WebKit's access controller; the specification's transient activation,
Device Orientation §6.1) and otherwise reject `NotAllowedError` while the
state is `prompt`. Elsewhere it answers the status at once. Every reader
and canvas input is a fact, never a request: on WebKit, while `prompt`,
they fail `NotAllowedError` with `message` naming
`requestMotionPermission`, and are asked again when the state changes.

**A press's own dispatch.** WebKit's rule is the gesture's dispatch, not
a window after it, and today a module send on the web goes through a
promise to an implementation loaded by `import()` on first use
(`host/web-js/modules.js`, `implementation`), which runs after the press
has returned. So the declaration marks the send `"gesture": true` (D12),
and the web runtime: loads that interface's implementation after first
pixel when the plan names a gesture send, rather than at the first call;
runs the send's admission synchronously inside the input event's
dispatch; and calls the implementation's handler in the same dispatch,
which calls `requestPermission` before it returns. Admission that would
hold a ticket (the agent's) or refuse holds or refuses first, as for any
send. If the implementation has not loaded when the press comes, the send
fails `NotAllowedError` with `message` `not ready`, journaled, and the
recipe's pattern (the button shown once `motionStatus()` has answered)
avoids it. Native hosts do not enforce a gesture (LLP 1069.002 Q2, LLP
1069.003 Q2), and nothing native prompts. Stage 1 proves the path in
Safari on an iPhone, and whether WebKit's gesture token survives a
microtask, which would let the dispatch stay asynchronous.

**Who may ask, read and start.** LLP 1133.002 D12's origin table, with
the capture rule of LLP 1133.009 D9 for starting a device:

- **A request from a tool or a wake** fails `person-required` while it
  would prompt (WebKit's `prompt`); elsewhere it answers the status.
- **Starting acquisition** is refused to a tool invocation and a wake
  (`NotAllowedError`, `person-required`), in every state: a tool-origin
  reader whose read would start a stream fails; one that reads a stream
  already running for an app-origin consumer joins it. A
  `startSensorInput` is `"origin": "app"`. Motion has no indicator, so the
  person has no notice that an agent acting through the app's tools is
  sampling their hand's movement; the delegation LLP 1133.002 D12
  describes may say otherwise when it exists.
- **The foreground:** acquisition never starts in the background (D8).

Recovery is LLP 1133.002 D11's: on Safari a denied origin is changed in
Settings › Apps › Safari › Advanced, which the app explains in its own
words; `openURL("app-settings:")` is refused on the web as before.

### D12 — The package

```
packages/motion/

  exact.json        the interface: D1's names and shapes, the permission, the substitute
  test/             the conformance suite: a fixture app and authored tests
  apple/            exact.json (headphoneMotion, requestHeadphoneMotion, the words), Motion.swift
  android/          exact.json (the words), Motion.kt
  web/              exact.json, index.js
```

An extension (LLP 1133 D5): the capability needs nothing only the runner
or the kernel has, beyond the general seam additions below. It needs no
Maven library (`SensorManager` is the platform's), no view and no audio
claim.

The interface declaration, abridged, in LLP 1133.002 D13's form with LLP
1133.009 D10's additions and this RFC's:

```json
{
  "kind": "interface", "name": "@exact/motion", "version": "1.0.0",
  "grants": ["device.motion"],
  "permission": { "name": "motion", "status": "motionStatus", "field": "state",
    "denied": "NotAllowedError" },
  "names": [
    { "source": "gravitySensor", "live": true, "poll": "interval",
      "samples": { "bound": "history", "cursor": "sequence", "frequency": "frequency" },
      "origin": "app", "foreground": true, "grants": ["device.motion"],
      "options": { "frequency": "option<number>",
        "referenceFrame": "option<enum<device|screen>>",
        "interval": { "type": "option<number>", "min": 50, "default": 100 },
        "history": { "type": "option<number>", "max": 1024, "default": 0 } },
      "answers": "GravitySensor",
      "substitute": { "default": { "x": 0, "y": 0, "z": 9.80665 }, "track": true } },
    { "source": "motionStatus", "live": true, "answers": "MotionStatus",
      "sync": { "name": "motionStatusSync", "from": "read" },
      "substitute": { "default": { "available": true, "state": "granted" } } },
    { "send": "requestMotionPermission", "request": true, "gesture": true,
      "options": { "absolute": "option<bool>" }, "answers": "MotionStatus" },
    { "send": "startSensorInput", "origin": "app", "foreground": true,
      "options": { "surface": "surface",
        "sensor": "enum<accelerometer|linearAcceleration|gravity|gyroscope|magnetometer|absoluteOrientation|relativeOrientation>",
        "frequency": "option<number>", "referenceFrame": "option<enum<device|screen>>" } }
  ]
}
```

The other six sensor sources and the two event sources are declared as
`gravitySensor` is, each with its own default. `"origin": "app"` on a
source means its read may not start acquisition for a tool or a wake
(D11); it joins one already running.

**The seam additions,** each general, each proved by the out-of-tree
fixture before this package uses it (LLP 1133.001 D8):

1. **A sampled source** (`"samples"`): on a polled source, the runner keeps
   each reader's cursor (the named answer field of its last delivered
   answer), passes it as `after` on the reader's next ask, hands it over
   with the reader, and refuses a `history` above its bound at bake. The
   implementation keeps the ring and answers from `after`. The runner
   reads no sample. A level meter's history (LLP 1133.009's `levels`), a
   Bluetooth characteristic's notifications and a heart-rate strap would
   use the same field.
2. **A floor on a poll** (`"min"` on the poll's option): refused at bake
   when literal, clamped at admission when computed, journaled.
3. **A package feeds a canvas** (D6): a declaration type `surface` (a
   canvas's surface name in the session, checked at bake against the
   app's canvases where literal); `InputEvent::Sensor` in `gpu/src/input.rs`;
   in the context, `surfaces.input(surface:)`, which hands the
   implementation a single-producer ring the host drains into that
   surface's input once per frame; the surface's displayed reports with the
   origin of the commit that changed them (LLP 1133.008 D8 item 2, extended
   from package views to a kernel `canvas` that a package feeds); and a
   development refusal of a surface name no canvas in the session has.
4. **The screen's orientation in the context:** the angle of the session's
   window (0, 90, 180, 270), with a change notice: `screen.orientation`
   on the web, the window scene's `effectiveGeometry.interfaceOrientation`
   on iOS, `Display.getRotation()` on Android. A `screen` reference frame
   needs it, and so will the roster's `screen` module.
5. **A send made inside the press** (`"gesture": true`, D11): on the web,
   the implementation is loaded after first pixel when the plan names such
   a send, and the send's admission and handler run synchronously in the
   input event's dispatch. Native hosts treat it as any send. Fullscreen,
   pointer lock, `navigator.share` with files and WebAuthn have the same
   rule on some browsers and will use the mark.
6. **A sampled substitute** (`"track": true`, §9): a preferred value of a
   sampled source may be a track of steps on the session clock; the runner
   and the web runtime synthesize samples from it on the reader's grid, and
   under the agent deliver a canvas input's samples on the
   runner-to-surface path.
7. **A grant row with several policy features,** some derived by the names
   and literal arguments used, and an Android normal permission derived by
   a literal argument (D9, D11).

Each is apparatus under `rules/RULES.md` and lands with this ruling.

### D13 — Callers

Contract reads every sensor source, both event sources and `motionStatus`
as sources; it sends `requestMotionPermission` from an action, which on
the web must be a press, and `startSensorInput` and `stopSensorInput` as
statements. Data code calls the sources and `requestMotionPermission`
through the generated binding (LLP 1133 D6 rule 1), in Promise form; a
data-code `requestMotionPermission` on WebKit is outside any press and
answers the status it can (`prompt` stays `prompt`), which the recipe
says. Requests: `requestMotionPermission` and, from the Apple
implementation, `requestHeadphoneMotion`. `sync`: `motionStatus`, on Apple
through `call`; the sensor sources are not `sync`, since a first reading
needs the hardware to start. Canvas inputs are Contract's alone: data
code has no surface.

**Which path.** A view shows a polled reading (D5). Data code that needs
every sample reads a batch (D5). A world or a canvas that moves at frame
rate takes an input (D6). Native code that needs the hardware's every
sample takes the hatch (D10).

source fails `NotSupportedError`, and `startSensorInput` fails the same,
so a game's toggle hides itself. Under the agent the declared substitute
answers on every target (§9), absent ones included, since the substitute
reads no device; `prefer extension motion.motionStatus={"available":false}`
gives a drive the production answer.

### D15 — Cost

An app that does not import the module links none of it, derives no
policy row or permission, and loads no page code (LLP 1047.001). One that
does loads it with the app's module after first pixel, and on the web,
when the plan names `requestMotionPermission`, loads the implementation
then rather than at its first call (D11); nothing runs before first pixel.
Core Motion is linked by the module dylib, as CoreLocation is by
geolocation's (LLP 1133.002 D16). Stage 2 records the implementation's
size; stage 0 records the runner's cost of a reader at 50 ms with a batch
of 64, against LLP 1133.009 D13's budget.

## 9. The substitute

**A declared substitute** (LLP 1133.002 §6), not an implementation that is
its own (LLP 1133.006 D8 item 4): the sensors' values are numbers on a
clock, which the runner can answer for every target from the declaration,
and games prove themselves on Linux's GPU-less host (`game/README.md`,
`prove`), where no implementation exists. An implementation as its own
substitute could not drive a game's tilt there (the cost LLP 1133.009 §10
names). Admission runs before the substitute as before any implementation.

**Shape:** every sensor source and both event sources are facts, sampled;
`motionStatus` is a fact; `requestMotionPermission` is a request; a canvas
input is fed by the substitute's samples.

**Defaults:** `motionStatus` `{available: true, state: "granted", sensors:
all true}`, since iOS and Android grant without asking; a drive of the
web's prompt says `--permission motion=prompt`. The device lies face up,
at rest, facing magnetic north: `accelerometer` and `gravitySensor` read
(0, 0, 9.80665), `linearAccelerationSensor` and `gyroscope` zeros,
`magnetometer` (0, 22, −42) µT (a mid-latitude field pointing north and
down), both orientation sensors the identity quaternion,
`deviceOrientation` alpha, beta and gamma 0.

**Tracks.** `prefer extension motion.<name>=…` takes a reading, which
holds from that moment, or a list of steps, each a reading with `at`
milliseconds after the moment it is preferred, each holding until the
next:

```
prefer extension motion.gravitySensor=[{"at":0,"x":0,"y":4.9,"z":8.49},{"at":500,"x":3.0,"y":4.9,"z":7.9}]
```

Samples are taken on the reader's grid of the session clock (every 1 /
`frequency` from the reader's first ask), so a batch is a pure function of
the track, the grid and the cursor, and is the same on every host. Steps,
not interpolation: the runner computes nothing about motion, and a drive
that wants a ramp writes its steps. Sensors are independent: a track on
`gravitySensor` does not move `accelerometer`; a drive sets what the app
reads. `=clear` returns to the default.

**Transitions:**

| Event | Result |
|---|---|
| `requestMotionPermission` while `prompt`, from a foreground origin | a `permission` ticket in `pending`; `allow` sets `granted`, `deny` `denied`, `cancel` leaves `prompt`; the call answers the status |
| a reader or a canvas input while not `granted` | fails `NotAllowedError`, asked again when the state changes |
| a reader while `granted` | answers the track at the reader's grid; batches by D5 |
| `startSensorInput` while `granted` | the canvas receives the track's samples for each interval a clock advance crosses, before that interval's ticks, as `InputEvent::Sensor` |
| `clock +N` | crosses polls and frames; returns after each crossed poll is answered and committed (LLP 1133.009 D1) and each crossed frame's samples are delivered |
| the app in the background (`prefer visibility-state hidden`) | readers answer `interrupted`, canvas inputs pause, as D8 |
| a tool-origin or wake-origin read that would start acquisition | fails `person-required`, as production (D11) |
| `prefer extension motion.motionStatus={"available":false}` | every source and input fails `NotSupportedError` |

**Disclosure:** `state.extensions` lists the process's streams with their
composed rate and frame, each reader with its arguments, cursor and
origin, each canvas input with its surface, displayed state and origin,
and the preferred tracks.

**Production:** none of it.

## 10. The consumer: Beacons

No app in `apps/` or `game/games/` reads motion today. The smallest real
use is the one phone games are known for: **tilt to move** in Beacons,
the walking game whose on-screen Move stick is its only movement on a
phone. A player holds the phone at a comfortable angle, sets that as
level, and tilts to walk. It is real (tilt steering is what a phone game
offers beside an on-screen stick) and small, and it needs every part of
this RFC that can fail: a permission asked in a press on the web, a
Contract reading the player watches, a value crossing from Contract into
the world, and samples reaching the world's ticks at frame rate,
deterministically, on the proof hosts.

Beacons gains:

- `"@exact/motion": "file:../../../packages/motion"` in a `package.json`
  of its own; a data module of one line, `app.ts` exporting `grants =
  'device.motion purpose.motion'`, since a game's grants are its data
  module's as every app's are; and a strings table for `purpose.motion`;
- in the pause screen, shown while `motionStatus().available`: **Tilt to
  move**, a toggle. Turning it on sends `requestMotionPermission()` (its
  press is the gesture WebKit needs) and, once `granted`, shows a level:
  a dot in a ring, placed by `gravitySensor(referenceFrame="screen",
  frequency=30, interval=100)`'s x and y less the level last set, moved by
  a 100 ms transition (D5), and **Set level**, which keeps the current
  gravity in Contract state and posts it to the world
  (`postMessage("tilt " + x + " " + y + " " + z, "world")`);
- on Resume with tilt on, `startSensorInput(surface="world",
  sensor="gravity", frequency=60, referenceFrame="screen")`; turning it off
  sends `stopSensorInput`;
- in `logic/src/lib.rs`, `Stick::wasd().or_arrows().or_pad(Pad::Left)
  .or_tilt(Tilt { max_degrees: 20.0, dead_zone: 2.0 })`, and the tick
  takes a `tilt` message as the neutral, saved in `InputState`;
- while `denied` on the web, the toggle's line says motion access is off
  for this site in Safari's settings.

Its acceptance drives, on the web, the iOS simulator and the Android
emulator under the agent, and on Linux in `prove` (ticket ids from
`state.pending`, `@p` here):

1. `--permission motion=prompt`; `tap play`; `tap pause`; `tap tilt`:
   a ticket; `tap @p allow`: the level shows the dot centred (the default
   pose is flat, so the screen frame's x and y are 0).
2. `prefer extension motion.gravitySensor={"x":0,"y":4.9,"z":8.49}`
   (held at 30°); `clock +200`: the dot has moved off centre by the 30°
   tilt; `tap set-level`: it returns to the centre; `tap pause` (resume).
3. `prefer extension motion.gravitySensor={"x":3.0,"y":4.9,"z":7.9}`;
   `clock +1000`: the player has moved right by the distance the movement
   table gives for that stick for one second, the same on every host;
   `state.extensions` shows one stream at 60 Hz (the input) beside none
   for the level, which unmounted with the pause screen.
4. `tap pause`, then quit to the title: the canvas unmounts, and
   `state.extensions` shows no stream.
5. `--permission motion=denied`: the toggle shows the denied line and no
   ticket; the on-screen stick still moves the player.
6. `prove`: a tilt leg on Linux and the web with drive 3's tracks, pinned;
   the existing legs' pins unchanged, since they ask for no sensor.
7. By a person, on an iPhone in the app and in Safari, and on an Android
   phone: the toggle asks in Safari and nowhere else; holding the phone at
   an angle and setting level makes that angle still; tilting walks; the
   app leaving and returning resumes the tilt; the level's dot moves
   smoothly.

The conformance suite (LLP 1133.001 D7) runs the real web implementation
in Chromium with its sensor emulation (Device Orientation §9's automation,
and the DevTools protocol's sensor overrides) and in WebKit and Firefox
with synthesized events; the Android implementation on an emulator, whose
console sets its virtual sensors (`sensor set acceleration x:y:z`); the
Apple implementation only on an iPhone, since the iOS simulator reports
no motion hardware. It checks the units, the sign of gravity, the screen
frame at each rotation, thinning beside a faster consumer, the cursor
across a superseded answer, `dropped` past the bound, the gap mark after
the background, and a data-code reader of a 64-sample batch.

## 11. What this amends

- **LLP 1133 D6 rule 7:** the bounded batch protocol it asks for is D5's
  (a polled answer carrying every sample since the reader's last delivered
  answer, with a runner-held cursor and a visible count of what the bound
  dropped), and frame-rate delivery is D6's input below the runner.
- **LLP 1069.007:** a sampled fact's substitute is a track of steps on the
  session clock (§9).
- **LLP 1133.009 D10 item 7:** a polled source may declare a batch with a
  runner-held cursor and a floor on its period (D12 items 1–2); recording's
  `levels` could take the cursor in place of "every interval since the last
  answer delivered", which the runner then keeps for it.
- **LLP 1133.008 D8 item 2:** displayed reports with their origin reach a
  package that feeds a kernel `canvas`, not only a package's own view.
- **LLP 1046.002 S1:** a package may feed a canvas's input
  (`InputEvent::Sensor`), and under the agent the runner does on the
  `postMessage` path.
- **LLP 1069.008:** the `device.motion` row; a row's policy features become
  a list, derivable by use.
- **LLP 1133.000 §3.3:** motion's row names `startSensorInput` and the
  headphone source, and its "tier 2 must reach" cell reads "attitude
  reference frames, headphone motion, Android's sampling period,
  hardware batching and uncalibrated sensors".
- **`game/README.md`:** `input.sensor`, `Stick::or_tilt`, and a sensor
  input among what a save holds.

## 12. What stays out

Each until a consumer asks:

- motion in the background or while the app is closed (`CMSensorRecorder`,
  an Android foreground service), and wake-up sensors;
- steps, activity and floors (the roster's `pedometer`), altitude and
  pressure (`altimeter`), light, proximity as tier 1;
- fall detection, water submersion, movement disorder (Apple's platform
  modules);
- a Contract reader faster than the poll's floor; a package view that draws
  from samples below the runner (a canvas does it, D6);
- `populateMatrix` and other conversions as names; the app computes from
  the quaternion;
- `deviceOrientation` and the sensor sources on macOS, which has no
  motion hardware an app can read;
- Windows, visionOS and watchOS cells, and Linux through IIO.

## 14. Questions for the ruling

1. **The batch with a runner-held cursor (D5)** as LLP 1133 D6 rule 7's
   bounded protocol for every sampled source, with a 50 ms floor on the
   poll that follows LLP 1133.009 D13's measurement. *Proposed: yes (80%).
   The alternative, a stream whose every message commits (LLP 1016.000
   D1), costs a commit per sample.*
2. **Frame-rate samples reach a canvas below the runner (D6),** started by
   a Contract send, held while the canvas is displayed, read by the engine
   per tick and saved with the input queue. *Proposed: yes (80%).*
3. **The declared substitute with step tracks (§9),** rather than the
   implementation as its own substitute, so that games prove tilt on Linux.
   *Proposed: yes (75%); the cost is a track vocabulary in both runtimes'
   substitutes, generic and computing nothing about motion.*
4. **A send made inside the press (`"gesture": true`, D11),** loading the
   web implementation after first pixel rather than at first use.
   *Proposed: yes (70%), pending stage 1's measurement of whether WebKit's
   gesture survives the asynchronous path, which would make it
   unnecessary.*
5. **One grant line, `device.motion`,** for the Registry's three names,
   required although iOS and Android ask nothing. *Proposed: yes (75%).*
6. **Starting acquisition is the app's (D11),** refused to tools and wakes
   in every state, as the capture rule. *Proposed: yes (70%); the
   alternative is geolocation's rule, under which a tool reads a granted
   value and so starts the sensor.*
7. **`DEFERRED.md`:** an "Expanded" record admitting the motion module by
   these names on the web, iOS and Android, with the canvas input and §12
   as its "Still out". Take: none offered; a waiver, or Charlie names one.
8. **D12's seven seam additions** as apparatus admitted with this ruling.
   *Proposed: yes.*
