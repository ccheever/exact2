## Summary

This spec gives documents the vocabulary they need, meaning the same thing on
every host.

- **Part A (phase 1a):** a `head` element, document scrolling and route policy
  fields, with meaning coming from roles lowered to HTML.
- **Part B (phase 1b):** required placeholders.

## Part A

**D1 — `head` is an element.**
`head title=… description=… image=… canonical=… robots=…` goes anywhere in a
route's view.
- It isn't visual and takes no space.
- The innermost active `head` wins, field by field.
- Values are ordinary expressions:
  `head title=post.title description=post.summary`.

**Status.** `status=404` or `status=410` makes the page answer with that HTTP
status (LLP 1048.000 D11). A view that shows "not found" declares it, whether
its item is missing or not public. Other values are a compile error. Native
hosts ignore it.

**Structured data.** A `head` field also carries structured data: a JSON-LD
string, usually built by a source. The renderer writes it into
`<script type="application/ld+json">`, escaped like the checkpoint
(LLP 1048.000 D6). Interview's question pages describe themselves as a
`QAPage`. The field's exact form is settled when those pages use it, in 1b.

**Per host:**
- **Web:** the document's `<head>` (LLP 1048.000 D3), kept in sync with
  `document.title` and the meta tags at runtime.
- **macOS:** `title` is the window title.
- **iOS:** `title` is the scene title.
- **Linux:** `title` is the window title.

In the kernel, `head` is a new node type with string props, excluded from layout.

*As built (1a):* `NodeType::Head` with the props `headTitle`,
`headDescription`, `headImage`, `headCanonical`, `headRobots` and the int
`headStatus`; the kernel lays a head out as `display: none` whatever its rows
say. Its six fields belong to `head` alone, and `head` takes nothing else;
`status` must be the literal 404 or 410 (`lower-attr-value`). "Innermost" is the deepest head,
the later in document order at one depth; a head in a route its navigation root
hasn't selected is inactive (`Runner::head`, `runner/src/head.rs`). The agent's
`state` reports the active head on every host. The web host never creates an
element for a head: it sends a `head` op when the active head changes, and the
document carries it (`Document::head`). The Apple host sends a `title` op
when the active title changes, and only the app that owns the chrome shows it:
on macOS the window toolbar host makes it the window's own title (a projected
toolbar heading still shows over it; no head gives back the app's title); on iOS
the app adapter's `onTitle` sets the scene's. An embedded view claims neither.
Linux has no window: its agent `state` is where the title shows. The agents'
`state` reports `window.title` beside `head`. Waiting: the glue's
`document.title` and meta tags (step 4).

**D2 — Meaning from roles, not new tags (r3).** This spec adds no semantic tags.
The meaning a crawler or screen reader needs comes from what nodes already say,
lowered to HTML by the one projection (LLP 1048.000 D1):
- a text with a heading level is `h1`–`h6` (landed, `44f8643c`);
- Markdown's blocks are paragraphs, headings, lists, quotes and code blocks;
- a `link` is an `<a href>`;
- an image with a label has its `alt`.

Each lowered element keeps the box a bare `div` would have, so layout is
identical on every host. The web host resets the element's HTML defaults, as
`index.html` does for headings today.

That reset covers only elements standing in for plain nodes. If a later spec
adds authored tags with HTML's defaults (r2 D2, at `bba74df6`), those tags don't
take the reset.

**D3 — Media variants: removed in r3.** Width variants were in phase 1 for
Interview's tabs/rail switch. But the rail renders only for signed-in readers
(`app.contract` ~413). Content that branches on the viewport renders at the page
viewport instead (LLP 1048.000 D4).

r2's design, with its corrected cascade, is the starting point when a consumer
needs one tree to lay out differently by width.

**D4 — Document scrolling, explicitly.** `scroll document` marks a view's scroll
container as the document on the web: `html` and `body` scroll instead of an
inner `div[data-scroll]`. That makes these work:
- printing;
- `#id` anchors and text fragments;
- scroll restoration;
- the mobile browser's collapsing toolbar.

It is explicit, not inferred, because layouts like Interview's scroll inside a
height-constrained container (`app.contract` ~637). A heuristic would miss them,
or change app shells that need an inner scroller. Natively, the document scroll
container is the window's.

*As built (1a):* `document` is a word the checker and lowerer read by its
spelling, never a name in scope. It sets the kernel prop `scrollDocument` on the
scroll view, which reaches the page and the document as
`data-scrolldocument="true"`. Natively nothing changes yet: the scroll view is
bounded by its layout like any other, and the unbounded-scroll refusal stands.
In `index.html`, one rule block under `html:has([data-scrolldocument="true"])`
lets `body` and `#exact-root` grow and makes the marked element a plain block,
so the page scrolls with JavaScript or without. A page's percentage heights then
resolve against its content, not the viewport. `document=(expr)` is the bound
form, so one wrapper can switch (bare `scroll document` is `document=true`;
the two together are refused): Interview marks only a signed-out reader's top
public entry, and two wrappers differing by case inlined its `Screen` twice. A
false binding reaches the page as `data-scrolldocument="false"`, which the rule
doesn't match.

**D5 — Route policy fields.** A route declaration (LLP 1038 D2) gains optional
fields:
- `render=client|build|cached|request` (LLP 1048 D2).
  - Undeclared, it is `client`.
  - The compiler reports the policy a route's inputs would allow, as a note. It
    never applies it.
- `activate=idle|never` in phase 1 (LLP 1048 D5).
  - Undeclared, it is `never` when the page needs no runtime and `idle`
    otherwise.
  - `visible` and `interaction` come with LLP 1048.001.
- `pages=<source call>` for parameterized routes. It lists the pages to render
  at build, and a per-request route's sitemap entries (LLP 1048.000 D2).
- `revalidate=<seconds>` for `cached`: the shared-cache lifetime, sent as
  `s-maxage` (LLP 1048.000 D11).

*As built (1a):* `render=` and `activate=` are `name=word` pairs after a route's
pattern (`tab home "/" render=build`), kept by `contract fmt` as written, and
carried in the plan's routes table as `RenderPolicy` and `ActivatePolicy`
(`inferred` when undeclared). An unknown field or word is `lower-route-field`,
and so is `render=build` on a route with parameters, until `pages=` comes with
enumeration. `pages=` and `revalidate=` arrive with their consumers (1b). The
compiler reports no inferred policy yet: that needs sources' stage labels (LLP
1048 D3), which nothing declares.

## Part B

**D6 — Required placeholders.** A resource whose source's stage is later than
`build` (LLP 1048 D3) needs a placeholder: the value it shows while pending. For
example: `resource cart = cart(user) as shape Cart else emptyCart()`.
- Shapes with an empty value (lists, options) have an implicit placeholder.
- A missing placeholder is a compile error naming the resource, so a boot never
  refuses an unanswerable resource.

## Verification

- **Corpus:** a fixture per element and field, compiled and booted. There is
  also a rejection fixture per new diagnostic: a missing placeholder, and an
  unknown value for a route field.
- **Roles:** the CDP accessibility tree shows headings, and Markdown's
  paragraphs, lists and quotes. Every lowered element lays out identically to the
  bare node it replaces, in the kernel and in Chrome (the 2026-09-22 parity
  harness).
- **Titles and print:** the window title follows `head title` on macOS and iOS.
  Printing a `scroll document` page produces every page, not only the first
  viewport.
