## Summary

The `queue/` entry asks two things: what a one-line edit to an app's Rust data
crate costs today, and whether Dioxus's Subsecond, which patches changed
functions into a running process, could apply to exact2's data modules.
This document records both. It builds nothing.

**Today's cost (warm, this Mac under load).** These are medians from save to
the new string on screen:

| Path | Caltrain | Outside app (heavy list, `EXACT_APP_DIR`) |
|---|---:|---:|
| Web dev loop, JS target (rebuild + page reload) | **2.34 s** | **3.15 s** |
| macOS, live module replacement over the dev URL (LLP 1029.000) | **1.99 s** | not enabled (`rust: off`) |
| iOS simulator, live replacement, Wasmi | **1.64 s** | not enabled |
| macOS, rebuild + relaunch | **9.0 s** | **9.3 s** |
| iOS simulator, rebuild + install + relaunch | **11.4 s** | **15.0 s** |

A Contract edit on the same loop is ~0.1 s.

**The finding.** The Rust compiler is a small part of these numbers. The
changed data crate compiles in 0.13–0.55 s. The rest is:
- the JS target's dev loop linking its module with the release profile
  (fat LTO, `opt-level = "z"`, `-Zbuild-std`);
- the native producer building its Wasm and native variants one after the
  other, then baking;
- Swift relinking, bundling and relaunching on the native rebuild path.

Subsecond's own advantage over a whole-module rebuild is skipping Cargo and
the full link. exact2's data module is already a separately linked small
artifact behind an encoded ABI. In the `logic-dev` profile it links in
0.08–0.14 s, so a function-level patch would save roughly 0.1–0.3 s more. In
exchange it would bring Subsecond's limits (struct layout, statics, TLS,
vtables, no iOS device) and about 4,900 lines of object-file surgery per
platform family.

**Recommendation:** do not build a Subsecond-style patcher now. Three cheaper
changes reach most of the way to LLP 1029.000 §6's sub-second objective:
1. Build the dev module with `logic-dev`.
2. Swap the module in place on the JS target instead of reloading the page.
3. Build only the variants that the connected clients need.

§5 lists them; `queue/` gets the first two.

## 1. What a one-line Rust edit costs today

### 1.1 Method

**The edit.** Each sample changes one string literal that the first screen
shows.
- Caltrain: `name: "Palo Alto"` in `apps/caltrain/data/src/lib.rs`, edited to
  `"Palo Alto v<i>"`.
- The outside app: the heavy-list app, copied from `~/bench/dioxus/exact-bounded`
  to `~/bench/dioxus/q4/bounded`, built with `EXACT_APP_DIR`. Its data crate
  parses a 7 MB `messages.json` and keeps a mutable `Feed`. The edit is
  `author: format!("{}{}", m.author, "~")`, with the `"~"` changed.

**What is timed.** From the file write until the marker is in the app's
text:
- On the web: headless Chrome's `document.body.innerText`, polled every 5 ms
  across the reload.
- On native: the agent driver's `tree`, through `scripts/agent.mjs`'s `open()`.
  The live-path polls advance the agent clock by 16 ms each.

The harnesses live outside the repository, in `~/bench/dioxus/q4/web/edit.mjs`
and `native/edit.mjs`. Raw samples are in `~/bench/dioxus/q4/logs/`. Each run
had 5–6 sequential edits, 1.5–2 s apart, after one warm-up build.

**Machine.** Mac Studio M5 Ultra, 36 cores. Four other agents' builds ran
concurrently, and the load average was **39–52** throughout. Treat every
number as pessimistic and noisy; the splits are more trustworthy than the
totals. Kelley's 130 ms for Subsecond (§2.4) is on an idle M4. `wasm-opt`
(binaryen) is not installed on this Mac, so every web build here skips it
and says "unoptimized". A machine with binaryen pays `wasm-opt -Oz` on top of
the web numbers.

### 1.2 Web dev loop (`bun host/web/dev.mjs`, JS target)

Save to new text, Caltrain: 2530, 1887, 2436, 2125, 2431, 2240 ms (median
**2.34 s**). The loop's own figure, edit to first frame in the DOM, is
1.87–2.47 s. The data module answers 10–64 ms after that frame, because it
loads after first pixel. The outside app: 3439, 3322, 2973, 2967, 3341,
2818 ms (median **3.15 s**).

**What a Rust edit runs.**
1. Every `.rs` save triggers the whole `host/web-js/build.mjs --render none --dev`.
2. That rebuilds the data module: `module.mjs`, run as `cargo +nightly build
   --release --target wasm32-unknown-unknown -Zbuild-std=std,panic_abort`.
3. The page reloads with its slots checkpointed (LLP 1071 §7). When the logic
   revision changed, settled answers are not carried; `carryAnswers` is false.

**Split.** These are clean reruns with no watcher, using Cargo's `--timings`:

| Phase | Caltrain | Outside app |
|---|---:|---:|
| Data crate (frontend + codegen) | 0.23–0.25 s (0.09–0.10 + 0.14) | 0.42–0.55 s (0.15–0.20 + 0.27–0.38) |
| Module cdylib: LTO + `wasm-ld` (Caltrain: the root `release`, thin LTO; outside app: generated crate, fat LTO, `opt-level=z`) | 0.48–0.56 s | 1.22–1.41 s |
| Cargo with `-Zbuild-std`, fingerprints (no-op build: 0.18–0.25 s) | ~0.2 s | ~0.1–0.2 s |
| `cargo build` alone | 0.92–1.02 s idle; 1.68–2.11 s inside the build under load | 1.75–2.02 s |
| The rest of `build.mjs` (Contract → JS, grants, Rolldown, stage rename) | ~0.25 s | ~0.2 s |
| Page reload → runtime up → data module answers | 10–64 ms | ~70–100 ms |

**What this shows.** For the outside app, the release link alone is 40% of
the edit. The parent RFC (LLP 1029.000 §6) already said a save should use
"an incremental development profile with light optimization, no fat LTO,
and no `wasm-opt` on saves". The native producer follows that rule; the JS
target's dev loop does not.

### 1.3 Native, live module replacement (LLP 1029.000, over the dev URL)

**Setup.** A macOS dev build (`apple-dev`) is opened by the driver with
`--url http://127.0.0.1:<port>/` against the JS dev loop. The loop forwards
the native client to the resident `--wasm` loop's producers
(`scripts/rust.mjs --serve`). On each save, the producers:
1. build `caltrain-logic` in `logic-dev`, for Wasm and then for native;
2. codesign the dylib;
3. bake with the resident `exact-logic-bake`;
4. publish a generation.

The client then fetches it, loads it (`dlopen` on the Mac, Wasmi on iOS),
validates it, and restarts with carry. `state.logic` afterwards reported
`rustExecutor: "native"` on the Mac and `"wasm"`, `ready: true` on the
simulator.

**Save to new text.**

| Client | First edit after connecting | Warm edits | Warm median |
|---|---:|---|---:|
| macOS | 112.4 s (resident loop and producers cold) | 2016, 1970, 1616, 2096 ms | **1.99 s** |
| iOS simulator, Wasmi | 6.19 s | 1644, 2400, 1931, 1644, 1575 ms | **1.64 s** |

The JS target's web rebuild ran concurrently on every one of these edits
(2.1–2.6 s), competing for the same cores.

**Producer split.** These come from a one-shot `bun scripts/rust.mjs caltrain`
with no watcher; the total was 1.25–1.54 s:

| Phase | Time |
|---|---|
| Producer start, Cargo metadata | ~0.25 s |
| Wasm variant, `logic-dev` | Cargo 0.25–0.35 s: data crate 0.13–0.20 s (frontend 0.06–0.08), cdylib link 0.08–0.14 s |
| Native variant | the same again, +0.35–0.45 s, serial after the Wasm variant |
| Codesign | ~10 ms |
| Bake (the one-shot pays a fresh `exact-logic-bake` start; the dev loop's is resident) | 0.3–0.4 s |
| Publish | ~25 ms |

In these runs `dlopen` of each fresh dylib was fast. LLP 1029.000 §6 recorded
the same step taking up to 104 s under a Gatekeeper `syspolicyd` assessment;
that did not recur here.

Under 2 s, this path already beats the JS target's web reload. It needs:
- the app to declare `rust.module` (Caltrain does);
- `rust` not to be `off` (the outside app's manifest says `"mode": "off"`).

## 2. How Subsecond works

These come from the 0.7.10 and 0.8.0-alpha.1 crate sources; file:line
citations are in `~/bench/dioxus/q4/subsecond-notes.md`.

### 2.1 Mechanism

**Fat build.** `dx` captures the first ("fat") build twice over:
- As `RUSTC_WORKSPACE_WRAPPER`, it records every workspace crate's rustc argv
  and environment.
- As the linker, it records the link line.

It then performs the link itself:
- Every workspace rlib's objects are force-loaded (`-force_load` or
  `--whole-archive`), with `-Clink-dead-code` and `-Csave-temps`, so that
  every symbol stays in the binary.
- `main` is exported as an ASLR reference.
- The original binary's symbol table is parsed once and cached. Per its own
  comment, that cache took the Dioxus docs site from 3 s to 1.1 s a patch.

**Thin build, per save.** No Cargo is involved:
1. Replay rustc for the changed workspace crates and their dependents, in
   topological order, and for the tip crate. 0.7.10 already does more than
   the documented "tip crate only"; crates.io dependencies are never patched.
2. Generate a stub object that turns every symbol the new objects need but
   do not define into a trampoline to its absolute address in *the running
   process*. The client reports `main`'s address as `aslr_reference` when it
   connects.
3. Link only the new objects and the stub into a dylib.
4. Build a jump table mapping old address to new address for every symbol
   name the patch shares with the original. There is no change detection,
   despite the docs' "diffing".
5. Send the table over the devtools websocket.

**Applying the patch.**
- **Native:** `apply_patch` dlopens the dylib, rebases the table by both
  `main` offsets, and swaps one global `AtomicPtr<JumpTable>`. Old code and
  tables are leaked on purpose.
- **Wasm:**
  1. Grow the host's shared memory and `__indirect_function_table`.
  2. Instantiate the patch with `__memory_base`/`__table_base` and every host
     export as imports.
  3. Run its relocations.

  This requires a base module built with `--emit-relocs --export-table
  --growable-table --no-gc-sections`, with every function placed in the
  table, and patches rewritten with `walrus` instead of re-running
  wasm-bindgen.

**Where new code runs.** Only calls through `HotFn` (`subsecond::call`) look
up the table. Dioxus wraps each component's render function in one and marks
every scope dirty after a patch.
- Inside the patch, calls between recompiled functions go to the new code.
- Everything else, including any fn pointer, closure or vtable created before
  the patch and any call from a dependency into the patched crate, keeps
  calling old code until the framework re-renders.

### 2.2 Stated limits

The ones that would bind exact2, quoted from `subsecond/src/lib.rs` and the
docs:
- **Struct layout.** "Subsecond currently does not support hot-reloading of
  structs… If layout or alignment change and new functions are called
  referencing an old version of the struct, the program will crash."
  Frameworks are told to "throw out the old state".
- **Globals.** "Changes to static initializers will not be observed." "You
  may add new globals at runtime, but their destructors will never be
  called." From the source (an inference, not tested): statics *defined in*
  the recompiled crate get fresh copies in the patch.
- **Thread-locals** in the recompiled crate "reset to their initial value on
  new patches… Sufficiently complex setups might crash or even segfault."
- **Trait objects.** "The real call function will likely end up in the vtable
  and will never be hot-reloaded." `FnOnce` is unsupported.
- **Generics.** Instantiations in dependency objects are reached through
  stubs, so they stay old. The docs give "a cascade of codegen changes" as
  the reason for the tip-crate rule.
- **Signature changes** are unchecked UB behind a matching symbol name
  (PR #3797: "Signature changes not supported").
- **No unwinding on Wasm.** `HotFnPanic`, the documented "unwind to the
  nearest changed caller", is never constructed in either version.
- **Requirements:** debug assertions and debug symbols are required.
- **iOS device:** "currently not supported due to code-signing requirements."
- **Off by default:** hot-patching is off by default in 0.7.10, with the help
  text "may lead to unexpected segfaults or crashes in development". It is on
  by default in 0.8.0-alpha.1.

### 2.3 How Dioxus keeps state

The VirtualDom stays alive and re-renders, so root hooks survive.

After a patch, `use_hook` replaces a slot whose type no longer downcasts
instead of panicking, so a hook list may change. The replacement is keyed by
`TypeId`, so a slot whose type is unchanged keeps its value even if it now
means something else.

The following is an inference from source, not tested. Child components
probably remount: `diff_vcomponent` replaces a component whose render-fn
pointer changed, and every patch remaps every tip-crate symbol.

## 3. Could a version apply to exact2's data modules?

### 3.1 What exact2 already has

A data module is already the unit that Subsecond's thin link approximates:

- **It is linked on its own.** It is a declared `cdylib` (`rust.module.package`)
  separate from the host.
- **It sits behind an ABI that carries no Rust type.** The encoded Value
  envelope of LLP 1029.000 §3 is that ABI.
- **It is replaced whole, through one indirection.** The host adapter's
  executor pointer is a jump table with one entry.

On the web it is a separate importless Wasm. On macOS it is a `dlopen`ed
dylib, and on iOS a Wasmi instance.

Replacement creates a fresh instance and restarts the session with carry
(LLP 1007 §6). That makes it **immune to every Subsecond limit in §2.2**:
- Struct layout, statics, TLS, vtables, generics and signatures inside the
  module all change freely, because nothing of the old module's code or heap
  is reached afterwards.
- It works on an iOS device: Wasmi needs no code signing, and LLP 1029.000
  measured an iPhone at 3.8–6.3 s.

What Subsecond has that exact2 lacks is **keeping the module's private heap**:
- **Caltrain:** `pub struct Caltrain;` holds nothing, so there is nothing to
  keep.
- **The outside app:**
  - Each replacement re-parses its 7 MB feed in `activate`.
  - Each replacement loses any reaction counts mutated through `react`, which
    live in its `Feed`, not in the Store.

  Under exact2's rules (LLP 1029.000 §1: "arbitrary Rust heaps do not
  migrate"), that state belongs in the Store or Contract slots.

  Subsecond would keep the `Feed` only while its layout is unchanged. An edit
  that adds a field to `Message` would read the old heap with the new layout,
  which is the documented crash.

### 3.2 What a Subsecond-style patcher would cost here

**Native (macOS, Linux, iOS simulator).** It would need all of the following:
- The rustc-wrapper and linker interception, around the `logic-dev` module
  build.
- A fat link of the module with `-Clink-dead-code -Csave-temps` and an
  exported reference symbol.
- A symbol-table cache.
- A Mach-O (and ELF) stub generator.
- A thin link per save.
- A table delivered over the dev URL.
- A `HotFn` indirection at the module's entry points. Here that is the ABI
  dispatcher, `exact_logic_call`, so every answer would run new code.

That is the per-platform surgery of `build/patch.rs` and `build/link.rs`, a
few thousand lines that track rustc's mangling and the platform linkers. It
is also new apparatus, which `rules/RULES.md` says needs a human's approval.

What it would save over today's `logic-dev` rebuild:

| Step | Saving per edit |
|---|---|
| Cargo's start and fingerprint checks | ~0.1–0.25 s |
| The cdylib link | 0.08–0.14 s |
| The restart with carry and re-ask | tens of ms |

The rustc work on the changed crate (0.13–0.20 s) stays. Each patch is still
a fresh dylib, so it would meet the same Gatekeeper assessment and the 64-load
cap of LLP 1029.000 §4.

**Web.** exact2's module is importless and gets a fresh instance per
replacement. Subsecond's Wasm patching needs:
- a relocatable base module with exported, growable memory and table;
- every function in the table;
- the patch instantiated against the base's exports.

Making the base module that shape costs the boot path: a larger table and no
dead-code GC in development. It also contradicts the importless,
single-instance contract that the iOS and web executors share. Wasmi's
adapter refuses imports, so iOS would need the same change inside the
interpreter.

**iOS device.** Subsecond does not support it. exact2's Wasmi path already
does.

### 3.3 What hot-patching cannot do for exact2, whatever it costs

- **It cannot skip re-asking.** LLP 1007 §6 reuses a carried answer only where
  "source name, arguments and data-module identity still match". An answer
  computed by the old function is stale by definition. A patched function
  still has to be asked again, which is exactly what restart with carry does
  now. Patching saves the restart, not the re-ask.
- **It cannot change a shape.** A data shape that Contract declares lives in
  the plan. Changing it is a Contract edit, and carry's type-conformance rule
  (slots whose value no longer fits start fresh) already handles it. Rust
  struct layout below the ABI never reaches the runner.
- **It cannot touch the host, kernel or runner.** Those are not behind a
  `HotFn`. A Rust edit there remains a new binary, as LLP 1007 §6 says ("a Rust
  edit there is a new binary"). The same holds for Dioxus, where only
  workspace crates patch and std and crates.io code never do.
- **It cannot preserve view-side state that carry drops.** Scroll, focus and
  a spring in flight do not survive (LLP 1007 §6). Dioxus keeps those only
  because its VirtualDom holds them in Rust.

  That cost belongs to exact2's tree rebuild, not to how Rust code is
  replaced. Identity matching between the old and new trees is the trade
  recorded in `rules/DEFERRED.md`.

### 3.4 Relation to the dev reload's carried state

**The two systems divide state differently:**
- **Dioxus** keeps the process and its heap and re-runs render functions. Its
  correctness rests on the framework discarding what a patch invalidated
  (hook downcasts, remounts).
- **exact2** keeps no Rust heap across a module change. Its state is the
  runner's slots, the Store, kept answers and the clock. Carry moves that
  state across a *new* instance by name and type, and invalidates answers by
  module identity.

**Consequences for exact2:**
- Durable correctness never depends on layout compatibility.
- The price is a reconstruction per edit: the module's `activate` and the
  re-asks. That is cheap for Caltrain and costs a 7 MB parse for the heavy
  list.

**If a consumer needed that heap kept,** the exact2-shaped answer is a
declared module checkpoint carried through the encoded ABI, next to slot
carry. LLP 1029.000 §4.1 deliberately has "no generic checkpoint hooks or raw
Wasm-memory copying". A checkpoint would be explicit, typed and refused on a
shape change, unlike a jump table over an old heap. No consumer asks for it
today.

## 4. Confidence

- **The numbers are single-machine runs under a load average of 39–52, with
  5–6 edits each.** They are not the 20-edit p50/p95 that LLP 1029.000 §6
  asks for. The splits come from Cargo's `--timings` and timestamped build
  output; they hold better than the totals.
- **Quoted, not measured here:**
  - Subsecond's 130 ms on an idle M4 (Kelley).
  - The iPhone figures from LLP 1029.000.
- **Inference, not tested:** two Subsecond behaviors are read from source
  without running `dx` (§2.1, §2.3):
  - statics in the recompiled crate being duplicated;
  - child components remounting.
- **Estimate:** the "0.1–0.3 s saved by function patching" in §3.2 is
  derived from the measured split.
- **Not measured: native live replacement for the outside app.** Its
  manifest disables replacement, and changing its policy would have measured
  a different app.

## 5. What would move the number, cheapest first

1. **Build the JS target's dev module with `logic-dev`.** Today it uses the
   release profile with `-Zbuild-std`: for Caltrain, the root `release`
   (thin LTO, one codegen unit); for an app without its own module, the
   generated crate's fat LTO and `opt-level=z`.
   - The native producer's `logic-dev` Wasm build of the same crate takes
     0.25–0.35 s. The JS loop's release build takes 0.9–2.0 s, and the
     outside app's link alone is 1.2–1.4 s.
   - Expected effect: about 0.6–1.5 s off every web Rust edit.
   - Not verified: that the JS runtime's `rust-data.js` accepts the larger,
     unoptimized module.
2. **Replace the module in place on the JS target.** Today a Rust-only edit
   reloads the page. It could instead instantiate the new Wasm in
   `rust-data.js`, invalidate answers by module identity, and re-ask, the way
   the wasm loop restarts a plan in ~20 ms. That removes the reload, the
   checkpoint round trip, and re-running the unchanged Contract → JS build.
3. **Build only the variants the connected clients execute, and in
   parallel.** A Mac-only session needs no Wasm build, and a web-only session
   needs no dylib. Today they build serially, 0.35–0.45 s each.

Together these would put a warm Caltrain Rust edit near 0.5–0.8 s on the web
and on native. That is inside LLP 1029.000 §6's "0.5–1 second", with no
function-level patching. Revisit Subsecond only if a consumer's module
reconstruction (`activate` plus re-asks) is the measured remainder, and §3.4's
explicit checkpoint has been ruled out.
