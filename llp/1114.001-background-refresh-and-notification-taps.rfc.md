- **Grok C1 (`periodicsync` misuses the web's name): taken.** The spec's event

## 1. Summary

Two stages and a note.

**Stage 1 (S): a tap opens a route.** `showNotification` gains `navigate=`, the
Notifications Standard's member of the same name. A tap on the notification
delivers that location the way an incoming URL is delivered today (LLP 1038 D8):
one `navigate` event on the navigation root while the app runs, or the launch
location when the tap starts it. Nothing new in the app's code: the navigation
root's existing `navigate` handler routes it.

**Stage 2 (M–L): a wake the system schedules.** A root `every` task marked
`wake` is unchanged while the app runs. On iOS and tvOS the system may also
run it while the app is suspended or not running. The host holds one
`BGAppRefreshTask` request for the app. When it fires, the host runs each due
task whose gate holds, as its own invocation, and fires no other timer. The
wake ends when those invocations' own work settles. Everything that needs a
person present is refused in a wake's commits. A `device.periodic-background-sync`
grant carries the background mode. Other hosts ignore the mark, and say so.

**APNs, briefly.** Moot for the clone: Bluesky's push service can reach only
Bluesky's own app. For an exact2 app with its own backend, push is the web's
Push API names plus stages 1 and 2's paths; it stays refused
(`rules/DEFERRED.md:435`) until such an app asks.

## 2. What Bluesky does

Bluesky registers the device's APNs token with its push service
(`app.bsky.notification.registerPush`: `serviceDid`, `token`, `platform`,
`appId`). The service sends remote pushes; a tap opens the post, profile or
thread. The app also shows an unread count on the Notifications tab and the app
icon.

The source's blocker is right. APNs routes a push by its topic, the bundle id,
and accepts it only from a provider holding a key of the team that owns that
bundle id. `push.bsky.app` holds Bluesky's keys, so it cannot reach
`dev.tuft.blueskyclone`, whatever `appId` the clone registers. The realistic
substitute is the one the source names: poll `listNotifications` and post local
notifications. That needs a tap that opens the right screen (stage 1) and,
for anything that arrives while the app is not running, a wake (stage 2).

Two corrections to the source:

- **"Badges"** are refused: `rules/DEFERRED.md:435-436` keeps "badges" on the
  still-refused list of the notifications entry. The clone's half-day estimate
  for "polling, badges and tap-to-open" assumes a capability that is not
  admitted (§6, Q4).
- **"While the app runs, this already works today"** holds on Apple and the
  web. Linux and Windows (which uses the Linux presenter,
  `host/windows/src/window.rs:1`, `:223`) refuse it as `unavailable`
  (`host/linux/src/presenter/picker.rs:100-109`, `commands.rs:43-44`). The
  terminal host drops it without a journal line
  (`host/terminal/src/host.rs:237-251`, the `_ => {}` arm).

## 4. What the web does

**A tap.** The [Notifications Standard](https://notifications.spec.whatwg.org/)
gives a notification a *navigation URL*, set by `NotificationOptions.navigate`.
When the person activates a notification that has one, the browser navigates a
top-level browsing context to it and fires no event. Without one, a page's
notification fires `click` on the `Notification` object, and a service worker's
(a persistent notification) fires `notificationclick` on the worker, whose
handler usually calls `clients.openWindow(url)` or focuses an open client. The
options also carry `data`, any serializable value, read back on click. WebKit's
Declarative Web Push uses the same `navigate` member in a push payload.

**A wake.** Every web wake runs in a service worker, never in a page:

- **[Periodic Background Sync](https://wicg.github.io/periodic-background-sync/)**:
  `registration.periodicSync.register(tag, {minInterval})`; the worker gets
  `periodicsync` with `event.tag` and extends it with `waitUntil`. The interval
  is a floor the browser may stretch (twelve hours by default); it fires only
  online, and the permission is `periodic-background-sync`. Chromium ships it,
  for installed web apps only. Safari and Firefox do not.
- **Background Sync** (`sync`, one-shot, retried when back online) and
  **Background Fetch** (large downloads) are neighbours with the same worker
  model. Nothing here needs them.
- **[Push API](https://www.w3.org/TR/push-api/)**:
  `pushManager.subscribe({userVisibleOnly: true, applicationServerKey})`
  answers a `PushSubscription` (an endpoint and keys) that the app's backend
  stores; the worker gets `push` and must show a notification. Safari supports
  it for Home Screen web apps, and Declarative Web Push shows one with no
  worker code.

exact2's web build registers no service worker (`rg serviceWorker` outside
`llp/` finds none), and the JS target's plan needs the DOM, which a worker
lacks. So on the web, stage 1 works while the page is open, and a `wake` task
is only its timer, while the page is open. The page has no name for "may run
while closed", so the mark is exact2's own word, declared as such (D2).

## 5. Design

### D1 — A tap carries a location: `navigate=` on `showNotification` (stage 1)

`showNotification(title=, body=, tag=, showTrigger=, navigate=)`. `navigate` is
a string, a location the app's routes match (a path, or a full URL that
`location_of` reduces, LLP 1038 §3). The runner's `Notice` gains the field and
`state.notifications` shows it.

On a tap, the host delivers the location through the path that already exists:

- **The app is running:** one `navigate` event on the navigation root
  (`Session.navigate`, `Session.swift:1424-1430`). The app's action chooses the
  verb, `open` for a notification, as LLP 1038 D8 already says.
- **The tap launches it:** the launch location (`Session.openURL` before boot,
  `Session.swift:1407`), journaled if no route or root hears it
  (`LaunchURL.swift:14-18`).
- **No `navigate=`:** the platform's default. The app comes forward and gets no
  event, as today.

*Options considered:*
- **(a) `navigate=`** (recommended). The web's own member, with the web's
  meaning: a location to open on activation. It reuses LLP 1038 D8's one path,
  so a tap and a link are the same thing to the app.
- **(b) A `notificationclick` event with `data`** on the root. It is closer to
  the worker model, but the app would then route by hand what the router
  already routes, and it is a new event kind and a new handler site.
- **(c) `data=` plus a `navigate` from the app's handler.** Two steps where the
  web has one.

**Per host:**

| host | where the tap arrives | what changes |
|---|---|---|
| iOS, iPadOS | `UNUserNotificationCenterDelegate.didReceive`; on a cold launch also `UIScene.ConnectionOptions.notificationResponse` | `content.userInfo["navigate"]` and the session's label; the delegate set in `didFinishLaunching`, not lazily (`Notify.swift:45`), because Apple delivers a launching tap only to a delegate set before launch ends. Before boot it is the launch location, read beside `urlContexts` (`ExactIOS/main.swift:213`); the request identifier keeps one tap from arriving twice |
| macOS | the same delegate, set in `applicationDidFinishLaunching` (`ExactMac/main.swift:440-443`) | the same |
| embedded (LLP 1031) | the same delegate, in `ExactKit` | routed to the session whose label the notice carries; one that has gone is journaled, not guessed |
| web (both targets) | `click` on the page's `Notification` | `onclick`: `preventDefault()`, `window.focus()`, then the root's `navigate` (`router.js:165`; `glue.js:1498`). The glue does **not** pass `navigate` to the constructor: a browser that honours it loads a fresh document, where a link to the app's own route is a same-document navigation (LLP 1038 D7). A declared deviation with that reason. A tap after the page has closed does nothing, as notifications posted from a page do |
| tvOS, Linux, Windows | none: notifications are refused here | nothing |
| terminal | none | journal the refusal (`host.rs:237-251` drops it silently today) |

**Grant:** none new. `device.notifications` covers the notification
(`runner/src/device.rs:93-100`); a location is not a capability.

**Compatibility:** a fifth argument changes no digest the classifier reads.
The plan's `Command` op is a name and an argument count
(`plan/tables/format.json:923`), so `FORMAT_DIGEST` does not move;
`compat.rs` hashes `formatDigest` and `kernelSchema`, not the compiler
identity (`bake/src/compat.rs:326-328`); and the runner checks only the kernel
schema (`runner/src/runner.rs:669`). An over-the-air plan using `navigate=`
would reach a runner that refuses five arguments (`notify.rs:67`), and the
notification would not post. So the compatibility id gains `commands`: a
digest of each host command's name and argument count (`HOST_COMMANDS`,
`contract/syntax/src/lib.rs:83`, and the lowering's fixed orders,
`expr.rs:57`). A changed command shape is then a binary change. Landing it
moves every app's id once.

**The agent** (LLP 1069.007 D7's Substitute paragraph): a notification is
listed, never posted, so there is nothing to tap. Each entry of
`state.notifications` gains `"navigate"`. A drive asserts it, then delivers it
the way 1069.007 D6 already does, `type <navigation root> "/notifications"`,
and checks the screen. A launching tap is `EXACT_LAUNCH_URL`, which the driver
already passes (`scripts/agent.mjs:622`; `ExactIOS/main.swift:215`). No new
operation. A person checks the real delegate once on a simulator.

### D2 — A task marked `wake` may also run when the system wakes the app (stage 2)

```contract
  task inbox when signedIn wake
    every(900000, checkInbox)
```

`wake` follows a task's trigger, `mount` or a gate (`task = "task" IDENT
( "mount" | gate ) [ "wake" ] block(schedule)`, beside
`docs/contract-grammar.md:190`). While the app runs, the task is exactly what
it is without the mark: an `every` timer, armed and dropped by its gate as LLP
1092 D8 says. The mark adds one thing: on iOS and tvOS, the system may run the
task's action while the app is suspended or not running. Only `every` takes
it, with a literal of at least 900000 (fifteen minutes); less is refused
(`type-task-wake-interval`), so a wake cannot become a poll loop in disguise.
`after` and `frame` are refused with `wake`. The interval is a floor, never a
promise.

*Options considered:*
- **(a) A mark on an existing task** (recommended). The page has no web name
  for this: Periodic Background Sync's `periodicsync` is a service-worker
  event on the browser's schedule, not a page timer, and a grammar word here
  is permanent (`rules/RULES.md`: delete, don't deprecate). A mark keeps
  `mount` and `when` as they are, and on hosts with no wake it means nothing,
  which D5 declares.
- **(b) r1's trigger, `task inbox periodicsync`.** It took the worker event's
  name for a page timer, and it duplicated what `every` already does while the
  app runs. Withdrawn (§0, Grok C1). The name stays free for a worker-hosted
  runner, if one ever exists.
- **(c) A command, `registerPeriodicSync(tag, minInterval)`**, as the web
  registers. The build needs the grant at build time and the plan must say
  which tasks may run unattended; a run-time call says neither.
- **(d) A data-module export the host calls with no plan.** No layout in the
  background, so cheaper. But it posts a notification from a source, a second
  effect path; a source returns values and an action applies them (LLP 1038
  D9's rule for navigation; commands are actions'). And the module would need
  the notification capability.

The action reads `exactPage().visibilityState` (`hidden` in a wake) to choose a
system notification over an in-window one, which the docs already teach for
`hasFocus` (`docs/contract-for-agents.md:1395-1398`).

### D3 — One request per app; what a wake runs, and when it is done

**One request.** Apple allows one pending refresh request per app
(`BGTaskScheduler.submit(_:)`: "a total of 1 refresh task and 10 processing
tasks scheduled at any time"; more throws `tooManyPendingTaskRequests`). So
the build writes one identifier, `<bundle id>.refresh`, into
`BGTaskSchedulerPermittedIdentifiers`. The app delegate registers its handler
in `didFinishLaunching`, as Apple requires. On entering the background, and at
the end of each wake, the host submits one `BGAppRefreshTaskRequest` whose
`earliestBeginDate` is the earliest due time among the `wake` tasks and
delivery's check (D5). A submit replaces the pending request. Each task's last
run is kept in the app's store, beside kept answers, so a cold wake knows what
is due.

**What runs.** During a wake the runner fires no timer: no `mount` task, no
gated task, and not the `wake` tasks' own timers. The host instead dispatches
each `wake` task that is due (never run, or last run at least its interval
ago) and whose gate holds. Each dispatch is its own invocation with LLP 1113
D4's owner set, as a tool call's is. A gate is read where LLP 1092 D8 reads
it, after the commit's settlement.

- **Cold** (iOS, tvOS): the system launches the process with no scene. The
  handler boots the session with no view at the last screen size (the
  `EXACT_PLAN` path, `ExactIOS/main.swift:239-241`). Kept answers seed the
  boot (LLP 1027 D4), so a gate on a kept `session` reads the signed-in state,
  not a placeholder. The host dispatches when the data module is ready, as
  1113 D4 requires.
- **Warm** (suspended): the same dispatch into the live session.

**Done** is every dispatched invocation complete (its owned set empty) and no
LLP 1097 background ticket left (`StorageHold.swift:13-18`'s count), because
1113 D4 cannot attribute background work to an owner. Work the wake did not
start neither holds it open nor is touched by it: the boot's re-asked
resources (`kept.rs:179-195`), a person's unfinished requests in a warm
session. Then `setTaskCompleted(success: true)`, the last runs are stored, and
the next request is submitted.

**Expiry.** If the system's expiration handler fires first, the host cancels
the requests the wake's invocations own that are still in flight (each answers
as a network failure would), calls `setTaskCompleted(success: false)`, and
journals `wake inbox: expired`. A storage write the module already began lands
or not as at any suspension; LLP 1097 D10 promises no more. The app should
move its cursor only after the notification is posted, so an interrupted wake
at worst re-reads (§7).

**A scene arriving mid-wake.** A later scene's view fits the booted session
(`ExactViewIOS.swift:330-341`). The person's own commits are theirs: nothing
D4 refuses applies to them. The wake's invocations keep D4's refusals and run
to completion or expiry. Timers resume when the scene becomes active.

### D4 — Nothing that needs a person runs in a wake

The predecessor argued that every capability-bearing OS callback fails closed
until an installed-service principal exists
(`llp/research/0552-exact-after-the-window.explainer.md:111`; research, not
authority). exact2 has no per-session principal to mint: an app's authority is
its grants, pinned in the binary (LLP 1069.008). A wake runs the app's own
action under those grants and reaches nothing the app could not reach in
front. What fails closed is anything that needs a person:

- Refused in a commit the wake owns, into the journal (`<command>: refused:
  during a wake`): `share`, the pickers, `saveFile`, `openURL`,
  `openAuthSession`, `copyText`, `playSound`, and any permission request.
- `showNotification` posts only if authorization is already granted
  (`getNotificationSettings`); otherwise `refused: not yet allowed`, never a
  prompt nobody can see. The app asks from a press while in front, as the web
  glue already requires (`notify-glue.js:3-4`).
- **Protected data first.** The Keychain snapshot is read before the runner
  boots (`host/apple/src/store.rs:1-6`). A wake before the first unlock, when
  protected data is unavailable, ends at once without booting, so it can never
  boot as if signed out.

Network and storage run under the existing grants.

**Grant: `device.periodic-background-sync`**, the Permissions Registry's name
for this reach. A background mode is reach an update cannot add, and LLP
1069.008 D4 ruled that background modes become `device.*` rows in D2's table.
The row has no purpose string. It contributes `fetch` to `UIBackgroundModes`
and the one identifier to `BGTaskSchedulerPermittedIdentifiers` on iOS and
tvOS, and nothing on macOS. Its web column is none: on the web the permission
belongs to a service worker this build does not register. The row needs a
background-mode field in `Device` (`runner/src/device.rs:20`), the column
1069.008 D4 anticipated. A `wake` task without the grant is refused at build
(`type-task-wake-grant`). The task line alone never turns the mode on.

### D5 — Per host

| host | while the app runs | suspended or not running |
|---|---|---|
| iOS, iPadOS | the task's timer | the app's one `BGAppRefreshTask`; opportunistic, about 30 s, often hours apart; not after the person force-quits the app, in Low Power Mode, or with Background App Refresh off |
| tvOS | the timer | the same (tvOS 13+); notifications stay refused (`Notify.swift:30-31`), so a wake refreshes data only |
| macOS | the timer (App Nap may stretch it; the floor allows that) | nothing: a quit app has no wake. Declared |
| web | the timer, while the page is open (a hidden tab's timers are throttled) | nothing: no service worker, and the plan needs the DOM. Declared; Chromium's Periodic Background Sync would need a worker-hosted runner, out of scope |
| Linux, Windows | the timer | nothing (systemd timers, or Windows' background tasks for packaged apps, launch a process: out of scope) |
| terminal | the timer | nothing |

This is not a job scheduler (`DEFERRED.md:55`, `:119-120`): one OS request,
run by the OS's scheduler, no queue, no pool, no retries.

**Compatibility.** The identifier is fixed per binary, so a bundle that adds or
renames a `wake` task changes no `Info.plist` and can ship over the air to a
binary that has the grant. Adding the grant is binary: `device.*` lines are in
`grantCeiling`, and a bundle whose grants a binary does not contain fails the
classifier's containment check (LLP 1069.008 D5). No `compat.rs` field is
needed beyond that.

**Delivery shares the request.** Delivery's owed check (1030.003, `:253-256`)
is host work, not a Contract task. It uses the same identifier, handler and
pending request, and runs beside the app's tasks in the same window; its due
time joins `earliestBeginDate`. How the binary declares `fetch` for delivery
alone is 1030.003's to say. The two share one budget, which is a cost, not a
saving.

### D6 — The agent's view

- **While running:** a `wake` task is a timer on the agent's clock.
  `clock +900000` runs it; `clock settle` treats it as any timer. The
  notification it posts is in `state.notifications`, with its `navigate`. That
  covers the app's logic on every host.
- **Under the agent, the wake's refusals hold** when the drive runs it as a
  wake (below), so a test sees `share: refused: during a wake`.
- **Cold:** LLP 1069.007 keeps cold-start and background delivery out until a
  rule (`:460-464`, `:543-547`). The rule proposed here: a development build
  honours `EXACT_WAKE=<task>`, launching through the same headless boot and
  handler as a cold wake (no scene, `visibilityState` `hidden`, the task taken
  as due), and the driver passes it as `--wake <task>`. The journal says
  `wake inbox: ran` and `completed` or `expired`; `state.wake` shows the
  outcome. That is new apparatus, so it is Q3.
- **The real system:** the simulator never runs `BGTaskScheduler` work on its
  own. A person checks it once in Xcode's debugger
  (`_simulateLaunchForTaskWithIdentifier:`) and on a real iPhone. No smoke
  depends on it.

### D7 — APNs, briefly

For the clone, moot (§2). For an exact2 app with its own backend, push would
take four pieces, each on a path above:

1. A `device.push` grant row (the Permissions Registry's `push`) carrying
   `ios_entitlements: ["aps-environment"]`. LLP 1069.008 anticipates exactly
   this (`llp/1069.008-permissions-from-grants.rfc.md:127`, `:190-192`).
2. A subscribe request by the web's name, `pushManager.subscribe`, answering a
   subscription the app sends to its backend: an endpoint and keys on the web,
   the APNs device token on Apple. A request held for the agent like the
   others (LLP 1069.007 D3).
3. A visible push shows without app code; its tap is stage 1 (the payload's
   `navigate`, Declarative Web Push's member).
4. A silent push (`content-available`) is a wake, stage 2's path, as the web's
   `push` event.

exact2 sends no pushes and relays none (LLP 1030.000 D6), and
`DEFERRED.md:435` refuses "push delivery from a server". Moving it needs an app
with a backend that asks; the clone is not one.

## 6. Questions for Charlie

- **Q1. Admit stage 1 under the existing notifications entry?** It is LLP
  1069 §5 #9's own design ("a tap arriving as a `navigate` event") and LLP 1038
  D8's, and refusing "actions and replies" does not cover a notification's
  default activation. Both reviewers agree. *Recommended:* yes, as a widening
  of the 2026-10-04 entry, no take.
- **Q2. Admit the wake (stage 2), with the Bluesky clone as consumer?** It moves
  LLP 1069's "Not now" background tasks. Grok: admit only in r2's shape (one
  gated action, its own work ends the wake, a grant owns `fetch`). Astra:
  admit conditionally, after the scheduling and lifetime are settled, and only
  if opportunistic alerts are worth the cost; Apple's engineers warn against
  expecting regular fifteen-minute runs, so alerts may come hours late or not
  at all. *Recommended:* yes, in r2's shape, built after LLP 1113 D4's owner
  set lands (stage 2 builds on it), and the clone tells its users that
  background alerts are best-effort. No take offered: r1's (delivery riding
  the same registration) is not one, since the two share a budget (Grok).
- **Q3. `EXACT_WAKE` and the driver's `--wake`?** New apparatus, so it needs

  the same headless boot, which D6 now says. *Recommended:* yes; without it a

- **Q4. Badges?** The clone's estimate includes them; `DEFERRED.md:436` refuses

- **Q5. APNs stays refused?** Astra asks whether timely alerts should send the

  push stays refused; stage 2 is a catch-up, and D7 is the path when the clone

- **Q6. Background modes as `device.*` rows, now?** LLP 1069.008 Q3 ruled they

## 7. What the clone does after

- **Stage 1:** each local notification carries `navigate=` (the thread, the
  profile, or `/notifications`). Verified by a drive that asserts
  `state.notifications[0].navigate`, types it into the root, and screenshots
  the thread; and by `EXACT_LAUNCH_URL` for the cold case. Ask for
  notification permission from a settings switch, inside the press.
- **Polling in front:** a gated task it can write today
  (`task poll when signedIn` with `every(60000, checkInbox)`), posting only
  when `visibilityState` is `hidden` or the window lacks focus.
- **Stage 2:** the grant line, and `task inbox when signedIn wake` with
  `every(900000, checkInbox)`, `signedIn` derived from a kept `session`. The
  data module answers only what is new since the cursor in its own storage;
  the action's `then` posts one notification with tag `inbox` (so a newer one
  replaces it) and `navigate="/notifications"`, then moves the cursor.
  Verified with `clock +900000` and `state.notifications`; cold with
  `--wake inbox` if Q3 is yes; once on a real iPhone by hand.

Clone work: about half a day, without badges.

## 8. Effort and complexity

**exact2, stage 1: S, about a day.** A fifth argument through the checker,
lowering and `Notice` (`notify.rs`), with tests beside
`contract/cli/tests/it/notify.rs`; the compatibility id's `commands` digest;
the delegate's `didReceive` and the launch-time assignment in both adapters
and `ExactKit`; `notificationResponse` before boot; two web `onclick`s; the
terminal's journal line. The hard part is small: Apple's delivery order on a
cold launch (delegate, scene options, boot) and keeping one tap from arriving
twice.

**exact2, stage 2: M–L, about a week, after LLP 1113 D4.** Easy: the `wake`
mark, the plan's bit, the grant row and its background-mode field, the one
identifier, the last-run record. Hard:
- the headless boot on iOS: the session, the module and the Keychain snapshot
  with no scene, and a later scene attaching to it;
- the wake's dispatch on 1113 D4's owner set, with no timers firing, and its
  completion, expiry and cancellation;
- the during-a-wake refusals in every command arm;
- testing: the system decides when a wake runs, the simulator never runs one,
  and a person checks the real thing by hand.

If 1113 D4 has not landed, stage 2 builds its owner set first, which is its
own work, sized there.

**Clone:** about half a day after both stages (§7).

## 9. Not in scope

- Remote push (D7), badges (Q4), notification actions and replies, repeating
  notification schedules: all still refused (`DEFERRED.md:435-436`).
- A service worker on the web, and Periodic Background Sync or Background Sync
  through one.
- `BGProcessingTask` (long work on power), background `URLSession` transfers,
  background location.
- An OS identifier per task.
- A wake on macOS, Linux or Windows for an app that is not running.
- Android (no host).
