## 1. Summary

Two stages and a note.

**Stage 1 (S): a tap opens a route.** `showNotification` gains `navigate=`, the
Notifications Standard's member of the same name. A tap on the notification
delivers that location the way an incoming URL is delivered today (LLP 1038 D8):
one `navigate` event on the navigation root while the app runs, or the launch
location when the tap starts it. Nothing new in the app's code: the navigation
root's existing `navigate` handler routes it.

**Stage 2 (M–L): a wake the system schedules.** A root task with the trigger
word `periodicsync` and one `every(minInterval, action)`. While the app runs it
is a timer. When the app is suspended or not running, iOS and tvOS wake it with
a `BGAppRefreshTask`; the host boots the app with no window, runs the action,
and tells the system it is done when the runner is quiet. Everything that needs
a person present is refused during a wake. Other hosts run it only while the
app runs, and say so.

**APNs, briefly.** Moot for the clone: Bluesky's push service can reach only
Bluesky's own app. For an exact2 app with its own backend, push is the web's
Push API names plus stages 1 and 2's paths; it stays refused
(`rules/DEFERRED.md:435`) until such an app asks.

## 2. What Bluesky does

Bluesky registers the device's APNs token with its push service
(`app.bsky.notification.registerPush`: `serviceDid`, `token`, `platform`,
`appId`). The service sends remote pushes; a tap opens the post, profile or
thread. The app also shows an unread count on the Notifications tab and the app
icon.

The source's blocker is right. APNs routes a push by its topic, the bundle id,
and accepts it only from a provider holding a key of the team that owns that
bundle id. `push.bsky.app` holds Bluesky's keys, so it cannot reach
`dev.tuft.blueskyclone`, whatever `appId` the clone registers. The realistic
substitute is the one the source names: poll `listNotifications` and post local
notifications. That needs a tap that opens the right screen (stage 1) and,
for anything that arrives while the app is not running, a wake (stage 2).

Two corrections to the source:

- **"Badges"** are refused: `rules/DEFERRED.md:435-436` keeps "badges" on the
  still-refused list of the notifications entry. The clone's half-day estimate
  for "polling, badges and tap-to-open" assumes a capability that is not
  admitted (§6, Q4).
- **"While the app runs, this already works today"** holds on Apple and the
  web. Linux and Windows (which uses the Linux presenter,
  `host/windows/src/window.rs:1`, `:223`) refuse it as `unavailable`
  (`host/linux/src/presenter/picker.rs:100-109`, `commands.rs:43-44`). The
  terminal host drops it without a journal line
  (`host/terminal/src/host.rs:237-251`, the `_ => {}` arm).

## 4. What the web does

**A tap.** The [Notifications Standard](https://notifications.spec.whatwg.org/)
gives a notification a *navigation URL*, set by `NotificationOptions.navigate`.
When the person activates a notification that has one, the browser navigates a
top-level browsing context to it and fires no event. Without one, a page's
notification fires `click` on the `Notification` object, and a service worker's
(a persistent notification) fires `notificationclick` on the worker, whose
handler usually calls `clients.openWindow(url)` or focuses an open client. The
options also carry `data`, any serializable value, read back on click. WebKit's
Declarative Web Push uses the same `navigate` member in a push payload.

**A wake.** Every web wake runs in a service worker, never in a page:

- **[Periodic Background Sync](https://wicg.github.io/periodic-background-sync/)**:
  `registration.periodicSync.register(tag, {minInterval})`; the worker gets
  `periodicsync` with `event.tag` and extends it with `waitUntil`. The interval
  is a floor the browser may stretch (twelve hours by default); it fires only
  online, and the permission is `periodic-background-sync`. Chromium ships it,
  for installed web apps only. Safari and Firefox do not.
- **Background Sync** (`sync`, one-shot, retried when back online) and
  **Background Fetch** (large downloads) are neighbours with the same worker
  model. Nothing here needs them.
- **[Push API](https://www.w3.org/TR/push-api/)**:
  `pushManager.subscribe({userVisibleOnly: true, applicationServerKey})`
  answers a `PushSubscription` (an endpoint and keys) that the app's backend
  stores; the worker gets `push` and must show a notification. Safari supports
  it for Home Screen web apps, and Declarative Web Push shows one with no
  worker code.

exact2's web build registers no service worker (`rg serviceWorker` outside
`llp/` finds none), and the JS target's plan needs the DOM, which a worker
lacks. So on the web, stage 1 works while the page is open, and stage 2 runs
only while the page is open.

## 5. Design

### D1 — A tap carries a location: `navigate=` on `showNotification` (stage 1)

`showNotification(title=, body=, tag=, showTrigger=, navigate=)`. `navigate` is
a string, a location the app's routes match (a path, or a full URL that
`location_of` reduces, LLP 1038 §3). The runner's `Notice` gains the field and
`state.notifications` shows it.

On a tap, the host delivers the location through the path that already exists:

- **The app is running:** one `navigate` event on the navigation root
  (`Session.navigate`, `Session.swift:1424-1430`). The app's action chooses the
  verb, `open` for a notification, as LLP 1038 D8 already says.
- **The tap launches it:** the launch location (`Session.openURL` before boot,
  `Session.swift:1407`), journaled if no route or root hears it
  (`LaunchURL.swift:14-18`).
- **No `navigate=`:** the platform's default. The app comes forward and gets no
  event, as today.

*Options considered:*
- **(a) `navigate=`** (recommended). The web's own member, with the web's
  meaning: a location to open on activation. It reuses LLP 1038 D8's one path,
  so a tap and a link are the same thing to the app.
- **(b) A `notificationclick` event with `data`** on the root. It is closer to
  the worker model, but the app would then route by hand what the router
  already routes, and it is a new event kind and a new handler site.
- **(c) `data=` plus a `navigate` from the app's handler.** Two steps where the
  web has one.

**Per host:**

| host | where the tap arrives | what changes |
|---|---|---|
| iOS, iPadOS | `UNUserNotificationCenterDelegate.didReceive`; on a cold launch also `UIScene.ConnectionOptions.notificationResponse` | `content.userInfo["navigate"]` and the session's label; the delegate set in `didFinishLaunching`, not lazily (`Notify.swift:45`), because Apple delivers a launching tap only to a delegate set before launch ends. Before boot it is the launch location, read beside `urlContexts` (`ExactIOS/main.swift:213`); the request identifier keeps one tap from arriving twice |
| macOS | the same delegate, set in `applicationDidFinishLaunching` (`ExactMac/main.swift:440-443`) | the same |
| embedded (LLP 1031) | the same delegate, in `ExactKit` | routed to the session whose label the notice carries; one that has gone is journaled, not guessed |
| web (both targets) | `click` on the page's `Notification` | `onclick`: `preventDefault()`, `window.focus()`, then the root's `navigate` (`router.js:165`; `glue.js:1498`). The glue does **not** pass `navigate` to the constructor: a browser that honours it loads a fresh document, where a link to the app's own route is a same-document navigation (LLP 1038 D7). A declared deviation with that reason. A tap after the page has closed does nothing, as notifications posted from a page do |
| tvOS, Linux, Windows | none: notifications are refused here | nothing |
| terminal | none | journal the refusal (`host.rs:237-251` drops it silently today) |

**Grant:** none new. `device.notifications` covers the notification
(`runner/src/device.rs:93-100`); a location is not a capability.

**Compatibility:** a fifth argument is a compiler change, so a bundle using it
needs a binary whose runner reads five (`notify.rs:67`). The plan's header
carries the compiler's identity (`plan/tables/format.json:3`), which the
classifier already treats as binary.

**The agent** (LLP 1069.007 D7's Substitute paragraph): a notification is
listed, never posted, so there is nothing to tap. Each entry of
`state.notifications` gains `"navigate"`. A drive asserts it, then delivers it
the way 1069.007 D6 already does, `type <navigation root> "/notifications"`,
and checks the screen. A launching tap is `EXACT_LAUNCH_URL`, which the driver
already passes (`scripts/agent.mjs:622`; `ExactIOS/main.swift:215`). No new
operation. A person checks the real delegate once on a simulator.

### D2 — A wake is a root task with the trigger `periodicsync` (stage 2)

```contract
  task inbox periodicsync
    every(900000, checkInbox)
```

`periodicsync` is a trigger beside `mount` and `when`
(`docs/contract-grammar.md:190`). The body is one `every(ms, action)`, with `ms`
the web's `minInterval`: a floor, never a promise. A literal of at least
900000 (fifteen minutes); less is refused (`type-periodicsync-interval`), so a
wake cannot become a poll loop in disguise. `after` and `frame` are refused.
The task name is the web's `tag`.

*Options considered:*
- **(a) A declared task** (recommended). iOS needs every identifier in
  `Info.plist` at build time (`BGTaskSchedulerPermittedIdentifiers`), so the
  set must be static, and a declaration in the plan is static. The build
  derives the identifiers (`<bundle id>.periodicsync.<name>`) and the `fetch`
  mode, as it derives the media session's requirements from the build graph
  (`build.mjs:974-975`). Nothing to keep in step in `app.json`.
- **(b) A command, `registerPeriodicSync(tag, minInterval)`**, as the web
  registers. Run-time names cannot be in a build-time `Info.plist`, so the
  names would also have to be declared in `app.json`: two declarations of one
  thing.
- **(c) A data-module export the host calls with no plan.** No layout in the
  background, so cheaper. But it posts a notification from a source, a second
  effect path; a source returns values and an action applies them (LLP 1038
  D9's rule for navigation; commands are actions'). And the module would need
  the notification capability.

**What it means:** one schedule per task, the last run plus `minInterval`.
While the app runs, the runner fires it as a timer at that time, whether or
not the window is in front, as the web's fires whether or not a page is open.
When the app is suspended or not running, the system may wake it at or after
that time; on iOS the host submits a `BGAppRefreshTaskRequest` with that
`earliestBeginDate` on entering the background and after each run. The action
reads `exactPage().visibilityState` (`hidden` in a wake) to choose a system
notification over an in-window one, which the docs already teach for
`hasFocus` (`docs/contract-for-agents.md:1395-1398`).

No `when` gate in v1. A cold wake boots with initial state, so a gate on state
would read its initial value; the module knows whether anyone is signed in.

### D3 — What a wake runs, and when it is done

**Cold** (iOS, tvOS): the system launches the process with no scene. The app
delegate registers a handler for each identifier in `didFinishLaunching`, as
Apple requires. The handler boots the session with no view at the last screen
size (the `EXACT_PLAN` path, `ExactIOS/main.swift:239-241`; a later scene's view
fits the booted session, `ExactViewIOS.swift:330-341`), waits for the data
module to be ready, and dispatches the task's action. **Warm** (suspended): the
same dispatch into the live session.

**Done** is the runner quiet: no request in flight, no `then` or queue entry
waiting, no LLP 1097 background ticket, no storage operation
(`StorageHold.swift:13-18`'s count), and the commands it emitted delivered.
Open streams (LLP 1016.000) and timers do not count; a wake does not wait for
them. LLP 1113 D4 needs an owner set because a person's own work would
otherwise count; in a wake no person is acting, so the whole runner's work is
the wake's, and this needs nothing from 1113. Then `setTaskCompleted(success:
true)` and the next request is submitted. If the system's expiration handler
fires first: `setTaskCompleted(success: false)`, journal
`periodicsync inbox: expired`, and what the store already has lands regardless
(LLP 1097 D10's hold covers the rest).

### D4 — Nothing that needs a person runs in a wake

The predecessor argued that every capability-bearing OS callback fails closed
until an installed-service principal exists
(`llp/research/0552-exact-after-the-window.explainer.md:111`; research, not
authority). exact2 has no per-session principal to mint: an app's authority is
its grants, pinned in the binary (LLP 1069.008). A wake runs the app's own
action under those grants and reaches nothing the app could not reach in
front. What fails closed is anything that needs a person:

- Refused during a wake, into the journal (`<command>: refused: during a
  wake`): `share`, the pickers, `saveFile`, `openURL`, `openAuthSession`,
  `copyText`, `playSound`, and any permission request.
- `showNotification` posts only if authorization is already granted
  (`getNotificationSettings`); otherwise `refused: not yet allowed`, never a
  prompt nobody can see. The app asks from a press while in front, as the web
  glue already requires (`notify-glue.js:3-4`).
- **Protected data first.** The Keychain snapshot is read before the runner
  boots (`host/apple/src/store.rs:1-6`). A wake before the first unlock, when
  protected data is unavailable, ends at once without booting, so it can never
  boot as if signed out.

Network and storage run under the existing grants. **Grant:** none new. A
`device.periodic-background-sync` row would be the web's permission name, but
the row table holds purpose strings and entitlements
(`runner/src/device.rs:60`), and a wake touches no device. The declaration is
the task line, which the build reads.

### D5 — Per host

| host | while the app runs | suspended or not running |
|---|---|---|
| iOS, iPadOS | the runner's timer | `BGAppRefreshTask`; opportunistic, about 30 s; not after the person force-quits the app, in Low Power Mode, or with Background App Refresh off |
| tvOS | the timer | `BGAppRefreshTask` (tvOS 13+); notifications stay refused (`Notify.swift:30-31`), so a wake refreshes data only |
| macOS | the timer (App Nap may stretch it; the floor allows that) | nothing: a quit app has no wake. Declared |
| web | the timer, while the page is open (a hidden tab's timers are throttled) | nothing: no service worker, and the plan needs the DOM. Declared; Chromium's Periodic Background Sync would need a worker-hosted runner, out of scope |
| Linux, Windows | the timer | nothing (systemd timers, or Windows' background tasks for packaged apps, launch a process: out of scope) |
| terminal | the timer | nothing |

This is not a job scheduler (`DEFERRED.md:55`, `:119-120`): one wake per
declared task, run by the OS's scheduler, no queue, no pool, no retries.

**Compatibility.** The identifiers are binary metadata: a bundle cannot add one
(LLP 1030 D5, `llp/1030-delivery-unified.rfc.md:481-484`). `compat.rs`'s
`capabilities` gains `periodicSync: [names]` beside `backgroundModes`
(`:360`), so a bundle that adds or renames a task is classified binary. A plan
whose task the binary does not list runs it as a timer only and journals
`periodicsync <name>: no system wake in this binary`.

**One mechanism for delivery too.** Delivery's owed background check
(1030.003, `:253-256`) is the host's own wake on the same registration code,
not a second implementation.

### D6 — The agent's view

- **While running:** a `periodicsync` task is a timer on the agent's clock.
  `clock +900000` runs it; `clock settle` treats it as any timer. The journal
  says `periodicsync inbox: ran` and `completed` or `expired`. The
  notification it posts is in `state.notifications`, with its `navigate`. That
  covers the app's logic on every host.
- **Under the agent, the wake's refusals hold** when the drive marks it a wake
  (below), so a test sees `share: refused: during a wake`.
- **Cold:** LLP 1069.007 keeps cold-start and background delivery out until a
  rule (`:460-464`, `:543-547`). The rule proposed here: a development build
  honours `EXACT_WAKE=<task>`, launching as a cold wake does (no scene, the same
  handler, `visibilityState` `hidden`), and the driver passes it as
  `--wake <task>`. `state.wake` shows the outcome. That is new apparatus, so
  it is Q3.
- **The real system:** the simulator never runs `BGTaskScheduler` work on its
  own. A person checks it once in Xcode's debugger
  (`_simulateLaunchForTaskWithIdentifier:`) and on a real iPhone. No smoke
  depends on it.

### D7 — APNs, briefly

For the clone, moot (§2). For an exact2 app with its own backend, push would
take four pieces, each on a path above:

1. A `device.push` grant row (the Permissions Registry's `push`) carrying
   `ios_entitlements: ["aps-environment"]`. LLP 1069.008 anticipates exactly
   this (`llp/1069.008-permissions-from-grants.rfc.md:127`, `:190-192`).
2. A subscribe request by the web's name, `pushManager.subscribe`, answering a
   subscription the app sends to its backend: an endpoint and keys on the web,
   the APNs device token on Apple. A request held for the agent like the
   others (LLP 1069.007 D3).
3. A visible push shows without app code; its tap is stage 1 (the payload's
   `navigate`, Declarative Web Push's member).
4. A silent push (`content-available`) is a wake, stage 2's path, as the web's
   `push` event.

exact2 sends no pushes and relays none (LLP 1030.000 D6), and
`DEFERRED.md:435` refuses "push delivery from a server". Moving it needs an app
with a backend that asks; the clone is not one.

## 7. What the clone does after

- **Stage 1:** each local notification carries `navigate=` (the thread, the
  profile, or `/notifications`). Verified by a drive that asserts
  `state.notifications[0].navigate`, types it into the root, and screenshots
  the thread; and by `EXACT_LAUNCH_URL` for the cold case. Ask for
  notification permission from a settings switch, inside the press.
- **Polling in front:** a gated task it can write today
  (`task poll when signedIn` with `every(60000, checkInbox)`), posting only
  when `visibilityState` is `hidden` or the window lacks focus.
- **Stage 2:** `task inbox periodicsync` with `every(900000, checkInbox)`. The
  data module keeps the last-seen cursor in its own storage and answers only
  what is new; the action's `then` posts one notification with tag `inbox`
  (so a newer one replaces it) and `navigate="/notifications"`. Verified with
  `clock +900000` and `state.notifications`; cold with `--wake inbox` if Q3 is
  yes; once on a real iPhone by hand.

Clone work: about half a day, without badges.

## 8. Effort and complexity

**exact2, stage 1: S, about a day.** A fifth argument through the checker,
lowering and `Notice` (`notify.rs`), with tests beside
`contract/cli/tests/it/notify.rs`; the delegate's `didReceive` and the
launch-time assignment in both adapters and `ExactKit`; `notificationResponse`
before boot; two web `onclick`s; the terminal's journal line. The hard part is
small: Apple's delivery order on a cold launch (delegate, scene options, boot)
and keeping one tap from arriving twice.

**exact2, stage 2: M–L, about a week.** Easy: the grammar word, the plan kind,
the runner treating it as an `every`, the Info.plist derivation and the compat
field. Hard:
- the headless boot on iOS: the session, the module and the Keychain snapshot
  with no scene, and a later scene attaching to it;
- the quiet check that ends the wake, and the expiration path;
- the during-a-wake refusals in every command arm;
- testing: the system decides when a wake runs, the simulator never runs one,
  and a person checks the real thing by hand.

**Clone:** about half a day after both stages (§7).
