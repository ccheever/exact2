# LLP 1046.006.000: Render hooks — a game's own passes in the engine's frame

**Type:** RFC
**Status:** Implemented, 2026-09-23, by Codex for Charlie. All four rulings in §7 are accepted. H1–H5 and the private consumer migration have code and tests; web, native Metal and iOS simulator evidence and remaining verification are in §8. Not linked into `llp/current/`.
**Systems:** `game/render` (`Renderer`, `WorldSurface`, `module!`); `gpu/` (the `Registry`); the app bake's shader roots
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-23
**Related:** LLP 1046.006 (the findings this answers: R1–R6, W1–W5, §5), 1046.003 (as built), 1046.005 (C5 draw-instance records); LLP 1009 (D2 optional module, D5 shaders at first use); LLP 1030 D8 (shaders as assets, interface digests); `CLAUDE.md` ("optional capability is a separate artifact … never a cargo feature")

## Summary

Let a game add **named stages** to the engine's frame, instead of replacing the
frame. A game supplies one `Hooks` type. The engine calls it at fixed points in
the frame, where it can encode compute, draw inside the forward pass with its
own pipelines, read a resolved copy of the scene, and post-process before the
tone curve. The engine hands it the frame's camera, sun and time as data, and
owns everything else: clock, feed, interpolation, shadows, models, particles,
bloom, readiness and perf. The default `()` retains the existing path without
extra render passes or resources. The engine gains **mechanism only**; the shading a
game brings stays in the game (1046.006 §5).

The acceptance test is concrete: Weird Waters moves onto hooks and deletes its
second renderer (1046.006 W1), after custom materials land. The ocean stays in
the deck; the seabed, castle, kelp, fish and boats use engine drawing. Public
fixtures prove the mechanism independently of the private deck. Existing games'
simulation pins must not move. Adding saved render entities/components to Weird
Waters changes its full-world hash: preserve gameplay observations, review that
structural change explicitly and establish new cross-host pins. Running hooks
against an otherwise identical world must never change its hash or save.

## D1. The shape: a type parameter, like `Presentation`

`WorldSurface<G, P = (), const ASSETS: bool = false, H = ()>`, with
`exact_game_render::module!(MyGame, hooks = MyHooks)` in the shell. `H:
Hooks + Default`. Every method has a default that does nothing, and `impl
Hooks for ()` sets `ENABLED = false`. A hookless game must retain its existing render path,
allocations and pass count, with no retained hook shaders; compare release size
against the same-toolchain baseline in `game/bench/README.md`. Literal binary
identity is not a useful promise across a Rust refactor. No cargo feature or
core engine dependency; D5 separately changes shared packaging tools.

Abbreviated API; callbacks return `Result<(), RenderError>` in the implementation:

```rust
pub trait Hooks: Default {
    /// After the frame's feed, before encoding: allocate or resize resources,
    /// write uniforms. RenderWorld exposes read-only extraction, not &World.
    fn prepare(&mut self, gpu: &HookGpu, view: &FrameView, world: &RenderWorld) {}
    /// Before the shadow passes: the game's compute (and any offscreen passes).
    fn compute(&mut self, encoder: &mut wgpu::CommandEncoder, view: &FrameView) {}
    /// Inside the forward pass, after opaque batches/quads, before the sky.
    fn opaque(&mut self, pass: &mut wgpu::RenderPass<'_>, view: &FrameView) {}
    /// In an engine-owned continuation pass, with the opaque scene snapshot.
    fn surface(&mut self, pass: &mut wgpu::RenderPass<'_>, scene: &SceneCopy, view: &FrameView) {}
    /// After surface + translucency, BEFORE bloom and tone (D3).
    fn post(&mut self, encoder: &mut wgpu::CommandEncoder, inputs: &PostInputs, view: &FrameView) {}
    /// Services and frame demand; read once after prepare, before encoding.
    fn needs(&self) -> Needs { Needs::NONE }
}
```

Hooks must never write the simulation. **`&World` is not read-only** in this
engine: `get_mut`, mutable queries and `resource_mut` take shared references.
`RenderWorld` must expose only read-only extraction, with no escape to the raw
world or mutable queries. GPU-derived buoyancy stays presentation state; gameplay
uses a deterministic CPU model (1046.006 K3). This is an API boundary, not a
sandbox for arbitrary native game code.

Hook resources belong to one canvas and one device generation. Device loss drops
them immediately; recreation, restore/carry and presentation-generation changes
prime histories before drawing. Resize invalidates size-dependent resources;
shader-generation changes rebuild candidate pipelines under the existing
interface checks. Expose paused/seekable state and host-derived time, define
zero/reset/clamped `dt` on resume or clock discontinuity, and never step the
simulation from a hook. History-dependent effects need an explicit reset/rebuild
policy; equal world hashes alone do not prove equal presentation after a seek.

`Needs::ANIMATE` requests further visible frames even when simulation is paused;
`PENDING` reports presentation preparation, not a new simulation-loading gate.
Failures use the existing named per-canvas error path (including shader/stage),
and a rejected shader replacement retains the last valid pipelines. The engine
owns attachments and submission and rebinds its GPU state after each draw hook.

## D2. The frame as data: `FrameView`

A read-only view of what the engine is about to draw: `view`, `proj`,
`view_proj` and their inverses; eye position; viewport in pixels and points;
render scale; the first posed sun (direction, colour, lux mapped to renderer
radiance); `Environment` (sky colours, fog, exposure); presentation seconds
and `alpha`; `dt` since the last drawn frame; paused/seekable flags; `reset`.
Attachment formats, sample count and logical viewport versus bucket capacity
are explicit. It supplies a reflected frame-uniform binding using the existing
`shaders/frame.wgsl` definition, not a second hand-maintained camera schema.
The current scene group also binds transform/material storage; it is not a
camera-only layout. Publish a frame-only binding for standalone hooks and
document the reserved scene/material groups for D4. LLP 1030 D8's interface
digest applies to the assembled shader, including the shared definition.

Geometry uses GPU transform histories; camera, model sorting and attachments
already retain some CPU history. A hook registers the few entities whose poses
it needs; the feed retains their history **at ticks**, not just drawn frames.
`FrameView::pose(entity)` uses the same interpolation, entity-generation checks
and birth/restore/teleport rules as engine drawing, including full affine socket
attachments. This avoids game-owned saved `prev` fields and a full CPU scene copy.

## D3. Optional services: the scene copy

The order is: skinning → hook compute → shadows → engine/hook opaque + sky +
optional hook background →
optional opaque snapshot → refracting surface → ordered translucency → final
resolve → optional HDR post → bloom → tone. The post output feeds **both** bloom
and tone. Raw hook geometry does not automatically cast shadows; D4 supplies
the paired shadow path.

`Needs::SCENE_COPY` splits the forward pass after opaque + sky. Resolve colour
into a sampled HDR snapshot, **store** MSAA colour/depth and continue them with
`LoadOp::Load`. The snapshot is distinct from the final resolve destination;
a texture sampled by the surface cannot also be its resolve output. The engine
opens the continuation pass and lends it to `surface`; `SceneCopy` contains
borrowed sampled views, not another live pass or an encoder.

For sampled depth, read the retained MSAA depth into `r32float`. With today's
forward-Z projection, select nearest covered depth across samples, not arbitrary
sample 0. Specify positive view-space depth, a far/sky sentinel and reconstruction
for perspective and orthographic cameras. This is a screen-space approximation
at mixed-coverage edges; it does not promise perfectly matched colour/depth.

The refractor writes composited colour **and depth**, so later translucent
geometry behind it cannot incorrectly draw over it. V1 refracts the opaque
background and supports ordinary translucent foreground geometry; it does not
solve transparent objects behind the refractor or multiple intersecting
refractors. Weird Waters currently includes particles in its pre-water snapshot:
that migration needs a deliberate composition choice and a visual comparison,
not the claim that drawing all particles afterwards preserves its picture.
The implemented `background` hook preserves this pre-water particle composition.

`Needs::HDR_POST` supplies distinct HDR input/output views. `PostInputs` must
also permit opt-in sampled depth without requiring a surface hook: final scene
depth and the earlier opaque depth have different meanings and are named
separately. Underwater effects choose the appropriate one. Exposure and tone
mapping happen once, in the engine. Hooks without these services keep today's
single forward pass and allocate no snapshot/post targets.

The scene-copy path adds an **early** resolve in addition to the final resolve,
depth conversion and intermediate HDR/depth targets. Today's colour/depth have
`TRANSIENT_ATTACHMENT` usage; the retained path must remove it and make depth
sampleable. Materializing 4× RGBA16F + Depth32Float can require 48 bytes/pixel of
backing storage before the single-sample intermediates, plus store/load bandwidth.
Reuse intermediates only after their last reader. Preserve bucket sizing and
effect-toggle release, but measure this path on iOS/Metal as well as web before
calling it cheap. Attachment load/store/resolve meanings follow the
[WebGPU attachment contract](https://gpuweb.github.io/types/interfaces/GPURenderPassColorAttachment.html).

## D4. Custom materials inside the engine's batches (phase 2)

Some meshes want a game's shader but the engine's batching, instancing,
interpolation and shadows. Examples: the kelp's sway, the fish's swim bend, a
hull that must float. C5's `DrawInstance` already exists and is used by models
(`game/render/src/lib.rs`, `models.rs`); extend it rather than wait for or repeat
the old consolidation pass. For those:

- A custom-material key names a registered pipeline family and reflected
  per-instance data; the exact `Material` representation remains implementation
  work. Registration includes entry points **and game-owned resource bindings**
  (textures, samplers, buoyancy buffers), not just shader names and a layout.
- The engine draws those batches with the game's pipeline, binds its own
  scene and transform groups, and passes custom parameters through the existing
  draw-instance record. Reserve bind-group/storage slots within granted web
  limits and validate the complete pipeline; silently requiring a fifth group
  or exceeding the model family's storage limit is not portable.
- Shadow casting uses a paired depth-only entry point with the **same vertex
  deformation, resources and alpha cutout**, or explicitly opts out. Preparing
  variants is readiness work, not a per-frame registration/compilation loop.

This replaces the "instanced meshes" half of 1046.006 W1. Entities become
inspectable, but GPU deformation does **not** automatically change CPU picking,
layout or bounds: declare a conservative pick/bounds proxy and report that
limitation. The implemented first family admits loaded, unskinned, opaque materials only.
`CustomMaterial` pairs forward/shadow pipelines and a game-owned group 2;
`DrawInstance.data` indexes game payloads. Group 0 is the engine scene, group 3
is the compact instance table. Forward group 1 is empty; shadow group 1 is the
light camera. Custom materials cast paired shadows but do not yet sample the
engine’s cascaded shadow maps. Transparent/skinned replacements are refused.

Phase 2 touches batch keys and the model pipeline family; D1–D3
already require attachment, lifecycle and scheduling work beyond call sites.

## D5. Shaders that live with the game

Compose shader registries at build time, preferably into the existing flat
`Registry.shaders` slice. Each game reflects its shaders; the app combines their
names and interface digests. Reflection, runtime lookup and delivery must use
the same namespaced identifiers, with duplicate names refused at the bake.

Declare additional flat directories in `gpu.shaderRoots` in `app.json`. Optional
`gpu.shaderPreludes` maps shader stems to ordered WGSL library paths, prepended
before reflection and packaging. External roots are explicit build inputs, resolved relative to the manifest
and packaged as ordinary digest-addressed assets. They must be present in a clean
checkout/dependency acquisition, not depend on an undeclared sibling on one Mac.
Reject symlink traversal; never expose source paths through the serving layer.
Use the same inventory for web and Apple bakes, dependency tracking, dev watching,
interface classification and production bundles. Runtime needs only packaged
assets. This removes manual shader copying, not W4's separate Contract/HUD copy.

For W5, `createShaderModule` + `getCompilationInfo` is useful diagnostics but
not pipeline proof. The existing web proof must create the actual render/compute
pipelines with their layouts, formats, sample counts and overrides, then submit
representative draws/dispatches and catch validation errors. WebGPU distinguishes
[module compilation information](https://gpuweb.github.io/types/interfaces/GPUShaderModule.html#getCompilationInfo)
from [pipeline creation](https://gpuweb.github.io/types/interfaces/GPUDevice.html#createRenderPipelineAsync).
Keep naga as the build gate; extend existing proofs, not the blocking-check count.

## D6. Inspection and budgets

- Name hook stages in timing output. Record separate GPU intervals where
  supported; report an enclosing pass honestly when an in-pass hook cannot
  be timed separately. Do not split render passes just for timing. CPU time
  in `prepare` goes into the `encode` ring.
- `state.world.renderHooks` separates engine-observed and hook-reported work in
  `beforeReady` / `afterReady`; `readyReasons` includes named
  pending reasons. Count renderer-provided allocations directly; raw-device hook
  allocations require explicit hook accounting and cannot be claimed automatically
  observed. `PENDING` clears after pipelines/resources are usable, not merely
  allocated. Foundational readiness/error handling lands with H1.
- The agent's `tree` for a canvas lists hook stage names, so an agent can see
  that a picture has a game-drawn surface without reading source.

H1–H3 prove basic hooks before H4. Instrument costs during those slices; H5 is
not permission to postpone correctness or readiness. No estimate assumes H2/H3
are merely extra call sites.

Use existing shipped-game proofs (`bun game/prove.mjs`) and public GPU readback
fixtures in `game/render/tests/`. Cover stage order; foreground/background depth
and silhouette edges; post-before-bloom with bloom on/off; perspective/orthographic
depth; hooks with no scene copy; resize/effect toggles; restore/seek and device
loss/recreation; rejected shader updates; and unchanged simulation hash/save with
hooks enabled. Keep a hookless allocation/pass/size baseline. Exercise real web,
macOS and iOS rendering, naming missing evidence rather than treating simulation
hashes or a build as pixel proof. Headless native readback can establish renderer
pixels without screen-recording permission; host presentation still needs its own
driven check. These extend existing tests/proofs, not a new gate or benchmark app.

Before retiring Weird Waters' renderer, capture a web/native pixel baseline and
frame-time/memory measurements, resolve the particle composition issue in D3 and
compare the migrated scene under matched cameras/times. Declare intended visual
changes (engine shadows, MSAA, bloom) instead of promising every pixel matches.

## 6. Alternatives

- **Keep the wrapper** (status quo, 1046.006 §3). No engine work. Every game
  with its own shading carries a second renderer and loses the engine's
  features. It is honest for one deck and wrong for a platform.
- **A node-graph material system** (three.js TSL, Godot's visual shaders).
  A graph could compile to enumerated shaders at build time and keep content
  game-owned. It is deferred because a new authoring language/compiler/editor
  is unnecessary for this consumer, not because graphs inherently violate
  shader enumeration or content ownership.
- **Embed Bevy's render graph.** Rejected for the reasons of 1046 F26: ECS
  coupling, a wgpu pin, tens of megabytes of wasm.
- **Expose the whole `Renderer` for a game to drive.** Most flexible, but it
  freezes every internal (MSAA, attachment buckets, batch keys) as API. Named
  stages freeze only their positions in the frame.

## 7. Rulings (Charlie Cheever, 2026-09-23)

1. **Scope accepted.** Game-supplied render hooks belong within the optional
   add-on, including reusable shader-packaging support in shared build tools.
   Keep the existing game-engine scope trade; add no engine dependency to core
   apps. The clarification lives in `rules/NOT-DOING.md`'s existing game entry.
2. **4× MSAA geometry, resolved inputs.** Custom geometry uses the engine's
   existing multisampled targets; refraction and post sample resolved textures.
   Preserve matching geometry coverage and measure the retained-attachment cost
   described in D3. No alternate single-sample geometry path is requested.
3. **Basic hooks, then custom materials.** C5's records already exist. Prove
   H1–H3, then extend those records in H4. The Weird Waters migration is not
   complete until custom materials replace its remaining duplicate drawing.
4. **Private consumer plus public fixtures.** Weird Waters may stay private
   while proving the hooks. Independently written public fixtures exercise web,
   macOS and iOS; engine tests/builds never depend on the private deck or its
   licensed ocean code. This is an architecture/testing ruling, not a change to
   the license's distribution terms.


## 8. Implementation and evidence (2026-09-23)

The implementation lives in `game/render/src/hooks/`, `renderer/draw.rs` and
`surface/render.rs`. `()` bypasses hook preparation, retained attachments and
stage calls. `Pipelines<T>` validates an entire candidate under a GPU error scope,
polls asynchronously, and retains the previous validated set on rejection. The
web agent’s existing settlement operation waits for that preparation. `RenderWorld`
has no `&World` escape; pose histories are sampled by the tick observer.

`shader_packs!` composes flat inventories and rejects duplicate names at compile
time. The same source inventory drives reflection, asset cards, web/Apple copying,
dev replacement and source capture. Source paths stay out of served assets.
Shared preludes avoid a generated-directory dependency or manual copy. Native
launchers read the captured asset generation, including external shader roots.
The compatibility CLI passes its already-resolved manifest to that inventory;
shader validation does not impose the full host manifest schema, and Cargo watch
directives are emitted only during a Cargo bake, preserving plain/JSON CLI output.

Named CPU stage rings are part of encode time. Arming existing perf inspection
allocates one optional timestamp query set and two readback buffers when the
adapter grants timestamps. Completion and readback are asynchronous. Available
GPU intervals appear under `world.gpuMs`; unsupported in-pass/encoder timestamps
are `null`, with opaque/background covered by forward and surface covered by its
continuation. These intervals can overlap and must not be summed. Device creation
requests supported timestamp features, without linking the game into `gpu`.
No query resources are created for hookless or unarmed canvases.

Public proof: `game/render/tests/hooks.rs` independently draws compute-fed opaque
geometry, refracts an HDR snapshot, writes depth and performs an HDR post. Six tests
cover service combinations, stage order, resize, seek/restore, device recreation,
unchanged world hash/save, invalid pipeline replacement and paired custom-material
shadows. The same public `TestGame`/`TestHooks<true,true,true>` source was compiled
into temporary ordinary Exact shells and driven on web, macOS and iOS simulator. Chrome exposed
a shader-stage flag native validation had accepted; the frame binding now requests
only vertex/fragment/compute visibility. The public browser and native fixture
pictures showed the expected coloured triangle; the iPhone 17 Pro / iOS 26.5
simulator also renders it with readiness true and no host errors. No private
source enters these tests.

The private migration removes the 1×1 wrapper, private target cache, ordinary mesh
buffers/draw loops, camera interpolation and second tone curve. Generated models
and draw-instance data now represent scenery, kelp, schools, player and six boats.
The game retains ocean compute, background particles, surface/refraction and HDR
underwater shading. GPU hull/kelp/fish deformation has conservative CPU pick proxies;
school proxies cover authored haunts, not individual animated fish. Presentation
history resets clear foam/buoyancy without rebuilding pipelines. Generated-mesh
validation also found a pre-existing negative-roundoff input to the fish profile’s
fractional power; clamping its sine to zero prevents non-finite vertices.

Web, native macOS and iOS simulator agree at tick 150 (`0x326d1207b0d9cbf8`) and tick 720
(`0xc02a0e819eee023d`) for seed 7 with no input. The old hash changed deliberately:
models, draw-data entities, Camera and light are now saved world content. Existing
breach and boat-spotting tests still pass; the private Metal readback test records
these new pins. Beacons’ existing Linux proof still passes its unchanged pins.

At 1280×760 active pixels, the 1280×768 bucket’s base and optional frame targets
account for **78,643,200 bytes (75 MiB)**, excluding shadows, bloom, ocean textures
and the host drawable. This is an allocation-size calculation, not driver RSS.
The private pack reports 34 pipeline, 22 buffer and 8 texture creations initially,
and none after readiness in the steady/seek check. Arming profiling adds two
engine readback buffers. The migrated web GPU module measured 2877 KiB / 683 KiB
gzip with timing support, versus 2117 / 550 KiB for the wrapper;
this compares complete consumers, not isolated hook overhead.

Evidence for this work is in `/tmp/exact2-render-hooks.OftnDL`: builds, test logs,
public fixtures, matched browser frames, private Metal readbacks and `waters-perf.json`.
A twelve-frame 640×380 Metal readback diagnostic obtained six asynchronous GPU
samples; those short debug-build observations establish instrumentation, not a
steady performance budget or an iOS claim.

After accepting the Xcode license, both the public fixture and private app build
and run on the iPhone 17 Pro / iOS 26.5 simulator. Captured private ocean and
underwater frames establish iOS host rendering. At 402×874 points and 3× scale,
the private frame targets account for **255,262,720 bytes (243.4 MiB)**, before
shadows, bloom, ocean textures and the host drawable. The same readiness counters
show no further hook pipeline/buffer/texture creation between the two checkpoints.
This is simulator correctness and an attachment-size calculation, not physical
iPhone frame-time, power or resident-memory evidence. The desktop-oriented HUD
also overlaps in portrait and still needs a separate mobile layout pass.

The existing clean sibling Ibex checkout now supplies vanilla Hermes at Exact's

  startup readiness); the directly relevant GPU asset, surface-record and
