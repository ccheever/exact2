## 1. Decisions

### D1 — content between the bar and the list sits below the bar

On iOS, a route's content that doesn't scroll (a row between the `header` and the list or `scroll`: a
persona switcher, a filter, a banner) is laid out below the navigation bar, large title included, and
moves with the bar as the title collapses. It is never drawn under the bar or covered by it. The
scroller beneath still scrolls under the bar as UIKit's does. An XCTest covers team-kanban's shape: a
segmented control between a large-title header and a grouped list, tappable, not overlapping the title.

### D2 — the split's empty pane is the platform's placeholder

On a wide window, a split with no detail shown draws a quiet placeholder in the detail pane, as an
iPad's split view does: the platform's secondary label, centred, in the strings' language. An author
who writes one in the root route (a `when` on no selection, an `EmptyState`) wins. An empty list is the
list's own empty state, not this.

### D3 — `verify` owns an app's server, on an empty database

For an app with a server (the `rest` pattern's shape: a `server.ts` run by Bun, its database in `DB`),
`verify` runs the server the app already calls, at the URL the app reaches, on an empty on-disk scratch
database it keeps through the tests, the journeys and the relaunch, then removes. The builder's own data
is left alone; if the builder's dev server holds the port, `verify` says so in one line rather than
writing into it. `api-test` uses the same lifecycle, so one way runs the server for both.

### D4 — a test can go back

The authored test grammar gains `back`: the platform's back (the router's `back`, a sheet's dismissal),
as a person would.

### D5 — `check` reads the background a text sits on

Contrast is judged against the nearest painted background under the text (its own box, a bubble, a
card), not the page's, so chat-rooms' real dark-mode finding stays and its false light-mode one goes.
Overlap and covering are judged on what is presented: a row clipped correctly by its list is not an
overlap (contacts).

### D6 — the keyboard's bar is the platform's

The ± and Done bar above a number pad (LLP 1116.003 D7) is drawn as UIKit draws an input accessory
bar: the system's material, the keyboard's width, no opaque band over the content. The field it serves
keeps its section in view.

### D7 — fewer files to read

- **`exact.mjs` is a few lines** that call the checkout's shared script; its verbs are in `--help`. A
  builder reading it gets the verbs, not 7 KB of code.
- **`app.contract.d.ts` opens with the shapes `app.ts` writes**, one line each, before the long
  declarations, so a builder can read its top.

### D8 — a test writes as another user

An authored test can write through the app's server as another persona (a request line with the
method, path, body and the persona's token, against the server `verify` runs), then advance the clock
past the app's poll and expect what the app shows. The second-user journey is then a test, and `verify`
covers it with no curl timed against a poll by hand. The `rest-backend` recipe's test shows it.

### D9 — finish on the graded platform

Start-here and `ios-driving` say the last `verify` is on the platform the app is for (`verify ios` for
an iPhone app), since a clean web `verify` doesn't show an iOS bar covering a control.

### D10 — the day at the moment of the write

The `dates-and-days` recipe computes the day key in the action that writes, from the instant of the
write (`time.epochAtZero + performanceNow()`), not from the minute-ticked state. An entry made just
after midnight is today's, and the zone is read again on change, as the host already answers it.

### D11 — a history row in the recipe builders open

`content-design` gains the row water-tracker's grader missed: a day's label, a bar of its value
against the goal, and a badge when met, aligned in a column. No new part, and no redesign.
