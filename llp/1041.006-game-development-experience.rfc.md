## 1. Proposal and scope

Make the normal loop: **play → capture a problem → reproduce it → inspect → edit → continue or restart deliberately → verify**. Keep one inspectable world, one serialization model, and the existing eight agent operations. The development experience should make these operations convenient without hiding which program, state, clock or input carrier is running.

Use one RFC with four independently deliverable slices, rather than a new document for every tool. Lanterns is the first consumer; Beacons is the small second consumer that keeps the implementation from becoming Lanterns-specific. Split a slice into a child only when implementation needs a separately owned decision.

Priority: ownership and truthful diagnostics first; convenient reproducible captures next; reliable reload on the web next; declarative scenes next. Native sweeps run behind the web loop. Native live game-code replacement and TS gameplay scripting are separate experiments, not prerequisites for this proposal.

The broader roadmap `1041.005-where-to-go-from-here.rfc.md` exists in the game/Lanterns checkout; it covers consolidation, assets and engine alternatives. This RFC refines the development experience without replacing that roadmap or the established agent protocol. Numbering was checked across live worktrees and deleted-document history: children through .005 are allocated. There is an existing .003 collision between the comparison research and the game-lane explainer; this document does not silently rename either. References here use filenames where that matters.

## 3. Shared constraints and proposed scope trade

- Preserve `tree`, `screenshot`, `tap`, `type`, `state`, `layout`, `logs`, `clock` (LLP 1012; 1041.001 D1). A driver convenience command may compose them; it is not a ninth host operation.
- Simulation state remains typed `Data` in the world. Time and random inputs stay explicit. No recorder-owned shadow world or renderer-owned gameplay state.
- The game remains an optional add-on, loaded after first pixel. No new core feature flags, boot-time source compilation, blocking check, daemon, registry or editor application.
- Contract owns UI. Scene authoring describes world data; Rust owns behavior today. Existing TS app-data support is not a TS game-tick implementation.
- A simulation reproduction is distinct from a platform-input reproduction and a visual/performance reproduction. Evidence must name which was exercised.

`DEFERRED.md` currently refuses session record/replay, causal trace, behavior diff/verify and a devtools UI. Existing saves plus hand-written scripts fit the current scope; the bounded recorder proposed in §5 extends it. **Proposed take:** admit only an opt-in, game-local input recording attached to the existing world save, to reproduce Lanterns bugs; defer TS gameplay execution and native live game-code replacement until this loop is proven. General app session recording, causal tracing, arbitrary mutation history, a replay service and a timeline editor remain out. This proposal does not amend the rule file or treat Charlie's request for a draft as acceptance of that exception.

The new RFC replaces the completed comparison research's working-set link, preserving the research and evidence in the corpus. The working set remains at fifteen.

## 4. Slice A — ownership, truthful clocks and useful diagnostics

### A1. A session has one input/clock owner

Report the active owner (`human` or `agent`), clock mode (`live` or `controlled`), host, carrier delivery class, loaded build identity and world tick through existing inspection. A read-only observer does not acquire the clock. Connecting a tool must not silently turn normal play into stepped simulation.

Use an explicit handoff: stop the previous driver, cancel its owned contacts/keys, acknowledge detachment, rebase the live clock without simulating the time spent paused, then return control. Disconnects release owned input and report the outcome. Persistent player saves are not changed by handoff. A human-facing development notice identifies an actively controlled session; automated tests use a separate instance where possible. On a single phone the operator is told before control is taken. No production debug overlay is required.

Simulation tests keep intentional recorded input in their checkpoint; a fresh human handoff clears physical held input. These are different operations and must not accidentally share a default. A test result records external human input during a controlled run as contamination, not silently as part of the intended script.

### A2. Exact tick advancement and readable failures

Add a small helper to the existing driver that advances an intended count of simulation ticks through `clock`, reports requested and actual tick boundaries, and refuses unsupported modes. Avoid per-test fractional-ms arithmetic. It must respect pause and restored clock epochs; it must not retry an action or step an extra frame silently to make an assertion pass.

Failures should answer: which app/build/world/entity, at what tick, what was requested, what was observed, and what next action is possible. Reuse existing replies and journal entries. Useful examples: `surface world: Load refused: game ID differs; current world retained` and `reload: scene changed; continuing preserves existing entities; restart to instantiate new content`.

Report loaded versus requested artifact identity, reload phase, last successful swap, restore outcome, available carriers, live input owner, and truncation/unavailability explicitly. Existing input delivery labels stay authoritative: a recognized button activation is not a synthesized physical touch. Source links for authored scenes are development sidecars tied to the scene digest, following LLP 1035.002/1035.005; do not ship source paths in production.

**Acceptance:** attach/detach during movement leaves no stuck keys; phone handoff returns to normal pacing; integer tick requests remain exact across pause and restore; a refused restore preserves state/hash; missing transport or unsupported input has an actionable error. Physical simultaneous move+Jump needs real input evidence, not only agent button activation.

## 5. Slice B — convenient, bounded reproducible bug captures

### B1. Begin with the existing save and driver

The first deliverable packages a checkpoint, an explicit reproduction script and observed failure from an existing agent run. No human-input recorder is required for this first useful step. Extend the current driver/proof entry point rather than install a second tool suite. Capture and replay vocabulary below is conceptual, not a commitment to new wire commands or exact CLI syntax.

A capture contains:

- Game ID/save version; code, Contract plan, scene and asset digests; fixed-step rate; seed; host/input/clock metadata. A Git commit alone is insufficient for dirty builds. Record actual artifact digests, including separate UI/game artifacts, without silently rebuilding a different program.
- A snapshot at a known tick boundary, its semantic hash, and the supported app/Contract state needed to restore the interaction. A world-only capture is labeled world-only; it cannot claim to reproduce title/HUD behavior controlled by omitted UI slots.
- Ordered input and live-binding records after that boundary, with tick, within-tick order and phase. Include pause/resume, action counters, viewport-dependent input context and relevant lifecycle transitions. Store supported external results or refuse claims of reproduction when hidden I/O is involved.
- Expected observations, checkpoint hashes, bounded logs and optional screenshots. Screenshots help identify a problem; they are not the simulation oracle.

Reopening a capture creates an isolated session and scratch storage. It must not overwrite a player's normal save, run arbitrary embedded shell code, install unknown executables, or fetch unpinned assets. Scripts are local author-controlled test source; imported captures are validated data. External sharing is explicit, with an inventory of included game state and local metadata.

### B2. Then add a narrowly scoped human-input recorder

At the existing input/binding ingress, record inputs actually accepted by the simulation, not a second interpretation of gestures. Raw platform events can be retained as optional diagnostic evidence; normalized simulation events reproduce behavior, not UIKit/Safari gesture recognition. Observe Contract actions' resulting world bindings in the same deterministic ordering as raw world input. Capture UI-owned state separately when the bug requires it.

Use a bounded checkpoint-plus-event buffer. Keep a checkpoint and a contiguous event suffix together; never evict required inputs and still call the capture complete. Exceeding byte/time/event limits produces a visible `incomplete` result or advances the retained checkpoint safely. Start with an explicit capture window, not always-on telemetry. A crash before the last completed boundary can lose the tail; say where the reliable interval ends.

### B3. Replay and mismatch semantics

Replay on the same compatible build first. Check recorded hashes at known boundaries and stop on the first mismatch with expected/actual hash and a bounded typed-state comparison for that checkpoint. Do not invent an exact first divergent tick when hashes were sampled less frequently. A changed-build replay is a regression experiment with intentionally different outcomes, not an exact reproduction of the old build.

Seeking backward means restoring a checkpoint and replaying forward. It is not negative time or arbitrary reversal of Rust execution. Forking means two isolated sessions from one checkpoint, each with its own input suffix and save store. Exact simulation equality and image tolerances are separate assertions; cross-host equality is a measured result for the recorded workload, not a promise inherited by every future API.

**Acceptance:** capture Lanterns after a crate push; restore and finish the same route twice with equal sampled world hashes; restore paused and terminal states; reproduce interleaved touch/Contract inputs; reject wrong build/game/version; detect a dropped event, corrupt checkpoint and unsupported external dependency without false success. Run same-build headless replay on the fleet and sweep web/Apple where supported. Keep absent phone/world-carrier support explicit until implemented and tested.

## 6. Slice C — state-preserving reload as a dependable operation

Expose three distinct intents: **continue** with compatible code and carried state; **restart** using new authored content and a chosen seed; **restore** a selected checkpoint. State preservation is the default for compatible behavior edits, not a claim that edited setup will rewrite a running world.

| Edit | Proposed result |
|---|---|
| Compatible Rust tick/behavior change | Build replacement, carry current state, continue at the same simulation tick |
| Contract UI change | Carry compatible UI state and uniquely identified world; report reset fields |
| Declared live argument | Bind at an explicit boundary; record old/new values for replay |
| Scene/setup/seed or construction argument change | Offer a fresh restart; continuing retains the old instantiated world and says so |
| Incompatible component/save schema, missing asset or invalid binding | Refuse continuation with named reason; retain current session; explicit fresh restart remains available |
| Core ABI/host change | Report rebuild/relaunch requirement; do not label it hot reload |

Use the existing web replacement mechanism. Capture at one boundary, validate/build the candidate, reconstruct renderer/executor state, restore, validate bindings/publications and establish readiness before committing the replacement. In a multi-canvas app, stage the complete participating set; partial cutover is a failure. Keep the old session until commitment. Compilation, restore, device setup or candidate-render failure must not discard the old world or its save.

Define rollback coverage explicitly: staging must suppress irreversible side effects such as audio playback and durable writes. State that cannot be staged safely forces restart or an unsupported result, not pretend transactionality. Tag asynchronous build results so an older completed build cannot replace a newer requested one. Validate immutable captured inputs/receipts; asset edits during a bake must be rejected or scheduled for a new bake, never bypass the verifier.

After a successful commit, rebuild disposable GPU/physics executor caches from the supported carry, release stale input owners, refresh HUD publications, and rebase the host clock. Compilation time is not elapsed game time. Define argument precedence: current compatible live UI bindings win; retained construction identity and reset fields are shown explicitly. Names alone are not enough to silently match duplicate world instances.

Web is the first fully verified reload loop. Native must advertise its actual capability: UI restart with carry, game rebuild/relaunch, or a separately proven live replacement path. Reusing the snapshot format does not make all three equivalent. Do not design an iOS native-dylib hot loader as part of this slice.

**Acceptance:** edit movement speed mid-run without losing timer/crate/lanterns; edit HUD with input held; fail compilation and keep playing; fail restore and retain old hash; trigger overlapping rebuilds; reject a receipt mismatch; add a scene entity and show why Continue differs from Restart. Verify repeated swaps release old resources. Test measured game time across a slow build and the first post-swap input.

## 7. Slice D — declarative scene authoring over the same world

Move repeated world construction data out of Rust, while leaving tick behavior in Rust and UI in Contract. Start with typed JSON scene data, compiled/validated at bake. A compact text syntax can follow if actual authoring friction warrants it; this draft introduces no `.contract` grammar extension or general-purpose game scripting language.

The initial scene vocabulary contains named entities, parent references, registered component values, asset references, and small reusable fragments with explicit parameters. Use one explicit coordinate/unit convention matching the existing game math. References use stable authored keys; spawned fragment instances qualify local keys by their instance key. Duplicate identities, cycles and missing references fail at build with source locations.

Component types, field types/defaults and serialization remain defined by the existing Rust `Data`/Component declarations. Generate or expose scene validation metadata from that authority; do not hand-maintain a parallel JSON schema for every component. Scene loading constructs the same components that Rust setup constructs. Unsupported opaque fields receive a deliberate typed construction boundary, not an arbitrary evaluator.

A scene definition is an initial condition, not a saved game. Runtime changes live in the world and its snapshot. Procedural generation remains a named Rust function with explicit seed/parameters. Start reusable fragments with explicit overrides; no implicit deep merges, multiple inheritance, hidden execution order or arbitrary expressions.

Prototype shape, not final field syntax:

```json
{
  "entities": [
    {
      "id": "crate",
      "components": {
        "Transform": { "position": [6, 0.6, 8] },
        "Mesh": { "Cube": 1.2 }
      }
    }
  ]
}
```

Actual enum encoding and required components must be derived from the existing type declarations; this illustration does not define a second encoding. Bake resolves asset references and dependencies. An agent can find an inspected authored entity's declaration through a digest-bound development source map; procedural entities report their generator and authored parameters rather than fabricate a source line per generated object.

**Acceptance:** author Lanterns' ground, wall, crate, ledge and lantern roster in scene data; show equivalent initial semantic state to Rust setup under fixed identities; edit a lantern position without rebuilding game behavior code; distinguish content rebake from code rebuild; reject a wrong field/type/reference with file and field location. Reuse one fragment in Beacons. Save/reload preserves runtime progress independently of later scene edits, with explicit compatibility/refusal behavior.

## 8. Other development experience work that belongs here

| Concern | First useful deliverable | Boundary |
|---|---|---|
| Small authoring/test loop | Existing scaffold/dev/proof commands, short named movement/inspection/assertion helpers, integer tick helper | No alternate test framework or game-specific privileged mutations |
| Asset diagnostics | Name asset, unsupported feature and source path; show declared, loaded and failed assets/readiness | Broad importer expansion is separate; do not claim arbitrary glTF support |
| Storage reliability | Isolated test slots, complete writes, corrupt/incompatible-save refusal, cold-start UI/world consistency | No cloud-save service or migration framework |
| Input fidelity | Report platform/recognized/unsupported delivery; tests for simultaneous move/Jump, blur, cancellation and device rotation | Scripted key success does not establish real multitouch success |
| Performance visibility | Existing state/log or development metrics output: build, replacement, first usable frame, tick and render costs | Controlled-clock results are not normal-play FPS; no new permanent profiler UI |
| Portable bug reports | Capability report, exact artifacts, reproduction class and unavailable host features | No silent simulation fallback presented as a GPU/phone pass |
| TS behavior experiment | Later, one small consumer using the same state/time/save contract and measured crossing cost | Not part of accepting this RFC; avoid hidden JS-owned simulation state |

Measure the actual loop: edit detected → build complete → replacement committed → first usable presented frame; separate cold/warm caches and code/content/UI edits. Report failures and sample counts as well as successful latency. Keep the repo's 30-second touched-crate, 60-second focused-check and five-minute warm-build budgets; measure the existing web module loop's 2-second warm target rather than assert it from architecture. Native compile/sign/install time is a distinct measurement. Fleet diagnostics run asynchronously; no sixth blocking check.

## 9. Delivery and success criteria

| Slice | Deliverable | Evidence required before calling it complete |
|---|---|---|
| A | Ownership/clock/capability reports and exact tick helper | Human handoff and pause/restore tests; no simulation-state mutation from inspection |
| B1 | Save + known script + artifact identity bundle | Another clean session reproduces a Lanterns failure without hand reconstruction |
| B2 | Bounded game-local human input capture, after scope admission | Contiguous capture, replay equality, truncation/corruption refusals and isolated saves |
| C | Dependable web continuation/restart/restore | Full failure/recovery matrix and measured edit-to-usable-frame timings |
| D | Typed scene content and source links | Lanterns conversion, Beacons reuse, no behavior rebuild for content-only edits |

A and B1 can start without admitting general recording. B2 needs the narrow rule amendment in §3. C builds on the existing swap/carry implementation; D must use its explicit restart semantics. Tests belong in the existing engine, host and consumer suites. Diagnostics are attributed to the tested artifact; passing root workspace checks alone does not test the separate game workspace.

Suggested experiment after the slices: hand a fresh agent a captured crate bug and ask it to reproduce, fix and verify it without author guidance. Measure time, manual reconstruction, native rebuilds and any unjustified claim of reproduction. Success is a small reliable loop, not the number of new tools.

## 10. Decisions still open

1. Admit the bounded game-input recorder proposed in §3? Recommendation: yes after B1 proves the bundle workflow; keep generic app recording and causal tracing out.
2. How much Contract state must the first capture include? Recommendation: support the named local UI state needed by Lanterns; explicitly refuse exact whole-app reproduction when unsupported resources are involved.
3. Is typed JSON sufficient for first scene authoring? Recommendation: prove the component authority and source mapping before choosing a custom language.
4. Which native live-reload capability is worth its cost? Recommendation: keep rebuild/relaunch with carry as the honest baseline; measure friction before proposing more.
5. Who implements each slice, and when? Unassigned. This is a requested draft RFC; no acceptance, implementation schedule or delivered capability is implied.
