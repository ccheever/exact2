# LLP 1071.000: Rows at scale on the JavaScript target — the TypeScript seam, unmoved keys and field-masked rows

**Type:** RFC
**Status:** Draft. Charlie approved the goal on 2026-09-30: close the 10k-row interaction gap with Solid and Svelte on the grid benchmark. D2 and D3 are written; D1 records what the seam can and cannot share. §8 (2026-10-03) is the second round, after the final grid run.
**Systems:** the JavaScript runtime (`host/web-js/rt.js`: `each`, `writeItem`, `effect`; `list.js`; `ts-data.js`); the JS emitter (`host/web-js/src/emit.rs`: binding field masks, pure keys). No plan, ABI, Contract or native-host change.
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-30

## 2. What the seam's semantics are, on every host

Normative for every host and executor (the Rust runner natively, Hermes on Apple
and Linux, the browser for the JavaScript target), restating LLP 1027 D2:

1. **A source receives values.** Each call's arguments are fresh ordinary values
   of the plan's types: plain objects with the declared fields in order, as
   own, enumerable, writable data properties; arrays for lists; `null` for an
   absent option. `JSON.stringify`, spreading, `Object.keys`, `structuredClone`
   and `postMessage` behave on them as on any plain value.
2. **A source's edits stay its own.** A source may edit what it was given in
   place, during a call or after it; nothing the runner holds changes, and a
   later call is given what the runner holds, never the edited value.
3. **An answer is a value.** It is read once when it is answered (or when its
   promise settles), converted by the plan's types, shape-checked and compared by
   value. Returning an argument, edited or not, is returning its current value.
4. **Identity is never observable.** A host may reuse its own storage for parts
   of an answer that equal what it held — the Rust runner keeps an equal answer's
   old object and re-checks only list items that are not the same object; the
   JavaScript target does the same (§3) — but a source cannot tell.

## 3. D1 — The JavaScript target's seam: shared on the runner's side, fresh on the module's

Landed (`2959c1d9`, `617eed58`): each type's converters are made once; an answer
converts against the last answer its target was given, so a record or list that
converts to what it did is the runner's existing array; a shape check skips a part
that is the same object as a value that conformed, as `conform.rs` does; a
mutation's answer is checked against its last. At 10,000 rows with one row changed
that took convert + check + compare from 5.7 to about 2.3 ms (desktop).

The module's side stays fresh: every call builds the module's objects anew. The
three ways to share it were weighed against §2 and set aside:

- **A lazy view** (a `Proxy` over the runner's array, LLP 1027.003 §3 B): a
  `Proxy` is not structured-cloneable (`structuredClone` and `postMessage` throw
  where a plain object succeeds, §2.1), so it is observably not a value; and every
  property read runs a trap, which a source that scans its argument — the grid's
  `toggleSelected` reads every row's `id`, `totals` four fields of every row —
  pays per row, where building the objects costs about 1.2 ms for 10,000 rows.
- **Handing back last call's objects** while unedited: an in-place edit of a
  plain object can't be detected without a trap or `Object.freeze`, and a freeze
  makes a source's edit throw (§2.2).
- **Patches from the source** (a source answering what changed): a different
  source API, which every host would have to carry; the declared refreshes of
  LLP 1054.000.000 and bounded answers of LLP 1027.004 already say what a write
  changes at the Contract level.

So a source that takes a whole list pays O(list) at the seam per call: about
1.2 ms each way for the grid's 10,000 rows on desktop. The pattern that bounds
the way in is the app's (LLP 1058 P4: a source takes what an interaction needs),
not a second representation. The way back stays O(rows) whatever the app does:
a resource's or mutation's answer is its whole value, so a list answer is
converted and compared row by row, even when the rows it reuses cost nothing
after that. Only a windowed answer (LLP 1027.004) is smaller than its list.

The grid benchmark's sources take the whole grid on purpose (its notes: pure
sources, so an adopted page's checkpoint is all its state). A draft that seeds
app.ts once and sends only what each action needs saved about 1.2 ms of a
~500 ms mobile operation, against a module copy that can drift from the
runner's if an answer is refused; it was not applied (2026-09-30). D2 and D3
keep the rest of an update O(changed).

## 4. D2 — A keyed list whose keys didn't move is not re-diffed

`each` today builds a key map for every item and a longest-increasing-run over the
kept rows on every change. When the new list has the old list's length, it first
walks both in step instead:

- an item that is the same value as the row's (by identity, which D1 now gives
  unchanged rows) is skipped without computing its key;
- otherwise its key is computed; the same key at the same place gives the row the
  new item (D3), and a different key ends the walk.

A walk that reaches the end is the whole pass: no map, no reordering, no DOM
operation. One that stops falls back to the full keyed pass, which re-does
nothing the walk did (writing a row's item twice is a no-op). The walk is taken
only when the key reads nothing but the row's item and index (the emitter marks
it, `each(…, 1)`): a key reading other state could differ for an identical item,
and the runtime doesn't track the key's reads. Rows waiting for adoption (LLP
1071 D6's slices) take the full pass.

Semantics: unchanged. The rows, their keys and their order are what the full pass
produces for the same list.

## 5. D3 — A row's new item re-runs only the bindings whose fields changed

The emitter knows which of a row item's fields each binding reads: its code reads
the item only as `i<r>()[k]` with constant `k`. For such a binding it marks the
effect with the mask of those fields (`fm(mask, …)`, fields 0–30; a binding that
reads the item any other way, or two items, is unmarked). When a row is given a
new item, `writeItem` compares the old and new item field by field (by value, as
`write` compares) and marks dirty only the item's observers whose mask meets the
changed fields; an unmarked observer — a derive, an unmasked binding — is marked
as before.

Semantics: unchanged. A skipped binding's inputs are the same values, so its
output is; derives that read the item re-run and cut off by value as before.
Only effects are masked, and only through the item's own signal: a masked
binding that also reads a derive still re-runs when the derive changes.

Cost: one number on an effect at creation; one field comparison per changed row
per update. The grid's update (1,000 rows, the name changed) re-runs 1 binding a
row instead of 17; a select, the row's selection bindings.

## 6. Not in this LLP

- **Two more elements a row than the others.** The grid's row makes 24 layout
  nodes where Solid makes 22 (`final-grid.md`, create: 240,022 against 220,018):
  a text inside a button is its own `<span>` (a kernel node is an element, LLP
  1007 §1). Collapsing a style-less text into its button's text is a projection
  change on every host, for its own LLP.
- **The virtualized list's rows** (`list.js`) take D3's `writeItem`; D2's walk
  is `each`'s only.

## 8. Round two (2026-10-03): what the final run's 537 ms still paid

The final grid run measured D1–D3 (`final-grid.md`, exact2-js-opt): update
every 10th at 10,000 rows, 537 ms against Svelte's 442, 82 ms of script
against 25. A CPU profile of that click on current main (desktop, the bench's
production build unminified) put most of the script outside the 1,000 rows
that changed. Landed, each for every app (`98aa3d29`, `98903ac7`):

- **D4. A router with no navigation root searches for none.** Every commit
  ran navigation.js's `project`, `root.querySelectorAll("[navigationBack]")`
  over the whole tree: 240,000 elements a click, about 40% of the update's
  script. The emitter knows whether any node binds `navigationBack`; a plan
  that has a router and none passes `router(slot, nav, 0)` and projects no
  roots (the page module's `onProject` still runs). paint.js's
  `p.querySelector(":scope>[data-exact-box]")` on a changed list was the
  same walk; it reads the children.
- **D5. The seam's converters and the shape check, constant factors.** A
  list of leaves is copied and compared in one loop; a record's objects come
  from one template (one shape). The check skips an unchanged part in one
  step (each type code's ends found once) and remembers, for a value and its
  parts one level down, the type code it conformed to: the derives that pass
  on a checked answer are not walked again. §2's semantics are unchanged.
- **D6. DOM writes the change needs, once.** A text binding writes its Text
  node's `data`; a style binding writes `setProperty` once (two style
  mutations a change before); a moved one-element row moves with one
  `insertBefore`, not through a fragment.
- **D7. Elements by clone.** The emitter hoists each element site's static
  arguments to one object (`$A[k]`); `h` builds that site's element once and
  clones it (`cloneNode(true)`), so a row's elements cost no `setAttribute`
  each. Adoption and the render DOM build as before. Effects share one empty
  observer set.

Measured with the bench's harness (`measure.mjs`, mobile: 4× CPU, shaped
network, builds interleaved; exact2 main `41a0e168` against this branch,
Svelte, Solid and React SSR) on a machine at load average 15–24 (other
agents' builds), so input→paint is too noisy to rank and the script column
(CDP ScriptDuration) is what this round claims; two runs (7 and 9 per build):

| step (10k rows) | main | this branch | Svelte | Solid | React |
|---|---|---|---|---|---|
| update every 10th, script ms | 128 / 128 | 48 / 60 | 29 / 52 | 59 / 68 | 98 / 101 |
| select row, script ms | 110 / 125 | 62 / 77 | 38 / 72 | 64 / 89 | 62 / 44 |
| swap rows, script ms | 169 / 246 | 111 / 172 | 111 / 171 | 104 / 146 | 178 / 160 |
| remove row, script ms | 176 / 169 | 96 / 122 | 87 / 137 | 90 / 114 | 42 / 44 |

Mutations are the scenario's minimum for the update (1,000) and unchanged
elsewhere. Conformance (24 apps and 36 synthetic plans against the wasm
oracle) and the grid's behavioural check pass.

Not closed here:

- **The seam is still O(rows) each way** (§3): about half of what is left of
  the update's and nearly all of the select's script. Only an answer that
  says what changed (LLP 1053 G8's keyed patches, a source API every host
  carries) or a source that takes less (LLP 1058 P4) removes it.
- **The grid's body is a flex column** (`column` in the bench's app; Svelte's
  `.grid-body` is a block). Chrome re-runs flex over all 10,000 children when
  1,000 change: 25–30 ms of the 4× update's layout, measured with the body
  switched to `box`. That is the app's transcription, not the runtime.
- **A keyed pass after a change at both ends** (swap, remove, append) is
  still the full map and run over every row; a common prefix and suffix
  would bound it.
