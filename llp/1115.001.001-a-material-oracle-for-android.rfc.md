## 0. Summary

On Android, "the platform's look" is a library, and it has a version. Compose Material 3 ships inside each app
that uses it, so it looks the same on every phone, and a hand-built app shows the version it pinned. That makes
Android the one host where Exact can be held to an exact, checkable reference: a version number, its source, and
what that source draws.

This RFC builds that check. It has four parts:

1. **One pin.** The Material 3 version the islands link is the version every painted component matches (D1).
2. **Tokens read, not remembered.** The design tokens come out of that version's own source by script, into the
   schema's `metrics` table, each row naming its token (D2).
3. **A reference and its oracle.** A catalogue of specimens is drawn twice, once by Compose Material 3 and once by
   Exact, and compared for geometry, colour, pixels, accessibility and motion. The reference renders on the JVM
   without a phone, so the build box can run it every hour; a Pixel confirms it (D3 to D5).
4. **A rule for each component.** Exact paints what holds the author's content or appears inline, and a Compose
   island shows what is modal and holds only its own (D6).

What it changes: a component is "Material" when the oracle says it matches at a named version, not when someone
remembers the spec. Keeping up is a version bump, a token diff and a list of failing specimens (D8). Compose never
runs in a shipped app for this; it runs in the reference, and in the islands 1115.001.000 already links by use.

## 1. Why, and what is there

1115.001 D1 made Compose Material 3 the reference, and its §5 Q4 said a reference app would keep the look current.
Nothing of that app exists yet. What is painted today was built from the spec pages and memory, and the documents
say so: the top app bar and navigation bar are "Compose Material 3's `TopAppBar` and `NavigationBar` as remembered,
not read against the library that day" (1115.001 §3, D11); the menu's motion is "as Compose's `DropdownMenu` moved
it (from memory)" (D10). The filled text field's numbers are constants in `paint/material.rs`, cited to
m3.material.io. A Material release that moves any of them would not be noticed.

What makes a better answer cheap here:

- **The library is pinned and bundled.** OEMs do not restyle it, as they do the framework's dialogs. The reader
  already pins it (`host/android/app/build.gradle.kts`: BOM `2026.09.00`, Material 3 1.4.0).
- **Its tokens are data.** The `androidx.compose.material3.tokens` package is generated from Material's design
  tokens (each file says so) and published in the library's sources jar on Google Maven
  (<https://maven.google.com/web/index.html#androidx.compose.material3:material3-android>).
- **It can be drawn without a phone.** Robolectric's native graphics mode (`@GraphicsMode(NATIVE)`, Robolectric
  4.10 and later) draws a Compose tree with Android's own Skia on a desktop JVM, and Roborazzi captures it
  (<https://github.com/takahirom/roborazzi>). Compose's test clock stops time so each frame of a motion can be taken
  (<https://developer.android.com/develop/ui/compose/testing/synchronization>).
- **Exact's side can be drawn without a phone too.** The Linux presenter paints the Android look headless when it
  is told a device and a palette and not told the neutral look (`Presenter::boot_with`, `set_device`,
  `roles::set_reported`; `presenter/device_tests.rs` does it today). Shaping is Exact's own on Android too (the
  reader draws glyphs the Rust shaped), so given the same font files a headless render's text is the phone's.
- **The repo already works this way on the web.** `host/web-js/conform.mjs` holds the web target to Chrome, and its
  Firefox and WebKit steps to Chrome's answers. This is the same shape with Compose as the oracle.

## 2. Decisions

### D1 — One pin

The Material 3 version the reader's Gradle build links (today 1.4.0, through the BOM) is the reference for every
component on Android, painted or not. A painted button and an island's picker in one app are never matched to two
versions. The pin lives in one place, the reader's version catalogue, and the oracle, the extractor and the islands
all read it from there.

The reference is what a hand-built app gets by default: `MaterialTheme` and each component's stable API with its
defaults, on the device's dynamic colours (1115.001 D1.1). Experimental APIs, the Expressive theme among them, are
not the reference until they are the default (§5 Q2).

### D2 — Tokens are read from the pinned source

A script (`host/android/reference/tokens.mjs`) reads the `tokens/*.kt` files from the pinned version's sources jar,
which Gradle fetches with its checksum verified, and writes:

- **a `material` column in the schema's `metrics` table** (`kernel/tables/schema.json`), beside `web`, `ios`, `mac`
  and `neutral`, for each row the Android look reads. Each value carries its token's name
  (`FilledTextFieldTokens.ContainerHeight`), so a reader can find it in the source. `kernel/build.rs` generates from
  the table as it does for the other columns. Lengths are dp; colours are role names, never colours, since the
  device's palette resolves them (1115.001 D4); shapes and type styles are the token's key (`CornerExtraSmallTop`,
  `BodyLarge`), resolved by the type and shape scales that are themselves tokens.
- **a token snapshot** of the whole package (`host/android/reference/tokens/<version>.json`), so that a version bump
  has a diff (D8).

Some numbers are not tokens: they are private constants in a component's own source (a checkbox's check path, a
switch thumb's pressed size, a ripple's timing). A row for one names the file, the line and the version
(`Checkbox.kt:612@1.4.0`), and the oracle checks it like any other.

What the painter has now as constants moves to rows (`paint/material.rs`'s `HEIGHT`, `INSET`, `ICON`; the bars'
heights and insets). A painted Android component then reads no Material number that is not a row.

### D3 — Specimens, drawn twice

A **specimen** is one component in one state at one size, with a scheme, a font scale and a direction: for example
`text-field/filled/focused/light/1.0/ltr`. A manifest lists them (`host/android/reference/specimens.json`), and each
is written twice:

- **in Compose**, in a Gradle module of the reader's build, `host/android/reference`. It is a library of
  composables, one for each specimen's component and state, with its tests and the Robolectric and Roborazzi
  dependencies. Nothing links it but its own tests and a debug APK that shows the catalogue on a phone;
- **in Contract**, as an Exact app, `apps/material-specimens`, whose routes are the same components written the way
  an author would write them in Exact's vocabulary (a `button` with a `buttonStyle`, an `input type="checkbox"`, a
  `header`, a `tablist`). It has a Linux crate, for headless drawing, and an Android crate, for the phone.

The pair is the claim that this Exact markup on Android is that Material component. A specimen with no
counterpart on either side fails, so the catalogue cannot drift into checking only what already matches.

### D4 — Where each side is drawn

| | the reference (Compose) | Exact |
|---|---|---|
| **JVM** (any machine with a JDK; the build box hourly) | Robolectric native graphics, through Roborazzi, at a fixed device configuration (411 × 891 dp, density 3) | the specimen app's Linux crate, headless: told the device, the palette and the clock; the Android look, not the neutral one |
| **Phone** (a Pixel; at each stage's end and each version bump) | the reference's debug APK, `screencap` | the specimen app on the reader, through `agent.mjs android --reader` |

The headless Linux host shows the neutral look today (`app::run_config` calls `show_neutral_look` before it
boots), so the specimen app's Linux crate needs a door the shells do not have: boot with the Android look, a
device and a palette given as a file. It is the specimen app's and the oracle's, not a host's: no shipped host
reads it.

On the JVM both sides are given the same font files and the same palette. The palette is a fixed set of schemes:
Material's baseline scheme, and two dynamic ones read from a Pixel's wallpapers. Each is used light and dark, and
handed to Exact by the door the reader uses (`presenter/palette.rs`). The JVM's answers are then a function of the
code and the version alone.

**Calibration.** The JVM draws Compose with Android's Skia, but not with the phone's fonts, its GPU or its
rasterization. So the first run of the reference on a Pixel is compared with its JVM run, specimen by specimen, and
the difference is the oracle's own noise floor. A specimen whose JVM and phone renders of the *same* Compose code
differ beyond that floor is checked on the phone only, and says so. The thresholds in D5 are starting values, to be
set from this measurement.

### D5 — What is compared

The oracle (`host/android/reference/oracle.mjs`) compares each specimen in five layers. Each fails on its own, so a
report says what is wrong and not only that something is:

1. **Geometry.** Each part's box: the component, its container, its label, its icon, its indicator. Compose's come
   from the semantics and layout trees (`boundsInRoot`); Exact's from the presenter's boxes. Equal to within 0.5 dp.
2. **Colour at named probes.** Points the manifest names for each component (the container's centre, the
   indicator, the label's ink, the thumb), sampled from both images. Within ΔE2000 2.
3. **Pixels.** A perceptual difference over the whole image, leaving out a one-pixel band along each edge, where
   two rasterizers' anti-aliasing differ. No more than 0.5 % of pixels past ΔE2000 5. This is the backstop for what
   the first two layers do not name, and the report's heat map is what a person or an agent looks at first.
4. **Accessibility.** Each node's class, name, state, actions and box. On the phone both sides are read the same way,
   as `AccessibilityNodeInfo` through `uiautomator`. On the JVM, Compose's semantics tree is compared with the
   presenter's accessibility statement (`presenter/access.rs`) through the class mapping D13 of 1115.001 uses.
5. **Motion.** For a specimen with a transition (a switch toggling, a label floating, a menu opening, a ripple), both
   clocks are stopped and frames are taken at the same times from the input to rest: Compose's `mainClock`, Exact's
   `clock`. Where a motion has a property to follow (a thumb's x, a scale, an alpha), that track is compared in
   values over time, which is steadier than frames. Otherwise the frames go through layers 1 to 3.

The report is JSON, for a script or an agent, and one HTML contact sheet with each specimen's two renders, their
difference and its failing layers.

### D6 — Paint or island

1115.001 D1.3 allows a component to be painted or to be a framework or library view, chosen per component. This
makes the choice a rule:

1. **What holds the author's content is painted.** A card, a list item, a sheet, a dialog, a menu: their insides are
   Exact nodes, and a Compose island cannot hold Exact nodes. When it is top layer it is painted into a window
   (1115.001 D10).
2. **What appears inline, repeats, or can be on a first screen is painted.** An island is an `AndroidComposeView`
   with its own composition. 1115.001.000 measured one inline bar at 19 to 34 ms to first draw, which is fine once
   and not per row, and Compose never runs on the launch path (1115.001 §5 Q3).
3. **What is modal and holds only its own content may be an island**, when its behaviour is most of the work (its
   own gestures, text entry, a structure of its own for TalkBack) and its cost is measured first. The pickers are
   the first (1115.001.000).
4. **What the framework owns is the framework's** in every case (1115.001 D1.2): `EditText`, `OverScroller`, windows,
   the system's Back.

An island is in the oracle too. Its drawing is the reference's own, so what the oracle checks is everything around
it: placement, scrim, colours from the reported scheme, the value written back, Back, and how it opens and closes.

The first assignments:

| Component (Compose Material 3) | Form | Why |
|---|---|---|
| `Button`, `FilledTonalButton`, `OutlinedButton`, `TextButton`, `IconButton`, `FloatingActionButton` | painted | inline, repeats |
| `Checkbox`, `RadioButton`, `Switch`, `Slider`, progress indicators | painted | inline, repeats |
| `TextField` (filled), `ExposedDropdownMenuBox`'s field | painted container round the framework's `EditText` | built (1115.001 D8, D9) |
| `TopAppBar`, `NavigationBar`, `PrimaryTabRow`, `SegmentedButton` | painted | structure, every screen |
| `ListItem`, `Card`, `HorizontalDivider`, `FilterChip`, `AssistChip`, `Badge` | painted | the author's content, rows |
| `AlertDialog`, `DropdownMenu`, `ModalBottomSheet`, `Snackbar` | painted, in a window where top layer | the author's content |
| `DatePicker`, `TimePicker` dialogs | island | built (1115.001.000) |
| `DateRangePicker`, `SearchBar`'s expanded view | open | `DateRangePicker` holds only its own; the search view holds the author's results (§5 Q5) |

### D7 — When a component is matched

A component is **matched at a version** when every one of its specimens passes all five layers on the JVM, and on
one Pixel in light and dark, at font scales 1.0 and 2.0, left to right and right to left. The component's file says
so in a line (`Matched: Compose Material 3 1.4.0, oracle 2026-10-…`), and `host/android/README.md` keeps the table.

Matching is work an agent can do in a loop. The brief for a failing component is the component's source at the
pinned version, its token rows, and the oracle's report; the agent changes the painter (`host/linux/src/paint/…`),
runs the oracle, and reads the report. CLAUDE.md's limit holds: three rounds, then stop and say what is left.

### D8 — Keeping up

When Compose Material 3 has a stable release:

1. One commit moves the pin, regenerates the token snapshot, and carries the token diff in its message: which tokens
   changed value, which appeared, which went. A token change alone names its components before anything is drawn.
2. The oracle runs on the JVM. What fails is the work list. Each component goes back to D7.
3. A Pixel run closes the bump.

Being a version behind is not a tell, since hand-built apps lag their pins too. Being a year behind is: a person who
knows Android notices a component that no current app shows. So the pin follows each stable minor release within
eight weeks (§5 Q3).

### D9 — Where it runs, and what it costs

- **The JVM oracle** runs in the async lane's second tier (hourly) on the Linux build box, beside its Android builds.
  It reports and does not block, like the tier's other checks (§5 Q4). It is not one of the six checks.
- **The phone run** is a lane's, under the phone lock, on the Pixels only.
- **A change to the Android look** runs the oracle for the components it touches before it lands, as advice, the
  way `contract-difftest quick` is for the semantics.
- **Cost:** the reference module and its test dependencies are in the reader's build and in no app's APK. The
  specimen app is one more app. The oracle needs a JDK, which the Android build already does.

## 3. Order of work

**O1, the slice: one comparison through every layer that does not need a phone.** On the build box:

- the token extractor and the `material` column for the rows the filled text field, the top app bar and the
  navigation bar read, with their constants moved;
- a manifest of about ten specimens: the filled text field (empty, filled, focused, disabled), the small top app
  bar, a navigation bar of three, a filled button, a checkbox, a switch;
- the reference module drawing them on Robolectric, and the specimen app drawing them headless;
- the oracle's geometry, colour and pixel layers, and its report.

O1 is done when the report runs from one command on a fresh checkout of the build box, and shows the text field and
the bars passing or failing with reasons. It is expected to show the button, the checkbox and the switch failing,
since they are not Material yet (1115.001 S2). That is the work list working.

**O2:** calibration on a Pixel (D4); the phone run for both sides. **O3:** the accessibility and motion layers.
**O4:** the hourly run in tier 2. **Then** 1115.001's S2 matches its components one by one through D7, and the
first version bump goes through D8.

## 4. Not in this document

- TalkBack's speech and its gestures: the oracle compares the tree a service reads, not what it says. 1115.001 D13's
  check by hand stands.
- Haptics, the keyboard, and anything else the framework owns (D6.4).
- The framework's own dialogs where Compose is not linked (1115.001.000 D1's fallback). They are the framework's
  and not a version's.
- Other hosts. The web's oracle is Chrome; iOS's is the system, which cannot be pinned.

## 5. Questions for Charlie

1. **The apparatus.** This adds a Gradle module (`host/android/reference`) with Robolectric and Roborazzi as test
   dependencies, an app (`apps/material-specimens`), and an oracle script. CLAUDE.md asks for a person's word before
   apparatus is added. *Proposed:* yes, all three; the reference module is in no app's APK.
2. **Which Material.** Material 3 1.4's default theme, or Material 3 Expressive, which Google's own apps ship and
   which is still experimental API in 1.4? *Proposed:* the default theme (D1). Expressive becomes the reference in
   the bump that makes it the library's default, and D8 then shows what it moves.
3. **How far behind.** *Proposed:* eight weeks after a stable minor release (D8).
4. **Does it block?** *Proposed:* no. It reports in tier 2, as the web's Firefox and WebKit steps do, and a matched
   component that regresses is a `QUEUE.md` line the same day.
5. **The search view.** The expanded `SearchBar` holds the author's results, so by D6.1 it is painted, but its
   transition and its field are most of its work. *Proposed:* painted, since the field is already the framework's
   `EditText`; revisit if its oracle report will not converge in D7's three rounds.
