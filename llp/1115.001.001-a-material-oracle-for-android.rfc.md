## 0. Summary

On Android, "the platform's look" is a library, and it has a version. Compose Material 3 ships inside each app that
uses it; OEMs do not restyle it, and a hand-built app shows the version it pinned. So Android is the one host where
Exact can be held to a reference that is a version number, its source, and what that source draws.

This RFC builds that check:

1. **Pins.** One Material version for painted components and islands alike, and one Android SDK level for what the
   framework draws (D1).
2. **Tokens read, not remembered.** The design values come out of that version's source by script, into a `material`
   column of the schema's `metrics` table, each row traceable to its symbol (D2).
3. **A reference and its oracle.** A catalogue of specimens is drawn twice: by Compose Material 3, on the JVM and on a
   Pixel, and by Exact, headless and on a Pixel. The oracle compares each component's geometry, colours, pixels,
   accessibility and motion (D3 to D5). Both sides are calibrated against the phone before a number gates anything.
4. **A rule for each component.** Exact paints what holds the author's content or appears inline; a Compose island
   shows what is modal and holds only its own (D6).

What changes: a component is "Material" when the oracle says it matches at a named version, not when someone remembers
the spec. Keeping up is a version bump, a token diff and a list of failing specimens (D8). Compose runs in the
reference and in the islands 1115.001.000 already links by use, and in no other shipped code.

## 1. Why, and what is there

1115.001 D1 made Compose Material 3 the reference; its §5 Q4 said a reference app would keep the look current. None of
that app exists. What is painted was built from the spec pages and memory, and the documents say so: the bars are
"Compose Material 3's `TopAppBar` and `NavigationBar` as remembered, not read against the library that day" (1115.001
§3, D11), and the menu's motion is "as Compose's `DropdownMenu` moved it (from memory)" (D10). The field's numbers are
constants in `paint/material.rs`, cited to m3.material.io. A Material release that moved any of them would go
unnoticed.

What makes a better answer cheap:

- **The library is pinned and bundled.** The reader's shell links BOM `2026.09.00` under `-Pcompose=1`
  (`host/android/app/build.gradle.kts`), and that BOM resolves `material3` to 1.4.0 (its POM on Google Maven).
- **Its tokens are data.** The `androidx.compose.material3.tokens` package is generated ("GENERATED CODE - DO NOT
  MODIFY BY HAND", each file headed with its token-set version, `v0_210` in 1.4.0) and is in the library's sources
  jar: 113 files in `material3-android-1.4.0-sources.jar`. They are not all of it. `FilledTextFieldTokens` has no
  height: the field's 56 dp is `TextFieldDefaults.MinHeight`, and a button's is `ButtonDefaults.MinHeight`, which is
  `ButtonSmallTokens.ContainerHeight`. Paddings, minimum sizes, paths and animation specs live in each component's
  `*Defaults` and private constants; the ripple and the 48 dp touch size live outside the library.
- **Exact's side can be drawn headless.** The Linux presenter has the doors: `Presenter::boot_with`, `set_device`,
  `Palette::tell`, `serve_bars` with a painter that keeps the bars' pictures (`presenter/bars_tests.rs` does this),
  `set_window`, `boxes`, `access_tree` and `clock`. What it lacks is a way to choose the Material look outside the
  reader (D4).
- **The repo works this way on the web.** `host/web-js/conform.mjs` holds the web target to Chrome by geometry, with a
  tolerance, and never compares pixels across engines. This oracle is stricter, since both sides here draw the same
  design on the same platform, and it has to earn that strictness by calibration (D4).

**Measured** (2026-10-18, `expo-build-1000`, a throwaway probe outside the repository): Compose Material 3 1.4.0 renders
under Robolectric 4.17's native graphics with Roborazzi 1.76.0 at SDK 36, about 6 s a run once Gradle is warm. It
needs Java 21 for SDK 36 and two JVM flags (`--add-exports` and `--add-opens` of `java.base/jdk.internal.access`), and
Roborazzi writes an image only in record mode. A filled button, checkbox, switch, filled text field, navigation bar,
elevated card and FAB drew as expected, in Roboto, with elevation shadows; the hardware capture mode
(`robolectric.pixelCopyRenderMode=hardware`) changed no pixel. The unmerged semantics tree gave each component's box
and its text's boxes, and nothing for a check path, a thumb, an indicator or a container.

## 2. Decisions

### D1 — The pins

One file, `host/android/gradle/libs.versions.toml`, holds:

- **The Compose BOM and the `material3` version it resolves**, both written, and a build check that they agree. The
  reader's islands, the reference module and the token extractor all read them there. A painted button and an
  island's picker in one app are never matched to two versions.
- **The Android SDK level of the reference**, which is the Pixels' (Android 16, API 36 today). Robolectric's
  `@Config(sdk=)` is it. The framework draws the ripple, the `EditText`, window animations and non-linear font
  scaling, so a reference at another level is another Android.
- **Robolectric and Roborazzi**, since their rendering is part of the oracle.

The reference is what a hand-built app gets by default: `MaterialTheme` and each component's defaults, on the device's
dynamic colours (1115.001 D1.1). Experimental APIs may be used where a stable one does not exist (the pickers opt in
today). Adopting the Expressive theme is a decision of its own, taken at a bump and recorded there, not something a
bump does by itself (§5 Q2).

### D2 — Tokens are read from the pinned source

1. **The extractor** (`host/android/reference/tokens.mjs`) reads the pinned sources jar, which Gradle resolves from
   Google Maven. From `tokens/*.kt` it takes each component's lengths, opacities, colour keys, shape keys and type
   keys. It resolves a shape key to its four corners in dp through `ShapeTokens`, and leaves a type key as a name
   (item 5). It fails on any value it cannot resolve rather than guessing.
2. **Values outside the tokens** come from the reference module at run time, not from parsing Kotlin: a JVM test
   reads each public `*Defaults` member the painter needs (`TextFieldDefaults.MinHeight`,
   `ButtonDefaults.ContentPadding`) and writes them beside the tokens.
3. **The palette door carries Material's whole scheme.** Today it carries twelve roles (`presenter/palette.rs`,
   `Palette.kt`). It grows to every role `ColorScheme` has, each named as Material names it, so a row whose colour is
   `onSecondaryContainer` or `outline` resolves on a device. The Exact roles 1115.001 D4 maps stay mapped; the new
   names are the Material look's own.
4. **The table.** `metrics` gains a `material` column beside `web`, `ios`, `mac` and `neutral`: `Column::Material`
   in `kernel/src/style/metrics.rs`, generated by `kernel/build.rs`, and chosen with `set_column` by the reader and
   by the specimen door (D4). Its cells are resolved values: dp, opacities, and Material role names for colours. A
   row's source is not a cell. It is a sidecar, `host/android/reference/rows.json`, mapping each row to its symbol:
   `FilledTextFieldTokens.FocusActiveIndicatorHeight`, `TextFieldDefaults.MinHeight`, or for a private constant the
   file and the declaration's name (`Checkbox.kt`, `StrokeWidth`), never a line number.
5. **Type is not tabled.** A text style follows 1115.001 D4's reported type ramp: size, line height, weight and
   tracking at the device's font scale, which is non-linear from Android 14. A row names the key (`BodyLarge`); the
   value is the device's.
6. **Constants become rows.** What the painter has as Material numbers (`paint/material.rs`'s `HEIGHT`, `INSET`,
   `ICON`; the bars' heights and insets in `presenter/bars/look.rs`; the dialog and menu numbers in
   `presenter/top/look.rs`) moves to rows as each component is matched (D7). Algorithms stay code: the check's path,
   a label's interpolation, a layout rule. Each is cited by symbol in a comment where it is written.

The whole token package and the read `*Defaults` are written per version to the build directory, not committed. The
extractor diffs two versions on demand (D8).

### D3 — Specimens, drawn twice

A **specimen** is one component in one state at one size, with a scheme, a font scale and a direction:
`text-field/filled/focused/light/1.0/ltr`. A manifest lists them (`host/android/reference/specimens.json`) with, for
each, the parts it names (container, label, indicator, icon), its colour probes, and its crop. Each is written twice:

- **in Compose**, in a Gradle module of the reader's build, `host/android/reference`: one composable per component and
  state, and the JVM tests that draw them. It also builds a debug APK that shows the catalogue on a phone. Nothing
  links it but these;
- **in Contract**, as an Exact app, `apps/material-specimens`, whose routes are the same components written as an
  author writes them in Exact (a `button` with a `buttonStyle`, an `input type="checkbox"`, a `header`, a `tablist`).
  It has a Linux crate, for headless drawing, and an Android crate, for the phone.

The pair is the claim that this Exact markup on Android is that Material component. A specimen missing on either
side fails, so the catalogue cannot drift into checking only what already matches.

### D4 — Where each side is drawn, and calibration

| | the reference (Compose) | Exact |
|---|---|---|
| **Build box** | Robolectric native graphics through Roborazzi, at the pinned SDK and the Pixel's density (`w411dp-h891dp-390dpi`, 2.4375) | the specimen app's Linux crate, native and headless, through the specimen door |
| **Phone** (a Pixel) | the reference's debug APK, captured whole | the specimen app on the reader, through `agent.mjs android --reader` |

**The specimen door.** The headless Linux host shows the neutral look (`app::run_config` calls `show_neutral_look`
before it boots), paints no bars, and has no windows. The specimen app's Linux crate boots differently: it chooses
`Column::Material`, tells a palette and a device, serves bars and windows to painters that keep their pictures, and
composites them over the page where the reader's views would show them. It is the specimen app's code over the
presenter's public doors; no shipped host has it.

**Inputs, held equal.** Each scheme is a fixed palette: Material's baseline, and two dynamic schemes captured from a
Pixel. Each is used light and dark, and told to Compose as a `ColorScheme` and to Exact through the palette door. Fonts
go one way: Robolectric's own (the `android-all` jar's Roboto and Noto) are given to Exact with `EXACT_FONTS`. Compose
is never handed a font, which would change the reference. Locale, density, window size and insets are the manifest's.
A focused field's caret is held shown on both sides.

**Calibration** comes before any threshold gates. On a Pixel, each specimen is drawn four ways: Compose on the JVM and
on the phone, and Exact headless and on the phone. For each layer of D5, the two Compose renders give the reference's
floor, and the two Exact renders give Exact's. Repeat captures of one render give the capture noise, separately. A
threshold is set from those floors, and holds only if two things stay true under it: independently captured valid
specimens pass, and every planted defect of O1 still fails. Where both cannot hold, that layer of that specimen is
checked on the phone only, and the manifest says so. A difference that is the same in every capture is systematic,
not noise: it is reported as a finding (a font, a rasterizer, a rounding) and never widened into a tolerance.

The `EditText` is the floor's sharpest case. On the phone a text field's value is the framework's, drawn by the
`EditText` (1115.001 D8); headless it is Exact's. Calibration measures that difference. Where it is above the floor,
the field's text is a phone-only observable, and the headless comparison holds the container, label and indicator.

### D5 — What is compared

The oracle (`host/android/reference/oracle.mjs`) crops each specimen to its component's visual bounds plus a margin
(16 dp, wide enough for a shadow), on both sides, and compares in six layers. Each fails on its own, so a report says
what is wrong.

1. **Geometry**, of three boxes, each as an offset and size from the component's origin:
   - the **layout box**: Compose's semantics `boundsInRoot`, Exact's node frame. A difference here is a finding, not a
     tolerance: Compose's `minimumInteractiveComponentSize` puts 48 dp into layout, and Exact's touch target does not
     enter layout (1115.001 D9). Whether Exact should follow is a ruling for S2, and the oracle makes it visible;
   - the **visual box**: the ink bounds in the crop, found from the image against the known ground, on both sides;
   - the **text boxes**: each text's line boxes, baseline and line count, from Compose's text layout result and, for
     text Exact draws, Exact's paragraph. A field's value on the phone is the `EditText`'s (1115.001 D8), so there
     its boxes come from the `EditText`'s own layout, through its padding, scroll and clip; headless, from Exact's.
   - the **touch box**: the area that takes a touch, on the phone, by the instrumented reader (item 5).
   Parts with no node on either side (a check path, a thumb, an indicator) are checked by probes and pixels.
2. **Colour at probes.** The manifest names points in flat interiors (the container's centre, the indicator's middle,
   the thumb's centre), sampled from both crops in sRGB. Within ΔE2000 2 to start.
3. **Text's appearance**, in each text box, since text is masked from the pixel layer: its **ink**, the colour of the
   pixels farthest from the ground there, which is the glyphs' colour at full coverage whatever the anti-aliasing;
   and its **coverage**, the summed distance of the box's pixels from the ground towards the ink, which is how much
   ink there is. A label in the wrong colour fails the first; a label left out, or drawn at a tenth of its weight,
   fails the second. The glyphs' own shapes are compared on the phone, where both sides' text goes through one
   rasterizer for the pixels the reader draws.
4. **Pixels**, over the crop: the share of pixels past ΔE2000 5, with each text's line boxes masked, since two shapers
   and two rasterizers place glyph edges apart. No edge band is masked: outlines and indicators are what is under
   test. Until calibration sets a threshold, this layer reports a heat map and does not fail.
5. **Accessibility**, on the phone: both apps read through one instrumented reader of `AccessibilityNodeInfo`.
   `uiautomator`'s dump lacks actions. Nodes correspond by the specimen's declaration: the manifest names each node a
   specimen has (the field, its label; the bar, its title, each destination) and how each side's is found (a tag in
   Compose, a `testId` in Exact). For each it compares the class, the name, the state, the actions, the box and the
   traversal order, normalized as `Access.kt`'s `kind()` maps Exact's roles, and it performs each action and compares
   the outcome (what changed in the tree, and where accessibility focus went, including back to the invoker when a
   surface closes). The JVM run checks nothing here.
6. **Motion.** On the JVM, only motion that Compose's clock drives and Exact's clock drives: a label floating, a
   switch's thumb, a check drawing in. Both clocks stop; frames are taken at the same times from the input to rest,
   and a property with a track (a thumb's x, a scale, an alpha) is compared as values over time. The ripple
   (`RippleDrawable`, on the RenderThread) and window animations (1115.001 D10's menu) are the framework's. They are
   compared on the phone as tracks against time elapsed from the input's own timestamp, each frame stamped by its
   presentation time, once the reader carrier can film (it cannot today: `agent-android.mjs` refuses `film`).

The report is JSON, for a script or an agent, and an HTML contact sheet with each specimen's two crops, their
difference, and its failing layers.

### D6 — Paint or island

1115.001 D1.3 allows each component to be painted or to be a framework or library view. The choice is made by these
rules, in this order:

1. **What the framework owns is the framework's** (1115.001 D1.2): `EditText`, `OverScroller`, windows, Back. A painted
   field's caret, handles and selection are the `EditText`'s, so the reader's theme gives them the scheme's colours
   (`primary`), as Compose's field shows them.
2. **What holds the author's content is painted**: a card, a list item, a sheet, a dialog, a menu. Their insides are
   Exact nodes. Compose could host Exact's view inside a component (`AndroidView`), but that is two layout systems
   around one box, and needs a reason this document does not have. Top layer is painted into a window (D10 there).
3. **What appears inline, repeats, or can be on a first screen is painted.** Compose never runs on the launch path
   (1115.001 §5 Q3), and an island has its own composition.
4. **What is modal and holds only its own content may be an island**, with its cost measured first. The pickers are
   (1115.001.000).

A red oracle is not a reason to change a component's form. An island is in the oracle too: its drawing is the
reference's own, so what is checked is everything around it (placement, scrim, colours, the value written back, Back,
opening and closing).

| Component (Compose Material 3) | Form |
|---|---|
| `Button`, `FilledTonalButton`, `OutlinedButton`, `TextButton`, `IconButton`, `FloatingActionButton` | painted |
| `Checkbox`, `RadioButton`, `Switch`, `Slider`, progress indicators | painted |
| `TextField` (filled), `ExposedDropdownMenuBox`'s field | painted container round the framework's `EditText` (built) |
| `TopAppBar`, `NavigationBar`, `PrimaryTabRow`, `SegmentedButton` | painted (bars built) |
| `ListItem`, `Card`, `HorizontalDivider`, chips, `Badge` | painted |
| `AlertDialog`, `DropdownMenu`, `ModalBottomSheet` | painted, in a window |
| `Snackbar` | painted; not modal, in the page's top layer, with its own lifetime |
| the expanded `SearchBar` | painted: it holds the author's results (rule 2) |
| `DatePicker`, `TimePicker` dialogs | island (built) |
| `DateRangePicker` | island when built (rule 4) |
| `PullToRefreshBox`'s indicator, `BottomAppBar`, `NavigationRail` | painted when built; not in the first catalogue |

### D7 — When a component is matched

A component is **matched** when each of its specimens passes every layer that applies to it: geometry and probes on
the build box, and on one Pixel all six layers in light and dark, left to right and right to left. It is matched at
an identity, written into the report as a fingerprint: the resolved Compose dependency graph (Material, UI,
Foundation, the ripple), the SDK level and the phone's Android build, Robolectric's and its native runtime's versions,
the capture mode, the font files' digests, the specimen manifest's revision and Exact's commit. The component's file and
the README's table name it. A regression under any of them revokes the claim.

States in the catalogue are those the component has: enabled, disabled, pressed, focused, selected and its error
state, and an authored override (an `accent-color`, a size) to show the author's word wins. Text-bearing specimens
also come with a label that wraps, and in a right-to-left script (Arabic) as well as mirrored; moving specimens with
reduced motion. Text-bearing specimens are
run at font scale 2.0 too, and are expected to fail there until the reported type ramp lands (1115.001 S2): Exact scales
text linearly today and Android 14 does not.

Matching is a loop an agent can run. The brief for a failing component is its source at the pinned version, its rows
and symbols, and the oracle's report. The agent changes the painter, runs the oracle, and reads the report. Three
rounds, then it stops and says what is left (CLAUDE.md).

### D8 — Keeping up

When Compose Material 3 has a stable release:

1. One branch moves the pin and runs the extractor's diff against the old version: which tokens and read `*Defaults`
   changed value, appeared or went, and the source diff of each component the catalogue holds, since a component's
   code can change while its tokens do not. Both are files beside the report. A changed value names its components
   before anything is drawn.
2. The oracle runs. What fails is the work list, and each component goes through D7.
3. The bump lands with its fixes, or it lands with the matches it breaks revoked by name. A pin and a "matched" that
   disagree are never both on main.
4. A Pixel run closes it. A change of the SDK pin, Robolectric or Roborazzi recalibrates (D4).

The pin follows each stable release as quickly as it can (§5 Q3: "ideally, within the hour of release"). So steps 1
and 2 are unattended: each hour the build-box job (D9) asks Google Maven for a stable `compose-bom` or `material3`
newer than the pin, and on finding one moves the pin on a branch, writes the diff, runs the oracle and files the work
list. The work list therefore exists within the hour; what takes longer is the work, and step 3 holds while it is
done. A hand-built app lags its pin too, so the hours between a release and its fixes are not a tell; a year would be.

### D9 — Where it runs, and what it costs

- **The build-box run** is a new job on the Linux build box (`expo-build-1000`, which has the SDK, the NDK and network
  to Google Maven and Maven Central). It runs hourly when a commit touches the Android look, the reference, the
  specimens or the pins, and each hour it asks Google Maven for a new stable release (D8). The job fails, and files an issue, when a matched component regresses; landing is never
  blocked by it, and it is not one of the six checks. Its owner is whoever holds 1115.001 S2; its budget, warm, is
  five minutes for the whole catalogue. It needs Java 21, the Android SDK at the pinned level, and the `android-all` jar for that
  level (fetched once). Warm, the reference's run is seconds; a cold first run is minutes.
- **The phone run** is a lane's, under the phone lock, on the Pixels only.
- **A change to the Android look** runs the oracle for the components it touches before it lands, as advice, as
  `contract-difftest quick` is for the semantics.
- **Cost:** the reference module and its test dependencies are in no app's APK. The specimen app is one more app. The
  catalogue file, the manifest and the sidecar are the only committed data; snapshots and reports are build output.

## 3. Order of work

**O1, the instrument.** On the build box, before the catalogue grows:

- the pins file (D1); `Column::Material` and the palette's whole scheme (D2.3, D2.4), for the rows O1 uses;
- the specimen door (D4), with bars and windows;
- five components: the filled text field (empty, filled, disabled, focused with the caret shown), the small top app
