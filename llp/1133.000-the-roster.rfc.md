# LLP 1133.000: The roster — every standard module, ranked

**Type:** RFC
**Status:** Accepted (Charlie, 2026-10-18: "recs mostly look ok"), as r2 with the rulings of §7. Each module gets its own RFC (LLP 1133.002 onward) when it is next to build; this document decides only what exact2's library holds and in what order. r2's order is from a blind panel (GPT-6 Astra at max, Claude Fable 5.1 and Grok 4.7 at xhigh).
**Systems:** as LLP 1133
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-10-18
**Parent:** LLP 1133 (the standard library: three tiers, the ceiling test, the checklist D9)
**Related:** LLP 1069 (the Expo survey; its §5 ranking, which this replaces); LLP 1124 (host extensions, the seam); LLP 1133.001 (packages: interfaces, implementations, hosts, distribution); `rules/DEFERRED.md` (each module's move, §5)

## Summary

The library should eventually hold about seventy modules. Nineteen exist
today in some form, built one at a time under LLP 1069, 1096, 1098 and
1125; they join the library as they are (§2). Fifty-five more are listed
in eleven areas (§3), and three waves set their order (§4):

- **Wave 1, the design's proof, one module at a time, each with an app
  that uses it:** geolocation (Weatherlight), which builds the seam it
  needs (LLP 1124 and LLP 1133.001) as it goes; notifications completed
  (a Caltrain departure reminder and the apps outside the repo); camera
  (the photo editor); recording (the recorder). Each tests what the one
  before cannot: data-code bindings and a light object, delivery while the
  app is closed, views and a heavy object's hatches, an app's own module
  becoming a package.
- **Wave 2, what most shipped apps need:** biometrics and keychain access
  control, passkeys and sign-in, speech, motion, purchases, the on-device
  language model, push.
- **Wave 3, the long tail,** in small batches by area: background work,
  contacts, calendar, photos, maps, Bluetooth, intents and Spotlight, the
  desktop's own pieces, health, game controllers, vision, and more.

A last group stays out of the library for now and is left to apps through
tier 3 and their own modules (§3.13). The library aims at seven targets
(LLP 1133 D8), filled in as practical; a module ships when its consumer's
targets work.

## 1. How modules are ranked

In order:

1. **A consumer** in or beside the repo that needs it now (`apps/`, the
   ports' diaries). The consumer is the module's acceptance drive.
2. **How common it is in shipped apps,** by the Expo SDK, the most used
   React Native and Flutter plugins, and each platform's own catalog (the
   survey behind this roster, summarised in §6).
3. **What it proves.** Early modules are chosen to test LLP 1133's tiers
   where they are most likely to fail, so that the design is amended before
   many modules depend on it.
4. **Cost against `DEFERRED.md`:** what each needs moved (§5).

Each module is named by its tier 1 surface where it has one. "Built" means
reachable by an app today on the hosts listed (an inventory of 2026-10-18,
by code).

**Open a URL: declared schemes (Claude, 2026-10-22, for the T3 Code
clone's "Open in editor").** `openURL` also opens a URL whose scheme the
app lists in app.json's `open_url.schemes`, such as an editor's deep link
(`vscode://vscode-remote/ssh-remote+host/path`, `zed://ssh/host/path`,
`jetbrains://gateway/ssh/environment?h=host`). The list is the manifest's,
as Android's `<queries>` and iOS's `LSApplicationQueriesSchemes` declare the
schemes an app reaches, so a link out of content the app did not write still
fails closed: an undeclared scheme is refused as before. The manifest
refuses the schemes the hosts handle themselves (`doc`, `app`,
`app-settings`, and the four already open) and those that run or read
content (`file`, `filesystem`, `javascript`, `vbscript`, `data`, `blob`,
`about`, `view-source`, `jar`, `intent`, `content`); the hosts refuse the
second set again whatever a bundle carries. `sms` may be declared: it opens
the system's composer, as `mailto` does. The web's JS target, macOS and iOS
open a declared scheme with whatever is registered for it (a browser asks
first), and journal an open the system could not perform; under the agent
it is journaled, not opened. A link (`href`) of a declared scheme differs
by host, and is recorded as a difference: macOS and iOS hand every
followed link to `openURL`, so it opens; the web keeps its link policy's four schemes,
checked when the page is compiled and again when it writes a bound
`href`, so it writes none. Admitting declared links on the web needs the
manifest's list in the JS target's compiler as well as its runtime. Linux and Windows journal
`openURL` as unsupported, as they do for every scheme, and the wasm web
host, which development's native forwarding alone runs, reads no
declaration and keeps the four.
Electron's `shell.showItemInFolder` (reveal a file in Finder) is not
admitted with it: it has no web name, and the files it would show are a
`storage.fs` path or a `doc:` handle, a new data-capability operation on
every executor, which waits for its own RFC beside LLP 1133.000 §3's
desktop-process work.

Files, SQLite, key-value, secrets, fetch and crypto are **data
capabilities** (LLP 1133 D5): a TypeScript or Rust source reaches them in
its answer, and their values never enter Contract. The rest are Contract's.

So the library already has about a third of Expo's surface. What it lacks
is mostly in Wave 1 and 2: location, sensors, the camera, biometrics,
purchases, push, speech, background work.

## 4. The order

### Wave 1 — the design's proof, in this order

1. **geolocation.** The cleanest web API with the widest gap below it
   (precise and approximate authorisation, activity types, Android's
   priorities). Consumer: `apps/weatherlight`'s "Use my location", whose
   forecast already takes coordinates (`app.contract`, `forecast(lat, lon,
   revision)`); approximate location is its tier 2 word, and its `app.ts`
   is the first data-code binding (LLP 1133 D6). Its permission state is
   its own fact. Its slice builds only the seam it uses:
   - of LLP 1124 and LLP 1133.001: the package format, module names in
     `use`, the binding per target, Swift and Kotlin from a package, the
     runner's inspection of native bodies, the TypeScript binding (a Rust
     binding through a fixture), the `bun.lock` check, and deploy installing
     before it asserts the Cargo closure;
   - the two public-seam tests (LLP 1133.001 D8): the module packed and
     installed into an app outside the repo builds unchanged, and a fixture
     implementation outside the tree replaces the endorsed one for one
     target and answers a real call;
   - on Android, what every later module needs there: the native-module
     slot an Android app does not have, the grant table's Android column,
     and a check that compiles the Android target. Android may land after
     web and Apple; the next module is not accepted until it does.
2. **notifications, completed.** Actions and replies, repeats, the badge,
   Android and Windows; delivery while the app is closed, which LLP
   1069.007 D7 says no rule covers yet, so its RFC proposes one. Consumers:
   a departure reminder with a Snooze action in `apps/caltrain`, the drive
   on each target, and the Habits, Dash and T3 Code reminders outside the
   repo (`DEFERRED.md`'s notifications entry). Push registration is
   designed here (§3.6).
3. **camera.** The heaviest native object (a session, a preview view and
   calls sharing one instance) and the hardest tier 3. It needs packages to
   carry views (LLP 1133.001 D1). Still capture first. Consumer:
   `apps/photo-editor`, which edits a fixed image through its own module:
   capture, then edit, testing a standard module beside an app's own.
4. **recording.** `apps/recorder`'s own microphone module made a package:
   the path a third party takes. Consumer: the recorder.

### Wave 2 — what most shipped apps need

In this order unless a consumer reorders it: **local-auth** (with secrets'
access control), **passkeys** and **sign-in**, **speech**, **motion**,
**purchases** with **store-review**, **language-model**, **push**.

### Wave 3 — the long tail, by area

Each batch is one area of §3, ordered by consumer when one appears:
background work and transfers; contacts and calendar; photos and image;
maps, geofencing and geocoding; Bluetooth and gamepad; intents, search
index and quick actions; share target, clipboard, in-app browser, compose
and print; the desktop's four; health, pedometer and altimeter; vision and
translation; attestation and age range; screen; alarms; device.

### The other targets of the seven

The built modules' missing cells (§2: Android's page facts, picker,
documents, sounds, media session and App Links; Linux's and Windows'
clipboard and links) are a queue, filled in the order apps ask for them
and never ahead of the wave. Expose's cells start when it is a host.

## 6. The survey behind it

The candidate list came from the Expo SDK 58 package list, the most used
React Native and Flutter plugins, the web's capability APIs (W3C and
WICG), Apple's and Android's capability frameworks, WinRT, and
xdg-desktop-portal's interfaces, deduplicated to 82 capability areas on
2026-10-18. Every area is in §2, §3 or §3.13. The areas where a single
cross-platform API would lose the most were background execution, widgets
and live status, system intents, health, purchases, haptics, hardware
buses and notification semantics; each of those modules lists in its row
what tier 2 must reach.

## 7. Rulings (Charlie, 2026-10-18)

"recs mostly look ok":

1. **The waves** as §4: geolocation, notifications, camera, recording;
   the seam built by geolocation's slice, not as a wave of its own;
   `device` and a `permissions` facade wait for an app.
2. **Consumers:** Weatherlight, Caltrain's reminder and the outside apps,
   the photo editor, the recorder.
3. **Left to apps (§3.13):** all of it for now; game services is watched.
