# LLP 1054.000.005: `trim` in the roster

**Type:** RFC
**Status:** Draft
**Systems:** Roster (`plan/tables/format.json` `stdlib`, `runner/src/stdlib.rs`)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-26
**Related:** LLP 1054 (the Bluesky port); LLP 1054.000.003 (dates and numbers in the roster, the same review round); LLP 1005 §5 and LLP 1004 D6 (the roster: added by fixture); LLP 1006 §3 (`fn`); LLP 1027.001 (language parity)

## Summary

Add one core roster entry: `trim(text: string) -> string`. It returns `text`
without leading or trailing whitespace, exactly as JavaScript's
`String.prototype.trim` does, on every host.

## Motivation

A send or post button that is disabled on an empty draft should also be
disabled on a draft of spaces or newlines. Contract can't say so:

- **Bluesky** (outside the repo). The chat send button is
  `disabled=(draft == "")` (`chat.contract:93`), and compose is
  `disabled=(busy or (draft == "" and quoteText == "" and quoteName == "") …)`
  (`sheets.contract:76`). A draft of three spaces enables both. The data
  crate then sends a blank message, or refuses it after the tap.
- **Messages** avoids the same bug by computing `canSend` in TypeScript with
  `!!body.trim()` (`apps/messages/app.ts:416`). That puts a view's enabled
  state in the data source, which re-answers on every keystroke of the draft.

A `fn` can't do it. Trimming needs to look at characters one by one until it
reaches a non-space, and a `fn` is one expression with no loop and no string
indexing (LLP 1006 §3). The roster has `length`, `isEmpty`, `contains` and
`toString` for strings, and nothing that inspects characters.

## Design

### D1 — `trim(text: string) -> string`

Removes every leading and trailing code point in ECMA-262's *WhiteSpace* and
*LineTerminator* sets:

- U+0009, U+000A, U+000B, U+000C, U+000D, U+0020
- U+00A0, U+1680, U+2000–U+200A, U+2028, U+2029, U+202F, U+205F, U+3000
- U+FEFF

That is JavaScript's set, not Rust's. `char::is_whitespace` (Unicode
`White_Space`) also strips U+0085 (NEL) and does not strip U+FEFF. Measured
with `node -e`: `"\u0085x\u0085".trim()` keeps both NELs, and
`"\ufeffx\ufeff".trim()` strips both. So the body is a 25-entry match, not
`str::trim`. U+200B (zero width space) and U+180E are in neither set and stay.

Where the input has no whitespace at either end, the answer is the same
`Rc<str>`, so a hot binding doesn't allocate.

### D2 — Core, not a linked capability

It is a few dozen bytes of code, with no tables beyond the match. LLP 1047's
linked tier is for code worth a seam. `contains` and `length` sit in the
same place.

### What an app writes

```
button press=send disabled=(trim(draft) == "") …
```

## Costs

- **Plan format.** One `stdlib` row. `FORMAT_DIGEST` changes, which is why
  this travels with LLP 1054.000.003: one re-bake and one update cohort for
  both, not two.
- **Runner.** About 15 lines and a unit test.
- **No compiler code.** The signature is plain `string -> string`, which the
  type checker takes from the table (`contract/types/src/lib.rs:678`).

## Tests

- **Oracle.** A table of about 40 strings, generated with Node, covering each
  code point in the set at each end, U+0085, U+200B and U+180E, interior
  spaces, the empty string, all-whitespace strings and astral characters.
  The runner's output must match `String.prototype.trim` exactly.
- **Identity.** An untrimmed-already input returns the same `Rc`.
- **A driven check.** In a Contract fixture, a button disabled on
  `trim(draft) == ""` stays disabled after typing three spaces.

## Refused, with the trigger

- **`trimStart`/`trimEnd`, `upper`/`lower`, `split`, `replace`, `slice`,
  regular expressions.** None has a fixture. Casing for display is CSS
  `text-transform` (LLP 1053, add now). Truncation is `line-clamp` and
  `text-overflow`. Anything that splits or rewrites text is data-source work.
  The trigger for any of them is a view-only need, demonstrated in source.
- **Grapheme length.** Bluesky's compose also refuses `length(draft) > 300`,
  but `length` counts UTF-16 units (`stdlib.rs:70`), while Bluesky's limit is
  300 graphemes. An emoji with a skin tone counts 4 and a flag counts 4.
  Counting graphemes needs segmentation tables, tens of kilobytes. Noted
  here as a finding, not proposed: the data source can answer it, with
  Hermes's `Intl.Segmenter` or a Rust segmenter.
