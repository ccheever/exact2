# LLP 1070.000: Scrolling a virtualized list to a row by key

**Type:** RFC
**Status:** Accepted in direction (Charlie, 2026-09-27: "approved a follow-on … scroll-to-row"); instant positioning built on the web, macOS, iOS and Linux (§10)
**Systems:** Contract (`contract/types/src/checks.rs`, `contract/lower`), Runner (`runner/src/instance/collection/`, `runner/src/runner/commit.rs`), hosts' agent carriers (a `tap` form)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Implementer:** the `feat/horizontal-lists` Claude lane, 2026-09-27, after LLP 1070 stage 4
**Related:** LLP 1070 (§4.2's kept position is the same mechanism, run on request), LLP 1050.000 D1 (a jump's destination is owed), LLP 1010 §6, LLP 1012 (the agent's nine operations), `llp/reviews/1070-scroll-to-row.astra.md` (dispositions in §9)

## Summary

A virtualized list cannot be told to show a row. An app can write `scrollTop` in pixels, and with variable heights a pixel does not land on row n (`~/bench/xheavy/EXACT2-GAPS.md`: `BENCH_START_INDEX` answers the feed *from* row n instead). The web's answer on an ordinary page is `Element.scrollIntoView()`; a virtualized list must give the same result for a row that may not exist yet.

This adds one host command, `scrollIntoView`, run by the runner:

```contract
action show(id: string) writes shown
  shown = id
  scrollIntoView("feed", id, block="center")
action showCard(post: string, card: string) writes shown
  shown = card
  scrollIntoView("strip", card, row=post, inline="center")
```

The oracle is `scrollIntoView` on the same page unvirtualized: the target's box lands where Chrome puts it, within half a pixel.

## 1. Surface

- **A host command**, beside `focus("id")`, which already names an element by its HTML `id`. The first argument is a virtualized list's `id`; the second is the row's **key**, the value its `each … key=` evaluates to, never a position (keys survive inserts and removals; indices stay inside the runner).
- **Options are named arguments** (`name=value`, as `share(title=, text=, url=)` takes its members), with the web's names and values (`ScrollIntoViewOptions`):
  - `block`: `"start"` (the default, as the web's), `"center"`, `"end"`, `"nearest"`, applied by every vertical scroller between the target and the list;
  - `inline`: the same values, default `"nearest"`, applied by every horizontal scroller (a row list's main axis is `inline`, as a carousel's is on the web);
  - `behavior`: `"auto"` (the default) or `"instant"`. `"smooth"` is refused by name until §6's second step: a long smooth traversal needs its own fill policy.
  - `row`: for an inner list (LLP 1070 N6), the outer row's key. The inner list's `id` names its template site; `row` names which instance. An inner list with no `row` is refused.
- **Checked in the compiler** (the new id `type-scroll-into-view`): the list id a string literal, a key, the option names and literal values, and `smooth` refused. Whether a virtualized list has that `id`, and whether it is an inner one needing `row`, is resolved when the command runs, and a miss is refused observably (§2.2).
- **No focus change**, as the web's `scrollIntoView` changes none. Reduced motion needs no policy: there is no animation yet.

## 2. What the runner does

1. **Resolve.** Find the list by id. For `row`, find the outer list, and the outer row by key.
2. **Refuse observably** a key not in the list's items (fetching more is the app's job), a key the list holds twice (the collection disambiguates duplicates by position; a request for one is ambiguous), a missing list: the command is journaled with its reason and `state.scrollIntoView` records `refused`.
3. **Prepare, in the same commit.** For an inner target, the outer list first builds the outer row's window as for a jump (the row owed, LLP 1050.000 D1); the inner list, created with the row or already there, then builds the target's window. Each scroller's destination is computed from the index: the target's start and size, aligned to the port by `block` or `inline` (`nearest` does nothing if the target already shows whole). The window is realized at the destination before any host moves, and a correction carries the destination offset, so the frame that first shows the destination shows its rows (never blank).
4. **Measure and correct.** Each report recomputes the destination from what is now measured, where the host says the port is, and corrects when the port is elsewhere. Success is the target's box within 0.5 px of its aligned place (clamped at the list's ends) on two reports running, with every mounted row up to the target measured and the window whole; while it is pending the list asks for its next report. At most 6 correcting reports; after that the request ends `unconverged`, and the list stays where it is.
5. **Lifetime.** A newer request on the same list replaces it; the reader's own travel (two reports running that carry a velocity: hosts sample it from a drag, a fling or a wheel, and no longer from a correction) cancels it and discards its remaining corrections; the target's key leaving the items cancels it; the list's destruction ends it. Neither the report's offset nor its sequence is the signal: a browser clamping the port when the window's extent changes moves both. While it is pending it overrides the list's kept position.

## 3. Nested lists

`row` addresses an inner list through its outer row. Both scrollers align: the outer one brings the outer row into view by the option for its axis (`block` for a vertical feed), the inner one the target (`inline` for a strip). This is what `scrollIntoView` on the unvirtualized page does: every scrollable ancestor aligns the target's own box (the outer row is aligned to the target's box's block extent, which, for a strip inside a row, is the strip's). Ordinary (eager) scrollers and the page between them are not moved: a virtualized list inside an ordinary scroller aligns in its own port only, a declared difference from the web, where the page would scroll too.

## 4. The target's box

The authored row root's border box, as the web aligns the element's: the runner's row wrapper encloses the root's margins, and the root's literal margins on the list's axis are taken off. `scroll-margin` and `scroll-padding` are not built: no consumer asks yet, and a sticky header over a list is written today as a sibling outside the list's port.

## 5. The agent

No tenth operation (`rules/DEFERRED.md`): a form of `tap` on a mounted list, `tap <list testId> into <key> [block <value>] [inline <value>]`, runs the same runner request (an inner list not mounted is reached through its outer list, or by the app's command with `row=`). Its outcome is in `state.scrollIntoView` (`{list, key, status}`, status `done`, `unconverged`, `refused: reason`, `cancelled`), and `clock settle` drains its corrections.

## 6. Staging

1. **Instant positioning** (this change): the command, the runner request, nested addressing, the agent form, the fixture and Chrome parity.
2. **Smooth**, only with a consumer: the platform's own scroll animation between an origin and a destination, with an explicit traversal policy (rows between the two are not built; what shows mid-flight is owed, as a fling's is) and the web's declared limitation (the browser's smooth scroll cannot wait for rows).

## 7. Acceptance

- Chrome parity: `apps/carousel` targets a feed row, a card in a strip, a message in an inbox, the first and last rows, with each `block`/`inline` value, cold (far from the mounted window); the target's box equals the unvirtualized page's after the browser's `scrollIntoView` on the same element.
- Bounded: mounted rows after a cold jump are the destination's window, not the path.
- Mutation and interruption: a request followed by an insert above the target, by the target's deletion, by a reader's scroll; a duplicate key; a missing key.
- Then xheavy's jump scenario uses it (`BENCH_START_INDEX` through the command, not the data source).

## 8. Not done

Smooth behaviour (§6.2); `scroll-margin`/`scroll-padding`; scrolling ordinary ancestors of a virtualized list; RTL row lists (LLP 1070 §3.2); `container: "nearest"` (the web's newer option: every request already stops at the list's ports).

## 10. As built (2026-09-27, `feat/horizontal-lists`)

- **Contract:** `scrollIntoView("list-id", key, block=, inline=, behavior=, row=)` with `type-scroll-into-view`; `smooth` refused.
- **Runner:** the command is the runner's own, run in the action's commit after its update; `Runner::scroll_into_view` and the agent's `tap <list> into <key>` on the web, macOS, iOS and Linux; `state.scrollIntoView` lists each list's latest request and refusals. Runner tests (`contract/cli/tests/it/collection_into_view.rs`): a cold jump centred on its measured size with the destination's window only, the last row at the end, a missing key refused, a reader's travel cancelling, and a card in a strip in a row far away.
- **Parity:** `apps/carousel`'s feed, eight requests (rows centred, at the start, the last row at the end; a card centred in a strip; a message centred in an inbox; `nearest` on a shown message). **macOS, iOS and Linux:** every target's box aligned in its port as the web defines it, within 0.5 px (0 of 8 off each). **The web:** 10 of 10 boxes equal Chrome's `scrollIntoView` on the unvirtualized page, both requests `done`, three runs running (2026-09-28). Three causes kept it apart until then, all in `host/web/collection-glue.js`: (1) the browser clamps the port when a row laid out smaller than its estimate shortens the extent at the end, and the glue took the clamp for the reader's scroll (a new sequence, which voided the runner's correction, and travel, which led the fill upward one row a report); a clamp is now no scroll, and the report carries the offset the painted frame had, the coordinates the runner anchors in; (2) while a request seeks (`seeking` in its snapshot) its corrections are authored moves, applied whatever the port did since, and its moves are not travel, until the reader's own `wheel`, `touchstart`, `keydown` or `pointerdown` on the port, whose travel then cancels it (§2.5); (3) the agent's `clock settle` built a slice a report and visited four lists a round, so a request ended the settle mid-way; it now ends motion, builds what each report owes whole and visits every list, as the native pumps do.
- **Not built:** smooth (§6.2); `scroll-margin`/`scroll-padding`; xheavy's jump scenario still answers from row n (`QUEUE.md`).
