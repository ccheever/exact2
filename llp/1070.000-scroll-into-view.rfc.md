# LLP 1070.000: Scrolling a virtualized list to a row by key

**Type:** RFC
**Status:** Accepted in direction (Charlie, 2026-09-27: "approved a follow-on … scroll-to-row"); instant positioning built on the web, macOS, iOS and Linux (§10)
**Systems:** Contract (`contract/types/src/checks.rs`, `contract/lower`), Runner (`runner/src/instance/collection/`, `runner/src/runner/commit.rs`), hosts' agent carriers (a `tap` form)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Implementer:** the `feat/horizontal-lists` Claude lane, 2026-09-27, after LLP 1070 stage 4
**Related:** LLP 1070 (§4.2's kept position is the same mechanism, run on request), LLP 1050.000 D1 (a jump's destination is owed), LLP 1010 §6, LLP 1012 (the agent's nine operations), `llp/reviews/1070-scroll-to-row.astra.md` (dispositions in §9)

## Summary

A virtualized list cannot be told to show a row. An app can write `scrollTop` in pixels, and with variable heights a pixel does not land on row n (`~/bench/xheavy/EXACT2-GAPS.md`: `BENCH_START_INDEX` answers the feed *from* row n instead). The web's answer on an ordinary page is `Element.scrollIntoView()`; a virtualized list must give the same result for a row that may not exist yet.

This adds one host command, `scrollIntoView`, run by the runner:

```contract
action show(id: string) writes shown
  shown = id
  scrollIntoView("feed", id, block="center")
action showCard(post: string, card: string) writes shown
  shown = card
  scrollIntoView("strip", card, row=post, inline="center")
```

The oracle is `scrollIntoView` on the same page unvirtualized: the target's box lands where Chrome puts it, within half a pixel, for a request made with the port at rest; one that meets the reader's hand or scroll is admitted as §2.6 says, by what the host's jump does to the reader's momentum.

## 1. Surface

- **A host command**, beside `focus("id")`, which already names an element by its HTML `id`. The first argument is a virtualized list's `id`; the second is the row's **key**, the value its `each … key=` evaluates to, never a position (keys survive inserts and removals; indices stay inside the runner).
- **Options are named arguments** (`name=value`, as `share(title=, text=, url=)` takes its members), with the web's names and values (`ScrollIntoViewOptions`):
  - `block`: `"start"` (the default, as the web's), `"center"`, `"end"`, `"nearest"`, applied by every vertical scroller between the target and the list;
  - `inline`: the same values, default `"nearest"`, applied by every horizontal scroller (a row list's main axis is `inline`, as a carousel's is on the web);
  - `behavior`: `"auto"` (the default), `"instant"` or `"smooth"` (§11).
  - `row`: for an inner list (LLP 1070 N6), the outer row's key. The inner list's `id` names its template site; `row` names which instance. An inner list with no `row` is refused.
- **Checked in the compiler** (the new id `type-scroll-into-view`): the list id a string literal, a key, the option names and literal values. Whether a virtualized list has that `id`, and whether it is an inner one needing `row`, is resolved when the command runs, and a miss is refused observably (§2.2).
- **No focus change**, as the web's `scrollIntoView` changes none. Under Reduce Motion every smooth correction lands at once on iOS and macOS, a keyed request's and a `scroll-behavior: smooth` list's end-follow (§11) alike, as an element's reveal does (§14).

## 2. What the runner does

**Terms.** A request is *admitted* when its window is built at its destination and the host is told to move there. It *lands* when the port reaches the destination: at once for an instant request, when its animation ends for a smooth one. It *completes* (`done`) when it has landed and §2.4 finds the target aligned and measured on two reports, or, having made no move, when the port already satisfies it (§2.6). `done`, `cancelled`, `unconverged` and `refused` are final. Each request a list begins has its own number; a host tells a request from the one before it by that number.

1. **Resolve.** Find the list by id. For `row`, find the outer list, and the outer row by key.
2. **Refuse observably** a key not in the list's items (fetching more is the app's job), a key the list holds twice (the collection disambiguates duplicates by position; a request for one is ambiguous), a missing list: the command is journaled with its reason and `state.scrollIntoView` records `refused`.
3. **Prepare, in the same commit.** For an inner target, the outer list first builds the outer row's window as for a jump (the row owed, LLP 1050.000 D1); the inner list, created with the row or already there, then builds the target's window. Each scroller's destination is computed from the index: the target's start and size, aligned to the port by `block` or `inline` (`nearest` does nothing if the target already shows whole). The window is realized at the destination before any host moves, and a correction carries the destination offset, so the frame that first shows the destination shows its rows (never blank). A request that waits (§2.6) is prepared when it is admitted instead.
4. **Measure and correct.** Each report recomputes the destination from what is now measured, where the host says the port is, and corrects when the port is elsewhere. Success is the target's box within 0.5 px of its aligned place (clamped at the list's ends) on two reports running, with every mounted row up to the target measured and the window whole; while it is admitted and pending the list asks for its next report (one that waits asks only as §2.5 and §2.6 say). At most 6 correcting reports; after that the request ends `unconverged`, and the list stays where it is. A request that waits is measured and corrected from its admission; waiting uses none of the six.
5. **Lifetime** (2026-10-30 and 2026-10-31, James). A request keeps its key, its alignment (or §13's row-relative offset), its behaviour and, for a nested request, its outer row; never a destination in port coordinates.

   - A newer request on the same list replaces it. The list's destruction ends it. The target's key leaving the items cancels it at once.
   - A gesture the reader begins after the request reached the host, in the list or able to move its port, cancels it: a touch, a pointer press and, where the host tells a new one from momentum, a wheel (§2.6 gives each host's). A key is no gesture: what it scrolls is motion like any other. An input counts by its own timestamp against the request's arrival: a request a handler makes in answer to it is not cancelled by it, and a finger already down when the request came is no gesture against it (its drag is the reader's scroll, next item). UIKit's animated scrolls stop at a new touch, a tap too, and Compose's yield to a drag or a wheel. AppKit's clip view animation stops only for a trackpad gesture, and the browsers' smooth `scrollTo` runs on through a wheel, a press and a touch; Exact stops it for a press and a touch too, as Apple's Human Interface Guidelines ask (Motion: "Let people cancel motion"), and leaves a wheel to the browser.
   - Once admitted, a request ends where the reader's own scroll leaves it, so its corrections never fight the reader: its admission's move is made whatever the port did (§2.6), and a correction planned before the reader's later move does not land. Hosts report that move as a gesture: the web and macOS any move they did not make; iOS a finger's drag (one already down at the admission too, which stops a smooth correction where the port is), a tap on the status bar or the selected tab, and the tvOS remote's step; the presenter that Android, Linux and Windows share, each move of the reader's it hears (§2.6 names what iOS does not hear).
   - While the request's corrections are the app's (admitted, and no gesture since), a host reports no travel, neither their moves nor what it sampled before the admission.
   - A request that ends in any way but `done` leaves the port where the reader is: its animation stops where the port is, and nothing it planned moves the port afterwards. A newer request takes its predecessor's animation with it the same way, as CSSOM View's next scroll aborts a smooth one. A `done` request leaves nothing owed. A list that goes, and a host that resets, stop the platform's animation where the port is before they let go of the list.
   - While the host's own smooth correction may run (reported running, or sent and not yet reported), the list knows only where the animation is headed (§11). A request that begins or ends then leaves the port's position unknown: the host stops the animation where the port is, and until a report made after the stop, which the list asks for, a data update anchors nothing and a request made meanwhile waits.
   - While it is pending it overrides the list's kept position: the list does not follow its end.

6. **A request that meets the reader's hand or scroll** (2026-10-30 and 2026-10-31, James). Every host owes the same result: the target aligned by the layout as it is when the request is admitted, and the reader's own motion never taken for the request's.

   On iOS a request is admitted under a finger, as UIKit's own calls take effect there: an instant `setContentOffset` lands under the finger and the drag goes on from there, taking the port over (§2.5), and an animated one runs under a still finger and lands before the lift. A smooth request made under a finger that has dragged the port, moving or still since, lands at once: UIKit's animated call would pull the port from under the finger. On the web a finger on the port holds nothing: a fling it catches ends at the browser's `scrollend` or after the quiet interval, whichever comes first, and a drag it holds still ends after the quiet interval (below), as a trackpad's does. A request made while it rests is admitted under it, and Chrome carries the drag on from where the request put the port, which is the reader's move that ends the request (§2.5). On macOS fingers resting on the trackpad hold nothing: AppKit's live scroll begins when they move, so a request made before that is admitted under them, and their move then ends it (§2.5). Compose refuses a suspending scroll call made during a drag. The presenter that Android, Linux and Windows share hears a finger only through the port's moves: a request made under a resting finger is admitted there, and the drag that follows ends it (QUEUE.md).

   What a programmatic scroll does to the momentum after the lift differs between the calls each platform offers, so when a request is admitted then differs by host. Waiting is Exact's choice where the host's call keeps the momentum going: a jump would land, and the momentum would carry the port on from it.

   Every host makes an admission's move, whatever the port did since the report it was planned on (a resize included) and whatever an anchor's guards on the host would hold (a rubber band, a scrollbar's knob held at the end).

   On every host a request that has made no move is `done`, moving nothing, wherever the port already satisfies it, as CSSOM View skips a scroll to where the port already is; a fling under way goes on, and a nested request's inner part begins at once. It is judged when made, as CSSOM View judges a scroll when it is called, unless the host's animation leaves the port's position unknown, and again where its wait ends. The port satisfies it when the list owes no move of its own, the host runs no animation, the alignment holds where the last report and any anchor's correction since put the port (on a row list, without that shift too, which the web does not make while the reader moves the list: LLP 1070 H4), and the target is mounted and measured with no mounted row unmeasured between the port's start and it. Rows above the port and rows not mounted do not count: the anchor's correction moves the port with the first, and the second are laid out at the size the list has for them.

   **Admitted at once where the host's jump ends the momentum: iOS and Android.** On iOS a request is admitted during a deceleration with UIKit's `setContentOffset(_:animated: false)`, which ends it and lands. A smooth request made during a deceleration first stops it where the port is (`stopScrollingAndZooming()`; before iOS 17.4, an instant `setContentOffset` to the offset it has), then animates from rest. Under a finger it is admitted as above. Android's reader ends its fling and takes the presenter's offset when the presenter moves it (LLP 1115.001 D7). A list's correction of its own offset (an anchor's) keeps the momentum going on both: it assigns UIKit's `contentOffset`, and it is the reader's relative move on Android.

   **Admitted when the reader's scroll ends where the host's jump keeps the momentum going: the web and macOS.** With a real trackpad on macOS 27.2, an instant `scrollTo` made during the momentum lands and is carried 167 to 700 px on from it in Chrome, Firefox, Safari and WebKit, as AppKit's `scrollRowToVisible` and clip view scroll are; a smooth one comes to its target and is carried 19 to 340 px on from it in Safari and WebKit, and stays on it in Chrome and Firefox. A request made while the reader's scroll is under way waits. The scroll is under way while motion the reader started (a drag, a touch fling's momentum, a wheel's run, a key's, a scrollbar's knob) has not ended. While the request waits:

   - The request makes no move and builds no window at a destination. The rows follow the port, led by its real velocity (LLP 1050.000 §6), and an anchor's relative correction moves the port with its rows.
   - It makes no correction and stays `pending`: a port that passes its destination does not complete it; only the judgment where its wait ends can (below). Waiting for the reader's scroll asks for no report; the reports of the scroll, of layout, data and visibility go on. Waiting for where the port is asks for one (§2.5).
   - A request made during the scroll is judged when made, as above, where the last report and its anchor correction put the port: a request done then never becomes a jump back once the reader has moved on. A nested request is judged so for its outer list; its inner part then begins at once, in the outer row the port shows, as at rest.
   - A nested request (§3) waits with its outer list, whatever the outer list waits for. Where the wait ends, its inner target is looked up again before the outer list moves, since the items may have changed meanwhile: if the outer row no longer holds a list of the inner id, or that list a row of the inner key, the request ends `refused` and nothing moves. Otherwise the outer row is built at its destination and the inner list in that row begins the inner part.
   - When the scroll ends, the request is judged again as above, else admitted (§2.3): its destination computed from the layout then, its window built, and the port moved there before the frame paints, or its smooth animation begun.
   - A request admitted in the frame before its host's report said the reader was scrolling, or after an end judged too early, lands. The scroll carries the port on from it, and the next report, which says the scroll is under way, ends the request there (§2.5). A request already `done` is not affected: motion that an end judged too early hid carries the port on from it.

   On macOS a drag is waited for as the live scroll that holds it: the main thread sees no scroll event that ends a gesture's phase.

   *The end of the reader's scroll on the web.* What follows belongs to the scrollport, shared by the lists in it. A write by one list is the glue's own for all of them: they take the move as one they have not reported, not as the reader's, so a correction one of them planned before it does not land, and the write owns the next `scrollend`. A smooth correction of one list is the glue's motion for all of them, the move that lands it included. A move of the port counts as the reader's wherever the host first finds it: its `scroll` event, or a report or a commit that reads the offset before that event.

   Only motion starts the reader's scroll: a press or a wheel event does not by itself. A finger resting on the port or a button held on its scrollbar carries no motion and holds nothing.

   The reader's motion ends at the first `scrollend` that does not answer the host's own write, or 300 ms after its last `scroll` event, whichever comes first. An instant write that moved the port owns the next `scrollend`: writes made before one rendering update share one, and a write in a later frame gets its own, during a fling too (measured in Chrome; in Safari on an iPhone, a write at rest, under a still finger and during a fling each gets its own, and a finger's lift after one adds none). The timer covers a browser without `scrollend`, an end the host's write took, a pause in a drag, which gets its `scrollend` only once the fingers lift, and a fling caught on an iPhone, whose `scrollend` Safari fires only at the lift. 300 ms is above the longest gaps measured between `scroll` events: 82 ms in a fling and 150 ms in a slow drag with a real trackpad on macOS 27.2 in Chrome, Firefox, Safari and WebKit, 96 ms in a fling and 83 ms in a slow drag with a finger in Safari 27.3 on an iPhone, 172 ms in a fling in headless Chrome.

   A list whose animation the glue stopped reports again only from the next frame, after observing the position the stop left: the browser runs the animation on its compositor, and the offset the page reads can move once more in the frame after the stop; that move is the stopped animation's, not the reader's. Stopping need not produce a `scrollend`: in Chrome, a smooth scroll stopped by an instant write to where it was produced none, and the one `scrollend` that came was its successor's own.

   *On macOS* the reader's scroll is AppKit's live scroll, from `NSScrollView.willStartLiveScrollNotification` to `didEndLiveScrollNotification`, which brackets a trackpad gesture with its momentum, a second gesture or a catch made during that momentum, and a scrollbar's tracking. Any move of the port outside a live scroll that the host did not make (a mouse wheel's notch, a key's step or AppKit's animated page, momentum AppKit carries on past a live scroll's end; not AppKit's clamp of the clip in a layout pass) keeps the scroll under way until 300 ms after the last. A trackpad's touches reach the list's document only while a request is under way. A contact already down when the request was made began before it and does not count against it (§2.5); whether AppKit reports such a contact again when the document starts to accept touches is unmeasured (QUEUE.md).

   *A gesture, on the web:* a touch anywhere on the port, and a pointer press in the list or on the port's own box (its scrollbar); a press beside the list, on a page that is its port, is not its gesture, as on iOS and macOS. Each is heard as the window captures it, before the app's handlers, counted by its `timeStamp` against the `performance.now()` at which the request reached the list (a tie is not after: WebKit counts both in whole milliseconds), and reported at once. A touch counts at its `pointerdown`. Chrome sends one for a finger that catches a fling (measured with emulated touches), which then cancels a request made during it. Safari on iOS sends none and fires the fling's `scrollend` only at the lift (Safari 27.3 on an iPhone), so a request waiting for the fling lands under the finger after the quiet interval, as UIKit's own calls land under a finger. A finger that touches the glue's smooth scroll sends its `pointerdown` in Safari too, which stops the animation (§11). A wheel event is no gesture, since none says whether it begins a scroll or carries a trackpad's momentum: a wheel acts only through the motion it makes. A trackpad's fingers that catch a glide send the page no event, and the browser ends the scroll with a `scrollend`, so a waiting request lands under them, where macOS, which hears the touch, cancels it. An assistive technology's scroll cannot be told from momentum either: a request made during it waits, then lands (QUEUE.md).

   *On macOS:* a finger coming down on the trackpad over the list (an `NSTouch` beginning; while a request is under way the list's document accepts indirect touches), a scroll event over the list that begins a phase or has none, and a mouse press on the list or its scroller. Presses are heard first in the monitor of the view that hosts the app, where its handlers run; wheels and middle presses in a local monitor, before AppKit gives them to views; a trackpad's touch at the list's document view. Each counts by its event's timestamp, a trackpad gesture's from its first scroll event (`mayBegin` when the fingers rest first, otherwise `began`). AppKit carries a second gesture, a catch and a click on within the live scroll still running, with no scroll event or start notification of their own: the touch beginning is a sign the main thread gets.

   *On iOS:* a finger coming down on the list, whether or not a drag follows, by its touch's timestamp. A scroll run for the reader with no finger on the list is a gesture too, as a drag is: a tap on the status bar, a tap on the selected tab, and on tvOS the remote's arrow click that steps the list. Each stops the host's animation where the port is, and a correction planned before it no longer lands. The iOS host hears no other scroll as the reader's: not an assistive technology's (`accessibilityScroll`), a hardware key's, or on tvOS the focus engine's toward the item it focuses (QUEUE.md). On iOS 27.0 a `UIScrollView`'s `allowsKeyboardScrolling` is off on iPhone and on on iPad, and Exact's lists leave it as it is: whether a hardware key then scrolls an Exact list on iPad is unmeasured (QUEUE.md).

   *On the presenter that Android, Linux and Windows share*, a gesture cancels a request through the reader's move of the port: a press that moves nothing does not.

   *The selected tab tapped again*, on iOS and on the presenter, scrolls its screen's list to the top after the tab's press runs. That scroll gives way to a request the press made in that list in answer to the tap, whether the request lands, is still under way or finds its row already shown: what the author asks for wins over the platform's default. A snapshot names the list's latest request, under way or ended (`lastRequest`). Before the press the host reads every list's latest request. After it, the host compares the screen's list's with that list's own from before, or with 0 for a list the press made, since the press may make the screen's list or make another list the screen's.

   **Linux and Windows** never wait for the reader's scroll. The Linux host has no kinetic scrolling yet (LLP 1050.000 §7). GTK 4's kinetic scrolling keeps its own path through `gtk_adjustment_set_value` and `gtk_list_view_scroll_to` and drops the jump, unless kinetic scrolling is first turned off (`gtk_scrolled_window_set_kinetic_scrolling`). Windows is unmeasured (QUEUE.md).

   A request made with the port at rest is admitted at once (§2.3); a smooth one completes when its animation lands (§11).

## 3. Nested lists

`row` addresses an inner list through its outer row. Both scrollers align: the outer one brings the outer row into view by the option for its axis (`block` for a vertical feed), the inner one the target (`inline` for a strip). This is what `scrollIntoView` on the unvirtualized page does: every scrollable ancestor aligns the target's own box (the outer row is aligned to the target's box's block extent, which, for a strip inside a row, is the strip's). Ordinary (eager) scrollers and the page between them are not moved: a virtualized list inside an ordinary scroller aligns in its own port only, a declared difference from the web, where the page would scroll too. The command looks the inner target up in the outer row before either list moves, building the row aside when it is not mounted, and what it refuses for the inner part (§2.2) it refuses whole: nothing moves. The JS target finds the inner target only once the outer row is built, so there the outer row stays in view (QUEUE.md). Of several outer lists with a row of that key, the one whose row holds the inner target takes the request.

## 4. The target's box

The authored row root's border box, as the web aligns the element's: the runner's row wrapper encloses the root's margins, and the root's literal margins on the list's axis are taken off. `scroll-padding` insets the alignment port (LLP 1010 §6.9); `scroll-margin` expands the target border box (the 2026-10-13 amendment below).

## 5. The agent

No tenth operation (`rules/DEFERRED.md`): a form of `tap` on a mounted list, `tap <list testId> into <key> [block <value>] [inline <value>]`, runs the same runner request (an inner list not mounted is reached through its outer list, or by the app's command with `row=`). Its outcome is in `state.scrollIntoView` (`{list, key, status}`, status `pending`, `done`, `unconverged`, `refused: reason`, `cancelled`), and `clock settle` drains its corrections.

## 6. Staging

1. **Instant positioning** (this change): the command, the runner request, nested addressing, the agent form, the fixture and Chrome parity.
2. **Smooth**, only with a consumer: the platform's own scroll animation between an origin and a destination, with an explicit traversal policy (rows between the two are not built; what shows mid-flight is owed, as a fling's is) and the web's declared limitation (the browser's smooth scroll cannot wait for rows).

## 7. Acceptance

- Chrome parity: `apps/carousel` targets a feed row, a card in a strip, a message in an inbox, the first and last rows, with each `block`/`inline` value, cold (far from the mounted window); the target's box equals the unvirtualized page's after the browser's `scrollIntoView` on the same element.
- Bounded: mounted rows after a cold jump are the destination's window, not the path.
- Mutation and interruption: a request followed by an insert above the target, by the target's deletion, by a reader's scroll; a duplicate key; a missing key.
- Then xheavy's jump scenario uses it (`BENCH_START_INDEX` through the command, not the data source).

## 8. Not done

Scrolling ordinary ancestors of a virtualized list; RTL row lists (LLP 1070 §3.2); `container: "nearest"` (the web's newer option: every request already stops at the list's ports).

## 10. As built (2026-09-27, `feat/horizontal-lists`)

- **Contract:** `scrollIntoView("list-id", key, block=, inline=, behavior=, row=)` with `type-scroll-into-view`; `smooth` refused.
- **Runner:** the command is the runner's own, run in the action's commit after its update; `Runner::scroll_into_view` and the agent's `tap <list> into <key>` on the web, macOS, iOS and Linux; `state.scrollIntoView` lists each list's latest request and refusals. Runner tests (`contract/cli/tests/it/collection_into_view.rs`): a cold jump centred on its measured size with the destination's window only, the last row at the end, a missing key refused, a reader's gesture cancelling, and a card in a strip in a row far away.
- **Parity:** `apps/carousel`'s feed, eight requests (rows centred, at the start, the last row at the end; a card centred in a strip; a message centred in an inbox; `nearest` on a shown message). **macOS, iOS and Linux:** every target's box aligned in its port as the web defines it, within 0.5 px (0 of 8 off each). **The web:** 10 of 10 boxes equal Chrome's `scrollIntoView` on the unvirtualized page, both requests `done`, three runs running (2026-09-28). Three causes kept it apart until then, all in `host/web/collection-glue.js`: (1) the browser clamps the port when a row laid out smaller than its estimate shortens the extent at the end, and the glue took the clamp for the reader's scroll (a new sequence, which voided the runner's correction, and travel, which led the fill upward one row a report); a clamp is now no scroll, and the report carries the offset the painted frame had, the coordinates the runner anchors in; (2) while a request seeks (`seeking` in its snapshot) its corrections are authored moves, applied whatever the port did since, and its moves are not travel, until a gesture the reader begins on the port cancels it (§2.5); (3) the agent's `clock settle` built a slice a report and visited four lists a round, so a request ended the settle mid-way; it now ends motion, builds what each report owes whole and visits every list, as the native pumps do.
- **Not built:** smooth (§6.2); `scroll-margin`/`scroll-padding`; xheavy's jump scenario still answers from row n (`QUEUE.md`).

## 11. Smooth, built (2026-10-03, §6 step 2)

Consumer: the Signal Clone app (an outside app), whose send must animate the
transcript to the new message, as Signal's does. `behavior="smooth"` is
admitted by the compiler. The runner's request carries it (`IntoView.smooth`,
`Target.smooth`) and marks its corrections — the first and each converging
one — `smooth: true` on the wire (`AnchorCorrection.smooth`, the snapshot's
`"smooth":true`). The same mark goes on a `scroll-behavior: smooth` list's
end-follow correction once the list has opened (`scroll-start="end"`'s
opening and a kept row's relative correction are never smooth): content
arriving at the end the reader is following animates there.

The traversal policy (§6.2): the window is built at the destination at once,
as for `auto`. Rows in between are not built. While the animation runs, the
list reports its destination (below), so a smooth jump longer than the
mounted window crosses unbuilt spacers mid-flight. That is declared, not the
fling-like realization §6.2 first described. An end-follow after a send
moves within the window and never shows it (QUEUE: "Smooth collection jumps
cross unbuilt rows"). On iOS a smooth correction is the host's own animation of the offset (`OffsetDriver`, 0.3 s). While it runs the host reports no travel for that list (`CollectionHost.animating`, `motion` nil). A further smooth correction, or rows moving under it (a relative shift), retargets the running animation from what shows rather than starting another: restarting it on every converging correction made it creep. While it runs the list's report gives the destination as

## 13. App-owned restoration (2026-10-13)

Charlie's 2026-10-08 ruling in issue #277 selects an app-owned first-visible

A `scroll` handler's `ScrollEvent` adds `firstVisibleKey: option<string>` and
`firstVisibleOffset: number`. The key is the authored key as text (numbers and
bools take their text representation). The offset is signed CSS pixels from
the first intersecting row wrapper's start to the port's start, on the list's
axis. It uses the event's physical offset and the index's current sizes, which
may include estimates; not a pending animation's destination. Zero-size rows
are skipped. Ordinary scrollers, empty lists and ports showing only padding
