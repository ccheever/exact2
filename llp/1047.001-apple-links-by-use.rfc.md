## Summary

Charlie, 2026-10-06: *"record that we want to make sure that features only
get linked in when used and that everything is sort of optional unless you
use it."*

LLP 1047 already states that rule for the web, and has carried it out there
(§10: Markdown, motion and others behind `exact_web::Linked`). It put native
after the web (§10, answer 5). This RFC is the same rule on Apple, in both
of the host's languages:

- **The rule.** An app's binary holds the core, plus each capability its
  plan uses or its manifest names in `link`. Everything else is absent.
- **"Uses" is derived, "names" is declared.** The plan's use-set is
  computed from its bytes (parent D2). The manifest's `link` list is parent
  D8's link-ahead, for a native binary that later bundles may outgrow.
- **Swift is not exempt.** Being in ExactKit does not make code core. The
  core is what a plan with one `text` and one `button` needs.

Today the iOS embed is far from that, and growing. A one-text-node app went
from 7.23 MB to 9.83 MB in production between 2026-09-30 and 2026-10-06
(§1). §3 traces why the code stays in, and §4 proposes how the rule is
carried out on Apple. §6 begins with one capability carried end to end,
not a broad split.

## 1. Measured

**The probe.** One `text` node, an empty data source, `exact_apple::host!`
with an `L=0` compat, linked into a UIKit `main.swift`.

- **Target:** `arm64-apple-ios17.0`, device (not simulator). Xcode 27.0
  (27A266a); Rust 1.97.0.
- **Link:** `swiftc -Osize` driver, `-dead_strip`,
  `-no_exported_symbols` (the executable exports nothing but what `main`
  needs), then `strip`.
- **Unit:** stripped bytes added over a plain UIKit app (73,056 bytes);
  MB = 10⁶ bytes.
- **2026-09-30:** at that day's main. The probe booted and painted on the
  iPhone 17 Pro simulator.
- **2026-10-06:** at `463acda68`, the plan rebaked by that commit's compiler
  (`contract build`). Linked, **not booted**.

| Configuration | 2026-09-30 | 2026-10-06 |
|---|---|---|
| Production: Rust opt-level 3 + thin LTO; `swift build -c release` (`-O`) | 7.23 MB | 9.83 MB |
| Rust opt-level z + fat LTO; Swift `-Osize -Xfrontend -internalize-at-link -enforce-exclusivity=unchecked` | 4.65 MB | 6.21 MB |
| + nightly `build-std`, `panic=immediate-abort`, `-disable-reflection-metadata` | 4.09 MB | — |

The second and third rows change semantics: unchecked exclusivity, and
without reflection metadata `String(describing:)` of an enum prints its
type name. They bound what flags alone can do. They are not candidate
production settings as they stand.

**Other frameworks,** measured 2026-10-06, arm64 iPhone, release, unsigned
file bytes:

| Framework | Bytes | What was measured |
|---|---|---|
| React Native 0.86.3 | ≈8.86 MB + the JS bundle | prebuilt `React` 5.76, `hermesvm` 2.33 and `ReactNativeDependencies` 0.77, local symbols stripped; the bundle not measured |
| Lynx 4.1.0 | 9.31 MB | a hello page's app over a plain app, run on the simulator |
| Flutter 3.44.2 | ≈13.07 MB | `flutter create`'s counter app: `Flutter` 9.24, `App` 3.43, `flutter_assets` 0.39 |

These boundaries differ: Exact2's row is an executable delta after dead
stripping, RN's and Flutter's are prebuilt dynamic frameworks that are not
dead-stripped, and Flutter's includes the app's compiled Dart and assets.
With that said: on 2026-09-30 production Exact2 (7.23) was below RN's native
frameworks, Lynx and Flutter. On 2026-10-06 (9.83) it is above RN's native
frameworks and Lynx, and below Flutter.

## 3. What keeps code in the Apple binary

The probe exports only `main`, so an exported `#[no_mangle]` is not, by
itself, a root there. Code stays because something live references it.

1. **Swift live paths reach capability code from every app.**
   - **Every batch.** `Presenter.apply` calls `swipeActions.prepare()` and
     `groupedLists.prepare()` on every batch (`PresenterIOS.swift:731-732`),
     and navigation and modal bookkeeping alongside them.
   - **Stored engines.** The presenter stores its feature engines (`let svg`,
     `let canvas2d`) and dispatches their ops in one `switch`.
   - **Every node.** `NodeView`'s setup reaches the canvas painter and
     `presenter.leaves.embed(self)` for every node
     (`NodeViewIOS.swift:551`, `:578`). The class also conforms to the
     UIKit delegate protocols its feature behaviours need.
   - **Session start.** `Session` wires Canvas 2D's callbacks when it starts
     (`Session.swift:494-496`).
   - **Boot.** `Bridge`'s boot asks for SVG islands (`Bridge.swift:170`,
     `exact_svg_islands`).
   - **Text.** Ordinary text styling calls into Markdown pieces
     (`MarkupRuns.swift:43`, `exact_markup_pieces`).
2. **Those Swift calls keep the Rust capability exports alive.**
   - `host!` emits eight export groups without condition
     (`exports.rs:19-29`).
   - It also emits capability exports inline: canvas, surfaces, motion and
     drag, lists, the router, the agent, grouped lists, select and radio,
     `exact_svg_islands`.
   - Because Swift calls them, removing a group before its Swift callers
     gives an undefined symbol, not a smaller app.
   - Which exports are core and which belong to a capability has never been
     inventoried.
3. **Native boot links everything on purpose.**
   - Apple's boot links every row's grammar (`host/apple/src/host.rs:364-368`,
     after LLP 1053.000 §2).
   - It boots the runner with every device linked
     (`runner/src/runner/delivery.rs`, `linking_every_device`).
   - The web reaches these through the entry's registrations. Apple has no
     such seam.
4. **The entry generator doesn't know the use-set.**
   - 20 of the 32 Apple app crates generate their entry. Each `build.rs`
     calls `contract::rust_entry` and writes `entry.rs`, which always ends in
     the full `host!` (`apps/caltrain/apple/build.rs:40-50`).
   - 12 hand-write `host!` in `lib.rs`: auth-fixture, canvas-gallery,
     color-gallery, completion-storm, duo-lab, expose, fieldnotes, messages,
     messages-legacy, recorder, update-lab and weatherlight.
   - The seam LLP 1047 D3 needs exists; it just doesn't select anything.
5. **iOS links the wasm interpreter whenever logic mode is `auto`.**
   - `Manifest::rust_mode` maps (`auto`, `ios`) to `wasm`
     (`contract/cli/src/manifest.rs`), whether or not the manifest names a
     `rust.module`.
   - The web already says `off` without a module
     (`contract/cli/src/logic.rs`, `web_rust_mode`).
   - The interpreter (wasmi, about 1.0 MB in a real app's archive on
     2026-09-30) is then linked into apps that have nothing it could run.
   - The one-text probe doesn't go through this path, so this is not part
     of its growth.
6. **The production Swift profile keeps public symbols.**
   - Without `-internalize-at-link`, public Swift symbols survive the link.
   - On 2026-09-30 that cost 1.2 MB on the probe; with the flag, 5 KB.
   - That is a compiler-flag fact, not a linking-by-use one (§5).

**What already works by use on Apple.** A production build with store level
0 leaves out every loaded arm the plan cannot reach: canvas, SVG, video, web
and sound (`host/apple/build.mjs`, `graph.loads`, "left out of this build").
That is the third tier working. This RFC is about the second.

## 4. Decisions

### D1: The rule, its exceptions and its scope

- **The rule.** Every host, in every language: the binary holds the core,
  plus each capability in the app's *composition*.
- **The composition** is the plan's use-set, plus the manifest's `link` list.
- **Development links everything** (D6).
- **The core** is what a plan with one `text` and one `button` needs:
  decode, boot, lay out, a first frame and a tap. Being common doesn't make
  something core.
- **Loaded capabilities** (arms, the GPU module, native modules) stay
  separate artifacts.
- **Scope.** The policy covers the web, Apple, Linux, Windows and the
  terminal. This RFC implements Apple: the UIKit presenter (iOS and tvOS)
  and AppKit (macOS), which share ExactKit. The other hosts follow by the
  same rule, each analyzed when its turn comes.
- **Reviews ask which tier a change is in.** A new feature lands as a linked
  or loaded capability unless a one-text, one-button plan needs it.

### D2: One composition drives Rust, Swift, admission and compatibility

The build computes the composition once per app, and four things read it:

1. the Rust entry (D3)
2. the Swift composition (D4)
3. the boot admission check (D5)
4. the compatibility id (parent D8)

**The use-set is `exact_runner::uses`, extended for native.**
- `Capability` currently describes what the *web* host must link. Motion,
  for instance, counts only springs and holds, because CSS plays every other
  transition. On native, the host's own engine plays every transition.
- So each capability gets a requirement per host, and the native roster
  gains the capabilities the Swift side needs separately: grouped lists,
  navigation bars, menus, swipe actions, and the others §6's maps show to be
  large.
- **Computed values stay conservative.** A computed value counts as a use of
  whatever it might select, across every route and state, not only the
  first screen.

**Non-plan inputs** that select code are part of the composition, named in
the build's receipt. Two exist today: the logic executor (D7) and the store
level, which already selects `ExactUpdates`.

### D3: Rust — the generated entry emits what the composition names

- **Every Apple app generates its entry.** `contract::rust_entry` learns the
  Apple form, and the 12 hand-written `lib.rs` callers fold into it, with no
  migration path.
- **The entry emits core exports, plus each capability's export group and
  registration**, only for capabilities in the composition. Every
  `#[no_mangle]` that `host!` emits is assigned to the core or to exactly one
  capability. That inventory is the first artifact of §6's slice.
- **Core reaches capabilities through registered seams.**
  - Apple's boot stops naming capability code.
  - The row-grammar links and `linking_every_device` become registrations
    the entry makes, as `exact_web::Linked` does on the web.
- **No cargo features.** Each crate builds one way. What differs per app is
  which symbols the entry names (parent D3).

### D4: Swift — capabilities are separate targets, chosen by the composition

**Core ExactKit names no optional concrete type.**
- A capability supplies factories and hooks for its op kinds, its tags'
  views and props, and its batch lifecycle (`prepare`, settle).
- It registers them with the presenter. `Presenter.apply` calls only the
  hooks that are registered.
- Feature behaviour moves out of `NodeView`: delegate conformances,
  `@objc` actions, and per-tag prop handling go into capability-owned views
  or objects that the core doesn't name.

**Each capability is its own SwiftPM target and product.**
- This generalizes the composition seam that already exists.
  `EXACT_APP_COMPOSITION` (`embedded` | `updating`) selects
  `ExactComposition`'s source and whether it depends on `ExactUpdates`
  (`Package.swift:16-36`).
- Under this RFC, the composition target's source is generated: it
  `import`s and registers the composition's capabilities, and its target
  depends only on their products.
- **Absence comes from the link line, not from `import`.** A capability
  that isn't in the composition isn't a dependency of anything that gets
  linked.
  - SwiftPM's static-module linking keeps conformances and Objective-C
    classes from what *is* linked, which is why their sections are roots.
    It cannot keep what isn't on the line.
  - Generic registration is specialized in the capability's own module,
    next to the types it names.

**Embedding (LLP 1031).**
- `--embed` emits, beside the app archive, the composition: the list of
  capability products and the generated composition source.
- An embedder links ExactKit's core product, plus the products named there.
- `exact.h` splits into a core header plus one header per capability, so a
  missing capability is a missing header and product, not an undefined
  symbol.
- Capability instances are session-scoped (two sessions, LLP 1031).
- The ABI changes coherently, with no compatibility shims.

### D5: A capability the binary lacks is refused before anything changes

- **Initial boot.** A plan whose use-set exceeds the composition is refused
  at boot with a named error, as on the web: `Unlinked("svg")`.
  - The refusal ends in a contained, terminal failure state (LLP 1031 D8).
  - Today a refused first boot on iOS recurses through `ExactView.fit()`
    without bound (QUEUE, 2026-09-30). That is fixed before this decision
    is exercised.
- **Reload, an applied plan, a delivered candidate.** These are checked
  against the composition in the prepare phase of the existing all-session
  prepare/commit boundary (`Session.swift`).
  - A rejected candidate leaves every session running its previous plan.
- **Deployment.** The composition is a compatibility input (parent D8).
  A bundle that needs more is a binary change, and `deploy.mjs` classifies it
  as one before anything ships.

### D6: Development links everything; smokes use what ships

- A development build links every capability, as on the web (parent D7).
  This keeps the agent, the dev menu and plan restarts working for any plan.
- An app's smoke runs its production composition.
- Whole-vocabulary fixtures run on an all-linked build, as `smoke.mjs web`
  already does with `EXACT_WEB_LINK=all`.

### D7: The logic executor follows the module

- iOS links the wasm interpreter only when the manifest names a
  `rust.module`. This generalizes `web_rust_mode`: `auto` with no module is
  `off`.
- This keeps Charlie's 2026-09-13 ruling (LLP 1029.000): an app with
  replaceable Rust logic gets the interpreter by default.
- An app with no module has nothing the interpreter could run. Today only
  Caltrain and update-lab name one.

### D8: The embed size is measured — proposed, awaiting a yes

**The proposal.** `metrics.mjs --long` gains an iOS embed row: §1's probe at
the production profile, in MB over the UIKit floor.

- It never blocks, like LLP 1047 D9 and §10's answer that the target is an
  outcome.
- It runs on the async lane, so its cadence is that lane's (about hourly,
  coalesced), not every commit.
- It lands before any composition change, so each step's effect shows.

**It needs approval.** This is new apparatus, and `rules/RULES.md` §Agents
needs a human to approve it explicitly. Charlie's request asked for the rule
to be recorded, not for a probe. This decision stands only with his yes.
Until then, measurements are taken by hand with `~/bench/embedsize`.

## 5. What this does not change

- **The plan format.** The use-set is derived from plan bytes.
- **Compiler levers.** Fat LTO, `-Osize` and `-internalize-at-link` are
  separate decisions. Each needs its frame cost measured on the iPad before
  it becomes the production profile. They shrink everything, but they don't
  make anything optional.
- **Loaded capabilities.** The arms and the GPU module stay as they are,
  and so does the left-out-of-this-build logic for `L=0`.
- **Budgets.** A byte row doesn't waive the rebuild, startup or frame
  budgets. A Swift split that rebuilt the whole host per app would break the
  rebuild budget. Capability targets are built once per destination and
  shared across apps, as ExactKit is today.

## 7. Questions for Charlie, with the author's recommendation

1. **Order.** Should Apple's steps 3–5 start now, or after LLP 1047's web
   goal?
   - *Recommendation:* now, for steps 1–3: they are small and stop the
     growth from going unseen. Step 4 waits for an implementer with free
     time, not for the web goal.
   - *Confidence:* high for steps 1–3. Medium for step 4's timing, which
     depends on what else is in flight.
2. **Link-ahead.** Should native keep parent D8's manifest `link` list?
   - *Recommendation:* yes, as D1 states. Without it, a delivered plan that
     starts using a capability forces a binary update. That is the problem
     D8 exists for.
   - *Confidence:* high.
3. **The iOS executor default.** Should it be D7's rule?
   - *Recommendation:* yes. It keeps the 09-13 ruling for apps that have
     Rust logic to replace, and drops an interpreter that apps without a
     module can never use.
   - *Confidence:* fairly high. The one way it's wrong: if "by default"
     meant apps should be able to gain a replaceable module through delivery
     alone. Today a module must be named in the manifest before the dev loop
     or delivery builds one, so it can't.
4. **The embed row (D8).** Should it exist?
   - *Recommendation:* yes, report-only, on the async lane, landing first.
     This week's +2.6 MB went unseen for lack of it.
   - *Confidence:* high.
5. **A target number.** Should the row carry one?
   - *Recommendation:* not yet. Set one after step 4 shows what a capability
     move actually removes.
   - *Confidence:* medium.
6. **Granularity.** One Swift target per capability, or bundles?
   - *Recommendation:* one target per native capability in the roster.
     Merge only capabilities that share most of their code.
   - *Confidence:* medium-low. The answer depends on step 4's measured build
     time and on how much code capabilities turn out to share.
7. **The agent in production.** Should it stay linked?
   - *Recommendation:* yes, as the web decided (parent §10, answer 3), so
     the smoked binary is the shipped one. But it should be created lazily
     and reached from no core path, so it costs bytes and no time.
   - *Confidence:* medium.

## 8. As built (2026-10-07)

Steps 2–4 of §6 landed together. Step 1's per-commit row (D8) waits for an
explicit yes; until then, measurements are taken by hand with
`~/bench/embedsize`.

### Step 2: the executor follows the module (D7)

- **The compatibility inputs say `off` when the manifest names no
  `rust.module`.** This is in `exact_bake::compatibility_id`, so every
  native entry and the web read it. The policy is still validated.
- **Effect on apps.** Only Caltrain and update-lab name a module, so every
  other app's archive drops its Rust executor.
  - Type Tour's iOS development binary now has no `wasmi` symbol.
  - Its compatibility inputs say `rustMode: "off"` and executors
    `["native"]`.
- **Test:** `an_executor_is_linked_only_for_a_named_module`.

### Step 3: a refused first boot is terminal (D5's prerequisite)

- `ExactView.fit()` on iOS no longer boots again after a refusal, and
  boots only once `session.state` is not `.failed`.
- The macOS view takes the same guard.
- A plan applied later still recovers through `presentCommitted`.

### Step 4: grouped lists, end to end

- **The use-set.** `Capability::GroupedLists` is a `listStyle` binding,
  which Contract sets on every `list appearance="auto"`.
  - The web always counts it as linked, because it draws the authored nodes.
  - The bake's graph names the use-set (`uses`).
- **Rust (D3).**
  - `exact_grouped_list` moved into `grouped_list_exports!`.
  - `host!` takes `; linked = EXACT_LINKED`, and a generated entry with
    that argument emits only the export groups it names.
  - `contract::apple_linked(&plan, host)` writes the set and its groups.
  - The 20 generated Apple entries pass it. The 12 hand-written ones keep
    every group and link everything; folding them in is still owed.
  - Apple's one decode path admits the plan against the archive's set
    (`exact_apple::link`): `HostError::Unlinked("grouped_lists")`.
- **The composition (D2, D6).** `host/apple/link.mjs` decides it, and
  `build.mjs` tells both builds what the archive links:
  - Cargo gets `EXACT_APPLE_LINK=plan` for a fixed plan (production, store
    level 0), and `all` otherwise.
  - SwiftPM gets the receipt's capability names.
- **Swift (D4).**
  - `GroupedListIOS.swift` is its own target and product,
    `ExactGroupedLists`.
  - The core keeps a `package` protocol (`GroupedLists`), the aim enum, a
    scroller marker and the install hooks (`GroupedListsLink`). Every core
    call site is optional.
  - `ExactComposition` depends on the module and defines
    `EXACT_LINK_GROUPED_LISTS` only when the composition links it, then
    calls `ExactGroupedLists.install()` before any session.
  - The model is read through a closure that a test can replace.
- **Access.** A module split for linking still needs the core's internals,
  so the types and members it reaches are `package`:
  - `Presenter`
  - `NodeView`, with its UIKit overrides and delegate methods
  - `Runtime`, `BatchValue`, `ProfileSpaces.Handle`, `TextEngine.color`
    and `assign`
  - two narrow accessors (`viewportScroll`, `keyboardContainer`) in place
    of the `ScrollView` and `ModalHost` subclasses
- **Embedding (LLP 1031).**
  - `--embed` writes `capabilities.json`: the products to link beside
    ExactKit, and the `install()` calls to make first.
  - `exact.h` stays one header. A declaration is not a reference, so
    D4's header split was unnecessary.
