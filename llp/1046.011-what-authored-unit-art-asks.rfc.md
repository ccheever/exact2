## 1. Summary

Skirmish's units are built in Rust from up to 20 stretched primitives and nine shared swept meshes, each over the same tiling maps. They look like plastic. As a trial, one unit, the siege tank, was rebuilt in Blender from a headless Python script. The script models it at true scale and bakes worn edges, grime, ambient occlusion and edge-rounding normals into one atlas per part. It then exports glTF to `art/`. The existing app bake imported it with **no engine change**. It renders in the engine with team colour, turret yaw and gun recoil, and it reads clearly better at both close and gameplay zoom.

The route works. This RFC is about the five places it rubbed:

| | Ask | Size |
|---|---|---|
| D1 | A model declares which of its materials take the entity's colour | **Held** (§8.1): games use `MaterialOverrides` from `present` |
| D2 | A stale captured lock says the SDK moved, and one verb refreshes it | shells.mjs + exact.mjs, small |
| D3 | A texture size cap for model maps, and the bake prints what each model costs | bake, small |
| D4 | `exact.mjs look`: an offscreen turntable of a model through the engine's renderer | tool, medium |
| D5 | The Blender bake kit ships in exact2, run by `exact.mjs art` | **Deferred** (§8.3): stays in the game until it proves general |

D2 is the most urgent: it blocked `test-rust` in both of today's Skirmish sessions. D1 would change no pixels; it only saves model files and batches, so it waits for a second game to ask.

## 2. Evidence: the tank trial

- **Pipeline.** `tools/blender/siege_tank.py` and `kit.py` in Skirmish run under Blender 5.2.2 (`blender -b --factory-startup -P …`).
  - Parts are tagged by kind (paint, armor, steel, track, …), beveled with hardened normals, joined into one object per articulated part, and smart-unwrapped.
  - Cycles bakes four passes: AO, then base colour, ORM and tangent normals. The colour and ORM passes read the AO.
  - Export is GLB.
  - A full rebuild takes about 22 s on Metal. The app bake takes 15 s; a single-unit offscreen render, 4.7 s.
- **What the bake accepted unchanged:**
  - glTF materials with base/ORM/normal/occlusion textures;
  - an ORM image shared by the metallic-roughness and occlusion slots;
  - `KHR_materials_emissive_strength` on the lamp material.

  Content-named textures meant the two models of each part (§3) shipped one set of maps. Only the `.model` names had to be declared.
- **Geometry:** 9,374 faces for the hull, 1,454 for the turret, 650 for the gun. Three entities replace about 40 primitive parts.
- **Texture weight:** 9 maps (3 per part; hull and turret at 1024², gun at 512²).

  | Payload | Bytes |
  |---|---|
  | `.bc.tex` (what a BC device fetches) | 9.4 MB |
  | `.astc.tex` | 9.4 MB |
  | `.tex` RGBA8 fallback | 37.8 MB |

  For comparison, the nine shared sculptures' 36 maps at 512² total 73.9 MB across all three variants.

## 3. D1 (held): a model's materials can opt out of the entity colour

Held by the ruling in §8.1. Kept here as the design to pick up if another game needs team colour without a `present` hook.

**Today.** A model entity's `Material` multiplies every node's base colour (`game/README.md`, "Team colours" row). Per-material looks exist as `MaterialOverrides`, but they are presentation state (LLP 1046.008 §3). They are written from `Game::present`, cleared before each present, never saved.

Skirmish has no `present`. Neither does its offscreen render example. So the trial exported each part twice:
- the body, tinted white;
- a `-paint` model with only the team faces, tinted by the team `Material`.

That is six models and six draws per tank where three would do. Every authored unit would pay the same.

**Proposal.** A glTF material may declare that it ignores the entity's colour:

```json
"materials": [{"name": "hull-body", "extras": {"exact": {"entityColor": false}}, …}]
```

- **Bake:** reads it into a new `MaterialData.entity_color: bool`. The default is `true`, so existing models are unchanged.
- **Render:** when it builds a model record (`render/src/world/assets.rs`), the renderer replaces the entity's base colour with white for materials with `entity_color == false`. `model.wgsl` then multiplies as today.
- **Emission:** the entity's emission still lands on every material, because a hit flash wants the whole unit.
- **Overrides:** `MaterialOverrides` and `NodeMaterials` keep their order. They apply under the entity's `Material`, and an override's colour still replaces a material's factor.

Then one model per part serves every team: the paint materials keep the default and the rest say `false`. Blender writes this from a material custom property when it exports with `export_extras=True`. The bake already reads `asset.extras.metersPerUnit`, so extras are an established channel.

**Consequences.**
- **Format:** `MaterialData` is a `Data` record, so adding a field changes the `.model` encoding. The implementer must check how `Data` evolves: rebake every model, or keep the field optional on read.
- **Whole-model tints:** a masked model's entity colour no longer recolours it all. Skirmish's grey "remembered under fog" ghost tints the whole unit with its entity `Material`. With a masked model, a ghost needs a whole-model look:
  - `NodeMaterials` from `present`;
  - or a ghost-only `MaterialOverrides`;
  - or the same ghost colour applied to every material through a small `Tint`-like rule.

  This is the main cost of D1; see §8.
- **Untouched:** saves, hashes and the presentation rules.

**Alternatives.**
- **Status quo: `MaterialOverrides` from `present`.** Correct under the authoring rule, already documented, and no engine work. A game adds `present`, maps each unit to its model entities and writes the overrides every present. This is fully viable. D1 claims only that the most common RTS look should not require a present hook.
- **Split models (the trial).** Works today, with no engine change, but doubles models and draws.
- **A saved `MaterialOverrides`.** Rejected. Presentation rows are cleared before each present, so one component type cannot be both.

## 4. D2: a stale captured lock names the SDK, and one verb refreshes it

**What happened.**

1. `bun exact.mjs test-rust` stopped before any test with this:

   > game Cargo graph: error: cannot update the lock file …/.shells/Cargo.lock because --locked was passed

   The cause was SDK drift. The exact2 checkout had moved to vendored `parley`/`fontique` (LLP 1085.000) since Skirmish captured its own `Cargo.lock`.
2. The printed remedy was `bun game/app/shells.mjs <dir> --update-lock`. That path is relative to exact2, not to the game, and from the game it needs `../exact2/`. Run that way, it failed offline (`failed to download harfrust v0.12.0`). The message also says to run `cargo fetch` first, but as a separate line that reads as an alternative.
3. The earlier diary found the precondition. The bake copies a captured lock into `.shells/` without checking it, and a plain `cargo run` there silently re-resolves ("Locking 7 packages"). So the render example kept building while `test-rust` refused.

**Proposal.**

1. **Name the drift.** When `metadata(true)` fails for a captured lock, `prepareGame` diffs it against the SDK lock (`sdkLockFile`) for SDK-owned packages. `outsideSdkLock` already computes the shape of this. When they differ, the error says so first:

   > exact2 moved since this game's lock was captured (added: fontique, parley, parley_data, …; updated: harfrust 0.5.2 → 0.12.0). Refresh it with `bun exact.mjs lock` (needs the network).

2. **One verb.** `bun exact.mjs lock` runs `cargo fetch` on `.shells/Cargo.toml`, then the existing `--update-lock`, and prints the changed packages. `exact new --update` and the game's `exact.mjs update` run the same check after rewriting `exact.mjs`, and offer `lock` when the captured lock is stale.
3. **Check at copy.** When the bake writes a captured lock into `.shells/`, it runs the same locked check and warns with the same message. A stale lock then surfaces at the first build, not at the next `test-rust`.

**Not proposed:** auto-updating the lock. Dependency changes stay explicit (the comment above `prepareGame`).

## 5. D3: a texture cap for model maps, and the bake prints the bill

The bake already drops leading mip levels to keep an RGBA8 chain within 2048² (`compress::capped`). D3 lets an author set a lower cap:

- **App-wide:** `app.json` `"game": {"assets": {"maxTexture": 512}}`. `game.assets` becomes `true` or an object.
- **Per model:** glTF `asset.extras.exact.maxTexture`, beside `metersPerUnit`.

Capping drops leading levels before encoding, so the output is the same as authoring at the smaller size, and the digests follow.

After each run the bake prints one line per model, for example:

```
skirmish-tank-hull.model  3 maps 1024²  4.2 MB per device (BC/ASTC)  16.8 MB fallback
```

`game/bake/README.md` gains a short "texture weight" note: what a device fetches, what is only on disk, and roughly what a roster costs. The RGBA8 fallback stays, because the GPU-less host and devices without either block family need it. Its cost lands on disk and in packages, not on BC/ASTC devices.

## 6. D4: `exact.mjs look`, a turntable through the engine's renderer

The most useful tool in the trial was not Blender. It was a five-second offscreen render of one unit, through the engine's own renderer, at gameplay and close zoom (Skirmish's `render/examples/unit_gallery.rs` with a unit filter). Every round of the art was judged from it. It was also what showed that the first version read as "a flat slab with a pencil barrel" at gameplay zoom.

```
bun exact.mjs look art/skirmish-tank-hull.glb            # bakes if needed, then 8 angles
bun exact.mjs look skirmish-tank-hull.model --zoom game  # the game's camera distance
bun exact.mjs look … --compare before/                   # side by side with an earlier run
```

- **Renderer:** `WorldSurface` with the asset module offscreen (`exact_gpu::fixture`), as `unit_gallery` does. It works on Metal and on Windows.
- **Scene:** the model on a disc under the default `Environment`, or the game's `Environment` when run inside a game.
- **Output:** PNG contact sheets, not PPM.
- **Multi-part units:** `--with` composes several models at given offsets.

This is a tool, not an engine change, and it serves any authored model, not only Blender's.

## 7. D5 (deferred): the Blender kit ships in exact2

Deferred by the ruling in §8.3: the kit stays in Skirmish's `tools/blender/` until it has made more than one kind of unit and a second game wants it. What follows is the shape it would take.

The trial's `kit.py`, about 560 lines, is not specific to Skirmish:
- tagged parts, bevel with hardened normals, join and unwrap;
- a procedural wear and grime look baked to base, ORM and normal maps;
- glTF export inside the bake's allowlist (no tangents, single-sided, ORM shared);
- the team-paint split (or D1's `entityColor` marking).

**Proposal.**

- **Location:** `game/art/blender/`.
- **Verb:** `bun exact.mjs art` runs every `art/src/*.py` through Blender headless, writing `art/*.glb`. The bake already ignores `.py`. Then it runs the bake.
- **Setup:** `exact.mjs setup --check` reports Blender as optional.
- **Author time only:** the `.glb` outputs are checked in, and no build or CI step needs Blender.

Its README carries the Blender 5.2 pitfalls the trial paid for:
- `object.join` merges `None` material slots, so per-kind slots need distinct materials;
- `BevelModifier.use_clamp_overlap`, not `clamp_overlap`;
- the exporter writes `doubleSided` unless the material has backface culling.

## 8. Rulings

1. **D1: held.** Team colour is appearance, so it is derived in `present` with `MaterialOverrides`, as `game/README.md` already says. D1 changes no pixels. It saves one model file per articulated part and one batch per model, not one draw per unit, and it would add a second way to get the same look. Skirmish adds a `present` that writes team colours and ghost looks, which also keeps colour changes out of its saves and pins. Revisit if a second game, or repeated agent sessions, need team colour without `present`.
2. **Whole-model looks under D1: moot while D1 is held.** For the record, a fog ghost is appearance derived from the vision memory, so it also belongs in `present`.
3. **D5: deferred.** The kit is one art direction (hard-surface, worn, RTS-scale), proven on one unit, and it tracks Blender's Python API. It stays in the game. D4 is style-free and ships in exact2 now.
4. **Smaller calls, as recommended:** D2 adds a `lock` verb and does not auto-update; the copy-time check warns rather than fails, because plain `cargo` users rely on it. D3 takes both an app-wide and a per-model cap, and the default cap is unchanged.

## 9. Phasing and acceptance

| Phase | Work | Accepted when |
|---|---|---|
| P1 | D2 | Skirmish's stale lock prints the SDK-drift message; `bun exact.mjs lock` refreshes it with the network on; `test-rust` then runs. The bake's copy-time check warns in the same case. |
| P2 | D4 | `exact.mjs look` renders a turntable of a `.glb` or `.model` in under 10 s on Metal and Windows, at game and close zoom, as PNG. |
| P3 | D3 | `maxTexture: 512` brings the tank to about 3.1 MB per BC device (from 9.4), and the bake prints each model's cost. |
| Game | Skirmish `present` | Team colour and fog ghosts come from `present` via `MaterialOverrides`; the tank goes from six models to three, with matching pixels. No exact2 change. |
| Later | D1, D5 | Only on the triggers in §8.1 and §8.3. |

Out of scope: an engine change to the PBR model, TAA, colour grading, or SSAO defaults. The trial showed the renderer was not the limit; the authored assets were.
