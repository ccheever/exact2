## Summary

LLP 1153 makes a built site a directory any static host serves, and leaves a route
declared `render=request` or `cached` to a render server "the author chooses", not
something `serve` becomes (D3.4). The benchmark behind 1153 forbids rendering API data at
build: "the app must get all of its data from the API over HTTP at request time", and its
tests swap the API's data after the build. A page whose data is an API's then arrives
complete only if a server renders it when it is asked for. Next.js, SvelteKit and Astro
each did that by default. Every Exact page was drawn in the browser after its data
arrived, so the footer moved down (layout shift 0.11 to 0.13) and the largest paint came
late (about 2.2 s on Lighthouse's mobile settings).

Exact already has that server. `bun host/web-js/render.mjs <dist> --serve` renders a page
per request under Bun from the build's server bundle: the app's module against a small
DOM, in a fresh VM context per render, with the app's own data source, until nothing is
in flight or 3 s pass. It sends the head first (LLP 1048.005) and composes the page so the
runtime adopts it (LLP 1048.001). It needs no Rust, which 1153 D2 keeps out of a
website. No verb runs it, and nothing an agent reads names it.

**This amendment makes `serve` that server.** A route declared `render=request` or
`cached` is rendered per request by `serve` (D1). The build writes the server bundle
whenever a route renders on a server (D2). `serve` takes `PORT` from the environment, as
every Node host sets it (D3). A static host outside Exact still serves the shell for such
a route (D4). The `site` pattern declares its routes `render=request`, and the recipe says
which policy fits which data (D5). The Rust render host stays what an authored
workspace's render entry and delivery use (D6). Renders share an HTTP cache of what they
fetch, under the origin's `Cache-Control` (D7, built). A server-rendered page's head
fetches the runtime at low priority, which closes the first-paint gap §1 measured (D8, built).

## 1. What it closes, measured

six routes declared `render=request`; `npm run build` running `web-build --render js`;
and `npm start` running `render.mjs --serve` (ten lines, in place of the run's
57-line static server). A second variant ran the Rust render host instead (`app-render
--serve`, an entry copied from `apps/realworld`). Both variants passed all 54 of the
benchmark's tests, each built and tested in a fresh container.

Per render on the same VM (wall clock to the last byte, warm): the home page 70 to 330 ms
under Bun, 190 to 550 ms under Rust; Pikachu's page, the heaviest (every move table),
180 to 370 ms under Bun, 460 to 1,700 ms under Rust. The Rust host rendered this app

which `app.tamber` brings. That is the Rust host's to fix (D6); it does not change the
choice here.

### 1.1 First paint

First paint was still about 400 ms behind Next.js's: 1,201 to 1,399 ms across the pages,
against Next.js's 794 to 991 ms. It is not server time. Every render above fetched the API
cold, and the home document finished arriving at 360 ms; with D7's cache (the API sends
`Cache-Control: public, max-age=86400`) renders take 5 to 12 ms warm and the home document
is whole by 55 ms, and first paint does not move. Lighthouse's mobile score simulates a
slow network over the trace it took, and its simulation counts a high-priority script
requested before first paint as holding first paint. The head's `<link rel="modulepreload"
href="./app.js">` makes the 70 KB runtime exactly that. A browser does not wait for a
preload before painting, but the preload does compete with the page for a slow link.
Next.js's scripts are `async`, and so low priority.

Each variant below is the Bun-rendered app with D7's cache, measured back to back with
the others (Lighthouse, mobile, median of five, first paint in ms):

|---|---|---|---|---|
| Home | 1,351 | 935 | 967 | 920 |

| Move | 1,351 | 947 | 943 | 991 |

Either change takes about 400 ms off first paint on every page, which leaves Exact level

move (1,809 ms on the home page either way), and performance is 97 to 100 throughout. D8 takes the low-priority preload, which keeps the runtime's early start. Built, it measured 1,050, 997, 961, 782 and 953 ms on the same five pages, within one run's spread of the hand-made variant.

## 2. Design

### D1. `serve` renders a route declared `render=request` or `cached` per request

LLP 1153 D3.2's rule, with rendering added. For a request:

1. A file at that path is served as `serve.mjs` serves it today.
2. An HTML navigation whose path matches a route declared `render=request` or `cached`
   gets that page, rendered now: the head at once, the rest when the render settles or
   reaches its deadline; `no-store` for `request`; for `cached`, the page kept at the
   origin for 60 s, up to 64 locations, as `render.mjs` keeps it today.
3. A `render=build` route gets its built page; a `client` route gets `shell.html`.
4. Anything else is the `notfound` route, rendered, with 404.

`serve.mjs` and `render.mjs`'s server become one server. `serve.mjs` keeps what it has
right: generations, content types, dot-path refusals, brotli. `render.mjs` supplies
`renderer(dist)`, unchanged. One fix comes with the merge: `render.mjs --serve` today
renders every path, a `client` route included. `serve` gives such a route the shell, as
`serve.rs` does, since the author declared that it is drawn in the browser.

A render reads what LLP 1048.002 allows: no store, no cookies, no device facts. A source
that asks for one keeps its placeholder, and the client asks after adoption. A page for
one reader is not this amendment's.

### D2. The build writes the server bundle whenever a route renders on a server

`web-build` bundles `.gen/server.js` only when `--render` is not `none`
(`host/web-js/build.mjs:617`). Three runs built with `--render none` to keep API data out
of the build, which would leave `serve` nothing to render with. The bundle is written
whenever any route's policy is not `client`, and `--render` goes on saying only who
renders the `render=build` pages at build.

### D3. `serve` reads `PORT`

`serve [<dir>] [--port <n>]` falls back to `PORT` from the environment, then to 8765.
Heroku, Render, Cloud Run and the benchmark's harness set `PORT` and expect
`npm start` to listen on it. Each of the five runs read it by hand in the server it wrote.

Built (2026-10-31, at Charlie's request to make exact2 the fastest framework on the benchmark), with the scaffold to go
with it. `exact new` writes `"build": "bun exact.mjs web-build --out dist"` and `"start": "bun exact.mjs serve dist"`,
so a host's `npm run build && npm start` serves the release, compressed (LLP 1048.007 D6), on `PORT`. This amends LLP
1153 D3.3's `"start": "bun exact.mjs serve"`, which served the last development build. Each of the five runs also wrote
its own build and start scripts.

Beside the app's sources, `serve` also builds the site again when a source changed since the build, before it answers
a browser's navigation, as it builds a changed setting again at its start (LLP 1153 D4). A build that fails is the
answer, a 500 with its output. Agents building the Pokédex ran a build and restarted `serve` after each edit, 13 to 25
builds a session, where the other frameworks' dev servers rebuilt on their own. A site copied to a host, without its
sources, is served as it is.

### D4. A static host outside Exact still gets the shell

D3.4 stands for a host that is not `serve`. A `request` or `cached` route there serves
`shell.html`, and the page draws in the browser. `routes.json` (D3.1) carries each
route's policy, so such a host can tell which paths it is drawing late. `web-build --out`
says so once per such route, naming `serve` as the server that renders them.

### D5. The `site` pattern renders per request, and the recipe says when not to

LLP 1153 D8's `site` pattern has a list route that renders at build and a detail route
drawn on the client. Under D1 both routes declare `render=request`: the data of a site
whose data is an API is the data at request time. The recipe (`recipes/website.md`)
leads with the choice, one line each:

- **`render=request`**: the data is a live API's.
- **`render=cached`**: the API's answer holds for a while, and every reader sees the same
  page.
- **`render=build`**: the content is fixed when the site is built, such as docs or a
  landing page.
- **`client`**: the page is one reader's own, behind a sign-in.

`start-here.md`'s website row names `render=request` beside `serve`. An agent need not
find it in `apps/realworld`, as the one run that looked for it did and then went no
further.

### D6. The Rust render host stays where it is

`<app>-render --serve` (LLP 1048.000 D10) remains the server for an app that authored a
render entry, and delivery's (`scripts/deploy.mjs`). `serve` uses Bun's renderer
regardless:

- it needs no Rust, as 1153 D2 asks of every web verb;
- it adds nothing to build beyond the server bundle, against the Rust entry's four
  minutes cold in §1's container and a Hermes bundle fetched from a private release;
- it rendered this app faster.

The existing composition tests run both renderers over the same sources
(`host/web-js/document-render.test.mjs`). The Rust host's kernel-path fallback for a
themed scheme (§1) goes to `QUEUE.md`.

### D7. Renders share an HTTP cache of what they fetch

Every render's fetches go through one cache per server process
(`host/web-js/http-cache.mjs`), a shared cache as RFC 9111 defines one. A render is
anonymous (LLP 1048.002), so an answer one render was given may be given to any render.
The cache keeps a GET's answer for the lifetime the origin gave it (`s-maxage`, then
`max-age`, then `Expires`), and keeps nothing without one: there is no heuristic
freshness. It keeps nothing a shared cache must not keep:

- an answer marked `no-store`, `private` or `no-cache`;
- an answer whose `Vary` is `*`;
- an answer to a request carrying `Authorization`, unless the answer is marked
  shareable (RFC 9111 §3.5);
- an answer that came by a redirect, since the runtime checks where a redirect led
  against the app's grants.

It keys an answer on the request headers its `Vary` names. A stale answer still within
`stale-while-revalidate` (RFC 5861) is given while one refetch replaces it. It obeys a
request's `cache` mode and `Cache-Control` as a browser's cache does, so an app that
needs fresh data says so where it fetches. It holds at most 256 answers, 64 MB and 8 MB
for any one answer; the least recently given goes first.

This is LLP 1048.002 §3's rule that HTTP caches do the storing: the origin's headers
decide, and the server keeps no store of its own design. The Rust render host keeps no
such cache, which `QUEUE.md` records.

### D8. A server-rendered page's head fetches the runtime at low priority

In a page that arrives drawn (`render=build`, `request` or `cached`), the runtime adopts
the page; it does not draw it (LLP 1048.001). So the runtime's preload is marked
`fetchpriority="low"` (HTML's fetch priority attribute) in the head both renderers
compose: `render.mjs` `headOf` and `page.rs` `head_js`, and so are the preloads a Rust
page adds after its head and the Rust server's 103 `Link` headers (HTML's Link header
processing reads `fetchpriority`). The capture script still imports
the runtime after first paint, as the page's `data-activate` asks, and an `interaction`
page still drops the preload. The shell a `client` route gets keeps it at high priority,
since that page cannot paint until the runtime runs. §1.1 measured the change.

## 3. Costs

- **`serve` grows a renderer.** It is code that exists: `renderer(dist)` from
  `render.mjs` (175 lines), called from `serve.mjs` for the routes D1 names.
- **Every server-rendered route costs a server bundle at build.** It is the bundle
  `--render js` already makes.
- **A production site runs Bun.** It is already the toolchain a website needs (1153 D2).
  One process interleaves renders while they wait on the API, each in a fresh VM
  context, but a render's computation holds the others behind it. More than one core is
  the host's to use: run more processes behind its balancer.
