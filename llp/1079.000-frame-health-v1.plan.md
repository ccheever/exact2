## 1 Frame health as a key performance metric

Frame health measures whether visible content updates on time, moves evenly and responds promptly to input. It is a runtime quality target for Exact, alongside startup and resource use. FPS describes throughput; pacing and latency explain whether that throughput feels good.

### Targets

| Activity | Target |
|---|---|
| High-impact interaction on flagship phones | 120 FPS |
| Desktop interaction, including macOS | The display's supported rate, including above 120 Hz |
| Static content | Stay idle; do not render extra frames to improve a counter |

Assess requested rate, operating-system schedule and observed delivery separately. A 60 Hz schedule is a restriction when the requested target is 120 FPS. Report intentional lower-rate effects and known power restrictions explicitly.

### The key measurements

| Measurement | What it tells us |
|---|---|
| On-time updates | How often we meet known presentation opportunities |
| Cadence overdue time | How long a frame remains visible beyond its intended replacement interval |
| Content and input latency | Whether evenly delivered frames still show old content or respond late |
| Frame-time tails and worst gaps | Whether occasional stalls hide behind a good average |
| Evidence and coverage | What we actually observed, and where the result is unknown |

Report these per surface and activity. V1 has no blended app-wide score. Presentation feedback, rendering deadlines and callback timing remain distinct evidence levels. When a platform exposes only callback timing, label it as a proxy and leave presentation health unknown. Missing data cannot turn a result green.

### Readouts for people and agents

Agents use the existing `perf frames` operation. The development inspector presents the same snapshots in a human-readable panel. Both show target, observed cadence, timing distributions, evidence, coverage and unresolved observations.

On iOS and iPadOS, the four-finger dev menu adds **Show Frame Health** and **Hide Frame Health**. The card starts hidden and follows the existing menu gate, including in release builds where that menu is enabled. The enabled macOS Develop menu offers the equivalent action.

The card moves when dragged from anywhere on it and takes the touches within its bounds; touches outside it reach the app. It sits above the app viewport and below sheets and alerts. Moving it changes only its own compositor position; it does not change app layout or app state.

The card's figures and table refresh at most every half second, from the collector's publications, and its charts take each frame the app's clock already runs (§7.2). Moving the card pauses its formatting; scrolling the app keeps publication live in tracking mode. Hidden or idle readouts do no periodic work. The card reads existing snapshots and frames: showing it cannot create a display link, raise refresh rate, enable full tracing or override disabled collection. Compare its cost while hidden, stationary and moving, including over a full-window GPU canvas.

### Send recent hitches to an agent

On a physical iPhone, show the card, reproduce the issue, and choose **Share Frame Health…** in the four-finger menu. Share or Copy returns JSON text capped at **4 KB (4000 bytes)**, including metadata, evidence and the agent carrier newline. Exact writes no report file and performs no automatic upload. The card's own Copy button is for people: it copies a text summary within the same cap and a picture of the card, which the cap does not cover.

Capture retains the latest 16 events in fixed memory and exports only those at most 120 seconds old. Reports carry callback gaps, scheduled and requested cadence, nearby callback context, the largest observed apply in the interval, matching asynchronous owner/landing boundaries, workload flags, thermal/power state and build identity. They distinguish measured wall time from unobserved CPU/GPU/presentation work. Reload preserves the tail and labels each event's generation. Overwrites, expired events and oldest rows omitted to fit the wire budget are explicit; retained time is not guaranteed during a hitch storm.

An agent uses `perf frames capture start [ms]`, `stop`, `clear`, and `perf frames report`; a lease lasts at most 120 seconds. The card and agent lease own capture independently. One report encodes at a time, off main after a bounded copy; agent admission is at most once per 15 seconds. There is no periodic sender, retry queue or idle expiry wakeup. The [wire schema and device workflow](../docs/contract-for-agents.md#compact-frame-health-reports-on-physical-devices) explain all fields and limits.

### Collection overhead

Production collection must use bounded counters, histograms and queues. Recorder hooks must avoid allocation, locking, logging, I/O and tree traversal, with no additional measurement wakeups at idle.

The initial native targets are at most 1 microsecond p99 per record/reduce event, at most 4 KiB per producer, and at most 256 KiB of collector-owned storage per process. Whole-collector work targets at most 0.1% of one CPU core at 120 Hz and 0.2% at 240 Hz. These are proposed budgets to prove on devices, not measured claims. Platform listeners, observation callbacks, bridge calls and UI work all count.

### Delivery

The Apple slice includes bounded frame-clock counters with frame-interval, work, refresh-count and lateness distributions (§4.6), hitch reports, agent readers, native detail inspectors and draggable cards. The iOS and macOS cards also chart frame rate and frame time over the last 30 seconds. Bounded asynchronous owner and apply evidence is available while a UI reader or agent lease owns capture. Presentation, native-only animation coverage, full deferred-work deadlines, the shared window protocol and remaining host adapters are open. Qualify each adapter before production default-on. The collector may correctly report that an app misses its frame-rate target; that is a useful result, not a reason to weaken the metric.

Read the [measurement contract](#4-measurement-contract), [resource budgets](#5-production-recorder-and-resource-budget), [UI design](#72-app-indicator), [validation](#8-validation-and-overhead-experiments), or [implementation stages](#10-implementation-sequence-and-completion-evidence) for the details.

## 3 Research that shapes the design

FPS is throughput. Pacing is the distribution and ordering of presentation intervals. Uniform 16.667 ms intervals and alternating 8.333/25 ms intervals both average 60 FPS. A game-style timeline, frame-time distribution and worst stall reveal what the average hides. Keep CPU, GPU, waiting and presentation measurements distinct: these stages overlap.

Vsync aligns presentation with display refresh. On a fixed-rate screen, missing a slot can keep the previous picture visible for another interval. Variable refresh changes the available schedule, so one nominal period cannot classify all frames. Queuing can also preserve smooth cadence while increasing response latency. These distinctions follow [Android frame pacing](https://developer.android.com/games/sdk/frame-pacing), [Apple variable refresh guidance](https://developer.apple.com/videos/play/wwdc2021/10147/), [PresentMon's metric definitions](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md), and [Unreal's stage readouts](https://dev.epicgames.com/documentation/en-us/unreal-engine/performance-and-profiling-overview).

For CADisplayLink, `targetTimestamp - timestamp` describes the scheduled interval, and `targetTimestamp - CACurrentMediaTime()` estimates time remaining when the callback runs. Neither acknowledges that Exact's content appeared. `duration` is not a substitute for the actual scheduled interval. Frame-rate preferences are hints, subject to system policy. [CADisplayLink](https://developer.apple.com/documentation/quartzcore/cadisplaylink), [preferredFrameRateRange](https://developer.apple.com/documentation/quartzcore/cadisplaylink/preferredframeraterange).

Metal's `presentedTime` reports a drawable's onscreen presentation time; zero is not a successful presentation. With CAMetalDisplayLink, the submission deadline and predicted presentation time are separate. V1 does not replace the renderer's scheduling API merely to collect metrics. [Drawable presentation](https://developer.apple.com/documentation/metal/mtldrawable/presentedtime), [Metal display-link deadline](https://developer.apple.com/documentation/quartzcore/cametaldisplaylink/update/targettimestamp).

Android FrameMetrics reports rendering duration and, where supported, deadline and GPU duration. FrameTimeline provides expected versus actual presentation and jank classifications for supported paths. An Android window observation does not automatically cover separately rendered SurfaceViews. [FrameMetrics](https://developer.android.com/reference/android/view/FrameMetrics), [FrameTimeline](https://perfetto.dev/docs/data-sources/frametimeline).

Apple's animation hitch ratio supplies a useful system KPI. Its perceptual adjustments and tracked animation population differ from Exact's raw overdue-time calculation, so store and display it separately. Browser Long Animation Frames entries describe long work, not every missed high-refresh deadline. [MetricKit hitch ratio](https://developer.apple.com/documentation/metrickit/mxanimationmetric/hitchtimeratio), [LoAF](https://developer.chrome.com/docs/web-platform/long-animation-frames).

## 4 Measurement contract

### 4.1 Identity and time

Each metric identifies the process instance, session instance, presentation surface generation, display, source and metric-definition version. An incarnation identifies one lifetime of a process or source; a new incarnation requires a fresh baseline. Schedule epochs annotate observations and slot arithmetic but do not reset cumulative counters/histograms. Identifiers are process-local integers; app content is not copied into the collector. Surface reuse and reload require a fresh baseline. Display moves can preserve deltas, with the crossed displays and epochs reported; source/population changes cannot be silently merged.

Keep timestamps as monotonic integer nanoseconds in a declared clock domain. Convert platform clocks at the adapter boundary and retain calibration uncertainty. Never subtract wall time, the agent's seekable clock, GPU timestamps, and host timestamps without an explicit conversion. JSON encodes nanosecond counters as decimal strings to preserve integers above JavaScript's safe range. FPS and derived ratios may be floating-point values.

An event is a fixed-size record: kind, source/generation, frame token, schedule epoch, timestamp, optional deadline/predicted presentation, and flags. Each source declares which fields are supported. A shared commit sequence can identify submitted content but is not proof of presentation. GPU completion is also not proof of presentation.

### 4.2 Activity and expected work

Track three activity classes: continuous visual demand, one pending visible update, and idle. Demand is declared by existing scroll/transition/animation/frame-task/native-control paths. The collector is not itself a source of demand. An authored animation that intentionally targets a lower rate carries that intent. The card cannot keep the measured activity segment open.

For continuous demand, use platform-supplied expected slots or an independently declared schedule. Do not infer a lower target from slowed delivery. Anchor a fixed-rate epoch to each authoritative timestamp/sequence and use rational period arithmetic only to bridge the following gap. Genuine schedule changes close slot arithmetic at the boundary and start another; counters persist. For variable refresh without a complete expected schedule, report per-frame timing and mark slot counts unavailable across ambiguous gaps. An uncertain gap is coverage loss, not an implicit schedule change.

For a pending visible update, start first-response timing at its input or invalidation event. Where the platform supplies render deadlines, the response target is the first predicted presentation whose render deadline has not passed at that trigger; otherwise the platform-deadline lateness is unavailable and response duration remains useful. Record the chosen deadline with the token before work starts. Record submission and acknowledged presentation independently. Superseded updates coalesce to the newest eligible content; they do not create a dropped frame for every intermediate commit. Pending-only time contributes to response-duration/lateness distributions, not continuous-motion FPS or overdue-time ratios. The first response after idle is measured even though callback cadence needs a baseline.

Native scrolling, Core Animation transitions, browser compositor animations, video and platform chrome may update outside Exact's own frame clock. V1's proposed native-scroll and browser-motion observation is conditional on S0 proving that an activity-scoped observer neither changes the presented cadence/power policy nor undersamples the target. Reuse an existing link where available. For an extra iOS link, S0 compares range/default choices with observer off/on under the same independent presentation oracle. Asking for the panel maximum can raise the rate; `.default` can undersample it. Neither outcome qualifies. Apply the same test to the macOS fallback and browser rAF observer, including loss of idle suppression. If no nonperturbing source exists, production core does not run that observer and reports native/compositor motion unavailable or reduced-rate proxy coverage, which cannot pass a 120 Hz target. The reference journey stays in the results as unqualified.

Charge all accepted observation callbacks to the adapter benchmark. Start iOS demand on drag, programmatic scroll or transition start and end it on drag without deceleration, deceleration end, animation completion/cancel, visibility loss or teardown. Include interrupted and nested scrolls. Browser animation lifecycle signals open/close observation; activities whose lifecycle cannot be identified remain uncovered. No observer remains running at idle.

Backgrounding, minimization, occlusion and an app's own visibility changes end eligibility at the observed boundary. Do not bridge the gap on resume. Partial occlusion is not inferred from a tree walk. Platform visibility is the declared approximation.

### 4.3 Cadence and latency

Every sample can carry three different rates: requested content rate, the OS schedule, and observed delivery. The hardware maximum is context, not observed FPS. The product policy requests 120 for high-impact interaction on capable mobile hardware, and the supported display rate on desktop, including above 120. Paint-only motion and video may intentionally differ; report their category and policy rather than mixing them into the high-impact target cohort.

Intervals are 8.333 ms at 120 Hz, 6.944 ms at 144 Hz, 4.167 ms at 240 Hz and 2.778 ms at 360 Hz. These are presentation intervals, not a guarantee of that much CPU time after callback arrival. A render duration below one interval does not establish equivalent delivered FPS.

Known low-power, thermal, user-rate and display restrictions are context. Unknown restriction causes remain unknown. Do not declare an OS restriction solely because callbacks became slower, and do not exclude a thermally degraded app from field reporting. Separate restriction cohorts alongside the overall distribution.

Input-to-presentation measures the earliest relevant input included in the acknowledged frame. Without that join, report input-to-submit or input-to-commit under its own name. Software presentation feedback excludes input-device and panel response latency; it is not a physical input-to-photon measurement.

### 4.4 Metrics and denominators

| Metric | Definition and conditions |
|---|---|
| `expected_opportunities`, `missed_opportunities` | Slots during observed eligible continuous demand, with the expected schedule independently known; a missing callback cannot erase a known slot; source/evidence determines whether these are presentation or callback opportunities |
| `on_time_fraction` | `(expected - missed) / expected` over that same observed continuous population; null when the denominator is zero or its schedule/coverage is unknown |
| `cadence_overdue_ns` | Union of excess frame residency during observed continuous demand on one surface: after a valid replacement, the next replacement is due one declared residency interval later; a gap G with fixed residency B contributes max(0, G-B), assigned to the finalized window that completes the gap (§5.3) |
| `cadence_overdue_ms_per_active_second` | `1000 * cadence_overdue_ns / observed_continuous_ns`; Exact's raw cadence measure, separate from content lateness and Apple's perceptual ratio |
| `content_lateness_histogram` | Per acknowledged token, max(0, actual presentation - that token's intended presentation); measures pipeline delay even when cadence is smooth; unmatched content has no such value |
| `presented_updates`, `presented_fps` | Acknowledged replacements during observed continuous demand and count divided by that observed continuous duration; repeated scanouts are not updates; actual content freshness requires a content revision match |
| `callback_*`, `submission_*`, `render_deadline_*` | Separate proxy metrics using their own event populations and denominators; never alias them to presented metrics |
| `interval_histogram`, `lifetime_max_gap_ns`, `window_max_gap_bounds_ns` | Fixed-bin timing distribution; exact maximum since source incarnation; bounds on a requested window's maximum from its histogram delta. Never subtract lifetime maxima to invent a window maximum |
| `input_response_histogram`, `response_lateness_histogram` | Duration for joined pending updates and lateness against their declared response deadline; populations and unmatched/superseded counts are separate from continuous motion |
| `system_animation_hitch_ratio` | Native system value, source, unit, covered animation population and reporting interval; no conversion into Exact's raw metric |

An intended presentation is the platform's prediction for that particular submission, recorded with its token before submission. CAMetalDisplayLink's `targetPresentationTimestamp` is such a candidate, subject to S0's clock/source validation. A plain CADisplayLink callback target, rAF time, command-buffer scheduled callback or FrameMetrics deadline is not automatically a prediction for the drawable/content being submitted. Those paths report content lateness unavailable unless a distinct validated prediction exists. A declared pipeline model may supply an intended target only with an explicit versioned phase/depth constant qualified against the oracle before measurement; report that model as modeled evidence, not a platform prediction. Never fit or subtract a steady offset from the run being evaluated. Otherwise a real queue-latency regression would be normalized away.

For continuous 120 Hz motion, suppose a previous frame presents at 0 and its replacement is due at 8.333 ms but arrives at 25 ms. Cadence overdue time is 16.667 ms, with [8.333, 25) counted once. In the half-open window [0, 25), slots at 8.333 and 16.667 are missed; the slot at 25 belongs to the next window. Integer arithmetic uses the rational schedule rather than repeatedly rounding 8.333 ms. If subsequent frames arrive every 8.333 ms but remain 16.667 ms behind their intended targets, cadence overdue time stops accumulating while every token records 16.667 ms of content lateness. Both facts appear; smooth cadence cannot erase queued latency.

A read without an acknowledgment reports pending-update age and unresolved status, not proof that old content remains onscreen. Presentation counters are finalized only through a source's completeness watermark, where the adapter proves all relevant observations through that time were consumed. Sources without such a watermark finalize a gap only when its next valid acknowledgment arrives. Provisional pending exposure is separate and never added to monotonic cumulative counters; a delayed acknowledgment cannot make a published lifetime total decrease. A source that proves a still-unresolved deadline may report right-censored overdue bounds, outside finalized totals. A dropped or unknown acknowledgment makes the affected span unobserved. Readers mark a stalled publisher stale rather than fabricating current display health.

Only adapters that match intended content revision and target to presentation can produce content lateness or freshness claims. A drawable token alone supports cadence. For a canvas that captures native children into a texture, include that capture's commit revision as well as the drawable revision; otherwise report cadence only. One canvas's health does not establish the health of overlays or another canvas.

### 4.5 Evidence and coverage

Evidence belongs to each metric: `presentation`, `render_deadline`, `callback_proxy`, `submission_proxy`, `system_aggregate`, `virtual`, or `unavailable`. A source may provide several metrics at different levels. Independent validation is metadata, never an evidence-level upgrade.

Coverage includes eligible time, time with the necessary observations, unsupported activity categories/surfaces, lost events, unmatched tokens, clock uncertainty, sampling, capacity exclusions and generation discontinuities. There is no claim of complete frame capture where the platform cannot enumerate expected events. Distinguish `unknown` from `none` for losses.

Coverage is `observed_continuous_ns / eligible_continuous_ns`, with unobserved spans retained in the denominator. FPS and cadence ratios use observed time and are conditional; missing time neither fabricates low FPS nor permits a full pass. Pending-update coverage has its own triggered/matched/unknown counts. Do not average percentages, FPS reciprocals or percentiles. Merge only compatible raw totals/histograms by metric definition, source, activity, device and build, preserving schedule changes and target restrictions. Report per-session/workload distributions alongside totals. V1 presents surfaces independently; it does not sum simultaneous surfaces' active durations into an app-wide user-time score or treat snapshots taken at different times as one simultaneous observation.

### 4.6 Apple frame-clock measures

Exact's frame clock on Apple platforms is a `CADisplayLink`. These measures describe Exact's schedule and its own work, at callback-proxy evidence (§4.5); none of them observes presentation.

- **Frames.** A display-link callback that starts frame work is a frame: it sends a tick or frame-task advance to the owner, applies one itself, renders a canvas or advances native animations. On iOS, a tick, advance or fill runs on the owner thread and lands on the main thread later. While one is in flight, a callback skips the work it holds, so content can update less often than callbacks arrive. A canvas render draws when it records into the frame its GPU module submits next. One that draws nothing, as without its drawable, draws when a drawable arrives, and its frame waits for that draw. A callback that starts no frame work because earlier work is in flight is held. So is one whose canvas render only changes which frame a render still waiting on its drawable will draw, and one whose canvas wanted a frame but rendered nothing, as during AppKit's starvation backoff. A callback with no frame work due, such as one kept for a timer, is idle. Neither is a frame, and an idle callback ends the run. Owner work is registered before it is sent, since it can land before its callback returns. A frame's timestamp is the link's `timestamp`, the start of its scheduled interval ([optimizing for ProMotion](https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays)).
- **Frame time and frame rate.** Frame time is the interval between consecutive frames' timestamps within one run. A run ends when the session stops wanting frames, even while the shared link keeps running for another session; at an idle callback; and at a callback whose timestamp does not advance. So idle time is never a frame time, and a timestamp out of order bounds no interval. A callback is recorded, under the request that governed it, before the work it applied can end its run or change the request. Frame rate is the number of frame intervals divided by their total time.
- **Missed frames.** While the host requests a rate, missed frames are the requested slots in which no frame started. Slots lie on a grid at the requested period, whose origin is the first callback after a run starts or the request changes. Each callback takes its nearest slot, so timestamp jitter cancels over a run, and a slot counts once however many frames start in it. A callback's slot finalizes every earlier slot: those without a frame are missed. A held callback's own slot stays open, since a later callback may still start a frame in it, until the run ends. A schedule slower than the request shows as missed frames, as the app's own slow frames do. A new preference takes effect at the next callback, so the rate requested for the interval across a request change is unknown, and that interval counts no slot; slots already passed on the old grid, a held callback's open one included, stay counted. Without a request, missed frames are not counted.
- **Refreshes and pacing.** Each frame interval spans a number of scheduled periods (`targetTimestamp - timestamp`), its refreshes: the interval divided by the period, rounded, and at least one. The count is exact on fixed and adaptive refresh, so a 60 Hz or 80 Hz schedule is even at its own rate; it describes the schedule the link gave, not how long the panel showed a picture. Refreshes beyond the first are scheduled slots the frame skipped. A pacing change is a frame interval whose refresh count differs from the previous one's. An interval across a schedule change, including one a held callback saw, has no single period, so it counts no refreshes and no pacing change; it is counted as unclassified where it finalizes. Refresh counts from different schedules, in one run or across stopped time, convert to no single time.
- **Work.** Each frame has one work record: its start (its timestamp), its deadline and its finish. The deadline is [`targetTimestamp`](https://developer.apple.com/documentation/quartzcore/cadisplaylink/targettimestamp), by which the app must submit the frame's changes. The work finishes at the latest of the callback's return, the landing of the owner work the callback sent, whether that work's batch is applied or skipped as changing nothing, and, for a canvas render that drew nothing, the first draw after which no canvas render waits. A frame whose waiting render cannot draw, because its canvas left the screen or the source stopped, has no work record. Batches from input, timers and fills belong to no frame and add no record. Core Animation's commit after the apply is not observed, so work time excludes it. Work time is finish minus start.
- **Lateness.** A frame is late when its work finishes after its deadline, by finish minus deadline. Where the deadline carries no information, lateness is unknown and work time is still reported: the iOS 27.1 simulator dispatched 119 of 120 callbacks about 0.5 ms after their own `targetTimestamp`. The native-scroll producer takes its deadline from [`UIUpdateInfo.completionDeadlineTime`](https://developer.apple.com/documentation/uikit/uiupdateinfo/completiondeadlinetime).
- **Figures.** Durations are absolute-time histograms (§5.3), so a schedule change within a window changes no bin. A median is its bin's upper bound. The longest frame time, and the slowest work with its own budget (deadline minus start), are exact to the nanosecond for each half-second read (§5.3). A frame whose work is still in flight past its deadline is certainly late, and readers report it as overdue beside the finalized counts (§4.4).

## 5 Production recorder and resource budget

### 5.1 Architecture

The host owns the collector because the runner does not know when pixels appear. Use one Rust reducer for native hosts and a JS implementation for the web. A producer is one independently identified measurement stream; the current Apple sources are app callbacks and experimental native-scroll updates. Swift/Kotlin hooks append fixed numeric records to preallocated native storage through a bounded C/JNI entry; charge the crossing in the hook budget. Drain on the owner's existing frame work, demand transitions and snapshot requests, not only at 2 Hz. A full queue records loss; it cannot synchronously drain on a foreign callback thread. Conformance fixtures compare the two reducers. Avoid a new general observability framework or renderer dependency in non-GPU apps.

Separate three modes:

| Mode | Work |
|---|---|
| Off | Report collection as disabled; do not register a collector or record events |
| Core | Scalar counters, fixed histograms, demand/schedule bookkeeping, bounded event handoff and snapshots |
| Detail | Explicit, timed capture into a preallocated ring; additional causal diagnostics remain development-only and carry their own cost |

Core remains independent of plan-site counters, trace export, hatch diagnostics and source-map lookup. A late event takes a bounded record path; it never triggers string construction, a stack walk or an unbounded diagnostic scan. Snapshot reads do not clear counters or change the rendering target. Production hooks never panic, throw or terminate on malformed observations: invalidate that source/span, increment a bounded fault counter and continue the app. Exact's vendor modifications are Exact-owned for the hook rules; pre-existing platform/driver work is measured as adapter cost rather than claimed allocation-free.

Each producer owns its mutable state. Foreign-thread presentation callbacks write to bounded preallocated handoff storage with numeric tokens. No synchronous dispatch to the main thread, busy waiting, or lock acquisition is allowed in a frame hook. Choose an SPSC layout only after proving a single producer; multiple callback threads require independent producer storage or a bounded MPSC design. Every handoff is race-free under the language memory model.

Publish snapshots with preallocated ownership slots and acquire/release publication. Readers cannot access slots while writers mutate them. A full snapshot channel drops a publication, increments its own counter, and preserves metric counters. Reclamation on teardown waits outside the frame hook for registered callbacks, or uses generation-safe storage that cannot be reused until callbacks finish. No raw pointer into a destroyed session escapes.

### 5.2 Budgets to establish before production enablement

All timing numbers below are acceptance targets, not benchmark results.

| Budget | V1 target |
|---|---|
| Native record and reduce work | p99 added wall time ≤1 microsecond per event in calibrated lab measurements, including the boundary crossing; report maximum and cold/cache-contended behavior separately |
| Collector-owned CPU, all core hooks and snapshots | Attributed work target ≤0.1% of one core at 120 Hz and ≤0.2% at 240 Hz for a single continuously active reference window; establish each callback/observer/bridge term rather than attempting to resolve this solely from whole-process noise |
| Critical-path operations | Zero allocations, locks, I/O, logging, app-code execution or tree reads in Exact-owned hooks |
| Core native storage | ≤4 KiB per registered producer, including its event queue and pending-token table; ≤16 producers per process |
| Total native-owned storage | ≤256 KiB per process, including registry, queues, detail ring and local snapshot readers; assert actual layouts |
| Additional measurement wakeups at idle | Zero; externally requested reads are counted separately |
| Snapshot publication | Coalesce active updates at half-second intervals across the process; publish lifecycle boundaries immediately and serve explicit reads without an idle timer |
| Recent-hitch detail | Latest 16 events within the producer budget; report horizon 120 seconds, agent lease ≤120 seconds, card-owned capture lasts while shown. Report overwrite, age expiry and export omission independently |
| Report | ≤4000 UTF-8 bytes including carrier newline; one process-wide encode in flight; agent admission once per 15 seconds; no app-side disk writes or automatic network sender. The card's Copy adds a picture outside this cap |
| App card | Coalesce active numeric updates at half-second intervals; direct drag positioning follows native input without a new frame source; at most one overlay per window; measure stationary and dragging costs separately |

Registration occurs outside hot callbacks. At producer capacity, decline registration deterministically and list the excluded surface/category in the window coverage inventory. Do not steal an existing slot or silently sample only the fastest surface. Counter overflow saturates and invalidates affected deltas; source-incarnation changes require a fresh baseline, while schedule-epoch changes do not. An unmatched/in-flight token table overflow is event loss, not an inferred drop.

Record and disassemble the worst common and late paths: instructions, explicit loads/stores, touched bytes and cache footprint. Limit clock reads and reuse timestamps already supplied by the platform. A bounded instruction count and memory footprint are enforceable design properties; a universal execution-cycle or physical-memory-read ceiling is not, because caches, faults, frequency scaling and scheduling vary. Do not read performance counters or time the recorder on every production event to enforce its own budget. A storm producing more than 16 timing events overwrites the oldest retained events. The 120-second horizon is an age filter, not a guaranteed duration of history.

Measure OS callback registration/allocation and platform listener overhead as part of the whole adapter, even when Exact's reducer allocates nothing. For Android, consume needed scalars before returning because callback data can be reused; include the API's dropped-report count. JS uses preallocated numeric storage, avoids object creation in the recorder, and reports its measured heap/JIT/GC behavior rather than claiming the native storage budget proves browser overhead.

### 5.3 Measurement windows and live snapshots

Keep fixed cumulative counters/histograms by producer/source incarnation, not an unbounded set per schedule epoch. Epoch changes update `epochs_crossed` and rate/restriction summaries without discarding history. Absolute-time bins let deltas cross rate changes; rate-normalized distributions are deferred. The Apple implementation keeps four distributions per producer (§4.6). Frame times and work times each use 64 bins: 48 of 500,000 ns covering [0, 24 ms), 15 doubling tails from 24 ms and one open bin. Lateness uses 32: 24 of 500,000 ns covering [0, 12 ms), 7 doubling tails from 12 ms and one open bin. Refresh counts use 32: one for each count from 1 to 31 and one open bin. A retained hitch stores one absolute timestamp and its other times as 32-bit microsecond offsets and durations. Counters, distributions and retained hitches fit the 4 KiB producer budget (§10). Quantiles are bin bounds, not invented point estimates. Half-open bin edges and saturation are part of the definition. A producer collects only its declared interval and one latency/lateness population; additional populations need an admitted producer slot. S0 must demonstrate the queue/token/scalar layout still fits 4 KiB; if it cannot, reduce populations or change the budget explicitly before S1, not by hidden allocation.

Subtract coherent cumulative snapshots from the same source incarnation. Each metric's actual delta window is [finalized-through at the first snapshot, finalized-through at the second snapshot), not the read timestamps. A gap that completes after a read is wholly assigned to the next finalized interval; it is not retroactively clipped to that read. Keep read/publication timestamps beside those metric endpoints. Cadence ratios divide by observed continuous time inside the finalized window; any later unresolved tail remains visible separately. Arbitrary wall-time clipping without retained interval records is unsupported. An empty or old finalized window cannot imply current health.

The card's reader samples on the collector's publications, at most every half second, and keeps at most 60 samples over 30 seconds, each with the reads that bound it and with 16-bit bins. It reads nothing while the card is hidden, paused, detached, in a hidden view, in a covered window or a background scene, or too large to fit. The last 0.5 s is the newest sample: what was finalized between its two reads. The last 5 s and 30 s are the samples that began within them. An interval that began before a sample's first read is finalized, and counted, in that sample. A stall, an idle spell or a pause delays publications, so a sample can cover more than half a second; a sample that spans more than its window names its span in every label that uses it: the figures, pacing, accessibility and Copy. Quantiles are bin bounds from histogram deltas. Histogram subtraction, formatting and source joins happen in the reader. Core mode has no raw-frame timeline; the card's charts take each frame instead (§7.2).

Exact window maxima need per-read values: the producer keeps the longest frame time and the slowest work, with its budget, since they were last taken, and only the card's sampler takes them. Snapshot reads leave them, so an agent read or a report cannot take a hitch from the card. The sampler discards its first take after the card shows, which covers time it did not watch, and a window's maximum is the largest of its samples'. Agent cursor reads have only histogram deltas, so their window maxima are bin bounds; lifetime maxima are never subtracted.

Reader samples, the registry and queues count toward the 256 KiB process limit. A card's samples take under 39 KiB as malloc sizes them, and its charts' 30 seconds of tenth-of-a-second columns and last half second of frame timestamps under 13 KiB more, so a card holds under 51 KiB. The charts hold that storage only while the card reads, and their layers release their pictures when it stops. Cards and Details inspectors keep history only while open, and at most four keep it at once; another shows why it reads nothing, and a card starts at a publication after one closes.

The snapshot includes observation time, finalized-through time and publication time. An outstanding deadline reports unresolved age subject to §4.4's watermark rules. An in-app UI may freeze with the app; devtools mark a snapshot stale after two expected publication intervals while continuous activity is expected, and show observation age. Polling clients distinguish an idle source from a disconnected or blocked publisher.

## 6 Platform implementation

### 6.1 iOS and macOS

Instrument frame-clock entry, outcome application/submission, demand transitions and visibility boundaries. Make an Exact-work deadline proxy mandatory in core: record the monotonic end of Exact-owned apply/commit work and its applicable target from the frame hook, charging the extra clock read. This catches Exact work finishing after its target even with on-time callbacks; it does not observe all render-server or unrelated main-thread work. Mark turns without an applicable target unknown rather than charging them to a future frame.

S0 must prove a nonperturbing scroll/transition-scoped observer under §4.2 before production runs it. A qualified observer is a callback proxy and its cost includes the extra active callbacks. Qualification includes that observer and the end-of-work proxy. If the observer changes cadence, undersamples or exceeds budget, production native-scroll coverage remains explicitly unavailable/unqualified; do not delete the flagship journey to claim completion. The Exact-work proxy still observes supported app-driven work. Inability to observe scrolling efficiently is a reported v1 limitation, not a fabricated pass or a reason to change the app's schedule.

The native-scroll probe is development-only and gesture-scoped. Its passive `UIUpdateLink` leaves rate, continuous-update and presentation preferences at their defaults. The platform supplies a completion deadline but no validated cadence, so this source records deadline overruns and sample loss; callback FPS, gaps and cadence distributions remain unavailable. Forwarded app work is explicitly temporal context and never enters the native work population. Device experiments must establish observation-rate, energy and composition effects before any production enablement.

On macOS, elect exactly one observation authority per window/display. Reuse the session Frames link when active, otherwise a suitable pump link, otherwise the scoped observer. Authority handoff keeps the current schedule anchor and deduplicates by the platform timestamp/target pair. Heavy-leaf, hover, follow and press links supply activity/work observations but cannot create additional expected slots for that window. Two windows with one canvas each use at most two window-schedule producers, two work producers and two canvas feedback producers; additional latency populations count toward the sixteen-producer limit. Frame opportunities are never multiplied by the number of links or sessions sharing a window.

Keep the run-loop overrun probe a separately costed adapter feature, initially development-only. `beforeWaiting` does not prove which Core Animation transaction was displayed or establish a universal commit deadline.

The Metal feasibility stage inspects the actual wgpu-hal presentation patch and drawable lifetime. Rename the existing `gpu_on_presented`/`shown` lifecycle signal as scheduled; it is process-global, not per-surface display feedback, and cannot feed health presentation metrics. Prototype a distinct `MTLDrawable.addPresentedHandler` path reading `presentedTime` and `drawableID`, with bounded generation-safe mapping back to surface/content tokens. A no-capture shared block is a hypothesis to test, not an allocation-free guarantee about Metal. Include any block creation, registration and dispatch cost in qualification. The callback must not panic or block. Preserve native-children capture revisions or limit that canvas to cadence evidence. If a broad backend fork is required, keep presentation metrics unavailable until a focused change passes the budget.

V1 does not import MetricKit into ExactKit or add a linked framework for this KPI. An embedder that already collects native animation aggregates can display them alongside Exact snapshots with their original source/window, outside the collector's schema arithmetic. A separate future opt-in capability may supply MetricKit integration. Its deployment floors, macOS support and startup cost would need independent verification; a GPU-free app must not acquire a renderer dependency here.

Audit macOS press feedback and all rate overrides; use the window's actual screen, follow display moves and changes, and do not retain a 120 cap on higher-rate screens. Preserve intentional lower-rate effects. Audit the iOS path's explicit 120 cap against current mobile hardware; changes above it follow actual supported rates rather than a hard-coded new ceiling.

macOS app work and per-window press display links request the current display’s maximum for full-rate work, including rates above 120 Hz. Paint-only work retains its 60 Hz policy; timers use the platform default. Requested rate is reported separately from observed callback cadence. Window/screen changes update the preference, and occlusion, minimization and teardown break baselines. These preferences are hints and do not certify that content was presented at that rate.

A targeted diagnostic can separate commit duration, the platform's completion deadline and a diagnostic drawable's presentation. A diagnostic layer's presentation is not proof that particular Exact content appeared, and extra Metal layers/commands can change composition and direct-to-display eligibility. Any such probe stays opt-in and requires matching by submission identity, coverage/loss accounting and the same observer off/on device experiments before production use. This plan reports those stages as unobserved.

### 6.2 Android

Add an Android window FrameMetrics adapter with API-level feature checks. Copy supported scalar values into bounded storage on the listener thread; never retain the reused callback object. Record drop counts and distinguish rendering deadlines from presentation. The Exact owner thread's Choreographer timing is runtime scheduling data, not window FPS.

### 6.3 Web

Observer-only callbacks remain proxy evidence; commit timing is a separate metric. Put integration in a separate module because `host/web-js/rt.js` is already near its source-line cap.

Retain target intent independent of observed cadence. The existing lowest-median estimator is descriptive `estimated_callback_period`, not OS schedule authority. Even a prior fast segment is not proof of the current hardware schedule. LoAF enriches detail where supported, with no inference from absent entries. Unsupported native/compositor lifecycle categories, cross-origin iframes and independent video remain coverage exclusions. ## 7 Human and agent readouts

### 7.1 Shared protocol

The Apple API returns `exact.frame-health.metrics/2` from `perf frames health` and `exact.frame-health/2` from `perf frames report`; the [agent guide](../docs/contract-for-agents.md#compact-frame-health-reports-on-physical-devices) defines both formats. The common cross-host protocol below is planned. It extends the existing `perf frames` operation without adding an agent operation. Android and Windows need new host-side answers for this existing operation. Replace misleading callback-as-presented field names and Metal's scheduled lifecycle names in current clients in the same change; Exact is pre-1.0 and needs no parallel compatibility API. Cursors retain source incarnation and definition identifiers; schedule changes return `epochs_crossed` instead of resetting the baseline. A source reset or incompatible definition requires a fresh baseline (`baseline-required` in the Apple API).

Apple readers share `exact.frame-health.metrics/2`. A caller supplies a cursor to obtain comparable cumulative deltas; generation changes and invalid populations require a fresh baseline. Frame intervals and work records each carry their own finalized-through watermark. Readers take the collector's publications, which one process-wide batch makes at most twice per second during ordinary activity, with no idle timer; the card's reader retains 60 typed samples (§5.3). Inspection and the card own detail capture independently of the bounded agent lease. `state` contains only UI apparatus metadata. Reports are capped at 4000 UTF-8 bytes including the carrier newline, keeping the newest evidence when trimming.

The following illustrates the proposed cross-host schema; it is not a current Apple response. Production does not enable the agent endpoint.

```json
{
  "schema": 1,
  "definition": "exact-frame-health-1",
  "process": 1,
  "session": 2,
  "surface": {"id": 3, "generation": 1},
  "schedule_epoch": 4,
  "state": "active",
  "window": {"from_ns": "1000000000", "to_ns": "6000000000"},
  "rates": {"requested_hz": 120, "scheduled_hz": 120, "observed_callback_hz": 118.4},
  "metrics": {
    "presented_fps": {"value": null, "evidence": "unavailable", "reason": "no_presentation_feedback"},
    "callback_interval": {"samples": "592", "evidence": "callback_proxy", "histogram": {"unit": "ns", "layout": "exact-frame-interval-1"}},
    "callback_missed_opportunities": {"value": "8", "expected": "600", "evidence": "callback_proxy"}
  },
  "coverage": {"lost_events": "0", "presentation": "unsupported", "excluded": ["native_compositor_animations"]},
  "instrumentation": {"mode": "core", "detail": "off", "snapshot_publications_lost": "0"}
}
```

Each metric includes its own interval and coverage if these differ from the envelope. Absent features use null plus a reason, not zero. The final protocol also carries clock domain, uncertainty, observation and publication timestamps, activity class, source, build, platform and restriction context. Keep field sets bounded and include truncation. There are no per-node labels or app strings in core replies.

The driver provides bounded JSON and a concise text summary. Clients poll cursor reads at most 2 Hz; the existing JSON request/reply carrier gets no unsolicited messages or subscription mode. A malformed or unbounded window/detail request is refused with what happened, why and the supported bound. Virtual-clock operations return `virtual` and no physical assessment.

For native live journeys, launch/attach using `--timing platform` (`EXACT_AGENT_TIMING=platform`) only after S0 proves production scheduler parity. The Apple implementation now gates frame tasks, timer scheduling, timer firing and asynchronous fills on the frozen-clock predicate, with a real-display regression for `every(frame)` and asynchronous owner submission. macOS scrollbar/reorder/press paths use the same distinction. Phased macOS trackpad replay is explicitly refused under platform timing until completion can be acknowledged reliably. Audio/MIDI/video, permissions and other agent overrides still require workload-specific qualification; live transport alone does not prove complete production parity. Frame tasks must not disappear from the measured build. A carrier that cannot preserve production scheduling certifies a normally running development/release app through its local snapshot/trace facilities instead; no automatic live pass is available.

During live measurement, refuse every operation that takes the clock before executing it. This includes explicit `clock` operations, `clock settle`, held-state paths that perform implicit takeover, virtual films such as `screenshot over`, and any compound drive that invokes those operations. S0 produces the exhaustive source-derived operation list and installs one common takeover guard, including direct protocol calls. The driver reads a baseline, drives only validated real input operations, and reads again without takeover. Add `perf frames live <ms>` for Apple/JS autonomous windows as well as wasm, capped at 30,000 ms. Native waits occur in the driver, never on the app's main thread. A virtual native session refuses with relaunch instructions. The web JS live adapter must lend its virtual clock to wall time and restore it monotonically or refuse by name. Windows' missing carrier support is explicit S3 work.

### 7.2 App indicator

The card shows §4.6's measures for the session's app source in a fixed, compact layout. At a width of 320 points, its rows are:

| Row | Height | Contents |
|---|---|---|
| Header | 44 pt | Close; the title, which opens the definitions; the status button; Copy at the right |
| Context | 36 pt | Requested rate and any system limit; the display |
| Figures | 45 pt | Frame rate and missed frames, for the last 0.5 s and the last 5 s |
| Pacing | 41 pt | A verdict over the last 5 s, then the counts behind it |
| Toolbar | 40 pt | Charts or Table, as a segmented control |
| Chart area | 200 pt | The frame-rate chart (80 pt) and the frame-time chart (104 pt), 16 pt apart; or the table |

Each separator has 4 points of space on either side, and the card has 10 points of bottom padding. Close and Copy are 32 points wide, in the card's top corners, and every control's touch target is at least 44 points. The iOS and macOS cards share this design. On iOS the whole card grows with the text size, as far as its window allows.

**Showing and hiding.** The iOS/iPadOS four-finger menu offers **Show Frame Health**
or **Hide Frame Health** according to that window's local choice, even when a modal
obscures the card. It also offers Details and Share. Preserve the existing tap/hold
and double-tap reload gestures. `EXACT_DEV_MENU=0` disables this UI; embedders install
neither a menu nor a card automatically. Release apps with the menu enabled offer
the same controls. There is no manifest `hud` field. Showing a disabled collector
explains why collection is unavailable and does not enable another sampler.

Each new window/session starts with the card hidden. Close, or Hide in the four-finger
menu or the macOS Develop menu, removes it; shown again in that session, it returns to
its corner. The macOS Develop menu resolves the eligible window through the responder
chain and disables its controls when none exists. Other hosts use their existing
inspector. A tvOS readout is display-only and adds no focus stop or drag gesture.

**Stacking.** The host supplies a container above the Exact viewport and below
controller presentations. On standalone iOS, the overlay is a sibling above
`exactView` inside `Controller.view`. An embedder supplies an equivalent container.
Sheets, alerts, the dev menu and system permission UI remain above the card without
polling or custom dismissal callbacks. Moving the card must not change its stacking
order, create a full-screen window or resize the app viewport. S4 tests this
arrangement through native presentations.

**Input and position.** The card takes the touches within its bounds. A press
anywhere on it, on a button or the title too, drags the card once it moves 4 points.
A press that does not move is a tap: it presses the control under it, and on a chart
expands that chart to the whole chart area or returns it. Touches outside the card
reach the app, and app gestures there keep their precedence. The card is opaque, so a
touch passed through it would reach controls the person cannot see. On macOS the
pointer follows the same rules. Accessibility actions move the card to any corner.

Dragging updates only the card's position, without app-state writes, app layout,
metric formatting, app-tree geometry queries or preference writes, and keeps the card
within its window's safe area, above any keyboard. On release the card springs to a
corner of that area: the one nearest where it would come to rest under the platform's
normal deceleration, as Picture in Picture chooses its corner ([Designing Fluid
Interfaces](https://developer.apple.com/videos/play/wwdc2018/803/)). A press held
still for 50 ms before it lifts carries no momentum. A press during the spring stops
the card where it is drawn, and one that does not drag returns it to its corner. The
card keeps its corner through rotation, resizing, keyboard and safe-area changes, and
a spring under way turns toward where the corner is. A new session starts in the
top-left corner; backgrounding, presentation or teardown cancels an active drag.

**Status and figures.** The status button reads Live, with an activity symbol, while
the session wants frames, and Idle once it stops; a stretch of held callbacks is not
idle, and pacing then reads "No frames". A tap pauses the card's figures and charts,
not collection: the reader stops reading, so the face, accessibility and Copy describe
the same samples. The button reads Paused with a pause symbol until a second tap,
after which the first sample covers the paused span and the row names it. It has one
fixed width and a 44-point touch target. The context row names the requested rate, or
that none is requested, and a system limit when the schedule was slower than the
request; its second line names the display. The figures give the frame rate and missed
frames for the last 0.5 s and the last 5 s; both rates are averages over their window.
Where a window covers a different span (§5.3), its row names that span. A figure
without data shows "—", never zero.

**Pacing.** Over the last 5 s, pacing gives a verdict from refresh counts, then the
counts behind it, so every frame is counted and the line has a bounded width. When
every frame held the same number of refreshes, the verdict is "Even at 120 FPS" for
one refresh or "Locked at 60 FPS" for more, with a count such as "600 frames at
8.3ms". Otherwise it is "Uneven", with the most common frame time and the rest as one
count with their range, such as "597 frames at 8.3ms, 3 at 25.0ms to 50.0ms", or "3 at
25.0ms or more" when the range reaches the last bin. When the schedule changed within
the window, refresh counts convert to no single time (§4.6): the verdict is "Schedule
changed", with the count of frame intervals across the change, and the counts are in
refreshes. Counts of 1,000 or more are abbreviated on the card and given in full in
Copy, and a line too wide for its space shrinks to fit, as a label that adjusts its
font size does. On a display that refreshes when each frame is ready
(`NSScreen.displayUpdateGranularity` of 0), refresh counts do not apply, and pacing
gives the frame time that 99% of frames came within.

**Charts.** Both charts take each frame the app draws and show the last 30 seconds as
tenth-of-a-second columns. Within a run of frames a column's lines reach back to the
frame before it, across any columns without frames, so a slow app still draws a line;
gaps fall where a run ended, as when the app idles, the card pauses or a generation
begins. The frame-rate chart plots the frame rate's moving average over the last half
second, at each column's newest frame. It runs from 0 to the requested rate, or the
display's maximum without a request; its top gridline is dotted as the target, and
further gridlines fall at halves of the top, or at quarters when the chart is
expanded. The frame-time chart plots each column's longest frame time in blue and
slowest work in orange, against that frame's own deadline, dotted, so every hitch
shows at its own height. Its top is twice the target frame time: the requested period,
or, when the app runs slower, its 30-second mean frame time rounded to whole
refreshes. Four gridlines divide it, the zero line is a step stronger than the
gridlines, and a value past the top ends at a caret. Lines are 1.25 points.

**Table.** The table gives, for the last 5 s and the last 30 s, what the face does not:
median and maximum work time, late frames, how late the median late frame finished
("Late by"), maximum frame time and pacing changes. Its caption states the deadline,
such as "Deadline: one refresh, 8.3ms (120 FPS)", or, when the schedule changed within
30 seconds, "Deadline: one refresh, now 8.3ms (120 FPS)". A median shows its bin's
upper bound, never above the window's exact maximum. Where lateness is unknown (§4.6),
late frames and Late by show "—".

**Copy and definitions.** Copy puts one clipboard item with a text summary and a PNG.
The text names every figure with its window, such as "Max work time: 4.6ms (last
0.5s), 20.0ms (last 5s), 45.8ms (last 30s)", within 4000 bytes. The picture shows both
charts and a table of every figure, with right-aligned tabular columns, outside that
cap. After a copy the button shows a checkmark for 2 seconds. A tap on the title,
which shows the same pressed fill as the buttons, opens a sheet that defines each
figure and names what Exact does not measure: presentation, compositor and GPU time,
Core Animation's commit and input latency.

**Words.** Frame time is the time from one frame to the next; the card never says
"on screen". A near miss is a frame that barely missed its deadline. A number and its
unit take no space ("8.3ms", "5s"), and figures use no "<", "average" or middots.

**What the card does not show.** The card's frame rate counts §4.6's frames, a
callback proxy; presentation FPS requires presentation feedback, and the charts do not
establish that content appeared at the plotted rate. The core keeps no per-frame
timeline; the card's charts keep their own 30 seconds of columns while it reads.
Detail shows only retained events, with gaps and overwrite counts.

**Drawing.** Draw nothing translucent. Colors are opaque: Exact's translucent roles
(secondary label, separator, fills, hover and press washes) are composited over the
card's background ahead of time. The card, its controls and its charts use no blur or
shadow, and every button has opaque hover and pressed fills. Use native text with
tabular digits in reserved columns, so changing numbers move nothing; changing numbers
must not resize the card or relayout the app. Avoid raster readback and continuous
effects. Reuse views and layers. Where the whole card does not fit, it leaves out its
toolbar and chart area.

Each chart's labels are drawn by hand on the card's opaque surface when its scale or
the view changes. Its gridlines and lines are one opaque layer over its plot, wider
than the plot by five seconds of axis, which shows each new picture, place and size at
once, with no implicit animation. The layer moves left by the time frames advanced, in
whole device pixels, and redraws only the columns they changed, from the line into the
previous frame's column to the newest frame's; once it has moved five seconds, it is
drawn whole again. Dotted lines keep their dashes' place in time, and each run of
columns at one height is one segment, since Core Graphics spaces dashes unevenly along
many short ones.

**Updates.** The figures and table update at most every half second, from the
collector's publications; lifecycle boundaries may update them immediately. The charts
move only as frames arrive: the frame hooks only store each frame and the charts draw
after them, so nothing draws between frames, and an idle or paused card's charts hold
still. The card adds no display link: it takes the frames the app's own clock already
runs. While the person moves the card, formatting pauses, and the newest snapshot
shows when the drag ends. App scrolling keeps the charts on the app callback source.
Publication uses common run-loop modes, including touch tracking. The experimental
native-scroll source remains a separate choice in Details because its cadence is
unknown. Position updates follow native input and have no measurement refresh-rate
limit.

**Reading and lifecycle.** Showing the card binds a reader to existing snapshots. It
must not create a display link, request a higher rate, enable plan-site/hatch
diagnostics or call `FrameSampler.reply()`. Optional bounded hitch capture follows §1.
Collector adapters may use only the observation callbacks qualified under §6. Stop
reader work on idle, background, container detachment, occlusion, Hide and teardown.
Show idle once and leave no redraw timer running. Release reader history and the
charts' storage on Hide/teardown, and resume with a valid baseline. Do not poll the
view tree to infer partial modal coverage.

**Accessibility and agent tools.** Identify the card and its controls as host UI,
outside app node identifiers. App findings, selectors and `tree --ax` describe the app
and leave the card out. Order the card's elements after app content without making the
card modal. Native modal accessibility takes precedence. `state`, window screenshots
and `check` report visibility and window-local bounds. Screenshots retain the visible
card, and comparisons report any resulting obstruction. Normal agent drives start with
it hidden.

Use text and symbols alongside color: the status names its state, a system limit is
written out, and each chart's accessibility label summarizes its lines. A disabled
collector says why. Missing data shows "—" and cannot read as healthy. The card states
no pass or fail of its own, so proxy data never shows as a presentation pass. Avoid
repeated accessibility announcements.

**Cost.** The card's CPU, GPU and compositor work counts toward its measured cost even
though it does not open an app-activity segment. Keep that cost in presentation
outcomes. An in-process chart cannot update through a blocked main thread; remote
devtools must detect that stall. Qualify hidden, stationary and moving-card overhead
under §8 before making performance claims.

### 7.3 Exact devtools and agents

Add a frame-health section to the existing development inspector, by selected build/session/surface. Show requested versus scheduled versus observed cadence, evidence, coverage, overdue time where supported, distributions, longest stall and response latency. Distinguish clock domains and surfaces in detailed timelines. Correlate existing commit/source information only when an explicit detail capture supplies tokens; core capture does not run attribution.

Agent tooling returns the same facts and separate assessments for schedule cadence, target delivery and content latency. Each has scope, source, evidence, policy version, predicates and one result: `pass`, `proxy-pass`, `fail`, `restricted`, `insufficient-evidence`, or `not-applicable`. There is no unscoped top-level pass.

V1 policy predicates are explicit:

1. Idle with no eligible work is `not-applicable`. Virtual, stale, disabled, unknown schedule, an empty population, lost/unmatched observations or incomplete required activity coverage yield `insufficient-evidence` for a full-window pass.
2. An independently known schedule below the requested interaction target yields target-delivery `restricted`, with known or unknown reason. A 60 Hz schedule cannot pass a requested 120 Hz target even when every 60 Hz slot is met. Observed callback rate alone cannot establish a restriction or successful OS schedule.
3. A complete callback/render population with no missed/late reference deadlines can yield only `proxy-pass` for that proxy's declared scope. Presentation target delivery remains insufficient without presentation or the independent certification oracle.
4. Presentation cadence `pass` requires complete observed continuous coverage, independently known requested/scheduled rates that meet the target, no missed opportunities and no cadence-overdue time beyond timestamp uncertainty. Content-latency `pass` additionally requires complete intended-content matches and no late token beyond that uncertainty. Borderline classifications are uncertain, not forgiven as on time.
5. A valid observed failure yields `fail` for the affected assessment even if the rest of its window is missing. Persist both the failure and incomplete coverage. A known restriction is a separate target result and does not erase observed cadence/latency failures.

On Apple platforms each reply carries these assessments under `exact-frame-health-policy/2`, over the same window as its counts and from §4.6's measures.

Cadence compares frames with the platform's schedule: a frame interval that held more than one refresh skipped scheduled slots, and a late frame, or one still in flight past its deadline, missed it; either fails cadence. A window without callbacks is idle only when the source has stopped. A running source that has sent no callback for two publication intervals, as through a blocked main thread, is stale, and a window with a callback whose timestamp went backwards is incomplete; either leaves cadence at best `insufficient-evidence`, while a failure already observed stands. An interval across a schedule change counts no refreshes, so that window's cadence is insufficient unless a failure was observed; a change across stopped time interrupts no interval and is not counted. Lateness is unknown on the iOS simulator (§4.6), so there cadence is at best `insufficient-evidence` (`simulator-deadlines`).

Target delivery compares frames with the request: it is restricted when either end of any frame interval was scheduled more than 0.1 ms slower than the request that governed that end, and otherwise fails on missed frames, even in a window that saw no callback. Spatial motion and canvases request the display's maximum, and paint-only motion 60 Hz. Frame tasks and timers run at the platform's default rate without a request, so a window of only those has no target, while its cadence is assessed against the schedule like any other.

With callback evidence only, cadence is at best `proxy-pass` and target delivery at best `insufficient-evidence`. Content latency is unobserved. A simulator, Low Power Mode and a serious or critical thermal state at the read are reported as context, not as the cause.

The card states no pass or fail: its figures are the facts these assessments read, from the same counters, so the two cannot disagree, and proxy success never shows as a presentation pass. Cursor reads use existing development read authorization. Production exposes only the local embedder snapshot API; no remote control or discovery port is added.

## 8 Validation and overhead experiments

### 8.1 Accounting and integration tests

Use existing unit/integration suites for the pure reducer. Check steady cadence at 60/120/144/240/360; one missing frame; an unresolved final stall; delayed feedback without a real stall; overlapping stale intervals; smooth cadence with fixed queued latency; a healthy pipeline with a valid per-submission prediction and the same pipeline with no prediction; one sparse tap; intentional lower-rate content; a late first update after idle; superseded input; mode change during a stall; frequent ProMotion rate changes; 59.94 Hz over several minutes; variable refresh without a schedule; background/resume; no observations; loss/overflow/saturation; surface reuse and a late teardown callback; mixed sources; snapshot coherence and two readers. Include a lifetime maximum before the cursor that exceeds all new gaps, a gap straddling the initial read but not its finalized watermark, a stale children texture in a fresh drawable, several macOS links on one vsync, and a web segment that never reaches its reference rate. Timestamp uncertainty and exact bin/window boundaries need expected results.

Verify that missing evidence returns null/insufficient, that a slow producer cannot erase a denominator, and that the card cannot keep the frame source running. Test active native scrolling while Exact's own frame link is paused. Race and allocation checks cover every callback mode, including late and teardown paths. Conformance fixtures compare host reducers on the same events; they do not certify physical FPS.

For the overlay, drive the actual four-finger menu's Show/Hide action. Verify dragging from anywhere on the card, a tap that expands a chart and one that returns it, touch pass-through outside the card, unchanged four-finger reload/menu behavior, no app gesture takeover, safe positioning through rotation/keyboard/window resize, accessibility movement, independent windows and cancellation during menu/background/teardown. Check root navigation, an app sheet/alert, the dev menu's actions/dismissal and a system sheet all stack above it without re-raising the card. Check logical Show/Hide titles while obscured, macOS window targeting, tvOS focus exclusion and host-apparatus reporting in AX/state/screenshots/check. Show/Hide on a disabled collector must add no sampler/link. Repeated hide/show must neither leak views/readers nor restart collection. Verify that text formatting stops during drag and idle/hidden states, and that showing, moving or hiding the card changes neither app bounds nor app activity counters.

### 8.2 Independent display validation

Use release builds without debugger, coverage, screenshot capture or detail tracing in normal overhead runs. Validate separate diagnostic runs with Apple animation hitch Instruments/XCTest metrics, Metal presentation records, Android FrameTimeline and desktop PresentMon/DRM observations. Each validation recipe states precisely which surfaces and activity it covers. A camera is optional for checking physical input-to-photon behavior; software timestamps must not claim panel-response measurement.

Induce known CPU stalls, GPU stalls, queue pressure, native-only scrolling, compositor-only animation and missing presentation reports. Establish which failures each adapter detects and which it cannot. Require no false presentation success for injected misses; near-boundary mismatches are bounded by recorded clock uncertainty, not forgiven by a generic millisecond tolerance. A source that cannot match tokens remains a cadence source.

### 8.3 Paired overhead experiment

Compare the same optimized executable with collector off, core on, core plus indicator, and separately detail on. Off must bypass adapter registration, not merely ignore events after paying callback costs. Include non-GPU apps and confirm they gain no renderer/framework dependency. Repeat cold launches and idle/resume as well as steady animation. Use the same workload replay, brightness/power policy, display mode and thermal starting state within a block; randomize or alternate order to limit drift.

Attribute collector cost component by component: calibrated record/reducer/bridge cost times measured event rates, snapshot cost times publication rate, plus the separately measured scoped observer/listener cost. Measure each term on the reference device, include cold and contended cases, and report an upper estimate and uncertainty. An instruction count is supporting evidence, not equivalent to CPU time. No component may disappear because it runs in an OS callback. Native sampled timing can validate tails after clock overhead is calibrated; browser cost uses batches because its clocks cannot resolve individual microsecond events. Hardware counters are lab-only.

Use at least ten paired 30-second active blocks per primary device/workload and a ten-minute idle pair for a whole-app non-inferiority check, not as the sole proof of the 0.1%-core attribution target. Predeclare one-sided 95% confidence bounds: extra missed opportunities at most 0.1 percentage point, extra p99 interval at most 5% of the scheduled interval, and extra whole-process CPU at most 0.5 percentage point of one core. A reproducible new stall/fault fails regardless of the averages. These are experiment margins, not the target-rate certification or field SLO. Report intervals that cross a margin as inconclusive; do not increase margins after observing the data.

At 240/360 Hz the p99 margin is finer than the recorder’s 500-microsecond histogram bins. Use platform/oracle raw timestamps for that outcome; the production histogram cannot resolve the acceptance margin. Any oracle used in a pair runs identically in both arms, with its presence/cost recorded. Keep those oracle-assisted display pairs distinct from untraced CPU/energy pairs and separate full diagnostic traces. If the available oracle perturbs cadence or cannot supply adequate resolution, display non-inferiority remains inconclusive, not inferred from coarse bins. No diagnostic-only result is presented as an untraced p99 measurement.

After at most three experiment rounds, an inconclusive adapter remains opt-in. Charlie Cheever or his human delegate owns a subsequent budget/scope decision, supported by recorded uncertainty; no agent silently qualifies it or changes thresholds. Missing hardware likewise leaves the result uncertified. Whole-app pairs cannot substantiate a universal zero-overhead claim.

Measure whole-adapter CPU time, callback counts, allocations, memory, render/interval tails, missed deadlines, launch time, snapshot work, detail loss, and OS energy/power estimates with their resolution. The record/reducer target is necessary but not sufficient. Core fails enablement if it changes refresh policy, adds idle wakeups or produces a reproducible presentation regression. Broader regressions that cannot be attributed remain unresolved until the paired experiment explains them.

card overhead gets its own report and a product decision if its cost exceeds 0.5% of one core or measurably regresses display/energy behavior. Budget violation disables the optional feature at configuration time; the collector does not adaptively suppress failure samples. Core events are unsampled in v1 within registered coverage. Detailed captures may overwrite old records and must report that fact.

The card report has hidden, visible-stationary and dragging conditions under the same autonomous scrolling/animation/GPU workload, including a full-window GPU canvas in both stationary and dragging comparisons. Measure GPU/compositor time and any presentation-path changes there; do not assume the current translucent CAMetalLayer gains direct scanout when the card is hidden. Include a static idle app to check for recurring wakeups.

Use a recorded XCUITest coordinate-drag sequence against the owned app window on iOS devices, and the corresponding targeted native pointer sequence on macOS. Apply identical paths, duration, start geometry and resets in each paired arm. The control arm has an equivalent small host-native target that consumes the touches but stays stationary and does no metric/text work, so dragging cannot scroll the underlying app in only one arm. Charge input injection to both arms. Report total moving-card cost and its increment over the stationary control, without subtracting moving-card cost from presentation outcomes. Record text refresh/format counts, app layout passes, frame-rate policy, misses, raw tails, CPU/GPU/compositor time, allocations and energy resolution. Test 120 Hz and above-120 desktop rates. If isolation fails, simplify the card or reduce display updates before adding further visual effects; do not relax evidence rules.

### 8.4 Reference journeys and hardware

Use navigation and search in a schedule app, scrolling a long chat transcript, scrolling and resizing a long Markdown document, native controls and sheets, and a GPU or game canvas. Fix the content, motion speed and duration before comparing builds. A reference workload includes both inexpensive and expensive content so a trivial animation cannot establish the runtime's target.

The minimum matrix is a 120 Hz flagship iPhone and Android phone; a Mac on 120 Hz; an external desktop display above 120 Hz; and a 60 Hz control. Record exact device, OS, GPU, display mode, app revision and build configuration at execution. Include mixed-display movement and two visible windows; do not extrapolate one window's overhead to arbitrarily many. Simulators and headless browser results are functional evidence only.

Run focused tests on changed modules, then the repository's six checks when landing implementation. Extend existing asynchronous performance workflows; no seventh blocking check or generic performance service is introduced. Device results and reproducible recipes accompany each adapter's enablement change.

## 9 Release policy and rollout

Production core collection is opt-in until each adapter passes accuracy and overhead qualification. Apple builds accept `frame_health: {mode: "off" | "core"}` in `app.json`. Without an explicit mode, builds with development trust default to core and production bakes default to off. The signed rollout and embedder restrictions below remain requirements before production default-on. There is no `hud` policy key: local Show/Hide follows §7.2's existing dev-menu gate in development and release builds, and starts hidden. A visible disabled/unqualified readout cannot override collection policy. For a qualified production adapter, a future build may resolve an omitted mode to core. Freeze the resolved choice in the baked policy so a module update cannot reinterpret omission under a new default. Old native hosts without compiled collector support cannot be enabled by an update.

S0 must prove how the resolved policy travels in Exact's existing signed app delivery stream. Extend that stream's validated manifest/bake data for this one field; no new fetch URL or control channel. A supported host reads the authenticated policy before registering collection and can apply a signed off update at a safe callback-quiescence boundary. Cached authenticated off policy takes effect at the next launch. Signed web/module updates can change collectors within the host's baked support; installed apps are not assumed immutable. Policy changes reset the reporting incarnation and are logged in aggregate metadata. If the existing compatibility rules prevent this narrow policy update, it is a release-blocking S0 finding that requires a focused delivery design before default-on; do not claim a kill switch already exists.

An embedder/local configuration switch also disables collection. A crash before an authenticated off update can be received still requires a native binary fix; an OTA switch cannot undo code already executing or add support to an old host. Demonstrate both the signed-policy rollback and that limitation before rollout. Unsupported adapters stay off with a reason. Collection is local and in memory: no upload destination, persistent identifier or per-frame disk writer. Apps can export aggregates through their existing explicitly configured telemetry and data policy.

The technical release bar is correct accounting, honest source/coverage, bounded work, no new idle callbacks, and a passing paired overhead experiment. Target-rate certification is a separate result for each device/workload. A collector can correctly report that Exact fails 120 FPS; optimizing that workload is follow-up runtime work rather than weakening the metric or a reason to hide the collector.

Initial target-rate certification uses five predetermined runs of each fixed journey with an independent presentation oracle in the same run as the collector, and complete required surface coverage. Require zero missed presentation opportunities in all five; report target, duration, content lateness and any platform-attributed misses separately. A miss prevents that full journey's zero-miss certificate, even when the platform caused it; diagnosis can still identify app-specific performance. UIKit callback success alone cannot certify the display. Where an oracle cannot resolve high-rate presentation or required surfaces, the result stays uncertified. These diagnostic certification runs are separate from the untraced overhead pairs.

Field reports publish conditional distributions, source-specific cadence overdue time and content latency as baselines accumulate. The UI follows §7.3's predicates; proxy success never becomes a presentation pass. No universal user-experience SLO is borrowed from Apple's thresholds or an invented composite score. Set fleet SLOs after workload/device baselines and coverage are reviewed.

Rollback reports old counters ended/disabled with the reason and policy generation. It does not lower the app's rendering target. Avoid silently turning measurement off when the application becomes slow.

## 10 Implementation sequence and completion evidence

### 10.1 What is implemented

The implemented slice includes live-clock scheduler fixes, frame-interval, work, refresh-count and lateness distributions (§4.6), cursor deltas, §7.3's scoped assessments, native-scroll feasibility observation, macOS Develop controls, the iOS and macOS cards and native inspectors. The iOS four-finger menu uses platform controls; the card is drawn by hand from semantic colors composited opaque, scales with Dynamic Type and keeps changing numbers in tabular columns. ### 10.2 Sizes and costs

The Rust collector occupies 3040 bytes; its fixed sixteen-slot registry occupies 48776
bytes. Each reading card holds under 51 KiB more and each open inspector less, and at
most four keep history at once (§5.3), so a process holds under 252 KiB, within the
256 KiB target. Isolated benchmarks establish the following costs, not complete
adapter or UI overhead.

The reducer benchmark (`rustc --edition=2021 -O --test
host/apple/src/frame_health.rs`, then the ignored `recorder_cost`) records at a
requested 120 Hz, so slot counting runs. Each run uses 31 batches of 100,000 records
on an M5 Pro and reports the median batch mean; each entry is the median of ten runs.
They ran at a load average near 700 on 18 cores, so a quiet machine is needed before
these figures bound the cost:

| Capture state | First slot | Sixteenth slot |
|---|---|---|
| Detail off | 8.50 ns | 11.43 ns |
| Detail on | 10.28 ns | 12.72 ns |
| Hitch storm | 13.86 ns | 16.25 ns |

The largest batch mean under that load was 61.5 ns. This benchmark excludes Swift/C
calls, clocks, owner/apply timing, readers, UI, export, GPU composition and energy.

The optimized Swift adapter benchmark (`FrameHealthAdapterBenchmarks`, opt-in with
`EXACT_FRAME_HEALTH_BENCHMARK=1` in a release test run) adds two clock reads and the
Swift/C calls to the reducer. It excludes frame work, UI formatting/composition, the
scroll observer, export and energy. Measure it on the same quiet machine. Neither
benchmark measures a per-call p99 or qualifies whole-frame or battery overhead.

### 10.3 Tests and the device fixture

Tests hold the Apple slice to this plan. The Rust collector's unit tests cover frames, held and idle callbacks, the slot grid across request changes and held slots, refresh counts, restriction at each end of an interval, out-of-order callbacks and saturation. The macOS and iOS frame-health XCTests cover pending work and its cleanup, canvas waits, the stale and out-of-order rules, cursors, the card's reader, windows and four-card limit, the charts' moving average, frame times and joins, the frame hooks that feed them, redraws that match a whole drawing in each layout to within antialiasing, evenly spaced dashes, a card's storage, and the card's input, corners and accessibility. The GPU module's tests cover its draw signal, and the agent reader's JavaScript tests cover `perf frames health` and `perf frames report`. Regression tests cover canvas frame demand, advancing canvas timestamps, stopping without a timer, and publication during touch tracking. Simulator runs are functional evidence only (§8.4).

The [device fixture](../scripts/fixtures/frame-health-app/app.contract) contains one
