## Summary

Three modules let the system reach into an app from outside its window:

- **quick actions**: the menu a long press on the app's icon shows
  (iOS's Home Screen quick actions, Android's app shortcuts, a Windows
  jump list, the Mac's Dock menu, a Linux desktop entry's actions);
- **search-index**: the app's content in the system's search (Spotlight),
  so a search for a book's title finds the book and opens it;
- **intents**: the app's actions offered to the system's callers (Siri,
  Shortcuts and Apple Intelligence on Apple; AppFunctions' agents on
  Android; a browser's agent through WebMCP), which run them with no
  window, and its content offered as their parameters.

They come in one RFC because they answer one question: how does the
system reach an app? Exact already has both answers, and this RFC adds no
third. **The system opens the app at a URL** through the navigation root
(LLP 1038), as a link does; a quick action and a search result are URLs.
**Or it calls one of the app's declared tools** (LLP 1111): a root
action, named, with a consequence the author states, run as an
invocation that owns its work, as a wake's event already is
(LLP 1133.017 D6, built). An intent is a tool with a face the system can
list. The one new noun is the **entity**: an entry of the app's content
index, which is what the system searches and what an intent's parameter
names.

```
use setAppShortcuts, ShortcutItem from "@exact/quick-actions"
use setContentIndex, ContentDescription from "@exact/search-index"

tool logPages writes idempotent closed "Set the page you're on in a book." = logPages
  fails when match logged { case some(a) => not a.ok, case none => false }
mutation logged as shape Ack queue refreshes lib
action logPages(id: string, page: number)
  send logged = setPage(id, page)

task index key=indexKey
  after(1, reindex)
action reindex
  setContentIndex(kind="book", entries=lib.books.map(b => ContentDescription(
    id=b.id, title=b.title, description=b.author, url=`/book/${b.id}`)))
  setAppShortcuts(shortcuts=reading.slice(0, 1).map(b => ShortcutItem(
    name=`Continue ${b.title}`, short_name=b.title, url=`/book/${b.id}`)))
```

```json
"shortcuts": [{ "name": "Add Book", "url": "/add", "apple": { "symbol": "plus" } }],
"intents": {
  "entities": { "book": { "title": "Book" } },
  "tools": {
    "logPages": { "title": "Log Pages",
      "parameters": { "id": { "title": "Book", "entity": "book" }, "page": { "title": "Page", "type": "integer" } },
      "apple": { "phrases": ["Log pages in ${applicationName}"] } } }
}
```

Tier 1 is the web's wherever the web has the capability: the manifest's
`shortcuts` member, the Content Index API's `ContentDescription` and its
`add`, `delete` and `getAll`, and WebMCP's tool for a browser's agent.
Where the web has none (a dynamic shortcut list; App Intents' model of
entities and parameters), the names are exact2's, said in §2. Tier 2
reaches Android's pinned shortcuts, App Shortcuts' phrases, an intent's
authentication policy and a Spotlight item's attributes; tier 3 hands the
app's Swift and Kotlin each platform object before it is published.

The consumer is Shelf (`apps/shelf`), the reading tracker, which a person
can reach today only by opening it and tapping through. With these
modules its icon offers Add Book and Continue Reading, Spotlight finds a
book by its title or author and opens it, and "Log pages in Shelf" asks
Siri which book and which page and writes it without opening the app
(§11).

## 0. What is new here

Writing the three modules out shows seven things the parent RFCs did not
settle, each decided below and asked in §15.

1. **One action model.** LLP 1111's `tool` line is the declared action
   every outside caller reaches: MCP's local door (LLP 1111 D7), and now
   App Intents, AppFunctions and WebMCP. A call runs as the runner's
   invocation, which the background module built for a wake
   (`runner/src/runner/modules/wakes.rs`): one at a time, ending
   `completed`, `superseded` or `expired`. This builds LLP 1111's core
   (D2–D4a) without its MCP door. An invocation knows its work by an id
   carried where the runner already carries a request's origin, LLP 1113
   D4's root-and-ids rule at those points; the wake moves to it too, since
   ownership by origin cannot tell a system call's work from a model
   handler's, which is also `tool` (D7).
2. **A face is part of the binary.** App Intents reads its actions from
   metadata extracted at build time, and its titles must be constants;
   Android reads AppFunctions from a schema in the APK. A tool with a face
   is therefore a binary input, which amends LLP 1111 D6 ("the tool table
   is plan data, not part of the compatibility id") for faced tools only
   (D8).
3. **An entity is a content-index entry.** The system resolves an
   intent's parameter, suggests values and searches without running the
   app's code. So the host keeps a mirror of the index the app set, and
   answers entity queries from it, with no session booted (D9).
4. **A system call may start the app with no view.** A Siri call to a
   closed app launches it in the background; the session boots headless
   as a wake's does (LLP 1133.017 D7), with origin `tool`. `rules/RULES.md`'s
   boot row names a wake launch as outside "App JS executed before first
   pixel"; a tool launch is the same kind of launch and needs naming too
   (§15 question 3).
5. **A destroying tool needs the platform's own confirmation.** LLP 1111
   D5's consent is an alert the host draws in a window. A system call has
   none, so a `destroys` tool gets App Intents' `requestConfirmation`,
   which the system draws and the caller cannot answer, and is not offered
   on a door with no such confirmation (D10).
6. **A quick action and a search result are URLs, delivered as a link
   is.** No new event: the navigation root receives them, cold as the
   launch location and warm as `navigate` (LLP 1038 D8). Android and
   Windows receive no URL at launch today, so both hosts gain the arrival
   every link needs (D15).
7. **A face needs an authenticated person.** App Intents' unsaid
   authentication policy is `alwaysAllowed`, which runs an intent with
   the device locked. exact2 cannot know what a tool's `returns` exposes,
   so a faced tool takes `requiresAuthentication` (the device unlocked,
   or the request made from an authenticated device such as an unlocked
   Watch) unless the face says `local` or `always` (D10).

## 2. One way in for each kind of reach

### D1 — The system opens a URL or calls a tool

Everything the system does to an app from outside its window is one of
two things, and each already has a mechanism:

| The person or the system | Arrives as | Origin of what it causes |
|---|---|---|
| picks a quick action | a URL at the navigation root | a link's (LLP 1038 D8): what a URL opened from another app has today, since on Android and Windows any app can start the app with the same location (D15 item 3) and a location reaches only what the routes do |
| picks a search result | a URL at the navigation root | a link's |
| asks Siri, Shortcuts or a system agent to open an entity | a URL at the navigation root | as any URL another app opens today (LLP 1038 D8) |
| asks Siri, Shortcuts, AppFunctions' agent or a browser's agent to do something | a call of a declared tool (D5, D7) | `tool` (LLP 1133.002 D12) |

There is no module event for any of them. A quick action is the W3C
manifest's ShortcutItem, whose one required destination is `url`; a
Content Index entry's is `url`; a hand-built app's quick action and
Spotlight result open a screen, which in exact2 is a location. A
module event that delivered `{type: "add-book"}` to the root would make
every app write a router from it to its routes, which LLP 1038 already is.

Because they are URLs, every one of them needs the app's navigation root
(`rules/DEFERRED.md`: "A no-router URL event remains deferred; Charlie's
ruling keeps the navigation root requirement"). An app with a shortcut, a
content index entry or an entity and no `navigate=` root is refused at
bake (`quick-actions-root`, `search-index-root`).

*Rejected:* an activation event per shortcut (`"raised": "activation"`,
LLP 1133.004 D6) beside `navigate`. It would be the one way to reach an
app with no router, which the ruling above keeps deferred, and two ways
to reach a screen would disagree on cold launch.

### D2 — An entity is an entry of the content index

The system's search, an intent's parameter and an "open" request all
name a thing of the app's: a book. One record serves all three, the
Content Index API's `ContentDescription`
([spec](https://wicg.github.io/content-index/spec/#content-description)):
`id`, `title`, `description`, `category`, `icons` and `url`, with one
member of exact2's, `kind`, the app's word for what it is (`"book"`).

- Spotlight indexes it (D4).
- An intent's parameter of that kind offers the entries of that kind, and
  resolves the one the person names (D9).
- Opening it is opening its `url`.

An entry is what the app chose to show the system, written by its own
code (D4), and nothing else of the app's is reachable as an entity. A
kind is declared once in the manifest (`intents.entities`, D8), with the
title the system shows for the type ("Book").

## 3. Tier 1

### D3 — Quick actions: the manifest's `shortcuts`, and a list the app sets

| Name | Kind | The web's | Deviation |
|---|---|---|---|
| `shortcuts` in `app.json` | manifest member: a list of ShortcutItem | [`shortcuts`](https://www.w3.org/TR/appmanifest/#shortcuts-member): `name`, `short_name`, `description`, `url`, `icons` | `url` is an app path; `apple` and `android` keys hold tier-2 words (D11) |
| `setAppShortcuts(shortcuts=)` | send, answers nothing (LLP 1133.004 D5) | none: the web's list is the manifest's, fixed at install | exact2's, named like the Badging API's `setAppBadge`; the list it sets follows the manifest's, which the platform shows first |
| `clearAppShortcuts()` | send, answers nothing | none | as `setAppShortcuts([])` |
| `ShortcutItem` | shape | ShortcutItem, minus `icons` beyond one local image | — |

**The manifest's list** is fixed per binary: iOS reads
`UIApplicationShortcutItems` from Info.plist, Android
`res/xml/shortcuts.xml`, the web `manifest.json`. So `shortcuts` is a
binary input (the compatibility id gains it, as `protocol_handlers` is,
`bake/src/compat.rs:450`), and `webAppManifest` adds it to its keys.

**The app's list** is what changes with the app's data: "Continue
*Dune*". `setAppShortcuts` replaces the whole of it; the platform shows
the manifest's items first and then the app's, up to its own limit
(Apple's HIG: "you can provide a total of four"; Android: "the API
supports a combination of up to 15 static and dynamic shortcuts … we
recommend that you publish only four",
[best practices](https://developer.android.com/develop/ui/views/launch/shortcuts/best-practices)).
iOS shows what fits. Android throws when `getMaxShortcutCountPerActivity()`
is exceeded
([`ShortcutManager`](https://developer.android.com/reference/android/content/pm/ShortcutManager)),
so its implementation keeps the first items that fit beside the
manifest's and journals the rest. A shortcut is
identified by its `url`, so setting the list again with a shortcut whose
`url` is unchanged updates it (Android keeps a pinned copy's id, D11).

**What is checked.** `name` is non-empty and `url` an absolute app path
that the navigation root's routes match (at bake for a literal, a
`TypeError` for a computed one). An icon is a local image (an asset or an
`app:/` path); a remote one is refused `TypeError`, since iOS takes only
symbols and bundled images and Android an `Icon` from a resource or a
bitmap.

**Errors**, by the web's names: `NotSupportedError` where §9 gives the
call no cell (a journal line from Contract, a rejection from data code).

### D4 — Search: the Content Index API's names

| Name | Kind | The web's | Deviation |
|---|---|---|---|
| `addContentIndexEntry(description=)` | send, answers nothing | [`ContentIndex.add(description)`](https://wicg.github.io/content-index/spec/#dom-contentindex-add) | prefixed: imported names share the app's namespace (LLP 1133.004 D1's `requestNotificationPermission`) |
| `deleteContentIndexEntry(id=)` | send, answers nothing | [`ContentIndex.delete(id)`](https://wicg.github.io/content-index/spec/#dom-contentindex-delete) | prefixed |
| `contentIndexEntries()` | source, answers `ContentDescription[]` | [`ContentIndex.getAll()`](https://wicg.github.io/content-index/spec/#dom-contentindex-getall) | answers the host's mirror (below) |
| `setContentIndex(kind=, entries=)` | send, answers nothing | none | exact2's: the entries of one kind replaced by these, the module adding, updating and deleting the difference |
| `ContentDescription` | shape | `id`, `title`, `description`, `category`, `icons`, `url` | gains `kind` (D2); `category` keeps the web's values (`""`, `homepage`, `article`, `video`, `audio`) |

**Why `setContentIndex`.** An app's index should equal its data. With
only `add` and `delete`, Contract would need the difference between
yesterday's books and today's, and a loop of sends over it; data code
could write that, every app again. One call that says "these are the
books" lets the module diff against the mirror, so an app's index cannot
drift from its data across a crash between two calls.

**The mirror.** Core Spotlight's index cannot be read back by the app
(it is queried through `CSSearchQuery`, by attributes, not listed), and
the system asks the app to index everything again when it has lost its
index
([`CSSearchableIndexDelegate`](https://developer.apple.com/documentation/corespotlight/cssearchableindexdelegate)).
So the host keeps what the app set, in the app's container, as the
host keeps a package's wake requests (LLP 1133.017 D8): a file of
entries by kind and id, written before the platform is told, each change
marked pending until the platform acknowledges it, so a crash between the
two leaves work the next launch finishes rather than an empty diff. It
answers `contentIndexEntries`, the diff, the reindex delegate, and entity
queries
(D9) with no session booted. It holds at most 5,000 entries, 1 KB of text
each (a larger set refuses `QuotaExceededError`, the web's name for a
full store); a Spotlight index of more than that is a search engine of
the app's own, out of scope (§13).

**Opening a result** opens its `url` (D1). On Apple the host receives
`CSSearchableItemActionType` with the item's identifier in
`scene(_:continue:)` and `application(_:continue:)`, looks the id up in
the mirror and delivers the `url`; an id the mirror no longer has opens
the app at its start.

**One named index.** Apple's guidance is to "create custom
`CSSearchableIndex` objects in your production code … instead of using
the default index", which supports data protection and batches, and to
"use the default index only during testing or prototyping"
([`CSSearchableIndex`](https://developer.apple.com/documentation/corespotlight/cssearchableindex));
the default index's own page says to use it "only during prototyping or
testing your Spotlight features", and Apple's indexing guide, "When
indexing your app's content, use a named index"
([Adding your app's content to Spotlight indexes](https://developer.apple.com/documentation/corespotlight/adding-your-app-s-content-to-spotlight-indexes)).
So the host makes one, named for the app, with the app's store's
protection class (`completeUntilFirstUserAuthentication`): an entry is
readable by Spotlight after the first unlock, as the app's files are.
Stage 2's simulator drive, Spotlight's own search field finding a book,
checks that a named index's items reach Spotlight.

**Expiry follows the mirror.** "The system automatically expires items
after a period of time, so setting an expiration date causes the system
to preserve the item" (the same guide). An entry stays in the mirror
until the app removes it, and `setContentIndex` publishes only
differences, so an item left to expire would vanish from Spotlight while
the mirror still held it. The host sets each item's `expirationDate` to
the distant future; the app's removal is the item's end.

### D5 — Intents: LLP 1111's tool line, with a face

The web's name for an app's action offered to an outside agent is
WebMCP's: `document.modelContext.registerTool(tool)` with a
`ModelContextTool` of `name`, `title`, `description`, `inputSchema`,
`execute` and `annotations` (`readOnlyHint`, `untrustedContentHint`,
`consequentialHint`), a Draft Community Group Report, "not a W3C
Standard nor … on the W3C Standards Track"
([WebMCP](https://webmachinelearning.github.io/webmcp/)). It is a page
API: the page registers a function. exact2 has no page function to
register, and already has the declared form of the same thing, LLP 1111's
`tool` line, whose MCP annotations map onto WebMCP's. So intents add no
name to Contract; the deviation from App Intents' model the roster names
(§3.10, "actions with parameters, entities") is answered by three pieces
that exist or are already designed:

| App Intents | AppFunctions | WebMCP | exact2 |
|---|---|---|---|
| an `AppIntent` and its `perform()` | an `@AppFunction` | a `ModelContextTool` and its `execute` | a `tool` line naming a root action (LLP 1111 D2) |
| `@Parameter` | a function parameter | `inputSchema` | the action's parameters, typed by the plan |
| `IntentResult`, `ReturnsValue` | the return value | `execute`'s result | `returns` and `fails when` (LLP 1111 D2), the outcome (D4) |
| `AppEntity`, `EntityQuery` | a schema type | — | a content-index entry of a kind (D2), answered from the mirror (D9) |
| `title`, `description`, phrases | display name | `title`, `description` | the face: `app.json` `intents.tools` (D8) and the tool's description |
| `requestConfirmation` | the app's own (AppFunctions has none) | `consequentialHint` | `destroys` (LLP 1111 D3, D5; D10) |
| `OpenIntent` | — | — | the entity's `url` (D1) |

**The tool line is unchanged** (LLP 1111 D2): `tool <name> <reads |
writes [additive] | destroys> [idempotent] [closed] "<description>" =
<action> [returns <expr>] [fails when <expr>] [available when <expr>]`,
root actions only, with D3's consequence lint and D4a's command classes.
What this RFC adds is a **face**: the manifest row that offers a tool to
the system's callers (D8). A tool with no face is offered to none of them;
a face names a tool that must exist.

**The types a face admits.** App Intents' parameters and results are
Swift types the metadata names, and AppFunctions' a schema. So a faced
tool's parameters are `string`, `number` (with `"type": "integer"` in the
face for a whole number, which the system's number field asks for),
`bool`, an `enum<…>` (an `AppEnum`), or a `string` bound to an entity
kind; its `returns`, if any, is a `string`, `number` or `bool`. Anything
else is refused at bake (`intents-face-type`), naming the parameter. A
tool without a face keeps LLP 1111's types.

### D6 — Unsaid defaults are the platform's

| Unsaid | Takes | Source |
|---|---|---|
| a quick action's icon | iOS: none (the item's title alone); Android: the app's icon; Windows: the app's icon; macOS and Linux: none | each platform's default for an item with no icon |
| how many quick actions show | the platform's limit | D3 |
| a search result's appearance | Spotlight's, from `title`, `description` and the app's icon | Core Spotlight |
| whether an intent opens the app | it does not: `supportedModes` `.background` on iOS 26 and later ([`supportedModes`](https://developer.apple.com/documentation/appintents/appintent/supportedmodes)), `openAppWhenRun` false before ([deprecated in 26](https://developer.apple.com/documentation/appintents/appintent/openappwhenrun)) | a tool's call never moves the person's view (LLP 1111 D4a, skip-class commands) |
| what Siri says on success | the platform's generic completion; a `string` `returns` is spoken as the result's dialog | [`ProvidesDialog`](https://developer.apple.com/documentation/appintents/providesdialog) |
| whether an intent runs while locked | **not** the platform's (`alwaysAllowed`): D10 | — |
| App Shortcuts | none unless the face names phrases | [`AppShortcutsProvider`](https://developer.apple.com/documentation/appintents/appshortcutsprovider) |

## 4. Calls from the system

### D7 — A system call is an invocation, as a wake's event is

A door is the host code that receives a call from a system caller: the
generated `AppIntent`'s `perform()`, the Android host's
`AppFunctionService`, the web runtime's WebMCP `execute`. Every door hands
the runner `{tool, args, door}`, and the runner runs it as LLP 1111 D4
says, as an **invocation**: the thing the background module built for a
wake's event (`runner/src/runner/modules/wakes.rs`), delivered once, one
at a time, as its own commit; done when it owns nothing; ended
`superseded` when a commit not its own lets go of work it owns; expired
at its deadline. What changes is how it knows its work (below). A tool
call is an invocation of origin `tool`:

1. **Validate** (LLP 1111 D4 step 1): the tool exists, is available, and
   the arguments decode against the plan type; the face's digest matches
   the plan's tool (D8). A failure is `refused` with certainty `none`.
2. **Await the platform's confirmation** for `destroys` (D10), outside the
   time bound.
3. **Dispatch** the root action as one commit of origin `tool`, cause
   `system`, with the door named in the journal
   (`tool:system:apple-intents logPages dispatched`, never the arguments).
4. **Complete** when it owns nothing, then evaluate `returns` and `fails
   when` once. The bound is LLP 1111's 10 s from dispatch, inside the
   platform's own (iOS's 30 s for an intent in the background,
   [`LongRunningIntent`](https://developer.apple.com/documentation/appintents/longrunningintent)).
5. **Answer** the door with LLP 1111 D4's outcome and certainty (`ok`,
   `failed`, `superseded`, `timeout`, `interrupted`, `refused`; `none`,
   `applied`, `uncertain`), `stale`, and `returns`' value.

**An invocation knows its work by its id, not by its origin.** The
built wake owns the work *of origin `wake`*, which stands in for LLP
1113 D4's owner set because one wake runs at a time. Origin `tool` is
not so narrow: a model's tool handler runs as `tool` concurrently with
the session (`invoke.rs:158`, LLP 1133.016 D10), and a resource keeps the
origin of its last ask for the device's re-asks (`admit.rs:139`). Owning
"the work of origin `tool`" would let a system call wait on, expire or be
superseded by work that is not its own. So each invocation has an id,
and the runner's origin tables, which already carry an origin per ticket,
armed `then`, held call and queue entry (`admit.rs` `note_asked`,
`note_then`), carry the id beside it:

- the dispatch commit stamps the id on every request, `then`, held call
  and queued send it makes;
- a commit that fulfils a stamped request, or runs a stamped `then` or
  queue entry, is stamped too, so a mutation's `refreshes` re-ask is the
  call's (Shelf's `lib` after `setPage`);
- a resource's re-ask by the device keeps its origin but no id, and a
  model's `invoke` run has none: neither is any invocation's;
- ownership, expiry and supersession read only the id.

This is LLP 1113 D4's root-and-ids rule carried at the points the runner
already tracks origin; the wake moves to it in the same stage, since its
origin-based stand-in has the same latent fault.

**Ownership is part of the commit.** A commit that is refused and rolled
back (`commit.rs`'s restore of slots, pending requests and queues) must
leave no ownership change behind. Today `wake_let_go` ends an invocation
`superseded` while the commit that let go of its request is still being
made (`commit.rs:812`), and a refused gate then restores the request
(`commit.rs:158`) with the invocation already over. So the id tables are
restored with the rest of the commit's checkpoint, and an invocation's
terminal transition (`superseded`, `completed`) is taken only when the
commit that causes it lands. LLP 1113 D4's owner transfer between
coalesced refreshes stays LLP 1113's.

**Storage.** Background storage work (LLP 1097) cannot be attributed: an
answer's un-awaited operations are re-homed to one background owner when
the answer finishes (`runner/src/runner/background.rs`). So, as LLP 1113
D4's v1 and LLP 1111 D4 say, a call is refused `busy` while a background
storage ticket exists, and a call at whose completion check one exists
ends `failed`, `uncertain` (`background`), never `applied`. A tool whose
source awaits its writes, as Shelf's `change` awaits `persist`
(`apps/shelf/app.ts`), never meets it. Giving each storage operation an
owner a call could wait on would amend LLP 1097 and is not proposed. The
wake keeps its rule (it waits for the whole queue before it ends).

**Data code's calls.** A data-code call made inside an answer takes that
answer's origin, which the async-context helper names (LLP 1133.002 D14).
Only a call it cannot trace takes the least privileged origin in flight
(`admit.rs` `data_origin`), the safe direction: during a system call such
a call of the person's may fail `person-required`, for the call's life at
most, and the journal says so.

**The web.** The page cannot tell one request from another, so the web
runtime's wake owns every answer after its delivery
(`host/web-js/wakes.js`). A WebMCP call instead stamps the requests its
dispatch commit issues, which the runtime makes and can mark, and
follows them as above; until that is built (stage 5) the web door is
not offered.

**One invocation at a time, of either kind.** A tool call that arrives
while a wake's invocation or another call runs waits for it, up to the
door's bound (5 s), then ends `refused` (`busy`, `none`); LLP 1111
refused at once, which suits an agent that retries, not Siri.

**The person's commits are theirs.** A person's commit during a call is
unstamped and not the call's. A tool whose `returns` or `fails when`
reads a mutation the person also sends can report the person's reply as
its own: a queue mutation is free for the next send once its own request
lands, before the call's owned `refreshes` re-ask does, so a person's
send in that window replaces the value the call then reads. So a tool
reads a mutation only tools send, which is LLP 1111 D2's tool-shaped
action, and the bake warns (`tool-shared-mutation`) when a faced tool's
`returns` or `fails when` reads a mutation a non-tool action sends. A
separate mutation keeps the call from reporting the person's reply, not
from being superseded by it: a person's commit that replaces work the
call owns (Shelf's `changed` refreshing `lib` while the call's re-ask is
out) ends the call `superseded`, with the certainty LLP 1111's table
gives.

**A call that starts the app.** On iOS, a call to an app that is not
running launches it in the background. The host's `perform()` boots the
session headless (LLP 1133.017 D7), which publishes one unpresented frame
and loads the data module, then hands the call over once the data module
is ready; the boot is inside the platform's 30 s. A scene that connects
meanwhile attaches to the session as a wake's does. A call is held to
a wake's two rules for a session: for the length of the call, a session
with no view or a hidden one fires no timer and no frame task (LLP
1133.017 D6's "Does not fire", which names a wake and is amended to name
a call, §12), and a session the call booted, with no view attached when
the call is answered, is ended as a wake's is. On Android the host's
`AppFunctionService` does the same through the headless session LLP
1133.017's stage 3 builds. On macOS a call launches the app as an
ordinary launch, with its window (§15 question 5). On the web a call
reaches only an open page.

**What a call may run** is LLP 1111 D4a's, since a call has no person:
refused-class commands fail the compile in a tool's reach, skip-class
commands (focus, scroll, haptics) are skipped, and a permission request
or any name that needs a person fails `person-required`. A tool call
cannot start a device (LLP 1133.009 D9), authenticate (LLP 1133.010 D12)
or show system UI.

*Rejected:* running a faced tool through `invoke` (LLP 1133.016 D15 item
1), so that an intent's handler would be a data source as a model's tool
is. `invoke` exists for a call that belongs to a handle a package holds
(a response's tool call), and a system call has none. Worse, a data
source answers a fresh request that fills no slot, so Shelf's open
screen would not show the page Siri logged until something refreshed it;
a root action's commit is what the app already shows. A model's tools
stay data sources (LLP 1133.016 D9); a session naming `tool` lines is
that RFC's question 7, and would reach this same table.

### D8 — A face is compiled into the binary

App Intents finds an app's actions in metadata Xcode's
`appintentsmetadataprocessor` extracts from the compiled Swift at build
time; an intent's `title` and `description` are static. Android finds
AppFunctions in a schema asset the APK carries. Neither can change with a
bundle. So:

**The face is a manifest member**, `intents`, as widgets' titles are
(LLP 1126 D2):

```json
"intents": {
  "entities": { "<kind>": { "title": "<type name>" } },
  "tools": {
    "<tool>": {
      "title": "<constant title>",
      "parameters": { "<name>": { "title": "…", "entity": "<kind>", "type": "integer" } },
      "apple": { "phrases": ["… ${applicationName} …"], "authentication": "always" },
      "doors": ["apple", "android", "web"]
    }
  }
}
```

`doors` defaults to every door §9 gives a cell. The tool's description is
its `tool` line's literal.

**The faced tools' signatures join the compatibility id.** The id gains
the face, and for each faced tool everything the generated code
compiles from the plan: its name, description, consequence, modifiers,
parameter names and types, and `returns` type, as
`bake/src/compat.rs` already takes widgets' titles. A plan whose faced
tool changed signature has another id, so the deploy classifier
(LLP 1030.000) sends it as a binary change, never as a bundle to binaries
whose faces it would break; the dry run says which tool moved it. A tool
without a face stays plan data (LLP 1111 D6), so adding an MCP-only tool
is still a bundle.

**A digest at the door.** The generated door carries the digest of the
same fields, and the runner refuses a call whose digest differs from
the plan's (`refused`, `unavailable`, reason `face`). Delivery makes this
unreachable in production; it is what a development plan reload hits.

**On Apple** the bake generates, per app, one Swift file beside the
widget bundle's (`host/apple/widgets.mjs` is the pattern): one `AppIntent`
per faced tool, one `AppEntity` with an `EntityStringQuery` per kind, an
`OpenIntent` per kind, and an `AppShortcutsProvider` if any face names
phrases. Each `perform()` is three lines: build the arguments, call
ExactKit's door, map the outcome. The file is compiled with `swiftc
-wmo -emit-const-values-path` and a const-gather protocols list, and
`appintentsmetadataprocessor` writes `Metadata.appintents` into the
bundle's resources. Measured 2026-10-25 on Xcode 27.1: a one-intent
module compiled by `swiftc` alone, outside Xcode and SwiftPM, gives the
processor what it needs, and it writes `extract.actionsdata` with the
intent's title, description and typed parameter. Whether the system
reads the metadata from a bundle that `build.mjs`, not Xcode, assembled,
and finds the intent's type in the app's executable, is stage 2's first
measurement and its kill line (§14).

**On Android** the bake generates one Kotlin file of `@AppFunction`
functions, one per faced tool, each forwarding its typed arguments to the
host's door, and the AppFunctions SDK's KSP processor in the locked
Gradle graph writes the schema asset, which is the documented path
([add AppFunctions](https://developer.android.com/ai/appfunctions/add-appfunctions)).
The schema is never written by hand: the platform's parser says the
schema "should be generated by the App Functions SDK"
(`AppFunctionDocumentParserImpl.java`, AOSP `android16-qpr2-release`).

**On the web** the runtime registers each faced tool with
`document.modelContext.registerTool` where `document.modelContext`
exists, with an `inputSchema` from the plan type and annotations from LLP
1111 D3's table (`readOnlyHint` as there; `consequentialHint` true for
`writes` and `destroys`), and unregisters it while `available when` is
false. Nothing is compiled; the face is still the manifest's, so that a
tool is offered to the web's agents only when its author chose to offer
it to agents at all.

### D9 — Entities answer from the host's mirror

The system asks an app for entities to resolve a parameter ("which
book?"), to suggest values, and to match a spoken name, and it may ask
"from the app or App Intents extension"
([`EntityQuery`](https://developer.apple.com/documentation/appintents/entityquery)).
Booting a session to answer is the wrong cost for a lookup, and the
answer is already on disk: the mirror (D4).

- **`entities(for:)`** answers the mirror's entries of that kind by id.
- **`suggestedEntities()`** answers the kind's entries in the order the
  app last set them (Shelf sets books currently being read first).
- **`entities(matching:)`** answers entries whose `title` or `description`
  contains the string, case- and diacritic-insensitive, in the person's
  locale ([`EntityStringQuery`](https://developer.apple.com/documentation/appintents/entitystringquery)).
- **The display representation** is `title`, `description` as subtitle,
  and the first local icon.
- **When the app changes the index,** the host calls
  [`updateAppShortcutParameters()`](https://developer.apple.com/documentation/appintents/appshortcutsprovider/updateappshortcutparameters())
  so App Shortcuts whose phrases name a parameter learn the new values.

The query is ExactKit's Swift over the mirror file, run on the system's
call with no runner and no plan; it reads only what the app chose to
index.

**Where the caller has no entity query** (AppFunctions, WebMCP), an
agent cannot know the app's ids. There the parameter is a string the
schema describes as "a book's title or id", and the door resolves it
through the mirror before validation: an id it has, else the one entry
whose title or description matches as `entities(matching:)` does. None
or several is `refused`, `arguments`, `none`, with the message naming up
to five candidates' titles, so the agent can ask the person which.

A call whose entity id the app no longer has dispatches like any other:
the app's action decides (Shelf's `setPage` of an unknown id changes
nothing).

### D10 — Destroying, locked, and who may call

**`destroys`.** LLP 1111 D5's consent is an alert the host draws, which a
caller cannot answer. A system call has no window to draw it in. On Apple
the door calls
[`requestConfirmation()`](https://developer.apple.com/documentation/appintents/appintent/requestconfirmation())
before dispatch, with the tool's title and the decoded arguments; the
system draws it and the person answers it, which is a yes the caller
cannot give. No means `refused`, `declined`, `none`. On a door with no
such confirmation (AppFunctions, whose guide makes confirmation the
app's own job: "your app should include its own confirmation step",
[add AppFunctions](https://developer.android.com/ai/appfunctions/add-appfunctions);
WebMCP, whose `consequentialHint` informs the agent, not the person), a
`destroys` tool has no face: the bake refuses `doors` naming it there
(`intents-destroys-door`).

**Locked.** App Intents' default policy is `alwaysAllowed`, "including
when the device is locked"
([`IntentAuthenticationPolicy`](https://developer.apple.com/documentation/appintents/intentauthenticationpolicy)).
A hand-built app's author chooses it per intent knowing what the intent
reads. exact2 does not know what a tool's `returns`, `fails when` or
message exposes (LLP 1111 D6), so every generated intent sets
`requiresAuthentication`: the person must be authenticated, which Apple
satisfies with the device unlocked or with a request made from a device
that is (an unlocked Apple Watch may run it on a locked iPhone,
[`requiresAuthentication`](https://developer.apple.com/documentation/appintents/intentauthenticationpolicy/requiresauthentication)).
The goal is that a locked phone in someone else's hand runs nothing, and
an authenticated person's own request is not that. A face may say
`"local"` (`requiresLocalDeviceAuthentication`, the executing device
unlocked) for a tool that should never run on a locked device, or
`"always"` to take the platform's default for one known safe locked. This
departs from "unsaid is the platform's" (LLP 1133 D4) on purpose: the
default is a security choice the platform leaves to the author, not a
presentation.

**Who may call.** Every caller of a door is trusted to call the tools it
is offered and nothing more (LLP 1111 D5's threat model): a Shortcuts
automation may run a `writes` tool with nobody present, which is what
origin `tool` already assumes. Presence is never delegated: a faced tool
cannot reach `requestLocalAuthentication` (LLP 1133.010 D12), since its
reach is linted and a call fails `person-required` there.

## 6. The ceiling test

Would someone who knows the platform notice, using Shelf built with these
modules, against a hand-built reading tracker on the same OS?

- **iOS.** Long press shows Add Book and Continue *Dune*; Spotlight finds
  *Dune* by "dune" or by "Herbert" and opens the book; Shortcuts lists
  Log Pages with Book and Page parameters, and "Log pages in Shelf" asks
  which book from the books being read. Missing beside a hand-built
  app: interactive snippets, Live Activity intents, App Intents in
  widgets and controls (LLP 1126 D7's later stage), assistant schemas.
  None is a tell on Shelf's screens; each is an ask of its own (§13).
- **macOS.** The Dock menu offers Add Book while Shelf runs; Spotlight
  finds books; Shortcuts runs Log Pages. A hand-built app's Dock menu is
  present only while running too.
- **Android.** The launcher's long press shows both shortcuts, and Add
  Book can be pinned. AppFunctions offers Log Pages to an agent with
  access. No system search of a third-party app's content is documented
  (§9), so its absence is not a tell.
- **Windows.** The taskbar's jump list shows Add Book and Continue
  *Dune*.
- **Linux.** The desktop entry's actions show Add Book in a dock or menu
  that reads them.
- **Web.** An installed Shelf shows the manifest's Add Book where the
  browser supports shortcuts.

## 7. Permission and origin

### D13 — LLP 1133.002 §4 for these modules

None of the three asks a permission: the platforms ask none for
shortcuts, Spotlight, App Intents or AppFunctions' publication (access
to call an app's functions is granted to the agent by the system,
[AppFunctions](https://developer.android.com/ai/appfunctions), not asked
by the app). So no permission is declared, no ticket is held, and D6–D11
of LLP 1133.002 have nothing to apply.

**Origins** (LLP 1133.002 D12):

| Name | A person's input, the app's code | `tool` | `wake` |
|---|---|---|---|
| `setAppShortcuts`, `clearAppShortcuts` | proceeds | proceeds | proceeds |
| `addContentIndexEntry`, `deleteContentIndexEntry`, `setContentIndex`, `contentIndexEntries` | proceeds | proceeds | proceeds |
| `requestPinShortcut` (Android) | proceeds | `NotAllowedError`, `person-required` | `NotAllowedError`, `person-required` |
| a quick action or search result opened | — (a link, D1) | — | — |
| a faced tool's call | — | its origin is `tool` | — |

Setting the shortcut list or the index from a wake is what an app does
after a sync, and changes nothing the person sees until they look, so it
is open to every origin. A tool's action may change the index as its
writes do. Shelf reindexes from a timer task, and during a call a
session with no view or a hidden one fires no timers (D7), so after a
cold call the index catches up at the next launch, when the task arms
again and `setContentIndex` republishes the whole kind's difference;
after a warm call into a hidden window, when the call ends, since the
timers are held only for the call's length; into a visible one, at
once. An app that needs the index current after a cold call
sets it in the tool's own action.

## 8. Packaging and callers

### D14 — Two packages and one piece of vocabulary

- **`@exact/quick-actions`** (an extension, LLP 1133 D5): `setAppShortcuts`,
  `clearAppShortcuts`, `ShortcutItem`, and `@exact/quick-actions/android`'s
  `requestPinShortcut`. The manifest's `shortcuts` is not the package's:
  it is the manifest's, derived by the bake whether or not the app imports
  the package.
- **`@exact/search-index`** (an extension): the D4 names. Its
  implementations are thin layers over the host's mirror and the
  platform's index (D15).
- **Intents are exact2 vocabulary**, not a package. A face must be
  compiled into the binary before any package loads, its door hands a
  call to the runner's tool table, and its entity query runs with no
  runtime: each is host or runner code. A package could not hold any of
  them without a private seam (LLP 1133.001 D8).

### D15 — Seam additions

1. **The host keeps the entry points** (LLP 1133.004 D7's and LLP
   1133.017 D8's rule): the shortcut item callbacks
   (`connectionOptions.shortcutItem` cold,
   [`windowScene(_:performActionFor:completionHandler:)`](https://developer.apple.com/documentation/uikit/uiwindowscenedelegate/windowscene(_:performactionfor:completionhandler:))
   warm), the Dock menu
   ([`applicationDockMenu(_:)`](https://developer.apple.com/documentation/appkit/nsapplicationdelegate/applicationdockmenu(_:))),
   `CSSearchableItemActionType`'s continuation, the reindex delegate, the
   generated intents, Android's shortcut intents and `AppFunctionService`,
   and Windows' jump list launch. Each exists before package code loads,
   and each delivers a URL (D1) or a call (D7).
2. **The context gains two stores** (`context.shortcuts.set(items)`,
   `context.contentIndex.set(kind, entries)`, `.add`, `.delete`,
   `.entries`), the host's, so the mirror and the shortcut list survive a
   launch with no package loaded. The packages' implementations call them
   and the platform; a third party's module reaches the same stores.
3. **A URL at launch and while running on Android and Windows.**
   Android: the launching intent's data becomes the launch location, and
   `onNewIntent`'s a `navigate`. The launcher activity is exported, so any
   app can start it with a location, as any app on iOS can open the app's
   URL; the location is a link, reaching only what the navigation root
   routes, with a link's origin (D1). Windows: the command
   line's first location argument, as Linux reads it
   (`launch_location`), and a second launch hands its argument to the
   running instance. Both are what every deep link on those hosts will
   need; neither is a module's.
4. **The tool door** (`ExactKit` `ExactTools.call(tool:args:door:)`,
   Android's `ExactTools.call`, the web runtime's) is public, so an app's
   own native intent, written by hand where a face cannot say it, calls
   the same table with the same rules.
5. **The invocation generalizes** (`wakes.rs`): an invocation has an
   origin (`wake` or `tool`) and an id, which the origin tables carry
   beside each origin (D7), and its refused commands are the union of a
   wake's list and LLP 1111 D4a's refuse class. LLP 1111's
   `runner/src/tools.rs` holds the tool table, validation and the
   envelope; the invocation holds ownership.

## 10. The substitute

**The implementation is its own substitute** (LLP 1133.006 D8 item 4):
under the agent the runner admits each call, and the implementations run
told so, writing the host's stores in the session's own directory and
telling no platform anything.

| Event | Result |
|---|---|
| `setAppShortcuts`, `clearAppShortcuts` | the list in `state.extensions["quick-actions"].shortcuts`, the manifest's first, each with its `url` |
| `setContentIndex`, `addContentIndexEntry`, `deleteContentIndexEntry` | the session's mirror changes; `state.extensions["search-index"]` shows counts by kind and the last diff (added, updated, deleted ids) |
| `contentIndexEntries` | answers the session's mirror |
| `requestPinShortcut` | answers `requested` and lists the shortcut under `state.extensions["quick-actions"].pinRequests`; `prefer extension quick-actions.pinSupported=false` makes it answer `unsupported` |
| a quick action or a search result | `type <root> <url>` (LLP 1038 D11), the way any link is driven; a quick action's or entry's `url` is listed in the state above, so a drive copies it from there |
| a faced tool's call | `call <tool> <json>` (LLP 1111's authored-test step, here an agent operation): the same door the platform's would reach, with `door` `agent`; `--door apple` makes the runner check the face as Apple's door would (types, the digest, `destroys` needing a confirmation, which is then a `confirm` ticket: `tap @t allow`) |
| an entity query | `state.intents.entities <kind> [<string>]` answers what the mirror's query would, without the platform |
| a cold call | `--call '<tool> <json>'` at launch: the session boots headless as `--wake` does (LLP 1133.017 §10) and the call is delivered after the data module is ready |

**Disclosure:** `state.intents` lists each face, its doors, its digest
and each call's door, origin, outcome, certainty and time, never its
arguments.

**Production:** none of it.

## 11. The consumer: Shelf

Shelf (`apps/shelf`) is the repository's iPhone recipe, a reading tracker
on iOS, macOS, the web, Android and Windows. A hand-built tracker
(Apple's Books, among others) offers the three things Shelf lacks: a
quick action to add a book, its books in Spotlight, and an action
Shortcuts and Siri can run. A reading tracker is opened many times a day
for one write, the page reached, which is the write a quick action or a
spoken "log pages" saves a person from tapping through to.

**What Shelf adds:**

1. **Quick actions.** The manifest's Add Book (`/add`, symbol `plus`),
   and the app's Continue *title* for the newest book still marked reading
   (`/book/<id>`), set by a task whenever the library changes.
2. **Search.** Every book in the index of kind `book`: title, author as
   description, `/book/<id>`. The same task sets it.
3. **Tools.** `logPages(id, page)` and `addToShelf(title, author,
   pages)`, two tool-shaped actions (LLP 1111 D2) that send into
   `logged`, a `queue` mutation only the tools use. The person's
   `turnTo` sends into `changed`; were a tool to share it, a page turn
   the person made while a call waited for `lib` could replace
   `changed`'s value before the call read it, and the call would report
   the person's reply as its own. With its own mutation, `fails when`
   reads the call's reply. Two mutations put two edits in flight at
   once, which Shelf's data module does not survive today: `change`
   (`apps/shelf/app.ts`) edits the snapshot `load` returned, so two
   edits waiting on the first load both start from it and the later
   persist drops the earlier book. `change` therefore applies its edit
   to the newest state once `load` has resolved, with no `await`
   between reading and setting it; `persist` issues its writes in its
   own answer's turn, and the module's storage runs them in the order
   issued (LLP 1097 D3), so the later edit is the page. Both tools
   are `writes … closed`. Removal stays the person's: no `destroys`
   tool.
4. **Faces** for both, with Book as `logPages`' `id` and the phrase "Log
   pages in ${applicationName}".
5. **Android:** a book's context menu gains Add to Home Screen
   (`requestPinShortcut`).
6. **Linux:** a `shelf-linux` crate, as Caltrain's, so the desktop
   entry's action is driven there.

```
use setAppShortcuts, ShortcutItem from "@exact/quick-actions"
use setContentIndex, ContentDescription from "@exact/search-index"

tool logPages writes idempotent closed "Set the page you're on in a book." = logPages
  fails when match logged { case some(a) => not a.ok, case none => false }
tool addToShelf writes additive closed "Add a book to your shelf." = addTitled
  fails when match logged { case some(a) => not a.ok, case none => false }

mutation logged as shape Ack queue refreshes lib

action logPages(id: string, page: number)
  send logged = setPage(id, page)
action addTitled(title: string, author: string, pages: number)
  send logged = addBook(title, author, pages, "want", "", "",
    time.epochAtZero + performanceNow())

derive reading = lib.books.filter(b => b.status == "reading")
derive indexKey = lib.books.map(b => `${b.id}|${b.title}|${b.author}|${b.status}`).join("\n")

task index key=indexKey
  after(1, reindex)

action reindex
  setContentIndex(kind="book", entries=lib.books.map(b => ContentDescription(
    id=b.id, title=b.title, description=b.author, url=`/book/${b.id}`)))
  setAppShortcuts(shortcuts=reading.slice(0, 1).map(b => ShortcutItem(
    name=`Continue ${b.title}`, short_name=b.title, url=`/book/${b.id}`)))
```

**Drives** (each under the agent on the web and macOS, and as §14
names on each target):

1. *Quick action, cold.* `state` lists Add Book and Continue *Dune*;
   relaunch with `--url /add`, as the host does for a cold quick action:
   the add sheet is up over the library.
2. *Search.* Add *Dune*: `state.extensions["search-index"]` shows one
   added id; `type shelf /book/<id>` opens it. Remove it: one deleted id.
3. *Log pages, warm.* With *Dune*'s screen open, `call logPages
   {"id":"<id>","page":120} --door apple`: outcome `ok`, `applied`; the
   open screen reads page 120 without a refresh.
4. *Log pages against the person.* Start `call logPages` and, while its
   `lib` re-ask is held (`clock held`), `tap page-plus`: both writes
   land, and the person's `changed` refreshes `lib`, replacing the
   call's re-ask, so the call is `superseded`, `applied` (D7; LLP 1113
   D4's unowned replace). With a failure armed on the person's `setPage`
   alone (`fail fetch`-style, on the data module's fixture) the call is
   the same, never `failed`. And with the first `load` held, `call
   addToShelf` and the person's Add Book both land: the library holds
   both books after a relaunch.
5. *Cold call.* `--call 'logPages {"id":"<id>","page":130}'`: the session
   boots headless, the call is `ok`, and a later launch shows page 130;
   that launch's index task republishes, since a session with no view
   fires no timers during a call and is ended after it (D7, D13).
6. *Entity query.* `state.intents.entities book her` lists *Dune* by its
   author; with no session needed on Apple (stage 2's XCTest).
7. *Refusals.* A face naming a `destroys` tool with `doors` `android`
   fails the bake (`intents-destroys-door`); a call whose arguments miss
   `page` is `refused`, `arguments`, `none`.

## 12. What this amends

- **LLP 1111.** D2–D4a become built, by this RFC's stage 1, without D5's
  window alert or D7's MCP door (each still LLP 1111's). D4's ownership is
  the invocation's, by an id carried where the runner carries origin
  (D7): LLP 1113 D4's root-and-ids rule at those points, restored on a
  rollback, its owner transfer between coalesced refreshes left to it;
  background storage as its v1 and D4 say. D4's `busy` waits up to 5 s at a system door. D6: a
  faced tool's signature is part of the compatibility id (D8). §4's App
  Intents door is specified here.
- **LLP 1133.016 D15 item 1**: "Any package whose platform calls back
  into an app (a map's tile provider, App Intents' perform) would use it"
  drops App Intents: perform reaches the tool table (D7). A tile
  provider still would.
- **LLP 1133.017**: the invocation (`wakes.rs`) gains origin `tool` and
  knows its work by an id rather than by its origin, the wake's included;
  the headless boot gains a second reason, a system call (D7); D6's
  "Does not fire" and the ending of a session no view attached to name a
  call beside a wake.
- **LLP 1126 D7**: an intent Siri and Shortcuts list "by name must be
  Swift types; bake generates them": this RFC's generated module is that
  stage for system intents. Widget configuration and control intents stay
  LLP 1126's.
- **LLP 1038**: Android and Windows gain a launch location and a warm
  `navigate` (D15 item 3).
- **`rules/RULES.md`**: the boot row's exemption names a launch for a
  system tool call beside a wake launch (§15 question 3).

## 15. Rulings (Charlie, 2026-10-26: "Accept all (Recommended)")

Each question below was ruled as recommended.

1. **Build LLP 1111's core here?** Intents need a declared action, and
   LLP 1111's `tool` line is the one exact2 has designed; it is parked
   after round 3, NOT READY, mostly over what a call owns. This RFC builds
   D2–D4a (stage 1) on the invocation background built, which it gives an
   id carried where the runner already carries origin (D7), so a call
   owns its own work and not a model handler's or a device re-ask's, and
   the wake moves to the same id. It leaves the MCP door and its window
   alert to LLP 1111, and LLP 1113 D4's finer points to LLP 1113.
   *Recommend yes:* it is the action model 1133.016 also defers to, and
   it builds the part of LLP 1113 D4 that a call and a wake both need,
   at the points the runner already tracks.
2. **A faced tool is a binary change.** Its signature joins the
   compatibility id (D8), amending LLP 1111 D6 for faced tools. *Recommend
   yes:* the platforms read faces only from the binary, and delivering a
   plan whose tool the binary describes wrongly would make Siri send
   arguments the action no longer takes.
3. **The boot row.** A system call to a closed iOS app boots headless and
   runs app code with no first pixel, as a wake does. *Recommend* the row
   read "a launch that presents nothing (a wake, a system tool call)". Ruled
   as recommended: the row has these words.
4. **An authenticated person by default.** Faced tools take
   `requiresAuthentication`: the device unlocked, or the request made
   from an authenticated device such as an unlocked Watch. A face may say
   `local` (the executing device unlocked) or `always` (the platform's
   `alwaysAllowed`) (D10). This departs from the platform's unsaid
   `alwaysAllowed`. *Recommend yes.*
5. **macOS cold calls open a window.** A Shortcuts call to a closed Mac
   app launches Shelf normally. A headless Mac launch (no window until the
   person activates the app) is possible but would be a third launch kind
   on the Mac. *Recommend* the ordinary launch now, measured against a
   hand-built app in stage 2, and a ruling only if it is a tell.
6. **Android's search cell is the mirror only** (§9). *Recommend yes*,
   until Android names a surface.
7. **Shelf on Linux.** A `shelf-linux` crate so the desktop action is
   driven with the consumer. *Recommend yes;* the alternative is an
   undriven cell.
8. **`rules/DEFERRED.md`.** These modules expand the surfaces area. The
   proposed record: "**Expanded (Charlie, <date>, on LLP 1133.023 §15
   question 8):** the app's content and actions reached from outside its
   window: quick actions by the manifest's `shortcuts` and
   `setAppShortcuts` (`@exact/quick-actions`), the system's search by the
   Content Index API's names (`@exact/search-index`), and LLP 1111's
   declared tools offered to the system's callers through a face in the
   manifest (App Intents, AppFunctions, WebMCP), each arriving as a URL at
   the navigation root or as a tool call of origin `tool`. Consumer:
   Shelf's Add Book, Continue Reading, books in Spotlight and Log Pages.
   Unblocks reaching an app's screens and writes without opening it.
   Take: none named. Still out (LLP 1133.023 §13): …". *Recommend* no take:
   the roster's own wave-3 rows, as the other modules' records were.
   Ruled as recommended, no take: the record has this text, is its own
   waiver, and lists §13 as still out.
