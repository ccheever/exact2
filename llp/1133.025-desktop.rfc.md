## Summary

Four pieces of a desktop app that the web has no names for:

- **A login item** (`@exact/login-item`): the app asks the system to open
  it when the person logs in, reads whether it is on, and can open hidden
  at that launch. `SMAppService.mainApp` on macOS; a startup task on
  Windows, and the per-user `Run` key for a development build.
- **Global shortcuts** (`@exact/global-shortcuts`): a chord, written as
  `aria-keyshortcuts` writes one, that reaches the app while another app is
  in front. A registration is a live source, held while something reads it;
  a press is an event on the app's root, a person's input.
  `RegisterEventHotKey` on macOS, `RegisterHotKey` on Windows.
- **A status item**: a `button` with `-exact-menu="status"` is also the
  app's item in the macOS menu bar (`NSStatusItem`) and its icon in the
  Windows notification area (`Shell_NotifyIcon`), and its popover target is
  that item's menu. With `host.macos.activationPolicy: "accessory"` the app
  has no Dock tile and opens no window at launch: a menu-bar app.
- **The Dock**: a `button` with `-exact-menu="dock"` is also an item of the
  app's Dock menu, and `requestAttention()` bounces the Dock icon or flashes
  the taskbar button. The badge is LLP 1133.004's `setAppBadge`, unchanged.

```
use registerLoginItem, unregisterLoginItem, loginItemStatus, LoginItemStatus from "@exact/login-item"
use globalShortcut, globalshortcut, GlobalShortcut from "@exact/global-shortcuts"
use requestAttention from "@exact/dock"

resource login = loginItemStatus() as shape LoginItemStatus
resource snap = globalShortcut(id="snapshot", keys=prefs.snapshotKeys) as shape GlobalShortcut
mutation openedAtLogin as shape LoginItemStatus
action openAtLogin
  send openedAtLogin = registerLoginItem(hidden=true)
action captured(id: string)
  send shot = captureWindow()
action show
  focus()
view
  column globalshortcut=captured
    button -exact-menu="status" popovertarget=tray aria-label="Excord" testId="tray"
      img src="tray.svg"
    column id=tray popover
      button "Open Excord" press=show
    button "New Conversation" press=openNew -exact-menu="file dock" aria-keyshortcuts="Meta+N"
```

The targets are macOS and Windows. Linux, the web, iOS, Android and tvOS
each have a cell that says why the capability is absent there (D14); the
buttons stay ordinary buttons on every host that does not present them, as
`-exact-menu`'s do today.

Four things in this RFC reach past its modules (§0): a launch that opens no
window, which the boot rule must name and which splits "the window is not
showing" from "the app is in the background"; the Windows host's extension
slot, which every Windows module needs and nobody has built; host services
in the package context for the platform's one-per-process objects; and a
second launch on Windows that hands its arguments to the running one.

The consumers: the T3 Code clone's SnapShot shortcut, which today
registers through Carbon in its own Swift (§12.1); Excord, Charlie's
Discord client, which on Windows must keep running in the notification
area when its window closes, and on both desktops opens at login and asks
for attention when a message comes while it is behind (§12.2); and Agents,
whose New Conversation joins its Dock menu as Messages' New Message does
(§12.3).

## 0. What is new here

Writing the four modules out shows six things the parent RFCs did not
settle, each decided below and each a question in §15.

1. **A launch that opens no window.** A menu-bar app opens none at any
   launch; an app that opens hidden at login opens none at that launch.
   On macOS today the host always orders its first window front, and the
   first pixel is that window's first draw (`DrawReceipt.drawn` →
   `ExactSession.firstDrawn`, `ExactKit/SessionActivation.swift`), which
   loads the app's module and data code. A window never ordered front never
   draws, so neither would ever load. LLP 1133.017 D7 met a like gap for a
   wake, but its boot loads the app's code with no first pixel at all,
   which this launch must not copy: it is the app running for the person,
   with no budget, and its first presentation is a status item or nothing.
   D6 gives it the window path's first pixel (the first commit laid out and
   one frame published, its status items placed), after which the host
   runs `firstDrawn`'s continuation itself. `rules/RULES.md`'s row, "App JS
   executed before first pixel: none", then holds as written, and its
   parenthetical names this launch beside the wake's (Q2).
2. **A status item and a Dock menu are presentations of the view, not
   packages.** The status item of a menu-bar app is its first pixel, so it
   is placed before any package code loads (package Swift loads with the
   app's module, after first pixel: LLP 1024 D3). Its menu is a Contract
   subtree that LLP 1021 already presents as an `NSMenu`. So both are
   exact2's vocabulary, as the menu bar's `-exact-menu` is, and the rest of
   each module (a login item, a hot key, attention) is a package (D1, Q1).
3. **The platform's objects are one per process, so the host keeps them.**
   One Carbon hot-key handler per application target, one `WM_HOTKEY` per
   thread queue, one Dock tile (whose badge LLP 1133.004 writes and whose
   attention LLP 1133.025 asks for), one launch to read for "opened at
   login". As LLP 1133.004 D7 keeps the notification delegate and LLP
   1133.017 D8 the wake entry points, the host keeps these and offers them
   to every package through the context (D11).
4. **Windows has no extension slot.** LLP 1124 D6 specifies one ("`linux/*.rs`,
   a type implementing an `Extension` trait, the statically linked module")
   and nothing builds it; no package in `packages/` has a Windows
   implementation, and LLP 1133.002's Rust binding stopped short of "a
   package's own Rust implementation compiled through D9's generated
   manifest … no module needs one yet". These are the first modules whose
   consumer needs a Windows cell, so this slice builds the slot, as
   geolocation's built Apple's and Android's (D11 item 1, Q3).
5. **On Windows an app that keeps running needs an icon.** LLP 1069.010 D8
   left the Windows host ending the app with its window, "that platform's
   convention for an app with no notification-area icon". With a status
   item placed, closing the window hides it instead, and a second launch
   hands its activation to the first instance through the Windows App
   SDK's redirection and ends (D6, Q11).
6. **A window that is not showing is not an app in the background.** The
   runner reads one bit, `page.hidden`, as Page Visibility and as "not in
   the foreground": `"foreground": true` names fail while it is set
   (`runner/src/runner/modules/admit.rs:536`), and modules are told they
   are in the background. A menu-bar app's page is hidden for its whole
   life, so a press on its status item could not start a recording. On a
   desktop the two separate (D6, D11 item 7, Q12).

The badge stays `@exact/notifications`' `setAppBadge` and `clearAppBadge`
(LLP 1133.000 ruling 4; LLP 1133.004 D1). Its Dock tile is the host's

LLP 1133 D5 asks a reason for exact2's vocabulary. Here it is the boot
path: a status item that is a menu-bar app's only presence must appear
from the plan's first commit, with no app code run (`rules/RULES.md`), and
package code loads after first pixel. The menu bar is the precedent: an
`-exact-menu` button is "a presentation of the existing button, never a
new action" (LLP 1021 §5.3), and these are two more such presentations.
The tier 3 hatch on each (D9) is the third-party path a package would
otherwise give.

*Rejected:* a `@exact/status-item` package whose source takes the item's
title, image and menu as data (`statusItem(title=, menu=[…])`), as
Electron's `Tray` and `Menu.buildFromTemplate` do. The menu's rows would be
records with ids, their presses events matched back to actions by id: a
second menu system beside LLP 1021's, outside the tree the agent taps, and
loaded after the first pixel it has to be.

## 3. Tier 1

### D2 — A login item

The web has none: a page cannot ask to run at login, and an installed web
app's "Start app when you sign in" is Chrome's own setting: "there is no
configuration that developers can use to enable run on login from their
apps" ([Chrome](https://developer.chrome.com/blog/run-on-login)). The names follow
`SMAppService`'s verbs (register, unregister, status), named for the
module because imported names share the app's namespace (LLP 1133.004 D1).

| Name | Kind | Meaning |
|---|---|---|
| `loginItemStatus()` | live source; a fact; `sync` | `{available, state, hidden, launchedAtLogin}` and the platform's words |
| `registerLoginItem(hidden=)` | send; answers `LoginItemStatus` | ask the system to open the app at login; `hidden` (default `false`) opens it with no window at that launch (D6) |
| `unregisterLoginItem()` | send; answers `LoginItemStatus` | stop opening it at login |
| `openLoginItemSettings()` | send; answers nothing | open the system's own page for login items, where the person allows or removes one |

**`state`**, one meaning on every target:

- **`enabled`**: the system will open the app at the next login.
- **`disabled`**: it will not, and `registerLoginItem` can change that.
- **`requires-approval`**: the app has asked, and only the person can allow
  it, in the system's settings; `openLoginItemSettings()` takes them there.
- **`unknown`**: the platform will not say.

| Platform | `enabled` | `disabled` | `requires-approval` |
|---|---|---|---|
| macOS 13+, [`SMAppService.mainApp`](https://developer.apple.com/documentation/servicemanagement/smappservice) | `.enabled` | `.notRegistered`, `.notFound` | `.requiresApproval` |
| Windows, installed (package identity, LLP 1115.004 D15) | [`StartupTaskState`](https://learn.microsoft.com/uwp/api/windows.applicationmodel.startuptaskstate) `Enabled`, `EnabledByPolicy` | `Disabled`; `DisabledByPolicy`, where `registerLoginItem` fails `NotAllowedError` | `DisabledByUser`, which "can only be re-enabled by the user" |
| Windows, a development build (no identity) | the app's value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` ([Run and RunOnce](https://learn.microsoft.com/windows/win32/setupapi/run-and-runonce-registry-keys)) | no value | — |

**Windows: a startup task where the app has identity.** The installed app
is packaged with external location (LLP 1115.004 D15), whose identity
"unlocks … startup tasks"
([Microsoft](https://learn.microsoft.com/windows/apps/desktop/modernize/grant-identity-to-nonpackaged-apps)):
a [`StartupTask`](https://learn.microsoft.com/uwp/api/windows.applicationmodel.startuptask)
declared in its manifest (`desktop:StartupTask`, derived from the grant,
D10, with `Enabled="false"`, since the attribute's true "enable[s] the
startup behavior when the app is first launched" and a login item is off
until the app asks), enabled by `RequestEnableAsync`, disabled by
`Disable`, of which Microsoft says "if
RequestEnableAsync is called from a packaged desktop app, no user-consent
dialog is shown", and read back by `State`, which carries the person's own
switch in Settings › Apps › Startup and Task Manager. The task takes no
arguments (its element lists `TaskId`, `Enabled` and `DisplayName`,
[schema](https://learn.microsoft.com/uwp/schemas/appxpackage/uapmanifestschema/element-desktop-startuptask));
the launch is known by its activation instead (D6). A development build
has no identity, so it writes a `Run` value, whose `enabled` means only
"registered": Windows documents no API for the person's switch over a
`Run` value. On macOS the system lets the app open at login "by
default, and users will be notified" (WWDC22,
[session 10096](https://developer.apple.com/videos/play/wwdc2022/10096/)),
and `requiresApproval` is also the status after the person turns it off in
System Settings.

**`hidden`** is what the registration asked; **`launchedAtLogin`** is
whether this launch is one the login item made, as the host reads it (D6,
"Knowing the launch").

**Errors**, by the web's names: `NotSupportedError` where the target has
none (D14); `NotAllowedError` when the system refuses the registration
(`SMAppService.register()` throws; the `Run` key cannot be written).

### D3 — Global shortcuts

The web has none: a page hears a key only while it has focus. The nearest
names are a browser extension's: Chrome's `commands` marked `"global"`,
which "also work while Chrome does not have focus", their suggested keys
limited to Ctrl+Shift+[0..9]
([`chrome.commands`](https://developer.chrome.com/docs/extensions/reference/api/commands)),
and Electron's `globalShortcut.register(accelerator, callback)`. The
chord's spelling is the web's own: `aria-keyshortcuts`
([WAI-ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/#aria-keyshortcuts)),
which exact2 already reads for in-window chords and the menu bar.

| Name | Kind | Meaning |
|---|---|---|
| `globalShortcut(id=, keys=)` | live source; a fact | while something reads it, `keys` is registered system-wide for `id`; answers `{id, keys, registered, reason}` |
| `checkGlobalShortcut(keys=)` | send; answers `{keys, registered, reason}` | whether `keys` could be registered now, registering nothing that outlives the call |
| `globalShortcutStatus()` | live source; a fact; `sync` | `{available}` and the platform's words |
| `globalshortcut` | event (LLP 1133.004 D6), on the app's root, `"raised": "activation"`, hold 16 | a press of a registered chord: `action pressed(id: string)` or `(id: string, e: GlobalShortcutEvent)`, `e` being `{id, keys}` |

- **`keys`** is one `aria-keyshortcuts` shortcut: modifiers from `Alt`,
  `Control`, `Shift` and `Meta`, then one key, joined by `+`
  (`"Meta+Shift+2"`). ARIA's space-separated alternatives are refused: one
  chord per registration. `Meta` is ⌘ on macOS and the Windows key on
  Windows, never Control (LLP 1115.004 D9), so an app chooses its default
  chord per platform; the Windows key's chords are mostly the system's,
  and a registration of one fails `reserved`.
- **A modifier pair** is a declared deviation in `keys`: `Shift+Shift`,
  `Control+Control`, `Alt+Alt` or `Meta+Meta` is both of that modifier's
  keys held at once, as the T3 Code clone's default is. ARIA has no
  modifier-only shortcut, and the platforms' hot-key APIs take a key, so
  each host hears a pair by watching modifier changes (D11 item 2). On
  macOS that is a global monitor, and "key-related events may only be
  monitored if accessibility is enabled or if your application is trusted
  for accessibility access"
  ([`addGlobalMonitorForEvents`](https://developer.apple.com/documentation/appkit/nsevent/addglobalmonitorforevents(matching:handler:)));
  Apple does not say whether modifier changes are key-related. Stage 1
  measures it on the macOS versions LLP 1115 supports. Where trust is
  needed and not given, a pair answers `registered: false` with `reason:
  "not-allowed"`; asking for Accessibility is the person's act in System
  Settings, which this module does not prompt for. A pair is not a hot
  key, so it is never `in-use`: two apps listening for one both hear it.
- **A pair's monitor sees modifiers and nothing else.** On Windows it is a
  low-level keyboard hook, which "the system calls … every time a new
  keyboard input event is about to be posted into a thread input queue"
  ([LowLevelKeyboardProc](https://learn.microsoft.com/windows/win32/winmsg/lowlevelkeyboardproc)),
  so it is the input monitor the ceiling test keeps out (§7) unless the
  host bounds it. The host installs it only while a pair has a reader and
  removes it with the last; its callback reads only whether the pair's
  two modifier keys are down, records, logs and hands on nothing else,
  always passes the event on (`CallNextHookEx`) and returns well inside
  `LowLevelHooksTimeout`, past which Windows removes the hook "without being
  called". Since the call is "made by sending a message to the thread that
  installed the hook", the hook lives on a thread of its own that does
  nothing but pump it, never the presenter's, and the host reinstalls it
  when a pair stops being heard. On macOS the monitor matches
  `.flagsChanged` only. Neither is a context service a package can listen
  to, nor a hatch.
- **macOS 15's rule.** "macOS Sequoia now requires that a hotkey
  registration use at least one modifier that is not shift or option",
  relaxed in 15.2 for Option alone (Apple's Frameworks Engineer,
  [developer forums](https://developer.apple.com/forums/thread/763878);
  Carbon's hot-key reference is no longer on Apple's site). A chord that
  breaks it answers `reserved`.
- **A registration is a reader.** It is registered at its first read and
  unregistered when its last reader goes (`release(name, args)`, LLP
  1133.009 D10 item 12). A reader whose `keys` change hands over: the
  runner asks for the new arguments before it releases the old
  (`runner/src/runner/modules/bound.rs`, `release_idle`), so a change to a
  chord that registers never leaves a moment with neither. A change to a
  chord that fails leaves neither, since no reader asks for the old one;
  so an app checks a candidate with `checkGlobalShortcut` first and reads
  the new `keys` only when it answered `registered`, as the clone's
  recorder does. A chord taken by another app between the two is an
  answer like any other.
- **One chord, many readers.** The host registers a chord once and
  counts its readers, each named by its session and its `id`. A press is
  delivered once, to one reader: the key window's session if it reads the
  chord, else the status session's (D4), else the oldest reader's; within that
  session, to each `id` reading it. One session's release never
  unregisters a chord another reads.
- **A check registers nothing it keeps.** `checkGlobalShortcut` answers
  `registered` for a chord this process already holds (its own current
  chord) and for a pair whose monitor is allowed, with no platform call;
  for any other chord it registers and at once unregisters, and answers
  what the platform said. So the person can pick the chord in use again,
  or `Shift+Shift`.
- **Data code.** A `globalShortcut` read from data code holds its
  registration until no reader of `globalShortcut` is left at all: the
  runner releases a data-code argument group only with the whole name
  (`release_idle`'s comment). An app that changes chords reads them from
  Contract (§15, "Beyond this module").
- **`registered`** is false with a **`reason`**: `in-use`, another app or
  the system holds the chord (`RegisterHotKey` "fails if the keystrokes
  specified for the hot key have already been registered for another hot
  key", [Microsoft](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-registerhotkey);
  on macOS, `RegisterEventHotKey`'s `eventHotKeyExistsErr`); `reserved`,
  the platform keeps it ("The F12 key is reserved for use by the debugger
  at all times", the Windows key's chords, macOS 15's rule above);
  `not-allowed`, a pair the platform withholds; `invalid`, `keys` is not
  one shortcut. A failed registration is
  an answer, not a failure: it is a state the app shows ("already used by
  another app").
- **The press** is delivered once per press, never by key repeat, in
  order, while any app is in front, the app's own included. The platform
  consumes a registered chord, so the app's in-window `aria-keyshortcuts`
  for the same chord does not also run. It is a person's input (D11
  item 3).

### D4 — A status item

The web has none. A `button` with `-exact-menu="status"` is presented as
the app's status item: on macOS an
[`NSStatusItem`](https://developer.apple.com/documentation/appkit/nsstatusitem)
in the menu bar, on Windows an icon in the notification area
([`Shell_NotifyIconW`](https://learn.microsoft.com/windows/win32/api/shellapi/nf-shellapi-shell_notifyiconw)).
It is a presentation of the button and never a new action (LLP 1021
§5.3). Unlike a menu bar entry it takes the button's place rather than
standing beside it: on a host that places it, the button takes no room in
the page (a tray icon has no second copy in the window), and the agent's
tree shows it as presented elsewhere. On every other host it is an
ordinary button in the page.

| The button's | The status item's |
|---|---|
| text, or `aria-label` | macOS: the item's title when the button has no image, and its tooltip; Windows: the icon's tooltip (`szTip`) |
| one `img` or `svg` child | the item's image: on macOS a template image, which the menu bar tints (D7); on Windows an icon drawn at the system's small-icon size for the display's scale. An app shows a count or a state by changing the image, as it would in the page |
| `press`, `popovertarget` | the clicks below |
| `popovertarget` naming a menu-shaped popover (LLP 1021 D1: `button` rows and `hr`) | the item's menu: on macOS AppKit's own, opened under the item; on Windows LLP 1115.004 D10.1's painted flyout at the pointer |
| `disabled` | the item shown dimmed (`appearsDisabled`); no press, no menu |
| `hidden`, or removed from the tree | the item removed |
| `hatch="…"` | the status item's hatch (D9) |

**The clicks** follow each platform, not HTML's press-then-toggle, which
is a declared deviation:

- **macOS:** a click opens the menu when the button has one, and runs
  `press` when it has none. Apple's HIG says "Display a menu — not a
  popover — when people click your menu bar extra"
  ([menu bar extras](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar#Menu-bar-extras)),
  and an `NSStatusItem` with a menu does not send its single-click action
  ([`menu`](https://developer.apple.com/documentation/appkit/nsstatusitem/menu)).
- **Windows:** with `NOTIFYICON_VERSION_4` the shell sends `NIN_SELECT`
  for a click or a keyboard selection and `WM_CONTEXTMENU` for the menu
  ([`Shell_NotifyIconW`](https://learn.microsoft.com/windows/win32/api/shellapi/nf-shellapi-shell_notifyiconw)).
  The first runs `press`, or opens the menu when there is no `press`; the
  second opens the menu and never presses. The left button does the
  icon's main thing (Excord's, showing its window) and the right one shows
  its menu.

The HIG also says "Let people — not your app — decide whether to put your
menu bar extra in the menu bar". In an app with a window, a status item is
therefore a setting's: the button hidden, the item goes. An accessory app's
status item is the app, and may be made removable by the person through
the hatch (`.removalAllowed`, `.terminationOnRemoval`, which Apple calls
"suitable for applications that display only a NSStatusItem").

**Whose, and for how long.** Status items are the app's, so they come
from one session, the **status session**: the one the launch booted. What
keeps it depends on the app's windows (LLP 1069.010 D4):

- **A one-window app** (`navigate`, and every accessory app): while the
  status session has a status item placed, closing its window hides the
  window, as `keepRunning` does (LLP 1069.010 D8), rather than ending the
  session. So an accessory app's Settings window closed leaves the status
  item, its timers and its shortcut readers running. An accessory app's
  window closed while no status item is placed quits the app, since
  nothing (no Dock tile, no menu bar) would reach it hidden. `host.macos.activationPolicy: "accessory"`
  with `navigate-new` is refused at build (`manifest-accessory-documents`):
  a document app has a Dock tile to come back to.
- **A document app** (`navigate-new`): a document window closes as a
  document does and its session ends (LLP 1069.010 D8), never hidden. When
  the status session ends, the oldest live session becomes it and places
  its own status items; when the last ends, the items go with it, and the
  Dock tile's reopen, which opens a window, places them again.

A `-exact-menu="status"` button in any other session (a document app's
second window, the sample host's second session) places nothing, and the
journal says so once.

**Showing the window.** A status item's "Open" needs to bring the app's
window forward, and nothing in Contract does that today: bare `close()` is
the window's, and `focus(id)` an element's (`focus` is in `HOST_COMMANDS`
with one argument). So bare **`focus()`** is the window's, as the web's
[`window.focus()`](https://html.spec.whatwg.org/multipage/interaction.html#dom-window-focus)
is: it shows the window of the session that ran it if it is hidden (by
`keepRunning`, by a launch with no window, D6), brings it forward and
activates the app. It changes nothing on a host with one always-shown
surface (iOS, Android, the web, the terminal), and a wake refuses it,
since a wake never presents (LLP 1133.017 D6).

**A menu-bar app** is `host.macos.activationPolicy: "accessory"`, which
the build writes as `LSUIElement`
([LSUIElement](https://developer.apple.com/documentation/bundleresources/information-property-list/lsuielement)):
no Dock tile and no menu bar of its own, and every launch is a launch with
no window (D6). Its window, if it has content worth one (Settings…), comes
forward by `focus()`.

**Windows' `keepRunning`.** `host.windows.window.keepRunning: true` makes
closing the window hide it while a status item is placed; with none placed,
closing ends the app as today (LLP 1069.010 D8). A launch while the app
runs hands its activation to the running instance and ends (D6), as it
does for every Windows app.

### D5 — The Dock

**The menu.** A `button` with `-exact-menu="dock"` is also an item of the
app's Dock menu: macOS asks the app delegate for it each time it opens the
menu ([`applicationDockMenu(_:)`](https://developer.apple.com/documentation/appkit/nsapplicationdelegate/applicationdockmenu(_:))),
and the host builds it then from the main window's session (the key
window's, else the first live one), in declaration order, above the items
AppKit adds itself. The item is the button as `-exact-menu` presents it:
its label, `disabled`, `aria-checked`; choosing it presses the button. The
literal joins one menu id: `-exact-menu="file dock"` files the button in
File and in the Dock menu, which is where Agents' New Conversation goes, as
Messages' New Message is in both.

Windows has no such menu: the taskbar's jump list holds shell links, each
starting the app's executable with arguments
([`ICustomDestinationList`](https://learn.microsoft.com/windows/win32/api/shobjidl_core/nn-shobjidl_core-icustomdestinationlist)),
not commands of the running app. A static jump-list task is the Web App
Manifest's `shortcuts` member ([manifest](https://www.w3.org/TR/appmanifest/#shortcuts-member)),
the roster's `quick-actions` (§3.10), which LLP 1133.023 takes. So
`dock` is ignored there, with the button left as it is.

**One Dock menu.** LLP 1133.023 puts its quick actions (the manifest's
`shortcuts`, then the app's list) in the same `applicationDockMenu(_:)`.
The host builds one menu: those items, a separator, this RFC's
`-exact-menu="dock"` buttons, then AppKit's own. A quick action is a
location the app opens; a Dock button is a command of the running
session, so each keeps its own path.

**Attention.** `requestAttention(critical=)`, a send that answers nothing,
asks the system to draw the person to the app while it is behind:

| Platform | `critical=false` (default) | `critical=true` |
|---|---|---|
| macOS | [`requestUserAttention(.informationalRequest)`](https://developer.apple.com/documentation/appkit/nsapplication/requestuserattention(_:)): the Dock icon "will bounce for one second" | `.criticalRequest`: it bounces until the app is activated |
| Windows | [`FlashWindowEx`](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-flashwindowex) with `FLASHW_TRAY`, a few flashes, then the button stays lit | `FLASHW_TRAY \| FLASHW_TIMERNOFG`: it flashes until the window comes to the foreground |

It does nothing while the app is in front, on both, and nothing where the
app has no Dock tile (an accessory app) or no taskbar button (a window
hidden on Windows); the journal says which. Apple: "Sending
requestUserAttention(_:) to an app that is already active has no effect."
An app kept in the notification area draws the person by its own means
there: a notification (LLP 1133.004), and the status item's image changed
to show unread (D4), as a chat client's tray icon does; the badge's
overlay, on a hidden window's absent taskbar button, likewise shows
nothing until the window does. Electron's names are `app.dock.bounce` and
`BrowserWindow.flashFrame`; the module's is one name for both.

**The badge** is `setAppBadge` (LLP 1133.004). On Windows that RFC's stage
3 draws it with `ITaskbarList3::SetOverlayIcon`, on the taskbar button this
RFC's host services keep (D11 item 2).

**Progress** on the Dock icon or the taskbar button is reached by tier 3
(D9), and becomes a shared word, `setAppProgress(value=, state=)` after
the Badging API's `setAppBadge`, when an app asks for it (§13).

## 4. A launch with no window

### D6 — The app model, and the boot rule

**Which launches.** A launch opens no window when:

- the app is accessory (D4), at every launch;
- the launch is the login item's and its registration asked `hidden`
  (D2), on macOS and, while a status item is placed, on Windows.

Any other launch opens its window as today.

**What it does.** The host makes the window and does not order it front.
It boots the session by the window's path, not a wake's: the plan and the
kept answers (LLP 1027 D4), the first commit, its layout at the window's
size, and one frame published that nothing presents. It places that
commit's status items (D4). That moment is the launch's **first pixel**.
A window never ordered front never draws, so no draw receipt calls
`firstDrawn` (`ExactKit/SessionActivation.swift`); the host calls the
continuation itself, which sets the first-draw time, loads the app's
module and its data code, and delivers held module events, as iOS's wake
boot calls `firstDrawn` itself (`ExactKit/SessionWake.swift`). The
continuation means the app's code may run, not that the window was seen.
LLP 1133.017 D7's boot, which loads the app's code with no first pixel, is
the wake's alone. So no app code runs before the first pixel, and what
the status item first shows comes from the plan and the kept answers, as a
window's first frame does.

**The page is hidden; the app is not in the background.** The person is
at the machine: the app runs with origin `app`, its timers fire and its
streams stay open. `exactPage().visibilityState` follows the window, by
Page Visibility, and is `hidden` until the window shows. The runner today
also reads that bit as "not in the foreground"
(`runner/src/runner/modules/admit.rs`: a `"foreground": true` name fails
while `page.hidden`; the package context's `foreground` and sampled
sources follow it), which would refuse a menu-bar app's status-item press
that starts a recording for the app's whole life. On a desktop host they
separate (D11 item 7): the host tells the runner a **background** fact of
its own, true only for a wake or a headless session there, and admission,
the context's `foreground` and the samples read it; Page Visibility reads
the window. On iOS and Android the two stay one, as today. The window's
first showing is not a restore: it does not go through `hideForClose`,
and `exactPage().restores` counts only reopenings after a close (LLP
1069.010 D8).

**App Nap is the platform's.** A Mac app with no visible window is a
candidate for App Nap, which coalesces its timers; the host does not opt
out, since a hand-built menu-bar app does not either. Stage 1 measures
whether a placed status item keeps a menu-bar app from napping; if a
status title on a one-minute timer lags by more than a minute there, the
host holds a user activity (`ProcessInfo.beginActivity`) for as long as
a status item is placed and no window shows. Work that must
not nap (a recording, a transfer) holds the activity its own module
holds. On Windows, the host's work runs while the window is hidden (D11
item 8).

**The boot rule.** `rules/RULES.md`'s row is "App JS executed before first
pixel: none (a wake launch, which presents nothing, is outside it: LLP
1133.017 D7)". A launch with no window has the first pixel above and runs
no app code before it, so the row holds; its parenthetical gains this
launch, so that "first pixel" is not read as a window's first draw. The
`boot` check counts the module graph reachable before first pixel, which
is the same graph here. The cold-start budget ("cold start to interactive
first frame, 100 ms p50") is measured to the status item's placement.
Proposed text for the row (Q2): "none (a launch with no window counts its
first published frame and its status items as first pixel, LLP 1133.025
D6; a wake launch, which presents nothing, is outside it, LLP 1133.017
D7)".

**Knowing the launch.** The host reads, before the session boots, whether
this launch is the login item's, and the registration's `hidden`, which is
the host's own record in the app's defaults or registry key, since
neither platform keeps one:

- **Windows:** the launch's activation record (below), kind `login`. An
  installed build's startup task arrives as the SDK's kind `StartupTask`:
  packaged apps,
  "starting in Windows 10, version 2004, … packaged apps with external
  location", can read their activation, including `StartupTask`
  ([Get activation info for packaged apps](https://learn.microsoft.com/windows/apps/desktop/modernize/get-activation-info-for-packaged-apps)).
  A development build's `Run` value carries the host's argument
  `--exact-login`, which the host turns into the same record kind and
  which never reaches the app's code. "The system may choose to delay the execution of
  programs in the Run key"
  ([Microsoft](https://learn.microsoft.com/windows/win32/setupapi/run-and-runonce-registry-keys)),
  so a login launch is not prompt.
- **macOS:** the open-application Apple event carries
  [`keyAELaunchedAsLogInItem`](https://developer.apple.com/documentation/coreservices/keyaelaunchedasloginitem)
  when "the receiving application was launched as a login item and should
  only perform actions suitable to that environment—for example, it
  probably shouldn't open an untitled document". The host installs a
  `kAEOpenApplication` handler in `applicationWillFinishLaunching`, before
  AppKit dispatches that event and before the session boots (it installs
  none today). macOS 13's `SMAppService` has no hidden flag: Electron's
  `openAsHidden` "does not work on macOS 13 and up"
  ([Electron](https://www.electronjs.org/docs/latest/api/app#appgetloginitemsettingsoptions-macos-windows)).
  Apple does not say whether a launch by `SMAppService.mainApp` carries the
  key. Stage 1 measures it first; if it does not, `launchedAtLogin` is
  `false` on every macOS launch, the status says `apple.loginLaunch:
  "unmarked"`, and `hidden` has no effect there (Q9).

**On Windows, one activation stack.** Startup, files, protocol links and
a toast's click all start the app with a payload, and LLP 1133.004's
Windows stage already chose the Windows App SDK's notifications
(`AppNotificationManager`, `NotificationInvoked`, "the activation arguments
at a cold launch"). So the host takes activation from the same SDK's app
lifecycle, once, for every Windows launch and every build, and LLP
1133.004 reads its toasts from what the host read:

- **The record.** Every launch first registers LLP 1133.004's notification
  activator (Microsoft: "You must call AppNotificationManager.Register
  before calling AppInstance.GetActivatedEventArgs",
  [quickstart](https://learn.microsoft.com/windows/apps/develop/notifications/app-notifications/app-notifications-quickstart)),
  then reads `AppInstance.GetCurrent().GetActivatedEventArgs()` into one
  **activation record**, `{kind, arguments}`: `launch`, `login`, `file`,
  `url` or `notification`, with the paths, the URL or the toast's
  arguments. The SDK's rich activation serves "all apps, packaged and
  unpackaged alike"
  ([rich activation](https://learn.microsoft.com/windows/apps/windows-app-sdk/applifecycle/applifecycle-rich-activation)),
  and its kinds map to the record's: `StartupTask` is `login`, `File` is
  `file`, `Protocol` is `url`, `AppNotification` is `notification`.
  A plain `Launch` is read from its command line: one carrying
  `--exact-login` is `login`; one whose first non-flag argument is a
  location, read as the Linux host reads it (`launch_location`,
  `host/linux/src/app.rs`), is `url`; any other is `launch`. A jump-list
  task (LLP 1133.023 D15 item 3, D17) is a shell link starting the
  executable with a location, so it arrives as a `url` record, and that
  RFC's "second launch hands its argument to the running instance" is the
  redirection below. A cold start's record is held, as LLP 1133.004 D6
  holds a click, and delivered after first pixel. Where the notification
  activator fails to register (an app that ships no notifications), the
  host still reads the record.
- **One instance, for every app.** The host calls
  `AppInstance.FindOrRegisterForKey` with the app's id: "Attempting to
  register an existing key will result in FindOrRegisterForKey returning
  the app instance that has already registered that key." A second
  process that gets another instance back calls
  `RedirectActivationToAsync` with its own activation, and "the calling
  app must wait for the method to complete, otherwise the redirection will
  fail"; then it ends. The first receives it through "that instance's
  Activated callback, the same callback that's used in all other
  activation scenarios"
  ([instancing](https://learn.microsoft.com/windows/apps/windows-app-sdk/applifecycle/applifecycle-instancing)),
  and delivers the record as macOS delivers an open to a running app: a
  notification's under LLP 1133.004 D6's hold, a URL or a file as the
  app's open, a plain launch by showing the window, as the Dock's reopen
  event does. The payload travels inside the platform's own redirection,
  so a toast clicked while the first instance is still starting is not
  lost, and nothing of exact2's carries it, provided the first process
  subscribes to `Activated` as soon as `FindOrRegisterForKey` returns it,
  before the host's event loop starts. This holds for every app, with
  `keepRunning` or without: LLP 1133.023's jump-list location and a
  document opened from Explorer reach the running app, as they do on
  macOS, where an app is one process. `keepRunning` decides only whether
  closing the window ends that process (D4).
- **Cost.** The host links the Windows App SDK runtime, as LLP 1133.004's
  Windows stage needs it anyway, and initializes it through the
  bootstrapper before registering the activator, in both builds: the
  installed build is packaged with external location (LLP 1115.004 D15),
  and such an app, like an unpackaged one, uses the bootstrapper to reach
  the runtime ([deploy](https://learn.microsoft.com/windows/apps/windows-app-sdk/deploy-unpackaged-apps));
  the installer deploys the runtime. Stage 2 lands it once, for both RFCs.

**Reaching the app.** A launch with no window must leave a way back: on
macOS the Dock tile's reopen event, or for an accessory app a status item;
on Windows a status item. The host first decides after the data module's
first commit settles, not at the first pixel, since the commit before it
can show a placeholder that data code then changes (Excord's setting that
shows the tray icon is the app's data). It decides again each time the
status session's placed status items become none while its window is
hidden. Where nothing reaches the app, the host shows the window and
journals `no-window launch: nothing reaches the app; window shown`.

## 8. Permission, grants and origin

### D10 — Nothing asks; who may call is the origin's

None of the four shows a permission prompt, so none has a permission
state (LLP 1133.002 D8): `SMAppService.register()`, the `Run` key,
`RegisterEventHotKey`, `RegisterHotKey`, a status item and the Dock ask the
person nothing. What each changes is the person's own session, so what
decides is who called (LLP 1133.002 D12):

| Name | Origin | Why |
|---|---|---|
| `registerLoginItem`, `unregisterLoginItem` | `"app"`: refused to a tool invocation and a wake, `person-required` | it changes what the person's next login does; App Review guideline 2.4.5(iii) says Mac apps "may not auto-launch or have other code run automatically at startup or login without consent" ([guidelines](https://developer.apple.com/app-store/review/guidelines/#2.4.5)), and the recipe says to register from the person's own choice, a switch in Settings |
| `openLoginItemSettings` | `"app"` | it opens system UI (LLP 1133 D6 rule 3) |
| `globalShortcut`, `checkGlobalShortcut` | `"app"` for a read's first ask and a change of `keys`, and for a check; a re-ask the device causes keeps its reader's origin | a registration takes a chord from every other app |
| `globalshortcut` | the event's origin is a person's input (D11 item 3) | the host raises it at the platform's call for a key press |
| `requestAttention` | any | it shows nothing the person must answer |
| a status item's and a Dock menu item's press | a person's input | the platform's own UI, as a menu bar item's is (LLP 1021 §5.3) |
| `focus()` | any but a wake | a wake never presents |

Under `"app"` a tool may still read `loginItemStatus` and
`globalShortcutStatus`. Presence-like rules do not apply: none of these is
a person's act at a moment, as LLP 1133.010 D12's is.

**What `"app"` does not promise.** The runner's `App` origin is "a
person's input, or the app's own code in a foreground session" (`admit.rs`),
which includes launch, a timer and a resource's answer (LLP 1133.002 D12);
`"person"` is the same test there. So neither word makes a registration
follow a click: an app that registers its login item at first launch, or
reads a global shortcut at boot, is admitted. Consent is the recipe's
(register from the person's own switch; read a shortcut the person chose)
and the system's (macOS notifies the person of a new login item and lists
it in System Settings; Windows lists it in Startup apps), as LLP 1133's
ruling 9 makes asking a guideline. A cause that is only a person's input
event, distinct from launch and timers, is beyond this module (§15).

**Grants.** `device.login-item` and `device.global-shortcuts`, rows that
name no purpose (as `device.background-sync`'s, LLP 1133.017 D14), since
no platform shows one. `device.login-item` derives the installed Windows
build's `desktop:StartupTask` manifest extension; neither derives anything
else. They are the app's statement of what
it may do, checked at bake (`grant-missing`) and listed by the delivery
classifier, so a bundle that starts registering a login item is a native
change. `@exact/dock`, the status item and the Dock menu need none, as
`setAppBadge` needs none (LLP 1133.004 §6).

## 9. Seam additions

### D11 — What the host keeps, and what Windows gains

Each is general, and each is proved by the out-of-tree fixture before a
package of this RFC uses it (LLP 1133.001 D8).

1. **The Windows extension slot.** LLP 1124 D6's row, built: a package's
   `windows/` holds Rust implementing the shared presenter's `Extension`
   trait (`call`, `later`, `release`, `release(name, args)`, `destroy`,
   with a context), beside the hatches' trait in `host/linux/src/hatches.rs`.
   The build compiles it as LLP 1133.001 D9's Rust row says: a generated
   manifest with a path dependency on the package, exact2's crates from the
   SDK checkout, the lock seeded from the SDK lock, `--locked --offline`,
   composed statically into the app's Windows executable, as the hatches
   are. The runner's native slot routes a declared name's body to it on the
   presenter's thread. Its context gives the window's `HWND`, a message
   hook (the host's `winit` loop's raw messages, through
   `EventLoopBuilderExtWindows::with_msg_hook`), and the services below.
   Linux uses the same trait when a desktop Linux host exists; this host
   binds none (D14). This is the slot every later Windows module uses.
2. **Host services in the context**, on Apple and Windows, each keeping a
   one-per-process object. The context is one per session (LLP 1124 D6),
   so every service keys what a session asks by that session, and one
   session's release never undoes another's:
   - **`hotkeys`**: `register(id:, key:, modifiers:)` and `unregister(id:)`,
     and `pair(id:, modifier:)` for a modifier pair, each the calling
     session's; the host counts readers per chord and picks the session a
     press goes to (D3). `check(key:, modifiers:)` answers
     `checkGlobalShortcut` as D3 says. The host keeps the one
     handler: on macOS an `InstallEventHandler` for `kEventHotKeyPressed`
     on the application target, with each registration's
     `RegisterEventHotKey` under the host's signature, and for pairs one
     `addGlobalMonitorForEvents(matching: .flagsChanged)` and a local
     monitor beside it, as the clone has; on Windows `RegisterHotKey` with
     a null window, whose `WM_HOTKEY` the message hook hears, and for pairs
     a low-level keyboard hook (`WH_KEYBOARD_LL`,
     [SetWindowsHookExW](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-setwindowshookexw)),
     bounded as D3 says. A registration answers `registered` or a reason.
   - **`dock`**: the Dock tile or the taskbar button: `badge(_:)` for LLP
     1133.004's `setAppBadge`, `attention(critical:)`, and the hatch's
     objects. On Windows the taskbar button belongs to the window, so a
     request while it is hidden does nothing and says so.
   - **`launch`**: `atLogin` and `hidden`, read before the session boots
     (D6), from the launch's activation record; `loginArguments`, the
     command line a development build's `Run` value carries; and
     the host's record of the registration's `hidden`, app-wide, so the
     last registration wins whichever session made it.
3. **A hot key's press is an activation the host raises.** LLP 1133.004 D6
   gives a person's origin only to an event that arrives through a
   platform callback for a person's act, bound by the host, never emitted
   by a package. A hot key is such a callback: the implementation
   registers through `context.hotkeys`, declaring the event the press
   raises, and the host raises it with a person's input as its origin on
   the session whose reader registered it. The fixture outside the tree
   declares a hot-key event of its own and is driven the same way.
4. **Two presentations in the presenters.** The compiler admits `status`
   and `dock` in `-exact-menu`, `dock` beside one menu id, and
   `status-quit` in `-exact-menu-remove`; `-exact-menu="status"` with
   another id is refused (`lower-menu-status`). The macOS host places
   status items from the status session and answers
   `applicationDockMenu(_:)` (`ShortcutsMac.swift`'s `sync()`, which already
   walks the buttons); the Windows host adds the notification-area icon,
   its hidden message window, its flyout and its re-adding when Explorer
   restarts (the `TaskbarCreated` message,
   [notification area](https://learn.microsoft.com/windows/win32/shell/notification-area)).
5. **A launch with no window** on macOS and Windows (D6): the host
   calling `firstDrawn`'s continuation after the unpresented first frame;
   `host.macos.activationPolicy` (`LSUIElement`); the status session's
   window hiding on close while it holds a status item; the login launch's
   reading; reachability decided after the data module's first commit and
   again when the last status item goes; on Windows,
   `host.windows.window.keepRunning`, the launch's activation record read
   once through the Windows App SDK's app lifecycle, and one instance by
   its `FindOrRegisterForKey` and `RedirectActivationToAsync`, which
   documents, protocol links and notification activation also need.
6. **Bare `focus()`** in `HOST_COMMANDS`' `focus`, the window's, on every
   host (a no-op where there is one surface always shown).
7. **Background, apart from visibility.** The runner's page gains a
   host-told `background` fact beside `hidden`; admission's
   `"foreground": true` check, the package context's `foreground`, the
   sampled sources' pause and a wake's timer stop read `background`, and
   Page Visibility reads `hidden`. iOS and Android set both together, as
   today; the macOS and Windows hosts set `background` only for a wake or
   a headless session. Every module that runs while a desktop window is
   not showing meets this, so it lands in stage 0, before either host's
   no-window launch.
8. **The Windows host runs while its window is hidden.** Today its work
   runs inside drawing (`host/windows/src/window.rs`: `draw` pumps the
   presenter, its tasks and timers, and returns early while minimized), so
   a hidden window would stop Excord's heartbeat. The host's turn (pump,
   tasks, timers, the session clock's deadlines) runs from the event loop's
   wake-ups whether or not a frame is drawn, and drawing is what a shown
   window adds.

Each is apparatus under `rules/RULES.md` and lands with this ruling.

## 11. The substitute

The substitute answers on every host; under the agent no login item is
written, no hot key registered, no status item placed and no Dock menu
built, so a drive never changes the machine it runs on.

**Shape.** `loginItemStatus`, `globalShortcutStatus` and a registration are
facts; nothing is a request; `globalshortcut` is an activation event.

- **The login item.** `loginItemStatus` defaults to `{available: true,
  state: "disabled", hidden: false, launchedAtLogin: false}`, set by
  `prefer extension login-item.loginItemStatus=…`.
  `registerLoginItem(hidden=)` sets `state` `enabled` and `hidden`, unless
  the preferred `state` is `requires-approval`, which it keeps;
  `unregisterLoginItem` sets `disabled`; both answer the new status, by
  LLP 1133.004 §7's value form. `openLoginItemSettings` is journaled. The
  launch flag `--login` makes a launch the login item's:
  `launchedAtLogin` true, and with `hidden` set the launch opens no window
  (D6), which `state.documents.windows[].visible` shows.
- **Shortcuts.** Each registration is an entry of `state.extensions`'
  keyed list (LLP 1133.004 §7): `{id, keys, registered, reason, ref,
  session}`. `prefer extension
  global-shortcuts.globalShortcut={"registered":false,"reason":"in-use"}`
  makes registrations answer so, and `checkGlobalShortcut` answer the
  same. `tap @<ref>` on a registered entry raises `globalshortcut` with a
  person's origin, as `tap @ref` raises a notification's click, delivered
  to one session by D3's rule; on an entry that is not registered it is
  refused by name.
- **Attention** is journaled (`requestAttention: critical`) and its last
  request listed under the extension.
- **The presentations** are listed as `state.statusItems` (`{label,
  image, disabled, menu, testId}`) and `state.dockMenu`, beside
  `state.menuBar`, on every host, from the session the host would take them
  from; the buttons are in the tree, marked as presented elsewhere, and
  `tap <testId>` is the item's primary click by D4's rule for the host
  driven (`contextmenu <testId>` its secondary). An accessory app's launch
  under the agent opens no window, and `focus()` shows it.
  `state.page` shows `background` beside `hidden` (D11 item 7).
- **Target restrictions hold** (LLP 1133.002 D14 step 2): on a target whose
  cell is absent, every package name fails `NotSupportedError` under the
  agent too.
- **Production:** none of it. `--bind login-item`, `--bind
  global-shortcuts` and `--bind dock` run the platform under the agent for
  the conformance suites, on macOS and Windows only.

**Declared, not built in** (LLP 1133.001 D8): each form above is in the
interfaces' `exact.json`, so a third party's module drives the same way.
