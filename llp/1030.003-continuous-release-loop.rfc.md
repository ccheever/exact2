## Summary

Charlie, 2026-09-11, building Interview: committing and pushing should deploy
the website and updates to installed apps; a running app should learn about a
release and refresh while keeping what the person was doing; Marc Bodnick must
be able to install the iOS app remotely and answer "what version are you on?"
with something quotable and copyable; and the dev and deploy loops are part of
what Exact2 offers, not a thing each app builds. He asked for this proposal
and for an integrated iOS distribution workflow, naming EAS Hosting as the
first hosting target and an always-on Linux machine behind an HTTPS tunnel as
where Interview's backend lives.

This extends LLP 1030 and 1030.000; it adds no second delivery architecture.
r2 rewrites r1 against the code as of 2026-09-12 rather than the 2026-09-04
landing review: every ticket that review filed is closed, so the publisher
already snapshots the whole source closure (Interview *and* the sibling
exact2 checkout), signs heads that point at immutable blobs, allocates `seq`
under a held lock, and the Apple host activates a bundle across every session
with prepare/commit/discard. What is genuinely missing is smaller and more
specific than r1 said: a signed publication time and a readable release id on
the head; the version facts on the `exactDelivery` resource and a bounded
history in the store's record; the check running on foreground and on an
interval, and on the web at all; two mechanical deferrals before activation;
the iOS distribution archive, its upload, and its version numbers; the
`--watch` publisher; a publisher that can run off a Mac (D8, on Charlie's
second ask of 2026-09-12); and one honest finding about EAS Hosting (D7).

Decisions: **one release run, several deliveries that finish on their own
clocks** (D1); **the release id is the quoted identity and gains a signed
publication time — no counter, no second ledger** (D2); **the version screen
is a `use`-able Contract component over an extended `exactDelivery`, with
history in the store's record** (D3); **the check runs after first pixel, on
foreground, on an interval, on the app's own nudge, and on the web** (D4);
**activation is `app-decides` plus two deferrals the runner and host apply
themselves** (D5); **iOS ships through TestFlight first, ad hoc from the origin
as the fallback, macOS through `exact release`; all three are lanes of the
same verb** (D6); **the first hosted release is on the directory origin behind
Interview's tunnel; EAS Hosting is the second adapter, after a spike** (D7);
**the publisher runs anywhere, a binary lane is a job on a Mac it names, and
EAS fills the gaps it verifiably fills — compute, iOS credentials, secret
files, TestFlight, enrollment — and not the ones it does not** (D8).

## 2. Decisions

### D1 — One release run, several deliveries that finish on their own clocks

A release is one `exact deploy --yes` from one immutable snapshot (1030.000
D3): bake, classify, publish the origin row and every stream whose cohort
check passed, and print what happened per row. Nothing here changes that
order. What this document adds to the run:

1. **The binary lanes are rows in the same table**, acted on by
   `binaries.<platform>` and `release.<platform>` (1030.000 D4): `ios` is
   "archive, upload, processing, availability" (D6); `macos` is "sign,
   notarise, staple, publish the `.dmg` as a blob" (`exact release` folded
   onto the deploy snapshot, D6). Each lane leaves a record beside the
   stream's (`releases/<release>.<platform>.json`: the archive's receipt,
   the upload id, what the console said last) and the table prints the lane's
   last known state: `uploaded`, `processing`, `available to internal`,
   `waiting for beta review`, `expired`, `failed`. **"Uploaded" is not
   "Marc can install it."** A lane's asynchronous states are asked for by a
   later run (`exact deploy <app> --status`, a read), never awaited inside
   the publish.
2. **Retries reuse the run.** `--release <id>` names an existing run
   directory; a stream already published under that id is `current`, a
   lane already uploaded is `processing`; nothing is republished and no
   number is reused (a refused or failed lane leaves a gap in `seq`, as
   today).
3. **An older publisher cannot overwrite a newer release**: `seq` is read
   under the held lock and the head is a conditional put on the digest
   read (1030.002 D3) — built. A slow build of an old commit publishing
   after a fast build of a new one is the one case the lock does not catch,
   because both are valid releases; `--watch` (item 4) prevents it by
   serialising on the branch head, and a terminal publisher is told by the
   table that the origin's head names a newer snapshot than its own and
   refuses without `--force-older`.
4. **`--watch`** (1030.000 D5 item 2, owed there and built here): the same
   library, a separate process on an always-on machine, watching one branch
   of one repository, snapshotting each new head commit, running the five
   checks the app declares, and publishing what the policy allows. It holds
   the signing key and, on a Mac, the Apple credentials by reference (D7 of
   1030.000); the dev server never does. Where it runs, and how a machine that cannot
   build a platform still publishes to that platform's stream and hands its
   binary lane to a Mac, is D8 — with the **bundle-only row** (a stream row
   classified from the plan graph alone, which is target-neutral by 1030
   D3a's ruling, leaving the binary row `unbuilt here`) as §6 question 2,
   recommended, since it is what makes "push to deploy" true from a Linux
   box.

Provider credentials stay outside source and outside the dev server
(1030.000 D7). There is no cross-provider transaction and no promise that
every device changes at once: the origin is a fresh load away, a bundle is
the next check and the app's chosen moment, a binary is the store's review
and the person's tap (1030 D5). A backend change the clients depend on is
published first, by Interview's own means, and stays compatible for the
whole tail (1030 D5's expansion before contraction); rolling a backend back
is Interview's operation, separate from publishing an older client.

### D2 — The release id is the quoted identity, and the head says when it was published

r1 proposed a human release number (`#42`) allocated by the publisher beside
the release id. That is a per-channel counter, and a per-channel counter
needs a per-channel guarded record and a lock the publisher does not hold
today (its locks are per stream). The cheaper identity is already there and
already correlates one deploy across every stream it touched (1030 D3a): the
**release id**. r2 makes it quotable and adds the one fact the client cannot
compute:

- **The default release id becomes `<UTC date>-<UTC time>-<sha7>`**:
  `2026-09-12-1432-a1b2c3d`. Monotonic to the eye, sortable, and it names
  the commit. The nonce that today keeps two publishers from colliding in one
  second moves to the *run directory* only; two releases in the same minute
  from the same commit are the same release (the second is `current`), and
  from different commits they differ in the sha. `--release <id>` still
  overrides it.
- **The signed head gains `published`** — the publisher's UTC clock as an
  ISO string, beside `release` — so a client can show "Published Sept 12 at
  2:32 PM" from bytes it verified, without a second fetch of the unsigned
  record. The publisher's clock is the authority for that field; the device's
  clock is diagnostic (D3).
- **`seq` stays the protocol's order and the anti-rollback floor**, per
  stream; the screen shows it in small type after the release id, because a
  developer reading a bug report needs it and Marc does not.
- **A channel promotion is a new signed head for the destination stream**
  (1030.000 D4) and keeps the release id — the same release, now on `prod`.
  Republishing older content is a new `seq` under a new release id; a
  rollback never lowers a floor.
- **The store's numbers.** `CFBundleShortVersionString` comes from a new
  optional manifest key, `app.version` (default `0.1.0`, as today).
  `CFBundleVersion` — which App Store Connect requires to increase on every
  upload — is the snapshot's commit count on its first-parent line
  (`git rev-list --count --first-parent`), monotonic along a branch,
  reproducible from the commit, and needing no ledger; a rebase or a hotfix
  branch can collide, the upload refuses, and `--build <n>` is the manual
  escape. Both land in the receipt and on the resource as `binary` (D3).

**The trade, stated.** A date-and-sha id is longer than `#42` and two people
can misread a time zone. If Marc cannot quote it, the counter returns as a
per-channel guarded record — the mechanism exists for the web root pointer
and could be reused — and this document names that as the door (§6 Q1).

### D3 — The version screen is a `use`-able component over an extended `exactDelivery`, with history in the store's record

**The resource grows.** `exactDelivery` (1030 D7, landed) answers seven
fields by name. It gains these, each a string, number, or `list<string>` so
the runner's `Value` carries it and a shape declares only what it wants:

| Field | Meaning | Filled by |
|---|---|---|
| `release` | the running generation's release id; `""` for a development plan; entry zero's comes from the publisher receipt the bake embedded (`EXACT_UPDATE_RECEIPT`) | store |
| `published` | the running head's `published` (D2); `""` if unknown | store |
| `entry` | the running entry's envelope digest; `""` for entry zero | store |
| `stagedSeq`, `stagedRelease` | what is waiting, so the banner can say which | store |
| `checkedAt`, `checkOutcome` | the last completed check: device wall clock; one of `never` · `checking` · `current` · `staged` · `refused` · `unavailable` | store (`unavailable` splits from `Refused` in `client.rs`: a transport failure is not a refusal) |
| `activatedAt` | when this generation booted or was activated on this device | store record |
| `binary` | the host's version and build as baked (`0.1.0 (143)`), from the receipt | host |
| `platform` | `iOS 26.6.1 · iPhone17,1`, `macOS 26.1`, the browser's UA family | host |
| `history` | newest first, at most 100 lines, `<device time> <event> <release> seq <n>[: reason]` | store record |

**History lives in `record.json`**, written in the same rename as the
transition it describes — received-and-verified, staged, activated,
activation deferred (with D5's reason), refused, entry demoted, fell back to
entry zero — so a crash cannot leave a line saying "activated" with the
record still selecting the old entry. On open, an unfinished activation is
reconciled against what the record actually selects and one line says so.
Retention of history is separate from retention of entries. Device
timestamps are diagnostic: ordering is `seq`.

**The component.** One Contract file apps `use` (1017 P8), placed as the
first file of `contract/use/` — `use Delivery from "…/contract/use/
delivery.contract"` — with no root of its own: a shape over the fields above
and a component that renders, offline, from the resource alone:

> Interview · Beta · 2026-09-12-1432-a1b2c3d
> Published September 12 at 2:32 PM · seq 43
> Activated on this device at 2:41 PM
> Last checked just now · Up to date
> [Check for updates] [Copy version info] [Update history ▸]

"Up to date" means the last completed check found the head current; it is
never a claim about a server the device could not reach, which reads
"Couldn't check · 2:40 PM". The other states, each a line the component
already knows how to render: checking; an update is ready (with the
`stagedRelease`, and a button that calls `deliveryActivate`); activation
deferred (D5's reason); refused (the reason from history); a new app is
needed (the sunset card's message and store link, 1030 D5 — the only way a
client learns a binary is required). A development plan shows
"Development · <compatibility id>… · plan <digest>…" and no release.

**Copy version info** calls `copyText` with a template the component
composes: app, channel, release, `published`, `seq`, `entry`, `binary`,
`compatibilityId`, `platform`, `checkedAt`/`checkOutcome`, `activatedAt`.
Nothing else: no tokens, phone numbers, invitations, drafts, or paths.
`state.delivery` mirrors every field for the driver; the eight operations
stay eight (`rules/NOT-DOING.md`).

An app places the component where it likes — Interview on the profile page,
under "A little about you" — and may restyle it; a wrapper must not claim a
release other than the one the resource reports.

### D4 — The check runs after first pixel, on foreground, on an interval, on the app's nudge, and on the web

Today the Apple host checks once, two seconds after first pixel, and on
`deliveryCheck`. r2 adds, all host work and no runner change:

- **On foreground** (`UIApplication.didBecomeActive`, `NSApplication.
  didBecomeActive`), debounced to at most once a minute.
- **On an interval while foregrounded**: fifteen minutes by default,
  `deploy.check.interval` in the manifest to change it. A head is a
  `no-store` fetch of a few kilobytes.
- **`BGAppRefreshTask` on iOS** when `deploy.check.background` is set
  (1030.000 D4: host metadata) — opportunistic, quota-limited, off in Low
  Power Mode, an accelerator and never the mechanism (1030 D5). Owed, and
  not in Interview's first slices.
- **The app's own nudge.** Interview already polls its backend every five
  seconds on a question page. If that response carries the channel's current
  release id — Interview's backend learns it however Interview likes; the
  head is a public file — the Contract compares it with `delivery.release`
  and calls `deliveryCheck` when they differ. No SSE, no WebSocket, no
  APNs; exact2 sends no pushes and relays none (1030.000 D6). A hint is a
  reason to check; the check verifies the signed head, the cohort and every
  digest exactly as an unhinted one does.
- **The web page.** The web has no store and a fresh load is current (1030
  D1), but an open tab — Interview's desktop and mobile web, which Charlie
  put first — is not. The page gains the same check: on `visibilitychange`
  to visible and on the interval, fetch its own origin's envelope (`Accept:
  application/vnd.exact.envelope+json` at `/`, `no-store`), compare the
  plan digest and asset digests with the running generation's, and, when
  they differ, apply the fetched generation through the restart-with-carry
  the dev loop already uses (LLP 1007 §6, `glue.js`), under D5's deferrals.
  `exactDelivery` on the web then answers `staged` honestly instead of
  never, and `deliveryActivate` means "restart with carry from the fetched
  generation". No service worker (1030 D1); an installed PWA's shell stays
  the browser's cached copy.

### D5 — Activation is `app-decides` plus two deferrals the runner and the host apply themselves

`activate: app-decides` (1030.000 D4, built) already holds a checked bundle
as `pending` until the app calls `deliveryActivate`, and `next-launch` stays
available. Interview's first policy: stage immediately, activate at a
boundary the Contract chooses — on the feed with no composer open and
nothing pending — and otherwise show the "update is ready" row and leave the
choice to the person. No global default changes.

Two deferrals are mechanical, so no app has to get them right:

1. **The runner refuses `deliveryActivate` while a command is in flight**
   (`send outcome = command(…)` awaiting its reply). A reply that arrives
   after a restart would land in a runner that no longer exists, and the
   person would post their answer twice or think it was lost. The refusal is
   a `history` line (`deferred: 1 command in flight`) and the resource's
   `checkOutcome` stays `staged`; the app retries at its next boundary. A
   resource read in flight is not a reason to defer: it is not carried and
   simply re-issues (`Runner::carry` filters `pending_res`).
2. **The host defers while an editor is composing or a gesture is in
   flight** — a first responder with marked text (IME composition), an
   active touch or drag, an interactive pop or sheet dismissal in progress
   (1035.001 D2) — and applies at the next quiescent main-thread turn. It
   never waits an arbitrary timer and never assumes typing ended.

What carrying keeps is what the runner keeps today and nothing more (1030
D9, said loudly): slots by name where their types still fit — Interview's
drafts are slots (`editName`, `editBio`, the composers), so they survive;
settled resource answers by name and arguments; the store; the clock. A slot
the new plan no longer declares is lost, and the history line says which.
Navigation, reading position, focus and selection are the host's to restore
across a reload, as 1035.001 D7/D8 already govern them for Messages and as
1029.000 §1 declines to promise for view objects; this document adds
acceptance cases (§4), not a second restore mechanism.

Failure paths are the built ones: a candidate one session refuses is
discarded for all (prepare/commit/discard); a crash before first pixel twice
demotes the entry and the next launch boots the last good one, then entry
zero (1026 D11); a demoted digest is not restaged. The screen reads the
truth from the record after any of these. An incompatible release — one the
classifier refused for this cohort — never reaches the device; the only
thing a client sees of it is the sunset card.

### D6 — iOS ships through TestFlight first, ad hoc from the origin as the fallback; macOS through `exact release`; all lanes of the same verb

**Why TestFlight first, for Marc.** Ad hoc needs Marc's UDID enrolled in
the developer portal, a profile regenerated and the archive re-signed for
every new device, and a valid HTTPS install page; a hundred devices a year.
TestFlight needs an App Store Connect app record, a distribution-signed
upload, and Marc's Apple ID in a tester group: no UDID, no re-sign, ninety-
day builds, install through the TestFlight app. External testers pass Beta
App Review once for the first build of a version; internal testers (App
Store Connect users) do not. 1030.000 §5 Q5 already ruled the launcher goes
through TestFlight first. Ad hoc stays as the lane for a device that cannot
wait for review, or a phone with no Apple ID.

**The archive** — `host/apple/build.mjs --ios --archive`, run on whichever
Mac the lane's builder is (D8) — is `--device` with distribution facts: an "Apple Distribution" identity from the keychain
(`EXACT_DISTRIBUTION_IDENTITY` names one), an App Store or ad hoc profile
for the bundle id (`EXACT_PROFILE`, else found by app id and type),
entitlements without `get-task-allow`, `EXACT_UPDATE_TRUST=production` with
`EXACT_UPDATE_RECEIPT` for an `L = A` binary (README), D2's version and
build numbers, and the app icon and `Info.plist` bake already writes. Output:
`Payload/<App>.app` zipped as the `.ipa`, its receipt (identity, profile
name and expiry, entitlements as signed, toolchain, the compatibility id,
`CFBundleVersion`) under `target/deploy/<release>/ios/`. Built from the
deploy snapshot, never the working tree.

**The upload** is a step of the `ios` lane with credentials by reference:
an App Store Connect API key (`EXACT_ASC_KEY_ID`, `EXACT_ASC_ISSUER_ID`,
the `.p8` in Apple's key directory) through Apple's uploader, or `eas
submit --platform ios --path <ipa>` — verified 2026-09-12 to accept a
locally built `.ipa` (eas-cli `submit.ts`: `--path`, "Path to the
.apk/.aab/.ipa file"). Either is an adapter; neither requires the app to be
an Expo project. What follows the upload is asynchronous — processing,
export-compliance and agreement prompts, availability to a group, Beta App
Review, expiry — and D1 item 1's `--status` reads it through the App Store
Connect API and prints it. Existing testers keep the build they have while
a replacement processes.

**Ad hoc from the origin.** The same archive signed with an ad hoc profile,
the `.ipa` published as a blob, and beside it `manifest.plist` and an
install page (`/.exact/install/ios/`) whose link is `itms-services://?action=
download-manifest&url=<https origin>/…/manifest.plist`. Safari on the
enrolled phone installs it; HTTPS with a trusted certificate is required and
the tunnel supplies it. Enrollment is Charlie's act in the developer portal;
exact2 runs no enrollment service. A new device is a new profile, a new
signature, and a new distribution artifact beside the old one, never a
rewrite.

**macOS** is `exact release` (1033 D8) taken onto the deploy snapshot and
into the table as the `macos` lane: Developer ID, hardened runtime,
notarise, staple, `spctl`; the `.dmg` published as a blob with a download
page. The Mac App Store lane and the Linux package stay in 1030.000 §6.

**The install page** on the origin (`/.exact/install/`) lists, per platform, the
current binary's release id, version and build, and how to get it —
TestFlight link, ad hoc link, `.dmg` — and the version screen's "a new app
is needed" state links to it. No promise of replacing an iOS binary
silently, of bypassing the person's tap or Apple's review, or of a custom
runtime exemption from Apple's rules on downloaded code: bundles carry a
plan, assets and bytecode, never native code (1030 §7).

**What Interview must declare** before its first distributed binary:
`deploy.store.ios: "A"` and `deploy.store.macos: "A"` (today `0` — a
binary that takes no bundle), `app.origin` (the update origin, D7),
`deploy.signing` (a key from `keygen`), `app.version`, and a channel
(`beta` first). The backend URL is compiled into its data crate today; the
first distributed binary fixes it to a stable hostname (D7), so a backend
move never needs a binary.

### D6a — The standard install page

Charlie, 2026-09-12: use `/.exact/install/`, initially web, iOS and macOS;
show different installation methods per platform, with future platforms and
prioritization possible. He explicitly commissioned the LLP and implementation.
This is the install-page slice, not a commission to implement Exact2 Go, EAS
signing or every binary distribution lane in D6.

The web bake generates `/.exact/install/index.html` and platform pages under
`web/`, `ios/`, and `macos/`. Exact's server resolves the trailing-slash and
slashless forms. `/install` remains an app-owned route; `.well-known` is not used.
All pages show stacked Web, iOS and macOS sections in that order, without tabs.
Unavailable sections are gray. Without JavaScript every section and
installation link is readable. No automatic downloads, custom-scheme probes, or
claims that a native client is installed.

`app.json` owns an optional `install` object. Each platform has `methods` in
presentation order and optionally `recommended`, naming one of those methods.
The recommended method appears first and is labeled. No numeric priorities or
platform ordering API in this slice. Unknown platforms, wrong-platform methods,
duplicate method kinds and a nonexistent recommendation fail validation.

```json
{
  "install": {
    "ios": {
      "recommended": "testflight",
      "methods": [
        {"kind": "testflight", "url": "https://testflight.apple.com/join/EXAMPLE"}
      ]
    },
    "macos": {
      "methods": [
        {"kind": "download", "url": "https://downloads.example.com/App.dmg", "version": "1.0 · Build 42"}
      ]
    }
  }
}
```

These URLs illustrate the shape, not available artifacts. Method vocabulary:
web `browser`; iOS `go`, `direct`, `testflight`, `app-store`; macOS `go`,
`download`, `terminal`. Each requires a URL, with optional `label`, `description`
and display `version`. `go` may provide `setupUrl` to install the shared client;
its open URL must be a configured HTTPS link with a real handler. `direct` may
be an HTTPS enrollment/download page (including a supported signing provider)
or an `itms-services` link to an HTTPS installation manifest. `terminal` requires
an authored `command` and an HTTPS instructions URL. The command is displayed and
copied only, never executed; clipboard refusal falls back to selectable text.
Do not synthesize a shell installer or assert notarization from a filename.

Omitting web configuration supplies “Open in browser” using `start_url` or `/`.
An explicit empty methods list disables that default. Missing native methods show
an honest unavailable state. The browser destination is visible as URL text,
resolved to an absolute URL by the page. Only
configured methods are rendered: installing a dedicated app and running inside
Exact2 Go have distinct labels. The first Interview page has a working web link;
no native artifact or Go URL exists yet to advertise. Home-screen instructions
and automatic links from distribution receipts remain follow-up work.

URLs accept HTTPS (browser additionally accepts root-relative paths); reject
credentials and script/file protocols. All authored text and attributes are
escaped. Methods are operator-configured availability, not a claim the bake
contacted Apple or verified provider readiness. A distribution publisher will
supply them only after D6's readiness checks; manual configuration is useful now.

Charlie’s subsequent design direction, 2026-09-12: reuse app branding, show
version and hosting context, and use a gray Exact mark and wordmark in the footer.
The optional `brand.logo` and `brand.wordmark.image` select images under `assets/`.

Build trust mode and serving context are separate: canonical Exact server pages

Generate these files ahead of time outside the app's boot graph. Include the

navigation URLs retain their canonical meaning rather than following the app's
immutable asset base. No new public directory wildcard or secret file exposure.

Verify real HTTP routes against local and published roots, old-reader retention,
removed methods and unknown-route refusal; test escaping and URL validation.
Drive the page in desktop and mobile browser sizes, stacked sections, explicit
links and terminal copy behavior. This slice adds no Rust runtime behavior,
backend service, signing provider or deployment gate.

### D6b — Local iOS installation

Charlie, 2026-09-12: build locally now; leave EAS as an option for later. On a
Mac, and only on the development server, D6a's iOS section gains one dynamic
method: **Build, install, and open**. It enumerates available iOS Simulators and
reachable, paired phones; the person chooses one; and the server invokes the
existing app-owned `host/apple/build.mjs --ios --sim` or `--device --phone` path
with that target and the page's app URL. The simulator path builds the simulator
triple, ad-hoc signs, installs through `simctl`, and opens Simulator. The phone
path selects an installed development profile covering the bundle id and device,
uses the matching Apple Development identity, builds and signs the device target,
installs it through `devicectl`, and opens it. It creates no second Apple builder
or signing policy (1036.000 §§2–4).

The action is an asynchronous dev-server job. The page keeps reporting
`building`, the bounded tail of its log, and the terminal `installed` or
`failed` result; a second request while it runs is refused. The POST needs a
random 32-byte token embedded only in install pages that process serves over
loopback, and an `Origin` naming its loopback address; the app URL is one of
the addresses the server printed, never a request header (2026-09-23). Target ids are namespaced and accepted
only after fresh `simctl`/`devicectl` enumeration, never as arbitrary command
arguments. A Simulator can use a loopback app URL. A physical-device request made
from a loopback page uses a printed LAN address when the server is on the LAN,
and refuses when the server is actually loopback-only. Static and hosted pages
contain no token, endpoint UI, or build action.

This is development provisioning, not ad hoc distribution: the phone must
already be paired with the Mac, enrolled in the chosen profile, reachable by
cable or Wi-Fi, unlocked, and in Developer Mode. It produces no `.ipa`, does
not enroll devices, uploads nothing, and adds no public signing endpoint. D6's
TestFlight/ad-hoc archive and D8's EAS/AppDrop-style remote builder remain the
non-Mac and remote-recipient paths.

**Implementation and proof, Codex 2026-09-12.** `host/web/dev.mjs` owns the
single in-memory job and invokes the existing Apple build; `scripts/install-page.mjs`
adds the dev-only UI without putting it in published bytes. The install tests
cover static/dev separation, Simulator presentation and token injection. Against
Interview's real LAN dev server, missing-token and cross-origin requests returned 404 and 403, the
page found one paired iPhone 17 Pro Max on iOS 26.6.1, and the page-equivalent
POST built, development-signed and installed `com.interview.app`, then
`devicectl` reported that bundle identifier launched. Interview exposes the
LAN flow as `npm run dev:phone`. Its ordinary loopback `npm run dev` page found
the booted iPhone 17 Pro Simulator, built and installed the simulator artifact,
opened `com.interview.app`, and the agent read Interview's 25-node tree and state.

### D7 — The first hosted release is on the directory origin behind Interview's tunnel; EAS Hosting is the second adapter, after a spike

Charlie named EAS Hosting first. Checked 2026-09-12 against its
documentation and eas-cli's source, four facts decide how it can be used:

1. **Deployments are immutable, each at its own URL; an alias (and the
   production alias) is repointed with `eas deploy:alias`.** Nothing is
   documented about whether repointing is atomic for a concurrent reader,
   and there is no conditional put on any file. 1030.000 §5 Q3 **ruled a
   conditional put required** of an origin adapter; EAS Hosting does not
   have one. The adapter would have to get serialisation elsewhere — one
   publisher process (`--watch`) and a `seq` read back from the alias URL —
   which is a weaker property than the ruling asked for.
2. **Static files get a 3600-second browser cache by default, and the
   documentation offers no per-path override for static files** — custom
   `Cache-Control` is documented for API routes only. The head is `no-store`
   by 1030 D1; served static from EAS, an update or a rollback reaches a
   client up to an hour late. Serving `.exact/**` from an API route that
   reads the deployment's own files with `no-store` is the workaround, and
   it is provider code the adapter would own.
3. **`eas deploy` uploads everything under `dist` except `.DS_Store` and
   its kin** (eas-cli `worker/assets.ts`: dotfiles are *not* skipped; 500 MB
   per file), so `.exact/` and `.well-known/` upload. Whether they are
   *served*, with what MIME type and headers, is unverified.
4. **`eas deploy` resolves an Expo project config** — an `app.json` whose
   `expo` key carries a slug and a project id — which is the name exact2's
   manifest already has. The adapter runs eas from its own staging directory
   with its own `app.json`, never from the app's root.

The one adapter that passes every property the RFCs paid for, today, is the
directory origin served by `serve.mjs --origin` — "or that same HTTP handler
behind TLS" (1030.000 D3) — and Interview already has an always-on Linux
machine behind an HTTPS tunnel. So: **slice 2 proves the loop there**, with
the web app at the root, the streams under `.exact/`, the install page, and
the tunnel's certificate; the publisher runs wherever D8 puts it and
writes to the box over the adapter's own transport (an `ssh`/`rsync`
directory target is the first remote directory origin; the held lock runs on
the box). **EAS Hosting is slice 2b**: a spike that answers, with one real
deployment, whether dot paths are served and with what headers, whether a
concurrent reader ever sees a half-repointed alias, and whether an API route
can serve the head `no-store` — then an adapter shaped as "one whole
deployment per release, alias promoted last", with the origin row `current`
until the alias reads back. The web app on EAS and the streams on the
directory origin is a permitted split (`app.origin` names the update origin;
the website's URL is the manifest's `start_url` host), at the cost of 1023
D1's one URL, and is named here so nobody has to rediscover it.

**The backend boundary.** Interview's Snapback2 owner, its adapter, the
tunnel, trusted-proxy handling, the database, its backups, supervision and
health checks are Interview's, specified in Interview's corpus and moved off
*Interview's* NOT-DOING ("production hosting") when its slice starts. What
this document needs from that backend is two things: a stable API hostname
before the first distributed binary (the URL is compiled in), and,
optionally, the current release id in a response the app already polls (D4).
An old client keeps calling the old way for the whole tail (1030 D5); the
compatibility window is Interview's to keep, and the classifier's table is
where a breaking backend change is noticed before a client that needs it
ships.

### D8 — The publisher runs anywhere; a binary lane is a job on a Mac it names; EAS fills the gaps it verifiably fills

Charlie, 2026-09-12: *"can we make it so that you can publish mac from any
platform and we use some Expo/EAS services to fill in any gaps?"* Yes, with
one boundary stated first: a macOS or iOS **build** runs on macOS — AppKit
and UIKit link there, and `codesign`, `notarytool` and `stapler` are
Apple's tools on Apple's OS — so "from any platform" means the **publisher**
is location-independent and a binary lane is **a job it submits to a Mac**,
not work it does itself. The publisher does everything else where it sits:
snapshot, bake the plan and assets, classify, publish the origin row and —
with §6 Q2's bundle-only row — every stream row, from a Linux box or a
laptop with no Xcode. Each binary lane records the job it submitted in its
lane record; `--status` reads the job and, when it is done, fetches the
archive and its receipt, publishes them as blobs with the install page, and
hands the `.ipa` to TestFlight (D6).

**The builder is named per platform**, `deploy.builders.<platform>`:

- `local` — this machine; today's `build.mjs` and `exact release`.
- `ssh://<host>` — a fleet or home Mac; the same scripts run there over
  the adapter's transport, on the same snapshot commit.
- `eas` — an EAS Workflows custom job on a `macos-medium` or `macos-large`
  runner.

All three run one code path: `node scripts/deploy.mjs <app> --release <id>
--lane <ios|macos>` on the worker, checking out the app and exact2 at the
snapshot's commits (a job on EAS starts from a stub Expo project directory,
because of D7 item 4's `app.json` collision), fetching the publisher receipt
the archive embeds (`EXACT_UPDATE_RECEIPT`) from the origin, and writing the
receipt and artifact the local lane writes. The dev loop is untouched, and
a Mac at the desk stays the fastest lane and the one a laptop uses.

**What EAS fills**, verified 2026-09-12 against its documentation and
eas-cli's source:

- **macOS compute with Xcode.** Workflows custom jobs run arbitrary `run:`
  steps on `macos-medium | macos-large` — a fresh VM per job with Xcode
  26.6, Node 22 and fastlane, and **no Rust**: the job installs the pinned
  toolchain from `rust-toolchain.toml` with `rustup`, minutes per job until
  a cache step is proven. Triggered `on: push: branches: [main]`, which is
  `--watch`'s trigger with no always-on machine of ours.
- **Secret files.** Environment variables of `file` type with `secret`
  visibility are materialised as paths on the runner and are unreadable
  outside EAS: the Developer ID `.p12` and the App Store Connect `.p8` live
  there. 1030.000 §5 Q4 ruled a least-privilege store for cloud
  credentials; this is one.
- **iOS credentials.** EAS credentials manage the distribution certificate,
  App Store and ad hoc provisioning profiles and push keys, and
  `eas device:create` provides the UDID enrollment page and QR code that
  D6 said exact2 would not run itself.
- **TestFlight.** `eas submit --platform ios --path <ipa>` as a `run:` step
  (the workflow's own `submit` job takes only an `eas/build` build id, so a
  custom job submits by path or `--url`).
- **Artifacts.** `eas/upload_artifact` and `eas/download_artifact` between
  jobs, and a URL the publisher's `--status` fetches.
- **The website.** EAS Hosting, with D7's caveats.

**What EAS does not fill, and stays ours:** the origin's conditional put and
`no-store` head (D7); the bundle signing key and every signed head (the
publisher's, wherever it runs); the archive, sign, notarise, staple and
version steps themselves (`build.mjs --archive`, `exact release` — our
scripts, run on the worker); custody of a macOS Developer ID beyond a secret
file (EAS manages no macOS certificate and knows nothing of notarisation);
whether EAS internal distribution's install page accepts an `.ipa` a custom
job produced rather than `eas build` (unverified — the `itms-services` page
on our origin is the fallback either way); the Rust toolchain on the worker;
and the job's minutes and metering.

**The spike before the lane is written:** one workflow job that checks out
Interview and exact2 at a commit, installs the toolchain, runs `build.mjs
--ios --archive` with EAS-managed credentials, uploads the `.ipa`, submits
it by path, and prints each step's time; and one for `exact release` with a
`.p12` and `.p8` from secret files, ending with `spctl` on the stapled
`.app` — which also gives 1033 D8 the notarisation proof this Mac could not.

## 3. What this refuses

- **A service** (1030 §7, `rules/NOT-DOING.md`): no "last seen running
  release" reports, no user directory, no targeting, no console. Which
  version Marc has is answered by Marc copying it; which versions are out
  there is `exact reach` over an origin log (1030.000 §6), when it exists.
- **Push delivery.** The app's own poll may carry a hint; exact2 owns the
  check and nothing that wakes it (1030.000 D6).
- **A second ledger, a counter, or a committed lockfile** (1030.000 D3).
- **A patch format, generations matched by identity, or runtime
  compilation** (`rules/NOT-DOING.md` §Runtime): activation is a restart
  with carry.
- **A second restore mechanism** for focus, scroll or navigation: 1035.001's
  is the one.
- **Native code to iOS by any carrier** (1030 §7).
- **An enrollment or install service**: install pages are static files.
- **A ninth agent operation** (1030 D7).
- **Pretending an EAS alias repoint is a conditional put**, or that a
  3600-second cached head is `no-store`.
