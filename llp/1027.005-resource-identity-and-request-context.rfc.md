## Summary

A resource's call arguments say which answer it is. Values after `with` are
what its source also needs in order to answer now. The source receives both,
in order, and a change to either asks again, as today. The difference is at
boot, before the data source is ready: the answer kept from the last launch
(LLP 1027 D4) shows if its call arguments match, whatever the `with` values
are now.

```contract
resource status = status(car) with minute as shape Status
```

`status` reads the car's last status from the store and uses `minute`, a slot
a timer sets (LLP 1027.000.000 D4), to judge whether that status is still
fresh or must be fetched. The first ask needs a current wall-clock sample,
not a slot's initial 0: LLP 1027.000.000 D4's example slot starts at 0 and
first ticks a minute later. The timer advances it thereafter. Yesterday's
status of this car is the right first frame today. Another car's is not.
Without `with`, every argument identifies the answer, as today.

This changes admission of one answer kept from the last launch. Current
requests still compare every argument. The implementation is in the runner;
D5 says where that applies and what it leaves on the web.

## Motivation

LLP 1027 D4 keeps a store-reading resource's last fresh answer, up to 8 KB.
On a host that creates the data source after first pixel, the first frame
shows that answer if its arguments equal the resource's current ones, else
the bake's empty-store answer. `data_ready` then asks again.

Arguments that differ from one launch to the next defeat the match, even when
the answer is about the same thing. Fieldnotes does this in this repo. Its
`library(query, saveRevision, serviceRevision)` is kept with the revisions of
its last answer. `fieldnotes.revision` is persisted and grows with every save
(`apps/fieldnotes/app.ts:12–17`). The next launch starts both derives at 0
(`app.contract:68–70`). So a notebook in which anything was saved last session
opens on the empty-store frame, which is the case D4 was built to avoid. This
is deduced from the declaration and the boot seed in `runner/src/runner.rs`,
for a library within the 8 KB bound; it has not been driven.

James's proposal names three kinds of such argument. Two already have a
better home, and moving them there fixes the kept answer without new syntax:

- **A counter that only forces a re-ask** belongs in `refresh` or
  `refreshes` (LLP 1016 D3; LLP 1035.005.000 D6). Fieldnotes' `library`
  source ignores both counters: its dispatch reads `[query]`
  (`app.ts:207`). With `refreshes library` on `saved` and `status`, the
  declaration is `library(query)`, and its kept answer matches whenever the
  query does. James's `session() with sessionRev` is the same case.
- **The date for display** belongs in a derive over
  `time.epochAtZero + now()`, not an argument (LLP 1027.000.000 D4). A `now()`
  argument asks again at every commit made later, wherever it is written.
- **Credentials** stay below the seam (LLP 1018 D5). A locale that changes the
  language is part of what is asked.

That leaves a store-reading source that needs a value which changes between
launches but does not change what the answer is about. The clearest case is a
source that uses the time to decide whether what it holds is fresh, or must be
fetched. Its last answer is right to show while the current answer is
pending. `with` is for that case; time is an example, not a special input
type.

## Design

### D1 — Syntax and meaning

```contract
resource name = source(call, …) with context, … as shape T
```

`with` takes one or more expressions after the call and before `as shape`.
A declared `else` keeps its grammar and place. A call may have no arguments:
`source() with x` names one answer for the declaration.

The source receives the call's arguments followed by the `with` values. Each
`with` value is typed, tracked and evaluated exactly as an argument is today.
A change to any of them asks again under the existing settlement rules
(LLP 1005 §5, LLP 1016 D5). Nothing becomes ambient, and no value stops
triggering a re-ask. A `with` on a resource that keeps nothing (one that
reads no store) changes nothing.

### D2 — What goes in `with`

A value goes in `with` when the last answer for the same call arguments is
right to show during revalidation. That promises only that the stale answer
is suitable to show. It does not promise that the fresh answer will be equal,
or that the source can skip its work.

| Input | Where it goes |
|---|---|
| The thing asked for: a car, a document, a query, a folder, a historical date | The call |
| A locale that selects the language or representation | The call |
| An account or tenant that partitions the data | The call, as a non-secret id the first frame can compute |
| A counter that only forces a new ask | Neither: `refresh` in the action, `refreshes` on the mutation |
| The date, to show it or a relative time | Neither: a derive (LLP 1027.000.000 D4) |
| The time the source needs, to judge whether what it holds is fresh or expired | `with`, as a slot a timer sets |
| Credentials | The granted store, below the seam (LLP 1018 D5) |

Time and locale are not context by nature. `weather(place, day)` asks a
different question when the day changes.

An empty call keeps one answer for the declaration, as `remember()` does
under LLP 1027 D4, including its one-frame correction when the store changed
underneath. It is no boundary between accounts. A resource that holds one
account's private data names the account in its call.

### D3 — Admission: the one comparison that changes

Let *identity* be the number of call arguments. Before the data source is
ready, a resource eligible for kept answers under LLP 1027 D4 (runner-owned
facts are still excluded) shows its kept answer when all three hold:

1. The value is this declaration's persisted kept answer. It is not a
   compiled value, a placeholder, a reload's carried answer or a document
   checkpoint's answer. Those keep their own rules.
2. The entry decodes, its argument list has *identity* values, and its value
   fits the declared shape.
3. Those values equal the current call arguments, under today's value
   equality.

Otherwise the existing fallback shows: the bake's empty-store answer, or the
declared placeholder. An admitted answer is stale, and `data_ready` asks with
the current full arguments. Under `with`, its state holds only the
identifying arguments (D6), so no full-argument comparison can take it for
the answer to the current ask. Without `with`, *identity* is every argument,
and the rule is today's.

The runner seeds kept, carried and checkpoint values into the same
`ResourceState` (the boot seed in `runner/src/runner.rs`). Condition 1 therefore
needs a boot-local eligibility mark set only by the persisted seed. Preserve
it while the seed stands through commits before readiness. Clear it when
the identity ceases to match, a fallback or fresh answer replaces the seed,
or activation commits (D4). Changing the arguments back does not readmit a
discarded seed. A refused commit restores this bookkeeping with the value,
as the commit checkpoint already restores `stale` (`runner/src/runner/commit.rs`).

Every other comparison stays on full arguments: request reuse, a pending
ticket, failed arguments, reload carry, checkpoint adoption and compiled
values.

### D4 — Activation, then ordinary requests

Once the source is ready, `data_ready` asks with the latest full arguments,
however many times the context changed before readiness. If the source
answers asynchronously, the kept value stands with its own identifying
arguments while the pending ticket records the current full arguments
(LLP 1016 D3). It stays provisional: it is not carried, checkpointed or kept
as the answer to that request. Only a fresh valid answer from a successful
commit is kept. A kept seed or placeholder never is.

**Build-time answers alike (2026-10-04).** A compiled answer shown before
readiness is now asked at `data_ready` too, even when its arguments are the
bake's (LLP 1048.003 D6). A kept seed and a build-time answer therefore
behave the same way: each is shown first and asked once the source is ready.
`with` still decides only which kept entry is admitted. Nothing here
changed.

From then on, request behavior is unchanged: a changed `with` value asks
again, every request comparison uses the full arguments, and identical
transport requests, superseded tickets, failures and late replies follow
LLP 1016 D5.

**Found in r3's review, outside this landing.** A second `data_ready()`
before the first ask's reply asks again: `data_ready` collects every `stale`
resource (`kept.rs`), `stale` clears only on a fresh answer, and a forced
ask bypasses `enqueue`'s rule that keeps an identical request in flight
(`commit.rs`). Astra's runner probe issued tickets 1 and 2. No host does
this. Apple and Linux activate once per runner (`data_activated`,
`host/apple/src/host.rs:665`, `host/linux/src/host.rs:580`), and the wasm
host once per boot. A worker-placed module reports ready only when the host
activates it, just before `data_ready` (`data/src/placed.rs`). The behavior
is the same with or without `with`, so it is a separate small fix (QUEUE),
not part of admitting `with`.

### D5 — Where it applies, and the gap it leaves

Kept answers are admitted only when the source is unready at boot. Once
admitted, they remain visible while its asynchronous answer is pending
(the boot seed in `runner/src/runner.rs`). Admission happens where a host loads
the module after first pixel and persists the entry: the Apple hosts and the
wasm web target (LLP 1027 D4). Linux persists none. D3 and D4 are
implemented once, in the runner those hosts share.

The default web JS target installs a TypeScript module before the first
commit (`host/web-js/build.mjs`, the generated `main.js`), and `mount` loads
the store from `localStorage` (`rt.js`). Its TypeScript sources are loaded at
boot, so it keeps nothing, and `with` there is ordinary trailing arguments.
The emitter already compiles every plan argument in order
(`host/web-js/src/emit.rs`), and a conformance case confirms it. Its
`checkpoint().kept` is a rendered document's answers (LLP 1048.000), which
keep full-argument adoption. D3's exception does not reach them.

A source already ready at boot can still answer slowly. Every target then
uses its existing fallback until the reply lands, the runner included, since
it seeds no kept answer for a source ready at boot. Astra's probe (2026-10-02) ran
Fieldnotes' real `library` source on the JS runtime with SQLite held: the
first commit showed "Opening your notebook…", the bake's answer
(`app.ts:139`), and the saved note followed the reply. The JS target also
keeps nothing for a Rust module it loads after first paint (`rust-data.js`),
where the runner would. Closing the first gap means keeping answers for a
slow first ask on every target, which changes LLP 1027 D4. Closing the
second means porting the runner's kept answers to the JS target. Neither is
part of this landing (follow-up 3).

### D6 — Representation

**Syntax**, as James wrote it. The parser appends the `with` expressions to
`ResourceDecl.args` and records `identity: Option<usize>`, the call's own
argument count, or `None` without `with`. Types, the source-signature table,
lowering and symbols all walk `args`, so they see the context expressions
without change. The formatter prints `with` at the boundary.

**Plan.** `resources.context: u16` is the number of trailing arguments that
are context, 0 without `with`. Counting the tail keeps the builder's default
right. Lowering declares each row before it installs the row's arguments
(`contract/lower/src/lib.rs:320` and `:388`, `set_resource_args`), so a count
of leading arguments defaulted when the row is declared would be 0 for every
row: every kept answer would match on an empty prefix. Lowering sets `context`
with a checked conversion, and validation refuses `context > args.len`. The
format's digest moves, and plans are baked with their runtime, so there is no
compatibility path.

**Kept entry.** The encoding is unchanged: an argument list and a value
(LLP 1027 D4). The list holds only the identifying arguments. An entry then
changes only when its identity or its answer does. `Store::keep` skips a
write identical to the stored text (`runner/src/store.rs`), so a source asked
every minute that gives the same answer is not persisted again every minute.
With the context in the entry, it would be. An entry whose list has a
different length (the declaration changed) is not used. A resource without
`with` keeps exactly today's entry.

## Alternatives

- **Keep by declaration alone, ignoring arguments.** It would show another
  car's or another account's answer.
- **A key clause (`kept by car`).** It allows any expressions in any order,
  but adds a second list to evaluate and name. The split point covers every
  case in hand.
- **Infer context from clock reads.** A slot that a timer writes looks like
  any other slot, and the author could not see the inference.
- **Annotate each argument.** James's reason holds: the split concerns the
  question as a whole, and it keeps `status(car)` readable.

## Verification

| Area | Evidence |
|---|---|
| Syntax and formatter | `with` after calls with zero, one and several arguments; nested context expressions; an empty `with` refused; `contract fmt` round-trips. |
| Lowering and plan | `context` is the number of `with` values, 0 without them, set after the arguments are installed; an invalid decoded count is refused before execution; TypeScript and Rust sources receive the same full argument order. |
| Runner | The cases below, beside the existing rollback and 8 KB tests. |
| Web JS target | One conformance case: the source receives all arguments in order, and changing a `with` value asks again with full-argument request rules. |
| Platform drive | Drive the existing Completion Storm request fixture on the web and Apple, alongside the kept-answer runner and real TypeScript seam tests. James's app has not been identified, so its returning-launch behavior remains unverified. |

The runner cases are:

- identity matches and context differs;
- identity differs;
- no `with`, where the entry's bytes are today's;
- an empty call;
- two context changes before readiness, followed by one ask with the latest;
- an identity change before readiness discards the seed; changing back does
  not readmit it;
- a refused commit before readiness restores the seed's mark with its value;
- an asynchronous activation: the kept value stands, provisional, while the
  ticket carries the full arguments;
- a context change while the activation request is pending: ordinary
  full-argument request rules, and a superseded reply cannot replace or persist
  the current answer;
- a failed activation request, which writes no kept entry;
- a context-only change with an equal answer, which writes nothing;
- damaged, wrong-length and wrong-shape entries;
- carried and checkpoint values, which do not gain the exception;
- a source ready at boot, which behaves as today.

Run the five checks and the platform fixture with the existing drivers. No new
check, script or benchmark app is proposed. On adoption, amend LLP 1027 D4
(identifying-argument admission), the plan format's `_resources` note,
Contract's syntax documentation and LLP 1071's runtime gaps (the JS target
keeps no answers).
