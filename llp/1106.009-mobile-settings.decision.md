## Context

[observed] The mobile oracle is T3 Code at `365aa87982`. Its Settings scope can
select several environments and one logical project. The desktop clone's shared
transport, permission checks and data helpers remain the mobile app's data owner.
A selected logical project can have a different physical project ID in each
environment. Usage has its own environment filter and pooled account limits.
Scheduled Tasks retains an editable draft across nested model and branch routes.

[observed] LLP 1106.004 covers the Home grouping and initial device preferences;
LLP 1106.003 covers transport and credentials. Neither defines these scoped
server writes, retained task drafts or pooled usage accounts. This child records
the choices implemented in M8. It does not accept the implementation or claim
that the screens match the oracle.

## Scoped server settings

[observed] [root-presentation.ts](../examples/t3-code/mobile/root-presentation.ts)
projects Settings scope from the existing saved environments and shared fleet.
Environment-wide scope uses `members: null`. A project scope contains the exact
physical project members; an unavailable project produces an empty member list
and never broadens to environment-wide writes. The selected environment list for
Provider accounts is independent of whether that project exists on each server.

[observed] [settings-server.ts](../examples/t3-code/mobile/settings-server.ts)
and [settings-provider.ts](../examples/t3-code/mobile/settings-provider.ts) keep
the shared RPC and current-permission checks. Multi-environment saves report
partial failures by environment. Provider preparation reads catalogs and actual
auth state; typing, choosing a pending option and reveal changes use synchronous
projection. Provider auth events pass through the existing shared native reader
before acknowledgement. No second transport event drain is introduced.

## Scheduled draft

[observed] [settings-scheduled.ts](../examples/t3-code/mobile/settings-scheduled.ts)
uses the shared live-environment and task-stream helpers. The editor captures its
actual environment, project and task identity. Edit saves require the task still
to exist. The mobile upsert keeps the source's webhook schedule, signature and
runtime values, which the adopted desktop draft helper does not fully represent.
New tasks set `creationSource: mobile`; existing tasks retain their source. This
is an app-local payload adaptation, not a shared-protocol change.

[observed] Nested model and branch routes edit that same draft. Branch responses
are checked against the current query and draft before updating the list. Save
locks the draft before awaiting a real reply, retains it on failure, and closes
only after success. Delete, webhook rotation and dirty close require the native
confirmation associated with the captured target. The time picker returns a
local clock time; the mobileScheduleInput validator owns its payload.

## Usage accounts

[observed] [settings-usage.ts](../examples/t3-code/mobile/settings-usage.ts)
prepares real server summaries and uses shared merge/window/format helpers.
Usage begins in Limits with all selected enabled environments, a 30-day window
and cost as the metric. Disconnected environments retain explicit status rows. Its selection is separate from Settings project scope.
The window anchor stays fixed until refresh or a new period is chosen.

[observed] [settings-usage-limits.ts](../examples/t3-code/mobile/settings-usage-limits.ts)
uses the pinned account-pooling rules to combine native and hub views of the same
provider account. Pooling keeps freshness, reset times, credits and the actual
eligible redemption target. A hub target takes precedence where the source
requires it. Missing summaries, denied permission and incompatible contract
versions do not become invented zero usage or quota. Account detail uses the
selected pooled key and window, and reset-credit redemption requires explicit
native confirmation before the existing server operation. The adapter captures the environment and exact redemption input before presenting confirmation, then revalidates both afterward. A changed target or credit requires a new confirmation.

## Root and native lifetime

[observed] [settings-scheduled-flow.ts](../examples/t3-code/mobile/settings-scheduled-flow.ts)
combines asynchronous preparation with a separate synchronous projection.
Contract resources and mutations remain in the root; the reusable
[SettingsAutomation component](../examples/t3-code/mobile/settings-scheduled-flow.contract)
contains presentation and actions. Only the top route renders the current-route
projection. Field changes refresh that projection without re-reading catalogs or
permissions on each keystroke.

[observed] The root uses separate mutations for local edits, branch reads and
native/server actions. A new search can replace an older read while typing cannot
abandon a Save or a pending native menu. Pending actions also project disabled
editor controls. Each command result carries its initiating route ID; a late
response cannot pop or push a different page. Debounced branch reads use their
own mutation so an earlier read cannot consume the next query's timer.

[observed] [T3MobileScheduledControls.swift](../examples/t3-code/mobile/modules/apple/T3MobileScheduledControls.swift)
owns only its presented menu, time picker or confirmation and its reply. It
refuses automated confirmation in agent mode. The scheduled navigation adapter
uses the existing Exact route and authored Back action, guards dirty modal
closure and temporarily disables interactive pop for the root editor. Model and
branch Back preserve the draft. The Scheduled list reuses the Settings scope menu
and adds an authored New action. Usage keeps its own filter and refresh controls.

## Information sources

[observed] [settings-information.ts](../examples/t3-code/mobile/settings-information.ts)
keeps About, Client Storage, Diagnostics, licenses and Legal local to the mobile
build. About reads actual bundle version/build; it does not expose Expo update
checks. License search/detail uses shared decodeNotices over the app-owned bundled
manifest, not a remote server or the upstream Expo dependency list. The manifest
contains source-derived notices for known app libraries/assets and explicitly says
complete framework and additional grammar attribution remain unverified.

[observed] The adopted client has no matching persistent five-kind offline cache
or Expo ErrorRecovery startup journal. Storage and Diagnostics therefore report
unavailable and disable Clear/Copy. They never substitute preference deletion,
remote server diagnostics, invented byte counts or a zero-crash success. Local
gap003/004 record missing app owners; no core-framework defect is established.

[observed] Legal uses an app-owned private WKWebView with JavaScript disabled,
nonpersistent storage, no-cache requests, an exact source-default legal path
allowlist, actual progress/errors, retry and explicit external-browser behavior.
Exact still owns the route and authored Close action. The existing iframe API does
not expose this per-navigation policy. Full license notice selection uses a
UIKit scroll/UITextView because the Contract compiler refuses user-select:text on
iOS. Native delegates and observations end with their view. Retry creates a fresh
WKWebView and rejects old callbacks; each live legal view holds the shared audio
lease until WebKit media suspension completes during teardown. Current root Legal
presentation is modal; full-screen source parity is not established. No second transport or
persisted Settings owner is introduced.

[observed] Information TS tests and Swift source checks pass. Its new isolated
Contract fixture stopped after three attempts: fixture action syntax, unsupported
user-select:text, then native prop collisions for line-height/muted. Those props
now have notice prefixes in source; that correction is not Contract-compiled. This
slice has no native launch, network/gesture/selection drive or visual parity proof.

## Alternatives

[inferred] Copying the mobile React state layer would give this app a second
transport and draft owner. Reusing the desktop task draft unchanged would lose
mobile schedule/runtime fields. Applying the Settings project scope to Usage
would exclude account data that the source includes. The implemented adapters
keep the existing shared owners and make those mobile differences explicit.
