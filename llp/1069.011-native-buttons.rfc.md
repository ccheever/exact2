## Summary

A `button` today is a `Pressable`: a box Exact lays out and paints, whose look is the author's. This lets an app ask for the platform's own button instead, per button, deliberately:

```
button appearance="auto" buttonStyle="glass" press=send aria-label="Send"
  image "symbol:send"
```

`appearance="auto"` (CSS's switch between the platform's control and the author's box) makes it a native button: `UIButton` with a `UIButton.Configuration` on iOS, `NSButton` on macOS, the browser's own `<button>` on the web, a painted button on Linux. `buttonStyle` picks the style from one table. Its `text` and `image "symbol:…"` children are its title and image. Its size is the platform's. `press`, `disabled`, `aria-label`, focus, keys and the agent's `tap` work as on any button. Without `appearance="auto"` nothing changes.

## 1. What exists

- **`button`** lowers to a `Pressable` with fixed rows `display: flex`, `flex-direction: column` and the role `button` (`tags.rs:252`). The Apple node view presses on touch-up (`NodeViewIOS.swift:1314-1352`), is the first responder for keys and Enter/Space (`247`, `289-297`), draws Exact's focus ring (`276-287`), and is the accessibility element (`997-1005`). The web host resets it (`index.html:27`, `all: unset`).
- **`appearance`** (bit 149, `auto | none`, default `auto` on every node, not inherited) and **`accent-color`** (bit 148, inherited) came with LLP 1069.001; only `Control` reads them.
- **`Control`** (LLP 1069.001 D2) is a measured leaf (`node.rs:94-98`, children not laid out, `133-136`). The host builds the platform control in the node's box (`ControlsIOS.swift:96-143`, `ControlsMac.swift`), reports its natural size after each batch (`presenter.onIntrinsic` → `Kernel::set_intrinsic_size`), and reads a `select`'s options through the kernel (`select_choices`, `exact_select_options`). Several paths assume "not a checkbox or switch" means "a select": `ControlKind::of` and `ControlKinds.kind` fall through to checkbox; the index lists `type:checkbox|select|range|date|time|datetime-local` (`ChromeIndex.swift:14-17`); iOS identifies a select by `is UIButton` (`ValueControlsIOS.swift`); Linux toggles any other control as a checkbox (`presenter/control.rs:37-62`).

## 2. Measured

A scratch UIKit app (iOS 27 simulator, iPhone 17 Pro) built each of the twelve `UIButton.Configuration` styles with the title "Send", a long title, the symbol `plus`, and both, and two rows of `glass()` buttons with an 8-point gap inside a `UIGlassContainerEffect`:

| Fact | Measured |
|---|---|
| Metrics at the default `medium` size | the same in all twelve styles: content insets 7/12/7/12, height 34.33 pt |
| Width with a title | the title's width + 24 ("Send" 63.33, "Send message now" 172) |
| Width, symbol only | 47 in the eight classic styles; 34.33 (a circle) in the four glass styles |
| Width, symbol and title | 90 for "Send" + `paperplane` in every style |
| `sizeThatFits(200×20)` | the intrinsic size, whatever is offered |
| Corners | `dynamic` in the classic styles, `capsule` in the glass ones |
| Glass buttons, gap 8, container spacing 8 / 24 | apart at rest / one merged shape (James's finding) |

macOS's `NSButton` and the web's looks are not measured here; the build measures them (§4).

## 3. Design

**D1. The switch: an `appearance` that is the literal `auto` after class merging.** CSS's `appearance` switches between the platform's control (`auto`) and the author's box (`none`). Exact's `button` has always been the author's box, so `button` gains a fixed row `appearance: none` (declared: Exact's UA sheet for `button`; `layout` now reports it on every ordinary button). The effective `appearance` — the fixed row, then the class's, then the node's own, last wins — decides:
- the string literal `auto` (one class, both arms of a class choice, or the node's own): a native button;
- absent or `none`: an ordinary `Pressable`, as today;
- anything bound, including the ternary a class choice synthesizes when only one arm sets `appearance` (the other arm's `none`-clear would fall to the kernel's `auto`): refused, `lower-button-appearance`. Being native decides what the node is; an app that switches writes `when`.

**D2. `buttonStyle` and the `buttonStyles` table.** A native button's style is a host-policy prop, `buttonStyle` (`str`), named in one schema table, `buttonStyles`, generated as `materials` is: `[name, iOS UIButton.Configuration, iOS before 26, macOS look, web/Linux look]`, kebab-case one-to-one with Apple's names. Names: `plain`, `gray`, `tinted`, `filled`, `borderless`, `bordered`, `bordered-tinted`, `bordered-prominent`, `glass`, `prominent-glass`, `clear-glass`, `prominent-clear-glass`. Absent, a native button is `bordered`, chosen as Exact's default because a browser's own button is a bordered one.
- Every row names what each platform draws; a `~` marks a stand-in. Known stand-ins are silent, as LLP 1053.000's accepted materials policy is; the agent reports the requested and the drawn style (D10). A bound name that is not in the table draws `bordered` and is logged once.
- *iOS 26+*: the named configuration. *Before 26*, the glass styles draw `bordered` (or `borderedProminent` for the prominent ones).
- *macOS*: `NSButton` looks, one per row: the plain and borderless styles borderless (`isBordered = false`, the accent as `contentTintColor`); gray, bordered and the tinted ones a `push` bezel; filled and the prominent ones a `push` bezel with the accent as `bezelColor`; the glass ones `NSBezelStyleGlass` on macOS 26 (else `push`). The build measures each and corrects the table.
- *Web and Linux*: five looks, each style naming one — `ua` (the browser's own button: `bordered`, `gray`), `text` (`plain`, `borderless`), `soft` (`tinted`, `bordered-tinted`), `fill` (`filled`, `bordered-prominent`), `glass` (the four glass styles; the prominent ones with an accent fill). Stated approximations.
- `buttonStyle` on anything but a native button is refused (`lower-button-style`), as is a literal name not in the table; a bound one must be a choice among literal names, each checked.

**D3. A native button is a `Control` of type `button`, and says so everywhere a control's kind is chosen.** Contract lowers the native button to `NodeType::Control` with fixed props `type = "button"` and role `button`, and fixed rows `appearance: auto`, `display: flex` (a block-level flex item, as a custom button is; no `flex-direction: column`). An authored `type` other than the literal `"button"` is refused, since the type is the discriminator. Kind dispatch names `button` before every checkbox or select default:
- *Kernel*: `ControlKind::Button`, matched before the switch/checkbox fallthrough; its size before a host reports is §2's medium metrics rounded, 64 × 34 (frame one on Apple until the report, as a select's 64 × 19 is; the web never uses kernel sizes). *Runner*: `control_payload`'s arm makes `input`/`change` on a button `InvalidEvent`; `press` is not a control payload.
- *Apple*: `ControlKinds.kind` returns `button` for `type == "button"` first; `type:button` joins the index lists (`ControlKinds.indexed`, `ChromeIndex`); the button's code lives in a new file per platform (`IOS/NativeButtonsIOS.swift`, `Mac/NativeButtonsMac.swift`), and every select-only path (configuration, typing, observation, `unopened`) tests the node's kind, not `is UIButton`.
- *Linux*: a `Control` of type `button` is pressed (`dispatch_press`, never `toggle_control`), painted by its look, refused by `type`, and sized (`size_controls`) as its title plus the look's padding; Space and Enter keep pressing it through the existing role path (`typing.rs:201-205`).

**D4. One owner for touch, keys, focus and VoiceOver.** On Apple the platform control takes the touch; the node keeps everything else:
- *Touch*: the control fills the node's content box (D6), so a touch on it is the control's; its primary action (`UIControl.Event.primaryActionTriggered`, `NSButton`'s action) dispatches the node's `press` once, through `presenter.press`. A touch on the node's padding is the node's, and presses as a custom button's does (padding is part of a button's box on the web too). Nothing sets `pressed`, so there is no press feedback.
- *Keys and focus*: the node stays the logical focus owner — `canBecomeFirstResponder` and `tabbable` include a native button, so Tab/Shift-Tab, `tabIndex`, `autofocus`, `focus()`/`blur()`, focus events, `retainFocus`, collection pins and Exact's focus ring are unchanged, and Enter/Space press through the node's existing path. The platform control is not a key view (`NSButton.refusesFirstResponder`), so a key is handled once.
- *VoiceOver*: the platform control is the accessibility element, labelled with `aria-label` or the title, `.notEnabled` when disabled; the node is not an element (the `kind == "button"` branch at `NodeViewIOS.swift:997-1005` does not apply to a control). `Accessibility.swift`'s name for the node reads the face (D5), not mounted children.
- *Disabled*: `isEnabled = false`; the node's own press guard applies to its padding.

**D5. The children are the face: data, never views.** A native button's children are its title and image, read through the kernel as a `select`'s options are: `Kernel::button_face(view) -> ButtonFace { title, symbol, leading }`, walking the live tree so a `when` updates it; Apple reads it through `exact_button_face` (beside `exact_select_options`), Linux directly. Apple does not project the children (`paragraph.rs` skips a native button's children as it skips options; no mirrors, no views); Linux does not paint them. The web emits them (D8).
- *Grammar*, checked by walking the children as `run()` does (`when` and `match` branches, `each` refused): every reachable face has at most one `text` and at most one `image`, and at least one of them. A face that can be symbol-only requires `aria-label`. The `text` is a string (literal or bound), whitespace-collapsed as an option label is; an `image`'s source is a literal `symbol:` role or a choice among literal roles, each checked against the symbols table. The children carry no attributes but `testId` and, on the `image`, nothing else; no `press` or other handler below a native button. Refused: `lower-button-content`, which takes precedence over the generic empty-button refusal.
- *Order*: an image before the title is leading, after it trailing (in the inline direction, so trailing-first in RTL); `imagePlacement` and `NSButton.imagePosition` follow.

**D6. Size and frame: the platform's, one line, the box's CSS around it.** A measured leaf: Apple reports the control's natural size (`intrinsicContentSize`) after a batch and on a content-size-category change (`UIContentSizeCategory.didChangeNotification`; AppKit's control size does not change with it), Linux its title plus padding; the web lays it out itself. Min-content, max-content and the intrinsic size are the same (the measure ignores the offer). CSS `width`/`height`/`min-*`/`max-*` and the flex item rules size the node's box as for any element — a native button in a column stretches, as a `<button>` flex item does; a hugging glass circle needs `width` or `align-self` — and the control fills the content box on both Apple platforms. The title is one line, truncated at its end, on every host (the web's face gets `white-space: nowrap; text-overflow: ellipsis`).
- *What the box may carry*: layout (margins, sizes, flex and grid item rows, position, `z-index`), `opacity`, transforms, `accent-color`, `visibility`. Refused on a native button (`lower-button-style-attr`), because the platform draws them and a browser would drop its native look under them: `background-*`, `border-*`, `border-radius`, `padding-*`, `box-shadow`, `backdrop-filter`, `color`, `font-*`, `text-*`, `line-height`, `letter-spacing`, the inner layout rows (`flex-direction`, `align-items`, `justify-content`, `gap`, `flex-wrap`), `press-scale`, `backgroundMaterial`, `glassGroup`. Put a group on the parent.

**D7. Colour: `accent-color` is the tint.** The fill of `filled`, the prominent styles and their web/Linux `fill` look; the title and image of the others (`baseBackgroundColor`/`baseForegroundColor`, `NSButton.bezelColor`/`contentTintColor`). It is inherited and resolves `auto` to the platform's accent (UIKit's `tintColor`, AppKit's `controlAccentColor`, CSS's `AccentColor`), with `light-dark()` pairs as LLP 1034 resolves them. Typography is the platform's.

**D8. The web.** A native button is `<button type="button" data-button-style="NAME">` (the attribute written for the default `bordered` too, and named the same whatever the node's other props, so the JS target's prop-name probe holds), mapped before the `Control` → `input` fallthrough (`element.rs:282-284`), with its children emitted as today: a `span` for the title, the symbol's masked `img`. The kernel's `accent-color` also goes out as `--exact-accent` on a native button. `index.html`:
- `button[data-button-style]` restores the browser's own button where `all: unset` removed it — `appearance: auto` and `background`, `border`, `border-radius`, `padding`, `font`, `color` reverted (D6 refuses all of these on the node, so nothing authored is lost) — and lays the face out as a row: `align-items: center; justify-content: center; gap: 0.25em; white-space: nowrap`; the title `span` truncates.
- The `text`, `soft`, `fill` and `glass` looks restyle it from `--exact-accent` (falling back to `AccentColor`), with the materials table's glass numbers written into the stylesheet for `glass`, so no capability is linked for it. The symbol's tint (`--exact-tint`, set on the `img`) follows the look: the accent, or white on `fill`.
- The JS target's agent maps `button[data-button-style]` to a `Control`.

**D9. Glass buttons join groups; the glass pass and the control share one mount point.** The four glass styles draw glass the platform merges in a `glassGroup` (§2). A native glass button registers with the isolation pass (LLP 1053.000.000 D4), and its glass body is the platform control: the iOS slot wraps the `UIButton` (the slot's hit test reaches it), macOS moves the `NSButton` into its isolation container. The control host mounts the control at the node's *control mount* — the slot's content view or the isolation container's when there is one, else the node — and the isolation pass moves only between those, so neither undoes the other (`ControlsIOS.swift:114` today re-adds a control under its node unconditionally).

**D10. The agent.** `tap` on a native button takes the ordinary tap path — hit test, occlusion, hidden and inert ancestors, then exactly one `press` — not the control shortcut that opens a select (`AgentIOS.swift:443`, `AgentMac.swift:412`); macOS keeps its real mouse events, which the `NSButton` receives. `type` on a native button is refused except Enter/Space, which press as on a custom button. `layout <node>` reports `native.control`: `{view: "UIButton"|"NSButton", style, drawn, title, symbol, enabled, size}`.

**D11. Where a native button may not be, in this slice.** Places that read a button's children as views or make their own native item from it: a menu invoker (`popovertarget`, `commandfor`), a row of a menu or a popover's actions, swipe-action content, a tab (role `tab` or inside a `tablist`), a macOS toolbar (inside `toolbarPlacement`), a `header`, and `href`. Contract refuses each where it can see it (the button's own attributes and its ancestors), `lower-button-context`, naming the custom button as the alternative.

**D12. Class-carried style: `buttonStyle` is styleable.** A `style` holds style rows only today, so a `PrimaryButton` class could carry `appearance` and `accent-color` but not `buttonStyle`. A prop row may say `"styleable": true` (read by `kernel/build.rs`, generated as `PropId::styleable`); only `buttonStyle` does. In a `style` it merges as rows do (the node's own wins); in `class=(c ? A : B)` both arms set it or neither (`lower-style-prop`), and each arm's literal is checked. `backgroundMaterial` and `glassGroup` stay unstyleable (LLP 1053.000.000 §7 holds).

**D13. Pooling.** A list row holding a native button is not pooled — destroyed and made, as rows holding checkboxes and selects are today (`control` is neither a reusable nor a fresh-leaf kind). Pooling rows around native controls is a separate change.

**D14. Docs.** LLP 1069.001 gains a line pointing here; LLP 1001's `button` text says Exact's UA sheet is `appearance: none`; `kernel/src/node.rs`'s note that a control's children are a select's options adds a button's face.
