## Summary

A `button` today is a `Pressable`: a box Exact lays out and paints, whose look is the author's. This lets an app ask for the platform's own button instead, per button, deliberately:

```
button appearance="auto" buttonStyle="glass" press=send aria-label="Send"
  image "symbol:send"
```

`appearance="auto"` (CSS's own switch between the platform's control and the author's box) makes it a native button: a `UIButton` with a `UIButton.Configuration` on iOS, an `NSButton` on macOS, the browser's own `<button>` on the web, a painted button on Linux. `buttonStyle` picks the platform's style from one table (`plain`, `bordered`, `bordered-prominent`, `glass`, `prominent-glass`, …). The button's `text` and `image "symbol:…"` children become its title and image, as a `select`'s options become its menu. Its size is the platform's. Everything else about a button stays: `press`, `disabled`, `aria-label`, the agent's `tap`. Without `appearance="auto"`, nothing changes.

## 1. What exists

- **`button`** lowers to a `Pressable` with fixed rows `display: flex`, `flex-direction: column` and the role `button` (`contract/lower/src/tags.rs:252`). It lays out its children; the Apple hosts handle touches, keys, focus and accessibility on the node view; the web host resets it (`index.html:27`, `button, input, textarea { all: unset; … }`).
- **`appearance`** (style bit 149, `auto | none`, default `auto`, not inherited) and **`accent-color`** (bit 148, inherited) came with LLP 1069.001. Only `Control` reads `appearance`; the kernel's default is `auto` on every node, so `auto` cannot by itself be the switch for buttons (D1).
- **`Control`** (LLP 1069.001 D2) is a measured leaf: its children are never laid out, the host builds the platform control in the node's box (`ControlsIOS.swift`, `ControlsMac.swift`), reports its natural size after each batch (`Kernel::set_intrinsic_size` through `presenter.onIntrinsic`), and reads a `select`'s `option` children as data (`exact_select_options`). The agent observes and activates controls (`controls.observation`, `controls.activate`). Linux paints them (`paint/control.rs`).
- **Native buttons already exist inside Exact** in three places: the iOS `select` (a `UIButton` with a pop-up menu), menu triggers (a transparent `UIButton` over a `popovertarget` button, `MenusIOS.swift`), and macOS toolbar items (`ToolbarMac.swift`, which reads a button's symbol and label as data, as the tab bar does in `SegmentsIOS.swift`).

## 2. Measured

A scratch UIKit app (iOS 27 simulator, iPhone 17 Pro) built each of the twelve `UIButton.Configuration` styles with the title "Send", a long title, the symbol `plus`, and both, and two rows of `glass()` buttons with an 8-point gap inside a `UIGlassContainerEffect`:

| Fact | Measured |
|---|---|
| Metrics at the default `medium` size | the same in all twelve styles: content insets 7/12/7/12, height 34.33 pt |
| Width with a title | the title's width + 24 ("Send" 63.33, "Send message now" 172) |
| Width, symbol only | 47 in the eight classic styles; 34.33 (a circle) in the four glass styles |
| Width, symbol and title | 90 for "Send" + `paperplane` in every style |
| `sizeThatFits(200×20)` | the intrinsic size, whatever is offered |
| Corners | `dynamic` in the classic styles, `capsule` in the glass ones |
| Glass buttons, gap 8, container spacing 8 / 24 | apart at rest / one merged shape (James's finding) |

So a native button's size depends on its title and image and is the platform's (LLP 1069.001 D3: "not a deviation"); it is reported after a batch as a `select`'s is.

## 3. Design

**D1. The switch: a literal `appearance="auto"` on a `button`.** CSS's `appearance` is the switch between "the platform draws the control" (`auto`) and "the author's box" (`none`). Browsers give `<button>` `appearance: auto` in their UA sheet; Exact's `button` has always been the author's box (the web host's reset says so). So:
- `button` gains a fixed row `appearance: none` beside its `display: flex`: Exact's UA sheet for `button`, declared, and what `layout` now reports for every ordinary button. Fixed rows come first, so a class's or the node's own `appearance` overrides it.
- A `button` whose `appearance`, from its class or its own attributes, is the literal `auto` is a native button. A bound `appearance` on a `button` is refused (`lower-button-appearance`): whether a button is native decides what the node is (D3), and that is fixed at compile time. An app that switches between a native and a custom button writes `when`.
- Whether Exact's bare `button` should one day default to native, with CSS's rule that an author background or border turns it back into a box, is left open (§5). Charlie asked for an opt-in.

**D2. `buttonStyle` and the `buttonStyles` table.** A native button's style is a host-policy prop, `buttonStyle` (a `str` prop, beside `backgroundMaterial` and `glassGroup`), whose names are one table in `schema.json`, `buttonStyles`, generated into the kernel as `materials` is (LLP 1053.000 D4): `[name, iOS UIButton.Configuration, macOS NSButton look, web and Linux look]`, kebab-case one-to-one with Apple's names, a `~` marking a platform that draws a stand-in (logged once). The names: `plain`, `gray`, `tinted`, `filled`, `borderless`, `bordered`, `bordered-tinted`, `bordered-prominent`, and iOS 26's `glass`, `prominent-glass`, `clear-glass`, `prominent-clear-glass`. The default, when a native button names none, is `bordered`: the browser's own `<button>` is a bordered one on every platform.
- Contract refuses a name not in the table, and `buttonStyle` on anything but a native button (`lower-button-style`): it means nothing elsewhere.
- *macOS*: `NSButton` with `bezelStyle` and `bezelColor` (the macOS 26 SDK has `NSBezelStyleGlass`): the plain styles are borderless, the gray and bordered ones `push`, the prominent and filled ones `push` with the accent as `bezelColor`, the glass ones `glass` (below macOS 26, `push`). Tinted and clear-glass are stand-ins.
- *Web and Linux*: a small set of looks the table names per style — the browser's own button (`bordered`, `gray`), a text button in the accent (`plain`, `borderless`), a soft accent fill (`tinted`, `bordered-tinted`), a solid accent fill with white text (`filled`, `bordered-prominent`), and the materials table's glass approximations (`glass`, `clear-glass`, and with an accent fill the prominent ones). Stated approximations, as the materials table's web column is.
- Below iOS 26 a glass style draws `bordered` (iOS) and logs once.

**D3. A native button is a `Control` of type `button`.** Contract lowers `button appearance="auto"` to `NodeType::Control` with the fixed prop `type = "button"` and the role `button`, as it lowers `select` (`controls.rs`). Being a `Control` gives it everything LLP 1069.001 built: a measured leaf whose children are not laid out, the host's control pipeline, its size report, the agent's observation and activation, Linux's painter. `ControlKind` gains `Button`, whose size before the first report is the iOS medium metrics' 64 × 34.
- *Events.* `press` works as on any node: the platform control's primary action (`UIControl.Event.primaryActionTriggered`; `NSButton`'s action; the web's `click`; Linux's press) dispatches the node's `press`. `disabled` is `isEnabled`. A `Control` dispatches no `change`/`input` for type `button`.
- *Accessibility* is the control's: the trait/role `button`, its label from `aria-label`, else its title; `.notEnabled` when disabled.
- *Focus and keys*: the platform's (UIKit's focus system, AppKit's key view loop and Return/Space, the browser's).
- *What a native button refuses*, for now, each with a message naming the custom-button alternative: `press-scale` (the platform has its own highlight), `popovertarget`/`commandfor` (the menu path lays a transparent button over the node; a native button would carry the menu itself — later), being a tab in a `tablist`, being a macOS toolbar item (`ToolbarMac` makes its own `NSToolbarItem`s from custom buttons), and `href` (a link is not a button).

**D4. Its children are its title and image.** A native button's children are data, as a `select`'s options are (LLP 1069.001 D2): at most one `text` (its title) and at most one `image` whose source is a `symbol:` role (its image, through the symbols table, LLP 1035.004). `when` and `match` may choose between them; `each` may not. Anything else — a `box`, a second `text`, a raster image — is refused (`lower-button-content`): a platform button draws a title and an image, not boxes. A button with neither is refused unless it has `aria-label` and a symbol (an icon button).
- *Order*: the image before the title is leading, after it trailing, as they would sit in the browser; `imagePlacement` and `NSButton.imagePosition` follow.
- *Typography and colour* inside the control are the platform's (LLP 1069.001 D6: "inside the control, the platform decides, as a browser does"), with one exception: `accent-color` is the tint — the fill of the filled and prominent styles, the title of the others (`UIButton.Configuration.baseBackgroundColor`/`baseForegroundColor`, `NSButton.bezelColor`/`contentTintColor`, CSS `accent-color` and the web look's fill). `color`, `font-*` and `text-*` on the button or its children are ignored by the native hosts and say so once.
- The hosts read the title and image through one ABI call per host, `exact_button_face` (Apple: JSON `{title, symbol, leading}`), as `exact_select_options` reads a select.

**D5. Its size is the platform's.** A measured leaf, sized by the control after a batch as a `select` is (`ControlHost.sync`): iOS `UIButton.intrinsicContentSize`, macOS `NSButton.intrinsicContentSize`, the web's browser layout, Linux's text measure plus the look's padding. CSS `width`/`height` override it; then the control is laid out in the content box (iOS: the button fills the box, its content centred). Dynamic Type and a title change re-report.

**D6. Glass buttons join glass groups.** The four glass styles are glass the platform merges inside a `glassGroup` (§2). They register with the glass-group pass (LLP 1053.000.000 D4), so a glass button whose path fades or clips is isolated like a glass material: the iOS slot wraps the `UIButton` as it wraps a material view; macOS moves the `NSButton` into its isolation container. The pass's "glass body" becomes the material view or the native glass button.

**D7. The web.** A native button is a `<button type="button">` whose children are emitted as today (a `span` for the title, the symbol image as a masked `img`). `index.html` gives back the browser's own button to `button[data-button-style]` (`all: revert`, then Exact's own layout declarations, which stay inline), and draws the other looks (D2) from `accent-color` and the materials' glass variables. The JS target emits the same element; its agent maps a `button[data-button-style]` to a `Control`.

**D8. Style classes may carry host-policy props.** A `style` holds style rows only today ("no `testId`, no handlers, no props"), so `class=PrimaryButton` could carry `appearance` and `accent-color` but not `buttonStyle` — nor `backgroundMaterial` or `glassGroup`. Props whose schema row says `"styleable": true` may now be in a `style`: `buttonStyle`, `backgroundMaterial`, `glassGroup`. They merge as rows do (the node's own attribute wins); in `class=(c ? A : B)` both sides must set such a prop or neither (`lower-style-prop`), since a prop has no `none` to fall back to. No other prop becomes styleable.

**D9. The agent.** `tap` on a native button activates the control (`sendActions(for: .primaryActionTriggered)`, `NSButton.performClick`, the web's `click`), which dispatches `press`; `layout <node>` reports `native.control` as for other controls: `{view: "UIButton", style, title, symbol, enabled, size}`.

**D10. Docs.** LLP 1069.001 gains a line pointing here; LLP 1001's `button` row says Exact's UA sheet is `appearance: none`.

## 4. Build

1. Schema: the `buttonStyles` table; the `buttonStyle` prop (`str`, `styleable`); `styleable` on `backgroundMaterial` and `glassGroup`. Kernel: `ControlKind::Button` and its default size; `generated::button_style(name)`.
2. Contract: `button`'s fixed `appearance: none`; the native lowering, content model and refusals (`controls.rs`); `buttonStyle`'s check; styleable props in `style` (`lib.rs` style lowering, `class.rs`). Tests beside LLP 1069.001's.
3. Apple: `exact_button_face`; `ControlKinds.kind` returns `button`; iOS builds `UIButton(configuration:)`, macOS `NSButton`; title, image, placement, accent, enabled, primary action → `presenter.press`; size reports; the agent's observation and activation; the glass-group pass's glass body.
4. Web: `element.rs` and `index.html`; the JS target's emit and agent. Linux: the painter and size report.
5. Tests: Contract (lowering, content model, refusals, styleable props); the Apple host's Rust (`exact_button_face`); XCTests on both platforms (the control, its configuration per style, title/image, enabled, press dispatch, size report, glass isolation); a fixture, `scripts/fixtures/native-buttons.contract`, every style with a title, a symbol and both, driven on iOS 26 and 27, macOS (window captures), the web and Linux.
6. A consumer: one Messages control made native (the inbox's compose button as `prominent-glass`, or a sheet's Cancel as `glass`), driven on iOS, macOS and the web.
7. The five checks, the iOS and macOS builds, both Swift suites.

## 5. Questions for review

1. D1: is a fixed `appearance: none` on `button` plus a *literal* `auto` the right switch, or should a native button be its own tag or a different attribute? Is refusing a bound `appearance` on a button right?
2. D3: lowering to `Control` reuses 1069.001's pipeline; what does it break that a `Pressable` had (focus ring, keyboard press, press feedback, chrome index entries, menus, swipe actions, the pool, collections)?
3. D4: is the content model (one text, one symbol image, `when`/`match`) right, and what of raster images and a subtitle?
4. D8: is "styleable" host-policy props the right fix for classes, and is the conditional-class rule enough?
5. The default (`bordered`), the web looks, and macOS's mapping: anything wrong or missing?
6. Anything in this that conflicts with LLP 1075.003's open rulings on native control?
