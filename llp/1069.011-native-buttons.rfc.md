## Summary

A `button` today is a `Pressable`: a box Exact lays out and paints, whose look is the author's. This lets an app ask for the platform's own button instead, per button, deliberately:

```
button appearance="auto" buttonStyle="glass" press=send aria-label="Send"
  image "symbol:send"
```

`appearance="auto"` (CSS's switch between the platform's control and the author's box) makes it a native button: `UIButton` with a `UIButton.Configuration` on iOS, `NSButton` on macOS, the browser's own `<button>` on the web, a painted button on Linux. `buttonStyle` picks the style from one table. Its `text` and `image "symbol:…"` children are its title and image. Its size is the platform's. `press`, `disabled`, `aria-label`, focus, keys and the agent's `tap` work as on any button. Without `appearance="auto"` nothing changes.

## 1. What exists

- **`button`** lowers to a `Pressable` with fixed rows `display: flex`, `flex-direction: column` and the role `button` (`tags.rs:252`). The Apple node view presses on touch-up (`NodeViewIOS.swift:1314-1352`), is the first responder for keys and Enter/Space (`247`, `289-297`), draws Exact's focus ring (`276-287`), and is the accessibility element (`997-1005`). The web host resets it (`index.html:27`, `all: unset`).
- **`appearance`** (bit 149, `auto | none`, default `auto` on every node, not inherited) and **`accent-color`** (bit 148, inherited) came with LLP 1069.001; only `Control` reads them.
- **`Control`** (LLP 1069.001 D2) is a measured leaf (`node.rs:94-98`, children not laid out, `133-136`). The host builds the platform control in the node's box (`ControlsIOS.swift:96-143`, `ControlsMac.swift`), reports its natural size after each batch (`presenter.onIntrinsic` → `Kernel::set_intrinsic_size`), and reads a `select`'s options through the kernel (`select_choices`, `exact_select_options`). Several paths assume "not a checkbox or switch" means "a select": `ControlKind::of` and `ControlKinds.kind` fall through to checkbox; the index lists `type:checkbox|select|range|date|time|datetime-local` (`ChromeIndex.swift:14-17`); iOS identifies a select by `is UIButton` (`ValueControlsIOS.swift`); Linux toggles any other control as a checkbox (`presenter/control.rs:37-62`).

## 3. Design

**D1. The switch: an `appearance` that is the literal `auto` after class merging.** CSS's `appearance` switches between the platform's control (`auto`) and the author's box (`none`). Exact's `button` has always been the author's box, so `button` gains a fixed row `appearance: none` (declared: Exact's UA sheet for `button`; `layout` now reports it on every ordinary button). The effective `appearance` — the fixed row, then the class's, then the node's own, last wins — decides:
- the string literal `auto` (one class, both arms of a class choice, or the node's own): a native button;
- absent or `none`: an ordinary `Pressable`, as today;
- anything bound, including the ternary a class choice synthesizes when only one arm sets `appearance`: refused, `lower-button-appearance`. Being native decides what the node is; an app that switches writes `when`.

**D2. `buttonStyle` and the `buttonStyles` table.** A native button's style is a host-policy prop, `buttonStyle` (prop 217, `str`), named in one schema table, `buttonStyles`, generated as `materials` is: `[name, iOS 26+ UIButton.Configuration, the factory before iOS 26, macOS look, web/Linux look]`. Names, kebab-case one-to-one with Apple's: `plain`, `gray`, `tinted`, `filled`, `borderless`, `bordered`, `bordered-tinted`, `bordered-prominent`, `glass`, `prominent-glass`, `clear-glass`, `prominent-clear-glass`. Absent, a native button is `bordered` (Exact's default: a browser's own button is a bordered one).
- *iOS*: the named configuration; before iOS 26 the glass styles are stand-ins, `bordered` and (prominent) `borderedProminent`.
- *macOS*: one look per row — `borderless` (plain, borderless: `isBordered = false`, accent `contentTintColor`), `push` (gray, bordered), `push-accent` (filled, bordered-prominent: accent `bezelColor`), `glass` (`NSBezelStyleGlass` on macOS 26, else `push`), `glass-accent` (prominent-glass). Stand-ins, marked `~`: the tinted styles draw `push`, the clear-glass ones `glass`/`glass-accent`. The build measures each and may add a `~`.
- *Web and Linux*: six looks — `ua` (the browser's own button: bordered, gray), `text` (plain, borderless), `soft` (tinted, bordered-tinted), `fill` (filled, bordered-prominent), `glass` (glass, clear-glass), `glass-fill` (the prominent glass styles). Stated approximations.
- Stand-ins are silent, as LLP 1053.000's accepted materials policy is; the agent reports the requested and the drawn style (D10). Contract refuses a literal name not in the table and `buttonStyle` on anything but a native button (`lower-button-style`); a bound name must be a choice among literal names, each checked. A host given a name not in the table (a producer below Contract) draws `bordered` and logs once.

**D3. A native button is a `Control` of type `button`, named first wherever a control's kind is chosen.** Contract lowers it to `NodeType::Control` with fixed props `type = "button"` and role `button` and fixed rows `appearance: auto`, `display: flex`, `box-sizing: border-box` (D6); no `flex-direction: column`. An authored `type` other than the literal `"button"` is refused. The lowering, grammar and refusals live in `contract/lower/src/controls.rs` (`lib.rs` is at the line cap).
- *Kernel*: `ControlKind::Button`, matched before the switch/checkbox fallthrough; frame one's size before a host reports is §2's medium metrics rounded, 64 × 34 (the web never uses kernel sizes). *Runner*: `control_payload`'s catch-all already makes `input`/`change` on a button `InvalidEvent`.
- *Apple*: `ControlKinds.kind` returns `button` for `type == "button"` first; `type:button` joins `ControlKinds.indexed` and `ChromeIndex`; a native button's code lives in `IOS/NativeButtonsIOS.swift` and `Mac/NativeButtonsMac.swift`; every select-only path tests the node's kind — iOS configuration, typing, observation and `unopened`; macOS `activate` (`ControlsMac.swift:123`) and `observation` (`136`).
- *Linux*: a button `Control` is pressed (`dispatch_press`, never `toggle_control`), painted by its look and not its children (the paint walk returns before them), refused by `type`, and sized by `size_controls` as its title plus §2's insets until the build measures the looks. Space and Enter keep pressing it through the existing role path (`typing.rs:201-205`).

**D4. One activation routine; one owner each for touch, keys, focus and VoiceOver.**
- *Activation*: the platform control takes the touch (it fills the node's box, D6). Its primary action (`UIControl.Event.primaryActionTriggered`, `NSButton`'s action) runs the node's own activation, factored out of the custom button's touch-up and shared with the agent: resolve the target as `activationTarget` does (the node's own `press`, else the nearest ancestor's, refused at a disabled ancestor); focus the node unless a `retainFocus` ancestor keeps the editor (iOS `contextRetainsFocus`, macOS its walk), else end editing (`endEditing` / `makeFirstResponder(nil)`); dispatch `press` once; `finishPointerPress`. Nothing sets `pressed`, so there is no press feedback.
- *Keys and focus*: the node stays the logical focus owner — `canBecomeFirstResponder` and `tabbable` include a native button, so Tab/Shift-Tab, `tabIndex`, `autofocus`, `focus()`/`blur()`, focus events, `retainFocus`, collection pins and Exact's ring are unchanged, and Enter/Space press through the node's existing path. The platform control is never a focus candidate: `NSButton.refusesFirstResponder`; UIKit's `FocusSearch` skips it as a foreign view.
- *VoiceOver*: while a native button is installed the platform control is the only accessibility element, on both platforms, whatever the node's role: labelled with `aria-label` or the face's title, `.notEnabled` when disabled, and carrying the node's selected and expanded state (`accessibilityTraits`/`accessibilityExpandedStatus`; AppKit's equivalents) without becoming a value control. The node is not an element: the `kind == "button"` branches (`NodeViewIOS.swift:997-1005`, `NodeViewMac.swift:327-339`) and `Accessibility.swift`'s role-`button` labelling (`71-76`) skip it, and the node's accessible name reads the face.

**D5. The children are the face: data, never views.** A native button's title and image come from the kernel, `Kernel::button_face(view) -> ButtonFace { title, symbol, leading }`, walking the live tree as `select_choices` does, so a `when` updates it; Apple reads it through `exact_button_face` in `abi/commands.rs` beside `exact_select_options`; Linux directly. Apple's `paragraph.rs` skips a native button's children in `create` and `update`, text and image both (no mirrors, no views); Linux does not paint them; the web emits them (D8).
- *Grammar*, walking the children as `run()` does (`when` and `match` branches; `each` refused): every reachable face has at most one `text` and at most one `image`, and at least one of them; a face that can be symbol-only requires `aria-label`. The `text` is a string, literal or bound, whitespace-collapsed as an option label is; an `image`'s source is a literal `symbol:` role or a choice among literal roles, each checked. The children carry nothing but `testId`, and nothing below a native button has a handler. `lower-button-content`, before the generic empty-button refusal.
- *Order*: an image before the title is leading, after it trailing (in the inline direction); `imagePlacement` and `NSButton.imagePosition` follow.

**D6. The box: the platform draws the chrome; the author places and sizes it.** A native button is `box-sizing: border-box` on every host (a fixed row; an authored one is refused), and the platform's chrome is inside its box: Apple's control fills the node's bounds, the web's restored padding and border sit inside the authored width, Linux's look's insets inside its box. So `width=100 height=40` is the same 100 × 40 everywhere, and with no size the box is the platform's natural size (Apple and Linux report it after a batch and Apple on a content-size-category change; the web lays it out). The measure ignores the offer, so min-content, max-content and the intrinsic size are one. As a flex item it stretches as a `<button>` does; a hugging glass circle needs `width` or `align-self`. The title is one line, truncated at its end, everywhere.
- *What a native button may carry*, the whole rule (anything else is refused, `lower-button-style-attr`): margins; `width`, `height`, `min-*`, `max-*`, `aspect-ratio`; the flex and grid item rows (`flex`, `flex-grow`, `flex-shrink`, `flex-basis`, `align-self`, `justify-self`, `order`, grid placement); `position`, the insets and `z-index`; `display` as its own `flex` or `none` (a literal or a choice between them); `opacity`, `visibility`; `transform`, `translate`, `scale`, `rotate`, `transform-origin`; `clip-path` (an isolation reason, LLP 1053.000.000 D4); `accent-color`; `cursor`; `transition` whose properties are among `opacity` and the transform rows; `animation` and `exit-animation` whose keyframes, looked up by name in the file, touch only those. Refused, among the rest: background, border, padding, shadow, `filter`, `backdrop-filter`, `overflow`, colour, typography, the inner layout rows and `direction` (the face's order is its children's), `pointer-events` (the platform hit-tests its own control), `press-scale`, `backgroundMaterial`, `glassGroup`. Handlers: `press`, `focus`, `blur`, `key`, `hover`. This departs from LLP 1069.001 D6 (whose controls' boxes take padding, border, background and font); LLP 1001 records it.
- *Inherited typography* reaches only the web's native face, so the web resets it there (`letter-spacing`, `word-spacing`, `text-transform`, `text-shadow`, `font-variant-*`) and Linux measures the face without it; Apple's title is untransformed.

**D7. Colour: `accent-color` is the tint.** It is UIKit's `tintColor` and AppKit's `bezelColor`/`contentTintColor`, and the platform decides what it colours; the web and Linux copy iOS. Measured on iOS 27 with an explicit accent (§8): the fill of `filled`, the prominent styles and the `fill`/`glass-fill` looks; the title and image of `plain`, `borderless`, `tinted` and `bordered-tinted`; `gray`, `bordered`, `glass` and `clear-glass` draw their title and image in the label colour whatever the accent. It is inherited; `auto` is the platform's accent (UIKit's `tintColor`, AppKit's `controlAccentColor`, CSS's `AccentColor`); `light-dark()` pairs resolve as LLP 1034 says. Typography is the platform's.

**D8. The web.** A native button is `<button type="button" data-button-style="NAME">` — an explicit `props_for` arm writing that one hyphenated name, the default `bordered` written only on a node of type `button` so the JS target's prop-name probe (a bare `Control`) still sees the attribute appear — mapped before the `Control` → `input` fallthrough (`element.rs:282-284`), with its children emitted as today. `index.html`, with a comment citing the schema rows it copies:
- `button[data-button-style]` restores the browser's own button where `all: unset` removed it (`appearance: auto`; `background`, `border`, `border-radius`, `padding`, `font`, `color` reverted; `box-sizing: border-box`), resets the inherited typography (D6), and lays the face out as a row (`align-items: center; justify-content: center; gap: 0.25em; white-space: nowrap`), the title `span` truncating.
- The `text`, `soft`, `fill`, `glass` and `glass-fill` looks restyle it from `--exact-accent`, an inherited custom property the web writes wherever `accent-color` is declared, static or bound (`auto` written as `AccentColor`), registered with `AccentColor` as its initial value. The glass looks write the materials table's `glass` and `glass-clear` numbers into the stylesheet (no capability linked). The symbol's `--exact-tint`, set on its `img` by the look, is the accent, or white on `fill` and `glass-fill`.
- The JS target's agent maps `button[data-button-style]` to a `Control`. `glue.js` and the JS target's `emit.rs` (both at the line cap) are not touched: the element and its attributes come from `element.rs` through `template::parts`.

**D9. Glass buttons join groups; the glass pass and the control host share one mount point and one lifetime.** The four glass styles draw glass the platform merges in a `glassGroup` (§2). A native glass button registers with the isolation pass (LLP 1053.000.000 D4), and its glass body is the platform control. The control host mounts the control at the node's *control mount* — the iOS slot's content view or the macOS isolation container's when there is one, else the node — in both of its re-add sites (`ControlsIOS.swift:114`, `ControlsMac.swift:73`), and frames it in the node's coordinates (the slot and the container fill the node's bounds). The isolation pass handles a body that is a control as one that is a material, in both directions: iOS, the slot wraps the `UIButton` and, when the button stops being glass, gives it back to the node in the same batch; macOS, `reconcileGlass` and `releaseGlassIsolation` move the `NSButton` into and out of the container. A leaving native button (its own exit, or an ancestor's) keeps its control and last configuration until its exit ends; only its identity for actions and the agent is retired at once.

**D10. The agent.** `tap` on a native button takes the ordinary tap path — hit test, occlusion, hidden and inert ancestors — and then D4's activation routine, once; it never also sends the control's action. macOS keeps its real mouse events, which the `NSButton` receives and turns into D4's routine. `type` on a native button is refused except Enter/Space. `layout <node>` reports `native.control`: `{view: "UIButton"|"NSButton", style, drawn, title, symbol, enabled, size}`.

**D11. Where a native button may not be, in this slice.** Places that read a button's children as views, make their own native item from it, or take its input another way. Contract refuses each where it can see it (the button's attributes and its ancestors), `lower-button-context`, naming the custom button as the alternative: a menu invoker (`popovertarget`, `commandfor`) or a row of a menu or popover's actions; swipe-action content or a swipe row's body; a tab (role `tab`, or inside a `tablist`); inside `toolbarPlacement`; a `header`; anything inside a `canvas`, and `action`; `aria-keyshortcuts`; and `href`.

**D12. Class-carried style: `buttonStyle` is styleable.** A prop row may say `"styleable": true` (read by `kernel/build.rs`, generated as `PropId::styleable`); only `buttonStyle` does. In a `style` it merges as rows do (the node's own wins); in `class=(c ? A : B)` both arms set it or neither (`lower-style-prop`), each arm's literal checked. `backgroundMaterial` and `glassGroup` stay unstyleable (LLP 1053.000.000 §7 holds).

**D13. Pooling.** A list row holding a native button is not pooled, as rows holding checkboxes and selects are not today.

**D14. Docs.** LLP 1069.001 gains a line pointing here; LLP 1001 records Exact's UA `appearance: none` for `button`, a native button's `border-box` and its refusals (D6), and the typography reset; `kernel/src/node.rs`'s note on a control's children adds a button's face.

## 7. As built (2026-10-02)

Built as §3 says, on every host. What running it found:

- **iOS 27 (simulator).** The fixture (`scripts/fixtures/native-buttons.contract`) draws all twelve styles as UIKit's own buttons; a symbol-only glass button is a circle; an image before the title leads, after it trails; `width` and a stretched flex item fill the box; `accent-color` tints; a disabled button dims and does not press. The agent's `tap` presses once through the ordinary path, an ancestor's handler included. In a `glassGroup` the glass buttons merge (spacing 24 over an 8-point gap; at 12 they stay apart, the platform's threshold), and one fading is isolated (`isolated: ["opacity"]`) and fades.
- **macOS.** `ExactMac` links with `sdk 14.0` in its build version (the iOS app with `sdk 27.0`), and AppKit keys its macOS 26 design on that number, so every Exact control on macOS draws in the earlier design, native buttons included. A probe linked both ways shows it (one window, made key): linked with the macOS 27 SDK, a push button is the new capsule, the glass bezel draws glass, and a `bezelColor` tints both; linked with `-platform_version macos 14.0 14.0`, the push button is the old bezel, the accent tints it in a key window (in an inactive one AppKit draws it white), and the glass bezel draws no bezel at all — bare text. So a glass look draws glass only when the app's main executable was linked with SDK 26 or later (`NativeButtonMac.glassDrawn`, read from its `LC_BUILD_VERSION`), and a push button otherwise, as before macOS 26. The link is the build's choice, not this feature's (`QUEUE.md`).
