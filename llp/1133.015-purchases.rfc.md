## Summary

`@exact/purchases` sells digital goods through the platform's store
(in-app products and subscriptions) on iOS, macOS and Android first, with
every other target of LLP 1133 D8 a visible `later` or `absent`.
`@exact/store-review` asks the store to show its rating prompt. Both are
extensions, written in one RFC because they ship together (LLP 1133.000
§3.7).

Tier 1 is the web's: the Digital Goods API's `getDetails`,
`listPurchases`, `consume` and its `ItemDetails` and `PurchaseDetails`,
with the purchase itself the send Payment Request's `show()` performs in
that API, and the words Digital Goods 1.0 had (`acknowledge`,
`acknowledged`, `purchaseState`, `purchaseTime`, `willAutoRenew`) where a
native store needs them. One shared word, `unfinishedPurchases`, is the
store's queue of what it has delivered and the app has not yet finished,
kept apart from `listPurchases`, what the person owns:

```
use getDetails, listPurchases, purchase, restorePurchases, purchasesStatus,
  PurchaseDetails from "@exact/purchases"
use requestReview from "@exact/store-review"

resource status = purchasesStatus()
resource plans = getDetails(itemIds=["plus.yearly", "plus.monthly"])
resource owned = listPurchases()
mutation bought as shape PurchaseDetails then thanked

action upgrade(itemId: string)
  send bought = purchase(itemId=itemId)
```

```ts
import { unfinishedPurchases } from "@exact/purchases";

// The one path every transaction the app must finish takes, however it arrived (D5).
for (const p of await unfinishedPurchases()) {
  if (p.purchaseState !== "purchased") continue;    // pending: nothing yet
  if (await alreadyDelivered(p.purchaseToken)) {    // idempotent, by the token
    await finish(p);
    continue;
  }
  await deliver(p);           // credit a tip, or post to the app's server (D8)
  await finish(p);            // consume a consumable, acknowledge the rest
}
```

Tier 2 reaches StoreKit 2's subscription status, offers, offer codes,
refunds, family sharing and the signed transaction, and Play Billing's
base plans, offer tokens, replacement modes and the purchase's signed
JSON. Tier 3 hands the app's Kotlin the `BillingClient.Builder` and each
`BillingFlowParams.Builder`, and its Swift each purchase's option set.

The web has the names and not the capability: a browser tab has no store.
The Digital Goods API answers only inside a store's container (a Trusted
Web Activity for Google Play, a Microsoft Store PWA in Edge), which an
exact2 web build is not, so the web cell is `absent` (D20).

The consumer is Weatherlight (§10): Weatherlight+, a subscription that
shows the sixteen-day forecast, a tip, and the rating prompt after the
person has come back to it on several days.

## 0. What is new here

The first wave's modules answer a value the device has now. A store is a
third party that holds a record of money on its servers, delivers it
whether or not the app is running, and insists that the app say when it
has delivered the goods. Writing the module out shows seven things the
earlier RFCs did not settle, each answered below and each a question in
§13 where it is a choice:

1. **A queue the store owns, not a value and not an event.** A store
   delivers each transaction until the app finishes it: StoreKit for as
   long as it is unfinished, Play for three days before it refunds. That
   is at-least-once delivery with an acknowledgement, which neither LLP
   1133 D6 rule 7's coalescing value nor LLP 1133.004 D6's
   delivered-once event describes. The module exposes it as a fact of its
   own (`unfinishedPurchases`), apart from what the person owns
   (`listPurchases`), and the app's processing is idempotent by the
   purchase's token (D3, D5).
2. **Work that must run from launch, before the app asks.** Apple:
   "Create a Task to iterate through the transactions from the listener
   as soon as your app launches." A package's implementation is made at
   its first call today; this one starts when the module loads, after
   first pixel, and nothing is lost in the gap because the store keeps
   every unfinished transaction (D6).
3. **A fact that goes stale at a known time.** A subscription's
   entitlement ends at its expiration date with no event from the store.
   An answer names when it goes stale, and the runner asks again then, on
   the session clock (D7).
4. **A first frame that should already know.** A subscriber's first frame
   should not offer the upgrade they bought. The entitlement fact keeps
   its last answer, as a TypeScript source does (LLP 1027 D4), and the
   store corrects it once the module answers (D4).
5. **A proof that leaves the device.** StoreKit verifies a transaction on
   the device; Google recommends a server for every verification. The
   module gives data code what each store's server API takes, and binds a
   purchase to the app's account, without ever treating the token as a
   secret (D8).
6. **Money in the agent's hands.** A drive must never spend the person's
   money, and an agent acting through the app's tools must never start a
   purchase. Under the agent no store is reached; a purchase is refused to
   tools and wakes in every case, and is never delegable (D14, §9).
7. **A store's distribution decides whether anything works.** In-app
   purchases work only in an app the store can identify: StoreKit's
   sandbox in a development-signed or TestFlight build, production only
   from the App Store; Play Billing only for a package uploaded to a Play
   track. A Developer ID Mac build has no In-App Purchase at all (D21).

## 1. Tier 1

### D1 — The Digital Goods names, Payment Request's flow, and the words of Digital Goods 1.0

The Digital Goods API is the web's interface to an app store's billing:
`getDigitalGoodsService(serviceProvider)` answers a `DigitalGoodsService`
with `getDetails(itemIds)`, `listPurchases()`, `listPurchaseHistory()` and
`consume(purchaseToken)`, and the purchase itself is a Payment Request
whose method is the store
([Digital Goods](https://wicg.github.io/digital-goods/); the
[explainer](https://github.com/WICG/digital-goods/blob/main/explainer.md):
"The purchase flow itself uses the Payment Request API", with the item
named in the method's `data`). Its version 1.0 also had
`acknowledge(purchaseToken, purchaseType)` and, on `PurchaseDetails`,
`acknowledged`, `purchaseState`, `purchaseTime` and `willAutoRenew`;
version 2.0 removed them and moved acknowledgement to the developer's
server ([DGAPI 2.0 migration](https://chromeos.dev/en/posts/dgapi-2-migration):
"Purchase acknowledgement must be made instead on the backend using
Google Play Developer API's acknowledge methods").

`@exact/purchases` declares:

| Name | Kind | Meaning | Contract | Data code |
|---|---|---|---|---|
| `getDetails(itemIds)` | live source; a fact | the store's description and price of each item it knows, re-answered when the storefront changes | `resource p = getDetails(itemIds=[…])` | `await getDetails({ itemIds })` |
| `listPurchases()` | live source; a fact; kept (D4) | what the store says this account holds now: its entitlements, and consumables not yet consumed (D3) | `resource o = listPurchases()` | `await listPurchases()` |
| `unfinishedPurchases()` | live source; a fact; a shared word | the store's queue: every transaction it has delivered that the app has not acknowledged or consumed, entitled or not (D5) | `resource u = unfinishedPurchases()` | `await unfinishedPurchases()` |
| `purchase(itemId, quantity, accountToken)` | send; a request (the store's sheet) | Payment Request's `show()` for the store's method: the store's purchase sheet, answering the purchase | `send b = purchase(itemId="…")` | `await purchase({ itemId })` |
| `consume(purchaseToken)` | send; answers nothing | the app has delivered a consumable; it may be bought again | a statement | `await consume({ purchaseToken })` |
| `acknowledge(purchaseToken)` | send; answers nothing; a shared word (Digital Goods 1.0's) | the app has delivered anything else | a statement | `await acknowledge({ purchaseToken })` |
| `restorePurchases()` | send; a request on Apple | ask the store to bring this account's purchases to this device; answers `listPurchases`'s new value | `send r = restorePurchases()` | `await restorePurchases()` |
| `purchasesStatus()` | live source; a fact; `sync` | `available`, `store`, `canMakePayments`, `storefront` | `resource s = purchasesStatus()` | `await purchasesStatus()` |

**Values.**

| Shape | Fields |
|---|---|
| `ItemDetails` | Digital Goods': `itemId`; `title`; `price` (`PaymentCurrencyAmount`: `currency`, an ISO 4217 code, and `value`, a decimal string); `type` (`product` or `subscription`); `description`; `iconURLs` (empty: neither store gives one); `subscriptionPeriod`, `freeTrialPeriod`, `introductoryPricePeriod` (ISO 8601 durations); `introductoryPrice`; `introductoryPriceCycles`. Shared: `displayPrice`, the store's own formatted price (Apple's [`displayPrice`](https://developer.apple.com/documentation/storekit/product/displayprice), Play's `formattedPrice`); `familyShareable` |
| `PurchaseDetails` | Digital Goods': `itemId`, `purchaseToken` (empty in Apple's `pending` answer, which carries no transaction until the store approves, [`PurchaseResult.pending`](https://developer.apple.com/documentation/storekit/product/purchaseresult/pending)). Digital Goods 1.0's: `purchaseState` (`purchased` or `pending`), `purchaseTime` (ms since the epoch), `acknowledged`, `willAutoRenew` (`option<bool>`, subscriptions only). Shared: `quantity`; `expirationTime` (`option<number>`, ms; D7); `apple`, `android` (D10) |
| `PurchasesStatus` | `available`; `store` (`app-store`, `google-play`, `none`), which server API verifies (D8); `canMakePayments` (Apple's [`AppStore.canMakePayments`](https://developer.apple.com/documentation/storekit/appstore/canmakepayments), false under parental restrictions; Play's billing service reachable for this account); `storefront` (`option<string>`, the store's country as an ISO 3166-1 alpha-2 code, the web's region subtag; Apple's three-letter code is `apple.storefront`) |

**`purchaseToken`** is the string the app's server gives its store's
server API to verify the purchase (D8): on Play the
[`purchaseToken`](https://developer.android.com/reference/com/android/billingclient/api/Purchase),
"globally unique, so you can safely use this value as a primary key"
([security](https://developer.android.com/google/play/billing/security));
on Apple the transaction's `id` as a decimal string, which
[Get Transaction Info](https://developer.apple.com/documentation/appstoreserverapi/get-transaction-info)
takes "for any transaction identifier". It is also the key `acknowledge`
and `consume` take and the app's processing records (D5).

**Errors.** In Contract, `failure(…).code`; in TypeScript and Rust a
rejection `{code, message}`, as LLP 1133.002 D1 does. Payment Request's
names where it has one, and the stores' shared cases otherwise:

| Code | Apple ([`StoreKitError`](https://developer.apple.com/documentation/storekit/storekiterror), [`Product.PurchaseError`](https://developer.apple.com/documentation/storekit/product/purchaseerror)) | Android ([`BillingResponseCode`](https://developer.android.com/reference/com/android/billingclient/api/BillingClient.BillingResponseCode)) |
|---|---|---|
| `AbortError` (Payment Request's, the person closed the sheet) | `PurchaseResult.userCancelled`, `StoreKitError.userCancelled` | `USER_CANCELED` |
| `NotSupportedError` | `StoreKitError.unsupported`; a target without the module | `FEATURE_NOT_SUPPORTED`, `BILLING_UNAVAILABLE` |
| `NotAllowedError` (message `person-required`, D14) | a tool, wake or headless origin; the app not in the foreground | the same |
| `ITEM_UNAVAILABLE` | `Product.PurchaseError.productUnavailable`, `StoreKitError.notAvailableInStorefront`; an id `getDetails` did not answer | `ITEM_UNAVAILABLE` |
| `ALREADY_OWNED` | — (StoreKit answers the existing transaction) | `ITEM_ALREADY_OWNED` |
| `NOT_OWNED` | `consume` or `acknowledge` of a token this account does not hold | `ITEM_NOT_OWNED` |
| `PURCHASE_NOT_ALLOWED` | `Product.PurchaseError.purchaseNotAllowed` | — (`canMakePayments` false) |
| `NETWORK` | `StoreKitError.networkError` | `NETWORK_ERROR`, `SERVICE_UNAVAILABLE` |
| `VERIFICATION_FAILED` | `VerificationResult.unverified` (D8) | — |
| `OperationError` | `StoreKitError.systemError`, `.unknown`; an offer error (`ineligibleForOffer`, `invalidOfferSignature`, …) with the platform's case in `apple.code` | `ERROR`, `DEVELOPER_ERROR`, `SERVICE_DISCONNECTED` after the library's reconnection, with the platform's code in `android.code` |

A pending purchase is not an error: `purchase` answers it with
`purchaseState` `pending` (D3).

**Declared deviations,** each because the web's form does not fit a
module that answers:

- **No service object.** `getDigitalGoodsService` exists to choose a
  store; a native target has one. `purchasesStatus().available` is the
  feature test, as `"getDigitalGoodsService" in window` is the web's.
- **`purchase` is a send, not `new PaymentRequest(…).show()`.** Payment
  Request's constructor takes method data, details and options for a
  sheet the page could also show for a card; the store's sheet takes an
  item. The send keeps what the Digital Goods flow uses: the item, its
  quantity, and an answer that is the purchase.
- **The answer is `PurchaseDetails`,** not Payment Request's
  `PaymentResponse` with the token in `details`, and there is no
  `complete()`: the store's sheet closes itself.
- **`acknowledge` and Digital Goods 1.0's fields are back,** because a
  native app may have no server, and Apple finishes a transaction only on
  the device ([`finish()`](https://developer.apple.com/documentation/storekit/transaction/finish()):
  "Call finish() to complete a transaction after you deliver the purchased
  content or enable the purchased service").
- **`listPurchases` is live,** and **`unfinishedPurchases` is a shared
  word** for the queue both stores keep, which Digital Goods 2.0 left to
  the developer's server (D3, D5).
- **`listPurchaseHistory` is not a name.** Play Billing removed its
  history query in version 8.0 ([release notes](https://developer.android.com/google/play/billing/release-notes)),
  so it has no shared meaning; Apple's [`Transaction.all`](https://developer.apple.com/documentation/storekit/transaction/all)
  is a tier 2 source (D10).
- **`restorePurchases` and `purchasesStatus` are shared words:** both
  stores have them; the web's container has neither.
- **Errors** are Payment Request's `AbortError` and `NotSupportedError`
  and domain codes for the stores' cases, where the web's single
  `OperationError` would hide the difference between a sold-out item and
  a network failure, which a hand-built app shows differently.
- **TypeScript gets Promise form;** a Contract `send` of an answerless
  name is a statement (LLP 1133.004 D5).

## 2. Purchases as facts

### D3 — Two facts: what the person holds, and what the store has delivered

A store answers two questions that look alike and are not: what this
account is entitled to now, and which transactions it has handed the app
that the app has not finished. A subscription bought, left unacknowledged
because delivery failed, and expired while the app was closed is in the
second and not the first; gating a screen on the second would grant it
indefinitely. So they are two sources.

**`listPurchases()`, what the account holds now:**

| | Apple | Android |
|---|---|---|
| entitlements | [`Transaction.currentEntitlements`](https://developer.apple.com/documentation/storekit/transaction/currententitlements): each non-consumable; the latest transaction of each auto-renewable subscription that is `subscribed` or `inGracePeriod`; each non-renewing subscription; never a refunded or revoked one | [`queryPurchasesAsync`](https://developer.android.com/google/play/billing/integrate) for `INAPP` and `SUBS` in state `PURCHASED`: owned products and subscriptions, including one "in the grace period" or canceled until its period ends, not one on account hold ([subscriptions](https://developer.android.com/google/play/billing/lifecycle/subscriptions)) |
| consumables not yet consumed | the verified, unrevoked consumables in [`Transaction.unfinished`](https://developer.apple.com/documentation/storekit/transaction/unfinished) (`currentEntitlements` never lists a consumable) | the same query: Play does not know which products are consumable, and an unconsumed one is owned until `consume` |
| pending | never listed | never listed: "grant entitlement only when the state is `PURCHASED`" |

Each row carries `acknowledged`, so a screen can say "Finishing your
purchase…" for one the app has not yet delivered.

**`unfinishedPurchases()`, the store's queue** (D5): every verified
transaction the store has delivered and the app has neither acknowledged
nor consumed, whether or not it still entitles anyone: Apple's
`Transaction.unfinished` (an expired subscription's last renewal, a
superseded one, a consumable); Play's query results with
`isAcknowledged()` false, `PENDING` ones included with `purchaseState`
`pending`. Delivery reads this source and nothing else; a screen never
gates on it.

**A non-renewing subscription** stays in `listPurchases` for as long as
StoreKit lists it, which is indefinitely: Apple leaves its period to the
app (it has no expiration date and its product no subscription period).
`expirationTime` is `none`; an app selling one computes its end from
`purchaseTime`, as a hand-built app does. Play has no such product type.

**They are re-answered** (their topics announced, LLP 1016.002) when:

- the store reports a change: Apple's
  [`Transaction.updates`](https://developer.apple.com/documentation/storekit/transaction/updates)
  (a renewal, a refund, an Ask to Buy approval, a purchase on another
  device, a family member's purchase),
  [`Product.SubscriptionInfo.Status.updates`](https://developer.apple.com/documentation/storekit/product/subscriptioninfo/status/updates);
  Play's `PurchasesUpdatedListener`;
- the app returns to the foreground: Play asks for a fresh query "in your
  app's `onResume()` method to handle purchases that have transitioned to
  the `PURCHASED` state while your app was not running"
  ([integrate](https://developer.android.com/google/play/billing/integrate)),
  and the Apple implementation reads `currentEntitlements` and
  `unfinished` again too, since the App Store account may have changed;
- the storefront changes ([`Storefront.updates`](https://developer.apple.com/documentation/storekit/storefront/updates));
- the app's own `purchase`, `acknowledge`, `consume` or `restorePurchases`
  completes;
- on Apple, an `expirationTime` in `listPurchases` passes (D7).

**What they can be trusted for.** On Apple they list only transactions
StoreKit verified (D8); an unverified one is in neither, and is listed in
`apple.unverified` on the status for an app that wants to see it. On
Android they are what the Play Store app reports to this process. Either
is as trustworthy as the device. A screen gated on `listPurchases` is
gated the way a hand-built app gates one; an app whose server must know
is gated on its server's answer, its own data source (D8).

**One account, every session.** A store's record is the account's, so the
facts are the process's: every session reads the same lists, and an
`acknowledge` from one acknowledges for all (D6).

**Offline.** Each store answers from its own cache when the network is
down; the module answers what it is given and never fails a fact for want
of a network.

### D4 — The first frame knows: the entitlement keeps its last answer

The module loads after first pixel (`rules/RULES.md`, the boot path; LLP
1024 D3), so a Contract that reads `listPurchases()` has no answer at
first frame, and a subscriber would see "Upgrade" until the module
answers. A hand-built app caches its last entitlement for the same
reason.

So an interface may declare a live source `"kept": true`, and the runner
keeps its last fresh answer as it keeps a TypeScript source's (LLP 1027
D4: `exact.kept.<resource>`, canonical bytes, capped, never granted to
the app), seeds the first frame with it when its arguments match, and
asks the module once it has loaded. The seed is provisional, as LLP
1027.005's is: never carried or checkpointed, replaced by the first
fresh answer. `listPurchases` is kept. `unfinishedPurchases` is not,
since delivery must act on the store's answer, never a seed; nor is
`getDetails`, since a stale price is worse than a placeholder.

A kept entitlement is as trustworthy as the app's own store for one
module load's time. Editing it shows a subscriber's screen for that
time; it is corrected before any purchase can be made, since the module
is the only path to the store.

### D5 — At least once, until acknowledged: the store's queue

**Every purchase that needs the app to finish it reaches the app the
same way, however it arrived:** a `purchase` in this session, in another
session or on another device; an Ask to Buy approval; a pending payment
completed while the app was closed; an offer code redeemed in the store;
a promoted purchase; on Apple, each renewal. It appears in
`unfinishedPurchases()` and stays there until the app calls `acknowledge`
or `consume`. The app delivers it once, keyed by its `purchaseToken`, and
then finishes it.

**A renewal differs by store, and the queue says so.** StoreKit makes
each renewal a new transaction that the app must finish, so on Apple a
renewal enters the queue. Play keeps a subscription's purchase token
across renewals and recoveries, and an acknowledged subscription stays
acknowledged ([subscriptions](https://developer.android.com/google/play/billing/lifecycle/subscriptions)),
so on Android a renewal enters nothing on the device: the subscription
stays in `listPurchases` and the queue is empty. The shared guarantee is
therefore what both stores keep: every transaction that needs the app's
completion is in the queue until it is completed. What an app delivers
per period (a monthly allowance, a server's billing record) it delivers
from Play's [Real-time developer notifications](https://developer.android.com/google/play/billing/rtdn-reference)
on its server, which is where Google sends renewals, and on Apple it may
do either. The recipe says so, and the Android substitute keeps Play's
token and adds nothing to the queue on a renewal (§9).

**Why a fact, not an event.** LLP 1133 D6 rule 7 lets a module declare a
bounded event protocol for what must each arrive, and LLP 1133.004 D6
built one: each event delivered once, held up to a bound, the oldest
dropped past it. A transaction is neither: the store delivers it again
until the app finishes it (Apple: "The updates listener receives
unfinished transactions just once at app launch, but you can use the
unfinished listener to get your app's unfinished transactions at any
time"; Play: redelivered by every query until acknowledged, refunded
after three days), and it must never be dropped. The store is the queue;
the fact is its current contents. This is a third shape beside LLP 1133
D6 rule 7's two, **a platform-owned queue read as a fact and drained by
acknowledgement**, and this RFC amends that rule to name it.

**The delivery loop is the one place that delivers.** It runs in data
code (D18), over `unfinishedPurchases()`, and for each `purchased` row:

1. skips to step 3 if the app has recorded the token as delivered;
2. delivers: credits a consumable in the app's own store, or posts the
   purchase to the app's server (D8) and waits for its answer, and records
   the token as delivered in the same commit as what it delivered;
3. finishes it: `consume` for a consumable, `acknowledge` for the rest.

A failure at step 2 (the server unreachable, the post refused) leaves the
row unfinished, and the loop runs again at the next answer of the fact.
A `pending` row is never delivered, posted or finished; Play's three days
begin when it becomes `purchased`.

**Idempotent by the token.** Because delivery is at least once (two
sessions, a crash between crediting and `consume`, a reply lost after
the store finished), the app records each token it has delivered and
skips one it has seen; a server does the same by its own record. The
recipe shows it with `storage.kv`; the substitute's drives crash between
the steps (§10, drive 7).

**A purchase's own answer is for the screen.** `purchase` answers the
purchase for the screen that asked ("Thank you", "Waiting for approval");
it delivers nothing and is never posted, so a `pending` answer and an
Ask to Buy approved days later take the same path, the loop. A `purchase`
whose mutation was superseded, whose session ended while the sheet was
up, or whose process died before the reply arrived loses nothing: the
store holds the transaction, and it is in the next `unfinishedPurchases`
answer. For the same reason a purchase reply is never a handle in LLP
1133.009 D10 item 10's sense: a dropped one is not disposed of, since the
store, not the app, owns it.

**Who finishes.** The app, explicitly (§13 question 1). Neither store
finishes by itself, and the right moment differs by app: a subscription
with no server is delivered when it is listed, a consumable when it is
credited, a purchase checked by a server when the server has recorded it
(on Play the server may acknowledge it itself through the Developer API,
and then `acknowledge` on the device answers at once). `acknowledge` of a
consumable consumes it on Apple, where finishing is consuming, and
acknowledges it on Play, where it stays owned until `consume`; the recipe
uses `consume` for a consumable on both.

**One exception: a revoked transaction.** A transaction bought, left
unfinished and then refunded before the next launch is still in
StoreKit's `unfinished`, with `revocationDate` set, and is in no
entitlement. There is nothing to deliver, so the Apple implementation
finishes a verified revoked transaction itself, lists it in neither fact,
and journals it by token; an app that took back what it credited learns
of the refund from `apple.transactions` (D10) or its server's
notifications. Play drops a voided purchase from the query by itself.

**What forgetting costs, made visible.** Apple delivers an unfinished
transaction again at every launch; Play refunds an unacknowledged
purchase after three days ("must be done within three days so that the
purchase isn't automatically refunded and entitlement revoked",
[integrate](https://developer.android.com/google/play/billing/integrate)).
A development build journals, a minute after the session's first
`unfinishedPurchases` answer, each `purchased` row still there, by token;
the substitute applies Play's refund on the agent clock on an Android
target (§9), so a drive shows what production would.

### D6 — From the module's load: the store's listener, before the app asks

**What Apple and Google ask.** Apple:
["Create a Task to iterate through the transactions from the listener as
soon as your app launches. If your app has unfinished transactions, the
updates listener receives them once, immediately after the app launches.
Without the Task to listen for these transactions, your app may miss
them."](https://developer.apple.com/documentation/storekit/transaction/updates)
And: "When your app launches, it needs to check currentEntitlements and
unfinished on Transaction to get any transactions that may have occurred
while the app wasn't running"
([offer codes](https://developer.apple.com/documentation/storekit/supporting-offer-codes-in-your-app)).
Google: query purchases "when your app is launched or comes to the
foreground", since `onPurchasesUpdated` "won't be invoked" while the app
is not running ([integrate](https://developer.android.com/google/play/billing/integrate)).

**What exact2 does.**

- **The implementation starts after first pixel, without waiting for a
  call.** An interface declared `"start": "load"` has its implementation
  made, per session, in the slot after first pixel where the host
  activates data (on Apple `prepareAppModule`, "after first pixel,
  before data activates", where the module artifact is loaded,
  `host/apple/Sources/ExactKit/NativeModule.swift`; on Android the
  matching slot after the reader's first frame, which this RFC names,
  since `Extensions.bind` runs in `ExactActivity.onCreate` before the
  first frame and only registers the roster), instead of at its first
  call (`ExactExtensions.adapter`). A seam addition (D16 item 1).
- **The listener is the process's, and outlives any one session.** The
  store's listeners are process objects, not a session's: on Apple one
  task over `Transaction.updates` and one over `Status.updates` and
  `Storefront.updates`, started by the first session's instance, which
  then sweeps `Transaction.unfinished` and `currentEntitlements`; on
  Android one `BillingClient`, with `enableAutoServiceReconnection()`
  (Play Billing 8.0), connected then and queried then and at every
  resume. A session's `destroy` releases its interest and cancels
  nothing while another session lives; the last session's end stops
  them, and the next session starts and sweeps again. A store change
  announces both facts' topics in every live session (`changed` on each
  session's context), so a purchase in one window unlocks the other. The
  sample host's two sessions (LLP 1031) are the case.
- **A call waits for the sweep.** A `purchase`, `acknowledge` or a read of
  either fact that reaches the implementation before the process's first
  sweep has finished waits for it, so no purchase is made before the
  listener runs (StoreKit warns of exactly that) and no list is answered
  before the unfinished ones are in it.
- **Nothing runs before first pixel.** The listener starts some hundreds
  of milliseconds after launch (LLP 1133.002 D16 measured the module's
  load at 216 ms after first pixel under the agent). Nothing is lost in
  that time: a transaction that arrives before the listener is unfinished,
  and `unfinished` "get[s] your app's unfinished transactions at any
  time". Apple's own current sample starts its listener from the root
  view's `.task`, after its first view appears
  ([Implementing a store in your app](https://developer.apple.com/documentation/storekit/implementing-a-store-in-your-app-using-the-storekit-api)).

*Rejected:* a StoreKit listener in ExactKit, started in
`didFinishLaunching` for every app that uses the package. It runs before
first pixel, which the boot rule refuses for any module's code, and it is
a private seam no third-party store package could use (LLP 1133.001 D8).
It would gain nothing the unfinished sweep does not already give.

**What arrives while the app is closed,** and how it reaches the app:

| While closed | Apple | Android | Reaches the app |
|---|---|---|---|
| a renewal; a billing retry recovered | a new transaction, unfinished | the same token, still owned and acknowledged | Apple: the new expiry in `listPurchases`, the renewal in `unfinishedPurchases` at the next load. Android: the subscription stays in `listPurchases`; nothing enters the queue; the app's server hears it from Real-time developer notifications (D5) |
| a refund, a revocation, family sharing ended | `revocationDate` set; gone from `currentEntitlements` | gone from the query | in neither fact (D5's exception) |
| an Ask to Buy approved; a slow payment completed | a new unfinished transaction | `PENDING` becomes `PURCHASED` | in both facts, unacknowledged |
| an offer code redeemed in the store | "StoreKit emits the transaction in updates on the next app launch" | owned at the next query | in both facts, unacknowledged |
| a subscription expired | gone from `currentEntitlements` | gone from the query | not in `listPurchases`; while running, D7 |
| a promoted purchase started on the App Store | [`PurchaseIntent.intents`](https://developer.apple.com/documentation/storekit/purchaseintent) (iOS 16.4, macOS 14.4) | — | `apple.purchaseintent`, an event (D10) |

The one event is the promoted purchase, which is the person asking to
buy, not a delivery: it follows LLP 1133.004 D6's cold-start rule (held
from launch, delivered once after first pixel to the handler the
declaration names). Everything else is a fact read at the next load or
resume: what needs the app's completion is in the store's queue, and a
Play renewal only in `listPurchases` (D5); none needs a rule beyond D5.

### D7 — A fact that goes stale at a known time

A subscription's entitlement ends at its expiration date, and on Apple
nothing reports it: `currentEntitlements` simply stops listing it. A
hand-built app checks at launch and on foreground, and while it stays in
front it shows "Plus" past the end.

So a module's answer may name the time at which it goes stale, `{"stale":
<ms since the Unix epoch>}` beside the answer, and the runner asks the
live source's readers again when the session's wall clock reaches it,
once per time named. The runner converts the time to its session clock
with LLP 1027.000.000's epoch (`exactTime().epochAtZero`, built in
`runner/src/time.rs`), so under the agent the agent's clock decides. The
ask runs outside the plan's timer wheel, as a polled source's does (LLP
1133.009 D10 item 7), so it never stops a clock advance, and `clock +N`
past the time waits for the ask, as it waits for a poll. Each answer
names its own next time. A seam addition (D16 item 2).

Every time in a `PurchaseDetails` (`purchaseTime`, `expirationTime`) is
milliseconds since the Unix epoch, on every target and under the agent,
where the substitute dates them from the agent clock's epoch.

**When the entitlement ends.** A subscription's `expirationTime` is when
its entitlement ends, not only when its paid period does: for one in a
billing grace period, which `currentEntitlements` keeps listing ("provides
full service … throughout the grace period",
[`RenewalInfo`](https://developer.apple.com/documentation/storekit/product/subscriptioninfo/renewalinfo)),
it is `RenewalInfo.gracePeriodExpirationDate`, since the transaction's
`expirationDate` is already past then. `listPurchases` names as its stale
time the earliest `expirationTime` still in the future; a time already
past is never named, so it cannot use up the ask, and a second
subscription ending later is not starved by the first. The re-ask reads
`currentEntitlements` and the subscription status again, where a renewal
the store has made is present, so a renewed subscription shows no gap. A
renewal that reaches the device after the stale ask re-answers the fact
through `Transaction.updates`.

**Android has no such time.** Play's client reports no expiration, so on
Android `expirationTime` is `none`, no answer names a stale time, and a
subscription that lapses while the app stays in front is dropped at the
next resume or listener call, as Google's guide does it. That is a limit
of Play's client, accepted; an app that must cut access at the minute
asks its server, which has `subscriptionsv2`'s expiry.

## 3. Validation

### D8 — Where a purchase is verified, and how data code reaches the server

**On the device.** StoreKit verifies every transaction's signature and
answers a [`VerificationResult`](https://developer.apple.com/documentation/storekit/verificationresult):
"StoreKit automatically verifies the Transaction … you might want to
verify the signed information yourself, either on the device, or on your
server for the most control and security." Apple accepts either: "To
validate purchases, you can verify transactions on your server, or rely
on StoreKit's verification" ([In-App Purchase](https://developer.apple.com/documentation/storekit/in-app-purchase)).
So the Apple implementation lists, answers and acknowledges only
`.verified` transactions; `purchase` of an unverified one fails
`VERIFICATION_FAILED` and leaves it unfinished, as Apple's sample does.
Google recommends no device verification: "Use the Purchases.products:get
or Purchases.subscriptionsv2:get endpoints in the Google Play Developer
API to verify with Google that the purchase is legitimate"
([security](https://developer.android.com/google/play/billing/security)).
The purchase's signed JSON (`getOriginalJson`, `getSignature`) is tier 2
for an app that checks it with its own key; the module checks nothing it
has no key for.

**On the app's server.** What the server takes:

| Store | The device sends | The server checks with |
|---|---|---|
| Apple | `apple.jwsRepresentation`, the signed transaction, "the same as the JWSTransaction that the App Store Server API returns" ([`jwsRepresentation`](https://developer.apple.com/documentation/storekit/verificationresult/jwsrepresentation-21vgo)); or `purchaseToken`, the transaction id | the [App Store Server Library](https://developer.apple.com/documentation/appstoreserverapi/simplifying-your-implementation-by-using-the-app-store-server-library)'s `verifyAndDecodeTransaction`, offline; or [Get Transaction Info](https://developer.apple.com/documentation/appstoreserverapi/get-transaction-info) |
| Play | `purchaseToken` and `itemId` | `purchases.products.get` or `purchases.subscriptionsv2.get`; it may acknowledge there too |

Afterwards the server learns of renewals and refunds from the store
itself: [App Store Server Notifications V2](https://developer.apple.com/documentation/appstoreservernotifications/app-store-server-notifications-v2)
and Play's Real-time developer notifications. exact2 relays nothing (LLP
1030.000 D6): the app's server and the store talk directly.

**How data code reaches it.** In D5's delivery loop, step 2: the loop's
data code posts each `purchased` row of `unfinishedPurchases()` with the
app's own `fetch`, and finishes it only when the server has answered:

```ts
async function deliver(p: PurchaseDetails) {
  const { store } = await purchasesStatus();          // "app-store" | "google-play"
  const res = await fetch(`${api}/purchases`, { method: "POST", body: JSON.stringify({
    store, token: p.purchaseToken, itemId: p.itemId,
    signed: p.apple?.jwsRepresentation }) });
  if (!res.ok) throw new Error(`not delivered: ${res.status}`);  // stays unfinished
}
```

The purchase that the person just made and the one approved while the
app was away take this one path; `purchase`'s answer is never posted
(D5). The account binding below travels with the purchase, so the server
checks it against its session. `purchasesStatus().store` says which
server API to use.

**Bound to the account, not secret.** A purchase token is not a
credential: using it needs the store's server API and the developer's
key. What stops a token being claimed for another account is the account
binding, which the shared word `accountToken` writes into the store's own
record: Apple's [`appAccountToken(_:)`](https://developer.apple.com/documentation/storekit/product/purchaseoption/appaccounttoken(_:)),
a UUID that "the App Store returns … in the resulting transaction"; Play's
[`setObfuscatedAccountId`](https://developer.android.com/reference/com/android/billingclient/api/BillingFlowParams.Builder),
"uniquely associated with the purchaser's user account in your app",
"limited to 64 characters", with no personal information "in cleartext".
`accountToken` is therefore a UUID string (36 characters, which fits
both), refused by name otherwise (`accountToken-not-uuid`). The token may
enter Contract state; the account's own credential never does (LLP 1018
D5).

**A server-authoritative app** gates on its server's answer, a source of
its own, and uses `unfinishedPurchases` only to find what to send. It still
calls `acknowledge` on Apple once the server has recorded the purchase,
since only the device can finish a StoreKit transaction.

## 5. Store review

### D12 — `requestReview()`

The web has no rating prompt; the name is a **declared deviation**, the
one both stores use.

| Name | Kind | Contract | Data code |
|---|---|---|---|
| `requestReview()` | send; answers nothing; shows system UI | a statement in an action | `await requestReview()` |
| `storeReviewStatus()` | live source; a fact; `sync` | `resource r = storeReviewStatus()` | `await storeReviewStatus()` |

`storeReviewStatus()` answers `available` only. Neither platform says
whether the prompt was shown: Apple "may not present an alert"; Google:
"The API does not indicate whether the user reviewed or not, or even
whether the review dialog was shown" ([In-App Review](https://developer.android.com/guide/playcore/in-app-review)).
So `requestReview` answers nothing, never fails for the platform's
silence, and journals `requestReview: requested`.

| | Apple | Android | Windows (later) |
|---|---|---|---|
| the call | [`AppStore.requestReview(in:)`](https://developer.apple.com/documentation/storekit/appstore/requestreview(in:)) with the session's `UIWindowScene` (iOS 16) or `NSViewController` (macOS 13); `SKStoreReviewController` is deprecated in iOS 18 and macOS 15 | `ReviewManagerFactory.create(context)`, `requestReviewFlow()`, then `launchReviewFlow(activity, reviewInfo)` | [`StoreContext.RequestRateAndReviewAppAsync`](https://learn.microsoft.com/uwp/api/windows.services.store.storecontext.requestrateandreviewappasync) (1809), with the window handle |
| the quota | "a maximum of three times within a 365-day period" | "a time-bound quota" that "can be changed by Google Play without any notice" | — |
| in development | "StoreKit always displays" the prompt in a development build; "no effect in apps that you distribute for beta testing using TestFlight" | shown only for an account that downloaded the app from a test track; never with internal app sharing | a Store-licensed install |

**Unsaid: the platform decides,** and the module adds no prompt or "Enjoying
Weatherlight?" pre-question of its own, which would be a tell. When to ask
is the app's choice (LLP 1133 §0 ruling 9); the recipe gives both
platforms' guidance: Apple, "don't call requestReview() … in response to a
button tap or other user action", "Avoid asking for a rating on first
launch or during onboarding", "allowing at least a week or two between
requests" ([HIG](https://developer.apple.com/design/human-interface-guidelines/ratings-and-reviews));
Google, no "call-to-action option (such as a button)", for which "redirect
the user to the Play Store instead". A "Rate Weatherlight" button opens the
store's page with `openURL`, which an app writes itself.

**Origin.** `"origin": "app"`, `"foreground": true`: a person's input or
the app's own foreground code may ask; a tool, a wake or a headless
session fails `NotAllowedError`, `person-required`, since the prompt is
system UI (LLP 1133 D6 rule 3).

**The queue of decisions, as far as the platform allows.** The request
joins LLP 1133.002 D9's queue, so it is made only after every earlier
sheet the queue holds has closed. What follows it differs: Android's
`launchReviewFlow` answers a `Task` that completes when the flow has
finished, shown or not, so the queue holds until then; Apple's
`requestReview(in:)` returns at once with no presentation or dismissal
signal, so the queue advances when it returns, and a purchase or Face ID
sheet asked right after may meet StoreKit's prompt. exact2 promises only
what the platform reports; the recipe asks for a review at a moment no
other sheet is coming.

**Packaging.** `@exact/store-review` is its own extension, so an app that
asks for ratings and sells nothing links no billing library (on Android,
review's dependency graph is smaller than billing's, D19).

**Under the agent** the implementation is its own substitute (§9): it shows
nothing, journals each request with its origin, keeps Apple's quota on the
agent clock on an Apple target (a fourth request inside 365 days is
journaled `requestReview: over quota`), and `state.extensions` counts
requests. There is no ticket, since the platform gives the person's
answer to no one.

## 6. Permission and origin

### D13 — No permission: the store's sheet is the consent

No platform asks a runtime permission for purchases or reviews, and none
derives an Info.plist key (In-App Purchase "do[es] not have corresponding
entitlements", [TN2415](https://developer.apple.com/library/archive/technotes/tn2415/_index.html);
it needs an explicit App ID, D21). The person's consent is the store's own
sheet, each time: StoreKit's confirmation with Face ID or the side button,
Play's purchase dialog. So the modules declare no `permission` (LLP
1133.002 D8's fact does not exist here) and no grant line (LLP 1069.008
D2's table gains a row reading "none", as the clipboard's does, LLP
1133.006 D9). Using the package is the app's statement that it sells.

On Android the billing library's own manifest adds
`com.android.vending.BILLING`, a `<queries>` entry for Play's billing
service and its proxy activities, through manifest merging (the AAR's
`AndroidManifest.xml`; the library's documentation does not list them).
The implementation declares that permission in its `exact.json`, and the
build refuses a merged permission that neither a grant line nor a bound
implementation declares (D19).

### D14 — Who may buy, and spending is not delegable

| Origin | `purchase`, `restorePurchases`, Apple's sheets | `acknowledge`, `consume` | `getDetails`, `listPurchases`, `unfinishedPurchases`, `purchasesStatus` |
|---|---|---|---|
| a person's input; the app's own code in a foreground session | the store's sheet (D15) | proceed | answer |
| a tool invocation (LLP 1111) | fails `NotAllowedError`, `person-required`, before reaching the store | proceed | answer |
| a background wake (LLP 1114.001); a headless session | fails `person-required` | proceed | answer |
| any origin while the app is in the background | fails `NotAllowedError` (`"foreground": true`, LLP 1133.009 D10 item 3) | proceed | answer |
| the development agent | §9 | §9 | §9 |

The declarations say `"origin": "app"` and `"foreground": true` on each
name that opens a sheet. A tool may read what the person owns, since the
app already has that right, and may acknowledge and consume, since
delivering what was bought is bookkeeping the person benefits from.

**Spending is not delegable.** LLP 1133.002 D12's direction lets agents
come to hold and pass on authority the platform granted the app. A
purchase is not such authority: it spends the person's money, from their
store account, confirmed by them in the store's sheet. No delegation
record lets a tool start one, as no record satisfies a presence check
(LLP 1133.010 D12). A tool that wants the person to buy something asks
through the app's own UI, from which the person buys.

**No user activation is required.** The 2022 Payment Request Recommendation
rejects `show()` without transient activation; the 2026 draft makes that
a MAY "to support redirect flows"
([§`show()`](https://www.w3.org/TR/payment-request/)). Native stores
require none, and Apple's promoted purchase is answered by a purchase
the person began on the App Store. So the module requires the app's
origin, not a press: any of the app's own foreground code may ask (LLP
1133 §0 ruling 9), and the store's sheet is the person's decision.

**Restore is the exception Apple names.** `AppStore.sync()` "displays a
system prompt that asks users to authenticate … Call this function only
in response to an explicit user action". Under ruling 9 exact2 refuses no
foreground caller, so `restorePurchases` keeps `"origin": "app"`; a
development build journals each call whose origin is not a person's
input, naming Apple's rule, and the recipe puts it behind a Restore
button. Nothing else needs it: every transaction the app must finish
reaches it through the queue without a restore (D5).

### D15 — One sheet at a time, over the session's window

`purchase`, `restorePurchases` (on Apple, where `sync()` "displays a
system prompt that asks users to authenticate") and Apple's sheets join
LLP 1133.002 D9's queue of decisions, each held until the platform
reports its sheet closed, so none opens over a permission prompt, a Face
ID sheet or another store sheet. `requestReview` joins it too, with the
weaker promise D12 states, since Apple reports nothing of its prompt. Like a presence check (LLP 1133.010 D8), a purchase is never
shared: two queued purchases show two sheets.

The sheet is presented over **the session's window**, which the package
context now gives (D16 item 3): the session's `UIWindowScene` on iOS,
for [`purchase(confirmIn:options:)`](https://developer.apple.com/documentation/storekit/product/purchase(confirmin:options:))'s
scene form (iOS 17, exact2's floor); its `NSWindow` on macOS, for the
window form (macOS 15.2), with
[`purchase(options:)`](https://developer.apple.com/documentation/storekit/product/purchase(options:))
below 15.2; the resumed activity on Android, for `launchBillingFlow`
(which takes a plain `Activity`, as `ExactActivity` is). A call while no
window of the session is in front fails `NotAllowedError` at once rather
than wait. A sheet cannot be withdrawn: a call cancelled while its sheet
is up leaves the sheet, and the store's answer still lands in the queue
(D5).

## 7. Packaging and callers

### D16 — Seam additions

Each is general, each is apparatus under `rules/RULES.md` that lands with
this ruling, and each is proved by the out-of-tree fixture before this
package uses it (LLP 1133.001 D8):

1. **An implementation started at load.** `"start": "load"` on an
   interface: its implementation is made for each session in the slot
   after first pixel where the host activates data (Apple's
   `prepareAppModule`; on Android a slot after the reader's first frame,
   which this addition names, since `Extensions.bind` in `onCreate` runs
   before it), rather than at its first call. Its process objects outlive
   a session that ends while another lives (D6). The bake allows it only
   on an interface the app imports, so an app that does not use the
   package starts nothing. Push registration, geofencing and Bluetooth
   state restoration will start the same way.
2. **An answer that names when it goes stale** (D7): `{"stale": ms}`, a
   Unix time, on a live source's reply; the runner asks its readers again
   when the session's wall clock (LLP 1027.000.000) reaches it, outside
   the timer wheel; `clock +N` waits for it. A
   calendar's next event and a cached token's expiry read the same rule.
3. **The session's presentation anchor.** `ExactPackageContext` gains
   `presentation`: on iOS the session's `UIWindowScene`, on macOS its
   `NSWindow` and its content `NSViewController`, `nil` while no window of
   the session is in front; Android's `ExtensionContext.activity` already
   is one. Today a package has no window (`ExactPackage.swift`), and every
   sheet StoreKit, AuthenticationServices or the share sheet presents
   needs one.
4. **A module source's kept answer** (D4): `"kept": true` on a declared
   live source, under LLP 1027 D4's rules.
5. **A sheet held as a ticket before an implementation that is its own
   substitute.** LLP 1133.008 D8 item 9 has the runner hold the
   *permission* decision as a ticket and pass the call on. A name may now
   declare its sheet: `"sheet": {"ticket": "purchase", "choices": [...]}`;
   under the agent the runner holds a ticket with those choices after
   admission, and the chosen answer reaches the implementation with the
   call (`decision`), which the implementation applies. So tickets stay
   the runner's, as every drive reads them in `pending`, and the store's
   behaviour stays the implementation's (§9).
6. **The one locked Gradle graph checks the merged manifest** (D19).

### D19 — Android: billing and review in the one locked Gradle graph

LLP 1133.008 D8 item 5 decided that an implementation's Maven libraries
join the Android project's one Gradle graph, held by Gradle's dependency
locking and dependency verification, with Google and Maven Central as
the only repositories. Purchases is the second module to need it and may
be the first to build it (§12).

**What joins the graph** (from the published POMs, compile scope;
[billing 9.1.0](https://dl.google.com/android/maven2/com/android/billingclient/billing/9.1.0/billing-9.1.0.pom),
[review 2.0.2](https://dl.google.com/android/maven2/com/google/android/play/review/2.0.2/review-2.0.2.pom)):

| Library | Its dependencies |
|---|---|
| `com.android.billingclient:billing:9.1.0` (2026-06-18, the latest) | `androidx.activity:activity:1.2.3`, `androidx.core:core:1.15.0`; `com.google.android.gms:play-services-base:18.5.0`, `-basement:18.9.0`, `-tasks:18.2.0`, `-location:19.0.0` (which brings `play-services-places-placereport`); `com.google.android.datatransport:transport-api`, `-backend-cct`, `-runtime`; and through `basement`, `androidx.fragment` and `androidx.collection` |
| `com.google.android.play:review:2.0.2` | `play-services-basement:18.4.0`, `-tasks:18.2.0`, `com.google.android.play:core-common:2.0.4` |

The non-KTX artifacts are named, so no Kotlin coroutines version enters
the graph from them. `androidx.core` 1.15.0 and `androidx.fragment` meet
Compose's (`-Pcompose=1`) and CameraX's in the same resolution, which is
why the graph is one: a pinned closure beside Gradle's would carry two
`androidx.core`, and Play Billing 9 needs "AndroidX.core library version
1.9 or later" at run time ([release notes](https://developer.android.com/google/play/billing/release-notes)).

Three consequences the build states:

- **Play services arrive with billing, and their manifests with them.**
  Geolocation chose the platform's `LocationManager` to need no Play
  services (LLP 1133.002 D3); an app that sells now carries Play
  services' base libraries, `play-services-location` among them, through
  billing's own POM, and every one of their AAR manifests merges into the
  app's. R8 removes unreached code but no merged `<uses-permission>`,
  provider, service or receiver. So stage 2's first step, before the
  graph is locked, inventories each artifact's manifest; the
  implementation declares every permission and component the merge adds,
  each of which this RFC then names; and an artifact billing does not
  need at run time (location is the candidate) is excluded from the
  graph only if billing's documented calls are shown to work without it
  on a device. Until that inventory, D13's statement that billing adds
  only `com.android.vending.BILLING` holds for billing's own AAR alone.
- **The merged manifest is checked.** Billing's AAR adds
  `com.android.vending.BILLING`, a `<queries>` element and two proxy
  activities. The build reads the merged manifest and refuses, by name, a
  permission that neither the app's grants (LLP 1069.008) nor a bound
  implementation's `permissions` declare, so a library cannot add one
  silently (D16 item 6).
- **The versions move on Google's schedule.** "All versions of the Google
  Play Billing Library have a two-year deprecation cycle"; version 9's
  date for new apps and updates is 2028-08-31
  ([deprecation](https://developer.android.com/google/play/billing/deprecation-faq)).
  The implementation pins one version; moving it is a minor of the
  implementation with its lock and verification files.

`minSdk` is 23 for billing and 21 for review, below the host's 29.

### D21 — What a store requires before anything works

A purchase reaches a store only from a build the store recognises:

| | Development | Testing with a store | Production |
|---|---|---|---|
| iOS | the simulator or a development-signed build with a profile for an **explicit** App ID ("apps that are code signed with a wildcard provisioning profile cannot use … In-App Purchase", TN2415); StoreKit's sandbox with a Sandbox Apple Account ([sandbox](https://developer.apple.com/documentation/storekit/testing-in-app-purchases-with-sandbox)) | TestFlight, which "always run[s] in the sandbox environment" (LLP 1030.003 D6) | an App Store build |

module unavailable there: `purchasesStatus().available` is false, and the
journal says why, rather than every call failing at the store.

### D22 — Cost

An app that imports neither package links nothing of them: no StoreKit
code, no billing library, no merged permission (LLP 1047.001). One that
does loads the implementation with the app's module after first pixel,
and `"start": "load"` makes the purchases implementation then rather
than at its first call: one task over three sequences on Apple, one
service connection and one query on Android, measured in stage 1 and
stage 2 on a device as time after first pixel and recorded here. StoreKit
is a system framework the Apple module dylib links, never the executable.
Stage 2 records the APK size billing adds after R8, and the number of
artifacts the locked graph gains, with LLP 1047's probe.

## 9. The substitute, and the stores' own test environments

There are three ways to exercise a purchase, and each has its place:

| | What runs | What it proves | Who uses it |
|---|---|---|---|
| **the substitute** | the implementation under the agent, with no store | the app's flows: gating, delivery, pending, expiry, refunds, relaunch, origins | every drive (§10) |
| **the store's local test** | Apple: real StoreKit against a StoreKit configuration file, in an XCTest with [`SKTestSession`](https://developer.apple.com/documentation/storekittest/sktestsession) (`disableDialogs`, `askToBuyEnabled`, `buyProduct(identifier:options:)` "outside the app", `expireSubscription`, `forceRenewalOfSubscription`, `refundTransaction`, `timeRate`), transactions "signed by Xcode"; Android: none (Play has no local store) | the Apple implementation's StoreKit code, renewals at speed, a purchase made outside the app | the conformance suite on macOS and the simulator |
| **the store's sandbox** | Apple's sandbox with a Sandbox Apple Account; Play's internal track with license testers and test cards ("Test card, always approves", "Slow test card, approves after a few minutes", "approves then charges back") | the whole path through the store's servers | by hand, Charlie (§10 drive 13) |

**The implementation is its own substitute** (LLP 1133.006 D8 item 4,
with LLP 1133.008 D8 item 9's split): under the agent the runner admits
each call and holds each declared sheet as a ticket (D16 item 5), and the
implementation runs, told it is under the agent, reaches no store, makes
no `BillingClient`, starts no StoreKit task and calls no hatch. It keeps a
**synthetic store** instead, in the drive's scratch tree (LLP 1018 D6), so
it survives a relaunch as the store's servers do. Why the implementation:
a store is a state machine with a catalogue, a queue, expirations and
refunds, and a declared substitute would need that vocabulary in the
runner and the web runtime for one module, as recording found for its
recorder (LLP 1133.009 §10). The cost, as there: a target with no
implementation cannot drive a purchase, and here every such target is
`absent` or `later` in production too, so the drive shows what the
person would see.

**The catalogue.** The synthetic store's products are the app's
**catalogue**, a JSON file of tier 1 `ItemDetails` (with `apple.type` for
the consumable distinction and a subscription `group`) that `app.json`
names (`"purchases": {"catalog": "store/catalog.json"}`, §13 question
3), carried in the plan's substitute table and never in a production
bake. `prefer extension purchases.getDetails=[…]` replaces it for a
drive. The same ids are the products configured in App Store Connect,
Play Console and the conformance fixture's StoreKit configuration file;
the catalogue is the app's statement of them, not a copy the stores read.

**Tickets** (in `pending`, their `args` naming the item, its
`displayPrice`, the session and the origin):

| Event | Result |
|---|---|
| `purchase` from a foreground app origin | a `purchase` ticket |
| `tap @t buy` | the synthetic store records a transaction (token from a counter the session's seed fixes; `purchaseTime` the agent clock's Unix time; on an Apple target a subscription's `expirationTime` its period later, on an Android target `none`, as Play's client reports, D7); `purchase` answers it; both facts are re-answered with it unacknowledged |
| `tap @t cancel` | fails `AbortError` |
| `tap @t pending` | answers `purchaseState` `pending`; on an Android target with Play's token, and `unfinishedPurchases` lists it `pending`; on an Apple target with an empty `purchaseToken`, and nothing is listed until an `approve` event makes the transaction |
| `tap @t unavailable` | fails `ITEM_UNAVAILABLE` |
| `tap @t fail` | fails `NETWORK` |
| `restorePurchases` on an Apple target | a `restore` ticket; `allow` answers the list, `cancel` fails `AbortError`; on Android no ticket |
| `acknowledge`, `consume` | applied to the synthetic store at once; `consume` removes the item |
| `clock +N` past an `expirationTime` (Apple targets) | the runner's stale ask (D7); the subscription leaves `listPurchases` unless a renewal was applied first |
| a relaunch or a return to the foreground on an Android target | the synthetic store drops each subscription whose period, which it keeps privately, has ended, as Play's next query would |
| `prefer extension purchases.storeEvent={…}` | **a change the store makes on its own**, applied once to the synthetic store by the implementation, keyed by token, when the value is set (on bind and on each change, LLP 1133.008 D8 item 9): `{"op": "approve", "purchaseToken": t}` (a pending purchase becomes `purchased`), `{"op": "renew", "purchaseToken": t}` (on an Apple target a new unfinished transaction one period on; on an Android target the same token, still acknowledged, its private period extended, and nothing in the queue, as Play does), `{"op": "revoke", "purchaseToken": t}`, `{"op": "purchase", "itemId": i}` (on another device or by an offer code); set before a relaunch, each is what arrived while the app was closed. It is never laid over an answer: both facts are always the synthetic store's own answers |
| an Android target, a purchase unacknowledged three agent-clock days after it became `purchased` | refunded and dropped from both facts, as Play does; journaled |
| an Apple target, a launch with unfinished purchases | each in `unfinishedPurchases` again, as StoreKit redelivers; a revoked one finished by the implementation (D5) |
| `apple.purchaseintent` | `{"op": "intent", "itemId": i}` as a `storeEvent` raises it, held across a relaunch per LLP 1133.004 D6 |
| a tool-origin or wake-origin `purchase` | as production: `person-required`, no ticket |

There is no `prefer` that buys: each purchase in a drive is a tap, so its
transcript shows every place the person would be asked to pay.

**Never real money.** A drive reaches no store. `--bind purchases` (the
real implementation under the agent, LLP 1133.002 stage 2) is allowed on
Apple targets, where a development-signed build reaches only StoreKit's
sandbox or Xcode's local environment, and refused by name on Android
(`bind-real-money`), where a sideloaded build signed in with an account
that is not a license tester pays "actual charges". Android's real
implementation runs only in the conformance suite's fixture, whose
package has nothing for sale outside its internal track.

**Disclosure:** `state.extensions` lists `purchases`, its binding per
target, the synthetic store (products, transactions with their tokens,
states and acknowledgement, expirations), each answer's origin, the
stale-time pending, and `store-review`'s requests; the journal names each
purchase and acknowledgement by token, never an account.

**Production:** none of it.

## 10. The consumer: Weatherlight+

No app in the repository sells anything today. Weatherlight is the closest
to needing to: its README says the forecast provider's public endpoint "is
for non-commercial use; commercial distribution needs the provider's
subscription", which a weather app on the stores pays for with a
subscription of its own. It has no server, so it exercises the device's
verification and delivery, and it already reads a module (geolocation)
from both Contract and data code. The feature is small and real:

- **Weatherlight+**, an auto-renewable subscription in one group, monthly
  (`plus.monthly`) and yearly (`plus.yearly`), shows the sixteen-day
  forecast (Open-Meteo's `forecast_days=16`) where the free app shows
  seven. A "Support" sheet lists both plans with `displayPrice`, their
  periods and the free trial if offered, and the terms and privacy links
  a subscription screen carries.
- **A tip,** a consumable (`tip.small`), thanked once per tip, with a
  count of tips kept in `storage.kv`: the consumable path.
- **Restore** on Apple, and on Android nothing to tap: Play lists the
  person's purchases at every resume.
- **The rating prompt** after the person has opened Weatherlight on five
  different days, while a forecast is showing, at most once per app

  its web cell is `absent` in a browser (D20); store review's Linux cell is

  Play's alternative billing as tier 1 (reachable now through the hatch).
