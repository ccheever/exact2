# LLP 1051.000: Hypothetical layout — an implementation outline

**Type:** RFC
**Status:** Draft. This is an outline, not a spec: it names no implementer and no date (`rules/RULES.md` §Scope). Building any part of it moves a line in `rules/NOT-DOING.md` (§9), and that is Charlie's call. It is not linked into `llp/current/`, which is at 15 of 15 on origin/main.
**Systems:** Kernel (a what-if pass, as a rolled-back transaction; `measure_height_targets` folded into it), Contract compiler (geometry reads allowed only in actions), Runner (a layout context for the stdlib, beside the router's), Motion (`exact-motion`: paths, contact events, a rest rule, a velocity read), Web host (a DOM what-if in the glue), Apple and Linux hosts (the kernel answers, and the engine presents paths at presentation time), Agent API (forms of `layout`)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-25
**Related:** LLP 1051 (the research: definitions, the survey, the uses, the ball); LLP 1001 §3, §6; LLP 1002 D4, D7, D8; LLP 1003 (motion); LLP 1007 §9; LLP 1012 §2; LLP 1013; LLP 1039 D5; LLP 1041 §8.12; LLP 1043.000; LLP 1047 (linking by use; `Kernel::on_demand`); `rules/NOT-DOING.md` §Motion and §Agent API; `rules/RULES.md` §Agents

## Summary

LLP 1051 found that systems expose hypothetical layout in four ways:
force-and-read, size questions, lookahead and motion projection. All four
compute the same thing at different times, and systems that build them
separately watch them drift apart (F2, F3). This outline proposes one
mechanism for exact2 and the smallest set of surfaces over it.

- **One mechanism: the what-if pass.** It is a kernel transaction that is
  laid out and then rolled back.
  - Its input can be structural edits, row values, a different offer, or rows'
    presented values at a time t.
  - It goes through the kernel's one write path, so every derivation (inherited
    rows, text runs, exclusions) is the committed one.
  - It reads only the frames it was asked for, and leaves the tree, its
    published frames and its epoch as they were.
  - `measure_height_targets` is the special case that exists today (heights
    only, root offer only). It becomes a caller, and its private path is
    deleted.
- **Two surfaces.**
  - Handler-time reads from Contract actions: synchronous, on the main thread,
    and refused by the compiler anywhere else (LLP 1051 §1.3).
  - Paths: closed-form, event-driven motion for paint-only rows, solved
    against layout at release and presented by the host. This is the ball.
- **Per host.** On native hosts the kernel *is* the layout, so its answer is
  exact. On the web the browser answers: the kernel's transaction supplies
  the forward and inverse batches, and the glue applies them around a forced
  layout inside one task. Native answers are held to the browser's by
  fixtures, as layout already is.
- **Cost in rules.** If fling projection or the ball becomes a consumer, a
  decay-and-contact driver comes off NOT-DOING's driver line. Nothing else in
  §Motion moves (§9).

## 2. The what-if pass

### D1. One pass, rolled back, nothing published

```rust
// exact-kernel — a sketch; names are not final
impl Kernel {
    /// Apply `overlay` as a transaction, lay out `root` under `offer`, read
    /// `targets`, then roll back. On return, even after an error, frames,
    /// overflow, flags, styles, selectors, receipts and the epoch are exactly
    /// as they were.
    pub fn what_if(
        &mut self,
        root: ViewId,
        offer: Offer,
        overlay: &Overlay,
        targets: &[NodeKey],
    ) -> Result<Answer, KernelError>;
}

pub struct Overlay {
    pub ops: Vec<Op>,                 // ordinary wire ops, validated as a commit's
    pub presented: Vec<PresentedRow>, // row values at a time: PresentedHeight, generalized
}

pub struct Answer {
    pub epoch: u64,         // the epoch it assumed; stale after the next commit
    pub frames: Vec<Frame>, // one per target
}
```

- **The ops are ordinary.** `ops` are the same ops a commit takes
  (`SetChildren`, `SetStyle`, `SetProps` and so on). A what-if can therefore
  express anything a commit can, such as a reparent, a reorder or a row
  change, and it refuses whatever a commit would refuse.
- **One write path.** The ops go through `txn::apply`, which the kernel
  describes as having no other write path. An overlay that bypassed it would
  have to re-derive inherited rows, text runs and exclusions separately. That
  would be a second implementation, and LLP 1051 F3 says second
  implementations drift.
- **Time rows.** `presented` generalizes `PresentedHeight` to the rows a time
  query needs.
- **What a frame means.** Frames are reported as the agent's `layout` reports
  them on the web: in the viewport's space, with scroll offsets and transforms
  folded in (`host/web/glue.js:1160`). Native hosts compose the kernel's
  layout boxes with motion's values at the query time so that they match.
- **Staleness.** An answer held across a commit is refused as stale, as a
  stale `PresentedHeight` is today.

### D2. Stage 1: a transaction that is laid out and rolled back

1. **Validate** the ops with `txn::Staged`, exactly as for a commit.
2. **Apply** them through `txn::apply` with an undo journal. This is new: each
   write records its inverse. The epoch is not bumped and no receipt is
   recorded.
3. **Lay out** the root without publishing, using the same engine call
   `measure_height_targets` makes. Read each target's box from the engine tree
   by composing Taffy's parent-relative locations up to the root.
4. **Roll back** by replaying the journal in reverse. The arena, the selector
   index and the engine tree's styles and children return to their prior
   values.

Several properties follow from this design.

- **Caches.** Clean subtrees keep their Taffy cache entries, and the what-if
  reuses them. The dirty paths now hold hypothetical results; rolling back
  marks them dirty again, and the next real layout recomputes them once.
  `measure_height_targets` already makes this trade. The reuse is only as
  sound as Taffy's cache key, which Exact's patch 11 made complete on
  2026-09-25.
- **New nodes.** A node that a what-if creates is created and destroyed
  inside it, and its key never escapes. A route that is about to mount can
  instead be built ahead of time as detached nodes, which are "live, no
  parent, in no root's layout" (LLP 1001). The overlay then attaches them.
- **Text.** A paragraph whose width changes is broken again through the host
  measurer. A paragraph whose width is unchanged hits the per-leaf memo of 16
  offers.
- **Allocation.** The journal and the scratch vectors keep their capacity
  between what-ifs, so a warm what-if allocates nothing new. Jordan raised
  allocation cost in Rust; this is the answer to it here.

Three invariants, each a test:

1. **Nothing moves.** After a what-if, every frame, overflow value, flag,
   receipt and the epoch are bitwise what they were.
   `kernel/tests/it/presented_height.rs:1002` and `:1040` already assert this
   for heights.
2. **The answer is the commit's.** For seeded trees and overlays, the layout
   boxes `what_if(ops)` reads (before transforms are composed) are bitwise
   the frames that committing `ops` on a `rehydrate`d fork publishes. This
   follows the style of the 512-tree differential in `kernel/src/layout.rs`.
3. **The next real layout is unchanged.** Laying out after a what-if gives
   the same frames as laying out without one.

### D3. Stage 2, only if measured: an overlay tree with its own caches

Stage 1 re-dirties the paths it lays out. That could show up in measurements,
for example with a what-if on every frame of a drag over a long list. If it
does, the overlay becomes a view onto a Taffy tree:

- Taffy's low-level traits implemented over the columns plus the journal;
- scratch caches for dirty nodes;
- read-only reuse of the committed caches for clean nodes.

That needs either a vendor patch to read cache entries or a move of the kernel
to Taffy's low-level API. It waits for a measurement that calls for it.

## 3. Asking from app code

### D4. Geometry reads are stdlib calls, allowed only in actions

- **The layout context.** The runner passes a layout context to
  `stdlib::call`, beside the router's (`runner/src/stdlib.rs`). Native hosts
  back it with the kernel; the web host backs it with the glue (D8).
- **Only in actions.** The compiler refuses these calls outside actions
  (`contract/analyze`). In a derive, a view expression or a resource argument
  they are an error that names LLP 1039 D5. They are calls, not new syntax.
  That matters while new Contract syntax waits behind formatting and
  navigation (NOT-DOING's LLP 1035 admission).
- **Which layout a read sees.** A read sees the layout of the epoch the
  handler started in. A handler that wants geometry after its own writes asks
  for a what-if of those writes.

A sketch of the sheet, with its stops taken from geometry instead of 180, 360
and 640 (`apps/interaction-gallery/app.contract:77-78`). It is illustrative;
the names and the list literal are not proposals:

```
action snapSheet(height: number, velocity: number) writes sheetPx
  sheetPx = nearestStop(projectFling(height, velocity),
                        [180, measure("reading-sheet").height, frame("sheet-bay").height])
```

The tallest stop then becomes the room the sheet actually has. Today it is a
640 that `max-height: 100%` clamps to 562.79 on AppKit (LLP 1041 §8.12).
`projectFling` uses the platform's deceleration (0.998 per millisecond), as
UIKit's own projection does.

## 4. Time

### D5. Layout at time t is the layout of the rows at t

- **Paint-only rows** (`translate`, `scale`, `rotate`, `opacity`). The
  position at t is the committed frame composed with exact-motion's value at
  t, and the velocity is its derivative. `SpringConfig::sample` returns both
  already. The engine does not expose them: its running curves are private to
  the crate. So this adds a read, `Engine::sample(node, property, t)`, which
  returns a value and a velocity. No layout pass is needed.
- **Layout-affecting presented rows** (LLP 1041 §8.12's heights). These need a
  what-if with `presented` samples at t. The velocity is a central difference
  of two what-ifs at t ± 1 ms. Layout's response to a single height is
  piecewise linear, so the difference is exact except across a break.
- **Discontinuities are reported, not smoothed.** A commit, or a paragraph
  that re-wraps, moves a box instantly, and the answer says so.
- **The web** takes paint-only rows from the same closed forms; it already
  samples exact-motion to lower springs. It takes presented heights from a DOM
  what-if with the height set to its value at t.

## 5. Paths: projection and the ball

### D6. A path is closed-form segments between events, solved at release

- **Where.** A solver in `exact-motion`, which depends on nothing. Its
  arithmetic goes through the pinned `libm`, with `log` added.
- **The laws between events.**
  - Constant velocity.
  - Exponential decay: the platform's deceleration, 0.998 per millisecond by
    default, as in UIKit.
  - Constant acceleration, such as gravity.
- **Obstacles.** Axis-aligned boxes from layout: the containing block's
  padding box, and sibling boxes named by id. Each is either static or moving
  by a closed form (D5).
- **Time of impact.**
  - For a static wall it is analytic: a division, a logarithm or a quadratic
    root, depending on the law.
  - For a moving wall it uses conservative advancement, bracketed by the
    wall's largest speed over the interval, then bisection to a fixed
    tolerance.
- **Events.**
  - *Contact*: time, position, normal, and speed in and out.
  - *Rest*: by a stated rule, shaped like a spring's. A spring rests when
    displacement and speed are both under 1e-3, found on a 240 Hz grid capped
    at 10 s (`motion/src/spring.rs:53`, `:59`, `:145`). Under gravity, a
    path also rests when the next bounce would rise less than 0.5 pt.
  - *Truncation*: past a cap of, say, 256 events, the path ends at rest and
    says so.
  - The rest rule and the cap are what keep a Zeno bounce finite (LLP 1051
    §5.6).
- **Release velocity.** Every host uses one estimator, the `VelocityTracker`
  that Linux already uses (a weighted least-squares fit over 100 ms). A
  projection magnifies any disagreement in its input. Today Apple and the web
  each estimate velocity their own way (LLP 1051 §3).
- **Output.** `Path { t0, segments, events, rest }`: a value, with the same
  bits on every host.

### D7. Commit the destination, present the path

- **The release handler commits `rest`**, or a decision derived from it, such
  as which bin or which stop. The row's transition names the path:
  `transition="translate path()"`. It is a timing in the same sense that
  `spring()` is: a declared deviation from CSS, lowered on the web.
- **Native hosts evaluate the path at each frame's presentation time.** On
  Apple that means `targetTimestamp`, which its canvases already use. UI motion
  there samples `CACurrentMediaTime()` when the display-link callback runs
  (`host/apple/Sources/ExactKit/Session.swift:920`) and would move to the
  target time with this change. Linux keeps its monotonic clock and paces by
  page flips.
- **The web** samples the path into WAAPI keyframes on the same 240 Hz grid
  that springs use (`spring_frames`, `motion/src/transition.rs:329`). Every
  event time becomes a vertex, so no bounce is smoothed away.
- **Side effects happen at event times.** Contact events reach the runner
  stamped with their time, which makes them deterministic under the agent's
  clock. Hosts may schedule a sound or a haptic at that time instead of at the
  next frame.
- **When a wall changes mid-flight** (a receipt names a node the path depends
  on, or that node's frame changes):
  - The path is solved again from the presented position and velocity at
    that moment, so the velocity stays continuous.
  - The committed rest is then out of date. The host reports the new rest as
    an event, and the app decides whether to commit it. §12 Q1 has the
    alternative.
- **Step independence is the test.** However [0, T] is split into clock
  steps, the presented value at T is bitwise the same on each host. Two
  existing exceptions need fixing or declaring:
  - the runner fires timers one by one, at most 4,096 per call
    (`runner/src/runner.rs:346`);
  - per-frame integrators such as Linux's reorder edge scroll depend on frame
    timing (`host/linux/src/presenter/arrange.rs:408`).

## 6. The web

### D8. The browser answers; the kernel is held to it

- **Batches.** The web's kernel still runs the transaction (it keeps the
  arena under `Kernel::on_demand`), so it produces the forward batch and the
  inverse batch.
- **One task.** The glue gets one import, `what_if(forward, inverse, targets)
  → frames`. Within a single task it:
  1. applies the forward batch to the live DOM;
  2. reads the targets' boxes as the agent's `layout` does;
  3. applies the inverse batch.

  No rendering opportunity falls inside a task, so nothing paints.
  ResizeObserver and IntersectionObserver compare at the next rendering step
  and see no net change.
- **Transitions.** A forced style change can start a CSS transition on a
  property that has one. The glue suppresses transitions on the touched nodes
  for the pass, with an inline `transition: none` that it restores afterwards.
  The web host's own motion runs as WAAPI animations, which a style change
  does not restart.
- **Moving nodes.** Moving a node can blur focus, lose a selection, reset
  scroll positions, restart CSS animations and reload an iframe.
  `Element.moveBefore()` moves a node without those effects in Chrome 133 and
  Firefox 144, but not in Safari. So the glue refuses, by name, any what-if
  that would move a focused, scrolled, media or iframe subtree, and uses
  `moveBefore()` only where the browser has it.
- **Cost.** A forced style and layout of the affected part, budgeted like any
  other handler work.
- **Taffy plus text flow on the web stays out.** That is the Pretext and
  Preflex route: a loaded capability under LLP 1047. It is fast, but it
  answers from a second engine that can disagree with the page. It would come
  back only if what-ifs on every frame of a drag measure too slow on the DOM
  path. Even then it would be a predictor checked against the DOM, never the
  answer of record.
- **Parity.** A fixture corpus asks the web and native hosts the same
  what-ifs, as layout parity already does.

## 7. Consistency and hit testing

- **Answers carry an epoch**, and a stale answer is refused.
- **Paths record the node keys and epoch** they were solved against.
- **Hit testing follows the web.** Browsers hit transformed, animating boxes
  where they are presented, and iOS and Linux already match that. macOS writes
  presented transforms to layers but hit-tests with `NSView.hitTest`, which by
  inference lands on the untransformed frame. That deviation needs a test and
  then a fix.
- **Drop previews keep LLP 1002 D8's rule**: hit-test logical boxes, not
  moving ones.

## 8. Agents

- **Three new forms of `layout`**, not a ninth operation:
  - `layout at +300`: geometry at a clock offset, without moving the clock;
  - `layout settled`: geometry at rest;
  - `layout if <ops>`: geometry under a what-if.

  NOT-DOING §Agent API allows this: "a new question is answered from `tree`,
  `state`, or `layout`."
- **The driver can check two properties**: step independence, and that a
  what-if equals the commit.

## 10. Order of work, if admitted

1. **Kernel `what_if`, stage 1**: the undo journal and the three invariant
   tests. `measure_height_targets` becomes a caller, and its special path is
   deleted.
2. **Stdlib reads and the compiler's refusal**, on native hosts first. The
   first consumer is the sheet.
3. **The web's DOM what-if** and the parity fixtures.
4. **Time**: the engine's velocity read and `at(t)`; `project` with static
   walls and one velocity estimator; `path()` presented at presentation time
   by the native engines and by web keyframes. The consumer is the photo
   release.
5. **Moving walls**: solving again mid-flight, and the rest event.
6. **The agent's `layout` forms.**
7. **Stage 2's overlay tree**, only if a measurement calls for it.

## 11. Alternatives considered

- **A fork per query** (`rehydrate`, commit, lay out). It is simple and exact,
  but it allocates a whole tree per question, which is Jordan's point about
  allocation in Rust. It stays as the test oracle.
- **An overlay beside the write path**, where the engine tree takes the
  overlay's styles directly. It is faster to write, but it re-derives what
  `txn` already derives, which makes it a second implementation.
- **A separate hypothetical engine**, like Flutter's dry layout. It drifts
  (LLP 1051 F3).
- **Geometry in derives**, like container queries. That is the loop (LLP 1051
  §1.3).
- **A physics world**, like UIKit Dynamics or the game add-on's Rapier. It is
  a second owner of frames, and the add-on stays the game's.
- **Per-frame stepping in the engine.** It depends on the frame rate, and it
  tunnels (LLP 1051 §5.4).

## 12. Questions

1. **When a wall moves mid-flight**, should the host report the new rest
   (D7), or keep the committed destination and hand the path over to a spring
   toward it?
2. **Which first consumer**, and what comes off the doing-list for it?
3. **On the web**, is refusing what-ifs that move focused or media subtrees
   enough? Or does D8 need a clone fallback for Safari from the start?
4. **The rest thresholds and the event cap**: fixed in the engine, or
   authored on `path()`?
5. **Obstacles**: should `project` accept anything other than axis-aligned
   boxes (a circle, another ball), or stop at boxes until a consumer asks?
6. **Geometry that changes without an event.** A box that resizes because the
   viewport did gives no handler a chance to read it again. Reflow's balls get
   their court from `exactViewport()` arithmetic for this reason. Should a
   named box's layout change fire an event, the way ResizeObserver does? That
   is an edge-triggered read after layout, but it is also the channel exact1
   paid for (LLP 0488 §3.7), so it would need its own admission.
