# LLP 1051.000: Hypothetical layout — an implementation outline

**Type:** RFC
**Status:** Draft, revised 2026-09-27 after three reviews (§R). This is an outline, not a spec: it names no implementer and no date (`rules/RULES.md` §Scope). §Decision is what Charlie is asked to approve. It is not linked into `llp/current/`, which is at 15 of 15 on origin/main.
**Systems:** Kernel (two reads: published frames, and `measure_height_targets` extended), Contract compiler (geometry reads allowed only in actions), Runner (a layout context for the stdlib, beside the router's), Web host (live DOM reads; one bounded style what-if in the glue), Apple and Linux hosts (the kernel answers)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-27 (first outline 2026-09-25)
**Related:** LLP 1051 (the research: definitions, the survey, the uses, the ball); reviews `llp/reviews/1051-hypothetical-layout.{astra,grok,claude}.md`; LLP 1001 §3, §6; LLP 1002 D4, D8; LLP 1039 D5; LLP 1041 §8.5, §8.12; LLP 1057.001 §3 (one velocity estimator, built); LLP 1063 (`layout-transition`: commit, then read); LLP 1047 (`Kernel::on_demand`); `rules/DEFERRED.md` §Motion and the 2026-09-16 expansion; `rules/RULES.md` §Scope, §Agents

## Summary

LLP 1051 found that systems expose hypothetical layout in four ways:
force-and-read, size questions, lookahead and motion projection. The first
outline (2026-09-25) proposed one mechanism for all four: a kernel
transaction laid out and rolled back, the same edits applied to the live DOM
and reverted on the web, and closed-form paths for the time axis.

Three reviews agreed with the direction and found the mechanism wrong (§R).
Rolling back through the kernel's write path doesn't restore the arena. A
forward and inverse batch through the web host is not a no-op. The runner
can't produce the hypothetical tree an action would ask about. The time half
is a physics engine that no named consumer needs yet.

This revision keeps what all three agreed on and narrows v1 to it:

- **v1: two read-only geometry reads, from actions only.**
  - `frame(id)`: where a node is now, as last laid out and shown.
  - `measure(id)`: the node's border-box height if its `height` were `auto`,
    under the offer it has now.
  - The compiler refuses both anywhere but an action (LLP 1039 D5).
  - Each is answered by the engine that commits: the kernel on native hosts,
    the browser on the web. Neither writes the committed tree.
  - An answer says when it is provisional or unavailable, instead of
    guessing.
- **The first consumer is the sheet.** Its stops come from geometry instead of
  180, 360 and 640, which also fixes the 562.79 pt clamp on AppKit (§3).
- **The rest waits for a consumer** (§4): hypothetical trees, the time half
  (`at(t)`, `path()`, contacts, moving walls), the agent's new `layout` forms
  and the overlay tree.
- **Two pieces landed elsewhere since the first outline.** LLP 1057.001 §3
  made one release-velocity estimator the rule. LLP 1063's
  `layout-transition` animates a layout move by committing and then reading,
  which is the commit-as-lookahead pattern the Claude review proposed.

| Read (names illustrative) | Axis | v1 | Answer |
|---|---|---|---|
| `frame(id)` | — | yes | The frame as last laid out and shown |
| `measure(id)` | Constraint | yes | A border-box height, as if `height: auto` |
| `whatIf(edits).frame(id)` | Tree | waits (§4.1) | A frame under a hypothetical state |
| `at(t).frame(id)` | Time | waits (§4.2) | A frame and its velocity |
| `project(body, release, walls)` | Time | waits (§4.2) | A path: segments, events, rest |

## 1. What v1 builds on

| Exists today (verified at origin/main `c1b01a13`) | In v1 |
|---|---|
| Published frames (`Kernel::compute_layout`, `kernel/src/kernel.rs:479`) | The native answer to `frame` |
| The agent's `layout` read on the web: every connected view's `getBoundingClientRect()`, in the viewport's space with scroll offsets and transforms folded in (`host/web/glue.js:1112`) | The web answer to `frame`; the same definition native hosts compose to |
| `Kernel::measure_height_targets` (`kernel.rs:564`): removes live height projections, calls `engine.compute` without publishing, reads border-box heights, restores the projections | The native answer to `measure`, extended from `auto`-authored targets to any border-box target (D3) |
| The engine's derived-style swap (`LayoutTree::set_style`, `kernel/src/layout.rs:398`), which `present_heights` uses | How the extension overrides one node's height without touching the arena |
| The content-region refusal (`layout_root_slot`, `kernel.rs:638-642`) | Kept: native `measure` is unavailable while a region is registered |
| The collection glue's anchoring guard (`overflowAnchor = "none"` around a size change, `host/web/collection-glue.js:371`) | The pattern the web's `measure` follows (D4) |

Two things the first outline built on are no longer in v1:

- **`txn::apply` as a what-if path.** It is a commit, and a replayed inverse
  does not restore it (§R1).
- **The web host's `apply` for a what-if.** It commits effects that an inverse
  batch cannot undo (§R3).

## 2. v1: geometry reads from actions

### D1. Two reads, and what each one means

- **`frame(id)`** is where the node is now, as last laid out and shown:
  - its layout box, composed with any presented paint-only motion and
    `layout-transition` offset;
  - in the viewport's space, with scroll offsets folded in;
  - the agent's `layout` definition on the web (`glue.js:1112`). Native hosts
    compose the kernel's published frames with motion's presented values at
    the handler's time.
- **`measure(id)`** is the node's border-box height if its authored `height`
  were `auto`, with presented heights removed and every other style kept,
  under the offer the node has now. `max-height`, padding and borders still
  apply. For the sheet it answers "how tall would this sheet be at its
  natural height, inside the room it has?".
- **Which layout a read sees.** Every read in a dispatch sees the layout that
  was last laid out and shown before the dispatch began. It does not see the
  dispatch's own writes.
  - The web host applies a dispatch's batch after wasm returns, and `advance`
    folds every timer that falls due into one batch (`host/web/src/host.rs`,
    `advance` and `batch_for`). A mid-dispatch DOM read therefore sees the
    state before the dispatch.
  - Native reads use the published frames, which match.
  - Flushing a partial batch mid-dispatch would give the web a view native
    doesn't have. It is the half-applied state the glue's `apply` exists to
    avoid (§R3).
- **Neither read commits.** Native reads write no arena state (§R1). The
  web's `measure` restores what it writes within the task (D4, §R3).

### D2. Allowed only in actions

- **The layout context.** The runner passes a layout context to
  `stdlib::call`, beside the router's (`runner/src/stdlib.rs`). Native hosts
  back it with the kernel; the web host backs it with the glue (D4).
- **Only in actions.** The compiler refuses these calls outside actions
  (`contract/analyze`). In a derive, a view expression or a resource argument
  they are an error that names LLP 1039 D5. They are calls, not new syntax.
- **No answer outlives its handler.** A read's value may be written to state
  as a number, but no answer object is held, so v1 needs no staleness check.
  The layout generation the reviews ask for (§R4) comes with the first
  consumer that holds an answer, which is the time half.

### D3. Native: the kernel answers

- **`frame`** reads the published frames and composes presented motion, as
  hit testing on iOS and Linux already does.
- **`measure`** is `measure_height_targets` extended.
  - Today it only answers targets whose authored height is `auto`: removing
    the projections leaves `auto`. For a numeric `height`, such as the sheet's
    `sheetPx`, it would return the authored number.
  - The extension overrides the target's derived height to `auto` in the
    engine tree, the way `present_heights` swaps in a sampled height.
    It lays out without publishing and restores the derived style. The arena,
    the epoch, receipts and text revisions are never written.
  - Its cost and its cache trade are today's: the dirty path is laid out, and
    the next real layout recomputes it once. The existing invariant tests
    (`kernel/tests/it/presented_height.rs`) extend to a numeric target.
- **Unavailable** when a content region is registered: ordinary layout is
  refused then (`kernel.rs:638-642`). Routing a size read through the region
  trial waits for a consumer on such a screen (§R5). `frame` still answers
  from the region's published frames.

### D4. The web: live reads, and one bounded what-if

- **`frame`** is a live read, as the agent's `layout` does it.
- **`measure`** is a style what-if on one existing node. It never goes
  through the host's `apply`, which commits: it writes `localStorage`
  (`glue.js:639`), tears down editors and media on destroy (`:740`) and writes
  scroll offsets (`:779`). The glue does the following within one task, so no
  rendering opportunity falls inside it:
  1. **Refuse** with `unavailable` if the node or an ancestor is animating a
     layout-affecting property (`Element.getAnimations()`). Easing transitions
     are CSS transitions on the web (`host/web/src/css.rs:59-68`), and a forced
     style after an inline write cancels a running one (CSS Transitions).
     A running WAAPI animation would override the write instead.
  2. **Snapshot** the node's inline `height` and the scroll offsets of its
     scrollable ancestors. Set `overflow-anchor: none` on those ancestors for
     the pass, as the collection glue does.
  3. **Write** `height: auto` and read `getBoundingClientRect().height`.
  4. **Restore** the inline value, the anchoring and the scroll offsets
     exactly.
- **What sees the pass.** Only this node's `style` attribute is written.
  - The glue's one attribute observer filters on `data-action`
    (`host/web/gpu-glue.js:427`).
  - App data modules run in a private realm, an iframe or a worker
    (`host/web/module-glue.js:1`, `:106-107`), not against the page.
  - ResizeObserver and IntersectionObserver compare at the next rendering
    step and see no net change.

  So no observer sees the pass.
- **No second engine.** Taffy plus text flow on the web, the Pretext and
  Preflex route, stays out. It would answer from an engine that can disagree
  with the page (LLP 1051 F6).
- **Parity.** A fixture corpus asks web and native hosts the same `frame`
  and `measure` reads, as layout parity already does. It includes a dispatch
  in which two timers fall due, to hold D1's "last shown" rule.

### D5. Provisional and unavailable answers

An answer comes with two flags instead of an estimate presented as exact.

- **`provisional: true`** when an input the answer depends on has not
  settled:
  - a replaced element in the measured subtree has no intrinsic size yet, and
    so lays out at 0×0 (`kernel/src/layout.rs:861-872`); on the web, an
    `<img>` with `complete` false or `naturalWidth` 0;
  - a paragraph's height is an estimate. On macOS a paragraph of 64 KiB or
    more gets an estimated height, marked pending
    (`host/apple/Sources/ExactKit/Mac/RegionReaderMac.swift:441`, `:128`,
    `:144`). The native measurer gains a way to say so. On the web the
    signal is `document.fonts.status` not being `"loaded"`.
- **`unavailable`** when the host can't answer exactly:
  - an unknown or unrealized id;
  - a registered content region (native `measure`);
  - a running layout animation (web `measure`).
- **How a caller learns more.** The action tests the flags and decides, for
  example by keeping its old stops. It can ask again at its next handler.
  v1 adds no event that fires when geometry settles. That would be the
  edge-triggered channel exact1 paid for (LLP 0488 §3.7), and it needs its own
  admission (§5 Q2).
- **The epoch is not the freshness signal.** `set_intrinsic_size`, `set_env`
  and `invalidate_text_metrics` change layout without bumping it
  (`layout.rs:398-400`). No v1 answer is held, so this only matters for the
  deferred consumers (D2).

## 3. The first consumer: the sheet

The interaction gallery's sheet projects `height + velocity · 0.15` onto
hard-coded stops of 180, 360 and 640 (`apps/interaction-gallery/app.contract:86-87`).
Its column has `max-height="100%"` (`:187`), so on an AppKit drive the tallest
stop lands at 562.79 pt (LLP 1041 §8.12). A sketch with its stops taken from
geometry, where the names and the list literal are illustrative and not
proposals:

```
action snapSheet(height: number, velocity: number) writes sheetPx
  sheetPx = nearestStop(height + velocity * 0.15,
                        [180, measure("reading-sheet").height, frame("sheet-bay").height])
```

- **The tallest stop becomes the room the sheet has,** and the middle stop its
  natural height.
- **The projection stays the app's own.** v1 adds no `projectFling` with
  UIKit's 0.998 constant, and so no decay law (§R6).
- **When the sheet asks.** At release, the sheet has been following the
  finger, not springing, so the web's refusal during a running animation
  (D4) should not bite. The implementation confirms that on each host.
- **Pagers are not this consumer.** A horizontal pager is a scroll container,
  and CSS scroll snap is already admitted for it (`kernel/tables/schema.json:2229-2234`).
  The iOS host projects flings against snap positions taken from layout
  (`host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift:704-718`). A pager needs
  no new API (§R7).

## 4. What waits for a consumer

Each of these is recorded with what the reviews found it would need, so that
the consumer that asks for it starts from there.

### 4.1 Hypothetical trees

This is the tree axis: a node's frame under a hypothetical state (reparenting
before a commit, a reorder over unmounted rows, the next route).

- **Consumers that would need it:**
  - reorder previews over unmounted rows;
  - photo zoom's return to an unmounted source (LLP 1041 §8.5, owed).
  - Animating a move after it is committed does not need it: LLP 1063's
    `layout-transition` commits and then reads, with FLIP on the web.
- **The runner has to realize a state without committing it.** An action
  writes state, not ops.
  - The runner's `update` mutates the instance tree and the id allocator
    before it applies kernel ops, and a failure poisons the runner until the
    host restarts it (`runner/src/runner/lists.rs:133-160`).
  - A bounded, side-effect-free realization from available data is the
    requirement. The precedent is the read-only realization of virtual rows
    (`runner/src/instance/text.rs`).
- **The kernel pass must not write the committed arena.** An undo journal
  through `txn::apply` cannot restore it:
  - `alloc` pops the free list and bumps the slot's generation;
  - `free_slot` wipes the node's columns (`kernel/src/arena.rs:642-720`);
  - `revise_text` advances a monotonic serial that the host measurer caches
    on (`arena.rs:415`);
  - `Kernel::apply` bumps the epoch, keeps a receipt and notifies a content
    region (`kernel.rs:318-355`).

  A handler-time question forks with `rehydrate` (`kernel.rs:875`). A
  drag-time question needs a side tree. The host measurer must also be safe
  to speculate with: on macOS, measurement can replace live paragraph owners
  (Astra #2).
- **The web has no inverse batch.** Nodes not in the document (unmounted
  rows, the next route) have no browser layout until they are inserted. An
  isolated measurement tree helps only where its layout context can be
  reproduced (Astra #1).

### 4.2 Time

This covers `at(t)` and velocity reads, `project`, `path()` presented at
presentation time, contact and rest events, and walls that move mid-flight.
The first outline's D5–D7 move to a follow-up RFC.

- **The consumer that would need it** is the photo viewer's release, the ball
  in a box. `releasePhoto` still drops `vx` and `vy`
  (`apps/interaction-gallery/app.contract:301-304`).
- **A static wall needs no more geometry than v1 gives.** The release handler
  reads the committed frame, and the path against it is a closed form
  (Grok #3). Presenting that path is still the driver below.
- **Moving walls need three more things:**
  - a layout generation that every layout input bumps;
  - notice that geometry changed (§5 Q2);
  - bounds on how fast layout can move a wall. A central difference of two
    samples is not one: Taffy's flex-shrink distribution is not linear in an
    authored height, and text wrapping jumps (Astra #5).
- **It moves `rules/DEFERRED.md`'s "Decay and sequence drivers" line**, since
  `path()` is a decay-and-contact driver. That needs a consumer and a take.
- **Release velocity is settled already**: LLP 1057.001 §3's `VelocityTracker`,
  wherever the platform measures none.

### 4.3 Agents and the overlay tree

- **Agents:** `layout at +300`, `layout settled` and `layout if <ops>` wait for
  the time half and the tree axis. Until then `layout` answers committed and
  presented geometry at the current clock, as it does now.
- **The overlay tree** (the first outline's stage 2, Taffy's low-level traits
  over the columns) waits for a drag-time what-if that measures too slow on a
  fork.
- **Hit testing is unchanged by v1.** The macOS deviation LLP 1051 §3 infers
  (`NSView.hitTest` on untransformed frames) needs a test either way; it is
  independent of this outline.

## 5. Questions

1. **Which reading of the admission** covers v1: see §Decision.
2. **A geometry-change event.** A box that resizes because the viewport did
   gives no handler a chance to read it again, and a provisional answer
   settles with no event either. Reflow's balls get their court from
   `exactViewport()` arithmetic for this reason. An edge-triggered read after
   layout, as ResizeObserver does, is the channel exact1 paid for
   (LLP 0488 §3.7), so it needs its own admission. v1 does without it.
3. **Width.** Should `measure` take an offer (a width) in v1? No consumer asks
   yet, so it doesn't.

## 6. Alternatives considered

- **An undo journal through `txn::apply`** (the first outline's stage 1). Its
  writes are commits that a reversed replay doesn't restore (§R1). Kept out.
- **A forward and inverse batch through the web host's `apply`** (the first
  outline's D8). It commits effects, cancels transitions and moves scroll
  (§R3). Kept out.
- **A fork per query** (`rehydrate`, commit, lay out). It is exact, and costs
  a tree per question. It is the path for hypothetical trees when a consumer
  arrives (§4.1), and the test oracle.
- **An overlay beside the write path**, where the engine tree takes an
  overlay's styles directly. For one node's height this is what `measure`
  does, by the existing derived-style swap. For general edits it would
  re-derive what `txn` derives: a second implementation.
- **A separate hypothetical engine**, like Flutter's dry layout. It drifts
  (LLP 1051 F3).
- **Geometry in derives**, like container queries. That is the loop
  (LLP 1051 §1.3).
- **A physics world**, like UIKit Dynamics or the game add-on's Rapier. It is
  a second owner of frames.
- **Per-frame stepping in the engine.** It depends on the frame rate, and it
  tunnels (LLP 1051 §5.4).

**Where the reviews disagreed (R1).** The Claude review found the rolled-back
transaction workable if rollback restores the exact `NodeKey`s, or expresses
removal as detaching, and never reuses a paragraph revision. It would keep the
transaction for constraint questions on existing nodes and for agents'
`layout if`. Grok would never mutate the committed arena. It would fork with
`rehydrate` for a handler-time question and use a side tree for a drag-time
one. Astra found the journal reasonable but not enough, because the host
measurer is not pure.

This revision takes Grok's position, for three reasons:

- The invariant that nothing moves is simple to guarantee only if the
  committed arena is never written.
- The generation, free-list and text-serial effects are real, and all of them
  sit on the commit path.
- No v1 consumer needs a tree what-if. The one constraint question v1 asks
  (`measure`) is served by the derived-style swap that `measure_height_targets`
  already uses, which writes no arena state.

**What all three got right, and this revision keeps:**
- one engine per host, with the browser as the oracle on the web;
- geometry reads in actions only;
- continuous channels on paint-only rows;
- `measure_height_targets` as the seed;
- no second engine on the web except as a checked predictor;
- the committed, presented and hypothetical vocabulary.

## Decision

**Charlie is asked to approve:**

- **v1:** `frame(id)` and `measure(id)` as stdlib reads, allowed only in
  actions and refused by the compiler everywhere else.
  - Native hosts answer with the kernel's published frames and with
    `measure_height_targets` extended to numeric-height targets.
  - The web answers with a live read and one guarded style edit.
  - Answers carry `provisional` and `unavailable`, and parity fixtures hold
    the hosts together.
- **The first consumer:** the interaction gallery's sheet, with its stops
  taken from geometry.
- **When it's built:** this outline becomes a spec with an implementer and a
  date (`rules/RULES.md` §Scope).

**Which `rules/DEFERRED.md` line it moves** depends on one reading, which is
Charlie's:

- The 2026-09-16 expansion admits "the bounded geometry/motion work those
  consumers need" for the four interactions. The draggable sheet is one of
  them. If that covers a general read surface whose first user is the sheet,
  v1 moves **no line**.
- If it doesn't, v1 is new doing-list work and needs a take or a waiver
  (`rules/RULES.md` §Scope).
- Either way, the §Motion lines stay: no gesture arena, no second value
  graph, no general layout transitions beyond those admitted, and no decay
  driver.

**What v1 deliberately leaves out:**
- hypothetical trees: no answers about reparenting before a commit,
  unmounted rows or the next route;
- the time half: no `at(t)`, `path()`, contacts, rest events or moving walls,
  so DEFERRED's decay-driver line stays;
- the agent's new `layout` forms;
- the overlay tree;
- an event that fires when geometry changes;
- a size question at a different width;
- a second layout engine on the web.

Each waits for a named consumer. §4 records what the reviews found each would
need.
