# LLP 1054.000.000: Declared refreshes and kept requests

**Type:** RFC
**Status:** Draft
**Systems:** Contract language (`mutation … refreshes`), plan format (`mutations.refreshes`), runner (settlement's forced set, request book-keeping)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-26
**Related:** LLP 1054 D2, D3 (the findings); LLP 1054.000 §Deferred (the constraints both reviews set); LLP 1016 D3–D5 (requests, re-asking, the newest arguments win) — amended here; LLP 1027 (sources in Rust and TypeScript); reviews `llp/reviews/1054.000-*`

## Summary

R1 and R2 of LLP 1054.000, designed together as both reviews asked.

- **R1 becomes a declaration.** `mutation dm as shape Msg refreshes chats,
  convos` says that sending `dm` changes what those resources would answer.
  From the send, the write shows in them through the data module's
  `overlay`, and nothing is asked. In the commit where the reply lands, the
  runner *refreshes* them, forced, as `refresh` does. The invalidation shows
  in the plan and in `state`.
- **R2 keeps a request only when nothing but the arguments moved.** If a
  resource is re-asked because its arguments changed, not forced, and the
  source hands back a request equal to the one in flight, the runner keeps
  that ticket. It sends nothing and parses the reply with the new
  arguments. A forced re-ask never keeps a request (`refresh`, a declared
  refresh, `data_ready`, delivery facts), and neither does a store-revision
  re-ask or any request carrying a continuation, storage or surface
  operation.

## Motivation

The Bluesky port threaded a `rev` state through eight resources as an
unused argument, bumped in five actions and again by a timer action that
polled mutation stamps. It forgot twice (LLP 1054 D2). `apps/realworld`
does the same with `changeStamp`/`authStamp`. The re-ask that D3 describes
cost a duplicate fetch whenever an argument moved during a load. The
common triggers are a `clock` argument when the date arrives, and a page
count on `reachend`.

## Design

### D1 — `refreshes` on a mutation

```
mutation dm as shape Msg refreshes chats, convos
```

The names must be resources of the same component, each at most once
(`type-refreshes-not-resource`, `type-refreshes-duplicate`). The plan's
`mutations` row gains `refreshes: range:mutation_refreshes`, whose rows
name a resource.

A send to the mutation is a write the runner records. Two things follow:

1. **From the send: the overlay.** The send asks the named resources
   nothing. While the write affects one of them, derives and views read the
   data module's overlay of it over that resource's answer
   (`DataSource::overlay`, a module's `overlay` export), until the first
   answer asked after the reply landed, unless the overlay keeps it over that
   answer (`keep`). A write that ends without landing stops showing at once,
   and the resource is asked again. A worker placement, which cannot be
   called synchronously, shows answers only.
2. **When the mutation's reply lands: a refresh.** When `fulfill` parses a
   value (`parse_for` answers `Now`), the named resources are forced in
   that same commit, as `refresh r` forces them. A reply that asks for one
   more round (`Later`) refreshes nothing until the last one.

*Why an overlay and not an ask at the send:* an answer the runner started at
a send and then discarded would run on after the runner let it go, its effects
with it, and a network-backed source would read the server before the write
landed. The overlay shows the write without starting an answer, and can show
rows a write adds or removes.

*Why the mutation and not the resource:* the author knows what a write
changes where the write is declared. "Forgot to bump `rev` in this action"
cannot happen, because every send to `dm` refreshes the same list.

*Why not `DataSource::changed()`:* it would have to cross every forwarder,
both module ABIs, worker envelopes and TypeScript, survive checkpoint and
restore, and it hides dataflow from the plan. The overlay crosses the same
seams, but it shows a write correctly whatever a source keeps in its own
memory, and the declaration keeps the dataflow in the plan.

The runner and the web JS target implement it in
`runner/src/runner/writes.rs` and `host/web-js/overlay.js`;
`contract/cli/tests/it/overlay.rs` is the lifecycle.

### D2 — the forced set is merged and kept, not overwritten

`refresh_next` was assigned from an action's `refresh` statements,
overwriting what a recommit had put there, and entries for a resource not
asked in that settlement (an argument still pending) were dropped. Now:

- An action's `refresh`es and its sends' declared refreshes are
  **added**.
- An entry that settlement did not consume stays for the next settlement.
  A resource whose argument is pending is still refreshed once it can be
  asked.

The checkpoint already covers `refresh_next`, so a refused commit restores
it (Astra, concern 1).

### D3 — keeping an identical request (amends LLP 1016 D5)

LLP 1016 D5 says the newest arguments win and a replaced request's reply is
dropped. Amended: when settlement re-asks resource *r* and every one of
these holds, the in-flight ticket is **kept**:

- *r* is not forced in this settlement;
- *r* has a ticket in flight, which the host has not refused at admission;
- the new arguments differ from that ticket's (so this is not a
  store-revision re-ask, whose server state may have moved);
- the source answers `Later` with a request **equal** to that ticket's
  (`Request`'s derived equality: method, URL, headers, body, scheduling,
  grants, and no continuation, storage or surface operation on either).

The ticket's arguments become the new ones. The reply is parsed with them,
which is what "the newest arguments win" means, and the kept value is
recorded against them, so the next settlement reuses it. The runner journals
`keep request N (r): the same request for newer arguments` and sends
nothing. A source that parks calls (the TypeScript module) has just parked
one for the new arguments. The runner reports `forgotten` with the kept
ticket's new arguments, so the source drops the call parked under the old
ones and keeps the new, as for any replacement.

Mutations never keep. A send is a new effect even when its bytes match.

*Why only argument-caused:* a forced or store-revision re-ask means "the
answer may be different now". A request issued before that point can
carry an answer from before it, which is the staleness both reviews
described (R1's refresh satisfied by a pre-mutation GET).

*Why the request must match exactly:* a changed header (a refreshed
token) or body is a different question.

## Costs

- Plan format: one table and one field; the format digest changes, so a
  plan built before this is refused at load as any older format is.
- `PendingReq` keeps a copy of a keepable request (HTTP only). Checkpoints
  clone it; a GET is small.
- No new Contract vocabulary beyond `refreshes`. The data seam gains
  `overlay`, through every forwarder, both module ABIs and TypeScript.

## Tests

- Runner: a send asks its declared resources nothing (an overlay shows the
  write) and refreshes them at the reply; a network-backed one keeps its
  load in flight, then fetches, forced, at the reply; a refused commit restores the forced
  set; a resource whose argument is pending is refreshed when it can be
  asked.
- Runner: an argument change with an equal request keeps the ticket (one
  request, parsed with the new arguments); a forced re-ask, a
  store-revision re-ask, a changed header, a refused ticket and a mutation
  do not keep.
- Compiler: `refreshes` naming a non-resource or a duplicate refuses; the
  formatter prints it.
- Consumers: the Bluesky port drops `rev`, and RealWorld drops
  `changeStamp`/`authStamp` where they only re-ask.

## Open questions

1. Should `refreshes` also be allowed on a `resource` (refresh B when A's
   answer changes)? Not proposed; derive arguments already express it.
