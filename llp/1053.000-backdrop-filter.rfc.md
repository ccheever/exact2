# LLP 1053.000: CSS `backdrop-filter`, by its web name

**Type:** RFC
**Status:** Accepted (Charlie, 2026-09-27: the rulings in §4); implemented on `feat/backdrop-pre`
**Systems:** Kernel (`backdrop_blur` row's grammar, `kernel/src/style/backdrop.rs`; the `materials` table in `schema.json`), Contract (`tags.rs`), web (`css.rs`, `index.html`), Apple (`Backdrop.swift`, the node views' material path), Linux (both painters, `exact_svg_raster::backdrop_blur`)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-27
**Related:** LLP 1053 (the list benchmarks' gaps; this is the Extra Heavy feed's gap 5, `~/bench/xheavy/EXACT2-GAPS.md`), LLP 1001 §1 and "Platform background materials" (the declared deviations; `backgroundMaterial`), LLP 1064 (box-shadow: one CSS value, rows take their part), LLP 1055.000 D14 (SVG `filter`, whose blur this shares on Linux), `CLAUDE.md` ("the web is the standard")

## Summary

The kernel has carried a `backdrop_blur` row (bit 62) since v1, and the web host has always emitted it as `backdrop-filter: blur()`. Contract never named it, so the only glass an app could write was the host-policy prop `backgroundMaterial="ultra-thin"`. The feed's glass row is written the web's way, so Contract now takes `backdrop-filter` with CSS's grammar, and each host draws it as close to Chrome as its public API allows, with the distance measured. Beside it, `backgroundMaterial` becomes the full platform vocabulary: every material UIKit and AppKit offer, by name (D4).

## 1. Decisions

**D1. Grammar: `none`, or one `blur(<length>)`.** The length is the Gaussian's standard deviation in `px` (unitless zero; `blur()` is zero), as CSS's. It lands in the existing `backdrop_blur` row; no row is added. Everything else CSS allows is refused by name, at compile time for a literal and at run time for a computed string, with the same text: `saturate()`, `brightness()`, `contrast()`, `grayscale()`, `hue-rotate()`, `invert()`, `opacity()`, `sepia()`, `drop-shadow()` and `url()` each say "is CSS, but exact2's `backdrop-filter` builds only `blur()`"; a second `blur()` is refused. Why only blur: it is what the consumer uses, and it is the one function each native host can draw. `saturate(180%)`, the web's usual partner, has no Apple mapping outside a material, which already saturates.

**D2. Per host:**
- **Web:** native. The row is emitted as `backdrop-filter: blur(Npx)`, and `none` as `none` (a `blur(0px)` would make a backdrop root).
- **Linux:** the CPU painter reads the pixels painted so far under the border box (the current layer, so an opacity group is its own backdrop, as CSS's backdrop root is), blurs them with the SVG island rasterizer's Gaussian (Filter Effects' three box blurs, over encoded sRGB as Chrome blurs, edges mirrored as Chrome's backdrop reads them) and writes them back inside the rounded box under the current clip. The GPU painter cannot read its own frame mid-scene, so a backdrop flushes: the scene so far is rendered and read back, the patch is blurred on the CPU by the same function, and the scene restarts from that frame as an image with its open clip and opacity layers pushed again. The node's background and border paint over the blur, as CSS orders them.
- **macOS:** Core Image's `CIGaussianBlur` as the node layer's public `backgroundFilters`, between `CILinearToSRGBToneCurve` and `CISRGBToneCurveToLinear`: Core Image blurs linear light, Chrome blurs encoded values, and without the curves the measured σ is 1.22 times too wide. With them the edge case measures σ = 8.00 against Chrome's 8.00 (4.03 and 16.02 for 4 and 16).
- **iOS:** UIKit has no public arbitrary-radius backdrop blur. `backgroundFilters` is macOS-only and `CABackdropLayer` is private. A blur therefore draws as the node's material view with `UIBlurEffect(style: .light)`, whatever σ is. Nearest-by-radius was measured and does not discriminate: every system material blurs with its own Gaussian of σ ≈ 19–33 pt (edge fit on the iOS 27 simulator), so the choice is by pixels against Chrome, where `.light` is nearest in every case, the tinted glass included (§4, ruling 1). r1 drew ultra-thin.

**D3. `backgroundMaterial` stays the host-policy spelling, not sugar.** A material is a semantic request (the platform's blur, tint, vibrancy, Reduce Transparency, glass on iOS 26 and macOS 26); `backdrop-filter` is a pixel request. Making the material sugar for `blur(20px)` would lose the first; making the blur sugar for a material would lose the second where it can be had (web, Linux, macOS). Where a node has both, the material wins on every host: Apple builds the material view and skips the filter, Linux paints the material's approximation instead of the blur (D4), and the web's material rule is `!important` over the inline `backdrop-filter`.

**D4. `backgroundMaterial` is the full platform vocabulary** (Charlie, 2026-09-27: "also give you some way to pick which one, in the spirit of exposing the full capabilities of the platform"). `backdrop-filter` is the portable, pixel-oriented request; `backgroundMaterial` names a platform's own material, every one it has, one-to-one in kebab case. There is no web-standard name for this, so the spelling stays.
- **The table** is `kernel/tables/schema.json`'s `materials`, the one authority: per name, the iOS `UIBlurEffect.Style` (or `UIGlassEffect` style), the macOS `NSVisualEffectView.Material` (or `NSGlassEffectView` style), and the web's and Linux's stated approximation (blur px, web `saturate()` %, a tint per scheme). `kernel/build.rs` generates `MATERIALS` and `material(name)`; Apple reads the platform names through `exact_material_platform`, and an XCTest per platform holds every row to a style the platform draws.
- **Compile time:** a literal name the table lacks is refused, listing the names.
- **Run time:** a computed name the table lacks draws `ultra-thin` and is logged once. A name a platform lacks (`~` in its column: `sidebar` on iOS, `ultra-thin` on macOS) draws the named stand-in silently (Charlie, 2026-09-27: "ok, (b)": the table's names are the standard cross-Apple ones, and `ultra-thin` drawn as `popover` on every macOS launch is not news). The agent's `state` shows it: `native.material` is `{name, drawn, standIn}` (`unknown` for the fallback) on iOS and macOS.
- **Web and Linux** draw the approximation: the web from CSS variables the host sets (`element.rs` `material_css`) under one `[backgroundMaterial]` rule; Linux blurs the backdrop by the table's σ and fills the tint where the author painted no background (an authored `background-color` paints instead, as the web's inline style beats the rule). They are approximate by declaration: the named look is Apple's.

## 2. What was built

- `kernel/src/style/backdrop.rs`: the grammar; `StyleValue::f32` routes `BackdropBlur` through it; `StyleValueError::BadBackdropFilter` carries the reason. Contract: `"backdrop-filter" => BackdropBlur` in `tags.rs`.
- Web: `css.rs` emits `none` for zero; `index.html`'s material rules are `!important`.
- Apple: `Backdrop.swift`; iOS's `updateMaterial` takes a `backdrop` kind (a `BackdropEffectView`); macOS's `updateMaterial` ends in `applyBackdrop()`. The agent reports the effect (`native.effect` is `backdrop` on iOS, `backgroundFilters(CIGaussianBlur)` on macOS).
- Linux: `Backend::backdrop_blur` (default no-op); `raster/backdrop.rs`; `gpu/backdrop.rs` with the open-layer record; `BoxPaint` carries σ, content-region pictures replay it, and a backdrop node takes a frame off the flow-damage path.
- Materials (D4): the `materials` table and its generator; Contract's refusal; `exact_material_platform` and `Materials` in `Backdrop.swift`, both node views' material paths; the web's `material_css` and one `[backgroundMaterial]` rule; Linux's `BoxPaint` material capture and a once-per-name log. `scripts/fixtures/materials.contract` and Chrome's `materials.web.png`, held by `host/linux/tests/pinned/materials.rs`; `MaterialTableTests` / `MaterialTableIOSTests` hold every row to its platform.
- Parity page `scripts/fixtures/backdrop.contract` and Chrome's picture `backdrop.web.png` (the web host at 1×); `host/linux/tests/pinned/backdrop.rs` holds both painters to it.

## 3. Parity and declared deviations

Mean absolute difference per channel (0–255) over each box, 2 px inset, and the share of pixels with a channel more than 48 off, against Chrome's picture. Apple captures are window/screen captures converted from the display profile to sRGB and box-downsampled to 1×; the `none` control measures the capture's own error.

| Case | Linux CPU | Linux GPU | macOS | iOS (`.light`) |
|---|---|---|---|---|
| `blur(4px)` | 0.95, 0% | 0.95, 0% | 1.2, 1% | 58.7, 73% |
| `blur(20px)` | 1.61, 0% | 1.61, 0% | 9.4, 9% | 44.8, 61% |
| glass: `blur(20px)`, radius 16, `#ffffff80` | 1.00, 0% | 1.12, 0% | 1.5, 0% | 18.0, 0% |
| `blur(8px)` across a black/white edge | 0.40, 0% | 0.40, 0% | 0.0, 0% | 52.4, 49% |
| `none` (control) | 0.00 | 0.00 | 0.1 | 0.0 |

The Linux test's band is the border page's (mean ≤ 2, ≤ 2% beyond 48). The Apple numbers are recorded, not checked: an XCTest's `layer.render(in:)` draws neither a material nor a background filter, so only a composited capture sees them.

**Declared deviations:**
- **iOS** draws `UIBlurEffect.Style.light` for `backdrop-filter`: its own blur (σ ≈ 30 pt at the edge fit) and its tint, whatever σ is asked, and it does not follow the appearance. Bound: the table's iOS column (measured on this branch's iOS 27 simulator; Charlie's probe on an iPhone 17 Pro simulator agrees, §4). The feed's glass (a tinted blur 20) is its best case.
- **`backgroundMaterial` on the web and Linux** is an approximation of Apple's look (D4). Linux draws no `saturate()` and no glass rim; `scripts/fixtures/materials.contract` (a grey backdrop, so saturation is moot) holds both Linux painters to Chrome within the border band (worst mean 0.97/255).
- **macOS** puts a material's view over the node's own layer, so an authored `background-color` under a material does not show (the web, iOS and Linux paint it over the blur). An AppKit material in an inactive window draws flat, as AppKit's `followsWindowActiveState` does.
- **macOS** filters a layer's backdrop only when the layer masks to its bounds, and the backdrop it sees is the superlayer's subtree: the parent's own paint and the earlier siblings' subtrees. So a backdrop node clips its children to its border box, and what an ancestor above the parent paints under the box shows through unblurred. Where the backdrop lies in the parent (the feed's glass over its photo; every case on the parity page) it is Chrome's σ. Core Image reads past the box where Chrome mirrors the box's edge, which is `blur(20px)`'s 9.4. Differing corner radii take the smallest.
- **Linux GPU** renders and reads back the frame once more per backdrop node per frame, and composites an opacity group's content drawn before a backdrop early.
- Every host: one `blur()` only (D1), and `backdrop-filter` does not animate (no transition or keyframe carries the row).

   | light | 58.7 | 45.2 | 18.7 | 52.1 |

   `light` is nearest in every case, the tinted glass included. `backgroundMaterial` keeps its own mapping (D4); only `backdrop-filter`'s iOS lowering changed.
2. **Linux `backgroundMaterial`:** "rec is good". Linux paints it as the web does, a blur plus a tint, through the backdrop blur built here (D4's table), instead of leaving it transparent.
3. **The vocabulary:** "also give you some way to pick which one, in the spirit of exposing the full capabilities of the platform": D4.
4. **Stand-ins are not logged:** "ok, (b)". Only a truly unknown (computed) name is logged, once; D4.
