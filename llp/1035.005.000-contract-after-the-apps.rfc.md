## Summary

Keep Contract's basic model: pure view expressions, explicit actions, resources
for reads, mutations for occurrences, and one source across hosts. The apps show
where its restrictions now create bookkeeping rather than useful boundaries.
That bookkeeping has three causes, and each wants a different remedy.

1. **The source restates what the compiler already knows.** 553 actions carry
   1,304 `writes` names. Interview provides 57 names to one component through a
   57-deep `provide` staircase. 57 inline `match`es only read a field of an
   option, with a default. Remedy: infer or abbreviate (D1, D9, D10).
2. **Apps rebuild request identity by hand.** Four apps run one polling action
   whose main job is to notice that an answer landed: RealWorld every 100 ms,
   Bluesky and Interview every 250 ms, Messages every frame. Others tag answers
   with the screen that asked, or pass revision counters as arguments. The
   runtime already has most of the answer (newest-wins sends, `refresh`,
   `refreshes`, `then`), but `then` runs off the agent's clock on the
   JavaScript target, and ownership has no answer. Remedy: repair `then` and
   adopt the existing tools (D7, D6), then design ownership (D5).
3. **Some values cannot be written.** A record cannot be built. Fieldnotes keeps
   its draft as six parallel slots and resets them by hand in four actions; one
   of the four misses a slot, and a drive shows the result. A string cannot be
   matched: Markdown dispatches on an eight-deep `when` ladder. A closed set
   cannot be declared. A virtualized list cannot hold a header, so Bluesky's
   source invents header, tab and loading rows as data. Remedy: D3, D4a, D11.

Most of the language changes cost less than r1 priced them. The plan format, the
VM and the JavaScript target already execute record construction (`Record`),
locals and option tests; the compiler just never emits records. D1, D2, D3, D9
and D10 change only the compiler. D4a, D5, D7b and D11 change the runtime.

## 2. Recommendations and reasoning

### D1 — Infer action effects; delete `writes`

**Evidence.** 553 actions carry 1,304 `writes` names: Bluesky 183, Interview
125, Messages 102, Fieldnotes 77. Each restates an assignment or a `send` in the
body. [The analyzer](../contract/analyze/src/lib.rs) already computes the set
through every branch (`writes_of`), refuses a missing name with the repair in
its message, and accepts a name the body never writes. Lowering copies the
authored list into the plan's `actions.writes`, so an over-declared slot is in
the VM's allowlist although no code writes it. Fieldnotes' `restore` lists 13
names; Interview's `tick`, 16.

**Recommendation.** Infer the writable slots from the body and emit exactly that
set into `actions.writes`. Keep the allowlist, slot ownership and types. The
refusal of a `then` action that sends its own mutation needs nothing new: it
already reads the body (`writes_of`), not the clause. Refuse a `writes` clause
with a message saying to delete it (no compatibility before 1.0); the landing
commit removes the clauses from every app mechanically. Put each action's
inferred effects in `contract symbols`, so a reader can still see them without
reading the body.

**Reasoning.** LLP 1017 §3 records `writes` as praised: "twice it caught me
assigning to state I had not declared" (Snapback diary 0103). In exact2 what
catches that is scope and type: a child cannot name a parent's slot, and an
undeclared name is `type-unknown-name`. Neither depends on the clause. What the
clause adds is a second listing, checked in one direction, whose repair the
compiler prints. An agent applies that repair mechanically, so the list no
longer records intent; it records the last compile.

**Tradeoff.** An unintended write to a valid, in-scope slot is no longer
refused. The inferred list in `symbols` and the source map is the review aid.
An optional `writes`, checked for equality, is rejected: two dialects, and
agents copy whichever they saw last. Indirect action calls, if they ever come,
must be accounted for statically before this conclusion extends to them.

**Proof before landing.** Every app's decoded plan is unchanged except
`actions.writes`, which holds the authored set (in slot order, not the author's)
where a clause was exact, and shrinks where an app over-declared. Corpus and reject fixtures move with the change
(`analyze-write-not-declared` and `analyze-writes-unknown-state` retire; the
clause's refusal is new). Branch-contained sends and row-owned writes keep their
behavior. Amend LLP 1004 and 1006 §2–§3.

### D2 — Local, immutable `let` in actions

**Evidence.** Interview's `followLink` computes `go(nav, url)` three times; its
comment explains that an action reads the values it began with.
[Messages' `animate`](../apps/messages/app.contract) reads
``frame(`bubble-${changeId}`)`` five times, and Interaction Gallery's sheet
actions read `sheetFullOf(frame("sheet-bay"), sheetFull)` four times. Across the
corpus, 11 actions repeat an identical call, 34 extra evaluations in all. The
compiler-only `Expr::Let` lowers to `BindLocal`/`LoadLocal`/`DropLocal`, which
both executors run; there is no authored form.

**Recommendation.** As r1: sequentially scoped, immutable locals in an action
and its branches. A local reads earlier locals and what is already legal at
that site. Writes still land together; reads still see the starting state.

```text
action followLink(url: string)
  let next = go(nav, url)
  nav = next
  if top(next).name == "search"
    search = searchParam(top(next), "q")
```

**Reasoning.** The author needs a name for a value already calculated, not a
slot or a global derive. `let` makes snapshot semantics usable without
order-dependent mutation, and makes a geometry read happen once.

**Tradeoff.** Scope, shadowing and diagnostics rules for statements. No
reassignment, loop, closure escape, `await`, or new way to run effects in
expressions. The evidence is modest; land it with D3, where a record built once
and assigned to two slots is the common use, not alone. Claim no speedup where
expression sharing already removes the work.

**Proof before landing.** Branch scope, unbound and duplicate names,
capture-avoiding component expansion, geometry reads and snapshot semantics on
both executors. Rewrite Interview's route action and Messages' geometry block;
navigation and animation are unchanged. Amends LLP 1017.000 P2's exclusion of
`let`.

### D3 — Build and update closed records

**Evidence.** [Fieldnotes](../apps/fieldnotes/app.contract) keeps its draft as
six parallel slots (`draftTitle`, `draftBody`, `draftPinned` and three
`original…`) beside `noteId`, `savedId` and `version`; its derives select
draft, original, opened and saved values field by field (twelve derives for
three fields). Four actions end an editing session (`edit`, `newNote`,
`restore`, `remove`), and each resets 10–12 slots by hand. `restore` does not
reset `confirmDelete`. Driven on the web
(wasm target, scratch store): write and save a note, press Delete…, open
Backups, save and restore a backup, return. The blank "A NEW PAGE" editor
shows "Delete this note?"; pressing Delete note sends `deleteNote("")`, and the
status reads "That note is not available." Harmless here, and exactly the
defect that grouping prevents: a slot added to a session must be added to every
reset. RealWorld's `SettingsPage` and `EditorPage` keep each field as a value
plus a `…Set` flag (seven flags) to overlay server data.

**Cost, corrected.** `Record` is already an opcode in
[`format.json`](../plan/tables/format.json), executed by
[the Rust VM](../runner/src/vm.rs) and compiled by
[the JavaScript target](../host/web-js/src/code.rs) to an array literal. Only
runner tests emit it; `contract-lower` never does. Equality is already
structural on both executors (`Eq` on records type-checks by unification;
`shape.js`'s `eq`). Construction and update are compiler work: an update lowers
to field reads of the base and one `Record`. No plan format or runtime change.

**Recommendation.** Construct and update statically known shapes in
expressions. Proposed spelling, Contract's existing named-argument form (as
`empty(…)` and component uses): `Fields(title=v, body="", pinned=false)` builds
(every field named; a missing one is refused, never defaulted), and
`Fields(base, title=v)` copies `base` with the named fields replaced. With
`loaded` the opened note's `Fields`, a draft is one optional record over it:

```text
state draft = none      // option<Fields>: the editor's copy, once edited
state base = none       // option<Fields>: what this session last saved
derive fields = match draft { case some(d) => d, case none => loaded }
derive dirty = fields != match base { case some(b) => b, case none => loaded }
action changeTitle(value)
  draft = some(Fields(fields, title=value))
```

Each of the four reset sites then assigns `draft = none` and `base = none`
where it assigned the six slots.

**Reasoning.** A form is already a structured value below the seam; parallel
scalar slots above it are an artificial asymmetry. A named draft makes reset,
discard and passing it to a child one value, and makes a missing field a type
error. Assembling a value from local fields should not need a data-source call.

**Tradeoff.** A one-field edit replaces the record, so every reader of the slot
re-evaluates; measure typing in Fieldnotes' body field. Keep the distinction
between absent and empty drafts with `option`. No dynamic objects,
dictionaries or defaults.

**Proof before landing.** Drive Fieldnotes through edit, save, edit while
saving, discard, switching notes, interrupted open, restore and delete, plus the
stale-confirmation case above, on both web targets and one native host. Reply
ownership and dirty state are unchanged. Compare the work of a title keystroke
as well as source size.

### D4 — Closed string choices first; payload variants only if still needed

**Evidence.** [Markdown's `Blocks`](../apps/markdown/app.contract) is an
eight-deep `when`/`else` ladder on a string `kind`; LLP, Markdown Stress and
Exact Live repeat it. Bluesky dispatches `note.kind` (13 values across seven
`when`s) and `post.role` the same way. 57 `when` lines in the corpus compare a
`kind`, `role` or `type` field to a literal. A typo is a valid string, and a new kind
does not ask its consumers to change. Today's `match` eliminates only
`option<T>`.

**D4a, recommended.** A closed choice of strings as a field or parameter type,
spelled as TypeScript and the roster already spell it (`formatDate`'s
`"medium" | "month-year"`): `kind: "heading" | "paragraph" | "item" | …`. Values
stay strings on the wire, in the VM and in generated TypeScript (the literal
union). `match` takes a choice in views and expressions, `case "heading"` per
arm; a missing case is refused, and an `else` arm is allowed only where the
type declares the domain open. A literal outside the choice is refused at
compile time; the seam's conformance refuses an unlisted string from a source.
The runtime part is one plan type kind carrying the literals, and that check in
both executors. The view `match` lowers to the existing two-arm regions, so the
runner does not change otherwise.

**D4b, later.** Variants with different record payloads (r1's D4) change value
representation, decoding, generated Rust and TypeScript types, and both
executors. Select it only when a consumer still shows a cost after D4a and D11:
a measured wire size, or a defect from reading a field that belongs to another
variant. Markdown's flat `Block` is unmeasured on both counts.

**Reasoning for the split.** The checked dispatch (typos refused, cases
exhaustive, one level of indentation) comes from D4a at a small runtime cost.
Half of Bluesky's `role` values are not data variants at all (D11). Do not use
either form to force resource states into exclusive loading/ready/error arms: a
prior answer and a pending request coexist (LLP 1017 §10 F4).

**Proof before landing.** Port Markdown's block kinds and Bluesky's
notification kinds; prove wrong literals refused, omitted cases diagnosed, an
unlisted source string refused at the seam, and plans and answers unchanged in
size on both executors.

### D5 — The navigation entry owns its requests

**Evidence.** A child resource is `type-child-resource`; resources, mutations
and tasks are root-only. The five apps that push screens (RealWorld, Messages,
Messages Legacy, Interview, Bluesky) render them as `each e in stack(nav)
key=e.id` (LLP 1038 D6), and pay for root-only data:

- **Interview.** `Screen`, one instance per stack entry, takes 11 props and 57
  injects. The root supplies them through a 57-deep `provide` staircase
  (`app.contract:406–462`). It tags answers with their owner by hand:
  `outcomeEntry` ("A mutation result belongs to the screen that submitted it"),
  `draftOwner` and `draftIdentity`. Its one `app(…)` resource is keyed by
  `params(nav, "question")`, `params(nav, "person")` and `params(nav, "post")`,
  every entry's parameters, so retained screens keep their data; a `search`
  mirror keeps a retained Search screen's query.
- **Bluesky.** `profiles`, `authorFeeds` and `threads` are keyed by
  `params(nav, "actor")` and `params(nav, "rkey")`, the same workaround for
  retained screens.
- **RealWorld.** Page mutations live in the root while form state lives in the
  pages; `editorSession` tags `tagEdit` answers; page interfaces take 9–14
  props.

r1 cited Caltrain's `Content` here. It is not ownership evidence: `Sky`
declares a slot, and a slot fill is inlined in the caller's scope, so
`Content`'s body can be written as the fill, with no interface. That cleanup
needs no language change; do it on its own.

**Recommendation.** Decide ownership before syntax, and start with the one owner
every app that pushes screens already has: a component instance that is a row of
the navigation root's `each … in stack(nav)`. It may declare `resource` and
`mutation`. Requests are created with the instance and answers land in it; an
entry beneath another is retained, not disposed, and keeps receiving answers;
popping an entry forgets its tickets (a late reply changes nothing, a server-side
write already sent stays sent). At bake, the launch entry's instance is baked as
the root is; later instances ask. A reload restarts instance requests as it
restarts instance state (LLP 1017 §8.4). Rows of any other `each`, and of
virtualized lists, stay `type-child-resource`: the rule "a row must not open N
requests" holds where N is data-sized, and the stack's depth bounds N here.

RealWorld's `ArticlePage` (article, comments, comment draft, `commented`) is the
first build. Interview's `Screen` is the acceptance test: `outcomeEntry`,
`draftOwner`, `draftIdentity`, the stack-wide `params(nav, …)` arguments and the
`search` mirror go, and most injects with them.

**Reasoning.** `provide`/`inject` shortens argument lists but does not move
request lifetime or answer ownership. Putting a request beside the state that
selects it lets keyed instance lifetime (P4c) do the bookkeeping the apps now
do by hand.

**Tradeoff.** The largest change here: owner identity, pending requests,
retained entries, bake, reload and disposal all need answers, and LLP 1017 P4c's
trade is revisited (a `rules/DEFERRED.md` take or Charlie's waiver at
selection). Preserve baked first frames and the data seam.

**Proof before landing.** Two entries with different arguments; back-stack
retention; disposal before a reply; a late mutation answer after navigation;
reload; a deep-link launch; first-frame bake. Measure whether a retained entry
still needs its requests.

### D6 — Expose data costs and make the efficient examples the default

**Evidence.** LLP 1058 P6's reports are not built: nothing in the runner, the
JavaScript runtime or the driver counts asks. Three patterns re-ask more than
their apps need:

- **Time as an argument.** [Messages](../apps/messages/app.contract) writes
  `time` from `poll` every 250 ms, and from `animate` every frame for 6 s after
  each send (`flightAt` restarts with the flight; `flightBody` is never
  cleared). `time` is an argument of `data`, the whole snapshot, which filters
  and maps every thread on each ask ([`app.ts`](../apps/messages/app.ts)
  `snapshot`). By LLP 1016 D5 a
  changed argument re-asks, so `data` would be asked at frame rate after every
  send. This is deduced, not measured; it is the first thing P6's counters
  should measure. Caltrain passes its one-second clock to both boards; its
  source filters departures by it, so removing the argument means filtering
  elsewhere.
- **Revision counters as arguments.** Fieldnotes' `library(query, saveRevision,
  serviceRevision)`; Interview's `app(…, revision, accountRevision,
  syncRevision)`, `accounts(started, accountRevision)` and `publicRevision`;
  Bluesky's five `…Fresh` counters and `seenStamp`. Messages folds two mutation
  revisions into `snapshot`'s arguments although both mutations already declare
  `refreshes data`, so the same answer is asked for twice over.
- **Whole lists and broad refreshes** (LLP 1058 R2): unchanged from r1.

**Recommendation.** Build LLP 1058 P6 in existing surfaces: `contract build`
names timer-driven resource dependencies; agent `state` gains defined `asks` and
`rows`. Count source invocations apart from network requests. Then fix the
exemplars with tools that exist: `refresh` and `refreshes` in place of revision
counters, which also deletes their projection derives; Caltrain's boards answer
a station's day with no clock argument, and the view keeps what is still ahead
with `filter(northBoard, d => d.at >= nowMs)` (LLP 1017.003); Messages formats
time in the view and stops passing `time` to `snapshot`.

**Reasoning, tradeoff and proof.** As r1. The cheap pattern must be the one an
author copies, and an expensive one must be visible. Reports explain; they do
not refuse a legitimate cheap query, and they are neither a profiler nor a
blocking check. The app owns invalidation correctness: narrowing refreshes must
not leave another tab stale (`touching` was withdrawn for that). Compare 60
seconds idle and representative writes on the same data and agent clock: asks
by source, answer sizes and visible results, on both executors. This continues
LLP 1058; no entity store, shared heap or automatic invalidation.

### D7 — `then`: repair it, adopt it in the polling actions, consider it for resources

**D7a: repair (evidence as r1).** The 2026-09-27 ruling: answers that land
before the host next advances arm one callback, reading the latest. The Rust
runner does this through `timer_due_ms` and `advance`
(`two_answers_before_advance_currently_coalesce_into_one_then`).
[The JavaScript runtime](../host/web-js/rt.js) instead runs
`setTimeout(() => m.then())` for each landed mutation after its commit. Two
answers give two callbacks, and both run on the wall clock, outside `advance`
and therefore outside the agent's `clock`: a drive cannot order them, which
breaks the seekable-clock rule as well as the count. Arm the continuation
through the JavaScript runtime's timer path with due time now, once per
mutation until the next advance, tied with timers as the Rust runner ties them.
Keep the ruling, the refusal of a continuation that sends its own mutation, and
"a refused continuation does not undo its answer".

**D7: adopt.** Four apps poll for answers:

| App | Action | Every | Looks for |
| --- | --- | --- | --- |
| RealWorld | `settle` | 100 ms | sign-in, publish and delete answers (`seenAuth`, `seenChange`) |
| Bluesky | `settle` | 250 ms | sign-in, post, change, DM and conversation answers (five `seen…` stamps) |
| Interview | `tick` | 250 ms | account, sign-in, phone and new-question answers; a saved draft; the appearance |
| Messages | `animate` | frame | a new conversation's answer (`seenChange`) |

Each mutation-answer branch becomes a `then` action that reads the answer from
its slot. In RealWorld that deletes `seenAuth`, `seenChange` and six derives
(`authStamp` … `changeSlug`) used nowhere else. The 100 ms task is left only for
the signed-out guard. Interview and Bluesky are outside the repo; their owners
adopt there.

**D7b: `then` on a resource (for selection).** What the polling actions still
do after D7 is mostly react to a *resource's* answer: Interview seeds
`draftAnswer` from `savedDraft` and re-applies the scheme when `data` answers;
RealWorld's guard waits for `me`. The same clause on a resource
(`resource savedDraft = … then seedDraft`) under the same ruling (once per
batch, reads the latest, its own commit) would remove them. It is refused when
the action can change the resource's own arguments, checkable from D1's
inferred effects. It is not `task … when [dep]`, which LLP 1017 kept out after
the hydration race: it fires when an answer arrives, not when a value changes,
and it does not remove the race (Interview's `draftReady` guard stays).
Consumers: Interview and RealWorld.

**Left over: time.** Bluesky's toast and Messages' flight phases poll elapsed
time, because an action cannot start a one-shot timer. Not proposed; recount
after D7.

**Proof before landing.** The same compiled fixture on Rust and JavaScript for
immediate and deferred answers, several arrivals, timer ties, refusals and
reload, driven on the agent clock. Then sign-in, publish and delete navigation
in RealWorld on the web, and the new-conversation path in Messages.

### D8 — Remove ignored assertion syntax; move application policy out of the roster

**Ignored `contract` blocks.** [The parser](../contract/syntax/src/parser.rs)
accepts a component's `contract` section and skips its lines, and the formatter
keeps its body opaque. A probe's plan with `assert n < 0` and a nonsense line is
byte-identical to the same app without the block; no app in the corpus uses the
section. Refuse it and point at `test` blocks beside the app. Accepted
assertion-looking text promises more than a comment and enforces nothing. This
completes LLP 1017 P7 and does not admit executable `contract` blocks (LLP 1006
§8). Keep formatter and reject fixtures consistent.

**Caltrain's policy in the standard roster.** `formatWalk`, `formatDistance` and
`formatCountdownMinutes` are used only by Caltrain, and
[their implementations](../runner/src/stdlib.rs) hold its choices: miles, the
word `nearby`, an 80-metre-per-minute walk and countdown rounding. Move them into
Caltrain `fn`s over existing pure functions: `floor`, `max` and `toString` cover
them (a ceiling is `-floor(-x)`; the one fixed decimal of "2.0 mi" needs a
whole-number case). Do not move a ticking label into a data source to shrink the
roster; justify any new primitive on its own. Verify exact strings at rounding,
unit and zero/negative-countdown boundaries. Claim no bundle saving until
measured.

### D9 — `provide` as a section of many names

**Evidence.** A `provide` takes one name and nests everything beneath it, so
Interview's root view sits 57 levels deep (`app.contract:406–462`), its content
starting more than 110 columns in. Of the corpus's 64 `provide`s, 55 forward a
same-named value (`provide nav = nav`). No name is provided twice on one path,
so widening each to its component's whole view changes no inject's value.

**Recommendation.** A component section, beside `props` and `inject`, one
binding per line; a bare name provides the value of that name:

```text
component Interview
  provide
    data
    nav
    accountPending = pending(accountOutcome)
```

Its scope is the component's view; a component deeper down still overrides with
its own section, so the innermost provider still wins. The nested view form is
deleted, since no use needs a narrower scope. Inliner only.

**Proof before landing.** Interview, Caltrain and the five `theme` providers
rewritten, with byte-identical plans; `syntax-missing-provide` keeps naming
every missing inject. D5 shrinks Interview's list further; this does not wait
for it.

### D10 — `??` and `?.` over options, with JavaScript's meaning

**Evidence.** 57 inline `match`es read one field of an option with a default,
for example `match auth { case some(a) => a.stamp, case none => 0 }`. Twelve
are RealWorld's, six of which exist only for its polling action, and D7 deletes
those.

**Recommendation.** Recount after D7 and D6. If the projections remain common,
add `o ?? d` and `o?.f` with JavaScript's meaning, `none` standing where the web
has `undefined` (as `at()` already does). They lower to the code the inline
`match` already compiles to. LLP 1017 §2.6 lists exact1's option-only `??`
among its "deliberately different rules"; the guard is JavaScript's semantics
exactly, with no `!`, no truthiness and no other extension.

### D11 — Fixed rows around a virtualized `each`

**Evidence.** A virtualized list takes exactly one direct `each`
(`lower-collection-template`). Bluesky's `Post.role` includes `header`, `tabs`,
`replybox`, `banner`, `space`, `loading`, `empty`, `error` and `end`: rows its
source invents so that a screen's header and its loading and end states can
live in the one list, which the view then dispatches back out.

**Recommendation.** Let a virtualized list hold fixed nodes before and after its
`each`, a header and a footer, as a scrolling container on the web does. Design
it under LLP 1070's owner. What remains of `role` (`post`, `parent`, `reply`,
`focus`) is a closed choice (D4a). This is collection work, not language work;
it is here because it removes evidence r1 counted toward D4.

## 3. Selection order and scope

1. **Correctness and deletion.** D7a (the JavaScript `then` on the agent's
   clock) and D8. Both have small reproducers and existing semantics.
2. **Compiler-only reductions,** in order of counted bookkeeping: D1, D9, D3;
   then D2 with D3; D10 after its recount. None changes the plan format, the VM
   or the JavaScript runtime, so each is proven by plan comparison, the corpus,
   and the apps it rewrites. The take `rules/DEFERRED.md` §Agent API recorded
   for the source map ("no new Contract syntax until formatting and navigation
   have landed") is met: `fmt`, `symbols`, `--json` and maps landed by
   2026-09-20 (LLP 1035.005 §7).
3. **Adoption, measured.** D7 in RealWorld and Messages, with the external apps'
   owners told; D6's counters, then Messages' time argument, the revision
   counters and Caltrain's boards; D8's Caltrain helpers; Fieldnotes rewritten
   with D1 and D3.
4. **Runtime designs, one at a time, each with its consumer.** D7b (Interview,
   RealWorld); D4a (Markdown, Bluesky); D11 (Bluesky, under LLP 1070); D5
   (RealWorld's `ArticlePage`, then Interview's `Screen`). D4b only if a
   consumer remains.

Use the existing compiler and runner corpus, the JavaScript conformance harness
and the app driver. Implementation still runs the required checks and the apps
it affects. No new script, registry, blocking check or authoring model follows
from this proposal.

These are not blanket scope waivers. D5 revisits an explicit boundary; D3, D4
and D10 widen expressions and types; D7b widens a ruled feature; D6's reporting
needs the interpretation LLP 1058 asked for. Where selection changes the binding
deferred scope, record the trade or Charlie's waiver then. No waiver,
implementer or date is invented here; drafting was requested, implementation
was not.

**As built (2026-10-02).** Stages 1–3 landed together:

- **D7a.** The JavaScript runtime arms a mutation's `then` on its timer path:
  once per batch, reading the latest answer, ahead of a timer due at the same
  time. A refusal, or 4,096 commits in one advance, stops the advance with the
  runner's error; a non-finite target is refused with the clock unchanged. The
  agent's `clock settle` stops after each commit that sends and lands its reply
  before the next fires, as a jump does. `host/web-js/conformance/then.contract`
  holds the cases (14 steps equal on wasm, JavaScript and Linux). On the
  JavaScript target a refused timer now stops the agent clock with an error, as
  on the other hosts.
- **D7.** RealWorld's sign-in, publish and delete redirects are `then` actions;
  `seenAuth`, `seenChange`, six derives and the answers' `stamp` are gone, and
  the 100 ms task keeps only the signed-out guard. Proven offline
  (`contract/cli/tests/it/realworld_then.rs`); nothing signed in or published on
  the public API.
- **D8.** A `contract` section is `syntax-contract-block`. Caltrain's countdown,
  distance and walk wording are Caltrain `fn`s, string-identical to the removed
  roster rows over 6,627 inputs on both executors. The roster's ordinals and
  `FORMAT_DIGEST` changed, so every app re-bakes (a native release for
  Interview's release loop).
- **D1.** A `writes` clause is `syntax-writes-clause`; `actions.writes` is the
  inferred set in slot order, and `contract symbols` shows it per action. The
  1,304 clauses went in one mechanical commit whose message holds the command.
- **D9.** `provide` is a component section; the nested form is
  `syntax-provide-in-view`, and the rewrite's script is in its commit message.
  Slot fills now type-check with their caller's providers, as they inlined.
- **D3 and D2.** `Shape(field=…)`, `Shape(base, field=…)` and action `let`, with
  no plan, VM or JavaScript-runtime change. Fieldnotes' editing session is one
  `Session` record built by `fn nextSession`, and the stale "Delete this note?"
  is gone. Interaction Gallery and Spark bind repeated reads with `let`.
- **The audits** (Astra xhigh, Grok 4.7 xhigh) found no blocker and five defects,
  fixed before landing: a record constructor refused in a list callback; the
  inliner renaming a constructor named like a child's state or prop; the
  JavaScript settle dropping a `then`'s request; a non-finite settle time
  poisoning the JavaScript clock; LLP 1005 §4 still describing a declared
  allowlist.

Not done: Messages' `then` adoption (the chat-demo Messages reached main after
stages 1–3 were built, and took the D1 command and the D9 script in that merge),
D6, D10's recount and stage 4. Outside the repo, Interview (57 clauses, 57
nested `provide`s), Weird Castle (9 clauses) and the Bluesky copy (55 clauses,
one nested `provide`, and the retired `contains`) need the D1 command and the D9
script before they build against main.

For the 15-document working-set cap, this child takes its parent's
`llp/current/` slot. The parent stays in the corpus, linked above; this changes
neither its status nor its remaining obligations.

## 4. Open decisions

- **D1.** Delete the author-written effect list (recommended), keeping the
  generated plan effects and showing them in `symbols`?
- **D3.** `Fields(base, title=v)` (Contract's named-argument form, recommended)
  or the web's spread, `{...base, title: v}`? And what measured invalidation
  cost is acceptable against today's scalars?
- **D4.** Accept the split: closed choices now, payload variants only with a
  remaining consumer?
- **D5.** Is the stack entry the right first owner (recommended), or any keyed
  instance? Which retained entries must keep receiving answers?
- **D7b.** Admit `then` on a resource, with Interview and RealWorld as its
  consumers, as distinct from the deferred `task … when`?
- **D9.** Delete the nested `provide` form once the section exists?
- **D6.** What exactly do `asks` and `rows` mean for composed sources and for
  records holding several lists?

Keep the settled strengths while answering these: CSS semantics, deterministic
atomic actions, explicit read/write occurrence boundaries, closed source shapes,
baked first frames, and a seekable clock shared by the app and its tests.

## 5. Not proposed

A reaction to arbitrary state changes (`task … when`), an entity store or shared
heap, automatic invalidation, generics, open records or dictionaries, indirect
action calls, an action-started timer (until D7's recount), and any new
authoring model.
