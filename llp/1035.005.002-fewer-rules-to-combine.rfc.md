## 2. What an improvement is

An improvement is one of three claims, said by name: a removed exception (a rule with two severities, a
special resolution path, a prohibition wider than its reason), fewer mistakes on representative tasks, or less
work to complete them. For a syntax change the instrument is 1116.016 §7's: guess-and-repair builds on the
real hosts, counting the refusals no message repairs in one edit. A shorter reference, a shorter root or a
smaller parser is explanatory, never the claim; LLP 1116.015 measured a spelling change level, and 1116.013
found that moving knowledge out of the first read moved it into more lookups. A removed exception with
inconclusive timing is recorded as "one rule removed; authoring benefit unproven".

Two things do not change: LLP 1116.016 D0 (no statements in expressions, no recursion, no functions as
values, no effects on change, bounded work) and the snapshot (an action reads the state it began with and
commits once). Every decision below is held to both. Every landing deletes the old form it replaces in the
same commit, with a diagnostic naming the new one; nothing is deprecated, aliased or kept as a mode.

## C1. A send and an assignment to one nonqueued mutation

The combination does not occur in the corpus: 0 of 2,070 files in the real builds, and once in the apps, as
Weird Castle's logout, send then assign, the idiom LLP 1016 D5 documents and `mutation.rs` tests. The mistake
D2 describes (a reset written first that drops the new request) is real in the runner and has not been made.
So C1 is a warning, not a refusal: on a path with both, in either order, the message says what the runner
does (`commit.rs`: a send is asked when the action runs; after the writes land, a request still in flight
for a nonqueued mutation the action assigned is forgotten, its reply dropped, and the slot keeps the
assigned value), and names the three intents' spellings (hide the old result while `pending(m)`; a second mutation for logout; the assignment
alone to dismiss). It never suggests `queue`. The warning lands with C2's lane, in the same analyzer pass, and
costs the one app nothing. The refusal is recorded as not justified by evidence; if the warning is ever seen
in a build's log, that is the trigger to reconsider.

**As built (2026-10-28, lane `lane/analyze-one-rule`, worktree `exact2-wt-analyze`):** `analyze-send-assigned`,
a warning from `contract/analyze/src/sends.rs` (`send_assigned`), emitted by lowering beside the read warning;
in either order, through calls (naming them), once a mutation an action; exclusive arms and a `queue` mutation
are not named. Tests: `warnings.rs` "a send and an assignment of one mutation on one path is named once in
either order" and "exclusive arms and a queue send beside an assignment are not named". Docs: the grammar's
semantic restrictions and the agent guide. The in-repo apps compile with no new warning; Weird Castle's logout
gets the one.

## C2. One rule for a read after a write

Keep the snapshot. The rule: on a path that has already written a value, a later read of it names an
explicit local or parameter, in the action's body and through its calls alike. For the new value, `let next
= count + 1`, write it, pass `next`; for the old, bind it before the write. The diagnostic offers both,
since choosing the new value would change correct snapshot programs. What the rule removes is one rule with
two severities and one missing exemption: the body warns (`rereads.rs`) and a call refuses (`calls.rs`); both
walk the same paths with the same exclusivity facts, but only the body knows the field-level record-copy
exemption (`rereads.rs` records the fields a copy replaces; `calls.rs`'s write record has no such field).

What stays, by the reviews: a derive read in an action is a settled value and is accepted after a write to
what it reads (1089 D3), so no derive clause; the record-copy exemption is kept at field level (`s = S(s,
f=…)` then `s.g` is safe); exclusive paths are safe. The phase-chain exemption (`if phase == …` branches
testing the starting phase) stays too. The census settles the severity: the body warning fires in 86 of
1,029 real builds, the call error in 2, and today's repo apps carry no warning where LLP 1089 counted 25
same-frame reads, repaired or exempt. Raising the body to an error would refuse 8% of builds
to catch a mistake the warning already names; lowering the call checker to the body's severity and giving it
the field-level exemption removes the exception at no cost. C2 is therefore: one rule, at warning severity,
with one exemption set, in the body and through calls. Interview's six remaining warnings (reads of `nav` after
assigning it) are the test that the message repairs in one edit.

C2 and C6 share a rule: narrowing by `x != undefined` must end at an assignment for the same reason. They are
written once (§4 Q3).

## C3. A continuation receives the reply that caused it

A `then` action may declare a parameter of the mutation's answer type and receive the admitted reply; a
parameterless handler ignores it, as event handlers may. The slot stays optional for the view. The reply is
captured when the continuation is armed and the continuation runs as its own transaction through the clock;
supersession, forgetting, queue order and reload rules are unchanged, and a captured value never revives a
continuation whose request lost ownership. A shaped domain refusal is a reply; a request that fails without
an admitted value runs no `then`.

What the reviews add as conditions: **coalescing** is specified before the prototype, because two answers
before an advance run one `then` today (`mutation.rs`), and the parameter must say which reply it carries
(the last admitted, with the earlier ones recorded as superseded, is the expected answer; the prototype
decides); and **the semantics gap is named**, since Lean models no `then` at all (1092 D12), so the
executor-against-executor conformance trace is the evidence until the QUEUE item that models `then` lands.
The code it removes is counted (§1.3): 40 of the apps' 67 continuations open by matching the slot and 50 read
it; in the builds 105 of 1,032 open so and 196 read it. The builds' 10% is the honest size of the gain for a
builder; the apps' 60% is the repo's. No diagnostic measures the handler's `match` (the `none` arm is dead by
construction and compiles).

**Decided (r3):** deferred, three advisers of four. The triggers, any one: a continuation found running on a
slot that is no longer the reply that armed it (a drive of the apps' 40 handlers or the builds' 105, after
leaving during the ask); a classification of those handlers showing that a substantial body, not a one-level
`match`, disappears with the parameter; or C5 stage B being scheduled, since arming and destruction are then
designed once per instance. Until then the dead `none` arm stays, and LLP 1016.001's ruling (once, reading
the latest) stands.

## C4. The capability test, and a deferred command pilot

No builder hit the name collision: `syntax-call-ambiguous` appears in 0 of 1,029 real builds and 0 of 1,388
guess screens. The app that `close` silently rebound was fixed by LLP 1089 D1's refusal, which is the one
that now never fires. A pilot that imports `close` through the package interface would remove a resolution
path nobody is paying for, at the cost 1035.005.001 D5 names (timing, a second dispatch route). It is deferred,
with its design kept as written there: `close` first, identical traces, the ambient spelling deleted for that
name, unshipped if the module AST cannot carry the timing. The trigger to take it up is a collision in a
build's log, or a second command whose import would remove a special case of its own.

What C4 keeps is the test adopted from LLP 1150 D3: **a future capability is a package unless its LLP shows a
package cannot say it** (a lifetime held while an element is displayed, a value re-read every commit, a
commit-time expression), and then the LLP says why. The reviews showed what fails the test today and stays
as it is: `sequence` (1133.001 D8 keeps sounds and MIDI in the runner), `wakelock` and `orientationlock`, the
media session, `tool`. The parser's case count should not rise again without such a line.

## C5. A component's behaviour has the component's lifetime

Two stages, because the reviews found one half free and the other the largest change in either draft.

**Stage A, static.** A child used outside every region arm (the inliner's `Owner::Instance` case: not under
an `if`, `match` or `for`) may declare `resource`, `mutation` and `task`; the compiler lifts them into the
root as it lifts that child's state, one copy per use, renamed apart. The runner and plan are unchanged for
these, because such a use lives as long as the root. A use under any arm is refused with the reason, and the
message shows the root-owned pattern the refusal teaches today (`tasks.rs`). Device facts (`exactViewport()`,
`exactPage()` with no arguments) are untouched: one shared answer, never a copy per use. This stage would remove
`type-child-resource` where its reason (a row must not open N requests; only the root has a clock) does not
apply, and nothing else.

**Decided (r3): skipped**, three advisers of four. It is not free: an `Owner::Instance` child's slots are late
slots, initialized after settlement (`runner/src/runner.rs`, `init_late_slots`), so a lifted resource whose
arguments read the child's state would be asked and baked on an uninitialized value, or the child's state
demoted to boot-time init: a new ordering rule either way. And the 26% counts placements, not features that
want a request; the refusal fired in one build of 1,029. A use that moves under an arm would change what it
may declare. Stage B decides the one lifetime.

**Stage B, instance lifetime.** 1035.005.000 D5's owner first: a row of the navigation root's `for … in
stack(nav)` may declare `resource` and `mutation` (and, by this document, `task`). Requests are created with
the instance and answers land in it; an entry beneath another is retained and keeps receiving answers;
popping an entry forgets its tickets (a late reply changes nothing; a write already sent stays sent); at bake
the launch entry's instance is baked as the root is and later instances ask; a reload restarts instance
requests as it restarts instance state. 1035.005.001 D4's lifetime rules apply to that owner: identity is the
instance's, including enclosing keyed regions; a destroyed instance removes its timers, queued sends and
armed continuations and releases its request ownership; a late answer cannot commit into a destroyed owner
or a successor with the same key; hidden and destroyed are distinct, and each of arm-hidden, tab-covered,
stack-covered and `display: none` is mapped to one of them before the prototype, since today hiding an arm
drops its child slots (P4c amendment). Rows of any other `for`, and of virtualized lists, stay
`type-child-resource`: the stack's depth bounds N, a data-sized list does not. In the builds, a third of
child uses are stack rows and a third data rows (§1.3): stage B's first owner is the common case, and the
refusal it keeps is as common.

Conditions from the reviews: destruction preserves cleanup an author wrote (Shelf stops a camera opened after
leaving its screen; a suppressed continuation must not lose that); a child's mutation that must refresh an
ancestor's resource (Shelf's central pattern) is either admitted by `refreshes` naming across owners or the
extraction is documented as partial; what is baked for an instance created after first pixel is stated;
packages still cannot read the platform facts 1139 D6 names; `members` stays, since the root it exists for
holds app-wide requests. Stage B changes the plan's owner columns, bake, reload, both executors and Lean. For `resource` and
`mutation` its gate is not a DEFERRED entry (`rules/DEFERRED.md` holds none for per-instance resources; LLP
1017 §5 P4 said they would go on, and only P4c's action-call rule did) but `rules/RULES.md` "Scope": an
implementer, a date and Charlie's selection, as 1035.005.000 D5 already says. For `task` it is: DEFERRED's
gated-timers entry keeps "component-scoped and action-started timers" still out, so an instance-owned task
needs that entry's take or waiver.

**Decided (r3): stage B waits for a scheduled consumer extraction**, three advisers of four. The direction is
kept and `members` stays. It proceeds when Interview's `Screen` or RealWorld's `ArticlePage` is scheduled as
the extraction, with an implementer and a date, and its baseline names the per-entry ownership bookkeeping
(owner tags, stack-wide `params`, the `provide` staircase) as the work to remove; that app is the acceptance.
What would bring it forward: a drive of either app showing a late reply committing into a successor with the
same key, or a popped entry's ticket still changing the screen. If both C3 and stage B are built, each is
measured apart against the baseline (one change per comparison), and the first whose trigger fires goes
first: the panel split on the order and agreed neither shrinks the other's core. Its acceptance is Interview's `Screen` (the owner tags and
stack-wide `params` go) and RealWorld's `ArticlePage`, with the lifecycle list of 1035.005.000 D5 green and a
long virtualized list's per-site request counts unchanged.
