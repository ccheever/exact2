## Summary

Many interactions need **derived presentation**: one property following
another value as it moves.
- The backdrop fades as a photo is dragged down to dismiss.
- A card rotates with its horizontal throw.
- A header collapses as its list scrolls.
- A context-menu preview lifts with press progress.

exact2 can't express these today (LLP 1057.002 §4.5). The only route is
`pan=`, app code once per frame. It has no release velocity, and it can't see
the spring the drag hands off to.

Charlie asked for both candidate forms to be tried (1057.002 §6.7), and both
were built on one case, C1's dismiss drag with its fading backdrop:

| | Gesture timeline (spike A) | Per-frame app code (spike B) |
|---|---|---|
| During the drag | exact, 0 frames of lag | exact, 0 frames of lag |
| Cost per frame | ~5 µs (iOS), 0.1–0.2 ms (web) | 0.2–0.4 ms of runner |
| The fling's velocity into the release | carried | lost: `spring()` takes none |
| Dismissal, backdrop against photo | ≤ 7e-7 apart | 0.118 opacity apart |
| Grabbing mid-spring | continuous (iOS) | jumps 94 px |

**This RFC proposes the gesture timeline.** It follows the web standard's
shape: CSS scroll-driven animations' named timelines, `animation-timeline`
and `animation-range`. One declared deviation adds a drag as a timeline's
source.

- A node's keyframes are held at the progress of another node's *presented*
  value: the photo's translate, a scroll offset.
- The engine evaluates that in the frame the source moves. No app code runs
  per frame, and nothing flows back into app state.
- It is right after release for the same reason. One spring moves the photo,
  and the backdrop is a function of what that spring shows. So nothing can
  drift, and catching and velocity come from the existing drag binding.

## 1. The problem

1057.002's catalog, C1–C13, names the cases. Four are derived presentation:

| Case | Source | Follower |
|---|---|---|
| C1, photo dismiss | the photo's vertical translate | backdrop opacity |
| C6, card fling | the card's horizontal translate | its rotation; the next card's scale |
| C8, collapsing header | the list's scroll offset | header height and title opacity |
| C9, context-menu lift | press progress | the preview's scale and shadow |

Each needs the follower to be a function of the source *as presented*: while
the finger moves, and through the spring that follows release.

## 2. What the spikes showed

- **Following the presented value is what makes release right** (§6.10).
  - Spike B's app sets end values, so each property runs its own spring.
  - The clamp in the opacity function makes those springs disagree (0.118).
  - The app knows only its own value, so a grab mid-spring jumps.
  - Spike A has one spring, owned by the drag binding. The follower reads it,
    so velocity, catching and the exit come for free.
- **Per-frame app code is cheap during the drag, but it isn't the problem.**
  - Spike B's runner costs 0.2–0.4 ms per frame. That would be fine at
    120 Hz.
  - Its limits are structural. Fixing the release would make the app its own
    spring driver, which is DEFERRED's decay and sequence drivers line.
- **The web needs one more piece** (spike A's second finding).
  - During the release spring, the spike seeks the follower once per frame
    on the main thread. That breaks "the web does nothing per frame", and a
    busy main thread would let it drift from a compositor-run spring.
  - The spring's frames are known at release: the engine samples its closed
    form (`spring::keyframes`). So they can go to the follower too, as a
    `linear()` easing, and the browser plays both together. See D3.

## 3. Design

**D1. Vocabulary.**
- **CSS's rows, kept as they are:**
  - `animation-timeline: <name>`;
  - `animation-range: <start> <end>`;
  - `scroll-timeline-name` / `view-timeline-name`;
  - `timeline-scope`.
- **The one deviation:** `drag-timeline: <name> <axis>` on a node that a drag
  binding moves.
  - Its progress is that node's presented translate along `<axis>`, mapped
    through the consumer's `animation-range` (px).
  - LLP 1001 declares it: CSS has no gesture-driven timeline.

**D2. Evaluation.**
- A node whose `animation-timeline` names a timeline is held, not played: its
  keyframes are evaluated at the source's progress.
- **Natively** that happens in the frame the source moves: the drag's reply,
  then each spring frame, in the same Core Animation transaction. Apple samples
  bound nodes rather than handing them to Core Animation.
- **On the web** it happens where the drag binding writes the held value:
  in the pointer event, before the next frame (motion-glue.js).
- Keyframes use the existing LLP 1055 evaluator.

**D3. The release on the web.**
- At release, the binding already samples the spring into keyframes for WAAPI.
- The follower gets the same frames, composed through its keyframes, as a
  `linear()` easing over the same duration.
- The browser then plays both with no per-frame work.
- A grab cancels both at their presented values, as a grab cancels the held
  spring today.

**D4. Scope.**
- Names resolve as CSS resolves them: `timeline-scope` on an ancestor, else
  the nearest declaring ancestor.
- The spike's names were global. That's fine for one fixture; it's wrong in
  a list of cards.

**D5. Scroll timelines.**
- C8 is plain CSS `scroll-timeline` / `view-timeline`: the browser runs it
  natively, off the main thread.
- Native hosts feed the scroll offset into D2 as the source, in the frame
  UIKit or AppKit delivers it.

**D6. What a timeline doesn't do.**
- It reads the source's translate. It doesn't decide which gesture is moving
  it: a pinch at fit also translates the photo, and would fade the backdrop.
- Choosing dismissal over pan by zoom is arbitration, LLP 1057.000's question.
- One option: a dismiss binding publishes its own displacement as the source.
  That needs the binding to own "dismiss", and waits for 1057.000.

**Limits found** (1057.002 §6.10):
- **Rotation in the ancestry:** both hosts refuse a drag binding with a
  rotated node in its handle's ancestry, so C6's rotation goes on a child.
- **The pivot:** it is `transform-origin` only, not the grab point.

## 4. Rules

- **DEFERRED §Motion, "A second value graph … no derived values, bindings":**
  this needs an amendment. Proposed wording:
  > *Presentation timelines (LLP 1057.003): a node's keyframes held at the
  > progress of another node's presented value (a drag's translate, a scroll
  > offset), evaluated by the engine with no app code per frame and nothing
  > flowing back into app state. Every other derived value stays out.*
- **"The web does nothing per frame":** kept once D3 lands. Until then the
  web seeks once per frame during a release spring only. (Phase 2 landed D3:
  a spring release runs nothing per frame; a source moved by a CSS eased
  transition is still sought per frame, §Phase 2 as built.)
- **"No per-frame app code":** kept.
- **"Laying out per frame":** only if a timeline animates a layout row, such
  as C8's `height`. That should be refused in v1, which takes paint-only rows
  (opacity, transform, filter, color).
- **LLP 1001:** declare `drag-timeline`.
- **RULES §Scope:** moving this onto the doing-list needs a take or Charlie's
  waiver.

## 6. Alternatives

- **Per-frame app code (spike B):** measured and cheap. It can't get release
  right without becoming a spring driver. Its `panstart` and `panend(vx, vy)`
  phases are small and could serve app-driven gestures on their own; they are
  not proposed here.
- **A general derived-value graph:** it expresses everything, and it is
  exactly what DEFERRED keeps out. Timelines are the narrow case the web
  standard already has.
- **Nothing:** C1, C6, C8 and C9 stay inexpressible, or become `pan=` app
  code that drifts on release.

## 7. Questions

1. **Scope of the amendment:** paint-only rows in v1, or layout rows too
   (C8's `height`)?
2. **Consumers:** is C1 in the gallery the admitted consumer, or does a
   product need one first?
3. **The handoff (D6):** wait for 1057.000's arbitration, or give the dismiss
   binding its own timeline source now?

## Phase 1 as built (2026-09-28)

Branch `llp1057.003/phase-1`, from the spike's code (`3e1290b7`), cleaned up
and extended.

**The rows** (`kernel/tables/schema.json`, bits 150–152), CSS text through
the one `CssValue` codec template (`kernel/src/timeline.rs`):
- `drag-timeline: none | <dashed-ident> [x | y | inline | block]?`, the
  declared deviation, entered in LLP 1001 with its reason.
- `animation-timeline: auto | <dashed-ident>` and
  `animation-range: normal | <length> <length>`, CSS's rows in a subset. A
  drag has no scroll range for `cover` or percentages to name. `normal`
  leaves the node on the clock.

**Evaluation** (`motion/src/engine/timeline.rs`):
- A bound node's plays are held, as `paused` holds them. They are re-sought
  at the start of every `Engine::frame()` and when a row arrives, so the
  hold's reply and each spring frame carry the consumer in the batch that
  moves its source.
- **The mapping is a CSS scroll timeline's**, checked against Chrome (below).
  The range spans the animation's delay and active interval together
  (Web Animations 2's conversion to a progress-based timeline), unclamped, so
  the fill decides outside the range. The spike clamped progress and spanned
  only the active interval; the parity cases `tl-fill-none` and `tl-delay`
  disagreed with Chrome until both hosts changed.
- Without a source, a consumer holds its range start.
- Apple samples bound nodes (`engine.timeline_bound`), on iOS and macOS alike.
- The web pauses the consumer's CSS animation (`animation-play-state:
  paused`, after the `animation` shorthand, so it cannot reset it) and
  seeks it in `motion-glue.js`:
  - where the transform drag writes its held value, in the pointer event;
  - once per frame while a translate animation runs (the release spring;
    phase 2 replaced this with D3's follower animations);
  - on the agent's clock seek.

**What the compiler refuses:**
- `lower-timeline-row`: a bound animation whose keyframes animate anything
  but opacity, translate, scale, rotate, the colours and `box-shadow` (Q1).
  Keyframes refuse `height` already, and an SVG element takes no timeline
  yet, so today it catches geometry keyframes on a box; it is the rule's
  guard for when either changes.
- `lower-timeline-endless`: an `infinite` bound animation. CSS gives it no
  duration on a progress-based timeline and shows its end at every
  position. A computed one that reaches a host holds its start there.
- A row outside its grammar, by its `StyleValueError`.

**Hosts:**
- **Web, iOS, macOS:** built and measured, below.
- **Linux: built, through the engine.** Its painter presents what the
  engine's frame gives, so nothing Linux-specific was needed.
  `host/linux/tests/it/timeline.rs` drives the presenter's contacts and the
  release spring and holds the backdrop to f(photo) in every frame.

**C1 in the gallery** (`apps/interaction-gallery/app.contract`):
- The backdrop is its own box. It is bound to `--dismiss`, the photo's
  vertical translate, over 0–300 px, only at Fit:
  `animation=(zoom == 1 ? "viewerFade 1s linear both" : "none")`.
- `releasePhoto` dismisses at Fit when the photo is past 120 pt or flung
  faster than 800 pt/s. It sets `panY = 900`, so the photo leaves on the same
  release spring, carrying the fling, and the backdrop reaches 0 on it.
  Anything less springs back.
- **D6's limit stands.** At Fit a pinch's translate fades the backdrop too,
  since the timeline cannot tell which gesture moved the photo; that waits
  for LLP 1057.000.
- **The viewer stays open after a dismissal.** Closing it when the exit ends
  needs an end-of-motion event, or an action that can call the `command`
  prop; Contract has neither (QUEUE).

## Phase 2 as built (2026-09-28)

D3, the web's release. When a timeline's source starts a release spring
(the `animate` op for its `translate`), `motion-glue.js` gives each bound
consumer's CSS animation a follower: a copy of its keyframes
(`getKeyframes()`), played by the browser over the spring's delay and
duration with a `linear()` easing (`follow`). Nothing runs per frame.

**The easing** (`timelineEasing`, exported for its tests). The spring's
frames are evenly spaced and the browser interpolates them linearly, so the
timeline's position, its progress and the consumer's local time are
piecewise linear in time. The easing is the consumer's *directed* progress
(Web Animations 1 §4.8: phase, fill, iterations, iteration start,
direction) at each frame, with a point added wherever the local time crosses
the delay, an iteration boundary or the end. With those points it is exact
between frames as well, not only at them: a kink is one point, an
iteration's wrap two points at one input. Keyframe easing stays the
browser's, since the follower carries the keyframes themselves.
- An endless animation holds its start, so it gets no follower.
- **No follower** where the easing cannot say it, and phase 1's per-frame
  seek runs for that release instead:
  - a fill that leaves the animation out of effect where the spring goes
    (`fill: none` before the delay or past the end), since out of effect is
    no progress at all;
  - `composite: add` or `accumulate`, which would count twice over the
    paused animation.
- The follower starts in the same task as the spring's animation, so both
  start in the same frame and the agent's clock registers and seeks them
  together. A grab or a new spring cancels it and re-seeks the paused
  animation where the source is caught (`cancelProperty`); when it ends,
  the paused animation takes over where the source rests.

**Found and fixed: a CSS-eased source was not followed.** Phase 1 sought
consumers only on a spring's `animate` op. A drag target whose `translate`
transition is a CSS easing (`translate 0.4s ease-out`, not `spring()`) is
released by the browser's transition, so the backdrop froze at its release
opacity. Measured on a temporary copy of the gallery with that transition,
it was up to 0.48 from f(photo) through a dismissal. A `transitionrun` on a
source's `translate` now starts the per-frame seek (`kickTimelines`), which
stops when the transition does. That path still runs per frame; composing
it too would mean sampling the browser's easing (QUEUE).

**Measured** (the gallery's C1 in headless Chrome 154: the phase 1 probe,

The exit evidence was no per-frame main-thread work during a release spring
and the follower within 10⁻³ of f(photo); both hold. The backdrop follows
the photo through a catch mid-spring, jump and all.

**The release's start, fixed with it.** After every release the photo
stood still for two frames (1057.002 §6.10). The engine starts the spring
at the release, but the browser starts a pending animation only when it
next commits one: 12–28 ms later in the probe's trace. So a catch, which
adopts the engine's clock, landed ahead of the screen. The `animate` op now
carries `at`, the host's clock when the spring was lowered, and the glue
pins the animation's `startTime` there (`performance.now() − now() + at`).
Its followers take the same start, and the agent's clock still seeks all of
them. Measured: the photo moves in the first frame after the release's
batch (+33 ms after pointer-up, was +44). A catch 80–120 ms into the
spring lands about 5 pt past the spring's next frame, against about 12
before; the rest is the recognizer's own timing (QUEUE).

**Tests:** `host/web/tests/timeline-easing.test.mjs` (`bun test`). Three
check the easing between frames against the directed progress written out
by hand: a clamp at each crossing, a delay, wrapping and alternating
iterations, and what has no easing. The fourth runs in Chrome: two copies of
one CSS animation, one sought to the timeline's progress as a held drag
seeks it, the other playing the copied keyframes with the easing, compared
at 998 instants off every frame, for six timings including keyframe easing,
a fractional iteration count, `reverse` and a delay. They agree within
10⁻⁴ (`getComputedStyle` serializes opacity to about six digits).

**Size:** none in the wasm; `motion-glue.js` grows by 93 lines, loaded only
