## 1. Summary

The first submissions favor improving entry into existing functionality: make
workspace preparation and lock recovery explicit, teach native drive preconditions
at the point where the drive fails, and give camera and icon paths that hold on
every host. Preserve the fast loops and the small testing vocabulary that authors
praised.

Two of the five items already have owners elsewhere. Lock recovery is LLP 1046.011
D2: ruled, with Charlie implementing. A photo from the picker is LLP 1114.002:
drafted, not yet ruled. Here those two take R2–R4 as evidence rather than open
parallel work. The cheapest items are a compiler message (D3, landed in
`f1950e7f5`) and a table row (D4).

This is a synthesis for choosing work, not an implementation spec or a commitment
to build every item. Charlie's request authorizes these documents; it does not
approve a new command, API, fixture, or scope admission. Existing art rulings
remain in LLP 1046.011.

## 3. Recommendations, in order

### D1. Make preparation and lock recovery one understandable path

**Evidence:** F8, F10, F12, F13. The copied ordinary app is a separate case from
an SDK-drifted game lock; diagnose each rather than giving every failure one label.

For games, carry out the already ruled LLP 1046.011 D2: explain which SDK-owned
dependencies changed, give the app-form explicit recovery command, and distinguish
missing cached crates from stale dependency choices. Ordinary builds remain locked;
they must not silently repair a captured lock.

`.shells/` needs no verb of its own. `test-rust`, every app build (`scripts/app.mjs:526`)
and D2's coming `lock` all write it through `prepareGame`. Whatever the order of R4's
commands was, nothing told its author which verb writes the workspace. Say so where
an author looks.
The generated instructions' `.shells/` sentence (`game/new.mjs:476`) names `bun
exact.mjs test-rust` as the quickest way to write it. The generated
`render/Cargo.toml` (`game/new.mjs:57`), whose `workspace = "../.shells"` is the line
behind Cargo's error, says the same in its header comment. If LLP 1046.011 D4's `look`
lands and a custom render example still needs more than that, reopen the question
with the evidence. A new verb would require explicit approval under
`rules/RULES.md#agents`.

**Acceptance:** run a copied ordinary app and a game whose captured lock predates
an SDK dependency change. The first failure identifies the cause and ordered
recovery steps. Explicit recovery succeeds with network/cache prerequisites met;
the locked game test then runs. From a fresh scaffold with no `.shells/`, the
render example fails with Cargo's error, the documented command writes the
workspace, and the example then runs. Record whether dependency resolution changed
and why.

### D2. Name `clock settle` where an iOS tap fails, and let `reveal` clear the keyboard

**Evidence:** F7. Transition settlement and keyboard occlusion are separate issues.
The diary can't split the 25 minutes between them.

**Transitions.** When an iOS tap is refused while `nativeInFlight()` is true, the
refusal says a native transition is in flight and names `clock settle`, as the web
carrier's does. The refusal is where an author learns it, and eight of R2's
unsuccessful invocations were `test ios`. Add a pitfall only if the refusal proves
not to be enough. Keep the seekable clock: no sleeps, and no settling inside `tap`,
which would hide intermediate frames a test may want.

**Keyboard.** The refusal is right and already says what to do. The gap is the
agent's `reveal`, which counts a target as in view when its middle is inside its
scroll view's full `bounds`, including the part the keyboard covers. The presenter
already knows the visible part. Its own `reveal` for a focused field (the browser's
rule) scrolls into `bounds.inset(by: adjustedContentInset)`, and under the default
`interactive-widget` the keyboard's overlap is that bottom inset. The agent's
`reveal` should use the same visible rect, so it scrolls a target above the keyboard
when the range allows, as a person scrolls a form up. Under `resizes-content` the
viewport already ends at the keyboard, so nothing changes there. Only
`overlays-content` sets no inset, and only there does `reveal` need `keyboard.top`,
converted into each scroll view's space. Where nothing can scroll the target there
(the non-scrolling root of `docs/agent-pitfalls.md:13`), the refusal stands: a person
couldn't reach the control either, and the fix is the app's. Keep real visibility and
hit-testing, with no automatic keyboard dismissal and no tap through the keyboard.

The web drive can't serve as the oracle here, because it has no software keyboard and
a control is never under one. What R2 saw on the web was an ordinary reveal of an
off-screen target. Mobile Safari is the reference for what a person sees.

**Acceptance:** a push or tab switch followed at once by a tap on iOS is either
accepted or refused with a message naming `clock settle`. With `clock settle`
between them, the sequence passes. In R2's shape (a focused field, with the form's
lower action under the keyboard inside a scrolling form), the action is reached on
iOS through `reveal` and a real tap, and the reply's `from`/`to` show the scroll. That
holds under the default policy and under `overlays-content`. The same form with a
non-scrolling root is refused with the existing message. Compare
tree, layout and screenshots before and after. Moving actions into the navigation
bar is a workable app choice, not proof the discrepancy was fixed.

### D3. Correct the camera refusal now; take R2 to LLP 1114.002

**Evidence:** F5. R2's native module and storage path worked once the bridge was built.

R2 reached for `capture` on the picker first, as a web author would. The refusal
quoted a sentence `rules/DEFERRED.md` no longer contains (§2), and R2 read it
correctly as "no camera". LLP 1114.002 §3 found the same drift.

1. **Now, with no ruling needed (landed in `f1950e7f5`):** `PICKER_ADMISSION` quotes
   DEFERRED's current sentence, and the `lower-picker-capture` refusal names the
   route: an app native module behind `device.camera`, in the shape of
   `apps/recorder`. That is the one pointer an author meets at the moment of need.
2. **For Charlie's ruling on LLP 1114.002:** R2 is a second app, after the Bluesky
   clone, whose author wanted one photo and tried `capture`. Under 1114.002, R2's
   iOS camera would have been one attribute. macOS and desktop browsers ignore
   `capture` (1114.002 §1), so a desktop camera would still need the module. Record
   R2 there as evidence. If 1114.002 is ruled in, step 1's message goes with it.
3. **The live viewfinder** (`start`/`stop`/`capture`/`flip`) stays `QUEUE.md:56`'s
   module, which needs its own RFC with an implementer. The repository has no camera
   code to document as a starting point. R2's module, built from `apps/recorder`,
   shows that the shape works across web, macOS and iOS. That makes it evidence for
   that RFC, not a recipe for a guide.

**Acceptance:** building an `input type="file" capture="environment"` prints a
refusal that quotes `rules/DEFERRED.md` as it stands and names the module route and
the grant. If LLP 1114.002 is ruled in, its own acceptance applies, with R2's shape
added as one iOS case: take a photo, keep it under `app:/data`, show it in a list. No microphone, video recording or OCR expansion follows from this item.

### D4. Add a `camera` symbol role, and document `sf/` where roles are listed

**Evidence:** F6. Each of its three observations has a cause in §2, and none is a
renderer defect.

- **Add one role.** Add `camera` to `kernel/tables/schema.json`'s `symbols` (SF
  Symbol `camera`, a 24-unit path in the table's style). Every host's table is
  generated from it. The table grows by what apps ask for, as the Bluesky clone's
  `at`, `hashtag`, `quote` and `feeds` did. A camera is as common a pictogram as
  `photo`, and LLP 1114.002 would make a "Take Photo" button ordinary. r1's caution
  against inventing roles holds for app-specific pictures, but this one is generic.
- **Document `sf/`.** Beside `symbol:<role>` (`docs/contract-for-agents.md:887`), add
  that `symbol:sf/<name>` is drawn on Apple only, is blank on the web and Linux,
  and that `layout` reports why. A tab that must show on every host uses a role.
  LLP 1035.004.000 ruled that a missing raw name stays silent, so the web host doesn't
  change.
- **No change for SVG.** The guide already says an SVG source is an `error` on Apple,
  and its tablist example (`image "symbol:home"` over a `text`) is already the
  portable recipe.

**Acceptance:** a tablist whose tab is `image "symbol:camera"` over a label shows a
`UITabBar` item on iOS under `--chrome platform`, and the role's path on the web, in
actual screenshots. Swapping in `symbol:sf/camera` draws on iOS and is empty on the
web, where `layout` says why. Another role in the same bar (`home`) shows that the
camera isn't special-cased.

## 4. Scope and verification

Use existing scripts, fixtures and test suites. Narrow regression tests are useful
when a reproduced parser, lock, projection or driver bug is repaired; documentation
edits do not need tests that repeat their wording. Apply the repository's required
checks and app drives to each implementation, with slow native work on the existing
async path. There is no new blocking gate, benchmark framework or feedback registry.

Priority reflects the expected benefit from this sample, not prevalence or a P0
classification. D1 repeats across encounters; D2 caused many retries in one app;
D3 had the largest single estimated time cost; D4 is narrower. D3's first step and
D4's role are each a few lines, so they can go first without waiting on the rest.
D5 can establish which remaining proposals are still necessary.
