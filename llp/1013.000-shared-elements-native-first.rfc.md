# LLP 1013.000: Shared elements, native first

**Type:** RFC
**Status:** Draft r4, 2026-10-04. r1–r3 took Charlie's rulings on Q1–Q4; r4 takes review round 1 (Astra max and Grok 4.7 xhigh, both NOT READY on r3: §7) and stages the design. Stage 1 is being built by Claude (Opus 5.5) at Charlie's word, 2026-10-04 ("go ahead and implement it").
**Supersedes:** LLP 1013's executor (D3, D4) and boundary (D2). Its identity-by-name rule (D1) is kept, as an Exact attribute.
**Systems:** Kernel (one prop; `CommitReceipt::handoffs`), Motion (none: a flight is an existing `Layout` curve on a host-owned node), Apple host (flights: lift, interpolate, land), Web host and JS target (`startViewTransition`), Contract (one attribute), the agent (flights on the clock)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-10-04
**Related:** LLP 1013 (the web's way, which this revises); LLP 1063 (exits, `layout-transition`, the web's presence glue); LLP 1002 D2–D4 (two executors, the seek, holds); LLP 1035.001 (`navigationSource`, `ModalIOS.swift`'s zoom); LLP 1041 §8.5 item 2 (photo collection and interactive zoom); LLP 1070.000 (`scrollIntoView` by key); LLP 1081 (names Exact invents); `rules/DEFERRED.md` (2026-09-16: "Shared-element presentation and the bounded geometry/motion work those consumers need are admitted"); CSS View Transitions Module Level 1

## Summary

Charlie, 2026-10-04: *"the philosophy of exact is that the web is the standard.
BUT, every platform should be able to express its best self fully — no lowest
common denominator sanding down. let's design something that will work best on
native platforms and ideally work in some fashion on the web."*

LLP 1013 made the browser's View Transitions the model and had native hosts
copy them: snapshots, a fixed curve, one transition at a time. This RFC keeps
what every framework agrees on, identity by a *name* (SwiftUI
`matchedGeometryEffect`, Compose `sharedElement`, Flutter `Hero`, Framer
`layoutId`), and lets each platform run it as well as it can:

- **Natively, the arriving element flies live.** The real view, not a
  snapshot, is lifted above its route's content and moves from where the
  leaving element was to its own place, then is put back. An image's crop
  morphs on the way (a `cover` thumbnail opens into a `contain` photo). The
  host interpolates between the two rectangles on one engine curve, as UIKit's
  zoom does, so the destination can move (a scroll settling) and the flight
  still lands on it. A change mid-flight starts a new flight from where the
  element is.
- **The destination comes into view first.** If the element's place is
  scrolled out of view, it is scrolled into view, then the flight lands there,
  as Photos does.
- **The web runs CSS View Transitions,** the platform's own feature, with the
  same pairs and the same curve.
- **Across routes, iOS keeps UIKit's zoom** (`navigationSource`, LLP
  1035.001), unchanged.

## 1. What it looks like

```
style Photo
  layout-transition="spring(300, 30, 1)"

component Grid
  view
    scroll
      each photo in photos key=photo.id
        button press=open(photo.id)
          image photo.asset sharedElement=`photo-${photo.id}` class=Photo object-fit="cover" height=120 …

component Viewer
  view
    image viewer.asset sharedElement=`photo-${viewer.id}` object-fit="contain" width="100%" height="100%" …
```

(LLP 1081 would spell the row `-exact-layout-transition` and the function
`-exact-spring()`.) Tapping a photo destroys the grid and creates the viewer
in one commit. The viewer's image starts at the thumbnail's box and crop and
springs to its place. Close reverses: the thumbnail flies back from wherever
the viewer's image is, mid-flight or not. Only one side needs the curve (D2).

## 2. Decisions

**D1 — Identity is the `sharedElement` attribute.** One new string prop,
`sharedElement` (`kernel/tables/schema.json`), mapped in Contract's tag table.
**Ruled (Charlie, 2026-10-04, Q1):** "if our behavior differs from the web, the
name should be different." It differs from CSS's `view-transition-name`, which
does nothing until script calls `startViewTransition()` and animates
snapshots. It is an attribute, not a CSS property, for the reasons
`navigationSource` and `testId` are: it names a thing rather than styling it,
and its values are dynamic strings (`photo-${id}`), which props carry and a
style row's interned codecs do not. On the web it is lowered to
`view-transition-name` for the transitions it runs (D7).

Names need not be unique in the tree. A pair is formed by *change*, not by
lookup (D3), so a route stack can hold the same name in two mounted routes
(both reviewers' must-fix on r3's uniqueness rule).

**D2 — A pair flies when either end declares `layout-transition`.** In a
commit where a name leaves node A and arrives at node B, B flies on B's
`layout-transition`, else A's (the leaver's row as it was). With neither,
nothing moves. The boundary is the commit; there is no action keyword (1013
D2): with no page snapshots there is nothing to keep a timer's commit out of.

**D3 — The kernel reports pairs.** `CommitReceipt` gains `handoffs: Vec<Handoff>`,
`{ name, from, to, transition }`. A name *leaves* A when the commit destroys A
(directly or with an ancestor; A's subtree is walked at destroy, as exits and
selectors already are). It *arrives* at B when the commit creates B with the
prop. A name left and arrived exactly once in the commit pairs; a name with
two leavers or two arrivers pairs nothing. Stage 1 does not pair a prop
changed on a live node. `transition` is D2's choice, resolved by the kernel,
which has both rows.

**D4 — Natively a flight is a host interpolation on one engine curve.** For a
handoff the Rust host starts a curve on a host-owned motion node (the
arriver's key with a flight bit; never on the wire), using the engine's
existing `Layout` property: first seen at 0, then observed at 1000 under D2's
declaration. So springs, easings, the agent's seekable clock and
`settle_time` all apply unchanged, and no new engine property is needed. Each
frame the presenter receives the curve's progress (`present … "flight"`), and
`land` when it settles.

The Apple presenter owns the geometry, which is host state (Astra and Grok,
r3 must-fix: presented boxes and scroll offsets are not the kernel's):

1. **Capture before teardown.** The `flight` op precedes the batch's destroys.
   The presenter records A's presented rectangle (its presentation layer,
   converted to window coordinates, so ancestors' transforms, scroll offsets
   and a drag in progress are all included), its corner radius, and for an
   image its drawn crop (the fitted image rectangle relative to the box).
   If A is itself mid-flight, its current interpolated rectangle and crop.
2. **Bring the destination into view** (D5), after the batch is applied.
3. **Lift.** B's view moves into a flight container: a pass-through view that
   is the last subview of the root view of the controller presenting B (a
   route, a sheet or a fullscreen presentation), so a flight inside a modal
   stays inside it. B is not hit-testable and is hidden from accessibility
   for the flight. B's place in its parent stays laid out and empty.
4. **Interpolate.** Each frame `shown = lerp(from, to, p)` for the box and
   the radius, with `to` re-read every frame from B's slot in window
   coordinates (UIKit's zoom re-asks its source the same way). For an `image`,
   the drawn crop interpolates from A's to B's own fit, clipped to the shown
   box: frame 0 shows A's framing, the last frame B's. Any other node shows
   its surface at the shown box with its children at their laid-out places
   (LLP 1063 D6's rule).
5. **Land.** On `land`, B goes back into its parent at its laid-out frame, its
   own radius, hit-testing and accessibility.

The curve's progress can overshoot under a spring; the rectangle overshoots
with it.

**D5 — The destination comes into view first.** **Ruled (Charlie, 2026-10-04,
Q3):** "try to do what Photos does." Before step 3, each scroller between B's
slot and the flight container is scrolled, innermost first, by the least
amount that shows the slot whole (`scrollIntoView`'s `nearest`), instantly. A
scroll view reports the move as any scroll, so app state that reads
`scrollTop` agrees and a virtualized list builds what now shows. A slot that
already shows is not moved.

A row a virtualized list has not built holds no node, so no name: nothing can
arrive there. The app names the returning item with the command it has:

```
action close
  scrollIntoView("grid", open, block="nearest")
  open = ""
```

`scrollIntoView` builds the row's window at its destination within the
action's commit (LLP 1070.000 §2.3), so B exists when the kernel pairs. Without
the line there is no arriver and no flight. A list's correcting reports after
that move the slot by a few points; since the flight re-reads `to` each frame
(D4.4), it lands where the row finally is.

**D6 — Interruption starts a new flight from the shown rectangle.** Close
while the viewer is opening destroys the viewer's image (the arriver, still
flying) and creates a thumbnail: a new handoff whose `from` is captured from
the flying view's current interpolated rectangle and crop (D4.1). The new
curve starts from rest. Velocity is not carried in stage 1: the position is
continuous, the speed is not (Q5).

**D7 — The web runs CSS View Transitions.** **Ruled (Charlie, 2026-10-04,
Q4):** "make the web behavior as idiomatic and canonical as possible." The JS
target flushes its effects directly rather than consuming kernel batches
(Astra), so the integration is in its commit:

- **When.** Before a commit's flush, if the app carries `sharedElement` and a
  region (`when`, `match`) or `each` about to rerun currently holds an element
  with the attribute, the flush runs inside
  `document.startViewTransition(update)`. Named leavers are given
  `view-transition-name` before the call; inside `update`, after the flush,
  each new element whose name matches a captured leaver gets the same
  `view-transition-name` and its group the pair's curve
  (`::view-transition-group(…)` duration and timing, a spring lowered to
  `linear()`). If no pair formed, or none has a curve, the transition is
  skipped (`skipTransition()`), and the update still runs, as the browser
  defines.
- **Order.** The browser calls `update` asynchronously. Until it has run,
  later commits change state but do not flush; their effects stay queued and
  `update` flushes them all, so no commit overtakes another. A second paired
  commit while a transition animates skips the running one first.
- **Leavers that also exit.** A leaver with `exit-animation` is not given the
  presence ghost: the transition is its exit.
- **Scrolling.** Inside `update`, after the flush, each arriver is scrolled
  into view (`scrollIntoView({block: "nearest", inline: "nearest", behavior:
  "instant"})`) before the browser captures the new state.
- **The agent.** The transition's animations are in `document.getAnimations()`
  once its `ready` promise resolves; the driver waits for it before seeking.
- **Unsupported or reduced motion.** Without `startViewTransition`, or under
  `prefers-reduced-motion: reduce`, the flush runs directly and cuts.

What the web gives up: the old image is a snapshot; a transition can't be
caught mid-flight (a new one skips it); input waits for the pseudo-element
overlay. That is the browser's model, and it improves as browsers do.

**D8 — Reduced motion lands at once.** On Apple, under Reduce Motion, a flight
is not lifted: B appears in place (the progress curve still runs, so the
agent's clock behaves the same). On the web, D7. This is host policy, since
`prefersReducedMotion` is a viewport fact the app reads, not a rewrite of its
rows (Grok).

**D9 — The agent sees flights.** The curve is an engine curve, so
`clock settle` waits for it, and a screenshot film shows it.

## 3. Staging

- **Stage 1 (this build):** D1–D9 on iOS and macOS, the web (JS target) and
  the agent; Linux journals `shared element: flights are not drawn on Linux
  (LLP 1013.000)` once and cuts, as it refuses exits (LLP 1063 D8). The example
  app, `apps/shared-elements`, exercises every form (§4).
- **Stage 2:** velocity carried into a new flight (a release's, a flight's);
  drag-to-dismiss handing a hold's velocity to the flight back.
- **Stage 3:** a name on the zoom's source (`navigationSource` naming a
  `sharedElement`, so one name serves both), and element flights across
  route pushes, which **Q2 (ruled 2026-10-04: "rec is ok for now")** defers.
- **Not planned:** a flying ghost of the leaver (r3's D5). Both reviewers
  found it doubles the photo and needs a nested-destroy path exits don't have.

## 4. The example app and its checks

`apps/shared-elements` has one screen per form:

1. **Grid → viewer** (`when` flip, eager scroll): open, close, close
   mid-open (reverse), scroll the grid so the photo is out of view then close
   (D5's scroll).
2. **Virtualized grid → viewer:** step the viewer to a photo whose row was
   never built, close with `scrollIntoView` (D5's command).
3. **Card → detail** (a box with children; D4.4's surface rule).
4. **Move between lists** (an `each` row moving between two lists by key:
   destroyed in one, created in the other).
5. **Zoom across a route** (`navigationSource`, iOS 18).

Checks, by `scripts/agent.mjs` with the clock: at progress 0 the arriver's
shown box equals the leaver's box (within 0.5 pt), at settle its slot; a
close at 40% starts from the 40% box; D5's scroll puts the slot in view before
the first frame; native and web settle at the same clock time for the same
curve.

## 5. Costs

- **Kernel:** one prop; `Handoff` and its pairing in `txn.rs`.
- **Contract:** one tag-table line.
- **Apple Rust host:** `flights.rs`: start, present and land; the `flight` op
  before destroys.
- **Apple Swift:** flight capture, lift, interpolation and landing for UIKit
  and AppKit; image crop drawing during a flight.
- **Web JS target:** a loaded piece `shared.js` and hooks in `rt.js`'s
  commit; the agent's wait for `ready`.
- **Example app and checks:** §4.

`rules/DEFERRED.md` admits shared-element presentation (2026-09-16). This adds
no plan portal (the lift is host state), no layout per frame, no new engine
property, no progress value in the plan, and no Core Animation executor.
LLP 1013's QUEUE item becomes this RFC.

## 6. Open questions

- **Q5. Velocity.** Stage 2 carries a flight's or a release's velocity into
  the next flight. The progress curve's velocity is in its own units; mapping
  it needs the rectangles, which only the presenter has.
- **Q6. Android.** No host yet (LLP 1076). Compose's `SharedTransitionLayout`
  renders the live element in an overlay with an interruptible bounds
  transform: the same model as D4.

## 7. Review round 1 (r3), dispositions

Astra (`gpt-6-astra`, max) and Grok (`grok-4.7`, xhigh), blind, on r3 (brief
sha256 `60eb07eb…96ee`); both NOT READY. Kept at
`llp/reviews/1013.000-shared-elements.{astra,grok}.md`.

- *Uniqueness contradicts the zoom* (both): taken. Pairs form by change (D1,
  D3); the zoom keeps `navigationSource` (stage 3 unifies).
- *Geometry is host state; `Layout` is parent-relative* (both): taken. The
  presenter captures and interpolates window rectangles; the engine supplies
  only progress (D4).
- *The leaver can't be an exit ghost* (both): taken. No leaver ghost (§3).
- *Drag takeover isn't built; the backdrop dies with the viewer* (both):
  taken. Moved to stage 2; a drag in progress still sets where the flight
  starts (D4.1).
- *Lifting breaks modal containment, hit-testing, accessibility* (both):
  taken. A per-presentation container, no hits, hidden from accessibility
  during the flight (D4.3).
- *The JS target has no batch hook; `startViewTransition` is async* (Astra):
  taken (D7's order).
- *Scrolling ordering* (both): taken. The host scrolls after apply and before
  the flight; unbuilt rows need the app's command (D5).
- *Browser contract details* (both): taken. Names only on paired elements, no
  presence ghost for a paired leaver, skip-then-start (D7). Astra's point that
  the browser updates the destination during the animation removed r3's claim
  that the web lands off.
- *The crop doesn't morph with `contentsGravity`* (Grok); *radius isn't an
  engine property* (both): taken. Crop and radius are interpolated by the
  presenter (D4.4).
- *Only the arriver had the curve* (both): taken (D2).
- *Reduced motion isn't a producer rewrite* (Grok): taken (D8).
