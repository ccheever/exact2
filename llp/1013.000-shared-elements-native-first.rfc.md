# LLP 1013.000: Shared elements, native first

**Type:** RFC
**Status:** Draft r3, 2026-10-04 (r2: Charlie's rulings on Q1 and Q4; r3: on Q2 and Q3, which adds D6.1). Nothing here is built. No implementer or date yet (`rules/RULES.md` §Scope); this is the design to rule on.
**Supersedes:** LLP 1013's executor (D3, D4) and boundary (D2). Its identity-by-name rule (D1) is kept, under an `-exact-` name.
**Systems:** Kernel (one style row; a receipt list), Motion (a layout transition seeded from another node), Apple host (the flight layer; UIKit's zoom for routes), Linux host (painted flights), Web host (`startViewTransition`), Contract (one attribute), the agent (flights on the clock)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-10-04
**Related:** LLP 1013 (the web's way, which this revises); LLP 1063 D3–D6 (the receipt's exits, the ghost, layout moving by offset and surface); LLP 1002 D2–D4 (two executors, the seek, holds); LLP 1057.003 (gesture timelines); LLP 1035.001 (`navigationPresentation="fullscreen"`, `navigationSource`, `ModalIOS.swift`'s zoom); LLP 1041 §8.5 item 2 (photo collection and interactive zoom: the acceptance case); LLP 1081 (names Exact invents are spelled `-exact-`); `rules/DEFERRED.md` (2026-09-16: "Shared-element presentation and the bounded geometry/motion work those consumers need are admitted"); CSS View Transitions Module Level 1

## Summary

Charlie, 2026-10-04: *"the philosophy of exact is that the web is the standard.
BUT, every platform should be able to express its best self fully — no lowest
common denominator sanding down. let's design something that will work best on
native platforms and ideally work in some fashion on the web."*

LLP 1013 made the browser's View Transitions the model and had native hosts
copy them: snapshots, a fixed curve, one transition at a time. That is the
lowest common denominator. A snapshot freezes what it shows, a second
transition skips the first to its end, input stops during the flight, and
nothing can be grabbed. On iOS, people judge hero transitions against Photos
and the system zoom, which do all of those things. LLP 1041 §8.5 already said
so: "LLP 1013 is a starting design, not evidence that snapshot transitions
already provide interactive takeover."

This RFC keeps the part of 1013 every framework agrees on. Identity is a
*name*, because a `when` flip destroys one node and creates another. SwiftUI
(`matchedGeometryEffect`), Compose (`sharedElement`), Flutter (`Hero`) and
Framer Motion (`layoutId`) all work that way. It replaces the rest:

- **Natively the shared element flies live.** The incoming node is the real
  view from its first frame, lifted above the content for the flight and put
  back after. It keeps drawing and stays hit-testable.
- **A flight is a layout transition from somewhere else.** LLP 1063 already
  moves a node from its old box to its new one, interrupts from the presented
  value, carries velocity and seeks on the agent's clock. A shared element is
  the same transition with its first box taken from the node that had the name
  before. Almost all the machinery exists.
- **Grabbing and reversing work.** A new commit mid-flight retargets from
  where the element is, with its velocity. A drag's release hands its velocity
  to the flight back, which is drag-to-dismiss.
- **Across routes, iOS uses UIKit's zoom.** That is the platform's own hero,
  with its own interactive dismissal. Messages already uses it through
  `navigationSource`; a name generalizes that.
- **The web uses `startViewTransition`.** It runs the same pairs on the same
  curve with the browser's snapshots. It can't grab or keep a flight running
  through a second one. That is the web doing what it can, not native doing
  less.

## 1. What it looks like

The interaction gallery's photos (LLP 1041 §8.5 item 2) already flip between
a grid and a viewer with `when gallery.viewerOpen`. Two attributes make the
photo fly:

```
style Hero
  layout-transition="spring(300, 30, 1)"

component PhotoCard
  view
    button press=command("open", photo.id, 0) …
      image photo.asset -exact-shared-element=`photo-${photo.id}` object-fit="cover" height=190 …

component Viewer
  view
    …
      image viewer.asset -exact-shared-element=`photo-${viewer.id}` class=Hero object-fit="contain" …
```

Tapping a card removes the grid and creates the viewer in one commit. The
viewer's image starts where the card's image was, at its size and corner
radius, and springs to its place. It is the viewer's own image throughout: it
decodes the full asset, and the pan, pinch and drag bindings on it work
mid-flight. The card's image leaves as an exit ghost, flying the same path and
fading. Pressing Close mid-flight reverses from where the image is. Dragging
the photo down and letting go closes the viewer, and the image flies back to
its card from where the finger left it, at the speed it was thrown. If the
grid has scrolled, or the viewer was swiped to a photo whose card was never on
screen, the grid scrolls to that card first and the image lands in it, as
Photos does (D6.1).

## 2. Decisions

**D1 — Identity is `-exact-shared-element`.** One new row,
`shared_element` in `kernel/tables/schema.json`. As in 1013 D1 it uses the
`font_family` codec precedent: the producer interns the author's string, and
the kernel and hosts carry a `u16` where `0` is `none`. In Contract it is
`-exact-shared-element=…`. A name is unique among live nodes in a session. A
second live holder is a `lower`/runtime error in development and is ignored
(no pair) in production, as the browser skips a transition with a duplicate
name.

**Ruled (Charlie, 2026-10-04, Q1):** "if our behavior differs from the web, the
name should be different." It differs: CSS's `view-transition-name` does
nothing until script calls `startViewTransition()`, and its flights are
snapshots; this one flies on a commit (D2), live and interruptible natively.
So it is an Exact name (LLP 1081), and `view-transition-name` stays free for
CSS's own meaning. On the web the host lowers it to the real
`view-transition-name` (D9), which is where the two meet.

**D2 — A pair flies when its destination has `layout-transition`.** The
boundary is the commit, the way layout motion already works, and the opt-in is
the row an author already uses to say how a box moves (LLP 1063 D1). In a
commit where a name leaves node A and arrives at node B, B flies if B declares
`layout-transition`. The curve is that row's: an easing or `spring()`. A name
"leaves" A when A is destroyed or its row is cleared or changed; it "arrives"
at B when B is created or its row is set. A and B are paired only within one
commit.

Without `layout-transition` on B the name does nothing.

*Rejected:* 1013 D2's action keyword. It was there to keep a one-second tick
from snapshotting the page. With no snapshots of the page there is nothing to
keep out, and the keyword would be a second way to say "this animates" next to
`layout-transition`. A timer that swaps a named node flies, as a timer that
moves a box with `layout-transition` slides today.

**D3 — The kernel reports pairs.** `CommitReceipt` gains `handoffs`, beside
`exits` (LLP 1063 D3): `(name, from, to)` for each name that left one node and
arrived at another in the commit. The kernel already knows both ends: it lists
destroyed exit roots and computes `layout_box` for created nodes. Not listed:
a name that arrives with no leaver (B appears normally, with its own
`animation` if any), one that leaves with no arriver (A exits normally), and
any node inside a subtree that the same commit creates or destroys whose root
also holds a name. The outermost pair flies; nested pairs ride along, as nested
exits do.

The leaver's box is its *presented* box: its laid-out box plus every
presentation value on it and its ancestors (translate, scale, a layout offset
still in flight, a drag hold). That is what makes interruption and
drag-to-dismiss continuous (D6, D7). Each host already reads it from its
presenter (Apple: the presentation layer's frame in window coordinates; web:
`getBoundingClientRect`).

**D4 — Natively the arriving node flies live, lifted above the content.**
Each window gets one host-owned **flight layer**. It is above route content
and below the host's presentations, and it is never a kernel node, as scroll
offset is host state. On a handoff the host:

1. lays out normally, so B has its final box and siblings take their places;
2. moves B's view (the live `NodeView`, with its subtree) into the flight
   layer, at A's presented box in window coordinates;
3. animates B's shown box from A's box to B's slot with the engine's
   existing `Layout` property (origin and size; LLP 1063 D6), seeded with A's
   box and A's velocity (D5). The slot is B's laid-out box in window
   coordinates, read each frame: if a scroller under it moves during the
   flight (D6.1's corrections, or the reader scrolling), the flight follows it,
   as UIKit's zoom re-asks its source provider;
4. puts B back into its parent, at its laid-out frame, when the transition
   settles. Its slot in the parent keeps its laid-out space throughout, empty.

B is not a snapshot. It keeps drawing (an image finishing its decode, a video
playing, a counter ticking), receives input and stays in the accessibility tree
at its *final* frame (VoiceOver reads the destination, not the path). Clipping
is why it is lifted: a thumbnail inside a scroll view, or under
`overflow: hidden`, would otherwise be cut off on its way out. The layer holds
nothing when nothing flies. A flight's lifetime is the transition's, so no
view is pinned indefinitely (LLP 1041 §8.5's bound).

Size follows LLP 1063 D6, with one addition for replaced content:

- A **box with children** shows its *surface* at the flight's size
  (background, border, radius, shadow, and its clip as a mask), while its
  children sit at their final geometry. A card that becomes a screen reveals
  its body under its title. Nothing is scaled, and nothing is laid out per
  frame.
- A **replaced element** (`image`, `video`, a canvas surface) draws its
  content into the shown box by its `object-fit`, each frame. That is drawing,
  not layout: on Apple it is the layer's bounds with `contentsGravity` from
  `object-fit`, which Core Animation interpolates itself. The thumbnail's
  `cover` crop opens into the viewer's `contain`, which is what Photos does.
  The crop is B's `object-fit` throughout. A cross-fit (`cover` into `contain`)
  takes B's.

`border-radius` and the other surface rows interpolate from A's values to B's
over the flight on the same curve. They are surface paint, not layout.

**D5 — The leaver flies too, then fades.** If A was destroyed it becomes an
exit ghost (LLP 1063 D4: out of layout, inert, hidden from accessibility, ids
stripped). Unlike a plain exit, its shown box follows B's for the flight, on
the same curve, at the same size, under the same D4 rules, in the flight layer
below B. Its opacity goes to 0:

- If A declares `exit-animation`, that plays instead of the fade, so an author
  can choose a faster fade, none, or a scale.
- Otherwise it fades over the first half of the flight. B is opaque from its
  first frame. The browser's default crossfade (both at half, `plus-lighter`)
  makes two images of one photo visibly double; native heroes don't do it.
  The web keeps its own (D9).

If A survives (its name moved to another node, A still live), it stays where it
is and nothing ghosts. B flies from A's box over a still-present A, the way a
dragged item's preview leaves its slot.

Linux refuses the ghost as it refuses exits (LLP 1063 D8). B still flies, and
the journal records `shared element: leaver not drawn on Linux (LLP 1013.000)`
once.

**D6 — Interruption is a retarget.** A flight is an engine transition, so a
commit during it is handled as CSS Transitions §3 and LLP 1002 D2 handle every
interruption: from the current presented value, keeping a spring's velocity.

- **Reverse.** Close during the open flight moves the name from the viewer's
  image back to a card. The card's image becomes B and flies from the viewer
  image's *presented* box, mid-path, with its velocity. The viewer image
  becomes the ghost.
- **Retarget.** Switching photos mid-flight moves the name to another node;
  the new B starts from where the old B is.
- **No pair.** If the destination is gone (the card was deleted, or a filter
  removed it), there is no arriver. The flying view exits in place from its
  presented box, by its own `exit-animation` or a fade. A destination that
  exists but is scrolled out of view is not gone: D6.1 brings it into view.
  These are the "unmounted, moved or deleted source" outcomes LLP 1041 §8.5
  asked to be defined.

**D6.1 — The destination comes into view first.** **Ruled (Charlie,
2026-10-04, Q3):** "try to do what Photos does." Photos never flies a photo
back to a point off screen; it scrolls the grid so the photo's cell is showing,
then lands in it. So, in a commit with a handoff, before the flight's first
frame, B's slot is scrolled into view by `block="nearest"` and
`inline="nearest"` (the web's `scrollIntoView` options: no scroll if it already
shows whole, else the least scroll that shows it). Instant, never smooth: the
outgoing view covers the grid at that moment, and the flight is the motion.
Three cases, by where B is:

1. **In an ordinary scroller** (an eager `scroll`): the host scrolls every
   scroller between B and the window, innermost first, and reports the new
   offsets as it reports any scroll, so app state that reads `scrollTop`
   agrees. This is a host-initiated scroll, like the browser's
   `scrollIntoView`; it needs nothing from the app.
2. **In a mounted row of a virtualized list:** the runner issues LLP
   1070.000's request for that row, `scrollIntoView(list, key, block="nearest")`,
   in the same commit. It knows the row because B is in its subtree. Its
   measure-and-correct reports (1070.000 §2.4) may move the slot for a few
   frames after the flight starts; the flight follows the slot (D4 step 3), so
   a correction bends the path instead of making the image land in the wrong
   place.
3. **In a row the list has not built:** nothing holds the name, because
   names are rows on nodes and an unbuilt row has no nodes. The runner can't
   find it without building every row. The app's action says which item is
   returning, with the command it already has:
   ```
   action close writes open
     scrollIntoView("photos", open, block="nearest")
     open = ""
   ```
   1070.000 builds the row's window at its destination in the action's commit
   (§2.3, "the window is realized at the destination before any host moves"),
   so B exists when the kernel computes the handoff, and case 2 applies. Without
   the line, case 3 has no arriver and the image exits in place, as for a
   deleted source; development builds journal `shared element: <name> has no
   arriver; is its row unbuilt? (LLP 1013.000 D6.1)` once per name, so the
   missing line is findable.

On the web the same scrolls run inside the `startViewTransition` update
callback, after the batch applies and before the callback returns, so the
browser's new capture already has the card showing. A virtualized list's later
corrections move the page under the transition; the group's end box was
captured before them, so on the web the image can land a few points off and
jump. Declared, and measured by the fixture.

A source scrolled out of view in a windowed list with smooth `scroll-behavior`
still scrolls instantly here: a flight following a smooth traversal across
unbuilt rows (1070.000 §11) would show blank spacers under it.

**D7 — Drag-to-dismiss is a hold handing its velocity to a flight.** The
pieces are built:

- the viewer's image is dragged by an existing binding (`pan`/`panrelease` or
  `transformDragFor`, LLP 1002 D4), with the finger exact and no app code per
  frame;
- the backdrop fades with the drag through a gesture timeline (LLP 1057.003),
  bound to the image's presented translate;
- release past a threshold runs an action that closes the viewer.

That close is a handoff whose leaver is the dragged image. D3's presented box
includes the hold, so the flight back starts under the finger, and the hold's
release velocity seeds the flight's spring (`Engine` gains one entry:
`seed_layout(node, from_box, velocity)`; the hold's `Release{velocity}` already
carries it). Release short of the threshold springs back by the hold, as today.
The backdrop keeps following the image, now driven by the flight, because a
timeline follows the presented value whatever moves it.

What is *not* here: a transition-progress value in the plan, or scrubbing a
flight with a finger before the commit that starts it. The drag is the scrub,
and the commit happens at release. LLP 1035.001 §6 excludes a progress value,
and this needs none.

**D8 — Across routes, iOS uses UIKit's zoom.** A route push, or a
`navigationPresentation="fullscreen"` route, whose incoming content holds a name
also held in the outgoing route is presented with
`preferredTransition = .zoom` (iOS 18+). The host resolves the source when
UIKit asks for it (`sourceViewProvider`), as `ModalIOS.swift` does today for
`navigationSource`. The destination aligns to the named node's box
(`alignmentRectProvider`). Interactive dismissal, its gesture and its timing
are UIKit's, and `closedby` refusal keeps working through
`interactiveDismissShouldBegin` (LLP 1035.001).

This replaces `navigationSource`, which names an HTML id for the same job. It
is deleted, and Messages puts `-exact-shared-element` on the contact photo and
the details header instead (`rules/RULES.md`: delete, don't deprecate).

Within a route, D4's flight runs. Across routes, on hosts with no platform
zoom (macOS, iOS 17, Linux), the route transition is the host's ordinary one
and nothing flies. A flight between two routes would have to run inside
UIKit's or AppKit's transition container with a custom animator. That is Q2.

**D9 — The web runs pairs with `startViewTransition`.** The web host sees
D3's pairs in the batch. A batch carrying a pair whose destination declares
`layout-transition` is applied inside `document.startViewTransition(() =>
apply(batch))`, with:

- `view-transition-name: v<n>` on each named element, and
  `:root { view-transition-name: none }`, so only pairs move (1013 D3);
- the pair's curve on its group, `::view-transition-group(v<n>) {
  animation-duration: …; animation-timing-function: … }`, from B's
  `layout-transition`. A spring is lowered to a `linear()` from the engine's
  frames, as `motion-glue.js` already lowers springs;
- a leaver's `exit-animation`, if it declares one, on
  `::view-transition-old(v<n>)`.

What the web gives up, honestly:

- **Snapshots.** The old image is a still picture. The new one is the live
  element, but its box animates toward where it was when the transition
  started, so it doesn't follow later movement (D6.1's corrections).
- **No interruption.** A second paired batch during a flight skips the first
  to its end (`skipTransition()`) and starts from there.
- **Input waits.** The pseudo-element overlay covers the page for the flight.
- **No velocity.** A drag's release starts the flight from the presented box
  (the snapshot captures the dragged transform), on the fixed curve.
- **The browser's crossfade.** The old and new images blend at half, which D5
  avoids natively.

Where `startViewTransition` is absent the batch applies and cuts. The JS
target (LLP 1071) and the wasm target share this: it lives in the glue that
applies batches. There is deliberately no Exact-built live tier on the web (Q4).

**D10 — The agent sees flights.** A flight is an engine transition and a ghost
is an engine exit, so `settle_time()` includes both and `clock settle` waits for
them (LLP 1012). `tree` reports a flying node at its final frame with
`flight: {from, shown}` (the drive reads where it ends up, and can see that it
is moving). On the web the group's animations are in `document.getAnimations()`,
which the agent's seek already walks; the parity fixture checks that it
actually seeks them.

**D11 — Reduced motion cuts.** The producer emits `transition: none` under
reduced motion (`rules/DEFERRED.md` §Motion). It must clear `layout-transition`
too, so that D2 flies nothing; whether it does today is unchecked, and if not,
that is a one-line change. iOS's zoom follows the system's own reduced-motion
setting (a crossfade).

## 3. Held by fixture

One case, the gallery's photos (LLP 1041 §8.5 item 2), run on iOS (simulator,
then a phone), macOS, web and Linux by `scripts/agent.mjs`:

1. Open: at 0 ms the viewer image's shown box equals the card image's box
   (within 0.5 pt); at settle, its laid-out box. The same samples at 25%, 50%,
   75% of the curve agree across native hosts within 1e-3 of the box, and with
   the web's group box (read from `getAnimations()`) within the same band. The
   web's content inside the box is a snapshot and is not compared.
2. Close mid-flight at 40%: the reverse starts from the 40% box, with no jump
   (native); the web skips to the end and flies back (declared).
3. Drag down 120 pt and release at 900 pt/s: the flight starts at the dragged
   box and its initial velocity is the release's (native).
4. Delete the source card while the viewer is open, then close: no flight; the
   image exits in place.
5. Photos' return (D6.1): (a) scroll the grid so the source card is out of
   view, open, close: the grid is scrolled so the card shows (`nearest`), and
   the image lands in it; (b) in the windowed rendering, open the first photo,
   swipe the viewer to the fortieth (never built), close with the
   `scrollIntoView` line: the fortieth card is built, scrolled into view and
   landed in, within 0.5 pt at settle (native and web); (c) the same without the
   line: no flight, one journal line.
6. A video in the viewer keeps playing through the flight (native, by pixel
   difference between two flight frames inside the box).
7. Tap the viewer's Close button at 50% of the open flight: the tap lands
   (native).
8. Messages: the contact photo zooms to details through D8, and the ten
   physical cases of LLP 1035.001 still pass after `navigationSource` is gone.

## 4. Costs

- **Kernel:** one row; `CommitReceipt::handoffs`; the duplicate-name check.
- **Contract:** one attribute in the tag table; the duplicate-literal check.
- **Motion:** `Engine::seed_layout` (a `Layout` transition whose start is a
  given box and velocity, not the node's previous box). Surface-row
  interpolation between two nodes' values (the rows already transition on one
  node).
- **Apple:** the flight layer (lift, place, return; a few hundred lines in a
  new `FlightIOS.swift` / `FlightMac.swift`); a ghost that follows a flight
  instead of staying put (`PresenceIOS.swift`); `contentsGravity` from
  `object-fit` on a flying replaced element; D8's provider from a name, and
  `navigationSource` deleted.
- **Runner:** D6.1 case 2's implicit `scrollIntoView` for a handoff whose
  arriver is in a virtualized row.
- **Linux:** paint B at its shown box after everything else; no ghost; D6.1's
  scroll.
- **Web:** the `startViewTransition` wrapper and group CSS in the batch glue;
  `:root` rule; D6.1's scroll inside the update callback.
- **Fixture:** §3, in the gallery and Messages.

`rules/DEFERRED.md` already admits shared-element presentation for these
consumers (2026-09-16). This adds no plan-level portal: the lift is host state,
like a scroll offset. It adds no layout per frame, no gesture arena, no
progress value and no Core Animation executor (a `contentsGravity` resize is
Core Animation drawing a layer the engine sizes). Nothing comes off the list.
LLP 1013's QUEUE item 5 becomes this RFC, still behind the webview/deck lane
unless Charlie moves it.

## 5. Open questions

- **Q1.** Ruled: an `-exact-` name (D1).
- **Q2.** Ruled (Charlie, 2026-10-04: "rec is ok for now"): no element
  flights across routes in this RFC. Across a push or fullscreen presentation,
  iOS 18+ zooms (D8), and every other host uses its ordinary transition. A
  custom `UIViewControllerAnimatedTransitioning` running D4's flight inside
  UIKit's transition, with the interactive pop driving it, waits for an app
  that needs an element to fly across a push rather than a zoom.
- **Q3.** Ruled (Charlie, 2026-10-04: "try to do what Photos does"): D6.1.
- **Q4.** Ruled (Charlie, 2026-10-04: "make the web behavior as idiomatic and
  canonical as possible"): the web runs CSS View Transitions, the platform's
  own feature, and nothing Exact builds in its place (D9). Rejected: a live web
  tier from LLP 1063's FLIP and `Element.moveBefore()`. It would out-build the
  browser rather than use it. The web's flights improve as the browser's do.
- **Q5. Android.** There's no host yet (LLP 1076). Compose's
  `SharedTransitionLayout` with `sharedBounds` renders the live element in an
  overlay with an interruptible bounds transform: the same model as D4, so this
  design should map onto it directly when a host exists.
