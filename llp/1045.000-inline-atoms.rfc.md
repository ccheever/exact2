## 1. Summary

An **atom** is a span of a Markdown source that the editor and the reader show as one
pill: a label that is not its source, an optional icon, and a tooltip. A caret cannot
stand inside it, a selection takes it whole, Backspace removes it whole, and a press on
it is an `atompress` with its source and destination. The value stays the Markdown
string (LLP 1045 D1): an atom is a way of drawing and editing source, not a value type.

An app declares which spans are atoms by their source form:

- a **scheme link**: a link (or image link) whose destination has a scheme the app names,
  `[Assistant quote](t3-citation://v1/…)`, `![shot.png](t3-context://v1/image/7)`;
- a **relative link**: a link with no scheme, `[main.rs](src/main.rs)`, when the app
  gives it a face;
- a **prefix token**: a character the app names (`@`, `$`) at the start of a word,
  `@src/main.rs` or `@"a path with spaces"`, when the app gives it a face.

The one `markdown/editor` crate recognizes the spans from the source every time it
styles, so no list of offsets is kept in step with the text. The app supplies a face for
each atom (label, icon, tooltip) keyed by the atom's source text, not by its position.
Identity is the source's: two spans with equal source are the same atom. Web, macOS and
iOS draw atoms in the editor and the reader. Linux, Windows and Android show the source in
the editor and the label as link text in the reader, as declared differences.

T3 Code is the consumer. Its composer chips and its transcript's `AssistantCitationChip`
are atoms in its reference; the clone draws them today as a "References" row below the
field and keeps them whole with app rules (#882, §8). Inline math, which the clone's
transcript also needs, shares the reader's inline box but not the atom's contract; it is
a child RFC's (§6).

## 2. Motivation

Reference paths below are under `apps/web/src/` of T3 Code at `74541bab17`; clone paths
are under `examples/t3-code/` at `3e0c90e7b5`.

The reference T3 Code's composer is Tiptap 3 (ProseMirror). Its four chip nodes
(`composer-mention`, `composer-skill`, `composer-citation`, `composer-context-reference`)
are each `inline: true, atom: true, selectable: true`
(`components/ComposerPromptEditorTiptap.tsx:238-259, 299-321, 376-398, 501-524`). Each
serializes to Markdown source, not to its label (`composer-rich-text-doc.ts:827-841`).
The person sees a pill with an icon and a short label (a basename, a skill name, a quote
cut at 64 characters); the source behind a citation is a percent-encoded URL that can run
to thousands of characters.

The clone's composer is LLP 1045's editor (`textarea markup="markdown"`). On the web it
hides `](destination)`; since r6, Apple does too. What it cannot do is draw a label that
is not the link text, keep the label out of editing, or deliver a press. So the clone
shows each reference twice: as link text in the field, and as a button in a References
row below it (`src/composer/composer-chip-controls.contract:20-53`). And it keeps each
reference whole with its own rules, in Contract and TypeScript, over
`setSelectionRange`, `setRangeText` and `beforeinput` (#882, §8). Every app with
mentions or tags would write those rules again, and each would differ in its corners.

LLP 1114.007 r3 removed atoms from `decorations` after three blind reviews found a second
editor beside LLP 1045's, hidden-range editing left to each browser, and app-supplied
offsets that go stale over new text. It sent chips here: "Hidden source, chips and block
layout in a plain field: LLP 1045's editor" (§8), and `QUEUE.md` says "Chips would need
their own RFC". This is that RFC. §7 answers each of r3's findings.

## 3. Design

### D1. An atom is a span of the source, recognized by the styler

The styler (`exact_markdown::style`) gains one output: `atoms`, a list of
`Atom { range, kind, source }`, where `range` is UTF-16 (LLP 1045 D2), `kind` is the
declaring `atom` name, and `source` is the substring. It is computed on every `style`
from the source, the field's declared kinds and the keys of its faces (D2), as the hidden
and replaced ranges are. The host keeps no atom state between styles.

**Where.** Recognition runs over the styler's inline parse. Links are the ones its bracket
scan finds (`markdown/src/inline.rs`); prefix tokens are found only in its text runs, so
never in a code span, a fenced block, a link's text or destination, an autolink, or hidden
syntax. No atom crosses a line break or holds another atom.

**The forms**, each declared by an `atom` (D3):

| Form | Matches | Gated by a face |
|---|---|---|
| `link="<scheme>:"` | `[text](dest)` or `![text](dest)` whose `dest` begins with the scheme, compared ASCII case-insensitively as URL schemes are | no: every match is an atom, with D2's default label until its face arrives |
| `link="relative"` | `[text](dest)` or `![text](dest)` whose `dest` has no scheme by RFC 3986 §3.1 (a letter, then letters, digits, `+`, `-`, `.`, then `:`), where one letter and `:` before `\` or `/` is a Windows drive and not a scheme, and `dest` does not begin with `//`; preceded by the start of a line or whitespace, and followed by whitespace | yes |
| `prefix="<c…>"` | one of the named characters, preceded by the start of a line or whitespace, then either one or more code points that are not whitespace, a named character or `"`, or `"` … `"` with `\"` and `\\` escapes and no line break; followed by whitespace | yes |

The boundaries are the reference's (`packages/shared/src/composerInlineTokens.ts:24-35`):
a token at the very end of the source is not one, and neither is a token followed by
punctuation such as an emphasis closer. A `prefix` may name several characters, as the
reference's skill token takes any currency symbol (`prefix="$€£"`).

**Order.** A scheme link wins over a relative link, and a link over a prefix token (the
reference's order, `composer-editor-mentions.ts:78-95`). Between two candidates of one
form, the earlier start wins. Two kinds in one `atoms` list with the same scheme, a
shared prefix character, or both `link="relative"` are a compile error
(`lower-atom-duplicate`), so every span has at most one kind.

**Gating.** A gated form is an atom only when the app's faces name its source. The gate
is the app's rule, and it keeps the reference's exclusions out of the framework: a
`$5`, an `@scope/pkg`, an `@name(` (`composerInlineTokens.ts:25-28, 36-42`), a skill the
provider does not offer (`composer-rich-text-doc.ts:467-470`), a relative link whose text
is not its file's name. Scheme links need no gate: the scheme says it.

**Identity is the source.** A typed `@x` and a picked `@x` share one key, so both are
atoms once a face names `@x`. When a face for a gated form arrives, its spans are atoms on
the next style; when it leaves the list, they are text on the next style. A scheme link
stays an atom without a face and goes back to its default label. Neither moves the selection
unless it is now inside an atom, where D5's caret rule moves it and `selectionchange`
reports it. Undo is the source's and does not depend on faces. §6 lists what this
changes from the reference, whose chips are nodes with their own state.

### D2. The app supplies faces, keyed by source text

`atomFaces` takes a list of `AtomFace(source, label, icon, title)`:

- `source`: the atom's whole source substring, the key.
- `label`: the text drawn in the pill and read by assistive technology. Empty takes the
  default: a link's text, or a token without its prefix character and quotes.
- `icon`: an image source, as `image` takes one (an asset, a symbol role, `symbol:sf/…`,
  an `app:/` file, a `data:` URL; `docs/contract-for-agents.md`, images). Empty draws none.
- `title`: the tooltip, and the accessible description. Empty has none.

A face keyed by source cannot go stale: new text is a new key. A face that arrives after
the keystroke that made its source changes the drawing a moment later and never the
source (LLP 1114.007 D3's lateness, without its offset reconciliation). A face whose
source matches no atom is ignored.

Faces are measured: a label changes the pill's width. The measurement key of LLP 1045 D3
gains the faces record.

### D3. Contract: `atom`, `atoms`, `atomFaces`, `atompress`

```text
atom citation link="t3-citation:"
atom context link="t3-context:"
atom file link="relative"
atom mention prefix="@"
atom skill prefix="$" background-color="light-dark(#efe7ff, #2c2340)"

component Composer
  view
    textarea id="composer" value=draft input=edit atompress=chipPressed
      markup="markdown" atoms="citation context file mention skill" atomFaces=faces

component Reply
  view
    text body markup="markdown" atoms="citation" atomFaces=replyFaces atompress=citationPressed
```

`atom <name>` is a top-level declaration, scoped and imported like `style` and
`decoration`. It takes exactly one form attribute from D1's table; optionally `role`,
`button` (the default) or `link` (D8); and optionally `color` and `background-color`, the
paint `decoration` already admits. Any other property is a compile error
(`lower-atom-style`): the pill's metrics (padding, radius, height, icon size) are the
platform's (D4), and D4's rule that a pill never changes a line's height holds only while
its vertical metrics are.

`atoms` on a `text` or `textarea` with `markup="markdown"` lists kinds visible in the
file; it is refused elsewhere (`lower-atom-field`), and a name with no visible
declaration is a compile error. `atomFaces` takes an `AtomFace[]`; without it every
ungated atom shows its default label and no gated span is an atom.

`atompress` is a new event on those nodes (D7). Its action may take one `AtomEvent`.
`MarkdownSelection` gains `atom`: the source of the atom when the selection is exactly
one atom, `""` otherwise, so an app can bind a key to the selected atom.

The kernel gains three str props on `Text` and `TextInput`: `atoms` (the declared forms,
as a compiled table), `atomStyles` (the paint rows, as `decorationStyles` carries
`decoration`'s) and `atomFaces` (the record as named JSON). `atoms` and `atomFaces` are
measured; `atomStyles` is paint only. They go in `kernel/tables/schema.json`.

### D4. What an atom looks like

Unsaid, an atom looks like the platform's token: on macOS like `NSTokenField`'s, on iOS
like `UISearchTextField`'s. Neither control's drawing can be reused inside a TextKit 2
text view, so the Apple host draws its own pill to those looks; the web's island is the
host stylesheet's pill, modeled on the macOS token, with Chrome as the layout oracle. Its
text is the field's font at the field's size; its height is the line's text height, so a
pill never changes the height of a line of plain text. `color` and `background-color`
from the kind's declaration win (author > platform, LLP 1115). The icon is square, as
tall as the text's cap height, before the label.

A pill is one line and never wraps: a line break moves it whole to the next line, as an
inline-block does. Its label's runs of whitespace, line breaks included, draw as one
space. A pill is at most as wide as its line; a longer label is cut at its end with an
ellipsis (`text-overflow: ellipsis`), as the reference's chip is `max-w-full` with a
`truncate` label (`components/ContextChip.tsx:8, 88`). The accessible name keeps the
whole label. Stages 0 and 1 drive a long filename in a narrow field and at the largest
text size.

Inline formats around an atom apply to its label: `**[x](t3-citation:…)**` draws a
bold label. A range that covers an atom draws the atom selected, in the platform's
selection colour, as the reference highlights a chip in a range
(`components/ComposerPromptEditorTiptap.tsx:731-741`).

### D5. Editing at an atom: one set of rules, in the crate

The rules are the crate's, as LLP 1045's other editing rules are. The web runs them in
`exact-markdown-editor`; Apple applies them over the styler's marks, as it applies r6's
destination rules (LLP 1045 D5 r6). Where the reference or the clone has a rule, it is
cited.

**One run.** An atom is one `Atom` run of the projection
(`markdown/editor/src/projection.rs`), from its first code unit to its last: for a link,
from `[` or `![` to `)`. A link that is an atom is not in `link_destinations` (the
styler's `l`) and has no `LinkClose` run, and no hidden inline syntax inside it is a run
of its own. Where a hidden-syntax rule and an atom rule disagree, the atom's wins: in the
crate's `select`, `remove`, `replace_visible` and `copy_range`, and in Apple's `place`,
`rewrite`, `past` and `copyRange` (`host/apple/Sources/ExactMarkdown/MarkupHidden.swift`).
A hidden cluster beside an atom (the `**` of a bold atom) stays a cluster; the caret
positions between them are that cluster's canonical ones (`projection.rs:211-228`), and
two adjacent atoms share one caret position.

**Interactive and explicit edits.** The rules below normalize what a person does: keys,
pointer, native typing, paste, drop, autocorrect, dictation. `setSelectionRange` is
normalized by the caret and selection rules, as it is beside hidden syntax now (LLP 1045
D6 r5). `setRangeText` replaces exactly the source range it is given, inside an atom too,
and the result is recognized again: an edit that breaks an atom's form leaves text, and
one that keeps it (a new label for a scheme link) leaves an atom. `format` applies to the
normalized selection.

- **Caret.** A caret at an atom's start stays. A caret strictly inside one goes to its
  end, which is where those offsets draw (on Apple every offset after the first draws at
  the pill's right edge), and where the crate puts a caret beside a `LinkClose` now.
- **Arrows.** An unmodified ← or → at an atom's edge crosses it in one step (the
  reference's `handleKeyDown`, `components/ComposerPromptEditorTiptap.tsx:1199-1243`). ⇧
  with an arrow extends a range over it whole. ⌥ (word) movement treats it as one word.
  ↑ and ↓ are the platform's line movement, then the caret rule.
- **Selection.** A range end inside an atom goes to the atom's outer edge, so a range
  holds an atom whole or not at all (the clone's `composerChipEdge`,
  `src/composer/composer-rich.contract:35`). A double-click on an atom selects it. A
  press on it in the editor selects it before its `atompress` (D7), as a click on
  ProseMirror's `selectable` atom makes a node selection.
- **Deletion.** Backspace with a caret at an atom's end, or Delete at its start, removes
  the atom's whole source in one edit (the clone's `composerChipDeletion`,
  `src/composer/composer-source-chips.ts:109-117`). ⌥⌫ and ⌥⌦ remove it and the spaces
  between it and the caret, stopping at a line break (`composerChipWordDeletion`,
  `:121-129`). ⌃H and ⌃D are Backspace and Delete. A range that holds an atom removes it
  with the range. The reference's own Backspace at a chip is the browser's deletion of a
  `contenteditable=false` node, read from the code and not driven; stage 1 drives both.
- **Typing and replacement.** Text typed, pasted, dropped or put by autocorrect over a
  range that holds an atom replaces the range, atom included. A caret is never inside an
  atom, so typing at its edge inserts outside it. A character typed directly after a
  prefix token, with no space, makes the token's source longer (`@foo` becomes `@foox`):
  a new key, text until the app names it.
- **Undo.** Each atom deletion is one undo step; undo brings the source back, and with it
  the atom. On the web it is a crate history step; on Apple, native replacement in a
  group of its own, as `setRangeText` is (LLP 1045 D5).
- **Input methods.** A composition cannot begin inside an atom. One that begins over a
  range holding an atom first deletes the range as an undo step of its own, then
  composes (r6's rule for a range holding a destination); a cancelled composition leaves
  that deletion done. Text being composed is not recognized: a token typed through an
  input method is an atom after the composition ends. No atom is restyled while marked
  text exists (LLP 1045 D1).
- **Copy, cut, plain copy.** A copy takes the atoms' source (LLP 1045 D1; the reference
  writes the source to `text/plain`, `components/ComposerPromptEditorTiptap.tsx:1783-1809`).
  Cut is one undo step. ⌘⇧C (LLP 1045 D1's plain copy) writes each atom's label.
- **Paste.** Pasted text is source: a pasted scheme link is an atom at once, a pasted
  gated form when the app names it. The reference parses pasted text into chips too
  (`components/ComposerPromptEditorTiptap.tsx:1388-1468`).
- **Commands.** `format` applies around an atom as around other text. `link` is in
  `MarkdownSelection.unavailable` when the selection is exactly one atom.
  `MarkdownSelection.link` reports a link atom's destination as it reports a link's.
- **Not the editor's.** The trailing space the reference adds when a menu inserts a chip
  (`components/chat/ChatComposer.tsx:1016-1025`) is the app's `setRangeText`. Menus (`@`,
  `$`, `/`) and their keys are the app's. A key that opens the selected atom is the app's
  `key` handler, reading `MarkdownSelection.atom` (D3).

`rangeFrame`, `input`, `beforeinput` and `selectionchange` keep source offsets (LLP 1045
D6 r5). `beforeinput` comes first: an app that cancels a Backspace at an atom keeps it.

### D6. Reading: atoms in `text markup="markdown"`

The reader draws an atom as the editor does, with no caret. `pieces` (LLP 1045 D4) gains
one piece kind, an inline box with the atom's kind, label, icon, title, destination and
source range, measured and painted by the code that measures and paints the other
pieces. A reader atom is a tab stop and Return or Space activates it, as the transcript's
`AssistantCitationChip` is a button (`components/chat/AssistantCitationChip.tsx:126-145`).

### D7. A press on an atom is an `atompress`

A click or tap on an atom, or its activation by keyboard in the reader (D6) or by
assistive technology (D8), fires the node's `atompress`. It never navigates: a declared
scheme and a gated form are the app's. The action may take an `AtomEvent`:

- `kind`: the declaring `atom`'s name;
- `source`: the atom's source text, the faces' key;
- `href`: a link atom's destination as written, `""` for a prefix token (relative
  destinations are not resolved: LLP 1045 D4's resolution is for following a link, and
  an atom is not followed);
- `start`, `end`: its source range in UTF-16;
- `shiftKey`, `ctrlKey`, `altKey`, `metaKey`: the modifiers, as a `MouseEvent` has them.

`MouseEvent` and `press` are unchanged. `rangeFrame(id, start, end)` answers the pill's
box on a `textarea`, as it answers any range (LLP 1114.007 D7), and gains the same answer
on a `text markup="markdown"`, so a popover anchors to the pill. In the editor the press
first selects the atom (D5). An editor atom is not a tab stop, as the reference's chips
are not (`components/ComposerPromptEditorTiptap.tsx:1245-1246`).

### D8. Accessibility: atoms are elements in text order

- **Value.** The field's accessible value reads each atom as its label, in place of its
  source, as r6's VoiceOver value omits link destinations
  (`host/apple/Sources/ExactKit/MarkdownLink.swift:89-99`).
- **Elements.** Each atom is an accessibility element with its declaration's role
  (button by default, as the reference's mention chip is a `<button>`,
  `components/ComposerPromptEditorTiptap.tsx:265-272`; link where declared), named by
  its label, described by its title, at its pill's frame, in source order among the
  field's other elements. Web: the island has `role` and `aria-label`, and
  `aria-description` from the title, inside the `role="textbox"`. macOS: an
  `NSAccessibilityElement` child of the text view with the button or link role. iOS: a
  `UIAccessibilityElement` with the `.button` or `.link` trait among the text view's
  accessibility elements. Activation is D7's `atompress`. Stage 0 measured that explicit
  children leave the text view's own editing and line reading intact on macOS; on iOS a
  text view is itself an element, whose own elements UIKit does not visit, so §5.1
  proposes another placement.
- **Icons** are not read, as the reference's chip icons are not
  (`components/chat/SkillInlineText.tsx:66-74`).

### D9. The agent

No new operation. `state.atoms` reports, per field and per `text`, each atom's kind,
source, range, label and frame. `tree` shows the three props as the app set them. `type`
drives editing as today, so a drive asserts the D5 rules by keys and reads `state`. A
press on an atom is `tap <field> at <x> <y>` inside its frame (LLP 1012).

**Stage 0 is a gate.** Before any Apple build, a probe on macOS and an iOS simulator
shows that an attachment present only in a delegate-supplied paragraph lays out and
draws, and checks: caret positions and the selection highlight over it; a citation of
several thousand code units; wrapping; bidirectional text around it; native undo and an
input method beside it; a face update redrawing it; its view provider's lifecycle across
restyles; `rangeFrame`; and VoiceOver reading the value and the atom elements. r6 does
not establish this: its delegate substitutes word joiners and supplies no attachment. If
the probe fails, the Apple plan is a new proposal for review (an underlay behind word
joiners, for one), not a fallback this RFC approves.

## 5. Stages

Each stage is accepted only when its conditions hold.

0. The TextKit 2 gate (§4), a hard gate before any Apple code. Accepted when the probe on
   macOS and an iOS simulator shows that an `NSTextAttachment` present only in a paragraph
   the delegate supplies lays out and draws, through every check §4 lists, and that the
   atom's accessibility elements leave the text view's native editing and line reading
   intact (Astra r1 #4 and #8; D8). If either fails, the Apple plan goes back to review as
   a new proposal; it does not fall back.
1. Crates, Contract, kernel, the web editor and reader, `state.atoms`; Markdown Stress

### 5.1 Stage 0: what the probe measured (2026-10-23)

The probe is `host/apple/tests/ExactKitTests/InlineAtomProbeTests.swift`: plain TextKit 2
text views configured as the Markdown text area is (`isRichText` and `importsGraphics`
off on the Mac), whose content storage delegate supplies each paragraph that holds a
citation link with U+FFFC carrying a new `NSTextAttachment`, then word joiners, while the
storage keeps the source. Every check ran for both ways an attachment draws: its view
provider's view, as §4 has it, and a picture the attachment hands the layout fragment.
macOS 26.6.2 with Xcode 27.1 (`InlineAtomProbeMacTests`, 10 tests, in the
`ExactKitTests` bundle); an iOS 27.0 simulator (`InlineAtomProbeIOSTests`, 10 tests, one
hosted with UIKit's accessibility runtime, run by `host/apple/xctest.mjs`'s runner from a
package holding the probe alone).

| §4's check | macOS | iOS |
|---|---|---|
| Lays out and draws | Yes, either way, with `isRichText` on or off: one attachment frame, the pill's colour at its centre, the storage unchanged | Yes, either way |
| Carets | The atom's start at the pill's left edge; every later offset in it at the right edge; in right-to-left text, the start at the right edge and the rest at the left | The same, by TextKit's segments and `caretRect(for:)` |
| Selection highlight | The selection's segments cover the pill, and the pill draws over them: a selected look is the pill's own, drawn on a restyle as a face update is | The same |
| A citation of 6,035 code units | One line; every offset inside at the pill's end | The same |
| Wrapping | The pill moves whole to the next line; a label wider than the line gets the line's width (`proposedLineFragment`) and stays one line | The same |
| Bidirectional text | Hebrew and Arabic on both sides: drawn between the words, carets as above | The same |
| Native undo, input method | A native replacement of the atom's source and its undo remove and bring back the pill; marked text at either edge is laid out beside it | The same; UIKit's smart delete also takes one of the spaces around a deleted atom |
| A face update | A new label is measured, the text after it moves, and nothing is left where the wider pill was | The same |
| The view provider's lifecycle | Fails: AppKit asks for a provider each time it lays the paragraph out and keeps every one, with its view, while the text view lives (121 views after 120 restyles, one in the hierarchy). An attachment in the storage does the same, so it is AppKit's, not the delegate's. A provider handed back again keeps its first location, so it cannot follow the text. A picture leaves nothing: at most 6 attachments were allocated across 120 restyles | UIKit frees the providers it no longer shows (at most 3 views allocated); a picture likewise |
| `rangeFrame` | The segments over the atom's source range, as `InlineGeometry.swift` takes them, are the pill's box | The same |
| VoiceOver | Read through the AX API from a thread of its own, as `AccessibilityClientMacTests` does: the atom is one button child with its label, help and frame, and `AXPress` reaches it; the text view's value reads the label; its role, character count, selection, insertion line, visible range, `AXLineForIndex`, `AXRangeForLine`, `AXRangeForIndex` and `AXStyleRangeForIndex` equal those of the same view without the child, the same attributes are settable, and a client's selection selects source | With UIKit's accessibility runtime: the text view stays an element with its own traits and its label-reading value while the atom element sits beside it in the container; editing goes on. Not read by a VoiceOver client |

Also measured. A pill as tall as the font's ascender and descender makes a 16 pt system
font line 0.84 pt taller on macOS (18.84 against 18); one point inside each keeps it, so
the pill's height has to come from the line, not the font. AppKit's arrows cross an atom
in one step with no editor rule: the word joiners are no caret stops. Word joiners also
forbid a line break on either side of themselves
([UAX #14](https://www.unicode.org/reports/tr14/) LB11), so two adjacent atoms wrap as
one, where CSS has a soft wrap opportunity between two inline-blocks
([CSS Text 3 §5.1](https://www.w3.org/TR/css-text-3/#line-break-details)). Two other
fillers were tried for that: combining grapheme joiners (U+034F) let the pair break but
make the atom one grapheme cluster, so offsets inside it draw at its start against D5's
caret rule; a last code unit of U+200B breaks there too but puts a caret
inside the first atom at the start of its line. An attachment's default
`attachmentBounds` is what makes its view provider, so an override that skips `super`
gets no view. With a warm text system and other builds running, the 6,035-unit citation
laid out in 4 to 12 ms on the Mac either way, and an edit beside it took 7 to 21 ms with
a view against 1 ms with a picture; on the simulator, 311 ms against 49 ms, and 36 against
6. The Mac's `AXNumberOfCharacters` stays the source's length while `AXValue` reads
labels, as with r6's hidden destinations.

**Outcome.** An attachment present only in a paragraph the delegate supplies lays out
and draws through every check of §4, on both platforms and both ways of drawing it, and on
macOS the atom elements leave the text view's own editing and line reading intact. One
check failed: drawn by a view provider, as §4 has it, the pill's views outlive restyles on
macOS. By §4 and §5 the Apple plan goes back to review; what follows is the proposal for
that ruling, not a decision. Stage 1, the web, is unaffected either way.

**Proposal for the ruling.** Each route keeps the delegate's paragraph (U+FFFC with the
attachment, then word joiners) and the storage as the source; they differ in what draws
the pill.

- *A picture* (proposed): the attachment draws the pill with
  `image(for:attributes:location:textContainer:)` and sizes it with
  `attachmentBounds(for:location:textContainer:proposedLineFragment:position:)`,
  `allowsTextAttachmentView` off, a new attachment in each paragraph TextKit asks for.
  Measured: every check of §4 passes and nothing is left behind. What it loses against a
  live view: the picture takes no events, so D7's `atompress`, the macOS pointer cursor
  over a pill and D2's `title` tooltip become the text view's work (hit-testing against
  the attachment frames, and `addToolTip(_:owner:userData:)` rectangles recomputed after
  each layout); a face with `light-dark()` colours, and Increase Contrast, need the
  picture asked for again when the appearance changes (iOS's
  `UIGraphicsImageRenderer` bakes the colours in, where a view with a dynamic `UIColor`
  would follow); and a pressed or selected look costs a re-layout of the paragraph each
  time. Caret, selection and accessibility are the same either way, and neither the focus
  ring nor Dynamic Type tells the routes apart.
- *Host-owned views over the attachment frames* (not measured): the attachment only
  reserves the pill's space (an empty picture of its bounds), and the host keeps one view
  per atom, keyed by the atom's source range, positioned over the attachment's frame after
  each layout and scroll (`NSTextViewportLayoutControllerDelegate`'s
  `textViewportLayoutControllerDidLayout(_:)`), added and removed by the host, not
  AppKit, so none is kept past its atom. It keeps events, the cursor, tooltips and dynamic
  colours, and a pressed look without re-layout. Its cost: a reconciliation pass after
  every layout and scroll, the views' stacking against the insertion point, marked text
  and the selection highlight, and clipping in the scroll view, each to be measured.
- *A view provider* (§4 as accepted): passes on iOS; on macOS AppKit keeps every provider
  and view while the text view lives. Handing back one provider per attachment stops the
  growth but pins the provider to its first location, so its view cannot follow the text.

Also for the ruling, whichever route:

- The pill's height is the line's, not the font's (above).
- iOS accessibility. A text view is an element, and UIKit does not visit an element's own
  elements ([`isAccessibilityElement`](https://developer.apple.com/documentation/objectivec/nsobject/1615141-isaccessibilityelement)),
  so D8's "among the text view's accessibility elements" does not reach VoiceOver. The
  probe puts the atom element beside the text view: the presenter then owns the
  container's `accessibilityElements` (`[view, atom]`,
  `InlineAtomProbeTests.swift:1008`), and VoiceOver reads the field's value, labels
  included, and then each atom again, out of text order. That conflicts with D8's
  "elements in text order"; stage 2's VoiceOver acceptance has to settle it (a custom
  rotor over the text view, or the field's value carrying the atoms as links, are the
  alternatives to measure).
- Two adjacent atoms wrap as one with word joiners (above). Either it is declared in §6,
  or stage 2 finds a filler that keeps D5's caret rule and lets them break.

## 6. Known differences, and what is not here

**From the reference**, whose chips are nodes with their own state:

- A typed `@x` whose source a face names is an atom at once; in the reference, typed text
  becomes a chip only when the document is rebuilt from the value
  (`components/ComposerPromptEditorTiptap.tsx:1598-1606`).
- Typing directly after a prefix atom lengthens its source, and deleting the whitespace
  after a gated atom makes it text. The reference keeps the node until a rebuild; the
  clone keeps the chip (`src/composer/composer-source-chips.ts:76-77`).
- The pill's metrics are the platform's; the reference's are its Tailwind classes.
  Colours can match through the declaration; padding and radius cannot (Q2).
- A chip with a second control inside it (the citation's pencil button,
  `components/chat/AssistantCitationChip.tsx:147-238`) is one press target here. The app
  opens the comment from the press or from a key. ⇧Tab to the pencil
  (`components/ComposerPromptEditorTiptap.tsx:1247-1270`) is dropped.
- iOS shows no tooltip (`title` is web and macOS only).
- Linux, Windows and Android editors show the source.

**Inline math is a child RFC's.** It needs the reader's inline box (D6) but none of the
atom's contract: it is not editable as a unit (the reference's composer keeps math as
text), not a pill, not pressed, and its size is the formula's. A child RFC on inline
replaced content in `text markup="markdown"`, which can take inline images too, has to
settle: the `$…$` grammar (remark-math's `singleDollarTextMath`, which the reference
uses, `components/ChatMarkdown.tsx:1588`), declared per node so `$` stays literal
elsewhere; the picture's source (the app's TeX-to-SVG, drawn as an SVG image source,
LLP 1011.001); its natural size, baseline and depth; horizontal overflow and keyboard
focus, which the reference gives a formula (`components/chat/MarkdownMath.tsx:25, 38`);
copy as `\(…\)`; and what assistive technology reads with no MathML on native hosts. The
upstream `markdown-render` task's inline math waits for it.

## 7. What r3's reviews found, and where this design stands

| r3 finding | Here |
|---|---|
| A second Markdown editor with different caret and hiding rules | One editor and one crate (LLP 1045). An atom is a run of its projection, and its rules are the crate's; where they meet the hidden-syntax rules, D5 says which wins. |
| A `<textarea>` replaced by a `div` in Safari and Firefox | Not this field: the Markdown editor is already `contentEditable` on the web (LLP 1045 D5). Plain textareas and `decorations` are untouched. |
| Hidden-range editing left to each browser | The crate decides every edit that touches an atom, from `beforeinput`; the browser types only outside atoms. |
| Prefix/suffix reconciliation leaves stale metadata over new text | Atoms are recognized from the source on every style, and faces are keyed by source text: no offset is carried across an edit. |
| DOM names given meanings the DOM's do not have | `MouseEvent` and `press` are unchanged. The new names (`atom`, `atoms`, `atomFaces`, `atompress`, `AtomEvent`) are new, not borrowed. |
| No approval on record | §10: ruled 2026-10-23, before any build. |

## 10. Rulings (Daehyeon Mun, 2026-10-23)

Each question below was ruled as proposed.

1. **Admission.** Admit atoms with the take in §9, another take, or a waiver?
   **Ruled:** admitted, with §9's take. Admission retires the clone's #882 chip rules and
   its References row (§8), and closes the clone's known difference "inline atom chip".
2. **Styling.** Colours only, with the platform's metrics (D3, D4)? Or also
   `padding-inline` and `border-radius`? **Ruled:** colours only. D4's promise that a pill
   never changes a line's height holds only while the platform keeps the metrics; padding
   and radius can be added later if the clone's known differences ask for them.
3. **The relative form.** A framework form gated by faces (D1), so the source stays the
   reference's `[name](path)`, which a provider reads as a Markdown link? **Ruled:** a
   framework form, gated by the app's faces. The gate keeps T3's basename rule in the app.
4. **Source identity.** Accept that equal source is one atom, with §6's differences from
   the reference's node state? **Ruled:** accepted. It removes the stale-offset bug class
   LLP 1114.007 r3 rejected.
5. **Math.** Move inline math to a child RFC on inline replaced content (§6)? **Ruled:**
   a child RFC, written when it is next to build. The upstream `markdown-render` task's
   inline math waits on it.
6. **Names.** `atompress` with `AtomEvent`, and `MarkdownSelection.atom`? **Ruled:** these
   names. `MouseEvent` has no `href`, and `press` maps by attribute in every app.
7. **Roles.** Button by default, link where declared (D8)? **Ruled:** button by default,
   as the reference's mention and citation chips are both buttons. D3's example declares
   no role on `citation`, so the clone's citation atom is a button.
8. **Host coverage.** Web, macOS and iOS first; Linux, Windows and Android show the
   source in the editor and the label in the reader, declared? **Ruled:** as proposed,
   matching LLP 1045 D5 (Linux editing is v2) and `rules/DEFERRED.md`'s "web, iOS and
   macOS first".
