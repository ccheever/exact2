## Summary

Three small modules from the roster's identity and security row (LLP
1133.000 §3.1), in one RFC because each is a platform service whose answer
matters to a server or a regulator more than to the view, and because the
web has none of them.

**`@exact/attestation`** lets an app prove to its own server that a
request comes from a genuine build of the app on a genuine device: App
Attest on Apple ([`DCAppAttestService`](https://developer.apple.com/documentation/devicecheck/dcappattestservice)),
Play Integrity on Android ([overview](https://developer.android.com/google/play/integrity/overview)).
The module produces a token over data the app names; the server verifies
it (Apple's validation steps, or Google's `decodeIntegrityToken`). As a
passkey assertion is (LLP 1133.011 D12), the token is data code's alone and
never enters `state`.

```ts
// grants: 'device.attestation', 'net.fetch https://api.example.com'
import { attest } from "@exact/attestation";

const { challenge } = await (await fetch(`${api}/attest/challenge`, { method: "POST" })).json();
const proof = await attest({ clientData: challenge, account: userId,
                             android: { cloudProjectNumber: "123456789012" } });
const verdict = await fetch(`${api}/attest/verify`, { method: "POST",
  body: JSON.stringify({ ...proof, clientData: challenge }) });
```

**`@exact/age-range`** asks the platform for the person's age range, as
the app stores must now provide and apps must now use in Texas, Brazil,
Australia and Singapore, with Utah, Louisiana and California following in
2027 (D7): Apple's Declared Age Range ([`AgeRangeService`](https://developer.apple.com/documentation/declaredagerange)),
Google Play's Age Signals ([overview](https://developer.android.com/google/play/age-signals/overview)).
The answer is a range, not a birth date, and it may enter `state`: the
view gates on it.

```
use requestAgeRange, ageRangeStatus, AgeRange from "@exact/age-range"

mutation age as shape AgeRange
action openRestricted
  send age = requestAgeRange(ageGates=[18])
```

**`@exact/tracking-consent`** is Apple's App Tracking Transparency
([`ATTrackingManager`](https://developer.apple.com/documentation/apptrackingtransparency/attrackingmanager)),
a platform module (LLP 1133 D8): no other platform asks a person before an
app tracks them, so it has no tier 1 and is imported from its Apple
implementation.

Four decisions carry the three:

- **A proof leaves the device in data code, to the app's own server, and
  exact2 verifies nothing** (D2). Attestation inherits passkeys' rule that
  a proof is never a Contract value and purchases' rule that exact2 relays
  nothing between an app and a platform's servers (LLP 1133.015 D8). The
  module's one tier 1 call hashes the same bytes on both platforms, so one
  server route verifies either.
- **Apple's attested key is one per account per device, and the module
  owns its lifecycle** (D3): generate, attest once, assert after; keep the
  key id where a restore cannot bring it back without its key; discard
  and re-attest on the errors Apple says to.
- **An age range is an answer in the app's own gates, which the view may
  read** (D8, D10). It is not a credential, and gating a screen on it is
  its use; it is kept by the platform, never by exact2 across launches.
- **Consent is never faked** (D13): where the platform has no tracking
  prompt the module reads `available: false`, and nothing answers
  `authorized`.

The consumers: the auth fixture gains "Check this build", an attested
request its fixture server verifies (§8.1); Excord gates Discord's
age-restricted channels on the age range (§8.2). No app in the repository
tracks anyone, and none should start: tracking consent's consumer is its
package's own fixture, as §11 rules.

## 0. What is new here

1. **A capability whose answer is for somebody else.** Every module so far
   answered the app or the person. An attestation token means nothing on
   the device: only the app's server, with Apple's root certificate or
   Google's API, learns anything from it (D2).
2. **State the platform keeps across launches that exact2 must mirror.**
   App Attest's key id is unrecoverable once lost, and Apple's guidance is
   one key per account per device ([Establishing your app's integrity](https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity)).
   The implementation stores it and must agree with the Secure Enclave
   about whether it exists (D3).
3. **Law, not a person's choice, decides whether a question can be
   declined.** In a regulated region Apple's age sheet has no decline, and
   the regions and dates change by statute and court order (D7).
4. **A platform module with no equivalent elsewhere and no consumer in the
   tree.** Tracking consent is written because Charlie asked for it, and
   §8.3 says what that means for acceptance.

## 1. Attestation

### D1 — Tier 1: a deviation, `attest`, because the web has none

The web has no API by which a page proves to its server that it runs an
unmodified copy in a genuine browser. Google withdrew Web Environment
Integrity on 2023-11-02: "the Web Environment Integrity proposal is no
longer being considered by the Chrome team" ([Android Developers Blog](https://android-developers.googleblog.com/2023/11/increasing-trust-for-embedded-media.html)).
Two things nearby are not it: Private State Tokens "convey trust in a
user, not establish trust" in the client ([Chrome](https://developer.chrome.com/docs/privacy-security/private-state-tokens)),
and WebAuthn's attestation is "evidence as to the origin of an
authenticator" ([Web Authentication Level 3](https://www.w3.org/TR/webauthn-3/)),
not of the app calling it. So tier 1 is a declared deviation, named after
the roster's row (`attest(challenge)`) and shaped by what both platforms
share:

| Name | Kind | Apple | Android |
|---|---|---|---|
| `attestationStatus()` | live source, a fact | `DCAppAttestService.shared.isSupported` | Play Store and Play services present |
| `attest({clientData, account?})` | send, data code alone | `attestKey` the first time for `account`, `generateAssertion` after (D3) | a standard request, `StandardIntegrityTokenProvider.request` (D4) |
| `prepareAttestation()` | send, data code alone | generates `account`'s key if it has none | `prepareIntegrityToken` |
| `resetAttestation({account?})` | send, data code alone | forgets `account`'s key | nothing to forget; answers at once |

```
shape AttestationStatus
  available: bool
  provider: enum<app-attest|play-integrity|none>
  apple: option<AppleAttestationStatus>        // environment: development|production

shape Attestation
  format: enum<apple-appattest|apple-appattest-assertion|play-integrity|exact-substitute>
  token: string        // base64url of the platform's bytes
  keyId: option<string> // Apple's key id, base64 as Apple gives it
  attested: option<string> // the same id, on an attestation alone: the answer's handle
```

**`clientData` is the bytes the server will hash.** Both platforms sign a
hash the app supplies: Apple's `clientDataHash` is a SHA-256 "of data
containing a server challenge" ([`attestKey`](https://developer.apple.com/documentation/devicecheck/dcappattestservice/attestkey(_:clientdatahash:completionhandler:))),
and Play's standard `requestHash` is a string of at most 500 bytes the
token carries back in `requestDetails.requestHash` ([standard requests](https://developer.android.com/google/play/integrity/standard)).
The module takes the data, not a hash: it computes SHA-256 of
`clientData`'s UTF-8 bytes and passes the digest to Apple, and its
base64url form (43 characters) to Play as `requestHash`, or as a classic
request's `nonce`, whose 16-to-500-character, URL-safe rule it satisfies
([classic requests](https://developer.android.com/google/play/integrity/classic)).
So a server hashes the same bytes whichever platform called, and an app
cannot pass a hash computed differently on two platforms. `clientData` is
the server's challenge alone for a check at sign-in, or a request body
that embeds the challenge for an assertion over that request, which is
Apple's recommended use at "sensitive moments" ([Establishing your app's integrity](https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity)).

**`account`** names whose key an Apple attestation uses (D3). It is the
app's own opaque account identifier, never sent to Apple; omitted, it is
the one unnamed account. Play has no per-account key and ignores it.

**Errors** are DOMException names, each with the platform's code beside
it (`apple.code` the [`DCError.Code`](https://developer.apple.com/documentation/devicecheck/dcerror-swift.struct/code)
case, `android.code` the [Play Integrity error code](https://developer.android.com/google/play/integrity/error-codes)):

| Name | Apple | Android |
|---|---|---|
| `NotSupportedError` | `featureUnsupported`; `isSupported` false | `API_NOT_AVAILABLE`, `PLAY_STORE_NOT_FOUND`, `PLAY_SERVICES_NOT_FOUND`, the `…_VERSION_OUTDATED` codes |
| `NetworkError` | `serverUnavailable` (the key is kept, D3) | `NETWORK_ERROR`, `GOOGLE_SERVER_UNAVAILABLE` |
| `QuotaExceededError` | — | `TOO_MANY_REQUESTS` |
| `InvalidStateError` | — | `CLOUD_PROJECT_NUMBER_IS_INVALID`, `APP_UID_MISMATCH`, `APP_NOT_INSTALLED` |
| `OperationError` | `unknownSystemFailure`, `invalidInput` | `CLIENT_TRANSIENT_ERROR`, `INTERNAL_ERROR`, `CANNOT_BIND_TO_SERVICE` |

Google's guidance for the retryable codes is exponential backoff from
5 s, and after three failures to treat the client as failing every check
(same page). The module does not retry: the server decides what a
missing proof costs, so the app sees each failure.

### D2 — What a token proves, and where it is verified

| | Apple App Attest | Play Integrity |
|---|---|---|
| The token | an attestation object in WebAuthn's CBOR form (`fmt` `apple-appattest`, an `x5c` chain and a receipt), or an assertion signed by the attested key | an encrypted, signed token |
| Verified by | the app's server, offline, by [Apple's validation steps](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server): the chain to the [App Attestation root](https://www.apple.com/certificateauthority/Apple_App_Attestation_Root_CA.pem), the nonce, the key id, the RP ID hash of team and bundle id, counter 0, the `aaguid` | the app's server, which calls Google's `decodeIntegrityToken` with a service account ([verdicts](https://developer.android.com/google/play/integrity/verdicts)) |
| What the server learns | that the key lives in this device's Secure Enclave and belongs to this team's app; from iOS 27, how the build was signed (`apple_validation_category_01`: development, TestFlight, App Store, Developer ID…) and its version ([WWDC26 session 201](https://developer.apple.com/videos/play/wwdc2026/201/)); with the receipt, Apple's risk metric ([Assessing fraud risk](https://developer.apple.com/documentation/devicecheck/assessing-fraud-risk)) | `appRecognitionVerdict` (`PLAY_RECOGNIZED`, `UNRECOGNIZED_VERSION`, `UNEVALUATED`), `deviceRecognitionVerdict`, `appLicensingVerdict` and the opt-in fields |
| Replay | the server's single-use challenge; an assertion's counter must increase | the challenge in `requestHash`; a token decoded again "comes back with its verdicts cleared" ([standard requests](https://developer.android.com/google/play/integrity/standard)) |

So the roster's tier 2 cell, "verdict fields per platform", is answered on
the server: the device never sees a verdict, and a module that decoded one
on the device would be trusting the device it is meant to check. The
module answers the token and the key id; the verdict's fields are
Google's and Apple's documentation for the server (§10 amends the roster
row).

**exact2 verifies nothing and relays nothing.** The token goes from data
code to the app's server over the app's own `net.fetch` grant, and the
server talks to Apple and Google itself, as LLP 1133.015 D8 settles for
store receipts. The auth fixture's server is a verifier for the fixture
(§8.1), not a library for apps.

**Why data code alone** (`"contract": false`, `module-name-data-only`):
a token is good for as long as its challenge is open on the server. In a
mutation's answer it would be in `state`, which the agent and a tool
invocation read (LLP 1111), so a tool could spend it. This is LLP 1133.011
D12's reasoning for a passkey assertion, unchanged.

### D3 — Apple's key, one per account per device

Apple's guidance: generate one key per user account per device, store its
key id because it cannot be recovered, attest it once, and assert with it
after; keys survive an update but not a reinstall, a migration to a new
device or a restore from backup, and do not sync ([Establishing your app's integrity](https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity);
[WWDC26 session 201](https://developer.apple.com/videos/play/wwdc2026/201/)).
The implementation keeps, per `account`, the key id and whether Apple has
attested it, in a file in the app's Application Support
directory marked excluded from backup
([`isExcludedFromBackup`](https://developer.apple.com/documentation/foundation/urlresourcevalues/isexcludedfrombackup)),
so a restore that cannot bring the key back does not bring its id back
either.

| What the implementation holds for `account` | `attest` does | It answers |
|---|---|---|
| nothing | `generateKey`, then `attestKey(keyId, clientDataHash:)` | `apple-appattest`, with `keyId` |
| a key Apple has not attested (`serverUnavailable` before) | `attestKey` again with the same key | `apple-appattest`, with `keyId` |
| an attested key | `generateAssertion(keyId, clientDataHash:)` | `apple-appattest-assertion`, with `keyId` |

- **`serverUnavailable`** keeps the key: Apple says to retry "with the
  same key" and the same client data hash to "preserve the risk metric"
  ([`serverUnavailable`](https://developer.apple.com/documentation/devicecheck/dcerror-swift.struct/code/serverunavailable)).
  The call fails `NetworkError`, and the app retries with the same
  `clientData` while its challenge is still open on the server, which
  the recipe and the auth fixture do; a new challenge is asked for only
  once the old one has expired.
- **Any other `attestKey` error** discards the key, as Apple says; the
  next `attest` generates a new one.
- **`invalidKey` from `generateAssertion`** means the Enclave no longer has
  the key (a restore that brought the file back regardless, or a reset of
  the Enclave). The implementation discards the id, generates and attests
  a new key in the same call, and answers `apple-appattest`: the server
  receives an attestation where it expected an assertion, which it
  verifies as a new key for the account. That inner `attestKey` follows
  the rules above: `serverUnavailable` keeps the new key and fails the
  call `NetworkError`.
- **The server's "unknown key"** (its own database lost the key, or the
  attestation's reply never reached it) is the server's answer to the
  app, which calls `resetAttestation({account})` and `attest` again.
  Re-sending a stored attestation would not do: its challenge is spent.
- **A dropped attestation.** A key is attested once `attestKey`
  succeeds. The answer is provisional until the runner delivers it to the
  awaiting call (LLP 1133.009 D10 item 10): its `attested` field, the key
  id again, is its handle, and if the runner drops it (the call's mutation was superseded or its
  session ended), the runner calls `dispose` with that id
  (`runner/src/runner/modules/handles.rs`), and no server has seen the
  key. The implementation then discards the key, since Apple does not say
  an attested key may be attested again; it costs one key on the device's
  risk metric.
- **An attestation let go in flight** is the same case. The
  implementation always replies to `attest`, even after a `cancel`
  (LLP 1133.016 D15 item 2; Apple's `attestKey` cannot be stopped), so the
  reply arrives with its request gone and the runner disposes its handle
  (`dispose_dropped`, `runner/src/runner/modules/handles.rs`). `dispose`
  is the one signal D3 relies on. It does not rely on `cancel`, which the
  runner does not yet send to a data-code call: a data-code body carries
  no request number when the runner records the send
  (`data/src/modules.rs`, `runner/src/runner/modules/bound.rs`), an
  inherited gap §10 records.
- **A reply that never lands** (the app killed between Apple's answer and
  the call's) leaves a key the implementation counts as attested and no
  server knows. The next call asserts with it, the server answers unknown
  key, and the app resets (above): the one case that recovers by the
  server's answer rather than by `dispose`.
- **A dropped assertion** disposes nothing: an assertion has no
  `attested` field, so it carries no handle, and the runner, which
  disposes every handle of a dropped answer without reading its format,
  has nothing to dispose. The key stays, and the server sees only a gap in
  the counter, which its rule (greater than the last) allows. An
  attestation dropped after a later assertion with its key was delivered
  is still disposed, which is right: the server never saw the key, so the
  assertion was for a key it will answer unknown.
- **One call per account at a time.** An assertion's counter must exceed
  the last the server saw ([validating](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server)),
  so the module serialises calls for an account; calls for different
  accounts run in parallel.
- **Rollout limits are the app's.** Apple asks for a ramp of "no more than
  10 million users per day per app" and under 100 `attestKey` calls per
  second across all installs ([Preparing to use the App Attest service](https://developer.apple.com/documentation/devicecheck/preparing-to-use-the-app-attest-service)).
  The module cannot see installs; an app with that many users ramps on
  its server.
- **Extensions.** Apple supports App Attest in action, extensible SSO and
  watchOS extensions only ([Establishing your app's integrity](https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity)).
  exact2 runs no session in an extension, so this needs no rule now.

### D4 — Play Integrity's requests

**Standard requests by default.** Google recommends them for most checks:
a few hundred milliseconds per token after a warm-up of a few seconds,
against classic requests' few seconds each ([overview](https://developer.android.com/google/play/integrity/overview)).
The implementation holds one `StandardIntegrityTokenProvider` per cloud
project number. `prepareAttestation` makes it; `attest` makes it if
`prepareAttestation` was not called first, and makes it again when a
request fails `INTEGRITY_TOKEN_PROVIDER_INVALID`, as Google says to
([standard requests](https://developer.android.com/google/play/integrity/standard)).
Google limits preparation to five times a minute per app instance and
asks for a timeout near a minute; the implementation keeps both.

**The cloud project number** is required by a standard request
(`setCloudProjectNumber`). It identifies the Google Cloud project whose
service account decodes the token, so it is a fact of the app's server,
and it is not a secret. It is an option of the call,
`android.cloudProjectNumber` on `attest` and `prepareAttestation`, which an
app writes as a constant beside its API's URL; an Android call without it
fails `TypeError`. *Rejected:* an `app.json` field, which would add a
build-time value read by a package's implementation, a seam no module has
for one string.

**Classic requests** are tier 2 (`android.request: "classic"`): Google
reserves them for "infrequent, highest-value" checks, limits them to five
tokens a minute and says not to cache their verdicts ([classic requests](https://developer.android.com/google/play/integrity/classic)).

**Quota is the server's to manage.** The default is 10,000 token requests a
day across classic requests and standard preparations, raised for an app
on Play with a linked Cloud project ([setup](https://developer.android.com/google/play/integrity/setup)).

**The library** is `com.google.android.play:integrity:1.6.0`, minSdk 23,
under exact2's 29 ([release notes](https://developer.android.com/google/play/integrity/reference/com/google/android/play/core/release-notes)),
resolved in the one locked Gradle graph (LLP 1133.008 D8 item 5).

**What a build gets.** A debug or sideloaded build is not the one Play
knows: its token decodes to `UNRECOGNIZED_VERSION` and `UNLICENSED`, and an
emulator fails the device verdict, except Google Play Games for PC
([verdicts](https://developer.android.com/google/play/integrity/verdicts)).
A token still issues, so a development drive proves the path end to end
and reads those verdicts; a `PLAY_RECOGNIZED` verdict needs a build
installed from a Play track (LLP 1133.020 §3.4). Play Console can assign a
tester's account fixed verdicts, marked `testingDetails.isTestingResponse`
([additional tools](https://developer.android.com/google/play/integrity/additional-tools)).

### D5 — Tier 2 and tier 3

| Word | Platform | What it beats in tier 1 |
|---|---|---|
| `apple.environment` (status) | the build's `com.apple.developer.devicecheck.appattest-environment` | which Apple service the key is registered with, so a server picks the `aaguid` and the receipt endpoint |
| `android.request: "classic"` | `IntegrityManager.requestIntegrityToken` | a token with a nonce, for a rare high-value check |
| `android.cloudProjectNumber` | `setCloudProjectNumber` | — (required, D4) |
| `android.code`, `apple.code` (errors) | the platform's error code | the cause, where tier 1's name groups several |

**Tier 3:** none. The implementations hold `DCAppAttestService.shared` and
the token provider, which have nothing an app could configure that the
words above leave out. An app that wants something else (Android Key
Attestation, below) writes its own implementation (LLP 1133.001).

### D6 — The grant, the origin, no permission

**`device.attestation`**, a row no platform asks the person about (no
purpose: LLP 1133.017 D14). On iOS and tvOS it derives the entitlement
`com.apple.developer.devicecheck.appattest-environment`, `development` for
a debuggable build and `production` for a release; TestFlight, App Store
and Enterprise builds use production whatever it says ([entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.devicecheck.appattest-environment)).
An App ID registered for the team is required ([`DCAppAttestService`](https://developer.apple.com/documentation/devicecheck/dcappattestservice)),
so a phone's development profile must carry the App Attest capability.
The Mac is D17's.

**No permission and no prompt.** An attestation shows nothing and says
nothing about the person: it proves the binary and the device. There is
no state fact.

**Any origin may attest,** a tool's or a wake's included. The inherited
rule that tools and wakes cannot start a device protects the person from
being sensed or prompted without their act; attestation does neither,
and Apple's guidance is to attest in the background, away from the moment
the person waits ([WWDC26 session 201](https://developer.apple.com/videos/play/wwdc2026/201/)).
A wake that posts the app's data may attest that request. Foreground is
not required on either platform.

Two cautions. Texas's law is in force under a stay of the district court's
injunction, which the Supreme Court declined to vacate on 2026-07-06; the
Fifth Circuit's decision on the appeal is pending, and a ruling could pause
it again, as the injunction did from 2025-12-23 to 2026-06-03 ([Apple,
2025-12-23](https://developer.apple.com/news/?id=8jzbigf4)). The
court dates are from secondary sources, and California's chaptered text
and Alabama's HB 161 (effective 2027-01-01) were not read in their primary
source. Neither caution changes the design: the module asks the platform,
and the platform knows which rules apply to the person's account.

So what drives the module is not a region table in exact2: Apple
substitutes its regulatory gates for the app's where a law requires them
and removes the decline ([Requesting people share their age range](https://developer.apple.com/documentation/declaredagerange/requesting-people-share-their-age-range-with-your-app)),
and Play returns signals only where it has them. The module passes the
platform's answer through and says which kind it is.

### D8 — Tier 1: `requestAgeRange` and `ageRangeStatus`, a deviation

The web has no age signal. The W3C's Digital Credentials API asks a
wallet for a credential, such as an identity document's `age_over_18`
claim ([Digital Credentials](https://www.w3.org/TR/digital-credentials/)),
which is identity documents' roster row (LLP 1133.000 §3.13), not a store's
signal. So tier 1 is a deviation in Apple's words, which are the closer of
the two platforms' to a single call:

| Name | Kind | Apple | Android |
|---|---|---|---|
| `ageRangeStatus()` | live source, a fact | `AgeRangeService.shared.isEligibleForAgeFeatures`, `requiredRegulatoryFeatures` | the library present and the app installed by Play |
| `requestAgeRange({ageGates})` | send, a request | [`requestAgeRange(ageGates:_:_:in:)`](https://developer.apple.com/documentation/declaredagerange/agerangeservice/requestagerange(agegates:_:_:in:)-2go8c) | `requestAgeSignalsAccess`, then `checkAgeSignals` ([request age signals](https://developer.android.com/google/play/age-signals/request-age-signals)) |

```
shape AgeRangeStatus
  available: bool
  regulated: option<bool>       // Apple's isEligibleForAgeFeatures; none where the platform does not say
  apple: option<AppleAgeRangeStatus>   // requiredRegulatoryFeatures

shape AgeRange
  status: enum<sharing|declined|unverified>
  lowerBound: number            // 0 when below the lowest gate
  upperBound: option<number>    // none at or above the highest gate
  declaration: enum<self|guardian|confirmed|unknown>
  apple: option<AppleAgeRange>     // activeParentalControls
  android: option<AndroidAgeRange> // ageRangeSource, significantChangeStatus, significantChangeApprovalDate, installId, accessStatus
```

**`ageGates`** are one to three ages, ascending, at least two years apart,
Apple's rule ([requesting](https://developer.apple.com/documentation/declaredagerange/requesting-people-share-their-age-range-with-your-app));
a list outside it refuses `TypeError` before the platform is asked. On
Apple they are the request. On Play they are not: Play answers in the
bands the app set in Play Console, by default 0–12, 13–15, 16–17 and 18+,
or up to three minimum ages of the app's own, changeable once a year
([responses](https://developer.android.com/google/play/age-signals/understand-age-signals-responses)).
The module cannot read the Console's bands, so it does not coarsen Play's
answer into the app's gates; it answers Play's `ageLower` and `ageUpper`
as they come.

**Both bounds are inclusive ages, and an app tests them by comparison:**
`lowerBound >= 18` for "at least 18", and `upperBound` present and below
18 for "under 18". These are Apple's own tests: its sample for a gate of
18 reads `if let upperBound = ageRange.upperBound, upperBound < 18` for a
person under 18, and `lowerBound >= 18` for one at or over it ([requesting](https://developer.apple.com/documentation/declaredagerange/requesting-people-share-their-age-range-with-your-app)),
so below the lowest gate Apple answers an `upperBound` one less than it.
Play's `ageLower` and `ageUpper` are inclusive by Google's description
(0–12, 13–15, 16–17, 18+), and Windows' pairs likewise. A band that
straddles the app's gate (Play's 13–15 against a gate of 14) satisfies
neither test: the person is undetermined, and the app decides what that
means, as it decides for a decline. The recipe says to set the Console's
bands to the app's gates, which removes the case on Play, and the
substitute answers exactly these integers, so a drive tests the rule the
device applies.

**`lowerBound`** is 0 where Apple answers `nil` ("below your lowest
gate"): every age is at least 0, and one number type is simpler for the
view than an option whose absence means a different thing on each side.

**`declaration`** maps Apple's [`AgeRangeDeclaration`](https://developer.apple.com/documentation/declaredagerange/agerangeservice/agerangedeclaration)
(`selfDeclared`, `guardianDeclared`, `confirmed`; the deprecated payment
and ID cases read `confirmed`) and Play's `ageRangeSource` (`TIER_A`
self-declared, `TIER_B` set by a parent, `TIER_C` and `TIER_D` checked by
card, ID or selfie) to one word; the platform's own value is in tier 2.

**`status`** is `declined` when Apple answers `.declinedSharing` or Play's
`requestAgeSignalsAccess` answers `NOT_SHARED`, and `unverified` when Play
answers `VERIFICATION_REQUIRED`: Play requires a verification the person
has not finished, which Google directs them to complete in the Play Store
([request age signals](https://developer.android.com/google/play/age-signals/request-age-signals)).
Either way the bounds are 0 and none.

**Errors:**

| Name | Apple ([`AgeRangeService.Error`](https://developer.apple.com/documentation/declaredagerange/agerangeservice/error)) | Android ([errors](https://developer.android.com/google/play/age-signals/handle-errors)) |
|---|---|---|
| `NotSupportedError` | `notAvailable`; below iOS or macOS 26 | `API_NOT_AVAILABLE`, `PLAY_STORE_NOT_FOUND`, `PLAY_SERVICES_NOT_FOUND`, the `…_OUTDATED` codes |
| `NotAllowedError` | `declinedOnboarding`, `invalidAccount` (27.0) | `APP_NOT_OWNED` (not installed by Play) |
| `NetworkError` | `network` (27.0) | `NETWORK_ERROR` |
| `OperationError` | `invalidRequest` | `CLIENT_TRANSIENT_ERROR`, `CANNOT_BIND_TO_SERVICE`, `INTERNAL_ERROR` |

### D9 — Tier 2 and tier 3; significant changes wait for a consumer

| Word | Platform | What it beats in tier 1 |
|---|---|---|
| `apple.requiredRegulatoryFeatures` (status) | [`RegulatoryFeature`](https://developer.apple.com/documentation/declaredagerange/agerangeservice/regulatoryfeature) (26.4) | which of the age range, an adult's notification and a parent's consent the person's region requires |
| `apple.activeParentalControls` | `ParentalControls` (`communicationLimits`) | that a parent limits who the person may talk to, which a chat app should honour |
| `apple.ageRangeDeclaration` | the platform's case | the deprecated cases' detail |
| `android.ageRangeSource`, `significantChangeStatus`, `significantChangeApprovalDate`, `installId`, `accessStatus` | `AgeSignalsResult`, 0.0.4 | the tier of the check; a parent's answer to the last significant change Play knows; the install id Play's revocation list names |

**Tier 3:** none: neither framework has an object an app configures.

**Significant changes stay out until a consumer asks.** Texas and Utah
require a parent's consent to a significant change. Apple's path is
PermissionKit's `SignificantAppUpdateTopic` with `AskCenter` for consent
([PermissionKit](https://developer.apple.com/documentation/permissionkit/significantappupdatetopic))
and `showSignificantUpdateAcknowledgment` for an adult's notification
(iOS 26.4), with `RESCIND_CONSENT` as an App Store server notification
([notification types](https://developer.apple.com/documentation/appstoreservernotifications/notificationtype));
Play's is a filing in Play Console, with revocations listed there by
install id as a CSV and no API ([notify significant changes](https://developer.android.com/google/play/age-signals/notify-significant-changes),
[revoked approvals](https://developer.android.com/google/play/age-signals/revoked-app-approval)).
No consumer makes a significant change to a minor's experience now, and
the two platforms share nothing a tier 1 could name; Android's
`significantChangeStatus` arrives in tier 2 as data at no cost. StoreKit's
`AppStore.ageRatingCode` belongs to the purchases module when it is
wanted ([`ageRatingCode`](https://developer.apple.com/documentation/storekit/appstore/ageratingcode)).

### D10 — The grant, the consent, the origin, the answer in state

**`device.age-range`**, with no purpose: the platform's sheet says what it
asks, and neither platform has a usage string for it. On iOS and macOS it
derives `com.apple.developer.declared-age-range` ([entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.declared-age-range)),
and the app must build with the 26.2 SDK or later ([Age assurance](https://developer.apple.com/support/age-assurance/)).
Android needs no manifest permission. The row does not apply on tvOS.

**The request is the consent,** as a passkey ceremony is (LLP 1133.011
D7): Apple shows its sheet, which outside a regulated region the person
may decline; Play may show its own prompt from `requestAgeSignalsAccess`,
and shows none in the US states with these laws ([request age signals](https://developer.android.com/google/play/age-signals/request-age-signals)).
There is no state fact of LLP 1133.002 D8 to read first: Apple offers no
query of whether the person has shared, only the request, which answers at
once when it holds an answer ("results are cached", [requesting](https://developer.apple.com/documentation/declaredagerange/requesting-people-share-their-age-range-with-your-app)).

**Origin: the person's act or the app's own foreground code**
(`"origin": "app"`, `"foreground": true`). The request may show a sheet,
so a tool invocation or a wake fails `person-required` before the platform
is asked (LLP 1111 D4a), in every state, even when the platform would
answer from its cache: whether it would is not knowable beforehand.
**One sheet at a time** is the implementation's: the runner forwards each
admitted request (the age range has no permission whose queue would hold
it, LLP 1133.002 D9), and the implementation calls the platform for one
request at a time, so a second waits for the first and is then asked of
the platform, which answers from its cache without a sheet.

**The sheet needs a window.** Apple's request takes a `UIViewController`
or an `NSWindow`. The package context has no presentation anchor yet (LLP
1133.015 D16 item 3, accepted and not built), so the implementation
presents from the key window's root view controller, or the key window on
the Mac, as passkeys' does; when the anchor lands, it uses the session's.
With no key window (a session with no window in front) the request fails
`NotAllowedError` at once, as purchases' sheet does (LLP 1133.015 D15),
rather than wait on an anchor that is not there.

**The answer may enter `state`.** An age range is not a credential:
nobody can spend it, and the view must read it to gate a screen, which is
the use both stores permit, "to provide age-appropriate content and
experiences" ([Play](https://developer.android.com/google/play/age-signals/overview)).
Two rules follow from that permission:

- **exact2 keeps no answer across launches.** A module's answer is never
  kept; only a store-reading resource's is (`runner/src/runner/kept.rs`),
  and the recipe says not to pass a range into one. The platform keeps the
  range, and the next launch asks again, which costs no sheet. The row is
  not `keeps_no_answers`: that flag drops every kept answer of the app
  (LLP 1133.019 D6), which would cost Excord its first frame for a value
  that is never kept anyway.
- **The journal and `state.extensions` name the outcome, never the
  range.** The agent reads the range where the view does, in `state`, in
  a development build.

## 3. Tracking consent

### D12 — A platform module in App Tracking Transparency's words

Apple defines tracking as "linking user or device data collected from
your app with user or device data collected from other companies' apps,
websites, or offline properties for targeted advertising or advertising
measurement purposes", or sharing it with data brokers, and requires
permission through ATT before it from iOS, iPadOS and tvOS 14.5 ([User
Privacy and Data Use](https://developer.apple.com/app-store/user-privacy-and-data-use/);
[App Review Guidelines 5.1.2(i)](https://developer.apple.com/app-store/review/guidelines/)).
No other target asks the person:

- **Android** has the advertising ID behind `AD_ID`, a permission "granted
  when the app is installed" ([`AdvertisingIdClient.Info`](https://developers.google.com/android/reference/com/google/android/gms/ads/identifier/AdvertisingIdClient.Info));
  normal permissions show no prompt ([permissions](https://developer.android.com/guide/topics/permissions/overview)).
  Google retired the Privacy Sandbox's attribution and audience APIs on
  Android and Chrome on 2025-10-17 ([Privacy Sandbox](https://privacysandbox.google.com/blog/update-on-plans-for-privacy-sandbox-technologies)).
- **The web** has no tracking-consent API; the Storage Access API grants
  an embed its unpartitioned cookies, which is not this.
- **Windows'** advertising ID is a setting the person chooses in Windows
  setup or Settings, with no prompt ([`AdvertisingManager.AdvertisingId`](https://learn.microsoft.com/en-us/uwp/api/windows.system.userprofile.advertisingmanager.advertisingid)).
- **macOS** declares the framework but shows no prompt in practice: an
  active AppKit app with the usage string gets `notDetermined` at once
  ([forum 719628](https://developer.apple.com/forums/thread/719628),
  FB11793091), the usage key is listed for iOS, iPadOS, tvOS and visionOS
  only ([`NSUserTrackingUsageDescription`](https://developer.apple.com/documentation/bundleresources/information-property-list/nsusertrackingusagedescription)),
  and the advertising identifier is always zeros on macOS ([`advertisingIdentifier`](https://developer.apple.com/documentation/adsupport/asidentifiermanager/advertisingidentifier)).

So `@exact/tracking-consent` has no tier 1 (LLP 1133 D8's platform
module), and its whole surface is Apple's, imported from the
implementation (LLP 1133.001 D2):

```
use trackingAuthorizationStatus, requestTrackingAuthorization, TrackingStatus
  from "@exact/tracking-consent/apple"
```

| Name | Kind | Platform API | Contract | Data code |
|---|---|---|---|---|
| `trackingAuthorizationStatus()` | live source, a fact; `sync` | [`ATTrackingManager.trackingAuthorizationStatus`](https://developer.apple.com/documentation/apptrackingtransparency/attrackingmanager/trackingauthorizationstatus) | `resource t = trackingAuthorizationStatus()` | `await trackingAuthorizationStatus()` |
| `requestTrackingAuthorization()` | send, a request | [`requestTrackingAuthorization(completionHandler:)`](https://developer.apple.com/documentation/apptrackingtransparency/attrackingmanager/requesttrackingauthorization(completionhandler:)) | `send t = requestTrackingAuthorization()` | `await requestTrackingAuthorization()` |
| `advertisingIdentifier()` | send, data code alone | [`ASIdentifierManager.advertisingIdentifier`](https://developer.apple.com/documentation/adsupport/asidentifiermanager/advertisingidentifier) | refused (`module-name-data-only`) | `await advertisingIdentifier()` |

```
shape TrackingStatus
  available: bool
  status: enum<notDetermined|restricted|denied|authorized>   // Apple's four cases
  state: enum<granted|prompt|denied>                          // LLP 1133.002 D8
```

`state` is `prompt` for `notDetermined`, `granted` for `authorized`, and
`denied` for `denied` and `restricted`; `restricted` is returned
"regardless of whether your app has presented the prompt" ([`restricted`](https://developer.apple.com/documentation/apptrackingtransparency/attrackingmanager/authorizationstatus/restricted)).

**`advertisingIdentifier`** answers the IDFA, all zeros unless the status
is `authorized`, and in the Simulator. It is data code's alone: it is an
identifier for tracking, and in `state` the agent and tools would read it
and a kept answer would outlive the person's revocation. It is in the
module because the consent has no other effect an exact2 app can reach:
ad and attribution SDKs read the IDFA themselves, and exact2 links none.

**The EU's expanded sheet** (iOS 27.2's
[`requestTrackingAuthorization(preferExpandedInterface:additionalInformationAction:completionHandler:)`](https://developer.apple.com/documentation/apptrackingtransparency/attrackingmanager/requesttrackingauthorization(preferexpandedinterface:additionalinformationaction:completionhandler:)),
with `NSUserTrackingMarkdownUsageDescription`) waits for a consumer:
its "Additional Information" button calls back into the app, which needs a
handler the module would `invoke`, and no app asks.

### D13 — Permission, by LLP 1133.002 D6 to D12

- **D6, declare:** `device.tracking purpose.tracking` writes
  `NSUserTrackingUsageDescription` with the purpose. Apple: "This key is
  required. Your app crashes if it attempts to use the
  AppTrackingTransparency framework without including the key"
  (same page), which the grant makes impossible to forget. The row applies
  on iOS and tvOS, and on no other target.
- **D8, read:** `trackingAuthorizationStatus` is a polled live source read
  again at each return to the foreground: the person changes it in
  Settings, outside the app.
- **D9, ask:** one request at a time, the implementation's queue, as the
  age range's is (D10): the module has no `permission` block, since a
  denial is an answer here, not a failure (below). ATT answers at once without a
  prompt when another request is pending, when tracking is restricted or
  the person turned off "Allow Apps to Request to Track", from an
  extension, and when the app is not active ([`requestTrackingAuthorization`](https://developer.apple.com/documentation/apptrackingtransparency/attrackingmanager/requesttrackingauthorization(completionhandler:))).
  The last is a known trap: a call made during launch, before the app is
  active, returns `notDetermined` and shows nothing. The implementation
  holds a request made while the app is inactive until
  `didBecomeActiveNotification`, so a request at launch shows the alert
  as soon as it can; a held request whose call is released or whose
  session ends is dropped, never shown later. A dismissal without a decision answers
  `notDetermined`, and the person may be asked again; in the EU an answer
  cannot be asked again for a year (same page).
- **Origin:** `"origin": "app"`, `"foreground": true`. A tool or a wake
  fails `person-required` (LLP 1111 D4a): consent is the person's.
- **D11, explain:** the app's own screen before the alert is allowed, with
  one button titled "Continue" or "Next", never "Allow", and no way to
  close it; incentives and images of the alert are rejected ([HIG,
  Privacy](https://developer.apple.com/design/human-interface-guidelines/privacy)).
  An app may not make tracking a condition of anything (5.1.2(i)). The
  recipe shows the allowed screen; the module adds no UI.
- **No `permission` block.** LLP 1133.002's permission ticket fails a
  denied request with the module's error (`runner/src/runner/modules.rs`),
  and ATT's request never fails: it answers the status, `denied` and
  `notDetermined` included. So `TrackingStatus.state` carries D8's
  meaning, and the implementation answers it; the request is an ordinary
  request with its own ticket under the agent (§7), and nothing else in
  the module is gated on it (`advertisingIdentifier` answers zeros until
  `authorized`, as the platform does).
- **D12, answer:** exact2 never answers the alert. Where the platform has
  no alert the status reads `available: false`, `status: "denied"` and
  `state: "denied"`, and the request refuses `NotSupportedError`, as every
  absent call does (LLP 1133 D8): its declaration lists those targets as
  `unsupported`, so admission refuses it before any ticket. Nothing reads
  `authorized` that the person did not choose.

### D14 — What tracking consent does not do

It does not decide whether an app tracks. An app that links data across
companies needs the person's authorization first, and an app that does
not track has no reason to ask: Apple's attribution APIs, SKAdNetwork and
AdAttributionKit, need no ATT ([SKAdNetwork](https://developer.apple.com/documentation/storekit/skadnetwork),
[AdAttributionKit](https://developer.apple.com/documentation/adattributionkit)).
It does not write the privacy manifest's `NSPrivacyTracking` and
`NSPrivacyTrackingDomains`, whose domains iOS blocks until the person
authorizes ([`NSPrivacyTrackingDomains`](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacytrackingdomains)):
exact2 writes no privacy manifest for any app yet (§10).

## 7. The substitutes

Each module is **its own substitute** (`"substitute": "implementation"`,
LLP 1133.006 D8 item 4), as contacts, calendar and photos are: under the
agent the bound implementation runs, told it is substituting
(`context.agent`), asks its framework for nothing, and answers from a
private store. The answers need computation a declared substitute cannot
do (a hash of the call's data, a key and counter per account, an age put
into the request's gates), and that computation belongs to the package,
not the runner (LLP 1133.001 D8). The runner keeps what it already does
for every module: admission, the origin and foreground rules, the tickets
of a request and of a permission, the status a permission names, and
`dispose`. A preferred value reaches the implementation through the
package context's `preferred` (`host/apple/modules/ExactPackage.swift`),
as `prefer extension calendar.store` does (LLP 1133.018 §10), and a live
source the implementation answers is `"overlays": "implementation"`
(LLP 1133.016). Where no implementation is bound (the web, Linux, Windows,
which have none), the declared per-target defaults answer, as D17 says.

**Attestation.** `attest` answers at once, with no ticket, since nothing is
shown: an `exact-substitute` token, the base64url of a JSON object naming
`clientData`'s SHA-256, the key id, the kind (attestation or assertion)
and the counter, under D3's per-account lifecycle, with keys in the
session's private store, so a drive sees the first call answer an
attestation and the next an assertion, `resetAttestation` start again and
a dropped answer's `dispose` discard the key. `prefer extension
attestation.attestationStatus=…` lays fields over the agent path's
reading, which is `available: true` with the target's provider wherever
the target has a cell (the real reading, false on an iOS Simulator, is
`--bind`'s, D17), so a drive sets `available: false` to see the absent
path; `prefer extension
attestation.fail="NetworkError"` (or another name of D1) makes the next
call fail with it, keeping the key as D3 says; `prefer extension
attestation.delay=<ms>` holds each answer that long on the agent's clock,
so a drive can supersede a call whose answer is in flight. `fail` and
`delay` are agent words the substitute declares (`"agent": {"fail":
"string", "delay": "number"}`, as `@exact/calendar` declares `store`),
which reach the implementation as preferred values.
`packages/attestation/test/verify.mjs` is the fixture server's verifier of
substitute tokens; a server accepts them only when started with
`--substitute`, and the auth fixture's refuses them otherwise (§8.1).

**Age range.** `requestAgeRange` is a request whose sheet the runner holds
as an `age-range` ticket (a `choose` ticket, as `selectContacts`' is, LLP
1133.018 D13 item 4), whose `args` name the gates, the target and the
call's origin; its answer reaches the implementation as the call's
`preferred`, and the implementation computes the range:

| Answer | Result |
|---|---|
| `type @t <age>` | the range that age falls in: the app's gates on Apple, Play's default bands on Android, so a drive sees each platform's banding |
| `tap @t decline` | `status: "declined"`; refused while the status's `apple.requiredRegulatoryFeatures` holds `declaredAgeRangeRequired`, since Apple's sheet has no decline there |
| `tap @t unverified` (Android) | `status: "unverified"`, Play's `VERIFICATION_REQUIRED` |
| `tap @t unavailable` | `NotSupportedError` |
| a tool-origin or wake-origin request | `person-required`, no ticket |

Every request under the agent holds a ticket, even one the platform
would answer from its cache: admission decides the ticket before the
implementation is asked, and cannot see the platform's cache. Excord asks
once a launch, so a drive answers one ticket per launch. `ageRangeStatus`
overlays as attestation's status does: `available: true` by default on
a target with a cell at or above its floor (iOS and macOS 26, Android).

**Tracking consent.** On iOS and tvOS every `requestTrackingAuthorization`
under the agent holds a `tracking` ticket (a `choose` ticket with no
`while`: the status it would test is the implementation's, which
admission cannot read); on every other target the declaration's
`unsupported` list refuses the call `NotSupportedError` before a ticket
(`unsupported_here`, `runner/src/runner/modules/permits.rs`), and the
status answers its declared per-target default. The ticket is
answered `tap @t allow`, `tap @t deny` or `tap @t dismiss`; the tap
reaches the implementation as `preferred`. While the implementation's
status is `notDetermined` it answers the tap (`authorized`, `denied`, or
`notDetermined` for Apple's dismissal); with any other status it answers
that status whatever the tap, as the platform answers without asking.
`prefer extension
tracking-consent.trackingAuthorizationStatus={"status":"restricted"}` and
the other cases set the status, which the implementation overlays;
`advertisingIdentifier` answers a fixed UUID when `authorized` and zeros
otherwise.

**Disclosure.** `state.extensions` lists each module, its binding per
target, each call's name and outcome and the held tickets; never a
token, a range or an identifier. `--bind <module>` binds the real
framework under the agent, as geolocation's stage 2 binds its.

## 8. The consumers

### 8.1 The auth fixture: "Check this build"

`apps/auth-fixture` is exact2's sign-in fixture, whose server already
verifies passkeys (LLP 1133.011 §10). No app in the repository has a
server whose requests need proving: Weatherlight calls a public weather
API with no key (`apps/weatherlight/README.md`), and Excord's server is
Discord's. Snapback's identity server is the product consumer it unblocks
(`snapback4/README.md`), the same ask of Snapback passkeys made.

The fixture gains one row, "Check this build", whose action runs in data
code:

1. `POST /attest/challenge` answers a 32-byte random challenge, single
   use, five minutes.
2. `attest({clientData: challenge, account: handle, android:
   {cloudProjectNumber}})`.
3. `POST /attest/verify` with the answer and the challenge. The server
   verifies:
   - **`apple-appattest`** by Apple's steps, offline, reusing the CBOR and
     authenticator-data readers of `relying-party.mjs` and `node:crypto`'s
     `X509Certificate`, which Bun provides; it stores the key and counter by key id, accepts both
     `appattestdevelop` and `appattest` `aaguid`s with the environment
     each means (Apple's pages disagree on the sandbox's, [preparing](https://developer.apple.com/documentation/devicecheck/preparing-to-use-the-app-attest-service)
     against [validating](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server)),
     and reads `apple_validation_category_01` where present;
   - **`apple-appattest-assertion`** against the stored key and counter,
     answering "unknown key" for a key it does not hold;
   - **`play-integrity`** by `decodeIntegrityToken`, with the service
     account whose key file `EXACT_PLAY_INTEGRITY_KEY` names, a secret
     kept outside the repository (LLP 1133.020 §3);
   - **`exact-substitute`** only under `--substitute`, which the agent's
     drives start it with.
4. The row shows what the server concluded, not the token: "Attested: App
   Attest, development build", "Play: unrecognized version, no device
   integrity", or the failure.

On "unknown key" the action calls `resetAttestation` and tries once more;
on `NetworkError` it tries once more with the same challenge (D3).
The verdict is a value the view shows, so it is the mutation's answer; the
token never is (D2).

### 8.2 Excord: age-restricted channels

Discord marks a channel age-restricted with the channel object's `nsfw`
field ([Discord](https://discord.com/developers/docs/resources/channel#channel-object)),
and its clients show a confirmation before one opens. Excord, a client for
the real Discord whose bar is Discord's own client
(`apps/excord/llp/0001-excord.rfc.md`), has no such screen yet: it opens
the channel. That is a gap in Excord today, and it is the use the stores'
signal exists for, so Excord is the age range's consumer:

- The `Channel` shape gains `ageRestricted`, from `nsfw`; the fixture
  world gains one such channel.
- Opening one asks `requestAgeRange({ageGates: [18]})` in context, the
  first time in a launch. `lowerBound >= 18` opens it after Excord's
  confirmation screen, as Discord's does; `upperBound` below 18 shows that
  the channel is not available, with no way past; `unverified` shows the
  same, with Play's instruction to finish verifying in the Play Store,
  since there Play has said the person must verify first.
- Declined, undetermined, `NotSupportedError` (the web, Windows, iOS
  below 26) or `NotAllowedError` (an Android build not installed by Play,
  D8) shows the
  confirmation screen alone, which is Excord's behaviour without the
  module and Discord's own. That is a deliberate fallback, not a hole:
  where there is no signal the app has nothing better than the person's
  own confirmation. On Apple a decline is possible only where the region
  does not require the signal (Apple removes it there, D7). On Play,
  whether `NOT_SHARED` can occur where a law applies is not documented;
  the RFC claims only that Excord then behaves as with no signal.
- `apple.activeParentalControls` with `communicationLimits` is read and
  shown in no UI yet: what Excord should do under a parent's limits on a
  service whose limits are Discord's is a question for Excord's own RFC,
  not this module.

Discord's server enforces its own age rules on the account; the store's
signal is about the person holding the device, which is what Texas and
Brazil ask an app to use (D7).

### 8.3 Tracking consent: the package's fixture

No app in the tree links data across companies, and none should start in
order to consume this module. Its consumer is its package's fixture app,
made by `exact new` as every package's is: a status row, the D11 pre-alert
screen with one "Continue" button, the request, and the IDFA in data code
compared with zeros. That is a conformance drive, not a product's: the
module's acceptance proves the binding and the alert on iOS and tvOS,
not that an app is better for it. §11 question 1 rules to build it on
those terms.

### 8.4 The drives

Under the agent: drives 1 to 5 on the iOS simulator and macOS
(`apps/auth-fixture`), and on Android once stage 3 builds it; drives 6 to
9 on the iOS simulator, macOS and Android (`apps/excord`); drive 10 on the
iOS simulator and an Apple TV simulator; drive 11 where it says.

1. **Attest, then assert.** "Check this build" twice: the first answers
   `apple-appattest` (Android: `play-integrity`), the second
   `apple-appattest-assertion`; the server's log shows the key stored and
   the counter increased.
2. **Unknown key.** The fixture server forgets its keys
   (`/fixture/reset`); the next check answers unknown, the action resets
   and the retry attests a new key.
3. **Failures.** `prefer extension attestation.fail="NetworkError"` shows
   the failure row; the key is kept, and the retry with the same challenge
   attests it.
4. **A dropped attestation.** With `prefer extension
   attestation.delay=5000` the agent path answers after 5 s on the
   agent's clock; supersede the check within it: when the delayed reply
   arrives the journal names `dispose`, and the next call attests a new
   key. The same with an assertion keeps the key.
5. **No proof in state.** The fixture's test reads `state` after drive 1
   and finds no token.
6. **Age, 18 and over.** Excord: open the age-restricted channel; answer

7. **Age, under 18.** Answer `type @t 15`; the channel is unavailable,
   and no tap gets past it.
8. **Declined, and required.** `tap @t decline` shows the confirmation
   alone; with `declaredAgeRangeRequired` among the status's required
   features, decline is refused. On Android, `tap @t unverified` shows the
   channel unavailable, with Play's instruction (§8.2).
9. **A tool asks.** A tool invocation's `requestAgeRange` fails
   `person-required` with no ticket.
10. **Tracking.** The fixture's Continue, `tap @t allow`, status
    `authorized`, the IDFA not zero; a second request answers
    `authorized` whatever its tap; again from a fresh session with deny;
    with `restricted` preferred, `restricted` whatever the tap.
11. **Absent targets.** On the web (both apps), Linux (the three
    packages' fixtures) and Windows (Excord, on the NucBox) the status rows
    read `available: false` from the declared defaults, the calls refuse
    as D17 says, and Excord's age-restricted channel shows its
    confirmation screen alone.
