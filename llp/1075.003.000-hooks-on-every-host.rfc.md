## Summary

Charlie, 2026-10-02: hooks "should be available on every platform for every
native element — if you want/need them — but generally have it made clear that
using these can cause performance to get worse since exact2 can't optimize
stuff as much … there's something powerful about being always able to do stuff
to the native platform nodes."

- **D1. Any node can reach the app's native code.** The author marks it, and
  the app's module receives the node's platform object on every host that has
  one: a `UIView` or `NSView` and the UIKit or AppKit object of its kind, or a
  DOM element. Linux paints its own pixels and has none.
- **D2. The mark is per node, opt-in and declared.** The cost lands only where
  the author asked, and the build knows which nodes they are.
- **D3. A hooked node leaves the fast path, and Exact says so.** It gives up
  what Exact would otherwise do with it (§3.4). The hook's documentation says
  what, the journal says it once per name, `state` lists it, and a development
  build warns when a hooked node sits in a list row. Stage 4 measures the
  price on the Extra Heavy feed and the documentation quotes it.
- **D4. What is promised is the hook, not the internals.** The hook's names,
  its moments and one ownership rule (§3.6) are the named surface of 1075.003
  Q1. Which view class a node is, its subviews, and whether an unhooked node is
  a view at all stay Exact's to change.
- **D5. Container hooks follow the containers.** Built on iOS (1075.003). On
  macOS the window toolbar Exact already builds (`ToolbarMac.swift`) gets one
  now. On the web the navigation root, routes and tablist are elements, and get
  the same hooks. Other AppKit containers (a sidebar, a split view) need Exact
  to own them first: their own LLP.

One question for Charlie, ruled: the mark is a `hook` attribute naming a
declared word (Q1 (a), 2026-10-02).

## 2. The question

### Q1 — The mark

**Ruled (Charlie, 2026-10-02): (a).**

**Recommended (a): a `hook` attribute naming a declared word.**

```
image src=avatar hook="avatar" width=40 height=40
```

```json
"hooks": ["avatar"]
```

- `build.mjs` generates `ExactHookKey.avatar` in Swift, as it generates
  `ExactDataKey` from `data` (1075.003 Q2).
- A word not in `app.json` `hooks` fails the bake by name, as an undeclared
  `data-*` word does.
- It is visible at the node. A reader of the Contract sees which nodes native
  code touches and leave the fast path, which is the signal Charlie asked for.
- A component that carries the mark marks every instance, so "every avatar"
  is one line.

**(b) HTML's `part` attribute: `part="avatar"`.** HTML's name for an element
that code outside reaches by name (`::part()`), and on the web a real
attribute. Its HTML meaning is styling across a shadow boundary, which exact2
has none of, so a reader who knows `::part` would expect the wrong thing.

**(c) No attribute: declared HTML ids.** `app.json` `"elements": ["avatar"]`,
and every node with that `id` is hooked. No new Contract vocabulary, but
nothing at the node says it left the fast path, and an `id` already means other
things (`navigationBack`, `navigationScroll`, `aria-controls`).

No web standard names this: the web hands every element to script, so it never
needed a mark. (a) is exact2's own word for the one thing the web never had to
say.

## 3. The design

### 3.1 The mark (D2)

- One word a node, a literal. A word follows `data-*`'s rule: lowercase
  letters and digits joined by `-`. A binding is refused (`lower-hook-value`):
  a node that became hooked at run time would need its view made mid-row, and
  the JS target could not compile the call only where it is needed.
- It lowers to one kernel row, `hook` (`schema.json`), so every host, the
  agent's `tree` and the bake see it.
- A module view (a hyphenated tag) is already the module's own instance; a mark
  on one is refused (`lower-hook-module`).
- `data-*` still never forces a view. A hooked node's `data-*` words reach its
  hook (`element.data`), so one word can name many differently-configured nodes.

### 3.2 The `element` hook and its moments

Swift, on the app's `ExactModule` (Apple):

```swift
open func element(_ element: ExactElement) {}
open func elementEnded(_ element: ExactElement) {}
```

`ExactElement` keeps what it has (`id`, `click()`, `focus()`, `blur()`, live
only while its node is) and gains, for a hooked node:

- `hook: ExactHookKey`, `data: ExactData`, `isNew`, `isLive`;
- `reusable`, which the hook sets when `elementEnded` undoes everything it
  added to the view: its list row may then be reused (iOS, §7.6);
- `view`: the node's `UIView` or `NSView`, weak;
- `platform`, the kind's platform object, nil when the kind has none, and
  typed views of it: `scrollView`, `textField`, `textView`, `control`
  (switch, slider, segmented control, date picker and the rest of
  `ControlsIOS`). A web view is `platform` (as-built, §7.1).

The web's page module (`modules/web/index.js`) exports the same names:
`element(e)` and `elementEnded(e)`, where `e` is `{ hook, data, element,
click(), focus(), blur() }` and `element` is the DOM element.

The moments are the route hook's (1075.003 §3.2):

- **built**, after the batch that mounts the node is applied: the view is in
  its parent and laid out. Never inside a batch;
- **changed**, when its `data-*` words change;
- **ended**, before its view leaves: unmount, a reload, the session's end.

Not on a style, layout or text change: those are Exact's. A heavy leaf whose
view waits during a fling (1068 §5.1) is hooked when its view is made.

### 3.3 What a hooked node is, per host

| Host | The hook receives | What Exact stops doing for it |
|---|---|---|
| iOS | its `NodeView` and the kind's UIKit object | It is never a flat leaf (1068 §6). A list row that holds one is never parked in the node pool, unless its hook is `reusable` (§7.6): it is destroyed and built again. Its hook is main-thread work at mount, on top of the row the owner thread built (1072) |
| macOS | its `NodeView` and the kind's AppKit object | Nothing beyond the call: macOS has no flat leaves or node pool |
| Web | its element | It stays its own element if Exact ever collapses elements (QUEUE: a button's only text). Nothing today: the web host reuses no elements |
| Linux | nothing | Nothing. The row stays in the plan; the journal says once that the host has no native objects |

Two kinds are not what the platform's own widget would be:

- **Text on Apple** is a `NodeView` whose layer shows a bitmap Exact rasterizes
  off the main thread (`TextRasterIOS.swift`), not a `UILabel` or
  `NSTextField`. Its text, font and layout are Exact's; a hook may add an
  interaction to it.
- **An element inside an `svg`** has no native object on Apple or Linux (an
  `svg` draws as one scene). On the web it is a real element, and the hook
  receives it (Charlie, 2026-09-27: allow what a platform supports, rather
  than the lowest common denominator). Elsewhere the journal says so once.

### 3.4 What it costs (D3)

What each lost optimization saved where it was measured:

| Lost | Measured when it was built |
|---|---|
| Flat leaves (iOS) | 1068 §6.2, the Extra Heavy feed's fling: main thread 405 → 390 ms/s on the iPhone 13 Pro Max, 411 → 392 on the M1 iPad Pro; in a Time Profiler window, pool take and retire 34 → 16 ms/s, `NodeLayer.display` 37 → 19, UIKit layout and display 47 → 23, the Core Animation commit 63 → 43 |
| The node pool (iOS) | `NodePoolIOS.swift` (LLP 1050.000's reuse): building a row's views is most of a row's cost in UIKit, and destroying one costs the same walk out; a parked row skips both. 1068 §6.2's window put the pool's own take and retire at 16–34 ms/s |
| The main-thread call | The C call is negligible. The hook's own work is not: the canvas feed's fling mounts about 25 rows a second (QUEUE, LLP 1056 D10), so 1 ms of hook per row is 25 ms/s of main |

- A few hooked nodes on a screen cost nothing measurable. A hooked node in
  every row of a long list gives some of the above back, and the hook's work
  runs on main as each row mounts.
- What the hook then does is outside Exact's view. A shadow path, a gesture
  recognizer or a sublayer per row costs what it costs in UIKit.
- Stage 4 measured the Extra Heavy feed with every row's avatar hooked, the
  hook empty, against none (§7.4). The hook's documentation quotes it.

### 3.5 Saying so (D3)

- **Documentation.** The doc comment on `element` (Swift) and the page module's
  (web) say what a hooked node gives up, with Stage 4's numbers.
- **The journal, once per word:** `hook element avatar: a view, not a flat
  leaf; its row is not reused (LLP 1075.003.000)`.
- **`state.hooks`:** per word, how many are live and what they gave up
  (`flat`, `pool`).
- **A development warning, once per word,** for a hooked node in a virtualized
  list's row: `hook element avatar is in every row of list feed: each row's
  mount calls it on the main thread, and the row is never reused`.
- **`tree`** shows `hook: "avatar"` on the node, as a row of the plan, so a
  drive knows it is there.

None of these gates anything. They make the cost visible where an author or an
agent will see it.

### 3.6 What Exact owns of a hooked node (D4)

One rule for every kind: **Exact owns every platform property an authored row
or attribute writes; the app owns the rest.**

- **Every view:** Exact owns frame, bounds, center, transform, alpha,
  `isHidden`, the layer paint it draws, its own subviews and their order, and
  the gestures and accessibility it derives. The app may add interactions
  (context menu, drag and drop, pointer, edit menu), its own gestures (under
  LLP 1057's precedence), and its own subviews and sublayers above Exact's.
  Stage 1 checks that the presenter orders and removes only its own children.
- **By kind,** what the authored rows write: a scroll view's offset, content
  size, insets, delegate and keyboard dismissal (1075.003 §3.5); a text
  field's text, the selection Exact sets, its delegate, and what `inputmode`,
  `enterkeyhint`, `autocapitalize` and `autocomplete` set; a control's value,
  enabled state and the actions Exact added; a tint `accent-color` sets.
  Anything no row writes (an input accessory view, a haptic, a badge) is the
  app's.
- **The development check** of 1075.003 §3.5 runs over each hooked node before
  each batch, comparing what Exact owns with what it last wrote, and journals a
  difference once. Production does not check.

### 3.7 Containers on every host (D5)

- **iOS:** `navigation`, `route`, `routeEnded`, `tabs`, `tabContainer`, as
  built.
- **macOS:** `toolbar(_ toolbar: ExactToolbar)`, with the window's `NSToolbar`
  that `WindowToolbarHost` builds for the Contract's commands, and its window.
  Exact keeps the toolbar's delegate (forwarded, as the navigation delegate
  is) and its own items. The app may set display mode and appearance, and add
  items after Exact's, which Exact never removes. Sidebars, split views and tab
  views are not Exact's on macOS today. A separate LLP decides which AppKit
  containers Exact projects, and each gets its hook then.
- **Web:** `navigation(root)`, `route(e)`, `routeEnded(e)` and `tabs(tablist)`,
  with elements, when `navigation.js` projects (a View Transition, a
  per-route behavior).
- **Linux:** none. **Android, later:** the same names in Kotlin.

### 3.8 The agent, delivery and the promise

- **The agent** sees the plan's tree, the `hook` row included, and never what a
  hook did (LLP 1021 D4). `screenshot` shows it. A control a hook makes is
  driven by clicking an authored one (1075.003 §3.4).
- **Delivery.** A Swift hook is native code: changing it is a native change
  (LLP 1030), a store release. The web's page module ships with the web root.
- **The promise** (1075.003 Q1): the hook names of §3.2 and §3.7, the moments,
  `ExactElement`'s members, and §3.6's rule. Not the view classes, their
  subviews, or which unhooked nodes are views.

**Stage 1 — the mark and `element` on Apple.**
- The `hook` row; its lowering, `lower-hook-value`, `lower-hook-module`; the
  bake's check against `app.json` `hooks`; `ExactHookKey`.
- iOS: a hooked node is never flat and its row is never parked; the three

- Acceptance: XCTests show a hooked leaf is a view, its row is not parked, the
  moments arrive in order across a push, a pop, a reload and a session's end,
  and an owned write is journaled; `smoke.mjs <ios|macos|web|linux>` sees the
  row in `tree`.

**Stage 2 — the web.**
- The page module's `element`, `elementEnded`, `navigation`, `route`,
  `routeEnded` and `tabs`, from the wasm glue and from the JS target's
  emitted code, which calls them only for marked nodes.
- They link by use (QUEUE's standing rule): an app whose page module exports no
  hook pays nothing.
- Acceptance: `smoke.mjs web --app native-fixture` sees the moments; the web
  cores of Caltrain, RealWorld and video-player are unchanged.

**Stage 3 — the macOS toolbar hook.** Acceptance: the fixture's hook sets a
display mode and adds an item; `smoke.mjs macos` sees both and Exact's items
still work.

**Stage 4 — the price.** The measurement of §3.4 on the iPhone and the iPad,
written into the hook's documentation and this LLP.

**Separately:** an LLP on which AppKit containers Exact projects.

## 5. Against the rules, and risks

- **"Still refused: native property names in Contract"** (DEFERRED's 1075.003
  entry; 1035.006 12.08): kept. The mark is a word the app declares, not a
  property, and no platform name enters Contract.
- **Agents add no apparatus:** the fixture and its tests grow. The warning is a
  journal line, not a gate.
- **Link by use:** web hooks reach the core only when the page module exports
  one (Stage 2's acceptance).
- **The escape hatch becomes the road.** An app can hook every node and lose
  parity across hosts, agent drives and the fast path. The mark, the journal,
  `state` and the numbers make that visible. Nothing prevents it, by design.
- **Freezing the internals.** D4 promises the hook, not the views. A hook that
  casts a view to a private class breaks when the class changes, and that is
  the app's to carry.
- **An app's subviews inside an Exact view** can disturb hit testing or
  accessibility order. Stage 1 checks the presenter, and the journal names the
  hook when the development check sees Exact's own children reordered.

## 7. As built (2026-10-02)

Stages 1–3 are built on `lane/native-control`; Stage 4 was measured on
devices (§7.4).

### 7.1 What runs

- **The mark.** The `hook` row (219), `lower-hook-value`, `lower-hook-word`,
  `lower-hook-module`, `bake-undeclared-hook` beside `bake-undeclared-data`,
  `app.json` `hooks`, `ExactHookKey` generated beside `ExactDataKey`. On the
  web the row is the attribute `data-hook`, so `hook` is a host word.
- **Apple** (`ElementHooks.swift`, shared by both presenters): the moments
  of §3.2, replayed when the module connects; module table entry 160 (a
  168-byte table; a 160-byte one still loads, with no `element`). The
  platform object is the node's text field or view, control (`ControlsIOS`'s,
  which includes date pickers), web view (iOS) or scroll view. A video's
  player is not exposed: `VideoView` keeps it private.
- **iOS opt-outs.** A hooked node is never a flat leaf (its `hook` prop makes
  it ineligible, as any prop but `data-*` does), and a list row holding one
  is never parked: the pool asks the view's own `hook` prop, which outlives
  its node's destroy op (a row's children are destroyed before the row). On
  the fixture's 200-row list: without the condition the scroll parked 14
  rows and the next rows took 10 of them; with it, none was taken.
- **Saying so.** The journal names each word once (`hook element dot: a
  view, not a flat leaf; its row is not reused`; macOS and the web: `nothing
  beyond the call on this host`) and warns once for a word in a list's row;
  in a list's row only the first call of each moment is journaled, and
  `state.hooks` counts every call. The agent's `tree` prints `hook="word"`
  on every host.
- **The development check** (iOS) covers a hooked node's scroll view (as a
  route's) and its text field's or text view's delegate. Not built: a base
  view's frame, alpha and the rest (no last write is recorded for them), and
  any check on macOS or the web.
- **The web** (Stage 2) is the JS target, which is what an app ships:
  `hooks.js`, bundled only into a plan that marks a node (Caltrain's bundle
  carries none of it, only `navigation.js`'s one-line call below). `data` is
  the element's own `dataset`, so the host's words are in it too. The
  container hooks load after first paint only for a page module that
  exports one (the build imports the module to see); routes hear built and
  ended, not changed. The wasm target, which now builds only games,
  conformance and fixtures (LLP 1071 §7), has no hooks.
- **macOS toolbar** (Stage 3): module table entry 168 (176 bytes), host
  callback 40 (`toolbar_item`, a 48-byte host table), `ExactToolbar` with
  `add(_:)` and a forwarded `delegate`; the app's items stay after Exact's
  until the toolbar is uninstalled. One platform fact: a window toolbar's
  window takes the `.unifiedCompact` style (ExactMac), under which AppKit
  shows icons only whatever `displayMode` says, so a hook that wants labels
  sets the window's `toolbarStyle` too (the fixture does).

### 7.6 A reusable hook (2026-10-02, Charlie: "I think it might be pretty common")

- **The opt-in.** A hook sets `element.reusable = true` when `elementEnded`
  undoes everything it added to the view. The `element` call returns it
  (module entry 160 returns flags; bit 0), the view carries the mark, and the
  node pool reuses a row whose hooked nodes are all reusable. A reused view's
  mark is cleared (`recycle`); the next node's hook decides again.
- **The safety net.** The pool's own checks still refuse a view with
  interactions or gesture recognizers left on it, so a hook that forgets to
  undo costs the reuse, not another row. A property the hook changed and
  left is not seen: that is the app's, as `prepareForReuse` leaves it.
- **The order.** A row's root is destroyed before its children, and the pool
  decides at the root. Every hooked node a batch destroys now ends at the
  batch's start (`ElementHooks.begin`), so a reusable hook has undone its
  additions before the pool looks.
- **Saying so.** The journal says a reusable word's rows are reused; the
  list-row warning drops "never reused"; `state.hooks` counts reusable nodes
  and leaves `pool` out of a word whose live nodes are all reusable.
- **Tested** by the fixture's Rows route: a Reuse toggle sets `data-reuse`
  on each row's dot, whose hook adds a long-press recognizer and takes it
  back in `elementEnded`; the iOS smoke checks that rows are reused only
  then. Measured on devices in [1075.003.000.000](1075.003.000.000-the-price-of-a-hooked-node.research.md) §8:
  a reusable hook in every row of the Extra Heavy feed runs as the unhooked
  feed within noise (iPhone 115.3 → 115.0 fps, CPU 573 → 583 ms/s; iPad
  117.6 → 117.6, 619 → 617), where a plain hook costs 5.1 and 2.5 fps.
