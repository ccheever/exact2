## Summary

`@exact/alarms` sets an alarm: an alert that comes at a set time, or when
a countdown ends, and keeps sounding through silent mode and Focus until
the person stops it. It is what a cooking timer, a practice timer or a
wake-up alarm needs, and what a notification is not:

```
use scheduleAlarm, cancelAlarm, pauseAlarm, resumeAlarm, alarms, alarmStatus,
  AlarmStatus, Alarm from "@exact/alarms"

resource status = alarmStatus() as shape AlarmStatus
resource running = alarms() as shape Alarm[]
action startPractice(minutes: number)
  scheduleAlarm(tag="practice", title=`Practice: ${minutes} min`,
    duration=minutes * 60000, snooze=minutes * 60000)
action stopPractice
  cancelAlarm(tag="practice")
```

```ts
import { scheduleAlarm } from "@exact/alarms";

await scheduleAlarm({ tag: `boil:${pot}`, title: "Eggs are done", duration: 9 * 60000 });
```

No web API sets an alarm, so tier 1 is a declared deviation (D2): the
shared words of AlarmKit and Android's alarm clock, under the web's
conventions for errors, tags and status. Where the module sits is the
decision this RFC exists for (D1):

- **A notification** (LLP 1133.004) is text the person reads when they
  choose, which silent mode and Focus may hold back; `showTrigger` times
  it.
- **A wake** (LLP 1133.017) runs the app's code at a time the system
  chooses, and shows nothing.
- **An alarm** is an alert at an exact time that silent mode and Focus do
  not stop, which rings until stopped, offers Stop and, if asked, Snooze or
  Repeat, and shows a countdown on the Lock Screen while it runs. **No app
  code runs when it fires**: the system presents it on iOS, the package's
  own receiver on Android, the system's scheduled toast on Windows. The
  app learns what happened at its next read of `alarms()`.

Android's exact-alarm permission is one per app, so this module owns it:
`device.alarms` derives `SCHEDULE_EXACT_ALARM` (D7), and notifications'
stage 3 posts a timed notification exactly only when the app holds it
(§12, a recommendation that reaches LLP 1133.004).

| Target | Cell |
|---|---|
| iOS, iPadOS 26+ | AlarmKit; below 26 `available` false |
| Android | `AlarmManager.setAlarmClock`, with the package's receivers, alert activity and ringing service |
| Windows | a scheduled toast in the `alarm` scenario |
| web, macOS, Linux, tvOS, terminal | absent: no platform API lets an app's alert override silence and Focus while the app is not running |
| Expose | later |

The consumer is Metronome's practice timer (D16). The stages are the
seams and the substitute (stage 0), iOS (1), Android (2) and Windows (3),
each with its drive (§14).

## 0. What is new here

1. **A third kind of timed thing,** with a line drawn against the two the
   library has (D1): an alarm runs no app code at fire, unlike a wake, and
   overrides the person's quiet, unlike a notification. Each platform
   keeps this line itself: AlarmKit is a framework separate from
   UserNotifications, and Apple says alarms "are not a replacement for
   other prominent notifications, like critical alerts or time-sensitive
   notifications" (WWDC25 230).
2. **The package owns Android's exact-alarm permission,** which is
   app-wide; notifications' timed posts use it only when held (D7, §12).
3. **A host-drawn Live Activity for a package.** AlarmKit "expects a
   widget extension if an app supports a countdown presentation.
   Otherwise, the system may unexpectedly dismiss alarms and fail to
   alert" ([AlarmKit](https://developer.apple.com/documentation/alarmkit)).
   LLP 1126's extension holds one `ActivityConfiguration`, generated only
   from `app.json`'s `live_activities`. A package now declares one more,
   which the host draws in the platform's look (D8).
4. **Android code that runs with no session and before first unlock:**
   receivers, a service and an activity the package declares through a
   manifest fragment (LLP 1133.026 D19 item 3, widened), with its records
   in device-protected storage (D9).
5. **The substitute's keyed list grows** app scope, a due time on the
   agent clock and named choices on `tap @ref` (D12).

## 2. The line

### D1 — Alarms, notifications and wakes

An app that wants something to happen later has three modules, and the
choice between them is the person's experience, not the app's code:

| | Notification (LLP 1133.004) | Wake (LLP 1133.017) | Alarm (this) |
|---|---|---|---|
| What the person gets | a banner and a list entry | nothing | an alert that takes the screen or a banner, and sound until stopped |
| Silent mode and Focus | hold it back, as the person set them | — | do not stop it: AlarmKit's alert "overrides both a device's focus and silent mode" ([AlarmKit](https://developer.apple.com/documentation/alarmkit)); Android's Do Not Disturb lets alarms through unless the person turns that off (D3) |
| When | `showTrigger`, as the platform delivers it | when the system chooses | exactly: `setAlarmClock`'s alarms are ones whose delivery time "the system never adjusts", and it "leaves low-power modes if necessary to deliver" them ([Schedule alarms](https://developer.android.com/develop/background-work/services/alarms)) |
| App code at that time | none, until a click (`notificationclick`) | the handler, in a session with no view | none |
| What the person can do | open it, dismiss it | — | Stop; Snooze or Repeat when the app asked; Pause and Resume a countdown |
| A countdown on the Lock Screen | no | no | yes, while it runs |
| Permission | notifications' | none (`initial: granted`) | its own (D7) |

**The test** an author applies: *would the person be surprised if silent
mode kept it quiet?* A wake-up alarm, a timer the person started, a
practice session's end: yes, an alarm. A reminder, a message, a
departure: no, a notification. Apple's guidance draws the same line:
alarms suit "countdowns with a specific interval, like a cooking timer,
or recurring alerts with a schedule, like a wake-up alarm" (WWDC25 230).

**Why no app code at fire.** An alarm must ring when the app is not
running, after a reboot, on a locked phone, and on iOS the app never gets
the chance: AlarmKit presents the alert itself. Running the app's code
then would make an alarm a wake with a sound, which the platform does not
allow on iOS and which on Android would put a plan boot between the
system's intent and the ring, before first unlock where the app's data is
unreadable (D9). So an alarm is complete when scheduled: its title, its
time or duration and its snooze are all it says, and the platform (or
the package on its behalf) does the rest. Alarms declare no module events.
An app that wants its code to run when the alarm rings (log the practice
session) reads `alarms()` when it next runs, or schedules a wake beside it
(LLP 1133.017), which runs when the system lets it.

**Not duplicated.** Alarms take nothing of notifications' (no
`showNotification` option rings through Focus: that stays an alarm) and
nothing of background's (no alarm runs a handler). On Android the two
modules that time things share one platform service, `AlarmManager`, and
one app-wide permission; D7 gives that permission to this module and §12
says how notifications uses it.

## 3. Tier 1

### D2 — Shared words, a declared deviation

No web API sets an alarm: the Notification Triggers draft that gave
`showTrigger` its name was abandoned, and nothing in the web platform
rings through a device's silence. So tier 1 takes the shared words of
AlarmKit's [`AlarmManager`](https://developer.apple.com/documentation/alarmkit/alarmmanager)
and Android's alarm clock, under the web's conventions: a `tag` as the
Notifications API keys a notification, `DOMException` names for errors,
and a status fact with `available` and `state` as geolocation's
(LLP 1133.002 D6).

| Name | Kind | What it does |
|---|---|---|
| `scheduleAlarm(tag=, title=, at=, duration=, snooze=)` | send, answers nothing (LLP 1133.004 D5); asks while `prompt` (D7) | sets an alarm: at the instant `at` (epoch milliseconds), or after `duration` milliseconds as a countdown; exactly one of the two. `title` is what the alert says. `snooze`, milliseconds, adds a second button that starts a countdown of that length: Snooze for an alarm at a time, Repeat for a countdown. A tag that names an alarm replaces it |
| `cancelAlarm(tag=)` | send, answers nothing | ends the alarm whatever its state: scheduled, counting down, paused, or ringing (it stops the ring) |
| `pauseAlarm(tag=)`, `resumeAlarm(tag=)` | send, answers nothing | pause and resume a countdown; `InvalidStateError` on an alarm that is not counting down or paused |
| `alarms()` | live source, `sync` on every target with an implementation | the app's alarms (D4) |
| `alarmStatus()` | live source, `sync` | `{available, state}` and each platform's words (D5) |
| `requestAlarmPermission()` | request | asks for what `state` lacks and answers the new status (D7) |

```
shape Alarm
  tag: string
  title: string
  state: enum<scheduled|countdown|paused|alerting>
  at: option<number>         // when it rings: the instant, or a countdown's end
  duration: option<number>   // a countdown's length as set
  remaining: option<number>  // a paused countdown's time left
  snooze: option<number>

shape AlarmStatus
  available: bool
  state: enum<granted|denied|prompt|unknown>
  countdown: bool            // the platform shows a running countdown outside the app
  apple: option<AppleAlarmStatus>
  android: option<AndroidAlarmStatus>
```

**Why tags, not handles.** An alarm outlives the session, the process and
a reboot (D4), so it cannot be a handle the package context ends at
`destroy` (LLP 1133.009 D10); the app names it, as a notification's tag
names a notification. Tags are the app's: every session of the app reads
one list, as two documents of one web app read one badge (LLP 1133.004
§7). The implementation maps a tag to the platform's identifier (a UUID
on Apple, a request code and record on Android, a scheduled toast's `Tag`
on Windows) in its own store.

**Replacing.** A second `scheduleAlarm` with a tag schedules the new alarm
and then cancels the old one, so a failed replacement leaves the old
alarm, not none.

**Refusals,** each a journal line in Contract and a rejected promise in
data code (LLP 1133.006 D8 item 2):

| Case | Error |
|---|---|
| no implementation on this target, or the OS is too old | `NotSupportedError` |
| `state` is `denied`, or a tool or a wake while `prompt` (D7) | `NotAllowedError` |
| neither or both of `at` and `duration`; `at` not after now; a `duration` or `snooze` under one second; an empty `title` | `TypeError` |
| AlarmKit's `maximumLimitReached` ([`AlarmError`](https://developer.apple.com/documentation/alarmkit/alarmmanager/alarmerror)) | `QuotaExceededError` |
| pause or resume in the wrong state; a tag that names no alarm (cancel is not refused: cancelling nothing does nothing) | `InvalidStateError` |

`at` is an instant: AlarmKit's [`Alarm.Schedule.fixed`](https://developer.apple.com/documentation/alarmkit/alarm/schedule-swift.enum),
which does not move with a change of time zone. An alarm that keeps a
local time of day across a time-zone change (AlarmKit's `.relative`) is
one that repeats, and stays out with repeats (§13).

### D3 — Unsaid defaults are the platform's

What the author leaves unsaid comes out as the platform's own alarm, so a
person who knows the platform sees the Clock app's behaviour:

| What | Default | Source |
|---|---|---|
| The alert | iOS: the system's alarm alert, full screen on the Lock Screen, a banner while the phone is in use; Android: a full-screen activity over the keyguard when the screen is off or locked, and a heads-up notification with Stop and Snooze while the phone is in use; Windows: a toast "displayed pre-expanded" that stays "till dismissed" | WWDC25 230; [`setFullScreenIntent`](https://developer.android.com/reference/android/app/Notification.Builder#setFullScreenIntent(android.app.PendingIntent,%20boolean)) and [time-sensitive notifications](https://developer.android.com/develop/ui/views/notifications/time-sensitive) ("the system UI displays a heads-up notification instead while the user actively uses the device"); the [`toast` element](https://learn.microsoft.com/uwp/schemas/tiles/toastschema/element-toast)'s `alarm` scenario |
| Sound | the platform's alarm sound, repeating until stopped: AlarmKit's `.default`; Android's default alarm ringtone (`RingtoneManager.TYPE_ALARM`) on the alarm stream (`AudioAttributes.USAGE_ALARM`); Windows' looping alarm sound, which the `alarm` scenario uses "by default" | AlarmKit's `AlertConfiguration.AlertSound`; [`AudioAttributes`](https://developer.android.com/reference/android/media/AudioAttributes#USAGE_ALARM); the `toast` element |
| Silence and Focus | iOS overrides both; Android lets the alarm through Do Not Disturb unless the person has turned off alarms there ([`NotificationManager.Policy`](https://developer.android.com/reference/android/app/NotificationManager.Policy)'s `PRIORITY_CATEGORY_ALARMS`, "Alarms are prioritized"), and the alarm stream is not the ringer, which silent mode mutes; Windows: the person's Do Not Disturb settings, measured in stage 3 | as cited |
| Buttons | Stop, which the system provides on iOS (`stopButton` is deprecated in iOS 26.1); the second button only with `snooze`, its label the platform's word ("Snooze", or "Repeat" for a countdown, as Apple's sample names it); on Windows the system's own snooze and dismiss buttons (`activationType="system"`) | [Scheduling an alarm with AlarmKit](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit); [App notification content](https://learn.microsoft.com/windows/apps/develop/notifications/app-notifications/app-notifications-content) |
| A running countdown outside the app | iOS: a Live Activity on the Lock Screen and in the Dynamic Island (D8); Android: an ongoing notification whose chronometer counts down (`setUsesChronometer`, `setChronometerCountDown`), as the Clock app's timer shows; Windows: none (`countdown` false) | ActivityKit; [`Notification.Builder`](https://developer.android.com/reference/android/app/Notification.Builder#setChronometerCountDown(boolean)) |
| The next alarm in the system's UI | Android shows an alarm set by `setAlarmClock` as the next alarm ("the system will typically also use the information supplied here to tell the user about this upcoming alarm") | [`setAlarmClock`](https://developer.android.com/reference/android/app/AlarmManager#setAlarmClock(android.app.AlarmManager.AlarmClockInfo,%20android.app.PendingIntent)) |
| Tint | the app's accent colour, as the system tints the alert's buttons | AlarmKit's `AlarmAttributes.tintColor`, which the app must give, so the package gives the accent |
| A paired Apple Watch | the system forwards the alert | WWDC25 230 |
| Vibration | the platform's, with the sound | as each alert above |

Android's alert screen is the one place exact2 draws an alarm's UI: Android
has no system alarm alert, so the package's activity draws title, time,
Stop and Snooze in Material's look, as the platform's Clock does (D9). It
is native, not a plan's view, because it must run before first unlock and
without a session.

### D4 — What the app knows, and when

`alarms()` answers the app's alarms, each with its `state`, which comes
from the platform where the platform keeps it:

| State | iOS | Android | Windows |
|---|---|---|---|
| `scheduled` | `Alarm.State.scheduled` | the package's record, alarm set | in `GetScheduledToastNotifications` |
| `countdown` | `.countdown` | the record, a countdown running | in the schedule, the record a countdown |
| `paused` | `.paused` | the record, no alarm set, `remaining` kept | the record, no toast scheduled |
| `alerting` | `.alerting` | the record, the ringing service running | not readable: a delivered toast leaves the schedule, so the alarm leaves the list |
| gone | not in `AlarmManager.alarms` | no record | neither in the schedule nor recorded |

AlarmKit reads back an alarm's id, schedule, countdown and state, not its
title, and Apple's sample keeps "your alarms in your own store" to compare
([Scheduling an alarm](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit)).
So each implementation keeps a record per tag (title, snooze, and the
platform's identifier) and answers the platform's state over it; an alarm
the platform no longer has is gone, and its record is removed at the read.

**When the list changes.** While the app runs: AlarmKit's `alarmUpdates`;
Android's receivers, which tell a running process; on Windows, a read
when the app comes to the foreground. While it does not run: nothing; the
next session's first read is current. A person who stops an alarm on the
Lock Screen is seen by the app as an alarm gone.

**What outlives what.** An alarm outlives its session, the process and a
reboot: AlarmKit keeps it; on Android the package sets it again after a
boot (D9); Windows keeps its schedule. Only `cancelAlarm`, the person, or
the platform (Android's revocation of exact alarms, D7) ends one. A
package context's `destroy` leaves alarms alone, and `release(name, args)`
has nothing to release: a send that answers nothing holds nothing.

## 4. Tier 2 and tier 3

### D5 — The platforms' words

| Platform | Word | Beats in tier 1 |
|---|---|---|
| Apple | `apple.tintColor` (a colour) on `scheduleAlarm` | the accent colour |
| Apple | status `apple.authorizationState`, `notDetermined|denied|authorized` ([`AuthorizationState`](https://developer.apple.com/documentation/alarmkit/alarmmanager/authorizationstate-swift.enum)) | — |
| Android | status `android.canScheduleExactAlarms` ([`canScheduleExactAlarms`](https://developer.android.com/reference/android/app/AlarmManager#canScheduleExactAlarms())), `android.notifications` (`granted|denied|prompt`, with notifications' history), `android.canUseFullScreenIntent` ([`canUseFullScreenIntent`](https://developer.android.com/reference/android/app/NotificationManager#canUseFullScreenIntent())) | — |
| Android | `openFullScreenIntentSettings()`, a send from `@exact/alarms/android` only: `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` | — |

A full-screen intent does not change `state`: without it the alarm still
rings, as a heads-up notification on the Lock Screen
(`setFullScreenIntent`'s documentation). An app that wants the full-screen
alert asks for it with its own explanation, through the platform-only
send. Windows has no words of its own now.

### D6 — Access hatches

| Platform | Object | When | The app may | The package keeps |
|---|---|---|---|---|
| Apple | `AlarmManager.AlarmConfiguration<ExactAlarmMetadata>` | before `schedule(id:configuration:)` | set a named `sound` (a file in the main bundle or `Library/Sounds`), a `stopIntent` or `secondaryIntent` with `.custom` behaviour, iOS 27's `appEntityIdentifier`, a pre-alert countdown before a fixed alarm | the id, the schedule or duration, the attributes' metadata type, the record |
| Windows | the toast's `XmlDocument` | before `AddToSchedule` | add text, images, inputs (a snooze-length selection box), a custom audio `src` | the `Tag`, `Group`, delivery time, the `alarm` scenario |
| Android | none | — | — | — |

Android has no hatch because no app code runs at fire (D1): the
notification, the activity and the sound are made by the package's
receiver in a process with no session. A hatch there would need the
app's Kotlin to be named in the manifest and run before first unlock,
which no consumer asks for. Intents given through the Apple hatch are the
app's own App Intents, which exact2's build does not process today (§1);
an app that uses them owns that.

Out, on purpose: repeats and local times (one DEFERRED refusal), an
author-drawn countdown (a surface, LLP 1126) and the Clock app's intents
(not this module's kind of alarm). Every other use is reached.

## 6. Permission

### D7 — LLP 1133.002 §4, for alarms

**Declare.** A new grant line, `device.alarms <strings key>`, the key the
explanation a platform shows:

| Platform | Derived |
|---|---|
| iOS | `NSAlarmKitUsageDescription` from the strings key: "If `NSAlarmKitUsageDescription` is missing or empty, apps can't schedule alarms" ([`NSAlarmKitUsageDescription`](https://developer.apple.com/documentation/bundleresources/information-property-list/nsalarmkitusagedescription)) |
| Android | `SCHEDULE_EXACT_ALARM`, `POST_NOTIFICATIONS`, `USE_FULL_SCREEN_INTENT`, `RECEIVE_BOOT_COMPLETED`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SYSTEM_EXEMPTED`, and the manifest fragment (D9) |
| Windows, web | nothing |

**`SCHEDULE_EXACT_ALARM`, not `USE_EXACT_ALARM`.** Android offers two.
`USE_EXACT_ALARM` is "granted automatically", "cannot be revoked by the
user" and is "subject to an upcoming Google Play policy"
([Schedule alarms](https://developer.android.com/develop/background-work/services/alarms)):
Play admits it only for an app whose core function is an alarm clock, a
timer or a calendar, through a declaration form
([Play policy](https://support.google.com/googleplay/android-developer/answer/13161072)).
`SCHEDULE_EXACT_ALARM` is the person's to give, is "not pre-granted to
most newly installed apps targeting Android 13 and higher" on Android 14
([denied by default](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms)),
and serves the "broader set of use cases". An app whose timer is one
feature among others, as Metronome's is, may not declare
`USE_EXACT_ALARM`. A second grant line for an alarm-clock app
(`device.alarm-clock`, deriving `USE_EXACT_ALARM`) waits for such a
consumer (§15 question 2).

**The exact-alarm permission is app-wide and this module's.** Android
grants exact alarms to an app, not to a use; whichever module asks, every
`AlarmManager` call of the app gets it. One module must own the manifest
line and the request, or two modules would ask for one thing with two
explanations. This module owns it because an alarm cannot work without it,
where a timed notification can (§12). An app that uses notifications'
`showTrigger` and not alarms declares no exact-alarm permission.

**Read.** `alarmStatus()`:

| Platform state | `state` |
|---|---|
| iOS below 26, macOS, web, Linux, tvOS, terminal | `unknown`, `available` false |
| AlarmKit `notDetermined` | `prompt` |
| AlarmKit `authorized` | `granted` |
| AlarmKit `denied` | `denied` |
| Android: exact alarms held and notifications granted | `granted` |
| Android: exact alarms not held, notifications not denied | `prompt` (the person can give it in Settings at any time; it has no "don't ask again") |
| Android: notifications permanently denied, or turned off for the app (`areNotificationsEnabled()` false) | `denied` |
| Windows: notifications `Enabled` | `granted` |
| Windows: notifications disabled by the person, policy or manifest | `denied` |

Android needs both because an alarm without notifications cannot be
stopped: the ringing service's notification carries Stop, and Android 13+
hides it without `POST_NOTIFICATIONS`. `POST_NOTIFICATIONS` is one
permission with one history whichever module asks (LLP 1133.008 D8 item
7); `@exact/notifications` and this module share its state as two
interfaces share one permission (LLP 1133.026 D19 item 2), each composing
its own status from it.

The status is `sync` on every target: AlarmKit's `authorizationState` is
a property, and `canScheduleExactAlarms()` and `areNotificationsEnabled()`
answer at once. It changes by itself: the implementation follows
`authorizationUpdates` on Apple, reads again at the app's foreground on
Android, and Android also sends
`ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` when exact alarms
are granted, on which the package's receiver announces the new status.

**Revocation ends alarms.** "When the `SCHEDULE_EXACT_ALARM` permission is
revoked for your app, your app stops, and all future exact alarms are
canceled" ([Schedule alarms](https://developer.android.com/develop/background-work/services/alarms)).
Android has no call that lists an app's alarms, so the package's records
are what it knows: at any read while `canScheduleExactAlarms()` is false,
and at the grant broadcast (which follows a revocation, since a grant
needs one before it), the package removes the records of every alarm the
system held, so `alarms()` shows them gone (D4) and `state` reads
`prompt`. Granting again does not bring them back. Android's guidance is
to reschedule at the grant "based on its current state"; here the app
decides, and sets them again if it wants them: the person took away the
permission those alarms rang by, which may have been about them. A
paused countdown, which held no system alarm, stays.

**Ask.** `requestAlarmPermission()`: on Apple, `requestAuthorization()`;
on Android, the decisions in order: notifications' dialog while it is
`prompt` (with its history, LLP 1133.002 D8), then, while exact alarms
are not held, `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` with the app's
package, which opens the Settings page for the one switch, and a read when
the app returns. It answers the new status, `granted` or `denied` asking
nothing. Windows answers at once.

**`scheduleAlarm` asks.** AlarmKit asks at the first schedule by itself,
so `scheduleAlarm` is `"permission": "asks"` (LLP 1133.004 §7): while
`prompt` it runs the request first and then schedules, on every platform,
so an app whose Start button sets the timer needs no separate request.
While `denied` it refuses `NotAllowedError`. `cancelAlarm`, `pauseAlarm`
and `resumeAlarm` are `"none"`.

**Origins** (LLP 1133.002 D12):

| Origin | `prompt` | `granted` |
|---|---|---|
| the person, the app in the foreground | asks | schedules |
| a tool invocation | `NotAllowedError`, `person-required` | schedules (§15 question 3) |
| a wake | `NotAllowedError`, `person-required` | schedules |
| the agent | the substitute's ticket (D15) | the substitute |

An alarm is a statement the app makes for later, like a notification
post, and it starts no device now: a tool or a wake that may post a
notification may set an alarm. The request needs the foreground: a
Settings page or a system dialog shown to a person who is not looking is
refused (LLP 1133.002 D12).

**Explain and recover.** The app's own UI before the request, and
`openURL("app-settings:")` after a denial, which opens the app's settings
page on each platform; on Android the exact-alarm switch is reached by
the request itself.

## 7. Each platform's machinery

### D8 — iOS: AlarmKit, and the countdown's Live Activity

The Apple implementation is AlarmKit's `AlarmManager.shared`, weak-linked
(the framework is iOS and iPadOS 26.0 and later; Mac Catalyst is
unavailable in the SDK's interface, and the macOS, tvOS, watchOS and
visionOS SDKs carry no AlarmKit). Below iOS 26 the package answers
`available` false and refuses `NotSupportedError`.

| Tier 1 | AlarmKit |
|---|---|
| `at` | `.alarm(schedule: .fixed(date), …)` |
| `duration` | `.timer(duration:, …)` |
| `snooze` | the alert's `secondaryButton` with `secondaryButtonBehavior: .countdown` and `CountdownDuration(postAlert: snooze)`; no intent |
| `title` | `AlarmPresentation.Alert(title:)`, and the countdown's and paused presentations' titles |
| `cancelAlarm` | `cancel(id:)`, and `stop(id:)` while `alerting` if cancel does not end the ring (stage 1 measures) |
| `pauseAlarm`, `resumeAlarm` | `pause(id:)`, `resume(id:)` |

**No App Intents.** Stop is the system's, and a `.countdown` second button
needs no intent; so tier 1 needs none, and exact2's build, which
processes no App Intents metadata, is enough. Stage 1 confirms by
building with none.

**The Live Activity is required for a countdown.** A timer and a snooze
both present a countdown, and without a widget extension "the system may
unexpectedly dismiss alarms and fail to alert" (AlarmKit, above). LLP
1126's extension has one configuration, for the app's own
`ExactActivityAttributes`, made only when `app.json` asks. So:

1. The package declares a Live Activity configuration: its attributes
   type, `AlarmAttributes<ExactAlarmMetadata>`, and its view. Both live in
   the package's Apple sources, built into ExactCore, the framework the
   app and the extension share (LLP 1126), since the app schedules with
   the type and the extension draws it.
2. `widgets.mjs` generates the extension when the app uses such a package,
   whether or not `app.json` asks for widgets, and the widget bundle
   holds each configuration: the app's and the package's. This is a seam
   (D12 item 4), so a third party's package can do the same.
3. The host draws the view in the platform's look: the title, the time
   left (`Text(timerInterval:countsDown:)`), "Paused" with the time left
   when paused, and the alert's tint, on the Lock Screen and the Dynamic
   Island's compact, minimal and expanded regions. It shows no buttons:
   a button in a Live Activity runs a `LiveActivityIntent`, which tier 1
   avoids. An author-drawn countdown is LLP 1126's surface, when a
   consumer asks (§13).

The Live Activity is AlarmKit's, not the app's: AlarmKit starts, updates
and ends it from `AlarmPresentationState`, and the app's own Live
Activities (LLP 1126) are unaffected. WWDC25 230 notes the Live Activity is
not shown before first unlock after a restart; the alert still comes.

**Alarms from a wake.** Whether AlarmKit schedules from a process with no
scene (a wake, LLP 1133.017) is not documented; stage 1 measures it, and
if it refuses, a wake's `scheduleAlarm` fails with the platform's error
and the origins table keeps its row.

**The audio session.** An alarm's ring interrupts the app's audio session
as a call does; the host's one claim model (LLP 1133.009 D10) hears the
interruption from AlarmKit as from any app, and the metronome stops and
resumes by its existing interruption handling. Stage 1 measures it with
the metronome playing.

### D9 — Android: `setAlarmClock`, and code that runs with no session

The Android implementation sets each alarm with
[`setAlarmClock`](https://developer.android.com/reference/android/app/AlarmManager#setAlarmClock(android.app.AlarmManager.AlarmClockInfo,%20android.app.PendingIntent)),
whose alarms "will be allowed to trigger even if the system is in a
low-power idle (a.k.a. doze) mode" and "will be allowed to start a
foreground service even if the app is in the background". Both `at` and a
countdown's end are set this way. `setExactAndAllowWhileIdle` would keep a
timer out of the system's next-alarm display, but in idle "this duration
may be significantly longer, such as 15 minutes" between its dispatches
([`AlarmManager`](https://developer.android.com/reference/android/app/AlarmManager)),
which a timer cannot accept. Stage 2 records whether a timer shown as the
next alarm reads as a tell beside the Clock app's own timer.

**What runs at fire, with no session.** The package's own components, which
reach nothing of exact2's runtime:

| Component | Does |
|---|---|
| a receiver for the alarm's `PendingIntent` | starts the ringing service |
| a foreground service, type `systemExempted` (allowed to "apps holding `SCHEDULE_EXACT_ALARM` or `USE_EXACT_ALARM`", [service types](https://developer.android.com/develop/background-work/services/fgs/service-types)) | plays the alarm sound on the alarm stream until stopped or until a limit the Clock app also keeps (stage 2 names it), and posts the alarm's notification: `CATEGORY_ALARM`, the full-screen intent, Stop and Snooze actions |
| an activity shown over the keyguard (`showWhenLocked`, `turnScreenOn`) | the full-screen alert: the title, Stop, Snooze |
| a receiver for `BOOT_COMPLETED`, `LOCKED_BOOT_COMPLETED`, `TIME_SET`, `TIMEZONE_CHANGED` and `MY_PACKAGE_REPLACED` | sets the alarms again from the records: "all alarms are canceled when a device shuts down" ([Schedule alarms](https://developer.android.com/develop/background-work/services/alarms)); a countdown's end is recomputed from elapsed time, so a change of the clock does not move it |
| an ongoing notification while a countdown runs | the countdown outside the app (D3) |
| a receiver for `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` | the status, and the records after a revocation (D7) |

These broadcasts reach a manifest receiver despite Android 8's limits on
implicit broadcasts: `LOCKED_BOOT_COMPLETED`, `BOOT_COMPLETED`,
`TIME_SET` and `ACTION_TIMEZONE_CHANGED` are on the
[exceptions](https://developer.android.com/develop/background-work/background-tasks/broadcasts/broadcast-exceptions)
list. Snooze sets a new alarm `snooze` from now; Stop ends the service,
the notification and the record.

**The manifest fragment.** None of this exists in the reader's manifest,
and nothing lets a package add a component. LLP 1133.026 D19 item 3 (in
Review) lets an implementation's `exact.json` carry activities, aliases
and `<queries>`; this widens it to receivers with their intent filters,
services with `foregroundServiceType`, and the `directBootAware`,
`showWhenLocked` and `turnScreenOn` attributes, merged only when the app
uses the package (D12 item 3). Whichever of the two modules is built first
builds the fragment.

**Before first unlock.** An alarm clock must ring after a reboot before
the person unlocks, and Android names alarm clocks as the apps for which
[Direct Boot](https://developer.android.com/privacy-and-security/direct-boot)
exists. In that state only device-encrypted storage is readable, and the
app's credential-encrypted storage, where exact2 keeps everything else, is
not. So the package's receivers, service and activity are
`directBootAware`, and its records live in device-protected storage
(`createDeviceProtectedStorageContext()`). **Declared cost:** an alarm's
title and time are readable from the device before first unlock, as the
Clock app's are. Nothing else of the app is: no plan boots, no session
starts, the app's data is untouched. This is a change to what exact2's
Android app may do (the manifest's comment says it does not), confined to
this package's components (§15 question 5).

**Pause and resume.** `setAlarmClock` has no pause: pause cancels the
alarm and keeps `remaining` in the record; resume sets it at now plus
`remaining`.

**The Gradle graph.** Every class used is in the platform and AndroidX
Core, already in the locked graph (LLP 1133.008 D8); nothing is added.

### D10 — Windows: a scheduled toast in the alarm scenario

The Windows implementation schedules a toast with
`ToastNotifier.AddToSchedule` and a `ScheduledToastNotification` whose
`Tag` is the alarm's tag and whose XML says `scenario="alarm"`, through
WinRT's `Windows.UI.Notifications` (the `windows` crate; the host links
only `windows-sys`'s Win32 bindings today, so this is a new dependency of
the Windows build, measured in stage 3). A scheduled toast appears
"regardless of whether your app is running"
([Schedule an app notification](https://learn.microsoft.com/windows/apps/develop/notifications/app-notifications/app-notifications-scheduled)).
In the `alarm` scenario "notifications will be displayed pre-expanded and
stay on the user's screen till dismissed. Audio will loop by default and
will use alarm audio", and the toast must have at least one button
([`toast` element](https://learn.microsoft.com/uwp/schemas/tiles/toastschema/element-toast)):
the system's dismiss, and the system's snooze when `snooze` is set, which
need no app code. The system snoozes for its own interval unless the
toast offers a selection box of lengths
([App notification content](https://learn.microsoft.com/windows/apps/develop/notifications/app-notifications/app-notifications-content));
the implementation offers one whose only choice is `snooze`, and stage 3
checks that it reads as the platform's. `cancelAlarm` is `RemoveFromSchedule` on the entry with
the tag; pause removes it and keeps `remaining`; resume schedules again.

**Declared differences.** "Scheduled app notifications have a delivery
window of 5 minutes. If the computer is turned off during the scheduled
delivery time, and remains off for longer than 5 minutes, the
notification will be 'dropped'" (Microsoft, above): an alarm on a PC that
is off misses, where a phone's would ring. A scheduled toast does not
wake a sleeping PC (stage 3 measures it). No countdown shows outside the
app (`countdown` false), and an alarm that has rung leaves the list (D4).
Local toasts need no package identity (LLP 1115.004 D15); the toast
registers the host's app user model ID as notifications' stage 3 will.

## 8. Packaging and callers

### D11 — One package, an extension

`@exact/alarms` is a standard-library package (LLP 1133 D5): an interface
`exact.json` and the implementations `apple/` (Swift, iOS only, compiled
for every Apple target and answering absence elsewhere), `android/`
(Kotlin, with its manifest fragment), `windows/` (Rust in the Windows
host's build, the first package implementation there), and `web/`
(absence).
It is an extension, not exact2's vocabulary: no layout or rendering
depends on it, and an app that does not import it carries none of it
(LLP 1047.001). Tier 2's Android send lives in `@exact/alarms/android`.

### D12 — Seam additions

Each is general, and stage 0 proves the first two with LLP 1133.001 D8's
fixture module outside the tree:

1. **An app-scoped keyed list with a due time.** The substitute's `list`
   (LLP 1133.004 §7) gains `"scope": "app"`, kept where `set`'s app scope
   is (`declared.rs`'s `AppState`), so every session reads one list; and
   `"due"`: the option that is an instant (`at`) or a length from the
   call (`duration`), against the agent clock, at which an entry's
   `delivered` becomes true and a declared field (`state`) takes a
   declared value (`alerting`).
2. **Named choices on `tap @ref`.** A listed entry may declare choices,
   `tap @ref stop` and `tap @ref snooze`, each either retiring the entry or
   moving it (`due` again from a field, a new `state`), as a person's
   button would. `tap @ref` without a choice is refused by name for such
   an entry. Pause and resume update an entry's `state` and `remaining`
   in place, a third effect beside `list` and `unlist`.
3. **The Android manifest fragment, widened** to receivers, services and
   lock-screen activity attributes (D9).
4. **A Live Activity configuration a package declares** (D8), compiled
   into ExactCore and listed in the generated widget bundle; it amends LLP
   1126's rule that only `app.json` adds the extension.
5. **The grant row** `device.alarms` with its derivations (D7), in
   `runner/src/device.rs`.

Nothing else is new: answerless sends, `sync` sources, `"permission":
"asks"`, admission before dispatch for a bound implementation's sends
(LLP 1133.006 D8 item 3) and the per-origin refusals exist.

### D15 — The substitute

Under the agent no alarm is ever set and nothing rings, on any target: an
alarm touches the person's device, so the implementation cannot be its
own substitute (LLP 1133.006 D8 item 4). The declared substitute, in
`exact.json`, by D12's forms:

- **The status** is `prefer permission.alarms granted|denied|prompt` or
  `--permission alarms=…`; the default is `prompt` and `available` true,
  except on targets the module marks absent (web, macOS, Linux, tvOS,
  terminal), where the substitute answers as production does,
  `available` false and `NotSupportedError`, so a drive on the agent sees
  the target's absence.
- **A schedule** while `prompt` holds a `permission` ticket (`tap @t allow`
  sets `granted` and lists the alarm); while `granted` it lists an entry in
  `state.alarms`, app-scoped: `{tag, title, at, duration, snooze, state,
  remaining, ref, delivered}`, its `state` `scheduled` or `countdown`, its
  due time `at` or the agent clock plus `duration`.
- **Ringing** is the agent clock passing the due time (`clock +N`): the
  entry becomes `alerting`, `delivered: true`, and `alarms()` says so.
- **The person's buttons** are `tap @ref stop` (the entry goes) and `tap
  @ref snooze` (a countdown of `snooze` from the agent clock).
- **Pause, resume, cancel** change or remove the entry, with tier 1's
  refusals.

**Disclosure:** the entries' tags and titles, the app's own text.
**Lifetime:** until cancelled or stopped, or the host's app state ends.
**Production:** none of it.

### D16 — Cost

An app that does not import the package carries nothing. One that does
adds, on iOS, the package's Swift, a weak link to AlarmKit, and the widget
extension if the app had none: an extension bundle with ExactCore, which
is the largest item and is measured by LLP 1047's probe in stage 1
(Caltrain's extension is the comparison). On Android, the package's
Kotlin and its manifest entries. On Windows, the WinRT bindings (D10).
Nothing runs before first pixel: the
status reads at the first read of `alarmStatus()`, the records at the
first read of `alarms()`, and the boot receiver runs only at a boot.

## 10. The consumer: Metronome's practice timer

### D17 — A practice timer

A musician practising with a metronome sets a length of time and plays
until it ends, often with the phone locked and the metronome sounding in
the background. When the time is up they want to be told even if the
phone is silent, and they often want another round. No app in `apps/` or
`examples/` sets an alarm today, and this is the smallest real feature
that needs one: a notification would stay silent under Focus, and a wake
cannot ring.

**The feature:**

- A **Practice** row under the transport: 5, 10, 20 or 30 minutes and
  Start, shown only where `status.available` (iOS 26+, Android, Windows),
  so the row is absent on the web, macOS, Linux and older iPhones, which
  is the module's visible absence.
- Start runs `scheduleAlarm(tag="practice", title="Practice: N min",
  duration=N·60000, snooze=N·60000)`: the system's alert at the end says
  the title, with Stop and Repeat (another round of the same length).
  While `status.state` is `prompt`, Start asks first (D7); while `denied`
  the row shows a line and a Settings button (`openURL("app-settings:")`).
- While the alarm runs, the row shows the time left, from the `practice`
  entry's `at` and the session clock, in tabular digits (it changes in
  place), with Pause, Resume and Cancel. The Lock Screen shows the
  system's countdown (D8).
- When the alarm has rung and gone, the row returns to its chooser.
- Grant: `device.alarms practice-timer-purpose`, its text in
  `apps/metronome/strings`; `package.json` depends on `@exact/alarms`.

Metronome builds for iOS, macOS, the web and Linux. Android and Windows are
driven through the package's fixture app
(`packages/alarms/test/fixture`), in the reader APK as
`packages/background` was, and on the NucBox.

## 12. Notifications' timed posts on Android

LLP 1133.004 leaves to its stage 3 "the exact-alarm grant and inexact
fallback". Since the permission is app-wide (D7), this RFC recommends:

- `showTrigger` on Android sets `setAndAllowWhileIdle` (inexact, no grant),
  which may arrive late in Doze, as a reminder may;
- when the app holds exact alarms (it declares `device.alarms` and
  `canScheduleExactAlarms()` is true), it sets `setExactAndAllowWhileIdle`
  instead;
- notifications declares no exact-alarm permission and never requests one.

This keeps a reminder app free of a permission it would have to explain,
and keeps one explanation for the one switch. It is notifications' stage 3
amendment to rule, not this RFC's; it is here because the line between the
modules depends on it.

## 13. What stays out

Each until a consumer asks:

- Repeating alarms and local times that follow the time zone (AlarmKit's
  `.relative`): `rules/DEFERRED.md` refuses repeating schedules for
  notifications, and the same refusal holds here.
- `USE_EXACT_ALARM` and an alarm-clock app's grant line (§15 question 2).
- A sound of the app's own as tier 1 (reachable on Apple and Windows by
  tier 3).
- Buttons that run app code, App Intents in the build, and buttons in the
  Live Activity.
- An author-drawn countdown (LLP 1126's surfaces).
- A pre-alert countdown before a fixed alarm (tier 3 on Apple).
- Handing an alarm to the system Clock app (`AlarmClock` intents).
- Running the app's code when an alarm rings (D1); a wake beside it is the
  way.
- The web, macOS, Linux and tvOS cells, absent until their platforms offer
  an alarm.
