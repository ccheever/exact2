## Summary

`@exact/alarms` sets an alarm: an alert that comes at a set time, or when
a countdown ends, and keeps sounding through silent mode and Focus until
the person stops it. It is what a cooking timer, a practice timer or a
wake-up alarm needs, and what a notification is not:

```
use scheduleAlarm, cancelAlarm, pauseAlarm, resumeAlarm, alarms, alarmStatus,
  AlarmStatus, Alarm from "@exact/alarms"

resource status = alarmStatus() as shape AlarmStatus
resource running = alarms() as shape Alarm[]
action startPractice(minutes: number)
  scheduleAlarm(tag="practice", title=`Practice: ${minutes} min`,
    duration=minutes * 60000, snooze=minutes * 60000)
action stopPractice
  cancelAlarm(tag="practice")
```

```ts
import { scheduleAlarm } from "@exact/alarms";

await scheduleAlarm({ tag: `boil:${pot}`, title: "Eggs are done", duration: 9 * 60000 });
```

No web API sets an alarm, so tier 1 is a declared deviation (D2): the
shared words of AlarmKit and Android's alarm clock, under the web's
conventions for errors, tags and status. Where the module sits is the
decision this RFC exists for (D1):

- **A notification** (LLP 1133.004) is text the person reads when they
  choose, which silent mode and Focus may hold back; `showTrigger` times
  it.
- **A wake** (LLP 1133.017) runs the app's code at a time the system
  chooses, and shows nothing.
- **An alarm** is an alert at an exact time that silent mode and Focus do
  not stop, which rings until stopped, offers Stop and, if asked, Snooze or
  Repeat, and shows a countdown outside the app while it runs. **No app
  code runs when it fires**: the system presents it on iOS, the package's
  own receiver on Android. The app learns what happened at its next read
  of `alarms()`.

Android's exact-alarm permission is one per app, and this module owns it:
`device.alarms` derives `SCHEDULE_EXACT_ALARM` (D7), and nothing else uses
it. Notifications' timed posts stay inexact (§12).

| Target | Cell |
|---|---|
| iOS, iPadOS 26+ | AlarmKit; below 26 `available` false |
| Android | `AlarmManager.setAlarmClock`, with the package's receivers and ringing service |
| Windows | later: a scheduled toast in the `alarm` scenario is designed (D10); no package can carry a Windows implementation until LLP 1133.001's desktop builder exists |
| web, macOS, Linux, tvOS, terminal | absent: no platform API lets an app's alert override silence and Focus while the app is not running |
| Expose | later |

The consumer is Metronome's practice timer (D17). The stages are the
seams and the substitute (stage 0), iOS (1) and Android (2), each with its
drive (§14).

## 0. What is new here

1. **A third kind of timed thing,** with a line drawn against the two the
   library has (D1): an alarm runs no app code at fire, unlike a wake, and
   overrides the person's quiet, unlike a notification. Each platform
   keeps this line itself: AlarmKit is a framework separate from
   UserNotifications, and Apple says alarms "are not a replacement for
   other prominent notifications, like critical alerts or time-sensitive
   notifications" (WWDC25 230).
2. **The package owns Android's exact-alarm permission,** which is
   app-wide, and is its only user (D7, §12).
3. **A permission that requires another.** On Android an alarm needs
   notifications too, so alarms' state is composed with notifications'
   shared one, in production and under the agent (D7, D12 item 1).
4. **The host keeps AlarmKit's countdown Live Activity.** AlarmKit
   "expects a widget extension if an app supports a countdown
   presentation. Otherwise, the system may unexpectedly dismiss alarms and
   fail to alert" ([AlarmKit](https://developer.apple.com/documentation/alarmkit)).
   The host draws it, in a file it compiles into the app and the extension,
   as it keeps notifications' delegate (D8).
5. **Android code that runs with no session and before first unlock:**
   receivers and a service the package declares through a manifest
   fragment under an allow-list (LLP 1133.026 D19 item 3, widened), with
   its records in device-protected storage (D9).
6. **The substitute's keyed list grows** app scope, a due time on the
   agent clock and named choices on `tap @ref` (D12).

## 2. The line

### D1 — Alarms, notifications and wakes

An app that wants something to happen later has three modules, and the
choice between them is the person's experience, not the app's code:

| | Notification (LLP 1133.004) | Wake (LLP 1133.017) | Alarm (this) |
|---|---|---|---|
| What the person gets | a banner and a list entry | nothing | an alert that takes the screen or a banner, and sound until stopped |
| Silent mode and Focus | hold it back, as the person set them | — | do not stop it: AlarmKit's alert "overrides both a device's focus and silent mode" ([AlarmKit](https://developer.apple.com/documentation/alarmkit)); Android's Do Not Disturb lets alarms through unless the person turns that off (D3) |
| When | `showTrigger`, as the platform delivers it | when the system chooses | exactly: `setAlarmClock`'s alarms are ones whose delivery time "the system never adjusts", and it "leaves low-power modes if necessary to deliver" them ([Schedule alarms](https://developer.android.com/develop/background-work/services/alarms)) |
| App code at that time | none, until a click (`notificationclick`) | the handler, in a session with no view | none |
| What the person can do | open it, dismiss it | — | Stop; Snooze or Repeat when the app asked; Pause and Resume a countdown |
| A countdown outside the app | no | no | yes, while it runs |
| Permission | notifications' | none (`initial: granted`) | its own, with notifications' on Android (D7) |

**The test** an author applies: *would the person be surprised if silent
mode kept it quiet?* A wake-up alarm, a timer the person started, a
practice session's end: yes, an alarm. A reminder, a message, a
departure: no, a notification. Apple's guidance draws the same line:
alarms suit "countdowns with a specific interval, like a cooking timer,
or recurring alerts with a schedule, like a wake-up alarm" (WWDC25 230).

**Why no app code at fire.** An alarm must ring when the app is not
running, after a reboot, on a locked phone, and on iOS the app never gets
the chance: AlarmKit presents the alert itself. Running the app's code
then would make an alarm a wake with a sound, which the platform does not
allow on iOS and which on Android would put a plan boot between the
system's intent and the ring, before first unlock where the app's data is
unreadable (D9). So an alarm is complete when scheduled: its title, its
time or duration and its snooze are all it says, and the platform (or
the package on its behalf) does the rest. Alarms declare no module events.
An app that is running when its alarm rings sees `alarms()` change, as
any live source changes, and may act on it (D17 stops the metronome); an
app that is not running reads `alarms()` when it next runs.

**Not duplicated.** Alarms take nothing of background's (no alarm runs a
handler) and nothing of notifications' portable contract (no
`showNotification` option rings through Focus). The one overlap is a tier
2 word: LLP 1133.004 D3's `windows.scenario` offers `alarm`, the toast this
module's Windows cell uses (D10). An alarm toast is an alarm, so
notifications' stage 3 drops `alarm` from that word and keeps
`reminder`, `incomingCall` and `urgent` (§11). On Android the two modules
share one platform service, `AlarmManager`; D7 and §12 keep them from
sharing the exact-alarm permission.

## 3. Tier 1

### D2 — Shared words, a declared deviation

No web API sets an alarm: the Notification Triggers draft that gave
`showTrigger` its name was abandoned, and nothing in the web platform
rings through a device's silence. So tier 1 takes the shared words of
AlarmKit's [`AlarmManager`](https://developer.apple.com/documentation/alarmkit/alarmmanager)
and Android's alarm clock, under the web's conventions: a `tag` as the
Notifications API keys a notification, `DOMException` names for errors,
and a status fact with `available` and `state` as geolocation's
(LLP 1133.002 D6).

| Name | Kind | What it does |
|---|---|---|
| `scheduleAlarm(tag=, title=, at=, duration=, snooze=)` | send, answers nothing (LLP 1133.004 D5); asks while `prompt` (D7) | sets an alarm: at the instant `at` (epoch milliseconds), or after `duration` milliseconds as a countdown; exactly one of the two. `title` is what the alert says. `snooze`, milliseconds, adds a second button that starts a countdown of that length: Snooze for an alarm at a time, Repeat for a countdown. A tag that names an alarm replaces it |
| `cancelAlarm(tag=)` | send, answers nothing | ends the alarm whatever its state: scheduled, counting down, paused, or ringing (it stops the ring) |
| `pauseAlarm(tag=)`, `resumeAlarm(tag=)` | send, answers nothing | pause and resume a countdown; `InvalidStateError` on an alarm that is not counting down or paused |
| `alarms()` | live source, `sync` on every target with an implementation | the app's alarms (D4) |
| `alarmStatus()` | live source, `sync` | `{available, state}` and each platform's words (D5) |
| `requestAlarmPermission()` | request | asks for what `state` lacks and answers the new status (D7) |

```
shape Alarm
  tag: string
  title: string
  state: enum<scheduled|countdown|paused|alerting>
  at: option<number>         // when it rings: the instant, or a countdown's end
  duration: option<number>   // a countdown's length as set
  remaining: option<number>  // a paused countdown's time left
  snooze: option<number>

shape AlarmStatus
  available: bool
  state: enum<granted|denied|prompt|unknown>
  countdown: bool            // the platform shows a running countdown outside the app
  apple: option<AppleAlarmStatus>
  android: option<AndroidAlarmStatus>
```

**Why tags, not handles.** An alarm outlives the session, the process and
a reboot (D4), so it cannot be a handle the package context ends at
`destroy` (LLP 1133.009 D10); the app names it, as a notification's tag
names a notification. Tags are the app's: every session of the app reads
one list, as two documents of one web app read one badge (LLP 1133.004
§7). The implementation maps a tag to the platform's identifier (a UUID
on Apple, a request code on Android) in its own store.

**Replacing.** A second `scheduleAlarm` with a tag schedules the new alarm
and then cancels the old one, so a failed replacement leaves the old
alarm, not none.

**Refusals,** each a journal line in Contract and a rejected promise in
data code (LLP 1133.006 D8 item 2), and each enforced by the substitute
too (D14), since under the agent no implementation is called:

| Case | Error |
|---|---|
| no implementation on this target, or the OS is too old | `NotSupportedError` |
| `state` is `denied`; a tool invocation or a wake in any state (D7) | `NotAllowedError` |
| neither or both of `at` and `duration`; `at` not after now; a `duration` or `snooze` under one second; an empty `title` | `TypeError` |
| AlarmKit's `maximumLimitReached` ([`AlarmError`](https://developer.apple.com/documentation/alarmkit/alarmmanager/alarmerror)) | `QuotaExceededError` |
| pause or resume in the wrong state; a tag that names no alarm (cancel is not refused: cancelling nothing does nothing) | `InvalidStateError` |

`at` is an instant: AlarmKit's [`Alarm.Schedule.fixed`](https://developer.apple.com/documentation/alarmkit/alarm/schedule-swift.enum),
which does not move with a change of time zone. An alarm that keeps a
local time of day across a time-zone change (AlarmKit's `.relative`) is
one that repeats, and stays out with repeats (§13).

### D3 — Unsaid defaults are the platform's

What the author leaves unsaid comes out as the platform's own alarm, so a
person who knows the platform sees the Clock app's behaviour:

| What | Default | Source |
|---|---|---|
| The alert | iOS: the system's alarm alert, full screen on the Lock Screen, a banner while the phone is in use; Android: the sound, and the ringing service's notification with Stop and Snooze: a heads-up while the phone is in use, and on the Lock Screen when the person wakes the screen; the screen does not light by itself (no full-screen intent: D5) | WWDC25 230; [time-sensitive notifications](https://developer.android.com/develop/ui/views/notifications/time-sensitive) |
| Sound | the platform's alarm sound, repeating until stopped: AlarmKit's `.default`; Android's default alarm ringtone (`RingtoneManager.TYPE_ALARM`) on the alarm stream (`AudioAttributes.USAGE_ALARM`), played by the service while the notification itself is silent | AlarmKit's `AlertConfiguration.AlertSound`; [`AudioAttributes`](https://developer.android.com/reference/android/media/AudioAttributes#USAGE_ALARM) |
| Silence and Focus | iOS overrides both; Android lets the alarm through Do Not Disturb unless the person has turned off alarms there ([`NotificationManager.Policy`](https://developer.android.com/reference/android/app/NotificationManager.Policy)'s `PRIORITY_CATEGORY_ALARMS`, "Alarms are prioritized"), and the alarm stream is not the ringer, which silent mode mutes | as cited |
| Buttons | Stop, which the system provides on iOS (`stopButton` is deprecated in iOS 26.1); the second button only with `snooze`, its label the platform's word ("Snooze", or "Repeat" for a countdown, as Apple's sample names it) | [Scheduling an alarm with AlarmKit](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit) |
| A running countdown outside the app | iOS: a Live Activity on the Lock Screen and in the Dynamic Island (D8); Android: an ongoing notification whose chronometer counts down (`setUsesChronometer`, `setChronometerCountDown`), as the Clock app's timer shows | ActivityKit; [`Notification.Builder`](https://developer.android.com/reference/android/app/Notification.Builder#setChronometerCountDown(boolean)) |
| The next alarm in the system's UI | Android shows an alarm set by `setAlarmClock` as the next alarm ("the system will typically also use the information supplied here to tell the user about this upcoming alarm"); its show intent opens the app | [`setAlarmClock`](https://developer.android.com/reference/android/app/AlarmManager#setAlarmClock(android.app.AlarmManager.AlarmClockInfo,%20android.app.PendingIntent)) |
| Tint | the app's accent colour, as the system tints the alert's buttons | AlarmKit's `AlarmAttributes.tintColor`, which the app must give, so the package gives the accent |
| A paired Apple Watch | the system forwards the alert | WWDC25 230 |
| Vibration | the platform's, with the sound | as each alert above |

### D4 — What the app knows, and when

`alarms()` answers the app's alarms, each with its `state`, which comes
from the platform where the platform keeps it:

| State | iOS | Android |
|---|---|---|
| `scheduled` | `Alarm.State.scheduled` | the package's record, alarm set |
| `countdown` | `.countdown` | the record, a countdown running |
| `paused` | `.paused` | the record, no alarm set, `remaining` kept |
| `alerting` | `.alerting` | the record, the ringing service running |
| gone | not in `AlarmManager.alarms` | no record |

AlarmKit reads back an alarm's id, schedule, countdown durations and
state, not its title, and Apple's sample keeps "your alarms in your own
store" to compare ([Scheduling an alarm](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit)).
So each implementation keeps a record per tag (title, snooze, and the
platform's identifier) and answers the platform's state over it; an alarm
the platform no longer has is gone, and its record is removed at the read.

**The time, after the person has touched it.** A countdown's current end
and a paused countdown's time left change when the person snoozes or
pauses from the system's UI, which the app does not see happen. AlarmKit
keeps them in the alarm's Live Activity's content,
[`AlarmPresentationState`](https://developer.apple.com/documentation/alarmkit/alarmpresentationstate)'s
countdown and paused modes, which the app reads through ActivityKit
(`Activity<AlarmAttributes<…>>.activities`); the iOS implementation
answers `at` and `remaining` from there, and from its own record only for
an alarm it changed itself. Where neither is readable (before first
unlock, the Live Activity is not shown) they are none, and the `state` is
still the platform's. On Android the package makes every change itself, so
its record is current.

**When the list changes.** While the app runs: AlarmKit's `alarmUpdates`;
Android's receivers and service, which tell a running process. While it
does not run: nothing; the next session's first read is current. A person
who stops an alarm on the Lock Screen is seen by the app as an alarm gone.

**What outlives what.** An alarm outlives its session, the process and a
reboot: AlarmKit keeps it; on Android the package sets it again after a
boot (D9). Only `cancelAlarm`, the person, or the platform (Android's
revocation of exact alarms, D7) ends one. A package context's `destroy`
leaves alarms alone, and `release(name, args)` has nothing to release: a
send that answers nothing holds nothing.

## 4. Tier 2 and tier 3

### D5 — The platforms' words

| Platform | Word | Beats in tier 1 |
|---|---|---|
| Apple | `apple.tintColor` (a colour) on `scheduleAlarm` | the accent colour |
| Apple | status `apple.authorizationState`, `notDetermined|denied|authorized` ([`AuthorizationState`](https://developer.apple.com/documentation/alarmkit/alarmmanager/authorizationstate-swift.enum)) | — |
| Android | status `android.canScheduleExactAlarms` ([`canScheduleExactAlarms`](https://developer.android.com/reference/android/app/AlarmManager#canScheduleExactAlarms())), `android.notifications` (`granted|denied|prompt`, notifications' shared state) | — |

**No full-screen alert now.** Android's full-screen alert over the
keyguard needs `USE_FULL_SCREEN_INTENT`, which for apps targeting Android
14 is "limited to those that provide calling and alarms only"; Google Play
revokes it from others, and the person can turn it off
([Android 14 behaviour changes](https://developer.android.com/about/versions/14/behavior-changes-14),
"Secure full-screen Intent notifications"). An app whose timer is one
feature among many, as Metronome's is, should not declare it, and without
it the alarm still rings: the service's sound plays on the alarm stream
and its notification, a high-importance one on a public channel, carries
Stop. What the person loses is the screen lighting by itself on a locked
phone ([`setFullScreenIntent`](https://developer.android.com/reference/android/app/Notification.Builder#setFullScreenIntent(android.app.PendingIntent,%20boolean))):
they wake it to see Stop, as for any notification. This RFC accepts that
presentation for an app that is not an alarm clock. So the full-screen
activity, `canUseFullScreenIntent` and its Settings
page go with `USE_EXACT_ALARM` to an alarm-clock app's grant line, when
such a consumer asks (§13).

### D6 — Access hatches

| Platform | Object | When | The app may | The package keeps |
|---|---|---|---|---|
| Apple | `AlarmManager.AlarmConfiguration<ExactAlarmMetadata>` | before `schedule(id:configuration:)` | set a named `sound` (a file in the main bundle or `Library/Sounds`), a pre-alert countdown before a fixed alarm | the id, the schedule or duration, the attributes, the record; `stopIntent` and `secondaryIntent`, which name App Intents the build does not register (§1) |
| Android | none | — | — | — |

Android has no hatch because no app code runs at fire (D1): the
notification and the sound are made by the package's service in a process
with no session. A hatch there would need the app's Kotlin to be named in
the manifest and run before first unlock, which no consumer asks for.

## 5. The ceiling test

The common uses of each platform's alarms, and which tier reaches each:

| Use | AlarmKit | Android | Tier |
|---|---|---|---|
| A one-time alarm at a time | `.fixed` | `setAlarmClock` | 1 |
| A countdown timer | `.timer(duration:)` | `setAlarmClock` at the end | 1 |
| Snooze, Repeat | `.countdown` behaviour, `postAlert` | the package's Snooze | 1 |
| Pause, resume a countdown | `pause`, `resume` | cancel, keep `remaining`, set again | 1 |
| List, observe, cancel | `alarms`, `alarmUpdates`, `cancel`, `stop` | the record | 1 |
| Authorization and its state | `requestAuthorization`, `authorizationState` | `canScheduleExactAlarms`, the Settings page, notifications | 1 |
| A countdown outside the app | Live Activity | ongoing chronometer notification | 1 (D8, D9) |
| Tint | `tintColor` | — | 2 |
| Own sound | `.named` | — | 3 (Apple); out on Android |
| A pre-alert countdown before a fixed alarm | `CountdownDuration.preAlert` | — | 3 |
| Own buttons running app code | `stopIntent`, `secondaryIntent` | — | out: App Intents are not in the build (§13) |
| A full-screen alert over the keyguard | — | `USE_FULL_SCREEN_INTENT` | out: Play's alarm-app policy (D5, §13) |
| Repeating alarms (every weekday at 7) | `.relative(…, repeats: .weekly)` | set the next one on each ring | out (§13) |
| A local time of day that follows the time zone | `.relative` | RTC with `TIME_SET` | out (§13) |
| An author-drawn countdown | the app's own `ActivityConfiguration` view | its own notification | out: LLP 1126's surfaces, when a consumer asks |
| The system Clock app's alarm instead | — | `AlarmClock.ACTION_SET_ALARM`, `ACTION_SET_TIMER` ([common intents](https://developer.android.com/guide/components/intents-common#Clock)) | out: it hands the alarm to another app, which the app cannot then read or cancel |

Out, on purpose: repeats and local times (one DEFERRED refusal); buttons
that run app code and the full-screen alert, which wait on the build and
on an alarm-clock consumer; an author-drawn countdown (a surface, LLP
1126); and the Clock app's intents (not this module's kind of alarm).
Every other use is reached.

## 6. Permission

### D7 — LLP 1133.002 §4, for alarms

**Declare.** A new grant line, `device.alarms <strings key>`, the key the
explanation a platform shows:

| Platform | Derived |
|---|---|
| iOS | `NSAlarmKitUsageDescription` from the strings key: "If `NSAlarmKitUsageDescription` is missing or empty, apps can't schedule alarms" ([`NSAlarmKitUsageDescription`](https://developer.apple.com/documentation/bundleresources/information-property-list/nsalarmkitusagedescription)) |
| Android | `SCHEDULE_EXACT_ALARM`, `POST_NOTIFICATIONS`, `RECEIVE_BOOT_COMPLETED`, `WAKE_LOCK`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SYSTEM_EXEMPTED`, and the manifest fragment (D9) |
| web | nothing |

**`SCHEDULE_EXACT_ALARM`, not `USE_EXACT_ALARM`.** Android offers two.
`USE_EXACT_ALARM` is "granted automatically", "cannot be revoked by the
user" and is "subject to an upcoming Google Play policy"
([Schedule alarms](https://developer.android.com/develop/background-work/services/alarms)):
Play admits it only for an app whose core function is an alarm clock, a
timer or a calendar, through a declaration form
([Play policy](https://support.google.com/googleplay/android-developer/answer/13161072)).
`SCHEDULE_EXACT_ALARM` is the person's to give, is "not pre-granted to
most newly installed apps targeting Android 13 and higher" on Android 14
([denied by default](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms)),
and serves the "broader set of use cases". An app whose timer is one
feature among others, as Metronome's is, may not declare
`USE_EXACT_ALARM`. A second grant line for an alarm-clock app
(`device.alarm-clock`: `USE_EXACT_ALARM`, `USE_FULL_SCREEN_INTENT` and the
full-screen activity) waits for such a consumer (§15 question 2).

**The exact-alarm permission is app-wide, and this module is its only
user.** Android grants exact alarms to an app, not to a use; one module
must own the manifest line and the request, or two modules would ask for
one switch with two explanations. This module owns it because an alarm
cannot work without it. And no other module spends it: revoking it
"cancels all future exact alarms" of the app, so a reminder set exactly
under it would vanish when the person took the switch away because of an
alarm. Notifications' timed posts stay inexact (§12).

**Android's state is composed.** An alarm on Android needs exact alarms
and notifications both: the ringing service's notification carries Stop,
and on Android 13 and later an app without `POST_NOTIFICATIONS` may run a
foreground service whose notification is not shown in the drawer
([notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission)),
which would be a ring the person cannot stop. `POST_NOTIFICATIONS` is one
permission with one history whichever module asks (LLP 1133.008 D8 item
7). So the `alarms` permission declares that on Android it requires
`notifications` (D12 item 1): its effective state is the lesser of its own
and notifications' shared one. Alarms' interface declares the
`notifications` permission on Android itself (its status
`alarmStatus().android.notifications`), so it exists in an app that does
not use `@exact/notifications`; one that does reads the same shared state
(LLP 1133.026 D19 item 2), so one answer changes both.

**Read.** `alarmStatus()`:

| Platform state | `state` |
|---|---|
| iOS below 26, macOS, web, Linux, tvOS, Windows, terminal | `unknown`, `available` false |
| AlarmKit `notDetermined` | `prompt` |
| AlarmKit `authorized` | `granted` |
| AlarmKit `denied` | `denied` |
| Android: notifications permanently denied, or turned off for the app (`areNotificationsEnabled()` false), or the package's alarm channel blocked | `denied` |
| otherwise, Android: exact alarms not held, or notifications `prompt` (Android 13+, asked by its history, LLP 1133.002 D8) | `prompt` (exact alarms have no "don't ask again": the person can give them in Settings at any time) |
| otherwise, Android: exact alarms held and notifications granted | `granted` |
| Android 12 (no runtime notification permission; exact alarms pre-granted unless revoked) | by the same rows: `granted` when notifications are enabled and exact alarms held |
| Android 10 and 11 (an app whose `minimumOS` is `"10"`) | exact alarms need no permission: `granted` when notifications are enabled, `denied` when not |

The status is `sync` on every target: AlarmKit's `authorizationState` is
a property, and `canScheduleExactAlarms()` and `areNotificationsEnabled()`
answer at once. It changes by itself: the implementation follows
`authorizationUpdates` on Apple, reads again at the app's foreground on
Android, and Android sends
`ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` when exact alarms
are granted, on which the package's receiver announces the new status.

**Revocation ends alarms.** "When the `SCHEDULE_EXACT_ALARM` permission is
revoked for your app, your app stops, and all future exact alarms are
canceled" ([Schedule alarms](https://developer.android.com/develop/background-work/services/alarms)).
Android has no call that lists an app's alarms, so the package's records
are what it knows: at any read while `canScheduleExactAlarms()` is false,
and at the grant broadcast (which follows a revocation, since a grant
needs one before it), the package removes the records of every alarm the
system held, so `alarms()` shows them gone (D4) and `state` reads
`prompt`. Granting again does not bring them back. Android's guidance is
to reschedule at the grant "based on its current state"; here the app
decides, and sets them again if it wants them: the person took away the
permission those alarms rang by, which may have been about them. A
paused countdown, which held no system alarm, stays.

**A denial after scheduling.** Turning notifications off cancels no
system alarm and stops nothing. So the package keeps its invariant where
it acts: at fire, the receiver starts no sound unless the notification
that carries Stop can be shown (`areNotificationsEnabled()` and the alarm
channel not blocked); otherwise it removes the record and the alarm is
gone, as a revoked one is. A ring under way stops when its Stop goes: the
service listens for `ACTION_APP_BLOCK_STATE_CHANGED` and
`ACTION_NOTIFICATION_CHANNEL_BLOCK_STATE_CHANGED`, which Android sends to
the app itself ([`NotificationManager`](https://developer.android.com/reference/android/app/NotificationManager#ACTION_NOTIFICATION_CHANNEL_BLOCK_STATE_CHANGED)).
At any read while `state` is `denied`, the package cancels its system
alarms and removes their records; a paused countdown, which holds no
system alarm, stays, and `resumeAlarm` refuses `NotAllowedError` while
`denied`. Ringing without a way to stop it is worse than not ringing, and
the app sees `denied` and the alarm gone.

**Ask.** `requestAlarmPermission()`: on Apple, `requestAuthorization()`;
on Android, the required permission first and then its own: notifications'
dialog while notifications is `prompt` (with its history), then, while
exact alarms are not held, `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` with the
app's package, which opens the Settings page for the one switch, and a
read when the app returns. Each step is skipped when already decided, and
the request stops at the first that comes back `denied`. It answers the
new status; `granted` or `denied` asks nothing.

**`scheduleAlarm` asks.** AlarmKit asks at the first schedule by itself,
so `scheduleAlarm` is `"permission": "asks"` (LLP 1133.004 §7): while
`prompt` it runs the request first and then schedules, on every platform,
so an app whose Start button sets the timer needs no separate request.
While `denied` it refuses `NotAllowedError`. `resumeAlarm` is `"asks"`
too, since it sets a system alarm again; `cancelAlarm` and `pauseAlarm`
are `"none"`.

**Origins** (LLP 1133.002 D12):

| Origin | `scheduleAlarm`, `resumeAlarm` | `cancelAlarm`, `pauseAlarm` |
|---|---|---|
| the person, the app in the foreground | asks while `prompt`, acts while `granted` | yes |
| a tool invocation | `NotAllowedError`, `person-required`, in every state | yes |
| a wake | `NotAllowedError`, `person-required`, in every state | yes |
| the agent | the substitute (D14) | the substitute |

An alarm commits the device to take the screen and sound through the
person's silence later, and the person who hears it never sees the
journal line of the tool or wake that set it. So only the person sets
one or resumes one they paused (a resume commits the device again, as
LLP 1133.009 treats a recording's resume as a start); anything may end or
pause one. This is stricter than a notification
post, which a tool may make while granted, because a notification
respects the person's quiet and an alarm does not. A request needs the
foreground in any case (LLP 1133.002 D12).

**Explain and recover.** The app's own UI before the request, and
`openURL("app-settings:")` after a denial, which opens the app's settings
page on each platform; on Android the exact-alarm switch is reached by
the request itself.

## 7. Each platform's machinery

### D8 — iOS: AlarmKit, and the countdown's Live Activity

The Apple implementation is AlarmKit's `AlarmManager.shared`, weak-linked
(the framework is iOS and iPadOS 26.0 and later; Mac Catalyst is
unavailable in the SDK's interface, and the macOS, tvOS, watchOS and
visionOS SDKs carry no AlarmKit). Below iOS 26 the package answers
`available` false and refuses `NotSupportedError`.

| Tier 1 | AlarmKit |
|---|---|
| `at` | `.alarm(schedule: .fixed(date), …)` |
| `duration` | `.timer(duration:, …)` |
| `snooze` | the alert's `secondaryButton` with `secondaryButtonBehavior: .countdown` and `CountdownDuration(postAlert: snooze)`; no intent |
| `title` | `AlarmPresentation.Alert(title:)`, and the countdown's and paused presentations' titles |
| `cancelAlarm` | `cancel(id:)`, and `stop(id:)` while `alerting` if cancel does not end the ring (stage 1 measures) |
| `pauseAlarm`, `resumeAlarm` | `pause(id:)`, `resume(id:)` |

**No App Intents.** Stop is the system's, and a `.countdown` second button
needs no intent (both intent parameters default to `nil` in the SDK's
interface); so tier 1 needs none, and exact2's build, which processes no
App Intents metadata, is enough. Stage 1 confirms by building with none.

**The Live Activity is required for a countdown.** A timer and a snooze
both present a countdown, and without a widget extension "the system may
unexpectedly dismiss alarms and fail to alert" (AlarmKit, above). LLP
1126's extension has one configuration, for the app's own
`ExactActivityAttributes`, made only when `app.json` asks, and package
Swift compiles into the app's module, which the extension never loads.
And ExactCore, which the extension does load, reads the app group's cohort,
where LLP 1126 D8 keeps the app's state away from what a Lock Screen
render touches. So the countdown's configuration is the host's, as the
notification delegate is (LLP 1133.004 D7):

1. Two host files. `host/apple/widget/AlarmAttributes.swift` holds the
   metadata type `ExactAlarmMetadata`; `host/apple/widget/Alarm.swift`
   holds `ActivityConfiguration(for: AlarmAttributes<ExactAlarmMetadata>.self)`
   and its view. They import SwiftUI, ActivityKit and AlarmKit only. The
   build compiles the attributes file into the module of the package that
   asks for it, on iOS only, and both files into the widget extension, as
   Apple's practice compiles one attributes file into both targets;
   ActivityKit matches the two by type. Nothing goes into `ExactPackage`,
   the seam every package imports on every Apple target, so an app that
   binds any other package links no AlarmKit.
2. A package's Apple implementation declares that it needs the AlarmKit
   countdown (`"apple": {"activity": "alarmkit"}` in its `exact.json`).
   When an app binds such a package, the build sets
   `NSSupportsLiveActivities` and adds the configuration, behind
   `if #available(iOS 26, *)`, to the widget bundle (D12 item 3). An app
   that has widgets or `live_activities` gets it in its extension, where
   the alarm's view reads nothing of the cohort. An app that has neither
   gets an alarm-only extension, which `widgets.mjs` builds without
   ExactCore, the snapshot archive, the app group or the cohort: the two
   files, AlarmKit weak-linked, and no app state at all. A third party's
   alarms package declares the same and gets the same.
3. The view is drawn in the platform's look: the title, the time left
   (`Text(timerInterval:countsDown:)`), "Paused" with the time left when
   paused, and the tint, on the Lock Screen and the Dynamic Island's
   compact, minimal and expanded regions. It shows no buttons: a button in
   a Live Activity runs a `LiveActivityIntent`, which tier 1 avoids. An
   author-drawn countdown is LLP 1126's surface, when a consumer asks
   (§13).

The Live Activity is AlarmKit's, not the app's: AlarmKit starts, updates
and ends it from `AlarmPresentationState`, and the app's own Live
Activities (LLP 1126) are unaffected. WWDC25 230 notes the Live Activity is
not shown before first unlock after a restart; the alert still comes.
Metronome's minimum is iOS 17, so the extension's AlarmKit configuration
and the package's calls are behind availability checks, and below 26 the
extension holds only what `app.json` asked for.

**The audio session.** An alarm's ring interrupts the app's audio session
as a call does; the host's one claim model (LLP 1133.009 D10) hears the
interruption from AlarmKit as from any app. What the app does after it is
the app's: Metronome stops its transport when its practice alarm starts
ringing (D17), so the interruption's end resumes nothing. Stage 1
measures it with the metronome playing.

### D9 — Android: `setAlarmClock`, and code that runs with no session

The Android implementation sets each alarm with
[`setAlarmClock`](https://developer.android.com/reference/android/app/AlarmManager#setAlarmClock(android.app.AlarmManager.AlarmClockInfo,%20android.app.PendingIntent)),
whose alarms "will be allowed to trigger even if the system is in a
low-power idle (a.k.a. doze) mode" and "will be allowed to start a
foreground service even if the app is in the background". Both `at` and a
countdown's end are set this way. `setExactAndAllowWhileIdle` would keep a
timer out of the system's next-alarm display, but in idle "this duration
may be significantly longer, such as 15 minutes" between its dispatches
([`AlarmManager`](https://developer.android.com/reference/android/app/AlarmManager)),
which a timer cannot accept. Stage 2 records whether a timer shown as the
next alarm reads as a tell beside the Clock app's own timer.

**What runs at fire, with no session.** The package's own components,
which reach nothing of exact2's runtime and read only the package's
records:

| Component | Does |
|---|---|
| a receiver for the alarm's `PendingIntent` | holds a wake lock until the service is in the foreground; checks the Stop invariant (D7); starts the ringing service |
| a foreground service, type `systemExempted` on Android 14 and later (allowed to "apps holding `SCHEDULE_EXACT_ALARM` or `USE_EXACT_ALARM`", [service types](https://developer.android.com/develop/background-work/services/fgs/service-types)), started with no type below 14, where `setAlarmClock` is what allows the start | posts the alarm's notification (`CATEGORY_ALARM`, silent itself, Stop and Snooze actions) and plays the alarm sound on the alarm stream until stopped or until a silence limit of its own, since this service type has no system timeout; stage 2 sets the limit by the Clock app's |
| a receiver for `BOOT_COMPLETED`, `LOCKED_BOOT_COMPLETED`, `TIME_SET`, `TIMEZONE_CHANGED` and `MY_PACKAGE_REPLACED` | sets the alarms again from the records ("all alarms are canceled when a device shuts down", [Schedule alarms](https://developer.android.com/develop/background-work/services/alarms)), as below |
| a receiver for `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` | the status, and the records after a revocation (D7) |
| an ongoing notification while a countdown runs | the countdown outside the app (D3) |

These broadcasts reach a manifest receiver despite Android 8's limits on
implicit broadcasts: `LOCKED_BOOT_COMPLETED`, `BOOT_COMPLETED`,
`TIME_SET` and `ACTION_TIMEZONE_CHANGED` are on the
[exceptions](https://developer.android.com/develop/background-work/background-tasks/broadcasts/broadcast-exceptions)
list. Snooze sets a new alarm `snooze` from now; Stop ends the service,
the notification and the record.

**Time across clock changes and reboots.** Each record keeps the alarm's
wall-clock instant (`at`, or for a countdown the schedule time plus
`duration`) and, for a countdown, an anchor: the wall clock, the
`elapsedRealtime()` and the boot count (`Settings.Global.BOOT_COUNT`) when
the instant was last set. A countdown measures real time:

- On `TIME_SET`, if the boot count is the anchor's, the package moves the
  instant by the change in the wall clock less the change in
  `elapsedRealtime()` since the anchor, sets the alarm again and stores a
  new anchor. An `at` alarm keeps its instant.
- At fire, the receiver checks a countdown against its anchor in the same
  way before it rings: a forward jump of the wall clock delivers an RTC
  alarm early, and an early one is set again instead of ringing. A ring
  already under way whose corrected end is still ahead stops and is set
  again.
- At a boot, when `elapsedRealtime()` starts again from zero, the package
  sets each stored instant, stores a fresh anchor, and posts the countdown
  notifications again (they do not survive a restart); one that fell due
  while the phone was off rings at once, as a timer that ended during a
  restart should.
- `TIMEZONE_CHANGED` moves no instant (an epoch instant has no zone).

**The manifest fragment, and what it may hold.** None of these components
exists in the reader's manifest, and nothing lets a package add one. LLP
1133.026 D19 item 3 (in Review) lets an implementation's `exact.json`
carry activities, aliases and `<queries>`. This widens it, under an
allow-list the merger enforces, since every package gets the seam (LLP
1133.001 D8):

- receivers, `exported="false"`, whose intent filters name only actions
  on a list the seam keeps: today `BOOT_COMPLETED`,
  `LOCKED_BOOT_COMPLETED`, `TIME_SET`, `TIMEZONE_CHANGED`,
  `MY_PACKAGE_REPLACED` and
  `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` (the system's
  protected broadcasts still reach an unexported receiver), and none for
  the package's own alarm intent, which is explicit;
- services, `exported="false"`, whose `foregroundServiceType` is on the
  same list's types: today `systemExempted`;
- `directBootAware` on those components;
- activities and aliases as LLP 1133.026 D19 item 3 admits them, exported
  only where the platform requires it and then guarded by the permission
  the platform names (Health Connect's rationale activity and alias are
  such);
- no `<provider>`, no `<uses-permission>` (permissions come only from
  grants, D7), no `android:process`, no `Application` subclass.

A receiver can be woken by `LOCKED_BOOT_COMPLETED` in any app whose grants
derive `RECEIVE_BOOT_COMPLETED`, so the list is what bounds what a package
runs at boot; a package that needs another action amends the list in its
RFC. The merger sees only the XML: that these components read only the
package's device-protected records and start no session, plan or runtime
is the package's obligation, checked by its review and its drives.

It is merged only when the app uses the package (D12 item 4). The same
rules belong in LLP 1133.026 D19 item 3 while it is in Review; whichever
module is built first builds the fragment with them.

**Before first unlock.** An alarm must ring after a reboot before the
person unlocks, and Android names alarm clocks as the apps for which
[Direct Boot](https://developer.android.com/privacy-and-security/direct-boot)
exists. In that state only device-encrypted storage is readable, and the
app's credential-encrypted storage, where exact2 keeps everything else, is
not. So the package's receivers and service are `directBootAware`, and its
records live in device-protected storage
(`createDeviceProtectedStorageContext()`). **Declared cost:** an alarm's
title and time are readable from the device before first unlock, as the
Clock app's are. Nothing else of the app is: no plan boots, no session
starts, the app's data is untouched. This is a change to what exact2's
Android app may do (the manifest's comment says it does not), confined to
this package's components (§15 question 5).

**Pause and resume.** `setAlarmClock` has no pause: pause cancels the
alarm and keeps `remaining` in the record; resume sets it at now plus
`remaining`.

**The Gradle graph.** Every class used is in the platform and AndroidX
Core, already in the locked graph (LLP 1133.008 D8); nothing is added.

### D10 — Windows: designed, and later

**Later, with the reason.** Windows has an alarm a third-party app can
schedule (below), but no package can carry a Windows implementation: LLP
1133.001 D5 compiles module code only with builders exact2 has, and none
composes a package's Rust into the Windows host, which binds no package
today; LLP 1133.026 D21 marks its Windows cells `later` for the same
reason. This module does not special-case the host. The cell is built
when that builder exists and LLP 1133.001 D8's fixture module proves it,
with the toast registration notifications' stage 3 makes.

**The design, for then.** A `ScheduledToastNotification` through
`ToastNotifier.AddToSchedule`, whose XML says `scenario="alarm"`, appears
"regardless of whether your app is running"
([Schedule an app notification](https://learn.microsoft.com/windows/apps/develop/notifications/app-notifications/app-notifications-scheduled);
Microsoft's own example builds the content with the App SDK's
`AppNotificationBuilder` and schedules it with `ToastNotifier`, "used
together in the same app"). In the `alarm` scenario "notifications will be
displayed pre-expanded and stay on the user's screen till dismissed. Audio
will loop by default and will use alarm audio", with at least one button
([`toast` element](https://learn.microsoft.com/uwp/schemas/tiles/toastschema/element-toast)):
the system's dismiss, and its snooze when `snooze` is set. Its records map
a tag to the toast's `Tag`, which is short, through the store. A delivered
toast leaves the schedule and enters the notification history, so
`alerting` is read from the history and `cancelAlarm` removes the toast
from both. It falls short of D1 in three declared ways: "if the computer is
turned off during the scheduled delivery time, and remains off for longer
than 5 minutes, the notification will be 'dropped'"; a sleeping PC is not
woken for it; and whether the person's Do Not Disturb holds it back is
measured when the cell is built.
Tier 2 and 3 there: the toast's XML before `AddToSchedule` (an app's own
audio `src`, a selection box of snooze lengths). The WinRT bindings (the
`windows` crate; the host links only `windows-sys` today) are its cost.

## 8. Packaging and callers

### D11 — One package, an extension

`@exact/alarms` is a standard-library package (LLP 1133 D5): an interface
`exact.json` and the implementations `apple/` (Swift, iOS only, compiled
for every Apple target and answering absence elsewhere) and `android/`
(Kotlin, with its manifest fragment), and `web/` (absence). It is an
extension, not exact2's vocabulary: no layout or rendering depends on it,
and an app that does not import it carries none of it (LLP 1047.001). The
countdown's Live Activity is the host's, which the package asks for (D8).

### D12 — Seam additions

Each is general. Stage 0 proves items 1 and 2 with LLP 1133.001 D8's
fixture module outside the tree:

1. **A permission that requires another.** A declared permission may name,
   per target, permissions it requires (`"permission": {"name": "alarms",
   "requires": {"android": ["notifications"]}}`). Its effective state is
   the least of its own and each required one's (`denied`, then `prompt`,
   then `unknown`, then `granted`), a required permission's state is the
   one shared state its own module reads (LLP 1133.026 D19 item 2), and a
   request or an `asks` call asks each required permission still `prompt`
   in order, then its own, one ticket each under the agent, and stops at
   the first answered `denied`. An interface may declare a permission
   another interface also declares (LLP 1133.026 D19 item 2), so a
   required permission exists whether or not its usual module is bound.
   The runner checks one permission today (`declared.rs`, `permits.rs`'s
   `grantedBy` expresses implication, not this conjunction), so this is
   new.
2. **The keyed list, app-scoped, with a due time and named choices.** The
   substitute's `list` (LLP 1133.004 §7) gains `"scope": "app"`, kept where
   `set`'s app scope is (`declared.rs`'s `AppState`), so every session
   reads one list (lists are per session today); and `"due"`, from an
   instant option (`at`) or a length from the call (`duration`), stored in
   the entry as an absolute instant on the agent clock. The first session
   whose agent clock passes it writes the transition into the shared entry
   once (a declared field, `state`, to a declared value, `alerting`;
   `delivered` true) and announces the listed source to every session, so
   `alarms()` changes as `state` does. A listed entry may declare choices,
   `tap @ref stop` (retire) and `tap @ref snooze` (a new due time from a
   field, a new `state`); `tap @ref` without a choice is refused by name
   for such an entry (it always retires today). Pause and resume update an
   entry's `state` and `remaining` in place, a write effect beside `list`
   and `unlist`.
3. **A host-kept Live Activity a package asks for** (D8): the declaration
   `"apple": {"activity": "alarmkit"}`, the extension generated for it,
   and `NSSupportsLiveActivities` set for it. It amends LLP 1126's rule
   that only `app.json` adds the extension.
4. **The Android manifest fragment, widened under an allow-list** (D9).
5. **The grant row** `device.alarms` with its derivations (D7), in
   `runner/src/device.rs`.

Nothing else is new: answerless sends, `sync` sources, `"permission":
"asks"`, admission before dispatch for a bound implementation's sends
(LLP 1133.006 D8 item 3) and the per-origin refusals exist.

### D15 — The substitute

Under the agent no alarm is ever set and nothing rings, on any target: an
alarm touches the person's device, so the implementation cannot be its
own substitute (LLP 1133.006 D8 item 4). The declared substitute, in
`exact.json`, by D12's forms:

- **The status** is `prefer permission.alarms granted|denied|prompt` or
  `--permission alarms=…`, composed on Android with `notifications`'
  (D12 item 1): `prefer permission.notifications denied` makes alarms
  `denied` there, and a schedule while either is `prompt` holds one ticket
  per permission, notifications' first. The default is `prompt` and
  `available` true, except on targets the module marks absent (web,
  macOS, Linux, tvOS, Windows, terminal), where the substitute answers as
  production does, `available` false and `NotSupportedError`.
- **A schedule** passes D2's `TypeError` checks and D7's origins, then
  while `granted` lists an entry in `state.alarms`, app-scoped: `{tag,
  title, at, duration, snooze, state, remaining, ref, delivered}`, its
  `state` `scheduled` or `countdown`, its due instant `at` or the agent
  clock plus `duration`.
- **Ringing** is an agent clock passing the due instant (`clock +N`): the
  entry becomes `alerting` and `delivered: true`, and `alarms()` says so in
  every session.
- **The person's buttons** are `tap @ref stop` (the entry goes) and `tap
  @ref snooze` (a countdown of `snooze` from the agent clock).
- **Pause, resume, cancel** change or remove the entry, with tier 1's
  refusals.

**Disclosure:** the entries' tags and titles, the app's own text.
**Lifetime:** until cancelled or stopped, or the host's app state ends.
**Production:** none of it.

### D16 — Cost

An app that does not import the package carries nothing. One that does
adds, on iOS, the package's Swift, a weak link to AlarmKit, and the widget
extension if the app had none: an extension bundle with the host's alarm
file. The extension is the largest item and is measured by LLP 1047's
probe in stage 1, with and without an extension already present
(Caltrain's is the comparison). On Android, the package's Kotlin and its
manifest entries. Nothing runs before first pixel: the status reads at
the first read of `alarmStatus()`, the records at the first read of
`alarms()`, and the boot receiver runs only at a boot.

## 10. The consumer: Metronome's practice timer

### D17 — A practice timer

A musician practising with a metronome sets a length of time and plays
until it ends, often with the phone locked and the metronome sounding in
the background. When the time is up they want to be told even if the
phone is silent, and they often want another round. No app in `apps/` or
`examples/` sets an alarm today, and this is the smallest real feature
that needs one: a notification would stay silent under Focus, and a wake
cannot ring.

**The feature:**

- A **Practice** row under the transport: 5, 10, 20 or 30 minutes and
  Start, shown only where `status.available` (iOS 26+), so the row is
  absent on the web, macOS, Linux and older iPhones, which is the
  module's visible absence.
- Start runs `scheduleAlarm(tag="practice", title="Practice: N min",
  duration=N·60000, snooze=N·60000)`: the system's alert at the end says
  the title, with Stop and Repeat (another round of the same length).
  While `status.state` is `prompt`, Start asks first (D7); while `denied`
  the row shows a line and a Settings button (`openURL("app-settings:")`).
- While the alarm runs, the row shows the time left, from the `practice`
  entry's `at` and the session clock, in tabular digits (it changes in
  place), with Pause, Resume and Cancel. The Lock Screen and the Dynamic
  Island show the system's countdown (D8).
- When the `practice` entry becomes `alerting` while Metronome runs (it
  does, in the background, while it plays), its action stops the
  transport, so the alarm is heard alone and nothing resumes after it.
  When the alarm has gone, the row returns to its chooser.
- Grant: `device.alarms practice-timer-purpose`, its text in
  `apps/metronome/strings`; `package.json` depends on `@exact/alarms`.

**Android's acceptance drive is the fixture.** Metronome builds for iOS,
macOS, the web and Linux; it has no Android host, and porting its audio
engine is not this module's work. LLP 1133 D9 item 11 makes the consumer
the acceptance drive on each target the module builds, so on Android
this RFC asks for a waiver: the package's fixture app
(`packages/alarms/test/fixture`), in the reader APK as `packages/background`
was, drives the same feature (a practice-length timer with Repeat, Pause
and Cancel) (§15 question 6).

## 12. Notifications' timed posts on Android

LLP 1133.004 leaves to its stage 3 "the exact-alarm grant and inexact
fallback". This RFC recommends that `showTrigger` on Android always sets
`setAndAllowWhileIdle` (inexact, no grant), which may arrive late in Doze,
as a reminder may, and that notifications declares no exact-alarm
permission and never uses one. Spending alarms' permission on reminders
would tie them to a switch the person may revoke because of an alarm, and
revocation cancels every exact alarm of the app (D7); an inexact alarm
survives it. A reminder that must be exact, and ring through silence, is
an alarm. It is notifications' stage 3 amendment to rule; it is here
because the line between the modules depends on it.

## 13. What stays out

Each until a consumer asks:

- Repeating alarms and local times that follow the time zone (AlarmKit's
  `.relative`): `rules/DEFERRED.md` refuses repeating schedules for
  notifications, and the same refusal holds here.
- An alarm-clock app's grant line: `USE_EXACT_ALARM`,
  `USE_FULL_SCREEN_INTENT` and the full-screen activity over the keyguard
  (§15 question 2).
- A sound of the app's own as tier 1 (reachable on Apple by tier 3).
- Buttons that run app code, App Intents in the build, and buttons in the
  Live Activity.
- An author-drawn countdown (LLP 1126's surfaces).
- Handing an alarm to the system Clock app (`AlarmClock` intents).
- Running the app's code when an alarm rings (D1).
- Setting or resuming an alarm from a tool invocation or a wake (D7).
- The Windows cell, until the desktop builder (D10); the web, macOS, Linux
  and tvOS cells, absent until their platforms offer an alarm.
