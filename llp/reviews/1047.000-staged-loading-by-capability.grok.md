## Review (verbatim)

I'll review LLP 1047.000 for direction only: read the binding rules and the document, then check the claims that would change what gets built.**Verdict:** RIGHT WITH CHANGES

**Overall assessment:** The order is right: unlink what RealWorld never calls, then stage what only some pages or an agent need, then look at the core. Served HTML really does move the wasm off the first paint. The SSR bench shows content at about 204 ms and a runtime that is up around 1.9 s, and the declined leads (errors-as-codes at 5–8 KB, a DOM-only kernel at 10–15 KB, compiling the runner once) are too small or already closed to chase. Capability staging cannot reach React SSR’s roughly 110 KB, and the document says so. Two things should change before the loader is written. The cut has to be a real seam, not the name-attribution map. And the later choice about the core should aim at the cold residue inside the roughly 205 KB, not at another diet of the hot runner.

**Strengths:**

- §1 and the parent’s §10 match the bench. Paint and link taps no longer wait on the wasm. What still waits is a press the capture script cannot answer (a signed-in ♥, a form). The 5 ms/KB figure on the 1.6 Mbps profile is the right unit for payload time.
- §2’s breakdown and §5’s split table agree with each other. The core at 212 KB brotli, secondaries of 13 / 20 / 6.6 / 8.9 KB, and about 10 KB of overhead (260.8 versus 250.1) is a real split, not a recompression of the attribution rows. Unlink-versus-stage is the right rule, including “nothing under a few KB is its own stage.”
- §4–§5 correctly drop a profile-guided split as the thing to ship. A per-build profile, a synchronous fallback, and coverage that decays are the wrong costs for this repo. Shared memory is the right mechanism for Markdown and inspection, because both read the live heap. That is the parent’s §8 exception, and it fits D1’s loaded tier. Separate instances stay right for the editor, text flow, and the GPU module.
- Staging inspection keeps one artifact for smokes and for users (parent §9 Q3) and simply delivers those 6.6 KB later. §6’s “or neither” is an honest exit.

**Concerns:**

- **HIGH — The capability map is an attribution heuristic, not a seam.** `metrics.mjs` assigns a function to the first `exact_*` module in its demangled name, and §2 says that overcounts by about 10%. §5 then feeds that map to `wasm-split --multi-split`. Any primary-to-secondary call traps until that module is instantiated (§5, step 2). A name cut will leave ordinary commit paths crossing the boundary, including monomorphized helpers the core calls on pages that never render Markdown. The runner-level “are we ready?” check only covers call sites that go through it. **Resolve:** on the split already measured, list every primary-to-secondary edge. Stage a capability only when those edges are the D4 table the entry fills. A boot-and-commit smoke with the secondary not loaded must pass. If the edge list is large, stop and deepen the seam. Tree shaking does not need the loader.

- **MEDIUM — Markdown’s win depends on a per-route use-set that does not exist yet.** `uses()` (LLP 1047 D2) is app-wide, and a computed binding counts as a use, so RealWorld’s plan uses Markdown on every page. Open question 3 says this; step 3 still says the render server already knows. Without a route-reachable set, every page preloads Markdown. On this bench’s HTTP/1.1 origin, that second wasm shares the 1.6 Mbps pipe and can add a round trip. Parent §10 already saw six requests saturate the origin and delay a tap. Payload arithmetic (13 KB is about 65 ms) understates that. App-wide preload can erase Markdown’s latency win and can make an article slower. **Resolve:** inspection does not need per-route sets; Markdown does. Before staging Markdown, confirm the server can omit it on `/` and that an article’s time-to-runtime does not regress when both modules are preloaded.

- **MEDIUM — “Decide the core” aims at the hot 50 KB.** After steps 1–4 the first download is still about 205 KB: runner core about 50, std about 39, kernel about 30, data about 30, web host about 27, plan loading about 20, plus the TypeScript bridge. §4 already measured the parent’s main runner lead (one `Runner<exact_js_web::Module>` instantiation; the per-type duplicate is gone). The profile’s extra roughly 50 KB (primary about 150–160 KB versus this core) is cold code spread through those buckets — validation, debug and error data, tables, paths nothing on the boot-adoption-press trace calls. Another runner diet will not produce it. **Resolve:** add a one-time diagnostic profile of the post-shake core. Name the cold families. Cut any family that has a seam, with the same loader. If the hot set is already near 180 KB, take the “neither” branch. The floor of this interpreter is the parent’s §8 limit, and it will not meet React’s about 110 KB.

- **LOW — A legitimate race should wait; a missing gate should trap.** Client navigation to an article while Markdown is in flight is the case open question 2 describes (wait with the data). Treating every early call as a bug traps a user. D6’s named refusal is the right behavior when the module was never going to be loaded.

**Suggestions:**

- Land tree shaking first and alone. It removes about 29 KB from the only request, with no new load protocol. Keep the list-engine seam coordinated with LLP 1050, and unlink the content region and text-flow shaper even if that seam slips.
- Build the loader for inspection first. One export (`exact_agent` from `glue.js`), no page preload, and the smoked bytes stay the shipped bytes.
- Leave the Markdown editor and text flow as separate artifacts (open question 1) until inspection has shipped. Merging them is a std-sharing win, and it is a second design.
- JSPI does not dominate. It removes the synchronous fallback, costs a suspendable runtime and uneven browser support, and does not shrink the download. Explicit load plus a gate matches D6.
- Pin the `wasm-split` that produced the table, and keep an unsplit production output if the tool fails. Dev stays one module (D7); only the production smoke proves the gate.

**Recommended next step:** Tree-shake, and before writing the loader, dump the cross-module edges from the split in §5. If Markdown and inspection are each a handful of gated edges, implement inspection, then Markdown with a real per-route preload. Measure a signed-in ♥ or a form at `load`, on `/` and on an article, on the mobile profile. Then take one diagnostic profile of that core and choose: seam the cold families, profile-split the core and accept its costs, or stop.
