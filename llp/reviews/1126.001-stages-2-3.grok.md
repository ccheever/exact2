# Review: LLP 1126.001 (stages 2 and 3)

**Family:** Grok 4.7 (xAI) · **Provider/runtime:** grok -m grok-4.7 --reasoning-effort xhigh --permission-mode plan --no-subagents · **Date:** 2026-10-18 · **Redacted:** no · **Method:** blind (neither reviewer saw the other's review in round 1; round 2 read both round-1 reviews), read-only checkout of origin/main 0cdfb4774 plus the draft; brief: high-level, directional and foundational findings only

## Round 1 (r1) — NOT READY

## Blockers

BLOCKER - Q1, WP11 - The second writer is specified against a store that does not have one committed file, and against a session that cannot write. `FileStore` is one file per key, each write a fresh temporary renamed into place (`vendor/ibex/crates/ibex2/src/kv.rs`). Kept answers are flushed by a process-private thread (`host/apple/src/store.rs`). The generation counter is a separate read-add-rename of `widget-store-generation` with no lock. Two writers can both read N and both publish N+1, so a refresh can capture the counter, miss the other process's key, and still see the same counter. That breaks the stage 1 rule this spec says it keeps: a timeline must not cross a store write. `widget_changed` returns immediately unless `EXACT_WIDGET_WRITER` is set, and only the app bundle sets it (`ExactWidgetKinds` in `build.mjs`; `WidgetContainer.configure`). The extension's `HeadlessSession` boots through `boot_entry`, which never endows I/O (`host/apple/src/abi/snapshot.rs`). `snapshot_timeline` errors if the refresh writes anything (`runner/src/runner/snapshot.rs`). Pressing in that session cannot commit, bump the counter, or post the ping, so the two-process acceptance cannot pass. A journal the app applies later is the wrong alternative: the reload would show a state the refresh does not read back. Do not copy the update store's lifetime `owner.lock`. Add a lock file in the app-group container, held by the app's existing publish path and by the intent, from the commit's first key write through `flush_kept` and the counter increment. Run the intent on a session that endows the group store and persists. Let the extension publish the counter.

BLOCKER - §1, WP8, WP10 - Placements cannot be told apart by `snapshot_viewport`, which §1 says is the only fact a render reads. Stage 0 measured expanded leading and trailing at the same width, 165 pt on a 402 pt phone (`llp/1126.000` §1.1). D9 makes the placements named slots of one component, so the slot is the identity. WP8 instead renders each placement from the region's size alone, and WP10 boots a headless session per region. Leading and trailing draw the same tree. One render of all four slots has only one viewport, so it cannot measure each slot at its own width. Separate sessions also multiply the footprint Q4 compares with the half-ceiling. Keep D9's slots. Have the driver measure each slot at the width the system gives that region and take `fit_content_height`. Do not add a placement value the author switches on, and do not freeze §1.1's widths into the gallery.

BLOCKER - WP9 - The three activity sends are refused at bake on the web, Android, Linux, and the terminal. D9 says they are present where ActivityKit exists and absent elsewhere. A send this repository cannot perform on a host is baked into the one plan and refused at runtime (a share of an element picture on the web). There is no bake-time "not on this host" edit. Caltrain is the fixture the other hosts' checks drive. A bake edit on those sends makes that app fail to build there. Bake the sends in the app plan. The Apple arm performs them. Every other host refuses the arm at runtime.

BLOCKER - WP11 - The intent is specified to run in the extension whenever the app is open, which is not how App Intents choose a process. The deployment floor is iOS 17 (`deploymentTargets`). An intent linked only into the extension always runs there. An intent also linked into the app runs in the app when the app is running and not suspended, and in the extension otherwise. D8 puts the app and the extension on one shared framework, and WP11 generates `ExactIntent` once. Placed in that framework, a tap while Caltrain is open writes in the app. The ping path is not taken, and the "app running" acceptance does not show a second writer. On iOS 18 and later `openAppWhenRun` is deprecated and `supportedModes` decides. A foreground mode launches the app, so the "app not running" acceptance and the 900 ms extension budget are both the wrong test. Compile the intent only into the extension, set `openAppWhenRun` false on iOS 17 and `supportedModes` to background on iOS 18 and later, and record the performing process in the acceptance.

## Major

MAJOR - WP11, `WidgetContainer` - The spec says the Darwin observer re-asks the app's resources. `storeObserver` only calls `reloadTimelines` through `WidgetCenter`. Nothing there calls `data_ready`. While the app is open, question 6 requires the window to re-read the store at once. As written, the "app running" acceptance can reload the widget and leave the window stale. On that ping, if the counter moved, re-ask the running session and reload the affected kind.

MAJOR - WP9, WP10 - Push-to-start and remote notifications are "refused" by adding no `NSExtension`. Neither feature is an `NSExtension`. Push-to-start is `Activity.pushToStartTokenUpdates`. Remote notifications are `registerForRemoteNotifications` and the `remote-notification` background mode. They do share the `aps-environment` entitlement, which this package correctly adds for update tokens. Live Activities themselves need `NSSupportsLiveActivities` on the app, which is also not an extension. The acceptance never checks that start stays a local send or that the app does not register for remote notifications. Keep the contract refusals (no `app.json` key, no push-to-start token, start remains a send). State the real controls, include `NSSupportsLiveActivities`, and assert the refused paths are absent.

MAJOR - WP8, WP11 - The two packages that start together disagree about handlers, and WP11 only lifts half of the profile. WP8 is done when any handler fails with stage 1's edit. WP11 admits a `button` or `toggle` handler in that same profile. The profile also rejects every mutation, sequence, and persisted write, and the edit says to move them into the refresh function (`snapshot-effect`). An activity has no refresh. A favourite toggle's commit is a persisted write, so admitting the attribute still leaves the handler unable to change state. Split those acceptances. Admit a commit from a button or toggle handler without a refresh function. Leave navigation and input refused.

MAJOR - WP9 - The simulator acceptance does not show the update send. The drive is `tap start-activity`, `clock +60000`, `tap end-activity`. A `time` or `progress` placement ticks with no `Activity.update`. Start and end can pass while the update send never runs. Drive an explicit update and assert the Lock Screen shows the new state, not only a ticking clock.

MAJOR - WP10 - Interview's job is an answer being written, advanced by push, and the acceptance is one push while the app is suspended. ActivityKit budgets updates. A stream of token pushes is throttled unless `NSSupportsLiveActivitiesFrequentUpdates` is set, and the person can turn frequent updates off. One accepted push does not show the activity keeps advancing, which is the failure question 5 exists to avoid. The payload limit is 4 KB for the whole APNs body. Name the budget and the entitlement, and accept a short series of pushes against a suspended app, including the over-budget and over-4 KB results.

MAJOR - §4, WP15 - The watch complication depends on WP10 "for the driver's region sizing." Accessory families already have a content size through `snapshot_viewport`. Island region sizing does not apply. D10 and track W say complications come with the stage 1 driver, and question 3 asks for full Apple platform support for launch. This dependency holds the watch behind Live Activities for no reason. Start WP15 from stage 1, beside WP14.

MAJOR - Q5, WP14 - Refusing the Mac bake when an entry has only accessory families is the wrong recommendation. A complication is a widget row with accessory families, and one entry is realized on iOS, Mac, and watchOS. That refusal makes a watch complication fail the Mac build of the app. An empty WidgetKit bundle is a tell. Not building the extension is the fix. On the Mac, drop families the Mac cannot show, and build no extension if none remain. Do not fail the app bake.

MAJOR - WP14 - The Mac package generalises the iOS group id `group.${id}` (`widgetGroup`) onto `build.mjs --run`. Since macOS 15 a development build may use a `group.` container only when an embedded profile authorizes it. A team-prefixed id needs no profile, and it is not valid on iOS or as a Keychain access group. `containerURL(forSecurityApplicationGroupIdentifier:)` returns a URL on the Mac even when the group is unauthorized, so a nil check does not catch it. The reload acceptance then fails or prompts. Use a Mac-only container id. Keep the Keychain group as the application identifier. Do not reuse `widgetGroup` for both.

MAJOR - WP14, WP15, Q3 - Stage 3 never names Interview's job, which question 7 requires for every stage. WP14's acceptance is Caltrain only, so a Mac extension that never runs the TypeScript refresh passes. Q3's "refuse TypeScript on the watch" matches D10, but then the watch acceptance is a Rust fixture on a simulator. Stage 1 already recorded that the simulator does not enforce an extension memory limit, and the watch probe was an app at about 34 MiB, not a widget extension. A simulator face does not show the complication surviving jetsam, or Interview's account data. Accept Interview's Mac widget with its TypeScript refresh. For the watch, keep the Hermes refusal, and add a device ceiling before calling the complication done. Do not treat Caltrain-on-simulator as the stage.

## Round 2 (r2) — NOT READY

BLOCKER - §5 Q1 / WP11 - The recommendation runs a widget intent in the app and keeps the app as the only writer, which reverses accepted D7 and D8, and the question never says so. D7 says the intent runs the handler in the extension, commits, and reloads. D8 says an intent commits in the extension while the app may be running, and that the store's writes stay transactional across processes. Option A is written as continuity with stage 1: the counter, `flush_kept`'s ordering, and `EXACT_WIDGET_WRITER` "hold unchanged." Option B, the cross-process transaction, is the design those two decisions already require. A "rec ok" would amend the RFC. The cost statement is also short of the acceptance it shares. Stage 1's publish path is last-write-wins per key, with the counter advanced on a process-private thread. Two in-flight read-modify-writes, such as two upvotes, can still drop one update inside that single process, so A does not meet "none lost" for free. On the Mac, whose widget floor is macOS 14 and where `LiveActivityIntent` does not exist, in-place intents wait for macOS 26 or become links that open the app, so D7's "act without opening" is given up across the current Mac range. If the cold background launch misses the 900 ms rule or D8's one-second kill line, the question names no successor. WP11's wait on §1.4's extension ceiling is the extension-process budget. It matters because this is the architecture of interactive widgets. Charlie's usual acceptance of a recommendation would build a different one than the accepted RFC. The fix is to put D7 and D8 in the question. Make B the recommendation, with the transaction text already there: the lock held from the snapshot read through `flush_kept` and the counter, one rename of the write set and its revision, the group store endowed, and the per-file KV restructured. Make A an explicit amendment of those two sentences, and state what accepting it commits to, including Mac links until macOS 26 and the successor, B or a `widgetURL`, when a cold app launch misses D8's one-second line. Keep the shared acceptance list.

MAJOR - §5 Q3 / WP17 - The watch question does not state its options, costs, and acceptance fairly. It bundles one gate: Hermes for the three watchOS targets without JIT, `app.hbc` booted in a watch extension, a measurement on a watch, and a new Interview sign-in route in the placeholder window, priced as one lane week, with a reduced scope only if "the gate fails." Failure has no line. D8's half-ceiling and one-second rule are the program's kill line, and Q4 uses the half-ceiling. Q3 uses neither. The week prices a watch Hermes port and a new account flow as one probe. "WatchConnectivity needs stage 4's app" is stronger than D10. Stage 4 is the live driver and a later watch-app RFC. The stage-3 watch app that WP17 already builds can carry a session from the phone. An authored sign-in route needs text entry and navigation, which D10 places on that same live driver, so the recommended path depends on the stage it presents itself as avoiding. Question 7 names Interview for every stage. The reduced scope amends that, and it is only a consequence of an undefined failure, not a choice he can make up front. It matters because this decides whether complications launch with the real consumer. The fix is to split the probe from the account. Time-box Hermes alone, and pass it only when a watch extension's refresh time and footprint meet D8's half-ceiling and one-second line, measured on a watch. For the account, give three options with costs: a sign-in flow in Interview, which may need stage 4's live controls; a credential or snapshot delivered by the phone through the stage-3 watch app; or Caltrain at launch and Interview after stage 4, named as a narrowing of question 7. State which consumer stage 3 ships for each result.

Q2, Q4, and Q5 are right. The token is a reserved source because it arrives asynchronously, rotates, and must be readable after relaunch with no send. The Island is measured in WP10 under the half-ceiling rule, with no new budget line. The Mac secret is a shared keychain-access group with profiles on both sides, and a development build without one shows the placeholder.
