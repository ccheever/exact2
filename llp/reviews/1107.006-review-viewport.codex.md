## Outcome

No actionable correctness finding in this bounded TS/root seam review.

- `viewport` executes before all native/storage work. It checks captured route visit, actual current owner (origin/environment/project/thread/generation/thread epoch/workspace), section, navigation revision, and file membership. Invalid reports leave selection/revision unchanged; malformed JSON is neutral.
- A full review read increments navigation revision synchronously before authorization. An explicit file pick increments it before changing selection. Old queued reports therefore cannot undo a newer refresh or explicit destination. Manual reports do not increment that navigation epoch, preventing every scroll report from invalidating later reports from the same visit.
- Passive visibility matches pinned `handleVisibleFileChange`: selection is updated without clearing the comment pick or emitting a scroll target. Lazy loading requests the visible file plus its next two. Existing failed patch entries remain present, so passive reports do not retry them; explicit file/toggle/retry still owns retry. Returning to top does not request again, but the first three are already the initial request set.
- `patchRequest` is a separate captured queue consumed by the existing root task. The viewport action itself has no native answer, network, persistence, or asynchronous adoption boundary. Root checks workspace readiness before dispatch and checks result route/owner before navigation or feedback.
- `app.ts` forwards the captured route argument into the adapter and echoes it in the result. Native event route identity must match that current root dispatch visit, preventing retained hidden-view events from acting on a new visit.
- `row.filePath` preserves the physical diff file independently of a comment row's delete-action context ID. `ReviewSnapshot.navigationRevision` and `ReviewRow.filePath` are declared in current Contract shapes. The result still contains only message/navigation/data (plus the root requestRoute wrapper).
