The direction is right, and decision 2 is aimed at the wrong host work. Shared SVG and the motion engine can carry this app. `d` in keyframes cannot, and several premises about symbols, numbers, and the zoom handoff do not match the code.

## 1. `d` in keyframes will not produce the logo morph or the zoom

Decision 2 makes SVG `d` keyframes the first host feature for "the logo's finite morphs," under ordinary SVG interpolation: compatible commands interpolate, and incompatible shapes change discretely.

The check-to-logo morph is a custom correspondence, not an interpolation of the authored paths. Both apps flatten the stroked check and the filled logo into 240 landmark-paired points, lerp those points, and rebuild a closed quadratic each frame. At the last frame the exact logo path replaces the samples.

```246:262:.refs/ios/modules/apple/EasNative.swift
    static func morphPath(_ t: CGFloat) -> CGPath {
        let n = morphCount
        func point(_ i: Int) -> CGPoint {
            let a = morph.from[i % n], b = morph.to[i % n]
            return CGPoint(x: a.x + (b.x - a.x) * t, y: a.y + (b.y - a.y) * t)
        }
        // ... one quadratic per point, then close
```

```342:372:.refs/android/src/screens/login/components/success-morph.ts
export function traceSuccessMorph(...) {
  // same 240-point lerp, quadTo through midpoints, then close
}
```

The logo `d` and the check stroke do not share a command list. Exact already does what the RFC asks Chrome to do: same commands lerp, anything else changes at once.

```7:12:motion/src/path.rs
//! Two paths interpolate when they have the same commands, one for one...
//! Any other pair is not interpolable, so a `transition` starts nothing and
//! the path changes at once
```

`d` is a transition only. Keyframed `d` is still unbuilt, and a `@keyframes` rule holds at most 32 frames.

```31:35:motion/src/property.rs
//! `d` is SVG 2's path data as a property...
//! named by `transition` (never `@keyframes` yet)
```

```27:27:motion/src/animation.rs
pub const MAX_KEYFRAMES: usize = 32;
```

The iOS modules do not use that model. They sample the whole remaining timeline at 120 Hz into Core Animation keyframes (`EasNative.swift` `rate = 120` at lines 1312 and 1548, `schedule()` at 1397–1433 and 1644–1655). Porting that bake into `@keyframes` is refused at 33 frames. It is also unnecessary for the morph: the two 240-quadratic endpoints are command-compatible, and a `d` transition (delay included, `motion/src/transition.rs` lines 80–89) is the lerp `traceSuccessMorph` already computes. Quadratics are elevated to cubics only when painted (`kernel/src/svg/path.rs` lines 1–8), after the lerp.

The zoom is the same class of miss. Both apps use a geometric scale whose aim grows with progress, then an ease-in is applied to that progress. A CSS `scale` transition eases a linear blend and will be huge at mid-zoom where this curve is still small.

```1600:1609:.refs/ios/modules/apple/EasNative.swift
        let finalScale = (hypot(w, h) * 1.1) / (2 * 4.75 * Mark.logoScale)
        let scale = Mark.settledScale * pow(finalScale / Mark.settledScale, zoom)
        let cy = h / 2 - focusY * Mark.logoScale * scale * zoom
```

`success-zoom.ts` lines 30–42 are the same formula. The resting bands are not path morphs either: `band()` at `EasNative.swift` 1265–1268 has a constant minor radius of 60 once tilt is out of scope, and the motion is rotation, opacity, and scale.

The chart does not need keyframed `d` either. Both apps lerp a fixed 1,024-sample grid and, when the timing finishes, swap back to the original cubics (`use-chart-morph.ts` lines 62–101, `TrendChartView.curvePath` at `EasNative.swift` 927–951). That is the existing `d` transition plus a discrete swap when the topologies stop matching. Retarget-from-presented is what `observe_path` already does.

Say this instead: bake the morph as two compatible paths and play it with the existing `d` transition; approximate the zoom's geometric transform with scale and translate keyframes inside the 32-frame cap, spaced for the end of the curve; do not block the app on keyframed `d`. Keep native Canvas 2D replay off this path. Android already shows Canvas 2D as tiny-skia pictures (`host/linux/src/canvas.rs` 657–663), which is the cost LLP 1056 measured and refused for per-frame drawing.

## 2. The zoom handoff has two owners, and neither CSS end signal exists

The iOS app advances login, zoom, and cold start on a 50 ms poll and fixed durations:

```554:561:.refs/ios/app.contract
    if phase == "success" and performanceNow() - successAt >= (still ? 300 : 1400)
      loginPhase = (still ? "done" : "handoff")
      loginZoomAt = performanceNow() + 34
    if phase == "handoff" and performanceNow() - zoomAt >= 450
      loginPhase = "done"
```

`loginClock` is `every(50, loginTick)` (lines 560–561). Reduced motion skips the morph at 300 ms. The native zoom view never reports completion.

The Android decision this RFC cites as the handoff to preserve says the opposite: session activation waits until the destination has laid out, the cover comes off when the timing finishes, and timers do not decide either (`llp/0001-login-flow-animation.decision.md` lines 164–168 and 281–307).

D3 says activation and completion stay application events and are never native animation callbacks. That matches the iOS poll and forbids the Android completion callback, and the draft never chooses. Contract also cannot see the end of a CSS animation. LLP 1055.000 line 90: animation events (D18) are not built. `QUEUE.md` line 508: there is no `transitionend` and no action at the end of motion.

Pick one owner before implementation. Keeping the iOS clock thresholds preserves the shipping app and drops the Android layout gate; write that down as the resolved difference. Adopting the Android rule means landing an end-of-motion action first. A shared animation whose duration merely hopes to match the 1,400 ms and 450 ms polls will remove the cover early or late under load, which is the failure the Android note exists to prevent.

## 3. Android does not resolve icons to Material, and this app does not use roles

D1 says ordinary icons use existing `symbol:` roles and that Android already resolves them to Material equivalents, with Apple's mapping left unchanged.

The Android painter strokes the schema's web path. An `sf/` name is an empty box. The symbol table is `[role, Apple name, web path]` only; there is no Material glyph column (`kernel/tables/schema.json` lines 4004–4008 and the `_symbols` note at 4596).

```90:94:host/linux/src/paint/svg.rs
    /// A portable symbol role ... as the web draws it: the
    /// role's path in a 24-unit box...
    /// An `sf/` name stays an empty box (LLP 1035.004.000 D4).
```

LLP 1115.001 D14 (lines 472–476) is the decision that adds a Material glyph beside the SF name and the web path. It is S2, dated only after S1 lands (line 860). It is not in this checkout.

The shipping app does not go through roles. `chrome.contract` line 37 is `image \`symbol:sf/${name}\``. `SymbolInstance` loads `UIImage(systemName:)` (`EasNative.swift` lines 81–86). LLP 1035.004.000 D4 (lines 205–214) says a non-Apple host paints `symbol:sf/…` empty, with no reverse lookup onto a role. The Expo Android app draws real Material Symbols through `expo-symbols` (`icon.tsx` lines 98–105) and authored SVGs for the rest.

The implementation order starts with icons. That slice cannot meet §5's Android comparison until D14 is actually in the painter, or until this app's closed set of SF names is redrawn as shared SVG. Extending the role table does not light up the existing `symbol:sf/…` sources. Say that the app must stop using `symbol:sf/` and the `sf-symbol` module, name D14 (or shared SVG) as host work ahead of the icon switch, and do not describe Material resolution as current behavior.

The same gap hits sheets. Four routes are sheets (`helpers.contract` line 13: account picker, project picker, run workflow, TTI). LLP 1115.001 line 680 still records a sheet as short of D10; the Android reader has a Sharesheet (`host/android/.../Requests.kt`), not a bottom sheet. "Sheets follow D10" is an unbuilt dependency, not a control this port can switch to.

## 4. There is no shared numeric-text motion that preserves iOS

§1 asks for one authored numeric transition that keeps the iOS app's appearance. D3 says to use shared keyed text and existing enter/exit motion, then compare with iOS before deleting SwiftUI.

iOS is SwiftUI's numeric transition, a 0.4 s spring with no bounce, tabular figures, and a custom face:

```220:232:.refs/ios/modules/apple/EasNative.swift
        Text(model.text)
            .font(.custom(model.font, fixedSize: model.size))
            .monospacedDigit()
            .contentTransition(.numericText(countsDown: model.countsDown))
            .animation(model.animated ? .spring(duration: 0.4, bounce: 0) : nil, value: model.version)
```

The Android reference is a different effect: one node per `` `${index}:${glyph}` ``, entering and leaving by a third of the line height with opacity, an ease-out, a width layout animation, and a scale-to-fit down to 0.7 (`animated-value.android.tsx` lines 76–100 and 117–131).

Exact has `animation`, `-exact-exit-animation`, springs, and `font-variant-numeric: tabular-nums`. It does not have `.numericText`. Keyed enter/exit can reproduce the Android roll. It will not reproduce the SwiftUI transition, so the §5 iOS before/after fails if that roll is what ships, and §1 fails if SwiftUI stays.

Choose in the RFC. Either the Android roll is the shared motion and the SwiftUI transition is an explicit iOS change, with the third-line travel, ease, overflow scale, and one accessible name written down, or the iOS renderer stays and "one authored numeric transition" is dropped. "Measure later" leaves the end state undecided.

## 5. The gradient gap is real and wider than SVG fills

The Android recorder's SVG path paints solid inks only. A gradient or pattern draws nothing (`host/linux/src/canvas.rs` 708–731). CSS `background-image` gradients are a separate stub: the first stop is painted as a solid (lines 536–540). The scene resolver and the GPU and raster backends already carry `Ink::Gradient` (`host/linux/src/paint/svg.rs` 21–31 and 241–250; `gpu.rs` and `raster.rs` `svg_path`).

D2 only completes SVG linear-gradient fills. This app already authors CSS gradients in the files the RFC says stay unchanged: the header fade (`chrome.contract` lines 15 and 27), the feed fade (`screens/feed.contract` line 95), and the sheet fade (`screens/sheets-parts.contract` line 80). On this host those are flat colors. The chart's under-plot tails are the same kind of view gradient (`chart.tsx` `fadeTail`, `EasNative.swift` `dataTail` / `placeholderTail` at 960–975). The area fill is a mask of a view-space gradient, which is an SVG `userSpaceOnUse` fill only if the chart is rewritten as SVG; until then it hits the CSS stub.

Complete both paints in the recorder: SVG gradient inks (so a chart fill is not invisible) and CSS linear gradients (so the unchanged chrome is not a solid bar). Clipping and gradient space are already in the resolved ink. That is the host work that unblocks the chart, not keyframed `d`.

## Verdict

Shared artwork on the existing motion engine, with platform controls and no second Kotlin geometry, matches LLP 1115 and the two apps' chart math. Before anyone implements, rewrite the host list: Android SVG and CSS gradients first; the logo morph as a `d` transition between the 240-point endpoints that already exist; the zoom as a baked geometric transform, not a `scale` transition and not a 120 Hz keyframe dump; the handoff owner chosen explicitly between the iOS clock thresholds and the Android layout-and-completion rule, with an end-of-motion action only if the latter wins. Drop the claim that Android already draws Material symbols, and do not start the icon or sheet slice until D14 and a D10 sheet exist or the RFC substitutes shared SVG and says so. State the numeric motion as the Android glyph roll or keep SwiftUI. Leave native Canvas 2D replay off the critical path.
