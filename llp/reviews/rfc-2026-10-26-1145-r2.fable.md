**LLP 1145 r2 review, Fable seat**

I read r2 against the tree (`RasterLoader.swift`, `RasterInput.swift`, `host/raster/src/policy.rs`, the runner's collection window, `PresenterMac.swift`/`PresenterIOS.swift`, `rows.rs`, `list.js`, LLP 1144 r2, Excord's RFC). My four r1 points are addressed as §R says: D3 is built and the attribute rule is gone, the retirement-blind `state` is fixed by the counts, the fade is an open question, D4 is honest about the edge stall. Three fundamental concerns remain, all about D1 and D2, most serious first.

**1. D2's attribution ("the download or the decode") cannot answer the question the plan hangs on it, so D1 gets built whatever D2 finds.**
The quantity that decides between D1 (ordering) and §3's prefetch is the *lead*: how long before its box reached the screen the image was asked for, against how long its bytes alone take. During a fling the mount lead is one viewport plus a quarter second of travel (`runner/src/instance/collection/mod.rs:46,59-72`), roughly 300-600 ms; a cold CDN round trip is in that range. If lead < download, no ordering helps, because ordering cannot create lead. D2 records enough to compute this (asked, bytes arrived, box first showed) but buckets late images only as "download" or "decode"; an image asked too late lands in "download", and the plan then builds D1 unconditionally ("D2 next, ... then D1") while §3's prefetch is gated on "downloads still late *after* D1". The asymmetry is backwards: the lever D2 is most likely to point at is the one deferred. Also check D1's premise in the report: admission is already effectively immediate. `inspectOne` fires the fetch and returns at once (`RasterLoader.swift:187-200`), the two workers loop, so every mounted image's download is in flight within milliseconds; the only thing that orders downloads today is the `metadataLimit = 64` cap on sources without a header (`:103-109`), past which `admitDeferred` round-robins by view id (`:1010-1030`), and `URLSessionTask.priority` only reweights streams already in flight. Instead: print per late image the lead the loader had beside its download time; bucket "asked too late" (late even alone) apart from "asked in time, queued behind others" (D1's case; `diagnostics.deferredAdmission` already counts the cap binding); gate D1 on the second bucket being material exactly as §3 gates prefetch on the first. If the first dominates, the lever is §3's prefetch at page arrival (Excord knows every avatar and attachment URL when the page lands, long before mount), and D1 is a detail inside it.

**2. D1's direction source does not exist as claimed, and the fact it needs already exists per list on both platforms (and in the runner).**
§R and D1 say the loader "already observes" each scroller's movement on iOS and macOS. It does not: `watchScrolls` is installed only by `park` and removed by `unpark` once nothing is parked (`RasterLoader.swift:826-833, 836-839, 877-905`), i.e. only under decoded-byte budget shortage, which Excord's avatar-sized images rarely cause (192 MiB budget vs. tens of KB per avatar); on macOS it is an anonymous `boundsDidChangeNotification` for every clip view, with no scroller identity, offset history or sign. Meanwhile the presenter already supplies a signed per-list velocity on both platforms, `collections.motion` → `listVelocity(id)` (`PresenterIOS.swift:205`, `PresenterMac.swift:180-185`; the r1 Grok claim that macOS reports none is wrong today), and the runner already uses it to bias the window toward travel and to realize rows "nearest the viewport on the side of travel first" (`mod.rs:59-72, 828-830`). So D1 proposes a third direction estimator for a rank the runner already computes for every host. Instead: do not build the loader's own. Either hand the loader the presenter's list velocity and keep `distance(view)` (`:870-876`), or, simpler and host-neutral, let the runner carry the rank with the mount, since it already orders realization by travel; the JS target then gets `fetchpriority` on `<img>` from the same fact for nothing, where today the web receives none of D1.

**3. "How long a box showed blank" cannot be measured where D2 puts it; it must be sampled where LLP 1144 already samples each frame.**
The loader learns visibility only in `reconcile` passes, which run on wakes (a download or decode landing, a scroll event only while something is parked), not per frame; `mayShow` is a walk of the superview chain evaluated on demand (`:645-665`). "Box first showed on screen" sampled on wakes is quantized to the gaps between them, which during a fling are the downloads themselves, so the p95 blank figure the report prints, the headline number and the one `--fail-on` would read, is wrong by construction in the direction that hides the problem. LLP 1144 D1 already records per presented frame the target scroller's offset and its unfilled rows. Instead: the loader keeps the per-image times (asked, bytes, decode ms, delivered) and a set of undelivered interests; 1144's per-frame record counts image boxes in the port without pixels, and blank time is accumulated on the frame clock by the thing already walking the port. The counts across retirements then come from the frame record, not the loader.

Not fundamental, but noted: D1's "behind before ahead" rule for `release` only matters when parking binds, which D2 should confirm or dismiss before it is written; D4's `reach-margin` moves a page fetch, not an image fetch, and only becomes an image lever together with §3's prefetch.
