## Review (verbatim)

**Overall assessment — revise and stay Draft.** The direction is sound: one list abstraction, with preferences governing incomplete presentation when preparation falls behind. The proposed guarantees and mechanics are not yet sound enough to implement as written.

It answers Charlie’s three questions unevenly:

1. **Can an app choose?** Generally yes, as a preference within host capabilities. The RFC overstates “never skipped,” “never wait,” and the enforceability of its ceiling.
2. **Is that the best thing to want?** It correctly identifies preparation and cheaper work as more valuable than choosing a failure mode. However, it omits the most important prerequisite: bounding the work inside one expensive row.
3. **One abstraction or different libraries?** One abstraction is the stronger choice here. The argument should rest on shared semantics and implementation cost; “two libraries cannot switch mid-fling” does not establish it.

This was a static audit. “Verified” below means inspected in this checkout, not executed. External platform judgments are explicitly identified as knowledge or inference; I did not open external sources, dependency sources, or images, run builds, or use skills or sub-agents.

**Strengths.** These parts should survive revision:

- **Research §1 and RFC §§1–3 distinguish preparation from the residual trade-off.** Earlier and cheaper content can reduce both hitches and holes; a policy cannot create missing computing capacity.
- **RFC §2 distinguishes destinations from intermediate travel.** This is a useful scheduling preference, especially for explicit jumps.
- **RFC §4 identifies the right shared obligations:** keys, anchors, pins, accessibility positions, selection, and lifetime.
- **RFC §6 puts elapsed-time decisions in the host and deterministic admission in the runner.** The existing iOS cost estimator supports that architectural direction. [ScrollPumpIOS.swift:35](/Users/ccheever/projects/exact2-wt-fill-policy/host/apple/Sources/ExactKit/IOS/ScrollPumpIOS.swift:35)
- **RFC §5 avoids an author-facing millisecond budget.** That is sensible across different refresh rates and workloads.
- **RFC §7 measures hitches and missing content together.** Neither metric alone can establish an improvement.
- **Research §5 labels important AppKit conclusions as untested inference**, and RFC §7 keeps Windows and Android out of implementation scope.

**Concerns and resolutions follow, ordered by importance.**

**1. HIGH — The overload ceiling is neither supported by its citation nor enforceable by the proposed mechanics.**

RFC §2.2 converts a **100 ms input-to-correct-viewport p95 target** into permission for **100 ms of synchronous main-thread occupation**. The cited plan explicitly pairs that completion target with **no event-handling span over 4 ms**. Its overload row requires pending feedback within one refresh while other controls remain responsive. [1044.001:264](/Users/ccheever/projects/exact2-wt-fill-policy/llp/1044.001-text-performance-astra.plan.md:264)

LLP 1041 also explicitly says that checking time after a long operation is diagnostic, not preemption, and that the chunk itself must be bounded. [1041:96](/Users/ccheever/projects/exact2-wt-fill-policy/llp/1041-graceful-overload.rfc.md:96)

The RFC’s `limit` exempts everything “the policy requires.” That preserves the central failure: an expensive visible row remains outside admission control. Today, collection realization constructs the complete row synchronously; the legacy rationer exempts visible and pinned rows. [collection/mod.rs:448](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/collection/mod.rs:448), [collection/mod.rs:510](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/collection/mod.rs:510), [window.rs:664](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/window.rs:664)

The existing Mac pump even explicitly permits the first indivisible expensive row to exceed its estimated budget. Copying that mechanism cannot establish the new ceiling. [PresenterMac.swift:808](/Users/ccheever/projects/exact2-wt-fill-policy/host/apple/Sources/ExactKit/Mac/PresenterMac.swift:808)

**Resolve:** Separate three quantities:

- maximum uninterrupted UI work;
- elapsed time until correct destination content;
- allowed duration/area of pending presentation.

Make admission apply to visible work too. Require bounded continuation units inside dense rows, including realization, layout, encoding, application, and paint where applicable. The cited plan already identifies yielding between span/cell groups as necessary. [1044.001:309](/Users/ccheever/projects/exact2-wt-fill-policy/llp/1044.001-text-performance-astra.plan.md:309)

This prerequisite must precede policy promises, not arrive with the ceiling in stage 4.

**2. HIGH — `auto` is a useful preference, but its rule is too absolute and its causes are incomplete.**

RFC §2 conflates input source, motion phase, destination confidence, and content invalidation. These are separate facts.

Examples where the table gives a questionable result:

- A fast finger drag or high-rate wheel input can traverse expensive rows just like a fling, yet `auto` waits for every visible row.
- A slow decelerating fling can be readable, yet the table permits holes until its landing zone.
- A thumb drag can be deliberate browsing. Showing nothing throughout it can prevent the user from finding where to release.
- A fling can stop early because of another touch, reverse, encounter a changed extent, or be superseded by a jump.
- Width changes can be continuous user input. Classifying them as an app operation that waits risks repeated stalls.
- Keyboard paging, Home/End, accessibility navigation, focus/caret reveal, selection autoscroll, scroll snapping, browser restoration, and animated app scrolling have no explicit disposition.
- One report can contain both a data change and user motion. The RFC specifies no precedence.

There are also **seven table rows**, while §6 refers to “six causes.” Treating “fling landing” as a phase rather than a cause could resolve the count, but that model is not stated.

Host classification is not presently available through the shared feedback structure. [collection/api.rs:18](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/collection/api.rs:18)

The relevant local hooks differ:

| Host | Checkout evidence | Consequence |
|---|---|---|
| iOS | Drag start and scroll callbacks exist; `targetContentOffset` is currently handled for horizontal snap behavior. [NodeViewIOS.swift:638](/Users/ccheever/projects/exact2-wt-fill-policy/host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift:638), [NodeViewIOS.swift:686](/Users/ccheever/projects/exact2-wt-fill-policy/host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift:686) | Phase/target reporting is feasible work, not an existing collection capability. |
| macOS | Wheel events expose phase and momentum phase; a separate knob tracker recognizes mouse-driven live scrolling. [NodeViewMac.swift:162](/Users/ccheever/projects/exact2-wt-fill-policy/host/apple/Sources/ExactKit/Mac/NodeViewMac.swift:162), [CollectionMac.swift:36](/Users/ccheever/projects/exact2-wt-fill-policy/host/apple/Sources/ExactKit/Mac/CollectionMac.swift:36) | Several distinctions are available, but geometry notifications alone do not carry them. |
| Web | Collection scrolling is observed as an offset change and queued report. [collection-glue.js:75](/Users/ccheever/projects/exact2-wt-fill-policy/host/web/collection-glue.js:75), [collection-glue.js:246](/Users/ccheever/projects/exact2-wt-fill-policy/host/web/collection-glue.js:246) | No current classifier establishes the proposed causes. **Resolve:** Define source, phase, destination, and invalidation separately; permit **unknown**. Specify a conservative fallback and interruption transitions. Recast the rule as prioritizing likely reading destinations while bounding all work. Explain the first-mount exception to `smooth`, which currently contradicts “never wait, even at rest.”

**3. HIGH — Scheduling priority, admission, continuation, and retention are underspecified.**

RFC §6’s order starts with policy-required rows, then the landing viewport. Under `smooth`, or `auto` during transit, what makes currently visible missing rows eligible before speculative landing work? The wording either exempts them from the limit again or risks starving them.

A distant landing also requires a **disjoint retained interval**. Today the collection selects its geometric window plus pins; rows outside the selected ranges are immediately destroyed. Merely building a destination early would not keep it alive through subsequent reports. [collection/index.rs:250](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/collection/index.rs:250), [collection/mod.rs:400](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/collection/mod.rs:400), [collection/mod.rs:476](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/collection/mod.rs:476)

Continuation must also work without new geometry. Current Apple and web adapters suppress identical reports. Adding a partial-fill reply without changing that rule can leave unfinished work asleep. [Collection.swift:300](/Users/ccheever/projects/exact2-wt-fill-policy/host/apple/Sources/ExactKit/Collection.swift:300), [collection-glue.js:130](/Users/ccheever/projects/exact2-wt-fill-policy/host/web/collection-glue.js:130)

The wire meaning of zero is especially important:

- Apple legacy ABI: `0` means unlimited; `1` means zero extra rows. [exports.rs:302](/Users/ccheever/projects/exact2-wt-fill-policy/host/apple/src/abi/exports.rs:302)
- Web legacy ABI: `0` means unlimited; other values are the extra-row count directly. [abi.rs:408](/Users/ccheever/projects/exact2-wt-fill-policy/host/web/src/abi.rs:408)

**Resolve:** Specify one versioned encoding with unambiguous zero and unlimited states; distinguish priority from total admission. Define continuation eligibility, progress under zero allowance, fairness across lists, and cancellation of obsolete landing work. Bound retained current, lead, landing, and pinned intervals without retaining their entire intervening span.

**4. HIGH — Pending needs an acceptance protocol, not just interval coordinates.**

RFC §§2 and 6 leave several correctness questions unanswered:

- Does pending mean unconstructed rows, unmeasured rows, unavailable pixels, or unavailable data?
- Which source/width/measurement generation do its offsets describe?
- Does it include only demanded content, or every unmounted row?
- What happens when measurements move an interval across the viewport?
- When a jump exceeds the ceiling, does the offset commit with pending, or remain at the old position?
- How does a new user gesture cancel a jump being prepared?

The current seam has revision, scroll-sequence, and row-epoch protections, including rejection of stale feedback. Those protections must encompass the pending representation and its replacement. [collection/api.rs:18](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/collection/api.rs:18), [collection/mod.rs:534](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/collection/mod.rs:534)

“Keep the accepted result” for data changes also needs qualification. Keeping an old coherent viewport during preparation can be correct. Keeping old content under newly committed labels, keys, geometry, or hit targets is not. The referenced plan explicitly distinguishes these. [1044.001:216](/Users/ccheever/projects/exact2-wt-fill-policy/llp/1044.001-text-performance-astra.plan.md:216)

The retirement rule is outright wrong: **the legacy path also retires when nothing remains to create**, and has immediate-retirement cases. Restricting retirement to creation reports can strand obsolete views after viewport shrinkage or pin release. [window.rs:696](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/window.rs:696)

**Resolve:** Define demanded, materialized, accepted, and presentation-ready coverage separately. Publish geometry, pending, rows, and hit metadata coherently. Make retirement independently bounded and capable of finishing after creation stops. Define `clock settle` as settling bounded current demand—not materializing all logical records.

**5. HIGH — Interaction and accessibility must be migration gates.**

RFC §4 names the invariants, but §6 does not explain their behavior across pending regions and stage 1 permits deletion based principally on hitch numbers.

The existing implementation provides useful foundations:

- Pins refer to mounted descendants; unknown pins are rejected. [collection/mod.rs:543](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/collection/mod.rs:543)
- Logical copy supports both engines and can realize an unmounted row without publishing it. [text.rs:49](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/text.rs:49), [text.rs:220](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/text.rs:220)
- Browser selection endpoints originate in mounted paragraph/row elements. [list-selection.js:85](/Users/ccheever/projects/exact2-wt-fill-policy/host/web/list-selection.js:85)
- Accessibility position/count metadata is published on mounted wrappers. [collection/views.rs:62](/Users/ccheever/projects/exact2-wt-fill-policy/runner/src/instance/collection/views.rs:62)

Those mechanisms do not answer:

- How does keyboard or accessibility focus request an unbuilt item?
- What happens when selection dragging reaches pending space?
- Are interaction/focus pins retained under every policy?
- What communicates pending status to assistive technology when the band is hidden?
- Can the list temporarily appear empty to accessibility despite a nonzero logical count?
- How do activation and editing behave during accepted/candidate replacement?

**Resolve:** Add explicit behavior and tests for these cases before enabling pending broadly or deleting the legacy path. Preserve bounded pins rather than pinning an entire selection. Use logical text for copy, while defining how new endpoints are acquired. Slice F already makes selection, full copy, focus, nested scrolling, and anchors prerequisites to migration. [1044.001:343](/Users/ccheever/projects/exact2-wt-fill-policy/llp/1044.001-text-performance-astra.plan.md:343)

**6. MEDIUM — The `pending` block is more expensive and less specified than it appears.**

RFC §5 promises per-row rendering at each known/estimated height, rasterized once per distinct size. RFC §6 supplies only pending intervals and one band per interval.

An interval of height 100 does not tell a host whether it contains rows of heights **20 + 80** or **50 + 50**. The proposed row-shaped placeholder cannot be reconstructed from interval endpoints alone.

“Once per distinct size” also supplies no cache bound. Variable row heights, continuous resizing, display-scale changes, and appearance changes can produce many raster variants. “Sees no item” does not establish that a Contract block is cheap, pure, or free of resource dependencies.

The compiler currently requires exactly one direct `each` child, so this is a real authoring-language extension, not just presentation styling. [collection.rs:36](/Users/ccheever/projects/exact2-wt-fill-policy/contract/lower/src/collection.rs:36)

**Resolve:** Prefer background-only pending for the first implementation. If custom pending remains, define allowed content, dependencies, invalidation, clipping, cache ownership/bytes, and the geometry supplied to hosts. Consider interval-level decoration instead of row-by-row skeleton replication.

**8. MEDIUM — One abstraction is justified, but the opposing argument is understated.**

The strongest alternative is not “two libraries, one permanently hitching and one permanently blank.” It is:

- an eager/native list for modest content and strong platform integration;
- a virtualized renderer for very large datasets;
- shared key/selection/geometry utilities where practical;
- each implementation able to offer its own fill options.

Different implementations can legitimately differ in text selection, accessibility integration, cell lifecycle, geometry constraints, and rendering ownership. A library can change scheduling policy during a fling. Thus RFC §4’s first argument is not decisive.

For exact2, I still favor one author-facing list with internal scheduling options: the proposed variation concerns admission and presentation, while most semantic obligations remain shared. But “grid, masonry, and inverted chat are the same engine with different layout” should be future compatibility intent, not additional admitted scope. Current collection validation deliberately constrains the supported shape. [collection.rs:35](/Users/ccheever/projects/exact2-wt-fill-policy/contract/lower/src/collection.rs:35)

The reuse argument also overclaims safety. Runner-owned local slots do not eliminate host-owned state. UIKit views contain text editors, pending composition values, raster state, and media; their retirement performs substantial invalidation. [NodeViewIOS.swift:96](/Users/ccheever/projects/exact2-wt-fill-policy/host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift:96), [NodeViewIOS.swift:262](/Users/ccheever/projects/exact2-wt-fill-policy/host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift:262), [NodeViewIOS.swift:535](/Users/ccheever/projects/exact2-wt-fill-policy/host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift:535)

**Resolve:** Keep one abstraction, explicitly permit host-specific implementation strategies, and replace “a reused view carries no stale state” with a reset/cancellation/identity contract. Keep reuse as a separately measured optimization.

**9. MEDIUM — The instrumentation cannot establish its stated presentation claims by itself.**

RFC §6 defines `holes` as **frames presented** with missing coverage. Main-thread observations cannot necessarily observe those frames while an off-thread scroller continues. Conversely, a declared pending interval can exist without ever reaching the screen.

`waits` counting fills longer than one frame also misses accumulated work: several shorter operations can miss a deadline, and a long operation is not equivalent to a known number of missed presentations.

Missing rows, missing text pixels, intentional whitespace, and pending decoration need separate accounting. Existing reader diagnostics already distinguish pending pixel/width state from row existence. [RegionReaderMac.swift:143](/Users/ccheever/projects/exact2-wt-fill-policy/host/apple/Sources/ExactKit/Mac/RegionReaderMac.swift:143)

**Resolve:** Call inexpensive counters what they measure—logical pending coverage, fill duration, scheduled callbacks. Use presentation evidence for presented-frame claims. Add time to first correct viewport, longest pending interval, area-time of missing content, input response, and retained memory. Document unavailable observations rather than returning a misleading zero.

Explicit-limit tests should exercise production scheduling decisions without real-time variability. `clock settle` needs a bounded failure result and must not erase the intermediate state those tests are intended to inspect.

**11. LOW — `fillPolicy` is defensible; the proposed estimate rename is not established by the web-standard rule.**

There is no direct CSS property for virtual-list admission policy. Using an exact-specific attribute beside `scrollFollowEnd` and `retainFocus` is consistent with the existing schema. [schema.json:311](/Users/ccheever/projects/exact2-wt-fill-policy/kernel/tables/schema.json:311), [schema.json:341](/Users/ccheever/projects/exact2-wt-fill-policy/kernel/tables/schema.json:341)

However, **CSS knowledge, not externally verified here:** `contain-intrinsic-block-size` describes an element’s intrinsic-size substitution under containment. A list-level estimate for each unmaterialized item is not automatically the same semantic property.

Also, `complete` and `smooth` read as guarantees that the RFC expressly cannot provide. They can remain names if their preference semantics are prominent and consistent.

**Resolve:** Keep the estimate rename out of this RFC, including the leading claim that it “already has a web name.” State that fill policy controls presentation preference, never data loss, native momentum, or an unconditional FPS/completeness guarantee.
