## Review (verbatim)

**Build with named changes.** The axis split, the one-level lifetime, and not keeping the offset are sound. Do not implement nesting from this text until the pin chain is respecified, and do not treat the fill and memory sections as descriptions of this tree.

1. **BLOCKER.** N5 does not pin an enclosing row, and the code change it names makes that worse. `update_collection` releases the category on every collection except the one being updated before it applies the report (`runner/src/instance/collection/traversal.rs:234–241`). `release_other_pins` already does that to an ancestor, because the outer list is reached from the root (`:412–416`); it does not walk mounted rows, so an outer report does not clear an inner pin. Descending, as N5 says to, clears both directions. A focus that is the only reason the outer row is mounted is cleared in that release, `release_pins` realizes the window without it (`mod.rs:1012–1038`), and the inner `Collection` is dropped before `feedback_walk` runs. That is the case the compiler refusal exists for (`contract/lower/src/collection.rs:62–64`). Hosts will not paper over it: Apple reports the pin only for the nearest owner and says an ancestor must not pin the outer row (`host/apple/Sources/ExactKit/Collection.swift:232–239`, `:351–369`); `testNestedCollectionsOwnOnlyNearestPinsAndReleaseBeforeTransfer` asserts at most one focus (`CollectionMacTests.swift:282–313`); the web `liveView` returns null unless this list is that nearest owner (`host/web/collection-glue.js:109–120`). The runner would already accept a descendant on an outer report: `pin` uses `find::contains`, and `NodeInst::contains` walks into a nested collection (`runner/src/instance/find.rs:74–77`). §1 is also wrong about Linux: `pin_owner` walks from the focused view upward and returns the first row wrapper, which is the innermost list (`host/linux/src/presenter/collection.rs:224–239`), not “the first snapshot.” **Change:** a chain is the addressed list plus every ancestor list whose mounted row contains that same pin view. Release the category only on lists off that chain. Report the pin to every list on the chain, and replace the nearest-only test. Do not describe Linux as failing to pick the innermost.

2. **MATERIAL.** F1, F3, H3, and F4 step 2 describe LLP 1050.000 behavior this tree does not have and this RFC does not schedule. `CollectionFill` is velocity and `limit` (`runner/src/instance/collection/api.rs:43–50`). There is no `fill-policy`, no per-key cost memo, and no rest offset. `limit` does not ration owed rows (`mod.rs:560–592`), and owed rows are the visible band plus pins. Creating the outer row runs the inner list’s `update_data`, which keys every inner item (`mod.rs:243`, `:272–299`). A visible filmstrip therefore does its O(N) setup on the fling that first shows it. F2’s `limit: Some(0)` only skips overscan. D3 is 1050.000 stage 3; the landing viewport is stage 4. The v3 rename table adds neither a cost nor a rest field, so “the rest offset is `targetContentOffset.x`” and “the outer landing viewport, when a rest offset exists” have nowhere to go. LLP 1068 §5.1 is also unmerged and would not skip that key pass: it withholds one heavy platform view, not the row’s setup. **Change:** make 1050.000 stage 3 a precondition of nesting, and add rest to the seam only if landing-first is actually in this RFC. Otherwise delete the pending-mid-fling and rest-offset sentences and state that a visible nested row, key pass included, is built during an outer fling.

3. **MATERIAL.** F4 removes the report caps that keep a fling inside one slice. iOS allows two feedback calls per main-queue turn, one list each (`Collection.swift:49–59`, `:339–364`). The web allows four reports per frame (`collection-glue.js:146`, `:152`). “Each pass visits every dirty list” and “one report per dirty list per frame” multiply that by every nested list on screen, and owed rows are outside `limit`. **Change:** keep both caps. Spend them on outer owed rows, then inner owed rows, then leads.

4. **MATERIAL.** N4’s byte math and its drop path are not what this repo is. `QUEUE.md`’s crypto-memory bullet, item (5), says the index is about 1.1 MB at 5,000 items (about 220 bytes an item today) and about 30 bytes only after an `Rc<str>` sharing change that is not built. It is not 40 bytes, and it is not entry 1. A 2,000-item filmstrip is about 440 KB, so 512 KiB holds one of them, not six, and two to four live strips are about 1–2 MB of index, not 0.2–0.4 MB. Whole-adopt also retains the items `Rc<[Value]>`, which the cap does not count. Nothing in the tree implements `didReceiveMemoryWarning`; `NodePool.reset` runs from presenter teardown (`PresenterIOS.swift:283`). The cache lives in the runner, which that reset does not touch. There is no typography epoch either: `invalidate_typography` only walks live collections (`traversal.rs:481–515`). **Change:** cite the measured size, count retained item values, and add a counter bumped from `invalidate_typography`. Delete the memory-warning and backgrounding sentences, or name a real host-to-runner signal. Web and Linux have only the cap.

5. **MATERIAL.** The bootstrap is not “16, so use the port instead,” and the runner does not know that port when it creates the inner list. The count is `ceil(16 × 32 / estimate)`, capped at 16 (`mod.rs:36–37`, `:216–220`). At `estimated-item-width=128` that is 4 rows, not 16; `ceil(600/128)` is 5. On a wide feed the port-sized count is larger than today’s 512 px budget, not smaller. The first window is that bootstrap, before any geometry report (`mod.rs:546–548`), and the inner list is created while the outer row is realized, before the host has laid the strip out. **Change:** define the number. Use the outer `row_width` for a stretched horizontal list, the authored main-axis length for a vertical inner list, and the existing 512 px budget when neither is definite. Correct the example.

6. **MATERIAL.** The macOS latch is unspecified exactly where the current router drops the events that define a gesture, and it is not hand-only. On an `auto` axis a zero-delta phased event returns `.drop` (`ChainingScrollView.swift:84–85`). A trackpad `began` is often that event, and the zero-delta `ended` is the lift AppKit needs or the rubber band stays stretched (`:77–83`). `tap … wheel dx dy gesture` already sends `began`, `changed`, and that zero-delta `ended` (`host/apple/Sources/ExactKit/Mac/AgentMac.swift:423–448`, `scripts/agent.mjs:12`, `:947`). **Change:** latch on the first non-zero `changed`, and deliver every later zero-delta phase of that gesture to the same view. Test it with `gesture`. Keep a physical trackpad only for the Chrome comparison.

7. **MATERIAL.** The iOS edge rule does not say what `gestureRecognizerShouldBegin` does when it does not yet know the direction. The pan override reads velocity (`ScrollViewIOS.swift:32–37`), which is often still zero on that call. Returning false then gives an inward drag to the outer; returning true latches the inner for the whole gesture, and G1 correctly forbids a later hand-off, so the outer never gets it. The refusal also has to run before `super`, and only for a known outward direction on an `auto` axis that actually scrolls. `bounces` per view is correctly noted. **Change:** if the dominant axis is not yet known, do not fail the inner pan. Fail it only when the inner is at the edge in a known outward direction under `auto`. Leave `contain` and `none` as written. Keep the device run as a landing gate, not as the spec of this case.

8. **MATERIAL.** G2’s `touch-action` sentence contradicts CSS and the host. `pan-x` does not hand a vertical touch to the feed. `gestureRecognizerShouldBegin` walks from the hit view through every `NodeView` up to that scroll view and returns false if any of them refuses the axis (`ScrollViewIOS.swift:39–46`), so `pan-x` on the strip also stops the outer vertical pan. LLP 1057.001’s rule is the same intersection: scroll wins only on axes `touch-action` leaves. What hands a vertical drag to the feed is a horizontal-only scroller, which LLP 1008 already gets by turning off forced vertical bounce when only x has travel (`llp/1008-apple-host-v1.spec.md:678–684`). **Change:** delete “hands every vertical-dominant touch to the feed.” Say `pan-x` on a strip means a touch there pans horizontally only, feed included.

9. **MATERIAL.** The phase-less diagonal is an undeclared web-versus-native split, and §2 already measured it. Chrome gives the horizontal strip the x component and drops y; the outer does not move. Linux takes the dominant axis and, if that scroller wins, applies both components (`host/linux/src/presenter.rs:1071–1082`). macOS does the same (`ChainingScrollView.swift:88–111`), and so does the iOS agent wheel (`AgentIOS.swift:560–588`). A y-dominant `tap wheel 60 100` therefore scrolls the feed on Linux, macOS, and the iOS agent, and scrolls the strip on the web. “A mouse wheel does not produce this” is wrong for that command (`scripts/agent.mjs:9`, `:1245`) and for the CDP `mouseWheel` the table used. §9’s script is axis-aligned, so it will not catch it. **Change:** for a phase-less wheel, follow Chrome (deepest scroller that can take any component, drop the rest) or enter the difference in LLP 1001. Do not wait on the trackpad check for a case the table already shows.

10. **MATERIAL.** N2 does not remove the key pass for the feed it is written for, and “a cached size is never an authority” is false on the whole-adopt path. `Collection::create` always `update_data`s fresh and keys every item (`mod.rs:243`, `:358–391`). The skip requires the same `Rc<[Value]>`. §8’s `stripItems(post)` is a new list unless the data module caches that allocation; otherwise only per-key sizes are reused and the key pass still runs. Adopting the index whole also keeps measured epochs for unmounted rows, and finding 4’s epoch does not exist to clear them. **Change:** state that the key pass disappears only when the items allocation is reused, and that the example must return that value or the cache does not pay. On adopt, store sizes as estimates. Leave “build it only if stage 3 measures a win.”

11. **MATERIAL.** The Q1 escape hatch, an authored `scrollLeft`, is build-then-move only for web `scrollTop`. `glue.js:815` special-cases `scrollTop`. `jumpTo` assigns `scrollTop` (`collection-glue.js:227–233`, `:391–396`). iOS writes `pendingScrollLeft` straight onto `contentOffset` (`NodeViewIOS.swift:864–866`). Linux collections read `ScrollTop` only (`presenter/collection.rs:625–635`). A restored filmstrip offset can paint an empty port, which is the bug 1050.000 stage 2 closed for `scrollTop`. The web anchor write is also still `port.scrollTop` (`collection-glue.js:381`) and is not in §7’s web list. **Change:** build the target rows, then assign `scrollLeft`, on every host. Make the correction write axis-generic in the same change.

12. **MATERIAL.** The depth rule is looser than today’s runner check, and inner edge re-arm cannot see the inner list. The compiler rejects a nested literal `true` (`collection.rs:72–74`). The runner rejects any nested `virtualized` binding that is not the constant `false`, including a dynamic one, on inactive arms (`traversal.rs:440–466`, called from `mod.rs:209`). §8’s “mirrors the depth rule” drops that. Separately, `find_collection` descends into mounted rows (`traversal.rs:348–358`) but `find_collection_mut` does not (`:383–384`). `rearm_collection_edge`, `take_collection_end`, and `wake_collection_edge` all use the mutable lookup (`:260–282`). `feedback_walk` does descend, so an inner `reachstart`/`reachend` can fire once and never re-arm. **Change:** depth one allows only a constant `true`. A dynamic `virtualized` stays rejected at every depth, inactive arms included. Make `find_collection_mut` descend the same way `find_collection` does.

13. **MINOR.** Smaller claim and checklist errors. `runner/src/instance/collection/tests.rs` is 1,445 lines, as §9 says, but those suites do not pass unchanged through the rename: `:554–556` asserts `scrollTop` in the snapshot JSON. §2’s table measures `contain`, not `none`, so “`none` stops chaining” is the spec, not that run. §3.2 allows `min-height` with `max-height` as the cross size; §8’s `lower-collection-cross` says `height` only. G3’s “pending interval” is a boolean `pending` (`api.rs:96`, `:250`), not an interval that can name a list. §9’s `strip-5` / `inbox-7` do not match §8’s `` `strip-${post.id}` ``. The parity fixture needs one assertion the RFC never states: the outer row’s used width stays the feed’s width. The strip’s spacer is the full extent, the example sets neither `width: 100%` nor `min-width: 0`, and it sits in a `column`, which is `display: flex` (`contract/lower/src/tags.rs:69–74`). **Change:** fix those sentences, and add that width assertion to the fixture.

14. **MINOR.** Accessibility is missing, and the existing machinery mostly covers it. Wrappers already publish `listitem`, posinset, and setsize per collection (`views.rs:21–22`, `:73–84`), so an inner list is its own list. Selection already stops at a list boundary (§11). **Change:** say that, and that assistive scrolling stays the platform’s. No new agent operation.

15. **MINOR.** The deferred-list take is honest and the four questions are the right product questions, with one schedule question left implicit. The entry names what it unblocks, keeps grids, masonry, wrapping, inverted lists, deeper nesting, and host keep-alive out, and deletes a path rather than adding a shim. That matches `rules/DEFERRED.md`. It is a cheap take, and Q2 already says so: “One list engine” in `QUEUE.md` already owes the `window.rs` deletion, and stage 2 ships horizontal lists before that deletion (“before nesting lands”). No new check, script, or harness; the Extra Heavy probe stays outside the repo, which is LLP 1050.000 D4. H4’s main-axis anchoring is a real deviation and is justified: the glue already sets `overflow-anchor: none` (`collection-glue.js:371`), and an off-screen virtualized measurement is not something the eager page does. G2 and the diagonal (findings 8 and 9) are the places it does not follow the web. LLP 1068 stage 1 is unmerged, as the RFC says; HEAD’s pool still refuses a row with a scroll view (`NodePoolIOS.swift:153–154`). N1 matches 1068 §4.2’s offset reset and §5.3’s rejection of key keep-alive. An implementer is still unnamed. `rules/RULES.md` wants one before this is built; the header says Charlie names them. **Q1, yes:** do not keep the offset. Re-insertion resets it, row lifetime is removal, and 1068 §5.3 is the right reason not to make position depend on whether the key was recently seen. **Q2, yes, with the caveat already in the question.** **Q3, yes:** `auto` chains and gives up the inner rubber band; `contain` keeps it.
