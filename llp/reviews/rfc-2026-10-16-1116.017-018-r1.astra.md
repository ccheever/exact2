I would substantially narrow 1116.017 and pursue a scoped 1116.018 first. The evidence supports fixing specific quality failures. It does not yet show that either proposal materially improves the program’s token or time advantage.

For **[1116.017](/Users/ccheever/projects/exact2/llp/1116.017-what-the-compiler-can-name-it-accepts.rfc.md), the core rule is too broad**. Being able to suggest an edit does not establish that silently applying it preserves the written meaning. The better rule is: **accept familiar syntax when its semantics are defined independently of the diagnostic and normalize exactly to existing behavior**.

This preserves [1116.014’s decision](/Users/ccheever/projects/exact2/llp/1116.014-what-builders-guess.rfc.md:11): no guessed role aliases or inferred identity. It permits useful syntax without expanding Contract’s computational capabilities. But D2’s hidden structure and D3’s approximations do not follow from that permission.

My answers to its §9:

| Question | Recommendation | Confidence |
|---|---|---|
| **1. Where is the line?** | Accept `h1`–`h6`, `image src`, the supported logical shorthands, multiline function bodies, and unambiguous component-call syntax. Keep the earlier exclusions. Describe this as a bounded language surface, rather than a general obligation to accept anything with a plausible repair. | High |
| **2. Warning or error for platform conflicts?** | Honor explicit choices when the rendering actually preserves their semantics. Keep errors for unsupported combinations. A conditional footer that faithfully becomes native footer text needs no convention warning. A warning cannot make an approximation faithful. | High |

| **4. Worth doing?** | Yes, as a small coherence and quality improvement. Ship the harmless syntax and guide corrections; establish the additional value of broader changes against better messages alone. | Medium |

Two examples make the boundary consequential:

- **`width` is not symbol point size.** CSS width sizes a box; Exact already measures a symbol’s glyph dimensions from its point size. Translating one into the other contradicts “what the author writes wins.” This is a semantic change, not an error becoming a warning. See [CSS sizing](https://www.w3.org/TR/css-sizing-3/#preferred-size-properties) and [SymbolMeasure.swift](/Users/ccheever/projects/exact2/host/apple/Sources/ExactKit/SymbolMeasure.swift:25).
- **A second root changes more than punctuation.** It inserts a layout box. With `view color=…`, a sole root button receives an own color; after adding a sibling, that button would inherit the wrapper’s color. [LLP 1115 deliberately treats those differently](/Users/ccheever/projects/exact2/llp/1115-write-the-web-ship-the-platform.principle.md:57). That is a reader-visible semantic discontinuity.

Cold builders can benefit from familiar syntax. Guided builders have already learned much of the current surface, so their benefit is smaller. Human readers must understand every accepted form even if the guide teaches only one; canonical formatting can reduce variation, but a +200-byte guide budget does not measure language complexity. Also watch induced guesses: [1116.016’s measurements](/Users/ccheever/projects/exact2/llp/1116.016-contract-expressions-are-typescripts.rfc.md:366) already show that promising familiarity invites neighboring unsupported features.

For **[1116.018](/Users/ccheever/projects/exact2/llp/1116.018-a-repair-keeps-the-feature.rfc.md), the core direction is right, but the universal promise is wrong**. Require **truthful repair suggestions whose claimed behavior is tested**. Allow a diagnostic to explain that no equivalent supported form exists. Otherwise D1’s “unsupported is a defect” creates pressure to expand the language whenever a builder encounters an intentional boundary.

The draft itself illustrates why text equality is insufficient: replacing a heading role with a button’s `aria-label` preserves a name, **not heading semantics**. [ARIA defines the label as an accessible name](https://www.w3.org/TR/wai-aria-1.2/#aria-label). Similarly, timer text can match while timing or cancellation is wrong. Tests should check the relevant state transitions, clock behavior, accessibility, layout, or work—not require every case to pass through a text-only runner oracle.

The ARIA premise also needs care: absence of an identically named UIKit property does not establish absence of equivalent behavior. Exact already [posts native live-region announcements](/Users/ccheever/projects/exact2/host/apple/Sources/ExactKit/Accessibility.swift:617). Native implementation gaps should be evaluated separately from language admission.

**Neither §7 currently distinguishes success from noise adequately.** There are structural measurement problems before statistical ones:

- **1116.017:** targeted error IDs disappearing follows automatically from accepting them. The repair harness [filters out warnings](/Users/ccheever/bakeoff/repair.py:77); its judge [skips first-try successes and unrepaired failures](/Users/ccheever/bakeoff/repair_judge.py:39). Thus error-to-warning changes can remove examples from evaluation without demonstrating correctness.
- **1116.018:** “whole repairs rise in both models” has no minimum effect or uncertainty threshold, and changing which screens require repair changes the denominator. The judge also [explicitly ignores styling](/Users/ccheever/bakeoff/repair_judge.py:19), so it cannot establish D3’s no-tells claim. A resource named `loadTasksByDueDate()` records an obligation; it does not prove the data module fulfills it.

Use the same fixed tasks across **current behavior, messages/docs alone, and messages plus selected acceptances**. Measure correct completed features across *all* tasks, including first-try successes and failures, within the repair budget. Use paired repetitions, report uncertainty by task and model, and validate on held-out complete apps with normal lookups. Keep compiler comparisons’ guides fixed; evaluate guide changes separately. Include Claude-like builders before generalizing beyond GPT and Muse.

Measure time, tokens, lookups, and warning-driven edits **to a correct result**, with execution and native presentation checks for the affected features. The existing 1.75 error sites per build are not 1.75 extra build cycles. [1116.016 already measured essentially unchanged repair rounds](/Users/ccheever/projects/exact2/llp/1116.016-contract-expressions-are-typescripts.rfc.md:360); neither draft should assume the framework-level advantage follows.

**Verdicts:** **1116.017 — RETHINK**, retaining its small syntax/coherence slice. **1116.018 — READY WITH CHANGES**, scoped to truthful suggestions and demonstrated losses.

My top three recommendations, most important first:

1. **Separate exact normalization from semantic invention.** Defer implicit roots and width-to-point-size conversion; preserve Contract’s computational boundaries.
2. **Fix observed feature losses with honest, behavior-tested repairs.** Unsupported behavior may remain unsupported; equivalent-looking text is insufficient.
3. **Measure correct apps on a fixed denominator.** Compare messages alone against acceptance, include native quality, and time-box this work against the larger data-protocol and tooling costs.
