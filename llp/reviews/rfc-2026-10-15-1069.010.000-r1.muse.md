# Review of LLP 1069.010.000 (r1)

**Reviewer:** muse muse-wonder-full-1.0, reasoning effort xhigh, run 2026-10-15 by Claude (Opus 5.5) for Charlie Cheever, read-only on the r1 draft over `9f4042a3a`, blind to the other two reviews. Scope given: foundational and directional questions only. The text below is the reviewer's final message, unedited.

VERDICT: ACCEPT WITH CHANGES

Stage 1's direction may proceed subject to findings 4–5; stage 2 should not receive the DEFERRED ruling on D3–D7 as written until findings 1–3 are settled.

1. **The kept grant is wider than the person's choice, in item, provenance, and mode.** D3 auto-keeps every mint and D7 claims it is "exactly what a person chose," but today's mints are wider: a file arriving by a host route is minted as a handle to its *parent folder* ([data/src/documents.rs](data/src/documents.rs:102) `open_route`; parent slice 3, "The routes"), so double-clicking one file would durably grant its whole folder; any absolute path arriving at the `open-file` node mints, including typed paths and followed links ([host/apple/Sources/ExactKit/DocumentPickers.swift](host/apple/Sources/ExactKit/DocumentPickers.swift:37)), as do the agent's picker answers (same file, `documentAnswered`), which are a test driver's words, not a person's choice; and no entry records whether it was chosen to read (open picker, drop) or to write (save, directory), so a view-only choice becomes durable write access wherever the app declares `fs.write doc:/`. Session-only handles tolerated these widenings; a durable grant must not, and the parent itself says the folder form is inexpressible under the App Sandbox (Q2). Change: record provenance, exact item, and read/readwrite mode at mint; only genuine picker and OS-open mints of the exact item are eligible to keep — never typed, agent-answered, or link-followed paths, and a routed file keeps the file, not its folder.

2. **A recents list is not yet a capability store: the proposal needs one source of truth, person-owned revocation, and honest eviction semantics.** D3 says the kept set *is* macOS's Open Recent list and "Clear Menu revokes it all," but that list belongs to `NSDocumentController` ([host/apple/Sources/ExactKit/Mac/DocumentsMac.swift](host/apple/Sources/ExactKit/Mac/DocumentsMac.swift:130)), while D4 also requires a host-side bookmark store and persisted counter — two lists that can diverge, with no mechanism shown for D5's per-entry `forgetDocument` reaching the system list or for system-side clearing reaching the bookmark store. Off macOS, D7's "the person can always revoke" reduces to the app's own forget affordance, i.e. revocation controlled by the grant's beneficiary. Meanwhile D4 invites apps to store `doc:` paths as durable references, but D3's bounded LRU silently revokes them by eviction, and whether *using* a kept path refreshes its position is undefined — Exact Draw's workspace folder can fall off while files inside it churn. Change: name the single source of truth and its reconciliation, give every host a revocation surface the person controls without the app's cooperation, and either present kept paths as opportunistic (re-derived from `recentDocuments()` each launch) or add explicit pinning for a workspace — not both promises at once.

3. **What a kept document *is* — its identity across move, rename, and replace — is undefined and contradicts the built containment model.** D4's refreshed bookmark follows the file object to its new location; the built model deliberately does the opposite: a selected file is a leaf name in a retained parent, "not a stable inode identity," and moving a pathname does not redirect it (parent slice 3 "Containment" and "Upstream retained-document adoption"); D3's Linux form, a canonical path, is pathname identity, a third answer; the web handle is a fourth. These disagree exactly on the cases document apps hit constantly, including atomic replace — which is Exact's own `atomicWriteFile`. An app cannot write portable reopen logic, and the security meaning of a kept path differs by host. Change: define identity once, as a small table over move/rename/atomic-replace/delete-and-recreate for files and folders, and show each host's persistence (bookmark, IndexedDB handle, Linux path) expresses that definition within the Q2 sandbox constraint, before D4 is accepted.

4. **Stage 1 solves refresh, not the overwrite problem its motivation promises.** Sections 1–2 sell the watch as showing an external change "instead of overwriting it at the next save," but a coalesced pull (LLP 1016.002 D1/D4) only says "look again" after the fact, fires for the app's own writes, and on browsers without `FileSystemObserver` never fires at all (D2) — while the conditional write that would actually prevent a lost update is deferred in section 8 with the trigger "an app that loses a write." The named consumers are editors that save explicitly (studio, per the parent's "document window"; Exact Draw, per the issue), so the race between `stat` and write is the core risk, not a follow-on. Change: either bring an `If-Match`-style conditional write or version token into stage 1's scope, or explicitly re-scope stage 1 to readers and listings and state that editor data-loss remains unsolved.

5. **The watch topic is too coarse for the folder-scale consumer that motivates it.** D1 defines a watch as "anything beneath the folder" and answers it with a full re-read; rejecting event streams for portability is sound for *values*, but what is lost — *which* path changed — is precisely what makes a large tree under git or sync churn tractable, and the issue records large-folder cost as unmeasured need 3. Authors will build on whatever granularity D1 fixes, so this cannot be tightened later without changing the API's meaning. Change: keep pull for the value (LLP 1016.002's model is right), but fix the topic at the watched file or the watched directory's entries rather than an unbounded subtree, or carry the changed path as a hint alongside the invalidation.

6. **The DEFERRED ask is incomplete as a ruling.** Section 5 proposes moving "durable capability grants" (refused wholesale in [rules/DEFERRED.md](rules/DEFERRED.md:458)) but names no take, which [rules/RULES.md](rules/RULES.md:47) requires (a take or a waiver); its lead consumers, Exact Draw and studio, are external and nowhere admitted as consumers in DEFERRED, and file watching was already named there as a deferred take behind the Markdown editor (DEFERRED, Expanded 2026-09-21), unmentioned here. This is the project's first durable grant and will be cited as precedent. Change: the Charlie ruling should in one decision admit the consumers, name the take or waiver, and write the section 5 fence as an enforceable provenance rule (per finding 1) — before stage 2 builds, not after.

What is right: both problems are real (the issue) and the split and order are correct — a session-scoped watch needing no rule change before any durable grant. The pull/invalidation model of LLP 1016.002 is the right default for values, and a host-owned, platform-persisted kept set behind a stable `doc:` path is the right direction against app-stored, forgeable bookmarks. The narrow "a document the person chose" fence and the declared deviations (`recentDocuments`, `forgetDocument`, like `saveFile` before them) fit the parent's Q2 intent and the project's web-names principle.
