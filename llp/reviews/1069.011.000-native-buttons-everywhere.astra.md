The plan is **not ready to build as written**. D8 can carry state and input across row identities, and D5 does not yet define menu activation consistently across input paths.

This was a read-only audit of the plan at `691b4b5c6` against this checkout. I did not modify files or run builds; citations use checkout line numbers.

For §5:

1. **Keep the two toolbar styles.** Map non-prominent glass to plain and the four prominent styles to prominent. The plan’s API evidence supplies no third toolbar style; inventing one adds behavior without a platform counterpart. [Plan:31](/Users/ccheever/projects/exact2-wt-buttons2/llp/1069.011.000-native-buttons-everywhere.rfc.md:31)
2. **Fix the custom handlerless-invoker quirk too.** Do it through a common default-action path, covering keys and shortcuts as well as pointer activation.
3. **Do not adopt every control kind.** The claim that configuring again reconstructs fresh state is demonstrably false for switches, checkboxes and date pickers. Initially, reuse the surrounding row views while recreating controls.

The findings follow, ordered by severity.

1. **Blocker — D8’s cache reset does not produce a fresh control.**

   `ControlHost.sync` writes switch and checkbox state only when `checked` is present. Reusing a checked control for a node without that prop preserves the previous row’s state. `configureDate` likewise changes the date only when the new value parses successfully; an absent or invalid value preserves the old date. Clearing `written`, `menus`, `reported` and `lastRange` fixes neither case. This violates the binding requirement that a reused view be indistinguishable from a new element. [ControlsIOS.swift:119](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/ControlsIOS.swift:119), [DatesIOS.swift:20](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/DatesIOS.swift:20), [DEFERRED.md:332](/Users/ccheever/projects/exact2-wt-buttons2/rules/DEFERRED.md:332)

   **Change:** Replace “adopts every control kind” with an explicit admission list and a complete reset contract, including absent props. Test checked→absent and date→absent/invalid transitions. Prefer recreating controls for this slice. If adoption remains, identify the concrete kind through `ControlKinds.kind`, since `type="checkbox"` can produce either a switch or a checkbox. [ControlKinds.swift:12](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/ControlKinds.swift:12)

2. **Blocker — D8 can redirect an interaction begun on one row into its successor.**

   Pool eligibility checks the `NodeView`’s pressed, focus and editing state, but not the owned `UIControl`’s tracking or presented interaction. Native-button callbacks consult the button’s current owner; switch and range callbacks consult the sender’s current tag. Rebinding those fields during an interaction can deliver its completion to the new row. Range configuration even deliberately preserves the current value while tracking. [NodePoolIOS.swift:307](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/NodePoolIOS.swift:307), [NativeButtonsIOS.swift:81](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/NativeButtonsIOS.swift:81), [ControlsIOS.swift:160](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/ControlsIOS.swift:160), [RangeIOS.swift:17](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/RangeIOS.swift:17)

   **Change:** Define control-specific retirement eligibility. Tracking controls and controls owning open menus/pickers must not be adopted. Invalidate outstanding callbacks using the pool’s incarnation mechanism; changing tags and weak owners is insufficient. Add a test that destroys a row between interaction start and completion and proves neither its old action nor its successor’s action fires.

3. **Blocker — D5 lacks a single owner for invoker activation.**

   Attaching an action to `NSButton` or a menu to `UIButton` does not cover the node’s keyboard path. Apple Enter/Space handling and macOS shortcut discovery still require a `press` handler. Thus a handlerless native invoker can work by pointer and fail by keyboard or shortcut. Conversely, literally implementing “press, then open” on macOS risks opening twice: `Presenter.press` already calls `menus.pressed`. [NodeViewIOS.swift:289](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift:289), [NodeViewMac.swift:217](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/Mac/NodeViewMac.swift:217), [ShortcutsMac.swift:53](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/Mac/ShortcutsMac.swift:53), [PresenterMac.swift:684](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/Mac/PresenterMac.swift:684)

   **Change:** Specify one default-action routine for custom and native invokers. Preserve the originating invoker separately from any ancestor handler target; run the applicable handler once, revalidate after its mutation, then perform the default action once. Route pointer, keyboard, shortcut and agent activation through that contract.

4. **Should-fix — Ordinary menus and confirmations need different attachment behavior.**

   D5 describes assigning a deferred `UIMenu` to the native button for both `popovertarget` and `commandfor`. Existing confirmations instead use a separate `.touchUpInside` action with `menu=nil`, then call `openConfirmation`. Merely replacing the ordinary-menu overlay leaves the confirmation overlay—and therefore the second control—intact. Existing cleanup also removes overlay views; it does not detach behavior from a surviving native control. [MenusIOS.swift:89](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/MenusIOS.swift:89), [MenusIOS.swift:132](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/MenusIOS.swift:132), [MenusIOS.swift:239](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/MenusIOS.swift:239)

   **Change:** Define three native-control states: ordinary activation, menu invocation and confirmation invocation. Specify attachment, replacement and removal of each named action, restoration of ordinary activation, and cleanup on target removal, destruction and pooling. Test a **native confirmation invoker**, not just native confirmation rows.

5. **Should-fix — D5 overstates `commandfor` support and leaves Linux’s refusal incomplete.**

   AppKit explicitly refuses dialog commands; they are not another supported menu-opening path. On Linux, `popover_invoker` checks only `popovertarget`, while the `commandfor` refusal examines only the eventual dispatched view. Pointer handling resolves an ancestor press handler before dispatch, so a handlerless native command invoker can miss that refusal and run an ancestor action. Updating only the node-kind test in `navigation.rs` does not fix it. [MenusMac.swift:51](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/Mac/MenusMac.swift:51), [navigation.rs:9](/Users/ccheever/projects/exact2-wt-buttons2/host/linux/src/navigation.rs:9), [surface_controls.rs:515](/Users/ccheever/projects/exact2-wt-buttons2/host/linux/src/surface_controls.rs:515), [host.rs:747](/Users/ccheever/projects/exact2-wt-buttons2/host/linux/src/host.rs:747)

   **Change:** State the supported presentation matrix explicitly. Preserve AppKit’s dialog refusal. On Linux, detect unsupported commands at the originating invoker before application dispatch, including handlerless invokers inside pressable ancestors.

6. **Should-fix — Copying the deferred-menu implementation preserves a known lifecycle risk.**

   Ordinary iOS menus are replaced every sync, invoke the handler from their deferred provider, then wait 80 ms before reading rows. But `Session.onPress` applies the batch synchronously, and confirmation code already relies on that fact. The handler can therefore trigger another menu replacement while the original provider is resolving. LLP 1021 records an unresolved loading-menu failure and specifically identifies replacement on every batch as a possible, unproven contributor. [MenusIOS.swift:118](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/MenusIOS.swift:118), [Session.swift:668](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/Session.swift:668), [MenusIOS.swift:245](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/MenusIOS.swift:245), [LLP 1021:301](/Users/ccheever/projects/exact2-wt-buttons2/llp/1021-menus.rfc.md:301)

   **Change:** Keep the attachment stable while the invoker/target relationship is unchanged. Read rows after the completed handler batch, without the elapsed-time guess, and reject retired invoker/target incarnations. Test repeated opening and handlers that remove, disable or retarget the invoker.

7. **Should-fix — D1 needs an explicit textual fallback for symbol-only faces.**

   A native button may legally contain only a symbol and an `aria-label`. Its kernel title is then absent. D5 and D7 nevertheless request its “title” for menu, confirmation and shortcut entries. Confirmation actions consume a textual title directly, so following the plan literally can produce an unnamed action despite a valid accessible label. [Parent RFC:66](/Users/ccheever/projects/exact2-wt-buttons2/llp/1069.011-native-buttons.rfc.md:66), [Plan:45](/Users/ccheever/projects/exact2-wt-buttons2/llp/1069.011.000-native-buttons-everywhere.rfc.md:45), [MenusIOS.swift:265](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/MenusIOS.swift:265)

   **Change:** Define the fields’ semantics and each projection’s fallback: textual platform entries use `title ?? label`; accessible names use `label`; image-only segments remain image-only but carry the label. Include symbol-only menu, confirmation and shortcut cases.

8. **Should-fix — D4’s tab migration requires more than a shared face reader.**

   `SegmentFace.image` currently contains a real `NodeView`; custom eligibility deliberately rejects badges, mixed content and text whose accessible name differs. `TabBarFace` also takes tint from the child image. Native faces have neither child views nor that tint source. Furthermore, iOS segments sync **before** native controls, while segment rendering reads `accessibleName`, whose native title currently comes from the control’s last-written configuration. That path can show stale text even after adding a kernel-backed face reader. [Accessibility.swift:36](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/Accessibility.swift:36), [SegmentsIOS.swift:39](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/SegmentsIOS.swift:39), [SegmentsIOS.swift:109](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/SegmentsIOS.swift:109), [PresenterIOS.swift:808](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/PresenterIOS.swift:808), [Accessibility.swift:10](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/Accessibility.swift:10)

   **Change:** Preserve projection eligibility separately from face extraction. Add a native-symbol representation without fabricating child views, define native tab tint from `accent-color`, and make rendering consume current kernel face data. Test mixed custom/native tabs, authored fallback, dynamic titles and unavailable symbols.

9. **Should-fix — Admitting new roles breaks assumptions outside projections.**

   Linux focusability and Enter/Space activation rely on role `button` or `link`; native buttons newly carrying `tab` or menu-item roles lose those paths. Apple’s agent accessibility enrichment similarly recognizes kind `button` or role `button`/`link`, so a native `control` under the new roles loses its reported accessible name. [surface_controls.rs:454](/Users/ccheever/projects/exact2-wt-buttons2/host/linux/src/surface_controls.rs:454), [typing.rs:205](/Users/ccheever/projects/exact2-wt-buttons2/host/linux/src/presenter/typing.rs:205), [Accessibility.swift:211](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/Accessibility.swift:211)

   **Change:** Include these consumers in D1’s audit. Button activation identity must recognize `Control(type=button)` independently of its accessibility role. Test keyboard activation and accessible names under every newly admitted role, including authored fallback.

10. **Should-fix — Glass-to-glass adoption misses re-registration.**

    D8 tears down the glass slot, but its reset list omits `isGlass`. Native configuration calls `syncGlassSlot` only when that Boolean changes. Reusing a glass button as another glass button therefore does not necessarily register the new owner with the glass pass; clearing `written` alone does not trigger that branch. [Plan:53](/Users/ccheever/projects/exact2-wt-buttons2/llp/1069.011.000-native-buttons-everywhere.rfc.md:53), [NativeButtonsIOS.swift:147](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/NativeButtonsIOS.swift:147), [GlassGroup.swift:263](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/GlassGroup.swift:263)

    **Change:** If adoption survives, explicitly re-register after mounting under the new owner, independently of appearance changes. Test glass→glass reuse across different groups, plus glass→non-glass transitions and eviction.

11. **Should-fix — D6 understates the swipe-body input risk and omits action-image bookkeeping.**

    The existing scroll host explicitly cancels touches in `NativeButtonIOS` so a pan wins. Swipe projection instead creates a plain `UITableView`; “UIKit’s ordinary case” is not evidence that dragging from a native button inside the body behaves correctly. Separately, swipe-action discovery uses a stored image map to locate and name UIKit’s rendered buttons; assigning a symbol only to `UIContextualAction.image` omits that path. [ScrollViewIOS.swift:29](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/ScrollViewIOS.swift:29), [SwipeActionsIOS.swift:177](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/SwipeActionsIOS.swift:177), [SwipeActionsIOS.swift:337](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/SwipeActionsIOS.swift:337), [SwipeActionsIOS.swift:359](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/SwipeActionsIOS.swift:359)

    **Change:** Preserve image bookkeeping for symbol actions. Require real-touch tests starting on the body’s native control: tap, horizontal swipe and vertical scroll, with no accidental activation. Verify one accessibility owner and reachable swipe actions.

Use the existing five checks and test infrastructure.
