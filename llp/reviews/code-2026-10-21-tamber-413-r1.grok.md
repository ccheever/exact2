1. **SHOULD-FIX** — The 5s destroy starts before the response exists, so a remote over-limit request can still be reset. `scripts/tamber-request.mjs:13`

`refuseBody` arms `setTimeout(..., 5000)` immediately, then calls `answer()`. On the shared `readBody` path `answer` is a no-op: the handler writes the 413 only after `readBody` resolves. For a remote door that write is after `await ready`:

```534:539:scripts/tamber-server.mjs
    const early = access.remote ? body(req, res) : null;
    await ready;
    if (res.destroyed || res.writableEnded) return true;
    const text = await (early ?? body(req, res));
    if (text == null) { json(res, 413, { error: { message: 'a request is at most 1 MiB' } }); return true; }
```

`ready` is the compiler hello (`refresh()`), and a cold start is allowed to take far longer than 5s — that is why the body is read early. A `Content-Length` over the limit calls `refuseBody` synchronously at the start of that early read, so the timer is already running through `await ready`. At 5s `req.destroy()` runs, line 537 sees `res.destroyed`, and the client gets a reset again.

The same pause skips `req` `'end'`, which is the only thing that stops the remote deadline (`scripts/tamber-remote.mjs:273`, 10s from accept, not restarted for a late head). An over-limit body therefore keeps that deadline armed across `await ready` and across the drain. Whichever of the 5s timer and the remaining deadline fires first cuts the socket. After `ready` has already settled, a content-length refusal writes the 413 on the next turn, so the steady state is fine. Pairing, canvas, and `forward` write inside or immediately after `refuseBody`, so they do not hit this gap.

The timer is cleared only from `'end'` (`scripts/tamber-request.mjs:17`). It does not leak: it is `unref`'d, fires once, and a close that never emits `'end'` (Bun closing on `connection: close`, the remote deadline, a reset) just means `destroy` runs again at 5s. The drain listener discards bytes, so a slow drip after refusal cannot hold a socket or grow memory past that 5s. Chunked refusals do keep the chunks already read (up to the limit) until that destroy. Listeners die with the request.

2. **SHOULD-FIX** — `null` is both "over the limit" and "client left", and `forward` answers both with 413. `scripts/tamber-server.mjs:1426`

`readBody` resolves `null` on `'error'` and `'close'` (`scripts/tamber-request.mjs:38`) as well as on the limit. A normal body is safe only because `'end'` settles first and `'close'` is then ignored. `forward` does:

```1425:1426:scripts/tamber-server.mjs
    const bytes = req.method === 'GET' || req.method === 'HEAD' ? null : await readBody(req, BODY_LIMIT, res, true);
    if (bytes === null && req.method !== 'GET' && req.method !== 'HEAD') { if (!res.destroyed) json(res, 413, { error: { message: 'a request is at most 1 MiB' } }); return true; }
```

If the client drops mid-body and the response is still writable, it is told the body was over 1 MiB. If `res` is already destroyed, the 413 is skipped and nothing is forwarded — that part is right. Upstream failure is unchanged: a failed `fetch` still becomes 502, or is dropped when the client abort has already fired `gone`.

The main wire has the same conflation at `scripts/tamber-server.mjs:539` (that line is older): any `null`, including a client that left during the read, is written as 413 whenever the socket still accepts it. Pairing is the intended collapse: `parse((await body(req, res)) ?? '')` at `scripts/tamber-server.mjs:655` is 400 for over-limit, gone, and bad JSON, and an over-limit body still goes through `refuseBody` first so the 400 is a lingering close rather than a reset. Canvas does not conflate them. Its own `readBody` returns `{over}` or `{gone}`; both call sites (`scripts/tamber-canvas.mjs:416` and `:533`) pass an answer, so the new `refuseBody` drains those the same way.

3. **SHOULD-FIX** — GET and HEAD skip the limit and are not consumed. `scripts/tamber-server.mjs:1425`

Previously the proxy read every method, refused past the limit, and only then omitted the body for GET/HEAD. Now a GET/HEAD never calls `readBody`, so a `Content-Length` over the limit still opens the upstream `fetch`, and the unread body is left on a keep-alive connection (the success path does not send `connection: close`). A normal GET/HEAD with no body still proxies correctly.

4. **NIT** — The 5s fallback is not what the tests run, and that is acceptable. `scripts/tamber-body-limit.test.mjs:70`

The suite does lock the contract that matters: announced and chunked bodies on both the wire and `--via` get the 413 JSON, `connection: close`, and a closed socket, the next request succeeds, and `--via` shows `connections === 0` before any upstream byte. The raw socket that announces an over-limit length and then stops only checks that the close happens within 7s, so an instant Bun close and the 5s timer both pass. That matches this runtime. A regression that deleted the timer would still pass here. Remote, pairing, canvas, GET/HEAD, and a client that leaves mid-read are untested. The assertions that are there are ordered tightly enough not to flake: each `send` waits until that socket closes before the next request.
