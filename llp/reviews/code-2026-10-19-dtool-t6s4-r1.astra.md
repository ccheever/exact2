1. **SHOULD-FIX — Another window on the canvas origin can acknowledge the wrong entry.** [pairing.ts:48](/tmp/rv-dt-t6s4/apps/design-tool/pairing.ts:48) checks the message type and exact origin, including scheme and port, but neither `event.source` nor an entry identifier. A canvas-origin popup holding a reference to the tool can keep posting the word while a new entry is pending. The tool then drops that new grant and navigates to `/`, potentially aborting its POST and showing 404 without a session. A same-origin opener, another referenced tab, or a non-entry page can do likewise. The framed app can also send the word; after its own successful entry that is harmless, but its messages are not bound to that attempt. Other origins cannot pass the check. **This permits entry disruption, not grant disclosure or creation of a gateway session.** Bind acknowledgement to the mounted frame and current attempt.

2. **NIT — Successful cleanup retains the grant in module memory.** [pairing.ts:46](/tmp/rv-dt-t6s4/apps/design-tool/pairing.ts:46) and the listener retain the complete grant URL in both `minted.frame` and `entered`. Returning `minted.root` does not clear either; minting another canvas also leaves the previous `entered` value. Successful cleanup does remove the grant from `canvasAt.frame`, iframe `src`, and consequently agent `state`/`tree`. These remaining private references contain a spent grant after genuine entry, so this is unnecessary retention rather than a live credential leak. Keep a non-secret completion identifier and discard the grant-bearing URL.

3. **SHOULD-FIX — Reload can leave the grant permanently in state and `src`.** [app.contract:687](/tmp/rv-dt-t6s4/apps/design-tool/app.contract:687) passes only `canvasIn.entered` into `loadCanvas`, while [canvasEntered](/tmp/rv-dt-t6s4/apps/design-tool/pairing.ts:78) ignores its tick argument. After one successful entry, Reload Canvas asks `canvasEntered` before the new mint finishes, obtaining the previous canvas’s `true`. If the new entry succeeds before the first poll, subsequent polls also return `true`: no argument changes, so `loadCanvas` never returns the clean root. An in-memory probe confirmed this sequence. Conversely, a slow entry can produce `true → false`, invoking the asynchronous cached load and [unmounting the iframe while entry is underway](/tmp/rv-dt-t6s4/apps/design-tool/app.contract:1412). Completion must belong to the current canvas key; resetting it must not recreate an unchanged entry frame.

4. **SHOULD-FIX — An obsolete mint reply can defeat the one-grant-per-key rule.** [pairing.ts:69](/tmp/rv-dt-t6s4/apps/design-tool/pairing.ts:69) awaits the request and then unconditionally replaces `minted`. Start a mint, then rename and Continue while it is pending: that starts another tick’s mint. If the newer reply arrives first and the older reply last, the older one overwrites the cache even though the resource runtime discards its obsolete answer. The current canvas’s acknowledgement can then cause another mint for its already-minted key. A controlled probe produced three requests for two keys. Track in-flight minting and reject obsolete completions before updating the cache.

5. **SHOULD-FIX — A new server epoch inherits the previous entry’s depleted poll budget.** [watchCanvas](/tmp/rv-dt-t6s4/apps/design-tool/app.contract:822) correctly limits timer firings to 40 per tick. However, only Reload Canvas and Continue replenish that budget. After 39 unsuccessful polls, restart the server and re-pair: the changed client/epoch mints a fresh grant, but only one poll remains. If entry takes longer than that, its acknowledgement changes module memory without triggering resource cleanup. At zero, it receives no polls. Give each new client/server-run attempt its own bounded budget.

The [new test](/tmp/rv-dt-t6s4/scripts/design-tool-scope.test.mjs:144) covers wrong-origin/type rejection and first-entry cleanup, but manually calls `loadCanvas` and reads the next tick only after minting finishes. It therefore misses the reactive ordering above, overlapping replies, and epoch/budget transitions. Ordinary mint failures remain explicitly retryable because Try Again increments the tick.
