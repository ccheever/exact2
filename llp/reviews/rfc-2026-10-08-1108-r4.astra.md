1. **BLOCKER — D2/D3: authorization must fence publication, not just the next lookup.** A download can start, a round can observe `E_AUTH`, and the successful download can then publish a kept file: `asset_home` checks rows, not sessions. The draft’s [asset_reply](/Users/ccheever/projects/exact2-wt-laneD/snapback4/client/src/media.rs:298) demonstrates this gap. Furthermore, [untrusted](/Users/ccheever/projects/exact2-wt-laneD/snapback4/client/src/client.rs:354) reads the last round’s refusal; another refusal or reopening can erase that protection without a successful round. Specify a partition authorization state that survives until successful revalidation, fences outstanding downloads, and is checked before publication. A known revocation must not become permission to write a transient file. Add D8 tests for these interleavings.

2. **MAJOR — D7: waiting for refresh does not guarantee adoption of the new bearer.** [`refreshSession()`](/Users/ccheever/projects/exact2-wt-laneD/snapback4/ts/snapback.ts:684) returns the session for its caller to install, while download waiters resume from the partition’s internal promise. An in-memory probe reproduced `credentials()` reading the **old** token even when the caller immediately adopted the returned session. Specify one session owner per partition and complete adoption before releasing refresh waiters—through shared credentials or an awaited adoption callback. Test two clients sharing the partition, including the retry after rotation.

3. **MAJOR — D2 “Time” contradicts D3’s open and expiry guarantees.** Using the last asset call’s `now` means repeated rounds can check against an indefinitely old timestamp. Before the first asset call, nothing is checked at all, despite D3 promising checks at open and purging a previous cache under `keep: "none"`. The draft [defers initialization accordingly](/Users/ccheever/projects/exact2-wt-laneD/snapback4/ts/snapback.ts:484). Give opening and maintenance explicit epoch-time inputs, with a Contract-driven maintenance call for expiry; perform time-independent policy and orphan cleanup at open. Test reopening without subsequently requesting an asset, and expiry while only maintenance/sync runs.

4. **MAJOR — D2/D4.5: invalidating exchanges does not cover an upload already persisting facts.** Close or clear can occur after `upload_reply` consumes its exchange but before the public upload promise settles. D4’s second check covers credential refresh, not those lifecycle changes. A probe holding the device reply reproduced `upload()` returning success after `close()` completed. Specify a lifecycle check covering persistence through public settlement; interrupted uploads must attempt `forget_upload_facts`, and close must await that cleanup. Add the post-persistence interruption test to D8, including cleanup failure.

5. **MAJOR — D3/§4: the four-line `appURL` change leaves released transient bytes alive.** [`appURL`](/Users/ccheever/projects/exact2-wt-laneD/host/web/picker-glue.js:35) revokes a deleted file’s object URL only when that exact path is resolved again. Each transient answer now has a unique path, so released files commonly never trigger that check. Their Blobs remain reachable through the URL map for the page’s lifetime, accumulating across refreshes. Specify revocation on file invalidation or display-handle release, including clear and close. Test repeated transient display/release without resolving old paths again.

6. **MAJOR — D2/D3: a kept answer has no usable lifetime guarantee.** With a cap holding one asset, concurrently requesting two different assets can return A’s path, publish B and evict A, then settle the containing resource with both paths. A disappears before its image ever loads. The queue guarantees existence during an individual operation, not until the consumer reads the file. Define ownership through `release()` for returned handles—pinning or transient backing when necessary—and explain its interaction with the cap. D8’s same-asset concurrency test misses this; add different assets exceeding the cap in one resource answer.

7. **MAJOR — D6/§4 slice 2: direct-to-file fetching lacks the admission step D2/D5 require.** `exactSaveTo` writes before the core sees headers, whereas D5 forbids writing any response marked `accept-ranges: none`, regardless of status. It also empties the body readers needed to recognize `E_ASSET_RANGE` and other JSON refusals. Specify header-gated file writing, preserved refusal bodies and actual byte counts, then unique staging files published inside the media queue after core approval. Cover stale completions and staging cleanup. An unconditional save followed by inspection cannot satisfy the stated guarantees.
