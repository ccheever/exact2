SOUND WITH CHANGES

1. **Major — D3's second Keychain group does not keep existing `secret.keep` items.** Simulator items are stored under the bare bundle id, which is today's whole `application-identifier` (`host/apple/build.mjs:308`). `vendor/ibex2/src/engine/darwin_keychain.mm:53-58` never sets `kSecAttrAccessGroup`, and `set` updates that same query, then adds if it is missing (`:101-111`). An unqualified operation uses only the default group, the first `keychain-access-groups` entry. After this change that is `SIMULATORX.<bundle id>`, so old items are invisible and the next `set` creates a second item there. A bare bundle id is also not a legal access group once the application-identifier prefix is `SIMULATORX` (every group has to carry that prefix); the simulator often fails those `SecItem` calls outright. This runs for every simulator build, not only Health apps. A 10-character prefix is what HealthKit's team-id split needs — the bare id `com.exact.test` (`scripts/app.test.mjs:1270`) splits as a 3-character prefix, the same class of misattribution as a 9-character `SIMULATOR.` — but listing the old id second does not preserve secrets.

2. **Major — D4 refuses the profile this tree actually signs with, and the remedy does not produce another one.** `profile()` accepts a team wildcard and then picks the latest expiry (`host/apple/devices.mjs:188-189`). That wildcard is the normal device profile (LLP 1008: a profile Xcode already installed for any app of the team). HealthKit cannot be turned on for a wildcard App ID, so the check fires on a default `--device` build. Creating an explicit HealthKit profile and downloading it again still loses to a newer wildcard. The build needs an explicit App ID profile, and `profile()` has to prefer it.

3. **Major — D1's own App Store rule is only applied to a read grant.** The draft says a binary that carries `com.apple.developer.healthkit` must contain both purpose keys, then only synthesizes `NSHealthUpdateUsageDescription` from a lone `device.health-read`. A lone `device.health-write` still takes the same entitlement (D2) and, through the existing one-key rows (`runner/src/device.rs:128-132`, `bake/src/reach.rs:135-136`), writes only `NSHealthUpdateUsageDescription`. Under that rule the write-only binary is rejected the same way. The filler also has to be the purpose's locale map, which is what `reach.usage` stores (`bake/src/reach.rs:136`); a single base string makes `usageKeys` (`host/apple/build.mjs:330`) drop it.

4. **Major — D7 does not keep an existing Health answer off disk or off the next first frame.** `keeps_answers` only gates new writes (`runner/src/runner/kept.rs:137-140`). Cold-boot seeding still loads `exact.kept.<resource>` for every reader and does not look at that flag (`runner/src/runner.rs:939-978`). `obsolete` forgets an entry only when nothing in the plan still reads it (`runner/src/runner/kept.rs:26-37`, forgotten at `runner/src/runner.rs:760-768`), which is the case the draft already sets aside. A Finder resource that remains a reader keeps `exact.kept.finderState` in the kv files (`host/apple/src/store.rs:20-23`) and paints it again. The rule needs to skip that seed and `forget_kept` the existing keys (a `None` write deletes the file, `host/apple/src/store.rs:261-262`).

5. **Major — D5's "macOS returns unavailable" premise is wrong, so the empty Mac derivation leaves a live Health call with no purpose string.** On macOS 13 and later `HKHealthStore.isHealthDataAvailable()` is true on a Mac that supports Health. It checks the OS, not the entitlement. The same Swift module then calls `requestAuthorization` without `NSHealthShareUsageDescription` or `com.apple.developer.healthkit`. HealthKit throws if the purpose key for the direction you request is missing. D5 derives neither the keys nor the entitlement on the macOS bake, which is what `macReleaseEntitlements` signs (`host/apple/build.mjs:352-358`).

6. **Minor — D5's tvOS exclusion cannot be done where D2 puts the column.** `--tvos` is baked as platform `ios` (`host/apple/build.mjs:631`, `:853`). Collecting `ios_entitlements` when `platform == "ios"` puts the HealthKit entitlement and usage strings on the Apple TV simulator binary.

D2 matches the code. `derive` is already per platform and only macOS fills `reach.entitlements` today (`bake/src/reach.rs:130-142`), and `entitlements()` is what both the simulator `__entitlements` section (`host/apple/build.mjs:1117-1119`) and the device signature (`:1332-1343`) write. A boolean `com.apple.developer.healthkit` can go through that field.
