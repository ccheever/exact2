**1. Verdict: RIGHT WITH CHANGES**

**2. Overall assessment**

An explicitly declared open grant is the right direction. It addresses a real federation requirement while preserving immutable grants and keeping protocol-specific discovery in the app. The significant architectural problem is the promised **public-internet boundary**: the proposed hostname filter does not establish one, and the grant also reaches server-side rendering.

**3. Concerns**

- **MAJOR — “Public HTTPS only” needs a destination policy, not a hostname rule.**

  [D1](/Users/ccheever/projects/exact2-review-1114/llp/1114.009-origins-learned-at-run-time.rfc.md:198) admits any multi-label DNS name on HTTPS port 443, describes that as public-internet access, and defers native DNS-rebinding protection. But a qualifying hostname can resolve directly and permanently to a private address; rebinding is unnecessary. HTTPS authenticates the hostname, not the destination’s public routability.

  The current [native connector](/Users/ccheever/projects/exact2-review-1114/vendor/ibex/crates/ibex2/src/transport/rustls_http.rs:253) attempts the resolved addresses without an address-space restriction. More significantly, [anonymous rendering preserves every `net.fetch` grant](/Users/ccheever/projects/exact2-review-1114/host/render/src/source.rs:19), and its [executor uses the same transport](/Users/ccheever/projects/exact2-review-1114/host/render/src/executor.rs:26). Consequently, this change would also authorize requests to internal HTTPS services from the rendering server when an app follows externally supplied discovery information during rendering. The RFC discusses that server’s CSP, but misses its outbound authority.

  This matters to the stated consumer: AT Protocol explicitly warns clients and providers about discovery URLs whose hostnames resolve to internal addresses. Browser Local Network Access likewise evaluates actual destination addresses, rather than hostname spelling. [AT Protocol security considerations](https://atproto.com/specs/oauth#security-considerations), [Local Network Access](https://wicg.github.io/local-network-access/#dns-rebinding).

  **Resolution:** Decide whether private-network destinations are authorized. If the grant must mean public-only, native enforcement belongs at the connection boundary, covering resolved destinations and redirects, including the render executor; that work cannot remain excluded from scope. If broader reach is intentional, Charlie should approve it explicitly, with a separate decision about server rendering. The “about a day” estimate should follow that decision.

**4. What it gets right**

The proposal chooses the appropriate layer: extend network authority without teaching the executor AT Protocol. Keeping grants fixed, callbacks exact, source scopes intact, and WebSockets outside this admission is sensible. Extending `auth.session` alongside fetch addresses the complete sign-in path. A conspicuous reach-table entry and the existing binary-release classification are appropriate; another deployment acknowledgement would add little.

**5. Questions for Charlie**

- **Does this grant authorize private-network HTTPS destinations?** The current questions present hostname spelling and port restrictions as though they answer that. I recommend retaining the public-only intention and including the native transport work required to enforce it.
- **Should anonymous rendering automatically inherit the open grant?** I recommend withholding that inheritance until its destination restriction is enforced, or explicitly admitting the broader server authority.
- **What browser guarantee is being approved?** D3 promises every-hop admission, but [LLP 1071 already records](/Users/ccheever/projects/exact2-review-1114/llp/1071-exact2-web-target.rfc.md:1735) that browser admission checks the final response after intermediate destinations have been contacted. Accepting that existing browser limitation is reasonable; it must inform the authority decision rather than count as protection equivalent to native admission.
