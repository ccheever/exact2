1. **MATERIAL — D5, lines 265–302; D18, lines 699–709: the new grant exposes the render operator’s network.** `host/render/src/source.rs:25–38` removes scheme-wide grants but retains `net.fetch local-network`. That retained grant reaches the render executor, which uses rustls without a private-address restriction (`host/render/src/executor.rs:26–54`). Once the proposed parser accepts it, a source whose destination depends on route input can reach the server’s internal services. LLP 1114.009 D5 explicitly withholds broad grants from renders for this reason. **Decision needed:** withhold `local-network` from render environments and defer those reads to client adoption, or specify an equivalent protective boundary.

2. **MATERIAL — D6, lines 343–354; D16, lines 662–666: runner admission misses redirected connections.** Native redirects proceed below the runner: `fetch_async.rs:356–394` starts each hop after `fetch.rs:430–444` checks its network grant. A tool-origin request under `net.fetch http:` can start at a public server and follow a redirect to `http://192.168.1.40/`, opening Apple’s alert despite passing the initial guard. This needs neither DNS rebinding nor the declared unicast-name exception. **Decision needed:** preserve causal origin and enforce permission admission before every redirect connection; define the corresponding browser behavior where intermediate hops are hidden.

3. **MATERIAL — D6, lines 348–352; D9, lines 431–437: Android’s proposed preflight contradicts its exemption.** D6 permits Android tool/wake reaches because denied sockets do not themselves prompt. D9 nevertheless makes exact2 call `Activity.requestPermissions` before a foreground local reach on API 37. A tool invocation in a foreground app therefore reaches a permission dialog created by the host. Android’s documentation distinguishes requesting permission from attempting the blocked connection. **Decision needed:** include Android API 37 in origin admission whenever the host’s preflight can ask. [Android local-network permission](https://developer.android.com/privacy-and-security/local-network-permission)

4. **MATERIAL — D6, lines 343–348; D10, lines 450–455: the existing `Device` origin escapes the guard.** `runner/src/runner/modules/events.rs:10–13` explicitly gives package-emitted events device origin so that requests they cause cannot prompt. D6 repeatedly restricts only tool and wake origins. A foreground package event can consequently cause a first local fetch that opens system UI. **Decision needed:** carry the inherited restriction across every non-App origin, while retaining App origin for actual platform activations.

5. **MATERIAL — D4, lines 246–254; D6, lines 334–360; D8, line 407: private address ranges cannot serve as Apple’s permission oracle.** Apple defines local addresses by directly connected, broadcast-capable interfaces, independently of RFC 1918/ULA ranges. A public IPv4 or global IPv6 address on the LAN can therefore prompt while escaping D6. Conversely, success against a routed private address, VPN destination, or exempt DNS-server address does not establish local-network permission, yet the proposed evidence rule can record `granted` and admit a subsequent prompting tool reach. The address-based native `host` also makes globally addressed LAN services fail D5’s grant. **Decision needed:** separate grant membership, prompt-risk classification, and valid permission evidence; explicitly handle globally addressed peers. [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)

6. **MATERIAL — D2, lines 170–190; D3, line 219: service identity loses the network.** Two different links may legitimately contain different devices named `Desk._wled._tcp.local.`. The proposed `(name, type)` identity merges them into one row, and `resolveService` cannot identify which device the person selected. This can send a control request to the wrong device. RFC 6762 expressly permits duplicate names across links and describes interface-aware queries. **Decision needed:** preserve network-scoped identity through resolution and connection, or explicitly restrict discovery to one network and reject ambiguity. [RFC 6762 §14](https://www.rfc-editor.org/rfc/rfc6762.html#section-14)

7. **MATERIAL — D5, lines 287–309; D8, line 412; §10, lines 838–841: the web combines distinct address spaces and permissions.** `targetAddressSpace: "local"` is prescribed even for development loopback fixtures. The cited specification rejects a resolved address whose space differs from that option, so those loopback drives cannot work as specified. Separately, Chrome split `local-network` and `loopback-network` permissions: a granted LAN fact does not establish loopback permission. Production D6 also excludes literal loopback from its classifier, although an explicitly granted loopback origin can prompt. **Decision needed:** use the destination’s appropriate permission and address-space behavior, including explicit loopback grants and development fixtures. [LNA fetching rules](https://wicg.github.io/local-network-access/#fetching), [Chrome 145 permission split](https://developer.chrome.com/blog/chrome-145-beta)

8. **MINOR — D8, lines 407–421; D10, line 452; D11, lines 464–466: recovery from cached Apple denial is unresolved.** Consider a macOS app using only a typed address: its denied fetch finishes, the person enables access in Settings, and the same process retries. There is no ongoing browse to supply the positive evidence D8 describes. If the inherited immediate refusal for `denied` applies, recovery is blocked; if foreground fetches bypass cached denial, D10 needs to say so. **Decision needed:** define an explicit foreground revalidation or retry transition.

9. **MINOR — D5, lines 272–294: the production loopback assurance exceeds the chosen namespace boundary.** Ordinary mDNS can advertise a `.local` name pointing to `127.0.0.1`; this does not require enterprise unicast DNS. Avahi’s project discussion documents both publication and resolution from another machine. Under D5’s chosen URL-only semantics, that name remains admitted. **Decision needed:** describe the production exclusion as excluding loopback literals, and explicitly disclose loopback through admitted names—or choose a stronger destination boundary. [Avahi issue #40](https://github.com/avahi/avahi/issues/40)

10. **MINOR — D7, lines 370–374: Android’s manifest derivation contradicts current guidance.** Android says apps targeting SDK 36 or lower should neither declare `ACCESS_LOCAL_NETWORK` nor request it. D7 postpones only the runtime request while adding the declaration unconditionally. **Decision needed:** gate both on the target SDK. [Android guidance](https://developer.android.com/privacy-and-security/local-network-permission)

11. **IMPLEMENTATION-PHASE — D5, lines 304–312; D16, lines 667–671: served-page CSP needs integration.** `host/render/src/serve.rs:1449–1468` emits connection sources only for scheme sources or URL-shaped targets. It emits nothing for `local-network`, leaving served Lights pages with `connect-src 'self'` and blocking their WLED requests. **Decision needed:** specify the CSP envelope for this source and disclose any broader browser allowance required alongside runtime admission. Updating only the browser validator and JS fetch options is insufficient.

Part 2 — New findings and defects in the revised decisions.

1. **IN-DELTA · MATERIAL — D6, lines 433–437: the browser redirect exception still contradicts the inherited origin rule.**

   R2 explicitly permits a tool’s public HTTPS fetch to redirect to a local HTTPS destination and open Chrome’s prompt. LLP 1133 D6 rule 3, lines 349–355, says tool invocations never open system UI.

   Hidden intermediate URLs prevent inspecting each destination; they do not require following redirects. Fetch’s `redirect: "error"` stops instead, and `host/web-js/admission.js:59–65,109` already supports that mode. [Fetch Standard, HTTP fetch](https://fetch.spec.whatwg.org/#http-fetch).

   **Decision needed:** choose a conservative redirect policy for restricted origins while permissions are uncertain, or explicitly amend the inherited guarantee. Calling the behavior a declared limit leaves that contradiction unresolved.

2. **IN-DELTA · MATERIAL — D6, lines 400–415; D8, line 492: loopback admission still consults the wrong permission.**

   Consider `local-network=granted`, `loopback-network=prompt`, and a tool fetching an explicitly granted loopback origin. D6’s destination test finds prompt risk, but its operative refusal requires the host’s LAN fact to be *not granted*. That condition is false, so the request proceeds and can prompt.

   D8 explicitly says the fact does not report loopback permission. Chrome’s two permissions are independent. [Chrome 145 permission split](https://developer.chrome.com/blog/chrome-145-beta#local_network_access_split_permissions).

   **Decision needed:** make admission depend on the destination’s relevant permission, without a bypass through the LAN fact.

3. **IN-DELTA · MATERIAL — D6, lines 400–405: the web classifier misses ordinary prompting destinations.**

   The classifier uses private literals and `.local` names. A tool’s fetch of `https://nas.example`, consistently resolving to `192.168.1.40`, escapes it despite being permission-gated by the browser. This requires neither redirects nor DNS rebinding: browser classification uses the resolved address. [WICG LNA fetching rules](https://wicg.github.io/local-network-access/#fetching).

   The public-page-only condition also misses local-page-to-loopback requests, which Chrome documents as permission-gated. [Chrome’s current LNA release notes](https://support.google.com/chrome/a/answer/10314655?hl=en).

   **Decision needed:** define conservative admission when the runtime cannot observe browser address classification, and cover local-to-loopback transitions.

4. **IN-DELTA · MATERIAL — D8, line 492: rejection of a permission descriptor does not establish that requests cannot prompt.**

   The row concludes that a rejected `local-network` query means no reach has prompt risk. Chrome 142 shipped prompting before Chrome 145 introduced the granular permission names; the earlier name was `local-network-access`. Merely mentioning that spelling does not repair the row’s rejection rule. [LNA launch announcement](https://developer.chrome.com/blog/local-network-access), [Chrome 145 announcement](https://developer.chrome.com/blog/chrome-145-beta#local_network_access_split_permissions).

   **Decision needed:** query applicable names and handle an unobservable decision conservatively, or establish and enforce a browser-version support boundary.

5. **IN-DELTA · MATERIAL — D6, lines 391–396; D8, line 487 and lines 504–517: exempt connectivity can still invent a process-wide grant.**

   Apple documents macOS network exemptions through `AllowedEthernetLocalNetworkAddresses` and `AllowedWiFiLocalNetworkAddresses`: access to those networks succeeds regardless of the program’s Local Network privilege. R2’s geometric classifier nevertheless includes them, and D8 accepts successful connections—or a ready probe—as positive permission evidence. [Apple TN3179, macOS considerations](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).

   Consequently, success on an exempt Ethernet subnet can record `granted`; a subsequent tool fetch to a protected Wi-Fi subnet then passes admission and can display the first alert.

   **Decision needed:** distinguish destination-specific exemptions from evidence of the general privilege. A conservative prompt-risk approximation cannot also serve unchanged as proof of permission.

6. **IN-DELTA · MATERIAL — D4, lines 268–271; D18, line 825: the globally addressed peer fix provides no usable connection path on some supported hosts.**

   When no resolved address passes D5, D4 falls back to `.local` `hostName`. On Linux with Avahi but without ordinary mDNS hostname resolution, discovery can return a global IPv6 address, yet the grant rejects that literal and the executor cannot resolve the fallback. R2 itself acknowledges this configuration; Avahi discovery and NSS hostname resolution are separate facilities. [nss-mdns documentation](https://github.com/avahi/nss-mdns#overview).

   Older supported Android configurations may lack the fallback hostname entirely: `NsdServiceInfo.getHostname()` arrived in API 36/T extensions 17. [Android API reference](https://developer.android.com/reference/android/net/nsd/NsdServiceInfo#getHostname()).

   **Decision needed:** provide a usable, admitted connection path for such peers, or explicitly narrow support. Returning a hostname the chosen transport cannot use does not resolve the original reachability problem.

7. **PRE-EXISTING · MATERIAL — D9, lines 537–543; D12, lines 592–604; D16, lines 780–782: Android’s picker path still requests broad permission afterward.**

   D12 promises communication with a chosen device without `ACCESS_LOCAL_NETWORK`. Choosing one device does not grant that broad permission, so the global fact can remain `prompt`. D9 then requests broad permission before the subsequent foreground fetch. R2’s new D6 rule also refuses a tool’s access to the selected device while that global fact remains `prompt`.

   Android explicitly permits connecting to addresses returned by its picker without broad permission. [Android local-network permission, Path A](https://developer.android.com/privacy-and-security/local-network-permission#android-17-enforcement).

   **Decision needed:** account for selected-device access in both preflight and origin admission, or withdraw the proposed permission-free picker path.

8. **IN-DELTA · MINOR — D6, lines 411–415, versus D10, lines 559 and 562–564: denied non-App fetch behavior is contradictory.**

   D6 refuses non-App requests with Apple prompt risk whenever the fact is not `granted`, including `denied`. D10 instead sends denied non-App fetches to the platform and says cached denial never refuses a fetch up front.

   **Decision needed:** restrict the retry bypass explicitly to foreground App-origin fetches, or reconcile the broader bypass with D6.

9. **IN-DELTA · MINOR — D5, lines 345–346: the WebSocket capability statement is stale.**

   Chrome 147 added LNA permission prompts for WebSockets in April 2026. D6 already proposes guarding WebSocket opens, so this factual error alone is not a readiness blocker. [Chrome 147 release notes](https://developer.chrome.com/release-notes/147#local_network_access_restrictions_for_websockets).

   **Decision needed:** update the platform statement and its corresponding verification expectations.

VERDICT: NOT READY
