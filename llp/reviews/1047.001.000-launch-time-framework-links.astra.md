# Round 1

Verdict: NOT READY

**1. Overall assessment**

E is the right architectural direction, and trying linker support before rewriting the adapters is sensible. However, r0 contains factual errors about the existing startup report and linker, leaves E’s selection/admission contract unresolved, and proposes a regression check that cannot prove its stated guarantees.

Reviewed at `9314e7a81`, also `origin/main`. This was read-only; I did not build, test, launch anything, or reproduce the external measurements.

**2. Strengths**

- **§3 preserves the principal measurements faithfully.** The simulator numbers and four-cell phone table match the supplied source. Explicitly distinguishing first-after-install from first-after-reboot is an improvement over the source’s “cold against cold” heading.
- **§3.4 correctly identifies the main dependency chains.** PhotosUI is imported by `Picker.swift`; AuthenticationServices by `Auth.swift`. Core retains concrete references through `Session`, the agent’s picker answers, and document handling. Neither framework is explicitly named by the package/build scripts.
- **§5 E uses an existing mechanism.** The four named Swift capabilities, conditional composition dependencies, installation calls, and `--embed` receipt are real. Development linking everything is correctly attributed to the parent.
- **§4 asks useful questions:** four framework combinations, separate launch conditions, retained samples, attribution traces, and first-use latency. Weak linking and mergeable libraries are reasonably excluded.

**3. Concerns**

1. **[material] §6 incorrectly says Apple has no startup timing report.**

   Evidence: [RFC:140][rfc-report] says there is a lifecycle hook, “not timings.” But [`ExactIOS/main.swift:17`][ios-start] measures process start→main; [`main.swift:148`][ios-report] prints that, main→didFinishLaunching, window, layout, and first-draw timings. [`Session.swift:82`][session-stamps] supplies startup stamps. This reporting predates this draft.

   These measurements are not identical to the external app’s report, and they are not all exposed through agent `state`. Nevertheless, proposing a report from scratch misstates both the code and the required apparatus.

   **Resolution:** inventory the existing timestamps, define their endpoints precisely, and propose only the missing measurements/exposure. Do not infer the external report’s provenance from what this checkout contains.

2. **[material] D’s linker investigation excludes a live possibility and omits a deployment-target obstacle.**

   Evidence: [RFC:110–114][rfc-d]. The installed [`ld` binary][ld-binary] identifies itself as **`ld-27037.1`**, matching the draft, and contains `-lazy_framework`, lazy-load handling, and diagnostics including “lazy-load will be ignored … because deployment target version is too low.” Absence from [`ld.1:215`][ld-man] establishes that lazy loading is undocumented there—not that it was removed. This inspection does **not** establish that lazy loading works for Exact’s references.

   More immediately, [`mach-o/loader.h:714`][loader] dates the alternate load-command encoding containing `DYLIB_USE_DELAYED_INIT` to **iOS 18/macOS 15**. Exact defaults to **iOS 17/macOS 14** ([`build.mjs:124`][deployment]). Running on iOS 27 does not change the binary’s deployment target. The linker also contains diagnostics rejecting particular Objective-C references on older targets.

   The proposed `-Xswiftc`/`-Xfrontend` and `-Xlinker` forwarding is structurally plausible for the actual [`swift build` invocation][swift-build]. Its effectiveness remains unproved. Delay-init is not general image-load avoidance; mapping/binding and ordinary dependency paths remain relevant. The quoted manual does not establish unconditional deferral of Objective-C registration.

   **Resolution:** retain lazy loading as an unverified candidate; screen both mechanisms against Exact’s actual deployment targets and reference kinds. Capture effective link arguments, warnings, and **load-command flags**, not merely command kind. Scope explicit framework flags to selected capabilities, or D could reintroduce dependencies E removed. Export applicable compile/link requirements for embedders.

3. **[material] E lacks one authoritative selection rule shared by Rust, Swift, admission, and embedding.**

   Evidence: [RFC:100–104][rfc-e]. Today [`appleComposition`][composition] consumes `graph.uses` plus manifest `link`. [`receipt.rs:584`][receipt-uses] derives `graph.uses` from the plan alone. Authentication has no capability roster entry and is always registered in [`host/apple/src/link.rs:199`][rust-auth]. The bake already handles another grant-driven input, I/O, separately ([`bake/src/link.rs:32`][bake-links]).

   Thus “use `auth.session`” is a reasonable direction, but adding a Swift target or changing Rust selection alone will not make the existing composition select it. Auth originates in data-source requests, so plan inspection alone cannot discover it.

   Picker granularity also changes the promised savings: using existing `picker` is conservative, but document-only file inputs can retain PhotosUI. A finer media key must conservatively handle computed `type`/`accept`, all routes, and replacement plans.

   **Resolution:** choose the picker rule and specify where grant-derived auth selection enters the authoritative composition, compatibility inputs, admission checks, and `capabilities.json`. Include link-ahead and development behavior. Verify the complete path for neither capability, each individually, and both.

4. **[material] Q3’s fallback would conceal an incorrect use-set and contradict the parent.**

   Evidence: [RFC:102 and Q3][rfc-e], versus [LLP 1047.001 D5:274][parent-refusal]. The parent requires refusal before boot or candidate commitment when a required capability is missing. A document-picker fallback “whose use-set missed it” makes an under-approximation appear successful and changes the promised photo-library experience.

   A refusal discovered only when the person presses the picker is also later than D5 specifies.

   **Resolution:** require conservative selection and boot/candidate refusal. If a Files-based media picker is intentionally offered as another supported implementation, specify that product behavior explicitly; do not use it to compensate for missed dependencies.

5. **[material] B’s delegate assertion is too strong, and its implementation surface is understated.**

   Evidence: [RFC:118–123][rfc-b]. Objective-C does not automatically enforce a protocol-qualified property assignment, but that does not promise the framework never checks conformance. The public SDK declares protocol-qualified, **weak** delegate/provider properties ([`PHPicker.h:274`][picker-header], [`ASWebAuthenticationSession.h:77`][auth-header]).

   B can use public APIs; dynamic lookup is not intrinsically private-API use. But “an NSObject answering the selector is enough” is an unverified implementation assumption. Public runtime APIs also permit looking up and adopting the protocol after loading.

   Auth is not merely “one class”: current code uses `ASWebAuthenticationSession.Callback` on newer systems and typed authentication errors ([`Auth.swift:60`][auth-implementation]). Those references must also disappear or be dynamically resolved.

   **Resolution:** specify public classes/selectors, exact calling conventions and ownership, retained initializer results, completion-block lifetime, strong ownership behind weak delegates, availability/failure handling, and process-lifetime library handles. Preserve the newer HTTPS callback path and older custom-scheme path. Separate “uses public SDK APIs” from any untested App Store acceptance claim.

6. **[material] The draft drops the source’s functional acceptance requirements.**

   Evidence: source [§4:119–123][source-behavior] requires real picker/auth behavior, cancellation, temporary-file lifetime, two windows, and teardown. Draft [§4:92][measurements] principally measures latency.

   This matters for E too: moving implementations changes ownership and registration even if the system frameworks remain eager. The picker must copy provider files inside their callback ([`Picker.swift:250`][picker-callback]). Auth retains sessions, cancels them, and suppresses late completions ([`Auth.swift:76`][auth-lifetime]).

   Agent substitutes do not exercise these paths. There is also a concrete extraction hazard: `authOp` obtains `authSessions` before checking agent mode ([`Auth.swift:35`][auth-hold]); moving loading into that factory could activate the framework for a substituted request.

   **Resolution:** add behavioral acceptance for real sheets, document-picker preservation, cancellation/failure, callback availability, two sessions/windows, and teardown/reload. Separately prove substitutes bypass loading/activation. Preserve macOS behavior and tvOS refusal. “E needs no M4” is defensible for deferred-load latency, not for functional verification.

7. **[material] §4 is a good screening plan, but does not yet decide everything it claims.**

   Evidence: [RFC:84–94][measurements].

   - Define process start, main, first draw, and **interactive**; they are different endpoints. The agent’s returned `boot` is `session.bootMs`, not an independently measured exec→interactive duration ([`ExactIOS/main.swift:120`][agent-boot]).
   - Specify repetition/stopping rules, dispersion, and the benefit/first-use thresholds that justify further complexity.
   - Define a separate reboot for each after-reboot sample and control the install/data conditions; randomizing four launches after one reboot would not give four equivalent cold samples.
   - Retain reproducible variant recipes, including exactly how framework references were removed.
   - One phone trace is diagnostic evidence, not a determination that D works. The simulator—the main remaining motivation—needs attribution too.
   - Include incremental rebuild cost: the parent explicitly preserves shared capability builds and rebuild budgets ([LLP 1047.001:359][parent-budget]).

   **Resolution:** turn “decides” into named measurements and acceptance criteria. Keep end-to-end observations separate from framework attribution and from the 100 ms p50 budget.

8. **[material] §6’s allowlist cannot prove E’s or B’s advertised invariant.**

   Evidence: [RFC:120 and 139][regression]. If a linked capability declares PhotosUI as allowed, an accidental ordinary PhotosUI dependency passes the proposed check—even when B was supposed to load it only on demand. D’s delayed-to-eager regression also retains the same framework name.

   Reading only the executable’s direct commands does not establish the full launch dependency closure or actual initialization behavior. A production-only check also misses development-only regressions affecting the simulator. Furthermore, `--embed` does not produce the consumer’s final executable ([`build.mjs:933`][embed]); the surrounding app may independently link either framework.

   **Resolution:** distinguish **absent**, **eager permitted**, and **deferred required** expectations. State whether inspection covers direct dependencies or the launch closure, and use runtime evidence where static inspection cannot prove the claim. Define separate embedding guarantees: “Exact introduces no dependency” is different from “the host process never loads it.” Derive the baseline from current artifacts rather than the unavailable experiment’s “13 frameworks.”

9. **[material] A is dismissed before the comparison needed to dismiss it.**

   Evidence: [RFC:128][rfc-a] says E+B provides everything A does “at a fraction of the cost” and records A so it is not proposed again. The source instead recommends comparing B against A ([source:129][source-recommendation]).

   A has packaging and ABI costs, but retains compiler-checked framework calls, protocol conformance, ARC behavior, and availability checking inside the adapter. B exchanges those advantages for manual dispatch and ownership work. Existing arm packaging reduces—but does not eliminate—A’s additional infrastructure cost.

   **Resolution:** prefer E and a bounded linker experiment, but retain A as the fallback comparator if B becomes brittle. Compare maintenance/correctness risk as well as code size and launch time. Stopping after E should also remain an explicit outcome.

10. **[material] Apparatus approval and execution budgets are incompletely addressed.**

    Evidence: [RFC:139–145][rfc-report] marks the report and one harness location as requiring approval, but presents the launch-link check and per-capability declarations as wanted regardless. [`RULES.md:64`][rules-apparatus] applies to checks and registries too. Moving a script under `llp/research/` does not exempt it.

    **Resolution:** record explicit approval for the actual assertion/declaration mechanism and retained harness, or keep them proposals. The parent’s approval of an embed-size metric is not evidence of approval for this new check. Keep slow timing/UI verification asynchronous; do not create a sixth blocking check. Specify the implementation owner/date and bound experimentation by the three-round rule.

11. **[minor] Several summaries are stronger or less accurate than their evidence.**

    Evidence: [RFC:25, 69, 147][rfc-summary] and [source:43–67][source-phone].

    - **506 ms is the after-reboot observation**, not first-after-install.
    - The phase improvements total **122 ms**, whereas interactive improves **103 ms**; “split between” omits the remaining phases’ offset.
    - One warm observation per build cannot establish a noise distribution or zero warm cost.
    - The simulator’s combined row contains all thirteen frameworks, not a measured PhotosUI+AuthenticationServices-only pair.
    - First-after-install results do not establish the cost of every in-place App Store update.
    - The header says QUEUE now points here, but [`QUEUE.md:70`][queue] still contains the older recommendation.

    **Resolution:** retain the tables, label causal/generalized conclusions as hypotheses, correct the arithmetic/conditions, and fix the stale reference. Attribute tvOS binary observations to the external source; source inspection here does not verify those artifacts.

**4. Suggestions**

Keep **E first as the architecture**, perform the cheap linker feasibility screen early, and choose any further deferral from measured residual cost. Replace “E → D → B, A rejected” with **E → viable linker mechanism → B versus A if justified**.

Reuse the existing launch stamps and an existing consumer/probe. Prefer a small set of precise absence/deferment assertions over a broad framework registry until the latter earns its maintenance cost.

Describe document pickers as *remaining in core for this slice*. “They only need UIKit” is not the parent’s definition of core.

**5. Open questions for the author**

- Will E use conservative `picker`, or introduce a finer media requirement with conservative dynamic-value handling?
- Must D support the existing iOS 17/macOS 14 floors, or is an explicitly limited newer-target optimization acceptable?
- What measured residual gain justifies B/A, what first-use regression is acceptable, and which new apparatus has explicit approval?

**6. Recommended next step**

Revise to r1 before implementation: correct the report/linker facts, settle E’s composition and refusal contract, restore behavioral acceptance, and define the regression invariant. Then run a bounded feasibility and measurement pass on the actual supported targets, retaining recipes and raw results.
