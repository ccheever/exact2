## Security

The listener is `onCanvasWord` at `apps/design-tool/pairing.ts:55-63`. It accepts `{type:'exact-canvas-entered'}` only while `minted.frame` is still set and `event.origin` is exactly `minted.origin` (scheme, host, and port from `made.root`). The browser sets `origin`. The tool's own origin, `"null"`, and any other origin are ignored. On acceptance it stores the canvas key and sets `minted.frame` to `''`. No reply is sent.

`pairing.ts:61` then requires `source.parent === source.top` and `source !== source.top`. That is "a direct child of the top window."

- **A second iframe the tool shows.** A direct child of the top window whose origin is the canvas origin would pass. In remote mode the contract mounts one iframe, `canvas-frame` (`app.contract:1414-1415`). The local dev-loop iframe is the other branch (`app.contract:1422-1423`) and is a different origin. The host does not add another iframe.
- **A frame of a frame.** While it is attached, its `parent` is the canvas window and its `top` is the tool, so `parent !== top` and it is refused. A nested frame that removes itself after posting is the discarded-window case below.
- **The framed app after entry.** The 303 stays in the same iframe window, so the geometric check passes, but the first accepted word has already cleared `minted.frame`, and a later word returns at `pairing.ts:56`. Reload sets `pending(canvasAt)` before the new mint writes `minted` (`host/web-js/rt.js:522`), and the iframe is unmounted for that whole wait (`app.contract:1414`), so the old app is gone before the new grant is stored.
- **A window the canvas opened, still open.** The iframe's sandbox is `allow-scripts allow-same-origin allow-popups` (`app.contract:1415`). An open popup is its own top, so `source === source.top` and it is refused. The tool itself does not open one in remote mode: `hello.page` is empty there, so the `_blank` link is not rendered (`app.contract:1406-1407`).
- **The tool framed by another page.** The page that can mint is the remote door's tool. Its HTML is sent with `frame-ancestors 'none'` (`scripts/tamber-remote.mjs:213`), and that door refuses a request whose `Origin` is not its own (`tamber-remote.mjs:187-199`). Framed, that document does not run, so the listener never sees a grant from a window that is not top. `parent === top` is then the same test as "direct child of this page."

**`parent` and `top` do not throw.** Both are on the cross-origin allowlist, and both getters return null when the window's navigable is gone (the HTML spec's own example is a removed iframe: `parent === null` and `top === null`). A throw would not remove the listener; these getters do not throw. The null return is what the check gets wrong.

**A discarded window passes.** `pairing.ts:61` does not require `parent` or `top` to be non-null. For a closed popup or a removed frame, `source === source.top` is false (`window === null`) and `source.parent !== source.top` is false (`null !== null`), so the word is accepted.

Concrete path: after one entry the framed app opens a popup and that popup keeps the tool window (`opener.parent`). Reload unmounts the iframe, but the popup stays. When the new entry URL is showing and `minted.frame` holds the new grant, the popup opens a throwaway same-origin window that does `tool.postMessage({type:'exact-canvas-entered'}, toolOrigin)` and closes itself before the task runs. The listener records the new key as entered and clears the new grant URL. The next poll, still inside the key's 40, returns the gateway root and can tear down the entry document before its POST. The message carries no grant, and the sender cannot read `minted`. This is entry disruption, the same class as round 1's popup, through the hole the null check leaves. An open popup, a live nested frame, and a missing source stay refused. `scripts/design-tool-scope.test.mjs:160-163` builds the open popup (`parent === top === self`) and does not build a source whose `parent` and `top` are null.

**After a real entry the grant is not kept past the poll.** The word stores `JSON.stringify([client, epoch, tick])` and clears `minted.frame`. `minted.root` and `minted.origin` have no fragment. `canvasAt.frame` and the iframe `src` keep the entry URL until the next poll, which is the designed handoff; the gateway has already deleted the grant before the 303 (`scripts/tamber-canvas.mjs:370-382`). An overtaken mint returns `{frame:'', root:''}` (`pairing.ts:100`). The module's answer map keeps only the latest conversion per resource (`host/web-js/ts-data.js:115-116`) and the poll's root replaces it.

## Correctness

One grant per key, shared. `loadCanvas` (`pairing.ts:81-102`) returns the stored frame or root when `minted.key` is already that key. A second ask for a key already in flight awaits the same promise (`pairing.ts:87-96`). `call` reports failure as `{error}` (`apps/design-tool/wire.ts:109-136`), the shared promise resolves to `{frame:'', error}`, `minting` is cleared, and `minted` is left unchanged. Try Again and Reload both bump `canvasTick` (`app.contract:856-857`, and `saveName` at `885`), so the retry is a new key.

A key change while one mint is in flight, including a new `hello.epoch`, starts a separate mint and increments `asks`. The older completion sees `mine !== asks` and `minted.key !== key`, returns `{ok:false, error:'', frame:'', root:''}`, and does not write `minted` (`pairing.ts:100`). The runtime keeps the later ticket (`host/web-js/rt.js:521-522`). The same-key double ask from a stale `canvasIn.entered` (Reload while the previous key had entered) shares one mint: the earlier ask is the one treated as overtaken, and the later ask writes `minted` and is the ticket that is shown.

The poll is gated on `not pending(canvasAt)` and `not pending(canvasIn)` (`app.contract:825`). A false gate drops the timer (`host/web-js/schedule.js:96-98`). The first firing for a new `canvasKey` (client, epoch, tick) sets the budget from 40 (`app.contract:854`), and the gate can arm a new key even when the previous budget is 0. That is 40 waits of 1000 ms, starting once the new frame has settled, which covers the grant's 30 s (`scripts/tamber-canvas.mjs` `GRANT_MS`).

The tests at `scripts/design-tool-scope.test.mjs:149-211` lock the wrong origin and type, an open popup, a nested frame, a missing source, one mint per key, the overtaken mint returning no grant, and the word not restoring a grant. They call `loadCanvas` directly, so they do not walk the contract poll. The shared-mint and overtaken-mint cases match the code. They never pass a source with `parent` and `top` both null, so they accept the discarded-window hole.

## Findings

1. **SHOULD-FIX** — A discarded canvas-origin window passes the frame check. `pairing.ts:61` treats `parent == null` and `top == null` as a direct child of the top window. A popup the framed app opened (`app.contract:1415` allows popups and same-origin) can keep the tool window across Reload, then post `{type:'exact-canvas-entered'}` from a throwaway window that closes itself before the listener runs. The HTML spec returns null from both getters and does not throw. The listener then marks the new key entered and drops the new grant URL; the next poll loads the gateway root and can abort that entry. The word still does not carry the grant. Require `parent` and `top` to be non-null before comparing them, and add that source to `scripts/design-tool-scope.test.mjs:160`.
