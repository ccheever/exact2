# Audit: LLP 1115.003 — Expo Services, shared graphics and native presentation

I verified the RFC's load-bearing claims against the Exact hosts and both app copies at the cited commits. The direction is sound; several of its premises, bounds, and bars are not. Findings are ranked by consequence.

## 1. The replacement is sampled on both hosts for exactly the properties that forced the native implementations, and D2 does not include lowering them

**Claim (§57, §16):** shared playback reuses "the existing shared clock timelines and host animation lowering," preserving iOS performance; a sampling host "must still pass the load test."

**Actually:** the login mark and zoom are native *because* sampled playback failed under load: they were moved from TypeScript surfaces at 30–60 Hz to phases "sampled at 120 Hz into Core Animation keyframes when they start, so the render server plays them whatever the main thread does" ([EasNative.swift:1308](.refs/ios/modules/apple/EasNative.swift:1308), [GAPS.md:242](.refs/ios/GAPS.md:242)). Neither host lowers the properties this artwork needs. Android's lowered set is opacity/translate/scale/rotate/`r`/dashoffset/`cx`/`cy` only — no `d`, no `rx`/`ry`, no fill/stroke — and a paint-server (gradient) shape is never playable ([lower.rs:30](host/linux/src/lower.rs:30), [lower.rs:510](host/linux/src/lower.rs:510)). On Apple, geometry and `d` are sampled and the scene rebuilt ([1055.000:269](llp/1055.000-completing-svg.rfc.md:269)). So the chart morph (a 1,025-point path) and the login bands/morph start life as per-frame scene resolves and re-recordings on the main thread — the failure mode the evidence already recorded.

**Why it matters:** §4 deletes each Swift implementation on switch, with only generic comparison evidence. The known risk is neither inventoried nor gated.

**Instead:** add a per-property inventory (each animated property of logo, chart, numbers × lowered/sampled per host) and a prototype gate measured on a 120 Hz device during session/data load before any app rewrite. Either accept sampled cost with that evidence, or put `d`/geometry lowering (Core Animation `path` keyframes; an Android reader path track, as dash already re-records one path) into D2's scope explicitly.

## 2. "Protecting iOS" ignores the app's unmerged 681-line Exact host patch

**Claim (§69–73):** record commits, build the real iOS app, retain "host patches."

**Actually:** the app cannot be built from this checkout. It requires applying `patches/exact2-ios-host.patch` to exact2 first ([PORTING.md:112](.refs/ios/PORTING.md:112)), covering navigation-bar behavior, caret color, menus, sheets, and `data-barfollows` — a bar that follows the drawer sideways and takes no touches while shifted ([PORTING.md:123](.refs/ios/PORTING.md:123), used at [app.contract:864](.refs/ios/app.contract:864)). None of it is in this tree, the six checks do not cover it, and several items have no Android equivalent (Android's bars live in their own views and change by per-stream statement, [1115.001:753](llp/1115.001-no-tells-on-android.rfc.md:753)).

**Why it matters:** every iOS baseline, comparison, and regression band in §4–§5 is measured against a forked host the RFC never names. Host work in D2 lands on main and must rebase under the patch.

**Instead:** inventory the patch in §2, define the baseline as exact2 commit plus patch, and decide per item: upstream it (with tests), keep it as a named fork cost, or accept the Android difference explicitly.

## 3. D2 understates the Android recorder's gaps; "SVG linear gradients" is the wrong cut

**Claim (§47–49):** the recorder "emits solid paths but omits gradient paints"; complete SVG linear-gradient fills, transforms, and clipping.

**Actually:** the recorder draws *nothing* for any gradient or pattern ink ([canvas.rs:708](host/linux/src/canvas.rs:708)), substitutes the first stop for CSS box gradients ([canvas.rs:536](host/linux/src/canvas.rs:536)), and does not implement `push_svg_clip` or `island_image` at all, so SVG `clipPath`s are ignored and masks/filters/blends vanish (defaults at [backend.rs:69](host/linux/src/paint/backend.rs:69) and [backend.rs:109](host/linux/src/paint/backend.rs:109)). The unchanged app already uses CSS `linear-gradient` header fades on every screen ([chrome.contract:15](.refs/ios/chrome.contract:15)), which today render on Android as a solid first-stop slab — a defect §2's evidence does not report. Box gradients also carry radial and conic geometry ([gradient.rs:88](host/linux/src/paint/gradient.rs:88)).

**Instead:** inventory the paints the existing app and the shared artwork actually use, add one gradient op serving both SVG and box gradients (including the Kotlin reader half), and state which SVG features (clip, pattern, islands) are completed, which are refused by name, and which the artwork is forbidden to use — silent omission is the current behavior and must not survive into authored assets.

## 4. The outcome promises an Android port; the scope only funds graphics

**Claim (§16, §18):** one implementation on iOS and Android, controls and system integration following each platform; scope is "this consumer and the reusable Exact host support it needs."

**Actually:** non-graphics Android behavior is uninventoried. System Back never closes the drawer: `back` only pops the nav stack while drawer state lives elsewhere ([app.contract:255](.refs/ios/app.contract:255)), and Android's Back order has no drawer step, so Back at the root leaves the app ([1115.001:271](llp/1115.001-no-tells-on-android.rfc.md:271)). There is no splash handoff on either Exact host — Android's launch icon is transparent ([themes.xml:8](host/android/canvas/src/main/res/values/themes.xml:8)) and iOS's launch screen is a colour ([GAPS.md:10](.refs/ios/GAPS.md:10)) — against the splash-first sequence the login decision specifies. The install flow is `itms-services` with resigned-active/timeout/simulator signals and no stated Android equivalent ([GAPS.md:39](.refs/ios/GAPS.md:39)). The overscroll cube depends on scroll offsets beyond the bounds ([home.contract:86](.refs/ios/screens/home.contract:86)), which Android's reader-owned stretch never reports. Gyroscope tilt is listed as behavior to preserve in §2, excluded in §94, and absent from the iOS reference itself ([GAPS.md:9](.refs/ios/GAPS.md:9)) — so §79's Android-vs-Expo comparison fails by construction. macOS, where every drawing module is currently an empty stub ([EasNative.swift:1690](.refs/ios/modules/apple/EasNative.swift:1690)), is never mentioned, though shared components change it.

**Instead:** either narrow §1 to "shared graphics components; a shippable Android app is a separate, later decision," or add the non-graphics inventory (Back/drawer, splash, install, sheets, overscroll, tilt) with an explicit accept/build/exclude per item.

## 5. `d` in keyframes is neither bounded nor shown to be the mechanism the logo needs

**Claim (§51):** complete `d` in keyframes, a "bounded SVG feature," for the logo's finite morphs.

**Actually:** keyframe values are numeric `(Property, Value)` pairs with no path payload ([animation.rs:104](motion/src/animation.rs:104)), capped at 32 keyframes ([animation.rs:27](motion/src/animation.rs:27)); `d` is a prop the kernel reads only where a *transition* covers it ([motion.rs:876](kernel/src/motion.rs:876)), and its transition runs as a scalar progress beside a path track ([path.rs:5](motion/src/engine/path.rs:5)). Keyframed `d` therefore needs a plan-codec path payload, keyframe grammar for a prop, engine animation sampling and precedence against the transition track, and web-target support. Meanwhile the two actual morphs are two-endpoint changes at phase boundaries — the chart's sample-set timing ([use-chart-morph.ts:96](.refs/android/src/screens/home/components/chart/use-chart-morph.ts:96)) and the check-to-logo window — which existing `d` transitions already express ([1055.000:273](llp/1055.000-completing-svg.rfc.md:273)). The genuinely hard parts — three composing phase clocks summed per frame ([EasNative.swift:1462](.refs/ios/modules/apple/EasNative.swift:1462)) and sinusoidal band geometry — are not solved by keyframed `d` at all.

**Instead:** show the authoring encoding phase by phase (keyframes vs transitions, implicit endpoints, composite order, state-dependent starts). If transitions suffice, drop keyframed `d` from the required path; if not, scope it as its own multi-crate stage, not a bounded add-on.

## 6. Icons: the Material resolution D1 relies on does not exist, is not in the bounded list, and the app's icon surface is open-ended

**Claim (§41, §93):** ordinary icons use existing `symbol:` roles; Android resolves them to Material equivalents; the bounded host work is gradients and `d` keyframes.

**Actually:** the schema's symbol table is `[role, Apple name, web path]` with no Android column ([schema.json:4004](kernel/tables/schema.json:4004), [schema.json:4596](kernel/tables/schema.json:4596)); the Linux painter draws that one web path on Android, and an `sf/` name "stays an empty box" ([svg.rs:90](host/linux/src/paint/svg.rs:90)). The app's chrome is built on dynamic SF names — `symbol:sf/${name}` ([chrome.contract:37](.refs/ios/chrome.contract:37)), a runtime-string `sf-symbol` wrapper ([ui.contract:24](.refs/ios/ui.contract:24)), and SF names inside menu JSON ([chrome.contract:13](.refs/ios/chrome.contract:13)) — so most header and menu glyphs are blank on Android today, which §2 never reports. The Android glyph column is LLP 1115.001 D14 ([1115.001:472](llp/1115.001-no-tells-on-android.rfc.md:472)), assigned to an undated S2 ([1115.001:860](llp/1115.001-no-tells-on-android.rfc.md:860)).

**Instead:** make the reachable-name inventory (including TypeScript-built menus) the first deliverable, since §4 puts icons first; take explicit ownership and sequencing of D14 for the needed roles (schema format, generator, painter column, RTL mirroring), or state Apple-shaped glyphs as an accepted Android difference.

## 7. Chart scrubbing has no stated mechanism, and its gesture ownership contradicts both references

**Claim (§63):** scrub original buckets; "check competition with vertical scrolling, the drawer and system Back… without introducing a gesture arena."

**Actually:** `pan` supplies only incremental `(dx, dy)` ([README.md:73](apps/textflow/README.md:73)); pointer events supply absolute offsets but "take nothing from `press`, `pan` or scrolling" ([1056:799](llp/1056-canvas-2d.rfc.md:799)); the drawer pan sits on the whole screen frame ([app.contract:963](.refs/ios/app.contract:963)); and Android's reader owns the scroll gesture ([1115.001:291](llp/1115.001-no-tells-on-android.rfc.md:291)). In both references the handle moves on the UI thread and only bucket changes cross to the app ([chart.tsx:125](.refs/android/src/screens/home/components/chart/chart.tsx:125), [EasNative.swift:1005](.refs/ios/modules/apple/EasNative.swift:1005)), and a vertical drag on the chart scrubs rather than scrolls ([GAPS.md:121](.refs/ios/GAPS.md:121)). The RFC never says how absolute x is obtained, which axis each gesture wins on each platform, or that handle motion becomes per-move app commits.

**Instead:** specify the claim (e.g. `pointerdown` offset plus `pan` accumulation under a stated `touch-action`, per platform), decide the vertical-drag behavior explicitly as §33 requires, and add scrub latency and frame cost to §5's performance row.

## 8. The conditional native Canvas 2D replay contradicts LLP 1056 and is not a bounded fallback

**Claim (§53, §93):** if procedural drawing misses its budget, add native replay of recorded Canvas 2D operations on Android, approved as bounded host work.

**Actually:** LLP 1056 decided Linux replays into tiny-skia under both painters for stated reasons ([1056:354](llp/1056-canvas-2d.rfc.md:354)); a canvas is a *kept bitmap plus whole persistent context* ([1056:187](llp/1056-canvas-2d.rfc.md:187)), which Android's display-list View Canvas is not — accumulating draws would need whole-history re-recording or a software bitmap canvas, defeating the acceleration. "Never mix executors" further requires retaining every list since the generation began, which the acceptance protocol does not do.

**Instead:** remove native replay from decision 2. State that CPU replay is the design on Android, that artwork must be authored as SVG when it cannot meet budget, and that a second executor requires its own RFC amending LLP 1056 with a measured consumer.

## 9. Admission and acceptance both rest on work this RFC neither owns nor dates

**Claim (§95):** "SVG, Canvas 2D and Android are already admitted"; §5 bars are passable by this work.

**Actually:** `rules/DEFERRED.md` contains no Expo Services consumer (the Android entry admits the host, take unnamed, [DEFERRED.md:394](rules/DEFERRED.md:394)), and binding rules require a DEFERRED trade or waiver to move work onto the doing list and an implementer and date for a spec ([RULES.md:47](rules/RULES.md:47), [RULES.md:58](rules/RULES.md:58)) — the RFC has neither, and sits outside a full 15-document working set. Its acceptance bars inherit explicitly unbuilt or unverified host work: Android sheets ([1115.001:680](llp/1115.001-no-tells-on-android.rfc.md:680)), TalkBack verification owed by hand ([1115.001:911](llp/1115.001-no-tells-on-android.rfc.md:911)), IME composition unseen on a device ([1115.001:633](llp/1115.001-no-tells-on-android.rfc.md:633)), filmed screenshots refused by the Android carrier ([README.md:159](host/android/README.md:159)), and agent taps that are not real Android input ([1115.001:743](llp/1115.001-no-tells-on-android.rfc.md:743)). Matched-timestamp comparison against the React Native app also depends on a live backend and a test account that locks after repeated logins ([PORTING.md:108](.refs/ios/PORTING.md:108)), with no Android seeding procedure named.

**Instead:** add the consumer admission (with its take), implementer, dates, and working-set trade as decisions; split §5 into bars this RFC can pass, prerequisites owned by named 1115.001 stages, and manual device evidence with its driver and account seeding named.

## Verdict

The direction is right: one authored implementation of the logo, chart, and numbers, no Kotlin copy of their geometry, and platform-owned presentation is the correct end state and consistent with LLP 1115. But the draft is not ready to implement. Before work starts it must (1) disposition the app's unmerged host patch and rebuild its iOS baseline on that truth; (2) inventory animated properties against real lowering and gate the sampled design on device evidence under load, or add lowering to scope; (3) re-cut D2 around the recorder's actual gaps, one gradient path for SVG and boxes included, and either justify keyframed `d` against existing transitions or drop it; (4) inventory icons and own the Android symbol work it depends on; (5) specify chart gesture ownership; and (6) narrow the outcome to shared graphics or inventory the remaining Android product work, with the consumer admitted in `rules/DEFERRED.md`, an implementer and dates named, and §5 split into what this RFC can actually pass.
