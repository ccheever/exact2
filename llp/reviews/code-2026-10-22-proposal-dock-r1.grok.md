1. **BLOCKER** `apps/design-tool/app.contract:984` — A press can still take focus after the user has moved on. `focusApply` is set by `resetParam` and `panelBackToPackage` and cleared only in `focusTheApply` (`:1513`). `dialText` (`:1120`), `dialNumber`, `dialStepped`, `cellText`, `cancelEdit` (`:1398`), and `selectCell` leave it set. The task arms on the false-to-true edge of `applyReady`, and `key=` re-arms when the key changes (`runner/src/runner/gates.rs:48`). It does not pin the press. `applyReady` drops whenever the proposal is pending, and `proposeAt` changes on every poll answer (`apps/design-tool/app.ts:1016`, `paced: answer ${answers}`), so a poll or a new draft cancels the 1ms timer and arms it again later. A reset, then typing, then a settled proposal, runs `focus("proposal-dock")` and pulls the caret out of the field. If that later edit is a grid edit, the column is not sticky, so the focus also scrolls to its in-flow place.

2. **SHOULD-FIX** `apps/design-tool/app.contract:921` — `dockedFor` is never cleared. A later edit with the same `op|name` docks. `panelBackToPackage` sets `remove-token|<packageToken>` (`:1374`); Cancel leaves it (`:1398`); the grid's `backToBase` (`:1352`) or `removeToken` (`:1389`) for that same token name sets `remove-token` again, and the proposal sticks. The same latch docks a later `set-param` of a name a dial already edited.

3. **SHOULD-FIX** `apps/design-tool/app.contract:2147` — The live line is cleared while `pending(proposal)` and set back to the same sentence on every settle. That is every keystroke, and every poll, because finding 1's `proposeAt` change refetches the proposal even when the draft did not change. A screen reader repeats "Proposal ready: Apply or Cancel." The predicate also ignores `applyReady`, so it says Apply when Apply is disabled (stale draft, read-only branch, write in flight).

4. **SHOULD-FIX** `apps/design-tool/app.contract:2141` — The 40vh cap does not keep the edited row above the dock. A row whose viewport box sits in the bottom 40% is covered. Focusing the field scrolls it into the scrollport, not into the band above the dock. The dock test's field is high (`y` about 458) and never places a row in that band.

5. **NIT** `scripts/design-tool-dock.test.mjs:41` — "In the window" is `dock.y + dock.h < field.y + 2000` (the 2458 bound). `layout` returns `viewport.h` and the test never reads it, so a dock still below the fold can pass. The reset check (`:48`) is only non-overlap, which stays true if focus has scrolled the row off the top.

6. **NIT** `apps/design-tool/app.contract:2141` — `tabindex=-1` on the region is a valid programmatic target, and on the web Tab from it reaches Apply. On the Mac host with Keyboard navigation off (the default), a button is not a stop, so Tab skips Apply. Focusing the region announces "Proposal," not the diff.
