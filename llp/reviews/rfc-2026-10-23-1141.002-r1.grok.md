Verdict: READY WITH CHANGES. The search tab is a structural fact the author has to name, and `UISearchTab` plus the existing header field is the right iOS shape, but the minimized-search word collides with a live CSS property and the all-apps `tabs` migration is thinner than the host it would replace.

## Strengths

- **§1 and D1.** Shelf and Harmony correctly kill inference. The marker sits on the tab, which `Kernel::root_tabs` can see on the first frame, while `runner/src/instance/tabs.rs` leaves the panel empty until selection. Refusing `role="search"` keeps the `tablist` legal. One search tab, the first, matches `TabRole.search`.
- **D2's fork.** One builder per OS, with stage 0 allowed to keep `tabBarSystemItem: .search` if that actually separates the tab, is the right response to the pilot: Expo's system item separated, GPT's did not, and mixing `UITab`s crashed (`insertObject:atIndex:`).
- **D3.** The field stays `input type="search"` in the root header. `searchField` already builds `navigationItem.searchController`. No second search widget.
- **D6.** Default `authoredChrome` still hits `testId`s, so drives do not learn UIKit's coordinates. `tree` reporting `searchBarPlacement` is the right check.
- **§4.** Words land before any pixel change, and every tab app is driven after the builder swap. That order matches the risk.

## Concerns

**MAJOR — D4, `field-sizing="content"`.** Contract already lowers `field-sizing` to `StyleId::FieldSizing` (`contract/lower/src/style_names.rs`). CSS `field-sizing: content` means "size to the text," and an empty search with a placeholder sizes to the placeholder. It does not mean "draw a button until used." On iOS this RFC would turn that declaration into `.integratedButton`; on the web it would stay content sizing. An author who meant the CSS, on a header search, would get a magnifying-glass button on iOS 26. Shelf and Harmony are the reason not to minimize when the author said nothing: a header field that filters a list must stay a field, and D4 already says `.automatic` puts a single stack's field in the bottom bar on iOS 27. Resolve by dropping this overload. Add a presentation attribute in the `buttonStyle` / `listStyle` family, copied into `contract vocab`, and leave minimize opt-in.

**MAJOR — D2, the `tabs` migration versus this host.** `installTabs` / `syncItems` / `TabDelegateProxy` do more than title, image, badge, and `isEnabled`. Selection is vetoed (`shouldSelect` returns false) and `selectTab` presses the authored tab, then a later sync writes `selectedIndex`. Reselect at the root scrolls to top (`reselectedRoot`). `accessibilityIdentifier` is the `testId`, else the symbol or title. Trait changes rebuild glyphs. The bar hides for `authoredChrome` and `appearance: none`. Held stacks call `setViewControllers` (`HeldStackIOS.swift`). `replayTabs` comments that emptying the controller loses the iOS 26/27 selection. `UITab.identifier` should be the panel id (stable, unique). The `testId` belongs on the accessibility identifier, where XCUITest already looks. A changing `testId` must not recreate the tab. A change of which tab is the search tab, with the same panels, has to rebuild the `UITab`/`UISearchTab` row; `reshape` today keys only on panel ids. Stage 0 should also record whether a `shouldSelectTab` that returns false still runs `automaticallyActivatesSearch`, still restores the previous tab on cancel, and still draws the previous tab's bubble beside the field (React Conf journey 08/09). If the veto swallows those, the migration needs a different selection handshake before every tab app moves.

**MAJOR — D2, iPadOS 18–25 and tvOS.** `UISearchTab` dates to iOS 18 and was part of the iPad top tab bar, so "iOS 18 to 25 draws it as one tab among the others" is unsafe for iPad. Stage 0 only measures 26.x and 27. Add an iPadOS 18 simulator, or narrow that row to iPhone. tvOS shares `NavigationTabsIOS.swift`, and `setTabBarHidden` is already `#available(iOS 18.0, tvOS 18.0, *)`. The new path has to be `#if os(iOS)` so tvOS does not follow iOS 18 onto `UITab`. Open question 5 should say that explicitly.

**MAJOR — D5 overclaims the rest state.** `hidesSearchBarWhenScrolling` defaults to true, and assigning `searchController` after the bar's first layout often starts the field collapsed. "Shows at the top of the content, then collapses" is the iOS 11 stacked picture. On iOS 26 `.automatic` is under the title in a tab app and in the bottom bar in a single stack (the behavior D4 relies on). Stage 0 should decide, and the RFC should not state the result now. Protocol: hand-built assignment in `viewDidLoad` and after layout, tab app and single stack, iPhone and iPad, 26 and 27, large title, offset 0. Fix assignment timing before touching the hide-when-empty rule. Also confirm in that spike that a `UISearchTab` plus `navigationItem.searchController` is sufficient for UIKit to move the field, with no extra placement call.

**MAJOR — D6, `back`.** "Search active" has to mean `UISearchController.isActive` (the close button is up). A visible or focused field with text is not active. Otherwise existing drives that `back` through a screen with a header search will cancel instead of pop. Add that drive next to the new ones.

**MINOR — D1 authoring convention.** "Write the search tab last" is how non-iOS hosts stay visually aligned with iOS 26's trailing move. A warning when it is not last would make the convention enforceable. A second search tab's warning is already specified.

**MINOR — D2 accessibility and D3 scope.** Image-only search chrome still needs the authored title as the accessibility label (VoiceOver). A scope bar (LLP 1134, already on `HeaderSearch`) should say where it goes once the controller moves into the tab bar. `tree`'s placement list should include `.inline` and whatever integrated cases the SDK actually has, not only stacked, integrated, integrated button, and the tab bar.

**MINOR — D7 coverage.** The XCTests are the right core. Add: search tab not last is still trailing on iOS 26; iOS 17 suite unchanged (the current `NavigationTabsIOSTests`, not one new assertion); Mac sidebar order and `NSSearchToolbarItem` unchanged; non-search inputs with the new presentation attribute do not change; `check`'s missing-field report is a check, and a landing page without a field still compiles.

## Open questions

1. **`rel` on a `button`.** Keep `rel="search"`. Confidence 78. `role="search"` replaces `tab` and breaks the `tablist`. Requiring `link role="tab"` fights the router for a validity nit. `rel="search"` is the HTML link type whose meaning is a search interface ([HTML, link type search](https://html.spec.whatwg.org/multipage/links.html#link-type-search)), and no browser or assistive technology acts on it on a `button`. Say that in the refusal for `role="search"`, so an agent does not "fix" the validator warning by switching roles.

2. **`field-sizing`.** Do not use it. Confidence 90. Minimize only when the author opts in. Confidence 82. I would not pick a final attribute name here. Confidence 55 that a `buttonStyle`-style property is the right shelf. Unsaid search stays `.automatic`.

3. **Rest state.** Measure with the protocol under D5, then change code only where Exact disagrees with the hand-built screen. Confidence 80.

4. **Mac.** Leave the sidebar row and the toolbar search for this RFC. Confidence 72. The Mac host is AppKit (`NSSearchToolbarItem` in `HeaderMac.swift`). A SwiftUI `Tab(role: .search)` screenshot does not decide it. Revisit only if a hand-built Mac screen of the same OS would put the search field at the top of the source list and would not also keep a toolbar field.

5. **tvOS.** Ordinary tab until an app asks. Confidence 88. Keep the `tabs` API off tvOS in this RFC. `NavigationBarIOS.swift` already skips `searchController` on tvOS.

6. **iPad and a virtual keyboard.** If `automaticallyActivatesSearch` already stays inactive for a software keyboard on iPad, do nothing. If it covers the landing page, do not set the flag in that case. iPhone still activates. Confidence 68. The HIG is the reason; stage 0 is the measurement.

7. **Hatches.** A log line is not enough. Confidence 84. Update Exact's own `setViewControllers` writers in stage 2, and if a module sets `viewControllers` on a `tabs`-built controller, fail with an error that names the replacement. Hand over `UITab`s where an in-repo module still has to build the bar. A UIKit nil crash is a bad 1.0 break.

## Missing

Stage 0 is the right gate and not sufficient. Add to the UIKit spike, before stage 2: delegate veto against activate, cancel, and the previous-tab bubble; badge, disabled, hidden bar, and symbol size on `UITab`; first selection of a lazy panel (the field has to be in the bar on that same update); search tab selected at launch with no previous tab; more tabs than the bar holds; iPadOS 18. Pin `automaticallyActivatesSearch` and `.integratedButton` to the SDK availability you compile against. This review did not open the iOS 26 headers.
