I'll review LLP 1133.017 as a blind design review: read the RFC whole, then check the rules and code it depends on. No files will be changed.The RFC is long. Next I’ll read the rules and the decisions it says it inherits, then the code it cites.The wake seam is the right shape, and it is not buildable as specified. Nine decisions are missing or contradict a rule the RFC inherits.

1. **MATERIAL.** §D1 (lines 171–178, 195–199), §D2 (line 228). A `sync` that is still pending when its invocation completes is defined as "re-registered while firing," and a registration fires at once whenever the device is already online. `lastChance` counts only platform expiries, so a round that fails while the radio is up (Harmony's `round.ok` is false for a down server as well as for offline) re-registers, completes, and fires again immediately. Nothing in the foreground path applies the 30-second budget (§D6, lines 387–389, limits timer suppression to a session with no view or a hidden one). Production will tight-loop; the agent will not, because §10 (lines 978–980) suppresses every wake the clock did not `tap`. The WICG register algorithm fires once per registration and leaves backoff to the user agent ([Background Sync](https://wicg.github.io/background-sync/spec/#dom-syncmanager-register)). **Decision:** re-registering inside the handler keeps the tag pending and does not schedule another run until the next connectivity edge or platform wake, with a backoff; application failure counts toward retirement.

2. **MATERIAL.** §D1 (lines 171–174), §D2 (lines 228–239), summary (lines 74–76), §11 feature 1 (lines 1050–1058) and drive 8 (lines 1148–1156). `sync` means "once, as soon as the platform judges the device online." On iOS the carrier is a `BGProcessingTaskRequest`, and a processing task runs only while the device is idle ([`BGProcessingTask`](https://developer.apple.com/documentation/backgroundtasks/bgprocessingtask)). The RFC's own sentence is that an iPhone often runs it at the next refresh, overnight, or when the person opens the app, and that a send which must leave promptly is a transfer. Harmony's outbox is that send, it is wired to `registerSync`, and no hand drive checks it. Android's `OneTimeWorkRequest` with `NetworkType.CONNECTED` does run when the network returns; the shared name does not. **Decision:** on iOS an offline `sync` is carried by a discretionary background `URLSession` (the primitive that starts when connectivity returns), with `BGProcessingTask` kept for `apple.task="processing"`; or the contract, the summary, and Harmony feature 1 are rewritten as best-effort idle work and stop claiming "when the device is back online."

3. **MATERIAL.** §D1 (lines 179–189) and §D12 (line 695). `minInterval` is "a floor every target keeps." The Android unsaid value of `flexInterval` is the whole period. WorkManager's flex is the window at the end of the period in which the work may run; a flex equal to the period makes the work eligible at the start of the period, immediately after the previous run ([define work](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)). **Decision:** flex is the platform minimum (5 minutes) at the end of `minInterval`, and the text states that Android may start up to one flex early.

4. **MATERIAL.** §D1 (lines 179–184), §10 (lines 992–1000), §11 drive 3 (lines 1129–1132). "No sooner than `minInterval` after its last run" does not say when the first run is due. `tap` on a periodic entry that is not `due` is refused. Drive 3 turns the switch on (`minInterval` 30 minutes) and taps `@<catch-up>` with no clock advance. **Decision:** the first fire is due at registration, or it is due at `minInterval` and drive 3 advances the clock. The agent refusal and `earliestBeginDate` use that same instant.

5. **MATERIAL.** §D3 (lines 265–274, 306–309), §D4 (line 321), §D10 (lines 552–559, 604–622). The record "never holds a header; only the platform's carrier keeps it," and a killed Android transfer "is retried from the first byte." On Android the carrier is the app's own worker, not a system daemon ([user-initiated data transfer](https://developer.android.com/develop/background-work/background-tasks/uidt); WorkManager runs in-process). A retry after process death has no `Authorization` header anywhere. The same record stores the full URL, while §D10 recommends presigned URLs, whose credential is the query. §D3 redacts the query in the journal and in `state`, and not in this file. The body stays at the caller's `app:/tmp` path; nothing copies it into the module's custody before the call returns, so a later purge of `tmp` fails the retry. iOS `nsurlsessiond` does keep the request, which is why the two platforms cannot share this rule. **Decision:** before the call returns, the body is copied to a file the module owns, and the headers and the query are stored in the platform secret store (readable after first unlock, never in the record, Contract, or the journal). The record keeps the URL without query or fragment. Android's retry reads the secrets back. A presigned query is covered by the same rule.

6. **MATERIAL.** §D6 (lines 382–385), §D8 (lines 499–520), §D10 (lines 561–603). Three iOS facts are collapsed into one sequence. The background session has to be recreated, with the same configuration, before `application(_:handleEventsForBackgroundURLSession:completionHandler:)` returns, or the system does not deliver the events ([that method](https://developer.apple.com/documentation/uikit/uiapplicationdelegate/application(_:handleeventsforbackgroundurlsession:completionhandler:))). Step 1 loads the app module and then makes the session. Package Swift is loaded with the app module after first pixel (the constraint §D8 cites). The host can instantiate a process class only from a table baked into the binary. Separately, §D6 completes any wake unsuccessfully without booting when `isProtectedDataAvailable` is false. Calling the stored URLSession completion handler means those events are finished; `setTaskCompleted(success: false)` on a `BGTask` means the system should retry. The same verb drops a finished download across a reboot. Third, step 2 appends an upload task's response body to a file during relaunch. `didFinishDownloadingTo` is the download-task callback and the file is deleted when that method returns ([downloading in the background](https://developer.apple.com/documentation/foundation/url_loading_system/downloading_files_in_the_background)); a background configuration does not support data tasks. Harmony's terminated-app success path (drive 6, lines 1141–1144) parses that body for the asset id. **Decision:** the build emits an identifier-to-process-class table; `handleEvents` constructs that object and the session synchronously, before it returns; the headless boot happens only at `urlSessionDidFinishEvents`. Before first unlock, a transfer launch must not call the completion handler; it finishes after protected data is available. The upload completion record is defined as what a relaunch reliably gets (the task's `HTTPURLResponse`), and Harmony's asset id has to be in that, or a terminated-app replay of the response body is measured and written down before stage 2.

7. **MATERIAL.** §D10 (lines 582–591), §11 (lines 1094–1098), §15 question 5 (lines 1285–1288). The record is retired when the invocation's owned set empties, including when the handler's follow-up write fails. Harmony's photo is two steps: the system upload, then `attachPhoto`, which reads the response and `db.write`s the message. A failed or refused write still completes the invocation (LLP 1113 §D4 completes when the set is empty). The event is not raised again. Keying the message by registration id makes a second delivery harmless; it does not create a second delivery. `sync` has an explicit re-register for this; a transfer does not. **Decision:** the process object retires the record only after the app acknowledges it (a data-code send made once the write has landed). Invocation expiry and a failed answer leave it "ended, not delivered."

8. **MATERIAL.** §D6 (lines 391–400, 402–421), §D7 (lines 434–463), §D11 (lines 642–647), §11 (lines 1069–1074), `rules/RULES.md` lines 42 and 53–56, LLP 1133.004 §D6 (lines 293–300), LLP 1113 §D4 (lines 216–218). A headless wake runs app code and never has a first pixel. `RULES.md` is a check: "App JS executed before first pixel: none," and LLP 1133.004 §D6 says an event that starts the app is delivered after first pixel and never runs app code before it. §D7 amends the second and then says `RULES.md` is unchanged. It also says nothing is laid out until a view asks, and that a view arriving mid-wake never waits for the wake. LLP 1072 has one owner thread for the runtime; the main thread only replays a published stream (`host/android/canvas/.../Owner.kt` lines 14–22). A view that asks while that thread is inside the wake has no stream to present. §12 does not amend `RULES.md` or LLP 1113. LLP 1113 §D4 refuses the invocation `busy` while a storage ticket exists and fails it if one appears. The wake's completion waits on `StorageHold` instead, and Harmony's handler writes the mention mark and the message. Those writes are the tickets §D4 fails. On Android the worker's process is not suspended when it returns `Result.success()` (`host/android/README.md` lines 492–493: the session ends with the process). Boot has already started Harmony's `live` stream (`app.contract` lines 182–186, `app.ts` lines 148–167), §D6 does not cancel work the wake did not start, and that socket keeps running in a cached process. The same boot re-ask is `db.sync()` on a device that serves one answer at a time, so `catchUp`'s sync contends with it inside a budget that §D18 says includes the boot. An expiry before the handler runs still counts toward `lastChance`. **Decision:** amend `RULES.md` and LLP 1133.004 §D6 so a wake launch is a named exception, and amend LLP 1113 §D4 so a wake may start storage and complete after `StorageHold` drains. A headless boot publishes one frame at the last size before any wake event, and the attaching view presents that frame without the owner thread. Resources and streams of a hidden session are not started (a rule the consumer follows, not a recipe). A session that the wake created, with no view when the wake ends, is ended and its boot requests cancelled before the platform is told. The budget starts when the event is delivered; an expiry before that does not count as an attempt.

9. **MATERIAL.** §D5 (lines 353–355), §D6 (lines 402–421), §D7 (lines 441–446), §D8 (lines 476–492). Each platform callback is one wake with one deadline, and timers stay stopped "while a wake runs." Android will overlap a periodic worker, a one-shot sync worker, and a transfer job in one process (WorkManager's executor runs workers together; the RFC uses a different unique name per key). Two deadlines, two completions, and the timer rule have no composition. A second wake ending while the first is still running either resumes timers under the first or tells the platform a task is finished while invocations remain. **Decision:** wakes are serialized per session (a later platform callback is queued until the one in progress has completed or expired), and each platform object is completed from its own queued wake.

10. **IMPLEMENTATION-PHASE.** §D8 (lines 480–492) and §D2 (line 229). After a `BGAppRefreshTask` runs, the pending request is consumed. LLP 1114.001 §D3 resubmits on entering the background and at the end of each wake; this RFC keeps "one request" and does not say when the next one is submitted. The same gap is the `ExistingPeriodicWorkPolicy` on re-register. Neither changes a decision already made. The delegate-queue hop is the same class of detail: `ExactPackage` entries are on the main thread (`ExactPackage.swift` line 9), and a `URLSession` delegate is not.

VERDICT: NOT READY

### Dispositions (r2)

1. MATERIAL, `sync` retry loops while online: FOLDED at D1. A re-registered tag waits a backoff (5 minutes doubling to an hour) and then fires at the next chance, never at once; every attempt that does not retire the registration counts towards `lastChance`.
2. MATERIAL, iOS `sync` is not "when back online": FOLDED at D1, D2 and §11, taking the second of the two decisions offered. The shared word is "at the next chance the platform gives the app to run while online"; D2 says iOS's timing (the next refresh wake, a processing wake, or the next launch) and that an app whose bytes must leave promptly uses a transfer; Harmony's feature 1 is renamed and its README says it; hand drive 9 records the time an iPhone takes. A discretionary `URLSession` was not taken as `sync`'s carrier: it runs one HTTP request, not app code, and Harmony's outbox is a sync round.
3. MATERIAL, a flex equal to the period breaks the floor: FOLDED at D2. Flex is WorkManager's minimum (5 minutes) and the repeat interval is `minInterval` plus the flex, so no run comes before `minInterval`.
4. MATERIAL, the first periodic run's due time: FOLDED at D1 and §11. The first run is due `minInterval` after registration; drive 3 shows the refusal, advances the clock, and taps.
5. MATERIAL, Android's retry has no headers; the query is in the record; the body is not in custody: FOLDED at D3 and D10. The record keeps the URL without query or fragment on every platform; on Android the headers and the query are kept in the secret store `secret.keep` uses, keyed by registration, deleted at retirement; the upload body is copied into the host's transfer directory before `backgroundFetch` answers.
6. MATERIAL, the iOS relaunch sequence: FOLDED at D8 and D10. The background session and its delegate are ExactKit's, made synchronously inside `handleEventsForBackgroundURLSession` with no package code; a session boots only at `urlSessionDidFinishEvents`. Before the first unlock a download that cannot be moved is recorded failed (`before-first-unlock`). Whether an upload's response body survives a relaunch after a system termination is measured on an iPhone before stage 2 builds; the record always keeps status and safe headers, `bodyLost` says when the body is gone, and Harmony then names its asset by a key of its own (a Snapback change made only then). The reviewer's claim that the session must be made before the call returns is taken as the safe order; Apple's text says to use the identifier to make the session, without naming the moment.
7. MATERIAL, retirement on invocation completion loses a failed follow-up: FOLDED at D10: explicit `retireBackgroundFetch(id=)`, with redelivery (at most three) until then; §11 retires after the write is admitted, and drive 7 checks a refused write's redelivery.
8. MATERIAL, the boot path, LLP 1113 D4's storage rule, the owner thread, streams, and the budget's start: FOLDED in parts. D7 says plainly that a wake launch is outside `rules/RULES.md`'s boot row and asks Charlie to word that line (Q12), since the file binds and this RFC cannot amend it alone; §12 lists it. D6 amends LLP 1113 D4 for a wake invocation: it may start storage, and the wake waits for it to land. D7's headless boot lays out and publishes one frame before the first event, so an attaching view has a frame without the owner thread. A session a wake booted opens no stream resource until a view attaches and is ended, its boot requests cancelled, when the wake is done with no view. The budget starts at the first event's delivery; an expiry before it is not an attempt. LLP 1133.004 D6's delivery rule was already extended in D7; that stays.
9. MATERIAL, overlapping wakes: FOLDED at D5: wakes are serialized per session, a platform callback arriving during one is queued, each platform object is completed by its own wake, and one expired while queued is completed unsuccessfully.
10. IMPLEMENTATION-PHASE, resubmission timing and the delegate queue: FOLDED at D8 (resubmission on entering the background and at the end of each wake) and D10 (the delegate's own queue).
