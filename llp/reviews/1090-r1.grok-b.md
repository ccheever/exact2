## Findings

1. **MATERIAL — §3 D4.** The elision rules accept values the runner refuses.

   One string is not bounded by `MAX_STRING`. `Opcode::LoadResource` pushes the answer with no extent check (`runner/src/vm.rs:589-603`). `Opcode::Str` pushes a plan string the same way (`vm.rs:546-550`). `Value::decode` caps depth at 64 and does not cap bytes (`plan/src/value.rs:326-345`). `too_long` applies to action arguments and writes (`runner/src/runner/commit.rs:7-11`), not to every input of `eval`. A record whose only string came from a resource can be past `MAX_VALUE_BYTES`. Skipping `K` because `Σ strings ≤ 1` makes JS succeed where the runner traps `ValueTooLarge`.

   “With two string parts it emits the length sum only” is a JS `.length` sum unless it says otherwise. Two strings of 2^25 CJK units have `.length` sum 2^26, which does not exceed `MAX_STRING`, and UTF-8 size about 2 × 3 × 2^25, which does. Three or more string parts are unspecified. “Specialized to the item’s string fields” does not require `strings(T)` finite, so a direct string plus `list<string>` can drop the list’s bytes. An `option<string>` field is `null` or a string; reading `.length` throws `TypeError`, which is not `Trap`.

   The 255 × 65,536 bound is arithmetically right for one map whose items are list-free (`65,536 × 255 + 1 = 16,711,681 < 2^24`). It must not be applied to an item whose `maxNodes` is infinite.

   “Correctness never depends on D4” is false while these rules are the ones stage 3 may emit.

   **Fix:** Elide a string check only when every string producer is itself a checked op (`cc`, `xj`, `xm`/`xf` byte accounting, the encoders). Otherwise keep D3’s `3*u` test, and sum UTF-8 byte counts, not `.length`. Specialize only finite string leaves that are not under a list, and treat `null` as 0 bytes. Any other shape, including `?` and three or more strings, calls `K`. Run D7 with elision on against a resource answer and a plan literal that are already past the cap.

2. **MATERIAL — §3 D1, D6.** A handler-argument trap does not refuse the commit.

   Arguments are inlined into the listener: `(...v)=>a_N(args, ...v)` (`host/web-js/src/emit.rs:1171-1172`, `:1232-1233`). `act` starts `commit` only around the action body (`host/web-js/rt.js:206`). `on` does not catch (`rt.js:769-776`). A trap in an argument is an uncaught listener exception. D6’s table says that evaluation refuses the commit and rolls the journal back. Wrapping each argument in an IIFE still runs before `a_N`.

   D7 case 4 only requires two 40,000-step handler arguments to succeed. That passes even when the throw never enters `commit`. The refusal path is untested.

   Resource arguments are already inside the memo `commit` settles (`emit.rs:427-429`, `rt.js:392-394`). Splitting that one callback into separate memos would change who subscribes.

   **Fix:** Pass thunks and force them inside `commit`, for example `act` becomes `(...a) => commit(() => fn(...a.map(x => typeof x === "function" ? x() : x)), "action")` and the emitter writes `(...v)=>a_N(()=>expr, ...v)`. Compiled values are not functions, so event payloads are not called. Keep the `rt.js` edit to that one line (1,498 of 1,500). Add a D7 case whose handler argument traps and whose following step shows a rolled-back commit on wasm, JS, and Linux. Leave resource arguments inside the existing `args()` callback; an IIFE per argument there is enough.

3. **MATERIAL — §3 D1, §4.** Several runner reset points are not one context per Code, and `expression()` will delete a context that is not a block.

   `code::expression` throws away the function wrapper whenever the body is an expression (`host/web-js/src/code.rs:99-101`). The D1 snippet is statements (`const o = enter(); try { … } finally { leave(o) }`). Those survive only if `wrap` (`code.rs:105-112`) emits a block, so the strip does not peel it and the call site becomes `(()=>{ … })()`. Map and filter callbacks must not enter and leave; they share the caller (`code.rs:432-434`).

   Row-state initializers are several `code::expression` results inside one row function (`host/web-js/src/regions.rs:72-81`, `:120-129`). One `try/finally` on that function charges two initializers against one budget. The runner evaluates each initializer alone, so the second of two 40,000-step initializers would trap on JS only. §4 asks for one context per resource argument and per handler argument. It does not ask for one per row initializer. D7 case 4 covers three row keys and two handler arguments, not two initializers. The same sharing applies to any other `expression()` site if the context is placed on the parent callback (surface arguments, list-option bindings).

   **Fix:** A metered `expression()` result is its own IIFE, including each row initializer, each surface argument, and each list-option binding. Do not wrap the row builder: it also builds DOM. State that an unmetered straight-line expression stays stripped. Extend the emitter test and D7 with two metered row initializers of 40,000 steps that both succeed, and with one that traps during `flush` and poisons.

4. **MATERIAL — §3 D5.** The ceiling describes an inlined loop. The helper API does not emit one, and the published JSC ratios do not reproduce on the machine the table names.

   Re-ran on this host (`sysctl` brand string Apple M5 Ultra, `bun` 1.4.2). Same-file shapes in `/tmp/budget-bench.mjs`, then cross-module shapes in `/tmp/budget-bench2.mjs` importing `/tmp/budget-ext.mjs`, medians, opaque strings so `+` cannot constant-fold. V8 was not re-measured.

   | Shape | RFC JSC | Reproduced JSC |
   |---|---|---|
   | Binding, no context | 2.2 ns | 2.2 ns (cross-module) |
   | Binding inside `enter`/`leave` | 2.2 → 3.7 | 2.0 → 3.4 same-file; 2.2 → 2.4 cross-module |
   | `map` of 48 numbers, steps only | 107 → 95 | `.map` 47 ns; inlined loop 54 ns; cross-module `xm(list, f)` 54 ns (+15% vs `.map` 47) |
   | Generic extent per item | 107 → 161 (+50%) | Inlined scalar walk ~53 ns (same as `.map`). Cross-module `xm`+`ext` 64 ns (+36% vs 47) |
   | 1,000 strings → records, generic `xm`+`K` | 5,240 → 15,280 (2.9×) | `.map` ~4,550 ns; outlined `xm`+`K` ~20,500–20,900 ns (~4.5×) |
   | Two checked concatenations | 4.0 → 5.8 | Opaque `+` 5.2 → `cc` 6.2 (+19%). Four opaque concats 9.3 → nested `cc` 17.2 |

   A focused re-run of inlined `3*length` against `.map` for 1,000 strings, five medians, ratios 0.927, 0.926, 0.929, 1.054, 0.982. An inlined step loop plus `3*length` in the same compilation unit meets a 10% ceiling. A callback into another module does not: `xm(list, f)` is slower than `.map` on the 48-number map, and the outlined record walk is about 4.5×. The “steps only is faster than `.map`” row is the inlined loop, not `xm(list, f, pc)`.

   “No measurable cost in a Code with no list step” contradicts “`cc` is never skipped.” A four-concat template is +8 ns absolute (~+85% on the microbench). “Nothing on an app that does not use `map`” fails once `cc` or an `act` string check is linked. Absolute generic cost is tens of microseconds (about +15 µs for the 1,000-record walk), which a frame will not show. The 10% line is what forces either inlining or the D4 lattice.

   **Fix:** If the ceiling stays, stage 3 emits the presized loop in the app module (step, body, integer add, and for a known string field `3*length` inline). `budget.js` keeps the trap class, the exact UTF-8 counter, and the fallback walk. Drop the claim that the helper call is the fast shape. Hold stage 3 to `host/web-js/bench.mjs` frame time, and treat 10% as a goal for that inlined path. Publish the harness (warmup, what is timed, per map vs per element); the current nanoseconds move with script size.

   **Fix:** Say that the exact recount replaces the accumulator, and add that pair to the emitter or conformance tests (two BMP strings under the cap on the upper bound, then a continuation that needs the exact count and must agree with the runner on which construction traps).

## Open questions

1. **D2 is acceptable.** Take it. A `Some` has one child and cannot multiply nodes; the doubling attack is still records and lists, and those stay counted. A factor of two on option-heavy values does not weaken that bound. Boxing would change `eq`, `conforms`, the DOM bindings, and the data seam, and it would allocate per optional. The runner change is the small one. Keep `ValueTooDeep` in the VM for plans the runner did not compile.

2. **Make `type-too-deep` a Contract rule.** Every target then refuses the same programs, and the JS target can skip a depth walk. Shapes cannot recurse (`contract/types/src/checks.rs:331`), so a value of a closed shape is no deeper than its type. D2’s “unreachable for a compiled plan” does not cover `?`. LLP 1088 §9.2 has not proved an unknown type nests at most 64. Exclude `?` from the depth claim, or keep a runtime depth walk where the type is unknown. Nothing in this repo nests near 64; that is not a proof for `?`.

3. **The 10% ceiling is tighter than §9.1 needs.** Finding 4 is the measurement: the inlined loop can sit near `.map`, and the outlined helper cannot, at about 4.5× on the 1,000-record map (~20 µs here). Prefer absolute frame time from `host/web-js/bench.mjs`. Do not hold stage 3 on Crypto or Bluesky fling numbers. Bluesky is not in this repo, and the in-repo list steps are the small filters in finding 8. The ceiling can remain a non-blocking goal for the inlined path. Stage 2, unelided, meets the LLP 1088 §9.1 precondition once findings 2 and 3 are fixed. Do not block list construction on D4.

4. **A separate `QUEUE.md` line.** Not this LLP. D2 makes `some(none)` irrelevant to the bounds (`code.rs:12-13` still collapses it). Refusing `option<option<T>>` and `option<unit>` is a Contract change with no role in the list-construction precondition.

**Cheaper design that still meets §9.1.** Ship D1, D2, D3, and D6 with the handler thunks and the per-expression IIFEs. Emit an inlined loop: step, body, and an integer add. For a known string field add `3*length` inline; call the outlined walk in `budget.js` only when the type is unknown or contains a list. That is the “specialized” row without a symbolic stack in the translator. Keep a local elision only for a list-free literal with at most one string, and only when every string producer is a checked op. D4’s type lattice is optional speed work. It is not the precondition.
