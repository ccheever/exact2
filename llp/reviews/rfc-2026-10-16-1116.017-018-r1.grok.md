**1116.017 is a RETHINK. 1116.018 is READY WITH CHANGES.** The quality problem is real, and it is fixed by a refusal that names an edit which keeps the feature. Accepting the form is the wrong tool for almost every row in 1116.017.

## 1116.017 — the rule is wider than the cases that pass it

The tests in §2 are the right filter, and they are the decision LLP 1116.014 already made: one meaning, no second name, nothing supplied that the author did not write. The slogan in §0 ("when the compiler can name the one edit, it compiles it") is looser than those tests, and several proposed rows fail the tests.

I checked the rows against the compiler.

**Several roots fail T1 and T3.** `lower-one-root` in `contract/lower/src/lib.rs` says "exactly one node" and names no edit. That hole is why Muse dropped a heading on 5 screens. The fix is to name the wrapper. An implicit bare block (`display: block`, LLP 1001) supplies a parent and a vertical axis the author did not write. The RFC's own example is a heading and a list side by side; a block stacks them, the screen compiles, and nothing teaches `row`. A `list` that was going to be the screen's root stops being the root, so scroll, safe area, and the navigation bar attach to a box the author cannot see. §9 question 3's answer is yes: it is a trap.

**Symbol `width` → point size fails T1 and T3.** LLP 1069.011.001 already says a symbol's point size is `font-size` on the image. `width` is the box. `contract/lower/src/buttons.rs` tells the builder to drop the width to keep the native button. Rewriting width as point size is a second meaning.

**A styled button inside a grouped-list cell is not a faithful rendering.** `contract/lower/src/grouped.rs` marks that button `button-context: grouped-list row`, and `contract/lower/src/controls.rs` refuses a native button there. UIKit's row is a plain cell. Drawing `buttonStyle="filled"` inside the cell is the tell LLP 1115 exists to stop. Author > platform applies when the same property can be drawn either way. This is a capability gap: the cell and the filled button are different controls. The two honest edits are the plain cell, and a custom button that is not a row. 1116.014 already chose "native first, both edits named."

**A footer that comes and goes is the two-section form.** `stray_message` in `grouped.rs` already says so, because section margins depend on whether a footer exists. Compiling "footer while the condition holds" is faithful only if those metrics follow the condition. The one case that does have a single meaning is an `if`/`else` whose every arm is one text: that is the ternary the message already names. That rewrite belongs in 1116.018, with a test, and only there.

**`h1`, `src`, and one-value `margin-inline` are second spellings aimed at the cold corpus.** The hint in `contract/lower/src/tags.rs` already says a heading is `text role="heading" aria-level=1`. `heading_style` sets the platform's title size and weight, and does not bring an HTML heading's margins, so an HTML reader and an Exact reader do not share one meaning. `src` is the image's positional argument (`PropId::ImageSource`); vocab currently says it belongs to `iframe`. `lint.rs` already rewrites one-value `margin-inline` to left and right. Accepting each leaves the old spelling in place, which is the circulation problem 1116.014 closed under "Delete; don't deprecate." Teaching a subset also invites the rest: `p`/`div`/`ul`, and `margin-inline-start`. LLP 1116.016 §7 watched that happen with TypeScript.

**Real builds do not hit D1 or D2.** Of 104 builds, the common ids are `lower-attr-value` (55 sites, stays refused), `lower-button-style` (40), `syntax-expected-newline` (11, and the RFC says those are generics and indexes), `lower-grouped-list` (9), and `lower-css-shorthand` (26, stays refused). The cold corpus is the population 1116.014's reviews said over-counts what a lookup fixes. Average 1.75 sites, and LLP 1116.014 already priced repair at 4.4% and 3.4% of tokens. LLP 1116.016 then showed better messages do not cut repair rounds. The quality claim that remains is the loss table, and LLP 1116.016 already showed the shape of the fix: naming the order took Muse from 1 of 18 to 15 of 18.

### §9

1. **Move the line in, to "refuse, and name the edit that keeps the feature."** D4 stays. Confidence: high, about 85%. I would move it back out only for a rewrite that is punctuation the grammar already uses (an indented `fn` body that is still one expression, as `on_its_line` in `contract/syntax/src/parser/names.rs` describes) or the single-text footer ternary. Neither is worth this RFC on its own.
2. **Keep the conflict an error, with both edits named.** A warning is an acceptance in a loop that stops at a clean compile, and LLP 1115's tell test is then left to a later grader. Confidence: high, about 85%.
3. **Yes. The implicit block is a layout the reader cannot see, and it has two axes.** The message should name `column` and `row` and repeat the author's nodes. Confidence: high, about 90%.
4. **No.** D4 plus 1116.018's messages cover the losses that were measured. Acceptance adds spellings and tells for a token effect inside the noise. Confidence: high, about 80%.

## 1116.018 — the standard is right, the net is too wide

"A refusal names an edit that keeps the behaviour" is what LLP 1116.016 T4 already requires for TypeScript, and what the loss table shows is missing elsewhere. The three kinds in §1 are the right taxonomy for the corpus: no edit, an edit that means less, a refusal on every host for a gap on one host. Kind 1 and kind 2 are a message standard. Kind 3 is a host-semantics decision and should not ride along.

The run-every-refusal test is too strong. There are about 330 diagnostic ids. A parse error has no screen to run. A generated oracle that restates the message will agree with itself; LLP 1116.016's audit already required expected values to come from outside Contract. The predecessor's D5 bar (the edit compiles, and the message says where it differs) is the right bar for the long tail. A running comparison is the right bar for the loss rows and for any message that claims "the same thing."

### §9

1. **Keep the standard. Apply the running test only where the message claims the same screen behaviour.** Everywhere else, keep D5: the edit compiles, and any difference is in the message. Confidence: high, about 85%.
2. **Leave `aria-atomic` refused, and name the gap in the message.** A documented no-op makes a written attribute false on iOS, which is a second semantics, and the evidence is one screen. Say that the web would announce it, that UIKit has no counterpart, and what to write so both hosts show the change. Where nothing works on both, the refusal stands and the RFC says why, which is D1's own last rule. Confidence: medium-high, about 70%. I would accept a warning that names the hosts if a later census showed builders deleting load-bearing web ARIA often; I would still avoid a silent no-op.
3. **The judge nominates. It does not decide.** Muse's keep rate moved from 19 of 32 to 15 of 33 across compilers with no quality change, and the judge counted `parseNumber` rejecting `"12abc"` as a loss even though that is a declared deviation. That spread is the size of the effect. Confidence: high, about 85%.
4. **Yes, three kinds the table does not cover.** A repair can keep the feature and still lose the platform control or add a tell (Astra's point on 1116.014, and the button-style rows). A repair can "lose" the feature because the keeping edit lives in the data module the guess prompt says is written separately (the order result in LLP 1116.016 §7). And the larger real-build cost is warnings builders treat as errors: `lower-header-unplaced` on 19 of 104 builds and `analyze-read-after-assign` on 15, which 1116.017 §3 defers. Those are outside this standard.

The D3 rows that should ship are the messages: `timer` → the builder's own `task` and `every(...)` (LLP 1092 stays the only timer); `parseNumber` states the `"12abc"` difference; the radio `change` keeps the guard; the button's `role` becomes `aria-label` or a custom face. `lower-one-root` and the footer stay refusals whose message contains the author's nodes. They should not wait on 1116.017 to accept them.

## Whether §7 can tell success from noise

**1116.017's plan cannot, as written.** Targeted ids falling to zero on a frozen fixture is real and would happen by construction once you accept the form, including a form that compiles to the wrong screen. "Clean screens do not fall" sits inside the run-to-run spread LLP 1116.016 measured (GPT clean 26 vs 29). "Whole repairs rise" sits inside judge noise. "Compile error sites fall" counts a warning as success, which is D3's failure mode. "No grader names a tell" assumes graders score tells; `scripts/no-tells.mjs` lists literals.

**1116.018's plan has the same aggregate problem.** "The share rises in both models" can pass or fail on the spread above. "Rounds to clean do not rise" is the measure LLP 1116.016 already saw stay flat (about 1.3 and 1.7), so it does not speak to quality. "Every refusal has a case" can pass with oracles that restate the message.

What would separate them: pin the loss rows (timer, one root, footer, `parseFloat`, radio, `aria-atomic`, button role). Re-repair those same screens. A person marks each whole or partial. Success is those rows becoming whole, with rounds not up. Report the judge's rate and do not gate on it. For any acceptance that draws through a platform conflict, run the no-tells check on that screen and treat a shipped tell as failure. Keep the cold corpus for D4 only: a fresh guess run, scored on whether the guide's old wording still appears, separate from compiler changes. Leave tokens out of the stop rule. The effect is inside one comparison's noise, and both drafts already say so.

## Verdict

| RFC | Verdict |
|---|---|
| 1116.017 | **RETHINK.** Keep D4. Keep the T1–T5 filter as a standing refusal policy. Drop the acceptances. The footer ternary, if it is done at all, is a tested rewrite under 1116.018. |
| 1116.018 | **READY WITH CHANGES.** The standard stays. Narrow D2 to the loss rows plus D5's compile bar. Keep host gaps as refusals whose message names the hosts. Decouple one-root and footers from 1116.017. Change the stop rule to a person's reading of the pinned rows. |

**Do these three, in order:**

1. Ship the keeping messages for the pinned loss rows, including a `lower-one-root` edit that wraps the author's nodes in a named `column` or `row`, and a footer edit that is the ternary or the two sections. That is the measured quality win, and LLP 1116.016 already showed that naming the kept behaviour stops the loss.
2. Leave author/platform conflicts as errors that name both edits. Map a symbol's size to `font-size`. Leave a grouped-list row a cell.
3. Judge those pinned rows by a person on a frozen fixture. Use D4's guide rewrite, capped at +200 bytes, as the cold-corpus experiment. Spend the next census on the warnings real builds actually stop for (`lower-header-unplaced`, `analyze-read-after-assign`), which outnumber these acceptances.
