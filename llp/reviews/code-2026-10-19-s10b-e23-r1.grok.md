## Should-fix

**1. A `when` that is the dial never becomes a set-dial.** `tamber/src/export_dials.rs:66-78` promotes a token only when its operation list is exactly one `SetToken` with an empty `when`, and only `decl.value` (the default line) is compared to a colour dial name. Any other shape is left as literals.

That misses theme2 Q6. A winning line that is the dial, including a `when`, should be one `set-dial` when every such line agrees on one literal.

- `accent.fill = accent` / `when contrast=more: accent`, every context changed to the same literal: reimport emits two `SetToken`s (`tamber/src/export.rs:1062-1080`), the single-op test fails, and both lines are pinned. If those lines were the dial's last references, the later trial (`tamber/src/export.rs:1326-1340`) refuses the token with `tamber-dial-inert` and the import answers nothing to propose.
- A dial that appears only on a `when` (`when` non-empty at `export_dials.rs:72`) is pinned the same way.

A `when` that is an expression, or two lines that disagree, correctly stays a pin. An unchanged `when` that still names the dial rides along with a default-line promotion, and `impact` lists those tuples because `checked.dials` is behavioral. That part matches Q6; nothing in `tamber/tests/it/export_dials.rs` covers it.

Fix: a token contributes to a dial when every `SetToken` it has replaces a line whose text is exactly that colour dial, and the values are one literal. Drop those ops for one leading `SetDial`. A token with any other line does not contribute and does not veto another token that does.

**2. Impact is the whole transaction, so a sibling pin hides the dial's reach.** `tamber/src/export_dials.rs:190-209` applies `ops` (every `SetDial` plus every later `SetToken`) and records only tuples whose folded value changes. A pin on a token that also depends on the dial replaces `after` with the pin's literal. If that literal equals the current colour, the token is omitted. Partial accept plans the ticked items again (`docs/tamber-protocol.md` under `accept`), so accepting the dial alone moves tokens the review did not list. Q6 asks for every token that dial moves, per tuple.

Fix: for each `DialChange`, `apply_all` only that `SetDial` against the current design and diff. Keep the pin list on the `SetToken`s.

**3. A new narrow `when` is marked with every line of the token.** `tamber/src/export_dials.rs:163-170`: when no existing `when` has the same conditions, `follows` is the union of the default and every `when`. A narrow `when` whose tuples followed only `accent` also picks up names from other lines (`lift` on a dim line, for example). Replacements of an existing `when` clone that line's conditions (`export.rs:1072`), so they match; the union is only the new one built at `export.rs:1212-1226`. Whole-word matching itself is right: `names` (`export_dials.rs:217-222`) treats `.`, `-`, and `_` as word characters, so `accent` does not match inside `accent.fill`.

Fix: take `follows` from the winning line for the tuples that `when` covers (`branch` in `export.rs`), not from every line on the token.

**4. The recognised-digest list does not fit in the stdio headroom.** `scripts/tamber-server.mjs:103-104` allows an HTTP body of `LINE_LIMIT - 64`. `importHeld` (`1103`) then adds `recognised` (the in-memory list, capped at 64 digests at `714-716`, about 1.2KB) and a request id on the line `ask` writes (`354`). A body the HTTP cap accepted is refused 413 inside `ask`. It fails closed; it does not widen what the client can do.

Fix: size the stdio check against the fields `importHeld` adds, or reject the HTTP body with that same reserve.

**5. A headerless file ignores the baseline the client just proved.** `plan` inserts the carried text at the front of `kept` (`contract/cli/src/tamber_import.rs:209`) only after the digest is recognised (`197-203`). `baseline_for` (`tamber/src/export.rs:666-686`) uses that text when the incoming header names its digest. With no header it picks by context keys among every kept export and a fresh export. After any edit, fresh has the same contexts and another digest, so the import is refused with "more than one export". That comes back as a source refusal, HTTP 400 (`tamber-server.mjs:1104` only maps `stale` to 409), not "pull first". A plugin that keeps `$extensions.exact.digest` is fine. One that drops it cannot reimport after a concurrent edit, which is the case the carried baseline was added for.

Fix: when the client named a baseline and the incoming file has no digest, use that baseline if its context keys match the file. Leave the "more than one export" refusal for a file that names no baseline.

## Nit

- **Impact colours and the dial value are different spellings of one colour.** `before` / `after` go through `Value::css` (`tamber/src/fold.rs:107-114`, `#rrggbbaa` or `light-dark(...)`). The `set-dial` value is the 6-digit `#rrggbb` reimport writes. Worth one clause in the protocol sentence so a client does not compare them as strings.
- **Same dial, two spellings, counts as a disagreement.** `export_dials.rs:90` compares the value strings. `#ff0000` and `#FF0000` both stay literals. Reimport's own writer usually emits one spelling; normalise before the compare if a tool does not.
- **A baseline is checked for every kind.** `tamber_import.rs:188-209` runs before the importer is chosen. `shadcn` / `tailwind` / a foreign DTCG file ignore `kept` and still 409 when the baseline's digest is unknown. Skip the check unless the file is a Tamber export.
