## 1. Verdict

**NOT READY** — Stage 0 can start, but as written the headline Safari leg, early-tap metric and reporting index would not produce credible numbers. See [LLP 1152](/Users/ccheever/projects/exact2/llp/1152-the-web-shootout.rfc.md:1).

## 2. Direction

The shape is fundamentally right. Confidence: **72**.

Two real applications plus an external microbenchmark is the correct triangulation. Conduit tests routing, fetching, SSR and forms. The feed tests rendering and scrolling at scale. Krausest supplies an externally owned update benchmark that Exact cannot be accused of designing. Tiering is also sensible in principle.

That direction remains sound only if the first round is much narrower and deeper. The present design multiplies roughly forty arms by two applications, expert variants, five legs, network conditions, CPU conditions, cold and warm loads, and a ten-minute soak. It will spend most of its budget resurrecting implementations and operating devices. It will then have too few repetitions where statistical confidence matters.

## 3. Major oversights

1. **The iPhone Safari leg has no demonstrated measuring route.** This is described as the most important leg. Yet [the proposed bake-off driver](/Users/ccheever/projects/exact2/bench/bakeoff/drive.mjs:2) drives iOS Simulator applications only. Separately, the probe assumes Safari supplies most PerformanceObserver entry types, with `longtask` as the notable exception. WebKit support for paint, Largest Contentful Paint, layout-shift and Event Timing cannot be assumed as a uniform set. Exact itself guards paint availability in [its capture script](/Users/ccheever/projects/exact2/host/web-js/capture.js:1). **Resolve it:** make a Stage 0 device spike produce an entry-by-entry support matrix on the exact iPhone and iOS version. Define a real-device touch route. Predeclare fallback metrics and “not measured” cells before building arms.

2. **The early-tap experiment does not define a repeatable successful tap.** It repeatedly taps one Conduit favourite. In Exact, a signed-out favourite is a link to registration, so an early successful tap changes route rather than toggling state; see [the RealWorld contract](/Users/ccheever/projects/exact2/apps/realworld/app.contract:478). Once signed in, repeated taps alternate the desired state and enter a network mutation queue. A late replay can therefore be indistinguishable from a lost or superseded tap. The self-reported `app:interactive` mark is also not comparable across hydration, resumability, server-driven HTML and Exact. Exact writes `bootMs` immediately before replaying captured input, not after replay effects have painted; see [the JS runtime](/Users/ccheever/projects/exact2/host/web-js/rt.js:1425). **Resolve it:** sign in from a seeded session, use distinct or idempotent local controls, and define success solely by externally observable state and paint. Treat the framework mark as diagnostic evidence, never as the metric.

3. **Community Conduit arms will often measure bit-rot, not current frameworks.** The rules permit an implementation two majors behind to enter at its own version. That cannot support conclusions about current React Compiler, Vue Vapor, zoneless Angular or other current claims. Upgrading those applications is frequently not mechanical. The statement that Tier 1 port cost is near zero is therefore the central schedule risk. **Resolve it:** restrict the headline table to maintained implementations on the pinned current framework major. Put older catalogue entries in a clearly labelled historical appendix, or replace them with newly built current-major arms. Pilot three difficult catalogue arms and record actual resurrection cost before committing to the field.

4. **Server-rendered and server-driven arms lack a fair server model.** Their application servers, the Conduit API, the proxy and the browser apparently share the Studio. Server CPU then competes with the measured browser, while server CPU and energy disappear from the results. This favours architectures that move work to an exceptionally fast, uncounted local server. The injecting proxy can also alter HTTP behaviour, compression, Early Hints, streaming, CSP handling and service-worker behaviour. **Resolve it:** place application and API servers on a separate pinned host. Record server CPU and response work per route. Validate three representative SSR arms with and without the proxy before adopting it universally.

5. **The reporting index is mathematically and interpretively unsound.** Ratios to the best arm fail or explode for legitimate zero values such as CLS, lost taps, blank samples and late frames. Higher-is-better and lower-is-better metrics require different ratio directions. Leaving unavailable metrics out of an arm’s mean rewards arms and legs with fewer hard measurements. Equal weighting is still weighting, contrary to the claim that ratios need no weights. A lab run also cannot establish a Core Web Vitals “pass,” which is a field p75 assessment. **Resolve it:** publish per-metric results and win/tie/loss summaries as the primary output. If an index remains, require complete data, define direction and zero handling, and disclose it as an equal-weight editorial index rather than a neutral measurement.

6. **The statistical plan is insufficient for the number of comparisons.** Medians, p95 values and an undefined noise band do not establish significance. A p95 from twenty taps is essentially an extreme observation. Dozens of arms and metrics guarantee apparent wins by chance. Phone thermal state, display refresh behaviour, battery state, browser updates and long interleavings are not controlled. This is a known hazard in the existing device work: [the heavy-list report](/Users/ccheever/projects/exact2/bench/heavy-list/README.md:50) warns not to compare rows run at different thermal states. **Resolve it:** use Stage 0 variance to preregister repetition counts, minimum meaningful effects, confidence intervals and tie rules. Record and gate on thermal state. Repeat headline comparisons independently rather than adding more arms.

7. **Several measurements are not portable across the named browsers.** Safari and Firefox do not offer Chrome’s CPU-throttling route. `measureUserAgentSpecificMemory` requires cross-origin isolation and cannot simply be mixed with CDP heap values in one column. Process accounting cannot cleanly attribute Safari’s shared processes to one page. Total browser CPU seconds are not energy: they omit GPU work, radio behaviour, display refresh and server work. `querySelectorAll('*')` also misses shadow-DOM contents, favouring web-component arms in the node count. **Resolve it:** maintain a metric-by-browser method matrix. Never merge unlike memory measures into one number. Rename the energy group to browser CPU unless real energy instrumentation exists on that leg.

8. **The applications do not fully answer the fine-grained reactivity question.** Conduit is mainly fetch-and-render. The feed primarily distinguishes virtualisers, image pipelines and list implementations. Krausest covers updates, but only as a Chrome desktop microbenchmark. Meanwhile, the proposed keystroke test names a feed “composer” that does not exist in [the heavy-list specification](/Users/ccheever/projects/exact2/bench/heavy-list/SPEC.md:51). Accessibility is only a reported Axe column, so a semantically poor or canvas-rendered arm could win performance while failing as an equivalent interface. **Resolve it:** add one measured many-independent-updates scenario to an existing application, define the editor workload as the same work in every arm, and make basic semantic and keyboard equivalence part of the correctness gate.

## 4. Errors

- **Real-device driving:** §6 says the bake-off driver can supply real iPhone touches. [That driver](/Users/ccheever/projects/exact2/bench/bakeoff/drive.mjs:2) is explicitly for “any iOS simulator app” and discovers its target through `simctl`. It is not a real-device Safari harness as written.

- **Long-task support:** §4.1 says `longtask` is available in Chrome and Firefox. The Long Tasks API’s browser-compatibility data lists Chromium support, not Firefox or Safari. TBT therefore has no Firefox route under the stated method.

- **Safari observer exceptions:** §4 presents `longtask` as the Safari-specific missing load metric and otherwise assumes the probe can collect the named entries. That is not established for Largest Contentful Paint, Layout Instability or Event Timing in WebKit. Those are separate specifications with separate implementation status. Exact’s own guarded paint observer in [its capture script](/Users/ccheever/projects/exact2/host/web-js/capture.js:1) shows that even paint requires a runtime check.

- **INP and the existing harness:** §4.3 calls INP “the worst interaction (p98)” and says the existing harness already measures through `event` and `first-input`. INP is the worst interaction only for low interaction counts; for larger counts it approximates p98 by discarding roughly one worst interaction per fifty. [The existing harness](/Users/ccheever/projects/exact2/bench/dioxus/web/bench.mjs:56) observes only `click` and `pointerup` event entries. It has no `first-input` observer and no interaction grouping.

- **Feed typing target:** §4.3 proposes typing into “the composer (the feed).” [The feed specification](/Users/ccheever/projects/exact2/bench/heavy-list/SPEC.md:51) requires only reaction-chip taps in rows. No composer is specified.

- **Builder alternation:** §8 says alternating the two builders as in [the bake-off pairs file](/Users/ccheever/projects/exact2/bench/bakeoff/pairs.json:1) means no framework is built by one model only. The pairs file fixes one model for each specification. Alternating one builder per framework still leaves every framework-by-application arm built by exactly one model, confounding builder and framework completely.

- **Prior bounded-feed standings:** §11 implies the bounded answer ended Exact’s losses on bytes, heap and tap latency, and says there were no late frames at any speed. [The recorded bounded standings](/Users/ccheever/projects/exact2/bench/dioxus/README.md:126) show Exact winning bytes but still losing heap, 4.1 MB to 1.8 MB, and tap latency, 24 ms to 16 ms. They say no more than one late frame per run, not zero at every speed.

- **Lighthouse on phone legs:** §9 proposes each arm’s Lighthouse score “on the phone legs.” Lighthouse drives Chromium through CDP. It cannot produce an iPhone Safari score. Its score also cannot be both excluded from the table under §6 and used as §9’s headline row without resolving that contradiction.

## 5. The eight decisions (§12 D1 to D8)

- **D1:** Run Tier 1 plus Krausest only in round one; defer Tier 2. Confidence **88**.
- **D2:** Provide idiomatic and expert feed arms only for a reduced headline field; do not double all Tier 1 arms. Confidence **78**.
- **D3:** Ask Krausest’s project first and do not add a Contract `table` tag solely for the benchmark. Confidence **82**.
- **D4:** Move the `xctrace` and Web Inspector investigation into Stage 0 with a fixed timebox and predeclared “not measured” outcomes. Confidence **92**.
- **D5:** Publish the first completed round, including losses, after a private factual-correction window for framework advocates. Confidence **72**.
- **D6:** Cross the builders: build every headline agent-built arm with both model families, or do not publish comparative authoring costs. Confidence **86**.
- **D7:** Use the Studio for browsers and devices, but put application and API servers on a separate quiet host. Confidence **84**.
- **D8:** Measure 0 ms, 50 ms and 150 ms, show 50 ms as the headline, and publish the full sensitivity curve. Confidence **94**.

## 6. The strongest alternative

Run a **small, deep shootout** instead of a broad, shallow one. Use Exact, vanilla/static baselines, React, Next.js, Svelte/SvelteKit, Solid/SolidStart, Vue, Angular and Qwik. Build both applications for every arm, have each implementation reviewed by a competent framework user, run many repetitions on every leg, and publish all sources and raw traces. Add Krausest for external update latency. This sacrifices catalogue breadth but can credibly answer the six questions.

The deciding measurement is a Stage 0 **variance-components pilot**: for the same primary outcomes, estimate how much variation comes from framework, builder, run and device state. If framework differences are not substantially larger than builder and run variation, the broad forty-arm table is not worth running. If framework effects dominate and three pilot ports prove cheap, the wider design becomes defensible.
