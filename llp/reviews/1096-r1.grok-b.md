## MATERIAL

### 1. A production Apple build never carries the sound arm
**Section:** D8, §4 Apple row.
**Problem:** D8 says `build.mjs` builds `libexact_sound.dylib` only when the plan declares a sound, "as it does `hasVideo`'s arm (`build.mjs:1043–1044`)". `hasVideo` is `carries('video')`. In a settled production build at store level 0, `carries` is true only for modules in `buildReceipt.graph.loads`. That list is derived from node types. A `sound` declaration is not a node, so `loads` never contains `"sound"`. Dev builds hide this because `carries` is true whenever the build is not settled. Stage 3's "heard on the simulator" exit can pass on a dev build while a shipped drums binary has no arm and plays nothing.
**Evidence:** `bake/src/receipt.rs:536–548` sets `loads` from `NodeType::Canvas`, `svg_islands`, `NodeType::Video`, and `NodeType::WebView` only. `host/apple/build.mjs:979–982` is `carries = (module) => !settled || reaches.includes(module)` with `settled` = release and store level 0. `build.mjs:1040–1044` compiles the video arm only when `carries('video')`. `leftOut` at line 982 is `['canvas', 'svg', 'video', 'web']`.
**Fix:** Teach `bake/src/receipt.rs` to add `"sound"` to `loads` when the plan's `sounds` table is non-empty. In `build.mjs`, gate the arm on `carries('sound')`, and add `'sound'` beside the four names in `leftOut`, the load list, and both copy sites (`1213–1218` and `1316`). Name `receipt.rs` in §4.

### 2. `audio_session` does not settle the ring-switch item, and a second writer can undo it
**Section:** D8 session, Q5.
**Problem:** Q5 says `app.json` `audio_session: "playback"` is app-wide and settles QUEUE's "iOS sound is silenced by the ring/silent switch" for an app that sets it, as the one piece of LLP 1042 §5's arbiter admitted here. The only reader D8 assigns is the sound arm. That arm is built only when a `sound` is declared (and, in production, only if finding 1 is fixed). QUEUE and LLP 1042 §8 are about `audio` and `video`, which declare no `sound`. Nothing in the bake reads the key: `Manifest` keeps raw JSON, and `host/apple/build.mjs` never mentions `audio_session`. Separately, ExactKit already sets the process-wide session. `CanvasAudio.activate()` writes `.ambient` once, from its own `configured` flag, not from the live category. If a canvas asks for audio after the sound arm has selected `.playback`, the next `activate()` puts `.ambient` back, and the ring switch silences the app again.
**Evidence:** QUEUE.md:8. LLP 1042 §5 item 3 (`llp/1042-video.spec.md:255–256`) and §8 (`439–441`). D8 at `374–376` and Q5 at `653–660`. `CanvasSeams.swift:684` is `if !configured { try session.setCategory(.ambient); configured = true }`, called from `requestAudio` at `782–791`. `AVAudioSessionTypes.h:95–97` (`AVAudioSessionCategoryAmbient`, mixes, unavailable on macOS) and `:471–474` (Playback still plays regardless of the ringer). `rg audio_session host/apple/build.mjs contract/cli/src/manifest.rs` finds no reader.
**Fix:** One ExactKit owner, loaded for a `sound` or for a `video`/`audio`, reads the manifest key and is the only `setCategory` caller. `CanvasAudio` must not set a category. State that a video-only app gets `.playback` only when that owner is ExactKit, not the sound dylib. Plumb the key through the bake the way `backgroundModes` is (`build.mjs:403`).

### 3. One `rate` indexes a buffer that D8 has already resampled
**Section:** D1, D4, D6, D8.
**Problem:** D1's `rate` is the file's sample rate, and D4's natural end is `at + frames / rate` in runner time. D8 converts each buffer to the output format with `AVAudioConverter`. D6 then places the first frame at `round((t0 + at/1000 - bufferHostSeconds - presentationLatency) × rate)`. Using the file rate as an index into the converted buffer shifts every onset and shortens every clip by `fileRate / outputRate`. A 250 ms hit in a 44.1 kHz file on a 48 kHz device lands at frame `0.25 × 44100 = 11025`, which is `11025 / 48000 = 229.7 ms`. The offline XCTest in §5 (`0.25 × rate`) passes if the test uses one rate for both.
**Evidence:** D1 at `170`, D4 at `231`, D6 at `313–315`, D8 at `361–363`. `AVAudioSourceNode.h:26–27`: if sample-rate conversion is downstream of the source node, the sample time is not valid.
**Fix:** Keep file `frames` and `rate` for duration in seconds. After conversion, index with the output format's sample rate, and set the end frame to the first frame plus the converted buffer's frame length. Say that the source node is connected in the output format so the engine does not convert again downstream.

## MINOR

### 7. The latency term is the device latency, and the XCTest cannot see it
**Section:** D6, D8, §5 Apple test.
**Problem:** The formula subtracts `AVAudioEngine.outputNode.presentationLatency`, which is device hardware latency. The source node is connected to `mainMixerNode`, so its downstream delay is `outputPresentationLatency`: the output node's presentation latency plus the output node's processing latency. The render timestamp is "the HAL time at which the audio data will be rendered," and downstream sample-rate conversion invalidates sample time. §5 feeds the mixer a host-time stamp offline. In manual rendering, output presentation latency is zero, so that test does not check the subtraction used on a device.
**Evidence:** D6 at `312–315`. `AVAudioIONode.h:115–123`. `AVAudioNode.h:218–238` (manual rendering is zero at `224–225`; a node in front of the output node adds processing latency at `227–228`). `AVAudioSourceNode.h:25–27`.
**Fix:** State whether `mHostTime` is already the HAL presentation time. Subtract only delay the timestamp does not include; use the source node's `outputPresentationLatency` for mixer and output processing. Keep the XCTest on frame indexes, and add a device check that the heard onset matches `at` within a few milliseconds.

### 8. The realtime-safe render block is not callable from Swift
**Section:** D8 mixer.
**Problem:** D8 puts the mixer, with no allocation and no lock, in `SoundArm.swift`. The initializer that requires a realtime-safe block is Swift-unavailable. The Swift-callable `initWithRenderBlock` may run on a realtime thread. The video arm's compile helper compiles one Swift file, so a C callback does not fit that helper as written.
**Evidence:** `AVAudioSourceNode.h:69–72` and `:82–88` (`__SWIFT_UNAVAILABLE_MSG("Swift is not supported for use with audio realtime threads")`, macOS/iOS 27). `host/apple/build.mjs:1023–1044` hashes one Swift source per arm.
**Fix:** Compile a C render callback into the dylib and let Swift only push the ring. Extend the arm compile past the single Swift file, and name that in §4.

## NIT

### 14. A player node still cannot stop an already scheduled voice at a future sample
**Section:** D8, §8.
**Problem:** The claim holds for a voice already in the node. `stop` takes no time, clears every scheduled event, and resets the player timeline to 0. It is slightly wider than the API: `scheduleSegment:frameCount:` can end a voice whose cut is known before that schedule. A choke that arrives on a later tick, which is the drums case, still has no future stop. Host time on a player node is ignored in manual rendering, so §5's offline test has to call the source-node render block with a sample time or a timestamp, not `scheduleBuffer(_:at:)` host time.
**Evidence:** `AVAudioPlayerNode.h:110–111`, `:125–128`, `:249–265`, `:286–298`.
**Fix:** Say "no stop at a future time for a buffer already scheduled." Keep the source node.
