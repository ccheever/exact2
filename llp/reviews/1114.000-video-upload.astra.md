1. **Verdict: RIGHT WITH CHANGES.**

2. **Overall assessment:** The ranged-body proposal is the right minimal addition. Bluesky’s current [multipart protocol](https://raw.githubusercontent.com/bluesky-social/atproto/main/lexicons/app/bsky/video/uploadPart.json) supports the central argument: upload file slices without moving the video through application JavaScript. I support R1, part-count progress, and retaining the 64 MiB cap. The significant architectural gap is in stage 3’s ownership and cancellation guarantees.

3. **Concerns:**

   **MAJOR — A long request does not provide the transcode cancellation guarantees D4 assumes.**  
   [D4](/Users/ccheever/projects/exact2-review-1114/llp/1114.000-video-upload.rfc.md:259) says replacing an answer aborts the transcode “for free.” The existing mechanism provides asynchronous completion and disposal of stale replies. [`Work::Later`](/Users/ccheever/projects/exact2-review-1114/runner/src/request.rs:613) passes its owner only a reply handle; the [executor’s handoff](/Users/ccheever/projects/exact2-review-1114/host/apple/src/executor_core.rs:764) passes no cancellation signal. Its [forget policy](/Users/ccheever/projects/exact2-review-1114/host/apple/src/executor_core.rs:380) explicitly allows effectful work to continue.

   Consequently, reusing this mechanism alone can leave an abandoned encoder running for minutes and eventually publishing its output, potentially overwriting a replacement operation’s file. Writing beside the destination and renaming prevents partial output; it does not prevent an obsolete operation from committing complete output.

   **Resolution:** Make cancellable work ownership an explicit part of stage 3. Specify how cancellation and session retirement reach the encoder, and how cancellation revokes permission to publish the destination. The existing [compressImage commit gate](/Users/ccheever/projects/exact2-review-1114/llp/1069.002-media-picker.rfc.md:261) illustrates the distinction already recognized by this repository. Preserve the long-request direction, but account for this additional lifecycle mechanism rather than treating it as inherited behavior. This need not delay stage 1.

4. **What it gets right:** Separating upload support from transcoding keeps the useful capability small. Matching [`Blob.slice`](https://w3c.github.io/FileAPI/#dfn-slice), retaining existing grants, avoiding a whole-file JavaScript round trip, and deferring transport-level progress are sound choices. Keeping codec work in an optional artifact protects the boot path. The proposed agent-visible results also give the capability an observable contract.

5. **Questions for Charlie:** I would split Q1 into approval of the compression capability and approval of its initial framework placement. D4 discounts T3 partly because an app module supposedly has no web equivalent, but [LLP 1067 D5](/Users/ccheever/projects/exact2-review-1114/llp/1067-native-later-and-swift-modules.rfc.md:89) already provides a web page module with long calls and device topics. That does not supply a transcoder automatically, but it makes the architectural alternative real.

   Should compression become a framework capability immediately, initially implemented only on Apple, or first be proven through the clone’s app-module seam? A shared built-in may still be preferable; the decision should rest on reuse, file access, and lifecycle costs. I would retain the recommendations for Q2–Q4 and condition stage 3 on resolving the cancellation concern above.
