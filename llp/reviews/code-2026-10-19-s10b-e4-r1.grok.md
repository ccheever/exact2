## Blocker

**Axis changes skip the conflict check and orphan Figma edits — `tools/figma-tamber/src/code.ts:85`, `tools/figma-tamber/src/mapping.ts:194`**

`check` rebuilds the fresh plan with `plan.collections[0].modes.length` as the mode cap, and `conflicts` pairs collections and modes by name only. A missing fresh value is ignored (`design === undefined` continues).

Adding one axis value to the theme fixture turns the stored 4-mode `Tamber` collection into three `Tamber · …` collections (6 contexts is over the stored mode count). Every `accent/fill` set to red in Figma then reports no conflicts. A renamed context does the same. `apply` goes ahead, writes the design into the new modes, and saves that plan. The next push reads only the new plan, so edits that were on the old modes are never proposed. On a collection already at its mode cap, `addMode` throws on the new names; that collection was not created in this attempt, so the `catch` does not remove it, and the retry adds a second set of Light/Dark collections beside it.

Fix: key conflicts by token and export context (`contexts`, or the header's `modes` and `scheme`), not by collection and mode name. If the context set changed, ask before apply. In `write`, migrate values onto the new modes, then `removeMode` and `variable.remove()` anything the new plan does not name, and roll those back if a later `addMode` throws.

## Should-fix

**A changed colour is not the 8-bit object re-import prefers — `tools/figma-tamber/src/mapping.ts:153`**

`fromFigma` writes raw floats and an opaque `#rrggbb`, with `alpha` only when `a < 1`. Unchanged values correctly keep the export object (oklch, `alpha`, `rem`, seconds). A changed one does not match `written_colour` in `tamber/src/export.rs` unless each channel is an exact byte: `alpha: 0.5` fails (`127.5` vs `128`), so the proposal becomes `color(srgb 1 0 0 / 0.5)` instead of `#ff000080`. `rem` to px, seconds to ms, and a changed family (always an array) do match `export_kinds::read`.

Fix: quantize each channel with `Math.round(clamp(x) * 255) / 255` before `components`, `alpha`, and `hex`. Omit `alpha` when the byte is 255.

**Re-pull never deletes variables or modes the design dropped — `tools/figma-tamber/src/code.ts:59`**

Modes are only renamed when the collection still has its single `Mode 1`. Later pulls `addMode` and reuse variables by name. Removed tokens, renamed tokens, and old context modes stay in the file. `setSharedPluginData('exact', 'token', …)` is written and never read, so a variable renamed in Figma is invisible to `holding` and its edits are kept as the baseline.

Fix: find variables by that token key, `remove()` variables not in the plan, and `removeMode` modes not in the plan. Catch only `in addMode: Limited to N modes`, and pass `made` into the second `write` so a 1-mode file does not leave a half-built collection (the second `write` currently has no rollback).

**Alias resolution uses another collection's arbitrary mode — `tools/figma-tamber/src/code.ts:22`**

Same-collection aliases work (`valuesByMode` is keyed by that collection's mode id). A cross-collection alias misses that id and takes `Object.values(valuesByMode)[0]`, which is whichever mode was created first (Dark, in this export's order).

Fix: resolve with the target collection's mode of the same name, then the same index. Do not use the first value.

**The baseline is one shared-plugin-data entry, capped at 100KB — `tools/figma-tamber/src/code.ts:99`**

`setSharedPluginData` rejects an entry over 100KB (enforced). The theme fixture is 24,244 bytes, so that pull fits. A larger export throws after the variables are written and before `plan` is saved, and the next push says "pull first".

Fix: split `baseline` and `plan` across keys under 100KB and join them in `stored`.
