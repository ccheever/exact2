The direction is right: Exact2 already wins on time, loses on tokens because of reading, and loses on quality because of what the hosts draw and a few traps. The decisions aim at those causes. Several of them stop short of the failure the grader actually saw.

## Decisions

**D1 — RIGHT WITH CHANGE.** Amending LLP 1115's web bullet is the highest-leverage quality fix. Exact2 lost every web pair on looks (platform 5–6 against React's 7–9) while code and robustness were even, and builders could not see it: the guide told them to leave presentation unsaid, and `no-tells` passed. Grey UA buttons, a 13 px checkbox for a switch, an unstyled dialog, and tabs with no selected state are tells by 1115's own test. Keep author > platform, with the new rules in `:where()` so an authored row still wins. The look has to include the surfaces the grades named, not only buttons, tabs, and an app bar: grouping (inset lists as cards, section rhythm), alert actions in a row with `destructive` in red, and field metrics at a real tap size. In the same stylesheet, restore the button's min-content floor. Flashcards squashed "End session" to "E… s…" because the web button sets `overflow: hidden` and `minmax(0, auto)`, which breaks the CSS layout oracle. Leave `facts.js` reporting the centred column's width as the viewport out of the first commit. That changes app logic. The rest of D1 does not.

**D2 — RIGHT WITH CHANGE.** The bottom cover, the header subtitle, keyboard avoidance by default, and `testId` as `accessibilityIdentifier` on bar items match repeated defects (the white band in five apps, household-list's missing count, unit-converter's covered fields, Maestro unable to hit Save). Two gaps remain. On weather, password-generator, and mood-journal the whole page was white in light mode, so grouped cards disappeared. The author had set `-exact-grouped-background` as the docs say. Dropping the 34 pt cover leaves that unpainted. Paint the route background and let an inset-grouped list run under the home indicator. And household-list lost the verdict with every sub-score in Exact2's favour because `expect text` and the default screenshot showed a count the navigation bar drops. Marks on the tree, plus a warning, leave that loop intact. The iOS screenshot the builder is told to trust, and any `expect` on a node the bar does not present, have to use the presented app.

**D3 — RIGHT WITH CHANGE.** A single-stack skeleton, diary-free `AGENTS.md`, and ship-quality recipes are the right attack on one-tab bars, copied "Synced" / `Refused: CODE` lines, and the fixed reading cost. The size target is too weak for the 20–30% claim. That estimate in the batch analyses was a ~150-line core. This draft goes from 30 KB to 20 KB and still points builders at `apps/shelf` (~500 lines, 37 KB in the anatomy) and at `contract-grammar` plus `contract-for-agents` (~200 KB of lookups). Point the lookup table at one short recipe per question builders actually searched for, and demote shelf and the long guides for those questions. Ten 80-line recipes read on top of a 20 KB start-here will raise tokens.

**D4 — RIGHT.** `--help` starts a server, runs the tests, or says `unknown op` on every verb, so builders read ~280 KB of CLI source and carried it on every later turn. A short per-verb text — purpose, flags, ports, whether it stays in the foreground, one example — that exits without starting anything is the clean token win. Keep it short so the help text does not become the next document replayed every turn.

**D5 — RIGHT.** Nine of twenty-four specs need a remembered setting. SwiftUI is `@AppStorage`. Exact2 is a resource, a mutation, a source, and grants, and builders skip it (persona resets on relaunch). Root `state … persist`, applied from the store snapshot before first paint, with each test starting empty, fits the runner store that already exists. It is the one decision that can make apps worse if the store leaks across tests or the first frame flashes, so last is the right place. It still has to land in this round. A recipe that restates today's boilerplate leaves those nine specs as a token and quality loss.

**D6 — RIGHT WITH CHANGE.** A non-fatal warning channel fits the traps that compile and then behave wrong: segment label ≠ text, header nodes the bar drops, a one-tab bar, and a `performanceNow()` value sent to a source. The stopwatch docs said the clock is "since boot"; the builder read them and still persisted it, and the virtual-clock `reload` confirmed the wrong theory. The warning is the real fix. A warning that does not fail `expect` on an unpresented node does not fix household-list. Also refuse a `column` that is a direct child of a grouped row. Password-generator and mood-journal both laid that out as a horizontal strip while tests passed.

**D7 — RIGHT.** Regular-weight headings were marked sparse on the web and on iOS. The web stylesheet sets `h1…h6 { font-weight: inherit }`, which strips the UA's own bold heading. That already violates 1115's precedence. Emphasized weight on content headings, an authored `font-weight` still winning, and the UIKit large title left on UIKit's regular weight, is the platform answer.

**D8 — RIGHT WITH CHANGE.** Grouped and currency `formatNumber` (tip-splitter's failed feature), determinate `progress` (refused in three batch-A apps, so builders painted bars), the favicon 404 on every web load, "since this launch", and naming `symbol:sf/` in the symbol refusal are all grader-visible holes. A number field should get a numeric pad with no authored `inputmode`. Unit-converter got an alphabetic keyboard and a QuickType "I'm" in a number. The spell exists, and it appears once in the long guide. Another start-here line repeats that miss. The `Math.random` refusal should name the randomness recipe. Trivia-quiz seeded a shuffle with 0 because randomness is refused and nothing pointed at a replacement.

## Missing

Three levers the evidence supports are absent.

- **A numeric readout style.** `no-tells` and "a title in a big `font-size` is a bug" produced a ~34 pt stopwatch. No text style is larger than large-title, and a hand-built Clock-style readout is ~80 pt with tabular figures. The rule made quality worse on the screen whose whole job is a number. Add a display style, or exempt a numeric readout, with `tabular-nums` as its default.
- **Per-run identity for backend tests.** In batch C, leftover rows on a shared dev server were the largest time sink after Snapback (on the order of a fifth of diary time, including ~20 minutes inside team-kanban). Findings say this recurs with Bun servers. Round 2's REST swap does not remove it, and D3's tests recipe does not mention a per-run id.
- **The presented tree as the test oracle**, covered above under D2 and D6. Batch C ranks "verification passed while the app was broken" second for quality, behind Snapback. Virtual-clock tests, authored-chrome screenshots, and `expect text` on dropped nodes are one class. Warnings do not close it.

## Order

Run D1, D2, and D4 together, with D3 beside them and D7 in the D1 lane. Web type is half of the web loss, and it is a lowering change, not an iOS host change. §11 puts quality behind docs. Those lanes do not depend on each other, and quality is the binding gap: 19 of 24 losses, against 0.85× the minutes and 1.23× the tokens. Then D6 and D8, including the numeric pad and the grouped-row refusal. D5 last, inside the round. Cut the `facts.js` viewport rewrite from the first D1 commit. Cut nothing else.

Judge round 2 on the pairs that were not Snapback losses. §10's move to a Bun server will move chat-rooms, team-kanban, and the other backend pairs by itself.

## Risks

D3 can raise tokens if the new recipes are read whole and shelf stays on the first page. D1 can lock in a mediocre house style if `no-tells` flags the overrides authors need for the few app-specific things (a progress ring, a big readout). The authored row has to keep winning, including against the linter. D5 is the only semantics risk, and sequencing it last is the mitigation. Leaving the iOS driver on authored chrome means builders will keep shipping what the screenshot shows. D1's amendment of 1115 is justified. The evidence says the browser's own controls are not "a well-made web page." Apple hosts stay out of that stylesheet, so the iOS win (native chrome, dark mode, say less) stays intact.

## Verdict

**READY WITH CHANGES.**

1. D1 adds grouping, alert action layout, and the button min-content floor. Defer the `facts.js` width change.
2. D2 paints the grouped route background, and the iOS driver and `expect` use the presented tree.
3. D3 cuts to a ~150-line core. Recipes replace the long-guide and shelf reads for the questions builders searched for.
4. D6 fails an `expect` on a node the host does not show, and refuses a `column` directly inside a grouped row.
5. D7 ships with D1. D1, D2, and D4 run in parallel with D3.
6. Add a numeric-pad default, a `Math.random` refusal that names the recipe, a display/readout style, and a per-run id for backend tests.
7. D5 stays last and stays in this round.
