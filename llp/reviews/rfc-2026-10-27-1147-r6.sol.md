Two fundamental issues remain.

Syntax, repeat phase, gate rollback, refusal continuation and clock takeover hold up at the design level. The existing JS live-clock tests pass 6/6.

1. **The web’s new rendering prerequisite can strand an uncapped `scrollend` timer.**

   [D7’s web row](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:285) permits checking scroll quiescence only inside `requestAnimationFrame`. [The wake rule](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:319) leaves a held timer no wake except its cap, which `scrollend` need not have. HTML excludes hidden documents from rendering updates, while ordinary timer execution need not stop. [HTML rendering algorithm](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering)

   Hide an otherwise quiet page before `after(100, save, wait=scrollend)` becomes due. Its deadline timeout executes, but its requested animation callback does not. There is no moving scroller, no future `scrollend`, and no cap. The action remains unfired indefinitely while the page stays hidden. R6’s fix for observing compositor scrolls therefore reintroduces the stopped-frame liveness problem for an uncapped wait.

   **Instead:** Give `scrollend` an explicit fallback when presentation is unavailable, including visibility-transition handling; retain the check after rendering’s scroll steps while rendering continues.

2. **Android’s proposed publication acknowledgement uses a number that does not identify publications.**

   [R6’s Android protocol](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:305) treats `Pub.seq` as the sequence of the last batch applied. It actually acknowledges scrolling: [`Owner.step`](/Users/admin/Developer/exact2-timer-wait-points/host/android/canvas/src/main/java/dev/exact/canvas/Owner.kt:283) assigns the last processed scroll sequence, and [`produce()`](/Users/admin/Developer/exact2-timer-wait-points/host/android/canvas/src/main/java/dev/exact/canvas/Owner.kt:402) copies that unchanged value into subsequent publications. [`takeOwned()`](/Users/admin/Developer/exact2-timer-wait-points/host/android/canvas/src/main/java/dev/exact/canvas/ExactView.kt:537) uses it to retire acknowledged scroll movements.

   Suppose the main thread has acknowledged sequence 0. Without another scroll, the owner publishes a new batch, also numbered 0. The main thread removes it from the queue and begins applying it. The previous quiet report still says “applied 0,” matching the latest publication’s 0. The proposed barrier cannot distinguish this unfinished batch from the previously applied one, so an `idle` timer can be admitted during application—the r5 failure persists.

   **Instead:** Introduce a separate monotonically increasing publication number, acknowledged after application finishes. Keep `Pub.seq` for its existing scroll acknowledgement role.
