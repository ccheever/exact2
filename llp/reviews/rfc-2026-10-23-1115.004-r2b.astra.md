For **F, choose option 1: literal modifiers plus a portability diagnostic. Confidence: 96/100.**

The repository claims are correct: the matcher compares modifiers exactly, and both Meta-only and paired declarations exist. `Meta` means the Windows-logo key on Windows; Win+N opens Notification Center. One correction: ARIA describes shortcuts—it does not install them; Exact supplies that behavior. [Matcher](/Users/ccheever/projects/exact2/host/linux/src/presenter/shortcuts.rs:70), [Meta-only example](/Users/ccheever/projects/exact2/apps/agents/app.contract:175), [paired example](/Users/ccheever/projects/exact2/apps/fieldnotes/app.contract:276), [W3C key definitions](https://www.w3.org/TR/uievents-key/#keys-modifier), [Windows shortcuts](https://support.microsoft.com/en-us/accessibility/windows/keyboard-shortcuts-in-windows), [ARIA](https://www.w3.org/TR/wai-aria-1.2/#aria-keyshortcuts).

Silently substituting Control changes an explicit author instruction and can create collisions. A lint should suggest the **corresponding** Control chord, preserving key and other modifiers. Show the declared Control alternative in Windows menus/tooltips; never label an undeclared binding “Ctrl”.

`Meta+Control+F` remains **Win+Ctrl+F**. Never collapse it to Ctrl+F. Diagnose its Windows reservation.

Treat Win chords, Ctrl+Alt+Del and Ctrl+Esc as OS-owned. Preserve Alt+F4’s normal close workflow and Alt+Space’s system menu. These are not all technically unoverrideable: Microsoft explicitly says application accelerators can override some system accelerators, and advises against doing so. [Win-key reservation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey), [system accelerators](https://learn.microsoft.com/en-us/windows/win32/menurc/about-keyboard-accelerators).

**What changes my answer:** an explicitly adopted portable “primary modifier” abstraction, consistently lowered across native hosts, browser behavior and accessibility metadata. Inferring that abstraction from literal `Meta` is too ambiguous.

For **G, ship the first public app as option 3: full MSIX through App Installer, with Exact bundles in writable per-user app data. Confidence: 85/100.** Add the Store as a distribution channel later.

The decisive correction is that Windows does **not yet have Exact delivery**: the host rejects nonzero update-store levels, and `deploy.mjs` excludes Windows. The general “about a second” delivery claim is therefore not established for this host. [Windows refusal](/Users/ccheever/projects/exact2/host/windows/src/window.rs:89), [deployment platforms](/Users/ccheever/projects/exact2/scripts/deploy.mjs:64).

Use MSIX/App Installer for the native host and packaged dependencies; retain Exact’s authenticated, compatibility-checked updates for its app bundle. Package files are read-only; downloaded bundles belong outside the installation directory. This preserves the fast bundle-update model without making Exact responsible for replacing its running Windows executable. [MSIX filesystem behavior](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes), [App Installer updates](https://learn.microsoft.com/en-us/windows/msix/app-installer/update-settings).

Other corrections and decisions:

- **“Toasts require package identity” is wrong as a blanket statement.** Unpackaged desktop toasts are supported. Receiving shares does require identity. Sparse packaging supplies that identity without full MSIX or the Store; it does not replace an installer/updater. Option 2 is attractive when those already exist. [Desktop notifications](https://learn.microsoft.com/en-us/windows/apps/design/shell/tiles-and-notifications/send-local-toast-desktop-cpp-wrl), [share targets](https://learn.microsoft.com/en-us/windows/apps/develop/windows-integration/integrate-sharesheet-receive), [sparse packaging](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/grant-identity-to-nonpackaged-apps).
- **Signing:** use a publicly trusted, timestamped package signature with the matching publisher identity; Authenticode-sign distributed executables and DLLs too. Prefer Microsoft **Artifact Signing, formerly Trusted Signing**, if eligible, or an established code-signing CA. Exact’s bundle signature serves a separate purpose. Neither ordinary signing, EV nor Trusted Signing guarantees immediate SmartScreen reputation. [Package signing](https://learn.microsoft.com/en-us/windows/msix/package/sign-app-package-using-signtool), [SmartScreen guidance](https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation).
- **WinGet:** publish a manifest pointing to each signed, versioned MSIX with its hash. It supplies discovery/install/upgrade distribution, not identity or Exact bundle delivery. [Manifest format](https://learn.microsoft.com/en-us/windows/package-manager/package/manifest).
- **Timing:** decide identity, publisher, writable-data location and ownership of binary versus bundle updates **before S1**. Build release automation alongside the host and qualify install/update/uninstall before public release; waiting until S3 conceals architectural work. This need not block S1’s control painting.

**What changes my answer:** a demonstrated MSIX incompatibility, or an existing qualified Windows installer and native updater, would favor option 2. A requirement for Store-first acquisition would add option 4; “the Store” is a channel, not a separate packaging architecture.
