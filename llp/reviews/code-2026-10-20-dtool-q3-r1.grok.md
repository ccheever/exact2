2. **NIT** — `host/web/tests/activation-noframes.test.mjs:19-25`. The other checks hold.

Activation runs once on each path the guard owns. `activate` is async, so `activated ??= activate()` (`glue.js:1492`) stores a promise even when that promise later rejects, and a second `requestAnimationFrame` or the 1 s timer returns that same promise. The body of `activate` catches module, boot, and `activateData` failures (`glue.js:1478-1482`), sets `dataset.error`, and fulfills; a throw before that `try` rejects the stored promise and the other caller does not retry. A served document calls `activateOnce()` immediately and schedules neither the frames nor the timer (`glue.js:1493`). A boot that throws in `main` never reaches the guard; `ready.catch` records the error (`glue.js:1496`). That is the same one-shot outcome as a frame callback that threw before. The restart at `glue.js:1362` is outside the guard on purpose: the first boot clears `inputReady` (`glue.js:1443`) and passes `fresh`, so it does not call `activateData`; a later plan with bytes and no module does.

The timer does not beat the first frame on a visible page whose first frame arrives within a second. Both are scheduled after `boot` returns. The timer wins when no frame is delivered for at least a second (the offscreen cross-origin canvas, a background tab, or a main thread blocked past 1 s, where a due timer task runs before the rendering steps). `frameCallbackMs` is still written only in the first frame callback (`glue.js:1493`). `loadAfterPaint` only injects a module script (`glue.js:92-100`); “after paint” was the caller’s two frames, and the plan accepts the timeout winning. `scripts/metrics.mjs:423` loads `?agent=1`, so it never arms this timer, and it reads `frameCallbackMs` only after `bootMs` and two frames (`:429-436`). `scripts/smoke-native.mjs:91` uses that attribute as a paint fallback. `js/web/tests/it/browser.rs:221` records `startup.painted` from the attribute inside `exact_data_ready`; that stays true while frames arrive within the second, which that fixture’s frame pump does.

The new test does not pass on the parent. `?noframes` replaces `requestAnimationFrame` with a function that never calls back (`activation-noframes.test.mjs:33`). Without the timeout, `moduleReady` stays unset, the plan reload waits on that same promise (`glue.js:1388`), and the 8 s poll throws. The dev wasm is built with `EXACT_WEB_LINK=all` (`dev.mjs:33`, `build.mjs:128`), so it is unsplit and `stages` stays empty (`glue.js:990-993`); the test’s export copy is never passed to a stage instantiation. The copy is a shallow spread of the primary exports plus a wrapper around `exact_data_ready` (`activation-noframes.test.mjs:30-31`). `glue.js` keeps that object as `wasm` and uses `wasm.memory` as the same `Memory`. The 8 s poll is the wait for instantiate plus the 1 s timer, not the wasm build (that finishes before the banner). The 1.5 s sleep is only long enough to see the activation timer fire again; it is not long enough to outlast the plan compiler, which is the race in finding 1.

`agentMode` is the right exclusion and it is already known. It is a module-top constant (`glue.js:163`) from `?agent`, evaluated before `main`. The agent clock is virtual, so a wall timer must not fire there; the startup fixture forces `agentMode` false and checks that the recorded 1000 ms timer returns the same promise as the second frame (`host/web/agent.test.mjs:864`, `:893`). The design-tool canvas is not `?agent` (`apps/design-tool` loads the dev page on `localhost`), so this timer is the one that unblocks it. An `?agent` page that is given no frames still never activates, which is what the plan asked for. The fixture does not itself exercise timer-first or the `agentMode` branch.
