The wait is a runner-held `PendingReq` (`reask_at: Some`, never a `RequestOut`). Settlement treats it as the outstanding ask, `pending_res` stays true through `in_flight()`, and `has_pending()` / the agent's `state.pending` leave it out via `waited()`. That split matches the approved visible state. A streak is two re-asks (250 ms, then 1 s), counted when the re-ask is dispatched; a third overrun fails with `FailureCode::Error`. An action's commit stands. Origin and invocation are kept (`note_asked` / `restamp`). Downstream overruns are absorbed on the resource being settled, not on the reply.

Hard checks that looked like the first build's bugs, and why they do not reproduce:

- **Forever-wait (`reask_at = INFINITY`).** `reask` parks there only when the re-ask commit succeeds, `refresh_next` still contains the resource, and the old ticket survives (`overrun.rs:217`). That is the not-ready settlement arm, which requires `data.ready()` to be false (`settlement.rs:530` and `:578`) and does not `force.retain`. A wait is only created by a query, which those arms skip, and on a live runner `ready()` does not go from true back to false (reload boots a new runner; `activate_for_validation` runs on a candidate). With the module ready, a forced re-ask cannot reuse, takes the query arm, and `force.retain` (`settlement.rs:684`) drops it from `refresh_next`, so the park is not taken. `reask_due_ms` ignoring non-finite times does not hide a due wait on this path.
- **Advance spin.** A fired re-ask re-arms at `now + 250/1000` after `now_ms` has moved to the due time, or the ticket is replaced, or the streak is spent and `release_failed` drops it. The due time does not stay `<= now`. Equal times fire the re-ask before timers (`advance.rs:461`, `ready` is `at <= timer`).
- **`until_request` and the new ticket.** `hold_reask` bumps `next_ticket` with no `RequestOut`, so `advance_until_request` can stop. Linux `clock_stepped`, Apple `advanceRunner`, and the web glue clock continue while `timer_due_ms() <= to` and `has_pending()` is false. The phantom ticket is not waited on.
- **Streak.** `overrun_reasking` wins over `forced`, so the re-ask commit does not reset itself. Any other forced ask starts at 0. The identical-wait return in `hold_reask` (`overrun.rs:81`) keeps time and count when the same args overrun again, so an unrelated commit does not burn a try. An args change misses that check and enqueue replaces the ticket.
- **Attribution.** `overran_reply` is set only from that reply's own parse (`commit.rs:1340`) and `mem::take`n in `hold_overrun_reply`. `fulfill_now` clears it before the next parse. `message()` never holds a stream. A downstream overrun inside `settle` takes the Wait arm for that resource and does not fail the reply; if the arm does not match, the commit rolls back as any other settlement error does.
- **Reply conversion.** It runs after `conclude`, restamps origin and invocation, drops continuation, and `hear_forgotten` excludes the wait, so the source lets the old turn go. No second `RequestOut`. Mixed, data-host, and JS `forgotten` drop the call because its token is gone.
- **Checkpoint.** `pending` and origins are cloned, so a refused action, reply, message, or recommit restores the wait; `reask` then re-arms or fails it. The reply conversion is intentionally outside that rollback.
- **Boot, kept seeds, reconcile.** An overrun at boot is published as a finite wait inside the initial `settle`, or fails boot when there is nothing to show, as any other boot data error does. Not-ready seeds are asked from `data_ready`, not from a re-ask. A keepable re-query does not match a wait (`keepable` is `None`) and replaces it.
- **Readers of `pending`.** `changed()` marking `ask_again` on a wait is subsumed by the forced re-ask query. `wake_deferred_edges` correctly keeps the edge deferred. Module deadlines do not time the wait out. `expire_wake` fails it through `reask_answered`. `prune_origins` keeps its stamps. `data_origin` skipping it is the stated rule (the wait runs nothing).
- **Hosts.** Linux (`host.rs:727`), Apple (`agent.rs:19`, `Agent.swift` `settle()`), and web (`host.rs:662`, `glue.js` `settleCandidate`) all chain `reask_due_ms()` into the settle op, and `timer_due_ms` chains it for the live clock. Two re-asks then a coded failure; the settle loops are capped at 16 rounds. The envelope keeps kind `"Overrun"`; unknown kinds still read as `Unavailable`.
