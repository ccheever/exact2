## New findings

### MATERIAL

**1. D2 and D3 — the awaited-but-queued answer is ticket 0 and `WAITING` at once**

D2’s algorithm returns today’s ticket 0 whenever the answer is not both finished and on the main thread. Today’s return is `prelude.js:770`: any `call.storage > 0` returns `{tag:1, ticket:0}` before any head check. An awaited read queued behind a background write is still `pending`, so it takes that path. D3 says that answer settles `WAITING` and takes ticket 0 only when its own operation is the head, and that background holds the only Ibex2 ticket while its operation is the head. Both cannot be implemented. Two `Session::continuation` callers would share one module-wide `is_idle`/`wait`. D4.5’s reason for deleting `DEFERRED` also assumes that queued read is ticket 0 and therefore `turn_open()` (`js/src/turns.rs:11–13`). Under D3 it is `WAITING`, and `turn_open()` is false.

Fix: ticket 0 only when this call’s operation is the queue head. Otherwise, if the promise is still pending, return the existing `{ticket:0, waiting:true}` form (`js/src/lib.rs:140–147` decodes that to `WAITING`). `background()` arms only when the head owner is `background` and no ticket is out. Delete D2 step 3’s “today’s ticket-0 return stands” for the queued case, and make D4.5’s parenthetical match D3.

**2. D4.5 — deleting `DEFERRED` drops the multi-step turn it still protects**

`js/src/lib.rs:831–838` parks a new answer while another is between storage steps so that a serialized database does not start inside the open turn. The queue orders operations that have been issued (D4.2). It does not keep an answer’s not-yet-issued second `await` ahead of a later answer. With the deferral gone, A’s `await write1` parks, B starts and issues, and A’s continuation then issues `write2`. The order is `write1`, B, `write2`. D4.5 says the queue “keeps” that order and “loses nothing.” That is false for the case the comment names. Its “why it must go” case, a read parked behind background work as ticket 0, does not exist once D3 is followed. §5 still requires the deletion: an answer asked during another’s read “begins and replies at once.”

Fix: keep `lib.rs:831–853` for a parked `ticket == 0`, an answer whose own operation is the head. Do not delete it in stage 1. Change the §5 test and §9 Q1 to “kept.”

**3. D5 — the next background round is never handed to a host, and the composers drop the token**

Hosts run work only from `take_requests()` (`runner/src/runner/commit.rs:809–810`). The only push onto `self.requests` is `enqueue` (`:783–788`), which also sets `forgot` and assigns a new ticket. Apple reads that list at `abi.rs:236` and Linux at `presenter.rs:778`. D5 forbids `enqueue`, `fulfill_inner`, `update()`, and `forgot`, and says `Some(next)` replaces the `PendingReq` in place. After the first continuation is fulfilled, `holds` stays true and nothing is dispatched again.

The token is also gone. `Storage::dispatch` removes a `Pending::Child` unless the dispatch is `Held` (`data/host/src/lib.rs:287–294`). `Storage::continuation` removes it too (`:331–332`). D5 remaps `background()` only. It does not say `background_landed`’s `Some(next)` is remapped or re-inserted, and the trait default returns `Ok(None)`, which D5 defines as “remove the entry.” `Module::continuation` finds only a parked call whose `call == token && ticket == 0` (`js/src/lib.rs:1241–1244`). A bare `BACKGROUND` token is not such a call. D6 special-cases `Module::dispatch`; the composers’ first dispatch still consumes the mapped token.

Fix: both `background()` and `background_landed`’s `Some(next)` go through `Storage`’s and `Mixed`’s remaps and re-insert the child token. Keep one runner ticket, and push a `RequestOut` on that same ticket after the fulfill so `take_requests` hands the host the next round, without `forgot` and without `update()`. Say the executor may run a ticket it has just completed.

**4. D7 — re-homing does not see an in-flight write, and the wasm realm never moves**

`storage.js:53` captures `owner` by value at issue. `completion()` pushes onto `queues` only when the backend resolves (`:31–35`, `:55–59`). Until then the queue is empty while the filesystem or SQLite work runs. `retire()` (`:110–116`) marks the owner and drops queued callbacks; `ready()` drops the callback when `retired.has(owner)` (`:32`). Moving “the queue” and refusing to retire a non-empty queue misses the in-flight operation. There is no registry to re-point.

The move that would let the turn end is gated on the main-thread flag (D2, D6). The wasm realm is `module-glue.js`, not the Hermes executor, and D7 never sets the flag. The loop stays on `tail` while `tag === 1 && ticket === 0` (`module-glue.js:199–204`), so `finish()` at `:167` is not reached when the value is ready, and the re-home never runs. Setting the flag without a mutable owner cell makes `finish()` retire the owner and drop the write. Stage 1’s prelude change is safe only while the flag defaults unset. The worker realm must stay unset (`module-worker.js:124`).

Fix: give each issued operation a mutable owner cell, registered at enqueue, and point that cell at `background` before any retire. Do not retire an owner that still has in-flight or queued operations. Set the flag in the wasm module realm in the same stage as the re-home. §5’s web test has to resolve the promise, not only see a background owner object.

**5. D5 and D6 — `Placed` does not forward, and every TypeScript app is `Placed`**

The default `TYPESCRIPT_PLACEMENT` is `Main` (`js/bake/src/lib.rs:315–318`). `Placement::Main` is the source inline (`data/src/placed.rs:5–6`): `inline()` is `owner.is_none()` (`:207–208`), and `answer_with` calls the inner module (`:232–233`). Fieldnotes is `Storage<Data<Placed<Module>>>` (`apps/fieldnotes/apple/src/lib.rs:8–14`); canvas-gallery and the other apps use the same `.placed(TYPESCRIPT_PLACEMENT)`.

D5 says “`Placed` does not forward.” The new methods default to `None` and `Ok(None)`. D6 says `Module::placed` (`js/src/lib.rs:483–485`) leaves the flag unset. On `Main`, `activate` calls `inner.activate()` (`placed.rs:481–484`), which is `Module::load`. If load sets the flag, the prelude replies early and no ticket is armed, so the write is stranded. If load does not set it, because the module was built through `placed()`, the move never happens and the stage 1 parity fixture cannot get “each answer at its input’s end.” `Placed::continuation` already forwards when `owner` is `None` (`:681–686`) and returns `None` while a worker holds the module. The blanket rule does not.

`take_logs` has the same hole. D8 says a module’s `console` reaches the journal on Apple and Linux. The trait default returns an empty `Vec`. D8 forwards `Storage` and `Mixed` only. `Mixed`’s child is `Placed`, so the journal stays empty for every TypeScript app. D11 defers worker placement, not `Main`.

Fix: on `Main`, forward `background()`, `background_landed()`, and `take_logs` the way `continuation` forwards, and set the flag on the inline module at load. Pass the flag unset through `Module::build` (`lib.rs:490–523`) so the worker instance does not set it. Keep `Placed` from forwarding while `owner.is_some()`.

**7. D2 — `background`’s `status` is unspecified, and `hostWork` ignores any other status**

`hostWork` (`prelude.js:162`) returns the promise unchanged unless `call.status === "pending"`. D3 says a digest counts in `call.storage` and moves with it. A background drain whose pseudo-call is not `pending` does not join that digest to the turn. Setting `status` to `pending` so the digest joins also lets `native.call` through, which D2 does not block.

Fix: state that `background.status` is `"pending"`, and name which `native.*` calls stay refused from that context.
