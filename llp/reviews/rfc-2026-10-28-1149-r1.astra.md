**2. Answers to LLP 1149 §5, questions 1 to 13**

1. **Write our own renderer? — Approve a bounded prototype, not the replacement commitment yet. Confidence: 88/100.**

   Instanced UI primitives and retained recordings fit Exact’s existing painter. Keeping the kernel, painter, and host behavior also avoids adopting another UI framework. However, the evidence does not isolate renderer cost: readback is imposed by [`Gpu::render_scene`](/Users/ccheever/projects/exact2/host/linux/src/gpu.rs), while build-time shader translation already works with vello in [`canvas/vello/build.rs`](/Users/ccheever/projects/exact2/canvas/vello/build.rs). Retention is also not inherently unavailable to vello: [`Scene::append`](https://docs.rs/vello/0.10.0/vello/struct.Scene.html#method.append) accepts a retained scene with a transform.

   **Evidence that would change my answer:** a representative Windows screen showing a material improvement over vello with direct presentation, build-time shader translation, and retained row encodings—not just today’s readback backend.

2. **Every platform’s own API instead of wgpu? — Allow direct backends where justified; do not prohibit wgpu everywhere. Confidence: 91/100.**

The interop and presentation requirements are also legitimate. But the quoted 23/93 ms is aggregate instance/adapter/device initialization, measured in [`Gpu::new`](/Users/ccheever/projects/exact2/host/linux/src/gpu.rs), not measured abstraction overhead. Direct Vulkan still initializes the driver and device. Charlie authorized repetition *when it improves performance*; the document assumes that result.

   Amend LLP 1009 narrowly to permit host-owned rendering APIs. Let the measurements select each implementation.

   **Evidence that would change my answer:** matched implementations of the same small renderer showing meaningful startup, CPU, memory, or interoperability benefits from each direct backend.

3. **DirectX 11 instead of DirectX 12? — Yes, as the initial Windows backend. Confidence: 90/100.**

Correct D7 first: choose flip-sequential for partial presentation, or flip-discard for whole-frame presentation. **E3. D7 combines incompatible DXGI choices.**

`DXGI_SWAP_EFFECT_FLIP_DISCARD` does not support partial presentation. Moreover, `Present1` dirty rectangles describe the region the application updates; Microsoft prohibits updating pixels outside that region. Thus “redraw the whole backbuffer, then present only dirty rectangles” is not a valid implementation of the stated DXGI contract. Use flip-sequential with correct incremental-buffer bookkeeping, or full-frame flip-discard presentation. [Swap effects](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ne-dxgi-dxgi_swap_effect), [present parameters](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/ns-dxgi1_2-dxgi_present_parameters)

**E4. “Metal and DirectX 11 boot with nothing compiled” is false as written.**

The repository’s Metal build emits AIR packaged in `.metallib`, not every device’s final GPU executable. Apple distinguishes generating Metal IR from finalizing GPU binaries and documents runtime compilation on binary-archive misses. DXBC is likewise shader bytecode; it does not eliminate driver translation to hardware instructions. [Apple’s compilation workflow](https://developer.apple.com/videos/play/wwdc2023/10124/), [Microsoft’s D3D11 driver shader input](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3d10umddi/nc-d3d10umddi-pfnd3d11_1ddi_createvertexshader), [NVIDIA’s shader-compilation explanation, pp. 6 and following](https://developer.nvidia.com/sites/default/files/akamai/gameworks/CN/Stuttering_Analysis_EN.pdf)

The defensible promise is **no application-side shader-source compilation on these platforms**, with driver compilation measured separately. The claim that Vulkan’s six pipelines take “milliseconds” is an estimate, not evidence supplied by this RFC.

**E5. D6.3 does not discharge the binding boot rule.**

The existing [DEFERRED Runtime entry](/Users/ccheever/projects/exact2/rules/DEFERRED.md:626) explicitly admits the Linux vello painter’s first-launch compilation. Reclassifying new compilation as “the driver’s” does not remove the work from the boot path. D6.3 and §8 need an explicit proposed replacement exception covering the actual behavior, rather than withdrawing the exception while preserving the prohibited cost.

The cited LLP 1009 D5 rule for optional GPU modules is correctly described: their compilation occurs after first pixel. [LLP 1009 D5](/Users/ccheever/projects/exact2/llp/1009-gpu-canvas.rfc.md:114)

**E6. The named Backend methods are real, but the claimed unchanged contract is insufficient.**

The names explicitly listed in §1 exist. There is no dedicated `caret` method; the caret is painter output through other primitives. More consequential omissions are:

- `text_blur`;
- `finish_for(FrameTarget::{Pixels,Window,Geometry})`;
- storage recycling and split-window composition;
- the distinction between recording a layer and subsequently driving its animation.

The imported-image proposal also does not fit the existing surface signatures: `canvas`, `surface_image`, and `island_image` receive CPU `Pixmap`s. D10 therefore requires a new resource path or interface change, not merely another implementation of the existing trait. [`Backend`](/Users/ccheever/projects/exact2/host/linux/src/paint/backend.rs:63), [`paint/layer.rs`](/Users/ccheever/projects/exact2/host/linux/src/paint/layer.rs)

**E7. The primitive description does not yet cover the existing painter.**

Examples that need explicit implementation decisions:

- `Shape` has **elliptical** corner radii and non-round `corner-shape`, not just four scalar radii.
- SVG brushes include gradients and repeated patterns.
- `island_image` carries blend modes beyond source-over.
- Backdrop operations include saturation; §6’s exclusion of filters beyond blur and shadow conflicts with existing behavior.

These are supported inputs, not future embellishments. Coverage masks can help implement them, but “tinted coverage” and a single rounded-rectangle shader do not specify the complete solution. [`Shape`](/Users/ccheever/projects/exact2/host/linux/src/paint.rs:114), [`SvgPaint`](/Users/ccheever/projects/exact2/host/linux/src/paint/svg.rs:21), [`gpu.rs` blend modes](/Users/ccheever/projects/exact2/host/linux/src/gpu.rs:825), [`raster/backdrop.rs`](/Users/ccheever/projects/exact2/host/linux/src/raster/backdrop.rs:84)

**E8. D4/D8 have an unresolved correctness conflict, not merely a tuning question.**

Kept instances refer to glyph/path atlas locations, while D8 evicts those locations by frame age. Without reference tracking, generations, or row invalidation, replay can sample another glyph’s pixels.

Likewise, arbitrary nested opacity/mask/clip layers can require more than two simultaneous viewport-sized intermediate targets. A hard two-viewport ceiling cannot guarantee D9’s “refuses nothing” without tiling, recomputation, or a defined fallback. These are deductions from [D2, D4, and D8](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:113), not claims that an implementation already fails.

**E9. D10 promises interoperability without specifying the producer or synchronization contract.**

The current GPU ABI explicitly says no device or texture object crosses the DLL boundary. The Apple Canvas module exists, but the RFC’s table treats corresponding GPU Canvas producers on other platforms as if already available. [`gpu/README.md`](/Users/ccheever/projects/exact2/gpu/README.md), [LLP 1056 D7](/Users/ccheever/projects/exact2/llp/1056-canvas-2d.rfc.md:330)

An image handle alone is insufficient: ownership, compatible allocation, format, adapter identity, producer completion, consumer completion, and reclamation must cross the boundary. In particular, Microsoft does not support cross-adapter shared resources across D3D API versions. [Microsoft shared heaps](https://learn.microsoft.com/en-us/windows/win32/direct3d12/shared-heaps), [Android native fences](https://registry.khronos.org/EGL/extensions/ANDROID/EGL_ANDROID_native_fence_sync.txt)

**E11. The text APIs are valid, but the text-equivalence promises are too strong.**

`CTFontDrawGlyphs` is a valid positioned-glyph drawing API. DirectWrite’s analysis object is also appropriate, but the RFC should specify the factory/version, antialiasing and grid-fit settings, and separate color-glyph handling. The old analysis documentation describes bilevel and ClearType textures; grayscale selection is explicit in the newer factory API. [Core Text](https://developer.apple.com/documentation/coretext/ctfontdrawglyphs(_:_:_:_:_:)), [DirectWrite analysis](https://learn.microsoft.com/en-us/windows/win32/api/dwrite/nn-dwrite-idwriteglyphrunanalysis), [Factory2](https://learn.microsoft.com/en-us/windows/win32/api/dwrite_2/nf-dwrite_2-idwritefactory2-createglyphrunanalysis)

Matching advances alone does not prove native appearance. Nor can the existing swash-based CPU oracle be the final authority when the explicit objective is to match a different platform rasterizer. Keep separate geometry, compositing, and platform-text comparisons.

**E12. Two factual errors underlie the web implementation plan.**

First, D1’s automatic wasm fallback contradicts the current build, as noted in question 1.

Second, §1 and D5 claim that the wasm kernel already measures through browser `measureText`. The current implementation says the browser lays out text, returns `TextMetrics::default()` from its otherwise-unused measurer, and constructs an on-demand kernel. A painted host needs a real measurement and layout integration. [`host/web/src/host.rs`](/Users/ccheever/projects/exact2/host/web/src/host.rs:266), [LLP 1071’s current-host description](/Users/ccheever/projects/exact2/llp/1071-exact2-web-target.rfc.md:114)

That omission also invalidates treating the new payload as the old wasm target with only a renderer substituted.

**E13. Browser text parity is not “satisfied by construction.”**

`OffscreenCanvas.fillText` exists. However, Canvas run drawing does not automatically reproduce DOM inline layout, all CSS font features, wrapping, or shaping across run boundaries. The proposed cache key also omits relevant state such as direction, language, spacing, and font-load generation. Arbitrary variation settings are not a standard Canvas text-style property. [WHATWG Canvas text styles and drawing](https://html.spec.whatwg.org/multipage/canvas.html#canvastextdrawingstyles)

The shared browser rasterizer is a useful starting point; it is not a proof.

**E14. D3 overpromises browser behavior from the mirror and proxy.**

- “Hidden DOM” must not mean `hidden`, `display:none`, `visibility:hidden`, or `aria-hidden`; those remove content from the accessibility tree. [WAI-ARIA tree exclusion](https://www.w3.org/TR/wai-aria-1.2/#tree_exclusion)
- An offscreen anchor’s `href` does not give a canvas pixel native middle-click or link context-menu behavior. The actual hit target and trusted event path matter. [UI Events, `auxclick`](https://www.w3.org/TR/uievents/#event-type-auxclick)
- EditContext handles text input, not an entire editor. Clipboard, undo, and other editing operations require application handling, and accessible content still needs DOM representation. [EditContext](https://www.w3.org/TR/edit-context/)
- The stated Chromium versus Firefox/Safari support split is supported by the checked evidence; it does not establish equivalent textarea-proxy behavior. [Chrome’s implementation documentation](https://developer.chrome.com/blog/introducing-editcontext-api), [WebKit’s open implementation issue](https://bugs.webkit.org/show_bug.cgi?id=269922)
- Page zoom can change the layout viewport and require reflow. DPR-driven rerasterization alone is insufficient; pinch zoom and visual-viewport movement are distinct. [CSSOM View](https://drafts.csswg.org/cssom-view/)

**E15. Stage completion and measurement claims need correction.**

S3 deleting `gpu.rs` before Android’s S4 removes a still-used parent implementation. The claim that painted tvOS needs no work beyond the existing native focus engine is also unsupported: the painted carrier still needs to expose its focusable items and geometry. [Stages S3–S4 and tvOS statement](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:333)

Finally, the agent’s controllable clock cannot measure real process startup or physical presentation latency. A one-deep CPU handoff is not proof of one-frame latency to the display; the existing Android code returns the scene after submission/presentation calls, not after observed scanout. [`gpu/present.rs`](/Users/ccheever/projects/exact2/host/linux/src/gpu/present.rs:150)

**5. Missing questions**

1. **What evidence earns the replacement and the maintenance cost?**  
   **Proposed answer:** agree on numerical acceptance thresholds before implementation, using the customer workload and an improved incumbent; require no material regressions in the other priority metrics. Stop expansion after the bounded prototype if it does not earn the change. **Confidence: 99/100.** [LLP 1149 §4](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:341)

2. **Does “one look everywhere” mean identical authored styling, identical pixels, or merely one rendering implementation?**  
   **Proposed answer:** promise common authored styling and layout semantics, with explicitly permitted platform text and accessibility differences. A presenter key does not override all unspecified platform behavior. **Confidence: 99/100.** [LLP 1115 §4](/Users/ccheever/projects/exact2/llp/1115-write-the-web-ship-the-platform.principle.md)

3. **What is the supported OS/GPU/session matrix?**  
   **Proposed answer:** name minimum OS versions, integrated GPUs, remote-session cases, desktop Linux window systems, and software-only operation. Specify the fallback for unsupported extensions rather than saying “every machine.” **Confidence: 98/100.**

4. **Who owns external images, and when may each side reuse them?**  
   **Proposed answer:** define a small ABI carrying image identity, format/color space, adapter identity, synchronization, ownership, and release semantics; qualify one real producer-consumer pair before generalizing it. **Confidence: 100/100.** [`gpu/README.md`](/Users/ccheever/projects/exact2/gpu/README.md)

5. **What happens when retained resources exceed the budgets?**  
   **Proposed answer:** correctness survives pressure: stable references or invalidation, bounded temporary allocations, tiled oversized content, and explicit fallback. Define GPU-completion-based retirement and count CPU copies as well as GPU allocations. **Confidence: 100/100.** [D4/D8](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:165)

6. **What is the color and blending contract?**  
   **Proposed answer:** specify color spaces, premultiplication, gradient interpolation, coverage gamma, image decoding/upload conversion, output formats, and treatment of already-supported wide colors. Do not let API defaults decide them independently. **Confidence: 99/100.** [`gpu.rs`](/Users/ccheever/projects/exact2/host/linux/src/gpu.rs), [`paint/svg.rs`](/Users/ccheever/projects/exact2/host/linux/src/paint/svg.rs)

7. **What exactly happens after device loss?**  
   **Proposed answer:** distinguish surface recreation from device loss; preserve logical state, invalidate device resources by generation, provide a working CPU presentation carrier, and retry with backoff rather than every frame. On Windows, account for DXGI’s restrictions on returning to GDI on an HWND after flip-model presentation. **Confidence: 99/100.** [Microsoft swap-effect remarks](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ne-dxgi-dxgi_swap_effect)

8. **Which native behaviors are required before an Apple painted presenter ships?**  
   **Proposed answer:** accessibility, editing/IME, keyboard navigation, focus, lifecycle, and essential system UI belong in its shipping gate; a benchmark carrier can precede that gate. **Confidence: 99/100.** [LLP 1149 D12 and §6](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:290)

9. **What is the painted web’s actual layout and typography architecture?**  
   **Proposed answer:** explicitly design the kernel measurement bridge, line/run construction, font availability, unsupported CSS text features, and measurement batching before promising DOM parity. **Confidence: 100/100.** [`BrowserMeasures`](/Users/ccheever/projects/exact2/host/web/src/host.rs:266)

10. **What happens when neither WebGPU nor WebGL2 can initialize?**  
    **Proposed answer:** choose and budget a usable fallback—DOM or software presentation—and preserve application state during loss/recovery. Feature detection must include adapter/device creation, not just `navigator.gpu`. **Confidence: 98/100.** [wgpu’s documented browser-detection caveat](https://docs.rs/wgpu/latest/wgpu/struct.InstanceDescriptor.html)

11. **Which trade or waiver admits the expanded host work and boot compilation?**  
    **Proposed answer:** make this explicit in Charlie’s decision: the renderer experiment, Apple carrier, web host, and revised compilation exception are separate commitments. **Confidence: 98/100.** [RULES](/Users/ccheever/projects/exact2/rules/RULES.md), [DEFERRED Runtime](/Users/ccheever/projects/exact2/rules/DEFERRED.md:626)

**6. Risks the documents understate, ranked**

| Rank | Risk | Mitigation |
|---|---|---|
| **1** | **The project becomes a host rewrite.** Apple and web need substantial editing, accessibility, focus, and platform integration beyond drawing. | Separate the renderer qualification from shipping-presenter qualification; name the first consumer and required interaction journeys. |
| **2** | **Retained-resource corruption and synchronization bugs.** Atlas eviction, asynchronous uploads, external producers, and submitted frames create overlapping lifetimes. | Specify generations, ownership, completion fences, and invalidation before optimizing recordings; exercise eviction and device loss during active scrolling. |
| **3** | **A false performance conclusion.** Removing readback, fixing presentation, changing glyph rasterization, and replacing vello simultaneously obscures causality. | Compare controlled variants with the same workload, rendering semantics, device selection, and presentation path. |
| **4** | **Layer and path workloads defeat the “few batches” premise.** Nested clips, blend modes, images with distinct bindings, masks, and backdrop filters multiply passes and bandwidth. | Count batches, intermediate pixels, rasterized path pixels, uploads, and peak allocations on real screens; define bounded overflow behavior. |
| **5** | **Driver and deployment diversity exceeds the proposed test matrix.** Lavapipe and headless browsers establish only part of correctness. | Qualify real Windows integrated GPUs, remote sessions, Android GPU families, Apple lifecycle/resize behavior, and actual browser/assistive-technology combinations. |
| **6** | **Text quality diverges during motion or configuration changes.** Atlas sampling, fractional positions, DPI, font changes, color glyphs, and platform settings can invalidate static parity. | Separate text-quality tests from broad screenshot bands; audit scrolling, transforms, monitor changes, variable fonts, and multilingual editing. |
| **7** | **Maintenance costs are materially underestimated.** Six API implementations plus interop, recovery, tooling, and host behavior are not established as roughly six thousand lines. | Estimate from the first complete Windows/Metal slices, including failure paths; retain shared implementations wherever direct code has not demonstrated a benefit. |

**7. The strongest alternative**

The strongest alternative is **the same retained UI-oriented core on wgpu where it meets the requirements, with a direct D3D11 backend for Windows compatibility**. This preserves the proposal’s useful algorithmic changes while making the rejection of a shared device layer a measured, platform-specific decision.

The absence of DX11 in wgpu is real. The claimed universal startup and efficiency penalty is not yet isolated. The repository already demonstrates build-time shader translation with wgpu, and Android already presents vello without the Linux readback loop. [wgpu backends](https://docs.rs/wgpu/latest/wgpu/enum.Backend.html), [`canvas/vello/build.rs`](/Users/ccheever/projects/exact2/canvas/vello/build.rs), [`gpu/present.rs`](/Users/ccheever/projects/exact2/host/linux/src/gpu/present.rs)

Decide with three controlled variants:

| Variant | What it isolates |
|---|---|
| **Improved vello:** direct presentation, retained row encodings, build-time translation and appropriate caches | Whether a new rendering algorithm is needed |
| **Ink core over wgpu** | Whether specialized primitives and retention provide the gain |
| **Same Ink core over direct APIs** | Whether owning each device layer provides additional worthwhile benefit |

Run the same real Windows screen and representative Apple/Android screens through cold installation, subsequent launch, sustained fling, small text updates, resize, idle, image arrival, and nested-layer workloads. Record actual presented-frame timing, input latency, CPU, GPU work, allocations/uploads, total footprint, and controlled energy measurements. Keep shader-cache state and hardware configuration explicit.

**Choose direct APIs where their incremental improvement exceeds measurement noise and the agreed maintenance threshold; choose the shared implementation elsewhere.** Retain vello if the improved incumbent already meets the customer’s targets.

Sparse strips deserve an additional path-heavy comparison, but not an assumed drop-in role: the upstream renderer currently documents unsupported mask/filter/blending cases and resource-lifecycle limitations. Its hardware-class reach also does not mean it supplies a native DX11 backend. [Linebender’s current Vello GPU documentation](https://github.com/linebender/vello/tree/main/vello_gpu)
