# Blind review: LLP 1149 and LLP 1149.000 (Draft r1)

Reviewer note: read-only review. No builds or tests were run, as instructed. Nothing under `llp/reviews/` was read.

## 1. Verdict

**LLP 1149: NOT READY.** The direction (a UI-shaped instanced renderer behind the existing `Backend` trait) is sound, but as written D7 specifies an illegal DXGI combination, D1 cannot express borders, corner shapes and backdrop saturation the trait already emits, and D10 contradicts the shipped GPU-module ABI — an implementer would have to redesign silently on the customer's critical platform.

**LLP 1149.000: READY WITH CHANGES.** Keeping the DOM as the web default is right and well argued from LLP 1115; the painted form must be unscheduled until a consumer is named, islands should precede the per-app form, and the run atlas and mirror need the scoping in §3 below.

## 2. Answers to LLP 1149 §5, questions 1–13

**Q1. Write our own renderer rather than take vello, GPUI or Skia? — Yes. Confidence 75.**
GPUI is correctly excluded as a framework that would own layout, hit testing and focus ([1115.004 D2 table](/Users/ccheever/projects/exact2/llp/1115.004-no-tells-on-windows.rfc.md:173)). Skia's loss in [LLP 1056 §8.5](/Users/ccheever/projects/exact2/llp/1056-canvas-2d.rfc.md:733) is real but narrow: an animated full-screen Canvas 2D fixture, not retained UI rows, so it excludes Skia for canvases more firmly than for UI. The proposer missed costing the cheaper fix to vello itself (build-compiled kernels everywhere, swapchain present everywhere, retained scenes) — see §7. *Would change my answer:* an S0 spike in which the instanced encode does not beat a present-from-swapchain, precompiled vello on CPU per fling second.

**Q2. Each platform's own API, not wgpu, amending LLP 1009 D1 for the host renderer only? — Yes, with a narrower amendment. Confidence 65.**
The Windows argument is decisive: wgpu has no DirectX 11 backend, and D3D11 plus Direct2D interop is what the Windows-first customer needs. The boot argument is weak as stated: `device_ms` in [gpu.rs](/Users/ccheever/projects/exact2/host/linux/src/gpu.rs:131) times `Instance` + `request_adapter` + `request_device`, most of which is driver initialisation that `ash`, Metal and `D3D11CreateDevice` will also pay. [LLP 1009 D1](/Users/ccheever/projects/exact2/llp/1009-gpu-canvas.rfc.md:24) currently reads “wgpu is the one GPU API, on every host” for *app* code; the amendment must also settle how two devices share textures (D10), or the split reintroduces the readback. Count the backends honestly: with WebGL2 there are six, not five. *Would change:* side-by-side `vkCreateDevice`/`D3D11CreateDevice` versus wgpu `request_device` timings on the NucBox, a builder and a VM showing the direct APIs save nothing.

**Q3. DirectX 11, not DirectX 12, on Windows? — Yes. Confidence 85.**
Correct for reach (feature level 11_0, WARP, Remote Desktop) and for RichEdit interop. Two omissions: Direct2D interop requires the device be created with `D3D11_CREATE_DEVICE_BGRA_SUPPORT` ([Microsoft: How to render by using a Direct2D device context](https://learn.microsoft.com/en-us/windows/win32/direct2d/devices-and-device-contexts)), which the RFC never states; and [LLP 1115.004 D4.3](/Users/ccheever/projects/exact2/llp/1115.004-no-tells-on-windows.rfc.md:236) already requires a DirectComposition swapchain (`CreateSwapChainForComposition`, premultiplied alpha) so Mica shows through — D7's plain flip swapchain conflicts with it. *Would change:* a UI need for a D3D12-only feature. None exists in the trait.

**Q4. OpenGL ES 3.0, not Vulkan, on Android? — Yes. Confidence 70.**
ES 3.0 instancing covers D1 and the driver surface is smaller. The proposer understates that this deletes a *working* pipelined Vulkan swapchain presenter ([present.rs](/Users/ccheever/projects/exact2/host/linux/src/gpu/present.rs:1)) for a new EGL window lifecycle (surface loss on background/rotation, context loss), and that `AHardwareBuffer` import into GLES goes through `eglGetNativeClientBufferANDROID`/`eglCreateImageKHR` with fence handling, not a texture binding. *Would change:* an A/B on the Nothing 4a Pro and a low-end Mali/Adreno device showing ES driver frame pacing or power worse than the current Vulkan path.

**Q5. One WGSL source translated at build, hand-written overrides where measured? — Yes, gated on an S0 translation spike. Confidence 60.**
Only the MSL leg is proven in-tree: [canvas/vello/build.rs](/Users/ccheever/projects/exact2/canvas/vello/build.rs:1) uses naga with `wgsl-in, msl-out` only, then `xcrun metal`. Naga's HLSL backend targets “Shader Model 5.0+ (DirectX 11+)” ([naga README via docs.rs](https://docs.rs/crate/naga/25.0.1/source/README.md)), so `fxc` is plausible — and necessary, since `dxc` emits DXIL that D3D11 cannot consume — but no derivative-using SDF shader has been shown through naga→HLSL→fxc, naga→GLSL ES 3.00, or naga→SPIR-V in this repo. Overrides double the parity matrix. For two or three tiny shaders, hand-written HLSL/MSL from the start may be cheaper than fighting naga's output. *Would change:* the spike — all five translations compiling clean and landing inside the oracle band on the SDF, gradient and blur shaders.

**Q6. Platform rasterizers (Core Text, DirectWrite) over swash everywhere? — Yes, decoupled from presentation stages. Confidence 80.**
The named APIs are the right ones: `CTFontDrawGlyphs` into a `CGBitmapContext` on Apple, and `IDWriteGlyphRunAnalysis::CreateAlphaTexture` ([Microsoft DirectWrite](https://learn.microsoft.com/windows/win32/api/_directwrite/)) on Windows. Ship swash first on every platform (it is already hinted grayscale in [text/catalog.rs](/Users/ccheever/projects/exact2/host/linux/src/text/catalog.rs:642)), then admit each platform rasterizer only on its advance audit, as [LLP 1115.004 D6.3](/Users/ccheever/projects/exact2/llp/1115.004-no-tells-on-windows.rfc.md:324) requires — S1/S2 currently bundle rasterizer and carrier into one gate. Unaddressed: colour glyphs (sbix/CBDT/COLR take different paths per rasterizer), synthetic bold/italic, and who owns font-smoothing settings. *Would change:* audit drift beyond band on the parity fixtures, per platform.

**Q7. Paths on the CPU into an atlas in v1, no GPU path rendering? — Yes. Confidence 80.**
Reusing tiny-skia keeps the oracle honest. The risk is budget, not correctness: dashed borders and per-row sparklines are ordinary UI, not edge cases, and a 2048² atlas evicted by frame age will thrash on path-heavy screens. Name the fallback measurement (atlas miss rate and re-raster milliseconds on Shelf, Excord, Reflow) in S0's gate. *Would change:* a named app whose frames are mostly animated paths — then evaluate sparse strips (LLP 1148 F5).

**Q8. Kept rows as instance lists, not textures? — Yes. Confidence 75.**
The texture arithmetic checks: 400×100 pt at 3× is 1200×300×4 ≈ 1.44 MB. But replay is not a pure `memcpy`: instances carry the clip in force (D1/D2.4), batches break on scissor, and a row replayed at a new scroll offset under its scroller's clip ([rows.rs](/Users/ccheever/projects/exact2/host/linux/src/paint/rows.rs:1), `group_begin`) must be re-clipped, not just offset. The 64-byte instance is asserted without a byte budget; an affine (24 B) plus rect (16 B) plus elliptical radii — `[(f32, f32); 4]` in [Shape](/Users/ccheever/projects/exact2/host/linux/src/paint.rs:114), 32 B — already exceeds it before colour, texture rect and clip. Publish the layout. *Would change:* a scroll benchmark where re-batching kept rows costs more than sampling cached row textures.

**Q9. Painted presenter opt-in on Apple; native stays default? — Yes. Confidence 90.**
This is LLP 1115 applied correctly: author > platform > CSS default, settled by “would someone who knows the platform notice?” Verify the manifest key's shape against LLP 1030 D2 conventions before S1; `host.apple.presenter` is invented in D12 without a sibling example. *Would change:* Charlie ruling that the prospect's “same everywhere” overrides the principle for all apps. That would be a principle change, not a renderer change.

**Q10. S0 on the Mac first, then S1 and S2 in parallel? — No. Run a Windows present spike inside S0. Confidence 65.**
The customer is Windows-first and every hard unknown is Windows: `D3D11CreateDevice` cost, the composition swapchain over Mica, the legal `Present1` model, Direct2D/RichEdit into a texture, naga→fxc. S0 as written validates the least risky platform (Metal, headless, read back) on exactly the path [LLP 1015 §7](/Users/ccheever/projects/exact2/llp/1015-linux-host-v1.spec.md:626) calls “wrong for the readback”. Add to S0, on the NucBox: device + composition swapchain + one instanced quad presented + a windowless RichEdit drawn into a D3D11 texture, with device-creation milliseconds. *Would change:* that spike landing clean inside S0's window — then the stated order is fine.

**Q11. Delete vello's painter backends per platform at parity; keep it in Canvas 2D? — Yes, once the parity gate is defined per method. Confidence 70.**
Delete-don't-deprecate is [RULES.md](/Users/ccheever/projects/exact2/rules/RULES.md:48), and keeping vello where arbitrary drawing arrives ([LLP 1056 §8.5](/Users/ccheever/projects/exact2/llp/1056-canvas-2d.rfc.md:733)) is right. Today's gate is one whole-app band test (`the_two_painters_agree_within_a_band`, [LLP 1015 §8](/Users/ccheever/projects/exact2/llp/1015-linux-host-v1.spec.md:683): mean 1.35/255, 0.73% of pixels >32 with pinned DejaVu, asserted at 5 and 6%). That is not “per-fixture bands” over every `Backend` method. Inventory fixtures per method — borders per side, corner shapes, masks, backdrop saturate, blend modes — before deletion is authorised. *Would change:* nothing about deletion itself; only its evidence bar.

**Q12. Electron and WinUI 3 as built-for-purpose Windows baselines? — Yes. Confidence 75.**
They are the comparators the prospect will use (LLP 1148 F10), and the WinUI 3 oracle app is already owed by [LLP 1115.004 D13](/Users/ccheever/projects/exact2/llp/1115.004-no-tells-on-windows.rfc.md:586), so the cost is shared. Pin Electron and Windows App SDK versions, one list screen, interleaved runs. Consider adding WebView2/Tauri later; Electron alone risks a strawman the prospect will discount. *Would change:* the baseline harness costing more than the stage it measures.

**Q13. Name and place: `host/ink`, `exact-ink`? — Accept. Confidence 60.**
Low stakes. One confusion to avoid: D14 puts the `Backend` implementation in `exact-linux` as `ink.rs` while `exact-ink` holds no painter types, so “the renderer” spans two crates under one name. Either name the adapter accordingly or move the trait-facing types. *Would change:* nothing material.

## 3. Answers to LLP 1149.000 §4, questions 1–7

**Q1. DOM stays default; nothing paints without the manifest key? — Yes. Confidence 95.**
Correct under LLP 1115 and consistent with [LLP 1071](/Users/ccheever/projects/exact2/llp/1071-exact2-web-target.rfc.md:225) (D2: the DOM is the tree). *Would change:* a measured class of ordinary document apps the JS target cannot run at 60 Hz. None is named.

**Q2. Per app first, islands second? — No. Islands first, when a consumer names one. Confidence 65.**
D7 itself notes Docs and Sheets paint an island inside a DOM page, keeping the surrounding chrome's selection, links and accessibility for free. The per-app form has no named consumer (§3) and the maximal tell surface. Building the harder, less useful form first because its device is a prerequisite inverts the value order; the device can be proven inside one island. *Would change:* a named whole-app canvas consumer (a design tool or map ported whole).

**Q3. Accessibility mirror and editing proxy required, not optional? — Yes. Confidence 85.**
Required is the right ruling; the scope is understated. A mirrored tree needs live regions, role/state/value synchronisation per commit, focus event ordering between canvas and mirror, and form semantics (labels, autocomplete, password managers) that neither a hidden `textarea` nor EditContext supplies by itself. Budget it as a second presenter, with screen-reader acceptance tests (VoiceOver, NVDA) in the gate. *Would change:* nothing about “required”; only about its cost line.

**Q4. Browser-rasterized shaped runs, not glyphs? — Yes, with a different cache design. Confidence 60.**
There is indeed no glyph-id rasterizer callable from a page, and `fillText` exists on `OffscreenCanvasRenderingContext2D` ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvasRenderingContext2D)). But an atlas keyed by (text, font, size, variations, subpixel phase) makes every distinct string an entry; eviction by frame age will thrash on prose. Worse, `fillText` shapes its argument (kerning, ligatures, bidi reordering within the call), so atlas run boundaries must exactly equal the layout runs the kernel measured via `measureText` (LLP 1001 §6) or ink and advances diverge — D5's “satisfied by construction” holds only under that unstated constraint. Prefer a byte-budgeted word/run cache with an uncached direct-texture fallback. *Would change:* atlas hit-rate and re-raster cost measured on a prose-heavy screen in Chrome and WebKit.

**Q5. The DOM build of the same app is the oracle? — Yes. Confidence 70.**
The right oracle, but the bands do not exist yet: the painter's bands are CPU-versus-vello on one fixture ([LLP 1015 §8](/Users/ccheever/projects/exact2/llp/1015-linux-host-v1.spec.md:683)), and text will differ legitimately across Chrome, Firefox and WebKit. Define the crop set and per-browser bands before S5, or D6 is unmeasurable. *Would change:* cross-browser text differences forcing bands so wide the oracle stops catching layout drift — then hold geometry to the DOM and pixels to looser bands explicitly.

**Q6. Build it last (S5) with no consumer named? — No. Leave it unscheduled. Confidence 75.**
[RULES.md](/Users/ccheever/projects/exact2/rules/RULES.md:57): “A spec needs an implementer and a date, or it isn't written,” and §3 contradicts Q6's own “built when an app asks” by sequencing S5 after S4. Record the decisions, name no stage, admit it to DEFERRED terms when a consumer appears. *Would change:* the named consumer.

**Q7. Should the build refuse a mostly-prose painted app? — No (agree with the proposal). Confidence 80.**
Author > platform (LLP 1115). Print the tells and D8's byte/time comparison, as LLP 1071 §7 refusals print today, and stop there. *Would change:* an accessibility or store-policy requirement with legal force, none of which applies to the open web target.

## 4. Errors

**E1. §1's `Backend` list is incomplete, and “the caret” is not a method.** Against [backend.rs](/Users/ccheever/projects/exact2/host/linux/src/paint/backend.rs:63), §1 omits `name`, `needs_geometry_paint`, `page`, `begin`, `recycle_frame`, `text_blur`, `pop_clip`, `pop_opacity`, `finish`/`finish_for` (with `FrameTarget::{Pixels, Window, Geometry}`), `rows`, `last_frame_ms`, and the whole split-window-canvas contract: `split_window_canvas`, `recycle_window_layers`, `take_window_underlay`, `window_overlay_rows`. There is no caret method; `pointer` exists. The omitted methods are load-bearing: `finish_for` is how a presenting backend answers the agent's screenshot, and the window-layer methods are how Windows composes a full-window game today.

**E2. D1 cannot draw what the trait emits.** [Shape](/Users/ccheever/projects/exact2/host/linux/src/paint.rs:114) carries elliptical radii plus optional `CornerShape` (squircle, superellipse, bevel — [kernel/src/corner.rs](/Users/ccheever/projects/exact2/kernel/src/corner.rs:1)); a rounded-rectangle SDF cannot express non-round corners. [BorderFill](/Users/ccheever/projects/exact2/host/linux/src/paint/border.rs:62) is arbitrary `PathOp` regions with side clips, a ring clip and per-side colours; D1's “two signed distances” covers only the `Ring` fast path. [BackdropOp](/Users/ccheever/projects/exact2/kernel/src/style/backdrop.rs:16) includes `Saturate(f32)`; D2.5 specifies blur only. `island_image`'s blend `mode: u8` and `image`'s `tint` have no instance kind. D9's gate (“every Backend method implemented”) is therefore unmeetable as D1 is written.

**E3. D7's Windows present is illegal and self-contradictory.** The table specifies “DXGI flip discard” while the text specifies `Present1` with dirty rectangles. Microsoft's [DXGI_SWAP_EFFECT](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ne-dxgi-dxgi_swap_effect) documentation states `DXGI_SWAP_EFFECT_FLIP_DISCARD` cannot be used with partial presentation; dirty rectangles require `FLIP_SEQUENTIAL`, whose back buffers keep their contents. Further, [Present1](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgiswapchain1-present1) requires the app to “confine its modifications to only the dirty regions that it passes” — incompatible with D7's “the whole frame is redrawn”. Pick one: full redraw with `FLIP_DISCARD` and no dirty rects, or partial redraw with `FLIP_SEQUENTIAL`. D7 also ignores [LLP 1115.004 D4.3](/Users/ccheever/projects/exact2/llp/1115.004-no-tells-on-windows.rfc.md:236) (DirectComposition, premultiplied alpha, for Mica).

**E4. The Windows numbers in §1 conflate superseded runs.** “11.3 ms p50 at 1280×720, 20.7 ms at 1920×1080” mixes [LLP 1015.001](/Users/ccheever/projects/exact2/llp/1015.001-opaque-canvas-composition.plan.md:12)'s Evidence (11.34 ms at 720p; 21.92 ms at 1080p, “not a controlled qualification”) with its Qualification fallback column (20.74 ms). The current cost after that plan's fast path is 7.22 ms / 10.83 ms p50. These are also game-canvas readback-plus-composition numbers, not UI paint — citing them as the Windows UI baseline overstates the case S2 must beat.

**E5. Two LLP 1015 citations name the wrong sections.** LLP 1148 F7 cites “fonts 3.7 ms for 43 faces… (LLP 1015 §5)”; the numbers are in the Summary and §3 ([1015:367](/Users/ccheever/projects/exact2/llp/1015-linux-host-v1.spec.md:367)); §5 is the agent API. Likewise LLP 1149's “§5 parity” and LLP 1149.000 D6's “LLP 1015 §5's instrument”: parity bands are §8. The vello cost numbers themselves check out against §6/§7 (773 ms / 9.8 ms; RADV 77/6 ms; device 23/93 ms; 155–164 ms boot; 4 ms render + 17–19 ms readback; 12.6 ms vs CPU 10.2 ms at 1080p), as do LLP 1056 §8.5's (0.7–2 ms pipeline states warm; 94/94 crops; 22 kernels; 3.98 MB; Skia 1.1–1.2 GB on iPad). One selection to note: §1's “103 to 157 ms to first GPU pixels” is the landing-tip range; the bake-off section reports vello at 117–166 ms.

**E6. D6.3 redefines the boot rule instead of satisfying it.** [RULES.md](/Users/ccheever/projects/exact2/rules/RULES.md:53) says the boot path “executes and compiles nothing”, counted as a module graph; the [DEFERRED §Runtime exception](/Users/ccheever/projects/exact2/rules/DEFERRED.md:631) is specifically “the Linux host's GPU painter… compiles its shaders on the first launch”. Metal still builds pipeline states at launch (the RFC's own 0.7–2 ms), and D3D11 drivers compile DXBC to GPU ISA at shader creation. “These are the driver's, not ours” is a new interpretation needing Charlie's ruling and a DEFERRED trade; withdrawing the exception at S3 while Vulkan, GLES and web driver compiles remain is incorrect in scope.

**E7. Linux presentation extensions are named incompletely and one is unproven.** A KMS swapchain needs `VK_KHR_display` **and** `VK_KHR_display_swapchain` (plus `VK_EXT_acquire_drm_display`, which [LLP 1015 §7](/Users/ccheever/projects/exact2/llp/1015-linux-host-v1.spec.md:646) names and D5 omits). `VK_KHR_incremental_present` exists in the [Khronos registry](https://registry.khronos.org/vulkan/specs/latest/man/html/VK_KHR_incremental_present.html), but Mesa WSI honouring present regions on display surfaces is not established by anything cited; D7 presents it as the plan. Similarly `eglSwapBuffersWithDamageKHR` requires `EGL_KHR_swap_buffers_with_damage` exposure per driver and, with D7's full redraw, the damage is the full surface anyway.

**E8. “Android's EGL keeps a program cache” overstates the guarantee.** AOSP lists `EGL_ANDROID_blob_cache` as “highly recommended”, not mandatory ([Implement OpenGL ES and EGL](https://source.android.com/docs/core/graphics/implement-opengl-es)); cross-launch persistence an app can rely on means handling `glGetProgramBinary`/`glProgramBinary` itself. D6.3 must budget first-launch link time on Android as uncached.

**E9. D10 contradicts the shipped GPU ABI.** [gpu/README.md](/Users/ccheever/projects/exact2/gpu/README.md:14) states of the Windows path: “No GPU device or texture object crosses the DLL boundary,” and a full-window canvas “can present directly from its module-owned GPU”. D10's “the DLL's texture by DXGI shared handle… the same” on every platform describes a different, unbuilt ABI. It also crosses API generations: the app module's wgpu on Windows is a D3D12 device, and sharing a D3D12 texture into a D3D11 device (shared NT handle, `OpenSharedResource1`, format and flag constraints, keyed-mutex or fence sync) is not the IOSurface row repeated. As written, D10 is false for Windows and unproven for Linux (two `VkDevice`s, `VK_KHR_external_memory_fd`, same physical device requirement unstated).

**E10. Six backends are promised; five are budgeted.** D5 and LLP 1149.000 D4 promise WebGPU **and** WebGL2 devices; D14's file list has `device/{metal,d3d11,vulkan,gles,webgpu}.rs` — no WebGL2 — and D5's cost paragraph says “five device layers”. The maintenance claim in §7 inherits the undercount.

**E11. LLP 1149.000 D4 mis-cites LLP 1009 D1 for “no wasm-bindgen”.** [LLP 1009 D2/§3](/Users/ccheever/projects/exact2/llp/1009-gpu-canvas.rfc.md:39) keeps wasm-bindgen out of the *core hosts* while the GPU module's web glue uses it (142 KiB / 70 KiB gzip “after wasm-bindgen and wasm-opt”). A bindgen-free painted-web glue is a new constraint; its real precedent is LLP 1056's `canvas2d-glue.js`, cited correctly elsewhere in the same document.

**E12. Points checked and right, briefly.** EditContext support as stated (Chromium 121+; no Firefox or Safari per [MDN](https://developer.mozilla.org/en-US/docs/Web/API/EditContext_API)). `CTFontDrawGlyphs` and `IDWriteGlyphRunAnalysis` are the correct rasterization APIs. The two-wgpu-versions claim (vello 0.10 pins wgpu 29; the GPU module is on 30) matches LLP 1015 §7. §1's Parley/fontique/swash description matches [text/catalog.rs](/Users/ccheever/projects/exact2/host/linux/src/text/catalog.rs:5) — it is LLP 1015 §2/§3's cosmic-text text that is stale, not the RFC. D4's row-texture arithmetic is correct.

## 6. Risks the documents understate, ranked

1. **Windows presentation is the critical path and is specified wrong** (E3, plus the missing BGRA flag and composition swapchain). Mitigate with the Q10 spike in S0, on the NucBox, before S1 starts.
2. **The instance model will be redesigned mid-implementation** (E2: borders, corner shapes, saturate, blends, tint). Mitigate by enumerating every `Backend` method to instances or paths in an S0 design note, with the byte layout published.
3. **Cross-device interop may force the readback back** (E9). Mitigate by prototyping D3D12→D3D11 and wgpu-Vulkan→ink-Vulkan sharing in S0; if either fails, the honest fallback is one shared device — which reopens Q2.
4. **The headline metric may not move.** Device creation is mostly driver cost and survives the rewrite (Q2); fonts (25 ms on a laptop, LLP 1015 §3) and layout bound cold start next. Mitigate by splitting the 100 ms budget per phase in §4 before S1's gate is agreed.
5. **Shader matrix fragility** (Q5): five naga outputs, a legacy `fxc`, optional overrides. Mitigate with the translation spike and a rule that an override deletes the generated file it replaces from that platform's parity set.
6. **Six backends, thin parity** (E10, Q11): one band test today. Mitigate with per-method fixtures run per platform in the async lane, budgeted as stage work, not hygiene.
7. **Text fragmentation**: four rasterizers, four colour-glyph paths, four smoothing behaviours. Mitigate per Q6 sequencing — swash everywhere first.
8. **Atlas and layer-pool spikes on real apps** (Q7, D8): budgets are declared but no app's working set is measured against them. Mitigate by instrumenting Excord/Shelf in S0 and publishing miss/raster milliseconds.

## 7. The strongest alternative

**Keep vello; remove its three measured costs directly.** (a) Compile its kernels at build on every platform, extending the proven [canvas/vello/build.rs](/Users/ccheever/projects/exact2/canvas/vello/build.rs:1) pattern (naga → MSL today; SPIR-V for Vulkan with a seeded `VkPipelineCache`, passthrough where wgpu allows). (b) Present from the swapchain everywhere, generalising [present.rs](/Users/ccheever/projects/exact2/host/linux/src/gpu/present.rs:147)'s one-frame-in-flight present thread to KMS, Windows and a macOS carrier, deleting the readback LLP 1015 §7 already flags as the wrong path. (c) Implement `rows()` in `gpu.rs` as retained scene fragments replayed under a transform, which the trait already permits. This keeps one renderer, one wgpu device shared with app canvases (no D10 problem), and the 94/94 Chrome parity LLP 1056 §8.5 measured. Its honest costs remain F5's: a compute-class floor (no feature-level 11_0 story — though vello's sparse-strips `vello_gpu` line targets exactly that class and should be re-evaluated at S0), a larger boot graph, and glyph outlines instead of platform rasterization.

**The deciding measurement:** LLP 1149 §4's own harness, run on the NucBox and the operator Mac, comparing vello-fixed (a–c) against ink at S0 on the *same* present path — cold start p50 interleaved, CPU ms/s and late frames during the heavy-list fling, footprint at rest. If vello-fixed lands within 10% on CPU and inside the 100 ms cold budget with a warm cache, the five-backend rewrite is not bought by performance and Q1/Q2 should be re-decided on the Windows floor alone. If ink wins on CPU by a wide margin *and* the Q10 Windows spike lands, the proposal earns its cost.
