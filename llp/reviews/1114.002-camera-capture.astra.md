**1. Verdict: RIGHT DIRECTION**

**2. Overall assessment**

The RFC chooses the right abstraction for “take a photo and attach it”: extend the existing file picker with HTML’s `capture` attribute. That matches both [HTML Media Capture’s deliberately limited scope](https://www.w3.org/TR/html-media-capture/#introduction) and Apple’s [system camera controller](https://developer.apple.com/documentation/uikit/uiimagepickercontroller). The proposal meets the clone’s need without requiring apps to build a viewfinder or introducing another command/result mechanism.

**3. Concerns**

None at the requested directional or major architectural threshold. I found no issue that warrants changing the proposed layer, API shape, or scope before implementation.

**4. What it gets right**

- **Reuses the established data path.** Returning `Picked` through `change`, backed by `app:/tmp/picked/`, fits the existing [runner picker interface](/Users/ccheever/projects/exact2-review-1114/runner/src/runner/picker.rs) and [Apple delivery code](/Users/ccheever/projects/exact2-review-1114/host/apple/Sources/ExactKit/Picker.swift). Capture becomes another way to obtain an attachment.
- **Keeps permission declarations unified.** Requiring the existing `device.camera` grant, deriving the usage description, and checking the running grant set follows [LLP 1069.008](/Users/ccheever/projects/exact2-review-1114/llp/1069.008-permissions-from-grants.rfc.md). Its existing binary-release classification also handles adding the permission.
- **Preserves agent control.** Extending the existing `pick` hold supplies deterministic attachments and cancellation without another driver operation. The RFC clearly distinguishes substitution from exercising the actual camera.
- **Draws a useful scope boundary.** System photo capture and an app-controlled live preview serve different needs. Keeping video recording, library saving, and cropping outside this change is appropriate. Camera access happens when the picker is invoked; no new startup mechanism is proposed.
- **Makes the earlier ruling explicit.** It asks Charlie to revise the picker prohibition rather than treating the broader camera-module admission as implicit authorization.

**5. Questions for Charlie**

No additional architectural ruling is needed. I support Q1’s narrow admission of photo capture, including an explicit trade waiver, and Q2’s recommendation to leave video capture deferred. Keeping HTML’s reasonless `cancel` event is also the right API direction; permission-specific messaging can use the separately designed permission mechanism.
