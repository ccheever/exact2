## Strengths

- **D3 is the best piece (§2 D3).** No new vocabulary: `button popovertarget=…` around `text role="heading"` composes two rules Exact already has — pressable-around-heading is the title ([kernel/src/bars.rs:270](/Users/ccheever/projects/exact2-wt-review-1141x/kernel/src/bars.rs:270)) and a menu button's popover is its pull-down. It fixes a real misfire I verified: today that button becomes a bar item, the heading inside is never counted, and the compiler reports `lower-header-no-bar` ([contract/lower/src/warnings.rs:479](/Users/ccheever/projects/exact2-wt-review-1141x/contract/lower/src/warnings.rs:479)). Hackers' original is exactly SwiftUI's `ToolbarTitleMenu`; this lands it with words an HTML author already knows.
- **D1's placement rule (§2 D1).** A bare `image` in the header taking its side of the heading, as a `role="status"` readout does, needs no placement attribute and matches how `headerLeft` is written in the original. Rejecting `<picture>` is correct: Contract already refuses it in favour of `image` ([contract/lower/src/tags.rs:1052](/Users/ccheever/projects/exact2-wt-review-1141x/contract/lower/src/tags.rs:1052)), and `media="(prefers-color-scheme: dark)"` follows the page preference, not the element's `color-scheme` — the RFC's stated reason is the decisive one.
- **The glass table (§2 D1) matches the code.** Mark = `customView` + `hidesSharedBackground`, button picture = `UIBarButtonItem(image:)` in the shared capsule. The existing badge rule does exactly the former ([host/apple/Sources/ExactKit/IOS/NavigationBarIOS.swift:1245](/Users/ccheever/projects/exact2-wt-review-1141x/host/apple/Sources/ExactKit/IOS/NavigationBarIOS.swift:1245)), and drawing the scheme-variant fresh rather than trusting a `UIImageAsset` is backed by the recorded iOS 27 sizing bug ([host/apple/Sources/ExactKit/IOS/BarFaceIOS.swift:38](/Users/ccheever/projects/exact2-wt-review-1141x/host/apple/Sources/ExactKit/IOS/BarFaceIOS.swift:38)).
- **D4 (§2) and staging (§6)** warn before they change behaviour, and D3 → D1 → D2 orders smallest-blast-radius first. §1's correction of 1141.001 D9's premise (a `titleView` shows above an expanded large title on iOS 27) is the kind of platform fact this RFC exists to settle.

## Concerns

**BLOCKING — §1/§6: the UIKit probe is not kept, and nothing re-runs it.** The 90-line probe "built in a scratch directory and not kept" carries three load-bearing claims (title view over large title, large-title menu reachability, glass). Open questions 1 and 6 are explicitly probe-shaped, yet no stage gates on them. Resolve: commit the probe as stage 0's artifact, run it on iOS 26 and 27, simulator and one device, and make Q1/Q6 answers a precondition of stages 1–2, not findings during them.

**MAJOR — §2 D3: `showsMenuAsPrimaryAction` does not exist on the drawn title's class.** `HeaderTitleView` is a `UIControl` ([host/apple/Sources/ExactKit/IOS/NavigationTitleIOS.swift:227](/Users/ccheever/projects/exact2-wt-review-1141x/host/apple/Sources/ExactKit/IOS/NavigationTitleIOS.swift:227)); `showsMenuAsPrimaryAction` is `UIButton`-only. As written the drawn-title path (avatar/subtitle titles — the common case) cannot show the menu as primary action. Resolve: give the drawn title a `UIContextMenuInteraction` whose menu is the pull-down, with tap-vs-long-press semantics stated, or make the view a `UIButton`.

**MAJOR — §2 D2: "top-layer root" is asserted, not bounded.** Laying the principal out as its own root at max-content is new kernel machinery for a non-popover node. Unstated: maximum width source on iPad/landscape/AX5, truncation priority between the principal's two text lines, focus order on tvOS (a pressable title view in a focus-driven bar), and what happens when the principal's subtree contains a popover or search field. Resolve: a one-route spike in stage 3's lane brief with those four cases as exit criteria, before the general mechanism is promised in §5 docs.

**MAJOR — §2 D1: a raster in `UIBarButtonItem(image:)` needs its rendering mode named.** A multicolour mark or photo passed as a bar item image will be template-tinted unless set `.alwaysOriginal`; the table in §2 D1 is silent, and the symbol path beside it is template by design. Resolve: state original rendering for raster/SVG sources, template only for `symbol:` and `tint-color` marks — and add it to the `BarFaceIOSTests` list in §4.

**MAJOR — §2 D3/§3: the menu-wrapped heading changes existing apps' shape.** Any header that today falls back to a painted in-page header (because its menu button hid the heading) becomes a native bar when stage 1 lands. That is the intent, but it is a visual break for apps that accepted the painted fallback; §6 calls no migration note and D4's warning text does not preview it. Resolve: extend D4's `lower-header-no-bar` repair text for this specific shape ("wrap the heading in its menu button and it becomes the title menu") so authors meet the change at build time first.

**MINOR — §2 D2: `principal` is SwiftUI's word, not the web's.** LLP 1115 keeps names CSS where CSS has one; CSS has none for the centre of a bar, and `toolbarPlacement` is already Exact's coinage, so extending it is internally consistent. But a web author will not guess `principal`. Resolve: keep the value, and have `contract vocab toolbarPlacement` (§5) teach it by contrast with the heading, not by reference to SwiftUI.

**MINOR — §2 D1: `light-dark()` for images is a resolution, not yet CSS.** The March 2026 CSSWG resolution and Firefox 150 make it defensible and forward-compatible, but today `image "light-dark(url(…), url(…))"` is Exact parsing CSS's future inside a string. Resolve: docs (§5) must call it an Exact-ahead-of-CSS form, and the compiler should accept exactly the two-`url()`/`none` grammar — which §2 already specifies — with no claim that browsers accept the same string.

**MINOR — §3: Android's principal "in the Material bar's title slot" and tvOS's pressable title view** are both stated as destinations with no width/focus story; acceptable at stage 4, but §3 should say what happens before stage 4 on Android as plainly as it does for the Mac ("in the page under the bar" is there — good; tvOS's focus behaviour is not mentioned at all).

## Open questions

1. **Large-title tap opens the menu?** Keep the `aria-level=2` advice; assume no until the kept probe (above) taps it on device. Confidence: 85.
2. **Top-layer root?** Yes — the alternative (laying out the whole header for the bar, retiring `ChipFace`'s style-reading) is a bigger, riskier change bundled into a feature RFC. Take the root, with the spike bounds above. Confidence: 70.
3. **Web heading inside a title-menu button?** Keep the composed author form as the only form; have the web host emit the heading around the button (the APG shape) so screen readers get a heading. Accepting a second authored form buys two kernel/compiler paths for one presentation. Confidence: 75.
4. **Web fallback for `light-dark()` images?** Resolve in the host by the element's used colour scheme (swap the source), not `<picture>` on `prefers-color-scheme` — the latter is wrong exactly under an authored `color-scheme`, the case D1 §2 already cares about. `<picture>` only as a no-JS static fallback. Confidence: 80.
5. **macOS title menu?** Not `representedURL` — that is a document-path menu with file semantics a feed picker does not have. Probe `toolbarTitleMenu`; if AppKit offers no equivalent, a centred toolbar title button opening an `NSMenu` is the hand-built shape. Confidence: 85 that `representedURL` is wrong.
6. **Round photo without glass?** Yes — a hand-built avatar button is a circular custom view, not a glass capsule member; extend the badge rule. Confirm with the stage-0 avatar probe. Confidence: 75.

## Missing

§4's test list is good but has no iOS 26 column (the probe was 27-only, while `hidesSharedBackground` and the subtitle path are 26-gated), no VoiceOver pass over the principal and title menu (traits: the title control is `.header` or `.button` today — which is it with a menu?), no AX5/largest-text drive of the principal's clamped line, and no async case: a remote or SVG mark that arrives after the bar is laid out must not resize the item.
