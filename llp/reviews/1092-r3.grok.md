## New findings

### MATERIAL — D3. A stall cleared by any standing commit is retried by the frame loop, and that retry skips frame tasks.

**Problem.** A non-ask refusal leaves the head queued and the mutation stalled, so nothing spins on `timer_due_ms` alone. The stall ends when any commit stands. `frame()` runs `advance_timed` and, if that returns an error, returns before firing frame tasks (`commit.rs:158–161`). With an armed frame task (`wants_frames`, D10) the display stays on `animation_frame` and does not take the `advance` branch (`display.rs:532–538`). The frames alternate: one frame’s task stands and arms the `next`; the next frame’s prelude runs that `next`, it fails the same way, and the frame task does not run. A permanently failing ask (the answer still breaks settlement after rollback) is retried every other frame for as long as the frame task stays armed, and that task is skipped on the retry frames. The same prelude abort cuts a seek short: the first timer that stands re-arms the `next`, the `next` fails, and `advance` returns before later timers, so one `advance(60_000)` and sixty `advance(1_000)`s stop at different fires while a stall is up.

**Evidence.** D3, the stall paragraph (the scan arms again when a commit stands; `timer_due_ms` is the cited anti-loop). `commit.rs:156–161` (`frame` returns on `a.error`). `commit.rs:211–350` (a refusal returns out of `advance_within`). `display.rs:532–538` (`wants_frames` selects `animation_frame`, not `advance`). D7’s `every(frame, step)` and D10’s seek equality are the two schedules this hits. §5 asks for that equality with no stall in the case.

**Fix.** Keep the head and do not arm a stalled mutation from a commit that did not change the slots, resources, or derives the refusal saw. In `frame()`, still fire armed frame tasks when the prelude stopped on a `next` refusal, and journal the refusal. Run that `next` only on a later wake, after those frame tasks, and only if that state changed.

### MATERIAL — D8, D9. A gate refusal at the start of `Runner::update` does not roll the commit back.

**Problem.** D8 puts the gate step first in `Runner::update`, after settlement, and both `TaskKey` and an eval trap refuse the commit. The checkpoint restores timers only if it was taken before the step, which is what D8 says. It does not restore row slots, the host request list, or `into_view`. Those are already applied by the time `update` runs, and today the only refusal that undoes row slots is a settlement error. A clean `Err` from the start of `update` leaves the row write in place, leaves `row_writes` queued for the next tree update, and leaves a `Later` request in `self.requests` after `pending` has been restored. The JS commit has the same split: the undo `try` ends at `settle`, and a throw from the tree update poisons (`rt.js:179`) instead of refusing.

**Evidence.** `commit.rs:546–602` applies row writes and undoes them only when `router_change` or `settle` fails. `commit.rs:610–645` enqueues and pushes `into_view`, then calls `update`. `commit.rs:18–30` and `:65–82`: the checkpoint has no row slots, no `requests`, and no `into_view`. `commit.rs:770` pushes `RequestOut` from `enqueue`. `lists.rs:44–48` and `:72`: `update` takes `into_view`, and `update_tree` takes `row_writes`; a return before either leaves both for the next commit. `lists.rs:94–98`: a failure inside `update_tree` poisons rather than restoring. `rt.js:157–170` undoes inside the `try`; `rt.js:176–179` poisons on `flush`.

**Fix.** Run the gate step after settlement and before those effects: in `run_action_inner`, on the settlement-error path, while `row_undo` is still in scope and before `enqueue` and `into_view`. On `TaskKey` or a trap, take that path (`discard_later`, undo row slots, then `conclude`). In `rt.js`, run `gated()` inside the undo `try` after `settle()`, and push `clock.timers` onto that undo. Do not return a clean refusal from the start of `update` or from `tail`.

### MATERIAL — D12. Lean’s drain commit is not a runner `next` commit.

**Problem.** D12 drains `Config.queued` at the start of `advance` and after every commit, but the gate table is applied only by `runAction` when it stands. A drain commit that asks a queued send, writes the slot, and does not apply D8 leaves later timers in that advance on the old deadlines. The runner’s `next` commit goes through `update`, so the gate step runs before those timers. D12 also has no stall. After a settlement or `TaskKey` refusal the runner keeps the head and will not ask again until a standing commit changes state; Lean’s next `advance` drains at the start and asks immediately, or, if the drain keeps going, asks before the timers the runner never reached. `random --count 500` emits both queue mutations and gated tasks, and difftest keeps going after a refusal and compares the later events.

**Evidence.** D12 (drain at the start and after each commit; D8 only on `runAction` that stands). D3 (non-ask refusal stalls; the advance stops). D8 (the gate step is on every commit, via `update`). `Runtime.lean:463` (`refuse` returns the input config) and `:604–631` (fires timers with nothing between them). `semantics/difftest/src/observe.rs:213–223` (a refusal records the outcome and `state`, then later events run).

**Fix.** Make each Lean drain commit a D3 `next` commit: on success apply D8 after its update; on the ask’s own refusal drop the head and stop the advance; on any other refusal keep the head, record a stall, and do not drain it at the start of a later `advance` until a standing commit changes the state that refusal saw.
