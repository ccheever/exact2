**Blocking**

1. `host/linux/src/presenter/images.rs:73` — A `load` is queued as a bare view id when the bitmap is accepted (`image.rs` around the `load_sent` pushes) and is only delivered later, from `apply_reports`. On the Linux and Canvas loops that delivery is after `pump`'s image sync, so input, timers, and frame tasks in the same turn can change the source first. `load_sent` is cleared on that change (`image.rs:406`), but the queued id is still dispatched. Wire ids are not recycled, so a removed node is skipped. The same image node is not: reconciliation keeps the id, `dispatch_at` runs due timers before the handler, and `load=loaded(src)` then sees the live source. `viewerLoaded` treats that as the picture that just loaded, so the thumbnail is removed while the new full image is not ready. A second accept before the flush can also deliver two `load`s for one source. Stamp a generation in the queued event, bump it wherever `load_sent` is cleared (and when the view is removed), and skip the handler unless that view is still the image that landed — after the clock advance inside `dispatch_at`, not only before it. Apple already does this with `loadGeneration` at announce time.

2. `host/linux/src/android.rs:575` — The GPU Android loop delivers `load` only from `poll_images`, and only when this iteration was woken by the image fd. `pump` always runs first and its image sync calls `drain_wake`, which empties that fd. If this wake was the executor, input, or a timeout while the image fd was also readable, the picture is accepted and the `load` is queued, then `poll_images` is skipped and the fd will not go readable again. `advance_after` (`android.rs:615`) has the same hole: it can accept a picture after the only flush in the turn. One image left on screen then keeps its thumbnail for good. Flush pending `load`s every iteration after `pump` and again after `advance_after`, even when `images_woke` is false. That flush is the generation check from finding 1, not another full image poll.

3. `host/linux/src/image/remote.rs:446` — `Retry-After` is an untrusted header, and the deadline is built with `Instant::now() + duration`. `Instant`'s `Add` panics when the sum does not fit (a 19-digit delta-seconds does it). That panic kills one of the six `exact-image-net` threads inside `fetch`, before `settle`, so that picture never fails and never retries; six such responses stop remote images for the process. `imf_fixdate` (`remote.rs:546`) can overflow `days * 86400` as well: debug builds panic, release builds wrap, and a wrapped positive value becomes a short delay. A far-future date then schedules a retry inside the 5-minute horizon, which is sooner than the server asked. Build the deadline with `checked_add` and checked date arithmetic. If the value does not fit or is past 5 minutes, keep a non-expiring deadline on the source (the latest `Instant` you can name, not "unreadable → 5 minutes") so this showing arms nothing and a later showing still will not ask early.
