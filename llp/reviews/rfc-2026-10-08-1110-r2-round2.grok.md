## Should-fix

**A watched topic asks an iterator again immediately, including while a round is in flight.** LLP 1016.002 D4 says a resource with a request in flight is marked and re-asked once after that reply lands, because dropping the reply starves the resource when the topic changes faster than the source answers. D2 says an iterator round is superseded the same way (`llp/1110-live-snapback-reads.rfc.md` lines 182–185).

`changed` only treats a pending request as in flight when `stream` is absent, and otherwise asks now:

```191:207:runner/src/runner/time.rs

                p.target == crate::Target::Resource(i)
                    && p.stream.is_none()
                    && !p.refused
                    && p.refusal.is_none()
            });
            match flight {
                Some(p) if p.ask_again => {}
                Some(p) => {
                    p.ask_again = true;
                    // ...
                }
                None => which.push(i),
            }
        }
        self.recommit(which, "changed")
```

Every iterator round has `stream: Some` from the first enqueue (`commit.rs` `enqueue_round`, lines 1012–1025). `changed` therefore always takes the `None` arm and `recommit`s. That forgets the round. Before the first message, and on a storage step or continuation after it, `PendingReq::in_flight` is true (`runner.rs` lines 307–314), so the new round holds `clock settle`. A topic that chatters faster than the first fetch never lets that settle return. `Snapback.changes()` does not call `native.watch`, so the first consumer does not hit this. Any iterator that does is uncovered: `iterator_tests.rs` has no topic case.

The message arm would honor the flag (`commit.rs` lines 1439–1474: `force_refresh`, then the next round, then `settle`). The no-message arm, which is the quiet re-poll, does not copy it:

The ordinary later-round arm does copy it (lines 1422–1425). A quiet round would drop the flag even after `changed` started setting it, and an iterator that only re-polls would never reach `force_refresh`.

The JS target has the same ask-now rule (`host/web-js/ts-data.js` lines 124–133: any `t.stream` calls `R(r)`). `rt.js` already re-asks on land when `t.again` is set (lines 158–159 and 475), including a stream message.

Fix: in `changed`, if the pending iterator round `in_flight()` (no messages yet, or `iterating && local`), set `ask_again` and leave it. Ask now only when the round is open (`stream` is set and `in_flight()` is false): that long poll has no device reply to wait for. On the no-message arm, carry `ask_again` the way lines 1422–1425 do, and if it is set, `force_refresh` and `settle` in that commit so a quiet stream cannot hold the flag forever. On the JS target, set `t.again` while `messages` is still 0 or a storage step of that resource is queued; ask now only after the first message when nothing local is in flight. D2 should state that split. Add a runner test for a topic during the first fetch, during a storage round, and during a no-message round.

## Nits

**D3 names every native agent operation as the settle loop.** A drive's determinism claim matches the code. `handle` pumps once before the operation (`host/linux/src/agent.rs` lines 62–68). `drain` returns one completion (`host/apple/src/executor_core.rs` lines 321–323). `clock settle` then loops in `wait_for_replies` (lines 1031–1043) only while `pending()`, which is `has_pending()` (`presenter.rs` lines 1354–1356), which is `in_flight()` (`commit.rs` lines 1185–1190). An open poll is not in flight, so settle does not wait it out. The next `clock settle` delivers one completion that arrived in between, then waits for the local work and the reader asks that message starts. A second completion already queued waits for the operation after that. Say that the opening delivery is every operation and the continued pump is `clock settle`.

**Worker refusal happens when a round leaves the turn envelope.** `encode` turns a `Later` with `iterator` or `yielded` into the D6 error (`data/src/envelope.rs` lines 43–48). `Placed::turn` runs a `continuation` on the owner and returns every other answer (`data/src/placed.rs` lines 378–390). A fetch leaves the turn and is refused. `Snapback.changes()` only fetches, so it is refused. App bakes put `Storage` outside `Placed`, so a storage request is refused at `encode` before the storage rewrite. The overclaim is an iterator that finishes inside the owner turn: `turn` swallows continuations, drops a `yielded` riding on them, and a final `Now` commits as a one-shot. That needs `Storage` inside the worker (`data/host/src/lib.rs` lines 126–131 copies `yielded` onto the continuation). Refuse in `__exact_call` when placement is worker, or the module is in an ordered set, before `pump`.

**Heartbeats are HTTP/1.1 only.** `serve_changes.rs` line 23 sets `heartbeat` only when `heartbeat=1` and the request version is at least HTTP/1.1. Snapback's `tiny_http` server is HTTP/1.1, so the 2 s cancellation in D5 holds for this server. Say the version gate, so a later HTTP/2 front does not look like a client bug.

**The bake scan lowers the whole bundle on a comment match.** `js/bake/src/typescript.mjs` lines 148–149. The scan comment already says a match in a comment only lowers. D1 should say the same.

**An ephemeral incarnation reset still ends the held poll.** With `ephTables=`, row moves do not (`serve_changes.rs` lines 28 and 64–69; an empty interest set produces no table names). `reset` still sets `eph_ready`, so the poll ends within 100 ms. The client then asks again without yielding when the durable cursor is unchanged (`snapback4/ts/snapback.ts` lines 530–536). One sentence in D8.

## Folds

Native lowering, `Request.iterator` from the first round, the message-plus-next-round commit (enqueue, then `settle`; a refused commit rolls back, drops the handed round, and `release_failed` because `iterating`), `Storage` carrying both fields, the cursor (`generation` is a `u64`, so `JSON.stringify` does not quote it), settle split by `local`, `heartbeat=1`, `ephTables=` for row moves, and the offline yield as the final value rather than `failure(live)` all match the code. Each awaited round gets a new ticket (`enqueue_round`); grants stay the per-request check those fetches already take. The native executor is one ordered worker and two independent workers on Apple, Linux, and Windows (`WORKERS = 3`, `usize::from(index != 0)`, Linux includes `executor_core.rs`, Windows goes through the Linux presenter). A long poll with `exactIndependentHttp` occupies one of those two; SSE uses the stream thread. `return()` on the hand-written iterator aborts its own `AbortController` while `next()` is pending. Recorded decisions do not forbid it.
