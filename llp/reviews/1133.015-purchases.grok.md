1. **MATERIAL.** §9 (the `prefer extension purchases.listPurchases` row) and D5. A purchase that arrives while the app is closed is specified as `prefer extension purchases.listPurchases`, “the store’s own truth, a partial overlay per token,” citing LLP 1133.009 D10 item 11. That mechanism does not merge a list by token. `partial` (`runner/src/runner/modules/agent.rs`) type-checks a non-record against the whole answer, and `from_json` (`js/value/src/lib.rs`) rejects a missing field and any field the shape does not have. `{"purchaseToken": t, "revoked": true}` is refused, so drive 5’s refund never reaches the substitute. A full `PurchaseDetails[]` is accepted, and `overlay` (`runner/src/runner/modules/admit.rs`) then replaces the implementation’s answer whenever the value is not a JSON object. `tell_preferred` (`runner/src/runner/modules/bound.rs`) also pushes that same value to the implementation. After `acknowledge`, the synthetic store can record the finish, and the next answer is painted back to the preferred, still-unacknowledged list. Drive 3 loops or stays unacknowledged. **Decision:** a closed-app change is a write into the synthetic store (insert, update `expirationTime`, drop on `revoked`), keyed by token, pushed on bind and on change. `overlaid()` does not apply to `listPurchases`. The store alone answers afterward.

2. **MATERIAL.** D8 (the `purchase()` sample and the sentence that points the away-path at the Summary loop) and D5. The one delivery path is the `listPurchases` loop. The only loop written there credits and `acknowledge`s / `consume`s and never calls the server. The only server sample posts from `purchase()`’s return value and then acknowledges, including when `purchaseState` is `pending`. Anything that never completes that call — Ask to Buy approved later, a slow Play payment with the app closed, an offer code, a renewal, a purchase on another device — is finished by the Summary loop with the server uninformed. The next pass skips it because `acknowledged` is true (a consumable is already gone). On Apple the device is the only place that can `finish()`, so the transaction will not come back. **Decision:** the server post lives in the `listPurchases` delivery loop, after `purchaseState == "purchased"` and before `acknowledge` / `consume`, and a failed post leaves the row unfinished. `purchase()` is the thank-you only. A `pending` result is not posted and not acknowledged.

3. **MATERIAL.** D3, D5, and D8. The module lists only entitlements and unfinished deliverable rows, and it finishes nothing itself; the app acknowledges. A transaction that is unfinished and revoked (bought, app killed before `acknowledge`, refunded before the next launch) is a verified transaction StoreKit still hands back, with `revocationDate` set, and it is not in `currentEntitlements`. The filter drops it, so the app never sees it and the module never `finish()`es it. `Transaction.unfinished` returns it on every launch. The one-minute journal only mentions rows still in `listPurchases`, so this one is silent. Apple’s own sample finishes a verified revoked transaction and grants nothing. **Decision:** the module `finish()`es a verified transaction whose `revocationDate` is set, grants nothing, and still drops it from the fact. Unverified transactions stay unfinished, as D8 says.

4. **MATERIAL.** D3, D7, and D10 (`apple.type` includes `nonRenewable`). `Transaction.expirationDate` is nil for a non-renewing subscription, so `expirationTime` is `none` and D7 arms no stale time. `currentEntitlements` keeps emitting the latest non-renewing transaction; the app is who decides the period is over. The re-ask reads `currentEntitlements` and will keep the row. A one-month pass sold through tier 1 stays owned for the life of the Apple ID. Weatherlight happens to use auto-renewable products; the tier-1 contract still includes this type. **Decision:** for a non-renewing product, `expirationTime` is `purchaseTime` plus the product’s period, and a re-ask omits the row once that time has passed even if `currentEntitlements` still emits it.

5. **MATERIAL.** D1, D7, and §9. `purchaseTime` and `expirationTime` are Unix epoch milliseconds. `stale` is a session-clock time, compared with `Runner::now_ms`. That clock is elapsed milliseconds since launch and starts at 0 under the agent (`llp/1027.000.000-wall-clock.rfc.md`; `exactTime().epochAtZero + now()` is the Unix time, and it is already built in `runner/src/time.rs`). D7 then says `listPurchases` “names the earliest `expirationTime`” as the stale time. In production that number is about `1.7e12` and the session clock is a few thousand, so the re-ask is decades out and a foreground auto-renewable never drops — the case D7 is for. §9 stores the agent clock in `purchaseTime` and “a period later” in `expirationTime`, so drive 4’s `clock +` works and any date formatted from `expirationTime` falls in 1970. **Decision:** `PurchaseDetails` times are Unix epoch on every target, including the substitute (`epochAtZero` plus the agent clock). `stale` is `now_ms + (expirationTime - epochNow)` at the moment of the answer. Each answer arms the next stale time; “once” is one ask per armed time.

6. **MATERIAL.** D7’s Android paragraph, §9’s `clock +` row, and §10 drive 4. D7 says Play’s client has no expiration, `expirationTime` is `none`, and the fact is re-answered on resume and on `PurchasesUpdatedListener`. §9 still sets `expirationTime` for every purchase, and the runner’s stale ask is not targeted. Drive 4 (`clock +` past `expirationTime`, seven-day forecast, no relaunch) is required on the Android emulator under the agent (§10, drives 1–11). That drive passes only if the Android substitute invents an expiry Play Billing will not report. A production session that stays in front keeps Plus until the next resume, and no acceptance drive catches a missing `onResume` query. Stage 2’s phone suite has no local Play store. **Decision:** on an Android target the synthetic store leaves `expirationTime` unset and drops a subscription only on resume, relaunch, or a preferred revocation. Drive 4 is an Apple drive. The foreground gap on Play is an accepted limit of the client.

7. **MATERIAL.** D6. `"start": "load"` is defined as after first pixel, and on Android as “when the activity binds the roster.” `Extensions.bind` runs from `ExactActivity.onCreate` before `setContentView` and before `read()` boots the host and paints (`host/android/canvas/.../ExactActivity.kt`). The boot rule is why the RFC refuses a StoreKit listener in `didFinishLaunching`. As written, the Android listener starts in that same pre-pixel window: `BillingClient` construction and `startConnection` inside `onCreate`. `bind` today only registers names; instances are made on the first call (`Extensions.kt`). Apple’s real post-pixel hook is `prepareAppModule` (“After first pixel, before data activates”). Android has no equivalent. **Decision:** name a post-pixel Android start, in the same slot as data activation, and keep `onCreate`’s `bind` as registration only. The process still owns one `BillingClient`.

8. **MATERIAL.** D3 (“the fact is the process’s”) and D6 (“the first instance in a process starts one task”; every other session reads from that place). The sample host runs two sessions in one process, and a session’s `destroy` runs when that session ends (LLP 1133.009: the process keeps the one capture and hands each session a lease). A `Task` owned by the first session’s implementation is cancelled in that `destroy`. A process-static “already started” flag then stops the surviving session from starting another listener, so its `listPurchases` never hears a renewal, a refund, or an Ask to Buy approval. `changed` on the first session’s package context does not announce the other session’s runner, so a purchase in one window leaves the other on Upgrade. Android is one session per process; this is the Apple process. **Decision:** the `Transaction.updates` / `Status.updates` / `Storefront.updates` tasks and the Android `BillingClient` are process singletons that `destroy` does not cancel. When the last session ends they stop; the next session starts them again and sweeps `unfinished` and `currentEntitlements`. A store change calls `changed("listPurchases")` in every live session.

9. **MINOR.** D2 and D14. D2 quotes Apple’s rule that `AppStore.sync()` is called only from an explicit user action, because it presents an Apple ID prompt.
