**Panel review — Fable seat. Five fundamental issues, most serious first.** (Claims were checked against the worktree; the diaries themselves are not in the repo, so the counts are taken as given.)

**1. D5 solves the wrong problem and ignores the mechanism already built for it.**
`verify` already has `app.json verify.accept` (LLP 1116.004, amended 2026-10-16; `scripts/verify.mjs` lines 55, 505-514, 1022-1030; `accepts()` in `scripts/agent-check.mjs:203`): findings the app's design accepts, keyed by `check` kind plus testId, printed under "accepted", not counted, with idle entries named. The RFC never mentions it. The evidence it cites — 500-625 standing problems on every run of one app, and ten diaries where `verify ios` was never green for "the same six refusals" — points at two different defects, neither of which a new/fixed/standing delta touches: (a) the standing set itself is the bug (500+ findings from `check`'s heuristics on one app means the heuristics misfire on that design, cf. QUEUE.md:189, or the builders never found `accept`, the same "did not find it" pattern §3 describes), and (b) refusals are exit-1 failures, not findings, so a delta over findings leaves "never green" exactly as it is. A delta on top of 500 findings normalizes the noise rather than removing it. Instead: classify that app's standing set by kind; fix or scope the heuristics that produce the bulk; widen `accept` where it cannot take a finding today (nodes without a testId, large-text and compiler-warning lines). If a delta survives that, key its identity on what `accepts` already uses (kind + testId) rather than threading the source map into `verify`.

**2. D6's dep-info change annotates a refusal whose cause is already known; fix the cause.**
`docs/game-pitfalls.md:139-144` records it: Cargo's cached dep-info holds absolute output paths, and on macOS alternating `/tmp/...` and `/private/tmp/...` makes `unitDepInfo` refuse a valid unit. `scripts/cargo-dep-info.mjs` compares with `resolve(...)` (lines 128, 155, 178), never `realpathSync`, so one spelling mismatch on either side fails the `includes`. Thirteen diaries hitting one refusal, three for whom "rebuild the stale unit" did nothing, is the signature of a false refusal, not an under-described one. Canonicalize both sides of the comparison (and the `target_directory`/`build_directory` nesting test) so the refusal stops firing on a path-spelling difference; the longer message is then moot.

**3. D6's simulator-state addition cannot distinguish the case it was written for.**
`host/apple/devices.mjs:249-298`: `simulator()` already boots the device and blocks on `simctl bootstatus -b` before `agent.mjs` ever runs `simctl launch`. So when "the app never opened its agent socket" fires after 20 s, `simctl list` will say `Booted` in every case, including the boot-logo hang the diary describes (that is a SpringBoard-not-ready state simctl does not expose). The process-alive half is useful; the state half is dead information. Instead: at the refusal, report whether the pid `simctl launch --console` returned is still alive, and attach a `simctl io screenshot` of the display (the driver already has `simulatorDisplay` plumbing) so a boot logo, a crash dialog or a blank window is seen rather than inferred.

**4. D2 is gated on the wrong switch and on an unlanded document.**
`HatchDiagnostics.measuring` exists on main today (`host/apple/Sources/ExactKit/HatchDiagnostics.swift:29`) as `available && FrameSampler.atBoot`, flipped by `measurePerf`: it is a perf-sampling window, not "this is a development build". Gated on it as written, D2's host lines would be absent from exactly the ordinary drives the twelve diaries describe. The switch D2 means is `HatchDiagnostics.available` (`!ExactEnv.productionBake`). If LLP 1142 redefines `measuring`, D2 inherits a dependency on a draft that is not in the repo (`ls llp | grep 1142` is empty), and the plan should say D2 waits for it or drop the coupling. (Plumbing otherwise checks out: `session.log` already lands host lines in `Runner::log`'s journal from `DocumentPickers.swift` and `Picker.swift`, so D2 is genuinely "more rows in that set".)

**5. D1's "moving" arm rests on an assumption that does not hold under default agent timing.**
Under the agent driver, pushes, sheets, modals and alerts are presented unanimated: `animated: !ExactEnv.agentFreezes` in `NavigationIOS.swift:755`, `ModalIOS.swift:689`, `DialogSheetIOS.swift:354`, `MenusIOS.swift:1331`; `agentFreezes` is true unless `EXACT_AGENT_TIMING=platform` (`Session.swift:47`). A `transitionCoordinator` or `isBeingPresented` in flight therefore occurs only under platform timing, real touches, or an interactive Back — not in the frozen-clock drives where the six diaries lost 25 minutes. Those `no view N on screen` refusals are more likely "covered", "unmounted", or an unanimated presentation whose completion lands a run-loop turn after the tap replied, and "a push is still moving; `clock settle` first" would be the wrong advice for them. Before building four arms, reproduce two of the cited failures and record which arm each would hit; if none is "moving", that arm is dead code and the remedy text for the asynchronous-completion case is what to write.

D3 and D4 check out: web-js already depends on the `contract` lib crate with `SourceMap::bake_error` as the model (`host/web-js/src/main.rs:393-405`, `contract/cli/src/map.rs:173`), and the JSON decoder already accepts a numeric array for a bulk (`game/engine/src/data/json.rs:362-370`). No fundamental concern with either.
