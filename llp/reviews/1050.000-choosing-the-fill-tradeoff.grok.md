## Review (verbatim)

The proposal is the right shape and it is not ready to rule on. One list engine can offer drop-views versus drop-frames, and that should not be two libraries. The default rule is a good product hypothesis, but this draft treats it as already true, and the mechanics do not implement it. Revise and stay Draft.

The checkout is `65d2a585`. Both documents are uncommitted. Code citations below were read here. Platform claims that are not in this tree are marked as knowledge, not checked against current vendor sources. `list_text` on Apple and Linux, and whether `710b29a6` / `b2b268bd` are in this commit, were not verified.

## 1. Overall assessment

**Question 1 — can a list let an app choose?** Yes, on the hosts that scroll on the thread that paints, and only partly on the web. The research record is right about the moment the choice exists: prefetch is not the choice; the choice is a frame that is due while visible rows are unbuilt (research §1). iOS, the macOS main-thread route, and Linux can wait or hole. The web compositor cannot wait on a user scroll (research §2.1; RFC §2.3). That split is real in this tree, not only in the platform survey: the legacy window never rations rows the scrollport shows (`runner/src/runner/lists.rs:88-93`, `runner/src/instance/window.rs:664-668`), and the collection has no row budget at all (`runner/src/instance/collection/api.rs:17-39`).

**Question 2 — is that the best thing to want?** Not as the first lever, and the RFC says so (§3). The better want is: one engine, a budget, build the landing first, make a row cheaper. The policy is what you do with what those miss. The draft then undermines that ranking by making `fillPolicy="auto"` the default that decides Charlie's deferred never-blank versus never-stall choice for every list, and by scheduling that policy before the ceiling, the landing prediction, and reuse (§7).

**Question 3 — one abstraction or several libraries?** One engine. Two libraries are the wrong cut, including after steelmanning them (§4 below). The per-scenario table is not what forces that conclusion. A per-list `complete` | `smooth` on one engine would also be one abstraction. The classifier has to win on its own, and it is the weakest part of the draft.

Do not treat this RFC as accepted design. Several statements the stages depend on are false in this tree (retirement, the 100 ms "overload bound", web jumps landing complete, `abi.rs:405`).

## 2. Strengths

- **The question is scoped to one moment.** Research §1 and RFC §1 separate cheaper rows and earlier rows from the hitch-versus-hole choice. That matches how the legacy pump already works: uncovered visible rows are reported immediately, the lead is filled in slices (`host/apple/Sources/ExactKit/Mac/PresenterMac.swift:432-453`, `:545-555`; `host/apple/Sources/ExactKit/IOS/ScrollPumpIOS.swift:73-88`, `:151-160`).
- **The platform split is the right one.** Where the platform moves pixels off the main thread, a user scroll cannot block on row construction. Where this process both scrolls and paints, it can. Research F1–F3, and the "app-initiated moves can wait everywhere" point, are the part worth keeping even if `auto` is rejected.
- **It refuses to steal momentum.** Slowing the fling stays out (RFC §1, Q4), which matches LLP 1010's "never reset native momentum" (`llp/1010-scrolling-v1.spec.md:331-332`) and `rules/NOT-DOING.md:258-260` ("Scroll always wins" as a refusal to own a gesture arena).
- **One engine is already the repo's direction.** `QUEUE.md:48` says bring `virtualized=true` up to the windowed list and delete the windowed one. RFC §4's drift list matches the code: only the legacy path has a budget and a velocity (`window.rs:472-474`, `lists.rs:88-93`); the collection window is ±1 viewport with no velocity and destroys rows in the same update (`runner/src/instance/collection/index.rs:259-262`, `runner/src/instance/collection/mod.rs:476-478`).
- **The author surface is small.** Three policies, no per-list millisecond knob (RFC §5), pending opt-in as the list background. That is the right size if the semantics are tightened.
- **The runner-does-not-read-a-clock rule is the right split**, and it is already how the legacy path works (`ScrollPumpIOS.swift:35-48` turns a duration into a row count; the runner only sees `create_limit`).
- **Q1–Q4 in RFC §8 are the owner's questions.** The draft is honest that the ceiling number and the default look are not decided.
- **The research marks its inferences.** Responsive scrolling carrying unmounted rows as holes, `preparedContentRect` as the steering hook, and self-rendered Windows/Android off-thread scrolling are labeled inference (research §2.2, §5). That discipline should be kept.

### HIGH — The 100 ms ceiling is not LLP 1041's bound, and the `limit` encoding cannot enforce any ceiling

RFC summary point 3 and §2.2 say a synchronous fill may take 100 ms because that is "LLP 1041's overload bound" and 1044.001's cold-jump p95.

LLP 1041 says one frame is `1000/H` (8.33 ms at 120 Hz) and that this is the whole frame, not a budget the runner may spend (`llp/1041-graceful-overload.rfc.md:19-21`). A time check after a long call cannot undo the missed frame; the work has to be incremental or leave the UI thread (`:96-101`).

1044.001's 100 ms figure is end-to-end content, and the same row forbids an event-handling span over 4 ms (`llp/1044.001-text-performance-astra.plan.md:264`). The overload row is pending feedback within one refresh, not a 100 ms stall (`:265`). §5.3 allows a pending landing area under overload and no placeholder in ordinary reading (`:216`).

The encoding makes even a real ceiling unenforceable. RFC §6 defines `limit` as rows created **beyond those the policy requires**. On drag, wheel, and `complete`, the policy requires every visible row, so they are outside the cap. That copies today's rule (`lists.rs:88-93`, `window.rs:664-668`) and then claims the opposite result. One 256-cell row is one runner call. 1044.000 already found a report indivisible and a dense row at 4.0 ms p50 / 6.5 ms p95 (`1044.000:350-354`), and the deferred case is a row of 256 cells (`:475-476`). 1044.001 Slice C says a dense row has to yield between cells (`1044.001:309`). This RFC never says that.

**Resolve:** Delete "1041's overload bound" as the name of 100 ms. Pick a main-thread hold that matches 1044.001's span (a few milliseconds), and keep 100 ms as time-to-correct-content if you want that number at all. Define `limit` as a cap on rows created in this report, in priority order, with no exemption. State plainly that a single row heavier than the cap still hitches until construction yields inside the row, and either pull that yield into this RFC or say the 256-column case is out of scope.

### HIGH — "Retirement only when creating" is not the legacy path

RFC §6 cites `window.rs:692-704` for "retirement happens only in reports that also create rows."

```696:701:runner/src/instance/window.rs
        let retire = if !defer_retirement {
            leaving.len()
        } else if creating || deferred.is_empty() {
            (2 * limit).max(4)
        } else {
            0
        };
```

Retirement also happens when nothing is left to create, and it happens for every leaving row when `defer_retirement` is false. That flag is false when port height, origin, width, or pins change (`window.rs:777-803`). LLP 1010 states the fuller rule (`llp/1010-scrolling-v1.spec.md:476-477`).

Implemented as written, a `smooth` fling whose budget creates nothing (`creating == false`, `deferred` non-empty) would keep every row that has left the window.

**Resolve:** Copy the real rule into §6: retire with a report that creates, or once nothing remains to create, and always when the viewport or the pins change. Bound how many leave per report.

### HIGH — `auto` does not do what §2.1 says it does to the case that motivated it

§2.1 says the 256-column table "is a fling" and that under `auto` it "flies over with pending rows and lands complete." The source paragraph says it scrolls at 3–5 fps because the scroll callback builds visible rows (`1044.000:474-478`). It does not say fling.

The table then classifies a finger-down move as drag, and drag **waits for visible rows** (RFC §2). A fast swipe is a drag until release. Only the coast is "fling, passing over." A short coast of a viewport or two still passes over rows a person can read; the table has no distance or speed floor.

On the web, "wait" is defined as "fill on the next frame" (§2.3). "Lands complete" is false there. Research §2.1 already says the web exposes no fling target. §2.3's "velocity projection from `scroll` samples" is an inference promoted to a column in the host table. A constant-velocity projection of a decelerating fling overshoots. That is knowledge of browser scrolling, not a measurement in this checkout.

The overload ceiling, once it is honest, also breaks the slogan. A drag whose visible rows exceed the hold hitches for the hold and then shows pending. The reader gets both a hitch and a hole. Stage 2's done-when ("flies over pending and lands complete") is not a test you can fail or pass.

`auto` as the default also decides the product choice Charlie deferred on 2026-09-21 (`1044.000:472-479`, `QUEUE.md:64`) for every list, including Messages. `complete` as an opt-in does not make that a small default.

**Resolve:** Split "one engine" from "this classifier is the default." Name the input that produced 3–5 fps. Add the missing causes (below). State the web landing as "best effort, may hole for at least one frame," not as complete. Do not make `auto` the default in the contract until that table is something each host can actually tag.

### HIGH — The build order drops focus and interaction pins

Legacy `render` always adds pinned indexes to the wanted set (`window.rs:482-486`). The collection window takes two pin keys (`index.rs:250-268`). RFC §4 lists focus pins as a reason there must be one engine. RFC §6's order is: policy rows, landing viewport, ahead, behind. Pins are not in it.

A focused editor, or the row under a finger, can sit outside the landing zone during a fling. Under the written order it is eligible to be skipped and then retired.

**Resolve:** Under every policy, including `smooth`, the focused row and the interacting row are owed. They are not pending and they are not retired.

### HIGH — Stages contradict §3, and stage 2 ships unbounded waits

§3 ranks budget, then landing-first, then cheaper rows, then the policy "once 1–3 are exhausted." §7 ships `auto` at stage 2, landing at stage 3, the ceiling and the overrides at stage 4, reuse at stage 5.

Stage 2's `auto` includes `wait*` for drag, jump, and data change. The ceiling that is supposed to bound every wait is stage 4. A stage-2 tree can hold the main thread for a whole visible window of expensive rows, which is the behavior §2.2 says must not ship.

Stage 0 makes a new Contract app and an Expo comparison part of "done when." `rules/NOT-DOING.md` has repeatedly traded away new benchmark apps. 1044.001 §9 says not to add apps or change working-set links under that plan (`1044.001:369-373`). `rules/RULES.md:64-67`: an agent does not add a design doc or a check without a human saying so. Charlie asked these three questions, so the draft itself is solicited. A new in-repo Expo app is not. `llp/current/` now contains this RFC; that file was not in the tree before, and the working set is capped at 15 (`rules/RULES.md:12-13`). The research note is correctly not linked. The RFC link spends the slot before anyone has accepted it.

**Resolve:** Put the hold ceiling in the same stage as the first `wait`. Move landing-first and the row-cost work ahead of `auto`, or stop calling the policy the last lever. Make stage 0 "report hitch time and blank area for the two engines we have," and leave Expo as Q6, outside the repo, unless Charlie names what comes off the doing-list. Keep the RFC in `current/` only if he wants the slot spent on a draft; otherwise unlink it until he does.

### MEDIUM — `pending`, accessibility, selection, anchors

- **`smooth` at rest hides the rows a screen reader would land on.** Pending intervals are `aria-hidden` and take no input (RFC §5). `auto` rebuilds at rest, so this is mostly a `smooth` bug. `complete` on the web never reaches rest with all rows present. LLP 1010 already left virtual accessibility navigation unfinished (`llp/1010-scrolling-v1.spec.md:380-383`). Making on-screen gaps `aria-hidden` extends that hole to pixels the user can see.
- **Selection across a gap is unspecified.** "Takes no input" might be `pointer-events: none` (the list still sees the drag) or a view that eats the drag. Logical copy without mounting is a windowed-list feature (`lists.rs:57-63`, `list-selection.js:1-3`, web glue at `glue.js:186`). Whether the collection path on Apple and Linux uses `list_text` was not verified.
- **Landing-first fights the anchor suppression you already have.** `CollectionIOS.swift:66-69` refuses `setContentOffset` while the user is tracking, dragging, or decelerating. Estimated heights for a predicted landing will be wrong often. Corrections wait until the fling ends, which is a jump at the worst moment. §6 does not mention this.
- **A width change is classified as "wait"** (RFC §2, citing the nonexistent 1044.000 §5.3). Live resize is a stream of those. 1044's actual rule is to keep the last good raster and not block the shell (`1044.000:233-235`, `1044.001:266`). Waiting up to a content budget on every width sample fights that.
- **The `pending` block can cost as much as a row.** "Rasterized once per distinct size" (`RFC §5`) is once per row when estimates differ. It is not forbidden from resources, images, text measurement, or handlers. A placeholder that runs app work erases the point.
- **Old-pixels versus wrong-row is blurred.** "Old rows never stand in for new ones" should mean a recycled view is cleared before it shows a new item. It should not mean the previous frame's pixels are wiped before the scroll moves them. Responsive scrolling and the browser compositor are that second thing (research §2.1–2.2).

**Resolve:** Pins and the landing row are real views. Pending bands are `pointer-events: none`, not hit targets. `smooth` still materializes the row accessibility focus enters. Specify selection as the existing logical path. Write the anchor rule: do not correct against estimated pending rows until the coast ends, and do not jump then if the correction is only estimate error. Constrain `pending` to static paint, no resources, no `each`.

### MEDIUM — Agent `state`, the eight operations, and the wire

`state` today is clock, slots, derives, resources, in-flight requests, store names, head, delivery, logic (`runner/src/agent.rs:437-535`). There is no coverage or hole count. LLP 1012 says `state` is answered in the runner (`llp/1012-agent-api-v1.spec.md:16-19`). A hole is "a frame was presented with a gap." The runner does not present frames and, by §6, does not read a clock. Host-counted `holes` / `waits` in `state` will differ per host and flake.

"Pass an explicit `limit` through the agent" (`RFC §6`) is a new input. `rules/NOT-DOING.md:285-292` allows a new question inside `state`, `tree`, or `layout`, and says a ninth operation replaces one of the eight. A test-only runner call is not an agent operation. An agent operation would be.

Adding four fields to `CollectionFeedback` breaks wire version 1. Web and Apple encode that layout by hand (`collection-glue.js:15-24`, `Collection.swift:20-30`). Linux builds the struct in Rust (`presenter/collection.rs:669-703`). §6 does not mention the version or the three encoders.

`clock settle` already tries to fill the window: `ScrollPump.settle` loops `syncLists()` with the default limit, and the Mac pump does the same up to eight rounds (`ScrollPumpIOS.swift:169-176`, `PresenterMac.swift:526-534`). Limit 0 means the whole window (`llp/1010-scrolling-v1.spec.md:479-480`). "Settle ignores policy" matches that, with the existing eight-round cap left unstated.

**Resolve:** `state` may list current pending intervals, which are a function of the report. Frame counters stay in the existing signposts (1044.001 §8 already asks for coverage timestamps, and asks Charlie before adding diagnostics, `1044.001:351-361`). Drive pending tests through `list_viewport_within` / collection feedback in runner tests, not a new agent verb. Bump the feedback version in the same change as the fields.

### MEDIUM — Naming against "the web is the standard"

`fillPolicy` is camelCase to sit with `scrollFollowEnd` and `retainFocus` (RFC §5). Those are camelCase in the schema (`kernel/tables/schema.json:311`, `:341`). The list's own host-policy attributes are kebab-case even though LLP 1010 says they are not CSS (`llp/1010-scrolling-v1.spec.md:350-354`): `item-height`, `estimated-item-height`. `virtualized` is a single word (`schema.json:256`).

`smooth` collides with CSS `scroll-behavior: smooth`, which means an animated scroll, not "drop views." An author who sets `fillPolicy="smooth"` will think they asked for smooth scrolling.

`contain-intrinsic-block-size` (Q5) is a real CSS name for the size of skipped content. It is a stretch as a rename of a list's row estimate: in CSS it applies to the element that is skipped, not to the list. Leaving that rename out of this RFC is right.

**Resolve:** `fill-policy` next to `item-height`, values that cannot be read as `scroll-behavior`. If the words stay, define them once as "prefer rows" and "prefer frames."

### MEDIUM — One-abstraction argument, steelmanned

The opposite case, as strong as it gets:

A `complete` list and a `smooth` list want opposite host integrations. `complete` wants the main thread to finish rows before the frame, and on the web that means giving up compositor scrolling, which this repo has refused. `smooth` wants the platform scroller and cheap stand-ins. UIKit, RecyclerView, and the browser already ship the second kind. Wrapping each platform list, and keeping today's synchronous window for logs and screen recordings, avoids a six-cause classifier and a cross product of host × cause × policy. React Native's FlatList versus a recycling list is that split, and Expo's PR is cited because the recycling list blanks on purpose (research §2.3). One component that does both will carry both bugs.

The steelman still loses, for the reason §4 actually proves, not for the per-scenario slogan.
