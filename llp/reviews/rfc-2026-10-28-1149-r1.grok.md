## 2. LLP 1149 §5

### 1. Write our own renderer, rather than take vello, GPUI, or Skia?

**Yes. Confidence: 70.**

GPUI is a framework, and Skia already lost the one bake-off this repo ran (LLP 1056 §8.5: Ganesh compiled SkSL on device, 1,133–1,188 MB on the iPad against vello's 154–162 MB). Classic vello is a compute renderer. That misses a DirectX 11 feature-level 11_0 floor and WebGL2, which is the real reason to leave it.

What the draft treats as vello's cost is mostly the current integration. Android already presents vello into a Vulkan swapchain with no readback (`host/linux/src/gpu/present.rs` lines 1–18). Apple's Canvas module already compiles kernels to a `.metallib` at build (`canvas/vello/build.rs` lines 7–10; LLP 1056 §8.5, 0.7–2 ms of pipeline-state creation). Linux's 773 ms / 77 ms shader hit and the 17–19 ms Metal map (LLP 1015 §7) are runtime WGSL plus a readback, which a presenting, precompiled vello would not pay. Device creation at 23 ms warm and 93 ms first launch (LLP 1015 §6) is wgpu's, and `MTLCreateSystemDefaultDevice` / `D3D11CreateDevice` / `vkCreateDevice` still sit on the boot path either way.

**What would change my answer:** S0's screen, drawn by precompiled vello into a swapchain with no readback, matching exact-ink on cold start, fling CPU, and memory within about 10% on the NucBox and the minisforum, including a WARP or VM run. If that holds, the five device layers are not earned.

### 2. Each platform's own API, not wgpu, amending LLP 1009 D1 only for the host?

**Yes. Confidence: 76.**

LLP 1009 D1 says wgpu is the one GPU API and "we own no API of our own." wgpu's Windows backend is DirectX 12, so it cannot be the Windows floor in §5 question 3, and it cannot host `ITextServices2::TxDrawD2D` on the same device (LLP 1115.004 D7). Scoping the amendment to the host renderer, and leaving app GPU code on wgpu, is the right cut.

The RADV 23/93 ms figures do not show that a hand-written device is cheaper to create. S0 plans to prove parity by reading a Metal texture back, so it will not show presentation bugs. The Mac's tier-2 Windows check is a cross compile (`scripts/async.mjs` lines 95–97) and cannot run `fxc`; `build.rs` has to embed bytecode or stub, the way `canvas/vello/build.rs` stubs off Apple.

**What would change my answer:** a wgpu DX11 backend with composition-swapchain, waitable latency, and `AHardwareBuffer` / DXGI shared-handle import that is actually smaller on the boot path than the five devices. There isn't one.

### 3. DirectX 11, not DirectX 12, on Windows?

**Yes. Confidence: 88.**

A UI of a few instanced draws does not need DirectX 12. DirectX 11 feature level 11_0 plus `D3D_DRIVER_TYPE_WARP` covers virtual machines and Remote Desktop ([WARP](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/directx-warp)). Direct2D is a DirectX 11 interop (`ID2D1Device` from `IDXGIDevice`), which is what `TxDrawD2D` needs. DirectX 12 would put Direct2D behind `D3D11On12`.

The swapchain in D7 is the part that is wrong, not the API choice. See Errors.

**What would change my answer:** a measured DirectX 12 present that beats DirectX 11 on the NucBox's cold start and fling and still draws the RichEdit without a readback.

### 4. OpenGL ES 3.0, not Vulkan, on Android?

**No. Keep the Vulkan swapchain. Add GLES only for a device Vulkan cannot open. Confidence: 78.**

`gpu/present.rs` already presents vello into the `ANativeWindow`'s Vulkan swapchain, one frame in flight. Replacing that with a new GLES device throws away the working present path. On current Pixels the system GLES driver is ANGLE over Vulkan, so "GLES is the native API" is often a translation layer. D10's worst interop cell is a wgpu Vulkan canvas module (LLP 1009) sharing an `AHardwareBuffer` with a GLES renderer.

**What would change my answer:** on the Nothing 4a Pro, GLES beating the existing Vulkan presenter on cold start, fling CPU, and energy, with the canvas module imported and no extra copy.

### 5. One WGSL source, translated at build, with hand-written overrides where a measurement earns them?

**Yes. Confidence: 80.**

## 3. LLP 1149.000 §4

**What would change my answer:** a named app whose only painted surface is one region of a DOM page. Then D7 jumps the queue, and the per-app key stays for apps that are canvases.

### 3. The accessibility mirror and the editing proxy are required, not optional?

**Yes. Confidence: 88.**

A canvas with no accessibility tree fails the same test as Flutter web. The proxy is required because a `<canvas>` does not take IME composition.

EditContext is Chromium-only. Can I Use shows Chrome and Edge from 121, Firefox through 156 unsupported, Safari through 27 unsupported ([caniuse](https://caniuse.com/mdn-api_htmlelement_editcontext)). That matches the draft. What it omits: the candidate window is placed by `characterboundsupdate`, not by the canvas's CSS box ([Chrome's EditContext introduction](https://developer.chrome.com/blog/introducing-editcontext-api)). The mirror also collides with "find in page is not in v1." Browser find searches text in the layout tree. An off-screen mirror with real text nodes is found; a mirror of only `aria-label`s is a worse screen-reader experience. See the missing question.

**What would change my answer:** a browser API that exposes the kernel's roles without a second tree. There isn't one.

### 4. Text rasterized by the browser as shaped runs, not glyphs?

**Runs for complex scripts. Simple Latin and digits as reusable clusters. Confidence: 68.**

The page cannot ask for a glyph id. `measureText` is what LLP 1001 §6's injected measurer already uses on the wasm target (`host/web/textflow-glue.js`), so drawing with `fillText` in the same CSS font keeps advances and ink together. `OffscreenCanvas` 2D supports `fillText` in current Chrome, Firefox, and Safari.

A whole-run atlas does not share ink. D2 names a grid of a hundred thousand cells as a reason to paint. Those cells repeat digits. Keying the atlas by the entire string stores "1234.56" and "1234.57" as unrelated images and will thrash D8's ceiling. `fillText` of one cluster at a time still uses the browser's rasterizer, matches a per-cluster `measureText`, and shares digits. Keep an unsplit run where shaping does not divide (Arabic, emoji sequences, ligatures the measurer treated as one unit).

**What would change my answer:** an atlas measurement on a Sheets-like grid where whole-run entries stay under the 2048² ceiling and the rasterization stays off the frame budget. Then whole runs are simpler and fine.

### 5. The DOM build of the same app is the oracle?

**Yes, with a declared text band. Confidence: 74.**

Same app, same browser, same crops is the right comparison, and it is the one the native painters already owe Chrome.

Canvas `fillText` and DOM text do not match in Chrome: the canvas path is Skia's, subpixel antialiasing is off for a canvas that is not the DOM's text, and gamma differs. LLP 1015 §8 already declares a text deviation between vello outlines and swash bitmaps and asserts mean 5/255 and 6% of pixels over a difference of 32. Copying that band onto DOM-versus-canvas text crops will fail for a reason that is not a bug. Declare a text band the way §8 does, and keep the tight band for rectangles, images, and solids.

**What would change my answer:** a crop set where DOM text and `fillText` already fall inside the existing band in Chrome, Firefox, and WebKit. Then one band is enough.

### 6. Build it last, as S5, with no consumer named yet?

**Yes. Confidence: 82.**

The prospect is Windows-first and native. A web device with no app would be the GPU module's mistake again. The no-compute, instanced-quad design is what makes WebGL2 possible later (`drawArraysInstanced` is core in WebGL2). Hold the shader to GLES 3.00 and WebGL2 in S4's tests so S5 does not discover naga's GLSL backend on its own.

One looseness: LLP 1071 estimates a JavaScript runtime of about 5–8 KB and a Caltrain payload around 20 KB. "A 20 KB runtime" is the payload goal, not the runtime.

**What would change my answer:** a named design tool or map that must ship on the web before S4. Then S5 moves up, and it still does not become the default.

**No. Confidence: 82.**

"Mostly prose" is not a property the build can compute without false refusals (a mail client, a chat, a mixed board). Printing the tells, as LLP 1071 §7 prints refusals, is the right pressure. The author who paints a document has the cost on screen.

## 4. Errors

1. **Windows is not "presented with damage" on the frame path.** `host/windows/src/window.rs` line 466 calls `buffer.present()` for the full frame. `present_with_damage` is only the caret blink (lines 573–576). LLP 1149 §1 and LLP 1148 F7 overstate this.

2. **The pair "11.3 ms at 1280×720, 20.7 ms at 1920×1080" is not what those plans report as the current cost.** LLP 1015.000 lines 265–269: paint+readback p50 **11.29 ms** at 1280×720, desktop locked, one development run. LLP 1015.001 lines 96–99, the landed table: fallback 11.56 / 20.74 ms, fast path **7.22 / 10.83 ms**. 11.3 rounds the earlier 720p number. 20.7 rounds the 1080p fallback, not the fast path in the same table. 1015.000 has no 20.7.

3. **`DXGI flip discard` plus dirty rectangles does not do what D7 says.** Microsoft documents dirty rectangles on a flip-model chain created with `DXGI_SWAP_EFFECT_FLIP_SEQUENTIAL`, and the runtime copies the preserved region from the previous buffer ([DXGI 1.2 presentation improvements](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-1-2-presentation-improvements)). `DXGI_SWAP_EFFECT_FLIP_DISCARD` does not preserve buffer contents ([`DXGI_SWAP_EFFECT`](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ne-dxgi-dxgi_swap_effect)). D7 names flip discard. D7 also says the whole frame is redrawn on the GPU. A dirty rectangle only saves bandwidth when the app did not redraw those pixels. A full redraw makes the dirty rectangle the whole buffer.

4. **That HWND flip chain contradicts accepted LLP 1115.004 D4.3.** Mica needs the frame's alpha to reach DWM. D4.3 (lines 236–242) moves presentation to `CreateSwapChainForComposition` with premultiplied alpha, and forbids `WS_EX_LAYERED`. An HWND swapchain's alpha mode is `DXGI_ALPHA_MODE_IGNORE`. DirectX 11 can create the composition swapchain; D7 does not say that.

5. **`push_css_clip` and `push_svg_clip` are implemented by both shipping painters.** `gpu.rs` lines 921–974 and `raster.rs` lines 1075–1110 return success. The trait default returns false / 0 (`backend.rs` lines 189–198). D2.4's "may already refuse today" describes the default, not the painters being replaced. Turning every CSS clip and SVG clip into a viewport-sized layer is a new cost.

6. **The Backend list in §1 omits methods the walk calls, and names a caret method that does not exist.** The caret is drawn by `paint/caret.rs` and `paint/neutral.rs` through ordinary fills. There is no `caret` method. `pointer` exists (`backend.rs` line 216). Unlisted and load-bearing: `page`, `begin`, `text_blur` (numeric rolls, `paint/numerals.rs`; implemented by the Android recorder at `canvas.rs` line 695), `pop_clip`, `pop_opacity`, `finish` / `finish_for`, and the window split (`split_window_canvas`, `take_window_underlay`, `window_overlay_rows`). `gpu/README.md` lines 14–29 is the current Windows game composition ABI, and it says no GPU texture crosses the DLL boundary. D10's shared handle is a new ABI, not a description of today's.

7. **D3's Android row is false in this repository.** "There is no platform rasterizer to match on Android" ignores `Canvas.drawGlyphs` from the shaper's font files (`canvas.rs` lines 1–8). swash is the swapchain painter's rasterizer, not the platform's.

8. **D9 and D3 cannot both be true unchanged.** Platform gray glyphs will not land inside LLP 1015 §8's swash-versus-outline band. The advance audit in LLP 1115.004 D6.3 is a different test from that pixel band.

9. **The 64-byte instance does not fit D1's fields.** Affine 24 bytes, rectangle 16, four f32 radii 16, colour 4, texture rectangle 16 is 76 before the clip. "Ten thousand instances of 64 bytes are 640 KB, a memcpy" depends on a layout the field list does not have. The texture-row side of D4 (1.44 MB, about 30 MB for twenty) does add up.

10. **LLP 1091.001 does not say Windows builds are made on Windows.** That file is "Windows package staging without symlink privilege," and it is superseded. The build rule that matches the claim is `host/windows/build.mjs` line 8: the Windows host is built on Windows with the MSVC target. The tier-2 check on the Mac cross-compiles `exact-windows` and will not run `fxc`.

11. **"Android's EGL keeps a program cache" is only the Android special case.** `EGL_ANDROID_blob_cache` is an application-managed cache in the Khronos extension. Android's copy of the text says the Android EGL module installs the callbacks and hides the extension from apps ([extension text](https://www.khronos.org/registry/egl/extensions/ANDROID/EGL_ANDROID_blob_cache.txt), Android note). The first process still compiles. Later launches depend on the device EGL. It is not an EGL guarantee, and it does not make D6.3's "compiles nothing" true on first boot.

12. **`eglSwapBuffersWithDamageKHR` and `VK_KHR_incremental_present` are hints, and the Linux one does not match a KMS page flip.** The EGL extension says the rectangles may be ignored. HWUI uses them, and also `eglSetDamageRegionKHR` (`EGL_KHR_partial_update`) so a tile-based GPU can skip untouched tiles. Exact-ink's full redraw cannot use the partial-update path, which is the battery win on Mali and Adreno. `VK_KHR_incremental_present` is optional and a hint ([Khronos](https://registry.khronos.org/vulkan/specs/latest/man/html/VK_KHR_incremental_present.html)). LLP 1015 §7's Linux present is a DRM dumb-buffer page flip; a full-screen flip scans the buffer out. Damage rectangles there do not shrink scanout.

13. **LLP 1149.000 D3 says pinch zoom is handled.** Desktop page zoom changes `devicePixelRatio`. iOS pinch zoom changes `visualViewport.scale` and does not change `devicePixelRatio` ([Visual Viewport](https://wicg.github.io/visual-viewport/), [devicePixelRatio](https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio)). The browser then scales the canvas bitmap. That is a blur, and it belongs in the tell column.

14. **D5's "one pipeline, the kind selects the fragment path" plus D4's "a few batches" needs the instance to carry the kind.** That part is consistent. It is inconsistent with a 64-byte budget once the clip and the texture rectangle are included, as in error 9.

15. **D5's "Vulkan nearer two" thousand lines contradicts D14 and `rules/RULES.md`'s 1,500-line cap.**

16. **Metal "loads binaries, so the boot path compiles nothing" omits the measured pipeline-state build.** LLP 1056 §8.5: 0.7–2 ms warm from AIR. The DEFERRED exception being withdrawn at S3 (the text at `rules/DEFERRED.md` lines 631–638, under the Runtime bullet) is the Linux painter's shader compile, cited correctly. Withdrawing it while `vkCreateGraphicsPipelines` still runs on first launch leaves the behavior the exception was written to allow. Counting it in `metrics.mjs` is not the same as fitting the 100 ms budget.

17. **The Apple cold-start citation is real, and it is the landing-tip number.** LLP 1056 §8.5 line 782: 103–157 ms at the tip. The bake-off comparison earlier in the same section is 117–166 ms. The draft picked the tip. The 0.7–2 ms figure is "warm," not a cold driver.

18. **LLP 1149.000's "20 KB runtime" loosens LLP 1071.** 1071's summary estimates the runtime at 5–8 KB and the whole small-app payload near 20 KB. The DOM-default claim does not depend on the number.

## 6. Risks the documents understate

1. **Windows presents the wrong kind of swapchain, and the prospect is Windows-first.** D7 as written cannot satisfy Mica or dirty-rect copies. Mitigation: the composition-swapchain spike beside S0, before `instance.rs` freezes a full-frame redraw as the present model.

2. **Platform text versus the tiny-skia band.** S1 and S2 can fail D9 for a reason D3 requires. Mitigation: split the gate, as in missing question 2, and write it into D9 before anyone treats a red parity run as a rasterizer bug.

3. **Five device layers, with S0 only exercising Metal readback.** Presentation, loss, and interop stay untested until each platform's stage. Mitigation: one lavapipe test and one WARP test in S0 that create a device, draw one rect, and read back, so the trait is not Metal-shaped. Keep the 1,500-line split.

4. **D3D11 host and D3D12 wgpu module, and GLES host and Vulkan wgpu module.** `gpu/README.md` currently forbids a texture from crossing the DLL. Shared NT handles and `AHardwareBuffer` import are where "no readback" dies. Mitigation: one imported canvas surface is a D9 fixture on Windows and Android before `gpu.rs` is deleted.

5. **Analytic shadows versus the CPU painter's blur.** The CPU path bands shadows (`paint/shadow.rs`, `BANDS`) and backdrop blur is the SVG three-box approximation over encoded sRGB (LLP 1053.000 D2), including saturate. Evan Wallace's Gaussian approximation will miss that. Mitigation: put one shadow fixture and one `blur() saturate()` fixture in the S0 band, and keep a rasterized shadow path when the analytic one misses.

6. **Full-frame fragment shading during a fling, plus a run atlas on the web.** Instance lists cut the walk, not the fill rate. A web grid keyed by whole strings thrashes the atlas. Mitigation: the cluster atlas, and a frame-time measurement of a text-heavy list before D4 is called a memcpy win.

7. **First-launch pipeline build after the DEFERRED exception is withdrawn.** Vulkan and GLES still compile in the driver. Android's blob cache and a `VkPipelineCache` help the second launch. Mitigation: do not withdraw the exception until the measured first launch on the minisforum and the Android emulator is inside the budget the exception was covering, or name a new exception with the new number.

8. **EditContext and the textarea proxy.** Composition, candidate-window bounds, and password-manager autofill are the long bug list. Mitigation: one Japanese and one Chinese field on Chrome, Firefox, and Safari in the S5 gate, the same journeys LLP 1115.004 D7.1 lists for RichEdit.

## 7. The strongest alternative

Precompile the vello kernels the way `canvas/vello/build.rs` already does, present them to the swapchain the way `gpu/present.rs` already does on Android, and implement `rows()` as retained recordings. Use a small DirectX 11 composition path only if wgpu's DirectX 12 device cannot host `TxDrawD2D` or fails WARP. Leave GLES as the Android fallback, not the Android implementation. Adopt sparse strips (`vello_gpu`) only if that presenting vello still cannot run without compute on the Windows floor.

The measurement that decides: one heavy-list screen, interleaved cold starts, a fling, and a rest, on the NucBox (hardware GPU and WARP), the minisforum, and lavapipe. Compare three builds. Today's painter. Precompiled vello with swapchain present, no readback, kept rows. exact-ink. exact-ink wins if it is clearly ahead on cold start or on CPU-per-second during the fling, or if the precompiled vello build cannot open a device on WARP. The performance work is killing the readback, compiling shaders at build, and keeping rows.
