Nothing here is blocking. The descendant view itself keeps its own press, and `rest` still holds the engine text colour, so its later release restores that colour.

1. **Should-fix** — `host/apple/Sources/ExactKit/PressPaint.swift:217` (inherited colour chosen at `:194`; the wipe is `:242`). A descendant whose own press writes `press_color` never takes the children the ancestor already inked, so the ancestor’s delayed release still clears them. Press the ancestor (`press_color` yellow), then during `releaseHeld` press the child (`press_color` red) that has a grandchild with no colour of its own. `inkBelow` only accepts a child already inked by this press, or whose `text_color` equals `rest["text_color"]` (the engine white saved on the first stand-in). The grandchild is showing yellow and `inkedBy` is the ancestor, so it is skipped. `endInked` then sees `inkedBy === ancestor` and fully restores the grandchild to white while the child is still down and showing red. Same for three levels: a middle node that writes `press_color` does not retake the grandchild, and a grandchild that only has `press_background_color` loses the lent text at the ancestor’s release (`endPressStandIn(only:)`) instead of showing the middle node’s press colour. Fix: in `inkBelow`, also take a node that does not `wrote("text_color")` and whose `inkedBy` is some other press (not itself). Keep the engine value already in `rest`. On the nearer press’s release, if an ancestor press is still `down` or `releaseHeld`, stand that ancestor’s colour back in and point `inkedBy` at the ancestor; do not restore `rest` yet. Releasing straight to `rest` would skip a still-held ancestor colour, because `standInForPress` will not overwrite the first saved engine value.

2. **Should-fix** — `host/apple/tests/ExactKitTests/PressPaintTests.swift:133` and `:136`. The new test does fail on the old code when the hold actually engages: the delayed `endPressStandIn` paints the inner background back to white, and the green assertion fails. It does not lock that precondition. `PressFeedback.unseen` is one frame (`1/60` s). If more than that passes between `v.pressed = true` and `v.pressed = false`, the release runs immediately, the inner press is applied to an already restored view, and every assertion still passes. The checks after the wait also depend on `DispatchQueue.main.asyncAfter` of `PressFeedback.duration` (0.12 s) firing inside `RunLoop.main.run(until:)` with a 50 ms margin — the same wall-clock wait as `testAQuickTapStillShowsThePaint`. A stalled main thread fails the ancestor’s background assertion, or the bug path never runs. The test also never covers a descendant that writes `press_color`, that descendant’s children, or three levels. Fix: assert `v.pressPaint.releaseHeld` immediately after the quick `pressed = false`, and assert the inner text is still yellow before the run-loop wait. Add a descendant that writes `press_color` (its text stays the press colour through the ancestor’s release; its own release restores the engine colour) and a grandchild under it.

3. **Nit** — `host/apple/Sources/ExactKit/PressPaint.swift:259`. `endPressStandIn(only:)` does not leave an empty overlay. That branch runs only when the view’s own press writes no `press_color`, so the press that set `inkedBy` to itself still has `press_background_color` in `overlay`, and `inkedBy === self` is right. An empty overlay with `inkedBy` still pointing at the view happens on the full restore: a down press loses its press-colour rows in `pressPainted` (overlay and `rest` cleared, `inkedBy` left as self), then release hits `guard !pressPaint.overlay.isEmpty else { return }` and never clears `inkedBy`. `atRest` stays false. Current readers still behave: `inkBelow` falls through to the colour compare, and the `writes text_color` branch requires a text overlay. Fix: clear `inkedBy` whenever `overlay` becomes empty, including that early return.
