**Reviewer:** codex gpt-6.1-sol, reasoning effort ultra (confirmed in the run log), run 2026-10-21 by Claude (Opus 5.5) for Daehyeon Mun, read-only (`codex exec -s read-only`) on an export of `87d0fae082` with `llp/reviews/` left out, plus the §3 probe files; it could read the clone and the reference app on disk. Scope given: the ceiling test, the tier boundaries, the deviations, feasibility, the bundled-page alternative, the questions for the ruling. A second family (Grok 4.7) was not run: its CLI was not signed in on this machine. The text below is the reviewer's final message, unedited.

VERDICT: NOT READY

1. **MATERIAL — §4 D3’s commit-safety argument is false.** Immediate decode writes into a track that mounted videos and canvases already observe (`llp/1133.003-video-decode.rfc.md:210–226`). A mapper can decode, then return a malformed snapshot or have its commit refused, while the picture and decoder state still advance. Existing socket effects explicitly wait for successful commit (`host/web-js/ts-stream.js:103–121`). **Resolve:** stage decoder operations until commit succeeds, or explicitly rule a nontransactional exception and define its failure behavior.

2. **MATERIAL — §4 D5’s GPU handoff omits required metadata and ownership.** The promised conversion uses pixel-buffer color attachments, but `gpu_video_frame(track, surface, width, height)` carries neither those attachments nor equivalent metadata (`llp/1133.003-video-decode.rfc.md:250–266`). It also lacks retention and completion rules across frame replacement, multiple readers, reset and stop. Existing Metal imports document their lifetime, retain the texture, and guard reuse (`gpu/src/lib.rs:1225–1238`, `:1250–1255`, `:1288–1294`). **Resolve:** specify a frame descriptor carrying generation, format and color metadata, with retention through asynchronous GPU reads and ordering against queued conversion/render commands.

3. **MATERIAL — §4 D3 defines the wrong `decodeQueueSize`.** Decrementing on outputs counts pending pictures rather than pending decode requests (`llp/1133.003-video-decode.rfc.md:205–209`). Delayed or dropped output therefore changes the consumer’s backlog recovery behavior. The reference resets/resubscribes when this property exceeds eight (`74541bab17:packages/client-runtime/src/device/stream.ts:641–650`); even the clone decrements around submission independently of its output callback (`/Users/daehyeonmun/orca/workspaces/exact2/t3-code-main/examples/t3-code/modules/apple/T3DeviceVideo.swift:204–222`). **Resolve:** decrement when queued input is accepted for decoding, following WebCodecs’ control-queue semantics; track output completion separately.

4. **MATERIAL — §6 misses timestamp-paced playback and selective presentation.** D4 always presents the latest decoded output at the next display tick (`llp/1133.003-video-decode.rfc.md:223–226`). No tier lets an app retain frames, schedule timestamps, or suppress preroll pictures until a seek target: D1 forbids callbacks and D7 reserves the native output callback (`:151–165`, `:294–298`). Demuxing alone does not supply these capabilities, despite §6’s file-demux row (`:314`). **Resolve:** provide bounded presentation scheduling/selection, or explicitly exclude paced file playback and selective output in §§6/13. This is an unnamed ceiling under parent D9 item 4.

5. **MATERIAL — §4 D1/D3 does not replace first-frame notification for GPU-only viewers.** It promises first-frame/size events, but supplies only a mounted video’s `loadedmetadata`/`resize` and settings refreshed on data turns (`llp/1133.003-video-decode.rfc.md:161–165`, `:216–219`). The consumer cancels its first-frame timeout and marks itself streaming from actual frame delivery (`…/modules/apple/T3DeviceClient.swift:127–142`, `:165–182`). A GPU-only viewer receiving one frame followed by silence has no specified notification. **Resolve:** define low-rate track metadata/first-frame notifications, including resource context and settlement behavior, and cover that idle-stream case.

6. **MATERIAL — §8 D9/§15’s throughput gate cannot yet decide the architecture.** The text asks whether crossing cost exceeds spare main-thread time, but specifies neither a budget nor adequate timing. Plain `perf` reports work counters (`host/web-js/perf.js:93–119`); commit timing starts after the mapper has run (`host/web-js/ts-stream.js:108–124`, `host/web-js/perf.js:151–155`). Stage 0 additionally uses a stub decode (`llp/1133.003-video-decode.rfc.md:522–524`). Arbitrary HTTP chunks also need not produce only 60 turns per second (`:370–378`). **Resolve:** define measurable pass/fail budgets and time delivery, parsing, byte transfer and settlement with realistic fragmentation and bursts for one and three streams.

7. **MATERIAL — §11 materially understates the bundled-page alternative’s inspectability.** Saying the drive sees only the iframe box and remains blind inside it (`llp/1133.003-video-decode.rfc.md:453–457`) conflicts with existing guest DOM outlines, taps and typing (`host/apple/Sources/ExactKit/WebModule.swift:379–461`), plus guest screenshots (`llp/1020-webview.rfc.md:232–245`). Remote device pixels lack semantic structure in either approach. **Resolve:** distinguish those supported guest operations from unverified drag/key behavior and device-screen semantics, then revise the comparison supporting §16 question 5. Leaving CORS, iOS integration and throughput unmeasured is otherwise honest.

8. **MINOR — §16 question 2 presents an incomplete choice.** Writable-only output versus mandatory callback crossings (`llp/1133.003-video-decode.rfc.md:543–545`) omits supporting the standard callback alongside the direct writable fast path. The RFC reports no crossing measurement and rejects handles based on this consumer alone (`:123–125`, `:163–165`). **Resolve:** include the dual-path option and justify callback prohibition separately from the fast path’s benefit.

9. **MINOR — §3 overstates the probe’s connected path.** It says decoded frames were written into a track (`llp/1133.003-video-decode.rfc.md:99–103`), but track playback uses newly constructed canvas frames (`.probe/probe.html:57–63`); decoded frames separately exercise drawing and external-texture import (`:26–30`, `:73–79`). Chrome also ran headless with `--enable-unsafe-webgpu` (`.probe/run.mjs:3`). **Resolve:** describe separate capability probes, label the Chrome configuration, and reserve end-to-end claims for the planned fixture.

The RFC identifies a concrete consumer, exposes the HTTP byte-stream dependency, and separates support queries from throughput evidence. Choosing vocabulary under D5 is justified by the private video/GPU track seam. The `srcObject` track-id adaptation is small and declared. The portable `TextureView` choice also follows the stated wgpu backend limitations; the unresolved issue is the frame handoff contract.

## r2 (2026-10-21)

**Reviewer:** codex gpt-6.1-sol, reasoning effort ultra (confirmed in the run log), a fresh session with the same prompt, read-only on an export of `662487d37b` with `llp/reviews/` left out. The r1 artifact was not in the export; r2's own §17 summarised r1's findings, so this round knew what r1 had raised. The text below is the reviewer's final message, unedited.

VERDICT: NOT READY

1. **MATERIAL — §4 D3 does not reconcile synchronous decoder state with refused operations.** D1 promises WebCodecs’ `state`; D3 counts staged chunks immediately but says failed turns execute none of their operations (`llp/1133.003-video-decode.rfc.md:136`, `:217`, `:224`). After `decoder.close(); throw error`, the facade can report closed while the host decoder continues producing frames. Existing socket staging checkpoints outgoing effects, not decoder objects (`host/web-js/ts-stream.js:108`). **Resolve:** define rollback or invalidation for decoder state, key-frame requirements and queue counts, including what happens to pending `flush()` promises when publication is refused.

2. **MATERIAL — §4 D3 leaves resource answers and asynchronous operations undefined.** Its publication rule covers mapper and mutation calls (`llp/1133.003-video-decode.rfc.md:224`), although the Summary creates and configures a decoder in an answer (`:22`). Mappers cannot await (`js/src/prelude.js:1404`); asynchronous answers publish initial effects with the commit that asks them (`host/web-js/ts-data.js:376`). Native answers awaiting promises without registered host work currently fail (`js/src/prelude.js:1206`). **Resolve:** specify publication and lifetime rules for initial answers, continuations, support queries and flush completion. Explicitly show how `decode(...); await flush(); return snapshot` avoids waiting for the settlement whose commit must start the operation.

3. **MATERIAL — §4 D5’s ownership and cache rules assume one GPU device.** The web path closes its handed-over frame after copying, while all canvases supposedly share one converted texture (`llp/1133.003-video-decode.rfc.md:297`, `:311`). Existing GPU artifacts each own a separate device (`host/web/gpu-modules.js:7`); one texture cannot serve them all. The “per new frame” delivery rule also omits mounting another artifact or recovering a device while the stream’s latest picture remains static (`llp/1133.003-video-decode.rfc.md:284`). **Resolve:** retain a canonical current frame, give consuming writers/artifacts separately owned clones or references, cache conversions per device generation, and deliver the current frame on mount and recovery. State bounded release rules for every copy.

4. **MATERIAL — §4 D5 rejects formats the RFC itself observes.** Its descriptor accepts only NV12 and BGRA8 and refuses other formats (`llp/1133.003-video-decode.rfc.md:290`), but §3 reports ordinary H.264 output as I420 in Chromium and BGRX in Firefox (`:111`). That contradicts the proposed portable GPU path. **Resolve:** restrict that plane-format requirement to native imports, letting the browser copy its opaque `VideoFrame`, or explicitly normalize/support those formats. Separate unsupported HDR policy from the browser’s internal storage format.

5. **MINOR — §4 D5 needs an explicit conversion order compatible with the existing encoder.** Conversion is recorded “at the start of the next flush, before any reader renders” (`llp/1133.003-video-decode.rfc.md:306`). Currently, surface rendering records commands before `flush` submits their encoder (`gpu/src/frame.rs:219`, `:349`, `:385`). Appending conversion during flush would therefore execute it after sampling. **Resolve:** specify conversion before the first surface render, or a conversion command buffer submitted ahead of the recorded draws, with a pinned generation for that batch.

6. **MINOR — §8 D9 understates the possible mapper/commit rate.** HTTP messages have arbitrary byte boundaries (`llp/1133.003-video-decode.rfc.md:420`), so “up to 60 mapper turns and commits a second per stream” is not an upper bound (`:429`). One encoded frame can require several deliveries; joining pending reads does not cap their rate. **Resolve:** remove that ceiling and require the throughput gate to report actual message and commit rates, including deliberately fragmented HTTP delivery and key-frame bursts. This matters to §16 question 8’s budget decision.

7. **MINOR — §§9 and 16 classify deferred Linux implementation as platform absence.** The target expressly acknowledges Linux decoders while proposing “Linux absent” (`llp/1133.003-video-decode.rfc.md:465`, `:635`). The parent defines this situation as **later**; **absent** means the platform lacks the capability (`llp/1133-the-standard-library.rfc.md:431`). **Resolve:** label Linux later while retaining the current visible unsupported result.

The RFC names the major ceilings deliberately: timed playback, selective presentation, HDR, pixel access, audio and encoding. Choosing executor vocabulary is justified by byte input and host presentation requirements; the track-id deviation is modest. The portable `TextureView` choice is sensible, and retaining Apple buffers until GPU completion is the right direction. §§3 and 11 honestly distinguish capability probes from a connected viewer and identify the bundled page’s remaining measurements.
