**SHOULD-FIX** — A scroll handler that moves the port again clears the debt for a scroll that has not fired — `host/web/collection-glue.js:438`

The controller listens in the bubble phase, and that listener is added when the list state is created, after the author’s `scroll` listener (`host/web/glue.js:553`, `host/web-js/rt.js:939`). The author’s listener therefore runs first. On the JS target that listener’s action commits synchronously (`host/web-js/rt.js:256`), and `After` publishes the list (`host/web-js/list.js:846`). On the wasm target `send` applies the dispatch before returning (`host/web/glue.js:903`). Either commit can `place()` or `move()` and set `owesScroll` again. `s.scrolled` then sets `owesScroll = false` unconditionally, so `fireOwedScrolls` sees the count drop and returns. The browser’s event for the new offset is still queued. The wasm settle does not yield another frame once the flag is clear, so that handler can still be pending when `clock settle` returns — the same race as `synthetic-startend`, one scroll later. A capture listener that only retires the flag, leaving `scrollChanged` on the bubble listener, keeps a re-entrant `place()` owed.

The boot landing this commit targets does not hit that path. `startend`’s `moved` only stores `atEnd`, and that commit does not publish a new correction, so the flag stays set until the landing event. That event is what the new wait is for.

No mark sticks on the agent path for the three cases you named. A non-smooth `place()` or `move()` sets `owesScroll` only when the read-back offset actually changes, so a clamp to the same position never arms a wait. `detach` drops the list from `states` before the next count, so a removed list cannot keep the flag. Smooth scrolls set the flag even when the position has not moved yet, but agent controllers never take that path (`correction.smooth && !agent`), and `clock settle` only runs there. The wait cannot spin: each call awaits at most 8 `requestAnimationFrame` plus `setTimeout(0)` turns, and a flag that never clears makes `fireOwedScrolls` return false instead of `continue`. Eight frames is enough margin for an event the browser fires on the next rendering step. The wait follows real frames, so CPU load delays it without skipping the event.

Lists with no `scroll` handler still wait. Any offset change arms the flag, the controller’s own listener clears it, and both settle loops take another round. On the JS target that round starts with the existing 30 ms poll. That is one frame plus one settle round per programmatic move during `clock settle`, including a `scroll-start="end"` list that nobody listens to. It is not on the live present path. Against the 20 s settle budget it is an acceptable cost for seeing the handler’s commit.

The wasm loop’s extra round does not by itself change other conform slots. Timers already due were consumed by the advance earlier in the same round. A second `exact_advance` at the same timestamp does not fire them again, and a list with no `scroll` handler never dispatches. Both targets now wait for the same landing event, which is why `atEnd` matches. The early clear above is the remaining way the two settles can part: the JS round’s 30 ms often covers the follow-up event, and the wasm round does not.

Waiting in settle is the right layer. The handler reads layout the browser has just committed, and it runs as a `scroll` listener, not inside `place()`. Suppressing the slot in the harness would hide a real update. Calling the action synchronously from `place()` would not be the event the page delivers.

The new test checks the mark on an instant correction: owed, moved, cleared within 8 frames, and a later call does not wait. It does not register a `scroll` listener, so it cannot see the re-entrant clear. `move()` and both settle loops are untested.
