Stage 1 is not ready as specified. Its proposed observations can miss property violations and blame successful actions for unrelated refusals.

1. **Evaluating a hidden derive at every commit does not check it at every commit.** D1–D3 promise every committed configuration, including poisoned ones. The Rust harness advances through the whole clock step and observes state afterward; the Lean harness likewise observes only after `step` returns. Meanwhile, `advance` can execute multiple actions before returning. A property can therefore become false at one timer firing and true at the next, leaving no reported violation. [semantics/difftest/src/observe.rs:236](/Users/ccheever/projects/exact2-wt-verify/semantics/difftest/src/observe.rs:236), [semantics/Contract/Observe.lean:159](/Users/ccheever/projects/exact2-wt-verify/semantics/Contract/Observe.lean:159), [semantics/Contract/Runtime.lean:1116](/Users/ccheever/projects/exact2-wt-verify/semantics/Contract/Runtime.lean:1116)

   Poisoning creates another hole: Rust breaks before printing the resulting state, and Lean deliberately omits it. This directly contradicts “poisoned ones included.” [semantics/difftest/src/observe.rs:241](/Users/ccheever/projects/exact2-wt-verify/semantics/difftest/src/observe.rs:241), [semantics/Contract/Observe.lean:89](/Users/ccheever/projects/exact2-wt-verify/semantics/Contract/Observe.lean:89)

   **Resolve:** record property results at individual commit boundaries on both sides, including the state retained by a poisoned commit. Make a false-then-true sequence inside one clock step and a violation followed by render failure acceptance cases. This needs an observation mechanism beyond D2’s “nothing else is new.”

2. **D2 cannot recognise property evaluation failures as described.** The RFC relies on a refusal reason containing `@always:`. Rust attaches the derive name to a result-type failure, but propagates ordinary expression traps without that name. Lean likewise propagates an evaluation error unchanged. [runner/src/runner/settlement.rs:322](/Users/ccheever/projects/exact2-wt-verify/runner/src/runner/settlement.rs:322), [runner/src/runner/settlement.rs:346](/Users/ccheever/projects/exact2-wt-verify/runner/src/runner/settlement.rs:346), [semantics/Contract/Runtime.lean:264](/Users/ccheever/projects/exact2-wt-verify/semantics/Contract/Runtime.lean:264)

   Consider a property containing `range(n)` when an action changes `n` from a valid count to `-1`. That expression refuses without naming the property; settlement failure rolls back the action. The checker can consequently inspect the previous, passing configuration instead of recognising that its instrumentation prevented the app’s transition. This follows from the range refusal and rollback paths. [semantics/Contract/Eval.lean:258](/Users/ccheever/projects/exact2-wt-verify/semantics/Contract/Eval.lean:258), [semantics/Contract/Runtime.lean:799](/Users/ccheever/projects/exact2-wt-verify/semantics/Contract/Runtime.lean:799), [semantics/Contract/Runtime.lean:834](/Users/ccheever/projects/exact2-wt-verify/semantics/Contract/Runtime.lean:834), [runner/src/runner/commit.rs:148](/Users/ccheever/projects/exact2-wt-verify/runner/src/runner/commit.rs:148)

   **Resolve:** give every property evaluation a structured identity and distinguish its failures from app failures, including at boot. Also reconsider evaluation outside the transaction: the claimed need for a third evaluator is false. Rust already exposes `vm::eval`, Lean exposes `eval`, and the observation already includes every root derive. Adapters would be needed, but another expression interpreter would not. 3. **`never refuses` attributes an event’s failure to an action that may have succeeded—or never started.** Rust’s `dispatch_at` preserves an earlier advance error when dispatch succeeds. Lean explicitly returns the due work’s outcome when dispatch succeeds. Furthermore, evaluating curried handler arguments can fail before `runAction` is entered. Looking up the handler and finding `outcome refused` therefore does not establish that its named action refused. [runner/src/runner/advance.rs:43](/Users/ccheever/projects/exact2-wt-verify/runner/src/runner/advance.rs:43), [semantics/Contract/Observe.lean:137](/Users/ccheever/projects/exact2-wt-verify/semantics/Contract/Observe.lean:137), [semantics/Contract/Runtime.lean:1036](/Users/ccheever/projects/exact2-wt-verify/semantics/Contract/Runtime.lean:1036)

   **Resolve:** observe action entry and its own completion separately from due work, handler argument evaluation and input rejection. Use those records for both refusal attribution and exercised-action counts. Merely adding an action name to the existing aggregate outcome would preserve the bug. Alternatively, defer this property form until that attribution exists.

4. **The proposed walk cannot discover controls beyond the preliminary exploration’s observations.** D3 freezes the candidate controls to what the explore run showed. Today’s explore script constructs its event list from boot IDs and never updates that list. This matters in the RFC’s own example app: Type Tour conditionally renders different controls for its lock, home and settings screens.    **Resolve:** enumerate currently available handled controls after every step. Generate the next event from that set and preserve the generated sequence for replay. More walks cannot overcome a permanently excluded control.

Unsupported steps reject the whole script, which `verify` then prints as `SKIP`. Implementing the entire authored-test grammar is additional work, much of it in the device-world territory being deferred.

**Stage 1:** Search before proof is the right direction; D1–D5 as one delivery is not the best first slice. I would first deliver authored `always` properties, accurate commit observation, isolated property errors, runner-only operation and explicit coverage limits. Then add a small adaptive seeded walk, using authored tests as starting paths. Include `never refuses` only with correct action attribution. Defer suggestion mining until a small sample of author-chosen properties demonstrates useful findings. The current plan spends effort generating candidate claims before reliably observing whether they hold. Deferring proofs is correct.

**Open questions:**

1. **Derives reading resources:** Refuse them transitively in stage 1. Apply the same dependency closure to mutations, clock reads and geometry. Otherwise a derive becomes a bypass around D1’s restrictions. Reconsider resource-dependent properties when their intended meaning is explicitly specified. **Confidence: high.**

2. **Typed values from tests:** Yes. Bias generation toward values associated with the same control, and reuse test prefixes to reach that control. Retain boundary and random values so the search can depart from the examples. **Confidence: high.**

3. **Clock refusal attribution:** Yes, before D10, through action entry/completion records as described in issue 3. A name attached to the current aggregate outcome is insufficient. **Confidence: high.**

4. **Suggestion limits:** Start with optional finite-set, integrality and presence suggestions. Defer automatic extrema: every finite walk manufactures a minimum and maximum, often yielding accidental bounds. Measure what authors keep before adding further inference. Relationships between states deserve authored examples before a mining feature. **Confidence: medium.**
