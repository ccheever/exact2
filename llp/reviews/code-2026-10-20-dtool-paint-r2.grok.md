Nothing blocks. A canvas that stays in the tree becomes ready in a frame Chrome gives no animation frames and no resize entries, and the runner accepts a second geometry. Two defects are in the new fallback.

1. **SHOULD-FIX** — The layout fallback is not the observer's content box, so scrolling the frame into view can drop the bitmap. `host/web/canvas2d-glue.js:247` reports `clientWidth`/`clientHeight` minus padding. `clientWidth` is the padding-edge width rounded to the nearest integer (CSSOM View). The observer at `canvas2d-glue.js:236-237` reports `contentBoxSize` `inlineSize`/`blockSize`, which are fractional content-box sizes. `report` dedupes on the exact string (`canvas2d-glue.js:219-221`), so any difference sends a second `exact_canvas_geometry`.

   Concrete case, no padding, device pixel ratio 2, content width 100.4. The fallback reads `clientWidth` 100 and the backing store is `round(200) = 200` (`runner/src/runner/canvas2d.rs:84`). The observer later reports 100.4 and the store is `round(200.8) = 201`. `set_geometry` treats a different pixel size as a new generation: it retires the bitmap, increments the generation, and clears the recorder (`runner/src/runner/canvas2d.rs:572-596`). The same file's test shows the threshold: 100.1 at scale 3 stays one generation (`runner/tests/it/canvas2d.rs:192-195`); a one-pixel store change does not. At ratio 2 this is the fractional parts in `[0.25, 0.75)`, about half of non-integer widths. A design-tool canvas sized by flex or percent is usually one of those; the gallery tiles are `width=150` `height=100` (`apps/canvas-gallery/app.contract:21-23`), so the new browser test never sees it.

   The mount draw is not held for being offscreen (`runner/src/runner/canvas2d.rs:683-687`), and `exact_data_ready` has already run when the one-second timer fires (`host/web/glue.js:1266-1274`). The canvas can paint at 200 device pixels while hidden. When the iframe is scrolled into view the observer corrects it, the generation changes, and the bitmap clears and redraws. A vertical writing mode swaps the axes as well: the observer passes logical `inlineSize`/`blockSize`, and the fallback passes physical `clientWidth`/`clientHeight`. Default `horizontal-tb` does not swap. `getBoundingClientRect().width` minus border and padding is the fractional content box and tracks `contentBoxSize` for horizontal text.

2. **SHOULD-FIX** — A canvas destroyed before its callback stays in `waiting`, and readiness never resolves. `firstGeometry` returns immediately when the element is no longer the view (`host/web/canvas2d-glue.js:245`) and does not remove the id. `report` is the only `waiting.delete` (`canvas2d-glue.js:220`). Destroy removes the DOM node and the view entry and never tells this glue (`host/web/glue.js:825-826`). The host stops watching the id and sends no unwatch (`host/web/src/canvas2d.rs:37-46`).

   Concrete case: the boot batch watches the canvas, then `exact_data_ready`'s batch removes it, while the iframe is still throttled. No observer entry arrives. A second later the timer sees `views.get(id) !== el` and returns. That id stays in `waiting`. `settled()` (`canvas2d-glue.js:322-325`) is what `activateData` waits on before it opens input and sets `dataset.moduleReady` (`host/web/glue.js:1270-1275`). One leaked id blocks the others. The same promise is what a later clock settle and `agentSettled` wait on (`host/web/glue.js:1194`, `glue.js:1232`). A replacement that watches the new element still completes: the new timer calls `report` and clears the id. A restart's `views.clear()` (`glue.js:1348`) is the same leak for an id the new plan does not watch again; the canvas2d instance is the one created for the life of the page (`host/web/navigation.js:498-506`). The gallery's stable tiles do not hit this. Dropping the id when the view is gone, and resolving `settle` when the set is empty, is the missing half of the guard.

3. **NIT** — The starve check runs only after ready, so it does not by itself force the fallback. `activation-noframes.test.mjs:103` throws `not ready offscreen; the piece asked N time(s)` if `dataset.moduleReady` is still unset after 8 seconds, and that flag is set only after `settled()` (`glue.js:1271`). With the frame throttled for the whole load, deleting `firstGeometry` fails there, and the piece request count stays 1 because `navigation.js:502` already loaded it. The probe at `activation-noframes.test.mjs:105-106` then arms a new animation frame and a new `ResizeObserver` for one second and expects `{frames:0, sizes:0}`. A pass means the frame is starved at that later moment. A single lifecycle during load, followed by throttling, would satisfy both assertions with the fallback removed. The iframe does start out of view: parent `http://127.0.0.1:<tool port>`, child `http://localhost:<dev port>` (cross-site), `frame-ancestors` includes that tool origin (`scripts/tamber-server.mjs:1236`, applied from `host/web/dev.mjs:1335`), spacer 6000px, viewport 800×600. Headless throttling follows the layout viewport. I did not run the test. Render throttling skips scheduled lifecycle updates; a script read of `clientWidth` still forces layout, and the usual zeros are `display:none` and inline boxes.
