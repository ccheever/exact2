## 2. The three asks

**Ask 1, a component declared across files: yes.** Real cost:

- `contract/syntax/src/parser.rs:506-515`: a top-level `extend` arm beside `component`, reusing `self.component()` and refusing the once-only sections; `use_decl` (`parser.rs:539-552`) requires at least one name today and must accept none.

- `contract/syntax/src/scope.rs:298-300`: the walk must visit extensions. A part walked alone would resolve a bare call to a root action through the file scope, and if another file declares a `fn` of that name it is mis-renamed or refused `contract-use-missing`. ## 5. Sketch of the language change

```contract
// app.contract
use "./src/transport/transport-root.contract"   // no names: the file's extend blocks join this file's components
component T3Code
  state elapsed = 0
  view
    T3Window(...)

// src/transport/transport-root.contract
use TransportTable, TransportConnect, TransportSocket from "./transport.contract"
extend T3Code
  state transportTable = TransportTable(...)
  resource transportConnect0 = transportConnect(0, transportTable.s0.key, ...) as shape TransportConnect
  task transportSoon when transportTable.soon
    every(250, transportTick)
  action transportTick
    send transportDeliver = command("transport:tick", "", "", 0)
```

Grammar: `declaration = … | extend ; extend = "extend" IDENT block(part-section) ; part-section = state | derive | resource | mutation | action | task | sequence ; use = "use" [ use-name { "," use-name } "from" ] STRING NL ;`

Rules the design document states:

- D1. `extend X` adds members to component `X`, a component declared in a file that uses this file directly; exactly one such file must (`contract-extend-unknown`, `contract-extend-ambiguous`). No transitive parts: a component's parts are listed by its declaring file's `use` lines. Precedent: C# `partial class`, Dart `part of`, Swift `extension`.
- D2. The once-only sections (`props`, `inject`, `provide`, `slot`, `view`, `params`) are the declaring file's; a part holds members only (`syntax-extend-section`).
- D3. One namespace: the component's members across its parts share one set of names (`type-duplicate-name`, both files named).
- D4. Order: the declaring file's members, then each part's in the declaring file's `use` order, each in source order: what one file with those lines would compile to. The plan is byte-identical (LLP 1091).
- D5. A part's top-level names (shapes, `fn`s, keyframes, styles) resolve in its own file through its own `use` lines, as any file's do; member names resolve in the component, and a part sees every member of every part.
- D6. `use "./x.contract"` with no names loads the file for its `extend` blocks (ES `import "./x.js"`, CSS `@import`); a used file's `extend` blocks join whether or not the line names anything.
- D7. Identity, persistence, dev carry and refusals are the declaring component's; every refusal points at the file and line the member is written in.
- D8. The semantics is untouched: `contract lean` reads the merged file. `contract sources` lists parts and the dev loop watches them; `contract fmt --uses` never writes a nameless use.
