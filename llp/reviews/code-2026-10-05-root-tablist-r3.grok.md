NOT READY

1. `host/apple/Sources/ExactKit/IOS/NavigationTitleIOS.swift:364` — **must-fix:** A pop back to the root still applies the tab bar after the route hook, so the hook loses. `followTablistAtRoot` returns at this guard before it sets `tablistRoot` whenever the root is not yet `topViewController` (Exact's own pop: `prepareRoutes` runs before `setViewControllers`) or `transitionCoordinator` is still set (UIKit pop: the back press and `pendingSync` both run inside `didShow`, which is why the settle was moved to the next turn). The hook in that projection therefore runs while the arrival is still unhandled. `NavigationIOS.swift:736` then runs `settleTablist`, sees `tablistRoot !== root`, and writes the bar on the next turn. The same order happens on a tab rebuild: `installTabs` calls `prepareRoutes` before `tabController` exists (`NavigationTabsIOS.swift:103`), the new navigation identity changes the hook signature so the hook runs there, and the later `prepareRoutes` in `sync` (`NavigationIOS.swift:342`) hides the new bar with `arrived` and does not run the hook again. An at-rest change (toggle, tab switch) is fine: that path sets `tablistRoot` and writes before the hook loop.

**Fix:** If the root is selected but not at rest (not top, coordinator set, or `tabController` nil) and this call would have run its route hook, skip that hook and leave `projected` unset. In the `didShow` async block, call `settleTablist` and then `prepareRoutes` on that stack when this settle was the arrival (`tablistRoot` was not the root). The second `followTablistAtRoot` sees the arrival already consumed and does not write again, so the hook runs once, after the bar. On rebuild the later in-sync `prepareRoutes` already does that, as long as the early call did not mark the hook done. Add a route hook on Home that calls `setTabBarHidden(false)` and assert the bar is still shown after both the UIKit pop and the reselect pop, once `transitionCoordinator == nil`.

Round 2's other items are in this diff: `tablistHidBar` is updated on both `setTabBarHidden` paths and set on the root only when that call hides a visible bar; a shown pushed route brings an Exact-owned hide back before it is top; `retireTabs` and the app-container handoff clear both fields; the fixture, the pop and tab coverage, and the LLP wording match that behavior.
