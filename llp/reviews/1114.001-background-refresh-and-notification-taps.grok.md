I'll review LLP 1114.001 for direction and architecture only. First I'm reading the parent summary, the RFC, and the repository rules it depends on.The RFC is loaded. Next I’ll check its load-bearing claims against the rules and the code it cites.**Verdict:** RIGHT WITH CHANGES

Stage 1 is the right capability and the right shape. Stage 2 is a real gap for this clone — Bluesky's push service cannot address `dev.tuft.blueskyclone` — but the proposed Contract trigger and the wake's runtime model should change before they are admitted. As written, the new grammar word means something the web API does not, and a cold wake will not fit the operating-system budget of the app it is for.

## Concerns

**1. MAJOR — `periodicsync` is a foreground timer with an iOS wake attached, and the web API it cites is neither of those.**

The [Periodic Background Sync](https://wicg.github.io/periodic-background-sync/) spec fires a `periodicsync` event in a service worker, on the browser's schedule, with `minInterval` only a floor. The spec's default cap is twelve hours. [web.dev](https://web.dev/articles/web-apps/periodic-background-sync) describes it as downloading while the page is not in use. It is not a page timer, and it does not run "whether or not a page is open." Section 4 of the RFC states the worker model correctly; D2 then defines the opposite and justifies it with that sentence.

While the process is alive, exact2 already has this behavior: a root `every` (the grammar in `docs/contract-grammar.md`, gates in LLP 1092). iOS suspends that timer with the process. `UIBackgroundModes: fetch` does not keep it running; it only allows `BGAppRefreshTask`. So the new trigger's only new behavior is the opportunistic wake on iOS and tvOS. The clone's own §7 already polls in the foreground with `task poll when signedIn` and `every(60000, …)`.

A grammar word is permanent here (`rules/RULES.md`: delete, don't deprecate). Resolve it by keeping `mount` and `when`, and marking a declared task as eligible for a system wake. On the web, Linux, Windows, macOS, and the terminal that mark means nothing, which the RFC already wants to say out loud. Leave the name `periodicsync` for a worker-backed implementation if one ever exists.

**2. MAJOR — A cold wake boots the whole session and ends only when the whole runner is quiet.**

D3 boots the session with no scene, which runs the plan's mount tasks, then dispatches the wake action, then waits until every request, `then`, queue entry, and storage operation in the runner has finished. Open streams are excluded. `BGAppRefreshTask` is about thirty seconds (the RFC's own table), and if the expiration handler runs first the system offers that app less time later.

The clone this is for loads a session, a timeline, and notifications at boot. That work sits on the same budget as `checkInbox`. The wake will often expire, and iOS will then schedule it less. D3's choice to ignore LLP 1113 and treat all runner work as the wake's is what creates that coupling.

The same section forbids a `when` gate because "a cold wake boots with initial state, so a gate on state would read its initial value." That is not how gates work. LLP 1092 D8 evaluates a gate after settlement on each commit and arms the timer on the commit that makes it true. It is not sampled once at boot. There is a real timing gap beside that: an `every(900000)` armed at boot is due fifteen minutes later, which is useless inside a thirty-second wake. The wake has to run the action immediately. That is a reason for an immediate dispatch after the data module is ready, not a reason to delete `when`.

Resolve it by restoring state, then running that one action now if its gate holds. The wake is done when that action's requests and storage have settled. UI mount tasks should not run, and their traffic should not hold the task open.

**3. MAJOR — `fetch` is background-mode reach, and the RFC gives it no grant.**

D4 says a wake touches no device, so there is no new grant. Adding the task writes `UIBackgroundModes: fetch` and `BGTaskSchedulerPermittedIdentifiers`. LLP 1069.008 D4 already ruled that a background mode is reach an update cannot add, and that `device.background-audio` and its siblings become `device.*` rows. "Not before" was sequencing: do that conversion when the first real mode lands, which was expected to be audio. This RFC is a real mode arriving first, and it does not mention that ruling. It cites 1069.008 only for `aps-environment`.

Today's `Device` row (`runner/src/device.rs`) has usage strings, entitlements, and a web permission name, and no background-mode field. That is the column D4 said to add. It is not evidence that a grant cannot fit. The web Permissions name is `periodic-background-sync`. `notifications` already shows that a row may carry an empty purpose list.

Resolve it with a `device.*` row that contributes `fetch` and classifies through the existing `grantCeiling` (1069.008 D5). Keep the task names in the compatibility id as well: `BGTaskSchedulerPermittedIdentifiers` is per task and is still host metadata (LLP 1030 D5). The task line alone should not be what turns the mode on.

**4. MINOR — Stage 1's compatibility claim is false.**

D1 says a fifth `showNotification` argument is already a binary change because the plan header's compiler identity "is what the classifier treats as binary." `compiler_identity()` in `contract/lower/src/lib.rs` is the `contract-lower` version string, stored in the header. The runner checks `kernel_schema_digest` only (`runner/src/runner.rs`). `bake/src/compat.rs` hashes `formatDigest` and `kernelSchema`, not compiler identity. A new argument does not change `format.json`, so it does not change `formatDigest` either. An over-the-air plan would reach an old runner, and `notify.rs` refuses anything but four arguments, so the notification would not post. Put an explicit compatibility input on the new command shape.

## What it gets right

Stage 1 belongs on the path LLP 1038 D8 and LLP 1069 §5 #9 already named: one `navigate` while running, the launch location when the tap starts the app. The app's existing handler routes it.

Keeping `navigate` off the web `Notification` constructor is the right deviation. The [Notifications Standard](https://notifications.spec.whatwg.org/) treats a navigation URL as "navigate a top-level browsing context and fire no `click`." Exact2's web router is same-document history (LLP 1038 D7). A click that calls the root's `navigate` keeps the open session.

The clone really cannot receive Bluesky pushes: APNs topics are bundle ids, and `push.bsky.app` holds Bluesky's key. Polling `listNotifications` and posting a local notification is the client-only substitute. Badges and push stay refused, matching `rules/DEFERRED.md`. Identifiers have to be static because `Info.plist` is build-time, so deriving them from the plan is the right call. This is not a job scheduler. The per-host table is honest: no service worker, the JS plan needs the DOM, and tvOS can refresh without a notification UI. Stage 1 needs no new driver operation. Q3 is right to ask before adding `EXACT_WAKE`.

## Questions for Charlie

Q1, Q3, Q4, and Q5 can stand. Q3's yes is what makes the cold path something an agent can run, and `--wake` has to use that same headless boot.

Q2 should not be a yes to D2 as written. Admit a system wake only in the shape above: one gated action, that action's own work ends the wake, and a `device.*` grant owns `fetch`. It will not resemble push. It is opportunistic, off in Low Power Mode, and absent after a force-quit. The parent's ranking (stage 2 near the end) already matches that.

Two questions the RFC does not ask. First: 1069.008 D4 sequenced background-mode grants behind audio. `fetch` is here first. Decide now whether it is a `device.*` row. Second: delivery's owed `BGAppRefreshTask` (LLP 1030.003) can share registration code and should stay host work, not a Contract task. It also shares the app's one refresh budget with the inbox wake. That sharing is not a reason to take stage 2, and it is not free.
