1. **MATERIAL — D11, line 471: Android cannot produce the promised HID list before permission.** D3 requires `attachedDevices` to return collection metadata and apply usage filters without prompting; D11 requires validating every collection before offering an interface. Android’s [`UsbInterface`](https://developer.android.com/reference/android/hardware/usb/UsbInterface) exposes no report descriptor. Fetching it requires a separate control request ([HID 1.11 §7.1](https://www.usb.org/sites/default/files/documents/hid1_11.pdf)), and Android requires [permission before communicating](https://developer.android.com/develop/connectivity/usb/host#permission). These requirements cannot coexist for an ungranted device.

   **Decision needed:** define an Android candidate list with explicitly unavailable metadata, followed by permission and descriptor validation before `force=true`; or narrow Android HID support.

2. **MATERIAL — D19 item 2, line 769: the reader limit does not enforce one reader per connection.** It rejects a second reader of the same *argument group*. Existing grouping retains every non-null argument except `after` (`runner/src/runner/modules/samples.rs:88–93`). Consequently, `serialInput(connection=c, interval=100)` and `serialInput(connection=c, interval=200)` occupy different groups and both pass, contradicting D8’s connection-wide exclusion at line 357. Independent cursors then govern one bounded byte backlog.

   **Decision needed:** key exclusivity by connection, independently of polling options. If generic, let the declaration name the exclusion key.

3. **MATERIAL — D7/D8, lines 319 and 365: serial defaults cannot sustain an ordinary continuous log.** The default buffer holds 255 bytes, polling occurs every 100 ms, and bytes remain retained until their delivered cursor returns. This permits at most 2,550 bytes/s of sustained consumption. A 115,200-baud 8N1 connection supplies 11,520 bytes/s, so finite OS buffers eventually overflow with the default `flowControl="none"`, even with prompt, successful commits. [Web Serial’s buffer default](https://serial.spec.whatwg.org/#dom-serialport-readable) accompanies continuous pulls; adding mandatory polling changes its practical meaning. Bench’s explicit 64 KiB buffer avoids this, but ordinary callers do not.

   **Decision needed:** choose defaults compatible with polling, or couple buffer capacity to baud rate and polling interval.

4. **MATERIAL — §11, line 831: the substitute cannot express Bench’s promised DFU drive.** Control responses are fixed values indexed by setup tuple. DFU repeatedly issues the same `GET_STATUS` setup while its response changes during programming and manifestation. Drive 8 at line 1002 supplies permanent `dfuDNLOAD-IDLE`, yet expects completion after the final zero-length `DNLOAD`. A conforming updater cannot traverse those transitions using that fixture. See [DFU 1.1 §6.1.2 and §7](https://www.usb.org/sites/default/files/DFU_1.1.pdf).

   **Decision needed:** provide sequenced control replies or a stateful device substitute, and use it for Bench’s acceptance drive.

5. **MINOR — D13, line 552: Android’s named cancellation mechanism excludes control transfers.** [`UsbRequest`](https://developer.android.com/reference/android/hardware/usb/UsbRequest) supports bulk and interrupt endpoints, explicitly excluding endpoint zero. `controlTransfer` is synchronous, so `UsbRequest.cancel` cannot abort it.

   **Decision needed:** qualify cancellation as best effort and document this exception; cancelling one request must not close the shared connection.

6. **MINOR — D11, line 485, and §7, line 636: gamepad tier 3 does not provide the claimed raw-report fallback.** `llp/1133.022-bluetooth-gamepad.rfc.md:455–460` exposes `GCController` on Apple and an Android `InputDevice` id, with no hatch on Linux, Windows or the web. These do not supply a raw HID report reader.

   **Decision needed:** mark raw pad reports as intentionally unavailable where no such seam exists, or identify the actual supported route.

7. **MINOR — §1, line 127, and §17 question 1, line 1121: the Linux dispatch ruling is stale.** `llp/1133.022-bluetooth-gamepad.rfc.md:1437–1444` already records Charlie’s acceptance and assigns that RFC the Rust builder and both desktop dispatch implementations.

1. **MATERIAL — IN-DELTA — D11, lines 505–509: Android’s descriptor-validation order still cannot work when a kernel driver owns the interface.**

   The HID report-descriptor request has interface recipient (`bmRequestType=0x81`; [HID 1.11 §7.1.1](https://www.usb.org/sites/default/files/documents/hid1_11.pdf#page=59)). Android’s [libusbhost](https://android.googlesource.com/platform/system/core/+/master/libusbhost/usbhost.c#643) sends it through `USBDEVFS_CONTROL`. The [Android kernel’s `check_ctrlrecip` and `checkintf`](https://android.googlesource.com/kernel/common/+/15d90b242290f228166ea79ee1cc2db6b31a2143/drivers/usb/core/devio.c#768) require an interface claim, implicitly attempting one when necessary. That claim fails while the kernel HID driver owns the interface. Consequently, the descriptor cannot be validated before the forced claim/detachment that the revised rule postpones. Even a driverless interface is implicitly claimed during retrieval.

   **Decision needed:** narrow Android HID support to interfaces whose descriptors can be obtained without detaching a system driver, or choose an explicit policy for identifying permitted devices before detachment. Qualify the promise that validation happens without claiming.

2. **MATERIAL — IN-DELTA — D8, lines 364 and 374–378: a byte-offset cursor cannot acknowledge an error-only answer.**

   D9:435 places errors at byte offsets, and §11:886 explicitly supplies a `BreakError` event without bytes. Suppose the delivered cursor is `n`. An error-only answer leaves the byte offset at `n`, whether its commit succeeds or is discarded. The next request therefore carries identical `after=n` in both cases. The implementation cannot both replay discarded errors and consume delivered ones. The inherited request protocol sends the cursor through `after`, with no separate delivery acknowledgement (`runner/src/runner/modules/bound.rs:198–202`).

   **Decision needed:** use an acknowledgement cursor that advances over errors independently of byte count, such as an event sequence or composite cursor. Preserve byte offsets as error metadata.

3. **MATERIAL — IN-DELTA — D8, lines 374–383; D19 item 2, line 822: a replacement reader cannot receive every byte since `open`.**

   Reader A can deliver bytes 0–99, acknowledge them on its next poll, and cause their release under lines 382–383. A can then release while the connection remains open: D5:273–276 ties connection lifetime to its lease. Reader B’s first request nevertheless passes no cursor and demands every byte since `open`, including the freed bytes. B is a distinct reader under the inherited resource/call-site identity (`llp/1133.022-bluetooth-gamepad.rfc.md:953–959`).

   **Decision needed:** keep the consumption position with the connection and transfer it to replacement readers, or change the reader-lifetime contract. Only the connection’s first-ever reader can necessarily start at `open`.

4. **MATERIAL — PRE-EXISTING — D13, lines 573–583; D3, lines 224–237: Android cannot evaluate USB serial-number filters before permission.**

   USB advertises WebUSB’s `serialNumber` filter, including during attached enumeration and chooser construction. Android’s [`UsbDevice.getSerialNumber()`](https://developer.android.com/reference/android/hardware/usb/UsbDevice#getSerialNumber()) throws `SecurityException` without device permission for apps targeting SDK 29 or newer. An ungranted device therefore cannot be matched by its actual serial number before selection. Prompting during enumeration conflicts with the permission flow; silently excluding it changes the advertised filtering semantics.

   **Decision needed:** define unavailable serial-number metadata and explicit candidate/filter behavior before permission, or narrow Android’s supported filters, as r2 now does for HID usage filters.

**MATERIAL — PRE-EXISTING — D13:616–620, 637–645; D18:834–850: Android’s Kotlin-only implementation cannot provide the declared WebUSB operations and transfer results.**

The chosen public Android APIs lose information required to distinguish successful transfers from stalls. For asynchronous transfers, [AOSP’s completion handling](https://android.googlesource.com/platform/system/core/+/master/libusbhost/usbhost.c#770) copies `actual_length` but discards the URB status. Consequently, a successful zero-byte transfer and a stalled transfer with zero bytes are indistinguishable through `UsbRequest`. Synchronous control transfers likewise [return the ioctl result without preserving `errno`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/jni/android_hardware_UsbDeviceConnection.cpp#183). The implementation cannot reliably supply D13’s promised `ok`/`stall` semantics.

Additionally, D13 offers `reset`, but Android’s [`resetDevice()` is hidden and marked `@SystemApi`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/hardware/usb/UsbDeviceConnection.java#326). It is unavailable through the supported public Kotlin API. Chromium avoids these limitations by obtaining the Android file descriptor and [performing I/O through native usbfs](https://raw.githubusercontent.com/chromium/chromium/main/services/device/usb/usb_device_handle_android.cc).

**Decision needed:** admit a native Android USB implementation path that preserves transfer status and supports reset, or explicitly narrow Android’s operations and result semantics. This changes the selected implementation boundary or advertised contract; it cannot be resolved by filling in Kotlin implementation details.

1. **MATERIAL — IN-DELTA — D14:690–696; §17 question 10:1334–1339: failed transfers can be reported as successful.**

2. **MATERIAL — IN-DELTA — D11:532–542, 568–573: the new input exclusion can still detach working keyboards and mice.**

   [D11’s safety argument](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/dev37/cap4/llp/1133.037-usb-hid-serial.rfc.md:532) assumes that system input carries the USB device’s vendor/product pair. Logitech Unifying/DJ receivers provide a counterexample: their driver creates child HID devices using each paired peripheral’s product ID, exposes the receiver through HIDRAW/HIDDEV without a corresponding input device, and destroys the paired input devices when any receiver interface is unbound. See [`hid-logitech-dj.c`, lines 774–779, 1844–1846 and 1920–1934](https://github.com/torvalds/linux/blob/master/drivers/hid/hid-logitech-dj.c#L774).

See [EventHub’s identity read](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/main/services/inputflinger/reader/EventHub.cpp#2300) and [GKI configuration](https://android.googlesource.com/kernel/common/+/refs/heads/android-mainline/arch/arm64/configs/gki_defconfig). The [WebHID blocklist](https://raw.githubusercontent.com/whatwg/hid/main/blocklist.txt) does not exclude Logitech receivers.

   Thus the receiver’s vendor-defined interface can pass the proposed checks, and `force=true` can remove live input. D11’s crash behavior then leaves it unavailable until replug.

   **Decision needed:** establish the USB device’s relationship to system input before detaching, or restrict Android force-claim support to known-safe devices. VID/PID inequality cannot establish the stated guarantee.

3. **MATERIAL — PRE-EXISTING — D13:635; D18:883–884: Kotlin’s public USB API cannot implement the promised endpoint-specific `clearHalt`.**

Linux explicitly warns against issuing that control request directly; its `USBDEVFS_CLEAR_HALT` performs the combined operation.    **Decision needed:** admit the native clear-halt ioctl path, or explicitly narrow Android’s `clearHalt` support. This is another limitation missing from question 10’s assessment.
