## 1. Fundamental issues

**1. A property is not checked at every commit, and `never refuses` blames the wrong outcome.**

D3 says `contract verify` checks every property at every commit, and that a `never refuses` violation is an `outcome refused` on a step whose handler names the action. The differential trace is one block per script event. `Contract.Observe.run` appends `lines` once per event (`semantics/Contract/Observe.lean:152-166`). A tap is `dispatchAt`, which runs the work already due and then `dispatch`, and returns one outcome (`Observe.lean:131-142`): the event's, when the event fails, otherwise the due work's. A clock step is one `advance` (`Observe.lean:147`). The runner prints the same shape (`semantics/difftest/src/observe.rs:220-258`).

A hidden derive is settled on every commit (`semantics/Contract/Runtime.lean:261-270`) and then overwritten by the next commit in that event. The observation prints it only in the final configuration (`Observe.lean:97-98`, `observe.rs:147-151`). A property false on one timer fire inside `clock +60000` and true after a later fire in the same advance is printed true. Update Lab's `sample` task is such a fire (`semantics/Apps/UpdateLab.lean:23`). The explore script ends on those advances (`semantics/difftest/src/lib.rs:477-478`).

`never refuses` uses that same line. The text is `outcome refused` plus a reason (`Observe.lean:80-82`). It names no action. `observe::site` returns the plan node of a `testId` (`observe.rs:266-284`), not the handler's action. Due work that refuses, followed by an action that commits, is reported as the tapped action (`Observe.lean:140-142`).

Shrink does not apply to this failure. `script::shrink` keeps a candidate only while the verdict is `Diverge` (`lib.rs:512-531`). `compare` returns `Agree` when the texts match (`lib.rs:303`). A property both sides print as `false` is an agreement, so the shrink D3 names returns the original script.

Resolve it by recording one configuration per commit on both sides, with the action that ran and that commit's outcome. Check `always` and `never refuses` on that trace, and shrink against that verdict.

**2. The hidden derive is the wrong place to evaluate a property. The reason for rejecting the harness is false.**

D2 puts the expression into settlement, so a failure refuses the commit the app would have committed (`Runtime.lean:270`; the runner returns that trap at `runner/src/runner/settlement.rs:347`). The run after that refusal is a different run. Stopping with a "property error" drops every later commit of the script that was going to be checked.

D2 rejects evaluating over the observation because that "cannot read a derive the app does not already observe." Both observations print every derive (`observe.rs:147-151`, `Observe.lean:97-98`) and every root slot (`observe.rs:130-138`, `Observe.lean:94`). Calling the runner VM and Lean `eval` on the property in the post-commit environment uses the two evaluators that exist. It does not add a derive, and it does not refuse the app's commit.

The previous commit's slot lines are the pre-state of a one-commit step, on both sides. That is what `after` and `old()` need. D7 defers `after` because "the runner's side has no pre-state." The transcript already has it whenever the step is one commit. Steps that contain several commits are issue 1.

Resolve it by dropping the hidden derive and evaluating the expression against the per-commit snapshots.

**3. The walk never sees a control that was absent at boot.**

`explore` boots with no events and collects `testId`s from that single observation (`lib.rs:455-478`). D3 runs the walk over "the controls the explore observation showed," which is this set. A tap whose target is absent reaches nothing (`Observe.lean:127-129`). Type Tour boots on `lock` (`semantics/Apps/TypeTour.lean:5`) and shows that screen's subtree only while `screen` is `"lock"` (`TypeTour.lean:36`). Controls on `home` and `settings` are not walk targets. The explore script only taps the boot ids (`lib.rs:474-476`).

The view line is `view "<id>" <text>` (`observe.rs:177-179`). It does not carry an input's kind, so "a value of the input's kind" is not data that observation has.

Resolve it by drawing each step from the controls present in that configuration, and by taking typed strings from the app's own `type` steps.

**4. Persisted state is allowed, and the search that would make that honest is not in stage 1.**

D1 lets a property read a persisted state. Any stored value of the state's type is a legal boot (`Runtime.lean:900-907`). `Reachable` quantifies over that store (`semantics/README.md:796-803`). A property that holds from the empty store can be false for a store the semantics already admits. D11 says the answer taken now is that the search also runs the stored cases. `verify` never builds them (`semantics/difftest/src/verify.rs:52-88`). `stored_variants` runs on the corpus path (`lib.rs:405`, `lib.rs:413-428`). Stage 1's plan does not add it. A green line read as "in the semantics' world" would describe a search that missed boots the semantics counts.

Resolve it by keeping persisted state out of stage 1, or by running stored variants on the app and saying that a green property covers only the stores that were drawn.

**5. A derive read walks around the bans in the same decision.**

D1 allows the property to read derives, and forbids the clock "directly or through a fn," plus resources and `failed`. A derive is another expression. Its body can call `performanceNow` (Video Player's `back` and `forward` do, `semantics/Apps/VideoPlayer.lean:38-39`) or `failed`. `failed` of a settled resource is `false` (`Eval.lean:385-388`). Settlement treats the clock as an input (`runner/src/runner/settlement.rs:217-218`), and `advance` moves `now_ms` even when it returns no timer receipt (`runner/src/runner/advance.rs:717-721`). The next settlement recomputes a clock-reading derive. The checker, looking at the property text and the `fn`s it calls, does not see the derive body. Open question 1 leaves the resource case admitted.

Resolve it by allowing a property to depend, transitively, only on root states that are not mutations and on derives and `fn`s whose bodies stay in that set. A clock read, a geometry read, a resource, or `pending` / `failed` / `failure` anywhere in that cone is refused at the property's line.

## 2. Is stage 1 the right first slice?

No. D1–D5 spend the work on a grammar, a compiler entry, and a walk over the boot screen, and the check still does not mean "every commit."

The slice that buys more per hour is the per-commit trace from issue 1, then `always` and `after` evaluated on those snapshots for both sides, with D5's suggestions printed from the same snapshots. No new syntax and no derive in the program. `after` is the shape of the proved properties that are not single-state invariants: `increment_adds_one` (`UpdateLab.lean:54-56`), `reset_spec` (`PhotoEditor.lean:39-42`), `toggle_flips` (`VideoPlayer.lean:41`). `ready_stays` (`PhotoEditor.lean:25-27`) and `advance_keeps_user_state` (`UpdateLab.lean:14-16`) need a fact about every event, and `done_focuses` (`VideoPlayer.lean:65-72`) is a command the observation already prints (`observe.rs:169-171`). `after` covers more of that set than `always` does.

Proof generation is the wrong first spend. D6's recipe is `Reachable.slotIn` plus `wp`. Several of the twelve theorems are not that recipe, and there is no prototype.

The demand sample is smaller than the RFC says. Ten apps contain a `*.test.contract`: metronome, design-tool, excord, variable-type, reflow, agents, caltrain, messages, shelf, harmony (228 `test "` lines). Type Tour, Update Lab, Photo Editor, and Video Player are not among them. The plan's `always` blocks on `apps/typetour/app.test.contract` and `apps/update-lab/app.test.contract` create those files.
