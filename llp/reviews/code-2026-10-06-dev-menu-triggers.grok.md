DO NOT LAND

1. **BLOCKING — A four-finger hold opens the sheet and the tap closes it, and the release can arm reload.** `shouldRecognizeSimultaneouslyWith` returns true for every pair (`DevMenuIOS.swift:31-33`), and UIKit treats that as forcing simultaneous recognition, so the press reaching `.began` does not fail the menu's own tap or double tap. The tap waits only on the double tap (`:74`), not on the press. Hold 0.6s: `menuPress` runs `toggle` and presents (`:19-22`, `:81`). Lift: that touch is still a tap. After the double-tap interval `menuTap` runs `toggle` again (`:15-17`) and dismisses the sheet. A second four-finger tap inside that interval is the double tap and calls `reload` (`:24-26`). Fix: return true only when `other.delegate !== self`, and `menu.require(toFail: press)` plus `reload.require(toFail: press)`.

2. **BLOCKING — The hold leaves the row's press live, so finger-up activates the app.** The press sets `cancelsTouchesInView = false` (`DevMenuIOS.swift:84`). The default sends `touchesCancelled` before the action; this recognizer does not. `delaysTouchesEnded` is false (`:83`), and the tap cannot cancel yet because it is still waiting on the double tap (`:74`). A stationary four-finger hold never starts the scroll pan, so nothing else cancels the touch. On lift, `NodeView.touchesEnded` sees `pressed` and calls `presenter?.press` (`PointerIOS.swift:187-193`). A hold on blank scroll content calls `endEditing` (`ScrollViewIOS.swift:116-123`). The tap path exists so a recognized dev gesture resets that press (`DevMenuIOS.swift:52-55`). The new test locks the wrong flag in (`DevMenuIOSTests.swift:40`). Fix: `cancelsTouchesInView = true` on the press. It cancels only once four touches have been recognized.

3. **MATERIAL — An in-flight dismiss still drops the menu, and the new retry never runs.** The walk stops before a dismissing child (`DevMenuIOS.swift:103`), then `show` retries only when the controller it landed on is itself `isBeingPresented` or `isBeingDismissed` (`:116-119`). While a route sheet is dismissing, that parent is neither, and `presentedViewController` is still the child, so `present` is refused (`:137`) and nothing schedules the retry. `saveTrace`, `share`, and `openProject` use the same presenter and have no retry (`:143`, `:164`, `:179`). The host's own confirmation path refuses this window (`MenusIOS.swift:549-550`). The retry also has no cap: a presenter that stays mid-transition journals `"dev menu: waiting for a presentation to finish"` and reschedules every 0.4s. Fix: treat `presentedViewController != nil` after the walk as in flight, share that wait in all four presenters, and stop after a few attempts.

4. **MATERIAL — The tests pass the broken behavior.** `settle` never asserts, so a `show` that does not present still passes (`DevMenuIOSTests.swift:25-27`, `:50-52`). `menuTap` is invoked directly on whichever tap was installed first (`:48`), so a swapped action, a missed `.began` guard, a missed press or double-tap journal line, and `minimumPressDuration` are all invisible. Simultaneous recognition is checked against a fresh pan (`:45`), not against the menu's own tap, so finding 1 stays green. `testTheSheetOpensOverWhateverIsPresented` only reads `presenter` (`:66-71`); `show`, Save Trace, the share sheet, and Open Project are never presented over a modal or a dismissing controller. Fix: drive `menuPress` at `.began` and again at `.ended` and assert one toggle; assert the tap does not fire after the press; assert `cancelsTouchesInView` on the press; present over a real modal and over a dismissing one, including the 0.4s retry; assert the popover `sourceView` is that presenter.

The idle-tick skip is untouched: this diff is `DevMenuIOS.swift` and `DevMenuIOSTests.swift` only, so those reviews' holes stay as they were. The nil-event guard still covers the new press (`DevMenuIOS.swift:34-38`, `:83-88`); agent taps still do not synthesize `UITouch`s, and a one-finger injected touch cannot meet `numberOfTouchesRequired == 4`. On tvOS `numberOfTouchesRequired` is unavailable and `allowedPressTypes` is empty, so the new press cannot see the remote, same as the existing taps.

A phone can still eat the four-finger tap with no journal line. The tap's movement slop is internal (the public `allowableMovement` is not on `UITapGestureRecognizer` in this SDK), so a quick tap whose fingers drift fails on its own; the 0.6s press is the only wider net, and finding 1 cancels that. A finger on the keyboard window or the home-indicator system gesture never reaches this window, so the recognizer never sees four touches. A system gesture gate that requires this recognizer to fail is not overridden by simultaneous recognition.
