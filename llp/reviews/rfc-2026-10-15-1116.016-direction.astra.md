## 1. The ideal end state

**I would aim for a small, coherent TypeScript expression profile, compiled into Contract’s existing plan, with immutable values, checked absence, deterministic execution, and bounded work.** Familiar syntax should preserve familiar behavior—including evaluation order and short-circuiting. Contract should comfortably express calculations over a screen’s existing state: labels, validation, lookups, filtering, and bounded ordering. Effects, persistence, substantial domain algorithms, and expensive shared computations belong in the data module. Over the next year, I would prioritize completing that coherent core over accumulating individually justified methods. “Pure subset with declared deviations” is a reasonable description, provided the deviations remain exceptional and some existing ones are treated as debt to remove.

The alternatives have real advantages, but none is better overall. A **strict TypeScript subset** offers the clearest compatibility promise and deserves more consideration than Claude gives it: refusing mutation or aggregate equality does not require implementing them. However, preserving every JavaScript string value or refusing every operation that could produce an unrepresentable one would impose costs disproportionate to ordinary UI work. A **distinct small language** could make immutability, structural equality, and options beautifully consistent, but asks agents and humans to learn another vocabulary for familiar calculations. **Binding-and-branching-only Contract** keeps the evaluator small while exporting complexity into source declarations, arguments, replies, and duplicated derived data. The existing [map/join consumer](/Users/ccheever/projects/exact2/llp/1017.003-map-filter-join.spec.md:23) is compelling evidence against that extreme: 5,000 sparkline rows otherwise carried both numeric series and formatted strings. **Embedding executable TypeScript** buys broad compatibility but moves expression evaluation outside the current proof, dependency, and work-budget mechanisms. Recovering those guarantees would require restricting and analyzing it again. I prefer borrowing TypeScript’s surface while retaining Contract’s execution model.

## 2. Answers to the three questions

**Q1: Accept the direction, but do not freeze r2’s deviation table as the ideal end state. Confidence: 90%.**

D1 should establish a semantic discipline, not make every existing difference permanent. Its table currently combines three different things:

- **Restrictions:** boolean conditions, immutable values, unsupported operations. These can be ordinary subset rules without changing any accepted expression’s meaning.
- **Deliberate representation and execution choices:** well-formed strings, bounded work, and one deterministic choice where ECMAScript allows implementations freedom.
- **Existing differences that do not protect an essential guarantee:** NaN-dropping `min`/`max`, and the proposed full-pass `some`/`every`.

The third category should shrink. For example, I also checked the current web implementation of `toFixed`: infinity produces `""`, whereas JavaScript produces `"Infinity"`. That difference is documented in [format.js](/Users/ccheever/projects/exact2/host/web-js/format.js:82), but absent from D1’s table. The directional lesson is that a compatibility promise needs an executable audit of the existing surface; a short table alone cannot establish it.

I would also reconsider two ostensibly necessary permanent deviations:

- **Structural equality is useful, but immutability does not make identity meaningless.** Immutable objects can still be distinct or aliased. My long-term preference is familiar equality on supported scalar types, with aggregate equality refused or exposed as an explicitly named value operation.
- **CSS property names do not require hyphenated expression identifiers.** Keeping `font-size` in attributes does not logically require `a-b` to mean a variable inside an expression. Keeping that rule may be a pragmatic choice, but it is not compelled by LLP 1115.

Admission should consider demonstrated Contract use, implementation and proof cost, and whether an addition completes a coherent family. Requiring guesses from both model families is useful evidence, not an absolute rule: one strong real consumer can justify an operation, while repeated guesses can still request something inappropriate.

**What would change my mind:** representative whole-app work showing that the supported profile cannot be explained compactly, and that its repeated refusals and exceptions cost more than a deliberately distinct expression language. Conversely, evidence that removing particular deviations is straightforward would move me closer to the strict-subset alternative.

**Q2: Approve a split stage, not D2–D6 wholesale as written. Confidence: 85%.**

My order would be:

1. **D2, D5, and D6 now:** fix method capture, improve diagnostics, and teach the actual boundary. Keep a compact supported-operation/signature index; availability remains something builders must know.
2. **D3 with real short-circuit semantics**, or defer it until that implementation is justified.
3. **D4 as a separate decision after a concrete view/data comparison**, with no automatic approval implied by “lands last.”

I disagree with shipping `some` and `every` as full-pass `filter` rewrites. ECMAScript’s `some` stops at the first successful predicate. Contract’s proposed rewrite can instead evaluate an expensive tail and refuse. That is observable behavior, especially when a binding trap can poison the runner. A documented exception makes the behavior explicit; it does not make it desirable. One bounded search primitive could support `some`, `every`, and subsequently `find`/`findIndex`, amortizing the implementation and proof work. [ECMAScript `some`](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-array.prototype.some), [Contract’s bound and trap behavior](/Users/ccheever/projects/exact2/llp/1017.003-map-filter-join.spec.md:86).

**I think bounded presentation sorting belongs in the eventual language.** Sorting is not intrinsically a data-module operation. Ordering already-loaded rows according to local UI state belongs naturally beside filtering them. Returning a canonical order from a database, maintaining a large ranking, or applying reusable business rules belongs naturally in the data module. The present [guide’s categorical placement of sorting](/Users/ccheever/projects/exact2/docs/contract-for-agents.md:46) should eventually become that more useful distinction.

But the current evidence does not establish urgency:

- I reproduced **8/80 post-D2 screens using `.sort`**, versus **one free-function sort before**.
- The **469 build logs show no sort refusal**.
- The [guess harness](/Users/ccheever/bakeoff/guess.py:31) asks for only `app.contract`, with `app.ts` written separately. It can declare a sorted source, but it cannot demonstrate the cost of implementing and repairing that alternative.

The increase is evidence of an expectation created by method syntax. It is neither proof that sorting should be added nor a reason to reject it. Compare the complete implementations.

If D4 is admitted, the fixed stable merge sort is the right general approach. ECMAScript permits implementation-dependent comparison schedules and results for inconsistent comparators; using each engine’s native sort would not establish Exact’s stronger cross-executor agreement. [ECMAScript sorting requirements](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-sortindexedproperties).

**What would change my mind:** a real app in which local ordering materially simplifies state flow, avoids an unnecessary source request, or makes subsequent edits faster would justify D4 without waiting for many refusals. Evidence that ordering consistently belongs with existing source logic would support keeping it outside Contract.

**Q3: Design stage 2 now, in full within its limited scope, and judge its implementation independently of stage 1. Confidence: 90%.**

I see stage 2 as **the more valuable language investment**. It improves composition across many operations, rather than adding another isolated method. The starter’s:

```contract
match added { case some(r) => r.error, case none => "" }
```

could become the proposed:

```ts
added?.error ?? ""
```

The corpus supports investigating this: I reproduced **29/80 unguided screens using `null` or `undefined`**, **10/80 using `??` or `?.`**, **16 `find`-using contracts across the 112 unguided sketches**, and **46/80 guided screens using `match`**. These are measures of expectations and syntax exposure, not demonstrated productivity gains. [RFC evidence](/Users/ccheever/projects/exact2/llp/1116.016-contract-expressions-are-typescripts.rfc.md:57).

I favor **`undefined` as the single expression-level absent value**, with a deliberately limited nullable type form rather than a general TypeScript union-type system. Existing options and matches can remain the internal representation.

The hardest part is **making the value model, narrowing, and data boundary tell one consistent story**:

- Generated types currently expose [`T | null`](/Users/ccheever/projects/exact2/contract/cli/src/typescript.rs:221). JSON, required fields, missing fields, and absent field values need explicit conversion rules.
- Directly nested options are [already refused](/Users/ccheever/projects/exact2/contract/types/src/bounds.rs:66). The task is therefore not preserving unrestricted nested-option programs, but defining flattening and retaining explicit records when two distinct absence states matter.
- `??` and `?.` must evaluate receivers once and skip unused work. Optional chaining’s exact boundary matters. [TypeScript’s semantics](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-7.html#optional-chaining).
- Narrowing must respect Contract’s action snapshot. It must never infer that a scheduled assignment changed what subsequent reads observe.
- Indexing should return a possibly absent value. Borrow the discipline of `noUncheckedIndexedAccess`, not merely `strictNullChecks`; refuse assertions that bypass the guarantee. [TypeScript’s checked indexing](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-1.html#checked-indexed-accesses---nouncheckedindexedaccess).

**What would change my mind:** an end-to-end design that requires pervasive special cases, or representative app edits showing that the concise forms conceal important states and increase behavioral mistakes. Stage 1 failing to produce a detectable total-token improvement would not change my mind: it is a different intervention.

## 3. Where I agree or disagree with Claude

I agree with Claude on keeping the TypeScript direction, improving diagnostics and documentation immediately, and measuring the view/data trade before implementing sorting.

My main disagreements are:

- **D3’s cheap implementation is the wrong permanent semantics.** Avoiding a search primitive is insufficient reason to introduce eager `some`/`every`.
- **Stage 2 should not depend on stage 1 proving that familiarity helps.** It has its own ergonomic case and its own correctness risks. Diagnose and measure those directly.
- **The case against a strict subset is overstated.** Identity remains meaningful without mutation; native string representations are architectural choices; CSS names do not dictate expression lexing. These arguments justify examining tradeoffs, not declaring deviations unavoidable.
- **“D2 created the sorting demand” is not itself a negative verdict.** Familiarity sometimes exposes a useful missing capability. The relevant question is whether satisfying it improves complete apps enough to justify its continuing cost.

I would put absence and shared short-circuit search ahead of sorting. That produces a more coherent language than broadening the roster while its option-returning operations remain awkward to compose.

## 4. Biggest risks, ranked

1. **Familiar syntax silently teaches the wrong behavior.** Diagnostics cannot repair accepted misunderstandings. Action snapshots are particularly consequential: the predecessor reports read-after-assignment expectations in **24/80 unguided screens versus 1/80 guided screens**. Keep the transaction model prominent, and distinguish expression compatibility from JavaScript statement execution. Remove accidental semantic differences before expanding the promise. [Predecessor’s findings](/Users/ccheever/projects/exact2/llp/1116.015-what-exact-asks-builders-to-learn.rfc.md:27).

2. **Bounds become surprising application failures.** D4’s proposed 5,000-item sort consumes **65,000 steps**, leaving only **536**. A filter retaining those 5,000 items followed by the sort consumes **70,000**, exceeding the shared limit. Measure useful pipelines, allocations, and frame latency—not an isolated operation that barely fits. Preserve short-circuiting and test refusal behavior explicitly.

3. **The deviation list becomes permission to change meaning whenever implementation is inconvenient.** NaN handling and eager predicates illustrate this danger. Separate enduring value-model decisions from temporary incompatibilities, and require a concrete author benefit for each enduring difference.

4. **The roster grows in response to the latest guesses without a coherent boundary.** Each addition invites adjacent expectations. Admit families where shared machinery makes them predictable and affordable; keep expensive domain work outside. D5 helps with unsupported syntax, but cannot eliminate repeated repair costs or substitute for an understandable supported surface.

5. **Proof coverage and language elegance are mistaken for product success.** The current semantics explicitly excludes resource-bound refusals from differential agreement, classifying them as `UNSUPPORTED`. And the measured spelling changes were level on cost and quality. Maintain separate evidence for semantic correctness, operational behavior, and app-building outcomes. [Semantics limitations](/Users/ccheever/projects/exact2/semantics/README.md:771).
