## Blocker

**Dropping the collection’s default context calls `removeMode` on `defaultModeId` — `tools/figma-tamber/src/code.ts:107`**

`defaultModeId` is readonly, and the plugin API has no call that chooses a new default. The first pull renames `Mode 1` to the export’s default context, so on the theme fixture that mode is `dark-style=black, light`. A later pull that drops that context, while another context such as `dark-style=black, dark` or `dark-style=dim, light` is still present and is `c.modes[0]`, skips the rename (`ids[c.modes[0]]` is already set) and runs `removeMode` on the default mode at line 109. Figma refuses that removal. The published `removeMode` page does not quote the message, so do not match a guessed string. The error is not the mode-limit error, `apply` rethrows, and `undo` has no addition to reverse. The file stays as it was, and that design cannot be pulled. The last-mode case is already avoided: when the plan’s first name is absent, line 108 renames one stale mode before any removal, so the sole remaining mode is kept. The in-memory stub removes any mode once two exist and never checks `defaultModeId`, and the re-pull test drops `dark-style=dim, dark` rather than the default context, so the suite stays green.

Fix: never call `removeMode(col.defaultModeId)`. When that mode’s name is stale, rename the mode that currently holds the name you need to a temporary name, `renameMode` the default onto that name, then `removeMode` the temporary mode. Do this before any other `removeMode`. Teach the stub to throw on `defaultModeId`, and add a test that drops `dark-style=black, light` after the fixture pull and still has the three remaining modes.

## Should-fix

**A refused re-pull does not restore modes, variables, or values it already changed — `tools/figma-tamber/src/code.ts:83`**

`undo` only `remove()`s variables and modes this attempt added, and only `remove()`s collections this attempt created. Before that, `write` has already `renameMode`d, `removeMode`d stale modes (line 109), `remove()`d token-marked variables the plan dropped (line 112), `remove()`d a variable whose type changed (line 115), and `setValueForMode`d. Those stand, and the previous plan stays saved. The rollback test throws on the third `createVariable` of a fresh file, where the new collection is in `made.collections`, so it passes while a re-pull does not. Two documented triggers: a mode name longer than 40 characters (Figma’s variables limit; a context such as `appearance=high-contrast, platform=ios, light` is 45), and `in addMode: Limited to N modes only` after a stale mode was already removed. The second `write` (line 152) is outside the inner `catch`. If it also throws, the first attempt’s removals are still gone.

`tooManyModes` (`code.ts:88`) does match the real `addMode` text `in addMode: Limited to N modes only`. On a 1-mode file the fallback still calls `pull(doc, 2)`, which hits the same limit. A fresh collection is removed by `undo`; the user sees the raw Figma error. `pull(doc, 1)` would have said the file needs at least Light and Dark, and `apply` never calls it.

Fix: snapshot mode names, removed variable definitions, and previous `valuesByMode`, and put them back in `undo` (again without `removeMode` on the default). Parse `Limited to (\d+)`; when the number is below 2, restore and throw the Light/Dark error instead of writing the 2-mode plan. Keep each context’s full string in plugin data and use a mode name of at most 40 characters.

**Server and token are two `clientStorage` writes — `tools/figma-tamber/src/code.ts:136`**

`save` awaits `setAsync('server')` and then `setAsync('token')`. The main thread’s `onmessage` is async, so a `load` already between its two `getAsync` calls (`code.ts:133`) can observe the new server with the old token, or the old server with the new token. `ui.ts:83` then assigns that pair to `paired`, including after a pair that already succeeded. The next pull sends that token to that server. A failed second `setAsync` leaves the same tear for the next session. The failed-pair path itself is fixed: `pair` calls with `token: null`, and `paired` changes only after success (`ui.ts:44`). A 401 clears the token only when `at === paired` (`ui.ts:17`).

Fix: one `clientStorage` key whose value is `{server, token}`, written with one `setAsync`. Ignore a `load` reply that arrives after a pair has succeeded in this session.

**A collection is reused by name — `tools/figma-tamber/src/code.ts:99`**

`find` takes the first collection named `Tamber` or `Tamber · {tuple}`. Figma allows duplicate names. An existing collection with that name is marked `owned`, then its modes that the plan does not name are `removeMode`d and the plan’s variables are written into it. `holding` (`code.ts:64`) and the layout migration (`code.ts:157`) use the same name lookup.

Fix: reuse a collection only when `getSharedPluginData('exact', 'owned') === '1'`. Otherwise create a new one, and use that same predicate in `holding` and when deleting a layout the plan no longer names.

## Nits

**`gone` conflicts share the “push them first” instruction — `tools/figma-tamber/src/ui.ts:55`**

The line does say the design no longer has the value. Cancel still tells the user to push, then pull. A push writes into the last pulled export; it does not put back a token or context the design has dropped. Use a separate sentence for `gone: true`: Cancel leaves Figma’s variable in place, and the next pull will remove it.

**An alias that goes nowhere is omitted — `tools/figma-tamber/src/code.ts:41`**

A cycle, a missing target, or a library variable (its collection is not in `getLocalVariableCollectionsAsync`) returns `undefined`. `push` then keeps the baseline value and the status says nothing. Same-collection resolution, a cross-collection mode of the same name, and `defaultModeId` as the fallback (`code.ts:46`) are in place. The same-name path is tested; the default-mode fallback is not. Surface those tokens in the push status.

**`load` has no `.catch` — `tools/figma-tamber/src/ui.ts:83`**

It sits outside `busy`. A storage failure is an unhandled rejection, and the buttons still run against `{server: '', token: null}`.

**Two non-dark schemes in one tuple share the key `Light` — `tools/figma-tamber/src/mapping.ts:150`**

`Object.fromEntries` keeps the last one. `split` treats every final segment other than `dark` as light. A tuple with two such contexts silently drops the earlier one.
