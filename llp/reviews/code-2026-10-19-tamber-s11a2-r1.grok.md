They plan with `exact_tamber::plan` (`tamber_serve.rs:1178`, `tamber_scrub.rs:83`) and `tamber_ops::params` only. `apply_all_with` then checks the edited text with `tamber/src/params.rs` `laid` (`edit.rs:452`), which is empty unless the app has component params. An app line `brand = reading.card` is `tamber-unknown-token`, so any edit that leaves that alias — set another token, add a `when`, add-token, scrub a dial — is refused. The edit that succeeds is one that deletes every package alias. Apps with no package reference are unchanged. `write_checks` (`tamber_scrub.rs:131`) uses raw `check` and treats a failed check as no role-axis rows, so fixing only `plan` would let a new role-axis through on the same write. `param_values` does call the new `laid`, but only after `plan` succeeds and only when component params exist. The new test’s header says these tokens are edited here; nothing proposes or scrubs.

## SHOULD-FIX

**Package diagnostics still quote the banded line.** `relocate` (`tamber_params.rs:75`) rewrites `d.line` and the file, and leaves the message. A duplicate (`tamber/src/check.rs:647`) or an ambiguous `when` (`check.rs:886`) says `line 268435460`. The build unbands that text (`theme.rs:766`, `packages.rs:212`). The primary `file:line` is already the package file, so the diagnostic is findable.

**`tamber check` skips the build it was given to run.** Admission is `tamber.rs:158`, but a fold error returns at `tamber.rs:149`. A pre-merge refusal (parse error, `tamber-package-block`, bad name) makes `merge` drop that package’s tokens (`packages.rs:189`). If the app then names one, `check_design` reports `tamber-unknown-token` on the app line and the package’s own refusal is never printed. `with_package_designs` (`lib.rs:101`) discards those refusals. Separately, no `app.tamber` and no component params exits at `tamber.rs:113` with “has no design”. The synthetic `tamber app` is only built when params exist (`tamber.rs:106`). `Lowerer::design` still folds packages in that case (`packages.rs:335`). The new predicate at `tamber.rs:160` does not run. When the laid fold itself succeeds, admission does compile the app and reports `references()` and the pre-merge refusals.

**Server reads are greener than the build.** `fold_with` (`tamber_params.rs:126`) is `check_design` on the join. It does not run `packages::references()` (`packages.rs:243`), so `describe` and `resolve` show a value for a package token that names another package’s token or a dial. A package the merge skipped disappears, and `describe` stays ok. `tamber check` says both, and only when its own fold succeeded.

**Export cannot emit an app-only document of a design the build accepts.** `export` calls `design()` (`tamber_serve.rs:772`), which checks the app file alone. `brand = reading.card` refuses the whole DTCG export. Keeping the document to the app’s own tokens still requires the package join, then dropping tokens whose lines sit in the package bands. `export::dtcg` emits every token in the folding, so pointing it at `design_with` would also dump the package tokens.

## What checks out

Reads agree with the build for a legal alias, and apps with no package designs are unchanged. An empty package list returns the design as it was (`packages.rs:106`), then `params::add_to` as before. `tamber check` still uses `exact_tamber::check` when both lists are empty (`tamber.rs:122`). `design_with`, `describe`, `resolve`, `explain`, and `uses` go through `fold_with`. The test’s `brand` resolves to `#112233`. The app’s own definition of the same name wins in `merge` (`packages.rs:195`). Param lines stay at `1<<29` and above, so they miss `package_line`. Explain of a package token returns its value; the `files` digest stays the app snapshot. History diffs those raw app texts (`tamber_history.rs:579`) and does not invent package files. The params cache key includes every `.tamber` in the source graph (`tamber_walk.rs:199`, `tamber_walk.rs:258`), so editing a package design reloads.

Band math and naming are exact. `(line - LINE) / BAND` is the package index and `% BAND` is the file line (`packages.rs:49`). `files[source_id]` is the app-relative path (`node_modules/@acme/reading/reading.tamber`); `home` (`@acme/reading/reading.tamber`) is only the fallback (`tamber_params.rs:79`). `source_id` is assigned after the path is pushed (`sources/packages.rs:105`), after the app design is already a source (`sources.rs:404`). Column is left alone. An out-of-range band returns before `d.line` is written (`tamber_params.rs:76`).

Writes do not splice a package token into a file. `parse_ops` (`tamber_ops.rs:11`) reads the wire, not the laid design. `set-token` and `remove-token` use `token_index` on the parsed app file (`edit.rs:1026`); a package-only name is “no token” and nothing is written. `add-token` of that name inserts an app line, which the build already treats as the app’s definition. Ops cannot name a path outside the snapshot. `files()` (`tamber_serve.rs:550`) is the app’s `*.tamber` files plus owned `.contract` files. Digests, hello, journal, and history stay on that set.

Gen and the successful admission path match the join. `tamber gen` lays the same way (`tamber_gen.rs:558`) and refuses camelCase and `SCREAMING_SNAKE` collisions (`tamber_gen.rs:472`). `reading.card` binds as `readingCard` / `READING_CARD`. The app’s same-name token wins, so one binding remains. `compile_path` runs first when `app.contract` exists (`tamber_gen.rs:547`), so a `references()` failure generates nothing. Gen still requires a design file (`tamber_gen.rs:521`). `ir` includes package tokens (`tamber.rs:374`). `eval` prints them and filters only the `param.` prefix (`tamber.rs:326`). The check’s token count includes them.
