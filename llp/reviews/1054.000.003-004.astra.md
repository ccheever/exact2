## RFC 1054.000.003 — Dates in the roster

### Assessment

Moving label-only clock dependencies into Contract can fix D8 while preserving deterministic rendering across hosts. The direction is useful, but the RFC overstates both Intl equivalence and the impossibility of alternatives. Its invalid-input contract is inconsistent, and the proposed scope needs stronger consumer and size evidence.

### Strengths

- Explicit timestamps and offsets preserve the existing clock model and require no data-seam or host API extension. The existing fact already supplies both values. [runner/src/time.rs:9][time]
- Using the roster authority, removing `formatClockTime`, and rebuilding incompatible plans fit existing mechanics. The stated cohort consequence is correct: compatibility includes `FORMAT_DIGEST`. [plan/tables/format.json:823][roster], [bake/src/compat.rs:297][compat]

### Concerns

- **BLOCKER — Invalid input contradicts the return type.** D4 returns `number`; D5 and the tests prescribe `""` for invalid arguments. That cannot be the advertised typed operation. Specify a numeric failure policy or an optional result, and distinguish the relative-time zero sentinel from valid Unix timestamps. Also define clipping and range checks on the **shifted** instant: a valid endpoint plus an offset can exceed Date’s range. [RFC:164][d3-days], [RFC:198][d3-invalid], [RFC:249][d3-invalid-tests]

- **MATERIAL — Intl supplies formatting, not these buckets.** Intl does not choose the one-second threshold, units, rounding, or average month/year lengths. The proposed arithmetic produces `1mo ago` at 60 days and `1y ago` at 730 days. Those are explicit application policies, not browser equivalence. The “byte for byte” replacement claim is also false: existing `formatClockTime(-0.5)` yields `11:59 PM`; Intl clips it to zero milliseconds and yields `12:00 AM`. Add fractional, BCE, extended-year, shifted-range, and both-direction bucket cases. [RFC:128][d3-buckets], [runner/src/stdlib.rs:115][old-clock]

- **MATERIAL — Fixed offset is not the viewer’s historical calendar.** The limitation is acknowledged, but “viewer’s yesterday” remains too strong. In Los Angeles, `2026-03-08T07:30Z` is March 7; applying that afternoon’s −420-minute offset makes it March 8. `calendarDays` consequently returns today instead of yesterday. The winter/summer example also has the direction reversed for the usual spring-forward change. Keep the bounded scope, but name it fixed-offset semantics and establish whether Messages accepts that behavior. [RFC:166][d3-days], [RFC:187][d3-offset]

- **MATERIAL — The motivation excludes working alternatives and overpromises D8’s result.** Separate labels can be joined with nested `each`/`when`; I compiled that construction. It is potentially quadratic, but possible. A pure source can also return decorated rows directly, retaining the marshaling cost. More importantly, Bluesky’s `unread` and `hasNew` clock arguments drive real polling, so removing formatting work cannot make every minute tick source-free. [contract/cli/tests/it/instance.rs:263][nested], [Bluesky reads.rs:651][unread], [Bluesky reads.rs:260][peek]

- **MATERIAL — Four entries are not yet justified by the admitted fixtures or core cost.** Fixed-offset day differences already fit a short Contract function; a probe compiled to 405 bytes. Relative counting also already works in `fn`, as the RFC acknowledges. Caltrain establishes short time and RealWorld establishes long dates; that does not establish every style and month/year policy. All apps currently pay for reachable roster implementations: the use-set does not select individual stdlib functions. Measure wasm bytes and rebuild cost rather than estimating source lines. [RFC:71][d3-alternative], [runner/src/uses.rs:20][uses], [plan/tables/format.json:823][roster]

- **MINOR — Examples and literal checking need tightening.** `minute = 0` leaves labels blank until the first 30-second timer fires, even after the date arrives. The calendar helper sends every negative day difference—including distant future dates—to the weekday branch. The literal check must run after function resolution and arity checking, respecting user-function shadowing; document that a wrapper cannot forward a style parameter. [runner/src/runner.rs:739][timer], [RFC:171][d3-example], [contract/types/src/lib.rs:625][resolution]

### Suggestions

- First compare a smaller solution: source-provided absolute labels/timestamps, an app `fn` for relative labels, and Contract arithmetic for fixed-offset day differences.
- If roster entries remain warranted, migrate actual consumers in the same change and count **label-driven application-source calls**, separately from polling.
- Resolve the generated-fixture check-in against the generated-file rule. Name the implementation date and obtain a concrete scope trade; deleting the old formatter is useful cleanup, not automatic justification for all additional behavior. [RULES.md:16][generated], [RULES.md:58][assignment], [DEFERRED.md:350][trade]

### Answers to the open questions

1. **Consumer:** Existing admitted apps suffice for the specific uses actually migrated. Broader relative/calendar behavior needs a driven admitted consumer; hypothetical future Messages use is insufficient.
2. **`narrow-bare`:** No additional roster style now. Preserve that presentation with an app function rather than requiring the app to accept “ago.”
3. **Seconds:** Keep a one-second boundary if adopting this API, but call it a policy choice. An app can choose “now” below five seconds; Intl does not decide this.

### Verdict

**NOT READY.** Resolve the typed failure contract, correct the semantic claims, and justify a smaller measured scope.

## RFC 1054.000.004 — Narrower refreshes and bounded feeds

### Assessment

Bounded answers and C5 directly address useful application problems. `touching` is an optimization of the already-landed D2 fix, and its placement inside the runner is sensible. However, the illustrated mutations violate its safety premise, and the lifecycle and cost analysis need correction before acceptance.

### Strengths

- A typed walk is appropriate for positional values. It requires no changed-answer signal, forwarder extension, worker envelope, or language-specific API, and its type-reachability metadata is not a second application-state graph. [plan/src/value.rs:15][value], [RFC:151][walk]
- Capturing keys at send time and retaining them with pending work is the right direction. Filtering additions to the refresh sets can preserve explicit refreshes and existing settlement behavior. [RFC:144][keys], [runner/src/runner/commit.rs:16][checkpoint]
- The syntax-freeze prerequisites have landed: `contract fmt` and `contract symbols` exist. That removes that particular objection, though it does not supply consumer admission or a scope trade. [contract/cli/src/main.rs:15][cli]

### Concerns

- **BLOCKER — The delete exception loses rollback refreshes.** D1 forbids row removal, then calls delete “in place.” Bluesky optimistically marks a post deleted; the send-time re-read filters it out. If the write fails, the source clears that flag, but the reply-time walk now finds no post and can skip restoring it. Retaining the predicate key alone does not solve this. The same problem exists if an optimistic edit changes the predicate field. [RFC:118][assertion], [Bluesky writes.rs:159][delete], [Bluesky reads.rs:72][filter], [Bluesky writes.rs:220][rollback]

- **BLOCKER — Favorite/like/repost are not necessarily membership-preserving.** RealWorld queries favorites through `favorited=username` and separately returns pagination metadata. A favorite can insert an absent article or change page counts; neither requires the current answer to contain that article. For example, navigate to Favorites while the mutation is pending, let its pre-write empty GET finish, then receive mutation success: the reply-time predicate matches nothing and leaves the feed stale. The “request in flight” exception no longer helps. These consumer examples cannot be accepted under the current assertion. [apps/realworld/app.ts:88][favorites], [apps/realworld/app.ts:159][favorite-write], [RFC:294][d4-consumers]

- **MATERIAL — Pending and continuation semantics need an explicit contract.** A resource can hold a placeholder and be pending without a host request; checking `Some(ResourceState)` and tickets is insufficient. Mutation parsing can return `Later` repeatedly, and the current path constructs a replacement pending request: touches must survive every such enqueue. Checkpoint cloning supports rollback once the metadata is included, but does not perform that propagation automatically. Require tests that change the key’s source slot before reply, exercise multiple continuations and refusal, preserve send-time requests, keep unconsumed forced refreshes, and forbid request reuse for reply-time forced refreshes. [runner.rs:181][placeholder], [commit.rs:596][pending], [commit.rs:715][continuation], [commit.rs:547][keep], [settlement.rs:633][unconsumed]

- **MATERIAL — The plan change is larger than costed and incompletely validated.** D1 adds **two** operands; Costs says one. More importantly, the shared decoder stores only three operands, so the proposed five-operand `Send` requires changing it and its consumers. Specify empty ranges, range bounds, record/field validity, key types, and malformed-plan rejection. Predicate comparison should use Contract `==`, including `-0 == 0`, rather than identity, bitwise equivalence, or `key_text`. Types are already acyclic, so a memoized DAG traversal suffices for reachability. The digest change also creates a new update cohort. [runner/src/vm.rs:323][decoder], [plan/tables/format.json:797][send], [runner/src/compare.rs:9][equality], [plan/src/lib.rs:478][acyclic], [bake/src/compat.rs:297][compat]

- **MATERIAL — Re-ask cost is real, but the stated evidence is misleading.** A TS `Now` answer crosses JSON and constructs values; a `Later` re-read returns a request envelope, which settlement discards without transferring a whole list. F5’s 3.75/108-ms capture figures describe the older implementation; lazy capture paths and direct ordinary-answer decoding already exist. Rust is not automatically cheap either: Bluesky constructs fresh post records, defeating the identity-based conformance shortcut. Measure current native TS, browser TS, and Rust paths before attributing savings. [settlement.rs:503][reread], [js/src/prelude.js:220][marshal], [js/src/lib.rs:594][decode-json], [Bluesky model.rs:509][fresh-post], [runner/src/conform.rs:62][conformance]

- **MATERIAL — Bounded feeds need an application design, not just a window argument.** `homeFeeds` returns `list<Feed>`; bounding each feed to K rows gives approximately F×K rows per resource, plus nested content. It does not bound producer cache size or bytes. Specify per-feed windows, cursor retention, backward movement, insertion/deletion anchoring, and error/retry behavior. C5 must bind progress/cursors as well as identity to remove `loaded(...)`; `more(f.id)` alone addresses only half of D4. Runtime edge dispatch currently passes an empty argument vector, so both compiler and dispatch must change. [Bluesky app.contract:76][feeds], [contract/analyze/src/lib.rs:438][edge-arity], [runner/src/runner/event.rs:666][edge-dispatch]

- **MATERIAL — D3’s trigger cannot identify a representation problem.** A 16.7-ms tap-to-commit breach might be network delay, producer work, layout, or transfer. Separate those phases and use the actual frame budget before reopening executor identity reuse. Furthermore, returning the same mutable JS object does not prove its contents are unchanged; reuse needs an immutability/version contract. Language parity requires equivalent observable behavior, not equal implementation costs. [RFC:243][trigger], [LLP 1027.001:13][parity]

### Suggestions

- Keep deletion, membership changes, aggregate changes, and predicate-field changes unnarrowed. If deletion remains supported, retain send-time matched resources through the mutation and union them with reply-time matches; that fixes the rollback example but does not fix absent-row insertions.
- First split broad mutations by operation: article reactions can declare article/feed refreshes, comment deletion can declare thread refreshes. This cannot discover exact membership, but it can remove unrelated asks without new syntax.
- Land the bounded consumer and C5 independently, then measure whether a walk still earns its complexity. Add web-driven correctness coverage and native/browser TS continuation coverage; do not infer parity from Rust-only tests.

### Answers to the open questions

1. **Consumer:** RealWorld supplies a candidate correctness fixture, but its four-way declaration alone does not establish a performance need, and the proposed favorite fixture is unsafe. Try operation-specific declarations first. D1 needs a valid measured consumer and a named scope trade; neither is supplied. [DEFERRED.md:350][trade]
2. **C5:** **Yes, independently.** Evaluate bound arguments in the live enclosing scope at dispatch, preserve edge gating, and demonstrate both list identity and progress. Bluesky’s admission remains Charlie’s decision.
3. **Warn or refuse:** **Warn**, considering the predicates collectively. With OR semantics, a resource is unreachable only when **none** of the predicates can occur in it. A wide declaration can intentionally contain resources irrelevant to this particular send.

### Verdict

**NOT READY.** D1’s examples can produce stale UI. Bounded answers and C5 are promising separable work; the narrowing proposal needs a sound applicability contract and current measurements.
