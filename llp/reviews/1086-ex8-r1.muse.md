## Finding 1 (E4, material): terminal placement refusal never finishes the server intent

`snapback4/client/src/round.rs:675` posts the placement; on a non-retryable, non-`E_AUTH` refusal the code falls through to `snapback4/client/src/round.rs:693-706` and settles locally `failed`. Nothing ever calls the pinned server's existing `POST /assets/intent/{id}/finish` route, whose handler exists precisely to persist terminal refusals for placements that return before receipt creation. `snapback4/client/src/uploads.rs` (candidate) has `prepare` only — no finish helper.

Effect: the uploaded bytes stay pinned under a server-side `pending` intent, and the refusal is never bound into a server receipt, so a later same-intent placement finds no replayable receipt. Reproduction: extend the `durable upload custody` test with a mutation the server refuses (e.g. a failing `require`), run `uploadAndPlace` + `sync`, observe local `failed` while the server still lists the intent pending. The worktree's uncommitted follow-up adding `uploads::finish` plus a flush hook corroborates this gap.
