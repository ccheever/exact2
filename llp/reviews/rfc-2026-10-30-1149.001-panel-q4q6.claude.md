## Q4: the order against S2's Windows queue

**Recommendation: option (c), amended.** Windows leads each instrument pair, and the Windows text layer (RichEdit into Shelf's search field, with M9's audit) moves ahead of Stage 1. Stage 0 and Stage 0b stay first, because 0b is dated and Stage 0 is the precondition for every Windows prediction; Stage 0's Windows half absorbs the startup tail as an instrument, not a hunt. Concretely:

1. **Now, beside each other:** Stage 0b (Mac, dated 2026-11-04; see Q6) and Stage 0 with its Windows half first in the lane: the per-thread profile of the G6e build, the counters `perf` reads on the headless presenter, the rest trace. Fold the startup tail into this half as two cheap, unattended NucBox items: (i) a watchdog in the Windows host that dumps all-thread stacks when runner-ready to layout-ready exceeds about 50 ms, left in the ordinary launch series until a stall is caught; (ii) a direct two-arm A/B of the loader-lock hypothesis (device thread started at process entry versus after layout-ready, about 100 launches each), which tests the hypothesis without needing a reproduced stall.
2. **Then the Windows text layer:** RichEdit bound to Shelf's search field (IME, selection, UI Automation) with M9's DirectWrite audit in the same lane. The author's pairing, led by the Windows item, and before Stage 1 rather than after it.
3. **Stage 1** (M1, M4, M5 are Mac; M2 is already met on Windows) after that, or in a parallel Mac lane if a second builder exists.
4. **M10:** the Windows phase table already exists, so the Windows chunk is the savings, ordered after the tail is caught; the Mac phase trace with Stage 0's, feeding Q6's 2026-11-30 decision point.
5. **Lock/unlock** whenever the NucBox has an unlock operator; it is infrastructure-blocked and competes with nothing.

**Confidence: 70.**

**Reasoning.**

- *The prospect's visible Windows items are not the scoreboard's.* On Windows, ink already leads the field on startup (160.8 DWM / 177.7 DXGI versus egui's 249, G6e), matches cadence (58 displays/s, 0 late) and beats egui on working set (153 versus 182). Its one scoreboard loss, fling CPU 84 versus 25 ms/s, is invisible on a desktop at that cadence. What a Windows user of Shelf would notice is the one-in-ten launch that stalls 200+ ms (S2.9: 209 versus 153 ms fresh, 197 versus 137 retained; `QUEUE.md` 1638), a search field that is not the platform's (LLP 1149 §4, S0 C7: "the RichEdit spike is test-only"; "binding to a Contract field, the IME, selection and UI Automation are S2's"), and text that is not DirectWrite's (D3's table calls it "the one tell a Windows user notices"). Those come before Mac fling-CPU fixes for a prospect who "cares about Windows first, startup first", and Charlie already ordered S2 before S1 on that ground (LLP 1149 §3: "the prospect's platform, and the strongest numbers").
- *Stage 0 cannot be skipped for Windows, and it is small.* The document's own Windows prediction "waits on Stage 0's trace of the G6c build" (§3, Stage 1), and G6e records "no CPU stacks to attribute the remaining CPU range miss". Nothing Windows-side past the text layer can be predicted without it. Ordering the Windows half first inside Stage 0 costs nothing; the two platforms' series need different machines (§4: a held Mac display for fifteen minutes; the signed-in NucBox with PresentMon), so the contention is builder and review attention, not hardware.
- *The startup tail is an instrument problem, not a chunk to "do first".* S2.9: "76 diagnostic launches across three traces did not reproduce" it; "the missing evidence is a blocking stack from a reproduced stall". A dedicated lane for a 1-in-10 event with no reproduction is open-ended. Two facts make the A/B cheap and pointed: the two recorded stalls began at 61.35 and 63.38 ms of process age, and hardware readiness in those launches was 59.4, 59.3 and 62.6 ms (MEASUREMENTS.md S2.9, "What the tail logs establish"), which is exactly when the device thread finishes loading the driver. That coincidence supports the loader-lock hypothesis enough to test it by construction rather than by catching a stack. This belongs in Stage 0's Windows instrument work, which is why I move it there rather than pairing it with M10 as the document does.
- *M10's Windows "phase trace" is largely done.* MEASUREMENTS.md S2.7, "The 100 ms budget, summed", already attributes the Windows first screen: fonts 24–27 ms, process creation to host entry 17–20, configuration and native window 12, show window to first redraw 20, submission to DXGI display 31 (composition), sums 131–154 ms, and "removing the remaining device join alone cannot deliver a 100 ms screen". So option (d)'s "M10's Windows phase trace before any Mac work" would redo what exists; the real Windows startup work is the tail and those host-side savings, none of which is renderer work.
- *Why not (b), the queue first?* Stage 0b is dated five days out and Mac-only; (b) would breach it or need Q6 renegotiated first. And the DirectWrite audit (M9) and the RichEdit field share the Windows text layer, so (b) with M9 deferred to "the program after" would open that layer twice.
- *Why not the document's (a)?* Its "Stage 0 and 1 are small and cross-platform" is half right: M1 and M2 are per-carrier changes to the same winit pattern (`host/apple-painted/src/window.rs:552` and `host/windows/src/window.rs:1205` each own an `about_to_wait`; the Windows one is also called explicitly from four other paths), M4 is shared `host/ink/src/layer.rs`, but M5 (`CADisplayLink`) is Mac-only and M1's predicted saving is the Mac's 12.6 ms/s. Windows's rest milestone ("no tick in ten seconds") is already met at G6e's 0.00 [0–6.22]. Stage 1 is Mac work in practice, and putting it ahead of Shelf's search field inverts the prospect's priority.

**What would change my answer.**
- A prospect deadline for a Shelf demo: the RichEdit field goes immediately after 0b, ahead of Stage 0's Windows half (the author's own caveat, and I agree with it).
- Charlie wanting the Mac scoreboard against GPUI and egui as the public story: then the document's order.

## Q6: the dated boot obligation

**Recommendation: option (d), decouple, carrying (a)'s relative guard as a standing gate rather than a dated one.** In full:

- **The device layer's obligation is D15's parts one and two, by 2026-11-04, with D15's consequence as written** (unmet and unrenegotiated, the layer is deleted). Part one I would read on the first-screen path, which is what Windows was held to: the summed first-screen p50 of ink on direct Metal within 5 ms of ink on wgpu in the same carrier on the same instrument, met either by closing the device-creation gap or by hiding it off the path as S2.4 did on Windows (44.7 ms of creation, "all of it hidden"). Part two is D6.3's archive-miss rule, unchanged.
- **The renderer's standing boot guard, mirroring Windows:** no more than 10% regression against the platform's existing painter on ink's own instrument, rerun at each stage landing under §4. On the Mac that baseline is the CPU painter presenting through the carrier once part two exists; until then the native host's 354 ms by its layer-snapshot instrument is the record, not a proof. This is (a)'s mechanism, kept as a guard, not as the renegotiated condition of a deletion date.
- **The 100 ms first screen is the application's obligation under `rules/RULES.md`'s cold-start budget,** owned by M10 on both platforms, with a decision point of 2026-11-30 whose deliverable is defined: the Mac phase trace published beside the Windows one, and a savings budget that sums to a number, after which Charlie funds the boot program or writes the trade into `rules/DEFERRED.md` as the Linux painter's first-launch cost was written (§Runtime, 2026-10-22). No device layer is deleted over app boot on either platform.

**Confidence: 78.**

**Reasoning.**

- *Part three is not the device layer's to meet, and deleting the layer cannot meet it.* On the Mac the device is 32 ms of ink's 352; the rest is plan, runner, layout and fonts, "unattributed so far" (1149.001 §3, M10). No arm is near 100 ms: native 354, GPUI 313, egui 337, ink 352 (RESULTS.md G4). Deleting direct Metal and running wgpu saves at most the 16 ms device difference (C5 "Boot phases": device 31.1 versus 13.2 ms retained, constructor 31.7 versus 15.6) and leaves a ~336 ms first screen, still 3.4 times the budget. A deletion that cannot move the metric it is conditioned on is not a lever; it is a loss of 27–30% paint time on Shelf and Excord, 11–47% CPU per frame and lower, spike-free memory (LLP 1149 §4, S0 C5; D5's Apple row: "earned its place on frame time, CPU and memory, not on boot").
- *D15 already conflicts with itself when the baseline is over budget, and Windows resolved it the way (d) does.* The panel's sentence "where the baseline already exceeds the budget, further regression is an explicit trade" and Muse's restatement "the complete first screen at p50 within the 100 ms budget with the phases summed" cannot both bind on a platform whose existing painter is at 354 ms. S2.7's orchestrator reading applied the relative gate and called the absolute 100 ms "the app's boot"; D12 then kept DirectX 11 as the Windows default with the tail and the 100 ms "open, but [they] do not gate ink's DirectX 11 default" (`QUEUE.md` 1638), and D15 says "DirectX 11 is built regardless", with no deletion clause. That is option (d) already in force on Windows. Applying it on the Mac is the "one rule for both platforms" the author's alternative asks for, more exactly than (b) does, because Windows carries no deletion date tied to the 100 ms.
- *Parts one and two keep a real consequence, which the panel insisted on.* D15 refused "boot owed" indefinitely. The device-creation regression is the layer's own and "unexplained" (LLP 1149 §4, C5), and the 127 ms empty-cache pipeline build must never block first pixel (D6.3). Both are inside the device layer's code, 1149.001 commits to landing them by the date, and five days is enough for a bounded change; if it is not met, D15's renegotiation clause exists and should be used with numbers, not slipped silently.
- *Why not (a) as proposed?* As the condition of the deletion date it has no teeth: ink is at 352 against a 354 baseline, so the 10% band is 35 ms of headroom on a comparison the document itself says "is not proof of equivalence" because the instruments differ (G4: "Native's settled layer-snapshot milestone is a different instrument"; G1 put the same native milestone at 464–597 ms). A gate that is passed before it is written reads as a renegotiation that removes the obligation. Its mechanism is good as a guard once the CPU painter's number exists on ink's instrument, which is how I keep it.
- *Why not (b)?* "The 100 ms work as the condition" is ambiguous. Read as "100 ms met by 2026-11-30", it is (c) delayed a month and will be unmet again: Windows, with a leaner host, is at 161–178 ms after moving the jump list off the path, and its phase table has 24–27 ms of fonts, 20 ms of show-window and 31 ms of submission-to-display with no renderer work left to remove. Read as "M10's trace and first chunk landed", it is the document's decision point restated, in which case (d) says the same thing without a deletion clause on a layer that cannot change the number.
- *Why not (c)?* It is self-defeating as above, and D15's own text permits renegotiation ("unmet and unrenegotiated"), which is what the document is doing.
- *RULES.md is respected, not evaded.* Its 100 ms p50 is a time budget "tracked every commit", a P0 on regression; the renderer did not regress it (352 against 354) and the [check] rule ("the boot path executes and compiles nothing") is a count, satisfied by D6.3's form that the r4 panel accepted (§5 Q14). The budget's debt sits with the application boot on both platforms, which is where M10 and the decision point put it.

**What would change my answer.**
- Stage 0's Mac phase trace showing the device layer owns much more of the 352 than the 32 ms device phase (the archive load, the layer attach, the first frame's atlas uploads): then parts one and two should widen to those phases, still short of the whole 100 ms.
- Part two not buildable by 2026-11-04 (the CPU painter cannot present through the carrier): (a) loses its baseline entirely; (d) does not depend on it, which strengthens (d), but the device obligation then needs a renegotiated date with the reason written.
- Charlie wanting the 100 ms as a hard product gate with a lever: then (b) with the condition read as "trace and savings budget landed by 2026-11-30", and the lever placed on the app-boot program as a named P0, not on the renderer's device layer.
- Evidence that the 16 ms device-creation gap is irreducible and cannot be hidden off the first frame's path on the Mac (unlike Windows): then part one's 5 ms is the wrong shape and should be restated as a summed-first-screen difference before it fires a deletion.
