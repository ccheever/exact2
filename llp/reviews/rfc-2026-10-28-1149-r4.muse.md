## Q14 — The boot rule

**Recommendation: option (b), modified.** Write the replacement exception per platform. But make the condition "a cache miss never blocks first pixel", not "ship an archive in the bundle".

**Confidence: 70.**

**Reasoning**

- The rule's own text mandates bytecode: "Modules ship as bytecode, never source strings transpiled per module at boot" ([RULES.md](/Users/ccheever/projects/exact2/rules/RULES.md:53)). DXBC is bytecode by Microsoft's definition: `CreateVertexShader` takes "a compiled shader" as bytecode ([Microsoft Learn: ID3D11Device::CreateVertexShader](https://learn.microsoft.com/en-us/windows/win32/api/D3D11/nf-d3d11-id3d11device-createvertexshader)). A `.metallib` is AIR. Shipping these is compliance with the rule's mechanism, not evasion of it.
- But driver lowering of AIR/DXBC to GPU ISA is still compilation. Option (a) asks us to rename it. That makes the rule unfalsifiable by layer: wgpu's 457 ms DirectX 12 translation also happens "below" the app. The defensible line is the input form and who could have done the work at build. D6.3 already draws it correctly: "no application-side shader compilation runs on Metal or DirectX 11" ([LLP 1149](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:424)).
- Option (a) also fails its own test. Cold start is 100 ms p50 ([RULES.md](/Users/ccheever/projects/exact2/rules/RULES.md:41)). A 127 ms pipeline phase cannot be "held to the budget phase by phase". Renaming it in `metrics.mjs` does not change the arithmetic. An exception is needed under any name. `boot.mjs` counts a module graph ([scripts/boot.mjs](/Users/ccheever/projects/exact2/scripts/boot.mjs:4)); driver work is not countable there, so the exception plus timed phases in metrics is the honest instrument.
- The precedent already exists and is looser than (b). The current entry accepts a first launch "over the cold-start budget: on RADV, device creation and shaders alone cost 170 ms (93 + 77 ms)" ([DEFERRED.md](/Users/ccheever/projects/exact2/rules/DEFERRED.md:631)). LLP 1009 D5's deferral — compile at first use, after first pixel ([LLP 1009](/Users/ccheever/projects/exact2/llp/1009-gpu-canvas.rfc.md:114)) — cannot apply to the presenter itself. The presenter is the first pixel. The replacement exception is narrower than today's if it requires: warm pipeline cost inside the 100 ms budget as a named phase (0.5 ms Metal, 2.7 ms DX11 pass trivially), first-launch cost written per platform, and the miss taken off the first-pixel path.
- "Ship the archive in the bundle" cannot be the compliance mechanism on Metal. Apple's model is device-built archives serialized for later launches ([Apple: Creating binary archives from device-built pipeline state objects](https://developer.apple.com/documentation/metal/creating-binary-archives-from-device-built-pipeline-state-objects)). An archive is specific to a device and OS; a bundled set will miss on new hardware and OS updates. The miss path must exist anyway. So the obligation should be: asynchronous pipeline creation, first frame(s) on the CPU painter through the fallback D5.4 already specifies, archive populated and serialized off the path. A bundled archive becomes an optional accelerator.
- Option (c) is disproportionate and does not achieve its purity. It bans a 0.5 ms warm cost. It forces a permanent second presentation path every launch. And it does not remove boot work: device creation (13–48 ms measured) stays, and on Windows the CPU first frame still needs the swap chain, since DXGI forbids returning to GDI after flip-model presentation ([LLP 1149](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:381)).
- The rule's rationale supports the split: "Every launch pays for boot" ([RULES.md](/Users/ccheever/projects/exact2/rules/RULES.md:56)). The 127 ms is not every launch. It is once per machine per binary. The per-launch costs (0.5, 2.7 ms) belong inside the budget. The once-per-binary cost belongs in the exception, off the first-pixel path.

**What would change my answer**

- True first-ever numbers (fresh OS or cleared system shader cache) for Vulkan on RADV and OpenGL ES on low-end Android. If either is several hundred ms and recurs on cache eviction, I would move to (c) on that platform.
- Evidence that asynchronous pipeline creation plus a CPU first frame needs a genuinely separate presentation path on some platform, rather than reuse of D5.4's fallback. That raises (b)'s cost toward (c)'s.
- Measurement showing bundled Metal archives hit reliably across the D5.3 support matrix including OS updates. Then the off-path requirement could be dropped.
- Evidence that the DX11 2.7 ms excludes driver compilation deferred to first draw. Then the Windows warm number reopens.

## Q21 — The thresholds

**Recommendation: keep both verdicts on substance. Restate D15 before S3 reuses it. Keep direct Metal with a dated obligation at the S1 gate, with deletion as the stated consequence.**

**Confidence: 75** that both keep outcomes are right; 85 that D15 as written was under-specified.

**Reasoning**

- Predeclaration worked. The control arm separated retention from algorithm: B alone took scroll paint from 2.716 to 2.152 ms, and ink then beat B by 30–42% at 1920×1080 ([§4 S0 C4](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:702)). The 20% bar discriminated as designed. The 10% bar correctly identified direct Metal as the marginal case.
- Medians or worst run: §4 already answers per metric, and D15 should inherit it. Cold start is defined as "median of interleaved runs" ([§4](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:654)). Memory is defined as peak (line 657). So: medians for times and CPU; for peak memory, median-of-peaks for the 10% guard, with any worst-run breach triggering mandatory localization rather than automatic failure. A max-of-five is a high-variance estimator that grows with n. Auto-failing on it would punish running more rounds. C4's actual handling — verdict on medians, spike carried as an open item — is the right judgment. It is not what D15 says. D15 should be amended to say it.
- But the spike is not closed. C5 shows the Metal arm has no spikes. The wgpu arm is what ships on Android (D5.2) and possibly Linux. The obligation follows the wgpu device layer into S3/S4. Deleting wgpu on Apple does not discharge it.
- Boot needed its own threshold, in milliseconds, not percent. The direct-layer clause — "at least 10% better on cold start by phase **or** on frame time" ([D15](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:616)) — has no guard clause at all, unlike the ink clause. An unbounded boot regression passes it. Percent is also the wrong unit here: device creation 12.9 → 29.6 ms is +129% but +16.7 ms; the pipeline phase is better warm (0.5 vs 2.1 ms) and 60× worse on first launch. The gate should be: warm device-plus-pipeline within 5 ms of the wgpu arm, total cold start p50 ≤ 100 ms with phases summed, first-launch cost handled per Q14.
- Keep with a dated obligation, not delete. The wins are every frame: 21–30% frame time on two workloads, CPU 15–47% lower, footprint ~150 MiB lower, RSS spikes gone ([S0 C5](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:749)). The losses are bounded and mechanistically identified: library load and archive are inside the 29.6 ms device figure and are movable (line 760). Deleting trades a permanent per-frame cost for a fixable launch cost. But "S1's first item" (line 768) is not a gate. D15's "deleted, not kept" consequence should be re-attached at S1: if the carrier's summed cold start is not within the ms gate above after the fix, direct Metal is deleted then.
- Application was loose in two places. First, C4 declared "earned on every median … nothing worse by more than 10%" two sentences after reporting worst-of-five RSS 15–23% above B. The statistic switched mid-paragraph to reach the verdict. Second, C5 kept direct Metal partly "on CPU per frame everywhere and on memory". CPU and memory are not in D15's direct-layer test. The multi-metric judgment is better than the text. The text should be amended — e.g. ≥10% beyond noise on frame time on at least two of three named workloads, none worse beyond noise, CPU or memory allowed as a substitute metric — rather than stretched at verdict time. The header's flat "the two D15 verdicts are earned" (line 4) overstates both.

**What would change my answer**

- Presented-frame data. All S0 verdicts rest on a headless readback bench. §4 defines frame metrics by presented-frame timestamps, p50/p95/p99 and late frames (line 655), and D15 requires "no more late frames". No late-frame number appears in any S0 result. If presenting carriers show more late frames for ink despite the paint-median win, the ink verdict reopens.
- A summed S1 cold start over 100 ms p50 after the archive fix. That triggers deletion of direct Metal under my restated gate.
- The RSS spike reproducing on a presenting wgpu platform (Linux, Android). That breaches the guard where wgpu actually ships.
- Evidence that scroll-heavy workloads like Messages Stress — where direct Metal was within noise at 3.5–6.6% — dominate real use. The keep case then rests on the workloads that matter least.

## Errors in §4's reading of its own numbers

- **"First launch on a machine" is mislabeled.** C5 measured 126.9 ms "on an empty application cache" and admits wgpu's 2.1 ms "is Metal's system shader cache, which no run here could clear, so a first-ever launch was not measured on either arm" (line 761). D5.2 and §8 nevertheless write "127 ms the first launch on a machine" (line 362). The comparison is also asymmetric: arm D cold-application-cache against arm C warm-system-cache.
- **C1 and C4 are unreconciled.** C1 reports a 325 ms first pipeline build from WGSL (line 672). C4 says "a first-ever compile was not measurable" (line 724). One of these labels is wrong, and §4 never says which. All later boot phases quietly use warm numbers.
- **The RSS localization overclaims.** C5 localizes the spike "to the wgpu arm's readback copy" (line 767). The evidence shown localizes it to the wgpu layer. Arm B shares "the same readback path for every arm" (line 704) without spiking, so the readback copy alone cannot explain a C-specific spike.
- **C6 credits the wrong variable.** The 457.3 ms control is WGSL translation plus DX12 pipeline build; the 2.7 ms is state creation from DXBC ([S0 C6](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:785)). Most of that delta is the shader-form decision (D6), not the device-layer decision. The assumption that the driver's compile is inside the 2.7 ms is unverified; no first-draw phase is split out.
- **Cold start is never reported as §4 defines it.** The definition is process start to first presented frame, phases summed, against the budget (line 654). C4/C5 report device and pipeline phases only. C6 reports 406–411 ms absolute, framed as a +46–49 ms delta "by a DWM-synchronized proxy" (line 791) — a `gpu-dev` build, granted, but D15's "the cold-start budget is argued phase by phase" (line 622) has not yet happened anywhere.
- **Dropped caveats.** Excord's percentages come from its start screen; "its chat did not load headless, so its loaded screen is unmeasured" (line 698) is stated in C3 and not repeated where C4/C5 draw verdicts. §4 also never maps "Messages Stress" to the "heavy-list screen" D15 names.
- **Derived precision.** "vello's compute passes cost about 1.2 ms" (line 716) is a subtraction of overlapping ranges (0.35–1.03 against 1.55–1.64). The supportable claim is roughly 0.5–1.3 ms.

## One missing question

**How often is "first launch"?** The pipeline cache is "keyed by the driver and the binary's hash" ([D14](/Users/ccheever/projects/exact2/llp/1149-the-renderer.rfc.md:589)). Exact's delivery pushes signed updates to installed apps routinely, with immediate activation available (LLP 1030). Every shader-changing update, driver update, and OS update re-incurs the 127 ms class of cost. Q14's options all frame it as once per machine. The panel was not asked: at expected update cadence, how many first launches per year does a user pay, can the archive be warmed at update install before activation, and who bounds and evicts the on-disk archives old binaries leave behind?
