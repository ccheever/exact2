**1. Verdict: RIGHT WITH CHANGES**

**2. Overall assessment**

The capability is worth admitting. A presentation hint on `openURL`, implemented with `SFSafariViewController` on iOS, is a sensible small addition. The [RFC](/Users/ccheever/projects/exact2-review-1114/llp/1114.004-in-app-browser.rfc.md) keeps browsing separate from authentication and avoids building a browser engine. Before implementation, I would correct the navigation ownership, lifecycle and agent boundaries, plus one material factual error.

**3. Concerns**

1. **MAJOR — A presentation preference should not bypass the embedding app’s navigation authority.**  
   D2 sends plain `openURL` to the delegate but handles `popup=true` inside ExactKit, explicitly postponing an override. Consequently, an embedder that governs external navigation loses that control when Contract changes one boolean. This conflicts with [LLP 1031 D5](/Users/ccheever/projects/exact2-review-1114/llp/1031-brownfield-embedding.rfc.md:379): navigation outside the Exact surface is an intention the containing app decides how to execute. The current [session implementation](/Users/ccheever/projects/exact2-review-1114/host/apple/Sources/ExactKit/Session.swift:1414) preserves that ownership.  
   **Resolve:** Keep the reusable Safari presenter in ExactKit, but retain the delegate’s decision over both forms. The standalone adapter can choose the standard presenter; this does not require inventing a general browser customization API.

2. **MAJOR — Page facts cannot provide the portable browser-return lifecycle D3/D5 imply.**  
   D3 promises that existing “person came back” behavior keeps working, and D5 forces `hidden`/unfocused until the agent answers `close` on every host. But a desktop popup can leave its opener visible, and the person can refocus the opener while the popup remains open. The RFC acknowledges the visibility difference in §4. [HTML page visibility](https://html.spec.whatwg.org/multipage/interaction.html#page-visibility) describes the document’s actual visibility, and Exact’s [page reporter](/Users/ccheever/projects/exact2-review-1114/host/web/navigation.js:784) keeps visibility and focus independent. The proposed substitute would validate return behavior that production need not exhibit.  
   **Resolve:** Specify `popup` solely as a presentation request, with no portable dismissal or return guarantee. Reporting an actually covering iOS sheet as hidden is reasonable. Keep agent visibility/focus independently controllable through `prefer`, rather than deriving them universally from a pending browser ticket.

3. **MAJOR — The presentation boolean also becomes an agent side-effect switch.**  
   D5 and §9 deliberately substitute only `popup=true`. Thus the proposed clone call, `openURL(url, popup=settings.inApp)`, opens a real browser under the agent when the setting is false, but becomes a held request when true. The RFC’s own verification sequence exercises this split. Although the plain-command gap predates this proposal, carrying it into the newly designed setting prevents the feature from having one dependable agent boundary. [LLP 1069.007]( /Users/ccheever/projects/exact2-review-1114/llp/1069.007-device-capabilities-in-the-agents-hands.rfc.md:64) assigns substitution to the capability, with real device behavior explicitly selected.  
   **Resolve:** Route both forms through the command door in this change. Choose browser presentation after the substitution decision.

4. **MAJOR — The Safari sign-in benefit is false.**  
   The summary, §3.2 and D4 say the sheet uses Safari’s cookies and preserves Safari sign-ins. `SFSafariViewController` has not shared Safari’s cookies since iOS 11; the documentation for the very [Expo API Bluesky uses](https://docs.expo.dev/versions/latest/sdk/webbrowser/) explicitly explains this distinction. AutoFill support does not mean an existing Safari login session carries over. This reverses a material part of the argument for replacing the external-browser experience.  
   **Resolve:** Base admission on convenient in-app reading and return, while acknowledging that an already authenticated website may require signing in again. Keep authentication on `openAuthSession`; do not use it to recover cookie sharing for ordinary content browsing.

**4. What it gets right**

The scope is appropriately small: system browser UI, no page inspection or navigation interception, and no custom desktop browser. Keeping authentication separate is correct. Omitting an app-facing dismissal event also matches [Bluesky’s actual handler](https://raw.githubusercontent.com/bluesky-social/social-app/main/src/lib/hooks/useOpenLink.ts), which uses the browser promise only to catch failure. `popup` is a defensible web-standard presentation hint.

**5. Questions for Charlie**

- **Should popup browsing preserve the embedder’s authority over external navigation?** Recommend yes, using the existing delegate boundary.
- **Should both forms of `openURL` become substitutable together?** Recommend yes; remove plain `openURL` from this RFC’s deferred list.
- **Admit the feature with separate Safari website sessions and no portable return guarantee?** Still recommend yes. Those are the actual tradeoffs; the existing colour and macOS recommendations remain reasonable.
