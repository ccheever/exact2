1. **The landing rule can turn noise into automatic commits (§§7–8).** N=3 is too small for a trustworthy bootstrap interval; three same-sign differences can produce an apparently decisive result. Matching task/model/machine does not establish pairing, and rerunning tasks selected for unusually bad results invites regression to the mean. Repeatedly testing fixes adds false positives. **Change:** randomize and interleave fresh A/B runs within machine/time blocks, predeclare the target metric and minimum worthwhile improvement, and choose replication from several representative cells. Require a confirmation batch before automatic landing; “inconclusive” must be an allowed outcome. Median fidelity alone also needs a critical-failure and completion-rate guard.

2. **Fidelity currently forgives precisely the framework failures it should measure (§5.3).** A cross-platform disagreement does not establish that Exact caused it: authored branches, platform conventions, data, fonts and driver behavior can differ. Even a confirmed Exact bug still makes the delivered app worse. Exempting it inflates Exact’s score against competitors. **Change:** score the observed app against each platform’s requirements regardless of fault; attach attribution separately, including `unknown`. Compare semantic outcomes across platforms, with explicitly allowed presentation differences. Deduplicate bug penalties by root cause so repeated manifestations—or a missing requirement plus its resulting bug—do not receive arbitrary cumulative penalties.

3. **The hidden SPEC makes fidelity partly a mind-reading test (§3).** The brief is deliberately underspecified, the full intent is withheld, and clarification is deferred until Phase 4. A reasonable implementation can therefore lose points for requirements it could not discover. This particularly distorts comparisons when frameworks encourage different defaults. **Change:** disclose every scored requirement and every visual reference needed to satisfy it; keep test inputs and verification procedures hidden. Alternatively, run ambiguity handling as a separate experiment with a fixed clarification mechanism. Clearly distinguish “match these pixels” from “use appropriate native presentation.”

4. **A neutral driver is feasible as shared scenarios over adapters, not as one interchangeable accessibility tree (§5.1).** Test identifiers, DOM nodes and accessibility elements are different interfaces. Exact does map `testId` to UIKit identifiers, but its [Linux implementation explicitly returns “no AT-SPI tree”](/Users/admin/.config/tuft/sessions/1791127507.794399/review/wt-astra/host/linux/src/agent.rs:523). Linux already exists; accessibility is the missing piece. The [documented agent mode also replaces native bars and menus](/Users/admin/.config/tuft/sessions/1791127507.794399/review/wt-astra/docs/agent-pitfalls.md:72). **Change:** first prove one scenario on Exact and a comparator, including normal launch, reset, persistence, keyboard, navigation and screenshots. Define platform adapters and driver-failure outcomes before expanding. T5 additionally needs explicit device or capability fixtures; simulator observation alone cannot establish every camera, notification or haptic requirement.

5. **Experience consensus establishes repeatability, not a validated experience scale (§6).** The plan acknowledges this, but Phase 1 still exits on grader agreement. Several families can share the same bias, and reconciliation can conceal it. Reading the diary first encourages anchoring; cutting every tool result to 40 lines can remove decisive evidence. Penalizing source reading and exempting “agent error” also removes real ergonomics costs from the score. **Change:** label this an *agent-assessed friction proxy*. Make transcript events primary, retain access to full outputs, use framework-neutral anchors, and separate observed difficulty from fault attribution. Without human labels, validate sensitivity using documented failures and controlled perturbations: added retries should worsen scores; diary verbosity or model-name changes should not. Treat other-family medians as diagnostics, not proof of self-favoritism.

6. **The time/token breakdown claims more causal precision than its inputs support (§4.3).** Build time, error-loop time and diary time overlap. File-read execution time is not time spent understanding documentation, and residual wall time includes scheduling, transport and idle waits. Diary-generated context also affects later inference, so subtracting diary writes cannot recover an undisturbed run. **Change:** keep raw elapsed time and billed usage as headlines. Report mutually exclusive execution spans separately from overlapping activity tags; call attributed “lost” time an estimate. Measure diary effects through randomized on/off trials. Preserve cache and reasoning-usage categories where available, and compare token efficiency primarily within a model—token counts across different tokenizers are not a common unit.

7. **“Brief to DONE” rewards stopping early unless completion is an explicit outcome (§4.1).** A fast incomplete app can improve time and tokens; allowing up to five fidelity points of loss per change permits gradual deterioration. Medians can hide one catastrophic run out of three. Also, the runner performs `exact new` before starting the builder, so the proposed setup score does not observe the whole advertised setup experience. **Change:** report completion rate and cost at a fixed acceptance threshold, retaining all failed and capped trials. Treat capped completion times as censored, not ordinary successful durations. Define whether provisioning/scaffolding belongs inside the measurement, standardize warm/cold cache conditions, and distinguish a running long build from an idle harness in the watchdog.

8. **The holdouts and isolation need stronger definitions (§8).** A fixed variant evaluated after every change becomes a validation set once its results influence decisions. Conversely, a targeted improvement need not improve every unrelated holdout; lack of improvement alone is not evidence of overfitting. “Cannot see past diaries” also conflicts with allowing unrestricted checkout access: the cited Beacons diaries live in that checkout. **Change:** distinguish development tasks, recurring regression tasks and fresh audit holdouts. Introduce holdouts before autonomous fixing, reserve some for infrequent evaluation, and enforce access boundaries rather than relying on a fresh directory. Keep the evaluated framework revision immutable and runner records outside builder-writable storage. Treat app content and diaries as untrusted evidence in grader prompts.

9. **Several comparator results would not be comparable as described (§9).** Joint web+iOS authoring time cannot be assigned fairly to an iOS-only SwiftUI result. Summing three native builds measures total effort, whereas parallel delivery wall time follows their critical path. The experience rubric’s CSS expectations are appropriate for Exact, not universally for SwiftUI or Flutter. T6 also inherits the quality of whichever single starting app happened to be generated. **Change:** use separate single-platform and matched-platform-set experiments; report total effort and elapsed delivery time separately. Compare contemporaneous Exact controls with identical builder and judge assignments. Normalize T6 baselines against common functionality and quality criteria, and phrase experience anchors around each framework’s documented behavior.

10. **Automatic landing needs a concrete integration and rollback protocol (§7).** Charlie’s authorization is clear; another approval ceremony is unnecessary. But model reviews and a benchmark win do not establish repository correctness, and independently good fixes can interact after merging. **Change:** retain the [existing five checks and asynchronous per-commit verification](/Users/admin/.config/tuft/sessions/1791127507.794399/review/wt-astra/rules/RULES.md:78), require the reproduction and relevant app verification, serialize integration, and rerun affected checks on the actual integration revision. Roll back attributed failures and pause after repeated bad landings. Explicitly preserve the feature/design and apparatus boundaries. Clarify how mandatory benchmark comparisons fit the rule against adding slow blocking gates.

11. **The budget supports a focused experiment, not the proposed breadth without measured unit costs (§§8–10).** Six tasks plus six holdouts × two or three builders × three repetitions already means 72–108 joint-platform trials nightly. The $1,200 allocation allows only about **$11–17 per fully graded trial**, including two platform judges and the experience panel. The monthly reserve is approximately $9,000: $25 per comparator trial for 360 trials. At that cost, the sweep cannot fit a $4,000 weekend ceiling. **Change:** start with T1–T3, one builder, Exact plus one web comparator, and objective checks. Establish repeatability and one real A/B improvement before adding iOS, a second builder and T6. Use the full grader panel on a calibration/audit sample initially; defer the remaining stacks and platforms. Budget fix authors, reviewers, triage and failed runs too, and reserve in-flight spend before dispatch so parallel jobs cannot overshoot the cap.

12. **The diary and command-log assumptions need correction before the first trial (§§4, 6).** [`docs/diary.md` says `feedback never` means no diary](/Users/admin/.config/tuft/sessions/1791127507.794399/review/wt-astra/docs/diary.md:7), and [the generator embeds that instruction verbatim](/Users/admin/.config/tuft/sessions/1791127507.794399/review/wt-astra/game/new.mjs:296). The proposed setup therefore contradicts itself. The [generated command logger](/Users/admin/.config/tuft/sessions/1791127507.794399/review/wt-astra/game/new.mjs:367) records a coarse verb only when the wrapped command returns; it lacks arguments and readiness events, folds automatic web builds into drives, and may lose interrupted commands. **Change:** explicitly support local diary collection with sending disabled, while preserving ordinary users’ `never` behavior. Capture command lifecycle and render/launch milestones in the external runner; use the existing log as corroboration. Make Phase 0 validate these facts, and remove its stale human-scoring requirement to match §11.
