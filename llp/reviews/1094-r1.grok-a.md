1. **MATERIAL** — D4, §5
   **Problem.** The board the RFC says replaces both hand-built drags is not authorable. A column strip that reorders is a virtualized row list, and that list requires a literal numeric `height`. Each card list inside a column row is a nested virtualized list, which requires its own literal numeric `height` or `max-height`. Percentages and `flex` fail those checks. Both kanban boards size the strip and the card wells from the window (`max-height="100%"`, `height="100%"`, `flex=1`), and §5 tells them to convert to this nested pair and delete `dragColumn` as well as `dragCard`. A card-only group inside a plain horizontal `scroll` does typecheck (`flex=1` is a bound on a list that is not nested). Column reorder at the window’s height does not.
   **Evidence.** `contract/lower/src/collection.rs:139–142` (`lower-collection-cross`), `:186–191` (`lower-collection-unbounded`). D4 keeps LLP 1070’s other row-list refusals and never mentions these two. `kanban/board.contract:63`, `:122`, `:136`; `kanban2/app.contract:671` (`height="100%"`). A virtualized list also has exactly one direct `each` (`collection.rs:72–77`), so the column header, the empty copy, and the quick-add cannot stay siblings of the cards the way they are now.
   **Fix.** Put a compiling board in D4. Either admit a parent-bounded `height`/`max-height` (percentage or `flex`) on the row list and the same on an inner list stretched to that list’s cross size, or state that the column strip stays a plain `scroll`, that only the card lists are grouped, and that `dragColumn` remains until a row list can take the window’s height. Say the header and the quick-add sit outside the card list.

2. **MATERIAL** — D7
   **Problem.** A release that is not over a list has two outcomes in one paragraph. “The pointer leaving the window” cancels the gesture and runs no action. “A drop outside every list” commits to the sticky target, “as SortableJS and both kanban builds do.” Releasing outside the window is both. Those apps commit on release to the last target, including a pointer that has left the window: `panrelease` sends `moveCard` / `drop-card` with the last column, and they never cancel on leave. SortableJS’s pointer fallback does the same (the last placeholder commits on pointer-up). UIKit is the one that fails the drop when the session ends outside a collection (`dropSessionDidExit`, then `animatesToStartingPositionsOnCancelOrFail`).
   **Evidence.** D7’s cancel list and the sticky-target sentence. `kanban/app.contract:225–227` (`dropCard` always edits `drag.to`). `kanban2/app.contract:516–535` (drop uses the last center, with no leave-window path).
   **Fix.** Three endings, in one place. Escape, `pointercancel`, lost capture, resigning key, or the source binding dying: spring home, no action. Pointer-up inside the window over no list: the sticky target’s `reorderdrop`. Pointer-up or a leave outside the window: pick one and cite it — commit to the sticky target, matching the two boards and SortableJS, or cancel, matching UIKit. The current “as both kanban builds do” sentence cannot stay attached to a cancel-on-leave rule.

3. **MATERIAL** — D7, D3
   **Problem.** The hold’s success test does not match the move the action is told to make, and two other session edges are unnamed. Success is “the dragged key sits in the target before `before`.” `before = none` has no such slot. Kanban’s `moveCard` inserts at the end when the `before` key is missing (`at < 0`), so a move that landed still fails the test. At 1 s the ghost springs home onto a source slot that no longer has the card, which is the spring-back-then-jump this hold exists to stop. UIKit’s drop placeholder waits until the data source commits and has no 1 s kill. Escape is a cancel “no action runs,” but the action has already been sent once the hold starts. A second lift during the hold is unnamed, so two sessions can exist. The outer-row pin in D4 is described for the lift, not for the hold and the spring home; LLP 1070 destroys an inner list when its outer row retires.
   **Evidence.** D7; D3’s `match before { none => "" }`; `kanban/app.ts:302–309`. Current preview pin ends with the preview (`runner/src/instance/collection/reorder.rs`, `runner/src/runner/reorder.rs:148–218`).
   **Fix.** Define the three endings against the data. `before = some(k)`: the key’s successor in the target is `k`. `before = none`: the key is the target’s last key. If the key is in the target at any other index, move the ghost onto that row instead of springing home. Cancel applies only until `reorderdrop` runs; during the hold, Escape does not retract the send. Refuse a new lift while the session is `holding` or `cancelling`. Keep the source column’s pin until the session ends, including the spring.

4. **MATERIAL** — D1, D6
   **Problem.** “Keys are unique across a group. The runner opens no gap in a list that already has the dragged key” includes the source list, which always has that key. Read that way, a grouped list never opens a gap on its own rows. A foreign list that already shows the key is also an unfinished rule: it may still become the target, and the drop may still fire. The app then inserts a second row with that key. A collection index rejects a duplicate and leaves the list unchanged, so the new board does not appear, the hold cannot see the slot, and the ghost springs home over data that now contains two copies.
   **Evidence.** D1; D6’s “excluding nothing in a foreign list.” `runner/src/instance/collection/index.rs:27–39` (`DuplicateKey`). `index_tests.rs:563` (duplicates leave the index unchanged).
   **Fix.** The source list is the exception: it gaps around the lifted key, as today. A different list that already contains `item` is not a target; the sticky target stays, and the journal notes it once. `reorderdrop` does not fire there.

5. **MATERIAL** — D8
   **Problem.** Cross-list keyboard and assistive moves do not determine `before`, and they cannot see a column that is not mounted. After Space, a cross-axis arrow “moves to the nearest grouped list that way, by viewport boxes, at the row nearest the ghost.” A virtualized row list has no box for an off-screen column, so ArrowRight from the last mounted column stops even when another column exists. Custom actions are “one drop without a lift,” so there is no ghost and no nearest row, yet they must still call the same `reorderdrop(item, before)`. Kanban’s hand-built alternative inserts at the same index clamped to the destination (`stepCard` left/right). LLP 1070 §4.7 already realizes an unmounted row before an accessibility move. Within-list “Move earlier” / “Move later” are determined (the previous key, or `none` at the end) and can stand.
   **Evidence.** D8. `kanban/app.ts:311–320`. `kanban/app.contract:167–171` (arrows on the card call `stepCard`). LLP 1070 §4.7, accessibility paragraph. dnd-kit moves toward a colliding item only while a drag is live; UIKit’s accessibility move is an index change inside one collection.
   **Fix.** Previous and next list are the group’s lists in tree order, not the mounted viewport boxes. An unmounted neighbor is realized first (LLP 1070 §4.7), then the drop runs. `before` is the destination key at the same index, clamped to the end. The same index rule is what “Move to previous list” and “Move to next list” send, with no lift and no hold. On a hold that times out or fades because the key is gone, focus returns to the source grip; it moves to the destination grip only when the move showed.

6. **MATERIAL** — D9, D10
   **Problem.** `elementFromPoint` plus an untransformed `frame()` is enough for a hand-built drag, and the text aims it at the point kanban2 spent half an hour rejecting. D10 says a drag tests `clientX`/`clientY`, or `offsetX` added to `frame().x`. Those are the pointer. On a left-edge grip the pointer is still over the source column while the card body covers the next one. Kanban2’s fix was the card center, `base + delta + size/2`, which is also the point D5 uses for the built-in ghost. `clientX`/`clientY` land on `PointerEvent` (`pointerdown` / `pointermove` / `pointerup`). Both boards drag with `pan`, whose payload is `dx, dy` only, so the pan path never sees `clientX`.
   **Evidence.** D5 (ghost centre); D9–D10. `docs/contract-grammar.md:502–508` and `:554–576` (`pan` is two numbers; `PointerEvent` is the pointer events). `kanban2/DIARY.md` item 3 and `app.contract:497–502` (center), `:541–549` (`grabColumn` stores `offsetX` because `pan` will not). `kanban/app.contract:210–211` (same center). `frame()` of a ghost positioned with `left`/`top` already includes that offset, because it is layout; a `translate` does not (kanban2’s column, `app.contract:671`).
   **Fix.** State the hand-built point as the visual center: `frame(id)` of the dragged node, plus the pan delta the action stored, plus half the box. `elementFromPoint` of that point returns the topmost id (a card id is looked up in the board; column padding returns the column). `clientX`/`clientY` stay the pointer, for hits that really want the pointer. Keeping `frame()` untransformed is the right parity rule; the recipe has to add the delta the author wrote.

7. **MINOR** — D1, D6
   **Problem.** The drop sees the `each` sequence, which is not what either board measures today. Kanban hides filtered cards with `when card.visible` inside the row, so those keys would still take slots and open gaps; the hand-built drag skips them with `k.visible`. The hit target is the list scrollport. The column header and the quick-add sit outside it and act as a gutter: the sticky target does not switch while the ghost’s center is on the header, whereas both boards hit-test the whole column frame. An empty well with no height never becomes a target.
   **Evidence.** `kanban/board.contract:136–159`, `app.contract:218`. `kanban2/app.contract:671–721` (header 52 px, footer 48 px, hit test uses the column box).
   **Fix.** In the board recipe: `each` over the visible cards; give the card list a `min-height` so an empty column is a target; expect the header and the footer to keep the previous list.

8. **MINOR** — D8, §5
   **Problem.** The host keyboard path attaches only to a grip with no `press` and no `key` of its own. Kanban2’s grips are `press=gripTap` (a no-op) plus `pan`. Leaving that `press` on the grip keeps the app’s keys and never installs Space, arrows, or the custom actions. The web grip is a `box` with `tabindex=0` and no role, so the focus stop is a generic element.
   **Evidence.** D8. `kanban2/app.contract:324–325`, `:674`, `:695`. The D1 example sets `aria-label` and not a role.
   **Fix.** Say the conversion deletes `press`, `pan`, and `key` from the grip. The host sets `role="button"` on the grip it focuses.

9. **NIT** — §2, D1
   **Problem.** “SortableJS’s model” is the shared group name, `from` / `to`, and the sticky placeholder. SortableJS’s `group` is also `pull`, `put`, and `clone`, which this RFC correctly omits. UIKit’s comparison (gap, placeholder, no system drag on iPhone) matches D5–D7.
   **Fix.** Say the borrowed part is the shared name and one list-to-list move, and that a group has no pull, put, or clone.
