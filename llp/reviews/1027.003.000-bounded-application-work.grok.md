## HIGH — D6: end watermark equal to start does not mean “nothing changed”

**Where:** plan `:285-290`; `apps/messages/snapback-client.ts:129-157, 184-191`.

**Failure.** `acquire` can apply records and finish with the same watermark it started with:

1. `observe_store` sets `reset=true`, local `watermark=0`, then catch-up pages are applied (`:144-148`).
2. Catch-up lands on the **same** numeric watermark as step 1.
3. A skip condition of “watermark did not advance” does not re-`read()`, does not `settle`/`restore`, and the UI keeps the pre-reset `held` map.

Snapshot pages with `page.snapshot && page.more` also `apply` and `continue` **before** `watermark=Number(page.watermark)` (`:153-155`). If that `acquire` then errors, `sync`’s `finally` runs with no watermark advance and, today, still rebuilds from `read()`. After D6 it would not.

Idle empty `/sync` pages: watermark unchanged **and** no records applied — skip is correct. Outbox settle is a separate signal and is required.

Watermark is **not** a sufficient “nothing changed” bit. The plan’s “or applied any record” is the actual predicate; “`acquire()` already tracks the watermark it applied” is not.

**Fix.** `acquire` returns `(appliedAnyRecord || reset || snapshotCatchup || outboxSettledThisTick)`. Only then `read()` + canonical compare. Treat store reset as applied even when the final watermark matches the start.

**S3.1 hole.** “Ten idle ticks issue zero record queries” passes on the happy idle path while a reset tick is skipped. Add a reset/catch-up fixture that asserts exactly one `read()` / one `restore`.

**Confidence:** high that watermark-only is wrong; medium-high that the written skip will be implemented as watermark-only.

## MEDIUM — D3: byte bound is fine; OFFSET is not O(N); the long lease fights D5

**Where:** plan `:157-184, 221-228, 496-498`; `host/web/storage-worker.js:85-99`; `host/apple/src/abi.rs` is unrelated; native cap is `ibex2-sqlite` `MAX_RESULT_BYTES` 16 MiB, same shape.

**Byte bound (not a defect).** `50 × 3 × (160 + 20_000)` ≈ 3.0 MB of title+body UTF-8, plus `substr` and 24-byte cells, is still ~3 MB vs 16 MiB. Extra `substr(body,1,200)` in the search SELECT is redundant (the full `body` is already there) and does not threaten the cap. Empty query must **not** take this path (`''.includes('')` is true for every row); the plan’s “non-empty query” split is required.

**Failure — OFFSET.** Chunks `LIMIT 50 OFFSET 0,50,…,950` on `ORDER BY pinned DESC, id DESC` with **no** `(pinned, id)` index: each chunk is a full table walk + skip. Twenty chunks ⇒ on the order of \(N^2/\text{page}\) row visits, and **twenty** full-body scans vs today’s **one**. §9 still calls this O(N). At 1,000 × 20k-unit notes this is slower than the path it replaces, and it holds the web exclusive lock (`storage-fs.js:57-82`, `ifAvailable: true` → `EBUSY`) for that whole time.

Astra’s sibling already refused OFFSET (“never an offset”) and used `(pinned, id)` keyset. r2 dropped the **UI** pager (correct; 1,000 rows are already capped) but kept OFFSET for the scan.

**Lease.** D3 holds one TS connection for the scan; D5 says keep the lease short so the Rust backup owner can acquire the file. On web that connection **is** the exclusive Web Lock until `close`. On native, `ibex2-sqlite` uses SQLite locks + **5s `busy_timeout`**, not a connection-lifetime exclusive. Same-tab `busy` includes `pending(library)`, so the backup **button** is off; another tab’s `sqlite.open` or an agent `backupNotes` still hits `EBUSY` / 5s wait. OFFSET makes that window longer than today’s single `library` query.

OFFSET is complete and stable **only** while no writer interleaves. The JS `serial()` gate covers TS sources only (`backupNotes` is the Rust Mixed owner). Row contents are stable because backup only `SELECT`s; use a single `BEGIN` + keyset anyway so completeness does not depend on that.

**Fix.** One connection, one read transaction, keyset:

`WHERE (pinned < ?) OR (pinned = ? AND id < ?) ORDER BY pinned DESC, id DESC LIMIT 50`

Add the `(pinned DESC, id DESC)` index if the query plan still walks bodies to skip. Do not call this O(N) until the plan shows a single pass.

**Confidence:** high on OFFSET complexity and the D3/D5 lease contradiction; medium that N=1,000 is user-visible on the slowest host.

## MEDIUM — D2: the declared excerpt deviation is not the only one, and it is understated

**Where:** plan `:137-155`; `apps/fieldnotes/app.ts:39-41, 48-50`.

Today: `String(row[2]).replace(/\s+/g,' ').slice(0,100) || 'An empty page.'` (UTF-16). Proposed: JS collapse+slice on `substr(body,1,200)`.

SQLite `substr` on TEXT is **UTF-8 code points**, not UTF-16. `title.length` / `body.length` are UTF-16. The “1,000 × (160 + 200) UTF-16 units → ~600 KB” line is therefore the wrong unit (200 code points of supplementary-plane text is 400 UTF-16 / 800 UTF-8 bytes). Still ≪ 16 MiB, so this is not the library overflow.

**Unchanged, if they still JS-slice the prefix:** `'An empty page.'` — only an empty body is falsy; whitespace collapses to `" "`, same as today. Surrogate splits of the **displayed** 100-unit excerpt: the first 100 UTF-16 units always lie inside the first 200 code points, so the cut matches today’s `.slice(0,100)` except when collapse of the prefix is shorter than 100 units.

**Extra / understated deviation.** Plan says leading whitespace “behave[s] exactly as they do now” **and** that a whitespace-heavy 200-char prefix is the one exception.

Body = `" ".repeat(200) + "Meeting notes for Tuesday"`:

- today → `" Meeting notes for Tuesday"`
- prefix of 200 spaces → `" "` (not `'An empty page.'`, and **none of the real text**)

That is wrong content, not a “shorter preview.” Any first-200 **code points** whose collapsed form is &lt; 100 UTF-16 units (whitespace runs, not only “~100 characters of runs of whitespace”) diverge.

**Fix.** Either keep reading until `replace(/\s+/g,' ').slice(0,100)` is stable or the body ends, or state the product change honestly and pin S1.4 on `200 spaces + real text → " "` vs today’s text. Do not claim leading whitespace is unchanged.

**Confidence:** high on `substr` vs UTF-16 and on the 200-space case; high that the fallback is **not** an extra deviation.

**Fix.** Spell S1.6 as “after process-local schema init, a `library`/`note` query issues no `execute` and no `persist`.” Run CREATE in the same missing-table retry for `restoreNotes`/`deleteNote`. Keep leases per operation except D3’s one search transaction.

**Confidence:** high on first-read vs S1.6; high on restore + missing table.

- **D5.** Confirmed on all four sub-points. r3 states S1.6 as "after process-local

- **Acceptance holes.** All six accepted. Every one is rewritten in r3: S1.5 asserts an

  tick, S3.2 and S3.4 gain unread and reaction operations, and S4 drops "leave it open"
  as a way to finish.
