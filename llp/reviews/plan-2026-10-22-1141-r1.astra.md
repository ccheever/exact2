**Strengths**

The direction is sound. Ports expose interactions, integration costs and workloads that small specifications miss. [LLP 1125, Summary and §1](/Users/ccheever/projects/exact2-wt-review-1141/llp/1125-a-transport-midi-and-the-small-pieces.rfc.md) provides convincing evidence: MIDI timing, backgrounding and device lifecycle requirements emerged together.

The replay/fresh-port distinction (§4.6) is particularly valuable: it separates runtime improvement from changed builder behavior. Independent coverage checks, reproduction before fixing, and fixing a reusable class (§§4.3–4.5) are also strong.

Ports suit fidelity, integration and realistic runtime workloads. Complement them with isolated startup/rendering/allocation benchmarks for causal diagnosis and scaling; physical-device measurements for energy and touch; the authoring bench for inexpensive repeated cost measurements; and the bake-off for novel specifications. Porting benefits from existing design and reusable source, so it cannot alone establish the best way to build a new app.

**Concerns**

1. **BLOCKING — Graduation can certify failure (§§2, 4.7).** Coverage is measured but has no mandatory bar. Matching a weak native port can qualify, and merely explaining every remaining miss also permits graduation. A cheaper incomplete app can therefore “win.” Require independently verified completion of a predefined minimum slice, explicit fidelity acceptance criteria, and no unresolved critical correctness failures before comparing cost or performance. Separate **passed**, **closed with accepted limitations**, and **inconclusive**; only passed contributes to win rates. The first euxy arms had unequal coverage, illustrating this risk ([RESULTS.md, “Coverage”](/Users/ccheever/projects/euxy-compare/RESULTS.md)). Preserve that result as discovery evidence, without treating its cost ratio as equal-quality productivity.

2. **MAJOR — The experiment does not identify framework improvement reliably (§§4.2–4.6).** Keeping an app’s model fixed helps, but one model per app confounds model and workload; a second fresh build still varies independently of Exact. Pin model version, effort, CLI, tools, documentation, dependency versions and cache policy. Use isolated sessions without previous solutions. Starting simultaneously on separate simulators does not isolate shared-machine compilation or service contention.

   Use one pair for discovery. For a consequential authoring claim, start with **3–5 independent pairs on the same pinned versions**; do not count launches as builder repetitions. Cross at least two model families over overlapping workloads. Report distributions and paired uncertainty, retaining failures and timeouts. Choose further sample sizes from observed variance and the smallest worthwhile improvement; 3–5 is a pilot, not automatic proof. Predeclare stopping rules instead of repeating until two favorable outcomes occur.

3. **MAJOR — Some instruments measure implementation structure rather than user experience (§§2, 4.0, 5).** Half the final layer count is not a comparable readiness definition across renderers. Euxy’s Expo first frame was a splash at 316 ms, with “UI built” at 1,241 ms ([RESULTS.md, “Cold start”](/Users/ccheever/projects/euxy-compare/RESULTS.md)). Define identical observable milestones: meaningful content displayed and a named control successfully usable. Keep layer counts as diagnostic evidence.

   Separate input-to-feedback latency from completion and animation duration. Specify workload size, interaction timestamps and frame measurements. Start with 20 interleaved launches and approximately 20 journey repetitions across multiple sessions; estimate uncertainty against the decision margin and repeat when inconclusive. Preserve tail observations. Calibrate probe overhead, and validate simulator rankings on physical iPhones before making device-performance claims.

4. **MAJOR — Bars need absolute budgets, meaningful cost and resource measures (§2).** The 1.1× startup and 1.2× memory ratios are reasonable provisional targets, but insufficient: a slow native implementation makes them easy. Compare runtime with a vetted original/native reference as well as the agent-built comparator. Reconcile startup with [RULES.md, “Time budgets”](/Users/ccheever/projects/exact2-wt-review-1141/rules/RULES.md)’s 100 ms interactive-first-frame target, explicitly defining any different scope.

   Replace literal “0.0% CPU” with no attributable recurring idle work and a measured noise allowance. Add peak memory, retained-memory growth across repeated journeys, active-work energy, and workload scaling. Define shipped-size accounting and an absolute ceiling; template-plus-native permits unexplained overhead. Report billed dollars alongside token categories, plus gross elapsed time and time excluding service interruptions. “Cheap” should mean cost to verified completion, with unsuccessful attempts included.

5. **MAJOR — Fidelity has competing authorities and weak grader calibration (§§1, 4.1, 4.3).** An agent-built native port is a productivity comparator; its toolkit does not make every decision authoritative. The original may itself have platform defects. Before building, identify intentional authored design, platform-owned behavior and known original defects, following [LLP 1115, Summary and §2](/Users/ccheever/projects/exact2-wt-review-1141/llp/1115-write-the-web-ship-the-platform.principle.md).

   A/B labels cannot guarantee blindness when presentation or tooling reveals Exact. Hide technical identifiers, record stack guesses after grading, and examine whether recognition tracks scores. Regrade a random 10–20% with reversed order; use a second independent grader for graduation and disputed findings. One duplicated pair cannot establish noise across the portfolio. Screenshot-region counts should locate differences, not determine their importance.

6. **MAJOR — Generalization and comparator coverage are underspecified (§§3, 4.2, 4.4–4.6).** Merely naming another possible consumer does not demonstrate a general fix. Exercise a materially different consumer and reserve workloads from tuning. Allow overlap in the coverage matrix: independent implementations of the same capability are valuable replication, despite §3’s “new coverage” rule.

   Native escape deserves investigation, but a well-supported optional module can be the correct framework boundary. Preserve unresolved findings with evidence rather than dropping intermittent failures because reproduction failed once. Rebench frozen original and comparator artifacts alongside Exact; historical numbers cease being comparable when machines, OS versions or fixtures change. Define the web comparator explicitly. An existing Expo original supplies runtime evidence, not an Expo agent-authoring baseline; React productivity also needs a corresponding arm or clearly scoped bake-off evidence.

7. **MAJOR — Cadence lacks an economic stopping rule (§9).** The listed sequential stages total roughly **5–9 hours elapsed**, with more aggregate machine time for parallel arms, before fixes. Cache-heavy token totals are not a dollar budget. “Every screen” also becomes expensive for a small slice of a large original; define the slice before exhaustive capture.

   Run a bounded three-app pilot, retain the two-lane limit, and measure baseline preparation, grading, maintenance and fixes separately. Continue when it produces reusable improvements confirmed elsewhere; pause a lane when successive batches yield little benefit. Use replays after runtime changes and fresh builds when authoring behavior is the hypothesis. Keep the bake-off as the broader comparison instrument rather than funding full repeated ports for every small documentation change.
