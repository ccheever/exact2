READY WITH CHANGES

## Overall assessment

The overall design is the right one for this repository, and the vocabulary stays as it is: parse the file into the kernel's own SVG nodes, resolve it with `kernel::svg::scene::resolve`, rasterize it the way each host already rasterizes an island, and hand the pixels to the raster pipeline. It treats the web as the oracle, adds no new vocabulary, and reuses the resolver and the island renderers rather than adding a third SVG drawing path. However, several of its claims about the code are wrong in ways that change the D3/D4 seams:

- where the resolver can run on Apple;
- how the decode plan sizes a picture;
- whether Linux can draw on its decode thread;
- what a browser does for `object-fit: fill`, for an SVG with only a `viewBox`, for `<style>`, and for animation.

None of these needs a different architecture. Each needs a rewritten paragraph, and the author should fold them before implementing.

## Strengths

- **One drawing path per host.** §3 and D3 rule out a separate rasterizer. "A picture and the same content inlined never differ on one host" is the right invariant, and the reason given for not building a shared Rust rasterizer (the hosts did not build islands that way) is honest.
- **D1, the picture model.** Treating the SVG as a raster means `object-fit`, `load`/`error`, the budget, the queue and the cache all apply unchanged. This matches how the browser treats an `<img>`, and avoids giving the image node a second kind of content.
- **The citations check out.** `kind_for` lists the SVG node types (`host/apple/src/host.rs:1435`). The `d` grammar is shared (`host/apple/src/icon_path.rs:25`, `host/linux/src/paint/svg.rs:84`). `SvgIsland.render` builds an `SvgScene` from the op's element JSON and calls `sub.root.render(in:)` (`SvgIsland.swift:161-183`). The 25% re-ask band exists (`RasterLoader.swift:576`), and `requestedPixel` is the box times the display scale.
- **§7 staging** puts Linux before Apple and retires the warning only when both hosts are done.

## Concerns

**1. The island module cannot hold the resolver (material).** D4 puts the parser into `libexact_svg.dylib` and has `exact_svg_file_scene` return "the same JSON the `svg` op carries, parsed and resolved in Rust". Two things block that:
- `resolve` takes a `&Kernel` and a `NodeRef` (`kernel/src/svg/scene.rs:258`), and the op's JSON is written by `exact-apple` (`host/apple/src/svg.rs`), which is in the core, not the module.
- `host/svg-raster/Cargo.toml` deliberately keeps the kernel out of the module ("which a loaded module would otherwise compile whole (LLP 1036.000 §12)").

As written, the module would have to compile the whole kernel and the Apple serializer, which contradicts the "the module grows by the parser's size" claim in §5. **Resolve:** decide where each step runs:
- the parser in the module, emitting a flat node and attribute list;
- the core building a scratch `Kernel` from that list (it accepts CSS text through `StyleValue::Text`);
- the core resolving and serializing the scene.

Alternatively, put the parser in the core and state the size cost against LLP 1047.

**2. The module reach rule for computed sources (material).** A build whose plan is fixed leaves `libexact_svg.dylib` out unless `exact_runner::svg_islands` holds (`bake/src/receipt.rs:605`, `host/apple/build.mjs:1044-1047`). D4's "a computed source opens it at first use" would then fail in production. **Resolve:** name the new reach rule. It probably means any `image` whose source is not a literal, which covers most apps with remote images, so §5's "an app that does not pays nothing" needs restating.

**3. `object-fit: fill` and the decode plan's ratio (material).** For an SVG, CSS Images 3 §5.5 makes the concrete object size under `fill` the content box. The SVG viewport is then the box, and `preserveAspectRatio` letterboxes inside it. `RasterDecodePlan`, however, always plans at the natural ratio (`RasterImage.swift:280-291`; Linux `image.rs:680-705`). So a picture planned that way and then placed by `fill` stretches, which is the opposite of the browser for the CSS initial value. D3's "object-fit then places the raster" is only correct for `contain`, `cover`, `none` and `scale-down`. **Resolve:** for an SVG under `fill`, the decode key is the box's pixel width × height, not a natural-ratio scale. The re-ask must also trigger on a ratio change, not only when the longest side moves 25%.

**4. Decode plans clamp to the natural size (material).** Apple uses `self.maxPixel = min(maxPixel, longest)` (`RasterImage.swift:287`). Linux caps the scale at `.min(1.)` and the bucket at `.min(longest)` (`image.rs:690-698`). An SVG with `width="24"` shown in a 96 pt box at 3× would be drawn at 24 px and scaled up, blurry. D1's "a 3× screen gets a 3× raster" is false with the plan as it stands. **Resolve:** state that an SVG plan is bounded by the existing caps (4,096 px, the budget, the 16 M-pixel island cap) and not by its natural size.

**5. Linux cannot paint on its decode thread as built (material).** `Painter` holds `Rc` fields and a `Box<dyn Backend>`, and its text engine is `Shared = Rc<RefCell<TextEngine>>` (`host/linux/src/text.rs:568`). The island child painter is built from the parent painter's text (`paint/island.rs:41-47`). D4's "paints the scene into a pixmap on its decode thread" is therefore not available for any scene with `text`, and §6 Q4's "Linux has the simpler seam" is doubtful. The decode workers also have no session kernel, so the scratch-kernel point in concern 1 applies to Linux too. **Resolve:** either paint on the paint thread, which is the same question as Apple's §6 Q1, or rasterize on the worker only when the scene has no text.

**6. Refusal policy and `<style>` for files (material).** D2 says that what the inline `svg` refuses, the file refuses too, and it drops `style` elements, citing LLP 1055.000 §7. That §7 gives its reason as "Contract has no selectors; its `style` sets are the stylesheet", which applies to authored Contract, not to a designer's file. Illustrator's default export styles through `<style>` and `class` (`.cls-1{fill:…}`) and wraps content in `<switch>`. Exports also use `em` units and editor-namespaced attributes. A browser draws all of these. Dropping `<style>` paints black shapes, which is the motivating case drawn wrong. Refusing on `switch` or `em` blanks the whole file. **Resolve:**
- for files, read `<style>` with type, class and id selectors and no combinators;
- take `switch`'s first child that passes its tests;
- resolve `em` against the initial 16 px;
- ignore foreign namespaces;
- separate "dropped, with a warning" from "fails the build" by whether the picture would still be right.

**7. Natural size and the browser (material, oracle).** D4 takes the natural size from `width`/`height`, "else the `viewBox`, else 300×150". Browsers do not take a natural size from a `viewBox`. An SVG with only a `viewBox` has a natural ratio and no natural size, so an inline `<img>` of it fills the containing block's width (CSS 2.1 §10.3.2). Percentage `width`/`height` also give no natural size. The kernel seam `exact_intrinsic(w, h)` cannot express "ratio only". **Resolve:** either add a ratio-only report to the kernel seam or declare the deviation in LLP 1001's manner. Then change §4's test "natural size from the `viewBox` alone" to match.

**8. The secure-mode citation is wrong (material, it justifies a decision).** SVG Integration defines `<img>` and CSS image references as *secure animated* mode, and all three engines animate SMIL and CSS animation in an `<img>`. "Secure static" is a different mode, and "Safari does not" animate appears to be incorrect. **Resolve:** present time-0 sampling as a declared deviation chosen for cost and determinism, not as matching Safari. §6 Q3 then becomes a ruling on that deviation.

**9. Bounds on untrusted input (material for remote sources).** A remote SVG is adversarial in a way an authored inline `svg` is not. The resolver bounds `use` depth at 16 but not fan-out (`scene.rs:787`), so ten `use`s of ten `use`s expand exponentially. The 64 MiB encoded cap bounds bytes, not work, and DOCTYPE internal entities (old Illustrator exports have them) invite entity expansion attacks. **Resolve:** state limits on elements, resolved items and filter work, refuse entity declarations beyond the predefined five, and make exceeding a limit the named `error`.

**10. `render(in:)` fidelity across a whole document (minor, verification).** Apple's documentation for `render(in:)` says layers with `mask`, `filters` or `compositingFilter` are not rendered. LLP 1011 §4 records `render(in:)` dropping a mask in this repo, while LLP 1055.000 stage 8 reports clips surviving in islands. Apple's SVG uses `CALayer.mask` for gradient fills, `clipPath` and masks, and `compositingFilter` for macOS blending. Islands have so far rendered small subtrees. A whole document is a broader test than D3 assumes. **Resolve:** make §4's conformance row draw every `svg-gallery` fixture as an `image` and compare it with the same fixture inline on the same host, as well as with Chrome. That makes §3's invariant a check, rather than one file at nine sizes and fits.

**11. Smaller corrections (minor).**
- D3 puts "each host rasterizes an island's source with the rasterizer it already has" in quotation marks as LLP 1055.000 D2. Those words are not in that document, and its D2 table still says tiny-skia on Apple. Cite "Stage 8 as built" instead.
- The header has no Implementer line (RULES.md: "A spec needs an implementer and a date").
- D5's "beside the name gate" in `receipt.rs` is a Bun asset inventory. The compiler already reads SVG files (`icon_svg.rs`) and owns `lower-image-svg`, so it is the more natural home for the build check, in one place.

## Suggestions

- For §6 Q1, look at `SvgFilterLive`: it already renders sub-scenes off the main thread when they have no text ("a sub-scene with text stays on the main thread, where the session's fonts are"). Off the main thread unless the scene has text is an available first stage on Apple, and the same rule fits Linux (concern 5).
- Measure §5's costs ("under a millisecond", "a few") on a real exported illustration with thousands of paths before choosing between the §6 Q1 options. Building that many `CAShapeLayer`s on the main thread may cost much more than drawing them.
- Cache the parsed and resolved document per source, so a resize re-asks only for the rasterization.
- Say in one line why an Xcode asset-catalog SVG was not used (it covers bundled assets on iOS only, and is drawn by a different renderer than inline SVG).

## Open questions

- Does `clock settle` wait on the main thread in a way the D4 worker→main→worker hop could deadlock?
- Should a resize that changes only the box's ratio under `fill` re-rasterize every frame of an animated resize, or is it held to the 25% band?
- `svg-file` under `host/`, with the compiler (`icon_svg.rs`) as a client: is that dependency direction acceptable, or does the crate belong beside the kernel?

Rewrite the D2 refusal policy for files (concern 6). Correct the oracle claims (concerns 7 and 8) and add input bounds (concern 9). Then implement stage 1 (`svg-file`), and widen the conformance row to the gallery fixtures before stage 3.
