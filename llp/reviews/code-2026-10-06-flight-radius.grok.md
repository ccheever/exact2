Next I’ll check how `applyBoxLayer` treats radius versus clip, and whether a gradient or a macOS backing layer still keeps the lift-time corner.**NOT READY.** The root cause is right, and the solid-color bubble this fixes will land rounded. On iOS a one-layer gradient still keeps the radius copied while the flight was holding the layer's corner, so that fill stays at the lift-time shape.

The cause matches the code. `applyBoxLayer` skips `layer.cornerRadius` while `flightLook != nil` (`BoxLayerIOS.swift:257`, `BoxLayerMac.swift:165`). The old land put back the radius saved at lift. A clip flight never writes the view's radius at all (`showFlight` rounds the clip), and the arriver's first display often runs only after lift has set `flightLook`, so a style applied in that same commit never reaches the layer. Re-running the box pass after `flightLook` is cleared is the right repair for a layer-painted fill.

Borders, shadows, vibrancy, materials, and clip boxes already follow the style during flight. Their radius writes are not gated on `flightLook`. A press ease is a transform animation: iOS removes it at lift (`FlightsIOS.swift:266`), and the box pass sets the radius inside a transaction with actions disabled. An interrupted flight still reads the clip's live radius (`FlightsIOS.swift:97-101`, `FlightsMac.swift:88-94`), or, for an image, the radius `showFlight` is interpolating. Those paths stay valid.

`forgetFlight` and `resetFlights` drop the view. Reduced motion returns before lift writes `flightLook` or a radius. The roots-changed branch calls `restore` on both hosts. `landFlights(inside:)` goes through `landFlight`. None of those miss this corner repair.

Leaving `masksToBounds` alone for a clip flight is right on both hosts. The clip flight never writes the view's flag; `syncScroll` / `applyStyle` can, and restoring the lift snapshot would undo that. On macOS, assigning a new non-zero `cornerRadius` on a view-backed layer sets both `masksToBounds` and `clipsToBounds`; assigning `0` leaves them. `applyBoxLayer` only puts a non-zero radius on that layer when `clipsToBounds` is already true, so the forced clip matches an `overflow: hidden` box. A visible overflow keeps radius `0` on the backing layer and the fill on `boxFill`, which is updated even while flying.

The new tests cover that layer-radius symptom. They would have failed before this change: an arriver rounded in flight, one whose radius changes (including to unequal corners, iOS), and one landing with its slot gone. They drive `applyBoxLayer` directly and assert `layer.cornerRadius` only.

A clip flight's bounds are still the last shown slot size; a frame op earlier in the landing batch has updated `f.geometry` and the slot, not the view. Pixel radii that fit both sizes match. A percentage radius, or one CSS must reduce to the old side, stays computed for the in-flight bounds, and iOS does not run `applyBoxLayer` from `layoutSubviews`. 3. **should-fix** — `host/apple/Sources/ExactKit/IOS/FlightsIOS.swift:181` and `host/apple/Sources/ExactKit/Mac/FlightsMac.swift:167`. Image flights still put back the lift-time `masksToBounds`. That correctly undoes the flight's forced clip when overflow did not change. A style applied while the image is flying can change overflow first: on iOS `clipsToBounds` is `masksToBounds`, and on macOS each new non-zero `cornerRadius` in `showFlight` turns `clipsToBounds` back on. Restoring the snapshot then undoes the newer overflow. On macOS that also makes `applyBoxLayer` treat the view as clipping, so it keeps a backing-layer radius. Before the box pass, set the flag from the current overflow (the same rule as `syncScroll`), not from the lift snapshot, and on macOS set it again after `applyBoxLayer` when that pass's radius write turns clipping back on.
