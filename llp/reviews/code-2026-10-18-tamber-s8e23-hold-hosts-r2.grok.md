# Review round 2, LLP 1121 stage 8 E2 (Apple) + E3 (Linux/Android) held states, Grok 4.7 (xhigh)

**RIGHT WITH CHANGES.** Round 1’s model is in place on both hosts: the hold is separate from the real press and the real looks, a press already down is taken over, hardware keys and Mac clicks and real touches let it go, disabled nodes and ancestors refuse, rows are CSS and answer for the named node, a generation swap lets the hold go unsaid and reholds under the same plan digest, and a frame for another plan is unsaid. Linux `planDigest` is the runner’s SHA-256 of the encoded plan (`inspection_digest`), the same value as the `sites` op and Apple’s `exact_plan_digest`, sent on registration and status, which is what the server stores and puts on the next hold frame. No touched source file is over 1499 lines. Android runs this Linux presenter, so the Linux findings below are Android findings.

1. **BLOCKING** — An iOS agent tap does not let a hold go. `AgentIOS.tap` (`host/apple/Sources/ExactKit/IOS/AgentIOS.swift:762`) is the one-shot click: it sends `fingerPointer` and `lift` (`AgentPanIOS.swift:236`), and `lift` calls `presenter.press`, but nothing calls `HeldState.input`. The same hole is on the host-activation returns above that (`AgentIOS.swift:552` inline, `:571` confirmation, `:577` grouped list, `:583` control, `:595` segment, `:600` chrome, `:604` swipe action) and on a pan’s pointer-down (`AgentPanIOS.swift:379`), which never reaches the `HeldState.input` added at `:365` (that line runs only for `tap … down` on a non-pan). The hold stays painted and the server is not told `input`, while the click still runs. Mac is fine: the agent posts a real `NSEvent` and `ExactViewMac.swift:281` sees it. Linux is fine: `pointer_pressed_with` calls `hold_input`. The iOS test does not catch this: `down` (`HeldStateTests.swift:76`) calls `HeldState.input` itself instead of `Agent.tap`. Fix: at the start of a one-shot press, before any of those returns, call `HeldState.input(at:)` on the named view; call it on the pan branch’s hit before `panPointer`. Drive the iOS test through `Agent.tap`.

2. **SHOULD-FIX** — iOS text and shortcuts never reach `keyEvent`, so a key does not let the hold go. Software-keyboard insertion calls `supersedePress` only: `TextAreaIOS.swift:116` (`TextField.insertText`) and `:164` (`TextArea.insertText`). `ShortcutsIOS.performShortcut` (`ShortcutsIOS.swift:105`) presses the shortcut’s button with no `HeldState.input`. The agent’s shortcut (`AgentIOS.swift:1092`) returns before `keyDown`, which is the call that would reach `HeldState.input`. A hardware key and a non-shortcut agent `key` do let go. Fix: call `HeldState.input(at:)` on the field’s owner or `focusedNode` in those three places, next to `supersedePress`.

3. **SHOULD-FIX** — After a same-plan generation swap, a Mac hover’s `over` bit is sampled from dead views, so the next pointer move lets the hold go as `input` even when the pointer never left the node. `hold` sets `over` from `pointerPath` (`HeldState.swift:136`), and `swap` does not refresh that path. `rehold` then runs `hold` against weak refs to the old tree, so `over` is false. The next `hoverLooks` (`HeldState.swift:88`) sees the new node under the pointer and treats it as a crossing. Linux samples the live hit in `pointer_in` (`held.rs:172`), so a move within after `rehold` keeps the hover. Fix: when applying a hover, hit-test the current mouse location in the held window and set `over` from that, and have the Mac `applyTogether` test move the pointer within the node after the swap and expect no `input`.

4. **SHOULD-FIX** — Linux `hold active` walks through a disabled node to the press above it. The walk (`held.rs:55`) breaks only on a `press` handler, then `disabled_at` checks the resolved press and its ancestors. A disabled node that is not itself the press is skipped. A real press does not do that: `handler_target` (`surface_controls.rs:505`) returns no target at a disabled node. Apple stops and answers `disabled` (`HeldState.swift:125`). Fix: in that walk, return `Err("disabled")` as soon as the node’s `disabled` prop is set, before climbing.

5. **SHOULD-FIX** — A Linux refusal that is `unsupported` does not end its revision. `hold_frame` ends the revision only when the report has a `reason` string (`held.rs:254`). An unknown state (`held.rs:241`) is `unsupported` and has no `reason`, so a resent frame is taken again and reported again. Apple ends that revision (`Inspect.swift:199` and `:228`). The server drops the second report after the first cleared the hold, but the host’s own ended set is what a lost poll answer is checked against. Fix: call `link.end(revision)` for an `unsupported` hold report as well.
