**1. Verdict: RIGHT WITH CHANGES**

**2. Overall assessment**

The core architecture is sound: `aria-actions` references existing controls, hosts expose those relationships through platform accessibility APIs, and activation uses existing behavior. The browser premise is supported by [Chrome 151’s release notes](https://developer.chrome.com/release-notes/151#aria-actions_attribute). Two choices need changing before approval: automatically collapsing the iOS accessibility subtree, and allowing authored attributes to substitute for observed platform actions.

**3. Concerns**

- **MAJOR — Adding actions should not remove access to descendants.**  
  [D3 and Q2](/Users/ccheever/projects/exact2-review-1114/llp/1114.008-accessibility-actions.rfc.md:196) make every element with actions a single iOS accessibility element, hiding its descendants. Adding Like and Reply shortcuts would consequently remove independently discoverable links and other controls unless the author exhaustively re-exposes them. A list of named presses also cannot preserve every descendant’s role, state, and interaction model.

  The claim that this is the only way to offer actions is too strong. Exact already handles UIKit’s container restriction by exposing a synthetic paragraph element **alongside** its interactive links in [TextInteraction.swift](/Users/ccheever/projects/exact2-review-1114/host/apple/Sources/ExactKit/TextInteraction.swift:80). Apple’s [UIAccessibilityElement](https://developer.apple.com/documentation/uikit/uiaccessibilityelement) provides the underlying representation.

  **Resolution:** Keep action association separate from subtree grouping. Use an accessible summary element carrying the actions while retaining descendant accessibility, or another projection with equivalent reachability. A deliberately collapsed notification can be a presentation choice; it should not become the universal meaning of `aria-actions`.

- **MAJOR — The proposed agent fallback compromises the accessibility oracle.**  
  [D5](/Users/ccheever/projects/exact2-review-1114/llp/1114.008-accessibility-actions.rfc.md:228) allows the web action list to be reconstructed from `aria-actions` whenever CDP does not expose it, then uses that list for platform parity. A target’s computed accessible name does not establish that Chrome exposes the target as an action on the referencing element. This could report agreement without observing the browser behavior being compared.

  That changes the architectural contract of `tree --ax`: [DEFERRED’s accepted scope](/Users/ccheever/projects/exact2-review-1114/rules/DEFERRED.md:764) explicitly reads platform exposure and retires guessed accessibility facts. [LLP 1080.002 D6](/Users/ccheever/projects/exact2-review-1114/llp/1080.002-the-accessibility-tree-in-the-agents-hands.rfc.md:222) likewise limits parity to mutually observable facts.

  **Resolution:** Report actions as unobservable when the carrier cannot read them. Attribute-derived relationships may be reported separately as authored intent, with parity restricted to actual platform observations.

**4. What it gets right**

Referencing real controls avoids duplicate labels and a second action-dispatch model. Keeping the implementation in host accessibility projections preserves the kernel and runner boundaries. No new grant is appropriate because these actions reuse existing app operations. Following the evolving web spelling without compatibility shims also fits repository policy. Treating context-menu accessibility as part of this consumer’s need is reasonable.

**5. Questions for Charlie**

Change **Q2’s recommendation to no**: approve accessible action shortcuts while preserving descendant reachability. The current question presents subtree collapse as technically unavoidable when the repository already demonstrates another structural approach.

Add an explicit decision that **action parity requires observed platform actions**. Missing carrier support should remain an acknowledged observation gap rather than being filled from authored intent.
