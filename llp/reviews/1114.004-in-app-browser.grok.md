I'll review LLP 1114.004 for direction and architecture only. First I'm reading the parent summary, the RFC, and the rules it depends on.The RFC's main bet is that HTML's `popup` is the right shape for an in-app browser. I'm checking that against the code and the LLPs it cites.**Verdict:** RIGHT WITH CHANGES

**Overall assessment:** The capability is the right one. Bluesky really does open non-`mailto:` links in `SFSafariViewController` and ignores that call's result (`useOpenLink.ts` on `social-app` `main`), and exact2's `openURL` really does leave via `UIApplication.shared.open` (`ExactIOS/main.swift`). A named argument on `openURL`, `SFSafariViewController` on iOS only, no new event, no grant, and the system browser everywhere else is the right shape. Three mechanisms, and the reason given for reversing LLP 1069, should change before this is ruled.

**Concerns**

1. **BLOCKING — `visibilityState: "hidden"` while the sheet is up corrupts a fact other apps already read.** D3 sets `visibilityState` to `"hidden"` and `hasFocus` to false for the life of the sheet, and the agent substitute does the same. Page Visibility uses `"hidden"` for a background tab, a minimized window, or the screen off; a popup does not hide the opener (MDN Page Visibility; the RFC's own §4 says a desktop popup only blurs the opener). exact2 already defines it that way: iOS `hidden` is scene background (`PageFacts.swift` `AppBackground.now`; LLP 1069.000 D2), and "a window behind another is still visible" (`runner/src/page.rs`). A presented controller leaves the scene `foregroundActive`, so `hasFocus` stays true. Share sheets and dialogs do not flip either fact. Readers of `exactPage()` — pause a feed, treat return as a resume — would treat "reading a link" as "the app was backgrounded," and a later real background starts from an already-hidden page. Bluesky does not need a signal. **Resolve:** change no page fact. `openURL: presented` / `openURL: closed` in the journal are enough for the agent.

2. **MAJOR — The reversal is argued on Safari sign-in, which this sheet does not keep.** The summary and §3.2 say the sheet keeps "Safari's cookies and autofill," and that LLP 1069 missed those sign-ins. AutoFill, Reader, and fraud warnings are real (Apple's `SFSafariViewController` overview). Shared Safari cookies are not: since iOS 11 the sheet's jar is per app, and the current doc says to use `ASWebAuthenticationSession` to share data with Safari. Today's `openURL` is the path that opens Safari itself, where the person is already signed in. D4's grant conclusion still holds — the app cannot read the jar — but Q1 as written oversells what admission buys. **Resolve:** restate the benefit as staying in the app (plus AutoFill), and rule Q1 on that.

3. **MAJOR — Passing the `popup` feature on the web is a behavior the clone does not want, and one source cannot turn it off per host.** `popup` asks the browser for a minimal popup window (MDN `Window.open`). Bluesky's web client always uses a normal open. §7 tells the clone to call `openURL(url, popup=settings.inApp)` everywhere; §8 says it can pass `popup` only where it wants it. Contract has no host test, so the setting that means "Safari sheet" on iOS also requests a popup window on the desktop web. HTML allows a browser to ignore `popup`. **Resolve:** the web host keeps today's `window.open(url, "_blank", "noopener,noreferrer")`. iOS is the only host whose behavior changes. One source can pass `popup=true` on every host.

4. **MAJOR — ExactKit swallowing the popup form breaks the embedder's ownership of `openURL`.** LLP 1031 D5: navigation outside the Exact surface is a command the delegate decides. `Session.follow` and link activation already deliver `openURL` to that delegate (`Session.swift`, `InlineText.swift`). D2 has ExactKit present the sheet and hand only the plain form to the delegate. The first embedder with a URL allowlist then misses every in-app open, and the sample host (`ExactHostIOS`) never sees the command. A later hook is a second path. **Resolve:** the runner may hold the command for the agent, as it does for `share`. When the ruling is present, the delegate still receives `openURL` with the argument. The stock iOS adapter presents `SFSafariViewController`; ExactKit can hold that helper.

**What it gets right**

- Opt-in on the existing command, so today's `openURL` stays a handoff to the system browser.
- `SFSafariViewController` on iOS, and a refusal of `WKWebView` as a chromeless browser. That matches LLP 1020's refusal of a guest the app can script, and LLP 1069.006's split (auth session returns a callback; content browsing must not).
- No dismissal event. Bluesky ignores the promise except to fall back to `Linking.openURL` on failure.
- No grant. The scheme allowlist is the check, and the app cannot read the page.
- macOS, Linux, Windows, and the terminal stay on plain `openURL`. AppKit has no `SFSafariViewController`.
- The agent shape (held request, origin-only disclosure, `tap @t close`) matches LLP 1069.007 D7, provided it does not also force `exactPage()` to hidden.

**Questions for Charlie**

- **Q1: still yes**, under the Bluesky admission, with no further trade. The reason to reverse LLP 1069 §5 and LLP 1069.006 is that the person stays in the app. It is not that they keep their Safari logins.
- **D3 is not asked, and the recommendation should be flipped.** Admit the sheet only if `visibilityState` and `hasFocus` stay on their current definitions.
- **Add:** the web ignores `popup` and keeps a tab. Q2 (manifest `theme_color` and `accent-color` only) and Q3 (macOS opens the default browser) can stand as written.
