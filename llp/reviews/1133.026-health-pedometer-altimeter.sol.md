1. **MATERIAL — History authorization has no independent state.** D5–D6 (lines 321–326, 402–404), D10 (514) and D19.1 track permission by health type. Once steps are granted, `requestHealthAuthorization(read=["steps"], android.readHealthDataHistory=true)` has no `prompt` key, so D6 returns the status without requesting history access. [Health Connect treats history access as a separate permission](https://developer.android.com/health-and-fitness/health-connect/read-data#read-data-older-than-30-days). **Decision needed:** include history authorization independently in admission, status, tickets and upgrade requests.

2. **MATERIAL — Android’s selected aggregation cannot honor the promised time zone.** D1 (lines 162, 187–190) selects `aggregateGroupByPeriod` while promising calendar buckets in the session’s time zone. That API requires `LocalDateTime`; [Jetpack defines its semantics as experienced local time](https://raw.githubusercontent.com/androidx/androidx/androidx-main/health/connect/connect-client/src/main/java/androidx/health/connect/client/time/TimeRangeFilter.kt), using record offsets rather than a caller-selected zone. Historical steps recorded at 23:30 in San Francisco can therefore land on the wrong date when viewed in a New York session. Passing instant boundaries instead is [explicitly unsupported for period aggregation](https://developer.android.com/health-and-fitness/health-connect/aggregate-data#period). **Decision needed:** aggregate over calculated instant boundaries for each session-zone bucket, or declare experienced-local semantics as the Android behavior.

3. **MATERIAL — The pedometer’s moving `since` contradicts its cumulative value.** D12 (lines 575–581) advances `since` to seven days before each answer’s current time, but selects `startUpdates(from: start)`. [Apple documents live updates as cumulative from the specified start](https://developer.apple.com/documentation/coremotion/cmpedometer/startupdates(from:withhandler:)); the seven-day restriction belongs to historical queries. After eight days, the proposed answer can claim to begin on day two while still counting day one. **Decision needed:** retain a fixed accumulation boundary for the live reader, or explicitly implement rolling totals whose values match the moving boundary.

4. **MATERIAL — The persistence exception does not resolve the RFC’s own iCloud restriction.** D9 (lines 482–490) invokes [App Review 5.1.3(ii)](https://developer.apple.com/app-store/review/guidelines/#health-and-health-research) to exclude personal health information from iCloud, while §16 question 2 permits kept pedometer answers and §12 (1115–1117) saves walk statistics into ordinary notes. Fieldnotes stores note bodies and backups under `app:/data/`, mapped to Application Support, with no backup exclusion found. A stamped walk therefore enters ordinary backed-up storage even if kept answers are disabled. **Decision needed:** define storage and backup handling for these fitness values, including saved notes and generated backups. Calling them sensor readings does not settle the cited restriction.

5. **MATERIAL — Refusing module calls does not establish the promised tool-disclosure boundary.** D7/D15 and Calendar acceptance drive 5 (lines 1088–1089) expect a tool reading the agenda to receive `person-required` instead of workouts. However, a workout already loaded for the person can be returned from an existing resource or data-module cache without another module call. LLP 1111 D2/D4 expressly permits standing-resource returns; the built tool handler path also returns ordinary data answers without another module admission. **Decision needed:** specify how the consumer prevents disclosure of previously loaded health values, or narrow the promise to direct module calls and explicitly assign derived-data disclosure to the app. `"origin": "app"` alone cannot enforce the broader boundary.

**Earlier finding 4 — MATERIAL remains: assigning storage responsibility to the app does not settle Fieldnotes’ storage.** D9 (558–565) now correctly separates framework caching from app persistence. But §12 (1256–1258) still inserts automatically collected fitness figures into ordinary note bodies, and §16 question 2 approves that behavior without deciding backup handling.

Failing scenario: the person stamps a walk and saves the note with iCloud Backup enabled. Fieldnotes stores its database and generated backups under `app:/data/` (`apps/fieldnotes/app.ts:10,29,184–185`), mapped to Application Support (`host/apple/src/picker.rs:48–51`), with no backup exclusion found. Apple documents that ordinary app data enters [iCloud Backup](https://developer.apple.com/documentation/foundation/optimizing-your-app-s-data-for-icloud-backup), while [5.1.3(ii)](https://developer.apple.com/app-store/review/guidelines/#health-and-health-research) retains the restriction the RFC cites. Calling the stamp the person’s text does not resolve that handling.

**Decision needed:** define storage and backup handling for stamped figures, including generated backups, or select the nonpersistent display. This requires an app-level decision, not generalized framework machinery.

**IN-DELTA — MATERIAL: Android’s new completeness guarantee can survive an unobserved authorization reset incorrectly.** D2 (247–256) treats Android’s granted reads as complete back to `since`. D5 (399–412) derives that cutoff from a remembered first grant and resets it after observing an empty-to-nonempty grant transition.

Failing scenario: the first observed grant was in January. In October, while the app is closed, the person revokes every Health permission and grants them again. The granted set looks unchanged when the app returns, but Health Connect has reset its historical-access boundary. [AOSP’s integration test](https://android.googlesource.com/platform/packages/modules/HealthFitness/+/8d79b9403cee11fdd9d2bea173adff0edb6bec13/tests/integrationtests/src/android/healthconnect/tests/backuprestore/BackupRestoreE2ETest.java) explicitly verifies this reset.

An August statistics query can consequently return empty buckets with `complete: true` and the old `since`, falsely classifying inaccessible history as days without samples. The proposed error recovery cannot reliably discover this: the [HealthPermission reference](https://developer.android.com/reference/androidx/health/connect/client/permission/HealthPermission#PERMISSION_READ_HEALTH_DATA_HISTORY()) says these reads omit inaccessible older data; the single-record API errors.

**Decision needed:** establish a cutoff policy that survives unobserved revoke/regrant cycles, and limit `complete` to the window that policy actually establishes.

**PRE-EXISTING — MATERIAL: retained registration does not establish Android background-count continuity.** D12 (683–692) retains the step-counter registration and leaves whether counting stops to a phone experiment. Application-processor suspension and an idle app UID are different conditions. AOSP’s [SensorService](https://android.googlesource.com/platform/frameworks/native/+/master/services/sensorservice/SensorService.cpp) propagates UID inactivity to [SensorDevice](https://android.googlesource.com/platform/frameworks/native/+/master/services/sensorservice/SensorDevice.cpp), which disables the hardware when no active clients remain.

Failing scenario: another fitness client keeps the counter active on the test phone, so continuity appears to work. On a user’s phone where this app is the only client, the UID becomes idle and counting stops. Counting later resumes without a falling-counter signal, leaving missing steps inside the interval still claimed by `since`. This follows from the native activation policy; one phone’s result cannot establish universal continuity.

**Decision needed:** conservatively establish a new baseline after potentially inactive gaps, or choose a supported mechanism that guarantees continued activation. The answer must not imply uninterrupted accumulation merely because the counter remained monotonic.
