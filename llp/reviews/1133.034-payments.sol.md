1. **MATERIAL — Callbacks lack a stable checkout identity, and token deduplication does not prevent duplicate charges.** RFC D1, lines 192–196, gives shipping handlers no request ID or original checkout context. Two queued checkouts with different items but identical addresses therefore give `quoteShipping` indistinguishable inputs. Existing [`invoke.rs:160–170`](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1034/capsule1/runner/src/runner/modules/invoke.rs:160) passes only the supplied callback argument into a fresh answer.

   D6, lines 381–394, additionally promises one charge by deduplicating the token’s transaction ID. Google’s [PaymentData](https://developers.google.com/pay/api/android/reference/response-objects#PaymentData) has no universal transaction ID, and another authorization can produce another token.

   **Resolution:** Create a merchant checkout ID before showing the sheet, include it in every callback, and associate it with an immutable order snapshot. Use that ID for server and processor idempotency and reconciliation. Drive a lost response followed by authorization with a different token, proving one charge.

2. **MATERIAL — A retry after the caller ends leaves an ownerless sheet.** D6, lines 368–379, preserves an authorization handler after its caller disappears and leaves the sheet open when it returns `retry`. D16, lines 680–685, retains the invocation grant only until that handler answers. The next authorization therefore lacks a valid grant; [`invoke.rs:139–156`](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1034/capsule1/runner/src/runner/modules/invoke.rs:139) checks it on every invocation. Section 9 also leaves cancellation after retry unspecified.

   **Resolution:** Define editing, authorizing and terminal phases. Retry returns to editing; if the original caller has ended, dismiss instead. Alternatively, explicitly retain an independent transaction owner until dismissal. Add drives for caller loss followed by retry, and retry followed by cancellation.

3. **MATERIAL — Advanced Apple payment types are placed in the wrong dictionary.** D9–D10, lines 483–510, places recurring, automatic reload and deferred payment configuration in `PaymentMethodData.data` as `ApplePayRequest` keys. Apple’s [ApplePayRequest](https://developer.apple.com/documentation/ApplePayontheWeb/ApplePayRequest?changes=_9) lacks these fields. Payment Request takes them through [ApplePayModifier](https://developer.apple.com/documentation/applepayontheweb/applepaymodifier?changes=_5), in `PaymentDetailsModifier.data`. Following the proposed dictionary can fail to request the intended payment type in Safari.

   **Resolution:** Preserve and validate the actual modifier dictionaries, including their selection semantics and native mapping, or explicitly defer these payment types.

4. **MATERIAL — The substitute violates the authorization handler’s input contract.** Section 9, line 881, supplies `details: {exactSubstitute:true, transactionId:n}`. D7, lines 398–418, promises an `ApplePayPayment` or Google `PaymentData`. An ordinary handler extracting `details.token.paymentData` or `details.paymentMethodData.tokenizationData.token` consequently fails under the agent. The fixture server’s special synthetic format hides this mismatch.

   **Resolution:** Generate method-shaped, unchargeable synthetic payments with the documented metadata and token locations. Test unchanged production handlers against both substitute and real responses.

5. **MINOR — The example and consumer cannot pass their own merchant-validation admission rule.** The summary’s send, lines 29–32, omits `onmerchantvalidation`; §10 likewise omits that handler while supplying Apple Pay method data. D8, lines 453–456, therefore rejects the checkout. Its unconditional rejection of any request containing Apple method data also contradicts D10, lines 524–525, where the unused method is inert.

   **Resolution:** Supply the validation handler and require it when Apple Pay is selected. Define a synthetic merchant-session response for account-free substitute drives: §9 invokes validation, but §10’s fixture endpoint otherwise returns 503 without a certificate.

6. **MINOR — The deadline policy promises behavior Safari need not deliver.** D5, lines 338–345, promises an update error while retaining the sheet at the 30-second bound. Question 3 says Apple and the web state no limit. Apple’s [TN3174](https://developer.apple.com/documentation/technotes/tn3174-diagnosing-issues-with-the-apple-pay-payment-sheet-on-your-website) explicitly gives Apple Pay handlers, including Payment Request shipping updates, 30 seconds before dismissal.

   **Resolution:** Distinguish the module’s handler budget from the platform’s deadline, leave completion margin, and document platform-owned timeout outcomes.

7. **MINOR — “The runner … keeps no copy” is stronger than the inherited implementation supports.** D7, lines 406–409, promises no retained argument copy. Existing [`invoke.rs:42–46`](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1034/capsule1/runner/src/runner/modules/invoke.rs:42) retains the argument in `Running.args` and reuses it when resuming at lines 239–242. This does not establish a diagnostic leak, but it contradicts the stated property.

   **Resolution:** Promise no publication, persistence, checkpointing or diagnostic recording, with temporary retention bounded by execution lifetime. If literal zero retention outside the data runtime is intended, include that redesign in the seam work.

8. **IMPLEMENTATION-PHASE — Processor authentication needs a demonstrated continuation recipe.** D5 prevents the authorization handler from opening another sheet, and D6 bounds it to 30 seconds. Google documents that [PAN payments can require subsequent 3D Secure authentication](https://developers.google.com/pay/api/android/guides/resources/sca). Wallet approval therefore does not always finish payment processing.

   **Resolution:** Demonstrate a post-wallet continuation using the existing result/data channel and an app-origin action, with server reconciliation. Clearly distinguish wallet completion from a paid order. This need not require another module seam.

9. **IMPLEMENTATION-PHASE — Merchant validation must not become an unrestricted URL forwarder.** D8, lines 447–455, forwards a client-supplied URL to a server using the merchant’s certificate. Apple’s [payment-session documentation](https://developer.apple.com/documentation/ApplePayontheWeb/requesting-an-apple-pay-payment-session?changes=_9) requires rejection of validation URLs outside Apple’s documented endpoints.

   **Resolution:** Implement and test a strict HTTPS endpoint allowlist, including redirect handling, in the fixture and production recipe.

The remaining concerns are:

1. **IN-DELTA · MATERIAL — The web opens the wallet before admission.**  
   **r2 D8, lines 512–528.** The button calls `PaymentRequest.show()` before the action’s `showPaymentRequest` call is admitted. Consequently, a computed, ungranted merchant identifier can reach the wallet before D13 rejects it.

   **Evidence:** LLP 1133.002 D14, lines 676–690, orders grant, target, origin and decision admission before implementation dispatch; `host/web-js/modules.js:653–660` follows that order. Sign-in’s precedent opens only `about:blank` before admission—LLP 1133.014 D5, lines 519–527—rather than invoking the provider.

   **Resolution:** Specify synchronous checkout admission before `show()`, including the bake-owned environment and decision-queue reservation. The later call should adopt a single-use admitted record. Drive an ungranted computed merchant ID and prove that no wallet opens.

2. **IN-DELTA · MATERIAL — Caller loss during web retry cannot perform the specified cancellation.**  
   **r2 D6, lines 405–409 and 428.** A live caller’s `retry` returns the request to editing; subsequent caller loss therefore promises `abort()`.

   **Evidence:** Payment Request’s [`abort()` algorithm](https://www.w3.org/TR/payment-request/#abort-method) rejects while `[[retryPromise]]` is pending. [`complete()`](https://www.w3.org/TR/payment-request/#complete-method) also rejects during that interval. Person cancellation works; screen departure or mutation supersession does not close the sheet through either specified API.

   **Resolution:** Define a web retry owner that survives caller loss until person cancellation or reauthorization, with no further charging callback after abandonment, or demonstrate another supported termination mechanism. Add the missing drive: retry opens, then the caller disappears.

3. **IN-DELTA · MATERIAL — Android’s terminal outcomes use its retry mechanism.**  
   **r2 D6, lines 418–429; D15, lines 794–796.** `fail`, `unknown`, and retry after caller loss are treated as terminal outcomes, but all map to an Android authorization error.

   **Evidence:** Google’s [`PaymentAuthorizationResult`](https://developers.google.com/pay/api/android/reference/response-objects#PaymentAuthorizationResult) defines its error as feedback displayed so the person can retry. The RFC itself acknowledges that the module cannot withdraw Google Pay’s activity, at lines 409–412. Returning an error therefore does not establish the promised Closed phase.

   **Resolution:** Distinguish a terminal application outcome from actual sheet closure. Retain an Android owner or tombstone and the decision-queue slot until the activity result arrives; reject subsequent authorizations without invoking the app. Document the remaining user-dismissal behavior. Apple can explicitly dismiss its controller; Android needs this lifecycle decision.

4. **IN-DELTA · MATERIAL — The substitute still violates Google DIRECT handlers’ input contract.**  
   **r2 §9, line 1032; D9, line 585.** The substitute always emits `tokenizationData.type: "PAYMENT_GATEWAY"`, although the module supports gateway and direct tokenization.

   **Evidence:** Google requires the response’s [tokenization type](https://developers.google.com/pay/api/android/reference/response-objects#PaymentMethodTokenizationData) to match the requested specification. A normal DIRECT handler can reject this response before reaching the fixture server.

   **Resolution:** Generate the selected tokenization type and its documented, unchargeable envelope. Exercise unchanged handlers for both gateway and DIRECT requests.

5. **IN-DELTA · MATERIAL — The server deadline cannot guarantee that a timed-out sheet leaves nothing captured.**  
   **r2 D6, lines 454–455.** A server can capture and send its answer within 20 seconds while the response is delayed or lost; the handler then exceeds 25 seconds and the sheet fails despite the capture. A processor response can likewise remain indeterminate beyond either deadline.

   **Evidence:** This conflicts with D6’s correct acknowledgment at lines 444–446 that failed sheets can accompany charges. Stripe documents [indeterminate network outcomes](https://docs.stripe.com/error-low-level#network-errors), and [cancellation](https://docs.stripe.com/api/payment_intents/cancel) is unavailable once a payment has succeeded.

   **Resolution:** Make 20 seconds a response target, remove the no-capture guarantee, and specify reconciliation of indeterminate checkouts, followed by voiding or refunding where appropriate. Preserve checkout identity throughout.

6. **PRE-EXISTING · MINOR — The consumer’s Express-shipping drive lacks its callback and server input.**  
   **r2 Summary, lines 31–34 and 54–56; drive 1, line 1133.** The send names no shipping-option handler, while the drive expects selecting Express to change the total. The payment POST also omits `shippingOption`.

   **Evidence:** D5, lines 354–356, says unnamed events receive the request’s existing values.

   **Resolution:** Add `onshippingoptionchange` and send the selected shipping option to the checkout server.

7. **IN-DELTA · IMPLEMENTATION-PHASE — Apply Google’s environment policy to the native client.**  
   **r2 D10–D11, lines 629 and 673–681.** Android selects its environment through `WalletOptions.setEnvironment`, rather than `PaymentDataRequest` JSON, as Google’s [client reference](https://developers.google.com/pay/api/android/reference/client) shows.

   **Resolution:** Apply the bake-owned value when constructing the client. The policy itself is sound; this does not affect the verdict.

The Apple modifier mapping is feasible through [`PKPaymentRequestUpdate`](https://developer.apple.com/documentation/passkit/pkpaymentrequestupdate); matching must preserve Safari’s selection semantics. The Android request-code addition also fits the existing routing in `Extensions.kt:500–519` and the documented `AutoResolveHelper` route. Neither introduces another material concern. Apart from the web admission gap above, the four testing safeguards and the choice to display `unknown` as native failure introduce no further material defect.

1. **IN-DELTA · MATERIAL — Timeout returns the native sheet to editing while its cancellation hold remains active.**

   **Location:** D6, lines 407–409, 436 and 452–455; D16, lines 852–859.

   At 25 seconds, the module answers the authorization as failed, allowing another native authorization. The original app handler continues, with its eventual answer dropped. But D16 suppresses caller-loss cancellation until that handler **answers**, potentially indefinitely.

   If the screen disappears during this interval, the implementation can remain unaware of abandonment and invoke the app on another authorization, contrary to D6, lines 424–427. Checkout deduplication does not prevent this: the first processor attempt could have declined, with its response stalled, leaving the checkout open for the second authorization to charge.

   **Evidence:** [bound.rs:229](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1034/capsule3/runner/src/runner/modules/bound.rs:229) supplies the described caller-loss notification. [invoke.rs:179](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1034/capsule3/runner/src/runner/modules/invoke.rs:179) retains an outstanding handler until its awaited request returns. Google’s [authorization-result contract](https://developers.google.com/pay/api/android/reference/response-objects#PaymentAuthorizationResult) confirms that failure permits retry.

   **Resolution:** Separate the cancellation-protected authorization span from continued execution of the late handler. End the hold at the answer **or deadline**, delivering any latched caller loss; alternatively, deliver a non-cancelling owner-loss notification during the hold. After abandonment, subsequent authorizations must invoke no app handler. Drive authorization → caller loss → deadline → reauthorization while the original handler remains unresolved.

2. **IN-DELTA · MINOR — The substitute discards the abandoned lifetime that production now retains.**

   **Location:** §9, lines 1080–1081, versus D6, lines 421–427.

   The substitute immediately retires tickets on caller loss, including Android and web-retry paths whose real sheets cannot close. It therefore cannot expose the retained decision slot or exercise rejection of later authorization without an app callback.

   **Evidence:** D6 explicitly retains those owners until platform closure, while the changed substitute rows retire them.

   **Resolution:** Retain an abandoned synthetic ticket on the affected targets until simulated platform closure. Reject further authorizations without invoking the app, and drive a second request while that slot remains occupied.

3. **IN-DELTA · MINOR — The refund sentence needs a server-visible policy.**

   **Location:** D6, lines 473–478; drive 4, lines 1198–1200.

   “Voiding or refunding it if the sheet was failed” provides no way for the server to learn that local failure. A lost processor answer and a lost server-to-client answer also differ: drive 4 deliberately preserves the latter checkout as paid.

   **Evidence:** The example at lines 54–61 posts payment data but reports no wallet outcome; the fixture endpoints at lines 1154–1164 contain no outcome-report route. [Stripe’s network-error guidance](https://docs.stripe.com/error-low-level#network-errors) supports preserving attempt identity and reconciling uncertain processor execution.

   **Resolution:** Distinguish those two lost-answer cases. Define fulfillment, voiding and refunding through the server’s checkout policy; if wallet failure controls refunds, specify a best-effort client report and the policy when that report is lost.

4. **PRE-EXISTING · IMPLEMENTATION-PHASE — Android’s payment-method callback uses the wrong intent name.**

   **Location:** D5, line 352.

   **Evidence:** Android’s [request reference](https://developers.google.com/pay/api/android/reference/request-objects#PaymentDataRequest) lists `PAYMENT_METHOD`, whereas the RFC names `OFFER`.

   **Resolution:** Use Android’s `PAYMENT_METHOD` mapping. The intended callback is feasible, so this does not affect the verdict.

5. **IN-DELTA · IMPLEMENTATION-PHASE — Deferred Apple request updates have a later availability floor.**

   **Location:** D10, line 658.

   **Evidence:** The installed SDK’s [PKPaymentRequestStatus.h:89](/Applications/Xcode.app/Contents/Developer/Platforms/iPhoneOS.platform/Developer/SDKs/iPhoneOS.sdk/System/Library/Frameworks/PassKit.framework/Headers/PKPaymentRequestStatus.h:89) declares `deferredPaymentRequest` at iOS 16.4/macOS 13.3.
