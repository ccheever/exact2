## Review as returned

Reviewed **Draft r2**, dated 2026-10-02, SHA-256 `975827f76b00b477106e83ac36062c44fbfff869058ba54e65a69ec8d317620b`. This is an independent review; I did not author or edit either draft.

**Overall assessment:** The central design is good and directly answers James’s request. Keep its architecture. I recommend several small directional simplifications before implementation, principally removing the special refusal for empty literals and the session-wide missed-name journal requirement.

**What should stay**

- **D1’s explicit `symbol:sf/` namespace and opaque name.** Passing names directly to the running OS eliminates Exact’s catalog bottleneck without weakening the meaning of existing portable roles. Both Apple lookup APIs return optional images, matching the proposed absence behavior. [UIKit documentation](https://developer.apple.com/documentation/uikit/uiimage/init(systemname:)), [AppKit documentation](https://developer.apple.com/documentation/appkit/nsimage/init(systemsymbolname:accessibilitydescription:))
- **Dynamic names through the existing image source.** No new image tag, button property, availability table, or capability module is necessary.
- **D2’s empty em-square fallback.** This is a reasonable extension of the existing font-sized symbol scheme. It gives unsupported hosts useful intrinsic geometry and avoids an automatically vanishing icon slot. Keep explicit dimensions authoritative.
- **D3’s projection eligibility based on authored structure.** A failed lookup must not change the kind of control, remove a tab, or reset selection.
- **D4’s blank web/Linux result.** It is the requested unsupported-platform behavior. No reverse mapping or new fallback-artwork API is needed.
- **The source-transition requirements and Linux stale-raster fix.** These are necessary correctness work, not unrelated scope expansion.

**Concerns and recommended resolutions**

1. **Medium — D2 turns expected absence into an unnecessarily durable diagnostic mechanism. Directional change recommended.**

   “Once per distinct unresolved SF name per session” requires remembering names for the session’s lifetime. Names can come from data, so that retained set grows independently of the live view count. The existing runner journal is bounded to 4,096 entries (`runner/src/runner.rs:425`), while current Apple symbol refusal suppression is attached to a view’s last source.

   More fundamentally, an unavailable name is an expected outcome of the feature. A lookup cannot distinguish a typo from a symbol intentionally used on an older OS. The sentence saying runtime inspection “replaces” typo checking overstates what it can establish.

   **Resolution:** Keep current-resolution inspection, but remove the mandatory session-wide journal guarantee and the claim of runtime typo detection. Let `layout` reveal the requested name and unavailable result. If logging remains useful, reuse bounded existing diagnostics rather than introduce lifetime name tracking. Do not add an application-facing availability API.

2. **Medium — D1’s literal-empty refusal is an unnecessary authoring distinction. Directional change recommended.**

   `image "symbol:sf/"` and a variable containing that exact string should have the same acceptance and rendering behavior. Intentional blank slots, initial placeholders, and temporarily disabled icons are legitimate uses; “no author writes an empty icon on purpose” is not a sound assumption. A literal can also preserve the symbol-over-label shape that D3 promises to project.

   The special error catches an empty value while permitting every nonempty misspelling, so it buys little validation at the cost of another language rule.

   **Resolution:** Accept an empty suffix for both literals and dynamic expressions. Render the same empty em square, report the empty state on inspection, and do not log it. Retain existing unknown-literal diagnostics for portable roles.

3. **Medium — D1 promises monochrome behavior that the named APIs do not automatically provide. Small directional clarification recommended.**

   The assertion that an arbitrary SF name renders as a template “in one colour” is stronger than preserving the existing path. The current Apple leaves configure point size and weight; the tab bar uses a direct system-name lookup. Apple documents that, since iOS 16, an unspecified rendering mode does not necessarily mean monochrome; `airpodsmax`, for example, defaults to hierarchical rendering. Monochrome must be requested explicitly when required. [Apple’s symbol configuration documentation](https://developer.apple.com/documentation/uikit/configuring-and-displaying-symbol-images-in-your-ui)

   **Resolution:** The smaller change is to preserve the existing native configuration and platform defaults, while saying this amendment adds no rendering-mode controls, variable-value controls, or symbol effects. Remove the universal monochrome promise. If guaranteed monochrome is instead intentional, explicitly require its configuration in every relevant projection and test that behavior; do not describe it as something today’s lookup already guarantees. I prefer preserving existing native behavior.

4. **Medium — D3’s projection inventory omits macOS image-only segments. Coverage correction, not a new design direction.**

   `host/apple/Sources/ExactKit/Mac/SegmentsMac.swift:99` uses the image when present, but otherwise clears it and displays `tab.accessibleName` as visible text. Thus a missing raw symbol can become a text segment, contrary to the requested blank-icon behavior. The iOS image-only segment is already listed; its failure branch also needs to clear both the prior image and the cached icon identity.

   **Resolution:** Include macOS image-only segmented controls among the existing image-consuming projections. Require a missing symbol to preserve the authored image-only presentation and accessible name without substituting visible text. Verify valid → missing → valid for both segmented controls, in addition to tab-bar and toolbar cases. This does not call for a new projection system.

**Implementation clarifications**

- Define `found` as a resolution result, not “whether this host drew a glyph.” Visibility, clipping, opacity, and native projection can prevent paint despite successful resolution. Avoid classifying an unknown portable role as an OS lookup failure.
- Describe the em square as **predictable fallback intrinsic geometry**, not “the right box” or a promise of only “a few points” of movement. Arbitrary symbols need not have near-square dimensions, and normal CSS constraints still affect used size. Explicit dimensions are the way to keep a fixed slot.
- Keep the prerender acceptance requirement. Both existing HTML emitters omit custom symbol sources from `img.src`; changing only the post-mount symbol refresh does not establish the promised em square before adoption.
- The existing acceptance work is sufficient in shape. Add the omitted macOS segment case and align it with the simplified empty-name, inspection, and rendering-mode decisions; no new script or blocking check is warranted.

**Open questions**

No unresolved architectural question blocks revising this draft. The remaining product choice is whether raw symbols preserve native default rendering or are deliberately forced monochrome; preserving defaults is the more proportional choice.

Implementation still needs an owner and date before this becomes a scheduled specification. The draft correctly acknowledges that neither is assigned.

**Recommended next step:** Revise r2 with the changes above and retain Draft status. Keep the namespace, OS-owned lookup, em-square fallback, native-control stability, and blank unsupported-platform behavior. There is no reason to redesign the feature or add another review loop.
