**Blocking**

1. `host/linux/src/store_writer.rs:95` — An empty commit does not retry a write that is still in flight, so a failure can be dropped on the way to the background. `submit` queues an empty commit only when `queue.pending` is already true. The writer sets that flag at line 78 only after `flush` returns, and that `flush` is the fsync (file and directory) that ran up to 154 ms. Frames in that window call `commit_effects` → `submit` with an empty write list, see `pending == false`, and enqueue nothing. `drain` then treats "idle and nothing queued" as success (line 110) even though the failed keys sit only in the writer's map. `onPause` posts that drain behind the exact thread and waits; once it returns true, Android may kill the process (including after `onPause`, before `onStop`). Those keys never reach the next attempt. Today's `flush` ran on the commit thread, so the next commit, empty or not, retried them before it returned. A later commit that does have writes still retries, because it shares that app's `StoreWrites` map. The hole is the empty commit, which is what `submit`'s comment says it still handles. `failed_store_writes_retry_on_commits_without_writes` stays green because `step` drains before the empty `advance`, so `pending` is already visible. Fix: in `submit`, also queue an empty retry while `queue.busy` is set or this app already has commits queued (a flush in progress can still fail). Keep collapsing only when this app's last queued commit is already an empty retry. `drain` then waits for that retry. When `drain` first finds the queue idle with `pending` set, queue one empty retry per app that still has failed keys and keep waiting for the time left, so a failure that surfaces as the activity pauses is attempted once before the process can be killed.

**Non-blocking**

1. `host/linux/src/system_support.rs:117` — The writer resolves `store_root` / `secret_root` when it flushes, from `HOME`, `XDG_*`, `EXACT_AGENT`, and `EXACT_AGENT_STORAGE` at that moment. A commit submitted under one environment can land in another tree if those variables change before the writer runs. `Ok(None)` (a nameless drive) clears that app's whole pending map, including failed keys from earlier commits that were waiting for the previous root. Shipping Android sets `HOME` / `XDG_DATA_HOME` once in `Native.start` / `startAsync` before boot, and a later start in-process leaves the environment alone. The retry test drains before it restores `HOME` or sets `EXACT_AGENT`, so it never covers this gap. Fix if a commit should keep the tree it was made against: resolve both roots in `submit` and store them on the queued commit; have `flush` use those paths, and do not `clear()` pending keys because a later environment read returned `None`.

2. `host/linux/src/system_support.rs:25` — The boot snapshot waits at most 5 s, then reads the kv and secret files while the writer may still be inside the same `flush`. That read can observe a name-ordered prefix of a commit (each key is still temp + fsync + rename + directory fsync, as in `FileStore::set` / `delete` and the secrets `FileStore`). The runner then boots from that mix while the writer finishes the rest to disk, so memory and disk disagree for the session. Fix: if `drain` returns false, do not read; keep waiting, or boot with an empty snapshot and say so.

3. `host/linux/src/store_writer.rs:89` — Warnings are one process-wide list, taken by whichever `submit` runs next. A failure is logged on a later commit than the one that queued the write whenever that commit arrived before the writer stored the warning, and a second host in the process logs the other app's line. `teardown::finish` drains and does not log what is still in the list. Per-app data ordering is intact: one `StoreWrites` map per app id, commits run one at a time in queue order, and a crash mid-`flush` can leave only a name-ordered prefix of that commit's keys, including failed keys merged into the next `flush` the way today's map did. Fix: key the warning list by app id and return only that app's lines; on orderly exit, log anything still queued.

4. `host/linux/src/host_tests.rs:104` — `step` drains, then `advance`s again and returns. That second advance queues another empty retry and does not wait, so the writer's next `flush` overlaps the test's `remove_dir` / `create_dir` / `set_var` on `HOME` and `EXACT_AGENT`. Drain again at the end of `step`, and change the environment only after that drain. `store_writer_tests.rs:88` calls `store_snapshot`, which itself drains for up to 5 s, so the "read back with no drain" check never observes the runner's in-memory store. The same test's final values also pass if several queued commits were merged in order. The `GATE` seam is valid: the writer takes it after `busy = true` and before `flush`, so a 50 ms `drain` times out and the directory stays empty. The abort child is valid on Unix (`abort` is signal 6, no destructors); it checks a kill after a successful drain, not a kill while commits are only queued.

Deadlocks: none. `Owner.drainStore` (`Owner.kt:353`) posts to the exact thread and `task.get` waits at most 2 s on the main thread; `Native.storeDrain` then waits on the writer, which only does filesystem work. The snapshot drain and `teardown::finish` wait on that same writer and do not run on it. The 2 s cap includes time already spent queued behind the exact thread. A foreground kill, or a drain that hits the cap with a backlog longer than the cap, loses writes that today's commit had already synced before it returned. After a finished drain, a crash can leave only a prefix `flush` could already leave. Apple's `persist()` and the web host are unchanged.
