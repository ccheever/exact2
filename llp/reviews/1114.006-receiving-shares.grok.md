I'll review LLP 1114.006 for directional and architectural issues only. First I'll read the parent summary, the RFC, and the rules it depends on.## Verdict

RIGHT WITH CHANGES.

## Overall assessment

Receiving a share as the manifest's `share_target`, and turning text and a URL into one location through LLP 1038 D8, is the right capability and the right layer. The Apple side is also right: a generic share extension with no Contract session, files streamed and converted in the main app, a separate signed target as LLP 1030 D6 already describes. The design breaks where a file path is treated as a query parameter. That choice fights the security rule in the same document, the web host's actual launch path, and LLP 1030's refusal of a service worker. Those are the parts to change before this is built.

## Concerns

### 1. BLOCKING — File paths in the location cannot be both unforgeable and delivered on the web

D3 says a path is a capability, so the runner strips every `files` parameter unless the host composed that location through `deliver_share` rather than `openURL`. D4 then delivers web files by a service-worker `303` to that same composed URL (`/compose?photos=app:/tmp/shared/…`). On the web the launch location is the document URL. `launchLocation` in `host/web/navigation.js` returns `pathname + search`, and LLP 1038 D5 makes that the boot fact. A `303` is an ordinary navigation, so the runner strips the paths and the share arrives with no files. Trusting that URL instead makes `/compose?photos=app:/data/session.db` work for any page that can link to the installed app, which is the attack D3 names.

The web's own file-share pattern does not put bytes or paths in the query. [Level 2](https://w3c.github.io/web-share-target/level-2/) posts `multipart/form-data` to the service worker; [Chrome's guidance](https://web.dev/articles/files/receive-shared-files) stashes the `File` and redirects with a marker. The picker already has the other half of this: LLP 1069.002 D3 delivers a `list` of `Picked` from the host, and the path never appears in a navigable URL.

`searchParam` also cannot read the repeated form D3 specifies. `route/src/location.rs` implements `URLSearchParams.get`: the first value only. Several photos, which is the clone's case, need a list.

**Resolve:** Keep `title`, `text`, and `url` as query parameters. Never accept a file parameter from a URL the browser or another app supplied. The service worker (and the extension) stash the files and redirect or open with an opaque token. The host checks the stash and calls `deliver_share`, which is what attaches the paths. A forged link has no stash, so there is nothing to honor. Deliver the files as a list the app can read, the way the picker does.

### 2. MAJOR — The file path requires exact2's first service worker, and LLP 1030 forbids one

Text and URL shares are a `GET` navigation. No worker. Files are Level 2 `POST`, and a page cannot read the body of the navigation that loaded it, so a service worker is mandatory on the web. LLP 1030 D1's web row is "no service worker in v1" because a fresh load is what makes the origin current. D5 keeps propagation to "static files, no service." LLP 1030.003 D4 repeats that an installed PWA is updated by fetching the envelope, not by a worker. A fetch handler makes the registration the page's controller and adds a second update channel beside that envelope check. "Not loaded before first pixel" covers the boot budget and leaves this delivery invariant untouched. The document never asks Charlie to overturn it.

Web file shares also reach only an installed Chromium app. Safari and Firefox have no share target. The clone can already attach images with the picker.

**Resolve:** Make the worker its own ruling. Admit it only as a fetch handler for that `POST`, with no caching and no `respondWith` on any other request, registered after first pixel. Or ship `GET` plus the Apple extension and leave web files until a worker is accepted on its own.

### 3. MAJOR — The recommended iOS handoff is an API Apple has already broken, and text has no fallback

Q2 recommends walking the responder chain to `UIApplication.open`. Apple DTS, on the iOS 18 break of the old `openURL:` form, said extensions are not allowed to open URLs and that the bypass is intentional ([thread 764570](https://developer.apple.com/forums/thread/764570)). Variants still ship, including Bluesky's, and they still get blocked in later releases. D6 step 2 keeps text and URLs only in that URL, with no App Group. Step 5's "the share is never lost" applies to files. A text share whose open fails is gone. A second app that registers the same scheme receives the shared text.

**Resolve:** Record every share, text included, in the App Group. Claiming pending tokens on the next activate is the mechanism. Opening the containing app is best-effort.

## What it gets right

The declaration is the web manifest key, checked and baked the way `file_handlers` already is, so a browser reads it unchanged. Text and links need no new event, and the clone's `/compose` route already exists. The extension stays a small second binary: no `ExactKit`, no decode, no in-sheet composer, conversion on the main app, which is the right call under the extension memory limit. Receiving stays grant-free, with a reach-table row, matching the picker. tvOS, Linux, Windows, and Android-without-a-package are refused for real platform reasons. The agent can already deliver a text location, and driving files through the claim path is the right test seam.
