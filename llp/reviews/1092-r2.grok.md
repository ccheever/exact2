## New findings

### MATERIAL — D3, D8. A `next` commit drops its head on every refusal.

**Problem.** The head is removed before `checkpoint()`, and the queue is restored from that checkpoint, so every refusal of the `next` commit drops the send. D3 names two drop reasons: the source refuses the ask, or the answer misses the shape. The same commit can also be refused by settlement (`DeriveType`, a cycle) or by `TaskKey` in the gate step, which runs in `update()` after the ask. The source may already have accepted the ask. `conclude` then calls `forgotten()`, the scan arms the successor, and the rolled-back answer never lands.

**Evidence.** `fulfill_measured` takes the checkpoint and only then removes the ticket (`commit.rs:937–939`), so a refused reply puts the ticket back. `conclude` restores `pending` from the snapshot (`:65–82`). D2 puts the queue in that snapshot. D3's `next` commit pops first, so the snapshot no longer has the head. `release_failed` drops a ticket only for `Data` or `Shape` (`:949–956`). A `TaskKey` from a NaN key is itself rolled back, so the refusal was not a durable bad key. A `next` commit on an already poisoned runner drops the head with no ask.

**Fix.** Leave the head in the queue through `checkpoint()`. Clear `next_due` before that commit, the way `then_due` is cleared at `commit.rs:271`, and do not restore that clear. Drop the head only when the commit stands, or when the refusal is the ask's own (source error or shape miss). On `TaskKey`, a settlement failure, or poison, restore the head and let the scan arm it again. A gate that still refuses after the rollback stops the advance with the send still waiting.

### MATERIAL — D3, D6. The JS wall clock never calls `drive()` for a queue with no `then`.

**Problem.** Putting `next_due` into `drive()`'s minimum does not schedule `drive()`. The wall-clock runtime calls it from a commit that armed a `then`, from `paint()`, and from `drive()` itself. A reply for a mutation with no `then` (D3's example, studio's `rec`) sets the due time and then waits on an idle page. `timer_due_ms` does wake Apple, Linux, and wasm, because those hosts read it every batch.

**Evidence.** `rt.js:184` is `if (m.then) { m.due = clock.now; if (!clock.agent) drive(); }`. `reply` is itself a `commit` (`rt.js:361`), so that tail is the only post-reply schedule. `drive()` (`:288–294`) does scan `Mutations`. The agent's jump predicate is `clock.timers` only (`agent.js:313`), so a jump ignores `m.next`. §5's "asked by `timer_due_ms` alone" is a runner test.

**Fix.** Arming `next_due` calls `drive()` the same way arming a `then` does, including when `m.then` is absent. The jump's `due()` includes mutation dues. The no-`then` case is a JS conformance step on the wall-clock runtime.

### MATERIAL — D8, D9, D12. The boot settle evaluates the gate before `init_late_slots`.

**Problem.** D9 turns the gate into `hide#when` / `hide#key` and evaluates them in settlement. Boot calls `settle` while late slots are still `Unit`, and only then `init_late_slots`. A gate that reads a late slot sees `Unit` and refuses boot with `DeriveType`, or caches the wrong bool. The later gate step reads that stale derive. `init_late_slots` does not settle again. Lean evaluates the gate expression after `lateSlots`, so the §5 test "a boot gate that reads a late slot" cannot pass on both.

**Evidence.** Slots start as `Value::Unit` (`router.rs:558`). Boot is `settle`, then `init_late_slots`, then arm timers, then `Tree::create` (`runner.rs:923–945`). A derive whose value is not its type returns `RunnerError::DeriveType` (`settlement.rs:311–314`). Lean `boot` applies D8 after `lateSlots` and emits the gate as an expression (`Runtime.lean:548–555`; D12). JS initializes late slots before timers (`emit.rs:413–418`, timers near `:541`), and `memo` is lazy, so the first JS settle can see the initialized value. §4's call sites are `runner.rs` and `settlement.rs`. `Runner::update` is `lists.rs:44`, and boot's first frame is `Tree::create`. Hooking the end of `settle` is this early read. `settlement.rs` is 1,451 lines.

**Fix.** Do not evaluate gate derives in the settle that precedes `init_late_slots`. Evaluate the gate expression in the boot step after `init_late_slots`, as Lean does, and on later commits after that commit's settlement. Hook `Runner::update` and the boot `Tree::create` site. Keep the gate step in `gates.rs`.

### MATERIAL — D8, D10. Seeking still fires an idle frame task.

**Problem.** Idle-skip is specified for `frame()` and for `paint()`, the presenting paths. A seek fires frame tasks inside `advance_within` from `next_ms` whenever the host is not presenting. "Dropped" is not a non-finite deadline, and "`timer_due_ms` reports only armed tasks" does not change who `advance` fires. `advance(60_000)` and sixty `advance(1_000)`s both use that path, so the §5 equality holds while the idle task runs.

**Evidence.** `advance_within` takes every timer with `next_ms <= now_ms` when `frames` is set, and `frames` is `!self.presenting` (`commit.rs:214`, `:240–245`). `frame()` is the presented path (`:156–187`). In the JS target, `gated()` calls `paint()` on arm, and `paint` returns immediately when `clock.agent` is set (`rt.js:301`). The re-armed seek timer needs `virtual_frame(now, 1)` inserted into `clock.timers`.

**Fix.** Dropping a frame timer clears its deadline, the same as a spent `after`. `advance_within` fires a frame task only when it is armed. On a seek, `gated()` inserts the timer at that virtual-frame due.

### MATERIAL — D12. Lean drains the queue once, before any timer in the advance.

**Problem.** "advance drains before timers, a commit each" empties the queue as a prologue. The runner, after every commit, scans and runs due `next`s before later timers (D3: at one time, thens, then nexts, then timers). A timer action that sends twice to a queue mutation asks the second send in that same runner `advance`. A prologue-only Lean `advance` leaves it queued until the next clock event. `random --count 500` diverges. The generator may emit two sends to a queue mutation.

**Evidence.** Lean `advance` fires timers by calling `runAction` and does not look at a queue between fires (`Runtime.lean:604–631`). `runAction` asks every send today (`:477–483`). One `Event::Clock` is a single `r.advance` (`observe.rs:201–203`). `observe` prints no waiting counts, so a tap-only `queue-two-sends` shows one ask until a clock step drains the rest.

**Fix.** Inside Lean `advance`, after every commit, drain sends queued at the current clock before the next timer, one commit each. `runAction` queues a later send. A corpus clock step observes the second ask, and `observe` prints the waiting counts.

### MATERIAL — D13. Chat2 is not chat's adoption.

**Problem.** "Chat2: the same" copies chat's two toast tasks (1,500 ms and 4,000 ms, keyed on `toastUndo`) and chat's `pending(stepped)` story. Chat2 has one toast, 1,600 ms, keyed on `toastUntil`, and its poll guard is `pending(changed)`. Following D13 adds fields chat2 does not have and changes the toast.

**Evidence.** `chat2/app.contract:117–124` clears on `now() >= toastUntil` and sends while `phase == "wait"` and `not pending(changed)`. `toastUntil = now() + 1600` is at `:149` and `:167`. There is no `toastUndo`. Chat is `chat/app.contract:146–153`: `now() - toastAt > (toastUndo ? 4000 : 1500)` and `not pending(stepped)`.

**Fix.** One task, `when toast != "" key=toastUntil after(1600, …)`, and `when phase == "wait" every(200, …)`, keeping `not pending(changed)`.

### MATERIAL — D13. `expire` and chat's `tick` use a strict `>` that is false when `after` fires.

**Problem.** `after(5000, expire)` fires at the commit's due time (D8: now is that commit's time). The assigning commit sets `toastUntil = now() + 5000`, so the fire runs with `now() == toastUntil`. `expire` clears only when `now() > toastUntil`, the action writes nothing, and a spent `after` stays spent. The toast never clears. Chat's `tick` has the same strict `>` against 1,500 and 4,000, so a toast task that calls `tick` sticks the same way. The stage-2 check, no commit at rest over `clock +60000`, is the idle case with no toast.

**Evidence.** `ledger2/app.contract:64–66`, with `toastUntil = now() + 5000` in `afterChange`. Chat's predicate is `chat/app.contract:149`. The current `every(1000)` clears because the next poll is late.

**Fix.** The fire action clears the toast, and ledger2's `undoId` or chat's `toastUndo`, without testing `>`. The timer already measured the interval.

An implementer who only edits the files §4 names either misses that early return or reads the gate at the end of `settle`, which is the boot bug above. `settlement.rs` at 1,451 lines cannot hold the step. The nine new files themselves fit the cap.

**Fix.** Name `commit.rs`, `admission.rs`, and `lists.rs` as the call sites. Keep queues in `runner/src/runner/queue.rs`, beside `commit.rs`, and the gate step in `gates.rs`.
