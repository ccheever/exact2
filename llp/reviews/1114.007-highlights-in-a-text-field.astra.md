**1. Verdict: RIGHT WITH CHANGES**

**2. Overall assessment**

The capability and its placement are right: the app detects ranges, the host paints them, and the field retains its ordinary string value and editing behavior. This matches [Bluesky’s native composer](https://github.com/bluesky-social/social-app/blob/main/src/view/com/composer/text-input/TextInput.tsx). The browser premise also checks out: [OpaqueRange supports Custom Highlights inside form controls](https://blogs.windows.com/msedgedev/2026/09/21/new-in-edge-for-developers-create-better-components-and-make-your-site-agent-ready/). One architectural issue needs resolution: how a computed range set identifies the text it describes.

**3. Concerns**

**MAJOR — D3 combines mutable host ranges with a snapshot API that carries no freshness information.**

[D3](/Users/ccheever/projects/exact2-review-1114/llp/1114.007-highlights-in-a-text-field.rfc.md:160) says the host shifts ranges while typing, drops them on an external value change, and replaces them when the app’s next list arrives. But Exact’s properties communicate changed state, not every recomputation: [binding emission skips equal values](/Users/ccheever/projects/exact2-review-1114/runner/src/instance.rs:851), and [resource settlement preserves equal answers](/Users/ccheever/projects/exact2-review-1114/runner/src/runner/settlement.rs:712).

For example, replacing the draft `@alice` with `@carol` produces the same `{name: "mention", start: 0, end: 6}` list. Following D3 literally drops the existing highlight, while the fresh, equal list produces no property update to restore it. Reapplying the stored list whenever text changes does not generally solve this either: during delayed recomputation, that list may still describe the previous text.

This is a mismatch between the proposed ownership model and the runner’s update semantics. **Resolve it by associating each range set with its source value or edit revision**, and defining reconciliation against the field’s current text. An equal range list for a new text snapshot must still establish freshness. Host shifting can remain temporary presentation while the matching answer is pending.

**4. What it gets right**

Keeping detection outside the kernel and preserving a plain string avoids unnecessary editor machinery. TextKit rendering attributes are the appropriate native layer: [Apple explicitly distinguishes them from attributes affecting layout](https://developer.apple.com/videos/play/wwdc2022/10090/). The limited scope, absence of new grants, and inspection through existing agent operations also fit the repository’s principles. The explicit no-paint fallback is reasonable for decorative highlighting.

**5. Questions for Charlie**

Add one ruling: **Are highlights authoritative snapshots tied to a particular draft value, with host-shifted ranges only provisional?** I recommend yes. That establishes the ownership boundary before the public API and native tracking mechanism are committed.

I would retain the recommendation against a browser mirror. I found no other directional concerns.
