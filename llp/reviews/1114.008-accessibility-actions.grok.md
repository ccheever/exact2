I'll review LLP 1114.008 for directional and architectural issues only. First I'm reading the parent RFC, the document itself, and the repository rules it depends on.The RFC's load-bearing claims are about Bluesky's real actions, the unmerged `aria-actions` spec, and how exact2's hosts expose accessibility today. I'll check those against the parent LLP, the code, and the platform sources.## Verdict: RIGHT WITH CHANGES

## Overall assessment

Adopting `aria-actions` as a list of ids of real controls, passing that attribute through on the web, and mapping it to each platform's custom actions is the right capability and the right layer. The context-menu half matches Bluesky's actual chat-message behavior. The design goes wrong where iOS treats the attribute as a reason to collapse the element into one accessibility node. That is not what the proposal does, and it breaks the notification behavior this RFC is for.

## Concerns

### 1. BLOCKING — `aria-actions` must not flatten the iOS tree

**What is wrong.** D3 and Q2 make any element with `aria-actions` one accessibility element, so VoiceOver reaches descendants only as actions. The proposal does the opposite. Action targets stay in the tree, including inside roles that otherwise have presentational children. Sarah Higley's implementation notes show an `option` whose name is the filename and whose Edit and Open buttons remain child nodes, and are also custom actions. The RFC already keeps children on macOS for that reason. iOS would be the host that deletes them.

That also misses Bluesky's notification, which is the cited use. In `NotificationFeedItem.tsx` the row is one element only while the author list is collapsed (`accessible={!isAuthorsExpanded}`). The actions are not both expand and profile: a grouped row has Expand/Collapse, and a single-author row has "View profile". Expand exists so the people become separate elements. The `viewProfile` action is declared and not handled in `onAccessibilityAction` (only `activate` and `toggleAuthorsExpanded` are). A permanent collapse leaves the expanded list unreachable, which is the feature.

exact2 already refuses this trade for text. `TextInteraction.swift` does not make a paragraph an accessibility element when it contains links, and `textAccessibilityChildren()` exposes the paragraph plus those links, because UIKit will not visit a container's children once the container is itself an element. `SwipeActionsIOS.swift` flattens a row only when the body is a labelled button. The other branch leaves `isAccessibilityElement` false.

**Why it matters.** One Contract source would navigate differently on iOS than in Chrome, which is the parity oracle. The parity check D5 extends compares action names, so it stays green while the children disappear. Before 1.0 this can be deleted, but the clone would be built on the wrong tree.

**What resolves it.** Do not infer a leaf from `aria-actions`. Leaf-ness stays with the roles that already set `isAccessibilityElement` (`NodeViewIOS.swift`, `actsAsButton` and `role="img"`). A column that is not an element gets a summary accessibility element that carries the actions, with descendants still exposed, on the paragraph pattern. The collapsed notification is an author choice: a flattening role while collapsed, and not that role once expanded. Change Q2's recommendation to no.

### 2. MAJOR — activating an action is not the target's own accessibility activate

**What is wrong.** D3 presses the target through `accessibilityActivate` / `accessibilityPerformPress`. Those are what run when VoiceOver focuses that control and activates it, so on macOS, where the child stays in the tree, the cursor moves onto Reply or Like.

The proposal's focus rule is the other way. [w3c/aria#2691](https://github.com/w3c/aria/issues/2691) asks that the screen-reader cursor stay on the referencing element. [w3c/aria#2845](https://github.com/w3c/aria/pull/2845) was merged into the `aria-actions` branch on 2026-10-02: the browser clicks the target, allows DOM focus to move, fires no accessibility focus events, and returns focus to the referencing element unless something else moved it. The web host gets that by writing the attribute. The native hosts, as specified, do not.

**Why it matters.** Q1 says exact2 follows the proposal if its meaning changes, and this part of the meaning is already on the branch. A feed that drops the user onto the button they invoked is a different product from the one Chrome ships.

**What resolves it.** Native activation runs the target's press, then leaves the accessibility focus on the referencing element. It does not call the target's `accessibilityActivate` as if the user had moved there. The web stays a pass-through.

## What it gets right

The correction in §2 is right. Feed posts in `social-app` at `35fd4fbad` are separate buttons with no custom actions. The chat message is one element whose action opens the context menu (`ActionsWrapper.tsx`: "Open message options"). Rejecting React Native's `{name, label}` plus `accessibilityAction` is right: that shape is not the web, and it allows an action with no control. A space-separated id prop, beside `accessibilityLabelledBy`, is the existing Contract shape. Passing `aria-actions` through on the web is the right host behavior. Chrome 151's release notes ship it on desktop and not on Android or ChromeOS, as the RFC says, and the PR was still open on 2026-10-01. D4's macOS `accessibilityPerformShowMenu` is the platform action, and the iOS half correctly waits on a device check. No new grant, no new agent operation, and no AT-SPI work are the right boundaries. Linux accessibility stays deferred in LLP 1015, and driving VoiceOver stays refused in `rules/DEFERRED.md`.

## Questions for Charlie

**Q2 is the one to change.** The recommendation should be no. `aria-actions` adds actions. It does not decide whether children are in the tree. The notification's collapsed and expanded shapes are an author-controlled leaf, toggled with the expand action, not a property of the attribute.

**Q1 can stay yes.** Firefox and Chrome 151 desktop already ship the attribute, and an unmerged name is acceptable under delete-don't-deprecate. "Follow the proposal" has to include the focus-return rule in the branch, not only the attribute.

**Q3 is right.** The chat message is this, and the macOS show-menu path is the platform's own action.
