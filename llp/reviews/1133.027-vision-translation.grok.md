### 1. The session window is the wrong seam, and a view added to it does not run `translationTask`

**Where:** §0 item 4 (lines 119–127), §1 (lines 157–159), D9 (lines 504–518), D17 item 3 (lines 722–729), §8 (lines 853–854), §13 question 5 (lines 1155–1157).

**Problem:** D17 adds `window` (`UIWindow` or `NSWindow`) and §8 amends LLP 1133.018 D13 item 1 as if that amendment were the presentation anchor contacts asked for. The accepted seams are different objects. Hosting by adding a zero-size controller to that window also never starts the SwiftUI task D9 depends on, so the `fatalError` guard does not hold.

**Evidence:** LLP 1133.015 D16 item 3 (accepted, not built) already names the seam `presentation`: a `UIWindowScene` on iOS, and on macOS the `NSWindow` plus its content `NSViewController`, nil while no window of the session is in front. StoreKit's `purchase(confirmIn:)` takes the scene. LLP 1133.018 D13 item 1 then adds `anchor`, the frame of the pressed node inside that window, because a macOS `CNContactPicker` must be shown relative to a rect. LLP 1133.020 row 9 records the missing piece as that rect: a Mac picker falls back to the window's centre. `ExactPackageContext` still has neither (`host/apple/modules/ExactPackage.swift`). A `UIWindow` supplies neither the scene nor the rect.

`translationTask` runs only while its view is in a view controller that receives appearance callbacks, and `TranslationSession` fatal-errors if used after that view disappears (Apple's `TranslationSession` docs). `addSubview` of a `UIHostingController`'s view, without `addChild`, does not forward `viewWillAppear` / `viewDidAppear`. SwiftUI then never starts the task, and `onDisappear` never marks the session dead. D9's "adds it to the session's window" is that pattern.

**Decision:** Build LLP 1133.015's `presentation`, and host one child of that session's view controller (on iOS, the scene window's root view controller). Leave LLP 1133.018's anchor rect to contacts. Drop the amendment that says this window is that anchor.

### 2. The live-scan substitute analyses a file the camera does not hand over

**Where:** §0 item 3 (lines 112–118), D17 item 2 (lines 715–721), §9 (lines 876–881), drive 1 (lines 1005–1008).

**Problem:** Drives 1–3 are specified to put an ISBN in front of the agent's camera and read it from `seen`. As specified, the observer never receives those pixels, and the prefer they set does not change the picture.

**Evidence:** The built camera picture is a record, not a string. `CameraModule.preferred` reads `values["picture"]["path"]` (`packages/camera/apple/Camera.swift` lines 94–99); LLP 1133.008's as-built note says the drive form is `prefer extension camera.picture={"path":"assets/sample.jpg"}`. A string prefer is ignored, so the viewfinder stays on `packages/camera/fixture/card.jpg`, which is not a barcode.

That path is resolved only inside the camera package: `EXACT_ASSETS`, the bundle, or `#filePath`'s sibling `fixture/` (`agentPictureURL`, lines 274–281). It is not an `app:/` path, so `context.file` will not open it, and the barcode package is told not to read `camera.picture` itself. On the web the agent picture is a `data:` URL of JPEG bytes (`packages/camera/web/index.js` lines 93–101). Consumers are told `live(null)` and draw that image themselves (`packages/media-capture/web/video.js` lines 20–22). The as-built camera viewfinder is a plain image, not a `captureStream()` in the `<video>`, so there is no frame for `BarcodeDetector.detect(video)` either. Android reads the same asset privately (`packages/camera/android/Camera.kt`).

**Decision:** The track entry carries the bitmap the viewfinder is already drawing. Drives use the record form and a path the camera resolver can open. The unattached `<video>` remains the production web path. The agent path runs the detector on those pixels.

### 3. A default scan does not return the same UPC-A value on Apple and Android

**Where:** D3 (lines 252–256), D6 (line 350), D11 (lines 580–586).

**Problem:** D3 says a clean barcode's `rawValue` is the same everywhere because the symbology defines it. D11's mapping makes a UPC-A disagree, and a default scan on Apple never returns `upc_a` at all.

**Evidence:** `VNBarcodeSymbology` has no UPC-A. Vision and AVFoundation report it as EAN-13 with a leading zero (the `ean13` documentation this RFC cites). ML Kit's `FORMAT_UPC_A` returns format UPC-A and the 12-digit value. D11 converts to `upc_a` and strips the zero only when `upc_a` was requested and `ean_13` was not. D6's omitted `formats` means every supported format, which includes both, so the Apple default keeps `ean_13` and 13 digits. `getSupportedFormats` can still list `upc_a`. The web cell returns the browser's `BarcodeDetector` result with no normalization, so Chrome on macOS (Vision) can add a third spelling.

**Decision:** If the payload is 13 digits with a leading zero and `upc_a` is among the requested formats, including the default, every target reports `upc_a` and the 12-digit value. Report `ean_13` and 13 digits only when `upc_a` was not requested. Apply that normalization to the browser's result too.

### 4. `zh-TW` does not reach a Traditional Chinese model on ML Kit, and BestFit does not define that mapping

**Where:** D7 (lines 398–405), §9 (lines 894–897).

**Problem:** Tier 1 says `zh-TW` matches both Apple's and ML Kit's Traditional Chinese through ECMA-402 `LookupMatchingLocaleByBestFit`. ML Kit has no such model, and that algorithm does not promise that result. The agent then treats Traditional Chinese as available on Android.

**Evidence:** ML Kit's translation language list has one Chinese entry, `zh` (Simplified). There is no `zh-TW` or `zh-Hant` model; a best-fit fallthrough translates Traditional Chinese as Simplified. Apple's Translation framework does distinguish `zh-Hans` and `zh-Hant`. ECMA-402 leaves BestFit implementation-defined. This repo's own truncation (LLP 1060) is `zh-Hant-TW`, then `zh-Hant`, then `zh`. The agent's fixed list includes `zh-Hant` and applies no Android restriction (only tvOS is named), so a scripted drive of Traditional Chinese passes on Android and fails on a device.

**Decision:** Ship an explicit tag table. On Apple, `zh-TW` and `zh-Hant` select `zh-Hant`. On ML Kit, those tags are `unavailable` / `unsupported-options` until a Traditional Chinese model exists. The agent's list applies that restriction.

### 5. One failed frame stops the live scan

**Where:** D2 (lines 209–220), D5 (lines 309–314).

**Problem:** D2 tells the implementation to answer `OperationError` when Vision or ML Kit fails. For `detectedBarcodes` that reply is not polled again, so Shelf's scan ends on a single bad frame and `seen` stops growing.

**Evidence:** `note_poll_answer` inserts an error reply into `extensions.failed`, and `polled()` skips those keys until a reader asks with new arguments or the implementation announces a change (`runner/src/runner/modules/poll.rs` lines 86–104). LLP 1133.009 records the same rule. `BarcodeScan` already has an `error` field, but D2 does not say a per-frame failure uses it. `NotFoundError` for a track the session does not hold should keep stopping the poll. A Vision completion error on one buffer should not.

**Decision:** A frame that fails to analyse sets `BarcodeScan.error` and is a normal answer, with `state` still `scanning`. `OperationError` is only for a detector that cannot be created.
