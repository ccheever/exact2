## Overall assessment

Paint-only named ranges over a plain string is the right capability, in the right layer. Bluesky's native composer only sets `color` on segments (`TextInput.tsx`, the `textDecorated` map). The posted record stays plain text plus facets. That is not rich text, and LLP 1045 D1, LLP 1008's plain-text textarea, and LLP 1035.006 row 03.12 all stay standing. The web path matches the platform: Chrome 152's release notes (stable 2026-08-25) ship `OpaqueRange` for `textarea` and text `input`, including CSS Custom Highlight integration, and the Microsoft explainer specifies the same UTF-16 offsets, incremental shift, and wholesale-value reset this RFC relies on. WebKit and Mozilla have not shipped it. A mirror or a `contentEditable` composer would be a second editor, which is the thing this API exists to avoid.

## Concerns

None that meet the bar.

## What it gets right

- The app owns detection. The host only paints. A `markup="facets"` grammar, or a rich value, would bake one product into the kernel and put a serializer on the string.
- The kernel shape fits the schema. Props are scalars (`kernel/tables/schema.json`), and `measure: true` is what invalidates text size. One paint-only `str` does not move layout. UTF-16 matches `selectionStart`, `slice`, and `indexOf` (`docs/contract-grammar.md`).
- Refusing `input` and `markup="markdown"` avoids a second native field path and a second styler. The Markdown editor already mutates text storage (`MarkupEditor.swift`); highlights should not share that path.
- Host-side shifting is the right fix for the real gap. Apple and the web both keep a typed buffer ahead of the bound value, and both skip the write when the echo is the same string (`TextAreaIOS.swift` `writeValue`, `host/web-js/rt.js` only assigns `.value` when it differs). During that gap an unshifted range colors the wrong characters. Clearing until the data module answers would flash on every keystroke. Shifting, then replacing with the app's list, matches `OpaqueRange`.
- `setRenderingAttributes:forTextRange:` is a real TextKit 2 method, separate from storage. `isRichText = false` can stay. Windows app UI rides the Linux presenter (`host/windows/src/lib.rs`), so one paragraph painter covers that row.
- No grant. The agent gets `tree`, `state`, and `screenshot`, and no new operation. Chrome is the paint oracle because it is the only engine that can paint this.

## Questions for Charlie

None missing, and neither recommendation should change. A `highlight` declaration that rejects layout properties is what keeps the paint-only rule a build failure. Painting nothing where `createValueRange` is absent is the right web fallback: Safari and Firefox still edit a normal textarea, and a mirror is the drift the design is written to avoid.
