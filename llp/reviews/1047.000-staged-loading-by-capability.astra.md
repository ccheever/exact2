## Review (verbatim)

Verdict: RIGHT WITH CHANGES.

Overall assessment: Keep the proposed order: remove unused code, stage capabilities with identifiable entry points, measure, then reconsider the remaining core. The analysis supports that direction, and I see no alternative that clearly dominates it. The substantive change is to distinguish a byte-attribution map from a safe loading boundary. The latter needs stronger guarantees than function names and successful splitting. This was a read-only review; I did not reproduce the measurements.

Strengths:

- §1 correctly shifts attention from first content to runtime readiness. The supplied React SSR comparison supports this: with inline CSS, content paints at roughly the same time, while exact2’s runtime becomes available substantially later. Links and captured presses improve early behavior without eliminating that runtime delay.
- §§2–4 and parent §10 identify the right scale of opportunity. Attribution is explicitly non-additive; Taffy is already absent; and the kernel still provides useful tree, transaction and style machinery. The estimated savings from error codes and a DOM-only kernel are reasonable grounds for declining those changes now, although they remain estimates rather than measured replacement implementations.
- §§5–6 correctly distinguish eliminating code from postponing its download. Shared-memory secondary instances are a sensible mechanism for functions operating on the same Rust state. Binaryen already provides the cross-module call and table rewriting this requires. [Binaryen implementation](https://github.com/WebAssembly/binaryen/blob/main/src/ir/module-splitting.cpp)
- Inspection and Markdown are sensible first candidates. Inspection has a distinct consumer; Markdown has a recognizable rendering seam. Keeping “neither” available in §6 is also right.

Concerns:

1. HIGH — The attribution map is not a safe partition specification (§5).

   scripts/metrics.mjs assigns ownership from names. Parent §10 already records LLVM merging a core-used function with a Markdown function and retaining the Markdown name. There are also ordinary runtime dependencies on inspection-namespaced helpers: runner/src/runner/lines.rs uses agent::num for journal timestamps.

   Consequently, gating the intended Markdown or inspection entry point does not necessarily guard every call to functions assigned to that stage. A compiler optimization or refactor could turn an innocent core operation into a premature call.

   Resolve this by using names to nominate functions, then establishing the boundary against optimized callers and the explicit capability seams. Shared or ambiguous helpers should remain in core. The first correctness check should boot and exercise a normal page with inspection unavailable, then attach an agent afterward. A smoke that loads inspection immediately could conceal this failure.

2. MEDIUM — Readiness must be established before an operation crosses the boundary (§6, §8.2–3).

   The current host dispatches into the runner before emitting the resulting DOM properties; Markdown parsing happens during that emission. Discovering a missing module there is too late to simply await and repeat the action: state or effects may already have changed.

   Page preloads help, but a server-observed tree is not necessarily everything the page can subsequently need. Local state, authentication and delayed data can reveal additional capabilities without navigation.

   Resolve this with conservative route capability sets, including shared components and possible branches, and an explicit wait before the dependent operation commits. Start with coarse readiness barriers where necessary. Network failure should produce a controlled failure while preserving usable content; the trap should remain an assertion that the barrier was bypassed.

3. MEDIUM — The benefit needs a complete startup measurement (§§1, 5–6).

   Approximately 205 KB is a projected core download after additional work. An article also needs roughly 13 KB of Markdown, and both pages need their JavaScript and other activation resources. The four-way experiment’s overhead cannot simply be carried forward unchanged after unlinking two groups.

   On the cited link, removing 45 KB buys roughly 225 ms of transfer time before other effects. That is worthwhile, but substantially smaller than the observed runtime-readiness gap. Parallel preloads also share bandwidth; they do not make required bytes free.

   Resolve this by measuring the finished artifact set on home and article pages, including first navigation into Markdown. Report navigation-to-ready, press-to-result, total bytes through readiness and content paint. Add presses at fixed times after navigation alongside presses at load, because load itself moves. The appendix does not directly establish signed-in mutation or form latency, so include an actual runtime-dependent interaction on both implementations.

Suggestions:

- Keep the shared-memory approach for the first implementation, but pin the Binaryen version and treat all split outputs as one build. Load them from the existing immutable asset namespace, bind the complete generated imports, and exercise delayed modules and different loading orders on supported browsers. This belongs in the existing production verification, not a new process.
- Separate-memory artifacts are a reasonable fallback for a coarse interface such as Markdown parsing. They trade simpler isolation for support-code duplication and data transfer. They are less natural for inspection of live runner state and do not presently justify changing direction.
- §5 overstates the necessity of synchronous fallback for profile splitting. Partition selection and loading policy are separate decisions: a profile-selected partition can also be gated. JSPI can suspend Wasm at an asynchronous import, although integrating that requires Promise-facing exports and careful handling of reentrancy. That corrects the claimed inevitability; it does not make JSPI the preferred next step. [JSPI design](https://github.com/WebAssembly/js-promise-integration/blob/main/proposals/js-promise-integration/Overview.md)
- Broaden “decide the core” slightly. Consider deterministic splits by operation or phase, and further compiler-derived specialization of runner features, alongside profiling and general size reduction. Also revisit cold data retained in the primary—parent §10 explicitly identifies it. The residual primary is not necessarily irreducible core.
- Make that decision from the new critical path. Download, compilation, boot/adoption and data activation are separate costs; faster readiness may come from reducing work without reducing bytes. The runner is the better architectural investigation than another kernel, but its attributed size alone does not establish the next bottleneck.

Recommended next step:

Finish tree shaking, then implement one narrow capability-loading experiment with Markdown and inspection. First prove normal operation while stages are deliberately withheld and correct waiting when they become necessary. Then measure the complete loading path against React SSR. Proceed to a core experiment only if those results show a remaining delay worth addressing; another design-review round is unnecessary.
