I worked alone and changed no files. I traced the code and exercised the existing compiler through stdin; I did not build an implementation of either proposal.

For **auto spacing, r2**, the earlier reviews are substantially addressed: the sentinel is explicitly reserved; percentage gaps are excluded; resolution uses Rust’s kernel style; reverse directions, grid, and block are defined; both Swift channels and both web writers are named.

1. **should-fix — The mixed-value typing and branch-validation changes are still missing from the build plan.**  
   D1 promises number/`"auto"` choices, but §3 names only `values.rs` and prop lowering ([RFC:25](/Users/ccheever/projects/exact2-wt-buttons2/llp/1053.000.000.000-glass-auto-spacing.rfc.md:25), [RFC:35](/Users/ccheever/projects/exact2-wt-buttons2/llp/1053.000.000.000-glass-auto-spacing.rfc.md:35)). The earlier type pass permits mixed number/string arms only for style attributes; ordinary props go through normal inference, which rejects them ([checks.rs:1167](/Users/ccheever/projects/exact2-wt-buttons2/contract/types/src/checks.rs:1167), [types/lib.rs:951](/Users/ccheever/projects/exact2-wt-buttons2/contract/types/src/lib.rs:951)). Prop lowering happens afterward ([lower/lib.rs:1263](/Users/ccheever/projects/exact2-wt-buttons2/contract/lower/src/lib.rs:1263)).

   The existing compiler confirms that `glassGroup=(true ? "auto" : 8)` fails with `type-branches`. Conversely, `glassGroup=(true ? -2 : 8)` compiles: today’s range check examines the outer expression, not each numeric branch ([values.rs:497](/Users/ccheever/projects/exact2-wt-buttons2/contract/lower/src/values.rs:497)).

   **Concrete change:** Add narrowly scoped type-pass handling for `glassGroup`, recursively validate supported choices—including nested ternaries and `match`—and rewrite literal `"auto"` to numeric `-1` before bytecode compilation. Validate authored numeric literals before that rewrite so the internal sentinel does not become an accepted negative literal. Test invalid strings and out-of-range numbers inside branches, plus runtime toggling between auto and numeric spacing.

I found no additional architectural defect in the two-channel design. The host recomputes both props and style for touched nodes, compares them with the mirror, and sends a complete replacement style dictionary; this supports gap changes and transitions into or out of auto mode ([paragraph.rs:272](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/src/paragraph.rs:272), [batch.rs:276](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/src/batch.rs:276)). Keep both channel values subject to the existing finite-value/range policy, and test clearing the gap and switching `auto → number → auto`.

**Open questions:** r2 has none remaining. Its chosen numeric-gap, grid-minimum, block-zero, and `glassGroup="auto"` DOM policies are reasonable.

For **glass morph, r1**, several earlier concerns are answered: `glassId` avoids misusing `view-transition-name`; a string prop avoids a new style codec; runtime candidate ambiguity replaces speculative co-mountability analysis; native buttons are excluded; the spring parameters are explicit; and lone appearances/departures remain immediate. Engine ownership also supplies the correct *basis* for frame demand and settlement. The following findings prevent the complete design from being sound as written.

1. **blocker — Hiding `materialView` still hides the content.**  
   D5 proposes `materialView.isHidden = true` while claiming that its content remains visible ([RFC:39](/Users/ccheever/projects/exact2-wt-buttons2/llp/1053.000.000.001-glass-morph.rfc.md:39)). On iOS the material’s `contentView` is the node’s child container; on macOS `MaterialContent` is installed inside `NSGlassEffectView` ([GlassGroup.swift:206](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/GlassGroup.swift:206), [NodeViewMac.swift:554](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/Mac/NodeViewMac.swift:554)). Hiding the ancestor hides its descendants, as [Apple’s `isHidden` documentation](https://developer.apple.com/documentation/UIKit/UIView/isHidden?changes=_2&language=objc) confirms.

   **Concrete change:** Specify and demonstrate a way to suppress only material paint while retaining live content, focus, hit testing, and accessibility. Do not prescribe hiding the current material container. Verify the replacement hierarchy on both platforms: macOS’s documented group paint order also means that simply moving content into an ordinary sibling is not proven sufficient ([glass-groups RFC:72](/Users/ccheever/projects/exact2-wt-buttons2/llp/1053.000.000-glass-groups.rfc.md:72)). The original body/content blocker remains.

2. **blocker — Capturing each node immediately before its own removal loses destroyed ancestors.**  
   D2 relies on chaining a departing node’s frame through ancestor mirrors ([RFC:30](/Users/ccheever/projects/exact2-wt-buttons2/llp/1053.000.000.001-glass-morph.rfc.md:30)). Destruction is preorder: the ancestor is listed first, and the host removes its mirror before reaching descendants ([arena.rs:379](/Users/ccheever/projects/exact2-wt-buttons2/kernel/src/arena.rs:379), [txn.rs:574](/Users/ccheever/projects/exact2-wt-buttons2/kernel/src/txn.rs:574), [host.rs:1182](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/src/host.rs:1182)). Replacing a wrapper containing named glass therefore breaks the proposed capture.

   **Concrete change:** Capture all departing candidates and their ancestry from an intact pre-mutation mirror in a separate pass before processing any destruction. Include named descendants of exiting ancestors. Do not reconstruct ancestry inside the destructive loop.

3. **blocker — Receipt identity does not recover intermediate trees or layout.**  
   D2 claims stepped and jump seeks agree, but the per-receipt loop reads the final kernel tree. A node created in an early receipt and destroyed in a later one is already absent; children and layout are finalized only after all receipts ([host.rs:1198](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/src/host.rs:1198), [host.rs:1215](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/src/host.rs:1215)). Receipts retain keys, not snapshots of props, ancestry, or boxes ([txn.rs:51](/Users/ccheever/projects/exact2-wt-buttons2/kernel/src/txn.rs:51)).

   For A→B→C across two timers, a jump can see no B to create or capture, whereas stepped seeks create A→B and interrupt it with B→C. Even a surviving destination can have been resized by a later receipt before the first morph’s target is read.

   **Concrete change:** Choose a concrete mechanism that preserves each relevant commit’s state and geometry: process commits while their trees exist, or retain sufficient owned capture data before advancing further. Merely tagging candidates with receipt identity does not suffice. Add A→B→C and later-destination-resize equivalence cases.

4. **blocker — The proposed late start cannot use the receipt’s timestamp with the existing engine API.**  
   D2 starts the pair after layout but assigns its earlier `at_ms` ([RFC:33](/Users/ccheever/projects/exact2-wt-buttons2/llp/1053.000.000.001-glass-morph.rfc.md:33)). Before layout, the host has already advanced the engine to final `now_ms` ([host.rs:1273](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/src/host.rs:1273)). `observe` starts at `self.now`; backward advancement is rejected ([engine.rs:381](/Users/ccheever/projects/exact2-wt-buttons2/motion/src/engine.rs:381), [engine.rs:511](/Users/ccheever/projects/exact2-wt-buttons2/motion/src/engine.rs:511)).

   **Concrete change:** Specify an ordering that obtains targets and starts ghosts before the final engine advance, or explicitly design a timestamped curve-adoption operation. Preserve the existing overdue-receipt floor, `max(receipt_time, engine.now())`. Also sample an interrupted ghost at that effective receipt time before capturing its replacement’s starting value.

5. **blocker — Mirror-frame sums are not the presented glass geometry or necessarily its mounted group.**  
   The mirror stores laid-out parent-relative frames ([layout.rs:108](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/src/layout.rs:108)). Presented translate, rotation, scale, press feedback, and layout offsets are applied separately ([PressFeedback.swift:110](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/PressFeedback.swift:110)). A translated source therefore produces a ghost at its untransformed position. Meanwhile, existing group membership follows mounted Swift ancestry, including navigation boundaries—not simply kernel ancestors carrying the prop ([glass-groups RFC:60](/Users/ccheever/projects/exact2-wt-buttons2/llp/1053.000.000-glass-groups.rfc.md:60)).

   **Concrete change:** Define one group-content coordinate space and capture effective presented geometry within it. Establish actual mounted-group identity. For a bounded first version, explicitly reject unsupported transforms, presentation mappings, and containment boundaries rather than claiming that summing layout frames handles them.

6. **blocker — Source isolation and hidden ancestry are bypassed.**  
   D6 explicitly ignores the source’s isolation and checks only the destination’s opacity/mask/clip path ([RFC:41](/Users/ccheever/projects/exact2-wt-buttons2/llp/1053.000.000.001-glass-morph.rfc.md:41)). A clipped or translucent source can consequently become an unclipped, opaque ghost in the outer group. A destination hidden below an ancestor can also acquire a visible ghost outside that ancestor: `glassPath` intentionally does not treat hidden state as isolation because ordinary glass remains within the hidden hierarchy ([GlassGroup.swift:115](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/GlassGroup.swift:115)).

   **Concrete change:** Capture source eligibility before removal and refuse isolated or hidden sources. Require a rendered, eligible destination in the same actual group. Continue checking visibility and group membership as well as isolation throughout the morph. This does not answer the earlier isolation finding as written.

7. **blocker — Swift cancellation leaves Rust with a false presentation source for the next morph.**  
   D6 removes the ghost and reveals B’s actual glass, but leaves its engine node running unseen. D7 then requires B→C to begin from that ghost’s current value ([RFC:41](/Users/ccheever/projects/exact2-wt-buttons2/llp/1053.000.000.001-glass-morph.rfc.md:41), [RFC:43](/Users/ccheever/projects/exact2-wt-buttons2/llp/1053.000.000.001-glass-morph.rfc.md:43)). After isolation cancels A→B, Rust’s moving ghost no longer describes what the user sees. Reusing it causes another jump.

   **Concrete change:** Make cancellation authoritative across both hosts: retire or invalidate the Rust ghost association before another pair can use it. Define how Swift admission/cancellation reaches Rust, or move the authoritative decision to a host path that has all necessary evidence. Apply the same rule when unsupported OS/design policy declines a ghost.

8. **should-fix — Exit participation produces two source glass shapes.**  
   D2 admits nodes beginning an exit, but D4/D5 suppress only the entering node’s glass. Existing presence deliberately retains the departing subtree until its independent exit deadline ([presence.rs:60](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/src/presence.rs:60), [PresenceIOS.swift:17](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/PresenceIOS.swift:17), [PresenceMac.swift:16](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/Mac/PresenceMac.swift:16)). Its original glass remains alongside the ghost.

   **Concrete change:** Transfer ownership of the source’s material paint to the ghost while preserving authored content exits, including named descendants. Alternatively, exclude exit-held sources from this version. Specify behavior when the exit finishes before or after the morph.

9. **should-fix — Lifetime rules omit changes that invalidate the destination or its container without destroying either node.**  
   D7 lists destruction, loss of glass/name, and pooling, but not group-prop removal, group conflicts, reparenting, or destination geometry changes. Existing `syncGlassGroup` can remove the platform container while its node remains alive ([GlassGroup.swift:209](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/GlassGroup.swift:209)). Intrinsic-size updates and resize can also relayout a destination independently of its creating commit ([host.rs:892](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/src/host.rs:892)). A frozen target then cannot guarantee a seamless handoff.

   **Concrete change:** Define cancellation or retargeting for destination box/radius/material/name changes, loss or replacement of the effective group, and reparenting. Include presenter reset. For v1, cancelling and restoring the real material on these changes is a concrete, bounded policy.

10. **should-fix — `Radius` needs an explicit driver and complete batch representation.**  
    D3 configures `set_layout_transition`, which governs only `Layout`; other properties obtain declarations from `set_transitions` ([engine.rs:314](/Users/ccheever/projects/exact2-wt-buttons2/motion/src/engine.rs:314), [engine.rs:391](/Users/ccheever/projects/exact2-wt-buttons2/motion/src/engine.rs:391)). Adding `Radius` to the listed property methods does not make it spring. Existing `present` transport also carries at most four numbers, whereas D4 needs a box plus four radii ([batch.rs:506](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/src/batch.rs:506), [BatchShapes.swift:96](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/BatchShapes.swift:96)).

    **Concrete change:** Configure the ghost’s ordinary transition table for `Radius`, or explicitly extend host-property routing. Keep it outside the authorable wire vocabulary. Define the complete ghost presentation payload, update both decoder paths, and dispatch ghost IDs before ordinary flat/live-view lookup. Test a radius-only morph.

11. **should-fix — Four authored radii do not identify the glass shape currently rendered.**  
    Kernel corner radii are dimensions, including percentages; Swift resolves and reduces them against the box ([schema.json:2062](/Users/ccheever/projects/exact2-wt-buttons2/kernel/tables/schema.json:2062), [BorderPaint.swift:20](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/BorderPaint.swift:20)). The existing iOS material uses a uniform radius derived from the top-left value; macOS uses the maximum reduced radius ([NodeViewIOS.swift:931](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift:931), [NodeViewMac.swift:590](/Users/ccheever/projects/exact2-wt-buttons2/host/apple/Sources/ExactKit/Mac/NodeViewMac.swift:590)). AppKit’s documented glass API exposes a scalar [`cornerRadius`](https://developer.apple.com/documentation/appkit/nsglasseffectview/cornerradius?language=_1).

    **Concrete change:** Define effective material geometry for capture, interpolation, and handoff. Either restrict this version to supported uniform point radii and matching material kinds, or specify the platform-specific reduction and rendering. State which material a pair uses when `glass` and `glass-clear` differ. Raw style radii alone cannot guarantee identical endpoint shapes.

12. **should-fix — The reduced-motion opt-out is not valid Contract, and the new prop’s value contract is incomplete.**  
    D8 uses `condition ? none : "send"` ([RFC:45](/Users/ccheever/projects/exact2-wt-buttons2/llp/1053.000.000.001-glass-morph.rfc.md:45)). Normal inference rejects option/string branches, and ordinary string-prop lowering accepts `Ty::String`, not an option ([types/lib.rs:99](/Users/ccheever/projects/exact2-wt-buttons2/contract/types/src/lib.rs:99), [values.rs:538](/Users/ccheever/projects/exact2-wt-buttons2/contract/lower/src/values.rs:538)). The existing compiler reproduces that rejection with a current string prop.

    **Concrete change:** Choose an implementable nonparticipation value—for example, explicitly reserve `""` and use `condition ? "" : "send"`—or specify complete optional-prop typing and clearing. Define literal and computed-name validation and whether renaming cancels an active pair. Add the promised `glassId` web attribute to the build steps and test static and bound forms: the JS target discovers supported prop names through the web writer ([web-js/style.rs:422](/Users/ccheever/projects/exact2-wt-buttons2/host/web-js/src/style.rs:422)).

13. **should-fix — The verification plan still does not establish the promised presentation behavior.**  
    D9 tests that the body is hidden, which would currently certify the content-hiding bug. Its sampled boxes do not establish visible content, focus/hits/accessibility, ordinary display-link operation, or cancellation correctness ([RFC:47](/Users/ccheever/projects/exact2-wt-buttons2/llp/1053.000.000.001-glass-morph.rfc.md:47)). These were explicit requests in the earlier review ([astra review:111](/Users/ccheever/projects/exact2-wt-buttons2/llp/reviews/1053.000.000.000-glass.astra.md:111)).

    **Concrete change:** Extend existing suites with the failures above, a ghost-only wall-clock animation that returns to idle, repeated frozen-clock reads, unsupported OS/design fallbacks, and live content/focus/hit assertions. Film through the actual handoff using macOS window capture, and drive an actual consumer. Keep the existing five checks and both Swift builds as implementation acceptance requirements.

**Answers to the morph’s open questions:**

1. **Native glass buttons:** Keep them excluded. For a later version, prefer preserving the real control while suppressing only its background, if demonstrated on both platforms. A title snapshot should not be the default substitute for live control content.
2. **Timing authoring:** Keep a fixed, explicitly chosen spring until a consumer needs authoring. Do not introduce `transition="glass-id …"` now. Distinguish response from duration: with `(322, 35.9, 1)`, a zero-velocity 100-point move is about 82.07 points complete at 175 ms, 98.63 at 350 ms, and settles around 967 ms under the engine’s threshold ([spring.rs:51](/Users/ccheever/projects/exact2-wt-buttons2/motion/src/spring.rs:51), [spring.rs:145](/Users/ccheever/projects/exact2-wt-buttons2/motion/src/spring.rs:145)).
3. **Lone appearance/departure:** Keep it immediate. This correctly avoids adding platform-timed motion outside the agent clock.
