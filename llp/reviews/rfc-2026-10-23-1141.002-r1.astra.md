Verdict: READY WITH CHANGES

The native-search direction is right, but the CSS mapping, selection lifecycle, and several UIKit assumptions need resolution before implementation.

The strongest parts are **§3 D1’s explicit search-destination marker**, **D3’s reuse of the existing header field**, and **§4’s native reference experiment with an escape to the smaller system-item change**. Distinguishing app search from list filtering avoids a damaging inference rule. Keeping ordinary destinations on web, Android, and desktop hosts is sensible.

The proposed minimized UIKit presentation is supported: `.integratedButton` keeps inactive search as a button even when a field would fit, and toolbar integration defaults to enabled. These APIs support the desired behavior, although they do not justify its proposed CSS spelling. [Apple placement documentation](https://developer.apple.com/documentation/uikit/uinavigationitem/searchbarplacement-swift.enum), [toolbar integration](https://developer.apple.com/documentation/uikit/uinavigationitem/searchbarplacementallowstoolbarintegration)

My concerns are:

1. **BLOCKING — §3 D4: `field-sizing: content` changes meaning.**  
   This is intrinsic sizing, not disclosure or activation behavior. An empty field with `placeholder="Search Hacker News"` still has displayed content: HTML explicitly includes the placeholder when determining its intrinsic size. Width constraints also remain meaningful. Converting that declaration into a minimized button prevents authors from independently requesting content sizing and search presentation, violating LLP 1115’s separation between authored layout and platform presentation. Use an explicit Exact presentation attribute with an automatic default; preserve CSS sizing semantics. [HTML rendering rules](https://html.spec.whatwg.org/multipage/rendering.html#the-input-element-as-a-text-entry-widget)

2. **MAJOR — §3 D2–D3: the unconditional iOS 26-and-later presentation promise is unsupported.**  
   Current Apple documentation describes standard search tabs and separate button appearances differently. Its `prominentTabIdentifier` documentation also conditions default search-tab prominence on `automaticallyActivatesSearch=true`; that page currently carries a beta qualification. This is enough to require separate 26/27 measurements, rather than extrapolating one journey. Resolve the matrix for autofocus absent/present, custom/default images, and first/subsequent selection. Treat the separate circle and bottom field as measured outcomes, not universal consequences of constructing `UISearchTab`. [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/search-fields), [prominence API](https://developer.apple.com/documentation/uikit/uitabbarcontroller/prominenttabidentifier)

3. **BLOCKING — §3 D2–D3, D6: selection and activation need an explicit lifecycle.**  
   The RFC recognizes that panels are lazy, but the same problem affects reading their header’s `autofocus`. Before first selection, where does `automaticallyActivatesSearch` come from? Does setting it after the route arrives activate search?

   Moreover, Exact vetoes UIKit selection, queues an authored press, then applies the router’s selection. Apple documents previous-tab restoration when automatic activation is enabled; it does **not** establish the RFC’s claim that cancellation necessarily passes through `shouldSelectTab`, especially under this veto/programmatic-selection sequence. [Automatic activation](https://developer.apple.com/documentation/uikit/uisearchtab/automaticallyactivatessearch), [selection delegate](https://developer.apple.com/documentation/uikit/uitabbarcontrollerdelegate/tabbarcontroller(_:shouldselecttab:))

   Define and test the ordering from tab intent through lazy construction, search configuration, router selection, activation, and cancellation. Cover cold selection, repeated selection, startup directly in search, and returning from a result. Also state that this native interpretation of `autofocus` changes cancellation and re-entry behavior: the [existing web implementation](/Users/ccheever/projects/exact2-wt-review-1141x/host/web/navigation.js:797) processes autofocus once per mount.

4. **MAJOR — §3 D2, D6: tab identity and automation identity are conflated.**  
   `UISearchTab` has a system-assigned identifier; `UITab.identifier` is read-only. Consequently, “every tab’s identifier is its testId” cannot hold as specified. Keep stable application identity, UIKit identity, and `accessibilityIdentifier` separate, with an explicit mapping. Prefer panel identity over a testing label for ordinary tab identity. Test duplicate identifiers and changed test IDs without rebuilding navigation state. [Search-tab identifier](https://developer.apple.com/documentation/uikit/uisearchtab/identifier), [UITab identifier](https://developer.apple.com/documentation/uikit/uitab/identifier)

5. **MAJOR — §3 D3–D4, D6: existing field plumbing is not automatically safe after relocation.**  
   Apple’s iOS 26 release notes document that `searchBar.searchTextField` can return different instances over time. Exact’s [HeaderSearch](/Users/ccheever/projects/exact2-wt-review-1141x/host/apple/Sources/ExactKit/IOS/NavigationBarIOS.swift:330) captures the text-field delegate and exposes a concrete field for focus and driving. Verify and, where necessary, refresh those bindings across expansion, cancellation, keyboard changes, and width changes. Test real typing, selection, paste, focus/blur, and accessibility identifiers against the displayed editor. [Apple release notes](https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-26-release-notes)

   Separately, `SearchBarPlacement` has no documented “tab bar” case. D6 must distinguish the enum’s placement from the field’s actual presentation container; do not report an inferred container as a UIKit-returned enum value. [Placement cases](https://developer.apple.com/documentation/uikit/uinavigationitem/searchbarplacement-swift.enum)

6. **MAJOR — §3 D2, D7; §4: migrating every tab app needs a separate compatibility gate.**  
   One implementation per OS is a reasonable endpoint, but a single drive per app does not qualify the migration. The [existing presenter](/Users/ccheever/projects/exact2-wt-review-1141x/host/apple/Sources/ExactKit/IOS/NavigationTabsIOS.swift:1) includes held stacks, late hatch takeover, reselection behavior, authored chrome, and iPad-specific discovery of tab controls.

   Require parity for retained stacks and scroll positions, reselection/pop-to-root, disabled states, badges, selected images, dynamic tab changes, `appearance:none`, hatch takeover, and compact/regular transitions. Qualify iOS 18 separately from 26/27 and compile the shared tvOS code. Keep this migration independently revertible. Accept the system-item shortcut only if its behavior—not merely its silhouette—matches.

7. **MINOR — §3 D1: `rel` is a defensible extension, not standard button vocabulary.**  
   Preserve `role="tab"`; rewriting a search landmark into a tab would corrupt ARIA’s meaning. But explicitly acknowledge the button extension, define normal token-list handling, and scope the restriction to search-tab projection rather than prohibiting legitimate `rel="search"` on links or forms. The web test should require valid, accessible output rather than specifically requiring an invalid button attribute. [HTML link types](https://html.spec.whatwg.org/multipage/links.html#link-type-search)

Stage 0 is necessary but insufficient as written. Alongside ordinary UIKit, add a small reference using **Exact’s delayed panel construction and veto-then-programmatic selection pattern**. Record callback order, selected tab, active search controller, first responder, and actual presentation container.

D7 also needs a minimized-search touch journey: expand, type, submit, cancel, reopen. Run it explicitly with both `--chrome platform --touch platform`. Add VoiceOver labels/selected states, focus restoration, Dynamic Type, RTL, and keyboard access. Scope `back` to the foreground presentation: an active search beneath a sheet must not consume that sheet’s dismissal. A missing field in an unbuilt panel should be “not yet known,” not a false `check` failure. Record OS/SDK versions and reproducible reference results.
