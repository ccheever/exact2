`pageTop` (`scripts/scale-check.mjs:165`) is sound for the portrait reader run. It takes the topmost expected fill box from the first-frame boxes (`check` passes `expect.calibrate`, and an omitted argument still defaults to `expect.boxes`), samples the middle of that box, and returns the start of the first fill run at least `floor(box.h * scale * 0.9)` pixels tall. For this target that box is `r-sm`, 120×48, solid `#0000ff`. At density 2 the run has to be about 86 px, longer than a status bar or the Flip button, and `coverage` ignores a pixel that is off the `#0000ff`–`#ffffff` line. The 8 pt gap under Flip resets the run, which is what the new test locks (a 1 px same-colour stroke at y=40, page top 30). An abutting same-colour ring would move the reported top by the ring's thickness; this fixture does not have one. There is a horizontal page origin in the presenter: a non-`viewport-fit=cover` root, which this contract is, is placed at `x = max(systemBars.left, cutout.left)` (`host/linux/src/presenter/window.rs:129`). Portrait phones and the x2 emulator leave that at 0, so the sample column is the box center and `scale = screencap width / page width` is the density. Landscape or a side cutout makes it non-zero, and layout does not report the frame origin (non-cover env insets are 0; the origin is `chrome().frame`). `pageTop` never adds a left margin. A side inset large enough to walk the sample off the 120 pt box returns 0 and the corner check fails. The 20/20 portrait result does not use that path.
