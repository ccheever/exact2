## MATERIAL

1. **MATERIAL — D2, D5.** `used_height` is the column content height, and `container_outer_height` is the border box after padding, border, and the min/max clamp.
   **Problem.** D5 writes the balanced H into `used_height`, and D2 assigns that value to `container_outer_height` after the children are laid out (`block.rs:615–618`). H is the height of a column interval (D3). `intrinsic_outer_height` already includes the vertical inset (`:640` subtracts it to recover the content height), and `:617` then clamps with `min_size` and `max_size`. Replacing the result with H leaves a border box short by the padding and border, and a `min-height` no longer raises it. `measure_auto_height` returns a border box (`geometry.rs:31–32`, `:81–86`); answering that same H returns the content height.
   **Evidence.** Chrome 154.0.8037.98, `/tmp/llp1093-r3.html` (removed after the run). `pad`: `padding: 10px`, `column-count: 2`, four 20px blocks, balance: offsetHeight 60, children at y = 10 and y = 30. `border`: border 5px, offsetHeight 50. `pad-border`: offsetHeight 68. `minh`: `min-height: 100px`, offsetHeight 100, children still only occupying y = 0 and y = 20. `maxpad`: `max-height: 30px` and `padding: 10px`, offsetHeight 50.
   **Fix.** Keep the column interval at the content-box height. The value written at `:615–618` is that height plus padding and border, then the existing min/max clamp. `measure_auto_height` returns that border box.

2. **MATERIAL — D5.** The cap does not apply when the initial guess already fits in N columns.
   **Problem.** The balancer starts at the flow thread's height over N and only grows while the cut needs more than N columns and H is below the cap. It stops when the content fits. When `content / N` is already above the cap, that guess fits in N columns, the loop never runs, and the columns are `content / N` tall. The table's "balanced within `h`" and "capped at `m`" are the other result: the column height is the cap, and the rest are overflow columns.
   **Evidence.** Chrome 154, `/tmp/llp1093-r3b.html`. `short`: six 20px blocks, `column-count: 2`, `height: 40px`, balance. `content / N` is 60, which holds 3 + 3. Chrome's offsetHeight is 40, `scrollWidth` 600, two blocks in each of three columns. `max30`: four 20px blocks, `max-height: 30px`. `content / N` is 40. Chrome's offsetHeight is 30, `scrollWidth` 600. D10.1 already keeps the sliced 20px box whole; the 30px container height is separate. `tall` shows the other side: `height: 100px` stays 100 while the columns remain 40.
   **Fix.** Clamp the initial H to the cap, and keep it at least the tallest unbreakable. For a definite height the container's border box stays the specified one. For `max-height`, the container's border box is the clamped outer height from `:615–618`.

3. **MATERIAL — D7, D10.4, §4.** The cited abspos overflow and the placement rule describe different boxes.
   **Problem.** D7's union "keeps D10.4's absolutely positioned boxes" and cites `scrollWidth` 620. §4 makes every Chrome result cited in D7 a parity case. D10.4 places an abspos unfragmented, translated with its containing block's first fragment. In this fixture the containing block's first fragment is at x = 90, and `top: 200px` then lands the box at (90, 200), which extends `scrollHeight`. Chrome paginates that offset through the columns.
   **Evidence.** Chrome 154, `/tmp/llp1093-r3b.html` case `abs` (the r2 fixture): the box is at (540, 0), size 10×10; `scrollWidth` 620; `scrollHeight` 40. Column pitch is 90, and 540 is column 6, which is where flow y = 240 falls in 40px columns.
   **Fix.** Choose one account. To keep 620 as parity, place the abspos by paginating its flow position into columns and include that column in the overflow union. To keep D10.4, publish the kernel rect (first fragment plus the offset) as a D10 row and drop 620 from the parity list.

4. **MATERIAL — D2, D10.5.** The content-sized width uses the border box as the column's content width.
   **Problem.** D1 defines U as the content-box width. D2 then says that for a content-sized width, U is the `:552` result and the children are laid out at W = U. The value computed at `:552–558` is `container_outer_width`, which adds `content_box_inset.horizontal_axis_sum()` (`:480`, `:555–556`).    **Fix.** Leave the outer width as the `:552` result. U is that width minus the horizontal content-box inset. N = 1 and W = U, and the children are laid out at W.
