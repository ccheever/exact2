## Blocker

**Composite alias expansion still allocates bytes it never charges.** `tamber/src/import/dtcg/kinds.rs:55` and the key clone at `:57-61`, reached from `tamber/src/import/dtcg.rs:1256` before `text()` runs.

`inner` does `spend(1)` for an object or array, then clones every key and builds the new value. Only a scalar goes through `copy()`, and that happens after the key clone. `raw` is not memoized: `visiting` is popped before the sibling alias, and the chain cap of 256 is the stack depth, not the node count. A `fontFamily` (or any other kind that calls `raw`) whose value is `["{next}", "{next}"]` for about twenty levels, ending at one object with an 8 KiB key, stays far under the budget — each visit spends 1 and the leaf string is tiny — and retains on the order of 2^20 copies of that key. Kind checking runs only after `raw` returns. The new test refuses the same tree when the leaf is the string `"Inter"`, because that string is `copy()`'d.

Fix: before any clone, `spend` the key lengths (and a realistic per-`Value` overhead, not 1) for the node you are about to build; keep `copy` on scalars before their clone. Memoize `raw` by path on the `Resolve` so each token is expanded once. Charge the `fontFamilies` split at `:81-91` for the member strings it allocates, not only the source string.

**Tailwind inlines `var()` with no budget at all.** `tamber/src/import/tailwind.rs:697-718`, called at `:848` and `:859-868`. `shadcn::import` and `tailwind::import_with` never call `Work::begin`, and `spend` is a no-op when `DEPTH` is 0 (`tamber/src/budget.rs:47-48`), so a later `spend` in this file would not count.

`written_out` pastes each `var()`'s full text back in, depth cap 16, with no cycle memo. Seventeen `--text-*` keys in one `@theme`, each `var(--next) var(--next)`, and a 20 KiB leaf, build a string of 2^16 copies (about 1.3 GiB) and only then try to read it as a type. `bare` on colour and family keys does not do this — it substitutes a token name — but every `type` size, leading, and weight does.

Fix: `Work::begin` at both CSS import entries, and `spend` the bytes you are about to append before concatenating. A depth cap alone does not bound a binary paste.

**Nested CSS braces abort the process.** `tamber/src/import/mod.rs:401` (`body`), recursing at `:467`. Both importers call it (`shadcn.rs:149`, `tailwind.rs:283`). There is no depth cap. A few thousand nested `{`…`}` pairs overflow the stack; that aborts rather than unwinding, the `contract tamber serve` child exits, and `scripts/tamber-server.mjs:325` fails the server. `engine::nested` already stops at 1024 selectors (`engine.rs:355`). This parser does not.

Fix: refuse past a small nesting depth (64) before recursing, and return that as an import error.

## Should-fix

**`type_of` is quadratic per tuple and uncharged.** `tamber/src/import/dtcg.rs:930-942`, called at `:1234` for every path in every tuple. An untyped alias chain walks the rest of the chain, cloning each target into a `BTreeSet`, and nothing is memoized. About 10,000 such tokens and 64 contexts fit under both the 1 MiB body cap and the 64 MiB budget (short `$value`s, one shared set). That is on the order of 64 × 10,000² / 2 chain steps, minutes on the one Rust process. The same shape is `reaches` at `:1308-1322`, once per colour token rather than per tuple.

Fix: memoize the resolved type (and the cycle bit) by path. One walk per chain.

**Re-import looks up every token by scanning the context's whole list.** `tamber/src/export.rs:766-772`, from the per-name loop at `:854` (`changed` calls it twice per context). After a legal expansion, cost is O(names × contexts × tokens in that context). A map from name to the winning token, built once per context, makes the diff linear.

**`apply_all` / `check` is repeated, and it is bounded.** Per changed colour token the repair loop at `tamber/src/export.rs:1287-1353` runs at most four times (`rounds > 3`). Then `:1383-1398` calls `apply_all` once per accepted token on the growing transaction, which is O(n²) applications. `export_dials.rs:228` does one `apply_all`+`check` per distinct dial, `:256` one more for the dials together, and `marks` at `:351-365` one per dial change. Not exponential, and not covered by the budget. Incremental apply, or one check of the finished transaction, is enough.

**Narrow-`when` search materializes every subset of the design's axes.** `tamber/src/export.rs:1226-1227` and `subsets` at `:1471`. `MAX_TUPLES` is 64 (`tamber/src/check.rs:13`), but an axis with one value does not increase the product (`check.rs:407`). A design with a few dozen one-value axes — an import can propose them — makes `subsets` allocate C(n, n/2) vectors. Fix: walk combinations without storing them, and cap axes as well as tuples.

## Budget

`Work` is scoped correctly. The outermost `begin` sets `LEFT` back to `LIMIT`; a nested one shares it (`budget.rs:26-34`). `Drop` always decrements `DEPTH` with `saturating_sub`, including on unwind, so a panic inside an import leaves `DEPTH` at what the surviving outer `Work` owns, or 0 if it was the outermost. The next outermost `begin` refills `LEFT`. A stack overflow aborts without dropping; the process is gone either way. Nothing outside an import is counted: `spend` succeeds immediately when `DEPTH` is 0. `check` and the fresh `dtcg()` export run inside `reimport_against`'s `Work` but do not spend; only the later copy of each context tree does.

`LIMIT` (64 MiB, `budget.rs:15`) does not refuse a real colour design of 3,000 tokens by 64 contexts. An export inlines every token into every context (`export.rs:381`). One colour token is about 125 bytes of `size()`, so 64 contexts are about 24 MiB of charged copies, under the limit. The 1 MiB body cap (`scripts/tamber-server.mjs:103-104`) already stops a client from sending that export; the server's own fresh export of the design is what gets copied, once. A resolver that re-walks one shared typography tree per context and then `raw()`s it per tuple lands near the ceiling (on the order of 50–60 MiB in the estimate above). Fatter values there are refused. That is the limit doing what it should, not a false refusal of the colour case.
