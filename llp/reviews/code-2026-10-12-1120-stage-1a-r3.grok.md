1. **MATERIAL** — Dropping the lane between `start` and `activate` calls the sink before activation. `didCompleteWithError` (`darwin_task.mm:105-114`) and `didFinishCollectingMetrics` (127-146) deliver as soon as the session finishes the task. `ibex2_darwin_lane_destroy` (224-230) is `invalidateAndCancel`. A never-resumed task still completes: a local probe of that sequence prints `metrics`, then `complete err=cancelled`, with the task in `Completed`, and never resumes it. `activate` (305-310) resumes unless the synchronized `cancelled` flag is set, and invalidation does not set that flag. The contract at 233-235 and `fetch_async.rs:160-165` says nothing reaches the sink before `activate`. `FetchTask::hop` holds the lane across that window, so this stage's only consumer does not hit it; D2 retirement will. A resume issued immediately after `invalidateAndCancel` opened no connection in the same probe, so this is an early callback, not a sent POST. Fix: if the session completes or collects metrics before activation, remember the terminal error and do not call the sink or arm the one-second timer. In `activate`, enqueue a block on the delegate queue (the keep-add from `start` is already ahead of it), mark the exchange activated, and if the session already finished the task, deliver that single end and `release_` once, with no `resume` and no metrics. Test: drop the lane after `start` and before `activate`; nothing for a few hundred milliseconds; after `activate`, one end, no metrics, the sink dropped once, no accepted connection.

2. **MINOR** — `FetchTask::abort` cancels before it reports the outcome. The comment at `fetch_async.rs:291` and `FetchEvents` at 187-189 say the abort is reported before the hop's physical end. The body (300-305) calls `exchange.cancel()`, drops `Released`, then `events.outcome`. `Reentrant` (`fetch_async_tests.rs:628-632`) runs `end` inside `cancel`, so `hop_ended` (542) precedes `outcome`. `a_cancellation_ending_on_the_abort_stack_stays_aborted` (639-654) checks that the outcome stays `Aborted`, not the order. On Darwin, `cancel` returns before the delegate runs, so the shipping order is still outcome, then a later `hop_ended`. Fix: after `decide`, drop the upload and the body, call `events.outcome`, then `exchange.cancel()`. The decision is already recorded, so the re-entrant `end` cannot replace it.

3. **NIT** — Queued time is measured from resume (`darwin_task.mm:136-137`, `resumed` set at 309), and the test does not pin that. `darwin_async_tests.rs:159-163` asserts `queued_ms < 1_000` on localhost, which a clock started at task creation also passes. Sleep a few hundred milliseconds between `start` and `activate` and assert `queued_ms` is below that sleep.

4. **NIT** — `a_cancel_before_activation_sends_nothing_and_still_ends` (`darwin_async_tests.rs:451-473`) checks silence, one end, and no connection. It never counts sink drops. `the_sink_is_freed_once_after_its_end_and_metrics` (425-446) covers the success path only, so a keep-set leak on the cancel-before-activate path would stay green. Count drops, wait out the one-second metrics grace, assert one.
