## Decisions

**D1 — RIGHT WITH CHANGE.** One pin for painted components and islands is the right rule, and leaving Expressive out until it is the default is right. There is no version catalogue. `host/android/app/build.gradle.kts` pins `compose-bom:2026.09.00` only inside `if (compose)`; it never names `material3:1.4.0` (that version is a comment in `Material.kt` and in 1115.001.000). Put one declaration, BOM plus the resolved artifact version, where the reference module, the extractor, and the islands read it, including apps built without `-Pcompose=1`.

**D2 — RIGHT WITH CHANGE.** Reading the pinned sources jar is right, and the snapshot diff is the right bump mechanic. Three changes. The schema cannot carry a token name: a `metrics` row is a name, a kind, and a value per column (`Web`, `Ios`, `Mac`, `Neutral` in `kernel/src/style/metrics.rs`). Store resolved numbers and role names in the table, and the token name only in `tokens/<version>.json`. Shape keys and type keys are not metric values. Resolve a shape to four corner dp in the extractor. Send type through 1115.001 D4's reported ramp (size, line height, weight, tracking at the current font scale), because a static `BodyLarge` cell will not track Android's non-linear scale. Identify a non-token constant by symbol, or by a hash of the expression, in the pinned file. `Checkbox.kt:612@1.4.0` moves on the bump D8 exists to do. I did not open the 1.4.0 jar, so that line is an illustration, not a checked fact.

**D3 — RIGHT.** A specimen that lacks either side should fail. Keep the Contract side in author vocabulary.

**D4 — RIGHT WITH CHANGE.** Fixed schemes, light and dark, handed through `Palette::tell`, are the right JVM inputs. Add a second noise floor. Calibration as written is Compose-on-Robolectric against Compose-on-a-Pixel. Exact headless is tiny-skia; the phone replays the same ops onto HWUI. Those rasters differ with the same font files. Inside a field they are different engines: 1115.001 D8 gives the value to `EditText`, while the label stays Rust-shaped. Also, `presenter/bars.rs` does not paint bars unless `serve_bars` runs, and it says a headless run does not. `device_tests.rs` only checks `set_device` preferences. O1's bars need that door and a compositor for the bar pictures, or the headless frame is the in-page header.

**D5 — RIGHT WITH CHANGE.** Five separate failures are the right report. The geometry method and the O1 thresholds are not. `boundsInRoot` is the semantics node's box in the compose root. Merged nodes hide the label and the icon. The unmerged tree still has no indicator, thumb, track, or container fill. `MinimumInteractiveComponentSize` (48 dp) inflates the layout box past the drawn control (1115.001 D9: a 40 dp button, a 20 dp checkbox). Exact's `PaintedBox` (`paint.rs`) is one transformed rect per node, not per part. Bars keep their own frames. Compare sizes and offsets from the component's origin, for the outer box and for parts both trees actually have. Crop both images to that box and scale them to the same pixels before the pixel layer. ΔE2000 2 is a fair probe on a flat fill (container centre). A probe on label ink is anti-aliasing. 0.5% of pixels past ΔE 5, ignoring a one-pixel edge, is too tight for text at density 3 and too loose if the image is the full 411×891 frame. The document says the numbers wait for calibration, then O1 and D7 use them first. Until both noise floors are measured, geometry of the outer box and flat colour probes gate; the pixel layer is a heat map only. Accessibility on the phone, both sides as `AccessibilityNodeInfo`, is the real check. The JVM check (Compose semantics against `presenter/access.rs`) is a different tree. Motion tracks are right for a thumb, a label, an alpha. They are wrong for the API 31 ripple.

Dialog, menu, sheet, and snackbar stay painted content in the framework window (1115.001 D10), with drag and fling left on `OverScroller`. The other rows match the rule. **D8 — RIGHT WITH CHANGE.** A token diff before any drawing is the valuable part. Drop file:line identities, or the bump invalidates them. Eight weeks is a policy, and it is fine as Q3. Tier 2 files an issue; it does not gate the six checks. Say that.

**D9 — RIGHT WITH CHANGE.** Advice, not a check, is right. Tier 2 today is tvOS, a Linux cross check, and a Windows cross check (`scripts/async.mjs`, `tierTwoChecks`). ## What fails in practice

1. **Headless is not the phone's painter.** Bars do not run. Field text is `EditText` on the device and not in tiny-skia. Same font files do not give the same pixels. O1 will "explain" failures that are the harness.

2. **Robolectric native graphics is faithful for flat M3 fills and weak for everything else.** I have not run the 2026 Robolectric this Gradle would pull; this is the NATIVE mode Roborazzi has shipped since 4.10. It draws with desktop Skia from the SDK, not the phone GPU. The default typeface is Robolectric's system font, not the Pixel's, and `MaterialTheme` uses `FontFamily.Default`, so handing Exact a font file does not hand Compose that file unless you replace the system font or set `Typography`, which leaves "the defaults." Elevation shadows and `RenderEffect` are missing or different. On API 31, which this reader sets as `minSdk`, the Material 3 ripple is a platform `RippleHostView` blur, animated off `mainClock`. Roborazzi often captures no ripple. `Dialog`, `DropdownMenu`, and `ModalBottomSheet` are other windows and are easy to miss. Solid buttons, bars, and an unfocused field can be compared. Ripple, shadow, and popup specimens cannot, until the phone.

3. **`androidx.compose.material3.tokens` is enough for sizes, role keys, state-layer opacities, and the type and shape scales. It is not a painter.** I have not opened this version's jar. From the 1.3/1.4 package: component objects, `ColorLightTokens` / `ColorDarkTokens`, `ShapeTokens`, `TypographyTokens`, `ElevationTokens`, `StateTokens`. Outside it: checkbox and switch paths, text-field label lerp (`TextFieldImpl` / `CommonDecorationBox`), most `tween` / `spring` durations, `surfaceColorAtElevation`, the ripple (`material-ripple`), dynamic scheme generation (`material-color-utilities`), and the 48 dp minimum target. Tokens are `internal`; the sources jar is the right place to read them. There is no `verification-metadata` under `host/android`, so "checksum verified" means Maven's published checksum, not Gradle dependency verification.

4. **Geometry as specified does not line up.** See D5. The pixel layer is the only check of indicator, thumb, and icon, and only after the crop and both noise floors.

5. **The twelve-role door runs out** at `outline`, `onSecondaryContainer`, `primaryContainer`, `surfaceVariant`, and `scrim`. A tonal button's content and a switch will not resolve.

6. **D6's assignments are right and several will not converge from tokens** (switch morph, slider, sheet motion). That is acceptable if D7 can stop at three rounds without a flip to Compose.
