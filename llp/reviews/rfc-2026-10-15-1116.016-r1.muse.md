# Review of LLP 1116.016

## 1. Verdict: READY WITH CHANGES

Charlie's direction is the right one to finish, and most of stage 1 is cheap sugar. It should not land as written: `Math.min`/`Math.max` would compile with a different meaning from TypeScript's (issue 1), and `toSorted` is priced as a roster row when it is a new callback machine with a sorting-correctness proof (issue 3). Fix those as below, narrow D1's standard, and split D3, and the rest of the stage is sound.

## 2. The most important issues, ranked

**1. `Math.min`/`Math.max` violate T4 on `NaN` — today, not hypothetically.** D2 rewrites them to nested `min`/`max`, claiming "the roster's are JavaScript's already" and citing only `round` ([RFC §D2](llp/1116.016-contract-expressions-are-typescripts.rfc.md)). For `min`/`max` they are not: the runner uses Rust's `f64::max`/`min` ([runner/src/stdlib.rs](/Users/ccheever/projects/exact2/runner/src/stdlib.rs:249)), the Lean model defines `fmax`/`fmin` as "a NaN yields the other argument" ([semantics/Contract/Number.lean](/Users/ccheever/projects/exact2/semantics/Contract/Number.lean:158)), and the JS target mirrors that ([host/web-js/roster.js](/Users/ccheever/projects/exact2/host/web-js/roster.js:7)). TypeScript's `Math.max(NaN, 5)` is `NaN`; Contract's `max(NaN, 5)` is `5`. `NaN` is reachable in Contract (`0/0`, `Infinity - Infinity`), so `Math.max(a, b)` would silently return a number where the author wrote code that propagates `NaN`. Consequence: the one accepted form in the RFC that compiles with another meaning. Change: either drop `Math.min`/`Math.max` from D2, or make this RFC explicitly change Contract's `min`/`max` to JavaScript's NaN-propagating semantics — a breaking semantic change to existing programs, with the Lean `fmax`/`fmin`, the `arith` difftest, and every app that relies on NaN-dropping re-examined — and say so in D2 rather than discovering it in review. Also specify arity: `Math.min()` is `Infinity` and `Math.min(x)` is `x` in TypeScript; "two or more arguments" leaves both to an unspecified diagnostic.

**2. D1's standard is uncapped, and its evidence oracle counts the wrong language.** LLP 1017.003 admitted an operation on "a view-only need demonstrated in source." D1 replaces that with "TypeScript programs commonly perform it" plus "the census or real builds show builders reaching for it." The strongest numbers for `Math.*` and `padStart` come not from Contract but from the `app.ts` data modules the same models wrote (RFC §1: `padStart` 36, `Math.floor` 20) — TypeScript that already runs as TypeScript, below the data seam, where Contract's roster is irrelevant. Counting it proves the data module wants these functions, which it already has. Meanwhile the 469 real builds, all guided, show `length` 24, `empty` 9, then `sum` 2, `flatMap` 2, `reduce` 1 — and no `sort` or `find` at all; `toSorted`'s evidence is 8 of 80 one-screen guess-corpus screens written *after* D2 taught method syntax (I verified: 5 GPT + 3 Muse in `~/bakeoff/guesses/post15`, against one free-function `sort(...)` in `pre15`). D2 created the demand D3 now satisfies; that loop has no natural stop, because every accepted method makes the next one a "wall." Consequence: a permanent, growing commitment — each roster row is four implementations (`format.json`, runner, JS runtime, Lean semantics plus difftest) bought with guess-corpus evidence from 40 features sliced from the same 24 apps, with no held-out set (a weakness LLP 1116.015 §2 already flags). Change: keep D1's rule as the *meaning* standard ("TypeScript's meaning or a refusal") but keep 1017.003's *admission* standard, widened to count a guess-corpus wall as a demonstrated need only when both model families hit it; state a threshold and name the ES edition whose pure subset is in scope. Note also that T5 of the predecessor holds: LLP 1115 settles CSS names and layout, not expression semantics, so D1 is a census decision and should not borrow 1115's authority.

**3. `toSorted` is not a roster row; it is the expensive half of D3, and its bound does not fit sorting.** `map`/`filter` lower to opcodes with an inline body, proved by induction over the items (`MapR`/`FilterR`, [semantics/Contract/Big.lean](/Users/ccheever/projects/exact2/semantics/Contract/Big.lean:142), `each_sem` in [LowerCorrect.lean](/Users/ccheever/projects/exact2/semantics/Contract/LowerCorrect.lean:16)). The VM's callback machinery assumes exactly that shape: one item and its index, run once each, in order ([runner/src/machine.rs](/Users/ccheever/projects/exact2/runner/src/machine.rs:268)). A comparator binds two items, runs O(n log n) times in an order the sorting algorithm chooses, and its correctness statement is permutation + orderedness + stability — none of which is an induction over the input list. Worse, for an *inconsistent* comparator (returns `1` always, or a cycle) ECMA-262 leaves the order implementation-defined, so the runner's sort, the JS target's TimSort, and Lean's definition will disagree unless all three implement the *same* algorithm; calling the browser's native `toSorted` on the JS target guarantees divergence that difftest's generator will eventually find. And counting comparisons against `MAX_LIST_STEPS` (65,536, [runner/src/vm.rs](/Users/ccheever/projects/exact2/runner/src/vm.rs:50)) caps a sortable list at roughly 4,000 items — below the 5,000-row list that motivated `map`/`join` in LLP 1017.003. Change: split D3. Land `padStart`/`padEnd` now; give `toSorted` its own section (or RFC) that names the algorithm (a stable mergesort is the provable choice), counts items rather than comparisons against the bound, specifies `NaN` comparator results read as `0` (ECMA-262 SortCompare — the RFC says this, good), `-0` likewise, and the inconsistent-comparator order as algorithm-defined and identical on every executor, with the same algorithm written out in `roster.js`/`budget.js` rather than delegated to the engine.

**4. The `find`/`some`/`every` rewrites are honest in value but not under the bounds, and their diagnostics will leak.** `xs.find(f)` as `filter(xs, f).at(0)` evaluates `f` on every item and builds the filtered list. Because callbacks are pure and total the *value* agrees with TypeScript's early exit — but a 70,000-item list whose first item matches returns immediately in TypeScript and traps `IterationLimit` in Contract, and the intermediate list can trip the value-extent bounds where `find` builds nothing. That is an observable difference D2 should state, not discover. The diagnostic requirement (RFC §2: a diagnostic "names the form the author wrote") is real work, not a note: the rewrite happens in the parser ([contract/syntax/src/parser/expr.rs](/Users/ccheever/projects/exact2/contract/syntax/src/parser/expr.rs:141)), so the checker will naturally report `filter`'s argument errors against a call the author never wrote, and the existing refusal text in [idioms.rs](/Users/ccheever/projects/exact2/contract/syntax/src/idioms.rs:123) already teaches `first(xs.filter(...))` — two of D2's spellings at once. Change: keep the rewrites (they are the right cheap design), but require, per rewrite, a same-plan test *and* a test at the step bound showing the trap, and keep the author's span and name through the checker so errors say `.find(...)`. State the full-pass cost in the card.

**5. `padStart`/`padEnd` are under-specified where `slice` was not.** The RFC gives the StringPad order (return `s` early when the target is short enough or `fill` is empty, bound only after) — that part correctly follows LLP 1088's deferral note. But it names the bound as "`MAX_LIST_STEPS` code units," where every other string builder is bounded by `MAX_STRING` (64 MiB of UTF-8, [runner/src/vm.rs](/Users/ccheever/projects/exact2/runner/src/vm.rs:27); [host/web-js/budget.js](/Users/ccheever/projects/exact2/host/web-js/budget.js:6)); 65,536 code units appears from nowhere and will refuse a legitimate long padding that `slice` would allow. It also omits the well-formedness rule LLP 1088 D2 imposed on every string result: truncating `fill` to a code-unit length can split a surrogate pair, the runner holds scalar values and must emit U+FFFD once over the whole result, and the JS target's native `padStart` will happily produce the lone surrogate — a difftest divergence unless the JS side normalises as `x_slice` does (`.toWellFormed()`, budget.js:99). Change: bound by `MAX_STRING` bytes counted as built, state the U+FFFD rule, and tabulate the numeric edges (`NaN` → 0, fractions truncate, negative → 0, `Infinity` with empty fill returns `s`, with non-empty fill traps) against `bun` as the runner's string tests already do.

**6. The uncanny valley is the real risk, and D4 already shows the next walls.** D4 refuses `xs.reverse()` with "no edit yet" while accepting its exact sibling `toSorted` — a builder who learns the `to*` pattern from D3 will write `toReversed` next and meet a dead end; `toReversed` is also the cheapest item in this whole RFC (no callback, a trivial Lean definition), so refusing it is the worst cost/benefit in the table. `trimStart`/`trimEnd`, `repeat`, `findIndex`, `findLast`, `lastIndexOf` will follow. Two D4 edits are also wrong as guidance: `xs[i]` → `xs.at(i)` is the substitution LLP 1116.015's reviewers already rejected, because `at(-1)` is the last item where TypeScript's `xs[-1]` is `undefined` — as a *refusal* it is fine, but the message must say "counts negative indices from the end, unlike `xs[i]`," or authors with a possibly-negative index will follow the edit into a wrong program; and `localeCompare` → `a < b ? -1 : ...` presents code-unit order as the edit for locale order, when it is a different order (that is precisely why it is refused) — the message should say locale collation is unavailable and code-unit order is the deterministic alternative. Consequence if unchanged: the guess corpus improves on the 40 known features while the wall moves one method over, which §7's "no other wall may rise" cannot detect on the same features. Change: add `toReversed` to D3 or give it a refusal naming it as the next trigger; fix those two messages; and judge the stage on held-out features, not only the 40 it was designed against.

**7. D5 may be the real lever, but as specified it measures bytes, not cost.** The honest ceiling (≈3% of a build's tokens) means nothing here can be judged on total tokens. What D5 deletes is small: start-here is 10,658 bytes and the card 12,176, and the Expressions bullet is three lines; deleting per-function signatures for the TypeScript methods likely stays under §7's own 1 KB A/B threshold. The risk runs the other way — LLP 1116.013's finding was that reading less up front did not help because builders fetched the same knowledge later — and a one-line method list invites `contract vocab` lookups and, worse, guesses at which methods exist (which is how `.sort` happened). The card today is explicit about absence ("Not in Contract: abs pow sqrt sort reduce find some every contains toUpperCase padStart parseInt," [docs/card.md](/Users/ccheever/projects/exact2/docs/card.md:205)); that line is worth more than the signatures. Change: keep D5's direction, but keep a signature for every method whose result is an option (`find`, `at`) — the place TypeScript's `undefined` and Contract's `none` force a `match` — and count `contract vocab` lookups in the judging builds, not just bytes deleted.

**8. The migration and the human cost are asserted, not shown.** Renaming `floor`, `ceil`, `round`, `min`, `max`, `performanceNow`, `first` touches, by my count, 133 lines of `.contract` in `apps/` and `contract/` alone, plus Contract embedded in tests, docs, and `contract vocab` output, plus every out-of-repo app consuming exact2 by path with no deprecation window (`rules/RULES.md`: "Delete; don't deprecate"). `first(xs)` → `xs.at(0)` is also a genuine readability loss for people: `first` says what it means, `at(0)` says it in TypeScript. LLP 1116.015 T6 required Charlie and James to read whole apps before and after; nothing in this RFC schedules that read. Change: run the rewriter as a dry run and publish the count, and do the T6 timed read of one app before D2's renames land, not after.

## 3. Per decision

| Decision | Verdict | Reason |
|---|---|---|
| D1 (standard) | **Change** | Keep "TypeScript's meaning or a refusal that names it" as the meaning rule; do not replace demonstrated-need as the admission rule with "commonly performed." Add a both-models threshold, a named ES scope, and exclude `app.ts` counts as evidence for Contract's roster. |
| D2 (sugar) | **Change** | Keep `find`/`some`/`every`, `Math.floor`/`ceil`/`round`, `performance.now()`, and `first` → `at(0)`. Fix or drop `Math.min`/`Math.max` (issue 1), specify their arity refusals, state the full-pass bound behaviour of the `find` family (issue 4), and carve out user `fn`s that shadow these names — an app-defined `fn floor` must not be refused as the roster's. |
| D3 (roster rows) | **Change (split)** | Land `padStart`/`padEnd` with issue 5's fixes. Take `toSorted` out into its own design with a named algorithm, item-based bounding, and a same-algorithm JS implementation (issue 3). Consider adding `toReversed`, which is nearly free. |
| D4 (refusals) | **Change** | Keep the table's shape. Fix the `xs[i]` message to warn about negative indices, make the `localeCompare` message say locale order is unavailable rather than implying `<` is the same comparison, and give `reverse` a destination. |
| D5 (docs) | **Keep, with a guard** | Teach the difference only, but retain signatures for the option-returning methods and keep the card's explicit "not in Contract" list; count lookups as well as bytes in the as-built note. |
| §6 (stage 2) | **Change (defer the commitment)** | Sound in principle under `strictNullChecks`, but it is a typing change (flow narrowing, union types in the checker and the Lean typing rules, migration or coexistence of `some`/`none`/`match` against the one-spelling rule) priced here at one paragraph. Write it as its own RFC after stage 1 lands and its valley is measured; do not pre-accept it as "the next RFC" in this one. |

## 4. Answers to §9

**1. Is D1's rule the end state you meant?** Not quite as stated. "TypeScript's meaning or a refusal that names the TypeScript" is the right rule for any form Contract accepts. "The pure operations a TypeScript program commonly performs are there" is an open-ended roster commitment that app.ts evidence and post-D2 guess walls will keep expanding; the end state should be that rule plus a demonstrated-need gate, or every future ES addition becomes an argument this RFC has already conceded.

**2. Accept D2–D5 as the first stage, judged by the guess corpus and D5's bytes?** Yes with the changes above: D2 minus the `min`/`max` problem, D3 split, D4's messages fixed. Judging by the guess corpus and bytes rather than total tokens is right — the 3% ceiling is honest, and LLP 1116.013's comparison cannot resolve it anyway. But the corpus must be re-run with a parser that reports more than its first error (its current counts are first-error only, as LLP 1116.015 noted of the census) and on held-out features, per model, or "no other wall may rise" is untestable.

**3. Stage 2 as the next RFC once this stage lands?** Write it after stage 1 lands, not as a commitment now. The census evidence it was missing does exist (null in 29 of 80 unguided features), but guided builds already learn `match` completely, so the benefit is concentrated in first-screen guesses; the cost is flow narrowing in the checker, union types in the Lean type system, and breaking or dual-spelling `some`/`none`/`match`. That trade deserves its own evidence — in particular whether stage 1's refusals already teach options cheaply.

## 5. To measure or verify before deciding

- **A `NaN`/`-0` table** for `floor`, `ceil`, `round`, `min`, `max` across runner, Lean semantics and JS target (the `arith` difftest already compares bits) — this settles issue 1 in an afternoon and should precede accepting D2.
- **Same-plan tests per D2 rewrite** (the RFC requires them; verify the harness exists and that a wrong rewrite — say `every` without the `not` — actually fails one), plus a diagnostic snapshot proving errors name `.find(...)`, not `filter`.
- **Bound probes:** `find`/`some` on a list past 65,536 items with an early match, and `toSorted` on 5,000 items under comparison counting — demonstrating issues 3 and 4 concretely before the bound design is chosen.
- **`toSorted` cross-executor fuzz** with deliberately inconsistent comparators, runner vs JS target, before committing to native sort on either side.
- **A `padStart` edge table against `bun`** (empty fill at `Infinity`, astral fill truncated mid-pair, fractional and negative lengths), following the runner's existing string-test pattern.
- **A fresh real-build wall count under the current method spelling.** The RFC's 469-build numbers predate D2; what guided builders hit *now* (post-`syntax-method-form`) is the honest baseline for D1's threshold.
- **The rewriter dry run and the T6 read** (issue 8), and a `topics.py`-style replay estimating D5's byte saving multiplied by re-sends, against the 1 KB A/B threshold in §7.
