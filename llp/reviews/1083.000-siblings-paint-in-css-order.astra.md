**Concerns**

The existing `nested-z` fixture is already a counterexample: narrowing isolation makes the web show red while native band sorting shows blue. The fixture requires blue. Evidence: [RFC:48](/Users/ccheever/projects/exact2-wt-sticky/llp/1083.000-siblings-paint-in-css-order.rfc.md:48), [parity.rs:48](/Users/ccheever/projects/exact2-wt-sticky/host/web/src/parity.rs:48), [parity.rs:65](/Users/ccheever/projects/exact2-wt-sticky/host/web/src/parity.rs:65). **Resolve:** specify how descendants that escape their parent’s CSS paint phase are handled. **1. Is §3 correct for every sibling arrangement?**

No. It works for the simple `S(relative), X(static)` case, but not for arbitrary subtrees.

CSS Appendix E orders contributions within a **stacking context**, not complete DOM sibling subtrees. In particular, `position: relative; z-index: auto` does not contain descendant stacking contexts the way `z-index: 0` does. Both receive band L here, although their descendants can participate differently in browser painting.

Use overlapping opaque rectangles in these examples; `T` is transparent and introduces no stacking context:

| Logical siblings | Browser under proposed §3 | Native under §2 |
|---|---|---|
| Blue `S(relative, auto)`, then static `T` containing red `P(relative, auto)` | **P** paints after S in the ancestor’s positioned phase | **S** paints after the entire band-0 T subtree |
| Static `T` containing red `P(absolute, z=1)`, then blue static X | X becomes an isolated zero-level context, but **P** escapes T and paints above X | **X**, band L, paints after T and P |
| Blue `S(absolute, z=1)`, then static T containing red `P(absolute, z=2)` | T is no longer isolated; **P** wins | T is band 0; **S** wins |
| `A(relative, auto)` containing positive-z P, then `B(relative, auto)` | P can escape A and paint above B | B paints after A’s complete subtree |

The third row is the repository’s existing `nested-z` case, not a newly invented fixture: [parity.rs:51](/Users/ccheever/projects/exact2-wt-sticky/host/web/src/parity.rs:51). It directly contradicts D6’s requirement to retain the blue expected result.

The RFC’s three-sibling example can hide disagreement: with `S, T(P), X`, X may cover everything at the sampled point. At another point where X does not cover S and P, their relative order can still disagree.

Moving the existing classifier unchanged introduces additional, simpler disagreements:

- **Earlier blue static A with `opacity: 1`, followed by overlapping red static X:** `Paint.stacks` assigns A to L, so native shows A. The browser creates no context for A and shows X.
- **Earlier blue static A with an opaque `mask-image`, followed by red static X:** `STACKS` misses `MaskImage`, so native can show X while the browser’s real masking context paints A above it.

Bound rows have the same false-positive problem: [rows.rs:28](/Users/ccheever/projects/exact2-wt-sticky/host/web-js/src/rows.rs:28) emits stacking attributes whenever the value is non-null, including opacity 1.

For `each` and regions:

- A repeated literal `T(P)` template can produce a first T that is unisolated and subsequent Ts that are isolated. A single build-time band for that template is insufficient.
- An inactive region arm must contribute no live descendant paint facts. Yet the template projection flattens **all arms** into one tree: [style.rs:85](/Users/ccheever/projects/exact2-wt-sticky/host/web-js/src/style.rs:85).
- Changing a preceding T from static to relative changes whether it qualifies as the **unlayered** predecessor in §3, even if its descendants are unchanged.
- For `T(when shown: P(relative)), X`, inserting P must reconsider X’s parent list. JS region insertion calls `paintList(T)` at [rt.js:1002](/Users/ccheever/projects/exact2-wt-sticky/host/web-js/rt.js:1002); `paintList` queues only T. It does not propagate the changed descendant fact upward. The live Rust implementation does propagate it.

`can_follow` is a conservative **candidate** calculation. `data-exact-box` does not mean “this instance is isolated”; `data-exact-layer` and `paint_own` supply runtime own-paint facts. The existing comments explicitly reject static template guesses for first copies and bound positions: [style.rs:250](/Users/ccheever/projects/exact2-wt-sticky/host/web-js/src/style.rs:250).

Literal **own facts** can be generated ahead of time. Final instance bands generally cannot.

**2. Is D2’s containing-block claim true, and is its rejected alternative worse?**

The narrow argument is sound for the mechanisms it lists, applied to the same ordinary box:

- Non-static positioning participates in positioned painting.
- Non-`none` transforms and filters establish stacking contexts.
- Layout/paint containment also establishes a stacking context.
- Relevant `will-change` hints are not a general escape hatch.
- Overflow, a formatting context, or `isolation` alone does not provide the required absolute-position containing block.

Thus, **leaving the emitted CSS unchanged while assigning compiler-positioned boxes native band 0 really does create the disagreement D2 describes.**

But that does not establish that every broader alternative is worse. The alternatives include narrower lowering—which the repository already implements—or changing the relationship between the containing-block element and the element that paints the authored box. Structural alternatives would need a concrete design for geometry, clipping, input, and accessibility before judging their cost. D2 only disproves a native-only relabeling.

The actual lowering also matters:

- `CONTAINS_ABSOLUTE` covers more than clipping: transforms, filters, several motion rows, and perspective: [tags.rs:48](/Users/ccheever/projects/exact2-wt-sticky/contract/lower/src/tags.rs:48).
- The `holds_nothing` exception can leave a clipping leaf static: [tags.rs:157](/Users/ccheever/projects/exact2-wt-sticky/contract/lower/src/tags.rs:157).
- Adding a possible absolute descendant can therefore change the ancestor’s synthesized position—and its proposed band—even if that descendant is invisible.
- Explicit `position: static` is rejected before that omission branch: [tags.rs:139](/Users/ccheever/projects/exact2-wt-sticky/contract/lower/src/tags.rs:139).
- Press-scale other than 1 emits `scale: calc(...)` at rest. Press-scale 1 emits no such declaration, but today’s paint predicate still counts the row.

The RFC should scope its impossibility claim to the same-element mechanisms it actually discusses. I did not fetch external specifications under the checkout-only restriction.

2. **Both designs need two orders.** With subview sorting, logical order must still exist separately for the consumers above. “A second order to keep in step” therefore does not by itself reject cached hit order.

3. **Reordering must preserve focus and animation state.** The collection code explicitly documents that detaching a view to reorder it clears AppKit’s first responder: [CollectionMac.swift:224](/Users/ccheever/projects/exact2-wt-sticky/host/apple/Sources/ExactKit/Mac/CollectionMac.swift:224). It is not simply an existing “D8 zPosition” exception. Projected-child hit testing must also remain.

5. **Remote native layers need validation.** [NodeViewMac.swift:1094](/Users/ccheever/projects/exact2-wt-sticky/host/apple/Sources/ExactKit/Mac/NodeViewMac.swift:1094) specifically cites WKWebView remote-layer ordering as a reason for setting zPosition. The proposal does not demonstrate that sibling insertion order suffices there.

For exits, LLP 1063 explicitly promises ghosts above their old siblings and outside input/accessibility: [1063:85](/Users/ccheever/projects/exact2-wt-sticky/llp/1063-presence-and-layout-motion.rfc.md:85). They have already left the live maps, so a kernel band alone cannot describe their ordering. Web exit code independently writes `position:absolute` and `z-index:1`: [presence-glue.js:298](/Users/ccheever/projects/exact2-wt-sticky/host/web/presence-glue.js:298). The revised policy must reconcile those mechanisms with authored positive z values and later siblings.

For accessibility, I would not rely on a blanket assertion about VoiceOver’s default ordering. This code already supplies decisive evidence: GPU overlays explicitly expose subview order as `accessibilityElements`, and accessible-name concatenation reads it directly. **Changing reading or keyboard order as an incidental consequence of a paint change is not acceptable.** Preserve logical accessibility order and verify it separately.

**4. Are D5 and §6’s deviations accurate and complete?**

No.

- **The CSS explanation in D5 is substantially correct; its “on every host” conclusion is not implemented by §3.** Put a negative positioned child inside the first, non-stacking, opaque static parent. The browser can paint the child beneath that parent’s background. Native subtree painting keeps it above the parent’s background. No preceding sibling is needed, so §3 supplies no isolation.

- **The cousin deviation is broader than stated and is not consistently shared.** The positive-z and positioned-auto examples in answer 1 remain web/native disagreements. Saying “`z-index` orders siblings” does not explain how the browser is made to obey that restriction.

- **Removing isolation changes grouping and blending, not just rank.** LLP 1001 explicitly promises that a promoted wrapper traps descendant z-index and excludes outside siblings from its blend backdrop: [1001:511](/Users/ccheever/projects/exact2-wt-sticky/llp/1001-kernel-v1.spec.md:511). Narrowing isolation removes those properties in cases currently covered by `--paint`.

- **The compiler-relative deviation needs the actual exceptions and causes.** It is not “every clipping or pressable box,” and a press-scale transform at rest is already layered in emitted CSS.

- **Host-generated contexts are missing.** Text flow writes `contain:layout` directly: [textflow-glue.js:517](/Users/ccheever/projects/exact2-wt-sticky/host/web/textflow-glue.js:517). Layout motion temporarily animates the parent’s isolation: [presence-glue.js:238](/Users/ccheever/projects/exact2-wt-sticky/host/web/presence-glue.js:238). Neither is represented by merely moving the current node-row classifier into the kernel.

- **Band 0 is not a complete model of Appendix E’s steps 4–7.** CSS separates in-flow block backgrounds from inline/text painting. An earlier static block’s text can paint over a later overlapping static block’s background, whereas native whole-subtree painting can cover it. This is a limitation of the claimed model, not a new four-band solution to all static overlap.

Accessibility, navigation, GPU-index, and selection changes should be prevented as regressions, not casually added as paint deviations.

**5. Is D6 sufficient?**

No, although retaining the existing `nested-z` expectation is a useful gate: it should reject the proposed §3 rule.

The minimum useful expansion is:

- **Descendant cases:** the counterexamples above; `auto` versus explicit zero; positive and negative grandchildren; parents with and without real stacking contexts; probes where a final covering sibling does not hide earlier disagreements.
- **Actual CSS facts:** opacity 1 versus less than 1, `none` versus active filter/mask/perspective, press-scale 1 versus active press-scale, and animations that do or do not create contexts.
- **Incremental cases:** bound position and opacity changes, parent block/flex/grid changes, reparenting, inactive-to-active region arms, nested branch removal, and `each` prepend/delete/reorder.
- **Every web execution path:** live Rust host, compiled JS target, initial document output, and adoption/hydration. [document.rs:498](/Users/ccheever/projects/exact2-wt-sticky/host/web/src/document.rs:498) independently computes isolation and is missing from the RFC’s systems list.
- **Apple representation cases:** mixed flat leaves/views, pooling, glass/material/scroll container changes, lifted popovers/dialogs, GPU child indices, and mixed-to-homogeneous band transitions.
- **Motion:** samples during press feedback, layout motion, exits, and Arrange lifts, including intervening batches. Preserve Linux’s explicit exit refusal rather than pretending it has the same ghost implementation: [1063:163](/Users/ccheever/projects/exact2-wt-sticky/llp/1063-presence-and-layout-motion.rfc.md:163).
- **Semantic invariants:** keyboard sequence, accessible names/elements, navigation projection, tab/segment indices, selection order, and reading anchors.

Paint and input must have separate expectations. A pointer-transparent or inert object can paint on top without being the first hit. A transparent hit target need not determine the visible pixel. Flat leaves may paint without a corresponding hit-testable NodeView. Consequently, geometry or `elementsFromPoint` alone cannot establish pixel parity.

For opaque rectangles, shared color probes are useful. Keep those, add web/Linux pixel checks where the assertion is about painting, and retain independent input assertions.

**6. Other inaccuracies, omissions, and overclaims**

- **Material — the homogeneous-list shortcut needs a restoration condition.** Start with logical `[A(L), B(0)]`, physically ordered `[B, A]`. Change A to band 0. **C1 — blocking: rule (b) cannot cover positive-z escaping descendants.**

Take overlapping siblings `T(P), X`, where T and X are static, T is first, and P is absolute with `z-index: 2`.

- T remains unisolated and “escapes.”
- Rule (b) isolates X, putting its stacking context at level zero.
- The browser paints escaped P at positive level 2, **above X**.
- Native whole-subtree painting assigns T rank 0 and X rank ½, putting **X above P**.

Adding static wrappers around P preserves the failure. Two `each` copies make it especially clear: in `T₁(P₁ z2), T₂(P₂ z2)`, r2 isolates T₂. The browser puts escaped P₁ above T₂/P₂; native painting puts T₂/P₂ above T₁/P₁.

**C2 — blocking: D2 confuses an identity transform with `none`.**

The necessary corrections are:

- Non-`none`, not nonidentity, for transforms.
- Classify lowered values: for example, numeric perspective zero emits `none`.
- Include prop-, stylesheet-, and glue-generated contexts.
- Distinguish actual contexts from contexts deliberately forced by Exact.
- Define dynamic lifecycle and precedence when authored isolation, computed isolation, and motion isolation coexist.

Permanent motion isolation can be adopted as policy, but it does not currently describe what all web paths emit, nor does it account for the parent isolation performed by presence glue. Its CSS rationale needs correction.

**4. D3 on Apple**

Keeping subviews in tree order and using zPosition is a sound foundation for ordinary two-dimensional sibling layers. It also preserves the mechanism used to address WKWebView remote-layer ordering: [NodeViewMac.swift:1094](/Users/ccheever/projects/exact2-wt-sticky/host/apple/Sources/ExactKit/Mac/NodeViewMac.swift:1094).

It is not a complete host design yet:

- Flat leaves and merged runs need rank support.
- Filter pictures need effective-rank synchronization.
- Glass, scroll, clipping, and canvas holders need their own correct hit ordering.
- Presence and Arrange need a consistent priority policy.
- Cached orders need mutation-based invalidation.
- Perspective needs matching geometry handling.
- Both capture paths need verification.

The WKWebView comment supports retaining zPosition; it does not prove the new fractional ranks, equal-rank ties, filters, and snapshot composition are correct together.

**5. D1 on the JS target and server rendering**

Yes, the JS target can implement the rule per instance. The current DOM-based architecture is suitable, and r2 correctly rejects baking instance isolation from flattened region arms or shared `each` templates. Those compile-time structures are explicit at [style.rs:85](/Users/ccheever/projects/exact2-wt-sticky/host/web-js/src/style.rs:85).

However, a correct implementation needs:

1. Separate current own facts and effective-z information.
2. Descendant summaries computed before their users.
3. Left-to-right sibling isolation decisions.
4. Propagation of changed exported paint/trap state.
5. Complete hooks for bindings, structure, host-generated contexts, and adoption.

The existing `Set` traversal and descendant selector are not that algorithm. C9 identifies concrete changes that the three-item plan misses.

Server rendering fits only through shared **pure classification/walk logic** plus precomputed descendant information. It cannot depend solely on a live Kernel, because `DocTree` intentionally exists without one.

**6. D5, D6, D8, and costs**

- **D5:** insufficient as written; C4 needs resolution and incorporation into the single isolation definition.
- **D6:** substantially improved, but add the counterexamples above, identity values, generated contexts, negative-z sign changes, flat-run splitting, intermediate holders, lifts/ghosts, perspective geometry, and both capture modes. Expected results must distinguish bare CSS, Exact web, and native results wherever divergence is accepted.
- **D8:** an unused kernel implementation can land first. Keeping active web/native behavior together is sensible. The accurate LLP 1001 deviations should accompany the behavior change, rather than follow it in a later independently landed step.
- **D4:** replacing Linux’s local sort key is straightforward, and its recorded paint traversal supports corresponding hit order. Its projective-depth tie-break should be stated as an exception to §2’s unconditional tree-order tie rule.
- **Costs:** the estimates omit server-summary work, JS state/invalidation, cached hit-order storage, flat-run splitting or promotion, host-only rank updates, and capture work. “Fewer boxes isolated” is not guaranteed for every tree once motion and negative-parent isolation are added. A homogeneous press-scale list benchmark does not exercise heterogeneous ranks, structural changes, transients, or these representations.
- **App validation:** web/macOS screenshots alone do not cover the iOS-specific flat-leaf and hit-container changes. Include affected iOS interaction cases as well as pixels.

The decisive prerequisite is correcting the paint model in C1–C4. Otherwise, broader parity testing will expose contradictions between the proposal’s own expected outcomes.
