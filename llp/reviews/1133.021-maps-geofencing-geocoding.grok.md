## 1. MATERIAL — Android region delivery calls `woke` before any session exists, and the receiver that is awake cannot read the intent

**Where:** D14 (Android row, transition step 1, re-arm), §9 items 5 and 6.

D14 has the host's `ExactRegionReceiver` link no Play services, then "hand the Intent to the geofencing package's `woke`", which calls `GeofencingEvent.fromIntent` and writes `context.regions`, and only then boots a session (step 2). Re-arm is the same entry with an extra constraint: `ExactBootReceiver` "hands a `restore` to the package's `woke`" and "boots no session." §9 item 6 says that until a headless session exists, a transition with no session "is kept and delivered at the next launch."

That entry does not exist on the seam this document inherits.

- LLP 1133.017 D8: a wake reaches the package as `woke` on its session instance, after the session has booted. The host parses a platform callback and writes a durable record before boot (D10's transfer carrier).
- `host/apple/modules/ExactPackage.swift` lines 1–8 and 246–248: one package instance per session; `woke(_:)` runs after the host has booted that session. `ExactWake.kind` (line 324) is `refresh`, `processing`, or `transfer`.
- `host/apple/Sources/ExactKit/Wakes.swift` lines 29–30: a wake with no module ready is held, and `boot` starts a session with no view. The package hears `exact.wakes.due` only after it exists.
- `host/android/canvas/.../Extensions.kt` lines 10–15 and 50–51: the reader makes an `ExactExtension` per session at its first call. Android `woke(id, outcome)` is the outcome callback after `ExtensionContext.wake`. That `wake` (lines 200–208) posts through `changed`, which needs a live session.

Two further facts make "keep it and deliver later" unreachable. Play services is how an app reads a geofence broadcast (`GeofencingEvent.fromIntent`); a receiver that does not link it cannot persist the transition. `BroadcastReceiver.goAsync`'s window, which D14 itself cites, is on the order of 30 seconds, and a process started only for the broadcast dies with the intent still unparsed. The justification for putting the receiver in the host — "a package's Kotlin cannot add" a manifest receiver — is already false in this repository: LLP 1133.017 §14 stage 3 records that WorkManager's library manifest merges `SystemJobService` into the app, and that the Canvas library stays dependency-free so a library there would enter every app's graph.

Adding a fence while a session is already up can go through `context.regions.pendingIntent()`. The closed-app transition, which is the module's point, cannot.

**Resolution:** Same split as transfers. The geofencing package's own manifest-merged receiver links Play services, parses inside `onReceive`/`goAsync`, and writes a process-global store the host can read before a session. It then asks the host to boot a region wake. Do not call session `woke` before boot. Re-arm is that same static entry, with no session and without `INITIAL_TRIGGER_ENTER` (D14 already says a restore raises no event). The headless session delivers the Contract event. It does not parse the intent.

## 2. MATERIAL — "Ask the base permission first" skips iOS provisional Always, and D13 describes both sequences

**Where:** D13 "Ask"; §9 item 8; §12; drive 10.

§9 item 8 says admission "asks the base's decision first in one queued request." The base is `device.geolocation`, whose iOS mechanism is `requestWhenInUseAuthorization()` (LLP 1133.002 D9, lines 427–429). §12 and drive 10 sequence the same two decisions: a `geolocation` ticket, then a `geolocation-background` ticket. D13's opening line says both platforms "ask in two steps."

D13's own iOS bullets, quoting `requestAlwaysAuthorization()`, say the opposite call. From `notDetermined`, that one call shows the When In Use dialog and "Allow While Using App" grants provisional Always. The second prompt is the system's, later, "typically when your app isn't running." From an authorization that is already When In Use, the same call "immediately prompts" for Always, and "further calls have no effect."

Calling the base first forces the second of those states before the fence exists. Caltrain's switch is the `notDetermined` case: both grant lines are new. Provisional Always is the path on which a closed app can receive a region event and meet the later Always prompt outside the app. The when-in-use-then-Always sequence replaces it with an immediate upgrade prompt whose decline sticks. Stage 0 builds item 8, so the wrong sequence is the first thing that lands.

Android's two steps are required: from API 29 geofencing needs `ACCESS_BACKGROUND_LOCATION`, and from Android 11 a single `requestPermissions` that includes both fine and background is ignored (D13 cites this; `runner/src/device.rs` asks one row's permissions in one request). Those two grant lines must stay separate on Android.

**Resolution:** On iOS the queued request's only platform call is `requestAlwaysAuthorization()`, including when `geolocation` is still `notDetermined`. The later system prompt maps to `granted` or `denied` on the next read, which D13 already describes. Run the immediate Always upgrade only when status is already `authorizedWhenInUse`. Keep the substitute's two tickets as the agent's model of the two grant lines. On Android, keep two decisions and never combine fine and background in one request.

## 3. MATERIAL — Caltrain's arrival notice cannot be authorized or reliably posted from the region wake

**Where:** §13 Caltrain (`action geofenceenter` / `action notify`, the grant list); D14 step 4; Q5.

The switch adds a fence. The first `showNotification` runs inside `geofenceenter`. The grants add `device.notifications` and no foreground notification request. Q5 treats the notification gap as Android-only and says the iOS path exercises "every part of the wake."

- LLP 1133.017 D6: a wake may call `showNotification` when notification state is already `granted`, and a wake refuses anything that opens system UI, including a permission request (`person-required`).
- The ruled Harmony consumer (LLP 1133.017 §11 feature 2, lines 1183–1187) calls `requestNotificationPermission()` from the person's foreground tap before registering the wake that posts. The as-built shortcut (same document, §14 stage 0, lines 1458–1460) skipped that because `@exact/notifications` is not built. This RFC cites the shortcut.
- `host/apple/Sources/ExactKit/Notify.swift` lines 58–66: authorization is requested at post time, and `center.add` runs in that completion. `device.notifications` has empty iOS usage keys (`runner/src/device.rs`), so the runtime prompt is the only ask. Apple presents that prompt while the app is in the foreground (`requestAuthorization(options:completionHandler:)`). A region wake is not in the foreground, so a `notDetermined` status does not become a grant.
- D14 step 4 ends `beginBackgroundTask` when the Contract invocation ends. `showNotification` returns before `center.add`'s completion, so a grant that already exists can still lose the post when the task ends.
- Drives 11 and 12 pass on the agent journal. `runner/src/notify.rs` lists the notice when the grant line is present and does not call UserNotifications.

**Resolution:** On the foreground switch, request notification authorization (Harmony's ruled pattern) and add the fence after it is granted. Keep the region background task until `center.add` completes or the expiration handler runs. Do not treat the agent journal as proof of a background post. Say so in Q5.

## 4. MATERIAL — Tier 1 `heading` and `pitch` cannot be implemented by the web map this RFC ships

**Where:** D1 (props, "a camera prop moves the map", `moveend`); D2 gestures; D3; D20 web cell.

D1 puts `heading` and `pitch` in the shared camera because Google's Maps JavaScript API and MapLibre GL JS place a camera that way, and `moveend` reports both. D3's web implementation "draws raster tiles" in Web Mercator, "map-demo's `index.js` made a package." That file (`apps/map-demo/modules/web/index.js` lines 1–2 and 97–100) places axis-aligned OSM PNGs. D2's web gestures are drag, wheel, pinch, and keyboard. They include no rotate. D20's web cell is those tiles.

An XYZ raster tile is north-up. Pitch is a perspective tilt those tiles do not have. A CSS rotation of the tile layer turns the labels with the image, which is a different camera from the one MapLibre and Google report. `moveend` then cannot satisfy D1: an app that sets `heading` to 45 either sees the map stay north-up while the event reports 45, or sees the event report 0 while the prop stays 45, and "a new value equal to the camera's current one moves nothing" no longer has one current value. Stage 1 is this web map, and it is the reference the other cells follow.

tvOS is a smaller cut of the same decision. D20 says "no rotate or pitch, as map-demo's Swift already does." `NativeMap.swift` lines 117–119 disable those gestures on tvOS and lines 127–129 force the camera to heading 0 and pitch 0. The tier 1 props still apply there.

**Resolution:** On the raster web cell, and on tvOS, `heading` and `pitch` stay unspecified as 0, a written value is ignored, and `moveend` reports 0. Keep them as real camera props only on the cells whose map can apply them (`MKMapView`, the Maps SDK). Stop justifying the shared vocabulary with engines the web cell does not ship.

## 5. MINOR — A background relaunch that connects a scene can be read as "a launch with a view"

**Where:** D14 steps 2 and 3.

Step 2 boots the fence's session with no view and delivers the wake. Step 3 holds an undelivered transition for "the next launch with a view, after first pixel" (LLP 1133.004 D6). LLP 1133.017 §14 stage 2, as built: on a background relaunch iOS connects a scene, the view lays the session out and boots it, nothing is drawn, and first pixel never opens the module. The wake opens the module in the background. A wake treated as in front waits for first pixel.

A region relaunch that connects a scene, which that note says happens, matches "a launch with a view" if step 3 is applied. The arrival then waits for a first pixel the background launch does not produce, and Caltrain's notice waits until the person opens the app.

**Resolution:** State that the region wake follows the as-built path: a scene that draws nothing is still a wake launch, and delivery does not wait for first pixel. Reserve step 3 for a transition whose invocation ended `expired` or `superseded`, or whose process died, delivered when a later launch actually draws.

## 6. MINOR — The Android map is given two lifecycle hooks, and `MapView` needs the activity's

**Where:** §14 stage 3.

Stage 3 forwards the `MapView` lifecycle "from the package context's foreground and destroy." `ExactExtension.foreground` and `destroy` are session events. `destroy` runs when the session is destroyed (`Extensions.kt`), which is not process death and is not `onSaveInstanceState`. Google's `MapView` requires the parent to forward `onCreate`, `onStart`, `onResume`, `onPause`, `onStop`, `onDestroy`, `onLowMemory`, and `onSaveInstanceState`. A map that only hears foreground and destroy comes back blank after stop and leaks across low memory.

**Resolution:** Forward the activity's full `MapView` lifecycle through the package context. Name those hooks in the seam list.

## 7. MINOR — Force-quit is a missed region event, and D14 declares the other misses only

**Where:** D14, the paragraph that begins "A fence crossed while it was not armed."

That paragraph declares a miss after reboot, before re-arm, and while location is off. It does not declare a user force-quit. LLP 1133.017 D10 already records, for the transfer carrier, that the system does not relaunch an app the person has force-quit until the person launches it again. The same holds for region monitoring. The next launch's `lastEvent` compare can still record the crossing, and Caltrain drops it when it is older than ten minutes.

**Resolution:** Declare force-quit beside the reboot miss: no relaunch until the next manual launch, and a crossing recovered then is subject to the same staleness rule.
