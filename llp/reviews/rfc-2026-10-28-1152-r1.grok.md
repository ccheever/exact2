## 3. Major oversights

**1. Exact's Conduit arm is not the page Exact ships.** `apps/realworld` public routes are `render=cached`, and `/article/:slug` has no `pages=` source, so the production build does not emit that article. `host/render/src/serve.rs` renders `build`, `cached`, and `request` routes per request and serves `shell.html` only for a client route. LLP 1071's own RealWorld numbers are "pages served per request" with cached routes kept at the origin, and the client-only column there is a different product (FCP 752 ms and content at 1,201 ms against about 420 and 420 for the rendered page). The shootout's harness extends `bench/dioxus/web/bench.mjs`, a static file server that falls back to `index.html`. Serving Exact that way measures the client shell. Resolution: Exact's arm is `<app>-render --serve` behind the same proxy, API origin and grant pointed at the bench server, `Cache-Control` left honest. The static shell is not an arm.

**2. The early-tap script destroys the load and interaction numbers, and its Conduit target does not work signed out.** The probe taps every 50 ms from FCP until 3 s past quiet, in the same session as LCP, CLS, and INP. Largest Contentful Paint stops at the first input. Layout Instability sets `hadRecentInput` for 500 ms after input, so shifts during that storm are excluded from CLS. INP is a high percentile of the session's interactions, so the storm is the INP. The tap target is the first article's favourite control. On Exact's anonymous home that control is a link to `/register`, not a toggle (`apps/realworld/app.contract`, the `Heart` branch). LLP 1071 and `host/web-js/bench.mjs` already record why: signed out, presses on `/` are links, so the press that needs the runtime is the sign-in submit. A logged-out favourite is also an authenticated POST in a typical RealWorld app, so "took effect" is navigation, a 401, or an optimistic flip that reverts. Resolution: two sessions. Session A has no input until LCP is finalized and the shift window has closed. Session B is the early-tap run and is not an input to LCP, CLS, or INP. On Conduit, tap a control that is live in the anonymous HTML and has the same effect in every arm (a tag, as `bench.mjs` does). Keep the favourite for the signed-in mutation, after the token is in place.

**3. The feed arm does not meet the spec the other arms are held to.** `bench/dioxus/exact-bounded/README.md` says the scrollbar spans the 200-row window, not the feed, and a jump cannot reach row 9,000. The device series kept the whole-feed app for that reason. `SPEC.md` is one list of all 10,000 messages. Rule 3 then tells every other framework to use a virtualizer, and those virtualizers keep a full extent. The correctness gate, as written, does not require reaching a late row. `bench.mjs` already shows why `scrollTop` speed is the wrong progress metric for this arm: at 12k and 24k px/s the bounded run reads 1,362 and −2,379 because `scrollTop` steps backward on a window shift. Resolution: the gate includes a jump to a late row, a scrollbar that tracks the full list, and stable position across a live insert. Exact enters only an arm that passes. Other arms may window, and must say so, under the same extent rule.

**4. An agent-built feed field will not be believed, and it is the half that answers question 3.** Conduit's claim is that the other arms were written by people who chose the framework. The feed has no such arms. Exact's entry is the hand-tuned bounded app. The "expert" pass is another model, except for Expo. Two builders alternating does not fix that. Resolution: before any Tier 1 feed port, build React and Solid two ways on the existing Chrome harness: the agent pipeline, and an adaptation of a known-good public virtualized list. Publish that delta. Open the rest of the feed only if that delta is inside run noise. Until then the feed ladder is vanilla, React, Solid, Svelte, Qwik, the existing Dioxus arm, and Exact.

**5. The number the table sorts by does not answer §1, and the index is not computable.** §9's primary table is Mac Chrome, unthrottled. §1.1 is a phone on a real network. Desktop unthrottled is where a compiled client framework is supposed to win and where HTML-first pays the least. The group index is a geometric mean of ratios to the best arm. Scroll mixes higher-is-better (`fps`, rows per second) with lower-is-better, and the best late-frame count, blank count, and CLS are often zero, so the ratio is undefined. Dropping an unmeasured metric from that arm's mean makes a hole rank as a different average. Krausest's mean is a slowdown factor, duration divided by the fastest, over strictly positive duration columns, with a failed benchmark excluding the row. Resolution: sort nothing by a seven-group mean. Report medians and run noise per metric. The headline load table is iPhone Safari at the proxy's 4G setting. Mac Chrome unthrottled is the interaction and scroll lab.

**6. The leg called the one that matters has no input path and no frame path.** Stage 2 says the feed table exists on five legs. The physical phone is specified as `bench/bakeoff/drive.mjs` plus XCTest. That driver is a simulator tool: `xcrun simctl`, and its own comment puts a tap at about 0.3 s. Scroll fps is defined as frames presented, while the harness being extended counts `requestAnimationFrame` callbacks (`bench.mjs` pushes one timestamp per callback and never observes a present). There is no Safari equivalent of that sampling that the document names. Resolution: stage 2's phone leg is specified as a tool that exists on a physical iPhone, or it is not in the round. Until then the phone reports only what the in-page probe can support (paints, a tap's effect, bytes via the proxy), and scroll stays on Mac Chrome with the existing rAF definition.

**7. The matrix does not finish on one Studio and one phone.** §4.1 records every load metric cold and warm at every CPU and network cell. Tier 1 is about thirty arms, the feed doubles the quality axis, the soak is ten minutes, and rounds are unspecified after stage 0's three. A 10-minute soak of forty arms on five legs for three rounds is about a hundred hours before the Chrome condition matrix. Resolution: one condition per leg in the published table (phone: proxy 4G; Mac Chrome: unthrottled, 1×), plus one stress cell (Chrome, 4× CPU, 4G). Soak and energy on a named subset of five arms, not the field. Rounds fixed in stage 0 from the noise of the three baseline arms, and that count is the count for every later arm.

**8. The proxy can erase the SSR result the Tier 1 meta-frameworks are there to show.** Injecting a script as the first child of `<head>` and counting bytes, implemented the way a static server is usually extended, buffers the document. Streaming SSR then becomes a single response, and TTFB moves. The Conduit server's round-trip knob and the proxy RTT are both specified and can stack, so a 4G leg at 170 ms plus D8's 50 ms charges API and server-driven arms twice. `bench.mjs` also refuses a cache-disable because `no-cache` forces the render server to render again. Resolution: the proxy is a streaming reverse proxy in front of each arm's real production server, including Exact's render server. It flushes through the first head bytes, adds one delay, and does not send `no-cache`. A chunked fixture in stage 0 asserts that the first byte and the first HTML chunk are not held for the body.

## 4. Errors

- **iPhone input.** `bench/bakeoff/drive.mjs` drives a simulator app by bundle id through `simctl`. A tap through the XCTest synthesizer is described there as about 0.3 s. It is not a driver for a physical iPhone 17 Pro Max, and it is not shown driving Safari.
- **Safari CPU.** §5 gives Mac Safari the same 1× and 4× CPU cells as Chrome, "with throttling at the proxy." A proxy can delay and bandwidth-limit. CPU throttling is Chrome's `Emulation.setCPUThrottlingRate`. WebKit has no equivalent, so the Safari 4× cell cannot be produced as specified.
- **Lighthouse on every leg.** Lighthouse audits through Chrome. It does not run against iPhone Safari, Mac Safari, or Firefox. §9's headline row, Lighthouse Performance on the phone legs, is unmeasurable on the leg §5 says matters most. The weights cited for Lighthouse 10 (TBT 30, LCP 25, CLS 25, FCP 10, Speed Index 10) match current Lighthouse scoring; the error is where the score is claimed to be collected.
- **LCP finalization.** The Largest Contentful Paint specification stops candidates at the first user input or when the document becomes hidden. A 10 s cutoff is not part of that definition. §4.1 calls the metric "the standard" and then adds the cutoff.
- **CLS during scroll.** The Layout Instability specification excludes a shift with `hadRecentInput`. Standard CLS over the first scroll does not include the shifts the scroll caused. §4.1 asks for both.
- **TBT.** Total Blocking Time, per web.dev and Lighthouse, is the sum of the portions of long tasks above 50 ms between First Contentful Paint and Time to Interactive. §4.1 uses a custom quiet window (the first 2 s after LCP with no long task) and still uses the standard name.
- **INP.** Interaction to Next Paint is the Event Timing duration of an interaction, events grouped by `interactionId`, taking the longest event in the group. With 50 or more interactions it is the 98th percentile; below that it is the worst. The `first-input` entry is the retired First Input Delay entry and is not part of INP. `durationThreshold` defaults to 104 ms in the Event Timing specification; Chromium will not deliver events shorter than 16 ms. `bench/dioxus/README.md` already records that floor ("Event Timing reports only ≥ 16 ms") on the same taps question 2 is trying to split. A metric that cannot see under 16 ms cannot separate Svelte, Solid, and Exact if they are all near that floor.
- **React and the early tap.** §4.2 says React drops the event until hydration. React 18's `hydrateRoot` replays discrete events that land on server-rendered markup during hydration (React DOM event replaying). A Vite client render has no such markup, so the element is absent and the tap misses. Those are different arms in §3.2, and the sentence treats them as one.
- **The whole-feed arm.** §2.2 says it is not a fair representative of the JS target. `bench/dioxus/README.md` built both feed apps as the production JS target. The 80–96 ms and the triple shipment (app.js, plan, data wasm) are the unbounded answer crossing the data-module seam. The bounded answer is a different answer shape on the same target.
- **Presented frames and display periods.** §4.4 defines fps as frames presented and a late frame as 1.5 display periods. `bench.mjs` records rAF timestamps and marks late against 1.5× the median of those intervals. A scroll locked at half the refresh rate has no late frames under the code and many under the RFC. The new series would not line up with the 2026-10-03 Chrome numbers even on the same machine.
- **Core Web Vitals as a lab pass.** The "good" cutoffs 2.5 s, 200 ms, and 0.1 are the field cutoffs. The Core Web Vitals assessment is the 75th percentile of real visits over 28 days. §9 says they are field thresholds and then uses them as a pass on one lab leg. Combined with oversight 2, that lab INP is the tap storm.

The repository checks that do hold: the API origin and grant are the constants in `apps/realworld/app.ts`; public routes are anonymous rendered HTML with the runtime preloaded and a press replayed once; `bootMs` is written on `#exact-root` at the end of `mount` in `host/web-js/rt.js`; the heavy list is 10,000 messages and 104 JPEGs; Contract's built-in tags (`docs/contract-grammar.md`) and `host/web/src/element.rs` have no `table`, `tbody`, `tr`, or `td`; `series.sh` does run 3k, 6k, 12k, and 24k px/s; heavy-list rounds are interleaved and rotated; the bake-off builders and `pairs.json` are as §8 describes.

## 5. The eight decisions

**D1.** Conduit for Tier 1, Krausest only if the stock check passes, and the feed limited to the calibration ladder in oversight 4. Defer Tier 2 and the rest of the feed. Confidence: 80.

**D2.** Community Conduit pins as they are. One feed arm per ladder framework, built to that framework's virtualizer documentation and held to the same extent gate as Exact. A second agent pass is not an expert arm. Confidence: 76.

**D3.** Do not adapt Krausest's DOM check, and do not add a `table` tag in order to be ranked. Ask upstream whether a non-table keyed row can be an official entry. If it cannot, report "does not meet the harness" and leave it out of that table. A table element, if the web vocabulary needs one, is its own Contract change. Confidence: 88.

**D4.** Agree with the document. Try `xctrace` in stage 2 and publish "not measured" if it does not hold. Do not block the Chrome pipeline on it, and do not describe `drive.mjs` as the physical-phone path. Confidence: 84.

**D5.** Publish the first round, losses included, after the method fixes in this review and not after a round of Exact fixes. Fixing Exact and then publishing the rerun is a different claim from the one §7 rule 8 describes. Confidence: 72.

**D6.** Upstream source for Conduit. For the feed ladder, a person who knows that framework signs the arm, or the column says "agent-built." Alternating two models does not answer "that model is bad at Svelte." Confidence: 70.

**D7.** The Studio, dedicated, with the chip and the load average written into the round the way `bench/dioxus/README.md` did. A shared mini is a worse bench even if it idles cooler. Confidence: 64.

**D8.** One delay, applied at the proxy. The server-driven headline uses the same 170 ms as the 4G load leg, with a 0 ms column beside it so framework time and network time can be separated. Showing only 50 ms understates the architecture relative to the network used for load. Confidence: 78.

## 6. The strongest alternative

Keep the existing two harnesses and add no new field until they disagree with a hand-built reference.

Use `host/web-js/bench.mjs` for Conduit: the render server, the mobile profile it already implements (150 ms, 1.6 Mbps, 4× CPU), content painted, a tag tap at `load`, runtime-up, and the sign-in submit, extended with an iPhone Safari leg for those same probes. Use `bench/dioxus/web/bench.mjs` unchanged for the feed, against vanilla, React, Solid, and the current Dioxus build, with Exact entered only under the extent gate. Use Krausest unmodified or not at all.

The measurement that decides: on that unchanged Chrome feed harness, compare the agent-built React and Solid arms to the hand-adapted public virtualizers, and compare Exact's bounded arm to an Exact arm that can reach row 9,000. If either gap is larger than three-round noise, the forty-arm agent shootout is not evidence, and the calibration ladder is the shootout.
