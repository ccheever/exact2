READY WITH CHANGES

**Overall assessment.** The architecture is the right shape: SVG files remain ordinary `image` sources, reuse the kernel’s SVG representation and resolver, and enter the existing raster lifecycle. No new author vocabulary, renderer, or governance apparatus is needed. However, D3–D4 assume sizing and budgeting properties the current pipeline does not provide. Those contracts need correction before implementation; they affect observable behavior, not merely implementation details.

This assessment is based on the requested file reads, without execution or web verification.

**Strengths**

- **D1 and D6 preserve author intent.** Keeping `image`, `object-fit`, and the browser’s existing rendering fits `CLAUDE.md`’s “what the author writes wins” rule.
- **D2 reuses real capabilities.** `kernel/src/svg/scene.rs` resolves inheritance, references, geometry, paint and effects. `kernel/src/svg/path.rs` implements the path grammar, including rendering through the last valid segment. `contract/lower/src/icon_svg.rs` does contain the tokenizer, entity handling and inherited-paint walk described.
- **D3 correctly reads the island implementation.** `host/svg-raster/src/lib.rs` explicitly performs work *after* source rasterization. `SvgIsland.render` constructs a `SvgScene` and calls `sub.root.render(in:)`; Linux’s `paint/svg.rs` consumes the resolved scene through its painter. This agrees with LLP 1055.000 §0’s built description and §8 ruling 4, which supersede its older tiny-skia-on-Apple proposal.
- **D4 and D5 choose sensible integration points.** Reusing source loading, admission, ownership, caching and diagnostics—and retiring the warning only after both native hosts work—avoids a parallel image subsystem.

**Concerns**

1. **Material — SVG dimensions cannot be treated as ordinary raster dimensions (D3–D4).**

   D4’s “width and height, else viewBox, else 300×150” conflates intrinsic dimensions, intrinsic ratio and fallback sizing. LLP 1055.000 D4 explicitly distinguishes them: a `viewBox` supplies a ratio, not intrinsic width and height. One specified dimension, percentage dimensions and fractional lengths also need a defined outcome. LLP 1011 §1’s existing intrinsic seam accepts a positive width/height pair, so this is a real integration question.

   **Resolve:** Specify the representation and sizing rules for SVG intrinsic dimensions and ratio, including how they pass through the existing image measurement seam. Do not turn viewBox coordinates directly into natural pixel dimensions.

2. **Material — requested viewport, raster resolution and cache identity need separating (D1, D3–D4).**

   [RasterDecodePlan](/Users/ccheever/projects/exact2/.claude/worktrees/review-1011-001/host/apple/Sources/ExactKit/RasterImage.swift:264) preserves the natural aspect ratio and caps `maxPixel` at the natural longest side. Linux’s [image planner](/Users/ccheever/projects/exact2/.claude/worktrees/review-1011-001/host/linux/src/image.rs:680) likewise caps scale at one. Consequently, a 24×24 SVG requested at 72×72 pixels still gets a 24×24 plan.

   Apple’s [requestedPixel/resized logic](/Users/ccheever/projects/exact2/.claude/worktrees/review-1011-001/host/apple/Sources/ExactKit/RasterLoader.swift:569) tracks one longest dimension. A viewport aspect-ratio change can require different SVG pixels without changing that scalar.

   D3 also sizes the resolver’s viewport in device pixels. Without a viewBox, absolute SVG coordinates then do not receive the intended display-scale transform. `preserveAspectRatio`, the concrete object size selected by `object-fit`, and raster density cannot be collapsed into one size.

   **Resolve:** Define logical SVG viewport size separately from output pixel dimensions; permit rasterization above natural dimensions; and ensure cache identity and invalidation preserve viewport-dependent content. State where `object-fit` chooses the concrete object size before SVG rendering. These are bounded changes within the raster pipeline.

3. **Material — existing raster reservations do not cover existing island allocations (D4, §5–§6).**

   `RasterDecodePlan.scratchBytes` reserves thumbnail/conversion storage. [SvgIsland.swift](/Users/ccheever/projects/exact2/.claude/worktrees/review-1011-001/host/apple/Sources/ExactKit/SvgIsland.swift:123) independently permits 128 MiB of filter work, plus mask/pattern surfaces and the outer render target. Handing the final bitmap to the loader does not make these intermediate allocations fit its reservation.

   The threading description also contradicts itself: D4 and §6 place Apple rendering on main; §5 calls rasterization off-main. “At most one frame late” and the submillisecond estimate have no evidence here. LLP 1055.000 §0 records substantial costs for complex islands.

   **Resolve:** Say how SVG-owned intermediate storage participates in admission, with resolution reduction when necessary. Explicitly accept or reject main-thread rendering for stage one, and replace timing guarantees with measurements to obtain during implementation. A new background renderer need not be a prerequisite.

4. **Material — the browser-equivalence claim overstates the proposed subset (D2, §3, §6).**

   Dropping `<style>` follows LLP 1055.000 §7’s Contract limitation, whose rationale is that Contract has no selectors. That does not establish equivalent behavior for a standalone SVG file. A designer’s export using classes can produce substantially different native pixels while the unchanged web host renders its stylesheet.

   The animation argument is internally inconsistent: §3 claims browser behavior while acknowledging Chrome animates. Moreover, LLP 1055.000 D15 says islands are **re-rendered as animation is sampled**, not frozen permanently at time zero. It does not justify the proposed still-image policy.

   **Resolve:** Declare stylesheet omission and frozen animation as explicit native limitations requiring acceptance, or support them. Distinguish “ignore animation elements” from “evaluate animation at time zero”; the latter can require animation machinery. Keep Chrome as the stated oracle and record deviations rather than selecting another oracle to excuse a mismatch.

5. **Minor — distinguish reusable ingredients from completed interfaces (D2, §5).**

   [scene::resolve](/Users/ccheever/projects/exact2/.claude/worktrees/review-1011-001/kernel/src/svg/scene.rs:258) requires a `Kernel`, `NodeRef`, environment and presented-value provider; it is not a standalone document resolver. The new module entry therefore needs an isolated kernel document and shared serialization, not just tokenization.

   Also, `icon_svg.rs` is a permissive icon extractor: closing tags simply pop its stack without matching names. It is useful source material, but does not already provide the promised malformed-XML rejection.

   **Resolve:** Name these adaptations and qualify the code-size estimate. Preserve one lowering/resolution implementation and the icon reader’s existing template restrictions.

**Suggestions**

- Extend §4 with focused cases: viewBox-only sizing, one intrinsic dimension, no viewBox at 3×, enlargement beyond natural size, and a viewport aspect change that preserves the longest dimension.
- Exercise one filtered or patterned image under budget pressure, including source replacement while Apple rendering is pending.
- Use LLP 1055.000 §5’s existing native parity smoke and its documented text exceptions. The RFC currently cites `host/web-js/conform.mjs` for island tolerances, whereas the cited specification assigns that comparison to `scripts/smoke.mjs svg`.

**Open questions**

- Is silently omitting embedded styles acceptable for the motivating designer exports?
- Does D5’s bake refusal apply only to targets requiring native decoding? A native subset restriction should not inadvertently reject a browser-valid web-only asset.
- Who implements this, and when? The header names an author and date but no implementer, as `rules/RULES.md` requires.

**Recommended next step.** Fold the sizing, reservation and subset decisions into r2, then implement the existing stages. Keep the shared resolver and host painters; no architectural replacement is warranted.
