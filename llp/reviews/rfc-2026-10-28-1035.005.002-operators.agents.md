# The operator spelling, asked of the agents

## 1. Comprehension

Every family scored 24 of 24 in both spellings: Astra, Grok, Muse, Fable. The spelling makes no measured difference to evaluating a condition.

The state: `{"signedIn": true, "ready": false, "busy": false, "count": 3, "score": 42, "limit": 40, "name": "ada", "mode": "edit", "owner": "ada", "page": 2, "pages": 2, "pinned": true, "draft": "", "kind": "note"}`. The conditions (word spelling; the symbol spelling is the mechanical rewrite):

The reasons given for the symbols: they are the spelling of the TypeScript meaning the language is defined against, they need no reserved words, precedence is the one the reader already knows, and two spellings cost surface, docs and formatting rules. The reasons for the words: they read as the sentence the condition was stated in, `not` stays visible beside its name where `!` is easy to miss next to `!=`, and a condition is a predicate that never needs the symbols' value semantics.

## The answers

### GPT-6 Astra (codex, high)

Assuming pages start at 1, an empty draft is `""`, and `owner === "me"` identifies the current user:

1. `signedIn && !busy`
2. `page === pages || signedIn`
3. `draft === "" && (mode === "view" || mode === "edit")`
4. `score > limit && !pinned`
5. `!ready && !busy`
6. `owner !== "me" || mode !== "edit"`
7. `count === 3 || count === 4 || count === 5`
8. `kind === "note" && !pinned`

I prefer writing the symbols and find them easier to read back because they match the TypeScript expressions I already recognize. If Contract accepted only one spelling, I’d choose `&&`, `||`, and `!`: they make the connection to TypeScript’s meaning immediate. Requiring words would cost me some familiarity and direct copying between the languages, though their meaning would remain clear.

I write the symbols, because the language is defined as meaning what the same TypeScript means, and `&&`, `||` and `!` are what my hands already type in TypeScript. If the language accepted only one spelling, I would keep the symbols, since they are the honest spelling of TypeScript's meaning. The cost of keeping both is larger: two ways to write everything, mixed spellings in one codebase, style arguments, and a formatter or linter needed just to pick one.

### Claude Fable 5.1 (fresh session)

1. `signedIn and not busy`
2. `page == pages or signedIn`
3. `draft == "" and (mode == "view" or mode == "edit")`
4. `score > limit and not pinned`
5. `not ready and not busy`
6. `owner != name or mode != "edit"`
7. `count == 3 or count == 4 or count == 5`
8. `kind == "note" and not pinned`

I prefer to write the words in Contract, and I find them easier to read back too. The conditions sit inside a declarative, CSS-shaped document where almost everything else is prose-like names and values, and `and`, `or`, `not` read as part of that sentence rather than as a jump into operator syntax; `not pinned` reads aloud the way the requirement was stated, while `!pinned` makes the eye stop on a one-character symbol that is easy to miss next to `!=`. The symbols earn their keep in TypeScript because they are surrounded by other symbol-heavy code and because `&&`/`||` carry short-circuit value semantics that a condition does not need. If the language had to accept only one spelling, it should accept the words: a Contract condition is a predicate, never a value expression, so the symbols' extra meaning buys nothing, and one spelling keeps every example, grep and diff consistent. What losing the symbols would cost me is only the muscle memory of pasting a condition straight out of TypeScript and the ability to write a long compound condition compactly; losing the words would cost readability for the people and agents who read the document far more often than they write it.
