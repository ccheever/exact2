**BLOCKER:** none.

**SHOULD**

1. A disposed held resource stays in `state.pending` as ordinary in-flight work. `host/web-js/rt.js:542` sets `r.gone` and leaves `r.ticket` in place, and `host/web-js/held.js:8` then drops that ticket from `heldAsks`. `host/web-js/agent.js:492` still lists every resource that has a ticket and no stream messages, and adds `held: true` only when the ticket is in `heldAsks`. After the region ends, a long poll that is still open is pending with no `held` flag, and it is not in `inflight` either (`counted` is not run on `gone`). `scripts/agent-test.mjs:624` reports that name as work a clock step will land, and `scripts/verify.mjs:824` treats it as busy: the relaunch keeps stepping real time until `REAL_MS` (4 s) and then files a loading finding. A live held request is marked and excluded; this is the let-go case round 2 stopped naming, listed as unmarked work.

2. The server bundle never installs the held hooks. `host/web-js/build.mjs:414` assigns `answering.loose` and `answering.heldReply` in the page entry, after `ts(data)` and before `app()`. `host/web-js/build.mjs:513` calls `ts(data)` and then `app()` in `__start` with the defaults at `host/web-js/ts-fetch.js:111` still in place (`loose` and `heldReply` are no-ops). Tied fetches still count: `call.held`, `call.plain`, and `recount` do not use the hooks, so a purely held answer stays out of `inflight.n` and `__render` does not block on the long poll. An untied fetch does need `loose`. While a held fetch is still out, a fetch started in a plain `.then` (where `answering.call` is null) is supposed to pull those candidates back into `inflight` (`host/web-js/held.js:22`). On the server that call is a no-op, so the render wait can return while that fetch is still out. Reply evidence is unaffected: `clock held` reads the page, and `heldReply` on the server is discarded with the render VM.

**NIT**

`docs/reference.md:1097` says the wait is "20 s at most" and spells the bound only as `<n>s`. The driver defaults to 20 s, also accepts `<n>ms`, and allows a finite bound up to an hour (`scripts/agent-held.mjs:12`). The RFC's wording is the default ("20 s unless given"), not a cap. `docs/contract-for-agents.md:2977` matches that default.

Counting, F10, and `clock held` otherwise match the ruling.

The reply count is per target and rises only for a request that was still held. The runner increments in `fulfill_now` after the ticket is removed from `pending` and only when `p.held` (`runner/src/runner/commit.rs:1081`); a ticket already gone is dropped with no count. `pending.rs:56` puts that map on `state` as `heldReplies`. Web-js does the same in `heldReply` when `current(call.ticket)` (`host/web-js/held.js:12`), and `agent.js:520` copies it onto `state`. The ticket is assigned in `counted` from `send`, which `commit` runs in `Out` before fetch's `finally` microtask, so a live reply sees it. Wasm does not keep a second counter: `glue.js:757` lists a held ticket and does not track it, and `glue.js:1114` returns the runner's state object with `heldReplies` still on it. Linux and Apple name `held` / `heldTargets` from the runner (`host/linux/src/agent.rs:1063`, `Agent.swift:676`). A page with no TypeScript never assigns the hooks and has no `exactHeld` path; `held.js` still loads through `rt.js` with empty maps, and the Rust module seam refuses a held `Answer::Later` (`logic/abi/src/lib.rs:302`).

Unmarked work still blocks a timer. `PendingReq::waited` is in flight and not held (`runner/src/runner.rs:357`); Linux `wait_for_replies` uses `has_pending` (`host/linux/src/agent.rs:1323`), Apple `pendingCount` drops `held` and `device` (`Agent.swift:1038`), and web-js clocks wait on `inflight.n`, which includes an answer that has any plain fetch. The Linux test `an_unmarked_long_hold_is_waited_on_before_a_timer` is still there.

`clock held` takes Apple's clock before the wait, on the same host list as the other clock ops, and `take` returns the frozen clock (`Agent.swift:710`). The bound is finite, greater than zero, and at most an hour, default 20 s. The wait is a rising `heldReplies` count, then `clock data`. The timeout reply is spread under `tags`; `s.op` throws on an `error` field, and the `.catch` leaves the timeout fields intact. The Android reader firing a timer already due at the frozen now is the QUEUE note from round 2.
