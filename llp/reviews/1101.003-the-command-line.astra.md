**1. Overall assessment**

A bounded print-once mode is worth building for the existing harness, and it fits the admitted terminal authoring model without requiring another Agent API operation. This draft is not ready to implement, however. Its completion rule conflicts with how tasks and the harness actually run; its argument for allowing writes depends on an unimplemented plan boundary; and several promised behaviors—failure status, stdin, installation—require substantially more work than §3 identifies. The broad direction is useful, but the implementer would currently have to invent essential lifecycle and interface semantics.

This was a read-only source review at `2ce193976`. I ran no binaries or builds. “Verified” below means verified against source, not observed at runtime.

**2. Strengths**

- **D1:** Reusing the established log-child settlement policy is a good foundation for streaming output. The implementation already tracks child identity and stops before the first busy child (`host/terminal/src/term.rs:373`).
- **D3:** Reusing the router and its URL encoders avoids a second declaration of positional command structure. Correcting the parent RFC’s mistaken claim about terminal launch locations is valuable.
- **D4/D9:** Explicitly authored terminal roots, shared data modules, and keeping screen-driving operations out of the user-facing command syntax fit the repository’s authoring rules.
- **D7/D10:** Reusing typed serialization and removing the compiler from installed binaries are sensible choices.
- **D6/§4:** The distinction between installed-command environment facts and LLP 1106’s rendering flags is consistent across the siblings. The draft also correctly acknowledges that surface expansion needs admission and that startup performance remains unmeasured.

**C1 — BLOCKING — D2/D4/§4: “Nothing in flight” does not describe command completion.**

There are three distinct problems:

- A gated task does not execute when its condition becomes true. It arms a future deadline. See [gates.rs:43](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv-surfaces/runner/src/runner/gates.rs:43). Task intervals must be at least 1 ms (`contract/lower/src/timers.rs:34`). Consequently, the boot commit can satisfy D2 before D4’s command-starting task fires, and D2 then explicitly discards that task.
- The assertion that the harness’s model reply is a runner request in flight is **wrong**. Harness sources return `Answer::Now` (`apps/harness/data/src/lib.rs:246`). Submission returns an acknowledgement while model work continues in a spawned thread (`commands.rs:15`; `agent.rs:47`). Busy state is an application field, `turn.is_some()` (`state.rs:275`), not `state.pending`.
- Request settlement can schedule a mutation’s `then` or the next queued send after removing the request (`runner/src/runner/commit.rs:1217`). Testing only pending requests and streams can terminate between causally connected commits.

**Resolution:** Specify startup, completion, and the draining of continuations as one lifecycle. Include executable Contract examples for starting `/add/:title` and submitting the harness prompt, and explain how their work remains tracked until completion. Changing `task … when` into an immediate reaction would contradict `rules/DEFERRED.md:601`; it cannot be an implicit implementation choice.

**C2 — BLOCKING — D4/D9: The claimed terminal/GUI isolation is not implemented.**

The plan header contains identity, router and locale fields, with no terminal-profile marker ([format.json:4](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv-surfaces/plan/tables/format.json:4)). Terminal source compilation performs admission checks, but emits an ordinary plan (`contract/cli/src/lib.rs:487`). Loading a `.plan` bypasses those source checks (`host/terminal/src/cli.rs:172`), and terminal boot has no surface gate.

Indeed, an existing terminal test boots a plan produced by ordinary `contract::compile` (`host/terminal/tests/screen.rs:53`). LLP 1101 D1 describes the intended header boundary; it is not evidence that the boundary exists.

Explicit CLI mutations are reasonable, but “the plan cannot be served” does not currently establish their safety. “Only the person typing” also excludes the scripts this RFC intends to support.

**Resolution:** Make the plan distinction and rejection on incompatible hosts an explicit prerequisite, enforced before effectful boot. Add it to §3, or replace the argument with another concrete boundary. Treat terminal invocation as deliberate execution, without claiming that its current plan representation prevents reuse elsewhere.

**C3 — MAJOR — D8: Resource failure is not an application exit outcome.**

LLP 1016 D4 deliberately makes transport failure ordinary application data. A source can convert a failed request or non-2xx response into a valid value, and settlement clears the runner’s resource-failure marker ([commit.rs:1287](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv-surfaces/runner/src/runner/commit.rs:1287), `:1333`).

Concrete examples already contradict D8’s promised protection:

- An unavailable harness provider becomes an error transcript entry while submission returns an ordinary acknowledgement (`apps/harness/data/src/agent.rs:38`; `lib.rs:237`).
- Markdown document errors become valid document values (`apps/markdown/data/src/lib.rs:112`).
- A failed mutation ends unsent without setting a resource failure marker (`runner/src/runner/admission.rs:98`).

Current terminal action and clock paths also discard runner errors (`host/terminal/src/host.rs:419`, `:425`).

**Resolution:** Define which outcome determines status: application success, transport failure, runner refusal, or some explicit combination. Include failed mutations and action/timer errors, and distinguish final failure from a recovered failure. D4 must close only after the write’s completion acknowledgement; issuing a send followed immediately by `close()` is insufficient.

Deferring authored status does not remove the need for an application-success signal.

**C4 — MAJOR — D1/D2/§4: The consumer needs an explicit noninteractive consent and shutdown policy.**

The harness requires approval for `bash`, `write_file`, and `edit_file` (`apps/harness/data/src/tools.rs:108`). Its worker waits for an approval decision ([agent.rs:390](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv-surfaces/apps/harness/data/src/agent.rs:390)). D1 prohibits reading keys, and the RFC supplies no other decision source.

After repairing completion tracking, a normal harness turn can therefore wait until timeout. Silent approval would change existing consent semantics. LLP 1105 D5 also explicitly treats absent human confirmation as a reason to withhold destructive tools.

Shutdown is consequential too: shell commands run in their own process group (`shell.rs:116`), and cancellation explicitly kills that group (`:143`). Merely exiting the parent on timeout or SIGINT does not perform that cleanup.

**Resolution:** Specify refusal or another explicitly authorized policy for approval-requiring work. Define cancellation and bounded cleanup for timeout, SIGINT, and broken stdout, including whether partial text or JSON is emitted. Do not add a grant/resume Agent API operation to solve this.

**C5 — MAJOR — D1/D3/D5/D8: Mode selection and argv parsing are not deterministic enough.**

The examples expose immediate inconsistencies:

- `todo active` promises print-once, but on a TTY none of D1’s print conditions holds.
- `cat notes.md | mdview` leaves stdout attached to a TTY, also satisfying none of those conditions.
- `todo tree` could name a route or invoke the existing headless `tree` operation.
- D8 rejects an “unknown host flag,” while D3/D6 turn flags the host does not own into query parameters.

The grammar also leaves unspecified the meaning of `--`, explicit URLs mixed with words or query flags, negative option values, conflicting modes, and absolute paths that could be either locations or existing files.

Existing routing behavior matters: `location_of` normalizes its input rather than preserving it “as-is” (`route/src/location.rs:27`); the route encoder rejects empty, `.` and `..` segments (`route/src/table.rs:448`); and a declared not-found route is itself a fallback match (`:161`).

**Resolution:** Supply a precedence table and concrete argv→mode/location/file examples. Define operation selection, URL-query merging and encoding, missing values, invalid combinations, and fallback-route status. Retain ordinary URL semantics without requiring the implementer to infer shell grammar from them.

**C6 — MAJOR — D5/§3: Stdin does not follow today’s document path, and the required I/O execution is missing.**

For applications granted `fs.read doc:/`, macOS converts incoming file paths into document handles ([DocumentPickers.swift:33](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv-surfaces/host/apple/Sources/ExactKit/DocumentPickers.swift:33); `host/apple/src/picker.rs:217`). The existing Markdown source rejects `/dev/stdin`, because it accepts only `doc:/` paths (`apps/markdown/data/src/lib.rs:400`). Thus “exactly as macOS” is inaccurate for the cited reader architecture.

Nor can a pipe automatically use the ordinary document-opening helper: that helper grants a file through its parent directory (`data/src/documents.rs:65`). Applying it mechanically to `/dev/stdin` would introduce the wrong directory scope.

There is a second missing prerequisite. The terminal loop pumps announcements and timers (`host/terminal/src/cli.rs:205`), but does not dispatch and fulfill general runner requests. Portable storage in LLP 1027.001 requires that host-work path; the existing Markdown source uses `Answer::Later` (`lib.rs:133`).

**Resolution:** Specify the document handle or explicitly different input contract, one-time pipe consumption, EOF/cancellation, and precedence between stdin and explicit files. Add the required executor, grants and storage integration to §3, or narrow the feature to an explicitly supported data-module path.

**C7 — MAJOR — D7: The JSON format and secrecy guarantee are overstated.**

The shared serializer is reusable, but it does **not** contain `navigation.url`; that is not part of `runner::agent::state` (`runner/src/agent.rs:726`). Hosts augment state differently—for example, Linux reports navigation as unavailable (`host/linux/src/agent.rs:224`).

The statement that state “cannot leak a token” is also false as a general guarantee. Store values are excluded (`runner/src/agent.rs:907`), but slots, derives and resources are serialized without secret redaction ([agent.rs:742](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv-surfaces/runner/src/agent.rs:742)). Password masking explicitly leaves application state holding the original value (`:478`). The harness has precisely such a slot, `keyDraft` (`apps/harness/terminal.contract:70`, `:211`).

This does not mean the default print invocation necessarily leaks a saved key. It means the claimed guarantee is not established by using this serializer.

**Resolution:** Specify the shared JSON object and any terminal augmentation precisely. Limit the privacy claim to store values, and decide whether exporting complete application state is the intended public behavior. Specify JSON behavior on timeout, interruption and application failure.

**C8 — MAJOR — D1/D6: Layout and output rules conflict with their cited implementation.**

Inline layout offers `MaxContent` height ([host.rs:207](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv-surfaces/host/terminal/src/host.rs:207)). Taffy converts that to an indefinite parent height before resolving percentages (`vendor/taffy/src/compute/mod.rs:79`, `:114`). Publishing a finite `exactViewport.height` does not itself give `height:100%` that containing-block height. The claimed Todo clipping behavior therefore does not follow from “use inline mode’s document height.”

Other contradictions need resolution:

- D1 forbids terminal queries; D6 permits OSC 11 queries. The claim that inline mode already does this is unsupported: current input decoding has cursor-position replies, not background-colour replies (`term.rs:65`), and the host initializes `dark: true` (`host.rs:156`).
- Loaded images fall back to coloured half-blocks, not text (`paint.rs:517`). Removing colour escapes would leave block characters. Text fallback is the unavailable-image branch.
- CSS `monochrome` is an integer depth, not a Boolean. [CSS Media Queries](https://www.w3.org/TR/mediaqueries-5/#monochrome)
- The precedence of `NO_COLOR` and explicit `--color` is unclear; the cited convention gives explicit command options precedence. [NO_COLOR](https://no-color.org/)

**Resolution:** Define the percentage-height basis, document extent and clipping behavior separately. Choose one query policy. Specify the plain-image path and exact styling precedence. Use CSS value types, and clarify how `media` reflects actual browser printing rather than unconditionally reporting `screen` on every other host.

**C9 — MAJOR — D10/§3: Installation requires more than an installer branch and embedded bytes.**

The application resolver rejects directories without `app.contract` ([app.mjs:475](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv-surfaces/scripts/app.mjs:475)). Both named terminal consumers currently lack that file and an app manifest. The manifest schema also lacks `host.terminal` and forbids additional host properties (`scripts/app.schema.json:397`).

The terminal runtime directly depends on the compiler (`host/terminal/Cargo.toml:22`), so a release artifact needs a concrete dependency separation. Baked plan bytes alone do not specify asset packaging or app identity.

Finally, current Mac shims invoke `open -a` (`scripts/exact.mjs:149`). They do not demonstrate a way to distinguish “a file or URL from Finder” from shell invocation. Finder normally reaches the registered bundle separately.

**Resolution:** Specify terminal-only app discovery, manifest shape, bake/build entry, compiler-free runtime boundary, artifact/assets location and uninstall behavior. Require terminal shims to preserve argv, working directory, stdio, signals and exit status. Resolve Q4 or defer dual-host dispatch.

**C10 — MAJOR — Header/§4: Admission and ownership remain prerequisites.**

The draft correctly says it has no implementer and requires an expanded admission. Those are substantive open conditions under `rules/RULES.md:47`, `:58`, and `rules/DEFERRED.md:760`, `:784`. The previous terminal waiver is recorded for that admission; it does not supply a new take for this expansion.

**Resolution:** Before treating this as implementation authority, identify the implementer and record the bounded admission with a take or written waiver. Include the newly exposed prerequisites above in that scope. Update shipped author guides with implementation, as required by `rules/DEFERRED.md:779`.

**C11 — MINOR — D4/D7/§5: Several rejected alternatives use incorrect reasoning.**

- “No public API stability” permits renames; it does not bind them. D7 itself correctly accepts that consequence for JSON names. Rejecting automatic action export may be sensible, but that is different from rejecting explicitly selected action bindings.
- LLP 1105 deliberately specifies authored tools and rejects deriving them from the accessibility tree (`llp/1105-apps-as-tools-for-agents.rfc.md:150`). D7’s statement that the accessibility view “belongs to LLP 1105” mischaracterizes the sibling.
- Shell completion does not require the route table outside the executable; an executable could answer completion queries from its embedded table. Deferring completion for lack of a consumer is sufficient.

**Resolution:** Correct these rationales without expanding implementation scope. Keep LLP 1106’s launch-input “state” distinct from D7’s serialized runner-state output; their different meanings are compatible, but neither is interchangeable with the other.

**4. Suggestions**

- Start with the harness lifecycle: submit once, track the full turn, handle approval requirements, report an outcome, and cancel cleanly. That should determine the completion contract.
- Add compact decision tables for mode selection, argv parsing, and termination/output behavior.
- Separate existing mechanisms from required prerequisites in §3, particularly surface gating, request execution, document handles and terminal-only packaging.
- Replace “one test per exit status” with cases that distinguish the semantics: delayed startup, mutation continuation, background model work, application failure represented as data, approval required, stdin with TTY stdout, timeout cleanup, and incompatible-plan rejection.
- Keep installation and persistent Todo writes only if they belong to the admitted first slice; otherwise defer them explicitly instead of understating their dependencies.

**5. Open questions for the author**

1. What observable event starts a command, and what proves that its complete application operation has finished?
2. Is print-mode harness work refused when approval is needed, or is another explicit authorization policy intended?
3. What application signal distinguishes successful output from an error represented as valid resource data?
4. Should positional commands and piped stdin imply print mode when stdout remains a TTY?
5. Are document input, portable storage and dual-host installation required for the first consumer, or separate follow-up work?
6. Who will implement the bounded slice, and what take or waiver admits it?

**3. New concerns**

**N1 — BLOCKING — D2/D4/§3: `turn` being set does not establish continuous `aria-busy`.**

D2 says an entry remains busy throughout the turn and that the harness already satisfies the required contract. These are different state fields:

- Starting a turn inserts a normal user entry, sets `s.turn`, and spawns the worker: [agent.rs:25](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv2-astra/apps/harness/data/src/agent.rs:25), `:50`, `:66`.
- The tree’s busy attribute is **`e.busy`**, on individual transcript entries: [terminal.contract:392](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv2-astra/apps/harness/terminal.contract:392). The live region conditioned on `session.busy` has no such attribute (`:242`).
- A busy assistant entry is created on text arrival, through `show_tail`: `agent.rs:225–236`, `:347–349`. Before that, the request returns `Answer::Now` and there is no runner request holding completion (`data/src/lib.rs:246–255`).

The existing mock makes this gap concrete: it emits usage and then waits **700 ms before text** ([mock.rs:19](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv2-astra/apps/harness/data/src/providers/mock.rs:19), `:260–264`). During that interval, D2 can declare the command done. Entry settlement also creates gaps around subsequent tool/model work.

**Resolution:** Explicitly change the harness to bind a persistent node’s `aria-busy` to the entire `session.busy` lifetime, independently of entry-level streaming. Add this to §3 and cover silent initial waits, tool-only replies, and transitions between rounds.

**N2 — MAJOR — D2/D8: Cancellation, cleanup completion, and the deadline are different mechanisms.**

The new assertion that the harness’s `interrupt` kills its process group is inaccurate. It sets a cancellation flag, clears the turn, and then calls `pump`, which may start the next queued prompt ([agent.rs:164](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv2-astra/apps/harness/data/src/agent.rs:164)). The shell worker later observes that flag and kills its group ([shell.rs:143](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv2-astra/apps/harness/data/src/shell.rs:143)). Returning from `interrupt`, or observing `session.busy == false`, therefore does not acknowledge cleanup.

The generic terminal host also has no specified connection to this application command. Harness does not implement `DataSource::interrupt`; that existing interface interrupts a running source call and defaults to `None` ([source.rs:461](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv2-astra/runner/src/runner/source.rs:461)).

Furthermore, “bounds the whole run” needs qualification. Source calls are synchronous (`source.rs:343`), and the current writer uses blocking `write_all`/`flush` ([term.rs:643](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv2-astra/host/terminal/src/term.rs:643)). A deadline checked by the main loop cannot bound either. LLP 1106 D11 explicitly distinguishes cooperative interruption from an externally enforced deadline.

Finally, `close()` must write what it committed, but “on any of these” it also cancels, after which the live region must not be written. The ordering is unresolved.

**R5-1 — MAJOR — D2: Timeout recording still depends on the thread that may be blocked.**

[D2:162–175](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv5-astra/llp/1101.003-the-command-line.rfc.md:162) assigns timeout recording to the loop, while requiring watchdogs to derive their status from the shared record.

Consider a streamed write that blocks **before** the timeout expires, with no signal received. At the deadline, the loop cannot record timeout. At deadline plus two seconds, the watchdog must select a status from a record that may contain no termination cause. The existing blocking boundary is real: `host/terminal/src/term.rs:643–644`.

**Resolution:** Require the timeout observer to record expiration independently of loop progress. Anchor forced termination to the original absolute deadline plus two seconds, rather than to when the loop notices expiration. Cover this case without sending any signal.

**R5-2 — MAJOR — D2: `std::process::exit` is not the claimed cleanup-free forced exit.**

[D2:159–160](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv5-astra/llp/1101.003-the-command-line.rfc.md:159) says it “runs no cleanup.” The repository’s pinned Rust 1.97.0 source contradicts that:

- [`process.rs:2537`](/Users/ccheever/.rustup/toolchains/1.97.0-aarch64-apple-darwin/lib/rustlib/src/rust/library/std/src/process.rs:2537) calls `rt::cleanup()` before exiting.
- [`rt.rs:139`](/Users/ccheever/.rustup/toolchains/1.97.0-aarch64-apple-darwin/lib/rustlib/src/rust/library/std/src/rt.rs:139) performs once-only cleanup, including stdout cleanup.
- [`stdio.rs:727`](/Users/ccheever/.rustup/toolchains/1.97.0-aarch64-apple-darwin/lib/rustlib/src/rust/library/std/src/io/stdio.rs:727) can flush buffered output.

Rust also explicitly documents execution of registered exit handlers. Skipping stack destructors is a narrower guarantee. [Rust `exit` documentation](https://doc.rust-lang.org/std/process/fn.exit.html)

Consequently, this call does not establish the unconditional, non-flushing forced path that the watchdog contract needs.

**Resolution:** Specify a forced-exit primitive that bypasses runtime flushing and exit handlers, such as the supported Unix platform’s `_exit` equivalent. Keep ordinary cleanup in the cooperative path, and correct the factual claim.

**R5-3 — MAJOR — D1/D2/D7: Interrupted final text can look successfully complete.**

[D2:177–196](/private/tmp/claude-501/-Users-ccheever-projects-exact2/bc4d76d2-3c4d-45d2-8102-28fc48fc9da5/scratchpad/rv5-astra/llp/1101.003-the-command-line.rfc.md:177) freezes status when final output begins, then cancels remaining output on a late signal or timeout while retaining that status.
