Answers to the open questions:

1. **Web refusal versus warning:** refuse known stale inputs. Do not treat passing this heuristic as proof of freshness. Prefer recording actual build inputs in the existing completion marker; until then, report freshness as unverified and warn on broad heuristic matches. Refusing only app-directory changes misses shared dependencies.
2. **Contact sheet versus paths:** lead with a bounded contact sheet, with frame times identifiable from labels or reply metadata. Preserve access to full-resolution frames when needed. Missed or overreaching items:

- **D1’s input coverage is the largest omission.** The web build reads inputs outside the named roots, including `canvas/recorder.js`, shared Rust dependencies and optional Markdown/text-flow engines. Apple’s binary receipt deliberately excludes replaceable app-artifact watches; adding only Contracts and `app.json` still misses packaged assets. Linux’s sibling `.d` omits environment dependencies, as `unitDepInfo` itself documents. Deleted inputs also need handling. These checks are useful detectors, not complete build equivalence.
- **Exemptions need truthful scope.** A web URL delegates build ownership to its server. A native `--url` still launches a local host binary, which can be stale. Explicit binary selection should report freshness as unchecked rather than silently implying verification.

Reject platform-timing film or label it appropriately. Inspect actual carrier PNGs before claiming universal support: `png.mjs` accepts only non-interlaced, eight-bit RGB/RGBA.

D9’s `bun test host/web/` also includes browser/integration tests with prerequisites; its scope is broader than four repaired clock tests. Name and measure the intended suite before adding it. Attached sessions remain a major usability priority, appropriately owned by their existing RFC.
