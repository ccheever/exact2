Reviewed independently.

1. **MATERIAL — macOS cannot recover crossings that occurred while the app was quit.** D14, lines 660–664, and D20’s macOS cell promise recovery through `record(for:).lastEvent`. [Apple’s documentation](https://developer.apple.com/documentation/corelocation/monitoring-the-user-s-proximity-to-geographic-regions) says macOS monitoring works only while the app runs and the system is awake. [Apple’s CLMonitor presentation](https://developer.apple.com/videos/play/wwdc2023/10147/) further explains that `lastEvent` records an event delivered to the app; it does not independently expose unconsumed changes. This cannot recover a crossing or its original timestamp during a quit interval.

   **Resolution:** limit macOS to monitoring while running and awake. Reconcile genuinely recorded events, and declare crossings during unmonitored intervals missed.

2. **MATERIAL — Caltrain’s first arrival notification lacks a permitted authorization path.** §13, lines 1064–1095, and drives 10–12 authorize location, then first call `showNotification` inside a wake. Inherited LLP 1133.017 D6, lines 419–427, permits posting only with notification authorization already granted and forbids permission requests during wakes. The selected built-in implementation calls `requestAuthorization` when posting ([Notify.swift:58](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1133021/r1/capsule/host/apple/Sources/ExactKit/Notify.swift:58)); [Apple documents](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications) that its first call prompts. The agent substitute merely lists the notification ([notify.rs:176](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1133021/r1/capsule/runner/src/notify.rs:176)), concealing this failure.

   **Resolution:** make foreground notification authorization part of enabling arrival notices, with the necessary permission API an explicit prerequisite. Add a fresh-install drive that obtains authorization before a cold arrival; wakes must post only under existing authorization.

3. **MINOR — The iOS permission sequence has two conflicting definitions.** D13, lines 536–543, describes calling `requestAlwaysAuthorization()` directly from `notDetermined`, producing provisional Always. But §9 item 8, §12, and drive 10 require the base geolocation decision first. The built base implementation calls `requestWhenInUseAuthorization()` on iOS ([Geolocation.swift:169](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1133021/r1/capsule/packages/geolocation/apple/Geolocation.swift:169)), so the subsequent request follows D13’s already-When-In-Use branch.

   **Resolution:** choose sequential acquisition or a combined Apple acquisition, then align the dependency queue, permission facts, substitute and drives.

4. **IMPLEMENTATION-PHASE — Apple’s map screenshot drive needs a verified capture path.** §12 and drive 4 promise screenshots after deleting map-demo’s snapshot implementation. That implementation explicitly compensates for MapKit’s Metal content being absent from ordinary host capture ([NativeMap.swift:5](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1133021/r1/capsule/apps/map-demo/modules/apple/NativeMap.swift:5)), while package factories currently force `snapshot = false` ([ExactNativeViews.swift:145](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1133021/r1/capsule/host/apple/modules/ExactNativeViews.swift:145)).

   **Resolution:** verify capture of plain tiles and native markers using compositor capture—the Mac already offers `screenshot … window`—and establish the iOS path. Add package snapshot support only if existing capture paths cannot satisfy the drive.

**Delta assessment**

The principal architectural changes are sound:

- Moving rotation and tilt into platform records makes tier 1 internally consistent while retaining native gestures.
- Android package receivers can parse Play services broadcasts before a session exists and persist transitions through the host’s store. Calling `woke` after boot preserves the package-instance seam.
- Forwarding the activity lifecycle closes a real MapView requirement: Google explicitly requires the eight callbacks r2 lists. [MapView reference](https://developers.google.com/android/reference/com/google/android/gms/maps/MapView).
- Treating a background scene connection as a wake follows LLP 1133.017’s as-built findings. Declaring force-quit uncertainty and measuring it is appropriate.
- Suppressing initial-enter during Android re-arm avoids manufacturing another arrival at every launch.
- Foreground notification authorization, the explicit notifications dependency, and holding the wake through posting completion are necessary corrections. The added resource guard, however, introduces the failure below.
- The screenshot obligation and revised staging are reasonable. Revision metadata and review notes introduce no substantive issue.

**New concerns**

1. **IN-DELTA — MATERIAL: the notification-status guard can permanently discard an authorized cold arrival.**

   **Location:** §13, lines 1127 and 1155–1156; D14, lines 676–680.

   `notices` is an independently loading resource. The immediate Rust `arrivalNotice` can finish before notification status arrives, leaving `notices` at its `empty()` fallback. The guard skips posting; the invocation completes and its transition is deleted. A later status update does not rerun `then notify`.

   **Evidence:** [LLP 1133.004:447](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1133021/r2/capsule/llp/1133.004-notifications.rfc.md:447) explicitly makes notification status asynchronous. [LLP 1133.017:459](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1133021/r2/capsule/llp/1133.017-background.rfc.md:459) excludes unrelated boot-time requests from wake-owned work. The [runner:271](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1133021/r2/capsule/runner/src/runner/modules/wakes.rs:271) completes an invocation once its owned work is empty.

   **Resolution:** perform current-authorization admission within the wake-owned posting operation, refusing without prompting, or explicitly await status within the wake’s chain. Import the module’s `showNotification` explicitly. Add a cold drive that delays the status answer until after `arrivalNotice` finishes.

2. **PRE-EXISTING — MINOR: “next departures” are computed at the arrival event’s time.**

   **Location:** §13, lines 1160–1163.

   The plan accepts events up to ten minutes old but queries the board at their timestamp. It can therefore advertise a train that has already departed, including under ordinary Android delivery latency.

   **Evidence:** [Caltrain’s board implementation:326](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1133021/r2/capsule/apps/caltrain/data/src/lib.rs:326) filters departures against the supplied time.

   **Resolution:** use the event timestamp for freshness and the current time for the departure board.

3. **PRE-EXISTING — MINOR: two retained sentences contradict Android’s new ownership split.**

   **Location/evidence:** D17, line 741, and §15 question 3, line 1312, still call the receiver the host’s; revised D14 assigns it to the package.

   **Resolution:** align those sentences with the package receiver over the host store.

4. **PRE-EXISTING — IMPLEMENTATION-PHASE: verify Android recovery after location returns.**

   **Location:** D14, lines 641–645 and 691–697; stage 3.

   Android requires re-registration after `GEOFENCE_NOT_AVAILABLE`; reenabling location does not itself restore those registrations. [Android’s re-registration guidance](https://developer.android.com/develop/sensors-and-location/location/geofencing#reregister-geofences).

   The RFC already acknowledges this requirement, so the retry mechanism is implementation work. Add an off→on drive while the app remains closed, verifying restoration without a synthetic initial-enter notification. If recovery intentionally waits for launch, declare that extended outage explicitly.

The broader scan found no additional MATERIAL defect in package separation, map camera semantics, geocoding availability policy or the region-carrier architecture.

Verdict: NOT READY
