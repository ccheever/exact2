The core/driver split is sound, and slice 1 is buildable on today's runtime. The core does no I/O and reads no clock; the driver moves bytes and passes `now`. One core per partition file matches the shared device. Concurrent downloads of one id can share the kept path if publication stays on one media queue. D3's choice to show a kept file online without a re-download is acceptable for ordinary avatars: `asset_home` on each `asset()` call is the same window as the row's text, and a download per avatar is the cost the farm was avoiding. 1. **BLOCKER** — §0.1 (the queued-rounds bullet), D2 "The queue" and the time paragraph, D2's table row "After every round, and at open", D3 "When it is checked" and the `keep: "none"` paragraph. r4's race fix says every manifest change (`asset`, `asset_reply`, `media_due`, `media_clear`, the open sweep) runs in one media queue. §0.1 and D3 still say the retention check runs after every round inside the partition's round queue, and at open. D2 also says nothing is checked before the page's first `asset` call, while D3 says `keep: "none"` purges on open. Following the round-queue and at-open sentences puts a removal on a different queue from a publication and recreates the race §0.2 says r4 closed. The draft avoids it by awaiting `mediaDue()` from the round while doing the manifest work on `partition.filing`, and only after the first `asset()` call (`snapback.ts` around the round's `mediaDue()` call and `media()`). A page that still holds `app:/cache/snapback4/<stem>/<id>.<ext>` and never calls `asset()` never purges, and `appURL` keeps serving the file. **Change:** one rule. Those six steps are the media queue. The round enqueues `media_due` and waits; it does not read or write the manifest. `asset()` takes the media queue only after `sync()` has returned, and `media_due` does not call `sync()`. `keep: "none"` and the stray-file sweep run at partition open.
