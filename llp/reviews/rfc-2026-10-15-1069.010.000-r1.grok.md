# Review of LLP 1069.010.000 (r1)

**Reviewer:** grok grok-4.7, reasoning effort xhigh, run 2026-10-15 by Claude (Opus 5.5) for Charlie Cheever, read-only on the r1 draft over `9f4042a3a`, blind to the other two reviews. Scope given: foundational and directional questions only. The text below is the reviewer's final message, unedited.

VERDICT: ACCEPT WITH CHANGES

1. A kept grant has to be the object the person chose, and it has to stay that object. D3 keeps every `doc:` handle minted from ⌘O, Finder, or Open With. On macOS and Linux those routes do not mint the file. `open_route` retains the parent directory and delivers the file beneath it (`data/src/documents.rs`; LLP 1069.010, "As built: slice 3", Containment and The routes). Persisting that handle gives lasting access to a directory the person did not choose. Slice 3 already records that the App Sandbox cannot do this and would mint the file alone, so the kept set would encode an unsandboxed widening. That breaks D7 ("widens time, not reach") and Q2, which requires handles to stay expressible as security-scoped bookmarks of the user's choice. Linux makes the same mistake in a second way: D3 stores a canonical path, and the next launch opens whatever now sits at that path. That undoes the retained-directory identity slice 3 was built to keep. Apple's stale-bookmark refresh and a web `FileSystemHandle` follow the chosen object. Change: the kept entry is the file or folder the person selected, the URL Open Recent already records (LLP 1069.010 D5). A parent handle used for sibling listing dies with the session. Across launches the id resolves to that same object, or it is forgotten with `ENOENT`. On Linux a stored path is only a way to find the object again; a replacement at that path does not take over the grant.

2. Revocation has to be a host act the app cannot withhold. D7 says the person can always revoke, and counts Clear Menu, `forgetDocument`, and the browser's site settings. `forgetDocument` is the app's own API. An app granted `doc.keep` that never calls it keeps the grant. `rules/DEFERRED.md` refuses durable capability grants until there is a store, revocation, and a rule for files that move. The proposal's store meets that only where a platform act clears the host's set: macOS Clear Menu, and only while the kept set is exactly that menu, and the web, if site settings drop the handles in the glue's IndexedDB. iOS and Linux have no such act. Parent D5's declared absences are that iOS keeps recents in Files and the web has none. Change: the host is the revoking authority. Keep the macOS list identical to Open Recent so Clear Menu clears every entry, with no second store beside it. On the web, clearing the site's file permission or site data must drop the host's handles. On iOS and Linux, name a host-level revoke the app cannot suppress before claiming the person can revoke there.

The two problems are real, listing a large tree is already in reach, and the watch belongs first: it is session-scoped, uses the `fs.read doc:/` grant the app already holds, and needs no rule change. LLP 1016.002's model is the right one for files. A topic that means "read again" is the fact FSEvents, inotify, and `FileSystemObserver` can all report, and re-reading loses nothing the editor must know. A host-owned bounded recents list, gated by `doc.keep`, with every other durable grant still refused, is the right stage 2 shape and the right trade (§5).
