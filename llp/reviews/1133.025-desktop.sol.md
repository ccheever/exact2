1. **MATERIAL — Failed shortcut replacement conflicts with the promised lifetime.** [D3, lines 292–310](llp/1133.025-desktop.rfc.md:292) promises uninterrupted registration, but an unavailable replacement returns a successful answer containing `registered:false`. The runner subsequently releases the previous argument group once the request settles ([bound.rs, lines 332–345](runner/src/runner/modules/bound.rs:332)). Changing working chord A to unavailable B therefore leaves neither registered.

   Keeping A implicitly would also contradict the stated reader lifetime: no reader now requests A, and the answer describes B. The existing consumer avoids this: [T3SnapShot.swift, lines 332–338](examples/t3-code/modules/apple/T3SnapShot.swift:332) retains the previous choice on failure, and [T3SnapshotShortcut.swift, lines 100–106](examples/t3-code/modules/apple/T3SnapshotShortcut.swift:100) releases its registration only after replacement succeeds. [§12.1, lines 802–816](llp/1133.025-desktop.rfc.md:802) removes that distinction while repeating the guarantee.

   **Decision:** separate candidate validation from the committed registration, or explicitly retain and report the effective registration after failed replacement. Test A → unavailable B, including which chord still fires and what settings display.

2. **MATERIAL — An accessory app’s status owner can disappear with its last document session.** [D4, lines 356–360](llp/1133.025-desktop.rfc.md:356) assigns status items to the launch session, falling back to the oldest surviving session. This explicitly accommodates `navigate-new`, but supplies no owner when none survives. The parent [LLP 1069.010 D8, lines 320–321](llp/1069.010-the-mac-as-a-document-platform.rfc.md:320) preserves normal document-window closing; [main.swift, lines 456–478](host/apple/Sources/ExactMac/main.swift:456) destroys the corresponding session.

   Consequently, an accessory `navigate-new` app can show its window, close its final document, and lose its status item, timers and shortcut readers while its process remains running. [D6’s promise of continued execution, lines 452–456](llp/1133.025-desktop.rfc.md:452), does not settle which session survives. Its reachability fallback checks only the initial commit. [§12.4, lines 865–870](llp/1133.025-desktop.rfc.md:865) tests showing Settings but never closing and reopening it.

   **Decision:** retain a dedicated application session, reserve the launch session independently of document windows, or reject this manifest combination. Extend the fixture through closing the last window and reopening it, verifying continued status updates and registrations.

3. **MINOR — The first status-item hatch cannot run at its promised moment.** [D9, line 552](llp/1133.025-desktop.rfc.md:552) promises the hatch before the item is first shown. [D6, lines 446–450](llp/1133.025-desktop.rfc.md:446) first places the item, then loads the app module. Existing activation follows that ordering ([SessionActivation.swift, lines 8–19](host/apple/Sources/ExactKit/SessionActivation.swift:8)); hatches connect after the gate.

   This affects initial configuration, including visibility restored through `autosaveName`, as [Apple documents](https://developer.apple.com/documentation/appkit/nsstatusitem/isvisible).

   **Decision:** explicitly permit an initial presentation with host defaults followed by the hatch, and declare any settings that must precede placement. The unpublished-frame boot approach itself is coherent; this contradiction does not independently block it.

**BEYOND — Data-code live reads lack the argument-specific ownership this design assumes.** [D12, lines 694–696](llp/1133.025-desktop.rfc.md:694) promises registration only while its owning answer is kept. However, [modules.rs, lines 994–1001](runner/src/runner/modules.rs:994) forwards data reads without their resource owner, and [bound.rs, lines 305–311](runner/src/runner/modules/bound.rs:305) explicitly releases their argument groups only with the whole source name. If data resources hold A and C, replacing A with B can leave A registered while C remains. Track argument groups by owning answer across Contract, TypeScript and Rust, and verify independent replacement and removal. Other argument-keyed modules face the same problem.

**BEYOND — Windows currently couples application progress to painting.** [D6, lines 452–455](llp/1133.025-desktop.rfc.md:452) requires hidden execution, but [window.rs, lines 235–267](host/windows/src/window.rs:235) pumps work and timers inside drawing; [lines 563–567](host/windows/src/window.rs:563) stop scheduling while minimized. Separating session execution from presentation is necessary across background uses. For this RFC, that is **IMPLEMENTATION-PHASE**: the intended behavior is already decided. Excord’s heartbeat must be verified while its window receives no paints.

1. **(IN-DELTA; MATERIAL) Command-line handover cannot preserve every Windows activation payload.**

   [D6, lines 583–596](llp/1133.025-desktop.rfc.md:583), and [D11 item 5, lines 803–805](llp/1133.025-desktop.rfc.md:803), prescribe forwarding a secondary process’s command line and then exiting, explicitly covering notification activation.

   Windows notifications do not necessarily carry their payload in that command line. Microsoft’s [notification quickstart](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-quickstart) registers the COM executable with the constant marker `----AppNotificationActivated:`; the notification arguments arrive subsequently through `NotificationInvoked`.

   This creates a startup race: if notification activation starts a secondary process after the primary takes its mutex but before its notification endpoint is ready, forwarding that marker and exiting loses the notification’s actual arguments. Ordinary warm clicks reaching an already registered primary are unaffected. The failing case violates [LLP 1133.004 D6, lines 293–300](llp/1133.004-notifications.rfc.md:293), which requires retaining the activation payload from launch.

   **Decision:** hand over a normalized activation request containing the actual payload. A secondary process receiving COM activation must obtain and transfer that payload before exiting, or the host must ensure the primary receives the callback directly. Include a notification click during primary startup in the drive.

2. **(IN-DELTA; MINOR) Windows login status contradicts its promised meaning, and the mechanism’s stated justification is incorrect.**

   [D2, lines 223–251](llp/1133.025-desktop.rfc.md:223), defines `enabled` as meaning the system will open the app at the next login, then deliberately reports it from the Run value’s presence even when the system’s Startup switch may prevent launching. Excord’s settings would therefore display an effective state the host cannot establish.

   The reason given for abandoning `StartupTask` is also false. Microsoft documents the in-box **`Windows.ApplicationModel.AppInstance.GetActivatedEventArgs`** for packaged desktop apps, including external-location packages, and explicitly demonstrates `ActivationKind.StartupTask`. This does not require Windows App SDK. See [Get activation info for packaged apps](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/get-activation-info-for-packaged-apps); [LLP 1115.004 D15, lines 569–571](llp/1115.004-no-tells-on-windows.rfc.md:569), already selects that package identity.

   **Decision:** reconsider `StartupTask` for installed builds using the documented activation API. Keeping Run remains possible, but correct the rationale and report `unknown` wherever effective enablement cannot be established. Exercise disabling startup through Windows Settings and reopening the app.

**BEYOND these modules — (PRE-EXISTING; MATERIAL): answer-specific ownership remains unresolved.** The restriction to Contract contains this module’s mutable-shortcut use, but data reads still reach `forward_body` without their owning resource ([modules.rs:994–1001](runner/src/runner/modules.rs:994)); argument groups are released only with the whole name ([bound.rs:305–311](runner/src/runner/modules/bound.rs:305)). That remains contrary to the answer-specific lifetime in [geolocation D5, lines 233–238](llp/1133.002-geolocation.rfc.md:233). The architectural repair is to retain argument groups by owning answer across Contract, TypeScript and Rust, so replacing or removing one reader releases its arguments independently.

1. **(IN-DELTA; MATERIAL) The activation record’s prescribed producer cannot obtain the selected notification mechanism’s cold-start payload.**

   **Where:** D6, lines 625–642; D11 item 5, lines 852–855; §17, lines 1270–1272 of `llp/1133.025-desktop.rfc.md`.

   R3 requires the host to obtain the complete record through **`Windows.ApplicationModel.AppInstance.GetActivatedEventArgs`**, called once before taking the mutex. A secondary process then forwards that record and exits. Notifications must consume this record.

   However, **LLP 1133.004 §8, line 562**, selects `AppNotificationManager` and `NotificationInvoked`. Microsoft’s [notification quickstart](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-quickstart#handle-activation-from-an-app-notification) describes a COM launch whose notification arguments arrive subsequently. Its activation example uses **`Microsoft.Windows.AppLifecycle.AppInstance`**, after notification registration—a different API from r3’s in-box choice.

   Microsoft’s implementation confirms the distinction: [`AppInstance::GetActivatedEventArgs`](https://github.com/microsoft/WindowsAppSDK/blob/main/dev/AppLifecycle/AppInstance.cpp) first tries the in-box API, then separately handles the SDK notification marker. [`AppNotificationManager::Deserialize`](https://github.com/microsoft/WindowsAppSDK/blob/main/dev/AppNotifications/AppNotificationManager.cpp) waits for the arguments delivered through COM. The initial in-box call therefore does not establish the complete notification record r3 requires. A secondary process can still exit before receiving its payload.

   **Decision:** retain the common activation record, but allow notification payloads to arrive through the host’s COM receiver. Establish that receiver before a secondary process can exit, and retain the process until the actual payload has been received and transferred successfully; alternatively, guarantee delivery directly to the primary. Keep the in-box API for supported platform activations such as `StartupTask`. Exercise the actual COM path in the proposed startup-click drive.

**BEYOND these modules — (PRE-EXISTING; MATERIAL): answer-specific data-code ownership remains unresolved.** §15, lines 1229–1232, records the limitation accurately. `runner/src/runner/modules.rs:1001` still calls `forward_body(..., None)`; `modules/bound.rs:184–195` records argument ownership only with a reader, and lines 305–311 explicitly retain data-code groups until whole-name release. This remains contrary to geolocation D5, lines 233–238.

The repair is to carry the owning answer and generation through TypeScript and Rust calls, releasing each argument group when that ownership ends. The Contract restriction contains this defect for the consumers proposed here; it does not independently block these four modules.

VERDICT: NOT READY
