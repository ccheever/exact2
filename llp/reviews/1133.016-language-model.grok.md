1. **MATERIAL** — Tool calling cannot be tier 1 on the native targets, and Agents creates every session with a tool anyway. Section D9 (lines 626–651), §9 (lines 983–986), §10 (lines 1072–1080), §13 stage 4 (lines 1201–1206), drives 4 and 9 (lines 1100–1103, 1116–1122).

   Apple’s `Tool` (the page D9 cites) is generic over `Arguments: Generable`. That schema comes from the `@Generable` macro as a static `generationSchema`. `DynamicGenerationSchema` is a different API, and D8 uses it only for `respond(to:schema:)`. `GeneratedContent` is not `Generable`. A session built from a runtime JSON Schema does not type-check against the cited protocol. "Stage 2 proves a dynamic `Tool`; if not, Apple tools are `later`" leaves the tier, and drive 9’s on-device tool, to an experiment the type signature already answers.

   Android is already decided the other way: tools are `later`, `tools` is false, and `createLanguageModel` with a tool list fails `NotSupportedError` (D9, lines 645–651).    D9 already refuses a computed tool list, so the schemas exist at bake. The decision to make: on Apple, emit one `@Generable` struct and one `Tool` per literal tool into the app target (app Swift, which LLP 1133.001 D9 does not forbid, unlike ML Kit’s KSP plugin). On every target, Agents reads `tools` and omits the tool list when it is false; drive 4 and drive 9’s tool are web and Apple only. §0’s "one screenshot on every host" (lines 132–138) holds for a text reply only.

2. **MATERIAL** — An aborted or failed reply stays on screen and leaves the session’s transcript. Section D6 (lines 430–451), D1’s message (lines 192–195), §10 (lines 1058–1068), drive 3 (lines 1098–1099), Android background failure (lines 717–719).

   The transcript is the source of truth, and a later `promptStreaming` is a new user turn on that session. §10 creates the session once from history, which only works if each later input is the new message, not the whole history again (resending history would double the transcript and evict every turn). Drive 3 and the Android background rule keep the partial text in the UI. Nothing says that text, or the turn’s tool calls, is appended as the assistant turn. The web’s abort and Apple’s cancelled `streamResponse` do not commit a partial turn on their own. The next send is answered by a model that has not seen what the person sees.

   D1 cannot store the missing piece: a message is `system` | `user` | `assistant` and text. A tool exchange is not a message, and eviction is defined only as "oldest turns after the system message" (lines 440–444). The decision to make: one turn is the user message, its tool calls and results, and the assistant text, evicted together; `complete`, `aborted`, and `failed` all commit `text` so far before the next prompt is admitted. §10 should say the send’s `input` is only the new user message.

3. **MINOR** — A model’s tool call has two origins. D9 step 2 (line 609) always admits the handler as `tool`. D10 (lines 688–690) uses `CallOrigin::min(prompt’s origin, tool)`. Widening lets the handler do what the wake could not. The handler also cannot ask the person: tool and wake open no UI, so the recipe’s confirmation pattern does not run for a wake’s prompt. The decision to make: the handler’s origin is `min(prompt origin, tool)`, the journal cause is `model` in either case, and a handler on a session a wake may prompt must be safe to run unattended.

6. **MINOR** — An omitted poll interval means two things. D7 (lines 460–466) defaults `interval` to 100 ms and also says that without an interval the source is read again only when `state` changes.
