# Round 1

The rule this draft records is the right one, and it is already LLP 1047’s rule. The draft is not ready to accept. Section 3 is not a complete account of why the Apple linker keeps the code, and D2–D3, as written, would not make that code droppable. Revise and stay Draft.

The audit is of this checkout (`f9d8e1ed1`), which is later than the size probe’s commit `463acda68`. The byte tables were not re-run. Code claims were checked against the current tree.

## 1. Overall assessment

Charlie’s sentence in the summary is a rule the parent already states: a small core, everything else in the binary only when the plan uses it, and the large pieces as separate artifacts. Applying that rule to the Apple host, including Swift, is the right record to make. The probe is the right kind of evidence for the urgency, and several of the decisions match settled parent decisions (the named refusal, development linking the full roster, a reported and non-blocking size row).

What is not ready is the mechanism. The draft treats eight Rust export-group macros, plus a Swift registry and a module split, as sufficient for the linker to drop unused features. In this tree the bulk of the capability exports are emitted inline by `host!`, and live Swift already calls them from boot and from every node. The use-set is named in the wrong crate. The generated Apple entry the draft says does not exist is already where most apps expand `host!`. D1’s “if and only if the plan uses it” drops the parent’s native exception: a binary outlives its plans and may link ahead of them. Accepting D2–D3 as specified would authorize an implementation that either fails to link or leaves the measured bytes in place.

## 2. Strengths

- **The rule is the parent’s rule, stated for both languages.** The summary and D1 (lines 30–34, 115–132) use LLP 1047 D1’s three tiers, including the loaded tier the GPU module and the web arm already occupy. “It’s in ExactKit” is the right thing to refuse as a definition of core.
- **The probe is described well enough to judge.** Section 1 names the app (one `text` node), `host!` with `L=0`, arm64, `-dead_strip`, exports limited to `main`, stripped bytes over a 73 KB UIKit floor, and the two profiles. It discloses that 2026-10-06 was linked and not booted. Section 5 is right that fat LTO, `-Osize`, and `-internalize-at-link` shrink the whole binary and do not make a feature optional.
- **The export groups really are unconditional.** `host!` invokes `raster_exports!`, `textflow_exports!`, `markup_exports!`, `collapse_exports!`, `app_module_exports!`, `material_exports!`, `corner_exports!`, and `pan_velocity_exports!` on every app (`host/apple/src/abi/exports.rs:19-29`). Each of those macros emits `#[no_mangle]` C functions (for example `host/apple/src/raster_exports.rs:8-9`, `host/apple/src/markup.rs:268-272`).
- **The Swift presenter really does make feature code reachable from every plan.** `Presenter.apply` (`PresenterIOS.swift:721`) calls `swipeActions.prepare()`, `groupedLists.prepare()`, `modals.prepare()`, and `navigation.prepare()` on every batch (`:730-734`). `let svg` and `let canvas2d` are stored on the presenter (`:114-117`). The op `switch` (`:797`) has `.canvas2d` and `.svg` cases (`:872-876`). A linker cannot see that a one-text plan never takes those cases.
- **D4, D5, and the non-blocking half of D6 match settled parent answers.** The named boot refusal is LLP 1047 D6. Development linking everything and production linking the use-set is §10’s answer to D7, and Apple already has a plan restart that does not relink (`Bridge.bootPlan`, `Bridge.swift:177-186`). Keeping the row off the five checks matches the 60-second rule and LLP 1047 D9.
- **The questions in §7 are the right ones.** Whether Apple moves ahead of the web target is exactly LLP 1047 §10 answer 5. Whether inspection stays in production is §10 answer 3. Module granularity and a byte target are real choices, and the draft does not pretend they are settled.

## 3. Concerns

### Blocking — D2 attaches the use-set to a function that does not exist and must not

D2 (`1047.001` lines 136–137) says the entry is `exact_plan::uses` mapped to export groups. There is no `exact_plan::uses`. The function is `exact_runner::uses` (`runner/src/uses.rs:203`). The runner documents why it lives there: a use is a kernel prop or style row, and the plan crate declares no kernel vocabulary (`runner/src/uses.rs:1-10`; LLP 1047 as-built, lines 539–542). The roster is the 23-variant `Capability` enum (`runner/src/uses.rs:20-91`).

**Resolve:** name `exact_runner::uses`. Do not move it into `exact_plan`.

### Blocking — §3.1 and D2 describe eight macros; `host!` always emits the capability ABI beside them

The eight groups are real. They are not the capability surface. The same `host!` arm always emits, among others, canvas (`exports.rs:66-76` and `:460-465` and `:566-572`), surfaces (`:206-212`, `:422`), motion and drag (`:314-416`), lists (`:479-486`), the router (`:157-169`), the agent (`:584-592`), auth (`:599`), grouped lists (`:613`), select and radio (`:620-627`), and `exact_svg_islands` (`:645`). `include/exact.h` is one header for that whole ABI (`exact.h:1-33`, version macro at `:33`), which LLP 1031 D2 makes the embedder contract.

D2 says `host!` keeps its core exports and each export group becomes conditional. Applied literally, the inline exports stay on every app. Swift already calls them from code a one-node app runs:

- `boot` always calls `islands`, which always calls `exact_svg_islands` (`Bridge.swift:163-175`).
- `NodeView.init` runs for every node, including a text node (`NodeViewIOS.swift:528`). The trait closure calls `presenter.svg.reappear` (`:547`) and `paintCanvas` (`:549`). `presenter.leaves.embed(self)` is unconditional (`:576`).
- `Bridge` methods call `exact_hold_begin`, `exact_canvas_draw`, `exact_list_index`, `exact_grouped_list`, and `exact_agent` (`Bridge.swift:227`, `:329`, `:478`, `:541`, `:621`).

If those Swift references stay, deleting an export group is an undefined symbol, not a size win. Parent D3’s “the linker drops what the entry does not name” worked on the web because `contract::web_linked` both builds `EXACT_LINKED` and emits `motion_exports!` / `list_exports!` / `surface_exports!` only for the use-set (`contract/cli/src/logic.rs:117-180`), and the host calls through that seam. `HostLinks` is only the drag, inspection, device, and auth seam (`host/web/src/host.rs:133-146`). Section 3’s “the web host has since fixed it (`HostLinks`)” understates the web fix and points D2 at the wrong pattern.

**Resolve:** inventory every `#[no_mangle]` in `host!` as core or as a named capability. The generated entry emits a group only for a used capability, and the Swift call moves with it. Prove one capability end to end, the way Markdown was proved on the web, before splitting the rest.

### Blocking — D3 does not yet make Swift droppable

D3 (lines 144–162) says: capabilities register, the presenter `switch` keeps only core ops, ExactKit splits into one module per capability, the generated entry imports the use-set, and the linker drops the rest. The first two are necessary. They are not sufficient, for reasons the draft does not mention.

**One module is one link unit.** ExactKit is a single SwiftPM target (`host/apple/Package.swift:28-33`). `Package.swift:2-8` defines that target as the session, the view, the presenters, text, canvases, web views, and the agent. `Presenter` (`PresenterIOS.swift:11`) and `NodeView` (`NodeViewIOS.swift:13`, a `UIView`) are the live roots. `applyProps` (`NodeViewIOS.swift:1070`) is one function that handles every tag’s props. Moving a `switch` case into a registry inside this same module leaves the case’s code in the object the presenter already pulls in.

**Reachability is stronger than “a plan might send.”** Grouped lists are not waiting behind a case. `apply` calls `groupedLists.prepare()` on every batch (`PresenterIOS.swift:731`; `GroupedListIOS.swift:80`). Navigation, modals, and swipe actions are the same (`:730-734`). SVG is reachable from every node’s trait registration, as above. Dead-strip never gets a chance to ask whether the plan contains an `svg` tag.

**The link line, not the import, decides what is linked.** Parent D3 can list every capability crate as a Cargo dependency because an unreferenced rlib member is not a root. A Swift module’s protocol conformances and `@objc` classes are discovered from Mach-O sections (`__swift5_proto`, `__objc_classlist`), which have no relocation from the caller. This checkout does not pass `-force_load` itself. SwiftPM’s Darwin link of a static Swift module has long force-loaded those sections so conformances and categories survive. D3 needs an explicit answer: an unused capability is absent from the link line. An `import` in a generated Swift file does not do that. The app target’s package manifest, or the embedder’s link phase, does.

**Generic specialization and `@objc`.** A generic `register<T: Capability>` specialized inside ExactKit emits the specialization into the core module and pins `T`. The specialization has to be emitted in the registering entry, beside the types that entry names. `NodeView`’s `@objc` methods (`NodeViewIOS.swift:151`, `:216`, `:225`, and `#selector(fieldChanged)` at `:572`) stay in the class’s method list for as long as the class is the one view. Feature views have to be other classes, in other objects, that the core does not name.

**LLP 1031’s embedder ABI.** An embedder links one archive plus ExactKit and nothing else (`llp/1031-brownfield-embedding.rfc.md` lines 410–414 and 425–434). Optional weight that already drops is a separate dylib: the GPU module and the web arm (1031 D7). Sound and Now Playing are already separate targets, not ExactKit dependencies (`Package.swift:50-55`). D3’s last sentence — an embedder pays for the core plus what that surface uses — needs a concrete link line. Splitting ExactKit without changing what “link ExactKit” means leaves the brownfield app on today’s product, which depends on all of it. `exact.h` also cannot stay a single always-complete symbol set if some archives omit symbols and ExactKit still references them. Two archives already cannot export the same names (1031, around line 418); per-app export sets make that ABI part of the compatibility id, which is parent D8’s job.

**Resolve:** one capability, two link lines measured from the same probe. The core binary’s link map has no symbol from that capability. The app that uses it has the symbols, and boot of a plan that uses it unlinked is the named refusal. State that the generated artifact list is the tree shaker. Keep tvOS on the shared presenter (`PresenterIOS.swift:6`, `#if os(iOS) || os(tvOS)`); DEFERRED says each Apple platform’s code goes into its own binary.

### Material — D1 and D4 keep only half of parent D8

Parent D8 (`llp/1047-pay-for-what-you-use.rfc.md:315-331`): on native the binary outlives its plans, so the linked set is a compatibility input; a bundle whose plan exceeds the binary is a binary change; the manifest may name capabilities to link before any plan uses them; a native app may reasonably link more than it uses. Section 10 answer 5 put that work after the web target (line 519).

D1 (lines 122–124) and the summary (line 32) say a feature is in the binary if and only if the plan uses it. D4 (lines 163–169) cites D8 only as the refusal check. There is no link-ahead field and no statement that production may link a superset. Shipping D2 as written makes the next delivered plan that adds a capability a forced binary update. That is the case D8 exists for.

D5 itself does not conflict with D7. It is the settled answer (development links everything, smoke runs the production artifact). The gap is the web’s second full-link build for fixture smokes that exercise capabilities the app’s production artifact does not contain (LLP 1047 as-built, lines 577–579). An Apple smoke of arbitrary plans needs the same split.

**Resolve:** restate D8 in this RFC, including link-ahead, or explicitly propose to drop link-ahead. Keep D4’s refusal. Point §6 at §7 question 1 so the work stays conditional on Charlie pulling native ahead of the web target.

### Material — §3’s “every export is a root” contradicts the probe’s own export list

Section 1 limits executable exports to `main` and passes `-dead_strip`. Under ld64, a global that is not exported and not referenced is not a live root. Section 3.1 says each `#[no_mangle]` is a root anyway. Both descriptions cannot be the reason the 9.83 MB binary looks like that.

The same harness, recorded in `QUEUE.md` on 2026-09-30, found that `-Xfrontend -internalize-at-link` collapsed an export penalty of 1.2 MB to 5 KB. That flag is in this RFC’s size-lever row and absent from the production row (Swift `-O`). Section 3 never mentions it. The production number is therefore partly “Swift emitted symbols the linker was not allowed to internalize,” which is a compiler-flag fact, and partly “live Swift references,” which is the code fact above. Cause 1, as written, explains neither cleanly.

**Resolve:** split the account into (a) symbols with a relocation from `exact_boot`, `Presenter.apply`, or `NodeView.init`, (b) symbols kept only because they are exported, and (c) what `-internalize-at-link` already removes. Attribute bytes from the link map under the production flags, with exports limited to `main`.

### Material — “none of this is reachable from a one-text-node plan” is stronger than the maps can show

Section 2 (line 87) puts the whole week of growth in that sentence: Swift +1.55 MB, including `NodeViewIOS` +203 KB and `PresenterIOS` +117 KB, and Rust +1.0 MB, of which the kernel is +0.27 MB. A one-text plan still decodes and lays out through the kernel. Growth in the decoder is reachable core. `NodeView` and `Presenter` are the core objects; growth inside those files is reachable even when the new code is feature code, which is the bug, and it is reachable because those types are live, not because the plan might send an op.

The 2026-10-06 column was not booted (line 47), and the plan was rebaked by a newer compiler. Some of the delta can be codegen or plan bytes. The link maps are outside this checkout, so the per-file numbers cannot be confirmed here. They can still be used as the author’s measurements. The unreachability conclusion cannot.

**Resolve:** mark kernel, runner, and `exact_apple` growth as unclassified until a map shows no relocation from the boot path. Boot the 9.83 MB binary, or stop pairing it with the booted 7.23 MB number as one series.

### Material — the framework sentence contradicts the table

Lines 65–67: on 30 September production exact2 was smaller than all three; today it is between React Native and Lynx. The table (lines 61–63) gives RN ≈8.9 MB plus an unmeasured JS bundle, Lynx 9.31 MB, Flutter ≈13.1 MB. The 6 October production figure is 9.83 MB (line 51), which is above both 8.9 and 9.31. The 30 September comparison also ranks 7.23 MB against RN’s native shell only. The dead-strip caveat in lines 65–66 is fair. The ranking sentence is not.

**Resolve:** rewrite the ranking from the table. Keep the bundle caveat on both days.

### Material — wasmi is real, and §3.4 names the wrong mechanism

`configured!` does not link wasmi by itself. `rust_entry` emits it only for modes `native`, `tiered`, `wasm`, and `browser` (`contract/cli/src/logic.rs:30-34`). Mode `off` is a type alias and a constructor (`logic.rs:31`), and `Swappable::off` passes no loader (`logic/src/lib.rs:100-103`). `Swappable::wasm` on a non-wasm target does take `wasm::load` (`logic/src/lib.rs:105-108`), and `mod wasm` is compiled for every non-wasm target, including iOS (`logic/src/lib.rs:33-34`). The code’s own comment says an unused executor can be dead-stripped (`logic/src/lib.rs:54`).

What actually links wasmi on iOS is the default policy. `Manifest::rust_mode` starts at `"auto"` (`contract/cli/src/manifest.rs:41`) and maps `("auto", "ios")` to `"wasm"` (`manifest.rs:69`), whether or not a module exists. The web path already returns `"off"` when no `rust.module` is named (`logic.rs:43-50`). Apple `build.rs` files pass `compat.inputs["rustMode"]` straight through and then unconditionally emit `host!` (for example `apps/caltrain/apple/build.rs:43-49`).

Section 2’s Rust +1.0 MB does not contain a wasmi line. The ≈1.0 MB figure matches the 2026-09-30 `QUEUE.md` note about a real app’s `apple-dev` archive (Type Tour), which is also where “wasmi as a separate artifact when the manifest names no swappable module” is already queued. Putting wasmi in §3 as a reason the one-text probe keeps its bytes mixes that archive with this probe. The one-text probe in that same `QUEUE.md` note used an empty data source, and its 4.09 MB breakdown does not list wasmi.

**Resolve:** describe the iOS default as `auto` → `wasm`, and the fix as the web’s rule: `off` unless a module is named. Keep it queued. Do not present it as the cause of the probe’s week.

### Material — “the Apple entry is hand-written” is true of some apps and false of the ones that matter for D2

Section 3.2 (lines 98–100) says each `apple/src/lib.rs` calls `host!` and there is nowhere to attach LLP 1047 D3. Caltrain’s `lib.rs` only includes the generated entry (`apps/caltrain/apple/src/lib.rs:14`). `build.rs` writes that entry, and the written entry always calls `host!` (`apps/caltrain/apple/build.rs:40-50`). The same shape is in spark, reflow, typetour, svg-gallery, exact-live, markdown, video-player, and others. A smaller set really does call `host!` in `lib.rs` (`apps/messages/apple/src/lib.rs:13`, and fieldnotes, weatherlight, canvas-gallery, expose, recorder, duo-lab, color-gallery, update-lab, auth-fixture, messages-legacy, completion-storm).

The attachment point exists. It currently expands the unconditional macro. D2 is “teach that generator the use-set,” plus folding the hand-written callers into it. Deleting every `lib.rs` (D2, lines 141–142) is the wrong edit for the generated majority. No migration path is still right.

### Material — D6’s apparatus claim is ahead of the ask, and the row is in the wrong place in the order

D6 (lines 177–184) adds an iOS embed build to `metrics.mjs` and says the RFC is the human asking for it. The quoted request (lines 12–14) is to record the linking rule. Parent §10 answer 7 authorized the web byte row under the shrink-the-runtime goal, not an iOS archive. `rules/RULES.md` §Agents: an agent adds a script or a design-doc obligation only with an explicit human yes. “Never blocks” is consistent with the five checks and with “nothing slower than 60 seconds blocks.” An iOS link is minutes, so the row belongs on the async lane, as D9’s web row does.

Question 2’s example target (production back under 7 MB) would become a P0 byte budget if it landed in `rules/RULES.md`. Parent §10 replaced D9’s byte budget with an outcome, not a byte count. A report-only row matches that. A new `RULES.md` row also spends the 700-word budget.

Section 6 numbers the metrics row fourth and then says it should land before step 2 (lines 199–203). The parent’s order starts with measure. This week’s growth is the argument for measuring first. The maps live in `~/bench/embedsize`, outside the repo, so until the row exists the claim is not checkable here.

**Resolve:** leave D6 as a question until Charlie answers question 2. If he says yes, the row is report-only, on the async lane, and it lands before any link change. Do not add a `RULES.md` budget unless he asks for a number. The sentence that the draft itself is the approval should go.

### Material — the order of work does not follow from §2

1. **wasmi first** recovers about 1 MB on a real app that inherited `auto` → `wasm`. It does not recover the probe’s week, which §2 assigns to Swift (+1.55 MB) and to kernel, export groups, runner, and `exact_apple`.
2. **All Rust groups, then Swift** (steps 2–3) cannot drop a symbol `Bridge` or `NodeView` still references. The link fails, or the bytes stay. The web order was one capability across the entry, the host call, and the refusal.
3. **Linux and Windows last** matches the parent. D1 stating their tiers now is fine. Implementing them now waits on question 1.
4. The decisions are written as adopted while question 1 asks whether to do the work. `rules/RULES.md` asks a spec to have an implementer and a date. Charlie asked for a record, which this RFC is. The build plan does not yet have an owner. That is a reason to keep it Draft, not a reason to delete it.

## 4. Suggestions

- Keep the record short: the parent’s three tiers apply to Apple, Linux, and Windows, in Rust and in Swift, and ExactKit membership is not what makes something core. Put the mechanism in a revision that an implementer can follow.
- Add a table of current `#[no_mangle]` symbols: core, which capability, which Swift file calls them. D2 is that table becoming conditional.
- Change the existing `entry.rs` generator. Point it at `exact_runner::uses` and at the same `off`-unless-a-module-is-named rule `web_rust_mode` already implements.
- Take one Swift capability that §2 says is large and that a one-text plan does not need. Move that type to its own product, omit the product from the one-text link line, and show the before and after link maps under the production flags with exports limited to `main`. Grouped lists, navigation bars, or the SVG host are the candidates the draft already names. The slice includes the `NodeView` and `Presenter.apply` references, not only a new registry.
- Say, in D3, that protocol witness tables and `@objc` classes are roots, that specializations are emitted next to the registration, and that the embedder’s link line is generated from the use-set plus any D8 link-ahead list. LLP 1031’s “link ExactKit” becomes “link the core product and the capability products the archive’s compatibility id names.”
- Rewrite the React Native / Lynx sentence from the numbers in the table.
- Boot whatever binary the next size claim cites. The 6 October column’s “not booted” is the gap in the series.

## 5. Open questions for the author

1. Question 1 stands. Until it is answered, D2–D3 are a proposal, not a decision to build ahead of LLP 1047 §10 answer 5.
2. For D8: does Apple keep the manifest link-ahead list, or is every new capability a binary change with no headroom? D1 cannot say “if and only if” while D8 still allows a superset.
3. The probe limits exports to `main`. Did that list apply to the Rust static library and to ExactKit, or only to the final executable’s export trie? The answer decides whether §3.1 is describing this probe.
4. Which symbols in the +0.27 MB kernel, +0.13 MB runner, and +0.08 MB `exact_apple` have no relocation from `exact_boot` or `Presenter.apply`? Those are the ones D2 can remove. The rest is core diet, which this RFC correctly does not claim to solve.
5. Was wasmi present in the one-text probe at all, or only in Type Tour’s `apple-dev` archive? Section 3.4 currently reads as the former.
6. Question 4, narrowed: parent §10 answer 3 kept inspection in the shipped web artifact so the smoked binary is the shipped one. `Agent` is created on first use (`Agent.swift:734-740`), and the probe still attributed +86 KB to it. Is the proposal to reverse that answer for Apple, or only to stop `NodeView` and settle paths from keeping the agent live in a binary that never calls it?
7. Question 3, narrowed: the linker drops a Swift product that is not on the link line, at whatever granularity that product has. Is the granularity question actually about build time of many small targets, or about how fine the use-set should be?
