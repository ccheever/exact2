Verdict: READY WITH CHANGES

1. **Keep the smaller first read as the next experiment, but soften the causal conclusion.** Early documentation is a credible, substantial lever; I reproduced the headline fit. It does not establish that removing those bytes would preserve the remaining workflow or achieve the quoted token totals. “Step counts were never the lever” also overreaches: steps alone explain R² 0.52 for GPT and 0.80 for Muse, versus 0.60 and 0.92 with replay included. Describe the savings as a hypothesis conditional on preserving quality and avoiding extra repair requests.

2. **Make the accounting invariant to where information lives.** D1 moves documentation into automatically injected instructions; D2 moves it into app files. Neither makes its replay cost disappear. The current scripts also disagree materially: for round-14 Muse builds, `replay.py` reports 2.46 documentation MB-steps per build, while `replayfit.py` reports 4.15 because it additionally recognizes file reads. That latter figure includes 0.38 from harness skills. Count injected instructions, framework examples and scaffold reads consistently, separate harness material, and avoid attributing entire mixed commands to documentation. Otherwise D4’s “half the docs” threshold can reward reclassification.

3. **Make independently graded quality and wall time promotion gates on the controlled builds.** Builder-written tests and `verify` passing as often cannot establish preserved quality when the intervention changes the examples and tests builders imitate. LLP 1116.011 already documents builders weakening coverage and choosing inferior compositions. Grade both A and B before adopting the change, including navigation, refusal handling, persistence and visual quality. A later graded round is useful confirmation, but cannot isolate this change’s quality effect.

4. **Judge the intervention directly against contemporaneous Exact2, separately by builder and platform.** Use paired B/A token changes with uncertainty; retain historical React and SwiftUI medians as the program’s absolute target. One standard error is weak evidence for promotion, especially across repeated experiments. Include both builders and iPhone cases rather than inheriting the previous web-only comparison. Start with D1 against the current unchanged baseline before bundling pattern and lookup rewrites, so a regression identifies something actionable.

5. **Treat the pattern caps as experimental budgets, subordinate to complete behavior.** Cutting `rest` from 18.7 KB to 8 KB is substantial redesign. Its current tests teach retained input after refusal, recovery after a lost server, polling and persistence; removing these can save context while producing worse apps. Keep patterns task-specific, remove duplication first, and explicitly preserve their relevant behavior and coverage. Their bytes are useful only when they replace work the builder would otherwise do—not automatically because they become “its own files.”

6. **Optimize lookups for a resolved question, not a fixed answer size.** A 1 KB answer that triggers a recipe read, another lookup and a failed build can cost more than the current complete answer. Keep the common case concise, but preserve essential constraints and an obvious complete answer for the requested topic. Measure cumulative tokens and requests through the successful fix. Helpful compiler diagnostics are particularly promising here because they can eliminate an entire lookup-and-repair cycle.
