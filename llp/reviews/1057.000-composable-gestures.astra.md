# Review: LLP 1057.000, composable gestures, 2026-09-26 (astra)

- **Family:** OpenAI, GPT-6 Astra at maximum reasoning effort, Codex CLI `codex exec -m gpt-6-astra -c model_reasoning_effort=max -s read-only`, in a detached checkout at `479bd946`.
- **Brief:** `gesture-brief.md` (the claude artifact's header).
- **Redacted:** no. Verbatim below.

---

**Assessment.** The RFC correctly identifies duplicated arbitration and a useful presentation model to preserve. C could retain native recognition for a bounded set of compositions, but it does not establish identical winners or phase ordering across hosts. A’s immediate work is justified; committing to the algebra afterward is premature. This is a static review of `479bd946`, checked against code and primary platform documentation; no files were changed or device tests run.

**Concerns**

1. **BLOCKER — Native thresholds can change the outcome, not merely its timing.** The RFC permits host-specific thresholds while promising identical winners ([RFC:210](/private/tmp/grok-wt2/llp/1057.000-composable-gestures.rfc.md:210)). A contact lasting between two hosts’ long-press thresholds can produce a long press on one and a tap on another. Similarly, `shouldBegin(B) = A not active` lets B win if UIKit examines it first; an order-independent relationship table does not establish “priority on ties.” B is deterministic only given identical normalized inputs, parameters and cancellations. C can promise shared composition semantics **given equivalent primitive recognitions**, not equivalent recognition of every physical interaction.

2. **BLOCKER — The proposed UIKit lowering is not a complete algebra.** Failure-dependency queries occur [once per recognition attempt](https://developer.apple.com/documentation/uikit/uigesturerecognizerdelegate/gesturerecognizer%28_%3Ashouldrequirefailureof%3A%29); they are not continuously reevaluated gates. Returning false from [`gestureRecognizerShouldBegin`](https://developer.apple.com/documentation/uikit/uigesturerecognizerdelegate/gesturerecognizershouldbegin%28_%3A%29) fails the recognizer—it does not suspend it until its predecessor succeeds. The RFC correctly notices the resulting sequencing hazard, but then overstates its resolution:
   - UIKit [long press is continuous](https://developer.apple.com/documentation/uikit/handling-long-press-gestures), contrary to §6’s discrete-leader classification.
   - Reusing one long-press recognizer works for the existing reorder idiom ([ReorderIOS.swift:35](/private/tmp/grok-wt2/host/apple/Sources/ExactKit/IOS/ReorderIOS.swift:35)). Turning drag’s **minimum** distance into long press’s **maximum** allowable movement changes semantics.
   - Stock `UIPanGestureRecognizer` exposes no public configurable recognition distance. Explicit `minDistance` cannot universally bind while retaining stock recognition.
   - `tap → drag` needs remembered success and timing across recognizer resets; current native states alone are insufficient.
   
   Strict failure priority over continuous recognizers is representable, but may stall the follower throughout the contact. That is a usability limitation, not justification for silently redefining `exclusively`.

3. **MATERIAL — The web ownership model breaks the reorder example’s native behavior.** Deriving `pan-x` for `sequenced(longPress(), drag(axis: y))` reserves vertical movement before the hold succeeds. Leaving vertical scrolling enabled instead permits browser takeover and `pointercancel`; changing `touch-action` afterward cannot reclaim the sequence. These are [Pointer Events constraints](https://www.w3.org/TR/pointerevents3/#determining-supported-direct-manipulation-behavior). UIKit’s existing reorder deliberately lets scrolling beat the long press ([ReorderIOS.swift:1](/private/tmp/grok-wt2/host/apple/Sources/ExactKit/IOS/ReorderIOS.swift:1)). Choose and document the compromise—such as a dedicated handle. Also, `drag(axis: x) → pan-y` unnecessarily disables browser pinch zoom; preserve `pinch-zoom` unless claimed. That value authorizes **browser** zoom, not application pinch recognition.

4. **MATERIAL — `follows` preserves the right boundary but omits essential semantics.** The existing machinery captures current presentation, atomically holds Translate/Scale, validates complete terminal input, and protects replacement tokens ([hold.rs:39](/private/tmp/grok-wt2/motion/src/engine/hold.rs:39), [hold.rs:103](/private/tmp/grok-wt2/motion/src/engine/hold.rs:103)). The proposed independent leaves need equivalent guarantees. Specify coordinate space, captured origin, additive versus multiplicative updates, allowable row types, conflicting writers, cancellation, and action ordering. Photo pinch also needs focal-point translation and geometry/bounds; `magnify follows scale` alone scales around the existing transform origin. Terminal displacement alone does not identify the caught presentation during spring takeover. Today’s release supplies absolute presentation values ([event.rs:201](/private/tmp/grok-wt2/runner/src/runner/event.rs:201)). Reorder, height clamping and swipe resistance therefore remain meaningful adapters, not merely graph sugar.

5. **BLOCKER — The trade understates what is being admitted.** C explicitly includes B’s arena on web/Linux, derived claims, and potentially B on Apple ([RFC:590](/private/tmp/grok-wt2/llp/1057.000-composable-gestures.rfc.md:590)). That contradicts both “compositions only” and §11’s continued refusal of a Rust arena on Apple. [NOT-DOING:258](/private/tmp/grok-wt2/rules/NOT-DOING.md:258) refuses all these mechanisms; [the consumer expansion:64](/private/tmp/grok-wt2/rules/NOT-DOING.md:64) expressly retains the generic-arena refusal. Consolidation can be a legitimate trade, but §11 has not demonstrated one: eligibility, geometry and native coexistence policies still need implementations. Name the maintenance obligation actually retired, and obtain Charlie’s explicit acceptance of the full scope. The photo and reorder examples already fit A; the generic fling is not yet a named product requirement.

6. **MATERIAL — Three examples and primitive injection cannot establish the promised conformance.** The proposed script already supplies recognition decisions ([RFC:449](/private/tmp/grok-wt2/llp/1057.000-composable-gestures.rfc.md:449)). Even if subclass state changes exercise UIKit relationships, they bypass physical recognition thresholds, touch delivery and cancellation. Current iOS agent phases honestly report unsupported ([AgentIOS.swift:416](/private/tmp/grok-wt2/host/apple/Sources/ExactKit/IOS/AgentIOS.swift:416)). Preserve that distinction. Add adversarial callback orders, nested compositions, unsuccessful attempts, finger addition/removal, failed recognizers awaiting reset, scroll/editor/system competition, and destruction/replacement during callbacks. Compare payload **values and resulting presentation**, not just payload shapes. Dispatch currently runs each action separately ([event.rs:775](/private/tmp/grok-wt2/runner/src/runner/event.rs:775)); simultaneous terminal callbacks can therefore produce order-dependent application state.

7. **MATERIAL — Accessibility belongs in the first usable slice.** A label cannot determine which item to move, dismissal direction, zoom limits, or a meaningful terminal displacement. The reorder example has no leaf `on end` from which the proposed derivation could produce its action. Keep semantic activation, keyboard operation and authored non-drag alternatives; bind explicit actions such as Dismiss, Move Up and Zoom In. Do not fabricate near-infinite motion payloads. Existing release validation requires finite values ([event.rs:294](/private/tmp/grok-wt2/runner/src/runner/event.rs:294)), and current NodeView accessibility only activates presses ([NodeViewIOS.swift:1441](/private/tmp/grok-wt2/host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift:1441)).

8. **MATERIAL — Cost ordering is plausible; the quantitative and latency claims are unproven.** C has the greatest implementation and verification burden. Lines of Rust do not establish compressed size, and “after-paint glue” does not remove statically linked wasm from transfer/compilation costs. LLP 1047 also makes input readiness wait for required pieces ([1047:799](/private/tmp/grok-wt2/llp/1047-pay-for-what-you-use.rfc.md:799)). Use-set derivation and generated linking are real ([uses.rs:138](/private/tmp/grok-wt2/runner/src/uses.rs:138), [logic.rs:63](/private/tmp/grok-wt2/contract/cli/src/logic.rs:63)), but sugar must select Gestures too, and `follows` must select its presentation dependencies. Measure unused-app overhead, complete marginal wasm/JS bytes, cold input readiness and per-sample cost. C still crosses the motion bridge during following ([TransformDragHold.swift:96](/private/tmp/grok-wt2/host/apple/Sources/ExactKit/TransformDragHold.swift:96)); exclusivity adds recognition delay under either engine.

10. **MINOR — The grammar and examples disagree.** Clauses attach only to primitives, yet `label` follows `sequenced(...)`; `of` requires a quoted ID, yet the photo uses an expression; gesture-name references are absent ([RFC:182](/private/tmp/grok-wt2/llp/1057.000-composable-gestures.rfc.md:182)). “Unlimited” also obscures the sequencing restrictions. The card example removes its item before demonstrating the exit spring and chooses direction from `dx` even when an opposite-sign velocity triggers dismissal ([RFC:239](/private/tmp/grok-wt2/llp/1057.000-composable-gestures.rfc.md:239)).

**Suggestions**

- Ship A0/A1 against the admitted photo consumer: consistent precedence, corrected activation ordering, complete relevant `touch-action` vocabulary, pinch with coordinated holds, and accessible zoom controls. Do not introduce a generic plan graph merely to avoid hypothetical throwaway work.
- Before authoring syntax, name a consumer that A cannot adequately express and define a small, precise supported algebra. Keep strict priority distinct from racing. Specify group success/failure, sequence milestones, contact lifetime and terminal dispatch order.
- Gate C on both UIKit **and browser** feasibility. Use graph tests for semantics and actual platform input for recognition/coexistence. Cover 1→2→1 contacts, slow threshold crossings, nested scrolling, regrabbing springs and callback-driven teardown.
- Keep new inputs as forms of `tap`; expose observations through existing `tree`, `state`, `layout` and `logs`. Run fast cases in existing tests and device sweeps asynchronously—no ninth operation or sixth blocking check.

I remain unsure whether the proposed stock-recognizer subclass injection exercises the same arbitration path without real touches, and of supported iOS versions’ exact finger-count cancellation/reset behavior and Touch Accommodations effects on raw input. Those require experiments. SwiftUI’s private implementation remains unknown.

**Answers to the open questions**

1. **Trade:** Insufficient as written. Accept a concrete consolidation only if Charlie explicitly counts it and the old implementations actually disappear; otherwise defer a named doing-list item.
2. **Double tap:** Preserve ordinary browser activation ordering everywhere. Explicit exclusive single/double tap may deliberately defer the single tap; it must not redefine `press`/`dblclick`.
3. **Continuous exclusivity:** No to type-dependent race semantics. Keep strict priority, or introduce a separately named race when a consumer needs it.
4. **Trackpad pan:** Keep ordinary two-finger input as scrolling. A photo binding may explicitly consume it for content panning, with clear boundary and momentum behavior.
5. **Accessibility payloads:** Require separate semantic actions, with authored arguments where necessary.
6. **Scope:** Photo pinch is admitted; reorder already exists. Rotation, arbitrary long-press drag and general flings need named product consumers before the general algebra.

**Verdict: REJECT the recommendation as written.**

Exact2 should pursue **A first**, including photo pinch and shared verification of its fixed rules. If a named consumer subsequently needs composition, pursue **a restricted C**, after proving its UIKit and browser realizations and explicitly paying the arena/composition trade. Keep B as the implementation for hosts without appropriate recognizers; do not silently substitute it on Apple when C fails. Preserve native recognition where useful, and promise consistent declared semantics with documented platform limits—not universal physical-outcome identity.
