## Concerns

1. P1: concurrent draft isolation is still false at the root seam.
   New task ownership says switching projects does not overwrite another draft slot.
   That holds for the current sequential tests. Root `editNewDraft` now sends the
   ordinary `draft` command, which fixes the exclusive-task busy rejection, but the
   shared command awaits load/devicePresentation before composerOps reads the current
   draftKey. A project switch can finish during that await.

   Executed witness with a fresh T3Client and synthetic native replies: write
   "original A" in project A; pause the next draft at devicePresentation; run
   new-thread for project B; release the draft. The actual result was:

   ```json
   {"selected":"b","drafts":{"env:new:a":"original A","env:new:b":"latest A"}}
   ```

   This used the real shared command path and no global singleton. Fix the mobile
   draft seam by capturing generation and draftKey before the first await and
   refusing or correctly queuing work after ownership changes. Keep the shared
   client authoritative. Add overlapping draft/project-switch coverage, and until
   then qualify the document's draft-isolation claim. This is a specific M5 defect,
   not a demand to finish later milestones before review.

2. P2: Settings ownership claims an unwired preference mapping.
   The paragraph says root maps the unified mobile Enter/follow-up values into
   shared composer settings. Current settings-preferences.ts defines and persists
   composerEnterBehavior/followUpBehavior, but app.ts/app.contract do not pass them
   into the composer/shared command settings. ThreadComposer has no Enter behavior
   input or keyboard-send handler. thread.ts still reads shared followUpBehavior.
   Rewrite as planned integration and name the current limitation. Persistence of
   the preference UI is not evidence that Send/Steer/Queue or Enter behavior uses it.

3. P2: narrowed branch preparation dependencies omit connection readiness/owner.
   The root correctly removed the broad data.revision dependency and stopped draft
   changes from explicitly refreshing branch preparation. Its current arguments
   are branchQuery, route-active and newTaskContextRevision. mobileNewTaskPrepare
   returns loaded:false when the client is not ready. If the route opens during
   reconnection, the later ready transition does not change those arguments, so
   preparation can remain unrequested until another context action. Add narrow
   ready and environment/draft-generation dependencies. Verify that readiness
   triggers preparation while ordinary typing still does not fetch branches.

4. P2: live Agents clock is only partly corrected at the root.
   The separate one-second timer avoids refetching archives on each second, which
   addresses the previous coupling. It is gated by agents.turnActive. The pinned
   ThreadAgentsSheet gates elapsed ticking by liveCount>0, including a live agent
   whose parent run has already settled. Use the live-agent condition. This is a
   root integration observation; I did not independently review my own Agents fold.
