## MATERIAL

### 1. D2 — The move is not an algorithm the cited `settle` can run

**Problem.** D2 says: when `settle` finds an answer `done` or `failed` with `call.storage > 0`, add that count to `background.storage`, mark the answer moved, and reply. Two facts make that procedure unrealizable as written.

The check that implements kanban F22 returns before an answer is ever observed in that state:

```770:770:js/src/prelude.js
    if (call.storage > 0 && !call.lost) return JSON.stringify({ tag:1, call:call.id, ticket:0 });
```

`finished` is computed at line 764 and only consulted at line 771, after that return. A branch added “when settle finds the answer finished and storage is outstanding” is dead. D1’s replacement of F22 never says to delete or gate this return.

The count itself has no owner after the add. `unstore` decrements the call the completion captured, not a module-level owner:

```419:422:js/src/prelude.js
  function unstore(call) {
    call.storage--;
    if (!call.storage) storing.delete(call);
  }
```

D2 adds `call.storage` onto `background.storage` and does not say to zero the call, nor which counter a later completion decrements. Leaving both counts live leaks the background ticket (`background()` in D6 stays out while `background.storage > 0`). Decrementing the captured call leaves `background.storage` stuck, so `clock settle` waits until its 20 s bound.

**Evidence.** `js/src/prelude.js:419–422`, `:764–777`. D6’s loop condition is “while `background.storage > 0`”. `host/linux/src/agent.rs:693–697` and `:831–836` (`wait_for_replies` until `pending()` is false, one 20 s deadline).

**Fix.** Specify the transfer in `settle`, ahead of today’s line 770: if the answer’s promise is already `done` or `failed`, set `background.storage += call.storage`, set `call.storage = 0`, mark the call moved, and reply. While the promise is still `pending`, keep today’s ticket-0 wait — that is the awaited case. The completion handler must `unstore` the owner that holds the count (`background` when the captured call is moved or replied). State that `call.storage` means “queued or in flight,” since D3 increments it at issue time, not at host start.

### 2. D1, D4, D12, Q1 — “Issued” is not “chained”, so the two ordering guarantees do not both hold

**Problem.** The summary, D2, and D12’s drums adoption all tell the app to write:

```ts
saving = saving.then(() => storage.fs.atomicWriteFile(PATH, JSON.stringify(song)));
return song;
```

A `.then` on a promise that has not settled does not call `atomicWriteFile` during the answer, nor during the microtask checkpoint Q7 correctly keeps (`js/src/shim.cc:352–356`, `drainMicrotasks` of what is already queued). The write is issued only when the previous promise resolves. D4.2’s “later read sees the earlier write” is defined on issue order. For this pattern the second edit’s write is not issued yet when a later read runs, so the read is ahead of it in D3’s queue.

That later read is also how fix/data6 refreshes a mutation that answered `Now`. `landed_now` forces every declared refresh in the sending commit (`fix/data6` `runner/src/runner/commit.rs:517`, `:593–603`), and `settle` then calls the resource (`:606`). A resource that reads the file issues `readFile` while `write` of this edit is still only a reaction. The read commits what it saw. D4.4 says a background completion re-asks nothing, so the stale answer stands.

D4.1 and D4.2 also fail together once the read is in the queue. The read’s answer parks with ticket 0, and `turn_open` is exactly that:

```11:13:js/src/turns.rs
    pub(crate) fn turn_open(&self) -> bool {
        self.parked.iter().any(|(_, p)| p.ticket == 0)
    }
```

D4.5, which Q1 tells stage 1 to keep, defers every later answer while that turn is open (`js/src/lib.rs:831–853`). Those answers wait behind the background write. Q1’s reason — R11’s `persist` mutation — is this schedule.

D7 says the JS target matches every observable D4 names. It has no answer turn. `host/web-js/ts-data.js:207–218` runs `source.answer` and returns its promise; a second answer runs while the first is awaiting storage. D4.5 is a Hermes rule. Keeping it in stage 1 means the two hosts disagree on who may touch module state during a storage wait, which is the hazard the comment at `lib.rs:831–838` exists for.

**Evidence.** Simulation of the summary pattern (Bun): edit 1 issues `write:song1`; edit 2’s checkpoint issues nothing; the following `read` is issued next; after the queue drains, `read` sees `song1` while the answers were `song1` and `song2` and the disk ends as `song2`. Same run: an `async` function that `await`s the write is still pending while the write is pending; one that calls the write and returns is already settled. So “promise settled while `storage > 0`” does distinguish `await` for a call that happened. It does not see a call that has not happened.

fix/data6 `e3add44c7` message and `commit.rs:586–603`. `runner/src/runner/settlement.rs:612–623` still drops a `Later` that is only a reread; the force path is what keeps the read. Drums R11 (`~/projects/x2apps/drums/DIARY.md:207–214`) is the deferral this reintroduces for any edit that arrives during that read.

**Fix.** Define “started” as `storageCall` having run in the answer body or in that checkpoint. Change the summary and D12 to call `atomicWriteFile` directly; D3’s queue is the serializer, and the `.then` chain is what skips the queue. State D4.2 only for operations that have entered the queue. Narrow D4.1 to “the background ticket is not a `turn_open`,” and say in D4 that a read parked behind a background write does defer later answers for as long as Q1 keeps D4.5. Either drop D4.5 in the same stage-1 commit that proves issuer-only delivery (§4), or stop claiming the JS target matches D4 until that lands. Add a test the simulation fails today: two unawaited edits, then a read, with no `clock settle` between them, on Hermes and on the JS target.

### 3. D7 — Finishing the answer retires the owner that already holds the completion

**Problem.** On the wasm realm a storage call captures its owner at issue time, which is the answer’s owner:

```53:56:host/web/storage.js

    const active = () => { if (disposed || retired.has(owner)) throw unavailable(); };
    return new win.Promise((resolve, reject) => {
      const ready = completion(owner);
```

`finish` retires that owner whenever the answer is not tag 1:

```167:167:host/web/module-glue.js

```

A retired owner’s completion is dropped:

```30:35:host/web/storage.js

    if (disposed || retired.has(owner)) { cleanup(); return; }
```

D7 ends the turn when the value is ready and moves “leftover storage” to a background owner. The completion is already queued on the answer owner. Moving a count, then finishing, takes the existing `retire` path and the write is gone. That is R10 on the wasm target. The same queue carries `hostWork` (digest, `store.keepKey`); an unawaited digest is `call.storage` too (`prelude.js:159–164`, `storage.js:39–44`) and is dropped the same way.

Say that `hostWork` is in the same transfer or is excluded from `call.storage` once the answer has replied.

### 4. D2 — `currentCall = background` makes `fetch` the next answer’s

**Problem.** D2 runs the completion drain with `currentCall` set to the background pseudo-call, and says a chained `storage` call is then background work. `fetch` does not refuse a current call that has already replied.     var call = currentCall;

```479:487:js/src/prelude.js
    // next answer to settle claims the request (see `settle`).

```

```520:520:js/src/prelude.js
    call.tickets.push(ticket);
```

The next answer that settles with nothing of its own still claims an unclaimed ticket (`prelude.js:779–782`). D1 defers a background `fetch` to §7, but the drain D2 specifies will accept the call and the liveness rule LLP 1027.003.000 §13 already shipped will hand it to whichever answer settles next. That answer waits on a fetch it did not make, which is the failure D4.1 is trying to stop. `native.later` and `openAuthSession` go through the same `fetch` (`prelude.js:838–839`, `:554`).

**Fix.** The background owner is not a fetch caller. `fetch` while `currentCall` is `background` rejects with a journal line, the same shape as “outside an answer,” until §7 gives it a ticket. Do not push those tickets onto `background`, and do not let `settle`’s unclaimed-ticket scan see them.

## MINOR

### 5. D4.4 — “runs no `then`” contradicts D1 and the tests

**Section.** D4.4, D1, D8, §5.

**Problem.** D4.4 says a background failure “runs no `then`.” In this RFC `then` is also the app’s promise reaction. Read that way, the `.catch(note)` in the drums pattern never runs, which contradicts D1 (“it rejects the app’s own promise”) and the §5 test “rejects the app’s promise.” Contract `then` (LLP 1016.001, LLP 1092) is the reading that matches D4.4’s other clauses.

**Evidence.** `llp/1097-storage-that-finishes-after-the-answer.rfc.md` D4 item 4; `llp/1092-sends-that-queue-and-timers-that-wait.rfc.md:159–163` uses `then` for the Contract clause.

**Fix.** Write “runs no Contract `then`, re-asks no resource, and refuses no commit.” Promise reactions run in the background drain.

### 6. D3 — Queue-full uses `EBUSY`, which already means “database locked”

**Section.** D3, Q4.

**Problem.** The storage contract tells the app to branch on `code`, never the message (`docs/reference.md:357–365`). `EBUSY` is already the POSIX/database code (`prelude.js:596`, `:601`). A retry of a locked database and a refusal of a full queue become the same branch. Q4’s recommendation of `EBUSY` fights that contract. LLP 1041 D2 (overload is refusal) does not require reusing the lock code.

**Fix.** Refuse with a distinct code (`full` or similar), journal it, and add it to the code list in `reference.md`. Keep 256 as the bound.

### 7. D9 and D10 — Two reloads, two bounds

**Section.** D9, D10, Q2, Q5.

**Problem.** D9’s `reload` (the test step and the interactive restart) waits the way `clock settle` waits: 20 s and 16 rounds (`host/linux/src/agent.rs:693–697`, `:764–766`). D10’s “dev reload, a `reload()` command, a runner restart” finishes background work in 5 s and then drops the rest. The test step today is `scripts/agent-test.mjs:90–93`: on the web, `carrier.reset({ keep: true })` with no storage wait. Q2 (settle first) is the right meaning of a test `reload`. D10’s web paragraph says a `pagehide` may lose in-flight work. A dev-loop reload is a navigation the harness chooses to start; it can wait and then navigate. Stated together, the same event both waits and may lose the write.

**Fix.** One rule: the agent’s `reload` and a dev-loop reload wait for the module queue with `clock settle`’s bound, journal `reload: waited for N storage operations`, then tear down. `pagehide` that the page does not get to delay stays the loss case, and the docs say so. Keep 5 s for `applicationShouldTerminate` / orderly exit only (Q5).

### 8. D5 — LLP 1092 D3 is used as a mechanism and silently reversed as a rule

**Section.** D4.1, D5, Amends.

**Problem.** LLP 1092 D3: a send stays in flight until the source answers `Now`, and “a storage step and its continuation therefore finish before the next send is asked” (`llp/1092-sends-that-queue-and-timers-that-wait.rfc.md:159–163`). D5 models the background ticket on that “one more round,” and also says the ticket has no slot and no `then`. Those two readings diverge. If the background round is the mutation’s `Later`, the send stays in flight and R11 is unchanged. If it is a separate `Target::Background`, the mutation is free when the value is ready, and 1092’s sentence is false for unawaited storage. The Amends line does not mention 1092. `has_pending` counting the ticket (`commit.rs:864–868`) is what `clock settle` needs; 1092’s “free” check is per mutation and must not treat that ticket as the send.

**Fix.** Amend 1092 D3 in one sentence: unawaited storage does not keep the send in flight; the background ticket is not that send’s request. `Mixed`’s `background()` polls child modules in a fixed order and holds one runner ticket.
