## SHOULD

**1. A superseded held ticket stays named, and its tail starts counting.** `host/web-js/rt.js:523` (also `:511`, `:463`, and the mutation forget at `:574`) only logs and drops `r.ticket` / `m.ticket`. It does not clear `waiting` or call `counted`. `host/web-js/held.js:6` lists every object still in the set, and `:8-11` installs `recount` on that ticket. The resource already points at the new ticket, so `state.pending` (`host/web-js/agent.js:491`) shows only the new one, while every later clock reply still names the old one for as long as its fetch is out. When that fetch ends, `call.held` drops to 0 and `recount` sets `counts` on the dropped ticket, so `inflight.n` goes up and clocks wait on the answer's continuation. The wasm reply filter (`host/web/glue.js:953`, `holds(ticket)`) and `Runner::held_requests` (`runner/src/runner/commit.rs:951`) both omit a ticket the runner has already let go.

**2. After a wasm reload, the old fetch's `finally` deletes the new generation's name.** `host/web/glue.js:757` does `heldAsks.delete(op.ticket)` with no incarnation. Boot aborts and clears at `:1353-1354`, then `focus.restart` applies the new batch synchronously at `:1357`. The next await is `:1366`, so the aborted promise's microtask runs after the new `heldAsks.set`. Fulfill already refuses a stale incarnation (`:962-964`) because boot reuses ticket ids; this delete does not. The new held request is still not tracked, so a jump does not wait on it, and no clock reply names it for the life of that fetch.

**3. A held mutation on the JS target is named as its data source and missing from `state`.** The ticket is built with `name: source` at `host/web-js/rt.js:601`, so `heldTargets` is the source name. `state.pending` (`host/web-js/agent.js:491`) still lists only resources. The runner's `held_requests` uses the mutation's target name and `pending::state` (`runner/src/agent/pending.rs:22-29`) marks it `held: true`. Counting itself matches resources: one edge-triggered `counted` flag, and the same forgotten-ticket hole as finding 1.

## NIT

- **`exactHeld: "yes"` together with a stream.** `js/src/prelude.js:747` rejects, and because `"yes"` is truthy the message is the stream sentence. `host/web-js/ts-fetch.js:18` checks the type first and reports `exactHeld is true or false`. Both refuse the fetch. `js/tests/it/castle.rs` covers the two cases separately.
- **Linux `clock land` is unnamed.** `host/linux/src/agent.rs:1038` returns before `held_named`. Jump, `clock settle`, and `clock data` go through `held_named` (`:1050-1056`); a reply that starts with `{"error"` is left alone (`:1064`), including `malformed`. web-js, wasm, and Apple name a land reply that has no error. The agents guide (`docs/contract-for-agents.md:2971-2973`) only requires jump, settle, and data.
- **A clock reply taken while GPU work is already pending skips the name.** `host/web/glue.js:1097` and `host/web-js/agent.js:264` return the `reason: "gpu"` object before `heldNamed`. The same reply produced inside the clock body is named.
- **`Request::held()` does not survive onto the JS target.** `logic/abi/src/lib.rs:413` decodes `held: false`, and `host/web-js/rust-data.js:102` builds the request with no `held` field. The wasm host's batch uses `is_held()` (`host/web/src/batch.rs`). The TS `exactHeld` path is the one web-js implements.
- **Tests.** The Linux comment at `host/linux/src/agent/tests/input.rs:1039` says jump, `clock data`, and `clock settle` each name the ask. The body never sends settle, and the data assertion checks `held` but not `heldTargets`. The unmarked test (`:1066`) does prove a long hold is waited on to the bound. `host/web/agent.test.mjs:356` seeds `heldAsks` directly, so it proves naming and the let-go filter, not that a held op is left untracked. `host/web/glue-fixture.mjs:2` still names `glue-held.test.mjs`. The Linux host test never releases the server; "work after the reply" on that host is the runner test, which is what `has_pending` uses.

## What holds

Pending flags still use `in_flight()` (`runner/src/runner/commit.rs:828`), so `pending(…)` stays true while a request is held. `has_pending` and the public `in_flight()` use `waited()` (`runner/src/runner.rs:357`), and `held_requests` is the named set. `is_held()` is plain HTTP only (`runner/src/request.rs:393`), so storage, a continuation, a surface, a native call, auth, and a stream stay on the F10 path. Background work and device holds are unchanged.

web-js counting is sound on the paths you listed besides supersession. `counted` flips once per change (`held.js:10`). `done` returns when `t.closed` (`rt.js:407`); `closeLetGo` sets `closed` and uncounts once (`:429-430`). A rejected fetch still runs the `finally` that decrements `call.held` (`ts-fetch.js:24`). A held fetch that starts before `send` runs finds `recount` empty, and `send` then sees the live counter.

Work after a held reply counts again on the runner (a later non-held `Answer::Later` is in `in_flight()`), which is what Linux and Apple wait on. The web-js end-to-end drive waits on the unmarked `/detail` fetch after release. Wasm tracks that follow-up because it is not `op.held`. I did not re-run the wasm or Apple drives.

D9 matches D5 and D6. It uses D5's open-stream exception and one-request-per-target rule, and D6's cursor re-ask is the supersede case D9 requires. The agents guide and `docs/reference.md:1086-1097` say the same thing, including that a held ask must be safe to supersede. The `pending.rs` and `glue-fixture.mjs` moves preserve the old behaviour apart from the held entries and the extracted `heldNamed`.
