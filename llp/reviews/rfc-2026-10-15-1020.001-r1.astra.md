# Review of LLP 1020.001 (r1)

**Reviewer:** codex gpt-6-astra, reasoning effort max, run 2026-10-15 by Claude (Opus 5.5) for Charlie Cheever, read-only on `07fdd0ff4`, blind to the other two reviews. Scope given: foundational and directional questions only. The text below is the reviewer's final message, unedited.

VERDICT: ACCEPT WITH CHANGES

1. **The guest-facing namespace must be narrower than the resolver’s authority.** §3 D2 proposes serving anything under the resolver’s asset root, justified by those files already being public on the web. The current resolver can read files throughout its root, which can be the application bundle or working directory; it is not restricted to the published `assets/` tree. Containment within that root therefore does not establish the promised security boundary. Define the handler’s authority as the explicitly published asset namespace, with reads still going through the resolver. Do not expose arbitrary resolver-readable files. ([Proposal §3 D2–D3](llp/1020.001-a-bundled-web-app-in-an-iframe.rfc.md#3-design); `host/apple/Sources/ExactKit/Assets.swift`, `delivery`/`embeddedURL`; `host/apple/Sources/ExactKit/Session.swift`, `ExactApp.init`; `host/web-js/build.mjs`, asset copying.)

2. **Persistent storage and isolation from the web parent require an explicit trust choice.** The declared native/web difference is reasonable, but “an author who wants the web to match writes `sandbox`” does not reconcile it with D1’s storage promise. Without `allow-same-origin`, a sandboxed guest loses origin-based localStorage and IndexedDB access. With `allow-scripts allow-same-origin`, a bundled page sharing the parent’s origin can access that parent and remove its sandbox. This matters if authors treat an embedded third-party editor as isolated from application data. Scope this proposal to trusted bundled code when retaining web-origin storage; isolated guests must use a restricted sandbox and app-mediated persistence. If isolated guests also need their own persistent browser storage, a separate web origin becomes part of the design. Castle’s per-deck origins do not establish the safety of one shared app origin. ([Proposal §3 D1, “What the web does differently,” and §7](llp/1020.001-a-bundled-web-app-in-an-iframe.rfc.md); [Parent §8 Q1](llp/1020-webview.rfc.md#8-open-questions).)

3. **The probe must qualify the actual browsing contexts before committing to this transport.** Q1–Q5 are the right questions, but a standalone WKWebView probe does not establish D4’s cross-origin wrapper behavior on iOS. A stable URL alone does not establish usable persistent storage in both configurations; changing a viewport declaration should not unexpectedly change access to saved drawings. Probe direct and wrapped pages, their effective origins and message origins, storage across remounts and relaunches, and enforcement of the claimed isolation. Failure of required loading APIs, persistence, sandbox enforcement, or existing loopback behavior must reopen the mechanism choice just as Q1 does. These uncertainties justify probing now, not accepting the custom scheme as proven. Loopback remains a candidate requiring its own origin and persistence decision. ([Proposal §3 D1/D4, §4 Q1–Q5, §5](llp/1020.001-a-bundled-web-app-in-an-iframe.rfc.md); [Parent §10](llp/1020-webview.rfc.md#10-one-document-per-row-charlie-2026-09-28-as-built-on-perfwebview-direct).)

The problem is real, and Exact Draw supplies the consumer explicitly anticipated by the parent’s D2.
The scheme handler is a sensible first candidate; keeping it in the optional arm and using the existing resolver fits the project’s architecture.
Preserving ordinary `iframe` authoring and leaving the web implementation unchanged fits `rules/RULES.md` §Scope and `CLAUDE.md`’s principles, subject to the trust choice above.
