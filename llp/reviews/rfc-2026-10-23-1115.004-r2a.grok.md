## B. Text field

**Recommendation: (1).** The field is painted. S1 uses winit’s IMM32 events. TSF is required before a chat composer is called done. Do not build an `EDIT` arm in S1.

**Confidence: 73.**

The airspace claim is only half right. `IDCompositionDevice::CreateTargetForHwnd`’s `topmost` flag is exactly a visual tree above child HWNDs. Microsoft’s four layers are: GDI/DirectX in the window, a non-topmost composition tree, the child HWNDs, then a topmost composition tree ([CreateTargetForHwnd](https://learn.microsoft.com/en-us/windows/win32/api/dcomp/nf-dcomp-idcompositiondevice-createtargetforhwnd)). One topmost target per window can hold the dialog smoke and D10.1’s flyouts, so those pixels can cover an `EDIT`. Hit-testing does not follow. Composition visuals are not windows, so the click still lands on the child unless the field is disabled or covered by a window that takes hits. Position is a separate failure: `SetWindowPos` is not the swap chain’s present, so a field inside a scrolling form (Shelf’s add-a-book form) lags the painted rows around it. WinUI’s own text box is drawn in the composition tree for that reason.

Text does not match either. The painter is swash, hinted, grayscale (`host/linux/src/text/catalog.rs` lines 642 and 651, `Format::Alpha`). Microsoft still describes system edit controls as GDI ([Introducing DirectWrite](https://learn.microsoft.com/en-us/windows/win32/directwrite/introducing-directwrite)): ClearType, aimed at an opaque background, which is the opposite of the Mica swap chain in D4.3. Windows Desk’s control is that `EDIT` (`apps/windows-desk/src/native.rs` lines 179–183).

`EDIT` and RichEdit are the real TSF text stores, and that is the part a painted field does not have. winit’s path is IMM32. Narrator’s gain is real and narrower than it sounds: the native field brings its own UI Automation provider, while the rest of the tree is AccessKit on the parent HWND (`host/windows` uses `exact_linux::Presenter`, `host/windows/src/window.rs` lines 1–3), so the field is a second fragment, not a node in that tree. A Discord-style composer (Excord’s, and Agents’ draft at `apps/agents/app.contract` lines 140–149) is the control this has to survive, and it is the worst fit for a child `EDIT`: multiline, Enter to send, custom chrome, CJK composition in place.

D7.0’s spike scores the oracle, Narrator, CJK, the touch keyboard, and dictation. Those are `EDIT`’s strengths. It does not score scroll sync or the glyph next to its label, which are the tells. Scored as written, the spike picks `EDIT`.

**What would change this:** on the NucBox, a child field that stays within a frame of the painted form during a fling, accepts a topmost smoke layer for both pixels and hits, and whose glyphs match the label at 100% and 150%. I do not expect `EDIT` to pass the first and third. If IMM32 composition is actually broken for CJK in S1, a temporary `EDIT` is a bugfix for that field, not the architecture.

## C. Menu bar

**Recommendation: (1), and only when the app declares menu items.** A painted Fluent menu bar, WinUI’s `MenuBar` look, as a row under the title bar, opening D10.1’s flyouts, with Alt, F10, and the accelerators. An app that declares none gets no bar.

**Confidence: 81.**

Of the inbox apps in the question, Notepad is the one with a menu bar: File, Edit, View, under the tab strip (still the File menu in 2026). File Explorer has tabs, a command bar, and a three-dot menu, and no supported way back to File/Edit/View. Settings, Terminal, Clock, Photos, and the inbox Media Player have no menu bar. Paint has a ribbon and a Paint menu button. WinUI’s own guidance for “a set of multiple top-level menus in a horizontal row” is a menu bar at the top of the client, not in the caption ([Menu flyout and menu bar](https://learn.microsoft.com/en-us/windows/apps/design/controls/menus)). UI Automation’s menu-bar access key is Alt ([MenuBar control type](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supportmenubarcontroltype)).

An `HMENU` bar is the classic metrics D10.1 already refuses for flyouts. Windows Desk’s bar is that object (`apps/windows-desk/src/native.rs` lines 747–761). Folding the commands into a command bar or a “More” menu drops a placement the author wrote: Agents puts New Conversation in File (`apps/agents/app.contract` line 175, `-exact-menu="file"`). Putting that row inside the integrated caption fights the drag region; Notepad keeps the menu under the tabs.

The Mac `app` and `window` menus do not become menus. There is no application menu on Windows. About goes under Help. Settings, if the author placed one, goes at the bottom of File or on a gear, which is where WinUI’s `NavigationView` puts it. Quit, Hide, and Services are omitted; Close and Alt+F4 are the platform’s. Minimize, Zoom, and Bring All to Front are the caption buttons, Snap, and Alt+Space. Do not synthesize a Window menu. Authored `Meta` chords are Ctrl on Windows: `Meta+N` must not become Win+N, which is Notification Center. An app with no `-exact-menu` items, Shelf included, gets no File/Edit/View/Help strip. Alt still shows access keys on controls; F10 does nothing if there is no bar.

**What would change this:** if the only declared menus in real apps stay one or two items, a command bar is the plainer Windows presentation and (1) is ceremony. Agents is the app that makes the bar real; until it is on Windows, a contract fixture has to carry this.

## What the RFC has wrong, and what to ask

The RFC is wrong, or stale, in three places:

- D7.0’s spike will pick `EDIT`. `topmost` covers pixels and does not cover hits or `SetWindowPos`. The score list leaves out scroll sync and the glyph beside the label.
- D9.4 assumes a menu bar “when an app has one.” LLP 1021 §5.3 says Windows ignores `-exact-menu` and keeps the ordinary button (`llp/1021-menus.rfc.md` lines 1210–1213). Nothing in the RFC amends that, so an implementer who reads 1021 will build no bar. The same sentence does not say that authored `Meta` chords become Ctrl.
- D0.1’s “more apps follow S1” is the bound from before today’s ruling. The waiver should not write Shelf-only back in.

Two questions worth asking now:

1. An unsaid root `tablist` on Windows: a left pane, as in Settings, Clock, Media Player, and Microsoft’s own WinUI shell ([the same app-structure doc](https://learn.microsoft.com/en-us/windows/apps/develop/ui/windows-app-sdk-app-structure)), or the phone tab bar Shelf uses? The Mac already turns that unsaid bar into a sidebar (LLP 1115.002 D3). Shelf’s S1 frame is this choice, and so is the default window size, which `app.json` does not name for Windows.
2. Confirm `Meta` maps to Ctrl on Windows, including chords that never appear in a menu.
