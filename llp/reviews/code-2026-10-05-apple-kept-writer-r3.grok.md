LAND WITH CHANGES

Round-1 and round-2 dispositions that match the code: coalesce-at-enqueue (`store.rs:167-170`, `store.rs:203-205`), `snapshot_of` flushing before a read (`store.rs:259-260`), failures of a dropped platform moving to `ORPHANED` (`store.rs:141-145`), `abi.rs` left at 1498 lines, secrets still synchronous (`store.rs:118-119`), and the gated two-key test. The round-2 exit claim does not hold.

1. **BLOCKING** — Orderly exit can replace a newer kept value with an older one, or drop a write `keep` already accepted. `drain` sets `CLOSING` and `flush_kept` only waits until `busy` is clear and `order` is empty (`store.rs:187-189`, `store.rs:243-250`). A later `keep` that sees the flag writes in place on the caller, beside the writer (`store.rs:177-180`), while `write_kept` may already be inside `write_one` for the previous value of that same key (`store.rs:218-221`). `FileStore::set` renames a temp over the key, so the slower call wins. Sequence: commit keeps `feed=v1` and the writer is in `sync_all`; quit runs `atexit` (`Agent.swift:121`, `main.swift:412`) and sets `CLOSING`; the owner, in a posted commit (`Owner.swift:128-132`), keeps `feed=v2` inline; `v1`'s rename lands last. The next launch's snapshot reads `v1`. A second hole is the flag check outside the mutex: `keep` can load `CLOSING == false`, block on `WRITER` until `flush_kept` has already observed an empty queue and returned, then enqueue. `_exit` then kills the writer with that write only queued. Before this change, `persist` did not return from a kept write until the rename and sync had finished. Fix: under `WRITER`, set the closing flag, keep enqueueing (do not call `write_one` beside the writer), and have `drain` wait until the queue is empty and `busy` is false, then hold that lock across the rest of exit (`mem::forget` the guard) so nothing starts a write the drain will not see.

2. **MATERIAL** — Two live sessions can persist an older value of one key over a newer one. The queue key is the platform's `Failures` address plus the key (`store.rs:109-114`), and a repeat stays at its first position (`store.rs:203-205`). Two runtimes in one process share `FileStore::for_app(app_identity())` and commit on the one owner thread. Sequence, writer busy on an earlier fsync: session A queues `feed=1`, session B queues `feed=2`, session A queues `feed=3` (same slot, still ahead of B). The writer stores `3` then `2`. The next launch reads `2`. One platform never does this, because it has only one slot. On replace, move that key to the tail of `order`, so the last commit is the last rename.

3. **MINOR** — The new tests never close the writer, so finding 1 does not fail a run, and a failing gated test hangs the process. `kept_answers_are_written_in_order_after_the_commit_and_a_snapshot_waits` leaves the gate shut until after the assertions (`store.rs:385-397`). `busy` stays true if an assertion panics, the `JoinHandle` is dropped, and every later `flush_kept` — including `atexit` — waits forever. Open the gate in a `Drop` guard. `Host::persist`'s call to `kept_failures` (`host.rs:704-706`) is still untested; that part was deferred and is still open.
