1. **The acceptance bar can pass while Android build installation remains broken.**  
   **Claim:** §1 promises platform-appropriate system integration; D1 proposes replacing `url-opener` with existing commands where possible, while §5 primarily qualifies presentation.

   **Actual:** The Exact app hard-codes `const device = 'IOS'` and consequently rejects Android builds as belonging to another platform ([details.ts:602](.refs/ios/src/details.ts:602)). Installation also requires `onDevice`, which starts false, changes through `detailsInstallSignal`, and disables both installation controls when false ([app.contract:182](.refs/ios/app.contract:182), [app.contract:606](.refs/ios/app.contract:606), [app.contract:871](.refs/ios/app.contract:871)). Its source is a startup event from the Swift URL opener ([EasNative.swift:416](.refs/ios/modules/apple/EasNative.swift:416)). The Android reference instead checks the actual device platform and device eligibility ([install.ts:15](.refs/android/src/screens/build/utils/install.ts:15), [install.ts:37](.refs/android/src/screens/build/utils/install.ts:37)).

   **Why it matters:** Replacing every drawing module successfully would still leave a central Expo Services workflow unavailable. The launch caveat in §2 acknowledges incomplete evidence, but the proposed acceptance criteria do not close this specific gap.

   **Change:** Include the platform-dependent installation policy and replacement for the URL opener’s device/result reporting in the port’s required integration work. Require an eligible Android build to reach the platform’s installation handoff, with refusal and failure behavior checked. Alternatively, explicitly define this RFC as a graphics milestone and make functional Android qualification a separate prerequisite for completing the port.

2. **“Thin native reporting modules” are not currently a working Android fallback.**  
   **Claim:** D1 allows version, device and posture reporting to remain thin native modules.

   **Actual:** The iOS reporting modules communicate through `events.change`; version and device nodes are deliberately zero-sized ([EasNative.swift:1761](.refs/ios/modules/apple/EasNative.swift:1761), [app.contract:987](.refs/ios/app.contract:987)). Android’s `NativeModule` interface supplies only view creation, property updates, reset and destruction—no event callback or instance identity—and its factory receives only context and module props ([Natives.kt:22](host/android/canvas/src/main/java/dev/exact/canvas/Natives.kt:22), [Natives.kt:420](host/android/canvas/src/main/java/dev/exact/canvas/Natives.kt:420)). Independently, the shared painter returns before emitting a native element when either content dimension is zero ([native.rs:61](host/linux/src/paint/native.rs:61)). These are capabilities the accepted native-module design explicitly provides through its event channel and instance lifetime rules ([LLP 1024:291](llp/1024-native-modules.rfc.md:291)).

   **Why it matters:** Writing small Kotlin equivalents would not make these reporters function. They lack both a supported return channel and, for the zero-sized nodes, creation through the current drawing path. This is additional host work beyond replacing app artwork.

   **Change:** Choose the reporting mechanism before implementation: use shared capabilities where available, or explicitly include the bounded completion of Android’s existing module event/lifecycle support. The plan must support reporting independently of visible drawing and reject callbacks from retired instances; it need not introduce a general new extension system.

3. **The native-presentation requirements need explicit implementation dependencies in the approved scope.**  
   **Claim:** D1 requires Material symbol resolution and Android sheets following LLP 1115.001 D10; §6 describes the bounded host work chiefly as gradients, `d` keyframes and conditional Canvas replay.

   **Actual:** Ordinary symbols still resolve through a table containing an Apple name and browser SVG path; the Android-shared painter draws that browser path ([schema.json:4596](kernel/tables/schema.json:4596), [svg.rs:135](host/linux/src/paint/svg.rs:135)). Modal route handling currently establishes visibility and inertness rather than a bottom-sheet presentation ([navigation.rs:246](host/linux/src/navigation.rs:246)); the top-layer presenter also explicitly refuses sheets and choosers ([top.rs:348](host/linux/src/presenter/top.rs:348)). The app actually uses modal routes and detents for its account/project selectors, workflow flow and TTI sheet ([app.contract:864](.refs/ios/app.contract:864), [app.contract:932](.refs/ios/app.contract:932)). LLP 1115.001 itself records Material symbols and sheets as later work ([1115.001:798](llp/1115.001-no-tells-on-android.rfc.md:798)).

   **Why it matters:** These are required host features, not outcomes supplied by changing app tags. The graphics work can finish while the promised platform presentation and its acceptance checks remain blocked.

   **Change:** Make the consumer’s required D10/D14 slices explicit prerequisites or owned implementation work in §6, and reflect them in sequencing. Shared graphics previews can proceed independently, but completing those previews must not imply that native presentation is qualified.

The direction is right: shared Contract/SVG artwork, platform presentation and Canvas acceleration only when measurements justify it fit the repository’s architecture. Before implementation starts, the RFC should close the functional integration gap, select a viable reporting mechanism, and explicitly account for the unfinished presentation dependencies. These changes make the proposed work sufficient for its stated Android outcome without requiring a broader graphics framework.
