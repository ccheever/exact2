# Review of LLP 1020.001 (r1)

**Reviewer:** muse muse-wonder-full-1.0, reasoning effort xhigh, run 2026-10-15 by Claude (Opus 5.5) for Charlie Cheever, read-only on `07fdd0ff4`, blind to the other two reviews. Scope given: foundational and directional questions only. The text below is the reviewer's final message, unedited.

VERDICT: ACCEPT WITH CHANGES

Accept the probe and the problem, not the mechanism as build-ready. Material findings:

1. **The probe is the decision, and it probes only one arm.** Q1–Q3 in [llp/1020.001 §4](llp/1020.001-a-bundled-web-app-in-an-iframe.rfc.md:104) are existential — a custom scheme may never be a secure context, load workers, or register service workers (restricted to secure http(s)/loopback origins), yet only Q1 has a stated failure consequence, and the probe runs only on macOS/iOS 27 simulators while the supported range starts at macOS 14/iOS 17 ([host/apple/Package.swift:88](host/apple/Package.swift:88); the parent D4 already records a simulator/device split). §5 dismisses in-process loopback HTTP on port persistence (solvable by persisting and rebinding a chosen port) and local readability (its own D2 says the assets are public), even though loopback is the one mechanism the consumer has actually proven with Excalidraw ([docs/agent-pitfalls.md:826](docs/agent-pitfalls.md:826)), and the Castle precedent served decks, which need none of Q1/Q2's features. Change: run one probe with both arms against the same question list (adding service workers, OPFS, cookies, and reload/history), across the supported OS range including a physical iOS device, with a pre-committed go/no-go and fallback per question, and accept a mechanism only on its results.
2. **The origin choice is a one-way door treated as a detail.** D1 makes `exact-app://app` the single, permanent origin for every local guest, so it becomes the durable key for guest `localStorage`/IndexedDB; any later change of scheme, host, or partition orphans user data, and the delete-don't-deprecate rule in [rules/RULES.md:49](rules/RULES.md:49) covers code, not that data. The cited Castle precedent chose a *per-deck* origin ([llp/1020 §8 Q1](llp/1020-webview.rfc.md:377)); the isolation unit is never discussed, so mutually distrusting bundled guests share storage forever. That storage also lands in the default `WKWebsiteDataStore` the arm deliberately shares with the embedding app ([host/apple/webarm/WebArm.swift:87](host/apple/webarm/WebArm.swift:87)), outside Exact's `app:/` storage, grants, eviction, and agent visibility — §7 says the guest gets none of the app's storage while silently granting it an unmanaged durable store. Android already loads local guests as `file://` ([host/android/canvas/src/main/java/dev/exact/canvas/Natives.kt:473](host/android/canvas/src/main/java/dev/exact/canvas/Natives.kt:473)) and §7 takes no position beyond Linux, so this would be a third guest-visible origin identity. Change: decide and declare the partition unit, the persistence/eviction/migration stance, and the per-host origin contract before anything ships under this origin.
3. **As written, the served tree and the handler's reach are broader than the web's.** D2 serves "anything under the asset root that the resolver holds," but the resolver is a whole-generation store: the embedded generation reads any well-formed name under the asset root, which is the bundle resources — or the working directory for the bare macOS development executable ([host/apple/Sources/ExactKit/Assets.swift:129](host/apple/Sources/ExactKit/Assets.swift:129), [Session.swift:165](host/apple/Sources/ExactKit/Session.swift:165)). Today only an author-chosen `src` is read that way; a scheme handler makes file selection guest-chosen at runtime, and the guest is third-party code. D1 also registers the handler on *every* web view, making the asset origin navigable from remote guests, where today `exact.localhost` is unserved and unreachable. Change: pin serving to the `assets/` subtree — exactly the tree the web build publishes ([host/web-js/build.mjs:631](host/web-js/build.mjs:631)) — and enable the handler only on web views whose committed `src` is local.
4. **The consumer does not quite justify the scope.** The parent admitted multi-file local *decks/pages* as D2's declared limit, with a DEFERRED trade paid for Weird Castle ([llp/1020 D2, §6](llp/1020-webview.rfc.md:184); [rules/DEFERRED.md:530](rules/DEFERRED.md:530)). This proposal's title and consumer widen that to arbitrary bundled web *apps*, the class that will earn back §5's refusals (permissions, popups, navigation, downloads) one at a time; Exact Draw is admitted nowhere in DEFERRED, and it still cannot launch standalone after this lands, because shell and editor call the same Bun companion for chosen files, which the sibling issue leaves awaiting Charlie's ruling — one possible ruling being that document apps keep a bundled companion, which could keep serving the editor app-side under the parent's §9 boundary ([issues/20261015-chosen-documents-outlast-the-launch.md:3](issues/20261015-chosen-documents-outlast-the-launch.md:3)). Change: either justify this strictly as D2 completion for local pages, with the web-app feature ceiling explicitly not committed, or obtain the admission/trade [rules/RULES.md:47](rules/RULES.md:47) requires for the web-app class, sequenced after the sibling ruling.
5. **Two included pieces have no consumer and carry the known risk classes.** D4 replaces the working typed-document path for non-HTML files (#115, parent §10) with scheme serving, and PDF presentation from scheme-handler responses is precisely the kind of WebKit behavior the probe never tests; D4 also makes sandboxed local guests direct on macOS, resting their sandbox on a CSP header delivered over a custom scheme (Q4), where the wrapper enforces `sandbox` by construction — the parent D2/§10 position after exact1's fail-open. Change: scheme-serve multi-file HTML guests only, keep #115's path, and keep sandboxed local guests in the wrapper unless Q4 passes across the supported range.
6. **The declared origin difference needs to become an author contract, not advice.** For untrusted decks "native is stricter" was the right call, but a trusted bundled app is exactly the guest whose web build may use same-origin `window.parent` access — which then works in the web dev loop and silently breaks on Apple. Telling authors to add `sandbox` on the web so it matches native inverts the web-as-oracle principle ([CLAUDE.md:16](CLAUDE.md:16); parent D1). Change: state the portable bundled-guest contract explicitly — communication with the shell is `postMessage` only, no parent DOM, no storage shared with the shell — in the proposal and the author docs, so the divergence is a designed rule authors write to rather than a per-app discovery.

What is right: a real named consumer executing a mechanism the parent pre-declared, with no Contract surface change and the handler inside the on-demand arm, so iframe-free apps pay nothing (parent D3). D3 is a genuine simplification — one resolver read path deletes the arm's duplicate filesystem reading and gives delivery/dev parity to every sub-resource. The probe-first instinct is correct; it just needs to become the gate in finding 1.
