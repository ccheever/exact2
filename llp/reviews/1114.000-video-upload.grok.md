I'll review LLP 1114.000 for direction and architecture only. First I'll read the parent summary, the RFC, and the rules it depends on.The RFC’s load-bearing claims are the range body, the 64 MiB cap, progress, and `compressVideo`. I’ll check those against the code and the LLPs they cite.## Verdict: RIGHT WITH CHANGES

Stage 1 is the right capability, and it should land. A Bluesky upload does not need a body over 64 MiB. It needs a range of a file, which `exactBodyFrom` cannot express today. Stage 3’s `compressVideo` contract, and the byte-progress mechanism written under stage 2, should not be ruled in as specified.

## Overall assessment

I checked the RFC against `social-app` on main, the `app.bsky.video.startUpload` lexicon, and the exact2 paths it cites (`runner/src/request.rs`, `host/apple/src/executor_body.rs`, `vendor/ibex/crates/ibex2/src/transport/darwin_http.mm`, `host/web/storage-fs.js`, LLP 1067, LLP 1016.002, LLP 1042, LLP 1069.002 A1.8, LLP 1108). The Bluesky correction in the parent holds: upload is `startUpload` / `uploadPart` / `finishUpload` to `https://video.bsky.app`, four parts at a time, `Content-Length` exact, service-chosen `partSizeBytes`, limits 300 MB and 10 minutes. Keeping the 64 MiB cap and adding a `Blob.slice`-shaped range is the right fix. The transcode and the progress API are a different, worse shape than the clone’s real upload.

## Concerns

**1. MAJOR — `compressVideo` freezes an Apple encode the web oracle cannot meet.**

D4’s result is always `video/mp4`: H.264 High, AAC, `moov` first, HDR converted to SDR. Bluesky’s web compressor (`compress.web.ts`, Mediabunny over WebCodecs) tries `avc`, then `hevc`, `vp9`, `vp8`, writes WebM when it has to, and passes the original through when encoding is missing or throws. WebCodecs does not reliably encode AAC into MP4, so “W1, a muxer” cannot implement this signature. LLP 1042 already says codecs are engine capabilities, not promises by Exact, and that the web’s formats are the oracle. W0 (`unsupported` on the web, Linux, and Windows) means the dev loop never runs the capability the ruling would admit. The long-request idea (a ticket, abort when the answer is replaced, the I/O worker not held) is the right carrier, but LLP 1067 D1 and LLP 1067.000 D1 give `exact-native:` to the app’s one module. This call has to be a host request, not that URL.

There is a second composition failure on the web. `requestBody` is zero-copy for a picked `File`. A file the app writes, as `compressImage` does via `atomicWriteOwnedFile`, is one IndexedDB byte record and is read whole (`storage-fs.js` `blob`). Ranged upload of a transcoded file would copy the entire output per part.

Resolve: do not admit Amendment A3 in this shape. Stage 1 does not need it. An Apple transcode, if the clone must have one before a shared contract exists, is T3 (the clone’s own Swift module). A framework call should return the type the host actually encoded (`video/mp4` or `video/webm`) or `unsupported`, and a web output has to be stored as a `Blob` (`putBlob`) so stage 1 can slice it.

**2. MAJOR — “parts are a few megabytes” is the S3 floor, and four buffered parts can be the jetsam case D1 rejects.**

`partSizeBytes` in the lexicon is an integer with no maximum. The 5 MiB figure is R2/S3’s minimum except for the last part. The client uses whatever the service returns (`planParts.ts`). Each in-flight part is read whole into the request (`executor_body.rs`, cap 64 MiB, at most four readers) and copied again into `NSData` (`darwin_http.mm` `HTTPBody`). Four Darwin sessions is also the pool’s ceiling, so a token refresh or `abortUpload` during those four parts waits for a slot. D1 says a 300 MB body held twice is about 600 MB and enough for iOS to kill the app. Four parts at the clone’s 64 MiB ceiling is that same shape.

Resolve: record an observed `partSizeBytes` from `video.bsky.app`. If it is a few mebibytes, buffering is fine and the RFC should state the number. If it is tens of mebibytes, the clone should keep fewer than four parts in flight, or the reader should stream the range to the socket. That is not a reason to raise the cap.

**3. MAJOR — the specified progress API cannot represent this upload, and it uses the app’s topic channel.**

P0 (count finished parts) is the right call for the clone. P1 is not a design to leave on the record. One slot, “the latest request under that name,” loses three of the four parts that are in flight together. The RFC’s own reason to build P1 later is a slow link where one 5 MiB part takes a minute, which is still four overlapping parts. LLP 1016.002 topics are announced by the app’s native module (`native.watch`, `ExactNative.changed`). A host HTTP stack publishing `progress:video` collides with application topics and adds a second read (`progress(name)`) beside them.

Resolve: rule P0. Delete the P1 signature. If a later app needs byte progress, specify a sum over the parts of one upload, owned by the host, not an app device topic.

## What it gets right

- The capability the clone lacks is a range, not a larger single body. `fetch` still has no upload progress, and a streamed body (`duplex: "half"`) would omit `Content-Length`, which `uploadPart` rejects. Counting parts matches the client.
- R1 now, deleted if LLP 1108 D5’s `Blob` lands, matches “delete, don’t deprecate.” That `Blob` is still NOT READY (slice 3). Waiting on it would block the upload on an unready RFC. Slice semantics (`end` exclusive, clamp) are the web’s.
- No new grant. `fs.read` on the picked file, `fs.write` for an output, `net.fetch https://video.bsky.app`. The service proxies the bytes. Upload does not go to a presigned bucket URL.
- Not transcoding at pick, which LLP 1069.002 D6 already forbids, and which the web picker cannot do.
- The optional-capability rule is respected in spirit for Apple video: AVFoundation stays in the on-demand `libexact_video` artifact, not a Cargo feature. The problem is the contract, not the packaging.
- Leaving the JS target’s existing “a replaced answer’s fetch runs to completion” behavior alone is right. Widening that here would be a second project.

## Questions for Charlie

**Q1 — change the recommendation to no.** Do not reopen LLP 1069.002 D6 for this `compressVideo`. The 4K-over-300MB gap is real on a phone. Closing it with an API whose return type is `video/mp4` leaves the web, the parity oracle, on the original file forever, and a later “muxer” cannot honestly implement the signature. T3 covers Apple in the clone until a result type both surfaces can produce is specified.

**Q2 and Q4 — keep the recommendations.** Range now (R1). Cap stays 64 MiB.

**Q3 — keep P0, and do not adopt P1 even as a future sketch.** Accepting the RFC as written would accept a one-slot observation that this upload cannot use.

**Missing question:** what `video.bsky.app` actually returns for `partSizeBytes`. Stage 1’s memory story depends on it. The S3 minimum does not answer it.
