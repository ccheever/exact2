**1. Verdict: RIGHT WITH CHANGES.**

**2. Overall assessment**

Stage 1 is directionally sound and can proceed independently. Reusing the existing incoming-location path gives notification taps the right shape. Stage 2 addresses a plausible need, but its proposed scheduling unit contradicts Apple’s limits, and its whole-session completion model lacks a sound boundary around background work. Those require architectural decisions before implementation.

**3. Concerns**

1. **MAJOR — One OS refresh request per Contract task does not work.**

   [D2 and D5](/Users/ccheever/projects/exact2-review-1114/llp/1114.001-background-refresh-and-notification-taps.rfc.md:255) give each task an Apple identifier and schedule, then add delivery’s own wake. Apple permits only **one pending refresh task per app**; additional requests fail with `tooManyPendingTaskRequests`. The conflict therefore appears with just the inbox task and the delivery consumer offered as the admission trade. [Apple’s scheduling documentation](https://developer.apple.com/documentation/backgroundtasks/bgtaskscheduler/submittaskrequest%28_%3Acompletionhandler%3A%29?changes=_6).

   **Resolution:** Use one application-level OS refresh request that dispatches eligible Contract tasks and delivery work within the granted execution window. Define how those consumers share that window. This also removes the claimed platform necessity for putting every Contract task name into binary metadata: logical task names can sit behind one fixed Apple identifier. Static declarations may still be desirable, but Apple’s identifier requirement does not establish the RFC’s one-to-one mapping.

2. **MAJOR — Whole-runner quiet is not a sufficient lifetime boundary for a wake.**

   [D3](/Users/ccheever/projects/exact2-review-1114/llp/1114.001-background-refresh-and-notification-taps.rfc.md:285) dismisses ownership because nobody is acting during a wake. But the proposed warm path uses the existing session, which can contain unfinished foreground requests, queued mutations and storage. The person can also reopen the app while the wake runs. Even cold activation re-asks deferred application resources, so executing the inbox action can bring unrelated work into the completion condition. [Runner data activation](/Users/ccheever/projects/exact2-review-1114/runner/src/runner/kept.rs:179).

   Consequently, unrelated work can consume the wake’s budget, and the design has no clear answer for which work expiration terminates or which commands remain subject to “during a wake” refusals after foregrounding.

   The expiration rule compounds this: reporting failure and relying on the storage hold does not define cancellation. [LLP 1097 D10](/Users/ccheever/projects/exact2-review-1114/llp/1097-storage-that-finishes-after-the-answer.rfc.md:647) explicitly allows suspension to interrupt storage after its assertion expires. Apple’s refresh example cancels the operation when the task expires. [Apple’s background-refresh guidance](https://developer.apple.com/documentation/uikit/using-background-tasks-to-update-your-app?changes=_8_4).

   **Resolution:** Give the wake an explicit execution lifetime—through invocation ownership or an isolated headless context that retains the existing action/effect boundary. Define completion, expiration, and transfer to foreground execution together. Whole-session draining is viable only with an explicit rule establishing exclusive ownership; the current cold/warm design does not provide that.

**4. What it gets right**

- `navigate=` reuses the router and existing cold-launch location handling without introducing another app event model.
- Separating notification taps from background execution lets the immediately useful part ship first.
- Existing grants, no background permission prompts, and refusal to treat unavailable protected data as signed-out state are good boundaries.
- The declared platform limitations and deterministic wake entry for agents are appropriate.

**5. Questions for Charlie**

- **Keep Q1’s recommendation: yes to stage 1.**
- **Change Q2 to conditional admission:** first resolve scheduling and execution lifetime, then explicitly decide whether opportunistic iOS alerts justify stage 2’s cost. The RFC acknowledges opportunism, but does not establish that the clone accepts potentially long gaps without alerts. Apple specifically cautions against expecting regular fifteen-minute execution. [Apple DTS explanation](https://developer.apple.com/forums/thread/685525).
- **If timely background notifications are essential, should the clone’s backend strategy be reconsidered?** Polling through `BGAppRefreshTask` cannot provide that guarantee. This need not expand this RFC’s implementation scope, but it should determine whether stage 2 is the right investment.
