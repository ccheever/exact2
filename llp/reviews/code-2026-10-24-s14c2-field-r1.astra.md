Found seven issues in HEAD `2126e2f2f8`.

1. **MAJOR — CSS comments can defeat the mixed-rule refusal.** [icon_svg.rs:261](contract/lower/src/icon_svg.rs:261) uses `property()`, whose declaration splitter does not consume CSS comments. A path with `fill-rule="evenodd" style="/* override */ fill-rule:nonzero"` is classified as even-odd. Beside another even-odd path, the mixed icon is accepted and painted incorrectly. CSS requires consuming those comments. **Fix:** tokenize the declaration list before resolving precedence; add this mixed-path case. [CSS Syntax](https://www.w3.org/TR/css-syntax-3/#consume-comments)

2. **MAJOR — Literal even-odd sources bypass compatibility detection.** [icon_rules.rs:27](bake/src/icon_rules.rs:27) checks only `plan.icons`. An accepted literal such as `image "symbol:icon||0 0 24 24|evenodd:M…|"` creates no icon-table row—the new web and Linux fixtures themselves use this form. Its plan therefore needs marker support while retaining the old compatibility cohort. **Fix:** account for accepted literal source forms through `Icon::parse`, or register their requirements during lowering. Add a compatibility test without Tamber declarations.

3. **MAJOR — Compatibility examines a fresh source compilation instead of the shipped plan.** [icon_rules.rs:15](bake/src/icon_rules.rs:15) returns no requirement when neither guessed contract path exists, even when `OUT_DIR/app.plan` contains an even-odd row. The bake API already requires that artifact, and `receipt::emit` decodes it. Recompilation can also observe different source bytes and adds another full compilation after `colors::check`. **Fix:** derive requirements from the actual baked plan; use a checked source fallback only for the standalone CLI. Ordinary `app.contract` compilation failures already propagate through `colors::check`; the new `.ok()?` is not independently fail-open in that ordinary case.

4. **MAJOR — The guard does not enforce the approved reader restriction.** [icon_path_readers.rs:73](contract/cli/tests/it/icon_path_readers.rs:73) misses `lookup(row.path)`, `plan.strings.get(row.path.0 as usize)`, and `let id = row.path; plan.str(id)`. Its source check misses single-quoted `'icon|'` files and slicing-only readers. At line 129, any nearby `Icon::of_row` exempts unrelated reads for four following lines. The scan also omits source locations/extensions such as `js/`, scripts and TypeScript. **Fix:** check path-field acquisition independently of accessor names, constrain exemptions to the actual call expression, expand coverage, and add negative fixtures for these bypasses.

5. **MINOR — Presentation attributes incorrectly accept `!important`.** [icon_svg.rs:282](contract/lower/src/icon_svg.rs:282) accepts `fill-rule="evenodd !important"` because `property()` strips importance from attribute values too. SVG treats that attribute value as invalid; this commit instead admits an even-odd template and can introduce holes absent from the original SVG. **Fix:** parse presentation values separately from style declarations and refuse unsupported values. [SVG presentation attributes](https://www.w3.org/TR/SVG2/styling.html#PresentationAttributes)

6. **MINOR — The JavaScript marker parser disagrees with `Icon`.** [symbols.js:32](host/web-js/symbols.js:32) treats an empty rule before a colon as an unmarked path. For `icon||0 0 24 24|:M0 0h4v4H0Z|`, JavaScript draws the square; Rust returns `None`. I reproduced this with the actual JavaScript function. **Fix:** distinguish “no colon” from “empty prefix”, and share rejection cases between the Rust parser and its JavaScript counterpart.

7. **MINOR — Double markers survive the shared parser.** [replaced.rs:187](kernel/src/replaced.rs:187) accepts `evenodd:evenodd:M…`, leaving `evenodd:M…` in the supposedly stripped path. JavaScript does likewise; `form()` preserves the malformed double marker. **Fix:** reject residual colons after stripping the single supported marker, and test double markers and whitespace-only marked paths.
