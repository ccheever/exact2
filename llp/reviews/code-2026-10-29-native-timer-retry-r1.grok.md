The retry itself is correct. `complete(_:retry:)` keeps the entry `pending` and at the front, so a Foundation callback in the meantime returns at `!entry.pending` and is not queued beside it. `resume(after: 1/60)` arms delivery without asking on every turn of a nested run loop: `notification` stays true until that block runs, so a second `resume` is not scheduled, and the next ask is at least a frame later. Busy is not sticky. `Owner.sync` returns `Runtime.busy` only while `serving > 0`, which is the `callMain` body; once that body returns, the delayed ask runs with `serving == 0` and the firing is delivered once. A held answer is the same shape, and `runtime.held` is only set for the synchronous `resetHeld()` / `destroy()` window. `cancel()` drops the queue and invalidates the timers; the delayed block holds `NativeTaskTimers` weakly and no-ops when `hasReady` is false, including after `destroy()` and after an epoch `cancel()`. No second delivery, no tighter-than-frame spin, no leftover timer.

The audit holds. `deliverNativeTimer` takes only after the `applying` / `ownerInFlight` checks, so an early return leaves the firing queued and `notification` already cleared by the ask. A landing that actually applies reaches `updateTimerState` → `resume()` because `clockUnchanged` is false while `hasReady`. A held landing is skipped in `landFill`, but that batch only exists inside `resetHeld()` / `destroy()`, and the commit `apply` or `cancel()` that follows re-arms or drops the queue. The async completion’s generation guard skips `complete` only after `generation` has moved; that epoch’s `update` / `destroy` calls `cancel()` and invalidates every entry, so a taken firing cannot sit `pending` on a live timer. `TimerAdmissions` really does clear `pending` on a busy or held check, sync and async, and the `beforeWaiting` observer plus the due-time wake call `check` again. Nothing else in these two types leaves a pending entry or a non-empty queue without an ask.
