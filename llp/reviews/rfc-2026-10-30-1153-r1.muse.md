## 3. Major oversights

1. **BLOCKER — D3.4: a web-only deploy has no envelope producer.** Today the envelope comes from the bake: [deploy.mjs](/Users/ccheever/projects/exact2/scripts/deploy.mjs:644) runs `host/web/build.mjs <app>-web --bake`, and the JS root merely carries that bake's origin files ([deploy.mjs](/Users/ccheever/projects/exact2/scripts/deploy.mjs:632)). A web-only app has no `web/` crate, so "bakes nothing" and "the envelope is still written" cannot both hold. Resolve: specify a JS-target producer for `exact.json` (plan, compat, cohort), or admit deploy brings `web/` — which changes D1's story.
2. **BLOCKER — D7: one shared plan cannot be lowered two ways at compile time.** The bake's plan is shared by the web root and every native stream ([deploy.mjs](/Users/ccheever/projects/exact2/scripts/deploy.mjs:625)). "The compiler lowers a `table` to a grid" on native hosts therefore needs a `table` node kind that kernel/hosts interpret per platform — schema, accessibility (header association, `scope`), and placement work the §4 cost ("lowering to the grid") omits. The claim that `auto` grid tracks are what the table algorithm does is also wrong: CSS auto table layout weighs min/max content, spanning cells, and table width; grid auto tracks do not place `rowspan`-displaced cells. Resolve: carry table semantics in the plan, lower in kernel/host, and conform against Chrome on span-heavy fixtures.
3. **BLOCKER — D5: fragment in `Entry.url` changes router identity, unspecified.** Canonical equality currently decides same-screen, `go` dedup, and validity ([route/src/location.rs](/Users/ccheever/projects/exact2/route/src/location.rs:15) drops fragments; [1038 §3](/Users/ccheever/projects/exact2/llp/1038-router.rfc.md:162)). A fragment-only change would mint a new entry, losing scroll restoration and Back behaviour a browser gives `hashchange`. Percent-encoding, empty `#`, and `#top` (HTML scrolls to top; D5.2 scrolls nowhere) are also undefined. Resolve: define the fragment's canonical form and whether fragment-only navigation replaces, pushes, or is not an entry at all.
4. **MAJOR — D4 leaks by design and diverges at deploy.** Vite exposes only prefixed names (`VITE_…`) precisely because inlined values ship to every client; D4 inlines any `[A-Z][A-Z0-9_]*` from the process environment into web and native bundles with no "this is public" rule. Worse, `.env.local` is gitignored, so the sealed production bake cannot see it while a dev build can — same app, different origin. Resolve: a public prefix or an explicit declaration in `app.json`, values named public in docs, and the env source included in the bake's input digest with deploy refusing an unset name it cannot capture.
5. **MAJOR — D1's first-native step is not atomic, and two platforms do not exist as written.** Steps 1–3 write the workspace, crate, and manifest before step 4's setup check stops the build, leaving a half-native website; [dropPlatform](/Users/ccheever/projects/exact2/game/new.mjs:1285) shows the rollback standard this repo expects. Separately, `windows` is a game-only verb ([app-cli.mjs](/Users/ccheever/projects/exact2/scripts/app-cli.mjs:77)) and deploy knows only `web, ios, macos, linux` ([deploy.mjs](/Users/ccheever/projects/exact2/scripts/deploy.mjs:64)), so `deploy.store.android`/`windows` in step 3 would be refused. Resolve: write-then-check with rollback, and state Android's store key (Linux's) and Windows' verb, or defer Windows.
6. **MAJOR — D6: the name and the fallback are not CSS.** Tamber emits each token as `--x-<name>` ([1121 D7](/Users/ccheever/projects/exact2/llp/1121-tamber.rfc.md:652)), so `var(--ink)` is neither the web's custom property nor a runtime `var()`: it is a new token-reference syntax wearing CSS spelling, and it kills the runtime redefinition (`.dark`, a host page's stylesheet) that the benchmark's `tokens.css` relies on. The fallback rule inverts CSS too: `var(--x, fallback)` substitutes at computed-value time when the property is undefined or invalid, not at build with a warning — a typo then ships the fallback silently where the no-fallback form refuses. Resolve: either accept the real property name and keep `var()` runtime on the web, or spell it as a token reference and refuse unknown names with or without a fallback.
7. **MAJOR — D2.4 moves Harmony but does not say who compiles it.** After the move the sixth check no longer compiles Harmony's Apple/Linux crates, and "the async lane checks the new workspace as it checks `game/`" names no command, lane file, or owner; Harmony's `web/` crate stays in the root while its siblings join Snapback's workspace, splitting one app across two locks. Resolve: name the lane step and its trigger, and say how `resolveApp` follows the split (the `package.workspace` mechanism [1036.001 D4](/Users/ccheever/projects/exact2/llp/1036.001-apps-outside-the-repo.rfc.md:117) already relies on).
8. **MINOR — D8's `header` heuristic is a per-host plan divergence.** "A `header` holding a `nav` is drawn as written" on the web, but the same node is iOS's bar from the same plan; which host applies which rule, and what the kernel node carries, is unstated. Resolve: state it as a web-host presentation rule only, tested against the iOS bar for the same source.

## 6. The strongest alternative to D1

Keep today's full scaffold, and fix only the costs: `resolveApp` skips Cargo when no verb needs it, and `exact new` runs only the web's setup rows. The website keeps its files but stops paying resolution and setup time, and no app ever changes shape mid-life. **The measurement that decides:** run the Pokédex spec plus a "now add iOS" follow-up, five runs per arm; D1 wins only if the web arm's median cost/calls drop materially (say ≥25%) while the web→iOS arm adds no extra failure or recovery calls over the always-native arm. If the savings are mostly the 17 s setup check — fixable in the alternative — D1's two-state scaffold is apparatus for a one-line scoping change.

## 7. A gap the five runs would still hit

A setting supplied only when serving. Benchmarks and hosts commonly run `API_BASE_URL=… npm start` against a finished build; D4 bakes the value at build time and D3 serves a prebuilt directory, so that run either fails D4.3's unset refusal at build or serves the wrong origin — and the agent is back to rewriting a literal or rebuilding with the variable exported, the exact workaround §1 counted. The RFC should state which moment `API_BASE_URL` is allowed to arrive, and make `serve` refuse, or rebuild, when a baked name was unset at build.
