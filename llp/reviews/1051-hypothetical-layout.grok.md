## Review (verbatim)

**Verdict**

Right, with a major correction to the mechanism. App code should be able to ask, on the main thread and only from an action, where a node is or would be, and the answer should come from the engine that will actually commit: the kernel on native hosts, the browser on the web. That read must not feed the next layout. I would build that. The pass has to run beside the committed tree. Replaying an inverse through `txn::apply`, and replaying a batch through the web host's `apply`, both commit. The two patterns that already keep a trial off the live tree are `measure_height_targets` (swap derived heights, do not publish) and content-region trials (a separate engine tree). A static wall only needs a read of the committed frame; the collision driver is a separate admission.

I read the kernel and the web host at this checkout. The cited line numbers match. The physics arithmetic, the external survey, Preflex, the three velocity estimators, and the macOS hit-testing inference I took on trust.

**Major gaps or problems**

1. An inverse journal through `txn::apply` does not put the kernel back. That function is the only write path, and it is a commit: `alloc` bumps the slot generation, `free_slot` wipes the columns, and `revise_text` monotonically advances `text_serial`, which is the paragraph stamp the host measurer caches on. A destroy followed by a recreate yields a new `NodeKey`. A style write followed by an inverse write bumps the stamp twice, so a rolled-back what-if changes later text identity. `Kernel::apply` also bumps the epoch, stores a receipt, and notifies a content region; a what-if must not call it. Layout is a third store. `measure_height_targets` stays safe because it calls `engine.compute` rather than `publication::publish`, then `present_heights` dirties the nodes it touched. The tests at `presented_height.rs:1002` and `:1040` check `export()` equality and a clean next presented layout for that height swap only. Taffy's cache holds nine size answers and each leaf keeps sixteen offers; patch 11 exists because one hypothesis's entry was served for another. Writing those caches and then only re-dirtying a path can evict the live entries. The free-list order can also change, so the next real `CreateView` gets a different slot. The fix is to stop mutating the committed arena. A handler-time question can fork with `rehydrate` (it already rebuilds the engine from the columns). A drag-time question needs the side tree the RFC postpones to stage 2. Content-region trials already require that split: arena handles must never be indexed in a trial tree.

2. On the web, "apply the forward batch, force layout, apply the inverse" is unsound if the batch is the host commit batch. `apply` in `host/web/glue.js` pauses video, tears down motion and GPU state, sets `cssText` through `motion.style`, focuses, writes `localStorage`, starts fetches, commits collections, and jumps scroll. Its own comment says the runner has already committed, so a partial DOM is the worst outcome. That is the opposite of a speculative edit. `positionContexts` then writes geometry from the boxes it reads. Observers are the part the RFC gets right: the GPU `MutationObserver` checks `isConnected` when the microtask runs, so a same-task revert is invisible to it, and resize and intersection observers also run after the task. Scroll anchoring is not. Collection updates already set `overflowAnchor = "none"` because a temporary size change moves `scrollTop`, and restoring styles does not reliably restore it. Setting `transition: none` and putting the property back does not resume a CSS transition the host may have in flight. Committed geometry needs none of this: the agent `layout` path already reads `getBoundingClientRect` on the live tree. A counterfactual size is a saved inline style, a write, a read, and a restore, with scroll offsets snapshotted and anchoring suppressed for the pass. A counterfactual tree must not call `apply`. Nodes that are not in the document (unmounted rows, the next route) have no browser layout until they are inserted, and an inverse batch does not cover that.

3. The ball is the wrong load-bearing case, and it drags a forbidden driver into the layout design. With a static wall, the release handler needs the committed frame and a closed-form path. `SpringConfig::sample` already returns displacement and velocity. Layout at an arbitrary time matters when the wall's box comes from an animating layout property, which today means presented heights. `path()` is the decay-and-contact driver `rules/DEFERRED.md` refuses until a consumer is named and something else comes off. The photo release is a fair later consumer. It should not be in the order of work for making geometry readable, and the kernel design should not wait on it.

4. While a content region is registered, `layout_root_slot` refuses ordinary layout, which is the gate on `measure_height_targets`. Apple and Linux register that region for contained content before the first layout, and the trial runs on its own engine tree with the shell's children cut. Folding the height pass into a root what-if either keeps the refusal, so those screens cannot ask, or lays out the cut tree and returns the wrong box. The uses that want a size before paint sit on this path. The region trial is the existing what-if; an app-facing read has to go through it.

**What it gets right**

The constraint from exact1 is the right one: a geometry read inside a derive loops, and a read inside an action does not. Paint-only rows are the safe continuous channel. One native engine, with the browser as the web oracle and a second engine only as a checked predictor, matches "the web is the standard." `measure_height_targets` is the right seed for an offer-varying size, and it really publishes nothing. Naming all four shapes as one question is the right taxonomy. Refusing a ninth agent operation, a gesture arena, and container queries is right. Closed-form time, a rest rule, and step independence are the right requirements for anything that later shares the seekable clock. The frame-rate rest-position failure is real for steppers; springs already avoid it.

**Anything you would cut**

Cut the inverse-journal stage. Cut `path()`, moving-wall contact, and the single velocity estimator from this RFC; they can return with the photo release. Cut generalizing `PresentedHeight` to arbitrary rows until a second row has a consumer. The first surface is a committed `frame` read and the height measure that already exists, on native and as a live DOM read on the web.
