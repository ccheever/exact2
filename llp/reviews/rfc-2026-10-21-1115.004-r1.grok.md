## 5. If text differs at 100%, take DirectWrite's glyphs?

**Recommendation:** If a side-by-side at 100% on a 96 DPI display shows a difference a Windows user would notice, rasterize Windows glyphs with DirectWrite grayscale (`DWRITE_TEXT_ANTIALIAS_MODE_GRAYSCALE` on `IDWriteBitmapRenderTarget1`, premultiplied alpha), using Exact's glyph ids, advances, and variation coordinates, including one optical size. Keep Exact's shaping and layout.

**Confidence:** 68. Whether current WinUI 3 draws ClearType or grayscale was not verified, so the photographs still decide the mode.

**Reasoning:**
- The CPU painter already hints and already emits grayscale coverage: `hint(true)` and `Format::Alpha` (`host/linux/src/text/catalog.rs` lines 634–657). The gap is swash's hinter against DirectWrite, not an unhinted rasterizer.
- `IDWriteGlyphRunAnalysis::CreateAlphaTexture` returns a bi-level mask or a ClearType 3×1 texture. ClearType "is not suitable for rendering text onto a transparent intermediate bitmap" ([`DWRITE_TEXT_ANTIALIAS_MODE`](https://learn.microsoft.com/en-us/windows/win32/api/dwrite_1/ne-dwrite_1-dwrite_text_antialias_mode)). D4.3's premultiplied composition swap chain over Mica is that bitmap. Grayscale is the mode that composites.
- Segoe UI Variable's `opsz` axis is automatic when the font is used ([typography](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/typography)). Exact already sets optical size (the RFC cites LLP 1019 §13). The DirectWrite face has to receive those coordinates once, so the rasterizer does not apply a second optical size and break the advances layout already measured.
- Matching the WinUI reference matters more than matching GDI ClearType. If the reference app is grayscale, ClearType would be the tell.

**What would change it:** The S1 photographs at 100%, 125%, and 150%, over both a solid ground and Mica, show no difference a person who knows Windows would call out.

## Errors

1. **D6.3 says the painter rasterizes "unhinted."** `host/linux/src/text/catalog.rs` lines 634–657 call `.hint(true)` and the comment says the font's hinting programs run. The output is grayscale (`Format::Alpha`). This is the premise of Q5.

2. **D6.3 names `IDWriteGlyphRunAnalysis` as the glyph source.** That API's antialiased texture is ClearType 3×1. Microsoft documents ClearType as unsuitable for a transparent intermediate bitmap, and documents grayscale, via `IDWriteBitmapRenderTarget1`, as the mode that composites ([`DWRITE_TEXT_ANTIALIAS_MODE`](https://learn.microsoft.com/en-us/windows/win32/api/dwrite_1/ne-dwrite_1-dwrite_text_antialias_mode)). D4.3 requires that transparent surface. This bears on Q5.

3. **D3.6 says WinUI applies text scale to text only, not to the layout around it.** The current text-scaling page says controls and containers must resize and reflow, and it tells custom frameworks to handle hard-coded heights ([text scaling](https://learn.microsoft.com/en-us/windows/apps/develop/input/text-scaling)). The icon half is right: font icons are not scaled. This bears on M2.

4. **D6.2 treats Fluent sizes as "the text styles' Windows column."** The schema has no per-platform size column. Sizes are Apple's ramp at the root font size (`kernel/src/style/relative.rs` lines 181–188). Root 14 selects large-title 31, title1 25 (`schema.json` lines 6080–6114), not Title 28 and Subtitle 20. This bears on M2.

5. **S1 says Shelf's screens use a `select`.** The library and add-a-book form do not (`apps/shelf/app.contract` lines 213–371). They use text fields, a number field, buttons, lists, and segmented tabs. This bears on Q1.
