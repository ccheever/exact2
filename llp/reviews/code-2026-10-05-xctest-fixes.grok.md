**`4d9889d41`: no findings.**

`+1` on each axis is the right shape. `RasterDecodePlan.scaled` (`RasterImage.swift:256`) is already an integer ceil, and for this fixture it is exact: `256 × 100 / 256 = 25` with remainder 0, so the plan is `100×25`. ImageIO on this machine (macOS 27) returns one extra row only for HEIC, AVIF, and HLG when that planned short side is odd (`100×25` → `100×26`, `12×3` → `12×4`, up through `252×63` → `252×64`). Even planned heights match. The width never moves, and the error never exceeds one pixel. The 16-bit PQ PNG is exact at every size tried. Changing `scaled()` would desync the Swift plan from the Rust work size (`RasterLoader` requires `plan.width == work.width`), and it would be wrong for even heights and for the PNG.

The tolerance stays inside the budget on the path that actually fails. The `100×26` BT.2100 thumbnail is 10 bits per component, 32 bits per pixel, 400 bytes per row: `400 × 26 = 10400` bytes. The HDR plan reserves 8 bytes per pixel, so `plan.outputBytes` for `100×25` is 20800 and `scratchBytes` is about 168 KB. `decode` reports `plan.outputBytes` (`RasterImage.swift:338`), which `complete` accepts, and the retained buffer is under that charge. The staging check (`:327`) still rejects anything past `scratchBytes`.

SDR does not adopt the odd size. `isAdoptable` (`:437`) still requires `width == plan.width && height == plan.height`, `!plan.deep`, and `bytesPerRow <= plan.stride`, so a `+1` SDR thumbnail is redrawn into a context of exactly `plan.width × plan.height` (`:396`) backed by `plan.outputBytes`. The BT.2100 early return (`:388`) has to keep the `+1` thumbnail as ImageIO made it; drawing it into that context would store extended linear and drop the tone map. Layout uses `naturalSize`, so the one-pixel decode difference is stretched into the CSS box and the displayed aspect stays the file's.

One residual, not a defect on the measured files: the guard allows a thumbnail up to `(width+1) × (height+1)` as long as `bytesPerRow × height <= scratchBytes`, while the resident charge after `complete` drops scratch is still `plan.outputBytes`. A tightly packed 8-bytes-per-pixel BT.2100 image one row over would exceed that charge by one stride, and Swift would not report it. Every reproducing fixture here is 4 bytes per pixel and lands under `outputBytes`; the 16-bit PNG does not get the extra row.

No findings.

The HDR adoption in `RasterImage.normalized` is bounded by the charged buffer. A BT.2100 thumbnail is kept only when both sides are at most one pixel over the plan and `bytesPerRow * height` is at most `plan.outputBytes` (`RasterImage.swift:388-390`). Anything larger falls through `isAdoptable` (false for an HDR plan, which is 8 bytes per pixel) and is redrawn into a `plan.width` by `plan.height` bitmap of `plan.outputBytes`. `decode` still rejects an overflow or a thumbnail bigger than `scratchBytes` before that (`RasterImage.swift:323-328`). On this machine the 256×64 PQ HEIC at a 100-pixel cap is 100×26, 10-bit, 400 bytes per row, 10,400 bytes against a 20,800-byte charge, so it is kept and still inside the charge.
