## MATERIAL

1. **MATERIAL. One implementation instance cannot own both the view and the process-wide capture session.** D7 (lines 555–558) says a camera is one object whose view and calls share one instance, and D3 (lines 287–298, 365–369) puts one `AVCaptureSession` and one CameraX `ProcessCameraProvider` inside "the implementation" for the whole process, made at the first video track and stopped when no track holds a device. D8 item 1 (lines 599–607) tries to get there by handing the view the session's adapter. The seam does not work that way, and the proposal does not close the gap.

   On Apple the view factory receives the session's `ExactModule`, the app module, not the extension adapter (`host/apple/modules/ExactNativeModule.swift:996–1018`, and the typed factory at 1011–1018 refuses any other type). Adapters are created per session and keyed by that module (`host/apple/modules/ExactExtensions.swift:34–46`). `ExactExtensions.destroy` drops the map entry and calls nothing on the implementation (`:77–80`). Views are already gone when the session ends (`ExactNativeModule.swift:226–227`). A process-wide session stored on the per-session adapter dies with the first session, or lives in a static the view never sees. The sample host's two sessions (D3, lines 320–321) are two adapters.

   On Android the call object and the view object are different registries. `Extensions.made` is one `ExactExtension` per process and outlives activities (`host/android/canvas/src/main/java/dev/exact/canvas/Extensions.kt:11–12`, `:49–56`). Views are `exact.app.Modules` / `NativeModules` (`host/android/README.md:465–469`). D8 item 1's Android sentence only joins the roster to `exact.app.Modules`. It never hands the hosted view the extension instance. Apple's sentence and the web's sentence both do name that handoff. Android's does not.

   Stage 0 also omits `destroy`. Recording's D10 item 1 (`llp/1133.009-recording.rfc.md:607–610`) adds it so session end can finish the session's objects. Camera D3 says "the session's end ends it" and then has no call. D8 item 1 cites LLP 1133.001 D2 rule 3 for this sharing. That rule is about two import paths reaching one implementation (`llp/1133.001-modules-anyone-can-write.rfc.md:175–180`), not about a view and a process-wide device.

   **Resolve:** name two objects. A per-session adapter that the view factory and the calls share, and a process-scoped device owner that is not that adapter. On Android the hosted view is built by that same `ExactExtension`. Session end calls `destroy` on the adapter, which ends that session's tracks and drops the process object only when no session still holds a device.

2. **MATERIAL. What keeps the hardware on, and what happens when a second session arrives, are three different rules.** D3 states all of these at once (lines 313–339, 360–363):

   - A new track takes the camera. The other stays `live`, `muted` `in-use`, and "runs again when the taker's track is muted or ends," with no check that it still has a consumer.
   - "Two tracks on one camera share its input."
   - No consumer mutes the track `idle` and releases the device. Consumers are displayed viewfinders, an in-flight `takePhoto`, and a hatch output that says it consumes.
   - One displayed viewfinder per track, and a second Apple preview layer is blanked so the targets match CameraX, which binds one `Preview`.

   The hole: session A is showing camera 1, session B opens camera 2, so A becomes `in-use`. A's viewfinder then hides. B ends. "Runs again" restarts A's camera with no consumer. Same-camera "share" and different-camera "preempt" are both stated as the rule for "another track of the process."

   Blanking a second `AVCaptureVideoPreviewLayer` so Apple matches CameraX is a tell. Several preview layers on one `AVCaptureSession` are the documented use of that layer ([Setting up a capture session](https://developer.apple.com/documentation/avfoundation/setting-up-a-capture-session)). LLP 1133 D4 says an unsaid behavior is the platform's.

   Readers fight consumers. `mediaStreamTrack`, `enumerateDevices`, `cameraStatus`, and `getPhotoCapabilities` are live sources (D1, lines 156–162). The built seam calls `release(name)` when the last reader goes (`runner/src/runner/modules/bound.rs:99–116`, `host/web-js/modules.js:100–107`, `Extensions.kt:18–19`). Geolocation's D5 is explicit that the last reader's `release` stops acquisition (`llp/1133.002-geolocation.rfc.md:239–245`). The photo editor's camera screen can drop those readers while the viewfinder is still the thing that should hold the device, and drive 5 (`:791–793`) requires the same track to unmute later with no second `getUserMedia`. Following geolocation here ends the track. The RFC never says `release` on these facts does not.

   Recording's D6, which D3 says the lifetimes follow, is a third model: tracks per session, one capture per input device for the process, each session subscribed, and the engine "stopped when its last track ends" (`llp/1133.009-recording.rfc.md:356–366`, `:393–394`). That is sharing, not preemption, and the engine sentence is per session. Recording's consumers subscribe to buffers (`:285–291`). Camera's consumers attach outputs.

   **Resolve:** consumers own the device. Say that `release` on the fact sources does not end the track or release the camera, and that a displayed-state change calls `changed` so readers re-ask. A preempted track resumes only while it still has a consumer. Otherwise it stays `idle`. Sharing an input is for one track's preview and photo, not for two displayed previews. One displayed consumer of a camera device across the process. Do not cite recording's "engine stopped when its last track ends" as the camera's rule.

3. **MATERIAL. The substitute and admission are on opposite sides of a hole, on both runtimes.** §9 (lines 709–717) and D7's `"substitute": "implementation"` require the implementation to run under the agent (the card, the file copy, the idle mute, the tracks in `state.extensions`) while permission tickets stay in the runner (`tap @p allow`). Both runtimes do the opposite. Under the agent the host binds nothing and the declaration's substitute answers (`runner/src/runner/modules/bound.rs:1–6`). The web runtime returns null from `implementation()` when `clock.agent` is set (`host/web-js/modules.js:86–92`). Stage 0's drives 1–7 run under the agent (`:860–867`), so the object that is supposed to draw the card is never constructed.

   Binding the implementation so §9 can run hits the other side. A bound call returns before admission (`runner/src/runner/modules.rs:532–537`, "past this admission"). There is no `person-required` check anywhere in the runner or the hosts. Ticket origin is hardcoded `"origin": "app"` (`host/web-js/modules.js:194`). `state.extensions` is the runner's own table of `bound`, `preferred`, `readers`, and `held` (`runner/src/runner/modules.rs:938–954`, `host/web-js/modules.js:175`). §9 (lines 744–746) and drive 1 want tracks, settings, consumers, `muteReason`, and each viewfinder's displayed state. D8's eight items do not include this handoff.

   LLP 1133.006 D8 item 4 is a different split. There the implementation replaces the declaration entirely and writes a private store (`llp/1133.006-clipboard-items.rfc.md:350–356`). The clipboard has no permission ticket. Camera needs the runner's ticket and the implementation. Citing that item as this mechanism builds the wrong one. It is also unbuilt.

   **Resolve:** specify the handoff on both runtimes. The runner admits the grant and the origin, then dispatches to the implementation, including under the agent. Specify how the implementation's tracks are merged into `state.extensions`. Do not cite 1133.006 item 4 as this split.

4. **MATERIAL. The foreground-only rule does not cover the paths that start the camera.** D6 (lines 520–533) refuses `getUserMedia(video=)` and `takePhoto` to a tool and to a wake in every state, granted included. It then says a viewfinder's display asks nothing, and a displayed viewfinder of an `idle` track takes the camera again under the existing grant, with no call and no ticket. Drive 5 is that path. A tool that invokes the photo editor's show action, or any tool commit that displays the node, starts the camera. The runner already knows the origin of a commit (LLP 1133.002 D12). The displayed edge throws that away.

   The same hole is the return from background. D3 (lines 371–380) restarts at `interruptionEndedNotification` whenever the track still has a consumer. A wake that foregrounds an app whose viewfinder is still displayed starts the camera with no origin check. Recording refuses a capture start to a tool and a wake even when granted, and it does not let a tool reconfigure the capture (`llp/1133.009-recording.rfc.md:547–558`). Camera D6 explicitly lets a tool `applyConstraints`. D1 (lines 213–218) says writing `deviceId` or `facingMode` moves the track to another camera. A tool can retarget the next resume, including the one drive 5 performs with no new `getUserMedia`.

   **Resolve:** resuming from `idle`, from a background interruption, or from a constraint that changes the camera is a capture start. Carry the origin of the commit that displayed the view, or of the foreground transition. A tool or a wake leaves the track muted and does not take the device. A constraint change that would retarget the next person-started resume is itself refused with `person-required`.

5. **MATERIAL. The Android feature line does not disable the filter the RFC is trying to disable.** D6 (lines 481–487) adds only `android.hardware.camera.any` with `required="false"`, quoting the sentence that `CAMERA` implies `android.hardware.camera`. Google Play's implied features for `CAMERA` are `android.hardware.camera` and `android.hardware.camera.autofocus`. Declaring `camera.any` does not unset either. The documentation says to disable that filtering by declaring both of those with `required="false"`, and the large-screen block also wants `android.hardware.camera.flash` with `required="false"` ([`<uses-feature>`](https://developer.android.com/guide/topics/manifest/uses-feature-element), "Filter based on implicit features" and "Large screen support"). As written, a camera app is filtered from a device with only a front camera, and from a device whose camera has no autofocus. The manifest the host writes today is only `<uses-permission>` lines (`host/android/app/build.gradle.kts:69–77`), so this feature block is new and has to be right.

   **Resolve:** declare `android.hardware.camera`, `android.hardware.camera.autofocus`, and `android.hardware.camera.flash` as `required="false"`, along with `camera.any`.

6. **MATERIAL. Pinning CameraX's closure and refusing a duplicate class makes the camera unbuildable next to Compose.** D8 item 5 (lines 631–649) vendors the whole CameraX 1.6.2 closure as `{url, sha256}` file dependencies, including `androidx.lifecycle`, `androidx.core`, `androidx.appcompat`, and `androidx.fragment`, and refuses `bake-artifact-conflict` when a class is supplied twice. Question 4 (lines 905–914) treats the alternative as reversing a rule it quotes as "Gradle resolves nothing for a module."

   Compose already resolves AndroidX through Gradle when the plan has a date or time control (`host/android/app/build.gradle.kts:9–12`, `:92–97`). The date picker installs a `LifecycleRegistry`. A hard refusal means an app with a camera and a date picker does not build. Leaving lifecycle out of the closure means a camera-only app does not build. LLP 1133.001 D9 says prebuilt libraries are named and never resolved transitively, and that Kotlin is source in the one Android project whose repositories are Google and Maven Central (`llp/1133.001-modules-anyone-can-write.rfc.md:395–410`). "Nothing resolves it again" is about the module's own source, not a ban on the host's Gradle classpath. The quoted sentence in question 4 is stronger than D9.

   **Resolve:** one classpath. Gradle-resolve the CameraX coordinates in that Android project, locked and verified, aligned with the host's AndroidX. Drop the duplicate-class refusal as the rule. Do not vendor a second AndroidX.

7. **MATERIAL. The shared surface does not agree with LLP 1133.009 §3, and a capture track id does not agree with LLP 1133.003 D2.** Both RFCs say they must agree (`llp/1133.009-recording.rfc.md:298–301`; this RFC §11, lines 818–823, and question 1). They do not.

   Recording's consumers look a track up and subscribe to buffers (`llp/1133.009-recording.rfc.md:285–291`). `applyConstraints` and `getCapabilities` stay out until a consumer asks (`:838–839`). Audio input is `AVAudioEngine` and `AudioRecord`, not an `AVCaptureSession` (`:303–308`). The shared names include `setTrackEnabled` (`:263–265`). Camera §11 adds an attach point, `applyConstraints`, `capabilities`, `muteReason`, and video constraint members to that same surface. Camera's re-export list (D7, lines 568–570) omits `setTrackEnabled` while D1 says the camera re-exports the shared names. One `@exact/media-capture` cannot be built from both texts.

   The combined call is the same kind of hole. Camera D1 (lines 239–242) says `getUserMedia` with both `audio=` and `video=` opens one stream where the target can, then says stage 1 rejects it because §12 leaves it out. §12 (lines 841–842) names no error. Recording D3 describes the combined call as the shared behavior (`llp/1133.009-recording.rfc.md:292–296`) while its own D1 is audio only. A silent rejection and an opening are both in the pair of documents.

   The re-export mechanism is not LLP 1091. 1091 D3 is no `export` keyword, and every top-level declaration is importable (`llp/1091-contract-modules.rfc.md:111–118`). Its `package.json` `exports` map `.contract` paths. Neither RFC's `exact.json` `"reexports"` field exists, and camera D8 does not list teaching the bake that field. Recording makes the same citation (`llp/1133.009-recording.rfc.md:279–282`).

   LLP 1133.003 D2 says a live track id in `video srcObject=` plays (`llp/1133.003-video-decode.rfc.md:198–201`). Camera §12 (lines 843–844) says a camera track there waits until a frame door is public. If both kinds of track live in the one table 1133.009 D3 describes, the element resolves a capture-track id and plays it.

   **Resolve:** one shared-interface paragraph that both RFCs accept. Whether a video consumer attaches or subscribes, and whether `applyConstraints` and `getCapabilities` exist now. The combined call is `NotSupportedError` until a later RFC. Either re-export `setTrackEnabled` for video tracks or stop claiming the lists are the shared surface. Specify the bake feature that makes a name re-export real, and stop citing 1091 as if it were already that feature. A capture-track id in `video srcObject=` is refused, or shows the empty box. It does not play.

8. **MATERIAL. On the web, `enabled = false` does not stop the camera.** D3 (lines 332–336) and D10 (line 683) idle a web track by setting `enabled = false`, after which "a browser may release the camera," and the module reports `muted` with `muteReason` `idle`. Reason 1 (lines 343–348) is that a camera left running keeps the indicator on, which a person notices. Drive 5 requires `state.extensions` to show no device held.

   Setting `enabled` to false makes a video track output black frames. It does not set `muted`, and it does not end the track ([MediaStreamTrack.enabled](https://www.w3.org/TR/mediacapture-streams/#dom-mediastreamtrack-enabled), [MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/enabled)). Whether the user agent releases the device is optional ([w3c/mediacapture-main#961](https://github.com/w3c/mediacapture-main/issues/961)). Chromium, the conformance target in §10, keeps the indicator on until `stop()`. A stopped track cannot resume. The module already stops and reopens under the same id when `facingMode` changes (D1, lines 213–218), and a granted permission does not prompt again. The tier-1 cell should do that for idle too. Reporting `muted` while the browser track is not muted is a tell on the reference platform.

   **Resolve:** on a browser that does not release a disabled track, `stop()` the browser track when the last consumer goes, and open again under the same module id when a consumer returns. Report `muted` only when the track is muted.

9. **MATERIAL. The unsaid photo size is the settings object's smallest, and the RFC cites it as the photo output's default.** D2's photo-size row (line 255) says Apple's unsaid size is "the photo output's default `maxPhotoDimensions`, the smallest the format supports," and links `AVCapturePhotoSettings.maxPhotoDimensions`. That property defaults to the smallest dimensions in `supportedMaxPhotoDimensions` ([settings `maxPhotoDimensions`](https://developer.apple.com/documentation/avfoundation/avcapturephotosettings/maxphotodimensions)). `AVCapturePhotoOutput.maxPhotoDimensions` is a different property: the ceiling for the session, set before `startRunning`, and a per-capture settings value must be no larger than it ([output `maxPhotoDimensions`](https://developer.apple.com/documentation/avfoundation/avcapturephotooutput/maxphotodimensions)). The same D2 table already overrides the session preset from the API's `.high` to `.photo` because that is what a photo app sets (line 253). Leaving the size at the settings default ships the smallest still the format lists. A hand-built photo app sets the output ceiling to the format's largest before `startRunning` and requests that size ([WWDC26, high-resolution capture](https://developer.apple.com/videos/play/wwdc2026/304/)). D4's test is whether someone who knows the platform would notice. They would.

   **Resolve:** before `startRunning`, set the output's `maxPhotoDimensions` to the format's largest, or to the platform photo default. An omitted `imageWidth` and `imageHeight` means that size. The settings object's "smallest" default then does not apply.

10. **MATERIAL. The viewfinder's preview layer is attached on the session queue.** D3 (lines 293–297) runs `configure` on the session queue between `beginConfiguration` and `commitConfiguration`, and lists "a viewfinder's preview layer connection" as something a consumer adds there. D5's session hatch is on that same queue (line 442). `AVCaptureVideoPreviewLayer` is a `CALayer`. Apple's setup sample assigns `previewLayer.session` on the view, on the main thread ([Setting up a capture session](https://developer.apple.com/documentation/avfoundation/setting-up-a-capture-session), [AVCaptureVideoPreviewLayer](https://developer.apple.com/documentation/avfoundation/avcapturevideopreviewlayer)). Touching that layer off the main thread is the crash in [layoutSublayers on a background thread](https://developer.apple.com/forums/thread/650676). The RFC's own rule (lines 384–389) is that nothing on the session queue waits on main. A layer setter that hops to main, while main is `sync`ing the session queue to enter `configure`, is that deadlock.

    CameraX `bindToLifecycle` on the main thread (line 302) matches the API. That part can stand.

    **Resolve:** the session queue adds and removes inputs and outputs only. The viewfinder attaches and detaches its preview layer on the main thread, outside `configure`. Main does not `sync` to the session queue.

## MINOR

11. **MINOR. D3's sentence that Apple does not resume a session by itself is false for the background reason.** `videoDeviceNotAvailableInBackground` says that if the app does not call `stopRunning()`, the `startRunning()` request is preserved and the session starts running again when the app returns to the foreground ([videoDeviceNotAvailableInBackground](https://developer.apple.com/documentation/avfoundation/avcapturesession/interruptionreason/videodevicenotavailableinbackground)). Other reasons are not documented that way. Restarting again at `interruptionEnded` then double-starts, or fights a `stopRunning` the implementation issued so that finding 4's origin rule could hold. Fix the citation, and make the background path call `stopRunning` so the platform does not start the camera on its own. The restart, if any, is the capture start in finding 4.

12. **MINOR. Question 7's "Take: none" does not match what the RFC admits.** The 2026-10-02 move is an app native module, one object per session holding a preview and its calls, web, iOS, and macOS first (`rules/DEFERRED.md:768–775`). This RFC adds Android, two packages, and the eight seam items in D8, and D3 splits that one object into a per-session track and a process-wide session (finding 1). The question already lets Charlie name a take. The "none" answer should go.

13. **MINOR. D3's paraphrase of `displayed` is wider than the function it cites.** `runner/src/wakelock.rs:44–58` treats a node as hidden when it or an ancestor is `display: none`, when the slot's cover is `HostCover::Whole`, or when a navigation root hides the route. The comment at lines 1–7 says the screen a sheet covers stays shown. D3 (lines 325–328) says "wholly covered by its host." Implemented from the paraphrase, a sheet over the editor would stop a viewfinder that wakelock would still count as displayed. Use the function, including the sheet case.

## IMPLEMENTATION-PHASE

- Stripping location from the platform's EXIF.

- A `capturePhoto` settings hatch on main racing a configuration on the session queue.
- How long `app:/tmp/camera/` files live.
- What the tier-3 session hatch returns when the app asks for `AVCaptureMultiCamSession`, given one camera per process.

- Main-thread `bindToLifecycle` can jank. The RFC already puts it on main. Measure it. Do not move it off main.
