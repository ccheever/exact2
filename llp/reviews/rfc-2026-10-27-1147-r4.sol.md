Two fundamental host-mapping issues remain.

D1, D3–D6 and D10 hold up at the design level: the revised refusal handling, clock takeover, phase rules and explicit wasm fallback resolve the earlier objections. The existing JS live-clock tests pass 6/6.

1. **D7 mistakes the absence of an Exact animation callback for the absence of browser motion.**

   [D7’s web row](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:266) detects updates through requested `requestAnimationFrame` callbacks or scrolling. But Exact emits ordinary CSS animations that the browser runs independently ([emit.rs:780](/Users/admin/Developer/exact2-timer-wait-points/host/web-js/src/emit.rs:780)); its runtime frame loop is for frame tasks ([rt.js:357](/Users/admin/Developer/exact2-timer-wait-points/host/web-js/rt.js:357)). HTML processes animations independently of animation-frame callbacks. ([HTML rendering model](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model))

   Consider a three-second CSS animation, no scrolling and no frame task. At 800 ms, an `update` timer follows D7’s “otherwise at once” branch despite ongoing rendering. The same omission undermines idle’s motion/frame predicate: an `idle` save can qualify during the animation, before its cap. `requestIdleCallback` cannot repair that omission because it deliberately offers idle periods between animation frames. ([Idle-period specification](https://w3c.github.io/requestidlecallback/#idle-periods))

   **Instead:** Define browser activity to include CSS and Web Animations lifetimes, with completion and cancellation rechecks, and use it for both waits. Otherwise narrow the web promise explicitly; the current mapping does not provide D2’s motion exclusion.

2. **R4 moves Android’s release into the wrong frame callback for the default executor.**

   [D7](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:269) detects and releases `update` through `ExactView.turn`. Android normally runs the runtime on `Owner`; main-thread execution requires the comparison switch `owner=0` ([ExactActivity.kt:210](/Users/admin/Developer/exact2-timer-wait-points/host/android/canvas/src/main/java/dev/exact/canvas/ExactActivity.kt:210)). `Owner` has its own frame callback, which already calls `Native.displayFrame()` and produces the frame ([Owner.kt:410](/Users/admin/Developer/exact2-timer-wait-points/host/android/canvas/src/main/java/dev/exact/canvas/Owner.kt:410)). Choreographers belong to separate loopers; their callbacks do not establish a shared phase order. ([Android documentation](https://developer.android.com/reference/android/view/Choreographer))

   With an armed frame task, no scrolling and no layer animation, `Owner` can be producing frames while both named `ExactView` flags are false. D7 then runs the waiting timer immediately. Posting `ExactView.turn` instead also cannot guarantee release before the owner has executed Exact’s frame work. Thus r3’s ordering objection remains on the normal Android path.

   **Instead:** Define detection and release for both execution modes. In the default mode, integrate release before the owner’s frame work, and specify how eligibility is revalidated across the owner and main loopers; qualify the claimed ordering relative to main-thread input.
