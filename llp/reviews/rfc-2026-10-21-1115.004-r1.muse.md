## Q1 — D0: admit Windows for general apps?

**Recommendation:** Yes, but bounded: admit Shelf S1 only, with a named implementer, a Take (or explicit waiver) in [DEFERRED.md](/Users/ccheever/projects/exact2-wt-review-1115004/rules/DEFERRED.md:418), and the Q2 machine secured first. Do not grant open-ended "general parity."

**Confidence:** 70. Limited by: no owner or capacity is named anywhere I can check.

**Reasoning:**

- The bar today admits only Skirmish and Windows Desk. "General Windows control parity remains behind these two consumers" ([DEFERRED.md](/Users/ccheever/projects/exact2-wt-review-1115004/rules/DEFERRED.md:425)). D0 correctly needs Charlie's ruling (RFC D0).
- The RFC names no Take and no implementer (RFC header, §5 Q1). Android's admission was an explicit waiver ([DEFERRED.md](/Users/ccheever/projects/exact2-wt-review-1115004/rules/DEFERRED.md:428)), and its RFC named lanes and a five-day S1 ([1115.001](/Users/ccheever/projects/exact2-wt-review-1115004/llp/1115.001-no-tells-on-android.rfc.md:523)). Windows should meet the same bar.
- Shelf is the right consumer by precedent (Android S1, same screens). But Shelf has only `android/`, `apple/`, `web/` entries today. Caltrain has `linux/`. S0 must add a Windows entry for Shelf. RFC §3 S0 does not list it.
- The tells are real under LLP 1115's test. `sans-serif` resolves to Arial ([fonts.rs](/Users/ccheever/projects/exact2-wt-review-1115004/host/linux/src/text/fonts.rs:105), [catalog.rs](/Users/ccheever/projects/exact2-wt-review-1115004/host/linux/src/text/catalog.rs:833)). The title bar stays light. No `Preferences` are set. A Windows user notices all three.

**What would change my answer:** No reachable Windows 11 machine or no named implementer when S0 is scheduled. Then defer D0. An admitted host with no lane is how D17 happened.

## Q2 — Which machine runs the oracle and agent?

**Recommendation:** One dedicated physical x64 Windows 11 machine (22621+) is the oracle of record, with a 100%-scale display and a precision touchpad. A VM may run headless agent regression. It must never sign off D4, D6.3, D8, or D11.

**Confidence:** 90. Limited by: I have not seen the Studio's actual configuration.

**Reasoning:**

- Microsoft: apps are "not rounded when… running in a Virtual Machine (VM), by design" ([Microsoft Learn, rounded corners](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/ui/apply-rounded-corners)). A VM cannot verify D4.5 at all.
- Mica falls back to solid on low-end hardware, Battery Saver, and deactivation ([Microsoft Learn, Mica](https://learn.microsoft.com/en-us/windows/apps/design/style/mica)). A paravirtual GPU risks exactly that fallback, silently. D4.2/D4.3 would pass against the fallback, not Mica.
- D6.3's decision needs photographs at 100% on a 96 DPI display (RFC D6.3). VM/RDP scaling destroys that measurement.
- The Studio is Apple-silicon, so a Windows VM there is ARM64 (from memory; not stated in this repo). The RFC sizes everything in x64 (D2, §5 Q4) and parks ARM in §4. An ARM oracle cannot validate x64 runtime size or first-frame cost.
- Narrator (D11), the touch keyboard and dictation (D7), and touchpad inertia (D8) need real HID at least once. The agent typing through the IME path (D13) does not replace that.

**What would change my answer:** A VM that demonstrably passes a DWM checklist — rounded corners present, Mica live (not fallback), DirectComposition presenting, 1:1 pixels at 100%. Then it is provisional, with a physical re-check before the S1 gate.

## Q3 — Header into the title bar?

**Recommendation:** Agree: system title bar first. Reject the coupling to the Mac. Decide the custom title bar on Windows evidence at the end of S2. The default stays "system" unless that evidence calls it a tell.

**Confidence:** 80. Limited by: "most WinUI apps" (RFC D4.4) is asserted, not counted.

**Reasoning:**

- D4.1 (dark caption) plus D4.2 (Mica) remove the actual tell — a white bar over a dark app — without owning the non-client area.
- The custom bar's costs are in the RFC itself: `WM_NCHITTEST`/`HTMAXBUTTON` for Snap Layouts, drag regions, caption glyphs (D4.4). Contrast-theme caption buttons and RTL add more (that detail is from memory, unverified here).
- Waiting for the Mac serialises two hosts. The Mac's structure is its own document ([1115.000 §4](/Users/ccheever/projects/exact2-wt-review-1115004/llp/1115.000-no-tells-on-every-host.rfc.md:907)). Android's lesson (D11) is to share the header-*shape* rule. It is not to share a schedule.
- Under LLP 1115, an unsaid header is the platform's. The system title bar is the platform's. A custom bar is a design choice, not correctness.

**What would change my answer:** S1 side-by-sides against the WinUI reference where Windows users identify Exact as foreign specifically by the title bar. Then promote S4.

## Q4 — Hosted WinUI date/time picker?

**Recommendation:** Do not pre-authorise. Default is No. Revisit only if S2's oracle shows a *behavioural* failure painting cannot fix, for a named shipping consumer. Any island then ships as an opt-in per-app crate, never a host requirement.

**Confidence:** 75. Limited by: the 48.7 MB / ~54 MB figures are the RFC's NuGet reading (Appendix A). I did not re-measure them.

**Reasoning:**

- It breaks D2's winning argument — no runtime beyond the OS — for two controls. Every user of any app containing one date field pays it (§5 Q4).
- An island is a native child HWND. The host must manage "input, focus, and deployment" and "verify accessibility… across the host and island" ([Microsoft Learn, XAML Islands](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/host-controls-existing-desktop-apps)). That cuts directly against D11's single-tree Narrator gate.
- The Rust gap is real but narrower than the RFC states (see Errors). Either way, a C#/C++ wrapper enters the build ([windows-rs #3404](https://github.com/microsoft/windows-rs/issues/3404)).
- The Android analogy fails on cost. Android D9 uses the framework's `DatePickerDialog`, already on the device ([1115.001 D9](/Users/ccheever/projects/exact2-wt-review-1115004/llp/1115.001-no-tells-on-android.rfc.md:388)). Windows has no in-box Fluent picker. "Loaded by use" there meant zero shipped bytes.
- Islands "don't require package identity by themselves," but the host must deploy the runtime correctly, via bootstrapper in unpackaged apps ([Microsoft Learn, XAML Islands](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/host-controls-existing-desktop-apps)). Servicing that runtime becomes Exact's support problem.

**What would change my answer:** A measured oracle failure in keyboard, Narrator, or locale behaviour — not pixels — that painting cannot close, blocking a named app.

## Q5 — DirectWrite glyphs if rendering differs at 100%?

**Recommendation:** Reject the unconditional "yes." Measure first, on corrected premises. Adopt DirectWrite only if photographs plus an advance-width audit prove swash is the delta, and then only grayscale textures behind a layout-agreement gate. Never ClearType over Mica.

**Confidence:** 80. Limited by: nothing here was run on Windows (RFC §1 says the same). No screenshots exist yet.

**Reasoning:**

- The premise is wrong. The painter hints: `.hint(true)` ([catalog.rs](/Users/ccheever/projects/exact2-wt-review-1115004/host/linux/src/text/catalog.rs:642)), with `Format::Alpha` grayscale masks ([catalog.rs](/Users/ccheever/projects/exact2-wt-review-1115004/host/linux/src/text/catalog.rs:651)). D6.3's "unhinted" misdiagnoses where a difference would come from.
- DirectWrite antialiasing "may be either ClearType or grayscale depending on the text antialiasing mode" ([Microsoft Learn, DWRITE_RENDERING_MODE1](https://learn.microsoft.com/en-us/windows/win32/api/dwrite_3/ne-dwrite_3-dwrite_rendering_mode1)). D6.3 assumes the WinUI reference is ClearType without reading its pixels. S0 must check for colour fringes first.
- D4.3 composites premultiplied alpha over Mica. Subpixel masks need a known opaque background. Microsoft's documented transparent-text path is grayscale ([Microsoft Learn, Rendering DirectWrite](https://learn.microsoft.com/en-us/windows/win32/DirectWrite/rendering-directwrite)). ClearType on D4.3's surface would fringe (inference from those two facts).
- "Keep shaping and layout" (D6.3) is not free. Hinting moves ink and can move advances. Glyph placements here come from the rendered image itself ([catalog.rs](/Users/ccheever/projects/exact2-wt-review-1115004/host/linux/src/text/catalog.rs:664)). Swash advances with DirectWrite ink risks clipping. That needs an audit, not an assertion.
- Variation coordinates already reach the scaler ([catalog.rs](/Users/ccheever/projects/exact2-wt-review-1115004/host/linux/src/text/catalog.rs:643)). Cheaper knobs (hinting behaviour, gamma, `opsz`) are untested before a second rasteriser.

**What would change my answer:** Matched size/weight/gamma photographs at 100% where Exact is still visibly softer, and a DirectWrite-grayscale prototype that matches the reference with no advance drift beyond oracle tolerance.

## Errors

1. **D6.3, "unhinted" (bears on Q5).** Wrong. The scaler is built with `.hint(true)` ([catalog.rs](/Users/ccheever/projects/exact2-wt-review-1115004/host/linux/src/text/catalog.rs:642)). Grayscale is right (`Format::Alpha`, line 651; subpixel masks collapsed at line 743). The S0 photographs will be interpreted against a false baseline.

2. **D6.3, the ClearType premise (bears on Q5).** "Windows renders Segoe UI through DirectWrite, with ClearType where the person has it on" assumes the reference's mode. Microsoft documents the mode as a choice: ClearType or grayscale ([DWRITE_RENDERING_MODE1](https://learn.microsoft.com/en-us/windows/win32/api/dwrite_3/ne-dwrite_3-dwrite_rendering_mode1)). Which one the WinUI reference uses is unmeasured. Q5 cannot be answered until it is.

3. **§5 Q2's VM parenthetical (bears on Q2).** It asks only whether the VM's GPU "can present a DirectComposition swap chain." That omits the disqualifying facts: no rounded corners in a VM by design ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/ui/apply-rounded-corners)), and Mica's solid fallback on low-end hardware ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/design/style/mica)). Note D4.3's related claim is correct: per-pixel alpha layering does block rounding, per the same Microsoft page.

4. **D3.6's mechanism claim (bears on Q1/S1).** Scaling the root font size is not "text only" in Exact. It also scales every `rem`/`em` metric, and the schema's metric lengths come in `px`, `em`, and `rem` kinds ([1115.000 D17](/Users/ccheever/projects/exact2-wt-review-1115004/llp/1115.000-no-tells-on-every-host.rfc.md:874)). WinUI keeps fixed-DIP padding (e.g. D12's button padding) while containers "resize and reflow" around larger text, and font icons must not scale ([Microsoft Learn, text scaling](https://learn.microsoft.com/en-us/windows/apps/develop/input/text-scaling)). At 200% text size, Exact-by-root and the reference will differ. The S1 oracle must include a non-100% text-scale specimen, or the gate will miss it.

5. **D2/§5 Q4 on windows-rs (bears on Q4).** Overstated. [Issue #3404](https://github.com/microsoft/windows-rs/issues/3404) is titled "Support composable classes with overridable methods." The maintainer's refusal covers that feature, with the workaround being a C#/C++ non-composable wrapper. "Does not project `Microsoft.UI.Xaml`" reads as total. The practical consequence for Q4 stands (glue is required), but the cost estimate should be for a narrow wrapper, not an absent projection.
