## What holds

An import's source does not reach the shared serve. `import` is not forwarded: `importHeld` builds the child request (`scripts/tamber-server.mjs:1108`). `import-plan` is not in `METHODS` (`scripts/tamber-server.mjs:112`, `:590`), and the serve accepts it only when `marks` is an array (`contract/cli/src/tamber_serve.rs:642`). That call is `ask({ method: 'import-plan', marks: ops })` (`scripts/tamber-server.mjs:995`). `ops` are the held proposal's operations, or a subset chosen by index. `reimport` is set only by the server (`:1113`, copied at `:983`). `plan` returns on the marks branch before it reads `source`, `sources`, or `baseline` (`contract/cli/src/tamber_import.rs:197-210`). The importer code does not spawn and does not read the filesystem; the only extra read is kept baselines beside the design.

A stop settles the promise immediately, clears the timer and the interval (`scripts/tamber-isolate.mjs:80-92`), and `finally` drops the queue slot (`:54`). A child that closes its pipes and keeps running is still answered at the deadline, because `close` waits for exit and the timer does not. Spawn failure emits `close` as well as `error`, so a missing binary does not stick the chain. The group kill refuses a pid of 0 or 1 (`:89`). A late probe sees `settled` and does not signal (`:102`).

On the wire, `reply.status` is the HTTP status (`scripts/tamber-server.mjs:599`), so 413 and 503 stay 413 and 503 with `{error:{message}}`. A planner `{error}` with no status is 400. `importHeld` retries only when `held.error.conflict && tries < 2` (`:1113`): three planning attempts, then the conflict is returned. A 413 or 503 from `planAlone` returns immediately (`:1109`).

The design path is not interpolated into the shell. On Linux the script is `ulimit -v ${kb} && exec "$0" "$@"` with the binary and the path as later argv (`scripts/tamber-isolate.mjs:33`). `kb` is `LIMITS.rssKb * 4` (4 GiB of address space). The `contract` binary uses the system allocator (no jemalloc in `contract/cli`). Four times resident is a backstop for an allocator that reserves ahead of RSS, and it is inherited across `fork`/`exec`, so a `rustc` grandchild is inside it. It is a wide ceiling: a child that touches pages can reach about 4 GiB RSS if the sampler is late.

`QUEUE.md` now calls `budget.rs` a partial second layer and carries both round-5 leftovers, including marks still running in the serve on server-built operations.

## Should-fix

**The resident sample can miss a large allocation, and on macOS nothing else stops it.** `scripts/tamber-isolate.mjs:37-39`, `:97-106`, `:24-33`.

`ps -o rss= -p <pid>` is the leader only, the first sample is 50 ms after start, and the next sample waits out the in-flight `ps` (up to its 1 s timeout). RSS excludes swapped pages. The steady-state planner does not fork, so once `target/debug/contract` is the child, the sample is the allocator. Two holes remain. The cargo fallback (`:26`) is `sh`/`cargo` while `rustc` is a grandchild: this run had no debug binary, and the real-planner test was killed at 10.0 s, so a cold tree never finishes the compile inside the watchdog and every attempt is 10 s of `rustc`. On Linux `ulimit -v` still caps that tree. On macOS the grandchild is uncapped until the group kill. A fast allocator in the leader is also observed a sample late; a `ps` that takes most of its 1 s timeout is a full second with no sample.

Fix: sum `ps -o rss=,vsz= -g <pgid>`, start the first probe immediately, and keep one sample of headroom under the 1 GiB target. If the debug binary is missing, fail the import in one line instead of compiling inside the 10 s clock. Keep the Linux `ulimit` as the backstop.

**A design open that does not return pins the only queue, and the 10 s clock has not started.** `scripts/tamber-isolate.mjs:60-70`, `:53`. `scripts/tamber-server.mjs:123-127`, called at `:1108`.

`designText` `realpath`s, then `open`s, and only then checks `isFile()` and size. `open` of a FIFO waits until some writer connects, on the thread pool, and that promise is the head of `last`. `waitMs` was already checked. The watchdog starts in `planOnce`, after this read. Every later import waits behind it. The same call path still does a synchronous `readFileSync` of `app.json` in `designPath` on the event loop, before the queue check; a FIFO there stalls timers for an import that is already running. An HTTP client cannot name this path. Replacing the design file, or `app.json`, on disk can.

`readFile` also reads to EOF (`:69`). The serve publishes the design by rename, so the open fd stays on the old inode; a writer that extends that same inode is not capped at 4 MiB.

Fix: `lstat` (or `stat` the real path) and accept only a regular file, then open that descriptor and `read` at most `designBytes`. Put a deadline on `designText` that settles the queue the same way `stop` does. Read `app.json` asynchronously, or with the same regular-file check.

**ENOENT still drops the digest guard.** `scripts/tamber-server.mjs:1112`. `contract/cli/src/tamber_import.rs:186-189`.

A missing design plans against `tamber app\n` with a null digest, and `hold` is called with no file precondition. `propose` does not treat a missing digest as "this path must still be absent", and the snapshot digest it returns becomes the proposal's base. A design that appears in that window is what a later accept applies those ops to. Other read errors correctly return 500 and do not plan (`scripts/tamber-isolate.mjs:72`).

Fix: when the read is ENOENT, require the design path to still be absent at `propose`. Re-read `designPath` once, at the start of the turn, and use that same path for the guard.

**One client can keep the planner busy for as long as they keep sending.** `scripts/tamber-isolate.mjs:41-55`. `scripts/tamber-server.mjs:1106-1113`.

The cap is real: one running, four waiting, each dropped after 30 s, and a full queue is an immediate 503. Slots free when a job finishes, and nothing ties a slot to a client or cancels it when the socket closes. One paired client can refill those five slots indefinitely. Other methods are not on this chain. Each HTTP import plans at most three times, and only on a digest conflict.

Fix: one outstanding import per client (a second from the same client gets 503), and drop a queued job if its request has already ended.

**A `ps` failure at exit turns a finished plan into 503.** `scripts/tamber-isolate.mjs:100-104`, `:115-119`.

Any `ps` error, including "no such process", stops the import. `close` is what parses a good stdout, and `stop` settles first, so a probe in flight as the planner exits wins the race and discards the answer. The other direction fails open: exit 0 with non-numeric stdout becomes `Number(out) || 0`, which is under the limit for that sample.

Fix: if the child has exited, or stdout parses, keep that answer. Treat a null sample as unwatchable only while the child is still running. Treat non-numeric stdout as null.

**Marks reloads every kept baseline into the shared serve, then ignores them.** `contract/cli/src/tamber_serve.rs:642-645`. `contract/cli/src/tamber_export.rs:160-172`.

`kept()` is called before `plan`, and the marks branch returns without using `kept`. Each file is read with `read_to_string` and no total cap. `read_dir` follows a symlink directory; a symlink file is skipped (`file_type().is_file()`). A partial accept of a re-import is enough to trigger it. The child read of the same files is the right place, and it is watched.

Fix: on the marks branch, do not call `kept()`. In `kept()`, refuse a symlink directory and cap the total bytes.

**Local Astryx still plans outside the watchdog.** `scripts/tamber-server.mjs:1457-1458`.

`kind === 'astryx'` uses `spawnSync('cargo', …, { maxBuffer: 64 << 20, timeout: 120_000 })`. No resident stop, and 120 s rather than 10 s. The wire rejects Astryx (`contract/cli/src/tamber_import.rs:213-215`); this is `bun exact.mjs tamber import` on the same machine. `sourcesOf` (`scripts/tamber-isolate.mjs:129-136`) also reads the source in that process, with `readFileSync`, before the child exists.

Fix: run the Astryx planner under the same group kill and resident sample, with a longer clock if the install needs it, and cap the source read.

## Nits

**`ulimit -v` sets the soft limit only.** `scripts/tamber-isolate.mjs:33`. A child can `setrlimit` the soft limit back up to an unlimited hard limit. The planner does not. Set both: `ulimit -H -v ${kb} && ulimit -S -v ${kb}`.

**The serve does not reject a source that rides along with marks.** `contract/cli/src/tamber_serve.rs:642`. `plan` ignores `source` / `sources` / `baseline` when `marks` is set, and the wire does not send them. Refuse those keys on that branch so a later caller cannot put a document back in that process.

**The tests lock the stub, not the boundary that fails open.** `scripts/tamber-isolate.test.mjs:37-78`. Covered: direct-child allocation to 413, time, a blind probe, a 2-waiting queue, a symlink out of the app, a character split across chunks. Not covered: `ps` on a grandchild or on `cargo`, a `ps` that returns after exit, `vsz`, a FIFO or a non-ENOENT read error, `waitMs`, group death rather than the leader's pipes closing, HTTP 413/503, three conflict retries, and a 413 that does not retry. The real-planner case currently fails closed in 10 s whenever the debug binary is absent, so it does not show that a plan matches the serve.

Round 1's blockers are fixed: stdout stops at 2 MiB (`scripts/tamber-isolate.mjs:109-111`), stderr is a 2,000-character tail (`:113`), and the queue refuses past four waiters (`:50`).
