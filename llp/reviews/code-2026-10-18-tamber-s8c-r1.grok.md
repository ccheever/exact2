## SHOULD-FIX

**`judge()` does not implement theme2's best-effort rule.** The ruling is ΔE00 > 3 from the authored colour and nearer that colour than the platform default is (ΔE(measured, authored) < ΔE(platform, authored)); otherwise `none`. The tool requires four pixels with ΔE(measured, plain pixel) > 1 and ΔE(measured, authored) < ΔE(measured, plain pixel) (`scripts/measure-controls.mjs:11-14`, `:139-146`). A partial tint that moves toward the author but stays closer to the platform pixel is `none` here and `best-effort` under the ruling. The same loop's blend starts at t = 0 (`:143`), so any pixel within ΔE00 3 of the plain pixel or the modal ground is treated as the rival's colour; a shift of ΔE00 ≤ 3 off the platform pixel can never count. `exact` is "≥ 4 pixels within ΔE00 3" with no comparison to the plain build (`:134`), so a platform default already inside that band would count as exact. The doc repeats this predicate (`docs/control-roles-measured.md:10-14`), and the test's best-effort sample passes the stricter bisector (`scripts/measure-controls.test.mjs:36-40`), so it does not lock the ruling. Landed measured cells sit at ΔE00 0–0.6 with thousands of pixels, or at 18–35 with zero close pixels, so this does not flip the current table.

**Sampling the inset node frame misses accent the reader draws outside it.** `pixels()` takes `space.viewport` inset by one point (`scripts/measure-controls.mjs:108-116`) and the fixture never opens the select. On the reader, `menu()` fills the chosen row with the accent after the walk, outside the node (`host/linux/src/paint/control.rs:307-338`); the neutral menu does not. `select`/`accent-color` is `none` on Android for "the painted menu button draws no accent" (`kernel/tables/schema.json:5801`). That is true of the closed button and of the Linux painter. It is false of the reader's open menu, and a `--reader` re-run of this sampler would still report `none`. The same frame drops Mac chrome that is centred at natural size, or a button bezel laid out with `frame(forAlignmentRect:)` (`host/apple/Sources/ExactKit/Mac/ControlsMac.swift:180-196`). The landed Mac accent cells were taken from code (`docs/control-roles-measured.md:31`), so this did not write them; the next key-window run of the tool can.

**macOS `field`/`Field` = `none` is wrong for a textarea.** The measured control is a single-line input, and that view draws no background (`host/apple/Sources/ExactKit/Mac/NodeViewMac.swift:840-841`), which matches the cell (`kernel/tables/schema.json:5804`). A Mac textarea sets both the scroll view and the text view background from the `Field` role (`host/apple/Sources/ExactKit/Mac/TextAreaMac.swift:313-316`). One `field` row makes the lint say the role is unreachable on macOS textareas.

## NIT

**`none` and `best-effort` need not carry a why.** `validate_controls` accepts a cell with no `: ` (`kernel/build/validate.rs:259-264`). The comment above it, the schema comment (`kernel/tables/schema.json:5794`), and stage 8 (`llp/1121-tamber.rfc.md:3427`) all say the why is part of the cell. Every such cell in this table has one. `write_controls` stores `""` when it is absent (`kernel/build/codec.rs:777`), so the lint would emit an empty reason.

**The Mac column is `mac` in the schema comment and the RFC, and `"macos"` in `CONTROL_HOSTS` (`kernel/build/codec.rs:761`).** The array is positional and `"macos"` matches the compiler's host name. A lint that looks up the RFC's `"mac"` misses the column.
