# Review: LLP 1054.000.003 r3, "Dates, numbers and durations in the roster"

## Assessment

r3 is much better than r2. The linking now follows the router precedent, and it works in the code as it stands: `RunnerLinks`, `exact_web::Linked`, `web_linked`, the bake and the native hosts all boot as described. The scope is cut to entries that have callers. Every citation I checked points at the right lines. Every Intl output it quotes matches Bun 1.4.2 / ICU 78.1. I could not check the Node 26.9.0 claims because Node isn't installed here.

The formatters themselves (D1–D3, D6–D10) are ready to build. The new live-label mechanism (D5) is sound in outline: one deadline, one generation input, a wake through `timer_due_ms`. It fits the runner's dependency machinery. But it has five correctness gaps the RFC doesn't see:
- `"static"` depends on when the runner happens to re-evaluate, not on its inputs.
- `set_time` can finish without committing anything, so labels that are waiting for the date stay blank.
- The refusal rule it prescribes causes a wake loop every frame.
- Rounding the deadline breaks "incremental equals full".
- The wall time drifts after the device sleeps.

Each has a local fix. None requires a new approach.

## Concerns

### BLOCKER: `"static"` depends on when the runner re-evaluates, not on its inputs

A static label shows the relative time "at the commit that evaluates its site". In this runner, that isn't well defined.

- **It breaks the runner's reference invariant.** LLP 1005 §8 says an incremental update must equal a full one:
  - `set_full_evaluation` "makes every site stale" (`llp/1005-plan-and-runner-v1.spec.md:418`).
  - Settlement never keeps a value in full mode (`runner/src/runner/settlement.rs:183`, `.filter(|_| !self.full …)`).
  - So a static label refreshes on every commit in full mode and never in incremental mode. The two modes produce different trees.
  - `runner/tests/it/incremental.rs` runs every app plan both ways in lockstep, but it never calls `set_time`. Every label would be `""` there, so the test would pass anyway and miss the difference.
- **It depends on the host's row window.** In a virtualized list, the label refreshes whenever its row remounts. Which rows stay mounted (overscan, bounded row lifetime) is each host's geometry policy. So the same source can show different text on web and iOS after the same scroll. `rules/DEFERRED.md:281` already rules on this: "state that must survive scrolling lives in keyed data."
- **It uses a stale clock (see the MINOR on the runner clock below).** The runner's clock moves only in `advance_within` (`commit.rs:204, 260, 288`). A reply or a tap commits at whatever time the runner last advanced to (`host/web/src/host.rs:538, 1170`). In an app with no armed timer, a static label on a row that arrives later is computed against launch time. Nothing ever corrects it.

**To resolve:**
- Either make static a pure function of explicit data: `thenMs` plus a reference instant the app holds, such as a `loadedAt` slot that an action sets. That is deterministic, needs no per-row runtime state, and can be baked.
- Or hold `"static"` until it has a caller (next concern but one).
- Either way, delete the test "static … fresh when its row remounts".

### MATERIAL: `set_time` commits nothing unless the plan declares an `exactTime` resource

- D5.1/D5.2 say a label is blank until the date arrives, and that the `wall` input then "fills in" the blank label.
- But `set_time` only re-asks resources whose source is `exactTime` (`runner/src/runner/time.rs:68-71`). With none of them, `recommit` returns `Ok(None)` and runs no commit at all (`settlement.rs:55-57`).
- `formatRelativeTime` reads the runner's `WallTime` directly, so it doesn't need an `exactTime` resource. A plan that calls it without declaring one would therefore show `""` forever.
- A blank label reports no boundary, so there is no wake either. The labels fill only if some unrelated commit happens later.
- The RFC's own example and its test fixture both declare `time`, so neither would catch this.

**To resolve:** have `set_time` commit when the plan contains any relative call (the scan already knows this). Add a test with no `exactTime` resource.

### MATERIAL: restoring `label_due` on a refused label commit causes a loop every frame

- D5.7 says "a refused commit restores" `label_due` and the generation. For a refused label wake, that puts `label_due` back at or before `now`.
- `timer_due_ms` then reports a deadline that is already due. The web wakes the next frame (`host/web/timer-glue.js:6-7`), the label step runs and is refused again, and this repeats every frame. It also fills the 4,096-line journal.
- Timers avoid this by using up their deadline before they run:
  - a timer's `next_ms` is advanced before `run_action` and isn't in the commit checkpoint (`commit.rs:16-28, 259-260`);
  - `then_due` is set to ∞ before its action runs (`commit.rs:205`).

**To resolve:** a label wake is used up in the same way. On refusal, `label_due` becomes ∞ (or at least `now` + 1 s). Restore only when a non-label commit is refused.

### MATERIAL: round only the wake, not the bump

- D5.3 rounds each reported boundary up to a whole second before it goes into `label_due`. D5.4 bumps only when `now ≥ label_due`.
- Take a commit landing between the true boundary `b` and `ceil(b)`, for example the 250 ms timer or a `clock` seek. Incremental mode keeps the old text there. Full mode prints the new text. That is the same divergence as the static case.

**To resolve:**
- Keep the exact boundary for the bump, and round only the value `timer_due_ms` reports. The wake still coalesces to at most one per second.
- With that change, live labels agree between the two modes, because a later evaluation never reports an earlier boundary.
- Also give the lockstep test a `WallTime`, so it covers this mechanism.

### MATERIAL: "hosts don't change" doesn't hold for live labels; the wall time drifts after the device sleeps

- The label's wall time is `epochAtZero + now()`.
- On Apple, `now()` is `CACurrentMediaTime()` (`host/apple/Sources/ExactKit/Session.swift:69`), which stops while the device sleeps.
- Hosts tell the time only at boot (`Session.swift:582, 660`; `host/web/glue.js:1300`; `host/linux/src/app.rs:303`).
- LLP 1027.000.000 D2's re-tell on clock or zone change (`NSSystemClockDidChange`; "Linux: at resume") was never built. Nothing in `host/apple/Sources` subscribes to those notifications.
- Result: after an iPhone has been locked for an hour, every live label is an hour young until the app relaunches. A daylight-saving change during a session also leaves the offset stale.
- Bluesky's current derive has the same flaw. But this RFC's promise is that labels "keep up", so it has to say how.

**To resolve:**
- Hosts re-tell the time on foreground or resume and on system clock or zone changes. On the web, `visibilitychange` would do. `set_time` already ignores drift under a second.
- List these host changes in D5.6 and in Costs.

### MATERIAL: `"narrow"` means something else on the web

- In Bun, `new Intl.RelativeTimeFormat('en-US', {style:'narrow'}).format(-5,'minute')` gives `5m ago`. r3's `formatRelativeTime(t, "narrow", …)` prints `5m`.
- A web author would reasonably expect the Intl meaning. The Refused table already reserves "`… ago` (`Intl.RelativeTimeFormat`)" for later, so this name would be taken.

**To resolve:** name the style or the entry after what it prints, and leave `formatRelativeTime` + `"narrow"` free for Intl's meaning. Two options:
- a style such as `"elapsed"`;
- an entry such as `formatElapsed(thenMs, update)`.

### MINOR: `"second"` and `"static"` have no call site

- `format.json:883` says "entries are added by fixture, never by speculation."
- Every call in the RFC uses `"minute"`, and open question 2 recommends `"minute"` for Bluesky.
- Charlie's direction ("prob have an option…") could serve as the fixture, but then say so in the row's `_comment`.
- Otherwise: land the `update` argument with `"minute"` only, and add the other two values when a caller appears. That also sidesteps the BLOCKER above.

### MINOR: the runner's clock is stale outside `advance`

- D5.4 says "an answer, a tap" can absorb the wake. They can't: those commits happen at the runner's last advanced time (`host.rs:538, 1170`), which is never past `label_due`.
- Live labels do correct themselves. A label computed from a stale Δ has its next boundary at or before real `now`, so the host wakes on the next frame and fixes it. The cost is one extra commit per reply after an idle stretch.
- Fix the text. Optionally, have hosts advance the runner to their own clock before they deliver an event or a reply; `resize` already does this at `host.rs:689`.

### MINOR: the mode scan relies on the literal sitting right before the `Call`

- That holds for current lowering, including inside a `fn`: a `fn` binds its arguments as locals, and the literal stays inside the body (`contract/lower/src/expr.rs:215-250`).
- But "a plan is never trusted" (`runner/src/vm.rs:460`). Specify that when the instruction before the `Call` isn't a `Str`, the scan treats the call as live, and that the VM checks the `update` value at run time.
- A cleaner option: declare literal-enum parameters in `format.json`, so D9's check is driven by the table rather than a special case in the compiler.

### MINOR: the examples compile only with shapes the document doesn't show

- Checked with the release CLI (`contract build`).
- Verbatim, the "today" example fails: `[type-unknown] unknown type 'Time'` and the same for `Post`.
- With the shapes added:
  - "today" compiles to 1 slot, 1 derive, 2 resources, 1 action;
  - the r3 example compiles to 0 slots, 2 resources, using stand-in `fn`s of the form `fn formatDate(t: number, o: number, s: string): string = "x"`.
- Show the shapes, or say they are omitted.

### MINOR: costs and measurement

- "Caltrain links nothing new" is true of the `format` bodies. It isn't true of D5's machinery (the two dependency bits, the bump, the advance step), which is core and so in every app. Check it against `WEB_CORE_KIB` (Caltrain's ceiling is 303, `scripts/metrics.mjs:755`).
- The proposed metrics row `/^exact_runner::format::/` misses a top-level `exact_runner::format` module; the neighbouring rows anchor with `$`. Use `/^exact_runner::format(::|$)/`.

### MINOR: two test claims don't match the behavior

- "`+86400000` … one label commit": this holds only when no timer sends a request. The agent's jump stops after each timer that sends (`advance_until_request`, `glue.js:1183-1188`). In Bluesky, the 30 s `tick` asks `unread` and `newPosts` again, so there is one label commit per `advance` call.
- The driven check's "no `query` line for a feed" should name `feeds`, because `newPosts` is legitimately asked within `+60000`.

### MINOR: RealWorld's `"long"` date

- `apps/realworld/app.ts:22-25` formats with `getMonth()`, `getDate()` and `getFullYear()`: the browser's own local zone, correct across daylight saving.
- Moving it to a fixed offset taken at launch is a small regression for dates near midnight on the other side of a DST change.

### MINOR: no date

"Implementer and date" gives "starting on Charlie's acceptance", but RULES asks for a date.

## Suggestions

- **Land in two steps.** First D1–D3, D6–D10 and the Caltrain migration: pure formatters that are ready now. Then D4/D5, with the fixes above.
- **Coarser wakes for `"minute"`.** Coalesce minute-mode wakes to about 10–15 s instead of 1 s. That caps idle wakes at 4–6 a minute on iOS, however many rows are mounted. Today's Bluesky labels are up to 60 s late anyway.
- **Use offset zones in the oracle.** Intl accepts them directly: Bun gives `{timeZone:"+05:45"}` → `Sep 26, 2026 at 6:47 PM`. The oracle can compare against Intl with the same offset instead of shifting to UTC, and D6 can say that a fixed offset is a web time zone.
- **Show the label deadline in `state`.** For example `state.time.labelDue` and the generation. It's a field on an existing read, not a new operation.
- **For SwiftUI parity:** `Text(date, style: .relative)` is also live by default, which supports r3's default.

## Answers to r3's open questions

1. **A third argument, or styles like `"narrow-second"`?** Keep the explicit, literal third argument. It reads plainly, it can be grepped, and the compiler can check it. Declare its values in the table and change the style name (the `"narrow"` concern).
2. **Bluesky under a minute?** Use `"minute"`. Today's `42s` is computed against a clock floored to the minute, so it's already wrong by up to a minute. `now` is honest, and it costs no wakes every second.
3. **What does "static" mean?** Not as r3 defines it: that version changes with the evaluation schedule, the host's row window and a stale clock (the BLOCKER). If Charlie wants static, make it a pure function of `thenMs` and a reference instant the app holds in keyed data. That is deterministic and needs no per-row runtime state. Otherwise hold it until a caller exists.
4. **RealWorld's `"long"`?** Drop it until RealWorld actually migrates. If it does migrate, record the daylight-saving regression (MINOR above).

## Verdict

**BUILD WITH CHANGES.** The formatters, the linking and the Caltrain migration can be built as written. Before D5 lands:
- redefine or hold `"static"`;
- have `set_time` commit whenever the plan has a relative call;
- use up a refused label wake the way a timer is used up;
- bump on the exact boundary and round only the wake;
- have hosts re-tell the time on resume;
- rename `"narrow"`.
