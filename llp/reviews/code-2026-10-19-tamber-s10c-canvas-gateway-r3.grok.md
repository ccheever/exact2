## Security pass

1. **Tokens, grants, sessions.** `randomBytes(32)` is 256 bits for the grant and the session (`scripts/tamber-canvas.mjs:321`, `:349`). Grant and session checks are SHA-256 then `timingSafeEqual` (`:111–112`, `:346`, `:366`). The grant is deleted before the success checks (`:345`), so a second try fails, and it expires at 30 s (`GRANT_MS`, `:346`). `mint` puts the grant in the JSON body; the entry URL is `/canvas/<client>/` with no secret (`:325`). Any query on the entry is 404 before the body is read (`:330`). Logs are client name and reason only (`:290`). Errors are fixed strings. The pairing token is taken from `x-exact-tamber-token` (`scripts/tamber-server.mjs:479`) and is never read from `Cookie`.

2. **Cookie.** `Set-Cookie` is `__Host-exact-canvas=<id>; Secure; HttpOnly; SameSite=Strict; Path=/` with no Domain (`scripts/tamber-canvas.mjs:356`). The value is only a key into the server map; `sessionOf` then re-checks `lookup` (`:361–369`). A value this process did not mint is not a session. The pairing token is 64 hex characters and fails the 43-character session check. Up to four same-name cookies are tried and the first live one wins (`:201–202`, `:362`), so a tossed value beside the real one does not hide it. Overwriting or deleting the real cookie yields 404, which forces a new grant. Page code on the tool port gets nothing from this cookie: the tool’s principal is the header only (`scripts/tamber-server.mjs:469–479`), and `remoteHandler` drops `Cookie`. Browser enforcement of `Secure` and the two-port toss wait on B’s TLS port; the header and the map are what this tree can show.

3. **CSRF / origin.** The entry requires `Origin` to be exactly the canvas origin or `toolOrigin` (`:332–333`). A proxied POST requires `Origin` to be exactly the canvas origin (`:389`). No CORS header is set, and `access-control-*` is dropped (`:437`). `SameSite=Strict` withholds the cookie on a cross-site request. A same-site POST from the tool origin fails the canvas-origin check.

4. **`forwarded` mark.** (a) `forwarded` is in `DROP_UP`, every `x-forwarded-*` is dropped by prefix, and `Connection`-named headers are dropped; the gateway then sets `forwarded: for="_exact-canvas"` (`:407–421`). (b) `developmentGate` treats any `forwarded` or `x-forwarded-*` as forwarding (`scripts/install-page.mjs:288`), including a loopback peer and a loopback Host. Both dev servers call `gate.check` before a route. Bun’s `fetch` delivered that marker in a loopback probe. `/__tamber` and `/__tamber/*` are `needs` null (`scripts/tamber-canvas.mjs:101`), so they are never fetched. The JS loop copies the marker when it forwards to the resident (`host/web-js/dev.mjs:1013`).

5. **Header and URL leaks.** Upstream drops `Cookie`, `x-exact-tamber-token`, `Referer`, and the client’s forwarding headers (`:77`, `:411`). Downstream drops `Set-Cookie` (`:78`). The probe and the address tests show (1) the loop’s own HTTP origin rewritten in headers and, by `JSON.parse`, in JSON; (2) other obvious loopback authorities (`localhost`, `127/8`, `[::1]`, any port, including `127.1` and `[::ffff:127.0.0.1]`) replaced with `loopback.invalid`; (3) `evil.test`, `192.168.1.20`, and `127.0.0.1.example.test` left byte for byte, including a JSON document that contains no loopback. `http://127.0.0.1%2F@evil.test/a` parses as `evil.test` and is unchanged. `Accept-Encoding` from the client is dropped; the dev loops do not gzip. `Range` is dropped, so a rewritten body is not a slice.

6. **Routes and scopes.** `read`: GET/HEAD outside `/__` and `/.exact`, the `READS` paths, `/__dev/generation/`, `/__dev/map/`, `/modules/`, GET `/__dev/design`, and the four beacons. `write`: POST `/__dev/design`, `/__dev/checkpoint`, `/__dev/open`, and GET/HEAD `/__dev/open` (`:99–108`). The raw-request test for the old bypasses got 404 and an empty upstream log.

## Findings

1. **NIT** — `scripts/tamber-canvas.mjs:149` and `:254`. `new URL('https://127.0.0.1:443').port` is `''`, and `port || '80'` then treats the loop’s own `https://127.0.0.1` as a foreign loopback, so it becomes `loopback.invalid` instead of the canvas origin. The HTTP dev loop, including port 80, rewrites correctly (probe and the test at `scripts/tamber-canvas.test.mjs:663`). Fix: default an empty port from the scheme (`https:` / `wss:` → `443`, otherwise `80`) in both places.

2. **NIT** — `scripts/tamber-remote.mjs:270`. Dormant until B attaches the canvas handler. `addPort` 403s when `Origin`’s host:port is not the canvas port, and the tool’s origin is that same host on the other port. The tool’s grant POST, which `enter` is written to accept, would never reach it. Fix: do not apply that check on the canvas port; `enter` and the proxied-POST check are the origin rule. `addPort` already leaves `Cookie` in place, which is what the session needs.
