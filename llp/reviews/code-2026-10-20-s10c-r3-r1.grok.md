## Should-fix

- **Revocation does not cut every connection.** `scripts/tamber-relay-server.mjs:334` only `clearTimeout`s each waiter. The wait object is `{give, timer}` and does not keep the socket, so the paused client stays open with no deadline, still holding the ClientHello. `ended` (`:314`) ignores `waiting`, and `byName` keeps accepting new clients until grace. TXT is handled in `record` (`:262`) before the socket is added to `conns` (`:301`), so reload never destroys it. `dnsHook` (`scripts/tamber-relay.mjs:129`, default 300s) has no abort, so a publish started before the revoke still completes.
- **Resource limits don’t bound what an attacker can hold.** `perMinute` (`scripts/tamber-relay-server.mjs:130`) never deletes keys. Refusal IPs and `session+ip` client keys live for the process life; an IPv6 source can grow both maps without limit. Idle connector sockets are appended with no cap (`:310`). `streamsPerSession` is checked only against `carried` (`:209`); waiters (`:224`) are not counted, and flushing a waiter (`:308`) does not check the cap again. Hello and greeting each have a 10s deadline and a size cap (`:183`, `:239`), but there is no cap on how many of those an IP may hold at once.
- **The refusal string matches; the work does not.** `scripts/tamber-relay-server.mjs:250` returns before `holds` (`:127`) when the label is missing or revoked, so a wrong token is the only case that hashes. `timingSafeEqual` is used only after that.
- **A replaced accounts file is watched once.** `fs.watch` on the file (`:346`) emits `rename` when the CLI’s `rename` (`:420`) replaces the inode, then the watch drops. The first revoke is read; a later one waits on SIGHUP. The CLI tells the operator the running relay will cut connections when it next reads the file (`:423`).
- **Logs keep a full IPv4 when the peer is IPv4-mapped.** `masked` (`:145`) only rewrites a dotted quad. `::ffff:a.b.c.d` takes the v6 branch and keeps all four octets. The `CLIENT` line already strips that prefix (`:215`).
- **After grace, or a relay restart, the same run is wedged.** The relay mints new names for the same run id. The connector destroys any `READY` whose names are not the ones it already accepted (`scripts/tamber-relay.mjs:276`) and dials again, which clears grace (`scripts/tamber-relay-server.mjs:297`) and keeps the new names alive. The process never accepts them. Restarting `tamber serve` is the only recovery.
