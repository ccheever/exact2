## Findings

**1. HIGH — T3 is not an open gap.** Upstream 0.14 already sizes an auto-width replaced block to its intrinsic width, and the kernel test pins that.

`vendor/taffy/src/compute/block.rs:1215-1219` sets `known_dimensions` to `Size::NONE` for a replaced element and cites CSS 2.2’s intrinsic width. `kernel/tests/it/image.rs:263-288` asserts a 320×120 image in a 390-wide block stays 320×120, with the comment that 0.14 removed the old stretch. `vendor/taffy/EXACT-PATCHES.md:82-84` and `:148-150` say the same, and `:263` says LLP 1001’s declaration is obsolete. LLP 1001 still states the deviation at `llp/1001-kernel-v1.spec.md:428-431`. The RFC followed that paragraph.

`block.rs:1279-1281` is not the remaining bug. That comment is about the float-avoidance inset when the width is still unknown (`unwrap_or(stretch_width)`). The used width is already the measure result. `image.rs:334-336` still calls the block case “the deviation”; that comment is stale relative to the assertion at line 287.

Drop T3 from the tranche. Correct LLP 1001. Do not change `image.rs` except to delete the stale comment.

**2. HIGH — T1’s route A, and “delete the paint-order rule,” break behavior the RFC does not name.** The web does not run Taffy. `host/web/glue.js:1030-1031` says the kernel’s layout never runs on the web; the browser is the page. `host/web/src/layers.rs` forces `position: relative` so the browser imitates the kernel: containing blocks, and tree-order paint (`host/web/tests/it/host.rs:1349-1352`). Native hosts then paint differently from that CSS. Linux walks boxes in tree order and does not read `z_index` (`host/linux/src/paint.rs:340`). AppKit and UIKit set `layer.zPosition` from `z_index` with no position check (`host/apple/Sources/ExactKit/Mac/NodeViewMac.swift:1097`). Deleting the web rule makes the browser use CSS Appendix E while native stays on tree order plus a raw z-position. That is a new split, not the removal of LLP 1001’s deviation.

Parent-relative coordinates do not survive scrolling. Route A lays the absolute out against the containing block and converts the result back into the parent’s coordinates (`llp/1074-css-taffy-lacks.rfc.md:77`). Hosts scroll by translating a scrollport’s descendants. CSS does not scroll an absolute whose containing block is outside the scrollport, and it does not clip it to an intermediate `overflow` that is not the containing block. After the conversion, the host scrolls it anyway. Route B’s note about overflow being attributed to the wrong box until a fixup (`block.rs:752` unions absolute overflow into the parent) is the same bug, one pass later.

The list claim is false. Windowed lists do not place rows absolutely. Unmounted ranges are in-flow spacers (`runner/src/instance/collection/views.rs:104-164`), and `validate_row` rejects `position` other than `relative` and rejects non-zero insets (`views.rs:207-217`). What patch 9 actually depends on is `boundary_style` (`kernel/src/layout.rs:131-141`): the box must be `Position::Relative` and clip both axes. A `static` default makes every scrollport fail that predicate, so list replay stops, even if no row is absolute. A hoisted absolute whose containing block sits outside the scrollport also escapes the boundary patch 9 was built to keep local (`EXACT-PATCHES.md:327-341`).

Insets without `position` change pixels too. Today the default is `relative` (`kernel/tables/schema.json:1305-1310`, `vendor/taffy/src/style/mod.rs:305-318`), so `top` and `z-index` apply. The web host adds `position: relative` whenever insets or `z-index` are set (`layers.rs:100-106`). `static` ignores both. Messages already writes `position="relative"` for a fractional `top` (`apps/messages/app.contract:776-778`). Anything that sets `top` or `z-index` alone stops moving. Canvas also gets its own `position: relative` (`host/web/src/element.rs:23-26`), separate from the paint rule; deleting only `layers.rs` leaves that, which is correct and unmentioned.

The cache-key warning is overstated, and the double caller is the real hazard. Patch 11 already keys on `parent_size` (`vendor/taffy/src/tree/cache.rs:83-94`). If the only layout call passes the containing block’s size as `parent_size`, no new key field is required. If the unpositioned parent also calls `perform_child_layout`, it stores an entry against the wrong box. Route A has to make sure that call does not happen.

Resolve this in the design round before any patch: one caller, containing-block size as `parent_size`, grid areas preserved (finding 3), host scroll and clip defined for an absolute whose containing block is not the scrollport, `boundary_style` treating `static` as in-flow, and a native paint rule for `z-index` and Appendix E in the same landing as deleting `layers.rs`. The migration sweep is every absolute’s containing block plus every node with insets or `z-index` and no `position`, not only “absolute means my parent.”

**3. MEDIUM — Route A against “the padding box” is the wrong containing block, and there is no better third route.** Three concrete mismatches:

- A grid that is the containing block positions an absolute against the grid area from `grid-column` and `grid-row` (`vendor/taffy/src/compute/grid/mod.rs:682-796`), not against the padding box. Hoisting every absolute to the ancestor’s padding box drops that path. If the grid is not the containing block, those lines do not form the area, and the static position is the hypothetical grid area mapped into the real containing block.
- Only block layout records a static position (`block.rs:1009-1014` and `:1395-1403`) and uses it when both insets are auto (`block.rs:1814-1828`). Flex, with both insets auto, aligns with `justify-content` (`flexbox.rs:3000-3058`). Grid uses the alignment offset (`alignment.rs:486-498`). CSS places that box at the hypothetical in-flow position. Copying today’s flex or grid fallback into the hoist will not match Chrome even after containing blocks are right. The section 2 probe never sets both insets to auto, so it does not show this.
- A scrollport is not a containing block for `absolute` or `fixed`. The proposal body says scroll containers are still to be decided (`1074:70`). Open question 3 does not list them. Treating `overflow` as a containing block makes native disagree with the browser, which is the split this tree exists to avoid. `overflow: hidden` on textflow’s pages (`apps/textflow/app.contract:94`) clips in-flow content; it must not capture absolutes whose `position: relative` ancestor is outside.

Route B lays the subtree out twice, leaves overflow on the wrong box until the fixup, and stacks a second fixed point on `LayoutTree::settle_flow` (`llp/1043.000-text-around-shapes.rfc.md:632-640`). That interaction is real. Reparenting in the kernel for the duration of layout is not a third route: `set_children` dirties the node (`layout.rs:515-521`) and throws away patch 9’s replay record. A corrected route A, inside Taffy, with a single caller and the grid-area path kept when the grid is the containing block, is the one to design. A block-only spike will look healthier than the engine is, because block is the only algorithm that already stores `static_position`.

**4. MEDIUM — T4’s grid bug is real; both the “cheap” fix and the root recommendation are wrong.**

For an absolute grid item with both insets set, `align_item_within_area` expands auto margins and then ignores them. The offset uses `non_auto_margin`, which turns auto into 0 (`alignment.rs:443-453` and `:486-493`). That is the measured x = 0. In-flow items use `resolved_margin`. Swapping to that value is still wrong when the insets are not zero: `free_space` is the grid area minus the border box (`alignment.rs:445`) and does not subtract the insets. CSS solves `left + margin-left + width + margin-right + right = containing-block width`. Block layout already does that (`block.rs:1743-1810`). Port that equation. It stays a small patch.

The root bug is also real. `compute_root_layout` resolves margins with `resolve_or_zero` and then skips auto margins (`compute/mod.rs:139-168`, the TODO at line 166), so a 100-wide root offered 400 sits at x = 0. Fixing it does not let the `taffy_style` special case go. That special case rewrites a root `width: auto` to `100%` (`kernel/src/style.rs:1368-1376`) because Taffy does not stretch a root. CSS 2.1 §10.3.3 is a different equation: if the width is auto, auto margins become 0 and the width stretches; if the width is definite, auto margins split the leftover. The comment at `style.rs:1374` says root margins are not subtracted. Keep the width rewrite. Fix root auto margins only for a definite width, as its own Chrome case, not as the condition for deleting `taffy_style`.

**5. MEDIUM — T5 is a real limit and the wrong schedule.** `BlockContext` offsets are provisional. `EXACT-PATCHES.md:164-192` records the same three probes the RFC cites (y 100→90, x 0→50, y 110→150), and `block.rs:1278-1329` measures the child before `y_margin_offset` and auto margins are resolved. “Medium” matches that note.

Auto-height flow does not wait on it. LLP 1043 stage 2 shipped a bounded re-layout under a block-only restriction, with no Taffy change (`1043.000:625-643`). `EXACT-PATCHES.md:189-192` says the vendor diff for that is still zero. `QUEUE.md:226-233` still lists stable offsets as owed; that line is older than stage 2. Building T5 now would add a second source of truth next to `settle_flow`. Leave it until someone needs to lift stage 2’s restriction (only blocks, exclusions with point `top` and `height`). Do not staff it as “whoever next works on text flow.”

**6. MEDIUM — The baseline correction misreads the comment, and T2 is not uniformly small.**

`alignment.rs:460` treats `Baseline` as start on both axes. `align_item_within_area` is the function used for x and for y (`alignment.rs:363-379`). Block-axis alignment of definite items works through `baseline_shim`, an extra top margin, computed in `resolve_item_baselines` (`track_sizing.rs:541-545`) only when the inline-axis track-sizing pass is told there is a baseline item (`grid/mod.rs:317-336`). The block-axis pass passes `false` (`grid/mod.rs:357` and `:543`). For two empty definite boxes, the missing first baseline falls back to the border-box height (`track_sizing.rs:525`), so shims of 20 and 0 reproduce y = 20, 0. The measured agreement can be true. “The comment covers the inline axis” is not. Row sizes still do not grow from baselines. T6 remains a real gap: `AlignItemsKeyword` has only `Baseline` (`style/alignment.rs:24-54`), and the kernel writes `Baselines::from_first` (`kernel/src/layout.rs:954`), which sets `last: None` (`vendor/taffy/src/tree/layout.rs:184-185`).

T2’s list matches patch 12 (`EXACT-PATCHES.md:484-487`): absolute boxes, grid items, a flex or grid container’s own ratio (`flexbox.rs:248-263`, `compute/mod.rs:86-100`), and the inline-axis automatic minimum. Item paths already call `sizes_through_ratio` (`block.rs:801`, `flexbox.rs:799`). Absolute, root, and the container’s own ratio are call-site work. Grid items are not small: track sizing and a ratio are cyclic, which is why patch 12 left them. “Four paths, small, one tranche” oversells the grid item and the min-content width transfer.

**7. LOW — Section 4 is true; section 5’s citations are not; one schema gap is missing.**

`grid_template_areas` and the line-name vectors exist (`style/mod.rs:755`, resolution in `compute/grid/types/named.rs`). `style/grid.rs:414` says “Named tracks are not implemented,” and the next variant is `NamedLine` (`grid.rs:427-435`). The comment is stale. `placement.rs:452` is one unit test that does not feed names, not a claim that resolution is unimplemented. Differential cases before exposing it are still the right gate.

`safe` and `unsafe` are applied, not merely stored: `resolve_self_alignment_safety` (`compute/common/alignment.rs:11-16`) and the flex item path (`flexbox.rs:2385`). Schema `JustifyContent` and `AlignItems` have no `safe` value (`schema.json:1258-1289`). LLP 1054.000.001 does propose `safe center` (`1054.000.001:174-176`).

`display: flow-root` is a real display mode. `is_block` is false for it (`style/mod.rs:97-101` and `:871-872`), and the tree dispatches it to block layout with no `BlockContext`, so it is a new block formatting context (`tree/taffy_tree.rs:403`). Schema `Display` is `block | flex | grid | none` (`schema.json:1332-1339`). The web host already appends `display:flow-root` on a block root (`element.rs:30-42`) so the margin does not collapse through to the page. That is the same class of host hack as the paint rule, and section 4 does not say so.

`BoxGenerationMode` is only `Normal` and `None` (`style/mod.rs:280-283`). `display: contents` is correctly excluded.

`flexbox.rs:451` is the `visibility: collapse` TODO. `flexbox.rs:1097` is the vertical-writing-mode TODO. Neither line is subgrid or tables. Subgrid appears only as a comment in `compute/grid/types/named.rs:125`. There is no table layout mode. `item_is_table` exists and only stops stretch (`block.rs:1215-1218`). Floats are disabled on purpose (`EXACT-PATCHES.md:10-11`). Inline layout is rightly a separate RFC. Those exclusions are fine. What section 4 misses, and what an RTL-aware framework actually needs, is `start`, `end`, `self-start`, and `self-end`. Taffy has them (`AlignItemsKeyword` at `alignment.rs:26-50`, `AlignContentKeyword` at `:68-71`) and the schema’s alignment enums do not.

`overflow: auto` is not a hidden Taffy feature. The enum is `Visible`, `Clip`, `Hidden`, `Scroll` (`style/mod.rs:371-386`). The kernel documents that `scroll` stands in for `auto` and forces `scrollbar_width` to 0 (`kernel/src/style.rs:1216-1231`). `Clip` is in Taffy and not in the schema; it is a smaller miss than `start`/`end`.

## Open questions

**1. Yes, `static` should be the default.** CSS and the web-is-the-standard rule say so, and the browser already lays the web out that way. There should be no compatibility mode. “Every app breaks” is the right sweep assumption and too coarse as a description: textflow, spark, and reflow already put `position="relative"` on the boxes that hold their absolute children, and Messages already sets `relative` so a fractional `top` applies. The sweep has to add `relative` both to the containing block of every absolute and to every node that has insets or `z-index` and no `position`. I did not walk apps outside this checkout.

**2. Corrected route A, not B, and not a kernel reparent.** B double-layouts, mis-attributes overflow, and fights `settle_flow`. Reparenting from the kernel dirties patch 9. A is tolerable only if the containing block’s size is the existing `parent_size`, the unpositioned parent does not also lay the child out, a grid containing block keeps its grid-area path, static position is the hypothetical in-flow position, and hosts do not scroll or clip an absolute whose containing block is outside the scrollport. A block-only spike will not show whether patches 9 and 11 survive.

**3. The properties the web host emits that CSS actually makes into containing blocks.** That is `position` other than `static`, `translate`, `scale`, and `rotate` (the browser already contains on those; LLP 1002 D2), `filter`, and `backdrop-filter`. Not `overflow`. Not opacity, `z-index`, `clip-path`, isolation, or `mix-blend-mode` (stacking contexts, not containing blocks). `contain: size` on a canvas is a host CSS hack, and that canvas is also forced to `position: relative`. `will-change` and `container-type` are not kernel rows.

**4. Yes, `fixed` should land with route A.** Its containing block is the viewport except where the same transform, filter, and backdrop-filter list captures it. The hoist is the same code. `sticky` stays a host scroll-time behavior and should not be in this change.

**5. Fix a definite-width root’s auto margins if you want the measured case. Do not expect that to delete the `width: auto` rewrite.** A root that is offered its own size and has `width: auto` never shows the margin bug. The two rules are different. The width rewrite stays.

**6. Do not make “send them upstream” part of the coding tranche.** The headings that say “to upstream” are patches 10, 11, 12, 14, and 17. The inventory does not record a pull request, and I did not look outside the checkout. Write T2 and T4 as upstream-shaped patches with Chrome cases and an `EXACT-PATCHES.md` entry. Sending them is a separate step.
