## Review (verbatim)

I'll audit the SVG completion RFC against the binding rules and the code it builds on, staying inside this checkout and reading the documents first.The RFC is in hand. ## What §1 leaves out, and what it gets wrong

§1 is a fair inventory of LLP 1055's refusals. It is not a complete SVG 2 plus CSS list. These are absent and should be either specified or refused by name:

- Elements Chrome does not implement, so they should be refused, not silently dropped: `hatch` / `hatchpath`, `mesh` / `meshgradient`, `solidcolor`. Also `switch` (and `systemLanguage` / `requiredExtensions`), `view`, and `metadata`. `metadata` must not paint.
- `color-interpolation` on gradients and the root (initial **sRGB**). This is not `color-interpolation-filters` (initial **linearRGB**). D14 only has the latter.
- `shape-rendering` (chart code uses `crispEdges`), `text-rendering`, `image-rendering`.
- `overflow` on inner `svg`, `marker`, `pattern`, and `symbol`. The root already defaults to hidden (LLP 1055 D3). Inner viewports need the same UA default or they will not clip.
- `direction` and `unicode-bidi` for RTL labels. Vertical `writing-mode` is refused; horizontal is never stated.
- `text-decoration` and its longhands on SVG text. `inline-size` (the SVG 2 property that actually wraps text).
- `pointer-events: bounding-box`.
- 3D transform functions (`matrix3d`, `rotateX`/`rotateY`, `perspective`). Chrome applies them to SVG elements. The grammar in D5 is 2D only and does not say 3D is refused.
- External `url(...)` (a paint server, filter, or mask in another file). Refuse it.
- SMIL `end`, begin-lists, and `attributeName="points"` (see D16).

The sharp spec errors, each with the correction, are in the decisions below. The ones that will paint the wrong thing if implemented literally: luminance coefficients, degenerate objectBoundingBox fallback, `clip-path`'s reference box, `baseline-shift`, gradient and pattern defaults, `rem`, inner `svg` sizing, additive `animateTransform` order, `animateMotion`'s anchor, and "pixels match Chrome's SMIL."

## D1. One resolved scene — agree, with changes

The split is sound. Native hosts already re-walk the tree and call `computed_style` per element (`host/linux/src/paint/svg.rs` lines 83–104, `host/apple/src/svg.rs` lines 238–255). Inheritance carried down the walk is the only way to implement `use`: the instance inherits from the `use`, not from the original's parent (SVG 2 shadow tree, the `use` element). A lookup through kernel parents cannot express that, and today's `computed_style` (`kernel/src/arena.rs` lines 396–404) bakes the defs ancestor. Copying a target's computed style into an instance will freeze `fill="black"` inherited from `<defs>` and the `use`'s `fill` or `color` will not take effect. Copy only the rows whose mask bit is set on the target; inherit the rest from the `use`.

Correct the motivation. `computed_style` is already one ancestor walk for every requested row (`arena.rs` lines 396–400), not a walk per property. The resolver is required for `use`, nested viewports, and paint references, not because the current walk is too slow for eight shapes.

Four rules the scene must state:

1. **Sampled versus lowered.** D1 says presented values are read at resolve time so every host sees the same instant. Apple does not work that way. Lowered properties are not sampled into the engine (`motion/src/engine.rs` treats lowered properties separately; LLP 1055 §0). The scene must carry the underlying value plus the animation spec, which is what `host/apple/src/svg.rs` already emits. Baking the presented value and also attaching a `CAKeyframeAnimation` double-applies.
2. **Group opacity is not inheritance.** `opacity` does not inherit. A `g` at 0.5 containing two overlapping shapes must be a group layer, as the first slice does (`svg.rs` lines 244–248, `paint/svg.rs` lines 88–94). Flattening 0.5 onto each child paints the overlap wrong. `transform` on a `g` is a coordinate change, not a copied animation.
3. **Paint servers are not cloned per `use`.** A `url(#g)` on a symbol looks up the gradient element in the tree. Stops inherit from the gradient's real parent, not from the shape being painted. `stop-color="currentColor"` in `<defs>` does not follow the icon's color. That is why `context-fill` exists. D19 says the opposite for `use` instances' `color`, which is right for the instance and wrong if someone applies it to the server.
4. **Code size.** The web paints with the DOM. It needs the resolver for id rewriting, not for a scene. Hit-test fixtures do not need to ship in the wasm. LLP 1047's point is that an app that does not use a capability does not link it. "Pays only its code size" (line 57) is the whole wasm budget. Keep pixel code in `exact-svg-raster`, and keep the scene builder from being pulled into every web app if the plan has no `svg`.

`kernel/src/svg/scene.rs` as one file will pass 1,500 lines once markers, text, and hit testing land. Split it in the plan.

## D2. Islands — agree for filters, change the rest

| Feature | Verdict |
|---|---|
| Shapes, dashes, groups, opacity | Agree. This is the first slice. |
| Gradients stay vector | Agree with the reason (a chart fill must stay under an animated stroke). The Apple and Linux mechanisms are wrong in detail. |
| `clipPath` | Agree it stays vector. |
| `pattern`, `mask`, `filter` as islands | Agree for filter output and for a pattern tile. Change how the mask is applied on the GPU path. |

**Apple gradients.** `CGContext.drawLinearGradient` and `drawRadialGradient` are real and the radial call is two circles, so `fx`/`fy`/`fr` can be exact. `CGGradient` only pads. Repeating the stop list "across the bbox's extent" (line 119) is not exact. The paint covers the stroke, which lies outside the fill bbox, and a `userSpaceOnUse` gradient is not in bbox space at all. A short gradient vector needs many periods; past the last stop, Core Graphics pads. Hard stops (two offsets equal) need an epsilon or `CGGradient` collapses them. Draw the gradient into a content layer masked by a **fill-only** path. The shape's `CAShapeLayer` cannot be that mask: as a mask its alpha is fill plus stroke (`SvgScene.swift` lines 182–196 draw both), so a gradient fill with a solid stroke, which is the area-chart case, would mask to both. `color-interpolation` on gradients defaults to sRGB, which happens to be close to `CGGradient`. Say so.

**Apple patterns.** `CALayer.contents` does not tile. There is no pattern paint on `CAShapeLayer`. A tile bitmap still needs `CGPattern` or a draw of the tiled image into the shape bounds, including `patternTransform` and the tile phase. Rotation does not survive "device scale times the transform's scale" (line 117) as an axis-aligned bitmap.

**Linux gradients.** `peniko` 0.6's radial kind is two circles plus `Extend::Pad|Repeat|Reflect`, so linear and radial servers can be brushes, and reflect/repeat do not need the Core Graphics workaround. Calling tiny-skia's radial "two-point conical" (line 64) is the wrong primitive. Conical is a sweep. SVG radial is not a sweep. tiny-skia 0.12's `RadialGradient` is two circles with a spread mode. Use that.

**Masks.** Rasterize the mask, not the masked subtree, whenever the content can stay vectors. vello 0.10 has clip layers and `Mix` (`host/linux/src/gpu.rs` lines 500–541) and no luminance mask, so a luminance mask becomes an alpha image first. The GPU painter can then mask vectors with that image. D10's "composites the masked subtree as an island too" (line 146) throws away clip, dash animation, and crisp zoom for every masked chart. An alpha mask (`mask-type: alpha`) does not need that fallback if the alpha bitmap is the mask.

**Filters** belong in islands. vello 0.10 has no filter chain. Core Animation has no public filter graph on iOS. One Rust implementation is the right call. See D14 for the parts that are not faithful.

**tiny-skia on Apple** is justified for filters. The 0.4 MB figure (line 297) is not a measurement in this checkout; "measured before stage 8 lands" has not happened. Antialiasing will differ from Core Graphics. The sparkline thresholds do not absorb text or blur (see §5).

## D3. References — agree, with constraints

Own-svg-first plus rewriting the emitted id to `x<svg>-<id>` is a sound way to make forty component instances paint their own gradients. It matches Chrome once ids are unique. Chrome's document order is what you get on invalid duplicate ids; the RFC is honest that this is the one intentional deviation (lines 76 and 324). Agree with question 1, under these rules:

- `href` wins over `xlink:href` when both are set. The RFC treats them as the same (line 74) and does not say which wins.
- Within one `svg`, first in tree order. Across `svg`s, local first, then document order.
- A missing or wrong-type **paint** server uses the fallback, or `none` if there is no fallback. A **cyclic** server or a **degenerate objectBoundingBox** server paints nothing, and the fallback is **not** used, because the `url()` resolved. D3 says cycles render nothing (line 78). D7 then says a zero bbox "renders as the fallback, or as none" (line 116). Drop the fallback. SVG 1.1 §7.11 / SVG 2: the effect is ignored.
- A missing `clip-path`, `mask`, or `filter` paints the element unclipped, as Chrome does. Good.
- `url()` does not search a `use` shadow tree. It finds the original element. Do not clone the gradient per instance.
- External URLs are refused.
- The rewrite has to cover every channel the browser will resolve: presentation attributes, style rows, `clip-path`, `mask`, `filter`, `marker-*`, `href`, `mpath`, and values computed at runtime. One missed channel paints the first instance's server.
- Compile-time `lower-svg-ref` ("same file", line 80) is right for a typo in one file. A sprite component whose ids live in another Contract module is a runtime reference, same as the forty-row case. Do not refuse that at compile time.

## D4. Geometry, units, view box — change

`ellipse`, deleting the `x`/`y`/`rx`/`ry` props, and making `d` a row are right. Geometry rows do **not** inherit (the existing `cx`/`cy`/`r` bits 111–113 are not inherited). Say that. D1's "inherited style is carried down" must not include them.

**Percentage rows cannot be `f32`.** `cx`, `cy`, `r`, and `stroke-width` are `f32` today (`schema.json` bits 102, 111–113). `stroke-dasharray` accepts only numbers and `px` (`kernel/src/svg/mod.rs` lines 131–145). A percentage is resolved against the viewport after layout, and again when the `svg` is resized. The authored form has to live in the row. The dimension codec already stores percent as authored (`schema.json` `_styles`). Geometry and stroke lengths need that, not a baked float. `em` depends on computed `font-size` at resolve time, not at lowering.

Which percentage uses which axis, from SVG 2's units rules (the RFC's "§8.9" does not match this repo's own numbering: `kernel/src/svg/shape.rs` lines 3–4 call the viewBox equations §8.2):

- `x`, `width`, `cx`, `rx` on ellipse and rect: viewport width.
- `y`, `height`, `cy`, `ry`: viewport height.
- `r` on circle, and `stroke-width` / dash lengths: the normalized diagonal √((w²+h²)/2).

**Absolute units** at 96 px per inch, converted to user units before transforms, are right. Doing it at lowering is fine for literals. Keyframes and `em` resolve at sample time.

**`rem`** is the document root's `font-size`, not the `<svg>` root's. "The root's" (line 87) is the wrong root for an inline `svg`.

**Intrinsic ratio.** The direction is right and it does replace LLP 1055 §0. The current code will defeat it. `layout.rs` lines 762–771 still returns 300×150 for every `Svg` with no host intrinsic whenever a dimension is unknown, and `taffy_style` only copies a ratio from `arena.intrinsic` (`kernel/src/style.rs` lines 1236–1241). Feeding Taffy `aspect_ratio` is not enough: if both axes are unknown, that callback returns 300 and 150, ratio 2, and ignores the viewBox.

Chrome, for this tree, where `svg` is `display: block` (LLP 1055 D3): a viewBox and `width`/`height` `auto` stretches to the containing block and takes height from the ratio. 300×150 is the default object size when there is **no** ratio (no viewBox and no resolved size), and the fallback width when the containing block's width is indefinite. A viewBox plus one of `width` or `height` computes the other from the ratio. Both set: the viewBox does not override them.

**Inner `svg`** is not that replaced-element formula. Width and height default to **100%** of the parent viewport. `x` and `y` place it. It clips because overflow's UA value is `hidden`, not because CSS's initial `overflow` is `hidden` (the initial value is `visible`; the first slice sets hidden on the root tag). D4 never says the 100% default. Reusing the root's 300×150 or aspect-ratio path for a nested `svg` paints it the wrong size. The viewBox fit itself can stay `view_box_transform`.

## D5. Transforms — change

Agree: `transform-origin` initial `0 0` and `transform-box` initial `view-box` on SVG elements. That is Chrome, and it is what makes a presentation-attribute transform behave like SVG 1.1. Agree that `transform` on HTML boxes stays out. Boxes already have `translate` / `rotate` / `scale`, and a general `transform` also changes hit testing, overflow, and containing blocks. Question 3: leave it out.

Agree with the CSS composition order: origin, then the individual `translate`, then `rotate`, then `scale`, then the `transform` list, then the inverse origin (CSS Transforms 2). Pin the matrix convention with `getCTM()` as §5 already proposes.

**The Apple layer pair does not implement that order.** Current layers have no bounds and no `anchorPoint`; only circles get a position (`SvgScene.swift` lines 180–186). `anchorPoint` is a unit point of the layer bounds, not a user-space origin. "Anchor at the origin" (line 98) does not mean `transform-origin`.

Core Animation stores one matrix. The key paths `transform.translation`, `transform.rotation.z`, and `transform.scale` are a decomposition of that matrix, not three CSS properties. Animating rotation and scale together shears or picks the wrong sign. Two key-path animations on one matrix are not CSS's multiplications.

Parent then child applies `M_outer · M_inner`. With the origin sandwich on the outer layer and the static `transform` on the inner layer, the inverse-origin translation lands **outside** the static transform. CSS wants it **inside**:

`T(origin) · translate · rotate · scale · transform · T(−origin)`

The pair as described produces `T(origin) · translate · rotate · scale · T(−origin) · transform`.

LLP 1055 §0 refused lowering transforms for this reason: reviewers required sampling so there is no matrix-composition deviation. Do one of these instead:

- Sample SVG transforms in the engine, as box transitions already are, or
- Bake one matrix per keyframe and lower a single `transform` animation, which is what the first slice already described for boxes.

Do not use the rotation and scale key paths.

**`scale` is one number today.** Schema bit 64 is `f32`; `motion/src/property.rs` lines 21 and 70–79 give `Scale` one component. CSS `scale` on an SVG element is often two numbers. Widening it changes every box animation's wire (`_animations` is `x f32, y f32`). Non-uniform scale can stay inside the `transform` list until that wire change is explicit.

**`vector-effect: non-scaling-stroke`** does not inherit. Baking the path into the `svg`'s pixel space (line 100) also bakes the fill, so an animated transform can no longer be a layer transform, and an `objectBoundingBox` gradient is computed in the wrong space. Dashes are in that same unscaled space. Mark this combination as sampled, and say so in D15.

`rotate(a cx cy)` belongs on the presentation attribute, not in the CSS `transform` grammar. Accept both grammars in one row.

## D6. Colour — change

Premultiplied sRGB for hex and `rgb()` is what CSS Color 4 specifies and what current Chrome does for legacy syntax. The citation is wrong: premultiplication is §12.2, and §12.3 is hue interpolation. `transparent` is premultiplied black, which is why a fade to transparent keeps the hue. Store the four components premultiplied, or the existing `Value::lerp` (`motion/src/property.rs` lines 126–130) will interpolate straight alpha and disagree with Chrome on any translucent pair.

The price flash (opaque green to opaque black) matches either way. Lower **opaque** `fill`, `stroke`, and `background-color` to Core Animation if you want. `CAShapeLayer.fillColor` and `CALayer.backgroundColor` interpolate components in the color space, alpha separate, not premultiplied. Any endpoint with alpha other than 1 must be sampled by the engine. Linux already samples everything.

This sentence should be deleted: fill and stroke "lower to the gradient layer's opacity when a server is involved" (line 109). Opacity fades the whole paint. It does not interpolate stops, and a color-to-`url()` pair switches discretely at 50% (that part of D6 is right). `stop-color` rebuilds the gradient. `currentcolor` is resolved at sampling; if it is lowered to a `CGColor`, it goes stale when `color` changes. The RFC already samples that case. Keep it.

`light-dark()` resolved before interpolation, and re-resolved on a scheme change, matches LLP 1034 and Chrome. Good.

The wire does not have four components. `_animations` is `x f32, y f32` per keyframe value (`schema.json` line 1848). Apple's track reads `v.x` only (`host/apple/src/svg.rs` `forward`, around line 405) and `SvgScene.swift` lines 92–97 expect a flat scalar list, with `r` special-cased to a path. The lowered-property array is `[bool; 7]` (`motion/src/engine.rs`). This is a codec change, not just new `Property` variants.

## D7. Paint servers — change

The element set is right. These defaults are not in the RFC and are the ones people get wrong:

- Linear: `x1=0%`, `y1=0%`, `x2=100%`, `y2=0%`. Radial: `cx=cy=r=50%`, `fx` defaults to `cx`, `fy` to `cy`, `fr=0`.
- `gradientUnits` initial `objectBoundingBox`. A percentage is then a fraction of the bbox, not of the viewport. `userSpaceOnUse` percentages use the viewport.
- `gradientTransform` applies in the gradient coordinate system **after** the bbox mapping.
- `href` inherits attributes that were omitted. Stops are inherited only when this gradient has **no** `<stop>` children. A cycle paints nothing, not the fallback.
- Stop `offset` defaults to 0. Clamp to [0,1] and force monotonic. That part is right.
- `stop-color` initial black, `stop-opacity` initial 1, not inherited. Right.
- A zero-width or zero-height bbox: the server paints **nothing**, not the fallback (see D3).
- `pattern` `width` and `height` initial **0**, which paints nothing. `patternUnits` initial `objectBoundingBox`, `patternContentUnits` initial `userSpaceOnUse`. The tile is clipped to the pattern viewport (`overflow: hidden`).
- `color-interpolation` initial `sRGB` for stop interpolation. Missing.

`paint-order` initial `normal` means fill, then stroke, then markers, and the property inherits. Good to have it before markers land.

## D8. `use` / `symbol` / `defs` — agree, with the inheritance rule made explicit

`defs` and `symbol` do not paint. A `symbol` or `svg` target creates a viewport: the `use`'s `width` and `height`, default **100%**, and the symbol's `viewBox` and `preserveAspectRatio`. The `use`'s `x`/`y` place it. Width and height on `use` are ignored for a `path` or `g` target. The RFC says this (lines 123–125). Good.

"Own rows still apply" (line 126) must mean mask bits set on the target, not `computed_style`. Events retarget to the `use`. Instances are not kernel nodes. All of that matches the shadow tree and should stay.

Animations on the target start when the **instance** is created, not when the document loads. That matches CSS on a shadow clone and matches LLP 1055 D9. It does not match Chrome SMIL. Fine if D16 keeps that deviation visible.

## D9. Markers — change

The properties, the defaults (`markerWidth`/`markerHeight` 3, `markerUnits` `strokeWidth`, `orient` initial `0`), inheritance, `context-fill` / `context-stroke`, and `paint-order` are right. `refX`/`refY` also accept `left`/`center`/`right` and `top`/`center`/`bottom`. Chrome implements those. The RFC only describes lengths.

"The bisector at mid vertices and the direction at a closed subpath's start" (line 135) is not the algorithm. SVG 2's placement rules:

- Per subpath, not once per path: `marker-start` on the first vertex, `marker-end` on the last, `marker-mid` on the others.
- A closed subpath draws start and end at the same point. It does not also draw a mid marker there. The corner where the close meets the first segment is not a mid vertex.
- Mid direction is the average of the incoming and outgoing unit tangents, not an unspecified bisector. A 180° turn has a defined fallback.
- Zero-length segments take their direction from the nearest non-zero segment.
- `auto-start-reverse` adds 180° to the **start** marker only. That is the whole feature. Listing the keyword (line 134) without this rule will point arrowheads the wrong way on polygons.
- `orient="auto"` aligns the marker's +x with that direction, around `refX`/`refY`.
- Marker content is clipped to the marker viewport.
- `markerUnits="strokeWidth"` scales by the stroke width, including under `non-scaling-stroke`.

Restricting markers to `path`, `line`, `polyline`, and `polygon` disagrees with SVG 2 and with Chrome, which paints them on `rect`, `circle`, and `ellipse` too (via the equivalent path, which does produce vertices). Either do all geometry elements or declare the restriction as a deviation and put it in the parity smoke.

Each marker is an instance so `context-fill` is the **referencing** shape's paint, including a gradient, not a color baked when the marker was defined. Good. Do not cache one raster per marker element.

## D10. Clip and mask — change

**`clipPathUnits` initial is `userSpaceOnUse`.** `maskUnits` initial is `objectBoundingBox`. They are opposites. The RFC states the mask default (line 143) and never states the clip default. Copying the mask default is the usual bug.

`clip-rule` initial `nonzero`, inherited. Children contribute their **fill silhouette**, unioned, stroke ignored. A `clip-path` on the `clipPath` intersects. Good.

**Basic shapes do not use `transform-box`.** CSS `clip-path` is `<basic-shape> || <geometry-box>`, and the initial geometry box is `border-box`. For an SVG element with no CSS layout box, `border-box` computes to **`fill-box`** (CSS Masking 1). `transform-box` initial `view-box` is a different box. `clip-path: inset(10%)` against the view box instead of the object's fill box will not match Chrome. The existing row only accepts `path("…")` with absolute `M/L/Q/C/Z` (`kernel/src/clip.rs` lines 10–16). Growing it to `url()` and `circle()`/`ellipse()`/`inset()`/`polygon()` is real grammar work; name the geometry box in that grammar.

Apple: one `CALayer.mask`, with one `CAShapeLayer` per child inside it, opaque fill, per-child fill rule, can represent a union. The mask's geometry has to be in the element's user space so it transforms with the layer. `objectBoundingBox` clip paths must be scaled to the bbox first. The RFC does not say that.

**`maskContentUnits` initial is `userSpaceOnUse`.** The default region −10%, −10%, 120%, 120% is right for `objectBoundingBox`.

**Luminance.** The coefficients (0.2125, 0.7154, 0.0721) are the SVG 1.1 `feColorMatrix` / `luminanceToAlpha` set. CSS Masking's current formula, and Skia's luma filter, are **(0.2126, 0.7152, 0.0722)**. Chrome follows Skia. Citing "CSS Masking 1 §7.2" and "what Chrome does" (line 143) is wrong on both the section and the numbers. §7.2 is not the luma equation. Apply the coefficients to premultiplied RGB **or** to straight RGB times alpha, not both. And do not also call tiny-skia's `Mask` luminance mode and claim the SVG 1.1 coefficients: those have to be shown to be the same function, and a Skia port is the other set. On Apple, `CALayer.mask` reads alpha, so the island must write luminance into alpha. Position and `contentsScale` have to match the layer or the mask slides. That is not mentioned.

Mask and filter do not affect hit testing. Clip does. D17 says "clips" (line 224). Keep mask out of that word.

CSS `mask-image` longhands on SVG elements: agree to refuse.

## D11. Text — change

The property list is what charts need, and shaping on the host is unavoidable (the kernel does not have the fonts). The mechanism described does not match the code it names.

`TextMeasurer::measure` returns width, height, and an optional first baseline (`kernel/src/text.rs` lines 230–238). It does not return per-glyph advances, bearings, or ink bounds. SVG text needs those for `x`/`y`/`dx`/`dy`/`rotate` per character, `text-anchor`, `textLength`, `textPath`, hit testing, and the object bounding box. "The advance is measured the way boxes' text is measured, through the kernel's `TextMeasurer`, so the scene stays one pass" (line 157) is false. Paragraph measurement also wraps. SVG text does not wrap unless `inline-size` is set, and `inline-size` is not in this RFC. Reusing the box inline-run model (line 152) will wrap chart labels.

Positioning rules the RFC skips (SVG 2 text layout):

- `x` and `y` lists do not repeat. Extra characters have no absolute position.
- Missing `dx`/`dy` are 0. The last `rotate` value **does** repeat.
- `text-anchor` is per chunk (a run of characters positioned by one absolute `x`/`y`), not per glyph.
- `textPath`: the point that sits on the path is the **midpoint of the advance along the baseline**, rotated to the tangent, not the ink center. Glyphs past either end are not drawn. That part is right. `spacing="auto"` is missing (only `exact` is mentioned). `method="stretch"` is refused later; good.
- `dominant-baseline` values are roughly right. `alignment-baseline` is not the same set (initial `baseline`; SVG also has `before-edge` / `after-edge`). **`baseline-shift` does not take that set at all.** It is `baseline | sub | super | <length> | <percentage>`. Line 151 is wrong.
- `xml:space="default"` maps to `white-space: normal`, `preserve` to `pre`. State the mapping. The initial value has to match Chrome, which is `normal` under SVG 2, not "whatever boxes do."
- `lengthAdjust="spacingAndGlyphs"` scales glyph outlines in x. `spacing` only changes gaps.

**Outlines into `CAShapeLayer` will not meet the parity bar.** `CTFontCreatePathForGlyph` is unhinted. Axis labels at 11 px will not land inside mean |Δ| ≤ 4/255 of Chrome's rasterizer. The threshold in §5 was measured on stroked sparklines with no text (LLP 1055 §0: about 1–2/255, worst 3.65% of pixels). Color glyphs and emoji have no path. Stroke-on-text is actually closer as outlines, because Chrome strokes the outline too. Fill of small text is not.

D6 says an animated `color` on text re-rasters because Core Text bakes pixels (line 109). D11 says the glyphs are a `CAShapeLayer`, whose `fillColor` animates without a re-raster. Pick D11's representation and delete the re-raster sentence, or pick a raster and delete the shape layer. The outline layer is the one that composes with gradients and clips. Use it, and do not claim sparkline pixel parity for small text. Pin baselines and advances numerically instead.

`title` and `desc` do not paint. Nothing in D11 or D17 says that. If they enter the text-run model they will show up as glyphs.

## D12. `image` — agree, with the Apple mapping changed

The pipeline reuse (LLP 1011) is right. Refusing an SVG file as the source is a fair v1 cut: it is a second document. `preserveAspectRatio` initial `xMidYMid meet` is right. `auto` means the intrinsic size; if only one axis is `auto`, the other comes from the ratio.

`contentsGravity` cannot represent the ten alignments times `meet` / `slice` / `none`. `view_box_transform` already implements that math (`kernel/src/svg/shape.rs` lines 157–190). Use it to set the layer's contents rect. Do not use `contentsGravity`.

## D13. `foreignObject` — agree to refuse

On the web it is free. On native it puts views, focus, and text input under an SVG transform, or it bakes them into an island and breaks interaction. No chart or icon needs it. Refusing it by name, with the error pointing at a box positioned over the `svg`, is the right permanent cut.

It contradicts the admission in `rules/DEFERRED.md` (lines 282–290): "SVG, complete, as the browser renders it." Record it as a declared deviation in that file and in LLP 1001. It is a bigger cut than the four questions in §8, and §8 does not ask it.

## D14. Filters — change

The stage split 9a / 9b / 9c is right. `BackgroundImage` and `enable-background` should stay refused. Owning the primitives instead of taking resvg's tree is right (the kernel stays dependency-free; the raster crate is the leaf).

These claims are false:

- **"Conversion to linearRGB once per filter"** (line 178). `color-interpolation-filters` is per primitive, initial `linearRGB`, inherited from the `<filter>`. Each primitive converts its inputs. `feFlood` and `feImage` are specified in sRGB and then converted. One conversion for the whole chain is wrong as soon as two primitives differ.
- **"Three box blurs when σ ≥ 2, as Chrome does"** (line 178). The spec allows a three-box approximation. It does not define a σ = 2 cutoff. Chrome's Skia blur is not that approximation, and the edge treatment differs. Pixel-matching Chrome on `feGaussianBlur` at mean ≤ 4/255 will not hold. Pin sigma, region, and a known error bound.
- **"A premultiplied buffer for every primitive"** (line 178). Filter Effects run many primitives on premultiplied values, but `feComponentTransfer` is specified on **unpremultiplied** channels. `feColorMatrix` has its own premultiplication rule. One buffer convention will fail `saturate` and the transfer functions against Chrome.
- **`feBlend` "the separable modes"** drops hue, saturation, color, and luminosity, which Chrome implements. Say that those four are in 9b or refused.
- **`feComposite arithmetic`** needs `k1`–`k4`. Not mentioned.
- **Primitive subregion** default is 0%, 0%, 100%, 100% of the **filter** region, not −10%. `primitiveUnits` initial is `userSpaceOnUse`. `feFlood` fills its subregion only.
- **`feDropShadow`** is the right 9a shorthand (icons). Its `dx`, `dy`, `stdDeviation`, `flood-color`, and `flood-opacity` are not listed.
- **CSS filter functions** do lower to the primitive graphs defined next to each function in Filter Effects 1. That is not a single "§12" table. `filter` is a list: `url(#a) blur(2px)` is legal in Chrome. The RFC talks about functions and about `url()` separately and never about a mixed list.
- **About 1,000 lines** (line 182) may cover 9a. `feTurbulence`, `feConvolveMatrix`, `feDisplacementMap`, and the three lights will not. The 1,500-line cap means several files. Say that in §6.

`in` / `in2` / `SourceGraphic` / `SourceAlpha` / named results are right.

## D15. Animation beyond the first slice — change

`display: none` cancels, including on an ancestor, and showing the element again starts the animation from the beginning (CSS Animations 1). That correctly replaces LLP 1055 §0. **`visibility: hidden` does not cancel.** D19's visibility rule is about painting, not about the timeline. Say both in one place.

Inherited animated **inherited properties** (`fill`, `stroke`, `stroke-*`, `color`, `font-size`) flow down. Copying a lowered spec onto each inheriting descendant (line 192) is right for `stroke-dashoffset` on a `g`, because the group has no stroke to animate. It is wrong for `opacity` and `transform`. The descendant's own specified value wins, so a child with its own `fill` does not take the parent's fill animation. `fill="currentColor"` tracks the animated `color`. That matches D6.

**Geometry.** Interpolating lengths is right if percentages re-resolve against the current viewport at sample time. Baking `50%` to pixels when the animation starts is wrong when the `svg` is resized.

**`d`.** Chrome interpolates when the **authored** command lists match after relative commands become absolute, and otherwise switches at 50%. This repo's parser destroys that identity: arcs and quadratics become cubics before any host sees them (`kernel/src/svg/path.rs` lines 1–8 and 230–239), and `H`/`V` become lines. Two arcs that Chrome interpolates as arc parameters will morph as different cubics. An `H` and an `L` that Chrome refuses to interpolate may both be `Line` here and will interpolate. Keep the authored command list on the animation; paint from the cubic form. `Value` staying a small vector, with a path payload beside it, is the right codec split. The payload is still a change to `_animations`.

**Apple `path` key path.** `CAShapeLayer` interpolates paths only when the element sequence matches, and it interpolates the elements it was given, which will be cubics. That cannot be the CSS `d` oracle. Circles already work only because both ends are the same four cubics (`SvgScene.swift` lines 52–64). Use that special case for `r`. Sample general `d`.

**`x`/`y`/`cx`/`cy` lowered to `position`.** Circles already sit at `position` with the path around the origin, so `cx`/`cy` can be `position` **after the viewBox transform**. A non-uniform `preserveAspectRatio="none"` sparkline scales x and y differently; a raw user-unit position is wrong. `rx`, `ry`, `width`, and `height` are not positions. Sampling those, as the RFC says, is right. A shape that also has a transform cannot use `position` for `x`/`y`. Good that D15 says "without a transform."

**`points`** is not a CSS property. D15 says it animates only through SMIL. D16 says every SMIL `attributeName` becomes a CSS row. There is no row. See D16.

Islands sample and re-render while an animation runs. Also re-render when an inherited value **outside** the island changes (`color` on an ancestor), and when the device scale or the `svg` box changes. Not said.

## D16. SMIL lowered to CSS — change

Lower once, including on the web. Two SMIL engines would violate LLP 1002. Question 2: agree with the choice, not with the table. The web will then match Chrome's rendering of the **lowered CSS**, not Chrome's SMIL. Line 218 says the parity smoke checks that the pixels match Chrome's SMIL. §5's smoke renders `apps/svg-gallery` through Contract on every host. Nothing in that loop loads a raw SMIL document in Chrome. The sentence is false. A separate fixture, raw SMIL in Chrome against the lowered Contract page, is what that claim needs. The timeline deviation (start at insertion, not document load) is the right product call and matches LLP 1055 D9. Keep it declared.

| Row in the table | What is wrong |
|---|---|
| `by` as `from + by` baked at lowering (line 203) | `by` is `underlying` to `underlying + by`, live. This engine already samples missing 0% keyframes from the live underlying (`motion/src/animation.rs` lines 368–408; LLP 1055 §0). A keyframe that sets only the end, plus a delta, does that. Baking an absolute value at compile time is wrong for inherited and computed bases. |
| `to` without `from` | Same mechanism: omit the 0% value. Do not capture the base at lower time. |
| `additive="sum"` only on `animateTransform`, "composing after" (lines 209, 215) | SVG appends the animated transform to the transform list. It is applied in the element's local space, **then** the base transform: `translate(10)` under `scale(2)` moves 20 user units. "After the element's own transform" reads as the other multiply. Pin it with `getCTM()`. |
| Two `animateTransform`s | Both target `transform`. CSS applies one animation's effect per property. `animation-composition` stays refused (LLP 1055 D12). Icon files routinely pair a rotate and a translate. Precompose them into **one** keyframe list in document order, or the second replaces the first. |
| `animateTransform` `rotate(angle cx cy)` | Interpolate angle, cx, and cy. Do not interpolate the expanded matrix. The D5 inner-layer matrix cannot represent a moving center. |
| `calcMode` default | `linear` for `animate`, **`paced` for `animateMotion`**. One default makes motion along a path equal-time per segment instead of constant speed. |
| `keyTimes` omitted | Even spacing, except `paced`, which ignores `keyTimes`. Not stated. |
| `repeatDur` and `repeatCount` together | Active duration is the minimum of the two. Not stated. Fractional `repeatDur / dur` is otherwise the right CSS mapping. |
| `set` → `steps(1, start)` | Right idea (hold `to` for the whole duration). LLP 1055 §0 already says steps are wrong at exact boundaries. Pin `set` against Chrome rather than assuming the easing helper is enough. |
| `animateMotion` → `offset-*` | `offset-anchor` initial is the box center. SMIL moves the user-space origin. Set **`offset-anchor: 0 0`** or every icon orbits its center. `mpath` includes the referenced path's transform; a bare `path()` string does not. `keyPoints` are not `offset-distance` unless you bake them into keyframes. Composition with the element's `transform` is a CSS Motion Path rule the table does not state. Apple has no lowering plan for this at all. |
| `points`, stop `offset`, `viewBox` | Not CSS properties in this schema. Refuse them by name until a row exists, or the table's "it must be animatable here" (line 202) drops them with a bad error. |
| `end`, `begin="0s; 5s"` | Not in the table and not in the refusal list. A single clock offset is fine. Any other `begin` or `end` must be refused whole, not parsed as the first offset. |
| Event and syncbase timing, `restart`, `min`/`max`, `accumulate` | Agree to refuse. |

`fill="freeze"` → `forwards` and `remove` → `none` is the right pair. `discrete` as a step per interval is close; pin the last segment.

## D17. Hit testing and accessibility — change

Admitting handlers on SVG elements, keeping one native view, and hit-testing in the kernel is the right extension of LLP 1055's "the `svg` is the one view." Reverse paint order, `use` retargeting, and bubbling through the kernel tree are right.

The hit test as specified will not match `elementFromPoint`:

- `pointer-events: auto` computes to `visiblePainted` on SVG graphics elements. The value list is missing `bounding-box`.
- `visiblePainted`, `visibleFill`, `visibleStroke`, and `visible` require `visibility: visible`. `painted`, `fill`, `stroke`, and `all` ignore visibility and treat `none` paints differently. The algorithm (line 224) tests fill and stroke and does not mention visibility or `none`.
- Fill uses `fill-rule`. Good. Stroke is the stroke outline: linecap, linejoin, miterlimit, and **dash gaps are misses**. "Distance ≤ half the stroke width, joins approximated by round" (line 224) is wrong for the default `miter` join on a sparkline and wrong for dashes. §5 says this is tested against Chrome's `elementFromPoint`. It will fail. Honor cap, join, miterlimit, and dashes, or drop that parity claim.
- `clip-path` and overflow clip hits. **Mask, filter, and `opacity: 0` do not.** `display: none` is not a target.
- Marker graphics are not separate targets. A click on an arrowhead hits the shape only where the shape's own fill or stroke is, which is usually a miss. Say that.
- `overflow: visible` content outside the `svg` box is hittable. Always clipping to the `svg` box (line 224) is wrong for that case. The root's default is hidden, so the common case is clipped.

**Scroll.** `rules/DEFERRED.md` lines 258–260: the platform owns gesture arbitration and scroll always wins. Pointer-move tracking on the one `svg` view, to synthesize hover (line 225), will steal pans inside a list. The chart consumer is a list row. Hover tracking has to be passive and lose to the scroll view.

**Accessibility.** `aria-label` wins over `<title>`, then the SVG-AAM name calculation. The RFC lists both and does not order them. `desc` is the description. Good. `title` is not a native tooltip. Good as a declared deviation.

D11 and D17 disagree about text. D11 exposes text as the `svg`'s accessible text unless the `svg` has a label. D17 says children without a handler or an explicit role are presentational, and the `svg` is one image whose label is `title`, `aria-label`, or nothing. Write one rule: if the author set `aria-label`, `title`, or `role="img"`, the `svg` is one element and the text is its name, not extra children; otherwise expose the text runs in document order. `tabindex` needs a focus target inside that single view. Say who draws the focus ring, or do not admit `tabindex` yet.

**`<a>`** is a container, not a rectangle. Hits are the children's geometry, then the link is the ancestor for navigation. A box `<a>`'s rectangular hit target is the wrong model (line 231).

## D18. Animation events — change

The four CSS event names, web native, and "an unhandled infinite animation never wakes the app" are right. `animationiteration` fires at the end of each iteration **except the last**. A three-iteration animation fires it twice. An infinite one fires it once per period. Not stated. `animationcancel` is not a timing boundary: it fires when the animation is removed, the element is destroyed, or `display: none` cancels it. The native paragraph only schedules boundaries.

Do not schedule an independent wall timer. The clock is seekable and, on Apple, a lowered animation runs with `speed = 0` under an agent clock (`SvgScene.swift` lines 66–68 and 110–119) while the engine stays quiescent so the display link can sleep (LLP 1055 §0). A timer fires during a frozen seek, and a seek that jumps over a boundary never fires it. Report crossings when the clock advances. For a lowered animation in real time, the scheduled wake has to use that animation's begin time and be cancelled while the agent clock is paused.

Pass the animation name to the handler. Two animations on one node are normal.

This does not belong in the SMIL stage. It is small and the price flash is the thing that wants `animationend`.

## D19. `class`, `currentColor`, blend — change the blend, agree the rest

`class` meaning "apply this style set's rows if they are legal on the element" matches Contract, which has no selectors. A class on the `svg` that sets `color` or `fill` works for icons because `fill` and `color` inherit. `.icon path { fill: red }` will never work. Say that in the decision so nobody expects stylesheet SVG.

`currentColor` on `fill`, `stroke`, `stop-color`, `flood-color`, `lighting-color`, and paint fallbacks is right, resolved to the element's computed `color`, and for a `use` instance to the instance's inherited `color`. It is wrong to resolve a stop's `currentColor` against the shape that references the gradient (see D1).

`display: none` removes the subtree from painting. `visibility: hidden` hides that element and not a descendant that sets `visibility: visible`. `collapse` is `hidden` in SVG. Good.

**`mix-blend-mode` on iOS is not an island of the subtree.** CSS blends with the backdrop inside the isolation group. A bitmap rasterized on transparent and then drawn with source-over does not multiply with the svg behind it, or with the page. That is the same backdrop problem as `BackgroundImage`, which §7 refuses. `CALayer.compositingFilter` exists on macOS and is not a public iOS API. vello's `Mix` is only used as `Mix::Normal` today (`host/linux/src/gpu.rs` line 540); peniko 0.6 does have the other modes, so Linux can be faithful if the blend is applied to a layer that contains the backdrop. Defer iOS blend, or include the backdrop in the island and say what the isolation group is. Do not claim stage 10 matches Chrome on iOS.

## Per host, the limits the RFC does not name

**Web.** Faithful, because it is the SVG DOM plus CSS. It stays faithful only if Contract emits the CSS the decisions describe. SMIL will not be faithful to Chrome SMIL after lowering. Id rewriting is the one place the DOM is intentionally not the author's DOM. No app JS reads those ids. That holds.

**Apple.** Besides the transform key paths, gradient mask, pattern tiling, and `contentsGravity` issues: `CAKeyframeAnimation` on `path` does not know CSS path compatibility; color animation is not premultiplied; `CALayer.mask` is one layer and uses alpha; there is no public iOS blend and no filter primitive graph; text outlines are unhinted; an island `CGImage` has to be premultiplied sRGB or the colors shift; `UIAccessibilityElement` frames are outside the scene JSON and must be dropped in `SvgHost.forget` (`SvgScene.swift` lines 241–244) or the pool reset brings them back. The pool bug LLP 1055 left is real; fixing it at stage 2 only stays fixed if every later layer is under the scene root that `forget` removes.

**Linux.** vello 0.10 can do gradients (`peniko` 0.6 linear and two-circle radial, pad/reflect/repeat), image brushes (already used, `host/linux/src/gpu.rs` imports `ImageBrush`), clips, and blend modes. It cannot do filters, pattern paints, or luminance masks. tiny-skia 0.12 can do two-circle gradients, spread modes, image patterns, and alpha/luminance masks, and cannot do filter primitives; those are yours. The CPU painter is the one that can composite an island. The GPU painter should take an image brush for an island, which the RFC says (line 66), and should not rasterize masked vectors when an alpha mask would do.

## §6 and §7 — costs and refusals

The style mask really is two `u64` words today (bits 0–114). About thirty new rows fit in a third word. That sentence is right. The count undercounts `d`, `filter`, `mask`, `color-interpolation`, `offset-anchor`, and length codecs that stop being `f32`. Still inside three words.

Web wasm does not "grow by the reference index and the codecs only" if the resolver and hit testing are linked into the kernel the web ships. Apple's growth is the resolver plus `exact-svg-raster` plus whatever 9a–9c actually compile to, not a pre-measured 0.4 MB of tiny-skia.

§5's thresholds (mean ≤ 4/255, ≤ 6% of pixels, from LLP 1055's sparkline residue) are the wrong gate for text, blur, and a second rasterizer. Use them for filled and stroked vectors. Use numeric fixtures (`getCTM`, `getComputedStyle`, `getTotalLength`, glyph advances) for transforms, colour, and text. Use a looser, stated error for blur.

Refusals I agree with: `foreignObject` (as a declared deviation), `script`, `style` elements, SVG fonts, `cursor`, `BackgroundImage` / `enable-background`, event and syncbase SMIL, the at-risk `vector-effect` values, `method="stretch"`, an SVG document as an image source, CSS `mask-*` longhands, `transform` on boxes, `restart` / `min` / `max` / `accumulate`, and `ex` / `ch` / viewport units until a consumer needs them.

Add to the refusal list: external `url()`, `hatch`, `mesh`, `solidcolor`, `switch`, SMIL `end` and begin-lists, SMIL of attributes that are not rows (`points`, stop `offset`) until those rows exist, and 3D transforms on SVG unless you take them on.

Do not treat as admitted-and-faithful: iOS `mix-blend-mode` via a transparent island, Chrome-matching Gaussian blurs, markers only on four elements (unless declared), and SMIL pixel-equality with Chrome.

## Verdict

Build stages 1–9a in the chart-then-icon order, after the corrections above. The resolver, the browser oracle, and filter islands are the architecture to keep. Change D4's length codec and sizing, D5's Core Animation transform lowering, D6's gradient-opacity sentence and the colour wire, D7's defaults and zero-bbox rule, D10's clip reference box and luma formula, D11's measurer and `baseline-shift`, D14's color-space and blur claims, D15's `d` interpolation, D16's mapping table, D17's stroke hit testing, and D18's timer. Split stage 10 and do not lower SMIL until that table is rewritten. That is a build with named changes, not a different design.
