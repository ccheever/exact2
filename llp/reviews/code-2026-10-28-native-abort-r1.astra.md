I would not land this round: an old abort can cancel a newer request, and several paths can still lose or strand cancellation. I read the approved plan and the diff. This was static review only; no edits, builds, or tests were run.

1. **Blocker — an abort can cancel the wrong request.**  
   [admission.rs:124](runner/src/runner/admission.rs:124) resolves a queued `Target` to whichever request currently occupies that target. Apple’s pump can drain real replies first ([abi.rs:354](host/apple/src/abi.rs:354)); Linux does the same. If the original reply lands after the app aborts, its rejected promise’s continuation can issue another fetch, which receives a new ticket on the same target ([commit.rs:1403](runner/src/runner/commit.rs:1403)). The next refusal turn then aborts **that new fetch**. A re-ask before the abort is consumed has the same problem. Preserve request identity through cancellation delivery; add reply-first and re-ask regression cases.

2. **Should-fix — cancellation heard during request collection can miss the pump wake.**  
   Apple checks `has_module_aborts()` at [abi.rs:253](host/apple/src/abi.rs:253), before `take_requests()` at line 268. But request collection itself drains module aborts ([commit.rs:944](runner/src/runner/commit.rs:944)). A concrete trigger is a forgotten answer’s `finally` aborting another fetch: forgotten calls run their rejection continuations at [turns.rs:76](js/src/turns.rs:76), after the answer’s earlier drain. The newly heard abort can remain queued until unrelated activity wakes the host. Linux has the same ordering at [presenter.rs:812](host/linux/src/presenter.rs:812). Check for owed cancellation after the final drain.

3. **Should-fix — discarding a worker turn discards its aborts permanently.**  
   [placed.rs:395](data/src/placed.rs:395) drains the worker’s aborts into that turn’s reply; they reach the proxy only through `apply_turn()` at [placed.rs:305](data/src/placed.rs:305). If answer B aborts A and B is superseded before its reply lands, B’s reply is discarded ([commit.rs:1199](runner/src/runner/commit.rs:1199)). A’s cancellation has already been removed from the worker and is never delivered. A remains parked on its original request. Cancellation needs delivery independent of whether the carrying answer remains current.

4. **Should-fix — wasm background callbacks never forward their aborts.**  
   Door 22 appends to the realm’s array, which only `finish()` drains ([module-glue.js:133](host/web/module-glue.js:133), [module-glue.js:228](host/web/module-glue.js:228)). A background storage completion can call a saved controller’s `abort()`, but `backgroundRound()` returns without that array ([module-glue.js:321](host/web/module-glue.js:321)); Rust’s background handler likewise only processes background state ([lib.rs:787](js/web/src/lib.rs:787)). With no subsequent ordinary turn, the request and parked answer remain held. Forward and consume cancellation on background completion too.

5. **Should-fix — the new realm request index leaks abandoned requests and their bodies.**  
   Every request is indexed in `requestMaps` ([module-glue.js:151](host/web/module-glue.js:151)), but entries are removed only on explicit withdrawal or handout. Consider an answer issuing two fetches and being forgotten while awaiting the first: the second remains indexed. Realm forgetting drops the parked call ([module-glue.js:405](host/web/module-glue.js:405)), while `__exact_forget` removes pending promises without issuing door 16 ([prelude.js:1292](js/src/prelude.js:1292)). The index therefore retains the abandoned request map, including unsent bodies. The worker realm has the same lifecycle. Remove all remaining index entries when their owning call retires.

6. **Should-fix — the TypeScript runtime compatibility discriminator must move.**  
   [compat.rs:38](bake/src/compat.rs:38) explicitly defines this discriminator for semantics supplied by the binary’s prelude that an updated bundle relies upon. It remains `4`, and is included in native compatibility IDs at [compat.rs:521](bake/src/compat.rs:521). The prelude is compiled into the binary ([lib.rs:129](js/src/lib.rs:129)). Consequently, an app update relying on the newly documented rejection/cancellation guarantee can still reach an older binary that keeps the request running. The older-door fallback prevents an exception; it does not supply the new guarantee.

7. **Should-fix — an expired DNS wait can start another lookup and even accept its result.**  
   Deadline checks occur only while the pool remains full ([lookup.rs:87](vendor/ibex/crates/ibex2/src/transport/lookup.rs:87)). If a slot becomes free as the deadline expires, execution exits that loop and increments the count without checking the deadline again. It then launches another uninterruptible lookup. Furthermore, `recv_timeout(0)` can receive an already queued result, which is accepted without a deadline check ([lookup.rs:128](vendor/ibex/crates/ibex2/src/transport/lookup.rs:128)). Check expiry before reserving/spawning and before accepting completion. The existing tests do not cover this boundary.

8. **Should-fix — the documented capacity guarantee is stronger than the implementation.**  
   [reference.md:1033](docs/reference.md:1033) limits the caveat to a few milliseconds of connection closure. Async `IN_FLIGHT` and per-origin reservations actually remain until `Event::Ended` ([executor_async.rs:786](host/apple/src/executor_async.rs:786)); bytes remain until physical completion too. A synchronous `body_to` disk write can retain its worker indefinitely ([executor_body_to.rs:20](host/apple/src/executor_body_to.rs:20)). Distinguish releasing an application’s logical slot from reclaiming executor capacity. Keeping physical reservations is correct; promising their prompt availability is not.

9. **Should-fix — the gallery test change restores a documented flake.**  
   [dev-gallery.test.mjs:232](host/web-js/dev-gallery.test.mjs:232) reduces the idle timeout from 3,000 ms to 200 ms, while [line 239](host/web-js/dev-gallery.test.mjs:239) still expects both processes to be alive after observing their PID file. The removed comment explicitly records that 200 ms allowed termination before this assertion, about one run in five. Revert this unrelated change or synchronize the lifecycle assertion.

10. **Should-fix — the resolver regression tests can hang instead of failing, and the fifth-waiter test does not establish its premise.**  
    [lookup.rs:240](vendor/ibex/crates/ibex2/src/transport/lookup.rs:240) joins the request thread before opening its held lookup. If abort delivery regresses, that join never returns; the elapsed-time assertion cannot enforce its bound. The transport tests repeat this pattern ([rustls_http.rs:614](vendor/ibex/crates/ibex2/src/transport/rustls_http.rs:614)). Also, sleeping 50 ms and observing an unfinished fifth thread does not prove it entered the pool wait ([lookup.rs:276](vendor/ibex/crates/ibex2/src/transport/lookup.rs:276)). Use an observed wait-entry event, bounded completion waits, and cleanup that opens gates on failure.

11. **Nit — lookup helper accounting is not unwind-safe.**  
    [lookup.rs:116](vendor/ibex/crates/ibex2/src/transport/lookup.rs:116) releases the slot only after `lookup()` returns. Under unwinding, a helper panic permanently consumes a slot. The abort callback also retains a sender ([lookup.rs:76](vendor/ibex/crates/ibex2/src/transport/lookup.rs:76)), so the receiver does not observe disconnection and reach the advertised “ended without an answer” failure. This concerns unwind builds/library consumers; this repository’s release profile aborts on panic. A slot guard and explicit helper-failure delivery would close that gap.
