# Round 1

Verdict: NOT READY

The tables match the source writeup, and the relabeling of the phone runs is a real correction. The recommendation is not safe to follow. Option D cannot be emitted for this host's deployment floor, and option E's promised production win depends on use-set keys the composition does not have. The measurement plan and the regression check would not decide what they say they decide.

## Strengths

- The simulator table (§3.1) matches the source, including sample counts, image deltas, the overlap, `dyld_sim`, and the unused-link limit. The phone section separates the confounded 187 ms comparison (§3.2) from the paired first-after-install runs (§3.3) and says the latter is one sample per cell. That is the right reading of the writeup, which had called those paired runs "cold."
- The import claims in §3.4 hold. `Picker.swift:16` imports PhotosUI only in the UIKit branch; `Auth.swift:9` imports AuthenticationServices; neither `Package.swift` nor `build.mjs` names either framework. The media branch is `accept` made only of `image/` and `video/` (`Picker.swift:229-240`). The file URL is copied inside `loadFileRepresentation` (`Picker.swift:254-277`). Agent mode returns before either OS object is built (`Picker.swift:79-82`, `Auth.swift:48-50`). `Auth.swift` is 110 lines; `Picker.swift` is 311.
- Option E's target shape matches the mechanism that exists: a capability target, `EXACT_APPLE_LINK`, `install()` from the composition (`Package.swift:19-33`, `host/apple/Sources/ExactEmbedded/Composition.swift:15-30`, `host/apple/link.mjs:6-22`). Development linking everything is LLP 1047.001 D6, and the draft says so (§5 E).
- The linker quotation is accurate. Installed `ld.1:215-217` says `-delay_framework` is "the same as `-framework` … but also specifies that the framework should be delay initialized," and documents `-delay_library` and `-delay-l`. It documents no `-lazy_framework`. Dropping the writeup's `-lazy_framework` was right.
- §2 uses the 100 ms cold-start budget (`rules/RULES.md:41`) and says these launches are already 337–506 ms to interactive with or without the frameworks. Weak linking and mergeable libraries are correctly set aside (§5).

## Concerns

1. **blocking.** Option D is not available at this host's minimum OS, and §5 D no longer says so. `mach-o/loader.h:713-730` defines delay-init as `DYLIB_USE_DELAYED_INIT` on `dylib_use_command`, "First supported in macOS 15, iOS 18." The host floor is iOS 17 and macOS 14 (`Package.swift:83`, `host/apple/build.mjs:116-127`). A binary whose deployment target is 17.0 does not get that load command. The source writeup named the iOS 17 minimum as a condition; the draft's §5 D (lines 109–114) drops it and still calls D a morning's experiment. Q1 (line 144) then aims D at the simulator. Resolving this means stating the iOS 18 / macOS 15 floor, and treating D as unavailable for any build whose `minimumOS` is below it.

2. **blocking.** The production result claimed for E is not what today's keys do. The summary (lines 16–19) says an app that never picks media or signs in links neither framework. `Capability::Picker` is every `input type="file"` and every `showPicker` (`runner/src/uses.rs:51-53`, `:271-273`, `:381-383`). It does not look at `accept`. Using that key still links PhotosUI for a PDF file input. A media-only key is new use-set work, and LLP 1047.001 D2 counts a computed value as every arm it might take; §5 E does not say what a non-constant `accept` does. Authentication is not a `Capability`. On Apple, `Links::of` always installs the auth function pointers (`host/apple/src/link.rs:128-129`, `:199`). The web adds `"auth"` from an `auth.session` grant (`contract/cli/src/logic.rs:149`). `appleComposition` only reads `graph.uses` plus the manifest `link` list (`host/apple/link.mjs:18-21`). A grant-keyed Swift target needs the same kind of extra as I/O in `bake/src/link.rs:32-44`, plus a name `Capability::from_name` accepts. The auth hold and `cancelAuthSessions()` live in the file that imports the framework (`Auth.swift:33-50`, `:100-109`; called from `Session.swift:1009` and `:1461`). Moving that file into a target that development still links puts AuthenticationServices back on the agent launch. Resolving this means deciding the two keys, naming the bake and `link.mjs` changes, and keeping the agent hold and teardown in core.

3. **material.** The order E, then D for the simulator, then B, does not match the cost that was measured. E leaves development on `EXACT_APPLE_LINK=all` (the draft says this at line 105). `scripts/agent.mjs ios` is that development build, so E leaves the simulator's agent launches alone. The simulator's extra time tracks extra images: PhotosUI +297, AuthenticationServices +313, and +320 together (§3.1). `QUEUE.md:70` attributes that to `dyld_sim` parsing Mach-O headers. §5 D (line 112) says delay-init still records a load command and still maps and binds at launch. D cannot remove that image-mapping cost even on iOS 18. B, or a link that does not compile the presenter, is what removes the load commands. Agent mode already returns before either class is built, except `EXACT_DEVICE=real` (`Picker.swift:79-82`, `Auth.swift:45-50`; LLP 1069.007). A development link that omits the presenter file would drop both frameworks from the agent path with no new artifact and no Objective-C loader. That option is missing. Closing A "so it is not proposed again" (line 128) is early: A is the loaded tier this repo already uses (`VideoModule.swift`), and it is the option that removes the load commands if B is rejected.

4. **material.** The draft assigns the phone's 46 ms to initializers that D might save. §3.3 says the ~100 ms "split between exec (−76) and UIKit's start (−46)." Those deltas sum to 122 ms; interactive falls by 103 ms (440 to 337). The spans are not a partition of the 100 ms. §5 D (line 112) then treats "UIKit → app delegate was 46 ms of the 100" as the initializer share. The source only reported the two deltas. Nothing in the samples separates mapping, paging, and initializers. The word "exec" has also drifted: the source defined it as process start to Exact's constructor; this tree's own figure is process start to `main`, including every initializer before `main` (`host/apple/Sources/ExactIOS/main.swift:17-28`).

5. **material.** §4 will not decide what it says it decides. M1 has no sample size and no rule for what counts as real. It does not require `otool -L` or an image count on the phone builds, so a prototype that still pulls the frameworks in transitively can be read as a zero. M2 is one Instruments trace per variant, on a phone, of an unspecified cold; the two colds already disagree for the linked build (exec 124 ms after install, 171 ms after reboot, §3.2–§3.3). The simulator's second is a different loader, and M2 does not trace it. M3 runs `scripts/agent.mjs ios` (development, link all) and says that decides the smoke gain too. LLP 1047.001 D6 sends an app's smoke through the production composition, which after E is a different link. iOS prewarms the process before a tap (`host/apple/Sources/ExactKit/PageFacts.swift:128-129`); M1 does not mention prewarm or the device shared cache. The budget comparison treats the measured "interactive" as `rules/RULES.md`'s "interactive first frame." This repo's matching clock is `firstDrawMs` (`Session.swift:399`, `ExactIOS/main.swift:153`).

6. **material.** §6 misdescribes the host and under-specifies the check. ExactIOS already prints exec→main, main→didFinishLaunching, the stamp list, first layout, and first draw when `EXACT_SMOKE=1` (`ExactIOS/main.swift:148-154`). The agent's `ready` payload is boot, views, error, and pid (`ExactIOS/main.swift:120`). macOS already puts `firstPixelMs` on `state` (`ExactMac/main.swift:271`). The work is to put the existing phases on the iOS `state`, which is still apparatus and needs a yes. The launch-link check is apparatus too (`rules/RULES.md:64`) and is not marked as needing one, while Q2 and the phase report are. "Today's 13" is not listed. `otool -L` shows the binary's direct load commands; the simulator cost was hundreds of transitive images. A delay-init framework still has a load command, so a check that allows whatever a capability names does not fail a framework that is still mapped at launch. Putting the check in `build.mjs` or the async lane, rather than the five-check gate, does respect the 60-second budget.

7. **material.** Option B states a runtime rule that is not established. Line 121 says an Objective-C delegate's protocol is not checked at run time, so an `NSObject` that implements `picker:didFinishPicking:` is enough, and that `ASWebAuthenticationPresentationContextProviding` is the same. Some of these APIs call `respondsToSelector:`; some call `conformsToProtocol:`. Which one these two use is a prototype result. If it is `conformsToProtocol:`, `objc_getProtocol` and `class_addProtocol` after `dlopen` are still public, so B survives, with that step written down. The sharp edge is the one the current code already has: copy the provider URL inside the callback (`Picker.swift:254-268`), hop to the main queue, and keep both initializers (`Auth.swift:64-73` — `callbackURLScheme` below iOS 17.4, and `.https` / `.customScheme` from 17.4). `NSItemProvider` is Foundation, so that part can stay typed. Public classes and public selectors reached through `dlopen` are not private API by themselves; a private selector would be. The handle has to stay mapped for the process. LLP 1029.000's `dlclose` rule is about pinned Rust images; `VideoModule.swift:38` does `dlclose` a failed video probe.

8. **material.** The proposed flags only partly match how `build.mjs` links. `-Xlinker` is already how this script talks to `ld` (`build.mjs:760-772`), and `-Xswiftc -Xfrontend` is already how it passes `-internalize-at-link` (`build.mjs:754`). `-disable-autolink-framework` is a string in `swift-frontend` and is absent from `swiftc -help` and `swiftc -frontend -help`, so SwiftPM may accept it through `-Xfrontend` or reject it as unknown. `--embed` builds no Swift (`build.mjs:933-938`). An embedder compiles ExactKit and reads `capabilities.json`, whose `swiftFlags` today carry only the size optimization (`build.mjs:956`). The compile-time autolink suppression and the link-time `-delay_framework` are two different arguments, on the embedder's own `swiftc` and `ld`. The same `swift build` invocation also builds macOS and tvOS. `-delay_framework PhotosUI` on those links adds a framework the macOS link does not have (`Picker.swift` imports PhotosUI only under `canImport(UIKit)`). An embedder who omits the flags keeps today's autolink, which still launches.

9. **minor.** The related line says the 2026-10-05 `QUEUE.md` entry now points here. `QUEUE.md:70` does not. It still says about 1.1 s each, that a phone very likely pays nothing, and that the fix is an on-demand artifact.

10. **minor.** "tvOS links neither, judging from the built binaries" (§3.4) cannot be checked in this checkout. The PhotosUI import is not inside `#if os(iOS)` (`Picker.swift:14-16`); tvOS takes the stub presenter (`Picker.swift:215-220`) and the PHPicker types are compiled only after that. `import AuthenticationServices` is unconditional (`Auth.swift:9`); the session type is used only under `#if !os(tvOS)`.

11. **minor.** §3.4 names `Agent.swift` and `DocumentPickers.swift` as how core reaches the picker. The command callers are `Session.swift:1111-1120`. `Agent.swift:181` delivers the agent's answer. `DocumentPickers.swift` is the document-picker half of the same `Picker` class. That half, and `save`, staying in core is the right split.

12. **minor.** Q3's document-picker fallback for an image-only `accept` when the media target is absent would change LLP 1069.002's iOS rule and would be a silent gap. LLP 1047 D6 and LLP 1047.001 D5 already require a named refusal.

## Suggestions

- Rewrite Q1 around what each option can change. E can drop direct load commands from a production binary whose composition omits the new keys. It leaves `EXACT_APPLE_LINK=all` builds as they are. D can defer initializers only when `minimumOS` is at least iOS 18 and macOS 15, and only if nothing initializes the framework while ExactKit loads. B, or compiling the presenter out of the agent link, is what removes the commands from a development launch. Keep A as the fallback that matches `VideoModule.swift` if B's delegate and block prototype fails.
- In §5 E, name the bake change beside the Swift target: a new use-set bit or a grant input, `exact_bake::apple_link`, `link.mjs`'s `SWIFT_CAPABILITIES`, the composition `install()`, and the `--embed` product list. State the computed-`accept` rule in the same paragraph.
- Make M1's decision rule numeric: at least five samples per cell, both phone colds, `otool -L` and an image count recorded per binary, install method fixed, prewarm called out. Point M2 at both loaders if D or B is supposed to explain the simulator. Split M3 into the development agent launch and a production-composition smoke.
- Point §6 at `ExactIOS/main.swift`'s existing print and at the macOS `firstPixelMs` field. List the allowlist from a fresh `otool -L` of a one-text production binary, with capability frameworks declared on the targets that import them (`GameController` and `AVFAudio` are on `ExactSurfaces`, not on core). Mark the check as needing a yes.
- For B, replace the protocol sentence with a prototype assertion, and list the two `ASWebAuthenticationSession` initializers and the in-callback copy as behavior the prototype has to keep.

## Open questions for the author

- Was "exec" on the phone process-start to a constructor, or this tree's process-start to `main`? The two include different initializer time, and D only has a chance at the latter's initializer slice.
- Should an agent build, which never constructs these objects unless `EXACT_DEVICE=real`, link PhotosUI and AuthenticationServices at all? LLP 1047.001 D6 says development links every capability so any plan runs. The agent substitute already satisfies that without the system frameworks.
- For a non-constant `accept`, does the media key link PhotosUI always, or only for a literal image/video list?
- Which apps in the farm have an `auth.session` grant or a file input? "Most apps never use" these two (§2) is doing a lot of work in the recommendation.
- The header cites `ld-27037.1` from Xcode 27.1. The wording matches the `ld.1` on this machine. Was the iOS 18 note in `loader.h` checked against that same linker?
