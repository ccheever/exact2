- **Family:** xAI. Grok 4.7, reasoning effort xhigh, run by the orchestrator against r1 (`6281b7b74`, on main). Codex/Astra's budget was exhausted, so this review and its companion (`1092-r1.grok-b.md`, implementation scope) are one family with two scopes. There is no second family.
- **Scope:** semantics only: driver-clock determinism, `then`/`refreshes`/`pending` interactions, predictability.
- **Transcription:** the run's output, unedited (from `~/projects/x2apps/_reviews/llp1092-r1-a.grok.md`).
- **Verdict:** READY WITH CHANGES. Four MATERIAL, four MINOR and two NIT findings.
- **Disposition:** the author checked each finding against the code; every one held. r2 resolves them, with no new round yet (round 1 of 3).
  1. **MATERIAL, no wake for a queue without `then`: taken.** Confirmed: `timer_due_ms` chains only timers and `then_due` (`runner.rs:1199–1208`); Apple reads it per batch (`host/apple/src/host.rs:1132`). D3 puts `next_due` on the wake path, in `drive()` too, and says `clock settle` runs due `next`s and waits on what they hand out.
  2. **MATERIAL, a refused `next` wedges the queue: taken.** Confirmed: `conclude`'s error path restores the checkpoint (`commit.rs:56–82`), and `arm_then` runs only when the commit stood (`:386`). D3 pops the head before `checkpoint()`, and a state-based scan after every commit arms the successor at that time, ahead of any timer.
  3. **MATERIAL, frame arming used the seek clock: taken.** Confirmed: `frame()` fires frame tasks at the presented frame and restarts `base` (`commit.rs:156–187`), and `advance` skips frame timers while presenting (`:245`). D10 splits the rule: presenting lists the task for the next `frame(now)`; seeking arms the next virtual frame.
  4. **MATERIAL, Lean drains in `dispatch`, and gates read before settle: taken.** Confirmed: Lean `boot` runs `startTimers` before `settle` and `lateSlots` (`Runtime.lean:548–555`); difftest taps `r.dispatch` without `land_then` (`observe.rs:191–193`).   5. **MINOR, the seek equality under the driver: taken.** Confirmed: `advance_until_request` stops at a commit that hands out a request (`commit.rs:192–197`). D10 scopes the equality to `advance` with no reply outstanding; §5 adds the driver case.
  6. **MINOR, `pending` is not idle, and `m = none` does not stick: taken.** D4 says `pending` is false while a `then` is armed and nothing waits, that sending while pending feeds the queue, and that later replies overwrite an assignment. D6 omits the `queue` hint when the action assigns the slot.
  7. **MINOR, ask-time `refreshes` and reload: taken.** D4 says the re-read uses the ask commit's arguments, the queue is not carried, and a kept answer records no unasked send.
  8. **MINOR, key comparison: taken.** Confirmed: `key_text` folds `-0` and has no NaN (`instance.rs:1028–1039`); Lean `rowKey` refuses non-finite keys. D8 compares by `key_text`; a non-finite key refuses its commit (`RunnerError::TaskKey`).
  9. **NIT, the `now()` reason: taken.** D9's message now gives the reviewer's reason.
  10. **NIT, a `Later` round is not a reply: taken.** Confirmed at `commit.rs:1036–1042`. D3 keeps the send in flight until `Now` or a release.

I'll review the design for semantics only: driver-clock determinism, then/refresh/pending interactions, and whether authors can predict the behavior. I'll read the RFC, the rules, and the cited LLP and diary evidence without changing anything.The RFC is in hand. Next I’ll check the cited specs and the current runner behavior those decisions rest on.The queue and the gate are the right models. A FIFO send with arguments captured where the `send` stands matches TanStack's scoped mutations, and a gate plus `key=` matches a React effect that arms a timer. Four holes in the clock and failure rules would make that model disagree with itself, with the driver, or with the hosts.

1. **MATERIAL** — §D3, §D10, §D4. A queued send with no `then` is never asked on a wall-clock host.
   **Problem.** The mutation becomes free in the reply's `fulfill`, which is not an `advance`. `next_due` is described as sitting beside `then_due`, but nothing puts it on the wake path. `timer_due_ms` today is what Linux (`display.rs`), Apple (the batch's `timerDueMs`), and the JS `drive()` loop actually wait on, and D10 says it "reports only armed tasks", that `clock settle` is unchanged, and that hosts do not change. Settle waits for requests in flight (LLP 1012 §2). A waiting send is not in flight.
   **Evidence.** Kanban's lost tap is a second `send` while `wrote` is in flight (`kanban2/DIARY.md:33`). With no `then`, the reply commits, `pending` goes false, and the label send sits until some unrelated advance. JS arms a wake only when a `then` is set (`rt.js:184`). Studio's `rec` is a mutation with no `then`. A queue that has a `then` survives only because that `then` already wakes the host and D3's loop can ask the next send inside the same `advance`.
   **Fix.** State that `timer_due_ms`, `has_timers`'s deadline, and JS `drive()` include `next_due` exactly as they include `then_due`, and that `clock settle` does not return while any send is waiting. One reply, then one ask, with no extra tap and no other timer.

2. **MATERIAL** — §D2, §D3, §D8. A refused `next` is specified two ways, and one of them wedges the queue.
   **Problem.** The queue lives in the checkpoint, so a refused commit restores it. D8 moves arming into `conclude` and says nothing arms in a refused commit. D3 also says a refused `next` drops that send, journals it, stops the advance, and arms the following send. After rollback the bad head is still first, the successor is not armed, and the next advance asks the same head again until `TIMER_FIRE_LIMIT`, then leaves it there.
   **Evidence.** A `then` that refuses leaves the previous answer standing because that answer was an earlier commit (`commit.rs` `arm_then` runs only when the commit stood). The ask is the whole of a `next` commit, so the same rule undoes the drop. LLP 1016 D4's shaped failure is an answer and must run `then`. The refusal in D3 is the other one: the source errors, or the value misses the shape.
   **Fix.** After the rollback, drop the head and arm the successor. That pair is not part of the refused commit. Say the advance's error is the same shape as a refused `then`, and that the following send is due at that time so the next successful `advance` asks it before any timer.

3. **MATERIAL** — §D8, §D10, against LLP 1073 D2–D4. "The next virtual frame" is the seek clock, not the display.
   **Problem.** D8 arms a gated `every(frame)` at `now + 1000/60`. On a presenting host, LLP 1073 fires the task once on the next displayed frame and does not catch up missed frames. `advance` does not fire frame tasks while `present_frames` is on. A flight phase that waits for a virtual quantum either starts late or, if some other advance runs, replays frames the display is required to skip. ProMotion is not 60 Hz. The seek equality in D8 is true only for the virtual grid.
   **Evidence.** LLP 1073 D4: `frame(now)` fires each frame task once at `now` and restarts `base`. `rt.js` `paint()` does the same for every listed frame task. D10 says `wants_frames()` becomes "a frame task is armed" and that hosts do not change. The Messages example in D7 is this task.
   **Fix.** Split the arming rule. While a host is presenting, arming sets `wants_frames` and the next `frame(now)` runs the task once at that frame. While the agent or a test is seeking, arm at the next virtual frame from the commit's time, and `advance(60_000)` matches sixty `advance(1_000)`s including those frames. Idle means the task is not listed, so `paint()` stops.

4. **MATERIAL** — §D12, against `semantics/Contract/Runtime.lean` and `semantics/difftest`. The Lean step does not observe the same queue the runner does.
   **Problem.** D12 drains `Config.queued` at the end of `dispatch`, one commit each. The runner's `dispatch` asks only the idle send and leaves the rest for `land_then` or `advance` (`commit.rs:207`, `481–518`). Difftest observes a single `dispatch` (`semantics/difftest/src/observe.rs`) and does not call `land_then`. A second synchronous send is already in the Lean slot and still queued in the runner. Separately, Lean `startTimers` runs before `settle` (`Runtime.lean:548–552`). D8 reads the gate after the first settlement. A gate that reads a resource or a derive arms from the wrong value, and difftest will call that a runner bug.
   **Evidence.** Lean asks every send inside `runAction` today (`Runtime.lean:477–483`) and has no `then`. The property that makes a queue different from "both answers in one commit" is that the next ask is its own commit after `then`. That order cannot be proved while `then` stays outside the model, and draining inside `dispatch` proves a different order.
   **Fix.** Keep the queue in the config. Have the harness drain it the way `land_then` does, and have `advance` drain it before timers, at the commit's time. Apply D8 to the booted config after `settle`, not inside today's `startTimers`. Name the corpus as `then`-free and frame-free, and keep the per-reply `then` order a runner test.

5. **MINOR** — §D8, §5, LLP 1012 §2. The seek equality is not what the driver does once a send exists.
   **Problem.** `Runner::advance(60_000)` fires every due timer without waiting, so a gated `every` whose `then` would clear the gate still fires the whole window and queues a send per tick. `clock +60000` and sixty `clock +1000` both stop at each commit that hands out a request and land the reply before the next timer (`agent.js` clock jump, `host/linux/src/agent.rs` `clock_stepped`). Under the driver the gate stops the later ticks. The two driver shapes match each other. They do not match the §5 test.
   **Evidence.** LLP 1012 §2, the comment on `advance_until_request` (`commit.rs:192–197`). Ledger2's exit check is `perf during "clock +60000"`, which is the driver.
   **Fix.** Say the runner equality is for `advance` with no outstanding reply, and that a driver jump waits. Add one driver case: a tick sends, its `then` clears the gate, and both `clock +60000` and sixty `clock +1000` stop together.

6. **MINOR** — §D2, §D4, §D13, LLP 1016 §4. `pending` is not "idle", and `m = none` does not stick.
   **Problem.** `pending` is false while a `then` is armed and nothing is waiting, even though D2 says the mutation is not idle. Kanban dropped the label tap because the handler checked `not pending(wrote)` (`DIARY.md:33`, `:71`). That guard still drops a tap that arrives while the request is in flight. The queue only helps a `send` that runs anyway. Separately, an assignment writes the slot and forgets nothing, so the in-flight reply and every later reply overwrite `m = none`. That is the logout rule (LLP 1016 §4: the late sign-in reply is dropped) inverted for `queue`. D6's diagnostic offers `queue` as the fix for every double send, including one the app also assigns.
   **Evidence.** `contract-for-agents.md:322–324` is the sentence authors copied. Flashcards' `afterEdit` keys off `ack.op == "saveCard"` (`app.contract:88–89`), which works only because each reply gets its own `then`. A session mutation does not want that.
   **Fix.** Say that sending while `pending` is how a queue is fed, and that `not pending` means "the spinner is off", not "it is safe to skip". Say that a queued reply still writes the slot after `m = none`. Keep the diagnostic's `queue` hint off any mutation the same action assigns.

7. **MINOR** — §D4, §D5, LLP 1027.005, LLP 1054.000.000. Ask-time `refreshes` and reload do not keep the captured write.
   **Problem.** Mutation arguments are frozen at the `send`. A `refreshes` re-read runs when the send is asked, with the resource's arguments at that later commit. Those arguments can move while the send waits, so the overlay is not the body that will be written. Reload and poison drop waiting sends (D4) and do not re-ask them (LLP 1016 D5). A kept answer (LLP 1027.005) stays matched, because identity never saw the dropped send. The carried draft can say the edit happened and the resource's kept frame says it did not, with `pending` false.
   **Evidence.** LLP 1054.000.000 D1 re-reads at send time so the overlay is immediate. Queue moves that send time. `boot_carrying` keeps slots and drops tickets (`runner.rs:551–554`).
   **Fix.** Say the re-read uses the arguments of the ask commit, not the queued body. Say the queue is not carried, and a kept answer is not a record of a send that was never asked.

8. **MINOR** — §D8, §D9. "Compared as an `each` key" is not `!=`.
   **Problem.** An `each` key uses `key_text`: `-0` is `0`, and `NaN` is not a key (`runner/src/instance.rs:1028–1039`), so the commit refuses with `KeyKind`. IEEE `!=` treats `NaN` as a new key on every commit, re-arms the timer, and the seek runs until `TIMER_FIRE_LIMIT`. A number-typed key can be `NaN` at runtime. The type refusal does not catch it.
   **Evidence.** Lean `rowKey` (`Runtime.lean:273–281`) already refuses a non-finite key and folds `-0` to `0`.
   **Fix.** Compare with `key_text`. A non-finite key refuses that commit and does not change the timer.

9. **NIT** — §D9. The reason given for refusing `now()` in a gate is stronger than the rule.
   **Problem.** D9 says `when now() < toastUntil` would never become false, because `now()` is re-read only at commits. D8 re-reads the gate after every standing commit, including the task's own fire. An `every` would stop on the first fire at or after the deadline. An `after` would still fire once, because nothing commits earlier.
   **Fix.** Refuse it for that reason: an `after` cannot be cancelled before it fires, and an `every` stops up to one interval late. Gate on state.

10. **NIT** — §D3. "Its reply lands" includes a continuation round if read against `fulfill`.
    **Problem.** `Answer::Later` keeps the same send, swaps the ticket, and does not push `landed` (`commit.rs:1036–1042`). Treating that as the request ending asks the next send between the storage step and its continuation, which is the dropped save in §1.1. §5's two-step test is right. The free-condition sentence is not.
    **Fix.** The send stays in flight until `Now` or a failure that brings no answer. A further `Later` is not a reply and does not run `then`.

Verdict: READY WITH CHANGES
