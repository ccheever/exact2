Five fundamental concerns, most serious first.

### 1. The benchmark's only definition of jank is a late frame. Most of Excord's jank is not a late frame.

**Issue.** D1 exits non-zero on a missed frame and reports nothing else about what the scroller did. Of the four causes the RFC lists, the rubber band fighting AppKit (`068772f00a`) produced jumps, not dropped frames. The open issue the RFC cites (`issues/20261022-reach-lead-is-fixed-at-one-screen.md`) is "the scroll stops at the edge and then jumps on." Excord's `scrollEnded` yanks the list back to its end with `behavior="instant"` (`apps/excord/app.contract:614-618`). A virtualized list whose fill lags shows blank rows, which `ScrollPumpIOS.fillCollections` explicitly chooses over a late frame ("its rows wait for the next slice rather than making this frame late", `host/apple/Sources/ExactKit/IOS/ScrollPumpIOS.swift:168-170`). Excord's own bar names these separately: "no stall and no jump" (`apps/excord/llp/0001-excord.rfc.md:150`) is a different item from the frame budget (`:190-192`). D1 passes all of them.

**Why fundamental.** The user's goal is to see and head off janky scrolling. A benchmark that certifies "no frame over budget" while the list stalls at an edge, snaps back, or flings over blank rows will be green on exactly the jank a person reports, and will send an agent looking at phases for a problem that is not in main-thread time.

**Instead.** The sampler already runs a display link per segment and keeps a 600-record ring. Add one or two numbers per record: the target scroller's presented offset (and for a collection, rows in the port not yet filled). D1 then reports, beside late frames, offset discontinuities (reversals, mid-deceleration stalls, deltas beyond velocity × period) and blank-row frames. That is what would make it Excord's criterion; late frames alone are one of three axes.

### 2. `scroll=` is delivered synchronously on the frame's critical path. D3 and D5 treat the cost as the author's, and D5's exemption gets it wrong.

**Issue.** On iOS, while tracking or decelerating, every `scrollViewDidScroll` with a `scroll` handler calls `sendScrollEvent()` "before the frame paints" (`host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift:787-792`) → `PresenterIOS.scroll` (`PresenterIOS.swift:679`) → `Session.onScroll` → `runtime.scroll` (`Session.swift:781`) → `Bridge.swift:424-428`, which runs inside `on {}` → `Owner.shared.sync`, where main blocks until the runner has dispatched, committed and run kernel layout (that wait *is* the `runtime` phase, per 1142 §12 and `Owner.swift:106`). The batch is then applied in the same turn. So every scroll event with any handler is a synchronous main-thread round trip into app code at up to 120 Hz, regardless of what the handler writes.

Excord's `scrolled` writes `scrollTick`, `endGap`, `historyStart`, `topKey`, `topOffset` unconditionally on every event (`app.contract:579, 608-611`). D5 exempts exactly this ("a write only actions read … commits nothing the view sees"), but the commit, the runner turn and main's wait still happen. D3's note ("each commit is a runner turn") is correct and understated.

The code's justification for synchronous delivery, "so authored scroll-linked geometry cannot lag a frame", is the use DEFERRED already routed to presentation timelines, "evaluated by the engine, with no app code per frame" (`rules/DEFERRED.md:1215-1222`).

**Why fundamental.** LLP 1115: what the author leaves unsaid is the platform's, as a hand-built UIKit app has it. A UIKit app does not run app code on the paint path of every scroll frame. A compile-time warning telling authors to guard their handlers is the wrong layer for a platform property; `4d404187a7` (hover follows a scroll once it rests, not every frame) already fixed the same shape at the platform, not with a warning.

**Instead.** Take `scroll=` off the paint path: coalesce to one dispatch per frame, delivered after the frame's commit (or on the runtime thread without main waiting, applied next frame), with the synchronous path either deleted or opt-in for the rare handler that truly needs geometry before paint. Then D5 is unnecessary, and D3's line becomes a measurement ("180 events, 180 commits, 9.4 ms runtime") rather than a moral.

### 3. The simulator cannot be the criterion, and one missed frame is a flaky gate; meanwhile the host where the jank was found is excluded.

**Issue.** The touch runner is "Simulator only so far; a phone is LLP 1080.000 stage 4" (`host/apple/touches.mjs:11`). Excord's criterion is "on the slowest device in each host's support range" (`0001-excord.rfc.md:192`). A simulator's frames are the Mac GPU's and its display link the Mac's; the accessibility runtime may be loaded (`touches.mjs:210-212`: 10 ms → 1.4 s launch); `trace --pid`'s simulator path is "unexercised" (1142 §12). Excord's own review already made this point: "simulator tests or filmed drives" cannot establish the frame-rate requirement (`apps/excord/llp/reviews/0001-excord.astra.md:14`). The RFC itself says the jank was found "mostly on macOS", then defers macOS entirely (§3).

**Why fundamental.** RULES prefers counts over timers because timers flake. Exit-non-zero on a single missed frame among N flings on a shared Mac's simulator is a timer gate on the wrong device, and it will be either ignored or appeased. Calling it "an app's criterion" assigns it a role it cannot hold.

**Instead.** Present D1 as a per-fling *work* ratchet: rows created, handler commits, and `runtime`/`rows`/`text`/`image` ms per 1,000 pt of travel, with a tolerance, which is stable on a simulator and comparable commit to commit. Treat the frame-miss pass/fail as the device run (1080.000 stage 4) and say so. For macOS, the agent's existing `wheel … gesture` under `perf … during` already measures the work side (hover per row, rows built, commits) without needing momentum; two of the four fixed causes were Mac-only and are work, not physics.

### 4. D4 would not have fired on either Excord list it cites, and D6's member-list change fixes a 100-row list.

**Issue.** The member list is op 37's `[[0, 99]]` subscription (`apps/excord/live.ts:528-529`; `app.ts:401` "its first 100 rows"); no action grows it. The DM list grows through `dmsShownCount`, a slice bound (`app.contract:506-508`), not a `concat` or push in an action, and is already capped at a hundred plus unread. The transcript is already `list virtualized=true`. So D4's growth evidence ("an action appends to it", "the scroller pages") matches neither, and D6 converts a list whose actual fix (`f3af880a77`) was keys, not count. Whether data grows is a runtime fact; the lowering is guessing.

**Why fundamental.** The warning is justified by the DM list that built 3,000 rows, and as specified it misses that case's shape while costing a `contract/` change and difftest. A warning with no true positive in its own motivating app is apparatus without a consumer.

**Instead.** The runner already counts `created` and `live` per plan site (LLP 1079), and 1142 D4 built an alert channel into `logs`. A development-build notice when a non-virtualized `for` in a scroller passes N live rows, named by site, is exact, needs no guess about data, and reaches the diary. Drop the compile-time heuristic.

### 5. The RFC adds a script and a criterion and says it adds nothing; RULES says this needs Charlie's explicit approval.

**Issue.** "This adds no operation; it is a script over `trace` and the touch runner" (D1). RULES: "An agent PR that adds a check, script, registry, config file, or design doc needs explicit human approval saying so." `scripts/fling.mjs` is a script, and "stand as an app's criterion" makes it a check in all but name. The RFC should ask for the waiver in its open questions, not assert the exemption. (The `bench/` directory is the existing home for per-app benchmarks, which may be the better fit than `scripts/`.)

Also for the record: D2 is already built in this worktree (`HostPhases.swift` has `case image` citing "LLP 1144 D2"; `RasterLoader.swift:765` and `AnimatedRasters.swift:89, 154` wrap it; all three uncommitted). Not a concern, but the RFC should say it is describing shipped work.

The trace already carries `perf` (sites and `handlers`), so D1 step 4 can read handler commits from a plainly launched app without an agent connection.
