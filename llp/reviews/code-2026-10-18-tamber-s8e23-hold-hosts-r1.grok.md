# Review round 1, LLP 1121 stage 8 E2 (Apple) + E3 (Linux/Android) held states, Grok 4.7 (xhigh)

**WRONG.** E3 (Linux, and Android through that presenter) matches the E1 contract: takeover of an in-progress press, press and key let-go, hover and focus crossing, ancestor disable, revision handling, same-frame reapply without `replaced`, generation swap unsaid then `rehold` before `status`, `planDigest` as the runner's 64-hex SHA-256 in registration and status, and `held` rows via `row_json`. The file cap holds (largest touched file is `host/linux/src/host.rs` at 1495). E2 (Apple) does not. The defects below are all on the Apple host.

1. **BLOCKING** — A press already down is not taken over; its release ends the hold and clears the paint. `host/apple/Sources/ExactKit/PressFeedback.swift:107` calls `heldInput("active")` only when `pressed` becomes false, and `:111` then `paintPress(false)`. `pressFollows` at `:127` unpaints on drag-off with the hold still recorded. Mac `MouseChainMac.swift:134` and `:143`–`:148`, and iOS `PointerIOS.swift:386` plus `touchesEnded`, drive that. Web `host/web/input-glue.js:358` drops the in-progress press so its release leaves the held paint; Linux `host/linux/src/press.rs:213` returns from `press_feedback` when `!down` and the node is held active. Fix: when an active hold lands, detach the live gesture (Mac mouse-chain target, iOS press contact, invoker, agent pan) the way the web sets `press = null`. The release and `pressFollows` of that gesture must not call `heldInput` or `paintPress(false)`.

2. **BLOCKING** — A new press or a key never lets a hold go, for any state. Web `input-glue.js:395` lets go on capture `pointerdown` and `keydown` when the event is inside the held node. Linux `pointer.rs:143` and `typing.rs:553` call `hold_input` the same way. Apple only lets `active` go on the transition to `pressed == false` (`PressFeedback.swift:107`). `MouseChainMac.swift:121` and `PointerIOS.swift:370` set `pressed = true` with no hold hook; `KeyEvents.swift:85` and iOS `NodeViewIOS.swift:478` never call `heldInput`. A click on a held hover or focus leaves it up, and a held press survives until release, at which point finding 1 also clears the paint. Fix: on pointer-down and key-down, if the hit or the focus is the held node or inside it, `letGo("input")` for whichever state is held. A press that was already down when the hold was applied is finding 1, not this path.

3. **BLOCKING** — Focus coming or going does not let a focus hold go on iOS, and on the Mac only when the held view itself is the focus owner. The only `heldInput("focus-visible")` is `NodeViewMac.swift:245`, and `FocusMac.swift:43` sets `focusVisible` only on that focused view. iOS has no such hook, but `hold("focus-visible")` still applies the look (`HeldState.swift:78`). A focus-visible hold on a container also stays when focus crosses its boundary. Linux `held.rs:131` compares `within(focus, held.view)` and lets go on a change. Fix: on every focus change, if the hold is `focus-visible`, let go when the new focus is inside the held view and the previous one was not, or the reverse. Wire that on iOS at the same place the focus ring moves.

4. **BLOCKING** — `held.rows` values are cache keys, so the design tool cannot read them. `HeldState.swift:106` sends `BatchValue.key`. `Batch.swift:13` defines that as a cache key: a color array becomes `"[29.0,78.0,216.0,255.0]"`, and a string uses `debugDescription` (extra quotes). The same node's layout rows come from the runner as CSS (`runner/src/agent/row.rs:22`, `"#rrggbb"`). `scripts/tamber-inspect.mjs:147` copies `r.value` through. Linux `held.rs:323` uses `row_json`, and `held_tests.rs:138` expects `"#0000ff"`. The Apple test at `HeldStateTests.swift:62` asserts only the name. Fix: take the rows from the runner `node` op `layout` already parsed (press rows for `active`, the look's rows otherwise), and assert the value, not only the name.

5. **BLOCKING** — A disabled ancestor is ignored, so a hold can land on a press the real press cannot reach, and disabling that ancestor does not let go. `HeldState.swift:66` walks to the press handler and `:70` checks only that node's own `disabled` (`NodeViewMac.swift:234`). `PressPaint.swift:97` lets go only when that same view's `disabled` flips. iOS `InvokersIOS.swift:81` stops the real press at a disabled ancestor and returns nil. Web uses `closest(":disabled,[disabled]")` (`input-glue.js:336`); Linux `disabled_at` walks parents (`held.rs:177`). Fix: while resolving `active`, stop at a disabled node and answer `disabled` (gone only when no press exists). On any props change, let go when the held node or an ancestor is disabled.

6. **SHOULD-FIX** — A Mac hover hold lets go only for a node that already has a hover look and is in `lookHovered`. `HoverMac.swift:41` drops nodes with no hover look, and `hold` does not record an over bit of its own. Enter and leave then never call `heldInput("hover")`. Fix: track over for the held node from the hit path, including a node with no look, and let go when that bit flips. Moving inside the node stays, as `held_tests.rs:210` does on Linux.

7. **SHOULD-FIX** — A generation swap does not let the hold go unsaid on the path `applyTogether` actually runs. `Session.swift:304` sets `swapping` around `presentCommitted`, but `PresenterMac.reset` (`PresenterMac.swift:589`) and `PresenterIOS.reset` (`PresenterIOS.swift:356`) drop the views in `forget()` without `holdGone`. `rehold` (`HeldState.swift:117`) bails while `HeldState.view` is still alive, and nothing retries. Mac `MouseChainMac.swift:602` keeps the pointer-down view in the window, so that retain is real. A press cancel inside `reset` can also `letGo("input")` while `swapping` is true (`swapping` only changes `holdGone`). The server then ends the hold, and `rehold` has no frame. Fix: at the start of `reset`, while `swapping` is true, `letGo(nil)` so the frame stays and `view` is nil before `rehold`. Ignore `heldInput` while `swapping`.

8. **SHOULD-FIX** — `HeldStateTests` do not test what their names and the E2 RFC claim. `testAHeldPressIsTheRealPressUntilARealRelease` (`HeldStateTests.swift:65`) assigns `pressed = false`; it never takes over a down gesture, never checks that paint survives, and never sends a key. `testANewGenerationLetsAHoldGoUnsaid` (`:91`) sets `swapping` and destroys; it never calls `rehold` or `applyTogether`. `testAHeldHoverGoesWhenThePointerComesOrLeavesNotAsItMovesWithin` (`:111`) repeats `setHoverPath([card])` and never moves onto a child. Fix: drive a real down-then-hold-then-up (paint stays, no `input`), a down after the hold (`input` at down), a key, a child move, `applyTogether` with the same digest (one `held` at the same revision, no `gone`) and a new digest (nothing said), and a held-row value.

9. **SHOULD-FIX** — An unknown state on the build channel is applied as a focus look. `HeldState.swift:78` sends anything other than `active` or `hover` through `lookState(focus:)`. `Inspect.swift:199` does not check the name. The agent path rejects it (`HeldState.swift:129`). The server's `holdRefused` also rejects it before a frame is sent, which is why this is not blocking; Linux still answers `unsupported` by name (`held.rs:220`). Fix: in `hold`, if the state is not `active`, `hover`, or `focus-visible`, return unsupported and do not paint. iOS `hover` already does this after the view is found.
