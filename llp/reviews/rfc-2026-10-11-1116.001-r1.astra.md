**D1 — RIGHT WITH CHANGE.** Fix these user-visible failures first. But “content replaced shows its top” is too broad: entering quiz results should reset position; refreshing or replacing a feed’s data should preserve the reader’s place. Define that distinction before implementation. Native grouped-row swipe actions are the right destination. Keep readout fitting explicitly opt-in, with a readable accessibility-size outcome; globally capping text size would hide clipping by sacrificing accessibility.

**D2 — RIGHT WITH CHANGE.** Accent colour and reusable content parts are useful, but they are only part of the answer to “generic.” Flashcards already used `exact:content` and remained generic; water-tracker used it and still stretched across desktop width. The reported weaknesses include composition, interaction affordances and state legibility—not merely palette. Make D2 about inexpensive, deliberate content design, including typography and layout. Reconcile that permission with docs and `no-tells` guidance that currently treats almost every literal text size outside a numeric readout as suspect. [Evidence](</Users/ccheever/bakeoff/rounds/r3/findings.md>)

**D3 — RIGHT WITH CHANGE.** This is the strongest proposed lever for structural quality: round 2 identified the one-screen teaching problem, and round 3’s polls repeated it. Patterns should replace assembly work and recipe reading, with adaptive desktop/phone composition, real routes and correct save/error behaviour already present. However, the proposed catalogue chiefly helps navigation-heavy apps. Its unchanged `one-screen` template does little specifically for tip-splitter or focus-timer. Keep simple apps simple; measure adaptation effort, including deleting unwanted scaffolding, rather than assuming generated code saves tokens.

**D4 — RIGHT WITH CHANGE.** Smaller, targeted reading and batched vocabulary lookup are right. File-size and line-count targets are inadequate acceptance criteria: moving material into recipes saves nothing if builders immediately read those recipes. Provide a minimal common introduction, then only the selected platform and pattern’s guidance. The one-screen tutorial should not duplicate the generated starting app. Measure total early context and subsequent steps. Cutting the core by 4.2 KB addresses only a fraction of the reported 16k-token context surplus. [Token anatomy](</Users/ccheever/bakeoff/rounds/r3/findings.md>)

**D5 — NOT PRESENT.** The supplied round-3 RFC contains only D1–D4; there is no fifth decision to assess.

**The larger missing lever is reducing complete authoring cycles.** D3 and D4 target the two biggest *measured cost categories*: steps and context. But they are not yet demonstrated to be the biggest effective interventions for small web apps. Round 2 already showed that Exact2 writes less code while carrying more context through more steps. Expand the workflow work beyond vocabulary batching: make type regeneration automatic in the ordinary build/test path, consolidate redundant validation/build work, and return requested drive observations together. Attribute the surplus steps to lookup, repair, build or verification before choosing further machinery. Preserve visual verification; eliminate repeated orchestration around it. [Round-2 evidence](</Users/ccheever/bakeoff/rounds/r2/findings.md>)

**The missing quality lever is complete, appropriate composition.** Ship patterns that demonstrate a bounded calculator/timer surface, a genuine desktop list-detail workspace, and meaningful completed/error states. A centred card works for water-tracker; a split workspace suits contacts. Neither “always use the width” nor “always centre a phone column” generalizes. The water-tracker screenshots make this especially clear. Accent, eyebrows and rings cannot repair those structural choices. [Grader report](</Users/ccheever/bakeoff/rounds/r3/grades/water-tracker/grade.md>)

**Principle risks need explicit resolution.** D2 says an authored root background is used on web while iOS keeps its grouped background “unless the author says otherwise.” Setting that background already *is* saying otherwise; require explicit platform scoping if different surfaces are intended. Likewise, app tint must preserve destructive/status meanings and explicit overrides. Pattern layouts are authored choices, so they can solve composition without changing bare CSS defaults. [LLP 1115](</Users/ccheever/projects/exact2/llp/1115-write-the-web-ship-the-platform.principle.md>)

**Overall: READY WITH CHANGES.**

- Bound scroll resets to meaningful screen transitions.
- Broaden D2 from decorative branding to deliberate composition and legibility.
- Make patterns replace reading and assembly, including for small web apps.
- Judge D4 by total context and steps; address repetitive workflow work.
- Resolve background precedence and contradictory design guidance.
- Use a few repeated or held-out builds alongside round 4 to distinguish improvement from run variation.
