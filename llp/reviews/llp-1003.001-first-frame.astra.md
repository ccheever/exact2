# Round 1 (gpt-6-astra, reasoning effort max, read-only, on r1 c166d914d)

**Verdict: NEEDS REWORK.** The first-frame origin is reasonable for the Bluesky lightbox, but D1–D6 do not yet define a safe lifecycle for pending motion or a consistent presentation boundary.

1. **P1 — Pending curves can advance, finish, or disappear before `start_pending` sees them.** [RFC:85](/Users/admin/.tuft/projects/exact2-bsky/llp/1003.001-motion-starts-at-the-first-frame.rfc.md:85)

   D6 changes retarget sampling, but Apple commits already call `engine.advance` before applying each receipt and again before presentation ([host.rs:1263](/Users/admin/.tuft/projects/exact2-bsky/host/apple/src/host.rs:1263)). `advance` samples **every** running key and removes completed curves ([engine.rs:533](/Users/admin/.tuft/projects/exact2-bsky/motion/src/engine.rs:533)).

   For example: start a 5 ms transition at t=0, commit an unrelated property at t=10, first display tick at t=16. The transition is already removed; D2 drops its record instead of presenting its start. Longer curves on other keys acquire advanced presentation values. An exit can likewise be destroyed by `present` before the anchoring tick ([presence.rs:305](/Users/admin/.tuft/projects/exact2-bsky/host/apple/src/presence.rs:305)).

   Pending must affect sampling, retirement, hold acquisition, interruption/reversal calculations, and deadline checks—not just the timestamp adjustment. D1 also misses SVG path transitions: `observe_path` constructs and interrupts `Running` directly ([path.rs:106](/Users/admin/.tuft/projects/exact2-bsky/motion/src/engine/path.rs:106)).

2. **P1 — The proposed anchoring point is neither a uniform frame timestamp nor necessarily the first presentation.** [RFC:112](/Users/admin/.tuft/projects/exact2-bsky/llp/1003.001-motion-starts-at-the-first-frame.rfc.md:112)

   Frame tasks receive `targetTimestamp`, while motion ticks receive `s.now()` ([Frames.swift:48](/Users/admin/.tuft/projects/exact2-bsky/host/apple/Sources/ExactKit/Frames.swift:48)). Let the callback’s wall time be C and its target presentation time be F. Anchoring and sampling the engine at C produces local time zero, but a CA animation with absolute `beginTime=C` has elapsed F−C when displayed. Running a frame task can advance the host to F first, changing this behavior through the host’s monotonic-time clamp. An unrelated frame task should not determine engine/CA phase agreement. Apple explicitly defines [`targetTimestamp`](https://developer.apple.com/documentation/quartzcore/cadisplaylink/targettimestamp) as the intended next display time.

   There are two further ordering holes:

   - `tick` can create layout transitions **after** the proposed `start_pending` call through height-driven layout ([host.rs:1115](/Users/admin/.tuft/projects/exact2-bsky/host/apple/src/host.rs:1115)). Those curves can present their start now and be shifted again next tick.
   - Normal iOS ticks can execute asynchronously and apply in a later main-queue turn ([Session.swift:593](/Users/admin/.tuft/projects/exact2-bsky/host/apple/Sources/ExactKit/Session.swift:593)). D4 cannot assume the replacement CA spec arrives before the original’s first display.

   Specify one frame context covering timers, frame tasks, layout, sampling, and native submission, including missed-target behavior. Preserve timers’ logical due times: [LLP 1073:64](/Users/admin/.tuft/projects/exact2-bsky/llp/1073-every-frame.rfc.md:64) deliberately distinguishes them from the frame task’s time. The RFC’s “inside tick means shift zero” is not true of the current receipt processing.

3. **P1 — Fully lowered animations may never receive the tick needed to start them; re-emission also omits native paths.** [RFC:119](/Users/admin/.tuft/projects/exact2-bsky/llp/1003.001-motion-starts-at-the-first-frame.rfc.md:119)

   Lowered-only plays deliberately do not enter `animating` ([animate.rs:156](/Users/admin/.tuft/projects/exact2-bsky/motion/src/engine/animate.rs:156)); `quiescent` therefore remains true ([engine.rs:657](/Users/admin/.tuft/projects/exact2-bsky/motion/src/engine.rs:657)). With no other frame demand, the display link stops and no `start_pending` runs. If another activity wakes it later, the pending record can instead rewind an animation that CA has already displayed.

   Pending native playback needs an explicit anchoring-frame demand, with its initial spec held/deferred until that anchor, or a deliberate exemption from this policy. Afterwards it should regain today’s ability to run without engine ticks.

   Re-emission must cover SVG scene animations and macOS’s lowered opacity, as well as UIKit box transforms/colors. Those are distinct paths in [svg.rs:28](/Users/admin/.tuft/projects/exact2-bsky/host/apple/src/svg.rs:28).

   **Repeated spec emission is not itself a double shift:** identical installed specs are skipped; changed specs replace the animation by ID, using an absolute start ([SvgScene.swift:91](/Users/admin/.tuft/projects/exact2-bsky/host/apple/Sources/ExactKit/SvgScene.swift:91)). The problems are premature playback, late replacement, and inconsistent sampling origins.

4. **P1 — A per-node shift cannot correctly update exit deadlines.** [RFC:94](/Users/admin/.tuft/projects/exact2-bsky/llp/1003.001-motion-starts-at-the-first-frame.rfc.md:94)

   D6 explicitly permits different shifts on one node, while D4 applies “the shift” to that node’s exit end. `play_exit` appends to existing plays rather than replacing them ([animate.rs:259](/Users/admin/.tuft/projects/exact2-bsky/motion/src/engine/animate.rs:259)).

   Suppose an ordinary play begins at 0 ms, an exit begins at 10 ms, and the first frame is 16 ms. Their shifts are 16 and 6 ms. A 100 ms exit must move its deadline from 110 to 116 ms. Applying both node entries gives 132 ms; collapsing them to an arbitrary node shift is also unsafe.

   Return changes associated with the actual curve/play or exit group, or recompute the relevant deadline from that group. Flights have a dedicated synthetic node and one progress curve ([flights.rs:91](/Users/admin/.tuft/projects/exact2-bsky/host/apple/src/flights.rs:91)), so their case is simpler. Preserve their intentional early-landing criterion rather than substituting the engine’s general settle time.

5. **P1 — The pending identity conflicts with LLP 1099’s component springs.** [RFC:77](/Users/admin/.tuft/projects/exact2-bsky/llp/1003.001-motion-starts-at-the-first-frame.rfc.md:77)

   LLP 1099 is **not** an additional native CA spring executor: iOS and macOS continue sampling the engine; `CASpringAnimation` remains unbuilt ([1099:615](/Users/admin/.tuft/projects/exact2-bsky/llp/1099-uikit-springs.rfc.md:615)). There is no automatic second native start to compensate.

   However, its duration/bounce springs retain multiple components per property. Retargeting adds a component while old components keep their own beginnings and ends ([1099:455](/Users/admin/.tuft/projects/exact2-bsky/llp/1099-uikit-springs.rfc.md:455)). “Later begin replaces the `(node, property)` record” loses older pending components. Shifting the whole property would instead rewind already-presented components.

   Pending state must belong to each newly born component, and survive promotion of an existing spring into component 0 without resetting its established age. This integration needs a decision in this RFC.

6. **P2 — D6’s play matching rule is incomplete: matched plays do not always keep their start.** [RFC:79](/Users/admin/.tuft/projects/exact2-bsky/llp/1003.001-motion-starts-at-the-first-frame.rfc.md:79)

   `set_animations` matches duplicate names from the end, but a matched pause captures `now-start`, and a matched resume changes `start` ([animate.rs:103](/Users/admin/.tuft/projects/exact2-bsky/motion/src/engine/animate.rs:103)). An unseen play started at 0, paused at 5, and resumed at 10 now has start=5; the `(node, start=0)` record no longer matches. Pausing alone already captures progress that the pending rule says should not have elapsed.

   Carry pending state through the actual matched play, including reorder, duplicate names, pause/resume, and dropping/replacement. Define transfer into and out of drag/clock timelines. Exempt plays actually joined to a clock, rather than every play on a clock-associated node: `play_exit` appends ordinary time-based plays without joining that clock.

7. **P2 — The proposed agent-switch location misses takeover paths.** [RFC:134](/Users/admin/.tuft/projects/exact2-bsky/llp/1003.001-motion-starts-at-the-first-frame.rfc.md:134)

   `presentFrames(false)` occurs in `advanceStepped`, but clock takeover happens earlier. `take`, `land`, and `data` return through other paths; `land` directly calls `runtime.tick` ([Agent.swift:482](/Users/admin/.tuft/projects/exact2-bsky/host/apple/Sources/ExactKit/Agent.swift:482)). Adding the switch only beside `presentFrames(false)` leaves these operations using frame-start semantics under an agent-owned clock.

   Disable it at the actual takeover, before those branches. Specify how pending curves and their deadlines transfer to seek mode, while preserving already-anchored starts. Also specify boot/reboot ordering so initial plays are recorded before their first batch is emitted.

8. **P2 — “Progress zero” and “at rest” are not universal curve semantics.** [RFC:38](/Users/admin/.tuft/projects/exact2-bsky/llp/1003.001-motion-starts-at-the-first-frame.rfc.md:38), [RFC:140](/Users/admin/.tuft/projects/exact2-bsky/llp/1003.001-motion-starts-at-the-first-frame.rfc.md:140)

   The coherent invariant is **local elapsed time zero at the chosen origin**, followed by ordinary evaluation:

   - Positive delays remain pending; negative delays intentionally start partway through the active curve.
   - Step timing, reversed keyframes, and fill behavior need not show the underlying `from` value.
   - A released spring has its supplied initial velocity, including at zero distance. `end_hold` explicitly supports this ([hold.rs:341](/Users/admin/.tuft/projects/exact2-bsky/motion/src/engine/hold.rs:341)); an unseen curve is not necessarily at rest.
   - Flights can use a zero origin if landing moves consistently. Exits need their own group’s end moved; older coexisting plays retain their ages.

   I support first-frame zero for newly scheduled visual effects, especially the rAF-triggered lightbox. **I would preserve release-time momentum for gesture releases**, rather than silently insert a stationary interval. If universal frame-zero releases are intentional, document and measure that added latency and preserve the velocity through intervening retargets/holds.

   This is a behavioral choice, not equivalence to CA. Reanimated’s [`valueSetter`](https://raw.githubusercontent.com/software-mansion/react-native-reanimated/main/packages/react-native-reanimated/src/valueSetter.ts) supports the same-timestamp initial step, but also has a non-frame timestamp fallback; it does not establish a universal first-presented-frame guarantee.

9. **P2 — Signal’s proposed acceptance test hides a real timing change.** [RFC:183](/Users/admin/.tuft/projects/exact2-bsky/llp/1003.001-motion-starts-at-the-first-frame.rfc.md:183)

   Signal schedules `runMenuAction` 400 ms after dismissal starts ([app.contract:1220](/Users/admin/.tuft/projects/signal-exact2/app.contract:1220)), paired with a 400 ms menu exit ([menus.contract:62](/Users/admin/.tuft/projects/signal-exact2/menus.contract:62)). Moving the exit origin without moving that logical timer makes the next action eligible before the exit finishes. Independently onset-aligned curves cannot reveal that choreography change.

   The trace tool already supports `--trigger` specifically to count late starts ([motion-trace.mjs:336](/Users/admin/.tuft/projects/signal-exact2/tools/motion-trace.mjs:336)). Require trigger-aligned recordings of the complete sequence, including keyboard/native motion, alongside curve-shape comparisons. “Only onset moves, by under a frame” is not established: the RFC’s own measured delay exceeds one interval, and stalls/asynchronous delivery remove that bound.

On the remaining Apple interactions: UIKit zoom, sheet presentation, and keyboard motion are separate owners and should remain exempt; I found no direct double shift there. `PressFeedback` is separate too, although its CA easing explicitly uses `press.start`, rather than uniformly starting at transaction commit ([PressFeedback.swift:166](/Users/admin/.tuft/projects/exact2-bsky/host/apple/Sources/ExactKit/PressFeedback.swift:166)). Accompanying engine motion can nevertheless lose phase agreement with these native effects. macOS shares Session but has different lowering and press execution, so sharing the flag is insufficient verification.

Layout first-seen behavior should remain intact: first observations settle; newly declaring a layout transition on an existing node seeds its old box; created/renewed nodes have no old box ([layout.rs:31](/Users/admin/.tuft/projects/exact2-bsky/kernel/src/motion/layout.rs:31)). Only a genuine new curve should become pending.

Finally, determinism should mean identical output for identical input **and supplied frame timestamps**. Variable refresh and skipped frames do not produce whole multiples of one interval. Tests should cover on-mode pending advancement, interleaved commits, pause/resume, release velocity, fully lowered idle playback, frame-task/layout creation, and takeover—not rely on unchanged flag-off fixtures.
