## 1. The ideal end state

The end state is a **closed, pure subset of TypeScript's expression syntax**: an expression Contract accepts has the same value as that TypeScript for every value Contract can hold, or it is on a short deviation table that exists because a guarantee needs it. What Contract refuses comes back with an edit that means the same thing, or with a sentence that says what is missing. The guide teaches the deviations and Exact's own library (`formatDate`, routes, `parseNumber`), and the card keeps an explicit "not in Contract" line. The roster does not grow toward ECMA-262. A new operation joins only when it is pure and total on Contract's values, its meaning already matches or the difference is already in the table, both model families write it in Contract (or a real build refuses it), and its cost class is named. A string function is a row. A callback algorithm is a new instruction plus proofs. A change to absence is a type system. Data-module TypeScript does not count: it already runs as TypeScript.

That beats the alternatives.

A zero-deviation subset cannot be built. Lists have no identity, so `[1] == [1]` is structural (`semantics/Contract/Value.lean`, and Astra confirmed it on the web runtime); identity equality would make equal lists unequal in a language that cannot mutate them. The runner holds scalar strings, so `"😀".slice(0, 1)` becomes U+FFFD (LLP 1088 D2); a Swift string cannot hold the lone surrogate JavaScript keeps. Names are CSS's (LLP 1115), so `font-size` is one name and subtraction is `a - b`, already taught in `docs/start-here.md`. View work is capped at `MAX_LIST_STEPS` (65,536), and a trap is observable. Conditions are booleans. Actions are one transaction. Where ECMA-262 leaves a result to the implementation, the runner, `host/web-js/roster.js`, and Lean have to pick one result. Those are the language. `min`/`max` dropping `NaN` is not one of them: `Number.lean`'s `fmin`/`fmax` and `roster.js`'s `x_min`/`x_max` copy Rust's `fminnm`, and that row should eventually leave the table as its own behavior change.

Contract's own small dialect was the language before D1/D2 (`when`/`each`, free functions). It was more honest, and leaving it measured nothing: ab3 tokens B/A 1.03 (SE 0.98–1.08), minutes 1.00, grade 7.3 vs 7.4. It did make builders write JavaScript's next method (`.sort` from 1 screen of 80 in `guesses/pre15` to 8 in `guesses/post15`). Going back would re-break `if`/`for` and method calls, which both models now write because they were shown them. A private dialect stays cheap only while the guide is in the prompt, and LLP 1116.013 already showed that cutting the guide moves the knowledge into lookups.

Pushing every non-trivial computation into the data module is right for effects and wrong for derives. `derive left = groceries.filter(i => not i.done).length` in `docs/start-here.md` is the point of an expression: synchronous, pure, no `pending`, no grants. The data topic is already the expensive one (0.49 MB-steps a GPT build, 1.21 a Muse build, against 0.20 and 0.31 for expressions). A view cannot call an `app.ts` function as a pure value. `Sources` is a resource or mutation boundary (`contract/cli/src/typescript.rs`). So "do it in the data module" means the answer arrives already computed. That is the right home for I/O, the clock, randomness, locale order, and canonical stored order. `apps/shelf/app.ts` sorts books by `addedAt` inside `library`, and `docs/contract-for-agents.md` already assigns sorting there. It is the wrong home for a presentation order of data the view already holds, especially an order chosen by view state: that becomes another resource argument and a re-read, or a mutation that writes display order into stored data.

Embedding real TypeScript in the data module's engine breaks the reason expressions exist. The plan runs natively on iOS. The data module is TypeScript on the web and Rust on iOS. The runner, the web roster, and Lean have to agree, which is why `semantics/README.md` differential-tests them. A browser `Array.prototype.sort` is implementation-defined for an inconsistent comparator and would diverge from Lean.

So the split is not "trivial versus non-trivial." It is **pure, total, bounded, and the same on every executor, over values the view already holds**, versus **effects, failure, device-specific behavior, or the data's own canonical form**. `toSorted` belongs on the view side of that line eventually. `localeCompare`, `Math.random`, and a shuffle do not. `docs/recipes/random-and-shuffle.md` already puts the shuffle in the data module, dealing from `exactTime()`'s seed. One of the eight post-D2 sorts, `guesses/post15/gpt/trivia-quiz-1`, sorts by `random()`; accepting that comparator in the view would be the wrong feature.

Absence can stay `none` / `some` / `match` forever. That is a coherent end state, and it is the deviation the guide already teaches successfully (46 of 80 post-D2 screens write `match`; unguided, `null` or `undefined` appears in 29 of 80). Spelling it `T | undefined` with `??`, `?.`, and narrowing is the one later change that would remove the largest remaining difference. It is a type-system project, not the completion of this rule. `contract/types/src/lib.rs` has no union in `Ty`. The web target already erases `some`, and `contract/types/src/bounds.rs` refuses `option<option<T>>` so that `some(none)` cannot be a distinct value. The data boundary already emits `T | null` (`typescript.rs`). Any respelling has to flatten, pick one absent value, and refuse to narrow across an action assignment, because an action reads the state it began with.

This direction will not close the gap with React or SwiftUI. Expressions are about 3% of a GPT build's re-sent tokens. D1 and D2 were accepted so the language would read as the web does, and they measured level. The levers that remain are the data protocol and tooling (0.49 and 0.60 MB-steps). Finish the expression rule so it stops leaking, then go back to those.

## 2. The three questions

**Q1. Yes. Accept r2's D1 as the end state. Confidence: 82%.**

The rule to accept is the one r2 wrote, not the open sentence "the common pure operations exist." An accepted expression means what TypeScript means for values Contract can hold, except the table in §D1. A refusal names a working edit or says what is missing. The table is closed: a new deviation is a language change, not a side effect of admitting a method. Admission stays as r2 has it (Contract sources or real builds, both families, cost weighed with the evidence), and `app.ts` stays excluded.

I would change my mind if a declared deviation started shipping wrong apps rather than refusals. Structural equality and `a - b` are the two that can do that quietly, because they parse and run. If a held-out repair study showed agents following `==` or a hyphenated name into a wrong screen more often than the old dialect produced repair steps, the honest response would be to refuse the colliding form, not to add another paragraph to the table. I would also change my mind if the table stopped fitting in start-here's Expressions bullet. A deviation list the guide cannot teach is no longer this end state.

**Q2. Accept a cut-down first stage: the D2 capture fix, D5's messages, and D6's docs now. Build D3 (`some`/`every`) only with the bound-trap test. Do not build D4 in this stage. Confidence: 78% on the cut, 70% on including D3.**

D2 is a bug, not a feature. The parser rewrites `s.trim()` to `trim(s)`, so an app's `fn trim` captures the built-in (`contract/syntax/src/parser/expr.rs`, Astra's probe). TypeScript never does that. Refuse the collision, keep `trim(x)` working. Ship it alone.

D5 is the part that actually changes repair cost. `contract/syntax/src/idioms.rs` already refuses `sort`, `find`, `some`, `reduce`, and `push` with an edit. r2's table is the right sharpening, with one sequencing constraint: `.sort` keeps today's "compute it in the data source" until `toSorted` exists. Do not lead with `.toSorted`, and do not promise that stage 2 will add `find`. The messages for `localeCompare`, `xs[i]`, `===`, `Date.now()`, and `Router.push` are the ones that prevent a repair from meaning something else. `===` to `==` has to say that lists and records compare by value. `xs.at(i)` has to say that a negative index counts from the end. `localeCompare` has to say there is no locale order.

D6 should add the deviation table in a line each and leave `docs/card.md`'s "Not in Contract" line in place, including `sort`. That line is worth more than the method signatures. Option-returning signatures (`at`, `first`) stay. No graded A/B: LLP 1116.013 cannot see a kilobyte.

D3 is optional sugar. The value matches TypeScript, including `every` of `[]`. The work does not: both rewrites walk the whole list and build the filtered one, so a match at the front can still hit the list bound and, under LLP 1017.003 D3, poison the runner. Evidence is thin: `.some` in 1 of 80 post-D2 screens, and `some`/`every` once each in the unguided sketches. The current message already gives `xs.map(x => …).includes(true)`. Build them only if the diagnostic names `.some` / `.every` and a test shows the early-match trap. Leave `find` out. Shipping `find` as `option<T>` moves the wall to `??` (all 16 unguided `.find`s bind the result as a record). If the bound-trap test is awkward to write, skip D3. Nothing in the program depends on it.

D4 should not land in this stage, and it should not be "last in the same stage." r2's design is the right design when you do build it: one bottom-up merge sort written out in `runner/src/machine.rs`, `roster.js` through `budget.js`, and Lean; never the engine's sort; item steps rather than comparisons, so 5,000 rows cost about 65,000 steps and fit; permutation, sortedness, and stability for a total preorder; an inconsistent comparator defined as this algorithm's result. That is a new instruction and a sorting-correctness proof, not a roster row like `toFixed`. The demand does not yet justify it. The 469 real builds, all on the free-function spelling, logged no `sort` refusal. The 8 post-D2 screens are one-shot guesses from start-here, with no repair loop and often nowhere else to put the sort: seven are `(a, b) => a.field - b.field`, one is a string `.sort()` on categories (`guesses/post15/muse/grocery-list-2`). D2 created that wall. Satisfying it on contact invites `toReversed`, `find`, `reduce`, and `flatMap`, each another four implementations. A restricted `sortBy` that only accepts a field difference would be a third dialect. Either the real `toSorted`, later, or the data module, now.

I would build `toSorted` if, after D5, guided builds still spend real repair steps on sort and the repaired app is worse for it, or if you and James read a list-heavy app whose derive is a presentation order of data it already holds (a column toggle, two orders of one list) and the resource round trip is the awkward part. The one-shot 8/80, by itself, would not change my mind. I would also build it if a native app's display order is visibly stale because the only legal sort re-enters the data module.

**Q3. Write the stage 2 RFC now, as a decision that is allowed to keep options. Build none of it with this stage. Confidence: 72% on writing it now, 84% on not building it yet.**

Stage 2 is not the prize of this direction. The prize is that accepted expressions mean what they say. Options already give you the guarantee stage 2 would have to re-prove: a value whose type does not include absence is never absent. Guided agents write `match`. Unguided agents write `null`. LLP 1116.015's lesson is that they write what they are shown, so a respelling buys first-contact guesses and shorter reading, which is what D1/D2 bought, and those measured level.

The hard part is not `??`. Lowering `??` and `?.` to `match`, so the right side does not run when the left is present, is ordinary sugar, and it matters because a trap and the list budget are observable. The hard part is flow-sensitive narrowing in a checker and a Lean type system that have no unions and no control-flow types. Narrowing has to die at an assignment. Inside an action that is not a stylistic choice: the read sees the pre-state, and `analyze-read-after-assign` exists because 24 of 80 unguided features assigned and then read the new value. TypeScript-shaped narrowing that follows the assignment would compile those programs and mean the old value. That is T4, the failure this whole direction exists to prevent. The second hard part is the absent value itself. `find`, `at`, and `?.` produce `undefined` in TypeScript; the generated `.d.ts` already says `T | null`. Pick one, refuse the other with the edit, and flatten nested options, which the web already does. The third is LLP 1081 and "Delete; don't deprecate": `some`, `none`, and `match` go away or the language has two absences, and that migration touches every source, the proofs, and the apps outside the repo.

`find` and `xs[i]` wait, correctly. Stage 2 still might not accept `xs[i]`. `at` counts a negative index from the end; JavaScript's `xs[-1]` is `undefined`. Familiar syntax with that meaning is the case LLP 1116.015 T4 already refused.

I would build stage 2 only if the design RFC contains one worked action — assign, then read, then narrow — whose diagnostic tells the truth, and if you and James are faster reading the `T | undefined` spelling of an option-heavy app than the `match` spelling. If the snapshot example cannot be made obvious, keep options and teach them as the deviation that matters. A stage 1 guess corpus in which `null` and `??` do not rise would not, by itself, be a reason to build it. Those walls are repaired by a message. The reason to build is that `match` is still the thing humans and agents stumble on after the message exists.

## 3. Where I agree and disagree with Claude

I agree that D1 should be accepted, and I agree that a zero-deviation subset is the wrong target. I would not use `min`/`max` and `NaN` as evidence for that. Identity, scalar strings, hyphenated names, the work bound, bool conditions, and immutability are the reasons. `NaN`-dropping `min`/`max` is an accident of `fminnm` (`runner/src/stdlib.rs`, `Number.lean` 158–171, `roster.js` lines 6–7). Keep it declared, and do not rename to `Math.min` until a separate change makes `NaN` propagate, with an `arith` difftest and a search for derives that rely on the swallowed `NaN`. r2 already says this. My confidence on D1 is 82% against Claude's 85%, because the clause that needs binding is "the common pure operations exist." Without the closed table and the cost-class gate, D1 is a license for the treadmill.

I agree on building the messages and the docs now, and on deferring `toSorted`. I am more sure about the deferral than Claude's 65%: about 75%. The 8/80 figure is real (I counted the post15 contracts: five GPT, three Muse, seven numeric field comparators, one string default), and it is the wrong electorate. The guess harness has no data module, so it pulls `app.ts` work into the contract. Real apps that sort — `apps/shelf`, `apps/fieldnotes`, `apps/messages` — sort in TypeScript, which is what the guide told them to do. The 469-build zero is pre-D2, so it is not a post-method baseline; it is still better evidence than a one-shot screen. Claude's "build it if the wall persists or a real app reads better" is the right trigger. I would add: persist in a guided build with a repair loop, not in the next guess corpus, and do not invent a field-only `sortBy` as a compromise.

I am less sure about D3 than Claude's 80%. `some` and `every` are fine sugar and a weak census. They are worth a few tests. They are not evidence that the predicate set should keep growing, and `find` must not ride along. Claude's summary also skips the D2 capture fix. That one should ship first. It is the live T4 hole.

I agree that the stage 2 RFC should be written now and built later. I disagree with the gate "build it once stage 1 shows that matching TypeScript helps," and with r2's D5 line that says stage 2 will give `find` itself. D1 and D2 matched TypeScript and the graded comparison could not see them. The gate is narrower: an honest narrowing design under snapshot semantics, a choice between `null` and `undefined` that accounts for the `.d.ts` already emitting `T | null`, and a timed read that shows `match` is the tax. The RFC should be allowed to conclude that options stay. Muse was right that this is a typing change priced, so far, at a paragraph. Writing it in parallel is cheap. Pre-accepting it as the next build is not.

## 4. The risks, in order

1. **The roster treadmill.** D2 made Contract look like JavaScript, and `.sort` went from 1 screen to 8. Each accepted method makes the next refusal look like a bug in the roster. `map` and `filter` are four implementations plus Lean (`format.json`, the runner, `roster.js`, the semantics). `toSorted` is that plus a sorting proof. `reduce` is another callback and another proof. There is no natural stop if guess-corpus walls are the admission oracle. **Do this:** treat r2's admission rule as closed, keep `sort` on the card's "Not in Contract" line, and do not let a post-D2 one-shot screen vote a new instruction into the language. The next real-build census, after method syntax, is the baseline. The 469 number is not.

2. **A familiar spelling that runs and means something else.** This is worse than a wall, and r1 almost shipped it for `Math.min`. The same class is still in the messages: `==` is structural, `at` counts backward, `<` is code-unit order, a list `push` is not `push(nav, location)`, `some`/`every` do not stop early, and a lone surrogate does not round-trip. Agents will apply the edit. **Do this:** land D5 as specified in r2, with `.sort` pointing at the data module, and add a fixture per row whose suggested edit typechecks and whose comment says what differs. Do not rename `min`/`max` in this stage.

3. **Stage 2 built as TypeScript control flow.** The action model reads the state the action began with. Narrowing that follows an assignment, the way TypeScript's control-flow analysis does, would take the bug the guide just suppressed (24 of 80 unguided, 1 of 80 once taught) and make it typecheck. **Do this:** the stage 2 RFC's central example is that action. If the diagnostic cannot say "this read still sees the old value" in one line, stop. `if (x)` stays refused either way.

4. **Determinism that difftest cannot see.** Resource-bound refusals are outside differential agreement (`semantics/README.md`: they become `UNSUPPORTED`). A `some` rewrite and a sort can agree on values and diverge on which list traps, and the web path will diverge the moment it calls the engine's sort. An inconsistent comparator, a `NaN` result, and `-0` are all places ECMA-262 refuses to pick for you. **Do this:** for D3, a corpus probe with an early match past the bound. For `toSorted`, when it exists, one written algorithm on all three executors and a corpus program for ties, `NaN`, `-0`, astral strings against code-unit order, and an inconsistent comparator. Do not accept a green difftest as coverage of the bound.

5. **Teaching less, and the knowledge coming back as lookups.** start-here's Expressions bullet is a few lines of a 10 kB page. LLP 1116.013's result was that a shorter first read did not shrink builds, because agents fetched the same facts later. Deleting per-method signatures while the roster is still a small, irregular subset will increase `contract vocab` calls and guesses at which methods exist. That is how `.sort` happened. **Do this:** add the deviation lines, keep the absence line, and record vocab lookups in the as-built note. Do not run an A/B for this.

6. **Human readers, and a migration with no deprecation window.** `rules/RULES.md` deletes rather than deprecates, and apps outside the repo consume exact2 by path. D1 already spent the word `when` that told a reader "this is the view." Stage 2 would spend `match`. `first` to `at(0)` was rightly dropped: no census, worse reading. **Do this:** you and James read one option-heavy app and one list-heavy app before any further spelling is deleted, which is T6. No source migrates for D2, D3, or D5.

## 5. What to measure before each commitment

**Before treating D1 as policy.** No bake-off. Confirm the deviation table fits in the Expressions bullet, and that you can name the rows from memory after one read. The rule is a standard for later diffs, not a behavior change.

**Before D2, D5, and D6 land.** These are the commitment I would make now.

- D2: the `fn trim` plus `s.trim()` probe is refused with "rename your `fn trim`"; `trim(x)` still compiles; a shape or action of the same name is covered.
- D5: one fixture per row. The edit typechecks. The four that are not meaning-preserving say so in the message: structural `==`, negative `at`, code-unit `<`, and router `push`. `.sort` does not mention `toSorted`.
- D6: a drafted net byte diff of start-here plus the card, with the "Not in Contract" line still present. On the next real judging run, count `contract vocab` lookups. Pass is "lookups did not jump," not "bytes fell."

**Before claiming the valley is under control.** Re-run the guess corpus per model, every diagnostic (`contract build --json`, cap 20), on the 40 features and on 40 held-out features, against `post15` and a baseline run twice so the run-to-run spread is known. Pass: truthiness, `null`, `try`, and the other refused TypeScript forms do not rise beyond that spread. Do not require the sort screens to compile. Separately, take the eight post15 sort screens, apply the new diagnostic, and see whether one edit lands in a data module and the screen still reads well. If the sort key is view state and the repair is a fake resource, that screen is the `toSorted` brief.

**Before D3.** Same-plan test against the `filter` expansion. Values against JavaScript for `[]`, one item, all true, all false, and an index predicate. A non-bool body whose diagnostic says `.some` or `.every`, not `filter`. A list past 65,536 items with a match at index 0, showing the trap. If that last test is the behavior you do not want to teach, do not ship the rewrite.

**Before `toSorted`.** A post-D5 guided sample, a real round or a small graded set, counting sort refusals and the steps to a working app. The pre-D2 469 builds are the wrong denominator. Build only if that wall is common and the data-module repair makes the app worse, or if a real derive is a presentation sort. Then r2's design is the spec: item charging, one merge sort, proofs, the corpus above, and 5,000 rows fitting. String default is code-unit order. A number list with no comparator stays refused, because `[10, 9, 1].toSorted()` is `[1, 10, 9]`.

**Before any stage 2 implementation.** The RFC decides `undefined` versus `null` (the `.d.ts` says `null` today), flattening (already required), lazy `??`, narrowing ended by assignment, `if (x)` still refused, and the deletion of `some`/`none`/`match`. It includes the snapshot example as a test, not a paragraph. Then you and James time a read of one option-heavy app in both spellings. Build only if the new spelling wins that read and the snapshot example is honest. A guess corpus full of `??` is a reason to improve the `match` message, not a reason to start the type system.
