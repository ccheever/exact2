# Review of LLP 1020.001 (r1)

**Reviewer:** grok grok-4.7, reasoning effort xhigh, run 2026-10-15 by Claude (Opus 5.5) for Charlie Cheever, read-only on `07fdd0ff4`, blind to the other two reviews. Scope given: foundational and directional questions only. The text below is the reviewer's final message, unedited.

VERDICT: ACCEPT WITH CHANGES

1. **A custom scheme is acceptable only if it keeps both properties LLP 1020 §10 already decided for local documents.** #135 serves a local page at `http://exact.localhost` so WebKit treats it as a secure context and still loads `http:` subresources, including loopback, which WebKit blocks from an `https:` page (`llp/1020-webview.rfc.md` §10). This proposal moves every schemeless `src` to `exact-app://app` (`1020.001` D1, D4). Q1 and Q5 ask the two halves of that decision, but only Q1 failure abandons the scheme (§4, §5). Exact Draw’s editor still calls a loopback companion (`docs/agent-pitfalls.md`, the local-server entry; `issues/20261015-chosen-documents-outlast-the-launch.md`). Change the gate: ship this origin only if the probe shows a secure context and loopback `http:` loads. If those conflict, the scheme is the wrong origin.

2. **The fallback does not provide the persistence D1 requires.** D1 makes `exact-app://app` stable so `localStorage` and IndexedDB survive relaunch. §5’s in-process loopback server uses a new port each launch, so the origin changes and that storage dies. The proposal says this, then offers that server as the fallback if Q1 fails. Change the fallback to a listener bound to `127.0.0.1` on a port the app reuses, so the origin stays put. A fresh port is not a fallback for this design. Q3 remains a kill-check for both mechanisms.

3. **The guest’s reach is the bundle resource root, which holds a credential the web does not publish.** D2 serves anything the resolver holds under the asset root, on the claim that the web already publishes those files. For an embedded app the resolver is a directory walk of `Bundle.resourcePath` (`host/apple/Sources/ExactKit/Session.swift`, `Assets.swift` `embeddedURL`), and `PlanURL.installInitial` keeps that resolver. That directory contains `receipt.json`, and a development receipt includes the opening-link token (`host/apple/build.mjs` `developmentAdmission`, written under `Contents/Resources`). The web allowlist does not serve it (`host/web/serve.mjs` `PUBLIC_FILES` / `PUBLIC_TREES`). Today the author names one `src`. After this, guest script can request any name. Private `host.macos.resources` files live under that same root. Change D2: answer only the published trees (`assets/`, `deck/`, `shaders/`), and 404 everything else, including `app:/` (§7 is right to keep those out).

4. **If sandbox cannot be applied, direct mode must not be used.** §10 keeps a sandboxed remote load in the wrapper because WebKit cannot sandbox a top-level network load, and approximating sandbox is the fail-open class D2 removed. Q4 asks whether `Content-Security-Policy: sandbox` is enforced on a scheme-handler document and does not say what a no means. A no means a direct local page silently drops the author’s `sandbox`. Change: on that result, sandboxed local pages stay in the wrapper, where the inner frame’s `sandbox` attribute already works. That does not abandon the scheme.

5. **`sandbox` does not reproduce Apple’s origin on the web, and the web host should stay unchanged.** On the web an `assets/` page is same-origin with the app page, so an unsandboxed guest can reach `window.parent.document` (`1020.001`, “What the web does differently”). Apple has no parent document, so the native arm is stricter. That matches LLP 1020 D2’s posture and LLP 1020 D1’s rule that a bare iframe is the oracle. Leaving the web host alone is right. The sentence that an author who wants the web to match writes `sandbox` is not. Without `allow-same-origin` the origin is opaque and storage does not persist. With it, the guest can touch the parent. Neither is a stable `exact-app://app` origin that persists and has no parent. State that persistent guest storage on the web is the app origin’s storage, and do not add a second web origin to chase this.

The problem is the one LLP 1020 D2 left open, and Exact Draw is a real consumer. Single-file inlining and `loadFileURL` are the wrong fixes. A `WKURLSchemeHandler` on one stable origin, read through the app resolver, is the mechanism §8 Q1 already pointed at. It adds no Contract surface, leaves Linux and the boot path alone, and needs no app id: LLP 1031 D1 is one Exact app per process. Probe before building. Q2 and Q3 are real kill-checks. None of Q1–Q5 is a reason to skip the probe.
