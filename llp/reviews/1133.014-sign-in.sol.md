1. **MATERIAL — GIS does not provide the request lifecycle the RFC promises.** D1, lines 191–199, promises dismissal errors and cancellation; D5, lines 433–437, makes completion release the shared ceremony queue. But the chosen Google web cell uses GIS’s successful credential callback. Its documented `cancel()` controls One Tap, not the button popup, and the button API documents no popup-dismissal completion or abort operation. [GIS JavaScript reference](https://developers.google.com/identity/gsi/web/reference/js-reference).

   Consequently, the plan has no established way to settle a dismissed button flow or withdraw its UI when the awaiting call ends. These are contract decisions, not callback plumbing. **Fix:** establish a supported completion/abort mechanism, or explicitly decide the web cell’s weaker lifetime, bounded settlement and queue-release semantics. §10’s substituted cancellation drive, lines 940–942, cannot prove this; real drive 9, lines 955–956, must include dismissal, supersession and retry.

2. **MATERIAL — Activation-bound firing conflicts with waiting in the one-sheet queue.** D5, lines 383–397, requires launching inside the press’s activation, while lines 435–437 put the fired request into passkeys’ queue. [Passkeys D9, lines 473–481](llp/1133.011-passkeys.rfc.md#d9--no-press-on-the-web-one-sheet-at-a-time), requires serialized ceremonies. If another decision owns that queue, launching immediately violates serialization; waiting can lose activation.

   Google’s iframe complicates admission further: `click_listener` is documented as a notification, without a cancellable preflight contract. [GIS button reference](https://developers.google.com/identity/gsi/web/reference/js-reference#click_listener).

   **Fix:** decide synchronous acquisition and an explicit busy outcome before provider UI launches. The provider control must be unable to launch while admission is closed, with a fresh press required afterward. Prove this against an occupied queue using the real web implementation. Arming alone does not resolve this conflict.

3. **MATERIAL — Auto-selection does not implement the promised silent mediation.** D1, line 136, defines `silent` as no UI or failure. D4, lines 362–365, implements it using GIS `auto_select` and Android `setAutoSelectEnabled(true)`. Google documents that unmet web auto-selection conditions fall back to interactive One Tap; Android likewise disables automatic selection when, for example, several authorized accounts exist. [GIS automatic sign-in](https://developers.google.com/identity/gsi/web/guides/automatic-sign-in-sign-out), [Android implementation guide](https://developer.android.com/identity/sign-in/credential-manager-siwg-implementation).

   D1, lines 226–234, also promises suppression until another sign-in, whereas GIS describes `disableAutoSelect()` as suppression for one day.

   **Fix:** refuse silent requests on cells without a documented mechanism that cannot fall back to interaction, or explicitly change the shared semantics. Persistent suppression requires module-owned state if the stronger `preventSilentAccess` promise remains. Test ineligible accounts and post-sign-out behavior.

4. **IMPLEMENTATION-PHASE — The unsupported Mac fallback must omit the restricted entitlement.** D7, lines 525–527, promises a runnable Mac build with Apple unavailable. D8, lines 535–537, instead emits `com.apple.developer.applesignin` for every Apple target carrying an `auth.apple` grant. Restricted entitlements require provisioning authorization; merely hiding the button cannot recover from a build the OS refuses to launch. [Apple TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles).

   **Fix:** derive both availability and emitted entitlements from the build’s provisioning support. Verify that the unsupported Mac release launches and Google still works.

5. **IMPLEMENTATION-PHASE — The Android registration output needs another input.** D8, lines 561–565, promises SHA-1 fingerprints from `host.android.certificates`. [Passkeys D6, lines 343–348](llp/1133.011-passkeys.rfc.md#d6--the-relying-party-the-grant-the-association-the-origins), defines that input as SHA-256 fingerprints. SHA-1 cannot be derived from SHA-256.

   **Fix:** accept certificate material or both fingerprints, and print a missing-input instruction when only SHA-256 is available.

**BEYOND — Presentation ownership is currently scoped to a session, not a window.** D6, lines 451–456, and D10, lines 685–689, assume an existing window-wide auth-session owner. In fact, [runner/src/auth.rs:539](runner/src/auth.rs:539) checks only the current runner’s sessions, [Session.swift:472](host/apple/Sources/ExactKit/Session.swift:472) stores sheets per `ExactSession`, and [AuthSessionHost.open](host/apple/Sources/ExactAuthSession/AuthSession.swift:23) starts them without reserving the window. The [Mac embedding fixture](host/apple/Sources/ExactHostMac/main.swift:48) already places two sessions in one window. Exposing the transport through package contexts does not establish shared admission. A host-owned presentation coordinator must arbitrate across sessions and across `openAuthSession`, credentials and other decision sheets.

**BEYOND — Web authentication grants now authorize executing remote code.** §7, lines 811–818, acknowledges this cost, and §13 question 3 explicitly asks Charlie to accept it; it is therefore a deliberate trade rather than another unresolved material finding. Nevertheless, it changes the existing [app-origin/baked-script CSP model](host/render/src/serve.rs:1446). The [data realm explicitly is not a security sandbox](host/web/module-glue.js:1), so keeping tokens below the data seam prevents routine state disclosure but offers no secrecy from provider scripts. Future payment and provider modules need the same explicit distinction between granting API access and trusting mutable code with page authority.

Carry the owning answer’s lifetime through the data runtimes and package adapters. Prove that superseding one task disarms or cancels its ceremony while another call in the same session remains live. The callback spelling is implementation detail; including this ownership path in the build plan is not.
