1. **SHOULD-FIX** — Recorded pids are signaled with no identity check, including after the leader is gone. `scripts/test-children.mjs:25`, `scripts/test-children.mjs:47`, `scripts/test-children.mjs:67`.
   `child.known` only grows. A short-lived descendant (a `cargo`/`rustc` from the dev loop) is remembered for the whole test, and `alive` is `process.kill(pid, 0)`, which is true for whatever process owns that pid now. `tell('SIGKILL')` then kills that process. The same hole exists for the group: line 67 always calls `process.kill(-child.pid, 'SIGKILL')` after the leader may already have exited. `host/web-js/dev.mjs:40` refuses that on purpose ("not once it is gone: its group id could be another's by then"). `tamber-server.mjs:991` also refuses a group signal when the pid is `0` or `1`, because `kill(-1)` goes to every process this user may signal. There is no `exit` listener, so a child that ends on its own stays in `running` and the 250 ms poll keeps calling `descendants` on that pid; if the pid has been reused, the new process's children are added to `known` and killed at `afterEach`. macOS pids are sequential and wrap near 99999, so this is situational, not every run, but this helper's only job is to kill the right processes.
   Fix: store each pid with its start time (`ps -o lstart=` / `etime=`). Signal only when the start time still matches; drop a pid once it does not. On the child's `exit`, `clearInterval` the watch. After the leader has exited, do not call `process.kill(-pid)`. Ignore `pid <= 1`.

2. **SHOULD-FIX** — The SIGKILL backstop cannot see a stop that has already started, and the `exit` hook forks `ps` before it kills. `scripts/test-children.mjs:53`, `scripts/test-children.mjs:63`, `scripts/test-children.mjs:77`.
   `running.delete` happens before the first `await`. The grace timer is `unref`'d, so it does not keep the process alive and does not run if bun then `process.exit`s (last test, or a crash during `stop`). The `exit` hook walks `running` and skips that child. What already ran is only SIGTERM. `host/web/dev.mjs` traps SIGTERM (`dev-startup.mjs` registers it; the wasm `stop` at `host/web/dev.mjs:987` waits until its own cleanup calls `process.exit`). That `stop` awaits `hostBuildChild` and `installer.child` with no timeout. If one of those ignores SIGTERM, the loop stays up, and nothing in this helper sends the SIGKILL. The `exit` hook also calls `descendants()` (`spawnSync('ps')`) before `signalGroup`. A throw or a stuck `ps` there skips the group kill for that child and every child after it.
   Fix: keep the child in a set the `exit` hook still walks until SIGKILL has been issued. In that hook, SIGKILL the group and the already recorded pids first, and do not fork.

3. **SHOULD-FIX** — The new tests never exercise an orphan or a process that survives SIGTERM, and they wait by sleeping. `scripts/test-children.test.mjs:12`, `scripts/test-children.test.mjs:38`.
   The grandchild is detached, but its parent is still alive when `stopAll` runs, so `descendants(child.pid)` finds it by ppid. Deleting the poll and `known` would still pass. Both processes use the default SIGTERM action (`setTimeout` and exit). `dev.mjs` does not: it installs a handler. Removing the grace SIGKILL and the `exit` hook would still pass. The inner timeout is 3 s for a nested `bun test` plus two spawns; under the same load that produced the 522 s hang, the pid file may not exist yet and `readFileSync` throws. The 200 ms and `sleep 0.3` waits are the fixed sleeps `docs/testing.md` says not to use, and `kill(pid, 0)` is still true for a zombie.
   Fix: have the parent exit so the grandchild's ppid is 1 before `stopAll`, and ignore SIGTERM in the grandchild so only SIGKILL counts. Wait until `kill(pid, 0)` fails with `ESRCH`, with a deadline. Give the inner test long enough to spawn, then hang.

4. **SHOULD-FIX** — The same timeout leak is still open in the other dev-loop tests. `scripts/design-tool.test.mjs:52`, `scripts/design-tool.test.mjs:1195`, `host/web-js/dev-builds.test.mjs:25`.
   `design-tool.test.mjs` starts `host/web/dev.mjs --app theme-fixture --wasm` and stops it with `child.kill` only, inside `finally`. A bun timeout skips `finally`, which is how `apps/theme-fixture/.exact/tamber.lock` was held for two hours. `dev-builds.test.mjs` is the old `devLoop` stop copied forward (SIGTERM the one pid, SIGKILL only that pid after 30 s). `host/web/tests/dev-scheduler.test.mjs:50` does the same for `realworld`. No `beforeAll` in `tamber-server.test.mjs` uses `spawnOwned` (the shared wire at line 256 is `tamberServer()` on a temp dir), so this file's `afterEach` will not kill a child early. Those other files should call `spawnOwned` now.

5. **NIT** — The poll is a synchronous `ps -A` every 250 ms on the test's event loop. `scripts/test-children.mjs:26`, `scripts/test-children.mjs:34`.
   It is `unref`'d, and `stopChild` clears it, so it does not keep the process alive and does not outlive a finished stop. While a dev loop runs (these tests allow 900 s), every tick forks `ps` over the whole machine and blocks the test. If `ps` takes longer than 250 ms, the callbacks run back to back. `docs/testing.md` says to poll cheaply.
   Fix: one async `ps` at a time, and skip a tick while one is in flight.

6. **NIT** — On Windows the helper does not track descendants or process groups. `scripts/test-children.mjs:12`, `scripts/test-children.mjs:20`.
   `detached` is forced off, `descendants` returns `[]`, and `signalGroup` is `child.kill`. `host/web/dev.mjs` and `host/web-js/dev.mjs` still spawn tools with `detached: true` on every platform, so a timed-out test there still leaves those tools. The new test also runs `sleep`, which Windows does not have. Fine for a Mac-only suite; the test should return immediately off POSIX instead of failing in `spawnSync('sleep')`.

Checked and not a defect: a child that exits by itself is left in `running` until `stop` / `afterEach` (that is what later kills orphans), which is finding 1's interval bug, not a missed removal. SIGTERM to `dev.mjs` and to its descendants in the same turn is intentional so a timeout still reaches detached tools before the first `await`. That races `host/web-js/dev.mjs:1009` (it wants `tamber.close()` to finish, and it only SIGTERMs the resident) and `host/web/dev.mjs:987`. The race does not stick the fixture lock: the Rust server has no signal handler, so SIGTERM kills it, and the flock dies with the process. SIGKILL as soon as the leader exits is what the comment on `spawnOwned` asks for, so orphans of a leader that already shut down do not keep running.
