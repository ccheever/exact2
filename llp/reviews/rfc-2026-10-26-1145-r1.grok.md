I'll check the RFC's claims against the raster core, the Apple loader, and the JS web target, and only flag problems that would break the design.D1 and D2 miss the path that actually makes an image late. D3 and D5 hold.

**1. Re-ranking the raster core's decode queue does not make the image arrive.**

An Excord avatar or attachment is late in the loader, before a `Demand` exists. `inspectOne` starts remote fetches in source-id order, with no priority (`RasterLoader.swift`). Under the eight-viewport budget, `park` cancels the request and waits until `mayShow`, so an ahead row has nothing left in the core's queue to re-rank. On a fast fling the pump already runs one decode (`fastTravel` at 20,000 pt/s, `RasterWorkers.single`); `next_decode` only sorts `Phase::Queued`, so the decode in flight keeps the only slot.

The frozen `Visible`/`Overscan` bit is real, and the core already repairs it: `RasterSession::request` replaces the demand for the same view and key and wakes. The loader never sends that update. Within one priority, order is entry id. Shared avatars are one `RasterKey`, and admission already takes the best subscriber (`min` over bindings). `Entry.demand` stays the first requester. A rank stored on that demand schedules the avatar by whoever asked first.

Keep one per-view rank in the loader (on screen, then ahead, then behind, by the distance it already computes). Order fetch starts with it, and make `release` park rows behind the travel before it parks rows ahead. When a view crosses onto the screen, re-request so its priority becomes `Visible`. Add a distance to the core's sort only if an on-screen decode still sits behind an overscan one after that.

**2. The direction D1 reads exists only on iOS.**

`ScrollPump.velocity` is in `IOS/ScrollPumpIOS.swift`. On macOS `collections.motion` is nil and reports carry no velocity. LLP 1144's jank was seen mostly on macOS, so the sign D1 depends on is never reported there. The pump's velocity also belongs to one list (`travel` is keyed by list id) and falls off after 150 ms, while the decode queue is one session for every image on the screen.

Take direction from the scroll observation the loader already installs on both platforms (`scrolled` and the bounds watch), per scroller, and rank each image from its own scroller. At rest, the nearer off-screen image wins.

**3. Pixel `width`/`height` attributes do not reserve a box the stylesheet has already reserved.**

The JS target never lays out. A literal `width` and `height` are CSS on the element (`style_row` / `css_text`), so a pixel size already occupies its box before the bytes arrive. `rows.rs` already appends `decoding="async"` on every `img`, citing this RFC. Excord's scrolling images are outside the rule anyway: avatars are `2.5rem`, attachments are `width="100%"` with `height` auto or `100%` and an `aspect-ratio` (`transcript.contract`).

Leave `decoding="async"` as it is and drop the attribute rule. A web image shifts when an axis is still indefinite; `aspect-ratio`, which Excord already sets on attachments, is the reservation that matches those images.
