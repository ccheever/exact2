# RFC review: LLP 1027.007 r1, 2026-10-21 (grok)

- **Family:** xAI, `grok --reasoning-effort xhigh --permission-mode plan --no-subagents --output-format streaming-json` (grok-4.6-build), run in the worktree at `e3e8426e32`.
- **Method:** mutually blind to the other family, which got an identical brief (the grok brief adds tool rules). Brief sha256 `c36031ace273f76773a9da50cc02afec7aa39043a58a2969209d1c68f4fb2d42`.
- **Reviewed revision:** `llp/1027.007-evaluating-the-module-off-the-owner.rfc.md` r1, before any fix.

1. **The one-time `Module` hand-off is an `unsafe impl Send` of a live VM, which LLP 1072 T1 and LLP 1027.002 D2 already forbid. Stage A needs a ruling.**

   The document says a 2026-10-21 survey “found nothing that pins a loaded module to the thread that evaluated it,” that this RFC “moves one quiescent module once, before any call, and never back,” and that “Stage A needs no ruling” (`llp/1027.007-evaluating-the-module-off-the-owner.rfc.md:3`, `:74-75`, `:69-71`). D3 sends the instance in a `Loaded` wrapper with `unsafe impl Send` (`:124-128`).

   LLP 1072 T1: “The registry, runners, kernels, hosts, data sources and Rust thread-locals live there. No `Send`, no `unsafe impl`” (`llp/1072-building-rows-off-the-main-thread.rfc.md:62`). §2.1 rejected lending a runtime per fill because a hand-off would move `Rc` graphs and thread-local state (`:412-414`). LLP 1027.002 D2: “Nothing moves a live VM between threads or marks its pointers shareable to satisfy the compiler” (`llp/1027.002-optional-worker-execution.rfc.md:152-154`). The TypeScript worker path exists so the engine is created on its owner: `Module::placed` says “The engine never crosses a thread” (`js/src/lib.rs:387-388`); `Placed::built` is “For a source that cannot be sent — one that owns a VM” (`data/src/placed.rs:196-201`). ibex2’s adapter contract: “All methods, including detach/destruction, run on the runtime's owner thread” (`vendor/ibex/crates/ibex2/include/ibex2_jsi.h:249`). `Context` is documented “Create after first pixel” (`vendor/ibex/crates/ibex2/src/bindings.rs:443-444`). `Engine` drop calls `exact_js_destroy`, which `detach()`s the adapter (`js/src/engine.rs:418-421`; `js/src/shim.cc:500-503`).

   This is a safety and governance defect. Stage A is the hand-off. Shipping it without waiving T1 and D2, or without building the VM on the owner, would mark Hermes/ibex2 pointers shareable to satisfy the compiler, which D2 names as the thing not to do. The worker placement already evaluates off the owner without moving a live VM (`data/src/placed.rs:580-607`; `js/src/lib.rs:399-437`).

   Change: drop `Adopt`/`unsafe impl Send`. Either keep evaluation on `exact.owner` after first pixel, or obtain the instance with `Spawn::Build` on a host-owned thread and leave it there (1027.002). If Charlie still wants a move, the header must ask for an explicit waiver of 1072 T1 and 1027.002 D2, and Stage A is not “no ruling.”

2. **Stage B’s waiver restates the rule as a first-frame timer. The cited documents make it a count so boot-path JS cannot accrete.**

   Q1: the rule exists “so that the first frame never waits on app code”; Stage B “keeps that purpose” because JS runs on the loader and “first frame's p50 does not move”; recommend restating the rule as “nothing the first frame waits for executes app JS,” with a p50 check (`llp/1027.007:147-152`, `:185-191`).

   `rules/RULES.md:42` is “App JS executed before first pixel | none.” Scope **[check]**: “The boot path executes and compiles nothing. No app JS before first pixel; … Startup is emergent and cannot be retrofitted, so the boot graph is budgeted from commit one — counted, not timed. Every launch pays for boot” (`:53-56`). LLP 1027 D4 keeps that “to the letter”: “The executor is created after the first pixel” (`llp/1027-typescript-data-sources.rfc.md:457-473`). The alternative of creating the engine before boot “was considered and not taken, not because the number is large but because the rule is a count, not a timer, and the reason it is a count is that the old repo's 5.47 MB of boot-path JavaScript began as a small number too. If Charlie wants the frame back, it is a ruling on the rule, not a change to this design” (`:655-660`). Out of scope: “JavaScript before first pixel, on any host, by any amount (D4). Trigger: a ruling on the rule, not a design” (`:1830-1831`). LLP 1027.002 D2 startup: “App initialization still happens after first pixel” (`llp/1027.002-optional-worker-execution.rfc.md:175-176`). Stage B runs `Module::load` / Hermes `evaluateJavaScript` of `app.hbc` (`js/src/lib.rs:453-478`; `js/src/shim.cc:308-311`) before first pixel.

   A p50 bar can hold while every launch still executes app JS, pays energy on an abandoned launch (Q1 already names this), and opens a path for more pre-pixel JS on “a thread the boot does not use.” That is the accretion D4 wrote the count to stop. “Off the boot path” also does not match D4’s “on any host, by any amount.”

   Change: do not restate the rule. If Stage B is wanted, ask Charlie to waive `RULES.md:42` and 1027 D4 as written, keep the count, and name the energy/abandoned-launch cost. Do not treat a first-frame p50 as the bar for that waiver.

3. **The Hermes stack-guard safety argument is unverifiable in this checkout, and D1’s “keep the loader forever” does not match how JS would run after the hand-off.**

   The document says pinned `hermes-v260318099.0.4` records native stack bounds, the slow path (`StackOverflowGuard::isStackOverflowingSlowPath`) re-reads via `thread_stack_bounds`, “the bounds follow a change of thread,” and the fast path can miss an overflow if the new thread’s stack lies inside the old range, so D1 keeps `exact.loader` for the process (`llp/1027.007:80-87`, `:111-114`). It says this is “read from the archive's symbols and upstream's source, not a local copy.”

   The pin string appears in receipt testdata (`vendor/ibex/crates/hermes-lean-sys/testdata/receipt-v2-valid.json:6`). `StackOverflowGuard`, `isStackOverflowingSlowPath`, and `thread_stack_bounds` appear only in this RFC. After the hand-off, JS runs on `exact.owner` (`host/apple/Sources/ExactCore/Owner.swift:61-63`, 8 MiB). Loader and owner stacks are disjoint while both live, so the fast path using loader-recorded bounds misses on owner SP and takes the slow path on every overflow check. The reuse case D1 spends a process-lifetime thread on is a later thread occupying the loader’s former range overlapping the owner’s stack after JS has already moved.

   This is an unverifiable safety claim plus a likely wrong mitigation. A missed overflow is a crash; a perpetual slow path is a silent tax on every later answer.

   Change: either vendor the Hermes stack-guard source into the checkout and argue from it, or treat stack affinity as a reason the VM stays on the thread that created it (finding 1). Do not keep a process-wide loader “so that cannot happen” without that source.

4. **ibex2 thread-locals and the adapter owner-thread contract survive “quiescence.” The survey’s Send diagnosis is also wrong.**

   The document: `shim.cc` keeps no thread-locals; ibex2 groups “hold `Arc`, `Mutex` and atomics”; the adapter contract “holds if the hand-off is the only transfer and no call is in progress”; `HostState.store` is `None`; `Watch`, `native_slot` and `storage::Session` are `Arc`s; `Module` is not `Send` because of “`Engine`'s raw pointer, `HostState`'s store pointer, the canvas environment” (`llp/1027.007:77-94`, `:105-107`).

   `shim.cc` has no TLS (agreed). ibex2 does: `CONSOLE` is “The console queue for this runtime's thread” (`vendor/ibex/crates/ibex2/src/boundary_abi.rs:241-249`); `RESULT_BUDGET` (`vendor/ibex/crates/ibex2/src/stdlib/fs.rs:44`); `CLAIMED_WAKES` (`vendor/ibex/crates/ibex2/src/task.rs:123-128`). Completions “pump on the JavaScript thread” (`vendor/ibex/crates/ibex2/src/task.rs:14-15`). `jsi` values are not `Send` (`:12`). `set_wake` “must return without entering JS” (`vendor/ibex/crates/ibex2/src/bindings.rs:597-601`). Apple does not install Intl (`js/src/shim.cc:292-300`), so `NativeFormatter`'s `unsafe impl Send` is off this host. In Rust, `*mut T` is `Send`; `TextEngine` is `Send + Sync` (`canvas/src/font.rs:483`). `Module` is `!Send` because `HostState.native` is `Option<Box<dyn NativeModule>>` and `NativeModule` has no `Send` bound (`js/src/lib.rs:190`; `js/src/native.rs:44-66`). That stays `!Send` even when `native` is `None`. An `unsafe impl Send` for `Loaded` would also cover a `Some(native)` if D4 is missed. `exact_js_load` does not `drainMicrotasks`; drain is `exact_js_drain` (`js/src/shim.cc:308-311`, `:473-477`), used from turns/background, not from `Module::load`. Console lines live on `State` in the engine (`js/src/shim.cc:183-204`), so they would move with the pointer; ibex2 `CONSOLE` would not.

   Quiescence of `HostState.store` is real (`js/src/lib.rs:872`, `:914`). It is not the compiler’s reason `Module` cannot cross threads, and it does not empty ibex2 TLS or change the adapter’s owner thread. Top-level storage is refused during init (`js/src/prelude.js:175-177`, `:885-896`), so “no storage continuation” is a prelude policy, not a drained event loop.

   Change: if a move remains, the safety comment must name `NativeModule: !Send`, ibex2 TLS, adapter detach, and undrained microtasks; require `native.is_none()` at send; drain (or prove empty) the Hermes job queue on the loader before send; destroy on the thread that then owns the runtime. The survey paragraph in §4 has to be rewritten.

5. **Stage B cannot start at `exact_create`: that entry does not construct a data source, and the bytecode that will run is chosen at boot.**

   D6: “`exact_create` starts the load, before the boot decodes the plan” (`llp/1027.007:147-148`). D2: the loader runs `Module::new` with the bake’s bytecode, admitted grants, `picker::app_dirs(app_id)`, and the template’s `watch` / `native_slot`, then `Module::load` (`:116-122`).

   `exact_create` only allocates a registry id (`host/apple/src/abi/exports.rs:45-61`). `Runtime` init is `Owner.shared.sync { exact_create() }` (`host/apple/Sources/ExactCore/Bridge.swift:116-119`). The factory `$new` runs in `exact_boot` / `boot_selected` (`host/apple/src/abi/exports.rs:267`; `host/apple/src/abi.rs:440-473`). `boot_selected` may replace that source with `delivery.selected_module` (`:460-465`). `Runner::boot` is where `data.bind(&plan)` runs (`runner/src/runner.rs:794`). Session setup calls `installAppModule` before boot (`host/apple/Sources/ExactKit/Session.swift:535`), so `native_slot.hosted()` can become true only after create.

   A load started at create evaluates the embedded bake, or has no `Module` at all. An update-store module is selected at boot. Grants and the plan’s source table are not admitted yet. `bind` has not run.

   Change: if Stage B exists, start it at `exact_boot` after `$new` / `selected_module` / `bind`, still after the plan is admitted and still after first pixel unless the waiver in finding 2 is granted. “At `exact_create`” is not a real hook.

6. **Adopt as specified cannot activate: storage is configured after load, `bind` is omitted for `main`, and `preload` is never pending today.**

   D2/D3: loader configures directories and loads; `prepare_data` adopts then “activates as today”; a still-loading module answers pending; load failure is reported where `activate_data` reports it (`llp/1027.007:116-133`, `:171-174`). D5: `firstDrawn` starts the load instead of posting `prepareData`; the wake runs activation (`:140-145`). Those two activation stories conflict.

   Today `activate_source` is always `configure_storage` then `activate` (`host/apple/src/activation.rs:10-12`). `Host::configure_storage` also `empty_fresh_tree` and `set_roots` (`host/apple/src/host.rs:728-738`; `host/apple/src/picker.rs:182-186`). `Module::configure_storage` errors once loaded (`js/src/source.rs:78-82`). `Module::activate` is `load`, which is a no-op if the engine is already up (`js/src/lib.rs:456-458`; `js/src/source.rs:160-161`). `set_roots` is what empties `app:/tmp/picked/` and pins picker roots; `know_roots` at boot does not empty picks (`host/apple/src/host.rs:442-444`; `host/apple/src/picker.rs:169-176`).

   `bind` fills `sigs` from the plan (`js/src/source.rs:287-309`). Answers without a signature are `UnknownSource` (`js/src/lib.rs:851-853`). Worker `Module::build` encodes the plan and binds before activate (`js/src/lib.rs:430-436`) because `keeps_plan` is true only for `Worker` (`:388-392`). A `main` template has `plan: None`. D2 never binds. `data_ready_after_store` after adopt would ask an unbound instance.

   `Module` does not override `preload`; the default is `Ok(true)` (`runner/src/runner/source.rs:456-458`). `prepare_data` returns immediately unless `preload()` is `Ok(true)` (`host/apple/src/activation.rs:24-26`). `activate_data`’s pending branch is `Ok(false)` (`:36-39`). The pending path the RFC relies on is unused for TypeScript until `preload`/`when_preloaded` are implemented on the in-flight load.

   D3 “waits for it on the owner” puts `Module::load` back on `exact.owner`. D5’s point is that the owner stays free for `tellPage`. Both cannot be the design.

   Change: configure storage and `set_roots` on the instance that will load, before `load`. After adopt, `bind` the runner’s plan; skip a second `configure_storage`. Override `preload` to `false` while the loader runs and `when_preloaded` to the channel completion. Pick D5 (wake adopts, owner does not wait) and delete D3’s wait.

7. **Destroy, reboot, replacement, and a process-wide loader are unspecified in ways that race the hand-off.**

   Verification: “a session destroyed while its module loads drops the module on the owner” (`llp/1027.007:171-172`). D1: one loader per process, one module at a time (`:111-114`). D3: validation and development replacement keep loading inline (`:133`).

   `ExactSession.destroy` sets `.destroyed`, then `runtime.destroy()` → `exact_destroy` on the owner (`host/apple/Sources/ExactKit/Session.swift:1442-1463`; `host/apple/src/abi/exports.rs:194-196`). That drops the registry entry. It does not `Interrupt::trigger` a loader. `Watch::trigger` can interrupt from any thread via `asyncTriggerTimeout` (`js/src/watch.rs:19-24`; `js/src/shim.cc:465-470`; `js/src/engine.rs:104-114`). D2 shares the template’s `watch`. Destroying an unloaded template does not drop the loader’s `Watched` and does not call `trigger`. If the session is gone, a successful send would adopt into a destroyed runtime; a failed send drops on the loader. Drop on the loader is the safe choice before hand-off (`Engine` drop / `Adapter::detach` on the creating thread, `js/src/shim.cc:500-503`). The written test forces the opposite.

   `Module::replacement` copies directories, document owner, native factory, and `keeps_plan`. It does not copy `watch` (`js/src/source.rs:174-183`). An in-flight loader still holding the old `Arc<Watch>` can deliver a module for a generation that has been replaced. `activate_for_validation` unloads and clears directories on the owner (`js/src/source.rs:164-171`); that is fine only if no loader still owns the live engine.

   The sample host embeds two sessions. One process-wide `userInitiated` loader serializes two 314 ms evals. Stage B’s loader at `userInitiated` also contends with `exact.owner` at `userInteractive` (`Owner.swift:61-63`) during first layout.

   Change: on destroy/reboot/replace, `watch.trigger()`, drop the channel, and drop a never-adopted `Loaded` on the loader. Identity the load with generation/`selected_module` hash and discard mismatches. Do not promise drop-on-owner before adopt. Say what a second session does while the loader is busy.

8. **Stage A as written may not free the main thread. The remaining stall after 74409073a6 is `tellPage` behind owner work, and D3 would restore that.**

   Stage A: the owner and main stay free while the module evaluates; data arrives when it does today; bar is the rail at 0.55 s (`llp/1027.007:25-26`, `:140-145`, `:178-179`). Q2: it “changes no rule and frees the main thread after first pixel” (`:194-195`).

   Commit `74409073a6` already posts activation to the owner and attaches native views at first pixel (commit message; `llp/1024-native-modules.rfc.md:5`, `:250-257`; `host/apple/Sources/ExactKit/SessionActivation.swift:14-46`, `:73-78`). The remaining stall is documented there: at the first frame iOS reports the app active, `tellPage` is `Owner.sync` (`host/apple/Sources/ExactKit/PageFacts.swift:346-353`; `Owner.swift:98-112`), and that job queues behind `Module::load`. `firstDrawn` still `Owner.sync`s `prepareAppModule` (dylib load historically 164 ms, then `bindExtensions`) before starting data work (`SessionActivation.swift:14-19`; `NativeModule.swift:641-655`; `Bridge.swift:621`). D3’s owner wait (`llp/1027.007:129-131`) is the same queue `tellPage` uses.

   Worker hero 0.39 / rail 0.55 vs main-at-74409073a6 0.59 / 0.59 is the owner being free, including for the turn that opens native views. LLP 1024 D3’s paint-gate amendment already moved native views off data activation. Stage A only matches the worker rail if the owner does not wait on the load. D3 undoes that. `prepareAppModule` still holds main even if the load moves.

   Change: delete D3’s wait. Start the loader without an owner job. Keep `tellPage` able to run on the owner during eval. Measure `prepareAppModule` separately; it is outside this RFC’s load move. Do not claim Stage A “changes no rule” (finding 1).

9. **Stage B’s “data 200 ms sooner” path re-stalls the owner at first pixel for whatever eval remains, and starts the wrong worker load.**

   D6: first pixel’s activation “adopts it, or waits for it if it is still loading” (`llp/1027.007:150`). D7: a worker-placed module “starts at session creation too, on that thread, which needs no hand-off” (`:154-156`). Brooks numbers: eval 314 ms, first frame ~240 ms (`:46-48`).

   If load starts at create and first pixel is at ~240 ms, about 74 ms of eval remain. A wait on the owner at activation is `tellPage` / `prepare_data` behind that remainder. First-frame p50 can still hold (the frame already committed) while main is held after first pixel, which is the bug 74409073a6 left.

   Worker `activate` today is post-pixel `Spawn::Build` (`data/src/placed.rs:580-607`). `Module::build` uses `template.directories` (`js/src/lib.rs:403, 427-428`). Directories are set in `Host::configure_storage` at `activate_source` (`host/apple/src/activation.rs:10-12`). Starting the worker at session create loads with `directories == None`, then a later `configure_storage` on the template does not reach the instance on the worker (`data/src/placed.rs:571-577`, `here()` is the template). `configure_storage` after load fails (`js/src/source.rs:78-82`). Storage then never installs (`js/src/lib.rs:573-605`).

   Change: Stage B activation must adopt without waiting on the owner (pending + wake), same as Stage A. Do not start worker `Build` before `configure_storage` and `bind`. Treat D7 as a separate design; it is not “the same RFC, no hand-off.”

10. **Several claims the document treats as settled are not true of this tree.**

    “Top-level evaluation leaves no storage continuation outstanding” (`llp/1027.007:126-128`): storage is refused during init (`js/src/prelude.js:890-896`); `exact_js_load` does not drain microtasks (`js/src/shim.cc:308-311`). A queued `Promise.then` is not a storage continuation, and is not drained.

    “Load installs the bridge to [the native module] unbound; a top-level `native` call during load is refused with an error naming D4” (`:136-138`): `load_engine` still runs the factory when directories and `native_factory` are set (`js/src/lib.rs:574-597`). Top-level `native.call` already throws “native call outside an answer” (`js/src/prelude.js:1220`). Hosted `native` can still be enabled if `native_slot.hosted()` is true (`js/src/lib.rs:609-613`), which `installAppModule` can set before boot (`Session.swift:535`; `NativeModule.swift:630-636`). D4 is new behavior, not current load.

    “The agent's `clock data` waits for it” (`llp/1027.007:174`): `landData` waits on `dataActivated` (`dataGeneration == generation`) and `drainLaunch` waits on `activationInFlight` (`natives.activationQueued || dataPreparing`) (`host/apple/Sources/ExactKit/Agent.swift:977-981`, `:1004`; `Session.swift:364`; `SessionActivation.swift:24`). If Stage A never sets `dataPreparing` (D5 starts a loader instead of `prepareData`), `activationInFlight` is false while the loader runs, and `clock data` can return before adopt unless `preload` pending plus wake sets `pendingActivation` (`Session.swift:584-589`; `SessionActivation.swift:49-53`).

    `HostState.store` “set and cleared inside each call” (`llp/1027.007:92-93`): true around answers (`js/src/lib.rs:872`, `:914`). Canvas `Env` is only set during `draw` (`js/src/source.rs:264-269`).

    Change: rewrite §4 and §6 to match `load_engine`, prelude refusals, `clock data`, and D4 as a load-path change that must actually skip the factory.

**Verdict: WRONG**
