Nothing is blocking. Two should-fix holes: `hello.live` on the wasm loop, and `uses` for sources outside the poll's file set. The dry-run commit key, the `filesAt` ordering, gap and new-run handling, scrub frames, and the existing tests hold.

1. **should-fix** — `apps/design-tool/app.contract:692` (read at `app.ts:881` and `app.contract:1440`). `advance` refreshes `hello` only when `changes.files` moves (or the answer is missed, not ok, or hello failed). On the wasm loop, `live` is `() => typescript || !portableRust` (`host/web/dev.mjs:428`), and a successful rust rebuild assigns those flags again (`host/web/dev.mjs:1251`) and then emits build-status. That moves `seq` only. Adding `app.ts` to a portable-Rust app, or turning Rust off while there is no `app.ts`, flips `live()` from false to true with no design or owned-Contract digest change. The tool keeps `hello.live` false, so the chip stays "Rebuilds" (`ok.class === 'live' && live === true`), Scrub live stays disabled, and the copy says to open the tool through a dev loop. The other direction is harmless: `proposeAt` still re-asks the proposal on every non-scrub answer, and a server class of `rebuild` disables scrub on its own. The JS loop passes `live: true` and a constant `page` (`host/web-js/dev.mjs:853`); a rebuild reloads the framed page through `/__dev/page`, so `hello.page` and `hello.frame` do not go stale there. Protocol, app, format, and the file list change with a new server epoch, which already bumps `fileChanges`. Fix: put the evaluated `live` value (and `page`, if a caller ever passes it as a function) on the poll answer and refresh hello when that value changes. Do not go back to refreshing on every `seq`.

2. **should-fix** — `apps/design-tool/app.contract:547`. `uses` is keyed only on `changes.files`. That string is the poll's `known` map: the app's `.tamber` files and its own `.contract` sources (`contract/cli/src/tamber_serve.rs:550`, `owned_kept` in `tamber_contract.rs:92`). `uses` compiles more than that. `motion_sites` scans every loaded source, including packages (`tamber_uses.rs:462`), and ordinary sites come from `compile_path_mapped` plus synthetic tokens whose key includes `code_beside` — `app.ts`, `data/Cargo.toml`, or `app.json` modules/hatches (`tamber_walk.rs:245`, `sources.rs:389`). None of those are in the poll map, and the design-server watcher does not emit `changed` for them. Edit a package `.contract` the app loads, or add or remove `app.ts`, while a token's impact list is open. The JS loop rebuilds and emits build-status; previously the next poll answer re-read `uses`, and now the list stays on the old sites until some watched design or owned-Contract digest moves. Outline is unaffected: `outlineUses` calls `uses` again (`app.ts:1436`). Fix: extend the poll key `uses` follows with the package digests the compile reads and the `code_beside` bit `sources_key` already computes, and publish it when it changes. Do not key `uses` on every answer.
