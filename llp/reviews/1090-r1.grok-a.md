## Findings

1. **MATERIAL — D2, §3.** Dropping `Some`'s node does not leave a 2× margin, and it stops bounding the walk the limit exists for. `MAX_VALUE_NODES` caps the expanded tree that equality walks, with a shared value counted once per place (`runner/src/vm.rs:24-28`). `equal` still recurses through `Option(Some(_))` (`runner/src/compare.rs:188`). `measure` counts that wrapper (`runner/src/vm.rs:334-340`). After D2 the wrapper is free, while a tower of 64 `some`s is still one straight-line chain (`vm.rs:1084-1095` allows 64). Doubling that shared tower through a local (`[x, x]`, the case in `vm.rs:991-1020`) makes the walk about 64× the new count, not 2×: each extra option layer is uncounted and then copied per place. Depth stays `inner + 1`, so `ValueTooDeep` is unchanged; the node cap is what moves. JS erasure matches the new count because there is no wrapper left to walk. The runner still allocates and walks it.
   **Fix:** Keep the runner's +1 node for `Some`. On JS, add one node per option layer from the static type while measuring (no box). If the looser cap is really wanted, replace the "factor of two" / "gives up nothing" sentences with the 64× walk and show equality still finishes.

2. **MATERIAL — D6, §3.** Tree-update traps are not journaled as `Trap(...)`. `update_tree` poisons and returns `InstanceError::Trap`, and `From<InstanceError>` wraps everything except `SlotType` as `RunnerError::Instance` (`runner/src/runner/lists.rs:94-98`, `runner/src/runner.rs:203-208`). `log_outcome` prints that with `Debug` (`runner/src/runner.rs:1026-1029`), so the line is `{what} poisoned the runner: Instance(Trap(IterationLimit { pc: N }))`. Action, derive, and resource-argument failures are `RunnerError::Trap` and do print `Trap(...)`. Surface arguments take the poison path too (`runner/src/instance.rs:913-926`); D6's table omits them. Slot writes are kept on poison (`runner/src/runner/commit.rs:64`); only the store is restored. JS `flush` records `poisoned: ${message}` (`host/web-js/rt.js:175`).
   **Fix:** Make the JS message the runner's `Debug` of the `RunnerError` that site actually returns. Put surface arguments on the poison row. Add a conformance step whose row key traps and compare the full reason, including `Instance(...)`.

3. **MATERIAL — D6, §3.** Handler-argument traps never enter `commit`'s catch. Each argument is its own `Code` and its own `vm::eval` (`runner/src/runner/event.rs:812-814` and `:969-971`), and a trap becomes `RunnerError::Trap` before `run_action`. The journal is `{what} refused: Trap(...)`, state unchanged, runner not poisoned. JS builds `(...v)=>a_N(arg, ...v)` (`host/web-js/src/emit.rs:1229-1233`) and `act` is `(...a) => commit(() => fn(...a), "action")` (`host/web-js/rt.js:206`). Arguments run before `commit`. `on` does not catch (`rt.js:769-799`). Edge handlers are the same closure, called as `c.edges[i]()` (`host/web-js/list.js:755`). D7 case 4 only checks that 40,000-step arguments succeed, so this miss stays green.
   **Fix:** Evaluate handler and edge arguments inside the callback `commit` runs, and journal `Trap(...)` from that catch. Add a case that traps in one handler argument and one edge argument and compare the reason text.

4. **MATERIAL — D6, §3.** Slot stores have a second string refusal the design never meters. After the body, and after sends are issued, a slot value with `as_str().len() > MAX_STRING` is `RunnerError::StringTooLong { name }` (`runner/src/runner/commit.rs:524-527`), then the commit rolls back (`settlement.rs:1432-1437` is the argument form of the same variant). `too_long` is only a top-level string (`commit.rs:8-11`). The argument check (`commit.rs:432-436`) does not cover a string loaded from a resource, a derive, or a literal and then stored: the `Str` opcode and resource settlement never apply `MAX_STRING` (settlement only `conforms`, `settlement.rs:299`). D6 adds the argument check on JS and not the store check. The `Debug` text is `StringTooLong { name: "text" }`, which is not `Trap(StringTooLong { pc })`. D8's `OUTSIDE` list names the trap reasons only.
   **Fix:** In the JS commit, after the body, refuse a too-long string store with that `Debug` text and roll back sends and writes. Point D8 at both `StringTooLong` variants. Add a conformance step that stores a resource string one byte over `MAX_STRING`.

5. **MATERIAL — D3, §3.** `xj` does not match `join` on a one-element string list. The VM always takes `items.len()` steps first (`runner/src/vm.rs:766-769`). `join` then returns that single string with no length check (`runner/src/stdlib.rs:192-195`). Every other shape checks `out.len() > limit` per item (`stdlib.rs:212-214`). A string longer than `MAX_STRING` can already exist (finding 4). `xj` "joins and checks the result's bytes" traps where the runner returns the string.
   **Fix:** Specify the fast path: one string item, one step, return it, no `StringTooLong`. Add that pair to D7.

6. **MATERIAL — D3, §3.** The UTF-8 shortcut, implemented as a running total of `3u`, traps on an earlier item than the runner. Rust compares exact UTF-8 (`str::len`) and uses `>` (`vm.rs:722`, `stdlib.rs:212`). A total of upper bounds crosses `2^26` while the exact total is still under it: 10M ASCII units plus 20M more is 30M bytes and 90M if each unit is charged 3. The sentence "once needed the exact count keeps counting exactly" does not say to recompute the prefix already stored as `3u`. A one-shot check (one `cc`, the finished `join` string, `native_props`, `t`) is fine, because `fill` and the VM only care whether the final byte length is `> MAX_STRING` (`plan/src/strings.rs:38`).
   **Fix:** Keep the accumulator in exact UTF-8 bytes. Use `3 * utf16Units` only to prove this addition cannot cross; when that upper bound crosses, rescan the exact prefix, then trap. State that this is required for `xm` / `xf` / `K` byte sums.

7. **MATERIAL — D4, §3.** Skipping the byte check when a composite has one string is unsound. The runner traps `ValueTooLarge` when a scalar string's bytes exceed `MAX_VALUE_BYTES` inside `of` (`vm.rs:245-261`). Nothing establishes that every string is already `≤ MAX_STRING` (finding 4). D4 skips `K` when `Σ strings(partᵢ) ≤ 1` and the node sum is `≤ 2^24`. A record or list of one resource string, derive string, or literal then succeeds on elided JS and traps on the runner. Two strings "check the length sum only", which still looks at real bytes; the hole is the one-string skip. `maxNodes(option<T>)` is also unspecified: under D2 it equals `maxNodes(T)`, and it has to recurse through record fields. A list anywhere stays unbounded. The `≤ 2^24` and `65536 × 255 + 1 < 2^24` arithmetic matches `nodes > MAX_VALUE_NODES` (`vm.rs:260`).
   **Fix:** Elide bytes only when every string leaf is produced in this evaluation by `cc`, `xj`, `t`, `NP`, or an encoder that already enforced `MAX_STRING`. Otherwise check the exact byte length. Spell the recursive `maxNodes` / `strings` rules, including `maxNodes(option<T>) = maxNodes(T)`.

8. **MATERIAL — D7, §3.** Case 5's oracle does not match the VM, and the restore the design depends on is untested. A step is taken in `Callback::begin` before the body (`vm.rs:224-226`, first call at `:826`). If derive A maps 70,000 and then reads B, A's `Map` hits `IterationLimit` and B never runs. "B's pc traps" is true only when A stays ≤ 65,536 and B goes over. The 40,000 + 40,000 success also passes when `leave` zeros A's counter, because A does no more steps after B. The case that catches a bad restore is: A maps 40,000, B maps 40,000, A maps 30,000 more, and the trap is A's second `Map`. Cases 8 and 9 should name the trap. With `shape Card` at 6 nodes (`apps/carousel/data/src/lib.rs:19-27`), `cards(2000)` is 12,001 nodes, `Two(a=cards, b=cards)` is 24,003, and the map's sum crosses `2^24` on the 699th item at the `Map` pc (`ValueTooLarge`, not the record pc). Case 9 is `ValueTooLarge` on the aggregate (`40,000 × 2048 > 2^26`, `30,000 × 2048` does not), not `StringTooLong`. "About 24,000" and "trap on bytes" will not catch a wrong pc or a wrong variant.
   **Fix:** Rewrite case 5 as above and add the resume case. Pin case 8 to 24,003 nodes and item 699, `Trap(ValueTooLarge { pc })` at the `Map`. Pin case 9 to `ValueTooLarge` the same way. Case 1's body has to stay the identity map: `1 + 65536 × 6` nodes is under the cap, a fatter body may not be.

9. **MINOR — D6, §3.** The encoder bound is easy to put on the wrong failure. `encode_route_segment` returns `Err` for `""`, `"."`, and `".."` before encoding (`route/src/table.rs:448-455`). The runner records a router refusal and then `TypeMismatch` (`runner/src/stdlib.rs:92-98`). JS already throws `Refusal("a path parameter cannot be empty, `.` or `..`")` (`host/web-js/rt.js:1386`). A length check belongs on the encoded `Ok` string, at the `Call` pc, as `Trap(StringTooLong { pc })`. §4 tests the runner only; D7 has no encoder step.
   **Fix:** Say that order in D6, and add one conformance step one byte past `MAX_STRING` plus the existing empty-segment refusal.

10. **MINOR — §1.** `scroll-restoration` is not a poisoning reset. `collection/mod.rs:354-358` evals that binding and discards the error with `.ok()`. The other virtualized bindings in the `:266-354` range propagate. A later `emit_bindings` eval (`instance.rs:817`) can still poison if the binding is not constant.
    **Fix:** Say this call swallows a trap, or drop the `.ok()` so it matches the other bindings.

11. **MINOR — D2, §3.** `type-too-deep` is a sound upper bound for values of acyclic shapes, and it refuses programs the VM would run. `check_shape_cycles` rejects a shape reachable again through `option` and `list` (`contract/types/src/checks.rs:330-387`). It does not walk `fn` or action types. VM depth is `depth > 64` (`vm.rs:258`); `Value::decode` uses the same cutoff (`plan/src/value.rs:327-328`). Counting scalar 0 and option, list, and record as `1 + max(child)` matches `with` (`vm.rs:271`). `none` and `[]` are shallower than those types (`Extent::scalar`, `vm.rs:242-254`; an empty `built` stays depth 0). A declared tower of 64 is legal; 65 is not. A shallow value of a type deeper than 64 runs on the VM today and is refused at check time under D2. That matches the JS target only when every target uses the same checker.
    **Fix:** Define the walk as value types only, after shape expansion, `depth > 64`. Leave `fn` and action types out so a cycle the shape check cannot see cannot loop the checker. Keep it a Contract rule (question 2).

12. **NIT — §1.** The filter-identity branch is `vm.rs:525` (the comment is `:524`). The empty-list return is the earlier fast path at `vm.rs:806-809`. `regions.rs:105` is the `each` subject for both the plain list and `$vl`. `emit.rs:339` is the locale slot; other root initializers go through `regions.rs:159`.

## Open questions

1. **D2 is not acceptable on the argument written.** It is the right correspondence for erased JS values, and it is a real weakening of the runner's walk bound, up to the option-depth factor of 64. I would keep the runner's node count and teach the JS measurer about option layers from the type.

2. **Contract rule.** A JS-build refusal rejects programs the runner still runs, including any shallow value of a deep type. D8 needs the same clause in both checkers. `ValueTooDeep` stays the VM's check for a plan the checker did not sign.

3. **The 10% figure is a performance budget, not a parity budget.** Meeting it by skipping a check in findings 6 or 7 breaks the oracle. The Crypto and Bluesky fling numbers are the right app-level bar for stage 3; they do not show that trap pcs match.

4. **Leave `some(none)` as a value bug.** After D2, `some(none)` and `none` are both one node and zero bytes, so the collapse is invisible to the caps, and depth is enforced on the type. Refusing `option<option<T>>` and `option<unit>` would reject programs the runner accepts. It does not belong in this LLP.

Conformance, beyond finding 8, never sees a poison reason, a handler-argument refusal, a slot-store `StringTooLong { name }`, a one-element `join`, an encoder, a one-string composite under elision, or a boot-time initializer trap.

Verdict: NOT READY
