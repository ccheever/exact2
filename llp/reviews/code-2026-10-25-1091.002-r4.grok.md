## 1. A method check inside `${…}` drops `in_block`

`contract/syntax/src/parser/expr.rs:470`

The template sub-parser is `Parser::new`, which sets `in_block` to false and never copies the outer parser’s flag. Calls it records are appended with `in_block: false`. A members file has no `members` line, so `host` is false (`contract/syntax/src/parser.rs:350`). Those calls are decided before the splice, against `file.components` only. The block’s actions live on `file.members` (`contract/syntax/src/parser.rs:561`), so they are invisible. The loader’s post-splice check (`contract/cli/src/sources/members.rs:274`) never sees them.

```contract
component App
  state count = 0
  state label = ""
  members "./more.contract"
  view
    text label
```

```contract
members App
  state label = `${"  hi  ".trim()}`
  action trim(s: string)
    count = 1
```

The same members written in `App` are refused with `syntax-method-shadowed`, because the file declares action `trim`. This split program accepts. The initializer does not see the action (`contract/types/src/component.rs:1227`), so `"  hi  ".trim()` is the built-in and `label` is `"hi"`.

The free spelling is the other way around. Replace the initializer with `` state label = `${trim("  hi  ")}` ``. The pasted file declares action `trim`, so the free call is allowed and, in that initializer, is the built-in. The split program reports `syntax-method-form`.

Fix: construct the sub-parser with the outer `in_block`. A `${…}` call in a block must be deferred like any other call there.

## 2. `declared()` decides a block’s calls from the members file

`contract/syntax/src/parser.rs:338`, `contract/syntax/src/parser.rs:356`, `contract/syntax/src/parser.rs:385`

For a free call, `declared()` skips the deferral. For a method call, `declared()` refuses immediately. `declared()` is this file’s fns, shapes, and component actions. A `members` block is not one of those components, but a sibling component, fn, or shape in the same file is. D4 pastes only the block into the listing file; D6 then judges that call against the listing file. The sibling never becomes part of that file.

```contract
component App
  members "./more.contract"
  view
    text label
```

```contract
component Card
  action trim
    let x = 1
  view
    text "Card"
members App
  state label = "  hi  ".trim()
```

Pasted into `App`, with `Card` left in its own file, `"  hi  ".trim()` is the built-in and the program compiles. The split program reports `syntax-method-shadowed` on the state, because `Card`’s action makes `declared("trim")` true.

Swap the initializer for `state label = trim("  hi  ")`. The pasted program reports `syntax-method-form`. The split program accepts it. `trim` is not a member of `App`, so the call stays the roster function and `label` is `"hi"`.

The same short-circuit fires for a fn or shape of that name in the members file. `fn trim(s: string): string = s` above the block makes `"  hi  ".trim()` in the block `syntax-method-shadowed`. Pasted into `App`, that fn is not in `App`’s file, and the method is the built-in.

Fix: if `in_block` is set, do not consult `declared()`. Defer the call and decide it from the listing file after the splice. A method call written in the block must not be rewritten to a fn or shape that stays in the members file; after the paste that call is the built-in unless the listing file itself declares the name. Scope today rewrites every `Expr::Call` of a same-file fn (`contract/syntax/src/scope.rs:921`), and a method is already that call, so the call has to stay distinguishable until that decision.

## 3. `listed_by` exempts bindings that are not pasted

`contract/cli/src/sources.rs:1065`, `contract/cli/src/sources/members.rs:231`

A listing-file fn or shape is left unrenamed when any other file binds the name and `listed[other] == Some(index)`. `listed_by` marks the whole members file, and `bindings` (`contract/syntax/src/scope.rs:170`) includes every local in it: fn parameters, and states of components that are not the block. Only the block is pasted (D4). Those other bindings remain another file’s, and they must still rename the listing file’s declaration or the type checker’s fn-before-binding order (`contract/types/src/lib.rs:847`) will reach it.

```contract
fn save(x: number): number = x + 100
component App
  state n = save(1)
  members "./more.contract"
  view
    text n.toString()
```

```contract
component Card
  state save = 0
  state shown = save(1)
  view
    text shown.toString()
members App
  state extra = 0
```

Paste the block into `App` and leave `Card` in `more.contract`. `Card` binds `save`, so `fn save` becomes `save__app`. `shown = save(1)` is not that fn and is refused (`unknown function`). The split program leaves the fn named `save`, because `listed[more] == Some(app)`. `save(1)` in `Card` is type-checked as `fn save` and `shown` is `101`.

A fn parameter is enough on its own: `fn helper(save: number): number = save` in the members file, with no `Card`, also suppresses the rename.

The mirror image changes a plan that should match the one-file program. `bindings` of the listing file includes `members.outer` (`contract/syntax/src/scope.rs:369`), the block’s names copied across before `unique_names`. A shape declared beside the block is then renamed because the listing file “binds” the block’s own state.

```contract
component App
  members "./more.contract"
  view
    text shown.value.toString()
```

```contract
shape Item
  value: number
members App
  state Item = 0
  state shown = Item(value=1)
```

One file, with that shape and those two states, keeps the shape named `Item` (a single unit never renames, `contract/cli/src/sources.rs:837`). `shown` is an `Item` record. The split program renames the shape to `Item__more`, because `App`’s outer set contains `Item` and `listed[app]` is not `Some(more)`. The call is rewritten to `Item__more`, and the plan’s record type is `Item__more`.

Fix: treat as the listing file’s bindings only the names the block itself declares (the ones `splice` moves), not fn parameters or other components. When testing a declaration that lives in the members file, ignore listing-file bindings that came only from that block’s `outer` copy. A state the listing file writes itself must still rename a shape or fn that stays in the members file.

**Verdict: NOT READY.**
