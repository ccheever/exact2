The check/secret split and the nondelegation rule are sound. Five material decisions need correction.

“RFC” below refers to [llp/1133.010-local-auth.rfc.md](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1/capsule/llp/1133.010-local-auth.rfc.md).

1. **MATERIAL — A previously unlocked answer can defeat the first-frame lock.**

   **Problem:** Excord’s TypeScript cannot inspect `store.has` before first pixel. The runner can instead seed the previous successful session answer, including its unlocked state. RFC D5 explicitly allows keeping that answer. Consequently, a cold launch can initially present unlocked UI before fresh authentication.

   **Evidence:** RFC:301,865–870; LLP 1018:203–215; [runner/src/runner.rs:1019](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1/capsule/runner/src/runner.rs:1019) restores kept answers before `data_ready`. `runner/src/runner/kept_secrets_tests.rs:148–152` expressly permits an admitted kept answer despite stored secrets. Excord’s `loadSession()` has no identifying arguments (`apps/excord/app.contract:101`).

   **Resolution:** Make authorization state transient. Decide either a pre-pixel host/runner lock guard or a rule excluding this state from kept answers, with a conservative locked placeholder. Specify carry/checkpoint behavior too. Drive a cold launch **after a successful unlock**, inspecting the actual first frame before data readiness.

   This demonstrates a presentation failure, not token decryption or a gateway bypass: current `connect` also checks the initially empty in-memory token (`apps/excord/live.ts:65–69,217–219`).

2. **MATERIAL — Enabling protection cannot confirm that the ungated copy is gone.**

   **Problem:** `set(locked)` followed by `forget(plain)` comprises independent writes after the logical commit. A failed deletion can leave the token ungated while the switch and logical store say protection is enabled. A failed protected write followed by successful deletion loses the durable session. The same issue affects automatic plain-to-presence migration.

   **Evidence:** RFC:278–281,322–331,860–864. [host/apple/src/persistence.rs:22](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1/capsule/host/apple/src/persistence.rs:22) persists writes independently and retains failures; its lines 5–6 explicitly say persistence cannot refuse an already committed operation. Android’s shared Linux host does likewise (`host/linux/src/system_support.rs:119–153`). Drive 1 checks the logical store list, which cannot prove durable deletion.

   **Resolution:** Define an acknowledged durable transition with recovery after partial completion or process death. Preserve the source until the protected destination is durable, and report protection enabled only after confirming source deletion. Add persistence-failure and crash-boundary drives in both directions and for policy migration.

3. **MATERIAL — Android key sharing ignores part of the required security policy.**

   **Problem:** D6 shares one key pair per policy under `exact.presence.<policy>`, but D10 permits individual names to require StrongBox. If an ordinary `user-presence` name creates the alias first, a later StrongBox name encounters that weaker key. Reusing it violates the guarantee; replacing it makes the earlier ciphertext unreadable.

   **Evidence:** RFC:375–380 versus 517–525. StrongBox protection is a key-generation property, and key authorizations cannot subsequently be changed. [Android Keystore documentation](https://developer.android.com/privacy-and-security/keystore#KeyUseAuthorizations).

   **Resolution:** Use per-name keys or key identities derived from the complete effective security descriptor, including StrongBox and applicable hatch configuration. Validate existing keys before reuse; treat modifier changes as policy changes. Test ordinary and StrongBox names in both creation orders.

4. **MATERIAL — Android cannot supply the lifecycle fact required by Excord’s return lock.**

   **Problem:** The consumer locks after a minute hidden using `exactPage().visibilityState`. Android currently supplies the default visible value, and the Android build stage does not include implementing this dependency. The substitute’s visibility override therefore proves behavior unavailable on the real host. With the token retained in memory, the intended return check need never occur.

   **Evidence:** RFC:873–876,897–900,952–958. `llp/1133.000-the-roster.rfc.md:65` explicitly records “Android answers defaults.” [ExactActivity.kt:444](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1/capsule/host/android/canvas/src/main/java/dev/exact/canvas/ExactActivity.kt:444) suspends rendering and notifies requests/extensions without propagating page visibility.

   **Resolution:** Include Android lifecycle-to-runner visibility and elapsed-background-time handling in the build plan, or choose an available lifecycle mechanism explicitly. Require a real background/resume drive; the proposed phone drive tests authentication prompts only.

5. **MATERIAL — The Android default selects a documented broken path on supported releases.**

   **Problem:** The RFC unconditionally sets `setUnlockedDeviceRequired(true)` while supporting API 30 onward. Android documents that on Android 12–14, weak biometric device unlock does not reauthorize these keys; biometric unlock also fails for profiles sharing their parent’s lock. This can prevent D6’s cipher initialization before the authentication prompt, despite the person having opened the app.

   **Evidence:** RFC:213,375–385,392–396. Android recommends applying this flag only on Android 15 onward. These failures are distinct from the two other documented issues that authentication-required keys already share. [Android builder documentation](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUnlockedDeviceRequired(boolean)).

   **Resolution:** Explicitly gate the flag to API 35+, retaining per-operation authentication on older releases, or choose and verify a recovery path. Add an affected-version weak-unlock/profile drive; an emulator fingerprint match does not cover it.

6. **MINOR — The unconditional hardware wording exceeds the stated platform guarantee.**

   **Problem:** The summary describes hardware as the enforcer, while the host table permits software-backed Android keys. Those are different protection levels, although software Keystore still provides enforcement outside the compromised app process.

   **Evidence:** RFC:25–28,170–171 versus 186. Android distinguishes key residence from hardware enforcement of authentication. [Android Keystore documentation](https://developer.android.com/privacy-and-security/keystore#KeyUseAuthorizations).

   **Resolution:** Qualify the hardware claims and distinguish app-process compromise from OS/Keystore compromise. If hardware enforcement is required, refuse unsupported keys instead of merely reporting their level.
