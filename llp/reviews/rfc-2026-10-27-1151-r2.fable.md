## 2. New fundamental issues

**1. `clock data` and `clock settle` as *empty* events is wrong; they are `clock +0`.** D4.1's justification is "under the synchronous oracle every answer has already landed". The answer has; its `then` has not. A commit that sends arms the mutation's `then` at the commit's time (`Runtime.lean:846`, `:896`, `armThens` at `:596-604`), and an armed `then` "runs at the next clock advance" (`Runtime.lean:538-540`), as its own commit, in `advance`'s `go` (`:1116-1118`). On a device `clock data` is exactly the step that "lands replies and their `then`s without moving the clock" (`docs/contract-grammar.md:813`). So an empty event leaves every `then` to run inside the *next* tap's step (`Observe.lean:131-141`: `dispatchAt` advances to `c.now` first): an authored `expect` after `clock data` that reads a `then`'s write fails on the harness where it passes on the device, and every tap after a send becomes a multi-commit step, so D1's `after "a"` is "counted, not checked" for precisely the actions that send, and `old` is read before the `then`. Resolution: deliver both as `Event::Clock(0.0)`, which `script.rs:153-154` already accepts (`ms >= 0.0`) and which Lean runs as `advance p o c c.now` (`Runtime.lean:1130`), firing the armed `then`s and queue `next`s due now and nothing else. Do the same in D4.3's walks: emit `clock +0` before each tap, so due work gets its own observed step and a tap step is one commit except in a `then` chain. That also answers open question 1 (below).

**2. D1 refuses derives on a false claim.** "`expect state` has never read one" is false on both runners: the harness matches `expect state` against `slot`, `derive` and `resource` lines alike (`lib.rs:345-347`), and the device driver reads `state.derives` and `state.resources` into the same bag (`scripts/agent-test.mjs:772`). The stated reason, "the harness cannot see through it", does not apply to stage 1's matcher, which sees through nothing: it matches printed values, and both sides print every derive after every step (`observe.rs:148-151`, `Observe.lean:97-98`). Refusing derives is therefore a choice, and a costly one: the properties agents' apps most want to state are over derives (`canSave`, `filtered`, a computed `screen`), D6's suggestions are "over states", so the demand measurement that decides stage 2 systematically misses them, and the document already admits mutation slots, whose value is the oracle's, with a receipt line. Resolution: admit derives in stage 1 under the cone rule the document already specifies for stage 2 (refuse one whose cone reaches a resource, the clock or geometry; the compiler has the derive dependency graph, `contract/syntax/src/inline/derives.rs:97`), suggest over them in D6, and keep the mutation-slot treatment consistent. If the authors still want them out, say it is a choice and why.

**3. The `after` form is unverifiable on the harness for records, and the document says it works "as `expect state` does".** `path` reads "a record's field or a list's index as `expect state` does" (D1). On the device it does (`agent-test.mjs:773-780`). On the harness `expectations` formats `slot a.b v` and record values print positionally, `{v,…}` with no field names (`observe.rs:50-56`, `Observe.lean:58`), so a path has never matched there. The matcher needs the plan's record type to resolve a field to a position on both observations. Small, but it is a stage-1 claim about today's code that is false, and it is the form every `after` over a record state needs.

**4. Once built, the differential check holds Lean's trace to the runner's and nothing holds either to the configuration they claim to have produced (open question 2). Not a redesign; a cost to name in §4 item 1 and a reason to answer open question 2 in stage 1 (below).

## 4. Open questions

1. *Steps with more than one commit.* With issue 1 fixed (`clock +0` as `clock data`/`settle` and before every walk tap), a tap step holds more than one commit only in a `then` chain or when an authored test taps without a `clock` step between a send and the tap. Count those; observing every commit is not stage 2's first item unless the counts stay large after the fix. Confidence: high.
2. *The trace's proof.* Prove `(advanceTrace p o c t).1 = advance p o c t` in stage 1, by the same induction on the fuel as `advance_preserves`; it is a page, and it is what makes D9 able to state anything over `ran` lines and what makes the trace a definition of the observation rather than a second interpreter. Defining `advance` as the projection would make it `rfl` but risks every proof that unfolds `advance.go`; keep `advance` as it is. Confidence: medium.
3. *Where suggestions stop.* No new form. "Once true, stays" is a monotone property the vocabulary cannot state (it is conditional on the current value), and `after` on every action is the wrong shape for it. Print it as a text-only suggestion ("`ready` never went from true to false over N steps") as evidence for a `once` form later; it costs one boolean per slot. Confidence: medium.
4. *The device claim.* Fail `bun exact.mjs verify` as a failed `expect` does. A property is an `expect` at every step, the author wrote it for the app's world, and a device run is the app's world; a report beside the tests is the line authors learn to skip. Name the step and the host in D4's form. Confidence: medium-high.
