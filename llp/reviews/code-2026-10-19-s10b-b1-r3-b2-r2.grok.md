## Should-fix

**1. An answered connection drops its deadline and holds one of the 64 slots.** `scripts/tamber-remote.mjs:173-176`, triggered by `scripts/tamber-server.mjs:491`.

`req.once('end')` always `clearTimeout`s. `res.once('finish')` always arms a new timer. On Bun 1.4.2 `finish` is deferred, and for these responses `end` runs after that re-arm, so the idle timer is cleared and nothing arms another. The map entry stays, so the socket still counts toward 64.

The production remote and tunnel path hits this on every request. `handle` answers 404 at `tamber-server.mjs:491` before `body()` whenever the method is not POST, the token is absent, or `access.remote` is set. That is every remote request until pairing lands. A GET with no body does it too.

Loopback probe, `timeoutMs` 400, handler writes the 404 without reading the body:

- TLS GET, POST with `Content-Length: 0`, and POST with `Content-Length: 1` (body byte sent after the 404) were all still open at 1600 ms.
- A second GET written 900 ms after that 404 was answered, past the deadline.
- 64 TLS connections that had each already received a 404 were still open 900 ms later. A 65th TCP connection was destroyed at 2 ms.
- The same GET on the tunnel was still open at 1600 ms.
- `close()` resolved after that.

A long poll and SSE that read the body first are left alone. Same probe, `timeoutMs` 350, handler consumes the body, then waits: an 800 ms answer completed (`answered@806`, connection closed by the idle timer at 1158 ms). An SSE response that never finishes was still open at 1600 ms. `/__tamber/events` waits `POLL_MS` (25 s) at `tamber-server.mjs:545` only after `body()` returns, and `/__tamber/subscribe` writes the stream and stays open. Today’s remote door never reaches either, because of the 404 at line 491. When pairing removes that early return, this order matches the guard and the wait is not cut.

The existing test stays green for the same reason. `scripts/tamber-remote.test.mjs:211-252` uses a handler that reads the whole body before `res.end()`, and its idle case is `Content-Length: 0` under that handler. The real wire’s remote 404 is the other order.

Fix the guard with two counters, still one timer and no per-request socket listeners. On each request increment “response still open” and “body not ended.” On `end` or `finish`, decrement and then:

- response still open and every accepted body has ended: clear the timer (long poll and SSE);
- nothing open and every body ended: arm the idle deadline;
- a body still outstanding: leave the accept deadline running. Do not clear it and do not arm a fresh one on `finish`.

That keeps the deadline absolute from accept through a body the 404 did not read, and arms one idle window only once the exchange is actually finished. Add a test whose handler `res.end()`s before reading, including `Content-Length: 0`, and assert the socket is gone within the deadline and that 64 such connections do not still fill the cap after it.

**2. Pipelined requests on the TLS door get one response and a closed connection.** `scripts/tamber-remote.mjs:183-185`.

`secure` parses by `http.emit('connection', socket)`. On Bun 1.4.2 that socket is not the HTTP server’s accepted socket, so it takes the HTTP/1 fallback, which calls `assignSocket` for every request immediately. The second request in the same buffer throws `ERR_HTTP_SOCKET_ASSIGNED` inside the parser’s data handler.

Probe, two requests in one write, `uncaughtException` count 0:

- TLS door, immediate 404: one response, 258 bytes, then the connection closed.
- Tunnel, native `http.Server.listen`: both responses, including an 800 ms second handler under `timeoutMs` 350 (`fast` and `slow` both present). The tunnel does not drop the pipeline, and that long second response is not cut.

Fix: do not let the fallback parser see the next request’s bytes until the current response emits `finish`. Hold the tail of the chunk and release it on `finish`. Pausing the socket on `request` is too late when both requests arrive in one segment. The tunnel path can stay as it is.

**3. A dev-loop listen failure still exits without stopping the design server.** `host/web/dev.mjs:1479` and `host/web/dev.mjs:1482`; `host/web-js/dev.mjs:1025` and `host/web-js/dev.mjs:1027`.

`tamberServer()` has already started the detached design child (`host/web/dev.mjs:405`, `host/web-js/dev.mjs:854`) before those listens. On `EADDRINUSE` the handlers call `process.exit(1)` and skip `tamber.close()`. `close` is what sends SIGTERM, then SIGKILL (`scripts/tamber-server.mjs:992-1013`); skipping it can leave `.exact/tamber.lock` held. Remote-bind failure already goes through `stop()` (`host/web/dev.mjs:1495`, `host/web-js/dev.mjs:1028`). `serveAlone` opens the doors first and awaits both closes on either failure (`scripts/tamber-server.mjs:1056-1059`).

Fix: on those four paths, `await tamber?.close()` (and `doors?.close()` if any) before `process.exit(1)`, as `serveAlone` does.

## Nit

**4. The wasm `stop()` never closes the dev HTTP server.** `host/web/dev.mjs:980-989`. A remote-bind failure sets exit code 1 and awaits `stop()`, and `tamber.close()` can take about 7 seconds. During that the main server still answers, including `GET /__tamber/token`. The JS loop closes its server at `host/web-js/dev.mjs:1012`. Call `server.close()` at the start of `stop()`.

**5. Both flags and no design names only `--remote`.** `host/web/dev.mjs:60`. If `--remote` and `--trust-tunnel` are both set, the message names `--remote` only. Name each flag that was set.

**6. Any `::1` bind error other than `EADDRINUSE` is ignored.** `scripts/tamber-remote.mjs:229-232`. `EADDRINUSE` closes the IPv4 listener and throws. Every other error (the intended “no IPv6 loopback” cases and anything else) continues with only `127.0.0.1` bound, and `six` is not closed. Treat `EAFNOSUPPORT` and `EADDRNOTAVAIL` as the skip; `six.close()` on that path; close and throw for every other code.

**7. `addPort` does not apply the wire’s Origin check.** `scripts/tamber-remote.mjs:239-243`. It checks the certificate name and origin-form, then hands the request to the canvas handler with the cookies still attached. Nothing calls it yet, and leaving canvas cookies in place is deliberate. When a handler is attached, run the same Origin comparison as `remoteHandler` at `scripts/tamber-remote.mjs:142-146` and 403 on a mismatch.
