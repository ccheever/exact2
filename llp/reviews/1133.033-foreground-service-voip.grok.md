## MATERIAL

### 1. The answer path waits on itself
D9, lines 513–517; D10, lines 541–554; D21, lines 905–913.

A person answering on the system UI is fulfilled only after the `callanswer` handler's commit lands. D10 tells that same handler it may open the microphone, and a capture started while the call's audio is not up yet waits for `provider(_:didActivate:)`. CallKit activates the session only after `fulfill()` (Apple's "Making and receiving VoIP calls": configure, then `fulfill()`, then `didActivate`). A Contract `send` is part of the commit (`docs/contract-for-humans.md`, "Resources and mutations"), and `startMediaRecorder` is the lease that calls the audio-session claim (LLP 1133.009 D6). The commit waits for the capture, the capture waits for `didActivate`, and `didActivate` waits for the commit. The wait ends at `CXAction.timeoutDate`; the mic fails, and the action is failed or fulfilled too late to start audio. Android already returns from `onAnswer` immediately because Core-Telecom tears the call down if a callback exceeds five seconds (D9, lines 518–522). The agent does the opposite of production: `tap @ref answer` sets `audio` true as it raises `callanswer` (D21), so drive 9 never hits the wait.

**Decision:** On iOS, configure the session and `fulfill()` (or `fail()`) inside `perform`, then deliver `callanswer`. The handler opens the mic after that, when `didActivate` can still arrive. Keep the Android "return at once" rule. Change the substitute so `audio` stays false until the same point production sets it.

### 2. Playback during the test call leaves the call's audio session
D10, lines 532–563; §9.2, lines 974–976. Built owner: `host/apple/Sources/ExactKit/AudioSession.swift` lines 278–284 and 241–246.

The Harmony test call records, stops the take, then plays it with `audio src=` while the call is still up. That playback is the sound arm's `AudioSession.hold`, which calls `reconcile()`. When the take's capture claim has ended, `captures` is empty, so `reconcile` sets the category back to the app's and calls `setActive(true)`. `releaseCapture` also runs `restoreAfterCaptures()` as soon as the last capture ends. D10's table covers "a call" and "a call and captures" only. Apple DTS (forum 749202, cited in D10) is this failure: an app `setActive` takes the session away from the phone session CallKit is activating. The test call's playback is the moment that happens.

**Decision:** Add a row for players and speech while a call claim is held: the call's category, mode, and options stay, and no path in the owner calls `setActive` or `setActive(false)` until the call claim ends. Restore the app's session only then.

### 3. One `audio` mode, two opposite policies
D3, lines 249–255; D5, lines 327–351; D10, lines 571–586; D16, lines 752–755; §9.2, lines 967–980. Built gate: `packages/media-capture/apple/MediaCapture.swift` lines 277–283 and 439–442.

`device.calls` and `device.microphone-background` both derive `audio` in `UIBackgroundModes`. The built capture treats that plist entry as the whole background-recording switch: `recordsInBackground` skips the pause, and the capture claim is stored with `background: true`. LLP 1133.009 D8 still says an iOS take continues whenever that mode is present. So Harmony, which gains `device.calls` and not `device.microphone-background`, keeps every capture running in the background on iOS. The summary (lines 40–42) says that without the microphone line, leaving the app pauses the take on both phones.

On Android the same app does the opposite. D5 pauses at `foreground(false)` unless `device.microphone-background` is granted. `device.calls` does not exempt an in-call lease. A test call that starts in the foreground and then locks, which §9.2 lists as what the consumer exercises, pauses on Android while it continues on iOS. D10 only admits a **start** while hidden. Android 9 and later still feeds silence to a background app that has no microphone-type foreground service (`Android 9` behavior changes, cited in D5), so a pause policy and a service type have to agree.

Drive 7 also expects a hidden start to be admitted on the web. A page cannot begin `getUserMedia` while hidden; Media Session does not activate a call audio session. The agent drive passes a policy the browser will refuse.

**Decision:** Key the iOS pause and the capture's `background` flag off `device.microphone-background`, not off the plist. Keep `audio` in the plist for calls so the process can stay up, and do not pause a lease whose call has `audio == true` and, on Android, a service that currently includes the microphone type. State that the hidden-start exception is iOS and Android only.

### 4. The call's service cannot legally use the microphone
D2, lines 177–186 and 197–202; D11, lines 590–595; D16, line 755; D10, lines 579–582.

D2 declares one service class per type, and the manifest `android:foregroundServiceType` is that one type. D11 then promotes the phone-call service with `FOREGROUND_SERVICE_TYPE_PHONE_CALL | FOREGROUND_SERVICE_TYPE_MICROPHONE` while the call's capture runs. `startForeground` throws `IllegalArgumentException` if the passed types are not a subset of the manifest attribute (Android 10+ service types; enforced for these types since Android 11, and as a hard error since Android 14). D2 only names `SecurityException` and `ForegroundServiceStartNotAllowedException` as refusals, so this throw is not one of the handled ones. Harmony does not grant `device.microphone-background`, so there is no second microphone service to satisfy the background-mic check either. Android 11 requires a service that uses the microphone in the background to include the microphone type. The same hole is the camera: D10 admits a hidden camera start for a video call, and `device.calls` never derives `FOREGROUND_SERVICE_CAMERA` or a camera type on that service. The app's `targetSdk` is 36 (`host/android/app/build.gradle.kts` line 41), so this enforcement is on.

**Decision:** The phone-call `<service>` declares every type it will pass to `startForeground` (`phoneCall`, plus `microphone` while a call captures, plus `camera` for a video call). D2's "one class per type" stays for separate capabilities. A call capture does not depend on `device.microphone-background` to be allowed to hear.

### 5. The seam's channel importance makes an incoming call invisible
D4, lines 291–294; D11, lines 604–623.

The claim seam creates one channel per type at the first claim, at `IMPORTANCE_LOW`. Android will not raise a channel's importance later; the first creation wins. A `CallStyle` incoming call needs `IMPORTANCE_HIGH` (or higher) to be a heads-up, and a full-screen intent does not launch the activity from a lower channel (Android 14 full-screen-intent rules, and `Notification.CallStyle`). D4's citation only requires `PRIORITY_LOW` or higher, which is the floor for a foreground-service notification, not the level a ring needs. Drive 13's locked-screen full-screen intent and its heads-up fallback both fail on a low channel. `USE_FULL_SCREEN_INTENT` does not override that.

**Decision:** The microphone channel stays `IMPORTANCE_LOW`. The phone-call channel is created `IMPORTANCE_HIGH` before the first `CallStyle` post. D4 must not be the channel rule for every type.

### 6. Ringing while the app is not visible cannot start the service
D2, lines 203–214; D16, lines 770–773; §9.2, lines 987–993; drive 13, lines 1043–1046.

D16 says `reportIncomingCall` proceeds when the app is hidden, because the app's own connection learned of a call. D2 says the seam refuses a claim while the reader is not resumed, unless the caller passes a permitted platform event, and the only such event named is D11's notification answer. The reader marks itself not resumed in `onPause` (`host/android/canvas/.../Extensions.kt`, `paused()`). Locking the screen pauses the activity. Android 12 and later then throws `ForegroundServiceStartNotAllowedException` for a `phoneCall` start from that state. The exemptions that remain are a visible activity, a user action on a notification, and a high-priority FCM message (the push path D12 does not build). Camera, microphone, and location lose even those exemptions except a few, including a notification action (Android 14 background-start restrictions, cited in D2).

§9.2's **Ring me** calls `reportIncomingCall` five seconds later so the incoming UI can meet a locked screen. After five seconds the process is still alive and the activity is stopped, which is the state that is refused. Stage 4 builds this path. Push is the exemption, and it is not in this stage.

**Decision:** Split the origin table by target. On Android, `reportIncomingCall` from a hidden app fails unless a `phoneCall` service is already in the foreground or the start is on an exemption the seam names (notification action, and later the push). Ring me starts and promotes the service while the activity is still resumed, then updates that notification to `CallStyle` when the five seconds elapse. Do not describe a locked-screen ring as something stage 4 can start cold.

### 7. A push-delivered call dies with the wake that booted it
D12, lines 641–663; §10, lines 1059–1060. Inherited rule: LLP 1133.017 D6, lines 463–471, and D9, lines 605–610.

D12 amends only "a wake never presents." It does not amend the rest of a wake. A session the wake booted is ended when the wake finishes if no view has attached, and that session may not open a stream (`exactStream`, Harmony's `live`) until a view attaches. An incoming call answered on the lock screen often never attaches a view. The host has already reported the call to CallKit, which will keep showing it. The session end releases the call's claims (D2, lines 225–228) and drops the handler that was supposed to connect to the server. D6 also runs no `every` or `when` timer in a headless session. D12 step 3 says that handler connects to the app's server, which on Harmony is the live socket the wake is forbidden to open. The same end applies to the Android FCM path once the headless session exists. Completing the PushKit handler before the boot (D12 steps 1–2) is right; it does not keep the session.

**Decision:** A call the host has reported holds its session, process, and signaling stream until the call ends, with or without a view, and that lifetime is not the wake's budget. Amend LLP 1133.017 D6 in those words. The wake still must not draw, and its own commits stay origin `wake`. The person's answer stays an activation.

### 8. Android rejects the tier-1 handle the test call uses
D7, lines 419–422; §9.2, line 970.

`handle` is an opaque string: a phone number, an email, or an account id. The test call passes `handle="test-call"`. On API 34 and later, `android.telecom.CallAttributes.Builder` throws if the address URI has no scheme. Core-Telecom builds that object on the API levels this app targets. `Uri.parse("test-call")` and `Uri.parse("555-0100")` both have a null scheme. iOS `CXHandle` takes the same string with a separate type (`generic`, `phoneNumber`, `emailAddress`), which this RFC puts at tier 2 as `apple.handleType` and leaves defaulting to `generic`. There is no Android mapping. `startCall` on the fixture fails before `addCall` returns.

**Decision:** Define the tier-1 mapping. Phone number, email, and opaque id become `tel:`, `mailto:`, and a scheme the module owns, on Android. iOS keeps `CXHandle.HandleType`. The test call's `"test-call"` must survive that mapping.

## MINOR

- **D10, lines 549–550, and D8, line 435.** `audio` is set only from CallKit `didActivate` / `didDeactivate`. The test call waits on `audio` before it opens the mic (§9.2, lines 973–974). Core-Telecom, macOS, and the web have no such callback. Say when each sets it: Telecom when `setActive` or `onAnswer` / `answer` succeeds; own-state targets when the call becomes `connected`.
- **D9, lines 479–483.** `supportsVideo` defaults to true when the bundle has no `video` literal. Harmony's test call then gets CallKit's video chrome. Default false, and set it when a declared call is a video call.
- **D5, lines 352–361.** `MediaCodec`'s AAC encoder emits raw access units plus `csd-0`, not ADTS. A writer that appends those buffers does not produce a file `MediaMuxer` can remux. Synthesizing ADTS (and stripping it on the way back, with timestamps rebuilt from the 1024-sample frame) can work. The parent already uses fragmented MP4 on Apple for this same kill (LLP 1133.009 D6); that is the closer Android mechanism if a fragmented muxer is acceptable in the locked graph.
- **D14, lines 700–702, and the ceiling table line 734.** Hold is tier 1, but `supportsSetInactive` is a tier-2 capability with no unsaid default. Without it, Core-Telecom does not offer `onSetInactive`, so a cellular call cannot hold the VoIP call. Default the capability on.
- **D13, line 683, and drive 12, line 1042.** `includesCallsInRecents` defaults to true, and the iPhone test treats a Recents entry as success. A local echo named `test-call` is written into the system phone log. The test call should turn that off. App Review has also rejected CallKit used for something that is not a real VoIP call; Q4 should weigh that before Harmony ships it.

## IMPLEMENTATION-PHASE

- Make each `.part` frame durable (finish the bytes, then `fsync`) and truncate a torn last frame on recovery. Delete the part only after `MediaMuxer.stop()` succeeds. Persist sample rate and codec config beside the frames.
- The answer `PendingIntent` has to be a service or activity the system counts as a user action. A broadcast that then starts an activity is a notification trampoline and is blocked on Android 12 and later.
- Promote the phone-call service, then `addCall` inside it. `addCall`'s block runs until the call ends.
- Handle `providerDidReset` by ending the module's calls and releasing the call claim.
- The service is not sticky. A process restart that still enters `onCreate` must call `startForeground` and then `stopSelf`, or the app crashes with `ForegroundServiceDidNotStartInTimeException`.
- Whether Bluetooth route names appear without requesting `BLUETOOTH_CONNECT` is already a stage-4 measurement (D11). Keep it there.
