## Findings

1. **MATERIAL. A presence secret cannot be both a snapshot fact and absent from the snapshot.** `store.has` is defined as a synchronous read of the boot snapshot, and `store.set` "rides the commit as every store write does." In this tree that commit path is `Store::set`, which inserts the plaintext into `values` (`runner/src/store.rs:386-399`). `Store::snapshot` copies those bytes (`runner/src/store.rs:465-470`). That vector is what a dev reload carries (`runner/src/runner.rs:726` into `boot_carrying` at `653-668`, which does not re-read the platform), what a logic-module call receives (`logic/abi/src/lib.rs:121-126`), and what the web and worker dispatch receive (`js/web/src/lib.rs:674-684`). On Android and Linux a non-carried boot also sweeps every file in the secrets directory and loads its bytes (`host/linux/src/system_support.rs:20-52`). Stage 0 then requires the presence name to be absent from the boot snapshot and from those per-call snapshots (`llp/1133.010-local-auth.rfc.md:294-303`, `:930-933`). Those requirements cannot be true of this `Store` at once. If the bytes stay in `values`, they are in the carry and in every worker snapshot, which is the leak the RFC forbids. If the name is omitted, `has` is false, `opened_with_secrets` stays false (`runner/src/store.rs:215`), and Excord's first frame cannot be the lock screen. A reload makes it worse: carry is the next boot's snapshot, so either the plaintext is carried or the lock disappears until a cold start.

   **Resolution.** Give the runner a presence-occupancy set: name and policy, no bytes. Boot fills it from an attributes-only or ciphertext-exists query. `set` emits a `StoreWrite` and updates occupancy, and does not insert the plaintext into `values`. `has` reads occupancy. Carry and per-call snapshots carry occupancy only. `opened_with_secrets` is true when any occupancy bit is set. Stage 0 asserts the byte snapshots, the carry, and `exact.kept.*` contain no presence plaintext, and that `has` survives a reload.

2. **MATERIAL. Excord's lock does not cover the credential Discord actually keeps.** The switch forgets `discord-token` and writes `discord-token.locked` once (`llp/1133.010-local-auth.rfc.md:860-864`). The gateway then rotates the token on `READY`: `discord/gateway.ts:253-255` pushes `{kind:'token'}`, and `perform` writes it back to the plain name (`apps/excord/live.ts:161-164`, `tokenKey` at `:73`). After that, a live session token sits in the ordinary store. On iOS that item is `AfterFirstUnlockThisDeviceOnly` (LLP 1018 D7), readable with no biometrics. The return path makes this routine: after a minute in the background the lock screen calls `authenticate` while the token stays in `live.token` and the gateway stays open (`llp/1133.010-local-auth.rfc.md:873-876`), so a refresh can run during the "lock." Drives 1–7 never inject a refresh, so they stay green while the ungated copy exists. `null` from `unlock` sending the user to sign-in (`:871-872`) does not delete that plain item.

   **Resolution.** While the lock is on, every write of the session credential, including `perform`'s refresh, is `store.set` of the locked name (D5 already shows no sheet for a write) and must not touch the plain name. Forget the plain name only after the locked `set` has committed. Add a drive: after unlock, deliver a `READY` with a new `auth_token`, assert the plain name stays absent, relaunch, `allow` the presence ticket, and assert the gateway identifies with the new token.

3. **MATERIAL. The plain-to-presence move races the first unlock and can destroy the session it is meant to keep.** D4 reads a plain item after first pixel, writes it gated, and then deletes the plain copy (`llp/1133.010-local-auth.rfc.md:275-281`). The first frame is also after first pixel, and the lock screen calls `unlock` immediately (`:865-869`). `unlock` answers `null` when the presence item is not there yet (`:371-373`, `:317-318`), and Excord treats `null` as "Sign in again" (`:871-872`). Nothing orders the move ahead of that call, and nothing stops a sign-in `set` from landing between the read and the delete. Same-name policy changes ("one policy to another," `:285-286`) have the same hole. Excord's two-name switch does not use this path; any later update that changes a name's policy does.

   **Resolution.** Perform the move on the host before data code runs again, still without a sheet and still off the pre-pixel read. `has` stays false and `unlock` is refused until the gated item is committed and the plain item is deleted. A `set` of that name during the move waits for it. The first frame shows the lock only after occupancy is true.

4. **MATERIAL. On Android the sheet is assigned to a channel that cannot carry the authenticator entry, and the channel that returns bytes is the one the secret must not use.** The runner is on the `exact` thread (`host/android/canvas/.../Owner.kt:82-84`). `BiometricPrompt` has to be shown on the main thread of the resumed activity. D8 says request kind 11 carries that call (`llp/1133.010-local-auth.rfc.md:444-449`). Kind 11 is `Extensions.call` (`host/android/canvas/.../Requests.kt:83`), which JSON-decodes a declared `source` or `send` and calls `later` (`Extensions.kt:11-16`, `:68-83`). The authenticator entry returns a `BiometricPrompt.CryptoObject` (`llp/1133.010-local-auth.rfc.md:638-642`). A `Cipher` is not that JSON body, and `CryptoObject` is not parcelable across that queue. The reply path for kind 11 is `Exact.answer`, the module reply LLP 1133 D6 rule 1 inspects and journals. D13 exists so the secret never travels that route (`:658-661`). As written, the implementation either cannot show the prompt or it returns the plaintext on the journaled route. `BiometricPrompt.Builder(Context)` itself does work with `ExactActivity` (it is an `Activity`, and the framework builder takes a `Context`: [Builder](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt.Builder#Builder(android.content.Context))). The activity type is fine. The dispatch is not.

   **Resolution.** Keep the `Cipher` in the host's Kotlin presence backend, keyed by an id. A new request kind, or a side table the module slot does not log, asks that backend to call `authenticate` on the main executor and then `doFinal` on a background executor. Only a success or failure code crosses back to the runner. The plaintext is delivered on the store-completion path that finding 1 keeps out of `values`, the journal, and `state`. The module's `authenticate()` send may keep using kind 11, because its answer is not a secret. State this channel in D8 and D13. Kind 11 is the wrong one for `unlock`.

5. **MATERIAL. One Keystore key per policy cannot honor a per-line `android.strongBox`.** D6 generates a single key pair `exact.presence.<policy>` for every name with that policy (`llp/1133.010-local-auth.rfc.md:375-379`). D10 puts `android.strongBox` on the grant line, after the policy (`:516-522`), and a missing StrongBox refuses the write rather than generating elsewhere. Two names with `user-presence`, one of them `android.strongBox`, share one alias. The second line cannot change the key, and the first key cannot satisfy both lines. Invalidation has the same shape: one `KeyPermanentlyInvalidatedException` deletes every file sealed under that policy (`:388-390`), including names the user did not expect to lose.

   **Resolution.** Either generate one key per name (the alias includes the name; `strongBox` and invalidation stay per secret), or make `android.strongBox` a per-policy word and refuse at bake when two lines of the same policy disagree (`grant-policy-conflict`). Do not share an alias and also accept a per-line hardware word.

6. **MINOR. "No answer may carry a secret" is not a runner invariant, and "holds against a tampered process" is stronger than the platforms.** D5 says a kept answer never contains the value because LLP 1018 D5 forbids it (`llp/1133.010-local-auth.rfc.md:301`). LLP 1018 D5 (`llp/1018-durable-client-state.rfc.md:231-249`) is how Castle's data crate is written. The runner keeps whatever the source returns under `exact.kept.*`, and the host reads those bytes back into the next snapshot (`host/linux/src/system_support.rs:54-71`). Excord's `Session` is only `ready` and `signedIn` (`apps/excord/shapes.contract:188-190`), so this consumer is fine if it stays that way. The row should be a caller rule, checked for Excord in stage 0, not a platform guarantee. Separately, D2's "holds" cell (`llp/1133.010-local-auth.rfc.md:171`) is confidentiality of the wrapped bytes when the key is hardware-backed. It is not integrity: `set` uses the public key with no authentication, which Android documents as unrestricted ([`isUserAuthenticationRequired`](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec#isUserAuthenticationRequired())). It is not hardware on a software `securityLevel`, which is what the emulator reports. The simulator and emulator suites do not prove the Secure Enclave or the TEE.

   **Resolution.** Say the kept-answer row as an app obligation and assert Excord's session answer. Narrow the "holds" cell to hardware-backed at-rest confidentiality, and point the emulator note at that cell.

7. **MINOR. Stage 0 runs the wrong drives on the web.** §11 stage 0 drives §9's drives 1–7 on the web and on macOS (`llp/1133.010-local-auth.rfc.md:941-942`). Drives 1–6 tap a lock switch that D15 and drive 7 say the web does not have (`:719-723`, `:906-908`).

   **Resolution.** Drives 1–6 under the agent on macOS. Drive 7 on the web.

## New findings

1. **IN-DELTA, MATERIAL.** A failed `set` of a name that already has a locked value is specified to clear occupancy. D5 says a write the platform refuses is retried, "and occupancy reads absent until it lands" (`llp/1133.010-local-auth.rfc.md:413-415`). The previous item is still in the keychain or the presence file. The host's pending write still holds the new bytes (`host/apple/src/persistence.rs:33-37`). Occupancy `absent` makes `has` and `locked` false, so Excord's `null` path shows "Sign in again" on a transient keychain or Keystore error while the old token is still gated on disk. The next sign-in can then replace it.

   **Resolution.** A failed overwrite leaves occupancy as it was. The previous item stays readable with `unlock`. Occupancy becomes absent only when the platform reports the item gone, or when the first write of a name never lands. Drive: fail one locked `set`, assert `locked` stays true and `unlock` still returns the previous value, then let the retry land and assert the new value.

2. **IN-DELTA, MINOR.** D14's table says `store.protect` is not a request, and §7's tickets are `authenticate`, locked `unlock`, and `unprotect`. The sentence under the table says the three waiting operations return requests (`llp/1133.010-local-auth.rfc.md:809-817`). Following that sentence puts `protect` on the ticket path and adds a sheet the switch does not have.

   **Resolution.** `protect` is a host future: no 1069 request, no ticket, no sheet. Only `unlock` and `unprotect` return requests.

3. **IN-DELTA, MINOR.** A launch whose only secret is locked still has `opened_with_secrets` false, because that flag is "any non-kept byte in the snapshot" (`runner/src/store.rs:215`) and LLP 1027's placeholder swap keys off it (`runner/src/runner/settlement.rs:101-108`). D5 suppresses kept answers, and it makes `locked` and `unlock` device reads so those callers compile no value. A store reader that calls only `store.has` still has a compiled empty-store answer, which is the signed-out screen until data code runs. Excord's `loadSession` calls `store.locked`, so drive 2 does not catch this.

   **Resolution.** Locked occupancy counts for `opened_with_secrets`, or every store read of a locked name, including `has`, is a device read.

## New findings

1. **IN-DELTA, MATERIAL.** Deferring the boot move until after the module loads leaves the plain copy on disk while the host's ordinary store refresh loads it into the runner.

   r3 sets occupancy to `locked` at boot and does not delete the plain copy until the move runs, which is after the module has loaded (`llp/1133.010-local-auth.rfc.md:343-352`). If the move cannot be made, that copy stays for good. `activate_data` and `refresh_store` then call `KeptStore::snapshot`, which reads every plain secret and `adopt_store` merges those bytes into `Store` (`host/apple/src/activation.rs:82-125`). The read is `snapshot_parts`: every name from `secrets.names()`, with no presence exception (`host/apple/src/store.rs:603-612`). Android's boot sweep is the same shape (`host/linux/src/system_support.rs:47-52`). `refresh_snapshot` inserts whatever that read returns (`runner/src/store.rs:430-453`). A name missing from `secrets.names()` is not removed from `previous`, so deleting the keychain item later does not drop bytes the refresh already inserted.

   Those bytes are a granted secret, so the next logic call and the next web dispatch send them in the per-call snapshot (`logic/abi/src/lib.rs:121-126`, `js/web/src/lib.rs:224-238` and `:674-684`). A reload carries them (`runner/src/runner.rs:726`, `runner/src/runner/carry.rs:26-27`). D5 says a locked value is never in the runner's `Store`, a carry, or a per-call snapshot. For a move that cannot finish, this lasts the whole session, and `get` throwing does not matter once the snapshot has already copied the bytes out. The boot path sets occupancy to `locked` before the move, so step 4 will not run again and clear them.

   **Resolution.** Every plain-store read that feeds the runner omits a name whose occupancy is locked, including activation and refresh, for as long as the plain copy exists. `from_names` and `refresh_snapshot` drop bytes for a locked name even if a read contains them. The move may read the plain copy in the host, off that path, and when it finishes it removes any bytes a refresh already inserted. Drive: interrupt `protect` after the record, relaunch, let the activation store read run, and assert the per-call snapshot, the carry, and `state` contain no token bytes before the move and after a move that fails.

2. **IN-DELTA, MATERIAL.** Apple's locked `set` deletes the item and then adds the new one, which contradicts "a failed overwrite leaves the previous value readable."

   D6 says a locked `set` deletes the item and adds the new one so rotation does not prompt (`llp/1133.010-local-auth.rfc.md:487-489`). D5 says occupancy stays as it was and `unlock` still returns the previous value (`:436-440`). After a successful delete, the previous item is gone. The new bytes live only in the host's in-memory `pending_store_writes` (`host/apple/src/persistence.rs:33-37`). The journal records the name only (`runner/src/runner/commit.rs:265-271`). A crash between delete and add, or an `unlock` queued after the failed `set` and before the retry, loses the token. `unlock` then answers `null` and clears occupancy, which is the sign-in path, while a later retry may write the old token back. Drive 8 proves this only with an agent-store fault point that can fail without deleting (`llp/1133.010-local-auth.rfc.md:1098-1100`). The conformance suite does not require the real keychain to keep the previous value.

   **Resolution.** The new bytes are durable in the presence backend before the old bytes are destroyed. On Apple, update `kSecValueData` in place when that does not prompt. If it does, add a staging item, then delete the old one, and reconciliation keeps the staging item if the delete did not finish. The same order on Android: write the new file, then replace the old one. A crash in between still unlocks the old value. `pending_store_writes` is not that durable copy. Drive 8's failed-set check runs against the real keychain in the conformance suite.

3. **IN-DELTA, MATERIAL.** Excord's return lock is specified as `visibilityState` turning `visible`. In Contract that gate is already true at launch, so it runs the return path on a cold start.

   A task gate follows a state. It is not an event. The page is `visible` at launch, so `task returned when page.visibilityState == "visible"` runs at launch and again on every return (`docs/agent-pitfalls.md:262-273`, LLP 1092 D8). r3 dropped the one-minute delay and made that the whole trigger (`llp/1133.010-local-auth.rfc.md:1046-1056`). The launch path also sends `unlockSession` while `session.locked` (`:1039-1045`). Both queue: a cold start shows two sheets, or the return path's `authenticate` runs while the token is not in memory yet. Drive 2 expects one presence ticket (`:1071-1075`). The pitfall's latch, `wasHidden` then visible, misses a return when `hidden` and `visible` arrive with no clock step between them. Drive 5 is that script (`:1085-1088`).

   **Resolution.** Latch a hide, then arm the return lock only when `wasHidden` is set, and clear it in the action. Cold start stays `unlockSession` alone. Drive 5 steps the clock between `hidden` and `visible` so the latch can hear it. Drive 2 asserts a single presence ticket.

4. **IN-DELTA, MINOR.** D14 says the TypeScript declaration gains six store operations (`llp/1133.010-local-auth.rfc.md:843-847`). D1 lists five (`has`, `locked`, `unlock`, `protect`, `unprotect`, `:124-127`), and stage 0 still says five (`:1136`).

   **Resolution.** Name the five, and say `get` on a locked name throws rather than counting it as a sixth operation.
