The direction is sound, but r1 is not yet an implementable cost program. Its strongest ideas are removing redundant service work and avoiding the final compose copy where possible. Its main weaknesses are incomplete correctness contracts and predictions presented with more certainty than the evidence supports.

References below use the specified commits: `9d9f7eb248`, except G6b/G6c and the Windows carrier at `77ab0960ee`. I used only read operations and did not access the unavailable trace.

1. **A1 needs to define what a capture represents and preserve destination-dependent composition.**

   A1 changes D9’s promise: the parent says a presenting backend reads back its presented frame; the amendment instead renders another image. An offscreen replay can agree with tiny-skia while the drawable path has incorrect channel order, alpha, colour presentation, clipping or stale resources. That leaves the new presentation path outside the pixel comparison. The current Metal renderer requires an RGBA target, while presentation uses a separate BGRA pipeline, so this is a concrete distinction. *(Cost RFC §3 M3, L89–94; §7 A1, L164–165; parent D9, L504–529; `host/ink/src/device/metal.rs:481–495`; `device/metal/present.rs:194–218`.)*

   Specify whether a screenshot captures the last displayed frame or the scene at the current agent clock. For a screenshot midway through an animation, retain the chosen frame’s sampled transforms, content revisions and resources; replay must neither advance time nor silently settle motion. Q1’s “the agent waits on `clock settle` anyway” is false as a general contract: explicit clock seeks support intermediate captures. D9 must compare identical sampled state and separately qualify the actual drawable path. *(Cost RFC §6 Q1, L152–154; `host/linux/src/agent.rs:994–999,1091–1118`.)*

   Also retain the compose-target path for backdrop filters and blend modes: D2.5 requires destination sampling and explicitly says the swap-chain image cannot supply it. M3 should be a conditional fast path. Explain how drawable acquisition stays off the main thread while preserving D11’s handoff; the existing main-thread scene encode requires a known target before the worker acquires its drawable. *(Parent D2.5, L258–265; D11, L553–560; `device/metal/present.rs:274–305`.)*

2. **A2 starts from an incorrect account of existing retention and lacks the invalidation contract.**

   The kernel has per-node dirty flags and commit/layout receipts, not an exported per-retained-row content-change bit. The painter already accumulates those receipts, marks retained rows stale or suspect, skips valid row subtrees, and replaces image slots without rewalking the row. M6 therefore cannot claim that simply adding a bit eliminates a walk currently performed for every kept subtree. *(Cost RFC §2, L66; §3 M6, L110–114; `kernel/src/id.rs:55–82`, `txn.rs:50–87`, `layout.rs:50–65`; `host/linux/src/paint/rows.rs:175–230,433–466,526–578`.)*

   Distinguish three things:

   - Content changes require recording or updating the affected slot.
   - Position changes require fresh placement and outer clipping, without necessarily changing row content.
   - Resource arrivals and presentation changes can occur without an authored kernel mutation.

   Today, Ink rejects reuse after fractional device-pixel translation, and an existing test checks fractional scrolling against a fresh walk. A kernel bit alone cannot remove that restriction while preserving hinted text and coverage masks. *( `host/linux/src/ink/rows.rs:287–303`; `presenter/kept_rows_tests.rs:312–340`.)*

   M7 also needs a minimal buffer-lifetime design: row-local placement and clips, range allocation/reuse after GPU completion, and resource pinning for outstanding frames and captures. Otherwise persistent ranges either become stale while scrolling or still need rewriting. D4 already proposes per-draw offsets if copying proves expensive; build on that. *(Parent D4, L318–337.)* Measure validation, metadata replay and instance replay separately before predicting “new rows only” or “costs that element.”

3. **A4 must coalesce frame work without making application progress depend on frames.**

   “Inputs only mark dirty” and “one service pass per frame” are too broad. Timers, executor completions, image loads and nonvisual effects must progress when no frame is wanted, including while occluded. A timer due between refreshes must retain its deadline and ordering rather than wait for display work.

   The existing Mac service function explicitly advances expired timers to prevent a past `WaitUntil` deadline from spinning. Windows explicitly pumps nonvisual effects without presentation and retains separate timer, recovery and retirement deadlines. *(Cost RFC §3 M1, L84–86; §7 A4, L170–171; `host/apple-painted/src/window.rs:552–589,636–646`; Windows `window.rs:1246–1268,1312–1349`.)*

   Headless commands are another exception: they synchronously service work, and `clock settle` may drain multiple rounds. A large seek fires timers at their own due times and stops at hatch instants. Preserve those semantics explicitly. Define M1 as avoiding redundant polling during active presentation, with independent service turns for actual pending work and deadlines. *( `host/linux/src/agent/stdio.rs:27–69`; `agent.rs:1091–1141,1223–1269`.)*

4. **The trace supports optimization candidates, but not the stage-1 totals.**

   The §2 phases sum to approximately **43.1 ms/s**, consistent in magnitude with G4’s **43.83 ms/s** main-thread CPU. S1.4’s normal-run inclusive walk and finish totals also make a several-ms/s walk and roughly 3-ms/s encode plausible. That is a consistency check, not independent verification of the control’s exclusive attribution. The markers use elapsed `CACurrentMediaTime`; exclusive elapsed spans must not be silently treated as CPU counters. *(Cost RFC §2, L60–74; RESULTS S1.4, L1381–1402; G4, L2000; `device/apple.rs:215–227`.)*

   | Prediction | Assessment |
   |---|---|
   | **M1: save about 10 ms/s main** | Plausible hypothesis. Reducing 358 passes/s to roughly one tenth gives about **11.3 ms/s** removable service-span time, assuming comparable remaining passes. Required service turns reduce that ceiling. |
   | **M2: rest ≤0.4** | Reasonable goal; the recorded totals do not establish that unnecessary carrier timers own all the excess. |
   | **M3: GPU 1.2 → about 0.3 ms** | A credible experiment if the reported 1.0-ms copy pass is removable on this scene. The separate **3-ms/s CPU** and worker-wake predictions are not established by GPU duration or completion waits. |
   | **M4: a few ms/s CPU and removal of 340 MiB** | The memory claim contradicts the recorded attribution. The CPU claim confuses waiting with execution unless separately measured. |
   | **M5: one frame less input latency** | Unproven. S1.5 leaves presentation latency unexplained and identifies restart cases as candidates, not a demonstrated one-frame remedy. |

   M4 is the clearest numerical error. S1.4 records only **4.77 MiB** in staging buffers, explicitly says the **339.8 MiB** owned-unmapped charge is not explained by staging or drawables, and still sees a **335.469 MiB** transient with images disabled. Egui’s similar transient does not establish a common upload cause. Moreover, **37.542 ms of staging waits over ten seconds** is worker elapsed wait time, not 3.75 ms/s of removable CPU. *(RESULTS S1.4, L1393–1399,1442–1476; cost RFC §1, L46–47; M4, L95–98.)*

   Consequently, neither **86 → 60 process** nor **44 → 25–30 main** after stage 1 has a complete savings budget. Windows needs its own attribution after G6c; the Mac phase costs cannot establish its remaining savings. *(Cost RFC L105–106; RESULTS G6c, L2688–2689.)*

5. **Correct the scoreboard and distinguish goals from measured floors.**

   The Windows baseline mixes revisions. G6c reports **182.25 ms** retained-cache startup and **1.55 ms/s** median rest CPU. The draft uses G6’s **175.98 ms** startup and cites its **4.66 ms/s** rest result while describing the baseline as G6c. G6c did not repeat the reset-driver series; label the **249 ms** figure historical. *(Cost RFC §1, L25–44; M2, L87–88; RESULTS G6c, L2690–2691,2717–2741.)*

   Other target qualifications matter:

   - Windows **60 ms/s** is still about **2.4× egui’s 24.91**, so it does not satisfy the summary’s “at or under egui” objective.
   - Mac **60 process / 28 main** is below egui’s measured **66.84 / 31.33**. Retention might earn that result; these whole-app comparisons do not establish an architectural floor.
   - Windows CPU accounting has **15.625-ms** granularity. A ten-second rest cannot resolve a **0.4-ms/s** threshold reliably.
   - M10’s “150–180 ms first screen” does not describe the Mac scoreboard’s **352 ms** complete-screen milestone. Keep phase sums tied to the same app, cache condition and endpoint.

   *(Cost RFC L19,49–56,129–131; RESULTS G4, L1997–2001; G6, L2261–2270.)*

   Preserve the benchmark’s limitations beside these goals: different text metrics, scrolling distances and presentation policies make these useful application comparisons, not isolated renderer rankings. *(RESULTS G4, L2088–2134.)*

6. **A5 turns useful measurement into an excessive landing tax and weakens the original gate.**

   Four Mac arms plus three Windows arms, repeated fling/rest and startup series, quiet-machine qualification and two-family review for every landing is substantial ceremony. The timed fling/rest phases alone exceed eleven minutes across the two machines. Making that blocking conflicts with the repository’s under-minute blocking rule. Requiring every landing to meet every end-program target also prevents an independently useful M1 fix from landing. *(Cost RFC §3, L78–80; §4, L137–142; A5, L172–174; `rules/RULES.md`, “Loop shape”.)*

   Use paired before/after measurements for affected paths, relevant correctness checks, and milestone or asynchronous full comparisons. Define targets as program milestones, with regression assessment against measured spread.

   Keep D15’s internal controls and unresolved obligations. G4 explicitly cannot decide improved-vello versus wgpu-Ink admission. Competitor application scores cannot replace the platform qualification or wgpu evidence needed for Linux and Android. *(Parent D15, L632–681; RESULTS G4, L2131–2134.)*

7. **Investigate the missing costs before declaring them unavoidable.**

   The **~15 ms/s unattributed main-thread remainder** exceeds the proposed encode savings and is comparable to the main-thread improvement target. Attribute it before calling most remaining cost the app model’s price. Likewise, separate shaping misses, width-layout work and glyph rasterization: **480 layouts/s at 1 µs is 0.48 ms/s**, not evidence about shaping cost. Existing text counters already distinguish shaped-source builds, cache hits and synchronous shape/layout miss time. DirectWrite rasterization will not itself remove Parley shaping work. *(Cost RFC §2, L68–70; §5, L146–148; `host/linux/src/text.rs:569–589`.)*

   M8 should remain optional. The shader already guards rounded and coverage clips by flags, so “every pixel runs two rounded clips and a coverage clip” overstates the work. A specialized pipeline might help, but the one-third-to-one-half prediction needs an A/B measurement. Define Q3’s denominator: 0.3 ms is already only 3.6% of a 120-Hz frame budget. *(Cost RFC M8, L119–124; Q3, L157–158; `host/ink/shaders/ink.wgsl:388–402`.)*

8. **Separate existing fixes from amendments and retain the parent’s platform obligations.**

   M1/M2, upload-copy improvements that preserve retirement, and display-link tuning can proceed as bounded fixes under existing authority. They need not wait for approval of the entire campaign. M3 changes the capture/presentation contract; A2 changes retained-state machinery. Those deserve the focused design text.

   Move the already-dated Metal boot obligation ahead of discretionary stages: D15 requires it by **2026-11-04 or carrier enablement**, whichever comes first. Keep M9 tied to D3’s advance audit and conditional ClearType rules. Give Linux/Android their existing carrier and wgpu qualification work rather than treating Mac improvements as transferable proof. M11’s “replacing vello … as D15 decided” also conflicts with D12/D13’s explicit opt-in and retained-backend ruling. *(Parent D3, L292–314; D12–D13, L564–609; D15, L667–681; cost RFC L128–133.)*

   Leaving web implementation unscheduled is consistent with the parent. Preserve its WebGL2-compatible buffer/shader constraints through M7/M8. Put G5’s baseline before the changes it is meant to evaluate, particularly M3, and assess power rather than inferring battery savings from GPU duration alone. *(Parent D6.1, L401–408; §3, L701; cost RFC §4, L139–141.)*

The smallest revision is to define A1/A2/A4’s correctness contracts; reconcile the scoreboard and express unearned savings as hypotheses, removing M4’s unsupported memory attribution; replace A5 with proportionate landing measurements while preserving D15; and correct the ordering and platform scope. That would let the straightforward fixes proceed without requiring a larger redesign.
