**1. Verdict: NOT READY — the comparison is worthwhile, but r1’s measurement protocol, workload equivalence, and aggregate scoring could produce misleading winners.**

**2. Direction — confidence: 94/100**

Conduit, a rich live feed, and an unchanged upstream js-framework-benchmark entry are a good combination. They exercise application loading and navigation, sustained scrolling and updates, and isolated DOM operations. No additional app is essential for the first round.

The five browser/device legs are sensible eventual coverage. Real iPhone Safari and mid-range Android Chrome should enter the feasibility stage: they answer the stated primary questions and contain the largest instrumentation risks.

The field is too large for the first credible result. Start with Exact, vanilla, React, one compiled client framework, Next.js, Qwik, one server-driven stack, and the requested Expo baseline. Establish measurement validity and credible implementations before expanding. Forty framework names do not compensate for uncertain endpoints or uneven implementations.

Keep three conclusions separate: **these implementations’ user experience**, **framework/runtime costs**, and **agent authoring costs**. The proposed experiment cannot automatically attribute differences in the first to either of the others.

**3. Major oversights, ordered by severity**

1. **The early-tap experiment contaminates loading and cannot reliably classify its own outcomes.**  
   Input ends LCP candidate collection; repeated inputs also affect CLS eligibility, activation, network requests, and the proposed quiet window. Toggling every 50 ms can cancel visible changes or overlap requests, making “lost” versus “deferred” ambiguous. Exact’s anonymous favourite is also a registration link, not a mutation.

   **Resolve:** use separate untouched-load, early-input, and steady-state runs. For early input, deliver one action per fresh navigation at controlled offsets, record the actual input timestamp, and observe a uniquely defined outcome until a declared timeout. Test native link navigation separately from an action requiring application code. Specify authentication state.

2. **The proposed measurements do not establish “paint showing the change” or “frames presented.”**  
   Event Timing measures an interaction through its next rendering update; it does not wait for an asynchronous article fetch or server-driven update. An optimistic favourite and a server-confirmed favourite can therefore receive superficially comparable timings while measuring different completion states. `requestAnimationFrame` runs before paint. DOM hit-testing cannot establish that a compositor frame displayed the expected content, especially for canvas renderers.

   **Resolve:** distinguish input responsiveness, visible feedback, and completed application outcome. Validate outcome timing against traces or recorded frames on representative arms. Label rAF intervals as such unless independently validated as presentation measurements. Measure scrolling progress and visible content together; a smooth stationary or stale viewport must not win.

3. **“Same app” is insufficiently specified, including a material exception for Exact.**  
   Exact’s bounded feed exposes a 200-row scrolling window, whereas competitors may maintain a full 10,000-row extent. That changes scrollbar behaviour, jumps, boundary work, and potentially the traversal used for memory measurements. Conduit implementations can also differ in page size, caching, optimistic updates, rendered content, and architecture despite implementing the same API. Historical community implementations are not automatically representative of current framework claims.

   **Resolve:** define observable equivalence before porting: data volume, pagination, traversal, scroll extent, mutation feedback, cache behaviour, and required rendered content. Either require the full-list contract or offer the same bounded-window contract to every arm and label it separately. Give competitors the same opportunity for expert review and tuning as Exact.

4. **The primary phone leg and several metric columns lack a demonstrated collection path.**  
   The named bake-off driver is simulator-only. Lighthouse cannot supply an iPhone Safari score. A network proxy cannot implement Safari CPU slowdown. PerformanceObserver entry support must be established for each pinned engine, including the asserted Firefox Long Tasks support. Several memory methods also measure different quantities.

   **Resolve:** make stage 0 include one physical iPhone and one Android device. Produce a capability matrix with an actual collection method, endpoint, resolution, and limitations for every required metric. Unsupported measurements remain absent; they must not be replaced by differently defined values under the same column. Establish how cold browser state is obtained on phones.

5. **The proposed indices are mathematically undefined in ordinary successful runs and unfair with missing data.**  
   Best-arm ratios fail when the best CLS, TBT, blank count, lost-tap rate, or late-frame count is zero. A geometric mean gives metrics implicit equal logarithmic weights; grouping introduces another weighting choice. Omitting unavailable metrics separately for each arm produces scores over different questions. Reporting the number included does not restore comparability.

   **Resolve:** publish raw measurements and uncertainty first. Remove the overall sort index. If group summaries remain, use a predeclared common metric set, correct directionality, and an explicit treatment of zeros and missingness. Do not invent an epsilon after seeing results.

6. **Serving topology and cache state can dominate the alleged framework comparison.**  
   The relationship between §5’s network profiles and D8’s additional round-trip knob is unclear. A client→origin hop and an origin→API hop are different costs. Cached SSR, uncached SSR, static generation, and client fetching require explicit scenarios. A proxy that buffers responses would erase streaming and distort SSE architectures. Browser-only CPU accounting also hides work transferred to servers.

   **Resolve:** specify the network topology and total latency on each edge, preserve streaming/WebSockets/SSE, and reset mutable fixtures between runs. Declare browser, API, and render-cache states and content-freshness requirements. Report backend work alongside client costs for server-driven arms. Measure TTFB for static arms too; it includes network effects.

7. **The statistical and instrumentation controls are too weak for the intended rankings.**  
   Twenty toggles cannot establish a useful p99. Hundreds of keys within one session are not hundreds of independent cold-start trials. Rotating order helps with drift but does not establish uncertainty or a meaningful tie. Identical probe source also does not imply identical overhead: layout reads and DOM sampling can perturb architectures differently.

   **Resolve:** choose independent-run counts from a pilot, predeclare practical effect sizes and interval-based comparisons, and retain failures and timeouts. Control refresh rate, thermal state, power mode, and cache state. Calibrate instrumented versus minimally instrumented runs. Replace unsupported tail claims with maxima or collect enough independent observations.

8. **The first round combines a large engineering program with an inadequately controlled authoring experiment.**  
   The 25 Tier 1 entries imply roughly 75 app implementations with two feed variants, before Tier 2, baselines, and templates. Five legs, network conditions, repetitions, and ten-minute soaks multiply that substantially. Alternating builders across frameworks confounds framework with builder; a third model’s review does not establish framework expertise. Existing Exact apps also have accumulated tuning that fresh ports do not.

   **Resolve:** name an owner, budget, time limit, and bounded initial field. Secure knowledgeable review for the principal competitors. For authoring claims, cross builders with frameworks using repeated, equally budgeted tasks, including fresh Exact builds. Compare token counts within a model and dollars across models, as LLP 1087 already requires.

**4. Errors against repository evidence or platform contracts**

- **§4.2’s anonymous favourite procedure does not perform the described mutation.** Exact renders the signed-out heart as an ordinary `/register` link, explicitly so it works before the runtime loads. Its earlier benchmark deliberately used sign-in submission because anonymous home-page controls were links. See [the actual control](/Users/ccheever/projects/exact2/apps/realworld/app.contract:478) and [LLP 1071’s measurement procedure](/Users/ccheever/projects/exact2/llp/1071-exact2-web-target.rfc.md:576).

- **§6 incorrectly presents the bake-off driver as reusable for a physical iPhone without new device support.** It enumerates `simctl` devices and refuses an identifier absent from that simulator list. See [drive.mjs](/Users/ccheever/projects/exact2/bench/bakeoff/drive.mjs:67).

- **§2.2’s distinction between the whole-feed arm and the JS target is misleading.** Both existing web arms use the JS target; Rust application data still crosses a wasm seam. The bounded arm is an application/data-contract improvement, not evidence that the other arm used the old wasm target. Its reduced scrolling contract is documented explicitly. See [Dioxus benchmark description](/Users/ccheever/projects/exact2/bench/dioxus/README.md:3) and [bounded-arm tradeoff](/Users/ccheever/projects/exact2/bench/dioxus/exact-bounded/README.md:16).

- **§11 overstates what bounding resolved.** The recorded bounded results still show Exact using 4.1 MB JS heap versus 1.8 MB and taking 24 ms versus 16 ms for taps; they allow up to one late frame per run. “Lost … until the bounded answer landed” and “no late frames at any speed” do not accurately summarize that result. See [the bounded standings](/Users/ccheever/projects/exact2/bench/dioxus/README.md:126).

- **§4.3 misstates both its existing implementation and the standard metric.** The existing harness observes `event`, filters click/pointerup entries, and checks the eventual count; it neither observes `first-input` nor calculates INP. INP groups events into interactions and uses an interaction-count-dependent outlier rule, rather than simply taking p98 of observed events. Event durations are quantized, and a 16 ms threshold omits faster ordinary entries. See [the observer](/Users/ccheever/projects/exact2/bench/dioxus/web/bench.mjs:55), [the count check](/Users/ccheever/projects/exact2/bench/dioxus/web/bench.mjs:166), the [Event Timing specification](https://w3c.github.io/event-timing/), and [INP’s definition](https://web.dev/articles/inp).

- **§6/§9 promise a Lighthouse result on unsupported legs and overclaim Core Web Vitals assessment.** Lighthouse’s browser measurement path is Chromium, not Safari. A scripted session can report lab observations against the familiar thresholds; it cannot establish a field Core Web Vitals pass, which uses the 75th percentile of visits. The listed thresholds and Lighthouse weights are not the problem. See [Lighthouse documentation](https://developer.chrome.com/docs/lighthouse/overview/) and [Web Vitals assessment](https://web.dev/articles/vitals).

- **§4.2’s “React drops the event until hydrated” is not generally true.** React supports selective hydration and event handling/replay mechanisms once its hydration machinery is installed. Input before that machinery loads is a distinct case. The benchmark must distinguish these periods. See the React team’s [Suspense SSR architecture explanation](https://github.com/reactwg/react-18/discussions/37).

- **§4.5 conflates incompatible memory quantities.** `measureUserAgentSpecificMemory()` estimates broader application memory, not just JS heap. The checkout’s CDP `Memory` interface exposes counters and allocation sampling, not the promised renderer-private-footprint measurement. Ordinary `ps` RSS is also not private footprint. See the [memory-measurement specification](https://wicg.github.io/performance-measure-memory/) and [the local protocol declarations](/Users/ccheever/projects/exact2/node_modules/playwright-core/types/protocol.d.ts:10451).

Platform references above identify API contracts; no online audit of current framework releases or browser compatibility was performed.

**6. Strongest alternative and deciding measurement**

The strongest alternative is **upstream-first comparison plus a small application study**: use unchanged js-framework-benchmark for the broad framework field, then compare Exact against two or three expert-reviewed implementations of Conduit and the live feed on real phones. Expand only where application behaviour exposes something the upstream results miss.

The deciding measurement is **p95 input-to-correct-visible-update while the live feed scrolls on the mid-range Android phone**, comparing Exact with the strongest matched competitor under a fixed network condition.

A reproducible ranking reversal or substantial actionable loss absent from the upstream results would justify a larger application shootout. If the small study explains Exact’s losses and the upstream results predict them adequately, the forty-framework matrix has little additional value.
