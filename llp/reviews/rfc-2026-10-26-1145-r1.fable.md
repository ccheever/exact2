**LLP 1145 review — Fable seat**

Four fundamental concerns, most serious first. I checked each against the tree.

**1. D1 fixes the decode queue, but for Excord's images the wait is almost certainly the fetch, which D1 cannot reach.**
On Apple a remote image's bytes are downloaded before any raster-core demand exists: `RasterLoader.inspectOne` (`host/apple/Sources/ExactKit/RasterLoader.swift:187-200`) fires `RasterInput.fetch` on URLSession's queue, and the `Demand` (with its priority) is only submitted after the downloaded body's header is read (`:870-885`). That stage picks sources by lowest id (`.min { $0.id < $1.id }`), has no priority, and is outside `host/raster` entirely. Meanwhile the decode side is small and fast: two workers, 64 pending jobs (`host/raster/src/types.rs:6,10`), and Excord's sources are already CDN-resized to their box (`apps/excord/shapes.contract:44-47`; avatars 16-40 pt). Decodes are milliseconds; a CDN round trip is 50-300 ms or more; the mount lead is one viewport plus a quarter second of travel. So re-ranking the decode queue through "one new export of the raster core" moves little, and the plan ("D4 first, so the rest is measured") contradicts the document deciding D1 before D4 has run. Instead: do D4 first in earnest (fetch start, bytes arrived, decoded, shown), run it on Excord, then choose. If the fetch dominates, the levers are download priority from the same rank (`URLSessionTask.priority`) and warming bytes for rows the data window already holds (a page's avatar and thumbnail URLs are known when the page arrives, long before mount); no mount-time ordering can beat a fling's viewport-per-quarter-second. If decode re-ranking does prove needed, it needs no new export: `RasterSession::request` with the same view and key replaces the binding's demand in place (`host/raster/src/policy.rs:538-543`) and `next_decode` reads priority from the bindings (`:314-323`), so the loader can re-request on `scrolled`.

**2. D4 as designed cannot see the images that were late during a fling.**
`state.raster.images` is the loader's live `interests` (`RasterLoader.swift:1111`), and `cancel` removes an interest when its row retires (`:588-595`). The rows that showed an empty box and scrolled past are exactly the ones gone by the time the agent reads `state`, so after a fling the timestamps answer nothing about it; the "nobody can see when an image arrived" problem survives for the case the goal names. Instead: a counter and histogram kept across retirements in the loader's diagnostics (images whose box was on screen before pixels landed, how late in ms, encoded bytes, fetch versus decode wait), printed by LLP 1144 D1's fling benchmark beside late frames, so an app's criterion can be "no image shown late during the fling". The per-node `image: {state, ms}` on `tree`/`layout` is fine for a settled screen but is the smaller half.

**3. Several of §1's web facts do not hold, and they carry D2 and half of D4's web case.**
The JS target already emits `decoding="async"` on every `<img>`, with a test citing LLP 1145 D2 (`host/web-js/src/rows.rs:1004-1008`, `:1082-1085`). The web screenshot already waits up to 3 s for incomplete images in the viewport and reports `imagesPending` (`scripts/agent.mjs:491-504`), so "an agent's screenshot can show an empty box a person never sees" is not the situation; only `clock` differs from Apple's (`Agent.swift:1019-1026`). And `width`/`height` attributes change nothing when CSS sizes both axes, which every Excord image does (`transcript.contract:110,157,354`; `members.contract:22`); where the author wrote one axis, the attributes cannot supply the picture's ratio, which is the only thing that would stop the shift. What remains of D2 is nothing; what remains of D4's web half is the `clock` wait and the timings.

**4. D5's recipe promises a distinction the app has no fact for.**
"How to keep a cached image from fading" needs the app to tell a cache hit from a slow arrival, but `load=` carries no payload (LLP 1011 §: "with no payload") and fires at delivery for a cached picture too, including a rebound recycled row. Either `load` carries the arrival's ms (a schema change the RFC does not propose) or the recipe cannot be written as described. Decide which before promising the document; otherwise §3's built-in opt-in fade is the honest next step, not a fallback.

Not raised as fundamental: D3 is sound and small, though note the runner's edges today come from the fixed one-viewport window (`runner/src/instance/collection/index.rs:537-544`, `mod.rs:809-818`) and Excord's own 15-row `scrolled` threshold is only slightly wider, so "Excord's hand-paging can then go" holds only with a margin of several viewports, and at fling speed no in-flight page arrives in time regardless; the stall-then-jump needs the list to keep an estimated extent past the loaded rows, which is a different change.
