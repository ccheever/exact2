## Should-fix

**The memory stop sees the direct child's RSS only.** `scripts/tamber-isolate.mjs:57-58` and the cargo spawn at `:22-27`.

`ps -o rss= -p <child.pid>` does not include grandchildren. A waiting shell stayed at 2.4 MiB while a child it had spawned climbed past 490 MiB. The fallback that runs when `target/debug/contract` is missing is `cargo run`: `ps` is watching `cargo`, and `rustc` and `contract` are grandchildren. On Linux, `ulimit -v` is inherited across `exec`, so that tree is still capped. On macOS there is no such cap. The 10 s timer still kills the group (`process.kill(-pid, 'SIGKILL')` did stop a background `sleep` in the same group), so this is up to 10 s of unbounded allocate, which is enough to push the machine into swap and have the OS kill the shared server.

The same check fails open when `ps` fails or is slow: `if (!e && Number(rss) > rssKb)`. A failed or delayed `ps` skips the memory stop until the wall clock. Samples are every 50 ms and do not wait for the previous `ps`. On this machine a tight touched allocator grew about 1 GiB of RSS per sample (793 MiB, then 1755 MiB). Crossing 1 GiB is observed a sample later, already near 2 GiB, and later if `ps` is late.

Fix: sum RSS for the process group (`ps -g` the leader), pass `execFile` a short timeout, and if `ps` errors twice in a row call the same stop as a memory breach. Keep the Linux `ulimit` as the hard backstop.

**The parent copies the child's output with no cap.** `scripts/tamber-isolate.mjs:60-61` and `:68-70`.

`out` and `err` append every chunk. A child that wrote 2 MiB of stderr with no newline came back as a 2,097,211-byte error string, and the parent RSS rose by tens of megabytes while the child itself stayed small. That string is the HTTP body (`scripts/tamber-server.mjs:599-600`). A child under the RSS cap can grow the shared process for the whole 10 s. A plan that exits under the cap is then parsed and, when it contains at least one op, stored in the held proposal (`:941`, `review` includes `unmapped`) for 15 minutes, up to 64 holds (`:108`).

Fix: once `out` or `err` passes a few megabytes (the propose line is already limited to 1 MiB), stop the group, drop the buffers, and return 413. Slice any stderr kept in the message to a short suffix.

**The design is read in the shared process before the watchdog exists.** `scripts/tamber-isolate.mjs:44` and `:74`.

`readFileSync` and the later `JSON.stringify` run on the server event loop, so the 10 s timer cannot fire during them, and there is no size check. The serve itself refuses a design reached by a link and a design outside the app (`contract/cli/src/tamber_serve.rs:258-266`, `:288-308`). This read follows a symlink and accepts any size. Kept baselines are read in the child (`contract/cli/src/tamber_import.rs:36`, `contract/cli/src/tamber_export.rs:160-164`), which is the right place, but every `*.json` beside the design is loaded with no total cap. A symlink directory is followed by `read_dir`.

Any read error is treated as "no design": the child plans against `tamber app` and `digest` is null, so `importHeld` holds with no file guard (`scripts/tamber-server.mjs:1112`). A design that exists but could not be read, or that appears during the plan, is proposed with the snapshot check skipped.

Fix: read a plain file, refuse a symlink and anything outside the app, and cap the bytes (a few megabytes). On `ENOENT`, plan against the empty design and have `propose` require the file to still be absent. On any other read error, return 503 and do not plan. Cap the sum of kept files inside the child.

**One client's imports can occupy the only queue for as long as they keep sending.** `scripts/tamber-isolate.mjs:31-39`, `scripts/tamber-server.mjs:1106-1113`.

The queue is one global chain. Each plan runs up to 10 s. A hold that conflicts retries while `tries < 2`, so one call plans at most three times (about 30 s) and only when `held.error.conflict` is set. A 413 or 503 does not retry. Nothing limits how many imports sit on the chain, and each queued call keeps its body (up to about 1 MiB). Other methods are not on this chain. They do stall while the event loop is inside the uncapped design read or the output append.

Fix: cap the queue (a small depth per server, and per client) and answer 429 past it.

**The local CLI still plans in an unwatched process.** `scripts/tamber-server.mjs:1455-1456`.

`importTheme` runs `cargo … contract tamber import` with `spawnSync` and a 64 MiB stdout buffer, then posts `propose`. That is the `bun exact.mjs tamber import` path. The shared server only receives the ops, and the body limit still applies, but the plan itself has neither the RSS stop nor the 10 s stop.

Fix: run that plan through `planAlone`.

## Nit

**The long-lived serve can still plan a source.** `contract/cli/src/tamber_serve.rs:642-646`. The wire never sends one: `import-plan` is not in `METHODS`, and the only `ask` of it is `marks` (`scripts/tamber-server.mjs:995`). Those ops are the held proposal's operations (a subset when `items` is set), read by `parse_ops` as the op schema. A client `propose` does not set `reimport`, so it is not marked. Refuse `source`, `sources`, and `baseline` on the serve's `import-plan` and accept only `marks`, so a later caller cannot put a document back in that process.

**Group kill has no pid guard.** `scripts/tamber-isolate.mjs:52`. The serve's own shutdown refuses pid 0 and 1 (`scripts/tamber-server.mjs:1131`) because `kill(-pid)` would hit this process group or every process this user may signal. Use the same guard. Ignore an in-flight `ps` callback after `close`: `clearInterval` does not cancel it, and a late callback can `SIGKILL` a recycled pid.

**`QUEUE.md:3` overstates where the leftover cost sits.** `marks` still runs in the shared serve. The input is the ops already accepted under the 1 MiB line, so it is not the document blow-up. The CSS, DTCG, and re-import expanders do run only in the child.

## What holds

The wire path builds the child request in `importHeld` and does not pass `source` or `baseline` to `ask`. `recognised` is the server's list of export digests. Linux `ulimit -v` uses `1.5 × 1 GiB` in KiB on the system allocator (this binary does not use jemalloc). That is a virtual-memory ceiling a little above the RSS target, and it also stops a one-sample overshoot. The design path is not interpolated: `sh -c 'ulimit -v … && exec "$0" "$@"'` takes the binary and the path as later argv, so a path with spaces or metacharacters is one argument.

A stop clears the timer and the interval and resolves the promise, which advances the queue. Checked here: a child that exits immediately answers 413 in a few milliseconds; a child that closes both pipes and sleeps still answers 503 at the deadline; a shell over `rssKb: 1` answers 413. Spawn failure emits `close` as well as `error`, so a missing binary does not stick the chain. HTTP keeps 413 and 503 (`reply.status`); a planner `{error}` with no status is 400, the same as the serve's other errors.

`bun test scripts/tamber-isolate.test.mjs -t 'past its time|one at a time'` — 2 pass. The real-planner test was not run (no `target/debug/contract` here). `cargo test -q -p exact-tamber --test it` was not run.

## Tests

The suite shows that a stub child is ordered, and that this wrapper's timer and `ps` paths return 503 and 413. It does not show the claims that matter if the isolation is wrong:

- `ps` on a grandchild, or on `cargo`
- `ps` failing, slow, or returning after exit
- a stdout or stderr cap, and a design read cap
- the process group dying, rather than only the leader's pipes closing
- 413 and 503 on the HTTP response
- a digest conflict retrying at most three times, and a 413 not retrying
- a read error refusing the hold instead of skipping the digest

The memory test sets `rssKb: 1` against a shell that is already larger than that, so it passes even if `ps` is watching a process that is not the allocator.
