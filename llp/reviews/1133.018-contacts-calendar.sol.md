The text below is the reviewer's final message, unedited; dispositions follow it.

---

1. **MATERIAL** — **D3, lines 310–311; D6, lines 433–459:** Native result order conflicts with stateless key pagination. Apple documents that EventKit results need not be chronological and recommends explicitly sorting them. The RFC forbids sorting but requires continuation after the last sort key and id; EventKit supplies no corresponding ordered-continuation contract. A traversal can therefore skip or repeat occurrences. Decide a deterministic occurrence order and permit the scanning/sorting needed to produce it. Also distinguish bounded replies and retained memory from bounded native fetch work. [Apple’s retrieval contract](https://developer.apple.com/documentation/eventkit/retrieving-events-and-reminders)

2. **MATERIAL** — **D8, lines 558–563:** Marking the answer that calls a never-kept name does not establish the stated privacy guarantee. Suppose resource A starts a cached `queryContacts()` promise and resource B awaits that same promise. Only A calls the binding; B can return the contacts and become eligible for persistence through an unrelated storage read. The inherited async-context helper restores B’s identity, but carries no provenance from A’s result; `keep_answer` persists eligible values and identifying arguments (`runner/src/runner/kept.rs:322`). Decide how never-kept status crosses shared promises, cached results and resource inputs—or choose an explicit conservative policy. More `await` depth testing alone does not cover this leak.

3. **MATERIAL** — **D2, line 229; D3, line 306; D15, line 938:** Floating timed writes have no defined Android behavior. The public model promises that `timeZone: none` means floating time. Google requires `EVENT_TIMEZONE` for direct inserts; the insert intent supplies a default zone instead. Substituting the current device zone changes floating-time semantics when the person travels. Decide whether Android refuses these writes/editor requests or performs an explicitly declared conversion. The omitted-zone default does not resolve an explicitly floating event. [Google’s insertion requirements](https://developer.android.com/identity/providers/calendar-provider#add-events)

4. **MINOR** — **§10, lines 994–1003; §11, lines 1070–1091; §14, lines 1144–1153:** The web acceptance plan contradicts target availability. Stage 0 requires drives 1–6 on the web, including enabling the calendar-store switch. But the consumer hides that switch when `available` is false, which the web target and drive 7 require. Inherited geolocation admission preserves target restrictions under substitution. Decide whether fixtures deliberately simulate unavailable capabilities, explicitly amending that rule, or run the store drives on capable targets and retain the web’s absence drive.

VERDICT: NOT READY

The explicit access-upgrade send, app-wide persistence policy, Android access reporting and restrictions on tool-origin writes fit the inherited architecture. The remaining concerns are:

1. **IN-DELTA · MATERIAL — D11, lines 769–775; D13, lines 967–971; §10, line 1102: permission-wide ordering contradicts the access requested by a save.**

   With both calendar grant lines, production `saveEvent` initially requests **write-only** access. The new substitute rule selects the widest access permitted by those lines: **full**. Consequently, the simulated first save enables reads immediately, while production requires `requestFullCalendarAccess`.

   This is structural in the cited mechanism: `runner/src/runner/modules.rs:899–905` sets the permission globally, and lines 1070–1099 select access from the app’s complete grant set without the requesting operation.

   **Decision needed:** carry the operation’s requested access through the permission decision. An initial save requests write-only; a read or explicit raise requests full. An independently forced `prefer permission.calendar granted` can retain a widest-access default.

2. **IN-DELTA · MATERIAL — D6, lines 494–506, against D3, line 329: deleted-contact continuation changes comparison order.**

   D3 orders Apple contacts by the person’s sort setting. When the cursor contact disappears, D6 instead resumes using a “formatter sort string.” Apple exposes [independent sort-order and display-order settings](https://support.apple.com/en-us/111793); a formatted display name is not an order-preserving cursor key.

   For example, with family-name sorting and first-name-first display, a one-contact page contains “Zoe Able.” Delete it. “Amy Baker” and “Bea Clark” follow it in native order, but neither formatted name follows “Zoe Able”; the specified fallback can skip the remainder.

   **Decision needed:** preserve a continuation key comparable in the same native order after deletion, or explicitly invalidate the cursor and require restarting. The precise key encoding belongs to implementation.

3. **PRE-EXISTING · MATERIAL — D2, line 240; D3, line 333: the public type cannot distinguish floating time from the default-zone request.**

   D2 assigns `timeZone: none` the meaning **floating**; D3 assigns omission **device zone**. But the shared `option<string>` field and inherited bindings collapse those cases. Rust’s `Option::None` encodes omission (`data/src/modules.rs:89–97`); Contract records require every field (`contract/types/src/records.rs:98–108`); and the runner recursively removes explicit JSON nulls (`runner/src/runner/modules/bound.rs:281–286`).

   Thus an explicitly floating event reaches the implementation indistinguishably from the device-zone default. Preserving JSON null alone would not supply the missing distinction in the Contract and Rust types.

   **Decision needed:** either give `none` one consistent meaning and revise the default promise, or introduce a representable default/floating/named-zone distinction across callers and transport.
