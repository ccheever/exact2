I'll check publication, the layout-equality mutator, and the LLP/QUEUE text, then write the findings.`d8a4a0ebf` gets the containing-block model, the shared absolute solver, and the in-flow root rule right for the cases LLP 1074 actually pins to Chrome: static position, auto margins on the inline axis, the block-axis negative-margin split, and a static root as the containing block of an absolute with no positioned ancestor. The incremental hoist and two host rules do not survive a second layout or a real paint. A `display: none` ancestor leaves a stale static-position record, and the next layout places that absolute again; Apple reads a flex or grid item's `z-index` before the view has a parent, so the new static default stores 0. 1. **HIGH.** A hoisted absolute that was once visible is laid out again after an ancestor becomes `display: none`, so an incremental layout disagrees with a fresh one. `static_positions` is written in `set_static_position` (`vendor/taffy/src/tree/taffy_tree.rs:503`) and dropped only in `clear` (`:767`) and `remove` (`:794`). `compute_hidden_layout` (`vendor/taffy/src/compute/mod.rs:310-321`) zeros the subtree and does not touch that map. `hoisted_absolute` (`taffy_tree.rs:512-525`) then returns the stale record and the origin sum; it never looks at `display`. Block and flex run `place_hoisted` and only then the hidden pass (`vendor/taffy/src/compute/block.rs:1649` then `:764`; `vendor/taffy/src/compute/flexbox.rs:484` then `:490`). Grid zeros a direct hidden child first (`vendor/taffy/src/compute/grid/mod.rs:670`) and still calls `place_hoisted` afterwards (`:823`).

   Concrete tree, laid out once while `gone` is shown, then again after `gone` is `display: none`: `cb` (`position: relative`) → `mid` (static, shown) → `gone` → `abs` (`position: absolute`, `width`/`height` 20, `left`/`top` auto). `mid`'s hidden pass zeros `abs`. `cb`'s `place_hoisted` then runs and writes a real parent-relative frame from the old static position, and unions that box into `cb`'s scrollable overflow. A tree built with `gone` already `display: none` never stored a static position, `hoisted_absolute` returns `None`, and `abs` stays 0×0. On a grid `cb` the same resurrection happens when `gone` is a direct child. Publication copies that layout into the frame (`kernel/src/layout/publication.rs:65-97`) and sets `HIDDEN` only for a node's own `display`, so `abs` is published. AppKit does not set `isHidden` from `display: none` (`host/apple/Sources/ExactKit/Mac/NodeViewMac.swift:841-852` only affects scroll retention), and a zero-size `gone` does not clip subviews, so the absolute is on screen. Linux paint returns at `gone` (`host/linux/src/paint.rs:795-800`) and does not draw it, but `cb`'s content size still includes it, so the scroll extent grows. `layout_equality.rs` never sets `Display::None`.

   Resolve it by treating a hidden ancestor as "no box" inside `hoisted_absolute` (return `None` before `place`), and by clearing the static-position record when a box is hidden. Add a layout-equality step that hides an ancestor and compares the result with a fresh tree.

2. **HIGH.** On macOS and iOS a static flex or grid item's `z-index` is applied before the view has a parent, so it stays 0. `usedZIndex` returns the row for `relative` and `absolute`, otherwise the parent `NodeView`'s `display` if that is `flex` or `grid`, otherwise 0 (`host/apple/Sources/ExactKit/Mac/NodeViewMac.swift:777-783`, the same walk in `IOS/NodeViewIOS.swift:751-756`). `applyStyle` assigns `layer.zPosition` (`NodeViewMac.swift:1107`, `NodeViewIOS.swift:1074`). Both presenters do that in the `.create` op, and only later add the subview (`PresenterMac.swift:833-836` then `:872`; `PresenterIOS.swift:693-701` then `:730-733`). At create, `superview` is nil, the parent walk fails, and a static item stores 0. `viewDidMoveToSuperview` (`NodeViewMac.swift:1140-1142`) does not recompute it, so a later reparent into a flex or grid container leaves the old value. Before this commit the default was `relative`, and that branch never consulted the parent. CSS gives a flex or grid item its `z-index` even when it is `static`. Concrete input: a `display: flex` parent and a static child with `z-index: 1`, created in one batch. Chrome paints the child above `z-index: auto` siblings. Apple paints it at `zPosition` 0 until some later style op runs after mount. `c1b94670d` makes the inline-text fixture `relative` so its `z-index` reaches the layer; it does not fix create or reparent.

   Resolve it by setting `zPosition` from `usedZIndex` again in `viewDidMoveToSuperview` / `didMoveToSuperview`, after the parent exists.

3. **MEDIUM.** `isolation: isolate` traps descendant paint that the old `position: relative` with `z-index: auto` did not. `isolated` is true for a static, non-stacking box that follows a layered sibling (`host/web/src/layers.rs:89-90`). CSS 2 Appendix E: `isolation: isolate` creates a stacking context; `position: relative` with `z-index: auto` does not. Concrete tree: sibling A `position: absolute; z-index: 1`; sibling B static, isolated only because it follows A; inside B an absolute with `z-index: 2`. Previously B was `relative` and the inner `z-index: 2` participated in the parent context, so it painted above A. Now the inner box is trapped in B's context and A paints above the whole group. The same group traps a descendant `mix-blend-mode` and changes the backdrop a descendant `backdrop-filter` reads. Opacity, blend, and filter on B itself are in `STACKS`, so B is not isolated; the change is only for descendants. LLP 1074's probe compared B's own paint order.

   Resolve it by isolating only when the box's own paint has to form a group, or by documenting this as a deliberate departure from Appendix E and adding a fixture with a descendant `z-index`.

4. **MEDIUM.** The JS target and the live web host disagree on two boxes. Ahead of time, a repeated static row is isolated when it or a descendant is layered, including the first copy (`host/web/src/layers.rs:137`, `after || (d.repeated && layered(...))`). The live `relayer` isolates a sibling only once an earlier sibling is layered (`layers.rs:239-255`), so the first copy is not isolated. Isolation is not a containing block, so layout matches and paint does not. Separately, the live host appends `position: relative` to a static root (`host/web/src/element.rs:55-57`). `host/web-js` emits no such declaration. A static root with `margin-left: 10px` and a child `position: absolute; left: 0; top: 0` is placed against the root's padding edge on the live page and in the kernel, and against the initial containing block on the JS page, so Chrome puts that child at the viewport origin. `host/web-js/flow.js:30` treats containing as `position !== 'static'` and has no root exception; `kernel/src/flow.rs:122` admits an exclusion whose parent is the root. A `wrap-flow: both` absolute that is a direct child of a static root is flowed in the kernel and refused as `context` by the JS mirror.

   Resolve it by emitting the same root `position` and the same isolation predicate from both targets, and by special-casing the root in `flow.js` the way `flow.rs` does.

5. **MEDIUM.** The compiler's containing-block rule is name-based, and a bound `position` skips it. `contains_absolute` matches the attribute name (`contract/lower/src/tags.rs:69-76`), so `overflow="visible"`, `transform="none"`, and `filter="none"` still force `position: relative`. Chrome does not make those a containing block; `overflow: visible` does not clip, which is the native-host reason the LLP gives for the deviation. `positioned` errors only on a literal `static` and then `Some(_) => Ok(None)` (`tags.rs:105-111`), so `position={expr}` on a scroll, clip, or transform box is left alone. If that binding evaluates to `static`, an absolute descendant is placed against an ancestor outside the native scroll or clip view and is still clipped by it. LLP 1074 §0 says the rule is decided from attributes "literal or bound" so every host sees the same literal row. Class rows expanded before this call are seen; a runner `set_style` after compile is not. `will-change`, `perspective`, and CSS `contain` are not in the schema, and the hosts do not emit them (`contain: size` on a canvas is paired with `position: relative` in `element.rs`). Other producers do author absolutes: the `dialog` tag, content-region placeholders, and contract tests.

   Resolve it by forcing `relative` unless the `position` attribute is a literal `relative` or `absolute`, and by consulting the attribute value so `visible` and `none` do not establish a containing block.

6. **MEDIUM.** A content-region trial and the ordinary tree pick different containing blocks for an absolute grandchild. The trial lays the owner out as the root of its own tree (`kernel/src/region/tree.rs`), so a static owner contains every absolute descendant. The check only rejects a static owner when the content node or the pending node is itself absolute (`kernel/src/region/state.rs:736-744`). An absolute grandchild is measured as if the owner contained it and, in the real tree, placed against a higher positioned ancestor. The comment on those lines says the two trees have to agree.

   Resolve it by walking the owner's descendants for an absolute, or by refusing any static owner.

7. **MEDIUM.** Percentage insets and sizes on an absolute resolve against the used area even when that height came from content. `AbsoluteBox::of` resolves `top`, `bottom`, and `height` with `area_size.height` (`vendor/taffy/src/compute/common/absolute.rs:193-199`). Concrete tree: a `position: relative` parent with `height: auto`, an in-flow child 100px tall, and an absolute `top: 50%; width: 10px; height: 10px`. Chrome treats `top: 50%` as `auto` because the containing block's height is indefinite, and the absolute sits at its static position (y = 100 if it follows the in-flow child). This solver sets `top` to half the used height. `left`/`width` percentages against a definite width are fine, and `top: 0; bottom: 0` correctly stretches to that used height. The fixtures (`browser_containing_block.tsv` rows 8-9) use a 300px root. This is the same resolution the old absolute pass used; the new solver is what carries it, and nothing in the 79 cases covers it.

   Resolve it by treating a percentage as `auto` when that axis of the containing block was not definite on the way in, and add that case next to the existing inset rows.

8. **MEDIUM.** An absolutely positioned root ignores its insets and stays content-sized at the origin (`vendor/taffy/src/compute/mod.rs:80-81` and `:128-176`: `known_dimensions` is `NONE`, `location` is `ZERO`). A root margin is added into every published frame (`kernel/src/layout.rs` `frame_of`) and into the Linux document extent.

   Resolve it by running the absolute solver for an absolute root against the offer, and say so in LLP 1074 §4.
