# Round 1

**1. Overall assessment.** **Revise and stay Draft.** The objective is sound: optional functionality should have a demonstrable cost only in applications that select it, across Rust and Swift. But r1 overstates what the measurements establish, misdescribes existing generated entries and interpreter selection, and does not yet show how D2–D3 produce the promised link boundaries.

This was a static audit against `f9d8e1ed1` and the uncommitted RFC. I did not reproduce the external measurements, inspect their artifacts, or run builds. Linker outcomes below are requirements to establish, not results I claim to have measured.

**2. Strengths.** Several parts should survive revision:

- **D1** extends the parent’s useful distinction between core, linked capabilities and loaded capabilities to Swift. “It’s in ExactKit” is correctly rejected as a reason to classify functionality as core.
- **§1** measures the final executable’s increment over a UIKit floor, distinguishes optimization configurations, and discloses that the October build was not booted.
- **D3** identifies real retention paths: concrete feature objects and general dispatch keep optional implementations reachable.
- **D4–D5** preserve the parent’s named refusal and production-artifact smoke principles.
- **D6** proposes reporting bytes without another blocking check.
- **§5** correctly separates reducing code size through compiler options from making functionality optional.

**3. Concerns.**

**C1 — blocking: §3’s explanation of Apple linker roots is incorrect as stated and incomplete.** The macro does invoke the export groups unconditionally, but `#[no_mangle]` does not, by itself, establish that every symbol is a live root in the final Mach-O executable. Symbol emission, archive-member extraction, final exports and dead stripping are different stages. The RFC’s own probe limits executable exports to `main`; the wasm export-root explanation cannot simply be transferred to that link. See [exports.rs:19](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/src/abi/exports.rs:19) and [the RFC’s link method:42](/Users/ccheever/projects/exact2-wt-1047-001/llp/1047.001-apple-links-by-use.rfc.md:42).

There are independently visible native retention paths. Apple boot explicitly links style grammars and calls the runner’s all-capability boot path. The web’s `HostLinks` addresses executable references through optional function pointers; its achievement is broader than suppressing export declarations. See [Apple host.rs:364](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/src/host.rs:364), [runner delivery.rs:74](/Users/ccheever/projects/exact2-wt-1047-001/runner/src/runner/delivery.rs:74), and [web host.rs:137](/Users/ccheever/projects/exact2-wt-1047-001/host/web/src/host.rs:137).

**Resolution:** Rewrite §3 around actual reference chains. D2 must include selective native host/runner hooks and removal of unconditional implementation references, not just conditional export groups. Identify which symbols are roots under the supported final-link configuration and demonstrate absence in that executable.

**C2 — blocking: D3’s module split and registration scheme do not yet establish Swift droppability.** A single Swift module does not inherently make all its code live; conversely, moving code into several modules does not inherently make unused code disappear. The current SwiftPM product names `ExactKit` without specifying a static-library product type. D3 must describe the target/product dependency graph and final linking arrangement, rather than treating an `import` list as proof of which object code reaches the executable. See [Package.swift:28](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/Package.swift:28) and [Package.swift:62](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/Package.swift:62).

The references to remove extend beyond non-core batch op cases:

- Presenter batch processing unconditionally invokes feature lifecycle methods, including grouped-list, menu and navigation preparation. See [PresenterIOS.swift:727](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/Sources/ExactKit/IOS/PresenterIOS.swift:727).
- The core node class conforms to several UIKit delegate protocols, and ordinary style application invokes optional feature helpers. See [NodeViewIOS.swift:13](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift:13) and [NodeViewIOS.swift:1209](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift:1209).
- Session initialization directly wires Canvas 2D callbacks. See [Session.swift:493](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/Sources/ExactKit/Session.swift:493).

Stored types, initialization/destruction, protocol conformances and witness tables, class metadata, `@objc` selectors and Objective-C registration all need consideration. They are possible retention paths, not evidence that every conformance always survives. Generic specialization can also leave code in callers or change duplication across module boundaries; splitting modules is not a guaranteed size improvement.

**Resolution:** Specify a core-owned interface that does not name optional concrete types, with selected capabilities supplying factories and lifecycle/dispatch hooks. Move optional delegate objects and conformances where necessary. Explain SwiftPM dependency selection and supported linker settings, including any Objective-C or force-loading behavior. Validate an actual capability containing UIKit/Objective-C behavior, not only a pure Swift helper. Define the promised granularity: “one module per capability” and “every feature independently optional” are not automatically equivalent.

**C3 — blocking: D2 assumes a universal use-set that the current code does not provide.** The implemented function is `exact_runner::uses`, not `exact_plan::uses`. More importantly, its capability model contains web-specific decisions: `Motion` covers springs and held gestures because CSS handles other transitions. A native host cannot reuse that selection unchanged while its own engine performs ordinary transitions. See [runner uses.rs:20](/Users/ccheever/projects/exact2-wt-1047-001/runner/src/uses.rs:20), [uses.rs:203](/Users/ccheever/projects/exact2-wt-1047-001/runner/src/uses.rs:203), and [uses.rs:299](/Users/ccheever/projects/exact2-wt-1047-001/runner/src/uses.rs:299).

The existing enumeration also does not independently represent every Swift capability proposed in D3, such as grouped lists, navigation bars and menus. SVG-related analysis already exists separately from that enumeration. Treating the current bitset as complete could omit required native behavior.

**Resolution:** Define shared semantic facts and their host-specific implementation requirements, including dependencies between capabilities. Preserve conservative handling of computed values and every reachable route/state, rather than selecting from the first rendered screen. Explain which non-plan inputs select executors or services. One resulting composition must consistently drive Rust, Swift, admission and compatibility metadata.

**C4 — material: §3 misdescribes generated entries and wasmi selection.** “Each app” has a handwritten entry and “there is no generated entry” are false. Caltrain and Type Tour already include generated `entry.rs` files, and their build scripts call `contract::rust_entry`. See [Caltrain lib.rs:14](/Users/ccheever/projects/exact2-wt-1047-001/apps/caltrain/apple/src/lib.rs:14), [Caltrain build.rs:44](/Users/ccheever/projects/exact2-wt-1047-001/apps/caltrain/apple/build.rs:44), and [Type Tour lib.rs:12](/Users/ccheever/projects/exact2-wt-1047-001/apps/typetour/apple/src/lib.rs:12). Some other entries remain direct macro calls. The missing piece is capability-aware composition, not generation itself.

Likewise, `configured!` does not imply wasmi in every application. `rust_entry("off")` generates a direct data source; the concrete `wasm` constructor references `wasm::load`, whereas the `native` constructor selects the native loader. See [contract logic.rs:30](/Users/ccheever/projects/exact2-wt-1047-001/contract/cli/src/logic.rs:30) and [logic lib.rs:101](/Users/ccheever/projects/exact2-wt-1047-001/logic/src/lib.rs:101). There is a real narrower issue: native mode selection defaults to `auto`, and iOS selects wasm without the web’s “no declared module means off” rule.

The interpreter default was also intentional policy, not merely accidental retention: [LLP 1029.000:20](/Users/ccheever/projects/exact2-wt-1047-001/llp/1029.000-rust-development-reload.rfc.md:20) records Charlie requesting it.

**Resolution:** Describe the current entry families and extend their existing generation seam. Narrow the wasmi claim to the applicable configurations. Explicitly reconcile the proposed module-presence rule with interpreter defaults and D5’s development policy, updating executor compatibility metadata alongside generated code. Do not treat the real-app ≈1 MB attribution as an established saving in the one-text probe.

**C5 — material: D3 does not specify the embedding composition promised by LLP 1031.** An embedder owns its application entry point. Generating the standalone Exact app’s Swift entry does not automatically give that embedder the same selected capabilities.

The current `--embed` path ships the app-specific Rust archive, header, assets and receipts, and tells the consumer to link the reusable Swift package. It explicitly builds no Swift for that output. See [build.mjs:934](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/build.mjs:934). LLP 1031’s unit is an app artifact supporting one plan and multiple sessions, not an arbitrary independently linked surface per view; see [LLP 1031:179](/Users/ccheever/projects/exact2-wt-1047-001/llp/1031-brownfield-embedding.rfc.md:179) and [its packaging contract:399](/Users/ccheever/projects/exact2-wt-1047-001/llp/1031-brownfield-embedding.rfc.md:399).

**Resolution:** Specify what generated Swift composition the embedding consumer receives, which package product it links, and how that composition participates in `ExactApp`/session creation without requiring Rust tooling. Keep mutable capability instances session-scoped. Explain how optional C exports, Swift registrations and the descriptor agree. Updating the ABI coherently is acceptable; preserving obsolete ABI shapes through compatibility shims is not required.

**C6 — material: the absolute rule conflicts with explicit parent exceptions; D4–D5 need precise scope.** Parent D8 explicitly permits native applications to link capabilities ahead of plan use. That conflicts with the child’s unqualified “if and only if.” D5 also deliberately links unused capabilities in development, and the parent retains inspection in production for operational reasons. See [parent D8:324](/Users/ccheever/projects/exact2-wt-1047-001/llp/1047-pay-for-what-you-use.rfc.md:324) and [settled answers:511](/Users/ccheever/projects/exact2-wt-1047-001/llp/1047-pay-for-what-you-use.rfc.md:511).

D4 and D5 themselves broadly agree with parent D6–D8. However, D4 must preserve the distinction between runtime admission and deployment compatibility: adding a required capability is a binary change, not merely something discovered at boot. D5 must also distinguish the application smoke using the shipped composition from whole-vocabulary fixtures requiring an all-linked host; the web already makes that distinction. See [parent D6:292](/Users/ccheever/projects/exact2-wt-1047-001/llp/1047-pay-for-what-you-use.rfc.md:292), [parent D8:320](/Users/ccheever/projects/exact2-wt-1047-001/llp/1047-pay-for-what-you-use.rfc.md:320), and [smoke.mjs:482](/Users/ccheever/projects/exact2-wt-1047-001/scripts/smoke.mjs:482).

**Resolution:** State the effective selection policy and its exceptions. Either retain explicit link-ahead selection or explicitly amend parent D8. Resolve production inspection before claiming smoke/shipping equivalence. Ensure the linked set enters bake/compatibility/classification as well as runtime admission. Generating different compositions while modules themselves build one way is consistent with the prohibition on Cargo feature matrices.

**C7 — material: a named refusal alone does not provide safe native failure behavior.** There is a concrete existing hazard on the initial iOS boot path: `ExactView.fit()` calls `session.boot()` and then recursively calls `fit()` while `session.booted` is false. `finishBoot` sets `booted` only on success. An initial capability refusal can therefore encounter repeated boot/fit recursion rather than settle into a contained failure. See [ExactViewIOS.swift:316](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/Sources/ExactKit/IOS/ExactViewIOS.swift:316) and [Session.swift:815](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/Sources/ExactKit/Session.swift:815).

Updates also have an existing all-session prepare/commit boundary. Capability admission must preserve that boundary, rather than reject after one session or performer has already changed. See [Session.swift:293](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/Sources/ExactKit/Session.swift:293).

**Resolution:** Cover initial boot, reload, explicit plan application and delivered candidates. Check actual Rust and Swift availability before activation, preserve the previous running state on candidate rejection, and provide a terminal initial-failure state. Record the recursive-fit issue as a prerequisite to exercising D4, not as a newly discovered consequence of the proposed architecture.

**C8 — material: the measurements support growth, but not all the causal conclusions or rankings.** Measuring stripped final-link bytes over an otherwise identical UIKit floor is a sound measure of executable overhead. The reported production increase is approximately 36%; “about a third” is reasonable.

However, link-map attribution to `NodeView`, the kernel or the runner does not establish that every attributed byte is unnecessary for a one-text plan. Core changes, shared implementations, specializations and metadata can contribute. Thus “none of this is reachable” and “every feature … adds bytes to every Apple app” exceed the evidence. Apple already selectively includes loaded modules for production `L=0` builds. See [RFC:26](/Users/ccheever/projects/exact2-wt-1047-001/llp/1047.001-apple-links-by-use.rfc.md:26), [RFC:87](/Users/ccheever/projects/exact2-wt-1047-001/llp/1047.001-apple-links-by-use.rfc.md:87), and [build.mjs:962](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/build.mjs:962). The sibling already discusses shared code and storage paths complicating optionality; see [LLP 1047.000:488](/Users/ccheever/projects/exact2-wt-1047-001/llp/1047.000-staged-loading-by-capability.rfc.md:488).

The cross-framework statement also contains a straightforward error: 9.83 MB is above Lynx’s 9.31 MB, not between React Native and Lynx. React Native’s unmeasured JS bundle prevents a complete ranking. Framework payloads, executable deltas and an application including assets are not identical accounting boundaries.

**Resolution:** Retain the observations, qualify the causal interpretation, and correct the ranking. Record the exact baseline revision, target triple, SDK/toolchain, flags and size units; “arm64 iPhone” does not distinguish device from simulator. Separate archive-input configurations from final-product measurements. Establish removable costs through comparable capability-present/capability-absent final links. Characterize the unchecked-exclusivity/no-reflection configurations separately from ordinary production semantics.

**C9 — material: D6 needs an honest approval and execution model.** Report-only bytes agree with the parent’s settled decision. But “this RFC is the human asking for it” is not established by the quoted request to record an optionality rule. The supplied record demonstrates authorization for this document; it does not itself demonstrate authorization for a new in-repository probe.

The binding rule requires explicit human approval for added apparatus. See [RULES.md:64](/Users/ccheever/projects/exact2-wt-1047-001/rules/RULES.md:64). D6 should request that approval or cite an existing authorization that actually covers it.

Placement also matters. The existing long metrics run is asynchronous, while the currently documented first lane coalesces commits hourly. Adding a row there does not establish “per commit” measurement or attribution. See [async.mjs:34](/Users/ccheever/projects/exact2-wt-1047-001/scripts/async.mjs:34) and [async.mjs:137](/Users/ccheever/projects/exact2-wt-1047-001/scripts/async.mjs:137).

**Resolution:** Specify the approved carrier and actual reporting cadence, reuse existing measurement machinery, and keep expensive iOS builds outside the blocking gate. A report-only byte row does not waive rebuild, startup or frame-performance budgets. The Swift split should account for the existing shared compilation strategy, rather than accidentally rebuilding all host code per application. Before §6 becomes assigned implementation work, supply its implementer/date and settle the parent’s native-after-web ordering. See [RULES.md:25](/Users/ccheever/projects/exact2-wt-1047-001/rules/RULES.md:25), [RULES.md:58](/Users/ccheever/projects/exact2-wt-1047-001/rules/RULES.md:58), and [build.mjs:162](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/build.mjs:162).

**C10 — material: §6 puts export removal before its prerequisites and measurement too late.** Existing Swift text code calls optional Rust markup functions through the ordinary text engine. Removing those exports before severing the Swift references can produce undefined symbols, not a smaller working application. See [Text.swift:1348](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/Sources/ExactKit/Text.swift:1348) and [MarkupRuns.swift:37](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/Sources/ExactKit/MarkupRuns.swift:37).

Likewise, the largest file-level growth is not necessarily the largest removable capability. Wasmi is a plausible independent optimization for particular apps, but its quoted size does not make it the best demonstration of this probe’s Rust/Swift retention problem.

**Resolution:** Measure before changing composition and implement the first capability through both languages together. Admission, embedding packaging and artifact inspection belong in that first slice, not after a broad export split.

**C11 — minor: “every host” needs an explicit scope statement.** D1 and §6 enumerate web, Apple, Linux and Windows, but terminal support is now admitted. Within Apple, the evidence is UIKit-focused while the package also supports macOS and tvOS. See [DEFERRED.md:313](/Users/ccheever/projects/exact2-wt-1047-001/rules/DEFERRED.md:313) and [Package.swift:61](/Users/ccheever/projects/exact2-wt-1047-001/host/apple/Package.swift:61).

**Resolution:** Distinguish the universal policy from the initial implementation scope, naming remaining hosts and Apple presenters without implying they have already been analyzed or implemented.

**4. Suggestions.** I would replace §6 with this order:

1. Resolve the selection policy: host-specific requirements, native link-ahead, interpreter defaults, production inspection and implementation priority.
2. Record a reproducible baseline using the intended production composition and embedding path. Obtain or cite authorization before adding measurement apparatus.
3. Carry one capability through the entire boundary: analysis, existing entry generation, Rust hooks, Swift factories/lifecycle, optional C calls, embedding output and admission.
4. Demonstrate both presence and absence in final artifacts, successful behavior when selected, contained refusal when unavailable, and unchanged two-session embedding behavior. Cover computed use and ordinary native transitions.
5. Expand according to measured marginal savings. Handle the narrower wasmi-default issue separately where justified.

Generated composition should remain build output, not committed per-app generated source, consistent with [RULES.md:16](/Users/ccheever/projects/exact2-wt-1047-001/rules/RULES.md:16).

**5. Open questions for the author.**

- Does the strict rule intentionally revoke native link-ahead, or does explicit application selection count as “use”?
- Does module-presence selection change the previously requested iOS interpreter default, and in which development/production configurations?
- What generated Swift product or source does an LLP 1031 consumer receive, and how is its registration invoked?
- Does production retain inspection, and what capability granularity must independently cost zero when absent?
- Is native work now prioritized ahead of the parent’s web outcome? Who implements the first slice, and when?
- What exact measurement configuration and prior authorization support D6’s probe and claimed reporting cadence?

**6. Recommended next step.** **Revise and stay Draft.** Preserve the cross-host optionality rule, correct §3 and the measurement conclusions, reconcile the parent’s exceptions, and specify one complete Rust/Swift/embedding capability boundary. The RFC need not implement the whole split before acceptance, but it must explain why that boundary is droppable and how its absence will be demonstrated.
