Three fundamental host-mapping issues remain.

D1, D3–D6 and D10 hold up at the design level: the revised clock, phase, gate, refusal and takeover rules resolve the earlier objections. The existing JS live-clock tests pass 6/6.

1. **Android’s owner can be idle while the session is animating or applying a batch.**

   [D7’s Android row](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:278) watches the owner’s frame source and published queue. But lowered animations deliberately [stop keeping the engine’s clock busy](/Users/admin/Developer/exact2-timer-wait-points/motion/src/engine/animate.rs:236), while [ExactView’s sampler](/Users/admin/Developer/exact2-timer-wait-points/host/android/canvas/src/main/java/dev/exact/canvas/ExactView.kt:1028) continues sampling them on the main thread. These animations do require the main thread, so D7’s Core Animation exemption does not cover them.

   During a three-second opacity animation, with no scroll or frame task, the owner can have no frame posted and an empty queue. An `update` timer then runs immediately, and an `idle` timer can qualify during ongoing frame production. Queue emptiness also fails D2’s “no batch … applied” test: [takeOwned removes the publication before applying it](/Users/admin/Developer/exact2-timer-wait-points/host/android/canvas/src/main/java/dev/exact/canvas/ExactView.kt:523).

   **Instead:** Define admission using main-thread frame demand and acknowledgements of completed batch application, including how the owner revalidates those reports. Moving release to the correct callback resolves only part of r4’s Android objection.

2. **The web’s scroll-event set cannot establish unconditional scroll exclusion.**

   [D7](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:275) detects scrolling through `scroll` and `scrollend`, reserving gesture tracking for older Safari. However, browsers scroll independently and deliver `scroll` events asynchronously. [Chrome’s documentation](https://developer.chrome.com/docs/css-ui/scroll-driven-animations) explicitly describes this separation.

   A permitted sequence is: compositor scrolling starts at 99 ms; a timer’s deadline timeout runs at 100 ms; the first DOM `scroll` notification arrives during the next rendering update. At 100 ms the set is empty, so the uncapped timer runs during scrolling. This contradicts [D7’s guarantee](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:299), including in browsers with native `scrollend`.

   **Instead:** Admit otherwise-ready timers after a rendering update’s scroll steps, track gesture starts on every browser, and define the guarantee against observed activity. Document-level scroll notifications cannot establish instantaneous compositor quiescence.

3. **R5 counts Web Animations but omits their completion wakeups.**

   [D7’s new animation rule](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:282) includes Web Animations, but its recheck sources are CSS animation and transition events. Plain Web Animations report `finish` and `cancel` on their `Animation` objects; those notifications do not become the named document-level CSS events. [Web Animations specification](https://drafts.csswg.org/web-animations-1/#animation-events)

   This is an existing Exact path: [motion-glue creates animations with `Element.animate()`](/Users/admin/Developer/exact2-timer-wait-points/host/web/motion-glue.js:589). Suppose an idle save becomes due at 800 ms during a two-second spring, with `max=5000`. The animation finishes at 2,000 ms without another Contract commit. Under the listed wake sources, the save receives no eligibility recheck and waits until its 5,800 ms cap despite the session becoming idle.

   **Instead:** Observe each relevant `Animation` object’s completion and cancellation, through its events or `.finished` promise, and feed those notifications into the idle recheck. CSS events alone are insufficient.
