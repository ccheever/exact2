**RIGHT WITH CHANGES**

1. **BLOCKING — Opacity-only keyframes bypass the round 2 fix.** [svg_lower.rs:662](/tmp/rv-s8b2-r3/host/apple/src/svg_lower.rs:662) checks `paints_over` only inside `box_eligible`. That function is reached only for `BOX_LOWERED` properties, which exclude opacity; macOS also has `box_motion == false`. Ordinary opacity animations therefore remain delegated on both platforms. With model opacity 1, rendered opacity 0.4 and active target 0.6, the press adds −0.4 and displays 0. [Core Animation adds to the rendered value.](https://developer.apple.com/documentation/quartzcore/capropertyanimation/isadditive?language=objc) **Fix:** perform the overlay check in the common eligibility path, including live changes, and test withdrawal of existing animation specs.

2. **BLOCKING — Zero depth leaves the press clock in the wrong state.** [PressPaint.swift:253](/tmp/rv-s8b2-r3/host/apple/Sources/ExactKit/PressPaint.swift:253) now derives the destination from `ease.to`, but `fadePressOpacity` returns before updating that clock when depth is zero. Start with base and active target both 0.6, press, then change the base to 0.8: `ease.to` remains zero, so the node stays at **0.8 instead of 0.6**, including under the agent clock. Releasing at zero depth can conversely leave the clock pressed. **Fix:** update press progress on every down/up before the zero-depth return; remove only the unnecessary animation.

3. **BLOCKING — Style updates during release do not recompute press opacity.** [PressPaint.swift:280](/tmp/rv-s8b2-r3/host/apple/Sources/ExactKit/PressPaint.swift:280) refreshes press depth through `pressPainted` only while `down`; after release, that function returns early. A live update to the held hover look therefore changes `lookOpacity` while retaining the old press contribution. At progress 0.5, changing hover opacity from 0.8 to 0.4 with active target 0.6 displays **0.3 instead of 0.5**. **Fix:** refresh against the incoming style whenever the press ease remains active, including release. Test a style-batch update during release.

4. **BLOCKING — Inline looks remain silently discarded.** [BatchShapes.swift:165](/tmp/rv-s8b2-r3/host/apple/Sources/ExactCore/BatchShapes.swift:165) still skips `looks`, and paragraph runs have no `NodeView` to compose them later. An accepted inline span’s hover background consequently never appears. This leaves round 2 Astra finding 4 unresolved. **Fix:** retain and compose looks in inline run tracking and invalidate the owning paragraph, or obtain an explicit scope restriction and diagnose unsupported parts rather than accepting them silently.

5. **SHOULD-FIX — Exiting a descendant tracking area clears the entire presentation’s hover.** [MouseChainMac.swift:535](/tmp/rv-s8b2-r3/host/apple/Sources/ExactKit/Mac/MouseChainMac.swift:535) treats every hosted-window `mouseExited` as leaving the window. Moving between children can deliver the new child’s enter before the previous child’s exit, leaving the new look cleared until another move; [AppKit does not guarantee tracking-event order.](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/TrackingAreaObjects/TrackingAreaObjects.html) **Fix:** hit-test the event’s window on exits too, retaining the current eligible path. Test that ordering inside both a sheet and a popover.

6. **SHOULD-FIX — Rebased fades still diverge from the tracked press curve.** [PressPaint.swift:256](/tmp/rv-s8b2-r3/host/apple/Sources/ExactKit/PressPaint.swift:256) starts another complete timing curve over the remaining duration, while `pressPaint.ease` continues describing the original curve. Rebase at 40 ms: at 50 ms the installed progress is approximately **0.9589**, versus tracked **0.9467**. Another update or release uses the latter and jumps. **Fix:** preserve the original animation start, duration and progress endpoints with the new depth, or use the correctly sliced curve. Test presentation values after rebasing; the new test checks only replacement endpoints.
