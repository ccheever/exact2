## Question A — the word

**Recommendation:** No umbrella word. Name the kind the author already says: `widgets` in `app.json`, in the agent's commands, and in prose, and `activities` for a Live Activity. The root file is an `entry`, as in LLP 1101's `host.terminal.entry`. The bake's admission profile stays `snapshot`, a compiler word in the same role as `terminal`, spoken in errors. Add `complications`, `controls`, or `snippets` only when that kind is admitted. Put the keys at the top level of `app.json`, beside `host`, because one iPhone widget is the same entry on the Mac, in CarPlay, and on HomeView.

**Confidence:** 82%

**Reasoning:** An agent with no teaching, asked for a Home Screen widget, looks for `widgets`. Asked for a Live Activity, it looks for an activity key. `glance`, `placement`, `outlet`, `satellite`, and `system view` are words it will not produce, and `glance` is already Android's widget toolkit and a retired watchOS product. `surface` is already what an author types for three other things in the same files: a canvas binding (`canvas surface=`, `exactSurface()`), a Tamber token (`surface.card`, `surface.page`, `pair=surface.page` in `docs/contract-for-agents.md`), and the platform list in `rules/DEFERRED.md` §Surfaces. It is also the Swift target `ExactSurfaces` and the C entry `exact_fulfill_surface`. D4 allows a canvas picture leaf inside a widget, so the two meanings would meet in one component. Renaming the canvas use would rewrite a settled binding, a reserved source, a Swift target, and the ABI, to free a word for a thing that already has platform names. LLP 1124 has taken `extension` for a declared device capability (`"extensions": { "battery": 1 }` in `app.json`). The terminal entry is the shape to copy: the kind is the key, the file is an `entry`, the profile name stays internal.

I would spell the Live Activity key `activities` and say "Live Activity" in prose. I have not checked which of `activities` and `liveActivities` agents actually emit. Freeze the spelling after one look at that, before the schema lands.

**What would change my mind:** A requirement that every kind share one JSON array, plus evidence that agents mishandle the same shape when it is split across keys. The key would then be `entries` with a required `kind`, still with no new noun. Or evidence that agents, unprompted, already call this a surface and do not confuse it with the canvas binding or with `surface.card`.

## Question B — Live Activity pushes

**Recommendation:** Leave ActivityKit push tokens out of stage 2. Admit them later, and only as update tokens, when a named consumer's activity is false without them. Expo Services' build progress is the consumer that qualifies. The app registers the token with its own backend; exact2 sends nothing and relays nothing; the payload is D9's envelope, within the 4 KB limit. Starting and ending an activity stay sends from the running app. Remote notifications stay refused, with badges, actions, replies, repeating schedules, and a readable permission fact.

**Confidence:** 78% on waiting. 90% on keeping remote notifications refused.

**Reasoning:** Stage 2 as D9 writes it is a real product for a date the phone already holds. Caltrain's departure is that case: a widget's truth is a timeline of instants, and a Live Activity's ticking text is `time` (D6), which the system draws with no process and no push. `rules/DEFERRED.md` still refuses "push delivery from a server" in the notifications entry, and it restated that refusal on 2026-10-11 when it admitted a notification's body click. The delivery entry refuses push as part of the service half of the old update economy. LLP 1030 and LLP 1030.000 D6 say exact2 sends no pushes and relays none, and they already allow a narrower thing: a push the app's own server sends may nudge the host to run `check`. An ActivityKit update token fits that shape once a consumer needs the system to apply content while the app is suspended. Admitting it at stage 2 spends the refusal on a capability that stage does not need.

The entitlement is a hazard of precedent. I am taking as given, and have not re-checked Apple's docs from this checkout, that an ActivityKit push token needs the Push Notifications capability and `aps-environment`. The APIs differ. A remote notification is an alert, a badge, and a payload the app handles. An activity update is `content-state` the system stores and the extension renders. A token and a content-state schema do not require a notification handler. The click ruling admitted one line and restated the rest. A later token ruling should do the same.

Push-to-start is a third mechanism and is outside this recommendation. It lets a server create an activity while the app is suspended, which cuts D9's line that starting an activity is a send from the running app.

Two platform facts I have not verified here: whether any entitlement narrower than `aps-environment` can mint an ActivityKit token on the iOS 17 floor Caltrain declares (`apps/caltrain/app.json`), and the current stale-date and maximum lifetime of a Live Activity. I believe a `Text` timer keeps running after the app is suspended and that content-state does not change until an update. I would not quote an hour limit.

**What would change my mind:** Naming Expo Services' build activity as the stage 2 acceptance. A "Building…" activity that freezes when the app leaves the foreground is a tell, so the update token belongs in that stage. Remote notifications still stay refused. Push-to-start joins only if that same consumer must have the activity appear while the app is killed. A build the person opened and then left needs updates. I would also move the token earlier if a measured timer activity is jetsam'd or marked stale so quickly that D6's countdown never reaches the Lock Screen. There is no such measurement.

## Question C — the first consumer

**Recommendation:** Caltrain for stage 0. Caltrain for stage 1. Interview for stage 2, limited to an activity whose truth the phone already has. Expo Services' build activity waits until the push ruling in question B names it.

**Confidence:** 88% for stage 0, 80% for stage 1, 64% for stage 2.

**Reasoning:** Stage 0 is a fidelity gate against a hand-built widget. Caltrain is in this checkout, its data is public, and its countdown is the case D6 exists for. The baseline has to be a platform timer to a departure instant. Caltrain's own card computes `countdownText(d.at, nowMs)` in `apps/caltrain/app.contract`; a baseline that copies that string blesses a widget that does not tick. Keep the baseline as text. The line map is a `canvas surface=`, which is the picture-leaf exception, not the reference. Q3's Hermes half belongs in this same stage, measured on an in-repo TypeScript module (`apps/fieldnotes` has `app.ts`), so the memory kill line is known before any out-of-repo app is wired in. Fieldnotes is the measurement. Its refresh may pull storage a widget never loads, so a failure there should be bisected before it condemns the session.

Stage 1 is the driver, the `snapshot` profile, the cohort, and the gallery, on the app this repo uses because "does it still work" is answerable in seconds (`rules/DEFERRED.md`). A departure widget has no secrets, so a Lock Screen render before first unlock is a rendering question. LLP 1018 D7 stores iOS secrets as `AfterFirstUnlockThisDeviceOnly`, unavailable from reboot until the first unlock. D8's rule that the render reads props and the plain store is unproven by Caltrain, and stage 1 should say so. A Rust data crate also does not stand in for Hermes. Stage 1 proceeds with a session in the extension only if stage 0's Hermes number is inside the kill line. Otherwise §6's render-only fallback is the decision, and Caltrain does not get a special pass.

Expo Services is the wrong stage 1 app. LLP 1115.003, accepted 2026-10-16, is still replacing its drawing modules, and that RFC records the iOS app building against a host patch that is not upstream. Signed-in Keychain data and a build's progress pull question B into the first widget. Interview is the wrong stage 1 app because it ships to users: the first extension, the first shared update generation, and the first Lock Screen account content would land together on a production binary.

Stage 2 is where a person's judgement and the secret rule earn their cost. Interview ships to users, holds account data, and its data module is TypeScript under Hermes (LLP 1048.000, Interview's `app.ts`). That is the pile stage 1 skipped, taken after the archive and the memory numbers exist. The activity has to stay true with the app suspended and with push still refused: a state the running app set, a countdown the system draws, a tap that is a route URL (LLP 1038). Secrets stay inside the refresh. I believe an extension cannot read the app's Keychain items unless the two bundles share a keychain access group. LLP 1018's "no extra entitlement for the app's own group" is about the app itself. Confirm the group before Interview's extension is signed, and keep the widget on an internal build until a before-first-unlock pass shows the placeholder. This checkout does not name an Interview activity that meets that bar. If the maintainers have none, stage 2 stays on Caltrain, a departure the user selected, and Interview's widget waits.

Expo Services is the build-progress consumer, and that activity is false without the update token. It also sits on a port that is still open. It becomes the stage 2 app only if question B admits update tokens in that same stage.

**What would change my mind:** A Hermes kill-line failure on the small in-repo module, which stops "session in the extension" for every candidate and makes stage 1 about the render-only fallback. An Interview activity that only a server can advance, which means stage 2 stays Caltrain, or B is admitted and Expo Services takes stage 2. Evidence that Interview's module is far larger than the stage 0 fixture, so the fixture did not measure the real refresh. Measure Interview's bytecode before calling stage 1 done, and still ship Caltrain's widget in stage 1.

## What these three questions get wrong

The RFC asks for one noun to occupy the manifest, Contract, the agent, and prose together. The terminal entry already split those jobs, and the guessable names are the kinds. It also treats "push" as one switch. A timeline of future departures, a `Text` timer, an ActivityKit update token, push-to-start, and a remote notification are five different wakes. Only the update token is the Live Activity feature people mean, and `aps-environment` is shared provisioning, which is a weak reason to open the notifications entry. "A shipping app" is also two different proofs. Interview can judge a widget a person keeps, on account data, with no server in the loop. Expo Services' natural activity is a server's build, on an app whose graphics port is still open (LLP 1115.003). Choosing it as stage 2 decides question B in the same breath. The countdown widget does not need that decision. The build activity does.
