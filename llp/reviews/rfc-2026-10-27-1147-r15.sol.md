One fundamental liveness issue remains.

1. **A cancelled smooth scroll can leave the web’s moving set occupied forever.** [D7](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:292) retires observed scrolling through `scrollend`, removal or stopped rendering; its quiet-time fallback applies only to older Safari. But the repository already contains a counterexample: [this browser regression test](/Users/admin/Developer/exact2-timer-wait-points/host/web-js/list.test.mjs:161) replaces a moving smooth scroll with an instant request that preserves the current position, and explicitly expects **zero `scrollend` events**. The [host command](/Users/admin/Developer/exact2-timer-wait-points/host/web-js/rt.js:270) calls the DOM directly. This behavior agrees with [CSSOM’s scroll algorithm](https://drafts.csswg.org/cssom-view/#perform-a-scroll): replacement aborts the previous scroll, and a replacement that changes no position emits no end.

   Start a smooth scroll, let its first `scroll` put the container in the set, and hold an uncapped timer. An action then makes that instant, no-op replacement. The container remains connected and visible, but its recorded movement never ends. Any touch-release recheck added by r15 still finds the stale entry. The timer can remain held indefinitely.

   **Instead:** Make cancellation and replacement of host-controlled scrolls explicitly retire their movement hold and request a condition check. Preserve independent touch, momentum and animation holds. Add the existing no-op interruption scenario to D10 with an uncapped timer.

I found no additional fundamental issue in Apple’s passive-observer design against UIKit’s documented [state machine](https://developer.apple.com/documentation/uikit/about-the-gesture-recognizer-state-machine) and [simultaneous-recognition rule](https://developer.apple.com/documentation/uikit/uigesturerecognizerdelegate/gesturerecognizer(_:shouldrecognizesimultaneouslywith:)). Those callbacks trigger a condition check; ongoing scroll holds still prevent release.

Android’s “no touch down” does **not** have r14’s missing-wake gap: [D7 requires reporting every touch-state change](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:330), independently of whether the touch moved a scroller.
