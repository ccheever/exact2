# Review: LLP 1057.000, composable gestures, 2026-09-26 (grok)

- **Family:** xAI, Grok 4.7, `--reasoning-effort xhigh --always-approve`, in a detached checkout at `479bd946`.
- **Brief:** `gesture-brief.md` (the claude artifact's header).
- **Redacted:** no. Final message verbatim below.

---

## Assessment

Design A matches the tree and the parent research. Design C does not yet deliver native feel and the same outcome together: discrete `exclusively` changes which actions fire, continuous `exclusively` is a race against undocumented thresholds, and the conformance suite injects winners instead of testing UIKit. The three worked examples are closed-table work the parent already scheduled. The shared `gesture` surface is a reasonable later Contract, and it is not justified now.

Checked at `479bd946`. The §2 citations that I re-read match, except the `touch-action` lines and the Linux velocity field noted below.

## Platform claims

Confident: UIKit default exclusion; `shouldRecognizeSimultaneouslyWith` succeeds if either delegate returns true; `require(toFail:)` delays the waiter until the other fails; a recognizer that has failed stays failed until every touch in the sequence ends; `UILongPressGestureRecognizer` reports `.changed` after `.began` with movement unbounded after recognition and `allowableMovement` applying only before it; web `click` is not delayed and `dblclick` follows the second `click`; Safari's `gesture*` events and Chromium/Firefox `wheel` with `ctrlKey` are the trackpad pinch signals; AppKit's recognizer classes and `magnify(with:)` / `rotate(with:)` / `smartMagnify(with:)` exist; SwiftUI's public combinators are `simultaneously(with:)`, `sequenced(before:)`, and `exclusively(before:)`, and `@GestureState` resets on end. Pre-iOS 18 SwiftUI ran its own gesture system. iOS 18 added `UIGestureRecognizerRepresentable`.

Unsure, agreeing with the RFC where it is unsure: the exact cadence of `shouldRequireFailureOf` / `shouldBeRequiredToFailBy`; UIKit's pan hysteresis, multi-tap interval, and `delaysContentTouches` delay; how far iOS 18's unification goes and how SwiftUI lowers `sequenced`; whether AppKit's delegate methods match UIKit's one for one. I lean to three further calls the RFC leaves open. A `UIPinchGestureRecognizer` with one finger stays `.possible` until the touch ends, so `require(toFail:)` on it stalls a one-finger pan. A pan whose touch count exceeds `maximumNumberOfTouches` fails rather than ignoring the extra finger. Setting `state` on a subclass that has no touches does not run the touch-delivery relationship pass. Touch Accommodations rewrite the stream before the app, so a raw-touch engine still sees them.

## Concerns

**BLOCKER — Discrete `exclusively` changes the outcome, not the timing.** One tap, then a second inside the system interval: the web dispatches `press`, `press`, `dblclick` (`llp/1057` §4; `host/web/glue.js:492-498`). UIKit `require(toFail:)` dispatches only the double tap (`DevMenuIOS.swift:53` is that pattern). macOS already drops the second `press` (`NodeViewMac.swift:1433-1443`). §6 defines `exclusively` of a discrete leader as that wait, and §12 still says C gets the same outcome on every host. The summary's exclusion of timing does not cover this. Which actions run is the outcome.

**BLOCKER — The examples are not the reopen trigger.** Parent §10.7 (`llp/1057:817-828`) reopens composition only when a v1 consumer has two authored recognizers that `touch-action`, the precedence table, and the one built-in pan/pinch pair cannot express. The photo is that built-in pair plus a double tap (`§10.2` items 5–6). Reorder is already `ReorderIOS.swift:9-50`. An any-direction fling is the parent's closed `panrelease`. `rules/DEFERRED.md:258-261` and `:70-71` still refuse the arena and compositions. Adopting C now reverses that without the trigger.

**BLOCKER — §11 does not qualify as one-in/one-out.** `rules/DEFERRED.md:348-351` requires something off the doing-list. The take deletes the four arbitration sites and the recognizers the new graph replaces. That is the implementation of the feature being added. No admitted consumer is given up. Q6 is right that this is capability, and the consumer bar admits consumers.

**MATERIAL — Continuous `exclusively` is a race, and the suite cannot see it.** §6 refuses `require(toFail:)` for a continuous leader and substitutes "B may begin when A is not `.began`/`.changed`". The winner is whichever threshold fires first. UIKit's hysteresis is undocumented; the engine would use its own slop. `recognize magnify 1.4` (`§10.2`) skips that race. One combinator name then means two relations. The algebra should have one meaning on every host.

**MATERIAL — The UIKit failure rules the RFC relies on are real, and one of them already crashed a phone.** A failed recognizer stays failed until all touches end, so two recognizers for `sequenced(longPress, drag)` drop the drag if the pan hits slop first. The one-recognizer `UILongPressGestureRecognizer` lowering is mandatory (`ReorderIOS.swift:35-50`). `require(toFail:)` uses the delayed-touch queue. `DevMenuIOS.swift:47-49` records an iOS 26.6.1 crash on a phone, which is why those recognizers set `delaysTouchesEnded = false`. A spike that only injects `.recognized` does not exercise that queue.

**MATERIAL — Derived `touch-action` breaks the reorder example.** `ReorderIOS.swift:1-4`: the list's pan wins until a long press recognizes, unless authored `touch-action` already removed that axis. §4.2 compiles `drag(axis: y)` to `pan-x` for the whole node, so a finger on the handle cannot scroll. §6.3 keeps the scroll view outside the graph and decides it only with that static claim. The same claim is what A, B, and C use for scroll. C does not buy a native scroll relationship the table lacks.

**MATERIAL — `press` is outside the algebra, and the default edge is the wrong one.** `press` is `touchesBegan`/`touchesEnded`, cancelled when a pan begins (`NodeViewIOS.swift:1372-1408`). Child `press` against a parent drag is how rows with buttons swipe today. §6.2's default "innermost wins" (`llp/1057` §10.2 item 3) gives the button the touch and the parent drag never starts. There is no attachment modifier (`gesture` / `highPriorityGesture` / `simultaneousGesture`). Mixing `tap(count: 1)` with `press` on one node is refused, and the cross-node case is unspecified.

**MATERIAL — The Contract surface does not cover the examples as written.** The grammar allows clauses only on primitives (`§4.2`), but `sequenced(longPress(), drag(axis: y)) label "Move"` puts `label` on a combinator. `on end` is per primitive, while §6 says a simultaneous group's phase begins with the first and ends with the last. A pinch that ends on the first finger-up would fire `releaseZoom` and reset `follows scale` while `drag` is still live. LLP 1002 D4's photo path takes translate and scale atomically (`begin_transform_hold`, `motion/src/engine/hold.rs:103`). Two independent follows drop that. Example 2 still calls `reorderMove` per move (`ReorderHold.swift:122-131`), so "no per-frame runner work" is false for that example.

**MATERIAL — The suite does not prove UIKit, and the Apple fallback puts the arena back.** Cases are winner set, phase sequence, and payload shapes. They omit failure delay, stuck-failed, nested `press`, scroll steal, cancellation, and velocity values. LLP 1035.003 D5: UIKit's clock is not seekable. D1 allows one contact and refuses a second `down`. D7: the driver does not fake an outcome. §12's escape, "that shape runs on the engine on Apple", is a Rust arena on Apple, which §11 still refuses.

**MATERIAL — Bundle and latency claims are aimed at the wrong place.** LLP 1047's roster (~72 KiB wasm and 37 KiB JS for motion, 11 KiB JS for drag) is what A stays inside. A `Gestures` use-bit matches D1/D2/D6, and plans without `gesture` can pay zero. Today's recognizers live in after-paint `motion-glue.js` (`llp/1047:799-812`). An engine linked into `app.wasm` sits on the download the press waits for. "First pixel: no change" leaves time-to-interactive uncounted. 1.5–3K lines and 10–20 KiB brotli is an estimate, as §15 says. Per-sample wasm at 120 Hz also drops the web pan's one-dispatch-per-frame coalesce (`host/web/input-glue.js:51-72`).

**MATERIAL — The comparison tilts toward C.** "What A can't say" includes a single double-tap rule, a closed long-press-then-drag, `panrelease`, and a hold instead of a per-frame `pan` commit (`runner/src/runner/event.rs:175-177`, LLP 1043.000 D8). Those are closed recognizers and the existing hold model (`motion/src/engine/hold.rs:192-279`). They do not need three combinators. Scroll is `touch-action` for all three designs. C's actual gain is participation in UIKit's relationships with text, interactive pop (`NavigationIOS.swift:347-371`), sheets, and swipe actions.

**MATERIAL — One citation is wrong, and macOS photo feel is outside the algebra.** `glue.js:373`, `:388`, `:567`, and `:581` force `touch-action: none` for GPU `data-action`, not for a drag binding. Arrange does force it at `motion-glue.js:812`. Transform calls `preventDefault` on pointerdown (`motion-glue.js:439`) and does not set `touch-action` there. Two-finger trackpad scroll over a zoomed photo, which is what Preview does, is open question 4. The algebra has no production for it. A web `magnify` listener on `wheel` has to be non-passive or the browser zooms as well. Firefox uses the same `ctrlKey` convention as Chromium.

**MINOR — Small citation and scope nits.** `mouseDown` offers swipe at `NodeViewMac.swift:1368`, one line past the citation; `mouseUp`'s swipe is `:1431`. `VelocityTracker` is a field of `Hold` (`contact.rs:32`), consumed at swipe release (`:458`), not a field of `Contact`. `dblclick` sets `delaysTouchesEnded = false` (`NodeViewIOS.swift:248`), so the first `press` is likely delivered; the second `press` is the open part. `host/apple/ios/touch.swift:271` is another `require(toFail:)`, in the crash probe, not the presenter. Inline links also implement `accessibilityActivate` (`TextInteraction.swift:126`). `Bridge.swift:123-158` is mutating `exact_dispatch`, not a pure query. A delegate answer needs its own non-reentrant C function. The web "arbitration order" is independent listeners plus the browser. "Apple moved from B to C" is an inference from the iOS 18 bridging API. RULES scope: this has no implementer and no date.

What did check out: 37 handlers (`contract/analyze/src/lib.rs:381-419`); no phase on input events; 13 `TouchAction` values and no `pinch-zoom` (`kernel/tables/schema.json:986-1002`); `TransformRelease.vscale` "primary pan supplies zero" (`event.rs:214-215`); `dispatch` runs one action (`event.rs:675-825`); `VelocityTracker` 100 ms and 16 samples (`motion/src/velocity.rs:13-15`); Motion and Drag from plan bytes (`runner/src/uses.rs:19-37`, `:138`, `:162-165`); every authored pan has `maximumNumberOfTouches = 1`; node `gestureRecognizerShouldBegin` is `NodeViewIOS.swift:177-196`; the scroll view intersects `touch-action` (`:41-58`, `:152-160`); the only product `shouldRecognizeSimultaneouslyWith` is the swipe-actions observer (`SwipeActionsIOS.swift:142`); no `NSGestureRecognizer` or `magnify(with:)` under `host/apple/Sources`; Linux candidate order and 4 px slop (`contact.rs:236-241`, `:280`, `:305`); no pinch (`presenter/transform.rs:1`); no multitouch slots (`input.rs:108-111`); the 64 px / 0.2 knee in `motion-glue.js:575-576`, `GestureHold.swift:24-36`, and `presenter/swipe.rs:8-22`.

## Suggestions

1. Do parent §10.6 phases 0 and 1 only. Write the precedence table, align AppKit (`NodeViewMac.swift:1364-1431`) and Linux (`contact.rs:236-241`) to it, add `pinch-zoom`, and use `VelocityTracker` where the platform supplies no velocity. Add pinch as a second native recognizer on the existing transform binding, simultaneous with its pan. Keep phase 1 as host code. A hard-coded proto-graph commits to C's IR before the gate.
2. On macOS, map trackpad `magnify(with:)` to that binding, and map two-finger scroll to pan when the photo is zoomed. Leave `NSMagnificationGestureRecognizer` off if `magnify(with:)` is installed.
3. Make the double-tap rule the web rule on every host, including fixing macOS so the second click also dispatches `press`. Ship `tap … pinch` as a form of `tap` with `recognized` delivery on iOS. Leave LLP 1035.003 D1's one-contact rule in place.
4. If a later consumer actually hits §10.7, specify one `exclusively` meaning, attach clauses to any expression, define simultaneous end as "all members ended", and keep translate+scale on `begin_transform_hold`. Derive no scroll claim from a drag sequenced behind `longPress`. Keep child `press` as "the pan wins only if it begins".
5. Split tests. Graph cases belong in `cargo test` under the virtual clock. UIKit proof is real touches on a simulator and a phone, async, and not a sixth blocking check. If a shape fails, it stays a closed recognizer.
6. Name an implementer and a date before any of this becomes a spec. Keep the RFC out of `llp/current/` until phase 0 is the work in hand.

## Answers to the open questions

1. **The trade.** No. Deleting the code the new design replaces is not taking an item off the doing-list. Composition stays refused until a named consumer meets §10.7 and the same change removes a real doing-list item. If nothing can come off, the answer is no.
2. **Double tap.** The web rule binds everywhere: `press`, `press`, `dblclick`, with no wait. A delayed single tap is a different outcome. It also reopens the delayed-touch queue that crashed a phone. Refuse that form until a phone proves a safe `delaysTouchesEnded = false` arrangement, and keep it out of the default.
3. **Continuous `exclusively`.** A race is not an acceptable definition. Refuse continuous leaders at compile time on every host. Ship strict fail-first only if every host can implement it, which UIKit's delegate model does not for a pinch that stays `.possible`.
4. **Trackpad pan.** For the photo binding, two-finger scroll should pan when zoomed. That is a closed behavior of that binding, the way the built-in pan/pinch pair is. It should not become a primitive, and it should not wait for the algebra.
5. **Accessibility payloads.** Authors name a separate action. `releaseCard(±large, 0, 0, 0)` depends on threshold logic the compiler cannot invert. Discrete `on end` leaves can dispatch an empty payload. A path or multipoint leaf needs an authored control, as the Fit and 2× buttons already are (`apps/interaction-gallery/app.contract:304-307`).
6. **Scope.** Readiness, not a new consumer. Photo zoom, reorder, and the sheet are already admitted. Pinch on the photo binding is the bounded work those consumers need. Unlimited composition is not.

## Verdict

**ACCEPT WITH CHANGES.**

Accept phases 0 and 1 of design A, with the double-tap rule fixed to the web's and with macOS trackpad pinch and zoomed-scroll pan included. Do not accept the algebra, design C, the §11 trade, or the claim that C preserves native feel and identical outcomes.

## Bottom line

exact2 should pursue design A now, in the parent's order: one precedence table, AppKit and Linux aligned to it, `pinch-zoom`, one velocity estimator, then a native pinch on the existing photo binding. Design C should wait until a real app has two authored recognizers that the table, `touch-action`, and that one built-in pair cannot express. At that point the shared Contract surface can be built, proved with the Rust engine on the web under the virtual clock, and only then tried against UIKit's delegates with real touches. If that spike fails, the closed native recognizers stay. A Rust arena does not move onto Apple to paper over the gap.
