1. **Android’s publication can land well into a scroll.** [D7](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:294) checks the main thread’s latest report, then claims the race is confined to the scroll’s first frame. But [Owner publishes asynchronously](/Users/admin/Developer/exact2-timer-wait-points/host/android/canvas/src/main/java/dev/exact/canvas/Owner.kt:368), and [ExactView applies queued publications](/Users/admin/Developer/exact2-timer-wait-points/host/android/canvas/src/main/java/dev/exact/canvas/ExactView.kt:514) later. Android documents that each looper has its [own Choreographer](https://developer.android.com/reference/android/view/Choreographer); there is no cross-thread frame-order guarantee.

   A quiet report permits a release; a drag starts while Owner constructs the publication; construction takes 50 ms; the publication reaches the main thread several scroll frames later. A publication acknowledgement describes completed work—it cannot reserve future quiet time. Likewise, Messages’ [asynchronous `pulse`](/Users/admin/Developer/exact2-timer-wait-points/apps/messages/app.ts:65) can return during a subsequent fling even if its timer started outside one.

   **Instead:** Distinguish action admission from UI publication. A promise about keeping batches out of scrolling needs ordered publication admission on the UI thread. Otherwise explicitly limit the guarantee to starting the timer’s synchronous work and remove the one-frame bound.

2. **Release and ordinary advancement have no defined relative order.** [D4](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:175) sends precise timers through ordinary advancement, while [D6](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:233) releases held timers separately. Neither says which happens first at a wait point. Today, the [runner](/Users/admin/Developer/exact2-timer-wait-points/runner/src/runner/advance.rs:291) and [Lean](/Users/admin/Developer/exact2-timer-wait-points/semantics/Contract/Runtime.lean:1090) select work through one ordering procedure.

   Suppose gated timer A is held from 50 ms, precise timer B disables A at 100 ms, and the host next runs at 120 ms when scrolling ends. Advance-then-release cancels A; release-then-advance fires A. Both satisfy the draft. Expired caps introduce the same problem.

   **Instead:** Require due precise work and expired caps to be processed before testing release conditions, then specify how released actions interleave with their `then`/`next` continuations. Also specify the ordering key when distinct deadlines round onto one virtual frame.

3. **The web heartbeat introduces an implicit escape from an uncapped scroll wait.** [D3](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:152) promises that omitting `max=` opts out of running mid-scroll. Yet [D7](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:270) treats a missing animation-frame callback as stopped rendering and counts observed scrollers as empty. Chromium explicitly supports [scrolling independently of main-thread work](https://developer.chrome.com/docs/chromium/renderingng-architecture).

   During an observed fling, block the main thread for slightly over one second. If the overdue watchdog runs before the next rendering update, it releases the timer while compositor scrolling continues. The draft acknowledges this at line 319, but acknowledging it does not reconcile it with D3’s contract.

   **Instead:** Treat missing callbacks as unknown activity, not an ended scroll. Retain observed scrolling until an actual completion, removal, or confirmed visibility transition; use an explicit `max=` to escape uncertainty.

4. **Self-rekeying repeats reintroduce an already-overdue next firing.** [D4](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:170) reschedules after callback completion, but its gated-task paragraph rearms changed keys from the commit’s time. Existing code explicitly distinguishes these cases: a repeat rekeyed by its own callback restarts from [completion](/Users/admin/Developer/exact2-timer-wait-points/runner/src/runner/advance.rs:593), with a [dedicated regression test](/Users/admin/Developer/exact2-timer-wait-points/runner/tests/it/live_timers.rs:184).

   An `every(100, …)` released at 1,250 ms changes its own key and completes at 1,370 ms. The draft’s key rule gives 1,350 ms—already overdue—while existing behavior gives 1,470 ms. Immediate advancement and release can therefore run it again without the intended interval.

   **Instead:** Preserve the explicit three-way rule: cancellation stays cancelled; an unchanged repeat keeps its phase; a repeat that rekeys itself starts its new interval at completion. Rekeying by another commit can retain that commit’s time.

5. **`update` cannot promise passive frame reuse using D7’s predicates.** [D2](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:103) promises never to cause an otherwise unnecessary frame. D7 infers future frames from animation state, scrolling, or recent callbacks. These are insufficient: the [Web Animations specification](https://drafts.csswg.org/web-animations-1/#play-states) expressly permits `playState === "running"` with zero playback rate.

   On an otherwise still page with such an animation, the busy branch is selected despite no motion. Requesting an animation frame creates the opportunity the policy promised only to reuse; requesting none leaves the timer waiting for its cap. A scroll stopping immediately after its latest report produces the analogous race.

   **Instead:** Define portable `update` as reusing an already scheduled Exact callback, otherwise running immediately. If broader platform observation is essential, describe it as a best-effort hint rather than a passive guarantee; `frame` already supplies the simpler explicit request.
