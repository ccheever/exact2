1. **BLOCKER** — `apps/design-tool/app.contract:2311` (condition is `r.set` from `components.ts:85`). The "still wins" clause is shown whenever the app has a param line. B2-levels only stops on that line when its value is not a bare reference (`contract/cli/src/tamber_levels.rs:148-184`).

   Scenario: package param `Pill.fill` defaults to `accent.soft`. The app sets `accent.soft = #ff0000` and `Pill.fill = accent.soft`. `reaches.app_set` is true and `set` is non-null, so the note says the app's own value of this param still wins. The walk does not stop at the param line. Tuple 0 wins as `app-token` / `accent.soft`. After Back to the package, the same walk ends at the package's `accent.soft`, and the color changes. The same lie holds for one `when` branch that names the token while tuple 0 is a literal (`level` is `app-param` and `levelVaries` is true). The clause is true only when every tuple's winner is `app-param`. The contract fixture uses a literal `#ff0000`, so it never sees this.

2. **SHOULD-FIX** — `apps/design-tool/app.ts:732-740`. The per-param `resolve` runs after `readDesign` has already checked digests (`app.ts:105-146`), and it does not use that check.

   - Which params: package components only, and only while the app design is open and `describe`'s `files` lists a `.contract`. That matches `fromPackage` in `components.ts:123`. App and `app.tamber#…` components are skipped. Cost: one `resolve` per package param, on the path that returns the grid, all at once. `readDesign` caps in-flight resolves at 4 (`RESOLVES_AT_ONCE`, `app.ts:44`) so the long poll keeps a connection. This `Promise.all` does not.
   - A failed resolve (`r.error`, no tuples, or `level` not a string) drops that param's line and does not fail the read. An old server with no `level` stays quiet. A real failure looks the same.
   - Stale read: these calls ignore `number === issued` and the reply's `files`. Scenario: `describe` shows `Pill.fill` unset and `app_set` false. A write lands `params` `Pill.fill = #ff0000` before the param `resolve` returns. The row still has no Reset, and the words say "wins: set for this app". An overtaken read keeps issuing those resolves for up to `READ_WAIT` after the runner has dropped the answer.

   - First tuple versus the selected column: the words are always `tuples[0]`, not `selColumn`'s tuple (`branches.ts:11-24`, id `` `${tuple}-light|dark` ``). `varies` is any later tuple whose `level` or `name` differs.
