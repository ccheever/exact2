**Blocking**

1. `host/linux/src/image.rs:448` (with `host/linux/src/image/workers.rs:164` and `host/linux/src/image/workers.rs:253`). A retry removes that source id from the process-wide index, but every other view of the same URL still holds the id. `Backend::source` finds an in-flight or failed download by generation and name, so the transcript proxy and the viewer underlay are one `SourceOwner`. `prepared` looks the id up in the index and returns `None` after `evict`, and `Images::poll` treats that as "not ready yet" (`image.rs:490`) and never resolves the name again. A view only notices on its own later retry. A view with no `retry_at` never does: leaving the screen or sitting under the photo route clears `retry_at` (`image.rs:320`) and keeps `source_id`. Opening the viewer, failing the proxy, and retrying the thumb therefore unhooks the transcript image; when the route is shown again it stays blank. The same gap stalls a second on-screen copy until its own backoff (up to 30 seconds) even after the replacement download has finished. `pending` treats that missing id as work still in flight (`image.rs:692`), so `wait` / `wait_images` run out the clock. On a miss from the index, drop `source_id` without incrementing `retries` and let the existing `source()` call join the replacement. Keep `evict` so the retry does not attach to the failed owner again.

2. `host/linux/src/image.rs:302` (also `image.rs:333` and `image.rs:362`), `host/linux/src/presenter/images.rs:23`. `retry_at` is cleared when the picture hides or its source string changes, but not when `sync_visible` drops the source and returns early: a `symbol:` source, a package picture, or a source longer than 4096 characters. `poll` skips those views, so a deadline that is already due stays due. `retry_due_in` (`image.rs:698`) still reports it, `poll_images` marks the presenter dirty every call, and both `turn_due_ms` (`host/linux/src/presenter/delivery.rs:54`) and `wake_due_ms` (`host/linux/src/presenter/hatch.rs:569`) stay at zero. The desktop loop and the Android reader's `nextDue` then turn without sleeping. Clear `retries` and `retry_at` on those three paths, and ignore a deadline in `retry_due_in` unless the view is a visible remote picture `poll` will still service.

**Non-blocking**

1. `host/linux/src/image/workers.rs:164`. `urgent` is applied only when `source()` creates the load. A later fullscreen view of a URL that is already queued or running keeps that load's place and its 30 second whole-load bound. The viewer's distinct original URL is a new load and does get the front of the queue and 120 seconds. The same-URL case (the transcript already asked for `full`) does not, until that attempt fails and a retry creates a new load. If the existing job is still queued, move it to the front and extend `Load::whole` to the urgent deadline when that deadline is later.

2. `host/linux/src/presenter/hatch.rs:569`. Retry deadlines are `Instant` (wall). `wake_due_ms` adds the relative delay to `host.now()`, which lags the display's wall clock until the next `advance`, so the desktop loop can wake once early and then sleep the rest. It does not spin on its own. Production Android `turn_due_ms` is already a relative delay and matches the reader's wall sleep. Under the agent, a `clock` jump does not make a retry due, and the reader's `nextDue` can still wake a wall-clock retry between commands. Drive the retry off the same clock the turn uses, or document that agent time does not.

3. `host/linux/src/image/remote_tests.rs:591`. The single-view flaky and dead-URL tests match the backoff (six re-asks, then stop; off-screen resets the count). They never show the dead URL again, never build two views of one name, and never read `turn_due_ms` / `wake_due_ms` or `Policy::urgent` (the queue test only checks order). The Excord test matches the fixture: `cafe.png` at 640×640 is not resized, so `viewingThumb` stays `""`; the harbor attachment at 540×1920 is resized, so the underlay is present. iOS zoom still resolves `navigationSource` to the full image's `id` (`photo-…`); the underlay has no id. The thumb is `aria-hidden`, and the column plus the full image keep the label. A thumb that fails or arrives after the full image stays behind it, so it cannot cover a picture that has already landed.
