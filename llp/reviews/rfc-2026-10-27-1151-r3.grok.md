## 2. Remaining fundamental issues

**1. D4's `clock settle` expansion is a different operation from the driver's.**

The host settle runs first: on Linux it waits for replies, seeks to the end of in-flight motion, and advances, so timers already due fire (`host/linux/src/agent.rs:1133-1164`). The driver's follow-up is `nextCommitTasks`: every task with `now < at && at <= now + 1`, whoever armed it, one-shot or not (`scripts/agent-inspect.mjs:883-888`). If any remain and the round is under 16, it clocks to the absolute time of the latest and calls `clock settle` again (`scripts/agent.mjs:1153-1154`). A task that re-arms `after(1, …)` is followed for those 16 rounds (`scripts/agent-inspect.mjs:891-894`). D4 instead starts at `land` (timers off) and continues only for a one-shot task the last commit armed (`llp/1151-properties-beside-the-app.rfc.md:350-354`). A task armed by a tap, then followed by `clock data`'s `then`, is still inside the driver's window and outside that filter. `tap` / `clock data` / `clock settle` is a real test shape (`apps/excord/typing.test.contract:12-14`). Expects after `clock settle` would be judged in a state the driver does not produce. That is the failure r2 named for this step.

Smallest change: write the expansion as the driver's loop. Under this oracle the host settle is an advance to now, then while any task has `now < at <= now + 1`, advance to the latest such time and repeat, 16 rounds. Drop "one-shot" and "the last commit armed". Say motion, scroll, hatch, and in-flight waits are the host's and have no image here.

**2. The cone rule cites an analysis that does not compute the cone.**

`dependencies` records only other derive names (`contract/syntax/src/inline/derives.rs:318-327`). A call head is not a derive, and a call's body is not walked (`derives.rs:319`, `derives.rs:463`). The slot walk that does exist ignores `pending(` (`contract/analyze/src/calls.rs:269-270`). A derive whose body calls `performanceNow()`, `pending`, `failed`, `failure`, a resource, or an `fn` that does any of those, is invisible to the cited compiler fact. §R says the reads are closed under derives and `fn`s (`llp/1151-properties-beside-the-app.rfc.md:24`). Built as cited, the rule admits the derives it was added to refuse, and a device `always` line then tracks the clock or the oracle.

Smallest change: specify a walk of the derive body, the bodies of the derives it names, and `fn` bodies, refusing a resource call, `pending` / `failed` / `failure`, `performanceNow()`, and a geometry read. Delete the claim that `derives.rs` already knows this.

**3. `land` cannot be both `land_then` and the Lean `then`/`next` slice.**

`land_then` is `advance_within(now, timers: false)` (`runner/src/runner/advance.rs:206-208`). With timers off it still commits a transport or MIDI answer (`advance.rs:369-377`), a re-ask (`advance.rs:534-549`), and then wakes (`advance.rs:240-252`). The tail can also commit presence, a module poll, live times, and text-axis frames (`advance.rs:722-793`). D4's Lean variant takes only the `then` and `next` branches (`llp/1151-properties-beside-the-app.rfc.md:344-349`). D3 says the extra kinds print no `ran` line and the receipt counts them (`llp/1151-properties-beside-the-app.rfc.md:316-318`). A transport answer changes the runner's configuration. The semantics' configuration does not move with it, so the corpus comparison fails. Counting a missing `ran` line does not keep `difftest corpus` green.

Smallest change: pick one. Either the Lean `land` performs the same commits `land_then` performs, or the harness `land` is the `then`/`next` slice and a transport, MIDI, re-ask, wake, presence, or poll commit is a divergence the receipt names. The sentence that it is `Runner::land_then` and the sentence that the variant takes only `then` and `next` cannot both stand.
