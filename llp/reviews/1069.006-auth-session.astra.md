## Review (verbatim)

The narrow host request and source-owned OAuth protocol are a good architectural fit, but **r2 is not ready to build**. Its PAR flow omits information required by its own callback checks, the web callback mapping happens at an unspecified—and potentially too late—point, and the popup design assumes an opener relationship that COOP can destroy. The first-consumer protocol also needs corrections around DPoP, issuer/account binding, and refresh. I reviewed `ed59545d`, the dependencies, cited code, the sibling Bluesky checkout, and primary platform/specification sources without editing files. These issues are fixable while retaining the owner’s principal rulings.

1. **BLOCKER — PAR hides the `state` that the host and substitute are supposed to check.**

   [D1’s request body](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.006-auth-session.rfc.md:80) contains only `url`, `callback`, and `ephemeral`. Its authorization URL contains `client_id` and `request_uri`. Nevertheless, D4 compares the callback’s state with “the request’s,” and D7 substitutes `{state}` and inspects PKCE parameters in that URL. With PAR, those parameters were sent to the authorization server earlier; they need not appear in the browser URL. [RFC 9126 §§2, 4](https://www.rfc-editor.org/rfc/rfc9126.html)

   Pass the expected state explicitly in the reserved request body, or redesign the host/source checking boundary explicitly. Require a nonempty, single state value and reject mismatches. The source should independently validate its transaction. Test PKCE parameters in the pushed request, not the launch URL. The substitute must use the same explicit expectation.

2. **BLOCKER — The effective callback must be available before PAR.**

   [D2 maps a native callback to the web callback](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.006-auth-session.rfc.md:146), but the source constructs PAR before calling `openAuthSession`. A host-side rewrite cannot change the `redirect_uri` already bound into a pushed request. The registered URI, PAR URI, token-exchange URI, and host expectation must agree. [RFC 9126 §2](https://www.rfc-editor.org/rfc/rfc9126.html)

   Expose the platform’s effective callback to the source before preparing authorization. Pin the actual client metadata, including public-client authentication, application type, redirects, grants, scopes, and DPoP declaration. AT Protocol ties native custom schemes to the reversed **client-ID hostname**, not an arbitrary reversed bundle ID; its localhost workflow also needs separate treatment. Demonstrate that the proposed shared native/web client metadata satisfies those constraints. [AT Protocol OAuth, Clients and Authorization Requests](https://atproto.com/specs/oauth)

3. **BLOCKER — COOP can break both popup completion and cancellation detection.**

   [D4](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.006-auth-session.rfc.md:181) requires `window.opener` and interprets `popup.closed` as user cancellation. A provider’s COOP policy can separate browsing-context groups, sever the opener, and make the original window reference appear closed although authentication remains visible. Returning to the application’s origin does not recreate that relationship. [HTML, Cross-origin opener policies](https://html.spec.whatwg.org/multipage/browsers.html#cross-origin-opener-policies)

   Specify an authenticated return channel that survives this, or explicitly limit supported provider/browser combinations and define bounded failure for unsupported ones. Test the first consumer with COOP transitions; do not turn isolation into a misleading 499 cancellation.

   **Touches ruling Q4:** the resolution must preserve no redirect fallback. Tapping again does not repair a severed opener.

4. **BLOCKER — “Check `state` and `iss`” does not define the necessary transaction and account binding.**

   [D6](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.006-auth-session.rfc.md:222) saves a verifier and state but does not specify the saved issuer, client, callback, endpoints, or expected account. An `iss` check must compare the decoded response value against the issuer selected **before opening**, before exchanging the code; it must also handle missing values and error responses. Selecting a token endpoint from the returned `iss` defeats that protection. [RFC 9207 §2.4](https://www.rfc-editor.org/rfc/rfc9207.html#section-2.4)

   Define a transaction record bound to state, with expiry and single-use consumption. AT Protocol additionally requires verifying DID/PDS/issuer authority and the returned `sub`; checking state and issuer alone does not authenticate the expected account. [AT Protocol OAuth, Identity Authentication](https://atproto.com/specs/oauth)

   Require negative cases for missing, duplicate, mismatched, expired, and replayed parameters and a wrong-account token response. Specify PKCE precisely: base64url-encode 32 random octets, then hash the ASCII verifier string. [RFC 7636 §4](https://www.rfc-editor.org/rfc/rfc7636.html)

5. **BLOCKER — DPoP starts too late, and the proposed refresh procedure is wrong.**

   [D6 steps 3–4](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.006-auth-session.rfc.md:230) describe plain PAR followed by DPoP on token/resource requests. AT Protocol requires initiating DPoP at PAR and handling server nonce challenges. [AT Protocol OAuth, DPoP](https://atproto.com/specs/oauth)

   Generate and retain the session key before PAR. Specify proof fields, public JWK, seconds-based `iat`, `htm`, `htu`, resource-token `ath`, and bounded nonce retries with fresh proofs. Track authorization-server and resource-server nonces separately where necessary. [RFC 9449 §§4–9](https://www.rfc-editor.org/rfc/rfc9449.html)

   [Step 7](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.006-auth-session.rfc.md:242) cannot reuse the port’s refresh protocol: [the existing function](/Users/ccheever/projects/bluesky-exact2/data/src/session.rs:141) calls an XRPC endpoint with a Bearer refresh token. OAuth refresh uses the authorization server’s token endpoint and `grant_type=refresh_token`, with the original DPoP key. Serialize refreshes and persist replacement tokens coherently; AT Protocol refresh tokens generally rotate. [AT Protocol OAuth, Tokens and Session Lifetime](https://atproto.com/specs/oauth)

6. **BLOCKER — Real authentication can be combined with deterministic credential entropy.**

   [LLP 1069.005 D2b](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.005-web-crypto-in-sources.rfc.md:247) replaces `getRandomValues` with a launch-seeded stream, default seed 1. [LLP 1069.007 D8](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.007-device-capabilities-in-the-agents-hands.rfc.md:291) separately enables real sheets through `--device real`. Nothing connects that override to secure entropy. This contradicts D6’s explicit prohibition on launch-seeded verifiers.

   Make deterministic authentication fixture-only, or require OS entropy whenever real authentication/network credentials are permitted. Browser substitution alone does not substitute discovery, PAR, or token fetches: [the web executor still performs fetches](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/host/web/http-body.js:58).

   Synthetic state, challenges, and request URIs may intentionally appear in `state.pending`; real verifiers, codes, keys, and tokens must not. **Touches the dependency’s deterministic-agent ruling**, requiring an explicit boundary for real authentication.

7. **MATERIAL — The private-scheme safety explanation is false, and full callback validation needs an explicit implementation rule.**

   [D2:143–145](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.006-auth-session.rfc.md:143) incorrectly says leaving a scheme unregistered prevents another app from claiming it. It reserves nothing. ASWebAuthenticationSession’s session-specific delivery and PKCE provide the relevant protections; custom schemes are not exclusive ownership claims. [Apple’s session documentation](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession), [RFC 8252 §§7.1, 8.1](https://www.rfc-editor.org/rfc/rfc8252.html)

   `.customScheme` matches the scheme, not the complete path. Therefore D3’s full-match promise requires host validation before its “URL is 200” branch. Specify exact callback-base comparison, including path, and rules for ports, fixed queries, fragments, and credentials. A wrong-path callback may already have terminated the Apple session; it must become a failure, not a successful response or navigation.

   Apply the same validator to web and substitute responses. Grant enforcement must also respect narrowed `Request.grants`, following [the existing surface-check precedent](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/runner/src/request.rs:163).

8. **MATERIAL — Claimed HTTPS needs a complete macOS entitlement/signing path.**

   The `webcredentials:` requirement is **correct for this Apple callback API**; replacing it with `applinks:` would be wrong. The local SDK confirms both that requirement and iOS 17.4/macOS 14.4 availability. [Apple SDK declaration](</Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk/System/Cryptexes/OS/System/Library/Frameworks/AuthenticationServices.framework/Versions/A/Headers/ASWebAuthenticationSessionCallback.h:10>)

   However, the cited [entitlements function](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/host/apple/build.mjs:425) reads `host.ios`, while [macOS signing](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/host/apple/build.mjs:1097) supplies no entitlements file. Specify the macOS derivation/signing work, AASA `webcredentials` application identifiers, and applicable provisioning requirements. Distinguish session capture from ordinary universal-link/cold-start routing. Keep the explicit older-OS 501 behavior.

9. **MATERIAL — Window ownership and cancellation are new integration work, not inherited automatically.**

   [D3](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.006-auth-session.rfc.md:163) selects a node’s window—or a key window for workers—and promises cancellation when a ticket is forgotten. But [RequestOut](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/runner/src/request.rs:421) carries a target name, not a presenting window. Existing asynchronous [handoff](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/host/apple/src/executor_core.rs:543) supplies a reply without an authentication-session cancellation handle.

   Define ownership by ExactKit session, incarnation, ticket, and presenting window. Workers must not use another session’s currently focused window. Specify cancellation on supersession, removal, reload, teardown, and window closure; suppress late completions exactly once. Cancel and release the superseded session before applying the one-per-window gate, so replacement does not incorrectly receive 409. Include equivalent popup/listener/poll cleanup.

10. **MATERIAL — The web message and callback-page contract is insufficiently constrained.**

    [D4:184–191](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.006-auth-session.rfc.md:184) should require the saved application origin as both target and accepted sender origin, the owned popup as `event.source`, a typed message, the exact callback base, and a live transaction. Origin plus state should not silently authorize a different tab. Names “per ticket” also need incarnation isolation: [tickets restart at one](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/host/web/glue.js:884).

    Specify how the exact registered path is served without a trailing-slash redirect or application-router fallback. Keep the page free of third-party content, apply referrer/cache/CSP protections, scrub the callback URL after capture, and handle delivery failure without printing it. Same-origin hostile script remains inside the web application’s trust boundary; these checks do not solve XSS. [RFC 9700 §§4.2, 4.3, 4.17](https://www.rfc-editor.org/rfc/rfc9700.html)

    The code-confidentiality promise also needs a source/error contract: successful [response summaries omit bodies](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/runner/src/request.rs:293), but failures retain message text. Never copy callback URLs into `Session.error`, logs, public carry, or inspection output. Scope “screenshots” to application inspection; browser chrome can briefly display the callback URL.

11. **MATERIAL — The ruled key locations still need a usable persistence and lifetime contract.**

    [LLP 1069.005 explicitly leaves “keep this key” unwritten](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.005-web-crypto-in-sources.rfc.md:186). The first consumer therefore lacks a defined cross-host operation for storing/loading/deleting its key, particularly from Rust/wasm on the web.

    Pin that operation and its grant, bind the key handle to the issuer/account/session and tokens, and prevent a new pending login from overwriting an active session’s key. Lost keys require reauthentication, not replacement keys used with old refresh tokens. Define cleanup and refresh coordination across tabs/windows.

    **Touches ruling Q3:** retain native JWK plus `secret.keep`, web non-extractable IndexedDB keys, and defer host-held keys. Clarify that non-extractability prevents private-byte export; same-origin script can still use the key. Web tokens remain in [origin-accessible localStorage](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/host/web/glue.js:634).

12. **MATERIAL — Saving the verifier does not make authentication resumable after process death.**

    [D6:228–229](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.006-auth-session.rfc.md:224) promises that a killed application can finish. Persistence does not recreate its ASWebAuthenticationSession, popup relationship, or request ticket. [LLP 1016 explicitly drops tickets on reload](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1016-async-data-settlement.rfc.md:233); the unregistered native scheme provides no separate cold-start route.

    Nor is `secret.keep` a durability acknowledgement: [Apple persistence failures are logged without failing the app](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/host/apple/src/host.rs:622), and web storage failures are similarly caught.

    Remove the promise and restart authorization after interruption, expiring abandoned transaction material. If recovery is required, specify its durable acknowledgement and callback-to-source routing explicitly; do not reintroduce credential-bearing navigation implicitly.

13. **MATERIAL — Preparing PAR early does not guarantee the second tap succeeds.**

    [D4:197–203](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.006-auth-session.rfc.md:197) overstates the result. The actual request path includes asynchronous source execution and [lazy HTTP-helper loading](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/host/web/glue.js:689). Browser activation is time-limited and consumable; a later batch is not itself an activation guarantee. [WebKit’s activation documentation](https://webkit.org/blog/13862/the-user-activation-api/)

    Define readiness, PAR expiry, and regeneration behavior. Test cold and warm paths through the real main/worker source arrangements in Safari and Chrome. Treat another blocked popup as a supported failure, not an impossible state. The parent survey already calls this [unmeasured](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069-expo-sdk-survey.research.md:600).

    **Touches Q4’s retry policy**, without requiring a redirect fallback.

14. **MATERIAL — D8 understates Sign in with Apple’s web requirements and overstates App Review policy.**

    [D8](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/llp/1069.006-auth-session.rfc.md:275) cannot describe the ordinary Apple web flow simply as D1: requesting name/email requires `form_post`, whose body a static page cannot recover from `location.href`. Code exchange also requires a developer-signed client secret that cannot safely ship in public app source. Mark the necessary provider-specific server handling and identity-token verification as future design work. [Apple authorization endpoint](https://developer.apple.com/documentation/signinwithapplerestapi/request-an-authorization-to-the-sign-in-with-apple-server.), [token validation](https://developer.apple.com/documentation/signinwithapplerestapi/generate-and-validate-tokens)

    App Review §4.8 requires an equivalent qualifying login option in applicable cases, with explicit exceptions—including clients for a specific third-party service. It does not universally mandate Apple login whenever another provider appears. Replace that claim, and remove the unsupported blanket rejection claim at line 69. [App Review Guidelines §4.8](https://developer.apple.com/app-store/review/guidelines/#login-services)

15. **MINOR — Correct remaining citations and qualify status/privacy semantics.**

    At this commit, [io_grants](/Users/ccheever/projects/exact2/.claude/worktrees/agent-a1304ffcbfa2279e2/runner/src/request.rs:20) strips only `surface.read` and `surface.write`; describe auth/device stripping as proposed work. The Bluesky `createSession` call is in [writes.rs:57](/Users/ccheever/projects/bluesky-exact2/data/src/writes.rs:57), and [signed_in.rs:34](/Users/ccheever/projects/bluesky-exact2/data/tests/signed_in.rs:34) is an in-process fake, not the network fixture server D7 implies.

[Apple’s authentication-session guidance](https://developer.apple.com/documentation/authenticationservices/authenticating-a-user-through-a-web-service)
