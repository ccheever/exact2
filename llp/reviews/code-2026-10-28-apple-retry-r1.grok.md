**Blocking**

1. `host/apple/Sources/ExactKit/RasterLoader.swift:739` — A held picture that leaves the screen and comes back by layout never retries and never gets its `error`. `hold` puts the view in the `parked` set (`:872`) but leaves `interest.parked` false. `resized` (what `NodeView.layout` calls) only wakes when that flag is set, then returns. A reflow that moves the frame into the window, including one that now fills it (`:738` only `urge`s), does not reconcile, and once the pending timer has already observed the view off screen there is no next ask. Scroll still works. Fix: if `interest.held`, `backend.wake()` from `resized` the same way a real parked view does, without setting `interest.parked` (that flag drops pixels and cancels the request).

2. `host/apple/Sources/ExactKit/RasterLoader.swift:211` — `RasterSource.urgent` is set and never cleared. `reset` (`:200`) keeps it, and the next `inspectOne` (`:227`) passes it into `fetch`. After any full-screen `urge`, every later download of that source — a retry after the view has shrunk, or a thumbnail that shares the URL — stays high priority with the 120 s bound. Linux recomputes this from the current box on each ask. Fix: clear `urgent` in `reset` (and at the start of a fetch). The reconcile that follows already calls `urge` when a live view `fillsScreen`.

3. `host/apple/Sources/ExactKit/RasterInput.swift:237` — `start` writes `urgent`, `task`, `asked`, and `done` on the raster worker, while `promote` (`:264`, queued at `:415`) writes those same fields on the session queue. `task()` publishes the download in the map before `self.task` is set, so a promotion in that window can set `task?.priority` on nil and then lose the write when `start` assigns the task. `start`'s later `arm` can also overwrite `urgent` back to false and re-arm the 30 s timer, undoing the 120 s bound. Fix: publish the task, read `urged`, set priority, and set `asked`/`urgent` on the session queue before `resume`, under the same lock `promote` uses. `promote` should only mutate a download that is already in that map.

4. `host/apple/Sources/ExactKit/RasterInput.swift:204` and `RasterRetry.swift:37` — A spool that fails `createFile` throws `RasterFailure.decode`, and `transient` returns false for every `RasterFailure`. That attempt is not retried and the `error` is `decode failed`. A write error or a `RasterSpool.file()` POSIX error does retry, and Linux treats every spool failure as transient. Fix: throw a non-`RasterFailure` (the POSIX error already used for the directory) from that `createFile` miss so `transient` keeps it.

**Non-blocking**

- `RasterLoader.swift:705` — `loadingOnScreen` treats `failure != nil` as settled, but `hold` sets `failure` while the ladder is still running. `waitForImages` / `settleForPicture` (3 s) return immediately, so a screenshot misses a retry whose first step is 1 s. A declined decode stays loading on purpose (`RasterLoaderTests`). Count an on-screen `held` interest that has not `announced` yet.
- `RasterLoader.swift:1228` — `setPaused` clears `held` and `retryWaiting` but does not `unpark`. If that source then loads without `askAgain` (pause cancelled the in-flight retry, another view finished it), the view stays in the watch set and the scroll observer never comes down. `retry` (`:809`) has the same hole. `unpark` whenever `held` is cleared.
- `RasterLoader.swift:1265` — diagnostics `"parked"` is the watch-set size, so an on-screen held picture counts as parked. The per-image `"parked"` bool is still the real flag. Split the counter, or document that the number is the watch set.
- `RasterInput.swift:417` — `urgedURLs` is removed on the first `finish` (`:271`) and inserted even when `promote` finds no live download (the in-flight one already finished). The URL can stay urged for the process lifetime, and the next download of it takes the long bound. Remove it only while a download of that URL is still in `downloads`, and do not insert when `matching` is empty.
- `RasterDownloads.cooling` (`RasterInput.swift:422`) drops expired rows only on the next `cool`. The map is capped at 256, so this is residue, not growth. Linux does the same.
- The whole-load deadline is `Date`-based (`RasterInput.swift:252`), so a wall-clock step moves it. Retry delays use `asyncAfter` (monotonic). Linux uses a monotonic clock for the bound.
- `RasterRetry.retryAfter` (`:51`) uses a lenient `DateFormatter`. Linux accepts only a strict IMF-fixdate and ignores a wrong weekday. A lenient parse can turn a garbage date into a real wait instead of the one-hour unreadable case.
- Tests: the new file is red before this commit (main has no ladder, no per-download bound, no URL memory). `testAPictureThatLeavesTheScreen…` calls `reconcile` itself, so a broken `scrolled`/`watch` still passes. Nothing asserts a single `error` event, or that `load` does not follow it. `testANon2xx…` matches the old 404 behavior.
- `docs/contract-for-agents.md:1719` lists network, timeout, 5xx, 408, and 429, and leaves out an empty body, the spool, a lookup, and TLS, which §4 and `RasterRetry.transient` both include.

Decode-decline, `cancel`, and a source change still retire the token, so a stale `asyncAfter` does not reset a new interest. An `error` is one `announced` settle after the six steps or a wait past five minutes; a non-transient failure settles immediately. `askAgain` will not `reset` unless `mayShow` is still true, so a timer does not download off screen, and six steps end the showing.
