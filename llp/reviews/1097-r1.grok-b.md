## MATERIAL

### 1. §4 risk, D3, D6 — the anti-spin sentence is the spin

**Problem.** Stage 1's first commit cannot prove the wait "cannot spin." The wait that exists returns as soon as the shared Ibex2 context is idle or any completion is queued, and D6 tells the runner to ask again whenever `background.storage > 0`. Those two rules, on the host pump that already dispatches a new continuation in the same turn, are a tight loop. `is_idle()` is not "this owner's queue head has landed," and a completion does not carry an owner.

**Evidence.** `Session::continuation` (`js/src/storage.rs:63–92`, not `:64–94`) returns a 204 as soon as `context.is_idle() || context.wait(25ms)` (`:77–82`). `Context::is_idle` is the shared queue empty, `in_flight == 0`, and no timer (`vendor/ibex/crates/ibex2/src/task.rs:728–731`). It cannot see a prelude FIFO. `wait` returns true when that shared queue is non-empty (`task.rs:273–282`). `admit` does `signal.notify_all()` (`task.rs:201`), so an answer's completion wakes the background waiter too. `Adapter::deliver_one` pops the head with `ibex2_take_task` and settles that promise id (`vendor/ibex/crates/ibex2/src/engine/ibex2_jsi.cc:1004–1015`). There is no owner. `Module::resume` ignores the bool (`js/src/lib.rs:1000`).

D6 then says `background_landed` returns the next round while `background.storage > 0`. D5 polls `background()` after every fulfill. Linux `executor.drain` is one completion per turn (`host/linux/src/executor.rs:93–96`); `pump` fulfills and `after_commit` → `service_commit` dispatches the new continuation immediately (`host/linux/src/presenter.rs:1348–1384`, `:764–799`). Apple does the same in `pump` then `emit` (`host/apple/src/abi.rs:298–332`, `:236–258`). An empty round whose Ibex2 context is idle returns at once, is fulfilled, and is re-enqueued on that same turn.

§4's "returns at once, and the runner does not re-ask until its owner issues again" contradicts D6. The fallback "a completion carries its owner" is not what `ibex2_take_task` does. The wasm realm does not spin this way: a continuation is `op: continue` (`host/web/src/batch.rs:547–553`), tracked at `host/web/glue.js:712–718`, and awaited. The bug is native Hermes.

**Fix.** Do not share `is_idle() || wait()` between two tickets. The first commit waits until this owner's completion is the one that can be delivered (filter `take` by promise id, or do not return while the head is another owner's). `background_landed` returns `None` when `deliver_storage_one` returns false. `background()` arms a ticket only after a new issue, and an empty fulfill does not poll it back into `take_requests()`. Delete the sentence that calls `is_idle()` "the queue's head has landed" (D3).

### 2. D5 — "like a Later" commits, and "no pending" lets the host drop the ticket

**Problem.** Routing the next round the way a `Later` that answers `Later` does violates D4.4 and D5: it commits, and a refused commit restores the ticket that already finished and drops the round just enqueued. Keeping the ticket out of `self.pending`, which the opening sentence calls "no `pending`", makes `holds` false, and both native hosts then let the I/O go.

**Evidence.** `fulfill_measured` checkpoints `pending`, then removes the ticket (`runner/src/runner/commit.rs:937–938`). `Answer::Later` logs "one more round", `enqueue`s, and returns `self.update()` (`:1036–1042`). `update` re-evaluates the tree and poisons on failure (`runner/src/runner/lists.rs:41–44`). On `Err`, `conclude` writes the checkpoint's `pending` back (`commit.rs:65–79`), so the removed ticket returns and the next round does not, and `forgot` makes `forgotten` run (`:85–97`). `enqueue` sets `forgot` whenever it replaces the same target (`:750–754`).

`holds` (`:900–902`) and `has_pending` (`:864–868`) scan only `self.pending`. Apple `executor.forget` uses `holds` (`host/apple/src/abi.rs:229`); Linux does the same (`host/linux/src/presenter.rs:772`). A ticket kept elsewhere is cancelled.

`progress += 1` does not call `wake`. The increment is at `js/src/lib.rs:873`, `:975`, `:1088` and `js/src/turns.rs:89`. `wake` runs from `dispatch` and `release` (`js/src/lib.rs:1163`, `:1186`). Hosts call `release_work` after the fulfill (`abi.rs:259`, `presenter.rs:801`, `host/web/src/host.rs:1041`). A path that "commits nothing" and skips that release leaves `WAITING` answers parked, which breaks D2.

Adding `Target::Background` does not compile until these matches grow an arm: `commit.rs` `target_name` (`:682–686`), `sync_pending_flags` (`:784–787`), `fulfill_inner` (`:1002–1005`, `:1048–1072`), `admission.rs` `release_refused` (`:57–62`) and `release_failed` (`:97–103`), `source.rs` `Target::text` (`:162–165`) and the pair at `:502`.

**Fix.** Specify a path in `runner/src/runner/background.rs` that does not call `fulfill_inner`. The ticket is one `PendingReq` in `self.pending`, so `holds` and `has_pending` see it, and it is absent from `pending_res` / `pending_mut`. Replacing it for the next round must not set `forgot` and must not be restored from a commit checkpoint. Say the host's existing `release_work` still runs after a background fulfill. List the matches above. One `Target::Background` is one slot: `enqueue` replaces the same target, and `Mixed` already maps continuations per child (`data/src/mixed.rs:841–848`). Stage 1 polls the JavaScript child only.

### 3. D7 — retiring the answer owner drops the completion this RFC is saving

**Problem.** D7 finishes the answer and adds a `background` owner that is never retired. It never moves the in-flight completion onto that owner before `retire`. The completion is keyed to the answer. `retire` deletes that queue. The write's promise never resolves, so D2's `saving.then(write)` never issues.

**Evidence.** `createStorage(win, admitted, () => context.owner)` (`host/web/module-glue.js:130`). Completions queue under `scope()` (`host/web/storage.js:53–56`). `finish` calls `storage.retire(context.owner)` whenever `answer.tag !== 1` (`module-glue.js:167`). `completion` drops the callback if `retired.has(owner)` (`storage.js:31–34`). `retire` runs each entry's cleanup and deletes the queue (`:110–116`). The same pair is in the worker realm, which D7 does not name: `host/web/module-worker.js:101` and the turn at `:116–129`.

**Fix.** Before `storage.retire(answerOwner)`, move that owner's queue onto `background`, and make later issues use `background` as `scope()`. Name `module-worker.js` in D7 and D11. The web test in §5 ("the realm's background owner surviving its answer's retirement") should assert the queued completion still runs, not only that the owner object remains.

### 4. D11 — the shared prelude cannot keep the worker's current rule while stage 1 moves storage off the answer

**Problem.** The prelude is one bytecode for every module, including a worker placement. Stage 1 moves unawaited storage onto `background` and the §4 table says `Placed` forwards both methods. D11 says a worker-placed module keeps today's rule. Those cannot be implemented together. After the move, the owner thread ends the turn at the reply and never runs the write, and a host-dispatched background ticket is missing work.

**Evidence.** `Module::placed` builds `Placed<Module>` from the same module (`js/src/lib.rs:483–485`). `Placed::turn` continues only `Answer::Later` whose request has a continuation, and runs that closure on the owner (`data/src/placed.rs:372–385`). A reply ends the turn. `Placed::continuation` returns `None` while `owner.is_some()` (`:681–686`), so dispatch is `Dispatch::Missing`. `Drop` does not wait (`:710–715`, LLP 1027.002 D5). The worker realm loads the same prelude (`module-worker.js:74–76`) and retires on a non-continuation answer (`:101`).

**Fix.** Until D11, the prelude moves storage only when the host says this executor is on the main thread. `Placed::background` stays `None`, and stage 1's composer row does not say `Placed` forwards. The worker realm keeps the `ticket === 0` loop.

**Fix.** Keep `inflight` a number. Put the label in a new field or a journal line. Cite `glue.js:1219–1250` for settle and `:712–718` for why the ticket is already waited on.

### 9. D6, D2 — token remap and `wake` are not where the doc points

**Problem.** `background()`'s `Request` never passes through the only remap that exists, and `progress += 1` is not `wake`. A fixed `BACKGROUND` call id also collides with real call ids.

**Evidence.** `Storage::step` remaps continuation tokens only on `Answer::Later` (`data/host/src/lib.rs:77–133`). `Mixed` remaps in `continuation` via `self.continuations` (`data/src/mixed.rs:841–848`). **Fix.** Say the forward calls the same remap `step` uses, or the host dispatches an inner token `Storage::continuation` does not know. Reserve `BACKGROUND` the way `WAITING` is reserved. State that `release_work` is what asks `WAITING` answers again after the increment.

### 10. D3, D4.2 — the JS target's reads do not wait for an in-flight write today

**Problem.** D4.2 says a read issued after a background write sees that write. On the JS target, which §2 treats as the web, a read does not wait for an in-flight write. D3's new queue changes that oracle. The doc should say so against the file that does it.

**Evidence.** Mutations chain on `mutationTails` (`host/web/storage-fs.js:335–347`). `readFile`, `readdir`, `stat`, and `realpath` call the store directly (`:349–350`). `ts-data.js` fires each op as its own promise (`:171–179`). The comment at `storage-fs.js:10–11` says calls retain invocation order. Reads are not on that chain.

**Fix.** Name `storage-fs.js:349–350` in D3 and D7. The JS queue serializes a later read behind an earlier write of the same module, which the filesystem does not do now. §2 already says the RFC adds an order the web leaves to chance. Point that sentence at this path.

### 11. D10 — the lifecycle APIs are absent, and the guarantee is stronger than the APIs

**Problem.** Neither background-task API exists. `beginBackgroundTask` can expire in seconds and must be ended in the expiration handler, or iOS kills the app. `.terminateLater` waits until the app replies. macOS does not have a 5 s system patience.

**Evidence.** No `beginBackgroundTask` and no `applicationShouldTerminate` under `host/apple`. The two Mac delegates only implement `applicationShouldTerminateAfterLastWindowClosed` (`host/apple/Sources/ExactMac/main.swift:374`, `host/apple/Sources/ExactHostMac/main.swift:178`). iOS has `ExactIOS/main.swift` and `ExactHostIOS/main.swift`. Q5 calls 5 s "the order of macOS's own patience."

**Fix.** Name which delegate gains the method (app and host, Mac and iOS). The expiration handler calls `endBackgroundTask`. Say a suspension can still cut the write when the assertion expires. Say `.terminateLater` is the app's own 5 s timer, then `.terminateNow`.
