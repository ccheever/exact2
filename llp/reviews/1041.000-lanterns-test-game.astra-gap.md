**Lanterns is not ready for an unrestricted S0–S5 builder run.** Most individual systems exist; the substantial gaps are procedural render geometry, gamepad input, actual sky IBL, and player-facing persistence. Physics, animation events, spatial audio, directional lighting, sixteen point lights, HUD publication, and placed children already exist.

The important integration defect is **settling**: today it means an observed world stopped changing, not specifically that its dynamic bodies slept. Lanterns’ moving sun, animated fox, and countdown can prevent it indefinitely.

This is a static audit of the supplied checkout. I ran no builds or tests and changed no files. “Exists” below means implemented in the inspected source. Line estimates are engineering estimates, not measurements.

### Engine slices to land first

Ordered approximately smallest first. Implementation ranges exclude the separately stated tests/examples. Proposed APIs below are not claims about existing APIs.

1. **E1 — Make light selection depend only on the current scene.** About **60–100 implementation lines in render**, plus **100–200 test lines**. Remove the unsaved incumbent preference; select eligible lights by a documented distance/entity ordering, excluding inactive lights. Keep the sixteen-light limit. Acceptance: twelve lights all contribute; a seventeen-light boundary scene has identical selected identities/order after continuous feeds, a long seek and restore at the same tick endpoint; a zero-intensity nearer light cannot displace an active one. **Risk:** removing hysteresis can expose boundary popping. Saving renderer selection would entangle presentation history with simulation; for this scale, deterministic selection is the cleaner trade.

2. **E2 — A saved spring multiplier for point-light intensity.** About **100–180 lines in engine/render**, plus **120–200 tests**. Add one narrow component consumed by the existing light feed; sample the existing `exact-motion` spring at presentation time, while retaining inspectable tick-end values and settling behavior. The game retargets it once when lighting a lantern. Acceptance: midway intensity, interrupted retarget continuity and final rest agree across save/restore; frame sampling changes no world bytes; illumination on nearby geometry changes, not merely the lantern’s emissive material. **Risk:** this can grow into a second binding/value graph. Keep it a direct component-to-light connection, with explicit treatment of negative spring overshoot.

3. **E3 — Make settling honest for a living scene, and certify the controller combination.** About **150–300 engine/physics lines**, plus **300–500 tests/example lines**. Have physics report work while any dynamic body remains awake. Give purely derived Environment/countdown publications an explicit way not to hold settling open, preserving their save/hash rules; use existing `Ambient` for cosmetic fox/sun entities, while the capsule and crate remain observed. Include a compact example composing existing Move/Jump/Gravity with `CapsuleController`, a light crate and a visual fox child. Acceptance: push the crate off a ledge while sun, idle animation and HUD continue; settle returns only after sleep and reports pinned coordinates; a supported-but-awake body cannot falsely settle; ordinary time still reaches night. Run the same fixture through Off/Save/FreshGame and close the documented EXPHYS v2 continuation boundaries. **Risk:** excluding too much can conceal active gameplay; excluding too little makes settle useless. Do not “fix” this by pausing time during settle or omitting physics state from hashes. The implementation estimate does not bound an undiscovered Rapier parity repair.

4. **E4 — One typed, declared level-data path.** About **350–600 lines in engine/bake/game-app integration**, plus **200–350 tests**. Let the game declare and read a level value using its existing `Data` representation; validate that same type during the ordinary bake and load it through the existing asset barrier. Keep lantern positions, crate parameters, sign text and seed in that value. Acceptance: a malformed position reports its field before play; a level-only edit changes delivered data without changing the game module; all hosts construct the same tick-zero world; save continuation either retains the original level identity or refuses an incompatible replacement explicitly. **Risk:** a second schema registry, general scene editor or hidden asynchronous gameplay input. Use one typed declaration and finish delivery before setup.

5. **E5 — Shared generated geometry, including heightfields and vertex colours.** About **600–900 lines across engine/render/physics/bake**, plus **250–450 tests**. Provide validated CPU geometry that a game can create during setup and reference from multiple entities; route it through existing mesh upload/batching. A heightfield helper must produce matching visual/collision coordinates and triangle conventions. Add optional vertex colours through the data, bake and shader paths. Acceptance: an asymmetric seeded heightfield’s rendered vertices and collision samples agree; slope/ledge contacts pin; repeated props share geometry and draws; save/restore preserves geometry identity without per-frame regeneration or upload. **Risk:** duplicated large geometry in every entity/save, mutable geometry leaking into renderer caches, or enlarging the primitive-only artifact unnecessarily. Do not introduce GPU-generated authoritative terrain.

6. **E6 — Bounded IBL from the authored sky.** About **650–1,000 lines in bake/render with a small engine description**, plus **200–350 tests**. Implement a small baked sky environment with diffuse and roughness-filtered specular lighting; permit a simulation-driven dusk/night mix. Use the same lighting interpretation for primitives and models. Acceptance: roughness changes reflection spread on a metallic prop; diffuse sky illumination matches the chosen environment; setting night illumination to zero leaves point lights as the source; dusk/night readbacks remain within host bands after restore. **Risk:** download size, texture memory and shader permutations can exceed the value delivered. Keep this out of primitive games that do not request it, and do not add dynamic GI or per-frame environment rebaking. If the architect accepts today’s hemisphere approximation, remove this slice and amend the RFC explicitly.

7. **E7 — Physical gamepad input through the existing action seam.** About **800–1,200 lines across engine input, GPU transport and web/Apple/Linux delivery**, plus **300–500 tests**. Add timestamped standard axes/buttons, deterministic dead-zone/magnitude rules, disconnect release and saved held state. Hosts collect device state; the simulation resolves actions. Acceptance: equivalent axis/button events produce identical movement and hashes across hosts; partial deflection walks, full deflection runs; simultaneous thumb/key input follows a stated combination rule; disconnect and restore do not leave stuck movement. Separately exercise real pads on web and Apple. **Risk:** platform device identities, polling cadence or host dead zones entering authoritative state. Agent injection proves event processing, not physical pad delivery; keep those evidence classes distinct.

8. **E8 — Player-facing Save/Continue using the existing surface bytes and app filesystem.** About **900–1,400 lines across optional game-app support and host/storage seams**, plus **350–550 tests**. Expose a supported route from an ordinary Contract action to surface capture and app-scoped atomic storage, and from Continue to restoration before the first world frame. Store the same **EXSIM bytes** the agent captures. Keep I/O outside the tick and outside the core simulation crate. Acceptance: save midway through a jump, animation fade and lantern spring with wind playing; destroy the process; Continue restores the same tick/hash/HUD and produces byte-identical subsequent saves under identical input. Missing/corrupt saves produce a usable title-screen result; the title still paints before loading the game module. **Risk:** a second persistence format, hidden filesystem dependencies in World, or asynchronous storage completion advancing gameplay. A non-game surface checkpoint is the appropriate shared app-engine reading of this seam.

These should extend existing tests and fixtures, not add another check suite or workflow. File sizes already constrain placement: `sim.rs` is **1,452 lines**, `surface.rs` **1,440**, and `animation.rs` **1,282**. Additions to those areas require small module extraction to respect the 1,500-line rule.

### Deliberately leave these discoveries to the builder

- **Game design:** terrain shape, reachable ledges, crate placement, lantern route, camera framing and the thirteenth-lantern task. These are the consumer’s work.
- **Movement composition and feel:** speeds, acceleration, jump height, slope/step tuning and explicit crate mass. Composing the existing motion primitives is not hand-writing physics.
- **Fox presentation:** speed thresholds, state names, procedural jump posture, marker-to-sound wiring and whether the current frozen-pose fade is attractive enough.
- **Contract composition:** title/pause/settings/won routes, retained world lifetime, HUD wording, touch layout and ordinal placement friction.
- **Sound design:** chime/sting timbres, footstep gain/pitch and wind placement. Reuse the executor.
- **Visual/performance tradeoffs:** twelve-light frame cost, shadows, bloom, mesh sharing, download size and real-device feel. Record measurements rather than preemptively adding a larger renderer.
- **Acceptance content:** the movement/crate pins, complete winning route, idle-loss session, dusk/night image bands and fresh-process continuation proof. Engine fixtures cannot substitute for these.

Do not leave missing physical gamepad transport, custom renderer geometry, full-save storage plumbing or false settling semantics as “discoveries.” Their absence is already established, and rediscovering them would mainly measure how much engine code the builder can imitate inside its game directory.

### The slice I would refuse

**I would refuse clustered forward lighting as a prerequisite for twelve lanterns.** The renderer already admits sixteen point lights. Its current cost is clear and measurable; nothing in this static audit establishes that clustering is needed to meet Lanterns’ frame budget.

Clustering would add spatial light lists, buffers, dispatches, limits and debugging obligations before the existing path has failed a measurement. Fix deterministic selection, build the twelve-light scene, and measure it. The RFC’s player-visible lighting requirement is justified; its prescribed clustering architecture has not yet earned its place.
