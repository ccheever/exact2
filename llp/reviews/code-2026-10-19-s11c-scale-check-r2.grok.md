### 1. [P2] Treat a missing `child` as a failure, even when some node has no testId — `scripts/scale-check.mjs:118`

`nodes.find(n => n.testId === want.child)` runs when `padding` is set and `child` is omitted. `want.child` is then `undefined`, so the find returns the first layout node that has no `testId`. Real layouts are full of those (`identifyLayoutNodes` only copies a truthy testId). The branch that reports `its child (unnamed) is not in the layout` runs only when every node has a testId. On a host drive the check instead measures that anonymous node: usually a confusing padding failure, and a pass when that node happens to sit at the expected offset on both axes — the natural shape of a padded box whose child was never given a testId. The same match is on the box lookup at line 111. The new test does not catch it: every node in its fixture has a testId, so the omitted-child case fails there for a reason that does not hold on a real layout.

The rest of the three commits matches the round-1 list. Padding is the named child's offset on both axes, compared with the same expected number (half a point). An unreadable corner, a per-host value that names other hosts only, and a failed drive all fail the run; a spawn error or a signal is included in the reason; later hosts still run. Edges stay fractional, the search limit is half the box plus one pixel, `--out` is resolved and refused when it contains whitespace, unknown flags and missing values are refused, and each drive passes `--storage scale-check --reset-storage`. The queue entry now describes one top-left corner, held to 1 point, and four radii as the later protocol change.

**Middle row.** `start` reads the half-coverage point on `floor(y + h/2)` and subtracts it from each of the six corner rows, so a constant edge bias drops out. A radius is at most half the box, so that row is at or past the tangent. When the fractional part of `y + h/2` is past a half, the sample sits up to half a pixel above the tangent; the circle is flat there, and the extra inset peaks at 0.02 px on the smallest box `edges` accepts (8 px, inset 0.02). A square pill and a wide pill are the same case. A box that runs past the screenshot, including one whose middle row would fall off the image, returns null from the bounds check before any row is indexed, and `check` fails it. It does not fit 0. An overlap to the right of the straight edge is never sampled, because the scan stops at the first pixel at or above half coverage. Another colour on that edge makes `coverage` return null and the corner fail. A shade that lies on the fill-to-ground segment moves the reference, and every row's inset moves with it.

**Thresholds.** `off` is the straight-line distance, in 8-bit RGB, from the pixel to the segment between ground and fill. The cutoff is an absolute 24 counts (`off > 24`), and `span < 32²` rejects a pair closer than Euclidean distance 32. A blend done in encoded sRGB, which is what these captures are built to be, lands within 1 count of that segment after rounding. Linear-light compositing of sRGB green on white is the outlier among ordinary colours: one sample reaches 24.3 and would fail closed; red and blue on white stay on the segment. The macOS picture this script takes is `Capture.picture`, which retags the cache bitmap to sRGB and draws into it so the blend is in that space whatever the display profile. The display-profile picture is the window-server capture, and this drive does not ask for `screenshot window`. `decodePng` does not apply a profile. Read as sRGB, a Display P3 encoding of sRGB red on white sits 23.85 counts off the segment, so the cutoff accepts it, and the solid pixel projects to about 0.83 rather than 1. A fit that close to the literals would not land within 0.2 pt, so those PNGs were on the sRGB segment.

**First pixel and the tie.** When the crossing is in the first column, `found = x + 1 - c`, which is the exact inverse of area coverage for a vertical edge in that pixel. Later columns interpolate between pixel centres; on a vertical edge that form is exact at coverage 0.5 and 1, and about 0.08 px off in between. The fractional-origin cases in the test (0, 0.25, 0.5, 0.75) stay inside the 0.3 px bound. `fitRadius` keeps the smaller radius when the squared error does not improve by `1e-5`. On a corner the six rows can see, one 0.05 step changes that error by about 0.001 to 0.013, so the rule does not pull a visible radius down by a step. It only collapses the flat region, where every sample still has inset 0, to radius 0. That region is a radius below the first row's depth. With a fractional top, the first centre can sit as deep as 1.5 px, and a radius of 1.5 is fitted as 0. At 1× that misses the 1 pt gate (a false failure). The literal runs are outside that blind spot.
