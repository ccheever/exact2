## Verbatim review

# Design review: presentation in exact2's game engine (Opus)

## Verdict

Neither side is complete on its own, and main landing first is no argument for M.

- **M(A), visibility inheritance:** keep it as is.
- **The authored crate:** keep M(B)'s implementation, which is better hardened and qualified, but rename it to F's `game.render` / `render/` / `hooks`.
- **Presentation-only state:** adopt F2 and F3. M's hooks-only model cannot do bob, recoil, fades or per-instance tints on stock-drawn content without per-game WGSL, and in several cases not even with it.
- **F needs four changes to merge:**
  1. Drawn offset and opacity must inherit through `Parent`, to match M(A).
  2. Presentation should run only at observed boundaries, not on every tick.
  3. F's renderer paths must use `World::is_visible`.
  4. The `Presentation` name collision must be resolved.

Citations to `REVIEW/*.diff` give line numbers inside the diff files. Paths without a prefix are in the `/tmp/design-capsule` checkout (main, e097e4cae). Both diffs are against the merge-base, before M(B) landed, so F's diff does not show main's `presentation` code being removed. That code would conflict.

## Q1. The authored crate: `game.presentation` (M) vs `game.render` (F)

F's naming is better. M's implementation is better.

### Concrete differences

| Concern | M (main) | F (fix2/core) | Better |

### Why rename

"Presentation" is already overloaded in this engine:
- `exact_game_render::Presentation` is the executor trait behind audio and models (`game/render/src/surface.rs:16`, `lib.rs:51`, `ModelPresentation` at `models.rs:1456`).
- There is also `World::presentation_generation`.

If F2 lands, `#[derive(Presentation)]` components live in the **logic** crate and are written by `Game::present`. Calling the GPU-only hooks crate "presentation" would then send authors to the one crate where presentation state cannot be written. The crate holds `Hooks` and shaders, so `render/` says what it is.

The `game-render` alias versus `exact-game-render` is a small cost. The `exact_game_render` qualifier keeps them apart.

**Should there be one?** Yes. Without it an external game cannot wire hooks without editing generated files (1046.008, "Two concrete gaps"). Exactly one is wanted, and it should be M's code under F's name.

## Q2. Presentation-only state (F2/F3) vs hooks only (M)

### Can hooks-only express what the games need? No.

The `Hooks` surface (`game/render/src/hooks.rs:200-330`) provides:
- `RenderWorld`, which is read-only;
- extra passes: `compute`, `opaque`, `background`, `surface`, `post`;
- `materials()`, which is restricted to "loaded unskinned opaque model materials" (`hooks.rs:240`, and 1046.006.000 D4: "Transparent/skinned replacements are refused");
- `instance_data`, one `u32` per instance.

There is **no channel from game code to the stock renderer's per-instance pose, opacity or tint.** Going through the needs one at a time:

| Need | With M only |
|---|---|
| Bob, sway, recoil of a primitive | Not possible except by writing the simulated `Transform` (moves pins) or drawing the object yourself in `opaque` (losing engine batching, shadows and picking) |
| The same on a loaded opaque model | Needs a per-game WGSL vertex `CustomMaterial` with a paired shadow entry, plus the `FrameView::pose` / `entities()` registration |
| The same on a skinned model | Refused |
| Fades | Not possible: custom materials refuse transparency, and post-processing cannot fade one entity correctly |
| Camera shake or recoil kick | Simulated camera `Transform` only |
| Team tints, mutation looks | Simulated `Material` (entity-wide only, and the save moves) or per-game WGSL. Per-node or per-material looks are impossible on primitives and need WGSL on models. |

So the diary complaint stands under M. Fog of war (Skirmish) suits hooks, but the common cosmetic cases do not.

### Is F's model sound? Mostly. These are the points I checked.

**Determinism.** `present` starts from cleared rows (`clear_presentation`, `fix2-core.diff:1624`). Every simulation write path panics while presenting (`sim_writes` at `:1638`, placed on spawn, despawn, insert, get_mut, mutable queries, resource writes, `rng`, log, emit, publish, busy and reseed). Ticks cannot read presentation state (`sim_reads` at `:1647`). Randomness is `presentation_rng(seed, tick, salt)` (`:1814`). Together these make `present` a pure function of (simulation state, args, tick), and it lives in the logic crate, so the determinism lints apply to it as well.

That purity is the strongest property of the design. It also makes pixels deterministic in seekable mode, whereas hooks driven by host `dt` are not.

**Restore and seek.** Presentation rows are excluded from saves, and a save carrying them is refused (`:1781`). Restore presents again, and a `present` panic becomes a refused restore (`:1384`). This uses `catch_unwind`, so under wasm `panic=abort` it is a host abort; that is acceptable but should be documented. The paranoid tests check that restore and both paranoid modes give the same presentation bits (`fix2-render.diff`, `tests/presentation.rs`, "rebuilt at every boundary"). Sound.

**Hashes and rest.** Presentation is excluded from digests (`digest.rs` hunk) and from rest observation (`inspect.rs` hunk), so a bobbing world still settles. One thing to verify: presentation storages share the world's mutation `epoch` (`storage::make::<C>(C::NAME, self.epoch.clone())`, `world.rs` insert). A `present` outside the loop (restore, an args change) therefore bumps the epoch and resets settle back-off, which is harmless but wasteful.

**Agents and proofs.** Pins never move for visual work. Agents can still read presentation values (engine README hunk: "agents can still read them"), and values that are a pure function of the tick are good for agent-driven visual tests. Hooks cannot offer this, because their state is GPU-side and depends on host time. Note that the brief's "excluded from observation" means rest observation only.

**Cost per tick: this is the real flaw.** `present` runs inside the tick loop (`fix2-core.diff:1120`), so a 10,000-tick agent seek or catch-up presents 10,000 times. The renderer observer only consumes ticks with `left < 2` (`game/render/src/surface.rs:240`), and because `present` is pure, skipping the other ticks changes nothing.

The clear-and-rebuild approach also makes revisions meaningless. F compensates with full content digests whenever they move, which is every tick:
- `offsets()` (`fix2-render.diff:7498`);
- `node_looks_digest` (`:7475`);
- the Opacity vector compare.

`NodeMaterial.node` is a `String`, so per-node team looks allocate on every present. Running `present` only at observed boundaries makes all of this proportional to frames, not ticks.

**Mental model.** "`tick` updates and `present` views" is easy to teach, but it has three limits authors must be told about:
1. `present` holds no state. Recoil and flashes must derive from simulated timestamps such as `last_shot_tick`, which games normally keep anyway.
2. `present` cannot spawn entities, so cosmetic particles and entities stay in the simulation (`Ambient` / emitters). The diary's "particles" item is therefore only partly addressed.
3. Presentation **resources** are not implemented, despite the brief. The derive yields a Component only (`fix2-core.diff`, `derive/src/lib.rs` hunk), and wind-fixture spawns a *simulated* `"wind"` entity just to hold its `Gust`.

**Enforcement is a maintenance hazard.** Runtime checks are scattered across around 20 write sites, and any future `World` writer must remember `sim_writes`. Either centralize the check in the existing mutation chokepoints (`mutated()`, storage `edited()`, journal, messages), or add a test that fails when a new `pub fn` on `World` that takes `&mut self` or returns `RefMut` is unguarded.

**LOD, sockets and shadows.** Offset is folded into `scene::pose` (`fix2-render.diff:7824`). That is used by the camera, lights, the transform pages and therefore shadows, and `FrameView::pose`, so offsets consistently move drawing, shadows, a shaken camera and hook-registered poses. Picking and physics keep the simulated pose. That is correct. Socket followers follow the drawn rig. LOD levels share pose, looks and opacity (`:1496`). The problems are:

- **Offset does not propagate to Parent children.** The docs say so ("Parented children keep their own poses (offset each one…)", `fix2-core.diff:921`). The code agrees: parented overrides use `w.global(e)` times the entity's *own* offset, and unparented offsets are added only `.without::<Parent>()` (`fix2-render.diff:7605`). F's own test leaves the child at y=2 while the root bobs (`fix2-render.diff`, the `Bobbing` test). This is wrong for exactly the multipart units 1046.008 describes (Skirmish roots, Forest Deer eyes and antlers). Per-part offsets cannot reproduce a whole-unit transform, because each part has a different local frame.
- **Opacity is per-entity and not inherited.** A multipart tree or unit cannot fade as one, which is inconsistent with M's `Visible` rule.
- **Opacity shadows are inconsistent:** model shadows fade, primitive shadows do not (`fix2-render.diff:4113`).
- **No presentation tint for primitives.** `NodeMaterials` and `MaterialOverrides` are model-only, so a hit flash on a primitive still needs a simulated `Material` write.
- **Static look config remains simulated** (`ModelLod`, `ParticleLook` registered as Components at `fix2-render.diff:2111-2116`), so adding it moves pins once. I think that is correct: rebuilding static config every present would be wasteful, and a one-time honest save change is not the diary's problem. The problem is per-tick cosmetics and RNG.

### Worth the complexity?

Yes. The engine change is contained:
- one const on `Component`;
- one registry bit;
- guards that are const-folded or a single `Cell<bool>` load;
- five `present` call sites in `Sim`;
- filters in the digest and inspect code;
- one restore refusal.

It removes per-game WGSL for the most common art-pass work and keeps pins stable.

I considered a hooks-side alternative, `Hooks::prepare` writing a `DrawOverrides` table each frame. It would avoid the World gating, but it has four drawbacks:
- it forces a GPU-linked crate on every game that wants a bob;
- it is not testable in `logic/tests`;
- agents cannot see it;
- it depends on host time.

F's placement is the better author experience, and hooks still compose with it: they read presentation components through `RenderWorld`, which is what wind-fixture's `Gust` demonstrates.

## Q3. M's visibility inheritance vs F's Opacity, LOD, ViewModel and the art passes

There is no conceptual conflict: `Visible` is simulated, `Opacity` is drawn-only. There are concrete merge conflicts and required adjustments:

1. **F's rewritten model batch loop uses local visibility:** `if w.get::<Visible>(entity).is_some_and(|v| !v.0)` (`fix2-render.diff:7684`). Main uses `w.is_visible(entity)` (`game/render/src/world/assets.rs:25`). The merge must keep `is_visible`.
   - Every new F path must also filter through `is_visible`: LOD bands, `part_looks`, the fades list, and `ParticleLook` texture requests and quads.
   - F's `Versions` must keep M's Parent-revision batch dependency (1046.008 amendment 1) alongside `opacity`, `lod` and the content digests.
2. **Use one hierarchy rule for drawn state.** Effective visible is AND over ancestors (M). Effective opacity should be the product over `Parent` ancestors. Drawn global should be `drawn(parent) · local · offset`. Compute all three in the same bounded parent-chain walk M already measured (about 88 µs for 1,000 three-level multipart entities). As with `Visible`, `SocketFollow` alone inherits none of the *look* state, but socket props keep following the drawn rig pose, as F does now.
3. **ViewModel:** no conflict. It is per-entity, and Rivals' locally hidden parts keep working (1046.008 qualification). Opacity dithering on viewmodel layers needs a pixel check.
4. **LOD:** `hide` distance and bands are GPU cull and independent of `Visible`. Document that agent "visible" (`agent.rs:364`) does not reflect LOD culling or `Opacity(0)`; both are drawn-only.
5. **Art passes' use of `Visible` must be audited.** I could not see them; only wind-fixture and engine tests are in the diffs.
   - Any `Visible(false)` on a parent whose children were meant to stay visible now hides them. Forest's Deer is the known case (`forest/logic/src/creatures.rs:82`, `:276`, and 1046.008 "Two concrete gaps").
   - Any `Visible` toggled per tick for purely cosmetic blinking or flashing should move to `Opacity` in `present`, so it stops moving pins.
6. **Lights:** M suppresses lights with a hidden ancestor. F's Offset moves lights through `pose()`, and Opacity does not affect lights. That is consistent; document it.

## Q4. Recommended design spec

### Keep

- **M(A) as landed:** `World::is_visible`, the extraction, shadow, light, pick and agent call sites, and the regression tests (`game/engine/src/scene/visibility.rs`).
- **M(B) machinery, renamed:** the declaration validation, `presentationGraph`, lint, conditional exact-gpu deps, receipts and watch inputs (`scripts/app.mjs:1087-1091`), and the `windows` membership.
- **F2:** `#[derive(Presentation)]`, `Game::present`, `presentation_rng`, the save refusal, hash and rest exclusion, tick-read panic and present-write panic.
- **F3:** `Offset`, `Opacity`, `NodeMaterials`, `MaterialOverrides`, and the content-digest rebatch avoidance.
- **wind-fixture** as the committed public hooks consumer, ported to the declaration below.

### Rename

- `game.presentation` → `game.render`, directory `presentation/` → `render/`, crate suffix `-presentation` → `-render`, generated alias `game-presentation` → `game-render`.
- Key `type` → `hooks`; keep `shaders`.
- `presentationDeclaration` / `presentationGraph` → `renderDeclaration` / `renderGraph`.
- Update the strings and paths in `scripts/app.mjs:1087-1090`, `scripts/agent-launch.mjs:311`, `scripts/app.test.mjs:342-372` and `:574-601`, and the schema.
- An old `game.presentation` key should fail with "renamed to game.render { crate, hooks, shaders }". Skirmish must migrate.
- Rename the render-crate executor trait `exact_game_render::Presentation` → `Executor` (`ModelPresentation` → `ModelExecutor`). It is SDK-internal, used only through `module!`. This leaves "Presentation" meaning author-facing drawn-only state.

### Change in F

1. **Present at observed boundaries only:** after setup, restore, an args change or `world_mut`, and on ticks where `target - tick < 2`, not on every tick (`fix2-core.diff:1120`). Optionally keep every-tick presenting under paranoid modes, to check purity by comparing.
2. **Inherit through `Parent`,** as specified in Q3 item 2: drawn pose composes ancestors' offsets, and opacity is a product down the chain. Delete the `.without::<Parent>()` special case (`fix2-render.diff:7605`), and correct the docs at `fix2-core.diff:619` and `:921`.
3. **Primitive shadows dither with `Opacity`,** matching models.
4. **Use `is_visible` in every F render path** (Q3 item 1).
5. **Centralize the `sim_writes` guard,** or add the coverage test from Q2. Verify that presentation writes do not bump the simulation mutation epoch.
6. **Implicit optional shader root `render/shaders`,** built on M's inventory and watch machinery, with `gpu.shaderRoots` still available for more.

### Add later, only if a consumer needs it

- Presentation resources, so wind-fixture's simulated `"wind"` holder entity goes away.
- An entity-wide presentation `Tint` for primitives.
- Interned node names, if measurement shows `NodeMaterials` allocation matters.

### Delete

- **From F:**
  - The `game.render` block in `shells.mjs` (`fix2-core.diff:90-168`), replaced by M's renamed code.
  - F's schema entry, replaced by M's renamed entry.
  - The global `exact-gpu` / `exact-gpu-reflect` lines in `game/Cargo.toml` (`fix2-core.diff:10`) and in `shells.lock`.
- **From M:** nothing functional. Revise the 1046.008 B text and the 1046.006.000 "SDK declaration follow-up" to the new names, and drop the stance that cosmetics need no presentation-only components.

### Qualification for the merged result

1. Equal hashes and saves with `present` on and off, and on restore, seek and both paranoid modes.
2. Every-tick vs boundary-only `present` gives equal drawn output.
3. Pixel tests:
   - a bobbing multipart root, children included;
   - a faded multipart tree, shadows included;
   - a hidden ancestor overriding `Opacity` and LOD.
4. The `renderGraph` refusal test against an indirect renamed dependency (M's existing test, renamed).
5. The wind-fixture GPU test and proofs on native and web.
