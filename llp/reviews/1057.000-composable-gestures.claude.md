# Review of LLP 1057.000: composable gestures (three designs compared)

**Reviewer:** Claude (Opus 5.5), independent. Read-only review at 479bd946.
**Read:** RULES.md, NOT-DOING.md, LLP 1000, 1002 (D1–D7), 1012, 1035.001, 1035.003, 1035.005 §1, 1047, 1057 and 1057.000. I spot-checked the RFC's §2 facts against the tree.

## Assessment

The RFC is honest and unusually well-sourced. Almost every code citation checks out. It is right that C, on Apple, is the only design that keeps UIKit's relationships with scroll views, back swipe and text.

Its headline claim doesn't hold as written. C does not give "the same outcome on every host." It gives the same outcome for the same sequence of recognized primitives. Races between primitives depend on each host's thresholds. UIKit's tie order is undocumented, which the RFC itself concedes in §6 race 1. Taps, presses and double clicks outside the graph stay per-host. The conformance suite runs at the primitive level, so it can't see any of this.

The comparison also sets A up to lose (details under M2), and it understates C's arena on web, Linux and the AppKit mouse. Step 1 is sound. Step 2 has no consumer and no qualifying take, so under NOT-DOING the answer to step 2 today is no.

**Corrections:**

1. **"The only `require(toFail:)` is the dev menu's" is wrong.** `host/apple/ios/touch.swift:271` has `single.require(toFail: double)`. It sits in the approved UIKit touch-reduction harness (`host/apple/touch.mjs`), not in ExactKit. That harness is also the natural place for the §13 phase 2a spike, and the RFC doesn't mention it.
2. **The phone crash is misattributed** (§6 `exclusively` row: "delayed-touch queue, which crashed on a phone (DevMenuIOS.swift:47-49)"). LLP 1012:44-130 isolates the `_delayTouchesForEvent` nil-insertion crash to creating the session before `UIApplicationMain`. It was fixed on 2026-09-07, and the dev-menu mitigations were explicitly "not a fix." Failure requirements are not a known crash risk. This correction actually helps C.
3. **"Pointer identity reaches only the GPU canvas"** is true only of what reaches the runner. `collection-glue.js:255-316` and `input-glue.js` track `pointerId` in glue.
4. **iOS probably does drop the second `press` today.** The double-tap recognizer (`NodeViewIOS.swift:243-250`) keeps the default `cancelsTouchesInView = true` but sets `delaysTouchesEnded = false`. So the first tap's `touchesEnded` reaches `press`, and the second tap's is converted to `touchesCancelled` when the recognizer fires. I'm fairly confident but didn't run it. If so, both Apple hosts fire `press, dblclick` and the web fires `press, press, dblclick`.
5. **Three files that phases 0–1 touch are at the 1,500-line cap:** `NodeViewIOS.swift` 1487, `NodeViewMac.swift` 1488, `glue.js` 1499. Any gesture work has to go into new files.

## Concerns

**B1 — BLOCKER (for step 2 only): no consumer, no take, no implementer.**
- NOT-DOING:348-351: "take something off the doing-list… If nothing can come off, the answer is no."
- §11's take is deleting code. Agents may already remove apparatus freely (RULES §Agents), so that trades nothing. The RFC admits as much in its own open question 1.
- Only photo pinch has a consumer (`apps/interaction-gallery/app.contract`; NOT-DOING:64-71), and A covers it.
- Rotate, fling in any direction and long-press-drag outside reorder have no named consumer. LLP 1002's transform trial actually requires no rotation.
- 1057 §10.7's reopening trigger ("a v1 consumer has two independently authored recognizers… whose conflict none of the following can express") is not met.
- There is no `Implementer:` line (RULES §Scope: "A spec needs an implementer and a date"). As written, step 2 is a speculative spec.

**M1 — MATERIAL: "same outcome" is defined so narrowly that it is almost always true, and it isn't what Charlie asked.**
- A conformance case scripts primitive events (`recognize magnify 1.4`, §10.2). On Apple, that skips recognition entirely.
- Which primitive reaches `.began` first depends on host constants:
  - UIKit's undocumented pan hysteresis;
  - the tap's allowable movement;
  - the engine's 4 px slop;
  - the double-tap interval.
- So `exclusively(drag, longPress)`, or any continuous race, can pick different winners on iOS and on the web for the same finger.
- The tie priority in §6 is not realizable either. The proposed gate, `shouldBegin(B) = A is not began/changed`, is redundant: default exclusion already failed B if A began. Within one touch event, the order in which recognizers transition is undocumented. §6 race 1 says exactly that, so "priority on ties" contradicts it.
- The honest claim: the winner is identical given identical primitive order, and races are timing-dependent per host by declaration.

**M2 — MATERIAL: the comparison sets A up to lose.**
- **Rotate.** 1057 §10.2 item 6 already puts rotate in the built-in pair ("rotate when it comes"). §4.1's "rotate with pinch, unless it's the built-in pair" hides this.
- **Following without a runner transaction.** `swiperight` already follows with a hold, knee and velocity spring and no runner transaction per frame (`GestureHold.swift:18-37`; `NodeViewIOS.swift:197-218`). Generalizing it to an x-axis swipe with a release handler covers the fling card. That is a closed binding, not composition.
- **Long press then drag** is 1057 §10.1's phase-2 `longpress` plus the reorder idiom.
- **Testing.** "Intended, not tested" is a choice, not a property of A. The precedence table can carry the same cross-host cases, run on raw input streams.
- **The missing option.** The fair alternative is A plus closed composite bindings, each lowered to the best native composite. It is not in the table, and it covers all three worked examples.

**M3 — MATERIAL: C's rules column understates it.**
- **Web and Linux.** C is B's engine there, which is the arena NOT-DOING:258 refuses. It sits on the standard host. §10.8 says so, but the summary table says "compositions (not an arena)."
- **AppKit.** Native `magnify(with:)` phases plus engine-recognized mouse drags, arbitrated by the graph, is an arena deciding over native inputs. §11's "still refused: … a Rust arena on Apple" contradicts §7.
- **Claims.** Derived `touch-action` is the same thing in B and C, but only B is marked "claims".
- **LLP 1002 D5** deleted "recognizer state machines, compositions… the plan node graph." The engine is recognizer state machines, and a "static graph table" in the plan will read as the last item. Name it a gesture table and argue that it is static data.

**M4 — MATERIAL: `follows` can't carry the bindings it claims to replace, and the photo example regresses the admitted consumer.**
- **No focal point.** Separate `drag() follows translate` and `magnify() follows scale` zoom about the transform origin, not the fingers. Every native photo view anchors at the pinch centroid, which couples translate to scale and centroid. That coupling can't be expressed.
- **No atomic pair.** Separate `on end releasePan` and `on end releaseZoom` break LLP 1002's photo invariant: `begin_transform_hold` pairs both, the whole terminal payload is validated, and one release happens while both tokens are live (llp/1002:135-161).
- **No mapping clauses.** There is no knee or resistance clause, yet the sugar table says "`swiperight` = `drag(axis: x)` with the knee". There is no bounds or clamp, no snap, and no reorder autoscroll or collection feedback.
- **Unspecified semantics:** whether scale follows multiplicatively, what `drag(axis: x) follows translate` writes to y, and when rotate converts radians to degrees.
- **Consequence.** The bindings can't become sugar, and the take's item 2 shrinks to little.

**M5 — MATERIAL: UIKit behaviors §6 misses.**
- **No re-begin until all touches lift.** An ended or failed recognizer doesn't restart until every touch ends. Pinch, lift one finger, add one back: on UIKit, pinch probably does not re-begin; a naive engine re-pinches. I'm fairly confident. The engine must adopt the rule, or the divergence must be declared. This is broader than §6's sequenced hazard.
- **Pan centroid jump.** `simultaneously(drag, magnify)` needs the pan at `maximumNumberOfTouches = 2`. UIKit's translation is centroid-based and jumps when a finger lands (fairly confident), so the adapter needs compensation. The open question of what a max-1 pan does with a second finger (cancel or ignore) remains; I'm unsure.
- **Long press has no velocity.** In `sequenced(longPress, drag)` realized as one `UILongPressGestureRecognizer`, there is no `velocity(in:)`. Apple velocity then comes from `VelocityTracker`, contradicting §10.1's "iOS velocity: UIKit's".
- **`minDistance` ≠ `allowableMovement`.** One is a minimum to start; the other is a maximum before failing.
- **`sequenced(tap, drag)` is stateful.** It remembers a past recognition across a reset. That contradicts §6's "the host passes current states rather than keeping a mirror, so there is no drift."
- **Gestures outside the graph.** `press`, `dblclick`, `contextmenu`, `pan`, collections' observer, text interaction, canvas input and swipe actions aren't in the graph. Take a child `press` under a parent `tap(count: 2)`. iOS cancels the child's second press through `cancelsTouchesInView`. On the web, the child still gets its DOM `click`. So A's table is still needed at the boundary, which argues for doing A first.
- **Graph freeze.** A `gesture=` value that changes mid-sequence, or a node re-keyed by an `on begin` commit, needs "graph frozen at down" on every host.

**M6 — MATERIAL: the conformance suite and the agent story are insufficient.**
- **Missing cases.** The three examples at the primitive level omit:
  - nested nodes;
  - `drag(axis: x)` in a vertical list and in a horizontal pager;
  - the 20 pt back-swipe edge;
  - cancellation: view removed, system cancel, `pointercancel`;
  - partial lift and re-add;
  - an `on end` that destroys the node;
  - interplay with `press`/`dblclick`;
  - VoiceOver actions;
  - raw-stream cases.
- **The subclass carrier.** It sets `state` on a recognizer with no touches. I doubt UIKit runs its relationship resolution over recognizers holding no touches (unsure). Long press does set state from a timer, but only while it holds touches.
- **An unused real-touch carrier.** The simulator mouse carrier already exists (`host/apple/pointer.swift`; llp/1035.003 candidate 1, unverified). The Simulator's Option-drag pinch could give `platform` delivery for pinch through real UIKit arbitration. Likely feasible, unverified.
- **CDP.** It has `Input.synthesizePinchGesture` (experimental) as well as multi-point `dispatchTouchEvent`.
- **Timers.** Long-press and double-tap timeouts in the engine fire with no input. On web and Linux they must be runner-clock timers (LLP 1002 D3), or "seekable on every host" is false.

**M7 — MATERIAL: one name, two semantics.** `exclusively` means fail-first when the leader is discrete and a race when it is continuous. RNGH splits these into `Exclusive` and `Race`. The algebra should too, and refuse the other combination at compile time.

**m1 — MINOR: grammar bug.** `gesture lift = sequenced(longPress(), drag(axis: y)) label "Move"` attaches `label` to a combinator, but `<clause>` attaches only to `<primitive>` (§4.2 grammar). Also, reorder via VoiceOver needs move-up and move-down actions, not one "Move".

**m2 — MINOR: new syntax and 1035.005.** NOT-DOING:313 and 1035.005 §1 require new syntax to answer friction "demonstrated in source." `contract fmt` exists (`contract/cli/src/main.rs:31`) and the source map is admitted, so the ordering gate looks met. The RFC should say so and cite real source. It should also consider a value mini-language (`gesture="exclusively(…)"`, like `transition`) over a new top-level declaration.

**m3 — MINOR: cost estimates are unmeasured.**
- 1.5–3K lines and 10–20 KiB brotli is plausible but optimistic. Pointer tracking, timers, `wheel`+`ctrlKey`/`gesture*` normalization and cancellation push it toward 3–5K.
- The four apps using drag bindings or `swiperight` (exact-live, interaction-gallery, messages, messages-stress) would link Gestures on top of Motion and Drag.
- On native, the linked set is a compatibility input (llp/1047 D8), so the first bundle to use `gesture` is a binary change.

**m4 — MINOR: SwiftUI history is evidence of difficulty.** As I recall (moderately confident), iOS 18's unification caused widely reported `DragGesture`-inside-`ScrollView` regressions. If so, Apple's own B→C move changed outcomes. That is evidence of how hard C's promise is, not only of its direction.

## Checks against platform knowledge

- **Confident:**
  - `shouldRecognizeSimultaneouslyWith` returning YES from either delegate wins.
  - `shouldRequireFailureOf` / `shouldBeRequiredToFailBy` are asked once per recognition attempt (the header's own wording, as I recall).
  - A failed recognizer stays failed until all touches end.
  - Default exclusion is decided by `canPrevent` / `canBePrevented`.
  - No public multi-tap interval.
  - Long press defaults: 0.5 s and 10 pt.
  - The `NSGestureRecognizer` classes and delegate shape.
  - `smartMagnify` is the two-finger double tap.
  - The web's click/dblclick order.
  - Chromium's `wheel`+`ctrlKey` pinch.
  - Safari `gesture*` on macOS and iOS.
  - Android detectors have no arbitration.
  - RNGH's Android orchestrator.
- **Fairly confident:** a pinch with one finger stays `.possible`; SwiftUI before iOS 18 ran its own gesture system.
- **Unsure:**
  - the iOS 18 internals;
  - what a max-1 pan does with a second finger;
  - whether subclass state injection runs arbitration;
  - `delaysContentTouches` is about 150 ms.

## Suggestions

1. Restate the promise: the winner and phase order are identical given identical primitive order; races and timeouts are host-timed and declared.
2. Add A plus closed composites to the comparison as a fourth column.
3. Phase 1: implement pinch inside the existing `TransformDragHold` / `begin_transform_hold` path, with focal-point anchoring and the atomic pair kept. Don't build a hard-coded "first compiled graph"; that is apparatus ahead of the trade.
4. Phase 0: make the web rule for `dblclick` bind everywhere.
   - iOS: set `doubleRecognizer.cancelsTouchesInView = false` (one line).
   - macOS: delete the `node.pressed = false` suppression at `NodeViewMac.swift:1437`.
   - Add a phase-0 smoke on raw streams (web CDP, macOS `NSEvent`, simulator pointer).
5. Keep the bindings as the presentation layer. If the algebra ever lands, primitives should feed bindings rather than replace them.
6. Split `exclusively` / `race`. Define "no re-begin until all touches lift" on every host. Freeze the graph at down. Put engine timers on the runner clock.
7. Add a `gestures` host section to `state`, following the 1035.002 D2 pattern (winner set, phase), so agents read outcomes without a ninth operation.
8. If the trigger fires: run 2a in `ios/touch.swift`'s harness, with real touches (simulator pointer, Option pinch) and on a phone, before any Contract syntax.
9. Put new code in new files; the three files above are at the cap.

## Answers to the open questions

1. **The trade:** not enough. Deleting apparatus is free, so it isn't a take. Until a consumer needs composition and a doing-list item comes off, the answer under NOT-DOING is no.
2. **Double tap:** the web rule binds on every host: `press`, `press`, `dblclick`, no delay. Fix macOS and iOS in phase 0. Don't offer UIKit's delayed single tap without a consumer. A photo "tap toggles chrome" idiom would be that consumer, and none exists.
3. **Continuous leaders:** reject race-with-tie-priority. Ties aren't realizable on UIKit. Call it `race`, with no priority, or refuse continuous leaders in `exclusively`.
4. **Trackpad pan:** stay scroll, which is the web default: wheel scrolls the nearest scroller. Preview pans because the image sits in an `NSScrollView` with magnification. If wanted, model the zoomed photo as a scroll container, not a `drag` fed by scroll.
5. **Accessibility payloads:** no synthesized terminal payloads. Require an explicit named action (`label "Dismiss" does dismissCard`) or an authored control. Magnify as adjustable with an explicit step is fine.
6. **Scope:** readiness, not product. Only photo pinch is a consumer, and phase 1 serves it.

## Verdict: ACCEPT WITH CHANGES

- **Accept:** step 1, which is 1057 §10.6 phases 0–1, with suggestions 3 and 4.
- **Reject for now:** steps 2–4 (C, the gate, the trade). Keep the §6 UIKit analysis and the §4.2 algebra as research, for when 1057 §10.7's trigger fires with a named consumer and a real take.

## Bottom line

Pursue A now: write the precedence table, align the AppKit and Linux orders to it, make `dblclick` follow the web everywhere, and use one velocity estimator and one threshold table. Then add pinch on `transformDragFor` for iOS, macOS and web, inside the existing paired transform hold, with focal-point zoom. After that, grow A with closed composite bindings, each only when a named consumer asks: `panrelease`, a direction-general swipe, `longpress`. Hold them to a raw-input cross-host smoke. Treat C as the right shape to reach for later, not B: it is the only design that keeps UIKit's relationships. But reach for it only when a real v1 consumer hits a conflict the table can't express, and something comes off the doing-list. Even then, run the UIKit spike with real touches (simulator pointer or Option-pinch, then a phone) first. Split `exclusively` from `race`. Keep bindings as the presentation layer. Promise the same winner given the same recognized events, not the same outcome for the same finger.
