Four fundamental issues remain.

D1’s syntax, D3’s caps, D4’s live sampling and repeat phase, D5’s takeover rule, and idle’s single-firing release boundary hold up. The existing JS live-clock tests pass 6/6.

1. **The refusal fix still permits permanent starvation.**

   [D4](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:171) puts an unrun released timer behind *every* precise timer due at each subsequent advance’s cutoff. A refusing repeat is consumed and rescheduled before the error stops the advance ([advance.rs:593](/Users/admin/Developer/exact2-timer-wait-points/runner/src/runner/advance.rs:593)).

   Suppose a precise `every(1, bad)` gets a recoverable `TaskKey` refusal every time. An uncapped `scrollend` timer becomes released, but `bad` refuses first. If retries arrive on display frames, `bad` is due again on every retry and always stops the advance before the released timer. Its scroll has ended, yet it never runs. This contradicts D6’s claim that the next wake runs the remainder.

   **Instead:** Preserve a release’s continuation order across refusals and fire limits. Newly due precise work must not repeatedly overtake its unrun remainder; replace D4’s renewed blanket priority with a defined ordering that guarantees progress.

2. **Persisting release eligibility breaks the wait guarantee when execution resumes elsewhere.**

   [D6](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:223) makes unrun released timers ordinary due work. D4 explicitly permits any later advance to execute them. That conflicts with D2’s frame boundary and [D7’s unconditional scroll exclusion](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:254).

   Two `frame` timers release in an animation callback; the first refuses. The second can now run from an ordinary timeout or input advance, before its cap and outside a frame. Likewise, after two `scrollend` timers release and the first refuses, scrolling can resume before the next wake; the second still runs during that scroll. The JS clock already advances from both [timeouts](/Users/admin/Developer/exact2-timer-wait-points/host/web-js/rt.js:347) and [input delivery](/Users/admin/Developer/exact2-timer-wait-points/host/web-js/rt.js:898).

   **Instead:** Preserve pending firings without making their admission unconditional. Resume frame work at another frame, and recheck scroll or idle eligibility before resuming their work; only an expired cap may bypass the condition.

3. **The implementation plan omits the supported wasm web host.**

   [D7](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:243) and [§4](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:333) cover the JS target but give the wasm browser host no wait protocol. Games still build wasm ([LLP 1071](/Users/admin/Developer/exact2-timer-wait-points/llp/1071-exact2-web-target.rfc.md:8)). Its glue reads only deadlines and frame interest ([glue.js:109](/Users/admin/Developer/exact2-timer-wait-points/host/web/glue.js:109)); its [scheduler](/Users/admin/Developer/exact2-timer-wait-points/host/web/timer-glue.js:12) has no release mechanism. The optional text-flow executor also owns this scheduling path.

   Following the listed stages would let the shared compiler and runner accept a wasm game’s uncapped `scrollend` timer, hold it, and never receive a scroll release. It can remain unfired even with no scrolling.

   **Instead:** Include the wasm host, its ABI, and text-flow scheduling in stage 2, preferably sharing browser wait logic with the JS target. Otherwise explicitly refuse these forms for wasm builds until supported.

4. **`update`’s portable mapping does not provide the early phase used to justify removing admission checks.**

   [D2](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:106) promises the update’s start, before its work. D7’s web and Android callbacks run later: HTML runs scroll steps before animation callbacks, and Android runs input before its animation callbacks. ([HTML processing model](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model), [AOSP Choreographer](https://android.googlesource.com/platform/frameworks/base/+/master/core/java/android/view/Choreographer.java))

   At 60 Hz, a 12 ms scroll handler followed by a 6 ms timer batch misses the frame, although the timer fits comfortably in the next quieter frame. Android’s separately posted callback can additionally follow Exact’s already posted [frame turn](/Users/admin/Developer/exact2-timer-wait-points/host/android/canvas/src/main/java/dev/exact/canvas/ExactView.kt:1024). Thus “before drawing” supplies neither “before Exact’s work” nor nearly a whole frame.

   **Instead:** Define the portable boundary as a scheduling opportunity before Exact’s frame work, integrate release into that callback, and qualify the available budget. Defer the stronger budget-sensitive `update` behavior until its admission mechanism exists.
