## Blocker

**The 20 s codec budget does not fit inside the 30 s continuation, and a timed-out call still writes.** Amendment A1, A1.4–A1.5 (`llp/1069.002-media-picker.rfc.md` around the timeout row and the “20 s / 30 s” bullets), against `js/src/storage.rs:83-105` and `js/src/prelude.js:702-712` and `1373-1386`.

A1 says the search is capped at 20 s, checked before each trial, and that a trial already running is allowed to finish, on the theory that this stays inside the storage continuation’s 30 s deadline. That deadline is not a codec timeout. `Session::continuation` polls until Ibex is idle and, at 30 s, returns `"storage continuation timed out"` without cancelling the pool job. The resume path then calls `__exact_storage_failed`, which forces `code: "failed"` (it does not go through `storageCode`) and `landed()`, which marks the op settled and **issues the next queued storage operation**. The pool job keeps running. When the codec returns it still performs the atomic rename onto `to`. `landed` ignores the late completion (`prelude.js:703-706`), so the caller has already rejected, and the file appears anyway.

Failing case: `maxDimension: 8192` on a large HEIC. The clock is at 19 s, so another trial starts. ImageIO cannot be cancelled. Encoding an 8192² bitmap takes more than the remaining 11 s. At 30 s the answer fails with `failed` / `"storage continuation timed out"`, not `timeout`. The next `readFile` or `writeFile` on that module runs while the codec is still inside `atomic()`. The codec then renames onto `to`. That breaks A1.4 (“on any failure `to` is left as it was”) and the one-at-a-time queue.

The Rust path does not have this race: `data/host/src/lib.rs` runs `native::run` to completion with no 30 s abort. Only the Hermes/Ibex path does.

Fix: make the Ibex task itself return before the continuation can fire, and write only after that return. Drop “a trial in progress finishes” unless the trial is cancellable. ImageIO is not. Do not start work you cannot finish inside the budget. Point `__exact_storage_failed` at this opcode only after the pool job has exited, and surface `compressImage: timeout:` rather than the hardcoded `failed`. A 10 s gap does not cover one 8192² trial.

## Should-fix

**`doc:/` and Windows native paths are not refused where this text says they are.** A1.1 and A1.4, against `data/host/src/native.rs:194-199` and `221-258`, `vendor/ibex/crates/ibex2/src/stdlib/fs.rs:388-393`, `host/web/storage.js:134-140`, `host/web-js/ts-data.js:232-257`, `host/web/storage-request.js:46-51`.

`copyFile` is the wrong model. On documents, `copyFile` is refused because `run_document` rejects rename/copy/realpath before it looks at a destination. `document_request` then **drops** the destination (`let (operation, _, data)`). A Windows path that is not `app:/` or `doc:/` is the opposite of a refusal: `native_filesystem` treats every `fs.*` op as a real disk operation, and `copyFile` is allowed there.

Failing cases:

- `from = "doc:/papers/scan.jpg"`, `to = "app:/tmp/a.jpg"` enters `document_request` and never sees `to`. The error is `"unsupported storage operation fs.compressImage"` or the copyFile document sentence, not `compressImage: needs app:/ paths`.
- `from = "app:/tmp/a.jpg"`, `to = "doc:/papers/scan.jpg"` fails later, if at all, with `"portable storage needs an app:/ destination"`. Wiring the op into the document executor like a write would replace the person’s file. The grant on `doc:/` already allows writes.
- `from = "C:\\Users\\me\\a.jpg"` on Windows is classified as native disk I/O and will not hit an `app:/`-only check placed after that branch.
- On the web, `storage.js` and `ts-data.js` send the call to the document backend when **either** of the first two arguments starts with `doc:/`. A worker has no document backend and answers `unsupported` (“documents live in the page”), which is the wrong code.

Fix: in `native::run`, `storage-request.js`, `storage.js`, and `ts-data.js`, reject unless both strings start with `app:/`, before the `doc:/` and `native_filesystem` branches. One message, code `failed`. Do not add this op to `run_document`.

**A side of 0 is a legal result of the algorithm.** A1.2, same math as `containImageRes` in `compress.ts:90-103`.

`maxDimension` may be 1. After a miss at 51 and 26, `dim` becomes `floor(1 * 0.8) = 0`, and the next size is still tried (`shrinks` is 1, not 4). Independently, an 8000×1 image at `maxDimension: 4000` scales to `floor(8000 * 0.5) × floor(1 * 0.5) = 2000 × 0`. `OffscreenCanvas(2000, 0)` throws `IndexSizeError`. `CGImageSourceCreateThumbnailAtIndex` with max pixel size 0 returns null or the full image. Neither is specified, and an exception on the web becomes `failed` rather than `unfit`.

Fix: if either side is 0, stop and return `unfit` without touching the codec. Pin it with `maxDimension: 1` and with an 8000×1 source. The prose “sizes are `maxDimension × 0.8^k`” is also wrong for any start that is not a clean tower: successive `floor(dim * 0.8)` from 333 is 333, 266, 212, 169, while `floor(333 * 0.8^k)` is 333, 266, 213, 170. The pseudocode matches `compress.ts`. The sentence does not. Record a sequence from 333, not only 4000.

**The memory bound is not true for every format, and the web check is after the decode.** A1.3 Apple row and A1.5, against `host/raster/src/types.rs:13-15` and `host/web/storage-fs.js:204-209`.

`kCGImageSourceThumbnailMaxPixelSize` is only a maximum. JPEG and HEIC are subsampled; PNG, GIF, TIFF, and WebP are not, and ImageIO often decodes those fully before scaling. A 64 MiB PNG at the 64 Mi pixel cap is about 256 MiB of pixels before the `w × h` context. The thumbnail is also not `floor()`-sized, so the draw into an exact `w × h` context is a second resample (usually one pixel of stretch, or an upscale when ImageIO returns the next smaller DCT scale). “Decode once per size” still holds. “Does not grow with the source” does not.

On the web, A1.5 says the pixel cap is checked from the header before decoding. The web paragraph checks `createImageBitmap(...).width/height`, which is the decode. A 64 MiB JPEG whose SOF claims 20000×20000 (400 megapixels, under the byte cap, over the pixel cap) is fully decoded in the page or the module worker, and the `close()` in `finally` runs too late. `readFile` today has the same hole natively: `app_fs_unix.rs` `ReadFile` is an uncapped `read_to_end`.

Fix: stat and refuse `too-large` before `read_to_end`. Parse the header (the Linux host already does this for JPEG, PNG, GIF, and WebP) and refuse before `createImageBitmap` / `CGImageSourceCreateThumbnailAtIndex`. State that the Apple draw is a second scale into exact `w × h`, and that PNG/GIF/TIFF/WebP may allocate the full source bitmap.

**`TypeError` is swallowed if it is validated in the queued call.** A1.4, against `js/src/prelude.js:909-922` and `968-979`, and `host/web-js/ts-data.js:154-158` and `255-258`.

`storageCode` only maps `denied: `, a Windows EISDIR suffix, `(os error N)`, and `busy`. Anything else, including a `TypeError`, becomes `kind: "Unavailable"`, `code: "failed"`. The JS target does the same in `codedError`, and every `fs` method returns `promise.catch(coded)`, so `return Promise.reject(new TypeError(...))` is rewritten. A synchronous `throw` before `storageCall` / `queued()` is the only path that stays a `TypeError` and never occupies a queue slot.

Fix: validate `from`, `to`, and both integer ranges in the prelude wrapper, in `ts-data.js`’s `storageOf`, and in `storage.js` before `enqueue`. Throw synchronously. Do not validate only inside Ibex or `storage-fs.js`.

**The web fallback and the lock placement do not match this host.** A1.3 web row, against `host/web/module-worker.js:1-6` and `61-70`, and `host/web/storage-fs.js:150-181` and `332-347`.

`module-worker.js` is a dedicated worker with no `document`. The specified fallback, a `<canvas>` and `toBlob` “in a window without `OffscreenCanvas`”, throws there (`document` is missing) instead of returning `unsupported`. Current Chrome, Firefox 105+, and Safari 16.4+ do have `OffscreenCanvas.convertToBlob` in workers, so the fallback is the branch that is wrong when it runs.

`createImageBitmap` / `convertToBlob` cannot run inside the IndexedDB transaction in `run()`: the transaction auto-commits on the next turn. The read and the `atomicWriteOwnedFile` have to be two transactions. `lockPaths` today is held only around one transaction. A 20 s encode that drops the lock lets another tab replace `to`, and this call then overwrites that replacement. Same-tab ordering is already provided by the prelude queue.

Fix: if `OffscreenCanvas` is missing, return `unsupported` in a worker; use `<canvas>` only when `document` exists. Hold `lockPaths` on `from` and `to` across the encode, and put the bitmap work outside the IDB transaction. `alpha: false` clears to black; the white `fillRect` has to happen before `drawImage` or a transparent PNG becomes black on the web and white on Apple.

**The codec runs on a Rust pthread with no autorelease pool.** A1.3, against `vendor/ibex/crates/ibex2/src/pool.rs:91-93` (`ibex2-host-task`).

`CGImageSource` and `CGImageDestination` autorelease. Those workers are `std::thread`, not `NSThread`, and they live for the process. A few dozen photos leak every intermediate object for the life of the process; under memory pressure ImageIO has aborted this way.

Fix: `objc_autoreleasePoolPush` / `Pop` around each codec call. Same requirement for the Rust-source path, which calls the codec directly on the host worker.

## What checks out

The restatement of `compress.ts` matches the source on the points that matter. `Math.round` sends halves up, so the probes are 51 then 26 then 13. `q <= 13` resets `lo`/`hi` and increments the shrink count. The fourth shrink is computed and then not encoded, so 4000, 3200, 2560, 2048 are tried and ~1638 is not. A fit sets `lo` to at least 26, so the search climbs instead of shrinking again. Using the encoded byte length instead of `round(base64Length * 3 / 4)` is an intentional difference of at most two bytes, and A1 says so. Running that search in the host as one queued call is the right shape: trials must not enter the module, and fifteen separate storage steps would take the same wall time plus a turn each.

Opcode 121 is unused (`FS_ATOMIC_WRITE_FILE` is 120, `intl_datetime` starts at 130). Exact patch 8 is the next id in `vendor/ibex/EXACT-PATCHES.md`. An `fs` member with a caller-chosen `to`, `fs.read` plus `fs.write`, and Ibex’s existing atomic rename (`app_fs_unix.rs:133-149`) is the right API. `copyFile` itself cannot implement `from === to`: it rejects the same inode and truncates the destination first (`app_fs_unix.rs:323-338`).

The 100 ms budget does not cover this call if it stays an async opcode. `DEFAULT_BUDGET_MS` wraps only the Hermes `__exact_call` / `__exact_settle` turn (`js/src/lib.rs:100`, `745-789`). The codec’s deadline is the continuation, which is the blocker above. `storage-fs.js` is already a dynamic import after first pixel; a dynamic `import()` of `storage-image.js` from inside `compressImage` keeps the codec off the boot path. Do not statically import it from `storage-request.js`.

There is no JPEG encoder in the workspace lock. `image` / `zune-jpeg` appear only under `game/Cargo.lock` and `bench/dioxus/heavy-dx/Cargo.lock`. `host/linux/src/image/jpeg.rs` parses headers and, on Android, decodes. It does not encode. Refusing Linux, Windows, and Android is justified.

## Verdict

**Yes. This blocks implementation.** Do not build it until the timeout and the continuation abort are one failure path: the pool job has finished, `to` is unchanged, and the queue has not moved. The `doc:/` and Windows dispatch, the 0-side, and the web “check after decode” hole should be fixed in the text in the same pass. They are easy to implement wrongly from A1 as it stands.
