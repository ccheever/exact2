## 1. The ideal end state

**A Contract expression is checked notation for a pure subset of TypeScript: if Contract accepts it, it means what TypeScript means apart from a short, closed list of deviations Exact's guarantees require; if Contract refuses it, the refusal names the TypeScript — or the data-module move — that works. Contract accepts only what a view should compute synchronously, boundedly, and identically on every executor.**

The second sentence is as important as the first. D1 in [LLP 1116.016 r2](/Users/ccheever/projects/exact2/llp/1116.016-contract-expressions-are-typescripts.rfc.md:91) states the meaning rule correctly, but the end state Charlie should commit to is a *meaning* standard plus a *view-local admission* standard, not "the common pure operations exist" as a completeness promise. TypeScript's `Array` and `String` surface is open-ended (a new `to*` method every edition); Exact implements every roster row four times — `plan/tables/format.json`, the runner, the web JS runtime, and the Lean semantics with difftest — so completeness is a permanent treadmill bought for a topic that is ~3% of a build's tokens ([LLP 1116.015 §3](/Users/ccheever/projects/exact2/llp/1116.015-what-exact-asks-builders-to-learn.rfc.md:135): expressions 0.20 of 2.06 MB-steps for GPT).

Why this beats the alternatives:

- **(a) Zero-deviation TypeScript subset** is not available at any reasonable cost. Identity equality for lists is meaningless without mutable identity; Swift/Rust strings cannot hold the lone surrogate `"😀".slice(0,1)` produces in JavaScript (LLP 1088 D2); hyphenated names follow CSS per [LLP 1115](/Users/ccheever/projects/exact2/llp/foundation/1115-write-the-web-ship-the-platform.principle.md:54); bounded list work (`MAX_LIST_STEPS` 65,536 in [runner/src/vm.rs](/Users/ccheever/projects/exact2/runner/src/vm.rs:50)) and immutability are the guarantees (T1), not accidents. Zero deviations means giving up the guarantees or the representations.
- **(b) Contract's own small language** was the pre-D1/D2 state and it worked when guided: with today's guide, models wrote `when`/`each`/free functions with 0 walls on those forms ([LLP 1116.015 As built](/Users/ccheever/projects/exact2/llp/1116.015-what-exact-asks-builders-to-learn.rfc.md:334)). Its cost is teach-bytes re-sent every step, and its virtue is honesty — no valley. But D1/D2 are built and kept; reverting now pays a second migration to recover a dialect neither model writes unguided (`if` 71/80, `for` 59/80). The measured A/B was level (tokens 1.03, grade 7.3 vs 7.4), so neither direction wins on tokens; the tie-breaker is that every future builder, human or model, arrives knowing TypeScript and knowing no Contract dialect.
- **(c) Minimal view, all computation in the data module** is the current boundary for sorting, grouping and aggregates ([docs/contract-for-agents.md:51](/Users/ccheever/projects/exact2/docs/contract-for-agents.md:51), [LLP 1017.003 Refused](/Users/ccheever/projects/exact2/llp/1017.003-map-filter-join.spec.md:258)) and it should stay the boundary for *domain* computation. It cannot be the whole answer: filtering by the search field's text, mapping rows to labels, formatting — presentation transforms over view state — belong in the view, which is why `map`/`filter`/`join` were admitted. The line is presentation vs domain, not trivial vs non-trivial.
- **(d) Embed real TypeScript in the data engine** destroys what Contract exists for: expressions run synchronously in render, must terminate within a budget, must give the same value in the Rust runner, the web JS target and Lean, and must be provable. An embedded engine gives none of that and reintroduces a JavaScript UI tier that `rules/DEFERRED.md` refuses.

So the pure-subset-with-deviations direction is right, with admission governed by "a view needs this, bounded, identically everywhere" rather than "TypeScript has this."

## 2. Answers to the three questions

**Q1 — Is D1 the end state? Accept, with the admission gate hardened. Confidence: 80%.**

The rule plus the nine-row deviation table is the right end state. Two amendments before treating it as settled. First, admission must stay LLP 1017.003's "view-only need demonstrated in source," widened only to count a guess-corpus wall when *both* model families hit it, with implementation cost weighed explicitly (r2 §D1 has this; it must not soften into "commonly performed"). Second, `min`/`max` dropping `NaN` should be a scheduled fix, not a permanent table entry: it is the one deviation that is a bug wearing a declaration, it blocks the `Math.*` spellings forever, and every reader who trusts the rule will be bitten by exactly it. What would change my mind: a systematic audit (beyond Astra's five probes) finding materially more accepted forms whose meaning already differs — that would mean the table cannot be kept short and honest, and (b) becomes attractive again.

**Q2 — Accept D2–D6 as stage 1 with D4 last? Accept a trimmed stage; do not pre-accept D4 even as last. Confidence: 75% for the trimmed stage, ~55% against committing D4 now.**

D2 (method capture is a bug), D5 (refusals that lead with a same-meaning edit) and D6 (teach deviations) are cheap and strictly improve honesty; build them. D3 (`some`/`every`) is worth less than it looks — one screen in the post-D2 corpus — and the `filter` rewrite is value-honest but not work-honest: it traps `IterationLimit` where TypeScript returns, and a binding trap poisons the runner (LLP 1017.003 D3). Ship it only with the bound behaviour declared and tested, or wait and build one short-circuit search primitive that also serves `find` in stage 2. D4 should leave the stage entirely and return as its own RFC if evidence appears: 469 real builds show **zero** sort refusals, the 8-of-80 `.sort` screens (from 1 before D2) come from a one-screen harness with no data module to sort in, and its cost is a new two-binder callback instruction, one hand-written merge sort in three executors, and permutation/sortedness/stability proofs. What would change my mind: guided real builds under the *current* method spelling hitting the sort wall and failing to repair via D5's "sort in the data source" message, or a real app where view-local ordering (e.g. a column-header toggle over already-loaded rows) reads clearly worse through a resource argument.

**Q3 — Stage 2 as the next RFC, designed in full before building? Write the RFC now; do not commit to building it. Confidence: 80% write now, 40% prior that building it will prove worth it.**

Design is cheap and stage 1 already depends on its answers (`find`, `xs[i]`, `at` all wait on the absence spelling). The hardest part is not `??`/`?.` lowering — it is flow narrowing (`x != undefined` through `&&`, ternaries, ended by assignment) in both the Rust checker and the Lean typing rules, plus the one-spelling migration that deletes or dual-spells `some`/`none`/`match` across every source, and the nested-option flattening decision (`contract/types/src/bounds.rs` already refuses direct nesting, which helps). The prize is real but narrow: guided builders already learn `match` completely (46 of 80 post-D2 screens; `null` in 0), so stage 2 buys readability of chained lookups (`questions[i].field`), not learnability. What would change my mind toward building: a census of real apps showing `match` nesting is a measurable share of expression lines or repair steps. Toward never: stage 1 showing refused TypeScript *rising* — stage 2 is the largest valley-widener of all.

## 3. Where I agree or disagree with Claude

I agree on Q1's accept, on building D5/D6 now, on deferring `toSorted` pending measurement, and on writing the stage 2 RFC in parallel while gating its build. I disagree in three places. First, Claude keeps D4 inside the stage "landing last and judged on its own"; a pre-accepted expensive item tends to land on momentum, so I would remove it from the stage commitment and make it earn a separate RFC — the default if the wall persists should be a better D5 message plus a taught resource-argument pattern for view-controlled ordering, not a sort opcode. Second, Claude builds D3 now at 80%; I put it near 60%, because the existing refusal in [idioms.rs](/Users/ccheever/projects/exact2/contract/syntax/src/idioms.rs:123) already names a one-line composition, and shipping a rewrite whose trap behaviour differs from TypeScript spends T4 credibility for one corpus screen. Third, Claude accepts the deviation table as is; I would schedule the `min`/`max` NaN fix as part of declaring D1, since a rule whose most likely first violation is enshrined in its own table invites exactly the silent-wrong-app failure T4 exists to prevent.

## 4. Biggest risks, ranked

1. **The roster treadmill.** Every accepted method makes the next a "wall" (`.sort` 1→8 after D2; `toReversed`, `reduce`, `flatMap` queue behind it), and each row is four implementations plus proof surface. Mitigation: the hard admission gate above, a named ES edition as scope, and a standing rule that callback-taking operations need real-build evidence, never guess-corpus evidence alone.
2. **The uncanny valley nets negative.** D1+D2 already traded errors (clean screens 40→37, errors 54→58 in `~/bakeoff/guesses/{pre15,post15}/summary.json`). D5's refusal-with-edit is the right mitigation but is *unmeasured*: the guess corpus is one-shot and never follows the diagnostic. Mitigation: judge on guess-**and-repair** trials and per-model refused-TypeScript rates on held-out features; if they rise, stop widening.
3. **The view becomes a compute tier.** Sorting or folding 5,000 rows in a `derive` runs unbounded-feeling work in render with a poison-on-trap failure mode. Mitigation: keep domain ordering/aggregation in the data module; teach ordering via resource arguments.
4. **A deviation silently produces a wrong app.** A refusal costs one repair step; a same-spelling-different-meaning costs a shipped bug no test may catch. Mitigation: T4 audits against a JavaScript oracle for every roster row, and no D5 edit that itself changes meaning (`localeCompare` → `<` must say it is a different order).
5. **Opportunity cost.** Expressions are 3%; tooling/tests (0.60 MB-steps) and the data protocol (0.49) are the program's levers. Mitigation: timebox this direction; D4 and stage 2 builds compete against those, not against zero.

## 5. What to measure before each commitment

- **Before declaring D1 settled:** a full T4 audit — every accepted expression form and roster row checked against JavaScript on edge values (`NaN`, `-0`, astral strings, empty lists), extending Astra's five probes; and D6 drafted in full with its net bytes and a `contract vocab` lookup count from judging builds, since deleting signatures can move cost into lookups (LLP 1116.013's finding).
- **Before D4 in any form:** a fresh wall census from guided real builds written under the current method spelling (the 469 predate D2); a held-out guess-and-repair trial comparing D5's "sort in the data source" repair success against a hypothetical `toSorted`; a timeboxed Lean spike proving permutation for the chosen merge sort, to price the proof honestly; and a perf probe sorting 5,000 rows in a derive under the step budget.
- **Before building stage 2:** counts from real apps of `match` sites, nesting depth, and option-related repair steps in guided builds; a repo-wide census of nested-option reliance; a rewriter dry run publishing the migration size under "Delete; don't deprecate"; and the T6 whole-app read by Charlie and James of one option-heavy app in both spellings.
- **Throughout:** per-model walls by diagnostic id (all errors, not first) on the 40 features plus 40 held out, run twice at baseline so run-to-run spread is known before "must not rise" is enforced.
