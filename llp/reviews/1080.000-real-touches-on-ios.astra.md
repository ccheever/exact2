# Review: LLP 1080.000 (Real touches on iOS)

**Reviewer:** Astra (codex gpt-6-astra, max), requested by Charlie, 2026-10-03

**Verdict:** NOT READY — contact continuity, delivery attribution, and the proposed proofs need concrete corrections.

1. **High — The compiled-contact fallback does not preserve the existing phase API.**

   D2 replaces independent requests with a predetermined gesture. Knowing argv does not establish when an intervening `layout` or `screenshot` will finish, so scheduled reads can occur after release. The existing smoke uses sequential library calls, precisely the interface the fallback rejects ([smoke.mjs:695](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/scripts/smoke.mjs:695)); the CLI also awaits each operation independently ([agent.mjs:1421](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/scripts/agent.mjs:1421)). G1’s scroll-offset assertion cannot distinguish a continuously held contact from a completed drag.

   **Edit:** Remove the compiled-contact fallback from this phase contract. Require G1 to observe one touch identity across separately acknowledged down/move/hold/reverse/up requests, with no intervening end, while all three reads complete. Run it on simulator and phone. Until that passes, ship real taps and advertise phased contacts as unsupported.

2. **High — The input barrier cannot associate an observed touch with the submitted record.**

   D5 requests `seen:<seq>`, but D1 defines no sequence in requests or replies, no observation baseline, and no mapping from a synthesis record to a UIKit touch. An unrelated touch could satisfy a counter. Conversely, coalesced moves and a stationary hold need not produce one window event per submitted sample. `ProbeWindow` supplies no existing correlation mechanism: it logs selected phases before `super.sendEvent`, omitting moved and stationary phases ([touch.swift:21](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/ios/touch.swift:21)).

   **Edit:** Specify a pre-injection observation baseline, request sequence, observed contact identity, phase-matching rules, and ambiguity/timeout errors. Attribute hits to their actual session and incarnation; a window-wide node number is insufficient for the two-session host. Define bounded storage and overflow reporting. The barrier must service the run loop: requests currently execute serially on the main thread ([Agent.swift:101](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/Sources/ExactKit/Agent.swift:101)).

3. **High — Platform timing still substitutes a different native presentation from the person’s app.**

   D4 promises “what a person sees,” and G3 proposes proving native tab selection. However, agent mode hides the navigation container’s tab bar and retains the authored tablist ([NavigationTabsIOS.swift:103](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/Sources/ExactKit/IOS/NavigationTabsIOS.swift:103)). It also suppresses native navigation bars ([NavigationBarIOS.swift:245](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/Sources/ExactKit/IOS/NavigationBarIOS.swift:245)) and substitutes painted non-confirmation popovers ([MenusIOS.swift:109](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/Sources/ExactKit/IOS/MenusIOS.swift:109)). These branches test `agentMode`, not timing. A replacement tablist may itself project another control; selecting it still does not test the production container’s bar.

   **Edit:** Explicitly include genuine native presentation in the platform-touch launch policy, with observed targeting for its controls. Require G3 to identify the actual container/control exercised. Otherwise cut the production-fidelity claim and narrow the first slice to controls whose presentation already matches.

4. **High — D3 confuses device orientation with interface orientation.**

   `XCUIDevice.orientation` is `UIDeviceOrientation` ([XCUIDevice.h:55](/Applications/Xcode-27.0.0.app/Contents/Developer/Platforms/iPhoneSimulator.platform/Developer/Library/Frameworks/XCUIAutomation.framework/Headers/XCUIDevice.h:55)); the record takes interface orientation. Apple explicitly reverses the landscape assignments between those enums. Device orientation also includes face-up, face-down and unknown states. [Apple’s orientation documentation](https://developer.apple.com/documentation/uikit/uiinterfaceorientation) confirms the distinction.

   The existing `layout.screen` contains dimensions and origin, but no orientation ([AgentIOS.swift:255](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/Sources/ExactKit/IOS/AgentIOS.swift:255)). Comparing width and height cannot detect a 180-degree rotation or distinguish the two landscapes.

   **Edit:** Obtain the owning scene’s effective interface orientation with its coordinate mapping, define the synthesis conversion explicitly, and revalidate orientation and viewport origin—not merely aspect ratio. Add both landscape directions, upside-down/locked-orientation handling, and both sample-host panes to the proof.

5. **High — The proposed `aim` form lacks both requested-point semantics and native-control geometry.**

   D3’s request contains only `id` and `aim`; it cannot validate the explicit point supplied by `down at`. LLP 1012’s implementation treats that point as an offset from the target box ([agent.mjs:1079](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/scripts/agent.mjs:1079)).

   Existing successful activation is not evidence that an equivalent coordinate resolver exists. Projected tabs hide their authored views, and activation simply presses the logical node ([SegmentsIOS.swift:205](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/Sources/ExactKit/IOS/SegmentsIOS.swift:205), [SegmentsIOS.swift:339](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/Sources/ExactKit/IOS/SegmentsIOS.swift:339)). Confirmation geometry is explicitly unavailable ([AgentIOS.swift:283](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/Sources/ExactKit/IOS/AgentIOS.swift:283)).

   **Edit:** Define a side-effect-free resolver accepting the actual viewport point and returning observed native geometry or a named refusal. Specify handling for projected tabs, segments, swipe actions and confirmations. Run it before every mutating branch, including `canvasTap` and `menus.agentTap`; do not derive native item positions from hidden authored boxes.

6. **High — Device-wide input needs explicit ownership, foreground checks and release-on-failure.**

   D1 ends the test on disconnect and eventually kills `xcodebuild`, without specifying release of a persistent touch. The current implementation explicitly attempts `up` before closing ([agent.mjs:797](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/scripts/agent.mjs:797)); LLP 1035.003 D4 requires cleanup on failure, timeout and disconnect.

   The old carrier also refuses input into another window ([pointer.swift:179](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/pointer.swift:179)). The proposed runner instead touches the device screen without a target-app object. An app-local hit test does not establish that the app remains foregrounded, particularly after launching another application—the test runner.

   **Edit:** Specify ownership per destination, including competing sessions; validate the intended foreground app/scene before injection; and release the owned contact on every failure path before teardown. Prove disconnect, runner failure, app backgrounding and geometry-change cleanup while held.

7. **High — The crash regression cannot be driven through the proposed agent path as written.**

   The diagnostic constructs `ProbeWindow` and prints readiness to its log; it never starts `Agent.startSocket` ([touch.swift:300](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/ios/touch.swift:300)). Its launcher supplies `TOUCH_CASE`, not an agent connection ([touch.mjs:73](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/touch.mjs:73)). Meanwhile, the phone carrier resolves a normal app artifact, validates its identity, launches it and awaits its agent connection ([agent.mjs:462](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/scripts/agent.mjs:462)). “Against `com.exact.touch-repro`” supplies none of that integration.

   **Edit:** Extend the existing diagnostic to invoke the same touch backend directly and use its touch log/crash report as evidence, then drive the fixed app through the ordinary agent. Provide exact Bun commands for both early/late launches and cleanup. Treat failure to reproduce on the current OS as inconclusive, rather than assuming the historical crash remains reproducible.

8. **Medium — Window dispatch does not prove recognizer cancellation or completed handling.**

   D5 promises `cancelled` when a recognizer wins, but Apple specifies that recognizer cancellation is delivered through `touchesCancelled(_:with:)` to the view; it does not promise another dispatch through the window override. Delayed touches also separate window receipt from responder delivery. [Apple’s cancellation contract](https://developer.apple.com/documentation/uikit/uigesturerecognizer/cancelstouchesinview) makes that distinction. The cited diagnostic only logs before dispatch ([touch.swift:23](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/ios/touch.swift:23)).

   **Edit:** Define the barrier narrowly as observed window dispatch, with recording after successful dispatch where appropriate. Prove any stronger cancellation observation separately, or mark it unavailable. Keep action success and recognizer outcomes as separate state assertions; never infer them from the planned path.

9. **Medium — Lazy startup depends on an unresolved launch contract with a documented alternative.**

   Q3 treats `UITargetAppPath` as an unknown. The installed Xcode manual declares it mandatory for ordinary UI-test configurations ([xcodebuild.xctestrun.5:142](/Applications/Xcode-27.0.0.app/Contents/Developer/usr/share/man/man5/xcodebuild.xctestrun.5:142)), but also documents `UseDestinationArtifacts`, which avoids installation and substitutes destination bundle identifiers ([xcodebuild.xctestrun.5:233](/Applications/Xcode-27.0.0.app/Contents/Developer/usr/share/man/man5/xcodebuild.xctestrun.5:233)). Neither documentation nor exported selector names proves that the proposed lazy launch preserves the running app.

   **Edit:** Add a concrete `.xctestrun` configuration and make preservation of app PID, socket, foreground state and editor focus a feasibility prerequisite. Specify the SPI signatures and continuation mechanism, not just selector strings. Compare public coordinate taps first: option B already supplies real touches on both destinations, so C’s claimed unique advantage depends on proving independent continuation or measuring a necessary cost reduction.

10. **Medium — The scheduled proof does not exist, and blanket skips can conceal carrier regressions.**

    The async lane invokes UIKit unit tests and `metrics --long`; it does not invoke an iOS smoke ([async.mjs:77](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/scripts/async.mjs:77)). The long metrics path builds/measures macOS ([metrics.mjs:687](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/scripts/metrics.mjs:687)). Furthermore, `smoke-native.mjs` is selected only for the native fixture module ([smoke.mjs:1431](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/scripts/smoke.mjs:1431)); placing Messages assertions there does not automatically run Messages.

    **Edit:** Name the existing async entry point, app builds and invocations that execute each proof. On the designated supported destination, runner startup/SPI failures must fail that async proof; reserve skips for explicitly optional environments. Include cancellation/reversal, held reads, long-press recognition and the promised glass interaction. This requires no sixth blocking check.

11. **Medium — D4’s clock and interactive-animation guarantees exceed the implementation.**

    Platform timing does not initially freeze the runner clock: the iOS main sets `session.clock = 0` only when `agentFreezes` is true ([main.swift:188](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/Sources/ExactIOS/main.swift:188)); otherwise `now()` reads elapsed wall time ([Session.swift:550](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/Sources/ExactKit/Session.swift:550)). A later clock operation assigns the seeked clock ([Agent.swift:423](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/Sources/ExactKit/Agent.swift:423)).

    Likewise, disabling animation on Exact’s programmatic stack updates does not establish that UIKit’s gesture-driven completion/cancellation becomes instantaneous; the interactive delegate path observes UIKit’s transition ([NavigationIOS.swift:552](/Users/admin/.config/tuft/sessions/1791014443.232549/worktrees/exact2/host/apple/Sources/ExactKit/IOS/NavigationIOS.swift:552)).

    **Edit:** State the actual initial-clock behavior or explicitly include its correction. Remove the unproved interactive-pop animation guarantee and verify both timing modes independently.
