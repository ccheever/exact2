The diagnosis matches macOS and Linux, and the harness lock covers the window it describes. `Store::open` takes `owner.lock` with `flock(LOCK_EX|LOCK_NB)` on the `O_CLOEXEC` file from `OpenOptions` (`update/src/store.rs:477`). A `flock` is tied to that open file description, so a `fork` or `posix_spawn` duplicate keeps the lock after the parent `close` until the child's exec closes the `CLOEXEC` copy.

On the toolchain here (Rust 1.97), both of this harness's spawns take the `posix_spawn` path: the owner child is `current_exe` plus env, and the publisher's `bun` is a `PATH` lookup with `current_dir` and piped stdio, which `posix_spawn_file_actions_addchdir_np` handles. `Command::spawn` returns only after that exec. macOS `posix_spawn` is one syscall that copies the fd table, maps the image, closes `CLOEXEC` fds, and only then returns. Linux glibc `posix_spawnp` is `clone(CLONE_VM|CLONE_VFORK)` and the parent thread stays stopped until the child's `execve`. The fork fallback, unused by these two commands, waits on the same event: the parent reads the `CLOEXEC` pipe until exec closes it. Other threads keep running during that window, which is why a loaded machine can lose the race and why releasing the write guard when `spawn` returns is the right boundary.

Every `Store::open` in the `it` binary goes through `open_store`, including `durability.rs` via `open()` and `windows.rs` (Windows-only, and it refuses before the product lock). The only spawns are `spawned` in `publisher.rs:341` and `store.rs:1436`. The child test binary's `open_store` runs after exec, in a new address space, against a fresh `RwLock`; the inherited `owner.lock` fd is already closed.

It does not deadlock. The read guard dies before `open_store` returns, and `Store::open` does not spawn, so a test never holds a read guard across `spawned`. The write guard dies when `spawn` returns, before `wait` or `wait_with_output`. The child's lock is not process-shared. A panic poisons the lock and `into_inner` recovers it without dropping exclusion. `try_lock` does not block, so a store open cannot sit on the read side waiting for a child that needs the write side.

Dropping the `QUEUE` line does not hide a product bug. The hosts open the store once at launch and hold it (`Updates::open` in `host/linux-update`, `Client::open` in `host/apple-update`). A spawn while that owner stays open does not make `try_lock` fail, and a single-threaded reopen after `spawn` returns is safe because exec has already closed the duplicate. The old queue note, waiting or a synchronous release inside `Store::open`, would turn a real second owner into a hang. An embedder that reopens on one thread while another thread is still inside `Command::spawn` can still hit this Unix window; nothing in the tree does that.
