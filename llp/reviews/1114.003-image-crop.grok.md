**Overall assessment**

Admitting a source rectangle on `storage.fs.compressImage`, and leaving the crop chrome in Contract, is the right capability and the right layer. Bluesky's avatar, banner, and post crops are a rectangle in the picked image's upright pixels followed by the compress step exact2 already has. The web has no crop-file API and no crop sheet; a page crops with `drawImage`'s source rectangle and its own handles. Putting that rectangle on the existing call keeps one decode and one lossy encode, adds no grant, queue, or host UI, and stays inside the 2026-10-08 reopen of LLP 1069.002 D6 (a step the app asks for after the pick). The native-sheet and per-app-Swift alternatives are correctly rejected.

**Concerns**

None.

**What it gets right**

- The clone's real gap is the pixel cut, not a widget. `apps/photo-editor` already draws crop handles and reports a rectangle as text; it writes no image. `compressImage` (`storage.d.ts`, opcode 121, `ImageCodec` as `Fn(&[u8], u32, u64, Instant)`) is the only cross-platform place that decodes and encodes. A second call would JPEG-encode twice, or write the PNG intermediate Bluesky's web client writes and then read it back under the 64 MiB cap.
- The rectangle matches the platforms the codecs already use. `Picked.width` and `height` are upright (`Picker.swift` `pixels`; runner `Picked`). Apple's codec transposes EXIF orientations 5–8 before the search; the web draws the bitmap from `createImageBitmap` with orientation applied. `{x, y, width, height}` is `DOMRect` and `drawImage`'s source rectangle. Running A1.2's `contain` and quality search on the cropped size, never upscaling, is the same rule an uncropped image already follows.
- A host crop sheet would be a new UI the web does not have. `UIImagePickerController.allowsEditing` only square-crops that controller's own pick or capture. PHPicker and AppKit have no crop sheet. The agent can already `tap … drag` and `tap … pinch` a Contract screen (`docs/contract-for-agents.md`); it cannot drive a system sheet. `transformDragFor` is enough for a fixed 1:1 or 3:1 frame: the target stays a full-size box in a clipping parent (`kernel/src/transform.rs`), which is the existing photo-viewer gesture. A free crop is `pan` on handles. Neither needs a new tag, grant, or kernel row.
- Bounds stay A1's. The source-pixel cap still applies to the whole image, because both codecs have to decode it. The call still needs `fs.read` on the source and `fs.write` on the destination. Nothing runs at boot. Linux, Windows, and Android stay `unsupported`, as they are for compress. `rules/DEFERRED.md` does not mention cropping; the only prior decision this moves is the "cropping stays out" sentence in the 2026-10-08 reopen of D6, and the RFC asks Charlie to reverse it in the open.

**Questions for Charlie**

No change. Admit the rectangle as Amendment A2. Leave rotation out: EXIF orientation is already applied, and no clone item asks for a quarter-turn. The ruling text in §6 D6 already keeps filters and any other edit out, which is the line worth holding so this does not become an image editor one option at a time.
