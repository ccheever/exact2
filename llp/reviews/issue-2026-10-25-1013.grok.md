Adopt ask 1. Let one component be written in several files that the loader concatenates into a single component before type checking, analysis, expansion, and the Lean embedding. That is the change that puts `examples/t3-code/app.contract` under the 1,500-line cap without changing what a program means. Leave ownership where it is, and do not exempt the file.

The root is one scope. `derive transportAnswering` reads `pending` of mutations from every feature (`examples/t3-code/app.contract:141`), and `resource data` takes those features' state as arguments (`app.contract:79`). A mounted child may own state and actions today, but it cannot own the resource those names feed, and a parent cannot name a child's slots. Moving ownership therefore moves the same closure into another file. Member files keep the scope, keep the authored names a reload carries, and disappear before the semantics.

## The three asks

**1. A component declared across files. Do this.**

It is a loader change. `use` already parses each file with its own `source_id` (`contract/cli/src/sources.rs:710-719`), scopes that file's imports (`sources.rs` `fn scope` at 878, `fn scope_of` at 1135), and then `merge`s the files into the one `File` later passes read (`sources.rs:1300-1384`). `merge` concatenates whole components (`components: all!(components)` at 1383). It does not append one component's members onto another. The root is that list's first component: the root file's first component (`docs/contract-grammar.md:257-258`, `contract/types/src/lib.rs:1379`).

What stays put, and why the cost is small:

- Member names are not file-scoped. The scoper leaves a value `Expr::Ident` unchanged (`contract/syntax/src/scope.rs:864-868`) and binds only the members of the component it is walking (`scope.rs:345-361`). After concatenation, `check_component` resolves them on one component (`contract/types/src/component.rs:74`). A members file still `use`s the shapes and `fn`s it calls, as every file does (`docs/contract-grammar.md:220-227`).
- Spans already name a file (`contract/syntax/src/lib.rs:63-71`, `sources.rs:118-126`). A diagnostic in a members file points at that file.
- Reload carries a root slot by authored name (`llp/1017.000-contract-v1-1.spec.md:336` and `:381`). Concatenation does not rename slots. The Lean semantics has no reload (`semantics/README.md:859-861`) and embeds the expanded root, not the source files (`semantics/README.md:5-7`). `Runtime.lean` and `CompSem.lean` do not change.
- `type-duplicate-name` already walks the merged member lists (`component.rs:86-109`). Its message cites `first.line` only (`component.rs:104`), so a cross-file duplicate needs the first span's path. That is the one diagnostic to extend.

What it complicates: state initializers see only states declared earlier (`scope.rs:345-352`), so a `members` line has to be a splice point, not an unordered bag. `contract fmt --uses` (`docs/contract-grammar.md:225-227`) must keep fixing per-file imports and must not ask a members file to import sibling state. A file-local search will not find a state declared in another members file; navigation has to ask the compiler, which already keys names by `Span`.

**2. Resources, mutations, and tasks on a component that stays mounted. Do not do this for this problem.**

The prohibition is real and narrow. Only the root may declare a resource, mutation, or task, except a child's argument-free `exactViewport()` or `exactPage()` (`docs/contract-grammar.md:309-313`, `contract/syntax/src/inline.rs:53-59`). The checker is `check_children` (`contract/types/src/lib.rs:1372-1400`), with the long refusal in `child_owns` (`contract/types/src/tasks.rs:15-24`). The reason is instance lifetime: a row must not open N requests, and only the root has a clock (`lib.rs:1375-1378`). The same refusal covers `sequence` (`contract/types/src/tasks/sequences.rs:19-21`). Device-fact resources are hoisted to one root resource per child component (`inline.rs:273-280`, `semantics/Contract/Components.lean:48-49` and `:97-104`).

Children already own state, derives, and actions, and the expander lifts those into the root (`inline.rs:135-136`, `llp/1017.000-contract-v1-1.spec.md:324-337`). A use outside every region becomes an ordinary root slot; a use inside `when`, `match`, `each`, or a slot fill is owned by that arm (`llp/1017.000:362-389`). So "stays mounted" is not a property of the component. It is a check on every use site, including fills inlined at `children`.

Doing it means teaching `expand_with_sites` (`inline.rs:243-271`), which today copies only the root's resources, mutations, and tasks, to lift a child's as well, and teaching `Contract/Expand.lean` (the transcription of that inliner, `semantics/README.md:39-40`) and `Components.lean` the same. A task, a mutation's `then`, and a `sequence`'s `ended` name a parameterless action of the same component (`contract/analyze/src/lib.rs:266-353`). `send` and `refresh` look up that component's own mutations and resources (`contract/types/src/actions.rs:211-218` and `:243-249`). Those rewrites have to follow the lifted names, which are `name#N` (`inline.rs:47-50`). Moving a slot off the root changes the name a reload carries.

If the lift is limited to uses outside regions, the expanded program is still the root's, and the runner can stay. The file does not get small. The issue's own closure leaves 17 members, 72 lines, outside the root's resources, tasks, mutations, and `provide`. I did not recompute that closure. The coupling that makes it plausible is on the page: one derive and one snapshot name the rest of the app (`app.contract:79` and `:141`). A parent resource cannot read a child's state. Provide and inject flow downward (`contract/syntax/src/ast.rs:672-679`). The 2,900-line closure would land in `T3Window` or in whichever ancestor still sees every name. `T3Window` is already the view half, at 1,117 lines (`examples/t3-code/src/shell/app-window.contract`), and the root passes it one argument per name (`app.contract:2998`). More component boundaries add more of that list.

The ownership change that would match the web is the one already written down for navigation rows (`llp/1035.005.000-contract-after-the-apps.rfc.md:304-341`): a stack entry owns its requests, and any other `each` stays refused. That changes open and close, bake, disposal, and late replies, and it still does not partition a single snapshot. It is a separate design, not the way through this cap.

**3. A named exemption. Do not do this.**

The budget is a trade. `rules/RULES.md:16-18` says a limit gets exceptions and a trade does not, and that generated files are exempt because they are built and not committed. `scripts/caps.mjs:146-186` reads the number from that line and, only if the line also says `baseline N`, allows N oversize files of any path. The rule has no baseline, so the allowance is 0. A named path would be new parsing in `caps.mjs` and a standing exception the rule forbids. The generated-file marker (`caps.mjs:36` and `:163`) would silence the check for a file that is committed. The issue is right to reject that. The next shell hits the same wall; Interview's root is already the documented case (`llp/1035.005.000:310-314`).

## Any other option

No app-side split meets the cap, and I would not add one.

- Pure `fn`s cannot absorb the actions. A `fn` is one expression with no state (`contract/syntax/src/ast.rs:528-532`, `docs/contract-grammar.md:102-103`). `composerKeyEvent` decides `preventDefault()` in the event's commit (`app.contract:1597-1628`). A data-crate round trip is a later commit. That part of the issue holds.
- Calling a root action from a child is already same-commit (`docs/contract-grammar.md:479-482`, `docs/contract-for-agents.md:486-490`). It is why an action that sends can shrink to a header and a `send`, and why the floor stays above 1,500. I did not reproduce the author's ~1,800.
- Raising the cap, or setting `baseline 1`, spends the budget on every future file. `caps.mjs:152-153` treats a baseline as a retrofit count, not a permit for one path.
- Instance-owned requests, as in LLP 1035.005.000 D5, stay worth doing for screens on `stack(nav)`. They are not a substitute for member files, and member files do not block them.

## Sketch of the language change

No new runtime construct. A component body may contain `members "relative/path.contract"`, spliced in source order at that line. The path rules are the rules of `use` (`docs/contract-grammar.md:206-208`). The same file included twice, a cycle, or a path that escapes the root is refused with the existing `use` refusals.

A members file is parsed with its own `source_id`. Its header is `members T3Code`. The name must be the component that includes it (`contract-members-owner`). It may contain `use`, `shape`, `fn`, and the other file-level declarations a file already may contain. Its component-shaped body may contain `state`, `derive`, `resource`, `mutation`, `action`, `task`, `sequence`, and `provide`. It may not contain `props`, `inject`, `slot`, or `view` (`contract-members-section`): those stay one section, in the component's primary file (`docs/contract-grammar.md:309-310`). `provide` lists concatenate. A name declared in two pieces is `type-duplicate-name`, and the message names both files.

The loader appends the members onto that component and does not push a second `Component`. Every later pass, including `contract lean`, sees one component. A child component may have member files too. Concatenation does not weaken `type-child-resource`: resources in a child's members are still refused. Per-file `use` scoping runs before the splice, so a members file names the shapes and functions it uses and does not see another file's unless it does. Member references are resolved on the spliced component.

Reload identity, request lifetime, and the plan are unchanged because the names and the expanded root are unchanged.
