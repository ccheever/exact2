NOT READY

**Overall assessment**

The browser-shell use case earns reconsideration of LLP 1020’s deferred capabilities. A native top-level guest selected by `partition`, with `sandbox` forbidden alongside it, is a defensible design. It avoids the specific mistake of pretending a native top-level document implements iframe sandbox semantics.

However, r1 still has material gaps in isolation, messaging, navigation observability and production automation. Its web subset and consumer-replacement claims also overstate what the proposed implementation delivers. These need resolution before acceptance, beyond answering the existing ruling questions.

This was a read-only review against checkout `c31add28a6361dfd4b97e24d1be80553eabd74cd`, the requested documents, relevant source files and local Apple SDK headers. No web access, edits or runtime probes were performed.

**Strengths**

- **D1:** Names the topology change explicitly and refuses `partition` plus `sandbox`, rather than approximating sandbox enforcement.
- **D2–D3:** Preserves authored `src` semantics and distinguishes reporting navigation from vetoing it.
- **D5:** Preserving WebKit’s configured popup and opener relationship is the right foundation for OAuth.
- **D6:** Starts from measured CSS behavior and keeps app-specific zoom steps out of the framework.
- **D7–D10:** Separates screenshot artifacts, recording and automation; acknowledges untrusted iOS input and unavailable web capture.
- **§10–§11:** Provides stages, an implementer, an acceptance fixture and explicit acknowledgment of the outstanding DEFERRED trade.

**Concerns**

1. **Material — The web subset silently removes the defining isolation guarantee.**  
   D1 makes `partition` inert on web. Consequently, two named profiles do not receive separate stores, and an “incognito” frame can use the browser’s ordinary storage. A same-origin unsandboxed guest can also access the host page. This is materially different from a native isolated browser tab and conflicts with LLP 1133 D8’s visible-absence rule.

   The summary additionally promises cross-origin `reload`, while §10 correctly limits cross-origin commands to `navigate`. An iframe `load` notification cannot establish successful loading or the actual cross-origin destination, so mapping it to `navigatesuccess` with the last authored URL risks reporting false success. Reattaching listeners at `load` also misses events emitted earlier in the new document. A local server on another port is cross-origin.

   **Resolve:** Define one authoritative capability matrix, expose unsupported isolation to the app, and require an explicit fallback before using an ordinary iframe. Distinguish requested URL from observed URL and load notification from verified success.

2. **Material — Reusing the direct-message bridge changes arbitrary websites’ behavior and introduces a popup attribution risk.**  
   The existing injected listener calls `stopImmediatePropagation()` on self-posted messages before forwarding them. That was an acknowledged limitation for controlled fixtures; browser-shell pages can legitimately use `window.postMessage` internally. See `host/apple/webarm/WebArm.swift:267`.

   The receiver checks main-frame status and origin, but not the originating web-view instance (`WebArm.swift:629`). D5’s popup inherits WebKit’s configuration; the clone explicitly guards against popup messages entering its parent’s favicon handler using `message.webView === page` (`T3BrowserFavicon.swift:40`, `:84`).

   **Resolve:** Specify browser-shell messaging separately from fixture-frame messaging. Preserve ordinary self-message delivery, retain document-generation revocation, and bind callbacks to the owning web view as well as its document and origin. Test same-origin popups and navigation during an outstanding reply.

3. **Material — “Deny all guest permissions” is an intention, not yet a per-host enforcement plan.**  
   Refusing sandbox emulation does not automatically preserve restrictions previously supplied by iframe policy. The clone explicitly denies camera/microphone (`T3BrowserSession.swift:391`); that does not prove denial of geolocation, clipboard or notifications.

   The local SDK documents media capture’s omitted delegate behavior as **prompt**, and its public geolocation permission delegate is available only from macOS/iOS 27 (`WKUIDelegate.h:163`, `:302`). The project supports macOS 14/iOS 17 (`host/apple/Package.swift:104`).

   **Resolve:** List the enforcement mechanism and minimum supported version for each promised denial, including popup descendants and the web fallback. Where enforcement is unavailable, narrow support or declare the limitation. This is necessary to substantiate D1’s claim that the old security class does not return.

4. **Material — The navigation record lacks a complete lifecycle contract.**  
   D2 acknowledges cross-document timing and title/icon deviations, but “the names and fields are the API’s” is too strong: this is an aggregate browser-state record, not the standard `NavigateEvent` shape. At navigation start, `currentEntry.url` also does not identify the pending destination.

   Define what happens on redirects, same-document transitions, explicit stop, superseded loads, failed traversal and crash recovery. Suppressing cancellation without another terminal update can leave app state showing `loading: true`. Recovery must distinguish the authored `src` from the current page: today’s arm calls `serve()` after a crash, which reloads from `src` (`WebArm.swift:664`, `:370`); the clone recovers its pending/current URL (`T3BrowserSession.swift:346`).

   **Resolve:** Add an event sequence table with destination/current URL semantics, navigation identity, ordering and terminal outcomes. Either retain the borrowed names with a complete deviation list or adopt browsing-context terminology consistently.

5. **Material — Partition lifetime and clearing are underspecified.**  
   D1 says an ephemeral partition lasts for the session, then says Apple retains it only while a frame uses it. Those differ when the last tab closes and another opens. The example also assigns every incognito tab the same partition, which needs explicit scoping guidance.

   Changes to a mounted frame’s `partition` need defined reconstruction and cancellation behavior. D4 has no completion/error channel, although clearing is asynchronous and can race live pages writing data. Clearing all data and deleting a persistent store are also distinct operations.

   **Resolve:** Specify ownership, namespace, lifetime, partition-change behavior and observable clearing completion. Declare that `clearSiteData` borrows the header’s type vocabulary but clears an entire profile across origins, rather than implementing the header’s origin-scoped semantics.

6. **Material — Popup policy is internally inconsistent and misstates the consumer.**  
   D5 says a frame without `windowopen=` opens no popups, but the `new-window` row opens a native popup independently of that handler. It is also unclear which behavior applies to ordinary sandboxed frames; D10 explicitly uses `windowopen` on one.

   The claim that both implementations refuse POST window requests is incorrect. The clone routes qualifying requests back into the current tab with the original request body (`T3BrowserSession.swift:379`); its policy distinguishes these from tab creation (`T3BrowserSession+Links.swift:72`). The oracle likewise distinguishes `"navigate"` from `"deny"` (`apps/desktop/src/preview/Manager.ts:484`).

   **Resolve:** Supply a policy table covering partitioned/unpartitioned frames, handler presence, sandbox tokens, popup features and POST requests. Q4 should distinguish notification from permission: `windowopen` and `allowpopups` solve different problems.

7. **Material — Production agent behavior is conflated with the development substitute.**  
   D9 allows a possible production automation grant, while §9 says substitute behavior is unreachable in production. Yet D5 relies on “under the agent” to save downloads automatically.

   The consumer has a separate production control state: automation marks a page agent-driven, and downloads then go to artifacts without a panel (`T3BrowserAutomation.swift:405`; `T3BrowserCapture.swift:269`). A grant alone does not describe that behavior.

   **Resolve:** Separate development substitution, production automation authority and human/agent control ownership. Define prompt behavior, download destinations, cancellation and focus restoration. For the BiDi-inspired binding, specify supported action types, input-source identity, release/cancellation behavior, result serialization and unsupported trusted-input semantics. The current JSON result and untrusted-input substitutions are additional protocol deviations.

8. **Material — LLP 1133 D9 is not fully answered.**  
   The ceiling test counts the consumer’s seventeen rows, whereas D9 asks for common uses of each platform framework and the tier reaching each. A post-construction `WKWebView` hatch with framework-owned delegates cannot, by itself, demonstrate access to construction-time configuration or delegate-based capabilities.

   The checklist also lacks explicit request classification, a complete ownership/forwarding contract, binary-cost measurements and consumer acceptance on each supported consumer target. Linux/Windows should distinguish **later** from platform absence; Expose is omitted. D3’s interpretation of “HOST_COMMANDS stops growing” needs an explicit ruling rather than relying solely on D5’s packaging exception.

   **Resolve:** Expand the checklist with those concrete answers and label unmeasured items as acceptance gates. The named trade or waiver remains required by `rules/RULES.md:46`.

9. **Material — Screenshot coordinates and PDF substitution need compatibility rules.**  
   D7 specifies clipping in guest CSS pixels, but `WKSnapshotConfiguration.rect` uses view coordinates (local SDK `WKSnapshotConfiguration.h:37`). Zoom, magnification and scrolling therefore require an explicit conversion. The consumer’s native input already performs such scaling (`T3BrowserAutomationInput.swift:16`).

   D10 also replaces a browsing context with `PDFView` without defining what happens to navigation commands, partition, sandbox, zoom, capture or the tier-3 hatch.

   **Resolve:** Define capture coordinates, clipping bounds, output scale and request-correlated errors. Add a PDF applicability table, including HTML↔PDF transitions, links and sandbox behavior.

10. **Minor — Several equivalence and deletion claims need qualification.**  
    `reloadFromOrigin()` documents conditional end-to-end revalidation, not an unconditional cache bypass (local SDK `WKWebView.h:251`). D3 should qualify the `ignoreCache` mapping or demonstrate equivalent behavior.

    Replacing the favicon implementation with the first icon URL loses candidate fallback, `/favicon.ico` fallback and image normalization (`T3BrowserFavicon.swift:26`, `:95`, `:154`). PDF `autoScales` alone does not reproduce the clone’s explicit short-document positioning (`T3MediaPreview.swift:375`).

    **Resolve:** Mark these as deliberate differences or retain the relevant acceptance cases. Make §12’s deletion totals conditional on verified replacement.

**Suggestions**

- Keep `partition` as the native browser-shell opt-in and keep `sandbox` incompatible with it. The coupling is acceptable if its lifecycle and unsupported-host behavior are explicit.
- Add a compact conformance matrix: profile separation, last-tab closure, redirects, stop, crash recovery, self-messaging, OAuth popups, POST targets, permission denial, zoomed capture and production-agent downloads.
- Treat D6’s Chrome measurements as the layout oracle, but measure Apple separately. `pageZoom` is documented as scaling page content (`WKWebView.h:509`); equivalent outer geometry and guest-visible metrics still need proof.
- Keep D9 independently gated. The core browser shell should have a complete acceptance case without automation or B10.

**Open questions**

The existing topology, sandbox, automation and trade questions are appropriate. Add these before ruling:

- May web silently discard partition isolation, or must the app explicitly choose a fallback?
- Are popup defaults enabled only for partitioned browser-shell frames?
- Which permission-denial guarantees hold on the minimum Apple versions?
- Does production automation access human profiles, and how does it handle dialogs and downloads?
- Is the event surface Navigation API-inspired state reporting, or a browsing-context lifecycle API?
- Which consumer differences are accepted, rather than counted as equivalent replacements?

Q9’s general element capture can be decided separately. Q10 should be presented as an explicit acceptance of lost functionality. Q11 is a working-set trade, not a design uncertainty.

**Recommended next step**

Revise to r2 with the isolation, messaging, lifecycle, policy and checklist answers above; then obtain the named DEFERRED trade or waiver and a separate D9 ruling. Retain the proposed stages, but make the claimed consumer deletions depend on their acceptance drives.
