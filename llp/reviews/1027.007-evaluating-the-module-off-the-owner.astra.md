# RFC review: LLP 1027.007 r1, 2026-10-21 (astra)

- **Family:** OpenAI, `codex exec -m gpt-6-astra -c model_reasoning_effort="xhigh" --sandbox read-only`, run in the worktree at `e3e8426e32`.
- **Method:** mutually blind to the other family, which got an identical brief (the grok brief adds tool rules). Brief sha256 `c36031ace273f76773a9da50cc02afec7aa39043a58a2969209d1c68f4fb2d42`.
- **Reviewed revision:** `llp/1027.007-evaluating-the-module-off-the-owner.rfc.md` r1, before any fix.

1. **P1 — The `unsafe Send` safety argument is not established.** §4/D3 treats quiescence, synchronized publication, and a permanently allocated loader stack as sufficient. The checked-in ibex contract requires **all adapter methods, including destruction, on the runtime’s owner thread**; it does not explicitly authorize changing that thread ([ibex2_jsi.h:249](/Users/ccheever/projects/exact2-wt-startup/vendor/ibex/crates/ibex2/include/ibex2_jsi.h:249)). Its adapter retains JSI functions, values, and runtime references—not merely Rust `Arc`s and atomics ([install.cc:451](/Users/ccheever/projects/exact2-wt-startup/vendor/ibex/crates/ibex2/src/bindings/install.cc:451)). The engine implementation needed to verify the Hermes stack-guard claim is outside this checkout ([EXACT-PATCHES.md:24](/Users/ccheever/projects/exact2-wt-startup/vendor/ibex/EXACT-PATCHES.md:24)). Keeping the loader stack alive addresses the stated address-reuse scenario; it does not establish the complete VM transfer contract. **Change:** make implementation conditional on a revision-specific engine/adapter ownership audit, including GC, interrupts, queued microtasks, and destruction. Restrict construction of `Loaded` to a state with no native object, canvas environment, store borrow, or shared owner-side `Rc` graph. Explicitly amend [1027.002 D2](/Users/ccheever/projects/exact2-wt-startup/llp/1027.002-optional-worker-execution.rfc.md:150) and [1072 T1](/Users/ccheever/projects/exact2-wt-startup/llp/1072-building-rows-off-the-main-thread.rfc.md:62). This is a missing safety proof, not a demonstrated crash.

2. **P1 — D3 and D6 recreate the owner blockage the RFC intends to remove.** D3 says `prepare_data` waits on the owner when loading is unfinished; D6 repeats that choice at first-pixel activation. D5 and §6 instead promise pending activation and a wake. Main-thread runtime calls synchronously wait for the owner ([Owner.swift:98](/Users/ccheever/projects/exact2-wt-startup/host/apple/Sources/ExactCore/Owner.swift:98)), so an owner-side receive blocks `tellPage`, input, and other sessions just as evaluation currently does. The host already has a nonblocking pending/wake branch ([activation.rs:36](/Users/ccheever/projects/exact2-wt-startup/host/apple/src/activation.rs:36)). **Change:** require nonblocking readiness checks in both stages, with completion and wake registration synchronized against lost wakes. Also define the relevant source API explicitly: current `preload` permits image preparation but prohibits creating app instances ([source.rs:453](/Users/ccheever/projects/exact2-wt-startup/runner/src/runner/source.rs:453)).

3. **P1 — Cancellation, supersession, and destruction have no ownership protocol.** D3 specifies a channel transfer; §6 merely asks that destruction during loading drop the module on the owner. A session can replace its host while retaining its runtime handle ([abi.rs:571](/Users/ccheever/projects/exact2-wt-startup/host/apple/src/abi.rs:571)); Swift separately increments its generation on boot, replacement, and destruction ([Session.swift:933](/Users/ccheever/projects/exact2-wt-startup/host/apple/Sources/ExactKit/Session.swift:933), [Session.swift:1442](/Users/ccheever/projects/exact2-wt-startup/host/apple/Sources/ExactKit/Session.swift:1442)). Consequently, a runtime handle alone cannot identify a valid completion. Closing a channel also does not stop evaluation: existing `Placed` destruction only closes its sender ([placed.rs:858](/Users/ccheever/projects/exact2-wt-startup/data/src/placed.rs:858)). One hung initialization could therefore occupy the process’s sole loader indefinitely. **Change:** specify per-incarnation job identity, cancellation of queued jobs, interruption of running initialization, rejection of stale results, and destruction responsibility before and after transfer—including failed sends. Keep interrupts generation-specific; `Watch` contains only one engine slot ([watch.rs:48](/Users/ccheever/projects/exact2-wt-startup/js/src/watch.rs:48)). No teardown path should wait on the owner for the loader to finish.

4. **P1 — At `exact_create`, the module to load has not been selected.** D2 names the bake’s bytecode and admitted metadata; D6 starts loading at `exact_create`. That function currently creates an empty registry entry, without constructing the data source or selecting delivery ([exports.rs:57](/Users/ccheever/projects/exact2-wt-startup/host/apple/src/abi/exports.rs:57)). `boot_selected` later selects an installed plan/module pair, validates its replacement, and can fall back to the embedded pair ([abi.rs:440](/Users/ccheever/projects/exact2-wt-startup/host/apple/src/abi.rs:440)). Pairing checks must precede execution ([paired.rs:20](/Users/ccheever/projects/exact2-wt-startup/js/src/paired.rs:20)). **Change:** launch from an immutable descriptor of the selected, admitted incarnation, at the earliest point that descriptor exists. Starting at creation requires moving selection/admission there explicitly. Otherwise the loader may evaluate obsolete embedded code, or its completion may be adopted into a different plan.

5. **P1 — The proposed loaded instance has no source signatures, and `Spawn::Adopt` does not reach the main-placement path.** D2 constructs a fresh `Module::new` and loads it; D3 then adopts it and activates “as today.” Loading does not bind a plan. `bind` builds the signatures ([source.rs:287](/Users/ccheever/projects/exact2-wt-startup/js/src/source.rs:287)), and an answer without one fails `UnknownSource` ([lib.rs:851](/Users/ccheever/projects/exact2-wt-startup/js/src/lib.rs:851)). Furthermore, `Placed::activate` returns directly for main placement before examining `Spawn` ([placed.rs:580](/Users/ccheever/projects/exact2-wt-startup/data/src/placed.rs:580)). **Change:** specify an actual main-placement adoption operation, then bind the adopted instance to the active plan on the owner before exposing readiness. Preserve the template’s configuration, including limits, agent seed, factory, document owner, and canvas roster; do not obtain signatures by sharing the runner’s plan graph across threads.

6. **P1 — D4 handles the Rust factory but omits the hosted native-module binding.** Besides `native_factory`, load captures `native_slot.hosted()`, `hosted_call`, and the `later` flag into `HostState` ([lib.rs:609](/Users/ccheever/projects/exact2-wt-startup/js/src/lib.rs:609)). The bridge currently installs those hosted callbacks immediately before preparation or activation ([abi.rs:619](/Users/ccheever/projects/exact2-wt-startup/host/apple/src/abi.rs:619)). A loader that evaluates earlier can capture “no hosted module”; sharing the slot does not update those cached fields afterward. An already-loaded module’s `load()` simply returns ([lib.rs:456](/Users/ccheever/projects/exact2-wt-startup/js/src/lib.rs:456)). **Change:** separate engine initialization from complete owner-side native binding, covering both factory-backed and hosted modules before any answer. D7 needs the corresponding split on a worker: starting today’s worker construction before pixel also runs its Rust native factory before pixel, contrary to the existing post-pixel contract ([1027:1486](/Users/ccheever/projects/exact2-wt-startup/llp/1027-typescript-data-sources.rfc.md:1486)).

7. **P1 — Storage cannot both be configured during load and activated unchanged afterward.** D2 says directories depend on app ID alone; actually they depend on agent/scratch settings, the app-group root, and `HOME`, and may deliberately be absent ([picker.rs:22](/Users/ccheever/projects/exact2-wt-startup/host/apple/src/picker.rs:22)). Current activation also empties a fresh scratch tree and publishes picker roots ([host.rs:728](/Users/ccheever/projects/exact2-wt-startup/host/apple/src/host.rs:728)). Calling that activation unchanged on the adopted module fails because `configure_storage` refuses a loaded instance ([source.rs:72](/Users/ccheever/projects/exact2-wt-startup/js/src/source.rs:72)). D2 also omits `document_owner`, which storage captures in its resolver during creation ([storage.rs:47](/Users/ccheever/projects/exact2-wt-startup/js/src/storage.rs:47)); setting the module’s field later cannot repair that closure. **Change:** resolve the complete storage configuration and document identity before loading, finish required scratch initialization first, and separate owner-side root publication from configuring an already-created engine.

8. **P1 — Stage B needs a separate activation gate, especially for worker placement.** D6/D7 start loading early while D8 promises unchanged answers and transactions. Existing readiness is not sufficient: `Module::ready` means the engine exists ([source.rs:247](/Users/ccheever/projects/exact2-wt-startup/js/src/source.rs:247)), while `Placed::ready` becomes true as soon as a worker owner exists ([placed.rs:510](/Users/ccheever/projects/exact2-wt-startup/data/src/placed.rs:510)). Boot uses readiness to decide whether to seed kept answers ([runner.rs:1003](/Users/ccheever/projects/exact2-wt-startup/runner/src/runner.rs:1003)). Starting a worker early can therefore change first-frame behavior and admit calls before the intended activation boundary. **Change:** distinguish “loaded” from “activated and callable.” Preserve the compiled/kept first frame, restore native/document bindings, adopt any pending shared-store revision, and only then perform the existing `data_ready_after_store` settlement, including queued mutations ([activation.rs:51](/Users/ccheever/projects/exact2-wt-startup/host/apple/src/activation.rs:51)).

9. **P1 — Load failure and template retirement need explicit terminal behavior.** D2 delegates failure reporting to existing activation; §6 promises reporting once. Existing activation consumes `source_prepared` and permits another activation attempt after failure ([activation.rs:44](/Users/ccheever/projects/exact2-wt-startup/host/apple/src/activation.rs:44)); a test explicitly requires that retry ([activation_tests.rs:141](/Users/ccheever/projects/exact2-wt-startup/host/apple/src/activation_tests.rs:141)). Without a defined state, a consumed loader error could lead to waiting forever or reloading inline. Retirement also has observable side effects: dropping even an unloaded template calls `unload`, which clears its shared `native_slot` ([lib.rs:635](/Users/ccheever/projects/exact2-wt-startup/js/src/lib.rs:635), [lib.rs:1347](/Users/ccheever/projects/exact2-wt-startup/js/src/lib.rs:1347)). **Change:** define failed, cancelled, delivered, and adopted states and an explicit retry policy. Retire the template before installing the adopted native handler, or transfer cleanup responsibility. Carry diagnostics with the result; drain engine logs only on its current owner, since log extraction mutates the engine ([shim.cc:487](/Users/ccheever/projects/exact2-wt-startup/js/src/shim.cc:487)).

10. **P2 — Stage A removes evaluation waiting, not every post-pixel main-thread stall.** D5 promises every main-thread call is answered “at once,” and §6 asks for a trace showing no waits after pixel. Activation still synchronously invokes `runtime.dataReady()` ([SessionActivation.swift:49](/Users/ccheever/projects/exact2-wt-startup/host/apple/Sources/ExactKit/SessionActivation.swift:49)); the owner then runs deferred answers, queued mutations, and settlement ([kept.rs:510](/Users/ccheever/projects/exact2-wt-startup/runner/src/runner/kept.rs:510)). D4 also leaves arbitrary native-factory work there. Further, loading does not drain microtasks ([shim.cc:308](/Users/ccheever/projects/exact2-wt-startup/js/src/shim.cc:308)); initialization work queued in promises can run during the first answer’s drain ([lib.rs:890](/Users/ccheever/projects/exact2-wt-startup/js/src/lib.rs:890)). **Change:** narrow the guarantee to eliminating waits caused by module evaluation. Measure native binding, first answers, microtasks, and activation commit separately. Worker-placement timings do not establish those costs for retained inline semantics.

11. **P2 — The Stage B waiver argument understates the change and uses an inadequate acceptance bar.** Q1 calls the cost the rule’s “letter” plus abandoned-launch energy. The actual rule deliberately budgets boot work **by construction and count, not timing** ([RULES.md:53](/Users/ccheever/projects/exact2-wt-startup/rules/RULES.md:53)); LLP 1027 also explicitly defers executor creation itself ([1027 D4](/Users/ccheever/projects/exact2-wt-startup/llp/1027-typescript-data-sources.rfc.md:457)). Concurrent evaluation can contend for CPU, memory, and I/O without any explicit boot wait. Ten launches on one device class with a median within 10 ms cannot establish that contention is harmless; §2’s 60 fps filming also cannot directly resolve a 10 ms difference. **Change:** propose a narrow Apple initialization exception, preserving no-wait, admission, and activation gates, rather than replacing the global rule. Use precise first-frame timestamps and report interaction latency, tail behavior, and resource costs. The external recordings cited in §2 cannot be independently verified from this checkout.
