READY WITH CHANGES

The round-3 withdrawal is correct, and it does not regress the behavior from before this change. `flushViewDarkSoon` is gone. A note taken while `schemeDark` is still nil goes into `unreported` (`Session.swift:1318`), not into `pendingViewDark`. On the first `scheme` (`Session.swift:1282`), `reportColors()` runs while that set is the only record of those views, so its outermost drain cannot flush them early. The replay then calls `noteAppearance` on the live `drawsDark`, which queues `pendingViewDark`, and `apply(runtime.scheme)` drains that queue after the engine scheme (`Session.swift:1008`), because the nested `viewScheme` apply sees `applying` and does not drain or `landFill`. A later note outside any `apply` waits for the next outermost `apply`, which is the old rule. A destroyed session sets `state` before `runtime.destroy()` (`Session.swift:1427`); a following `apply` returns immediately, and a call on the dead handle is refused by name (`abi.rs:1433`). `forgetAppearances` (`Session.swift:1328`) runs only after boot or `commit_plan` has installed a new host (`abi.rs:828`) and before that tree is applied; `rebooted` is what calls `scheme`, and the insets and segments applies inside `rebooted` still see `schemeDark == nil`, so those notes stay in `unreported` and are replayed after the new engine's scheme. The new `PaintMotion` is empty, so that replay is a first report.

The declared gaps can stand, except the Linux repaint sentence, which is wider than the code.

1. Keyframe animations of `light-dark()` follow only a view's first differing report. Acceptable, and §8 is accurate. `set_view_scheme` passes `playing: first` (`kernel/src/motion/paint.rs:279`), and `first` is true only when that view had no entry. Transitions are a different path: `appearance()` prefers the computed scheme (`paint.rs:27`), and an authored report adopts with `snap: first && !authored` (`paint.rs:276`).
2. A report outside a batch waits for the next one. Acceptable, and §8 is accurate. That wait is the pre-change drain. The removed main-queue flush is what reordered batches; putting it back would restore the round-3 defect.
3. A subtree fixed to the scheme the session leaves is reported only when one of its views next changes appearance. Acceptable, and §8 is accurate. `scheme` does not scan views, and an `overrideUserInterfaceStyle` or `appearance` that does not change gets no callback, so a later keyframe keeps the session half. Static paints, materials, platform colours, and transitions still follow the computed scheme. On iOS a contrast or level change also calls `noteAppearance` (`SystemColor.swift:203`), so the wait can be shorter than the sentence says. It is not longer.
4. Linux keyframes stay on the app scheme. Acceptable, and §8 is accurate. Production Linux never reports a view appearance, so `play.dark` is the session scheme captured when the animation starts (`motion/src/engine/animate.rs:126`).
5. A Linux content region resolves its runs in the app scheme. Acceptable, and §8 is accurate. `apply_scheme` passes that one bool (`host/linux/src/presenter/preferences.rs:139`), and the region resolves `text_color` with it (`host/linux/src/content_region/source.rs:141`).

1. **should-fix, does not block.** `llp/1034-scheme-aware-colour.rfc.md:415`. §8 says a frame with a `color-scheme` subtree mounted repaints in full. The painter sets `damage.unsupported` only when this node's own `p.dark` differs from the appearance the walk reached it with (`host/linux/src/paint.rs:871`). `p.dark` is set only for a node that has the row or a view report (`host/linux/src/host.rs:606`), and a `display: none` node returns before the check (`paint.rs:852`). A `color-scheme="dark"` subtree in an already dark app does not disable flow damage. Amend the sentence to that rule: a painted node whose own appearance differs from the painter's current one marks the frame unsupported, which is the rule already used for any such node.
