1. **[P2] A hidden preview can still execute its action.** [ContextMenusIOS.swift:259](/private/tmp/x2-peek-review/host/apple/Sources/ExactKit/IOS/ContextMenusIOS.swift:259) replaces `eligible(row)` with checks that omit visibility. If a batch sets the lifted row—or an authored ancestor above its popover—to `display: none`, committing the existing preview still calls `presenter.press`. The runner does not reject hidden-node presses. The round-one ancestry fix needs to preserve visibility checks while exempting only the popover’s presentation hiding.

2. **[P2] Source removal during a commit still bypasses restoration.** [ContextMenusIOS.swift:74](/private/tmp/x2-peek-review/host/apple/Sources/ExactKit/IOS/ContextMenusIOS.swift:74) excludes every `committed` owner from fallback cleanup, but that flag is set **before** the synchronous press. A non-navigating preview action that removes its source or clears `contextPopover` therefore removes the interaction without calling this cleanup. If `willEndFor` does not arrive, the row remains lifted until reset or another configuration. This leaves round-one finding Astra 1 incomplete; cleanup must also cover invalidation during the press.

3. **[P2] Both web targets can still open the pre-action popover.** [rt.js:727](/private/tmp/x2-peek-review/host/web-js/rt.js:727), [glue.js:431](/private/tmp/x2-peek-review/host/web/glue.js:431). Moving resolution into `setTimeout` fixes synchronous updates, but does not wait for the action’s DOM update. The JS target can defer that update through `shared.commit`; wasm can hold the batch while loading its presence module. I reproduced both using the actual listeners and repository helpers: the timeout opened `"old"`, then the deferred update changed `contextpopover` to `"new"`, without opening it. Resolution needs to follow the applied update. Astra 4 remains partially fixed.

4. **[P2] Restoration still loses valid frame updates.** [ContextMenusIOS.swift:107](/private/tmp/x2-peek-review/host/apple/Sources/ExactKit/IOS/ContextMenusIOS.swift:107) cannot distinguish a frame operation from its own placement when their rectangles match. For example, lift `(8,8,300,180)`, then deliver `(0,0,300,180)`: that equals `placed`, so dismissal incorrectly restores `(8,8,300,180)`. Also, a batch that changes geometry and invalidates the source restores at line 76 before `place` captures the new geometry. Record delivered frame operations explicitly. The purported origin-zero regression test actually sends `(8,8)` at [ContextMenuIOSTests.swift:193](/private/tmp/x2-peek-review/host/apple/tests/ExactKitTests/ContextMenuIOSTests.swift:193), missing the remaining Astra 5/Grok 1 case.

5. **[P2] The iOS agent opens a popover for a source its action destroyed.** [MenusIOS.swift:411](/private/tmp/x2-peek-review/host/apple/Sources/ExactKit/IOS/MenusIOS.swift:411) does not recheck source liveness or eligibility. `AgentIOS` retains `target` across the synchronous `contextmenu` action and then calls `agentContext(target)`. If the action removes that row while leaving a shared popover, `agentShow` still lifts and unhides it; anchoring subsequently finds no source. This differs from the native source-invalidation behavior.
