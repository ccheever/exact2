## Strengths

- Pending confirmation and file exclusions reset on captured reviewOwner changes. Async native calls validate environment, project, thread, generation, threadEpoch and cwd before and after replies.
- Default-branch confirmation revalidates branch identity. Creating a feature branch precedes metadata update and only then the originally selected push/PR operation. Denied or failed metadata cannot be reported as full success.
- Branch checkout re-reads occupancy immediately before mutation. Worktree creation uses project root and server-returned branch/path; its narrow expected-cwd allowance retains the other immutable owner fields.
- Action progress and terminal events remain in the shared reducer. Later branch metadata reconciliation requires an admitted stream owner and fresh grants, and does not flush an arbitrary cross-environment queue from a read resource.
- Status preparation uses shared subscriptions/quiet refresh. Explicit permission denial hides host data. Parallel overview/branch permission reads can both finish while known downgrades revoke older handles.
- Linked PRs come from actual orchestration metadata; opening revalidates current linkage and HTTP(S) URL, rejecting credential URLs.

## Findings

1. **P2, corrected — landed branch mutation skipped status refresh on ID allocation failure.** `mobileGitBranchAction` originally placed IDs allocation outside the metadata dispatch try/finally. A real createRef/createWorktree could land, then IDs fail, leaving cached branch status unchanged. Pinned `use-selected-thread-git-actions.ts` syncSelectedThreadBranchState refreshes status and branches even when metadata fails. The author now includes IDs in metadata outcome handling and uses fresh read authorization to refresh the actual captured cwd, preserving the original error and refusing success.

2. **P2, corrected — default feature confirmation had the same partial-write hole.** After createRef, failed IDs/metadata skipped status refresh entirely. The action's sticky native failure wrapper also means merely adding a finally request on that wrapper cannot fix it. Revised code obtains a fresh read-only authorization, validates captured owner, refreshes, then rethrows metadata failure. It never proceeds to push on that failure.

3. **P2, corrected — invalidating refs without starting a read leaves retained Branches loading.** After a mutation, setting state.loaded=false alone leaves snapshot.loading=true. Root preparation is keyed by route and owner, so a metadata failure that keeps the same owner does not schedule another read. A witness begins with loaded refs, injects IDs failure after createRef, then sees no listRefs call and loading=true. Pinned branchState.refresh actively reloads. The author added readRevision to the snapshot, increments it after a metadata attempt, and the parent root includes it in the preparation task key. A settled error no longer reports pending loading. The independent witness verifies that token change and explicitly runs the read the root schedules; refs reload and loading settles. The reviewer read the actual root key but did not compile or execute that root task.
