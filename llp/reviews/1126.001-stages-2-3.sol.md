## Round 1 (r1) — NOT READY

BLOCKER - §5 Q1 / WP11 - The recommended lock does not establish the transaction D8 requires - There is no single “committed file”: [store.rs](/Users/ccheever/projects/s1126-wp7/exact2/host/apple/src/store.rs:289) writes persisted state synchronously, queues kept answers asynchronously, and publishes the counter separately. The underlying KV store replaces individual files by rename. Locking a replaced file is unstable; locking only writes also allows two processes to compute changes from stale snapshots and lose an update. It cannot guarantee “deadline expired, no commit” after writes have begun - Make cross-process transactions an explicit prerequisite: stable coordination, fresh reads or conflict detection, atomic publication of the durable write set and revision, and bounded cancellation before commit. Acceptance must cover conflicting read-modify-write operations, multi-key visibility, counter races, and timeout without partial writes. The deferred-to-app journal option also fails the app-not-running requirement.

MAJOR - WP11 / §1 - The app invalidation path is described as already implemented, but it is absent - [WidgetContainer.storeObserver](/Users/ccheever/projects/s1126-wp7/exact2/host/apple/Sources/ExactCore/WidgetContainer.swift:59) only calls `reloadTimelines()`. It does not reload the app’s store snapshot or re-ask session resources. Calling the existing `data_ready` entry again would not suffice either: [activate_data](/Users/ccheever/projects/s1126-wp7/exact2/host/apple/src/activation.rs:8) returns early after activation. An intent could update the widget while the visible app remains stale, contrary to the accepted foreground-and-ping ruling - Assign explicit work to reconcile the store and invalidate affected resources in every active session, including a counter check at foreground. Verify both a running app and a suspended app that misses the ping.

MAJOR - WP11 / WP12 - The archived action payload and the proposed execution mechanism do not match - The payload carries an action name, arguments and digest, but execution boots a new tree and presses a node. Node identity and repeated-row context need not survive that boot. A switch also emits a Boolean change; [HeadlessSession.press](/Users/ccheever/projects/s1126-wp7/exact2/host/apple/Sources/ExactCore/HeadlessSession.swift:211) dispatches a press, not that change. Moreover, stage 1’s render boot deliberately endows no storage, and its profile refuses persisted effects. Adding handler admission alone does not create an intent executor - Define a distinct mutating invocation contract that restores the archived action’s stable context and arguments, dispatches the correct control event, and uses Q1’s transaction. Have the gallery invoke that same contract. Acceptance should include a repeated-row action, a switch, and a cold extension process.

MAJOR - WP8 / WP10 - One shared `ActivityAttributes` type conflicts with generating one `ActivityConfiguration` per entry - Apple’s configuration API selects by `Attributes.Type`; the JSON `kind` supplies no entry-specific configuration selection. The single-entry Caltrain acceptance cannot expose this ambiguity. [ActivityConfiguration](https://developer.apple.com/documentation/widgetkit/activityconfiguration) - Keep D9’s shared Swift envelope and generate one configuration that dispatches by its immutable entry kind. Prove two different activity entries render their own plans concurrently.

MAJOR - WP8 / WP10 - The versioning promise lacks the machinery needed to fulfil it - The RFC requires retaining the shapes of activities still alive. The draft specifies only decoding against the installed plan. Stage 1 retains generation directories, but `WidgetContainer.pin()` selects the current generation; it supplies neither an activity-to-version mapping nor recoverable last-good activity state. After an incompatible push and a fresh render process, ActivityKit supplies the new state, not the previous valid state. Its `isStale` is system-provided, not a flag the decoder can set. [Apple’s stale-state contract](https://developer.apple.com/videos/play/wwdc2023/10185/) - Specify active shape/plan retention, last-good recovery across process death, and application-level stale presentation. Test an activity across delivery and binary updates with the app suspended. If the pure-render model cannot preserve the promised fallback, seek an explicit amendment instead of asserting it works.

MAJOR - WP9 / §5 Q2 - Loading the ActivityKit arm only at the first send leaves recovery after relaunch undefined - An app can relaunch with an existing activity and need its current token without starting, updating or ending anything. The reserved source is the right recommendation, but it cannot answer or observe rotation while its implementation remains unloaded - Load the arm on first source demand as well as first send, enumerate existing activities, and establish token and lifecycle subscriptions. Acceptance must recover an existing activity after relaunch without issuing another activity send, then demonstrate a backend update using the recovered token.

MAJOR - WP8–WP10 / WP13 - ActivityKit’s state and delivery limits are missing from the consumer contract - A valid Contract shape or JSON Schema can still produce an oversized activity envelope. Apple limits combined static and dynamic activity data to 4 KB; APNs encoding adds its own envelope overhead. Activities also have an eight-hour active lifetime, and frequent pushes may be throttled. One small successful push does not establish that Interview’s progressing answer remains workable. [ActivityKit constraints](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities), [push budgets](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications) - Define a bounded activity summary, validate actual encoded sizes, coalesce server updates, and specify stale and terminal behavior. Exercise a realistically long answer and a sequence of updates while suspended, including server-driven completion.

MAJOR - WP8–WP10 / §4 - Required packaging work has no explicit owner - Stage 1’s extension, shared framework, entitlements and publication paths are gated on `widgets` being nonempty, including [build.mjs](/Users/ccheever/projects/s1126-wp7/exact2/host/apple/build.mjs:654). An activity-only app therefore needs more than adding configurations to `widgets.mjs`. Separately, device builds currently exit unconditionally for widget-enabled apps; supplying Charlie’s profiles does not remove that refusal - Assign packaging work for either entry kind, including activity-only publication and delivery, `NSSupportsLiveActivities`, and separate app/extension profile validation and embedding. Make it a prerequisite of device acceptance and include an activity-only fixture.

MAJOR - WP9 / WP10 / WP12 / §4 - The completion dependencies contain cycles - WP9 must show its activity on the Lock Screen, but WP10 supplies that UI and depends on WP9. WP10 must pass through the gallery in WP12, while WP12 depends on WP10. These packages cannot each land completed in the declared order - Separate lifecycle infrastructure from visible integration acceptance, and land the required gallery support before the acceptance that uses it. Put device provisioning and Q1’s transaction work explicitly in the dependency graph.

MAJOR - WP14 - Mac packaging omits the sandbox and authenticated-refresh design - An App Group and a platform-generalized extension bundle are insufficient. The Mac widget extension needs its own sandbox and networking entitlements; the containing app can remain unsandboxed. Existing Mac assembly signs development bundles without entitlements, and the Keychain backend deliberately uses login-keychain ACLs rather than opting into the data-protection keychain. Caltrain cannot establish that Interview’s extension can read shared credentials and refresh unattended. [Apple on sandboxed extensions](https://developer.apple.com/forums/thread/776568), [network entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.network.client) - Specify the extension’s sandbox, signed resource access and shared-secret policy. Add Interview’s signed-in TypeScript widget, with the app closed, to acceptance.

MAJOR - WP15 / §5 Q3 / stage 3 scope - The proposed completion bar omits the ruling’s real consumer and leaves the launch goal unowned - WP14 and WP15 accept Caltrain alone. Q3 then puts Interview’s complication into `QUEUE.md`, despite §0 naming Interview for every stage. D10 permits TypeScript to wait, so refusing unsupported watch execution is reasonable; counting that as completed consumer support is not. The independent watch store also needs an account/bootstrap story: it cannot inherit the phone’s credentials. Finally, RFC §5 explicitly names visionOS widgets alongside the port requested for full Apple support, but this plan names no owner or dependency - Add a bounded watch Hermes feasibility gate, explicit Interview acceptance and account provisioning, or obtain a clear reduced-scope ruling. Track the visionOS port/widgets and stage 4 watch app as owned launch dependencies; a placeholder watch app proves neither.

MINOR - WP8 / WP11 - WP8’s permanent handler-refusal acceptance conflicts with D7 and WP11’s shared-profile relaxation - State whether Live Activity actions are included; if included, account for `LiveActivityIntent` running in the app process. [Apple’s execution rules](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities)

MINOR - WP11 / WP12 - The minimum supported iOS 17 path is unqualified by the proposed evidence - Require archived intent discovery, parameter round-trip and execution on iOS 17 and 18+, including metadata packaging in the custom build; an in-process press or iOS 27-only run cannot establish this.

MINOR - WP8 / WP10 - `compact` leaves the two required compact regions unspecified - Name `compactLeading` and `compactTrailing` slots and their independent viewport sizing. [Dynamic Island presentations](https://developer.apple.com/videos/play/wwdc2023/10184/)

MINOR - WP14 acceptance - A visible WidgetKit reload within one second is not a host-controlled guarantee - Bound the reload request and measure eventual presentation separately, because WidgetKit schedules and may throttle reloads. [Widget refresh scheduling](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date)

MINOR - WP9 - Omitting an `NSExtension` does not enforce refusal of push-to-start or ordinary remote notifications - Those mechanisms do not require a dedicated extension; preserve the correct update-token-only API boundary and verify that boundary directly.

MINOR - §1 / WP12 - “Only the extension links `ExactSnapshot`” excludes the existing development gallery - Document its explicit exception: [Package.swift](/Users/ccheever/projects/s1126-wp7/exact2/host/apple/Package.swift:78) links the snapshot target into gallery builds.

MINOR - WP15 - Compile success and a phone/Mac gallery do not qualify watch execution limits - Measure the actual watch extension’s refresh, retained footprint and archived render against watch-specific limits.

MINOR - WP15 / Q3 - Refusing a TypeScript entry at bake and installing its placeholder are different outcomes - Choose an explicit failure or omission policy; a failed bake cannot produce the promised placeholder.

## Round 2 (r2) — NOT READY

Most round-1 findings are resolved. Q2, Q4 and Q5’s recommendations are reasonable, and the Mac App Group rejection is supported by [Apple’s DTS explanation](https://developer.apple.com/forums/thread/721701). The remaining material issues are below.

BLOCKER - §5 Q1 / WP11 - Moving execution into the app does not establish the transaction promised by the acceptance - Option A boots separate sessions against the store. Two sessions can read the same value and overwrite each other’s changes even within one process. The existing [write path](/Users/ccheever/projects/s1126-wp7/exact2/host/apple/src/store.rs:289) also persists keys individually and queues kept answers; retaining it unchanged cannot guarantee timeout without partial writes or atomic visibility to extension readers. Option B improves publication, but taking the app’s lock only from its first write does not protect an earlier read-modify-write calculation - Make transaction coordination a prerequisite under either choice: fresh reads or conflict detection, coordination with active app sessions, atomic publication with the revision, and cancellation before publication. Include this work in A’s stated cost. The round-1 transaction blocker is only partly resolved.

MAJOR - WP8, generation retention - Retaining an activity’s generation does not establish that a replacement binary can render it - R2 supplies the previously missing generation identity and durable last-good state, but [generation admission currently rejects another compatibility cohort](/Users/ccheever/projects/s1126-wp7/exact2/host/apple/Sources/ExactCore/WidgetContainer.swift:40). A binary change can change the plan format or kernel schema; keeping the old directory and JSON does not provide a compatible decoder and renderer. Thus the round-1 versioning concern remains across compatibility-changing binary updates - State the compatibility boundary and the supported transition for an alive activity. Either preserve its shape/rendering in a form the new binary accepts or obtain an explicit amendment to D9’s fallback promise. Acceptance must include delivery and compatibility-changing binary updates, followed by a fresh extension process while the app remains suspended.

MAJOR - WP11, Live Activity controls - The newly included controls have no defined path from a committed mutation to updated activity state - WP8 renders only supplied `ContentState`, while WP11 relies on the guaranteed timeline reload after `perform`. Live Activities have no timeline refresh; their dynamic state changes through ActivityKit or an ActivityKit push. A toggle can therefore persist successfully while its activity continues displaying the old Boolean. The generic invocation also does not identify the activity instance. [Apple’s update model](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities) - Define the activity invocation context and how its handler updates or ends the intended activity through WP9, or explicitly defer Live Activity controls. Accept a real control interaction that changes visible state, including when multiple instances of one activity kind exist.

MAJOR - §5 Q3 / WP17 - The bounded watch gate is sensible, but its alternatives and completion bar are incomplete - “WatchConnectivity needs stage 4’s app” is not a platform requirement: WP17 already creates the paired watch app needed to host `WCSession`; it does not require Exact’s live renderer. Apple demonstrates receiving companion data into a watch app’s shared store for its WidgetKit complication. Excluding that route makes a separate watch sign-in flow appear compulsory. Meanwhile, WP17 can finish with Caltrain alone, and Q3’s success criteria never explicitly require Interview’s authenticated complication to work. [Apple’s companion-app example](https://developer.apple.com/documentation/watchconnectivity/transferring-data-with-watch-connectivity) - Present credential bootstrap through the WP17 wrapper and independent watch sign-in as separate options, with their transport, authentication and UI costs. If WatchConnectivity is deferred by scope, say so. Define gate success as Interview’s actual signed-in refresh and archived complication on hardware within stated time and memory thresholds; retain Charlie’s explicit reduced-scope ruling on failure.

MINOR - §5 Q1, rejected finding - Rejecting `supportedModes` on iOS 18 is correct, but extension-only intents already execute in the background before iOS 26; `openAppWhenRun`’s cited error concerns setting it to `true` - The current explanation unfairly weakens option B - Correct that distinction and separate execution target from foreground/background mode. [Apple’s execution rules](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities)

MINOR - WP15 - “One past the budget” assumes a known, fixed push allowance that Apple does not specify - This makes acceptance indeterminate - Require an observed throttling exercise and separately verify adaptation when frequent updates are disabled. [Apple’s push-budget guidance](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications)

VERDICT: NOT READY
