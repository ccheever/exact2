Reviewed r1 independently, without consulting other reviews. I found four MATERIAL concerns.

1. **MATERIAL — Granted reads can still open system UI.**  
   At [RFC line 387](llp/1133.019-photos-image.rfc.md#L387), the automatic limited-library alert remains enabled unless the app uses `managePhotoSelection`. Yet D7 permits tool-origin reads while permission is granted. Apple documents that the first PhotoKit fetch after launch can show this alert under limited access. A tool’s first `photoAssets` call can therefore open system UI despite passing permission admission. [Apple’s explanation](https://developer.apple.com/videos/play/wwdc2020/10641/)

   Pictures have a related contradiction: the origin table permits prompting picture reads, but [line 425](llp/1133.019-photos-image.rfc.md#L425) explicitly gives pictures no origin. This cannot enforce the inherited [prohibition on tool-triggered system UI](llp/1133-the-standard-library.rfc.md#L349).

   **Resolution:** make picture loads non-prompting and conditional on existing read authorization. Suppress automatic alerts on paths tools can reach, or admit their possible presentation explicitly. Keep selection UI behind an origin-checked request. Exercise the real implementation with limited access and a tool making the first fetch after launch.

2. **MATERIAL — Ordinary raster invalidation does not revoke an already displayed picture.**  
   [RFC line 366](llp/1133.019-photos-image.rfc.md#L366) promises that a withdrawn picture fails at its next draw; [D11](llp/1133.019-photos-image.rfc.md#L554) places it in the ordinary raster cache and refreshes it through URL change announcements.

   The inherited behavior contradicts that promise. [Cache invalidation](host/apple/Sources/ExactKit/RasterLoader.swift#L174) removes the lookup identity, while [image replacement](host/apple/Sources/ExactKit/IOS/NodeViewIOS.swift#L505) retains the previous raster until a replacement succeeds. A failed replacement reports an error without clearing that raster. Consequently, even announcing a withdrawn URL can leave its old pixels visible.

   **Resolution:** distinguish revocation from ordinary image replacement. Revocation must clear displayed leases and cached representations, cancel outstanding loads, and prevent late replies from restoring them. Acceptance should retain an independently mounted `img` while removing its asset from a limited selection—permission remains `granted`. Drive 6 currently removes the whole strip and cannot establish this guarantee.

3. **MATERIAL — `metadata: "no-location"` does not deliver its stated privacy property.**  
   [RFC line 701](llp/1133.019-photos-image.rfc.md#L701) preserves the remaining metadata and relies on `kCGImageMetadataShouldExcludeGPS` to remove location. Apple explicitly documents that this flag leaves proprietary location data in EXIF MakerNotes and custom XMP properties. Preserving those payloads can preserve coordinates while returning `metadata: "no-location"`. [Apple documentation](https://developer.apple.com/documentation/imageio/kcgimagemetadatashouldexcludegps?changes=_2)

   **Resolution:** either rebuild metadata from a conservative set that excludes opaque location-bearing payloads, or rename and document the option as GPS-tag removal and narrow the “strip location” guarantee. Checking only the ordinary GPS block, as the proposed conformance does, misses this case.

4. **MATERIAL — Android’s permission design cannot support the advertised location-preserving library round trip.**  
   The permission set at [RFC line 265](llp/1133.019-photos-image.rfc.md#L265) omits `ACCESS_MEDIA_LOCATION`, while [D15](llp/1133.019-photos-image.rfc.md#L695) promises preservation of GPS metadata for edits.

   Android hides photo location metadata by default. Retrieving unredacted bytes requires separately declaring and requesting `ACCESS_MEDIA_LOCATION`, then using `MediaStore.setRequireOriginal()`. Library read permission alone is insufficient. Once `copyPhotoAsset` produces a redacted file, the image codec cannot recover its original location. [Android documentation](https://developer.android.com/training/data-storage/shared/media#media-location-permission)

   **Resolution:** either design the separately authorized original/location path, or explicitly declare Android library copies redacted and narrow the preservation promise and disclosure accordingly. An image-codec test using an app-owned GPS fixture does not prove the MediaStore import path.

The reference/file split, image’s placement in storage, and the two purpose-specific calls are otherwise reasonable decisions. No files were modified.

Verdict: NOT READY

**New concerns**

1. **IN-DELTA · MATERIAL — Direct-call tracking cannot guarantee that library answers are never kept.**

   At [RFC:415](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1019/capsule2/llp/1133.019-photos-image.rfc.md:415), and D11 item 4, only the answer that *calls* a Photos name becomes ineligible for persistence.

   The inherited architecture explicitly supports answer B awaiting a shared promise created under answer A: B resumes as B ([geolocation:722](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1019/capsule2/llp/1133.002-geolocation.rfc.md:722)). Consequently, A can initiate `photoAssets`, while two store-reading sources await that promise and return its photos. Only A made the binding call; B remains eligible for keeping. The runner persists eligible answers independently ([kept.rs:322](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1019/capsule2/runner/src/runner/kept.rs:322)).

   B’s ids, dates and picture URLs can therefore appear at the next launch after revocation, without the app explicitly saving them. This defeats D6’s stated guarantee.

   **Resolution:** retain the conservative app-wide exclusion, or define persistence eligibility that also covers consumers of shared and cached results. Prove the shared-promise case before replacing the existing exclusion.

2. **IN-DELTA · MATERIAL — The new Android owner exception conflicts with both admission and redaction.**

   [RFC:377](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1019/capsule2/llp/1133.019-photos-image.rfc.md:377) promises that an app holding only `device.photos-add` can draw and copy its own saved assets without prompting. But D5 leaves its read `state` at `prompt` or `denied`, while [D2:219](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1019/capsule2/llp/1133.019-photos-image.rfc.md:219) forbids entering the implementation unless that state is `granted`. The copy declaration also selects `"permission": "photos"`. Adding an alternative grant does not reconcile these authorization rules.

   Ownership also invalidates [D4:321](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1019/capsule2/llp/1133.019-photos-image.rfc.md:321)’s blanket claim that missing `ACCESS_MEDIA_LOCATION` means redacted bytes. Android’s MediaProvider exempts the owning app from redaction. An owned copy can retain GPS without that permission; deriving `locationRedacted` from permission alone would give callers a false privacy assurance. Drive 9’s expectation for an owned photo is correspondingly wrong. [AOSP ownership check](https://android.googlesource.com/platform/packages/providers/MediaProvider/+/69a25763cdb46c8f23fe9eb976132acbe2af82d6%5E!/)

   **Resolution:** define one asset-sensitive admission policy using verified platform ownership, and make redaction disclosure describe the actual export. Exercise owned and other-app assets separately, with location permission absent.

3. **IN-DELTA · MATERIAL — The prescribed Android decode path cannot supply the gain map its HDR step needs.**

   [RFC:805](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1019/capsule2/llp/1133.019-photos-image.rfc.md:805) switches API 30+ decoding to the reader’s `AImageDecoder` route, then expects a Java `Bitmap` carrying a `Gainmap`.

   `AImageDecoder` returns pixels into client memory, with no public gain-map extraction API. The cited reader route explicitly requests RGBA8888 and returns a `Pixmap` ([jpeg.rs:278](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1019/capsule2/host/linux/src/image/jpeg.rs:278)). Attaching to Java for encoding cannot recover the discarded auxiliary image. [NDK decoder documentation](https://developer.android.com/ndk/reference/group/image-decoder)

   The literal “same matrix” prescription also fails when the gain map has smaller pixel dimensions: crop offsets and rotation translations require conversion between coordinate systems. Android explicitly documents this distinction. [Android’s HDR editing guidance](https://developer.android.com/media/grow/ultra-hdr/edit)

   **Resolution:** choose a decode path that retains the real `Bitmap` and `Gainmap`, and use corresponding geometry in their respective coordinate systems—or the platform’s supported bitmap transformations. Reporting `hdr: false` does not establish that an otherwise capable host cannot preserve HDR.

4. **PRE-EXISTING · MATERIAL — A creation-date-only cursor cannot paginate the advertised library reliably.**

   [RFC:172](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r1019/capsule2/llp/1133.019-photos-image.rfc.md:172) defines `before` as a `creationDate`, with a maximum page size of 500.

   For 501 assets sharing a timestamp, an exclusive cursor permanently skips the remaining asset; an inclusive cursor repeats the same page. A deterministic tie-breaking sort cannot fix a cursor that cannot express the tie-breaker. This is especially plausible with Android’s specified `DATE_ADDED` fallback, whose precision is seconds. [MediaColumns documentation](https://developer.android.com/reference/android/provider/MediaStore.MediaColumns#DATE_ADDED)

   **Resolution:** use an opaque continuation cursor or a compound cursor containing the effective sort date and asset identity, matched to a total ordering. Verify enumeration across a page boundary containing equal timestamps.

Verdict: NOT READY

Two MATERIAL concerns remain in the delta.

1. **IN-DELTA · MATERIAL — Runtime-wide tracking still misses indirect consumers of library data.**

   [RFC:434](llp/1133.019-photos-image.rfc.md:434) disables persistence only when a data runtime calls a Photos name. But Contract can call `photoAssets` and pass its result into a store-reading data source. That runtime never calls Photos, so the exclusion never activates.

   This already retains sensitive data even when the source returns only a summary: [kept.rs:333](runner/src/runner/kept.rs:333) persists identifying arguments alongside the answer. Passing the library list as an ordinary argument therefore writes its ids, dates and picture URLs automatically.

   The displayed-data failure is possible too:

   ```contract
   resource recents = photoAssets(limit=24) as shape PhotoAsset[] else empty()
   resource cards = decorate() with recents as shape PhotoAsset[] else empty()
   ```

   If `decorate` reads a stored presentation preference and returns the photos, its answer remains eligible for keeping. `with` inputs are excluded from the persisted identity, so the previous list can seed the next launch before authorization is checked. This follows the existing [context semantics](llp/1027.005-resource-identity-and-request-context.rfc.md:124).

   **Resolution:** use the existing app-wide exclusion, or cover consumers of Contract results as well as binding callers, including cached results. Prove the Contract-to-data case before claiming D6’s no-retention guarantee.

2. **IN-DELTA · MATERIAL — The below-34 Android path applies EXIF orientation twice.**

   [RFC:833](llp/1133.019-photos-image.rfc.md:833) explicitly says the reader’s decoder does not apply EXIF orientation and directs the transform matrix to apply it.

   Android’s decoder already applies that orientation. The [AOSP decoder implementation](https://android.googlesource.com/platform/frameworks/base/+/46ec4b060150e28dc9fb1455c97e79461277a153/libs/hwui/hwui/ImageDecoder.cpp) swaps dimensions for encoded orientation and applies `SkEncodedOriginToMatrix` during decoding. Android’s [NDK conformance tests](https://android.googlesource.com/platform/cts/+/f7679a054c594286f0b2692e69a2d7ebe2831685/tests/tests/uirendering/src/android/uirendering/cts/testclasses/AImageDecoderTest.kt) likewise compare `AImageDecoder` output with orientation-corrected expected pixels.

   The repository wrappers do not undo this: [jpeg.rs:278](host/linux/src/image/jpeg.rs:278) requests format, size and crop; [Legacy.kt:33](host/android/canvas/src/main/java/dev/exact/canvas/Legacy.kt:33) calls Java `ImageDecoder`. Following r3 would rotate common camera images again and interpret crops in the wrong frame.

   **Resolution:** treat these decoders’ output as upright and apply only the authored transforms afterward, or select an explicitly unoriented decoder. Verify orientation-6 input with both no edit and a crop on API 29 and 33.

The brief pass over unchanged text found no additional PRE-EXISTING MATERIAL concern.
