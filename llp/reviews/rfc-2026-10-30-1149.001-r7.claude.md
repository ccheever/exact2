**The predicate is complete and conservative.** Ink calls `destination()` in exactly three places: `blended_image` (`effects.rs` 64–68), `backdrop` (`effects.rs` 175) and a kept row's replay of a blended instance (`ink/rows.rs` 317–320). `blended_image` with a nonzero mode is reached only through `island_image` from the SVG path (`ink.rs` 502–505; `paint/svg.rs` 540–556, LLP 1055.000 D19); the other `island_image` callers pass mode 0 (`island.rs` 166, `text_clip.rs` 81, `text_shadow.rs` 194, `text_stroke.rs` 52), and the painter has no node-level or image-node `mix-blend-mode` path at all (no match in `paint.rs` or `paint/`). So r7's "a blend mode on a node or on an image" (L232) counts nodes ink does not blend today: an over-count, which the text's "the counts are conservative" (L238) covers, and harmless to correctness. `backdrop` is reached from `backdrop_filter` when `BoxPaint.backdrop` is non-empty (`paint.rs` 298–299), which a material or a `backdrop-filter` style produces (`paint.rs` 217–221, 261–264). Two facts the builder will like: the kernel already evaluates all three tests in one place, `paint_order.rs` 238 (`BackdropFilter`), 243 (`mix_blend_mode != Normal`) and 258 (`PropId::BackgroundMaterial`), so the count's predicate exists and the kernel change is a counter beside it; and an SVG item's blend is the SVG element node's own style (`kernel/src/svg/scene.rs` 521 reads `style.mix_blend_mode`), so the same kernel count over present nodes covers islands too, which would make the painter-side SVG count and the "unresolved counts as sampling" rule (L238–240) unnecessary. The latter matters for performance, not correctness: under the painter-side rule, a screen whose kept rows hold an SVG island is never resolved at `begin()` (replayed rows are not walked, `paint/rows.rs` 550–578) and would take the compose path every frame.
