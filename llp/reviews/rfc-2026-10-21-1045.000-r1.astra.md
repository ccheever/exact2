## Overall assessment

The direction is sound: atoms should extend LLP 1045’s source-backed editor, with shared recognition and editing rules. Source-keyed faces eliminate offset-reconciliation ambiguity for presentation.

However, r1 conflates presentation with token identity, leaves important editing interactions unspecified, and repeats the DOM-naming problem. It resolves r3’s second-editor and plain-textarea replacement objections; shared editing behavior and Apple feasibility remain unproven. §9 correctly leaves admission pending.

This was a static review of the authorized sources. No files were edited; no browser, builds, or runtime validation were used. Reference-app citations below are at `74541bab17`.

## Strengths

- **D1–D2:** Preserving literal source and deriving spans from the existing parser fits LLP 1045. `markdown/src/style.rs:105` already exposes bracketed-link syntax suitable for this extension.
- **D3, §7:** Keeping atoms separate from plain-field decorations respects the boundary enforced by `contract/lower/src/decorations.rs:8`.
- **D5:** Whole-atom deletion, source copy, cancelable `beforeinput`, and composition protection are appropriate requirements.
- **§4–§5:** Testing the TextKit 2 mechanism before committing to the Apple implementation is the right sequence.
- **§8–§9:** Naming app code to delete and explicitly requesting admission makes the scope reviewable.

## Concerns

1. **BLOCKING — D1–D2, D5: source-keyed presentation cannot reproduce occurrence-specific token identity.**  
   One face for `@foo` makes every matching occurrence atomic, including an independently typed occurrence that should remain text under D1’s claimed reference behavior. Likewise, typing beside an existing reference node does not establish that the node dissolves: the reference stores mention source on the node and rebuilds content only on a changed controlled value (`apps/web/src/composer-rich-text-doc.ts:827`; `apps/web/src/components/ComposerPromptEditorTiptap.tsx:1598`). The clone explicitly preserves existing chips through adjacent edits (`examples/t3-code/src/composer/composer-source-chips.ts:76`).  
   **Resolve:** Choose source-determined semantics and declare these reference differences, or define occurrence identity within the editor. Do not claim both stateless recognition and reference-equivalent behavior. Specify face arrival/removal, selection normalization, and undo when a previously available face disappears.

2. **BLOCKING — D5, §4: atom precedence over hidden syntax and raw-source edits is incomplete.**  
   Projection currently merges adjacent hidden runs and removes them from visible ranges (`markdown/editor/src/projection.rs:164`, `:230`). Replacement preserves hidden syntax (`markdown/editor/src/editor.rs:903`); Apple similarly preserves destinations and openers (`host/apple/Sources/ExactMarkdown/MarkupHidden.swift:104`). An atom must instead contribute its entire source to deletion. Separately, `Editor::replace` deliberately replaces the exact requested source range (`editor.rs:366`), even where an interactive selection cannot sit. D5 does not settle explicit `setRangeText` edits inside atoms, adjacent atoms separated by hidden formatting, or composition cancellation after its preliminary deletion.  
   **Resolve:** Define atom-versus-marker precedence and distinguish interactive edits from explicit source edits. Add shared cases for adjacency, formatting boundaries, partial replacement, IME cancellation, and undo. Correct the caret citation too: `composer-rich.contract:35` chooses the **start** on a tie and measures against the shown label, unlike D5.

3. **MATERIAL — §4 web plan: the proposed DOM breaks the existing source-counting invariant.**  
   `toSource` counts DOM text, `readDom` concatenates every text node, and the fast reconciliation path uses `line.textContent` (`host/web/markup-editor.js:157`, `:254`, `:315`). Hidden source plus a separate label island would therefore count and read back both strings without additional mapping. `contenteditable=false` alone does not solve this.  
   **Resolve:** Specify how presentation islands contribute zero source characters, how their two boundaries map to source, and how native replacement/composition handles detached islands and retained hidden spans. Include atom-only fields, adjacent atoms, range geometry, and all three browsers.

4. **MATERIAL — §4, stage 0: r6 does not establish attachment feasibility.**  
   The existing delegate substitutes equal-length word joiners and returns an `NSTextParagraph`; it supplies no attachment (`host/apple/Sources/ExactMarkdown/MarkupHidden.swift:23`). I could not confirm that an attachment present only in that paragraph supports the required layout, view-provider lifecycle, selection, and accessibility behavior. The parent also explicitly leaves phone VoiceOver line reading unproven (`llp/1045-markdown-editor.rfc.md:340`).  
   **Resolve:** Make stage 0 a genuine implementation gate covering long citation sources, wrapping, bidirectional text, native undo/IME, face updates, geometry, and accessibility on both Apple hosts. Verify D4’s fixed-height claim against native token appearance. Treat the kern/underlay alternative as a new proposal requiring review, not an established fallback.

5. **MATERIAL — D7, §7: the proposed event still changes DOM meanings.**  
   `press` currently maps globally to DOM-named `MouseEvent`, containing modifiers (`contract/types/src/selection.rs:79`, `:246`). An anchor’s `href` is not a `MouseEvent` property; a prefix token’s source is not an anchor destination. Relative destinations also need an explicit resolution policy—the parent distinguishes web and native behavior (`llp/1045-markdown-editor.rfc.md:232`).  
   **Resolve:** Use a separately named atom-activation payload with source range, kind, source, destination where applicable, and modifiers. Remove §7’s claim that this is already ordinary DOM `href` semantics.

6. **MATERIAL — D1, D3: recognition is not yet deterministic enough.**  
   “Earlier start” cannot resolve two declarations matching the same span. The quoted-prefix form conflicts with the table’s “next whitespace” endpoint, and precedence against surrounding Markdown delimiters is unclear. The reference grammar also has trailing-whitespace requirements, numeric-skill exclusions, quoted-token rules, and math exclusions absent from this definition (`packages/shared/src/composerInlineTokens.ts:23`, `:126`, `:139`).  
   **Resolve:** Define duplicate-form rejection or explicit priority, exact quoted/unquoted boundaries, escapes, and interaction with Markdown syntax. State intentional differences from the reference. For relative links, define Windows paths, absolute/network paths, queries/fragments, and malformed percent escapes.

7. **MATERIAL — D6 versus D4, D7–D8: math shares rendering machinery, but not the proposed token contract.**  
   D4 requires a text-height pill and square icon; D6 requires natural formula dimensions and baseline depth. D7 makes every atom activatable, although a formula need not perform an action. The reference additionally provides constrained horizontal scrolling and a keyboard-focusable formula surface (`apps/web/src/components/chat/MarkdownMath.tsx:25`, `:38`). SVG image support alone establishes none of those behaviors.  
   **Resolve:** Defer math to a child RFC. It may reuse inline-box measurement, but needs its own sizing, baseline, overflow, copy, grammar, and accessibility contract. I did not independently confirm the claimed remark-math delimiter rules.

8. **MATERIAL — D7–D8, §6: keyboard activation and accessibility roles are underspecified.**  
   The no-tab-stop rule applies to readers as written, while no ordinary keyboard activation path is supplied. Calling every token a link also misdescribes preview/popover actions: the reference mention uses a button (`apps/web/src/components/ComposerPromptEditorTiptap.tsx:265`). Removing the pencil shortcut is acknowledged, but its replacement must remain keyboard reachable.  
   **Resolve:** Distinguish reader focus from editor caret navigation, define activation of a selected editor atom, and assign roles according to action semantics. Verify that explicit accessibility children preserve text editing and reading order rather than assuming that adding children is sufficient.

## Recommendations on §10 Q1–Q7

- **Q1 — Admission:** Seek an explicit, narrowly scoped waiver for composer/transcript chips after revision. Name the implementer and implementation date. The existing Markdown grant is insufficient; `rules/RULES.md:46` and `:57` remain binding.
- **Q2 — Styling:** Colours only for the first slice, with verified platform defaults. Document this as a bounded surface; face width already affects layout, so “a second layout model” is not sufficient justification by itself.
- **Q3 — Relative links:** Preserve the consumer’s `[name](path)` source. Prefer app-controlled eligibility over parsed links to embedding T3’s basename heuristic as general framework policy.
- **Q4 — Face gating:** Keep app opt-in, but explicitly choose uniform semantics for equal source strings. Do not claim menu/paste provenance can be represented by a source key.
- **Q5 — Math:** Defer to a child RFC; reuse measurement machinery where appropriate.
- **Q6 — Press record:** Use a distinct atom-activation record. Specify an extension to `tap` for coordinates or an atom target; D9 currently promises a drive that Q6 acknowledges is unavailable.
- **Q7 — Hosts:** Web, macOS, and iOS first is reasonable. Declare editor, reader, activation, geometry, and accessibility coverage separately; showing source alone does not establish the other capabilities.
