1. **BLOCKER** — D3 "An ordinary asset that fails any of these is transient"; D5 "Until slice 3"; D2's `{fetch}`; `snapback4/client/src/client.rs:33-40`; `snapback4/ts/snapback.ts:445` (HEAD). A `once` asset is safe only because `GET` with `Range: bytes=0-` is refused with `E_ASSET_RANGE` before any byte is sent (`snapback4/src/assets.rs` in Snapback 0.4.13, status 416). The existing `Fetch` has no header field, and the driver's `exchange` sends only `headers()` plus `content-type` for a JSON body. A download that omits `Range` gets `200` with `accept-ranges: none` and the body, and the view is spent (`record_asset_view` after a successful send). D3 then classifies that as transient, because it failed the keep checks, and the driver writes `app:/tmp/snapback4/…`. D5's interim rule mentions only the `E_ASSET_RANGE` refusal. Change: the asset fetch always sends `Range: bytes=0-`. Any response with `accept-ranges: none`, or `E_ASSET_RANGE`, is discarded, never written, and answered `E_ASSET_ONCE_UNSUPPORTED`. `transient` is only a complete `accept-ranges: bytes` object that failed a non-once keep check (no confirmable home, over the cap, or `keep: "none"`).

2. **BLOCKER** — D2, "Downloads and uploads run beside rounds" and "Removes the files, inside the partition's round queue." `media_due` drops the manifest entry and returns `{remove}` while an in-flight `asset_reply` may already have returned `{keep: path}` for that same path. Whichever file operation runs last wins. If the write runs last, the file is back on disk, the manifest does not name it, and the app was given the path, so the picture keeps showing until the next open sweeps strays. `appURL` (`host/web/picker-glue.js:35-53`) will not drop an object URL until that path is resolved again. Change: one file queue per partition, in the order the core answered, and a keep/transient write that finds the manifest no longer names that path does not create the file and does not return it. Inside one answer, apply `remove` and then the new write so the path you return exists. D8 should include this interleaving.

3. **MAJOR** — D4.5 and D2 `upload_reply {exchange, reply, changed}`. Snapback records `upload_facts`, then checks the session again, then `forget_upload_facts` (`node_modules/snapback4/dist/local.js:1756-1773`). The device keys the receipt by viewer, not by bearer (`media.rs` `upload_key`), and says the host supplies the authenticated receipt. A single `changed` bit sampled before `upload_reply` misses a refresh that lands during the device call, and there is no later forget. `headers()` is also per client, while the partition is shared, so two openers can present different bearers for one viewer. Change: record facts only when `changed` is false, using the partition's bound viewer; after `upload_reply` returns ok, sample `headers()` and any in-flight `refreshSession` again, and if they differ call `forget_upload_facts` and return `E_AUTH` ("start the upload again"). One credential source per partition, as `refreshSession` already is.

4. **MAJOR** — D2 `media_due {now}`, `asset {id, now}`; §4's driver surface (`asset`, `upload`, `release`, `clearMedia`); LLP 1027.000. Expiry is defined as the `now` the driver passes, and r3 correctly removed the `setTimeout` retry because a data module has no clock. `open` and `sync` do not take `now`, and the driver cannot call `Date.now()`. A round-end check with no `now` either skips expiry or reads the machine clock. Change: `asset(id, now)` and an optional `now` on `sync`, used only for `media_due`. With no `now` yet, do not expire anything. Say the driver must not read the clock.

5. **MAJOR** — D3, "The partition's first opener sets the policy, and a later open with another policy is refused." The manifest shape has no policy, and the core is rebuilt on every process start, so the rule exists only inside one page. The next launch's first `open` with `keep: "none"` is not a "later" open; the next `media_due` then purges files the previous policy kept. Snapback does purge on `keep: "none"`; this RFC says refuse. Change: store `{keep, maxBytes}` in the partition beside `exact:media`. If a stored policy exists and differs, refuse. If none is stored, store the opener's and, for `keep: "none"`, purge.

6. **MAJOR** — D2, the `x-snapback-asset-home` header and "its home no longer matches." The server sends percent-encoded JSON of `{store_id, table, row, column}` only (`snapback4/src/assets.rs:101-106` in the 0.4.13 tree). `asset_home` adds `generation`, `expiresAt`, `tables`, and `type`. Snapback keeps only when `accept-ranges` is `bytes`, the body is a whole `200` or a `206` whose `content-range` is `bytes 0-(n-1)/n` with `n` equal to the body length, and the confirmed home's identity `(store_id, table, row, column, generation)` is unchanged (`dist/local-assets.js:15, 179-181, 186-199`). Parsing the header as raw JSON keeps nothing. Treating any successful `asset_home` as "still matches" and rewriting `generation` keeps bytes across a store generation change, which Snapback drops. Change: put that decode, that completeness predicate, and that identity in D2, and drop rather than rewrite when the identity differs.
