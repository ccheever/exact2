## Should-fix

**1. D8's wake list is missing the server's ephemeral early return, so a hot ephemeral table turns the long poll into a 100ms re-poll.** D8 step 2 (`llp/1110-live-snapback-reads.rfc.md:369-373`) says the server answers when the head moves, the store is replaced, the generation changes, or the wait runs out. `serve_changes.rs:64-69` also returns when `eph_ready && now >= paced`, and `paced` is 100ms after the request starts (`serve_changes.rs:16`). With no `eph` parameters, `changed()` treats every ephemeral table as interesting (`ephemeral.rs:47-53`, `interest.is_none_or`). `Snapback.changes()` then sees an unchanged cursor and asks again at once (`snapback4/ts/snapback.ts:531-535`). Open question 2 (`llp/1110-live-snapback-reads.rfc.md:497-499`) still treats ephemeral as undecided, but the server already ends the wait. While presence or typing moves, each live client re-polls at that pace and still takes one long-wait worker per poll. Name this in D8. Keep an ephemeral-only body (same `seq`, `store_id`, and `generation`) as "ask again", state the 100ms pace, and close the open question: this stream does not yield ephemeral rows.

**2. The first failure has no last cursor, and yielding one re-asks every reader.** D8 (`llp/1110-live-snapback-reads.rfc.md:374-377`) says a transport failure, a refusal, or a non-2xx yields `{ cursor: <last>, seq: <last>, online: false }` and returns. Before any head, `seq` is null and `cursor` is `''` (`snapback.ts:495-497`). The catch yields `{ cursor: '', seq: 0, online: false }` with `done: false` (`snapback.ts:521-526`). That is a first message. Readers take `live.cursor` (`llp/1110-live-snapback-reads.rfc.md:395`), so they ask again with `''`. If no head has been yielded, throw: the stream fails, no message lands, and `failure(live)` is set. After a head, yield the last cursor with `online: false` and return. Say that path does not set `failure(live)`; the app reads `online`.

**3. D7 describes the runner's ticket, and the JS target's agent state is different.** D7 (`llp/1110-live-snapback-reads.rfc.md:338-343`) says the ticket changes every round, and that `state.pending` lists the stream again while it awaits storage or a continuation. The runner does that: each round gets a new ticket (`runner/src/runner/commit.rs:1055-1056`), and an iterator storage step or continuation stays in flight after the first message (`commit.rs:311-314`). On the JS target, `state.pending` is resources whose ticket has no messages yet, and `state.streams` keeps the opener's one ticket (`host/web-js/agent.js:419-420`). A storage step still increments `inflight.n` (`host/web-js/ts-data.js:190`), so `clock settle` waits, but `state.pending` does not show the stream. Scope the changing ticket and the storage-pending sentence to the runner. Say the JS target's stream ticket is the opener's for the life of the iterator.

## Nits

**Journal words in D7 don't match the runner.** D7 (`llp/1110-live-snapback-reads.rfc.md:342-344`) says the journal logs `message`/`reply`, `one more round`, and `forgot ticket …`. The runner logs `fulfil {ticket} ({name}) [{summary}]` (`runner/src/runner/lines.rs:139`), `{name}: the reply asks for one more request` (`lines.rs:163`), and `forget request {ticket} ({name})` (`lines.rs:106`). `message`/`reply` is the JS target's line (`host/web-js/rt.js:406`). Quote the runner lines, and attribute `message`/`reply` to the JS target.

**`wait` is clamped at 25s.** D8 gives `wait = 20` (`llp/1110-live-snapback-reads.rfc.md:363`) and no ceiling. The server clamps with `.min(25)` (`serve_changes.rs:13`). The new client clamps to 25 (`snapback.ts:504`). The Rust client's `poll` still asks up to 55 (`snapback4/client/src/client.rs:894`), which the server shortens. Say the server ceiling is 25s. 20 is inside it.

**"A reply that has arrived is delivered" is one completion, then only while something is in flight.** D3 (`llp/1110-live-snapback-reads.rfc.md:227-231`) says `settle` delivers a reply the host already holds, and the iterator's parse and yield commit in that operation. Native `drain` returns one completion (`host/apple/src/executor_core.rs:321-323`). The Linux agent pumps once on the way in (`host/linux/src/agent.rs:66`) and then only while `pending()` (`agent.rs:1033-1042`), which is `has_pending` (`host/linux/src/presenter.rs:1355-1356`). After the first message an HTTP round is not in flight (`commit.rs:311-314`), so a second already-queued open-stream reply can sit until the next operation. The bounded re-ask already covers that. Say one queued completion is delivered at the start, and the loop continues only while something is in flight.

## What holds

Each awaited `fetch` is its own ticket. The prelude calls `host(1)` per fetch (`js/src/prelude.js:825-828`), and the JS target grant-checks each one in `fetchWith`. `Answer::message` sets `Request::yielded` and `iterator` (`runner/src/request.rs:65-71`). `enqueue_round` strips `yielded`, carries `StreamCount`, and never keeps an iterator request (`commit.rs:1013-1031`). A refused commit drains the round it just handed out and `release_failed` drops the restored ticket (`commit.rs:1476-1485`, `admission.rs:49-62`). `discard_request` stays on continuation tokens (`commit.rs:1152-1155`). `Storage<D>` copies `yielded` and `iterator` onto the continuation (`data/host/src/lib.rs:126-131`). After the first message, HTTP and `native.later` do not hold `clock settle`; storage and continuations do (`commit.rs:311-314`). The first fetch does hold it. Drives re-ask `clock settle` for a later message. That argument is right, with the nit above.

Worker placement and any module in an ordered set are refused at the first round by the envelope (`data/src/envelope.rs:46-48`, `data/src/mixed.rs:369-386`). That matches LLP 1016.000's "not built" and is acceptable. The wasm glue returns 2 for an open round, `waiting()` ignores 2, and `letGo` keeps it (`host/web/src/abi.rs:217-226`, `host/web/glue.js:951-955`). `module-glue.js` relays tag 4. Bake stays deferred like any fetching answer.

Forget calls `return()` (`js/src/prelude.js:1364-1368`). A generator suspended at `await` runs that `return()` when the await settles; the rejected fetch unwinds it. `Snapback.changes()` is hand-written: one `AbortController`, aborted in `return()` (`snapback.ts:499-543`), and `fetchWith` passes that signal (`host/web-js/admission.js:47-57`), including a poll started after an `await` inside `next()`. `heartbeat=1` makes the server write every 2s on HTTP/1.1 (`serve_changes.rs:8`, `serve_changes.rs:23`, `serve_changes.rs:77-79`), so a closed poll frees its worker within a beat.

The stream cursor is the last announced head, not the partition watermark. Polling the watermark busy-loops, because the server returns immediately while `head != since` and the watermark moves only when a reader syncs (`snapback4/client/src/client.rs:885-894`). `wait=0` on the first turn returns the head at once. Readers take `live.cursor`, which includes store and generation, so a replaced store or a new generation re-asks them even when `seq` is unchanged. One long-wait worker per live client, 32 per host (`serve.rs:436`), is the right steady-state cost once ephemeral wakes are named.
