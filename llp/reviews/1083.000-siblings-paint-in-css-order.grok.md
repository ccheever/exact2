## Concerns

**1. blocking — §3's third row is wrong, and the new rule reverses a locked paint case.** Today an earlier layered sibling isolates the next static sibling. In `S`, `T` (static, holding `P`), `X`, both `T` and `X` are isolated (`host/web/src/layers.rs:95-97`, `259-263`). The table says only `X` is isolated and that the row is unchanged. After the change `T` is no longer isolated, so `P` escapes into the parent's step-8/step-9 list.

That is the fixture `parity.mjs --paint` already locks. `host/web/src/parity.rs:45-65` is a relative parent, an absolute at `z-index: 1` (blue), then a static wrapper holding an absolute at `z-index: 2` (red). Expected pixel is blue. Today the wrapper is isolated, the red is trapped, and the blue's `z-index: 1` paints above the group. The same happens natively: the wrapper's used `z-index` is 0 and the blue's is 1 (`NodeViewIOS.swift:771-778`, `NodeViewMac.swift:749-756`; Linux sorts that pair in `host/linux/src/paint.rs:1238-1260`). §3 stops isolating the wrapper because the blue sibling is layered. On the web the red then paints above the blue (`z-index: 2` against `z-index: 1`). On a native band sort the wrapper stays band 0 and the blue stays `+z`, so the blue stays on top. Web and native diverge, and D6's "existing `--paint` cases must still pass" fails on the web. LLP 1001's own example of this trap is `llp/1001-kernel-v1.spec.md:511-515`. §6.4's "unchanged" is the same claim.

Resolve it by deciding the cousin case explicitly: either keep isolating the unlayered holder so the descendant stays trapped (and say what that does to the holder's own background), or name the blue/red reversal as a deviation and change `PAINT_EXPECTED`. As written, §2's subtree band order and §3's web result are different orders.

**2. blocking — band L is `Paint::stacks`, and that set is wider than CSS step 8.** `STACKS` (`host/web/src/layers.rs:41-60`) includes `Transition`, `LayoutTransition`, `ExitAnimation`, `DragTimeline`, `AnimationTimeline`, `PressScale`, and `Opacity`. The web host does not give those a stacking context just because the row is set:

- `transition` is emitted as CSS `transition` (`host/web/src/css.rs:41-69`). The property does not create a stacking context.
- `exit-animation`, `drag-timeline`, `animation-timeline`, and `layout-transition` are custom properties (`css.rs:85-136`).
- `press-scale: 1` emits no CSS (`css.rs:1177`). `press-scale` other than 1 emits `scale: calc(...)` (`css.rs:191-196`), which does create one.
- `opacity: 1` is a real `opacity` declaration and does not create a stacking context. `backdrop-filter: 0` is emitted as `none` (`css.rs:565-566`).

§3 isolates a later static box only when an earlier sibling is unlayered. A `transition` box matches `paint_own` (`host/web-js/src/style.rs:398-417`, `host/web-js/src/rows.rs:28-29`), so the later static box is not isolated. The browser then paints that static box over the transition box. Native band L paints the transition box over it. Same split for `press-scale: 1`, `opacity: 1`, and the custom-property rows. The old rule isolated the followers and kept tree order on both sides.

Resolve it by banding a box from the CSS it actually emits (positioned, or a property that creates a stacking context at the current value), and by keeping follower-isolation for rows that only might stack later.

**3. blocking — D3's subview reorder fights accessibility, focus, exits, and several index readers the audit list misses.** VoiceOver and AppKit accessibility walk subview order (`NodeViewMac.swift:345-346`; iOS uses the default container order). The macOS key-view loop does too (`PresenterMac.swift:1118-1126`). HTML focus and the accessibility tree stay in tree order when paint order changes. A sticky header moved to the end of `subviews` is read and tabbed after the rows.

Reordering also breaks index-as-tree-index uses that are not in D3's list:

- Dialog and menu restore: `DialogsMac.swift:21`, `93-95`; `MenusMac.swift:23`, `146-149`, `168-173` (the saved index is updated from the children-op list, then applied to `subviews`); `MenusIOS.swift:37`, `297`.
- Navigation's first snapshot of logical children (`NavigationIOS.swift:168-192`) and every `root.subviews.first` used as the page root (`PresenterMac.swift:1011-1014`, `PresenterIOS.swift:834`, `NavigationIOS.swift:168`).
- Flat-leaf interleave assumes the children-op id list and the view/layer order are the same order (`FlatLeavesIOS.swift:203-254`).
- Swipe-action icon capture takes `container.subviews.first` (`SwipeActionsIOS.swift:370`).
- Exits are kept above their old siblings by `bringSubviewToFront` / `addSubview` above nil (`PresenceIOS.swift:29`, `PresenceMac.swift:30`). A later band sort that appends a band-L sibling puts the ghost under it. Parked rows use the same trick (`NodePoolIOS.swift:281-282`). Segment bars are brought to front (`SegmentsIOS.swift:255`).
- `CollectionMac.orderChildren` (`CollectionMac.swift:223-227`) rewrites subviews to the array it is given, non-`NodeView`s first. Passing the children-op's tree-order ids undoes the band sort.
- Reorder lifts set `zPosition = 1000` (`ReorderHold.swift:189-198`; tests in `ReorderMacTests.swift:59` and `ReorderIOSTests.swift:83`). D3 sets `zPosition` back to 0 and deletes `hitOrder` (`NodeViewOrderIOS.swift:14-22`) and `raisedHit` (`Sticky.swift:133-145`). The phrase "except as LLP 1077 D8's depth" does not match the code: nothing in D8 writes `zPosition`.

`cacheDisplay` (the agent's default screenshot, `AgentMac.swift:757-765`) follows subview order and ignores `zPosition`. That part of D3 is right for the default capture. The window-server path (`AgentMac.swift:737-750`) follows layers. Reordering subviews makes those two captures agree for ordinary layers and makes VoiceOver disagree with the web.

Resolve D3 by keeping tree order in `subviews`, `accessibilityChildren` / `accessibilityElements`, and the key-view walk, and by saying how a lift, an exit ghost, a parked row, and a remote `WKWebView` layer stay above the right siblings. If subview order is still the paint order, the audit has to include the index readers above and an accessibility order fixed to the kernel's child list.

**4. material — D2 misstates when the compiler adds `relative`, and the "no CSS mechanism" claim.** `positioned` adds `relative` only when the box can hold an absolute descendant, or is a scroll-by-default tag, a canvas, or a Markdown editor (`contract/lower/src/tags.rs:153-178`, `class.rs:92-99`). LLP 1074 records the narrowing (`llp/1074-css-taffy-lacks.rfc.md:36`). A clipping cell that holds nothing absolute stays `static`. It is band 0 on every host. D2's blanket "a clipping or pressable box paints like a positioned one" covers boxes the compiler leaves in flow.

`press-scale` other than 1 is already step 8 on the web because of the emitted `scale` property, so calling that a deviation from CSS is wrong for this host. `press-scale: 1` is the case that stays in flow and must not be band L (concern 2).

`contain: layout` (CSS Containment 2) is a containing block for absolute and fixed descendants and does not, in that spec, create a stacking context; paint containment does. The parenthetical in D2 that lists it with the step-8 mechanisms is the wrong reason to reject it. It is still a poor substitute: it also contains `fixed`, it makes an independent formatting context, and a non-stacking containing block still lets absolute descendants paint in the ancestor's level-0 layer. State those costs if the rejection stays.

**5. material — D1's "build time for literal rows, runtime for bound rows" does not match how the JS target decides.** Isolation is decided in `paintFlush` for every `data-exact-box` element (`host/web-js/paint.js:18-31`), literals included. Build time only marks candidates (`style.rs:250-269`, `323-391`). `element_children` flattens every region arm into one sibling list (`style.rs:85-104`), so a build-time isolation bit sees arms that are never siblings. An `each` root is one template node; later copies must be isolated and the first must not (`style.rs:387-389`). A literal follower of a bound position depends on `data-exact-position` at runtime (`rows.rs:23-27`, `rt.js:577-578`). Adoption strips baked `isolation` and redecides (`rt.js:536`). The server document bakes the same walk as `relayer` (`host/web/src/document.rs:499`, `666`). One kernel rule has to feed `relayer`, `document.rs`, `isolates`, and `paint.js`. Baking the bit onto literal elements will isolate the wrong arm and the first copy.

**6. material — D6 cannot see the disagreement in concern 1, and it fights the fixture it says must pass.** The new fixture records the topmost box. On row 3 a point covered by `X` is `X` on both hosts while `S` and `P` are reversed underneath. The nested-z probe has no third sibling: the topmost box itself flips, so `--paint` fails if §3 lands. `host/web/parity.mjs:173` still says Linux does not order `z-index` and refuses Linux and iOS; that comment is already stale relative to LLP 1083 D6. The new fixture also never mentions `each` copies, region arms, a bound `position`, `opacity: 1`, or a `transition` row.

**7. minor — a few statements are looser than the code.** Appendix E's stacking-context list is background, negative, blocks, floats, inlines, level 0, positive. The table's "step 3 / 4–7 / 8 / 9" is a different numbering; the category column is the rule that matters, and Exact has no floats or inline layout (LLP 1074 §7), so collapsing in-flow siblings into one tree-order band matches the boxes that exist. `usedZIndex` returns the numeric field, whose default is 0 (`schema.json:2144-2147`). It cannot tell `z-index: auto` from `z-index: 0` on a flex or grid item. CSS makes only the explicit 0 a stacking context. D5 is right that a negative `z-index` stays above its parent's background on every host (`paint.rs` paints the parent, then children). When the parent is not a stacking context, CSS also sinks that descendant under the parent's siblings, which D5 does not say. A positive `z-index` descendant of an unlayered sibling sinks the other way: step 9, above an isolated later sibling (concern 1).

## Answers

**1. §3 does not produce §2's band order, and it diverges from native on cases that agree today.**

The simple sticky/relative-then-static case does. `S` is band L, `X` is band 0, §3 does not isolate `X`, and CSS paints `S` above `X`. A sticky header over static rows is that case. A sticky header over `press-scale` rows is not, when `press-scale` is not 1: both are level-0 stacking contexts, tree order puts the rows above the header, and a positive `z-index` on the header is what lifts it. The fixture should expect that Chrome result.

Counterexamples:

- **Nested z, already in-repo.** Blue `z-index: 1`, static wrapper, red `z-index: 2` (`parity.rs:51-54`). Today every host shows blue. After §3 the web shows red and native band order shows blue.
- **`S`, `T(P)`, `X` with no extra z-index.** Web, `X` isolated: level-0 tree order is `S`, then `P` (it escapes `T`), then `X`, so `P` is above `S`. Native bands: `T`'s whole subtree (including `P`) is band 0, then `S` and `X` in band L, so `S` is above `P`. Today both show `P` above `S`, because native paints whole subtrees in tree order and the web isolates `T` as well as `X`. The band sort is what creates the split.
- **`transition` / `opacity: 1` / `press-scale: 1` followed by an overlapping static sibling.** Web: the static sibling is on top. Native band L: the "stacking" row is on top.
- **`each` copies of a static row that holds a relative child.** Runtime `paint.js` can isolate later copies if the rule is the DOM rule. A build-time bit on the template node isolates the first copy too, or none of them. Region arms flattened by `element_children` (`style.rs:85-104`) are the same class of mistake at build time. Bound `position` is already a runtime attribute (`rows.rs:23-25`); a literal row after it cannot be decided at build time.

**2. The "no CSS mechanism" sentence is false, and the rejected alternative is still worse for the boxes that are actually `position: relative`.** `contain: layout` contains absolute descendants without painting the box at level 0 and without a stacking context (paint containment is the one that stacks). It also contains `fixed`, changes margin collapse, and does not trap the absolute child's paint. Reject it for those reasons. For a box the compiler really marks `relative` (`tags.rs:179-186`), treating it as band 0 on native while the page paints it at level 0 splits an earlier authored `relative` from it: the web paints the clipping box above that sibling, native band 0 paints the sibling above the clipping box. A shared "this box paints as positioned" deviation is the smaller split, and only for those boxes. Clipping boxes with `holds_nothing` are already in flow everywhere and should stay band 0.

**3. The audit list is not complete, and subview reorder is the worse of the two options unless accessibility order is saved.** Besides the list in D3, these read or write a tree index through `subviews`: `PresenterMac.swift:931-946` and `PresenterIOS.swift:884-905` (the writers), `PresenterMac.swift:1118-1126` (Tab order), `DialogsMac.swift:21` and `93-95`, `MenusMac.swift:23` and `146-173`, `MenusIOS.swift:37` and `297`, `NavigationIOS.swift:168-192`, `FlatLeavesIOS.swift:246-254`, `SwipeActionsIOS.swift:370`, `PresenceIOS.swift:29`, `PresenceMac.swift:30`, `NodePoolIOS.swift:281-282`, `SegmentsIOS.swift:255`, `CollectionMac.swift:223-227`, `GlassGroup.swift:228-255` (it replays whatever order the array has), and `root.subviews.first` for the page background and viewport fit. Glass groups and the children-op diff keep working if they are given the band-ordered list and chrome (scroll indicators, the glass container, parked rows, exit ghosts) is left out of the sort. Dialog restore, flat-leaf interleave, the navigation snapshot, the swipe glyph, and `root.subviews.first` do not.

Reorder is a `zPosition` of 1000, not a subview move. Arrange on Linux is "paint this child last." Both have to stay explicit. Exit ghosts have to stay the frontmost subview for the whole exit. `zPosition` is also what keeps a `WKWebView` under a later sibling.

Subview order is better for the default `cacheDisplay` screenshot and for not turning a band into perspective depth. It is worse for VoiceOver, Tab order, and every index above. That reading-order change is not acceptable under "the web is the standard": paint order and accessibility order are different orders in CSS. A banded `zPosition` keeps tree order for both, at the cost of a real 3D depth under `sublayerTransform.m34` and a per-touch sort whenever any sibling's `zPosition` is non-zero (`NodeViewOrderIOS.swift:15`). Homogeneous `press-scale` rows are all `zPosition` 0 today, so the "every touch sorts the list" cost appears only if band L is encoded as a non-zero `zPosition` even when every sibling is in that band. Either design needs an explicit hit path for the reorder lift.

**4. §6 is not accurate.** Item 1 describes `X` ending above `S` and treats native as matching the web. After §3 the web has `P` above `S` and native band order has `S` above `P`. The nested-z case has no `X`, and the web's top box flips. Item 2 is too wide: `holds_nothing` clippers stay in flow, and `press-scale` other than 1 is already a stacking context on the web. Item 3 misses the sink under the parent's siblings, and the opposite escape of a positive `z-index` descendant. Item 4 is the nested-z behavior, and §3 removes the isolation that enforces it. New deviations the rule adds: `transition`, `opacity: 1`, `press-scale: 1`, and the custom-property motion rows paint as band L on native and in flow on the web; VoiceOver and Tab order follow paint order if subviews are reordered.

**5. The parity test is not sufficient.** Topmost-at-a-point misses `S` versus `P` whenever `X` covers the probe. It does catch the nested-z fixture, which then fails, contradicting the "must still pass" line. It needs the order of every box under the point (`elementsFromPoint` already returns that), a probe where `S` and `P` overlap outside `X`, the nested-z probe kept as whatever the new rule really does, a `transition` and an `opacity: 1` beside a later static sibling, `press-scale: 1` and `press-scale` not 1 against a sticky header, a flex item with `z-index: auto` and one with `z-index: 0`, an `each` of two copies, both arms of a region, and a bound `position` toggled at runtime. Linux hit-testing is reverse paint order (`presenter.rs:1089-1102`), so painted-box order covers Linux hits. Apple needs `hitTest` and a capture, and the capture has to be the one the user sees: `cacheDisplay` and the window server disagree when `zPosition` and subview order disagree.

**6. The strongest overclaims, with the lines above.** §3's "unchanged" third row (`T` is isolated today). §2's "native paints what the web then paints" for that case. D6's requirement that `parity.rs:65` stay blue while §3 makes it red on the web. D2's account of which boxes become `relative`, and of `press-scale` at rest. D1's build-time literal decision. D3's claim that `hitOrder` and `raisedHit` can be deleted while `ReorderHold` still writes `zPosition`, and that the audit list is the full set of tree-index readers. D5's "above the parent's background" as the whole negative-`z-index` story.

## Concerns

**1. blocking — A non-zero `z-index` descendant of a box that does not trap still paints in different orders on the web and on the native hosts.** Rules (a) and (b) only force a static holder to trap when an earlier sibling is positioned, stacks, is isolated, or escapes. A first static holder is not isolated. Rule (b) then isolates a later static sibling, which is only a stack level of 0 (`isolation: isolate` on a static box). A descendant with a positive `z-index` paints in the parent's positive layer, above that sibling. Native rank paints the holder's whole subtree at rank 0, then the sibling at rank ½, so the sibling covers the descendant. Deviation 1 says the isolation makes those hosts agree.

Arrangement: `T` static, holding `P` (`absolute`, `z-index: 2`), then `X` static. Web: `P` above `X`. Native: `X` above `P`. The same split with `S` (`relative`, `z-index: auto`) in place of `X`, because (b) does not apply to a positioned sibling. Nested static wrappers do this too: `holds` propagates through `M` in `T > M > P`, and `T` still is not isolated.

The other side is undeclared as well. `A` (`relative`, `z-index: auto`) holding `N` (`z-index: -1`), then `B` static: D5 does not isolate `A` (`A` is not static). On the web, `N` joins the ancestor's negative layer and paints under `B`. On native, `N` stays inside `A`'s rank-½ subtree and paints over `B`. Deviation 7 states only the positive-`z` version of this.

The six worked rows do not include these. Row 3 (the nested-`z` fixture) stays blue, because `S` precedes `T` and (a) isolates `T`. Row 4 is true only while `P` is `z-index: auto`.

Resolve: trap every non-auto `z-index` before it can leave a static ancestor (extend D5 to positive `z-index` and to each static ancestor that does not itself trap), and state the negative-`z` descendant of a positioned `z-index: auto` box in §3. Until the hosts agree, delete the "isolated to agree" sentence.

**2. blocking — A flat leaf is not rank 0, and nothing in the leaf painter assigns `zPosition`.** `position_type` is an inert flat-leaf row (`host/apple/Sources/ExactKit/Prepared.swift:57`), so an absolute or relative colored leaf stays flat. `flush` inserts layers in tree order and never sets `zPosition` (`host/apple/Sources/ExactKit/IOS/FlatLeavesIOS.swift:228-254`). `runKey` (`:220-226`) merges adjacent leaves that share a fill, including one positioned leaf and one static leaf, into one shape layer that can have only one `zPosition`.

Arrangement: absolute flat leaf `B`, then static view `V`. The rank table puts `B` at ½, above `V`. The layer tree leaves both at `zPosition` 0, so `V` paints above `B`. A merged run of `[B, static leaf]` placed before `V` keeps `B` under `V` as well.

Resolve: promote any positioned leaf (sticky leaves already promote), or set each leaf layer's `zPosition` to its rank and refuse to merge a run across ranks.

**3. blocking — Layout containment does not establish a stacking context, and D2 treats a text-flow paragraph as if it did.** CSS Containment 2 §3.2 is inline-size containment. Layout containment (Level 2 §3.3; Level 1 §3.2) establishes an independent formatting context. Paint containment is the rule that establishes a stacking context and a containing block. `textflow-glue.js:519-521` writes `contain: layout` only. Today neither `Paint::stacks` nor the browser lifts that paragraph. D2 and the §7 row that dismisses Grok's concern would rank it ½ on native while the page leaves it in flow.

Resolve: drop the text-flow paragraph from the stacking list, or write `isolation: isolate` on it and declare that as a deviation from CSS. Do not cite Containment 2 §3.2 for this.

**4. material — "Not the identity" is a different predicate from the CSS the web emits.** Transforms 2 creates a stacking context when `transform`, `translate`, `rotate`, or `scale` computes to a value other than `none`. `scale: 1`, `translate: 0`, and `rotate: 0deg` stack. `css.rs` emits those numbers (`css.rs:545-562`); only `perspective: 0` and `backdrop-filter: 0` are rewritten to `none` (`css.rs:183-184`, `css.rs:564-566`). A static `scale: 1` followed by a static sibling is level 0 on the web and rank 0 on native.

Resolve: stack when the emitted value is not `none`.

**5. material — D2 misses stacking and positioning the hosts already inject.**
- A tinted raster gets `mask-image` (`host/web/src/element.rs:199-216`); a symbol does too (`host/web-js/symbols.js:9`). `mask-image` other than `none` stacks. The kernel has no `mask-image` row on that node, so native leaves it at rank 0 and a later static sibling paints above it.
- A static root is emitted as `position: relative` (`element.rs:187-191`). Two roots, sticky then static: both are level 0 on the web, so the later root paints on top; native rank puts the sticky root on top.
- A canvas is emitted with `isolation: isolate` (`element.rs:166-171`, explained at `element.rs:16-19`) so its host-injected surface (`glue.js:633`, `z-index: -1`) stays inside it. The compiler also marks the canvas `relative` (`contract/lower/src/tags.rs:157-178` excludes canvas from `holds_nothing`), so its rank is ½ either way, but the model says a `relative` + `auto` box does not trap. The canvas does trap, on the web only, because of that injected isolation.

Resolve: add these three to the host-generated list, with the root and the tint counted as real stacking or positioning facts.

**6. material — D5 matches native paint only above the parent's background, not above the parent's text.** Inside an isolated box, CSS paints the background, then negative `z-index`, then the box's own text. iOS draws that text into the view (`NodeViewIOS.swift:1290`) and sublayers composite above those contents. Linux paints the node's text and then its children (`host/linux/src/paint.rs:1129-1140`, then the child loop at `paint.rs:1261-1263`). A negative-`z` child stays above the parent's text on both native hosts and below it on the web.

Resolve: declare that remaining difference, or paint the parent's text as a rank-0 layer above negative children.

**7. material — A hit order cached per batch is stale for `zPosition` written outside the batch.** `ReorderHold.raise` sets `zPosition` to 1000 and back to `usedZIndex` (`ReorderHold.swift:186-194`). `raiseLifted` exists because a style batch puts the authored value back. `hitOrder` (`NodeViewOrderIOS.swift:14-22`) and `raisedHit` (`Sticky.swift:133-145`) read the live `zPosition`. A cache filled when ranks were applied does not see the lift, so the row on top is not the row hit.

Resolve: drop the cache, or invalidate it inside `raise`. Equal ranks can still skip the sort.

**8. material — The JS target's own-fact attributes are still "row present", which is the predicate D2 retires.** `rows.rs:28-29` sets `data-exact-stack-*` when `v!=null`, so a bound `opacity: 1`, `filter: none`, or identity `scale` still matches `paint_own`. Literals take the same predicate at `host/web-js/src/style.rs:267-268` via `Paint::stacks`. D2's "re-decide as today" cites the position binding (`rows.rs:23-27`), which does test the value. `paint.js` decides isolation from those attributes (`paint.js:10-17`).

Resolve: name the value tests for every D2 row in `rows.rs` and in the literal `data-exact-layer` emission. Candidacy (`data-exact-box`) can stay broad.

**9. material — Stacking every motion row at rest puts later transition rows above a sticky header.** Both are rank ½, so tree order paints the rows on top. Chrome stacks the sticky header and does not stack `transition`. Several of the rows never stack in CSS at all: `exit-animation`, `drag-timeline`, `animation-timeline`, and `layout-transition` are custom properties (`css.rs:78-136`), and a `transition` of `color` does not stack while it runs. §3.3 says CSS would stack the box only while the motion runs. ## 3. D2 and D3

D2's authored list matches the CSS these hosts actually paint, and it is stricter than today's presence test (`layers.rs` `STACKS`, `rows.rs:28-29`). `opacity: 1`, `filter: none`, `perspective: 0`, and `backdrop-filter: 0` do not stack. Identity `scale`, `translate`, and `rotate` do. `position: sticky` stacks even with `z-index: auto`. Flex and grid applicability is right. The host-injected list matches the emitters cited above, with the pressed-child and text-flow gaps. `navigationKey` is correctly gone. Nothing in this tree emits `will-change` or `content-visibility`.

D3 is the right rule for the browser: a transition counts when the property list names a stacking property or `all`; an animation counts when a keyframe sets one; `layout-transition` and `exit-animation` always count because the hosts move them with transforms. The motion engine's own interpolated set is smaller (no filter, clip-path, mask, or perspective), but the predicate is the declared motion, and §3.4 already says the box stacks at rest. That is implementable on the live host and in `paint.js` if they read the emitted list, including `--exact-scale` rewrites that still name `scale` (`css.rs:186-196`). It is not implementable for the presence parent until that parent is a fact adoption will not strip. The text-flow span is a D2 fact, not a D3 one: while `contain: layout` is installed the paragraph already traps, and after `restore` the parent-of-`layout-transition` rule is what keeps a moving child inside.

## 4. D4

`zPosition` for the rank, `subviews` left in tree order, and one setter that also writes the filter picture and the shadow mirror is the right Apple design. Rank 0 must be sent, because a `WKWebView` remote layer depends on an explicit `zPosition`. Applicable `0` and a positioned `auto` are both ½ (both level 0); the trap is the isolation bit, not a different rank. Flat leaves only at rank 0, with the rank in the run key and `position_type` no longer inert, fixes the r2 merge. The no-cache helper is right for the holders it names. Transients at `2147483647` and `2147483646`, restored through the setter, sit above every real rank except the tie above. Stopping `PresenceIOS.swift:29` and `PresenceMac.swift:30` is required and stated.

The design does not survive contact with negative ranks, with iOS projection, or with the default capture, for the reasons in the concerns. Those are part of D4, not follow-ups.

## 5. D1

The shape is right: pure `own`, `summarize`, `decide`, `rank` over a facts view; the live `relayer`; a `document.rs` post-order side table because `DocTree` has no kernel; `paint.js` mirrored per instance; adoption strips server isolation and decides again. Left to right within a list is necessary, because (a) and (b) depend on earlier siblings. Propagation has to dirty the parent when the export or the isolation changes, not only when today's "layered" bit changes. Widening `data-exact-box`, carrying a signed applicable `z`, and running `paintList` on structural edits are the right adoption of the build-time hole. Rejecting a generated JS port is reasonable if D6 really runs all four web paths.

Still open on this decision: the facts view has to include host-injected stacking and the layout-transition parent, or `paint.js` will not see them in `data-exact-stack-*`; `data-exact-own-isolation` must stay "authored `isolation: isolate`" and not "any Isolation row," which is what `style.rs` writes today; the document pass has to emit the CSS behind a kernel stacking fact (`contain: layout`, canvas isolation, the root's `relative`), not only an `isolation` attribute.

## 6. D5, D6, D7, D8, and whether to build

D5 is small and right once rank exists: sort by rank, then projective depth, then tree order, and keep the Arrange lift last. Linux hit-testing already walks painted boxes in reverse (`presenter.rs:1089-1102`), so it follows. `sort_by` is stable today (`paint.rs:1252`); the third key should be explicit so a later unstable sort does not drop tree order.

D6 is the right fixture shape: pixels, separate input and Apple logical order, every web path, both macOS captures, the nested-z case labelled §3.1, and the stale Linux sentence at `parity.mjs:173` corrected (Linux does order `z-index`). It is not sufficient while its Exact column can be copied from §4.1. Add probes that separate parent background, parent text, and a negative child on web, Apple, and Linux, and a probe for the layout-transition parent at rest. `elementsFromPoint` stays a cross-check; the ghost is `pointer-events: none` (`presence-glue.js:299`).

D7 will catch gross app regressions and iOS hit-order changes in flat lists and glass groups. It will not catch the negative-z split unless some screen overlaps a negative child with its parent's background.

D8's order is right: kernel tests first, then every web path plus Apple, Linux, and the LLP 1001 rewrite in one landing, then the heavy-list measurement. §6's kernel and Linux costs are real. The missing costs are the ones in the last §8 row.

It is not ready to build. Fix the negative-z contract first, then the motion parent, the text-flow emit, the iOS plane, the capture inputs, and the remaining hit holders. The rank table, rules (z)/(a)/(b), and the worked rows other than the inside of `A(N z−1)` can stand.
