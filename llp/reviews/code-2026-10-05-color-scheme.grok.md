NOT READY

1. **Must-fix.** An inline run paints in its paragraph’s scheme, so a nested `color-scheme` on a run is dropped. `host/apple/Sources/ExactKit/NodeText.swift:93` resolves every run with the paragraph view’s `drawsDark`. The paragraph op does carry the run’s computed `color_scheme` (`style_json_presented` uses `StyleMask::INHERITED` for text), and `host/apple/Sources/ExactKit/BatchShapes.swift:275` sends that key to `paint.set`, which ignores it (`TextRunPaint.swift:44`). `host/linux/src/paint/inline.rs:24` recurses with the same `dark` (and `text_backgrounds` at line 62 does the same). A light run inside a dark paragraph stays dark. A paragraph with no inner override is fine: the text view gets the computed row and sets its own appearance. Fix: keep `color_scheme` on `InlineStyle` and, in `run(dark:)`, use that run’s value when it is `light` or `dark`. On Linux, set `dark` from `node.color_scheme_dark().unwrap_or(dark)` at the start of `text_palette` and `text_backgrounds`.

2. **Must-fix.** A dynamic `color-scheme` of `normal` does not follow the parent. `kernel/src/kernel.rs:176` maps `ColorScheme::Normal` to `None`. `computed_source` (`kernel/src/arena.rs:521`) stops on the node that sets the row, so an explicit `normal` never reaches a dark ancestor. `appearance` (`kernel/src/motion/paint.rs:26`) then uses the session scheme. Linux always paints that result (`host/linux/src/host.rs:603`). Under a dark sheet on a light app, that node paints light. `set_dynamic` accepts `normal` (`ColorScheme::from_name`); the compiler only refuses literals (`contract/lower/src/values.rs:622`). `host/web/src/css.rs:234` writes `color-scheme:inherit`, and Apple’s `.unspecified` / `nil` appearance follows the parent view. §8 says every host treats this as unset. Fix: if this node’s mask has `ColorScheme` and the value is `Normal`, return the parent’s `color_scheme_dark()`. Return `None` only when no ancestor sets `light` or `dark`. CSS-wide `inherit` / `unset` already clear the bit (`kernel/src/style.rs:360`) and should stay that way.

3. **Should-fix.** The JS target writes a dynamic `color-scheme` through as the author string. `host/web-js/src/style.rs:556` has no `ColorScheme` arm, so `style_row` ends at `("color-scheme", "")` (line 649) and `host/web-js/rt.js:821` assigns that string. `normal` becomes CSS `normal` (the page’s schemes). `light dark` and `only …` are applied by the browser. `light` and `dark` happen to be right. Fix: map `null` and `normal` to `inherit`, `light` and `dark` to those keywords, and anything else to `null` with a journal line.

4. **Should-fix.** A stored per-view appearance outranks a newly computed `color-scheme`. `kernel/src/motion/paint.rs:26` reads `views` before `color_scheme_dark()`. `set_view_scheme` adopts the reported bool (line 268) and calls `set_node_dark` with `playing` only when that view had no previous entry (lines 263 and 272). On Apple, `paint_sync` during the commit still sees the old report. The flush after `presenter.apply` (`host/apple/Sources/ExactKit/Session.swift:1007`) retargets transitions. A keyframe that started in that commit, or was already playing, keeps the old halves, because `playing` is false when the view was already reported. Linux’s `set_view_scheme` (`host/linux/src/presenter/preferences.rs:123`) sticks the same way for that node until another report. Production Linux does not call it; the views map there is empty. Fix: use `color_scheme_dark()` first and the views entry only when that returns `None`. After updating the map, adopt with `appearance()`, and pass `playing: true` whenever the resolved appearance changed. Linux keyframes of `light-dark()` inside an override, and content regions, still follow the app scheme, as §8 says.

5. **Should-fix.** A box whose ancestor sets `color-scheme` never receives the row, and the host reparents some of those views out of the ancestor. `host/apple/src/style.rs:838` adds only text color, direction, cursor, pointer-events, and dynamic-range-limit for non-text nodes. Text, text input, image, control, and video get `StyleMask::INHERITED` and set their own override. `host/apple/Sources/ExactKit/Mac/DialogsMac.swift:68` moves a dialog onto the viewport backdrop. `host/apple/Sources/ExactKit/IOS/MenusIOS.swift:353` moves a popover onto a layer on the viewport or modal host. A lifted box then paints in the window scheme while its text stays dark. The sheet that sets the row on itself is fine: that view carries the key, and subviews that stay inside it inherit. The same gap is what macOS descendant updates depend on. `ColorScheme.swift:39` sets `appearance` only on that view. `NodeViewMac.swift:1049` makes it layer-backed after `applyColorScheme` (line 1034). Nothing walks descendants; `viewDidChangeEffectiveAppearance` (line 777) only notes the view that received it. Fix: when `color_scheme_dark()` is `Some`, put `dark` or `light` on every node’s presented style, as with `dynamic-range-limit`. `applyColorScheme` already runs when the key changes, including when it disappears.

6. **Should-fix.** Linux resolves the scheme with a kernel walk per painted node, and a stable override disables flow damage for the whole frame. `host/linux/src/host.rs:603` calls `dark_in` for every node: a views miss, then `node_by_key`, then the ancestor walk. `host/linux/src/paint.rs:871` sets `damage.unsupported` when `p.dark` differs from the parent’s `self.dark`, which is before this node’s assignment at line 932. `host/linux/src/paint/damage.rs:82` then skips flow damage on every frame a color-scheme subtree is mounted. The pixels are the full repaint. Fix: in the painter, if this node sets `light` or `dark`, use that; otherwise keep the parent’s `dark`. Leave `dark_in` for paint motion. Mark the frame unsupported only when a node’s scheme changes.

7. **Should-fix.** An SVG scene is one scheme. `host/linux/src/paint/svg.rs:344` uses the svg element’s `self.dark` for every shape. Apple resolves the scene once from the svg view (`NodeViewIOS.swift:540`, `NodeViewMac.swift:781`). A descendant with its own `color-scheme` stays on the svg’s scheme. Fix: resolve each shape with that element’s `color_scheme_dark().unwrap_or(svg dark)`.

8. **Nit.** §8 disagrees with the code in three places. `llp/1034-scheme-aware-colour.rfc.md:386` says only the setting node and text nodes carry the row; image, control, video, and text input do too (`host/apple/src/style.rs:823`). The same section says the root keeps `light dark`: `host/web/glue.js:764` does, and `host/web-js/rt.js:259` sets `colorScheme` to `""` for `system` (that line is older than this change). `ColorSchemeIOSTests.swift:35` calls `child.applyBoxLayer()` itself, so it does not show that the trait callback repainted the layer. The material’s `traitCollection` does show UIKit inheritance. The macOS test reads `effectiveAppearance` live. `ColorScheme.swift` is built for tvOS 17, where `updateTraitsIfNeeded` exists; the test is `#if os(iOS)`.

Checked and holding: a box that sets the row includes it, a flip rewrites it, and removal drops the key. Flat leaves cannot carry the row (`Prepared.swift` rejects any key outside the inert set, and a `light-dark()` background is not a flat fill). The iOS trait handler calls `applyStyle` again with the style already stored, so `applyColorScheme` does not run twice and the loop stops. Clearing the override to `.unspecified` and calling `updateTraitsIfNeeded` re-resolves that view. The Linux pinned test’s transition inside the dark subtree is a real `dark_in` path.
