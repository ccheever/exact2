## Material

### 1. Dispose discards the account key on every dropped `attest`, including an assertion

D3 (lines 240–246) makes `keyId` the answer's handle and says a dropped attestation calls `dispose`, which discards the key, because no server has seen it and Apple does not say an attested key may be attested again. The declaration puts that handle on `attest` itself (lines 702–705), and both the first attestation and every later assertion return `keyId` (lines 221–223, shape at 137).

The runner disposes every id on a dropped handle-bearing reply, with no look at `format`. `runner/src/runner/modules/handles.rs` (lines 1–19, 177–213) sends `{"dispose": [ids]}` whenever the request is gone. Passkeys do not do this for an assertion: `llp/1133.011-passkeys.rfc.md` puts `handles` only on `create` (lines 515–527) and says a dropped assertion is simply dropped (D11, lines 633–634). A dropped `generateAssertion` has already moved Apple's counter. The server accepts a later counter that is merely greater. Deleting the key forces a new attestation, spends another key on the risk metric, and leaves the server holding a key the device has forgotten.

"Delivered" is also two different facts. The table (line 222) means Apple's `attestKey` failed with `NetworkError`. The bullet (lines 240–241) means the runner handed the answer to the awaiting call. `landed_handles` (`handles.rs` lines 164–175) only forgets the provisional entry. The implementation never receives a delivered signal, so it cannot flip D3's third row from "attest again" to "assert" by anything the seam tells it.

Stage 0 cannot prove the rule it states. §7 (lines 811–812) says the substitute answers at once, with no ticket. Drive 4 (lines 949–950) says to supersede the check while the substitute holds its answer and to see `dispose` in the journal. A substitute answer is disposed only when a held ceremony ends after its request was let go (`runner/src/runner/modules/ceremony.rs` lines 296–322). `Decision::Now` (`runner/src/runner/modules.rs` lines 1018–1035) never calls `arrive`. The per-account lifecycle in the session scratch directory is also not expressible by the declared substitute LLP 1133.002 §6 already interprets, which D15 says is all the seam this RFC needs.

What is sound in D3: one key per account, the id in a file marked `isExcludedFromBackup`, `serverUnavailable` keeping that key, any other `attestKey` failure discarding it, and `invalidKey` generating and attesting a new key inside the same call so the server sees `apple-appattest` for this `clientData`. Those match the recovery the fixture's verify route already branches on (§8.1). Apple's pages for "an attested key may not be attested again" and for `isExcludedFromBackup` were not re-checked from here.

### 2. The one comparison does not classify a person under the gate Excord asks for

D8 (lines 414–418) says an app tests `lowerBound >= 18` for "at least 18" and `upperBound` present and below 18 for "under 18", and that this holds for either platform's bands. D11 (line 523) says that rule is what makes one app work on Apple, Play, and Windows. The only normalization is Apple's `nil` lower bound becoming 0 (lines 420–422). Play is answered as Console bands, written as inclusive ranges 0–12, 13–15, 16–17, 18+ (lines 409–413). Windows is the same kind of list (lines 521). Apple's bounds are "the app's gates" (line 519), and `upperBound` is defined only as "none at or above the highest gate" (line 399).

For Excord's call, `requestAgeRange({ageGates: [18]})` (§8.2, lines 909–912), every minor is the "below your lowest gate" case. After `nil` becomes 0, the block depends on `upperBound` being a number strictly less than 18. The RFC never says Apple returns that. If the upper bound is the gate the person is under (18), or is absent whenever the lower bound was `nil`, both of the RFC's own tests fail, the person is undetermined, and Excord shows the confirmation screen, which a minor can pass. Drive 7 (lines 956–957) thinks `type @t 15` proves the block. The substitute's banding rule (line 832) does not say which integers it emits, so the drive can pass while the device fail-opens.

Play's `NOT_SHARED` and `VERIFICATION_REQUIRED` are both tier-1 `declined` (lines 430–432). The difference is `android.accessStatus`, tier 2. Excord treats every `declined` as the confirmation screen (lines 912–915). A Play response that means "do not continue until the person verifies" is the same tier-1 result as a voluntary decline, and the acceptance consumer opens the channel after a tap.

Apple's `AgeRange` bound convention and Play's access-status duties were not re-checked from here. The hole is in what this RFC specifies: one comparison, one normalization, and a consumer that fail-opens on everything that comparison does not call under 18.

### 3. `keeps_no_answers` does not keep the range off disk, and it does turn off keeping for all of Excord

D10 (lines 507–510) says the `device.age-range` row is `keeps_no_answers`, so an `AgeRange` never sits in `exact.kept.*`. The flag is app-wide. `runner/src/device.rs` (lines 56–58, 435–438) is true if any granted row sets it. `runner/src/runner.rs` (lines 813–819 and 1031) then forgets every `exact.kept.*` entry at every boot and stops keeping.

A mutation answer is not a kept answer. Kept answers are store-reading resource replies (`runner/src/runner/kept.rs` lines 1–5). The Contract example (lines 49–53) stores the range in mutation state, which a cold boot already drops. A `state age persist` would live under `exact.state.` (`runner/src/store.rs` lines 370–374), which this flag does not clear.

Excord is the consumer, and it is a TypeScript data module (`apps/excord/app.ts` lines 1–9), so it is not ready at the first frame. Its lists are store-reading resources (`apps/excord/app.contract` lines 157–205) whose last answers are exactly what `exact.kept.*` seeds. It also has persisted slots the flag leaves in place (`drafts`, `server`, `lastChannels`, lines 79–83). Granting `device.age-range` as specified makes every Excord launch forget those kept lists. The privacy property the section is aiming at is already true of an unpersisted mutation, and it stays false of `persist`.

## What holds

The token belongs in data code alone, and exact2 should verify nothing and relay nothing. That is passkeys' D12 (`llp/1133.011-passkeys.rfc.md` lines 644–655) and purchases' D8 (`llp/1133.015-purchases.rfc.md` lines 590–591): the answer is good while the server's challenge is open, a Contract value is in `state` where a tool can read it, and decoding a Play token or walking Apple's chain needs the app's own server material. The auth fixture's server is a verifier for that fixture (§8.1), and the row it shows is the verdict, not the token.

D1's choice to hash `clientData` in the module is the right shared word. Apple takes a 32-byte `clientDataHash`. Play's standard `requestHash` and classic `nonce` take a short URL-safe string. SHA-256 of the UTF-8 bytes, raw to Apple and base64url (43 characters) to Play, is one digest a server can recompute. The length claims against Play's 500-character cap were not re-checked from here. The cited pages are the ones in D1 (lines 142–149).

D7's table does not drive the module, and that is the right dependence. The module asks the platform and passes the answer through (lines 370–374). A wrong date in the table would not change a call. Those statutes and the 2026-10-25 status were not re-checked from here.
