1. **MATERIAL — Redisplaying an idle track bypasses capture-origin admission.**

   D6 refuses `getUserMedia` and `takePhoto` to tools and wakes, but automatically reacquires the camera when an existing track’s viewfinder becomes displayed (`llp/1133.008-camera.rfc.md:520–533`). The consumer explicitly reuses that track when reopening its camera screen (`:771–793`). A tool invoking an action that reveals the screen can therefore restart physical capture without calling either restricted operation.

   The proposed `displayed(view, bool)` callback carries no origin (`:617–620`); the borrowed predicate only examines visibility (`runner/src/wakelock.rs:45–58`). This conflicts with the causal-origin rule in geolocation D12 (`llp/1133.002-geolocation.rfc.md:520–543`) and recording’s explicit treatment of resume as capture initiation (`llp/1133.009-recording.rfc.md:547–558`).

   **Resolve:** Apply origin and foreground admission to device acquisition and resumption, including display-driven reacquisition and enabling a track. Prove on both runtimes that a tool revealing a previously opened, idle track leaves the camera released.

2. **MATERIAL — Per-track attachments cannot implement the promised sharing of the physical capture graph.**

   D3 chooses one Apple capture session per process, permits consumers to attach their outputs, and says same-camera tracks share an input (`llp/1133.008-camera.rfc.md:287–321`). Meanwhile, camera implementation instances are session-local (`host/apple/modules/ExactExtensions.swift:34–46`) and own their photo outputs (camera D5, `:434–445`).

   Two Exact sessions cannot independently attach their `AVCapturePhotoOutput` objects: Apple permits only one output of that type per capture session. [Apple’s output restrictions](https://developer.apple.com/documentation/avfoundation/avcapturesession/canaddoutput%28_%3A%29?language=objc).

   Android has the corresponding problem: per-track lifecycle bindings do not provide simultaneous sharing. Only the latest active lifecycle’s use cases remain running, and aggregate use-case combinations are constrained. Restricting viewfinders *per track* does not address multiple tracks. [CameraX binding rules](https://developer.android.com/reference/androidx/camera/lifecycle/ProcessCameraProvider#bindToLifecycle(androidx.lifecycle.LifecycleOwner,androidx.camera.core.CameraSelector,androidx.camera.core.UseCase...)).

   **Resolve:** Choose process-owned physical outputs that multiplex logical tracks, capture requests and hatch access, or explicitly exclusive ownership across tracks. Test two Exact sessions opening the same camera; this requires an ownership decision before implementation.

3. **MATERIAL — The proposed Android artifact rule makes camera incompatible with existing date/time controls.**

   D8 item 5 packages the entire CameraX closure as file dependencies, then refuses classes also supplied through Compose (`llp/1133.008-camera.rfc.md:631–650`). Existing Android builds enable Compose for date/time controls and link Material 3 (`host/android/app/build.gradle.kts:9–11`, `:94–97`).

   Both closures contain AndroidX Core and Lifecycle dependencies. Thus an ordinary app combining a camera and a date picker becomes unbuildable under the proposed rule. [Camera View dependencies](https://raw.githubusercontent.com/androidx/androidx/androidx-main/camera/camera-view/build.gradle), [Compose UI dependencies](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/ui/ui/build.gradle).

   **Resolve:** Choose one locked, verified dependency graph—the alternative already identified in §14 question 4—or reconcile host and module artifacts by library identity, version and hash before packaging. Duplicate-class refusal alone does not provide composition. Include camera plus date/time controls in acceptance.

4. **MATERIAL — Selecting `AVCaptureMultiCamSession` cannot deliver the advertised MultiCam hatch.**

   D5 permits choosing the session class (`llp/1133.008-camera.rfc.md:441`), and the ceiling test claims two simultaneous cameras through that hatch (`:471`). However, D3 always displaces the previously running camera (`:313–321`), while D5 reserves inputs and `sessionPreset` to the module (`:442`). D2 also specifies `.photo` (`:253`).

   MultiCam requires multiple inputs, always uses `inputPriority`, and requires selecting each device’s active format. Choosing the subclass does not override the RFC’s arbitration and ownership policies. [Apple’s MultiCam model](https://developer.apple.com/documentation/avfoundation/avcapturemulticamsession/).

   **Resolve:** Define a custom-graph hatch that changes input ownership, format selection and arbitration, or explicitly revise the ceiling claim and scope. The current class-selection hatch is insufficient.

5. **MATERIAL — Web zoom requires a permission decision the RFC currently defers.**

   D1 includes zoom, while D6 models only ordinary camera permission and expressly allows tools to change constraints (`llp/1133.008-camera.rfc.md:172–174`, `:497–527`). §12 attributes the stronger `panTiltZoom` permission only to the deferred pan and tilt features (`:850–851`).

   Image Capture also places **zoom** behind that stronger permission. Without the appropriate permission request, its capability range must not be exposed; applying zoom must request that permission or decline to expose the setting. Ordinary camera permission being granted does not settle this. [Image Capture’s zoom capability and permission rules](https://www.w3.org/TR/image-capture/#dom-mediatrackcapabilities-zoom), [camera permission descriptors](https://www.w3.org/TR/mediacapture-streams/#permissions-integration).

   **Resolve:** Explicitly choose web zoom’s permission and reopening behavior, including origin checks, permission queuing and substitution. Alternatively, declare web zoom unavailable for this stage. An unrestricted `applyConstraints` path must not introduce a tool-origin permission prompt.

6. **MINOR — The Android feature declaration does not make camera optional as claimed.**

   D6 derives only `android.hardware.camera.any required=false` (`llp/1133.008-camera.rfc.md:481–487`). Android requires explicit optional declarations for `android.hardware.camera` and `android.hardware.camera.autofocus` to override the requirements implied by `CAMERA`. Front-only and no-autofocus devices otherwise remain filtered. [Android’s manifest rules](https://developer.android.com/guide/topics/manifest/uses-feature-element#permissions).

   **Resolve:** Correct the derived feature list.

7. **MINOR — The stated photo-settings hatch cannot select RAW.**

   D5 hands over an already-created `AVCapturePhotoSettings` for mutation, while the ceiling test credits that hatch with RAW/ProRAW (`llp/1133.008-camera.rfc.md:445`, `:473`). The RAW pixel format is read-only and selected at construction. [Apple’s RAW settings property](https://developer.apple.com/documentation/avfoundation/avcapturephotosettings/rawphotopixelformattype).

   **Resolve:** Add a settings factory/replacement hatch or identify a supported capture path through the photo-output hatch.

### IMPLEMENTATION-PHASE

8. **IMPLEMENTATION-PHASE — Encode the already-decided conditional permission policy.** Recording §3 specifies camera, microphone, or both according to `getUserMedia` arguments (`llp/1133.009-recording.rfc.md:292–300`). The built declaration machinery currently copies one interface-level permission onto every name (`contract/cli/src/declaration.rs:192–207`), consumed similarly by Rust and JavaScript (`runner/src/runner/modules.rs:303–329`; `host/web-js/modules.js:41–51`). Stage 0 should prove the richer encoding and cross-package admission.

9. **IMPLEMENTATION-PHASE — Prove substitute controls reach the shared implementation.** §9’s `camera.picture` is not a declared source, and `mediaStreamTrack` belongs to media-capture rather than camera (`llp/1133.008-camera.rfc.md:724–742`). Both runtimes currently reject undeclared preference keys (`runner/src/runner/modules.rs:1036–1079`; `host/web-js/modules.js:242–249`). Define their general delivery route and track scoping during stage 0, alongside the planned view/call instance proof.

**IN-DELTA / MATERIAL — Display provenance misses `srcObject` rebinding.** This continues finding 1.

D3:382–390 records the origin that displayed a viewfinder. D8.2:683–690 supplies that origin when its displayed state changes. Consider:

1. A person displays a viewfinder showing track A. Track B already exists but is idle.
2. A ends; the viewfinder stays displayed, showing its empty box. The camera is released.
3. A tool changes that viewfinder’s `srcObject` to B.

B gains its first consumer without a displayed-state transition. The specified mechanism therefore supplies either no causal origin or the earlier app-origin display. Reusing that origin admits a tool-caused capture start.

The current property paths confirm that visibility and rebinding are separate operations: Apple passes aggregate props through `setProps(handle, json)` in [NativeModule.swift:882–902](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r2/capsule/host/apple/Sources/ExactKit/NativeModule.swift:882); the web’s attribute observer calls `setProps(handle, next)` in [native-glue.js:111–118](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/r2/capsule/host/web/native-glue.js:111). Neither carries origin. D6’s requirement to admit every lease does not supply the missing provenance.

**Resolve:** Carry the causal commit origin on track attachment and rebinding, including when visibility remains unchanged. Admit the resulting acquisition under that origin. Add the already-visible-viewfinder/tool-rebinding case to both runtimes’ acceptance. This requires a seam decision before implementation.

**IN-DELTA / MINOR — Apple capture cardinality is inconsistent.**

D3:299 says one `AVCaptureSession` for the process, and :321–325 describes one physical photo output. But :403 permits another macOS camera to open another capture. The per-device decision is otherwise clear in D3:288–291 and recording D3:305–312.

**Resolve:** Describe per-device session/output pairs on macOS and the single active capture on iOS. This wording inconsistency does not independently block building.
