1. **MATERIAL — The data-code reader seam cannot provide D15’s notification guarantees.**  
   **RFC:** §11 D15, lines 778–801; §15 D19, lines 939–953. Bluetooth notifications are data-code-only, yet [samples.rs:175](runner/src/runner/modules/samples.rs:175) identifies a data reader by module name and arguments, without its owning resource. Distinct resources therefore share a cursor. [modules.rs:1093](runner/src/runner/modules.rs:1093) advances that cursor before the containing answer commits; [bound.rs:305](runner/src/runner/modules/bound.rs:305) explicitly releases data-code argument groups only with the whole source name. The JS target repeats these limitations at [modules.js:857](host/web-js/modules.js:857).

   Consequently, readers can consume each other’s batches, discarded answers can lose notifications, and retargeting A→B can leave A subscribed. **Fixing decision:** add stable data-reader identity, generation, delivery acknowledgement and argument-group release to the public seam. Stage 0 must prove two identical readers, retargeting beside another reader, and a discarded containing answer. Pulse’s single reader does not prove these guarantees.

2. **MATERIAL — The shared pad registry needs to own output arbitration.**  
   **RFC:** §3 D4, lines 253–266; D6, lines 324–337; §7 D10 item 1, lines 479–484. Outputs are process-wide, but package implementations are [per session](host/apple/modules/ExactExtensions.swift:143). The proposed registry returns whether output is supported and announces input changes; it provides no effect identity or completion/preemption notification.

   If session B replaces A’s rumble, A cannot reliably answer `preempted`. A’s later cleanup can also stop B’s output or restore an obsolete light colour. This contradicts D6 and the [Gamepad actuator semantics](https://w3c.github.io/gamepad/#gamepadhapticactuator-interface). **Fixing decision:** make the registry arbitrate effects and light ownership across sessions/packages, report completion/preemption, and make teardown release only the caller’s surviving claims. Prove two sessions and two package clients.

3. **MATERIAL — AccessorySetupKit cannot be selected independently per call.**  
   **RFC:** §11 D14, lines 729–743; §12 D16, line 823; §14 D18, line 867. `apple.accessory` selects ASK on one call, but derives an app-wide Info.plist declaration. Apple explains that declaring ASK support changes CoreBluetooth authorization and restricts scans to accessories paired with that app. Another call cannot obtain the specified unrestricted sheet merely by omitting `apple.accessory`. [Apple’s ASK presentation](https://developer.apple.com/videos/play/wwdc2024/10203/).

   **Fixing decision:** choose an app-wide authorization/discovery mode and reject incompatible calls at bake time, or specify a documented coexistence mechanism. Apply that decision consistently to status, discovery and remembered devices.

4. **MATERIAL — The availability decision can make initial setup unreachable.**  
   **RFC:** §14 D18, lines 873–889; §17, lines 1043–1045 and 1060–1061. `available` means “adapter powered on,” yet the Apple manager supplying that state is created by the authorization-requesting operation. Under ASK, Apple additionally makes `poweredOn` contingent on having paired accessories. On the web, `getAvailability()` explicitly counts a software-disabled adapter as available. [Apple](https://developer.apple.com/videos/play/wwdc2024/10203/), [Web Bluetooth §4.2](https://bluetooth.spec.whatwg.org/#overall-bluetooth-availability).

   Pulse hides Connect when `available=false`, potentially hiding the operation needed to establish consent. **Fixing decision:** distinguish capability availability, authorization and radio state; permit unknown radio state before safe observation; keep setup reachable. Add a bound fresh-install drive, since the substitute starts available.

5. **MATERIAL — Notification ownership conflicts with shared GATT handles.**  
   **RFC:** §11 D15, lines 796–815. Subscriptions are keyed by `(gatt, service, characteristic, instance)`, and the last reader writes notifications off. However, multiple `gatt` handles share one platform link. If handles A and B subscribe to the same characteristic, releasing A’s last reader disables the physical subscription B still needs. The [Bluetooth GATT specification, §3.3.3.3](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-60/out/en/host/generic-attribute-profile--gatt-.html) defines one CCCD for that client/server characteristic, not one per Exact handle.

   **Fixing decision:** define logical handle leases over physical connections and subscriptions, counted across handles and sessions. Specify how explicit disconnect, forgetting and conflicting `autoReconnect` options affect other leases. Prove that releasing or destroying one subscriber leaves another working.

6. **MINOR — Identity-only web readers cannot follow `current`.**  
   **RFC:** §2 D2, lines 227–233; §3 D5, lines 311–316. `current` follows button presses, but web polling stops unless values are requested. Switching between two connected controllers produces neither connection event. The [Gamepad specification](https://w3c.github.io/gamepad/#other-events) supplies no button-change event; the existing [gpu-pads.js:28](host/web/gpu-pads.js:28) therefore polls.

   **Fixing decision:** continue acquisition polling while `current` is observed, independently of whether button values cause commits.

7. **IMPLEMENTATION-PHASE — Android rumble requires a manifest permission.**  
   **RFC:** §6 D9, lines 411–418. “Nothing derives” is incorrect for output: Android’s [controller documentation](https://developer.android.com/games/sdk/game-controller/controller-features#haptics) requires `android.permission.VIBRATE`.

   **Fixing decision:** derive this normal permission from output use. This does not require a runtime prompt or invalidate the no-grant choice.

8. **IMPLEMENTATION-PHASE — The bytes refusal would also reject the Contract chooser.**  
   **RFC:** §11 D13, lines 658 and 682–683; D15, lines 767–771. `requestDevice` is Contract-callable, but its manufacturer/service-data filters contain byte-valued prefixes and masks. Refusing every byte-bearing name *by name* would reject even Pulse’s service-only call. [Web Bluetooth filter definitions](https://bluetooth.spec.whatwg.org/#device-discovery).

   **Fixing decision:** make refusal depend on supplied byte-bearing arguments, or provide a Contract-safe filter shape.

**BEYOND — Reader context is a general architectural gap.** Finding 1 also affects motion and other argument-keyed live sources. Repair the shared binding/runner protocol and test it outside the tree; a Bluetooth-specific workaround would leave the parent guarantee false.

**BEYOND — World messages erase caller origin.** D6, lines 339–354, relies on `emit`→Contract send for admission, while D9 refuses tool-origin output. But commands cross [Session.swift:1185](host/apple/Sources/ExactKit/Session.swift:1185) without origin, and emissions return as plain strings through [CanvasSeams.swift:368](host/apple/Sources/ExactSurfaces/CanvasSeams.swift:368). Their handler defaults to app origin. A tool-facing action that commands a world can therefore cause a later emission whose handler starts device output. Decide whether simulation effects require an explicit app-owned lease or preserved provenance; send admission alone does not settle this.

**BEYOND — Android couples pad acquisition to event consumption.** D3, line 247, leaves navigation outside a canvas to the platform, but [ExactActivity.kt:63](host/android/canvas/src/main/java/dev/exact/canvas/ExactActivity.kt:63) suppresses platform dispatch whenever [Pads.key](host/android/canvas/src/main/java/dev/exact/canvas/Pads.kt:39) recognizes a pad key, including D-pad keys, regardless of canvas focus. The registry should observe input while focus routing decides whether to consume it.

VERDICT: NOT READY
