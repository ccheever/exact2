**1. Verdict: RIGHT WITH CHANGES**

**2. Overall assessment**

`share_target` is the right declaration, and reusing location-based routing is sensible. Keeping the Apple extension independent of ExactKit also fits the repository’s architecture. The changes needed concern trusted delivery and Apple’s launch behavior: a location can identify the composer, but the proposed handoffs do not yet reliably preserve the share’s authority, confidentiality and contents.

**3. Concerns**

1. **MAJOR — The web redirect loses the provenance required by the file security model.**

   [D3–D4](/Users/ccheever/projects/exact2-review-1114/llp/1114.006-receiving-shares.rfc.md:179) requires file parameters to arrive through a trusted `deliver_share` call, but the service worker instead redirects to an ordinary GET URL containing those parameters. The existing [web launch path](/Users/ccheever/projects/exact2-review-1114/host/web/navigation.js:868) reads only the pathname and query. The web standard provides a multipart POST and recommends a subsequent redirect; it supplies no authenticated “these query parameters came from that share” marker. [Web Share Target Level 2](https://w3c.github.io/web-share-target/level-2/)

   As specified, the stripping rule would discard legitimate redirected attachments. Exempting the composer URL would admit the forged paths D3 correctly identifies as dangerous.

   **Resolve:** specify a host-owned claim containing the imported files, with an opaque identifier or trusted worker-to-page handoff. Resolve that claim before `deliver_share`, deriving attachment paths exclusively from its recorded files. This can preserve the existing navigation event and avoid a new public Contract API.

2. **MAJOR — The text-only Apple handoff can disclose shared content to another app.**

   [D6](/Users/ccheever/projects/exact2-review-1114/llp/1114.006-receiving-shares.rfc.md:222) puts the complete title, text and URL into a custom-scheme URL. Its security discussion acknowledges duplicate scheme registration but considers only what another app can *send*. Another app can instead **receive** that URL. Apple explicitly says the selected recipient is undefined when multiple apps register the same scheme. [Apple’s custom URL scheme documentation](https://developer.apple.com/documentation/xcode/defining-a-custom-url-scheme-for-your-app?preferredLanguage=occ)

   Consequently, choosing the legitimate share extension can expose private shared text to an unintended recipient. The comparison with an origin-owned HTTPS GET target does not establish equivalent confidentiality.

   **Resolve:** carry text and URLs through the private App Group too, leaving only an opaque token in the launch URL, or provide an authenticated alternative. This moves App Group provisioning into the first Apple slice; avoiding that cost is insufficient justification for transmitting arbitrary shared content through an ambiguous recipient.

3. **MAJOR — Q2 understates the unsupported launch dependency, and its fallback does not cover every share.**

   [Q2](/Users/ccheever/projects/exact2-review-1114/llp/1114.006-receiving-shares.rfc.md:327) recommends the responder-chain approach because the fallback covers failure. Apple’s position is stronger than “undocumented”: its engineers explicitly describe launching the containing app from a share extension as unsupported and warn against runtime bypasses. [Apple Frameworks Engineering](https://developer.apple.com/forums/thread/773342), [Apple DTS](https://developer.apple.com/forums/thread/764570)

   Moreover, D6’s text-only branch retains nothing after completing the request, so the pending-token fallback cannot recover it. D8’s prohibition on all extension UI also leaves no way to explain that a share was saved for later when immediate opening fails.

   **Resolve:** define a complete receive-and-save experience for every payload, including a small native confirmation when necessary. Treat immediate opening as an explicitly chosen best-effort enhancement. Excluding an embedded Contract session remains reasonable; that does not require excluding a lightweight native status view.

**4. What it gets right**

The RFC identifies a real consumer need, adopts the web’s manifest vocabulary, places extension packaging in the build layer, and keeps the extension free of the runner and media decoding. Reusing app-scoped files and existing read grants is sound. The agent input also exercises the host’s import path without adding another operation.

**5. Questions for Charlie**

- **Change Q2:** Is “saved for the next app opening” an acceptable supported experience? I recommend establishing that baseline before adopting the launch workaround.
- **Add:** Is App Group provisioning acceptable for text-only shares as well? I recommend yes, for confidentiality and recoverability.
- **Qualify Q4:** Approve paths in the delivered location only after specifying the trusted claim mechanism on both web and Apple. The stripping rule alone does not complete that mechanism.
