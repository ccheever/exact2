## 1. Verdict

**NOT READY** as a plan to execute, **READY** as a question worth two days. The direction is sound and cheap to test, but r1 spends its first day building host plumbing (bounded subtree reads on the build channel) before knowing whether the stock Elements and Styles panels can show an Exact node honestly, which is the only thing that can sink it. Reorder, name the user, and correct the precedent.

## 2. Direction

Should Exact try this? **Yes. Confidence 78.**

- The reads exist. The runner already answers `tree`, `node` (every row with `authored | dynamic | inherited (+from) | initial`, `site`, `instance`, `planDigest`), `ancestors` and `sites` in-process, and `Inspect.swift` calls them from an ordinary development build with no agent launch (`s.agent("{\"op\":\"node\"…}")`). Native picking, one-instance selection, outlines, the plan map join and the stale-source digest check are all built for LLP 1122 T2c. The adapter is a translation, not a new observation.
- The web is already the oracle. The same plan runs as a real DOM under real DevTools (LLP 1071). What native inspection adds is exactly the delta the web cannot show: what AppKit/UIKit applied, platform-owned values, native geometry. That is a crisp, bounded purpose, and r1 §3 D3 names it. Say it as the purpose, not as a constraint.
- It is cheap to be wrong. A read-only adapter in Bun over existing reads can be thrown away.

Extend LLP 1122's inspector instead? **No, not as the first move, but r1 must say who this frontend is for.** The design tool's inspector (1122 D5) already answers the five questions of LLP 1035.002 in Exact's own vocabulary, with the token chain, which DevTools can never show. Agents, who write most Exact apps (LLP 1143's corpus), read JSON from `agent.mjs` and will not open a GUI. So the DevTools frontend is for people: the author checking a layout, the reviewer hunting tells. That is a legitimate audience and the familiarity argument holds for it. The evidence that decides between the two is the Stage 1 diagnosis the RFC already proposes, with one addition: run it with a person who knows Chrome DevTools and does not know Tamber's inspector. If they reach the answer faster in DevTools, continue; if the inspector's token chain is what they needed, the money goes to 1122.

## 4. Oversights

1. **Major: the order of work.** r1 D1 and §6 Stage 0 start with the attachment boundary and bounded reads on the build channel. The experiment's only real unknown is D3/D2 (can the stock panels show the tree honestly), and that can be tested in a few hours over the existing agent socket with zero host changes. **Resolve:** Stage 0 = a throwaway CDP server in Bun over `agent.mjs`'s carrier under an ordinary agent launch; Stage 1 = the build-channel shape only if Stage 0 passes.
2. **Major: who the frontend is for is unstated.** Agents will not use it; people will. **Resolve:** one paragraph in §1 naming the audience and the one case where DevTools beats Tamber's inspector (familiarity, no token chain needed, the web/native delta). Make the Stage 1 diagnosis a comparison by a person who knows DevTools and not the inspector.
3. **Major: the precedent is misread.** React Native DevTools is a customised frontend build with an inspector proxy, serving a real Hermes `Runtime`/`Debugger`, and it shows the React component tree in its own panel rather than projecting native views into Elements (from memory; verify). The closest precedents for "native tree in Elements" that I know of (Lynx DevTools, Hippy, Weex) forked the frontend. **Resolve:** cite RN for "the frontend can be reused by a non-browser", not for "unmodified", and name the fork-or-extend-1122 stop rule.
4. **Minor: "unavailable" has no CSS spelling.** D3 requires the panel to show an unavailable host value as unavailable; the Styles and Computed panes can only omit. **Resolve:** decide in Stage 0 whether omission plus a UA-origin "platform-owned" rule is honest enough, and if not, that is a fail on fidelity, as D3 already says.
5. **Minor: the editing affordances are tells.** The Styles pane offers checkboxes, editable values and source links regardless of the target. Clicking a source link calls `CSS.getStyleSheetText`; editing calls `CSS.setStyleTexts`. **Resolve:** refuse the write with a protocol error (r1 already says so) and serve the stylesheet text as the Contract excerpt, or accept the tell and record it.
6. **Minor: the web target is the oracle; say so.** A layout bug that reproduces on the web build is already inspectable in real DevTools today. The native adapter's value is the native delta. **Resolve:** one sentence in §1; it also narrows what the Stage 1 diagnosis should be (a defect that does not reproduce on the web).

## 5. Errors

- §1: "React Native DevTools uses the Chrome DevTools frontend" is true; the implication that it is the unmodified frontend is not, to my knowledge (see oversight 3). Verify against reactnative.dev/docs/react-native-devtools and the `@react-native/debugger-frontend` package before citing.
- §2 table, "Apple inspect mode … A: an outline of exactly one requested instance": `Inspect.swift`'s `revealing` and the `selected` state already resolve one instance by generation, plan, site and canonical instance path; the outline command outlines every copy, but the selection is one instance. The gap is a *highlight* of one instance on hover, not identity. Small, but it shrinks D4's host work.
- §4 D1, "The current build channel's selection report is insufficient for arbitrary subtree reads": correct for the channel; incomplete because the same host answers arbitrary reads over the agent carrier today. Nothing else found against the repository.

## 6. Recommendation

**Revise and stay Draft, then run Stage 0 as the spike. Confidence 80.** The revision is small: reorder §6 (spike over the agent carrier first), name the audience, correct the precedent and the stop rule, pick a host app with a live defect, and move the "unavailable" question into Stage 0's pass criteria.

## 7. Strongest alternative

**Extend LLP 1122's inspector into a full Elements-like tree view** (it has the picker, the provenance, the token chain, the outlines and the build channel; it lacks a browsable tree and hover-highlight of one instance). **The deciding measurement:** the Stage 1 diagnosis run twice by a person who knows Chrome DevTools, once in each frontend, on a defect that does not reproduce on the web build. Time to the correct explanation, and whether the token chain was needed to reach it.
