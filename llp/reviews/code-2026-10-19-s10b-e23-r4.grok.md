## Blocker

**`$extends` / `$ref` merge is still exponential.** `tamber/src/import/dtcg.rs:245` (called from the walk at `:358`, after the new check at `:303`).

`extended` follows `$extends` and `$ref` with cycle detection only on the current stack and a depth cap of 64. A diamond is not a cycle: `aN` extends `aN-1` and refs `bN-1`, and both of those extend `aN-2` and ref `bN-2`. Each call re-expands both parents. Depth 30 is a few kilobytes and about 2^30 merges. The walk increments `visits` once per walked node, then calls `extended` on a fresh stack, so the recursion returns only after the blow-up. `deep` does not walk children, so this is independent of the visit cap.

Fix: memoize `extended` by the target's name (each group once) and charge every recursive call to the same `VISITS` budget the walk uses. Add a regression with a depth-20 diamond that must fail quickly.

**The resolver's `expand` starts a new visit budget per leaf.** `tamber/src/import/dtcg.rs:376` and `:761`.

`tokens` always walks with `&mut 0`. `expand` (depth cap 16, cycle check only for a ref already on the stack) calls `tokens` on every leaf. Eight sibling `$ref`s to the next set, ten levels deep, is the round-3 billion-leaf tree: each leaf is one tiny token, under 200,000 visits on its own, and the parent ref is popped before the next sibling. A single DTCG document with `resolutionOrder` and no Tamber context map takes this path (`read` at `:473`), so `is_own` does not divert it into the budgeted export resolver.

Fix: one `visits` counter for the whole import, threaded through `expand` and `tokens`, counting every source. Refuse past `VISITS` before appending more defs.

## Should-fix

**The export budget counts entries, so one fat token is still cloned until memory dies.** `tamber/src/export.rs:559` and `:574`.

`spent` charges 1 per source plus the number of flattened tokens, after `flatten` has already cloned them. A recognised baseline can keep the real context map and point one context at ~25,000 `$ref`s to a single ~500KB `$value`. That is under 200,000 charges and about 10GB retained in `out`, which `tokens_by_context` then keeps. The round-3 tree (many tiny leaves) is refused; this shape is not.

Fix: cap retained clone bytes (a few MiB is enough) and count them before accepting the clone. Memoizing a pointer does not help while every reference still appends its own copy.

**After a budget-legal expansion, winner selection is quadratic.** `tamber/src/import/dtcg.rs:1188`.

A `$ref` tree that stays under 200,000 visits (one shared node per level, ternary, depth about 10) yields on the order of 10^5 defs from about a kilobyte of JSON. The pair loop over those paths is O(n^2) string work, on the debug `cargo run` server the wire actually spawns. `extended` is not on this path: each node's merge is one step, and the walk counts the copies.

Fix: resolve group-versus-token shadows with a parent map or a trie, instead of comparing every path to every path.

**A CLI import is no longer re-marked.** `scripts/tamber-server.mjs:1000`, with the proposal created at `scripts/tamber-server.mjs:1494`.

That is the round-2 bug on `bun exact.mjs tamber import`.

## Security pass

The export resolver and the DTCG walk's own nodes are bounded. `extended`, the resolver's `expand`, and the byte size of flattened tokens are not. Colour and kind reading do not multiply: `colour` and `text` walk the value once, and alias resolution is memoized with a chain cap of 256.

The retry loops cannot be spun. `importHeld` and `remark` each stop after three attempts, and the only continue condition is `error.conflict`. A conflict is returned before `proposals.set`. The Rust child is still one request at a time, so either blocker above stalls every other client for the length of the hang. Three retries only repeat that.

A held re-import's dials, pins, and diff describe one design. Marks come from `import-plan` on text `T`; the hold carries `digest(T)`; `propose` plans the diff from the snapshot it just checked against that digest. Offers on a Tamber re-import are empty.

Only the server sets `reimport`: `importHeld` after a successful hold, then `replaced` when that proposal is recomputed. It is not part of `shown`, and a client `review` cannot turn it on. A hand-built `propose` is not remarked. The CLI hole is the should-fix above.

Earlier guarantees still hold. A baseline is still recognised, then compared as whole contexts and axes, and the operations are still planned against the current design. The retry enters `import-plan` again, so a forged or stale baseline is still `409` with `stale: true` before any search. Dial fallback is unchanged apart from comparing colours through `same`. A client-supplied `dials` or `pins` list no longer causes remark.
