## MATERIAL

**1. A sheet does not win. D3’s nesting claim is false for this tree.**

D3 (lines 181–193) says the nearest displayed holder wins, and that a sheet wins because “the sheet’s content [is] a descendant of the screen in the tree.” In this repository a stack’s routes are siblings. `docs/recipes/navigation-stack.md` (lines 55–66 and 105–106) puts the list, the detail and the modal sheet (`navigationPresentation="modal"`) as sibling columns under `main`, produced by `for e in stack(nav)`.

The displayed rule this RFC adopts keeps the covered screen in the holder set. `runner/src/wakelock.rs` (lines 6–7 and 44–58) and `runner/src/head.rs` (`hidden_route`, lines 90–94; `under_a_sheet`, lines 264–268) treat a route under a sheet as still shown. `docs/reference.md` (“Keep the screen awake,” lines 1589–1594) says that screen holds a wake lock. Wake lock is a boolean OR, so a covered screen that stays shown is harmless. An orientation lock has a value. The screen and the sheet are both holders, neither is an ancestor of the other, and D3’s intersection applies.

A portrait screen with a landscape sheet is then the conflict in D3 (lines 190–199): no lock, the manifest’s orientation, `state.orientationlock.conflict` set. The sheet does not take the window. The same pairing holds for a `dialog` written beside the routes, as in that recipe (lines 63–68): the page behind it stays displayed.

A pushed screen still works. A stack screen under the top is hidden, so only the top route is a holder, and a lock on an ancestor is overridden. D3’s video example (“when the stack pops it,” lines 182–185) is that case. The sheet sentence is the other case, and `head.rs` already distinguishes them (`under_a_sheet` versus `beside_a_pane`, lines 109–111 and 121–129). Side-by-side panes can intersect. A route that covers another cannot, or the cover loses.

Beacons does not hit this. Its lock sits on the one world canvas (`game/games/beacons/app.contract`, lines 63–82). The vocabulary rule still does not do what D3 says for a sheet, which is the ordinary way a screen is shown over another screen here.

**2. The runner decides a conflict it cannot see, because only the host knows `current`.**

§0 item 3 (lines 89–91) and D3 (lines 223–228) resolve `current` on the host, at the moment the session’s lock comes to include it, and the runner never learns the screen’s orientation. D3 (lines 190–199 and 230–234) also has the runner compute the intersection, journal `orientationlock: conflict: …; none held`, and set `state.orientationlock.conflict` when the intersection is empty. `current` is one of the sets in that intersection (line 227).

Those two decisions do not meet. A portrait holder beside a `current` holder is not a conflict in the runner: `current` is not a set there. After the host resolves it, the intersection may be empty. Nothing in D5–D8 tells the host to journal that as a conflict, to clear the runner’s lock, or to fill `state.orientationlock.conflict`. §8 (lines 488–492) defines `held` and `lock` from the runner’s result and `applied` from the host. The agent can then see a held lock whose window is following the manifest.

Beacons uses `current` alone (§9, lines 518–519), so this does not break the consumer. It does make the composition rule, as stated, unimplementable for a value the RFC adds.

## Weighed, and sound

**D11 against LLP 1133 D5.** Vocabulary is the right package. LLP 1133 D5 (the packaging section) defaults to an extension, and allows vocabulary when the runner or the kernel is the only place the work can be done. All three reasons hold. Which elements are displayed is `exact_runner::wakelock::displayed`; a package hears that only for its own views (LLP 1133.008 D8 item 2) and for canvases it feeds (LLP 1133.013 D12 item 3). The window is the presenter’s: the iOS root and full-screen controllers, the Android activity (`host/android/canvas/.../Requests.kt` already performs kind 8 on that activity), the page. Motion’s context exposes the angle as a read (`host/apple/Sources/ExactKit/ScopeHatches.swift`, lines 125–134), not a setter. And Beacons is a game: LLP 1133.013 §13 records that the wasm host loads no extension modules, while it already loads `host/web/wakelock-glue.js`. A `lockOrientation()` package would miss the consumer’s web host and would still need this host seam.

**D1 and `current`.** An attribute held while the element is displayed is the right form. It is the same leak argument as LLP 1125 D11, and it matches UIKit asking the controller that fills the window. Calling that a D1 declared deviation is slightly loose — the web has `lock()` / `unlock()`, and D1’s deviation is for a missing or too-coarse name — but the form itself is the right decision. `current` is a fair shared word: the web has the idiom and no type name. It is the lock Beacons wants.

**D10.** No platform API cited here has an authorization for this. The web’s gate is fullscreen, which the person enters. A lock does not start a device or open a prompt, which is LLP 1133 D6 rule 3’s line. A wake with no window locks nothing (LLP 1133.017). A tool that shows a landscape screen showing it in landscape matches “the screen a tool may already display.” The effect ends when the holder stops being displayed. Camera’s origin check is a capture start; this is not one.

**The manifest bound, one window, embedders.** Narrowing the manifest, and refusing a disjoint literal at bake, is the right single rule. UIKit throws `invalidInterfaceOrientationException` for a mask outside Info.plist; Android and the web would otherwise widen. One lock for the session’s window, scenes locking separately, and an embedded session journaling `the window is the embedder's` because it does not own the window, all match the host model.

**Beacons needs this, and the iPhone drives can show it.** `referenceFrame="screen"` turns gravity by the window’s angle (`packages/motion/apple/Motion.swift`, lines 353–373, reading `context.orientation`). A rotation mid-tilt remaps the stick against the tilt the player is holding and rotates the HUD. The canvas stays mounted through pause and victory (`app.contract`, lines 62–82), so `orientationlock=(tilt ? "current" : "none")` holds for the whole steered session and releases when tilt turns off. There is no way in this game to leave the world while it is mounted; drive 4 using the stage 0 fixture is the honest release test. Drives 2 and 3 observe the scene’s interface orientation (`host/apple/Sources/ExactKit/IOS/TouchIOS.swift`, lines 187–198) after `XCUIDevice.shared.orientation` (`host/apple/touches.swift`, lines 150–153), which is the right pair for “the device turned, the interface did not.”

**Brightness, screenshots, and a Contract reader for the angle.** Leaving them out matches `rules/RULES.md` (a spec needs a consumer) and D9 item 12. The roster row names three capabilities; only the lock has an app. Excord’s app-switcher snapshot is a real gap and a product choice (question 2), not something this module has to take. Motion’s package context already carries the angle for the screen frame. No Contract reader is required for Beacons while a held lock keeps that angle still.

## MINOR

**The bake does not, by itself, prevent the iPhone throw D3 exists to stop.** D3 (lines 201–217) refuses a literal that shares no orientation with the manifest word. In the Screen Orientation API, `portrait` includes `portrait-secondary`. `host/apple/devices.mjs` `phoneOrientations` (lines 762–770) maps every portrait, including `portrait-secondary`, to upright only, and the comment says that is the only portrait an iPhone with Face ID offers. A literal `orientationlock="portrait-secondary"` in an app whose manifest says `portrait` shares an orientation with the manifest word, so the bake allows it, and the Info.plist `orientationKeys` writes does not contain upside-down. D5 (lines 269–271) says D3’s check refuses `portrait-secondary` on the iPhone. That is true of the plist image, and it is not what the bake bullet says. The host intersection with “what its device supports” (line 233), applied before any UIKit call, is what avoids `invalidInterfaceOrientationException`. The bake does not.

Stage 2 (lines 599–603) allows Android to land “built, not driven” when this Mac’s emulator does not boot. LLP 1133.020 §4 row 17 does put an Android phone and tablet on the person checklist. The consumer’s iPhone path is the one the simulator drives actually prove.

**Whole host covers.** `wakelock.rs` (lines 8–12) drops a holder the host has covered whole, including a header it shows as its own bar, because the kernel cannot tell those apart. ## IMPLEMENTATION-PHASE

**Android’s single `screenOrientation` enum.** D6’s “narrowest value that covers the set” has to be chosen for a three-orientation default (iPhone `allButUpsideDown` has no Android constant). The host can do that without a new decision. Restoring `none` for a manifest of `natural` should restore `MainActivity.naturalOrientation()`’s resolved value (`MainActivity.kt`, lines 19–31). The manifest placeholder is `nosensor` (`host/android/app/build.gradle.kts`, lines 20–24), and `onCreate` replaces it once; `configChanges` includes `orientation` (`AndroidManifest.xml`, lines 23–24), so `onCreate` does not run again.

**Who UIKit asks.** D5 names the root and the topmost modal that fills the window. That is the right pair. `ModalController` uses `.pageSheet` unless the route is the fullscreen kind (`ModalIOS.swift`, line 36); on an iPhone a page sheet fills the window and UIKit asks that controller. The override belongs on every `ModalController` that fills the window, and on the navigation controller UIKit actually forwards to. The RFC already states the criterion.

**Web re-ask.** D7’s `fullscreenchange` re-ask is the right shape if `lock()` does not need a fresh user activation once the document is fullscreen. Drive 7 does not show a successful lock. Whether Chrome Android accepts that re-ask cannot be checked from this snapshot.
