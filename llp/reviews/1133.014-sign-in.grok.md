I'll review LLP 1133.014 read-only, starting with the project rules and the RFC itself, then the parent decisions and the code this module has to fit.The RFC is in. Next I’ll check the decisions it inherits—especially passkeys §8, the package rules, and the auth-session path—against the code those decisions name.The split with passkeys is the right reading of LLP 1133.011 §8: one `identity` member on `credentials.get`, passkeys owning the single platform request. As specified, that table cannot be built on the package seam that exists, and several provider cells contradict the platform contracts they cite.

1. **MATERIAL** — The credential-request table does not fit the package seam, so one sheet cannot be built as D10 specifies. §8 of LLP 1133.011 (lines 846–859) is honoured by a member another package declares and by passkeys owning the controller. D10 (lines 654–684) puts that table "in the context" and passes `ASAuthorizationRequest` and `CredentialOption` objects through `ExactCredentialMember` in `ExactPackage.swift`. The seam does not work that way. `host/apple/compose.mjs` lines 9–14 constructs a new `ExactPackageContext` per package; `ExactExtensions.swift` lines 8–10 and 58–68 makes each adapter on that extension's first call; `host/android/canvas/.../Extensions.kt` lines 10–15 and 62–63 does the same with a private `ExtensionContext`. A table on sign-in's context is invisible to passkeys. `ExactPackage.swift` imports only `Foundation`, and each package is its own Swift module, so sign-in cannot hand passkeys an `ASAuthorizationRequest` unless `ExactPackage` itself imports AuthenticationServices. That import is forbidden by the link gate: `host/apple/link.mjs` lines 9–20 and 41 and `ExactAuthSession/AuthSession.swift` lines 1–8 allow AuthenticationServices only inside `ExactAuthSession`, which is linked only when the grants name `auth.session`. `host/web-js/modules.js` lines 106–115 loads an implementation on the first use of that extension's own names, while D10 item 1 routes `get` to passkeys, so an identity-only `get` never loads sign-in and the handler is never registered. Passkeys §8 then refuses the undeclared member. The same hole breaks one runtime owner and conformance (LLP 1133.001 D2 rule 3, D4, D7): a replaced passkeys implementation has no suite obligation to dispatch foreign members. **Decision:** keep the member and the single owner. Put one session-scoped registry in the host, not on each package's context. Packages register plain descriptors; a host credential capability, linked when the app depends on passkeys or sign-in, is the only code that imports AuthenticationServices and `androidx.credentials`, builds the one controller or `GetCredentialRequest`, and returns the picked credential to the handler. Admission loads every package that declared a present member before the owner runs. Passkeys' conformance suite covers "a registered member is in the one request" and "an unknown member is refused". `exact add sign-in` writes a direct dependency on both packages (LLP 1133.001 D4; LLP 1133.009 D3 does this for recording).

2. **MATERIAL** — Google on Apple cannot use the host auth session under the grants D8 declares. D6 (lines 439–464) runs the OAuth code flow with PKCE through "the host's auth session" and says the two endpoints "are named by the grant (D8)". D8 (lines 532–560) only declares `auth.google <client id>` and, on Apple, "nothing in Info.plist". `runner/src/auth.rs` `check_grants` (lines 332–376) refuses an authorization URL without `auth.session` for that origin and a callback without a matching `auth.callback`. `Auth.swift` lines 74–77 refuses to open a sheet unless `AuthSessionLink` is installed, and `link.mjs` lines 20–30 installs it only for an `auth.session` grant. A side door that calls `ASWebAuthenticationSession` from `SignIn.swift` skips that link, the grant check, and the one-session table in `AuthSessions`. The token response also carries an `access_token` (and a refresh token if `access_type=offline` is ever set); D6 says only `id_token` is the credential and never says the rest is dropped inside the implementation. The loopback choice is right: LLP 1133.005 D9's loopback is `NSWorkspace.open` plus a local listener, and `ASWebAuthenticationSession` accepts a private-use scheme or `https` only, which is what an iOS-type client uses on macOS. **Decision:** `auth.google <ios-client-id>` derives `auth.session https://accounts.google.com`, `auth.session https://oauth2.googleapis.com`, `auth.callback com.googleusercontent.apps.<id>:/<redirect>`, a `net.fetch` for the token origin, and the `auth_session` link. `context.authSession.open` is that same runner path (one session per window, supersession, state check), and the implementation is the source that exchanges. The exchange posts only to the derived token origin, keeps the verifier in the implementation, and returns the `id_token` alone. I could not re-read Google's native-app page here; the redirect path should be confirmed in stage 2 (see implementation-phase item 1).

3. **MATERIAL** — D1's uniform nonce does not match Apple's and Google's token contracts, so D2's server check rejects a real token. D1 (lines 150–156) passes `params.nonce` through to `ASAuthorizationAppleIDRequest.nonce`, `setNonce`, Google's `nonce`, Sign in with Apple JS, and Google Identity Services, and says that value "is in the token's nonce claim on every target". D2 (lines 251–252) tells the server to check `nonce` the same way for both providers. Apple's request property puts in the claim exactly the string you set, and Apple's own guidance is to set the SHA-256 of the nonce you issued. Sign in with Apple JS hashes before it sends, so the claim is the hex SHA-256 of what you passed to `init`. Google's ID token, on the web, on Android's `setNonce`, and on the token endpoint, echoes the nonce parameter unchanged. A server that compares the claim to the raw nonce rejects Apple's web token. A server that compares it to the hash rejects Google. Confidence high; these are the published request contracts, not re-fetched today. **Decision:** the server issues a raw nonce. The module sets Apple's native `nonce` to the hex SHA-256 and passes the raw nonce to Apple's JS (which hashes once) and to every Google API. D2 says Apple's claim equals that hash and Google's claim equals the raw nonce.

4. **MATERIAL** — Sign in with Apple JS cannot be configured with this request. D3 (lines 278 and 294–299) calls `AppleID.auth.signIn()` with `usePopup: true`. D1's provider (lines 140–145) has `configURL`, `clientId`, and `params.nonce` only. Apple's JS `init` requires `redirectURI`, and that URI must be the Services ID's registered return URL on a verified domain. Question 6 (lines 1047–1052) asks Charlie for that return URL, and the interface has nowhere to put it. LLP 1069.006 D8 (lines 513–518) already records that Apple's `form_post` body is invisible to a page that only reads `location.href`, which is what `/.exact/auth/callback` does. Confidence high that `redirectURI` is required. **Decision:** the web Apple cell uses the host callback `https://<page origin>/.exact/auth/callback` (LLP 1069.006 D2's `authCallback()`), the Services ID registers that URL, and the popup flow returns the credential to the page module through Apple's JS success event. The callback page stays a static `no-referrer` page and is not the token's parser.

5. **MATERIAL** — D1, D3, and the ceiling test disagree on what one `get` may contain. D1 (lines 201–210) says that on Apple and Android a `get` with `identity` and `publicKey` is one sheet, and that `withPublicKey` tells the app so. D3 (lines 280–282) says active Google is a `GetSignInWithGoogleOption` that must be the only option in the request, and that Apple on Android is `later`. The ceiling test (line 772) still lists "a passkey and Sign in with Apple in one sheet" on Android. Passkeys' `mediation` is `optional|conditional` (LLP 1133.011 lines 521–526); D1 (line 136) uses `silent|optional|required` on that same parameter and does not say what `conditional` means beside `identity`, or `silent` beside `publicKey`. A portable app that trusts `withPublicKey` will send active Google, or Apple on Android, in the same `get` as a passkey. **Decision:** one sheet is passkey plus Apple on Apple, and passkey plus passive Google on Android. Active Google beside any other option is `NotSupportedError`. Apple on Android stays `NotSupportedError` until that cell exists. `withPublicKey` is per provider and per mode. `conditional` beside `identity` is `NotSupportedError`. `silent` means Google auto-select only, and on Apple it is the `NotAllowedError` D4 already specifies. The amendment to LLP 1133.011 widens `mediation` to Credential Management's four values and states these combinations.

6. **MATERIAL** — The web cell's scripts break the page's script boundary, and the data realm is not a wall in front of them. D3 (lines 327–335) and §7 (lines 811–818) load Google Identity Services and Sign in with Apple JS into the page, and question 3 (lines 1031–1037) calls that the first third-party script an exact2 page loads. Boot is intact: `scripts/boot.mjs` counts the initial document, and a script inserted when the view mounts is after first pixel. The document CSP is not. `host/render/src/serve.rs` `csp()` (lines 1446–1492) allows scripts only from `'self'`, wasm, and sha256 hashes of the host's own bytes. There is no `'unsafe-inline'` for script. D8 (lines 566–574) opens `script-src` to `https://accounts.google.com/gsi/client` and Apple's script host, unpinned, so those files can change without a rebuild. The data module is a hidden same-origin iframe with no sandbox (`host/web/module-glue.js` lines 1–3 and 100–102), and LLP 1027 (around lines 1198–1203) states that realm is an authoring boundary, not a security sandbox. Page script can reach `contentWindow` and `__exact_host`, including `secret.keep`. A hand-built page that loads these scripts does not have that realm. **Decision:** question 3 states the actual reach: those two origins execute as the app's data code, with the store and the grants, for the life of the page. Accept that, and pin every baked script URL the way `csp()` already pins host scripts, accepting that a provider update needs a rebuild. Deriving `connect-src` from the grant is the right shape either way. `Referrer-Policy: strict-origin-when-cross-origin` is already the document default (`serve.rs` line 471); the callback page stays `no-referrer`.

Firing the button is a new ceremony, which aborts the passive ticket; the passkeys recipe restarts a ceremony aborted that way, which aborts the button's sheet. The view also mounts from Contract as soon as `caps.providers` is true, while the nonce arrives later on the data-code task. `renderButton` before `initialize` has no nonce. The provider button is not shown until the page module holds that armed request. Google's completion is app-origin, foreground, because the person consented in Google's UI after the app armed it. Firing an armed request aborts a passive ceremony in that session, and the passive task stays down until the active ceremony ends. A Developer ID slice omits it, prints why, and reports `providers.apple` false. The web grant does not force the entitlement onto that slice.
