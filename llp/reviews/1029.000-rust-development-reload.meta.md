## Overall assessment and recommendation

**Recommendation: PROCEED WITH LIMITED CHANGES.**

Do not radically change direction. Native-first-where-practical + browser Wasm + Pulley-on-physical-iOS + complete-module-replacement with host-owned state is a coherent development-loop architecture, and it correctly narrows the parent 1029 to development only, defers production push, and reuses the proven 1027 D5 prepare/commit/carry shape.

The document is unusually honest about what it has not proven: Wasm compile probes are labeled as query-only, not paint/native/phone metrics; `dlclose` safety is called an implementation gate; iOS Wasmtime is Tier 3; native crashes cannot be contained. That honesty is why this does not need a rewrite — it needs a small interface and lifetime specification before code, then the two probes it already orders first.

## Strengths

- Correct unit of replacement: explicitly bounded business-logic module, not Rust `mod`/file, no heap patching, no per-function hashes, reuse Cargo graph. §1.
- Ownership made explicit: no `String`/`Vec`/trait-object/unwind/allocator across versions, buffers copied to host before producer retires, module caches discardable, durable state in host Store/slots. §3. Matches `carry.rs` carried slots/resources/store/clock model.
- Reuses complete-artifact + all-session prepare/commit + restart-with-carry, latest-edit-wins, invalid state preserves all sessions, no mutation replay, pending-read cancel, stale-reply exclusion. §4. Right inheritance from 1027 D5.
- Native-until-edited with input identity, not Wasm-output equality, incorporating parent D4 correction. §5.
- No combinatorial matrix: dev composition selects adapters, release can ship native-only without Wasmtime. §2.
- Speed section separates the 100ms restart/request-to-present budget from compilation, requires p50/p95 over 20 real edits per surface including first-after-ready, phase timestamps. §6. Consistent with `RULES.md` time budgets.

## Concerns — defects vs hypotheses

Established defects (follow from the cited text, no measurement needed):

**1. [Blocker] Proposed bytes/C interface is not yet sufficient for `source.rs`. §3 vs `source.rs`.**
`DataSource` is wider than identity/grants/activation/answer/parse/destroy: `configure_storage(paths)`, `continuation(token)->Box<dyn FnOnce()->Outcome+Send>`, `activate_for_validation`, `replacement()->Self`, `query`, `app_id`, `answer(&mut Store,...)`, `parse(&mut Store,...,Outcome)`, `bind(&Plan)`, `ready`, `revision`, `grants`. §3 names only a subset and punts to “reconcile with `source.rs`, not copied.” Specifically unworkable as written:
  - native closures cannot cross `dlopen`; `continuation` must become tokens + host-side work, not `Box<dyn FnOnce>`.
  - `&mut Store`, `&Plan`, `Value`, `Outcome`, `Answer` have no encoded form defined; bounded encoded args/results are asserted but not specified.
  - `replacement()->Self` cannot return a Rust `Self` by value across independently loaded cdylibs safely.
  - Remedy before implementation: write the exact encoded IDL — function list, arg/result encoding, who allocates/frees each buffer, panic-ABI (`panic=abort`, `extern "C"`, no unwind), `bind` shape projection, `Store` accessor API replacing `&mut Store`, continuation token protocol, and `revision` string scope. No code until this table exists.

**2. [Blocker] Native retirement rule admits unbounded retention without a bound. §4.**
“Unique path, never overwrite,” “changing dispatch does not make `dlclose` safe,” prohibit threads/escaping callbacks, “if OS retains mappings, measure and bound… at bound require restart.” That is honest, but there is no cap, no counter definition, no diagnostic text, and no statement of what “calls, buffers, handles, destructors, callbacks, worker refs are gone” means for Rust statics, TLS with destructors, `lazy_static`, panic runtime duplication, and symbol interposition across two copies of the same crate. Two copies of `std`/allocator-adjacent state in one process is the classic cdylib hazard.
  - Remedy: specify first-implementation prohibitions — no module-owned threads, no TLS with destructors referencing module code, no escaping function pointers beyond the C table, constructors do no work, `panic=abort` — plus a concrete retention budget e.g. N versions or M bytes, `state`/`logs` exposure, and exact restart-required diagnostic. Prove `dlclose` or document pinned-retain + restart as the shipped behavior.

**3. [Major] Native-until-edited identity is sound in principle, underspecified in practice. §5.**
Including deps/build-scripts/config/target inputs is right, but “validating the matching inputs” needs a canonical input-hash rule: rustc/cargo versions, profile flags, absolute paths, env vars, target triple. Without it, “return to embedded” and “removed providers are removed” cannot be tested deterministically.
  - Remedy: define the identity string contents and hash normalization, and what executor label (`embedded-native`/`loaded-native`/`browser-wasm`/`pulley`) is reported in `state`/`logs` after each commit.

Hypotheses to measure (do not block the direction, must gate slices):

**4. [Major] All-session prepare/commit + latest-edit-wins preserves state on paper; effect withholding needs a test. §4 + `carry.rs`.**
Invalidating all answers from a replaced module when one module initially equals the whole data crate is safe but coarse; fine for slice 1. Risk is `activate_for_validation` withholding storage caps while `parse` may write the store — validation behavior may diverge from committed behavior — and cross-host “commit at different times” interacting with superseding edits.
  - Remedy: verification list in §7 already covers refusal, invalid-carry preserves all sessions, superseding edits, pending-read cancel, no mutation replay, add/remove provider. Keep it; add an explicit validation-vs-commit parity case for a store-writing `parse`.

**5. [Major] Device Pulley path is plausible, not established. §2, §6.**
Rust→Wasm→precompiled `pulley64`, app links interpreter only, no JIT/exec ARM, is the correct reading of Pulley docs. But iOS Tier 3, precompiled-artifact loading without executable memory, Swift/Wasmtime C-API linkage, bundle size, load latency, and UI responsiveness on a real workload are all open. The 10× heuristic, 13× Fibonacci on Mac, ~100µs `board` under wasmi, and slow JS-in-Wasm numbers all correctly do not transfer — §6 says so.
  - Remedy: no doc change needed; do not let Pulley performance claims enter the loop budget until the §7 phone probe runs real data cases natively vs Pulley with answers, latency, load time, and scroll/input responsiveness.

**6. [Major] 0.5–1s save-to-visible target is not yet supported. §6.**
Warm compile alone is 398–455ms median for the query-only wrapper, before watch, pairing/bake, fetch to 4 targets, per-target native builds, validation, carry, presentation. “Under 1s p50 initial objective” plus honest p50/p95 methodology is the right target shape, but current figures exclude the full ABI, native link/`dlopen`, and phone delivery. Native targets need separate builds; sharing Wasm between web and Pulley helps only those two.
  - Remedy: keep target as objective, report per-phase timestamps from day one, report cold setup separately, and do not promise the budget in user-facing docs until 20-edit runs per surface exist.

**7. [Minor] Clarify scope trades in one line each. §8 + `DEFERRED.md`.**
§8 proposes prioritizing dev replacement over Level B delivery and per-source digest analysis, deferring GPU/surface and Android. State the take explicitly per `DEFERRED.md` “moving something off” convention, and annotate 1029 D2–D5/§7 and 1027 §8 as promised.

## Genuinely better alternative

Universal Wasm/Wasmtime for all dev replacements, including macOS/Linux, would remove `dlopen`/`dlclose`, signing/library-validation, and dual native/Wasm build paths, at the cost of abandoning the user’s explicit “retain native speed wherever practical” goal and native-execution fidelity during development. Given the user cares about a fast sleek loop *and* native speed, and native hosts start embedded-native with zero interpreter cost until edited, the RFC’s native-first choice is better aligned. Revisit only if the macOS retirement probe shows unbounded growth with no acceptable bound/restart UX.

## Recommended next step

Smallest decisive first experiment, before slice 2 code: **repeated native Caltrain library replacement loop on macOS** — 30–50 consecutive edits, each with changed answer, carried input + clock via existing carry path, superseding rapid edits, plus `dlclose` behavior, resident-memory growth, TLS/destructor check, and signing config. If retirement cannot be bounded with a clear restart rule, native-first needs rescoping; if it passes, the phone Pulley latency probe is next. Do not add a check or server; add runtime cases to existing suites as §7 states.
