1. **A1’s speculative acquisition can still block later resource work and the main thread.**

   RFC §3/M3 L230–244 says acquisition runs last, after queued uploads, captures and resource waits, “so nothing queues behind an acquisition.” That conclusion does not follow. Those operations can arrive **after** `nextDrawable` starts.

   The existing worker executes jobs serially. Uploads and command commits use that queue; synchronous calls wait for their queued job. Metal resource waits can also wait for a worker receipt. Consequently, speculative acquisition started with an empty queue can delay a subsequently requested upload, capture or synchronous resize until acquisition returns or times out. Putting acquisition last among currently queued jobs does not provide independent progress. (`host/ink/src/present.rs:33–44,52–98`; `device/metal.rs:189–234,634–652`; `device/metal/present.rs:92–109,247–250`.)

   This is the unresolved part of round 4’s lifecycle finding. Bootstrap acquisition, generations, retained damage, retries and release at rest are now specified; progress during an outstanding acquisition is still asserted rather than established.

   The live-resize exception also needs an explicit handoff sequence. Today the host encodes the compose scene before the synchronous worker call acquires a drawable and encodes its copy. Direct rendering needs the drawable texture **before host-thread scene encoding**. State the acquisition-before-encode handoff, where the main thread may synchronously wait during resize, and how it avoids an older outstanding acquisition. The ordinary path can retain worker acquisition and host encoding, but “the main thread never waits” needs that exception. *(RFC L235–244; parent D7 L476, D11 L555–560; `device/metal/present.rs:229–258,274–318`.)*

   **Smallest correction:** write an enforceable acquisition/handoff protocol covering work arriving during acquisition and synchronous resize. Either preserve independent progress or explicitly propose and qualify the blocking behavior as a D11 trade. A layer timeout alone does not establish the current promise.

2. **A2 answers round 4’s principal correctness objections.**

   The conversion from points to device pixels is explicit, placement is defined by a fresh walk at the rounded scroll offset, scaled rows record fresh, sign crossings record fresh, and settling requests an exact final redraw. Those are actual answers, not acknowledgments. *(RFC §3/M6 L272–294; §7/A2 L387–392.)*

   The code supports the premise: `Ink::reusable` currently requires whole-device-pixel origin differences; glyph x phases and y truncation are chosen before the instance transform. Restricting reuse and retaining fresh recording where equivalence fails is therefore necessary. (`host/linux/src/ink/rows.rs:287–303`; `ink/text.rs:13–51`; `host/ink/src/glyph/swash.rs:245–272`.)

   Implementation must apply the snap before glyph quantization, not merely change capture/replay origins. Eligibility must also cover glyphs under descendant transforms, rather than testing only the row root. These follow from r5’s “only where that equivalence holds” rule.

   One nonblocking arithmetic correction remains: since increasing scroll offset moves content negatively, the signed row displacement is `round(p_rec) − round(p_new)`, not the expression at L279. The fresh-walk placement definition has the correct sign, and either difference is integral. (`host/linux/src/paint.rs:196–202,1261–1268`.)
