## 1. Diagnosis

Verified against the records: 23 of 24 apps wrote an `accent-color` (11 indigo, 7 teal), one used `swipeTrailing`, none called `haptic()`, all five patterns write indigo ([patterns](/Users/ccheever/projects/exact2/docs/patterns/list-detail/app.contract:76)), and start-here teaches the accent as "the one colour you write" with a teal example ([start-here.md](/Users/ccheever/projects/exact2/docs/start-here.md:13)). The cited code checks out: grouped title `min-width: 0` ([grouped.rs](/Users/ccheever/projects/exact2/contract/lower/src/grouped.rs:1150)), intrinsic size becoming a minimum ([style.rs](/Users/ccheever/projects/exact2/kernel/src/style.rs:1461)), the agent's pinned root font size ([PageFacts.swift](/Users/ccheever/projects/exact2/host/apple/Sources/ExactKit/PageFacts.swift:33)), press-ends-editing ([PointerIOS.swift](/Users/ccheever/projects/exact2/host/apple/Sources/ExactKit/IOS/PointerIOS.swift:444)), black ink under 3:1 ([ButtonConfigurationIOS.swift](/Users/ccheever/projects/exact2/host/apple/Sources/ExactKit/IOS/ButtonConfigurationIOS.swift:177)). D1, D3's black label, D5, D6 are correctly Exact's defaults; accent everywhere and no-swipe are correctly the docs'.

Three problems:

- **Coverage arithmetic.** Records hold 143 Exact tells (the RFC says 141). §1's counts are *apps per cause* with overlaps, never tell instances, so D1–D7's claimed coverage (~55–60) can't be summed or audited. §7 needs a drop of ≥48 instances to reach <4/app; "each cause falls by half" on ~60 covered instances yields ~4.7/app. The two stop rules contradict each other.
- **The residual class is structural, not residual.** My rough census of the 143: ~24 presentation-structure tells across 15 apps (push vs modal, no composer/input-accessory bar, custom cards vs grouped list, tiles vs rows), search not in the nav bar in 3 apps, full instead of relative timestamps, fixed-size figures that don't scale in ~10 apps. These share one cause the RFC never names: where Exact has no one-line semantic name, builders paint the web version. The [list-rows recipe](/Users/ccheever/projects/exact2/docs/recipes/list-rows.md:26) itself teaches search as a header field. Parts builders used as instructed still earned tells (AnswerTile "grey slabs", trivia). This — missing names in `exact:content` and the bar — is also the token lever, since a named part deletes builder code.
- **Tells are only half the fidelity gap.** Exact apps also carry 96 graded *bugs* (~4/app) in [the records](/Users/ccheever/bakeoff/rounds/r17/records), correlating with overall score about as strongly as tells (−0.50 vs −0.54), and the 5 losses are bug-heavy. Some "tells" are unattributed possible host bugs no D claims (contacts' stale search field over the nav bar; grocery's VoiceOver "selected" on every row — a D7 doc line won't fix a host trait). Also note prompt bias: every backend prompt forces a persona switcher, inflating the segmented/rest-pattern share relative to real apps.

## 2. The §9 questions

- **Q1 split / D2 reflow — split right; do not reflow authored CSS. Confidence 85%.** Reflowing author rows breaks LLP 1115's layout layer, the web parity oracle, and D12.1, and forces an unknowable choice of what truncates. But reflow freely inside Exact-owned structures (grouped/list lowering *and content parts* — extend D1 there). D2 as written is too weak: a recipe line is lookup reading; what builders copy is patterns, and what they obey is `verify`. Put the wrap/stack remedy in the finding text and in the patterns, and run the overflow check on the web host at a large root size in ordinary `verify`, not only in end-of-run `verify ios` — otherwise AX5 fixes loop at iOS-build prices.
- **Q2 D3 fill — it is an override, not the platform's answer. Confidence 85%.** UIKit does not substitute the Increase Contrast colour when the person hasn't enabled it; that setting outranks the author only when enabled ([LLP 1115](/Users/ccheever/projects/exact2/llp/1115-write-the-web-ship-the-platform.principle.md:24) as amended). It also creates two teals in one app (filled button vs switch, segmented, links on the same accent), diverges from web/Mac, and leaves authored `light-dark()` pale accents unhandled. Do less: delete D3.10's black ink (high confidence — UIKit never draws it), keep UIKit's white, and let `check` steer at the accent site toward unsaid. And delete the "hues that keep white text" list: indigo itself was graded a tell (password-generator, team-kanban in the records); a permission list re-invites the behaviour D3 exists to stop. Unsaid, with `app.tamber` for real brands, is already the documented path.
- **Q3 D5 — Done yes (70%); focus rule needs reformulation; web/Mac safe (90%) if host-local.** Done is not UIKit's default (`.default` Return doesn't resign by itself); it's the honest label for Exact's own D9.2 resign behaviour — say that instead of claiming the platform answer. Done will lie on refocusing add-another fields; acceptable minority, `enterkeyhint` is the escape. "Every press that neither presents nor navigates" is not implementable as stated: `focusForPress` runs *before* callbacks, so the host cannot know. Reframe to UIKit's actual mechanism: a press never resigns; presentation/navigation resigns when it happens. The `step`→pad inference is the weakest item (60%): make authored `inputmode` explicitly win — it's the existing idiom ([number-field recipe](/Users/ccheever/projects/exact2/docs/recipes/number-field.md:3), dashboard's money field) — and derive only from structure, never label text.
- **Q4 tokens / noise — §7 as written cannot tell. Confidence 80%.** See §4 below. D2's pass is not the main cost risk; D4's warning is (vocab lookup plus hand-writing the ten-attribute scroll-snap swipe, in every list, per app).

## 3. Directional risks

- **D4's warning is the footgun Charlie fears**: inference from label text and symbols ("Delete", minus) will false-positive on legitimate per-row actions and builders will evade it by renaming. Sequence it last: pattern carries swipe/menu first, measure adoption in round 18, warn only if that fails. The deferred `SwipeRow`-as-structure is actually the main event — the recipe's non-compiling menu proves the current apparatus is too much to copy correctly.
- **D1's grouped wrap is shared lowering**, so it moves the web and Mac too. Probably fine (the `rem` basis makes it trigger mainly at iOS AX sizes; desktop web is wide), but the RFC should state that reasoning as its T3 evidence and test a Mac grouped form.
- **D2 findings will invite the next uncanny guess** — builders shrinking or fixing font sizes to clear overflow (already a tell class: fixed 44 pt totals) — unless each finding names its remedy, as Exact's other diagnostics do.
- Deleting D3.10 and reopening D9.3 correctly follow "delete, don't deprecate" — but start-here's "`check` refuses it" sentence ([start-here.md](/Users/ccheever/projects/exact2/docs/start-here.md:17)) must change in the same commits or the docs contradict the host.

## 4. §7 measurement

- Pin the baseline: the RFC's 9-2-1 vs SwiftUI and 141 tells match the pre-regrade snapshot; current records say 10-2-0 and 143 ([regrade-orig](/Users/ccheever/bakeoff/rounds/r17/regrade-orig) shows why). That regrade also gives the noise floor: tell counts moved +0/+1 per arm, one `better` flipped — so per-cause baselines of 4–8 instances halving is inside grader noise before builder variance (n=12/stack, tell SD ≈1.4/app).
- Split the measurement by mechanism. **Replay gate first**: rebuild the same 24 Exact apps on new main with no builder; D1, D3-label, D5, D6-row tells must vanish at zero tokens. That is a causal, deterministic test of defaults — and what "author > platform" promises existing apps. Round 18 then measures only docs adoption, with source-countable metrics (accent written? `swipeTrailing` present?) alongside grader prose, since new-main + new-builder confounds attribution.
- Pin the token definition before using it as a guard: from the records I cannot reproduce the RFC's ratios (vs UIKit: 0.60× on fresh-token aggregate, 0.93× on total; vs SwiftUI 1.28×/1.29×; the GPT-vs-UIKit 1.28× footnote matches neither). ±15% on an aggregate with per-pair wall ratios from 0.11× to 1.59× is not a detectable band; use paired per-prompt medians with the timeout/outlier rule stated. Add bugs/app and feature pass to the stop rule.
