The 4 MiB door limit (`llp/1133.006-clipboard-items.rfc.md` D8) is real and is why bytes stay out of a module request; a path-based package would not hit it, so the codec and the caller are the reasons that decide.

A single `purpose` word is one omission away from either failure. Reporting `colorSpace`, `hdr`, and `metadata` on the result makes a host that cannot keep something visible.

### 2. Android's read model hides media the platform already lets the app read

D5 (lines 307–309) maps "neither `READ_MEDIA_IMAGES` nor `READ_EXTERNAL_STORAGE`" to `access: "none"` and a `state` taken from the host's ask history. `photoAssets` and `copyPhotoAsset` ask whenever that state is `prompt` (D1, lines 156–157). A denied state fails the read (D7).

D6 (lines 326–336) states the platform fact those rows erase: Android lets an app read the media it created with no read permission, and `addToPhotoLibrary` returns an id "the app may then read" on Android even when the only grant is add. Add on API 29+ asks nothing (D4, line 265), so `addState` stays `granted` while `state` is still `prompt` or `denied`. The read calls then prompt for `READ_MEDIA_IMAGES`, or fail if the person has denied it.

That prompt is the permission Google Play restricts and tells apps not to request when the photo picker or their own inserts would do. An app that only saves — question 5's add half — is told it received a readable id and then cannot list or reopen that photo without a broad read prompt. Drives 1–3 never read the saved id back, so they pass either way.

**Resolve:** on Android, rows the app owns are readable while `addState` is `granted`, with no prompt. `photoAssets` includes them when `access` is `none`. `copyPhotoAsset` and a picture of an owned id proceed. Any other id asks for `device.photos` or fails `NotFoundError`. `state` and `access` describe the rest of the library only.

### 4. The Android edit path cannot keep a gain map, and its crop runs after the scale

D15 (lines 686–704) makes "keep HDR" the unsaid default of `transformImage`, and the ceiling (line 755) assigns that to tier 1. D16's Apple path can do it: decode with `kCGImageSourceDecodeToHDR`, draw, encode with `kCGImageDestinationEncodeToISOGainmap`. The Android path (lines 721–728) decodes with `ImageDecoder`, draws through a `Canvas` and a `Matrix`, and `Bitmap.compress`es.

A gain map is a separate object, `Bitmap.getGainmap()` / `setGainmap()` (API 34), which the RFC already cites. `Canvas.drawBitmap` paints the base bitmap. The bitmap it produces has no gain map unless the codec transforms that gain map and calls `setGainmap`. A quarter turn, which drive 1 requires, therefore writes SDR on every API level. "Stage 3 records what survives below Android 15" describes a platform limit. The cited pipeline drops the map on Android 15 as well.

The same paragraph uses `ImageDecoder.setTargetSize` and `setCrop`. The method the RFC quotes crops "a subset of the (possibly) scaled image", so scale happens before crop. D14's order is crop, then resize. An implementation that follows the cited calls crops the wrong pixels whenever both are set.

**Resolve:** give Android the same shape as Apple: one oriented decode, then rotate, flip, crop, and resize in D14's order, then attach a gain map transformed by that same matrix when the API level has one. Where the host cannot, the result's `hdr` and `colorSpace` say so, as the web's result already must, and the ceiling lists Android HDR as later until a drive shows a quarter turn of a gain-map JPEG still classifies as HDR.
