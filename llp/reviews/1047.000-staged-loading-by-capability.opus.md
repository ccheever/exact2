## Review (verbatim)

**Verdict:** RIGHT WITH CHANGES

**Overall assessment**

The order is right: unlink what an app never uses, then stage by capability, then decide the core. The two mechanism choices are also right: split at designed seams rather than by a recorded profile, and share one memory rather than run separate instances. The document is honest that almost all of the −15–18% comes from step 1, and that nothing here reaches React's ~110 KB.

Two things must change before step 2 is built:
- **The split's membership** has to come from the call graph, with a check that fails the build. The name-based attribution map is not safe to split by.
- **The document must say what a staged capability does before it arrives.** As written, a mistake either kills the runtime in a reader's browser or silently renders wrong.

Step 5 needs a bar to decide against, and it is missing options.

**Strengths**

- **§1 frames the problem correctly.** Served pages made the wasm a time-to-runtime problem, not a paint problem. The 5 ms/KB rule matches 1047 §10's measurements.
- **§5 measures the split, overhead included,** instead of asserting it. That gives the right rule: unlink what's never used, stage what some pages need, never stage anything tiny.
- **Capability over profile (§5).** Cross-module calls then happen only at a few designed seams, not at every branch the profile missed. Linking by use already built those seams (`Linked`, `HostLinks`, `RunnerLinks`).
- **Shared memory over separate instances.** A separate instance carries its own std, as the Markdown editor and text flow do today, and inspection has to read the runner's memory.
- **Inspection as a stage (§6.2)** keeps the smoked bytes the shipped bytes. That resolves 1047 §9 Q3's trade instead of picking a side.
- **§4 sizes what it declines,** and each is small. "The runner once per data type: zero here" closes off a dead end.

**Concerns**

1. **HIGH, and the biggest risk: the manifest is an attribution heuristic, not a safe partition.** `scripts/metrics.mjs:737–775` files each function under the first exact2 module in its demangled name. Two cases already break that:
   - When identical functions are merged, the surviving name is arbitrary. 1047 §10 found Markdown's `|p| !p.is_empty()` closure standing in for core's `SplitWhitespace` filter. This manifest would move it into the Markdown stage, where core code calls it.
   - The map files `Collection::create` (`runner/src/instance/collection/mod.rs:139`) under lists, but it runs for every realized node (`instance.rs:614`). Unless it was inlined, §5's split traps on RealWorld's first render.

   §5's table is a byte partition; nothing says the split artifact booted. To resolve it:
   - Define a stage as the code its seam entry reaches, minus the code core reaches.
   - Fail the build if the core references a stage function anywhere but its seam.
   - Simplest: the stage's own export fills its seam when it arrives, so the core holds no stage address at all.

   "Loud" then means a build error, not a trap in production.

2. **HIGH: "not ready" is undefined, and a mistake is not loud.**
   - A trap mid-commit leaves the runner inconsistent, so that page's runtime is dead. It happens on paths the smoke didn't reach, the same coverage dependence §5 holds against the profile split.
   - If the gate is the existing seam (`None` until registered), `host/web/src/element.rs:164–171` silently paints the Markdown source as plain text.

   Make "used and linked, but not yet arrived" an explicit state. Neither first candidate needs a gate in the runner:
   - Markdown's adapter is a pure text-to-pieces function called when a batch is emitted. A batch emitted early can carry the source and be held in order until the stage fills it, as D5's JS pieces already queue.
   - Inspection's only caller is the glue.

   The smoke should delay every stage, so the not-ready path runs every time.

3. **MEDIUM: version skew.** A split module is bound to its core's build: it imports by generated names and its table slots are positional. Suppose a reader loads the core, a deploy lands, and the reader then opens an article: they get the new `markdown.wasm`. At best that's a LinkError; at worst the table slots are mis-wired. Fix it with:
   - stage URLs that carry a content hash, named by the core;
   - a build-id check before instantiating;
   - on a mismatch, a full navigation to the served URL, which is cheap here.

4. **MEDIUM: staging saves little where first visits land.**
   - On pages without Markdown it saves about 15 KB net: ~75 ms on the bench, ~10 ms on an ordinary link.
   - On an article, where a Medium clone's first visits probably land, it saves roughly nothing.
   - The build, delivery and smoke work exceeds §7's "a day or two."

   That's acceptable if staging is infrastructure: inspection, §8 Q1, a later core split. It argues for a small pilot, though. Start with inspection: the glue is its only caller, and it needs no render-server work.

5. **MEDIUM: "repeat visits have it cached" holds only until a deploy.** The plan and `app.js` are embedded in `app.wasm` (1047 §1), so every deploy re-downloads 250 KB for every returning reader. Returning readers are the signed-in ones whose ♥ needs the runtime. So for §1's own example press, a reader returning after a deploy is likely the more common cold start. Two levers may beat staging there:
   - keep the plan out of the wasm's cache identity;
   - send the new `app.wasm` compressed against the previous one as a dictionary (round 8 built dictionaries for pages).

6. **LOW: the bench will confound preloads.**
   - Its server speaks only HTTP/1.1 and already uses all six connections (1048.000, 2026-09-25).
   - Its throttling ignores fetch priority.

   Measure behind HTTP/2, include article pages, and add a faster network profile. On a faster link, boot and lazy compilation (~80 of `exact_boot`'s ~143 ms) outweigh bytes.

**Suggestions**

- **§8 Q3 may not need answering.** The render server goes through the same seams, so it can record which ones a render touched: that's exact for the first page's preloads. After activation, prefetch the app's other stages when idle, and let the hold path cover the race.
- **§8 Q1 is probably where the loader pays most.** The editor (45 KB) and text flow (38 KB) each carry their own std.
- **For first-visit bytes, as opposed to time,** activating on interaction beats staging on pages people only read.
- **Deciding the core (your Q4):**
  - **It needs a bar.** 1047 §10 put parity for a runtime press at load at ~129–133 KB. Neither option gets there alone: the profile split is ~150–160 KB, and the smaller core is unsized.
  - **Missing: finer linking by use inside the core.** The plan's vocabulary would select stdlib functions, style-row codecs, value operations and validators. That is deterministic with no fallback, which is 1047's own thesis. Size it first: of the ~1,571 functions the profile never ran, how many does RealWorld's vocabulary exclude?
  - **Missing: the returning-reader levers** from concern 5.
  - **Missing: the CPU side** (boot and lazy compilation), which dominates on ordinary networks.
  - **JSPI** would remove the profile split's synchronous-fallback objection where it ships. Revisit it once every engine the web host serves has it.

**Recommended next step**

Land step 1. Meanwhile, read the 121d629e split and list every reference from the core to a stage function other than a seam entry; expect the merged closure and `Collection::create`. Then pilot inspection with call-graph membership, the build check and a smoke that delays stages, and bench it. Build Markdown's hold path and preloads after that.
