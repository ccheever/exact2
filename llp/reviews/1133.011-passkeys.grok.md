Publishing the id through data code, or returning it from `store.unlock`, would let the D11 recipe (`:626-631`) pass it to `signalUnknownCredential` and delete the lock. A memory denylist of ids does not sync either, which is why the marker replaced one.

   **Resolution.** Add an entry operation, called only by the presence backend, that asserts with an empty `allowCredentials` and, when the chosen `userHandle` carries the marker, returns the credential id and the PRF output to that backend alone. Persist the id only in the presence backend, below the data seam, and never in the unlocked value, a ticket, a journal body, or a module answer. The second device shares the lock by the person picking the synced passkey once through that operation. Keep data-code `get` as the refusal item 3 already specifies.

3. **MINOR. IN-DELTA.** Item 3's proof fails open when `userHandle` is absent. It says data code can learn a credential id only from an assertion this module delivered (`:784-787`). A `get` with an empty `allowCredentials` whose assertion omits `userHandle` is delivered, and the new D11 recipe then signals that id unknown (`:626-631`). A conforming authenticator returns the user entity when the allow list is empty (CTAP `authenticatorGetAssertion`; confidence about 85%), so this is the non-conforming case.

   **Resolution.** On a `get` with an empty `allowCredentials`, withhold the assertion when `userHandle` is missing as well as when it carries the marker.
