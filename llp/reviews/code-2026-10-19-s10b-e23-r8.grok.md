## Should-fix

**A. `app.json` is still a blocking read on the request path.** `scripts/tamber-server.mjs:125`, called from `importHeld` at `:1106` (before `planAlone`), `hold` at `:902`, and `remark` at `:995`. `readFileSync` plus `JSON.parse`, with no size cap and no regular-file check. A FIFO there blocks the read (verified: `readFileSync` on a fifo does not return inside 2 s; `realpath` and a non-blocking open return immediately). That freezes the event loop, so an in-flight child's 10 s timer and RSS interval do not run. On macOS there is no `RLIMIT_AS`. A remote client cannot plant the fifo; a local replacement of `app.json` can, and any request that resolves the design (`hello`, `import`) triggers the read while another import's child is alive. A multi-gigabyte manifest is the same stall plus memory in the parent.

Fix: accept only a regular file of a few KiB. Open it `O_NONBLOCK` and read it with a deadline, asynchronously. Do not `readFileSync` it on the request path.

**B. The Linux address-space backstop never installs, and the planner never starts.** `scripts/tamber-isolate.mjs:32–33`:

```sh
ulimit -H -v ${kb} && ulimit -S -v ${kb} && exec "$0" "$@"
```

Setting the hard limit while the soft limit is unlimited makes `setrlimit` fail (`EINVAL`: the new hard limit is below the current soft limit), and `&&` skips `exec`. The shell exits with empty stdout, `JSON.parse` fails, and every Linux import is 413 "planner stopped". The limit the lead asked for is not in effect. Verified on this host's `sh` with the analogous limit: `ulimit -H -n 32` fails while the soft nofile limit is unlimited; `ulimit -S -n 32 && ulimit -H -n 32` and a single `ulimit -n 32` succeed. `-v` itself was not executed (this machine is Darwin).

Fix: `ulimit -S -v ${kb} && ulimit -H -v ${kb}`, or one `ulimit -v ${kb}` that sets both, then `exec`.

**C. A probe that loses the race with exit still 503s a finished plan and can signal a reused pid.** `scripts/tamber-isolate.mjs:101` sets `gone` only in the `exit` handler. The sample at `:124–128` ignores a null probe only when `gone` is already true. `5f5c21fa6d` fixed the case where `exit` has already been delivered. If `ps` returns ESRCH (null; the probe timeout is 1 s) and that callback runs before `exit`, `stop` (`:109–115`) answers 503 and `process.kill(-pid, 'SIGKILL')` even though stdout is a plan `close` would have parsed. After the pid has exited, that signal can hit a reused pid.

Fix: treat ESRCH as gone and let `close` win. Call `stop` only when the null result is a timeout or a non-ESRCH error while the pid is alive. Do not signal a pid `ps` cannot see.

**D. The planner is detached and outlives the wire.** `contract()` uses `detached: true` (`scripts/tamber-isolate.mjs:28` and `:33`). `close()` at `scripts/tamber-server.mjs:1118` signals the serve child only. Nothing on `process` `exit` kills the import group. A detached child survives `process.exit` and a dev reload. Parent death removes the watchdog; on macOS the orphan is uncapped and can keep allocating the client's source. A remote client cannot exit the parent by itself. A restart during an import does.

Fix: remember the active child pid. In `close()` and in a synchronous `process.on('exit')` handler, `process.kill(-pid, 'SIGKILL')`. On Linux, set `PR_SET_PDEATHSIG` to `SIGKILL` before `exec` so a parent crash is covered too. The exit handler does not run if the parent is killed with `SIGKILL`.

**E. One slow `ps` is a blind window past about 1 GiB.** `scripts/tamber-isolate.mjs:37–38` and `:121–131`. `probing` drops interval ticks while one `ps` is in flight, and that `ps` may run until its 1000 ms timeout. A fast allocator can pass 1 GiB by a long way before the late sample, or before the timeout's null result, kills it. RSS excludes swap. There is no headroom under the 1 GiB line. The lead accepted a poll because macOS ignores `RLIMIT_AS`, and the cargo grandchild is gone, so this is the residual of that poll. The first sample can also 503 when `ps` cannot see the new pid yet, which fails closed and can flake.

Fix: probe timeout 100–200 ms. Kill around 768 MiB so one late sample still lands near 1 GiB. If a probe has been in flight past one interval, `SIGKILL` without waiting out the `ps` timeout.

**F. The design-read deadline does not bound the permit.** `scripts/tamber-isolate.mjs:59–62` clears the queue timer before `designText`. The 2 s race covers only `file.read` (`:84`); `realpath` and `open` sit outside it, the timer is never cleared, and `finally` awaits `file.close()` (`:88`). On this machine a fifo never reaches `read` (finding A is the fifo that still blocks). A stuck regular-file read (NFS) or a `close` queued behind it holds the only planner slot with no client deadline, and the 10 s watchdog has not started. New arrivals past the queue depth get an immediate 503. Waiters are answered at 30 s only while the event loop runs.

Fix: arm the deadline around the whole read, and on timeout close the numeric fd so the read returns. Do not await a close that is queued behind the read. Leave the queue timer armed until the child has been spawned, or answer 503 and release the slot. A single `read()` that returns less than the file can be treated as the whole design; loop to EOF or compare `st.size`. The uncleared 2 s timer is a leak of one timer per such read.
