1. **MATERIAL** — **D8: Android’s capability probe can cause the failure it is meant to prevent.** The proposed 500 ms experiment starts recognition before establishing that the service accepts supplied audio. An unsupported service opens its microphone, potentially silencing the recorder already using `AudioRecord`. A slow pipe reader also does not prove unsupported input. Worse, a tool-admitted `path=` request could open the room’s microphone despite D10’s promise that file transcription opens no device. I would treat support as unknown until established without competing capture, and refuse supplied-audio operations on unqualified services. This follows Android’s documented [EXTRA_AUDIO_SOURCE fallback](https://developer.android.com/reference/android/speech/RecognizerIntent#EXTRA_AUDIO_SOURCE) and [input-sharing policy](https://developer.android.com/media/platform/sharing-audio-input). See [D8](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:493).

2. **MATERIAL** — **D7/D8/D12: handover is not an implementation of consuming the named track.** Bare browser `start()` and an Android recognizer opening its microphone do not inherit the track’s selected `deviceId` or processing. Recognition can therefore silently switch physical microphones. Moreover, “sole consumer” is checked per track, while takeover stops the process-wide device capture and expressly mutes other sessions. Session A can interrupt session B’s recording, contradicting recording D3’s isolation guarantee.

   I would distinguish **consume these samples** from **acquire exclusive recognizer microphone access** at the architecture level. The latter must check every lease on the device and must disclose—or refuse an inability to preserve—the selected input. Keep track consumption for the platforms that actually support it. See [speech D8](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:470), [recording D3](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.009-recording.rfc.md:317), and the [Web Speech API’s distinct start forms](https://webaudio.github.io/web-speech-api/).

3. **MATERIAL** — **D8/§9/§10: inability to share capture does not imply ability to transcribe a file afterward.** Safari’s missing supplied-track support also prevents the proposed browser file-to-track route. Android services ignoring `EXTRA_AUDIO_SOURCE` cannot transcribe supplied files either; older Android targets lack that input altogether. Nevertheless, the recorder promises file transcription precisely where `sharesCapture=false`, and substitute drive 3 always succeeds.

   I would expose file-input support independently, disable Transcribe where unavailable, and make the substitute preserve those restrictions. A file request must never substitute microphone recognition. See [the consumer’s fallback](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:918) and [RecognizerIntent](https://developer.android.com/reference/android/speech/RecognizerIntent#EXTRA_AUDIO_SOURCE).

4. **MATERIAL** — **D11/D12: Android file transcription has no coherent runtime-permission path.** The RFC requires `RECORD_AUDIO` even for files, but reports speech permission as always granted, associates the microphone grant only with `track` in the declaration, and says a file asks the speech decision alone. A build-time grant does not obtain runtime permission. On that stated contract, fresh-install file transcription fails, and tool admission cannot determine whether fulfilling it would prompt.

   I would declare operation-specific permission dependencies and reuse the microphone permission authority for Android file input wherever required. If a supported injected-audio implementation is exempt, document and model that exemption instead of imposing an unconditional requirement. See [D11](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:593), [SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer), and [runtime permissions](https://developer.android.com/training/permissions/requesting).

5. **MATERIAL** — **D4: Apple’s `transient-solo` mapping contradicts its promised exclusivity.** `.interruptSpokenAudioAndMixWithOthers` also enables mixing. Without `.duckOthers`, ordinary music continues at full volume; only another spoken-audio session is interrupted. The installed Apple SDK header confirms this explicitly.

   I would map `transient-solo` to nonmixable `.playback`/`.voicePrompt`, without mixing options. The proposed combination belongs to a different policy than “pause/mute all other audio.” See [D4’s table](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:254) and [Apple’s option documentation](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/interruptspokenaudioandmixwithothers).

6. **MATERIAL** — **D4: the claim ordering can weaken an existing playback claim.** Even transient speech outranks the app’s `audio_session` policy for existing output. Thus an app playing nonmixable media under `audio_session: playback` can become mixable when it speaks a transient prompt, although the media’s playback requirement remains.

   I would normalize sounds, players and speech into the same output-policy claims and compose all active claims consistently. Frozen capture configuration is a separate constraint; Android audio focus is output arbitration, not microphone ownership. One process owner remains appropriate, but one ordering that places every speech claim above existing playback is defective. See [composition](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:269) and the existing [session reconciliation](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/host/apple/Sources/ExactKit/AudioSession.swift:79).

7. **MATERIAL** — **D2/D4/D6: Android’s selected synthesis API cannot implement the promised pause/resume semantics.** `TextToSpeech` has no pause or resume operation. `stop()` interrupts the current utterance and discards the queue. Restarting from optional “about to speak” range callbacks cannot preserve playback position reliably; it can repeat or skip words.

   I would choose a rendered-audio path with pausable playback on Android. Retaining direct `speak()` requires an explicit weaker resume contract, such as replaying the current utterance. This changes the public behavior or playback architecture and must be decided before stage 4. See [the portable operations](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:167) and [Android TextToSpeech](https://developer.android.com/reference/android/speech/tts/TextToSpeech).

8. **MATERIAL** — **D7/D9: complete transcripts have no bounded delivery or reclamation mechanism.** Continuous recognition is unbounded, yet stopping—or reading ended state—returns every result plus the complete text. Native replies are capped at 1 MiB in both the [generated TypeScript binding](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/js/bake/src/typescript.mjs:1104) and [Rust native requests](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/runner/src/request.rs:189). A sufficiently large transcript cannot deliver its promised result. Keeping every ended recognition until session end also accumulates transcripts across takes.

   I would retain the live window, but provide bounded pagination or an admitted transcript file, plus explicit release of completed handles. Raising the reply limit does not solve the unbounded contract. See [D7’s values](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:408).

9. **MATERIAL** — **D2/D6/§10: provisional-handle cleanup does not establish the claimed speech cancellation guarantees.** Once native speech is queued, disposing a subsequently dropped reply cannot retract words already heard. The inherited seam supplies `dispose(ids)`, not activation after accepted delivery.

   Separately, Markdown’s `listen()` awaits each inner `speak()` before returning its outer mutation answer. Those inner handles have already been delivered, and D6 explicitly makes them outlive that mutation. Superseding `listen()` therefore does not cancel the first paragraph queue as the drive claims.

   I would keep the inherited cleanup guarantee, remove the stronger “never speaks” assertion, and give Listen explicit replace/cancel semantics. If never-audible-before-delivery is required, add a delivery-triggered activation mechanism. See [D2](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:199), [the consumer](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:967), and [inherited handle disposal](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.009-recording.rfc.md:856).

10. **MATERIAL** — **D2: twenty outcomes are not sticky terminal results.** Canceling a long queue, flushing it, or encountering immediate failures can terminate more than twenty utterances before any reader runs. Reading “often enough” cannot prevent that loss. Disappearance from `queue` establishes termination but cannot recover `end` versus `error` or the error code.

    I would provide terminal state addressable by utterance handle, with explicit release, or an acknowledged bounded result protocol. Boundary highlighting can remain a coalesced value. See [the retention guarantee](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:203) and [the parent’s event rule](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133-the-standard-library.rfc.md:376).

11. **IMPLEMENTATION-PHASE** — **D7/D10: implement the stated recognition lifetime, beyond start admission.** `"foreground": true` only checks starting; inherited capture can continue after hiding. Implement §12’s exclusion by finalizing recognition on foreground loss and requiring a fresh admitted start. Likewise, a file recognition must retain its admitted read for the recognition’s lifetime, rather than borrowing the initiating mutation’s lifetime. Recording already introduces handle-scoped file checkout. These follow the intended policy and do not independently require redesign. See [D10](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:546) and [recording’s file ownership](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.009-recording.rfc.md:813).

12. **IMPLEMENTATION-PHASE** — **D11/§13: authorization must follow the selected Apple engine.** SpeechAnalyzer’s on-device transcribers should not be gated by legacy `SFSpeechRecognizer` authorization; legacy recognition still requires that authorization even when configured on-device. The RFC already schedules resolving this before the Apple stage lands, so it is not another material blocker. I would test both “legacy authorization denied, Analyzer succeeds” and an explicit legacy-engine selection requiring its decision, and align the substitute accordingly. See [D11’s contingency](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:619) and [Apple’s permission guidance](https://developer.apple.com/documentation/speech/asking-permission-to-use-speech-recognition).

Also exercise prompt completion while sound/player claims remain: Apple documents deactivation as necessary to release ducking and spoken-audio interruption, while the existing owner retains holders and players. These are implementation measurements, not reasons alone to reject the one-owner architecture. See [D17](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/llp/1133.012-speech.rfc.md:851), [owner deactivation](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/speech/capsule-r1/host/apple/Sources/ExactKit/AudioSession.swift:87), and [Apple’s ducking documentation](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/duckothers).

1. **IN-DELTA — MATERIAL — D4/D6: cached engine ownership freezes speech policy indefinitely.**  
   [D4](llp/1133.012-speech.rfc.md#d4--spoken-audio-is-a-claim-on-the-hosts-audio-session) accepts speech under whatever configuration an existing engine holds. This is not limited to overlapping sounds: `SoundModule.swift:219` takes its session hold when the engine opens and releases it on shutdown or failure, not when a sound finishes. An ambient app that plays one click can therefore keep later explicit `playback` speech under `.ambient`, where the Silent switch can mute it. Conversely, opening that engine during a transient prompt can prevent deactivation indefinitely, keeping other apps ducked after the prompt finishes.

   The new fixed queue type also makes playback appended after a transient prompt remain transient, including cancellation on backgrounding. These are accepted requests whose written policy silently loses.

   **Decision instead:** distinguish active audio requirements from cached engine ownership. Quiesce idle engines and perform controlled configuration transitions; reject incompatible claims when necessary instead of silently substituting ambient or transient behavior.

2. **IN-DELTA — MATERIAL — D8/D11/D12: parameterless status cannot describe the requested recognizer.**  
   `speechRecognitionStatus()` takes no selection arguments, yet D11 makes its state depend on `apple.engine`, and D8 makes `inputs` depend on the Android service. On Android, `processLocally=true` selects a different recognizer from the default service whose capabilities the consumer reads. On Apple 26, the default Analyzer status is `granted`, while explicit `sfSpeechRecognizer` may require authorization. D12 still declares one permission source without mapping the operation’s selection into it.

   Consequently, capability checks can describe the wrong service, and admission cannot reliably establish whether the actual engine would prompt—a requirement of LLP 1133.002 D14.

   **Decision instead:** resolve engine, service, input, language and locality before admission. Query capabilities and permission dependencies for that same selection, through parameterized status or separate engine facts, and carry the resolved selection into execution.

3. **IN-DELTA — MATERIAL — D7/D13/§10: the transcript file moves the delivery limit rather than removing it.**  
   D13 directs data code to read the unbounded JSONL transcript through `storage.fs`; the recorder reads its first line that way. But the public filesystem exposes only whole-file `readFile(path)`, without ranges or streaming (`vendor/ibex/crates/ibex2/src/bindings/storage.d.ts:14`). Native storage rejects files above approximately 12 MiB because the base64 result must fit its 16 MiB envelope (`vendor/ibex/crates/ibex2/src/stdlib/fs.rs:28–31, 78–79, 104–108`).

   A valid long transcript therefore eventually becomes unreadable through the prescribed interface—even retrieving its first line fails. This is the remaining part of round-1 finding 8.

   **Decision instead:** retain the durable file, but provide bounded range/line reads, transcript pagination, or bounded chunks with an index. Raising the cap would only move the failure again.

4. **PRE-EXISTING — MATERIAL — D9/§10: file transcription can stop at the first finalized segment.**  
   D9 says omitted `continuous=false` ends Apple recognition at the first final result. The recorder’s file Transcribe operation does not override it. `SpeechAnalyzer` produces finalized audio ranges through an asynchronous result sequence; a finalized range is not file EOF. The installed Speech SDK exposes those ranges separately from its end-of-input finalization operations.

   Applying the stated mapping to a multi-utterance take can therefore produce only its first segment, despite presenting the operation as transcription of the take.

   **Decision instead:** define `path=` recognition to consume and finalize through EOF independently of the live-input `continuous` setting, or explicitly require continuous file recognition and specify EOF completion.

1. **IN-DELTA — MATERIAL — D4: a muted player is running I/O, not an idle engine.**

   The new composition rule protects only players “playing with sound” and permits deactivation when nothing is audible. A muted video can therefore keep playing through a prompt and then lose its session when the prompt finishes.

   Existing [AudioSession.swift:20](host/apple/Sources/ExactKit/AudioSession.swift#L20) deliberately protects muted players because deactivation stops a running player. The installed Apple SDK’s `AVAudioSession.h:255–262` likewise requires stopping or pausing running I/O before deactivation. Removing that protection contradicts the revision’s promise that speech never cuts a player.

   **Decision:** distinguish audible policy requirements from running I/O. Stop idle sound engines, but retain the running-player guard or explicitly quiesce and restore players before session transitions.

2. **IN-DELTA — MATERIAL — D7/D12: 500 results is not a byte bound.**

   D7 guarantees readable chunks by asserting that results with alternatives occupy a few hundred bytes. Neither transcript length nor `maxAlternatives` has a declared maximum. For example, 500 results containing 20 alternatives of 1,300 UTF-8 bytes already exceed native storage’s approximately 12 MiB read ceiling, before JSON overhead. Count-bounded state windows can similarly exceed the 1 MiB module-reply ceiling.

   This leaves the persistent retrieval finding unresolved under the replacement design; measuring a typical payload does not establish its bound.

   **Decision:** rotate files by serialized byte size and define fragmentation for an oversized individual result. Bound state replies by bytes too, retaining full text and alternatives in retrievable fragments.

3. **PRE-EXISTING — MATERIAL — D4: pausing a transient queue can leave other apps ducked indefinitely.**

   The claim remains held from the first utterance until the queue empties or is canceled. `pauseSpeech()` does neither. Under that lifetime and the stated deactivation rule, pausing a transient prompt leaves `.duckOthers` and spoken-audio interruption active while no speech plays. D4 itself correctly states that these effects end only at deactivation.

   **Decision:** suspend the paused queue’s output claim while preserving its utterances, release the session when other running I/O permits, and reacquire the claim on resume.

4. **PRE-EXISTING — MATERIAL — D6: separate Android TTS clients do not provide simultaneous speech.**

   D6 promises that two sessions speaking simultaneously are heard together. Android’s selected direct `TextToSpeech.speak()` architecture cannot guarantee this: the installed framework source gives each `TextToSpeechService` one `AudioPlaybackHandler`, whose single playback thread runs queued items serially. Separate clients using the same engine share that playback queue.

   **Decision:** declare Android’s serialized playback and arbitrate the session queues accordingly. If overlapping speech is required, choose rendered audio with independent playback streams.
