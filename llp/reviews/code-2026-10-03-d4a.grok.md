## BLOCKER — A `?:` under a wanted choice can be a non-string

`contract/types/src/choices.rs:83-99`. When the wanted type is a choice, `given` re-infers only text arms, then:

```rust
Ok(if want.accepts(&a) && want.accepts(&b) {
    want.clone()
} else {
    a.join(&b).unwrap_or(a)
})
```

`join` of a choice and a number is `None` (`choices.rs:47-53`, `lib.rs:105-121`). `unwrap_or(a)` then returns the choice whenever the choice is the first arm. Callers treat that as success (`want.accepts`): function results (`contract/types/src/lib.rs:1137-1148`), slot and mutation writes (`contract/types/src/actions.rs:146-171`), record fields (`contract/types/src/records.rs:82-91`), props (`contract/types/src/uses.rs:214`), and call arguments (`contract/types/src/lib.rs:782-793`, `contract/types/src/component.rs:459`). `some(cond ? "a" : 1)` takes the same path when the inner type `has_choice` (`choices.rs:101-103`).

```contract
fn f(cond: bool): "a" | "b"
    cond ? "a" : 1
```

This typechecks. `cond ? 1 : "a"` is refused, because `unwrap_or` then yields `number`. The same hole is `Shape(kind=cond ? "a" : 1)` and `mode = cond ? "a" : 1` once `mode` is already that choice.

At runtime the false arm is the number `1`. A later slot write is refused by `conforms` on both executors. A use that compares it is not. The parser has already lowered `match` to `subject == "a" or …` (`contract/lower/src/expr.rs:427-441`). The Rust VM’s `==` traps when the kinds differ (`runner/src/vm.rs:704-708`, `runner/src/compare.rs:177-201`). The JavaScript target emits `===` (`host/web-js/src/code.rs:343-348`), `1 === "a"` is false, and a multi-arm match takes its last arm (`contract/syntax/src/parser/choice.rs:190-202`).

Suggested fix: return the wanted choice only when both arms `accepts` it. Otherwise return the arm that failed, so the caller’s existing `type-fn-return` / `type-assign` / `type-argument` fires. `a.join(&b).unwrap_or(a)` is the wrong fallback.

## BLOCKER — A JavaScript dev-reload slot keeps a string outside the choice

A choice is a `string` row whose fields name the literals (`plan/src/builder.rs:203-235`), and `Value::conforms` checks them (`plan/src/value.rs:245-251`). The Rust runner drops a carried slot that fails that check and re-runs the initializer (`runner/src/runner/router.rs:579-589`).

The JavaScript dev checkpoint does not. `type_json` writes every string, choice or otherwise, as `"s"` (`host/web-js/src/types.rs:32-37`). Slot emission stores that as the declared shape (`host/web-js/src/emit.rs:366-372`). `shape` is JSON equality (`host/web-js/checkpoint.js:33`, `44-47`), so changing `"a" | "b"` to `"a" | "c"` still matches. `devSignal` then installs the kept `"b"`. `sig` records the type code and does not check the initial (`host/web-js/rt.js:88`). Reads do not recheck. The slot is live; a `match` takes the last arm, because the value equals none of the new literals.

The runtime type code `(a|b)` (`host/web-js/src/types.rs:73-79`, `host/web-js/shape.js:14`) is what writes and fresh answers are checked against. The carry identity never sees it.

Suggested fix: put the literals in the carry identity (the type code, or a `type_json` like `["s",["a","b"]]`), and drop a carried initial that fails `conforms`, as `init_slots` does.

The same erased identity affects resources, with a different outcome. `devResource` (`host/web-js/checkpoint.js:51-54`) and the document checkpoint (`host/web-js/rt.js:1261-1267`, installed at `rt.js:367-370`) can hand a non-member to a choice-typed resource. The memo then `conforms` and throws (`rt.js:92-94`, `380-383`). Rust `seed_checkpoint` skips that answer and asks again (`runner/src/runner/checkpoint.rs:151-160`). One executor poisons the commit; the other re-asks. Fold that into the same identity fix, and drop there too.

## MATERIAL — An authored `match` on a string literal skips exhaustiveness

`contract/types/src/choices.rs:151-179`. `case` returns `bool` for any subject that infers as `string` and is a string literal, a `?:` of those, or an option-`match` of those. Membership and exhaustiveness are not checked.

That skip is what keeps a component `match kind` valid after inlining substitutes a checked literal. Children are checked on their own before expansion (`contract/types/src/lib.rs:1211-1227`), so a real choice prop is exhausted first. The same predicate also accepts source that was written as a literal:

```contract
match "nope"
    case "a"
        text "A"
    case "b"
        text "B"
```

This typechecks. `"nope"` equals neither arm, so the view shows `B`. A one-arm expression lowers to `test ? body : body` (`contract/syntax/src/parser/choice.rs:194-196`), so `match "nope" { case "a" => "A" }` is always `"A"`. The reject fixture at `contract/corpus/rejects.txt:1265` covers a string state, which infers as `string` and is correctly `type-match-subject`. A literal subject never reaches that arm.

`literal` does not treat `Expr::Let` as a literal. Derive sharing runs at lower time, after this check (`contract/lower/src/lib.rs:227-230`), and it does walk `Expr::Case` (`contract/syntax/src/share.rs:70`, `304-313`). A substituted subject is not wrapped in `let` before the recheck, so a valid component match is not refused that way.

Suggested fix: skip only a subject that substitution just replaced, after the prop or argument was held to the choice. An authored literal, `?:`, or option-`match` stays `type-match-subject`.

## MATERIAL — Generated Rust enums are incomplete, and some do not compile

`contract/cli/src/rust.rs:173-187`, `224-247`, `282-285`. `pascal` keeps only ASCII alphanumerics. A legal literal with none (`"_"`, `"."`, `"-"`, `":"`, `"..."`) becomes an empty variant and is emitted as `    ,` or `    #[default] ,`. `pascal("self")` and `pascal("_self")` become `Self`, which is not a variant name. Two literals that share one non-empty variant are refused (`rust.rs:231-236`). A single empty name is not. Variants are not raw identifiers; field names are.

`choice_names` (`rust.rs:193-218`) registers a choice only when a named shape field holds it. `contract types` emits a literal union for every string row that has fields (`contract/cli/src/typescript.rs:34-41`). A choice that is only a `fn` result, an action parameter, or `resource r = src() as shape "a" | "b"` is `String` in the generated Rust, so `from_value` accepts every string (`rust.rs:75`). The runner still `conforms` if the plan row has the fields, so this is a generated-API hole rather than a silent installed answer. The LLP’s “one enum per choice” (`llp/1035.005.000-contract-after-the-apps.rfc.md:343-347`) is wider than this walk.

Suggested fix: emit one enum per choice type row; name it from the first shape field when there is one. Refuse or escape an empty variant and a keyword (`r#Self`, or a `V` prefix).
