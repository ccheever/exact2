## New findings

**MATERIAL — `fits` rejects subjects that are inside the arms.** `contract/types/src/choices.rs:171-181`. The carried check special-cases a string literal and a `?:`, then trusts an inferred `Choice` or `?`. `given`, which is what the use site runs (`contract/types/src/uses.rs:214-215`), also walks an option `match` (`choices.rs:103-123`). Expansion's sharing `let` (`contract/syntax/src/inline/derives.rs:214-224`, `266-272`) is invisible to `fits`, and `infer` of that `let` types a literal binding as `string` (`lib.rs:652`, `981-987`).

Reproduction 1, option `match`. The use site accepts this, because both arms are literals of the wanted choice. Expansion substitutes the `match` for `k`, marks the child's test checked, and `fits` infers the arms as `string`, so the whole program is `type-match-subject`. At runtime the value is only `"a"` or `"b"`.

```contract

    Child(k=match o { case some(x) => "a", case none => "b" })
component Child
  props
    k: "a" | "b"

    text match k { case "a" => "A", case "b" => "B" }
```

The same refusal hits `flag ? "a" : (match o { case some(_) => "b", case none => "a" })`: `given` walks the inner `match`, `fits` stops at it. The existing option-`match` test (`choices.rs:174`) is a `fn` return checked with `given`, so it never enters `fits`.

Reproduction 2, the derive the error text recommends. In the child, `mode` is `"a" | "b"` and the `match` is exhaustive. The body reads `mode` in the subject and in both arms, so resolution binds it once: `let mode = k in …`. With `Child(k="a")` the binding's value is the literal `"a"`, inferred as `string`, and the carried test's subject is the name `mode`. `fits` never sees the literal and refuses. Before this fit rule the program compiled, and both executors would take the `"a"` arm.

```contract

  derive line = match mode { case "a" => mode + "!", case "b" => mode + "?" }
```

`derive d = kind` in `choices.rs:183` does not hit this: each view read is a separate copy, so no `let` is inserted. Opening the `let` and re-inferring the body is not enough; the name's type is already `string`.

Suggested fix: give `fits` the same value walk as `given` (literal, `?:`, option `match`, both arms). For a compiler `let`, remember the value expression on the binding — the scope currently stores only the inferred type — and let `fits` on that name recurse into the value. Then a literal passed for the prop still counts as a member after sharing, while a comparison such as `mode == "b"` keeps seeing `string` and is not re-rejected. The sentence at `choices.rs:248` becomes true once that derive is accepted.
