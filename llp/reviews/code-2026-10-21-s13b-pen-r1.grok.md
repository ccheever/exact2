## Should-fix

1. `default`/`dark` as the scheme is the right reading of a two-value appearance axis when `default` is the non-dark side and is listed first, as in `mode.pen`: the default tuple matches Pencil and the colour is `light-dark()`. It is not exact beyond that. Selection walks a `BTreeMap` (`pen.rs:115`), so the alphabetically first `light`/`dark` or `default`/`dark` axis becomes the scheme (`pen.rs:126-129`), not the first in the file. A second such axis is enough to steal it, and non-colour values on the winner are then dropped as sided (`dtcg.rs:1288-1297`). The scheme's default tuple is always the non-dark side (`dtcg.rs:1115`), not the first listed value, so `["dark", "light"]` imports with light as the default. `docs/tamber-protocol.md:1060-1061` says each axis's first value is the default.

2. Kind-by-use keys off the immediate JSON key (`pen.rs:70-75`), not the property. Arrays keep the parent key, so `padding` and `cornerRadius` arrays work. Objects do not: `strokeWidth: { top, right, bottom, left }` is counted as `top`/`right`/`bottom`/`left`, none of which are in `PIXELS` (`pen.rs:32-41`), so a per-side thickness becomes a number. Nested `width`/`height` count as pixels, including a gradient's `size`, which Pencil normalizes to the box, so a unitless number becomes a px length.

3. An alias is followed per tuple, so a target that varies by theme is right, but the target's Pencil type is never compared. `type_of` returns at the first def that has a type (`tamber/src/import/dtcg/kinds.rs:48-50`), which is the source. A `number` aliasing a `string` `"16"` parses (`kinds.rs:175-180`). A `color` aliasing a `string` `"#fff"` parses as a colour. A `color` aliasing a number does not, and is reported.

The axes test only checks `source == mapped + reported` (`import_pen.rs:215-218`). Depth and a tiny walk budget are tested (`import_pen.rs:237-254`).
