3. **Disabling video preserves the picture instead of blanking it — MATERIAL**

## 2. New findings

### The web substitute cannot carry the promised session-clock timing

**PRE-EXISTING · MATERIAL**

**Where:** §8:841–849; drive 1:962.

The substitute promises that advancing the agent clock produces corresponding frames and a recording of that duration: `clock +3000` should yield three seconds of video. Its selected web path is a canvas’s `captureStream()` recorded through the browser’s `MediaRecorder`.

Canvas capture is a real-time source. Its frame-request APIs provide no timestamp argument. Chromium derives canvas-frame timestamps from browser `TimeTicks`, independently of Exact’s session clock. Drawing three seconds’ worth of synthetic counters during a clock jump therefore does not give the recording three seconds of presentation time. [Canvas capture specification](https://w3c.github.io/mediacapture-fromelement/), [Chromium implementation](https://chromium.googlesource.com/chromium/src/+/fc03862479bdb9db115db5ee798750f3ef87bd47/third_party/blink/renderer/modules/mediacapturefromelement/canvas_capture_handler.cc).

The existing architecture recognizes this distinction: [the agent driver](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/sc/r2/capsule/scripts/agent.mjs:1084) provides `clock +N real` separately, while [the current web recording substitute](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/sc/r2/capsule/packages/recording/web/index.js:20) generates an offline WAV from session-clock spans.

This blocks the specified web substitute’s observable result and acceptance drive. Reporting a three-second duration in recorder state would leave the file’s actual duration inconsistent.

**Fix:** choose an explicit web timing rule. The smallest change is to retain synthetic canvas capture, run its recording drives with `clock +3000 real`, and narrow §8’s accelerated-clock promise accordingly. Alternatively, specify and qualify a timestamp-controlled encoding or retiming path across the supported browsers.

I found no additional substantiated MATERIAL defect in the changed admission, Android service ordering, renderer seam, or capture boundaries.

## 2. New findings

### The web container fallback conflicts with the recorder’s required output path

**PRE-EXISTING · MATERIAL**

**Where:** D6:483; §8:876–877; §9.3:967–968; drive 1:990.

D6 explicitly falls back to `video/webm` when MP4 recording is unavailable. However, the recorder consumer always supplies `app:/data/takes/<n>.mp4`, and the substitute and acceptance drive require MP4 across the web target.

This conflicts with recording’s inherited rule: an explicit extension that disagrees with the container must produce `NotSupportedError`. [LLP 1133.009:198–205](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/sc/r3/capsule/llp/1133.009-recording.rfc.md:198). The current implementation enforces that rule in [pathFor](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/sc/r3/capsule/packages/recording/web/index.js:138).

Firefox still lacks MP4 recording, as tracked by Mozilla’s [open implementation bug](https://bugzilla.mozilla.org/show_bug.cgi?id=1631143). Consequently, the specified recorder feature cannot successfully use its WebM fallback there. This blocks a supported browser’s consumer and acceptance drive.

**Fix:** give the recorder an extensionless path, retain its returned full path and MIME type, and make web acceptance require the browser’s supported container. Explicitly requested unsupported MIME types should continue to fail.
