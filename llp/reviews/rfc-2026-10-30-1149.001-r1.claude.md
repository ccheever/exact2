## 3. The stages

**M1 (L84–86).** The premise is right: `about_to_wait` runs `service()` (pump, run_commands, hatch_turn, poll_images, and in live mode `advance`) on every loop turn (window.rs 552–564, 636–647), and `draw()` runs the same set again (221–229). The arithmetic 44 → ~34 follows if the 12.6 is exclusive time of near-empty passes, which the trace cannot yet show (§2 above). Three things the stage must state: (a) input delivery stays per event (`wheel_at`, `pointer_down` at 450–508 apply the input and advance the clock); "inputs mark the presenter dirty and nothing else" (L84) would otherwise reorder timers against input. (b) A pass cannot be "per frame" literally: a frame is drawn only when dirty (230), and an executor reply or image report is what makes it dirty, so a Wake with the link stopped must still service once; the rule is "at most one pass per display period while the link runs; one per wake otherwise". (c) Timer latency: in live mode a timer wakes the loop at its due time and `service` advances it (586–589, test at 742–758, which asserts a timer advances *without* a display frame). Folding service into the frame delays a due timer by up to one period and removes that contract; say which. The headless agent is unaffected (requests are handled synchronously, 351–387; `clock` and `settle` step the runner directly, clock.rs 55–71, agent.rs 1000–1064) and the RFC should say so.

**M2 (L87–88).** No rest-phase trace exists in the record (S1.4 traced the fling). Which timer wakes the Mac carrier at 1.4 ms/s main (G4 2002) is unnamed; name it from a trace before predicting ≤0.4. On Windows the instrument is quantized at 15.625 ms (2263): one tick in ten seconds is 1.56 ms/s, so "≤0.4" means zero ticks; write the target as that, or name another instrument.

**M3 (L89–94).** Confirmed in code: every present encodes a full-viewport pass sampling the compose target into the drawable (`present.rs` 326–385), then the worker waits for completion (56–59). Three problems:
- The compose target is not only "for D7's readback". D2.5 (1149 L258–265) needs it for any frame with a backdrop filter or blend mode ("a swap-chain image cannot be sampled"); `destination()` copies from the draw target for blended instances (`ink/rows.rs` 317–320, effects.rs 43); and the layer is `framebufferOnly` (apple.rs 52). M3 must keep the compose path for those frames and render directly otherwise, and say so; it amends D2.5 as well as D7.
- The drawable's texture is known only after `nextDrawable`, which D7 puts off the main thread (1149 L476) and the code runs on the worker (present.rs 286–289), while the scene is encoded on the host thread (D11; metal.rs 618 from `flush`). Rendering into the drawable means either acquiring it on the main thread (what GPUI and egui do) or moving Metal command encoding to the worker. Either amends D7 or D11; the RFC names neither, and "a worker wake gone" (L94) is wrong either way: the worker still acquires and presents.
- The prediction "~3 ms/s of CPU" is not in the record; the control's `present encode` exclusive time would be.

**M4 (L95–98).** The description is accurate: two slots, each waiting on the slot's previous command (present.rs 146–155), bytes copied twice (107, 174–180). But the CPU claim is weak: S1.4's 48.5 ms of worker upload is mostly `waitUntilCompleted` (37.5 ms, 1393–1394), blocked time, not CPU; the main-thread copy is 6.5 ms/10 s (1389). And the memory claim is contradicted (see §1): the transient survives with images disabled. One cheap lead the record does not mention: the renderer already reports the viewport-target pool's used count, retained count and bytes (`stats.rs` 17–22, `layer.rs` 15–21); targets are viewport-sized (10.2 MiB each at 1600×1600) and retained for 120 frames after last use (`layer.rs` 32); 335 MiB is ~33 of them; private textures have no malloc stacks, which fits S1.4's description; and G6b found the same pool retaining 1,201 targets on Windows during the churn (2476–2478). Read `layer_targets`/`layer_bytes` during a fling before any stage claims the number.

**M5 (L99–103).** Two premises are stale or unsupported. The link is not "stopped and restarted every frame" during a phased gesture: `Scrolling` keeps `running` true through began/moved and three quiet ticks (window.rs 577–585, 593–612); S1.5 identified the per-frame stop only for unphased events (1617–1622), and G3c/G4 posted phase-bearing events (1963). "Lands five milliseconds after vsync" appears nowhere in the record (S1.4 measured callback-to-wake, 0.016 ms, 1401–1402). The prediction, "one frame less input latency", has no instrument: G4 says no input-to-photon latency is measured (2117). M5 does not meet the RFC's own "trace that names it" rule (L79). A4 also amends D7's table ("CVDisplayLink on the Mac", 1149 L476) and should say so.

**M6 (L110–114).** The premise is wrong against the code. The kernel's commit and layout receipts already reach the painter per node (`paint/rows.rs` 31–47) and are mapped to rows as `stale`/`suspect` (175–231); a valid kept row is not walked, only its boxes are translated into the walk's list and `row_draw` is called (546–578); scroll translation alone keeps the row (`moved` → suspect → relative-frame check, 512–523); an arriving picture re-records only its slot (`pictures_again`, 437–467; `slot_again`). D4's "scrolling a list of unchanged rows walks none of them" is true today, so "now they also skip the walk" amends nothing. What the 5.7 ms/s is (new rows' recording, kept rows' box copies and `row_valid` checks, the chrome outside rows) is not in the record and needs a finer mark before a stage is designed. One question to answer with a counter: `Ink::reusable` requires whole-device-pixel offsets (`ink/rows.rs` 287–293, because `row_local` is false for hinting, backend.rs 273–275); if AppKit's fractional momentum deltas fail it, rows re-record every frame, which would look exactly like "every node every frame" and has nothing to do with a change bit. Statistics has no rows-replayed/recorded counter (`stats.rs`); add one and read it.

**M7 (L115–118).** This is the real cost: `replay` re-emits every instance through the clip stack (`ink/rows.rs` 306–383). It is also D4's own contingency, stated there ("If the copy shows in S0's measurement … the offset becomes a per-draw constant", 1149 L327–328), not an amendment. The design must say how the outer clips are applied without rewriting instances: D1.1's two rounded-clip slots are per instance, so a persistent range works as-is only under rectangular (scissor) outer clips, with the copy as the fallback.

**M8, Q3.** Fine as conditional.

**M9 (L128).** "ClearType included" is a tell the other way: the composition swap chain is premultiplied-alpha over Mica (D7, 1149 L477), where Windows's own apps render grayscale-antialiased text. Leave it to D3.3's audit.

**M10 (L129–131).** "35 to 50 ms of a 150 to 180 ms first screen" is Windows (D3D11 device 48 ms, MEASUREMENTS 589; G6 176–187 ms). The Mac first screen is 352 ms (G4 1997) with device creation 31.7 ms (MEASUREMENTS 429) and no phase attribution of the rest in the record. The ≤250 Mac target has no basis yet; say that M10's first chunk is the phase trace.

**M11 (L132–133).** D15's direct-Metal boot obligation is dated 2026-11-04 (1149 L666–668) and is in stage 3, after two staged lanes with two-family reviews each. It cannot be met in this order; either it moves first or the RFC renegotiates the date explicitly.

Stage-1 sum (L105–106): the listed predictions give main 44 − 10 (M1) − 3 (M3) = 31, not "25 to 30", and process 86 − 10 − 3 − "a few" ≈ 70, not "about 60". On Windows there is no trace of the G6c build at all (G6b's trace is the 6,337-paint build, 2442–2447); "at or under 60" is a guess, and G6b's largest named main-thread item, clip masks rebuilt per paint (2444, 2510–2511), has no stage.

## 4. The amendments

**A1.** After it, D9's pinned suites still exercise only the offscreen path (`finish()`, ink.rs 642–667); the drawable path becomes pixel-untested, and a screenshot is a re-render of that same offscreen path, so it cannot catch a drawable-path defect. Add the gate: a window capture of the presented frame (as the G3c/G4 captures are) compared to the re-rendered screenshot within the band. Define "the retained scene": the last encoded frame's batches and instance buffer (the three-slot ring already holds them), re-submitted before the next encode so atlas entries are as encoded; in live mode a mid-animation screenshot is therefore the last *encoded* frame, up to one ahead of the glass. Headless screenshots are unchanged.

**A2.** The change bit exists; the amendment should be M7's persistent ranges only, with the box copy and `row_valid` checks named as what remains per frame.

**A4.** "Nothing wakes at rest" needs "except a due timer, a reply or an image".

**A5.** Workable per stage, not per landing: a Mac series is ~15 minutes of a held quiet display with a human "GO" (1861–1879, 1976–1986), and a Windows series needs the signed-in NucBox with elevated PresentMon; the record shows retakes, focus theft and an egui readiness timeout per series. Say "one rerun per stage landing, plus any fix that moves a row".

## 5. Targets against floors

Mac ≤60 process / ≤28 main is below egui's 67 / 31 with the kernel and runner kept (§5), while ~15 ms/s of main thread, half of egui's whole main thread, is unattributed (L70). §5's "egui's 25 ms/s" is egui's Windows number; on the Mac egui is 67. Peak ≤400 MiB has no stage addressing an identified cause. Cold ≤250 has no attribution. Windows ≤60 has no trace. The GPU ≤0.4 follows from M3 if the split holds. "At the earned clock" (L53) is undefined.
