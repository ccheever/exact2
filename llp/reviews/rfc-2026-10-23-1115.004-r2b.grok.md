He names **TextBox and RichTextBox**, not RichEditBox, and he says color emoji is off until `EM_SETTYPOGRAPHYOPTIONS` with `TO_DEFAULTCOLOREMOJI | TO_DISPLAYFONTCOLOR`. The same post says the **RichEditD2D window class** never landed in `msftedit.dll` ([RichEditD2D window controls](https://devblogs.microsoft.com/math-in-office/richeditd2d-window-controls/)). `ITextHost::TxClientToScreen` is what places the candidate window. That works in a non-XAML host only if the host converts the caret from the composition surface to screen pixels on every query, including while the transcript scrolls. The 2007 note does not prove Windows 11 suggestions, Win+H, or reconversion.

5. **Excord’s composer, not only Shelf’s search.** The RFC’s spike specimen is Shelf’s search field (D7.0, lines 313–320). ## F. Map Meta-only chords on Windows, and lint them

**Recommendation.** Option 3, narrowed to Windows. A chord that contains `Meta` and not `Control`, whose list has no copy with `Control` in `Meta`’s place, matches and is shown as `Control`. Lint every chord the map rewrites. Desktop Linux stays literal. The same lint runs there.

**Confidence: 76.**

**Facts.** Matching is exact: `has("Meta") == held.meta` and the same for Control (`host/linux/src/presenter/shortcuts.rs` lines 70–74). The web host does the same (`host/web/input-glue.js` lines 145–148). ARIA 1.3 says the modifier tokens are the UI Events names, that on Apple computers Meta is Command, and that user agents must not change keyboard behavior because of the attribute ([`aria-keyshortcuts`](https://www.w3.org/TR/wai-aria-1.3/#aria-keyshortcuts)). Exact already treats the attribute as the binding. On Windows, `KeyboardEvent.metaKey` is the Windows key. The shell takes Win+N (Notification Center) and Win+. (emoji panel), so a literal match never sees those keys. The app must not install a hook or `RegisterHotKey` to observe them.

Meta-only chords in `apps/*/*.contract` include `apps/agents`: `Meta+N`, `Meta+.`. `apps/native-fixture`: `Meta+Shift+Enter`, and `Meta+Shift+Enter Meta+Plus c`. Fieldnotes, the galleries, and exact-live already list `Control` siblings (`Meta+S Control+S`, `Meta+[ Control+[`, `Meta+1 Control+1`, and so on). Harness uses `Control+o` only. Nothing declares `Meta+Control+F`.

**The two chords you asked about.**

- `Meta+Control+F` stays literal. Both modifiers are required, so it is not the Control form of a Command chord. It matches only when Windows and Control are both down. Lint it. Many Win+Ctrl chords belong to the shell (Win+Ctrl+Enter is Narrator, Win+Ctrl+D a virtual desktop) and never arrive.
- A list that already has both (`Meta+S Control+S`) is not rewritten. `Control+S` matches Control. `Meta+S` matches the Windows key and does not arrive. Menus and tooltips show Ctrl+S.

**Reserved chords.** If the key never reaches the window, it does not match: Win+anything the shell owns, Ctrl+Esc, Ctrl+Shift+Esc, Alt+Tab, Win+Tab, and Ctrl+Alt+Del (the secure attention sequence). Alt+F4 and Alt+Space do arrive, and `DefWindowProc` keeps them (close, window menu). An author declaration does not override that. F10 and Alt alone stay D9’s menu and access keys. Lint any declared chord in this set.

**What would change this.** A decision that native Windows must fire the same chords a browser page can fire. Then option 1 is right, and `Meta+N` / `Meta+.` stay dead until every contract gains a Control sibling. Or a measurement that GNOME takes Super+letter the way the shell takes Win+letter. Then the same map applies on desktop Linux. I would not start there: Linux’s look is still the neutral web look, and Super often reaches the page.

## G. Per-user install, sparse identity, Exact’s updater

**Recommendation.** The first public Windows app ships as option 2. Not before S1. Before the first public installer, and before S3’s share target.

**Confidence: 81.**

**What “option 2” means.** A per-user unpacked install under `%LOCALAPPDATA%\<Publisher>\<App>`. Exact’s delivery keeps updating that tree: signed bundles a release binary already fetches (LLP 1030; `scripts/push.mjs` is that one-second path). The installer also registers a sparse identity package, `Add-AppxPackage -ExternalLocation`, so the exe stays where Exact updates it.

Microsoft’s current packaging page is the ISV row: own installer, external location, “your existing mechanism” for updates, Store-eligible later as an MSI/EXE submission that does not itself push updates ([Packaging overview](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/packaging/), 2026-08-29). Share target, WNS push, startup tasks, and manifest file associations need package identity. Sparse identity supplies them. Full MSIX is not required.

**The RFC’s packaging sentence is partly wrong.** `llp/1115.004-no-tells-on-windows.rfc.md` lines 488–489 say toasts and being a share target need package identity (MSIX). Share target does need identity. Local toasts do not: an unpackaged app sends them with an AUMID and a Start-menu shortcut, or with `AppNotificationManager` ([unpackaged desktop toasts](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/send-local-toast-desktop-cpp-wrl)). WNS push does need identity. Sparse registration is the piece S3’s share sheet needs. Full MSIX is a second choice.

**Signing.** Authenticode on the installer and the exe, and the same publicly trusted cert on the sparse `.msix`. The Learn page’s name for the cheap path is Azure Artifact Signing, formerly Trusted Signing. A new cert gets SmartScreen’s “Windows protected your PC” until that cert has reputation. The Store’s free signing applies to a Store submission, not to this installer.

**winget.** A manifest whose installer URL is that per-user installer, once the URL is public. `winget upgrade` follows installer versions. It does not see a bundle push. Publish the manifest with the first public installer, not as the updater.

**When.** S1 is Shelf on the NucBox via `agent.mjs`. A copied folder is enough. S1 should still put mutable bundles and user data under `%LOCALAPPDATA%`, and keep the install directory stable enough to name as an external location. Deciding the identity package can wait until just before S3, which is what §4 says. Deciding full MSIX or the Store can wait forever.

Option 3 makes the install directory immutable, so a host-binary fix leaves Exact’s stream and becomes an MSIX or Store update. Option 4 as the updater conflicts with a signed origin the app polls itself. A later Store listing of the same installer is compatible with option 2, because that submission path does not push updates.

**What would change this.** A requirement that the Microsoft Store is the only way the first public app is installed. Then the ship form is full MSIX, Exact updates only bundles in the package’s local data, and host binaries move on the Store’s schedule. Or a measurement that sparse registration on Windows 11 22621 fails for a public CA without sideloading policy. Then ship option 1 for the first public installer and add identity only where that policy can be set.

`rules/DEFERRED.md` lines 443–452 still bound general Windows to Skirmish and Windows Desk. The 2026-10-23 full-speed admission is not in that file.
