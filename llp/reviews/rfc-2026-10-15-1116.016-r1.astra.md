## 1. Verdict

**RETHINK.** Keep Charlie’s direction, but revise the semantic boundary and implementation plan before accepting this RFC: several proposed forms violate T4, and important parts of D2 are not semantics-preserving sugar. The predecessor’s level measurements justify treating this as a language investment; they do not justify understating its runtime, proof, or migration cost.

## 2. The most important issues, ranked

### 1. D1 promises more than the existing language can deliver

The problem extends beyond missing methods. Existing accepted expressions already have observably different meanings:

| Accepted Contract | Difference from TypeScript |
|---|---|
| Equality between distinct lists containing `[1]` | Contract compares structurally; JavaScript compares array identity. |
| `" x ".trim()` with a declared `fn trim` | The parser rewrites the method to a free call, which the user function captures. A JavaScript function named `trim` does not replace `String.prototype.trim`. |
| `"😀".slice(0, 1)` | Contract replaces the lone surrogate with U+FFFD; JavaScript preserves it. |
| `a-b`, when that identifier exists | Contract reads one variable; TypeScript subtracts. |
| `performance.now()` | The intended rewrite retains Exact’s injected evaluation clock, which needs an explicit semantic qualification. |

I confirmed the equality, method-shadowing and hyphen cases through the existing compiler’s stdout-only Lean emitter, and the equality difference through the web runtime. The relevant implementation is [parser/expr.rs](/Users/ccheever/projects/exact2/contract/syntax/src/parser/expr.rs:146), [types/lib.rs](/Users/ccheever/projects/exact2/contract/types/src/lib.rs:804), [shape.js](/Users/ccheever/projects/exact2/host/web-js/shape.js:29), and LLP 1088 D2’s declared string normalization.

**Consequence:** D5 would replace a small dialect description with an inaccurate general rule. Adding more familiar spellings increases the number of places where that rule misleads.

**Change:** Define a checked, deterministic subset of TypeScript expressions, with an explicit mapping of values and a small, complete list of required deviations. For overlapping syntax, preserve ECMAScript behavior or refuse it; separately decide what happens to structural equality, expression identifiers containing hyphens, string normalization, and method resolution. Built-in methods and `Math` members must resolve to built-ins, not accidentally to same-named free functions.

This is a new language decision. LLP 1115’s CSS rule does not settle it, and LLP 1081 D5 explicitly excludes expression functions. D1 should also price admission by usefulness **and semantic cost**; “as frequent as `toSorted`” is not a useful universal threshold for operations of very different complexity.

### 2. `Math.min` and `Math.max` require a semantic correction

The current roster does **not** implement JavaScript’s functions:

- [runner/src/stdlib.rs:249](/Users/ccheever/projects/exact2/runner/src/stdlib.rs:249) uses Rust’s `f64::max`/`min`.
- [host/web-js/roster.js:5](/Users/ccheever/projects/exact2/host/web-js/roster.js:5) explicitly returns the other operand when one is NaN.
- [Number.lean](/Users/ccheever/projects/exact2/semantics/Contract/Number.lean) models that behavior.
- [floor-max-min.contract](/Users/ccheever/projects/exact2/semantics/corpus/numbers/floor-max-min.contract) positively asserts it.

I ran the web entries: `x_max(NaN, 1)` and `x_min(NaN, 1)` return `1`; JavaScript’s functions return NaN. This is reachable with ordinary Contract values: `max(0 / 0, 1).toString()` compiles. Refusing failed numeric parsing does not eliminate arithmetic NaNs. [ECMAScript’s definitions](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-math.max) require NaN propagation.

**Consequence:** The proposed namespace rewrite silently accepts a familiar spelling with another meaning—the exact failure T4 forbids.

**Change:** Make min/max correction a separate semantic change across the runner, web runtime, Lean model and arithmetic corpus. Audit existing consumers: a derive that currently obtains a finite fallback could instead refuse after the correction.

`floor`, `ceil` and `round` are much better candidates for genuine sugar. The existing `js_round` handles negative ties, negative zero and nonfinite inputs deliberately. For min/max, preserve signed-zero behavior, evaluate every argument once in source order, and explicitly decide zero/one-argument support. Refusing those arities is a permissible subset; it is not JavaScript’s complete signature.

### 3. `find`/`some`/`every` through `filter` are not observationally equivalent

Purity does not make skipped callbacks irrelevant when evaluation can refuse.

Suppose `big` contains 65,536 numbers:

```ts
[0, 1].some((x, i) => i == 0 || big.map(y => y).length > 0)
```

JavaScript returns `true` after the first callback. The proposed filter rewrite reaches the second callback and exceeds Contract’s shared list-step budget. The same issue affects `find`, and `every` after its first false result. Smaller inputs can expose unnecessary allocations and substantially more work.

This is especially material because LLP 1017.003 D3 permits a binding trap to poison the runner. “The result is the same” is therefore false under the shipped execution model.

Moreover, [semantics/README.md:771](/Users/ccheever/projects/exact2/semantics/README.md:771) explicitly excludes these resource-bound refusals from differential agreement: they become `UNSUPPORTED`. Green Lean proofs and ordinary difftest runs would not settle this objection.

**Change:** Implement short-circuit search semantics and price them honestly. One internal search primitive returning the first matching index could support all three operations—and make `findIndex` inexpensive—without three independent execution mechanisms. Preserve original callback indices, evaluate the receiver once, retain the authored operation in diagnostics, and define the current restriction on lists of options.

T2 also needs qualification for `first` → `at(0)`: these are currently separate roster entries, `first` and `at`, with different arguments and emitted calls. They are behaviorally equivalent for supported inputs, not currently identical plans. Remove the redundant operation without making byte identity the wrong acceptance test.

### 4. `toSorted` needs an algorithm and a substantially broader cost estimate

A callback-taking sort is not just another roster row. A roster `Call` consumes values; the comparator is executable code. The present callback machinery in [machine.rs](/Users/ccheever/projects/exact2/runner/src/machine.rs), [Vm.lean](/Users/ccheever/projects/exact2/semantics/Contract/Vm.lean) and [LowerCorrect.lean](/Users/ccheever/projects/exact2/semantics/Contract/LowerCorrect.lean:16) implements sequential map/filter traversal. A comparator instead binds **two items**, suspends sorting to evaluate their comparison, and resumes it.

The design must cover the opcode or equivalent execution mechanism, validation, captures, nested callbacks, dependency tracking, web emission, typing and evaluation relations, lowering correctness, and the [extracted VM proofs](/Users/ccheever/projects/exact2/semantics/vm-extract/README.md). Extending `each_sem` alone does not describe this work.

Two decisions are missing:

- **Deterministic sorting and accounting.** ECMAScript leaves comparison order implementation-defined, and permits implementation-defined results for inconsistent comparators. Purity does not establish transitivity. Counting comparator calls also makes algorithm choice observable through refusal—even for consistent comparators. Specify one deterministic, bounded algorithm across Exact’s executors; do not delegate independently to Rust sorting and each browser’s native sort. Distinguish agreement with ECMAScript’s specified result from Exact’s policy where the standard leaves freedom. [SortIndexedProperties](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-sortindexedproperties)
- **Default sorting.** Accepting JavaScript’s actual lexicographic default does not violate T4; silently replacing it with numeric sorting would. There is direct evidence for the default: [post15/muse/grocery-list-2/app.contract:23](/Users/ccheever/bakeoff/guesses/post15/muse/grocery-list-2/app.contract:23) deduplicates category strings and calls `.sort()`. At least admit the string-list default. Requiring a comparator for numbers can be a deliberate guardrail, but “no author means it” is unsupported.

**Change:** Split sorting from padding and approve its execution/proof design explicitly. A cheaper candidate is a restricted, recognizable comparator subset lowered to existing `map` plus a non-callback key-sort operation; seven of the eight post15 sort expressions use simple numeric field differences, and one sorts strings. That alternative must be refused outside its proven subset and checked for evaluation-order and budget differences. It is worth pricing, not assuming equivalent.

### 5. Padding exposes the string-model conflict and introduces an unexplained bound

`"x".padStart(2, "😀")` produces a leading lone surrogate in JavaScript. Contract’s scalar-string representation cannot preserve that result. Reusing LLP 1088’s `toWellFormed` policy would therefore break D1’s unqualified promise even though both inputs are valid Contract strings.

The specified bound also changes policy: LLP 1088’s deferred padding decision says to apply the **byte bound** after the no-op cases; this RFC substitutes 65,536 UTF-16 units. Existing `MAX_STRING` is 67,108,864 UTF-8 bytes. Those are different limits with different purposes.

**Change:** Decide whether an unrepresentable result is refused or normalized as an explicitly retained language deviation. Preserve `ToLength`, fill repetition/truncation, and the early returns—including `"abc".padStart(Infinity, "")`—then specify exactly what is bounded, whether it consumes shared work budget, and which refusal occurs. The order matters. [StringPad](https://tc39.es/ecma262/multipage/text-processing.html#sec-stringpad)

### 6. Stage 2’s absence model must be designed before stage 1 commits to it

The direction is promising: removing repeated `match` scaffolding could improve both reading and authoring. But D2 says the eventual spelling is `T | undefined`; §6 proposes `T | null`. These are not interchangeable TypeScript semantics. `find` returns undefined when unsuccessful, and optional chaining short-circuits to undefined even when its receiver was null. [TypeScript strictNullChecks](https://www.typescriptlang.org/tsconfig/strictNullChecks.html), [optional chaining](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-7.html)

There is a useful existing constraint: [types/bounds.rs](/Users/ccheever/projects/exact2/contract/types/src/bounds.rs) already refuses directly nested options because the web erases `some`. I confirmed that `[some(1), none].at(0)` is refused. Thus stage 2 does not need to preserve arbitrary nested option tags, but it does need to define flattening and nullable-element behavior deliberately.

**Change:** Write the next RFC now, while allowing its implementation to land separately. Decide between distinct null/undefined values and an explicitly restricted, single-nullish model. Specify:

- Nullable widening and branch joins.
- Lazy, single-evaluation lowering of `??` and `?.`.
- Narrowing through conditions, short-circuit operators and action snapshot reads.
- Nullable fields versus missing fields, and generated TypeScript/data-boundary behavior.
- `find`/`at` on nullable elements and optional chains returning nullable fields.
- The status of casts, non-null assertions and unchecked indexing.

`strictNullChecks` is evidence that familiar syntax can express the guarantee, not a replacement for proving Exact’s checker and lowering preserve it.

### 7. The evidence supports a language improvement, but neither the ceiling nor the proposed judge is sufficient

The predecessor’s principal measurements check out:

| Measurement | Verified result |
|---|---:|
| Guess corpus, clean screens | 40/80 → 37/80 |
| Guess corpus, errors | 54 → 58 |
| Post15 `.sort` use | 8 screens: 5 GPT, 3 Muse; 7 sort diagnostics |
| Paired total-token geometric ratio | 1.031 |
| Paired time geometric ratio | 1.003 |
| Grader preference | Change 6, base 7, tie 3 |

Sources: [pre15 summary](/Users/ccheever/bakeoff/guesses/pre15/summary.json), [post15 summary](/Users/ccheever/bakeoff/guesses/post15/summary.json), and [ab3 grade records](/Users/ccheever/bakeoff/rounds/ab3-grades/records).

Three qualifications matter:

**The 3% is a direct exposure estimate, not a hard causal ceiling.** Avoiding an early repair saves subsequent re-sending of every topic; adding repairs can amplify cost likewise. Conversely, the expression category contains concepts this stage retains. The defensible conclusion is “small expected direct token effect, below the previous experiment’s resolution.”

**D5’s plausible deletion is small.** The current Expressions bullet is 368 bytes. A generous removal of 26 card function/property lines is 837 bytes before replacement text, and some entries need qualifications retained. LLP 1116.013 already showed that much larger first-read cuts simply moved knowledge into lookups. Draft the actual cut and measure eliminated knowledge, not just deleted bytes.

**The census needs comparable units.** My raw scan of the 112 `app.ts` sketches finds `padStart` in 22 files/43 textual occurrences and `find` in 13 files/28 occurrences; §1 reports 36 and 19. Reconcile the selection and counting method before comparing these with once-per-build refusals or once-per-screen Contract guesses. The demand remains plausible, but the ranking is not yet reproducible.

**Change:** Keep fresh guesses as one judge, add held-out features and diagnostic-repair trials, and retain whole-app behavioral assessment. `.sort` remains refused under D4: a one-shot harness that never follows the diagnostic cannot measure whether that refusal now costs one successful edit. Nor can a zero-increase rule on every diagnostic category distinguish regression from sampling noise in 40 screens per model.

## 3. Per decision

| Decision | Recommendation |
|---|---|
| **D1** | **Change.** Keep TypeScript as the default expression vocabulary and behavioral reference. Define the accepted subset, required deviations and existing incompatibilities before claiming general equivalence; include implementation cost in roster admission. |
| **D2** | **Change.** Keep the straightforward namespace renames and `first` consolidation. Correct min/max semantics explicitly and replace the filter-based searches with short-circuit execution; neither belongs under an unchanged-runner/proofs claim. |
| **D3** | **Change; split.** Sorting has strong Contract evidence but needs its own execution and proof design. Padding is smaller, provided its surrogate policy and bounds are settled; support default string sorting. |
| **D4** | **Keep, with behavioral qualifications.** `.push` often needs `xs = xs.concat([x])`, not merely a substituted expression; bracket indexing and `.at` differ for negative/fractional indices, and code-unit ordering is not equivalent to locale collation. Add focused diagnostics for likely next guesses: `===`, named/block callbacks, optional arguments, spread and stage-2 syntax. |
| **D5** | **Keep the objective; change the gate.** Teach differences and retain a compact supported-operation index, but remove explanations only when familiarity actually replaces them. Judge net context exposure, lookups and repair success alongside bytes. |
| **§6** | **Keep as a separate RFC; design now.** Options can retain T1 under a sound checked subset, but null/undefined and lowering choices cannot be deferred while D2 assumes their answer. |

Carry T6 forward explicitly. Charlie and James should read representative whole apps, including option-heavy and callback-heavy code. Migration must distinguish built-ins from user functions named `min`, `first`, etc.; cover embedded Contract, examples, diagnostics, `contract vocab`, generated app scaffolds, external path consumers and open branches. Separate mechanical renames from behavior changes, with no compatibility aliases.

## 4. Answers to the RFC’s §9 questions

1. **Is D1 the right end state?** Yes as a direction: familiar expressions should preserve their familiar meaning, and Exact-specific guarantees should be explicit. No to the current unconditional formulation; the existing value model, lexical grammar and method resolution contradict it.

2. **Accept D2–D5 as the first stage, judged by guesses and bytes?** Not as this package. After the semantic corrections and sorting design, accept them as independently reviewable language changes, judged primarily by correctness, successful repairs and whole-app quality; guesses and bytes are useful secondary measures.

3. **Write stage 2 after this lands?** Write it now and implement it separately. Its absence model is a dependency of the API promise being made here, while its narrowing implementation need not block independent arithmetic or documentation work.

## 5. Anything to measure or verify before deciding

- **Rewrite honesty:** same-plan tests for genuine sugar, plus independent expected results. Cover captures, shadowing, receiver/argument evaluation once, nested callbacks, empty lists, callback indices, and diagnostics naming the authored form. Use behavioral equivalence for `first`/`at`, not an assumed existing plan identity.
- **Numeric edges:** NaN in every argument position, both signed-zero orders, infinities, arities, and rounding around negative halves and representational boundaries. Verify bits or reciprocals, since printing hides negative zero.
- **Search behavior:** first/last/no match, empty `some`/`every`, expensive skipped tails, nested work budgets, nullable items, allocation cost, and refusal/rollback behavior.
- **Sorting:** stability with duplicate keys, permutation preservation, comparator NaN and ±0, inconsistent comparators, UTF-16 order across astral/BMP characters, nested callbacks, and identical budget outcomes across native and web executors. Measure realistic list sizes and the full proof/extraction maintenance cost.
- **Padding:** omitted/empty fill, fractional/negative/NaN/infinite targets, no-op inputs already beyond the proposed cap, multicode-unit fills, surrogate cuts, and exact boundary refusals.
- **Agent and human outcomes:** reproduce census units, draft D5’s actual net cut, run held-out guess-and-repair trials per model, and complete T6’s whole-app reading and migration inventory.
