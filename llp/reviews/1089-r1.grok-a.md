## Findings

1. **MATERIAL** — §2 D1, "Host commands". A host command and an action of the same name already coexist, and the statement is the command. D1 refuses that statement.

   Files, one of the three diaries this RFC is for, wraps the host command:

```549:551:/Users/ccheever/projects/x2apps/files/app.contract
  action share
    if preview.text != ""
      share(title=preview.name, text=preview.text)
```

   Caltrain, in this repo, does the same with `setScheme` (`apps/caltrain/app.contract:109-110`). Both names are host commands (`contract/types/src/checks.rs:744-776`). A probe with `action share` and a statement `share(text="hi")` compiles today (`cargo run -q -p contract -- build`, exit 0, `[]`). The action is not callable, so the statement is the command. D1's `type-call-ambiguous` makes that statement an error. The sentence "apps that never call such an action are unaffected" (line 97) does not cover it: the call is the command, inside the action that shares its name. Renaming the action changes the plan, so the byte-identical exit (§2 D8, §4) fails for Caltrain.

   **Fix:** A statement whose name is a host command stays the command. An action may still have that name and be bound with `press=share`. It cannot be the target of a call. That leaves every current plan unchanged and keeps the wrapper idiom.

2. **MATERIAL** — §2 D3, "The rule". The read set and the write set are not the reads and writes that diverge between the snapshot the runner implements and statements run in order.

   During the body, slot loads read the starting slots (`runner/src/vm.rs:561-572`). Derives read the settled values (`vm.rs:574-581`, `contract/lower/src/expr.rs:158-160`, `semantics/Contract/Eval.lean:47-48`). `pending(mutation)` reads the flag array the commit updates only after `vm::eval` returns (`runner/src/runner/commit.rs:464-470`, then `557-569`). Send answers are applied after the body, and any assignment is applied after every answer (`commit.rs:543-549`). Lean states the same order (`semantics/Contract/Axiomatic.lean:507-508`). `failed(x)` does not accept a mutation: a probe `failed(saved)` is `type-failed-argument`, "`saved` is not a resource" (`contract/types/src/lib.rs:740-756`). A probe `send saved; flag = pending(saved)` compiles.

   So a root derive read, a `pending(m)` read, and a read of the mutation slot after a send see the starting value under both readings. D3 still calls a send a write of `pending(m)`, and a derive read a read of every slot the derive mentions (lines 141-147). Splitting the spreadsheet's `label = status` (`app.contract:160`, `status` reads `message`) into a helper after `message = ""` is refused, and the suggested `let next` passes the same old value the inline form already produced. Child derives are a different case: they are substituted into the action before it is lifted (`contract/syntax/src/inline.rs:584-593`), so a child derive of child state is already a slot read and the two readings do differ.

   **Fix:** On the expanded body, after capture conversion and child-derive substitution, a read is a reference to a state or mutation slot: assignment and `let` right-hand sides, conditions, `match` subjects, member receivers (`cell.n` compiles), templates, command and send arguments, and `map`/`filter` arrows (a probe `map(xs, x => x + n)` compiles; a `fn` cannot see state, probe `type-unknown-name`). Count a call argument in the callee's frame, and count it before the callee's own writes. A name that is still a derive or a resource is a settled value. A capture parameter is not a slot. A send is not a write; an assignment of the mutation slot is. Drop `pending` and `failed`.

3. **MATERIAL** — §2 D3, "The walk". The walk described there is coarser than "some path", and coarser than LLP 1088 D8's walk, which it says it is.

   D8's walk treats sequential `if`s that test one name against disjoint literals as exclusive (`contract/analyze/src/sends.rs:11-15`, `32-70`), because key handlers are written that way. D3's prose keeps only "arms start from the incoming set, union after the branch" (lines 149-152). After `if k == "ArrowDown" move(1, 0)`, that union carries `move`'s write of `ar` into `if k == "ArrowUp" move(-1, 0)`. The second call reads `ar` in another frame, so D3 refuses it. Spreadsheet `clipKey` is this shape (`app.contract:349-367`): each branch computes the next cell from the starting `ar`/`ac`. On every path that can run, only one call runs, and snapshot and statement-order both move once from the starting selection. There is no `else if` (files and spreadsheet both hit that). The factoring F21 asks for is a sequence of those calls.

   **Fix:** "Some path" is the rule. The walk includes `sends.rs`'s literal-exclusion, and it enters `Stmt::Call`'s body without resetting the path set. A test for `if k == "ArrowDown" or k == "Enter" move(1, 0)` then `if k == "ArrowUp" move(-1, 0)` is accepted; `move(1, 0); move(0, 1)` stays refused. The second really does disagree: both calls read the starting cell, and the later write wins, so the result is not a diagonal step.

4. **MINOR** — §2 D5 and D8. `actions.writes` is not the union "by construction" once the call is a `Stmt::Call`. `Action::effects` walks `if` and `match` only (`contract/syntax/src/ast.rs:515-540`). The VM traps a store or send outside that allowlist (`runner/src/vm.rs:831-832`, `860-861`). Tail calls are visible today because their statements are spliced. A `Call` node hides them until `effects`, `sends::check`, and `check_mutation_then` (`contract/analyze/src/lib.rs:207-229`, which still reads the authored body) recurse into `body`. Rust exhaustiveness will force a match arm; the spec should say the arm recurses, and that the allowlist is that union.

5. **MINOR** — §2 D9. The two bullets under-specify the call that difftest is supposed to check against expansion. Thread the whole effect record (root writes, row writes, sends, commands, refreshes) through the call, and drop it if the callee refuses. `.call`'s arguments are the callee's full parameter list: capture parameters and the curried prefix are the caller's already-bound parameters, then the source arguments, evaluated in the caller against the action's starting slots. The body that runs is the owner's action in its own scope. A prop call inside a row does not follow from "look up the action and bind the source arguments" alone, and that is one of the corpus cases (line 274).

6. **NIT** — §2 D2, lines 112-116. "Writes land in statement order, and the last wins" is true of assignments. The theorem cited on the next line says an answered send counts as a write before every assignment, which is what `commit.rs:543-549` does. Keep that sentence about assignments. Finding 2 is what stops a send from being put in that order for D3.

7. **NIT** — §2 D10, the `analyze-call-stale-read` text. It assumes the author wanted the new value. Files `go` pushes `remember(back, location)` after `location = to` (`app.contract:134-136`) so the stack records the folder being left, and `goBack` sets `cursorPath = location` after `location = back.a` (`147-155`) so the cursor stays on the folder being left. Both are the snapshot, and both are what a correct extract must pass explicitly. Say that the helper sees the starting value, and that passing a `let` bound before the write keeps that value.

## Open questions

1. **The DEFERRED waiver.** The semantic content that should stay refused is recursion, a return value, and an action as an argument. Those three keep expansion terminating and keep `.call` static. The waiver is Charlie's, the same kind he gave the tail call. The compatibility sentence in D1 needs the host-command rule from finding 1 before that waiver matches programs that already run.

2. **D3 inside one frame.** Leave it as it is for this RFC. The same-frame snapshot is load-bearing, not only the docs' `doubled` example. Files `go` and `goBack` (lines above) and spreadsheet `er = clampRow(ar + 1)` after `ar = clampRow(ar + 1)` (`app.contract:354-356`) are reads of the value the action started with, on purpose. Refusing them is a source break with a mechanical `let` rewrite, and it is a separate change from calls. The stage 1 census should count these so the number is real.

3. **The size bound.** 1,024 statements does not change the meaning of an accepted program. The diary factorings duplicate a straight-line helper into a handful of callers. The exponential case is a chain that calls the next action twice. The bound is a backstop. Measuring the converted spreadsheet and files, as stage 1 already says, is the right check.

4. **A Lean theorem for D3.** State it, and do not prove the bullets as written. Those bullets refuse programs the two readings agree on (findings 2 and 3), so the theorem is false for that statement. The theorem that matches the executors is: if no path reads a slot that another frame wrote earlier on that path, then loading each slot as the last assignment on the path, or the starting value when there is none, equals the snapshot load. Derives, resources, `pending`, and sends are outside that statement. It can wait past stage 1, since both executors stay on the snapshot either way. It is the check that the refusal matches the divergence.

A web developer can predict the repaired rule in one sentence: a helper sees the state the action started with, and if an earlier call wrote a slot the helper reads, pass the value. `move(1); move(1)` staying a one-cell move is the case that sentence is for, and refusing it is the right surprise. React's model is the snapshot; the error is stricter than React, and the message makes the data flow visible. The unrepaired rule also errors on extracts that already agree, and on `share()` inside `action share`, which reads as arbitrary.

Verdict: READY WITH CHANGES
