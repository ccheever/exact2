1. **Separate prerequisite advancement from host admission.**

   **Where:** [D4, lines 200–211](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:200); [D6, lines 274–285](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:274).

   Two definitions conflict. Ordinary release advances precise timers and expired caps first; the frame paragraph instead places held timers “among” due timers in deadline order. A held timer due at 49 ms and a precise timer due at 50 ms that disables it have opposite outcomes under those orders.

   There is also an admission gap: the host supplies `kinds` **before** the prerequisite advance. That advance can start scrolling, request frames, or produce an unapplied batch. Its earlier `idle` or `scrollend` decision can therefore be stale.

   Adopt:

   > A live release turn has one fixed cutoff. First advance ordinary scheduled work, including expired caps, to that cutoff. Apply its resulting batch. Then determine the eligible wait kinds from the resulting host state and release held firings due by the cutoff. Frame processing uses this same order, followed by frame tasks. There is no second prerequisite advance between checking eligibility and releasing.

   This requires an application boundary between preparation and release—either two calls or a release operation that returns preparation work before accepting the final mask. Keep the runner/host responsibility split.

   Among admitted non-idle firings, retain original-deadline then plan-row order. Admit idle separately, one firing after applying and rechecking preceding work. Replace “never depends on the order … a host notices” with “does not depend on the enumeration order of kinds eligible at the same admission point.” Different platform callbacks are different admission points.

   The existing runner already uses a fixed cutoff and samples each callback separately: [advance.rs:264](/Users/admin/Developer/exact2-timer-wait-points/runner/src/runner/advance.rs:264), [live_timers.rs:142](/Users/admin/Developer/exact2-timer-wait-points/runner/tests/it/live_timers.rs:142).

   **D10 — Runner and hosts:** Test the 49/50 ms cancellation through both `release` and `frame`; a prerequisite precise action that starts a smooth scroll; and a prerequisite batch that enables a frame task while an idle timer waits.

2. **Specify refusal continuation without claiming every release makes progress.**

   **Where:** [D4, lines 205–207](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:205); [D6, lines 278–282](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:278).

   Keep the deliberate rule allowing non-idle held work after an ordinary timer refuses, but state its consequence:

   > A recoverable refusal stops the prerequisite advance. Eligible non-idle held firings may nevertheless run; ordinary work that the advance did not reach remains pending. This is an explicit exception to ordinary-work-first ordering. Idle cannot qualify while that work remains due.

   Distinguish a refused firing from `TimerFireLimit`. The latter is checked **before** consumption: [advance.rs:545](/Users/admin/Developer/exact2-timer-wait-points/runner/src/runner/advance.rs:545). It must not spend the next firing or grant an additional release budget.

   Adopt:

   > Prerequisite advancement and release share the turn’s firing budget. At the limit, return to the host and retain the unfinished cutoff; resume with a fresh budget and recheck host eligibility. Newly due work beyond that cutoff does not repeatedly overtake its remainder. A recoverably refused firing is consumed; an unreached firing remains held.

   Delete “Each release spends at least one firing.” A prerequisite commit can cancel every candidate, and a limit can prevent any firing. Recheck only while candidates remain and the relevant opportunity is available; do not recursively retry an empty release. Poisoning is terminal, not a recoverable release opportunity.

   **D10 — Runner:** Cover a refusing precise repeat, a refused held firing followed by another, a limit reached before the first held firing, cancellation of all candidates, and a resumed scroll before continuation. Assert consumption, remaining work, and ordering—not just the returned error.

3. **Give the seekable clock an executable scheduling definition.**

   **Where:** [D4–D5, lines 195–242](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:195).

   Distinguish each firing’s **nominal deadline**, **execution time**, and **repeat phase**. Rounding `next_ms` in place loses the deadline needed for ordering and the phase needed for repetition.

   Adopt:

   > On the seekable clock, a firing retains nominal deadline `D`. Its execution time is `D`, except for `wait=frame`, whose execution time is the least `F(k) >= D`, where `F(k)` is the binary64 evaluation of `k * 1000 / 60`, multiplication first. Select by execution time; among simultaneous task timers, put idle last, then compare nominal deadline and plan row. Preserve the existing `then`/`next` precedence, reconsidering them after every commit.

   Explicitly restrict D4’s “runs in a later advance” sentence to **live release turns**. Applying it to seeks would break the existing one-large-seek/equivalent-small-seeks rule.

   Specify rounding by correction against `F(k)`, not bare `ceil(D*60/1000)`. I reproduced:

   ```text
   D = 1000 / 60 = 16.666666666666668
   ceil(D * 60 / 1000) = 2
   ```

   Thus that obvious implementation skips an exact boundary. Estimate `k`, then adjust until `F(k-1) < D <= F(k)`. Do not narrow the absolute frame index to `u32`: the existing [helper](/Users/admin/Developer/exact2-timer-wait-points/runner/src/runner.rs:622) accepts that type, whereas the accepted clock range is much larger.

   A waiting repeat must select its next **nominal** beat strictly after execution/completion, including on seeks. Otherwise `every(1, …, wait=frame)` can replay sixteen nominal beats at one virtual frame. Lean currently advances an ordinary repeat by one interval: [Runtime.lean:519](/Users/admin/Developer/exact2-timer-wait-points/semantics/Contract/Runtime.lean:519). Its selector and JS’s selector also need the new execution-time comparator: [Runtime.lean:1090](/Users/admin/Developer/exact2-timer-wait-points/semantics/Contract/Runtime.lean:1090), [rt.js:316](/Users/admin/Developer/exact2-timer-wait-points/host/web-js/rt.js:316).

   **D10 — Semantics:** Extend the proposed corpus with exact frame boundaries and adjacent representable values, several deadlines rounding to one frame, `every(1, …, wait=frame)`, a fractional rearming time, `then` and queue `next` created by a firing, and equivalent split seeks.

4. **Make clock takeover atomic, including overdue timers whose deadline wake was skipped.**

   **Where:** [D6, lines 257–260 and 287–293](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:257).

   The host may skip a deadline wake. Consequently, “already held” cannot mean only timers an earlier advance explicitly marked held. Otherwise an overdue waiting timer can escape takeover normalization.

   Adopt:

   > At takeover, serialize with runner execution, sample the old live clock, and choose `R` no earlier than the runner’s current time. Materialize every implemented waiting firing whose deadline has passed, including those with skipped deadline wakes. Give each surviving firing one execution time at `R`, retaining its original deadline for tie-breaking and phase. No callback left from the old clock may release it.

   Define the treatment of **other overdue scheduled work** too: it must retain scheduling precedence without making a post-takeover commit observe a time before `R`. Do not simply leave overdue entries in the seek scheduler, which currently assigns a task’s deadline directly to `now_ms`: [advance.rs:586](/Users/admin/Developer/exact2-timer-wait-points/runner/src/runner/advance.rs:586).

   Cancellation alone is insufficient for callbacks already queued. Use a clock-ownership generation checked when callbacks execute, covering frame, timeout, idle, observer, animation-promise, and Android report callbacks.

   Retain consume-before-checkpoint behavior, and include all new held/deadline/cap state in rollback. Existing timer state is already checkpointed: [commit.rs:98](/Users/admin/Developer/exact2-timer-wait-points/runner/src/runner/commit.rs:98).

   **D10 — Runner and hosts:** Take over without advancing through a skipped deadline; mix held and overdue precise work; seek by zero; deliver stale callbacks; refuse a takeover firing; and return to live timing. Assert one attempted firing, monotonic observed time, and preserved phase.

5. **Define caps as bounds on intentional deferral, and correct the lost-beat claim.**

   **Where:** [D3, lines 169–184](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:169); [Open questions, lines 660–668](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:660).

   “Runs at its cap at the latest” is not implementable as a wall-clock guarantee. Browser timers explicitly permit scheduling delays; Foundation timers are also not real-time mechanisms. [HTML timers](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#timers), [Apple run loops](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/Multithreading/RunLoopManagement/RunLoopManagement.html).

   Adopt:

   > The cap is measured from the firing’s original deadline and never slides while held. At cap expiry the wait condition ceases to restrict admission: the firing becomes ordinary due work. The host schedules an independent cap wake. Execution may be later because the executor is unavailable or earlier scheduled work must run.

   Keep all numerical caps unchanged. Also remove the assertion that idle’s default lets an `every` lose at most one beat. With interval 250 ms, a firing held from 250 to its default cap at 1,250 ms merges five beats; its successor is 1,500 ms.

   Waiting callbacks must give `then` and `next` their **sampled commit-start time**, not their old nominal deadline. Existing precise callbacks intentionally propagate their scheduling instant through [armed_at](/Users/admin/Developer/exact2-timer-wait-points/runner/src/runner/advance.rs:96) and [scheduled](/Users/admin/Developer/exact2-timer-wait-points/runner/src/runner/advance.rs:720); reusing that path unchanged would violate D4.

   **D10 — Runner:** Test cap/wait-point races, delayed cap delivery, a cap hidden behind another uncapped timer, the 250 ms example, and a waiting callback whose start and completion differ. Check both `then` and queue `next`.

6. **Make `scrollend` mean an empty observed-activity set, with one canonical approximation policy.**

   **Where:** [D2, lines 132–146](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:132); [D7, lines 306–352 and 384–402](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:306).

   The quiet backstops are **sound approximation policies**, not proofs of completion. Keep them, but define them once:

   > `scrollend` becomes eligible when the session’s observed scroll-activity set is empty. Activity includes reported gestures and reported scrolling/scroll animation. On the web, unheld activity is retired by native completion, removal, the reported-offscreen policy, or sampled quiet: 1,000 ms with native `scrollend` support, 100 ms without it. Quiet retirement permits execution before a physical scroll has finished.

   Specify that quiet is measured from the last **observed** movement and evaluated at rendering callbacks while rendering callbacks are available. It cannot establish continuous physical stillness between observations. Feature-detect support; Safari versions belong in the evidence, not the algorithm.

   Three mechanism details need correction:

   - Keep gesture holds separately from movement. Lifting a finger must not erase deceleration; an old completion event must not erase a newer gesture.
   - Do not equate `pointercancel` or lost capture with physical lift. Browsers cancel pointer delivery when taking over a pan. Use touch lifetime where available; cancellation without a usable lifetime signal becomes an explicitly approximate observation. [Pointer Events suppression](https://www.w3.org/TR/pointerevents3/#suppressing-a-pointer-event-stream).
   - Remove unconditional retirement on a host scroll command. The saved Firefox result says the supposedly cancelling command **did not stop the scroll**. Existing quiet retirement already handles silent termination without this additional false-completion path. [Probe implementation](/Users/admin/Developer/exact2-timer-wait-points/experiments/timer-wait-points/web/probe.mjs:305), [§5 result](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:623).

   Define the session boundary: owned/reported scrollers, including viewport scrolling. If visual-viewport scrolling is included, listen on `VisualViewport` itself; its events have that distinct target. Opaque embedded documents cannot silently be included in a document-listener guarantee. [CSSOM event targets](https://drafts.csswg.org/cssom-view/#event-summary).

   **D10 — Hosts:** Extend the scripted set tests with pointer cancellation followed by a held finger, multiple touches, nested-scroller handoff, lift-to-deceleration, stale completion, and the Firefox replacement case. Retain both long-pause/resumption tests.

7. **Keep the covering observer, but stop calling its result “rendering has stopped.”**

   **Where:** [D7, lines 330–352](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:330); [lines 389–394](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:389).

   The covering element fixes the root-box and corner-pixel bugs. The saved three-browser results support that geometry. It remains an **asynchronous intersection observation**, not a rendering-state API: observations are computed during rendering processing and delivered through queued tasks. [Intersection Observer processing model](https://w3c.github.io/IntersectionObserver/#processing-model).

   Adopt:

   > The web host treats the session as reported offscreen when the document is hidden or the latest delivered observation of its viewport-covering target is nonintersecting. This is an admission policy, not a claim that rendering or scrolling has stopped. Before an initial observation, intersection is unknown and grants no offscreen exemption.

   Preserve the target’s viewport-containing-block assumption; if that assumption is invalidated, treat the observation as unknown. Process the latest observation before deciding, and recheck on visibility/intersection changes. Delayed reports during return onscreen remain an explicitly stated limitation.

   Delete the claim that the unseen-scroll window is bounded to one frame. Checking after scroll steps improves ordering, but does not impose a cross-thread delivery bound. Chromium expressly permits compositor scrolling without main-thread execution. [RenderingNG architecture](https://developer.chrome.com/docs/chromium/renderingng-architecture).

   **D10 — Hosts:** Retain the three geometry cases; add initial-unknown state, offscreen-to-onscreen return with delayed observer delivery, and a scroll report arriving after an admission check. Assert decisions against the recorded observations, separately from physical visibility.

   A callback cannot guarantee subsequent presentation, and a delayed deadline callback cannot reconstruct whether frames were being produced at the nominal deadline.

   Adopt:

   > `frame` runs at the next host frame opportunity whose sampled session time has reached the deadline, before Exact’s frame tasks, or through the existing no-display/cap rule. `update` checks demand at the first host scheduling check at or after its deadline. With demand, it waits for the next applicable update opportunity; without demand, it is eligible immediately.

   Exclude callbacks requested **solely to inspect waits** from demand. Otherwise scroll observation or Safari’s idle fallback can make `update` sustain its own frame requests. Define “one frame period” explicitly; the smallest portable choice for the recency/lookahead heuristic is the existing `1000/60 ms` constant, identified as a scheduling horizon rather than a predicted display interval.

   Apple’s passive mapping is sound; its broader detection is a platform capability. Older Apple systems and the web legitimately observe less. 9. **Make idle admission a sampled condition, and close its missing wakeups.**

   **Where:** [D2, lines 148–165](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:148); [D7, lines 354–366](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:354).

   The five terms are useful, provided they describe **known session work at admission**. They cannot establish that nothing is pending anywhere, or prevent newly arriving input from being delayed.

   Adopt:

   > At an idle opportunity, resample the clock and recheck all five terms immediately before admitting one firing. “Pending” and “coming due” mean work known to the session’s scheduler. Observation-only callbacks do not count as frame demand. After application, check again before another idle firing.

   Include every existing scheduler deadline in lookahead—not just authored timers and caps. [timer_due_ms](/Users/admin/Developer/exact2-timer-wait-points/runner/src/runner/gates.rs:100) already includes continuations, transport, polls, presence and other runtime work.

   Replace “keeps an idle batch from pushing back work” with “avoids admission when known scheduled work lies within the lookahead horizon.” Remove the blanket claim that platform queued work goes first. `IdleHandler` may run with future messages pending; Safari’s timeout merely yields a task boundary. [Android IdleHandler](https://developer.android.com/reference/android/os/MessageQueue.IdleHandler), [HTML task scheduling](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model).

   Animation completion promises are insufficient wakeups: pausing an animation or setting its rate to zero need not settle `finished`. Keep per-animation completion/cancellation notifications, recheck after host animation changes, and while an idle wait is blocked on document animations use one shared 100 ms timeout rescan, bounded by the existing cap. Re-enumerate animations at actual admission. [Web Animations pause and completion rules](https://drafts.csswg.org/web-animations-1/#pausing-an-animation).

   Finally, change “nothing … is moving” everywhere to reference this predicate: the draft intentionally ignores native compositor-only animations while conservatively counting web document animations.

   **D10 — Hosts:** Pause and zero-rate an already-blocking animation without finishing it; replace an animation while an idle callback is queued; start a frame task before that callback; and make a precise deadline enter the lookahead window. Test two idle firings where the first creates work.

The useful simplifications are:

- **Delete scroll-command retirement.** The existing quiet backstop handles silent aborts without a browser-specific assumption that the command succeeded.
- **Omit the `requiresContinuousUpdates = false` assignment.** False is already the documented default; adding actions and enabling the passive link avoids the measured setter trap.
- **Give D2 sole ownership of guarantees and approximations.** Summary, D3 and D7 should reference those definitions. Remove the now-decided alternatives from “Open questions,” and replace “at most one lost beat” with the actual phase rule.
- **Use one frame admission sequence.** Separate timeout, display-link and update-link paths should reach the same ordering rules.

The draft should carry this exception, once, wherever its guarantees are defined:

> Live waits govern admission according to host-observed activity. They do not guarantee physical quiescence, presentation, an available frame budget, or exclusion of scrolling that begins before its report arrives or after admission. Web quiet retirement and delayed offscreen reports can admit work during physical scrolling. Android publication and asynchronous replies may arrive during a later scroll.
>
> Caps bound intentional waiting, not wall-clock execution latency. Suspended, blocked, throttled or lifecycle-disabled executors can run later; Android currently disables its timer scheduler when the activity stops. Uncapped `scrollend` has no finite liveness bound during continuous observed scrolling or when required observations never arrive. Unsupported waits execute precisely under D6 and provide no wait guarantee.

That final uncapped exception is unavoidable while preserving the chosen design.
