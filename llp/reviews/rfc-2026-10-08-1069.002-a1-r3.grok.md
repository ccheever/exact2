## Blocker

**Unload never takes the right to write away.** A1.5 (`llp/1069.002-media-picker.rfc.md:268-279`) says a waiter that gives up calls `abandon_image_work`, so nothing is renamed after the guest is told the call failed and later storage never meets a late write. The 30-second path does that. Teardown does not.

`Module::unload` (`js/src/lib.rs:548-556`) gives background storage one second via `finish_background` (`js/src/background.rs:124-151`). That wait is `Session::wait_until` (`js/src/storage.rs:77-87`), which never calls `abandon_image_work`. On the deadline it logs `dropped at teardown` and returns. Dropping the session only stores `alive = false` (`js/src/storage.rs:183-186`). Dropping `Context` drops the last `OwnerLease` (`vendor/ibex/crates/ibex2/src/bindings.rs:531`, `task.rs:1306-1307`), and `release_owner` calls `shutdown` (`task.rs:932-939`). `shutdown` (`task.rs:861-911`) closes subscriptions, sqlite, and the completion wake. It does not touch `image_work`, and it does not cancel the pool job. The job's `Arc<RuntimeState>` comes from `clone_queue` (`task.rs:1806-1811`), which does not hold an owner lease (`task.rs:1288-1290`), so the job outlives shutdown.

The gate is still `Nothing`. `compress_image` writes unless the state is `Abandoned` (`vendor/ibex/crates/ibex2/src/stdlib/fs_image.rs:125-135`). After the rename, `ibex2_async_begin`'s worker sees `is_shutdown` and drops the completion (`vendor/ibex/crates/ibex2/src/boundary_abi.rs:919-924`).

A continuation that is already looping does not repair this. `Session::continuation` checks `alive` before the deadline (`js/src/storage.rs:95-99`) and returns `storage runtime was unloaded` without calling `abandon_image_work`. The "Written, wait 5 s more" branch (`js/src/storage.rs:115-118`) is skipped. Retirement of the Apple executor drops a queued continuation without running it (`host/apple/src/executor_core.rs:703-707`), so that path never abandons either.

Failing case: an answer calls `compressImage` of a large photo into `app:/tmp/out.jpg` and does not await it. A dev reload arrives while ImageIO is still decoding. `finish_background` gives up at 1 s. The new session writes `app:/tmp/out.jpg`. The old pool job then passes the still-`Nothing` gate and renames the JPEG back over it. The same thing happens for an awaited call whose continuation is parked on an I/O worker. If the atomic write has already set `Written` and shutdown lands before `queue.complete`, the success is discarded and the `alive` check reports failure for a file that is already on disk.

Fix: take the right away before the session is dropped. `finish_background`'s give-up and `RuntimeState::shutdown` should call `abandon_image_work` (shutdown once, at entry, before it returns). A job that has not entered the write then sees `Abandoned` and does not rename. A job inside `AtomicWriteFile` holds the gate mutex, so abandon waits for that rename and observes `Written`. Keep the completion for a `Written` call, or treat `to` as committed. Do not report failure from the `alive` check until abandon has returned, and do not report failure when it returns `Written`.

## What holds on the 30-second path

Registration, a call queued behind another, two compresses in flight, background storage, and the extra 5 seconds all hold while the session stays alive.

- The gate is created on the JS thread in `ibex2_async_begin` before `task_started` and `pool::run` (`boundary_abi.rs:895-930`). The 30-second waiter starts only after that call returns and the answer parks.
- The prelude issues the next operation only when it reaches the head (`js/src/prelude.js:992-993`, `702-711`). A queued call is not registered, and its waiter does not start, until then. A1.9's "job start is the clock" correction matches `Instant::now()` in `compress_image` (`fs_image.rs:90`).
- After a timeout, `__exact_storage_failed` marks the call lost and `landed` ignores a late settlement (`prelude.js:1399-1412`, `702-705`). The successor gets its own gate. `abandon_image_work` walks every gate (`task.rs:619-626`); the abandoned one cannot pass the check under the lock.
- The write holds that same mutex across `write` / `sync` / `rename` (`fs_image.rs:123-136`). Abandon blocks, sees `Written`, and the completion is queued before `end_image_work`. The extra 5 seconds covers that handoff.
- A post-reply round uses the same `continuation` (`js/src/background.rs:72-74`), so a 30-second background timeout does take the right away. Rust-source and web calls pass no gate, which is what A1.5 says.

## Web pixel limit

No format the web still admits was shown to decode past 64 Mi pixels before the check. HEIF/AVIF return null before `createImageBitmap` (`host/web/storage-image.js:132`, test at `host/web/storage-image.test.mjs:48`). JPEG SOF, PNG IHDR, the GIF screen and first descriptor, both BMP headers, and a still WebP `VP8` / `VP8L` size (the larger of that and the `VP8X` canvas) are read first (`storage-image.js:80-131`). A `VP8X` canvas over the cap is refused, and libwebp sizes its animation buffers from that canvas and rejects a frame rectangle outside it. The decoded size is checked again (`storage-image.js:173`).

## Should-fix

**The animated-WebP frame size is read from the wrong bytes.** A1.5 (`llp/1069.002-media-picker.rfc.md:236-237`) and A1.9 (`:442-444`) say the first `ANMF` frame is read. `headerSize` reads a 24-bit duration at `pos + 20` and the flags byte plus the start of the frame payload at `pos + 23` (`host/web/storage-image.js:114`). In the container those fields are duration and flags. The frame width and height are the 24-bit values at `pos + 14` and `pos + 17`. The guard `pos + 24 <= n` is also two bytes short of the second `le24`, so a truncated chunk throws from `DataView` instead of returning null. The Bun tests cover a `VP8L` larger than its canvas (`storage-image.test.mjs:67-71`) and never an `ANMF`.

Failing case: an ordinary animated WebP whose canvas is 100×100 and whose first frame duration or payload bytes look like a multi-million "side" is refused `too-large` and never reaches `createImageBitmap`. A duration of 0 with a zero flags byte can also fail `positive` and come back `undecodable`.

Fix: read width-minus-one and height-minus-one at `pos + 14` and `pos + 17`, require `pos + 26 <= n`, and take the larger of that rectangle and the canvas. Add an `ANMF` fixture whose real frame is small and whose duration is large.
