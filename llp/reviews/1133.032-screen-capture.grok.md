## Findings

### 1. Self capture has no prompt, no indicator, and no press

**Class:** MATERIAL

**Where:** D3 (lines 325–345), D4 (lines 371–387), D9 (lines 597–608)

**Problem:** On native, `getDisplayMedia(preferCurrentTab=true)` draws the session by the host's own rendering, including a guest iframe via `WKWebView.takeSnapshot`, and shows no prompt and no indicator. D4 then keeps that capture alive with no consumers: frames are dropped, but the host keeps snapshotting until `stopTrack`. The reason given is that a picker or MediaProjection consent cannot be spent twice. Self capture spends no consent, so that reason does not apply to it, and LLP 1133.008 D3's reopen rule could: stop when the last consumer leaves, and start again with no prompt.

D9 says a person chooses, because the name is `"origin": "person"` and `"gesture": true`. Neither check is a press.

- `CallOrigin::App` is "a person's input, or the app's own code in a foreground session" (`runner/src/runner/modules/admit.rs` lines 49–51). `"person"` refuses only a tool or a wake (lines 255–266). LLP 1133.025 D10 (lines 787–797 and 1260–1262) says `"person"` is that same test, including launch and timers, and that no module can require a gesture.
- `"gesture": true` is web dispatch timing. Native hosts do not enforce it (LLP 1133.013, line 754).
- LLP 1133.009 D9 (lines 749–764) already allows any foreground app code to start a capture, and relies on the platform indicator as the person's notice. Self capture removes that notice. A foreground timer can continuously snapshot the session, including another process's guest pixels (LLP 1020.002 D7 lines 569–570, D8 lines 582–585), with nothing on screen.

The picker path is a different case: a timer can raise it, and the person still chooses in the platform UI. Tier 2 is also a different case; its why-column only claims "never a tool's or a wake's," which `admit.rs` does.

The same origin word fails the RFC's own error. `"person"` returns `PERMISSION_DENIED` (`admit.rs` lines 263–265; `contract/cli/src/declaration.rs` lines 376–377). D9 (line 608) and drive 2 require `NotAllowedError`. `"origin": "app"` is the word that returns `NotAllowedError` with `person-required` (`admit.rs` lines 533–534 and 275–277). It still admits timers, so it is not the press gate.

**Fix:** Keep host rendering, and keep skipping the platform picker for the app's own pixels. Require a real press to start self capture on native, or show an indicator for the whole time the track is live. `"gesture": true` and `"person"` do not do this until admission grows a press-only cause. Apply never-idle only to a picker or programmatic capture whose consent cannot be renewed; self capture idles when the last consumer leaves. Use `"origin": "app"` so a tool or a wake gets `NotAllowedError`. Say the reopen exception in §11's amendment of LLP 1133.008.

### 2. Recording's permission check does not follow the stream

**Class:** MATERIAL

**Where:** D6 (lines 466–471); §11 (lines 978–980)

**Problem:** A list of grant lines is "any of" for the declaration check (`admit.rs` lines 460–465). The permission check is a different step. For a name with more than one line, `permission_of` selects the first permission whose grant the app declares (`admit.rs` lines 337–350 and 487–502). It does not read the stream or its track kinds. `permissionBy` only sees which arguments were passed, and `stream` is present for every recording.

`apps/recorder` already grants `device.microphone` (`packages/recording/exact.json` lines 6–8 and 50–52) and §9.3 adds `device.display-capture`. "Record screen" is then admitted against whichever of those permissions is listed first: a microphone prompt, or a failure if the microphone is denied, for a video-only take. A screen-only app happens to work, because an undeclared line is skipped. That is not a bypass. It is the wrong permission for the consumer this RFC adds.

**Fix:** Admit the recorder from the stream's track kinds. That needs a seam that resolves the handle, which D11 does not add. Do not cite `permissionAny` as that check. A separate name, or a `permissionBy` that can see the tracks, also works.

### 3. Web self capture under the substitute calls the real browser

**Class:** MATERIAL

**Where:** §8 (lines 739–766); §9.5 (lines 884–899)

**Problem:** The substitute "asks the platform for nothing and captures no screen," then says self capture "runs as in production" and "on the web the browser is asked as in production." A real `getDisplayMedia({preferCurrentTab: true})` without `--auto-accept-this-tab-capture` can show a picker and share a screen or a window. That is the hazard §9.5 forbids for `--use-fake-ui-for-media-stream` alone. Drive 5's flag is the right tool for one bound drive. The substitute bullet applies it to self capture in general.

**Fix:** The substituting web implementation draws the app's nodes (or the test card) and does not call `getDisplayMedia`. Real browser capture stays on drive 5, which requires `--auto-accept-this-tab-capture`.

### 4. Android self capture names a canvas API 29 does not have

**Class:** MATERIAL

**Where:** D11 item 2 (lines 673–674); D12 (line 715)

**Problem:** The Android host "draws the view subtree into a `HardwareBuffer`-backed canvas" on exact2's floor, API 29. There is no `Canvas` on a `HardwareBuffer`. `Bitmap.Config.HARDWARE` and `Bitmap.wrapHardwareBuffer` (API 29) are immutable and cannot be drawn into. `HardwareBufferRenderer`, which renders a `RenderNode` into a `HardwareBuffer`, is API 34. `PixelCopy` of the window does exist near this floor and would include occluding content, which breaks D3's independent rendering of the subtree.

**Fix:** Name a path that exists on API 29: draw the subtree into a software bitmap, then copy into the `HardwareBuffer` the frame source already delivers. Keep `ImageReader` for the projection path (D5).

### 5. `stopTrack` does not see a display track

**Class:** MATERIAL

**Where:** D4 (lines 373–377); D10 (lines 640–642); D11 (lines 660–667)

**Problem:** D4 says media-capture's names act on a display track unchanged, because the entry is in the shared table. Those names are implemented on media-capture's private map, not on `ExactTracks`. `stopTrack`, `setTrackEnabled`, and `mediaStreamTrack` consult `cameras.owns` or that private map and otherwise return `NotFoundError` (`packages/media-capture/apple/MediaCapture.swift` lines 86–99 and 143; the same split is in `packages/media-capture/web/index.js` lines 220–226 and `packages/media-capture/android/MediaCapture.kt` line 96). `ExactTrackOwner` only has `subscribe` (`host/apple/modules/ExactPackage.swift` lines 441–445). D11 adds a frame source and leaves this control path unnamed. §11 does not amend it.

The second video entry itself is the right seam. `ExactVideoSource` is an `AVCaptureSession` graph (lines 465–473), and a display capture has no graph. The separate package is also right: LLP 1133.001 D2 rule 3 (lines 195–200) is one implementation instance per module, and D10's amendment of "the only package that opens an input" matches that. The missing piece is how a media-capture name reaches an owner it did not open.

**Fix:** Give `ExactTrackOwner` stop, enabled, and state, and have media-capture forward those names through `ExactTracks.lookup` when its private map misses. List that on D11 and in §11.

### 6. `getMediaProjection` is specified before the service has called `startForeground`

**Class:** MATERIAL

**Where:** The Android start (lines 284–294); D11 item 3 (lines 677–695)

**Problem:** On `RESULT_OK` the module claims the foreground service and then calls `getMediaProjection`. The result callback runs on the main thread, inside `activityResult`, before `start` returns (`host/android/canvas/src/main/java/dev/exact/canvas/Extensions.kt` lines 504–518). `startForegroundService` returns before `onStartCommand`. `getMediaProjection` in that window throws the `SecurityException` the RFC quotes, because `startForeground` with type `mediaProjection` has not run. A `claim()` that blocks until `onStartCommand` deadlocks that same main thread.

Owning one host service, with a type union and install-time `android_normal` permissions, is the right seam, and question 2 is the right place to hand it to the roster. The call shape is what cannot work. Reaching past this module is not the defect.

**Fix:** Pass the result `Intent` into the service start. In `onStartCommand`, call `startForeground` with the live types, then `getMediaProjection`, then register the callback, then `createVirtualDisplay`. `claim()` completes when that has happened. Do not call `getMediaProjection` in the activity-result callback.

### 7. Drive 7's appop is not MediaProjection consent

**Class:** MATERIAL

**Where:** §9.5 (lines 908–916); drive 7 (line 868); against D4 (lines 382–384) and D9 (line 586)

**Problem:** The drive says `adb shell appops set <package> PROJECT_MEDIA allow` makes SystemUI grant consent with no dialog, citing `MediaProjectionPermissionActivity.java`: "Automatically grant consent if a system-privileged component is recording." That branch is a privileged system component, not this appop on an ordinary package. D4 and D9 already state the API 34 rule: consent every session, and each `MediaProjection` used once. A stored appop is what that rule stopped honoring. Drive 7 runs on API 34 and 35 images, so the unattended path does not establish a projection. The emulator's own screen as the fixture is allowed. The consent claim is not.

**Fix:** Drop the appop as consent. Drive the dialog with UiAutomator on the emulator, or cite a check that actually auto-returns `RESULT_OK` for a test package. Keep the ban on capturing this Mac's screen or a physical phone.

### 8. The usage string is on the grant the picker does not use

**Class:** MINOR

**Where:** D9 (lines 572–573); §9.3

**Problem:** `NSScreenCaptureUsageDescription` is derived only from `device.screen-recording`, the tier-2 row. The in-tree recorder and the clone's browser recording call `SCContentSharingPicker` and `SCStream` under `device.display-capture`, which derives nothing on macOS. WWDC23 10053, quoted at lines 263–266, says the picker does not need the separate Screen Recording permission. A missing purpose string is a different check: a bundled app that touches the API without the key aborts rather than prompting. The overview the RFC cites tells apps to add the key, and the binary that starts `SCStream` is the one that does not get it.

**Fix:** Stage 2 confirms the picker in a bundled app with no `NSScreenCaptureUsageDescription`. If that aborts, the key belongs on `device.display-capture` for macOS as well.

### 9. SnapShot's sample never calls the request name

**Class:** MINOR

**Where:** D7 (lines 499–515); §9.2 (lines 821–830); D9 (line 603)

**Problem:** `apple.shareableContent` and `apple.captureImage` are `"foreground": false` so the global shortcut can fire while another app is frontmost (LLP 1133.025 D11 item 3, lines 857–863). That part is right, and the why-column correctly limits itself to tools and wakes. The sample then calls those two names and never `apple.requestScreenRecording`. D7 also says that without the grant, `shareableContent` fails `NotAllowedError` and in practice the system shows its prompt. The first shortcut press is then a prompt from a name declared not to be a request, while the app is not foreground. The name that is a request requires the foreground.

**Fix:** The sample checks `apple.screenRecordingStatus` and, while `prompt`, asks with `apple.requestScreenRecording` from a foreground press. The shortcut calls only the capture names after `granted`.
