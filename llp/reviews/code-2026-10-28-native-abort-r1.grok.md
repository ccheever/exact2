## Findings

**1. should-fix — An abort is applied to whatever fetch currently occupies that target, so a reply that lands first makes the abort cancel the answer's next fetch.**

`js/src/lib.rs:759-766` turns the prelude ticket into a `Target` and drops the ticket. `runner/src/runner/admission.rs:122-138` later aborts the pending row whose target matches, with `continuation` and `stream` both empty, and pushes **that** runner ticket into `explicit_aborts`. It does not remember the ticket that was in flight when the abort was heard.

The abort is heard at the end of the turn (`runner/src/runner/commit.rs:1369`), after the pump has already chosen refusal or drain. Apple (`host/apple/src/abi.rs:349-370`) and the Linux presenter (`host/linux/src/presenter.rs:1330-1354`, also the Windows and Android presenter) alternate. `emit` / `service_commit` only cancel tickets already in `explicit_aborts` (`abi.rs:253-257`, `presenter.rs:810-814`), which is still empty on the turn that heard the abort. The answer waits for a later pump.

If that pump drains first and the aborted request's reply is already queued, `fulfill_now` removes that pending row (`commit.rs:1228`) and resumes the answer. `__exact_fulfill` is a no-op because the abort listener already settled the promise (`js/src/prelude.js:692`, `prelude.js:1444-1446`), then `__exact_settle` claims the next fetch of the same answer. `Answer::Later` enqueues it as a new ticket for the **same** target (`commit.rs:1403-1418`). The following refusal pump matches that new row and answers it `Failed { Aborted }`, and the host cancels that new ticket.

That next fetch is the ordinary one: a fallback after the rejection, or a second fetch the answer already started and had not claimed yet (native claims one fetch at a time). The reply has to be in the drain queue; a still-hung request takes the abort on the empty-drain fallback and is fine. The fast reply is the case this work is for, including a 429 already on the wire. The web host does not have this window: `host/web/src/host.rs:1016-1051` takes every aborted answer in the same `complete()` that heard it, before the resumed answer's new request is admitted.

Fix: at `hear_aborted`, record the runner ticket of the pending fetch for that target, and have `take_aborted_answer` fulfill and cancel only that ticket. If it is already gone, still hand that ticket to the host, and leave a newer pending row alone.

**2. nit — A lookup that panics never returns its helper.**

`vendor/ibex/crates/ibex2/src/transport/lookup.rs:111-118` increments the process pool (4), then calls `lookup()` and `free()` in the helper with nothing tying `free()` to the thread exiting. A panic drops the channel, so the waiter gets `Unanswered::Failed` (`lookup.rs:138-140`), and the slot stays taken until the process exits. Four of those and every later lookup waits out its abort or deadline without a helper ever freeing. The resolvers in tree (`rustls_http` and `websocket.rs:417-420`) return `Result` from `to_socket_addrs` and do not panic; a `defer`/`catch_unwind` around `lookup()` would make the bound actually hold.

**3. nit — The transport abort tests borrow the process-wide pool and return while the helper may still be in `getaddrinfo`.**

`rustls_http.rs:591-618` and `websocket_tests.rs:2147-2172` hold `Gate::hold_here()` on the global `SYSTEM` pool, abort, then `gate.open()` without waiting until `running() == 0`. The helper then resolves `resolving.invalid` on one of the four process slots. The unit tests in `lookup.rs:229-298` use their own `static POOL` and do wait until the slot is back. The 50 ms `!is_finished` check and the 500 ms abort bound fail only if the waiter does not wait, so they are stable; the shared pool is the isolation gap.

## The rest

**(a) Races, apart from finding 1.** An abort is not dropped on the floor. Every `take_logs` site also calls `hear_aborted` (`commit.rs:1369`, `query.rs:104`, `queue.rs:411`, `writes.rs:295`, `background.rs:131`). `has_request_refusals` is true while `module_aborts` is non-empty (`admission.rs:266-267`), and both presenters notify on that (`abi.rs:253-255`, `presenter.rs:812-814`). The web host answers inside `complete()` rather than waiting for a pump. The same ticket is not answered twice: the refusal pump and the drain pump are alternatives (`abi.rs:354-370`), and a reply that arrives after the abort fulfill hits `fulfill_now`'s missing-ticket drop (`commit.rs:1199-1204`). Continuations and streams are skipped (`admission.rs:125-128`); the prelude returns before door 22 for a stream (`prelude.js:564`). The ordered deque drops the cancelled ticket inside `cancel` (`executor_core.rs:748`); the lane count stays until the exchange ends, which is the latency the new paragraph describes.

**(b) Executor safety.** Clean. `Core::cancel` is `forget_with` with the explicit list (`executor_core.rs:683-686`). A queued explicit job, write included, is dropped and its count, stream bit, and `job.charge` come off once (`executor_core.rs:704-708`). A running one is marked forgotten and aborted through `Running.exchange`, which is set for a non-stream HTTP exchange and left empty for a stream (`executor_core.rs:1040-1041`, `735-745`). `run.abort` stays safe-read-only, so an ordinary `forget` still does not cancel a write. Completion of a forgotten job releases count and bytes once on the sync path (`executor_core.rs:1068-1077`) and once on the async path (`executor_async.rs:1098-1101` plus `physical` at `1158-1176`). A queued job is not also running, and a sync completion leaves `running` before it enters `completed`, so the two arms do not both subtract.

`exactBodyTo` writes a staging file and publishes only after a full 2xx body (`executor_body_to.rs:84-102`). An abort makes `read` fail, `receive` returns before `publish`, and `Staged`'s drop unlinks the temp (`app_fs_unix.rs:838-844`; the Windows impl does the same). The web file is one IndexedDB put of a finished blob (`storage-fs.js:489-501`); `close()` does not publish. Storage and native-module jobs have `work.is_some()`, so an explicit cancel does not drop them queued and does not set `exchange`; they finish as forget already let them finish.

**(c) Slot accounting.** Clean, and it matches the new paragraph (`docs/reference.md:1028-1039`). The runner's one-pending-per-target row (`source.rs:275-277`) is removed when the abort outcome is fulfilled, so the next ask of that target can be admitted at rejection. Executor `IN_FLIGHT` and `PER_ORIGIN` stay in `book.reserved` until `physical` (`executor_async.rs:1144-1146`, `1014-1025`), which is the "few milliseconds while the connection closes" caveat, not a leaked slot, provided finding 1 does not aim that cancel at the next request. The ordered count stays up until the same end, so a sync worker finishes the cancelled exchange before `ordered_idle`; the async machine claims `Claim::Cancelled` immediately (`executor_async.rs:1282-1289`), which is what `an_app_aborted_running_write_frees_the_ordered_slot_at_once` asserts.

**(d) Web.** Clean. `js/web` applies `aborted` before recording the turn's new fetch, and only while `waiting` is still the fetch (`js/web/src/lib.rs:339-348`). A let-go call drops `waiting` (`833-868`), so a late ticket does not name a target. `glue.js:714` aborts the controller stored for that ticket and `:760` deletes `byTicket` only when it is still that controller; tickets are monotonic. `exact-native:` is never entered. Door 16 removes the unsent request (`module-glue.js:134`, `module-worker.js:49`); an early GET that the turn does not report is aborted in `finish` (`module-glue.js:229-232`). The worker has no early fetch; its aborted tickets ride the turn envelope (`placed.rs:395-397`, `envelope.rs:123-129`), and a malformed entry is ignored. An abort does not consult incarnation; the fetch it closes was started under the incarnation that created that controller.

**(e) Lookup, apart from findings 2 and 3.** Clean. The waiter holds the count lock across the aborted-check and `wait` (`lookup.rs:86-102`); the abort callback takes that same lock before `notify_all` (`80-84`), and `free` decrements under the lock before notifying (`58-60`). An abort or a deadline while waiting for a helper returns before the increment (`88-106`). Spawn failure calls `free` and returns `Failed` (`120-124`). The thread name `ibex2-lookup` is 13 characters. A websocket lookup passes no deadline (`websocket.rs:417`); the HTTP resolver passes one. `getaddrinfo` itself cannot be cut short either way, and `Err(_)` on the socket path cannot be a timeout while the deadline is `None`.

**(f) Compatibility.** No bump. `RUST_ABI` and `TYPESCRIPT_RUNTIME` stay 4 (`bake/src/compat.rs:37-48`); `EXACT_ABI_VERSION` stays 16 (`host/apple/include/exact.h:35`). The policy bumps `TYPESCRIPT_RUNTIME` when a new prelude behavior is something a bundle cannot do without and an older prelude would ignore. Door 22 is the opposite direction: the new prelude calls it inside try/catch (`prelude.js:565-572`), and an unknown op is an error (`door.rs:241`), so an older door leaves the request running. An older prelude never sends 22. Op 19 remains presence (`door.rs:215-221`); 22 is the abort (`234-239`). The envelope's `aborted` array is additive.

**(g) Tests.** They prove the claims they state, and they do not reach finding 1. `js/tests/it/abort.rs` covers GET, POST, withdraw-before-claim, and an older door; `castle.ts:158-170` catches and returns, with no second fetch. The executor tests cover a running write cancelled, a queued write dropped, the async ordered slot, and a real socket close on Darwin and rustls (`executor_tests.rs:811-911`, `executor_async_tests.rs:373-396`). The realm test checks that the halting turn reports the prelude ticket (`module-storage.test.mjs:267-282`). The batch golden is the `"abort"` op. `scripts/abort-fixture.mjs:36-91` aborts a POST the server never answers, then a **later** action fetches `/next`, so the drain never contains `/held` and the next fetch is a new target turn. Nothing parks a second fetch of the same answer between the rejection and the refusal pump.
