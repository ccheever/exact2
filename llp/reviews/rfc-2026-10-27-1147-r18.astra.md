1. **The web’s visibility detector can release timers during an ordinary visible scroll.**

   [D7](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:324) treats a nonintersecting document root as stopped rendering and counts its moving scrollers as empty. But the shared shell sets [`html { height: 100% }`](/Users/admin/Developer/exact2-timer-wait-points/host/web/index.html:19). Its [`scroll document` rules](/Users/admin/Developer/exact2-timer-wait-points/host/web/index.html:375) let the body and content grow without removing that root height. Intersection Observer measures the target’s bounding box, rather than its overflowing descendants. [W3C intersection algorithm](https://w3c.github.io/IntersectionObserver/#compute-the-intersection)

   Consequently, on a 600-pixel-high viewport, scrolling a long document past 600 pixels moves the observed root box entirely above the viewport while its content remains visibly scrolling. D7 would release an uncapped `scrollend` timer immediately. Neither the long-pause exception nor the unobserved-first-frame exception covers this.

   The [iframe probe](/Users/admin/Developer/exact2-timer-wait-points/experiments/timer-wait-points/web/probe.mjs:366) observes a short, internally unscrolled child; D10 repeats that case. Neither exercises this geometry.

   **Instead:** Detect the embedded viewport’s intersection using a viewport-fixed observation target, and never infer that a visible top-level document stopped rendering merely because its root box left the viewport. Add a real `scroll document` fling beyond one viewport to D10.

2. **Simultaneously eligible wait kinds have no defined live-clock order.**

   [D4](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:198) orders held timers within their kind; [D6](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:269) releases one kind per call. Neither orders those calls when several conditions hold together. The existing [runner selection](/Users/admin/Developer/exact2-timer-wait-points/runner/src/runner/advance.rs:291) instead breaks equal deadlines by plan row.

   Consider an entirely still screen. Earlier-row timer A is gated on `enabled` and says `after(100, record, wait=scrollend)`. Later-row timer B says `after(100, disable, wait=update)`; `disable` clears `enabled`. Both waits are satisfied at 100 ms. Releasing `scrollend` first runs A; releasing `update` first cancels A. Both implementations satisfy D4–D7. The discrepancy occurs without any actual waiting or platform race, and D5 gives the seekable clock a definite result.

   D10’s [same-time ordering case](/Users/admin/Developer/exact2-timer-wait-points/llp/1147-timers-that-may-wait.rfc.md:483) covers only the seekable clock, so it would miss this divergence.

   **Instead:** Define arbitration across kinds eligible at the same wait point—for example, original deadline then plan row, with `idle` last—and add this cancellation case to the live-clock tests.
