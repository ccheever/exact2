## Blocker

**A failed `compressImage` can still rename onto `to`, and the new issue-time budget expires every call that was only waiting in the queue.** Amendment A1, A1.5 (`llp/1069.002-media-picker.rfc.md:243-258`), against `js/src/storage.rs:83-105`, `js/src/prelude.js:702-712` and `1373-1386`, `js/src/lib.rs:880-948`, `vendor/ibex/crates/ibex2/src/stdlib/app_fs_unix.rs:133-149`, and `vendor/ibex/crates/ibex2/src/pool.rs:31`.

A1.5 says nothing lands after the guest has been told the call failed, then leaves “a write begun before 24 s still running at 30 s” and calls a 6 s margin enough for an atomic write of at most `maxBytes` (64 MiB). The write it would call is `write_all`, then `sync_all`, then `rename`. `sync_all` has no deadline. The 24 s check, as written, happens before that sequence starts. At 30 s the continuation returns `"storage continuation timed out"`. `__exact_storage_failed` forces `code: "failed"` (it never reads `compressImage: timeout:`) and `landed()` starts the next queued operation. The pool runs other jobs beside the one still inside `sync_all` (up to 64 workers). The rename can land after the caller was failed, and after a later write to the same path.

Failing case: a trial finishes at 23 s with a 64 MiB JPEG, `atomic()` begins, and `sync_all` stalls past 7 s (a nearly full iPhone, or a simulator disk under memory pressure). The answer is `failed` / `"storage continuation timed out"`, not `timeout`. The next `writeFile` of that path completes. The stalled rename then puts the JPEG back. A1.4’s “on any failure `to` is left as it was” is false, and the queue order is false. A1.7’s stand-in (“a result ready after the commit budget writes nothing”) never enters `sync_all`, so it stays green.

The same paragraph starts the 20 s / 24 s clock “when the guest issues it, on the JS thread, before any wait can begin.” That waiter does not start then, and it does not cover the queue. `continuation()` starts a fresh 30 s when that closure runs. After each completion, `resume` delivers one operation and, if the answer is still pending, parks another continuation. The opcode is specified as four values (`llp/1069.002-media-picker.rfc.md:109-113`) and does not carry a deadline, so the pool job cannot see a timestamp captured before it was queued. The moment Ibex actually runs the call is when the prelude’s `issue` invokes the method, which is when the operation becomes head.

Failing case: `Promise.all` of four `compressImage` calls, which is what A1.5’s “four images are four calls” is. All four clocks start together. The first photo takes 12 s. The second has 8 s of trial budget left. If the first takes 20 s, the second is already past `TRIAL_BUDGET` when it starts and returns `timeout` without encoding. Each of those calls would have had its own 30 s waiter.

Fix: start both budgets when the pool job begins, which is the same moment as that step’s waiter. After `sync_all` and before `rename`, commit only if this operation is still the one the waiter has not failed. A failed operation must lose the rename. Surface `compressImage: timeout:` for that path. Add a test where the stand-in blocks inside the write, the waiter fires, and a following write to the same path is the bytes that remain.

## Should-fix

**An HDR HEIC drawn into an 8-bit sRGB context is not the SDR rendition A1.3 describes.** A1.3 (`llp/1069.002-media-picker.rfc.md:184-191`), against `host/apple/Sources/ExactKit/RasterImage.swift:383-395` and `407-411`.

The thumbnail options never set `kCGImageSourceDecodeRequest` to `kCGImageSourceDecodeToSDR`. This tree already does that for a non-HDR plan, because drawing a BT.2100 thumbnail into a bitmap does not tone-map the way a layer does. A1.8 keeps the picker’s gain map and says this call drops it. A PQ HEIC from the camera becomes a dark or clipped JPEG on Apple and a canvas SDR JPEG on the web. The fixture test (“the HEIC decodes”) does not look at those pixels.

Fix: decode with `kCGImageSourceDecodeToSDR`, then draw into the sRGB context. Pin a PQ or gain-map fixture against the web’s pixels, not only against “it decoded.”

**BMP and GIF “stored size” can pass the cap and still be decoded.** A1.5 (`llp/1069.002-media-picker.rfc.md:224-232`), against `host/linux/src/image/jpeg.rs:26-27` and `41-42`.

The header-before-`createImageBitmap` rule closes the round-1 case for a JPEG SOF or a PNG IHDR. Two formats the same sentence admits do not have one obvious size:

- BMP height is a signed 32-bit value; negative means top-down. `20000 * -20000` is not “more than 64 Mi pixels,” and `createImageBitmap` then allocates the frame.
- The GIF reader in this repo uses the logical screen, not the image descriptor. A 1×1 screen with a 9000×9000 descriptor is under the cap and is then decoded.

A 0 side also skips the one-pixel clamp. That clamp is only on the scale branch (`llp/1069.002-media-picker.rfc.md:124-125`). A header of `0×100` “fits” inside `maxDimension` and is requested as `0×100`. `OffscreenCanvas(0, 100)` throws, and the caller sees `failed` rather than `undecodable`. JPEG and GIF inspection here already reject a 0 side.

Fix: take absolute BMP dimensions, and the max of the GIF screen and its image descriptor. If either side is not a positive integer, or the header scan passes `exact_raster::MAX_HEADER_BYTES` (256 KiB) without a size, return `undecodable` and do not call `createImageBitmap`. Reuse that rule on the ImageIO property read.

**A1.9’s Firefox and WebKit argument does not hold.** A1.9 (`llp/1069.002-media-picker.rfc.md:380-384`), against `scripts/async.mjs:99-100`.

`conform-firefox` and `conform-webkit` run `host/web-js/conform.mjs` on the app list. None of those apps call `compressImage`. A green step never loads `storage-image.js`, never builds an `OffscreenCanvas`, and never takes the `imageOrientation` retry. “Recorded under As built as not verified” is not in that section. As built (`llp/1069.002-media-picker.rfc.md:483-485`) records the picker’s unverified paths only.

The iOS TypeScript omission does hold: `exact-render` is a `cfg(unix)` dev-dependency of `exact-js` (`js/Cargo.toml:35-36`) and it opens a `UnixStream` (`host/render/src/linger.rs:30`), so those tests do not cross-compile to the simulator. The codec and the Rust-source path on the simulator are the real coverage for ImageIO.

Fix: run `storage-image.js` once under Firefox and once under WebKit, the same way `conform.mjs` launches those browsers, including a worker. Until that exists, say those two engines are untested. Do not cite conformance.

## Nit

**“As it answers `stat` flat, and the prelude makes the record” points at the wrong converter.** A1.1 (`llp/1069.002-media-picker.rfc.md:109-113`), against `vendor/ibex/crates/ibex2/src/bindings/install.cc:1912-1948` and `1987`.

`stat` is not reassembled in the prelude. `filesystem_promise` runs only for opcodes 113 and 116, and it throws `"invalid filesystem stat"` unless the string has four tab fields. Opcode 121 left on that branch rejects `"width\theight\tsize"`. Leave 121 as a raw string and split it in the prelude wrapper, which is also where `path` and `type` are added. Do not add 121 next to 116.

## What holds

The round-1 web blocker, as a mechanism, is fixed: the size is read from the header, and an unread size never reaches `createImageBitmap`. JPEG SOF and PNG IHDR of 9000×9000 are covered. `doc:/` and a Windows native path are refused before `native::run`’s document and `native_filesystem` branches (`data/host/src/native.rs:251-262`), and before the same branch in `host/web/storage-request.js:46-51`, `host/web/storage.js:134-140`, and `host/web-js/ts-data.js:232-258`.

The `compress.ts` restatement matches the source. `Math.round` sends halves up, so the probes are 51, then 26, then 13. `q <= 13` resets the range and counts a shrink. The fourth shrink is computed and not encoded: 4000, 3200, 2560, 2048, and from 333 the tower 333, 266, 212, 169. One host call is the right place for that search. The one-pixel clamp is a real deviation and the pseudocode states it. Opcode 121 is free (`FS_ATOMIC_WRITE_FILE` is 120, `intl` starts at 130). Patch 9 is the right id; patch 8 is the Android Hermes target (`vendor/ibex/EXACT-PATCHES.md:125`).

Passing four scalars, copied before `storageCall`, avoids the `"[object Object]"` conversion in `install.cc`. A synchronous `TypeError` before `queued` / `storageCall` is the path that stays a `TypeError`. The 100 ms budget wraps only the Hermes turn (`js/src/lib.rs:100`), not an async opcode. `storage-environment.js` binds `Date.now` at evaluation (`host/web/storage-environment.js:6`), which in the worker is before the prelude replaces it (`host/web/module-worker.js:7` versus `init`). There is no JPEG encoder in the root `Cargo.lock`. `image` and `zune-jpeg` are only in the `game/` and `bench/` locks. Refusing Linux, Windows, and Android is justified. Not holding the web path lock across the encode matches `writeFile`: the lock covers the IndexedDB write, and a multi-second lock would be a new `EBUSY`.

## Verdict

**Yes. This still blocks implementation.** Do not build it until a timed-out call cannot rename, and until each queued call gets its own budget from the moment it starts rather than from the moment it was queued. The BMP/GIF header fields and the HDR decode request should be corrected in the same text. They are easy to implement wrong from A1.5 and A1.3 as they stand.
