Verdict: READY WITH CHANGES — the native projections are well chosen, but title semantics, projection precedence, and cross-host staging need explicit decisions before implementation.

**Strengths.** D1–D3 address concrete port failures without adding specialized tags. Reusing images, buttons, `popovertarget`, and menu roles is the right direction. D2’s separation of the screen’s heading from its principal content preserves navigation meaning while allowing richer presentation. D4 makes existing losses observable.

The main API choices check out: Apple documents replacement and resizing through [`titleView`](https://developer.apple.com/documentation/uikit/uinavigationitem/titleview), title-triggered menus through [`titleMenuProvider`](https://developer.apple.com/documentation/uikit/uinavigationitem/titlemenuprovider), and removal of shared glass through [`hidesSharedBackground`](https://developer.apple.com/documentation/uikit/uibarbuttonitem/hidessharedbackground). These support the architecture; they do not independently establish the reported iOS 27 geometry or large-title interaction. I did not reproduce the simulator probe.

The vocabulary is mostly defensible. `toolbarPlacement="principal"` is an established Exact extension borrowing a meaningful platform term; CSS alignment would describe a different thing. `light-dark()` is especially good: the current [CSS Color 5 draft](https://drafts.csswg.org/css-color-5/#light-dark) expressly accepts image pairs and `none`, and [Firefox 150’s release notes](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/150) confirm implementation. I prefer it over introducing `<picture>` solely for this use.

**Concerns and resolutions**

1. **BLOCKING — D2, D3, §4: title ownership is incomplete.**  
   Today, any title with a tap becomes a drawn title: [`HeaderTitle.drawn`](/Users/ccheever/projects/exact2-wt-review-1141x/host/apple/Sources/ExactKit/IOS/NavigationTitleIOS.swift:166) explicitly includes `tap != nil`. Simply expanding the shared rule to menu openers therefore risks selecting `HeaderTitleView` instead of UIKit’s title control. A custom control’s menu does not automatically establish UIKit’s title chevron.

   Specify separate paths for a plain system title menu and a genuinely customized title. Also settle principal-plus-title-menu: D2 replaces the visible title and overrides its press, while §4 proposes tapping both on one route. Use separate fixture routes unless coexistence is deliberately supported. Conflicts must produce a clear diagnostic or an accessible alternative.

2. **MAJOR — D3, open question 3: the recommended structure loses heading semantics.**  
   A button containing a heading makes that descendant presentational under [ARIA’s button semantics](https://www.w3.org/TR/wai-aria-1.2/#button). Make **heading containing button** the canonical authoring form, and recognize it consistently across hosts. The [APG’s interactive-heading pattern](https://www.w3.org/WAI/ARIA/apg/patterns/accordion/) demonstrates that ordering.

   Avoid silently restructuring only the web DOM: that changes selectors, event ancestry, and the relationship between authored and inspected trees. Existing wrapper syntax can remain recognized, but should receive an accessibility diagnostic. Test heading navigation, menu-button naming and expanded state, radio selection, keyboard operation, and focus restoration. Advising `aria-level=2` solely to obtain an inline presentation is also an unfortunate coupling of document hierarchy and appearance; describe it as the existing convention, not a general accessibility recommendation.

3. **MAJOR — D1, D2: the layout boundary needs a contract.**  
   A separately measured principal subtree is reasonable, but “like a top-layer root” leaves substantial behavior unspecified. Preserve authored ancestry for inheritance and events; preserve node identity; distinguish host suppression from authored `display:none`; and define containing-block dimensions, clipping, coordinate conversion, and invalidation when UIKit changes available space. It must not acquire popover dismissal, modality, or stacking semantics.

   D1’s permanent one-row rule also conflicts with LLP 1115’s protection of authored CSS layout. UIKit permits custom views; stacked text is not inherently unnative. Keep flattening as a diagnosed implementation limitation, or preserve the supported face layout. Do not make rasterizing text the prescribed repair.

4. **MAJOR — §3, §6: the stages can remove Android functionality.**  
   After D3 changes the shared rule, a menu-wrapped heading can become a projected header on Android. Its current [`read_bars`](/Users/ccheever/projects/exact2-wt-review-1141x/host/linux/src/presenter/bars.rs:250) builds a plain title and separate item targets; it has no title activation. The menu opener can disappear before stage 4 supplies its replacement.

   Land a usable fallback with every shared classification change. Mac’s whole-header fallback is sensible; Android needs an equally explicit guarantee that controls remain reachable. Test unsupported hosts at each intermediate stage. This RFC proposes no wholesale tab-controller migration; keep that separate. The immediate regression surface is header recognition and title projection.

5. **MAJOR — D1, §3: image semantics need more than a new drawing case.**  
   Specify original-color versus template rendering, one-dimension sizing, intrinsic dimensions, loading failure, and stale asynchronous completions after source changes or route removal. Both scheme variants must enter asset discovery and release packaging, including SVG capability requirements.

   Resolve by the **image node’s** used scheme consistently; D1 alternates between that and the page’s scheme. Define `none` precisely: CSS treats it here as a transparent image without natural dimensions, not removal of the element.

   On the web, CSS image-function support does not make the expression a valid [`img.src`](https://html.spec.whatwg.org/multipage/embedded-content.html#the-img-element). Choose an implementation that preserves `alt`, intrinsic sizing, `object-fit`, and load/error behavior, rather than silently substituting a CSS background.

6. **MAJOR — §1, §4, §6: measurement and verification are too narrow.**  
   In this draft, **stage 0 is D4 warnings**, not UIKit measurement. Add measurement before decisions dependent on observed behavior. Preserve the small probe within existing test infrastructure, with OS/build identifiers and results.

   UIKit alone is necessary but insufficient where SwiftUI’s `.principal` and `ToolbarTitleMenu` are the reference. Compare both on iOS 26 and 27, then exercise Exact’s integration. Include expanded/collapsed transitions, push/pop and cancellation, conditional principal insertion/removal, narrow widths, long localized text, RTL, Dynamic Type, and VoiceOver.

   Driver tests must deliver real platform input, avoid dependence on `_UINavigationBarTitleControl`’s private class name, and reject hidden or stale targets. Verify exactly one `press` per activation, current menu rows, and retargeting or disabling during activation—not merely that a provider exists.
