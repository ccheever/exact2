# Review of LLP 1069.010.000 (r1)

**Reviewer:** codex gpt-6-astra, reasoning effort max, run 2026-10-15 by Claude (Opus 5.5) for Charlie Cheever, read-only on the r1 draft over `9f4042a3a`, blind to the other two reviews. Scope given: foundational and directional questions only. The text below is the reviewer's final message, unedited.

VERDICT: ACCEPT WITH CHANGES

1. **Recent-history eviction must not revoke an open document.** D3 bounds the list; D4 makes eviction invalidate the path. Consequently, opening enough other documents can make an existing editor unable to read or save its document. Enabling `doc.keep` would introduce a restriction that session-only handles do not have. It also ties future workspace restoration to an unrelated recent-items preference. Separate live access, permission to reopen after relaunch, and recent-history presentation. Automatic eviction can end remembered reopening without ending an existing session’s access; deliberate revocation should be a distinct operation. A bounded host-managed recents list remains a reasonable default, but should not determine every document’s lifetime. ([RFC D3–D5 and §6](llp/1069.010.000-documents-that-outlast-the-launch.rfc.md:116))

2. **Automatically keeping existing handles can preserve substantially more authority than the person chose.** The parent’s implemented host routes turn a selected file into a handle for its containing folder, allowing sibling access. Applying D3 to those handles would make that entire subtree persist across launches, although D7 promises that persistence preserves exactly the selected document’s reach. This also carries forward the precise deviation the parent says cannot work under App Sandbox. Durable authority must follow the original selection: keep a selected file as a file, and preserve a subtree only after an explicit folder choice. Any broader transient navigation access needs to remain separate. ([Parent, “As built: slice 3 — The routes”](llp/1069.010-the-mac-as-a-document-platform.rfc.md:583); [data/src/documents.rs, `open_route`](data/src/documents.rs:97); [RFC D7](llp/1069.010.000-documents-that-outlast-the-launch.rfc.md:196))

3. **A saved Linux pathname does not preserve the selected folder’s identity.** If the chosen folder moves while the app is closed and another folder occupies its former pathname, restoring that pathname gives the old `doc:` identifier access to a different subtree. Never reusing the numeric identifier does not prevent this rebinding. It contradicts the existing containment guarantee that replacing a folder’s pathname cannot redirect access. Persist a reference that preserves the selected root’s identity, or verify that identity and require another selection when it cannot be recovered. Path-only restoration should not silently weaken the capability boundary. ([RFC D3–D4](llp/1069.010.000-documents-that-outlast-the-launch.rfc.md:116); [Parent, slice 3 “Containment”](llp/1069.010-the-mac-as-a-document-platform.rfc.md:555))

4. **User revocation is not guaranteed on every host.** D7 promises that the person can always revoke, but outside macOS and browser settings it relies on the app exposing `forgetDocument`. D5 supplies a programming interface, not a guaranteed user action. An app that omits that control leaves the person without the promised revocation path, while the protected store is intentionally inaccessible through ordinary app storage. Since revocability justifies the narrow durable-grant exception, provide a host-controlled way to inspect and revoke remembered document access on every participating host, independently of the authored interface. ([RFC D5–D7](llp/1069.010.000-documents-that-outlast-the-launch.rfc.md:159))

5. **Change notification does not solve the stated lost-update problem.** An external write can occur after the app’s final `stat` and before its save, regardless of whether notifications are coalesced or delivered individually. Re-reading also needs an explicit relationship to the editor’s unsaved work. The proposal motivates watches as preventing destructive overwrites, but §8 defers conditional writing until somebody loses a write. Keep the watch model, but make conflict handling part of the editor acceptance criteria: preserve unsaved work, detect divergence, and define how saving proceeds when versions conflict. If stronger save protection remains deferred, stage 1 should be accepted as freshness support with the overwrite problem still outstanding. An event stream would not eliminate this race. ([RFC §1 and D1](llp/1069.010.000-documents-that-outlast-the-launch.rfc.md:11); [RFC §8](llp/1069.010.000-documents-that-outlast-the-launch.rfc.md:255))

Both problems are real, and watches before durable handles is the right staging.  
[LLP 1016.002’s pull/coalescing model](llp/1016.002-changes-the-device-announces.rfc.md:33) fits these current-state consumers; they do not need an ordered filesystem event log.  
Stable `doc:` identifiers, host-controlled minting, existing file grants, declared recents deviations, and the explicit DEFERRED gate are sound foundations.
