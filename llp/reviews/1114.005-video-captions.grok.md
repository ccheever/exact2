I'll review LLP 1114.005 for directional and architectural issues only. First I'm reading the parent LLP, the RFC, and the rules it depends on.## Verdict: RIGHT WITH CHANGES

## Overall assessment

The rulings Charlie is asked to make are the right ones. Bluesky's captions ride inside the HLS playlist (`app.bsky.embed.video#view` has no caption field; the record's `text/vtt` blobs are written in by the video service), and exact2 already hands a stream's alternate tracks to the engine (LLP 1042 §2). Confirming that on each host, exposing it in `state.media`, and letting the composer pick a `.vtt` is the work the clone needs. Building `<track>` now would implement a sidecar design Bluesky does not use. Two sketches in the "later" design should not be left standing: the selection API cannot see these captions, and the native `<track>` path takes on a second WebVTT layout engine.

## Concerns

**1. MAJOR — D3 (b) cannot select the captions this LLP is about.** `track … mode="showing"` is a writable projection of a `<track>` element's `TextTrack.mode`. An HLS subtitle rendition has no element (the RFC says so, §4). Bluesky's own web player never uses `<track>`: hls.js reports `SUBTITLE_TRACKS_UPDATED` and a custom CC button sets `hls.subtitleTrack` (`VideoEmbedInnerWeb.tsx`). A feed player without native controls — the shape of that player — would need to choose an in-band rendition. D3 (b) does not do that, and it is still the recommended API "with stage 2." Adopting it means the next CC button needs a second mechanism. **Resolve:** keep (a) for now. Do not adopt (b). If a drive shows a host that plays the playlist but offers no subtitle menu, the control is a choice on the `video` (which rendition is showing, or off), covering in-band and sidecar the same way.

**2. MAJOR — D4's Apple path is a second caption layout engine.** AVFoundation still will not attach a sidecar WebVTT to a progressive MP4 (Apple's own guidance is to rewrite an HLS manifest, which a plain MP4 is not). Drawing cues in `contentOverlayView` is the right family of workaround. Parsing `line`, `position`, `size`, `align` and the `b`/`i`/`u`/`c`/`v`/`lang` spans, then comparing screenshots with the browser, is the WebVTT cue model minus regions. That model is the browser's, and it is not a 700-line port. Exact would own layout that drifts from the parity oracle. **Resolve:** leave `<track>` deferred, as question 1 says. If a progressive-file consumer ever appears, native hosts draw the cue text in the system caption style (`MACaptionAppearance`) and say what they ignored. The browser keeps the real `<track>` renderer. Cue-placement parity is not the bar.

## What it gets right

- The clone's playback path is the playlist with `controls`, not a sidecar. Stage 1 is a drive, then observation, not a media-selection layer that would duplicate AVKit and Safari.
- `state.media` is the agent's channel (LLP 1012 / LLP 1042 §3). Tracks and the showing cue text belong there. `clock +N real` is the existing way to let the media clock move.
- D5 splits the picker from document registration. `file_handlers` would make the app a `.vtt` viewer (`DOCUMENT_UTIS` in `scripts/app.mjs`, LLP 1069.002 D1). A picker-only `text/vtt` does not. The upload stays clone work: the blob is at most 20 KB, and `uploadBlob` must send `text/vtt` (Bluesky drops any other type).
- No new grant. A track `src` would be a view source, same as `video src`. The kernel stays childless for `video` (`kernel/src/node.rs`). Firefox with no HLS, and Linux and Windows with no playback, stay out of this LLP.
- Question 1's recommendation matches `rules/DEFERRED.md` and LLP 1098: `track` waits until a consumer plays a progressive file with a sidecar.

## Questions for Charlie

Questions 1 and 2 are framed correctly. Do not move `track` yet. Do admit `text/vtt` in `accept`.

Do not treat D3 (b) or D4's cue-layout scope as decided by accepting this RFC. No new question is needed unless the stage-1 drive fails. If a host plays the HLS playlist and does not surface its subtitle renditions (desktop Chrome is the one the RFC already marks unverified), the follow-up is in-band selection and display on that host, not `<track>`.
