1. **must-fix** — `host/apple/Sources/ExactKit/IOS/NavigationTitleIOS.swift:331`. `tablistHidBar` is set only on the root path (`:358`), and the pushed-route `setTabBarHidden` never updates it. `hidesBottomBarWhenPushed = false` does not clear `tabBarHidden`.
   Hide the tablist on Home (`setTabBarHidden(true)`, `tablistHidBar == true`), then push Detail. That batch already sees the tablist shown (`choosing` applies only at Home), so the loop sets `hidesBottomBarWhenPushed = false` and then `continue`s at `:330` because Detail is not top yet. `didShow` settles only when the root is top (`:367`). Detail's `tablistHidden` is now `false`, so a later batch does not enter the loop either. The bar stays hidden over a shown tablist.
   The other direction is the same latch. An in-place hide on a pushed route (`:331`, the route already top) leaves `tablistHidBar` false. A pop onto a root whose tablist is shown runs `settleTablist` and does not call `setTabBarHidden(false)`. `tablistHidBar` does matter there: a hide done with `setTabBarHidden` is the controller's stored `tabBarHidden`, and the pop does not clear it. A hide done only with `hidesBottomBarWhenPushed` still comes back on its own.
   **Fix:** On the pushed path, whenever Exact calls `setTabBarHidden`, set `tablistHidBar = hidden`. In that same loop, if the selected route wants the bar shown and `tablistHidBar` is set, call `setTabBarHidden(false)` and clear the flag even when that route is not top yet (`transitionCoordinator == nil`). Assert both cases in the test (finding 4).

2. **should-fix** — `host/apple/Sources/ExactKit/IOS/NavigationTitleIOS.swift:358`. A hidden wish sets `tablistHidBar = true` even when the bar was already hidden, so Exact takes ownership of a hook's hide. Hook hides the bar while the tablist is shown (flag stays false, and that part stands). The tablist then goes hidden and back to shown: the second change takes the `else if tablistHidBar` branch and shows the bar.
   **Fix:** Set `tablistHidBar = true` only inside `if !tabs.isTabBarHidden`, where this call actually hides the bar. An arrival that still wants the bar hidden re-hides it when a hook has shown it in between, because the bar is visible again.

3. **should-fix** — `host/apple/Sources/ExactKit/IOS/NavigationIOS.swift:109`. `tablistHidBar` and `tablistRoot` survive `retireTabs` (`NavigationTabsIOS.swift:302`) and the swap to the app's container (`replayTabs`, `:183`). Route controllers are reused, so the weak `tablistRoot` still points at the same root. After the containers are built again, `installTabs` runs `prepareRoutes` before `tabController` exists, which records the wish and returns. The later `prepareRoutes` in that same sync sees `changed == false` and `tablistRoot === root`, so `arrived` is false and the new bar stays visible under a hidden tablist. The app's container itself is left alone (`tabBarShows` is false), which is right, but the stale flag is still there if Exact's controller comes back.
   **Fix:** Set `tablistHidBar = false` and `tablistRoot = nil` in `retireTabs` and in the `replayTabs` branch that drops Exact's controller. The next at-rest root then counts as arrived and applies the current wish to the new bar.

4. **should-fix** — `host/apple/tests/ExactKitTests/NavigationBasicsIOSTests.swift:204`. `until { tabs.isTabBarHidden }` after the pop also passes when the bar never reappeared. The push of Detail while Home is hidden (`:201`) never asserts that Detail's bar is visible, which is finding 1. There is no case that flips the tablist to hidden while a pushed route is already top and then pops to a shown root.
   **Fix:** After Detail settles, assert `!tabs.isTabBarHidden`. Drive an in-place hide on a pushed route (`setTabBarHidden` at `:331`), pop to a shown root, and assert the bar is visible once `transitionCoordinator == nil`.
