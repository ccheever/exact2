# Review round 1, LLP 1121 stage 10 A2 (pairing), Astra (gpt-6-astra, max), security review

Reviewed: d2cb3414a1 (each finding fixed in the next sha; the landed A2 is the last re-checked one, rebased).

Three blocking issues in `d2cb3414a1`. Reproduced with read-only, in-memory Bun probes.

- **BLOCKING — Revoke/expiry does not invalidate pending requests.** [tamber-server.mjs:516](/tmp/rv-rl-a2/scripts/tamber-server.mjs:516) authenticates before awaiting readiness/body, without rechecking afterward. Completing a body after revoke dispatched a transaction with **200**; subscriptions and immediate polls disclosed fresh snapshots. A waiting poll instead hit an uninitialized `poll` callback at [580](/tmp/rv-rl-a2/scripts/tamber-server.mjs:580). Async continuations also need protection: revocation during [scrub-release’s hook](/tmp/rv-rl-a2/scripts/tamber-scrub.mjs:227) still allowed its write. Carry the authenticated principal through pending work and check cancellation before effects or disclosure.

- **BLOCKING — Paired identities can collide with local identities.** [tamber-pairing.mjs:214](/tmp/rv-rl-a2/scripts/tamber-pairing.mjs:214) allocates names against paired clients only; local client IDs permit arbitrary strings. A local proposal owned by `reviewer#1`, followed by pairing with `name: "reviewer"`, gave the remote that same identity. Its **propose-only token successfully dropped the local proposal**. Ownership and private-stream filtering need identities that cannot collide across local and paired clients.

- **BLOCKING — Remote/tunnel flags do not protect the token endpoint.** [tamber-server.mjs:505](/tmp/rv-rl-a2/scripts/tamber-server.mjs:505) handles token/tool routes before checking those flags. With `{local: true, tunnel: true}` or `{local: true, remote: true}`, unauthenticated `GET /__tamber/token` returned the local token. Make remote/tunnel status override `local` consistently. B’s documented flags alone currently do not enforce “only pair.”

- **SHOULD-FIX — Revoked proposal markings disappear.** [tamber-server.mjs:627](/tmp/rv-rl-a2/scripts/tamber-server.mjs:627) marks only proposals currently in the map. I reproduced both an in-flight proposal completing unmarked after revoke and a partial acceptance recomputing a marked proposal into an unmarked replacement. Preserve the revoked state when creating/restoring proposals at [934](/tmp/rv-rl-a2/scripts/tamber-server.mjs:934).

- **SHOULD-FIX — Pairing permits unbounded retained state and rejection telemetry.** [tamber-pairing.mjs:145](/tmp/rv-rl-a2/scripts/tamber-pairing.mjs:145) never sweeps idle peers: 1,000 one-shot buckets remained after advancing ten minutes. Many IPv6 peers can grow this without authentication. Every rejected attempt also logs/broadcasts at [202](/tmp/rv-rl-a2/scripts/tamber-pairing.mjs:202), bypassing any limit on that work. Separately, `revokedTokens`, `ended`, and name counters grow for the run; closing streams can recreate deleted presence entries. Bound retention and rejection telemetry. The `ends` map itself is deleted correctly on termination.

- **SHOULD-FIX — Malformed tokenless input escapes the handler.** [tamber-pairing.mjs:172](/tmp/rv-rl-a2/scripts/tamber-pairing.mjs:172): `{"code":{"toString":null,"valueOf":null}}` throws during coercion, producing an unhandled request rejection instead of a controlled response. Validate code type and length before normalization.

- **SHOULD-FIX — Advertised lifetimes above 24.9 days expire early.** [tamber-pairing.mjs:220](/tmp/rv-rl-a2/scripts/tamber-pairing.mjs:220) clamps the timer to `2³¹−1` milliseconds and then expires unconditionally. Thus `30d` lasts approximately 24.855 days. Rearm against the remaining lifetime; test timer-driven expiry as well as lookup-driven expiry.

- **NIT — Tighten the C/B contract.** [Interface comments:108](/tmp/rv-rl-a2/scripts/tamber-pairing.mjs:108) should specify synchronous `onEnd` invocation for an already-ended client, trusted/canonical `access.peer` values, and IPv4-mapped/IPv6 normalization. Keys are currently used verbatim. [Protocol:181](/tmp/rv-rl-a2/docs/tamber-protocol.md:181) should describe burst-five/refill-five-per-minute semantics; this is not a strict rolling-minute cap. Burn logs also omit the promised peer.

What checks out: unbiased 50-bit generation, full-length constant-time code comparisons without early loop exit, 256-bit tokens stored by SHA-256, and constant-time local-token comparison. Normal credential flows do not expose secrets in lists, events, URLs, or server logs. Cookie authentication is absent. Body `client`, `scope`, and `local` spoofing does not override the authenticated principal, apart from the identity collision above. Normal revocation clears subscriptions, polls, pins, inspect, outlines, holds, and external callbacks; `ended` defeats the 35-second presence grace. The revoked-token 401 oracle is acceptable given token entropy.

Five failures globally burn every live code, so additional peers do not expand a code’s guessing budget. Minting/redemption is synchronous; the eight-code cap and replacement preserve that bound. **Five unauthenticated requests can nevertheless destroy all pairing codes**—an availability tradeoff inherent in the explicit ruling.

The [new tests](/tmp/rv-rl-a2/scripts/tamber-pairing-server.test.mjs:98) miss these races, identity collisions, tunnel/local flag combinations, malformed codes, retention, and long TTLs. They also omit inspect/outline/hold cleanup, actual scrub restoration, and timer-driven expiry of open streams. Fixed sleeps weaken the revoke test.
