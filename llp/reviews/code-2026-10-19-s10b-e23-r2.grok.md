## Blocker

**Tokens that share a dial but not a value, and a dial the checker refuses, are dropped instead of pinned.** `tamber/src/export.rs:1043` and `tamber/src/export_dials.rs:157`.

`candidate` returns before any literal `SetToken` is built (`export.rs:1052` `continue`). `dials` then unmaps every token in the group when the values differ (`export_dials.rs:157-165`), when `SetDial` fails alone (`197-207`), or when the sets fail together (`210-218`). The proposal's `ops` stay empty.

Same value is correct: one `SetDial`, `from` in candidate order (`accent.fill`, then `accent.line`). Different values are the case theme2 left as a pin. `accent.fill = accent` → `#ff0000` and `accent.line = accent` → `#0000ff`, with anything else still following `accent`, checks as two literals marked `no longer follows accent`. Today both are only an unmapped note, which `two_tokens_on_one_dial_agree_or_are_reported` locks in. A refused `SetDial` has the same hole: the sole-consumer fix correctly tries the dial before the literal, then throws the literal away if that try fails.

Fix: plan the literals first. Drop them only for tokens whose dial was actually adopted. On disagreement, a lone refusal, or a together-refusal, keep those literals and let the existing trial pin them or report `tamber-dial-inert` when the design really refuses.

## Should-fix

**A new `when` takes `follows` from one line for both scheme sides.** `tamber/src/export_dials.rs:250`.

An existing `when` is replaced from its own text, and `sides` correctly keeps a side the literal still names (`light-dark(day, #f00)` still follows `day`). Whole-word matching is right: `.`, `-`, and `_` are word characters, so `accent` does not match inside `accent.fill`.

A new `when` does not use `branch`. It takes the narrowest existing `when` whose conditions are a subset, and runs that text through both sides. On an axis `under scheme=dark` the light winner is a different line.

```
ink = day
  when dark-style=dim: light-dark(white, night)
```

A narrower `when brand=loud, dark-style=dim` whose value is `light-dark(day, #ff0000)` marks `white` and `night`. The shown light side followed `day` and still does. `white` sits only on the dark `when`'s unselected light side, which the checker folds (`fold.rs:299-303`) so it is in `checked.names`. The same path misses `day` when the selected line writes `#ffffff` and the light winner is the dial `day`.

Fix: for each scheme side, take the old text from `branch(decl, under, modes, dark)` on the tuples that `when` covers, then diff that side against the new side.

**A baseline whose axes or contexts are not the design's is a 400 source refusal, not 409 `pull first`.** `tamber/src/export.rs:738` and `scripts/tamber-server.mjs:1108`.

## What holds

The "line is the dial" test is the winning line's whole text, default or `when`, not only `decl.value`. One scheme side changed is a pin (`light-dark(accent, #ff0000)` follows `accent`). A `light-dark(...)` line is an expression, so it stays a pin. A token whose default is the dial and whose other `when` is not becomes a `set-dial` only when every context that dial line wins changed to the same literal; editing the other line as well leaves the token as literals and does not veto another token. A role written as the row (`AccentColor = accent`) uses that same rule. The `-exact-` spelling still fails the older name lookup, before `candidate`.

Impact is that `SetDial` alone, in design token order, tuple index order. `label` matches `Folding::tuple` (first axis slowest). `before` / `after` are `Value::css` (`#rrggbbaa` or `light-dark(...)`). A sibling pin does not mask it. Tokens that do not move, including `surface.raised` on `lift` only, are absent.

Pins run on the ops that survived the trial. Re-import only emits `SetDial` and `SetToken`. `SetDial` is skipped. A token the trial refused is not in `ops`.

A `baseline` is export text, not a path. `importHeld` overwrites `recognised` with this run's export digests (at most 64). Rust also accepts a kept export and the current design's digest, so a restart still recognises those. An unknown digest is one 409 `pull first`. A non-string is 400. A baseline on shadcn is 400 before the digest check. The body limit reserves `64 + 64 * 72` bytes; a digest is 16 hex characters, so the reserve covers `recognised` and the request id. Ops are the file diffed against that baseline and applied to the current design, so a token the file did not change produces no op and another client's edit stays. A forged body wearing a real digest can only add ops the review shows.

`import-plan` always has `dials` and `pins`. The held review adds each only when non-empty, so `importTheme` and shadcn/tailwind reviews stay as they were. `export`'s `digest` is additive. `scripts/tamber-dtcg.test.mjs` reads the digest inside the DTCG document. The design tool ignores the new review fields and renders a `set-dial` with the existing `accent = #ff0000` text. It still does not show impact or `follows`; this commit leaves that to the design-tool pass.
