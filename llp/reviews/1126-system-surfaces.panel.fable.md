## Question A — the word

**Recommendation.** Do not coin an umbrella word. Name entries by the platform's own kind names and use the repository's existing word, *entry*, when prose needs the genus:

- `app.json`: top-level `widgets` and `live_activities` (snake_case, beside `protocol_handlers`, `file_handlers`, `launch_handler`), not under `host.ios`. A complication is a widget with accessory families, so it is a row of `widgets`, not a third key. Snippets are App Intents, a different class; they get their own key when their RFC comes.
- Contract: nothing new. The admission profile stays `snapshot`, a compiler-facing class name like `terminal`. The environment WidgetKit hands a render (family, rendering mode, colour scheme) is "a read-only fact about where the app is running", which is exactly what `exactSurface(name)` already means (`docs/contract-for-agents.md:2361`; the terminal publishes `exactSurface("terminal")`), so `exactSurface("widget")` reuses the existing word in its existing sense.
- The agent: address by kind, `agent.mjs ios widget <name> --family systemSmall tree screenshot`, `activity <name> --placement compact`.
- Prose: "a widget entry", "an activity entry", "the app's entries outside its window". Reserve *surface* for the places (Home Screen, StandBy, CarPlay, the Dynamic Island), which is how Apple uses the word and what the RFC's title already means. Never for the entry. Do not rename the canvas use.

**Confidence.** 80%.

**Reasoning.** The test in the brief is "a word an agent guesses with no teaching". An agent asked for a Home Screen widget types `widgets`; asked for a Live Activity it types `live_activities` or `liveActivities`; it would never type `glance`, `placement`, `outlet` or `satellite`. "Widget" is also Apple's own umbrella at the API level (WidgetKit's `WidgetBundle` holds widgets, `ActivityConfiguration`s, `ControlWidget`s and watch complications), Android's (Glance app widgets), Windows' (the Widgets Board), and, as far as I know, the Web App Manifest's own incubated member is spelled `widgets` (Microsoft's PWA widgets; I am not certain of its current standing). "Write the web, ship the platform" points the same way. "Surface" is now in five author-facing senses in this repository (canvas `surface=`, `exactSurface`, Tamber's `surface.card`, DEFERRED's platform sense, `ExactSurfaces`); a sixth is the one an agent would guess wrong, because to Apple a surface is where a widget appears, not the widget. "Extension" is taken by LLP 1124 and, on Apple, names the binary that holds many widgets, the wrong granularity. "Placement" the RFC already uses correctly for an activity's regions (D9). `live_activities` rather than `activities` because `Activity` is Android's screen class, and D13 wants the entry portable. Note that Charlie's own DEFERRED amendment already speaks this vocabulary: "An app's widgets, Live Activities and complications are entries of the one app"; the RFC should adopt its ruling's words. Why top-level rather than `host.<x>`: the terminal went under `host.terminal` because the terminal is a medium; a widget is realized by the iOS, macOS, watchOS and Android hosts alike, like a protocol handler.

**What would change my mind.** If stage 1's spec shows widgets and activities share nearly every field (root, props shape, refresh) so that one list with `kind` is cleaner, keep one key, and let it be `widgets` with `kind: "activity"`, since WidgetKit itself files activities there. If Charlie wants one spoken word for the genus that is not "entry", I would take "widget" as the umbrella in prose before any invented word.

## Question B — Live Activity pushes

**Recommendation.** Admit now, for stage 2, scoped to ActivityKit tokens: the update token and the push-to-start token (iOS 17.2+), both. An activity entry declares `"push": true`; the build adds `aps-environment` and the extension's `NSSupportsLiveActivities`; the token stream is a device fact the data module reads (a `native.watch` topic or a reserved source) and sends to its own backend with its own `net.fetch`. exact2 relays nothing and the payload is D9's envelope, whose JSON Schema the bake already emits for the backend. Stage 2 is not done until a push updates an activity on a locked phone with the app killed. Remote notifications do not come with it.

**Confidence.** 70%.

**Reasoning.** Question 7's ruling changed question 5's answer. "The first consumer needs no push" (D9) was true of Caltrain's countdown and is false of Interview, whose natural activity is server-side (an `aiJobs` answer being written, an answer arriving). A Live Activity the running app alone updates goes stale the moment the app is suspended, which is precisely when a Live Activity is looked at; someone who knows the platform notices, so it is a tell at the level of the feature (LLP 1115's test). Without push, stage 2 for the ruled consumer is a demo. The refusals do not bite on what is being admitted: DEFERRED's "service half … push delivery" and "push delivery from a server" were written about an update console and about notifications delivered to app code; here exact2 runs no service and relays nothing (LLP 1030.000 D6 already allows "a developer's own push"), no app JavaScript runs on receipt (the system replaces the state and the extension re-renders D3's pure function), there is no permission prompt, no action, reply or badge, and the 4 KB bound lands on the app's backend. The coupling to remote notifications is the entitlement line only: ActivityKit has its own token streams and needs neither `registerForRemoteNotifications` nor `UNUserNotificationCenter`. So admit the shared piece (LLP 1114.001 D7's piece 1, the entitlement) and leave D7's pieces 2–4 behind their own consumer; a Quora successor will ask for them soon, and that is the day to admit them as a unit, not by implication. Cost is small: an entitlement (note `host/apple/build.mjs:325` sets grant-derived entitlements to `true`, and `aps-environment` is a string, so it needs its own line), the Push Notifications capability on the App ID, a token fact, docs. Push-to-start belongs in the same ruling because that is where most of the server-side value lives and it adds no new mechanism.

**What would change my mind.** If Charlie would rather admit LLP 1114.001 D7 whole for Interview's notifications, do that as the unit and let activity tokens ride along as a line of it. If stage 0's Q3 shows the extension cannot re-render D9's envelope within budget at a push cadence, the activity should stay local until the render-only fallback exists. If Interview's first activity turns out to be something the phone itself knows, there is no consumer and "later with a named consumer" is right. Platform facts I am not certain of: that the simulator accepts `liveactivity` pushes through `simctl push` (which would decide whether the agent can drive one); whether an `alert` in an activity push needs notification permission; and the exact provisioning step the build's own signing needs when a capability is added.

## Question C — the first consumer

**Recommendation.** Keep Charlie's ruling, Interview for stages 0 and 1, with two riders. First, Caltrain gets a widget too, as the in-tree fixture: D14's async-lane extension test and the smoke run this repository's apps, and Interview is out of tree, so a departure countdown (two components) must exist for the checks regardless of who the judge is. Second, stage 0's Q3 reports two numbers, a Rust-only pruned plan (Caltrain's, which exists) and Interview's refresh under Hermes with the Snapback4 replica, so a kill-line failure says whether it is the design's floor or the consumer's weight. Stage 2: Interview if question 5 admits pushes (an AI answer job as the activity; an upvote or "mark read" as the intent); Caltrain's next-train countdown if it does not, since neither Interview nor Expo Services has an honest local-only activity. Expo Services second, as the port consumer (LLP 1069's `expo-widgets` gap) and the canonical server-driven activity, once its sender exists.

**Confidence.** 65%.

**Reasoning.** What each exercises: Interview has `app.ts` under Hermes, `secret.keep interview.session` in the Keychain (LLP 1018 D7: `AfterFirstUnlockThisDeviceOnly`, so a refresh cannot read it before first unlock and a Lock Screen render must not try), a SQLite replica with a one-writer gate (`src/replica.ts:12`) that an extension must open read-only or bypass, and a backend Charlie's team controls (`snapback/backend.ts`, auth and AI workers), so a push sender is a day's work. That is every hard property of D3, D8 and Q3 on the real consumer, and finding them in stage 0 beats finding them after building on Caltrain. Caltrain exercises D6's countdown and the Rust path, but D6 is HTML's `time`, which Interview's "answered 3m ago" also exercises. Expo Services is not first: the port talks to `api.expo.dev/graphql` directly and has no backend of its own, so its builds activity needs Expo's production servers to send to an unshipped port's bundle id, an external change; it loads nine native modules; and its original app has no widget to be the fidelity baseline against. What each risks: Interview risks stage 0 dying on Interview-specific weight (the replica in a ~30 MB extension), which the second Q3 number disarms; Caltrain risks a green stage 1 that taught nothing about Hermes, secrets or two writers. On "a real user's judgement": none of the three is on the App Store (Interview's README: "App Store release is not configured", `backendURL` is a LAN Mac), so the judge available is Charlie, who knows the platform; that is the judgement LLP 1115 actually asks for, and it favours the app he uses daily.

**What would change my mind.** If the replica cannot be opened in the extension and Interview's refresh is network-bound every time, its widget is no different from Expo Services' and the port consumer could go first. If question 5 is refused, stage 2's consumer is Caltrain and Interview waits for interactive widgets only. If Charlie plans a store release of Interview before stage 2, I would still choose it, but the activity's state shape should be frozen behind D9's envelope first.

## What the RFC frames wrongly

Question 4 conflates the entry with the place: Apple's surfaces are where one widget appears, and §3's table mixes classes with places, so once "surface" is reserved for places the naming problem mostly dissolves and the DEFERRED entry Charlie already approved has the words. Question 5 is framed as a scoped exception to a push refusal, which makes it look like a slope; what is admitted is a device fact and a server-to-system channel in which neither exact2 nor the app's code takes part at receipt, categorically unlike the refused things, while the RFC under-states the other side: for the ruled consumer a Live Activity without push is not "useful by itself", and §0 should say that the ruling on question 7 reopened question 5. Question 7 treats the consumer as if it were also the fixture; the apparatus approved under question 8 runs this repository's apps, so the real question was which app judges and which app the checks drive, and the "ships to users" criterion is weaker than it reads, since none of the three ships.
