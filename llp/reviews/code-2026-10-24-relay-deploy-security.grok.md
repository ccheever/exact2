**Blocking**

1. **`relay/deploy/deploy.sh:28`** (and the same option on `put_up` at `:42`). `StrictHostKeyChecking=accept-new` pins whatever key answers the first SSH handshake and never shows a fingerprint. That session is root (or `sudo bash -s`) and is how the control private key and the account token later move. A network attacker on the first connection records their own key in `known_hosts` and stays trusted for every later `release`, `install-cert`, and `accounts-add`. Pin the provider console’s host key in `RELAY_KNOWN_HOSTS` before the first run and use `StrictHostKeyChecking=yes`. Print the fingerprint and stop when it is not already pinned.

2. **`relay/deploy/remote.sh:88-95`**. `ufw --force reset` disables the firewall and flushes the rules before `22/tcp` is allowed and `ufw enable` runs. For that window the host is open; if the script dies after `reset` and before `enable`, it stays open. `22` is allowed before `enable`, so this is fail-open, and an established SSH session usually survives. The follow-up compare makes it worse. `want` (`:86-88`) requires four lines, including the two `(v6)` rules. `ufw` emits those only when `IPV6=yes`. With `IPV6=no`, or any extra rule, or any status-text drift, `got` never equals `want`, so every later `provision` resets again. With `IPV6=no` the kernel still has IPv6, `sshd` is on `[::]:22`, and ufw does not filter it, so any other `::` listener bypasses the “only 22 and 443” claim. `check` (`deploy.sh:79-82`) only probes a short IPv4 TCP list, so it will not catch that. Force `IPV6=yes` (or turn IPv6 off in the kernel and do not expect v6 rules). Keep the firewall up: ensure `22/tcp` is allowed, then delete every other inbound rule. Do not `reset` a live host. The provider security group has to allow only 22 and 443 as well; stock Ubuntu/Debian images usually listen on 22 alone, but a provider agent on any other port is exposed whenever ufw is down, and `check` will still pass.

3. **`relay/deploy/remote.sh:243-244`**. After the digest check, `release` does `chmod 0755` and `"$path" --help` as root. `bun build --compile` bundles `scripts/tamber-relay-server.mjs`; it does not run it. The first execution of that binary is this smoke test, unsandboxed, as root, before the unit’s user and `ProtectSystem` exist. The honest `--help` path prints usage and exits before `readConfig`, but anything in the bundle runs as root first. A dirty tree still ships (`deploy.sh:62`). The digest (`remote.sh:240`, computed in `deploy.sh:61` and sent on the same SSH session) catches a torn upload. It does not establish a second author. Copy the binary into root-owned `/opt/tamber-relay/releases/<id>/` and run `--help` with `runuser -u tamber-relay`. The smoke test never needs the key, the accounts file, or `CAP_NET_BIND_SERVICE`.

4. **`relay/deploy/remote.sh:161-178`**. The unit is not as tight as the relay’s own needs. The process must bind 443, read its config and control key, watch and write `/var/lib/tamber-relay`, and spawn `dns-hook` with outbound network. It does not need any other privileged port, and it does not need link-local. `AmbientCapabilities` / `CapabilityBoundingSet` leave `CAP_NET_BIND_SERVICE` for the whole life of the process and of the hook, so a compromise can bind 22, 53, or 80 if those sockets are free. There is no `SocketBindAllow=tcp:443` / `SocketBindDeny=any` (systemd 249 on Ubuntu 22.04, 252 on Debian 12). There is no `IPAddressDeny=169.254.169.254/32` (and the rest of link-local). A compromised relay can read the cloud metadata service and, on providers that put credentials or user-data there, take the project account. Add those two directives. Outbound otherwise has to stay open: the hook’s DNS API host is chosen later, in the runbook, which is not in this checkout.

**Non-blocking**

- **sshd (`remote.sh:67-77`, `:83-84`).** Write, then `sshd -t`, and delete the drop-in if the test fails, is the right order. The reload happens only after a clean test. The name `10-tamber-relay.conf` is first-match ahead of the usual `50-cloud-init.conf` / `60-cloudimg-settings.conf`, so `PasswordAuthentication no` wins on stock images. Nothing checks the effective config. A snippet that sorts earlier, or a `PermitRootLogin` / `PasswordAuthentication` set above `Include`, leaves passwords on and `sshd -t` still exits 0. After reload, assert `sshd -T` shows `passwordauthentication no`, `kbdinteractiveauthentication no`, `permitrootlogin prohibit-password`, and `pubkeyauthentication yes` (and set `AuthenticationMethods publickey`). The port check uses `sshd -T`, not the sockets `ss` shows. A socket unit on another port while config still says `22` passes the check, then ufw allows only 22 and the live SSH port is cut. The die text says nothing changed; the drop-in may already have been reloaded.

- **Secrets.** Modes match the access the relay needs. `/etc/tamber-relay` and `/var/lib/tamber-relay` are `0750`. The control key is `0640 root:tamber-relay` (`:146`). `dns.env` is created `0640 root:tamber-relay` (`:122`). `accounts.json` starts `0640` and the accounts tool rewrites it `0600`; `labels.seen` is appended `0600`. Other uids cannot traverse those directories. `EnvironmentFile=` (`:161`) does not put the file’s values in `systemctl show`; that property is the path (`EnvironmentFiles=… (ignore_errors=yes)`). The values are in the service process environment (`/proc/<pid>/environ`, mode `0400`, root and the service uid). A coredump can later copy that environment into the journal, which the default `adm` user can read. `accounts-add` (`:319-324`) runs the binary under `runuser`; the token is written only to that process’s stdout (`scripts/tamber-relay-server.mjs:564`), which is the SSH channel. It is not in argv, the shell history, the journal, or a server file. The Mac terminal scrollback is the copy. Redirect it straight into `~/.exact/relay/<label>/token` created `0600`, which is what the connector already requires. Uploads use `umask 077` and `mktemp -d` (`deploy.sh:41`); `install-cert` / `release` trap into `unload` (`remote.sh:194`, `:238`, `:225`). There is no lego/ACME client in these scripts. The hook is a placeholder that exits 1; the control key arrives only through `install-cert`. Provision does not re-apply mode if `dns.env` or `dns-hook` already exist (`:114-122`). In-place edits keep the inode mode; a delete-and-recreate follows root’s umask.

- **What a compromised relay can do, given this unit.** It runs as `tamber-relay` with `ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true`, `NoNewPrivileges=true`, and `ReadWritePaths=/var/lib/tamber-relay` only. It cannot change the unit, the binary, `relay.json`, or `dns-hook`, and it cannot write `/root/.ssh`. It can read the control private key and terminate the control endpoint, so connector bearer tokens are in its memory (that is the control connection). It can rewrite `accounts.json` (new hash, revoke, new label) and append `labels.seen`. It can read `dns.env` and call the provider with whatever that token allows; the hook is `sh -c` as the same uid (`scripts/tamber-relay.mjs:131-136`) and inherits the environment and the ambient capability, and the parent can ptrace the child. Scoping the token to TXT under `_acme-challenge` is the real limit; a setgid helper is not a boundary against a parent that can ptrace it. `MemoryDenyWriteExecute` is omitted on purpose (`:179`) because Bun writes code. There is no seccomp filter. `CAP_NET_RAW` is dropped, so `AF_PACKET` sniffing of other flows is not available. Metadata and extra privileged binds are the gap in item 4.

- **Supply chain otherwise.** The symlink switch (`ln -sfn` then `mv -T`, `:232-233`) is atomic, and the release id is 16 hex chars of a hash that was compared in full (`:240-241`). Prune (`:254-256`) keeps the current and previous ids and refuses an empty `OPT`. `release` never `systemctl enable`s. `provision` enables only when `current` already exists (`:186-188`), so provision-then-release stays up only until the next reboot.

- **`unload` (`:225`).** The `case` pattern is a bash glob, so `/` matches. A path whose `dirname` is `/tmp/tamber-relay-upload.X/../../..` is `rm -rf`’d after normalization. `deploy.sh` quotes every remote argument with `printf '%q'` (`:39`) and only passes a `mktemp` path, so this is not reachable from the operator-facing arguments. Refuse any upload path that is not `^/tmp/tamber-relay-upload\.[A-Za-z0-9]+/[^/]+$`, and validate `updir`’s stdout the same way (a PAM motd on the SSH stdout is otherwise captured into `dir=$(updir)`).

- **R4 gate (`scripts/tamber-relay-gate.mjs`).** Each line still proves its claim against a real relay, within the limits below. The in-process “deployed” test (`scripts/tamber-relay-server.test.mjs:337-363`) uses `relayServer()` on loopback with `RELAY_GATE_CERTS`. It never starts the unit, the hook, or a real network.
  - **Line 1 (`:143`).** The client’s `getPeerCertificate().fingerprint256` is compared to the fingerprint the design server computed locally (`tamber-remote.mjs:29`, `X509Certificate.fingerprint256`). Termination with the relay’s own certificate fails the name check or the fingerprint. The line shows the handshake ended on the design server’s key.
  - **Line 2 (`:152-158`).** `polling()` is the design server’s in-flight `/__tamber/events`, and revoke runs only after that is non-zero and the watched response is still empty. The 401 has to come back through the same TLS connection, which goes through the tap to the relay. A timeout makes `pending` false and the line fails.
  - **Line 3 (`:160-161`).** An empty read is treated as “closed at the relay”. The tap destroys the client with no bytes when its forward errors (`:83`), so a failed dial is also MET. Require the forward’s `connect` before accepting an empty close, and give the read a deadline.
  - **Line 4 (`:167-170`).** The tap records the bytes of connections the gate itself opens. Connector tokens, pairing codes, and the design string are inside TLS on that path, and the search is over the concatenation. A capture of ciphertext stays clean even if the relay terminated TLS; line 1 is the termination check. The tap does not see the relay’s own outbound sockets (DNS API, or an exfil connection).
  - **Lines 5-7.** Cross-account pairing is 403 then 200 on the two session names; the TXT refusal is the relay’s own `not your account's name` (`tamber-relay-server.mjs:353`) and happens before the hook. The canvas cookie is checked on the other account’s canvas and on both tools. Eleven bad pairs on A still leave B able to pair; both clients share the runner’s address, and `perIpPerSession` is 30, so the relay does not pre-empt the design server’s 429.
  - `deployedRelay` (`:34`) splits the relay address on the first colon, so an IPv6 `RELAY_GATE_RELAY` is wrong, and it does not apply the connector’s `0600` check on the token file.
