## The review, verbatim (final message)

**Verdict: go with named changes.** I would choose the whole-runtime owner thread. The direction is justified; the P1 findings below need resolution before implementation.

1. **P2 — The architectural choice is right.** The physical-device evidence meets the reopening condition in [1044.000:249](/Users/ccheever/projects/exact2-wt-mount/llp/1044.000-text-performance-claude.plan.md:249) and [1022:100](/Users/ccheever/projects/exact2-wt-mount/llp/1022-serial-runtime-owner-parked.research.md:100). Moving only collection fills between threads still moves a mutable runtime containing thread-local state and `Rc` ownership. Detached subtree construction would need new rules for IDs, local state, dependencies, effects, layout integration and invalidation. A snapshot of the immutable plan does not snapshot those mutable dependencies. One dedicated owner preserves serial mutation without those changes. Keep ordinary operations synchronous, but treat asynchronous ticks as a second explicit exception—not merely a detail of fill.

2. **P1 — The callback pump needs a reentrancy contract.** `Owner.callMain` solves the direct `main.sync` deadlock, but a main callback can itself request the owner: native-module initialization logs through `session.log → runtime.log` ([NativeModule.swift:318](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/NativeModule.swift:318)). Main would then wait for an owner already waiting for that callback. Executing nested runtime work inline is also invalid: Rust retains a mutable runtime borrow across the callback ([abi.rs:1442](/Users/ccheever/projects/exact2-wt-mount/host/apple/src/abi.rs:1442)). Specify that callback service cannot synchronously reenter a runtime; defer notifications/logging and explicitly reject unsupported synchronous reentry. Release mailbox/cache locks before invoking callbacks, claim each callback exactly once, and support worker-placed source callers too. The proposed `.notOnQueue(.main)` assertion does **not** detect an owner calling `main.sync` ([1071:405](/Users/ccheever/projects/exact2-wt-mount/llp/1071-building-rows-off-the-main-thread.rfc.md:405)).

3. **P1 — Replace “every C call” with an explicit ABI ownership classification.** The claim that `changed` is unchanged is wrong: [nativeChangedCallback:246](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/NativeModule.swift:246) calls `exact_app_changed` on main, which would find the wrong thread-local registry. [installAppModule:378](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/NativeModule.swift:378) also enters Rust directly. Both must move. Conversely, `exact_app_answer` writes the waiting caller’s stack slot and must remain usable from the serviced main callback; queuing it behind the suspended owner would deadlock ([app_module.rs:55](/Users/ccheever/projects/exact2-wt-mount/host/apple/src/app_module.rs:55)). Make each input-write → operation → output-copy/decode one indivisible owner job, because output bytes expire on the next call ([Bridge.swift:80](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Bridge.swift:80)). Owner-local markup/textflow helpers must execute directly rather than enqueue and wait on themselves.

4. **P1 — FIFO execution does not establish FIFO application or fresh feedback.** Suppose fill F produces batch 1 and an event produces batch 2. Applying batch 1 can synchronously issue another report and apply batch 3 before batch 2: `Session.apply` calls back into Rust and flushes collections ([Session.swift:753](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Session.swift:753)). Introduce one non-reentrant application coordinator, defer apply-triggered reports until the preceding batches are installed, and return from a synchronous operation only after its batch has applied. Gather geometry **after** this drain. Currently feedback is encoded from the applied snapshot and marked sent before calling Rust ([Collection.swift:390](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Collection.swift:390)); an intervening fill/data update makes its revision stale, and Rust rejects it wholesale ([collection/mod.rs:858](/Users/ccheever/projects/exact2-wt-mount/runner/src/instance/collection/mod.rs:858)). Serialization protects data mutation, but rejected geometry must remain dirty and be retried. Never discard a committed live-generation batch merely because newer data exists.

5. **P1 — The tap/pin argument is incorrect.** A fill *can* retire a still-present UIKit row ([collection/mod.rs:708](/Users/ccheever/projects/exact2-wt-mount/runner/src/instance/collection/mod.rs:708)). A reversal, touch or focus change before its batch applies can target that row. Rust then returns `UnknownView`, rather than delivering the interaction ([event.rs:789](/Users/ccheever/projects/exact2-wt-mount/runner/src/runner/event.rs:789)). This is a new interval during which hit-testable views have no runtime instances; [1071:233](/Users/ccheever/projects/exact2-wt-mount/llp/1071-building-rows-off-the-main-thread.rfc.md:233) cannot dismiss it as existing behavior. Specify a bounded retirement/interaction handshake, potentially retaining pending-retirement instances until main acknowledges retirement. A subsequent `pinsChanged` is too late. Test touch-down through click, focus transfer, accessibility, selection and IME composition while publication is held. Existing marked-text protection guards value replacement, not destruction of the editor ([TextAreaIOS.swift:235](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/IOS/TextAreaIOS.swift:235)).

6. **P1 — Never-blank is not established by awaiting the old fill.** Its geometry describes the viewport at submission. By completion, reversal, a jump, keyboard/width changes, changed row heights or another list may require different rows. After draining, re-read current geometry, synchronously rescue uncovered owed rows, apply, and verify actual coverage before presentation. Retain coherent accepted content during resize; preserve correction sequence checks and UIKit momentum ([Collection.swift:43](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Collection.swift:43), [CollectionIOS.swift:89](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/IOS/CollectionIOS.swift:89)). Lead must cover queueing, build, publication delay and apply—not just build plus an assumed frame. Also qualify “every case”: D3 explicitly permits pending rows, and 1068 permits absent heavy-leaf content inside present row boxes. Measure both uncovered rows and missing-content area × time ([1050.000:74](/Users/ccheever/projects/exact2-wt-mount/llp/1050.000-choosing-the-fill-tradeoff.rfc.md:74), [1068:719](/Users/ccheever/projects/exact2-wt-mount/llp/1068-recycling-heavy-views-in-list-rows.rfc.md:719)).

7. **P1 — The text split is directionally sound but materially incomplete.** Ordinary iOS measurement uses CoreText, font descriptors, literal `UIColor` values and locally built attributed strings; I found no view/TextKit-control operation in that path ([Text.swift:573](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Text.swift:573)). The problem is shared mutable ownership. `measuredBreaks` accesses residency outside the proposed break-cache lock; painting calls `paragraph`/`accepted`, and Canvas 2D also mutates font caches ([Text.swift:715](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Text.swift:715), [NodeText.swift:24](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/NodeText.swift:24), [Canvas2DImage.swift:99](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Canvas2DImage.swift:99)). Give measurement and painting separate mutable caches, with immutable font/geometry publications keyed by content, width and font generation. Remove the “copy cached lines into the batch” fallback: copying an array does not create independently owned `CTLine`s. **Stage 1 also has a concrete macOS failure:** `measure → readerMeasure → RegionReaderTiming.begin` asserts main-thread execution ([RegionReaderMac.swift:428](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Mac/RegionReaderMac.swift:428), [:59](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Mac/RegionReaderMac.swift:59)). Resolve that ownership now, not in stage 5.

8. **P1 — Tick coalescing and `clock settle` need a complete settlement protocol.** Rust `tick` can settle layout, perform height layout and advance Canvas 2D; it is not merely a replaceable motion sample ([host.rs:1065](/Users/ccheever/projects/exact2-wt-mount/host/apple/src/host.rs:1065)). Coalesce only unexecuted requests without crossing intervening event/timer barriers; never discard already-produced delta batches. Specify ordering with native canvas rendering. Also, `Frames.tick` performs synchronous timer advancement *before* `runtime.tick`, so T6 does not currently ensure a display callback avoids waiting on a fill ([Session.swift:1157](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Session.swift:1157)). Preserve captured virtual timestamps, and include fills, queued ticks, publications and apply-generated work in the agent’s fixed point. Recheck after the request and native completion turns, not only before it. Eight rounds must yield an explicit unsettled result if work remains; they are not proof of settlement ([1071:279](/Users/ccheever/projects/exact2-wt-mount/llp/1071-building-rows-off-the-main-thread.rfc.md:279)).

9. **P2 — “One fill” is neither “one row” nor an 8.9 ms latency bound.** The pump requests `max(1, fits, needed)` rows ([ScrollPumpIOS.swift:126](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/IOS/ScrollPumpIOS.swift:126)); changed pins/geometry remove the limit, and data updates realize the whole window ([collection/mod.rs:934](/Users/ccheever/projects/exact2-wt-mount/runner/src/instance/collection/mod.rs:934), [:596](/Users/ccheever/projects/exact2-wt-mount/runner/src/instance/collection/mod.rs:596)). Fill edge actions can also issue application requests ([abi_collections.rs:99](/Users/ccheever/projects/exact2-wt-mount/host/apple/src/abi_collections.rs:99)). Replace that promise with measured queue/build/apply distributions and input-to-visible latency. With one process owner, bound speculative admission across sessions and test one heavy session beside an interactive one. Measure sustained production rate: waiting for apply before submitting the next fill limits throughput, and no amount of lead fixes insufficient sustained throughput.

10. **P2 — Lifecycle, pressure and background policy are missing.** Moving boot alone is insufficient: font checkpoints, hook replacement, candidate preparation and commit must form owner-safe transactions ([Session.swift:590](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Session.swift:590), [:637](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Session.swift:637)). Retain callback contexts through completion; stop admission before destruction, resolve waiting callbacks, then release runtime-owned objects. Route pressure/rest trimming to the appropriate cache owner—the current pressure handler mutates `TextEngine` on main ([Session.swift:473](/Users/ccheever/projects/exact2-wt-mount/host/apple/Sources/ExactKit/Session.swift:473)). Add per-job autorelease pools and account for queued batches plus duplicate text storage. Backgrounding should stop speculative admission; foregrounding must drain and refresh coverage before resuming fills. Cancellation may discard unstarted work, but cannot silently discard committed deltas for a surviving runtime.

11. **P2 — Keep staged validation, but revise the order and gates.** I recommend **1 → 2 → 4 if profiling warrants it → 3 → 5** ([1071:463](/Users/ccheever/projects/exact2-wt-mount/llp/1071-building-rows-off-the-main-thread.rfc.md:463)).
    - **Stage 1:** all Apple paths, including large Markdown, native callbacks, reload and two-session operation; settled first-frame timing and seek/capture A/B. Separate CPU time from blocked wall time: this stage already moves Rust *and* decode CPU, while main still waits. A coarse hop is plausibly acceptable, but 3 ms/s at 120 calls/s allows only **25 µs per round trip**; actual call counts and tail latency decide.
    - **Stage 2:** retain ≤3 late frames/s and zero unintended gaps, adding input latency, presentation cadence, owed-wait duration and forced interleaving tests. Hold fills before commit/publication/apply to exercise the races above.
    - **Stage 4:** require an actual reduction in main apply/CA cost with pixel and motion parity.
    - **Stage 3:** clarify scope first. The current collection API has no whole-row D3 cost memo ([api.rs:43](/Users/ccheever/projects/exact2-wt-mount/runner/src/instance/collection/api.rs:43)); 1068’s heavy-leaf hold explicitly differs from D3 ([1068:698](/Users/ccheever/projects/exact2-wt-mount/llp/1068-recycling-heavy-views-in-list-rows.rfc.md:698)). This is not simply retiming an existing memo.
    - **Stage 5:** physical Mac scrolling, reversal, jumps, resize, anchors and input—not only hitch counts and smokes.

12. **P2 — Recommendations for all five §10 questions.** **Q1:** one process owner initially, conditional on the two-session latency gate; per-session owners only if measured contention requires isolation. **Q2:** keep a narrowly scoped diagnostic/test `EXACT_FILL_SYNC` switch using the same implementation, explicitly approved as requested by the repository’s apparatus rule. **Q3:** land stage 1 separately once its corrected gates pass. **Q4:** keep Linux synchronous; semantic parity does not require identical scheduling. **Q5:** yes, permit off-main building during motion when its unavoidable main-thread work fits the **remaining** frame budget, including paint/CA and callbacks. Keep owner-occupancy admission separate, and explicitly amend D3 rather than presenting this as an unchanged reading.
