1. **MATERIAL — The web dispatch architecture rests on an obsolete WebKit restriction.**

   **Evidence:** [D9, lines 439–476](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/pk1/capsule/llp/1133.011-passkeys.rfc.md:439) requires activation-preserving dispatch, preloading, worker refusal and failure of an early press. Lines 739–743 use the same premise to require local-auth’s Unlock button. WebKit [removed the WebAuthn gesture requirement in December 2023](https://bugs.webkit.org/show_bug.cgi?id=264444); the [merged change](https://github.com/WebKit/WebKit/pull/20191) removes checks for both creation and assertions. The cited 2020 article cannot justify these restrictions today.

   **Resolution:** Establish the supported browser floor before adding `"activation": "web"`. For current top-level browsers, retain ordinary asynchronous admission and page dispatch, including calls from worker-placed data code. Remove the mandatory early-press failure and revise local-auth’s activation premise. Keep Exact’s tool/wake restrictions; they are independent of browser activation.

2. **MATERIAL — The native composition hatch cannot construct or return the mixed credential sheet it promises.**

   **Evidence:** [D5, line 297](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/pk1/capsule/llp/1133.011-passkeys.rfc.md:297) lets the app add requests through an already constructed controller, but Apple’s [`authorizationRequests` is read-only](https://developer.apple.com/documentation/authenticationservices/asauthorizationcontroller/authorizationrequests). The module also retains the delegate, while line 532 declares only `AuthenticationResponseJSON`. There is no declared completion path for a hatch-added password or Apple ID credential.

   This prevents the tier-3 mixed sheet claimed at line 384 and relied upon by §8. Apple [supports those combinations](https://developer.apple.com/documentation/authenticationservices/supporting-passkeys), using a request array supplied before construction and heterogeneous credential handling afterward.

   **Resolution:** Provide a preconstruction request-list/factory hatch and define how added credential types complete below the data seam. Preserve admission, cancellation and controller ownership. Prove selection of a non-passkey credential before claiming this ceiling is removed.

3. **MINOR — D11’s cleanup stops before server registration completes.**

   **Evidence:** [Lines 600–613](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/pk1/capsule/llp/1133.011-passkeys.rfc.md:600) dispose registrations dropped before delivery to data code. The consumer subsequently posts the response to its server at lines 870–872. Cancellation or network failure between those steps leaves another orphan path. A new account might never reach the later successful sign-in proposed for reconciliation.

   **Resolution:** Describe disposal as best-effort cleanup before binding delivery. Add reconciliation for failed or indeterminate registration submissions. Check server status before signaling “unknown”: a lost HTTP response can follow successful registration.

4. **MINOR — Android preparation is not reachable through the declared request hatch.**

   **Evidence:** [Line 385](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/pk1/capsule/llp/1133.011-passkeys.rfc.md:385) claims `prepareGetCredential` through D5’s request replacement hatch. Android preparation returns a pending handle consumed by a [different `getCredential` overload](https://developer.android.com/reference/androidx/credentials/CredentialManager). Replacing `GetCredentialRequest` cannot select that execution path.

   **Resolution:** Expose the prepared-operation lifecycle, or explicitly defer preparation instead of counting it as reachable tier 3.

**IN-DELTA / MATERIAL — The page’s registry cannot protect synced lock credentials across clients.** [§7:752](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/pk2/capsule/llp/1133.011-passkeys.rfc.md:752) records lock IDs and user handles “in the page” and promises sign-in reconciliation can never delete them. Yet [lines 771–780](/private/tmp/claude-501/-Users-ccheever-projects-exact2/f4b5c629-4ed6-4746-9045-74f6106a629d/scratchpad/pk2/capsule/llp/1133.011-passkeys.rfc.md:771) explicitly make these discoverable, synced credentials.

A second browser or native client sharing the RP can offer that lock credential for sign-in without possessing the registry. Its server rejects the unknown credential, and normal `signalUnknownCredential` handling bypasses the guard. The standard permits removing the credential or hiding it from future ceremonies; the PRF-backed secret depends on retaining access to it. See [WebAuthn’s signal algorithm](https://www.w3.org/TR/webauthn-3/#dom-publickeycredential-signalunknowncredential).

**Resolution:** defer the lock entry itself until local-auth establishes RP separation or ownership recognized across participating clients. Merely deferring the consuming web cell leaves §7’s promised protection defective. Prove the chosen design with two clients sharing a synced credential.
