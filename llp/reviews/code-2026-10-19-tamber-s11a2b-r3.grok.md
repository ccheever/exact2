## Findings

### SHOULD-FIX — `watched` can list a directory outside any package — `contract/cli/src/tamber_packages.rs:58`

`watch.links` is every consulted path whose file name is `package.json` and which contains a `node_modules` component, then that path's grandparent. `source_graph` puts unmade design paths on `consulted` (`packages::sources` → `missing`). `package_design` does not keep a `"tamber"` value inside the package, and `Path::join` keeps an absolute value. A package whose `"tamber"` is an absolute or `..` path that folds to a **missing** `…/node_modules/…/package.json` therefore lands in `links`. The local wire `fs.watch`es that grandparent (`scripts/tamber-package-designs.mjs:33`). A normal `../secret.tamber` is not listed (the name is not `package.json`). An existing outside file is a source, not a link, and `read` still refuses it, so this does not ship the file's text. It does break "never a path outside a package", and only the grandparent has to exist. Filter links to real install manifests (the package's own `package.json`, install path and canonical path), not every consulted `package.json`.

### NIT — a directory that leaves `watch` stays watched — `scripts/tamber-package-designs.mjs:21`

`follow` adds or replaces a watcher. It never closes one whose path dropped out of `roots` or `links`. A package removed, or a bad path from the filter above corrected, is watched until the process exits.

## What checks out

**Rows and reads.** With no package designs, `packaged`, `mark`, and `fields` add nothing, so hello, describe, resolve, and explain stay byte-identical. Otherwise hello and describe gain `packages[{package, file, digest}]` (`file` is `@pkg/reading.tamber`, digest is sha256 of the design text). Describe rows for a package token gain `package` and `file` (the app's design when the app defines the token, else the package file). Resolve and explain add `package`, `file`, and `identity` (`<package>/<file>#<token>`). Explain adds `package_value {value, whens, file}` only when the app sets the token. Resolve does not.

**set-token.** It rewrites to an `add-token` of the given value only (no kind, meta, or whens) when the name is absent from the app design, as earlier ops in the batch left it, and a package defines it or it is one of the nine base names (`space.xs`–`space.xl`, `radius.sm`–`radius.full`). Those nine match the stage 11 B scale table. It does not fire for a name the app already defines, for `set-param` / `unset-param`, for an icon (icons are not design tokens; packages cannot declare them), or for a role (a role is an app name: `add-token` until it exists, then `set-token` edits it, including the checker's other spellings). Schema rows are `set-row` / `set-state` and are split off before this transform. A `when` on that first set is refused (`isn't set for this app yet… takes the token whole`); a later `set-token` in the same batch, once the name is defined, keeps the when. `remove-token` is not rewritten: it deletes the app line so the package or base value shows through. `add-token` of a package or base name is refused and points at `set-token`, except `restore`. A new name under a package's last path segment is refused, as is `rename-token` onto a package name, a base name, or that namespace.

**Undo, proposals, scrubs.** The inverse of the rewritten add is a `Restore`, and `undo` applies those bytes with `undo: true` without running the transform. The round-trip test covers set, explain's dropped whens, undo, set, remove. Propose stores the client's ops and both propose and accept run the transform again, so a held proposal is judged on the packages as they are then. `scrub-fold` runs the same transform (`tamber_scrub.rs:83`, `restoring: false`); release writes the original ops through `transaction`, which transforms again. `restore` is set only by the server's revert and import holds (and their replans). Dispatch deletes a client's `restore` on every method before that, so a transaction with `restore: true` and `add-token` of a package name is refused.

**Read-only file.** An op whose `file` is a package design is refused by wire name (`home`), stored path, or `canonicalize` (symlinks, `..`, the app.json `"tamber"` that names the package file). The package file is not in the snapshot otherwise, so a miss still fails as "no file of this design" rather than writing it.

**hello `{paths: true}`.** The wire calls the design server with `paths: false` for every client hello, so a paired read client gets no `packages[].path` and no `watch`. `file` is the package identity, not a host path. The internal refresh is the only caller of `paths: true`. That is acceptable. (The pre-existing hello field `app` is still the absolute app directory for every client.)

**JS announce.** The first successful hello is the baseline and does not emit. Later, a digest change, an added design, or a removed one is one `changed` event with those identity names in `edited` and `packages` stripped of `path`. App-file changes still go out through `publish` first; a package-only change does not double-send. Announce competes a scrub and clears the param key; `learnParams` then runs in the same read, so a package-only change refreshes params. Package roots are watched recursively and install directories non-recursively, which covers a design created where none was, a `package.json` `"tamber"` move, and a link retarget. Package roots may lie outside the app when the package itself is linked there. That part is intended.

**Tests.** The Rust file covers rows, refusals, batch sets, rename, restore, scrub-fold, hello `watch`, the explain/undo/remove round-trip, and an app design that is the package file. The JS file covers the listing, the change event, the held proposal re-check, a design appearing, no client paths, no client `restore`, and a design moved by `package.json`. They do not cover the `"tamber"` path that becomes a `watch` link.
