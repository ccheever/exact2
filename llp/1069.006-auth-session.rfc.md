# LLP 1069.006: Signing in through the system browser — `openAuthSession`

**Type:** RFC
**Status:** Draft r2; Charlie's rulings folded 2026-09-27

**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-27

**Related:** LLP 1069 §5 #7 (the survey item) and §3 (the consumers); LLP 1069.005 (random bytes, SHA-256 and P-256, which PKCE and DPoP need); LLP 1069.007 D3, D4, D7 (the substitute); LLP 1069.008 (entitlements and associated domains derived from grants; the reach table); LLP 1018 D5 (the token never enters the plan) and D6 (the secret store per host); LLP 1016 D4 (failure is data) and D5 (one request per resource, the newest wins); LLP 1038 D8 (an incoming URL is one `navigate` event); LLP 1067 D1 (a long call is a request to a reserved URL); LLP 1054 (the Bluesky port, which signs in with an app password); `rules/DEFERRED.md` (Bluesky's OAuth sign-in named as one of its asks, 2026-09-27)

## Rulings (Charlie, 2026-09-27)

- **Q1: the name is `openAuthSession`,** chosen for what an agent or developer will most likely guess right (Charlie: "whatever you think agents will most correctly guess"). It follows Expo's `openAuthSessionAsync` and Apple's `ASWebAuthenticationSession`. The text below uses it.
- **Q2: Bluesky's OAuth sign-in is one of its admitted asks.** `rules/DEFERRED.md` says so explicitly.
- **Q3: DPoP keys follow LLP 1069.005's ruling:** a JWK first, a non-extractable key in IndexedDB on the web, and a host-held key after review.
- **Q4: no redirect fallback on the web.** **This overrides D4's fallback.** A blocked popup fails, and the app asks the person to tap again.

## Summary

An app that signs in through someone else's account uses OAuth 2.0 or
OpenID Connect: Bluesky, GitHub, Google, or an app's own identity provider.
A native app does this in the system browser (`ASWebAuthenticationSession`
on Apple; RFC 8252 names the rules). A web app does it in a popup. exact2
has none of this. The Bluesky port signs in with an app password, which
Bluesky deprecates for third-party clients.

The proposal is one request. A source asks the host to open an
authorization URL and wait for a callback. The host answers with the
callback URL, or a failure when the person cancels. Everything else stays
in the source:

- building the URL, PKCE and `state`;
- pushed authorization (PAR);
- the code-for-token exchange by `fetch`;
- DPoP proofs;
- keeping the tokens with `secret.keep`.

```ts
// app.ts — the whole of the new surface a TypeScript source sees
export const grants = [
  'net.fetch https://bsky.social',
  'auth.session https://bsky.social',
  'auth.callback social.exact.bluesky:/oauth',
  'secret.keep bluesky.session',
].join('\n');

const back = await openAuthSession(url, { callback: 'social.exact.bluesky:/oauth' });
// back: "social.exact.bluesky:/oauth?code=…&state=…&iss=…"
```

It is a request, like `native.later` (LLP 1067 D1). Tickets, supersession,
`pending(x)`, worker placement and failure as data apply unchanged, and no
request type gains a field.

## Motivation

- **Bluesky.** The AT Protocol's login for third-party clients is OAuth
  with PKCE, PAR and DPoP. The port uses `com.atproto.server.createSession`
  with an app password (`bluesky-exact2/data/src/session.rs`). It works,
  but it asks people to mint a credential by hand, and Bluesky is moving
  away from it.
- **Everything else.** "Continue with Google/GitHub/Apple", or a delegated
  login (Auth0, Clerk, Cognito), is the same flow. `expo-auth-session` is
  among Expo's most used packages (LLP 1069 §2.6).
- **It can't be done today.** `openURL` hands the URL to the system
  browser, which owns the page; the callback returns as a `navigate` event
  to the navigation root (LLP 1038 D8). That event has no ticket and no
  source, the code is visible to the view, the tab stays open behind the
  app, and on iOS App Review rejects the flow.

## Design

### D1 — One request to a reserved URL, answered with the callback URL

`openAuthSession(url, options)` is a request to `exact-auth:`, as
`native.later` is a request to `exact-native:` (LLP 1067 D1,
`runner/src/request.rs:87`). `Request::is_auth` names the URL, as
`is_native` does; the rest rides in the JSON body:

```json
{ "url": "https://bsky.social/oauth/authorize?client_id=…&request_uri=…",
  "callback": "social.exact.bluesky:/oauth",
  "ephemeral": false }
```

The reply is HTTP-shaped:

| status | body | when |
|---|---|---|
| 200 | the full callback URL | the provider redirected to the granted callback |
| 499 | `cancelled` | the person closed the sheet or pressed Cancel |
| 403 | the grant | a grant refused it (D2) |
| 409 | `already open` | a session is open in this window (D3) |
| 428 | `popup blocked` | web only: the popup was blocked (D4) |
| 501 | the host's name | no system browser (Linux, D5) |
| 502 | the error | anything else |

A TypeScript `openAuthSession` resolves with the string, or rejects with
the status and message. A Rust source receives the reply as any other: its
answer names a `Need::AuthSession` and `parse` receives the response.
Failure is data (LLP 1016 D4), so "cancelled" is a value the view can show.

The reply goes to the **source**, never to the plan. The callback URL
carries an authorization code, a credential while it lasts, so LLP 1018
D5's rule for tokens applies: the source exchanges it, keeps the result
with `secret.keep`, and the plan sees `Session { ok, handle, error }`.
`state`, the journal, `carry` and a screenshot never show the code.

*Rejected:* the callback through `navigate` (LLP 1038 D8). No ticket, it
reaches the view, and on Apple the session captures its own callback, so
the event would never fire.

*Rejected:* a first-party native module over LLP 1067. `native.later` plus
about forty lines of Swift is the Apple arm, but every OAuth app would copy
it; the web's callback page is a bake output; and the grants and
entitlements (D2) are the bake's business, not a module's.

### D2 — Two grants: where the person signs in, and where they come back

- **`auth.session <origin>`** admits authorization URLs on that origin, with
  `net.fetch`'s grammar, the `https://*.domain` form included. A `url`
  outside every such grant is refused with 403 before anything opens.
- **`auth.callback <callback>`** admits one callback:
  - `scheme:/path`, a private-use URI scheme (RFC 8252 §7.1), by
    convention the bundle id reversed;
  - `https://host/path`, a claimed HTTPS callback (RFC 8252 §7.2).

  A `callback` that isn't granted is refused with 403.

Two kinds, not one line with two values: the grant grammar is one
capability, one target (`vendor/ibex2/src/grant.rs:290-294`). Like
`surface.*` and LLP 1069.008's `device.*`, both are exact2 grants that
`io_grants` strips before `ibex2` parses the rest (`runner/src/request.rs:20`);
the host's `exact-auth:` arm checks them.

The bake derives the platform setup from these lines, through LLP
1069.008's table:

- **An https callback on Apple** needs an associated domain
  (`webcredentials:host`) and the host's `apple-app-site-association`. It
  joins the domains `host.ios.associatedDomains` produces
  (`host/apple/build.mjs:435`).
- **A private-use scheme** needs nothing. `ASWebAuthenticationSession`
  matches it without a `CFBundleURLTypes` entry, and not registering it
  keeps another app from claiming the callback.
- **The web.** The callback is always the app's own origin (D4), so the
  bake maps a granted native callback to `/.exact/auth/callback`.

### D3 — Apple: `ASWebAuthenticationSession`, one per request

The executor hands an `exact-auth:` request to the presenter on the main
thread, which creates the session:

- **The callback matcher.** `.customScheme(scheme)` or
  `.https(host:path:)`. That API needs iOS 17.4 / macOS 14.4, above the
  floor of 17.0 / 14.0 (`host/apple/build.mjs:85-86`). Below it, the older
  `callbackURLScheme:` initializer covers private-use schemes only, and an
  https callback there answers 501. Only a URL matching the full granted
  callback, path included, completes the session.
- **`prefersEphemeralWebBrowserSession`** from `ephemeral`. `true` shares no
  cookies with Safari ("switch account"); `false`, the default, lets a
  person already signed in tap once.
- **`presentationContextProvider`**: on iOS the scene's key window; on
  macOS the window holding the node that asked, or the key window for a
  worker-placed source.

The completion handler replies on the runner's thread, as `fulfill` does: a
URL is 200, `canceledLogin` is 499, anything else 502.

When the runner forgets the ticket (superseded, or the resource went away,
LLP 1016 D5), the host calls `cancel()`. At most one session is open per
window; a second answers 409. `SFAuthenticationSession` and in-app
`WKWebView` login are not offered: providers refuse embedded web views, and
a web view can read the password.

### D4 — Web: a popup to the app's own callback page

The browser has no auth-session API, so the web arm is `window.open` plus
`postMessage`:

1. **Open.** The glue opens a popup at `url`, named per ticket. A press
   gives transient user activation (about five seconds in Chrome); the glue
   executes a request in the batch that follows it.
2. **Callback page.** The bake emits one static file,
   `/.exact/auth/callback/index.html`, about twenty lines with no
   framework. It posts `location.href` to `window.opener` (target: the
   page's own origin) and closes itself. The provider registers
   `https://<app origin>/.exact/auth/callback`.
3. **Answer.** The glue checks the message's `origin` and that the URL's
   `state` matches the request's, and answers 200. A popup closed without a
   message is 499, seen on a `closed` poll every half second.

**A blocked popup fails** (ruled): `window.open` returns null, and the
request answers 428 `popup blocked`. The app shows it and asks the person to
tap again. There is no redirect fallback and no page reload.

A popup is blocked when the request comes too long after the press. The
likely cause is work before the call: PAR is a `POST` (D6 step 3), and
Safari's activation window is shorter than Chrome's. So a source should do
discovery and PAR when the sign-in screen appears, keep the `request_uri`,
verifier and `state`, and call `openAuthSession` directly from the press.
The tap-again path then succeeds without redoing PAR while the
`request_uri` is fresh.

A web build served from a development origin registers that origin with
the provider as usual.

### D5 — Linux: unavailable, declared

The Linux host is a painter over DRM/KMS or a buffer (LLP 1015), with no
browser to hand a URL to. An `exact-auth:` request answers 501, "no system
browser on this host". A desktop Linux host would use RFC 8252 §7.3:
`xdg-open`, a loopback redirect to `http://127.0.0.1:<port>/`, and a
one-shot listener. Written down so nobody invents another shape.

### D6 — The source keeps the protocol: PKCE, PAR, DPoP, tokens

Nothing below is new API. It is what a source writes with `fetch`,
`secret.keep`, the time fact and LLP 1069.005, and the Bluesky port is its
first test.

1. **Metadata.** Resolve the handle to a DID and a PDS, then the
   authorization server's metadata: two `fetch`es under `net.fetch`.
2. **PKCE and state.** A 32-byte verifier and a `state` from
   `crypto.getRandomValues`; the S256 challenge from
   `crypto.subtle.digest('SHA-256', …)` (LLP 1069.005 D1, D2). The launch
   seed can't be a verifier: one 53-bit number per launch, visible to the
   agent. Both are kept with `secret.keep` before the session opens, so an
   app killed while the sheet is up can finish.
3. **PAR.** A `POST` to the pushed-authorization endpoint returns a
   `request_uri`. Plain `fetch`, done before the press on the web (D4).
4. **DPoP.** Each token and resource request carries a JWT signed with
   ES256 (ECDSA P-256), with a fresh `jti`, the `iat` from `exactTime`, and
   a server-supplied nonce that rotates. `generateKey`, `sign` and
   `exportKey` for P-256 are LLP 1069.005 D1b. The key's home is that
   document's ruling: a JWK under `secret.keep` natively, a non-extractable
   `CryptoKey` in IndexedDB on the web, a host-held key after review.
5. **Authorize.** `openAuthSession(authorizationUrl, { callback })`, D1.
6. **Exchange.** Check `state` and `iss` on the callback URL, then `POST`
   the code and verifier with a DPoP proof. Keep the tokens with
   `secret.keep`, and answer `Session { ok, handle, error }`.
7. **Refresh.** As the port refreshes an app-password session today
   (`refreshSession`), with a DPoP proof.

Bluesky's client-metadata document is served at the HTTPS URL that is the
`client_id`: a static file on the app's origin next to the callback page,
and the same URL for a native build (`app.json`'s `origin`).

### D7 — Substitute

LLP 1069.007 D7's paragraph for this capability:

1. **Shape:** a request (a runner ticket, `exact-auth:`).
2. **Pending:** under `EXACT_AGENT=1` or `?agent=1` no browser opens and no
   real account is touched (LLP 1018 D6's rule for the store).
   `state.pending` lists `{ticket, device: {capability: "auth", args: {url,
   callback, ephemeral}}}`, the URL shown so a test checks the query
   (`code_challenge_method=S256`, `state`, `request_uri`). **Answer:**
   `type @t "social.exact.bluesky:/oauth?code=fixture&state=<the
   state>&iss=…"` (the host checks it against the granted callback and
   answers 200), or `tap @t cancel` (499). **Fixture:** `--answer
   auth=<callback URL>`, where `{state}` in it is replaced by the request's
   `state`. `delivery` is `substituted`.
3. **Web override:** none in CDP; the glue holds the request.

The source then calls the token endpoint, a real `fetch` answered by a
fixture server, as the port's `data/tests/signed_in.rs` does for
`createSession`. The sign-in is a deterministic drive: `tap sign-in`,
`state`, answer, `clock settle`, `tree`.

### D8 — Later, in the same shape: Sign in with Apple and passkeys

Both are the same request with another reserved URL. Neither is built here.

- **Sign in with Apple.** `ASAuthorizationAppleIDProvider` on Apple, whose
  sheet returns an identity token and a code; Apple's OAuth endpoint (D1)
  on the web. The grant is `auth.apple <client id>` (the bundle id
  natively, a Services ID on the web: the grammar needs a target), and the
  bake adds `com.apple.developer.applesignin` (LLP 1069.008). App Review
  requires it wherever another third-party login is offered on iOS, so it
  becomes owed once D1 ships a Google or GitHub login there.
- **Passkeys.** WebAuthn is the vocabulary:
  `navigator.credentials.create({ publicKey })` and `.get(…)`, a request
  answered with the credential as JSON.
  `ASAuthorizationPlatformPublicKeyCredentialProvider` on Apple, the
  browser's own call on the web. The grant is `auth.passkey <rp id>`; the
  relying party needs `webcredentials:` on Apple and `/.well-known/webauthn`
  for related origins.

## Not in this RFC

- **An OAuth client library.** Discovery, PKCE, PAR, DPoP and refresh stay
  in the app's source. If a second provider repeats the code, a shared
  TypeScript helper beside `exact-route`'s is the place.
- **A token vault or refresh scheduler.** `secret.keep` and refresh-on-401
  are enough.
- **In-app browsers for content** (`SFSafariViewController`). `openURL`
  covers reading a page.
- **FedCM.** Chrome-only and provider-gated.
- **A redirect fallback on the web** (ruled out).

## Decided

1. The name is `openAuthSession` (D1).
2. Bluesky's OAuth sign-in is one of its admitted asks; no separate trade.
3. DPoP keys follow LLP 1069.005 D1b (D6 step 4).
4. No web redirect fallback; a blocked popup answers 428 and the app asks
   again (D4).

## Implementer and date

None assigned. The first consumer is the Bluesky port's sign-in, replacing
app passwords. It needs:

- LLP 1069.005's digest, random values and P-256 (it can't start without
  them);
- LLP 1069.007's first slice, for the substitute;
- LLP 1069.008's first slice only for an https callback; a private-use

Order: the Apple arm and the TypeScript/Rust binding; the web popup and
