## Rulings (Charlie, 2026-09-27)

- **Q1: the name is `openAuthSession`,** chosen for what an agent or developer will most likely guess right (Charlie: "whatever you think agents will most correctly guess"). It follows Expo's `openAuthSessionAsync` and Apple's `ASWebAuthenticationSession`. The text below uses it.
- **Q2: Bluesky's OAuth sign-in is one of its admitted asks.** `rules/DEFERRED.md` says so explicitly.
- **Q3: DPoP keys follow LLP 1069.005's ruling:** a JWK first, a non-extractable key in IndexedDB on the web, and a host-held key after review.
- **Q4: no redirect fallback on the web.** **This overrides D4's fallback.** A blocked popup fails, and the app asks the person to tap again.

### After review (Charlie, 2026-09-27)

- **Item 1, the web return channel: confirmed.** The popup stays; the
  callback page also returns on a same-origin `BroadcastChannel`; a closed
  popup alone isn't cancellation; the wait is bounded and the app shows its
  own "Signing in… Cancel". COOP providers are supported. (Charlie asked
  for a recommendation; the recommendation was this.)
- **Item 2: `openAuthSession` is forbidden from worker placement on the
  web,** at authoring time.
- **Item 3: two client ids,** one per application type (Claude's call,
  Charlie: "you decide"): a native client metadata document and a web one,
  both derived at bake from the `auth.callback` grants. Check against the
  AT Protocol OAuth spec that a document can't mix types before building.
  **`authCallback()` is admitted** as a binding.
- **Item 4: an interrupted sign-in restarts.** Resuming across a kill is
  cold-start delivery, out of scope (LLP 1069.007).

## Summary

An app that signs in through someone else's account uses OAuth 2.0 or
OpenID Connect: Bluesky, GitHub, Google, or an app's own identity provider.
A native app does this in the system browser (`ASWebAuthenticationSession`
on Apple; RFC 8252 names the rules). A web app does it in a popup. exact2
has none of this. The Bluesky port signs in with an app password, which
Bluesky deprecates for third-party clients.

The proposal is one request. A source asks the host to open an
authorization URL and wait for a callback. The host answers with the
callback URL, or a failure when the person cancels. Everything else stays
in the source:

- building the URL, PKCE and `state`;
- pushed authorization (PAR);
- the code-for-token exchange by `fetch`;
- DPoP proofs;
- keeping the tokens with `secret.keep`.

```ts
// app.ts — the whole of the new surface a TypeScript source sees
export const grants = [
  'net.fetch https://bsky.social',        // plus the PDS, plc.directory, … (D6)
  'auth.session https://bsky.social',
  'auth.callback social.exact.bluesky:/oauth',
  'auth.callback https://app.example/.exact/auth/callback',  // the app's own origin
  'secret.keep bluesky.session',
  'secret.keep bluesky.pending',
].join('\n');

const callback = authCallback();         // this carrier's callback, known before PAR (D2)
// … PAR with redirect_uri = callback, state, code_challenge, a DPoP proof (D6) …
const back = await openAuthSession(url, { callback, state });
// back: "social.exact.bluesky:/oauth?code=…&state=…&iss=…"
```

It is a request, like `native.later` (LLP 1067 D1). Tickets, supersession,
`pending(x)`, worker placement and failure as data apply unchanged, and no
request type gains a field. The host checks where the session may go, that
the callback is this request's exactly, and that its `state` is this
request's; the source checks everything else before it spends the code.

## 0. What r3 changed (reviews by Astra and Grok)

Both reviews: "revise and re-review". Dispositions are in the review
files. Both were asked for a security review of the callbacks, `state`,
key storage and the web popup. The changes, in order of weight:

- **PAR hides `state`** (both). With PAR the authorization URL carries only
  `client_id` and `request_uri`; `state`, the challenge and `redirect_uri`
  went in the pushed request. r2 had the web glue and the substitute read
  `state` from that URL. The request body now carries `state`, and the
  host compares the callback's against it (D1, D4, D7).
- **The callback is known before PAR** (both). r2 rewrote a native callback
  to the web's callback page in the bake, but `redirect_uri` is bound into
  the pushed request before the host sees anything. `authCallback()` gives
  the source this carrier's callback first; the host never rewrites (D2).
- **The web popup survives COOP** (both; touches ruling Q4). A provider's
  `Cross-Origin-Opener-Policy` severs `window.opener` and can make the
  opener's `closed` read true while the person is still signing in. The
  callback page now returns on a same-origin `BroadcastChannel` as well as
  `opener.postMessage`, and `closed` alone is no longer a cancellation.
  No redirect fallback is added (D4).
- **Apple's custom-scheme matcher matches the scheme only** (both). The
  host compares scheme, host and path with the request's callback after
  every completion (D3). The claim that leaving the scheme unregistered
  stops another app claiming it is withdrawn: it reserves nothing (D2).
- **The transaction is bound** (Astra): a record keyed by `state` holds the
  issuer, client, callback, endpoints, verifier, DPoP key and expected
  account; single use, with an expiry; `iss` is compared to the issuer
  chosen before opening, and the token's `sub` to the expected DID (D6).
- **DPoP starts at PAR, and refresh is the token endpoint** (both): r2
  began DPoP at the token request and refreshed with the app-password
  `refreshSession` (D6).
- **No real sign-in with seeded entropy** (Astra; touches LLP 1069.005's
  ruling). Under the agent, sign-in is fixture-only; a real authorization
  server is reached only with OS entropy (D7).
- **The web popup opens in the press's own call stack** (both): today a
  `request` op waits on `httpHelpers()` (`glue.js:695`), which Safari's
  activation rule does not survive (D4). The callback page's script is
  external or hashed, because the CSP has no `'unsafe-inline'`
  (`host/render/src/serve.rs:1256`).
- **Supersession and the one-session rule** (both): a superseding request
  cancels its predecessor and starts; 409 is only for a different live
  session; a late completion is dropped unless the ticket is still held
  (D3). `exact-auth:` runs on the independent lane, as `native.later`
  does (D1).
- **"An app killed while the sheet is up can finish" is withdrawn** (both):
  the session, popup and ticket die with the process; sign-in restarts.
- **Smaller:** macOS signing gets associated domains and the AASA gets
  `webcredentials` (D2); grants for discovery and `io_grants` stripping
  `auth.*` (D6); a `start()` that returns false is 502 and the session is
  retained until completion (D3); 200 means a callback arrived, not a
  sign-in (D1); D8's Sign in with Apple and App Review claims corrected;
  citations fixed.

## Motivation

- **Bluesky.** The AT Protocol's login for third-party clients is OAuth
  with PKCE, PAR and DPoP. The port uses `com.atproto.server.createSession`
  with an app password (`bluesky-exact2/data/src/writes.rs:57`). It works,
  but it asks people to mint a credential by hand, and Bluesky is moving
  away from it.
- **Everything else.** "Continue with Google/GitHub/Apple", or a delegated
  login (Auth0, Clerk, Cognito), is the same flow. `expo-auth-session` is
  among Expo's most used packages (LLP 1069 §2.6).
- **It can't be done today.** `openURL` hands the URL to the system
  browser, which owns the page; the callback returns as a `navigate` event
  to the navigation root (LLP 1038 D8). That event has no ticket and no
  source, the code is visible to the view, and the tab stays open behind
  the app. RFC 8252 and the providers expect an in-app authentication
  session instead.

## Design

### D1 — One request to a reserved URL, answered with the callback URL

`openAuthSession(url, options)` is a request to `exact-auth:`, as
`native.later` is a request to `exact-native:` (LLP 1067 D1,
`runner/src/request.rs:87`). `Request::is_auth` names the URL, as
`is_native` does (`:91`); the rest rides in the JSON body:

```json
{ "url": "https://bsky.social/oauth/authorize?client_id=…&request_uri=…",
  "callback": "social.exact.bluesky:/oauth",
  "state": "…",
  "ephemeral": false }
```

`state` is required and non-empty. The host never parses OAuth fields out
of `url`: with PAR they are not there.

**The lane.** Like `native.later` (LLP 1067 D3), `exact-auth:` leaves the
ordered HTTP lane: it is presenter-owned, handed off, independent, with a
small reply ceiling. A sheet open for minutes must not hold every ordered
fetch behind it. The TypeScript binding marks it independent as
`native.later` does (`js/src/prelude.js:309`). The host checks the grants
(D2) before anything opens.

The reply is HTTP-shaped. The statuses are this protocol's own
conventions, not their HTTP meanings:

| status | body | when |
|---|---|---|
| 200 | the full callback URL | a callback matching this request's callback and `state` arrived. It may carry an OAuth `error`; 200 is delivery, not a sign-in |
| 499 | `cancelled` | the person closed the sheet or pressed Cancel |
| 403 | the grant | a grant refused it (D2) |
| 409 | `already open` | a different session is open in this window (D3) |
| 428 | `popup blocked` | web only: the popup was blocked, or the request came outside a press (D4) |
| 501 | the host's name | no system browser (Linux, D5), or an https callback below iOS 17.4 / macOS 14.4 (D3) |
| 502 | the error | anything else, a callback that fails the host's checks included |

A TypeScript `openAuthSession` resolves with the string, or rejects with
the status and message. A Rust source receives the reply as any other: the
runner sees `Answer::Later(Request { url: "exact-auth:", … })`, and the
Bluesky crate's own `Need` gains a step for it. Failure is data (LLP 1016
D4), so "cancelled" is a value the view can show.

The reply goes to the **source**, never to the plan. The callback URL
carries an authorization code, a credential while it lasts, so LLP 1018
D5's rule for tokens applies: the source exchanges it, keeps the result
with `secret.keep`, and the plan sees `Session { ok, handle, error }`.
The runner's journal already logs a response's status and size, never its
body (`runner/src/request.rs:290`). The source must not copy the callback
URL, the code or a token into `Session.error`, a log line, carried state
or an error message; a failed request's message is kept, so the host's
own 502 text never includes the callback. "Never shown" is about the app
and the agent's inspection: browser chrome can show the callback URL for
a moment.

*Rejected:* the callback through `navigate` (LLP 1038 D8). No ticket, it
reaches the view, and on Apple the session captures its own callback, so
the event would never fire.

*Rejected:* a first-party native module over LLP 1067. `native.later` plus
about forty lines of Swift is the Apple arm, but every OAuth app would copy
it; the web's callback page is a bake output; and the grants and
entitlements (D2) are the bake's business, not a module's.

### D2 — Two grants: where the person signs in, and where they come back

- **`auth.session <origin>`** admits authorization URLs on that origin, with
  `net.fetch`'s grammar, the `https://*.domain` form included. A `url`
  outside every such grant is refused with 403 before anything opens.
- **`auth.callback <callback>`** admits one callback. An app lists one per
  form it uses:
  - `scheme:/path`, a private-use URI scheme (RFC 8252 §7.1: one slash).
    For the AT Protocol the scheme is the `client_id`'s hostname reversed;
    elsewhere, by convention, the bundle id reversed;
  - `https://host/path`, a claimed HTTPS callback (RFC 8252 §7.2).

  A `callback` that isn't granted is refused with 403. A source whose
  grants were narrowed (`Request.grants`) is checked against the narrowed
  set, as the surface checks are (`runner/src/request.rs:163`).

Two kinds, not one line with two values: the grant grammar is one
capability, one target (`vendor/ibex2/src/grant.rs:290-294`). Both are
exact2 grants that `io_grants` must strip before `ibex2` parses the rest,
as it strips `surface.read` and `surface.write` today
(`runner/src/request.rs:20`) and as LLP 1069.008 will strip `device.*`;
`GrantSet::parse` refuses an unknown capability (`grant.rs:355`). The
host's `exact-auth:` arm checks them.

**The callback is known before PAR.** The source puts `redirect_uri` into
the pushed request before the host sees anything, so the host can't
rewrite it. `authCallback()` (TypeScript; `exact-data` in Rust) returns
this carrier's granted callback: on a native build the private-use or
claimed https callback the app granted, on the web
`https://<app origin>/.exact/auth/callback`, pinned exactly (no trailing
slash, no `index.html`). The source uses that string for PAR, for
`openAuthSession`'s `callback` and for the token request; the provider's
registration and client metadata list every form.

The bake derives the platform setup from these lines, through LLP
1069.008's table:

- **An https callback on Apple** needs the `webcredentials:host` associated
  domain in the entitlements and a `webcredentials` entry in the host's
  `apple-app-site-association`: `ASWebAuthenticationSession.Callback.https`
  requires web credentials, not `applinks:`. Today the entitlements helper
  writes `applinks:` only and reads `host.ios` only
  (`host/apple/build.mjs:425`), macOS signing passes no entitlements file
  (`host/apple/build.mjs:1097`), and the web build's AASA carries
  `applinks` only (`host/web/build.mjs:324`). All three change for an https
  callback, macOS included; `applinks:` stays LLP 1038 D8's routing.
- **A private-use scheme** needs no `CFBundleURLTypes` entry, and gets
  none. The session captures its own redirect, which is why the code never
  becomes a `navigate` event. Not registering the scheme reserves nothing:
  another app can register the same scheme. What protects the code is the
  session's in-process delivery and PKCE; not registering only keeps this
  app from receiving the callback through `openURL` if the session fails.
- **The web.** The callback page at `/.exact/auth/callback` (D4).

### D3 — Apple: `ASWebAuthenticationSession`, one per request

The executor hands an `exact-auth:` request to the presenter on the main
thread, which creates the session and **retains it until its completion
handler runs** (releasing it cancels it):

- **The callback matcher.** `.customScheme(scheme)` or
  `.https(host:path:)`, which need iOS 17.4 / macOS 14.4 (the SDK's
  `ASWebAuthenticationSessionCallback.h`), above the floor of 17.0 / 14.0
  (`host/apple/build.mjs:85-86`). Below it, the older
  `callbackURLScheme:` initializer covers private-use schemes only, and an
  https callback there answers 501.
- **The host's own match.** `.customScheme` and `callbackURLScheme:`
  match the scheme only, so a completion's URL is accepted only if its
  scheme, host and path equal **this request's** `callback` exactly, with
  no userinfo, no unexpected port, and `https` for a claimed callback; its
  query is the answer, and its `state` must equal the request's. A URL that
  fails is 502, never a 200 and never a `navigate`: the session has
  already ended.
- **`prefersEphemeralWebBrowserSession`** from `ephemeral`. `true` asks for
  no shared cookies ("switch account"); `false`, the default, lets a person
  already signed in in Safari tap once. It is a preference: another default
  browser on macOS may ignore it, and the popup on the web ignores it.
- **`presentationContextProvider`**: the window of the ExactKit session
  that owns the request. On iOS, that session's scene's window; on macOS,
  the window holding the node that asked. A worker-placed source uses its
  own session's window, never whichever window has focus. `RequestOut`
  carries a target name, not a window (`runner/src/request.rs:421`), so the
  handoff learns the owning session.
- **`start()` returning false** (no window, no scene) is 502.

The completion handler replies on the runner's thread, as `fulfill` does:
an accepted URL is 200, `canceledLogin` is 499, anything else 502. It
fulfils only while the runner still holds the ticket, as the HTTP executor
drops forgotten outcomes (`host/apple/src/executor_core.rs:241-284`).

**One live session per window, and supersession.** When the runner forgets
a ticket (superseded, the resource gone, LLP 1016 D5), or the session's
ExactKit session is torn down or reloaded, or its window closes, the host
calls `cancel()` and suppresses the late completion exactly once. A
request that supersedes the window's live session cancels it first and
then starts, so a double tap does not answer 409. A request for a
different resource while a session is open in that window answers 409.
Supersession does not answer 499.

`SFAuthenticationSession` and in-app `WKWebView` login are not offered:
providers refuse embedded web views, and a web view can read the password.

### D4 — Web: a popup to the app's own callback page

The browser has no auth-session API, so the web arm is `window.open`, a
same-origin callback page, and two return channels:

1. **Open, in the press's own call stack.** Safari lets `window.open`
   through only inside the user-activation call stack of the press; a
   promise that waits on `httpHelpers()` (`glue.js:7`, `:695`) is too late.
   So the glue handles an `exact-auth:` request synchronously inside
   `apply()` for the press's batch, before `send()` returns, and never
   through the HTTP helpers. A request that arrives outside a press's
   batch (a worker-placed source, or a source that awaited something
   first) answers 428. The popup's name is unguessable (random per
   request), not the ticket, since tickets restart at 1 per incarnation.
2. **Callback page.** The bake emits one static page at exactly
   `/.exact/auth/callback`, served without a trailing-slash redirect or the
   app's router, with no third-party content, `Referrer-Policy:
   no-referrer`, `Cache-Control: no-store`, and its script either an
   external same-origin file or hashed into the CSP the way `capture()` is
   (`host/render/src/serve.rs:1256`; there is no `'unsafe-inline'`). The
   script:
   - posts a typed message `{type: "exact-auth", url: location.href}` on
     a `BroadcastChannel` named for the app, and to `window.opener` with
     the app's own origin as target when `opener` is still there;
   - replaces its own URL (`history.replaceState`) so the code does not
     linger, and closes itself;
   - never prints the URL, even when neither channel delivers.

   The `BroadcastChannel` is the channel that survives a provider's
   `Cross-Origin-Opener-Policy: same-origin`, which severs `opener` and
   leaves nothing for `postMessage`: the callback page is the app's own
   origin, so it joins the app's channel. The provider registers
   `https://<app origin>/.exact/auth/callback`.
3. **Answer.** The glue accepts the first message whose origin is the
   app's own, whose `type` is `exact-auth`, which comes from the owned
   popup where `event.source` is available (the opener path), whose URL's
   scheme, host and path equal the request's callback, whose `state`
   equals the request's, and while the ticket is live. It answers 200. A
   same-origin script can still post a matching message: the web app's
   own origin is inside its trust boundary, and these checks do not defend
   against XSS.
4. **Cancellation and the bound.** A provider's COOP can make the popup
   reference read `closed === true` while the person is still signing in,
   so `closed` alone is not a cancellation. The glue answers 499 when
   `closed` has been true for a grace period *and* no message arrived,
   and the view offers its own cancel (`tap` on it supersedes). A request
   with no message within a bound (the survey's measurement sets it; ten
   minutes until then) answers 499. A new press supersedes (D3's rule).

**A blocked popup fails** (ruled): `window.open` returns null, and the
request answers 428 `popup blocked`. The app shows it and asks the person to
tap again. There is no redirect fallback and no page reload.

A popup is blocked when the request comes too long after the press, or
off its call stack. So a source does discovery, key generation and PAR
when the sign-in screen appears, keeps the transaction (D6), and calls
`openAuthSession` directly from the press. The tap-again path then usually
succeeds without redoing PAR while the `request_uri` is fresh; when it has
expired, the source regenerates it before the next press. Another blocked
popup stays a supported failure. Safari and Chrome, cold and warm, main
thread and worker placement, are measured before this ships (LLP 1069 §7,
open item 6).

A web build served from a development origin registers that origin with
the provider as usual.

### D5 — Linux: unavailable, declared

The Linux host is a painter over DRM/KMS or a buffer (LLP 1015), with no
browser to hand a URL to. An `exact-auth:` request answers 501, "no system
browser on this host". A desktop Linux host would use RFC 8252 §7.3:
`xdg-open`, a loopback redirect to `http://127.0.0.1:<port>/`, and a
one-shot listener. Written down so nobody invents another shape. The
Bluesky port on Linux keeps app passwords until then.

### D6 — The source keeps the protocol: PKCE, PAR, DPoP, tokens

Nothing below is new API beyond `authCallback()`. It is what a source
writes with `fetch`, `secret.keep`, the time fact and LLP 1069.005, and the
Bluesky port is its first test. The AT Protocol's OAuth profile is the
reference for each step.

1. **Discovery.** Resolve the handle to a DID, the DID to its PDS, the
   PDS's protected-resource metadata to its authorization server, and that
   server's metadata. Grants: `net.fetch` for the PDS hosts
   (`https://*.host.bsky.network`, as the port already grants,
   `bluesky-exact2/data/src/session.rs:20`), `plc.directory`, and each
   authorization server; an `auth.session` for each.
2. **The transaction.** Before anything opens, the source makes one record
   and keeps it with `secret.keep bluesky.pending`:
   - `state` (32 random bytes, base64url), the PKCE verifier (32 random
     octets, base64url-encoded; the S256 challenge is SHA-256 of the
     verifier's ASCII, RFC 7636 §4), from `crypto.getRandomValues` and
     `crypto.subtle.digest` (LLP 1069.005 D1, D2);
   - the issuer chosen, the `client_id`, `authCallback()`, the token and
     PAR endpoints, the expected DID;
   - the DPoP key's handle (step 3); a creation time and an expiry.

   It is single-use: consumed at the exchange, dropped on expiry or on a
   new sign-in, and never overwrites an active session's key or tokens.
   The launch seed can't be a verifier: one 53-bit number per launch,
   visible to the agent. `secret.keep` is not a durability receipt (Apple
   logs a failed write, `host/apple/src/host.rs:622`); the record exists
   for in-process completion, not for resuming after the process dies. An
   interrupted sign-in restarts.
3. **DPoP key.** Generated before PAR, for this transaction and the
   session it becomes (RFC 9449; `generateKey`, `sign` and `exportKey` for
   P-256 are LLP 1069.005 D1b). Its home is that document's ruling: a JWK
   under `secret.keep` natively, a non-extractable `CryptoKey` in
   IndexedDB on the web, a host-held key after review. Non-extractable
   means the private bytes can't be exported; same-origin script can still
   sign with it. The key is bound to the issuer, account and tokens; a lost
   key means signing in again, never a new key with the old refresh token.
   LLP 1069.005 does not yet write the "keep this key" operation for every
   host (for Rust on the web in particular); this RFC needs it (after
   review, 5).
4. **PAR, with DPoP.** A `POST` to the pushed-authorization endpoint with a
   DPoP proof, `redirect_uri = authCallback()`, `state`, the challenge;
   it returns a `request_uri`. Done before the press on the web (D4).
5. **Proofs.** Each PAR, token and resource request carries a fresh proof:
   ES256, the public JWK in the header, `jti`, `htm`, `htu`, `iat` in
   seconds from `exactTime`, `ath` on resource requests, and the server's
   nonce. A `use_dpop_nonce` error retries once with a new proof and the
   new nonce; the authorization server's and each resource server's
   nonces are kept apart.
6. **Authorize.** `openAuthSession(authorizationUrl, { callback, state })`,
   D1.
7. **Exchange.** Look up the transaction by the callback's `state`
   (exactly one `state`, `iss` and `code` value each; an `error` is
   reported). Compare `iss` with the issuer saved in step 2 before
   anything else, and send the code to the token endpoint saved there,
   never one chosen from the response (RFC 9207 §2.4). `POST` the code and
   verifier with a DPoP proof. Check that the token response's `sub` is the
   expected DID and that the DID's PDS names this issuer. Keep the tokens
   with `secret.keep`, drop the transaction, and answer `Session { ok,
   handle, error }`. Tests cover a missing, duplicated, mismatched,
   expired and replayed `state`, a wrong `iss`, and a token for another
   account.
8. **Refresh.** `grant_type=refresh_token` at the authorization server's
   token endpoint, with the session's DPoP key; not the app-password
   `com.atproto.server.refreshSession` the port calls today
   (`session.rs:141`). Refreshes are serialised, and the rotated refresh
   token replaces the old one in one `secret.keep` write.

Bluesky's client-metadata document is served at the HTTPS URL that is the
`client_id`, a static file on the app's origin next to the callback page.
It pins `token_endpoint_auth_method: none`, `dpop_bound_access_tokens:
true`, the grant types, the scopes, `application_type`, and every
`redirect_uri`. Whether one `client_id` serves the native and web builds
(its `application_type` is one value, and the native scheme is the
`client_id`'s hostname reversed) is for Charlie (after review, 3).

### D7 — Substitute

LLP 1069.007 D7's paragraph for this capability:

1. **Shape:** a request (a runner ticket, `exact-auth:`).
2. **Pending:** under `EXACT_AGENT=1` or `?agent=1` no browser opens and no
   real account is touched (LLP 1018 D6's rule for the store).
   `state.pending` lists `{ticket, device: {capability: "auth", args:
   {origin, path, callback, state, ephemeral}}}`: the authorization URL's
   origin and path, the query's parameter *names* and the values of
   `client_id` and `request_uri`, never other values (a URL can carry an
   `id_token_hint`). A test checks PKCE and `redirect_uri` in the PAR
   request the fixture server received, not in this URL. **Answer:** `type
   @t "social.exact.bluesky:/oauth?code=fixture&state=<the state>&iss=…"`
   (the host checks it as D3 does and answers 200), or `tap @t cancel`
   (499). **Fixture:** `--answer auth=<callback URL>`, where `{state}` in
   it is replaced by the request body's `state`. `delivery` is
   `substituted`.
3. **Disclosure:** the reply to `type @t`, the journal (`device auth 7
   answered: callback accepted`, `… cancelled`) and any validation error
   never echo the callback URL.
4. **Web override:** none in CDP; the glue holds the request.

**Fixture-only.** Under the agent, entropy is the seeded stream (LLP
1069.005 D2b), so the verifier, `state` and key are predictable. Sign-in
under the agent therefore runs against fixture servers only: discovery,
PAR and the token endpoint are local, as the smoke's own server; an agent
session never sends a seeded verifier to a real authorization server.
Reaching a real one means `EXACT_DEVICE=real` (LLP 1069.007 D8), which
restores OS entropy, and never a production bake with agent mode reached
(1069.007 D2). The port's `data/tests/signed_in.rs` fakes `createSession`
in process; the OAuth fixture is a server of the same kind for PAR and the
token endpoint. The sign-in is a deterministic drive: `tap sign-in`,
`state`, answer, `clock settle`, `tree`. DPoP signatures differ run to run
on the web (ECDSA, LLP 1069.005), so a test asserts their verification,
not their bytes.

### D8 — Later, in the same shape: Sign in with Apple and passkeys

Neither is built here, and each needs more than another reserved URL.

- **Sign in with Apple.** `ASAuthorizationAppleIDProvider` on Apple, whose
  sheet returns an identity token and a code rather than a callback URL, so
  its 200 body is different. On the web, Apple's flow posts the name and
  email with `form_post`, which a static page reading `location.href`
  cannot recover, and the code exchange needs a client secret the
  developer signs, which can't ship in app source: it needs a server.
  The grant would be `auth.apple <client id>` (the bundle id natively, a
  Services ID on the web: the grammar needs a target), and the bake adds
  `com.apple.developer.applesignin` (LLP 1069.008). App Review §4.8 asks
  for an equivalent privacy-preserving login option in some cases where a
  third-party login is the primary one, with exceptions, among them a
  client for a specific third-party service; the Bluesky client is such a
  client. Whether a Google or GitHub login elsewhere triggers it is a
  per-app reading of §4.8.
- **Passkeys.** WebAuthn is the vocabulary:
  `navigator.credentials.create({ publicKey })` and `.get(…)`, a request
  answered with the credential as JSON.
  `ASAuthorizationPlatformPublicKeyCredentialProvider` on Apple, the
  browser's own call on the web. The grant is `auth.passkey <rp id>`; the
  relying party needs `webcredentials:` on Apple, and
  `/.well-known/webauthn` only for related origins.

## Not in this RFC

- **An OAuth client library.** Discovery, PKCE, PAR, DPoP and refresh stay
  in the app's source. If a second provider repeats the code, a shared
  TypeScript helper beside `exact-route`'s is the place.
- **A token vault or refresh scheduler.** `secret.keep` and refresh-on-401
  are enough.
- **Resuming a sign-in after the process dies.** It restarts (D6 step 2).
- **In-app browsers for content** (`SFSafariViewController`). `openURL`
  covers reading a page.
- **FedCM.** Chrome-only and provider-gated.
- **A redirect fallback on the web** (ruled out).

## Decided

1. The name is `openAuthSession` (D1).
2. Bluesky's OAuth sign-in is one of its admitted asks; no separate trade.
3. DPoP keys follow LLP 1069.005 D1b (D6 step 3).
4. No web redirect fallback; a blocked popup answers 428 and the app asks
   again (D4).

## As built (2026-09-27, Claude (Opus 5.5))

Built on every host to D1–D7 as ruled, with LLP 1069.005 D1b under it
(the P-256 and "keep this key" operation after-review item 5 asked for).

**Checked before building: `application_type` in the AT Protocol's OAuth
spec** (atproto.com/specs/oauth, read 2026-09-27). Client metadata's
`application_type` is optional, one of `web` (the default) or `native`,
borrowed from OpenID Connect and used by the authorization server to
enforce the type's practices. A `web` client's `redirect_uri` is an HTTPS
URL; a `native` client may use a private-use scheme (the `client_id`'s
hostname reversed, then `:/` and a path, one slash) or an HTTPS URL. The
spec gives a document one type and nowhere lets one document declare both
kinds of redirect, so a document can't mix them: ruling item 3's two
client ids stand. `dpop_bound_access_tokens: true`, `grant_types` with
`authorization_code`, `response_types` with `code` and a `scope` with
`atproto` are required; a public client omits `private_key_jwt`.

**Runner** (`runner/src/auth.rs`, one rule for every host):

- `Request::auth`/`is_auth` (`exact-auth:`, the independent lane, a 64 KiB
  reply); `io_grants` strips `auth.*` before ibex2.
- `Session` (the body, D1), `check_grants` (D2: `auth.session` by
  `net.fetch`'s grammar, the `https://*.domain` form included;
  `auth.callback` exactly; a narrowed source by its own lines; on a
  loopback development page its own `/.exact/auth/callback` without a
  grant), `accept` (D3's match: scheme, host with the same port, path, no
  userinfo, exactly one `state` equal to the request's; the reason never
  echoes the URL), `carrier_callback` (`authCallback()`, D2).
- `arm(runner, request, agent, browser, web origin)`: refuse now (403, 501
  on Linux, 409 for another target's live session, 502 for a bad body),
  hold for the agent, or hand the host the session. The settled answer
  rides the admission-refusal path (`take_request_refusal`), so Apple and
  Linux deliver it on the next pump unchanged; the web fulfils kind 9.
- The one-session rule and supersession (D3): a second press of the same
  target supersedes (the runner forgot the old ticket; `forgotten()` hands
  it to the host to cancel, and `complete()` drops its late completion); a
  different target's press while one is live is 409.
- **The held request** is the first HTTP-shaped hold (LLP 1069.007 D3):
  `Runner::hold_request` holds it under its own ticket; `pending()` lists it
  once, under `device`, and `has_pending()` leaves it out, so no clock
  waits on it; it is retired when the runner forgets the ticket.
  `type @t <callback URL>` is checked by `accept` before the hold is spent
  (a wrong URL is refused by name and can be corrected); `tap @t cancel` is
  499. The journal says `device auth 7 held (agent)`, `auth 7: callback
  accepted`, never the URL.
- The summary `pending` shows (D7): the URL's origin, path and parameter
  names, the values of `client_id` and `request_uri` only, the callback,
  `state` and `ephemeral`.

## For Charlie after review

Items 1–4 are ruled (§Rulings, "After review"); 5–7 remain.

1. **The web return channel (touches Q4).** Both reviews show COOP breaks
   r2's popup: `opener` severed, `closed` true while signing in. r3 keeps
   the popup and adds no redirect fallback, but returns on a same-origin
   `BroadcastChannel`, stops treating `closed` alone as cancellation, and
   bounds the wait. The person sees a "waiting for sign-in" state with its
   own cancel a little longer when they close the popup. Confirm, or rule
   that COOP providers are unsupported on the web.
2. **Worker-placed sign-in on the web.** A request that isn't in the
   press's call stack answers 428 (D4), so a worker-placed source can't
   open the popup. Forbid `openAuthSession` from worker placement in the
   binding, or accept 428? Recommendation: forbid, so the failure is at
   authoring time.
3. **One `client_id` or two** for Bluesky's native and web builds, and the
   production client-id domain and callback URIs. `application_type` is a
   single value, and the native scheme must be the client-id hostname
   reversed. The same answer names `authCallback()` (D2), a second binding
   beside `openAuthSession` that r3 adds because the callback must be known
   before PAR; confirm the name and that it is admitted.
4. **An interrupted sign-in restarts.** r2 promised an app killed with the
   sheet up could finish; nothing in the design delivered that, and it is
   withdrawn. Confirm restart is acceptable.
5. **Q3 stands, with a gap.** The key lives where the ruling says, but LLP
   1069.005 leaves the cross-host "keep this key" operation unwritten
   (Rust on the web especially). It is a prerequisite here; LLP 1069.005
   should write it.
6. **Sign-in under the agent is fixture-only** (D7), and depends on LLP
   1069.007's production gate (its after-review item 1).
7. **An implementer and a date** (`rules/RULES.md`).
