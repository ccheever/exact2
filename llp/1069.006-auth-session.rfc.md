# LLP 1069.006: Signing in through the system browser

**Type:** RFC
**Status:** Draft; Charlie's rulings recorded 2026-09-27 (§Rulings, which overrides the text below where they differ)
**Systems:** Runner (a reserved request URL beside `exact-native:`; no new request field), Grants (`auth.session`, `auth.callback`), TypeScript and Rust sources (one binding each), Apple hosts (`ASWebAuthenticationSession` on iOS and macOS), Web host (a popup, with a redirect fallback, and a static callback page), Linux host (declared unavailable), the bake (entitlements from the grants, LLP 1069.008), Agent API (a fixture answer, LLP 1069.007)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-27
**Related:** LLP 1069 §5 #7 (the survey item this designs) and §3 (the consumers); LLP 1069.005 (randomness and hashing, which PKCE and DPoP need); LLP 1069.007 (agent substitutes); LLP 1069.008 (permissions and entitlements derived from grants); LLP 1018 D5 (the token never enters the plan) and D6 (the secret store per host); LLP 1016 D4 (failure is data) and D5 (one request per resource, the newest wins); LLP 1038 D8 (an incoming URL is one `navigate` event); LLP 1067 D1 (a long call is a request to a reserved URL); LLP 1054 (the Bluesky port, which signs in with an app password); `rules/DEFERRED.md` (Bluesky admitted as a consumer, 2026-09-27)

## Rulings (Charlie, 2026-09-27)

- **Q1: the name is `openAuthSession`,** chosen for what an agent or developer will most likely guess right (Charlie: "whatever you think agents will most correctly guess"). It follows Expo's `openAuthSessionAsync` and Apple's `ASWebAuthenticationSession`. The text below uses it.
- **Q2: Bluesky's OAuth sign-in is one of its admitted asks.** `rules/DEFERRED.md` says so explicitly.
- **Q3: DPoP keys follow LLP 1069.005's ruling:** a JWK first, a non-extractable key in IndexedDB on the web, and a host-held key after review.
- **Q4: no redirect fallback on the web.** **This overrides D4's fallback.** A blocked popup fails, and the app asks the person to tap again.

## Summary

An app that signs in through someone else's account uses OAuth 2.0 or
OpenID Connect. Examples are Bluesky, GitHub and Google, and any app of
ours with its own identity provider. A native app does this in the system
browser: `ASWebAuthenticationSession` on Apple. A web app does it with a
popup or a redirect (RFC 8252 names the native rules). exact2 has none of
this today. The Bluesky port signs in with an app password, which Bluesky
deprecates for third-party clients. RealWorld posts a password to its own
API.

The proposal is one request. A source asks the host to open an
authorization URL and wait for a callback. The host answers with the
callback URL, or a failure when the person cancels. Everything else stays
in the source, where it already is:

- building the URL, PKCE and `state`;
- pushed authorization (PAR);
- the code-for-token exchange by `fetch`;
- DPoP proofs;
- keeping the tokens with `secret.keep`.

```ts
// app.ts — the whole of the new surface a TypeScript source sees
export const grants = [
  'net.fetch https://bsky.social',
  'auth.session https://bsky.social',
  'auth.callback social.exact.bluesky:/oauth',
  'secret.keep bluesky.session',
].join('\n');

const back = await openAuthSession(url, { callback: 'social.exact.bluesky:/oauth' });
// back: "social.exact.bluesky:/oauth?code=…&state=…&iss=…"
```

It is a request, like `native.later` (LLP 1067 D1). So tickets,
supersession, `pending(x)`, worker placement and failure as data all apply
unchanged, and no request type gains a field. The host arm is small on each
host. The rest of the protocol is ordinary source code, so the feature is
core rather than a module every app copies.

## Motivation

- **Bluesky.** The AT Protocol's supported login for third-party clients
  is OAuth with PKCE, PAR and DPoP. The port uses
  `com.atproto.server.createSession` with an app password
  (`bluesky-exact2/data/src/session.rs`, README "Sign in with your handle
  and an **app password**"). That works today, but it asks people to mint
  a credential by hand and hand it to the app, and it is the path Bluesky
  is moving away from.
- **Everything else.** Most apps with accounts offer "Continue with
  Google/GitHub/Apple", or delegate their own login to an identity
  provider (Auth0, Clerk, Cognito). All of these are the same flow.
  `expo-auth-session` and `expo-web-browser`'s auth session are among
  Expo's most used packages (LLP 1069 §2.6).
- **It can't be done in an app today.** `openURL` hands the URL to the
  system browser, which then owns the page, and the callback returns as a
  `navigate` event to the navigation root (LLP 1038 D8). That event has no
  ticket and no source, the code is visible to the view, the browser tab
  stays open behind the app, and on iOS App Review rejects the flow.
  The system session is the platform's answer to all four.

## Design

### D1 — One request to a reserved URL, answered with the callback URL

A source's `openAuthSession(url, options)` is a request to `exact-auth:`, in the
same way `native.later` is a request to `exact-native:` (LLP 1067 D1).
`Request::is_auth` names the URL, as `is_native` does, with the rest of the
request carried in its JSON body:

```json
{ "url": "https://bsky.social/oauth/authorize?client_id=…&request_uri=…",
  "callback": "social.exact.bluesky:/oauth",
  "ephemeral": false }
```

The reply is HTTP-shaped:

- **200:** the body is the full callback URL, query and fragment included.
- **499:** the person closed the sheet or pressed Cancel. The body is
  `cancelled`.
- **403:** a grant refused it (D2).
- **501:** the host has no session (Linux, D5). The body names the host.

A TypeScript `openAuthSession` resolves with the string, or rejects with the
status and message. A Rust source receives the reply as any other request's
reply: the answer names a `Need::Authorize` and its `parse` receives the
response. Failure is data (LLP 1016 D4), so "cancelled" is a value the view
can show, not an exception.

The request's reply goes to the **source**, never to the plan. The callback
URL carries an authorization code, which is a credential for as long as it
lasts. So it follows LLP 1018 D5's rule for tokens: the source exchanges it
and keeps the result with `secret.keep`, and the plan sees
`Session { ok, handle, error }`. `state`, the journal, `carry` and a
screenshot never show the code.

*Rejected:* delivering the callback through `navigate` (LLP 1038 D8). It
has no ticket, it reaches the view, and on Apple the session captures its
own callback, so the event would never fire.

*Rejected:* a first-party native module over LLP 1067. It would work on
Apple, since `native.later` plus about forty lines of Swift is the whole
arm. But every OAuth app would copy those lines. The web arm needs the glue
before boot (D4), which a page module loaded after first paint doesn't
have. And the grants and entitlements (D2) have to be the bake's business,
not an app module's.

### D2 — Two grants: where the person signs in, and where they come back

- **`auth.session <origin>`** admits authorization URLs on that origin.
  It has the same grammar as `net.fetch`, including the `https://*.domain`
  subdomain form. A request whose `url` falls outside every such grant is
  refused with 403 before anything opens.
- **`auth.callback <callback>`** admits one callback, in one of two forms:
  - `scheme:/path`, a private-use URI scheme (RFC 8252 §7.1). By
    convention it is the bundle id reversed.
  - `https://host/path`, a claimed HTTPS callback (RFC 8252 §7.2).

  A request whose `callback` isn't granted is refused with 403.

These are two kinds rather than one line with two values, because the
grant grammar is one value per line (`secret.keep castle.session old` is a
parse error, `vendor/ibex2/src/grant.rs`).

The bake derives the platform setup from these lines (LLP 1069.008):

- **An https callback on Apple** needs an associated domain
  (`webcredentials:host`) and the host's `apple-app-site-association`.
  The associated domain joins the ones `host.ios.associatedDomains`
  already produces (`host/apple/build.mjs:435`).
- **A private-use scheme** needs nothing. `ASWebAuthenticationSession`
  matches it without a `CFBundleURLTypes` entry, and not registering it
  keeps another app from claiming the callback. It is not added to
  `urlSchemes`.
- **The web.** The callback is always the app's own origin (D4). It isn't
  a grant line there, so the bake maps a granted native callback to
  `/.exact/auth/callback` on the web.

### D3 — Apple: `ASWebAuthenticationSession`, one per request

The executor hands an `exact-auth:` request to the presenter on the main
thread. The presenter creates the session:

- **The callback matcher.** `.customScheme(scheme)` for a private-use
  scheme, or `.https(host:path:)` for an HTTPS callback. That matcher API
  needs iOS 17.4 / macOS 14.4, above the hosts' floor of 17.0 / 14.0
  (`host/apple/build.mjs:85`). Below it, the arm uses the older
  `callbackURLScheme:` initializer, which covers private-use schemes only,
  and an https callback there is refused with 501. Only a URL matching the
  full granted callback, path included, completes the session. Any other
  URL is left to the page.
- **`prefersEphemeralWebBrowserSession`** comes from `ephemeral`.
  - `true` shares no cookies with Safari. Choose it for "switch account",
    or when the app must not inherit a signed-in browser.
  - `false`, the default, lets a person already signed in to the provider
    tap once.
- **`presentationContextProvider`** is the session's window. On iOS that is
  the scene's key window. On macOS it is the window that holds the node
  that asked, or the key window when the request came from a worker-placed
  source.

The completion handler replies on the runner's thread, in the form the host
already uses for `fulfill`:

- a URL is 200;
- `ASWebAuthenticationSessionError.canceledLogin` is 499;
- anything else is 502 with the error's description.

When the runner forgets the ticket (a newer request superseded it, or the
resource went away, LLP 1016 D5), the host calls `cancel()`. At most one
session is open per window; a second request while one is open is refused
with 409. `SFAuthenticationSession` and in-app `WKWebView` login are not
offered. Providers refuse embedded web views (Google does), and a web
view can read the password.

### D4 — Web: a popup to the app's own callback page, a redirect when blocked

The browser has no auth-session API, so the web arm uses the standard
technique, `window.open` plus `postMessage`, in three steps:

1. **Open.** The glue opens a popup at `url`, named per ticket. A press
   gives the page transient user activation, which lasts about five
   seconds in Chrome and Safari. The glue executes a request in the batch
   that follows the press, so `window.open` is allowed.
2. **Callback page.** The bake emits one static file,
   `/.exact/auth/callback/index.html`, about twenty lines with no
   framework. It posts `location.href` to `window.opener` (target: the
   page's own origin) and closes itself. The web callback the provider is
   registered with is therefore `https://<app origin>/.exact/auth/callback`.
3. **Answer.** The glue answers the ticket with the posted URL. It checks
   the message's `origin` and that the URL's `state` matches the one the
   request's `url` carried. A popup closed without a message is 499, which
   the glue sees on a `closed` poll every half second.

**When the popup is blocked**, `window.open` returns null. This happens
when the request came too late after the press (a worker-placed source
that took longer than the activation window), and on some embedded
browsers. The glue then falls back to a top-level redirect, in four steps:

1. It writes `{ key, callback-state, started }` to `sessionStorage` under
   `exact.auth.pending`. The `key` is the request's canonical form minus
   volatile fields.
2. It navigates the page to `url`, and the running app is gone.
3. The provider redirects to the callback page. With no opener, that page
   stores the callback URL in `sessionStorage`.
4. It replaces the location with the page the app was on (saved at step 1).

At the next boot, the glue holds that stored callback. When a source issues
an `exact-auth:` request with the same `key`, it is answered at once with
200, and the stored entry is deleted. An entry older than ten minutes is
dropped.

Two conditions make that re-ask happen. The source must keep what it put
into the URL (the PKCE verifier and `state`) under `secret.keep` before
asking, which it must do anyway to survive an app kill on native. And the
sign-in must be a resource keyed on stable arguments.

This fallback is honest about its cost: the page reloads. It needs no
server, and a runner rebooting at the app's location is exactly the launch
path LLP 1038 D8 already has.

The web asks nothing of the provider except that the redirect URI is on the
app's origin. A web build served from `file:` or a development origin
registers that origin with the provider as usual.

### D5 — Linux: unavailable, declared

The Linux host is a painter over DRM/KMS or a buffer (LLP 1015). It has no
browser to hand a URL to and no window a browser could return to. An
`exact-auth:` request answers 501, "no system browser on this host".

A desktop Linux host would use RFC 8252 §7.3 when it exists. That means
`xdg-open` to the system browser, a loopback redirect to
`http://127.0.0.1:<ephemeral port>/`, and a one-shot listener. It's written
down so that whoever builds it doesn't invent another shape.

### D6 — The source keeps the protocol: PKCE, PAR, DPoP, tokens

Nothing below is new API. It is what a source writes with `fetch`,
`secret.keep`, the time fact and LLP 1069.005, and the Bluesky port is its
first test.

1. **Metadata.** Resolve the handle to a DID and a PDS, then the
   authorization server's metadata. This is two `fetch`es, under `net.fetch`
   grants the port already declares for its PDS.
2. **PKCE and state.**
   - A 32-byte verifier and a `state` from `crypto.getRandomValues`.
   - The S256 challenge from `crypto.subtle.digest('SHA-256', …)`.

   Both come from **LLP 1069.005**. Today a source has only
   `exactTime().seed`, one number per launch. That isn't a verifier, and
   deriving one from a launch seed and a counter isn't a secret the source
   can defend. The verifier and `state` are kept with `secret.keep` before
   the session opens (D4's re-ask, and an app killed while the sheet is
   up).
3. **PAR.** A `POST` to the pushed-authorization endpoint returns a
   `request_uri`. That is plain `fetch`.
4. **DPoP.** The AT Protocol binds tokens to a key the client holds. Each
   token and resource request carries a JWT signed with ES256 (ECDSA
   P-256), with a fresh `jti`, the `iat` from `exactTime`, and a
   server-supplied nonce that rotates.

   This needs `crypto.subtle.generateKey`, `sign` and `exportKey` for ECDSA
   P-256, which **LLP 1069.005 must include**. Digest and random alone don't
   cover it. The private key is kept under `secret.keep` as a JWK. A
   Secure-Enclave, non-exportable key is better on Apple and is an open
   question (§Open questions 3).
5. **Authorize.** `openAuthSession(authorizationUrl, { callback })`, D1.
6. **Exchange.** Check `state` and `iss` on the callback URL, then `POST`
   the code and verifier with a DPoP proof. Keep the access token, refresh
   token and key with `secret.keep`, and answer
   `Session { ok, handle, error }` to the plan.
7. **Refresh.** Exactly as the port refreshes an app-password session
   today (`refreshSession`), with a DPoP proof.

Bluesky's client-metadata document must be served at an HTTPS URL that is
the `client_id`. For a web build it is a static file on the app's origin,
next to the callback page. For a native build it is the same URL, since the
app's `origin` in `app.json` already names where the web build is served.

### D7 — The agent answers the session; nothing opens in agent mode

With `EXACT_AGENT=1` (native) or `?agent=1` (web), no browser opens and no
real account is touched, following LLP 1018 D6's rule for the store. The
request stays pending, and the agent sees it and answers it:

- **`state`** lists it under `pending` as
  `{ kind: "auth", url, callback, ticket }`, with the authorization URL
  shown so a test can check the query (`code_challenge_method=S256`,
  `state`, `request_uri`).
- **The answer** is a fixture callback URL, for example
  `social.exact.bluesky:/oauth?code=fixture&state=<the state>&iss=…`, or
  cancel. How the agent gives it is LLP 1069.007's decision for every
  device capability, not this document's. Its candidate is a form of
  `type` addressed to the pending prompt, so no operation is added.

The source then calls the token endpoint, which is a real `fetch` the test
answers from a fixture server, as the port's `data/tests/signed_in.rs`
already does for `createSession`. That turns the whole sign-in into a
deterministic drive: `tap sign-in`, `state`, answer, `clock settle`,
`tree`.

### D8 — Later, in the same shape: Sign in with Apple and passkeys

Both are the same request with a different reserved URL. Neither is built
by this RFC.

- **Sign in with Apple.** On Apple this is `ASAuthorizationAppleIDProvider`,
  whose native sheet returns an identity token and an authorization code.
  On the web it is Apple's own OAuth endpoint, which is D1 with Apple as the
  provider. It uses the grant `auth.apple`, and the bake adds the
  `com.apple.developer.applesignin` entitlement. App Review requires it
  wherever another third-party login is offered on iOS. So once D1 ships
  on iOS for a Google or GitHub login, this becomes owed for that app, not
  optional.
- **Passkeys.** WebAuthn is the web's name, and it is the vocabulary:
  `navigator.credentials.create({ publicKey })` and
  `navigator.credentials.get({ publicKey })`, a request answered with the
  credential as JSON. On Apple it is
  `ASAuthorizationPlatformPublicKeyCredentialProvider`, and the web uses the
  browser's own call. The grant is `auth.passkey <rp id>`. The relying
  party's domain needs `webcredentials:` on Apple (LLP 1069.008) and
  `/.well-known/webauthn` for related origins. A passkey signs a challenge
  the server issued, so the source's code is `fetch` plus this one request.

## Not in this RFC

- **An OAuth client library.** Discovery, PKCE, PAR, DPoP and refresh stay
  in the app's source (D6). If a second provider shows the same code
  twice, a shared TypeScript helper beside `exact-route`'s is the place.
  The core doesn't grow a protocol.
- **A token vault or refresh scheduler.** `secret.keep` and the app's own
  refresh-on-401 (as RealWorld's `store.forget` on 401) are enough.
- **In-app browsers for content** (`SFSafariViewController`). `openURL`
  already covers reading a page (LLP 1069 §5 "Not now").
- **Federated Credential Management (FedCM).** It is Chrome-only and
  provider-gated. Revisit when a provider needs it.

## Open questions for Charlie

1. **The name.** The web has no standard for an auth session, so
   `authorize(url, { callback })` is a declared deviation from "the web
   names it". Should it be `authorize`, `openAuthSession` (Expo's
   `openAuthSessionAsync`), or `signIn`?
2. **A DEFERRED line.** Bluesky's admission (2026-09-27) unblocks "what its
   port asks for (LLP 1054, 1054.000)", and OAuth isn't in 1054. Is signing
   in through OAuth part of that consumer, or does this need its own line
   and a take?
3. **DPoP keys.** A JWK under `secret.keep`, which is portable and works
   on the web and in tests? Or a Secure-Enclave key on Apple, which is
   non-exportable and needs a `sign` request to the host rather than
   `crypto.subtle` in the source? The first is one mechanism everywhere;
   the second is what a security review would ask for. This RFC assumes
   the first and leaves the second for later.
4. **The web redirect fallback (D4).** Is a page reload an acceptable
   fallback, or should a blocked popup simply fail with 403-style "popup
   blocked", so the app tells the person to tap again? Failing is simpler
   and is what many SPAs do.
