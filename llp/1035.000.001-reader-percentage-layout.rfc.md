## Summary

Restore `width:100%; max-width:720px` in the LLP reader and the corresponding
740px column in Markdown, with a reduced browser-backed regression for any
native layout repair required. The user-visible result is a scrollbar that
ends after the document and its intentional bottom padding, at every window
width. This refines 1035.000's existing slice 3 and separates it from the
unrelated baseline-rounding investigation. Implementation evidence and remaining limits are recorded below.

## 1. Evidence and the uncertainty to resolve

QUEUE records LLP 1032's blocks ending at 30,145 points inside a 67,373-point
column on 2026-09-08. Those are historical measurements, not a fresh result.
Both apps still use a definite preferred width and `max-width="100%"`, with
comments explaining that it keeps intrinsic measurement and wrapping aligned.

The current Taffy vendor already contains patch 1, which clamps the cross size
used while measuring a content-based flex basis. Its patch note covers both
percentage-width/fixed-maximum and fixed-width/percentage-maximum cases, but
explicitly says its old focused kernel regressions no longer exist. Additional
flex and leaf changes are staged. Therefore another generic "clamp the width"
patch is not yet justified: first distinguish a remaining algorithm defect,
bad measurement constraints, stale cached layout, or a defect already repaired
since the report.

A fresh temporary kernel/Chrome 152 probe of the simple shape in §2, with 60
identical wrapping paragraphs at 16px/26px, **did not reproduce the defect**.
Both width spellings gave these same values in both engines:

| Viewport width | Column width | Column height / last block bottom | Scroll content height |
|---|---|---|---|
| 360 | 360 | 31,318 / 31,318 | 31,414 |
| 720 | 720 | 14,158 / 14,158 | 14,254 |
| 1,000 | 720 | 14,158 / 14,158 | 14,254 |

The extra 96 points are the declared 24 top + 72 bottom padding. This establishes
that the obvious small case works now, not that the real reader is repaired.
Probe source and browser output were kept in the temporary
`exact2-1036-probe-ivtizpul` directory; the selected implementation must preserve
its eventual regression in the existing tests, rather than depend on that path.

## 2. Reduce the real document before choosing the repair

Open LLP 1032 in the current reader, record the viewport, font, document bytes,
column box, final block bottom, outer padding and scroll extent. Run both width
spellings on that tree, at a narrow viewport, at the column maximum and wider
than it. Repeat after resize and resource replacement. Use the same Contract
source on native and web, plus literal HTML/CSS for the reduction: a lowering
bug shared by Exact hosts must not become the oracle.

Reduce only while retaining the discrepancy. The intended small case has a
definite viewport, the reader's scroll surface, its centered auto-height flex
wrapper, a border-box column with 32px side padding, and wrapping paragraphs.
Keep an image or nested block if removing it makes the failure disappear.
Replace platform text with a deterministic width-sensitive measurer once the
shape survives; preserve the actual offers, measured heights and final boxes.
Choose words and widths away from font-dependent wrap thresholds in the browser
counterpart. Do not encode 67,373 as the desired or permanently expected number.

If the old failure no longer reproduces, the useful change is still the
regression and deletion of both app workarounds. Record which existing behavior
now handles the case; do not invent an engine change to justify this proposal.

## 3. Repair the owner, then delete the workaround

Inspect the reduced case through `kernel/src/layout.rs` and the existing
Taffy flex-basis/final-layout passes. A finite known width, an available width
and an intrinsic sizing offer are distinct inputs; cache entries cannot treat
them as interchangeable. If the measurement callback is given the wrong content
box, fix that seam. If the Taffy basis or final layout carries an obsolete size,
correct that pass and amend the existing patch note, retaining its old cases.
An intrinsic probe and a final pass need not have identical widths; the
requirement is the browser's final geometry and correct reuse of measurements.
The relevant sizing steps are in
[CSS Flexbox §9.2](https://www.w3.org/TR/css-flexbox-1/#algo-main-item).

Do not clamp native scroll range to the last child, subtract the historical
excess, change `flex-shrink` defaults, or move the app workaround into the host.
Those would conceal a bad box from the user while leaving hit-testing and
subsequent layout wrong. Keep percentages in the authored rows. Remove the
readers' workaround comments and swap their width/max-width declarations only
after their original shapes pass.

## 4. The regression and exit condition

The small deterministic case belongs in the existing kernel layout tests;
record its browser geometry in the fixture/test itself, following the existing
motion-parity precedent without adding a new script or blocking check. Cover
the original and workaround spellings with both content-box and border-box
variants, fixed and percentage maxima, and narrow/wide containing blocks.
For the padding-free, gap-controlled inner column, its height must equal the
children's laid-out extent; for the scroll surface, include the wrapper's
authored top/bottom padding and any genuine descendant overflow.

Initial layout, narrow→wide→narrow resize, text replacement, maximum-width
change and removal/recreation must match a freshly built tree. Add the reduced
mutation sequence to `layout_equality.rs` so incremental, replayed and
rehydrated layouts agree. A browser comparison permits 0.02 logical units for
matching deterministic geometry; platform font differences are recorded
separately rather than absorbed into a large scroll-range tolerance.

Finally drive both real readers through `tree`, `layout` and wheel forms of
`tap`, reaching the document bottom and resizing back. The viewport should
show the final content followed only by the declared padding, with no phantom
range and no clipped content. Sweep web, macOS, iOS and headless Linux using
the existing drivers; run the five checks with `EXACT_UPDATE_TRUST=development`.
Measure the long reader's layout cost using existing metrics: repeated global
relayout is not an acceptable cure for a stale measurement.

Remove F1's QUEUE line when both apps use the original CSS shape and the proof
passes. If three reduction/fix rounds do not establish the cause, retain the
workaround, report the remaining counterexample and stop per `RULES.md`.


## Implementation evidence — 2026-09-12

The real failure remained. LLP 1032 (`1032-javascript-in-wasm-measured.research.md`,
57,683 UTF-8 bytes, SHA-256
`e3aa682ebc7b29ed892555da12c88a3963703ddc5295266cd9f7a67160d33510`)
contains 128 rendered blocks. On AppKit at a 720-point column, the original
spelling produced height 67,333 with the last block ending at 30,049; the
workaround produced 30,049. The original wheel range left 37,356 points after
the last block instead of the declared 72.

Code block 123 retained the failure; the other individual code blocks and
ordinary paragraphs did not. Its overwide unbreakable token makes an intrinsic
column width exceed the maximum. Taffy's cache treated the clamped intrinsic
result width as equivalent to a newly known width, reusing a height measured
with unresolved descendant percentages. `vendor/taffy/src/tree/cache.rs` now
keeps intrinsic and definite offers distinct when promoting a result to a
known dimension. Exact-input cache hits remain; no global relayout or scroll
clamp was added. The existing cross-size clamp remains necessary and intact.

The permanent reduction is `kernel/tests/reader.rs` and its literal browser
fixture `kernel/tests/fixtures/reader.html`: 24 cases across both width
spellings, both box-sizing modes, narrow/maximum/wide viewports and ordinary
versus overwide-token text in nested padded blocks. Chrome 152 and the kernel
agree within 0.02 points. The intrinsic text offer produces height 1,716;
the final 628-point content offer produces 468. The final column is 5,974 and
the scroll extent 6,070. The separate measurement assertion also proves that
an unchanged layout makes no new text measurements. `layout_equality.rs`
checks frame and scroll-overflow bits after narrow→wide→narrow, text replacement,
maximum-width change and subtree destruction/recreation against replay and
rehydration, with the wrapper padding checked independently.

Both readers now author `width="100%"` with their fixed 720/740 maximum.
At the maximum and at a 1,000-point viewport, the real document produced:

| Host / text engine | LLP column height | Markdown column height | Padding after wheel-to-end |
|---|---:|---:|---:|
| macOS / CoreText | 30,049 | 29,493 | 72 |
| Chrome 152 / system fonts | 28,409 | 28,118 | 72 |
| Headless Linux / pinned DejaVu Sans | 30,537 | 30,206 | 72 |

On the iPhone 17 Pro simulator (iOS 26.5, 402×778 logical viewport), both
spellings also matched: LLP column 46,127 and Markdown 46,085, with 72 points
after the last block. The iOS sweep was portrait only; the deterministic
resize regression and desktop pane toggles cover the width mutation sequence.
The first simulator link used a stale warm ibex2 native archive; cleaning only
that target's ibex2 release cache restored the current transport symbols and
both builds then passed. No external source changed.

Both width spellings matched on each host, including narrow viewports. These
font-dependent heights are observations, not cross-font parity tolerances.
The browser used captured real resource values through a temporary data-source
adapter because it cannot read the repository's filesystem. Linux used the
existing host and real reader data crates through a temporary entry point;
neither reader ships a Linux adapter. AppKit also replaced LLP 1032 with LLP
1000 and back while toggling the folder pane (720↔490 content widths); every
column ended at its last block with exactly 72 points of bottom padding.

The existing metrics script has no native reader metrics binary. Applying its
release `Instant` sampling pattern to this 1,277-node real reader measured
narrow/wide relayout at 1.926 ms p50 / 2.564 ms p95 (40 samples), with repeated
unchanged layout averaging 0.010 ms. The kernel caches remain active. Artifacts
for the live checks and reduction are in `/tmp/reader-*`; only the permanent
fixture and assertions above are needed to run the regressions.

Validation: `cargo build --workspace`, `cargo test --workspace --no-fail-fast`
(612 tests), `cargo clippy --workspace --all-targets -- -D warnings`,
`cargo fmt --all -- --check`, staged `node scripts/caps.mjs`, and
`node scripts/boot.mjs` passed with development trust. The slow workspace
checks ran asynchronously. `node scripts/metrics.mjs --scaling --json`
completed separately. These measurements precede the sibling typed-line-height
integration; its combined host validation may change font-dependent heights.
