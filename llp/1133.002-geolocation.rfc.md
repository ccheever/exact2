## Summary

`@exact/geolocation` gives an app the device's position on the web, iOS,
macOS and Android first, with every other target of LLP 1133 D8's seven a
visible `later` or `absent`. Its tier 1 is the W3C Geolocation API
([W3C Geolocation](https://www.w3.org/TR/geolocation/)):

```
use getCurrentPosition, geolocationStatus, GeolocationPosition from "@exact/geolocation"

mutation located as shape GeolocationPosition then arrived
action useMyLocation
  send located = getCurrentPosition(enableHighAccuracy=false, maximumAge=600000,
    apple.desiredAccuracy="threeKilometers", android.quality="lowPower")
```

```ts
import { watchPosition } from "@exact/geolocation";

const here = await watchPosition({ maximumAge: 600000,
  apple: { desiredAccuracy: "threeKilometers", distanceFilter: 5000 } });
```

Tier 2 reaches CoreLocation's accuracy, activity type and distance filter,
and Android's platform `LocationRequest` qualities, providers and
intervals. Tier 3 hands the app's Swift the module's one
`CLLocationManager`, and its Kotlin the `LocationRequest.Builder` before
each request.

The module is also where exact2 first decides **how every module asks the
person for permission** (§4): declared once as a grant, explained by the
app, read as a fact, asked by the app's code wherever its author chooses,
and never answered by exact2. Every call carries its origin, so a later
rule can let an agent act with authority another agent or the person gave
it, with no person at each step. That section becomes LLP 1133 D7 when it
is ruled.

The consumer is Weatherlight: "Use my location" asks, and from then on the
forecast follows the person, read in data code with approximate accuracy
and a five-kilometre filter.

## 0. Rulings (Charlie, 2026-10-18)

1. **Asking in context is a guideline, not a rule:** "we should let
   developers do whatever they want" (D9).
2. **Agents will come to grant agents permission without humans in the
   loop** (D12's direction).
3. **Platform words in Contract are dotted keyword arguments**,
   `apple.desiredAccuracy="threeKilometers"`, not a record literal: "i am for
   dotted keywords unless there is something compelling the panel comes up
   with against them". The second round's three reviewers recommended them
   (Astra 85%, Fable 75%, Grok 70%); their strongest objection, grouping a
   platform's words as one value, is met by a shape-call value for a word
   whose value is a record (D13).

## 1. Tier 1

### D1 — The Geolocation API's names: a send, a source and a fact

The interface `@exact/geolocation` declares these names, and the shapes
they answer (`GeolocationPosition`, `GeolocationCoordinates`,
`GeolocationStatus`), which an app imports with them (D13):

| Name | Kind | Meaning | Contract | Data code |
|---|---|---|---|---|
| `getCurrentPosition(options)` | send; a request | one position, `PositionOptions` (`enableHighAccuracy`, `timeout`, `maximumAge`) | `send x = getCurrentPosition(…)` | `await getCurrentPosition(options)` |
| `watchPosition(options)` | live source; a fact, whose first read may be a request (D9) | the latest position, re-answered as it changes, while something reads it (D5) | `resource here = watchPosition(…)` | `await watchPosition(options)` |
| `geolocationStatus()` | live source; a fact; `sync` (D14) | `available`, `state`, `accuracy` (D8) | `resource status = geolocationStatus()` | `await geolocationStatus()` |
| `requestPreciseLocation(purposeKey)` | send; a request | ask to raise an approximate grant to a precise one (D10) | `send x = requestPreciseLocation(purposeKey="…")` | `await requestPreciseLocation({ purposeKey })` |

**Values.** One representation, on every target:

| Field | Value |
|---|---|
| `coords.latitude`, `coords.longitude` | degrees, WGS 84 |
| `coords.accuracy` | metres, as the platform reports it. The W3C asks a 95% confidence radius; Android reports 68% ([`Location.getAccuracy`](https://developer.android.com/reference/android/location/Location#getAccuracy())); Apple documents a radius of uncertainty and no confidence. A declared deviation; `accuracyConfidence` is a tier 2 result word (`0.68` on Android, `none` on Apple) |
| `coords.altitude`, `coords.altitudeAccuracy` | `option<number>`, metres above the WGS 84 ellipsoid, as the W3C defines it (§9.2): Apple's `ellipsoidalAltitude` (iOS 15, macOS 12), Android's `getAltitude()`, the web's value. Mean sea level is tier 2 (`apple.altitude`; `android.mslAltitudeMeters`, API 34). Android's vertical accuracy is a 68% radius too, under the same declared deviation as `accuracy` |
| `coords.heading` | `option<number>`, the course of travel in degrees from true north; compass heading is tier 3 (D4) |
| `coords.speed` | `option<number>`, metres per second |
| `timestamp` | milliseconds since the epoch |
| errors | in Contract, `failure(…).code` is `PERMISSION_DENIED`, `POSITION_UNAVAILABLE`, `TIMEOUT`, or `NotSupportedError` where the target has no implementation, the domain codes LLP 1109 D3 lets a source supply; a refusal under D12 is `PERMISSION_DENIED` with a `message` that says `person-required`, and the tool call that caused it ends `person-required` (LLP 1111 D4a). In TypeScript and Rust a call rejects with `{code, message}`, the same strings: a declared deviation from the W3C's numeric `GeolocationPositionError.code`, so one spelling serves every caller |

The W3C's absent fields are present and `null`; Contract's are `option`
fields, `none`. A platform's result words sit in `option` fields, `apple`
and `android`, `none` on every other target.

**Declared deviations,** each because the web's form does not fit a
function that answers:

- `watchPosition` is a live source, not a callback registration; the
  runner holds the watch and re-asks the reader (LLP 1016.002).
- `clearWatch` is not a name: a watch ends when its last reader stops
  reading (D5).
- `getCurrentPosition` resolves or fails, in Promise form in TypeScript.
- `geolocationStatus` folds `"geolocation" in navigator` (`available`),
  `navigator.permissions.query({name: "geolocation"})` (`state`,
  [Permissions API](https://www.w3.org/TR/permissions/)) and the shared word
  `accuracy` (D8).
- `requestPreciseLocation` is a shared word: Apple and Android can raise
  an approximate grant; the web cannot (D10).

### D2 — Unsaid options are the platform's; written ones are the web's

LLP 1133 D4's precedence, author > platform > web default: an option the
author omits leaves the platform's own default; an option the author writes
takes the web's meaning.

| Option | Web | Apple | Android |
|---|---|---|---|
| `enableHighAccuracy` omitted | the browser's | `desiredAccuracy` unset: `kCLLocationAccuracyBest` on iOS, `kCLLocationAccuracyHundredMeters` on macOS ([desiredAccuracy](https://developer.apple.com/documentation/corelocation/cllocationmanager/desiredaccuracy)) | `QUALITY_BALANCED_POWER_ACCURACY`, the builder's default |
| `enableHighAccuracy=false` | the browser's | `kCLLocationAccuracyHundredMeters`, as WebKit maps it ([CoreLocationGeolocationProvider.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/cocoa/CoreLocationGeolocationProvider.mm)) | `QUALITY_BALANCED_POWER_ACCURACY` |
| `enableHighAccuracy=true` | the browser's | `kCLLocationAccuracyBest` | `QUALITY_HIGH_ACCURACY` |
| `maximumAge` omitted | `0`: no cached fix | `0` | `0` |
| `maximumAge` written | a cached fix younger than it | `CLLocationManager.location` when younger | the provider's last known location when younger |
| `timeout` omitted | the W3C's default, `0xFFFFFFFF` ms (about 49.7 days) | the same | the same |
| `timeout` written | the browser's | the module's timer | the module's timer |

As the W3C's acquisition does (§6.6, §7.2):

- **A cached fix is eligible** only when `maximumAge` is above 0 and the
  fix was taken with the same `enableHighAccuracy`.
- **The timer measures acquisition.** It starts when the position is first
  sought, after any permission prompt and any wait in D9's queue, and
  bounds one acquisition: one `getCurrentPosition`, or a watch's next fix.
  It never ends a watch. On Android, `setDurationMillis` carries it on a
  one-shot only, never on a watch's registration. `timeout=0` answers an
  eligible cached fix or fails `TIMEOUT` at once.
- **A platform failure is `POSITION_UNAVAILABLE`,** not `TIMEOUT`, including
  Android's own cap on `getCurrentLocation`.

### D3 — The platforms' words

**Apple** (`apple.…`; CoreLocation's names,

### D5 — Readers, generations and acquisition

Three things are kept apart: a **reader** (an answer that read a live
source, with its options), the answer's **generation** (which of its asks
it was), and **acquisition** (the module's hardware work).

- **Readers.** The runner keeps, per declared live source, the readers and
  their options. A replaced answer hands its readers to its replacement
  atomically, at the commit that lands the new answer: the new answer's
  reads are registered before the old answer's are released, so a refresh
  never stops and restarts the watch. A removed resource, a cancelled
  answer and the end of the session release their readers.
- **Acquisition** runs while at least one reader exists and the state is
  `granted`. When the state turns `denied`, acquisition is suspended and
  the readers are kept, failing `PERMISSION_DENIED`; when it turns
  `granted` again, acquisition resumes and the readers are asked again.
  The last reader's release stops acquisition: a `release` call into the
  module beside `later`, because `NativeSlots` today has no last-reader
  notice (`runner/src/runner/source.rs`).
- **Options compose** at the finest of the readers' `desiredAccuracy` or
  `quality` (D3's published orders), the smallest distance filter and
  interval. Each reader's own `maximumAge` and distance filter apply when
  it is re-asked: a reader with a 5 km filter is re-asked only when the fix
  has moved 5 km since its last answer. Words that have no order (Apple's
  `activityType`, Android's `provider`) must agree across readers; two
  readers that disagree are refused by name in development
  (`geolocation-options-conflict`, naming both) and the first reader's
  word holds in production.
- **One-shots beside a watch.** Apple's `requestLocation()` does nothing
  while updates run, and `startUpdatingLocation()` cancels a pending one
  ([requestLocation](https://developer.apple.com/documentation/corelocation/cllocationmanager/requestlocation())).
  So a pending one-shot is part of acquisition's demand: during a watch it
  is answered from an eligible cached fix, else the next update, and while
  it is pending the module lowers the distance filter to none so a
  stationary device still delivers; starting a watch answers a pending
  one-shot from its first update.
- **A mutation's answer does not subscribe.** A `watchPosition` read in a
  mutation answers once; only a resource's answer is re-asked.

## 4. Permission: how every module asks

Every capability that touches the person's data or devices passes the
same stages, and the platforms do each differently. exact2 owns their
shape, so a module author writes the platform calls and nothing else, and
an app author writes one grant line, the explanation, and the UI around
the moment of asking. Three authorities are kept apart throughout: what
the app is built to request (its grants), what the platform currently
permits (its state), and what the caller of a given call may do (its
origin). This section becomes LLP 1133 D7 when it is ruled.

### D6 — Declare: one grant line, every manifest

The app writes `device.geolocation locationPurpose` in its grants (LLP
1069.008 D1); `locationPurpose` is a key in its strings table, so the text
is translated with the app's others. The build derives every manifest from
it, per target, through the host's grant column (LLP 1133.001 D5):

| Target | Derived | Does the system prompt show the purpose? |
|---|---|---|
| iOS | `NSLocationWhenInUseUsageDescription` | yes |
| macOS | `NSLocationUsageDescription`, `NSLocationWhenInUseUsageDescription`, `com.apple.security.personal-information.location` | yes |
| web | `Permissions-Policy: geolocation=(self)` | no |
| Android | `ACCESS_FINE_LOCATION` and `ACCESS_COARSE_LOCATION` | no |

Where the system's prompt cannot carry the purpose, the app's own UI does
(D11). The grant table has no Android column today
(`runner/src/device.rs`; the manifest asks only `INTERNET`); this module
adds it. Grant purposes are in the compatibility id already
(`bake/src/reach.rs`); the temporary-accuracy keys join them (D10).

### D7 — Approximate: a ceiling where the module can keep it

`device.geolocation-approximate locationPurpose` is a declared deviation
(the Permissions Registry has one `geolocation`). It derives the same usage
keys and `Permissions-Policy` as `device.geolocation`, and:

| Target | Effect | Is it a ceiling? |
|---|---|---|
| iOS, iPadOS, visionOS, watchOS | `NSLocationDefaultAccuracyReduced`, which asks the prompt to open with "Precise: Off" ([the key](https://developer.apple.com/documentation/bundleresources/information-property-list/nslocationdefaultaccuracyreduced)); iOS 27 opens it with Precise on regardless. The module reads the key and asks CoreLocation for `kCLLocationAccuracyReduced` on every request ([the constant](https://developer.apple.com/documentation/corelocation/kcllocationaccuracyreduced)) | yes: positions are reduced whatever the person grants, and `requestPreciseLocation` asks nothing |
| macOS | none: the key does not exist there; the line is `device.geolocation` | no |
| Android | `ACCESS_COARSE_LOCATION` alone | yes: fine can never be asked |
| web | none | no |

So the line says what the app needs; `geolocationStatus().accuracy` says
what it got: the platform's current authorization, held to `approximate`
under a ceiling (`apple.accuracyAuthorization` still names the grant). A
precise word (`enableHighAccuracy=true`, `apple.desiredAccuracy="best"`)
is never refused: under a ceiling or an approximate authorization the fix
is clamped, and where the person has granted precise without a ceiling it
takes effect. iOS has a ceiling because iOS 27 ignores the key (Charlie,
2026-10-21): without one, an app that asked for approximate would read
precise positions from a prompt the person did not change. Two things
are refused by name, both Android's ceiling under the approximate line: `android.provider="passive"`,
and `requestPreciseLocation`. An app writes one of the two lines, never
both: `grant-twice`, a new bake refusal (`runner/src/device.rs` already
refuses two purposes for one name, but `geolocation-approximate` is another
name, so nothing refuses the pair today).

### D8 — Read: availability, state and accuracy are facts

`geolocationStatus()` answers:

- `available`: the target has an implementation and the platform has
  location services on. On Apple it is cached from the delegate, since
  `locationServicesEnabled()` can block the main thread.
- `state`, with one meaning on every target: **`granted`**, a read
  proceeds; **`prompt`**, a request will show a platform dialog;
  **`denied`**, a request will show nothing and fails; **`unknown`**, the
  platform will not say (no module here; HealthKit hides read authorization
  by design,
  [authorizationStatus(for:)](https://developer.apple.com/documentation/healthkit/hkhealthstore/authorizationstatus(for:))).
- `accuracy`: `precise`, `approximate`, or `unknown` (the web).

Each platform's states map to those:

| Platform state | `state` |
|---|---|
| Apple `notDetermined`, including after "Allow Once" lapses | `prompt` |
| Apple `authorizedWhenInUse`, `authorizedAlways` | `granted` |
| Apple `denied`, `restricted` | `denied` (`restricted` is tier 2) |
| Android never asked | `prompt` |
| Android rejected once | `prompt`, with `android.shouldShowRationale` true |
| Android rejected twice, or "Don't ask again" | `denied`, with `android.permanentlyDenied` true |
| Android revoked in Settings, or "Only this time" lapsed | `prompt` |
| Android granted, fine or coarse | `granted` |
| web `PermissionStatus.state` | the same word |

`shouldShowRequestPermissionRationale` is false both before the first ask
and after a permanent denial
([Request runtime permissions](https://developer.android.com/training/permissions/requesting)),
so the Android implementation keeps a history in its own preferences: the
outcome of each request it made, and whether it last read the permission
as granted. A request whose result is a rejection with no rationale owed
afterwards is a permanent denial (`denied`). A read that finds the
permission ungranted after the last read found it granted is a revocation
in Settings or a lapsed one-time grant, and the state returns to `prompt`
with the denial history cleared. Never asked, with no history, is
`prompt`. A history the implementation cannot read (a reinstall clears
it) starts again at never asked, and the platform's own count still
decides whether a dialog shows. On the web,
`PermissionStatus` is live: the module follows its `change` event and
reads it again when the page becomes visible. A browser whose grant does
not persist reads `prompt` again afterwards, and the next request may ask
again; that is the browser's behaviour, and the status says it.

The state changes by itself: a revocation in Settings, a one-time grant
lapsing, a coarse-only grant. Apple reports it through
`locationManagerDidChangeAuthorization`, the web through `change`, and
Android, which has no event, by a fresh read on `onResume` (a precision
downgrade on Android restarts the app's process). The host announces the
change and every reader is asked again (LLP 1016.002). A module whose
permission has more states than these declares them as tier 2.

*Amended by LLP 1133.037 §13 (Charlie, 2026-10-27: "Accept 037, hold 032 (Recommended)"):*
for a module of many devices, `state` says whether opening will show a
prompt, and each device record's `granted` whether this process can open
it without a further prompt, false meaning `open` fails or may ask. They
differ on Linux, where no prompt exists and a device node's mode may
still refuse the process: `state` reads `granted` and the record's
`granted` false (LLP 1133.037 D17).

### D9 — Ask: where the app's code chooses, one request at a time

**Asking is the app's choice** (§0). Any of the app's own code in a
foreground session may ask: an action, a resource's answer, a task, at
launch. exact2 refuses none of them. Asking in context, when the person
does something that needs it, is the platforms' guidance and exact2's
recommendation, in the recipe and the agent's guides: Apple asks for it
while allowing an essential request at launch
([Privacy](https://developer.apple.com/design/human-interface-guidelines/privacy)),
Android asks for it in context
([Request runtime permissions](https://developer.android.com/training/permissions/requesting)).
Whether a resource asked again prompts again is the platform's: iOS shows
its dialog once, while `notDetermined`; Android shows it until a second
rejection; a browser decides by its own policy, which may block an origin
that keeps asking. While the state reads `prompt`, a re-asked resource
asks again, and an app that would rather not reads `geolocationStatus()`
before it reads the position. The recipe says so.

What a request does follows the state and its origin (D12's table):

- `granted`: it proceeds, with no prompt.
- `denied`: it fails `PERMISSION_DENIED` at once. iOS's
  `requestWhenInUseAuthorization()` does nothing and calls no delegate
  unless the status is `notDetermined`
  ([requestWhenInUseAuthorization](https://developer.apple.com/documentation/corelocation/cllocationmanager/requestwheninuseauthorization())),
  so the module never waits on it there.
- `prompt`: it asks, through the platform's own mechanism, and settles
  once. A request the platform will not present (the app is not in the
  foreground) fails at once rather than wait for a delegate call that will
  not come. A person dismissing the dialog fails the request
  `PERMISSION_DENIED`, and the state is whatever the platform then
  reports.

**The mechanism is the implementation's.**

- **iOS and macOS:** `requestWhenInUseAuthorization()`, answered on the
  delegate.
- **Android:** the platform's `Activity.requestPermissions` and
  `onRequestPermissionsResult`. Fine and coarse go in one request (Android
  12 ignores fine without coarse,
  [runtime location](https://developer.android.com/develop/sensors-and-location/location/permissions/runtime)).
  The host's `ExactActivity` is a plain `Activity` with no AndroidX, and
  the platform path needs none. A result lost to recreation is recovered
  by reading the permission again when the new Activity resumes, which
  settles the pending request.
- **The web:** the first `getCurrentPosition` or `watchPosition`; both run
  the W3C's permission request (§6.2 and §6.3, through §6.5).
- **The Location portal:** its own dialog.

**One request at a time.** The runner queues module requests that need a
permission decision, in order, so two modules asked together prompt one
after the other. What is queued is the decision, not the call: the queue
advances when the decision is made, before any position is acquired. Two
queued requests that need the same decision share it, and each keeps its
own options, origin, result and lifetime. If the request that opened a
dialog is cancelled while others wait for the same decision, the dialog
stays (no platform can withdraw it) and its answer still settles the
others; if none waits, the answer is recorded as the state. The
permissions inside one request (Android's pair) stay one request.

### D10 — Raise: precise for a task

`requestPreciseLocation(purposeKey)` asks to raise `approximate` to
`precise`. It answers the new `geolocationStatus`; success is read from
its `accuracy`, never assumed.

- **Apple:** `requestTemporaryFullAccuracyAuthorization(withPurposeKey:completion:)`
  ([Apple](https://developer.apple.com/documentation/corelocation/cllocationmanager/requesttemporaryfullaccuracyauthorization(withpurposekey:completion:))),
  for this session; its completion says only that the prompt was handled,
  and the module answers from `accuracyAuthorization`. The build writes
  `NSLocationTemporaryUsageDescriptionDictionary` with one entry per
  `purposeKey` the app passes, each a literal strings key the bake collects
  (link by use, LLP 1047.001); an app that never calls it gets no
  dictionary.
- **Android:** the fine and coarse pair again, under `device.geolocation`
  only.
- **Web:** `NotSupportedError`.

By state: while `granted` and `approximate`, it asks for precision; while
`granted` and `precise`, it answers the status at once; while `prompt`, it
asks for permission first, in one queued request, and then for precision
if the answer is approximate; while `denied`, it fails
`PERMISSION_DENIED`. A precision prompt the person declines or dismisses
is not a failure: the call answers the status, unchanged. Admission
(D12, D14) asks of each operation whether it would show a dialog in the
current state, so `requestPreciseLocation` while `granted` and
`approximate` is a prompting request, and a tool invocation's fails
`person-required`.

Asking for higher quality never raises the grant by itself (D7).

### D11 — Explain and recover: the app's own UI

The system prompt carries the purpose only on Apple (D6). Explaining is
otherwise the app's own screen, and a hand-built app writes it itself, so
exact2 adds no pre-prompt (it would be a tell). The recipe,
`docs/recipes/permissions.md`, gives the pattern: read the status; while
`prompt`, show why beside the button that asks, and on Android show the
rationale first when `android.shouldShowRationale` is true, with a way to
decline; while `denied`, say how to change it.

To recover, `openURL("app-settings:")` opens the platform's settings for
the app. The scheme is Apple's own: `UIApplication.openSettingsURLString`
is the string `"app-settings:"`. On macOS it opens the Privacy & Security
pane's Location Services (the URL is the macOS host's to name and test,
since it has changed across releases); on Android,
`ACTION_APPLICATION_DETAILS_SETTINGS`. Each host intercepts the scheme,
which its `openURL` allowlist refuses today
(`host/apple/Sources/ExactIOS/main.swift`, `ExactMac/main.swift`,
`host/web-js/commands.js`). On the web it is refused as any other scheme
is, with a journal line; a web app shows the browser's own instructions.
It is not open to tool invocations (LLP 1111 D4a). Whether to send the
person to Settings, or to ask again while the platform still can, is the
app's judgement; Android advises against Settings as persuasion.

### D12 — Answer: exact2 never answers a platform's prompt

**The platform's prompt is answered only by whoever the platform lets
answer it.** exact2 never answers, pre-grants or fakes one, and calls no
API that grants. Where a platform offers a path without a person (an
Android device owner's `setPermissionGrantState`, a managed browser's
policy such as Chromium's `PreciseGeolocationAllowedForUrls`), the grant
line of D6 is what that policy targets and D8's fact is how the app learns
the result. When platforms add agent-aware asking, each host's
implementation of D6 and D9 changes, not any app.

**Every call carries its origin,** and the origin follows causation:

- a person's input event; the app's own code in a foreground session (an
  action from a timer or a task, a resource's answer, launch); a tool
  invocation (LLP 1111, with its id); a background wake (LLP 1114.001); the
  development agent.
- The origin of a resource's answer is the origin of the commit that asked
  it. A commit a tool invocation made, and the commits that settle its
  requests, carry the tool's origin to every answer and request they cause;
  a wake's likewise. So a tool that sets state which makes a resource read
  `watchPosition` makes a tool-origin read.
- A re-ask the device causes (a module's topic, a permission change, a
  preferred value under the agent) carries the origin of the reader's own
  last ask: each reader keeps its origin, and an invalidation that reaches
  readers of different origins re-asks each under its own.
- The origin travels with the call's context (D14) through admission, into
  `pending`, the journal and `state.extensions`.
- **Where a runtime cannot be sure, the origin is the least privileged.**
  Code the context helper does not reach (D14: an explicit `.then`
  callback, an async generator's steps) runs under whichever answer's turn
  drains it. So while any tool-origin or wake-origin answer is in flight in
  a data runtime, a prompting call from that runtime's data code outside an
  `async` function's own steps is admitted as tool-origin, whichever answer
  it reads as current. A Contract `send` carries its origin exactly and is
  unaffected.

**What a request does, by origin and state:**

| Origin | `granted` | `prompt` | `denied` |
|---|---|---|---|
| a person's input; the app's own code, foreground | proceeds | asks (D9) | fails `PERMISSION_DENIED` |
| a tool invocation | proceeds under the app's grant (the direction below may narrow it) | fails `PERMISSION_DENIED`, reason `person-required`; the tool call ends as LLP 1111 D4a says | fails `PERMISSION_DENIED` |
| a background wake; a headless session | proceeds where the platform delivers in the background (this module asks for no background location, so it fails `POSITION_UNAVAILABLE`) | fails `person-required` (LLP 1114.001 D4) | fails `PERMISSION_DENIED` |
| the development agent | §6 | §6 | §6 |

Grant state is set only by the platform and, in development, by the
driver: no argument a caller passes changes it.

*Amended by LLP 1133.036 §11 (Charlie, 2026-10-26: "Accept r9, build (Recommended)"):* a fetch hop or a WebSocket open
whose destination has prompt risk (LLP 1133.036 D6) is a request. A
tool, wake or device origin's is refused before it connects:
`NotAllowedError` with `person-required` while the permission that
governs it is undecided, and `NotAllowedError` unsent while it is denied
(the fetch's error, where this table has `PERMISSION_DENIED`).

*Direction, not specified here:* once the platform has granted the app,
which callers may use that capability is the app's authority, checked at
the same admission (D14) against the call's origin. An agent holding such
authority may grant another agent a subset of it with no person at each
step: use and delegate are separate rights, a grant never exceeds its
grantor's, it expires, revocation reaches the work derived from it, and
authority is a record the runner holds, never a claim in a caller's
arguments or context (as in GNAP, [RFC 9635](https://www.rfc-editor.org/rfc/rfc9635.html),
and the attenuating credentials of UCAN and macaroons). It is written
beside LLP 1111 when a door's caller has an identity and a consumer needs
it, with a `rules/DEFERRED.md` move of "durable capability grants".

### D13 — The declaration, the grammar and the bindings

```json
        "maximumAge": "option<number>" },

      "sync": { "name": "getCurrentPositionSync", "from": "cache" } },

```

Types are `number`, `string`, `bool`, `option<T>`, `T[]`, `enum<a|b>`, a
shape name, or `strings-key` (a literal key the bake checks against the
strings table). The `AppleLocation`, `AndroidLocation`, `AppleStatus` and
`AndroidStatus` shapes are the implementations' tier 2 result words (D3),
declared in their `exact.json`; on a target whose implementation is not
bound the field is `none`.

**Imports.** `use getCurrentPosition, GeolocationPosition from
"@exact/geolocation"` resolves the package's `exports` to its `exact.json`
and imports names and shapes from it: a loader origin built from a JSON
declaration, beside `resolve.rs`'s compiled-in and file origins (LLP
1133.001 §3). An app declares no position shape of its own.

**Keyword arguments, and dotted ones** (§0). A module's sends and sources
take keyword arguments only, `name=value`; Contract's ordinary calls stay
positional (`docs/contract-grammar.md`). A platform word is a dotted
keyword, `apple.desiredAccuracy="threeKilometers"`: the parser's argument
name becomes `IDENT { "." IDENT } "="`, which is unambiguous because `=` is
never an operator (only `==` is), and today's refusal of a colon in a call
(`contract/syntax/src/parser.rs`, "named arguments use `name=value`")
stays. The bake checks each path against the platform's words as the endorsed
implementation declares them in its `exact.json`, which the bake reads on
every target whether or not that implementation is bound there (LLP
1133.001 D2 rule 2: reading a declaration never links), and against the
bound implementation's where another is bound; it checks them as it checks
a field; no platform key is reserved, a repeated path is
refused (`call-argument-twice`), an unknown path is refused by name, and an
omitted word stays distinct from one written. A word whose value is itself
a record takes a shape call, `apple.region=AppleRegion(…)`. `contract fmt`
and `contract vocab` learn the form. LLP 1133 D2's example is amended to it.

**Bindings are generated by the bake, not committed.** The TypeScript bake
(`js/bake/src/typescript.mjs`) maps an `app.ts` import of
`@exact/geolocation` to a module it generates from `exact.json`, with its
types, beside the app's generated `app.contract.d.ts`; the Rust binding is
generated into the app's generated workspace (LLP 1133.001 D9). The package
carries only `exact.json`, so a published package and a `file:` one are
read the same way. A binding call with neither grant line in the app
refuses at bake (`grant-missing`).

**The wire body** is LLP 1124 D5's, with keyword arguments as an object
rather than a list:
`{"extension": "geolocation", "send": "getCurrentPosition", "args":
{"enableHighAccuracy": false, "apple": {"desiredAccuracy": "threeKilometers"}}}`.
A Contract `send` to a module send, and a resource read of a module
source, are routed to the native slot by the declaration (LLP 1124 D5).

### D14 — One admission, from every caller, with its context

**Admission.** Every call to a declared module, from any caller, passes one
runner operation that applies, in order:

1. the grant check (D6, D7);
2. the target's own restrictions, which hold under the agent too (D15; a
   synchronous form where there is no `call`, a web precision request, the
   Android ceiling, an `available: false` target: `NotSupportedError` or the
   named refusal);
3. whether the operation would show a dialog in the current state (D9,
   D10), and if so, the origin rule of D12;
4. if it would, D9's queue for the decision (under the agent, a ticket);
5. the authorization the operation needs, checked again after any decision
   and again before a pending result is delivered;
6. the answer: the implementation, or under the agent the substitute's
   preferred value or declared default (§6);
7. the journal line and the `state.extensions` count.

So a `watchPosition` read while `prompt` asks before any default can
answer it. Today there are three paths
and none admits:

- the runner's long call, `Runner::native_work`, which forwards the body
  unread (`runner/src/runner/commit.rs`);
- Hermes's synchronous `native.call`, which reaches the module through
  `js/src/door.rs`. Its host closure runs on the main thread, where the
  runner is (LLP 1067.000 D9: a worker-placed source's call already hops
  to main), so the closure calls admission there before the module;
- the web's `native.later`, which goes from `host/web-js/ts-data.js` to the
  page module directly, and calls admission in the page's runner first.

Raw bodies are admitted too: a body that spells a declared call is that
call.

**Context.** Each call carries the answer that made it and its origin.
The rule, on both runtimes: **an async function that began under an answer
resumes under that answer** after every `await`, whatever promise it
awaited, and a binding call reads the answer current at the moment of the
call. Both runtimes run one turn at a time and keep the current answer in
one slot (Hermes's `currentCall`, `js/src/prelude.js`; the web's
`answering`, `host/web-js/ts-data.js`), exposed to the bundle as
`__exact_async_context` (`current`, `swap`).

No engine carries context across a native `await` (Hermes has no async
context, and patching `then` does not reach one), so the bake lowers a data
module's `async` functions to generators (`lowered`, ES2016, in
`js/bake/src/typescript.mjs`) and replaces Rolldown's `asyncToGenerator`
helper with `asyncContextHelper`: called, an async function captures the
current answer; each step it resumes puts that answer back and restores
the one before after. So a promise answer A made and answer B awaits (an
in-flight cache shared across answers) resumes B as B: the case LLP
1016.000's socket amendment had to accept as running under whichever turn
drained it. As built (2026-10-18), on Hermes and in the web's page bundle;
the native fixtures bundle the same way, so every `exact-js` test runs
lowered, and `js/tests/it/context.rs` fails without the helper.

What the helper does not reach runs under the turn that drains it: an
explicit `.then` callback outside an `async` function, and an async
generator's steps. There D12's least-privileged origin applies, so a
misattributed call never widens a tool's or a wake's authority. Lowering
also lowers the later syntax ES2016 lacks (`?.`, `??`, object spread,
class fields); it adds 1.9 to 2.6 KB to a data module (0.7 KB gzipped;
Weatherlight, Messages, RealWorld and Field Notes, 7 to 8 KB minified
before).

A binding call made under no answer, or under an answer that has already
settled (a late continuation), refuses by name. An exported function is
shared by every answer, so the binding never rebinds it; it asks the
runtime. The stage 0 proof so far covers answers awaiting a shared promise,
then a `Promise.all` and an imported helper, and an answer let go
(`js/tests/it/socket.rs`); a foreground answer beside a tool-origin one
waits on the origin, later in stage 0.

**Synchronous forms** (LLP 1133 D6 rule 4). The portable functions return
promises on every target; the synchronous forms are separate names,
declared in `exact.json`:

- `geolocationStatusSync()`: a cheap read of the cached status;
- `getCurrentPositionSync({ maximumAge })`: the manager's last fix when it
  is eligible (D2), otherwise it fails at once with `POSITION_UNAVAILABLE`,
  so the caller falls back to `getCurrentPosition`; it never starts
  hardware and never prompts.

They exist where the host has a synchronous path to the module: TypeScript
on Apple, through `call` (LLP 1067.000 D9). On the web, in Rust, and on
Android until its host has a `call` that answers inside the 100 ms budget,
they throw `NotSupportedError`. Each passes admission; a cached fix is
returned only while the state is `granted`; under the agent each answers
from the preferred or default value and is never held. The Contract source
`geolocationStatus()` is marked `sync`, so it answers at its first ask with
no pending frame where the host can (LLP 1124 D5).

## 6. The substitute

**Shape:** `watchPosition` and `geolocationStatus` are facts;
`getCurrentPosition` and `requestPreciseLocation` are requests (LLP
1069.007 D1).

**One authority per fact.** `state` is set only by `prefer
permission.geolocation granted|denied|prompt`, the launch flag
`--permission geolocation=…` (LLP 1069.007 D2's group, built here) and
permission tickets. `available` and `accuracy` are set by `prefer extension
geolocation.geolocationStatus=…`, which refuses a `state` field, and by
ticket answers; the later of the two holds, and the journal records each.
The position is set by `prefer extension geolocation.watchPosition=…` and
by a position ticket's answer.

**A preferred position is an acquisition, not a cache entry.** As the
W3C's emulated position is (§6.6), it answers whatever the options, so
`maximumAge=0` and either `enableHighAccuracy` take it; its `timestamp` is
the value given, else the agent clock at the moment it answers.

**Timers run on the agent clock.** A request's written `timeout` is the
runner's timer under the agent: `clock +N` past it fails a pending
`position` ticket `TIMEOUT` and retires it, and `timeout=0` with no
preferred position fails `TIMEOUT` at once. A permission ticket has no
timer, as a platform's dialog has none.

**Target restrictions hold under the agent** (D14 admission step 2): a
web drive sees `NotSupportedError` from a synchronous form and from
`requestPreciseLocation`, an approximate Android app sees its ceiling, and
`prefer extension geolocation.geolocationStatus={"available":false}` makes
every call fail `NotSupportedError`.

**Values.** A position is
`{"coords":{"latitude":48.8566,"longitude":2.3522,"accuracy":3000}}`;
omitted fields take `accuracy` 100, every `option` field `none`, and
`timestamp` the agent clock's now. A failure is `{"error":"TIMEOUT"}`, with
any D1 code. `type @t 48.8566,2.3522` and `type @t 48.8566,2.3522,3000`
are the short forms. `=clear` returns to the defaults, never to the device.

**Defaults:** `geolocationStatus` is `{available: true, state: "prompt",
accuracy: "unknown"}`; no position is preferred.

**Transitions:**

| Event | Result |
|---|---|
| a request while `prompt`, from a foreground origin, including a `watchPosition` read | a `permission` ticket in `pending`, its `args` naming the capability, the request and its origin |
| `tap @t allow` on a `permission` ticket | `state` `granted`; `accuracy` `approximate` under `device.geolocation-approximate`, else `precise`; the request continues |
| `tap @t deny` on a `permission` ticket | `state` `denied`; the request fails `PERMISSION_DENIED` |
| `tap @t cancel` on a `permission` ticket | `state` stays `prompt`; the request fails `PERMISSION_DENIED` |
| `prefer permission.geolocation granted` or `denied` while a `permission` ticket is pending | settles it as `allow` or `deny` |
| `getCurrentPosition` while `granted`, a position preferred | answered from it, if eligible under `maximumAge` (a preferred position is always fresh) |
| `getCurrentPosition` while `granted`, none preferred | a `position` ticket: `type @t …` answers it and becomes the preferred position; `tap @t cancel` fails `POSITION_UNAVAILABLE` |
| `watchPosition` while `granted`, a position preferred | answered from it; re-asked when it changes, filtered by the reader's options |
| `watchPosition` while `granted`, none preferred | fails `POSITION_UNAVAILABLE`; asked again when one is preferred |
| a preferred position while `position` tickets are pending | settles each of them with it |
| `requestPreciseLocation`, `granted` and `approximate` | a `precision` ticket, a capability of its own: `allow` sets `accuracy` `precise`; `deny` and `cancel` leave the grant and `accuracy` as they were, and the call answers the status; D10's other states as D10 says |
| `prefer permission.geolocation denied` | readers fail `PERMISSION_DENIED`; a pending `position` ticket's one-shot fails `PERMISSION_DENIED` and the ticket is retired, so a later `type` delivers nothing; the preferred position is kept for when the state is `granted` again |
| a synchronous form | answered from the preferred or default value; never held |
| a tool-origin or wake-origin request | as production (D12) |

A ticket is retired when its request's answer is replaced, its mutation is
superseded, or its reader is released (D5). `--answer` fixtures (LLP
1069.007 D4) are not built; drives use tickets. The web uses no CDP
carrier (`Browser.setPermission`, `Emulation.setGeolocationOverride`): the
runner substitutes before the module, as on every host.

**Declared, not built in** (LLP 1133.001 D8: the standard library uses the
seam everyone uses). The runner, natively and on the web, knows no
geolocation: each name's `substitute` in `exact.json`, and the interface's
`permission`, say all of the above, and the plan carries them
(`modules.substitute`). As built (2026-10-19):

- `permission`: `name`, the `status` source, the `field` that is the state,
  the `denied` code, and what `allow` sets per grant line
  (`{"accuracy": {"device.geolocation": "precise",
  "device.geolocation-approximate": "approximate"}}`, the longest line the
  app grants winning).
- On a source: `default`; `short`, the paths `type @t a,b,c` fills;
  `fill`, what a preferred value leaves out (`"now"`: the agent clock's
  date).
- On a send: `from`, the source whose preferred value answers it; `ticket`,
  the capability held when there is none, whose typed answer becomes that
  source's preferred value; `cancel`, what `tap @t cancel` fails it with;
  `timeout`, the option that is its timer on the agent clock.
- A name's `request` (`always`, `when-prompt`) says when it waits on a
  `permission` ticket. A held request is ordered work under a continuation
  token of the runner's, which every host already dispatches and parks, so
  no host learned a capability; what a ticket's answer changes is announced,
  so readers are asked again by the path a live source's topic takes.

Every name of an interface the app uses is in the plan's `modules` table,
read or not, since a status or a `from` source is the substitute's to read.

**Disclosure:** `state.extensions` lists `geolocation`, its binding per
target, its readers and their options, each answer's origin and whether it
was native, substituted or a default, and the preferred values.

**Production:** none of it.

## 7. The consumer: Weatherlight

Weatherlight shows one city's weather and asks for no permission today

## 8. What this amends

- **LLP 1133 D2 and D6:** the examples take dotted keywords; D6's
  `resource here = getCurrentPosition(…)` becomes `watchPosition`, and its

  example likewise.
- **LLP 1124 D5:** `args` is an object of keyword arguments.
- **LLP 1133.000 §3.2:** geolocation's row (D3).

## 9. What stays out

- Background location, and delivery while the app is closed: they need
  LLP 1069.007's rule for work while closed, which notifications' RFC
  proposes first.
- Geofencing, visits and significant changes as tier 1 or 2: the roster's
  `geofencing` (reachable now through the hatch, in the foreground).
- Geocoding: the roster's `geocoding`.
- Play services' fused provider: a third party's implementation (D3).
- A `permissions.query` facade over every module (LLP 1133.000 §3.1).
- Agent-held authority and delegation records: LLP 1111's (D12).
- Windows, Linux, tvOS, visionOS, watchOS cells (D15).
