## Summary

Two modules of LLP 1133.000 §3.9, in one RFC because they share an area
and a wave, not a design. They differ in the thing that decides the most:

- **Gamepad** has a working acquisition already. Every host reads pads
  into the W3C Gamepad API's standard mapping and hands them to a game's
  canvas below the runner (`game/README.md`, "Controls": GameController on
  Apple, key and motion events on Android, the Gamepad API on the web,
  evdev on Linux, XInput on Windows). `@exact/gamepad` does not read pads
  again. It opens the host's **one pad registry per process** to a package
  (D4), so the module, the canvas and an app's native code see the same
  pads at the same indices, and adds what Contract and the platforms have
  that a canvas does not: which pads are connected and whose labels to
  show, effects (`playEffect`, the Gamepad API's rumble), a controller's
  light, and the platform objects.
- **Bluetooth** has nothing. `@exact/bluetooth` is Web Bluetooth's GATT
  client: `requestDevice` through a chooser, `connectGATT`, services and
  characteristics by UUID, reads, writes and notifications. Its two deep
  questions are **who draws the chooser and who holds consent** (D13: the
  browser's, AccessorySetupKit's, CompanionDeviceManager's, Windows'
  `DevicePicker`, or the module's own sheet where the platform has none),
  and **how notifications reach code without a commit each** (D15: values
  are bytes, so they are data code's, and a characteristic's notifications
  arrive as LLP 1133.013 D5's batch with a cursor the runner holds).

```
use getGamepads, playEffect, setLight, GamepadList from "@exact/gamepad"

resource pads = getGamepads() as shape GamepadList

action lit
  # the current pad when the send arrives; no pad or no rumble fails, unread
  send buzz = playEffect(type="dual-rumble", duration=180,
    strongMagnitude=0.6, weakMagnitude=0.3)
```

```ts
import { characteristicValue } from "@exact/bluetooth";

// Every Heart Rate Measurement the strap sent since this reader's last
// answer, at most 16, one commit a second.
const hr = await characteristicValue({ gatt, service: "heart_rate",
  characteristic: "heart_rate_measurement", interval: 1000, history: 16 });
```

**Consumers.** Gamepad's is Beacons (`game/games/beacons`), which gains
what a game built by hand with GameController has: its prompt names the
pad's own button ("Press ▢ to light this beacon" on a DualSense, the
SF Symbol on Apple), its on-screen controls step aside while a pad is in
use, the pad rumbles when a beacon lights, and its light bar turns the
beacons' amber when all three are lit (§10). Bluetooth has no consumer in
or beside the repo; this RFC proposes **Pulse**, a heart-rate display for
a Bluetooth chest strap: the Heart Rate profile is a public Bluetooth SIG
profile that straps from Polar, Garmin and Wahoo implement, and the
example Web Bluetooth's own specification opens with (§18).

**Targets.** Both modules: web, iOS, macOS, Android, tvOS. Gamepad also
on Linux and Windows, whose hosts already read pads, through a Rust
implementation in the package that LLP 1133.001 D5's `rust-static`
builder compiles (not built; D10 item 5 builds it, §22 question 1).
Bluetooth also on Windows by WinRT through the same builder; Linux is
`later`, with its reason (D20).

## 1. What exists

**Pads, on every host, for canvases.** A host reports a pad's whole state
when a button or an axis changes, in 1/256 steps, to the canvas that has
the focus, as `InputEvent::Pad { index, connected, standard, buttons:
[f32; 17], axes: [f32; 4], at_ms }` (`gpu/src/input.rs`). The index is the
host's slot: the next pad to connect takes the lowest free one, as the
Gamepad API's `index` rule says ("the lowest previously used index is
reused"). The engine folds pads into actions by standard position
(`GamepadSouth` and the rest, `game/engine/src/input/pad.rs`), and the
agent drives a pad as its own pad 0 inside the world
(`game/engine/src/agent.rs`, `delivery: synthesized`). Per host:

| Host | Registry | What only it can do |
|---|---|---|
| Apple | `CanvasPads.shared` (ExactSurfaces): slots of `GCController`, each `extendedGamepad.valueChangedHandler` set by it | `valueChangedHandler` is one closure per profile: a second owner would replace the first |
| Android | `Pads` (the canvas reader's `ExactActivity`): every `KeyEvent` and `MotionEvent` is offered to it first | only the activity sees input events; Android has no call that reads a pad's state |
| web | `navigator.getGamepads()`, polled per frame by `gpu-pads.js` (the wasm host's) | the browser's own registry; any reader may poll it |
| Linux | evdev devices opened at start (`input/pad.rs`), read-only, no hotplug | force feedback needs the device's file open for writing ([ff.html](https://docs.kernel.org/input/ff.html): `open("/dev/input/eventXX", O_RDWR)`) |
| Windows | XInput's four slots, polled (`pad_poll.rs`) | `XInputSetState` takes the same slot index |

Not built: rumble, lights, glyphs and identity on any host; any reading
of pads outside a canvas; no physical pad has been driven (QUEUE, "Game
pads have not met a real pad"). GameController is linked by ExactSurfaces,
which only an app with a canvas links (`host/apple/Package.swift`,
`EXACT_LINK_SURFACES`); an app without one dlopens it only for `GCMouse`
on an iPad (`DisplayPreferences.swift`), since linking it costs an iPhone
app's launch (LLP 1047.001.000).

**Bluetooth: nothing.** No host, package or app calls CoreBluetooth,
`android.bluetooth`, `navigator.bluetooth` or WinRT's Bluetooth. The
audio session's `allowBluetoothHFP` and `allowBluetoothA2DP` options
(`host/apple/modules/ExactExtensions.swift`) are audio routes, not this
module. `rules/DEFERRED.md` names "Bluetooth MIDI pairing" as out of the
MIDI entry and "Bluetooth restoration" as out of background's.

**The seams this RFC uses as built:** the package context (`destroy`,
`now()`, foreground, `origin`, `emit`, `surfaces`, `orientation`,
`ExactPackage.swift`); polled live sources and LLP 1133.013 D5's batch
with a runner-held cursor (`runner/src/runner/modules/samples.rs`);
`handle<kind>` and provisional replies (`handles.rs`); a module's events
on the root (`events.rs`); `"gesture": true` on the web; Android activity
results for an extension (contacts' `startActivityForResult`); bytes in a
declaration (LLP 1133.006 D8 item 1); the declared substitute with tracks.

**The web's wasm host has no extension modules** (QUEUE, 2026-10-24): it
binds no implementation and answers no `prefer extension`, and games run
on it. So Beacons on the web cannot reach `@exact/gamepad` until that
host can; the web implementation is driven on the JS target by the
conformance fixture (§10, §21).

# Part A — Gamepad

## 2. Tier 1

### D1 — The names

| Name | Kind | Web | Contract | Data code |
|---|---|---|---|---|
| `getGamepads(interval=)` | live source; a fact; `sync` | `navigator.getGamepads()` | `resource pads = getGamepads()` | `await getGamepads()` |
| `gamepadconnected` | event on the root, args `Gamepad` | the window's `gamepadconnected` | `column gamepadconnected=padOn` | — |
| `gamepaddisconnected` | event on the root, args `Gamepad` | `gamepaddisconnected` | the same | — |
| `playEffect(index=?, type=, duration=, startDelay=, strongMagnitude=, weakMagnitude=, leftTrigger=, rightTrigger=)` | send, answers `GamepadHapticsResult` | `gamepad.vibrationActuator.playEffect(type, params)` | `send r = playEffect(…)` | `await playEffect(…)` |
| `resetEffects(index=?)` | send, answers `GamepadHapticsResult` | `vibrationActuator.reset()` | the same | the same |
| `setLight(index=?, color=)` | send, answers nothing | none: a shared word | statement | `await setLight(…)` |

**Values:**

| Shape | Fields |
|---|---|
| `GamepadList` | `available` (the target has an implementation, and on the web `"getGamepads" in navigator`); `gamepads` (`Gamepad[]`, connected pads only, by index); `current` (`option<number>`, D2) |
| `Gamepad` | `index`; `id`; `mapping` (`standard` or `""`); `family` (`xbox`, `playstation`, `nintendo`, `generic`); `labels` (17 strings by standard index, D2); `effects` (`dual-rumble`, `trigger-rumble`: what `playEffect` can play on it); `light` (bool: `setLight` can colour it); `buttons` (`option<GamepadButton[]>`), `axes` (`option<number[]>`) and `timestamp` (`option<number>`), present only when the reader asks with `interval` (D5); `apple`, `android`, `windows`, `linux` (D7) |
| `GamepadButton` | `pressed`, `touched`, `value` (Gamepad §`GamepadButton`) |
| `GamepadHapticsResult` | `result`: `complete` or `preempted` (Gamepad §`GamepadHapticsResult`) |

Options of `playEffect` are the Gamepad API's `GamepadEffectParameters`:
`duration` and `startDelay` in milliseconds (default 0; the specification
recommends capping `duration` at 5 seconds, and the module does), and
`strongMagnitude`, `weakMagnitude`, `leftTrigger`, `rightTrigger` in
[0, 1] (default 0). `type` is `dual-rumble` or `trigger-rumble`.
`color` is a CSS colour string, or omitted to give the light back (D6).
`index` is optional on all three: without it, the current pad (D2);
`setLight()` with neither gives back every light the caller holds.

**Errors** are the specification's: `playEffect` and `resetEffects` fail
`InvalidStateError` while the app is in the background (the
specification's "document is not fully active or is hidden"),
`NotSupportedError` for a type the pad's `effects` lacks, `TypeError` for
a parameter out of range; a pad index with no connected pad fails
`NotFoundError`; a caller the origin rule refuses fails `NotAllowedError`
with `message` `person-required` (D9).

**Declared deviations,** each with its reason:

- **A list, not a sequence with holes.** `getGamepads()` returns
  `sequence<Gamepad?>` indexed by `index`; Contract needs a shape, so the
  answer is a record with connected pads only, each carrying its `index`.
- **Values are opt-in, by rate.** The web's snapshot always carries
  buttons and axes. A Contract reader that shows only which pads are
  connected would otherwise commit at every stick movement; so a reader
  receives `buttons`, `axes` and `timestamp` only when it names an
  `interval` (D5), and that number bounds its commits.
- **Three shared words the web lacks:** `current`, `family` and `labels`
  (D2), and `setLight` (D6). Apple's HIG asks a game to "use the connected
  controller's labeling scheme when referring to controls", and, of
  several pads, "labels and glyphs that match the one that the player is
  actively using" ([Game controls](https://developer.apple.com/design/human-interface-guidelines/game-controls));
  the web gives an `id` string only.
- **The pad is an argument,** not an object: `vibrationActuator` and its
  methods are sends taking `index`.
- **No `touches`.** The specification's `GamepadTouch` (a DualSense's
  touchpad) is left out until a consumer asks (§20); tier 3 reaches it.

### D2 — Identity, labels and the current pad

**`family`** is the face buttons' scheme, from what each platform says:

| Platform | From |
|---|---|
| Apple | `GCDevice.productCategory` ("DualSense", "DualShock 4", "Xbox One", "Switch Pro Controller", …) |
| Android | `InputDevice.getVendorId()` (API 19): `0x045E` Microsoft, `0x054C` Sony, `0x057E` Nintendo |
| Linux | the evdev device's vendor (`EVIOCGID`), by the same table; its driver already picks the layout (`gamepad::layout_for`) |
| web | the vendor in `Gamepad.id` where the engine writes one (Chromium's `Vendor: 054c`, Firefox's `054c-0ce6-…`), else the product name, else `generic` |
| Windows | `xbox`: XInput reports only XInput devices, which are Xbox-class |

**`labels`** are each standard button's name on that pad, so a prompt
says the pad's own word. On Apple each is the element's `localizedName`
([GCControllerElement](https://developer.apple.com/documentation/gamecontroller/gccontrollerelement/localizedname)),
which follows a person's remapping in Settings. Elsewhere the module's
table by `family`, declared once in the interface's `exact.json` so every
implementation and the substitute read the same words:

| Index | `xbox` | `playstation` | `nintendo` | `generic` |
|---|---|---|---|---|
| 0 south | A | Cross | B | A |
| 1 east | B | Circle | A | B |
| 2 west | X | Square | Y | X |
| 3 north | Y | Triangle | X | Y |
| 4–7 | LB, RB, LT, RT | L1, R1, L2, R2 | L, R, ZL, ZR | L1, R1, L2, R2 |
| 8, 9 | View, Menu | Create, Options | −, + | Select, Start |
| 10, 11 | LS, RS | L3, R3 | LS, RS | L3, R3 |
| 12–15 | Up, Down, Left, Right | the same | the same | the same |
| 16 | Xbox | PS | Home | Home |

`generic` is Android's own naming of a pad's buttons by position
(`KEYCODE_BUTTON_A` is "the first button on the bottom row",
[KeyEvent](https://developer.android.com/reference/android/view/KeyEvent#KEYCODE_BUTTON_A)).
The labels are text; the HIG prefers symbols, which is Apple's tier 2
(D7, `apple.symbols`).

**`current`** is the pad the player is using: on Apple
`GCController.current` ("the most recently used game controller … for a
single-player game", [current](https://developer.apple.com/documentation/gamecontroller/gccontroller/current));
elsewhere the registry's own, the pad whose button last went down (a
stick's drift is not use); `none` while no pad has been used since it
connected. It changes only when another pad takes over, so a reader of
the list commits on that, not on presses. A send without `index` is for
the pad that is `current` when the implementation receives it, so a
world's message, sent by the press that also made a pad current, needs no
commit to have landed first (D6); with no current pad it fails
`NotFoundError`.

## 3. One registry, three readers

### D4 — The host's pad registry is the one acquisition

Each host keeps one registry of pads per process: slots, the standard
reading of each, its identity, `current`, and, new here, the output
objects (haptic engines, vibrators, the evdev file, the XInput slot). The
canvas routing that exists reads it, and so do:

- **the module,** through the package context (`context.pads`, D10 item
  1): connected pads with their identity and readings, a change notice,
  and output calls (`rumble`, `stopRumble`, `light`), each by index;
- **the app's native code,** through the module's hatch (D8), which hands
  the platform object of a slot.

So an index means one pad everywhere: the world's `InputEvent::Pad`
index, `getGamepads().gamepads[i].index`, the index the app passes to
`playEffect`, and the slot a hatch receives. Each bound stage checks it
(§21).

**The registry is process-wide; its clients are not.** Package
instances are per session (LLP 1133.009 D10), and an app may embed two
sessions (LLP 1031 D10). So the registry arbitrates its outputs: each
effect and each light setting is a claim with an id, made by one client
(a session's package instance) on a device, not a slot: the index names
the device at the moment of the send, and a claim follows that device
while it stays connected, the background included. A disconnect ends
every claim on the device: an effect answers `preempted`, and a light
claim ends, so the pad shows the platform's colour when it returns. A pad
that drops and returns is a new connection (a new `GCController`, a new
Android `getId()`), and no platform names a physical controller
uniquely (Android's descriptor and Apple's vendor and product are shared
by identical pads), so nothing could tell it from an identical pad
connecting; a game sets its colour again from its own code. The
registry tells the claim's client when it completes or another claim
preempts it, which is how `playEffect` answers `preempted` across
sessions; and a client's `destroy`, or its
`resetEffects`, ends only its own claims. A light shows the newest
surviving claim's colour, and the platform's when none survives.

*Rejected:* the package reading pads itself. On Apple a second
`valueChangedHandler` would take the canvas's input away; on Android a
package never sees input events; on Linux a second open of a device
holds a second file whose effects are its own ("effects are file
descriptor specific", [ff.html](https://docs.kernel.org/input/ff.html));
and on each, two slot tables would number one pad differently.

*Rejected:* moving pads into the package and the canvas reading it. Pads
to a canvas need no permission and no asking, every game has them today
without importing anything, and the bake finds a module's use in Contract
and data code, not in a game's Rust (LLP 1133.013 D6's second rejection).

**Where the registry lives** is each host's. On Android it grows out of
the activity's `Pads`, with three changes. It moves from the activity to
the process, beside the host that a replacement activity adopts
(`ExactActivity.onCreate`, `Exact.live`): today each activity makes its
own `Pads` and its `onDestroy` releases it, so an activity the system
remakes while the process lives would start with no pads, no `current`
and no claims. No activity's `onStop`, `onDestroy` or `release()`
unregisters or clears the process's registry; it lives until the
process ends. Only the activity that is `Exact.reader` reports the
background to it (the all-released reading, below), and the same guard
holds for that activity's `Exact.hidden(true)`, which a replaced
activity's `onStop` sends today after its successor's `onStart`
(`ExactActivity.kt`), hiding the page the successor shows. Today `Pads.blur()` frees every slot when the app goes to
the background, so a pad comes back at whatever slot is free; the
registry instead keeps each slot's device across the background, as
Apple's `CanvasPads` and Windows' `pad_poll` already do, sending the
canvas an all-released reading (so a world's holds drop) and reporting
that reading until the pad's next event. And
`ExactActivity` today consumes every key `Pads` recognises, the D-pad's
included, whatever has the focus; the registry observes every pad event
and consumes it only while a canvas has the focus, so the platform's
navigation (D3) keeps the rest. On the web it is the browser's, so the web
implementation reads `navigator.getGamepads()` itself and the indices
agree by the browser's own; on Linux and Windows it is the host's crate.
On Apple it is `CanvasPads`'s slot table today, inside ExactSurfaces;
the Apple stage moves the registry where both a canvas and the module
reach it without either linking GameController before first pixel in an
app that has no canvas (the module's Swift loads after first pixel, LLP
1133.002 D16). Which target holds it is the stage's; that there is one
per process is this RFC's.

**Focus.** A canvas hears pads only while it has the focus (built). The
module's list does not follow the canvas's focus: like the web's
`getGamepads()`, it reports the pads while the app is in the foreground,
and nothing in the background (on the Mac, GameController forwards
nothing to an app that is not frontmost by default,
[shouldMonitorBackgroundEvents](https://developer.apple.com/documentation/gamecontroller/gccontroller/shouldmonitorbackgroundevents)).

### D5 — Contract reads which pads, and their values at a bounded rate

`getGamepads()` is a live source announced when its answer changes. With
no `interval`, the answer is identity only (D1), so it changes when a pad
connects or goes, when `current` changes and when a pad's `effects` or
`light` change: a handful of commits in a session. With `interval` (in
milliseconds, at least 50, LLP 1133.013 D12 item 2's floor), each pad
also carries `buttons`, `axes` and `timestamp`, and the implementation
announces a change at most once per `interval`, the latest reading, so a
controller-test screen or a "press the button for Jump" settings row
reads at most twenty answers a second whatever the pad does. A reader
that needs every press at frame rate is a canvas (built), not Contract.

On the web, the browser exposes no pad until "a gamepad user gesture"
(Gamepad §`getGamepads()`: a button pressed or an axis moved after
reading neutral), so the list reads empty until then; that is the
platform's, and the recipe says so. The web has no event for a press,
so the web implementation polls `getGamepads()` on animation frames
while any reader reads the list and the page is visible, to follow
`current`, and announces only what the reader's answer carries; a send
without `index` reads `getGamepads()` once more at receipt, so a press in
the same frame counts.

`gamepadconnected` and `gamepaddisconnected` are LLP 1133.004 D6 events,
raised on the root with the pad's identity, in order, once each,
whatever reads the list.

### D6 — Effects and lights go out through the registry

`playEffect` reaches the registry's output for that index on the main
thread (D3's mappings): it plays, and answers `complete` when
`startDelay + duration` has passed, or `preempted` when another effect or
`resetEffects` on the same pad replaces it, as the specification says. A
pad that disconnects while an effect plays answers `preempted`.

`setLight(index=, color=)` sets the pad's light where `light` is true:
`GCDeviceLight.color` on Apple, an RGB light's request in a
`LightsManager.LightsSession` on Android (`InputDevice.getLightsManager()`,
API 31). Without `color` it gives the light back: on Apple it writes the
colour it read before its first write, and on Android it closes the
session, which returns the light to the system. The app's background
gives every light back; the registry keeps the claims and writes them
again when the app returns, so a game sets its colour once per
connection. A disconnect ends the pad's claims (D4); the game sets the
colour again from its own app-origin code, not from `gamepadconnected`,
whose handler has the device's origin (`events.rs`), which `setLight`
refuses (D9).

**From a world.** A game's effects begin in its tick. The world says so
on the path that exists, `w.emit("lit")`, which the canvas's `message=`
handler hears as a Contract action, and the action sends `playEffect`
without `index`, for the current pad (D2). This crosses the runner: the
effect starts a frame or two after the tick that caused it. For a
one-shot effect (a hit, a beacon lit) that is inside what a person feels
as simultaneous; stage 2 measures emit to motor on each host and records
it.

**A world's message carries what caused it.** A `message=` handler is a
new commit at the app's origin today (`event.rs`), whatever made the
world emit. A tool that invokes an action which posts to a world could so
make a later emission start the pad's motors, which D9 refuses a tool.
The canvas seam therefore marks each emission with an origin, and the
mark is sticky: once a message of `tool`, `wake` or `device` origin is
posted into a world, every emission of that world carries the least
privileged origin posted so far; `app` otherwise. The mark and each
queued message's origin are simulation state: written when the message
is posted, saved in the world's snapshot (`sim/snapshot.rs`, EXSIM) and
restored with it, so a new canvas that restores a marked save is marked.
Only a restart that builds a fresh world from its arguments and discards
the queue clears it; not the clock, a sensor sample or a person's input,
since a tool's message can leave state that emits much later and the
world's code is not traced. The cost falls only on a game that lets a
tool drive its world, or posts into it from a module's event (a
`device` origin, `events.rs`), and also starts devices from it: until a
fresh start, its effects fail `person-required`. Such a game posts what
it learns from an event in its next app-origin action instead. This is seam addition D10 item 6, and any
module whose device a world drives meets it (§19).

*Rejected for now:* a world driving a pad's motors below the runner, as
pads reach it. A continuous effect tied to the simulation (an engine's
rumble following a throttle each frame) would need it, and it is the
first thing to build when a game asks (§20). It would be the canvas
seam's output direction, the reverse of LLP 1133.013 D6's
`surfaces.input`, and would need its own admission story, since a world
is not a caller the runner admits today.

## 6. Permission

### D9 — No grant, and who may play

No platform asks: GameController, Android's input devices, XInput and
evdev need no permission, and the web's `gamepad` Permissions Policy
feature defaults to `*` (Gamepad §"Permission Policy integration"). The
hosts read pads for every canvas with no grant line today. So the module
declares **no grant**, a recorded exception to LLP 1133 D7's "names its
grant": a line here would gate nothing, and requiring one for the module
but not for the built pads would be a rule with no reason. What the
platforms need is a manifest entry, not a grant: Android's
`android.permission.VIBRATE`, a normal permission that shows no prompt,
for a controller's vibrator ([controller haptics](https://developer.android.com/games/sdk/game-controller/controller-features)),
which the Android implementation's own manifest declares and the
reader's merge carries. There is no permission state, and `available` is
the only fact.

**Origins.** Reading the list and hearing the events are facts any caller
may read. `playEffect`, `resetEffects` and `setLight` move a device in a
person's hands, so they take LLP 1133.009 D10 item 8's `"origin": "app"`
and `"foreground": true`: a tool invocation or a wake fails
`NotAllowedError`, `person-required`, as starting any device does; the
app's own foreground code and a person's input may, and so may a world's
message only when nothing but the app's own code and a person's input
was posted into it since its fresh start (D6).

**Seam additions,** each general and proved by the out-of-tree fixture
first (LLP 1133.001 D8):

1. **The pad registry in the package context,** on every host:
   `pads.list()` (each slot's index, identity and latest standard
   reading), `pads.changed(handler)` (a slot connected, disconnected, its
   reading changed, or `current` changed; main thread), and output by
   index (`rumble(index, strong, weak, durationMs)`, `triggerRumble`,
   `light(index, rgb?)`), each a claim with an id that the registry
   reports complete or preempted to its client, and `end(claim)`; a
   client's `destroy` ends its claims (D4). On Apple this moves the
   registry out of `CanvasPads`; on Android it keeps slots across the
   background and consumes events only for a focused canvas (D4). On Linux
   the host opens each pad read-write, falling back to read-only, which
   then reports no effects.
2. **A `color` type** in declarations: a CSS colour string, refused at
   bake when literal and invalid, delivered to an implementation as RGB.
3. **A send answered after a span on the agent clock** (`"after"` and
   `"preempts"` in the substitute): the timer geolocation's `timeout`
   built, keyed by an option, so the substitute answers `playEffect` as
   the specification's timing says (§9).
4. **A context member's absence is a fact, not a failure:** an
   implementation on a host whose context lacks `pads` (an older host)
   answers `available` false.
5. **A package implementation for a Rust host.** LLP 1133.001 D5 designs
   `builder: rust-static`; nothing builds it, so no module has a Linux or
   Windows implementation today. The Linux and Windows hosts already route
   a declared module's body to the native slot (`bound.rs`), but nothing
   on the desktop loops answers it: the slot has one handler, installed
   only by `Presenter::serve_requests` for a shell
   (`host/linux/src/presenter/requests.rs`), which the Android reader
   calls and the Linux desktop host and the Windows host do not. So the
   item is three parts: the build step that compiles a package's `linux/`
   or `windows/` crate into the app's host crate, as a path dependency the
   build generates (LLP 1133.001 §3's Rust row); a trait the host calls
   (`later`, `call`, `release`, `destroy`, with the context); and **the
   dispatch**, one handler on each desktop loop that sends a package's
   bodies to its crate on that loop's thread and a shell's requests to the
   shell's inbox, so neither installation replaces the other. The Windows
   loop initializes COM on its window thread, where WinRT's
   `DevicePicker` and GATT calls run (D20). Gamepad is the cheapest first
   user, because both hosts already own its devices. Until all three
   land, the Linux and Windows cells read `available` false. §22
   question 1.
6. **An origin on a world's message** (D6): a posted message's origin
   enters the simulation's state and snapshot; every emission carries
   the least privileged origin posted since the world's fresh start; the
   `message=` handler's commit takes it. The snapshot's layout changes, so
   its version (the `EXSIM` prefix) moves, under the snapshot's own rule.

**Values.** `BluetoothDevice` is `{id, name}`: `id` an opaque string,
stable for the app across launches on native targets and per origin on
the web; `name` the advertised or GAP name, `option`. `BluetoothGATT` is
`{gatt, device, connected}`. `gattServer` answers `{connected,
reconnecting}`. `gattServices` answers `{services: [{uuid, isPrimary,
characteristics: [{uuid, properties}]}]}`, `properties` the eight booleans
of `BluetoothCharacteristicProperties`. `characteristicValue` answers
`{value, timestamp, sequence, samples: [{value, timestamp}], dropped,
interrupted}` (D15). A UUID option takes what `BluetoothUUID.getService`
and `getCharacteristic` take: a GATT assigned-number name
(`heart_rate`, `battery_level`), a 16- or 32-bit number, or a 128-bit
string; answers carry the 128-bit lowercase form. Filters are
`BluetoothLEScanFilter(services=, name=, namePrefix=, manufacturerData=,
serviceData=)`, the specification's `BluetoothLEScanFilterInit`, with
each data filter's `dataPrefix` and `mask` a hex string (a deviation:
the web takes a `BufferSource`), so `requestDevice` is a Contract value
throughout. `bluetoothStatus` answers `{available, radio, state}` (D18).

**Errors** are the specification's: `NotFoundError` when the person
cancels the chooser or nothing matches, or a service or characteristic is
absent; `SecurityError` for a service the person's choice does not cover
(below), the GATT blocklist on the web, or a write to a Client
Characteristic Configuration on any target; `NetworkError` when the device
is not connected; `NotSupportedError` where the target has no
implementation or a characteristic lacks the property an operation needs;
`InvalidStateError` for a released handle; `NotAllowedError`,
`person-required`, for a caller the origin rule refuses (D18).

**Declared deviations:**

- **Filters are what every chooser can apply.** Android's chooser takes
  `BluetoothLeDeviceFilter`s, each one `ScanFilter` (one service UUID,
  one service-data and one manufacturer-data entry) with a name pattern,
  any of which may match, and no exclusion
  ([BluetoothLeDeviceFilter.Builder](https://developer.android.com/reference/android/companion/BluetoothLeDeviceFilter.Builder)).
  So each filter names at most one service, one `manufacturerData` entry
  and one `serviceData` entry, with `name` or `namePrefix`, and there is
  no `exclusionFilters`; a literal filter beyond that fails the bake, a
  computed one `TypeError`. The web and the Apple sheet could do more;
  they take the same, so an app's choice means one thing everywhere.
- **Services and characteristics are named by UUID within a connection,**
  not held as objects: CoreBluetooth, Android and WinRT discover them
  that way, and a Contract value holds no method. A characteristic that
  appears twice in one service takes `instance=` (its order in
  `gattServices`), default 0.
- **A notification subscription is a live source** (D15), started by its
  first reader and stopped at its last release, as motion's sensors are.
- **`gattserverdisconnected` is a live source's change,** `gattServer`'s
  `connected`.
- **`autoReconnect`, a shared word:** every native platform keeps a
  dropped link trying (Apple's `CBConnectPeripheralOptionEnableAutoReconnect`,
  iOS 17 and macOS 14, [Apple](https://developer.apple.com/documentation/corebluetooth/cbconnectperipheraloptionenableautoreconnect);
  Android's `connectGatt(…, autoConnect = true, …)`; Windows'
  `GattSession.MaintainConnection`, "the system waits indefinitely for a
  connection", [Microsoft](https://learn.microsoft.com/windows/apps/develop/devices-sensors/gatt-client)).
  The web has none, and its implementation calls `connect()` again on
  `gattserverdisconnected` while the page is visible, with a backoff.
- **The person's choice covers services everywhere.** On the web a
  device's grant covers the filters' services and `optionalServices`, and
  any other fails `SecurityError` (the specification's "allowed
  services"). Native platforms have no such rule; the module applies it on
  every target, so an app that works natively works on the web. The GATT
  blocklist stays the web's: native platforms apply their own (iOS hides
  the HID service, for one).

### D14 — The chooser, by platform

`requestDevice` is a person choosing one device. Who draws that choice,
and what consent it carries, differs:

| Target | Chooser | Consent it carries |
|---|---|---|
| web (Chromium) | the browser's, which requires transient activation (`"gesture": true`, LLP 1133.013 D12 item 5) | that device, for the origin, for its allowed services |
| iOS and iPadOS 18+, in an app that declares `apple.accessories` (D16) | AccessorySetupKit's picker ([ASAccessorySession](https://developer.apple.com/documentation/accessorysetupkit/asaccessorysession)) | that accessory, without the app's Bluetooth authorization ("privacy-preserving user consent", [AccessorySetupKit](https://developer.apple.com/documentation/accessorysetupkit)) |
| iOS, iPadOS, macOS, tvOS otherwise | **the module's own sheet**: a list of matching peripherals as `scanForPeripherals(withServices:)` finds them, by name, with Cancel, in the platform's list style; Apple draws no chooser for CoreBluetooth | the app's Bluetooth authorization (`CBManager.authorization`), asked by the system when the module first makes its `CBCentralManager`; then the device |
| Android | CompanionDeviceManager's system dialog (`associate` with a `BluetoothLeDeviceFilter`), returned through the activity's result | no scan or location permission ("doesn't require location permissions", [Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)); `BLUETOOTH_CONNECT` for the connection, asked first (D18) |
| Windows | `DevicePicker` over Bluetooth LE's device selector ([DevicePicker](https://learn.microsoft.com/uwp/api/windows.devices.enumeration.devicepicker)) | none asked by an unpackaged app |

AccessorySetupKit cannot be tier 1's default. Its picker requires each
item to carry "a `bluetoothCompanyIdentifier` or `bluetoothServiceUUID`,
and at least one" name substring or data mask, a name and an image from
the app, and the same identifiers in Info.plist, without which "the app
crashes" ([Discovering and configuring accessories](https://developer.apple.com/documentation/accessorysetupkit/discovering-and-configuring-accessories)).
So it serves an app setting up its maker's own accessories, not "any
heart-rate strap", and it is tier 2. It is also **a mode of the whole
app, not of one call**: an app that declares AccessorySetupKit's support
is not shown CoreBluetooth's permission prompt, and its CoreBluetooth
reaches only the accessories the person gave it through the picker; its
manager does not read `poweredOn` until there is one
([Meet AccessorySetupKit](https://developer.apple.com/videos/play/wwdc2024/10203/)).
So the app declares it once, in its manifest (`apple.accessories`: each
accessory's name, image and literal filters, each a service or company
identifier with a name substring or one manufacturer-data mask, which is
all `ASDiscoveryDescriptor` matches: no `serviceData`, no exact `name`), the bake derives
the Info.plist keys from that list, and on iOS 18 and later every
`requestDevice` opens the picker with the declared accessories its
filters match; a call that matches none fails `NotFoundError`, and the
bake refuses a literal filter that matches none. One iOS bundle serves
iPhone and iPad (`build.mjs`'s `UIDeviceFamily`), so the mode holds on
both; only where the OS has no AccessorySetupKit (iOS and iPadOS 17,
macOS) does the same app use the sheet, and stage 3 confirms on iOS 17
that the declaration is inert there. tvOS has no AccessorySetupKit and
its bundle never carries the key.

**The module's own sheet** is what a hand-built Apple app draws, since the
platform draws none; it is a tell only if it looks like a browser's. It
shows discovered peripherals that match the filters, de-duplicated by
identifier, updating as they appear, and closes on a choice or Cancel. On
tvOS it is a focusable list. It is not a package view: the
implementation presents it as the contacts picker presents
`CNContactPickerViewController`.

**Remembered devices.** `getDevices()` lists the devices the person chose
that the app has not forgotten. On the web it is the specification's
`getDevices()`, which Chromium ships behind a flag ([MDN data](https://developer.mozilla.org/docs/Web/API/Bluetooth/getDevices)), so it reads empty and a
reload needs another choice. On Apple the module keeps the chosen
peripherals' identifiers and their allowed services in the app's own
store and finds them with `retrievePeripherals(withIdentifiers:)`
(AccessorySetupKit's own `accessories` list in that mode); on
Android the app's CDM associations (`getMyAssociations`); on Windows the
device ids it chose, in the app's store. `forgetDevice` removes the
record, disassociates on Android and calls `ASAccessorySession`'s removal
where AccessorySetupKit chose it.

### D15 — Values are data code's, and notifications arrive in batches

**Bytes are not Contract values.** Contract has no bytes type; LLP 1133.006
D8 item 1 gives `bytes` to data code (a `DataView` in TypeScript, as the
web's `value` is; `Vec<u8>` in Rust; base64 on the wire). So the names
whose answers or options carry bytes (the characteristic and descriptor
values) are data code's, and the bake refuses them in Contract by name
(`contract-module-bytes`). Contract
reads the status, the devices, the connection and the service tree, and
shows what the app's data code makes of the values. That is also how a
hand-built app is layered: a profile parser between the radio and the UI
(Microsoft: "an application profile must be defined … to interpret the
data").

**Notifications are a batch with the runner's cursor** (LLP 1133.013 D5,
whose seam names "a Bluetooth characteristic's notifications and a
heart-rate strap"). `characteristicValue` is a polled live source: the
runner asks every `interval` (default 1,000 ms, at least 50) while a
reader reads; the first answer carries the latest value and no batch;
each answer after carries every notification since the reader's last
delivered answer, oldest first, at most `history` (default 0, at most
1,024), with `dropped` counting what the bound let go and `interrupted`
true when delivery paused (the background, a disconnect). The
implementation keeps a ring per reader group and answers from the `after`
cursor the runner passes. `history` 0 keeps only the latest; a profile
that needs every notification sets a bound its rate fits.

**Data readers need the cursor Contract readers have.** LLP 1133.013 D5
promises that an answer the runner discards loses nothing, and that each
reader has its own cursor. That holds for Contract readers. It does not
yet hold for data code, which is every reader of `characteristicValue`:
a data reader is keyed by the source's name and arguments alone
(`samples.rs`, `data_reader`), so two data resources reading one
characteristic share a cursor; its cursor moves when the reply leaves
the implementation (`modules.rs`, `cursored`), before the answer that
holds it commits, so a refused or superseded answer consumes a batch; and
a data argument group is released only with the whole name (`bound.rs`,
`release_idle`), so a resource that moves from one characteristic to
another leaves the first subscribed. D19 item 5 closes all three in the
runner, for every sampled source (motion's data readers too): a data
reader's identity is the data resource that made the call, the call's
site in that resource's source (not its order in one evaluation, which a
branch can shift) and its argument group, so a reader that moves to
another characteristic starts that ring without a cursor; its cursor lands only with the
commit that delivers that resource's answer, as a Contract reader's
does; and a data group no resource read in the last commit is released
as a Contract group is.
A peripheral notifying at 100 Hz costs a reader one commit per
`interval`, not a hundred. Each notification is stamped on the session
clock when it arrived; the platforms give no peripheral-side time.

*Rejected:* one event per notification (LLP 1133.004 D6's events). Each
would be a settlement, and a peripheral sets the rate, not the app.

**Starting and stopping.** The first reader of a `(device, service,
characteristic, instance)`, through any handle in any session, writes
the Client Characteristic
Configuration descriptor (`setNotifyValue(true, for:)` on Apple; on
Android `setCharacteristicNotification` and the CCCD write; WinRT's
`WriteClientCharacteristicConfigurationDescriptorAsync`); the last
release of all of them (`release(name, args)` or a session's `destroy`)
writes it off: a characteristic has one CCCD per client on the
peripheral (Bluetooth Core, Vol 3 Part G §3.3.3.3), and the process is
that one client. A characteristic that has
neither `notify` nor `indicate` fails `NotSupportedError`, and the app
reads it with `readCharacteristicValue`.

**Connections are handles.** `connectGATT` answers a `handle<gatt>`
(LLP 1133.009 D10 item 10): provisional until the runner delivers the
reply, disconnected if it drops the reply, and every handle a session
holds is let go at its end (`destroy`). **A handle is a lease** on the
process's one link to its device, which the module keeps beside its one
`CBCentralManager`, `BluetoothGatt` or `BluetoothLEDevice` across
sessions: the link stays while any lease does; `disconnectGATT` and
`destroy` end their own leases only; the link keeps reconnecting while
any lease asked for `autoReconnect`; and `forgetDevice` ends every lease
on the device, whose other holders then read `connected` false. A
dropped link with `autoReconnect` keeps the handle, `gattServer` reads
`reconnecting`, and readers of its characteristics answer `interrupted`
until it returns, when the module subscribes again for the readers it
has. Without `autoReconnect`, the handle stays and reads `connected`
false; a read of it fails `NetworkError`, and `connectGATT` again makes a
new one.

## 14. Permission

### D18 — LLP 1133.002 §4 for Bluetooth

**Declare.** `device.bluetooth <purposeKey>`. Derived:

| Target | Derived | Does a prompt show the purpose? |
|---|---|---|
| iOS, iPadOS, tvOS | `NSBluetoothAlwaysUsageDescription` (required "if your app uses the device's Bluetooth interface", [the key](https://developer.apple.com/documentation/bundleresources/information-property-list/nsbluetoothalwaysusagedescription)); with `apple.accessories`, on iOS only, `NSAccessorySetupKitSupports` `Bluetooth` and `NSAccessorySetupBluetoothServices`, `…Names`, `…CompanyIdentifiers` from its filters | yes |
| macOS | the same usage key, and `com.apple.security.device.bluetooth` in the sandbox ([entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.device.bluetooth)) | yes |
| web | `Permissions-Policy: bluetooth=(self)` | no (the chooser is the consent) |
| Android | `BLUETOOTH_CONNECT`; `<uses-feature android:name="android.software.companion_device_setup">`; `android.hardware.bluetooth_le` not required; at a manifest minimum below 31, `BLUETOOTH` with `maxSdkVersion="30"` | no |
| Windows | nothing for an unpackaged app; `<DeviceCapability Name="bluetooth"/>` if the host is ever packaged | — |

**Read.** `bluetoothStatus()` answers three facts, kept apart so that
reading them never asks and the way to consent is never hidden:

- `available`: the target can do this at all (an implementation, and
  Bluetooth LE hardware: `navigator.bluetooth` and
  `getAvailability()`, which counts a radio switched off as available,
  [Web Bluetooth §"Overall Bluetooth availability"](https://webbluetoothcg.github.io/web-bluetooth/#availability);
  `FEATURE_BLUETOOTH_LE` on Android; every Apple device and Windows
  adapter the module runs on). An app hides its Bluetooth feature only
  when this is false.
- `radio`: `on`, `off` or `unknown`. On Apple it is `unknown` while
  `CBManager.authorization` is undetermined (reading it needs a
  `CBCentralManager`, and making one is what prompts); once the person
  has decided, the module makes its manager when the status is first
  read and reports the manager's state; in AccessorySetupKit's mode it
  stays `unknown` until an accessory is set up. On the web it is always
  `unknown`; elsewhere the adapter's state. An app says "Turn on Bluetooth" on `off` and still
  offers the choice, whose failure says the same.
- `state`, meaning on every target what LLP 1133.002 D8 says: whether
  `requestDevice` and a connection need the person to allow something
  more than the choice. On Apple it is read from the class property
  `CBManager.authorization`, which makes no manager.

| Platform | `state` |
|---|---|
| web | `granted`: the chooser is the only consent; `denied` where the policy or the browser blocks Bluetooth; `permissions.query` refines it where Chromium answers |
| Apple, the sheet's path | `notDetermined` `prompt`; `allowedAlways` `granted`; `denied`, `restricted` `denied` |
| Apple, AccessorySetupKit's mode on iOS 18+ | `granted`: the picker is the consent |
| Android | `BLUETOOTH_CONNECT`'s state, with LLP 1133.002 D8's history in the host's one permission store (LLP 1133.008 D8 item 7) |
| Windows | `granted` |

**Ask.** `requestDevice` is the request, and it may take two decisions,
in order (LLP 1133.009 D10 item 9): the platform's permission while
`prompt` (Apple's system prompt when the module makes its manager;
Android's `BLUETOOTH_CONNECT` dialog), then the chooser. A denial fails
`NotAllowedError` before any chooser opens. Cancelling the chooser fails
`NotFoundError`, as the specification says. Android's CDM "requires
Location Services to be enabled" ([Companion device pairing](https://developer.android.com/develop/connectivity/bluetooth/companion-device-pairing));
with them off it fails `NotFoundError` with `message` `location-off`, and
the recipe says to tell the person.

**Who may.** `bluetoothStatus`, `getDevices` and `gattServer` are facts
any caller reads. `requestDevice` opens system UI, so a tool invocation's
or a wake's fails `person-required` in every state; on the web it must
also run inside a press (`"gesture": true`), and a data-code call outside
one fails `SecurityError` there, as the browser's rule. `connectGATT`,
every read, write and descriptor operation, and a `characteristicValue`
read that would start a subscription are `"origin": "app"`,
`"foreground": true`: the radio is a device, and a tool does not start it
or write to a peripheral (a lock, a heater) in the person's name. A
tool's read of a subscription the app already runs joins it as it runs,
LLP 1133.013 D4's "a join changes nothing", and never holds it.
`forgetDevice` is the app's too.

**Foreground.** Delivery stops in the background: iOS suspends an app
without the `bluetooth-central` mode, and this module declares none.
Links are kept as each platform keeps them; on return, readers answer
`interrupted` and continue, and a link the system dropped reconnects by
`autoReconnect`.

**Recover.** `openURL("app-settings:")`, as LLP 1133.002 D11; a web app
explains the browser's own setting.

## 16. The substitute

A **declared substitute**: Pulse's drives run on every host, the Linux
proof host included, and a chooser, a connection and a strap's
notifications are data on the agent clock.

- **Status:** `{available: true, radio: "unknown", state: "prompt"}` on
  the first read, as a fresh install on Apple reads;
  `prefer permission.bluetooth granted|denied|prompt` and
  `--permission bluetooth=…` set `state`.
- **Devices:** `prefer extension bluetooth.devices=[…]`, each
  `{"id", "name", "reachable": true, "services": {"<uuid>": {"<uuid>":
  {"properties": [...], "value": "<base64>", "events": [{"at": 0, "value":
  "<base64>"}, …]}}}}`, names allowed for UUIDs (`heart_rate`).
- **Transitions:**

| Event | Result |
|---|---|
| `requestDevice` while `prompt`, foreground origin, in a press | a `permission` ticket; `allow` sets `granted` and continues to the chooser |
| `requestDevice` while `granted` | a `chooser` ticket listing every preferred device (the agent is the person choosing; the filters are not simulated, the conformance suite drives them in Chromium); `tap @t <id>` answers that device and records its allowed services; `tap @t cancel` fails `NotFoundError` |
| `connectGATT` to a `reachable` device | `{gatt: <a new handle>, device: <id>, connected: true}`; the keyed fixture reads `devices[<the handle's device>]` |
| `connectGATT` to one not reachable | with `autoReconnect`, a handle reading `connected` false, `reconnecting` true until the device becomes reachable; without, `NetworkError` |
| `prefer extension bluetooth.devices=…` making a connected device unreachable | its handles read `connected` false; readers `interrupted`; with `autoReconnect`, back when reachable again |
| `characteristicValue` | the events of that characteristic, each delivered once when the agent clock passes its `at` (counted from the subscription's start), in batches by D15; the first answer the latest value |
| `readCharacteristicValue` | its `value` |
| `writeCharacteristicValue`, `writeDescriptorValue` | journaled in `state.extensions.bluetooth.writes`, answered at once |
| a service the choice did not cover | `SecurityError`, as production |
| a tool's or wake's `requestDevice`, `connectGATT`, write | `person-required`, as production |

- **Disclosure:** `state.extensions.bluetooth` lists the remembered
  devices, each link with its leases (handle, session, `autoReconnect`),
  each subscription with its readers and cursors, and the writes.

**Production:** none of it.

## 17. The consumer: Pulse

No app in or beside the repository reads a Bluetooth device. The
smallest real one is the example Web Bluetooth opens with: a heart-rate
monitor. **Pulse** (`apps/pulse`) shows a chest strap's heart rate. It is
small, a person can buy the hardware anywhere, and it needs every part of
this module that can fail: a chooser behind a permission, a connection
that drops when the strap leaves the skin and comes back, a notification
stream parsed in data code, a read, a remembered device at the next
launch, and absence on the web where the browser has no Bluetooth.

- **Contract:** `bluetoothStatus`, `getDevices` and `gattServer`; a
  **Connect a strap** button whose press sends
  `requestDevice(filters=[BluetoothLEScanFilter(services=["heart_rate"])],
  optionalServices=["battery_service"])` and then `connectGATT(device=…,
  autoReconnect=true)`; the device's id kept as a persisted setting
  (`docs/recipes/persisted-setting.md`); at launch, a remembered device in
  `getDevices()` connected from the app's own code; a **Forget** button.
- **The reading:** the heart rate in large tabular digits, "Not touching
  skin" when the strap says so, the battery, the strap's name, and
  "Reconnecting…" while `gattServer` reads it.
- **Data code (`app.ts`):** `heartRate(gatt)` reads
  `characteristicValue(service: "heart_rate", characteristic:
  "heart_rate_measurement", interval: 1000, history: 16)` and parses the
  latest Heart Rate Measurement per the GATT Specification Supplement:
  the flags byte (bit 0, a `uint16` rate rather than `uint8`; bits 1–2,
  sensor contact supported and detected; bit 3, energy expended present;
  bit 4, RR intervals present, in 1/1024 s), then the rate. `battery(gatt)`
  reads `battery_level`, one `uint8` percent.
- **Grant:** `device.bluetooth bluetoothPurpose`, and a strings table.
- **States:** `available` false: "This browser has no Bluetooth" on the

## 19. What reaches beyond these modules

- **Apple's game-controller declarations.** No exact2 app declares
  `GCSupportsControllerUserInteraction` or `GCSupportedGameControllers`.
  Without the first, the App Store shows no controller badge and "users
  can customize their game controller mappings in Settings" does not
  apply ([GCSupportsControllerUserInteraction](https://developer.apple.com/documentation/bundleresources/information-property-list/gcsupportscontrolleruserinteraction)).
  Every game whose actions name a `Gamepad…` button should derive both
  (`ExtendedGamepad`) at its bake; that is the game shell's, not this
  module's (QUEUE line).
- **A pad's Menu button pauses** in a hand-built game (the HIG's table:
  "Opens game settings or pauses gameplay"); Beacons does not. The world
  can `emit` it to Contract today; Beacons' own fix (QUEUE line).
- **Bluetooth MIDI** is MIDI's: on Android it needs this module's chooser
  to find the device `MidiManager.openBluetoothDevice` opens; on Apple
  CoreAudioKit's own sheet. LLP 1125's entry should name it when an app
  with a Bluetooth MIDI keyboard asks.
- **The wasm host's extension modules** (QUEUE, 2026-10-24) now block two
  modules' consumers on the web, motion's and this one's.
- **A world's message has no origin today** (D6, D10 item 6). Any module
  whose device a game drives from its tick meets it; the seam fixes it for
  all of them.
- **Process-wide devices under per-session packages.** The pad registry
  and Bluetooth's links are shared by every session in a process, while a
  package instance and its `destroy` are per session; recording's capture
  has the same shape. This RFC settles it for its two modules by claims

- **Android's reader consumes pad keys whatever has the focus**
  (`ExactActivity`); D4 changes it, and that touches every app with a
  canvas on Android. Its `onStop` also calls `Exact.hidden(true)` for an
  activity its successor has already replaced, the same overlap D4
  guards for pads.
- **The Rust hosts have no package dispatch** (D10 item 5): every module's
  Linux and Windows cell waits on it, not only these.
- **Data code's readers of a sampled source** share cursors and lose
  batches today (D15, D19 item 5); motion's data readers have the same
  defect.
