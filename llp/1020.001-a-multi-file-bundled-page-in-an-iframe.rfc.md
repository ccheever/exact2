## 1. Summary

An `iframe` whose `src` is an HTML page in the app's `assets/` or `deck/`
runs that page with its scripts, stylesheets, fonts, workers and lazy chunks
on the web, and before this only its HTML on Apple. The Apple web arm now
serves those two trees under a custom URL scheme through a
`WKURLSchemeHandler`, so every relative URL in the page resolves to the file
beside it, read through the session's asset resolver. The web host does not
change.

This completes the case LLP 1020 D2 declared and left for a consumer. It is
not an admission of bundled web apps as a class: LLP 1020 §5's refusals
(permissions, popups, navigation policy, a process-death event) stay refused,
each with its own trigger.

## 2. Motivation

Exact Draw embeds Excalidraw, a built web app of JavaScript, CSS, fonts and
asynchronous chunks, in a Contract shell. On the web,
`src="assets/editor/index.html"` works: the build copies `assets/` beside the
app's page (`host/web-js/build.mjs`), so the page's relative URLs load. On
macOS and iOS the arm read the one HTML file and gave it to WebKit as a
document at `http://exact.localhost/frame/<id>/index.html` (LLP 1020 §10). No
server answers that origin, so every sub-resource failed and the frame was
blank. Exact Draw serves the editor from a Bun process on loopback instead.

A single-file build (everything inlined) is a workaround, not a fix: a large
app's lazy chunks, workers and wasm do not inline. This change does not by
itself let Exact Draw drop its companion: the companion also serves the
chosen files, which waits on the issue named above.

## 3. Design

**D1: the app's bundled pages have an origin on Apple, `exact-app://app`.**
The arm registers a `WKURLSchemeHandler` for the scheme `exact-app` on each
web view it makes. A local HTML `src` under a served tree is loaded as
`exact-app://app/<path>`, with its query and fragment: `/deck/index.html` is
`exact-app://app/deck/index.html`, and its `./app.js` is
`exact-app://app/deck/app.js`. `WKURLSchemeHandler` cannot take `http` or
`https` (WebKit refuses the registration), so `http://exact.localhost` could
not be served this way. Castle shipped the same mechanism for its decks
(`castle-deck://`, LLP 1020 §8 Q1).

The origin is a contract, because a guest's saved data is keyed to it:
- **One origin per app,** as a web build's pages share the app's origin. Two
  bundled pages of one app share `localStorage`, IndexedDB and OPFS, as they
  do on the web. A standalone app is its own process and data store
  (LLP 1031 D1), so the origin needs no app id; an embedding app shares its
  data store with its own web views, which do not register `exact-app`.
- **It does not change.** A later change of scheme or host orphans what
  guests saved, so it would need a migration, which this LLP does not plan.
- **The data lives in WebKit's default data store,** as a remote guest's
  does now: not in `app:/`, not under Exact's grants or the agent's
  `storage`, and cleared with the app's website data.

**D2: what is served, and to whom.** Only the trees a web build publishes
beside the app's page for a page to live in: `assets/` and `deck/`. Never the
rest of what the resolver can read: an embedded generation's resolver walks
the bundle's resources (which hold `receipt.json`, with a development
build's opening-link token, and `host.macos.resources` trees) or, for a bare
development executable, the working directory. Only a web view whose
committed `src` is a bundled page answers the scheme; a remote guest cannot
read the app's assets through it. A missing or refused file is a 404, and the
host logs it (`exact: iframe <src>: <url> is not an app asset under assets/
or deck/`). The types a browser is strict about are named exactly
(`text/javascript` for `.js` and `.mjs`, `application/wasm`, `text/css`), and
`bytes=` ranges are answered for media.

**D3: reads go through the session's resolver.** ExactKit already read the
top document through `ExactApp.resolver` (`WebModule.swift`) and handed the
bytes to the arm. The arm gains a read callback from ExactKit
(`exact_web_set_reader`), which it calls off the main thread. A delivered
generation's assets and a development client's (the dev URL) reach every
sub-resource, as they reach the top document.

**D4: the table of LLP 1020 §10, as amended.**

| Guest | macOS | iOS |
|---|---|---|
| Bundled HTML page under `assets/` or `deck/` | direct, at `exact-app://app/<path>` | direct when its viewport `<meta>` asks for `width=device-width` at scale 1; otherwise a wrapper at `exact-app://app/.exact/frame/<id>/index.html`, its inner frame at `exact-app://app/<path>` |
| Other local files (a PDF, an image; `app:/` sources) | as §10 has them (unchanged) | as §10 has them (unchanged) |
| Remote http(s), no `sandbox` | direct (unchanged) | the wrapper (unchanged) |
| Remote with `sandbox`, and `data:`/`about:`/`blob:` | the wrapper (unchanged) | the wrapper (unchanged) |

The iOS wrapper is served at the page's own origin because WebKit partitions
a frame's storage by the top document's site: under a wrapper at any other
origin (`http://exact.localhost`, or `exact-app://frame`) a framed page's
`localStorage` and IndexedDB did not survive a relaunch, and under a
same-origin wrapper they are the direct page's. So a viewport tag does not
change what a page keeps. A direct page's `sandbox` is sent as
`Content-Security-Policy: sandbox …` on its response, as the synthetic local
document's is now; WebKit enforces it on a scheme response (§4). The message
check expects `exact-app://app`, or `null` under a sandbox without
`allow-same-origin`.

**D5: the bundled-page contract.** A bundled page is the app's own code, and
a portable one follows three rules, on every host:
1. It talks to the app by `postMessage` only (LLP 1020 D2). On the web an
   unsandboxed `assets/` page is same-origin with the app's page and could
   reach `window.parent.document`; on Apple it has no such parent (direct) or
   only the wrapper. A page that reaches its parent works on the web and
   breaks on Apple.
2. Its saved data is the app origin's: on the web the app's own origin, on
   Apple `exact-app://app` (D1). It is not the app's `app:/` storage; data the
   app must own crosses by message.
3. It does not rely on a service worker or `document.cookie`: WebKit refuses
   both under a custom scheme (§4), where the web has them.

Untrusted content does not belong in `assets/`: load it by URL from its own
origin, or sandbox it without `allow-same-origin` (an opaque origin, with no
saved data, on every host).

**D6: what is unchanged.** The web host, the Contract surface (no new tag,
attribute or event), `app:/` sources and other local files (#115), remote
guests, the agent's `tree` and `screenshot` of a guest, and the arm's
on-demand load: the handler lives in the web arm's library, so an app with
no `iframe` pays nothing for it. Android, which loads a local guest as
`file://`, and Linux, which has no `iframe` (LLP 1020 D5), are outside this
LLP; a host that serves bundled pages adopts D1's contract.

## 4. The probe, and what it settled

A one-file `WKWebView` app with the handler, on macOS 27.0.1, loading a page
of a module script, a static and a dynamic import, a stylesheet, a JSON
fetch, an empty wasm module, a classic and a module worker, and storage
counters, each run twice. Then Caltrain's deck fixture through the built arm
on macOS 27, iOS 27.0 and iOS 26.5 simulators, direct and (iOS) wrapped.

| Question | Result |
|---|---|
| Q1: a secure context? | Yes: `isSecureContext`, `crypto.subtle` (a SHA-256 digest) and `navigator.clipboard`, direct and framed. The deck posts `deck-ready` only from a secure context, so every smoke keeps checking it. |
| Q2: what loads | Module scripts, static and dynamic `import()`, `fetch`, `WebAssembly.instantiateStreaming`, classic and module workers, stylesheets, OPFS. **Refused:** `navigator.serviceWorker.register` ("must be called with a script URL whose protocol is either HTTP or HTTPS"), and `document.cookie` is dropped. |
| Q3: storage across relaunch | Kept, direct and under a same-origin wrapper; not kept under a wrapper at another origin (the reason for D4's wrapper). |
| Q4: CSP `sandbox` on a scheme response | Enforced: origin `null`, `localStorage` throws `SecurityError`. |
| Q5: `http:` loopback sub-resources | Load (an image, and a `no-cors` fetch). |

Not measured: macOS 14–26 and iOS 17–26.4 (no runtimes on this Mac), and a
physical device. The async lane's iOS and tvOS runs and the next device run
cover what they reach; a failure on an older OS keeps that OS's sandboxed
pages in the wrapper (Q4) or reopens §5 (Q1).

## 5. Alternatives

- **A loopback HTTP server in the process.** A real `http://127.0.0.1`
  origin needs no answer to Q1, Q2's refusals included. Its port is the
  origin, so it must bind a port the app keeps across launches, or every
  guest's saved data is lost at relaunch; a kept port can be taken by another
  process, and the server is reachable by every local process. It is the
  fallback if the scheme fails on a supported OS.
- **`loadFileURL(_:allowingReadAccessTo:)`.** A `file:` page has an opaque
  origin in WebKit: module scripts and `fetch` of its own files are refused,
  and its storage is not kept. Rejected.
- **A single-file build.** The author's workaround before this. It cannot
  carry lazy chunks, workers or wasm.

## 6. Verification

- Caltrain's deck fixture (`apps/caltrain/deck/`) takes its title's colour
  from `deck.css` and posts `deck-ready` from a module once a dynamic chunk
  and a JSON fetch have loaded, in a secure context. `smoke.mjs` checks the
  message and counts the title's pixels on the web, macOS and iOS.
- Removing `deck.json` fails the macOS smoke with `exact: iframe
  /deck/index.html: exact-app://app/deck/deck.json is not an app asset …`:
  the check exercises the scheme, not a cached page.
- Without its viewport tag the deck is wrapped on iOS, and the smoke passes.

## As built (2026-10-15)

- `WebArm.swift`: `AssetScheme` (one per web view, holding its arm weakly;
  stopped tasks are not answered; the wrapper is served from memory),
  `assetURL`, and `exact_web_set_reader`. A sub-resource the scheme misses is
  logged by the handler, not again by the page's `error` listener.
- `WebModule.swift`: the reader, through `ExactApp.shared.resolver`.
- Smokes: macOS 27 and web pass; iOS 27.0 and 26.5 pass every deck step and
  fail one keyboard step that does not touch an iframe ("Enter at the
  field"). tvOS compiles.
- Not done here: Exact Draw itself has not been run against this; its editor
  moves into `assets/` on their side.
