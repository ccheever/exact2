# LLP 1126.002: The watch app and its live driver

**Author:** Douglas Lowder, with Claude (Opus 5.5)
**Date:** 2026-10-18

## 0. Summary

A whole exact2 app runs live on Apple Watch with the plan, runner and kernel in Rust, as on the
other Apple platforms. SwiftUI draws the kernel's frames. The spike ran Caltrain this way on the
watch simulator and on an Apple Watch Series 10 (watchOS 27.0.1):

- boot 67–73 ms and first frame 0.40–0.72 s after process start on the watch;
- 15 MiB footprint;
- a 1 Hz timer turn of 1.6 ms (median);
- taps, the Digital Crown, text input and Back work.

The driver is one new file beside the snapshot driver, which it reuses for every node. The core
needs a few public calls that iOS already makes. Nine decisions follow; four of them are
questions for Charlie (§6).

## 1. Motivation

LLP 1126 admitted watchOS on 2026-10-17 ("let's try to hit full apple platform support for
launch"). Its D10 plans complications through the snapshot driver, and these have landed for
the simulator (LLP 1126.001 WP17). The app itself was left open: "A watch app is its own small
app, so its entry is the author's to write. Its design is a later RFC's." Today the watch app is
a gallery of complication placeholders (`docs/reference.md`). An app's complications can only
show snapshots, because an entry plan has "no request, timer or handler"
(`contract/cli/src/snapshot/entry.rs`). A watch app that a person opens and uses needs the live
session.

## 2. What the spike shows

The spike changes no Rust, no C ABI and no plan format. It adds:

- `ExactSnapshot/LiveDriver.swift`: `LiveModel`, an `@Observable` that owns a
  `HeadlessSession`, its latest snapshot and the clock; `LiveView`, the roots in `FrameLayout`.
- In `HeadlessSession`: public calls for what a live host does (§D3).
- In `SnapshotNodeView`: when a live input is present, a node with `press` becomes a plain
  `Button`, a vertical scroller becomes a `ScrollView`, and a native control (`control`) and a
  field (`input`) get platform leaves (§D5). Widgets do not change: they have no live input.
- In `ExactWatch`: the live root, the platform's Back (§D5), and, in a development build, an
  agent link on the simulator (§D8).
- `watch.mjs --watchos --device --phone <watch udid>`: the watch app alone, arm64, watchOS 26,
  signed with the team's development profile (§D7, §D10).
- In Caltrain: a watch screen (§D4).

The turn times are the runner's and the kernel's only. SwiftUI's own work after a turn was not

By hand, on the simulator and on the watch: the departures show and the countdown changes with

## 3. Design

### D1 — The driver lives beside the snapshot driver

**Proposed:** the live driver is a file of `ExactSnapshot`, and it draws with the snapshot
driver's nodes (`SnapshotNodeView`, `FrameLayout`, the text, image, icon and progress leaves).
A live input on `SnapshotEnvironment` (`live`, package-visible) turns on what only a live
session does: presses, scrolling, the platform leaves. A widget sets none, so its archive does
not change.

The two drivers then share every paint rule, and a fix to one is a fix to both. The cost is
that `ExactSnapshot` grows by about 150 lines and the watch app links SwiftUI views that a
widget extension also links, which it does already.

### D2 — One observable snapshot per batch

**Proposed:** `LiveModel` publishes the whole `HeadlessSession.Snapshot` after each turn.
SwiftUI identifies each node by its id and draws again what changed. The snapshot is
copy-on-write (`HeadlessSession.swift`), so publishing it copies no nodes.

LLP 1126 D10 proposed one observable model per node. The spike's tick costs 1.6 ms in the
runner on the watch, which leaves room. A model per node is the change to make if a measured
frame is late, and the spike did not measure SwiftUI's part. Stage 1 (§4) measures it.

### D3 — `HeadlessSession` becomes live

**Proposed:** keep one session type. `HeadlessSession` gets public calls for the host's half of
a live session, each of which iOS's `ExactSession` already makes through `Runtime`:

| Call | What it does |
| --- | --- |
| `timerDue`, `advance(at:)` | the runner's next timer deadline (from each batch that is not busy) and running it |
| `onWake(_:)` | a request's reply wakes the session (`exact_set_wake`); the host calls `refresh(at:)` |
| `insets(top:right:bottom:left:)` | the safe area (`env(safe-area-inset-*)`) |
| `scrolled(_:left:top:)` | a scroller's offset |
| `fieldEvent(_:kind:payload:at:)` | a field's input event (`FieldInput`'s wire) |
| `controlTitle(_:)` | a native control's title (`exact_press_face`) |
| `agent(_:)` | the runner's agent operations |

`Node` keeps its `handlers` (from `create`) and its scroll content size (the `content` op).
These are public because the watch links `ExactCore` as a binary framework, across which
`package` access was not tested.

A separate `LiveSession` would keep the snapshot driver's session free of input. It would also
copy the turn, apply and text code, which is most of the file.

### D4 — The watch entry: the app's plan, with a branch the author writes

The spike first ran Caltrain's phone layout at 204 × 168 pt. It runs, but a phone screen does not
fit a watch. With about 50 lines of Contract, Caltrain's root branches on `exactViewport().width < 300`
into a watch screen: the station, the next two trains each way, Change station, and the station
list with search and Back.

**Proposed:** for now, a watch app runs the app's main plan, and the author writes the watch
screen as a branch on the viewport, as a web page does for a small screen. Nothing new enters
the manifest or the bake. The cost is that the whole plan ships to the watch, with the phone
screens the watch never shows.

The other answers, each with a manifest or bake change: a second full plan from a root the
manifest names; or a separate app folder that shares the data crate. Question 1 (§6).

### D5 — The platform's controls at the leaves

**Proposed**, as built in the spike:

- **A press:** a node with a `press` handler is a plain `Button`. It plays no haptic, as
  SwiftUI's `Button` plays none by itself; the app's `haptic()` command is how an author asks
  for one (LLP 1115). The spike's `.click`, which was not felt on the watch, is removed. To
  check on a watch: that a hand-built SwiftUI button there gives no haptic either.
- **A native button** (`control`, a `button` the kernel left to the platform): its title from
  `exact_press_face`, drawn by the platform. The spike draws a capsule; the watch's bordered
  button style is the answer to build.
- **A field** (`input`): a `TextField`. The system's input (dictation, Scribble, the keyboard)
  returns the whole text, which the driver sends as one `insertReplacementText` input event
  with the caret at the end.
- **Scrolling:** a vertical scroller is a `ScrollView`, which the Digital Crown scrolls. Its
  offset goes to `scrolled` (watchOS 11 and later).
- **Back:** the navigation bar's back chevron, shown while the screen has a press target that
  declares `aria-keyshortcuts="Escape"`, presses it. This is the rule tvOS's Menu button follows
  (`RemoteTVOS.swift`).

Not built: `select` as a `Picker` on the Crown; a route's depth as a `NavigationStack` push
(Caltrain's router has one level, so the spike could not test it); toggles; the watch's
list style for a list of buttons.

### D6 — Lifecycle: timers run while the app is active

**Proposed:** the driver arms one timer at the runner's deadline. When `scenePhase` leaves
`active`, it stops; when it returns, the driver advances once. On the watch, one 40 s run had 4
ticks and a 60 s run with the screen kept on had 29. The stop at `scenePhase` is the likely
cause of the first; the spike did not log the phase.

In Always On (`isLuminanceReduced`), the app stays on screen and does not tick. A `time` node
with a `countdown` or `relative` format is drawn by SwiftUI from its instant, as in a widget
(`SnapshotLive`), so it stays correct without the runner. Caltrain's countdown is a string that
`tick` makes, so it would freeze. Question 2 (§6) asks whether Always On needs more than this.

### D7 — Architectures: arm64 at watchOS 26

Rust's `aarch64-apple-watchos` sets watchOS 26 as its minimum (LLP 1126.000 §1.6). The spike
built for it and ran on a Series 10, which runs arm64 and arm64e. `arm64_32-apple-watchos`, for
watches whose `usize` is 32 bits, builds (stage 0) but has not run; `host/apple/link.mjs`
refuses a 32-bit Mach-O.

**Proposed:** arm64 only, watchOS 26 and later. Question 3 (§6).

### D8 — Development and the agent

On the simulator, a development build listens on the Unix socket that `EXACT_AGENT_SOCKET`
names, as the iOS simulator does, and answers JSON lines: the runner's `tree`, `state`, `logs`
and `tags`, and `tap` and `input` by testId. The spike drove every check through it with `nc`.
Screenshots come from `xcrun simctl io <watch> screenshot`.

On a device, low-level networking is restricted ([TN3135](https://developer.apple.com/documentation/technotes/tn3135-low-level-networking-on-watchos)), so there is no socket. The spike read its
measurements from standard output through `devicectl --console`.

**Proposed:** a `watchos` host in `scripts/agent.mjs` over this socket on the simulator. A
device's agent is later work: an outbound URLSession bridge, as the phone's token bridge is.
A new agent host is apparatus (`rules/RULES.md`), so this needs a human's yes.

### D9 — What the watch refuses

The watch has no Metal and no JIT (LLP 1126 D10). Caltrain's phone screens have three GPU
canvases and an iframe deck. The watch branch shows none of them. In the spike's first run (the
phone screens at watch size), the driver drew the sky canvas's children and not its surface.

**Proposed:** the watch build keeps the bake's `hasGpu: false`. A canvas surface or an iframe
that the watch would show draws its children only. An app with `app.ts` stays out until Hermes
builds for watchOS (LLP 1126.001 §5 Q3), as `watch.mjs` already does. A development build
writes one log line for each node it cannot draw.

### D10 — Packaging

On the simulator, the watch app is inside the iOS app with its complications, as `watch.mjs`
builds it. The spike's device build installs the watch app alone: `WKWatchOnly`, no App Group
and no complication extension, so the team's development profile signs it.

**Proposed:** on a device too, the watch app ships inside the iOS app with its complications.
That needs the App Group and the extension's profile, as LLP 1126.001 WP13 does for the
phone, and is its own work item. A watch-only app (no iPhone app) is question 4 (§6).

## 4. Stages

1. **The driver lands**, behind the existing `--watchos` simulator build: D1–D3, D5 as built
   (the haptic removed), D6, D9's log line. Caltrain's watch screen lands with it. Done when
   the simulator checks of §2 pass and the six checks, the iOS and tvOS builds and the iOS
   smoke match `origin/main`. SwiftUI's time per turn is measured here.
2. **The agent host** (D8), with the human's yes.
3. **The device build** inside the iOS app, with complications (D10), arm64 (D7).
4. **The other leaves** of D5: `select` on the Crown, routes as a `NavigationStack`, toggles.

## 5. Alternatives

- **The UIKit presenter.** watchOS has no UIKit views, so the iOS presenter cannot be built for
  it (LLP 1126 §1).
- **A SwiftUI view per Contract element, laid out by SwiftUI.** A second layout engine would
  disagree with the kernel, which is the web's layout everywhere else (LLP 1115).
- **plan2cpp** (a C++ target over a board interface, outside exact2). It needs no Rust on the
  device, but it runs only the subset it admits, and its semantics are a second copy. The watch
  runs Rust, so the runner and kernel run as they are.

2. **Always On (D6):** is a frozen screen with live `time` nodes enough, or should the runner

3. **Older watches (D7):** arm64 at watchOS 26 only, or arm64_32 too?
4. **A watch-only app (D10):** does the manifest need one, or is the watch app always a
