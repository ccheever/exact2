# LLP 1069.011.000: Native buttons in toolbars, tabs, menus and swipe actions, and in reused rows

**Type:** RFC
**Status:** Draft r1 (2026-10-02)
**Systems:** Contract (`controls.rs` contexts), Apple host (`ToolbarMac.swift`, `ShortcutsMac.swift`, `SegmentsIOS.swift`, `SegmentsMac.swift`, `MenusIOS.swift`, `MenusMac.swift`, `SwipeActionsIOS.swift`, `NodePoolIOS.swift`, `ControlsIOS.swift`, `NativeButtons*.swift`), Linux host (`navigation.rs`), docs
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-10-02
**Related:** LLP 1069.011 (native buttons; this lifts its D11 and D13), LLP 1021 (menus), LLP 1059 (the native tab bar), LLP 1035.001 D10 (segments), LLP 1068 (row reuse), LLP 1075.003 (native platform control: the header and bar items, Draft), LLP 1069.001 (form controls)
**Decision:** Charlie, 2026-10-02: "Do all these" (the owed list of LLP 1069.011 §7)

## Summary

LLP 1069.011 refused a native button (`button appearance="auto"`) wherever a host reads a button some other way than as a button: a toolbar, a tab, a menu row or invoker, a swipe action, a keyboard shortcut, a `header`. And it kept rows holding one out of list reuse. Each host projection that makes a platform item from a button finds it by `kind == "button"` and reads its label and glyph from its child views; a native button is kind `control` and has no child views (its face is kernel data, LLP 1069.011 D5). So the refusals were the honest answer, not a choice.

This RFC lifts them with one change underneath every projection: **a button's face has one reader**. `NodeView.pressFace` returns a button's label, title and symbol, from its child views for a custom button and from `buttonFace` for a native one, and every projection asks "is this a button" with `isButton` (kind `button`, or a native button). Then each context maps what a native button adds: its symbol (menu rows and swipe actions get an image they could not have before), its style (a prominent style is a prominent toolbar item), its accent (a toolbar item's tint, a swipe action's colour). Rows holding controls join list reuse by handing the control across the id change.

## 1. What exists (2026-10-02, at `485020542`)

- **The refusal.** `contract/lower/src/controls.rs` `button_context` (the ancestors: `header`, `toolbarPlacement`, a `role` that is or may be `tablist`, `popover`, a swipe row) and `check_native_button` (the button's own `popovertarget`, `commandfor`, `popover`, `toolbarPlacement`, `swipe*`, `aria-keyshortcuts`, a `role` other than `button`, `href`, `action`).
- **Kinds.** The Apple bridge sends `Pressable` as kind `button` and `Control` as `control` (`host/apple/src/host.rs:1398-1399`). A native button's children are not views (`paragraph.rs`, LLP 1069.011 D5).
- **Toolbars.** iOS projects nothing: `toolbarPlacement` renders as authored. macOS (`ToolbarMac.swift`) makes an `NSToolbar` from a `toolbarPlacement="window"` toolbar owner whose visible children are all `kind == "button"` with `press` (142) or one heading (143); any other child falls the whole toolbar back to authored (146-149). An item reads `accessibilityLabel ?? text(node)` and its first image child's `symbolName` or raster (170-181); it is always `isBordered`, icon-only; `toolbarPlacement="navigation"` on the button makes it navigational (183). No style, prominence or tint.
- **Shortcuts.** `ShortcutsMac.swift` makes `NSMenuItem`s for chord-declaring buttons and toolbar items, `kind == "button"` (53-61), titled by their child views (141-145).
- **Tabs.** iOS (`SegmentsIOS.swift`) and macOS (`SegmentsMac.swift`) take a tablist's direct children with `kind == "button"`, role `tab` and `press` (iOS 91-95, macOS 33-37). iOS projects a `UITabBar` when every tab has a `TabBarFace` (two child views: a `symbol:` image and a label) or a `UISegmentedControl` when every tab has a `segmentFace` (one image child, or text only); macOS the segmented control. Selection is `accessibilitySelected`; a pick presses the tab.
- **Menus.** iOS (`MenusIOS.swift`) lays a transparent `UIButton` with `showsMenuAsPrimaryAction` over each invoker (`popovertarget`, `commandfor`; 106-114); its deferred menu presses the invoker's own handler, then builds items from the popover's rows with `press` (287-306): title from child views, `.on` from `aria-checked`, `.disabled`, `.destructive`; no image ever. A row without `press` starts a section. Confirmations (`alertdialog`/`dialog`) need exactly one `kind == "button"` action and one cancel (250-256). macOS (`MenusMac.swift`) pops an `NSMenu` when a `presenter.press(id)` lands on an invoker (`PresenterMac.swift:684-689`), rows as on iOS without destructive or image. The web is the browser's popover. Linux refuses a press on an invoker (`POPOVER_UNSUPPORTED`), found by walking to the nearest `Pressable` (`navigation.rs:9-21`).
- **Swipe actions.** iOS only (`SwipeActionsIOS.swift`): each named action needs `press` and a non-empty `accessibilityLabel` (77-88), else the whole row falls back to the authored scroll; its colour is its `background-color` (default system blue, set even over destructive's red, 321), its image a snapshot of its first child view (323-338). macOS, the web and Linux render the authored row.
- **Header.** No Apple code reads `header`; the refusal anticipated LLP 1075.003, which lifts a header's heading and buttons into a navigation bar (Draft).
- **Row reuse.** iOS only (`NodePoolIOS.swift`): a row parks only when every node's kind is in `["view", "text", "image", "button", "scroll", "svg"]` (86, 209, 381) and every platform subview is the node's own glyph, material, clip box or glass view (`children(_:)`, 178-191). A control's kind is `control`, and its `UIControl` is a platform subview, so a row holding any control never parks. Parking keeps views and drops ids (`presenter.release(id) { $0.recycle() }`); a take rebinds a parked tree to new ids (`rebind`, 466-488). `ControlHost` keys everything by id (`controls`, `kinds`, `reported`, `menus`, `lastRange`), and switches and checkboxes report through `tag = id`.

## 2. Measured and checked

- **AppKit 26** (the macOS 27 SDK's headers): `NSToolbarItem.style` (`plain`, `prominent`) and `backgroundTintColor` ("only if the item's style is prominent"), both `macos(26.0)`; UIKit has the same two on `UIBarButtonItem` (`ios(26.0)`), which no iOS projection uses yet.
- **UIKit** puts an image on a `UIAction` and on a `UIContextualAction` from `UIImage(systemName:)`; a native button's face already names its symbol as the platform does (`exact_button_face`, LLP 1035.004.000 `sf/` names included).

## 3. Design

**D1. One face reader, one test.** Every host projection that makes a platform item from a button asks `isButton` (kind `button`, or `isNativeButton`) where it now asks `kind == "button"`, and reads the face through `NodeView.pressFace -> PressFace { label, title, symbol, image }`: for a custom button, what each projection reads today from child views (unchanged behaviour); for a native button, `title` and `symbol` from `buttonFace`, `label` from `aria-label` or the title. The places: `ToolbarMac` (142, 170-186), `ShortcutsMac` (53-61, 141-145), `SegmentsIOS` (91-95, `TabBarFace`, `segmentFace`), `SegmentsMac` (33-37), `MenusIOS` (`items(of:)`, `title(of:)`, the confirmation filter), `MenusMac` (`menu(of:)`, `title(of:)`), `SwipeActionsIOS` (`label()`, `configuration`). One function, so a projection cannot read a native button's empty child list again.

**D2. Toolbars.** Contract admits a native button inside `toolbarPlacement` and `toolbarPlacement` on it. iOS: unchanged (toolbars render as authored, so the native button is itself). macOS: a native button with `press` is a toolbar item like a custom one: label, image (its symbol), title from D1; `toolbarPlacement="navigation"` as today; and its style: a prominent `buttonStyle` (`filled`, `bordered-prominent`, `prominent-glass`, `prominent-clear-glass`) is `NSToolbarItem.style = .prominent` with `backgroundTintColor` its `accent-color` (absent: the system accent), on macOS 26 in the 26 design (`LinkedDesign.liquidGlass`); any other style is a plain item. A custom button stays plain. The web and Linux: as authored.

**D3. The header.** Contract admits a native button inside `header`. Nothing reads `header` on Apple today; when LLP 1075.003 lifts a header's buttons into bar items it reads them through D1, and a native button's prominent style maps to `UIBarButtonItem.style = .prominent` as D2's does (written into 1075.003's owed list, not built here).

**D4. Tabs.** Contract admits `role="tab"` on a native button (its fixed role `button` yields to it) and a native button inside a `tablist`. A native tab is one of the tablist's tabs on both platforms (D1's `isButton`, role `tab`, `press`). Its face decides the projection as a custom tab's does: a symbol and a title is a `TabBarFace` (iOS's tab bar); a symbol alone (with its `aria-label`) or a title alone is a segment; the projection's own rules then apply unchanged (every tab must qualify, or the tablist stays authored). Selection stays `aria-selected`; its style is not read (a tab bar and a segmented control have their own look). Authored (not projected), native tabs are native buttons whose control carries the `.selected` trait, as today. The web: `<button role="tab" aria-selected data-button-style>`.

**D5. Menus.**
- *Rows.* A native button is a menu row (a popover's direct row with `press`): its title from D1, and its symbol as the item's image (`UIAction.image`, `NSMenuItem.image`), which a custom row cannot have; `aria-checked`, `disabled` and `destructive` as today (AppKit has no destructive item, as now). Its style is not read. A native row in a confirmation is an action or a cancel as a custom one is.
- *Invokers.* A native button with `popovertarget` or `commandfor` opens its menu from its own control, not an overlay. iOS: the `NativeButtonIOS` gets the deferred menu as its `menu` with `showsMenuAsPrimaryAction = true` (no overlay, no second accessibility element; the glass button's press response is UIKit's own); its primary action then no longer fires `activateNative`; the deferred menu presses the invoker's own handler first, as the overlay's does today. macOS: the `NSButton`'s action presses its own handler (if it has one) and then opens the menu, so a native invoker opens with or without `press` (a custom invoker needs one, an existing quirk this does not change). Linux: a native invoker is an invoker (`popover_invoker` walks to the nearest `Pressable` or native button) and its press is refused as a custom one's is. The web: the browser's own popover invoker.
- `role="menuitem"`, `menuitemcheckbox` and `menuitemradio` are admitted on a native button (its fixed `button` yields), as on a custom one.

**D6. Swipe actions.** Contract admits native buttons inside a swipe row (the body and its descendants) and as a named action. iOS: a native action's label is D1's (its `aria-label` or its title, so a title-only native action no longer drops the row to authored); its image is its symbol (`UIImage(systemName:)`), not a snapshot; its colour is its `accent-color`, or the platform's (system blue, or red for `destructive`: UIKit's default is no longer overwritten for a native action); a press is `presenter.press` as today. A native button inside the body is a native button in a table cell (UIKit's ordinary case). macOS, the web and Linux render the authored row.

**D7. Keyboard shortcuts.** Contract admits `aria-keyshortcuts` on a native button; `ShortcutsMac` makes its menu item through D1 (title, and its symbol as the item's image). Elsewhere it is what it is on a custom button.

**D8. Row reuse.** A row holding controls parks and is reused on iOS. The pool accepts kind `control` (its shape string carries the control's type, so a switch row never takes a native-button row's views) and accepts the node's control as one of its own platform subviews. Parking hands the control to the view (`NodeView.parkedControl`, out of `ControlHost`'s maps, still mounted, hidden with the row); a take's rebind leaves it there; `ControlHost.control(for:)` adopts a parked control of the same kind for the new id (`tag`, owner, and every per-id cache: `written`, `reported`, `menus`, `lastRange` reset, so the next sync configures it fully and reports its size). A parked control that is not adopted (the row was taken by a different kind) is removed then. A native glass button's slot is torn down with the row's material on recycle. macOS, the web and Linux have no row pool.

**D9. What stays refused.** `href` (a link is not a button), `action` (a form's submit is LLP 1069.001's), anything inside a `canvas` (its children are painted, not views). Their messages stay.

**D10. Tests.** Contract: each lifted context compiles, the three stay refused. XCTests (iOS and macOS): a toolbar with a native prominent item and a custom one (style, tint, image, press); tabs of native buttons projected as a tab bar and as segments, selection and press; a menu whose rows are native (titles, images, checked, destructive) and whose invoker is native (the control's own menu, no overlay, one press); a confirmation with native rows; a swipe action that is native (label from its title, symbol image, accent colour, destructive red); a shortcut on a native button; a row of a list holding a native button and a switch parked and reused (the same `UIControl`s adopted, configured for the new ids, presses delivered to the new ids). Linux: a native invoker refused as a custom one. The fixture gains a toolbar, a tablist, a menu and a swipe row of native buttons.

## 4. Build

1. Contract: lift the contexts (D2–D7), keep D9; tests.
2. Apple: `isButton` and `pressFace` (D1) in one shared file; each projection switched to them; D2's prominence; D5's invoker on the control; D6's colour and image; D8's pool and control handoff; XCTests.
3. Linux: the invoker walk. Docs: LLP 1069.011 (D11 and D13 replaced, pointing here), LLP 1001's native buttons paragraph, LLP 1075.003's owed list (D3).

## 5. Open questions

1. D2 maps four prominent styles to a prominent toolbar item and everything else to plain. Should `glass` (non-prominent) be distinguishable in a toolbar? AppKit 26's toolbar items are already glass; there is no third style.
2. D5 makes a native invoker open its menu without a `press` handler on macOS while a custom invoker still needs one. Fix the custom quirk in the same change?
3. D8 adopts every control kind. A select's menu and a date picker's state are rebuilt each sync, as far as the code shows; if a reviewer finds a kind whose state survives the rebind wrongly, that kind stays out of the pool.
