## Summary

LLP 1069.011 refused a native button (`button appearance="auto"`) wherever a host reads a button some other way than as a button — a toolbar, a tab, a menu row or invoker, a swipe action, a keyboard shortcut, a `header` — and kept rows holding any control out of list reuse. Each host projection finds a button by `kind == "button"` and reads its label and glyph from its child views; a native button is kind `control` with no child views (its face is kernel data, LLP 1069.011 D5).

This RFC lifts those refusals with one change underneath: **a button is recognised by `isButton` and read by `pressFace`** — its label, title and symbol, from its child views for a custom button and from the kernel's `buttonFace` for a native one — while each projection keeps its own eligibility rules and its own image path for custom buttons. A native button can be a menu row but not, in this version, a menu's invoker (§5). Rows holding controls join iOS row reuse with their controls recreated, never carried.

## 1. What exists (at `485020542`)

Unchanged from r1 §1 in substance; the reviews added: menu rows are any direct child with `press`, not `kind == "button"` (`MenusIOS.swift:290`, `MenusMac.swift:76`); a confirmation invoker is its own overlay with `.touchUpInside` and `openConfirmation`, which presses the invoker once (`MenusIOS.swift:89-104`, `:248`); macOS opens a menu only through `Presenter.press → menus.pressed(id)` (`PresenterMac.swift:684-688`) and refuses dialog commands (`MenusMac.swift:51`); Enter/Space on Apple and macOS shortcut discovery require a `press` handler (`NodeViewIOS.swift:289-294`, `NodeViewMac.swift:217`, `ShortcutsMac.swift:53`); segments sync before controls (`PresenterIOS.swift:808-809`), so a native button's control-written title is stale on its first batch; `SegmentFace.image` holds a `NodeView` and `TabBarFace` takes its tint from the image child's `tint-color` (`Accessibility.swift:36`, `SegmentsIOS.swift:48`, `:217`); the swipe table is a plain `UITableView` (`SwipeActionsIOS.swift:179`), and swipe-action discovery keeps an image map to find and name UIKit's rendered buttons (`:337`, `:359`); Linux focus and Enter/Space and the Apple agent's accessible-name enrichment key on role `button`/`link` (`surface_controls.rs:454`, `presenter/typing.rs:205`, `Accessibility.swift:211`); a reused row's view must be indistinguishable from a new element (`rules/DEFERRED.md:332-335`), and the pool already reuses rows around **holes** — heavy leaves destroyed on park and created fresh on take (`NodePoolIOS.swift:203`, `:263`).

## 2. Measured and checked

AppKit 26: `NSToolbarItem.style` (`plain`, `prominent`) and `backgroundTintColor` (prominent only), `macos(26.0)`; UIKit 26 has both on `UIBarButtonItem`. `UIAction.image`, `NSMenuItem.image` and `UIContextualAction.image` take a symbol image; `exact_button_face` already names the symbol as the platform does.

## 3. Design

**D1. `isButton` and `pressFace`.** `NodeView.isButton` is `kind == "button" || isNativeButton`. `NodeView.pressFace -> PressFace { label: String?, title: String?, symbol: String? }`: for a custom button what each projection reads today (its child views' text; `label` its `aria-label`); for a native button `presenter.buttonFace(id)` — the kernel's current face, never the control's last write — `title` its title, `symbol` its platform symbol name, `label` its `aria-label` (`buttonFace` has no label: `pressFace` reads it from the node). Each projection keeps its existing precedence for custom buttons — the toolbar item's label and a shortcut's title are `label ?? title`, as today (`ToolbarMac.swift:170`, `ShortcutsMac.swift:144`) — and a native button follows the same precedence there; a menu row's or confirmation's visible title is `title ?? label`, so a symbol-only native row shows its label. `PressFace` replaces child-view reads only; each projection keeps its eligibility rules and, for custom buttons, its own image path (toolbar rasters, segment and swipe snapshots); a native symbol is a `systemName`/`systemSymbolName` image at those three call sites. Button identity outside the projections also uses `isButton`, not the role: the Apple agent's accessible-name enrichment (`Accessibility.swift:211`); on Linux focusability and Enter/Space (`surface_controls.rs:454`, `presenter/typing.rs:205-210`) and the agent's accessible name (`host/linux/src/agent.rs:444-457`: a `Control` of type `button` is named as role `button` is, its accessibility label, else its title) recognise a native button under any role.

**D2. Toolbars.** Contract admits `toolbarPlacement` on a native button and a native button inside a toolbar. iOS projects no toolbar (unchanged: the native button is itself). macOS: a native button with `press` is an item like a custom one, its label, image and title from D1, `toolbarPlacement="navigation"` as today; in the 26 design (`LinkedDesign.liquidGlass`) a prominent style (`filled`, `bordered-prominent`, `prominent-glass`, `prominent-clear-glass`) is `NSToolbarItem.style = .prominent` with `backgroundTintColor` its `accent-color` (absent: the system accent); every other style, and every style in the earlier design, is the plain bordered item the toolbar makes today (a silent stand-in, as LLP 1069.011 D2's are). A custom button stays plain.

**D3. The header.** Contract admits a native button inside `header`; nothing reads `header` on Apple today. LLP 1075.003 now says its header buttons are read through D1 and a prominent style is `UIBarButtonItem.style = .prominent`; not built here.

**D4. Tabs.** Contract admits `role="tab"` on a native button (its fixed role yields) inside a `tablist`. A native tab is a tab on both platforms (`isButton`, role `tab`, `press`). Eligibility is decided per projection, separately from the face: iOS's tab bar needs a symbol and a title on every tab (a custom tab: its two child views, as today; a native tab: `pressFace.symbol` and `.title`); a segment needs a symbol alone or a title alone (a native tab with a visible title whose `aria-label` differs from it stays authored, as the custom text guard does, `Accessibility.swift:47-49`; a symbol-only native tab projects, its segment carrying its label, as a custom image segment does). `SegmentFace` gains `.symbol(name)`, drawn with `systemName`/`systemSymbolName` and carrying the label; a custom image segment keeps its view snapshot. The tab bar's selected tint: a custom tab's image `tint-color`, a native tab's `accent-color`, else the label colour. macOS has no tab bar: a symbol-and-title face stays authored there, as a custom one does. Rendering reads the kernel face each sync (D1), so a changing title and an unavailable symbol (no image, the label kept) are current on the first batch. A native tab has no context menu (`contextmenu` stays refused on native buttons). Mixed custom and native tabs project together when each qualifies.

**D5. Menus.**
- *Rows.* Unchanged eligibility: any direct child with `press` (no `isButton` filter). A row's title is D1's (`title ?? label`); a native row's symbol is its item's image (`UIAction.image`, `NSMenuItem.image`), a custom row stays text-only; `aria-checked`, `disabled`, `destructive` as today. A confirmation's action and cancel are `isButton` rows (`MenusIOS.swift:251-254`); a native action's alert tint is its `accent-color`, a custom one's its `text_color` as today. A native button nested deeper than a popover's direct child (inside a menu row) is refused: it would compile and never be shown.
- *Invokers.* A native button with `popovertarget` or `commandfor` stays refused in this version (D9). Both reviews of r2 found that a native invoker's activation — its handler (own or an ancestor's), the menu's opening, its confirmation, its keys, shortcuts and the agent — cannot be one routine without reworking how `Presenter.press` opens menus (`PresenterMac.swift:684-689`) and how the iOS deferred provider presses (`MenusIOS.swift:118-129`, `:248`); that is a follow-up, written down in `QUEUE.md`. A native button inside a menu row is a row; the invoker of that menu is a custom button.
- *Contract.* A popover adds no refusing context itself; lowering a popover's direct child sets the context "inside a menu row" for that child's descendants (`contract/lower/src/lib.rs:1014-1018`), so a native row is admitted and a native button deeper than a row is refused.
- `role` `menuitem`, `menuitemcheckbox`, `menuitemradio` are admitted on a native button (its fixed role yields).

**D6. Swipe actions.** Contract admits a native button as a named action and anywhere in a swipe row's body. iOS: the swipe table cancels a touch in a `NativeButtonIOS` (`touchesShouldCancel`, as `ScrollView` does), so a pan that starts on a native button in the body becomes the swipe or the scroll. A native action's label is D1's; its image is its symbol (`UIImage(systemName:)`, no title text), recorded in the action-image map as a snapshot is today, so discovery finds and names it; discovery (`actionView`, `SwipeActionsIOS.swift:359`) searches UIKit's rendered actions only, excluding the authored row (its body and the hidden original actions), so a native body button labelled like an action is never taken for it; its colour is its `accent-color`; with none, system blue, and for `destructive` no colour is set (UIKit's red; the custom path's override is not copied); a press is `presenter.press` as today, the action's own control hidden with the node. macOS, the web and Linux render the authored row.

**D7. Keyboard shortcuts.** Contract admits `aria-keyshortcuts` on a native button; `ShortcutsMac` admits `isButton` nodes with a `press` handler (its eligibility otherwise unchanged; with no native invokers there is no handlerless case), titles their item `label ?? title` as today, its image the native symbol, and performs a press as today.

**D8. Row reuse: controls are holes.** A row holding controls parks and is reused on iOS; its controls are not. The pool accepts kind `control` in a row's shape as the atom `control/<token>` — the token the control's `ControlKinds.kind` (`button`, `switch`, `checkbox`, `select`, `range`, the date kinds) and `file` its own, read from the view's props on park and from the create op's `type` and role on take (the pool's created-node record keeps them) — so a control's view is never taken for a custom button's (`button()`), whose `kind` a rebind cannot change. The node's control and a native glass button's slot are its own platform subviews in both of the pool's ownership checks (`NodePoolIOS.swift:181-188`). Parking a row removes its controls as a hole's content is removed, at once and in this order: the native button's glass flag cleared and `syncGlassSlot` run (the slot torn down, the control back on the node), then `ControlHost` forgets the id — `controls`, `kinds`, `reported`, `menus`, `lastRange` — and the `UIControl` is removed from its view and its action and owner detached, so no callback of the old control reaches the reused view; a take creates fresh controls for the new ids in the next `controls.sync`, so no state, tracking or callback crosses rows (`rules/DEFERRED.md:332`). A row is not retired (it is destroyed as today, `PresenterIOS.swift:748`) when any control in it is tracking (`isTracking`) or owns an open presentation: a select's menu, a date picker's calendar, a confirmation (`MenuHost.confirmation`), a file picker (`Picker`'s open set). Every control kind joins (a fresh control is always correct).

**D9. What stays refused.** On the button: `popovertarget` and `commandfor` (native invokers, D5's follow-up), `href`, `action`, `popover` (a native button is not a popover), `swipeContent`/`swipeLeading`/`swipeTrailing`/`swipeIndicator` (the row carries those), any other `role`, a `type` other than `button`, `contextmenu`. As a context: inside a `canvas`, inside a native button, deeper than a popover's direct child. Linux: with no native invokers, `popover_invoker` stops at a native button (not an invoker, whatever its ancestors), so a press on a native row inside a pressable invoker is the row's.

**D10. Tests.** Contract: each lifted place compiles; each D9 refusal holds (with the parent's face, type and style rules); roles as literals and choices. XCTests (iOS and macOS): toolbar items native and custom (prominence, tint, image, the earlier design's stand-in, press); native tabs as a tab bar and as segments, mixed with custom, a changing title, an unavailable symbol, authored fallback; native menu rows (title, symbol, symbol-only with a label); a native swipe action (label, symbol, colour, destructive red, image map); a shortcut on a native button; a row with a native button and a switch parked and taken (fresh controls, `checked` absent after present, presses to the new ids) and a tracking control blocking retirement. Real touches on the simulator (the agent's held-contact pointer, `tap … down`): a tap, a horizontal swipe and a vertical scroll starting on a native button in a swipe body, with no accidental press. Linux: keyboard activation and the agent's name under role `tab` and `menuitem`. Pool: a row parked with an open select menu, date calendar, confirmation or file picker is destroyed, not retired; a parked native glass button's slot is gone and its old action reaches nothing. The web (JS target, and the wasm oracle for its emission): a native tab and menu row. The fixture gains a toolbar, a tablist, a menu and a swipe row of native buttons; Messages' swipe actions become native.
