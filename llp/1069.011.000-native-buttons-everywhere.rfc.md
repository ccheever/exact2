## Summary

LLP 1069.011 refused a native button (`button appearance="auto"`) wherever a host reads a button some other way than as a button — a toolbar, a tab, a menu row or invoker, a swipe action, a keyboard shortcut, a `header` — and kept rows holding any control out of list reuse. Each host projection finds a button by `kind == "button"` and reads its label and glyph from its child views; a native button is kind `control` with no child views (its face is kernel data, LLP 1069.011 D5).

This RFC lifts those refusals with one change underneath: **every button has one face, computed by the kernel** — its title, symbol and label, from its children whether it is a custom button or a native one — and every host projection reads that face instead of walking views, while keeping its own eligibility rules. Custom menu rows and swipe actions gain the symbol images native ones have; a future host (Android) gets the same face. A native button can be a menu row but not, in this version, a menu's invoker (§5). Rows holding controls join iOS row reuse with their controls recreated, never carried.

## 1. What exists (at `485020542`)

## 2. Measured and checked

## 3. Design

**D1. One face, in the kernel.** `Kernel::press_face(view) -> Option<PressFace>` for a button — a `Pressable` (a custom `button`) or a native button (`ControlKind::Button`) — read live from its direct children, as `button_face` reads a native button's today (`kernel/src/control.rs:273-301`), which it replaces: `title` (its one `text` child's text, white space collapsed, a blank title none), `symbol` (its one `image` child's `symbol:` role or `sf/` name), `raster` (whether that image child is a raster instead), `leading` (the image before the title), `label` (its `accessibilityLabel`), and `fits` — whether its direct children are at most one `text` and at most one `image` and nothing else. A native button always fits (LLP 1069.011 D5's grammar); a custom one fits when its children do (a badge, a second text or a box makes it not fit). `None` for anything that is not a button. The Apple bridge's `exact_button_face` becomes `exact_press_face` (the symbol as the platform names it, the native style columns when it is native); Swift's `presenter.pressFace(id)` reads it each sync — never a control's last write, never child views.

Every projection reads the face where it read child views, and asks `isButton` (kind `button`, or a native button) where it asked `kind == "button"`; each keeps its eligibility rules, now stated on the face (`fits`, a title, a symbol), and its precedence for text — the toolbar item's label and a shortcut's title are `label ?? title` (`ToolbarMac.swift:170`, `ShortcutsMac.swift:144`), a menu row's or confirmation's visible title is `title ?? label`. A custom button whose image is a raster keeps today's image path for it (the toolbar's raster, the segment's and the swipe action's view snapshot); a symbol is a `systemName`/`systemSymbolName` image wherever a projection shows an image, for custom and native buttons alike. Button identity outside the projections uses `isButton` too: the Apple agent's accessible-name enrichment (`Accessibility.swift:211`); on Linux, focusability and Enter/Space (`surface_controls.rs:454`, `presenter/typing.rs:205-210`) and the agent's accessible name (`host/linux/src/agent.rs:444-457`, its label else the face's title).

**D2. Toolbars.** Contract admits `toolbarPlacement` on a native button and a native button inside a toolbar. iOS projects no toolbar (unchanged: the native button is itself). macOS: a native button with `press` is an item like a custom one, its label, image and title from D1, `toolbarPlacement="navigation"` as today; in the 26 design (`LinkedDesign.liquidGlass`) a prominent style (`filled`, `bordered-prominent`, `prominent-glass`, `prominent-clear-glass`) is `NSToolbarItem.style = .prominent` with `backgroundTintColor` its `accent-color` (absent: the system accent); every other style, and every style in the earlier design, is the plain bordered item the toolbar makes today (a silent stand-in, as LLP 1069.011 D2's are). A custom button stays plain.

**D3. The header.** Contract admits a native button inside `header`; nothing reads `header` on Apple today. LLP 1075.003 now says its header buttons are read through D1 and a prominent style is `UIBarButtonItem.style = .prominent`; not built here.

**D4. Tabs.** Contract admits `role="tab"` on a native button (its fixed role yields) inside a `tablist`. A native tab is a tab on both platforms (`isButton`, role `tab`, `press`). Eligibility is decided per projection, separately from the face: iOS's tab bar needs a symbol and a title on every tab (a custom tab: its two child views, as today; a native tab: the face's symbol and title; a custom tab: its face (`fits`, a symbol and a title), which is today's two-child rule stated on the face); a segment needs a symbol alone or a title alone (a native tab with a visible title whose `aria-label` differs from it stays authored, as the custom text guard does, `Accessibility.swift:47-49`; a symbol-only native tab projects, its segment carrying its label, as a custom image segment does). `SegmentFace` gains `.symbol(name)`, drawn with `systemName`/`systemSymbolName` and carrying the label; a custom image segment keeps its view snapshot. The tab bar's selected tint: a custom tab's image `tint-color`, a native tab's `accent-color`, else the label colour. macOS has no tab bar: a symbol-and-title face stays authored there, as a custom one does. Rendering reads the kernel face each sync (D1), so a changing title and an unavailable symbol (no image, the label kept) are current on the first batch. A native tab has no context menu (`contextmenu` stays refused on native buttons). Mixed custom and native tabs project together when each qualifies.

**D5. Menus.**
- *Rows.* Unchanged eligibility: any direct child with `press` (no `isButton` filter). A row's title is D1's (`title ?? label`); a row's symbol — a native row's, or a custom row's whose face has one — is its item's image (`UIAction.image`, `NSMenuItem.image`); `aria-checked`, `disabled`, `destructive` as today. A confirmation's action and cancel are `isButton` rows (`MenusIOS.swift:251-254`); a native action's alert tint is its `accent-color`, a custom one's its `text_color` as today. A native button nested deeper than a popover's direct child (inside a menu row) is refused: it would compile and never be shown.
- *Invokers.* A native button with `popovertarget` or `commandfor` stays refused in this version (D9). Both reviews of r2 found that a native invoker's activation — its handler (own or an ancestor's), the menu's opening, its confirmation, its keys, shortcuts and the agent — cannot be one routine without reworking how `Presenter.press` opens menus (`PresenterMac.swift:684-689`) and how the iOS deferred provider presses (`MenusIOS.swift:118-129`, `:248`); that is a follow-up, written down in `QUEUE.md`. A native button inside a menu row is a row; the invoker of that menu is a custom button.
- *Contract.* A popover adds no refusing context itself; lowering a popover's direct child sets the context "inside a menu row" for that child's descendants (`contract/lower/src/lib.rs:1014-1018`), so a native row is admitted and a native button deeper than a row is refused.
- `role` `menuitem`, `menuitemcheckbox`, `menuitemradio` are admitted on a native button (its fixed role yields).

**D6. Swipe actions.** Contract admits a native button as a named action and anywhere in a swipe row's body. The first consumer is Messages' inbox: each row's mute and delete actions (`apps/messages/app.contract`, `GlassButton` glass buttons today) become native buttons with their symbols and labels, so on iOS they are `UIContextualAction`s drawn from the face (a crisp symbol, not a snapshot) and elsewhere native glass buttons in the authored row. iOS: the swipe table cancels a touch in a `NativeButtonIOS` (`touchesShouldCancel`, as `ScrollView` does), so a pan that starts on a native button in the body becomes the swipe or the scroll. A native action's label is D1's; its image is its symbol (`UIImage(systemName:)`, no title text), recorded in the action-image map as a snapshot is today, so discovery finds and names it; discovery (`actionView`, `SwipeActionsIOS.swift:359`) searches UIKit's rendered actions only, excluding the authored row (its body and the hidden original actions), so a native body button labelled like an action is never taken for it; its colour is its `accent-color`; with none, system blue, and for `destructive` no colour is set (UIKit's red; the custom path's override is not copied); a press is `presenter.press` as today, the action's own control hidden with the node. macOS, the web and Linux render the authored row.

**D7. Keyboard shortcuts.** Contract admits `aria-keyshortcuts` on a native button; `ShortcutsMac` admits `isButton` nodes with a `press` handler (its eligibility otherwise unchanged; with no native invokers there is no handlerless case), titles their item `label ?? title` as today, its image the native symbol, and performs a press as today.

**D8. Row reuse: controls are holes.** (Built first: it stands alone, and D6's consumer puts native buttons in rows that reuse.) A row holding controls parks and is reused on iOS; its controls are not. The pool already reuses rows around **holes**: a heavy leaf (`video`, `iframe`, `native`, `canvas`, `canvas2d`, `input`, `textarea`; `NodePoolIOS.swift` `leaves`) is destroyed at park as any destroyed view is and built fresh at take, while the row's other views are rebound. A control joins that set: its whole node — its `NodeView`, its `UIControl`, a native glass button's slot — is destroyed at park exactly as an unpooled control is destroyed today, and the taking row's create builds a new one. So nothing of a control crosses rows: no value, no tracking, no callback, no `kind` a rebind would have to change; an open select menu, date calendar or a control under a finger behaves at park as it does today when its row is destroyed. The shape's hole is `control*` (its type does not matter: the node is new). A control's face children are not views (LLP 1069.011 D5), so the hole holds no node children, as a heavy leaf must.

**D9. What stays refused.** On the button: `popovertarget` and `commandfor` that open (native invokers, D5's follow-up; a row whose literal `popovertargetaction="hide"` or `command="close"` only closes its popover or dialog — a confirmation's action or cancel — is not an invoker and is admitted), `href`, `action`, `popover` (a native button is not a popover), `swipeContent`/`swipeLeading`/`swipeTrailing`/`swipeIndicator` (the row carries those), any other `role`, a `type` other than `button`, `contextmenu`. As a context: inside a `canvas`, inside a native button or a custom one (a projection makes one item of a custom button and would drop it), deeper than a popover's direct child. Linux: with no native invokers, `popover_invoker` stops at a native button (not an invoker, whatever its ancestors), so a press on a native row inside a pressable invoker is the row's.

**D10. Tests.** Contract: each lifted place compiles; each D9 refusal holds (with the parent's face, type and style rules); roles as literals and choices. XCTests (iOS and macOS): toolbar items native and custom (prominence, tint, image, the earlier design's stand-in, press); native tabs as a tab bar and as segments, mixed with custom, a changing title, an unavailable symbol, authored fallback; native menu rows (title, symbol, symbol-only with a label); a native swipe action (label, symbol, colour, destructive red, image map); a shortcut on a native button; a row with a native button and a switch parked and taken (fresh controls, `checked` absent after present, presses to the new ids) and a tracking control blocking retirement. Real touches on the simulator (the agent's held-contact pointer, `tap … down`): a tap, a horizontal swipe and a vertical scroll starting on a native button in a swipe body, with no accidental press. Linux: keyboard activation and the agent's name under role `tab` and `menuitem`. Pool: a row parked with an open select menu, date calendar, confirmation or file picker is destroyed, not retired; a parked native glass button's slot is gone and its old action reaches nothing. The web (JS target, and the wasm oracle for its emission): a native tab and menu row. The fixture gains a toolbar, a tablist, a menu and a swipe row of native buttons; Messages' swipe actions become native.

## 8. Revision r4 (2026-10-02)

Charlie asked what this work gets and whether it is the ideal end state. The face reader of r2–r3 (`pressFace` in Swift, child views for a custom button and kernel data for a native one) was the place both review rounds kept finding inconsistencies, because it kept two sources of truth. r4 moves the face into the kernel for every button (D1): one definition, read the same way by every projection and every host, with custom buttons gaining what native ones have (symbol images in menus and swipe actions). Row reuse (D8) is built first, as it stands alone; Messages' swipe actions are the first consumer (D6). Native invokers stay the follow-up (D5), and the glass morph is parked (LLP 1053.000.000.001).
