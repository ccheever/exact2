## 2. Decisions

### D1. A production build ships the SVG module when an `.svg` image needs it

`svg_islands(plan)` (`runner/src/uses.rs`) finds masks written in Contract but not inside the
`.svg` files an `image` loads, so the receipt omits `libexact_svg.dylib` and those images draw
blank in release builds only. The fix is in the bake: scan the app's bundled `.svg` assets for
the features the island renders (`<mask>`, and whatever else `decodeSVG` sends to the module),
and list the module when any has them.

A development build already carries it, so the test is a release build. `smoke.mjs` or an app
under `apps/` gets a masked SVG image, and the release drive checks its pixels.

- **Moves:** closeness and bugs in any app with vector logos.
- **Second consumer:** Shelf's or Bluesky's icons (any masked SVG asset).

### D2. Host builds stop producing proc-macro dylibs that macOS 27.0.1 refuses

`HOST_MACOS = '14.0'` (`scripts/filesystem.mjs`) reaches every host cargo run an app outside
the repo makes. With ld-27037.1, any deployment target of 12.0 or later yields proc-macro dylibs
that dyld refuses ("mis-aligned LINKEDIT string pool"); 11.0 loads. 12.0 is where ld turns on
chained fixups by default.

The fix keeps 14.0 for what links into the app and passes `-C link-arg=-Wl,-no_fixup_chains`
to proc-macro and build-script builds. If that does not cure it, host-only builds go to 11.0.
The script's comment says why, with the linker's version, so the workaround can go when Apple
fixes ld.

- **Moves:** wall clock and tokens for every builder outside the repo (6 to 15 minutes each in
  the pilot).
- **Priority:** first.

### D3. An unpainted sheet at a partial detent is the platform's glass; `transparent` is honoured

LLP 1116.021 D7 paints a route with no background of its own `.systemBackground` to keep a
white band from showing at full height. On iOS 26 a sheet at a partial detent is glass: SwiftUI's
`.sheet` and React Native's form sheet draw it, and both originals and one SwiftUI port showed
it.

The decision:
- a modal route with no paint at a partial detent leaves the controller's view clear, so UIKit
  draws its glass;
- at the full (`large`) detent, D7's system background stays;
- an author's `background-color="transparent"` is the author's, at any detent, so it is never
  replaced.

Grouped sheets keep D7's grouped background. LLP 1115's test is a hand-built SwiftUI sheet at
`.medium` on iOS 27, side by side.

### D4. The scroll-edge band under a bar holds for a scroller with `refresh=`

On React Conf's Calendar and Hackers' feed, content ran sharp under the bar's title while the
same app's Info tab had the band. Both scrollers carried `refresh=` (pull to refresh); React
Conf's also had a sticky column.

A lane first reproduces it with the three variants (plain, `refresh=`, `sticky`) on a large-title
route. It then fixes what the repro names; the suspect is the refresh control's scroller not
being the one `setContentScrollView` was handed. The repro becomes a test in the iOS XCTests.

### D5. Custom list rows are not hyphenated

`contract/lower/src/grouped.rs` adds `hyphens: auto` to every row it lowers, on the basis that
`UIListContentConfiguration` hyphenates. That holds for the stock cell's text roles only. A custom
cell's `UILabel` and SwiftUI's `Text` do not hyphenate, and Hackers' grader named it the first
tell.

The rule becomes: the row text roles Exact draws as the stock cell's (title, subtitle, value)
keep `hyphens: auto`, and an author's own content in a row takes CSS's `manual`.

- **Amends:** LLP 1116.021 D7's grader note, which excused hyphenation in list cells; it now
  covers stock cells only.

### D6. `autofocus` reaches a header's search field

The iOS autofocus pass skips a header's authored nodes, which are hidden; the editor is the
projected `headerField`. `38a4743782` routed `focus()`, `blur()` and Tab there; autofocus takes
the same route. Test: a pushed route with `input type="search" autofocus=true` in its header is
first responder once the push settles.

### D7. A modal route's level-1 heading is a large title

LLP 1116.020 D2 made a sheet's title inline, which is the platform's default for a sheet. An
author who writes `role="heading" aria-level=1` on a modal route has asked for a large title.
Settings sheets in SwiftUI apps commonly have one, the Hackers original's among them. Author
over platform: the explicit level wins, and an unsaid level keeps D2.

### D8. iOS 26 search placements get their own RFC

All three Exact builds lacked the search tab, a tab that becomes the search field at the bottom
on iOS 26. Two builders tried and stopped. Hackers' search is iOS 26's minimized toolbar search,
a button at the bottom that expands in place. Exact has neither, and the header search it has is
hidden until the list is pulled down.

These are structure, not looks, so LLP 1115 wants the author to say "this tab is search" and
the platform to place it. A sub-LLP (1141.002) decides the Contract words (a candidate:
`role="search"` on one tab of a `tablist`, as the original's `NativeTabs.Trigger role="search"`
says), their presentation on each host (`UISearchTab` on iOS 26, a search field elsewhere), the
minimized toolbar search on a route, and `hidesSearchBarWhenScrolling` for a root route's
header search.

### D9. Images in the bar, and a title that is a menu, get their own RFC

React Conf's header mark (an image, stacked text) became a one-line wordmark in a capsule,
because a bar item draws only dots, symbols and text and drops an image silently. Hackers' feed
title is a menu in the original (SwiftUI's `ToolbarTitleMenu`), and Exact's title can only run a
press.

A sub-LLP (1141.003) decides:
- an image in a bar item;
- a custom title view (its content and how it collapses with a large title);
- a title menu: `popovertarget` on the heading presents UIKit's title menu.

Until then the compiler warns when a bar item's image is dropped, instead of dropping it silently.

### D10. A data module can yield: `scheduler.yield()`

Each data-module turn has 100 ms (`js/src/lib.rs`, `DEFAULT_BUDGET_MS`), and the only way to
yield is an await on I/O. A TypeScript module that parses a large response (Hackers' 963 KB
thread) fails as `Unavailable` only on large inputs, so its tests pass.

The web's answer is `scheduler.yield()` ([Prioritized Task Scheduling](https://wicg.github.io/scheduling-apis/#dom-scheduler-yield)):
an `await` that ends the turn and resumes in a new one. A data module gets that name, and each
resume starts a fresh budget. The budget stays; a turn that never yields still fails, with a
message that names `scheduler.yield()`. The docs' section on large responses shows a parse loop
that yields every few thousand nodes.

### D11. Docs and messages

- **Glass for floating buttons.** The compiler message at `contract/lower/src/controls.rs`
  (~986, "takes no `color`; write a custom `button`") points to `buttonStyle="glass"` and
  `-exact-tint-color` for a floating control's look. `contract-for-agents.md` shows glass for an
  in-page floating button, not only for bar buttons. Both apps' builders drew grey or pale
  buttons where the original floats glass.
- **React Native's font sizes.** The React Native porting pitfall says a unitless `fontSize`
  scales with Dynamic Type there, so it becomes `rem` (or a text style) here.
- **A list's loading state.** The loading recipe shows a native list's loading state: the
  refresh control, or a centred `progress` over an empty list, never a row.

### D12. Reproduce before deciding

Each of these gets a `QUEUE.md` entry with its repro, and a decision once it reproduces:

- **Pinning a control under a large title.** React Conf's sticky day picker scrolled away with
  both builders, though `Sticky.swift`'s arithmetic says the workaround should pin. LLP 1131 gives
  a large-title route no band for a fixed control, so this may also be a gap.
- **A Day 2 tap that did not take** in GPT's React Conf Exact build, in light and dark.
- **The device's zone printed as "GMT (Local)"** where SwiftUI prints "GMT-07:00 (Local)": the
  Intl long name or the device zone on Apple hosts.
- **Hackers' long-press menu missing at the largest size** with the keyboard up.
- **Hackers' Exact build spinning a full core at rest in 1 of 10 launches.** Reproduced and
  fixed under D13: the native list laid itself out again on every turn.

### D13. A list row costs what a hand-built cell costs in layers

Hackers' Exact feed holds six times the layers of the SwiftUI and original feeds (1,550 against
250 and 241) for the same rows. A lane measures where they come from: a row's views per node,
images, separators, the swipe container the port used for its leading swipe. It compares a
row's layer count with a hand-built `UICollectionViewListCell` showing the same content. The
reduction lands where it applies to every list (LLP 1068's recycling and the flat-box layer
tree of 2026-10-18 are the starting points). The bench measures it again in the replay.

**As measured (2026-10-23).** A fixture of Hackers' compact `PostRow` (a 55-point thumbnail over
a symbol, a meta line of three texts and two symbols, the title, a long-press menu and a
leading swipe) in a `list appearance="auto" listStyle="plain"`, on an iPhone 17 simulator under
iOS 27.0, its layers counted as the bench counts them (every layer under the windows). A
hand-built `UICollectionViewListCell` of the same content is 15 layers with a subview each, or
7 with `UIListContentConfiguration`. Exact's row was 33:

| A row's layers | Exact | Hand-built |
|---|---|---|
| The cell, its background and content view | 4 | 4 |
| Boxes: the swipe scroll, the row, the thumbnail's button, the column, the meta line | 5 | 3 (the row view, the thumbnail's box, a stack) |
| Four texts | 12: a view, its ink view and the ink | 4 labels |
| Three symbols | 6: a view and its image view | 3 image views |
| The thumbnail | 3: a view, a clip layer and the bitmap | 1 image view |
| The leading swipe's Upvote button, hidden | 3 | 0 (UIKit builds it on the swipe) |

The screen is another matter. Of Hackers' 1,562 layers at rest (its production build, the same
simulator), 1,168 are hidden: 1,005 are the 47 rows below the screen, which a grouped list builds
whole and keeps in its hidden sections (LLP 1084 D1), 91 are rows left in three cells UIKit keeps
for reuse, and the rest are hidden swipe buttons, menus and dialogs. The 394 shown are the bars
and ten rows of about 33. The fixture at 60 rows has 1,575 layers, 1,180 of them in the hidden rows, and 5.9 MB
more footprint than at 12 rows (38.60 MB against 32.68).

Built:
- **A one-colour paragraph's ink is one layer.** Its colour is masked by its coverage on the
  ink's own layer, where it was a layer inside it. A paragraph with a `text-shadow` is never
  tinted, so the mask clips no shadow. A row: 33 → 29 layers; the fixture's screen, 481 → 439;
  footprint 32.92 → 32.68 MB (medians of eight interleaved launches); pixels unchanged in light
  and dark.
- **A long grouped list of custom rows comes to rest.** A cell UIKit gave to another row took
  that row's height, and the list counted that as a resize: it invalidated its layout, UIKit
  handed two cells at the bottom edge between rows of two heights again, and so on every turn.
  The list now compares a row's height with its own last. The fixture at 60 rows spent 10.1 s
  of CPU in 10 s at rest and never came to rest; now it spends none and comes to rest 1,977 ms
  after launch (median of eight). Hackers' build spun in both of two launches here. This is D12's spinning
  core.

Left, each a design change:
- **The rows off the screen** (two thirds of Hackers' layers). A grouped list would build a
  custom row's views only near its cell, or a feed would be a virtualized collection drawn as
  UIKit cells. Either amends LLP 1084 D1, which keeps every row built, "as a settings screen
  does", and leaves a long feed to a collection, whose rows are not UIKit cells. Hackers' feed
  is a grouped list.
- **Swipe actions built at rest.** The action buttons are views from the start and hidden while
  UIKit draws the swipe; they could be built when a swipe projects them.
- **A view per node.** A text, a symbol or a raster image is a `NodeView` holding what draws
  it, where a hand-built cell has only the label or image view; a box holding views is a view.
  LLP 1068 §6.3's flat boxes take only boxes holding boxes. The thumbnail's clip layer is
  c4200064b8's, for UIKit's resize animations.

## 4. The bench this round

Cold start could not be measured. Bones, the quiet Mac LLP 1141 §5 names, had another user's
iPad and "iPhone Duo" simulators booted, with load averages between 3 and 130 during the run.
Only 6 of 20 interleaved rounds ran at a load under 4.

Measured from the `simctl launch` request, the three React Conf builds' first frames were all
1.6–1.9 s. On 2026-10-08 euxy's SwiftUI build reached its first frame in 285 ms on the same
machine under iOS 18.6, so the floor is the machine and the runtime, not the apps.

Hackers' bench later ran on a quiet bones: all 60 launches at a load under 4. Every build still
waited until about 1.5 s before its first frame, so the floor is the iOS 27.0 simulator on this
machine, not the load. Inside it, the Exact build drew first (1492 ms against SwiftUI's 1571) but
reached rest about 140 ms after SwiftUI (1922 against 1779). It drew the same feed screen with
1,550 layers against SwiftUI's 250 and the original's 241. That is the same class of cost as
euxy's 401 layers at launch (LLP 1141 §1), and it becomes D13.

Cold start needs a device, or a simulator runtime without this floor, before a launch bar can
be judged; until then the plan reports launch milestones but does not pass or fail on them.

## 5. A question for Charlie: authored point sizes and Dynamic Type

LLP 1115.000 D12.1 ruled that an authored absolute `font-size` is the author's number on every
host, with `rem` and text styles following Dynamic Type. Both React Conf Exact builds wrote point
sizes, though `verify` listed every one ("45 font sizes the reader's text size does not move"),
because the original's React Native `fontSize` values look like points. In React Native those
values scale with Dynamic Type by default, and so do SwiftUI's `.custom(_:size:)` fonts. So both
graders saw the Exact build's text stay small at the accessibility sizes while the original's and
SwiftUI's grew. Bake-off round 18 recorded the same thing (LLP 1116.020: fixed sizes, 7 to 6).

The options:

1. **Keep D12.1, and make `verify` stop the build** on a fixed size in body text, instead of
   listing it.
2. **On iOS, scale an authored point size by Dynamic Type relative to body,** as SwiftUI's
   `.custom(_:size:)` and React Native do. An author who means a fixed size says so (for
   example, a `-exact-text-scale: none` declaration, name to be settled). The web keeps CSS's
   pixels.

The author recommends option 2. It is what both of the other stacks a builder knows do, and
someone who knows iOS notices fixed text at the accessibility sizes, which is LLP 1115's test.
It reverses part of a ruling of Charlie's, so it waits for him.
