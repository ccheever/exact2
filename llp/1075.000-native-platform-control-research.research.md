## 1. Scope and confidence

This records research for James's request for native API access without repeated
Exact patches. The parent preserves his statements, the supplied navigation-bar
patch, and the later tab-controller request. Recommendations are in the sibling
RFC so another author can use or challenge these findings independently.

Sources were inspected on 2026-10-01. Local observations refer to the working
checkout whose HEAD was `f2c0fe260016f6aecfc2daf5ff3c384af2135dab`, not a claim
about the latest upstream branch. The checkout contained unrelated staged and
unstaged app work. The relevant native infrastructure was read, not rebuilt.

Evidence levels used below:

- **Source observation:** visible in the named local implementation.
- **Upstream documentation:** a project's documented capability, not an Exact
  integration result. External links are living pages, not pinned benchmarks.
- **Inference:** the architectural consequence or estimated maintenance trade.

No NativeScript embedding, Rust UIKit app, new extension hook, or reproduction
of James's app was run. No runtime cost, binary size, SDK-completeness, or
performance ranking has been measured by this research. Existing LLP receipts
retain their own dates and scopes; they are not new verification here.

## 2. Findings in Exact

### F1 — Existing objects are the missing access point

[NavigationIOS.swift](../host/apple/Sources/ExactKit/IOS/NavigationIOS.swift)
defines a private `RouteController` and an internal `NavigationHost`. Exact
constructs the navigation controllers, hides their bars, assigns its own
navigation and gesture delegates, and keeps route-controller mappings. This
explains why an app cannot accomplish James's supplied patch merely by creating
its own `UINavigationItem` or calling an unrelated native module.

The patch crosses the kernel schema, Contract lowering, and UIKit presenter for
five settings. That is a concrete example of a maintenance cost that grows with
each newly requested platform property. Whether all five deserve convenient
portable authoring is a separate product choice from providing general access.

**Inference:** language bindings and access to Exact-owned objects are separate
requirements. A complete bridge does not supply object discovery, mutation
precedence, containment, or a supported controller factory by itself.

### F2 — Swift modules already provide native views and calls

[ExactNativeModule.swift](../host/apple/modules/ExactNativeModule.swift) provides
`ExactModule`, `ExactNativeFactory`, and `ExactNativeInstance`. A module offers
view factories, `call`, `later`, and teardown. Its views and operations share
one module instance per session. Calls and replies carry JSON-compatible
values; view properties are string values; the module view is a `UIView` on iOS.
The view API is not a controller-containment API.

[LLP 1067.000](1067.000-one-native-module-or-two.rfc.md) describes main-thread
entry to the Swift module, synchronous `native.call` for cheap queries within
the asking answer's 100 ms budget, and asynchronous `native.later` for work.
The artifact loads after first pixel, before data activation. The web module
has an asynchronous path, not equivalent synchronous object access.

**Inference:** this is a useful home for app-specific Swift behavior and native
components. Its JSON seam cannot directly represent live UIKit object identity,
JS function callbacks, or arbitrary Objective-C protocol implementations. It
also does not currently expose the navigation objects identified in F1.

### F3 — Exact can already be embedded in a UIKit app

[ExactViewIOS.swift](../host/apple/Sources/ExactKit/IOS/ExactViewIOS.swift)
implements public `ExactView: UIView`, containing a session's presenter.
[Session.swift](../host/apple/Sources/ExactKit/Session.swift) provides session
creation and a delegate for post-commit commands and state changes.
[LLP 1031 D3/D5](1031-brownfield-embedding.rfc.md) gives the containing app its
own geometry and controller hierarchy; Exact's internal navigation controllers
are children within its surface.

Two boundaries matter. An `ExactView` represents a session viewport, not an
existing public API for mounting arbitrary Contract subtrees in arbitrary
controllers. Two sessions have separate runtime state; sharing the plan or the
module artifact does not create a shared live application object graph.

**Inference:** a native tab/navigation shell with embedded Exact surfaces has a
foundation. General composition of controllers inside one Exact session and
communication among several sessions still require a deliberate design.

### F4 — Retained route stacks do not establish retained tab UI

[route/src/lib.rs](../route/src/lib.rs) defines `Router { tab, tabs, next }` and
`Tab { name, stack }`. [route/src/router.rs](../route/src/router.rs) selects a
retained tab and pops to its root when the already selected tab is selected
again. Those are source facts about navigation values.

They do not prove preservation of a native controller, a Contract component's
local state, text selection, scroll offset, or an in-flight operation when the
app changes its selected view. Nor does retaining a `UITabBarController` alone
make destroyed Exact state survive. The missing reproduction must distinguish
route-value retention, component/session retention, native-view retention, and
persistence across process restarts.

### F5 — Synchronous callbacks are an architectural integration point

[Owner.swift](../host/apple/Sources/ExactKit/Owner.swift) owns the Apple runtimes
on `exact.owner`. Main submits runtime work; the owner can request work on main
through `callMain`. While main is servicing such a request, a synchronous call
back into the runtime is refused. Notifications can be deferred instead.
[NativeModule.swift](../host/apple/Sources/ExactKit/NativeModule.swift) routes
synchronous app-module calls through that mechanism. This newer implementation
must be read alongside older descriptions of main-placed data sources.

The [JS shim](../js/src/shim.cc) hosts a bytecode-only Hermes runtime through JSI.
Its existence supplies a possible interop attachment point; it does not supply
an unrestricted UI-thread JS callback model.

**Inference:** a JS call that invokes UIKit, which immediately calls a delegate
implemented in that JS runtime, cannot simply be inserted into the present
one-way callback service. Swift delegates can answer locally and defer state
notifications. General JS delegates need an explicit ownership/re-entry design.

### F6 — The large-title mechanism was prototyped and stopped *(Claude)*

**Source observation (LLP record):**
[LLP 1035.001 D9](1035.001-native-interaction-ownership.rfc.md) measured a UIKit
large-title table: an 80-point drag moves it about 62 points while its top inset
goes 168 → 116. It also found that the scroll-edge effect appears only under a
real bar with a native label.

D9's prototypes (2026-09-10) attached the route's scroll view as the bar's
content scroll view, as the supplied patch does. Three implementation rounds
stopped on scroll coordinates:

- With a 106-point header, after UIKit's inset changed, a requested `scrollTop`
  of 80 became 132 and a requested 0 became −52.
- Header heights of 74 and 148 also failed.
- The browser reported 0 and 80 for the same Contract.

D9 concluded that it "still needs a single mapping for native available area,
content origin, changing insets and authored assignments/events." Charlie then
ruled "no `title` prop now".

**Source observation (patch):** `configure` sets the first descendant
`UIScrollView`'s `contentInsetAdjustmentBehavior` to `.automatic` and calls
`setContentScrollView(_:for: .top)`. Nothing in the patch maps the adjusted
inset into Exact's scroll values.

**Inference:** unless code outside the patch does that mapping, Contract under a
titled route will read or write scroll positions shifted by the bar's inset.
That covers assignments, `scroll-into-view`, scroll events and
`scrollFollowEnd`. This has not been run. A constant inset (an inline title that
never collapses) is a fixed shift. That is far easier to map than the changing
inset of a collapsing large title.

### F7 — Bar visibility behaves as a property of the stack *(Claude)*

**Source observation:** the patch's `showBar` runs in `willShow` at each
transition. It hides the bar for a route without `navigationTitle` and shows it
for one with a title.

[LLP 1037 F1](1037-dartnative-lessons.research.md) records DartNative's
2026-09-08 iOS 26 fixes:

- one system bar for the whole stack;
- "The bar is no longer hidden after a pop, so the blur is continuous";
- taps in the bar region pass through after navigation.

It proposes an invariant for Exact: the stack owns one visible system bar for its
whole life, and a route fills it or leaves it empty.

**Inference:** on a stack that mixes titled and untitled routes, the patch
reintroduces the toggle that invariant removes. A stack whose routes all have
titles never toggles.

### F8 — Unselected tabs drop their rows by design; today's tab bar is a view *(Claude)*

**Source observation:**

- [LLP 1038 §7](1038-router.rfc.md) defers "Retained *views* for unselected
  tabs (their entries are retained, their rows are not)" and names its fix: "It
  needs one navigation owner per tab in the Apple projection."
- Apps render the selected stack (`each e in stack(nav)`,
  `apps/realworld/app.contract:276`).
- [LLP 1059](1059-tab-bar-projection.rfc.md) projects a symbol-over-label
  `tablist` to a `UITabBar` inside the tablist's own box. Layout stays authored
  (D2), and the bar's height reaches layout through the intrinsic-size seam
  (D2a).

**Upstream documentation:** iOS 26's floating tab bar is controlled through
controller properties:

- `UITabBarController.tabBarMinimizeBehavior` (for example `.onScrollDown`)
  shrinks it on scroll.
- `bottomAccessory`, a `UITabAccessory`, places a view such as a mini player
  above the bar.

[WWDC25 “Build a UIKit app with the new design”](https://developer.apple.com/videos/play/wwdc2025/284/).

**Inference:** a `UITabBar` in an authored box gets neither behavior. Both
retained per-tab UI and these features point to a container, the "one
navigation owner per tab" LLP 1038 named.

### F9 — No app vocabulary; one aggregate exists for module tags *(Claude)*

**Source observation:**

- [tags.rs](../contract/lower/src/tags.rs) maps each attribute through a fixed
  table (`attr()`), and nothing under `contract/lower/src` lowers `data-*`.
- A module tag's leftover attributes lower to one binding of `nativeViewProps`
  through the `NativeProps(n)` opcode (LLP 1024 §9). Its one implementation is
  `exact_runner::stdlib::native_props`: keys sorted, values carried as strings.
- The supplied patch's rows take ids 216–220. The highest prop id on `origin/main`
  at `54ae031df` is 215.

**Inference:** one schema row per attribute is where app patches collide on
upgrade. An aggregate like `NativeProps` is the existing mechanism that needs no
row per word.

### F10 — The sample host already drives a native shell around Exact *(Claude)*

**Source observation:**
[ExactHostIOS/main.swift](../host/apple/Sources/ExactHostIOS/main.swift) puts each
pane's `ExactView` under its own `UINavigationController`. On a command it pushes
a native `NativeScreen` over a pane (`push(over:)`), then pops it and remounts the
pane (`pop(_:)`). `bun scripts/smoke.mjs host-ios` drives that host. LLP 1031
D10's fixture list includes "handles an Exact command by pushing a native screen
and returns with both sessions intact." This was not run for this research.

**Inference:** the UIKit-first arrangement James describes (native shell, Exact
screens) is exercised today. It is not documented as an adoption path, and the
per-session cost of one surface per screen is not stated anywhere read here.

## 3. External mechanisms

### E1 — NativeScript's metadata and object bridge

NativeScript generates metadata at build time from platform SDKs and included
libraries. It uses that metadata to expose native entities to JavaScript; APIs
absent from the metadata are unavailable. Metadata filtering can reduce what is
shipped, with a corresponding limit on accessible APIs.
[Source: NativeScript metadata](https://docs.nativescript.org/guide/metadata).

Its iOS marshalling documentation describes wrappers around Objective-C objects
that preserve object identity, property and method access, struct conversion,
and functions used as Objective-C blocks. A separate guide documents native
subclassing and protocol conformance. This reaches substantially beyond a
serialized request/reply interface.
[Object marshalling](https://docs.nativescript.org/guide/ios-marshalling);
[subclasses and protocols](https://docs.nativescript.org/guide/extending-classes-and-conforming-to-protocols-ios).

There are two relevant runtime repositories: the established
[`NativeScript/ios`](https://github.com/NativeScript/ios) describes its V8-based
iOS runtime, while the newer
[`NativeScript/napi-ios`](https://github.com/NativeScript/napi-ios) describes an
engine-independent Node-API architecture and explicitly lists Hermes, V8,
QuickJS, and JavaScriptCore. Its README identifies a Clang metadata generator,
a native FFI runtime, and JSI/React Native integration work.

**Inference:** reuse of the interop layer is worth evaluating without adopting
NativeScript's UI framework or assuming Exact must switch to V8. The README is
not proof that it can attach to Exact's existing Hermes instance, use our pinned
Hermes build and bytecode restrictions, or preserve our runtime/thread model.
Those are experiments, not established compatibility. Node-API also must not
be confused with a requirement to ship the Node.js runtime; build-tool
requirements are a separate integration cost.

NativeScript's Swift guide exposes Swift members with `@objc` or `@objcMembers`.
That is not automatic access to every Swift-only type or API. An app-specific
Swift wrapper remains relevant for unsupported signatures and Swift-only
facilities. [Swift integration](https://docs.nativescript.org/guide/native-code/ios).

### E2 — UIKit from Rust through objc2

[`objc2-ui-kit`](https://docs.rs/objc2-ui-kit/latest/objc2_ui_kit/) already offers
broad UIKit bindings. [`objc2`](https://docs.rs/objc2/latest/aarch64-apple-ios-macabi/objc2/index.html)
documents SDK-generated framework bindings and notes that newer APIs depend on
the SDK version used to generate them. Its
[`define_class!`](https://docs.rs/objc2/latest/objc2/macro.define_class.html)
macro supports Objective-C subclasses and protocol implementations. This is an
existing foundation rather than a reason to maintain a hand-written UIKit
mirror inside Exact.

Rust calls still need correct ownership, thread affinity, availability checks,
and safe handling of native signatures. Generated coverage is not identical to
all APIs in the developer's newest Xcode. Swift-only APIs can still require a
Swift adapter. **Inference:** useful for developers choosing Rust or for an
implementation layer; it does not itself expose objects to TypeScript or solve
F1's controller ownership.

### E3 — Direct Swift and native containment

Swift app code can call the APIs available to its SDK without a separate Exact
binding for each one. An extension could receive actual UIKit objects, or supply
a controller whose implementation stays in Swift. The remaining framework work
is the extension boundary described in F1–F3.

Apple documents UIKit's main-thread requirement and the parent/child controller
operations needed for containment. A controller's view alone is not its full
lifecycle. `UITabBarController` accepts custom and navigation controllers as tab
roots. These are concrete platform mechanisms for native-owned composition.
[UIKit threading](https://developer.apple.com/documentation/uikit);
[controller containment](https://developer.apple.com/documentation/uikit/creating-a-custom-container-view-controller);
[tab controllers](https://developer.apple.com/documentation/uikit/uitabbarcontroller).

For James's first example, Apple documents navigation-bar customization through
`UINavigationItem`, bar buttons, and large-title settings, with scrolling
participating in title collapse. That supports the choice of objects in the
patch, but does not validate Exact's descendant-search heuristic or inset
behavior. [Navigation-bar examples](https://developer.apple.com/documentation/uikit/customizing-your-app-s-navigation-bar).

### E4 — Generated selective bindings

An alternative is to generate TypeScript declarations and native call adapters
from selected SDK declarations or an app's explicitly exported Swift/Objective-C
API. A narrow app API is easier to generate, but asks the developer to write a
wrapper for each new operation. SDK-wide generation removes more wrapper work
but inherits substantially more language-interop responsibility.

**Inference:** static adapters may give more control over linked code and type
checking than a broad runtime metadata bridge. No size or speed advantage has
been measured here. Blocks, object identity, return ownership, optional protocol
methods, subclasses, nullability, and availability remain real implementation
work. Generating declarations alone does not generate correct interop behavior.

### E5 — Generic setters and patching

A native property bag or string-based selector call could cover simple settings.
It does not by itself cover correctly typed struct arguments, callbacks,
controller construction, containment, or ownership. It also makes mistakes and
unsupported operations harder to diagnose than typed native code. This is an
inference about the design, not a tested Exact API.

Maintaining app-specific patches remains technically possible and was James's
starting point. It exposes all framework internals but leaves update conflicts
with the app author. Better patch tooling changes that cost, not the absence of
a public extension contract.

### E6 — React Native's native stack and Expo Router's native tabs *(Claude)*

**Upstream documentation:** React Navigation's native stack offers large titles
as a screen option, `headerLargeTitle`. For the title to collapse, the screen's
content must be a scroll view with `contentInsetAdjustmentBehavior="automatic"`.
[Native Stack Navigator](https://reactnavigation.org/docs/native-stack-navigator/).

Expo Router's native tabs use the system tab bar, which is `UITabBarController`
on iOS. "All tab screens in native tabs render eagerly when the navigator mounts",
so inactive tabs keep their state. The web has "no standard system tab bar"; it
gets "a basic implementation, loosely based on iPad design", and the docs suggest
headless tabs in platform-specific `.web.tsx` files for a custom web layout.

The listed limitations include "Cannot measure the tab bar height", "No support
for nested native tabs" and "No support for dynamically adding or removing tabs".
Native tabs arrived in SDK 54 as `unstable-native-tabs` and became stable in
SDK 58. [Native tabs](https://docs.expo.dev/router/advanced/native-tabs/).

**Inference:** James's own ecosystem made both of his cases framework features
with platform containers, not escape hatches. The web side of tabs is the part
it left basic. React Native's `ScrollView` reports UIKit's content offset, so it
never has to reconcile a changing inset with a CSS `scrollTop` (F6). Exact does.

### E7 — Reaching into framework-owned objects needs a version contract *(Claude)*

**Upstream documentation:** SwiftUI Introspect finds the UIKit or AppKit object
behind a SwiftUI view by walking the hierarchy between marker views. It requires
explicit opt-in for each OS version, because underlying UIKit/AppKit types can
change between major versions. On a version not listed, the customization closure
is not called.
[swiftui-introspect](https://github.com/siteline/swiftui-introspect).

**Inference:** reaching into objects a framework creates works when someone names
those objects and the versions they hold for. Without that, any OS or framework
release can silently change what is found. The patch's search for the first
descendant `UIScrollView` is the same technique without the version gate.

### E8 — Synchronous native interop has meant running on the main thread *(Claude)*

**Upstream documentation:** Flutter merged its UI and platform threads by default
on iOS and Android in 3.29, and on macOS and Windows in 3.35, so Dart can call
native APIs synchronously through FFI.
[Merged threads](https://docs.flutter.dev/release/breaking-changes/macos-windows-merged-threads).
DartNative runs all Dart on the main thread for the same reason
([LLP 1037 §2](1037-dartnative-lessons.research.md)).

**Inference:** in each precedent, synchronous UIKit access from a language
runtime meant running that runtime on the main thread. Exact's runtimes live on
`exact.owner` (F5). A synchronous bridge needs one of two things: the calling
code runs on main, or F5's re-entry design.

## 4. Comparative assessment

These are architectural judgments, not measured rankings. The first two rows
can be combined with any language bridge.

| Approach | Reach | Main cost or unresolved boundary |
|---|---|---|
| Public Swift hooks into Exact-owned objects | Native customization using Apple's API names | Hook lifetime, stable object discovery, mutation precedence, and supported delegate composition. |
| Native containers hosting Exact content | Controller choice and native presentation ownership | Content/session boundary, layout and state retention, and one routing authority. |
| NativeScript interop | Broad direct JS/TS access to represented native APIs | Exact/Hermes integration, synchronous callbacks, GC/native ownership, reload, and optional weight. |
| objc2 | Broad native access from Rust | Rust authoring cost, SDK gaps, and a separate TS bridge if desired. |
| Selective generated bridge | Chosen APIs with generated signatures | Generator maintenance and the point where unsupported signatures require wrappers. |
| One Exact property per native feature | Convenient explicit controls | Framework changes and review for every new capability; James's current problem. |
| Generic untyped access or patches | Quick access to particular internals | Weak lifecycle/API guarantees and recurring app maintenance. |

## 5. Cross-cutting questions

- **Web:** share application semantics where they fit; choose native versus DOM
  presentation deliberately. A UIKit hook does not automatically have a browser
  equivalent. Retained tab state and browser history need behavior of their own.
- **Layout:** give the parent the outer box and its child the interior layout.
  Do not let UIKit and Exact independently write the same frames or insets.
- **Callbacks:** distinguish an immediate native decision from a later Exact
  action. Test a delegate returning a value, not only a fire-and-forget event.
- **Reload:** determine which native objects survive, what invalidates JS handles,
  how callbacks from retired runtimes are dropped, and when teardown happens.
- **Build and boot:** distinguish a small existing Swift extension from loading a
  new engine or metadata artifact. Preserve the no-app-JS-before-first-pixel rule
  unless an explicit product decision changes it.
- **Delivery:** native adapter changes and newly included metadata may require a
  new binary. Do not promise arbitrary newly introduced APIs through a code-only
  update when their bridge or availability information was never shipped.
- **Compatibility:** the present pre-1.0 policy offers no public API stability.
  James asks for a supported boundary; its exact commitment is a product decision.

## 6. What would turn this research into evidence

Reproduce James's app behavior and record the revision and platform first. Then
prove the large-title route and a tab switch with separate history, scroll, and
editor state. Include a custom child controller, cancelled back gesture,
remount, and a programmatic update while a tab is inactive. Separate same-tab
reselection policy from accidental state loss.

For a JS bridge, add one struct-valued call, one callback block, one synchronous
protocol result, a retained native object across an ordinary update, and teardown
or reload with a callback outstanding. Measure build, startup, binary, memory,
and interaction costs on actual Exact integration; an upstream benchmark is
not that evidence. The proof must use the real app paths and existing tools.

*(Claude)* Exact's own records give ready-made acceptance.

- **Navigation bar, from D9's fixtures (F6):**
  - Request `scrollTop` 0 and 80 under a titled route at header heights 74, 106
    and 148, and compare with the browser.
  - Short and overflowing lists.
  - Collapse, pull-to-top, and a held then cancelled sheet drag.
- **Navigation bar, from LLP 1037 F1 (F7):**
  - A pop from an untitled route to a large-title route and the reverse,
    checking scroll-edge blur continuity frame by frame.
  - Back identity across push and pop.
  - Taps in the bar region after navigation.
- **Tabs:**
  - A scroll offset, an editor draft and a pushed screen survive a switch away
    and back, on iOS and the web.
  - Reselecting a tab pops it to its root.
  - Memory measured with every tab visited.

The main remaining uncertainty is not whether UIKit exposes the desired APIs.
It is whether a chosen extension/bridge can fit Exact's ownership and state
model while removing the need for an app to patch its presenter.
