# LLP 1048.007: Pages that wait for the reader — an undeclared route infers its activation

**Type:** RFC
**Status:** Draft, built (2026-10-31). Charlie asked for exact2 to be the fastest framework on the Pokédex benchmark's page loads, keeping its ergonomics and correctness ("make it so exact2 is the fastest web framework on as many of these measures as possible", 2026-10-30); his request is the approval `rules/RULES.md` asks for.
**Systems:**
- Both renderers: the render host (`host/render/src/lib.rs` `activation`, `page.rs`) and the JavaScript render server (`host/web-js/render.mjs` `infer`).
- What they share: `exact_runner::activation` and `exact_runner::viewport_reads`, the latter moved from the render host.
- The capture script (`host/web-js/capture.js`) and the JS build's server entry (`host/web-js/build.mjs`, `names.js`).
- The page's sheet: `host/web-js/page-style.mjs`, `host/render/src/page_style.rs`, and the runtime's entry (`build.mjs` `main.js`).
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-10-31
**Amends:** LLP 1048.001 D4 (the default activation); LLP 1153.001 D8 (where an undeclared route's preload goes)
**Related:** LLP 1048.001 (activation policies, replay); LLP 1048.006 (the reader's viewport, whose comparisons D2 reuses); LLP 1071 D6 (the early flush); LLP 1153.001 (pages per request from `serve`, the measurement)

## Summary

A route that declares no `activate=` used to run its runtime on every page as soon as the page had painted (`eager`). On the Pokédex benchmark that cost each page 87 KiB of script and up to 145 ms of blocked main thread under Lighthouse, for pages whose only work before the reader acts is replaying what the capture script already records.

An undeclared route now infers its activation from its render. When the render left the runtime nothing to do before the reader acts, the page waits for the reader (`interaction`), otherwise it runs at once as before (D1). A plan laid out by the viewport makes every waiting page carry the comparisons it was laid out by, as media queries. The capture script checks them and wakes the runtime when the reader's viewport differs (D2). Only a page that may wait leaves the runtime out of the head a server sends before the render (D3). A rendered page carries only the style rules its document can match, and the runtime restores the rest before its first render (D4).

Measured on the Pokédex app (§2), declaring `activate=interaction` on every route took script at load to 0 and TBT to 0 on five of six pages, with all 54 tests passing. Inference gives that page the same result without the declaration.

## 1. Decisions

### D1. An undeclared route waits when its render left the runtime nothing to do

A route that declares no `activate=` gets `interaction` when all of these hold, and the old default (`eager` on the JS runtime) otherwise:

- **Nothing in the plan is kept by the runtime** (`exact_runner::activation::runtime_kept`):
  - a reserved source of the reader's device: the time and zone, the page's state, a surface, MIDI. Only `exactViewport` (D2) and `exactDelivery`, the build's own facts, are allowed;
  - a virtualized list, whose later rows the runtime makes as the reader scrolls;
  - a canvas, a native view or a web view;
  - page code (`hatch`), an app's frame (`src`), or an instant (`datetime`), which is shown in the reader's zone.

  This is asked of the plan, not the page, because a page the render host sends as it is written decides before its document exists.
- **No answer is pending.** A page held at its deadline needs its runtime to finish.
- **Nothing is due on the clock:** no armed timer, `then`, queue `next` or frame task (`Runner::timer_due_ms`, `wants_frames`; the JS clock's timers and mutations).
- **Every handler on the page is one the capture script replays or wakes for.** It replays `press`, `change`, `input` and `navigate` (`REPLAYED`); a link navigates natively. It wakes for `intersect` (`WOKEN`): an intersect handler's first report is its element's visibility, which only matters once the element shows or the reader scrolls. So the capture script watches those elements and wakes the runtime when one intersects or at the first scroll, and the runtime then reports each as it is (LLP 1048.001 D4's `visible`). Any other kind (key, focus, a gesture, media) runs the runtime at once. A declared `interaction` keeps LLP 1048.001's own wider set.
- On the JavaScript render server, **the render formatted no date in the default zone.** The render's `Intl.DateTimeFormat` notes it as it substitutes UTC.

Only pages for the JavaScript runtime infer. A page for the wasm runtime (a document carrying view ids) keeps the old default; that target is retiring on the web (LLP 1071 §7).

The rules are stated once, in Rust. The JS build writes them into `names.js` (`activation`, `viewportMedia`) for `render.mjs`.

**Why the capture script's set.** A waiting page loses nothing the reader does: the capture script records a press, a change and typing from first parse and replays them after adoption (LLP 1048.001 D5). An event it does not record would be lost, so a page with such a handler cannot wait.

**What a waiting page gives up.** In-app navigation from a waiting page is a document navigation until the reader first acts. Every rendered route is served whole, so the reader still gets a complete page.

### D2. A page laid out by the viewport carries its comparisons

A plan reading `exactViewport` is laid out for one viewport: the reader's, as near as the request tells, on the render host (LLP 1048.006), and 390×844 on the JavaScript render server. Waiting would leave a reader on another viewport with that layout until they act.

Each comparison the plan makes on a viewport fact is a media query that matches exactly when the comparison holds (`viewport_reads::Media`):
- `width >= 640` is `(width >= 640px)`;
- `prefersColorScheme == "dark"` is `(prefers-color-scheme: dark)`;
- a negation is `not all and (…)`.

The size uses `innerWidth`/`innerHeight`, as the media feature measures. Each preference is the query `navigation.js` `preferences` already reads.

Every waiting page of such a plan carries the comparisons with the answers its render saw, on the checkpoint as `data-wake="[[query, holds], …]"`. The capture script wakes the runtime if any query differs, now or on a later change. The runtime then adopts and lays the page out for the reader.

A plan that reads the viewport in a way no query expresses never waits. Such readings are:
- a fact used whole, or in arithmetic;
- a gamut or dynamic range, which a wider screen also matches;
- `gpuTier`, a fold's segments;
- an order on a keyword.

### D3. Only a page that may wait leaves the runtime out of the early head

A server sends a page's head before its render (LLP 1071 D6). That head and the 103 have always named the runtime's preloads, except on an `interaction` route.

For an undeclared route of a plan whose pages can wait, the early head and the 103 now leave them out. A page whose render then chose `eager` names them after the head's fields, still in `<head>` (`body_open_js`'s `late`). A complete page (a page at build, a cached page) names them in its head as before.

A plan none of whose pages can wait, by D1's plan-wide rules, keeps the early preload and the 103.

### D4. A rendered page carries the rules its document can match

The shell's one sheet holds the web host's base stylesheet and every class of the app: 85 KB on the Pokédex app, 11.5 KB compressed, 73% of its home page on the wire. Most of it styles controls the page does not have. Lighthouse's simulated network charges every byte of the document, and a document past about 14.6 KB pays another round trip while TCP's window opens.

**The build analyzes the sheet once** (`host/web-js/page-style.mjs` `analyze`, into `.gen/page-style.json`). Each rule is recorded with what its selector needs of a document, as alternatives of tokens: a tag, a class, an id, an attribute name.
- `:is()`, `:where()` and `:has()` add their lists' alternatives.
- `:not()`, other pseudo-classes, attribute values and the structure between compounds need nothing.
- `open` needs nothing, because the browser sets it itself.

Being needed is therefore a necessary condition for matching. A rule left out matches no element of the page, as written or in any state the browser reaches without the runtime.

**Both renderers select the page's rules** (`select`, `page_style.rs`). They keep the rules whose needs the tokens of the page's document and the shell around it meet, in the sheet's order, so whatever a kept rule wins it still wins. The page carries them as `<style data-exact-page>` after its head's fields. The head sent before the render then carries no sheet, which costs first paint nothing, because the document arrives with the rest.

A page the render host sends as it is written, before its document exists, carries the whole sheet in the same place.

**The runtime restores the whole sheet before its first render.** The build writes it as `style.css`. The entry adds it, waits for it to load, as it waits for the declared fonts, then removes the page's sheet. What the runtime then shows is styled as on the shell. If `style.css` fails to load, the page keeps its own sheet and the render goes on.

The home page's sheet went from 85 KB (11.5 KB compressed) to 21 KB (4.0 KB). The page went from 15.6 KB to 8.3 KB compressed, and it is pixel-identical with its script off, light and dark, at 412 and 1280 px.

### D5. An image a `for` repeats loads as its row comes into view

A platform list loads a row's image as the row comes into view (a `UITableView` cell's, a `RecyclerView` item's). The web's word for it is `loading="lazy"`. The JS build writes it on an `img` whose plan node a `for` repeats at any depth (`facts.rs` `repeated`). A lone image, a hero or an article's figure, keeps the browser's default and loads with the document.

On the Pokédex home page, 48 sprites (all but four below the fold) no longer compete with the document. Lighthouse leaves low-priority images out of its largest-paint simulation, so the page's largest paint is its first paint.

The render host's projection does not write the attribute, as it does not write `decoding="async"` (`QUEUE.md`). Adoption walks tags, so its pages adopt as before.

There is no vocabulary for the author to say otherwise, because Exact has no `loading` property. A gallery whose first rows must load with the document is the case that would want one.

## 2. Measurement

The Pokédex app from LLP 1153.001 §1 under Lighthouse's mobile settings, median of five, with every route declared `activate=interaction`, which D1 now infers. Alongside are the benchmark's medians for the other frameworks, across five builds each:

| Page | Exact before (TBT / JS) | Exact waiting (TBT / JS) | Astro | Next.js | SvelteKit |
|---|---|---|---|---|---|
| Home | 118 ms / 87 KiB | 0 / 0 | 0 / 0 | 51 / 142 | 0 / 36 |
| Pikachu | 102 / 88 | 0 / 0 | 0 / 0 | 49 / 142 | 0 / 37 |
| Move | 145 / 87 | 45 / 0 | 0 / 0 | 50 / 141 | 0 / 36 |
| Ability | 33 / 87 | 0 / 0 | 0 / 0 | 48 / 141 | 0 / 36 |
| Type | 71 / 87 | 0 / 0 | 0 / 0 | 48 / 141 | 0 / 36 |

The move page's 45 ms is the parse and style of a 289 KB document, not script. All 54 of the benchmark's tests pass, including:
- typing in the search before the runtime has loaded;
- sorting a table;
- changing the game in a `select`.

## 3. Verification

`host/web-js/document-render.test.mjs`, "both document renderers infer an undeclared route's activation from its render", checks that with both renderers:
- a page with only a press handler waits;
- a page with a running task runs at once, with its preload after the head;
- a viewport-laid page carries `[["(width >= 640px)",false]]`.

In Chromium, that page's runtime loads at 1280 px wide and not at 390.

The render host's tests check two more things. A wasm-runtime page keeps its default. A page held at its deadline runs at once, with no 103 and its preload after the head.

For D4, "both document renderers give a page its own rules, and the runtime restores the whole sheet" checks:
- the page's sheet is under half of `style.css` and lacks the `select` rule the page does not need;
- in Chromium, once the reader shows a `select`, it has the whole sheet's `appearance: none`, the page's own sheet is gone, and `style.css` is linked.

The adoption tests in the same file compare computed styles before and after adoption, and pass with every page carrying its own sheet.
