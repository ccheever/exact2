# LLP 1149.000: The renderer on the web — the DOM by default, the canvas by choice

**Type:** RFC (a decision brief: each question carries a proposed answer; §4 lists the ones that are Charlie's)
**Status:** Draft r3, 2026-10-28. r1 was reviewed blind by Muse Wonder Full 1.0 (READY WITH CHANGES), Grok 4.7 (READY WITH CHANGES) and GPT-6 Astra (NOT READY) (`llp/reviews/rfc-2026-10-28-1149-r1.{muse,grok,astra}.md` §3); r2 folded Muse, r3 folds Grok and Astra. All three keep the DOM as the default. What r3 corrects: the wasm target has no text measurement bridge today (the browser lays out the DOM; `BrowserMeasures` returns default metrics), so a painted web target is a text integration before it is a renderer; a JS-target refusal fails the build rather than falling back to wasm; the mirror must be in the accessibility tree (never `display: none` or `aria-hidden`) and hold real text so find in page sees it; EditContext is text input, not an editor; pinch zoom scales the canvas's pixels and is a tell; a no-GPU browser falls back to the DOM build; the atlas caches clusters where shaping allows and runs where it does not; the oracle gets a declared text band. ## 0. Summary

Charlie's instinct is the principle. LLP 1115 says what the author leaves unsaid is the
platform's, and on the web the platform's renderer is the DOM: it is what selects, finds,
zooms, prints, reads aloud, fills forms, follows links and takes extensions. An app painted
into a canvas on the web fails LLP 1115's test at once — someone who knows the web notices
that text will not select — the way a non-native look fails it on iOS. Flutter web is the
running example (LLP 1148 F3). So:

1. **The DOM is the default** on the web and stays what it is: the JS target, the same
   Contract compiled to one ES module over a runtime of 5 to 8 KB (about 20 KB for a small
   app's whole payload, LLP 1071). Nothing in LLP 1149 changes it (D1).
2. **Painting on the web is an app's conscious choice**, in its manifest, for the apps whose
   content is not a document: a design canvas, a map, a board, a grid of a hundred thousand
   cells, a timeline (D2). Figma, Google Docs and Google Sheets made that choice for those
   reasons; a settings screen never should.
3. **An opted-in app still gets what the web owns**: an accessibility tree the host mirrors
   from the kernel's roles into DOM that assistive technology and find in page can see,
   text input through the browser's editing context, links and history through the browser's
   (D3). What it loses (selection on the pixels, print, pinch zoom without blur) is declared
   at build, so the author pays knowingly.
4. **The renderer is the same code** (`exact-ink` through wgpu's WebGPU backend, LLP 1149
   D5), so "works on every platform" is true of the renderer; it is the *default* that is the
   platform's (D4). What the painted web does not have today is text: the wasm target lets
   the browser lay out the DOM and measures nothing (D5), so the painted target is a text
   integration before it is a renderer.
5. **Islands or the whole app**: the first consumer decides (D7).

The one refinement to Charlie's framing: "heavy and gross" is the right description of
painting a *document* app into a canvas, and the wrong one for a design tool, where the DOM
is the heavy option. The manifest key makes the author say which one they are building.

## 1. What is there today

- **Two web targets** (LLP 1071): the JS target, the DOM as the tree, used by default when an
  app qualifies; what it refuses fails the app's build (LLP 1071 D5; `host/web/build.mjs`).
  The wasm target, the kernel in `app.wasm` with the web host projecting its tree to the DOM,
  is what games build and what the smoke's fixtures keep (`--wasm`); it is not a fallback the
  build takes on its own. Neither target paints: on both, pixels are the browser's.
- **Text on the wasm target is the browser's**: the web host projects the tree and the
  browser lays out the text in the DOM; the host's measurer (`BrowserMeasures`,
  `host/web/src/host.rs`) returns default metrics and is otherwise unused. There is no
  measurement bridge from the kernel to `measureText` today; LLP 1001 §6's injected
  measurement is the seam one would go through.
- **A game's canvas** on the web is the app's GPU module on wgpu's WebGPU backend, loaded
  after first pixel (LLP 1009 D1, D2), with a wasm-bindgen glue (LLP 1009 §3).
- **Canvas 2D** replays through `canvas2d-glue.js` into a `CanvasRenderingContext2D`
  (LLP 1056): a small JS glue file the web host owns without wasm-bindgen.

## 2. Decisions

### D1 — The DOM is the default

Unchanged. An app that says nothing builds the JS target; an app the JS target refuses fails
its build and says why, as today; a game builds the wasm target. No app is painted on the
web without the key in D2.

### D2 — Painting is a manifest choice, per app

`app.json`: `"web": { "presenter": "painted" }`. The build then makes the wasm target with
`exact-ink`'s web device in place of the DOM projection: the kernel lays out with the
measurement bridge of D5, the painter walks, the renderer draws into one `canvas` covering
the viewport, and the DOM build of the same app is produced beside it (D4's fallback, D6's
oracle). The build prints, as a refusal list prints today (LLP 1071 §7), what the app gives
up on the web (D3's third column), so the choice is made with the cost in view; a build
cannot tell "mostly prose" from a mixed board and does not try (§4 Q7).

### D3 — What the painted web still owes the web

| The web owns | The painted target provides | Declared tell in v1 |
|---|---|---|
| Accessibility | a DOM tree mirrored from the kernel's roles, names, values, states, bounds and focus order, updated per commit, **in the accessibility tree**: visually hidden by clipping, never `display: none`, `visibility: hidden` or `aria-hidden`, which remove it; with live regions, focus moved between the canvas and the mirror as the kernel's focus moves, form semantics (labels, `autocomplete`) on the proxy fields, and **real text nodes**, so a screen reader reads the words and find in page finds them. Budgeted as a second presenter, with VoiceOver, NVDA and a mobile screen reader in real browsers in its gate; headless screenshots cannot qualify it | find in page highlights the mirror's text, not the pixels |
| Text input and the IME | the `EditContext` API where the browser has it (Chrome and Edge from 121; not Firefox, not Safari), with the candidate window placed by `characterboundsupdate` from the kernel's caret and selection bounds; a `textarea` proxy positioned at the field where it does not. EditContext is text input only: selection, clipboard, undo and the editing commands are the presenter's, as the painted hosts' are | — |
| Links and history | `navigate` through `location` and `history` as the JS target does; an anchor in the mirror carries the `href` for assistive technology | middle-click, the link context menu and drag of a link are the mirror's, reached by keyboard; the pixel has none |
| Scrolling | the kernel's scroller with the web host's wheel and touch physics, as the Linux host's; `scroll-behavior` and the keyboard as today | browser extensions that scroll do not |
| Zoom | page zoom changes `devicePixelRatio` and the layout viewport: the kernel lays out again and the renderer re-rasterizes glyphs | pinch zoom changes `visualViewport.scale`, not `devicePixelRatio`: the browser scales the canvas's pixels, which blurs |
| Selection on the pixels | — | not in v1 |
| Print | — | prints the canvas's pixels |
| Forms autofill, password managers | the proxy field carries `autocomplete` | partial |

### D4 — The device: wgpu's WebGPU, and the DOM when there is no GPU

`exact-ink`'s web device is wgpu's WebGPU backend (LLP 1149 D5.1), with the WGSL source as
is; a WebGL2 layer exists only if a browser without WebGPU must be served, with the GLSL ES
3.00 the build translates. The browser compiles the shaders (LLP 1149 D6.3: counted, the
browser's, unavoidable). Feature detection is the adapter and device being created, not
`navigator.gpu` existing; when neither API yields a device, or it is lost and not recovered,
the page loads the DOM build of the same app (D2 makes it), and the kernel's state carries
over as a reload carries it. Instances cross the boundary as one typed-array view per frame
over wasm memory; textures as `ImageBitmap`s and atlas uploads from the same memory, through
a glue file the web host owns as `canvas2d-glue.js` is owned (LLP 1056); that it carries no
wasm-bindgen is this document's constraint, not LLP 1009's, whose GPU module glue uses it.

### D5 — Text: the measurement bridge, then the browser rasterizes what it measured

The painted target needs what the wasm target does not have: the kernel measuring text
through the browser. That is the first thing built, not the renderer: a batched
`measureText` bridge over LLP 1001 §6's seam, with line breaking and run construction on
the kernel's side from the browser's advances, the fonts the page has loaded (a declared
font, LLP 1019, is a `@font-face` loaded before first paint, as the JS target loads it), and
the CSS text features Canvas cannot express declared as gaps (`font-variation-settings` is
not a Canvas text property; `letterSpacing`, `wordSpacing` and `fontVariantCaps` are).

Then the atlas: the page has no glyph-id rasterizer, so the browser rasterizes with
`fillText` into an `OffscreenCanvas` exactly what it measured. Entries are **clusters** where
shaping does not divide them (Latin, digits, most scripts), so a grid of numbers shares its
digits, and **whole runs** where it does (Arabic, Indic conjuncts, emoji sequences, a
ligature the measurer treated as one unit); the key is the text, the CSS font, the size,
the direction and language, the spacing properties, the subpixel phase and the font-load
generation; the cache is bounded by bytes and not only by frame age, with an entry past the
budget drawn into its own texture for the frame. Ink and advances then come from the same
rasterizer under the one constraint that the atlas's units are the measurer's units. The hit
rate and re-raster cost on a prose-heavy screen and on a Sheets-like grid are measured in
Chrome and WebKit before the design is called done.

### D6 — The oracle is the DOM, with a declared text band

A painted app on the web must land against the DOM build of the same app in the same
browser, on the smoke's crops (LLP 1015 §8's instrument, pointed at two builds of one app):
geometry, images and solids within the tight band; text within a **declared text band**,
because canvas `fillText` and DOM text differ in Chrome by design (the canvas path has no
subpixel positioning or LCD filtering and its gamma differs), and because Chrome, Firefox
and WebKit differ from each other. The crop set and a band per browser are defined before
anything is built. Pixels are not the whole oracle: focus order, the mirror's text and
states, and editing journeys (a Japanese and a Chinese field on Chrome, Firefox and Safari,
the journeys LLP 1115.004 D7.1 lists for RichEdit) are checked in real browsers with
assistive technology. Then an author who opts in gets the same layout they would have had,
and the painted hosts' parity with Chrome (LLP 1148 F9) extends to the web itself.

### D7 — Islands or the whole app: the first consumer decides

A **painted app** is D2. An **island** is a node marked `painted` inside a DOM page: the DOM
owns the page and the island's box; the kernel in wasm lays out the island's subtree inside
that box and the renderer draws it into a canvas the DOM positions. Docs' document, Sheets'
grid, a map in a settings page. The seam is the box: the DOM's layout outside, the kernel's
inside, which LLP 1001's parity makes coherent; what the seam must also carry is overflow,
nested scrolling, focus crossing, accessibility order and overlays, which need a consumer to
be designed against. The island keeps the page's selection, links and accessibility for the
rest of the page for free and proves the device in one screen; the whole-app form is what a
design tool or a map ported whole wants. Neither is first by fiat: the consumer that names
itself first sets the order (§4 Q2).

### D8 — The cost is shown

An opted-in app's bytes before first paint (the wasm kernel, the renderer's module, the glue)
and its time to first frame in headless Chrome are printed by the build beside the JS
target's for the same app, so the author sees what the choice costs; `metrics.mjs` keeps
both.

## 3. Order of work

Unscheduled. The decisions stand; no stage is dated until an app asks, as `rules/RULES.md`
requires ("a spec needs an implementer and a date"), and LLP 1149 S0 holds the ES 3.00
subset of the shader so the web does not discover it alone. When an app asks, in order: the
measurement bridge (D5), the device and its DOM fallback (D4), the atlas (D5), the mirror
and the editing proxy (D3), the manifest key and the build's refusal list (D2, D8), the
oracle with its text band and its assistive-technology journeys (D6), on Chrome, Firefox and
WebKit through the conformance harness's browsers, after LLP 1149's native stages. Islands
(D7) are a sub-LLP when a consumer names one.

## 4. Questions that are Charlie's

Each carries the proposed answer and the panel's recommendation and confidence (0 to 100):
Muse (M), Grok (G), Astra (A), on r1.

1. **The DOM stays the default; nothing paints on the web without the manifest key?** Yes
   (D1, D2). *M:* 95. *G:* 93. *A:* 100.
2. **Islands or the whole app first?** The first consumer decides (D7). *M:* islands first,
   65. *G:* per app first, 86. *A:* let the consumer decide, an island for a mixed app, 85.
3. **The accessibility mirror and the editing proxy are required, in the accessibility tree,
   with real text, tested with screen readers in real browsers?** Yes (D3). *M:* 85. *G:* 88.
   *A:* 100 (behavioural gates, not roles alone).
4. **The measurement bridge first, then clusters and runs rasterized by the browser?** Yes
   (D5). *M:* runs, byte-budgeted, 60. *G:* clusters for simple scripts, runs for complex,
   68. *A:* a starting mechanism, not a proof of parity; the bridge does not exist today, 88.
5. **The DOM build of the same app is the oracle, with a declared text band and
   interaction and accessibility checks?** Yes (D6). *M:* 70. *G:* 74. *A:* 98.
6. **Unscheduled until an app asks, the ES 3.00 subset held in S0?** Yes (§3). *M:* 75.
   *G:* 82. *A:* 97.
7. **Should the build refuse a painted app whose screens are mostly prose?** No: the author
   decides; the build prints the tells, and refuses only a required capability the target
   cannot provide (D2, D3). *M:* 80. *G:* 82. *A:* 98.
