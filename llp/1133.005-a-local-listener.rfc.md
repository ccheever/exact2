## Summary

A desktop app is sometimes the server. T3 Code's command line opens a
project in the running app: `t3 app <dir>` dials a Unix-domain socket the
app listens on, writes one JSON line and waits for one back. Its ChatGPT
sign-in redirects the browser to `http://127.0.0.1:1455/auth/callback`,
where the app must be listening (RFC 8252 §7.3). exact2 can do neither: a
source can fetch and hold a WebSocket open, but nothing accepts a
connection, and `openAuthSession`'s callback is a private-use scheme or a
claimed `https` URL. The T3 Code clone does both in 1,038 lines of its own
Swift.

This RFC proposes two things, sharing one piece of native code:

1. **A local listener** (§2–§5), a data capability beside `fetch` and the
   WebSocket. A TypeScript source answers with
   `exactListen("unix:/path", { exactStream(event, connection) { … } })`.
   The resource is listening while it is held. Its stream is LLP 1016.000's:
   `listening`, then each `connection`, each line on it, and each `end`,
   mapped in arrival order. Replies go back by D7's rules: the mapper may
   answer its own connection's line, and a mutation or an answer in flight
   sends on a connection handle it kept. Addresses are `unix:<path>` now;
   loopback TCP and HTTP are written down for when a consumer asks.
2. **A loopback redirect for `openAuthSession`** (§6), the shape LLP
   1069.006 D5 wrote down: a callback `http://127.0.0.1:<port>/<path>`
   makes the host listen on that port, open the authorization URL in the
   default browser, answer the one GET whose path and `state` match, and
   reply 200 with the callback URL, as every other callback form does.

Both need the window to come forward when work arrives from outside it
(the reference's `DesktopWindow.activate`), so §7 adds the window's
`focus()`, as bare `close()` is the window's.

Targets: macOS and the Linux host first (one Rust implementation), the web
refusing by name; Windows' named pipes and iOS are `later` (§8).

## 1. The consumer and what it needs

The T3 Code clone (`examples/t3-code` on `daehyeon/t3-code-main`) follows
T3 Code's desktop app (MIT, reference `1e2ecbd975`). Two of its Swift files
exist only because exact2 has no listener:

- **`t3 app`** (`modules/apple/T3AppControl.swift`, 716 lines;
  `T3Module+Activation.swift`, 48). The reference is
  `apps/desktop/src/app/DesktopAppActivation.ts`
  (`startDesktopAppControlServer`), `DesktopAppActivationBroker.ts` and
  `packages/shared/src/desktopAppControl.ts`. What it does:
  - listens at `<os.tmpdir()>/t3code-<uid>/<24 hex of sha256(<T3
    home>/userdata)>.sock`, a path the CLI computes the same way;
  - makes the directory `0700`, refuses one that is not a directory or
    belongs to another user, and never follows a symlink there;
  - reads one line of at most 64 KiB within 5 s, answers one line, ends the
    connection; a client that leaves first cancels its request;
  - listens only while the app's embedded server runs;
  - lets two app instances on one T3 home share the path: the newer takes
    it over (bind a staging name, then `rename`), a close unlinks the path
    only while it is still this instance's inode, and an instance binds
    again when the path vanishes;
  - brings the window forward when a request arrives.

  The protocol (validating the request, queueing requests until the window
  is ready, one at a time, timeouts) is app logic and moves to the clone's
  TypeScript; only the socket and the window's activation are the
  framework's.
- **Codex sign-in** (`T3CodexAuth.swift`, 234 lines;
  `T3Module+CodexAuth.swift`, 40). The reference is
  `packages/shared/src/codexAuthCallback.ts:16-100` and
  `codexAuthHandoff.ts:27-80`. T3's server builds the authorization URL;
  its `redirect_uri` is `http://127.0.0.1:<port>/auth/callback` with a port
  the server chose. The app binds that port before the browser opens,
  answers the one GET on `/auth/callback` with the right `state` and
  exactly one `code` or `error` with a "return to T3 Code" page, hands the
  URL back, frees the port, and raises the window. The URL's own checks
  are already TypeScript (`src/providers/codex-auth-request.ts`).

The two needs differ in kind. `t3 app` is a long-lived listener whose
protocol is the app's: a data capability, like the WebSocket. The
sign-in is one request answered by one callback URL, which is what
`openAuthSession` already is (LLP 1069.006 D1); only its callback form is
missing. Building the sign-in on the general listener would put the
callback's checks (the port, the path, `state`, a page for the browser, no
other request answered) in every app's source, where LLP 1069.006 keeps
them in the host so that each app gets them right once.

## 2. Tier 1: the listener's words

### D1 — `exactListen(address, options)`, answered as a stream

A TypeScript source returns the listener as its answer, as it returns
`fetch(url, { exactStream })` for a stream (`docs/reference.md`, "An
answer that keeps coming"):

```ts
import type { ListenConnection } from "./app.contract.d.ts";

const connections = new Map<number, ListenConnection>();
const queue: Activation[] = [];

export function answer(source: string, args: unknown[]) {
  if (source === "appControl") {
    const [path, running] = args as [string, boolean];
    if (!running) return { status: "off", queue: [] };
    return exactListen(`unix:${path}`, {
      takeover: true,
      idleTimeout: 5000,
      exactStream(event, connection) {
        if (event.type === "connection") connections.set(event.id, connection);
        if (event.type === "end") connections.delete(event.id);
        if (event.type === "message") {
          const request = parseActivation(event.id, event.data);
          if (request.ok) {
            queue.push(request.value);
          } else {
            connection.send(JSON.stringify(request.failure));
            connection.end();
          }
        }
        return { status: event.type === "error" ? event.message : "listening", queue: [...queue] };
      },
    });
  }
  if (source === "activationComplete") {
    const [id, response] = args as [number, string];
    const connection = connections.get(id);
    if (!connection) return { sent: false };
    connection.send(response);
    connection.end();
    return { sent: true };
  }
}
```

The words:

- **`exactListen(address, options)`** returns what a source answers with,
  as `fetch` does; the promise never settles, and each event is mapped now
  (the mapper cannot await) and commits as the resource's answer (LLP
  1016.000 D1). It is valid only as a resource's answer. A mutation that
  calls it throws `InvalidStateError`, because a listener with no resource
  holding it would have no end (D2).
- **Events**, by Node's `net.Server` and `net.Socket` names where they fit:
  - `{type: "listening", address, port}`: the address is bound. `port` is
    the bound port of a TCP address, `0` for `unix:`. It is always the first
    event, and `pending(resource)` is true until it lands.
  - `{type: "connection", id}`: a peer connected. `id` is a positive
    integer, unique for the resource incarnation; the handle passed beside
    it is that connection's.
  - `{type: "message", id, data}`: one line from that connection, as a
    string without its line terminator (`\n`, or `\r\n`), decoded as UTF-8
    (invalid bytes become U+FFFD, as `TextDecoder` does by default).
  - `{type: "end", id, reason}`: the connection ended: `"peer"` (the peer
    closed or reset it), `"app"` (the app's `end()` finished), `"idle"`
    (`idleTimeout` passed with no complete line), `"overflow"` (a line or
    the connection's queue passed its bound, D3).
  - `{type: "error", kind, message}` ends the stream: the address could not
    be bound or stopped working. `kind` is `Refused` (outside the grants,
    or a directory or path that fails D4's checks), `AddressInUse`,
    `Unsupported` (D8), or `Network` (anything else the OS reports, its
    text in `message`).
- **`ListenConnection`**, the handle: `send(text)` writes `text` and a
  `\n`; `end()` closes the connection once what was sent before it has
  been written (Node's `socket.end()`); `readyState` is `0` before the
  `connection` event, `1` while open, `3` after `end`. `send` refuses a
  string that contains `\n` (`SyntaxError`), since the peer would read it
  as two lines.
- **Options:** `takeover` (D4; default `false`), `idleTimeout` in
  milliseconds (a connection with no complete line within it ends `idle`;
  default none, at most 600,000), `maxLineBytes` (default 65,536, at most
  1,048,576), `maxConnections` (default 16, at most 64; a connection past
  it is accepted and closed at once, without an event, as a full backlog
  would refuse it).

**Declared deviation.** The web has a listener only for Isolated Web Apps:
Direct Sockets' `TCPServerSocket`, whose `opened` promise hands a
`ReadableStream` of connections, each with its own streams. That shape
needs an async reader per connection; a stream's mapper here answers each
event now and sends only in defined turns (LLP 1016.000 D7). So the
listener takes `fetch`'s shape and LLP 1016.000's mapper, Node's event and
method names (`listening`, `connection`, `end()`), and Direct Sockets'
words where it has them (`localPort` is the `listening` event's `port`).
Node's `net.createServer().listen()` is not offered: it is a callback API
over a long-lived object no resource would own.

**Rust sources** answer `Answer::Stream(Request::listen(address))` and read
the same events through their `parse`. They have no connection handle,
as they have no WebSocket handle (LLP 1016.000, "As built"), so a Rust
listener only reads; replies from Rust wait for a consumer.

### D2 — The resource holds the address

The listener lives exactly as long as the resource that answered with it,
by LLP 1016.000 D2's forget path. New arguments, `refresh`, or the
resource leaving the plan close the listener: every
connection ends (`app`, without further mapper calls), the socket file is
removed (D4), and a new incarnation binds again. So the app says when it
listens with the resource's arguments, from state Contract already has
(the clone's embedded server), and the source answers a value now, not a
listener, while it should not listen:

```
resource control = appControl(server.home, server.running) as shape Control
```

**Within one process, an address is held once.** A second resource that
asks for an address another resource of the same process holds (another
window's session asking for the same `unix:` path) is not bound: it stays
pending, `state.streams` lists it as `waiting for <address>`, and it binds
when the holder lets go. Two windows of the clone therefore share one
socket, served by whichever window bound it first, and the next window
takes over when that one closes. The reference serves requests from its
focused main window; the clone's queue picks the window, as §1 says.

*Rejected:* refusing the second resource with `AddressInUse`. A window
that opens second would show an error for a socket the app holds.
*Rejected:* one listener shared by every session, with connections handed
to the most recent. Each connection must be answered once, by one mapper;
a shared listener would need a rule for which session answers that no
host could keep when sessions come and go.

### D3 — Bounds

Each connection's incoming lines are never coalesced: each is mapped in
arrival order, then its snapshot settles, as a two-way socket's frames are
(LLP 1016.000 D7). The bounds are D7's, per connection: 256 lines and
1 MiB undelivered, besides `maxLineBytes` for one line. A line past
`maxLineBytes`, or a connection past its queue, ends that connection
`overflow` after the lines already queued; the listener stays open.

Sending follows D7's bounds per mapper call, mutation or answer: 256
operations and 1 MiB of payload, and each connection's buffered bytes at
most 1 MiB. Overload throws `QuotaExceededError`, never drops.

The listener counts as one ticket on the stream lane while it is open, as a
stream does. Connections cost no ticket.

## 3. Addresses

### D4 — `unix:<path>`

`unix:` followed by an absolute path. The path is the source's: the T3
address needs `os.tmpdir()` and the user id, which the desktop-process
RFC's home paths provide (B8). A relative path, one with a NUL byte, or
one longer than the platform's `sun_path` (104 bytes on macOS, 108 on
Linux) is refused before anything is created.

**The directory.** The parent directory is created if missing, mode
`0700`, with its own parent required to exist. An existing parent must be
a directory (by `lstat`: a symlink is refused, never followed), owned by
the user, and is set to `0700`; otherwise `Refused`, naming why. These are
T3's checks (`T3AppControl.swift`, `prepareDirectory`), which keep another
user from reaching or replacing the socket. The socket file is created
`0600` (the umask is set around `bind`, as `bind` gives no mode argument).

**A path that exists.** A socket file that accepts a connection is live:
without `takeover` the listener fails `AddressInUse`. A socket file that
refuses connections (`ECONNREFUSED`: its owner died without removing it)
is stale, and is replaced. Anything that is not a socket is never removed:
`Refused`.

**`takeover: true`** is T3's rule for two instances on one path, newest
wins:

- bind a staging name in the same directory, then `rename` it onto the
  path, which replaces a live socket in one step (POSIX `rename`); the
  older listener keeps its open file descriptor and its connections, and
  stops receiving new ones;
- remember the bound inode; on close, unlink the path only while it is
  still that inode, so a closing older listener never removes the newer
  one's socket;
- watch the directory while listening; if the path vanishes (the newer
  instance closed and unlinked it), bind it again with `link`, which
  claims the path only while it is free (`EEXIST` otherwise), so two
  instances never trade it back and forth.

A process that exits without closing (a crash, or an exit that skips the
session's teardown) leaves a stale socket file, which the next listener
replaces as above. A host that runs teardown at exit removes the files it
still owns, as the clone's exit hook does.

### D5 — Loopback TCP and HTTP, written down for later

Neither is built until a consumer asks. They are here so that nobody
invents another shape, and so that §6 can share their code.

- **`tcp://127.0.0.1:<port>`** (and `tcp://[::1]:<port>`): the same lines
  over loopback TCP. Port `0` asks the OS for one; the `listening` event
  carries it. A host name (`localhost`, which may resolve to an external
  interface) and any non-loopback address are refused: a LAN listener is
  out of scope (§11).
- **`http://127.0.0.1:<port>`**: requests instead of lines. A `request`
  event carries `{id, method, path, headers, body}` (a body of at most
  `maxLineBytes`), and the handle's `respond(status, headers, body)`
  answers it and ends the connection. The host refuses a request whose
  `Host` header is not the bound address, or that carries an `Origin` of
  another site, before the mapper sees it: a page in the person's browser
  can send requests to loopback ports, and a server that answers it is
  open to DNS rebinding and cross-site requests.

A loopback port is reachable by every local user's processes, where a
`unix:` socket under a `0700` directory is not, so an app that only talks
to its own CLI should use `unix:`.

## 4. Replies

### D6 — Sends follow LLP 1016.000 D7 and its amendments

A connection handle is a socket handle in every rule of D7, with the
connection as the unit:

- **The mapper** may `send` and `end` on the connection it was handed,
  while it answers that connection's `connection` or `message` event (the
  amendment of 2026-10-16). On `end` and `error` the handle is closed and
  refuses.
- **A mutation's synchronous source** may `send` and `end` on a handle it
  kept, and a mutation whose source answers with a promise, and a
  resource's answer in flight, may too, in their own turns (the amendment
  of 2026-10-18). A handle whose connection no resource of this module
  owns throws `InvalidStateError`.
- What a call stages goes out once the commit that ran it stands, in order,
  ahead of later calls' operations; a thrown source, a malformed answer or
  a refused commit sends nothing, and the journal says so
  (`mapper <resource> failed: …; connection sends were refused`).
- A mutation may not both send on a connection and `fetch`, as D7 rules
  for a socket.
- A send on a connection that ended before the batch went out is dropped
  by the host, and the journal says so: the peer is gone, as a browser
  accepts a send until its close event runs.

**The runner.** `SocketSend`'s operation is addressed to `(stream ticket,
resource)` today (`runner/src/request.rs`, `SocketSend::ops`). A listener's
is addressed to `(stream ticket, resource, connection id)`, and
`SocketOp` gains `End`. The checkpoint, the refusal of a commit's batches
and the journal keep D7's rules unchanged.

*Rejected:* a reply only by mutation, as the audit's first sketch said.
The clone answers an invalid request at once, in the line's own turn,
which the mapper's send covers; it answers a valid one after the window
has opened the project, which a mutation covers. Both are D7's existing
rules.

## 5. Tier 2, tier 3 and the ceiling test

### D7 — Platform words and hatches

No platform words in this RFC. Two candidates wait for a consumer:
`linux.abstract=true` (Linux's abstract socket namespace, no file) and
`apple.peerCredentials` (the connecting process's user id by
`getpeereid`, which T3 does not check: the `0700` directory already admits
only the user).

No access hatches: the listener's native object is a file descriptor in the
shared Rust executor, which no app's native code could use without
breaking D3's bounds.

### D8 — The ceiling test

What a desktop app does with a local server, and what reaches it:

| Use | Reached by |
|---|---|
| a CLI that talks to the running app (T3's `t3 app`, VS Code's `code`, Zed's `zed`) | `unix:` lines (D1, D4) |
| a single-instance handoff (a second launch passes its arguments to the first) | `unix:` lines; the launch side is the desktop-process RFC's |
| a loopback OAuth redirect | `openAuthSession` (§6) |
| a local HTTP API for scripts or a browser extension | `http:` (D5, later) |
| a byte protocol (a debugger adapter, a language server over a socket) | not reached: lines only; binary framing waits for a consumer |
| a LAN server (file sharing, a local multiplayer host) | left out on purpose (§11) |
| Windows: the same CLI handoff | `pipe:` (§8, later) |

## 6. A loopback redirect for `openAuthSession`

An amendment to LLP 1069.006, which keeps every rule there that this does
not change.

### D9 — The callback `http://127.0.0.1:<port>/<path>`

RFC 8252 §7.3: "Native apps that are able to open a port on the loopback
network interface without needing special permissions (typically, those on
desktop operating systems) can use the loopback interface to receive the
OAuth redirect." §8.3 recommends the IP literal over `localhost`.

**The grant.** `auth.callback http://127.0.0.1/<path>` admits a loopback
callback on that exact path, at any port, as RFC 8252 §7.3 requires an
authorization server to allow any port. `http://[::1]/<path>` likewise.
`localhost` and any other host are refused in the grant and in the
request. The `auth.session` grant still names where the person signs in.

**The request.** `openAuthSession(url, { callback, state })` with a
callback of that form, where `callback` names the port: the T3 server
built the URL and chose its port, and the source passes the URL's
`redirect_uri` unchanged, as LLP 1069.006 D2 wants ("the callback is known
before PAR"). The host never parses `url` (D1 there).

**The host:**

1. Checks the grants (403 as before), then binds `127.0.0.1:<port>` (or
   `[::1]`). A port in use answers 502 `port in use`, before the browser
   opens; T3 shows its own sentence for it ("The ChatGPT callback port is in
   use on this computer…").
2. Opens `url` in the person's default browser: `NSWorkspace.open` on
   macOS, the OpenURI portal or `xdg-open` on Linux. Not
   `ASWebAuthenticationSession`, whose callback matcher takes a private-use
   scheme or `https` only (`ASWebAuthenticationSession.Callback`), and not
   what T3's reference does (Electron's `shell.openExternal`): the person is
   likely signed in to the provider in their own browser.
3. Answers each connection: a `GET` whose path equals the callback's and
   whose query has exactly one `state`, equal to the request's, is the
   callback. The host replies to the browser with a short page (below) and
   `Connection: close`, stops listening, frees the port, and answers the
   request 200 with the full callback URL (`http://127.0.0.1:<port>` plus
   the request target). Anything else (another path, another method, a
   wrong or repeated `state`, a `Host` header that is not the bound
   address) gets a 400 with a plain sentence, and the listener stays open
   for the real callback. Each connection has 5 s to send its request
   head, and heads past 32 KiB are refused, as T3's are.
4. Raises the window that asked (§7's activation), as the reference's
   `providerAuth.ts:16-49` does once the callback arrives.

Whether the query carries exactly one `code` or `error` is the source's
check, as every OAuth field is (LLP 1069.006 D6 step 7); 200 is still
delivery, not a sign-in.

**The page** the browser shows: a title and one sentence, "Return to
<app name>" and "You can close this tab.", in the app's name from its
manifest and the language the host's own strings use, with
`Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'`,
`Cache-Control: no-store`, `Referrer-Policy: no-referrer` and
`X-Content-Type-Options: nosniff`, as T3's page carries. It never shows
the URL or the code. An app that needs other words for it says so when a
consumer asks.

**Ending.** The person cancels in the app, which supersedes or forgets
the request (LLP 1069.006 D3's supersession, unchanged): the host stops
listening and frees the port, and a late callback gets the 400. The wait is
bounded at ten minutes, as the web popup's is (D4 there), and then answers
499. Closing the browser tab tells the app nothing, so the app keeps its
own "Waiting for sign-in… Cancel".

**Port 0.** RFC 8252 §7.3's usual form is an ephemeral port the client
chooses. That needs the port before the authorization URL exists, so
`authCallback()` would bind and reserve it until the next
`openAuthSession`. T3's server chooses the port, so this RFC builds the
fixed-port form only, and leaves the ephemeral form for its first consumer
(§12, question 4).

**Targets.** macOS: as above. Linux: in a desktop session (a
`DBUS_SESSION_BUS_ADDRESS` or `XDG_CURRENT_DESKTOP`), through the OpenURI
portal; the headless host still answers 501 `no system browser on this
host`. The web answers 501 `a page cannot listen`: a browser app uses the
popup and its callback page (D4 there). iOS: `later`; a loopback callback
there answers 501 until §8's question is measured. Windows: `later`.

**Substitute.** LLP 1069.006 D7's, unchanged: under the agent no browser
opens and no port is bound; the request is held, `pending` shows its
summary (the callback with its port is shown, as a private-use callback
is), and `type @t <callback URL>` is checked by the same rule as step 3,
or `tap @t cancel` answers 499. A drive that wants the real listener runs
with `EXACT_DEVICE=real` (LLP 1069.007 D8), dials the port itself and
reads the page.

## 7. The window comes forward

### D10 — Bare `focus()` is the window's

`focus(id)` focuses an element; bare `focus()` focuses the window, as
bare `close()` closes it and as the web's `window.focus()` does. A desktop
app calls it when work arrives from outside the window: a request on its
listener, a finished sign-in, a notification it handles itself.

- **macOS:** the app is activated (`NSApplication.activate()`), unhidden
  if hidden, and the session's window is deminiaturized and made key and
  front. From macOS 14 activation is cooperative: an app that is not
  frontmost may be refused unless the frontmost app yielded. A CLI in
  Terminal does not yield, and the reference (Electron's `app.focus({
  steal: true })`) uses the older `activate(ignoringOtherApps: true)`,
  which still raises the app; the host does what the reference does, so
  `t3 app` brings the window forward as T3 Code's does.
- **The web:** `window.focus()`, which browsers honour only for a window
  the page opened; a tab is not raised. That is the web's answer.
- **iOS, Android:** nothing; a phone app is in front or not running.
  Journaled as unsupported, as iOS's `close()` is.
- **Linux, Windows:** journaled as unsupported until a windowed host asks.
- **The agent:** journaled, the window untouched (`focus window`).

The host raises the window itself in §6's step 4, so an `openAuthSession`
caller does not call it.

## 8. Every target

| Target | Listener (`unix:`) | Loopback `openAuthSession` | `focus()` |
|---|---|---|---|
| macOS | the shared Rust executor (`std::os::unix::net`, `kqueue` for the directory watch); stage 1 | stage 1 | stage 1 |
| Linux | the same code (`inotify` for the watch); stage 1, driven on the headless host | desktop session: stage 1; headless: 501 | unsupported |
| web | absent: `NotSupportedError` from `exactListen`; a page cannot accept connections | 501 | `window.focus()` |
| iOS | absent: no other process can reach a socket in the app's container, save the app's own extensions | later: an `ASWebAuthenticationSession` whose page load reaches the app's own loopback port while the app is in front, to be measured on a device | unsupported |
| Windows | later: `pipe:\\.\pipe\<name>` (named pipes, the reference's Windows half of `resolveDesktopAppControlAddress`); `unix:` on `AF_UNIX` where a consumer wants it | later | later |
| Android | absent for a CLI handoff (no shell on the device); later for loopback | later | unsupported |
| tvOS, the terminal | absent | absent | absent |

Absence is visible: `exactListen` on a target without it throws
`NotSupportedError` synchronously, and a source can test
`"exactListen" in globalThis` first.

## 9. Grant, substitute and cost

### D11 — The grant `net.listen`

`net.listen unix:<path prefix>` admits a `unix:` path under the prefix,
compared after `.` and `..` are resolved and without following symlinks.
`net.listen unix:` admits any path, for a path computed at run time (the T3
address under `os.tmpdir()`), as `net.fetch https:` admits any host. An
address outside every line is refused before anything is created (`error`,
kind `Refused`). The line is exact2's own, so `own` in
`runner/src/grants.rs` strips it before ibex2 parses the rest, as it
strips `auth.*`.

Derivations (LLP 1069.008): none for `unix:`. A sandboxed macOS app would
need `com.apple.security.network.server` for a TCP listener (D5, later)
and a socket path inside its container; exact2's macOS apps are not
sandboxed today, and `tcp:` and `http:` grants derive that entitlement
when they are built.

### D12 — Substitute

LLP 1069.007 D7's paragraph:

1. **Shape:** a stream resource, as LLP 1016.000's. Not a fact and not a
   request: it opens no system UI and touches nothing of the person's
   beyond a file under a directory the app chose.
2. **Under the agent** the listener binds for real. A drive is isolated by
   its data root (the clone's agent drives run with their own T3 home, so
   their address differs), and it dials the socket itself (`nc -U`, or the
   app's own CLI) to deliver a connection, as the WebSocket smoke runs its
   own server. No agent operation is added (LLP 1133 §7).
3. **`state.streams`** lists the listener: its address, `listening` or
   `waiting for <address>`, its open connections, and lines received and
   sent per connection. `clock settle` does not wait on an open listener
   once its `listening` event has landed (LLP 1016.000 D5).
4. **Disclosure:** the journal records `listen <resource> unix:<path>
   bound`, `took over`, `connection 3 opened`, `ended (peer)`, and
   `send: N bytes (<resource>, connection 3)`, never a line's text, as
   frames' bodies are never journaled.
5. **Production:** a production bake has no agent; nothing changes.

### D13 — Cost

A binary whose plan never answers with `exactListen` links the listener's
code only as part of the shared executor; the executor's `listen` arm is a
few hundred lines of Rust and no new dependency (`std::os::unix::net`,
`libc` for `lstat`, `chmod`, `link` and the watch). Nothing runs before
first pixel: a listener is a resource, asked after the first frame like any
other. Stage 1 measures the executor's size before and after with LLP
1047's probe and records it here.

## 10. Building it

Stage 1, for the T3 Code clone, each step driven before the next:

1. **Runner and grants:** `Request::listen`, the `net.listen` grant and
   its stripping, `SocketSend` addressed by connection, `SocketOp::End`,
   the per-address hold within a process (D2), `state.streams`'
   listener rows. Unit tests in `runner/`.
2. **TypeScript:** `exactListen` and `ListenConnection` in the prelude
   (Hermes) and `host/web-js/ts-data.js` (which throws
   `NotSupportedError`), the declaration in `app.contract.d.ts`, the
   mapper's and an answer's sends through door ops 14 and 17 with a
   connection id.
3. **Executor** (`host/apple/src/executor_listen.rs`, shared with Linux):
   bind, D4's directory and path rules, `takeover`, accept, line reading
   with D3's bounds, `idleTimeout`, sends and `end`, teardown that unlinks
   by inode. Tests with real sockets are `async lane:` tests, as the
   executor's socket tests are.
4. **Loopback `openAuthSession`:** `runner/src/auth.rs` admits the
   callback form and the grant; the Apple and Linux arms bind through the
   executor's code, open the default browser and answer the one callback;
   `apps/auth-fixture` gains a loopback sign-in against its fixture server
   (`scripts/smoke-auth.mjs`).
5. **`focus()`:** the compiler admits the bare form; macOS, the web and
   the journal on the rest.
6. **Drive:** a fixture app that listens on a `unix:` path and echoes
   lines, driven on macOS and the Linux host with `nc -U` and with a
   takeover by a second instance; the auth fixture's loopback sign-in on
   macOS with `EXACT_DEVICE=real` and a real browser.

The clone's adoption is a later app PR: `desktop-activation.ts` answers
with `exactListen` and its broker moves to TypeScript; `codex-setup-ops.ts`
calls `openAuthSession`; the five Swift files of §1 go.

## 11. What stays out

- **Listening beyond loopback.** A LAN server needs a permission story
  (iOS's local-network prompt, a firewall prompt on macOS and Windows) and
  a consumer; `local-network` in LLP 1133.000 §3.9 is where it would go.
- **Binary framing and raw byte streams,** until a consumer (a debugger
  adapter, a language server) asks.
- **Rust replies,** until a Rust consumer asks (D1).
- **Peer credentials** (D7), **abstract sockets** (D7).
- **The ephemeral-port loopback callback** (§6), until a consumer whose
  authorization server lets the client choose the port.
- **An HTTP server for content.** D5's `http:` answers requests from a
  source; serving files or a site from an app is not proposed.

## 12. What a ruling decides

1. **Admit the listener** as a data capability (exact2's vocabulary, LLP
   1133 D5): the reason is that it is a transport the runner's streams and
   the executor own, as `fetch` and the WebSocket are, with no Contract
   surface and no platform object worth a hatch. `rules/DEFERRED.md` has no
   entry refusing a listener; the ruling adds the doing-list line with its
   consumer, T3 Code's `t3 app`, and its take or a waiver.
2. **The name:** `exactListen(address, options)` in `fetch`'s shape with
   Node's event names (recommended, D1), or Direct Sockets'
   `TCPServerSocket` shape, which would need per-connection async readers
   the mapper model does not have.
3. **One holder per address within a process,** the others waiting (D2,
   recommended), or `AddressInUse` for the second.
4. **The loopback redirect** in `openAuthSession` with a fixed port only
   (recommended, §6), or the ephemeral form now as well (an
   `authCallback()` that binds and reserves a port).
5. **The default browser on macOS** for a loopback callback (recommended:
   what T3's reference and RFC 8252 §7.3 do), or
   `ASWebAuthenticationSession` with its page load caught by the listener,
   which keeps the in-app sheet but signs in without the browser's own
   session in Chrome or Firefox.
6. **Bare `focus()`** for the window, raising the app on macOS with
   `activate(ignoringOtherApps:)` as the reference does (recommended, D10),
   or the cooperative `activate()`, which a frontmost Terminal refuses.
7. **`tcp:` and `http:` written down and not built** (D5, recommended), or
   built now with the auth arm's code.
8. **An implementer and a date** (`rules/RULES.md`).
