## 1. The problem

Exact paints a parent's children in tree order on every host (LLP 1001), and a native host paints each child's whole subtree in its turn. A browser paints a stacking context in phases (Appendix E). In order:
1. the background;
2. negative `z-index`;
3. in-flow blocks;
4. their inline content;
5. positioned boxes and child stacking contexts at level 0, in tree order;
6. positive `z-index`.

A descendant can therefore paint outside its ancestor's turn.

The web host gets tree order back by **isolating** (`isolation: isolate`, a stacking context). Today it isolates every static, non-stacking box after anything that paints in step 5. That both **traps** a box's descendants in its turn and **lifts** the box itself into step 5. The lift is why a `position: sticky; top: 0` header paints under plain rows on every Exact host, where a browser paints it on top (LLP 1083 D6).

This RFC keeps every trap, drops every lift that no trap needs, and gives every host one order. Where that order differs from bare CSS it is a deviation every host shares (§3). Where a host still differs from another, it is declared (§4).

## 2. The model

### 2.1 Own facts

Each node has these facts of its own, from the CSS each host actually paints (D2):

- **positioned:** its used `position` is not `static`. A root counts: the hosts make a static root `relative`. A root also stacks, by policy: every web path writes `isolation` on it, so a negative `z-index` at the top level stays above the root's background, as on a native host's root view (measured; §3.1).
- **stacks:** a stacking context by its own values (D2), or by host policy (D2, D3).
- **z:** its *applicable* `z-index`: the authored value on a positioned box or a flex/grid item, else none. Authored `z-index` is kept as its own fact, apart from applicability, because a change of `position` or of the parent's `display` can make it apply (D1). An applicable `z`, 0 included, makes the box stack.
- **level0:** it paints at level 0 when it is not in flow. That is, it is positioned with no non-zero `z`, or it stacks with `z` 0 or none.

### 2.2 Potentials and contributions (no circularity)

A node N's **potentials** describe what its children would let escape *into N*. They are computed from the children's final records, before N's own isolation is decided, so N's isolation never feeds back into them. A child c **traps** when it stacks or is isolated. c **contributes** to N:

- **Z:** c has a non-zero applicable `z` (c itself paints at that `z` in N's context), or c does not trap and c's potential Z is set.
- **0:** c is level0 or isolated (an isolated box is itself a stacking context at level 0), or c does not trap, is not positioned, and c's potential 0 is set. A positioned box's level-0 descendants paint in tree order right after it, as its own subtree would, so they do not count as escaping N.

N's potential Z is the OR of its children's Z contributions, and its potential 0 is the OR of their 0 contributions.

**Order of work, per node:**
1. Compute its children's potentials (recursively).
2. Decide its children's isolation, left to right (§2.3).
3. Compute its own potentials from its children's own facts, isolation and potentials.

One post-order pass does a whole tree. An incremental pass re-runs a node's list and then walks up while any node's potentials or isolation changed. Running a flush twice changes nothing.

### 2.3 Isolation

A child X that does not stack is isolated if and only if one of these holds:

- **(z)** X's potential Z is set. X traps a non-zero `z-index`, positive or negative, which can then never leave X's turn. X may be static or positioned.
- **(a)** X is static, X's potential 0 is set, and an earlier sibling is positioned, stacks, is isolated, or leaks.
- **(b)** X is static and an earlier sibling leaks. A sibling **leaks** when it is static, does not stack, is not isolated, and its potential 0 is set.

A static, non-stacking box that lets nothing escape, after only positioned, stacking or isolated siblings, is not isolated. It paints in flow, under them, as in CSS.

### 2.4 Rank

Among siblings, a child paints in order of (rank, then tree order):

| Rank | Child |
|---|---|
| its `z` | a non-zero applicable `z`, negative or positive, sorted by value |
| ½ | otherwise positioned, stacking, or isolated: `z` 0, no `z`, or a `z` that does not apply |
| 0 | otherwise |

The table is total. A canvas's placed children are a partition below its ordinary children (D5).

## 3. Deviations from bare CSS that every host shares (LLP 1001)

1. **`z-index` stays inside its holder.** A non-zero `z-index` is ordered among its siblings and never above or below its parent's turn. The web isolates the holder (rule z). The nested-`z` fixture's blue is this, not CSS (`parity.rs:48-65`). This replaces LLP 1001's "`z-index` orders siblings", which now holds on the web too.
2. **A level-0 descendant escaping a static box is covered by a later static sibling** (rule b).
3. **An isolated holder paints its own background and in-flow content at rank ½** (rules z, a).
4. **Motion that can change stacking stacks at rest** (D3). So does the parent of a `layout-transition` child (D3).
5. **A compiler-added `relative` is positioned** (LLP 1074 T1). The compiler adds it to a box that clips, scrolls, transforms, animates or has a backdrop (`contains_absolute`), to a scroll-by-default tag, a canvas or a Markdown editor, or when the host transforms the box. It skips the box when nothing absolute can be under it (`holds_nothing`), unless the box is one of those tags or has a material, navigation or context-target prop, an authored `z-index` or an inset (`contract/lower/src/tags.rs:127-186`).
6. **A flowing paragraph stacks** (D2): a text node beside an exclusion.
7. **Authored `z-index` is clamped to ±2147483645.** The two values above it are the exit ghost's and the Arrange lift's (D4).
8. **A ghost's parent stacks while the ghost lives** (D4).
9. **The top layer** (a modal `dialog`, a popover) is outside the sibling model, as in CSS: it paints over the document on every host.

## 4. Differences between the web and the native hosts that remain (declared, LLP 1001)

1. **Inline painting.** Between two overlapping in-flow blocks, the web paints the earlier block's text (Appendix E step 4) over the later block's background (step 3). A native host paints the earlier block's whole subtree first. This exists today.
2. **A resizing `layout-transition`'s surface.** While a box resizes, the web paints its background and border in a stand-in sibling at `z-index: -1` (`presence-glue.js:198-208`). Native hosts keep the surface inside the node (`Surface.swift:49`, `paint.rs:998`). Against an overlapping earlier sibling, the web puts the moving background under it for the length of the transition. The parent's isolation (D3) keeps the stand-in inside the parent; it cannot keep it in the node's own turn.

## 5. Decisions

**D1. One definition, run by every path.** `paint_order.rs` exposes four pure functions over a facts view that any tree implements:
- `own(facts) -> Own`;
- `contribution(child: &Own, isolated, potentials) -> Contribution`;
- `decide(list: &[(Own, Potentials)]) -> Vec<bool>` (left to right);
- `rank(&Own, isolated) -> Rank`.

The facts view includes:
- authored `z` and its applicability inputs (the parent's `display`, its own `position`);
- the host-policy facts (D2, D3);
- structural facts (a text node beside an exclusion; a parent of a `layout-transition` child).

Every path runs them:
- **Live web host (`relayer`).** It dirties a node's parent list on a change to:
  - its own facts;
  - its authored `z` or `position`;
  - its parent's `display` (applicability);
  - its children (insert, remove, move, region arm, `each` reorder).

  It runs §2.2's per-node order deepest-first and walks up while potentials or isolation change.
- **Rust server document (`document.rs`).** One post-order pass over the `DocTree` facts before streaming, then a side table the emitter reads at each opening tag. Every fact above is structural or a row value, so `DocTree` has all of it (r3's text-flow fact needed geometry; r4's does not, D2). The emitter writes the CSS behind each host-policy fact as well as the computed `isolation`.
- **JS target (`paint.js`).** It mirrors the functions per instance on the live DOM:
  - **Own facts:** from value-tested attributes: `data-exact-position`, `data-exact-stack` (value-tested in `rows.rs` and the literal emitter, no longer `v != null`), `data-exact-zi` (authored `z`, kept while it does not apply, with its sign), and `data-exact-policy` (the host-policy and structural facts).
  - **Potentials:** each element caches its potentials and contribution.
  - **`paintFlush`:** processes dirty lists deepest first and propagates as above. It no longer skips lists without a candidate.
  - **Candidacy:** `data-exact-box` widens to "may follow a layered sibling, or may hold a positioned, stacking or `z-index` descendant in any arm".
  - **Re-deciding:** `paintFacts` fires on a bound `position`, a bound stacking row, a bound `z-index` and a parent `display` change. Structural edits call `paintList`.
- **JS server render (`render.mjs` over `dom.js`).** `dom.js` gains the traversal `paint.js` uses (`children`, `firstElementChild`/`nextElementSibling`, attribute reads) and an `isolation` style write. Its output is tested before adoption (D6).
- **Adoption (`rt.js:536`).** It strips a server-baked `isolation` from every element not marked `data-exact-own-isolation` (authored `isolation: isolate` only) or `data-exact-policy`. Then `paint.js` decides afresh, potentials first.

The fixture runs the kernel, the live host, both server renders, the JS target and an adopted page on every case.

**D2. Stacking is decided from the CSS actually painted.** Measured in Chrome 154 (author's check, in the reviews):
- **Stack:** `contain: layout`, `contain: paint`, `scale: 1`, `translate: 0px`, `rotate: 0deg`, `mask-image`, `position: sticky`, `isolation: isolate`.
- **Do not stack:** `opacity: 1`, `filter: none`, `transition: opacity 1s` at rest.

The own fact *stacks* holds for any of the following.
- **Authored values:**
  - `opacity` < 1;
  - `translate`, `scale`, `rotate` or `transform` emitted as anything but `none`, identity values included;
  - `press-scale` ≠ 1;
  - `filter`, `backdrop-filter`, `clip-path` or `mask-image` emitted as anything but `none`;
  - `perspective` not `none`;
  - `mix-blend-mode` not `normal`;
  - `isolation: isolate`;
  - `position: sticky`;
  - an applicable `z-index`.
- **Host policy:**
  - a canvas (`isolation`);
  - a tinted raster image and a symbol image (`mask-image`, in both web targets: `element.rs:212`, `glue.js:358`, `host/web-js/symbols.js`);
  - a native button in a glass style (backdrop filter);
  - a disabled native button that is not `bordered` or `gray` (`filter`);
  - a `backgroundMaterial`.

  The glass and disabled rules in `index.html:67-71` become `!important`, as the material rule already is (`index.html:86`). An authored `backdrop-filter: none` or `filter: none` then cannot silently unstack a box the native host draws as glass or dimmed. A pressed native button's children (`index.html:60`, `opacity: .5`) all stack together inside the button, which clips them, so their order among themselves and the button's rank are unchanged; this needs no fact.
- **Structural:** a text node whose parent has an exclusion child (`flow::is_exclusion`). Every web path writes `isolation: isolate` on it, the server document included. The glue's `contain: layout` keeps containing its fragments and stacks the same way, so the client write changes nothing about order (r3's fact depended on that write; r4's does not).
- **Top layer:** a modal `dialog` or popover is outside the model (§3.9). A `navigationKey` alone stacks nothing.

**D3. Motion stacks at rest only if it can stack.** A box with `transition`, `animation`, `layout-transition`, `exit-animation`, `drag-timeline` or `animation-timeline` stacks, at rest and while running, if and only if its motion can animate a stacking property. The stacking properties are `opacity`, `translate`, `scale`, `rotate`, `transform`, `filter`, `backdrop-filter`, `clip-path`, `mask-image` and `perspective`.
- **Which motion counts:**
  - a transition counts if its property list names one of them or `all`, read from the emitted list including the `--exact-scale` rewrites (`css.rs:186-196`);
  - an animation or timeline counts if a keyframe sets one (`motion/src/animation.rs`);
  - a `drag-timeline` names a source, and counts by the keyframes of the animation it drives;
  - `layout-transition` and `exit-animation` always count.
- **The layout-transition parent.** The parent of any child with `layout-transition` also stacks, structurally (§3.4). `presence-glue.js:238`'s animated parent isolation is deleted.
- **Web emission.** Every web path writes `isolation: isolate` for these facts, as `data-exact-policy`, which adoption keeps.

**D4. Apple: `zPosition` carries a dense rank; `subviews` stay in tree order.**
- **Dense rank.** The kernel sends each node's rank whenever it changes, 0 included, encoded losslessly as an integer: twice the rank, so ½ is 1. Each parent then maps its children's distinct ranks, in order, to dense indices, with rank 0 at index 0. The setter writes `zPosition = index × 0.001`. Order is all Core Animation needs, so the depth under a `perspective` parent (`sublayerTransform.m34`) is a thousandth of a point per distinct rank among one parent's children (usually a few) and r3's §4.3 is gone. When the set of distinct ranks among a parent's children changes (rare), the parent re-runs its children's setters.
- **One setter.** It also writes the node's box-filter picture (`BoxFilter.swift:53-61`) and scroll-shadow mirror (`Shadow.swift:275`). `usedZIndex` is deleted.
- **Flat leaves.** Only a rank-0 node with no stacking fact may be a flat leaf. A rank change promotes or demotes it; runs never mix ranks; `position_type` is no longer inert for flattening (`Prepared.swift:57`).
- **One hit helper** for every override that walks node children:
  - `NodeView` and its scroll content;
  - `PlainView` (`ScrollViewIOS.swift:11`);
  - `GlassGroupView` and `GlassContent` (`GlassGroup.swift:195`, `:315`, `:332`);
  - `MaterialContent`, `GlassBackground`, `BlurBackground` (`NodeViewMac.swift:12-31`);
  - the clip holders (`BoxShadow.swift:316`);
  - the macOS document view;
  - the menu layers (`MenusMac.swift:308`, `MenusIOS.swift:43`).

  The helper:
  - returns children in reverse order when their `zPosition`s are all equal (one linear check, no cache) and stably sorted by `zPosition` otherwise;
  - includes flat-leaf layers: if a flat leaf is topmost at the point, the hit is its owner, as the web's hit on a leaf bubbles to the parent;
  - inside a canvas, sorts HUD children by rank within the HUD partition, above placed children (`NodeViewMac.swift:681`).
- **Transients.**
  - The Arrange lift is the topmost dense index under its parent, on every host. The web keeps `z-index: 2147483647` (`motion-glue.js:277`), Linux paints it last (`paint.rs:1264`), and authored `z-index` is clamped below it (§3.7).
  - An exit ghost is just under the lift: web `z-index: 2147483646` (it was 1); Apple the index below the lift, at the ghost's own place in `subviews`, with no `bringSubviewToFront` (`PresenceIOS.swift:29`, `PresenceMac.swift:30`).
  - While a ghost lives, its parent stacks on every host (§3.8): the web isolates it, and Apple sets its rank to ½ through the setter. Linux refuses exits (LLP 1063).
  - When a lift or ghost ends, the setter restores the rank.
- **Lossless `z-index`.** `css.rs` and the Apple style serializer write `z-index` as an integer, not through `f32` (`css.rs:545-559`, `host/apple/src/style.rs:327`).
- **The macOS default capture** (`AgentMac.swift:757`) composes a node as:
  1. its own layer contents;
  2. its replacement or mirror layers (filter picture, with the masked box omitted; shadow casters);
  3. its children in paint order.

  It keeps the existing `WKWebView`, GPU and canvas snapshot paths and their clip, transform and opacity grouping, and draws each child exactly once.

**D5. Linux sorts by (partition, rank, tree order).** Placed canvas children come first, by projective depth, as the web gives them negative indices by placement depth (`gpu-glue.js:190-205`). Then every other child, by rank, then tree order (stated explicitly, not relying on a stable sort). The Arrange lift is painted last. Hit-testing reads painted boxes in reverse, so it follows. `z-index` stays an `i32`.

**D6. The fixture checks paint, input and logical order separately.** It lives in `host/web/tests/paint-order/` as cases of plain markup, one file each.
- **The cases:**
  - every row of §2.5;
  - nested holders;
  - `each` copies (prepend, delete, reorder);
  - a region arm inserting and removing a `z` descendant;
  - bound `position`, `opacity` and `z-index`, including a sign change and a parent `display` change that makes `z` apply;
  - a flex/grid item with an authored 0 and with none;
  - an inapplicable `z-index`;
  - every D2 fact at a value that stacks and one that does not, identity transforms included;
  - every host-policy fact, including an authored override;
  - a flowing paragraph;
  - two roots;
  - a sticky header over `color`, `opacity` and `press-scale` ≠ 1 rows;
  - a layout-transition parent at rest, and its child mid-resize (§4.2);
  - an Arrange lift and an exit ghost beside large `z-index` values, including the clamp and a nested ghost;
  - `z-index` values beyond 2²⁴;
  - a flat leaf over a negative-rank control;
  - canvas HUD and placed children;
  - a box under a `perspective` parent;
  - a negative child against its parent's background and in-flow children.
- **Paint.** Every box is an opaque distinct colour. Each probe's pixel names the box painted there, and probes include points where only earlier boxes overlap. Pixels are read from:
  - Chrome on plain HTML, for bare CSS;
  - every web path (live, JS target, Rust and JS server render before adoption, adopted);
  - Linux;
  - the macOS default and window captures;
  - iOS.
- **Input.** `elementsFromPoint` on the web, Linux's hit test, `hitTest` on Apple.
- **Logical order.** On Apple, Tab order and accessibility elements stay in tree order.
- **Expectations.** Each case records bare CSS's answer and Exact's, naming the §3 or §4 item where they differ. `parity.mjs --paint` keeps its cases, with the nested-`z` expectation labelled §3.1, and its stale Linux note (`parity.mjs:173`) is corrected.

**D7. Apps.** Every repo app is screenshot before and after on the web, macOS and iOS. The iOS apps with flat-leaf lists and glass groups are also driven by taps. Every difference is intended or a bug, and the list goes in the landing commit.

## 6. Costs

- **Kernel.** Own facts, two potentials, an isolation bit and a rank per node, recomputed per dirty list and propagated while they change. No layout.
- **Server render.** One post-order pass and a side table per render, in both renderers.
- **Web.**
  - Plain followers of positioned siblings are no longer isolated.
  - Holders of `z` descendants, stacking-capable motion boxes, layout-transition parents and flowing paragraphs now are.
  - The net count depends on the app, and D7 records it. `paint.js` keeps potentials per element.
- **Apple.**
  - A rank per view, sent on change. Dense indices recomputed only when a parent's set of ranks changes.
  - One linear check per holder per hit.
  - Flat leaves are given up only for ranked nodes, and promotion and demotion churn only where ranks change.
  - The capture compositor is new code, and agent-only.
- **Linux.** A partitioned sort key per painted parent.
