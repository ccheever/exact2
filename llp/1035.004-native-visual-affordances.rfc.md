## Summary

An author who wants Back, Close, Compose, Add, Microphone or Send gets the
platform's own symbol on the platform that has one, a declared fallback
where none does, and never draws a chevron out of two rotated boxes. A
material or a presentation surface keeps the platform's appearance,
pressed state and accessibility, and the app paints nothing that competes
with it.

At the initial survey, Messages had 35 `clip-path` attributes — 20 inline `path()` literals
(12 distinct, 2,251 bytes) and 15 through five derives holding paths —
plus rotated-box chevrons for Back and Close, all beside 20
`backgroundMaterial` uses that already reach UIKit's glass and ultra-thin
materials (LLP 1001 §1). The duplicate sheet corner seam was the app and
UIKit painting one surface; host-owned dimming fixed it. The scroll-edge
effect appeared with a native label and not with a painted view. The
lesson is one rule: **a platform affordance is declared by its meaning
and rendered by the host that has it**, the way LLP 1021 presents a
menu-shaped popover as a `UIMenu` and paints it in agent mode.

Decisions: **a symbol is an `image` whose source is a role** (D1), **its
size, weight and colour are the node's font rows and `tint_color`** (D2),
**an unknown role is a compile refusal** (D3), **each host renders the role
its way, and the web's way is declared, not Apple's artwork** (D4),
**materials stay the two that landed and report their support** (D5),
**presentation chrome is the host's** (D6), and **the layout box is the
kernel's** (D7). Twelve roles are now integrated in the working tree; D4
records the evidence and remaining limits. This RFC is not fully implemented.

## 1. Motivation — what the app owns that the platform has

At that survey, `apps/messages/app.contract` authored the compose pencil as one `path()` of
several hundred characters on the New Message button (`:403`); the
search magnifier and microphone are two more (`:398`, `:401`); Back is two
3×14 boxes rotated ±45° (`:410-411`), Close two 2×20 boxes (`:415-416`,
`:420-421`); Send's arrow, the reply arrow, the bubble tails and the
person silhouette are paths; five derives (`personPath`, `laughPath`,
`bellPath`, `callPath`, `trashPath`, `:114-118`) exist to reuse them. The
record calls them "authored shapes, not SF Symbols; exact symbol geometry
remains part of the visual comparison" and lists "native symbols and glass
grouping" as unfinished. Every one of the six roles has an SF Symbol whose
weight, size and tint follow the surrounding text by design, an
accessibility name the control (not the glyph) should carry, and a web
equivalent the app must supply because HTML has no symbol element.

What already crosses the boundary correctly and is the model: `image`
is a measured leaf with an intrinsic size the host reports (LLP 1011 §1);
its source policy is the host's (`http(s)`, a path under the asset root,
nothing else — LLP 1011 §4); `backgroundMaterial` is a request for a
system material that UIKit fulfils with `UIVisualEffectView` and
`UIGlassEffect`, holding authored children in its `contentView` and
enabling the interactive response for a pressable node, while the web
approximates and other hosts leave it transparent (LLP 1001 §1, 1008 §9).

## 2. Decisions

### D1 — A symbol is an `image` whose source is a role

```
button press=back aria-label="Back to Messages" …
  image "symbol:back" font-size=17 font-weight=600
```

No new tag (the count stays ~15). The `symbol:` scheme joins LLP 1011
§4's source policy as the one scheme a host resolves without loading: the
role after the colon names an entry in the symbols section of
`kernel/tables/schema.json`. `kernel/build.rs` generates the compiler's
check (D3) and the host mappings (D4) from that declaration authority;
there is no separate symbol registry. The roles and their Apple names:

| role | SF Symbol | meaning |
|---|---|---|
| `back` | `chevron.backward` | leave this route |
| `close` | `xmark` | dismiss this surface |
| `compose` | `square.and.pencil` | start a new item |
| `add` | `plus` | add to this collection |
| `microphone` | `mic` | speak |
| `send` | `arrow.up` | submit this item |
| `search` | `magnifyingglass` | find in this collection |
| `copy` | `doc.on.doc` | copy this content |
| `select-text` | `selection.pin.in.out` | select this text |
| `more` | `ellipsis.circle` | show further actions |
| `delete` | `trash` | delete selected content |
| `forward` | `arrowshape.turn.up.right` | forward selected content |
| `home` | `house` | the app's first place |
| `person` | `person.crop.circle` | an account or profile |
| `messages` | `bubble.left.and.bubble.right` | conversations |
| `notifications` | `bell` | notifications |
| `settings` | `gearshape` | app settings |
| `repeat` | `repeat` | recurring work (added 2026-09-24 for the Crew port's Routines tab) |
| `activity` | `waveform.path.ecg` | what is happening now (the Crew port's Activity tab) |
| `bookmark` | `bookmark` | save this item for later (added 2026-09-25 for the list port) |
| `bookmark-fill` | `bookmark.fill` | this item is saved |
| `document` | `doc.text` | a document or attachment |
| `select` | `checkmark.circle` | choose this item; a count of chosen items |
| `select-fill` | `checkmark.circle.fill` | this item is chosen (a list's edit-mode selection) |
| `reorder` | `line.3.horizontal` | drag to reorder this item |
| `sort` | `arrow.up.arrow.down` | change this collection's order |
| `filter` | `slider.horizontal.3` | filter or adjust this collection |

A filled state is its own role named as Apple names it: `<role>-fill` is
exactly `<name>.fill`, and `<role>` must exist beside it (`kernel/build.rs`
refuses either half alone). Apple renders the `.fill` symbol; the browser
path of a `-fill` role is a filled silhouette (even-odd, so the check cut
out of `select-fill` is a subpath) instead of a stroke, and the web host
marks it `data-symbol-fill`. A state is a source change (`image (saved ?
"symbol:bookmark-fill" : "symbol:bookmark")`), not a style row: no host
has a fill flag to honour, and Apple's `.fill` artwork is a different
glyph, not the outline filled.

A role is portable meaning. [1035.004.000](1035.004.000-arbitrary-sf-symbols.rfc.md)
adds `symbol:sf/<name>` for an opaque OS name, literal or dynamic (including
empty), resolved directly on Apple and empty elsewhere. No catalog is bundled.
An `image` with a role carries no `label` of its
own; the accessible name belongs to the control around it (`aria-label`
on the button), and the image is decorative (`alt=""` on the web).

### D2 — Size, weight and colour are the node's font rows and `tint_color`

A symbol is glyph-like: its point size is the node's computed `font_size`
(1035.000 D1 — inherited, so a symbol inside a 17-point button is a
17-point symbol), its weight the computed `font_weight` (the CSS number
mapped to `UIImage.SymbolWeight` by the nearest of the nine), its colour
the node's `tint_color` (bit 89, initially `AccentColor`, the platform's
dynamic tint, since LLP 1095 stage 2; not inherited),
which takes a `light-dark()` pair like every colour row (LLP 1034). The
old unused tint row had been replaced by `caret-color`; this is a separate
schema declaration with an actual symbol consumer. Apple
builds `UIImage.SymbolConfiguration(pointSize:weight:)` from them; the
web's fallback follows the same three through CSS. A definite `width`/
`height` still wins, as on any image; without one the symbol's intrinsic
size enters through the existing `intrinsic` callback (LLP 1011 §1), so a
`button` with only a symbol sizes as a browser button with a glyph would.

### D3 — An unknown role is a compile refusal

The compiler already checks literal values against kernel rows (LLP 1006
§2, P1). A `symbol:` source whose role is not in the table is
`lower-attr-value` at compile time — `symbol "chevron" is not a role;
roles: back, close, …` — not a runtime fallback. A dynamic source (an
expression) that resolves to an unknown role at runtime paints the
declared box empty with a one-font-size square as its fallback intrinsic size.
Existing portable-role diagnostics remain; unavailable SF names are silent
and inspectable through `layout` (`native.symbol.found` and `reason`). No host guesses a browser icon
from an authored Apple name; only the generated mapping supplies one.

### D4 — Each host renders the role its way; the web's way is declared

- **Apple** (iOS and macOS): `UIImage(systemName:)` / `NSImage(systemSymbolName:)`
  with D2's configuration, presented inside the existing image leaf;
  `tint_color` as the template colour; the platform's appearance,
  accessibility and Dynamic Type response where the point size is not
  fixed by a `font-size` (it is, in v1, LLP 1019).
- **Web**: the declared SVG paths generated from the schema into the host, each
  drawn to match the role’s *meaning* at a 24-unit box, rendered as
  a CSS `mask-image` on the `<img>`'s box with `background-color` from
  `tint_color`, so colour, size and `light-dark()` follow CSS. The web
  never impersonates Apple's artwork; a reviewer comparing the two hosts
  compares meaning and box, not glyph geometry (1035.000 D8).
- **Linux**: the same declared stroked paths rendered by the painter when a
  consumer runs there; until then the
  declared box paints nothing and LLP 1015 §7 names the gap.

**Image-path prototype (Codex, 2026-09-10):** a temporary copy of the current
iOS `NodeView` compares seven configured symbols with `UIImageView`, at
17/22/28 points, weights 100/400/500/600/900, in natural and 44-point square
boxes with `object-fit: contain` (210 cases). Natural-size drawing differs
by at most one channel level; scaling through the existing bitmap draw
path differs visibly in some fixed boxes (maximum RGBA RMS 30.15/255).
A noninteractive, decorative `UIImageView` inside the same Exact leaf
matches the reference pixels in all 210 cases. This supports delegating
symbol rendering to that native child while the kernel retains its box.
The temporary browser mask proof passes 42 size/weight/appearance cases;
natural sizes follow the configured font, definite boxes win, and the
button retains its label and hit box. Light/dark captures were inspected.
These are renderer feasibility proofs; the integration evidence below is
separate (`/tmp/messages-symbol-image-proof/verification.json`).

**Role integration (Codex, 2026-09-10, working tree):** all seven roles now
flow from `schema.json` through generated mappings, literal compiler refusal,
Apple native image leaves and browser masks. The new tint row is independent
of caret colour. Apple images receive computed inherited font rows; queued
intrinsic reports require both source generation and actual view identity.
Unknown dynamic roles paint empty and log; changing/clearing/restoring a source
updates the same leaf. Native symbol children are decorative and noninteractive.
`layout <node>` identifies the actual `UIImageView` / `NSImageView`, generated
name, intrinsic dimensions and frame.

The compiler corpus and Apple/web host tests pass. Temporary native/browser
fixtures pass natural and fixed boxes, font size/weight changes, source swaps,
unknown/cleared/restored sources and symbol-button actions; iOS/browser captures
include content-box padding, cover, none and scale-down. AppKit geometry and
button actions pass, but both capture methods returned transparent images;
AppKit paint remains unverified. Production Messages passes eight public-XCTest
taps under platform timing: Compose/Cancel, Add/Close, ordinary Send, Back and
dark Compose/Cancel. Taps inside the Compose/Send glyphs activate their owning
controls; ordinary Send sends once and keeps the keyboard. These checks do not
retest first-Send handoff or establish exact native glyph sizing.

Messages replaces 14 occurrences with the seven roles: seven path literals
and 14 logical nodes leave, `clip-path` attributes drop 39 → 32, and source
lines drop 890 → 876 against the immediate pre-integration source. Fieldnotes
uses Add and Close on iOS and the web; New Note increments its version and
focuses its title through the unchanged action. The notebook remains unavailable or opening in those agent drives; they
prove controls, not note persistence. Browser light/dark
captures and iOS light/dark Messages captures were inspected. Full evidence and
remaining limits: `/tmp/messages-symbol-integration/verification.json`.
A pinned native Compose crop measures its Close ink at 50×50 pixels; the
initial 20/500 replacement measured 46×46. A 24-configuration UIKit comparison
selects 22/400; the rebuilt Messages sheet now measures 50×50 and the full
physical control drive still passes. Colour-normalized, translation-aligned
coverage error falls from 0.00707 to 0.00147. One pixel of placement and the

pixel equality (`/tmp/messages-symbol-sizing/`, `close-glyph-final.json` in the

**Message-action roles (Codex, 2026-09-11, working tree):** native Messages
accessibility identifies Copy, Select and More as `doc.on.doc`,

**Selection-toolbar roles (Codex, 2026-09-11, working tree):** Delete and

Four public-XCTest iOS Simulator cases and four browser cases pass, each host

The web's paths are host assets, not app assets: an app declares a role,

### D5 — Materials stay the two that landed and report their support

`backgroundMaterial` keeps `ultra-thin` and `glass` with the mappings LLP
1001 §1 and 1008 §9 record. Before a third material is named, the two are
inspected: 1035.002 D5's `applied` reports the effect class the host
mounted (`UIGlassEffect`, `UIVisualEffectView(.systemUltraThinMaterial)`,
the CSS approximation, or `unsupported`), so a support gap is
distinguishable from a flat-colour implementation in one read. A material
on a host that has none paints nothing extra (as today) and reports
`unsupported`; an app that needs a floor sets `background-color` beside
it, as it would on the web under `@supports not (backdrop-filter: …)`.
No property is added per sampled blur or shadow constant; no glass
grouping until a consumer's fixture shows the seam.

**AppKit slice (Codex, 2026-09-15):** the existing two values now mount regular
`NSGlassEffectView` on macOS 26 for `glass`, or `NSVisualEffectView(.popover)` for
`ultra-thin` and the older-macOS glass fallback. `layout <node>` reports the actual
mounted class under the existing `native.effect` observation (`backgroundMaterial`
is a prop, not a style row with an `applied` field); an unknown value reports
`unsupported`. This is a material implementation, not native sidebar/toolbar
projection, a third material, or acceptance of the remaining Draft decisions.

**Palette/material probe (Codex, 2026-09-11):** regular UIKit glass on a
saved Messages backdrop approaches the native palette: the sampled upper band
has 0.06/0.10 mean RGB-level error in dark/light. A 50% underlay or tint worsens
that band; ultra-thin blur also fails the light comparison. Adding ordinary
labels leaves the action card's blank background byte-identical. The same public
fixture renders essentially identically on the two reference/Exact Simulators.
These findings do not establish full palette or action-card parity.

A stock context menu supplies the native 250×188 card and 42-point action rows,
but places it above this probe's source and retains different backdrop content.
Its public `UIVisualEffectView.effect` is nil, so that property cannot identify
its material. The third UIKit candidate corrects the fixture's window appearance:
a dark content controller alone left the separately presented menu light.
No tint, underlay, third material or host change is adopted from this probe.

The direct Exact comparison remains unverified. Its three drive rounds exposed
an incorrect 375-versus-375.1 assertion, then a 62-point safe-area offset, then
confirmed that adding navigation does not remove that offset. The missing
existing setting is `viewport-fit="cover"`; further fixture retries stop at the
repository limit. Saved offset-adjusted crops are diagnostic, not a renderer
parity claim. Source, public UIKit captures, failures and measurements:
`/tmp/messages-glass-palette/verification.json`.

### D6 — Presentation chrome is the host's

UIKit owns a sheet's outer surface, corner radius and dimming (landed:
the seam went with the app's backdrop); it owns the navigation bar, its
large title, the collapsing inset and the scroll-edge effect (1035.001
D9 — a real bar with a real title, because the edge effect needs a native
element, not a proxy or a hand-tuned blur). Authored content never paints
a competing backdrop inside a host surface. Editing stays with the native
editor (1035.001 D7): a reusable visual shell never replaces a text editor
with painted text and a hidden focus target.

**Action intent (Codex, 2026-09-10):** Messages' Block/Discard colour miss
earns back LLP 1021 §5's destructive role. The existing swipe property becomes
`destructive`, shared by UIKit swipe, menu and confirmation presentation. The
app supplies intent; UIKit chooses the native style. Physical checks deliberately
oppose the authored colour and role and verify the role wins. This repairs the
action text. The subsequent contact-row CSS correction removes Block's anchor
error; glass and browser placement remain unfinished (LLP 1021 D2).

**Native button probe (Codex, 2026-09-10, not integrated):** stock
`UIButton.Configuration.glass()` transforms a black foreground to approximately
25/255 in light mode and its default foreground to 243/255 in dark mode;
a black `UIImageView` inside the current `UIGlassEffect` stays black. This is
control presentation, not a missing colour constant in the app. The configuration
also defaults to large symbol scale; explicit medium preserves the image's
configured intrinsic dimensions. The public API permits foreground transforms
([Apple](https://developer.apple.com/documentation/uikit/uibuttonconfiguration/baseforegroundcolor)).

An isolated copy of current Messages promotes centered, natural-size, single-symbol
circular glass buttons to actual `UIButton`s, retaining kernel boxes and the
existing focus/dispatch rule. Eight public-XCTest actions pass, including ordinary
Send with the keyboard retained and Add's return to the authored rotating image.
The Close foreground and horizontal placement approach the native reference, but
translation-aligned RGB error worsens: 0.00156 for production, 0.00297 for the
candidate. Twelve size/weight combinations in the third calibration still prefer
22/400 and do not beat production. No button projection lands; the three
calibration rounds are stopped. Glyph rasterization, broader CSS shapes, held
cancellation/retirement and truthful inspection of the delegated image remain
unresolved. Evidence: `/tmp/messages-glass-controls/` and
`/tmp/messages-glass-button-candidate/verification.json`.

**Confirmation dimming probe (Codex, 2026-09-11, not integrated):** physical
opening/outside cancellation in three standalone UIKit variants distinguishes
native tint, control configuration and disabled appearance. All descendants
report `.dimmed` while the confirmation is open, consistent with Apple's
[`tintAdjustmentMode`](https://developer.apple.com/documentation/uikit/uiview/tintadjustmentmode-swift.property)
contract, but their visible output differs. Representative gray glyph pixels
(light/dark, 0–255) under the prompt are:

| Presentation | Light | Dark |
|---|---:|---:|
| Native Messages Close reference | 167 | 113 |
| Glass UIButton, enabled (also after configuration update) | 25 | 243 |
| Glass plus template UIImageView / custom draw using native tint | 51 | 208 |
| Standalone toolbar item, enabled | 71 | 198 |
| Glass UIButton, disabled | 207 | 71 |
| Standalone toolbar item, disabled | 212 | 68 |

Fixed-colour drawing does not dim; blocking `isUserInteractionEnabled` also
leaves the enabled glyph unchanged. Cancellation restores the initial control
state. These isolated surfaces do not match the native background exactly and
the table is not a full pixel comparison; the first variant's theme-switch
capture is transient, so its dark baseline uses the settled cancellation frame.
No tested policy reproduces Messages, and neither replacing the material nor
setting app `disabled` is justified by this evidence. The three-variant probe
stops here without reopening the earlier button-projection calibration. Source,
16 physical taps, 18 captures, metadata and pixels:
`/tmp/messages-confirmation-dimming/verification.json`.

### D7 — The layout box is the kernel's; hit target, visual bounds and baseline are three things

The kernel lays out the `image`; the host reports the symbol's intrinsic
size; the control's hit target is the control's box, never the glyph's
ink (a 17-point chevron in a 44-point button is a 44-point target); the
symbol aligns in a line box as a replaced element does (CSS: on the
baseline, bottom edge). A symbol never shrinks a usable button.

## 3. Verification and removal

Verify the seven roles in the existing Messages screens — Back on the
conversation and details routes, Close on the reply thread and selection,
Compose on the inbox, Add and Microphone on the composer, Send — and
compare: normal, pressed and disabled states; light and dark; the authored
font size and weight; the accessible names (VoiceOver reads the button,
not the glyph); real tap targets through 1035.003. Include an ordinary
launch (platform timing) and the browser fallback, and record the OS and
device configuration because native artwork changes between releases.

Replace the corresponding authored shapes only when the native result and
the fallback are both verified. Count what leaves: the six roles remove
the two rotated-box chevrons (four nodes), the compose, microphone
(twice) and send paths (four literals), and the search magnifier if
`search` is admitted as a seventh role for the inbox pill; the bubble
tails, the reply arrow, the person silhouette and the five derives are
*not* symbols and stay until 1035.005 D5 gives artwork a home. Confirm a
second consumer uses the boundary without a Messages-specific prop:
Fieldnotes' Add and Close, Caltrain's Back if 1035.001 D9 gives it a bar.
The benefit is less app-owned platform geometry and a smaller, more
legible component (1035.005 §3 measures it), not a longer symbol list.

## 4. Landing order

1. **Slice 1 (this implementer):** the table, the scheme in the compiler
   check, `tint_color` wired on `image`, Apple's symbol rendering with D2's
   configuration, the seven web masks and the Linux gap declared. The landing
   uses existing corpus/host test files and temporary driven fixtures, with no
   new tracked check or script; D4 records their coverage and gaps. Messages and
   Fieldnotes replacements are in the same working tree.
2. **Slice 2:** remaining native pixel/accessibility verification and D5's
   `applied` through 1035.002.
3. **Later, on evidence:** platform-name access, if a consumer shows a
   role table cannot serve it; bar items by role (1035.001 D9).

## 5. What this deliberately does not add

A component library, a theme framework, a wrapper per UIKit class, a
second asset registry, a core cargo feature, a symbol name space that
bypasses the table, exact Tapback artwork or participant presentation, a
third material before the two are inspected, Dynamic Type scaling (font
sizes are authored, LLP 1019).

## 6. Open questions

- Should `font-weight` map to the nine symbol weights by nearest number,
  or should only the CSS keywords `normal`/`bold` be honoured on a symbol?
  Leaning: nearest of nine; it is what the text already does with a
  variable font.
- Is `search` a role (an inbox pill on every platform) or Messages-
  specific? Leaning: a role — Caltrain has a search field too.

## 7. Acceptance questions for Charlie

1. Roles only in v1, platform names never without a role row — accept?
2. The web fallback is host glue (six SVGs in `glue.js`), not an app asset
   — accept, or should a role be declared as an app asset through the
   asset row so a brand can override it?

**Decided (Charlie, 2026-09-10, on the recommendations):** roles only in v1;
a platform name never without a role row; the web fallback is host glue,
not an app asset; `search` is the seventh role from the start; `font-weight`
maps to the nearest of the nine symbol weights. Slice 1 is implemented from
this date.
