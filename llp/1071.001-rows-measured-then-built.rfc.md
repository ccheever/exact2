# LLP 1071.001: The JS target's rows — measure less, then build cheaper

**Type:** RFC
**Status:** Draft r1, 2026-10-28. Not yet reviewed. §8 lists what Charlie decides.
**Systems:** the web JS target's runtime (`host/web-js/rt.js`: `h`, `P`, `S` and `css`, the `each` region; `host/web-js/list.js`; `host/web-js/paint.js`; `host/web-js/symbols.js`), the virtualized list's browser half (`host/web/collection-glue.js`), the JS target's compiler (`host/web-js/src/emit.rs`, `rows.rs`), and the shootout's profiler (`bench/web-shootout/scrollprof.mjs`, to land with LLP 1152 stage 0)
**Author:** Claude (Fable 5.1) for Charlie Cheever
**Date:** 2026-10-28
**Implementer:** unassigned. §6's stages are sized for one lane each.
**Related:** LLP 1152.000 (the research this follows: the two Krausest engines read against the JS target, and §2.1's profile of the bounded feed scrolling); LLP 1152 (the shootout, whose feed and Krausest lanes are this RFC's measure); LLP 1071 (the JS target) and LLP 1071.000 (rows at scale); LLP 1010 §6, LLP 1050.000 §6 and LLP 1070 (the virtualized list's contract: reports, measurements, anchoring, the fill); LLP 1048.000 and 1048.001 (adoption of rendered rows); LLP 1079 (`perf` by plan site); LLP 1083.000 (paint order); LLP 1011 §3 (tinted rasters); `bench/dioxus/README.md` (the last web standings)

## Summary

A profile of the bounded heavy-list feed scrolling on the production JS target (LLP
1152.000 §2.1) found that the first milliseconds of a scroll are not spent building rows.
They are spent measuring rows that did not move, scanning stylesheets per image, reading
attribute names per element, and stringifying snapshots per commit. Those are part A:
eight small changes to the collection glue and the runtime's per-element bookkeeping, each
with a predicted movement against the same profile, most of them a day's work. Part B is
what the two engines nearest vanilla on Krausest's table do that the JS target does not:
a row as one `cloneNode` of a compiled prototype, bindings specialised by the compiler
with no DOM read on the update path, and keyed lists that skip unchanged rows. Part B is
the answer for construction-bound pages (a feed page that mounts hundreds of rows at once,
the Krausest entry) and for window fills at high scroll speeds, where the JS target
spends about 100 µs per element all-in. Part A comes first because it is cheaper, its
numbers exist, and it is where the shootout's scroll columns will be decided.

Nothing here changes what an author writes or what the web standard says a page does.
The runner's semantics (commits, the journal, refusals) and the list's contract (reports,
anchoring, the fill limit) are kept; what changes is how many DOM calls each of them costs.

## 1. What was measured

LLP 1152.000 §2.1 has the table. The shape, at 6,000 px/s for 3 s on a 120 Hz Mac:

| | per 3 s | per frame |
|---|---|---|
| main-thread task ms (script, style, layout) | 486 (222, 23, 36) | 1.3 |
| `getBoundingClientRect` + `getClientRects` | 10,599 | 28 |
| `getComputedStyle`, `document.querySelectorAll` | 736, 748 | 2, 2 |
| elements built; `setProperty` + `removeProperty`; `getAttributeNames` | 1,725; 12,665; 1,725 | 4.6; 34; 4.6 |

The rect reads do not scale with speed (5,668 + 4,266 at 24,000 px/s), because they are
one per mounted row per report. Construction does: the 24,000 px/s run built 4,393 more
elements for 435 ms more task time, about 100 µs per element all-in. At rest the page
costs about 30 ms of task time per second, nearly all in V8's `(program)` bucket, which
is a phone's browser-CPU column waiting to be explained.

Self time by source, 6,000 px/s: the collection glue's measurement and scroll handling
about 146 ms (30% of sampled script); the symbol tint lookup 28 ms; the paint-order flush
and facts 13 ms; the DOM calls of construction about 20 ms; GC 14 ms; `(program)` 184 ms.

The agent's `perf` by plan site during one 6,000 px wheel scroll (28 rows built) counted
about 170 binding evaluations per row, 150 of them the paragraph runs' seven style
bindings each (LLP 1152.000 §2.1). A row is 170 effects created and disposed before its
first DOM call, which is the cost B2 and B5 address.

## 2. Part A: measure less

Each item names the code, the cost in the profile, the change, the predicted movement
against the same run, and what must stay true. Items are independent; each lands alone
with its before-and-after from `scrollprof.mjs`.

**A1. Rows measured by their observer, not per frame.** `collection-glue.js` `report`
(lines 256 to 266) runs `getClientRects` and `getBoundingClientRect` on every mounted
row every report, about 28 reads per frame. Each row already has a `ResizeObserver`
entry (`s.observed`), so a row's size is known from its last notification and changes
only when the observer fires (fonts, images, a wrap). Change: keep each row's size from
its observer and from its first measurement; a report measures only rows whose size is
unknown or whose observer fired since the last report, and derives the rest. The port's
rect is read once per report. Predicted: rect reads from ~28 per frame to ~1 at steady
state; the glue's share of script roughly halved. Must stay true: the anchoring and
correction rules of LLP 1010 §6, which depend on the sizes the report carries; a row that
changes size without a notification is the risk, and a row whose observer has not yet
fired after mount is measured directly. This is the one part A item with design risk, so
it lands behind the conformance harness and the Dioxus series, not before.

**A2. The scroll handler reads one thing.** `scrollChanged` (the profile's `K`, 57 ms)
reads the port's offset, then its scroll size and client size to detect a clamp, per
scroll event; the size reads force layout inside the handler. Change: the handler reads
the offset only and queues; clamp detection moves to the report, which already reads the
port once. Predicted: `K`'s self time to a few ms. Must stay true: a clamp at the end of
the list is still detected before the next report's fill decision.

**A3. The port found once.** `portOf` (`F`, 33 ms) walks the list's ancestors with
`getComputedStyle` on every `commit`. Change: cache the port on the list's state and
re-find it only when the element is detached and re-attached, or on a `restyled`
notification. Predicted: `F` to zero during a scroll.

**A4. Snapshots compared without stringify.** `list.js` line 866 stringifies every
collection's snapshot at every commit to decide whether to call `commit`; lines 293, 307
and 655 do the same per list. Change: a revision counter bumped where a snapshot's
inputs change, compared as a number. Predicted: `eo` (3 ms) and its allocations gone,
and fewer `commit` calls, which also helps A3.

**A5. The tint decided at build time.** `symbols.js` `tinted` scans every rule of every
stylesheet for each class of each image built (`declares`, 28 ms, 6% of task). The
classes are the compiler's output (`element.rs` `host_css`), so the compiler knows which
carry `--exact-tint`. Change: the compiler marks a tinted image's static class set with an
attribute (or a bit in the facts of A6), and `template` reads it; an inline
`--exact-tint` on the element itself stays a runtime check. Predicted: 28 ms to under
1 ms. Must stay true: a tint set by a mode boundary or a bound colour (LLP 1121 stage 9)
still decides at runtime through `inked`, which does not scan stylesheets.

**A6. Paint facts carried, not read back.** `paint.js` `facts(e)` reads
`getAttributeNames` once per element built to OR the `data-exact-f*` attributes into
bits, and `paintFlush` walks from each dirtied element to the root to bucket it by
depth. Change: `h` is told the facts as a number (the compiler already writes them) and
stores them on the element; the depth is the parent's stored depth plus one. Predicted:
`getAttributeNames` from one per element to zero, the flush's walk gone, about 13 ms.

**A7. Symbol images tracked, not queried.** `symbols.js` lines 169 and 170 run two
document-wide `querySelectorAll` after every commit. Change: `h` registers an image
whose attributes name a symbol source or an `app:` source at creation, and the commit
pass walks that set. Predicted: 748 queries per 3 s to zero, about 11 ms.

**A8. One write per inline style value.** `css()` (rt.js line 844) removes a property
before setting it, then reads it back to detect a refused value, so each value costs
three style operations and a read; the profile counts 12,665 operations per 3 s.
Change: the compiler knows the row's value kind (a typed length, a colour from the
colour map, an enum), and for a kind that cannot be refused it emits a setter that sets
once with no read-back; the general path keeps the check. Predicted: style operations
roughly halved. Must stay true: a refused value still journals and falls to `unset`.

**A9. Rest explained.** The 30 ms per second at rest is a stage 0 question for the
shootout's phone legs (LLP 1152 §4.6): find what runs (a frame loop kept alive, a
timer, image work) and stop it when nothing changes.

Predicted together, at 6,000 px/s for 3 s: script from 222 ms toward about 100 ms, task
from 486 ms toward about 330 ms, with style and layout unchanged. The prediction is what
the first lane checks before the second starts; if A1 alone does not move the rect reads
and the glue's share as predicted, the profile was read wrong and the rest waits.

## 3. Part B: build cheaper

What `re` and Thane do (LLP 1152.000 §1) and the JS target does not, for the workloads
where construction is the cost: a page mounting hundreds of rows at once, the Krausest
entry, and window fills at the speeds where 100 µs per element is the frame budget.

**B1. A row is one clone.** The compiler emits, per row template, a `<template>` with the
row's static markup (the same markup the render host writes for a page) and a slot list:
for each dynamic text, attribute, inline style row and region anchor, the path from the
row's root as sibling hops. A row instance is `cloneNode(true)` and one walk of the slot
list; `Paint?.list` is told the row once. Conditional regions inside a row keep their
comment anchors in the prototype, which is what adoption already expects of a rendered
row (LLP 1048.001), so adoption and fresh construction become the same walk over
different DOM. Static attributes, static text and static classes cost nothing per
instance. Per-instance work left: the slot walk and the bindings. Predicted: construction
from about 14 `createElement` and 40 attribute and style writes per row to one clone and
the dynamic writes only; `re` traced the difference between indexed child access and
sibling hops at 0.8 µs per row, which is the scale of each DOM call saved per node.

**B2. Bindings specialised by the compiler.** `P(e, name, f)` is one effect whose body
is a ladder of about fifteen cases on every update, guarded by a DOM read. The compiler
knows the name, so it emits per-kind setters: `Pt` keeps the slot's `Text` node and
writes `.data` when the closure's last value differs; `Pa` writes a plain attribute
guarded by a cached last value; `Pb` toggles a boolean attribute; `P` stays for the
names that need the ladder (`src`, `href`, `sandbox`, `value`, media, `data-exact-`
paint facts, the anchor's `target`). No DOM read on the update path. Predicted: an
update's cost becomes the write itself; the live feed's once-a-second relative times and
reaction bumps stop paying the ladder and the `textContent` serialisation.

**B3. Keyed lists that skip unchanged rows.** The `each` region keys every item on every
change (a string concatenation per row), rebuilds its map and runs the LIS. Change: keep
the normalised key on the row record; walk by position first and skip rows whose item is
the same object; fast paths for a prefix append, a one-row prepend (a stream's insert),
one removal and a two-row swap; the map rebuilt and the LIS run only on the general
path. Predicted: a live insert at the top of a 10,000-row list stops keying 10,000 items.

**B5. Enumerated style bindings lowered to classes.** The feed's text runs bind seven
style properties, each a pure function of the run's kind (`r.s == "code" ? … : …`), so
each run instance creates seven effects and seven inline style writes. Where every
binding on a node depends on one enum-valued field and each arm is a literal, the
compiler can lower them to one class per enum value and one binding that picks the
class, which is what an author would have written in CSS. Predicted: the run's cost from
eight effects and seven style writes to one effect and one attribute. Must stay true:
the lowered classes are the author's values, so the web oracle sees the same computed
style; a binding with a non-literal arm stays an effect.

**B4. Delegated events for list rows**, only if the Krausest entry or the whole-feed arm
shows listener count or setup time as a cost: one listener per event type on the list's
parent for the events rows declare, with the same `:disabled` and inert checks the
per-element handlers make.

B1 and B2 are compiler changes in `emit.rs` with new runtime helpers; B3 is `rt.js`.
Their measure is the shootout's Krausest lane (create 1,000 and 10,000 rows, partial
update, swap, remove) and Conduit's feed page, where construction is the whole cost, and
the feed at 24,000 px/s, where it is a third.

## 4. What does not change

- What the author writes, and what a bare node does: layout stays CSS and the web stays
  the parity oracle (LLP 1115, `CLAUDE.md`). No new tag or property comes from this RFC;
  a `table` tag for the Krausest entry is LLP 1152 D3's question, decided on its own.
- The list's contract: reports, measurements, anchoring, the fill limit and the agent's
  settle (LLP 1010 §6, 1050.000 §6, 1070). A1 changes when a size is read, not what a
  report says.
- The runner's semantics: commits, refusals, the journal, replayed presses. B2's setters
  run inside the same effects; B3's fast paths produce the same DOM order the general
  path does.
- Fairness: none of this is a bench-only flag (LLP 1152 §7 rule 7). Every change ships
  in the production build or not at all.

## 5. Checks

Each lane runs, before landing: the JS target's conformance (`host/web-js/conform.mjs
--strict`, the async lane's step, run locally for the lane); `cargo test -p exact-web-js
--bins`; the web-core ceilings (`bun scripts/metrics.mjs`); the smoke
(`bun scripts/smoke.mjs web`); and the profile of §1 before and after on the same
build, with the predicted movement stated in the commit. Part A's A1 also reruns
`bench/dioxus/web/series.sh` for the bounded arm (blank samples, progress, late
callbacks), since it touches what a report measures. Part B's lanes run the Krausest
harness on the Exact entry once it exists, or Conduit's feed page under
`host/web-js/bench.mjs` until then.

compiler and are sequenced after the shootout's first round so their measure exists.

## 7. What this costs and risks

- A1 is the only part A item that touches a contract with proofs behind it (the
  collection's anchoring). It is staged last and gated on the series.
- B1 changes the shape of every generated row function. The dev loop's compile hint and
  hoisted constants (LLP 1071 "Generated code at scale") are unaffected in principle,
  but a prototype per row template adds a `<template>` per template to the module, which
  the size ceilings will see; the bytes saved per instance call should exceed it on any
  app with a list.
- B2 multiplies runtime entry points. The ladder stays for the names that need it, so
  the risk is a name routed to the wrong setter; the conformance run is the check.
- None of this moves the native hosts, whose rows the runner builds (`runner/src/instance/collection`).

## 8. Decisions for Charlie

- **D1, order.** Part A before part B, as §6 stages it. The alternative is B1 first,
  which is the larger structural change and the one the Krausest table rewards; it would
  leave the feed's scroll where the profile found it for another month.
- **D2, where the tint and paint facts live.** A5 and A6 move two runtime lookups to the
  compiler's output. The alternative is runtime caches keyed by class list, which keep
  the compiler unchanged and keep the first lookup's cost per class. Recommended: the
  compiler, since it already writes both facts.
- **D3, the refused-value check.** A8 drops the read-back for value kinds the compiler
  can prove. The alternative keeps every inline write at three operations and a read for
  the journal's sake. Recommended: drop it where proven; the journal still sees every
  refusal the general path finds.
- **D4, A1's gate.** Land A1 behind the conformance harness and the Dioxus series
  (recommended), or behind the shootout's first round, which is later and broader.
- **D5, part B's measure.** The Krausest entry, which needs LLP 1152 D3 answered, or
  Conduit's feed page alone. Recommended: both, with Conduit's page as the gate until an
  entry exists.

## 9. Open questions

- Whether a row's observer notification arrives before the next report in every case A1
  relies on (fonts, decoded images, a wrap after a cross-size change), or whether some
  rows need a measurement on the report after mount regardless.
- What runs at rest (A9), and whether it is the JS target's or the page's data module.
- How B1's prototype interacts with a row whose template branches at its root (a region
  as the first node), which today gets comment anchors: the prototype holds the anchors,
  and the region's arms are their own prototypes.
- Whether B3's one-row prepend path is enough for a stream that inserts several rows per
  tick, or the prefix path should run both ways.
