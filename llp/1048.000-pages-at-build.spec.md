## Summary

Phase 1 of LLP 1048, in two parts.

- **1a: documents at build.**
  - Every in-repo app's routes render at build into `dist/` as real HTML, with titles, descriptions, real links, a sitemap and a 404.
  - Sources that can't answer at build render their placeholders.
  - The runtime loads when the page is idle, builds its own DOM, and swaps it in once, with the same content.
  - There is no server and no Hermes.
- **1b: documents per request.**
  - A serve mode of the Linux host renders Interview's public question, post and profile pages per request, locally. It uses the async render host, with Hermes for Interview's TypeScript sources.
  - Each page carries a checkpoint of its answers. The runtime boots from it and adopts the DOM when its canonical document matches.
  - Documents carry cache headers a CDN can use later.

## 1. The document

A document is the DOM projection of a settled checkpoint, before browser layout
(LLP 1048 D1).

- **Settled.** The runner has booted at the route's location, and every request
  the document's bindings depend on has answered, failed, or hit its deadline
  (D9).
- **Projected by the live host's rules.** One Rust module produces the document
  from the same tag, attribute and property decisions the live host makes (D1).
- **Before browser layout.** These are named and excluded:
  - font loading;
  - symbol sizing from computed styles;
  - focus;
  - scrolling;
  - context positioning;
  - windows chosen from scrollport geometry.
- **Meaning** comes from roles and markup lowered to HTML (D1): heading levels,
  Markdown's blocks, links.
- **Stacked presentations.** Entries that a later one covers are marked in the
  document exactly as the live host marks them. If the live host leaves them in
  the accessibility tree, both change together: it is one projection.
- **Virtualized collections** render their items in full, up to a bound, in a
  public document. Interview uses none. This waits for the first app that needs
  it and is coordinated with the list-engine work, which owns
  `runner/src/instance/collection`.
- **Canvas** nodes render their fallback content.

## 2. Decisions

**D1 — The safe document projection.** `exact_web::document` sits beside
`Host::create` (`host/web/src/host.rs` ~874). It reuses `tag_for`, `props_for`
and `css.rs`, and moves into Rust the rules `glue.js` applies imperatively
(`applyProps` ~387, create ~597):

- the URL allowlist for every navigating attribute (landed as one policy,
  `871e2631`);
- `value` and `checked` as attributes on inputs;
- boolean attributes (`disabled`, `inert`, `hidden`);
- `textarea` content as text;
- the canvas wrapper;
- Markdown markup, expanded by one Rust function shared with the live host.
  Today that is `renderMarkup` (`host/web/navigation.js` ~1420), which emits
  spans and `<br>`. The shared function emits Markdown's blocks as their HTML
  elements — paragraphs, headings, lists, quotes, code blocks — styled to look
  as they do today. This changes the live page too, so it lands in 1b and is
  coordinated with the Markdown work in progress;
- HTML escaping;
- content models, where the parser would otherwise restructure output: for
  example, a paragraph holds only inline content.

Elements keep their `data-view` ids. Output that the HTML parser would
restructure is a render error that names the node, never silently repaired.

*As built (1a, `82cf7be4`):* `host/web/src/document.rs` is a child module of
`host.rs`, so it calls `tag_for`, `props_for` and `host_css` themselves; each
`glue.js` rule it restates sits beside the rule it mirrors. The URL rule reads
a scheme as the URL parser does and refuses an http(s) authority the parser
can't read (IDNA aside). Until 1b, Markdown is `renderMarkup`'s spans, restated.
The parser-undone cases refused so far: a link in a link, a button in a button,
a NUL. An app's render entry is `exact_render::main` (D9; Caltrain's
`caltrain-render`: `--plan`, `--viewport`, locations; one JSON line each). The
parity check is `host/web/tests/document.test.mjs`: Chrome parses the served
page with JavaScript off and compares it with the live DOM once the runtime is
ready. On Caltrain `/` there is no difference.

**D2 — Enumeration.** A parameterized route lists its pages for build through a
build-stage source named on the route (LLP 1048.003 D5, `pages=`). Unlisted
locations are rendered per request by the server (D10), or fall through to
`404.html` on a static host. For a per-request route, the same `pages=` source
lists its entries in the `sitemap.xml` the server serves. A route without one
isn't in the sitemap.

**D3 — Head.** Each document's `<head>` holds:
- `<title>`, `description`, `canonical`, OpenGraph and Twitter tags, `robots`,
  and structured data (JSON-LD), from the active `head` element
  (LLP 1048.003 D1);
- `<html lang>` from the manifest (landed, `44f8643c`);
- `@font-face` declarations and font preloads (LLP 1019);
- the envelope `<link rel=alternate>` (LLP 1023).

Nothing preloads the glue or the wasm. They would compete with the page's own
images and fonts, and activation waits for idle anyway (D6). Today `build.mjs`
writes the head by string replacement (~147–151); that moves into the renderer.

*As built (1a):* `Document::page_head` (`host/web/src/page.rs`) writes the
title (the manifest's name when no head sets one), the viewport meta the glue
would write, the description, canonical, robots, OpenGraph and Twitter tags —
canonical, image and `og:url` absolute against `app.origin`, and dropped when
not navigable — and the plan's faces as `@font-face` rules with a preload each.
`build.mjs` keeps the shell's `lang`, manifest, icon, theme colour and envelope
link, swaps its `<title>` and viewport meta for the renderer's head, and drops
the shell's wasm and `navigation.js` preloads, failing the build if the shell
no longer has those places. Not yet: JSON-LD (1b, with its first consumer).

**D4 — The page viewport.** Content that branches on `exactViewport()` renders
at the manifest's `web.pageViewport`: by default 390×844, the bake's
`LINT_VIEWPORT`. That makes the document mobile-first. At a different width, the
runtime's first tree differs, so it renders fresh (D6), and parity is claimed at
that viewport only. Width variants left the plan in r3 (LLP 1048.003 D3).

**D5 — The clock.** A checkpoint's time is the render time. On the client the
clock continues from the device, and content that reads the clock updates after
boot as an ordinary update. A fresh runner's clock starts at zero today
(`runner/src/runner.rs` ~602); the renderer sets it explicitly. Nothing keys a
cache on the clock (D11).

**D6 — The checkpoint, the boot and adoption.**

- **The checkpoint** is the state the document was projected from. It is not the
  dev loop's `Carried` (`runner/src/runner/carry.rs`), which is reload state. It
  holds:
  - **answers:** every resource the document read, with its source, arguments,
    logic identity, the answer and a freshness stamp;
  - **pending:** the resources still pending at the deadline, which render
    placeholders;
  - **the router location and the render time;**
  - never a store.
- **Encoding.** The checkpoint is encoded canonically: names as strings, values
  in the plan's value encoding (`plan/src/value.rs`). It is embedded as inert
  data (`<script type="application/vnd.exact.checkpoint">`). Inside it, `<`, `>`
  and `&` are written `<`, `>` and `&`, so user text can never
  close the element or open a comment. Structured data is escaped the same way.
- **Checkpoint answers are their own runner input.**
  `boot_checkpoint(checkpoint, launch, width, height)` seeds each resource's
  `ResourceState` from the checkpoint, outside the store, the way `boot_carrying`
  seeds carried state (`runner/src/runner.rs` ~321).
  - Kept answers (`runner/src/runner/kept.rs`) are not the vehicle. They seed
    only resources that read the store, cap an answer at 8 KiB, and are asked
    again at `data_ready`.
  - The runtime treats a checkpoint answer as an answer it already has. It
    isn't asked again at boot or when the module loads, only when its
    arguments or inputs change, as for any answer.
  - Failure stays data (LLP 1016 D4). A later refresh that fails reaches the
    source's `parse`, and the app decides what the page shows.
- **The digest.** SHA-256 over:
  - the plan digest;
  - the launch location;
  - the checkpoint bytes;
  - the canonical document: the parsed DOM's normalized serialization, excluding
    runtime incarnation ids such as reorder runtimes
    (`host/web/src/reorder_drag.rs:12`).

  The preimage excludes the digest's own field. The renderer writes the digest
  beside the checkpoint. The runtime computes it from its own first batch,
  projected the same way, before touching the DOM.
- **Adoption (1b).** On a digest match:
  - **DOM:** for each `create` in the first batch, the runtime finds
    `[data-view=<id>]` through a one-pass index. The first batch's props, style
    and children are already there and aren't reapplied.
  - **Host state:** everything `applyProps` and `attach` initialize (`glue.js`
    ~387, ~431, ~496) is restored separately from DOM mutation — listeners,
    authored inertness, autofocus, scroll-follow state, list and context
    bookkeeping, and readiness.
  - **Later batches** apply normally.
- **Rendering fresh (1a, and any mismatch).** The runtime keeps the document on
  screen until its own first tree has settled, then replaces the document once.
  The reader never sees less than the server sent. The agent's `state` reports
  `adopted: true | false`, and a mismatch journals the first differing node.
- **Activation.**
  - The runtime loads when the page is idle, or at the first pointer or key
    interaction, whichever comes first. "Idle" means `requestIdleCallback` after
    `load`, or a short timeout where that is missing.
  - A press before adoption is recorded against its view id and replayed once,
    after adoption. Other early events wait for phase 2's semantic replay
    (LLP 1048.001).
  - The document never marks controls disabled while activation is pending.
  - A page that needs no runtime (LLP 1048 D5) loads none.
  - **The document boot is its own host module.** That covers rendering fresh,
    the digest and adoption. It is loaded after paint through `glue.js`'s
    `loadAfterPaint`, as `rust-glue.js` is, and only on pages that carry a
    checkpoint. `scripts/boot.mjs` allows two modules before first pixel,
    `glue.js` and `navigation.js`, and no dynamic `import()` in them. Both stay
    as they are.
- **Afterwards.** The device's store (sign-in, drafts) and clock apply as
  ordinary updates. A checkpoint never overrides the store.

In 1a, a document rendered at build has no answers from sources that can't run
at build. Its checkpoint holds the location, the time and the pending set, and
the runtime renders fresh. Adoption lands with 1b.

*As built (1a):* a page with a checkpoint loads `host/web/document-glue.js`
through `loadAfterPaint`; `glue.js` holds only call sites. The runtime starts at
`requestIdleCallback` after `load` (200 ms without it) or at the first
`pointerdown` or `keydown`. Its batches are held while the document stays on
screen; `activateData` (data ready) replaces the document once and applies them.
A press on the document is recorded as its chain of view ids, with each
element's tag and text, from the moment `glue.js` evaluates (the glue keeps
clicks until the module loads). It replays a task after readiness, on the
innermost element that takes a press, and only if that element's tag and text
still match; a dropped press is journaled. Links keep their default, and the
glue's click gate stays open while the document holds. The agent's `state`
reports `adopted: false`, and `window.title`. Verified by
`host/web/tests/document.test.mjs`: parity with the served document, no frame
with an empty `#exact-root`, one replacement, the wasm fetched after `load`, and
a press made before the runtime replayed once.

*As built (1b, step 5):* `exact_runner::Checkpoint` holds the location, the
render time, the logic identity (`DataSource::revision`), each answer's source,
arguments and value, and what was still pending. The render time stands for
every answer's freshness: they come from one render. `Runner::document_checkpoint`
takes it from a render. The runner's own facts (delivery, the viewport, surface
records) are never in it: the runtime answers those itself.

`Runner::boot_checkpoint` seeds an answer when its name and source match, the
same logic answered it, and its value still fits. It seeds outside the store,
as `boot_carrying` seeds carried state, and the clock starts at the render time.
A seeded answer isn't asked at boot or at `data_ready`, only when its arguments
or inputs change.

The render had no store. So when the device's store holds the app's own
entries, a store-reading resource is asked again: at boot if its source can
answer, otherwise at `data_ready`. It shows the rendered answer until then. The
journal says how many answers were taken.

Verified by `contract/cli/tests/it/checkpoint.rs`. The page's checkpoint still
carries only the location, the time and the pending set. Its answers join the
page with the web runtime that boots from them (step 7), so no page carries
bytes nothing reads.

*As built (1b, step 7):* the page's checkpoint carries `logic` and `answers`:
one list of (name, source, arguments, answer) records in the plan's value
encoding, as base64. Base64 never holds `<`, `>` or `&`. The renderer writes
the digest as the checkpoint element's `data-digest` (`exact_web::document::digest`).
Its location term is the location the document was rendered at, which the
checkpoint also carries, not the runtime's launch. The runtime's only input of
its own is then its first tree, so a query the app doesn't read, or `404.html`
served at any path, still adopts an identical document. That is a reading of
"the launch location" for Charlie to confirm. Adopting two identical trees is
never wrong.

The glue hands the wasm the digest and the checkpoint before boot
(`exact_checkpoint`). `Host::boot_checkpoint` boots the runner from the
checkpoint, projects its own first tree, and opens the first batch with an
`adopt` op. `document-glue.js` reads the op when data is ready:
- **Adopt.** It indexes the document's `[data-view]` elements once, and the
  first batch's creates bind them instead of creating elements, so listeners,
  views, lists and the rest of the host state attach as on any create. Setting
  what is already there is skipped for attributes and text, so an adopted
  iframe or video doesn't reload. Roots already in place aren't reinserted.
  The props and styles already there are set again, with no visible change.
- **Otherwise** it replaces the document once and journals the first view whose
  id or tag differs, or "the same N views; a property or text differs".

The agent's `state` reports `adopted`. A checkpoint that doesn't read boots as
a page without one, journaled. The document's projection now runs in the wasm:
Caltrain's `app.wasm` grows from 1,257 to 1,285 KiB (526 to 539 KiB gzip),
and its page from 44 to 52 KB with the answers.

Verified by `host/web/tests/document.test.mjs` in Chrome:
- Caltrain's page is adopted: every one of its 277 views is the served element,
  with no frame of an empty root, no swap, and the checkpoint's 7 answers
  taken, not asked.
- A tampered digest is replaced once and journaled.
- A press made before the runtime starts still replays.

And by `host/web/tests/it/page.rs`: the checkpoint round-trips, including user
text; the verdicts hold (another launch of the same tree adopts, another
document doesn't); an unreadable checkpoint is journaled. The web agent over
`dist/` reports `adopted: true` and drives taps and typing on the adopted page.

**D7 — `dist/`.**
- `dist/index.html` for `/` and `dist/<location>/index.html` for every other
  rendered location.
- `dist/404.html`, `dist/sitemap.xml` (absolute, against the manifest's origin)
  and `dist/robots.txt`.
- Content-hashed assets with precompressed siblings.
- A static host serves these as they are.

*As built (1a):* the build runs the app's render entry (`<app>-render
--build`, when `web/src/bin/<app>-render.rs` exists) over the plan the wasm
carries. `build_locations` lists every route declared `render=build` and, when
the not-found route is, `/404.html` (refused if a pattern matches it). Each
document goes to `<location>/index.html` (`/` replaces the shell's
`index.html`), or `404.html`, with its checkpoint — 1a's `{location, time,
pending}`, `<`, `>` and `&` as JSON escapes. `sitemap.xml` lists the documents
that aren't `noindex` and is written only with an origin. `robots.txt` is
neutral (`User-agent: *`, `Allow: /`, and `Sitemap:` with an origin); the policy
for AI crawlers waits for real hosting. An app that renders nothing gets none of
these files. Not yet: content-hashed assets with precompressed siblings.

*Since (1b):* the render entry lives in the app's Linux crate (D9). The pages
come whole from `exact_render::page`, and `dist/shell.html` keeps the shell.
The wasm exports `exact_build_locations`, so an app with no `render=build`
route builds and runs no render entry ("documents: none declared"). A render
entry that is missing when routes are declared is named in the build's line.

**D8 — Links.** Links in documents are real `<a href>`. Once the runtime is up,
same-origin links to a declared route are followed in place (landed,
`1e7016a0`).

**D9 — The async render host.** A Rust library used by the build and by the
server:
- **Sources run as they do natively:** Hermes for TypeScript modules (LLP 1027),
  Rust sources directly, and requests through the native executor core (the
  grant-checked executor, `host/linux/src/executor.rs` and
  `host/apple/src/executor_core.rs`, not the dev plan fetcher).
- **Settling.** The host pumps continuations and fulfils requests until the
  document is settled (§1).
- **The completion rule ignores** ordinary timers (`task … every`), mutations
  and actions; no action runs during a render.
- **Deadline.** Each render has one (default 2 s). At the deadline, still-pending
  resources render their placeholders with `pending(x)` true and are listed in
  the checkpoint, and the runtime asks them again. The response is a 503 (D11).
- **Cancellation.** Requests are cancelled when the client disconnects or the
  render is abandoned.
- **Anonymous renders only in phase 1.** Sources get no cookies, no store, and
  no request context except the URL. Personal renders are LLP 1048.002.
- **Every source runs** (LLP 1048 D3), in that environment. The render host
  refuses device capabilities: SQLite, kept secrets, and grants the server
  doesn't hold. A refused source keeps its placeholder, and the client asks it
  after adoption.
- **Where it lives.** The render host is its own native crate over `exact-web`'s
  projection, the executor core (by `#[path]`, as the Linux host includes it)
  and Hermes. `exact-web`, which builds to wasm, gains no target-specific
  dependencies.
- **Placeholders, never refusals.** A resource whose source cannot answer at the
  current stage takes its placeholder, with `pending(x)` true. The placeholder is
  declared (LLP 1048.003 D6) or is its shape's empty value. Boot never refuses
  because of it; today it does (`runner/src/runner/settlement.rs` ~380).

*As built (1b, step 6):* `host/render` (`exact-render`) is the render host.
`render(plan, data, viewport, location, site, deadline)` boots a fresh runner
with the app's own source wrapped as `Anonymous`. Its grants are the app's
`net.fetch` lines only: no kept secrets (the store is empty and refuses a
write), no files, no SQLite, no key-value storage. A module that loads after
first pixel on a device loads before the render settles. What it would be asked
at `data_ready` it is asked there.

`Executor` is the executor core, included by `#[path]`, with a condition
variable for its wake. `settle` hands out requests and dispatches continuations
on the render's thread. It fulfils replies until nothing is in flight but what
the environment refused, or until the deadline.

These are refused there: a storage or surface request, a fetch the grants
don't cover (the core answers `Refused`), and a request over the core's limits.
The resource keeps its placeholder, and the checkpoint lists it. A network
failure is the source's data (LLP 1016 D4). Dropping the executor at the
deadline aborts what is in flight; a running continuation finishes on its
worker, unobserved. The clock stays where boot put it: the render time is set
with adoption (step 7), when the runtime boots at the checkpoint's time.

`exact_render::main` is the build's render entry, moved from
`exact_web::document`. It takes `--deadline <ms>`, and each JSON line gains
`settled`, with status 503 when the deadline passed. An app's entry lives
beside its native data source, in its Linux crate (Caltrain's
`caltrain-linux --bin caltrain-render`). `host/web/build.mjs` runs it and names
the documents that reached their deadline. Its status is D11's:
- the head's `status` (404, 410, 503);
- 404 for any location the router sends to the not-found route
  (`exact_web::document::route_at`), not only the listed `/404.html`;
- 503 when the deadline passed.

Verified by `host/render/tests/it/main.rs`: a continuation's answer is waited
for; at the deadline the placeholder shows and is listed as pending; storage
and an ungranted fetch keep their placeholders; the store is empty; a real
fetch runs through the core from a server on this machine; a refused
connection is shaped by the source.

**D10 — The server: a serve mode of the Linux host.**
- **Where.** The Linux host binary gains a serve mode rather than a new host. It
  already has:
  - the executor core (`host/linux/src/executor.rs`, sharing
    `host/apple/src/executor_core.rs`);
  - grant-checked fetches;
  - Hermes loading;
  - delivery (`host/linux/src/delivery.rs`);
  - the agent server.

  If the serve mode would put the painter or windowing on the server's startup
  path, the implementer uses a separate binary over the same crates and records
  why here.

  *Decided (1b):* the server is a separate binary, an app's `<app>-render`
  with a serve mode (step 8). The Linux host binary brings its painter up at
  startup, and the render entry has neither painter nor window. It runs the
  same crates: the executor core, grant-checked fetches, and the app's own data
  source with its Hermes module.
- **Local.** It binds loopback (LLP 1048 §9.6). Moving to a CDN or a hosting
  provider needs configuration, not code.
- **Isolation.** Each request gets a fresh runner and a fresh module realm.
  Interview's module holds mutable replica and identity globals (`app.ts` ~22),
  so a realm is reused only with a proven reset.
- **Bounded:**
  - concurrent renders, with a queue and a 503 when it's full;
  - output bytes;
  - runner work (the core lane's per-commit envelope);
  - source time, with a deadline that interrupts a running call. Hermes' call
    budget is checked only after the call returns (`js/src/lib.rs` ~660), so the
    server needs an interrupting watchdog.
- **Outbound fetches:**
  - only to the app's granted origins;
  - redirects stay within granted origins;
  - no private-network addresses unless granted (SSRF);
  - never cookies or credentials in an anonymous render.
- **Operations.**
  - A health endpoint.
  - Per-render metrics, as log lines: render time, the module graph loaded, and
    source calls and bytes.
  - Panic containment: a failed render answers 500, and the server keeps
    serving.
  - Restarts drain in-flight renders.
  - Version skew:
    - assets are content-addressed and kept for pages still open;
    - each document names its plan digest;
    - a checkpoint from another plan renders fresh.
- **Trust.** Module code is trusted application code, not sandboxed
  (`README.md` ~275). The server runs one app, the one it was built for.

**D11 — The server's HTTP contract.**
- **200** with the document.
- **404** when the route resolves to the router's not-found route, or when the
  active `head` declares `status=404` (LLP 1048.003 D1). Interview's not-found
  view declares it for missing and non-public items alike, so a private item's
  existence isn't revealed. The body is the rendered not-found document. A
  `status=410` answers 410 the same way.
- **503 with `Retry-After`** in three cases: the server is overloaded; a render
  reaches its deadline with the page's content still pending; or the active
  `head` declares `status=503` because its view shows failed data. The body is the
  document with its placeholders:
  - a browser shows it, and the runtime finishes it;
  - a crawler returns later;
  - no cache keeps it.
- **500** with a static error page when a render fails.
- **HEAD** is supported.
- **Canonical URLs.**
  - Paths are normalized, and trailing slashes follow one policy.
  - The route table canonicalizes the query.
  - Canonical URLs are built from the configured origin, never from request
    headers (`Host`, `X-Forwarded-*`), so they can't be poisoned.
- **Caching.**
  - **Anonymous documents:** `Cache-Control: public, max-age=0, s-maxage=<route
    lifetime>, stale-while-revalidate=<window>`, plus an `ETag`. They also carry
    surrogate keys (`Surrogate-Key` and `Cache-Tag`) naming the source and
    arguments of each answer the page used, so a purge by key refreshes every
    page that showed a record.
  - **Errors:** 404s are cacheable for a short lifetime; 500s and 503s are
    `no-store`.
  - **Assets** are `immutable`.
  - **The server stores no documents.** Locally every request renders; a shared
    cache in front does the storing (LLP 1048 D11).
- **Representations.** The envelope (LLP 1023) has its own URL, the one in
  `<link rel=alternate>`. The HTML URL doesn't negotiate on `Accept` and never
  sends `Vary: Accept`; today `serve.mjs`'s `readWebRequest` does (~591).
- **Security headers:**
  - a strict `Content-Security-Policy`: scripts only from the app's own origin
    or by hash, since the only inline elements are inert data;
  - `X-Content-Type-Options: nosniff`;
  - `Referrer-Policy: strict-origin-when-cross-origin`.
- **Robots.** The head's `robots` is also sent as `X-Robots-Tag`. Interview's
  search pages are `noindex`.
- **Unknown locations** get the not-found document with a 404, never the SPA
  fallback's 200 (`serve.mjs` ~591, ~639).

## 4. Verification

- **1a.** Every in-repo app's rendered locations are served from a plain static
  file server with JavaScript off: titles, links, the 404 and the sitemap. The
  runtime's takeover changes nothing the parity check can see.
- **The acceptance case (1b).** An anonymous Interview question URL, from the
  local server, with deliberately delayed data (after LLP 1048 §10's Interview
  work). It must deliver:
  - useful HTML and head metadata with JavaScript off;
  - real links;
  - a 404 for a missing or non-public question;
  - a 503 with `Retry-After` for a render past its deadline;
  - a 500 page for a failed render;
  - the caching headers of D11;
  - adoption (`adopted: true`), with no content lost when the runtime starts.

  Then a signed-in reader whose replica is cold: the public content stays until
  their own view is ready.
- **Parity** (async lane). For every app and rendered location, parse the served
  HTML and compare it with the live host's document at that URL in headless
  Chrome, normalizing tags, attributes, text and inline style. A difference names
  the view id. Parsing catches parser repairs that batch comparisons can't.
- **Counterexamples**, each a test:
  - a reply after the deadline;
  - a network failure at boot, which changes nothing the server sent;
  - a store read after an await (an anonymous render shows the logged-out
    state);
  - user text containing `</script>`, `<!--` and `]]>`, in the checkpoint and
    in the structured data;
  - repeated renders in one process, which must produce equal documents (the
    reorder runtime counter differs);
  - malformed and non-canonical URLs;
  - an empty `each`;
  - an overloaded server;
  - a checkpoint from another plan, which renders fresh.
- **Measurements** at 150 ms RTT and 6 Mbit/s, before and after:
  - time to first byte;
  - first contentful paint;
  - layout shift;
  - document and checkpoint bytes;
  - time to adoption;
  - on the server, per render: render time, the module graph loaded, and the
    source calls made.
- **Rules:**
  - `bun scripts/boot.mjs` stays green;
  - no app JavaScript runs before first pixel;
  - `dist/` works from a plain static file server;
  - the dev loop stays client-rendered and unchanged.
