## Summary

Phase 1 of LLP 1048. An app's routes become real HTML documents — rendered at
build for static routes, and per request by a native Rust server for
data-driven ones. Documents carry titles, descriptions and real links, and
survive readers without JavaScript. When the runtime starts, it boots **seeded**
with the page's answers, so its first tree equals the document. It then replaces
the DOM once with the same content; adoption, which keeps the DOM, comes in
phase 2.

The first consumer is Interview's public question, post and profile pages (LLP
1048 §10).

## 1. The document

A document is the DOM projection of a settled checkpoint, before browser layout
(LLP 1048 D1).

- **Settled.** The runner has booted at the route's location, and every request
  the document's bindings depend on has answered, failed, or hit its deadline
  (D9).
- **Projected by the live host's rules.** One Rust module produces the document
  from the same tag, attribute and property decisions the live host makes (D1).
- **Before browser layout.** These are named and excluded:
  - font loading;
  - symbol sizing from computed styles;
  - focus;
  - scrolling;
  - context positioning;
  - windows chosen from scrollport geometry.
- **Virtualized collections** render their items in full, up to a bound, in a
  public document. Interview uses none. This waits for the first app that needs
  it and is coordinated with the list-engine work, which owns
  `runner/src/instance/collection`.
- **Canvas** nodes render their fallback content.

## 2. Decisions

**D1 — The safe document projection.** `exact_web::document` sits beside
`Host::create` (`host/web/src/host.rs` ~874). It reuses `tag_for`, `props_for`
and `css.rs`, and moves into Rust the rules `glue.js` applies imperatively
(`applyProps` ~387, create ~597):

- the URL allowlist for every navigating attribute (landed as one policy,
  `871e2631`);
- `value` and `checked` as attributes on inputs;
- boolean attributes (`disabled`, `inert`, `hidden`);
- `textarea` content as text;
- the canvas wrapper;
- Markdown markup expanded to spans and anchors (`renderMarkup`, moved to Rust
  and shared with the live host);
- HTML escaping;
- the content models of semantic elements (LLP 1048.003 D2) — for example, a
  `p` holds only inline runs.

Elements keep their `data-view` ids. Output that the HTML parser would
restructure is a render error that names the node, never silently repaired.

**D2 — Enumeration.** A parameterized route lists its pages for build through a
build-stage source named on the route (LLP 1048.003 D5, `pages=`). Unlisted
locations are rendered per request by the server (D9), or fall through to
`404.html` on a static host.

**D3 — Head.** Each document's `<head>` holds:
- `<title>`, `description`, `canonical`, OpenGraph and Twitter tags, and
  `robots`, from the active `head` element (LLP 1048.003 D1);
- `<html lang>` from the manifest;
- `@font-face` declarations and font preloads (LLP 1019);
- the envelope `<link rel=alternate>` (LLP 1023);
- `modulepreload`/`preload` for the glue and the wasm.

`build.mjs` writes the head today by string replacement (~147–151); that moves
into the renderer.

**D4 — The page viewport.** Width variants (LLP 1048.003 D3, in phase 1) become
CSS `@media` rules, so a document is right at every width. Content that branches
on `exactViewport()` renders at the manifest's `web.pageViewport` (default
390×844, the bake's `LINT_VIEWPORT`) and is corrected when the runtime starts.
Interview moves its tabs/rail switch to width variants (LLP 1048 §10.9).

**D5 — The clock.** A checkpoint's time is the render time. On the client the
clock continues from the device, and content that reads the clock updates after
boot as an ordinary update. A fresh runner's clock starts at zero today
(`runner/src/runner.rs` ~602); the renderer sets it explicitly.

**D6 — The seeded boot (phase 1).**
- **The page carries its answers.** Every resource answer the document used is
  embedded as inert data (`<script type="application/vnd.exact.answers">`),
  with its source, arguments and logic identity, plus the router location and
  the time. It carries no store and nothing private (LLP 1048 D3).
- **The runtime boots seeded.** The answers enter the runner through the
  kept-answers path (`runner/src/runner/kept.rs`), which already shows kept
  answers in the first frame before the logic module is ready and re-asks them
  when it is. So the runtime's first tree equals the document even though the
  TypeScript module loads after first pixel (`glue.js` ~1463). The glue then
  replaces the DOM once.
- **Never less than the server.** If seeding is refused (a logic identity or
  plan mismatch), the glue keeps the server document until the runtime's own
  tree has settled, then swaps. The reader never sees less than the server sent.
- **Afterwards.** The device's own store (sign-in, drafts) applies after boot as
  an ordinary update.

**D7 — `dist/`.**
- `dist/index.html` for `/` and `dist/<location>/index.html` for every other
  rendered location.
- `dist/404.html`, `dist/sitemap.xml` (absolute, against the manifest's origin)
  and `dist/robots.txt`.
- Content-hashed assets with precompressed siblings.
- A static host serves these as they are.

**D8 — Links.** Links in documents are real `<a href>`. The web lane's
same-origin interception routes them in the app once the runtime is up.

**D9 — The async render host.** A Rust library used by the build and by the
server:
- **Sources run as they do natively:** Hermes for TypeScript modules (LLP 1027),
  Rust sources directly, and requests through the native executor core (the
  grant-checked executor, `host/linux/src/executor.rs` and
  `host/apple/src/executor_core.rs`, not the dev plan fetcher).
- **Settling.** The host pumps continuations and fulfils requests until the
  document is settled (§1).
- **The completion rule ignores** ordinary timers (`task … every`), mutations
  and actions; no action runs during a render.
- **Deadline.** Each render has one (default 2 s). At the deadline, still-pending
  resources render their placeholders with `pending(x)` true, and the client
  asks again.
- **Cancellation.** Requests are cancelled when the client disconnects or the
  render is abandoned.
- **Phase 1 renders public data only.** Sources get no request context, no
  cookies and an empty store.

**D10 — The server: isolation and limits.**
- **Isolation.** Each request gets a fresh runner and a fresh module realm.
  Interview's module holds mutable replica and identity globals (`app.ts` ~22),
  so a realm is reused only with a proven reset.
- **Bounded:**
  - concurrent renders, with a queue and 503 when full;
  - output bytes;
  - runner work (the core lane's per-commit envelope);
  - source time, with a deadline that interrupts a running call. Hermes' call
    budget is checked only after the call returns (`js/src/lib.rs` ~660), so the
    server needs an interrupting watchdog.
- **Outbound fetches:**
  - only to the app's granted origins;
  - redirects stay within granted origins;
  - no private-network addresses unless granted (SSRF);
  - no cookies or credentials forwarded in phase 1.
- **Trust.** Module code is trusted application code, not sandboxed
  (`README.md` ~275). The server runs one app, the one it was built for.

**D11 — The server's HTTP contract.**
- **200** with the document.
- **404** when the route resolves to the router's not-found route, or a public
  source reports its item missing (a typed not-found answer). The body is the
  rendered not-found document.
- **500** with a static error page when a render fails. **503** when overloaded.
  **HEAD** is supported.
- **Canonical URLs.** Paths are normalized, trailing slashes follow one policy,
  and the query is canonicalized by the route table. Canonical URLs are built
  from the configured origin, never from request headers (`Host`,
  `X-Forwarded-*`), so they can't be poisoned.
- **Phase 1 caching.** Documents are `Cache-Control: no-store`; assets are
  `immutable`.
- **Unknown locations.** A request that matches no route gets the not-found
  document with a 404 — never the SPA fallback's 200 (`serve.mjs` ~591, ~639).

## 3. Not in phase 1

- Adoption (keeping the DOM), activation policies, event replay and navigation
  data: LLP 1048.001.
- Holes, cache policies, streaming, the edge and server-only artifacts: LLP
  1048.002.
- Media features beyond width, and required placeholders: LLP 1048.003 part B.

## 4. Verification

- **The acceptance case:** an anonymous Interview question URL with deliberately
  delayed data (after LLP 1048 §10's Interview work). It must deliver:
  - useful HTML and head metadata with JavaScript off;
  - real links;
  - a 404 for a missing question and a 5xx page for a failed render;
  - no content lost when the runtime starts.
- **Parity** (async lane): for every app and rendered location, parse the served
  HTML and compare it with the live host's document at that URL in headless
  Chrome (normalized tags, attributes, text, inline style; a difference names the
  view id). Parsing catches parser repairs that batch comparisons can't.
- **Counterexamples**, each a test:
  - a reply after the deadline;
  - a store read after an await (it must render the logged-out state);
  - repeated renders in one process, which must produce equal documents (the
    reorder runtime counter differs);
  - malformed and non-canonical URLs;
  - an empty `each`;
  - an overloaded server.
- **Measurements** at 150 ms RTT and 6 Mbit/s, before and after: time to first
  byte, first contentful paint, layout shift, document and answer bytes. Also the
  server's render time per page.
- **Rules:** `bun scripts/boot.mjs` stays green; no app JavaScript runs before
  first pixel; `dist/` works from a plain static file server.
