## 0. Summary

Until 2026-10-23 Windows was a host because of two consumers: standalone Skirmish (LLP
1015.000) and Windows Desk. `rules/DEFERRED.md` admitted nothing past them: "General
Windows control parity remains behind these two consumers." LLP 1115.000 D17 says what an
app shows there in the meantime, by Charlie's ruling: "build web look until someone builds
native ones." So Windows draws the neutral web look, and its IME, UI Automation and native
controls "need an owner".

This document is that owner's plan. It answers three questions:

1. **Should Exact keep painting on Windows, or present through a Windows toolkit?** Keep
   painting (D1, D2). Windows has no single toolkit that is both the system's and current:
   Win32's controls are always present and keep the look of an older Windows; WinUI 3 is
   the current design but ships as a library beside the app and is awkward from Rust.
   Windows itself mixes the two. Many of the most used Windows apps draw their own
   controls (VS Code and every Electron app; Teams, in WebView2), and Microsoft's React
   Native for Windows draws through Composition and hosts XAML only as islands. A person who
   knows Windows does not notice who drew a button. They notice the things the operating
   system owns.
2. **What does Exact take from Windows itself?** The window frame and its backdrop (DWM),
   the system font, the person's settings (theme, accent, contrast, text size, animations),
   text input through the IME, scrolling, the keyboard, the system's own dialogs, and UI
   Automation for Narrator (D3 to D11).
3. **What is painted, and against what?** Fluent 2 as WinUI 3 draws it, measured against a
   hand-built WinUI 3 app on the same Windows 11 build (D12, D13).

Charlie admitted Windows as a host for general apps on 2026-10-23 (D0), with Shelf and
Excord its first consumers, and answered §5 the same day.

## 1. What is there today

Read from `origin/main` at `fade920ee5`. Nothing below was run on Windows for this document.

**Default amended (Charlie, 2026-11-01; LLP 1149 D12):** Windows apps now
use ink's DirectX 11 composition path when the manifest names no painter.
`host.windows.painter: "cpu"` keeps the CPU painter and `softbuffer`;
`EXACT_PAINTER` overrides both. The survey below describes the earlier host.

**The window** (`host/windows/src/window.rs`, 653 lines) is a winit 0.30 window with
winit's default decorations: the system's title bar, light whatever the theme. It runs the
shared presenter from `host/linux` (`exact_linux::Presenter`). A frame is either the CPU
painter's, copied pixel by pixel into a `softbuffer` surface, or the GPU module's, presented
through its own swap chain on the window's HWND (`Presenter::window_frame`). It forwards
focus, occlusion, the pointer, the wheel and keys; Xbox pads are polled through XInput.

**What it does not do**, by reading the code:

| Area | Today | A hand-built WinUI 3 app on Windows 11 |
|---|---|---|
| Look | the neutral web look (D17): the role table's neutral column, the `neutral` metrics | Fluent 2: WinUI's theme resources and control templates |
| Colour | fixed; light and dark exist in the table but nothing reports the system's theme | the app's light or dark mode, the system accent and its shades, contrast themes |
| Type | `system-ui` and `sans-serif` resolve to **Arial**: without fontconfig the generic sans is the default `Arial` (`text/fonts.rs`, `Generics::default`), and Segoe UI is last in the fallback list (`text/catalog.rs`, `sans_family`) | Segoe UI Variable on Windows 11, Segoe UI on Windows 10, at the person's text size |
| Window frame | a light system title bar over the app's own first row | the title bar in the app's theme, Mica behind the window, often the app's content in the title bar |
| Settings | none reaches the app: the runner's `Preferences` are never set by this host | theme, accent, contrast, text scale, "Animation effects", "Transparency effects" |
| Text input | `hardware_key` with winit's logical key text; no IME composition, no candidate window placement | IME composition in place, the candidate window at the caret, the touch keyboard, dictation (Win+H) |
| Scrolling | wheel deltas (a line is 40 px), no inertia of its own | precision touchpad and touch panning with inertia; thin scroll bars that widen on hover |
| Menus and dialogs | `alertdialog` painted in the window (LLP 1115.000 D13.4); no context menu | Fluent flyouts that may leave the window; `ContentDialog`; the system's file dialogs |
| Accessibility | no tree: nothing leaves the process (LLP 1114.008) | a UI Automation tree Narrator reads |
| Out of the app | the app's folders (`picker_windows.rs`); files dragged in are refused (`QUEUE.md`) | clipboard, links, the share sheet, drag and drop, the system's file dialogs |
| Install and update | a folder: the host refuses an update store (`host/windows/src/window.rs:89`), and `scripts/deploy.mjs` names no Windows platform | an installer, updates, and an identity to receive shares |

`apps/windows-desk` shows the other road: an app-local presenter that maps Contract's nodes
onto real HWND controls (`EDIT`, `LISTBOX`, a combo box, common dialogs, menus with
accelerators). Its README says it "does not establish full control parity for the general
Windows host". It is the best evidence of what Win32's own controls look like under an Exact
app today: correct in behaviour, and visibly of an older Windows.

## 2. Decisions

### D0 — Windows is a host for general apps (admitted)

Charlie admitted it on 2026-10-23: "We are no longer deferring Windows. We are going full
speed ahead on it right now." `rules/DEFERRED.md`'s Windows bullet records it in his words,
as Android's admission of 2026-10-07 is recorded.

1. **Two consumers from S1.** `apps/shelf`, the recipe app whose screens Android's S1 used,
   for Fluent's controls; and `apps/excord`, the Discord client, for a desktop window: panes
   that scroll on their own, a long transcript, and a growing composer typed through an IME.
   Excord has a Windows crate and reached its fixture's gateway on the Windows box
   (`3f88621a7`); neither app's `app.json` has a Windows window, so S0 adds both. More apps
   follow without a new admission; `apps/agents` follows the menu bar (D10.6).
2. **Implementer:** Claude (Opus 5.5) lanes, S0 from 2026-10-23.
3. **The floor is Windows 11 build 22621 or later on x64**, the build
   `DWMWA_SYSTEMBACKDROP_TYPE` needs. Windows 10 runs what it can; ARM64 is compiled by the
   hourly tier and qualified when there is an ARM64 machine (§4).

### D1 — What "the platform's" means on Windows

On the Mac the system's controls are AppKit's views, so Exact uses them. Windows has no
equivalent: Win32's common controls are part of the system and keep the look of an older
Windows; WinUI 3 is Microsoft's current design and a library an app ships. Windows
itself mixes the two, and many of its most used apps draw their own (VS Code and every
Electron app; Teams, in WebView2). Microsoft's React Native for Windows renders its components
through `Microsoft.UI.Composition` and hosts XAML only as islands. A person who knows Windows
therefore does not notice that a button was painted. They notice:

- the window: its title bar, caption buttons, Snap Layouts, backdrop and corners;
- the system font and how it is rendered, and the person's text size;
- the theme, the accent and contrast themes, and the animation and transparency settings;
- text input: the IME's composition and candidates, the touch keyboard, dictation;
- scrolling: touchpad and touch inertia, the scroll bar;
- the keyboard: Tab, the focus visual, Alt and access keys, F10, Shift+F10 and the Menu key;
- the system's own dialogs (files, colours, printing) and the share sheet;
- Narrator, and anything else that reads UI Automation.

**Proposed.**

1. **The reference** is a hand-built WinUI 3 app (Windows App SDK, C#) on the same Windows 11
   build: its controls as the WinUI 3 Gallery shows them, in the system's theme and accent.
   Each stage that paints a control names the WinUI version it matched.
2. **Exact uses everything in the list above and never imitates it.**
3. **Painting a Fluent control is the default, not a rule.** A control is the system's or
   WinUI's only where painting cannot match the reference at a cost worth paying, decided per
   control and recorded where it is built. The text field's editing engine is Windows's
   own, drawn by Exact (D7); the date and time pickers are painted, with a WinUI control
   their exception only by D10.5's test.

LLP 1104 D7 and LLP 1115.000 D17 hold for desktop Linux. **For Windows they are amended**:
Windows leaves the neutral look for Fluent, and the presenter stays Exact's (D2). Charlie
made that amendment on 2026-10-23 (§5 Q6).

### D2 — The presenter stays Exact's; no Windows toolkit presents an app

The shared presenter keeps layout, paint, hit testing and focus on Windows, as it does on
Linux and Android. The alternatives, and why each is not chosen:

| Presenter | What it would give | Why not |
|---|---|---|
| WinUI 3 (XAML) for every node | Fluent controls, UIA and text input for free | the Windows App Runtime installed, or about 54 MB of its DLLs beside every app (self-contained, x64); its XAML tree and layout would own what the kernel owns (LLP 1001: the web is the layout oracle); `windows-rs` will not support the composable classes XAML is built on (its maintainers' answer is a C# or C++ wrapper), and their `windows-app-rs` is archived |
| Win32 controls (as Windows Desk) | the system's own controls, real `EDIT` text input | an older Windows's look, not Fluent; a control per node is an HWND per node |
| WPF or MAUI | Fluent-like controls | .NET in every app; MAUI is a cross-platform layer over WinUI, another Exact |
| GPUI | a Rust platform layer: window, DirectWrite text, IME | a whole UI framework whose element tree, layout and focus would duplicate the kernel's (LLP 1076 §3.5); no native controls either |

What Exact takes from Windows is the platform layer under the presenter (D3 to D11), each
piece through the system's own API, with no runtime beyond the OS. Windows Desk shows that
kernel layout can drive HWND controls, so a single native control under Fluent chrome is not
ruled out by this table (D1.3); a presenter of native controls is. GPUI's Windows code is a
reference for how others did the same pieces, not a dependency.

### D3 — The person's settings reach the app, before its first layout

One call carries the settings before the first layout and again, whole, when any changes
(`WM_SETTINGCHANGE`, `WM_THEMECHANGED`, `UISettings.ColorValuesChanged`):

1. **The theme**: the app mode, light or dark (`prefers-color-scheme`).
2. **The accent** and its shades (`UISettings.GetColorValue`), reported as colours (D5).
3. **Contrast themes** (`SPI_GETHIGHCONTRAST`, again on `WM_SYSCOLORCHANGE`):
   `forced-colors: active`, and the theme's colours (`GetSysColor`) reported as CSS's system
   colours in Microsoft's pairs (Window and WindowText, ButtonFace and ButtonText, Highlight
   and HighlightText, Hotlight for links, GrayText for disabled); the person's palette
   replaces the app's, as Windows expects
   ([contrast themes](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/high-contrast-themes)).
   `prefers-contrast: more` follows.
4. **"Animation effects" off** is `prefers-reduced-motion: reduce`.
5. **"Transparency effects" off** is `prefers-reduced-transparency: reduce`, and the window's
   backdrop becomes a solid colour (D4).
6. **The text size** (Settings, Accessibility, Text size, 100% to 225%:
   `UISettings.TextScaleFactor` and its change event) reaches the reported type ramp (D6.2),
   so text grows and what is sized by its content grows with it. Microsoft's rule for a
   custom framework: "controls and containers must also resize and reflow", a hard-coded
   control height has to give way, and font icons do not scale. So a control's Fluent height
   is a minimum (D12), and a symbol keeps its size. A custom renderer gets none of this from
   the system (DirectWrite and GDI "do not natively support text scaling"), so the host
   reads the factor itself. Exact's root font size is the reported body size, which also
   scales what an author wrote in `rem`; S1's oracle includes a specimen at 200% so the
   difference from WinUI is seen, not assumed.
7. **The locale, its direction and the 24-hour clock**: the doors Android's D3 builds.
8. **The pointer**: `pointer: fine` and `hover: hover` for a mouse; a touch screen's input is
   coarse and cannot hover while it is the one in use.

The runner's `Preferences` already carry 1, 3, 4, 5 and 8; this host never sets them.

### D4 — The window is the system's

1. **The title bar follows the theme**: `DWMWA_USE_IMMERSIVE_DARK_MODE` in dark mode, so the
   caption is not white over a dark app. A Win32 frame is light unless the app opts in.
2. **Mica is the main window's backdrop**, as Microsoft's guidance gives for long-lived
   windows; a transient window (a flyout, D10.1) takes Desktop Acrylic. Exact sets them
   through DWM (`DWMWA_SYSTEMBACKDROP_TYPE`: `DWMSBT_MAINWINDOW`, `DWMSBT_TRANSIENTWINDOW`),
   not the Windows App SDK's `MicaController` that Microsoft's Win32 how-to uses, so no
   runtime ships; the attribute needs Windows 11 build 22621. Mica shows where the page's
   background is unsaid; an authored background covers it, by LLP 1115's precedence. DWM
   itself gives a solid colour when transparency is off, on Battery Saver, when the window is
   inactive and on older builds, and a contrast theme's colour replaces it.
3. **Mica needs the frame's alpha to reach DWM.** Ink's default Windows path uses
   a DirectComposition swap chain (`CreateSwapChainForComposition`, premultiplied
   alpha), so the painted frame composes over the backdrop (LLP 1149 D12).
   The explicit CPU path keeps `softbuffer`'s `0x00RRGGBB` through GDI without
   per-pixel alpha. S2.5 and S2.9 in `host/ink/MEASUREMENTS.md` record the
   first-screen comparison. It must not be a layered window
   (`WS_EX_LAYERED`): Windows 11 never rounds a window that uses per-pixel alpha layering.
   A Windows manifest declaring `game` defaults to CPU to preserve the
   module's direct presentation, with explicit `"ink"` or `"cpu"` honoured
   and `EXACT_PAINTER` overriding either (orchestrator, 2026-11-01; LLP 1149 D12).
   Changing that default waits for Ink's window to hand a lone full-window
   canvas to the module and match LLP 1015.001's 7.22/10.83 ms frame p50 at
   720p/1080p.
4. **The route's header moves into the title bar, in S2.** Windows 11's own apps extend
   their content into it (Explorer's and Notepad's tabs, Settings's Back, Terminal's tabs),
   and Microsoft's guidance for a new WinUI 3 app is to keep the app's identity in the title
   bar and not repeat it in the page
   ([app structure](https://learn.microsoft.com/en-us/windows/apps/develop/ui/windows-app-sdk-app-structure)).
   In Win32 that means drawing the caption area; keeping DWM's caption buttons and calling
   `DwmDefWindowProc` first; answering `WM_NCHITTEST` with `HTMAXBUTTON` over the maximise
   button, so Snap Layouts open on hover; and keeping dragging, double-click to maximise and
   the system menu. The bar is 32 px high, 48 with a search box. What moves up is what LLP
   1115.002 D2's rule finds projectable: Back, the route's title, a search field, the primary
   tabs. A pane's own heading (Excord's channel) stays in the page. S1 keeps the system's
   title bar (1, 2) with the header painted below it: for one stage a second row is a
   smaller tell than a broken Snap Layouts menu.
5. **Corners, shadow and the window's opening animation are DWM's**, which a plain winit
   window already gets on Windows 11.

### D5 — Colours are reported, from WinUI's theme resources

The values are WinUI's theme resources at a pinned `microsoft-ui-xaml` release, copied into
the host as light and dark pairs (there is no XAML at run time to look them up in), with the

fills name statuses, not hues; a placeholder uses the secondary text fill.

| `-exact-tertiary-label` | `TextFillColorTertiary` |

### D6 — The system font, at the person's size

1. **`system-ui` and `sans-serif` mean the system's font**: Segoe UI
   Variable on Windows 11, Segoe UI on Windows 10, found by name before the generic list.
   Arial stops being Windows's sans. Segoe UI Variable's optical size axis follows the size
   (LLP 1019 §13), as DirectWrite's automatic optical sizing does.
2. **Fluent's type ramp is reported by the host**, not tabled. The kernel's text-style sizes
   are one ramp read at the root font size (`kernel/src/style/relative.rs`,
   `text_style_size`); only weights and leadings have per-platform columns. Read at a root of
   14, that ramp gives `large-title` 31 and `title1` 25, Apple's sizes, not Fluent's. So the
   host reports each style's size, line height and weight, already at the person's text scale
   (D3.6), through the door Android's reader is to use for the same reason (LLP 1115.001 D4,
   LLP 1115.001.001 D2.5); Windows builds it if Android has not. The mapping:

   | Text style | Fluent (size/line, weight) |
   |---|---|
   | `large-title` | Title 28/36, semibold |
   | `title1` | Subtitle 20/28, semibold |
   | `title2` | Body Large's 18/24, set semibold (Body Large itself is regular) |
   | `title3`, `headline` | Body Strong 14/20, semibold |
   | `body`, `callout`, `subheadline` | Body 14/20 |
   | `footnote`, `caption1`, `caption2` | Caption 12/16 |

   So the root font size is 14 at 100%, where Apple's is 17 on iOS and 13 on the Mac. Five
   styles land on 14/20 and differ only by weight; that is Fluent's ramp, which has three
   sizes below Subtitle. Title Large (40/52) and Display (68/92) have no text style; an
   author reaches them with a size.
3. **Windows's own text is measured, and the closest candidate ships.** The aim is text that
   looks like the rest of Windows (Charlie, 2026-10-23). The painter rasterises glyphs itself
   with swash, hinted (`host/linux/src/text/catalog.rs`, `.hint(true)`) and grayscale
   (`Format::Alpha`). DirectWrite renders ClearType or grayscale by its antialiasing mode;
   ClearType is "not suitable for rendering text onto a transparent intermediate bitmap",
   which the composition swap chain over Mica is (D4.3); and DirectWrite's default rendering
   parameters carry the person's ClearType Text Tuner settings, which swash never reads. S1:
   1. Photographs what Windows draws: Settings, Notepad, File Explorer, the WinUI Gallery and
      a classic Win32 dialog, zoomed until colour fringes (ClearType) or grey edges
      (grayscale) show, at 100%, 125% and 150% on a display that runs at 100%, light and
      dark, over a solid ground and over Mica.
   2. Renders the same strings with each candidate: today's swash; swash with its hinting,
      gamma and contrast tuned and Segoe UI Variable's optical size set (D6.1); DirectWrite
      grayscale (`DWRITE_TEXT_ANTIALIAS_MODE_GRAYSCALE`) from Exact's glyph ids, positions and
      variation coordinates; and DirectWrite ClearType where the ground under the text is
      opaque.
   3. Compares them per glyph (pixel difference, stem darkness, ink width, positions) and in
      side-by-side crops, with the Text Tuner at its default and at a tuned setting.
   4. Ships the closest. Shaping and layout stay Exact's whichever wins, so a line breaks the
      same on every host; a DirectWrite path lands only after an audit of ink against
      advances shows no drift beyond the oracle's tolerance. Never ClearType on a transparent
      surface.

### D7 — The text field is Windows's editor, drawn by Exact

A text field is the control painted toolkits get wrong longest (LLP 1115.001 D8): the IME's
composition and candidates, reconversion, the touch keyboard's suggestions, dictation (Win+H),
selection, undo and the clipboard. Windows has one engine that does all of it and needs no
window of its own: XAML's `TextBox` is a **windowless RichEdit** drawn through Direct2D and
DirectWrite ([Sargent](https://devblogs.microsoft.com/math-in-office/richeditd2d-window-controls/)).

0. **The default is a windowless RichEdit, decided by a spike in S1.** The host implements
   `ITextHost2` over the presenter's field, creates the editor with `CreateTextServices` from
   `msftedit.dll` (never Office's `riched20.dll`), and draws it into Exact's frame with
   `ITextServices2::TxDrawD2D` (Windows 8 and later). TSF is on
   (`EM_SETEDITSTYLE`, `SES_USECTF`). The spike compares it with a painted field over winit's
   IMM32 events, on Shelf's search field and Excord's composer, on the NucBox. A Win32 `EDIT`
   or RichEdit child window is not an arm: a `topmost` DirectComposition target can draw over
   it, but its hits stay its own, it moves by `SetWindowPos` outside the swap chain's present
   and so lags a scrolling form, and `msftedit`'s window draws with GDI beside painted labels.
   Windows Desk stays the evidence for that road (§4).
1. **The windowless arm stays the default only if the spike shows all of:**
   1. Japanese and Chinese composition drawn in the field, the candidate window at the caret
      as the transcript scrolls and the window moves (`TxClientToScreen` converts from the
      composition surface on every query); reconversion of committed text; the touch
      keyboard's suggestions, with its occluded area shrinking the layout so the composer
      stays in view; Win+H dictation into the field and over a selection. RichEdit owns the
      editing; winit's interpreted text is not inserted as well.
   2. One accessibility tree: RichEdit's provider
      (`IRicheditWindowlessAccessibility::CreateProvider` with an
      `IRawElementProviderWindowlessSite`) parented under AccessKit's node for the field, its
      rectangle right after a scroll, no second root and no duplicate node. AccessKit's
      Windows adapter embeds no foreign fragment today, so this extends it (D11).
   3. Drawing on both paths: into the composition swap chain (D4.3), premultiplied, over Mica;
      and on today's CPU path through an intermediate Direct2D bitmap copied into the frame,
      since a `softbuffer` slice is not a Direct2D target. First-frame cost, typing latency
      and device-loss recovery are measured.
   4. Fluent's look: RichEdit's ground transparent; the host paints the chrome, the bottom
      stroke and its focused accent line (D12), and the placeholder in
      `TextFillColorSecondary` (`EM_SETCUEBANNER` does not apply to RichEdit); selection from
      the accent through `TxGetSysColor`; colour emoji through `EM_SETTYPOGRAPHYOPTIONS`
      (`TO_DEFAULTCOLOREMOJI | TO_DISPLAYFONTCOLOR`). Photographed against WinUI's `TextBox`
      at 100% and 150%.
   5. Excord's composer: measured with `TxGetNaturalSize2`, grown to its authored maximum
      and then scrolled, with the web host's height for ASCII, a wrapping CJK line and an
      emoji sequence; selection, undo and composition kept across reactive value updates.
      A key goes to RichEdit first. The Enter that confirms a candidate is consumed even when
      the composition ends during its dispatch, so it never sends the message; a later
      Enter sends and Shift+Enter breaks the line (`apps/excord/app.contract`, the composer's
      `key` handler, has no guard of its own).
   6. A host that does not re-enter the presenter mutably from RichEdit's callbacks
      (`TxInvalidateRect`, `TxViewChange`, `TxGetDC`). `windows` 0.62.2 declares `ITextHost2`
      with a zero IID, so IIDs come from the SDK's headers and `msftedit.dll`'s exports
      (`IID_ITextServices`), not from generated code alone.

   Any miss and the painted field is the default, with TSF its later piece: a text store
   (`ITextStoreACP`) over the presenter's field, which no established Rust crate provides.
2. **The context menu of a field** is Fluent's text command bar flyout: Cut, Copy, Paste,
   Select All, Undo, as WinUI's `TextBox` shows it (D10.1).

### D8 — Scrolling and the pointer are the system's

1. **Precision touchpads and touch pan with the system's inertia.** The presenter takes
   `WM_POINTER` input and Windows's DirectManipulation for panning, so a flick on a touchpad
   or a screen coasts as it does in WinUI's `ScrollViewer`. Wheel notches keep the
   system's lines-per-notch setting (`SPI_GETWHEELSCROLLLINES`), not a fixed 40 px.
2. **The scroll bar is Fluent's**: a thin panning indicator that becomes the full bar under a
   mouse or pen, over the content's last 16 px, and stays the full bar when the person has
   turned off "Automatically hide scroll bars" (`UISettings.AutoHideScrollBars`, which
   Microsoft gives for custom scroll bars).
3. **The cursor** is the system's for each CSS keyword (it is today).

### D9 — The keyboard is Windows's

1. **Tab and Shift+Tab** move through controls, and the arrow keys within a group (a radio
   group, a tab list, a segmented control), as WinUI's controls take them.
2. **The focus visual is Fluent's**: a two-pixel outer ring with a one-pixel inner one, 3 px
   outside a button (`FocusVisualMargin`), drawn only after keyboard input (CSS's
   `:focus-visible`).
3. **Shift+F10 and the Menu key** open the focused element's context menu.
4. **Access keys**: an author's `accesskey` (HTML) is Alt plus the key, and holding Alt shows
   it, as WinUI's `AccessKey` does. A menu bar, when an app declares one, takes focus on Alt
   and F10 (D10.6).
5. **Enter and Escape** in a dialog: Enter is the default action, Escape cancels (D10).
6. **Shortcuts match as written.** On Windows `Meta` is the Windows key, as a browser's
   `metaKey` is there, and the shell takes most Windows-key chords before an app sees them
   (Win+N is Notification Center, Win+. the emoji panel). So `aria-keyshortcuts` matches
   literally, as `chord_matches` does today (`host/linux/src/presenter/shortcuts.rs`), and
   `Meta` is never read as Control: that would rewrite what the author wrote and part from the
   web, the oracle. Instead the build warns, in an app with a Windows host, of a chord that
   names `Meta` with no `Control` sibling in its list (suggesting the sibling, the key and
   other modifiers kept, as Fieldnotes writes `Meta+S Control+S`), and of a chord Windows keeps
   for itself: Windows-key chords, Ctrl+Esc, Ctrl+Shift+Esc, Ctrl+Alt+Del, Alt+Tab, and
   Alt+F4 and Alt+Space, which arrive and stay the window's close and system menu. Menus and
   tooltips show the chord that works on Windows, the `Control` one. A portable "primary
   modifier", if one is ever wanted, is a word the author writes, not one guessed from
   `Meta`.

### D10 — Menus, dialogs and pickers

1. **Context menus and dropdowns are painted Fluent flyouts in their own popup window**, so
   they can leave the app's window as a WinUI flyout can, on Desktop Acrylic with an 8 px
   corner. `TrackPopupMenu` is not used: its menu is rounded on Windows 11 but keeps the
   classic menu's metrics, and no public API gives a Win32 app the Windows 11 menu outside a
   XAML island.
2. **A dialog is WinUI's `ContentDialog`**, painted in the window over a smoke layer, as the
   Linux desktop's `alertdialog` path already places it (LLP 1115.000 D13.4), with Fluent's
   metrics and its button order (the primary on the left).
3. **Files are the system's dialogs**: `IFileOpenDialog` and `IFileSaveDialog`, for
   `showPicker`, `input type="file"` and saving.
4. **A `select`** opens a Fluent `ComboBox` list (1).
5. **Date and time pickers are painted** (WinUI's `CalendarDatePicker` and `TimePicker`),
   and their behaviour is matched with their look: the calendar's month grid scrolls and
   snaps by month and zooms out to years and decades (Ctrl+Up); the arrow keys, Page Up and
   Page Down, Home and End move as WinUI's do; the time picker's columns loop under the wheel
   and touch with inertia. Narrator reads the calendar as a grid, which needs UIA's Grid
   pattern (D11). Locale (the first day of the week, formats, other calendar systems) comes
   from the ICU Windows ships (`icu.dll`, since Windows 10 version 1703), not a copy of our
   own. A WinUI picker hosted in the window (XAML Islands, `DesktopWindowXamlSource`), which
   costs the Windows App Runtime (D2's table), is considered only for a named app whose
   painted picker fails on behaviour painting cannot fix (the keyboard, Narrator, locale), and
   then as that app's opt-in (§5 Q4).
6. **A declared menu bar is a painted Fluent menu row** under the title bar, as Notepad's and
   Paint's are, opening (1)'s flyouts, with Alt and F10, access keys, the arrows, Escape and
   UIA's MenuBar. An app that declares none gets none. Where the Mac's `app`, `about` and
   `window` items go (File, Help; Window only with authored items) and File ▸ Exit are LLP
   1021 §5.3.2. Its consumer is `apps/agents`, which has no Windows entry yet; until it does,
   a Contract fixture carries the row.
7. **A dialog or a popover its author lays out** (*Draft, 2026-10-26, for Charlie*). Item 2's
   ContentDialog presents an `alertdialog` whose rows are an alert's; Excord's quick
   switcher, profile card, member list and emoji pickers are `dialog`s and popovers whose
   content the author lays out, and until now this host refused them. Proposed:
   - **A modal `dialog`** is presented as ContentDialog presents its content: the kernel
     lays out the author's subtree in the window's block, the presenter centres it over
     the smoke layer (`ContentDialogSmokeFill`, `SmokeFillColorDefault`, black at 30%),
     the window's content is inert to the pointer, the keyboard, the wheel and UI
     Automation, and focus moves in (the first `autofocus` descendant, else the first
     tab stop, else the dialog itself: HTML's dialog focusing steps) and returns, when it
     closes, to what had it when it opened, else the invoker.
     Escape and Back are close requests unless its author wrote `closedby="none"`, and a
     click on the smoke layer is one only under `closedby="any"` (HTML's default for a
     modal dialog is `closerequest`; ContentDialog likewise closes on Escape and not on a
     click outside). A close request fires `cancel` at the dialog and closes it unless a
     handler prevented that (HTML's close request steps, as the iOS host does for a sheet
     the person dismissed). Its own `command="close"` button and `close(id)` close it
     with no `cancel`. Either way its `close` event runs. Content taller than the window
     scrolls inside the dialog, whose height is capped by HTML's UA rule
     (`max-height: calc(100% - 2em - 6px)`). An `alertdialog` that is not alert-shaped
     is presented so too, with its label drawn as its title, as the web's neutral look
     draws it. While it is open the accessibility tree is the dialog alone.
   - **A popover** (`popover="auto"` or `manual`, not a menu) is presented as a Flyout:
     placed against its invoker by its `position-area` and `position-try-fallbacks`,
     and where its author wrote no area by the web's UA default (`block-end
     span-inline-end`, flipping), as the Apple hosts place a painted popover, 4 px from it
     (the neutral look's `margin: 4px 0`, `host/web/neutral.css`); a context popover
     opens at the pointer. An `auto` popover is light-dismissed as WinUI's
     Flyout is: a click outside closes it and is absorbed, so it presses nothing
     beneath, and Escape and Back close it; focus moves in and stays in while it is open
     ([Flyout controls](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/dialogs-and-flyouts/flyouts),
     "Light dismiss behavior"). A `manual` one is closed only by its author.
   - **The surface is the neutral look's until D12 gives Fluent its column.** Every
     metric that enters layout is a kernel row only the author's row beats: a dialog's
     padding (HTML's `1em`), its scrolling (`overflow: auto`), its corners, fill and
     shadow (`surface-radius`, `-exact-secondary-grouped-background`, the modal
     shadow), and a popover the compiler marked `defaultSurface` the raised one. With
     D12's `fluent` column these become WinUI's: an 8 px corner (`OverlayCornerRadius`),
     a 1 px `SurfaceStrokeColorDefault` edge, `SolidBackgroundFillColorBase` under a
     `LayerFillColorAlt` content area, 24 px padding (`ContentDialogPadding`), between
     320 and 548 px wide and at most 756 tall (`ContentDialogMinWidth`, `MaxWidth`,
     `MaxHeight`); a Flyout's padding 16, 15, 16, 17 (`FlyoutContentPadding`) and its
     1 px `SurfaceStrokeColorFlyout` edge on Acrylic. Sources:
     `controls/dev/CommonStyles/ContentDialog_themeresources.xaml` and
     `FlyoutPresenter_themeresources.xaml` in `microsoft/microsoft-ui-xaml`, read
     2026-10-26.
   - **Not WinUI's:** the popover is painted inside the app's window, so it cannot leave
     it as item 1's menus will. WinUI's Flyout places itself `Top` by default
     (`FlyoutBase.Placement`); this host keeps the web's default so one contract opens
     alike everywhere, as the painted popovers on iOS and the Mac do. *Question for
     Charlie:* should an unsaid popover on Windows open above its invoker, as a Flyout
     does?

   The Linux desktop presents the same two, with the same behaviour, in the neutral look.

### D11 — Accessibility through UI Automation, built with the rest

The presenter builds one accessibility tree from the kernel's roles, names and states, and
AccessKit's Windows adapter serves it to UI Automation from the window. The same tree serves
AT-SPI on Linux through AccessKit's Unix adapter, so desktop Linux gets a tree for the cost
of an adapter.

The dependency is AccessKit's schema crate (`accesskit` 0.25) in the shared presenter (types
and a tree update, no platform code) and its Windows adapter (`accesskit_windows` 0.35) in
`host/windows` alone, as a `cfg(windows)` dependency; no feature on a core crate. The adapter
answers `WM_GETOBJECT` for a raw HWND (`accesskit_winit` 0.34 wraps it for winit 0.30, which
this host already uses).

The adapter provides UIA's Invoke, Toggle, Value, RangeValue, ScrollItem, SelectionItem,
Selection, ExpandCollapse, Window and Text patterns (with text ranges). It has no Scroll,
Grid or Table provider, so a scroller cannot be scrolled by a screen reader's command and a
grid is read as a list. Microsoft requires the Scroll pattern of a list whose items scroll
([List control type](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supportlistcontroltype)),
and Shelf's library is one, so S1 adds a Scroll provider, upstream in AccessKit if its
maintainers take it. Grid comes with the calendar (D10.5), and Table waits for a consumer.
The text field's provider is RichEdit's, parented under the field's node (D7.1.2): the
adapter gains the one embedded fragment, so Narrator sees one tree.

It is built with the controls, not after them: every stage builds the tree for its screens,
every control says its role, name, state and value, and the accessibility actions of LLP
1114.008 map to UIA's patterns. **Narrator gates an app called supported, not a stage**, as
Charlie ruled for TalkBack (LLP 1115.001 §5 Q5, "don't block") and for Windows (§5 Q9);
each stage is read with Narrator on the NucBox once by hand and what it finds is written
down.

### D12 — The Fluent look, painted

The painter gains a Fluent look beside the neutral one and Material, chosen by the process
before a plan boots (`app::show_fluent_look`, as `show_material_look`). The schema's `metrics`
gain a `fluent` column, which is the `web` column's where a row has none.

- **Metrics enter measurement**, through the control-measurement seam Android's D9 uses: a
  text box's minimum height is 32 px (`TextControlThemeMinHeight`), a button's padding of
  11, 5, 11, 6 and its 1 px border make it about 32 around a 14 px line, and every control's
  font is the body size. Heights are minimums, so a control grows with scaled text (D3.6).
  An authored size, padding or radius wins, and `appearance="none"` is the author's box.
- **Corners** are 4 px on controls (`ControlCornerRadius`) and 8 px on flyouts and dialogs
  (`OverlayCornerRadius`).
- **Buttons by `buttonStyle`**, keeping the order of emphasis: `filled` and the prominent
  styles are the accent button, `bordered`, `gray` and `tinted` the standard button, `plain`
  and `borderless` the subtle button.
- **Check box, radio button, toggle switch, slider, progress bar and progress ring** in
  Fluent's metrics and motion.
- **A text box** has the bottom stroke that turns to a two-pixel accent line when focused.
- **Press and hover** are the fill's own states (`ControlFillColorSecondary`,
  `ControlFillColorTertiary`), not a ripple and not a dim; a mouse hovers, so every pressable
  answers it.
- **Motion** uses Fluent's durations and curves for the controls' own changes (a switch's
  knob, a flyout's entrance), and none when "Animation effects" is off.
- An inherited `color` does not tint a control's chrome (LLP 1115 D4).

The numbers are WinUI's control templates and theme resources at the pinned release, each row
citing its resource; the oracle (D13) checks them in pixels.

### D14 — An unsaid root tab bar is a navigation pane

As on the Mac (LLP 1115.002 D3), a root `tablist` whose placement is unsaid becomes the
window's navigation: on Windows a left pane as WinUI's `NavigationView` draws it, as Settings,

### D15 — Installed per user, updated by Exact's delivery

1. **The install is per user, under `%LOCALAPPDATA%`**, by an installer, with no
   administrator prompt, as the most used Windows apps that are not from the Store install
   (Chrome, VS Code, Discord, Slack). Exact's delivery (LLP 1030) updates it: the host
   binary as well as the app's bundles, so one stream carries both.
2. **A sparse package gives it identity** (packaging with external location,
   [`Add-AppxPackage -ExternalLocation`](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/grant-identity-to-nonpackaged-apps)),
   registered by the installer, for what needs identity: receiving a share and WNS push.
   Local toasts do not need it.
3. **Signing:** Authenticode on the installer and the executables, and the same publicly
   trusted certificate on the sparse package, through Azure Artifact Signing (formerly
   Trusted Signing) or a public certificate authority. No certificate gets past SmartScreen's
   warning until it has reputation.
4. **`winget`** gets a manifest pointing at each signed installer with the first public
   build: a way to find and install the app, not its updater.
5. **Not chosen:** full MSIX, which Astra recommended (r2b): its install directory is
   read-only, so a host fix would move on App Installer's schedule, not the stream's, and its
   install-from-a-link protocol (`ms-appinstaller:`) has been off by default since December
   2023. A Store listing of the same installer remains open and changes none of this; if the
   Store becomes the way people install, full MSIX is the form and Exact updates only the
   bundles in the package's data.
6. **When:** S1 already keeps the app's bundles and data under `%LOCALAPPDATA%` and its
   install directory stable. Windows has no Exact delivery yet (`host/windows/src/window.rs:89`
   refuses an update store; `scripts/deploy.mjs` names no Windows platform), so the update
   store, the deploy platform and the installer are a stage of their own (§3, S3), before the
   first public build.

### D16 — A list and its detail side by side

**Draft (Claude, 2026-10-26), for Charlie to accept.** Built on branch `linux-split`.

The Windows half of LLP 1115.002 D4. A window wide enough for two columns shows a stack
that splits by the shared rule (`Runner::stack_split`, LLP 1116.004 D1.2) as a list column
beside its detail, as Windows's own list/details apps do (Mail, Settings, Discord's Windows
app). Until now the detail was pushed over the list with a Back button. The rule for
*whether* a stack splits is unchanged; this decides *when* it does and *what the columns
look like* on the painted presenter (`host/linux`, `presenter/split.rs`), which draws
Windows and the Linux desktop.

1. **When, and how wide.**

   | Host | Splits when the routes' box is | List column | Source |
   |---|---|---|---|
   | Windows | 641 epx wide or more | 320 epx | Microsoft's [list/details guidance](https://learn.microsoft.com/en-us/windows/apps/design/controls/list-details): "320 epx-640 epx: Stacked; 641 epx or wider: Side-by-side"; the toolkit's `ListDetailsView` changes at 640 (`CompactModeThresholdWidth`'s default, `ListDetailsView.Properties.cs`); [`SplitView.OpenPaneLength`](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.splitview.openpanelength), the pane the guidance builds the list in, is 320 |
   | Linux desktop | 900 px wide or more | 320 px | the web's (LLP 1116.004 D1.2), since the Linux desktop draws the web's neutral look (LLP 1115.000 D17) |
   | Android | not split yet | | item 6 |

   `navigationSplit="<width>"` on the root route names the list's width instead of 320.
   The detail keeps at least 320 and the list at least 200, the Mac's minimums (LLP
   1115.002 D4); a box that cannot hold both does not split. The split is decided again
   after every commit and resize, so crossing the width splits or pushes the same stack
   in place. Microsoft's 1008 epx (`NavigationView.ExpandedModeThresholdWidth`, the
   [large breakpoint](https://learn.microsoft.com/en-us/windows/apps/design/layout/screen-sizes-and-breakpoints-for-responsive-design))
   is when a navigation pane opens, not when a list/details pattern goes side by side.

2. **Which box is which column.** Each route above the list, up to the first modal route,
   is laid out in a containing block the detail pane's size (LLP 1115.002 D8.2) and shown
   beside the list, as on the Mac. The list column is the root route laid out narrower by
   a host cover on its right edge (`HostCover::Edges`, which changes no authored row), so
   its own padding and border stay inside the column. A root route whose authored width
   does not narrow that way (a content-box `width: 100%`) does not split, and the log says
   so once. The page keeps the window's width, so `vw`, media queries, `viewport.width`, a root tab bar
   and a modal route keep the whole window. That is where the painted host differs from
   the Mac, whose page is the list's column (LLP 1115.002 D4, "Which view is which pane").
   A 1-pixel line in the separator's colour divides the columns.

3. **A row's detail has no Back.** A route a row of the list shows is the pane's base, as
   on the web and the Mac. The stack's Back control in it (the element the navigation
   root's `navigationBack` names) is covered whole, neither painted nor hit; a route pushed
   inside the detail keeps its own. Back (Alt+Left, the mouse's back button, the driver's
   `back`) pops the detail as before, and the pane then shows its empty state. A row whose
   press is an action, not a link, is the row of the route its press pushed.

4. **The selected row and the empty pane.** The base's row is filled in the tertiary fill,
   as the web's neutral sheet marks it, and the list's rows draw no disclosure chevron.
   With only the list on the stack the pane shows the author's placeholder
   (`navigationSplit="placeholder"`, LLP 1116.006 D2). With none, the Linux desktop says
   "No Selection", as the web does, and Windows leaves the pane empty, as WinUI's
   `ListDetailsView` does when an app gives it no content for no selection.

5. **Keys and the driver.** Tab goes through the list and then the detail, in tree order.
   `scripts/agent.mjs linux|windows` reaches both panes (`tree`, `tap`, `type`,
   `screenshot`), and `state` has `split`: the `list` route, `listWidth`, `detailWidth`,
   `authoredWidth`, the pane's `routes`, the `detail` shown, its `base`, the selected
   `row` and `empty`, or null when no stack splits.

6. **Open, for Charlie.**
   - *Android.* Material 3's list-detail shows two panes from the expanded width class,
     840 dp, the list 360 dp wide and 24 dp between the panes
     ([window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes);
     `calculatePaneScaffoldDirective` and `PaneScaffoldDirective.DefaultPreferredWidth` in
     androidx's `material3-adaptive`). The reader keeps its stack pushed until its top bar
     can show two routes' headers (LLP 1115.001 D11); those are the numbers proposed for
     it then.
   - *The selected row on Windows.* A WinUI `ListView`'s selected item is a subtle fill
     with an accent pill at its leading edge. That waits for D12's list row; until then the
     row takes the neutral fill.
   - *The column's width is fixed.* WinUI's list/details has no divider to drag either; a
     draggable divider, and remembering its place, are not built.
   - *A root tab bar beside a split* stays a bar across the window until D14's navigation
     pane is built.
