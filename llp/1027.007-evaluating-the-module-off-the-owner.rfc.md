## 1. Summary

A TypeScript module on the default `main` placement is evaluated on the owner
thread after first pixel. Brooks' module, which builds a 2 MB catalog at its top
level, takes 314 ms there on an iPhone 17 Pro Max. Two costs follow:

1. **The main thread waits.** At first pixel iOS reports the app active, and
   `tellPage` makes a synchronous runtime call that queues behind the
   evaluation. While it waits, decoded photos are not put on screen and input
   is not handled.
2. **Data comes 314 ms after first pixel.** Nothing that reads the module's
   answers can show sooner.

Path P1 (§4) removes the first cost and needs no ruling. Removing the second
means evaluating before first pixel, which `rules/RULES.md` and LLP 1027 D4 forbid
and which, done off the owner, means moving a live VM between threads, which LLP
1072 T1 and LLP 1027.002 D2 forbid. P2 and P3 (§5, §6) are that design, for
Charlie to rule on. P4 makes the evaluation itself cheaper and needs a
measurement first.

Time Profiler traces of the same launches (`~/bench/brooks-device/diag`): the
first frame commits at about 240 ms, then the owner runs `Module::load` (Hermes
`evaluateJavaScript`, 314 ms; Bun loads the same module in 60 ms), and the main
thread waits inside `tellPage` for it. With the worker placement the owner is
free and nothing waits; the worker's answers come `Later`, outside the runner's
transaction (LLP 1027.002 D1, D3), which is why it is not the default.

Holding page facts until the data is ready was tried in 74409073a6's lane and
not kept: it changed what the page is told (`WindowMannersMacTests` lost a
`pagehide` with `persisted`).

## 3. The rules this touches

- `rules/RULES.md`: "App JS executed before first pixel: none", a **[check]**
  that is "counted, not timed", so that boot-path JavaScript cannot accrete.
- LLP 1027 D4: "The executor is created after the first pixel". Creating it
  earlier "was considered and not taken … because the rule is a count, not a
  timer … If Charlie wants the frame back, it is a ruling on the rule, not a
  change to this design."
- LLP 1072 T1: the owner holds the data sources; "No `Send`, no `unsafe impl`".
- LLP 1027.002 D2: "Nothing moves a live VM between threads or marks its
  pointers shareable to satisfy the compiler." A worker-placed module is built
  on its own thread and stays there.

P1 and P4 touch none of these. P2 needs T1 and 1027.002 D2 waived for one
transfer. P3 needs the count rule and 1027 D4 waived.

## 4. P1: page facts are told without waiting (no ruling)

**D1.** `tellPage` reads the window's facts on the main thread as now, and sends
the runtime calls (`setPage`, `setRootFontSize`, the display scale, and the
`readsOnLine` read `setPage` depends on) to the owner as one job, not a
synchronous call. The job ends by applying its batches on the main thread
through `Owner.callMain`, which the main thread serves from its wait loop, or
from a main-queue hop when it is not waiting. A later synchronous call is queued
after the job, so its batch cannot be applied first: the order the page sees is
the order the calls were made, as today.

**D2.** Only the page-facts observer (`PageFacts.observe`) takes this path. A
direct `tellPage` (window focus in `ExactViewIOS`/`ExactViewMac`, tests) stays
synchronous, so it has told the page when it returns.

**D3.** What P1 does not change: the facts, their order and their content; the
module's evaluation, still on the owner after first pixel; input during the
evaluation, which still waits for the runtime, because data is not ready.

**Verification.** `WindowMannersMacTests` and the page-facts tests unchanged; a
test that sends a page-facts notice while the owner is held and checks that the
main thread returns at once and the facts arrive in order. On the iPhone, ten
filmed cold launches of Brooks, Caltrain and Fieldnotes; bar: Brooks' rail at
0.55 s, and a Time Profiler trace with no main-thread wait inside `tellPage`.
`prepareAppModule` (the app module's dylib load) is measured separately.

## 4a. P1 as built

`SessionNotices.swift`. Two observers make the notices: page facts and display
preferences (iOS re-reads both when the app becomes active). The synchronous
`tellPage` was not the only call waiting: once it was moved, the trace showed the
main thread waiting in `setPreferences` instead, and the colours report it makes.
So a notice's runtime calls (`setPage`, the root font size and display scale;
`setPreferences` and `reportColors`) go to the owner as one job through
`Runtime.later`, and their batches land as a published kind, `.notice`, in the
owner's order (LLP 1072 T4).

D1 as written made every notice asynchronous. Tests and the agent rely on a
notice having taken effect when it returns (`AgentAppearanceMacTests`,
`PrimaryInputTests`, `SessionClockTimerTests`, `DisplayModeMacTests`,
`TamberBindingMacTests`, `WindowMannersMacTests` failed). As built, a notice is
asynchronous only while the data source activates (`dataPreparing`), which is
when the owner is known to be busy; at any other time it is told at once.

Measured on the iPhone 17 Pro Max with Brooks (poster on, `main` placement),
five filmed launches: rail photos 0.55 s (UIKit 0.55 s; 0.59 s at 74409073a6),
hero 0.53 s (0.59 s). A Time Profiler trace shows the tab bar painted at 225 ms,
before the module's evaluation (246–525 ms), and the main thread idle, not
waiting, while it runs. Brooks' hero still waits for the evaluation: its video
node takes its properties in the batch after the data.

## 5. P2: the module is loaded on a loader thread and handed to the owner (needs T1 and 1027.002 D2 waived)

P2 alone frees the main thread no better than P1. It is the means for P3. r1's
design had holes both reviews named; this is the design with them closed.

- **Identity.** The load starts from an immutable descriptor of the selected,
  admitted module: the bytecode `boot_selected` chose (embedded or installed),
  the grants it was admitted with, the plan it is paired with, and the session's
  generation. `exact_create` builds no data source and cannot start it; the
  earliest point is in `exact_boot`, after selection.
- **Before load.** Everything load captures is resolved first, on the owner:
  the directories `picker::app_dirs` gives (they depend on agent mode, the app
  group and `HOME`, not only the app id), the scratch tree emptied, the
  document owner, the placement's `main_thread` flag, and fresh `watch` and
  `native_slot` handles for this incarnation. Picker roots are published on
  the owner at adoption.
- **Native modules.** Load makes neither the Rust native module (the factory)
  nor the hosted binding. Both are bound on the owner at adoption, before any
  answer. A loaded module with a native object is not sent.
- **The send.** The loader drains the module's microtask queue, checks it holds
  no native object, store borrow or canvas environment, and sends it once. The
  `unsafe impl Send` names each of these, ibex2's thread-locals (`CONSOLE`,
  `RESULT_BUDGET`, `CLAIMED_WAKES`), the adapter's owner-thread contract
  (`ibex2_jsi.h:249`), and Hermes' stack guard. The stack-guard argument is made
  from the pinned Hermes source (`hermes-v260318099.0.4`), checked into the
  argument before building, not from upstream memory.
- **No waits.** The owner never waits for the loader. Until the module arrives,
  the source's `preload` answers pending and `when_preloaded` wakes the session;
  activation then adopts, binds the plan (`bind` builds the source signatures),
  binds native modules, adopts any pending shared-store revision and settles as
  `data_ready_after_store` does today. "Loaded" and "activated" are separate
  states; `ready` means activated.
- **Lifecycle.** A load is one of loading, delivered, adopted, failed or
  cancelled. Destroying, rebooting or replacing a session cancels its load:
  its `watch` is triggered, its channel dropped, and a module never adopted is
  destroyed on the loader. A delivery for another generation is destroyed there
  too. A failed load is reported once by activation and retried at most once.
  Two sessions' loads queue on the loader; the second is named in the journal.

## 6. P3: the load starts before first pixel (needs the count rule and 1027 D4 waived)

P2's load starts in `exact_boot` before the first layout, on the loader, at a
QoS below the owner's. First pixel's activation adopts the module if it has
arrived, and otherwise answers pending; no thread waits. Expected for Brooks:
data about 240 ms sooner. Costs: every launch executes app JS, including one
the user abandons; the loader contends with the boot for cores, memory and I/O;
and the rule against boot-path JS becomes an exception to argue each time.
Bar: precise first-frame stamps (not film) over twenty cold launches on two
device classes, first frame's p50 and p95 within noise; data-driven content
200 ms sooner in Brooks; touch latency during launch no worse. The
worker placement's load would move earlier by the same waiver, with its
storage and plan binding resolved first as in §5.

## 6a. P4, measured: the evaluation's cost is the app's own top level

Brooks' module baked three more ways, each loaded fifteen times through
`exact_js::Module::loaded` on an M-series Mac (`~/bench/brooks-device/p4`, with
the harness `time_load.rs`):

| bake | bytecode | load, median |
|---|---|---|
| as ported | 1.6 MB | 294 ms |
| the catalog and reviews JSON as `JSON.parse("…")` strings | 4.4 MB | 305 ms |
| without the eager look lists (`completeTheLook` for each of 226 products) | 1.6 MB | 74 ms |
| with the whole `catalog.products.map(product)` made lazy | 1.6 MB | 5.5 ms |

Building the JSON's objects costs about 5 ms; parsing it from a string is no
cheaper and triples the bytecode, so the bake keeps object literals. 220 ms is
one helper, `completeTheLook`, which scans every product with regular
expressions for each product, about 250,000 matches in Hermes' interpreter.
The Expo original calls it for one product, when its page opens. Nothing in the
bake makes app code cheaper. What exact2 does about it is say so: the journal
line for a top level slower than 50 ms, and the agent-pitfalls entry
(74409073a6).

## 7. Questions for Charlie

**Q1. Build P1 now?** It needs no ruling, frees the main thread during the
evaluation, and is small. My recommendation is yes. Confidence 85%.

**Q2. Do you want data sooner badly enough to waive the count rule (P3), and
with it LLP 1072 T1 and 1027.002 D2 for one transfer (P2)?** That is three
rulings and the riskiest code in the runtime, for about 240 ms after first
pixel. My recommendation is not now. Do P1 and P4 first: the journal line and
the agent-pitfalls entry already tell an author whose top level is slow, and
Brooks' own 314 ms is mostly its eager catalog transform. Ask again if a
measured app still waits after its top level is made cheap. Confidence 65%.

**Q3 (P4). Measure making the evaluation itself cheaper?** Bun evaluates the
same module in 60 ms; Hermes takes 314 ms. One candidate: bake a large JSON
import as a string Hermes parses with `JSON.parse`, instead of an object
literal it builds in bytecode. That needs no ruling. My recommendation is to
measure it on Brooks' catalog first. Confidence 70% that it is worth measuring,
no estimate of the gain until then.
