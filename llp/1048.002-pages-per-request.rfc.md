# LLP 1048.002: Pages per request — provenance holes, cache policies, streaming, and the edge

**Type:** RFC
**Status:** Draft
**Systems:** Runner (provenance on sources; holes at a render stage); a request renderer (a native server binary; the same code in wasm for edge workers); a page cache (keys, TTL, tags, revalidation); streaming; data sources on a server (Rust modules; TypeScript on Hermes) with a request context; the web host (filling holes; the data endpoint)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Implementer:** assigned by Charlie at phase 3 kickoff
**Date:** 2026-09-23
**Related:** LLP 1048 (parent: D2, D3, D9), 1048.000 (rendered pages), 1048.001 (adoption; payloads), 1048.003 (route policy fields), 1005 §8 (the dependency table), 1016 (answers now or later), 1018 (the store), 1027 and 1027.001 (sources in TypeScript and Rust), 1039 (the viewport fact), 1030 (delivery)

## Summary

Phase 3 of LLP 1048: pages that need information only a request has — cookies,
a session, a locale, fresh inventory — rendered at CDN speed. Nobody marks
Suspense boundaries or `use cache`; the split falls out of **provenance**:

- Each source says where it can answer: `build`, `request` or `client`.
- The dependency table says what each subtree reads.
- A page renders everything available at its stage and leaves **holes**: build
  fills its part, a request renderer fills its holes (inline or streamed), and
  the client fills the rest after adoption.

One renderer serves `cached` pages (Incremental Static Regeneration, on-demand
revalidation) and `request` pages (per-request rendering), from a native binary
or an edge worker.

This is an RFC, not a spec: §7 lists what phase 3 must settle before it becomes
one.

## 1. Provenance

- **Sources declare it.** The module that implements a source knows where it can
  run: a TypeScript module exports a `provenance` map, and a Rust source answers
  a trait method. The bake records it in the plan's sources, a new column. A
  source with no declaration is `client`, which is safe: it never renders early.
- **Runner inputs have fixed provenance:**
  - the store: `client`;
  - the viewport: `client`, or `request` when client hints provide it (D8);
  - the clock: `request`;
  - the router location: `build` for enumerated routes, `request` otherwise;
  - `setScheme` / `prefers-color-scheme`: `client`, or `request` with the
    `Sec-CH-Prefers-Color-Scheme` hint.
- **Everything else is inferred.** A binding's provenance is the latest of its
  inputs (`build` < `request` < `client`). A site's provenance is the latest of
  its own bindings, subject and key. The dependency table (LLP 1005 §8) already
  has these reads; provenance is one more column per input.

## 2. Holes

- **What gets rendered.** A render at stage *S* renders every site whose
  provenance is ≤ *S*. A site above *S* renders its placeholder: the
  resource's placeholder value with `pending(x)` true (LLP 1048 D6), so the
  author's own loading state is what shows.
- **How a hole is marked.** Its subtree's root carries
  `data-hole="<instance path>"`: the site plus its `each` keys and `when` arm
  (the path the agent API already reports, LLP 1035.002 D6). No wrapper element
  is added.
- **Who fills each hole.**
  - A `request` hole is filled by the request renderer (§3), inline or streamed
    (§4).
  - A `client` hole is filled after adoption, when the runner settles on the
    device.
  - With static hosting only, `request` holes are filled on the client too —
    the static fallback of partial prerendering.

## 3. The request renderer

- **Form.** A native Rust binary that links the runner, the web host's mapping
  (LLP 1048.000 D1), the app's Rust sources and Hermes for TypeScript modules
  (LLP 1027). It serves:
  - `dist/` files for `build` pages;
  - `cached` pages from its cache, rendering on a miss;
  - `request` pages on every request;
  - the data endpoint (D7).
- **Request data.** A request context — cookies, headers, the URL, client
  hints — reaches `request` sources through a grant-checked capability, as the
  store does today (LLP 1018). An app's grants name which headers and cookies a
  source may read.
- **Placement.** The render path stays in Rust (LLP 1048 D9). The binary is the
  Linux host's runner without the painter; its shape follows
  `host/linux/src/fetch.rs` and the executor core.

## 4. Streaming

1. A `request` page first flushes `<head>` and the shell: everything already
   rendered, plus placeholders for holes whose sources answer later.
2. As each such source answers, the renderer settles the runner and streams
   `<template data-fill="<path>">…</template>`. A small host-glue swap —
   counted, with no app code — moves the fill into place.
3. The payload (LLP 1048.001 §1) closes the stream with the final carried state,
   so adoption sees every answer.

Adoption waits for the payload. A page adopted before its stream ends is an
open question (§7).

## 5. Cache policies

- **Key.** `cached` pages are keyed by the plan digest, the location, the digest
  of the build inputs, and the public request inputs the page actually reads —
  for example the locale from `Accept-Language` or the country. That set comes
  from the dependency table, so `Vary` is exact rather than guessed.
- **Freshness.** Each route declares a TTL with stale-while-revalidate.
  Invalidation is by tag: a source name and its arguments form a tag, and an
  authenticated endpoint revalidates by tag (the on-demand ISR shape).
- **Storage.** The cache lives in the server's filesystem, or in the edge's KV
  store (D9).
- **Private pages.** `request` pages are never shared-cached:
  `Cache-Control: private, no-store` when any `request` input is personal
  (cookies, the session).

## 6. Decisions

**D1 — Provenance lives with the source** (§1), is recorded in the plan, and is
inferred for everything else.

**D2 — Holes are subtrees at instance paths**, rendered as the author's own
pending state. The design adds no boundary syntax.

**D3 — One request renderer for `cached` and `request`**, as a native binary
first.

**D4 — Streaming is out of order**, uses the host glue, and ends with the
payload.

**D5 — Cache keys come from what the page reads**, not from author-declared
lists.

**D6 — Personal data never enters a shared cache.** A `build` or `cached` render
that would read a personal `request` input refuses. The refusal names the
binding and the source, with a test per app.

**D7 — A data endpoint for navigation.** `GET <location>?__exact=data` returns
the carried answers of the location's `request` sources — the `data-only` shape
TanStack Start offers. It uses the same privacy rules as pages.

**D8 — Client hints.** The renderer sends `Accept-CH` for
`Sec-CH-Viewport-Width` and `Sec-CH-Prefers-Color-Scheme`. When they arrive,
the viewport and color scheme become `request` inputs, and the page renders
for the real width and scheme.

**D9 — The edge.** The same render compiles to wasm (`exact-web` already
targets `wasm32`) behind a `render` export, for Workers or Deno. Rust sources run
there; TypeScript sources need the edge's own engine and the language-parity
constraints of LLP 1027.001, so the edge starts with Rust-sourced apps.

## 7. To settle before this becomes a spec

1. Where provenance is declared: the module (proposed) or Contract.
2. Whether adoption may begin before a stream ends, with late fills becoming
   ordinary updates.
3. The cache store and the revalidation endpoint's authentication.
4. The route policy syntax, shared with LLP 1048.003 D5.
5. Whether TypeScript sources run on a server through Hermes from the start, or
   whether phase 3 begins Rust-only.
6. How a `cached` page's TTL interacts with delivery's release streams (LLP
   1030): a new release invalidates by plan digest, since the plan digest is in
   every key.

## 8. Verification (when specified)

- Personal-data refusal tests per app.
- Parity of the request-rendered page and the live DOM, as in LLP 1048.000 §4.
- Streaming order and final-payload equality.
- `Vary` exactness: a public input the page doesn't read doesn't split the cache.
- Latency for `cached` and `request` pages from a nearby server.
