## Summary

Phase 3 of LLP 1048. Some pages need information only a request has — a session,
a locale, fresh inventory — and should still arrive at CDN speed. Nobody marks
Suspense boundaries or `use cache`. The split follows from two labels on every
input:

- **stage** — when it can be known: `build`, `request` or `client`;
- **confidentiality** — who may see it: `public` or `private`.

A page renders everything available at its stage and leaves **holes** for the
rest. Public content can be cached; private content never is. The native server
from phase 1 serves `cached` pages (incremental regeneration with tag
revalidation) and fills request holes, inline or streamed.

## 1. Stage and confidentiality

**Declared by sources.** A TypeScript module exports a `provenance` map; a Rust
source answers a trait method. The bake records both labels in the plan's
sources table, as new columns. An undeclared source is `client` and `private`,
which is safe: it never renders early and is never cached.

**Fixed for runner inputs:**

| Input | Stage | Confidentiality |
|---|---|---|
| Store | `client` | `private` |
| Viewport | `client`, or `request` with client hints (D8) | `public` |
| Clock | `request` | `public` |
| Router location | `build` for enumerated routes, `request` otherwise | `public` |
| Color scheme | `client`, or `request` with its client hint | `public` |

**Propagated statically.** Labels flow through bindings, derives, resource
arguments, control flow (`when`/`match` subjects), `each` keys and pending
state. The dependency table (LLP 1005 §8) has the reads; each input gains two
columns.

**Tracked at runtime** for what a source reads inside its own code. Each call
and each continuation records the capability reads it makes: store, request
context and cookies. Two consequences:

- The attribution gap is fixed first. Fulfillment passes the store to `parse`
  without recording a read delta (`runner/src/runner/commit.rs` ~595), and a
  Hermes continuation can first read the store after an await
  (`js/src/lib.rs` ~743).
- A source whose reads are unknown is private.

**Checked on output.** The renderer inspects the whole serialized payload — the
document and its checkpoint — not only visible bindings.

## 2. Holes

- **What renders.** A render at stage *S* renders every site whose stage is
  ≤ *S* and whose confidentiality the page's policy allows. Any other site
  renders its placeholder with `pending(x)` true, so the author's own loading
  state shows.
- **Boundaries.** The dependency table's per-site unions include every
  descendant (`runner/src/instance/deps.rs` ~214), so using them directly would
  push a client dependency up to the root. A hole is the smallest subtree whose
  own inputs exceed the stage; the selection algorithm is part of this RFC's
  spec work (§7.1).
- **Anchors.** A hole is identified by its instance path: the site, its `each`
  keys and its `when` arm (the path the agent API reports, LLP 1035.002 D6).
  Empty regions, absent arms and multi-root regions need anchors that survive
  fulfillment changing the arm (§7.2).
- **Who fills.** The server fills `request` holes, inline or streamed (§4). The
  client fills `client` holes after adoption. On a static host, `request` holes
  are filled on the client too.

## 3. The request context

In phase 3, request-stage sources receive a request context: the URL, cookies,
headers and client hints. It comes through a grant-checked capability, as the
store does (LLP 1018), and an app's grants name which headers and cookies a
source may read. Reads are tracked (§1), so a page's personal inputs are known
exactly.

The server is phase 1's (LLP 1048.000 D9–D11): isolation per request, limits,
the grant-checked executor core, and the HTTP contract.

## 4. Streaming

1. A `request` page flushes `<head>` and the shell once the head's own inputs
   have settled, so the title and status are never frozen wrong.
2. As each hole's sources answer, the server settles the runner and streams
   `<template data-fill="<anchor>">…</template>`. A small host-glue swap —
   counted, with no app code — places each fill.
3. A final checkpoint closes the stream. Fills and the checkpoint carry one
   checkpoint version, so adoption knows they describe the same state.
4. **Failure.** An aborted or failed stream leaves placeholders, and the client
   asks again after adoption.
5. **Without JavaScript,** fills don't apply: holes stay placeholders, and pages
   that must read fully without JavaScript use `request` rendering without
   streaming.

## 5. Cache policies

- **What may be cached.** `cached` pages may contain public inputs from any
  stage, never private ones (D6).
- **Key:** the plan digest, the location, the build inputs' digest, and the
  values of the public request inputs the render actually read — tracked at
  runtime (§1). So `Vary` covers exactly what was read, not what the dependency
  table suggests.
- **Freshness.** Each route has a TTL with stale-while-revalidate.
  Invalidation is by tag: a source name and its arguments form a tag, and an
  authenticated endpoint revalidates by tag.
- **Storage:** the server's filesystem; an edge's KV store (D9).
- **Private pages** are `Cache-Control: private, no-store`.

## 6. Decisions

**D1 — Two labels.** Every input carries stage and confidentiality. Sources
declare them; static propagation and runtime capability tracking carry them.
Unknown means private.

**D2 — Holes are minimal subtrees at anchored instance paths**, rendered as the
author's own pending state. No boundary syntax.

**D3 — One server** — phase 1's native binary — serves `cached` and `request`
pages and the data endpoint (LLP 1048.001 D7).

**D4 — Streaming is out of order and versioned:** head timing, fills and a
closing checkpoint share one version.

**D5 — Cache keys come from runtime-tracked public reads.**

**D6 — Private data never enters a shared cache.** A `build` or `cached` render
that would include a private value refuses. The refusal names the binding and
the source, with a test per app.

**D7 — Client hints.** The server sends `Accept-CH` for `Sec-CH-Viewport-Width`
and `Sec-CH-Prefers-Color-Scheme`. When present, the viewport and color scheme
become `request`-stage public inputs.

**D8 — Server-only artifacts.** Sources that are only ever answered on the
server can be bundled apart from the client module. Today the whole paired
module ships (`host/web/build.mjs` ~98–104). Until this lands, no claim is made
that server code stays off the client.

**D9 — The edge.** The same render compiles to wasm (`exact-web` targets
`wasm32`) behind a `render` export, for Workers or Deno. Rust sources run
there; TypeScript sources need the edge's own engine and the constraints of LLP
1027.001, so the edge starts with Rust-sourced apps.

## 7. To settle before this becomes a spec

1. The minimal-boundary selection algorithm.
2. Anchors for empty regions, absent arms and multi-root regions, stable across
   fulfillment.
3. Patch ordering, and checkpoint versions shared with LLP 1048.001 §4.
4. Where stage and confidentiality are declared: the module (proposed) or
   Contract.
5. The cache store and the revalidation endpoint's authentication.
6. How a `cached` page's TTL meets delivery's release streams (LLP 1030). The
   plan digest is in every key, so a new release invalidates.
7. The server-only artifact boundary (D8), and its capability rules.

## 8. Verification (when specified)

- Private-data refusal tests per app, including a store read after an await.
- Parity between the request-rendered document and the live DOM, as in LLP
  1048.000 §4.
- Streaming order and equality with the final checkpoint.
- Exact `Vary`: a public input the render doesn't read doesn't split the cache.
- Time to first byte and render time for `cached` and `request` pages.
