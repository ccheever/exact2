## Summary

The server renders two kinds of page and never mixes them (LLP 1048 D3):
- **anonymous pages**, for requests without a session: public data only, and
  cacheable (LLP 1048.000);
- **personal pages**, for requests carrying the reader's session: the whole page
  rendered for that reader, never stored by a shared cache (this RFC).

The rule is structural: a render that received a session is personal, and its
response is private. That has three consequences:
- nothing depends on tracking which reads were personal;
- no labels or read tracking are needed;
- no page has a shared-cached part next to a personal part.

## 1. Personal pages

- **Opt-in per route.** A route declares that it renders for signed-in readers.
  The proposed syntax is `personal=true`, beside `render=` (LLP 1048.003 D5).
  Without a session, the route's anonymous policy applies.
- **The session** is a cookie the app's grants name. The proposed grant is
  `request.cookie <name>`, and the cookie is `HttpOnly`, `Secure` and
  `SameSite=Lax`. Request-stage sources read it through a grant-checked
  request-context capability, the way the store is read today (LLP 1018). The
  store stays empty on the server.
- **The response** is `Cache-Control: private, no-store` with `Vary: Cookie`.
  The server keeps no cache of any kind for personal renders. When the app is
  hosted behind a CDN, the CDN passes requests carrying the session cookie
  straight through on personal routes, and strips cookies from anonymous ones.
- **Isolation** works as for anonymous renders: a fresh runner and module realm
  per request (LLP 1048.000 D10).
- **The checkpoint** carries the reader's answers and nothing of anyone else's.
  The runtime adopts the page as it does anonymous pages; the device's store
  applies afterwards.
- **Mutations** keep their own path. The cookie authorizes rendering pages, not
  changing data, so a cross-site request can't act with it.
- **Cost.** Every personal view is a render. Limits per reader join the server's
  limits (LLP 1048.000 D10).

**For Interview:**
- its backend sets the cookie at sign-in;
- its viewer source reads the credential from the request context on the server,
  and from the store on the device;
- for signed-in web readers, its private routes (messages, notifications,
  profile, settings) and its feeds become personal pages.

## 2. Deferred until a measurement or a consumer asks

- **Streaming.** Flush the shell, then stream holes as their sources answer.
  - Starting point: r2's design — anchored holes, and a versioned stream closed
    by the checkpoint.
  - Waits for: a measured page whose slowest source dominates time to first
    byte.
- **Personal holes inside cached pages**, which is partial prerendering with
  credentials.
  - Why deferred: it needs every read's confidentiality to be known, which is
    the proof obligation r3 removed.
  - Waits for: a measurement showing that a cached shell, plus the device
    filling in the reader's parts, is too slow.
- **Declared public request facts** beyond the URL: a locale from
  `Accept-Language`, or client hints for the viewport or color scheme.
  - Each would become an explicit part of the cache key.
  - Waits for: a consumer.
- **The edge.**
  - Waits for: a consumer. Interview is TypeScript, and the edge would start
    with Rust-sourced apps.
- **Server-only artifacts**: sources answered only on the server, bundled apart
  from the client module.
  - Today the whole paired module ships (`host/web/build.mjs` ~98–104). Until
    this lands, no claim is made that server code stays off the client.

## 3. Removed in r3

- **Confidentiality labels, and runtime tracking of capability reads.** An
  anonymous render has no credentials and no private data to leak, and a
  personal render is never shared.
- **Cache keys from tracked reads, and a `Vary` derived from them.** An
  anonymous render reads only the URL (and, later, declared public facts).
- **A server cache store or KV.** HTTP caches do the storing
  (LLP 1048.000 D11).
- **Private request-context holes in cached pages.** See §2.

## 4. To settle before this becomes a spec

1. The opt-in's syntax. Also, whether a route can be personal without an
   anonymous policy; if so, a signed-out reader gets the not-found or sign-in
   route.
2. The request-context capability: its grant, and how a source tells a server
   render from a device one.
3. Limits per reader, and what a personal render does at its deadline.
4. How the CDN is told which routes are personal, once there is one.

## 5. Verification (when specified)

- A personal response is `private, no-store`, and a shared cache under test
  never stores it.
- An anonymous render never receives a cookie; the server strips them.
- Two readers' requests, interleaved in one process, each get their own page.
- A session cookie can't make a mutation.
- Time to first byte for personal pages, compared with an anonymous page plus
  the device filling in the reader's parts.
