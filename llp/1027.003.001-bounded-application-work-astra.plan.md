# LLP 1027.003.001: Bound application work at the operation boundary

**Type:** Plan
**Status:** Draft
**Systems:** Messages persistence, Fieldnotes queries and editing, browser storage, runner settlement, viewport collections, native presentation and retirement
**Author:** Astra (`gpt-6-astra` at max effort through Codex) for Charlie Cheever
**Date:** 2026-09-20
**Related:** [LLP 1027.003](1027.003-value-transfer-and-shared-storage.research.md) §11–§13; [LLP 1027.004](1027.004-bounded-resource-answers.plan.md) D4/D5/§5; [LLP 1010](1010-scrolling-v1.spec.md) §6; [LLP 1041](1041-graceful-overload.rfc.md); [LLP 1016](1016-async-data-settlement.rfc.md); [LLP 1027](1027-typescript-data-sources.rfc.md) D10; [LLP 1027.002](1027.002-optional-worker-execution.rfc.md); [RULES](../rules/RULES.md); [DEFERRED](../rules/DEFERRED.md)

## 1. Recommendation

Build bounded application operations in this order:

1. Make every admitted Fieldnotes notebook readable through bounded library pages
   and a separate selected-note read.
2. Replace Messages’ successful-write snapshot/diff path with explicit changed
   records, preserving durable atomicity and failure recovery.
3. Consolidate native collection filling, then bound visible construction and
   retirement as well as overscan work.
4. Close the lifetime acceptance for those changes using the existing consumers.

Lifetime checks accompany every slice; the last slice is the repeated application
sweep, not the first time ownership is considered.
Keep ordinary immutable resource answers, the current data seam, and one executor
owner per stateful module.
Do not reopen shared-heap or generic structural-reconciliation work.

This reverses the first two items in the research’s suggested order.
Fieldnotes has a recorded correctness failure with data the app explicitly admits.
Messages’ persistence path is expensive, but its existing refusal and reopen
behavior give a smaller, separately shippable next repair.
A readable notebook is the more urgent result.

**If only one thing can be built, build the complete Fieldnotes slice.**
Cut Messages and native scheduling work before cutting selected-body loading,
search correctness, or draft protection out of that slice.
Do not substitute a higher query-result limit for the repair.

This plan deliberately does not promise that every ordinary operation becomes
independent of accumulated data on every host.
Source inspection found another whole-store cost in browser storage, described
in §3 and §8.
The proposed app changes cannot remove it, and their acceptance must say so.

Charlie commissioned this document, not an implementation campaign.
Codex is the proposed implementer for a subsequent commission; implementation
dates and completed measurements must be recorded when that work actually starts.

## 3. What the source confirms and corrects

| Research finding | Working-tree finding |
|---|---|
| F7: successful Messages writes traverse the model | Confirmed. `snapshot()` enumerates people, live messages and recovery records, then JSON-detaches every value. `persist()` visits the key union, canonicalizes values, and copies the held map after admission. See [app.ts:400–409](../apps/messages/app.ts#L400) and [snapback-client.ts:94–119](../apps/messages/snapback-client.ts#L94). |
| F8: Fieldnotes library reads all bodies | Confirmed. The unbounded SELECT returns every body; `library()` lowercases and filters them in TS. Opening a note currently copies its already-loaded body directly from a library row. See [app.ts:39–42](../apps/fieldnotes/app.ts#L39), [app.ts:70–76](../apps/fieldnotes/app.ts#L70), and [app.contract:211–212](../apps/fieldnotes/app.contract#L211). |
| F9: urgent visible filling escapes the row budget | Confirmed. Visible and pinned rows are excluded from the rationed missing set, and the Apple host explicitly excludes visible rows from its budget. See [window.rs:546–578](../runner/src/instance/window.rs#L546) and [host.rs:730–781](../host/apple/src/host.rs#L730). |
| F10: bounded views do not establish bounded total memory | Confirmed. Messages retains complete thread maps and indexes; the shared collection retains supplied items and keys independently of mounted rows. See [app.ts:26–35](../apps/messages/app.ts#L26) and [collection/mod.rs:41–65](../runner/src/instance/collection/mod.rs#L41). |

There are three corrections or qualifications worth carrying into implementation.

First, F7’s “separate reply answer” is misleading.
The reply sheet is a separate visual consumer, but `replies` is decorated into
the **same** `conversation` result as `messages`.
An open reply thread can therefore enlarge that resource’s transfer and settlement
despite the main transcript window:
[app.ts:243–253](../apps/messages/app.ts#L243).

Second, the “after each received sync page” wording in LLP 1027.004 D5 and the
[queue](../queue/) is stale.
`acquire()` applies pages without calling `restore`; `sync()` rereads and compares
the complete local record set in its final local section, then calls the model
replacement callback if changed:
[snapback-client.ts:129–158](../apps/messages/snapback-client.ts#L129) and
[snapback-client.ts:184–190](../apps/messages/snapback-client.ts#L184).
Research §11’s narrower “when the sync path replaces its records” is accurate.
The full pass remains, including after an unsuccessful sync attempt.

Third, the current Mac presenter uses `CADisplayLink`, rather than the older
`BeforeWaiting` arrangement recorded in LLP 1010.
It still performs urgent synchronous list work and synchronous visible text
rasterization.
UIKit still passes the unlimited list-report value.
See [PresenterMac.swift:346–430](../host/apple/Sources/ExactKit/Mac/PresenterMac.swift#L346),
[TextRasterMac.swift:59–103](../host/apple/Sources/ExactKit/Mac/TextRasterMac.swift#L59),
and [PresenterIOS.swift:368–402](../host/apple/Sources/ExactKit/IOS/PresenterIOS.swift#L368).

The important omission from §11 is **browser whole-file storage work**.
SQLite opens by reading and deserializing the complete file, and exports the
complete database after every execute or transaction:
[storage-worker.js:133–153](../host/web/storage-worker.js#L133),
[storage-worker.js:170–189](../host/web/storage-worker.js#L170), and
[storage-worker.js:113–123](../host/web/storage-worker.js#L113).
Fieldnotes opens, executes `CREATE TABLE IF NOT EXISTS`, and closes for each
operation: [app.ts:28–37](../apps/fieldnotes/app.ts#L28).
Consequently even a library read currently causes a complete database export.

The file provider adds another pass: every operation calls IndexedDB `getAll()`,
including unrelated file contents, before building its temporary map:
[storage-fs.js:153–175](../host/web/storage-fs.js#L153).
These are declared initial limitations in
[LLP 1027 D10](1027-typescript-data-sources.rfc.md#L1036), not inferred defects in SQLite itself.
A targeted SQL UPDATE is not an end-to-end bounded write on this browser backend.

## 4. The contract this plan will establish

Use N for total records, D for changed durable records, K for supplied rows,
V for mounted rows including permitted pins, and B for the relevant payload bytes.
Also distinguish P, the number of Messages people/conversations, from message N.

| Operation | Selected application-work target | Explicit additional cost |
|---|---|---|
| Unfiltered Fieldnotes page | Indexed seek plus K records and their excerpt construction | Body bytes of the selected records; browser file loading until §8’s larger storage work |
| Open a note | Primary-key lookup and that note’s bytes | Browser file loading; editor measurement proportional to the selected body |
| Save a note | That note, its count/revision bookkeeping, and the requested library refresh | Browser whole-database persistence |
| Messages send, reaction, draft or read-state change | D durable records, their bytes, and maintained lookup/index updates | Requested answer decoration; inbox work proportional to P; underlying device work must be measured |
| Move a supplied viewport window | Existing key/geometry work over the supplied window | One row’s actual text and subtree complexity |
| Replace visible content | Bounded construction, publication and retirement opportunities | An indivisible expression or platform shaping call remains a measured unit |

This is an operation contract, not a claim that K rows have constant byte size.
Messages selection strings, reaction decoration and reply rows remain separately
sized work unless explicitly changed below.
For example, selected IDs are incorporated into each decorated row at
[app.ts:221–240](../apps/messages/app.ts#L221).

A performance result must identify which row of this table it establishes.
“Keys evaluated,” “bytes returned,” and “maximum uninterrupted native work” are
different results.
None can stand in for the others.

## 5. Slice 1: make Fieldnotes readable with bounded reads

### 5.1 Resource and query shape

Replace the body-bearing library result with summaries containing
`id`, `title`, `excerpt`, and `pinned`.
Add one selected-note resource containing the body, the requested ID, and the
editor generation.
Keep the existing database identity, notes table, IDs, grants and backup format.

Use a proposed page size of **50 summaries**.
This trades the current complete sidebar for explicit previous/next pages.
It is not a reduction of the notebook’s admitted capacity.
Keep pagination controls explicit in this slice; automatic edge loading is not
necessary to repair the app and would involve the outstanding edge-rearming case.

Create an ordering index on `(pinned DESC, id DESC)`.
Cursors carry the pinned value and exact decimal ID, never an offset or a JS
conversion of the SQLite integer.
Forward pages seek below the cursor; backward pages seek above it in reversed
order and reverse only the bounded result.
A deleted cursor remains a position in that ordering.

Initially read bodies only for the selected candidate page, compute the existing
excerpt, and discard those bodies before returning library summaries.
Do not add a persistent summary/search projection yet.
This retains O(B_selected) excerpt work while eliminating the all-notebook transfer.
The current excerpt semantics are whitespace collapse followed by a UTF-16 slice:
[app.ts:39–42](../apps/fieldnotes/app.ts#L39).

The proposed page size also leaves room beneath the existing query-result limit.
The admitted title/body bounds are 160 and 20,000 UTF-16 units respectively
([app.ts:48–50](../apps/fieldnotes/app.ts#L48)).
Using the UTF-8 upper bound of three bytes per UTF-16 unit, 51 candidate rows,
including lookahead, have at most `51 × 3 × (160 + 20,000)` title/body bytes,
before small ID and cell overhead.
This is a derived bound, not a measurement.
The browser’s actual result accounting and 16 MiB refusal are at
[storage-worker.js:85–99](../host/web/storage-worker.js#L85).

Keep the displayed count as the total notebook count, not matching results.
Maintain a reconstructible singleton count and database revision in SQLite,
updated by notes-table triggers inside the same transaction as each write.
Initialize it once from existing rows; that initialization is O(N).
Use it for the existing capacity refusal as well, so small writes do not acquire
a new `COUNT(*)` scan.
The singleton is an application aggregate, not a second data authority.

Each page SELECT must read its metadata and rows in one SQLite statement,
including a metadata-only result for an empty page.
Do not assume the storage interface supports a read transaction across awaits;
its portable write transaction accepts execute commands only:
[data/host/src/native.rs:106–120](../data/host/src/native.rs#L106).

### 5.2 Preserve search, and name its scan

Keep the exact current predicate:
`(title + "\n" + body).toLowerCase().includes(query.toLowerCase())`.
Do not substitute SQLite `lower`, `LIKE`, token search, or FTS and call that parity.
The current concatenation permits matches across the title/body separator.

Search scans indexed candidate pages in the same stable order, applying that
predicate in TS and collecting at most K matching summaries.
Retain only the accumulated summary page and one candidate page of bodies.
The cursor names the last consumed candidate; lookahead must not skip matches.
This bounds transfer per storage result and memory, but total search remains
O(N + B_notebook) in the worst case.

Release the app’s serialization gate between candidate reads.
Before another read, check whether this search is still wanted.
A newer query replaces queued read interest; a save gets an opportunity between
chunks and is never coalesced.
The current gate covers complete operations
([app.ts:19–24](../apps/fieldnotes/app.ts#L19)); it must no longer cover an entire scan.

Read the database revision with each chunk.
If it changes while assembling a result page, discard that partial page and return
an explicit retryable search notice.
Do not publish a result assembled from incompatible notebook versions.
Cross-page browsing remains live browsing, not a retained database snapshot.

This deliberately declines storage-side substring indexing.
Its take is avoiding duplicate notebook text, index rebuilding, and new search
semantics before bounded reads establish whether search is still the problem.
If that scan later dominates interaction, a maintained folded search projection
is the next app repair; a worker pool is not.

### 5.3 Load a body without overwriting a draft

Change the note-opening action to set the requested ID and increment the editor
generation.
The selected-note resource echoes both.
While it is pending, show loading for that selection and disable editing of its
unloaded body.
Never show the previous note’s body under the newly selected note’s title.

Derive the editor’s initial fields from the matching completed read.
User changes then live in the existing Contract draft state.
Per-field edited flags can distinguish an untouched loaded field from a local
edit without a completion callback.
A late result for another ID or generation cannot supply editor fields.

Preserve the existing successful-save generation guards and dirty comparison:
[app.contract:47–52](../apps/fieldnotes/app.contract#L47).
That `version` is an editor-generation guard, not a database concurrency version.
This slice does not introduce optimistic conflict resolution.
A save to a deleted ID retains the current visible failure and draft-preservation
behavior: [app.ts:83–94](../apps/fieldnotes/app.ts#L83).

Searching or paging must not clear a draft, change the selected note by row
position, or refresh its body underneath edits.
Pinning may move the note outside the current page; the editor still owns its ID.
Opening a note must not refresh the library.

Remove schema creation from ordinary reads after initialization.
Keep database leases short enough that the Rust backup owner can acquire the file;
do not solve repeated open costs by holding a TS handle indefinitely.

### 5.4 Acceptance

Extend the existing native notebook and browser worker tests.
Seed the aggregate boundary directly in their isolated storage; the backup limit
must not become the fixture’s accidental notebook limit.
Verify every admitted note can be reached and opened, including the final page.

Cover Unicode lowercasing, separator-spanning matches, empty queries, deleted
cursors, pin-induced movement, edits during search, delayed body reads, failed
saves, reload, and unchanged total-count semantics.
Use the existing native search/restart and mixed-language backup cases in
[notebook.rs](../apps/fieldnotes/apple/tests/notebook.rs).

Done means the recorded legal-notebook failure no longer occurs, every returned
library answer is summary-only and bounded, and selected reads preserve drafts.
It does not mean browser database I/O is independent of notebook size.

## 6. Slice 2: Messages produces the records it changed

### 6.1 Prepare, admit, publish

Replace `persist(completeRecords)` with an app-private edit batch:
unique record keys mapped to replacement payloads or explicit deletion.
An omitted key means unchanged.
No runner delta format or cross-runtime object representation is introduced.

Each mutation prepares candidate durable records and its local publication changes
while holding the existing local gate.
Copy only touched payloads; do not mutate the committed model before admission.
Perform shape, key, payload and aggregate-count validation before issuing the
durable operation.

Admit the complete edit through the existing `putRecords` mutation.
After admission succeeds, update the private committed map in place for those keys
and publish the corresponding model/index changes without another await.
Remove the union-of-all-keys comparison and `new Map(this.held)`.

Committed payloads must not alias objects later mutated in place.
Use immutable replacement records within this TS owner, sharing unchanged values
where safe.
This is local application ownership, not the research’s shared heap.
Restrict complete-map access to initialization and authoritative resynchronization.

A no-op mutation produces no durable batch.
A canonical comparison is permitted for a touched key when it avoids a redundant
write; it must not discover changes by enumerating the model.
Pure reads retain the existing bypass at
[app.ts:470–473](../apps/messages/app.ts#L470).

### 6.2 Make mutation bookkeeping genuinely local

| Mutation family | Records and local state to prepare |
|---|---|
| Send or generated reply | New message; affected person preview/read state; that conversation’s draft and pending activity |
| Reaction | The addressed message |
| Draft, mute, block or unread state | The addressed person/settings record and affected transient activity |
| Selected deletion or recovery | The addressed message records, affected conversation record, and recovery membership |
| Recovery expiry | Only expired recovery records; enumeration cost remains explicit |
| Contact/group creation | New or changed person/group records and their stable order positions |

Person records currently persist their array positions
([app.ts:402–404](../apps/messages/app.ts#L402)).
Assign stable order positions on insertion; do not renumber every person after a
prepend and then claim the edit touched only the new conversation.
Retain deterministic tie-breaking during restore.

Maintain a person-ID lookup for ordinary message operations.
Keep sorted thread arrays for now.
Their middle insertion/removal can still shift O(thread) entries; that trade is
preferable to introducing a new ordered-tree implementation in this slice.

Track outgoing messages whose delivery state still needs advancement.
`advanceReplies` currently visits every outgoing message
([app.ts:360–366](../apps/messages/app.ts#L360)).
Update the tracked set when inserting, restoring or changing delivery state.
A tick with no delivery changes should not become another historical scan.

Transient rollback preparation must also be local.
Replace the whole `pending` map copy at
[app.ts:474](../apps/messages/app.ts#L474) with touched entries and scalar state.
Keep ID allocation monotonic; refused edits may leave gaps.

### 6.3 Failure and bulk semantics

Keep the current atomic edit limit.
It is **512 changed records**, including person/settings records, not 512 messages:
[snapback-client.ts:105](../apps/messages/snapback-client.ts#L105) and
[schema.q:24–30](../apps/messages/snapback/schema.q#L24).
The payload ceiling remains the schema’s 65,536 bytes per record
([schema.q:6–9](../apps/messages/snapback/schema.q#L6)).

Preflight a bulk delete, recovery or purge before changing visible state.
If its complete effect exceeds the record limit, refuse the whole operation with
a useful explanation.
Do not split it into independently committed batches, raise the cap, or silently
delete only a prefix.
A resumable bulk-operation protocol is explicitly outside this plan.

Before durable admission, failure discards the prepared edit and leaves the draft
and committed model intact.
After known admission, a publication failure requires recovery from durable state;
it must not be reported as an unexecuted write that is safe to repeat with a new ID.
An uncertain outcome remains pending until reconciliation establishes its outcome.

Keep full restore as exceptional recovery and initial-load machinery.
Do not run it after successful small writes.
The browser device’s own reconstruction after failed storage remains separate:
[snapback-core.ts:39–46](../apps/messages/snapback-core.ts#L39).

### 6.4 Acceptance and limits

Extend [snapback.test.ts](../apps/messages/snapback.test.ts), which already uses
the actual Wasm device, SQLite and server and injects a failed durable commit.
Extend the native draft/reopen and refused-save cases in
[snapback_tests.rs](../apps/messages/apple/src/snapback_tests.rs).
Exercise each mutation family, no-ops, cap boundaries, lost receipts, offline
reopening, and a successful edit after failure.

Observe admitted key counts and encoded bytes through those existing test seams.
They establish the boundary size, not the absence of an earlier hidden traversal.
Use the existing actual-bytecode timing comparison pattern in
[window.rs:290–340](../apps/messages/apple/tests/window.rs#L290) for matched
small-write diagnostics, holding D and payload size fixed while increasing N.

Done means successful small mutations no longer snapshot, diff or copy the complete
application record map, and durability tests preserve the same outcomes.
Startup, complete sync reconciliation, inbox enumeration, recovery scans, sorted
array shifts, selection output and the reply sheet retain their named costs.
Underlying Snapback prediction/rebase work and browser persistence are not proven
O(D) by a smaller `putRecords` request.

## 7. Slice 3: native filling must have a presentation policy

First consolidate the measured Markdown list and the shared viewport collection.
Carry logical selection and full-document copy onto the shared collection, then
remove the redundant measured-list route.
This follows the existing [queue entry](../queue/).
Do not add a third collection path or independently extend both current paths.

Carry the useful existing behavior across: key anchors, measured-height epochs,
focus/interaction pins, overscan filling, and deferred retirement.
Fix provisional-height edge rearming before adopting automatic page edges in
another production consumer.
The declared case is in [LLP 1027.004 D5](1027.004-bounded-resource-answers.plan.md#L208).

Then apply creation admission to **visible rows too**.
A distant jump may publish lightweight estimated row space with an explicit loading
state while destination content is prepared.
Already valid destination rows remain usable.
Do not paint old rows at a new location, present an empty result as complete, or
dispatch an action through placeholder geometry.

Selection remains keyed logical text.
A placeholder cannot become a selection endpoint or accessibility target for
unavailable content.
Existing selection may survive eviction; copy continues through logical row
projection rather than mounting the selected range.

Construction proceeds through a private, generation-qualified row preparation.
Publish a complete row only after its values, subtree and geometry are coherent.
Superseding geometry discards obsolete preparation before publication.
There is one desired window and one candidate per owner, not a queue of abandoned
jump destinations.

Break preparation at subtree and text-paint boundaries where possible.
Reuse measured line information and existing text workers.
Remove the synchronous visible-raster escape at
[TextRasterMac.swift:90–93](../host/apple/Sources/ExactKit/Mac/TextRasterMac.swift#L90)
once the loading/retained-content policy is implemented.
Do not pretend that moving rasterization also moves attributed-string preparation
or kernel measurement.

Use the Mac display-link opportunity and the equivalent UIKit frame opportunity
to resume work, alternating creation, text publication and retirement.
A deadline check controls whether another unit starts.
It cannot bound an indivisible expression or shaping call already running.

Keep resource settlement atomic.
The native executor already drains one completion or refusal per pump
([executor_core.rs:171](../host/apple/src/executor_core.rs#L171);
[LLP 1041 §8.4](1041-graceful-overload.rfc.md#84-bounded-native-http-admission-and-completion-pumping)).
Do not replace this with partial resource commits or reorder durable outcomes.
Presentation may lag a complete committed answer, with qualified input ownership.

Acceptance uses Markdown’s distant jump and richly styled row, Messages stress
during updates, and Completion Storm during input.
Include UIKit, not only the shared Rust half.
A row-count improvement alone does not close this slice: record the longest
observed construction, apply and retirement units and remaining indivisible work.
If the selected workload still exceeds its observed presentation opportunity,
leave that acceptance open rather than certify a frame-rate bound.

## 8. Browser storage: take the small repair, expose the larger debt

Include a narrow host cleanup with the Fieldnotes work:
make point file reads, stat, and point writes use targeted IndexedDB requests
within their existing transactions.
Read the required parent/target records; do not load every file’s contents.
Keep directory-wide operations proportional to the directory they actually affect.

This removes the unrelated-file amplification in
[storage-fs.js:153–205](../host/web/storage-fs.js#L153).
It preserves app scoping, Web Locks, atomic publication and failure behavior.
Use the existing browser storage tests; add no diagnostic service or new file API.

**Do not include a new SQLite persistence backend in this campaign.**
Removing whole-file import/export requires page-backed persistence, not another
cache over `sqlite3_js_db_export`.
The selected architectural direction for that subsequent work is page-backed
SQLite on the existing storage worker, preserving the existing capability surface.

That replacement must resolve ordinary SQLite-file access through `storage.fs`,
cross-tab ownership, quota failures, crash recovery and existing durable data.
This document does not authorize a new backing format, a migration path contrary
to the current rules, or silently requiring cross-origin isolation.
Those decisions are larger than the app repair and need a concrete storage plan.

Until then, browser database opening costs O(database bytes), and each write
persists O(database bytes).
Fieldnotes’ bounded reads fix readability, not that I/O bound.
Messages’ changed-record production fixes its TS integration, not that persistence
bound.
A claim that “one send now costs only the changed records on web” would be false.

Once these app slices land, this browser backend is the next storage priority,
ahead of shared representations, generic resource deltas or new showcase work.

## 9. Lifetime and overload acceptance

Use one committed resource answer and the existing newest-request semantics.
Do not add a visited-page cache.
Fieldnotes retains one summary page, one selected body, the draft/reference values,
and one bounded search chunk.
Messages retains its complete model and indexes; that remains O(N).

Every new candidate and retired owner must have a named release condition.
Charge old and new ownership during replacement.
Removing a cache entry is not release while a view, worker or callback retains it.
Do not send runner `Rc` values to another thread merely to move destruction.

Retirement receives its own continuation opportunity and admission bound.
An obsolete candidate cannot accumulate behind a newer candidate indefinitely.
If ownership cannot be reclaimed safely, stop admitting more replacement work
and expose pending/refused state; do not terminate arbitrary native work.

Keep existing native HTTP and raster limits.
The raster budget includes retained backing and reservations under
[LLP 1010 §6.3](1010-scrolling-v1.spec.md#63-raster-memory-is-a-separate-budget).
Browser-decoded images, opaque codec allocations and complete process memory
remain distinct observations.
No new blanket “application memory cap” is proposed.

Repeat traversal, page replacement, note changes and module replacement.
Hold stale completions, retain and release pins, inject failed operations, then
stop load and observe recovery.
An admitted durable effect must reach an outcome or remain visibly pending;
retiring read interest must not discard its write.

Use the existing twenty-traversal collection acceptance from
[LLP 1010 §6.4](1010-scrolling-v1.spec.md#64-acceptance-and-landing).
Compare the same settled position after warmup and after repetition.
Growth in visited-row state fails; growth in Messages’ admitted durable model is
reported as model growth, not relabeled as a collection leak or hidden in RSS.
