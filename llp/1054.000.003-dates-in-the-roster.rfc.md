# LLP 1054.000.003: Dates and relative time in the roster

**Type:** RFC
**Status:** Draft
**Systems:** Roster (`plan/tables/format.json` `stdlib`, `runner/src/stdlib.rs`), Contract compiler (a literal check on one argument), Caltrain (migration off `formatClockTime`)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-26
**Related:** LLP 1054 D8 (the finding); LLP 1054.000 §Not proposed ("D8 stays a cost of explicit time"); LLP 1027.000.000 D4 and open question 3 (this answers it); LLP 1027.000 (explicit time; no ambient clock); LLP 1005 §5 and LLP 1004 D4/D6 (the roster: locale-free, added by fixture, a ticking clock never re-queries); LLP 1047 §6 (the core diet); LLP 1054.000.004 (what else the Bluesky data layer asks)

## Summary

Contract can show a timestamp only as a string a data source made. A relative
label ("5m ago") is only correct for the minute it was made in. So an app
that shows them passes a minute-granular clock into every list resource, and
each list is re-asked once a minute to rebuild its labels. The Bluesky port
does this for ten resources (LLP 1054 D8). Moving its data layer to
TypeScript (LLP 1027) makes every one of those re-asks a JSON crossing of the
whole list.

LLP 1027.000.000 D4 already says where relative text belongs: "In Contract,
as a derive over `time.epochAtZero + now()`… not a request". Its open question
3 asks whether Contract gets a date formatter or dates stay in TypeScript.
This RFC answers **yes, four roster entries**:

| entry | example |
|---|---|
| `formatDate(epochMs, utcOffset, style)` | `"Sep 26, 2026"` |
| `formatTime(epochMs, utcOffset, style)` | `"1:02 PM"` |
| `formatRelativeTime(thenMs, nowMs, style)` | `"5m ago"`, `"in 2 hours"` |
| `calendarDays(thenMs, nowMs, utcOffset)` | `1` (yesterday, in the viewer's zone) |

Every output is the output of `Intl` in `en-US` for the same inputs, so the
browser is the test oracle ("the web is the standard"). There is one declared
exception, the AM/PM separator (§D5). The entries stay locale-free and
deterministic like the rest of the roster. `formatClockTime` is exactly
`formatTime(t, 0, "short")`, so it comes off the roster: that is the take.

With these, a source returns `createdAt: number`. Only the view reads the
clock, and a minute tick re-evaluates text, not resources (LLP 1004 D4).

## Motivation

**What an app does today.** `now()` is elapsed milliseconds
(`runner/src/stdlib.rs:50`). The date arrives as a host fact, `exactTime`,
with `epochAtZero` and `utcOffset` (`runner/src/time.rs:9-11`). The roster's
only time formatter is Caltrain's `formatClockTime`, which is UTC `h:mm AM`
(`stdlib.rs:113-126`). So:

- **Bluesky** (outside the repo) derives
  `clock = time.epochAtZero + floor(now() / 60000) * 60000` and passes it to
  `session`, `homeFeeds`, `authorFeeds`, `threads`, `notes`, `unread`,
  `results`, `convos`, `chats` and `hasNew`. Its Rust crate makes `"5m"`
  (`data/src/fmt.rs:112`, `ago`) and `"Sep 26, 2026 at 1:02 PM"` (`date`).
  Every minute, every loaded list is re-asked, re-shaped and re-checked
  (`runner/src/runner/settlement.rs:385-405` reuses an answer only when the
  arguments are equal).
- **RealWorld** makes `"September 26, 2026"` in TypeScript with a hand-written
  `MONTHS` table (`apps/realworld/app.ts:21-25`).
- **Messages** stores fixture labels (`"9:41 AM"`, `"Yesterday"`, `"Monday"`;
  `apps/messages/app.ts:10-15`), the calendar-relative style of iOS Messages
  and Mail.
- **Typetour** hard-codes `"12m ago"`, `"1h ago"` (`apps/typetour/app.contract:72-74`).

**Why a TypeScript source can't fix it.** LLP 1027.000.000 D4 offers a second
route: a pure source `relativeLabels(timestamps, minute)` that re-answers once
a minute. For a list this doesn't work. The labels come back as a separate
`list<Label>`, and a row inside `each p in feed.posts` has no way to find its
own label: Contract has no list indexing and `fn` cannot loop (LLP 1054 L5).
The label has to be computed from the row's own timestamp, in the view.

**Why not a Contract `fn`.** Relative time *without* a calendar fallback can
be written as a `fn` today, over `floor` and `toString`. A probe with nested
ternaries for counts and a label compiles (1,437-byte plan). But "Sep 12",
"Saturday" and "yesterday in my zone" need civil-from-days date arithmetic and
month names. A `fn` is one expression over its parameters and the roster
(LLP 1006 §3). The corpus calls it "the escape for a price string or a choice,
never a traversal" (`contract/corpus/fn.contract:1-4`).

## Design

### D1 — `formatDate(epochMs, utcOffset, style) -> string`

The calendar date of `epochMs + utcOffset × 60,000` in the proleptic
Gregorian calendar, formatted as `Intl.DateTimeFormat("en-US", options)` with
`timeZone: "UTC"` would format that shifted instant.

| `style` | Intl options | 2026-09-26 |
|---|---|---|
| `"short"` | `dateStyle: "short"` | `9/26/26` |
| `"medium"` | `dateStyle: "medium"` | `Sep 26, 2026` |
| `"long"` | `dateStyle: "long"` | `September 26, 2026` |
| `"full"` | `dateStyle: "full"` | `Saturday, September 26, 2026` |
| `"month-day"` | `month: "short", day: "numeric"` | `Sep 26` |
| `"weekday"` | `weekday: "long"` | `Saturday` |

The four `dateStyle`s are Intl's. `month-day` is the same-year fallback that
social feeds use (Bluesky's `ago` beyond 30 days). `weekday` is the
calendar-relative style's middle case (Messages' `"Monday"`). Each has one
fixture. No other options bag is admitted (see *Refused*).

### D2 — `formatTime(epochMs, utcOffset, style) -> string`

| `style` | Intl options | 13:02:27 |
|---|---|---|
| `"short"` | `timeStyle: "short"` | `1:02 PM` |
| `"medium"` | `timeStyle: "medium"` | `1:02:27 PM` |

`long` and `full` print a zone name, which the runner does not have
(`exactTime` carries an offset, not a zone; LLP 1027.000.000). They are not
admitted.

A date and a time together are composed by the app with Intl's joiners:
`"long"` and `"full"` join with `" at "` (`September 26, 2026 at 1:02 PM`), and
`"medium"` and `"short"` with `", "`. This is written in the authoring notes,
not taken as a fifth argument.

### D3 — `formatRelativeTime(thenMs, nowMs, style) -> string`

Both arguments are epoch milliseconds. Δ = `nowMs − thenMs`, and a positive Δ
is the past.

1. If `thenMs ≤ 0` or `nowMs ≤ 0`, the answer is `""`. The date is unknown
   until the host says it (`epochAtZero` is 0 at bake and at boot), and a blank
   is better than "in 56 years". An app passes
   `time.epochAtZero > 0 ? time.epochAtZero + now() : 0`, as Bluesky does.
2. If |Δ| < 1,000 ms, the answer is `"now"`: Intl with `numeric: "auto"` for 0
   seconds, the same in every style.
3. Otherwise the unit comes from |Δ|, truncated toward zero:

| |Δ| | unit | value |
|---|---|---|
| < 60 s | second | ⌊s⌋ |
| < 60 min | minute | ⌊min⌋ |
| < 24 h | hour | ⌊h⌋ |
| < 30 days | day | ⌊days⌋ |
| < 365 days | month | max(1, ⌊days / 30.4375⌋) |
| otherwise | year | max(1, ⌊days / 365.2425⌋) |

   It is formatted as `Intl.RelativeTimeFormat("en-US", { style, numeric:
   "always" }).format(±value, unit)`, negative for the past:

| `style` | past, 1 / 2 | future, 2 |
|---|---|---|
| `"narrow"` | `1m ago` / `2m ago`, `1d ago`, `2mo ago`, `3y ago` | `in 2m` |
| `"short"` | `1 min. ago` / `2 min. ago`, `1 day ago` / `2 days ago`, `2 mo. ago`, `3 yr. ago` | `in 2 min.` |
| `"long"` | `1 minute ago` / `2 minutes ago` | `in 2 minutes` |

   (Measured with Node 26.9.0 (ICU 78.3); the full grid is the test fixture.)

*Why `numeric: "always"`:* with `"auto"`, Intl's narrow style says
`last mo.`, `last yr.` and `last wk.`. It also says `yesterday` for any Δ from
24 to 48 hours, which is wrong in the evening. Calendar-relative words belong
to `calendarDays` (D4), where "yesterday" means the viewer's yesterday.

*Why no weeks:* social feeds (Bluesky, X) go from days to a date, and
Messages goes from a weekday to a date. Neither says "3w ago". Weeks can be
added by fixture.

*Why months and years by average length:* they are approximations. An app that
wants the exact calendar switches to `formatDate` after some age, as Bluesky
does at 30 days:
`age < 2592000000 ? formatRelativeTime(t, n, "narrow") : formatDate(t, off, "month-day")`.

### D4 — `calendarDays(thenMs, nowMs, utcOffset) -> number`

The number of calendar days from `thenMs`'s local date to `nowMs`'s local date,
both shifted by the same `utcOffset`: 0 is today, 1 is yesterday, and −1 is
tomorrow. With it, the calendar-relative style is one `fn`:

```
fn when(t: number, n: number, off: number): string = calendarDays(t, n, off) == 0 ? formatTime(t, off, "short") : calendarDays(t, n, off) == 1 ? "Yesterday" : calendarDays(t, n, off) < 7 ? formatDate(t, off, "weekday") : formatDate(t, off, "short")
```

`"Yesterday"` stays the app's word. It is capitalized differently in different
places, and Intl's `"yesterday"` is lower case.

### D5 — Deterministic, locale-free, one declared deviation

- **Pure.** Every input is an argument. Nothing reads a clock, a zone database
  or a locale (LLP 1027.000 D1). The runner implements each entry once
  (`format.json:823`), so the web, Apple and Linux print the same bytes.
- **`en-US` only**, as `formatClockTime` and the rest of the roster already are
  (LLP 1005 §5, "deterministic and locale-free by design"). A locale is a
  launch-time value that has no mechanism yet (LLP 1053 G9). When it arrives,
  these entries gain a locale argument or a sibling. A TypeScript source that
  needs another locale today has Hermes's `Intl` (LLP 1027 D5).
- **The fixed offset** is the zone's *current* offset (`exactTime.utcOffset`;
  `validate` bounds it to ±18 h, `runner/src/time.rs:24-34`). A timestamp from
  the other side of a daylight-saving change is shifted by the wrong hour, so a
  post made at 00:30 in winter can print as the previous day in summer.
  Named zones need tzdata, which costs hundreds of kilobytes. Refused until an app
  needs it; the deviation is declared here and in the authoring notes.
- **Declared deviation: the AM/PM separator is U+0020.** ICU 72 and later
  emit U+202F (narrow no-break space) before `AM`/`PM`. Engines patched it
  back unevenly (Node 26.9.0 prints U+0020), so the browser is not a stable
  oracle for this one character. `formatClockTime` has
  always printed U+0020. The oracle test normalizes U+202F to U+0020.
- **Invalid input.** A non-finite argument, an `epochMs` outside ±8.64 × 10¹⁵
  (JavaScript's `Date` range), a `utcOffset` outside ±1,080, or a `style` that
  is not listed gives `""`. See D6 for how a bad style is caught earlier.

### D6 — `style` must be a string literal

The type table can say `string` but not "one of these six". The compiler checks
the third argument of `formatDate`, `formatTime` and `formatRelativeTime`:
it must be a string literal naming a listed style. Otherwise it refuses with
`type-format-style` ("`formatDate` style must be one of `short`, `medium`,
`long`, `full`, `month-day`, `weekday`"). This is the precedent `first` set
for special typing in `contract/types/src/lib.rs:710`. The runtime `""` in D5
then covers only plans that were not compiled by this compiler.

### D7 — The take: `formatClockTime` leaves the roster

`formatClockTime(t)` is `formatTime(t, 0, "short")` byte for byte (UTC,
`h:mm AM`). Caltrain's two calls migrate, the corpus's reject cases move to
the new name, and the entry is removed. NOT-DOING asks for one thing off the
list per thing on (`rules/NOT-DOING.md:350-351`). This takes one roster entry
off for four on, and removes the only app-specific date formatter.
`formatCountdownMinutes`, `formatDistance` and `formatWalk` stay Caltrain's.

## Costs

- **Plan format.** Four `stdlib` rows added and one removed. `FORMAT_DIGEST`
  changes, so every plan re-bakes, older plans are refused at load, and a new
  update cohort starts (`bake/src/compat.rs:298-300`). No opcode is added; a
  call is the existing `Call` with a `Stdlib` operand (`format.json:755-759`).
- **Runner code.** About 200 lines in `stdlib.rs`: civil-from-days (Hinnant's
  algorithm, integer only), two name tables (12 months short and long, 7
  weekdays, about 150 bytes), and the Intl plural rule for `en` (one vs other).
  It is written without `core::fmt`, as `stdlib.rs:108-109` already does for
  numbers on the boot path. It can be charged to the use-set when LLP 1047 D2
  covers stdlib functions (`runner/src/uses.rs` doesn't yet).
- **Compiler.** One literal check and one diagnostic (D6).
- **Nothing else.** No data-seam, host, ABI or kernel change. The hosts already
  deliver `exactTime` (web `glue.js:1362`, Apple `Session.swift:786-790`,
  Linux `host/linux/src/app.rs:289-297`).

## Tests

- **Oracle.** A generated fixture from Node's `Intl` (checked in, with the ICU
  version recorded): every `formatDate`/`formatTime` style over about 200
  instants (month and year ends, leap days, 1970, 2000-02-29, negative epochs,
  offsets of −720, 0, +345 and +840), and every `formatRelativeTime` style
  across each bucket edge (999 ms, 1 s, 59.999 s, 60 s, 29 d, 30 d, 364 d,
  365 d) in both directions. The runner's output must match exactly, after
  the U+202F normalization.
- **`calendarDays`.** Across midnight in positive and negative offsets, and
  across a year boundary.
- **Invalid input.** Non-finite values, out-of-range epochs and offsets, and
  `thenMs`/`nowMs` ≤ 0 give `""`.
- **Compiler.** A non-literal or unknown style refuses with
  `type-format-style`. `formatClockTime` is unknown after the take.
- **Runner.** A view site reading `formatRelativeTime(p.at, clock, "narrow")`
  re-evaluates on a timer commit while the resource that supplied `p` is not
  asked. The test counts `answer` calls, as `contract/cli/tests/it/time.rs`
  counts host facts.
- **Caltrain.** `bun scripts/smoke.mjs web` is unchanged after migration.

## What an app writes

```
resource time = exactTime() as shape Time
state minute = 0
action tick writes minute
  minute = time.epochAtZero > 0 ? time.epochAtZero + now() : 0
task clock mount
  every(30000, tick)

resource homeFeeds = feeds(session.did, homeFeed, feedMore, feedFresh) as shape list<Feed>
…
text formatRelativeTime(p.createdAt, minute, "narrow")
```

`homeFeeds` no longer takes the clock. The tick commits `minute`, the view
sites that read it re-evaluate (`runner/src/instance/deps.rs:315-317`), and no
source is asked. A thirty-second tick keeps "5m ago" within half a minute.
A seconds display needs a one-second task and pays for it.

## Refused

- **A pattern language** (`formatTime(epochMs, zone, pattern)`, as 1027.000.000
  Q3 floated). ICU skeletons and patterns are a large surface with locale
  semantics attached. Named styles cover every fixture in hand.
- **An ambient wall clock** (`wallNow()`). 1027.000.000 D1 rejected "a stdlib
  `date()` beside `now()`". The app composes `epochAtZero + now()` explicitly.
- **Named time zones and DST** (tzdata, hundreds of kilobytes). See D5.
- **Other locales.** Waits for a locale fact (LLP 1053 G9).
- **Compact numbers** (`1.2K`). The probe shows a `fn` over `floor` and
  `toString` does it (compiled, not driven). They are not time-varying either:
  a count changes only when its source answers anyway.
- **Bluesky's bare form** (`"5m"` with no "ago"). It is not an Intl form. See
  open question 2.

## Open questions for Charlie

1. **Consumer.** NOT-DOING admits named consumers, and Bluesky is not one
   (LLP 1054.000). In-repo, Caltrain (via the take), Typetour's literals and
   RealWorld's `MONTHS` table would use these. Messages would if its labels
   moved to the view. Is that enough, or does this wait for Bluesky's
   admission?
2. **A `"narrow-bare"` style** for feeds that drop "ago" (`5m`, `3h`). It has
   one fixture (Bluesky) and no Intl equivalent. Recommend no: apps write
   `formatRelativeTime(t, n, "narrow")` and live with "5m ago".
3. **Seconds.** Bluesky prints `"5s"` and below 5 s `"now"`; this RFC says
   `"now"` only under 1 s, as Intl does. Should the second bucket start at a
   threshold (like 5 s or 45 s) instead?
