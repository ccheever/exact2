# LLP 1149.001: The renderer's cost program

**Type:** RFC
**Status:** Draft r3, 2026-10-30. r1 and r2 were reviewed blind by Sol and Claude (`llp/reviews/rfc-2026-10-30-1149.001-r{1,2}.{sol,claude}.md`); r2 narrowed both to contracts; r3 writes them (§R).
**Systems:** host/ink, host/apple-painted, host/windows, host/linux (the painter and the presenter), bench/heavy-list
**Author:** Claude Fable 5.1 (orchestrator); Astra (gpt-6-astra) builds each stage
**Date:** 2026-10-30
**Related:** LLP 1149 (the renderer: this refines its D1.1, D2.5, D4, D6.3, D7, D9, D11 and D15), LLP 1148 (the options), LLP 1142 (traces), LLP 1079 (`perf`), `bench/heavy-list/gpui/RESULTS.md` (G3c, G4, G5 prepared, G6c: the scoreboard)

## Summary

Ink is now measured against egui, GPUI and the native hosts on the same screen, the same
input and the same probe, on the Mac and on Windows. It starts fastest on Windows, matches the
field on cadence, sits within GPUI's range on fling CPU on the Mac, and costs more than egui
during a fling on both platforms. The traces say where the cost is and most of it is plumbing
around the renderer. This document orders the work: first the numbers the program will be
judged by, published and reproducible, with the counters that turn its leads into facts;
beside them the dated obligation LLP 1149 already carries, stated as LLP 1149 wrote it; then
the fixes that need no design change, each with its contract and prediction; then the design
changes, as amendments to LLP 1149 with their contracts written; then the platform layers. It
says how each stage is measured and what it will not do.

## 2. Where the cost is

The ink carrier's ten-second Mac fling, main thread, from S1.4's image-disabled control trace
(`target/s1-4/g3-control/ink-1.json.trace.json`). These are **elapsed** main-thread spans on
`CACurrentMediaTime`, each charged to its innermost phase; G4's 43.8 ms/s is **CPU time**. The
two agree in magnitude, which is a consistency check, not the same instrument. The table is
the orchestrator's derivation and is not yet in RESULTS.md; by §4's rule it is not a number
until Stage 0 publishes it with its script. Counts are totals over the ten seconds.

| Phase | ms/s | Count in ten seconds | Notes |
|---|---:|---:|---|
| Event-loop service passes | 12.6 | 3,579 | 35 µs each; ten per presented frame: the runner, hatches and image polling pumped on every wheel event, tick and wake |
| Paint walk | 5.7 | 358 | 0.16 ms each |
| Carrier draw and scene encode | 5.9 | 348 | the instance buffer rebuilt every frame |
| Glyph raster; refine collections; layout | 1.2; 1.0; 0.4 | 481; 4,775; 3,362 | layouts at a microsecond each |
| Wheel input | 1.3 | 422 | |
| Unattributed | ~15 | | AppKit and winit delivery, display-link wakes, the probe; not yet marked |

On the GPU, per frame in the same trace: the scene's command buffer 0.23 ms; the pass that
samples the compose target into the drawable 1.0 ms (S1.4's normal run: 1.46). A one-quad pass
costing four times the scene is not proportional to its work; Stage 0 explains it (the GPU's
clock state, the sRGB-to-unorm conversion, a wait inside the measured interval) before M3's
saving stands. Off the main thread: ImageIO decodes at the drawn size (the same code as egui's
arm), the staging ring's waits (blocked time, not CPU), the present worker's completion wait.

Three leads the reviews found in the code, each a hypothesis until Stage 0's counter says:

- **The viewport-target pool** (`host/ink/src/layer.rs`) reuses a target as soon as its last
  GPU use completes and evicts a target unused for 120 frames; a lagging worker therefore
  makes a frame allocate fresh targets, and nothing frees them for two seconds. A target is
  about 10 MiB at 1600×1600; 335 MiB is 34 of them; private textures have no malloc stacks,
  which fits S1.4's description; G6b found 1,201 targets on Windows during the repaint churn,
  which G6c removed. Against it: S1.4's tracked textures total 61 MiB in the normal run, the
  footprint falls to 246 MiB by the end of the fling phase, and egui shows a 320 MiB transient
  with no such pool. So a second cause stays open; Stage 0 reads `layer_targets` and
  `layer_bytes` beside a `vmmap` of the same run.
- **A kept row is reused only at whole-device-pixel offsets** (`Ink::reusable`,
  `host/linux/src/ink/rows.rs`): rows are recorded in row space and replayed by a per-instance
  translate, but each glyph was rasterized at a quarter-pixel horizontal phase and a truncated
  y chosen at record time, so a fractional replay would place the wrong raster. AppKit's
  momentum deltas are fractional. If most frames fail the test, rows re-record every frame,
  which would look exactly like the painter walking every node; the kernel's change receipts
  already reach the painter, which derives a row's stale and suspect state from them, and a
  valid kept row is not walked today.
- **On Windows, clip masks were rebuilt per paint** (G6b's largest named main-thread item);
  G6c cut the paints but no trace of the G6c build exists yet.

## 3. The program

Each stage is one or more lanes: trace, predict in writing, change one thing, measure as §4
says, two-family review, land. Stages are ordered by evidence and by date, not by size. Stage
0 and Stage 0b run beside each other.

### Stage 0: the numbers first

One lane, no design change, before any prediction stands:

- Publish §2 as a section of RESULTS.md with its script beside `aggregate.mjs`, run on the
  retained S1.4 traces and on a fresh trace of the current build, printing elapsed and CPU
  separately and every count with its denominator.
- Cumulative counters in the live carrier, read through the agent's `state` and the probe
  (on Windows `perf` drives the headless presenter, not the window): paint attempts,
  submitted frames and displayed frames; service passes per display period; rows replayed,
  rows recorded, and rows refused as not reusable, separately from stale, suspect and
  picture-arrival re-records; viewport targets allocated, reuses blocked by incomplete GPU
  work, targets retained and their bytes, targets retired; clip masks built; the text
  engine's existing shaping-cache counters. Read them during a fling on both platforms,
  with a `vmmap` of the Mac run at its peak.
- Mark the Mac carrier's unattributed ~15 ms/s: AppKit and winit event delivery, the
  display-link wake, the probe's own work.
- A rest-phase trace on both carriers naming every wakeup.
- A trace of the G6c build's fling on Windows.
- Publish the display-link phase measurement S1.5's analysis made (the callback's position in
  the refresh interval) with the same script, and explain the present pass's 1.0 ms.

### Stage 0b: the dated obligation, as LLP 1149 wrote it

D15 keeps direct Metal on a dated obligation, 2026-11-04 or the carrier's enablement, with
three parts: the warm device-plus-pipeline phase within 5 ms of the wgpu arm's (today about
16 ms over); a cache miss that never blocks first pixel, D6.3's rule, with the CPU painter's
first frames presented through the same swap chain while pipelines build and the archive is
populated off the path; and the complete first screen at p50 within the 100 ms budget with
the phases summed, measured with an empty and a retained application cache. Stage 0b lands
the first two by the date. The third is M10's: no arm on either platform is within the budget
today (313 to 354 ms on the Mac), and D15 reads that case as no more than 10% regression
against the platform's painter where the baseline already exceeds the budget, which is the
clause Stage 0b is accepted on for the third part. This is the renegotiation, stated.

### Stage 1: fixes within the design

These amend one table row of LLP 1149 (M5, D7's pacing row) and nothing else; the RFC
records their contracts and predictions.

- **M1, coalesce the polling; service pending work independently.** Input delivery stays
  per event: a wheel or pointer event applies its input and advances the clock when it
  arrives, as now. What changes is the polling: the runner's command queue, hatches and image
  reports are pumped once per display period while the display link runs, not on every event,
  tick and wake. Pending work is serviced when it arrives, in order: a due timer on its wake,
  a hatch or executor reply on its wake, an image report on its wake; a wake whose cause is
  already served by the period's pass does nothing. A timer's latency is therefore unchanged;
  what is removed is the redundant pumping of empty queues. The headless agent is untouched
  (requests are serviced synchronously; `clock` and `settle` step the runner directly), and so
  is the live-mode agent request, which keeps its synchronous service. Predicted, if Stage 0
  confirms the 12.6 ms/s as near-empty passes: Mac main thread 44 → ~34 ms/s.
- **M2, nothing wakes at rest** except a due timer, a reply or an image. Predicted after the
  rest trace names the wakeups: Mac ≤ 0.4 ms/s; Windows no tick in ten seconds.
- **M4a, the pool's policy**, if and only if Stage 0's counters show idle targets, not
  targets held by incomplete GPU work: retain for the frames in flight plus a short grace.
  Predicted: the Mac peak footprint down by the idle targets' bytes; CPU unknown, since
  trimming adds allocation. **M4b, one copy per upload** into a per-frame staging arena
  fenced on that frame's completion. Predicted: at most the 6.5 ms per ten seconds of upload
  preparation now on the main thread; a small number, honestly.
- **M5, the display link.** During a phased gesture the Mac carrier keeps the link running
  through three quiet ticks (S1.6); the per-frame restart S1.5 found applies to unphased
  events only. What remains is the callback's position in the refresh interval, measured by
  the orchestrator at about 5 ms after the presented-time grid and published in Stage 0.
  `CADisplayLink` from `NSView.displayLink` (macOS 14, the carrier's minimum) gives a target
  timestamp and a callback at the interval's start. Instrument: the probe records each wheel
  event's timestamp and each drawable's presented time; input-to-photon is their difference,
  a new row. Prediction, as a hypothesis: one refresh less. Amends D7's table, which names
  `CVDisplayLink` for the Mac.

After stage 1 the arithmetic is main 44 − 10 (M1) ≈ 34 and process 86 − 10 − small ≈ 75 on
the Mac. The direction of 60 needs a further budget of about 15 ms/s: M6 and M7 name 8.6 on
the main thread; the rest is unnamed until Stage 0 marks the unattributed 15 and the worker.
The Windows prediction waits on Stage 0's trace of the G6c build.

### Stage 2: design changes, as amendments to LLP 1149

- **M3, render into the drawable where the frame allows.** Today every frame renders into a
  compose target and a second full-viewport pass samples it into the drawable; D2.5 needs
  that target for frames with a backdrop filter or a blend mode (a swap-chain image cannot be
  sampled) and D7 for readback. Amendment A1:
  - *The choice is made before the first flush.* The painter knows from the kernel's tree
    whether any visible node samples its destination; `begin()` takes that flag and allocates
    the compose target only then. A frame with none renders into the drawable; a frame with
    one keeps today's path.
  - *The bound on the main thread.* The drawable is acquired on the main thread, but only
    when the carrier knows one is free: the presented handlers and the ring count the
    drawables in flight, and a frame finds fewer than the layer's maximum or is skipped and
    retried at the next display period, the Windows carrier's rule. `nextDrawable` is then
    never a wait; its one-second timeout is never reached. The render worker keeps uploads,
    submission, completion and retirement (D11).
  - *Formats.* The layer is BGRA; the scene's pipeline states exist for RGBA. A BGRA set is
    built and archived beside them, one archive entry per pipeline, and counted in Stage 0b's
    device-plus-pipeline phase.
  - *Readback.* A `screenshot`, the agent's pixels or an oracle comparison re-renders the
    retained scene into an offscreen target, on the request's turn and before the next
    `begin()` (which retires pool targets and ages atlases). The retained scene is the last
    encoded frame's batches and instance buffer with its resources pinned: the pool targets
    and atlas pages it references stay unreclaimable until the capture completes or the next
    frame is encoded. In live mode that frame is the last encoded one; a mid-animation
    capture replays its sampled state without advancing or settling time. Headless screenshots
    are unchanged and, since today's live screenshot is a walk, a render and a readback of a
    new target, the re-render is cheaper than today.
  - *The parity gate (D9).* In test builds the present pass copies the presented drawable on
    the GPU into a readback texture at present time, so the frame compared is the frame shown,
    and the comparison is against the same frame's re-render within the band; an asynchronous
    window capture is not the gate. The offscreen path keeps its comparison against tiny-skia.
  Predicted: GPU per frame 1.2 → ~0.3 ms on frames without destination sampling, once Stage 0
  has explained the 1.0 ms pass; the present pass's encode gone; the worker's per-frame wake
  kept; no CPU saving claimed beyond that.
- **M6, rows reusable across fractional offsets.** Stage 0's counter decides. If kept rows
  re-record because momentum deltas are fractional, amendment A2: the per-draw offset of a
  replayed row is rounded to whole device pixels, so every recorded glyph phase and coverage
  mask is the one a fresh walk would choose at that position; the whole row sits at most half
  a device pixel from its layout position, and only while it moves. When a row's offset stops
  changing, it is re-recorded once at the exact offset, so the settled frame is pixel-exact
  with a fresh walk. The fractional-scroll test asserts equality with a fresh walk at the
  rounded position during motion and exact equality at rest. Predicted: the walk's 5.7 ms/s
  becomes new rows' recording, kept rows' box copies and validity checks; a static screen with
  one animating element records that element and replays the rest.
- **M7, persistent instance ranges.** A replayed row still re-emits every instance through
  the clip stack. Kept rows keep ranges in a persistent instance buffer under rectangular
  outer clips (a scissor), with the copy as the fallback for every other outer clip, rounded
  or coverage. Lifetime: a range is immutable while any submitted frame or pinned snapshot
  references it; a changed row takes a new range and the old one is reclaimed after those
  references retire. Also D4's contingency. Predicted: encode 2.9 → under 1 ms/s, less the
  added draw calls, measured after M6.
- **M8, a plain pipeline.** The shader guards its rounded and coverage clips by flags, so
  the general path's cost per pixel is a branch and the general vertex load; a second
  pipeline for clip-free rectangles and glyphs with solid or image brushes is worth its
  second shader on four device layers only if G5's GPU rows, after M3, show the GPU above
  about 15% of the frame budget on either platform. Otherwise it is dropped. D6.1's portable
  buffer and shader constraints hold through M7 and M8.

### Stage 3: the platforms, where measured

  over Mica and Windows's own apps render grayscale there.
- **M10, the first screen, phase by phase, on both platforms.** On Windows the device is

- **M11, Linux and Android** on D15's own terms: the wgpu arm's obligations and D12/D13's

## 4. How a stage is measured

One rerun of the four-arm Mac series and the three-arm Windows series per stage landing,
with the committed drivers and `aggregate.mjs`; the section appended to RESULTS.md and
LLP 1149 §4.1's table updated. A fix predicted to move a scoreboard row is measured by a paired
before/after of the affected path on one platform, and the full series is run asynchronously
after the landing, not as a blocking requirement (`rules/RULES.md`, the loop shape). A Mac
series needs about fifteen untouched minutes of a held display and a Windows series the
signed-in NucBox with PresentMon. G5 (the static screen: a bar advancing every frame and a
caret blinking at 2 Hz; GPU busy time from the probe's command-buffer hook; power from
`powermetrics`, which now runs without a password on the measurement Mac) is prepared on
`lane/g5-static` with zero samples taken; it runs before Stage 2 and again after it, since M6
and M7 are measured by it. D15's remaining obligations, the vello and wgpu control arms and
the Linux and Android qualifications, stand unchanged. A row that cannot be reproduced from
the retained raw files is not a number.

## 5. Not in this program

Thinning the kernel or the runner to chase egui: on the Mac egui's 67 ms/s is its whole
application without a kernel, runner or painter; the gap is the app model's price and it is
small in absolute terms. GPUI's re-presentation policy. Returning to vello. Text shaping and
width layout, excluded by their size (under 3 ms/s in §2) after Stage 0 reads the shaping
counters, not by assignment to D3's audit, which is about rasterization. The web, which
LLP 1149.000 leaves unscheduled.

## 6. Questions

- **Q1.** Under A1 a live `screenshot` shows the last encoded frame, up to the pipeline's
  latency ahead of the glass, and costs a re-render. Acceptable? Recommendation: yes, with the
  GPU-copy parity gate. Confidence 85%.
- **Q2.** M3 acquires the drawable on the main thread, bounded by the in-flight count, rather
  than moving Metal encoding to the worker. Recommendation: main thread. Confidence 80%.
- **Q3.** M8's rule: dropped unless the GPU is above about 15% of the frame budget after M3.
  Confidence 80%.
- **Q4.** Order against S2's Windows queue: Stage 0, 0b and 1 first; M9 with the RichEdit
  field; M10 with the startup tail. Confidence 75%.
- **Q5.** Under A2 a moving row sits at most half a device pixel from its layout position and
  is re-recorded exactly when it settles. Acceptable? Recommendation: yes. Confidence 75%.
- **Q6.** A1's BGRA pipeline set doubles the archive entries and is charged to Stage 0b's
  5 ms device-plus-pipeline gate. If it breaks the gate, the alternative is an RGBA16Float
  layer, which costs memory and bandwidth. Recommendation: build the BGRA set and measure.
  Confidence 70%.

## 7. Decisions, as amendments to LLP 1149

- **A1 (D7, D2.5, D9, D11, D6.3).** A frame without destination sampling, known from the
  kernel's tree before its first flush, renders into the window's drawable, acquired on the
  main thread only when the in-flight count says one is free; a frame with it keeps the
  compose target. Scene pipelines exist in BGRA for the drawable. Readback is a re-render of
  the last encoded frame, with its resources pinned until the capture, before the next frame
  begins. D9 compares the presented drawable's GPU copy with that re-render.
- **A2 (D4).** A replayed row's per-draw offset is rounded to whole device pixels while the
  row moves and the row is re-recorded exactly when it settles; kept rows hold persistent
  instance ranges under rectangular outer clips, immutable while referenced. Both are D4's
  stated contingencies made the rule.
- **A3 (D2).** A plain pipeline for clip-free rectangles and glyphs, if G5 earns it.
- **A4 (the carriers; D7's table).** Input delivery per event; the runner, hatches and image
  reports pumped once per display period while the link runs; pending work and deadlines
  serviced on their own wakes, in order; nothing wakes at rest except a due timer, a reply or
  an image; the Mac carrier paces on `CADisplayLink`.
- **A5 (D15).** The comparison arms are the native host, GPUI and egui on the Mac, and ink's
  own wgpu arm and egui on Windows. §1's milestones are per-stage gates with the
  preconditions and savings budgets named there; D15's own obligations stand, and Stage 0b
  states the dated one as written.
