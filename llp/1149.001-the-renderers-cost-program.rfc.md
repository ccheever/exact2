# LLP 1149.001: The renderer's cost program

**Type:** RFC
**Status:** Draft r2, 2026-10-30. r1 was reviewed blind by Sol and Claude (`llp/reviews/rfc-2026-10-30-1149.001-r1.{sol,claude}.md`), both NOT READY; r2 answers both (§R).
**Systems:** host/ink, host/apple-painted, host/windows, host/linux (the painter and the presenter), bench/heavy-list
**Author:** Claude Fable 5.1 (orchestrator); Astra (gpt-6-astra) builds each stage
**Date:** 2026-10-30
**Related:** LLP 1149 (the renderer: this refines its D2.5, D4, D7, D9, D11 and D15), LLP 1148 (the options), LLP 1142 (traces), LLP 1079 (`perf`), `bench/heavy-list/gpui/RESULTS.md` (G3c, G4, G6c: the scoreboard)

## Summary

Ink is now measured against egui, GPUI and the native hosts on the same screen, the same
input and the same probe, on the Mac and on Windows. It starts fastest on Windows, matches the
field on cadence, sits within GPUI's range on fling CPU on the Mac, and costs more than egui
during a fling on both platforms. The traces say where the cost is and most of it is plumbing
around the renderer. This document orders the work: first the numbers the program will be
judged by, published and reproducible; then the dated obligation LLP 1149 already carries;
then the fixes that need no design change, each with its prediction; then the design changes,
as amendments to LLP 1149 with their contracts written down; then the platform layers. It says
how each landing is measured and what it will not do.

## 2. Where the cost is

The ink carrier's ten-second Mac fling, main thread, exclusive time per phase. This table is
the orchestrator's derivation from S1.4's image-disabled control trace
(`target/s1-4/g3-control/ink-1.json.trace.json`, 15,473 main-thread spans, each charged to
its innermost phase); it is not yet in RESULTS.md and by §4's rule it is not a number until
Stage 0 publishes it with its script. It sums to 43 ms/s, consistent with G4's 43.8.

| Phase | ms/s | Notes |
|---|---:|---|
| Event-loop service passes | 12.6 | 358 passes a second, ten per presented frame, 35 µs each: the runner, hatches and image polling pumped on every wheel event, tick and wake |
| Paint walk | 5.7 | 358 walks, 0.16 ms each |
| Carrier draw and scene encode | 5.9 | the instance buffer rebuilt every frame |
| Glyph raster; refine collections; layout | 1.2; 1.0; 0.4 | 480 glyphs; 4,775 refines; 3,362 layouts a second at a microsecond each |
| Wheel input | 1.3 | |
| Unattributed | ~15 | AppKit and winit delivery, display-link wakes, the probe; not yet marked |

On the GPU, per frame in the same trace: the scene's command buffer 0.23 ms; the pass that
samples the compose target into the drawable 1.0 ms (S1.4's normal run: 1.46). Off the main
thread: ImageIO decodes at the drawn size (the same code as egui's arm), the staging ring's
waits (blocked time, not CPU), the present worker's completion wait.

Three leads the reviews found in the code, each a hypothesis until Stage 0's counter says:

- **The viewport-target pool retains a target for 120 frames after its last use**
  (`host/ink/src/layer.rs`); a target is viewport-sized, about 10 MiB at 1600×1600; 335 MiB
  is about 33 of them; private textures have no malloc stacks, which fits S1.4's description;
  and G6b found the same pool holding 1,201 targets on Windows during the repaint churn. The
  renderer already reports `layer_targets` and `layer_bytes`.
- **A kept row is reused only at whole-device-pixel offsets** (`Ink::reusable`,
  `host/linux/src/ink/rows.rs`), because rows are recorded in window space for hinted text.
  AppKit's momentum deltas are fractional. If most frames fail that test, rows re-record
  every frame, which would look exactly like the painter walking every node, and no change
  bit would help; the kernel's change receipts already reach the painter and a valid kept
  row is not walked today.
- **On Windows, clip masks were rebuilt per paint** (G6b's largest named main-thread item);
  G6c cut the paints but no trace of the G6c build exists yet.

## 3. The program

Each stage is one or more lanes: trace, predict in writing, change one thing, measure as §4
says, two-family review, land. Stages are ordered by evidence and by date, not by size.

### Stage 0: the numbers first

One lane, no design change, before any prediction stands:

- Publish the exclusive-time attribution of §2 as a section of RESULTS.md with its script
  beside `aggregate.mjs`, run on the retained S1.4 traces and on a fresh trace of the
  current build.
- Counters in the renderer's statistics, read by `perf` and the probe: service passes per
  presented frame; rows replayed and rows recorded per frame, with the reason a row was not
  reusable; viewport targets in use, retained and their bytes, per frame; clip masks built
  per frame. Read them during a fling on both platforms.
- Mark the Mac carrier's unattributed ~15 ms/s: AppKit and winit event delivery, the
  display-link wake, the probe's own work.
- A rest-phase trace on both carriers naming every wakeup.
- A trace of the G6c build's fling on Windows.
- Publish the display-link phase measurement S1.5's analysis made (the callback's position
  in the refresh interval) with the same script.

### Stage 0b: the dated obligation

LLP 1149 D15 requires, by 2026-11-04, that a direct Metal binary-archive miss never blocks
the first pixel. It moves ahead of everything below as its own lane; this document does not
renegotiate the date.

### Stage 1: fixes under existing authority

These change no decision of LLP 1149; the RFC records their contracts and predictions.

- **M1, service once per display period.** Input delivery stays per event: a wheel or
  pointer event applies its input and advances the clock when it arrives, as now. What
  changes is the pumping of the runner, hatches and image reports: at most once per display
  period while the display link runs, once per wake otherwise. A due timer, an executor reply
  or an image report still wakes the loop and is serviced on that wake; a timer's latency is
  therefore bounded by one display period during presentation and unchanged at rest. The
  headless agent is untouched: its requests are serviced synchronously and `clock` and
  `settle` step the runner directly. Predicted, if Stage 0 confirms the 12.6 ms/s as
  near-empty passes: Mac main thread 44 → ~34 ms/s.
- **M2, nothing wakes at rest** except a due timer, a reply or an image. Predicted after the
  rest trace names the wakeups: Mac ≤ 0.4 ms/s, Windows no tick in ten seconds.
- **M4a, the pool's retention.** If Stage 0's counters confirm the lead, viewport targets are
  retained for the frames in flight plus a short grace, not 120 frames. Predicted: the Mac
  peak fling footprint 592 → under 400 MiB and the Windows working set's churn gone; CPU
  unchanged. **M4b, one copy per upload** into a per-frame staging arena fenced on that
  frame's completion. Predicted: the 6.5 ms per ten seconds of main-thread copying, and the
  worker's serialization behind a thumbnail burst; a small CPU number, honestly.
- **M5, the display link.** During a phased gesture the Mac carrier already keeps the link
  running through three quiet ticks (S1.6); the per-frame restart S1.5 found applies to
  unphased events only. What remains is the callback's position in the refresh interval,
  measured by the orchestrator at about 5 ms after the presented-time grid and to be
  published in Stage 0. `CADisplayLink` from `NSView.displayLink` (macOS 14, the carrier's
  minimum) gives a target timestamp and a callback at the interval's start. Instrument: the
  probe already records each wheel event's timestamp and each drawable's presented time;
  input-to-photon is their difference, reported as a new row. Prediction, as a hypothesis:
  one refresh less. Amends D7's table, which names `CVDisplayLink` for the Mac.

After stage 1 the arithmetic is main 44 − 10 (M1) ≈ 34 and process 86 − 10 − small ≈ 70 on
the Mac; the Windows prediction waits on Stage 0's trace of the G6c build.

### Stage 2: design changes, as amendments to LLP 1149

- **M3, render into the drawable where the frame allows.** Today every frame renders into a
  compose target and a second full-viewport pass samples it into the drawable; D2.5 needs
  that target for frames with a backdrop filter or a blend mode (a swap-chain image cannot be
  sampled) and D7 for readback. Amendment A1: a frame with no destination-sampling instance
  renders into the drawable or swap chain directly; a frame with one keeps today's path; the
  choice is per frame at encode. The drawable is acquired on the main thread with a bounded
  wait (what GPUI and egui do), so the scene can be encoded against it there; the render
  worker keeps uploads, completion and retirement (D11). An acquisition that times out skips
  the frame and the next display period retries, the behaviour the Windows carrier already
  has. Readback under A1: a `screenshot`, the agent's pixels or an oracle comparison
  re-renders the retained scene, defined as the last encoded frame's batches and instance
  buffer, into an offscreen target; in live mode that is the last encoded frame, up to one
  ahead of the glass; headless screenshots are unchanged. D9's parity gate gains a window
  capture of the presented frame compared to that re-render within the band, so the drawable
  path is pixel-tested. Predicted: GPU per frame 1.2 → ~0.3 ms on frames without destination
  sampling, the present pass's encode gone, the worker's per-frame wake kept.
- **M6, rows reusable across fractional offsets.** Stage 0's counter decides. If kept rows
  re-record because momentum deltas are fractional, amendment A2: a row records in row space
  and is placed by a per-draw offset at replay, with hinted glyphs snapped to the device grid
  at their replayed position (the snap moves a glyph by at most half a device pixel, and only
  while the row moves). This is D4's own contingency ("the offset becomes a per-draw
  constant") made the rule. Predicted: the walk's 5.7 ms/s becomes new rows' recording only;
  a static screen with one animating element records that element and replays the rest.
- **M7, persistent instance ranges.** A replayed row still re-emits every instance through
  the clip stack. Kept rows keep ranges in a persistent instance buffer under rectangular
  outer clips (a scissor), with the copy as the fallback where an outer clip is rounded.
  Also D4's contingency. Predicted: encode 2.9 → under 1 ms/s.
- **M8, a plain pipeline.** The shader guards its rounded and coverage clips by flags, so
  the general path's cost per pixel is a branch and the general vertex load; a second
  pipeline for clip-free rectangles and glyphs with solid or image brushes is worth its
  second shader on four device layers only if G5's GPU rows, after M3, show the GPU above
  about 15% of the frame budget on either platform. Otherwise it is dropped.

### Stage 3: the platforms, where measured

- **M9, text on Windows** under D3.3's advance audit: DirectWrite rasterization where the
  audit says so; no ClearType claim, since the composition swap chain is premultiplied alpha
  over Mica and Windows's own apps render grayscale there.
- **M10, the first screen, phase by phase, on both platforms.** On Windows the device is
  48 ms of a 176 to 182 ms first screen; on the Mac the device is 32 ms of 352 and the rest
  is unattributed. M10's first chunk is the phase trace; the 100 ms program follows it.
- **M11, Linux and Android** on D15's own terms: the wgpu arm's obligations and D12/D13's
  opt-in, not a replacement decided here.

## 4. How a landing is measured

One rerun of the four-arm Mac series and the three-arm Windows series per stage landing,
plus a rerun for any fix that moves a scoreboard row, with the committed drivers and
`aggregate.mjs`; the section appended to RESULTS.md and LLP 1149 §4.1's table updated. A
Mac series needs about fifteen untouched minutes of a held display and a Windows series the
signed-in NucBox with PresentMon, so per-landing reruns within a stage are paired
before/after measurements of the affected path on one platform. G5 (the static screen: a bar
advancing every frame and a caret blinking at 2 Hz; GPU busy time from the probe's
command-buffer hook; power from `powermetrics`) runs before Stage 2 and again after it, since
M6 and M7 are measured by it. D15's remaining obligations, the vello and wgpu control arms
and the Linux and Android qualifications, stand unchanged. A row that cannot be reproduced
from the retained raw files is not a number.

## 5. Not in this program

Thinning the kernel or the runner to chase egui: on the Mac egui's 67 ms/s is its whole
application without a kernel, runner or painter; the gap is the app model's price and it is
small in absolute terms. GPUI's re-presentation policy. Returning to vello. Text shaping and
layout, which belong to D3's audit. The web, which LLP 1149.000 leaves unscheduled.

## 6. Questions

- **Q1.** Under A1 a live `screenshot` shows the last encoded frame, up to one frame ahead of
  the glass, and costs a re-render rather than a copy. Acceptable? Recommendation: yes, with
  the window-capture parity gate. Confidence 85%.
- **Q2.** M3 acquires the drawable on the main thread with a bounded wait rather than moving
  Metal encoding to the worker. Recommendation: main thread; it is the simpler amendment and
  the precedent of both comparison arms. Confidence 80%.
- **Q3.** M8's rule: dropped unless the GPU is above about 15% of the frame budget after M3.
  Confidence 80%.
- **Q4.** Order against S2's Windows queue: Stage 0, 0b and 1 first; M9 with the RichEdit
  field; M10 with the startup tail. Confidence 75%.
- **Q5.** Glyph snapping under A2 moves a glyph by at most half a device pixel while a row
  moves. Acceptable, or must rows stay whole-pixel and the fix be elsewhere? Recommendation:
  acceptable; UIKit's scrolled text does the same. Confidence 70%.

## 7. Decisions, as amendments to LLP 1149

- **A1 (D7, D2.5, D9, D11).** A frame without destination sampling renders into the window's
  drawable, acquired on the main thread with a bounded wait; a frame with it keeps the
  compose target. Readback is a re-render of the last encoded frame into an offscreen target.
  D9 compares the presented frame's capture with that re-render.
- **A2 (D4).** Rows record in row space and replay at a per-draw offset, hinted glyphs
  snapped at replay; kept rows hold persistent instance ranges under rectangular outer clips.
  Both are D4's stated contingencies made the rule.
- **A3 (D2).** A plain pipeline for clip-free rectangles and glyphs, if G5 earns it.
- **A4 (the carriers; D7's table).** Input delivery per event; the runner, hatches and image
  reports pumped at most once per display period while the link runs and once per wake
  otherwise; nothing wakes at rest except a due timer, a reply or an image; the Mac carrier
  paces on `CADisplayLink`.
- **A5 (D15).** The comparison arms are the native host, GPUI and egui on the Mac, and ink's
  own wgpu arm and egui on Windows. §1's milestones are per-stage gates with the
  preconditions named there; D15's own obligations stand.
