# LLP 1149.001: The renderer's cost program

**Type:** RFC
**Status:** Draft r5, 2026-10-30. r1 to r4 were reviewed blind by Sol and Claude (`llp/reviews/rfc-2026-10-30-1149.001-r{1,2,3,4}.{sol,claude}.md`); round 4 found round 3 answered and left the lifecycle of A1's parked drawable, A2's units, sign and eligibility, the kernel count, Q6's baseline and the Windows startup endpoint, which r5 writes (§R).
**Systems:** host/ink, host/apple-painted, host/windows, host/linux (the painter and the presenter), kernel (A1's destination-sampling count), bench/heavy-list
**Author:** Claude Fable 5.1 (orchestrator); Astra (gpt-6-astra) builds each stage
**Date:** 2026-10-30
**Related:** LLP 1149 (the renderer: this refines its D1.1, D2.5, D3, D4, D6.3, D7, D9, D11 and D15), LLP 1148 (the options), LLP 1142 (traces), LLP 1079 (`perf`), `bench/heavy-list/gpui/RESULTS.md` (G3c, G4, G5 prepared, G6c: the scoreboard)

## Summary

Ink is now measured against egui, GPUI and the native hosts on the same screen, the same
input and the same probe, on the Mac and on Windows. It starts fastest on Windows, matches the
field on cadence, sits within GPUI's range on fling CPU on the Mac, and costs more than egui
during a fling on both platforms. The traces say where the cost is and most of it is plumbing
around the renderer. This document orders the work: first the numbers the program will be
judged by, published and reproducible, with the counters that turn its leads into facts;
beside them the dated obligation LLP 1149 already carries, stated as LLP 1149 wrote it, with
the one part this document asks to renegotiate put as a question; then the fixes that need
no design change, each with its contract and prediction; then the design changes, as
amendments to LLP 1149 with their contracts written; then the platform layers. It says how
each stage is measured and what it will not do.

## 2. Where the cost is

The ink carrier's ten-second Mac fling, main thread, from S1.4's image-disabled control trace
(`target/s1-4/g3-control/ink-1.json.trace.json`). These are **elapsed** main-thread spans on
`CACurrentMediaTime`, each charged to its innermost phase; G4's 43.8 ms/s is **CPU time**. The
two agree in magnitude, which is a consistency check, not the same instrument, and the
unattributed row is a difference of the two, not an attribution. The table is the
orchestrator's derivation and is not yet in RESULTS.md; by §4's rule it is not a number until
Stage 0 publishes it with its script. Counts are totals over the ten seconds.

| Phase | ms/s | Count in ten seconds | Notes |
|---|---:|---:|---|
| Event-loop service passes | 12.6 | 3,579 | 35 µs each; ten per presented frame: the runner, hatches and image polling pumped on every wheel event, tick and wake |
| Paint walk | 5.7 | 358 | 0.16 ms each |
| Carrier draw and scene encode | 5.9 | 348 | the instance buffer rebuilt every frame |
| Glyph raster; refine collections; layout | 1.2; 1.0; 0.4 | 481; 4,775; 3,362 | layouts at a microsecond each |
| Wheel input | 1.3 | 422 | |
| Unattributed | ~15 | | AppKit and winit delivery, display-link wakes, the probe; not yet marked |

Off the main thread G4 has 42 ms/s more process CPU that no trace attributes: ImageIO decodes
at the drawn size (14 ms/s in S1.4's normal run, the same code as egui's arm), the present
worker, the Metal driver's threads; the staging ring's waits and the completion wait are
blocked time, not CPU. On the GPU, per frame in the control trace: the scene's command buffer
0.23 ms; the pass that samples the compose target into the drawable 1.0 ms (S1.4's normal
run: 1.46). A one-quad pass costing four times the scene is not proportional to its work and
no format conversion explains it (both targets are unorm); Stage 0 explains it (the GPU's
clock state, or a wait inside the measured interval) before M3's saving stands.

Three leads the reviews found in the code, each a hypothesis until Stage 0's counter says:

- **The viewport-target pool** (`host/ink/src/layer.rs`) reuses a target as soon as its last
  GPU use completes and evicts a target unused for 120 calls of `begin()`, so idle time does
  not age it; a lagging worker therefore makes a frame allocate fresh targets that nothing
  frees for 120 frames. The targets are shared-storage textures, about 10 MiB at 1600×1600;
  335 MiB is 34 of them; G6b found 1,201 targets on Windows during the repaint churn, which
  G6c removed. Against it: S1.4's tracked textures total 61 MiB in the normal run, the
  footprint falls to 246 MiB by the end of the fling phase, and egui shows a 320 MiB transient
  with no such pool. So a second cause stays open; Stage 0 reads `layer_targets` and
  `layer_bytes` as timestamped gauges beside a `vmmap` of the same run.
- **A kept row is reused only at whole-device-pixel offsets** (`Ink::reusable`,
  `host/linux/src/ink/rows.rs`): rows are recorded in row space relative to their unrounded
  recording origin and replayed by a per-instance translate, but each glyph was rasterized at a
  quarter-pixel horizontal phase and a truncated y chosen at record time, so a replay whose
  shift from the recording is fractional would place the wrong raster. AppKit's momentum
  deltas are fractional. If most frames fail the test, rows re-record every frame, which would
  look exactly like the painter walking every node; the kernel's change receipts already reach
  the painter, which derives a row's stale and suspect state from them, and a valid kept row is
  not walked today.
- **On Windows, clip masks were rebuilt per paint** (G6b's largest named main-thread item);
  G6c cut the paints but no trace of the G6c build exists yet.

## 3. The program

Each stage is one or more lanes: trace, predict in writing, change one thing, measure as §4
says, two-family review, land. Stages are ordered by evidence and by date, not by size. Stage
0 and Stage 0b run beside each other.

### Stage 0: the numbers first

One lane, no design change, before any prediction stands:

- Publish §2 as a section of RESULTS.md with its script beside `aggregate.mjs`, run on the
  retained S1.4 traces and on a fresh trace of the current build, printing elapsed and CPU
  separately and every count with its denominator.
- A per-thread CPU profile of the posted fling on both platforms (Instruments' Time Profiler
  or `sample` on the Mac; the sampled attribution G6b made on Windows, on the G6c build), so
  the 42 ms/s off the main thread has names.
- Cumulative counters in the live carrier, read through the agent's `state` and the probe
  (on Windows `perf` drives the headless presenter, not the window), as timestamped gauges
  and high-water marks: paint attempts, submitted frames and displayed frames; service passes
  per display period; rows replayed, rows recorded whole, image-slot patches, and rows refused
  as not reusable by reason (a fractional shift, a scaled transform, a sign crossing),
  separately from stale, suspect and picture-arrival re-records; viewport
  targets allocated, reuses blocked by incomplete GPU work, targets retained and their bytes,
  targets retired; clip masks built; the text engine's existing shaping-cache counters; the
  observer's own overhead, measured. Read them during a fling on both platforms, with a
  `vmmap` of the Mac run at its peak.
- Mark the Mac carrier's unattributed ~15 ms/s: AppKit and winit event delivery, the
  display-link wake, the probe's own work.
- A rest-phase trace on both carriers naming every wakeup.
- Publish the display-link phase measurement S1.5's analysis made (the callback's position in
  the refresh interval) with the same script, and explain the present pass's 1.0 ms.
- The baseline Q6 needs, as far as the carrier can give it: the heavy list's cold start in the
  Mac carrier on the CPU painter, once Stage 0b's second part lets the CPU painter present
  through the layer; until then the native host's 354 ms (G4) is the Mac baseline the record
  holds. vello has no presentation path in the carrier and none is proposed.

### Stage 0b: the dated obligation, as LLP 1149 wrote it

D15 keeps direct Metal on a dated obligation, 2026-11-04 or the carrier's enablement, with
three parts: the warm device-plus-pipeline phase within 5 ms of the wgpu arm's (today about
16 ms over); a cache miss that never blocks first pixel, D6.3's rule, with the CPU painter's
first frames presented through the same swap chain while pipelines build and the archive is
populated off the path; and the complete first screen at p50 within the 100 ms budget with
the phases summed, measured with an empty and a retained application cache. Stage 0b lands
the first two by the date, as written. The third it cannot land: no arm on either platform is
within the budget today (313 to 354 ms on the Mac), and the 100 ms is the application's
boot, which M10 attributes. This document asks to renegotiate that part, in §6 Q6, and does
not call it met.

### Stage 1: fixes within the design

These amend one table row of LLP 1149 (M5, D7's pacing row) and one policy sentence (M4a,
D2.5's pool); the RFC records their contracts and predictions.

- **M1, coalesce the polling; service pending work independently.** Input delivery stays
  per event: a wheel or pointer event applies its input and advances the clock when it
  arrives, as now. What changes is the polling: the runner's command queue, hatches and image
  reports are pumped once per display period while the display link runs, and that pass is
  `draw`'s own; the pass `about_to_wait` runs on every loop turn is skipped while the link
  runs. Pending work is serviced when it arrives, in order: a due timer on its wake, a hatch
  or executor reply on its wake, an image report on its wake; a wake whose cause the period's
  pass already served does nothing. A timer's latency is therefore unchanged; what is removed
  is the redundant pumping of empty queues. The headless agent is untouched (requests are
  serviced synchronously; `clock` and `settle` step the runner directly), and so is the
  live-mode agent request, which keeps its synchronous service. Predicted, if Stage 0 confirms
  the 12.6 ms/s as near-empty passes: about 1.2 ms/s of passes remain (348 draws' own
  passes, which the draw row may already contain, so the saving may be the whole 12.6), the
  Mac main thread 44 → ~33 ms/s; the necessary timer, reply and image turns that remain are
  what Stage 0 counts.
- **M2, nothing wakes at rest** except a due timer, a reply or an image. Predicted after the
  rest trace names the wakeups: Mac ≤ 0.4 ms/s; Windows no tick in ten seconds.
- **M4a, the pool's policy**, if and only if Stage 0's counters show idle targets, not
  targets held by incomplete GPU work: retain for the frames in flight plus a short grace.
  This amends D2.5's sentence that the pool grows to the high-water mark and is trimmed on
  warning and background (§7 A6). Predicted: the Mac peak footprint down by the idle targets'
  bytes; CPU unknown, since trimming adds allocation. **M4b, one copy per upload** into a
  per-frame staging arena fenced on that frame's completion. Predicted: at most the 6.5 ms per
  ten seconds of upload preparation now on the main thread; a small number, honestly.
- **M5, the display link.** During a phased gesture the Mac carrier keeps the link running
  through three quiet ticks (S1.6); the per-frame restart S1.5 found applies to unphased
  events only. What remains is the callback's position in the refresh interval, measured by
  the orchestrator at about 5 ms after the presented-time grid and published in Stage 0.
  `CADisplayLink` from `NSView.displayLink` (macOS 14, the carrier's minimum) gives a target
  timestamp and a callback at the interval's start. Instrument: the probe records each wheel
  event's timestamp and each drawable's presented time; input-to-photon is the difference
  between a frame's presented time and the timestamp of the input that frame incorporated,
  joined by the frame's sequence number, not the latest input before its commit (S1.5 shows
  why). Prediction, as a hypothesis: one refresh less. Amends D7's table, which names
  `CVDisplayLink` for the Mac.

After stage 1 the arithmetic is main 44 − 11 (M1) ≈ 33 and process 86 − 11 − small ≈ 75 on
the Mac. The direction of 60 needs a further budget of about 15 ms/s: M6 and M7 address 8.6
ms/s on the main thread, which is addressable cost, not a savings budget, since the walk keeps
new rows and validity and the encode keeps its draw calls; the rest is unnamed until Stage 0
marks the unattributed 15 and profiles the other threads. The Windows prediction waits on Stage 0's trace of the G6c build.

### Stage 2: design changes, as amendments to LLP 1149

- **M3, render into the drawable where the frame allows.** Today every frame renders into a
  compose target and a second full-viewport pass samples it into the drawable; D2.5 needs
  that target for frames with a backdrop filter or a blend mode (a swap-chain image cannot be
  sampled) and D7 for readback. Amendment A1:
  - *The choice is made before the first flush.* This is a kernel change: the kernel keeps a
    count, maintained on commit, of present nodes that sample their destination (backdrop
    filters, blend modes, and the modes of SVG islands, which the painter must learn from the
    SVG scene), so `begin()` learns in constant time whether this frame may need the compose
    target and allocates it only then. Present, not visible: the count is conservative. A
    frame with none renders into the drawable; a frame with one keeps today's path.
  - *Acquisition stays on the worker, as D7 has it; the main thread never waits.* The worker
    acquires one drawable when the layer attaches and parks it, and after each present it
    acquires and parks the next, as the last item of its turn, after queued uploads, captures
    and resource waits, so nothing queues behind an acquisition; the acquisition uses the
    layer's timeout, a bounded worker wait. A park carries the layer's size and scale
    generation; a resize or scale change discards it, and the live-resize frame acquires
    synchronously after the resize (encode, commit, `waitUntilScheduled`, present inside the
    transaction), as S1.6 made it. The carrier checks for a park before the walk, where the
    Windows carrier calls `prepare_window_frame`; with none parked, no frame is painted, the
    presenter keeps its damage, and the carrier retries at the next display period; an
    acquisition that returned nothing is requested again at that period, independent of any
    present. When the display link stops, the park is released, so rest holds no drawable and
    the end-of-rest footprint row is unchanged; the first frame of the next gesture waits one
    period for its acquisition, stated as a cost. Encoding on the host thread, commit and
    present on the worker, are D11's division unchanged.
  - *Formats.* The BGRA pipeline set already exists: `attach_layer` builds and archives it in
    its own archive today and keeps only its replace pipeline; A1 keeps its blend pipeline
    too. Nothing new is built or archived, and Stage 0b's phase already includes it.
  - *Readback.* A `screenshot`, the agent's pixels or an oracle comparison takes the frame's
    pixels in one of two ways. A frame that rendered into the compose target is read from it,
    as today's `finish()` does: no re-render, every pass of the frame included. A frame that
    rendered into the drawable is a single pass and is re-rendered from the retained scene:
    the last encoded frame's clear, size, batches and instance buffer, with the pool targets
    and atlas pages it references pinned until the next frame's encode replaces them, since
    a live request arrives on an arbitrary turn: one frame's targets and entries are held one
    frame longer than today, a cost stated; the re-render happens on the request's turn and
    before the next `begin()`. In live mode that frame is the last
    encoded one; a mid-animation capture replays its sampled state without advancing or
    settling time. Headless screenshots are unchanged and, since today's live screenshot is a
    walk, a render and a readback of a new target, the re-render is cheaper than today.
  - *The parity gate (D9).* In test builds the layer is created with `framebufferOnly` false
    and, after the scene pass on the worker's commit, a blit copies the drawable into a
    readback texture tagged with the frame's sequence number, compared after channel
    normalization (the drawable is BGRA, the readback RGBA); the snapshot of that frame survives until its
    comparison completes, even when later frames have been encoded. The gate compares that
    copy with the same frame's readback within the band, so the frame compared is the frame
    shown, and it qualifies the test configuration of the layer; the shipped configuration
    keeps `framebufferOnly` true and is qualified by the window captures of the series. The
    offscreen path keeps its comparison against tiny-skia. The copy's cost is kept out of
    ordinary performance samples.
  Predicted: GPU per frame 1.2 → ~0.3 ms on frames without destination sampling, once Stage 0
  has explained the 1.0 ms pass; the present pass's encode gone; no CPU saving claimed.
- **M6, rows reusable across fractional scroll offsets.** Stage 0's counter decides. If kept
  rows re-record because momentum deltas are fractional, amendment A2, a moving-content
  policy under D3 and D9, not a D4 contingency: the snap is per scroller, not per row, and it
  is defined in the coordinates glyphs are rasterized in. The backend receives the scroller's
  offset in points at `group_begin`; with `p` that offset times the device scale, the rows of
  that scroller are recorded and replayed where a walk at the offset `round(p)` device pixels
  (`round(p) / scale` points) would place them. The shift between a row's recording and its
  replay is then `round(p_new) − round(p_rec)` device pixels, whole for every row, so every
  recorded glyph phase and coverage mask is the one a fresh walk at that position would
  choose; rows keep their mutual positions, so there is no seam between rows whose layout
  heights are fractional (the kernel does not round frames); the whole list sits at most half
  a device pixel from its layout position while `p` is fractional, which is what an AppKit
  clip view's pixel-aligned bounds origin does. The fast path is taken only where that
  equivalence holds: rows whose transform is a pure translation (no scale, no skew; the row
  path admits axis-aligned scale today and such rows record fresh) and whose glyphs do not
  cross zero in device coordinates under the shift (truncation is not translation-invariant
  across zero; a row with such a glyph records fresh, so the mismatch today's whole-pixel
  reuse accepts at the viewport's edge is not extended). When the scroller's offset stops
  changing, the carrier requests one final redraw and the rows re-record at the exact offset,
  so the settled frame is pixel-exact with a fresh walk; when motion resumes they re-record
  once at the snapped position. The fractional-scroll test asserts equality with a fresh walk
  at the snapped offset during motion and exact equality at rest, with the fallback rows
  recorded fresh in both. Predicted: the walk's
  5.7 ms/s becomes new rows' recording, kept rows' box copies and validity checks; a static
  screen with one animating element records that element and replays the rest.
- **M7, persistent instance ranges.** A replayed row still re-emits every instance through
  the clip stack. Kept rows keep ranges in a persistent instance buffer under rectangular
  outer clips (a scissor), with the copy as the fallback for every other outer clip, rounded
  or coverage. Lifetime: a range is immutable while any submitted frame or pinned snapshot
  references it; a changed row takes a new range and the old one is reclaimed after those
  references retire. D4's contingency. Predicted: encode 2.9 → under 1 ms/s, less the added
  draw calls, measured after M6.
- **M8, a plain pipeline.** The shader guards its rounded and coverage clips by flags, so
  the general path's cost per pixel is a branch and the general vertex load; a second
  pipeline for clip-free rectangles and glyphs with solid or image brushes is worth its
  second shader on four device layers only if G5's GPU rows, after M3, show the GPU above
  about 15% of the frame budget on either platform. Otherwise it is dropped. D6.1's portable
  buffer and shader constraints hold through M7 and M8.

## 4. How a stage is measured

One rerun of the four-arm Mac series and the three-arm Windows series per stage landing,
with the committed drivers and `aggregate.mjs`; the section appended to RESULTS.md and
LLP 1149 §4.1's table updated. A fix predicted to move a scoreboard row is measured by a paired
before/after of the affected path on one platform, and the full series is run asynchronously
after the landing, not as a blocking requirement (`rules/RULES.md`, the loop shape). A Mac
series needs about fifteen untouched minutes of a held display and a Windows series the
signed-in NucBox with PresentMon. G5 (the static screen: a bar advancing every frame and a
caret blinking at 2 Hz; GPU busy time from the probe's command-buffer hook; power from
`powermetrics`, which now runs without a password on the measurement Mac) is prepared on
`lane/g5-static` with zero samples taken; it runs before Stage 2 and again after it, since M6
and M7 are measured by it. D15's remaining obligations, the vello and wgpu control arms and
the Linux and Android qualifications, stand unchanged. A row that cannot be reproduced from
the retained raw files is not a number.

## 5. Not in this program

Thinning the kernel or the runner to chase egui: on the Mac egui's 67 ms/s is its whole
application without a kernel, runner or painter; the gap is the app model's price and it is
small in absolute terms. GPUI's re-presentation policy. Returning to vello. Text shaping and
width layout, excluded by their size if Stage 0's shaping and cache-miss deltas confirm it
(§2's combined row mixes them with glyph rasterization, refinement and layout and does not
isolate them), not by assignment to D3's audit, which is about rasterization. The
web, which LLP 1149.000 leaves unscheduled.

## 6. Questions

- **Q1.** Under A1 a live `screenshot` shows the last encoded frame, up to the pipeline's
  latency ahead of the glass, and a direct frame costs a re-render. Acceptable?
  Recommendation: yes, with the GPU-copy parity gate. Confidence 85%.
- **Q2.** M3 keeps acquisition on the worker, parked for the main thread, rather than moving
  Metal encoding to the worker. Recommendation: the parked drawable. Confidence 85%.
- **Q3.** M8's rule: dropped unless the GPU is above about 15% of the frame budget after M3.
  Confidence 80%.
- **Q4.** Order against S2's Windows queue: Stage 0, 0b and 1 first; M9 with the RichEdit
  field; M10 with the startup tail. Confidence 75%.
- **Q5.** Under A2 a moving scroller's content sits at most half a device pixel from its
  layout position and is re-recorded exactly when it settles; scaled rows and rows with a
  glyph crossing zero record fresh. Acceptable? Recommendation: yes; it is what the
  platform's own scroll views do. Confidence 80%.
- **Q6, the renegotiation.** D15's third part, the complete first screen at p50 within
  100 ms by 2026-11-04, is not met by any arm and is the application's boot, not the device
  layer's. Proposed replacement for direct Metal: the first screen in the Mac carrier within
  10% of the platform's existing painter on the same screen, where the baseline the record
  holds today is the native host's 354 ms (G4; ink is at 352) and the CPU painter's becomes
  measurable once Stage 0b's second part lets it present through the layer; vello has no
  carrier path and is not proposed as a baseline. The 100 ms program is carried by M10 to a
  decision point of 2026-11-30, when its phase trace and first chunk have landed.
  Recommendation: that replacement. Confidence 70%. Until ruled, Stage 0b's third part is
  unmet and this document says so.

## 7. Decisions, as amendments to LLP 1149

- **A1 (D7, D2.5, D9, D11, D6.3; the kernel).** A frame without destination sampling, known
  from the kernel's count of present destination-sampling nodes before its first flush,
  renders into the window's drawable, which the worker acquired and parked at attach and after
  each present, last in its turn, generation-checked, released at rest and discarded on
  resize; the carrier checks the park before the walk and a frame without one keeps its
  damage and retries next period; a frame with destination sampling keeps the compose target. The existing BGRA pipeline set serves the drawable. Readback reads the
  compose target when the frame had one and otherwise re-renders the last encoded frame from
  its pinned retained scene before the next frame begins. In test builds D9 compares a GPU
  copy of the presented drawable, tagged by frame, with that frame's readback.
- **A2 (D3, D9, D4).** While a scroller's device-pixel offset is fractional, its
  pure-translation rows are recorded and replayed where a walk at the rounded offset would
