## Summary

Three packages give an app the device's own vision and translation, by
the web's names:

- `@exact/barcode-detection` reads barcodes and QR codes in a still image
  and, live, in a camera track the app is showing: the Shape Detection
  API's `BarcodeDetector` over Vision on Apple, ML Kit on Android and the
  browser's detector on the web.
- `@exact/text-detection` reads the text in a still image: the Shape
  Detection API's `TextDetector`, which no browser ships, over Vision and
  ML Kit. The web cell is `absent`, said plainly (D3).
- `@exact/translation` translates text and identifies its language on
  the device: the Translator and Language Detector APIs over Apple's
  Translation and Natural Language and ML Kit's translation and language
  identification, and the browser's own on the web.

Shelf scans a book's ISBN and fills the add sheet from Open Library:

```
use getSupportedFormats, detectedBarcodes, BarcodeFormats, BarcodeScan
  from "@exact/barcode-detection"
use getUserMedia, stopTrack, MediaStream, MediaStreamTrack from "@exact/media-capture"

state track = ""
resource formats = getSupportedFormats() as shape BarcodeFormats else empty()
resource scan = detectedBarcodes(track=track, formats=["ean_13"])
  as shape BarcodeScan else empty()
derive isbn = match scan.seen.at(0) { case some(b) => b.rawValue, case none => "" }
resource found = lookupIsbn(isbn) as shape FoundBook else empty()
mutation opened as shape MediaStream then show

action startScan
  send opened = getUserMedia(video=true, videoConstraints=backCamera)
  nav = push(nav, "/add/scan")
action show
  match opened
    case some(s)
      track = match s.tracks.at(0) { case some(t) => t.id, case none => "" }
    case none
      track = ""
```

Excord identifies a message's language in data code and translates it
when the person asks:

```ts
import { languageDetectorAvailability, createLanguageDetector, detectLanguage }
  from "@exact/translation";

let detector: string | null = null;
export async function messageLanguage(text: string) {
  const a = await languageDetectorAvailability({});
  if (a.availability !== "available") return null;
  detector ??= (await createLanguageDetector({})).id;
  const [top] = (await detectLanguage({ detector, input: text })).results;
  return top.detectedLanguage === "und" || top.confidence < 0.7 ? null : top;
}
```

Images reach the vision packages as LLP 1133.019 settled: by path, a
file in `app:/` the app may read, never bytes in Contract; boxes are in
the upright image's pixels. A live scan is a polled source reading a
track the camera package shows: the detector rides on the capture and
starts nothing (D5). A translator and a language detector are handles,
and their availability is LLP 1133.016 D5's four states and a reason,
inherited unchanged: a download is a person's act, refused to tools and
wakes, on the web inside the press's activation, and on Apple behind the
system's own download sheet (D8). Since no platform offers a create
that refuses to download, every create is the app's foreground act,
admitted by the runner as any `"origin": "app"` name is (D16).

Tier 2 reaches Vision's recognition level and language correction,
ML Kit's download conditions, and each platform's identifiers. Tier 3
hands the app's Swift each Vision request before it runs and its Kotlin
each ML Kit options builder.

What the parent RFCs did not settle, and this one decides (§0): how a
detector reads a camera without being a camera consumer; what a scan
that sees a code for one frame leaves for the app to read; how Apple's
Translation, which hands its session only to a SwiftUI view, works under
a host that draws no SwiftUI; and what the agent sees in place of the
platform's detectors and models.

The consumers are Shelf (`apps/shelf`): Scan Barcode in the add sheet
and Add Quote from Photo in a book's notes; and Excord (`apps/excord`):
Translate in a message's menu (§10).

## 0. What is new here

1. **A detector reads a capture without keeping it.** The camera's
   leases follow its consumers, the viewfinders that are shown (LLP
   1133.008 D3). A scanner is not one: it analyses frames only while a
   consumer keeps the capture running, takes no lease and starts
   nothing, so a hidden viewfinder stops both the camera and the scan,
   and no origin question arises that the viewfinder did not already
   answer. The track table gains a non-consuming output for it (D5, D17
   item 1).
2. **What a scan saw is kept until it is read.** A code may be in frame
   for a tenth of a second. The scan's answer carries the latest frame's
   detections and, beside them, every distinct code seen since the scan
   began, so a coalesced poll loses no code (LLP 1133 D6 rule 7; D5).
3. **Detection on a still runs for real under the agent.** It needs no
   device and no permission: it is computation on a file the app already
   reads, as `transformImage` is (LLP 1133.019 D13). So drives run the
   platform's own detector on fixture images, and the implementation's
   main risks (orientation, coordinates, format names) are what they
   test (§9). The camera's agent picture is a frame the live scan
   analyses the same way (D17 item 2).
4. **Apple's translator lives in a view.** A `TranslationSession` comes
   from SwiftUI's `translationTask`, is valid only while that view is
   attached, and "the system throws a fatalError" if it is used after
   ([TranslationSession](https://developer.apple.com/documentation/translation/translationsession)).
   Such a session can always ask the person to download, so before iOS
   and macOS 26 a translate could show Apple's sheet. The Apple
   implementation hosts one hidden SwiftUI view per translator in the
   session's own view, treats the platform's session as a cache it
   rebuilds, never calls one whose view has gone, and
   checks that a pair is installed before every translate (D9). That
   needs the session's presentation, which the package context does not
   give today (D17 item 3).
5. **Availability and downloads are LLP 1133.016's.** The four states,
   the shared `reason`, the live fact read again at the foreground, and
   a download only by a person's act are inherited. What is added is
   Apple's own consent: `prepareTranslation()` "asks for permission to
   download", and the person's decline is an answer the app reads (D8).

## 1. What exists

- **No vision or translation module.** `rules/DEFERRED.md`'s camera
  record keeps "barcode and document scanning" out until a consumer asks
  (LLP 1133.008 §12), and its camera §5 sends barcodes to tier 3 (an added
  `AVCaptureMetadataOutput` or `ImageAnalysis`) until this module.
- **The camera** (LLP 1133.008, built): `@exact/media-capture` keeps one
  capture per camera for the process and a per-session track table;
  `@exact/camera` draws `exact-camera srcObject=` and takes photos. A
  video track's entry offers `ExactVideoSource.configure` on the capture
  session's queue (Apple), `add(useCase)` on CameraX's use-case set
  (Android), and the `MediaStreamTrack` (web). Every subscriber counts as
  a consumer today (`VideoCapture.swift`'s `subscribe`).
- **Images by path** (LLP 1133.019, built on Apple and the web): a picked
  file lands in `app:/tmp/picked/`, a photo in `app:/tmp/camera/`, a
  library copy in `app:/tmp/photos/`; a module option of type `path`,
  `"access": "read"`, is admitted against the app's `fs.read` grant (LLP
  1133.006 D8 item 3), as speech recognition's `path` is.
- **The language model** (LLP 1133.016, built): the `download`
  declaration, which the runner validates and only the implementation's
  agent path applies (the runner's admission reads a name's top-level
  `origin` and `foreground`, `runner/src/runner/modules/admit.rs`),
  `"gesture": true` (a send inside the
  press's activation on the web), `"poll": {"while": …}`, `cancel`, and
  weak-linked frameworks (`"frameworks"` in an Apple implementation's

- **Linux and Windows** run the shared native presenter, and no package

- **The consumers.** Shelf's add sheet takes a title, an author and a

  (`net.fetch https://openlibrary.org`). Excord's `message-menu` popover

## 2. Tier 1

### D1 — The Shape Detection API's names

| Web | Tier 1 | Kind |
|---|---|---|
| `BarcodeDetector.getSupportedFormats()` | `getSupportedFormats()` | source, live (D6) |
| `new BarcodeDetector({formats})` then `detect(image)` | `detectBarcodes(image=, formats=)` | send |
| `detect(video)`, called per frame | `detectedBarcodes(track=, formats=, interval=)` | source, live, polled (D5) |
| `TextDetector.availability({languages})` | `textDetectorAvailability(languages=)` | source, live |
| `TextDetector.create({languages})` then `detect(image)` | `detectText(image=, languages=)` | send |

`image` is a path (D4). `formats` is the specification's
[`BarcodeFormat`](https://wicg.github.io/shape-detection-api/#barcodeformat-section)
list: `aztec`, `code_128`, `code_39`, `code_93`, `codabar`,
`data_matrix`, `ean_13`, `ean_8`, `itf`, `pdf417`, `qr_code`, `upc_a`,
`upc_e`; `unknown` is answered, never asked for. `languages` is BCP 47
tags.

### D2 — Values and errors

| Shape | Fields |
|---|---|
| `BarcodeFormats` | `formats: string[]` (empty where there is no detector), `tracks` (bool: `detectedBarcodes` runs here), `apple`, `android` |
| `DetectedBarcode` | `rawValue`, `format`, `boundingBox: Rect`, `cornerPoints: Point[]` (four, clockwise from the top left), `apple`, `android` |
| `DetectedBarcodeList` | `barcodes: DetectedBarcode[]`, `width`, `height` (the upright image's pixels) |
| `SeenBarcode` | `rawValue`, `format`, `firstSeen`, `lastSeen` (session-clock ms), `frames` (how many analysed frames held it) |
| `BarcodeScan` | `state` (`idle`, `scanning`, `ended`), `barcodes: DetectedBarcode[]` (the latest analysed frame), `seen: SeenBarcode[]` (D5), `frame` (count of analysed frames), `width`, `height` (that frame's upright pixels), `error: option<string>` |
| `TextDetectorAvailability` | `availability` (`unavailable`, `downloadable`, `downloading`, `available`), `reason: option<…>` (LLP 1133.016 D2's words), `languages: string[]` (those the detector reads here), `apple`, `android` |
| `DetectedText` | `rawValue` (one line), `boundingBox`, `cornerPoints`, `apple`, `android` |
| `DetectedTextList` | `texts: DetectedText[]` in reading order, `width`, `height` |

`Rect` is `x`, `y`, `width`, `height`; `Point` is `x`, `y`; both in
pixels of the upright image, origin at the top left, as the
specification's `DOMRectReadOnly` and `Point2D` are in the image's
pixels.

**Errors** are LLP 1133.006 D8 item 2's (`{error, message}`, a
`DOMException` in TypeScript, `failure(…).code` in Contract), with a
`reason` where the name alone does not say what happened:

| Name | When |
|---|---|
| `TypeError` | `formats` empty or naming a format not in D1's list (the specification's constructor) |
| `NotSupportedError` | no detector on this target; a format or language the detector here does not read; a track on a target whose `tracks` is false |
| `NotAllowedError` | a path the app's grants do not let it read (`fs.read`, LLP 1133.006 D8 item 3) |
| `NotFoundError` | no file at the path; a track the session does not hold |
| `InvalidStateError` | a file that does not decode as an image (`decode`); the specification answers this name for an image source with no usable pixels |
| `OperationError` | the platform's detector failed on a still, or could not be made (Vision's error, ML Kit's `MlKitException`), its message kept |

A detection that finds nothing is not an error: it answers an empty
list. A live scan answers an error only when it cannot run at all (no
detector, a track the session does not hold), since the runner does not
poll a source again after an error answer until a reader asks anew
(`runner/src/runner/modules/poll.rs`). One frame the detector fails on
sets `BarcodeScan.error` to its message and leaves `state` `scanning`;
the next analysed frame clears it.

### D3 — Declared deviations

- **No detector objects.** The specification's `BarcodeDetector` holds
  only its formats, so tier 1 takes them on each call; implementations
  keep one platform detector per format set for the process. A
  `TextDetector` holds a loaded model; implementations keep it in the
  same way and drop it on memory pressure.
- **An image is a path.** The specification's `ImageBitmapSource` is a
  page object; here the image is a file (D4), and a camera frame is the
  track it comes from (D5).
- **A video is a track, polled.** The specification's `detect(video)`
  reads the frame the element shows when called, so a page loops on
  `requestVideoFrameCallback`. Tier 1 is one source per track, polled on
  the session clock, whose answer also keeps what earlier frames saw
  (D5).
- **`seen` is not in the specification.** It is what a page's own loop
  keeps, and without it a code in frame between two polls is lost.
- **Text detection follows an unshipped specification.** The Text
  Detection part is a Draft Community Group Report, and Chrome keeps
  `TextDetector` behind an experimental flag; no browser ships it
  ([MDN](https://developer.mozilla.org/docs/Web/API/Barcode_Detection_API),
  [Text Detection](https://wicg.github.io/shape-detection-api/text.html)).
  Its names are taken because they are the web's only names for the
  capability, with two deviations: `rawValue` here is Unicode, where the
  draft's Latin-1 limit reflects one implementation; and the module
  answers lines, which the draft leaves to the implementation.

**What tier 1 does not promise: the same reading.** Vision and ML Kit
are different models. A clean barcode reads the same `rawValue` and
`format` everywhere, since its symbology defines the value and D11's
UPC-A rule makes the one platform difference in naming the same; its box
differs by a few pixels. Text differs in line breaks, punctuation and errors. Drives
compare barcodes exactly and text by the lines a fixture prints (§9).

### D4 — How an image reaches the module

LLP 1133.019 settled it, and this module inherits it:

- `image` is a declared option `{ "type": "path", "access": "read" }`.
  The runner admits the path against the app's `fs.read` grants before
  dispatch (LLP 1133.006 D8 item 3), and the implementation reads the
  file the host maps it to (`context.file(path)` on Apple). An app
  detects in what the picker (`app:/tmp/picked/`), the camera
  (`app:/tmp/camera/`) or a photo library copy (`app:/tmp/photos/`) put
  there, or in its own files. No bytes cross Contract.
- The image is decoded **upright**: its EXIF orientation applied (Apple:
  `VNImageRequestHandler(url:orientation:)` with the file's
  `CGImagePropertyOrientation`; Android: `InputImage.fromFilePath`,
  which reads the rotation; the web: `createImageBitmap` with
  `imageOrientation: "from-image"`, the default). `width` and `height`
  are the upright image's; every box is in its pixels, top left origin.
  Vision answers normalised coordinates with a bottom left origin; the
  implementation converts.
- A HEIC the target cannot decode (the web outside Safari) fails
  `InvalidStateError`, `decode`. The recipe says to detect in the
  camera's JPEG or a `transformImage` copy.

### D5 — A live scan rides on a capture it does not keep

`detectedBarcodes(track=, formats=, interval=)` is a live source over a
video track the session holds. While read, it attaches a detector to
the track's capture as a **non-consuming output** (D17 item 1):

- **It takes no lease and holds none.** The capture runs because a
  viewfinder showing the track is a consumer (LLP 1133.008 D3); the scan
  analyses frames only while it runs. A hidden viewfinder stops the
  camera and the scan together, as a hand-built scanner screen stops its
  session when it disappears. The answer's `state` is `scanning` while
  frames arrive, `idle` while the track is muted or idle, and `ended`
  with the track.
- **So it starts nothing,** and needs no origin rule of its own. A tool
  invocation or a wake that reads the source learns what an app's state
  would show of a scan the person is already pointing the camera at; it
  cannot open the camera, which only a consumer admitted with an app
  origin does (LLP 1133.008 D3). In the background on iOS and Android
  the system interrupts the capture and the scan reads `idle`. On macOS
  a capture keeps running while its window is shown and the app is not
  frontmost (`VideoCapture.swift`'s `foreground` changes nothing there),
  as a hand-built Mac camera window's does, and so does its scan; the
  journal and `state.extensions` say so, and stage 2 drives it outside
  the substitute.
- **The latest frame only.** Each `interval` (default 100 ms, at least
  50, on the session clock) the implementation analyses the newest frame
  and drops the rest: Apple's video data output with
  `alwaysDiscardsLateVideoFrames` true and a delegate that hands one
  frame at a time to Vision; Android's `ImageAnalysis` with
  `STRATEGY_KEEP_ONLY_LATEST` ([image analysis](https://developer.android.com/media/camera/camerax/analyze));
  the web's `BarcodeDetector.detect()` on a module-owned, unattached
  `<video>` playing the track's stream. A frame still in the detector
  when the next is due is not queued behind.
- **What it answers.** `barcodes` is the latest analysed frame's;
  `seen` is every distinct `(format, rawValue)` since the source was
  first read for this track and formats, newest `lastSeen` first,
  bounded at 32 (the oldest dropped). The poll's answer is the whole
  value, so two that coalesce lose nothing; a code that was in frame for
  one analysed frame is in `seen` until 32 others displace it. A
  different `formats` is a different source, with its own `seen`.
- **The frame's coordinates.** Boxes are in the analysed frame's upright
  pixels (`width`, `height`): the sensor's rotation applied as the
  viewfinder applies it (Apple: the video data output connection's
  rotation; Android: `imageInfo.rotationDegrees`). Mapping a box onto the
  viewfinder's `object-fit` is the app's; Shelf draws none (§11).
- **Its end.** The last reader's `release(name, args)` (LLP 1133.009 D10
  item 12) removes the output and drops `seen`. A track's end answers
  `ended` and removes it.

**Attaching costs a reconfiguration.** Apple adds the video data output
inside `configure` between `beginConfiguration` and
`commitConfiguration`, which may hitch the preview once. CameraX binds a
use-case set at once, and adding `ImageAnalysis` to a bound set rebinds
it; one set holds a `Preview`, an `ImageCapture` and an `ImageAnalysis`
together ([CameraX architecture](https://developer.android.com/media/camera/camerax/architecture)),
so the camera's photo still works while scanning. The recipe reads the
scan in the screen that shows the viewfinder, from its first frame, so
the attach happens as the screen opens.

**Why not the platform's metadata output.** Apple's
`AVCaptureMetadataOutput` reads codes inside the capture pipeline at no
frame cost, and Android's ML Kit Analyzer pairs a detector with
`ImageAnalysis` in one call. The first answers normalised boxes in the
preview's space and its own type names, and has no counterpart on
stills; one path for stills and frames, Vision's, makes a scan and a
still answer the same formats and coordinates. The metadata output stays
reachable through the camera's capture-session hatch (LLP 1133.008 D5).
ML Kit Analyzer is a convenience over the same `ImageAnalysis` the
implementation uses.

### D6 — Unsaid defaults are the platform's

| Option | Web | Apple | Android |
|---|---|---|---|
| `formats` omitted | every supported format, as the specification's constructor | the request's default symbologies (all Vision supports) | `FORMAT_ALL_FORMATS` |
| `languages` omitted (text) | — | the request's default `recognitionLanguages`, with `automaticallyDetectsLanguage` at its default, false | the Latin script recognizer |
| recognition level | — | `.accurate`, the request's default | — |
| language correction | — | `usesLanguageCorrection` true, the default | — |
| `interval` omitted | 100 ms | 100 ms | 100 ms |

The interval is the module's, since no platform has one: Apple's and
Google's samples analyse every frame, which costs a phone's battery for
a value Contract reads at most once a frame.

**What the module adds to the screen: nothing.** It draws no
highlight, box or reticle, and plays no sound or haptic on a find. A
hand-built scanner screen does those itself or uses the system's scanner
UI (§11); a module that drew them would be a tell on every platform
whose look differs.

`textDetectorAvailability(languages=)` answers, in `languages`, what
`detectText` with the same `languages` reads, its tags matched by D7's
table to the recognizer's (Vision's `supportedRecognitionLanguages()`,
ML Kit's Latin list), and `unavailable`, `unsupported-options` where one
does not match: with them omitted, the
default request's list, which is not every language the recognizer
knows. So an app that reads more than that names its languages, as
Shelf does (§10). Its `downloadable` and `downloading` are the
specification's and occur on no target built here: Vision and the
bundled Latin recognizer download nothing.

`getSupportedFormats` and `textDetectorAvailability` are live on the web,
where a browser update changes them; each is read again at the return to
the foreground. On Apple and Android they are fixed for a build.

**Languages** are BCP 47 tags, validated and canonicalised as the
specification does. The web implementation passes them to the browser,
whose best-fit matching is its own (ECMA-402 leaves
[LookupMatchingLocaleByBestFit](https://tc39.es/ecma402/#sec-lookupmatchinglocalebybestfit)
to the implementation). The native implementations share one table in
the interface: a tag's script is made explicit where its region implies
one (`zh-TW`, `zh-HK` and `zh-MO` are `zh-Hant`; `zh-CN` and `zh-SG`,
`zh-Hans`; bare `zh` is `zh-Hans`), then it is truncated as LLP 1060
truncates (`zh-Hant-TW`, then `zh-Hant`, then `zh`) until the platform
lists it. Apple's Translation lists `zh-Hans` and `zh-Hant`. ML Kit's
translation has one Chinese model, Simplified (`zh`), so on Android every
`zh-Hant` tag is `unavailable`, `unsupported-options`, never translated
as Simplified. A pair whose source and target match after that is `unavailable`,
`unsupported-options` on every target, as Apple's `LanguageAvailability`
answers it; the specification leaves it to the browser, and one answer
everywhere is the point of tier 1.

**Detection's results** follow the specification's algorithm on every
target: the platform's probabilities sorted by confidence, those below
the unknown share dropped, stopping once they sum to 0.99, and an `und`
entry last with the unknown share. Apple's `languageHypotheses(withMaximum:)`
and ML Kit's `identifyPossibleLanguages` (confidence threshold 0.01, its
default) give the probabilities; ML Kit's own `und` becomes the unknown
share.

**Errors**, LLP 1133.016 D2's names with this module's causes:

| Name | When | Platforms' cause |
|---|---|---|
| `NotSupportedError` | a create or translate where `availability` is `unavailable` | Apple `unsupportedSourceLanguage`, `unsupportedTargetLanguage`, `unsupportedLanguagePairing`; ML Kit's `fromLanguageTag` null |
| `NotAllowedError` | a create from a tool or a wake (`person-required`) or the background (no reason; the runner's refusal, D16); a download whose activation has lapsed (`activation`; D8); before iOS and macOS 26, a translate from a tool, a wake or the background (`person-required`, `background`; D8); the person declined Apple's download sheet (`declined`); a permissions policy refusal on the web (`policy`) | web as specified; Apple's sheet dismissed |
| `QuotaExceededError` | an input longer than `inputQuota`, with `requested` and `quota` | web as specified |
| `InvalidStateError` | a destroyed handle or one the session does not hold; a translator whose language pack was removed (`not-installed`) | Apple `notInstalled`; ML Kit's model deleted |
| `OperationError` | the model failed to load or run | Apple `internalError`; ML Kit's `MlKitException` |
| `AbortError` | a destroyed handle's call in flight; a call let go (LLP 1133.016 D15 item 2) | Apple `alreadyCancelled` |

Empty input answers as the specification does: an empty translation,
and detection's `und` at 1. Apple throws `nothingToTranslate` for it, so
the implementation answers before calling. Apple's
`unableToIdentifyLanguage` cannot arise, since a tier 1 translator always
names its source.

### D8 — Availability and downloads, inherited

LLP 1133.016 D5's availability holds as written: a live fact with a
shared `reason`, read again at the return to the foreground, at each
create and while something downloads; `available` is a promise about
now; a download is started only by a create while `downloadable`. Its
admission is narrowed: every create, not only one that downloads, is
the app's foreground act (D16). The platforms map:

| Platform | `available` | `downloadable` | `downloading` | `unavailable` |
|---|---|---|---|---|
| web | the same word | the same word | the same word | the same, `not-supported` |
| Apple `LanguageAvailability.status(from:to:)` | `.installed` | `.supported` | while the module's own `prepareTranslation()` runs, `progress` absent | `.unsupported`: `unsupported-options`; below iOS 18 or macOS 15: `os`; tvOS: `not-supported` |
| Android ML Kit `RemoteModelManager.isModelDownloaded` for both languages' models | both downloaded | either not | while the module's `downloadModelIfNeeded` runs | a language ML Kit does not translate: `unsupported-options` |
| Apple `NLLanguageRecognizer`, ML Kit language identification (bundled) | always | — | — | — |

Two things the web adds, and the module keeps:

- **Chrome hides which pairs are downloaded.** It reports `downloadable`
  for every pair the browser supports until this site has created a
  translator for it, so a site cannot learn which languages the person
  reads ([Translator API](https://developer.chrome.com/docs/ai/translator-api)).
  An app reads the web's answer as it is; the recipe says `downloadable`
  on the web may need no download.
- **A create that downloads needs transient activation** and consumes
  it (Writing Assistance APIs §5.2, which `Translator.create` and
  `LanguageDetector.create` share). The web implementation calls
  `create()` inside the press's activation (`"gesture": true`, LLP
  1133.016 D15 item 5). A press whose handler downloads a detector and
  then a translator has used its activation on the first; the second
  fails `NotAllowedError`, `activation`, and asks for another press
  (Excord's recipe, §10).

What Apple adds:

- **The system asks the person.** `prepareTranslation()` "asks for
  permission to download" with the system's sheet
  ([TranslationSession](https://developer.apple.com/documentation/translation/translationsession)).
  The implementation calls it itself inside a create while
  `downloadable`; every create is the app's foreground act (D16). A dismissed sheet fails the create `NotAllowedError`,
  `declined`, and the availability stays `downloadable`.
- **A translate must not ask.** A session from `translationTask` "can
  always request downloads", and translating on one whose languages are
  not installed prompts the person; only a session made by
  `init(installedSource:target:)` (iOS and macOS 26) cannot, and throws
  `notInstalled` instead
  ([canRequestDownloads](https://developer.apple.com/documentation/translation/translationsession/canrequestdownloads)).
  So:
  - **iOS and macOS 26 and later:** every translate runs on an
    installed-only session (D9), from any caller. A pack the person has
    removed fails it `InvalidStateError`, `not-installed`.
  - **iOS 18 to 25 and macOS 15 to 25:** each translate first reads
    `LanguageAvailability.status(from:to:)` and runs only when it
    answers `.installed`; otherwise it fails `InvalidStateError`,
    `not-installed`, without touching the session. The read and the
    translate are not atomic: a pack removed in the instant between
    them would let the session show its sheet. So on these versions a
    translate is admitted only from the app's own foreground code,
    where a sheet is one the person can answer in the app they are
    using; a tool's, a wake's or a background translate fails
    `NotAllowedError`, `person-required` or `background`. The
    implementation applies this rule (D16), and stage 3 drives the real
    removal on both versions by hand (LLP 1133.020's row).
- **The person removes languages in Settings.** Either way the
  availability is announced as `downloadable`, and the app creates
  again, by a person's act.

Android adds **download conditions**: `DownloadConditions` with no
requirement is ML Kit's default, and so the module's; `android.requireWifi`
is tier 2 (D12). A model is about 30 MB per language
([translation](https://developers.google.com/ml-kit/language/translation/android));
ML Kit pivots through English, so a pair downloads up to two.

There is **no permission** on any platform: none asks before an app
translates. Apple's sheet is the person's consent to a download, not a
grant; the module has no permission state, no ticket and no grant line,
as LLP 1133.016 §14 question 8 ruled for the language model.

### D9 — Translators and detectors are handles; the platform's object is a cache

A `translator` and a `language-detector` are handles the implementation
holds for the app's session (LLP 1133.009 D10 item 10): one whose
creating reply is dropped before delivery is disposed; a delivered one
lives until `destroyTranslator` or `destroyLanguageDetector`, or the
session's end, whatever answers still refer to it (LLP 1133.009 D6). `translate` and `detectLanguage` on one handle run in admission
order, one at a time, as Chrome runs translations sequentially (Chrome's
Translator API page); different handles run concurrently where the
platform allows.

The handle is the module's, and the platform's object behind it is
rebuilt whenever it is lost:

- **Apple, iOS 18 to 25 and macOS 15 to 25.** A `TranslationSession` is
  obtained only through SwiftUI's `translationTask(_:action:)` on a view,
  and the configuration must not change while the session is used. The
  implementation hosts, per translator, a zero-size hidden SwiftUI view
  carrying `translationTask` with the translator's fixed configuration,
  inside the session's own view (D17 item 3):
  - **iOS:** a `UIHostingController`, made a child of the session
    window's root view controller (`addChild`, its view added under the
    session's view, `didMove(toParent:)`), so it receives the appearance
    callbacks that start SwiftUI's task; a hosting controller's view
    added without the containment calls does not get them.
  - **macOS:** an `NSHostingView` added under the session's view. A
    session window has no content view controller to be a child of
    (`ExactMac/main.swift` sets `contentViewController` to nil outside a
    sidebar, and the sample host's two sessions are panes of one window,
    `ExactHostMac/main.swift`), and an `NSHostingView` runs its SwiftUI
    hierarchy, its tasks included, once it is in a window.

  Stage 0 proves the task runs in each: a second macOS window, a sample
  host pane on macOS and on iOS. Inside the action it
  keeps the session and serves the handle's calls through it, one at a
  time, until the handle is destroyed. The view's `onDisappear` marks
  the session dead before anything can call it, so the fatalError cannot
  be reached: a call then finds no session and rebuilds one (a new view;
  `prepareTranslation()` is not called again, since the pair is
  installed), or, if the pair is no longer installed, fails
  `InvalidStateError`, `not-installed`. A macOS window closing, a scene
  disconnecting on iPad and a session's end are all an `onDisappear`.
- **Apple, iOS 26 and macOS 26.** `TranslationSession(installedSource:target:)`
  makes a session with no view for an installed pair, and cannot request
  downloads ([init(installedSource:target:)](https://developer.apple.com/documentation/translation/translationsession/init(installedsource:target:))).
  The implementation serves every translate through one, and uses a
  hosted view only for a create that downloads, which it removes once
  `prepareTranslation()` returns. So on 26 no translate can prompt (D8).
- **Android.** `Translation.getClient(TranslatorOptions)`; the module
  calls `close()` at destroy and on memory pressure, and makes a new
  client at the next call.
- **Web.** The `Translator` object; `destroy()` at destroy.

Apple's language detection is `NLLanguageRecognizer`, a value made per
call, and its detector handle holds only `expectedInputLanguages`, passed
as `languageHints`. ML Kit's `LanguageIdentification.getClient()` is kept
per handle and closed at destroy.

**`inputQuota`** is the web's where the browser gives one. Apple and ML
Kit document no limit, so it is absent there, and the implementation
splits a long input at paragraph breaks into the platform's calls and
joins the results, so a long message does not fail where the web's
would not. `measureInputUsage` is not tier 1 (§11).

### D10 — Unsaid defaults are the platform's

| Option | Web | Apple | Android |
|---|---|---|---|
| translation strategy | the browser's | the framework's default: no `Strategy` given to the session or to `LanguageAvailability`, so availability and translation consider the same models | — |

**What the module adds to the screen: nothing** but Apple's own sheet,
which is the platform's. How a translation is marked is the app's
(Excord's "Translated from Japanese", §10), with one exception the
platform's terms impose: an app using ML Kit's translation "must comply
with the Google Cloud Translation API" attribution requirements
([usage guidelines](https://developers.google.com/ml-kit/language/translation/translation-terms)):
the "powered by Google Translate" graphic "adjacent any translation
results", a mobile button that starts a translation "clearly labeled
'Translate with Google'", and a statement in the app's description and
help that Google Translate is used
([attribution](https://docs.cloud.google.com/translate/attribution)).
So `TranslatorInfo` answers `attribution`, `google-translate` on Android
and none elsewhere, and the app shows what it names (§10). The module
draws nothing itself, since where the translation appears is the app's;
the recipe gives the graphic and the label, and the Android store
listing's line is the app author's.

**Where text goes.** Every endorsed implementation translates on the
device: Apple's Translation runs on device once its languages are
installed, ML Kit's translation is on device, and Chrome's Translator runs
its model locally. The web's API does not promise it for every browser,
and the module claims only what the implementation does: each availability
answers `apple`/`android` details, and the recipe for an app whose text
must not leave the device names the web as the one target to check.

Vision has no UPC-A symbology
([VNBarcodeSymbology](https://developer.apple.com/documentation/vision/vnbarcodesymbology));
AVFoundation documents that it reports UPC-A as EAN-13 with a leading
zero ([`ean13`](https://developer.apple.com/documentation/avfoundation/avmetadataobject/objecttype/ean13)).
ML Kit answers `FORMAT_UPC_A` and the 12 digits, and a browser answers
whatever its detector does (Chrome on macOS is Vision). A UPC-A is an
EAN-13 whose first digit is 0, encoded the same way, so one rule makes
every target agree. Each implementation asks its platform for both
formats whenever either is asked (or none is), then, on the platform's
results and the browser's alike:

1. **Normalises.** A code reported as `upc_a` with 12 digits, or as
   `ean_13` with 13 digits beginning with 0, is one UPC-A code. It is
   answered as `upc_a` and 12 digits where `upc_a` is among the formats
   asked (the default includes it), and otherwise as `ean_13` and 13
   digits, a 0 put in front of a platform's 12.
2. **Filters.** A result whose format, after that, is not among the
   formats asked is dropped, so asking for `upc_a` alone never answers a
   book's ISBN, and asking for `ean_13` alone never answers a `upc_a`.

Stage 1's fixtures check it on each target: a UPC-A asked as `upc_a`, as
`ean_13` and with the default; an ISBN asked as `upc_a` (no result).

**Web:** no words. **Windows** (when built, D18): `OcrEngine`'s
`RecognizerLanguage`.

### D14 — Packaging on Android: bundled models

ML Kit offers each vision model two ways: bundled into the APK, or
unbundled, downloaded by Google Play services at install or first use.
The implementation links the bundled ones,
`com.google.mlkit:barcode-scanning:17.3.0` (about 2.4 MB) and

## 5. Permission, callers and origins

### D15 — Permission: none of its own

No platform asks the person before an app runs a detector on its own
file or a translator on its own text, so no name declares a permission,
a grant line or a ticket. The paths a still names are admitted against
`fs.read` (D4). A live scan reads a track whose camera permission and
`device.camera` grant are the camera's (LLP 1133.008), and adds nothing:
an app that scans already holds a track. LLP 1133.002 D6–D12 apply
where they are, in `@exact/media-capture`.

### D16 — Callers

- **Contract** reads `getSupportedFormats`, `detectedBarcodes`,
  `textDetectorAvailability`, `translatorAvailability` and
  `languageDetectorAvailability` as sources, and sends the rest from
  actions.
- **Data code** calls every send and reads the availabilities through
  its generated binding, in Promise form. `detectedBarcodes` is
  Contract's: a scan means something only beside the viewfinder it rides
  on, which is the view's.
- **Origins.** Detection and a translate show no UI and start no
  device, so any caller may run them on a handle that exists: a tool
  invocation (LLP 1111) may translate a message with a translator the
  app made, or read a file's codes under its own `fs.read` admission.
  Two rules keep the person's acts the person's:
  - **Every create is the app's foreground act.** `createTranslator` and
    `createLanguageDetector` declare `"origin": "app"` and `"foreground":
    true` at the top level, which the runner's admission already applies
    before dispatch (`runner/src/runner/modules/admit.rs`): a tool, a
    model's tool call and a wake fail `NotAllowedError`,
    `person-required`, and a create in the background `NotAllowedError`
    with no reason, as the runner answers it, whatever the
    availability. A rule conditioned on availability, LLP 1133.016 D5's
    `download` form, cannot be enforced: the web's create reads
    availability again in parallel and may find a pair evicted since any
    read before it, and then downloads under whatever activation the page
    holds ([create an AI model object](https://webmachinelearning.github.io/writing-assistance-apis/#create-an-ai-model-object)
    and [download eviction](https://webmachinelearning.github.io/writing-assistance-apis/#download-eviction)),
    and the specification has no create that refuses to download. So the condition is dropped; the cost is that a tool or
    a wake cannot make a translator, which no consumer needs.
  - **A translate before iOS and macOS 26** runs only from the app's
    foreground code (D8). It depends on the OS version, which only the
    implementation knows, so the implementation applies it, told the
    call's origin and the foreground (the context's `origin` and
    `foreground`, LLP 1133.009 D10 items 3 and 8), before it reads
    anything; nothing races it.

  The conformance suite proves both in production mode, not only under
  the agent: its fixture binds each implementation over a stand-in
  platform object (a `Translator` the test supplies on the web; a
  protocol the Apple and Android implementations already call through)
  and asserts that a tool's and a wake's create, and a pre-26 tool's
  translate, never reach it. On Apple the create is the only path to the
  system's sheet, so a wake never shows one (LLP 1114.001 D4).
- **`sync`.** `getSupportedFormats`, `textDetectorAvailability` and
  `languageDetectorAvailability` have synchronous forms through `call`
  on Apple, where each is fixed for a build; elsewhere, and for
  `translatorAvailability` everywhere (Apple's `status(from:to:)` is
  `async`, which `call`'s 100 ms budget cannot wait on), they throw
  `NotSupportedError` (LLP 1133 D6 rule 4), as the language model's do.
- **No name is a request** in LLP 1069.007 D1's sense: Apple's sheet is
  part of a create's download, admitted as the download is.

## 6. Every target, and cost

### D17 — Seam additions

Each general, each proved by the out-of-tree fixture before a package
uses it (LLP 1133.001 D8):

1. **A video output that is not a consumer.** A video track's entry
   gains `observe(id, observer)` beside `subscribe` on every host
   (`ExactTrackOwner` on Apple, `TrackOwner` on Android, the web
   implementation's track table). An observer is told `live(video:)`,
   `muted`, `unmuted` and `ended` as a consumer is, and attaches and
   removes outputs through the same `configure` (Apple) and
   `add`/`remove` (Android), but never takes, holds or reopens a lease
   and never counts toward the consumers `mediaStreamTrack` reports.
   The camera's hatch (LLP 1133.008 D5) already lets an app's output
   declare "a consumer or not"; this builds the "not". The text-detection
   package does not use it; a future frame consumer may.
2. **The agent's picture is a frame.** Under the agent no capture
   exists, a consumer is told `live(video: nil)`, and the camera package
   resolves and draws its picture itself: a record, `prefer extension
   camera.picture={"path":"…"}`, naming an app asset, found through
   `EXACT_ASSETS` or the bundle on Apple (`agentPictureURL` in
   `Camera.swift`), the APK's `app/` assets on Android, and the page's
   base URL on the web, else the package's test card. A video track's
   entry under the agent gains the decoded picture the viewfinder is
   drawing (a `CGImage` on Apple, a `Bitmap` on Android, an
   `ImageBitmap` on the web) and announces a change of it, so an
   observer analyses those pixels as each frame. The camera package
   stays the one authority on the picture; the barcode package never
   resolves a path of its own.
3. **The session's presentation, on Apple.** LLP 1133.015 D16 item 3,
   accepted and not built, is built here, with two changes. The package
   context gains `presentation`: on iOS the session's `UIWindowScene`
   and its window's root view controller, on macOS the session's
   `NSWindow`; and beside it `view`, the session's own root view (in the
   sample host, its pane), which hosted views go under. It is nil while
   the session's view is in no window on screen, and set while it is,
   key or not, since a translator for a window behind another must be
   hosted in that window. The changes from LLP 1133.015's text: macOS
   gives no content view controller, which session windows do not have
   (D9), and "in front" is not the nil condition; a purchase's refusal
   while no window of the session is in front (LLP 1133.015 D15) becomes
   purchases' own check on a set `presentation` (the scene's
   `activationState`, the window's `isKeyWindow`). A package presents and
   hosts views in its own session rather than the key window's. Translation needs it for D9's hosted
   view: in the sample host's two sessions (LLP 1031 D10), or two macOS
   windows, the key window is often another session's. LLP 1133.018 D13
   item 1's anchor, the pressed node's rectangle within that window,
   which a Mac contact picker is shown from, is not built here and stays
   contacts'.

The rest is inherited unchanged: handles and their disposal, `release`,
`destroy`, the session clock, the foreground, polled sources and `clock`
waiting on polls, preferred values reaching the implementation,
`download`, `gesture`, `cancel`, `"poll": {"while": …}` (unused: a scan

### D19 — Cost

- **Apple:** the frameworks are the system's; the implementations are
  Swift in the app's package module, linked only where the app imports
  the package. Translation is weak-linked below its OS.
- **Android:** the bundled models of D14, in an app that imports the
  package: barcodes about 2.4 MB, Latin text about 4 MB per architecture,
  language identification about 900 KB, translation's library without
  models. Translation models download at a person's act (D8).
- **Web:** each package's implementation is a chunk loaded at the app's
  first read of one of its names (LLP 1133.016 D15 item 5); nothing else.
- **An app that does not import a package:** nothing. **Before first
  pixel:** nothing; no detector, model or session is made until a name
  is read or sent. Stage 0 measures each with LLP 1047's probe.
- **A scan:** one analysed frame per interval, the others dropped before
  conversion. Stage 2 measures a phone's CPU and energy with a scan
  running against a viewfinder alone, at 100 and 200 ms, and sets the
  default from it.

## 9. The substitute

**The implementation is its own substitute,** in LLP 1133.008 D8 item
9's split: under the agent the runner admits each call (paths, origins,
the foreground, downloads), and each implementation runs, told so, opens
no device, downloads nothing, presents nothing and calls no hatch.

**Vision runs for real on fixture images.** A still's detection is the
platform's detector on the named file, as in production: nothing about
it is a device, a prompt or the person's data, and drives use only the
packages' fixture images and the apps' own assets, never this machine's
photos. The answer differs across Vision and ML Kit only as D3 says, so
the conformance suite compares `rawValue` and `format` exactly, the
count of results exactly, and each box within 4% of the image's longer
side; text by the lines the fixture prints, each found as a substring
of one answered line after folding case and whitespace.

**A live scan analyses the camera's agent picture** (D17 item 2) at
each interval of the session clock, so `prefer extension
camera.picture={"path":"assets/test/isbn-9780747532743.png"}`, an asset of the
app under test, puts an ISBN in front of the agent's back camera, and
`clock +200` shows it in `seen`. The picture must be an app asset,
since that is where the camera's resolver looks on every host; Shelf
carries its two drive images (the ISBN and `none.png`, a few kilobytes)
in `assets/test/`, and the conformance fixture app carries the
packages' fixtures. A drive
that changes the picture changes the next analysed frame; `firstSeen`
and `lastSeen` are session-clock times, so they are the same every run.

Where a target has no detector (the web outside Chrome on macOS,
ChromeOS and Android; text on the web), the declared answers hold under
the agent as in production. `prefer extension
barcode-detection.getSupportedFormats={…}` and the other preferred values
of LLP 1133.009 D10 item 11 overlay an answer as for any source, for a
drive of an app's absent path; a drive that needs a real detection runs
on a host that has one, and the drive list says which (§12).

**Translation is scripted.** No model runs, because every target's
differs and a screenshot must be the same on every host:

- **Availability** is `available` for any pair of distinct languages in
  a fixed list (`ar`, `de`, `en`, `es`, `fr`, `hi`, `it`, `ja`, `ko`,
  `pt`, `ru`, `zh`, `zh-Hant`), after D7's tag table, each target's
  restrictions applied: Android answers `zh-Hant` `unavailable`,
  `unsupported-options`, as ML Kit does; tvOS answers translation
  `not-supported`; Apple below 26 refuses an unattended translate as D8
  does. `prefer extension
  translation.translatorAvailability={"availability":"downloadable"}`
  overlays it, as LLP 1133.016 §9's does. A create while `downloadable`
  from an admitted origin sets `downloading` with `progress` 0 and waits;
  the drive completes it with `{"availability":"available"}`. On Apple
  the create first passes the system's sheet, which the agent answers
  with `prefer extension translation.downloadSheet="decline"` (default
  `accept`), so the declined path is driven where it exists.
- **A translation** comes from the script `prefer extension
  translation.translations=[{"text":"…"}, …]`, each translate taking the
  next entry in admission order; `{"error":"InvalidStateError",
  "reason":"not-installed"}` fails one. With the script empty, the text
  is the input with the target's tag in front, `[en] 明日は十時から。`.
- **Detection** comes from `prefer extension translation.detections=[…]`,
  else a fixed rule on the scripts of the input's letters: any Hiragana
  or Katakana is `ja` (Japanese text mixes kana with Han, and is often
  led by a Han character, as "明日" is); otherwise any Hangul is `ko`;
  otherwise the first letter's script: Han `zh`, Cyrillic `ru`, Arabic
  `ar`, Devanagari `hi`, Latin `en`. Each answers at 0.9 with `und` at
  0.1; no letter answers `und` at 1.

These are agent-only sources of the interface (`"source":
"translations", "agent": true`, and likewise `detections` and
`downloadSheet`), the form `camera.picture` takes.

**Disclosure:** `state.extensions` lists each scan's track, formats,
interval, frames analysed and `seen`; each detection's path and its
result count; each translator and detector with its languages, the
platform object's state (live, rebuilt, dead) and calls in flight; the
script's remaining entries; and each answer's origin.

**Production:** none of it.

### Shelf: Scan Barcode and Add Quote from Photo

Adding a book by hand is three fields typed on a phone; every printed
book since the 1970s carries its ISBN as an EAN-13 barcode beginning
978 or 979. Shelf gains:

1. **Scan Barcode** in the add sheet's header, shown where
   `formats.tracks` and `formats.formats` includes `ean_13` and the
   camera is available. It opens the back camera (`getUserMedia`,
   `facingMode` `environment`) and pushes a scan screen inside the
   sheet: the viewfinder, the line "Point the camera at the barcode on
   the back of the book", and Cancel. `detectedBarcodes(track=,
   formats=["ean_13"])` reads it.
2. **The lookup.** The first `seen` value that is a valid ISBN-13 (978
   or 979 and its check digit) is looked up in data code at
   `https://openlibrary.org/isbn/{isbn}.json` and its first author's
   record ([Books API](https://openlibrary.org/dev/docs/api/books)), under
   the grant Shelf already has. The scan screen shows the title and
   author it found with **Use This Book**, or "No book found for ISBN …"
   with Try Again. Use This Book fills the add sheet's title, author and
   page count, stops the track and pops back; the person still saves.
   Nothing is added by the scan alone.
3. **Add Quote from Photo** in a book's notes: a file input
   (`accept="image/*"`, LLP 1069.002) takes a photo of a page from
   wherever the platform's picker offers; `detectText(image=,
   languages=[…])` reads it. The languages are the person's
   (`time.locale`, through D7's tag table, so `zh-Hant-TW` is `zh-Hant`)
   and English, where `textDetectorAvailability` for them answers
   `available`; otherwise none are named and the platform's default
   applies, since a tag the recognizer does not list fails the call
   (`NotSupportedError`, D2). A sheet lists the lines, each a toggle, all on; Add appends
   the chosen lines to the notes as one quoted paragraph. Shown where
   `textDetectorAvailability` is `available`: not on the web (D18).

Shelf's `package.json` depends on `@exact/media-capture`,
`@exact/camera`, `@exact/barcode-detection` and `@exact/text-detection`,
which `app.contract` takes by `use`. Its grants, in `app.ts`, gain
`device.camera` with a purpose key and its strings-table purpose, as
`apps/photo-editor/app.ts` has, and `fs.read app:/tmp/picked`. Its
`assets/test/` holds the two drive images (§9).

### Excord: Translate

## 11. What stays out

Each until a consumer asks:

- **Text recognition on camera frames** (Live Text in a viewfinder),
  and text recognition on the web through a wasm OCR.
- **The system's scanner UI**: VisionKit's `DataScannerViewController`
  (iOS 16, a full-screen system scanner with its own highlights) and
  the Google code scanner (Google's UI, no camera permission). §13
  question 2.
- **Document scanning**: VisionKit's document camera and ML Kit's
  document scanner, both system UI that answer page images.
- **Live Text interaction** on an image (`ImageAnalysisInteraction`) and
  **Apple's translation overlay** (`translationPresentation`).
- **Apple's translation strategy** (`highFidelity`, `lowLatency`, iOS
  and macOS 26.4): it selects different models with their own
  availability, so it would be an option of `translatorAvailability` and
  of every create and rebuild at once, not a create's word (D10).
- **Streaming translation** (`translateStreaming`), `measureInputUsage`,
  and the Summarizer and Rewriter of the same family.
- **Scripts other than Latin for text on Android** (ML Kit's Chinese,
  Devanagari, Japanese and Korean recognizers, each bundled separately);
  on Apple every language Vision reads is in.
- **Android's platform `TranslationManager`** (API 31) and
  `TextClassifier.detectLanguage` (API 29): the first is backed by an
  on-device translation service whose availability varies by device and
  answers null when the service cannot create a translator; the second
  is a classifier that "may take several seconds" per call. ML Kit is
  the same everywhere from API 23 and is what an Android developer
  reaches for.
- **Barcode generation**, and Vision's other requests (faces,
  rectangles, saliency, body pose).
- **The Windows and Linux cells** of D18 that are `later` or a third
  party's.
