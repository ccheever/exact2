## Summary

Save Rust business logic, rebuild the affected modules, and replace their
implementations in the running app. Keep the host process open and carry
compatible application state. Use native machine code on native platforms
where replacement is practical, Wasm in the browser, and Wasmtime's Pulley
interpreter for replacements on a physical iPhone, without JIT.

Native hosts start with their compiled-in Rust implementation. They need not
interpret anything until an edited module arrives. On physical iOS, only
replaced modules become interpreted; the next native rebuild makes them
native again. One module initially contains the app's entire Rust data crate,
so any edit initially replaces that whole crate, not just the edited function.

This records Charlie's September 8–9 discussion and request for an LLP. It is
a proposal, not an implementation report or acceptance of the parent RFC.
For development, it replaces the parent's proposed universal Wasmtime path,
per-source digest staging, and coupling of development capability to release
engine selection. The parent's mixed-language direction remains separate.
Production Rust code delivery is deferred; this document does not authorize it.

**Sanity check (2026-09-09):** [Grok](reviews/1029.000-rust-development-reload.grok.md)
and [Muse](reviews/1029.000-rust-development-reload.meta.md) independently
recommended proceeding with limited changes, not a change of direction.
The interface map, native retention policy, and identity/effect clarifications
below incorporate those findings. The reviews cover the earlier revision
identified by SHA-256 in their headers; this revision has not been re-reviewed.

## 1. The experience and the boundary

The developer opens the same development URL on web, macOS, and an iOS
simulator or phone. A Rust edit builds in the background while the old app
continues running. A successful, compatible candidate updates the running
session. A compiler error or rejected candidate leaves the old version usable.
Latest edit wins; a slower old build cannot overwrite a newer result.

The host, runner code, kernel, renderer, input, and host services remain
resident. A logic reload can reconstruct session runners and views through
the existing restart-with-carry path. Keeping the process open does not
promise stable view objects, scroll position, or focus across reconstruction.

The unit of replacement is an explicitly bounded business-logic module with
a versioned interface. A Rust `mod` or `.rs` file is not a loadable unit.
Cargo reuses unaffected dependencies and incremental compiler work inside
crates; each affected loadable artifact still needs a link. Shared helper or
interface changes invalidate their dependent modules. Host/ABI changes
outside the admitted boundary require a host rebuild, reported as such.

Start with one data module per app. Introduce additional independent modules
only when an app needs them. Reuse Cargo's graph for build dependencies and
the existing app composition for routing; no function-reachability analysis,
per-function hashes, Rust heap patching, or new module registry.
Caltrain's pure data crate is the first complete replaceable module. An app
whose data crate still owns native file/worker work does not qualify wholesale:
adapt that work to host services or keep the crate binary-bound. A mixed
replaceable/binary-bound crate is not silently inferred from provider names.

## 2. Executors

| Surface | Initial Rust logic | Replacement artifact/executor |
|---|---|---|
| Web | Baked into the initial app Wasm | Separate logic Wasm, executed by the browser |
| macOS | Linked native Rust | Rust `cdylib` as a uniquely named `.dylib`, loaded with `dlopen` |
| Linux | Linked native Rust | Rust `cdylib` as a uniquely named `.so`, loaded with `dlopen` |
| iOS simulator | Linked native Rust | Prefer simulator-target native library; prove loading/signing and retirement first; Pulley is the fallback |
| Physical iOS | Linked native Rust | Wasmtime runtime + Pulley, loading precompiled `pulley64` bytecode |
| Android, future | Native Rust | Native `.so` is a candidate; Android host work remains out of scope |

Native loading is supported by [macOS](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/DynamicLibraries/100-Articles/DynamicLibraryUsageGuidelines.html),
[Linux](https://man7.org/linux/man-pages/man3/dlopen.3.html), and
[Android's NDK](https://developer.android.com/ndk/reference/group/libdl).
Exact2's `host/apple/Sources/ExactKit/GpuModule.swift` already loads a library;
it does not prove repeated logic replacement or safe unloading. macOS builds
must satisfy [library validation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation)
through appropriate signing or development configuration. Android would
also need device delivery, ABI selection, and permitted library paths.

For the phone, the development machine compiles Rust → Wasm → optimized
Pulley bytecode. The installed app links the runtime/interpreter, not
Cranelift or Winch. No executable ARM code is generated or loaded by this
replacement path. Wasmtime's [Pulley documentation](https://docs.wasmtime.dev/examples-pulley.html)
describes the execution mode; [iOS is Tier 3](https://docs.wasmtime.dev/stability-tiers.html),
so actual device integration needs verification. A native precompiled
Wasmtime artifact is not a workaround for the phone's executable-memory
restrictions. Pulley bytecode is the portable interpreted artifact here.

The development composition explicitly selects its adapters, independently
of release delivery policy. A release app can ship native Rust and no
Wasmtime. Optional executors remain separate adapters/artifacts above core
crates, not Cargo features on the runner or hosts. Existing platform build
scripts select concrete compositions; no combinatorial build matrix.

## 3. One interface, with ownership made explicit

Both loaders implement the existing `DataSource` replacement seam. Define a
small versioned C-compatible interface for native libraries and equivalent
exports over Wasm linear memory: identity, grants, activation, answer/parse,
and destruction, with bounded encoded arguments/results and explicit buffer
ownership. LLP 1026 D3 is the starting point; it must be reconciled with the
current `runner/src/runner/source.rs`, not copied as an already complete ABI.

The **host adapter**, not the loaded library, implements the Rust trait.
`replacement() -> Self` constructs another adapter in the host; no Rust `Self`
crosses the ABI. The method-by-method map for the first implementation is:

| `DataSource` method | Host adapter | Encoded module operation |
|---|---|---|
| `replacement` | Validate receipt, select loader, own candidate lifetime | Create an isolated instance; no effects |
| `app_id`, `grants` | Cache and enforce the admitted values | Read metadata once; compare with receipt |
| `revision` | Own the module identity in §5 | No module-selected revision authority |
| `bind` | Validate paired plan and compatibility | Supply existing encoded plan bytes; module owns its decoded copy |
| `ready` | Track deferred/active state | No separate readiness authority in the first synchronous adapter |
| `configure_storage` | Retain host paths/capabilities; open nothing before first pixel | No paths or filesystem handles cross |
| `activate`, `activate_for_validation` | Select committed or disposable mode | Activate fresh instance with the selected mode, without direct I/O |
| `query` | Supply an empty Store context, require an immediate value | Same dispatcher as `answer` |
| `answer` | Encode granted Store snapshot, source and arguments | Return `Answer`/error, ordered Store writes, and Store-read observations |
| `parse` | Encode the same context plus `Outcome` | Return the same result envelope as `answer` |
| `continuation` | Own work and ticket lifetime | V1 refuses module-local continuation requests; no Rust closure crosses |
| Adapter drop | Release instance resources while its library is still mapped | Destroy the instance using its own implementation |

Use `exact-plan`'s canonical `Value` encoding and format identity. Additional
envelopes encode `Request`, `Outcome`, `DataError`, and Store snapshot/writes
as explicit tagged fields, never Rust object layouts. Include observations
of Store reads, including absent keys, so resource invalidation and kept
answers retain their meaning. Never expose runner-private `exact.kept.*`
entries to module code. The host rechecks grants and applies returned writes
only through its transaction. An invalid result applies no partial writes.

Specify the field order, integer widths, tag values, byte/depth bounds, and
allocator/free signatures in the shared ABI declaration before loader code.
Inputs are borrowed only for a call; outputs are copied before the next call
and freed by their producing allocator. Native and Wasm adapters consume
the same envelope fixtures. These are the same ABI for the probe and final
adapter; the initial Caltrain probe exercises a subset, not a throwaway ABI.

Do not pass Rust `String`, `Vec`, trait objects, references, unwinding panics,
or allocator ownership between independently loaded implementations. Any
opaque module handle is destroyed by its owning version before retirement.
Buffers are copied into host ownership before their producing module can go.
Time and randomness remain explicit inputs; each session owns its logic state.

Durable state belongs to the host's Store and runner slots. Module-local
caches may be discarded. Existing Markdown and LLP sources return native
worker closures and access native files; these are not automatically portable
to Wasm. Keep those operations in host adapters and pass values/request
tokens across the boundary. Until adapted, those sources remain binary-bound.
An old closure or continuation cannot silently resume in a new implementation.

Native code is trusted app code, not sandboxed Wasm. Candidate validation
can detect interface/answer errors but cannot contain an arbitrary native
crash, infinite loop, or direct OS side effect. This limitation applies to
claims about failed-candidate recovery. Native module constructors must do
no work; external effects go through host services, after acceptance.
Compile native module entry points with a C ABI and `panic=abort`; an abort
is process-fatal, not a recoverable validation error.

## 4. Replacement and retirement

Use the existing complete development artifact, prepare/commit, and
restart-with-carry mechanism from LLP 1027 D5 and LLP 1031:

1. Capture build inputs. Produce affected modules and any changed paired
   plan/assets in private output. Publish only a complete compatible set
   for each target; clients never observe half of a dependency update.
2. Verify artifact bytes, target, ABI, app identity, and admitted grants.
   Prepare the candidate for every session in that host process. Validation
   withholds effectful host capabilities; a refusal preserves all sessions.
3. Finish the active synchronous call before committing. Carry compatible
   slots, Store, kept-answer persistence, and clock. Re-ask resources whose
   logic changed; initially invalidate all answers from a replaced module.
   Pending reads restart or cancel; stale replies cannot enter the new
   session. Do not replay mutations or external writes as part of reload.
4. Commit the prepared session set. New sessions use the accepted module.
   Hosts sharing a URL may commit at different times; no distributed
   all-devices transaction is promised.
5. Retire the old implementation only after its calls, buffers, handles,
   destructors, callbacks, and worker references are gone.

Preparation uses a disposable Store snapshot. Its writes and requests never
escape to live services. An answer that depends on discarded validation
writes cannot seed a committed candidate as if those writes occurred.
Recompute it in the committed context, applying legitimate writes once.
Test this explicitly with a Store-writing `parse`, not just pure queries.
Qualify request tickets by the owning session/executor instance; a numeric
ticket reused after reload must not admit an old reply. If an external write
is already in flight, hold replacement until its existing owner settles it;
do not cancel it and pretend the external effect was undone, or issue it again.

Every native artifact gets a unique path and loader identity; never overwrite
a mapped file or expect another `dlopen` of the same path to select new code.
Changing dispatch does not itself make `dlclose` safe. Prohibit module-owned
background threads and escaping callbacks in the first implementation. Test
TLS/destructor and symbol-resolution behavior on each supported loader.

V1 does **not** rely on `dlclose` reclamation: destroy quiescent per-session
instances, but pin each native library handle until host exit. This is a
bounded development limitation, not an invisible leak. Reject a load before
it exceeds **64 distinct native load attempts or 128 MiB of cumulative native
artifact bytes per process**, whichever comes first. Charge a candidate before
`dlopen`, including one later refused; reuse the same mapped artifact across
sessions but create independent instances. Keep the active app usable and
report `Rust reload limit reached; restart the development host` in existing
`state`/`logs`. Never silently restart or discard carried user state.

The byte counter is an admission budget, not a claim about resident memory;
measure actual RSS, mappings, and retained instance allocations in the probe.
Delete superseded never-mapped output once no build/client references it.
Prohibit module-owned threads and module-authored TLS destructors/escaping
function pointers; inspect dependency/runtime TLS behavior as well. Enabling
early unloading later requires a platform-specific lifetime and reclamation
proof; a successful `dlclose` alone is insufficient. Adjusting the provisional
limits needs the probe's measured growth and restart-frequency evidence.

Native artifacts and precompiled Wasmtime artifacts may execute arbitrary
code. A digest or app ID is not producer authentication. Reuse an authenticated
or explicitly trusted local development producer relationship; a LAN URL
alone does not establish it. The transport/trust mechanism must be specified
before network-fed native loading lands. Release discovery never enables
this development capability implicitly.

## 5. Native until edited

Record the source/build-input identity of each embedded module and the
identity of its replacement. Include dependencies, build scripts, relevant
configuration, and target-sensitive inputs; Wasm output equality alone
cannot prove native code is unchanged (parent D4's correction).

Reuse the existing build-receipt input graph. Hash a versioned canonical
tuple of logical module identity, complete declared dependency inputs and
lockfile, relevant build-script inputs/environment, compiler and linker
toolchain identity, target, ABI/plan-format identities, and effective profile
flags. Normalize captured workspace paths to logical roots; undeclared or
unresolved inputs refuse reuse rather than falling back to output equality.
Keep semantic module identity separate from target-artifact identity. An
edit back to old source with different build flags is not proof that the
embedded implementation matches. V1 may conservatively stay on a replacement
until a host rebuild instead of optimizing the revert-to-embedded case.

Unchanged modules keep using the embedded native implementation. A changed
module switches wholly to its replacement executor. Removed providers are
removed, not answered by falling back to stale embedded code. A full native
rebuild establishes a new baseline. Returning to the embedded implementation
is permitted only after validating the matching inputs and compatible state.

Expose module identity and executor (`embedded-native`, `loaded-native`,
`browser-wasm`, `pulley`) through existing `state`/`logs`. Do not claim that
only `board` is interpreted if `board` and `stations` share one artifact.

## 6. Speed: measurements and targets

The September 8 session measured a scratch copy of today's Caltrain data
crate behind LLP 1026 §11's `query`-only Wasm wrapper. Each sample changed
the returned San Francisco station name, ran Cargo, and included compiler
process startup and linking. Five warm edits followed each profile's first
build. Only the data crate and wrapper rebuilt on warm edits.

| Profile | Five warm samples, ms | Median | First build | Wasm bytes |
|---|---|---:|---:|---:|
| Incremental, opt 0, debug 0 | 444, 455, 668, 541, 260 | 455 ms | 20.7 s | 256,065 |
| Incremental, opt 1, debug 0 | 398, 391, 360, 463, 417 | 398 ms | 16.9 s | 146,774 |
| Web: opt z, fat LTO, one codegen unit | 885, 861, 897, 933, 871 | 885 ms | 12.2 s | 78,980 |

Method: rustc 1.97.0; separate temporary Cargo workspace and cache, repository
runner/plan/Taffy dependencies, `EXACT_UPDATE_TRUST=development`,
`cargo build --offline --target wasm32-unknown-unknown --profile <profile>`.
The first two profiles used `panic=abort`; web copied the repository's size
settings. `wasm-opt` was not run. Node instantiated each importless artifact
and verified the changed answer; one opt-1 sample compiled/instantiated in
0.29 ms. These are small compile/execution probes, not a browser paint metric,
a native library reload, the full answer/parse ABI, or a phone measurement.

Use an incremental development profile with light optimization, no fat LTO,
and no `wasm-opt` on saves; preserve release optimization separately.
[Cargo's profile controls](https://doc.rust-lang.org/cargo/reference/profiles.html)
support these choices. Build only affected artifacts for connected targets;
native targets require separate builds. Share the Wasm build between web and
Pulley compilation. Existing receipt/dependency logic owns invalidation.

Aim for **0.5–1 second save-to-visible for small warm Rust edits**, with
**under one second p50** as the initial measured objective. This includes
watching, compilation, pairing/bake, fetch, validation, carry, and presentation.
Report p50/p95 over at least 20 real edits per surface and include the first
edit after readiness. Report cold setup separately. Keep timestamps for each
phase; a DOM update or next-frame callback is not a compositor measurement.
The repository's 100 ms restart/request-to-present budget remains separate
from source compilation and is not relaxed by this objective.

Pulley documentation advises roughly 10× native computation time. LLP 1028
measured 13× on Fibonacci on a Mac, not on an iPhone. A 10 µs calculation
becoming 100 µs is often harmless; a 5 ms calculation becoming 50 ms can
block interaction. Host layout/rendering and host-side I/O stay native.
LLP 1026's ~100 µs Caltrain `board` result was **wasmi**, not Pulley;
LLP 1032's much slower results were **JavaScript interpreted inside Wasm**,
not Rust. Neither establishes this design's phone latency.

## 7. Implementation order and proof

Implementation owner and dates remain unassigned; this is an author-requested
RFC. Before implementation, assign the first slice and record its date here.

1. **Probe the two risks.** Repeated native Caltrain library replacement on
   macOS, then the simulator: execution, retirement, memory growth, and signing.
   Exercise 50 replacements, shared libraries with separate session instances,
   rejected candidates, and an intentional crossing of each retention limit.
   Record phase times and RSS/mappings after instance destruction; do not
   require physical unloading for the first bounded implementation.
   On a physical iPhone, run the real Rust data cases under Pulley and native
   Rust, measuring answers, latency, loading, and UI responsiveness. Use wasmi
   as a comparison only if Pulley misses the workload budget.
2. **One app, one replaceable module.** Implement the shared interface and
   ownership rules, browser Wasm replacement, macOS native replacement, and
   physical-iOS Pulley. Simulator native or declared Pulley fallback follows
   the probe. Start native and demonstrate the executor changing after an edit.
3. **Complete the development loop.** Extend existing build/dev/metrics/agent
   entry points for paired outputs, input identity, latest-edit wins, and
   all-session acceptance. Drive edits through web, macOS, simulator, and
   phone; then sweep Linux's native loader. Do not add another check or server.
4. **Split only when needed.** A real app with two independent Rust modules
   proves that an edit rebuilds/replaces one while the other stays native.
   A shared dependency edit proves both update as a compatible set.

Verification includes changed answers with carried user input and clock;
type/ABI/grant refusal; an invalid carried-state candidate preserving all
sessions; rapid superseding edits; pending-read cancellation; no mutation
replay; adding/removing a provider; and repeated replacement memory behavior.
For native candidates, interface/grant/state refusals preserve sessions;
crashes, aborts, or hangs during preparation do not carry that guarantee.
Malformed or looping Wasm must fail within executor budgets. Run the five existing checks for implementation,
and add runtime cases to existing suites/smokes, not new blocking checks.

## 8. Scope, trade, and open details

Proposed take: prioritize Rust development replacement over the parent's
production Rust Level B delivery and automatic per-source digest analysis.
GPU/surface code replacement and Android implementation remain deferred.
This unblocks the requested edit loop without taking on release code-push
policy or automatic migration of arbitrary Rust objects.

On acceptance, annotate LLP 1029 D2–D5/§7 and LLP 1027 §8's executor trade
with this development scope. Clarify `rules/NOT-DOING.md`'s reload paragraph:
complete logic replacement uses restart with carry, with module identity for
cache invalidation; no live object graph or function patch format is added.
Production scope and the parent's mixed-app scaffold need their own decisions.

Open before the relevant slice lands: simulator native-loading behavior;
measured suitability of native retention limits; the trusted-producer transport; the exact encoded
interface and module declaration shape; and measured phone workload budgets.
The working set replaces the parent link with this child while development
reload is active; the parent remains available through Related.
