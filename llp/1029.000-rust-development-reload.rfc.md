## Summary

Rust business logic can be replaced in a running app in development and
production by default. Native hosts start with linked Rust; changed logic
uses a native shared library on macOS/Linux or a Wasm interpreter on iOS.
The browser executes Wasm itself. The host process stays open and the
existing restart-with-carry path retains compatible application state.

Charlie expanded the September 8–9 development proposal on September 13:
include the iOS interpreter by default, permit an easy opt-out globally,
per environment and per platform, and implement production delivery too.
This revision records that request; Draft does not imply author acceptance
of the parent RFC. Implementation belongs to Codex starting September 13.
The September 9 [Grok](reviews/1029.000-rust-development-reload.grok.md) and
[Muse](reviews/1029.000-rust-development-reload.meta.md) reviews cover the
older development-only revision, not these production changes.

## 1. The experience and the boundary

Starting `node host/web/dev.mjs` opts into a watcher. Within that session,
save-triggered rebuilds are the default for both Rust and TypeScript.
Rust developers reasonably expect a deliberate `cargo build` outside a
watch session; inside an explicitly started development server, automatic
rebuilds make the useful edit loop consistent across both languages.
Agents often benefit from manual rebuilds after a coherent multi-file edit.
Make the trigger a choice, separate from whether the binary can replace Rust:

```json
{
  "dev": {
    "rebuild": { "rust": "manual", "typescript": "save" }
  }
}
```

Each value is `save` or `manual`; omitted values mean `save`. Run
`node scripts/rust.mjs caltrain` after the initial app web bake to build the
independent module variants;
the dev watcher consumes the completed immutable output generation. In the
dev server’s terminal, `r` + Enter rebuilds Rust and `t` + Enter rebuilds
TypeScript. The one-shot build remains an explicit action. No editor or agent detection changes the
policy. A compile failure preserves the current running app; publishing a
complete candidate, not saving a half-written file, is the replacement event.
Superseded builds must not publish over newer successful output.

The host, runner, kernel, renderer, input and host services remain resident.
Reload reconstructs session runners/views through restart with carry; stable
view object identity, focus and scroll position are not promised. Durable
state lives in runner slots and the host Store; arbitrary Rust heaps do not
migrate, and mutations are never replayed to reconstruct state.

The unit of replacement is an explicitly declared `cdylib` Cargo package
exporting the logic ABI. A Rust `mod` or `.rs` file is not a loadable unit.
The first declaration selects one portable wrapper package (Caltrain’s
`apps/caltrain/logic`, which depends on its ordinary `data` crate):

```json
{ "rust": { "module": { "package": "caltrain-logic" } } }
```

Start with one cohesive module. Keep domain logic and data transformations
in small ordinary Cargo crates, with filesystem/network/native worker work
in host adapters. Keep the loadable wrapper thin. Cargo can reuse unchanged
helper crates and incremental compiler work, although a change to a helper
still requires relinking its dependent loadable module. An unrelated domain
should become a separate artifact only when the app composition can route
its providers independently. Multiple Rust modules in one data `cdylib`
still update together; this implementation does not infer separate units or
provide a multi-module manifest registry. That distinction keeps build-time
and update-blast-radius promises honest.

Caltrain's thin logic wrapper over its pure data crate is the first consumer. A crate that owns native
files, threads, escaping callbacks or worker closures is not automatically
portable. Adapt these operations to host services or keep the source linked
into the host. A host/ABI/capability change requires a new native binary.

Update Lab is the mixed-language consumer added September 14. Its previous
`Lab<TypeScript>` composition kept the Rust probe linked into each client;
only the web's full-program rebuild observed a Rust save. The lab now declares
`update-lab-logic` and routes `rustProbe` through the configured Rust executor.
The host admits one complete pair of TypeScript and Rust artifacts against
one plan, validates both before committing, and carries compatible state once.
This validates bytes, identity, grants and initialization; it does not prove
that every future user-triggered answer will succeed.
A TypeScript-only candidate cannot silently reset an enabled Rust module to
its embedded baseline. With Rust replacement disabled, TypeScript updates
remain available. Contract and TypeScript bakes reuse the accepted Rust bytes,
rebinding their receipt to the common plan without recompiling Rust.

This is one fixed app composition, not a multi-module registry or scheduler.
Both probe calls are mutations invoked after first pixel, so each producer can
bake the same initial plan without executing the other language. A mixed app
that needs both languages to compute its baked first frame needs a composed
producer; this lab does not establish that capability. Previously installed
lab binaries require one rebuild to acquire the composition.

## 2. Executors and user control

`app.json` has one `rust` policy. It accepts `true`/`false`, a mode string,
or an object. Modes are `auto`, `native`, `tiered`, `wasm`, and `off`; `true` means
`auto`, `false` means `off`. Omission means `auto` in dev and prod.

```json
{
  "rust": {
    "mode": "auto",
    "prod": false,
    "module": { "package": "caltrain-logic" },
    "platforms": {
      "ios": { "prod": false },
      "macos": { "prod": "native" },
      "linux": { "mode": "wasm", "dev": "native" }
    }
  }
}
```

Resolve **global → environment → platform → platform environment**. Each
later explicit choice overrides the earlier one; absent choices inherit.
`dev` and `prod` accept a boolean, mode, or `{ "mode": ... }`. Platform
entries additionally accept their own `dev` and `prod`. The module declaration
is global. `{ "rust": false }` disables everywhere; `{ "rust": { "prod":
false } }` keeps development enabled; `{ "rust": { "platforms": { "ios":
false } } }` disables iOS only. These controls are independent of deployment
cadence and TypeScript updates.

| Platform | Default dev replacement | Default prod replacement |
|---|---|---|
| Web | Browser Wasm | Browser Wasm |
| macOS | Native `.dylib` | Native `.dylib`, subject to distribution/signing requirements |
| Linux | Native shared library | Native shared library |
| iOS device and simulator | Interpreted Wasm (`wasmi`) | Interpreted Wasm (`wasmi`) |
| Android, future host | Native `.so` | Interpreted Wasm |
| Windows, future host | Native `.dll` | Native `.dll` |

Explicit `native` is refused on iOS and web. `wasm` on web uses the browser.
Desktop users can explicitly choose Wasm, including only for production.
Android and Windows policy names reserve the intended defaults; their hosts
remain outside v1 and are not claimed as implemented or tested.

The effective policy is resolved at bake time, with development selected by
`EXACT_UPDATE_TRUST=development` and production otherwise. `off` selects an
entry with no replacement loader or interpreter reachable from the binary;
it is not a runtime boolean guarding already-linked interpreter code.
Optional executors are separate adapters/artifacts above core crates, not
Cargo features on the runner or hosts. Baked compatibility inputs include
`rustMode`, `rustAbi`, `rustTarget` and `rustModule`; the executor list names
`native-dylib`, `wasmi` or `browser-wasm` as selected. Disabled Rust has no ABI
or target capability. An installed binary cannot enable a missing executor by downloading
an app-manifest change. Re-enabling it requires rebuilding the native binary.

The iOS interpreter is `wasmi`, replacing this document's earlier Pulley
proposal. It consumes the same portable Wasm artifact as the browser without
an additional Wasmtime precompilation format or native-code deserialization
path. Validate and prepare Wasm only after first pixel; no app code, JIT or
native machine-code generation enters the boot path. This choice is an
implementation trade, not a claim of measured phone performance. The older
Pulley measurements below remain historical comparisons.

Platform permission to execute a format and store permission to deliver an
update are separate. Apple's [App Review Guideline 2.5.2](https://developer.apple.com/app-store/review/guidelines/)
restricts downloaded code that changes app features; an interpreter is not a
general exemption. Mac App Store distribution has additional update rules
in 2.4.5. Default capability does not promise every production distribution
can use it; store-bound apps can disable it for production.

Google Play's [Device and Network Abuse policy](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en)
forbids externally downloaded executable `.so` code and describes an
exception for VM/interpreted code with indirect Android API access. This
supports the proposed Android production default, not a guarantee that any
particular Wasm app/update qualifies. Native Android loading may be useful
for development and permitted non-Play distribution.

macOS native loading must satisfy code signing and library validation.
Apple's [library validation entitlement documentation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation)
is the reference for that boundary. Use properly signed libraries for the
host's distribution; development ad-hoc signing does not establish that a
production Hardened Runtime host can load them. The production module
producer requires `EXACT_RUST_SIGN_IDENTITY` for the host's team. Exact bundle signatures
prove the publisher but do not replace platform code signatures. Policy
sources checked 2026-09-13.

## 3. One interface, with ownership made explicit

The implementation is `exact-logic-abi` plus the optional `exact-logic`
adapter. A thin wrapper package exports
`exact_logic_abi::export!(DataType, constructor_expression)`; the constructor
creates fresh per-session state. ABI 1 uses little-endian integers and
`exact-plan`'s bounded Value encoding inside explicit operation envelopes.
The source codec is the field/tag authority, with a 16 MiB limit on each
input/output message and a 32 MiB artifact limit before engine creation.

`wasmi` accepts no imports (including WASI), no start function and no native
machine-code format. It limits memory to 64 MiB, each call to 20 million
fuel units plus 1,000 for each byte the host hands it, recursion to 512,
stack to 1 MiB, and instances/memories/tables to one each. (Amended
2026-10-03, Charlie: a flat 20 million refused Caltrain's 46 KB plan at
activation, which decodes it at about 430 fuel a byte. The module cannot
enlarge its own input, so a runaway loop still stops at the base, and plan
size is bounded only by the 16 MiB message limit.) Native code has the same encoded seam but remains trusted
process code; fuel and memory isolation apply only to the interpreter.
Browser Wasm uses the browser executor and does not acquire wasmi's fuel
guarantees.

Both loaders implement the existing `DataSource` replacement seam. Define a
small versioned C-compatible interface for native libraries and equivalent
exports over Wasm linear memory: identity, grants, activation, answer/parse,
and destruction, with bounded encoded arguments/results and explicit buffer
ownership. LLP 1026 D3 is the starting point; it must be reconciled with the
current `runner/src/runner/source.rs`, not copied as an already complete ABI.

The **host adapter**, not the loaded library, implements the Rust trait.
`replacement() -> Self` constructs another adapter in the host; no Rust `Self`
crosses the ABI. The method-by-method map for the first implementation is:

| `DataSource` method | Host adapter | Encoded module operation |
|---|---|---|
| `replacement` | Validate receipt, select loader, own candidate lifetime | Create an isolated instance; no effects |
| `app_id`, `grants` | Cache and enforce the admitted values | Read metadata once; compare with receipt |
| `revision` | Own the module identity in §5 | No module-selected revision authority |
| `bind` | Validate paired plan and compatibility | Supply existing encoded plan bytes; module owns its decoded copy |
| `ready` | Track deferred/active state | No separate readiness authority in the first synchronous adapter |
| `configure_storage` | Retain host paths/capabilities; open nothing before first pixel | No paths or filesystem handles cross |
| `activate`, `activate_for_validation` | Select committed or disposable mode | Activate fresh instance with the selected mode, without direct I/O |
| `query` | Supply an empty Store context, require an immediate value | Same dispatcher as `answer` |
| `answer` | Encode granted Store snapshot, source and arguments | Return `Answer`/error, ordered Store writes, and Store-read observations |
| `parse` | Encode the same context plus `Outcome` | Return the same result envelope as `answer` |
| `continuation` | Own work and ticket lifetime | V1 refuses module-local continuation requests; no Rust closure crosses |
| Adapter drop | Release instance resources while its library is still mapped | Destroy the instance using its own implementation |

Use `exact-plan`'s canonical `Value` encoding and format identity. Additional
envelopes encode `Request`, `Outcome`, `DataError`, and Store snapshot/writes
as explicit tagged fields, never Rust object layouts. Include observations
of Store reads, including absent keys, so resource invalidation and kept
answers retain their meaning. Never expose runner-private `exact.kept.*`
entries to module code. The host rechecks grants and applies returned writes
only through its transaction. An invalid result applies no partial writes.

Specify the field order, integer widths, tag values, byte/depth bounds, and
allocator/free signatures in the shared ABI declaration before loader code.
Inputs are borrowed only for a call; outputs are copied before the next call
and freed by their producing allocator. Native and Wasm adapters consume
the same envelope fixtures. These are the same ABI for the probe and final
adapter; the initial Caltrain probe exercises a subset, not a throwaway ABI.

Do not pass Rust `String`, `Vec`, trait objects, references, unwinding panics,
or allocator ownership between independently loaded implementations. Any
opaque module handle is destroyed by its owning version before retirement.
Buffers are copied into host ownership before their producing module can go.
Time and randomness remain explicit inputs; each session owns its logic state.

Durable state belongs to the host's Store and runner slots. Module-local
caches may be discarded. Existing Markdown and LLP sources return native
worker closures and access native files; these are not automatically portable
to Wasm. Keep those operations in host adapters and pass values/request
tokens across the boundary. Until adapted, those sources remain binary-bound.
An old closure or continuation cannot silently resume in a new implementation.

Native code is trusted app code, not sandboxed Wasm. Candidate validation
can detect interface/answer errors but cannot contain an arbitrary native
crash, infinite loop, or direct OS side effect. This limitation applies to
claims about failed-candidate recovery. Native module constructors must do
no work; external effects go through host services, after acceptance.
Compile native module entry points with a C ABI and `panic=abort`; an abort
is process-fatal, not a recoverable validation error.

## 4. Replacement and retirement

Use the existing complete development artifact, prepare/commit, and
restart-with-carry mechanism from LLP 1027 D5 and LLP 1031:

1. Capture build inputs. Produce affected modules and any changed paired
   plan/assets in private output. Publish only a complete compatible set
   for each target; clients never observe half of a dependency update.
2. Verify artifact bytes, target, ABI, app identity, and admitted grants.
   Prepare the candidate for every session in that host process. Validation
   withholds effectful host capabilities; a refusal preserves all sessions.
3. Finish the active synchronous call before committing. Carry compatible
   slots, Store, kept-answer persistence, and clock. Re-ask resources whose
   logic changed; initially invalidate all answers from a replaced module.
   Pending reads restart or cancel; stale replies cannot enter the new
   session. Do not replay mutations or external writes as part of reload.
4. Commit the prepared session set. New sessions use the accepted module.
   Hosts sharing a URL may commit at different times; no distributed
   all-devices transaction is promised.
5. Retire the old implementation only after its calls, buffers, handles,
   destructors, callbacks, and worker references are gone.

Preparation uses a disposable Store snapshot. Its writes and requests never
escape to live services. An answer that depends on discarded validation
writes cannot seed a committed candidate as if those writes occurred.
Recompute it in the committed context, applying legitimate writes once.
Test this explicitly with a Store-writing `parse`, not just pure queries.
Qualify request tickets by the owning session/executor instance; a numeric
ticket reused after reload must not admit an old reply. The current hosts
conservatively refuse module replacement while any data request is in flight.
Retry after its existing owner settles it; production pollers retain the
unaccepted candidate for retry. A development refusal is visible and can be
retried with an explicit rebuild. Never cancel an external write and pretend
its effect was undone, or issue it again.

Every native artifact gets a unique path and loader identity; never overwrite
a mapped file or expect another `dlopen` of the same path to select new code.
Changing dispatch does not itself make `dlclose` safe. Prohibit module-owned
background threads and escaping callbacks in the first implementation. Test
TLS/destructor and symbol-resolution behavior on each supported loader.

The host's `DataSource::preload` starts native image preparation after first
pixel and returns pending without waiting for the OS loader. One worker per
process writes and maps images; a digest-keyed result shares each mapping
across sessions. No cache mutex spans `dlopen`. Queued images consume the same
retention budget as completed and refused images. Constructors and ABI export
inspection must not perform app work. Instance creation, disposable validation,
state carry and the final swap stay on the host's owning thread.

While preparation is pending, keep the current generation interactive. The
Apple URL connection retains the verified payload and checks readiness every
50 ms; a newer resolution supersedes its retry. Production activation and
local-file development retry too. Take the state snapshot when preparation
finishes, so input received during loading is carried. Initial activation
uses the same pending path after first pixel and reports boot success only
once its executor is ready.

V1 does **not** rely on `dlclose` reclamation: destroy quiescent per-session
instances, but pin each native library handle until host exit. This is a
bounded loader limitation, not an invisible leak. Reject a load before
it exceeds **64 distinct native load attempts or 128 MiB of cumulative native
artifact bytes per process**, whichever comes first. Charge a candidate before
`dlopen`, including one later refused; reuse the same mapped artifact across
sessions but create independent instances. Keep the active app usable and
report `Rust reload limit reached; restart the host` in existing
`state`/`logs`. Never silently restart or discard carried user state.

The byte counter is an admission budget, not a claim about resident memory;
measure actual RSS, mappings, and retained instance allocations in the probe.
Delete superseded never-mapped output once no build/client references it.
Prohibit module-owned threads and module-authored TLS destructors/escaping
function pointers; inspect dependency/runtime TLS behavior as well. Enabling
early unloading later requires a platform-specific lifetime and reclamation
proof; a successful `dlclose` alone is insufficient. Adjusting the provisional
limits needs the probe's measured growth and restart-frequency evidence.

Native artifacts may execute arbitrary code. A digest or app ID is not
producer authentication. Production artifacts use the existing authenticated
signed bundle and baked grant/target/ABI boundary. Development uses the
explicitly selected trusted producer relationship; a LAN URL alone does not
establish it. A disabled baked executor refuses replacement even when the
producer is trusted. No new update service or discovery protocol is added.

### 4.1 Two-phase evaluation and the bounded implementation

Charlie requested evaluation and implementation if practical on September 14.
**Verdict:** practical for portable modules with no essential executor-private
state; not a transparent mechanism for arbitrary Rust heaps. The measured
103.9-second native load is enough to justify an explicit mode, even before
optimizing the roughly three-second producer path. It does not establish the
cause of every Mac's delays or justify changing all production defaults.

`rust: { platforms: { macos: { dev: "tiered" } } }` selects the two-phase
executor; the usual environment/platform overrides apply. `auto` keeps its
existing defaults. Explicit `native` links no Wasm interpreter through this
constructor; `wasm` never promotes; `off` retains the embedded source. The mode
is available where native replacement is available and is refused for iOS/web.
Update Lab opts into macOS development and leaves production policy unchanged.

Eligibility is explicit at the exported module seam:
`exact_logic_abi::export!(Data, constructor, stateless)`. Both variants must
export the contract. Observable state must be in host inputs, Contract state,
Store or host-owned storage. Constructors, bind, activation and destruction
must have no external effects; private caches must be safely reconstructible;
`parse` must use its explicit arguments/outcome rather than private pending
state. An unmarked Wasm module is refused before activation. This is an author
contract, not a static proof; marking a stateful implementation is incorrect.
No generic checkpoint hooks or raw Wasm-memory copying are introduced.

The producer packages the Wasm and native bytes in one bounded `.bin` container:
8-byte `EXLT`/version header, little-endian u32 Wasm length, then Wasm and native.
Its ordinary receipt binds the complete digest, exact native target, plan, ABI,
app and grants. Development publishes a `tiered` variant beside native/Wasm;
production packages that complete container as its existing authenticated Rust
asset pair and requires a tiered-capable cohort. No unattested companion or
second deployment is fetched. Both variants still build before publication;
early Wasm publication before native compilation is a separate optimization.
A native compile failure therefore still prevents this producer's publication.

After first pixel, validate and activate the candidate using Wasm. The single
normal generation commit carries host state and restarts the changed logic
once. Native mapping proceeds on the existing loader worker. Tiered sessions
admit a new image only while that worker is idle; otherwise only a still-live
session retries at a later call. This avoids an obsolete-image FIFO during
rapid saves. An already-entered OS load cannot be cancelled. Mappings retain
the same 64-attempt/128 MiB limits; exhaustion stops promotion, not Wasm use.

Between subsequent Rust calls, a ready native image gets a fresh instance,
matching app/grants metadata, the same plan binding and effect-free local
activation. Change the Rust executor pointer and release the Wasm instance.
Do not construct another host/runner, re-execute business calls, restart JS,
invalidate settled answers, change the logical revision, or emit another app
update event. Promotion can occur before `parse` because the eligibility
contract makes the host-owned request and explicit arguments sufficient; the
original ticket and external effect are neither cancelled nor reissued. A
newer generation owns a different executor object, so an older result cannot
promote into it. Recoverable native load/metadata/activation errors log once and
leave the current Wasm working. Native crashes remain process-fatal, as in §4.

Costs are the linked interpreter, temporary Wasm execution overhead, both
artifact variants and bounded retained native mappings. This recovers native
call speed when loading succeeds; it does not promise eventual promotion if
loading fails or the retention limit is reached. Update Lab exposes an executed
Wasm/Native label to distinguish readiness from publication. Larger workloads
still need measured interpreter load/call and owner-thread budgets. Stateless
promotion does not by itself fix the earlier mixed-generation JS-ready race.

Implementation: `logic/src/tiered.rs`, the native worker's idle admission,
producer/policy/container readers, and Update Lab's opt-in. The five focused
runtime tests passed, including a real blocked library with working Wasm calls,
no replayed Store writes on promotion, superseded candidates never admitted,
and refusal/identity mismatch retaining Wasm. Six producer tests and fourteen
Contract policy/receipt tests passed, including full-container tampering,
exact native target requirements and the existing signed-roster checks.
Focused Clippy, caps and boot passed. Producer, browser and Swift generation
digests all bind the tiered target, as does the artifact receipt.

The live Mac proof passed (`target/update-lab-tiered-result.json`). Two distinct
saves first answered in Wasm at 8.553 s and 4.477 s; the second promoted at
6.596 s after its save. Counter, note, TypeScript result and Contract stayed
intact, and promotion kept the exact logical revision. Candidate preparation
was 25 ms for each edit. The normal app separately activated the initial
candidate with 36 ms preparation while `dlopen` took 54.341 s, then promoted
on its probe clock (`target/update-lab-tiered-macos.log`). The agent proof uses
explicit clock advancement; its largest multi-operation observation was 259 ms.
These are individual runs under concurrent build load, not latency percentiles.
The deliberately blocked fixture, rather than these fast later native loads,
proves that dropped candidates never queue behind an unfinished load.

Rebuilt macOS, simulator and physical iPhone clients. A separate save/restore
reached web, simulator and iPhone with carried state at 3.822/3.908/6.956 s
(`target/update-lab-tiered-cross-host-result.json`); phone observations include
several agent round trips. The earlier JS-engine-not-loaded diagnostic did not
recur in these native traces. Source was restored to Rust v8 after both probes.
Cold build-helper launches and shared Cargo locks still made initial builds
take minutes; tiering removes neither producer work nor executable cold starts.
Full workspace checks run asynchronously; no production deployment was made.

## 5. Native baseline and replacement identity

A normal installed host boots its linked implementation. A newer signed Rust
bundle replaces the whole data module through the selected executor. The
browser likewise boots its resident Wasm and follows newer paired modules.

The development watcher publishes an initial candidate when it starts. A
connected native app conservatively accepts that candidate after first pixel,
even if its source happens to match the embedded implementation. On iOS this
means interpreted logic for the connected dev session. An ordinary launch
without a development URL stays native until it receives a Rust update.

The producer captures and rechecks the complete declared Cargo dependency
inputs and app Contract files; moving inputs never publish a pair. Receipts
bind the exact plan, target, ABI, grants and module bytes. They do not claim
semantic equivalence between a Wasm artifact and linked native code. Reusing
the embedded implementation after comparing normalized, target-sensitive
source/build graphs is a future optimization; output equality alone is not
sufficient evidence. A host rebuild establishes a fresh native baseline.
Removed providers never fall back to stale embedded code.

Existing `state.logic` reports the actual data-source revision, active Rust
executor (`native`, `wasm`, or `browser`) and readiness. A null Rust executor
means the embedded source is still selected. Do not claim that only `board`
is interpreted if `board` and `stations` share one artifact.

## 6. Speed: measurements and targets

The September 8 session measured a scratch copy of today's Caltrain data
crate behind LLP 1026 §11's `query`-only Wasm wrapper. Each sample changed
the returned San Francisco station name, ran Cargo, and included compiler
process startup and linking. Five warm edits followed each profile's first
build. Only the data crate and wrapper rebuilt on warm edits.

| Profile | Five warm samples, ms | Median | First build | Wasm bytes |
|---|---|---:|---:|---:|
| Incremental, opt 0, debug 0 | 444, 455, 668, 541, 260 | 455 ms | 20.7 s | 256,065 |
| Incremental, opt 1, debug 0 | 398, 391, 360, 463, 417 | 398 ms | 16.9 s | 146,774 |
| Web: opt z, fat LTO, one codegen unit | 885, 861, 897, 933, 871 | 885 ms | 12.2 s | 78,980 |

Method: rustc 1.97.0; separate temporary Cargo workspace and cache, repository
runner/plan/Taffy dependencies, `EXACT_UPDATE_TRUST=development`,
`cargo build --offline --target wasm32-unknown-unknown --profile <profile>`.
The first two profiles used `panic=abort`; web copied the repository's size
settings. `wasm-opt` was not run. Node instantiated each importless artifact
and verified the changed answer; one opt-1 sample compiled/instantiated in
0.29 ms. These are small compile/execution probes, not a browser paint metric,
a native library reload, the full answer/parse ABI, or a phone measurement.

Use an incremental development profile with light optimization, no fat LTO,
and no `wasm-opt` on saves; preserve release optimization separately.
[Cargo's profile controls](https://doc.rust-lang.org/cargo/reference/profiles.html)
support these choices. Build only affected artifacts for connected targets;
native targets require separate builds. Share the Wasm build between web and
interpreted native targets. Existing receipt/dependency logic owns invalidation.

The development producer keeps `exact-logic-bake --serve` resident across
requests. Each request gets a fresh disposable Wasm instance and private
input/output paths; the compiled Wasm is copied before baking so another
producer cannot replace Cargo's output underneath it. Cargo checks the helper
before each request; a changed executable starts a new helper. A refused bake
does not poison the next request, and producer shutdown terminates its helper.
This avoids repeated executable launches and their security-scan delay. It
does not promise to remove the OS's first-launch or new-library verification.

Aim for **0.5–1 second save-to-visible for small warm Rust edits**, with
**under one second p50** as the initial measured objective. This includes
watching, compilation, pairing/bake, fetch, validation, carry, and presentation.
Report p50/p95 over at least 20 real edits per surface and include the first
edit after readiness. Report cold setup separately. Keep timestamps for each
phase; a DOM update or next-frame callback is not a compositor measurement.
The repository's 100 ms restart/request-to-present budget remains separate
from source compilation and is not relaxed by this objective.

Pulley documentation advises roughly 10× native computation time. LLP 1028
measured 13× on Fibonacci on a Mac, not on an iPhone. A 10 µs calculation
becoming 100 µs is often harmless; a 5 ms calculation becoming 50 ms can
block interaction. Host layout/rendering and host-side I/O stay native.
LLP 1026's ~100 µs Caltrain `board` result was **wasmi**, not Pulley;
LLP 1032's much slower results were **JavaScript interpreted inside Wasm**,
not Rust. Neither establishes this design's phone latency.

## 8. Scope and trade

This request takes Rust replacement in development **and production** ahead
of the parent's general mixed-language scaffolder, per-source digest
analysis and multi-module registry. It unblocks updates to declared portable
Rust business logic with control over inclusion cost. Android/Windows hosts,
GPU/surface replacement, arbitrary native object migration, automatic
function-level splitting and general native-view modules remain deferred.

The update remains complete module replacement plus restart with carry;
optional stateless promotion changes only the executor within that generation.
There is no function patch format, live Rust object graph migration, staged
revision surface or new agent operation. The existing single update store
and producer own delivery. The parent remains available through Related;
this child owns the concrete Rust replacement work.
