# LLP 1027.000.000: The date as an explicit input

**Type:** RFC
**Status:** Draft
**Systems:** Runner (a reserved source, `exactTime`, answered from a host fact), Plan (`runner_owned_source` gains the name), Contract compiler (the bake's shape check and the TypeScript declaration skip it as they skip `exactViewport`), Web, Apple and Linux hosts (the fact at boot and on a system clock or zone change), Agent API (the driver's substitute epoch), TypeScript bake (the build-time diagnostic question, D5)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-24
**Related:** LLP 1027.000 D1 (app-owned clock slots), D2 ("adds no wall-clock provider"), D3 (the runtime refusal is the boundary), D4 (bake and caching), "Alternative" (waits for a named consumer); LLP 1039 D1/D2 (`exactViewport`, the reserved-source pattern this copies) and LLP 1030 D7 (`exactDelivery`, its original); LLP 1012 §2 (the agent clock); the Crew port report, 2026-09-24 (Seth), items D12 and D13

## Summary

Contract's `now()` is elapsed milliseconds since launch, and a TypeScript
data source may not read the machine's clock. So an app that shows "synced
4:00 PM" or "Idle · 3h" has nowhere to get the date. This RFC adds the
date as a **fact the host supplies**, not a clock the source reads: a
reserved source `exactTime()` whose fields are the Unix time at runner
clock zero (`epochAtZero`) and the IANA zone (`timeZone`). The current date
is `time.epochAtZero + now()`. It follows the `exactViewport` pattern
exactly: the host sets it before the first settlement and again when the
system clock or zone changes, and a resource that reads it re-asks only
then. Under the agent driver the fact is a substitute set at launch, so a
drive is deterministic and relative times render against a real-looking
date instead of 1970.

## Motivation

The Crew port report (2026-09-24):

- **D12.** "`Date.now()` and `new Date()` with no argument refuse inside
  TS. Every relative time ('Idle · 3h') needs `now()` threaded from
  Contract through every resource's arguments, which also re-asks those
  resources on each tick." And the refusal is "invisible until runtime".
- **D13.** "In agent mode `now()` starts at 0 ms, so 'synced 4:00 PM' and
  relative times render against 1970."

Both are consequences of a decision LLP 1027.000 made on purpose and left
open on purpose:

- D2 (`llp/1027.000-explicit-time-and-randomness.rfc.md:66-77`): "This
  proposal adds no wall-clock provider. An app needing a fresh production
  UTC timestamp must obtain it as an explicit host/service input, with its
  test substitute and refresh policy specified when that capability is
  implemented. A fixed epoch in a test must never become the default
  production clock accidentally."
- The "Alternative" (`:127-139`) waits for "a named library or application".
  Crew is that application.

`now()` is elapsed time on every host: `performance.now() - t0` on the web
(`host/web/glue.js:111-115`), milliseconds since `main` on Apple
(`Session.swift:43-45`, `:406`), and 0 at boot under the agent
(`ExactIOS/main.swift:182`). The apps in the repo work around the missing
date three ways: Caltrain hard-codes an instant in `state nowMs`
(`apps/caltrain/app.contract:40`) and ticks it; Weatherlight uses the
server's own "current" time (`apps/weatherlight/app.ts:82`); Messages
counts from a fixed fixture anchor (`apps/messages/app.ts:213-214`). None of
these can say "3h ago" about a server timestamp.

The re-asking in D12 is not inherent. A `now()` read makes whatever reads
it depend on the clock (`runner/src/instance/deps.rs:351-353`), so passing
`now()` into a network resource's arguments does re-ask it on every clock
move. LLP 1027.000 D1 (`:60-64`) already names the alternative, an
app-owned slot a timer updates. Messages does this (`apps/messages/app.contract:464-475`).
But nobody has written down the pattern for an app that needs the date.

## Design

### D1 — One reserved source, `exactTime`, filled by field name

```
shape Time
  epochAtZero: number
  timeZone: string
component Crew
  resource time = exactTime() as shape Time
```

- `epochAtZero` is the Unix time, in milliseconds, at which the runner's
  clock read zero. The date now is `time.epochAtZero + now()`.
- `timeZone` is the system's IANA zone, e.g. `America/Los_Angeles`.
- Fields are filled by name from the declared shape, as `exactViewport`'s
  are (`runner/src/viewport.rs:6-9`), and an unknown field is a bake
  refusal. Arguments are refused.
- `plan/src/lib.rs:564-566` `runner_owned_source` and
  `scripts/app.mjs:113` gain the name. The TypeScript declaration skips it
  (`contract/cli/src/typescript.rs:65`).

*Rejected: a stdlib `date()` beside `now()`.* A function that reads a
changing value would make every reader depend on it every frame, which is
the D12 cost again. A fact that changes only when the host says so costs a
re-ask only then. *Rejected: the runner-backed ambient `Date.now()` of LLP
1027.000's "Alternative".* It needs an epoch anchor anyway, plus dependency
tracking inside the executor. This RFC is that anchor, without the
tracking.

### D2 — The host sets the fact at boot and when it changes; there is no default

Each host computes `epochAtZero` from the same clock that drives `now()`.
On the web that is `Date.now() - (performance.now() - t0)`, taken once at
boot; Apple and Linux do the same against their own `now()` origin. The
host passes it with the viewport to `Runner::boot*`, before the first
settlement. A `set_time(epochAtZero, timeZone)` in the shape of
`set_viewport` (`runner/src/runner/viewport.rs:16`) re-answers every reader
in one commit. Hosts call it on a system clock or zone change:

- Apple: `NSSystemClockDidChange` and `NSSystemTimeZoneDidChange`.
- Linux: at resume.
- The web: never. It has no such event, and a page reload is cheap.

The runner has **no default**. A plan that reads `exactTime` refuses to
boot on a host that did not supply the fact. So no fixed instant can
become the production clock by omission, which is the case LLP 1027.000
D2 guards against. The bake shape-checks against a lint instant, as it does
with `LINT_VIEWPORT` (`runner/src/viewport.rs:21-29`). No value that depends
on `exactTime` is ever compiled into a baked frame or page: a baked date is
build time.

*Rejected: the host sets the current date on every frame.* That turns the
fact back into a clock, with the same re-ask cost.

### D3 — The agent driver supplies a substitute, set at launch

Under `EXACT_AGENT=1` / `?agent=1`, the host reads `epochAtZero` from
`EXACT_AGENT_EPOCH` (or `?epoch=`) and `timeZone` from `EXACT_AGENT_TZ`,
never from the machine. `scripts/agent.mjs` passes them:

- `--epoch <ISO|ms>` and `--time-zone <zone>`, each with a documented
  fixed default (`2026-01-01T00:00:00Z`, `UTC`).
- Screenshots and relative labels are identical across runs and machines.
- `clock +N` still moves elapsed time, so the date moves with it.
- `state` reports both values.

The smoke's `state.clock === 60000` stays true, because `now()` is
unchanged. A production launch never reads `EXACT_AGENT_*`. A test asserts
that a non-agent boot reports the machine's zone and an `epochAtZero`
within a second of the machine's clock.

*As built (2026-09-27):* on web, Apple and Linux, with `--locale` and
`--seed` (LLP 1069.007 D2). The zone variable is `EXACT_AGENT_TIME_ZONE`
(`?timeZone=`), not `EXACT_AGENT_TZ`; hosts take `EXACT_AGENT_EPOCH` and
`?epoch=` as Unix milliseconds (the driver converts an ISO date); the
agent's `utcOffset` is its zone's at the epoch; `state.time` carries both.

*Rejected: start the agent clock at a real epoch.* That contradicts D2's
elapsed-time meaning and breaks every check that reads `clock`. *Rejected:
seed the substitute from the machine's clock.* Screenshots would differ run
to run.

### D4 — How an app uses it without re-asking every tick

Time is kept out of network resources' arguments. A network resource
returns server timestamps. Relative text is computed where the date is:

- **In Contract**, as a derive over `time.epochAtZero + now()`. It is not a
  request. It re-evaluates at the next commit made at a later time (a
  timer's, an input's, a reply's), not when the clock moves by itself: a
  clock move commits nothing (`runner/src/instance/deps.rs`'s clock read;
  the JS target's `now()` the same; conformance's `clock.contract`). A
  derive that must stay current with nothing else happening needs a timer,
  as the slot pattern below has. *Corrected 2026-10-02:* this said "a derive
  re-evaluates on a clock move", which no runner did. It stays corrected by
  design, not left as a gap: on a device the clock moves continuously and
  nothing wakes to re-render until a timer, an input or a reply does. A
  runner that committed on a bare clock move would make an agent drive show
  updates a device never shows (the agent's `clock +N` with no timer due is
  a device left idle that long).
- **Or in a pure TypeScript source** whose arguments are the timestamps and
  a minute slot:

```
state minute = 0
action tick writes minute
  minute = time.epochAtZero + now()
task minutes mount
  every(60000, tick)
resource labels = relativeLabels(crew.sessions, minute) as shape list<Label>
```

`relativeLabels` re-answers once a minute and does no I/O. `crew` does not
depend on the clock at all. This is LLP 1027.000 D1's app-owned slot with
a real origin. It goes into LLP 1027's authoring notes beside the
`grants` and `answer` documentation, which is where D12 says an author
looked.

Formatting in TypeScript stays explicit: `new Intl.DateTimeFormat(locale,
{ timeZone: time.timeZone }).format(epochMs)` is allowed today (1027.000
D3). An omitted timestamp is still refused. Contract-only apps have no
date formatting; that is a separate question (open question 3).

### D5 — The build-time diagnostic (D12's "invisible until runtime")

The runtime refusal stays the boundary (1027.000 D3: "searching source
text for `Date.now` is insufficient"). The question is whether the build
should also say something earlier. The app's TypeScript is checked with
`--lib ES2020,WebWorker` (`js/bake/src/lib.rs:704-710`,
`js/bake/src/resident.rs:153`). A generated `.d.ts` can add overloads to
`DateConstructor` but cannot remove `now(): number`, so the declaration
file alone cannot make `Date.now()` a type error. The options:

1. **A producer-owned lib, generated at build.** Copy the pinned
   TypeScript's `lib.es5.d.ts` into the stage and strip four members:
   `DateConstructor.now`, the zero-argument `new ()` and call signatures,
   and `Math.random`. Then check with that lib. `Date.now()` becomes a
   type error at its line in both the bake and the dev compiler, aliases
   included (`const n = Date.now` has no member to read). The copy is
   generated from the pinned version, never committed. Editors see it only
   if the app's own `tsconfig` points at the stage.
2. **A literal check in the bundler step, as a warning.** It catches the
   spelled forms, misses aliases, and adds noise for the same text in a
   comment or a string.
3. **Nothing.** The bake already refuses reads at module load and in boot
   resources. Anything else refuses on first call, with a message that
   names the remedy (`js/src/prelude.js:23-24`).

**Recommendation: 1.** It is the only option that is a real compile error
at the author's line, and it is not text search. It is new tooling under
`rules/RULES.md` §Agents, so it needs Charlie's approval. If he declines,
3 is honest: the runtime message already says what to do, and D4's
documentation removes most of the reason to reach for `Date.now()`.

## Cost and what it touches

- **Runner:** `runner/src/time.rs`, beside `viewport.rs` (the source name,
  its fields and the substitute); `Runner::boot*` and `set_time`; the bake's
  lint instant.
- **Plan:** the name, at `plan/src/lib.rs:564`. The Contract compiler's
  field check sits beside `bake-viewport-field`.
- **Hosts:** the boot fact and the change notifications. That is
  `host/web/glue.js` near `:111`, the Apple `Session`, and
  `host/linux/src/presenter.rs`.
- **Agent:** two launch flags in `scripts/agent.mjs`, and the `state`
  field.
- **Apps:** Caltrain's hard-coded `state nowMs` could start from
  `time.epochAtZero` instead, but it is a fixture app whose fixed instant
  is deliberate. Crew is the consumer.
- **Docs:** 1027.000 D2's "adds no wall-clock provider" becomes "the date is
  the `exactTime` fact (1027.000.000)".

## Implementer and date

Unassigned. It becomes a spec when Charlie answers 1 and names an
implementer and a date. D1–D4 are one landing. D5 is separable.

**As built so far.**
- cbf60c13, for the Bluesky client: `epochAtZero` and `utcOffset`
  (minutes east of UTC), set by `set_time`.
- 2026-09-26, for grnl: `timeZone`, as D1 writes it, and `locale`, the
  device's first preferred language as BCP 47. These come from a second
  host call, `set_place(locale, timeZone)`, because they are strings and
  change independently of the clock.
  - The Apple session and the web glue send both after boot.
  - Each field is filled by name, so an app that declares only the date
    fields is unaffected.
  - Until the host speaks, both strings are empty, as the date is zero.
  - `locale` answers the "device formatting" half of question 3 for
    TypeScript: `new Intl.DateTimeFormat(time.locale, { timeZone:
    time.timeZone })`. Contract-only formatting is still open.
- 2026-09-26, also for grnl: `seed`, a whole number below 2^53 from the
  platform's secure random source, drawn once per launch.
  - It is LLP 1027.000's explicit seed, supplied by the host rather than by
    the app. A source mixes it with the date and a counter for ids.
  - It travels as a third field on the same host call (`locale NUL timeZone
    NUL seed`) and reaches the runner through `Runner::set_seed`.
  - The runner draws none itself, so a test or the agent supplies its own.
- Linux supplies none of these facts yet.
