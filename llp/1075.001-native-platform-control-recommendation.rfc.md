# LLP 1075.001: Native platform control — Codex's recommendation

**Type:** RFC
**Status:** Draft
**Systems:** ExactKit (public native customization and controller composition); Swift app modules; native navigation geometry and retained tabs; Contract data attributes and web presentation; optional TypeScript native interop
**Author:** Codex for Charlie Cheever
**Date:** 2026-10-01
**Revised:** 2026-10-01
**Related:** [1075](1075-native-platform-control.explainer.md) (James's problem); [1075.000](1075.000-native-platform-control-research.research.md) (research); [1075.002](1075.002-native-platform-control-claude.rfc.md) (Claude's recommendation); [1024](1024-native-modules.rfc.md); [1031](1031-brownfield-embedding.rfc.md); [1035.001](1035.001-native-interaction-ownership.rfc.md); [1035.006](1035.006-public-ui-coverage.plan.md); [1037](1037-dartnative-lessons.research.md); [1038](1038-router.rfc.md); [1059](1059-tab-bar-projection.rfc.md); [1067.000](1067.000-one-native-module-or-two.rfc.md); [1072](1072-building-rows-off-the-main-thread.rfc.md)

## 1. Proposed direction

Make native customization and controller composition supported parts of Exact,
and build correct native navigation geometry and retained tabs into the framework.
Use Claude's concrete module-hook proposal as the initial implementation starting
point, with two supported levels of control:

1. **Customize Exact-owned presentation.** Swift hooks on the app's existing
   module receive real UIKit objects and app data at documented lifecycle points.
   Exact integrates its navigation containers, CSS scroll coordinates, and tab
   lifetimes; hooks configure the objects within that ownership contract.
2. **Own a native screen or container.** When configuration is insufficient, app
   code can supply a controller or own the surrounding native container, with
   Exact content attached through a supported composition boundary. This must
   work without a new Exact projection for each native feature.

Evaluate reuse of NativeScript's interop layer separately to make those same
capabilities convenient from TypeScript. Native object access alone does not
make Exact's existing layout and lifecycle cooperate with every UIKit behavior.

Do not build a hand-maintained mirror of UIKit in Rust. Existing `objc2` bindings
are the candidate for authors or implementation work that specifically needs
Rust. Do not make another five kernel properties the only answer to the next
five UIKit capabilities an app needs.

**Revision provenance (2026-10-01):** the first draft preceded reading Claude's
recommendation. This revision, requested by Charlie, incorporates his findings
in 1075.000 F6–F10 and the module hooks, data channel, container work, and explicit
first-frame choice in 1075.002. The main remaining difference is the stronger
app-owned controller path in §4. This is still Codex's Draft recommendation;
the request to update it is not acceptance or implementation authorization. No
implementer or delivery date is assigned, and the sketches are not implemented APIs.

## 2. Why this addresses the supplied examples

James's large-title patch needs access to the route controller, its navigation
item, the enclosing navigation controller, and the intended scroll view. His
tab work needs to choose controllers and retain their state. Language bindings
solve neither access to the correct object nor its ownership on their own.

Claude's research establishes why hooks alone are insufficient for these cases:

- **Navigation geometry:** the earlier [large-title prototype](1035.001-native-interaction-ownership.rfc.md#d9--title-intent-goes-to-the-navigation-bar-uikit-owns-collapse-insets-and-the-scroll-edge)
  records a requested `scrollTop = 80` becoming `132`, and a requested zero
  becoming `-52`, as native insets changed. My original `setContentScrollView`
  sketch understated this integration work. The framework needs one mapping of
  native available area, content origin, changing insets, and CSS assignments
  and events. The record describes prior experiments, not a new test of James's patch.
- **Tab lifetime:** [LLP 1038 §7](1038-router.rfc.md#7-what-this-deliberately-does-not-add) explicitly
  deferred retaining unselected tabs' views while retaining their entries, with
  a complaint about a tab forgetting its place as the return trigger. James's
  report fits that trigger; reproduce his particular state loss before assigning
  a cause. [LLP 1059](1059-tab-bar-projection.rfc.md) projects a tab bar, not the
  complete `UITabBarController` containment and retention model he asks for.

The product promise should be that an app can reach supported public platform
capabilities through app-owned code and a supported composition boundary, without
editing Exact's presenter for each capability. Shared Exact logic and layout can
continue inside those native surroundings.

Common native behavior needs a shared integration where Exact owns the affected
objects. That responsibility must coexist with an app-owned composition path;
waiting for a new framework feature cannot be the only route to native control.

## 3. Native customization of Exact-owned objects

Start with hooks on the app's one `ExactModule`, as [1075.002 D1](1075.002-native-platform-control-claude.rfc.md#d1--hooks-on-the-apps-one-module)
proposes. Expose public, typed contexts for route and navigation objects, then
the native tab container. Element hooks should expose views an app explicitly
needs to customize. Use Apple's real objects, names, and types; avoid copying
UIKit's vocabulary into the kernel schema. No second extension artifact is needed.

For example, a route callback could configure James's navigation item after
Exact has established the container and its bar:

```swift
// Proposed shape only. NativeRouteContext does not exist today.
func configureRoute(_ context: NativeRouteContext) {
    let item = context.viewController.navigationItem
    item.title = context.data["title"]
    item.backButtonDisplayMode = .minimal
}
```

This configures an item; it does not implement large-title collapse. Structural
containment and the content-scroll relationship must precede the first child
geometry where the earlier prototype requires that ordering. Configuration must
reach the first drawn frame. Define separate construction and completed-update
points where needed, plus transitions, unmount, replacement, and list reuse;
one callback after every batch is not a complete lifecycle contract.

Adopt `data-*` as the app-specific channel from Contract to hooks, carried in an
aggregate rather than a schema row per name. On the web these should be real
attributes and `dataset`, following [HTML's data-attribute semantics](https://html.spec.whatwg.org/multipage/dom.html#embedding-custom-non-visible-data-with-the-data-*-attributes).
Prefer an open vocabulary over Claude's mandatory second list of every name in
`app.json`; optional validation can catch mistakes without making registration
an admission requirement. The app defines the meaning and each host's behavior.
An attribute alone should not force a flat leaf to become a native view; an
explicit request for a native view by a hook is the reason to materialize one.

The invariants to establish are:

- **Stable identity:** associate the context with a session and a stable route
  visit or component identity, not an array position or an incidental descendant.
- **Mutation ownership:** define which presentation fields the app controls and
  ensure normal Exact updates do not silently reset them.
- **Lifecycle:** deliver configuration when the right objects exist, update when
  relevant inputs change, and invalidate the context on replacement or teardown.
  State how app configuration resets on reuse. Returning real UIKit objects
  does not make extracted native references automatically safe after retirement.
- **Events:** scoped `click()`, `focus()`, and `blur()` handles can use the
  existing semantic paths, queued after the batch to avoid re-entry. App code
  should not need private `NodeView` lookup or direct Contract-state mutation.
- **Delegates:** do not ask an app to overwrite the navigation delegate Exact
  needs for pop reconciliation. Provide an intentional delegation boundary or
  controller ownership, depending on the behavior requested.
- **Geometry:** assign each frame and inset to one owner. Large-title collapse,
  keyboard insets, and Exact layout must compose without double adjustment.
  List Exact-owned fields and the app's mutation rights, using 1075.002 D4 as
  a starting point. Diagnostic snapshots help find conflicts but cannot enforce
  ownership of arbitrary native references or their later asynchronous effects.

Expose supported platform-facing interfaces rather than declaring all internal
presenter classes public. The extension contract should survive routine internal
refactoring; breaking that contract must be deliberate and documented.

## 4. Controller choice and native container ownership

Configuration must have an escalation path. Claude's rule that changing geometry
and offscreen lifetime require an Exact projection is appropriate for Exact-owned
objects. As the only extension policy it recreates James's ceiling: a new native
behavior would still wait for an Exact release. Retain a supported app-owned
boundary as part of this proposal, not just a fallback to rewriting the whole app.

An app may supply a controller for a screen, or place Exact content inside a
container it owns. For James's second
example, that can mean a `UITabBarController` with persistent tab roots, often
one `UINavigationController` per tab, containing Exact screens or fully native
screens. UIKit supplies containment and presentation behavior.

This requires actual controller composition: add/remove child relationships,
appearance transitions, safe-area and keyboard propagation, focus, and teardown.
Putting a controller's view in a native-module box alone is insufficient.

The boundary must specify how native content bounds and safe areas reach Exact
layout, and which owner controls scrolling. App code owns its native container;
Exact owns CSS layout inside the content area supplied to it. A native scroll
subtree must either have an explicit coordinate exchange or remain wholly
native-owned. Arbitrarily overriding an Exact-owned frame, inset, or delegate
while Exact continues writing it is not the proposed escape path.

Existing `ExactView` embedding is the starting point, but its boundary is a whole
session. The implementation decision must distinguish two shapes:

| Shape | Required state and composition decision |
|---|---|
| Several native controllers present content from one Exact session | Define how stable route content is attached to each controller. There is no existing public arbitrary-subtree mounting API to assume. |
| Each native tab/controller owns an Exact session | Keep each session alive for its intended lifetime; make shared services and application data explicit. Separate sessions do not share runtime state automatically. |

I favor preserving one logical application/navigation state for the ordinary
Exact app, with UIKit containers as its presentation. For an already native app,
its own application state can remain the authority and Exact sessions can serve
as bounded embedded screens. Whichever shape is selected, the same stack must
not be independently authoritative in both UIKit and the Exact router.

In the ordinary Exact shape, completed native navigation and tab selection
update logical state once; cancellation leaves it unchanged. The native
controller tree follows that state without generating a second echo event.
In a native-owned shape, app code owns outer navigation and receives intentions
from Exact content through the embedding boundary.

## 5. Exact's navigation and tab responsibilities

For ordinary Exact apps, correct navigation geometry and retained tab content
are explicit framework deliverables alongside hooks.

**Navigation:** build the container/scroll mapping described in §2 once. Keep
the existing D9 direction of authored header semantics as the default shared
title source; hooks can customize the native navigation item. Removing an
authored header from native painting must have a consistent layout and scroll
mapping. An inline or noncollapsing title can be an intermediate milestone, but
does not satisfy James's full large-title request. Test CSS assignments and
events as well as physical collapse, expansion, and keyboard behavior.

Treat one visible bar per stack as a possible initial simplification, informed
by [LLP 1037 F1](1037-dartnative-lessons.research.md). Do not make fixed visibility
a permanent restriction. Per-screen visibility needs explicit transition and
cancelled-pop support; it must not be reset indiscriminately on every update.

**Tabs:** use `UITabBarController` for the ordinary native tab projection, with
one navigation owner per tab that contains a stack. Keep each visited live tab's
content mounted across selection changes. On the web retain the corresponding
content hidden and inert, preserving the authored tab bar and browser-history
semantics. Selection should not accidentally destroy drafts, lose scroll
positions, or leave hidden content focusable. Controller type customization
beyond this default uses §4's composition boundary.

Before implementing a fix, reproduce which state James loses and identify the
app revision and authoring pattern. The router already retains per-tab stacks;
that is not evidence that a tab's component/session and native controller stay
alive. Same-tab reselection also has an explicit pop-to-root policy today and
must be distinguished from switching away and returning.

The target should preserve each tab's promised route history, scroll position,
and editing state across ordinary tab switches. Operation ownership should be
explicit too: hiding a tab need not cancel its useful work; destroying its owner
must not leave callbacks targeting dead content. Persistence across process
restart is a separate feature and is not implied by retaining a tab in memory.

Retention is bounded by live tab and route lifetimes, not every historical screen.
Record memory after all tabs are visited and test removal and memory pressure.
If a later policy evicts content, it must define restoration rather than silently
reintroduce state loss. Persistent application values belong in their state/service
owner, not accidentally in a UIKit view that happens to live.

## 6. TypeScript convenience after the ownership proof

Swift hooks address native control for authors willing to write platform code.
They do not satisfy a separate requirement to make arbitrary synchronous UIKit
calls and receive immediate native callbacks entirely in TypeScript. If that is
part of James's requirement, record it as outstanding; neither this proposal nor
Claude's first implementation delivers it.

Evaluate [`NativeScript/napi-ios`](https://github.com/NativeScript/napi-ios) as a
reusable interop component. Its documented Hermes support makes it a plausible
candidate; it is not evidence of compatibility with Exact's particular Hermes
build, bytecode-only configuration, or owner-thread model. The research child
records the source and confidence limits.

The desired result is real native object access from TypeScript through the same
supported composition boundary. A JSON `native.call` wrapper around a generic
selector name does not provide object identity, typed callbacks, or protocol
implementation. Retain Swift for unsupported signatures and Swift-only APIs.

The decision experiment must settle:

1. Can the bridge use Exact's existing Hermes runtime, or does it require a
   different/additional runtime and what would that cost?
2. Where does native-facing JS execute, and how can UIKit obtain an immediate
   delegate result without violating the present refusal of synchronous runtime
   re-entry? Keep immediate decisions in Swift for the first proof.
3. Who retains a UIKit object or JS callback, and what invalidates its handle
   after reload, unmount, or session destruction?
4. Can metadata and bridge code be paid for only by apps that use them, with
   measured build, first-pixel, binary, and interaction costs?
5. Which APIs require an SDK/metadata rebuild, which Swift adapters remain
   necessary, and how are those limits reported to the author?

If reuse fails those tests, compare generated selective adapters with continuing
to use Swift extensions. Do not commit to maintaining a universal bridge before
that evidence exists. Direct UIKit calls from Contract would be a separate
language/effect decision; this proposal does not make them expression semantics.

## 7. The web and first frame

Share route identities, application values, tab selection semantics, and Exact
content/layout where they apply. On iOS the presentation may use UIKit
containers; on the web it uses DOM and browser history. UIKit configuration is
an explicitly Apple-specific layer, with an app-provided web behavior where the
feature needs one. A native controller type is not a new portable node type.

Retained tab state and history must be demonstrated on both surfaces. The web's
existing navigation-history policy need not mimic UIKit's presentation details.
CSS defaults remain the default wherever Exact defines shared layout or style.

Preserve the existing no-app-JS-before-first-pixel rule. Initial navigation
chrome needs a deliberate construction path; today's app module loads after
first pixel. Favor Claude's explicit opt-in for an app whose initial native
hooks require opening its existing module before first layout, subject to a
measured startup budget and an explicit boot-policy decision. Apps without such
hooks should not pay that cost. Compare host-linked configuration if the early
module load is too expensive; do not introduce a second module by default.

Measure native loading, initialization, first-frame correctness, and interactive
startup against the same app without hooks. The existing `boot.mjs` module-graph
check does not measure native `dlopen` cost; native startup measurements must
establish it. Early Swift hooks do not justify moving app JS or a JS bridge onto
the first-pixel path.

## 8. Alternatives and scope trade

- **Extend the five properties in James's patch:** useful convenience may still
  be justified, but alone this repeats his problem for the next native feature.
- **Mirror UIKit into Rust ourselves:** duplicates SDK-binding work already
  available through `objc2`, without resolving object access or composition.
- **Adopt NativeScript's entire UI layer:** much wider than reusing an interop
  component and would introduce another set of layout/presentation semantics.
- **Make patching the normal interface:** leaves the upgrade cost James
  explicitly objects to with app authors.
- **Only support full native apps:** gives native control but makes the shared
  layout and logic benefits harder to retain. Embedding should be usable at a
  smaller boundary than rewriting the entire application.

The proposed first consumer is James's actual navigation and tab use case. The
proposed take is to put further one-off UIKit property expansion and a universal
binding generator behind the hooks, navigation/tab integration, and controller
composition proof. This is a proposed ordering, not a recorded waiver or an
accepted scope change.

This direction revisits [LLP 1035.006 item 12.08](1035.006-public-ui-coverage.plan.md),
which favors semantic properties or optional components over arbitrary native
styling. I recommend typed native contexts with explicit ownership instead of
that being the only route to a platform capability. It also requires a narrow
supported-extension commitment despite [the current pre-1.0 policy](../rules/DEFERRED.md)
against public API stability. That commitment need not promise permanent ABI
compatibility; it must at least identify the public boundary and communicate
intentional source breaks. Adopt a fixture that exercises that boundary through
the existing checks. Claude's one-release deprecation overlap would require a
separate change to the current delete-rather-than-deprecate policy; this revision
does not silently adopt that promise.

General JS UI execution remains a later decision. The first Swift composition
proof need not change the rule against app JS before first pixel, introduce a
second shared object graph, or add a feature matrix to core crates. Before
implementation is selected, name its implementer/date and record the applicable
scope trade in the existing rules/owning LLPs.

## 9. Proposed proof and decision points

Use James's app, or the smallest reproduction he provides, through the existing
build and agent/manual paths. This table describes what must be demonstrated;
none of its rows is a completed test result.

Proposed order: reproduce the existing failures; add module hooks and the minimum
bar integration needed to demonstrate title/items in the first frame; then prove
retained tabs, collapsing-title coordinates, and app-owned controller composition
against the same consumer. A hooks-only milestone does not complete the request.
Evaluate TypeScript interop after those ownership boundaries are demonstrated.

| Exercise | Evidence sought |
|---|---|
| Large title, collapse, inline destination, trailing action | Exact supplies correct container/scroll integration; app Swift configures the native item and dispatches its action without a presenter patch. |
| CSS `scrollTop` at zero, middle and end; header heights 74, 106 and 148; title/header changes | D9's prior failure cases preserve assignments and events against the browser as native insets change. |
| Push/pop, cancelled interactive pop, keyboard visible | Bar, focus, geometry, and logical route state remain coherent; cancellation dispatches no completed Back. |
| Two tabs with distinct routes, scroll positions, and drafts | Ordinary switches retain the promised state; reselection behavior is intentional. |
| A tab with a custom native controller and Exact content | Controller choice and genuine containment work without private presenter access or a new built-in projection for that controller type. |
| Update an inactive tab; unmount/remount; destroy with work outstanding | Configuration is reapplied appropriately, state lifetime is explicit, and retired callbacks cannot affect a successor. |
| Web version of the same application flow | Shared content, state, and URLs remain useful; native-only presentation has an explicit disposition. |
| First frame and cost before and after, with and without hooks | Initial chrome appears without pop-in; build loop, native module startup, memory retention, and ordinary interaction costs are recorded. |

The initial decisions cover the public hook commitment, the data channel, early
module loading, retained-tab memory, and the controller composition boundary.
The later decision, informed by that proof and James's authoring needs, is whether
TypeScript-native interop is worth its measured integration cost. The intended
result is supported native control at both ownership levels, with correct shared
navigation and state behavior, rather than hooks alone being declared sufficient.
