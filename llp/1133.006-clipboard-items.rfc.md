## Summary

An app writes an image to the system clipboard with the Async Clipboard
API's names:

```ts
import { write, ClipboardItem } from "@exact/clipboard";

await write([new ClipboardItem({ "image/png": pngBytes })]);
```

exact2 can write text (`copyText`, web, Apple and Android) and read a paste
(`paste` with its text and files, LLP 1069.010). It cannot write an image.
T3 Code's media menu has **Copy image**, which the reference does with
`navigator.clipboard.write([new ClipboardItem({"image/png": blob})])`
after converting the image to PNG in a canvas (`readMediaPng`). The T3 Code
clone does it in its own Swift (`T3MediaActions.swift`'s `mediaCopyImage`
and its PNG conversion).

This RFC is the clipboard module's: it brings the built pieces under LLP
1133's checklist (D11) and adds `write` with a `ClipboardItem`, from data
code, for `image/png` and `text/plain`. It follows the web: an `image/png`
item holds a PNG (by `app:/` path, or small bytes), which the host
sanitizes as Chrome does. Data code converts other images to PNG with the
capability that already does, `storage.fs.compressImage(…, {type:
"image/png"})`, which this RFC amends to keep an image's size, bound its
source pixels and read SVG. Targets: the web, macOS and iOS in stage 1; Android, Windows and Linux
`later`; tvOS absent.

The package needs four seam additions that every later module can use
(D8): bytes and a constructible record in declarations, a send answering
nothing, admission for a bound implementation's sends, and an
implementation that serves as its own substitute.

## 2. Tier 1

### D1 — `write(items)` and `ClipboardItem`, by the Clipboard API's names

The W3C Clipboard API: `navigator.clipboard.write(data)` takes a sequence
of `ClipboardItem`, each constructed from a record of MIME type to data,
and resolves once the clipboard holds them; `writeText(data)` writes text.
The package exports the same names as functions, because data code never
calls `navigator` (LLP 1133 D6 rule 5):

```ts
import { write, writeText, ClipboardItem } from "@exact/clipboard";

await write([new ClipboardItem({ "image/png": png, "text/plain": url })]);
await writeText("…");
```

- **`ClipboardItem(items)`**: a record of MIME type to data; `types` is
  the record's keys in order. `ClipboardItem.supports(type)` answers
  `true` for `image/png` and `text/plain` on a target that has the module.
- **Data**, by type:
  - `text/plain`: a string, or a promise of one.
  - `image/png`: an `app:/` path (a string) to a PNG the host reads under
    the calling source's `fs.read` grant, as `fetch`'s `exactBodyFrom`
    reads one, so the image never passes through JavaScript (it is what
    `compressImage` writes); or, for a small image, PNG bytes as an
    `ArrayBuffer` or `ArrayBufferView` of at most 2 MiB, or a promise of
    one. The bytes form is bounded by the native module request, which a
    host refuses above 4 MiB (`host/apple/src/executor_core.rs:1142`), and
    the bytes travel base64 in it (D8); a larger buffer rejects `DataError`
    naming the path form.
- **`write(items)`** replaces the clipboard's whole contents, as every
  platform's write does. Writes land in the order they were called: the
  binding registers each write with a sequence number when it is called,
  before awaiting any promised data, and a later write supersedes an
  earlier one that has not landed, even if the earlier one's data resolves
  last (D2). It resolves with `undefined`, or rejects with a
  `DOMException`:
  - `NotAllowedError`: the target refused (the web without focus or
    without an activation it requires, D3); a type the module does not
    write, as Chrome rejects one ("Type … not supported on write"); more
    than one item, as Chrome rejects it; or a caller whose origin may not
    write (D6);
  - `DataError`: `image/png` data that does not decode as PNG, over the
    pixel bound, or over the byte bound (D2), the message saying which;
  - `NotSupportedError`: a target without the module (§5).
- **`writeText(text)`** is `write([new ClipboardItem({"text/plain":
  text})])`.

**The image is sanitized,** as the specification asks and Chrome does: the
host decodes the PNG and writes a new PNG of its pixels, so metadata and
anything else in the file are not carried. An animated PNG writes the
first frame of its animation, as Chromium's clipboard writer decodes frame
0 and its PNG decoder skips a default image that is not part of the
animation. Both hosts select that frame explicitly rather than whatever
their decoder shows by default (on Apple, ImageIO's animation frames as
`kCGImagePropertyAPNGDictionary` describes them; on the web, the first
frame of an `ImageDecoder` track), and so does `compressImage`'s
conversion; stage 1 checks each against a file whose default image is
not part of the animation.

**Declared deviations,** each because data code is not a page:

1. *Bytes or a path, not a `Blob`.* Data code has no `Blob`
   (`docs/reference.md`, the TypeScript globals: "no `Request`, `Blob` or
   `FormData`").
2. *Exported functions, not `navigator.clipboard`.* LLP 1133 D6's binding
   form, as `getCurrentPosition` is imported.
3. *`supports("text/html")` is `false`.* HTML is a mandatory type for the
   web's write, and Chrome answers `true`; it waits for a consumer, with
   its sanitization (§10).

An empty `write([])` and a write with zero types follow what Chrome does,
measured by the conformance run (§9).

**Converting first.** An image that is not PNG (a JPEG, a WebP, an SVG) is
converted by the app, as T3's `readMediaPng` converts in a canvas: data
code calls `storage.fs.compressImage(from, to, {type: "image/png",
maxPixels, maxBytes})`, which decodes what the platform reads and
writes a PNG, and passes `to` as the item's path. `compressImage` needs
three amendments for this use:

- **Keep the size.** It always scales the longer side to `maxDimension`
  and shrinks while over `maxBytes` (`host/web/storage-image.js:69`), so
  no bound keeps both a 16,000 × 1,000 image whole and a large square one
  refused. `maxDimension` may be omitted with `type: "image/png"`: the
  image is written at its own size, and `maxBytes` refuses (`unfit`)
  rather than shrinks.
- **A pixel bound on the source.** `maxPixels`, checked against the
  header before decoding (as its 64 Mi bound is today), refuses
  `too-large` above it. The clone passes 64,000,000, the reference's
  bound.
- **SVG input.** ImageIO has no SVG decoder and the web's path reads
  raster types. On Apple it decodes through the SVG rasterizer the hosts
  already have for `img` (LLP 1011.001; `RasterImage.swift` `decodeSVG`),
  on the web through an `Image` element drawn to the canvas. The size is
  an `img`'s with no CSS size: the file's width and height, one of them
  with the `viewBox`'s ratio, the `viewBox`'s own size when the file
  gives none (the native hosts' declared deviation,
  `host/svg-file/src/lib.rs:84-100`), else 300 × 150, CSS's default
  object size.

### D2 — Bounds

- **Bytes:** an image file is at most 64 MiB (the `exactBodyFrom` and
  `compressImage` bound) by path and 2 MiB as bytes; more rejects
  `DataError` before decoding.
- **Pixels:** a decoded image is at most 64,000,000 pixels, the bound of
  T3's `readMediaPng` and close to `compressImage`'s 64 Mi; past it,
  `DataError` ("too large"), and nothing is written.
- **Text:** at most 1 MiB of UTF-8, inside the module request's bound.
- **One write at a time** per session, in call order: a `write` called
  while an earlier one has not landed (its data still resolving, or still
  decoding) supersedes it, as a second Copy replaces the first; the
  earlier promise rejects `AbortError` and its data, when it resolves, is
  dropped. The order is fixed when `write` is called, as WebKit registers
  a writer before it collects promised data.

### D3 — When a write may happen, per target

- **Native hosts** write whenever the app's foreground code asks: neither
  `NSPasteboard` nor `UIPasteboard` asks the person before a write, and
  iOS's paste prompt is for reads.
- **The web** follows the browser. Chrome writes while the document has
  focus and grants `clipboard-write` to the active tab, with no user
  activation. Safari and Firefox require transient activation, which HTML
  defines by time: it lasts a browser-defined duration after the press
  ([transient activation](https://html.spec.whatwg.org/multipage/interaction.html#transient-activation)),
  not for a call stack. A data-code write reaches the page module after
  its answer's turn, and after whatever the source awaited first (T3's
  menu pick and the RPC that mints the image's URL). Whether it lands
  inside the activation therefore depends on how long that took, and on
  each browser's duration. Stage 1 measures it on current Safari and
  Firefox, with T3's path and with a delayed fetch, and records the
  result as the web's host difference. A write outside the activation
  rejects `NotAllowedError`, and the app shows its own failure.

### D4 — The platforms' words, none built in stage 1

Declared now so the shape is known; each is built when an app asks. Each
modifies the write and none overlaps a tier 1 word, so none beats one.

| Word | Platform API | Platform |
|---|---|---|

| `apple.expirationDate=<epoch ms>` | [`UIPasteboard.OptionsKey.expirationDate`](https://developer.apple.com/documentation/uikit/uipasteboard/optionskey/expirationdate) | iOS |
| `apple.currentHostOnly=true` | [`NSPasteboard.ContentsOptions.currentHostOnly`](https://developer.apple.com/documentation/appkit/nspasteboard/contentsoptions/currenthostonly), through `prepareForNewContents(with:)` | macOS |
| `android.isSensitive=true` | [`ClipDescription.EXTRA_IS_SENSITIVE`](https://developer.android.com/reference/android/content/ClipDescription#EXTRA_IS_SENSITIVE): hidden from the copy confirmation (Android 13) | Android |

Each is inert on the other platforms (LLP 1133 D2).

### D5 — Unsaid defaults

- **macOS** writes what a hand-built AppKit app writes when it copies an
  image (LLP 1115, LLP 1133 D4): `NSPasteboard.general.clearContents()`
  then `writeObjects([NSImage])`, which writes the image's own
  representations (TIFF, at least), and `public.png` beside them so that
  the type the web names is there. Stage 1 lists the types
  `writeObjects` writes for an image on the current macOS and records
  them here; what Chrome on macOS writes for the same item is comparison
  evidence, not the rule. `text/plain` is `public.utf8-plain-text`, as
  `copyText` writes.
- **iOS** writes one pasteboard item through
  `UIPasteboard.general.setItems` with `public.png` (what
  `UIPasteboard.general.image` writes for a PNG image) and
  `public.utf8-plain-text`, with no options: Universal Clipboard on, no
  expiry, `UIPasteboard`'s own default.
- **The web** writes what the browser writes for the item.
- **A write gives no feedback** on any platform: no sound, and no system
  banner on iOS for a write. Android 13 shows its own confirmation, which
  an app does not duplicate. The app's own toast (T3's "Image copied") is
  the app's.

### D6 — Tier 3, and who may write

**No hatches** (LLP 1133 D3): `NSPasteboard.general` and
`UIPasteboard.general` are singletons an app's native code reaches without
the module, and the module holds nothing between writes.

**Origin** (LLP 1133.002 D12): any of the app's foreground code may write,
as with `copyText`. A write whose origin is a tool invocation (LLP 1111) or
a headless session rejects `NotAllowedError` (`person-required`), and so
does one from a wake (LLP 1114.001): replacing the person's clipboard is an
effect they did not ask for in the app. D8 says how the origin reaches a
bound implementation.

## 4. The ceiling test

The common uses of `NSPasteboard`, `UIPasteboard` and `ClipboardManager`,
and what reaches each:

| Use | Reached by |
|---|---|
| copy text | `copyText` (Contract), `writeText` (data code) |
| copy an image (Copy image, a share card, a chart) | `write` with `image/png` (D1), after `compressImage` for another format |
| copy an image and its URL or alt text together | one item with `image/png` and `text/plain` |

## 5. Packaging, callers and targets

### D7 — `@exact/clipboard`, an extension; `copyText` stays a command

The default of LLP 1133 D5: a host extension package, `packages/clipboard`,
with `exact.json` for the interface and implementations for `web` and
`apple`. Nothing here needs the runner, the kernel or a data executor: the
bytes come from the source, and the platform's pasteboard takes them.

**Callers** (LLP 1133 D6):

- **Data code** calls `write` and `writeText` through the generated
  binding. This is the consumer's path: T3's Copy image runs after a menu
  pick and an RPC that mints the image's URL. Rust gets
  `exact_data::modules::clipboard::{write, write_text, ClipboardItem}`,
  generated from the same declaration (LLP 1133.001 D9), with `Vec<u8>`
  or an `app:/` path for an image.
- **Contract** keeps `copyText(text)` as it is. LLP 1133 D6: "a name moves
  only when its module's RFC rewrites it", and this RFC leaves it, since
  moving it renames every app's call for no new behaviour. A Contract
  `write` for an image (an `img` by `#id`, as `share(files=["#id"])` names
  an element), which would write inside the press on every browser, waits
  for a consumer (§11, question 3).
- Neither is a request in LLP 1069.007 D1's sense (no system UI, no
  permission), and neither is `sync`.

**Targets** (LLP 1133 D8):

| Target | `write` (image and text) | Stage |
|---|---|---|
| web | `navigator.clipboard.write([new ClipboardItem(…)])` | 1 |
| macOS | `NSPasteboard.general`, D5's types; ImageIO to sanitize | 1 |
| iOS, iPadOS | `UIPasteboard.general.setItems`; ImageIO to sanitize | 1 |
| Android | later: `ClipboardManager.setPrimaryClip` with a `ClipData` URI from a `FileProvider`, the platform's way to put an image on the clipboard | — |
| Windows | later: `Clipboard.SetContent` with a `DataPackage` bitmap and the `PNG` format | — |
| Linux | later: the host has no clipboard yet (`copyText` is journaled as unsupported) | — |
| Expose | later, when it is a host | — |
| tvOS | absent: no pasteboard | — |
| the terminal | absent for images; OSC 52 carries text, a `copyText` matter | — |

On a `later` or absent target the module is optional (LLP 1124 D9):
`ClipboardItem.supports` answers `false` and `write` rejects
`NotSupportedError`.

### D8 — Four seam additions

The geolocation slice built the module seam for a source and a send with
keyword options and JSON answers. This package needs four more, each
general:

1. **Bytes and a constructible record in declarations.** A declaration
   type `bytes` (an `ArrayBuffer` or view in TypeScript, `Vec<u8>` in Rust,
   base64 in LLP 1124 D5's JSON body, since the door's calls are strings,
   `js/src/door.rs`), and a shape declared as a record keyed by string
   (`"ClipboardItem": {"record": "string", "of": "string | bytes | path"}`)
   from which the binding generates a class with the shape's constructor,
   `types` and a static `supports` answered from the declaration. The
   generator today emits `send(options): Promise<answers>` only
   (`js/bake/src/typescript.mjs:1042`); it gains positional parameters
   for a send that declares them (`write(items)`), a sequence number
   taken at the call (D2's order), awaiting promise-valued data after it,
   and a copy of a view's bytes. Bytes stay within the native module
   request's 4 MiB, base64 included; a module that needs more takes an
   `app:/` path, as this one does.
2. **A send answering nothing** resolves `undefined`; an answer
   `{error: name, message}` rejects with a `DOMException` of that name and
   message, where `answered` today throws an `Error` with `code`
   (`typescript.mjs:1062`).
3. **Admission for a bound implementation's sends.** A bound module's
   body passes the runner today without admission
   (`runner/src/runner/modules.rs:532`, "a bound module answers it … past
   this admission"), and the Apple module receives roots and agent mode,
   not the call's authority (`NativeModule.swift:566`). Every send to a
   bound implementation now passes LLP 1133.002 D14's admission first: the
   origin rule (D6 here), the calling source's effective grants (for an
   `app:/` path, `fs.read`; the runner resolves the path and hands the
   implementation a file it may read, so the implementation never checks
   grants itself), and the call's lifetime, so a write whose mutation or
   session ends before it lands is cancelled and its promise rejects
   `AbortError`. The check is repeated at the moment of the write.
4. **An implementation as its own substitute.** Under the agent the web
   loads no implementation (`host/web-js/modules.js:90`), and the
   declaration's substitute answers instead. A module that touches nothing
   of the person's when pointed elsewhere declares `"substitute":
   "implementation"`: under the agent the bound implementation runs,
   told it is substituting, and writes to a private store (§7). Its
   decoding and bounds are then production's.

### D9 — Grant, cost

**Grant:** none, as `copyText` has none: writing the clipboard needs no
permission on any stage 1 platform, and no manifest entry. A page in an
iframe needs `Permissions-Policy: clipboard-write`, which an Exact page
never is.

**Cost:** an app that does not import the package links none of it (LLP
1047.001). One that does adds the Apple implementation (ImageIO is already
linked by the host) and a few hundred bytes of page module. Nothing runs
before first pixel. Stage 1 records the measured sizes here, and the time
of a write of a 20 MB image by its `app:/` path on macOS.

## 6. The consumer: T3 Code's Copy image

The clone's `src/media/media-actions.ts:187` asks its Swift module for
`mediaCopyImage` with the image's URL, and its menu needs that module
(`:162`, `native.available`). After this RFC it fetches and converts in
TypeScript, as the reference's `readMediaPng` does in a canvas:

```ts
const bytes = url.startsWith("data:image/") ? dataUrlBytes(url) : await fetchMedia(url);
await storage.fs.writeFile(`app:/tmp/copy/${seed}`, bytes);
const png = await storage.fs.compressImage(`app:/tmp/copy/${seed}`, `app:/tmp/copy/${seed}.png`,
  { type: "image/png", maxPixels: 64_000_000, maxBytes: 64 * 1024 * 1024 });
await write([new ClipboardItem({ "image/png": png.path })]);
```

`fetchMedia` is the reference's `readMediaBlob` (HTTP failures and a web
page refused with its sentences). An inline image, a `data:image/` URL,
which the clone renders in published HTML (`src/timeline/html-render.ts:267`)
and which `fetch` does not take (its grants admit `http` and `https`
only, `grants/src/lib.rs:385`), is decoded by `dataUrlBytes` in
TypeScript with `atob`, refused above 64 MiB, as the reference's `fetch`
of a `data:` URL reads it.

The reference's sentences stay the app's: `compressImage`'s `too-large`
is `TOO_LARGE`, `undecodable` is `UNDECODABLE`, a `DataError` from `write`
is `NOT_PNG`. The fetch needs `net.fetch` for the environment's origin,
which the clone grants; the two paths need `fs.read` and `fs.write` on
`app:/tmp`. A PNG could skip the conversion (`compressImage` always
re-encodes); the clone converts every image, as the reference does.

## 7. The substitute

LLP 1069.007 D7's paragraph:

1. **Shape:** a send that answers once; not a fact, not a request.
2. **Under the agent** nothing reaches the person's clipboard: the
   implementation runs as its own substitute (D8 item 4). On Apple it
   writes a private named pasteboard per session (`NSPasteboard(name:)`;
   on iOS `UIPasteboard(name:create:)`); on the web it keeps the item in
   memory instead of calling the browser. Decoding and bounds run as in
   production, so a drive sees the same `DataError`s. `copyText` takes
   the same path under the agent, which fixes its writing the real
   clipboard today (`Session.swift`'s `NSPasteboard.general`, `rt.js`'s
   `writeText`).
3. **`state.extensions.clipboard`** shows the last write beside the
   module's call counts: its types, the text (cut to 200 characters, as
   journal lines are), and for an image its width, height, byte count and
   SHA-256, never the bytes. A drive asserts Copy image with `state`, with
   no new agent operation (LLP 1133 §7).
4. **Journal:** `clipboard: wrote image/png 1280×720 (412,388 bytes)`,
   `clipboard: write refused: DataError (too large)`.
5. **`EXACT_DEVICE=real`** (LLP 1069.007 D8) writes the real clipboard, for
   a drive that pastes into another app.
6. **Production:** unchanged; a production bake has no agent.

## 8. Acceptance

The module is accepted (LLP 1133 D10 step 5, D9 item 11) by the consumer's
drive in the clone's adoption PR, not by the framework's fixtures: on the
web (Chrome), macOS and an iOS simulator, open a PNG, a JPEG, an SVG
without a size, a 16,000 × 1,000 image, an inline `data:` image and an
APNG whose default image is not part of its animation in the media
preview, Copy image, and read `state.extensions.clipboard`'s dimensions and
hash (the APNG written directly as well as converted); an image over the pixel bound shows the reference's "too large"
toast; with `EXACT_DEVICE=real` on macOS, the copy pastes into Preview's
New from Clipboard and into Messages. Safari and Firefox are driven for
D3's measurement. The clone's Swift for Copy image goes in that PR (§1).
