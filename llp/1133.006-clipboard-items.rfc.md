## Summary

An app writes an image to the system clipboard with the Async Clipboard
API's names:

```ts
import { write, ClipboardItem } from "@exact/clipboard";

const bytes = await (await fetch(url)).arrayBuffer();
await write([new ClipboardItem({ "image/png": bytes })]);
```

exact2 can write text (`copyText`, web, Apple and Android) and read a paste
(`paste` with its text and files, LLP 1069.010). It cannot write an image.
T3 Code's media menu has **Copy image**, which the reference does with
`navigator.clipboard.write([new ClipboardItem({"image/png": blob})])`
after converting the image to PNG in a canvas (`readMediaPng`); the T3 Code
clone does it in its own Swift (`T3MediaActions.swift`, `mediaCopyImage`
and the PNG conversion, about 70 lines, plus the module routing).

This RFC is the clipboard module's: it brings the built pieces under LLP
1133's checklist (D11) and adds `write` with a `ClipboardItem`, from data
code, for two types: `image/png` and `text/plain`. Targets: the web, macOS
and iOS in stage 1; Android, Windows and Linux `later`; tvOS absent.

One declared deviation carries the consumer: an `image/png` item may hold
any image the host can decode (JPEG, GIF, WebP, HEIC, SVG), which the host
writes as PNG, because data code has no canvas to convert it the way
`readMediaPng` does.

What is missing, by the roster's row (LLP 1133.000 §3.10): rich types on

## 2. Tier 1

### D1 — `write(items)` and `ClipboardItem`, by the Clipboard API's names

The W3C Clipboard API: `navigator.clipboard.write(data)` takes a sequence
of `ClipboardItem`, each constructed from a record of MIME type to data,
and resolves once the clipboard holds them; `writeText(data)` writes text.
The package exports them under the same names, as functions rather than
`navigator.clipboard` members, because data code never calls `navigator`
(LLP 1133 D6 rule 5):

```ts
import { write, writeText, ClipboardItem } from "@exact/clipboard";

await write([new ClipboardItem({ "image/png": bytes, "text/plain": url })]);
await writeText("…");
```

- **`ClipboardItem(items)`**: a record of MIME type to data. Its `types`
  is the record's keys in order. `ClipboardItem.supports(type)` is `true`
  for `image/png` and `text/plain` on every target that has the module,
  as the web's static method answers.
- **Data**, by type:
  - `text/plain`: a string, or a promise of one.
  - `image/png`: an `ArrayBuffer` or `ArrayBufferView` of an image file,
    or a promise of one, or an `app:/` path (a string) the host reads under
    the app's `fs.read` grant, as `fetch`'s `exactBodyFrom` reads one, so
    large files never pass through JavaScript.
- **`write(items)`** takes an array of exactly one item, as Chrome does
  (`NotAllowedError` for more, its message naming why). It replaces the
  clipboard's whole contents, as every platform's write does. It resolves
  with `undefined`, or rejects with a `DOMException`:
  - `NotAllowedError`: the target refused the write (the web without
    focus, or without the user activation Safari and Firefox require,
    D3), or the call's origin may not write (D6);
  - `DataError`: an image the host cannot decode, over the pixel bound, or
    over the byte bound (D2); the message says which;
  - `NotSupportedError`: a type other than the two, or a target without
    the module (D8).
- **`writeText(text)`** is `write([new ClipboardItem({"text/plain":
  text})])`.

**Declared deviations,** each because data code is not a page:

1. *Bytes, not a `Blob`.* Data code has no `Blob` (`docs/reference.md`,
   the TypeScript globals: "no `Request`, `Blob` or `FormData`"), so an
   item holds an `ArrayBuffer` or view, or an `app:/` path.
2. *Any decodable image for `image/png`.* The web's `image/png` data must
   be a PNG: Chrome decodes it as PNG and re-encodes it (the specification's
   "sanitized" image), and other bytes fail. A page converts first, in a
   canvas, which is what T3's `readMediaPng` does. Data code has no canvas
   and no image decoder, so the host converts: PNG bytes are written as
   they are, and any other image the platform decodes is decoded and
   written as PNG. An SVG is rasterized at its own size, as an `img`
   shows it. Animated images write their first frame, as a canvas draws
   one.
3. *Exported functions, not `navigator.clipboard`.* LLP 1133 D6's binding
   form, as `getCurrentPosition` is imported.

### D2 — Bounds

- **Bytes:** an item's image data is at most 64 MiB (the `exactBodyFrom`
  bound); more rejects `DataError` before anything is decoded.
- **Pixels:** a decoded image is at most 64,000,000 pixels, T3's
  reference bound in `readMediaPng`, which keeps a write from allocating
  gigabytes; past it, `DataError` ("too large"), and nothing is written.
- **Text:** at most 16 MiB of UTF-8.
- **One write at a time** per session: a `write` while another is
  decoding supersedes it, as a second Copy replaces the first; the earlier
  promise rejects `AbortError`.

### D3 — When a write may happen, per target

- **Native hosts** write whenever the app's foreground code asks: neither
  `NSPasteboard` nor `UIPasteboard` asks the person to write, and iOS's
  paste prompt is for reads by another app.
- **The web** follows the browser. Chrome writes while the document has
  focus, with no user activation, and grants `clipboard-write` to the
  active tab; Safari and Firefox write only within a user activation.
  Safari accepts a `ClipboardItem` whose data is a promise inside the
  activation, so the page module calls `navigator.clipboard.write` at
  once and resolves the item's data as the bytes arrive and convert. A data
  module's call reaches the page module only after its answer's turn, which
  is outside the press's activation: on Safari and Firefox a `write` from
  data code rejects `NotAllowedError`, and the app shows its own failure.
  That is the web's rule, and a Contract form inside the press (§11,
  question 3) is how an app would meet it there.

## 3. Tier 2 and tier 3

### D4 — The platforms' words, none built in stage 1

Declared now so the shape is known; each is built when an app asks:

- `apple.localOnly=true`: `UIPasteboard.OptionsKey.localOnly`, kept off
  Universal Clipboard (iOS; `NSPasteboard` has no such option).
- `apple.expiresAt=<epoch ms>`: `UIPasteboard.OptionsKey.expirationDate`
  (iOS).
- `android.sensitive=true`: `ClipDescription.EXTRA_IS_SENSITIVE`, which
  hides the content from the copy confirmation (Android 13).
- `apple.tiff=true`: also write `public.tiff` on macOS, for apps that read
  only TIFF (D5).

### D5 — Unsaid defaults

- **macOS** writes `public.png` for `image/png` and `public.utf8-plain-text`
  for `text/plain` on `NSPasteboard.general` after `clearContents()`. The
  oracle is what Chrome on macOS puts on the pasteboard for the same
  `ClipboardItem` (the T3 reference runs in Chromium): stage 1 reads
  `NSPasteboard.general.types` after a page's write in Chrome and matches
  it, adding `public.tiff` if Chrome writes it. An `NSImage` written with
  `writeObjects` writes TIFF; the image pastes into Preview, Pages,
  Messages and Slack either way.
- **iOS** writes one pasteboard item with `public.png` and
  `public.utf8-plain-text` through `UIPasteboard.general.setItems`, with
  no options: Universal Clipboard on, no expiry, as `UIPasteboard`'s own
  default is.
- **The web** writes what the browser writes for the item.
- **A write gives no feedback** on any platform (no sound, no system
  banner on iOS for a write; Android 13 shows its own confirmation, which
  an app does not duplicate). The app's own toast (T3's "Image copied") is
  the app's.

### D6 — Tier 3, and who may write

**No hatches** (LLP 1133 D3): `NSPasteboard.general` and
`UIPasteboard.general` are singletons an app's native code reaches
without the module, and the module holds nothing between writes.

**Origin** (LLP 1133.002 D12): any of the app's foreground code may write,
as with `copyText`. A write whose origin is a tool invocation (LLP 1111)
or a headless session rejects `NotAllowedError` (`person-required`):
replacing the person's clipboard is an effect they did not ask for in the
app. A write from a wake (LLP 1114.001) is refused the same way.

## 4. The ceiling test

The common uses of `NSPasteboard`, `UIPasteboard` and `ClipboardManager`,
and what reaches each:

| Use | Reached by |
|---|---|
| copy text | `copyText` (Contract), `writeText` (data code) |
| copy an image (Copy image, a share card, a chart) | `write` with `image/png` (D1) |
| copy an image and its URL or alt text together | one item with `image/png` and `text/plain` |
| copy rich text (`text/html`, RTF) | not reached: `text/html` waits for a consumer, with its sanitization (§10) |
| copy files (Finder's copy) | not reached: file promises wait for a consumer |
| copy a custom type for the app's own paste | not reached: the web's `web ` custom formats wait for a consumer |
| read the clipboard outside a paste | not reached: `read`/`readText`, and iOS's paste prompt, wait for a consumer (§10) |
| keep a secret off Universal Clipboard, expire it | `apple.localOnly`, `apple.expiresAt` (D4) |
| mark a copy sensitive on Android | `android.sensitive` (D4) |
| watch the clipboard change | left out: `NSPasteboard.changeCount` polling is a privacy tell, and the web has no event for it outside `clipboardchange`'s proposal |

## 5. Packaging and callers

### D7 — `@exact/clipboard`, an extension; `copyText` stays a command

The default of LLP 1133 D5: a host extension package, `packages/clipboard`,
with `exact.json` for the interface and implementations for `web` and
`apple`. Nothing here needs the runner, the kernel or a data executor: the
bytes come from the source, and the platform's pasteboard takes them.

```json
{
  "kind": "interface",
  "name": "@exact/clipboard",
  "version": "1.0.0",
  "grants": [],
  "names": [
    { "send": "write", "request": false,
      "options": { "items": "ClipboardItem[]" }, "answers": "none" },
    { "send": "writeText", "request": false,
      "options": { "text": "string" }, "answers": "none" }
  ]
}
```

**The wire body.** LLP 1124 D5's JSON body carries the item: a string for
`text/plain`, an `app:/` path, or the image bytes in base64 (the door's
calls are strings, `js/src/door.rs`). At the 64 MiB bound that is 85 MiB of
JSON, so stage 1 measures a 20 MB image's write on macOS and records it
here; if it misses the answer's budget the binding writes large bytes to
`app:/tmp/` and passes the path.

**Callers** (LLP 1133 D6):

- **Data code** calls `write` and `writeText` through the generated
  binding. This is the consumer's path: T3's Copy image runs after a menu
  pick and an RPC that mints the image's URL.
- **Contract** keeps `copyText(text)` as it is. LLP 1133 D6: "a name moves
  only when its module's RFC rewrites it", and this RFC leaves it, since
  moving it renames every app's call for no new behaviour. A Contract
  `write` for an image (an `img` by `#id`, written at its natural size, as
  `share(files=["#id"])` names an element) waits for a consumer (§11,
  question 3).
- Neither is a request in LLP 1069.007 D1's sense: no system UI, no
  permission. Neither is `sync`.

### D8 — Every target

| Target | `write` (image and text) | Stage |
|---|---|---|
| web | `navigator.clipboard.write([new ClipboardItem(…)])`, the image converted to PNG through `createImageBitmap` (an `Image` element for SVG) and an `OffscreenCanvas` | 1 |
| macOS | `NSPasteboard.general`, `public.png`, ImageIO to decode and encode (`NSImage` for SVG, as the clone does) | 1 |
| iOS, iPadOS | `UIPasteboard.general.setItems`, ImageIO (an `UIGraphicsImageRenderer` draw for SVG) | 1 |
| Android | later: `ClipboardManager.setPrimaryClip` with a `ClipData` URI from a `FileProvider`, the platform's way to put an image on the clipboard | — |
| Windows | later: `Clipboard.SetContent` with a `DataPackage` bitmap and the `PNG` format | — |
| Linux | later: the host has no clipboard yet (`copyText` is journaled as unsupported) | — |
| tvOS | absent: no pasteboard | — |
| the terminal | absent for images; OSC 52 carries text, a `copyText` matter | — |

On a `later` or absent target the module is optional (LLP 1124 D9):
`ClipboardItem.supports` answers `false` and `write` rejects
`NotSupportedError`.

## 6. Grant, cost

**Grant:** none, as `copyText` has none: writing the clipboard needs no
permission on any stage 1 platform, and no manifest entry. A page in an
iframe needs `Permissions-Policy: clipboard-write`, which an Exact page
never is.

**Cost:** an app that does not import the package links none of it (LLP
1047.001). One that does adds the Apple implementation (ImageIO is already
linked by the host) and a few hundred bytes of page module. Nothing runs
before first pixel. Stage 1 records the measured sizes here.

## 7. The substitute

LLP 1069.007 D7's paragraph:

1. **Shape:** a send that answers once; not a fact, not a request.
2. **Under the agent** nothing reaches the person's clipboard. On Apple
   the write goes to a private named pasteboard per session
   (`NSPasteboard(name:)`; on iOS `UIPasteboard(name:create:)`), and the
   web glue keeps the item in memory instead of calling the browser. The
   decode and the bounds run as in production, so a drive sees the same
   `DataError`s. `copyText` takes the same path under the agent, which
   fixes its writing the real clipboard today (`Session.swift`'s
   `NSPasteboard.general`, `rt.js`'s `writeText`).
3. **`state.clipboard`** shows the last write: its types, the text (cut to
   200 characters, as journal lines are), and for an image its width,
   height, byte count and SHA-256, never the bytes. A drive asserts Copy
   image with `state`, with no new agent operation (LLP 1133 §7).
4. **Journal:** `clipboard: wrote image/png 1280×720 (412,388 bytes)`,
   `clipboard: write refused: DataError (too large)`.
5. **`EXACT_DEVICE=real`** (LLP 1069.007 D8) writes the real clipboard, for
   a drive that pastes into another app by hand.
6. **Production:** unchanged; a production bake has no agent.

## 8. The consumer: T3 Code's Copy image

The clone's `src/media/media-actions.ts:187` asks its Swift module for
`mediaCopyImage` with the image's URL. After this RFC it fetches the bytes
itself and writes them:

```ts
const response = await fetch(url);
if (!response.ok) throw new Error(`The file could not be fetched (HTTP ${response.status}).`);
if (mediaType(response) === "text/html") throw new Error(WEB_PAGE);
await write([new ClipboardItem({ "image/png": await response.arrayBuffer() })]);
```

The reference's sentences for each failure stay the app's: a `DataError`
whose message says "too large" is `TOO_LARGE`, any other is
`UNDECODABLE`. The fetch needs `net.fetch` for the environment's origin,
which the clone already grants.

The acceptance drive, on the web (Chrome), macOS and an iOS simulator:
open a PNG, a JPEG and an SVG in the media preview, Copy image, and read
`state.clipboard`'s dimensions; an image over the pixel bound shows the
reference's "too large" toast; with `EXACT_DEVICE=real` on macOS, the copy
pastes into Preview's New from Clipboard.

## 9. Building it

Stage 1:

1. The package and its declaration; the TypeScript binding (`write`,
   `writeText`, `ClipboardItem`), generated by the bake.
2. The Apple implementation: decode, bounds, encode, the pasteboard; the
   agent's private pasteboard; `copyText` moved onto the same path under
   the agent.
3. The web implementation: the page module's `write`, the PNG conversion,
   the in-memory substitute.
4. `state.clipboard` and the journal lines in the runner's agent.
5. A fixture app (an image in three formats, a button per format whose
   mutation fetches and writes), driven on the web, macOS and the iOS
   simulator; conformance against Chrome for `ClipboardItem.supports`,
   `types` and the rejections.

The clone's adoption is a later app PR (§8).

## 10. What stays out

- **`read` and `readText`** outside a paste, with iOS's paste prompt
  (`UIPasteControl` or the system alert) and the web's permission, until a
  consumer asks.
- **`text/html` and RTF,** until a consumer asks; HTML needs the
  specification's sanitization on write.
- **Custom formats** (`web <type>`), **file promises**, **several items
  in one write**.
- **Linux, Windows and Android** cells, in the order apps ask (LLP
  1133.000 §4, "the other targets of the seven").
- **A clipboard-change event.**

## 11. What a ruling decides

1. **Admit `write` with `ClipboardItem`** for `image/png` and `text/plain`,
   web and Apple first, as the clipboard module's RFC (LLP 1133 D11).
   `rules/DEFERRED.md` refuses no clipboard type by name; the roster's row
   moves from wave 3 to this consumer.
2. **The declared deviation:** the host converts any decodable image to
   PNG (recommended, D1 deviation 2), or the module takes PNG bytes only
   and data code converts, which it cannot do today without an image
   decoder.
3. **Data code only in stage 1** (recommended), or a Contract `write` with
   an `img` by `#id` as well, which would meet Safari's activation rule
   from a press but has no consumer yet.
4. **`copyText` stays** a Contract command (recommended, D7), or moves into
   the package as `writeText`, renaming every app's call.
5. **macOS writes what Chrome writes** for the same item, measured in stage
   1 (recommended, D5), or PNG only whatever Chrome does.
6. **A tool invocation's write refuses** `person-required` (recommended,
   D6), or tools may write the clipboard.
7. **`copyText` under the agent** writes a private pasteboard
   (recommended, §7), which changes what a drive of any app that copies
   text does to the machine it runs on.
8. **An implementer and a date** (`rules/RULES.md`).
