## The idea

Contract made an app's UI a small, closed, declarative language: compiled at
bake, refused with a line and column, restarted in ~20 ms, the same on every
host. A game's *world* — what exists at tick 0 — is still Rust in `setup`.
The idea: author that world in a specialized language of the same spirit,
and keep Rust for what changes it.

## Why it is worth a look

Measured 2026-09-18 on Lanterns (`exact2-wt-lanterns`,
`game/games/lanterns/logic/src/lib.rs`):

- **289 of the logic crate's 583 non-blank lines construct the world** — a
  table, `setup`, five helpers. None of it is behavior.
- An edit to `setup` rebuilds the module, and a carried world does not
  respawn from it (`game/README.md`, "The world dev loop"): moving a lantern
  costs a rebuild *and* a restart; on a phone, a relaunch.
- `world:lantern-7` has no path back to the line that made it.
- A wrong name or field is a runtime `unwrap`, not a compile error.

1041.006 §7 answers with typed JSON and defers the language (§10 Q3).
Charlie, 2026-09-18: a proposal need not build on that work if reimagining
is better — **ergonomics and speed are the goals.**

## What binds every proposal

Rules, not preferences. The add-on stays an add-on: its own workspace, core
gains seams only, the five checks stay blind to it. The boot path compiles
nothing; the module loads after first pixel. The eight agent operations stay
eight. Same seed, inputs and clock ⇒ the same `world.hash()` on every host.
No editor application. Component types have one declaration authority,
whichever side holds it — nothing hand-kept in parallel (the rule
`kernel/tables/schema.json` follows). "No new Contract syntax until
formatting and navigation have landed" (NOT-DOING, 2026-09-10) governs
`.contract` files.

Everything else — file format, artifact, loader, how far past initial
conditions the language reaches — is the proposal's to argue.

## How proposals are compared

Each proposal renders **the same exercise**: Lanterns' world (those 289
lines) in its language, and the story of one edit — move `lantern-7` two
metres — on the web and on a phone. Then, in Charlie's order:

1. **Ergonomics.** Lines and concepts to author Lanterns; what an error
   looks like (span, all at once, did-you-mean); how an agent learns the
   vocabulary; entity → source; whether the running game can write back.
2. **Loop speed.** Save → visible in the running world, per host; whether
   play state survives; whether `cargo` is in the loop.
3. **Runtime.** Bytes added to the module; load time; nothing compiled at
   boot.
4. **Engine cost.** New lines, formats and seams — and what it deletes.
5. **Exit.** What is left, and what is lost, if the language is deleted.
