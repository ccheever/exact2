# LLP 1101.002: What the terminal still asks of Exact

**Type:** RFC
**Status:** Draft (r1)
**Systems:** The terminal host (`host/terminal`: its headless driver, pointer hit-testing, inline layers, its user-agent sheet), the kernel (closed layers' layout), the runner (retirement through collection windowing), Contract (a dialog's `close` event, a lint, `exactSurface` as the host's channel), the data seam (generated shapes, the shape-mismatch error), the gate (`default-members`), the harness (model attribution, no silent mock), `docs/agent-pitfalls.md`
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-10-06
**Implementer:** none yet
**Related:** LLP 1101 (terminal apps; accepted 2026-10-06), LLP 1101.000 (authoring in cells) and LLP 1101.001 (what the coding harness taught; r2 and its §7 measurements) with their reviews, LLP 1021 (dialogs: open state is the host's), LLP 1104 (a bare text field's user-agent sheet), LLP 1047.000 (collection windowing), LLP 1046.003 (`exactSurface`), LLP 1012 / LLP 1012.001.000 (the agent's operations; refusing a stale build). Evidence: `main` at `ce7c2a856` (the terminal landed) — `host/terminal/`, `apps/harness/`, `apps/todo/`.

## Summary

LLP 1101.001 r2 was built and measured. Then the terminal was made an
officially supported surface (Charlie, 2026-10-06). The work between r2 and
landing taught something LLP 1101.001 does not record. It covers:

- settling and retirement, wired end to end;
- `/clear`;
- the model picker in inline mode;
- the merge with main;
- a person using real models for the first time.

Most of this round's bugs were invisible to the tools used to look for
them. Several more came from state that only the host knew, and that the
kernel or the app needed. A few came from the seam between the screen and
the data module.

This document proposes sixteen changes, in four groups:

1. **Test what the terminal shows.**
2. **Let the host own what every app would otherwise repeat.**
3. **Close three Contract gaps the harness hit.**
4. **Fix the harness's honesty about which model is answering**, plus
   process lessons.

The four with the most leverage, which together would have caught or
prevented every bug Charlie met this round:

- a headless driver that runs the real writer against a virtual terminal
  (P1);
- the terminal's tests in the gate (P2);
- closed layers that do not lay out (P4);
- a terminal user-agent sheet for form fields (P7).

## 1. What happened

- **Five bugs got past the headless `print`.** Each was found by a person,
  or by replaying recorded bytes through `vt100`:
  - the model picker hung above the live region;
  - closed dialogs left blank rows that hid the prompt;
  - `/clear` left the old transcript on screen;
  - a second `/clear` problem (retirement had emptied the writer's printed
    set);
  - the inline mouse wheel used the full-screen frame's coordinates.
- **Merging main broke the terminal silently.** LLP 1104 gave a bare text
  field a visible sheet (border, pixel padding, radius, fill). The todo
  fixture's one-row input became three rows and its keyboard test failed.
  Nothing reported it until the merge, because the terminal's crates are
  outside `default-members`.
- **The person could not tell which model answered.** Charlie added an
  OpenRouter key, chose a model, and saw the mock's tour. The reply carried
  no attribution, and a model that could not be reached would have fallen
  back to `mock`'s text in the same voice. A direct test through his key
  answered "pong", so the route worked. What he selected is still unknown.
- **A stale binary failed opaquely.** A harness binary built before
  `shapes.contract` gained a field failed at boot with
  `Shape { resource: "session" }`. That names the resource, but not the
  field or the cure (rebuild).
- **Retirement is correct and costly to write.** Flat cost needed six
  pieces of app code (§4 P5). Every inline app would copy them.

## 2. Test what the terminal shows

**P1 — A virtual-terminal headless driver.**
- *What goes wrong today:* headless, `print` renders the whole document.
  The inline writer, which decides what a person sees, does not run at all.
  A correct `print` can coexist with a broken screen; Astra said so in the
  1101.001 review, and this round proved it five times.
- *The change:* a headless mode that runs the real loop:
  - against an in-memory `vt100` of the given size, with a scripted input
    stream;
  - with the virtual terminal answering cursor-position queries as a real
    one does;
  - with `print` and `screenshot` showing the virtual terminal's screen
    and scrollback.
- *The document view* stays, as its own verb. The writer test
  (`host/terminal/src/term.rs`, `writer`) and `examples/replay.rs` are
  that driver's first two pieces.
- *Recordings:* a drive can save its bytes. Parent D8 already makes the
  ten operations the interface, so this is how `tree`, `print` and
  `screenshot` are answered, not a new operation.

**P2 — The terminal's tests in the gate.**
- *The change:* add `exact-terminal` and `harness-data` to
  `default-members`.
- *Cost:* their tests are deterministic and headless, and take
  milliseconds. The HTTP test talks to a local stand-in server.
- *Why:* when the terminal was exploratory, keeping them out was right.
  Now an official surface can be broken by an unrelated change (LLP 1104),
  and only the async lane would notice, after the push.
- *Check before adding:* that `harness-data`'s tests stay offline when no
  key is set. They do today, through `Options::offline`.

**P3 — One painting answers every pointer event.**
- *What goes wrong today:* there are two coordinate spaces. Inline clicks
  are hit-tested against the live region's painting; the wheel was
  hit-tested against the full-screen frame, until a fix made it a third
  path.
- *The change:* the host keeps one record of the last presented painting
  in both modes, with its screen origin (inline, from the cursor-position
  answer). Every pointer event hit-tests against that one painting, so
  there is one function per event kind, not one per mode.

## 3. Let the host own what every app would repeat

**P4 — A closed layer does not lay out.**
- *The problem:* a dialog's or popover's open state is the host's (LLP
  1021), so the kernel lays a closed one out like any box. On the web, a
  closed `dialog` is `display: none` (the user-agent sheet's
  `dialog:not([open])`).
- *What it cost:* the harness first placed its dialogs in flow, so the
  closed ones took rows. That hid the prompt behind an open picker, and
  left most of the screen blank after `/clear`.
- *The workaround:* every dialog stays absolutely positioned. An app
  author cannot know that rule.
- *The change:* the host tells the kernel which layers are open (one bit
  per node, host state, never in the plan). A closed layer then lays out
  as `display: none`. This is every host's concern, not the terminal's:
  any host whose author puts a dialog in flow meets the same blank space.

**P5 — Retirement without the boilerplate.** Today a flat-cost inline app
writes:

- an `id` on each log child;
- a read of `exactSurface("terminal")`;
- a `task` that fires when the printed id changes;
- an action that sends `retire(id)`;
- a data-module `retire` that drops entries;
- an epoch key on the log, so `/clear` makes a new one.

Two parts can move:

- **The view half becomes the runner's.**
  - In inline mode, the host reports which log children are printed, and
    the runner stops mounting them. This reuses collection windowing
    (LLP 1047.000; LLP 1101.001 Q7). A printed child behaves like a
    windowed-out row, so the kernel tree stays a screen tall without the
    app's help.
  - The record keeps `printed`, so a data module that also wants to drop
    its snapshot can.
- **The rest becomes a documented pattern.**
  - The snapshot half stays the data module's, since only it knows what
    the model still needs.
  - The epoch key on the log (LLP 1101.001's `/clear`) goes into the
    guide with the pattern.

The 1101.001 done-when (flat nodes and memory after `/stress 3000`) is
the test for both halves.

**P6 — Inline layers have a stated rule.**
- *The rule:* an open layer in inline mode is placed below the live
  content and anchored to the region's bottom. The region grows downward
  into new rows (pushing older ones into scrollback), and never upward
  over printed rows. Those rows are the terminal's, and erasing them would
  delete them.
- *Where it lives now:* only in the writer.
- *The change:* LLP 1101 D10 says it. A layer taller than the screen
  scrolls inside itself (the harness's picker has a `max-height` and a
  `scroll`). The rule's reason should also be stated, because the first
  two implementations got it wrong.

**P7 — A terminal user-agent sheet for form fields.**
- *The problem:* LLP 1104's field sheet (border, pixel padding, radius)
  is not cell-shaped. The terminal profile checks only authored rows, so
  user-agent rows reach a terminal entry unchecked.
- *Evidence:* the merge broke the todo input. The harness's fields now
  say `appearance="none"`, as the repository's self-styled fields do,
  and every terminal app would have to.
- *The change:* a declared terminal sheet. A bare field is the bare box:
  no border, no padding, one row. The caret and placeholder are drawn by
  the host as now.
- *Precedent:* Grok's 1101.000 review proposed a declared terminal sheet
  (button text at `start`, rows `nowrap`). Forms are the case the merge
  proved.
- *Declaring it:* it is declared beside the reverse-video focus indicator
  as the terminal's deviations. The web layout oracle compares authored
  lengths, so it is unaffected.

## 4. Close three Contract gaps

**P8 — A dialog's `close` event.**
- *The problem:* the host closes a dialog on Escape or on a click outside
  (`closedby`), and the app is not told.
- *How it showed:* the harness's key dialog clears its draft on save, and
  again when `/key` opens it, but not on Escape. A key typed and then
  abandoned stays in the app's state until the dialog is opened again.
- *The change:* `close=` on `dialog`, fired by every way it closes, as
  HTML fires `close`. The host already knows each path.

**P9 — Generated shapes on the data side, and a useful mismatch error.**
- *The problem:* `harness-data` builds each record by position
  (`value.rs`), in `shapes.contract`'s field order. Adding `href`, `link`,
  `retired`, `queued` and `epoch` meant matching that order by hand.
- *The tool that exists:* `contract rust` generates typed shapes already.
- *The change:*
  - the harness uses generated shapes, so drift is a compile error;
  - a shape refusal at boot names the field that differs and suggests
    rebuilding the binary that answers it. That was the cure for this
    round's stale-binary failure.

**P10 — Lint `else` around a lone `when`.** The harness's renderers were
written as nine-deep `else` + `when` pyramids while `else when` existed.
LLP 1101.001 F6 records the author's mistake. A lint that suggests
`else when` when an `else` holds only a `when` would have caught it at
the first compile.

**P11 — `exactSurface` documented as the host's channel to the app.**
- *What it carried:* the terminal's record (mode, image protocol, colour
  depth, printed-through id). No new vocabulary was needed, and the
  runner's existing host record did the work.
- *The change:* the guide documents `exactSurface` for host facts in
  general, not only for GPU surfaces' published records. The next host
  fact should use it before anyone proposes a new source.

## 5. The harness, and process

**P12 — Say which model answered.**
- *Attribution:* when the model changes mid-session, the next reply's
  first line names it.
- *The mock:* its replies are labelled as the mock in their marker line.
  A person must be able to tell a scripted reply from a model's.

**P13 — Never fall back to the mock.** A chosen model that cannot be
reached (no key, unknown provider) is an error entry that says what is
missing. The default model at startup is the mock only when no provider
has a key; the harness already does that, and it is stated here.

**P14 — Release a stress batch in screen-sized pieces.**
- *The problem:* `/stress 3000` hands 3,000 entries to the screen in one
  answer, before any can print and retire: 1.5 s and 111,592 nodes at
  once (LLP 1101.001 §7).
- *The change:* release them in batches, each settling and retiring
  before the next. No real session appends that much at once, but the
  stress command should measure what it claims to.

**P15 — A pitfall: a sub-agent's crate joins the workspace once it
compiles.** A half-written crate in the root `Cargo.toml` broke every
build in the worktree for about ten minutes. This goes in
`docs/agent-pitfalls.md`.

**P16 — A launcher for "run it in a terminal".**
- *The problem:* opening the harness in a new Ghostty window
  (`open -na Ghostty.app --args -e …`) failed twice ("The terminal failed
  to initialize"), with nothing in the system log. That is not Exact's
  bug, but an agent asked to "run it for me" needs to know whether the
  app started.
- *The change:* a small script that launches the host in the person's
  terminal and confirms the process is running, or says it is not. It is
  new apparatus, so it waits for a human's yes.

## 6. Order

1. P2 (gate membership) and P7 (field sheet): small, and they stop the
   terminal breaking silently.
2. P1 (virtual-terminal driver) and P3 (one painting): the testing model.
3. P4 (closed layers), P8 (`close`), P6 (the stated rule): layers done
   properly on every host.
4. P5 (retirement's view half in the runner): after P1, so it is measured
   through the driver.
5. P9–P16 as their files are touched.

## 7. Open questions

- **Q1. Does P5's view half belong in the runner?** The alternative is
  an `exact:terminal` transcript component that hides the boilerplate.
  Moving it into the runner reuses windowing and helps any long list. A
  component is cheaper and local.
- **Q2. P7's sheet beyond forms.** Should it also cover buttons (`start`,
  not centred) and single-line rows (`nowrap`), as Grok proposed? Or
  should those stay authored, because they read as design choices more
  than as medium constraints?
- **Q3. Should P4's open bit be visible to the app**, for example as
  `:open`, or a value a view can read, since the app cannot know today
  whether its dialog is showing? P8's `close` event covers the transitions
  but not the initial state.
