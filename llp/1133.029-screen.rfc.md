## Summary

The roster's screen row (LLP 1133.000 §3.3) names three capabilities: the
Screen Orientation API's `lock`, the screen's brightness, and screenshots
(detecting them, and blocking capture where a platform can). Only the
first has an app that needs it now. This RFC builds that one and leaves
the other two out until a consumer asks (§12).

**An orientation lock is an attribute, held while its element is shown.**

```
canvas surface=world(seed=7, paused=paused) orientationlock=(tilt ? "current" : "none")
```

While any element that is mounted and displayed says `orientationlock`,
the session's window keeps to the orientations it names. The values are
the Screen Orientation API's `OrientationLockType`
([W3C](https://www.w3.org/TR/screen-orientation/), §2): `portrait`,
`landscape`, `portrait-primary`, `portrait-secondary`, `landscape-primary`,
`landscape-secondary`, `natural`, `any`; and one shared word, `current`,
which keeps whatever orientation the window has when the lock begins. When
no displayed element holds a lock, the app's manifest `orientation` applies,
as it does today.

It is the shape `wakelock="screen"` took for the Screen Wake Lock API (LLP
1125 D11), for the same reasons: a screen that unmounts or hides releases
its lock, so a lock cannot leak; and it is the platforms' own shape, since
iOS asks each full-screen view controller which orientations it supports
([`supportedInterfaceOrientations`](https://developer.apple.com/documentation/uikit/uiviewcontroller/supportedinterfaceorientations))
and whether it prefers the orientation locked
([`prefersInterfaceOrientationLocked`](https://developer.apple.com/documentation/uikit/uiviewcontroller/prefersinterfaceorientationlocked)).

Four decisions carry it:

- **It is exact2's vocabulary, not an extension** (D11). Whether an element
  is displayed is the runner's rule, and the window's orientation is the
  host's: the iOS root view controller, the Android activity, the page.
  A package would need both, and Beacons, the consumer, is a game, whose
  web host loads no extension modules.
- **A lock's types narrow the manifest and never widen it** (D3). iOS
  refuses a view controller whose orientations fall outside the app's
  Info.plist, which the manifest writes, so a type outside the manifest is
  refused at bake when it is literal and journaled when it is computed, on
  every host. `current` is the window's own orientation and is not bounded
  by the manifest: on an iPad or an Android tablet, where a portrait app's
  window turns, it holds the orientation the window has.
- **The lock in front wins** (D3). The topmost sheet's lock wins over
  what it covers, and a descendant's replaces its ancestor's, so a
  portrait app can show a landscape screen; locks on unrelated elements
  intersect, and locks that share no orientation hold none and are
  journaled. A lock inside a `dialog` or popover counts on no host.
- **`current` is a shared word** (D2), because Apple
  (`prefersInterfaceOrientationLocked`, iOS 26) and Android
  ([`locked`](https://developer.android.com/guide/topics/manifest/activity-element#screen),
  API 18) both have it and the web reaches it by locking to
  `screen.orientation.type`. It is also the one lock iPadOS 26 and Android
  16 honour on large screens (D5, D6).

The consumer is **Beacons**' tilt to move (LLP 1133.013 §10). A player
steering by tilting the phone tilts it far enough for the system to turn
the interface, and a turn mid-game swaps the axes of the screen frame the
tilt is read in. While tilt is on, the world's canvas locks the current
orientation (§9).

The cells: iOS and iPadOS, Android, the web (both targets), and Windows
(`SetDisplayAutoRotationPreferences`) apply the lock; macOS, tvOS, Linux and
the terminal have no screen orientation an app can lock, and say so once
in the journal (D12).

## 0. What is new here

1. **A second hold while displayed.** `wakelock` was the first: one
   boolean, ORed over the session's elements. An orientation lock has a
   value, so two holders can disagree; D3 says which one wins: the
   topmost sheet over what it covers, and otherwise the nearer
   declaration, as in CSS.
2. **A hold bounded by the bake.** The manifest's `orientation` decides
   what the iPhone's Info.plist allows, and UIKit throws
   [`invalidInterfaceOrientationException`](https://developer.apple.com/documentation/uikit/uiapplication/invalidinterfaceorientationexception)
   at a controller whose orientations it does not allow. So the module
   checks a lock against the manifest at bake, and every host checks it
   again at runtime.
3. **A word whose value only the host knows.** `current` is resolved by
   the host, at the moment the session's lock comes to include it; the
   runner never learns the screen's orientation.

## 2. Tier 1

### D1 — `orientationlock` on any element: a declared deviation in form

```
column orientationlock="landscape"
canvas orientationlock=(tilt ? "current" : "none")
```

The Screen Orientation API locks with a promise-returning call and
unlocks with another: `screen.orientation.lock(type)`, `unlock()` (§5.2,
§5.3). exact2 takes the API's types as the value of an attribute on any
element, held while that element is mounted and displayed. The web has
the capability and its words are kept; what departs is the call's form,
recorded as `wakelock` recorded the same departure from
`navigator.wakeLock.request("screen")` (LLP 1125 D11):

- **It cannot leak.** A lock taken by a call stays until something calls
  `unlock`, and a screen that is popped, hidden or replaced without doing
  so leaves the app locked. An attribute is released when its element
  stops being displayed.
- **It is the platforms' shape.** UIKit asks the window's root or topmost
  full-screen view controller for its orientations "when the device
  orientation changes" ([`supportedInterfaceOrientations`](https://developer.apple.com/documentation/uikit/uiviewcontroller/supportedinterfaceorientations)):
  a statement per screen, not a command. The manifest's `orientation` is a
  statement too.
- **It needs no handler.** A lock's failure is the platform's decision
  (D5–D8), journaled once and readable by the agent (§8); a view shows
  nothing different when a lock is refused, so no Contract code waits on
  the promise.

The attribute is lowercase, one word, beside `wakelock`. `"none"` is the
default and holds nothing. The compiler's did-you-mean table maps the
names an author or an agent may reach for (`screenOrientation`,
`lockOrientation`, `orientation`, `requestedOrientation`,
`supportedInterfaceOrientations`, `screen-orientation`) to it, as it maps
`keepScreenOn` and `idleTimerDisabled` to `wakelock`
(`contract/lower/src/tags.rs`).

### D2 — The values

| Value | Means | Source |
|---|---|---|
| `portrait` | either portrait | `OrientationLockType` |
| `landscape` | either landscape | the same |
| `portrait-primary`, `landscape-primary` | the device's own portrait or landscape: angle 0 or 90 on a phone, whose natural orientation is portrait | the same; §2.1, §2.2 |
| `portrait-secondary`, `landscape-secondary` | the opposite of the primary one | the same |
| `natural` | the device's natural orientation: portrait on a phone | the same |
| `any` | no narrowing: the manifest's orientations (D3) | the same, bounded by D3 |
| `current` | the one orientation the window has when the lock begins (D3) | a shared word: Apple's `prefersInterfaceOrientationLocked`, Android's `locked` |
| `none` | holds nothing | `wakelock`'s `"none"` |

**`current` is a shared word** (LLP 1133 D1: a feature several of the
module's platforms share and the web lacks, named once in the web's
style). The web has no lock type for it, but its idiom is
`screen.orientation.lock(screen.orientation.type)`, which the web cell
uses (D7). Apple's preference "to lock the scene's interface
orientation" keeps the orientation the scene has; Android's `locked`
"locks the orientation to its current rotation, whatever that is" ([the
activity element](https://developer.android.com/guide/topics/manifest/activity-element#screen)).
A game steered by tilt wants exactly this: whichever way the player is
holding the phone when the steering starts.

A literal outside the table is refused at bake, by name, with the table's
words. A computed value outside it is journaled (`view N: invalid
orientationlock value "…"; unset`) and holds nothing, as `wakelock`'s is.

### D3 — Which lock holds

**The holders** are the elements that are mounted and displayed, by
`wakelock`'s rule (`exact_runner::wakelock::displayed`: no ancestor
`display: none` or covered whole by its host, under no tab the navigation
leaves unselected and no screen a stack keeps under its top), outside
every `dialog` and popover, whose `orientationlock` is a word other than
`none`.

**A top-layer box holds no lock.** Whether a `dialog` or popover is open
is the host's state, not the tree's: the host opens it by command
(`showModal`) after the batch is built, and the runner hears of it only
afterwards (`top_layer_frames`; "the host stays the source of truth for
what is open", `runner/src/geometry.rs`). And on every host but iOS and
tvOS a closed box is laid out and hidden by its views
(`host/apple/src/closed.rs`), so `displayed` counts what is inside it. A
lock in one is refused at bake (`orientationlock-in-top-layer`), and one
the bake cannot see is journaled once and not counted. A dialog over a
locked screen leaves the lock as it is, as an alert or a form sheet does
over a screen a hand-built app has locked.

**What a sheet covers stays displayed.** A sheet route
(`navigationPresentation="modal"`) shows what it sits over: the page and
every sheet between it and the top (`host/web/navigation.js`, `covered`),
and the split's list beside the page when the page is a split's detail
in a pane. `under_a_sheet` in `runner/src/head.rs` names only the route
just beneath the top today, so the displayed rule and the web disagree
for a sheet over a sheet; stage 0 widens it to the web's set (§11). A
boolean wake lock does not care which of them count; a lock with a value
does, so three rules, in order, decide which holders count.

1. **The topmost sheet that holds wins.** Of the routes a stack shows (the
   page, the sheets over it, the top), the holders in the topmost route
   that has a holder count, and those in the routes beneath it, and in
   the split's list beside them, do not. A sheet that holds nothing leaves the
   lock beneath it in force, so a sheet slides over a locked screen
   without turning it. Stack routes are siblings in the tree
   (`docs/recipes/navigation-stack.md`), so this rule, not nesting, is what
   lets a sheet's lock win.
2. **The nearest holder wins.** Of the holders left, one with a holder
   among its descendants is overridden by it: a portrait app's root says
   `orientationlock="portrait"`, a screen under it says `"landscape"`, and
   while that screen is displayed the window is landscape. This is how an
   inherited CSS property's nearer declaration replaces an ancestor's, and
   what lets a subtree release its ancestor's lock: `any` there means "this
   subtree takes the manifest's orientations". A pushed screen needs
   neither rule: the stack hides the screen under its top.
3. **Unrelated holders intersect.** The holders left, none covering or
   containing another (a split's list and detail side by side with no
   sheet over them, two panes of a page), each name a set (D2); the
   session's lock is their intersection, bounded as below.

**A conflict holds none.** When the intersection is empty, **no lock
holds** and the manifest's orientation applies; the journal says
`orientationlock: conflict: view 12 "portrait", view 30 "landscape"; none
held`, and `state.orientationlock.conflict` names the holders. A conflict
is an authoring error, and holding none is the answer that leaves the
person able to turn the device. Who finds it depends on what it needs:
the runner finds one among types alone; the host finds one that only its
resolution reveals (`current`, `natural`, or a set this device cannot
show, below), journals the same line and reports it in its readback,
which the agent's state carries (§8).

**What the runner decides and what the host decides.** The runner knows
the tree; the host knows the device. The runner computes the holders
under the three rules, their words, and the intersection of the words
that need no device (the types other than `natural`), and sends the host
one batch field: `none`, or that set with the device-dependent words
beside it and each holder's view and words, which a conflict line the
host writes names. The host resolves `current` and `natural`, intersects
with the orientations its window can take (below), decides a conflict
the runner could not see, and applies the result in the same main-thread
turn as the batch, before the frame the batch draws is presented. The
web's two targets run the runner's half in `orientationlock-glue.js`, as
`wakelock-glue.js` runs the wake lock's, from the same test table (§10,
stage 0).

**`current` is captured once a hold.** The host reads its window's
orientation when the session's lock comes to include `current`, and keeps
that value while any counted holder says `current`, whether or not the
platform applies it at the moment: a web page's re-ask after fullscreen
or visibility (D7), and an iPad's lock that the system lifted and may
restore (D5), reuse it. A re-render, or a holder replaced by another that
also says `current`, does not capture again; a release and a new lock
does. With `current` beside other words, the captured orientation is one
more set in the intersection.

**A lock narrows the manifest and never widens it.** The manifest's
`orientation` (`app.json`) is the app's set, mapped per device as it is
today: on the iPhone, Info.plist's `UISupportedInterfaceOrientations`
(`orientationKeys`, which maps every portrait to upright, the only
portrait an iPhone with Face ID offers); on the iPad all four, which its
multitasking requires; on Android, the activity's `screenOrientation`;
on the web, the manifest's member.
UIKit compares a view controller's orientations "with the app's supported
orientations — as determined by the Info.plist file"
(`supportedInterfaceOrientations`) and throws
`invalidInterfaceOrientationException` at an invalid set. Android and the
web could widen past their manifest, but the same author writes for all
three, so the rule is one:

- **The host enforces it.** Before any platform call, the host intersects
  the lock's types with the orientations its window can take: the
  manifest's value as this device maps it wherever a type is applied (the
  iPhone, an Android phone, the web). An iPad and an Android screen 600 dp
  wide apply no type (D5, D6), and their window takes all four whatever
  the manifest says, except under a `natural` manifest on Android, which
  maps to `nosensor`, a value Android 16 still honours there. `current` is the orientation the window has, inside
  that set by construction, and is never intersected with the manifest:
  on an iPad or a tablet it is the one lock that works, in a portrait app
  turned landscape too. An empty result holds nothing and is journaled
  (`orientationlock: "portrait-secondary": this device does not show it`).
  This check, not the bake's, is what keeps UIKit from throwing.
- **The bake catches the plain mistake.** A literal value whose set is
  disjoint from the manifest's value can hold on no device (a phone
  bounds it out, a tablet applies no type), so it is refused
  (`orientationlock-outside-manifest`: `"landscape"` in an app whose
  manifest says `portrait`), with the fix: widen the manifest and lock
  the screens that need portrait. A literal that only some devices cannot
  show (`portrait-secondary`, which an Android phone shows and an iPhone
  does not) passes the bake and is the host's.
- Without a manifest `orientation`, the set is the platform's default: on
  the iPhone portrait and both landscapes (Apple's default for the iPhone
  idiom is `allButUpsideDown`), on the iPad all four, on Android and the
  web all four.

**One window, one lock.** A session presents into one window and locks
that one; an iPad's scenes each have a session and each lock separately.
A session embedded in another app's view controller (LLP 1031's sample
host, an ExactKit embedder) does not own its window: its lock is journaled
once (`orientationlock: the window is the embedder's`) and not applied.

**What the host shows as its own control holds nothing natively,** as with
`wakelock`: a header the host draws as its navigation bar, a confirmation
as a native alert, a menu as a native menu are covered whole, so a lock
written on one of them holds on the web and not natively
(`runner/src/wakelock.rs`). A lock belongs on the screen's content.

### D4 — Unsaid defaults are the platform's

| Unsaid | What happens | Source |
|---|---|---|
| no lock | the manifest's orientation; with none, the platform's default (D3) | Apple's `supportedInterfaceOrientations`: "all for the iPad idiom and allButUpsideDown for the iPhone idiom"; Android's `unspecified`: "the system chooses the orientation" |
| how a forced turn looks | the platform's rotation animation | Apple: `setNeedsUpdateOfSupportedInterfaceOrientations()` "animates any changes to orientation" |

## 3. Each platform

### D5 — iOS and iPadOS

The host's root view controller answers the session's lock, and so does
every controller the host presents that UIKit may ask: `ModalController`,
in its full-screen kind and as an iPhone page sheet; `DialogSheetController`,
a `dialog`'s `.pageSheet` (`DialogSheetIOS.swift`); and any container UIKit
forwards the question to. UIKit asks "the root view controller or the
topmost modal view controller that fills the window", and a presented
controller's default is not its presenter's answer; `ModalController`
already answers the status bar's style for this reason (LLP 1105 D6),
and `DialogSheetController` does not yet. So a dialog over a locked
screen leaves the lock (D3) on iOS too.

| Lock | iPhone, iOS 17 to 25 | iPhone, iOS 26 and later | iPad, iPadOS 26 and later | iPad before 26 |
|---|---|---|---|---|
| a set of types | `supportedInterfaceOrientations` returns its mask (the manifest's mapping, `phoneOrientations`); `setNeedsUpdateOfSupportedInterfaceOrientations()`; when the scene is outside the mask, `requestGeometryUpdate(.iOS(interfaceOrientations:))` turns it | the same | not applied: "multitasking apps must support all orientations", so UIKit does not ask (`supportedInterfaceOrientations`), and exact2's iPad apps support all four (`IPAD_ORIENTATIONS`) | not applied, the same reason |
| `current` | the mask of `effectiveGeometry.interfaceOrientation` at resolution | `prefersInterfaceOrientationLocked` true, then `setNeedsUpdateOfPrefersInterfaceOrientationLocked()` | the same; the system locks only while "the scene is centered on the screen", "the same size as the screen" and "not occluded by another scene", and lifts it when one stops being true ([`prefersInterfaceOrientationLocked`](https://developer.apple.com/documentation/uikit/uiviewcontroller/prefersinterfaceorientationlocked)) | not applied |
| readback (`state.orientationlock.applied`) | the mask returned and the scene's orientation | `effectiveGeometry.isInterfaceOrientationLocked` ([Apple](https://developer.apple.com/documentation/uikit/uiwindowscene/geometry/isinterfaceorientationlocked)) and the scene's orientation | the same | `"unavailable"` |

`portrait-secondary` is outside the iPhone's set (Info.plist omits
`UIInterfaceOrientationPortraitUpsideDown` on the iPhone, as Apple's
default does), so on the iPhone it is refused by D3's check. The iPad
cells are the platform's answer, not a gap: Apple deprecated opting out of
multitasking in iPadOS 26 ([`UIRequiresFullScreen`](https://developer.apple.com/documentation/bundleresources/information-property-list/uirequiresfullscreen),
"Use a combination of UISceneSizeRestrictions and
prefersInterfaceOrientationLocked"), and an iPad app that locks to a
type is the tell. On an iPad, `current` is the lock that works, and only
in full screen.

**tvOS** has no interface orientation (`TouchIOS.swift` says so): the
shared Swift compiles the lock out there and journals once
(`orientationlock: this host has no screen orientation`).

### D6 — Android

The reader's activity's `requestedOrientation`, through a new request
kind beside kind 8 (`wakelock`, `Requests.kt`), told when the lock changes
and anew to a reader made again:

| Lock | `setRequestedOrientation` |
|---|---|
| `portrait`, `landscape`, `-primary`, `-secondary`, `natural`, `any` | the manifest's mapping in `build.gradle.kts`, reused: `sensorPortrait`, `sensorLandscape`, `portrait`, `landscape`, `reversePortrait`, `reverseLandscape`; `natural` the panel's own axis as `MainActivity.naturalOrientation()` resolves it; `any` the manifest's own value |
| a set of several types (an intersection) | an intersection of types is one orientation, a portrait or landscape pair, or all four, and each has a value above (`fullUser` for all four) |
| `current` | `SCREEN_ORIENTATION_LOCKED`, which "locks the orientation to its current rotation" |
| none | the activity's value from the manifest, restored; for `natural`, the axis `naturalOrientation()` resolved at launch |

**Large screens.** exact2's Android target is API 36
(`host/android/app/build.gradle.kts`), and for such apps "orientation,
resizability, and aspect ratio restrictions no longer apply on displays
with smallest width >= 600dp" ([Android 16 behaviour changes](https://developer.android.com/about/versions/16/behavior-changes-16)):
`portrait`, `landscape`, their `reverse`, `sensor` and `user` forms and
`setRequestedOrientation` with them are ignored there. Android 17 removes
the temporary opt-out ([Android 17](https://developer.android.com/about/versions/17/changes/ff-restrictions-ignored)).
`locked`, `nosensor` and `unspecified` are not on the ignored list, so
`current` holds on a tablet and an explicit type does not, as on the iPad;
the readback says which. Games are exempt "based on the
android:appCategory flag", which exact2 does not set (§12).

**Multi-window:** "in multi-window mode, the requested orientation does not
act as a suggestion for the overall orientation" ([the activity
element](https://developer.android.com/guide/topics/manifest/activity-element#screen));
the readback is the activity's request, and the journal says nothing
more, since the platform decides.

The reader handles orientation as a configuration change itself
(`configChanges` includes `orientation` in `AndroidManifest.xml`), so a
turn the lock causes recreates no activity.

### D7 — The web, both targets

`orientationlock-glue.js`, shared by the JS target and the wasm host as
`wakelock-glue.js` is, loaded after first paint and only for a plan that
binds the prop (`exact_runner::wakelock::bound`'s test, for this prop):

- A lock: `screen.orientation.lock(type)` for one type, the narrowest
  covering type for a set, and `screen.orientation.lock(screen.orientation.type)`
  for `current`. None: `screen.orientation.unlock()`.
- **The browser's pre-lock conditions decide.** "A user agent MUST restrict
  the use of lock() to simple fullscreen documents" (Screen Orientation
  §9), and a fullscreen exit unlocks. The glue asks again on
  `fullscreenchange` into fullscreen and on `visibilitychange` to visible,
  while the lock is held, as the wake lock glue asks again.
- **Support.** Chrome and Firefox on Android lock (Firefox since 144);
  desktop Chrome "always throws `NotSupportedError`"; Safari has no
  `lock()` on macOS or iOS
  ([browser-compat-data](https://github.com/mdn/browser-compat-data/blob/main/api/ScreenOrientation.json)).
  Each refusal is journaled once by its DOMException name
  (`orientationlock: unavailable: NotAllowedError`), and the readback
  holds whether the last lock resolved.

So on the web a lock holds only in fullscreen, which is the web's own
rule: a page that is not fullscreen does not take the screen's
orientation from the person.

### D8 — Windows

[`SetDisplayAutoRotationPreferences`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setdisplayautorotationpreferences)
"sets the screen auto-rotation preferences for the current process"
(Windows 8 and later), with [`ORIENTATION_PREFERENCE`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ne-winuser-orientation_preference)
flags: `portrait` the portrait and flipped portrait flags, `landscape`
both landscape ones, `-primary` and `-secondary` one each, `natural` the
panel's own (`DMDO_DEFAULT` of [`DEVMODE.dmDisplayOrientation`](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-devmodea)
read with `EnumDisplaySettingsW`), `current` the flag of the display's
present `dmDisplayOrientation`, none `ORIENTATION_PREFERENCE_NONE`. It
matters on a convertible or a tablet; a desktop monitor does not turn by
itself. The readback is `GetDisplayAutoRotationPreferences`. A
preference is per process, so with two windows the host applies the
focused window's session's lock.

## 4. Tier 2, tier 3, and the ceiling

### D9 — Tier 2 and tier 3

**Tier 2: none now.** The platform words a lock could take are Android's
`user*` forms (`userPortrait`, `userLandscape`, `fullUser`, which follow
the person's own rotation lock), Android's `fullSensor`, and Apple's
`preferredInterfaceOrientationForPresentation`. None has a consumer, and
the `user*` forms are among those Android 16 ignores on large screens. A
dotted platform word on an attribute (`orientationlock.android=`) would
be the first of its kind and waits for one (§12).

**Tier 3: the window hatch,** which exists (LLP 1075.003; `window(_:)` in
Swift, `window(w)` on the web). The module adds no object. Its ownership
list: **the host owns** the root and full-screen controllers'
`supportedInterfaceOrientations` and `prefersInterfaceOrientationLocked`
(Apple), the activity's `requestedOrientation` (Android), the process's
auto-rotation preference (Windows), and the page's lock (web), and writes
each when the session's lock changes. An app's native code that writes
one is overwritten at the next change, and a development build journals
the difference it finds then (`orientationlock: requestedOrientation was
changed outside exact2`), detection rather than enforcement (LLP 1133 D3).

### The ceiling test

| Use | Tier |
|---|---|
| lock a screen to portrait or landscape, or one side of either | 1 |
| lock the orientation the person is holding (tilt steering, a camera's capture, a level) | 1 (`current`) |
| a landscape screen in a portrait app; a subtree free of an ancestor's lock | 1 (D3's nearest holder, `any`) |
| release on leaving the screen | 1 (displayed) |
| the app-wide default | the manifest's `orientation`, built |
| widen past the manifest at runtime by a type (a portrait-manifest app locking `landscape`) | none, on purpose: D3; widen the manifest and lock the screens instead. `current` on an iPad or a 600 dp Android screen a portrait app has turned holds the orientation it has (D3) |
| follow the person's rotation lock (`user*`), `fullSensor` | none; out until a consumer asks (D9) |
| the presentation orientation of a modal | none; out until a consumer asks |
| read the screen's orientation and its changes in Contract or data code | none; out until a consumer asks (§12); a package reads the context's angle today |
| an explicit type on an iPad or an Android tablet | none: the platform refuses it (D5, D6) |

## 5. Permission, origins, grant

### D10 — No permission; the origin is not consulted; no grant

**No permission.** No platform asks the person before an app locks its
orientation: none of the APIs above has an authorization, and the web's
gate is fullscreen, which the person enters. So LLP 1133.002 D6–D12 does
not apply: there is no state to read and nothing to ask.

**Origins.** The inherited rule is that a tool invocation or a wake cannot
start a device or open a prompt (LLP 1133 D6 rule 3; LLP 1133.008 D8 item
2). A lock does neither: it is presentation, like the screen a tool may
already display. So the origin of the commit that displays a holder is
not consulted, and a tool that opens a landscape screen opens it in
landscape. A wake's headless session (LLP 1133.017) presents into no
window and locks nothing.

**No grant.** No manifest declares anything for it (no Info.plist key,
no Android permission, no Windows capability), so it needs no grant line
(LLP 1069.008). The manifest's `orientation` is its bound, not its grant.

## 6. Packaging and callers

### D11 — exact2's vocabulary, and why

LLP 1133 D5 makes a module an extension unless it needs what only the
runner, the kernel or a data executor has, and asks the RFC for its reason.
This one has three:

1. **Which elements are displayed is the runner's.** The rule is
   `wakelock`'s, over the kernel's tree, host covers and the navigation's
   hidden routes. A package learns "displayed" only for its own views (LLP
   1133.008) and the canvases it feeds (LLP 1133.013 D12 item 3); an
   attribute on any element is outside both.
2. **The window is the host's.** The iOS root view controller and the
   Android activity are the presenter's, and every full-screen controller
   the presenter makes must answer the same lock. A package would need a
   seam into all of them, and that seam is this module.
3. **The consumer is a game,** whose web host is the wasm host, which
   loads no extension modules (LLP 1133.013 §13, the canvas seam's note); its glue
   loads `wakelock-glue.js` today and would load this module's the same way.

A package form, `lockOrientation(type)` and `unlockOrientation()` sends on
`@exact/screen`, was rejected: it leaks (D1), and its `unlock` has no
caller when a screen is popped.

**Callers.** Contract writes the attribute on any element. Data code has
no surface: a lock belongs to what is shown. The agent reads
`state.orientationlock` (§8). Nothing is `sync`, a request, or a source.

### D13 — Cost

An app that does not write `orientationlock` gains nothing: the web glue
is bundled only for a plan that binds the prop, and the native code is a
branch on a batch field that stays `nil`. An app that does gains, on the
web, one module of under 2 KB loaded after first paint at the first lock;
natively, about a hundred lines of host code that every app links, as
`wakelock`'s are. Nothing runs before first pixel beyond reading the first
batch, which the presenter reads anyway; the boot count does not change.
Stage 0 measures the glue with LLP 1047's probe.

## 8. The substitute

There is nothing to substitute: the lock asks no service, shows no
prompt, and reads no device. Under the agent it is applied for real, as
`wakelock` is, so a drive sees the platform hold it. What the agent adds is
readback (LLP 1069.007 D7's paragraph):

- **`state.orientationlock`** on every host's driver: `{held, by, words,
  lock, conflict, applied}`, where `by` is the counted holders' view ids
  (D3's three rules) in tree order, `words` their values, `lock` the
  runner's batch field, `conflict` the holders of a conflict, whichever
  side found it, or null, and `applied` the host's readback (D5–D8): the
  orientations it asked the platform for, whether the platform holds them
  (`isInterfaceOrientationLocked`; the scene's or display's orientation
  after a turn; a web lock's promise, cleared when fullscreen ends), and
  why not when it does not. A request is not an effect: a drive judges a
  lock by the orientation the window keeps, and reads `applied` for why.
  `orientationlock` joins the agent's reserved state names
  (`contract/cli/src/modules.rs`).
- **Turning the device:** on the iOS simulator, the touch runner's
  `orientation` op (`host/apple/touches.swift`), and `layout`'s
  `screen.orientation` reads the scene's orientation after it; on the
  Android emulator, `adb emu rotate`.
- **No `prefer`:** there is no fact to set. A drive that needs another
  orientation turns the device.

## 9. The consumer: Beacons

Beacons' tilt to move (LLP 1133.013 §10) reads gravity in the `screen`
reference frame, whose x and y follow the screen's orientation. A player
holds the phone at a comfortable angle, sets that as level, and tilts to
walk. The system turns the interface "when the device orientation
changes" (`supportedInterfaceOrientations`), and a player tilting to steer
changes it: the further they steer, the nearer the phone comes to the
next orientation. A turn mid-game rotates the HUD under their thumbs and
swaps the frame's axes against the tilt they hold. A hand-built tilt game
keeps its orientation while it is steered, and the platforms' word for
that is the one this module calls `current`.

Beacons gains one attribute, on the world's canvas:

```
canvas surface=world(seed=7, paused=paused, restart=again) testId="world" … orientationlock=(tilt ? "current" : "none")
```

So the lock begins when the player turns **Tilt to move** on (in the
pause panel, before Resume), in whatever orientation they are holding the
phone, holds through play and pause, and ends when they turn tilt off or
leave the game's screen. Beacons has no manifest `orientation`, so D3's
bound is the platform's default and `current` is always inside it.

## 12. What stays out, each until a consumer asks

**Brightness.** No app in the repository shows a code to be scanned or
anything else that needs the screen brighter, and QR codes are themselves
out (`rules/DEFERRED.md`, LLP 1125's entry). For the next RFC, the shape
this module's form suggests is another hold while displayed, since the
platforms scope it so or need restoring: Android's window
`screenBrightness` (per window), iOS's `UIScreen.brightness` ("Brightness
changes remain in effect until the person locks their device, even if the
person closes your app", [Apple](https://developer.apple.com/documentation/uikit/uiscreen/brightness)),
so a hold would restore it on release and on leaving the foreground;
absent on the web (the Screen Wake Lock group's brightness proposals,
[w3c/screen-wake-lock#129](https://github.com/w3c/screen-wake-lock/issues/129),
shipped nothing), macOS and Linux; Windows' `BrightnessOverride` is a
WinRT API whose `GetForCurrentView` "requires CoreWindow"
([Microsoft](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.display.brightnessoverride)).

**Screenshots and capture.** No app needs them now. What each platform
offers, for the RFC that takes them:

The one candidate consumer in the repository is Excord's lock (LLP
1133.010 §9): with Lock Excord on, the app switcher's snapshot still shows
the conversation the person left, since the lock covers the screen only
on return. Apple's guidance above says to remove it. That is a feature
proposal for Excord, not a need it has stated, so §13 question 2 asks.

**Also out:**

- reading the screen's orientation (`screen.orientation.type`, `angle`, its
  `change`) in Contract or data code: no consumer. A package reads the
  context's angle today (LLP 1133.013 D12 item 4); a source would read the
  same, with no new host code;
- widening past the manifest at runtime (D3);
- a lock in a `dialog` or popover (D3): it would need the host, which
  alone knows what is open, to decide the holders as well, and no
  consumer has a dialog that must turn the screen;
- Android's `user*` and `fullSensor` forms, Apple's
  `preferredInterfaceOrientationForPresentation`, and dotted platform words
  on an attribute (D9);
- `android:appCategory="game"` for exact2's games, which would exempt them
  from Android 16's large-screen rule (D6). It is a manifest decision for
  every game, not this module's (it also changes how Play lists the app);
  QUEUE.md records it.

and the Inhibit portal's idle flag on Linux ([portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Inhibit.html)).
