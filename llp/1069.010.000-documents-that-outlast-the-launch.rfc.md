## 1. Summary

A document app needs two things from the files a person chooses that Exact
does not give it.

**Stage 1: keep up with a chosen document, and save without clobbering it
(D1–D2a).** `storage.fs.watch(path)` in an answer makes the runner ask that
answer again when the path changes on disk, as LLP 1016.002 does for a
device topic. A write can carry what the app last read
(`{ expect: stat }`) and is refused if the file has changed since. Both are
session-scoped, under the grants the app already holds.

**Stage 2: reopen what the person chose after a relaunch (D3–D7).** The host
keeps the exact file or folder a person chose, in a bounded list the
platform already shows as recents where it has one, persisted as the
platform persists such a choice (a security-scoped bookmark on Apple, a
`FileSystemHandle` in IndexedDB on the web). A kept document's `doc:` path
stays valid across launches. The app opts in with `doc.keep`; the person can
revoke from outside the app on every host. This admits a durable capability
grant, narrowly, so it needs Charlie's DEFERRED ruling.

## 2. Motivation

**Exact Draw** edits Excalidraw drawings on disk: a Contract shell (file
explorer, recents, search) around an embedded editor. It needs recent files
and folders that reopen with one click after a relaunch, and it needs to
show a drawing that another program changed, without losing either side's
work. Exact gives neither, so it runs a Bun companion with absolute paths
and its own watcher, which is unsandboxed, cannot ship in the Mac App Store,
must be started and stopped with the app, and is what every document app
would rebuild.

**The readers and studio.** The Markdown and LLP readers lose their
document at relaunch (LLP 1069.010 §Motivation), and reopen only through File
▸ Open Recent on macOS. Studio (LLP 1069.010, "the document window") saves
explicitly, so a file changed under it is overwritten at its next save.

**Why narrowly.** `rules/DEFERRED.md` refuses durable capability grants
because a permission that outlives the session needs a store, revocation and
rules for files that move, and each platform does it differently. A
document a person chose is the one durable grant every platform already
models, with a store, a revocation and move rules of its own: Apple's
security-scoped bookmarks and recents, the web's persisted
`FileSystemHandle` and its permission prompt, the freedesktop recent-files
list. LLP 1069.010 Q2 ruled that nothing should make the sandboxed form
harder. This RFC takes exactly that path and nothing wider.

## 3. Stage 1: changes to a chosen document

### D1 — A watch is a topic; the answer stays a pull

An answer that calls `storage.fs.watch(path)` depends on `path`, and the
runner asks that resource again when it changes on disk. It is LLP
1016.002's `native.watch(topic)` with the path as the topic, and keeps that
LLP's rules: the change carries no value; the source reads again; changes
before the host applies them coalesce into one re-ask; a request in flight
lands first, then the resource is asked again (1016.002 D4); a fresh answer
replaces the resource's watches.

```ts
export const grants = 'fs.read doc:/';
// answer: the folder's drawings, listed again when an entry changes
await storage.fs.watch(folder);
return (await storage.fs.readdir(folder)).filter((n) => n.endsWith('.excalidraw'));
```

- **Scope, as Node's `fs.watch` has it:** a file's watch covers the file; a
  folder's covers its own entries (created, removed, renamed, written).
  `watch(path, { recursive: true })` covers the whole subtree, for an
  answer that reads the subtree. An app watching a large tree under churn
  watches the folders it shows, not the root.
- **What it covers:** `doc:` paths, under `fs.read doc:/` (watching is a
  read). Not `app:/`: nothing outside the app writes there, and two windows
  of one app already tell each other through 1016.002 topics.
- **What "changed" means:** something in scope was created, written,
  removed or renamed, by any process, including this app. The answer reads
  again and compares. A change the app made itself re-asks too: one read,
  and one rule for every writer.
- **The document itself moving or vanishing** re-asks, and the read reports
  what any read would (`ENOENT`).
- **What it does not do:** tell an editor that its save would overwrite
  someone else's (D2a does), or merge the editor's unsaved work with the
  new file (the app's; Exact Draw keeps its scene and offers the choice).

*Rejected:* an event stream (Node's `fs.watch` events, the web's
`FileSystemObserver` records, LLP 1016.000's value streams). The platforms
disagree on events: FSEvents coalesces by directory, inotify reports per
inode and misses an atomic replace it is not watching the folder for, the
web reports `appeared`/`modified`/`moved`. "Something in this scope
changed" is what each can say truthfully, and the answer stays the single
source of what the app shows. *Rejected:* a changed-path hint beside the
re-ask; the scoping above gives a large tree the same economy without a
second channel that hosts would fill differently.

### D2 — What each host watches with

| Host | Mechanism | Notes |
|---|---|---|
| macOS | FSEvents on the retained folder, file-level events | Survives atomic replace (a new inode at the same name), which a vnode source on the file does not |
| iOS | `NSFilePresenter` on the document's URL, plus a dispatch vnode source for local files | iOS has no FSEvents; a file provider's (iCloud Drive, Files) changes arrive through file coordination |
| Web | `FileSystemObserver` where the browser has it | Elsewhere a watch is accepted and never fires; `exactPage().canWatchFiles` says which, as `canOpenFiles` does for pickers |
| Linux | inotify on the retained folder | |

The host announces from any thread; the runner's queue (1016.002 D3)
applies it at the next pump. Under the agent, `state.watches` lists the
watched paths and the substitute can announce one (`changed <path>`).

### D2a — A write that expects what it read

`writeFile`, `atomicWriteFile` and `appendFile` on a `doc:` path take
`{ expect }`: the `stat` the app last read (its `modifiedMs` and `size`).
If the file on disk no longer matches, the write is refused with `ECHANGED`
and nothing is written; a file that is gone refuses `ENOENT`. The app then
reads the new file and decides: offer to keep either version, or save its
own under another name. It is HTTP's `If-Unmodified-Since` on a file. The
check and the write are not one atomic step on any of these file systems,
so a write in the instant between them is still possible; what it closes is
the window that matters, minutes of editing. Without `expect` a write is
today's. The web's `FileSystemWritableFileStream` has no precondition; the
glue checks `getFile().lastModified` first, the same check. A declared
deviation: no web or Node name exists.

## 4. Stage 2: documents that outlast the launch

### D3 — Only the person's exact choice is kept

When an app granted `doc.keep` receives a document **the person chose**, the
host keeps that item, exactly:

- **Kept:** a file or folder chosen in a picker (`showOpenFilePicker`,
  `showDirectoryPicker`, a written `showSaveFilePicker`), opened from the
  system (Finder, Open With, ⌘O, Open Recent, the web's `launchQueue`,
  Files "Open in"), or dropped.
- **The file, not its folder.** A system route delivers a file beneath a
  handle to its folder (LLP 1069.010 slice 3, "The routes"), so a reader can
  list its siblings this session. The kept entry is the file alone, as
  the App Sandbox would mint it; the folder handle ends with the session. A
  folder is kept only when the person chose a folder.
- **Never kept:** a path typed into the `open-file` field, a followed link,
  a path reached beneath a handle, and anything the agent answered. Under
  the agent the kept set is the drive's scratch store, never the person's.
- **With its mode:** read, or read and write, as the choice granted it on
  that platform (a save picker grants writing; the web records the
  permission it was given). A later write grant in the app's code does not
  widen a kept read.

### D4 — Three lifetimes, and one identity

**Live access, reopening and the recents shown are separate:**

- **Live access** is today's session handle: it lasts while a session holds
  the document, whatever happens to the list.
- **Reopening** is the kept entry: after a relaunch the document's `doc:`
  path resolves again, in any window of the app. A kept handle belongs to
  the app, not to one session.
- **The recents shown** is the bounded list the platform shows (D6). An
  entry that falls off the end of that list is no longer reopened after the
  next relaunch, but a session that has it open keeps it.

**A kept document keeps its path.** Its `doc:/<n>/<name>` stays valid across
launches: `<n>` comes from a counter the host persists and never reuses. An
app keeps the path wherever it keeps state and reads it after a relaunch.
When the entry is gone (revoked, fallen off, or its object cannot be found),
the path refuses as a forgotten handle does now (`ENOENT`), and the app asks
the person to choose again.

**A kept item is the object the person chose, natively.** Whatever later
sits at its path never inherits the grant:

| Event | A kept file or folder (macOS, Linux) |
|---|---|
| Written in place | the same document |
| Replaced by the app's own `atomicWriteFile` while a session holds it | the same document: the host carries the entry to the new file it wrote |
| Replaced at its name by another program (a new file or folder at the path) | **not** the same document: forgotten when next resolved |
| Renamed to a backup, then a replacement put at its name (by another program) | the renamed original, which is the object chosen; the replacement does not inherit |
| Moved or renamed on the same volume | macOS follows it (its bookmark resolves the object); Linux forgets it |
| Deleted | forgotten when next resolved |

macOS keeps a security-scoped bookmark and checks the object it resolves
to (its file identity) against the one recorded; a bookmark it reports
stale is refreshed in place. Linux keeps the path with the object's device
and inode and forgets an entry whose object is not at that path: weaker (a
move forgets rather than follows), never wider. The `<name>` segment stays
the name at the choice; `stat(path).name` gives the current one. An editor
that saves with its own atomic replace keeps its document; one that is
replaced by another program while the app is closed is chosen again.

**On the web the identity is the browser's.** A kept handle is the
`FileSystemHandle` the browser gave, kept in IndexedDB as any page may keep
it, and reopened under the browser's own permission (D7). Exact cannot see
an object identity behind it, so it promises nothing beyond what the
browser's handle does: what a page could keep without Exact, Exact keeps,
and no more.

### D5 — The app lists and forgets

```ts
export const grants = ['fs.read doc:/', 'doc.keep'].join('\n');
const recent = await storage.fs.recentDocuments();
// [{ path: 'doc:/12/drawings', name: 'drawings', kind: 'directory', mode: 'readwrite', opened: 1760572800000 }, …]
await storage.fs.forgetDocument('doc:/12/drawings');
```

- `recentDocuments()` lists the kept entries the platform's list still
  holds, most recent first, without reading them: an entry whose file is
  gone lists until a read finds it gone. `storage.fs.watch('doc:/')`
  re-asks when the list changes.
- `forgetDocument(path)` is the app's own removal (a "Remove from Recents"
  item). It is not what makes revocation safe; D6 is.

Neither the web nor Node has a recents API, so both names are Exact's,
declared as deviations in the manner of `saveFile`.

### D6 — The person revokes from outside the app, on every host

The kept set has one source of truth per host, a surface the app cannot
withhold:

| Host | The list | The person revokes with |
|---|---|---|
| macOS | `NSDocumentController`'s recents: File ▸ Open Recent (LLP 1069.010 D5) | Clear Menu; the system's "Recent items" count bounds it |
| Linux, in a desktop session | the freedesktop recent-files store (`recently-used.xbel`), entries marked with the app | the desktop's "clear recent history"; with no desktop session (headless, the DRM kiosk) nothing is kept |
| Web | the glue's IndexedDB handles | clearing the site's data in the browser revokes; withdrawing the file permission only suspends, until a press asks again (D7) |
| iOS | the host's own list, shown in the app's page in Settings (a Settings bundle the host writes) | "Clear Recent Documents" there |

The host keeps only what each entry needs beside it (the bookmark, the
identity, the mode, `<n>`), in the host's own storage for the app, outside
`app:/`, the agent's `storage` and anything a data module can write. At
launch and whenever the system list changes, an entry the list no longer
holds is dropped from that store. An app that could add an entry could name
any path on a host with no sandbox and read it, so only the host's mint of
a person's choice (D3) adds one.

### D7 — Permission on the web, the grant, and the sandbox

- **The web asks again under a press.** A browser may withhold a kept
  handle's permission after a reload (Chromium asks again unless the person
  chose "Allow on every visit"). A read or write then fails with `EACCES`,
  distinct from a gone entry's `ENOENT`, and the app offers a button that
  issues the web's call as a command, `requestPermission(id, path, mode)`,
  inside the press's activation as the pickers are (LLP 1069.010 D2). The
  result arrives as `change` on the node `id` names: `granted` or `denied`.
  Native hosts answer `granted` for a kept entry that resolves.
- **`doc.keep`** is an Exact grant (filtered by `io_grants` before Ibex,
  beside the device and presenter grants). Without it nothing is kept:
  today's behaviour, and macOS's Open Recent menu keeps reopening through
  the host's route as it does now.
- **It widens time, not reach.** A kept entry is the item the person chose,
  in the mode the choice granted, under the read and write grants the app
  declares. A kept folder keeps its subtree; that is what choosing a folder
  means, and what the sandbox's bookmark of a folder grants.
- **Under the App Sandbox** (not built; LLP 1069.010 Q2) D3's entries are
  `withSecurityScope` bookmarks under
  `com.apple.security.files.bookmarks.app-scope`, the platform's documented
  way to keep a user's choice. D3's rule that a route keeps the file and not
  its folder is what makes the unsandboxed and sandboxed builds keep the
  same thing.

## 5. The DEFERRED words (Charlie's)

- **Stage 1** reverses part of a take: the Markdown editor's expansion
  (Charlie, 2026-09-21) put the reader's "file watching" behind the
  editor. The editor is built (`markdown/editor/`, LLP 1045). Stage 1 asks
  to lift that take for `doc:` watches.
- **Stage 2** moves one form of "durable capability grants" onto the
  doing-list: **a document the person chose (D3), kept in the platform's
  bounded, person-revocable recents (D6), under `doc.keep`.** It unblocks
  document apps reopening their documents (Exact Draw and studio outside
  the repo; the Markdown and LLP readers inside it) and the Mac App Store
  path LLP 1069.010 Q2 keeps open. Still refused: every other durable grant
  (a network origin, a device, anything the app names rather than the
  person chooses), and keeping what a route or the app reached rather than
  what the person chose. The take is Charlie's to name, or a waiver.

## 6. Alternatives

- **The app stores the handles it wants (the web's model).** Natively it
  needs an unbounded set of bookmarks the host can never prune and the
  person can never see, or bookmark data the app could forge on an
  unsandboxed host. The platform's list gives the same reopening with a
  revocation the person controls.
- **Restore the windows at launch instead.** AppKit's state restoration is
  worth doing on top of D3 (a later slice of LLP 1069.010), but it gives no
  list of recent folders and reopens nothing on request.
- **Pinning a workspace beyond the recents' bound.** A folder an app treats
  as its workspace can fall off a busy recents list. Not in this RFC: the
  app asks the person to choose again, and the trigger to revisit is an app
  where that happens in use.
- **A companion process (Exact Draw's today).** Works unsandboxed on a Mac
  and nowhere else; recorded in the issue as the "neither" option.

## 7. Verification

- **Stage 1.** A fixture app lists a chosen folder with a watch; a file the
  test writes into it appears on macOS, iOS, Linux and Chromium, and one
  written two levels down does not until the watch is `recursive`; an
  atomic replace of the open file re-asks on macOS; a write with a stale
  `expect` is refused `ECHANGED` and leaves the file as the other writer
  left it; a browser without `FileSystemObserver` reports `canWatchFiles:
  false`.
- **Stage 2.** On macOS: choose a folder, quit, relaunch, and read beneath
  the stored `doc:` path with no panel; open a file from Finder, relaunch,
  and its sibling is refused while the file reads; Clear Menu, relaunch, and
  the path refuses `ENOENT`; a folder moved away and replaced by another at
  its path is forgotten, not reopened. On Linux, the same with the desktop's
  recent files. On the web, a reload with permission withheld fails
  `EACCES`, and a press's `requestPermission` restores it. The host's store
  is not reachable through `storage.fs` or the agent's `storage`.
- **Exact Draw** reopens its last folder, shows an external edit, and
  refuses to save over it, with its companion's file service stopped.

## 8. Not in this RFC

- **Window restoration at launch** (§6). Trigger: the readers, once D3 is
  built.
- **iCloud placeholders and coordinated writes** beyond what
  `NSFilePresenter` reports. Trigger: a document app on iCloud Drive.
- **Android and Windows**, which take D1–D7 when they gain `doc:` pickers;
  Windows's list would be its Recent items.

## As built: stage 1 (2026-10-16)

Built by Claude (Opus 5.5) on macOS, Linux and the web. Where the build
differs from the design above, it says so here.

- **The topic.** `storage.fs.watch(path, {recursive})` records
  `doc-watch:<path>` or `doc-watch-recursive:<path>` as an LLP 1016.002
  topic (`exact_data::documents::watch_topic`); a Rust source records the
  same with `store.observe_topic`. `Runner::watched_topics` lists what the
  current answers watch, and `state.watches` shows it on every host.
- **The hosts** (`host/apple/src/doc_watch.rs`, `host/linux/src/doc_watch.rs`).
  After every commit the host matches its watches to the answers' topics,
  keeping only `doc:` paths its session owns and `fs.read` covers, and
  announces a change through the native slot. macOS: one FSEvents stream
  over the watched folders, file-level events. Linux: one inotify instance,
  a watch per folder (and per folder beneath a recursive watch, up to
  4,096), read on its own thread. Both watch the folder, so an atomic
  replace of a watched file is seen. The web JS target: the glue's
  `FileSystemObserver` on the handle, for TypeScript sources
  (`documents-glue.js` `observe`).
- **The expected write** is a `stat`, a comparison and the write, queued
  together: in the native prelude, in Exact's Rust storage
  (`data/host/src/native.rs`), and in the web glue. Ibex runs neither; its
  `storage.d.ts` declares both (Exact patch 14, `vendor/ibex/EXACT-PATCHES.md`).
- **The consumer.** The Markdown reader watches what it opened and its
  folder (`apps/markdown/data`).
- **Verified.** macOS, by driving the Markdown reader: a README replaced
  atomically by another process and a file added beside it show without a
  reload. TypeScript on Hermes (`js/tests/it/watch.rs`): both topics
  recorded, a stale `expect` refused `ECHANGED`, a fresh one written. Rust
  storage (`data/host/src/tests.rs`): the same refusal and write. The web
  glue in Chrome 155 (a scratch probe over an origin-private folder):
  `FileSystemObserver` fires on another handle's write, `expect` refuses
  and writes as natively. Linux: `doc_watch`'s unit test (a new entry, an
  atomic replace, a sibling folder unheard, a grant that does not cover the
  path).
- **Not built.** `exactPage().canWatchFiles`: a browser without
  `FileSystemObserver` but with the document pickers is an old Chromium,
  and every other browser opens no document to watch. The agent's
  `changed <path>`. iOS (no FSEvents; `NSFilePresenter` is owed). A Rust
  source's watch on the web JS target, where no Rust topic is wired
  (`native.watch` from Rust is not either). The wasm web host accepts a
  watch that never fires.

## As built: stage 2 on macOS (2026-10-18)

Built by Claude (Opus 5.5) for Charlie on macOS; Linux and the web are
next, iOS stays out (Rulings). Where the build differs from the design
above, or settles what it left open, it says so here.

- **The kept set** (`exact_data::documents::kept`, shared with the hosts to
  come). Per app, a file the host names outside every `app:/` root:
  `~/Library/Application Support/exact/<app id>/kept-documents.json`, beside
  `data/`; under the agent, the drive's scratch store's root, and a drive
  with no scratch store keeps nothing (D3, D6). Each entry holds `<n>`, the
  name at the choice, the kind, the mode, when it was opened, the object's
  device and inode, where it was last found, and the host's own handle on it
  (on a Mac, a security-scoped bookmark, which Swift makes and resolves;
  `KeptDocumentsMac.swift`). Swift reads no file and decides nothing: it
  reports what each bookmark found and what Open Recent holds, and the
  library checks each object's identity and drops what the list no longer
  holds. The set is written whole, flushed and renamed into place, and the
  folder flushed after the rename; a choice
  that could not be written is not kept, and a set that exists but does not
  read keeps nothing that launch and is left as it is. One process of an
  app holds the set (a lock beside it, held while it runs); a second keeps
  nothing.
- **`<n>` (D4).** The table numbers handles from a counter each keeping app
  persists, and every handle a keeping app's session mints advances it, not
  only the kept ones: a session handle from an earlier launch is never given
  again either, and a number that could not be written down is not given
  (the choice is refused). The host reads the set before the session mints
  anything. A
  kept entry belongs to the app: any of its sessions resolves it, and it
  outlives the session that chose it.
- **Restoring (D4).** As a session's data activates, before any answer can
  read a kept document, the host resolves each bookmark (once a process),
  the library first drops what Open Recent no longer holds, and then keeps
  an entry only if the object found is the one recorded, read through the
  descriptor it retains (`fstatat` beneath a file's folder). Because Open
  Recent is checked first, a record written into the set by anything else
  (an app that can write where the set is, through a folder the person
  chose above it) reopens nothing Open Recent does not hold.
  A bookmark resolves by path first: a file another program renamed to a
  backup before writing its own at the name resolves to that new file, so the
  host follows the recorded inode instead (`fsgetpath(2)`), which is D4's
  "the renamed original". A file deleted and replaced is gone. A rename or
  move keeps the path: the guest names the file by the name it was chosen
  by, and its leaf is its current name (Ibex patch 15,
  `DocumentLease::selected_file_named`); chosen again under its new name, it
  is still that path. The app's own `atomicWriteFile` from a Rust source
  carries the entry to the file it wrote, whichever handle it wrote through
  (the kept file's, or a route's folder's): the host reads the identity at
  the target through the folder it is in, held before the write, so a
  folder moved during the save does not lose it. Another object at a kept
  file's name, chosen, is a document of its own, with a number of its own. Once restored, a kept file is live access
  as any session handle is, a leaf in its retained folder, so another
  program's replacement at its name shows this launch (stage 1's watches
  rely on it) and is not the document at the next.
- **The list (D6).** What Open Recent holds is the truth: the host reports
  it at launch, after it notes a document, and after Clear Menu (now the
  host's own item, which clears and then reports), and the library drops
  entries whose objects it no longer holds, by identity, so a move is no
  removal. Under the agent the list is the person's own (a drive shares the
  reader's bundle id, as slice 1 of LLP 1069.010 records), and the kept set
  the drive's. A development build, signed ad hoc again by every rebuild,
  starts with an empty Open Recent (seen on macOS 27, at its first launch
  or, once, its second), so a rebuild keeps nothing from before; the list,
  not the kept set, is what went.
- **What is kept (D3).** A picker's choice (the handle it delivered is the
  kept one), ⌘O, Finder and Open Recent, the command line (the terminal's
  route in, LLP 1033 D3), and a drop of a declared type (an app that keeps
  nothing still takes a drop as content and notes nothing). A drop of any
  other type, a folder's included, and a paste's files are content: minted
  for the session, not kept and not noted (2026-10-20, LLP 1069.010 "Files
  dropped or pasted"). A route's file
  is kept alone, beside the session's folder handle. A typed path and a
  followed link are not. A document chosen again is the entry it was: same
  `<n>`, same name, first in the list, moved to where it is now; a picker
  or a drop delivers that path. Every choice on a Mac grants reading
  and writing (`mode: "readwrite"`), as the panels and Finder do; a later
  write still needs `fs.write doc:/`.
- **`recentDocuments()` and `forgetDocument(path)` (D5).** Storage requests
  `fs.recentDocuments` and `fs.forgetDocument` for a Rust source; for
  TypeScript the prelude answers both from the same list through the host
  door, and `storage.d.ts` declares them (Ibex patch 15); a replacement
  module on trial can list but not forget. Without `doc.keep`
  both are refused; a session that keeps nothing lists nothing. Every change
  to the list announces `doc-watch:doc:/`, which `storage.fs.watch('doc:/')`
  records. `forgetDocument` also takes the document off Open Recent:
  AppKit removes no single entry, so the host clears the list and notes the
  rest again, oldest first (`exact_on_document_forgotten`). A forgotten or
  pruned entry stays readable until the app quits, in any of its windows:
  live access is the app's, as the entry was.
- **`doc.keep`** is one of Exact's own grant lines (`runner::grants::own`,
  the web's `exactOnly`), left out of Ibex's grants by `io_grants`.
- **The consumer.** The Markdown reader is granted `doc.keep`. Its sidebar
  lists Recent above the folder's files, watching the list; a press reopens
  one with no panel, and its context menu's Remove from Recents forgets it.
  Window restoration at launch stays out (§8).
- **Verified** by driving the Markdown reader in its assembled bundle
  (`Markdown.app/Contents/MacOS/Markdown` under `EXACT_MAC_BIN`, a scratch
  store): a folder and a file chosen through the held pickers, then each
  launch a new process. After a relaunch both list and read with no panel,
  a file in the kept folder too; a sibling of the kept file and the folder
  handle a route delivered refuse `ENOENT`. A file opened by the command
  line is kept alone. Renamed while the app was closed, the file reads
  through its kept path; renamed to a backup with an impostor at its name,
  the original reads; deleted, the path refuses and the impostor is not
  listed. A folder moved away and replaced at its path is forgotten: Open
  Recent itself names the replacement, so the list drops the original.
  Remove from Recents leaves both the app's list and the drawn Open Recent
  menu. Unit tests: the kept set across a simulated relaunch (numbers, an
  impostor, a move, the list, forgetting, the app's own save), storage's two
  requests and a renamed file read through its kept path, a TypeScript
  answer listing and forgetting; an XCTest for bookmarks (a move, a backup
  and an impostor, a deleted file, a folder) and for Open Recent without a
  forgotten entry.
- **Not verified or not built.** Clear Menu from the real menu bar (the
  agent drives no menu bar; the item calls the same pruning a launch does,

  Finder drag. iOS keeps and lists nothing. (The TypeScript

## As built: stage 2 on Linux and the web (2026-10-26)

Built by Claude (Opus 5.5) for Charlie. Where the build differs from the
design above, or settles what it left open, it says so here.

- **TypeScript's own atomic save (D4), every native host.** The prelude
  wraps `atomicWriteFile` of a `doc:` path: before the write the host reads
  what it replaces (`kept::before_write`, held under a token), and once it
  is written carries the entry to the new file (`kept::carry`); a failed
  write lets the token go. A save issued while an earlier save of the same
  file is in flight shares that one's token, since the earlier rename may
  have landed before its carry (`js/src/storage.rs`). A `recentDocuments()`
  refused at bake carries the code `bake`, so a resource that lets it
  through bakes.
- **Linux: the list (D6)** is the freedesktop recent-files store,
  `$XDG_DATA_HOME/recently-used.xbel`, each entry marked with a
  `bookmark:application` named by the app's id, whose `exec` is the host's
  executable quoted as GLib unquotes it (`host/linux/src/kept.rs`). The host
  edits the person's file in place: other apps' entries stay as written; an
  entry another app marks gains this app's mark under the prefix in scope
  there; the result must parse or nothing is written; it is written to a
  private (`0600`) file and renamed into place, as GTK keeps it; and since
  GLib's writers take no lock, the store is read again before the rename
  and the edit made again on another writer's store (three tries). An app
  marks at most 50 entries (GTK's former `gtk-recent-files-limit`); past
  that its oldest lose the mark. The desktop's own writers prune by age.
  `forgetDocument` takes the app's mark off the entry for the object and for
  the path it was last found at, and off the store with it where no other
  app marks it. The store's folder joins the document watch's inotify, so
  the person clearing recent history while the app runs drops the entries
  then, and announces the list.
- **Linux: the handle (D4)** is the path the object was last found at,
  restored only where the device and inode recorded are still there; a
  moved file, or one replaced at its path, is forgotten. The kept set is
  the library's, `kept-documents.json` beside the app's `app:/` roots, read
  as the data activates.
- **Linux: a desktop session (D6)** is one whose environment names a
  display server (`XDG_SESSION_TYPE` `x11` or `wayland`) or a desktop
  (`XDG_CURRENT_DESKTOP`), with a display: a drive (`EXACT_AGENT`), a smoke
  run, a screenshot and `EXACT_DISPLAY=headless` keep nothing, nor does the
  DRM kiosk, whose session is a console's. The Linux host has no file
  chooser of its own (LLP 1069.002 D8), and its only document chooser is
  the agent's held picker, which is headless; so today a Linux desktop
  session chooses nothing to keep. The keeping path is what a desktop
  picker will call (`kept::chosen`).
- **The web: the store (D4, D6)** is the page's IndexedDB,
  `exact-documents:<storage key>` (the key `app:/` storage uses, so a drive
  with no scratch store keeps nothing and clearing the site's data
  revokes): each entry the `FileSystemHandle` the browser gave, `<n>`, the
  name at the choice, the kind, the mode the browser had granted at the
  choice (`queryPermission`), and when it was chosen
  (`host/web/documents-glue.js`). The web has no recents list, so the
  glue's is bounded at 20, its oldest no longer reopened after a reload.
  Every `<n>` a keeping page gives, kept or not, comes from a counter in the
  same database, reserved 256 at a time in a transaction and never given
  past the block reserved, so neither a reload nor another tab gives one
  again: a page reads its entries back and reserves before it mints, a
  paste in that first instant or past the block hands over nothing, and a
  choice waits for the next block. Choosing and forgetting take turns
  under the app's Web Lock, across tabs. Chosen again (`isSameEntry`), a
  document is the entry it was, at the path and name it was kept by. An
  entry another tab kept resolves here too, read from the database when
  its number is asked for. A number this page never gave, or one no longer
  kept after a reload, refuses `ENOENT`, as natively; a kept file or
  folder a read finds gone is forgotten then (D4, D5).
- **The web: what is kept (D3)** is a picker's choice, a file the
  installed app was launched with (`launchQueue`), and a dropped file of a
  type the manifest declares; a dropped folder, a paste and the agent's
  files are the session's (the agent's handles cannot be stored, so a drive
  keeps nothing).
- **The web: permission (D7).** A read or write of a handle whose
  permission the browser withholds refuses `EACCES`, checked before
  anything beneath a kept folder is reached (a read never prompts; a write
  asks, as before, which the browser grants only in a press). The mode an
  entry lists is what the browser granted at the choice; when the browser
  later lets the page write it, which only the person's answer to the
  browser does, the entry is kept as `readwrite`. The app's own grants
  never widen it (D3).
  `requestPermission(id, path, mode)` is a command on every host, checked
  by the compiler (`type-permission-argument`) and ruled by the runner as
  the pickers are (`file_pickers::permission`: a `doc:/` path, `read` or
  `readwrite`, an element). The web calls the handle's `requestPermission`
  inside the press, and the wasm host delivers the answer only to the
  generation that asked; a number the page has not read back yet is looked
  up first, outside the press. Linux and macOS answer `granted` for a path
  that resolves for the session, else `denied`. A wake's commit may not run
  it.
- **The web: the two calls (D5)** on both targets: the JS target's
  storage, the wasm host's TypeScript storage (the prelude asks it rather
  than the host door, which is synchronous) and a Rust source's
  `fs.recentDocuments` / `fs.forgetDocument` requests. A change to the list
  announces `doc-watch:doc:/` on both: the JS target's answers hear it, and
  the wasm host's runner through `exact_changed`. A change another tab made
  is seen at the next call, not announced.
- **Verified.** Linux: unit tests over a GTK-written store (marks added and
