## 1. Summary

Bluesky opens links in `SFSafariViewController`: a Safari sheet over the
app with AutoFill and Reader, and a Done button that returns to where the
person was. exact2's `openURL` hands every link to the system browser,
which takes the person out of the app.

This RFC proposes one named argument, by the web's own word:
`openURL(url, popup=true)`. `popup` is HTML's request for a popup window,
and a browser may ignore it. On iOS it presents `SFSafariViewController`.
Every other host does what plain `openURL` does there, the web included.
It adds no event and changes no page fact: the app learns nothing when
the sheet closes, as Bluesky needs nothing.

Under the agent, both forms of `openURL` become a held request in the
runner's command door, so a drive never opens a real browser.

It is small: one argument, one iOS view controller, one runner ruling for
the agent. It reverses a recommendation in two earlier documents (§3.2).

## 2. What Bluesky does

`src/lib/hooks/useOpenLink.ts` (social-app `main`, read 2026-10-08):

- On native, for a non-`mailto:` URL, it reads the "open links in app"
  setting. Unset, it shows a consent dialog first. Set, it calls
  `WebBrowser.openBrowserAsync(url, {presentationStyle: FULL_SCREEN,
  toolbarColor: <theme background>, controlsColor: <primary>,
  createTask: false})`, which is `SFSafariViewController` on iOS.
- If that call fails, it falls back to `Linking.openURL(url)`.
- Otherwise, and always on the web, `Linking.openURL(url)`.

**Correction to the source:** the source asks for "an event when it's
dismissed". Bluesky doesn't use one. It ignores the promise
`openBrowserAsync` returns except to catch a failure. Nothing in the app
runs when the sheet closes.

## 3. What exact2 has today

### 3.1 `openURL`, per host

`openURL(url)` is a fire-and-forget host command (`contract/syntax/src/lib.rs:95`).
It takes one string. No grant governs it; each host checks the scheme.

| Host | What it does | Where |
|---|---|---|
| Web, wasm glue | `window.open(target, "_blank", "noopener,noreferrer")` for http, https, mailto, tel; refuses anything else to the console; refuses more than one argument | `host/web/glue.js:784-786`, `host/web/navigation.js:520` |
| Web, JS target | the same `window.open` and allowlist; extra arguments ignored | `host/web-js/commands.js:20-25` |
| iOS, tvOS | `UIApplication.shared.open(url)` for http, https, mailto, tel; refuses more than one argument | `host/apple/Sources/ExactIOS/main.swift:51-58` |
| macOS | a `doc:` or local path goes to the app's documents; http, https, mailto to `NSWorkspace.shared.open` | `host/apple/Sources/ExactMac/main.swift:66`, `:80-96` |
| Linux, Windows | journaled as unsupported ("no browser") | `host/linux/src/presenter/commands.rs:84`; Windows runs the same presenter (`host/windows/src/window.rs:223`) |
| Terminal | ignored; a link is written as OSC 8, which the terminal opens on Cmd/Ctrl-click | `host/terminal/src/host.rs:237-251`, `host/terminal/src/grid.rs:33` |

On Apple, `openURL` reaches the session's **delegate**, not ExactKit: the
adapter decides (`ExactSessionDelegate.exactSession(_:command:args:)`). A
link the reader follows (`Session.follow`, `Session.swift:1415`;
`InlineText.swift:205`) also ends there unless it names one of the app's
routes. An embedder (LLP 1031 D5) handles `openURL` itself.

`openURL` doesn't pass the runner's command door
(`runner/src/commands.rs:1-5`, which `share`, `saveFile`, the pickers and
notifications pass). So under the agent it opens the real browser, and
nothing of it reaches `state`. LLP 1069.007 says such a command can't be
tested and gets a redesign; D5 is that redesign.

Two smaller corrections found while reading:

- `docs/contract-for-humans.md:1036` says "the JavaScript web target has no
  `openURL`". It has had one since `commands.js:20`. The doc is stale.
- `docs/contract-grammar.md:1247` names Linux's missing `openURL` but not
  Windows', which shares it.

## 4. What the web does

The web has no in-app browser. It has two ways to show a URL away from
the page, both through [`window.open(url, target,
features)`](https://html.spec.whatwg.org/multipage/nav-history-apis.html#dom-open):

- A new tab: `window.open(url, "_blank")`. This is what exact2's `openURL`
  does today.
- A **popup window**: `features` with
  [`popup`](https://html.spec.whatwg.org/multipage/nav-history-apis.html#popup-window-is-requested)
  asks for a window with minimal UI. HTML lets the browser decide: desktop
  Chrome and Firefox open a small separate window; iOS Safari and Android
  Chrome open a tab.

`noopener` and `noreferrer` are tokens of the same string. `noopener`
gives the new page no `window.opener`, and `window.open` then returns
`null`. `noreferrer` sends no `Referer` and implies `noopener`. exact2
always passes both, so the page that opened the link never gets a handle
to it.

So the web has **no close event** for a page opened this way, and no
portable signal of return. A mobile tab hides the opener; a desktop popup
only blurs it, and the person can refocus the opener while the popup
stays open.

`SFSafariViewController` is the iOS form of the popup window: a browser
with minimal chrome, over the app, that the person dismisses.

## 5. Design

### D1 — The argument is `popup`, by the web's own name

Options:

1. **`openURL(url, {inApp: true})`**, the source's shape. `inApp` is a
   React Native word (`expo-web-browser`'s, roughly). The web has no such
   flag. The project's rule refuses it: a name that could follow the web
   follows the web.
2. **A new command, `openBrowser(url)`**. Same objection, and a second
   command for one boolean.
3. **`openURL(url, popup=true)`**. `popup` is the `window.open` feature
   that asks for exactly this, and HTML already lets a browser decline
   it. Named, as `share(title=, text=, url=)` and
   `showNotification(title=, …)` are: Contract's commands take a web API's
   member names as named arguments (`contract/lower/src/expr.rs:55-58`).
4. **A link attribute** (`link href=… target=…`). HTML's `target` names a
   browsing context, not its presentation, and there is no `popup` value.
   Bluesky's links all go through one press handler anyway.

**Recommended: 3.** `popup` takes a bool expression, so the setting is
`openURL(url, popup=settings.openLinksInApp)`. Absent or `false` is
today's `openURL`. It is a presentation request: each host decides how to
honour it, as each browser does, and it promises nothing about return.
The other `window.open` features (`width`, `height`, `left`, `top`) are
not admitted: no native host can honour them, and no consumer asks.

Leaving `noopener` and `noreferrer` out of the argument is deliberate.
They are always on, on every host. `SFSafariViewController` has no opener
to give, and an opener handle would be a channel from a guest page into
the app, which LLP 1020 keeps out for `iframe`.

### D2 — Per host, and who decides

| Host | `openURL(url, popup=true)` |
|---|---|
| Web (both targets) | as plain `openURL`: `window.open(url, "_blank", "noopener,noreferrer")`, a tab. The second argument is accepted and ignored, as iOS Safari and Android Chrome ignore `popup`; a desktop popup window is what Bluesky's web client never opens |
| iOS | `SFSafariViewController` for http and https, presented full screen over the session's window; mailto and tel go to `UIApplication.shared.open` as today, since the view controller accepts only http(s) and raises on any other scheme |
| macOS | as plain `openURL`: the default browser. AppKit has no `SFSafariViewController`. A `WKWebView` window would be a browser without an address bar, which is a phishing surface; not offered |
| tvOS | refused by name (`openURL: refused: no browser on tvOS`). tvOS has neither Safari nor the view controller; plain `openURL` already fails there silently, and the refusal fixes that too |
| Linux, Windows | as plain `openURL`: journaled as unsupported. Windows could open the default browser with `ShellExecuteW`; that is plain `openURL`'s gap, not this RFC's (§9) |
| Terminal | as plain `openURL`: ignored |

**The delegate decides both forms** (LLP 1031 D5). ExactKit asks the
runner's door (D5); when the ruling is present, the delegate receives
`openURL` with `[url, popup]`, as it receives the plain form today. A
followed link (`Session.follow`, `InlineText`) asks the same door. The
stock iOS adapter presents the sheet through a helper ExactKit holds, so
an embedder that wants Safari's sheet calls one function, and one that
keeps a URL allowlist sees every open. No browser customization API is
added. One live sheet per window: a second `popup` while one is up
dismisses it and presents the new URL.

**iOS details.** The helper builds the view controller with
`SFSafariViewController.Configuration()` defaults:

- `dismissButtonStyle` `.done`;
- `preferredBarTintColor` from `app.json`'s `theme_color` when it is set.
  That key already writes the web's `<meta name="theme-color">`
  (`host/web/build.mjs:294`, `:354`), which browsers use to tint their own
  chrome. Unset, the system's bars.
- `preferredControlTintColor` from the root's `accent-color` when it is
  set (`kernel/tables/schema.json:3246`), else the system's.
- `overrideUserInterfaceStyle` follows `setScheme`, as the app's window
  does.

Bluesky passes its theme's background and primary colours; the two keys
above carry the same. A colour that follows the app's own theme switch at
run time would need a third argument; §6 Q3.

### D3 — No dismissal event, and no page fact moves

Options:

1. **A new event**, `close` on some element. There's no element: the
   command addresses none, and `share`'s outcome is a journal line, not an
   event (LLP 1069.003 D2). The web has nothing to fire it from.
2. **A `cancel`/`close` handler on the pressed element**, as `showPicker`
   answers its element. Same objection: nothing on the web corresponds.
3. **Report the sheet through `exactPage()`**, `visibilityState: "hidden"`
   and `hasFocus: false` while it covers the app. This redefines both
   facts. On iOS `hidden` is the scene in the background and `hasFocus`
   the scene `foregroundActive` (LLP 1069.000 D2;
   `host/apple/Sources/ExactKit/PageFacts.swift:53-61`, `:88-95`). A
   presented controller leaves the scene active, and the share sheet and
   dialogs don't flip either fact. An app that pauses its feed on
   `hidden` would treat reading a link as going to the background, and a
   real background during the sheet would start from a page already
   hidden. The web gives no portable signal to copy (§4).
4. **Nothing.** The sheet is a presentation; the app keeps running under
   it, as under a share sheet.

**Recommended: 4.** Bluesky needs no signal. The journal says
`openURL: presented` and `openURL: closed` for the agent and the logs.
The cost is plain: on iOS, plain `openURL` sends the app to the
background and `popup=true` doesn't, so an app that watched
`visibilityState` for "the person came back" sees nothing with `popup`.
`popup` makes no return promise on any host. If a later consumer needs an
action to run on return, that is the general `visibilitychange` question,
not this command's.

### D4 — Grant

None. Plain `openURL` has none; the scheme allowlist is the check, and it
is unchanged. `SFSafariViewController` needs no entitlement or
`Info.plist` key, so LLP 1069.008's reach table gains no row. The page
runs in Safari's process with its own per-app cookie jar; the app can't
read it, so there is nothing for a grant to govern.

### D5 — The agent: both forms through the door

Today `openURL` bypasses the runner under the agent (§3.1). r2 sends both
forms through the command door (`runner/src/commands.rs`), as `share`
goes, and chooses the presentation only after the ruling. One boundary,
whatever the setting. LLP 1069.007 D7's paragraph:

1. **Shape:** a command-shaped request with no answer to the app; its
   outcome is a journal line (`openURL: presented`, `openURL: closed`,
   `openURL: refused: <reason>`).
2. **Pending:** under the agent no host opens anything. `state.pending`
   lists `{ticket, device: {capability: "openURL", args: {url, popup}}}`,
   the URL's origin and path only (a query can carry a token). The hold
   moves no page fact; `prefer` sets `visibilityState` and `hasFocus` as
   it does today. **Answer:** `tap @t close`. **Fixture:**
   `--answer openURL=close`. `delivery` is `substituted`.
3. **Disclosure:** the journal names the origin, never the query.
4. **Web override:** none in CDP; the wasm glue holds the request under
   `?agent=1` through `exact_command`, and the JS target holds it as
   `files.js` holds `share`.

A drive: `tap open-link`, `state` (the pending entry with `popup: true`),
`tap @t close`, `tree` (the view, unchanged). The same on web, macOS,
iOS and Linux. `EXACT_DEVICE=real` presents the real sheet or browser
(LLP 1069.007 D8).

## 6. Questions for Charlie

1. **Admit the in-app browser for Bluesky, reversing LLP 1069 §5's "Not
   now" line and LLP 1069.006's "Not in this RFC" line?** What it buys
   is the person staying in the app, with AutoFill and Reader. It does not
   carry Safari's sign-ins: the sheet's cookies are the app's own since
   iOS 11. Both reviewers: still yes. Recommended: yes, as a clarification
   under Bluesky's admission with no further trade (§3.2).
2. **Does the sheet move `exactPage()`?** Grok: no fact changes; `hidden`
   while the app stays in the foreground breaks `hidden`'s definition and
   every reader of it (blocking). Astra: no portable return guarantee,
   but an actually covering iOS sheet reported `hidden` is reasonable.
   Recommended: no fact changes (D3). The full-screen sheet does cover the
   app, but iOS's `hidden` is the scene's state, not occlusion, and the
   share sheet sets the precedent.
3. **Colours from `theme_color` and `accent-color` only, or a third
   argument for a colour that follows the app's theme switch?**
   Recommended: the two keys only. Under a system dark mode the sheet's
   bars are dark already; Bluesky's in-app theme toggle is the one case
   left, and a cosmetic one.
4. **macOS: the default browser, not an in-app web view?** Recommended:
   yes (D2).

## 7. What the clone does after

- An "Open links in app" setting, kept with `store`, defaulting to unset.
- A consent dialog (a Contract `dialog`) the first time a link is pressed
  while the setting is unset, as `useOpenLink` does.
- Every external link press calls `openURL(url, popup=settings.inApp)`.
  `mailto:` stays plain. On the web the setting changes nothing, as on
  Bluesky's web client.
- The link warning (a link whose text names another domain) is Contract
  and needs nothing from exact2.

**Verified by** an agent drive on iOS, macOS and web: press a link with the
setting on and see the pending entry with `popup: true`; `tap @t close`;
press with it off and see the pending entry with `popup: false`. Then once
by hand on the iOS simulator with `EXACT_DEVICE=real`: the sheet opens over
the app, Done returns to the same scroll position.

## 8. Effort and complexity

**Size: S.**

exact2 work:

- The compiler: `popup` as a named argument (`expr.rs`, a `checks.rs`
  arm), a test.
- The runner: an `openURL` ruling in `commands.rs` (refused, held,
  present), on the share module's model, for both forms.
- Apple: ExactKit asks the door before the delegate, for the command and
  for a followed link. About 60 lines of Swift for the
  `SFSafariViewController` helper, its delegate and the anchor; the iOS
  adapter calls it. The one subtle part is presenting from the right view
  controller (the topmost presented one of the session's window) when a
  dialog or share sheet is already up.
- The web: accept the second argument in both targets, and the hold under
  `?agent=1` (the wasm glue through `exact_command`, the JS target in
  `files.js`).
- Linux: the hold under the agent. tvOS: the refusal. Docs: the command
  table and the two stale sentences.

Clone work: S (the setting, the consent dialog, the link warning).

Nothing here is hard. Bringing plain `openURL` through the door changes
what an existing drive sees: a press that opened a real browser now
leaves a pending entry. No app in `apps/` calls `openURL` and no script
names it; a drive that presses an external link gains a `tap @t close`.

## 9. Not in scope

- An in-app browser on macOS, Linux, Windows or the web.
- `window.open`'s geometry features, a returned window handle, or any
  message channel to the opened page.
- Reading the opened page's URL or navigations. Sign-in is LLP 1069.006's
  `openAuthSession`; a guest's navigations stay out (LLP 1020 §5).
- A signal when the person returns (D3).
- `openURL` on Windows through `ShellExecuteW`, and the two stale doc
  sentences (§3.1). Each is a QUEUE line, not this RFC.
- Links opening in the app's popup by default (an `app.json` policy). The
  web has none; the clone's press handler decides.
