**Author:** Claude Opus 5.5 for Charlie Cheever

**Related:** LLP 1046.008 (amendment: derived presentation state); LLP 1046.003 (skeletons, culling); `game/engine/README.md` ("save the cause, derive the appearance"); Castle `engine3d/pxmodel.js` `animateModelParts`, `gait.js`; reviews `llp/reviews/1046.013-per-node-pose-offsets.{astra,fable}.md`

## Summary

`NodeOffsets` is a new presentation component that moves an instance's model nodes.
It holds up to 16 rows of (node name, `Transform`). Each named node is drawn at
`local ∘ offset`, in the node's own frame, after clips, layers and IK. It is `Offset`
for nodes:

- `Game::present` writes it;
- it is never saved or hashed;
- the renderer interpolates it between the two ticks it was fed.

Only nodes the asset marks posable can be offset. A model with a posable node draws on
the palette path that clip-animated rigid models already use. No shader or GPU path is
added.

Three changes come with it:

- presentation columns keep their storage pages when they are cleared;
- each instance uploads its pose once, rather than once per draw;
- `Present` can write a component for each row of another component without
  allocating.

## Motivation

Castle's `animateModelParts` sets `legL`, `legR`, `armL`, `armR` and `torso` every frame:
a swing of `sin(phase)·0.8·swing`, a torso bob, an air pose and a turn lean, all derived
from observed motion. The hub town shows about 30 avatars, 5 nodes each. exact2 has no
way to do this:

- `Offset` (`engine/src/scene.rs:587`) moves the whole drawn hierarchy.
- `NodeMaterials` changes looks only.
- Only `animation::step` writes `Pose`.
- A model with no skins or clips never reaches the palette path. Three places gate it
  (`render/src/skinning.rs:93`, `render/src/models/merge.rs:17`,
  `engine/src/asset.rs:364`).

## Design

### D1. Save the cause; present the pose

The game saves its integrator, for example `Gait { phase, swing, air, lean, amplitude,
last }`. This is Castle's `modelAnim`: about nine floats, stepped in `tick` from
`Transform` deltas. `present` derives the offsets from it as a pure function. Reasons:

- A save holds 9 floats per avatar instead of `Pose`'s 2 × 10 × N, which is 400 for
  `avatar-0.glb` (N = 20).
- Tuning the look moves no pin.
- `animation::step` stays the only writer of `Pose` (`engine/src/animation.rs:1098`).

**The interpolation contract.** The renderer keeps the rows of the last two ticks it was
fed. The stock observer feeds each of an advance's last two ticks, after that tick's
`present` (`render/src/surface.rs`, `observer`, `left < 2`; the after-callback in
`engine/src/sim.rs`'s advance loop). So the two ticks are T−1 and T, the same pair as
`Pose.previous` and `Pose.local`, and as `Offset`'s history.

At Castle's fastest cadence (6 Hz) and 60 Hz ticks, a stride lasts 10 ticks. Linear
interpolation between those endpoints is off by at most 1 − cos(π/10), about 5 % of the
swing, or roughly 2°.

**The price.** Offsets are drawn only, as `Offset` is. Picking, physics, IK and
`animation::socket` see the simulated pose. IK on a chain whose ancestor is offset
therefore misses its target in the drawn picture, and `socket(w, "hero", "handR")`
returns the hand before the swing. The engine README's "save the cause" section states
both.

### D2. API

```rust
const LEG_L: NodeName = NodeName::new("legL");
fn present(p: &mut Present<'_>, _: &()) {
    p.insert_each::<Gait, NodeOffsets>(|_reads, _, g| {
        let swing = math::sin(g.phase) * 0.8 * g.swing * (1. - g.air) * g.amplitude;
        let pitch = |x| Transform { rotation: Quat::from_rotation_x(x), ..Transform::default() };
        Some(NodeOffsets::default()
            .with(LEG_L, pitch(swing - 0.55 * g.air))
            .with(TORSO, Transform { position: Vec3::Y * bob(g), rotation: lean(g), ..Transform::default() }))
    });
}
```

**`NodeName`** is `Copy`. A `const fn` builds it from a `&'static str` and stores the
name's 64-bit FNV-1a hash beside it.

- The string is authoritative. The renderer finds a node by hash, then compares the
  string. `with` also replaces rows by string equality.
- It names nodes as `NodeMaterials` does: by glTF node name, resolved separately against
  each LOD level's model. So one constant serves all 16 avatar models and survives
  redelivery.
- Its `Data` implementation writes the name and refuses to read it. Presentation rows
  are never loaded, so agents' JSON for this component is write-only.
- `NodeName` is the intended scheme for naming nodes; `NodeMaterials` moving to it is a
  separate change.

**`NodeOffsets`** is `Copy`, holds at most 16 rows of about 80 bytes each (about 1.3 KB
in all), and derives `Presentation`.

- The capacity is fixed so that the renderer can keep the previous tick's row as a plain
  copy.
- A 17th distinct name is dropped. The row records the overflow and the renderer reports
  it once per model. Present never panics on content: a panic in `present` refuses a
  restore.
- Rows are never saved, so the bound can change freely.

**`Present::insert_each::<C, P>(f)`** visits the rows of simulation component `C`, in
entity order, and inserts the `P` that `f` returns.

- `f` receives the read half of `Present` (`get`, `tick`, `rng`, `global`, and so on),
  the entity and `&C`.
- It walks the column without holding a live query guard, restructures leases once, and
  does not allocate.
- It exists because `for_each` borrows `Present` immutably, so `insert` cannot be called
  inside it.

### D3. Composition

At each tick endpoint, the node's local transform `(p, r, s)` and its offset
`(p′, r′, s′)` combine into:

- position `p + r·(s ⊙ p′)`;
- rotation `r·r′`;
- scale `s ⊙ s′`.

This is `Offset`'s `local · offset`, taken component by component. It equals the affine
product only when `s` is uniform. Under non-uniform `s` it drops the shear that product
would have, because pose arrays hold only TRS (`asset/pose.rs`).

The base is one of two things:

- `Pose.previous` and `Pose.local`, after clips, `Layers` and `Ik`
  (`animation.rs:1000–1094`);
- or the bind pose, when the entity has no `Pose`.

The offset is applied last. A missing row is the identity.

**Additive layers differ.** They rotate in the node's frame too, but they add
translation in the parent's frame (`animation/layers.rs:141`). The two rules are the
same for a node with an unrotated, unit-scale rest. This RFC follows `Offset`, the
control whose name it shares.

**Limits.** Presentation state is never validated like a save, so nothing is refused;
this follows `Opacity`. The renderer handles bad rows as follows:

- It drops a row with a non-finite value, or with a scale component ≤ 0, and reports it
  (D4). Dropping non-positive scales keeps each part's winding fixed at its rest value
  (D4).
- It try-normalizes each rotation. A rotation that cannot be normalized, such as the
  zero quaternion, becomes the identity. The CPU interpolation already does this
  (`world/scene.rs` `interpolate`: `try_normalize`, else identity), and `skin.wgsl`'s
  `rotation` guards the same division.
- It checks both composed endpoints. If either is not finite, which finite inputs can
  still produce by overflow, it drops the row for that tick, draws the base, and reports
  it.

**Castle's arms.** They rest splayed ±16° about Z (`avatar-0.glb`). three.js sets
`rotation.x` with Euler XYZ, which gives Rx(swing)·Rz(16°): it swings about the torso's
X axis. Node-frame offsets would instead tilt the swing plane by 16°.

So the exporter pre-multiplies each arm's splay into the arm's children. `armL` (node 9
of `avatar-0.glb`) is a pure group with children 10 and 11: their matrices become
Rz(16°)·child, and the arm rests unrotated. This is exact, adds no node (N stays 20),
and leaves every descendant, including the hand anchors, in its world frame. Only the arm
pivot's own frame changes, so a socket on `armL` itself would see it unrotated.
`tools/verify.mjs` compares world-space triangles and anchor names (`:87`, `:90`), so it
is unaffected.

A per-row "parent axes about the pivot" flag (`r′·r`, `p + p′`) is the alternative. It
waits for a model whose posed nodes cannot be restructured that way (see Not in scope).

### D4. Which nodes, which models

- **Marking.** A glTF node marked `extras: {"posable": true}` gets
  `asset::Node.posable`. The bake already reads animation and asset extras
  (`bake/src/lib.rs:228`, `:297`). `tools/export.mjs` writes the mark on the five
  parts, and `rig::Rig::model` marks every bone.
- **Cost of the mark.** It changes the `.model` format and every model's content
  identity, so:
  - everything rebakes;
  - saves that recorded a model's identity refuse it (engine README, "Saves and
    assets");
  - the committed `game/bake/tests/fixtures/crate.model` is regenerated.
- **One predicate.** `Model::requires_palette()` (skins, clips, or any posable node)
  replaces the three gates.
  - One mark promotes the whole model, including instances that never receive offsets.
  - `animated_bounds` keeps its skins-or-clips test: simulated bounds follow the
    simulated pose (`engine/src/spatial.rs:147`).
- **Validation.** `Model::validate`, at bake and prepare, refuses a posable model in two
  cases:
  - two posable nodes share a name;
  - a node transform has shear. The palette path decomposes each transform to TRS
    (`bind_pose`), which loses shear.
- **Mirrored rest nodes are drawn, not refused.** 15 of the 16 avatar GLBs contain
  Castle's mirror groups: an unnamed node scaled (−1, 1, 1) under the head or torso,
  holding the second eye, glint, cheek or leaf. The static merge rewinds such parts
  (`merge.rs:148–156`); the animated merge does not (`:192`), and `bind_pose` turns them
  into a negative scale. The palette path gets the same winding rule as the static path:
  - The animated merge rewinds the triangles of each member whose composed rest matrix
    has `determinant() < 0`.
  - A lone rigid part's record takes its winding group from its node's composed rest
    determinant. Today it keys on `local` (`world/assets.rs:433`), which is the identity
    on the palette path.
  - Winding is fixed at rest, because no offset can flip it (D3 drops scales ≤ 0).
    `model_vertex.wgsl`'s cofactor normal already handles mirrored matrices.
  - Clip scale tracks that cross zero keep their present behaviour, which is out of
    scope.
- **Unmatched or dropped rows** draw nothing. They are reported once per model and name
  (`DiagnosticRegistry`, `render/src/world/scene.rs`), so the reports are bounded by
  models × names, not entities × rows.

### D5. Rendering

- **Palette path.** A posable model loses static pre-transformation and the
  zero-weight-buffer draw. It keeps per-material merging: rigid parts that share a
  material become one mesh skinned with weight one (`merge.rs` `animated_groups`).
  `avatar-0` still draws in 2 draws and runs 2 skin jobs per instance.
- **One pose per instance.** Today `set` and `pack` give every skinned record its own
  pose words (`skinning.rs:289`).
  - Instead, each (entity, model) gets one pose span, which all of its jobs reference.
    Job words already carry the pose offset, so the shader is unchanged.
  - `pack` composes the rows into that span once, at both endpoints.
  - The span is primed if any of the instance's templates is fresh, OR-ed over them as
    `mark_fresh` marks them (`skinning.rs:374`).
  - This halves `avatar-0`'s upload and helps clip models equally.
- **History lifecycle.** The renderer keeps the previous rows only for instances that
  have rows, sorted by entity, with capacity reused.
  - It shifts once when a feed sees a new tick. A re-present at the same tick (an
    argument change or a tool edit) replaces only the current rows.
  - It primes current/current exactly when the span's pose words are primed: on the
    initial feed, at birth, on first pose, on teleport (`World::is_fresh`), on a
    generation change, on model replacement, on LOD arrival and on restore.
  - A row that disappears interpolates to the identity for one tick, then leaves the
    history.
  - Hidden instances keep their history, as model pose histories do.
- **Attachments.** These apply the same endpoint composition to the socket chain's
  `[prev, curr]` pairs (`world/scene.rs:852`), including on models without `Pose`. A
  socketed prop therefore follows the drawn node, as it does under `Offset`. A content
  digest, like `offsets` (`world.rs:359`), detects changes.
- **Culling.**
  - The GPU cull bounds a skinned record by its mesh sphere under every joint of the
    frame's palette (`cull.wgsl:70`). That bound is conservative and never stale, but
    looser than the static bound.
  - Blended parts on the palette path are never culled on the CPU (`renderer/draw.rs`,
    `order_translucent`: only records without a skin are). They sort by their rest
    centre, as clip-animated parts do.
- **LOD.** Each level resolves names against its own model. A static far level ignores
  the rows and dispatches no skin job.

### D6. Presentation storage keeps its pages

Presentation clearing currently frees each emptied 512-row page and re-allocates and
zeroes it on the next present (`storage/raw.rs` `clear_slot`, `Bytes::new`). It also
collects the names of written columns into a fresh `Vec` (`world/presentation.rs:19`).

`clear_presentation` will instead drop the values and keep both the pages and a reused
scratch list. This helps every presentation component.

**Reclamation.** A page that is still empty after 60 consecutive presents (one second
at 60 Hz) is freed. Retention is therefore bounded by the pages that held a row within
the last 60 presents, and in any case by the peak entity index.

A `NodeOffsets` page is 512 rows × about 1.3 KB, roughly 0.65 MB. It costs that whether
it is retained or re-allocated, and the reviewers' two cases show the range:

- 1,000 avatars spread over 20,000 entity indices touch about 40 pages, about 26 MB
  (Fable).
- 1,000 avatars on distinct pages would hold about 650 MB (Astra). That is the paged
  layout's worst case for large rows; it is not caused by retention.

## Cost

These figures are read from the code. The proof measures them; none is asserted from
source inspection beyond these.

| | 30 avatars | 1,000 avatars |
|---|---|---|
| Pose upload per tick (one span, 1.6 KB for `avatar-0`) | 48 KB (2.9 MB/s) | 1.6 MB (96 MB/s) |
| Skin jobs per frame | 60 | ≤ 2,000, drawn levels only |
| `NodeOffsets` written per present | 39 KB | 1.3 MB |

**Per frame**, each job composes its whole hierarchy serially on one lane (`skin.wgsl`).
Spans do not remove that duplication.

**Per vertex**, merged weight-one vertices run the generic four-influence blend and the
cofactor normal (`model_vertex.wgsl`, `skinned`). The static path runs neither.

**At 1,000 avatars**, `pack` still packs every instance's level-0 span, even beyond a
static far level. If the Pixel 5 measurement shows the upload, the next cut is to pack
drawn levels only and write the dirty range.

**Resident presentation memory** is 0.65 MB per page holding avatars (D6): about
0.65 MB for castle-town's 30, about 26 MB for 1,000 over 20,000 indices, and at most
650 MB with one per page.

## Not in scope

- Replacement semantics, and parent-axes rows. Trigger: a posed model that the export
  cannot restructure. Note that a true parent-frame pre-multiply, `p′ + r′·p`, would
  rotate a leg about the hip's parent, which nobody wants.
- Double-buffered presentation columns. The stock observer already feeds both
  endpoints.
- A saved procedural layer that gameplay can see, applied before IK. Trigger: the first
  game that reads one.
- Packing drawn levels only, uploading only posable nodes, and a weight-one fast path
  for merged vertices.
- Keeping unmarked subtrees of a posable model statically merged.
- Moving `NodeMaterials` to `NodeName`.
- `CustomMaterial` on posable models.
- Presenting at display rate.
- Castle's network walk hints.

## Alternatives considered

- **Write `Pose` in `tick`.** This saves and hashes derived state (400 floats against 9),
  moves pins when only visuals change, gives `Pose` a second writer, and still needs D4.
- **Generated clips with `Animator`/`Blend`, plus `Layers` for air and lean.** That is
  four to six saved, CPU-sampled layers per avatar, and only an approximation of the
  speed-dependent amplitude.
- **Parts as entities, or `Offset` per part.** This contradicts "imported nodes are never
  entities" (`asset/pose.rs:6`), multiplies entities by about 6, and splits each model.
- **An empty clip or a weight-one skin at export.** This is fake data used to select a
  render path.
- **Promoting a model on the first `NodeOffsets` that names it.** Pixels would then
  depend on history, and the rebatch would hitch mid-session.
- **Per-node CPU transforms on the static path.** This interpolates composed matrices,
  which is wrong under rotation.
- **A `Present` call into an engine-side table.** Agents could not read it, and neither
  clearing nor save refusal would cover it.

## Proof

1. **Engine.**
   - Hashes and saves are equal with and without `NodeOffsets`.
   - Paranoid every-tick presents compare equal.
   - The whole clear, present and feed cycle allocates nothing once warm, with avatar
     entity indices both clustered and sparse.
   - A sparse population and a churning one (avatars spawned and despawned across
     pages) report resident presentation bytes. A page left empty is freed after 60
     presents.
   - Duplicate posable names and sheared nodes are refused.
2. **Render (GPU).** A test model in `render/src/test_model.rs` with a clip, a two-bone
   IK chain and a posable node shows:
   - the palette equals the CPU `joint_matrix` of `base ∘ offset` at alpha 0, ½ and 1;
   - the order is clip, then IK, then offset.

   Other tests show:
   - an unmarked model keeps zero weight bytes;
   - a posable avatar with a mirror group draws at rest with the same pixels as its
     static draw, both merged and as a lone rigid part;
   - a zero-quaternion row draws as the identity, and a row whose composed endpoint
     overflows draws the base;
   - every priming event in D5 primes, and a same-tick re-present does not shift;
   - a removed row eases to the identity;
   - a socketed prop follows its node;
   - a LOD level without the names ignores the rows;
   - one pose span serves both of an instance's jobs.
3. **Measurement**, on the Pixel 5 and the iPad Pro 12.9″ (M1), in castle-town:
   - Populations: 30 and 1,000 avatars, each all near, beyond a static far level, and
     offscreen; with shadows.
   - Each population runs with offsets and without them (the static path).
   - Report: `pack` CPU time, allocations, upload bytes, and the `skin palettes`, cull
     and geometry GPU times (`bun scripts/agent.mjs perf`).
   - Also, a stride of screenshots compared with Castle's.
4. LLP 1046.003 records what landed.
