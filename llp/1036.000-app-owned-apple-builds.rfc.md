## Summary

Make an Apple build's executable, modules, metadata and bundle belong to the
resolved app throughout the build and launch. Building LLP and Weatherlight
concurrently must produce two correct apps, and `agent --app llp` must select
LLP regardless of which build finished last. This is the first recommended
1036 repair: the present failure can package and launch another application's
code. Implementation evidence and remaining limits are recorded below.

## 1. Evidence and the full boundary

On 2026-09-11, invoking the exported path helpers for `com.exact.llp` and
`com.exact.weatherlight` returned the same paths:

| Artifact | Current path under `host/apple/` |
|---|---|
| Swift scratch, both updating compositions | `.build/composition-updating` |
| macOS executable | `.build/arm64-apple-macosx/release/ExactMac` |
| Simulator bundle | `.build/ExactIOS.app` |
| Device bundle | `.build/device/ExactIOS.app` |
| Simulator sample host | `.build/ExactHostIOS.app` |

`build.mjs::main` links in the composition scratch directory, republishes into
the shared product directory, then copies from there into an app-specific Mac
bundle. The shared directory also receives `libexact_gpu.dylib`,
`libexact_web.dylib`, the plist sidecar and `receipt.json`.
`scripts/agent.mjs` and `scripts/metrics.mjs` import its global binary paths.
SwiftPM serializing its own build does not protect the subsequent copies.
The wrong-app launch is the witnessed QUEUE incident; this audit verified
path aliasing, not another concurrent packaging failure.

## 2. Proposal

**One path resolver, with an app argument.** Replace `macBinary`,
`macHostBinary`, `appBundle`, `deviceBundle` and `hostBundle` constants with an
Apple artifact resolver in the existing build module. It consumes
`scripts/app.mjs::resolveApp`; it does not rediscover external workspaces.
Its build namespace includes the canonical app directory and manifest id,
Rust target/Apple SDK destination, composition and trust policy. Put it below
the app's resolved target directory. Including the source directory keeps two
checkouts with the same bundle id apart even with a shared target override.
Simulator and device outputs are distinct, as are standalone and sample hosts.

**Private products all the way to packaging.** Give SwiftPM that namespace's
scratch path and copy directly from its completed products into an invocation's
private stage. The archive selected by the bake, GPU/WebKit modules, plist,
assets and receipt are captured for that invocation; later steps do not reread
a globally published `ExactMac`. Retain warm Cargo dependency caches. If two
builds can overwrite the same *named Cargo output*, protect build-and-capture
for that output or isolate it; Swift isolation alone is insufficient. Ordinary
in-repo app archives already have distinct crate names.

**One writer per source/app.** Hold a source/app-scoped build lock from bake
through placement, shared by all its Apple build forms and trust/composition
choices. A second writer gets a clear busy error identifying the owner and
app. Different apps continue concurrently; same-app macOS/iOS builds serialize.
Use an ephemeral lock inside the build output, with exception
cleanup; no lock service, timeout-based stealing or global Apple-build lock.
For a stale owner, require explicit removal after verifying it is no longer
running. Keep a stable Mac bundle per source/app at
`<target>/clients/<source-key>/<id>/macos/<Name>.app`, with `source-key` derived
from the canonical app directory, so a shared target and bundle id cannot alias
two checkouts. All consumers learn this path from the resolver.
Stage complete bundles beside their destination, preserve new-inode replacement
for mapped signed files, and retain/restore the previous bundle if placement
fails. A bare build and a bundled build share the lock even though they request
different final outputs from the same scratch directory.

**Launch the same artifact the builder names.** Change `agent`, `metrics`,
`exact run`, the simulator install helper and both sample-host paths together.
They ask the resolver for the selected app's artifact; no fallback to the last
shared product. Keep the existing explicit binary override for diagnostics,
with an app-identity check before driving it. Packaging and driving both check
the executable's embedded app identity against the manifest; checking only the
plist or receipt would let the original failure pass. The existing wrong-app
guard stays as a cheap assertion, not the concurrency mechanism.

## 3. Proof and deletion

Land the resolver, producer and all consumers in one change. Delete the shared
product publication step, app-independent path constants and installer defaults.
There is no compatibility symlink at the old paths. Update the existing build
instructions instead of adding a launcher or a registry.

Extend the existing Apple/script tests with path separation and failed-placement
cases. Then run a real concurrent LLP/Weatherlight build and drive each through
`agent --app <name>`: check distinctive tree/state content, embedded identity,
receipt, bundle identity and signature, after both builds finish. Reverse their
completion order. A copied executable under the other app's plist must be
refused. A same-app contender must fail before touching artifacts, and a
failed rebuild must leave the previous app runnable. Include an external app
and two source directories sharing a bundle id in the path/capture cases.

Sweep simulator, device packaging and `--host` through the same resolver;
exercise both `embedded` and `updating` compositions without adding a Cargo
feature. Report cold and warm build times and disk growth: per-app Swift caches
cost space, while a same-app rebuild must retain incremental compilation.
The real Apple builds run asynchronously outside the blocking minute. The five
existing checks remain the checks. Delete F4's QUEUE line only after the build
and driver proof passes.

## 4. Boundary

This changes build ownership, not delivery identity or signing policy. It does
not unify the web dev output, invent a build scheduler, or redesign the CLI.
The decision to make is whether this bounded correctness repair goes first;
the recommendation is yes.

## Implementation and lane validation — 2026-09-11

Implemented in `host/apple/build.mjs`, `scripts/app.mjs`, `agent.mjs`,
`exact.mjs` and `metrics.mjs`. The source key also scopes default bake output.
The shared bake takes named Cargo-output claims through its capture callback;
archive/module bytes must match the completed product hashes before capture.
Swift links captured archives, and complete stages replace standalone and sample
products independently. App claims release after placement, before a foreground
launch. Failed placement restores the previous artifact; failed signing never
publishes its private stage. Packaging and driving inspect the embedded COMPAT
identity, including an explicit diagnostic binary override.

Two overlapping LLP/Weatherlight macOS runs passed with opposite completion
orders: LLP then Weatherlight (35.7/71.8 seconds), Weatherlight then LLP
(43.0/66.4 seconds). Both were driven after both builds completed; their distinct
`llp-main`/`weatherlight` trees, state, embedded IDs, receipts, bundle plists and
deep signatures agreed. Sample-host and standalone paths both remained usable
following `--host`. A Weatherlight executable under LLP's plist and receipt,
re-signed as that bundle, was refused before launch. A same-app macOS contender
was refused while its iOS build held the claim. A running foreground app released
its claim, and a deliberately failed signing rebuild retained a runnable prior
binary. The existing Apple tests cover source aliases, external same-id source
directories, trust/destination separation, named-product capture mismatch,
failed placement restoration and a real child-process lock contender.

Cold Swift namespaces took 24.0 seconds for LLP and 29.1 for Weatherlight;
subsequent standalone relinks took 0.47–0.94 seconds. A quiet warm Weatherlight
build reported 6.5 seconds Cargo and 7.2 seconds Swift plus the WebKit arm.
Per-app Swift scratch costs were approximately 83 MiB for LLP, 105 MiB for
Weatherlight and 95 MiB for updating Caltrain; Cargo dependency caches remained
shared. These are this Mac's measurements, including concurrent load where
reported, not new gates.

Updating Caltrain macOS sample-host smoke passed; the simulator standalone and
sample bundles passed identity/receipt/signature checks and session routing.
External Weird Castle's updating bundle built and drove successfully using its
existing path dependencies. LLP's device bundle and updating Caltrain's device
standalone/sample bundles built, signed and installed; the latter also passed
embedded-identity, receipt, plist and deep-signature checks. `exact run llp`
completed its native smoke, and `--host --embed` produced the captured archive
and independently drivable standalone/sample products.
Apple inherited tests (6), script caps regressions, Apple clippy, formatting and
boot passed. Integrated workspace validation remains the parent run's gate.

Limitations observed during the wider sweep: the simulator sample smoke failed
`a's blur reached b: keyboard 0 → 0, searchFocused true`. Standalone simulator
smoke had six software-keyboard/inset assertions and a canvas-reference mismatch
(76.65% pixels beyond its band; mean 80.65); its three Contract assertions passed.
`com.apple.iphonesimulator ConnectHardwareKeyboard` was `1`, and keyboard overlap
stayed zero. No baseline comparison established the causes. The physical phone
installed the selected bundle but its agent connection failed `No route to host`.
These are recorded separately from the passed build-ownership proof.

## 5. One Swift compile for every app — 2026-10-04

§2 gave each app its own SwiftPM scratch. The Swift host is the same code for
every app, and it has grown: on a quiet M4 a new scratch now takes 53–60
seconds, in one thread, and every app paid it again for each destination,
composition and trust policy. A second app's first macOS build was 86 seconds,
61 of them recompiling ExactKit.

The scratch is now one per destination and deployment target,
`<target>/apple-swift/<destination>-<minimum OS>`, for every app, composition
and trust. What §2 required still holds, by different means:

- **The link is the app's, and private from there.** An app's build takes a
  claim beside the shared scratch, removes the executable, runs `swift build`,
  and copies the executable to its own stage before letting the claim go. The
  embedded-identity check runs on that copy, as before.
- **The claim waits.** Another app's build of the same destination waits for
  it and says whose build it is waiting for; a dead owner's claim is taken.
  It is held for the Swift step only (about a second once ExactKit is
  compiled), so two apps still bake, package and sign concurrently. This is
  the one place §2's "no global Apple-build lock" gives way.
- **Composition changes two small targets.** `ExactComposition` and the
  executable's `main.swift` recompile when the next app has the other
  composition: 2.5 seconds, against a second 55-second scratch.
- **The app's own directory** (`…/<trust>/link`) keeps what names the app: its
  entitlements, its typed data keys and its module artifact's cache. The web
  and video arms are cached in the shared scratch.

In the same change the host's two Rust modules (`exact-svg-raster`,
`exact-canvas-vello`) build with the app's profile. A development build's were
`release`: the kernel compiled a second time in one codegen unit and through
thin LTO. `apple-dev` is now unstripped as a profile, so the archive, the GPU
crate and those two modules share their units.

Measured on an M4 Mac mini (10 cores, 16 GB), quiet, Caltrain unless named:

| | before | after |
|---|---|---|
| Cold macOS build | 184 s | 151 s |
| First iOS simulator build, after the macOS one | 176 s | 132 s |
| Second app, first build (Markdown, macOS) | 86 s | 29 s, 23 of them its own Rust; 6 s once that is built |
| Third app, first build (Sparkline, macOS) | 68 s | 9 s |
| Second app, first build (Markdown, iOS simulator) | 90 s | 26 s |
| Touch `kernel/src/lib.rs` | 35 s | 8.6 s |
| Nothing changed, iOS simulator | 12.8 s | 5.7 s |
| Nothing changed, macOS | 4.5 s | 4.5 s |

The iOS no-op row is a separate fix: the GPU module's signed copy was verified
against a certificate requirement an ad-hoc signature cannot meet, so every
simulator build signed it again and reran the app's bake.
