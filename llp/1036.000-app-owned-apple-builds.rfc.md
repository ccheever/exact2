**Implementer:** Astra high / apple_builds, from 2026-09-11

**Author:** Codex for Charlie Cheever
**Date:** 2026-09-11

**Related:** [LLP 1036 F4](1036-elegance-frictions.research.md#f4-concurrent-apple-builds-ship-each-others-binaries); [LLP 1030 D2/D4](1030-delivery-unified.rfc.md#d2--host-metadata-is-a-baked-artifact-from-one-manifest-policy-is-not-identity); [LLP 1031 D6/D10](1031-brownfield-embedding.rfc.md); [LLP 1033 D2](1033-markdown-viewer.plan.md); [LLP 1008](1008-apple-host-v1.spec.md); [LLP 1012](1012-agent-api-v1.spec.md)

## Summary

Make an Apple build's executable, modules, metadata and bundle belong to the
resolved app throughout the build and launch. Building LLP and Weatherlight
concurrently must produce two correct apps, and `agent --app llp` must select
LLP regardless of which build finished last. This is the first recommended
1036 repair: the present failure can package and launch another application's
code. Implementation evidence and remaining limits are recorded below.

## 1. Evidence and the full boundary

On 2026-09-11, invoking the exported path helpers for `com.exact.llp` and
`com.exact.weatherlight` returned the same paths:

| Artifact | Current path under `host/apple/` |
|---|---|
| Swift scratch, both updating compositions | `.build/composition-updating` |
| macOS executable | `.build/arm64-apple-macosx/release/ExactMac` |
| Simulator bundle | `.build/ExactIOS.app` |
| Device bundle | `.build/device/ExactIOS.app` |
| Simulator sample host | `.build/ExactHostIOS.app` |

`build.mjs::main` links in the composition scratch directory, republishes into
the shared product directory, then copies from there into an app-specific Mac
bundle. The shared directory also receives `libexact_gpu.dylib`,
`libexact_web.dylib`, the plist sidecar and `receipt.json`.
`scripts/agent.mjs` and `scripts/metrics.mjs` import its global binary paths.
SwiftPM serializing its own build does not protect the subsequent copies.
The wrong-app launch is the witnessed QUEUE incident; this audit verified
path aliasing, not another concurrent packaging failure.

## 2. Proposal

**One path resolver, with an app argument.** Replace `macBinary`,
`macHostBinary`, `appBundle`, `deviceBundle` and `hostBundle` constants with an
Apple artifact resolver in the existing build module. It consumes
`scripts/app.mjs::resolveApp`; it does not rediscover external workspaces.
Its build namespace includes the canonical app directory and manifest id,
Rust target/Apple SDK destination, composition and trust policy. Put it below
the app's resolved target directory. Including the source directory keeps two
checkouts with the same bundle id apart even with a shared target override.
Simulator and device outputs are distinct, as are standalone and sample hosts.

**Private products all the way to packaging.** Give SwiftPM that namespace's
scratch path and copy directly from its completed products into an invocation's
private stage. The archive selected by the bake, GPU/WebKit modules, plist,
assets and receipt are captured for that invocation; later steps do not reread
a globally published `ExactMac`. Retain warm Cargo dependency caches. If two
builds can overwrite the same *named Cargo output*, protect build-and-capture
for that output or isolate it; Swift isolation alone is insufficient. Ordinary
in-repo app archives already have distinct crate names.

**One writer per source/app.** Hold a source/app-scoped build lock from bake
through placement, shared by all its Apple build forms and trust/composition
choices. A second writer gets a clear busy error identifying the owner and
app. Different apps continue concurrently; same-app macOS/iOS builds serialize.
Use an ephemeral lock inside the build output, with exception
cleanup; no lock service, timeout-based stealing or global Apple-build lock.
For a stale owner, require explicit removal after verifying it is no longer
running. Keep a stable Mac bundle per source/app at
`<target>/clients/<source-key>/<id>/macos/<Name>.app`, with `source-key` derived
from the canonical app directory, so a shared target and bundle id cannot alias
two checkouts. All consumers learn this path from the resolver.
Stage complete bundles beside their destination, preserve new-inode replacement
for mapped signed files, and retain/restore the previous bundle if placement
fails. A bare build and a bundled build share the lock even though they request
different final outputs from the same scratch directory.

**Launch the same artifact the builder names.** Change `agent`, `metrics`,
`exact run`, the simulator install helper and both sample-host paths together.
They ask the resolver for the selected app's artifact; no fallback to the last
shared product. Keep the existing explicit binary override for diagnostics,
with an app-identity check before driving it. Packaging and driving both check
the executable's embedded app identity against the manifest; checking only the
plist or receipt would let the original failure pass. The existing wrong-app
guard stays as a cheap assertion, not the concurrency mechanism.

## 3. Proof and deletion

Land the resolver, producer and all consumers in one change. Delete the shared
product publication step, app-independent path constants and installer defaults.
There is no compatibility symlink at the old paths. Update the existing build
instructions instead of adding a launcher or a registry.

Extend the existing Apple/script tests with path separation and failed-placement
cases. Then run a real concurrent LLP/Weatherlight build and drive each through
`agent --app <name>`: check distinctive tree/state content, embedded identity,
receipt, bundle identity and signature, after both builds finish. Reverse their
completion order. A copied executable under the other app's plist must be
refused. A same-app contender must fail before touching artifacts, and a
failed rebuild must leave the previous app runnable. Include an external app
and two source directories sharing a bundle id in the path/capture cases.

Sweep simulator, device packaging and `--host` through the same resolver;
exercise both `embedded` and `updating` compositions without adding a Cargo
feature. Report cold and warm build times and disk growth: per-app Swift caches
cost space, while a same-app rebuild must retain incremental compilation.
The real Apple builds run asynchronously outside the blocking minute. The five
existing checks remain the checks. Delete F4's QUEUE line only after the build
and driver proof passes.

## 4. Boundary

This changes build ownership, not delivery identity or signing policy. It does
not unify the web dev output, invent a build scheduler, or redesign the CLI.
The decision to make is whether this bounded correctness repair goes first;
the recommendation is yes.

## Implementation and lane validation — 2026-09-11

Implemented in `host/apple/build.mjs`, `scripts/app.mjs`, `agent.mjs`,
`exact.mjs` and `metrics.mjs`. The source key also scopes default bake output.
The shared bake takes named Cargo-output claims through its capture callback;
archive/module bytes must match the completed product hashes before capture.
Swift links captured archives, and complete stages replace standalone and sample
products independently. App claims release after placement, before a foreground
launch. Failed placement restores the previous artifact; failed signing never
publishes its private stage. Packaging and driving inspect the embedded COMPAT
identity, including an explicit diagnostic binary override.

Two overlapping LLP/Weatherlight macOS runs passed with opposite completion
orders: LLP then Weatherlight (35.7/71.8 seconds), Weatherlight then LLP
(43.0/66.4 seconds). Both were driven after both builds completed; their distinct
`llp-main`/`weatherlight` trees, state, embedded IDs, receipts, bundle plists and
deep signatures agreed. Sample-host and standalone paths both remained usable
following `--host`. A Weatherlight executable under LLP's plist and receipt,
re-signed as that bundle, was refused before launch. A same-app macOS contender
was refused while its iOS build held the claim. A running foreground app released
its claim, and a deliberately failed signing rebuild retained a runnable prior
binary. The existing Apple tests cover source aliases, external same-id source
directories, trust/destination separation, named-product capture mismatch,
failed placement restoration and a real child-process lock contender.

Cold Swift namespaces took 24.0 seconds for LLP and 29.1 for Weatherlight;
subsequent standalone relinks took 0.47–0.94 seconds. A quiet warm Weatherlight
build reported 6.5 seconds Cargo and 7.2 seconds Swift plus the WebKit arm.
Per-app Swift scratch costs were approximately 83 MiB for LLP, 105 MiB for
Weatherlight and 95 MiB for updating Caltrain; Cargo dependency caches remained
shared. These are this Mac's measurements, including concurrent load where
reported, not new gates.

Updating Caltrain macOS sample-host smoke passed; the simulator standalone and
sample bundles passed identity/receipt/signature checks and session routing.
External Weird Castle's updating bundle built and drove successfully using its
existing path dependencies. LLP's device bundle and updating Caltrain's device
standalone/sample bundles built, signed and installed; the latter also passed
embedded-identity, receipt, plist and deep-signature checks. `exact run llp`
completed its native smoke, and `--host --embed` produced the captured archive
and independently drivable standalone/sample products.
Apple inherited tests (6), script caps regressions, Apple clippy, formatting and
boot passed. Integrated workspace validation remains the parent run's gate.

Limitations observed during the wider sweep: the simulator sample smoke failed
`a's blur reached b: keyboard 0 → 0, searchFocused true`. Standalone simulator
smoke had six software-keyboard/inset assertions and a canvas-reference mismatch
(76.65% pixels beyond its band; mean 80.65); its three Contract assertions passed.
`com.apple.iphonesimulator ConnectHardwareKeyboard` was `1`, and keyboard overlap
stayed zero. No baseline comparison established the causes. The physical phone
installed the selected bundle but its agent connection failed `No route to host`.
These are recorded separately from the passed build-ownership proof.

## 5. One Swift compile for every app — 2026-10-04

§2 gave each app its own SwiftPM scratch. The Swift host is the same code for
every app, and it has grown: on a quiet M4 a new scratch now takes 53–60
seconds, in one thread, and every app paid it again for each destination,
composition and trust policy. A second app's first macOS build was 86 seconds,
61 of them recompiling ExactKit.

The scratch is now one per destination and deployment target,
`<target>/apple-swift/<destination>-<minimum OS>`, for every app, composition
and trust. What §2 required still holds, by different means:

- **The link is the app's, and private from there.** An app's build takes a
  claim beside the shared scratch, removes the executable, runs `swift build`,
  and copies the executable to its own stage before letting the claim go. The
  embedded-identity check runs on that copy, as before.
- **The claim waits.** Another app's build of the same destination waits for
  it and says whose build it is waiting for; a dead owner's claim is taken.
  It is held for the Swift step only (about a second once ExactKit is
  compiled), so two apps still bake, package and sign concurrently. This is
  the one place §2's "no global Apple-build lock" gives way.
- **Composition changes two small targets.** `ExactComposition` and the
  executable's `main.swift` recompile when the next app has the other
  composition: 2.5 seconds, against a second 55-second scratch.
- **The app's own directory** (`…/<trust>/link`) keeps what names the app: its
  entitlements, its typed data keys and its module artifact's cache. The web
  and video arms are cached in the shared scratch.

In the same change the host's two Rust modules (`exact-svg-raster`,
`exact-canvas-vello`) build with the app's profile. A development build's were
`release`: the kernel compiled a second time in one codegen unit and through
thin LTO. The development profile (`host-dev`, `apple-dev` until this date) is
now unstripped as a profile, so the archive, the GPU crate and those two
modules share their units.

Measured on an M4 Mac mini (10 cores, 16 GB), quiet, Caltrain unless named:

| | before | after |
|---|---|---|
| Cold macOS build | 184 s | 151 s |
| First iOS simulator build, after the macOS one | 176 s | 132 s |
| Second app, first build (Markdown, macOS) | 86 s | 29 s, 23 of them its own Rust; 6 s once that is built |
| Third app, first build (Sparkline, macOS) | 68 s | 9 s |
| Second app, first build (Markdown, iOS simulator) | 90 s | 26 s |
| Touch `kernel/src/lib.rs` | 35 s | 8.6 s |
| Nothing changed, iOS simulator | 12.8 s | 5.7 s |
| Nothing changed, macOS | 4.5 s | 4.5 s |

The iOS no-op row is a separate fix: the GPU module's signed copy was verified
against a certificate requirement an ad-hoc signature cannot meet, so every
simulator build signed it again and reran the app's bake.

## 6. Development builds compile Swift incrementally — 2026-10-04

With one scratch for every app, what remained was the compile itself: SwiftPM's
release configuration compiles ExactKit as one whole module, in one thread (34
of its 49 seconds are the SIL optimizer), so one edited Swift file rebuilt all
196.

A development build now uses the debug configuration with `-O` on top: the same
optimizer, file by file and incrementally. A production bake (`EXACT_UPDATE_TRUST
=production`) and an archive (`--archive`) keep the whole-module build. This is
the Swift half of what `host-dev` already is for the Rust half.

Measured on the same M4, through `build.mjs`:

| | whole module | incremental |
|---|---|---|
| Touch one ExactKit file, macOS | 48 s | 6.1 s |
| Touch one ExactKit file, iOS simulator | 61 s | 8.8 s |
| ExactKit compiled from nothing | 55 s | 25 s |
| `ExactMac`, Caltrain | 13.2 MB | 22.5 MB |

The executable is larger because the debug configuration compiles for
`@testable` and exports every symbol, which also defeats the linker's dead-code
strip. Only a development build carries that.

What it costs at run time, eight alternating launches and three alternating
rounds of each binary: Caltrain's boot is the same (85 ms median both ways) and
its first batch applies in 18.2 ms against 17.8; Messages Stress's resize
acknowledgement over 1,000 eager rows is 58–59 ms against 57–59. About 2% on
the paths that are mostly Swift. A number that is going into a comparison with
another framework should come from a production bake.

## 7. The Swift compile and the host's Rust modules run beside the bake — 2026-10-04

A build ran its steps in a row: the app's GPU crate, its archive, the Swift
host, the arms, then the host's two Rust modules. ExactKit needs nothing of the
app's Rust until the link, and the two modules need nothing of the app at all.

- **ExactKit compiles while Cargo bakes.** The build starts `swift build
  --target ExactKit` in the shared scratch before the bake and waits for it
  only before the link. It takes no claim: what it compiles is the same for
  every app, and SwiftPM's own lock orders two builds in one scratch. A pull
  that changed Rust and Swift rebuilds both at once.
- **The modules have a build directory of their own**, `<target>/apple-modules`,
  and start with it. Cargo runs one build at a time in a directory, so in the
  app's they waited for the whole bake. What they share with the app (the
  kernel) is compiled for both, at the same time. The two copies had already
  parted: the app's graph turns on a `smallvec` feature (through `url`) that
  the module's does not, and Cargo keeps a kernel for each.
- **The last line says what each step still cost**: `cargo`, the bake; `swift`,
  the link and whatever of the compile the bake did not cover; `arms`;
  `modules`, whatever of theirs was still running; `package`.

The same M4, Caltrain, development builds, against the builds of §5 and §6:

| | in a row | beside |
|---|---|---|
| Cold macOS build | 151 s (§5, the whole-module Swift) | 106–111 s |
| First iOS simulator build, after the macOS one | 106 s | 94–97 s |
| Touch `kernel/src/lib.rs` | 8.6 s | 6.7 s |
| Touch one ExactKit file | 6.1 s | 5.4 s |
| Touch both | | 6.4 s |
| Nothing changed, macOS | 4.5 s | 3.6 s |

A cold build on those ten cores is now bound by the processor: 830
CPU-seconds, 150 of them Swift (the incremental compile spends twice the
whole-module one's CPU to finish in half its time). It was 184 s before §5.
On an M5 Pro (18 cores) it is 61 s.

That M5 Pro's shells export `CARGO_INCREMENTAL=0` for another project, and
Cargo lets the variable overrule a profile's `incremental = true`: a touched
kernel line there recompiled the kernel and everything over it whole, 17 s.
The build now keeps `host-dev`'s own setting for its Cargo runs and says that
it is ignoring the variable: 5.5 s. A hand-run `cargo build --profile host-dev`
(the Linux host) still obeys the shell.

## 8. What is distributed — 2026-10-04

An archive (`--archive`) and the Mac bundle `exact release` signs
(`--bundle --distribution`) are built to leave the machine:

- **The whole-module Swift host** (§6), whatever the trust.
- **No local symbols in the executable.** `strip -x` after `dsymutil` has
  written them beside the artifact (`<name>.dSYM`; the image's UUID is kept, so
  a crash report still symbolicates): 3.6 MB of Caltrain's 13.1 MB Mac
  executable. The dylibs stay as they are (Xcode 27's strip, `Cargo.toml`).
- **A receipt without the build's file list.** The receipt inside a bundle held
  every file the binary was compiled from, with this machine's paths: 1.86 MB,
  read only by the driver's staleness check. A distributed bundle carries the
  rest (21 KB); the whole receipt is written beside the artifact.

A production binary at store level 0 runs the plan it was baked with and no
other. The bake's graph lists the loaded modules that plan can reach
(`loads`), each by the rule its host loads it by: the Canvas 2D GPU module for
a `Canvas`, the SVG island module where the runner's `svg_islands` holds, the
video arm for a `Video`, the web arm for a `WebView`. Such a build neither
compiles nor bundles the rest:

| production Mac bundle, store level 0 | carries | bytes beside the binary |
|---|---|---|
| Sparkline | none of the four | 0 (was 4.7 MB) |
| SVG gallery | the SVG island module | 0.47 MB |
| Video player | the video arm | 0.15 MB |
| Canvas gallery | the Canvas 2D GPU module | 3.9 MB |

Sparkline's bundle is 16.3 → 11.6 MB, and its build compiles neither Rust
module nor either Swift arm. A build that carries a Rust module starts its
compile after the bake has said, not before it. Nothing is refused for a
module left out: no node of the plan asks for it, and each loader names its
module when it is absent. A development build and a binary that takes updates
carry all four as before (LLP 1047 D7, D8); the second is QUEUE's.

A production bake for an Apple target optimizes its Rust as one module: fat
LTO where `[profile.release]` says thin. Sparkline's production Mac binary,
on the M4, same commit otherwise, two cold builds each:

| | as built | `strip -x` | cold build | of it Cargo |
|---|---|---|---|---|
| thin LTO | 11.72 MB | 8.81 MB | 76–78 s | 61–62 s |
| fat LTO | 11.56 MB | 8.39 MB (−4.8%) | 82 s | 78 s |

Boot, the runner's layout and the first apply are the same either way (sixteen
alternating launches: apply 16.7 and 16.9 ms, layout 5.1 and 5.1). The bake
says it on Cargo's command line and the profile does not, because `release`
is also every developer tool's profile and only a bake builds for an Apple
target at it, so nothing is compiled under both. The host's two Rust modules
are untouched: they are `rlib` and `cdylib` at once, which Cargo builds with
no LTO at all, and built as `cdylib` alone fat LTO takes 0.1 MB off the canvas
module and thin adds 0.26 MB to it.

Measured beside it and not taken: sixteen codegen units under the same fat
LTO. The cold build is 72 s against 81–84 (Cargo 64 against 78–80), boot and
apply the same, and the binary gives back 1.8% (8.57 MB stripped against
8.42). A production build is made for its bytes; a developer never waits for
one.

Also not taken: `-Osize` for the Swift. The stripped binary
is 7.8% smaller (8.73 → 8.04 MB; 7.62 MB with fat LTO) and the first apply of
Sparkline's 295 views 7% slower (17.9 ms against 16.7). What ships is not made
slower to be smaller without someone ruling so.

## 9. What a build asks every time — 2026-10-04

With nothing changed, a build still asked SwiftPM where it puts its products
(`swift build --show-bin-path`, 0.5 s) and what the package holds (`swift
package describe`, 0.6 s, for the receipt's Swift sources), and an iOS build
remade the app's icons and asset catalog. Each answer is now kept: the output
path in the scratch it names, by compiler and arguments; the description beside
the scratch, by the manifest, the composition and the list of source files; the
assets in the app's own directory, by the icon's bytes, the colours, the
platform and the toolchain.

The same M4: nothing changed, macOS 3.6 → 2.7 s and iOS simulator 5.6 → 4.3 s;
a touched kernel line 6.7 → 6.0 s; a touched ExactKit file 5.4 → 5.2 s (iOS
7.8 → 7.3 s); a touched `app.contract` 4.4 → 3.9 s.

`build.mjs` had reached the 1,500-line cap, so the icon and asset catalog moved
to `host/apple/assets.mjs`.

The web and video arms and an app's own module artifact (and, on iOS, the macOS
probe of it that the roster check loads) were compiled one after another, after
the Swift link. Each is one `swiftc`; they now start before the link and are
waited for after it. An edited file of an app's Swift module (the native
fixture) rebuilds in 4.3 s on macOS, from 6.0, and 6.7 s on the simulator, from
10.1; nothing but that module recompiles.

## 10. The host's Rust modules, kept for the machine — 2026-10-04

The Canvas 2D GPU module and the SVG island module hold nothing of an app, and
were compiled from nothing by the first build of every checkout, beside the
bake: 124 and 62 CPU-seconds. On the ten-core M4 that is a quarter of the
build. Caltrain from an empty `target`, twice each:

| | wall | of it Cargo |
|---|---|---|
| both modules compiled | 106.6, 106.0 s | 101 s |
| both already built | 79.0, 79.7 s | 74 s |

A development build now keeps each module it compiles in
`~/.cache/exact/apple-modules`, and a build in any checkout takes a kept module
whose inputs are this checkout's bytes (`host/apple/modules.mjs`). Two things
say so. The group is everything that is not a source file of ours: the crate,
target and profile, `rustc -vV`, the crate's closure in `Cargo.lock` with each
registry crate's checksum, the workspace manifest apart from its member list,
Cargo's config files, the variables a compile reads, and the SDK, Xcode and
Metal toolchain versions. The entry is every file Cargo's dep-info names for
the module (the sources of the path crates under it and their build scripts'
inputs, directories whole), those crates' manifests, and each variable a build
script asked to be rerun for; every one is compared by SHA-256.

- A checkout that has compiled a module itself goes on asking Cargo, which
  answers in a third of a second and is never stale. The kept module is for
  the checkout that has not.
- A module is kept only when git says its inputs are as committed and none
  changed while it compiled, so an edit loop neither keeps what nobody else
  will have nor pushes out what they will. Six entries a group, twenty-four
  groups.
- A checkout that took a module remembers what it saw (each input's size and
  modification time); while that holds, the next build does not hash or ask
  `rustc` anything. The search itself is 50 ms.
- A production build compiles what it ships.

Built, on the same M4: a first checkout's first build 106.9 s, keeping both; a
second checkout's first build 79.5 and 76.7 s, taking both; its next build,
nothing changed, 3.3 s. For the iOS simulator, 113.6 and 77.7 s. On the
eighteen-core M5 under load the two first Mac builds were 95 and 63 s.

The canvas module's inputs are four crates that change rarely, so nearly every
fresh checkout takes it. The SVG module's include the kernel, so it is taken
only from a checkout at the same kernel; the first build that changes the
kernel compiles it there, as before.

## 11. Compiled registry crates, kept for the machine — 2026-10-04

With the two modules kept, a fresh checkout's first build on the M4 was 78 s,
73 of them Cargo compiling 228 crates, of which 190 are from the registry: the
same bytes in every checkout, compiled again by each. A development build now
keeps what Cargo compiled of them in `~/.cache/exact/apple-crates`, and a
target directory that has compiled nothing starts as a copy-on-write clone of
what is kept (`host/apple/crates.mjs`).

| the M4, Caltrain | wall | of it Cargo | crates compiled |
|---|---|---|---|
| a first checkout, macOS | 81.3 s | 76 s | 228 |
| a second checkout, macOS | 58.7, 57.8 s | 53–54 s | 38 |
| a first checkout, iOS simulator (after its macOS build) | 76.7 s | 69 s | 187 |
| a second checkout, iOS simulator, installed and launched | 55.7, 57.8 s | 47–49 s | 29 |

On the eighteen-core M5 under load, a fresh worktree's first build was 95 s
before the two sections above, 63 s with the modules kept, and 34 s with this.

Nothing here decides whether a unit may be used. Cargo does, by the unit's own
fingerprint (compiler, profile, features, target, and every crate under it)
and by the order of its files' times, exactly as it would had the directory
been moved. Three things follow from leaving it to Cargo.

- **What is kept is one target directory at a time**, whole and with its
  times: a generation. Units from two directories are never put together. The
  first version did (it kept each unit the first time any build had it) and
  Cargo rebuilt a hundred of them in the next checkout, rightly: a unit from
  the modules' directory was newer than one from the app's compiled against
  its twin. Two builds of one unit are not interchangeable to what was
  compiled against them, since a crate that includes a file from its build
  script's directory has that directory in its hash, and the times are what
  say which were built together. A directory that started from a generation,
  or made the first, makes the next when it has compiled a registry unit the
  newest lacks; a directory that compiled apart from them keeps nothing. Two
  generations stay.
- **A kept unit is of a registry package with no path crate under it**, by any
  version of its name. A path crate's unit names its checkout, so it and all
  above it are no use to another. That leaves out `wgpu-core` and `wgpu`,
  which stand on the vendored `wgpu-hal`, and they are most of what a second
  checkout still compiles that is not ours.
- **rustc's dep-info is rewritten.** A `.d` file names the target directory it
  was written in, and the bake's receipt reads it as the evidence of what a
  unit was compiled from. It is kept with that directory as a token and
  written out with the taker's, its time unchanged.

A production build compiles everything it ships. A build after the first costs
this one stat per profile directory. The store on the M4 is 1.7 GB for macOS
and the simulator together, of blocks shared with every target directory
cloned from it.

## 12. The SVG module does not compile the kernel — 2026-10-04

`exact-svg-raster` read one thing of the kernel's, the resolved filter chain
and its wire form (`svg::filter`: `Filter`, `Primitive`, `Op` and their kin,
`encode`, `decode`), and for it compiled the kernel, Taffy, motion and text
flow a second time in its own build directory: 62 CPU-seconds from nothing,
and again, incrementally, after every kernel edit. Its kept copy (§10) was
keyed by all of those sources, so a checkout with any other kernel compiled
its own.

The chain is now a crate, `exact-svg-filter`, with no dependency. The kernel
depends on it and re-exports it where it was (`exact_kernel::svg::filter`), so
nothing else that names those types changed; the CSS filter-function list,
which needs the kernel's colours and parser, stayed. The module's graph is two
crates where it was thirty-nine.

| the M4, Caltrain | before | after |
|---|---|---|
| a fresh checkout whose kernel no kept module was built from | 66.6, 66.9 s | 59.3, 59.5 s |
| the first touched kernel line in it | 9.3 s | 6.2 s |

The SVG gallery's pages 8 to 10, the filters' page among them, are the same
bytes before and after (`agent.mjs macos --app svg-gallery "tap page-9" …
screenshot`).

## 13. What every build paid again — 2026-10-04

A build with nothing changed was 2.7–2.9 s on the M4, and little of it was
Cargo or SwiftPM finding nothing to do. Timed inside the bake, on the M5: the
two `cargo` runs 0.15 s each; `cargo metadata` 0.17 s; the receipt 0.41 s; then
a link of the executable, every time.

- **The receipt named 3,700 inputs by scanning 300 roots for each.** An
  input's name is its path under the longest package or generated directory
  that holds it, found by `find` over the roots, longest first, with a path
  comparison each: 0.2 s. It is now the first of the path's own ancestors that
  is a root, which is the same answer. The receipt Caltrain's build writes is
  the same bytes, product hashes aside.
- **It read every input's bytes to hash them.** A development bake keeps each
  hash in the target directory with the size and time its file had, which is
  what Cargo goes by to call the unit built from it fresh, and reads a file
  again when either differs. A production receipt reads every byte. Checked by
  hashing all 3,655 inputs and the three products from their bytes against a
  receipt written from the kept hashes: no difference.
- **`cargo metadata` was asked every build.** A development bake keeps the
  answer with the size and time of the lock, the toolchain file and every path
  crate's manifest, and asks again when one differs.
- **The executable was linked on every build.** SwiftPM does not see the Rust
  archive, which is named to the linker by `-L` and `-l`, so the build dropped
  the executable to have it linked again: 0.4 s. And the archive SwiftPM would
  have seen was a new file each time, copied into a fresh capture directory. A
  development build now takes an archive whose bytes the last capture holds
  from that capture, the same file, and drops the executable only when
  `<product>.linked` beside it names another archive, another app's, or other
  simulator entitlements. Changing `app.contract` relinks (the plan is in the
  archive) and the driven app shows the change; so does a kernel line; two
  apps built in turn each get their own.
- **SwiftPM was asked after the bake, though it needs nothing of it when the
  archive is as it was.** A development build whose last link in the scratch
  was this app's starts the product's build at the start, where it started
  only ExactKit's compile, and holds the link's claim from there. When the
  bake leaves `<product>.linked` true, that build was the link and nothing
  runs after; when it does not, the executable is dropped and linked as
  before. With another app linking, a second product (`--host`), or a first
  build, the build is as it was. A changed Swift file with the Rust untouched
  is compiled and linked by the early build, and the placed binary has it.
- **Four apps rebuilt themselves every time.** Sparkline, the SVG gallery, the
  map demo and the carousel told Cargo to watch `../assets`, which they do not
  have, and a watched path that is missing is always changed: the bake ran,
  the app's crate compiled and the executable linked on every build. The bake
  already watches an optional asset root the safe way (its nearest existing
  ancestor; `bake/src/receipt/watch.rs`), so the line is gone from those eight
  build scripts. Making and removing `assets/` still rebuilds.
