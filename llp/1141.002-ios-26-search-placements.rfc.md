## Summary

iOS 26 gives search two places Exact cannot ask for: a **search tab**, set apart at the
trailing end of the tab bar, whose root screen's search field sits at the bottom where the tab
bar was; and a **minimized toolbar search**, a button at the bottom of a screen that expands
into a field in place. Every Exact build in the pilot lacked the first; Hackers' build pushed a
whole search route for want of the second.

| | Decision |
|---|---|
| D1 | A root tab that says `rel="search"` is the app's search tab. It stays `role="tab"`. |
| D2 | iOS 18 and later build the tab bar from `UITab`s, and the search tab is a `UISearchTab`; each other host keeps it in its place. |
| D3 | The search tab's field is its root route's header search; `autofocus` on it is `automaticallyActivatesSearch`. |
| D4 | `field-sizing="content"` on a header's search field is the minimized search: `.integratedButton`. |
| D5 | A root route's header search keeps UIKit's `hidesSearchBarWhenScrolling`, and shows at rest wherever a hand-built screen's does. |
| D6 | The agent drives both as it drives tabs and header search now, and `tree` says which placement UIKit chose. |
| D7–D8 | Tests, and the docs, recipes and compiler messages that teach both. |

## 1. Evidence

**React Conf** (Expo Router). The original marks its Speakers tab
`NativeTabs.Trigger role={isLiquidGlassAvailable() ? "search" : undefined}`, and the Speakers
route's header has `headerSearchBarOptions`. On iOS 27 its journey (`original/journey/08`,
`09`) shows:

- the Speakers tab as a separate glass circle at the trailing end, its image alone;
- once selected, a large "Speakers" title with no field under it, and at the bottom a circle
  holding the previous tab's image beside a "Search speakers" field;
- tapping the field brings the keyboard, with the field above it and a close button.

Expo reaches this through React Native Screens, which makes the tab's item
`UITabBarItem(tabBarSystemItem: .search)` and then sets its image.

Both Exact builds drew Speakers as an ordinary fourth tab with the field under the title,
hidden until pulled. Both graders called that major (`RESULTS.md` findings 1 and 6), and
`ATTRIBUTION-port1.md` (rows 1 and 6) puts it down to Exact, with confidence 90 and 75.
Opus spent about 3 minutes looking for a way (`runs/1-exact/DIARY.md`). GPT tried three ways
in 4 minutes through the tab hatch, and each failed (`runs/1g-exact/DIARY.md` R6):

- a container of its own duplicated the tabs' labels and lost hit-testing;
- swapping in `UITab`s crashed UIKit (`insertObject:atIndex: object cannot be nil`);
- the `.search` system item on Exact's controller stayed inside the four-item pill.

GPT's SwiftUI port found that `Tab(role: .search)` did not set the tab apart on iOS 27. It
used `UITabBarController.tabs` with a `UISearchTab` under SwiftUI, which took 3 minutes
(`runs/1g-native/ReactConf/ReactConfApp.swift`).

**Hackers** (SwiftUI). The feed writes
`.searchable(text:, placement: .toolbar, prompt: "Search Hacker News")`,
`.searchToolbarBehavior(.minimize)` and
`ToolbarSpacer(.flexible, placement: .bottomBar)`, then
`DefaultToolbarItem(kind: .search, placement: .bottomBar)`
(`original/src/Features/Feed/Sources/Feed/FeedView.swift`). The Exact build floated a
bordered button that pushed a `/search` route. Leaving a post opened from it took two backs
(finding 8), and the field was not focused (finding 7, LLP 1141.001 D6).

**What does not work: inferring the search tab.** Shelf's and Harmony's root tabs have header
search fields, a filter over their own lists. Neither is a search tab. A search tab is a
destination, which the author has to name.

## 2. What exists

- **Root tabs.** These are the tabpanels that the root tablist's `role="tab"` children name
  with `aria-controls` (`Kernel::root_tabs`). On iOS they become a `UITabBarController` with
  `setViewControllers` and one `tabBarItem` per tab (`installTabs`, `syncItems`). A bar
  selection presses the authored tab (`TabDelegateProxy`).
- **Tab panels are built late.** A panel stays empty until its tab is first selected
  (`runner/src/instance/tabs.rs`). Nothing inside a panel can mark its tab before then.
- **The Mac** shows the root tablist as a source-list sidebar (LLP 1115.002 D3). The web
  shows a bottom bar, or a sidebar at 900 px and up. Android shows Material's navigation bar,
  painted by `host/linux/src/presenter/bars.rs`. Desktop Linux, Windows and the terminal paint
  the authored tablist.
- **Header search.** An `input type="search"` in a route's header is
  `navigationItem.searchController` (`searchField`), with UIKit's automatic placement. On
  iOS 27 that is under the title in a tab app and in the bottom bar in a single stack
  (LLP 1115.000 D11.2). `hidesSearchBarWhenScrolling` is true while the query is empty,
  unless the field sticks (`HeaderSearch.applyHiding`). The Mac uses an
  `NSSearchToolbarItem`; Android and Linux keep the field in the page under the top bar.
- **The minimum is iOS 17** (`Package.swift`, `build.mjs`). `UITab` and `UISearchTab` arrive
  in iOS 18. The `.integrated*` placements and `automaticallyActivatesSearch` arrive in
  iOS 26.

## 3. Decisions

### D1. `rel="search"` on a root tab names the search tab

```contract
row role="tablist"
  button role="tab" aria-controls="panel-calendar" aria-selected=(nav.tab == "calendar")
    press=pick("calendar") testId="tab-calendar"
    image "symbol:calendar"
    text "Calendar"
  …
  button role="tab" rel="search" aria-controls="panel-speakers"
    aria-selected=(nav.tab == "speakers") press=pick("speakers") testId="tab-speakers"
    image "symbol:people"
    text "Speakers"
```

`rel="search"` is HTML's link type for "the referenced document provides an interface
specifically for searching the document and its related resources"
([HTML §4.6.8.22](https://html.spec.whatwg.org/multipage/links.html#link-type-search)).
That is the HIG's distinction exactly. A search tab searches the app; a header field on a
list filters that list ([HIG, Search fields](https://developer.apple.com/design/human-interface-guidelines/search-fields)).

Where the word could have gone instead:

- **`role="search"` on the tab** (the candidate in 1141.001 D8, and Expo's word). This
  replaces `tab`, and a `tablist` may own only tabs
  ([WAI-ARIA 1.2, tablist](https://www.w3.org/TR/wai-aria-1.2/#tablist)). The web build
  would announce a search landmark where a tab stands and would leave the tabs' arrow-key
  order. ARIA's fallback list `role="tab search"` is read as `tab`, so it says nothing.
- **A search landmark in the panel** (`role="search"` on the root route, or HTML's `search`
  element around the stack). This would be valid, but the panel is empty until its tab is
  first selected, and the tab bar must know its search tab at launch.
- **Inference** from the header field or the tab's symbol. Shelf and Harmony refute the
  first, and React Conf's search tab shows `person.2`.

The rules:

- Contract accepts `rel="search"` only on a `role="tab"` child of a root tablist. Lowering
  already tells a root tablist apart (`lower-single-tab`). Anywhere else it is refused with a
  message.
- The first such tab is the search tab, as SwiftUI takes the first tab with the search role
  ([`TabRole.search`](https://developer.apple.com/documentation/swiftui/tabrole/search)). A
  second one is a warning.
- `role="search"` on a tab is refused with a message that names `rel="search"`.
- `RootTabs` gains `search: Option<usize>`. The kernel reads it from the tab's props, so
  every host has it from the first frame.
- Write the search tab last. iOS 26 moves it to the trailing end, and hosts that keep the
  author's order then agree.

The tab's own symbol and label are its face (author > platform). A tab with no symbol gets
the platform's magnifying glass.

### D2. Presentation on each host

| Host | The search tab |
|---|---|
| iOS 26 and later | A [`UISearchTab`](https://developer.apple.com/documentation/uikit/uisearchtab), which UIKit sets apart at the trailing end ([Adopting Liquid Glass, Search](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass): "use the standard system APIs for indicating which tab is the search tab"). Pinned tabs show their image alone, with the title as their accessibility label. Selected, its root's search field takes the tab bar's place, as in the original's journey. |
| iOS 18 to 25 | The same `UISearchTab`, which UIKit draws as one tab among the others. |
| iOS 17 | An ordinary tab: `UITab` does not exist. |
| iPadOS 26 and later | The `UISearchTab` as a pinned tab at the trailing end of the top tab bar. Its field is UIKit's for the width. |
| tvOS | An ordinary tab for now (Open questions). |
| macOS | A sidebar row in the author's order, as today. Its root's header search stays the toolbar's `NSSearchToolbarItem`. |
| Web | The tab as written, in the author's order, bottom bar or sidebar. The DOM carries `rel="search"`, which no browser acts on. A web user sees no difference, which is the web platform's answer (LLP 1116 D1). |
| Android | An ordinary destination of Material's navigation bar, in order, as a search destination is in Google Play. Its root's header search stays in the page under the top app bar. |
| Linux, Windows, terminal | The authored tablist, painted. `rel` is not read. |

**On iOS 18 and later, every tab app moves to the `tabs` API**, not only one with a search
tab. One path per OS keeps a search tab from being a second way of building the bar.

- `installTabs` makes one `UITab` per panel, or a `UISearchTab` for the search tab. Each
  `viewControllerProvider` returns the panel's existing stack (`makeTabStack`).
  [`UITabBarController.tabs`](https://developer.apple.com/documentation/uikit/uitabbarcontroller/tabs)
  replaces `setViewControllers`. `syncItems` writes `title`, `image`, `badgeValue` and
  `isEnabled` on the [`UITab`](https://developer.apple.com/documentation/uikit/uitab) instead
  of `tabBarItem`.
- A tab's `identifier` must be unique across the controller. It is the tab's `testId`, else
  its panel's `id`.
- `TabDelegateProxy` answers
  [`tabBarController(_:shouldSelectTab:)`](https://developer.apple.com/documentation/uikit/uitabbarcontrollerdelegate/tabbarcontroller(_:shouldselecttab:))
  by pressing the authored tab and returning false, as it does now for controllers. Selection
  stays the router's (LLP 1038 D4), and the router's choice is written to `selectedTab`.
- The tab hatch (`tabsHatch`, `tabContainer`) hands modules a controller built from `tabs`.
  A module that sets `viewControllers` on it is told so in the log (Open questions).

iOS 17 keeps today's `tabBarItem` path, which already exists.

### D3. The search tab's field, and `autofocus`

The search tab's field is the `input type="search"` in its root route's header, unchanged in
Contract. On iOS 26, UIKit moves that navigation item's search controller into the tab bar
when the search tab is selected. Exact keeps building it as `searchField` does now.

`autofocus` on that field is `UISearchTab.automaticallyActivatesSearch`
([docs](https://developer.apple.com/documentation/uikit/uisearchtab/automaticallyactivatessearch)).
The HIG calls the two forms a "standard tab", a landing page to explore, and a "button
appearance", where search starts at once and returns to the previous tab when cancelled.
HTML's `autofocus` already says "focus this when it shows", and 1141.001 D6 makes it reach a
header's field, so no new word is needed.

When search is cancelled, UIKit restores the previous tab, and that selection goes through
`shouldSelectTab`, so it presses the authored tab. A search tab whose root route has no
header search field is still a search tab: a landing page with no field, which `check`
reports (D6).

### D4. `field-sizing="content"` is the minimized toolbar search

```contract
header
  text feedTitle(category) role="heading" aria-level=2
  button press=openSettings aria-label="Settings" testId="settings"
    image "symbol:settings"
  input type="search" field-sizing="content" value=query input=editQuery
    placeholder="Search Hacker News" testId="search"
```

No HTML or ARIA word means "a field shown as a button until used". The nearest is CSS's
[`field-sizing: content`](https://drafts.csswg.org/css-forms-1/#field-sizing), which Contract
already accepts: the field takes the size of what it holds rather than a fixed width. An empty
field that is not being edited then holds nothing, and its platform form is a button that grows
into a field when used. SwiftUI's name for this is `.searchToolbarBehavior(.minimize)`
([docs](https://developer.apple.com/documentation/swiftui/view/searchtoolbarbehavior(_:))).

On each host:

- **iOS 26 and later:** `preferredSearchBarPlacement = .integratedButton`
  ([docs](https://developer.apple.com/documentation/uikit/uinavigationitem/searchbarplacement-swift.enum/integratedbutton)).
  On iPhone, UIKit puts an integrated search into the navigation controller's toolbar
  ([`searchBarPlacementAllowsToolbarIntegration`](https://developer.apple.com/documentation/uikit/uinavigationitem/searchbarplacementallowstoolbarintegration),
  true by default), trailingmost when no
  [`searchBarPlacementBarButtonItem`](https://developer.apple.com/documentation/uikit/uinavigationitem/searchbarplacementbarbuttonitem)
  places it. That is Hackers' `ToolbarSpacer` and `DefaultToolbarItem`. If stage 0 finds
  that the toolbar must be shown, Exact shows that route's toolbar with the search item alone,
  which the HIG names as one of search's forms. On iPad the item is a button in the
  navigation bar.
- **iOS 17 to 25:** `.automatic`, as today. The minimized form is new in iOS 26.
- **macOS:** the `NSSearchToolbarItem` as today. AppKit already collapses it to a button when
  the toolbar is short of room.
- **Web, Android, Linux:** CSS's own `field-sizing: content` on the authored field.

A header search without it keeps `.automatic`, which UIKit resolves (LLP 1115.000 D11.2).
That already puts a single stack's field in the bottom bar on iOS 27. So Hackers needed only
the header field on its feed route, not a pushed route; the docs say so (D8).

### D5. A root route's header search at rest

UIKit's default `hidesSearchBarWhenScrolling` is what a hand-built screen has
([docs](https://developer.apple.com/documentation/uikit/uinavigationitem/hidessearchbarwhenscrolling)):
the field shows at the top of the content and collapses into the bar as the content scrolls.
Exact keeps that rule unchanged:

- it hides only while empty;
- it never hides when the author wrote `position: sticky` with a `top`. The HIG suggests
  pinning an inline field at the top.

On the search tab under iOS 26 the field is in the tab bar, so the property does not apply.
That removes React Conf's case.

What changes is where Exact differs from a hand-built screen at rest. React Conf's GPT
journey needed "search pulled into view" on a root route. A screen that sets its
`searchController` in `viewDidLoad` gets UIKit's layout from the first frame. Exact assigns
the controller in a batch, possibly after the bar's first layout.

- **Stage 0** measures a hand-built root, in a tab app and in a single stack on iOS 26.x and
  27, against Exact's.
- **Stage 4** assigns the search controller before the route's first layout, as LLP 1115.000
  D11.1 did for the scroller, if Exact's field starts hidden where the hand-built one shows.

### D6. The agent driver

- **By default** (`ExactEnv.authoredChrome`) the agent paints the authored tablist and header,
  and nothing changes. `tap "tab-speakers"` selects the search tab, and
  `type "speaker-search" Lauren` types its field. A drive never has to know where UIKit put
  the field.
- **`tree`** marks the search tab (`tab … search`) and a minimized field (`minimized`).
  Under `--chrome platform` it also gives the placement UIKit resolved
  ([`searchBarPlacement`](https://developer.apple.com/documentation/uikit/uinavigationitem/searchbarplacement-swift.property):
  stacked, integrated, integrated button, or the tab bar), so an agent can confirm UIKit's
  choice without a screenshot.
- **Under `--chrome platform --touch platform`**, a real touch reaches the search tab's
  button by its `testId`. Stage 0 measures how XCUITest exposes a `UITab`'s button. If the
  identifier does not reach it, Exact sets the button's `accessibilityIdentifier` as
  `syncItems` does now.
- **`back`** with a search active cancels the search, as its close button does, before it
  dismisses a sheet or pops.
- **`check`** reports a search tab whose root route has no header search field.

- **Compiler** (`contract/lower` tests):
  - `rel="search"` is accepted on a root tab and refused elsewhere;
  - a second search tab warns;
  - `role="search"` on a tab is refused with its message;

- **Kernel:** `root_tabs` reports the search tab from the first frame, before its panel is
  built.
- **Web conformance** (`host/web-js/conformance/tabs.steps`): `rel` is in the DOM, the order

  - `testTabsAreUITabsWithTestIdIdentifiers`;
  - `testAMinimizedHeaderSearchIsIntegratedButton`;

## 5. Open questions

1. **`rel` on a `button`.** HTML allows `rel` on `a`, `area`, `link` and `form`, so a validator
   flags `button rel="search"` though no browser or assistive technology acts on it. The
   alternatives:
   - require the search tab to be a `link role="tab"`, which the router does not use for tabs
     today;
   - accept `role="search"` on the tab and write `role="tab"` into the web's DOM, which makes
     Contract's `role` differ from ARIA's in one place.

   The author recommends `rel`, as the one word that means search to the web and leaves ARIA
   correct. Charlie decides.
2. **`field-sizing="content"` borrows a sizing property** for a presentation that has no web
   word. The other choice is an Exact attribute beside `buttonStyle` and `listStyle`. Also
   undecided: whether minimizing is ever the platform's answer when the author says nothing,
   for example with several items in the bottom toolbar.
3. **A hand-built root header search at rest** (D5): stage 0's numbers decide whether D5
   needs a fix.
4. **The Mac.** `TabView(.sidebarAdaptable)` with a search-role tab on macOS 26 may draw a
   search field at the top of the sidebar rather than a row, as Music does. A SwiftUI
   reference screen decides whether the Mac's row becomes that field.
5. **tvOS.** A tvOS search tab hosts a `UISearchContainerViewController`, and tvOS navigation
   items carry no search controller. Until an app asks for it, tvOS draws an ordinary tab.
6. **iPad and the virtual keyboard.** The HIG leaves a dedicated search area unfocused when
   only a virtual keyboard is present. If UIKit does not already do this for
   `automaticallyActivatesSearch`, does Exact?
7. **Hatches.** An app module that set `viewControllers` on Exact's tab controller breaks on
   the `tabs` path. Is a log line enough before 1.0 ("Delete; don't deprecate"), or does
   `tabContainer` hand over `UITab`s?
