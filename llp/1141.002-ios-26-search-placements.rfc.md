## Summary

iOS 26 gives search two places Exact cannot ask for: a **search tab**, set apart at the
trailing end of the tab bar, whose root screen's search field sits at the bottom where the tab
bar was; and a **minimized toolbar search**, a button at the bottom of a screen that expands
into a field in place. Every Exact build in the pilot lacked the first; Hackers' build pushed a
whole search route for want of the second.

| | Decision |
|---|---|
| D1 | A root tab that says `rel="search"` is the app's search tab. It stays `role="tab"`. |
| D2 | On iOS 18 and later the tab bar is built from `UITab`s, the search tab a `UISearchTab`, behind a compatibility gate; other hosts keep the tab in place. |
| D3 | The search tab's field is its root route's header search; its `autofocus` is `automaticallyActivatesSearch`, in a specified order. |
| D4 | `searchStyle="minimized"` on a header's search field is iOS 26's `.integratedButton`. |
| D5 | Stage 0 decides whether a root route's header search differs from a hand-built one at rest. |
| D6 | The agent drives both as it drives tabs and header search now; `tree` says what UIKit chose. |
| D7–D8 | Tests, and the docs, recipes and compiler messages that teach both. |

## 1. Evidence

**React Conf** (Expo Router). The original marks its Speakers tab
`NativeTabs.Trigger role={isLiquidGlassAvailable() ? "search" : undefined}`, and the Speakers
route's header has `headerSearchBarOptions`. On iOS 27 its journey (`original/journey/08`,
`09`) shows the Speakers tab as a separate glass circle at the trailing end, its image alone;
once selected, a "Speakers" title and, at the bottom, the previous tab's image beside a
"Search speakers" field. Expo makes the item `UITabBarItem(tabBarSystemItem: .search)` and
then sets its image.

Both Exact builds drew Speakers as an ordinary fourth tab with the field under the title,
hidden until pulled. Both graders called that major (`RESULTS.md` findings 1 and 6), and
`ATTRIBUTION-port1.md` (rows 1 and 6) puts it down to Exact. GPT tried three ways through the
tab hatch (`runs/1g-exact/DIARY.md` R6): its own container lost hit-testing; swapping in
`UITab`s crashed UIKit (`insertObject:atIndex: object cannot be nil`); the `.search` system
item on Exact's controller stayed inside the pill. GPT's SwiftUI port used
`UITabBarController.tabs` with a `UISearchTab` (`runs/1g-native/ReactConf/ReactConfApp.swift`).

**Hackers** (SwiftUI). The feed writes
`.searchable(text:, placement: .toolbar, prompt: "Search Hacker News")`,
`.searchToolbarBehavior(.minimize)`, `ToolbarSpacer(.flexible, placement: .bottomBar)` and
`DefaultToolbarItem(kind: .search, placement: .bottomBar)` (`FeedView.swift`). The Exact
build pushed a `/search` route from a floating button; leaving a post opened from it took two
backs (finding 8).

**Inference does not work.** Shelf's and Harmony's root tabs have header search fields, a
filter over their own lists. Neither is a search tab. A search tab is a destination, which the
author has to name.

## 2. What exists

- **Root tabs** are the tabpanels that the root tablist's `role="tab"` children name with
  `aria-controls` (`Kernel::root_tabs`). On iOS and tvOS they become a `UITabBarController`
  built with `setViewControllers` and one `tabBarItem` per tab (`installTabs`, `syncItems`).
- **Selection is the router's** (LLP 1038 D4). `TabDelegateProxy` answers `shouldSelect` by
  pressing the authored tab (`selectTab`, a queued press) and returning false; the router
  selects, and a later sync writes `selectedIndex`.
- **Tab panels are built late.** A panel stays empty until its tab is first selected
  (`runner/src/instance/tabs.rs`). Nothing inside a panel can mark its tab before then.
- **Other hosts.** The Mac shows the root tablist as a source-list sidebar (LLP 1115.002
  D3); the web a bottom bar, or a sidebar at 900 px and up; Android Material's navigation
  bar. Desktop Linux, Windows and the terminal paint the authored tablist.
- **Header search.** The first `input type="search"` in a route's header is
  `navigationItem.searchController` (`searchField`), with UIKit's automatic placement: on iOS
  27, under the title in a tab app and in the bottom bar in a single stack (LLP 1115.000
  D11.2), hidden when scrolling while empty unless it sticks (`HeaderSearch.applyHiding`).
  The Mac uses an `NSSearchToolbarItem`; Android and Linux keep the field in the page.
- **The minimum is iOS 17** (`Package.swift`, `build.mjs`). `UITab` and `UISearchTab` arrive
  in iOS 18; the `.integrated*` placements and `automaticallyActivatesSearch` in iOS 26.

## 3. Decisions

### D1. `rel="search"` on a root tab names the search tab

```contract
row role="tablist"
  button role="tab" aria-controls="panel-calendar" aria-selected=(nav.tab == "calendar")
    press=pick("calendar") testId="tab-calendar"
    image "symbol:calendar"
    text "Calendar"
  …
  button role="tab" rel="search" aria-controls="panel-speakers"
    aria-selected=(nav.tab == "speakers") press=pick("speakers") testId="tab-speakers"
    image "symbol:people"
    text "Speakers"
```

`rel="search"` is HTML's link type for "the referenced document provides an interface
specifically for searching the document and its related resources"
([HTML §4.6.8.22](https://html.spec.whatwg.org/multipage/links.html#link-type-search)).
That is the HIG's distinction: a search tab searches the app; a header field on a list
filters that list ([HIG, Search fields](https://developer.apple.com/design/human-interface-guidelines/search-fields)).
HTML allows `rel` on `a`, `area`, `link` and `form`, not on `button`; on a tab it is Contract's
extension, and the web DOM does not carry it.

Not `role="search"` on the tab (Expo's word): it replaces `tab`, and a `tablist` may own
only tabs ([WAI-ARIA 1.2, tablist](https://www.w3.org/TR/wai-aria-1.2/#tablist)), so the web
would announce a landmark where a tab stands. Not a search landmark in the panel: the panel is
empty until first selected, and the bar must know its search tab at launch.

The rules:

- `rel` is a new string row in `kernel/tables/schema.json` (none exists today), read as HTML's
  [set of space-separated tokens](https://html.spec.whatwg.org/multipage/common-microsyntaxes.html#set-of-space-separated-tokens),
  ASCII case-insensitively. A new row changes the kernel schema digest and so the
  compatibility id (LLP 1030): a released app gets it only with a new binary.
- Contract accepts `rel` on `link` and `form`, with HTML's meaning, written into the web DOM
  and read by no native host; and on a `role="tab"` child of a root tablist (lowering already
  tells one apart, `lower-single-tab`), where the token `search` names the search tab and
  other tokens are ignored. Anywhere else it is refused with a message.
- The first search tab is the search tab, as SwiftUI takes the first tab with the search role
  ([`TabRole.search`](https://developer.apple.com/documentation/swiftui/tabrole/search)).
  A second one is a warning, and is an ordinary tab on every host.
- A search tab that is not the last tab is a warning: iOS 26 moves it to the trailing end, and
  the hosts that keep the author's order agree only when it is written last.
- `role="search"` on a tab is refused with a message that says why, so that an agent does
  not switch back: "a tablist owns only tabs (WAI-ARIA), so keep `role="tab"`; write
  `rel="search"` to make this the app's search tab".
- `RootTabs` gains `search: Option<usize>`, read from the tab's props, so every host has it
  from the first frame.

The tab's own symbol and label are its face (author > platform). A tab with no symbol gets
the platform's magnifying glass.

### D2. Presentation on each host, and the `tabs` migration

| Host | The search tab |
|---|---|
| iOS 26 and later | A [`UISearchTab`](https://developer.apple.com/documentation/uikit/uisearchtab), which UIKit may set apart at the trailing end ([Adopting Liquid Glass, Search](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass): "use the standard system APIs for indicating which tab is the search tab"). Where it is drawn, and whether its field takes the bar's place, stage 0 measures with and without `autofocus` (§5). |
| iPhone, iOS 18 to 25 | The same `UISearchTab`, among the others. |
| iPadOS 18 and later | The `UISearchTab` where UIKit places it in the top tab bar and sidebar; stage 0 measures iPadOS 18 apart. |
| iOS 17 | An ordinary tab: `UITab` does not exist. |
| tvOS | An ordinary tab, on today's path; its root's search input stays in the page, reachable by focus. |
| macOS | A sidebar row in the author's order; its root's search stays the toolbar's `NSSearchToolbarItem`. |
| Web | The tab as written, in order; the DOM's `button` has no `rel` (LLP 1116 D1). |
| Android, Linux, Windows, terminal | An ordinary tab or destination, in order; the field stays in the page. |

**The end state is one path per OS: on iOS 18 and later every tab app is built from
[`UITabBarController.tabs`](https://developer.apple.com/documentation/uikit/uitabbarcontroller/tabs)**,
not only one with a search tab, so that a search tab is not a second way to build the bar. The
code is `#if os(iOS)` and `#available(iOS 18, *)`; `automaticallyActivatesSearch` and
`.integratedButton` are behind `#available(iOS 26, *)`, compiled against the 26 SDK or later.
iOS 17 and tvOS keep today's `viewControllers` path.

- `installTabs` makes one `UITab` per panel, or a `UISearchTab` for the search tab; each
  `viewControllerProvider` returns the panel's existing stack (`makeTabStack`). `syncItems`
  writes `title` and `image` on the [`UITab`](https://developer.apple.com/documentation/uikit/uitab),
  and `badgeValue` and `isEnabled` wherever stage 0's API checklist finds them take effect
  (the `UITab`, or the provided controller's `tabBarItem`).
- **Identity.** A `UITab`'s [`identifier`](https://developer.apple.com/documentation/uikit/uitab/identifier)
  is fixed at creation and must be unique: it is the panel's `id`. A `UISearchTab`'s
  [identifier is system-assigned](https://developer.apple.com/documentation/uikit/uisearchtab/identifier),
  so the host keeps an explicit map from `UITab` to panel. The `testId` goes on the tab
  button's `accessibilityIdentifier`, as `syncItems` writes it now. A changed `testId` never
  recreates a tab; a change of which tab is the search tab rebuilds the row (`reshape` keys on
  panel ids and the search index).
- **Selection** keeps the router's handshake: `TabDelegateProxy` answers
  [`tabBarController(_:shouldSelectTab:)`](https://developer.apple.com/documentation/uikit/uitabbarcontrollerdelegate/tabbarcontroller(_:shouldselecttab:))
  by pressing the authored tab and returning false, and the router's choice is written to
  [`selectedTab`](https://developer.apple.com/documentation/uikit/uitabbarcontroller/selectedtab),
  unless stage 0 shows the veto breaks search (D3).
- **Hatches.** Exact's own `viewControllers` writers (held stacks in `HeldStackIOS.swift`,
  `replayTabs`) move to `tabs` in stage 2. `tabContainer` hands modules the `UITab`s. A module
  that sets `viewControllers` on a `tabs`-built controller fails with an error naming
  `tabs` as the replacement, before UIKit's nil crash.

**Compatibility gate.** Stage 2 lands only when the `tabs` path matches today's on: held
stacks and their scroll positions; reselect, pop to root and scroll to top; disabled tabs;
badges; selected images; tabs added, removed and reordered at run time; `appearance: none`
and authored chrome (`ExactEnv.authoredChrome`); hatch takeover, early and late; compact and
regular size-class transitions; more than five tabs and the More list; the iPad's floating tab
bar and sidebar; each on iPadOS 18 as well as 26 and 27. It lands in its own commits, so reverting
it returns every tab app to the `viewControllers` path with nothing else changed.

If stage 0 shows that the `.search` system item on today's path behaves as a `UISearchTab`
does (set apart, the field in the bar, activation and cancel), not only looks the same, D2
takes that smaller change and no tab app moves.

### D3. The search tab's field, and its lifecycle

**The field** is the first `input type="search"` in the search tab's **root** route's header,
built as `searchField` builds it now. A route pushed inside the search tab keeps its own
header search, as today. On iOS 26 UIKit moves the root's search controller into the bar when
the tab is selected (stage 0 confirms no other call is needed, and where a scope bar, LLP
1134, goes). Because `searchBar.searchTextField` may return a different instance over time
([iOS 26 release notes](https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-26-release-notes)),
`HeaderSearch` refreshes its delegate, field bindings and `accessibilityIdentifier` across
expansion, cancellation, keyboard and width changes.

**Before the panel's first build** there is no field. The `UISearchTab` shows the authored
image and title, and `automaticallyActivatesSearch` keeps UIKit's default until the root's
header is known. A built root with no header search is a landing page with no field: it
compiles, and `check` reports it (D6).

**`autofocus`** on the root's field is
[`UISearchTab.automaticallyActivatesSearch`](https://developer.apple.com/documentation/uikit/uisearchtab/automaticallyactivatessearch).
The HIG calls the two forms a "standard tab", a landing page to explore, and a "button
appearance", where search starts at once and returns to the previous tab when cancelled. On
iOS 26 this `autofocus` activates search on every selection of the tab, where the web
(`host/web/navigation.js`) and the other hosts focus once per mount. That is deliberate: it is
the platform's search tab, and the author asked for that form. Without `autofocus` the tab
follows UIKit and the HIG (which leaves search unfocused on iPad with only a virtual
keyboard); explicit `autofocus` is honoured there too.

**The order.** Each case runs through Exact's handshake: UIKit asks `shouldSelectTab`, Exact
presses the authored tab and refuses, the runner applies the press, the router selects, the
host writes `selectedTab`.

| Case | The order |
|---|---|
| Cold first selection | press → the router selects → the panel's root route is built → `searchField` assigns the search controller and the host writes `automaticallyActivatesSearch` from `autofocus` → the host writes `selectedTab` → UIKit activates, if asked. The field is in the bar on the update that selects the tab. |
| Repeated selection | press → the router selects → `selectedTab` → UIKit activates again, if asked; the query is what the route holds. |
| Launch into the search tab (the router's first tab, or a deep link) | the first frame builds the panel and selects it with no previous tab; a cancel leaves the search tab selected unless UIKit picks another, which the router then follows. |
| Return from a result | a result pushed inside the tab pops back to the root, where the search controller keeps its state and query; a result that selects another tab is a selection like any other, and coming back is a repeated selection. |
| Cancel | UIKit deactivates the search controller and, with automatic activation, restores the previous tab. That restore must reach the router, through `shouldSelectTab` (the veto presses the previous tab) or through [`didSelectTab`](https://developer.apple.com/documentation/uikit/uitabbarcontrollerdelegate/tabbarcontroller(_:didselecttab:previoustab:)), which Exact turns into a press. |

Stage 0 records which of these UIKit honours under the veto and programmatic `selectedTab`.
If the veto breaks activation or cancel's restore, or leaves UIKit and the router
disagreeing, the handshake changes before any tab app moves (§5).

### D4. `searchStyle="minimized"` is the minimized toolbar search

```contract
header
  text feedTitle(category) role="heading" aria-level=2
  button press=openSettings aria-label="Settings" testId="settings"
    image "symbol:settings"
  input type="search" searchStyle="minimized" value=query input=editQuery
    placeholder="Search Hacker News" testId="search"
```

No HTML or ARIA word means "a field shown as a button until used". CSS's
`field-sizing: content` does not: it sizes an empty field to its placeholder
([HTML rendering](https://html.spec.whatwg.org/multipage/rendering.html#the-input-element-as-a-text-entry-widget)).
So it is an Exact presentation attribute beside `buttonStyle` and `listStyle`, with an
automatic default: a new string row in `kernel/tables/schema.json` (a new compatibility id, as
for `rel`), accepted only on an `input type="search"` in a header. SwiftUI's name is
[`.searchToolbarBehavior(.minimize)`](https://developer.apple.com/documentation/swiftui/view/searchtoolbarbehavior(_:)).

| Value | iOS 26 and later | Every other host |
|---|---|---|
| `automatic` (the default) | `preferredSearchBarPlacement = .automatic`, which UIKit resolves (LLP 1115.000 D11.2) | a field, as today |
| `minimized` | [`.integratedButton`](https://developer.apple.com/documentation/uikit/uinavigationitem/searchbarplacement-swift.enum/integratedbutton) | a field, as today |

Unsaid never minimizes: a filter field such as Shelf's stays a field. On iPhone UIKit puts an
integrated search into the navigation controller's toolbar
([`searchBarPlacementAllowsToolbarIntegration`](https://developer.apple.com/documentation/uikit/uinavigationitem/searchbarplacementallowstoolbarintegration),
true by default), trailingmost when no
[`searchBarPlacementBarButtonItem`](https://developer.apple.com/documentation/uikit/uinavigationitem/searchbarplacementbarbuttonitem)
places it, which is Hackers' `ToolbarSpacer` and `DefaultToolbarItem`. If stage 0 finds the
toolbar must be shown, Exact shows that route's toolbar with the search item alone. On iPad
the item is a button in the navigation bar. The Mac's `NSSearchToolbarItem` already
collapses to a button when the toolbar is short of room.

`.automatic` already puts a single stack's field in the bottom bar on iOS 27, so Hackers
needed only the header field on its feed route, not a pushed route (D8).

### D5. A root route's header search at rest

React Conf's GPT journey needed "search pulled into view" on a root route. A hand-built
screen that sets its `searchController` in `viewDidLoad` gets UIKit's layout from the first
frame; Exact assigns the controller in a batch, possibly after the bar's first layout. Where
each rests is not assumed here.

Stage 0 measures hand-built assignment in `viewDidLoad` and after layout, in a tab app and a
single stack, on iPhone and iPad, iOS 26 and 27, with a large title, at scroll offset 0,
against Exact's. If Exact's first frame differs from the hand-built `viewDidLoad` one, stage 4
moves the assignment before the route's first layout, as LLP 1115.000 D11.1 did for the
scroller. The hide-when-empty rule
([`hidesSearchBarWhenScrolling`](https://developer.apple.com/documentation/uikit/uinavigationitem/hidessearchbarwhenscrolling),
never hidden when the author wrote `position: sticky` with a `top`) changes only if a
difference remains after that.

### D6. The agent driver

- **By default** (`ExactEnv.authoredChrome`) nothing changes: `tap "tab-speakers"` selects
  the search tab and `type "speaker-search" Lauren` types its field.
- **`tree`** marks the search tab (`tab … search`) and a minimized field (`minimized`). Under
  `--chrome platform` it reports apart the
  [`searchBarPlacement`](https://developer.apple.com/documentation/uikit/uinavigationitem/searchbarplacement-swift.property)
  UIKit returns, one of the [enum's cases](https://developer.apple.com/documentation/uikit/uinavigationitem/searchbarplacement-swift.enum)
  (`automatic`, `inline`, `stacked`, and from iOS 26 `integrated`, `integratedButton`,
  `integratedCentered`, checked against the SDK in stage 0), none of them the tab bar; and the
  field's actual container (navigation bar, toolbar, tab bar or content), read from the view
  hierarchy.
- **Drives that touch UIKit's own search** (the search tab's button, the minimized button,
  the bar's field and close button) need `--chrome platform --touch platform`. Stage 0
  reports the element type and identifier XCUITest finds for a `UITab`'s button.
- **`back`** cancels a search, before it dismisses or pops, only while
  [`UISearchController.isActive`](https://developer.apple.com/documentation/uikit/uisearchcontroller/isactive)
  and only in the foreground presentation: an active search under a sheet does not swallow the
  sheet's dismissal, and a field with text that is not active pops as today.
- **`check`** reports a built search tab whose root route has no header search field, and
  "not yet known" before the panel is built.

### D7. Tests

- **Compiler** (`contract/lower` tests): `rel="search"` accepted on a root tab, `link` and
  `form`, refused elsewhere; a second search tab and a search tab not last warn;
  `role="search"` on a tab is refused with its reason; `searchStyle` accepted on a header's
  search field and refused elsewhere; a search tab with no field compiles.
- **Kernel:** `root_tabs` reports the search tab from the first frame, before its panel is
  built.
- **Web conformance** (`host/web-js/conformance/tabs.steps`): the tab's `button` has no `rel`,
  the order is unchanged, and arrow keys move across every tab, the search tab included.
- **XCTests** over `apps/native-fixture` with a search tab and a minimized field, iOS 26 or
  later: a `UISearchTab` with the authored image and title, trailing even when not written
  last; selecting it presses the authored tab; its field is its root's search controller;
  each case of D3's order; identifiers are panel ids, a changed `testId` keeps the tab;
  `.integratedButton`; typing, selection, paste, focus and blur on the displayed editor after
  expansion and cancel; the gate's items (D2), on iPadOS 18 too; the rest state from stage 0.
  iOS 17's `NavigationTabsIOSTests` run unchanged.
- **Accessibility:** VoiceOver's label and selected state for an image-only pinned tab; focus
  on activation and on the return from cancel; the accessibility text sizes; right-to-left;
  a hardware keyboard.
- **Mac:** sidebar order and the `NSSearchToolbarItem` unchanged.
- **Drives:** `smoke.mjs ios` taps the search tab and types in it under `--touch platform`;
  a minimized-search journey under `--chrome platform --touch platform` (expand, type, submit,
  cancel, reopen); `back` through an inactive header search still pops; Shelf and Harmony on
  iOS 26 keep their filter fields and have no search tab. The React Conf and Hackers Exact
  sources gain `rel="search"` and the header field (Hackers' feed with
  `searchStyle="minimized"`, no `/search` route), are compared under `--chrome platform` with
  the original's journey 08 and 09, and go back to the graders (LLP 1141 §4.6).

### D8. Docs, recipes and messages

- **`docs/recipes/tabs.md`:** a search tab in the example, written last, and what each host
  does with it. **`list-rows.md`** and **`keyboard-and-focus.md`:** a header field filters
  its list; a search tab is the app's search; `searchStyle="minimized"` minimizes the field;
  never push a route for the bar's search.
- **`docs/contract-for-agents.md`:** "Tabs and stacks" gains the search tab; "Bar buttons,
  glass and the search field" gains `searchStyle` and where UIKit puts each.
- **`contract vocab`:** `search`, `rel` and `searchStyle`, with synonyms `UISearchTab`,
  `Tab(role: .search)`, `role="search"` (Expo's trigger), `searchToolbarBehavior`,

## 5. Open questions

1. **Where a search tab is drawn without `autofocus`.** Apple's
   [`prominentTabIdentifier`](https://developer.apple.com/documentation/uikit/uitabbarcontroller/prominenttabidentifier)
   page (marked beta) ties a search tab's default prominence to `automaticallyActivatesSearch`.
   If stage 0 finds that a `UISearchTab` without it is drawn among the others, that is the
   platform's answer for a "standard tab" search, and the docs say so; Exact sets no
   prominence of its own unless Charlie decides otherwise.
2. **The handshake if the veto breaks search.** If stage 0 shows that refusing
   `shouldSelectTab` stops activation or cancel's restore, the candidate is to let UIKit
   select the search tab, press the authored tab after, and write the router's choice back if
   it differs. Its effect on reselect and on held stacks is unmeasured.
