## 1. Decision and authorization

An application operation should be able to move between TypeScript and Rust
while preserving its inputs, results, durable data, permissions, and observable
behavior. Language choice is primarily about authoring, libraries, and measured
performance. Host capability, executor, and scheduling are explicit dimensions;
choosing a language must not silently choose a different data model.

Charlie approved this direction and requested its LLP and implementation on
2026-09-14: “Write up an LLP encoding this and then do all the things on your
list.” This authorizes the implementation below. The Draft header records that
this transcription has not separately been ratified; it does not turn the
explicit implementation request into another approval gate.

This refines LLP 1027, rather than accepting every proposed engine or scaffold
in Draft LLP 1029. LLP 1029.000 continues to govern executable formats, signed
replacement and lifecycle. Existing modules and host capabilities are the units
of composition; no new module registry or arbitrary code evaluator is introduced.

## 2. What equality means

- Both languages answer Contract resource and mutation declarations through
  `DataSource`, using the plan's argument and result shapes.
- Durable state belongs to the runner Store or app-scoped host storage. The
  same app identity, paths, database schema, grants and serialization survive a
  language change. Changing language never grants a new capability.
- Source ownership is explicit. Routing never calls one implementation to
  discover whether it owns a name; that can perform effects twice.
- Permissions are enforced at host boundaries. A mixed app declares the union
  required by its sources; the source's own admitted scope still limits its
  requests and Store access. Candidate metadata cannot widen that authority.
- Pending work, errors, stale completion, replacement and external-read tracking
  retain their meaning across implementations. Filesystem/SQLite work is an
  explicit storage request, never a disguised HTTP URL.
- Web standards supply URL, text and base64 semantics. Native TS binds the
  canonical Ibex Rust implementations, with thin language adapters; apps do not
  maintain private UTF-8 implementations.

Application languages do not own the UI tree. Contract/runner owns UI state and
commits; data sources receive values and return values. A shared database is not
shared memory: Rust allocations, JS objects, native handles and runtime closures
retain an owner and do not cross the module ABI. Cross-runtime shared object
graphs remain outside scope.

When an actual application operation is blocked only because one language lacks
a host binding, expose the existing capability through the common boundary.
When one language is better for its implementation, keep that implementation
and make its service callable across the boundary. Preserve a difference when
it follows from the host, ownership, startup discipline or a measured cost;
name it explicitly instead of presenting incidental missing plumbing as policy.

## 3. Deliberate differences

Native Rust implements host services, rendering and OS integration. TypeScript
consumes exposed host services and JS/npm libraries; Rust consumes Rust/native
libraries. Equivalent services should be callable from either language without
requiring a second implementation of each library.

Rust may return `Answer::Later` and handle an `Outcome`; TS may use `await`.
Syntactic equality is unnecessary. Portable requests and outcomes are required:
a source that moves into a replaceable Rust module keeps its storage access
without carrying an OS handle or native closure through the ABI.

Native Rust remains trusted code and can reach OS APIs directly. Portable app
logic follows the explicit time/seed discipline of LLP 1027.000; TS's ambient
read guards do not claim to sandbox linked Rust. App JavaScript executes only
after first pixel; baked data supplies the first frame.

“Either language can run on any thread” is not the current application API.
Rust can create native threads, while each JS engine and browser realm has an
owner. In the current hosts, ordinary TS and Rust sources execute on the runner's
UI thread. The browser's private iframe isolates globals, not execution onto a
worker. The shipped common path offloads host I/O and returns results to that
owner; `await` resumes app computation there. There is no app-level thread selector.
Running arbitrary TS computations on another worker, or moving a Rust
data source there, requires explicit scheduling and transfer semantics. This
LLP does not equate `async` with parallel execution or promise a shared heap.

The native TS executor currently checks a default 100 ms elapsed-call budget
after each call/resume, including synchronous host bindings, result decoding,
captured-string restoration and shape validation.
It is not a preemptive deadline and is not yet a common guard on Rust or browser
sources. Therefore an overrun identifies a slow executor turn, not necessarily
slow TS computation. This executor difference remains explicit; moving an
operation to Rust does not by itself prove that the UI stays responsive.

## 4. Implementation

### D1 — The standard utility surface

Install URL/URLSearchParams, TextEncoder/TextDecoder and atob/btoa in the native
TS module environment, using Ibex's pure Rust algorithms. Keep browser-native
implementations in its private app realm. Test Unicode, invalid input, URL
mutation and encoding boundaries against the browser and native fixtures.
Replace the Messages UTF-8 byte counter and Fieldnotes backup encoding helpers
with the standard calls. Preserve explicit-time guards and the no-app-JS boot
rule. Broader services such as sockets and timers do not follow from this work.
The native decoder currently accepts UTF-8 labels only; other encodings refuse
with `RangeError`. Browser decoders retain their wider standard encoding set.
`Headers` retains its existing adapter. Neither difference is hidden behind a
claim that all WinterCG APIs or all encoding labels have been unified.

### D2 — Portable storage requests

Add a storage request/outcome variant to the existing host-work boundary. Its
versioned bounded payload uses JSON, with tagged signed integers and byte arrays
where JSON numbers would lose information. The Rust module ABI transports it;
no executor-local continuation crosses that ABI.

`exact-data` contains engine-independent composition and request helpers. A
separate native adapter executes storage through Ibex's existing app-directory,
filesystem and SQLite capabilities on host workers. The browser adapter uses
Exact's existing IndexedDB filesystem and SQLite worker. Grants come from the
admitted source/app, and paths are the same `app:/` namespace in both languages.
Rust module ABI 2 carries storage and preserves an absent scope separately from
an explicitly empty, deny-all scope. ABI 1 modules require a rebuild; this
pre-1.0 change does not add a compatibility decoder.

HTTP requests also retain source scopes. Native Ibex checks redirect targets;
browser scoped requests refuse redirects because browser fetch cannot expose
each redirect for authorization before following it. Browser CORS remains a
host restriction. These are executor differences shared by both app languages,
not a promise that every network operation works on every host.

SQLite request batches open and close their connection within host work. Atomic
write transactions use the existing SQLite transaction primitive. Read/execute
sequences are explicitly ordered; they are not advertised as transactions.
Prepared handles and arbitrary callbacks stay inside the host. Filesystem
atomic-write and database transaction guarantees remain separate; this does not
invent a transaction spanning both.

Validation/bake receive no effectful storage. Unload retires outstanding work;
late results cannot mutate a replacement session. Existing runner tickets and
external-read tracking govern settlement and cached answers.

**Windows implementation, 2026-10-04 (Codex; Charlie's Windows engine request):**
the vendored Ibex snapshot at `e3e00690` supplies app-scoped file operations over
retained directory handles. Every descendant open and mutation stays relative
to an owned handle; reparse nodes, alternate streams and ambiguous Windows name
aliases are refused. Exact's shared grant grammar and `app:/` admission remain
the authority; adding a platform backend adds no grant or storage request.

SQLite retains its maintained native Windows VFS and the existing trusted
embedder contract: the configured database ancestry must remain stable for the
connection's lifetime. Admission verifies the pinned parent identity and rejects
preexisting reparse nodes at the database and journal/WAL/SHM names. SQLite's
subsequent I/O is path-based; this is not a handle-relative VFS or protection
against a hostile host renaming ancestry during a transaction. Atomic file
replacement promises whole-file visibility, not Windows directory durability.
The upstream design and review are [Ibex LLP 0068](https://github.com/expo/ibex/blob/e3e00690/llp/0068-the-standard-library-for-a-rust-consumer.spec.md).

Qualification uses the existing `exact-data-host` storage tests and both calendar
persistence suites (actual SQLite reopen, rollback and paging), the vendored
Ibex file/SQLite tests, and affected strict lint. Refreshing the full snapshot
also checks the native C++ binding seam and prelude rather than inferring
compatibility from the Rust-only consumer. The result does not claim general
Windows application or TypeScript engine parity.

#### Proposed Windows native filesystem grant integration

Implementer: Codex, 2026-10-04, under Charlie's Windows engine/Skirmish request.

**Current route and gap.** `exact-grants` owns the pure grammar; vendored
`ibex2::grant` reexports it and supplies only filesystem realization. The runner
validates the complete set, retains exact source lines for child scopes, and
serializes typed tuples for browser admission. Updating upstream `grant.rs` in
place would delete this delegation and Exact's `doc:/` namespace.

Windows uses the shared native presenter/executor: a baked Rust source is wrapped
in `exact_data_host::Storage`, which converts a bounded storage request into an
owned continuation. `host/linux/src/executor.rs` uses the shared
`host/apple/src/executor_core.rs` worker to run that continuation. The worker's
direct storage-request refusal remains correct: only the storage adapter owns
that protocol. `data/host/src/native.rs` currently insists on `app:/` and opens
app directories before dispatching its file operation to Ibex. Native absolute
requests therefore need a narrow adapter route as well as the backend backport.

**One lexical authority, separate platform execution.** Put the upstream drive
parser in a small, pure `exact-grants::WindowsPath` seam. It exposes parsed drive,
components and canonical spelling, with no filesystem or Windows API dependency.
Both `PathPrefix` and the vendored Windows executor use it; the latter's local
`windows_path` module becomes a reexport, not another grammar. Actual NT opens
still validate each component before using it. This is the only new public Rust
seam; no app request, grant family, OS handle or foreign ABI is added.

Unlike upstream's platform-gated parser, Exact's pure parser recognizes this
syntax on every compilation host. A manifest must not change meaning when the
same producer runs on Windows, Linux or wasm. The namespace is `win:C`, disjoint
from POSIX, `app:` and `doc:`; recognizing it supplies no native executor on those
other targets. Preserve exact component comparison, ASCII drive folding,
canonical verbatim-disk alias handling, request-only traversal normalization,
strict component validation and every upstream UNC/device/reparse/remote-drive
refusal. Filesystem lookup follows its actual case policy; spelling aliases do
not enlarge lexical grants. Native path grants pin one local drive and all
admitted ancestors per operation, not permanently across operations. Hard links
retain their ordinary shared contents. Native SQLite execution remains refused.

`map_fs` preserves opaque app/doc/Windows namespaces instead of reconstructing
them as POSIX strings. The vendored realization helper returns the unchanged
lexical set on Windows, so a POSIX `/` grant cannot become a drive-root grant.
Non-Windows POSIX realization retains its existing behavior. Raw Rust code remains
trusted; these grants govern the host capability boundary, not an OS sandbox.

Port upstream JSON-quoted targets only for `fs.read` and `fs.write`, with complete
remainder decoding by `serde_json`, no trailing tokens/comments and no decoded
controls or lone surrogates. Preserve unquoted grammar and exact declared-line
child scopes; alternate JSON escape spellings do not become interchangeable
scope declarations. `PathPrefix` Display prints an unambiguous normalized target,
quoting spaces, quotes and backslashes. Preserve `doc:/` in that formatter too.
The round-trip guarantee excludes legacy programmatic POSIX/app/doc controls;
their constructors are not tightened by this change. Promote the existing
serde_json dev dependency in `exact-grants`; no engine dependency follows.

**Browser admission.** The browser currently verifies a typed tuple against its
source spelling, including a two-word token check. Extend that verification for
the same one-pass JSON string form and Windows lexical tuple, retaining full-set
validation, sealing and immutable admission. Match Rust's Unicode whitespace,
control and lone-surrogate behavior. Update the shared corpus and differential
fixtures rather than accepting arbitrary tuples or trusting a forged seal.
Windows tuples may be carried as inert declarations; browser `coversPath`,
IndexedDB storage and portable browser request execution continue to refuse
native disk paths. A Windows grant must never cover an app/doc/POSIX path or
invalidate unrelated valid app grants merely because this host cannot execute it.
No new browser module enters the pre-pixel graph.

**Windows request branch.** For existing `fs.*` storage operations, admit a valid
local-drive path without requiring configured app roots, just as chosen documents
already have their separate route. Do this classification without I/O. Validation
and bake still reject effects; child scopes, payload/result bounds, continuation
ownership, retirement and worker scheduling remain unchanged. On the worker,
parse the complete carried grant set and dispatch native file requests directly
to the backported `fs::run` with no app-directory initialization. It normalizes
and admits both operands before any OS lookup, then uses retained NT handles.
Unknown operations, malformed namespaces, cross app/doc/native operands and
ungranted paths refuse before opening or creating native nodes. Native SQLite
requests continue to refuse even if their grant spelling parses. Other platforms'
native request refusals remain; their app/doc operations are unchanged.

Keep existing app-directory creation, app path semantics, SQLite provider/VFS,
document ownership and serialization on their present routes. The backport
shares the existing Windows app operations over pinned operands internally; it
must rerun app storage and SQLite regressions rather than infer neutrality from
the diff. No host/windows window, GPU, sound, game save, C++ shim, Hermes archive,
bytecode version, storage protocol version or Rust module ABI changes are needed.
Exact's Windows TypeScript engine remains its existing explicit stub; this slice
does not claim to enable it.

### D3 — Routine mixed composition

A reusable composer routes explicitly declared source names to either executor,
checks duplicate ownership and app identities, and forwards lifecycle/configuration
to both. It isolates continuation identities and source grant scopes. A JS-only
replacement must preserve the admitted Rust implementation; enabled Rust updates
require the existing complete paired receipt. Construction must not silently
reset an arbitrary Rust source through `Default`.

Update Lab uses this composer instead of its own implementation. Fieldnotes
uses it for a real storage operation. No runtime probing, per-source content
hash system, new scheduler or loadable-module manifest registry is needed.

`build_mixed` reads the actual Rust source's identity and grants without
activating or querying it. Compatibility hashes the host's union ceiling and
each language's own grant declaration; a Rust receipt carries its source scope,
not a sibling's capabilities. Both Fieldnotes and Update Lab use this producer.

The current TypeScript first-frame producer still bakes through TypeScript.
An exclusively Rust-owned resource therefore needs a TypeScript bake placeholder
or a separate Rust first-frame producer. This change proves mixed mutations and
runtime source ownership; general mixed-resource baking and development
orchestration remain a concrete follow-up in `queue/`.

### D4 — Prove a stateful language move

Move Fieldnotes `backupNotes` to a Rust source while TS continues to save and
restore the same notes. Compare the operation against its TS implementation:
TS saves notes; Rust reads the same SQLite database and writes the same backup
format; a fresh TS module restores that backup; results, denied capabilities,
Unicode and size failures retain the same meaning. Prove a subsequent language
switch reads existing data without conversion. Exercise through an actual app
and through native/browser integration fixtures.

Fieldnotes keeps its mutation revision in the shared runner Store under
`secret.keep fieldnotes.revision`. Both implementations advance it on settlement,
including application errors. This replaces executor-local counters that could
collide after a language change or reload. The added grant names app-local state;
filesystem and SQLite grants, note schema and backup format stay the same.

### D5 — Scheduling is earned by a workload

The follow-on [LLP 1027.002](1027.002-optional-worker-execution.rfc.md) proposes
optional module placement for UI responsiveness. It remains Draft; the current
implementation and default described here have not changed.

Measure the real Fieldnotes backup/search workload, including near its supported
size limit, after replacing its private encoders. Report time spent in app
computation separately from storage. Existing I/O workers already offload native
storage and browser SQLite. `async` does not promise that computation after an
await runs off the UI/runtime owner.

Add a general source-worker API only if this concrete workload still requires
it after the utility and source changes. Such an API must support either language
with explicit inputs/results, cancellation and single-owner state; UI commits
stay on the existing owner. Resolving a measured hitch through the Rust source
and existing storage worker can satisfy this step without a new scheduler.

The measured large-result cost warrants a native transfer optimization behind
the existing app seam. For primitive strings of at least 64 Ki UTF-16 units,
the trusted prelude's JSON replacer records exact object/array paths and sends
the strings separately, leaving empty string placeholders in the JSON message.
JSON.stringify retains authority over getters, toJSON, omitted fields, cycles
and unusual values. Rust restores the strings before the existing shape check;
no property name is reserved and no application data is silently dropped.

Capture-path bookkeeping retains only the current ancestor chain, dropping
finished branches as the serializer advances. It allocates a link for each
visited object but no longer retains a WeakMap entry for every object. Paths
are still built only for captured strings; aliases are visited at their current
path, and built-in serialization still owns getter and `toJSON` evaluation.

The native capture binding is removed from globals before app initialization.
Each call owns its captures; errors, overruns, consumption and disposal clear
them. Aggregate capture storage is bounded by the module's heap ceiling. Direct
UTF-16 extraction and strict Rust decoding retain the existing refusal of lone
surrogates; decoding stays inside the call budget. The browser retains its JSON
transfer, and both paths keep the same module ABI and application values.
