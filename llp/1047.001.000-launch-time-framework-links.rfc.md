## 1. Summary

Every iOS app built on ExactKit links PhotosUI and AuthenticationServices, because one Swift file in ExactKit imports each. The loader maps them, and everything they link, before `main`, whether or not the app can ever show a photo picker or a sign-in sheet.

Known so far, at screening quality: in the iOS simulator each adds about 0.9 s to process start → `main` (overlapping: about 1 s together); on an iPhone 15 Pro the two together cost about 100 ms of a first-after-install launch and nothing measurable warm, from one sample per cell.

LLP 1047.001 already has the mechanism that removes this from most production apps: a capability is its own SwiftPM target, linked only when the app's composition names it. This RFC proposes:

1. measuring properly first (§4);
2. making the media picker and the sign-in sheet linked capabilities under LLP 1047.001 D4 (§5 E), which removes the cost from production apps that use neither;
3. trying a linker flag (§5 D) and, failing that, run-time Objective-C loading (§5 B) for what E leaves: development builds, which link everything (LLP 1047.001 D6) and are what the simulator runs, and apps that do use the two;
4. a check that fails when a framework no linked capability names enters the launch-time link (§6), whatever else is decided.

## 2. Why this matters

- **The budget.** `rules/RULES.md` holds cold start to interactive first frame at 100 ms p50. The phone's first-after-install launches measured here take 337–506 ms to interactive, so the budget is missed by a wide margin regardless, but ~100 ms is the size of the whole budget, spent on two capabilities most apps never use.
- **The simulator.** Every agent drive, smoke run and feel pass on an iOS simulator launches an app, and about 1 s of each launch is these two frameworks (§3.1). Development pays it, not users; it is what `QUEUE.md` first recorded on 2026-10-05.
- **It recurs.** Nothing today stops the next `import` of a heavy framework into ExactKit from adding the same cost silently. These two were found by a feel pass, not by a check.

The 2026-10-07 writeup parked this as "not worth it for ~100 ms on cold launches only". That weighed only the phone, and only the costly options. With LLP 1047.001 carrying out link-by-use, option E is that RFC's next step applied to two more capabilities.

## 3. Findings so far

None of the raw samples were kept. The phone's builds came from Exact commit `ddf16a21c` and branch `proto/no-photos-auth-cold`, neither reachable from this repository's remotes. The phases on the phone ("exec", "UIKit → app delegate", "interactive", and the cold/warm label) came from the measured app's own launch report, not Exact's. Every figure here is a size estimate for §4 to replace.

### 3.1 Simulator: a synthetic app

A one-file iOS app that logs process start → `main`, built with different link lines; iOS 27 simulator.

| Binary links | Images loaded | Process start → `main`, median |
|---|---|---|
| UIKit only (15 launches) | 504 | 168 ms |
| UIKit + the 12 other frameworks the iOS host links (15) | 824 | 1,136 ms |
| UIKit + PhotosUI alone (7) | +297 | +949 ms |
| UIKit + AuthenticationServices alone (7) | +313 | +932 ms |
| UIKit + GameController alone (7) | +8 | not measurable |
| UIKit + each of the other nine alone (7 each) | 0 | not measurable |

`otool -L` showed each test binary kept its load commands.

- The two frameworks pull in largely the same libraries, so their costs overlap.
- The simulator loads through `dyld_sim`, with its own binaries and caching. Its times say nothing about a phone.
- The frameworks are linked and not used, so this measures loading only.

### 3.2 Phone: cold against warm

iPhone 15 Pro, iOS 27, Xcode 27.1 RC, an app built against Exact. The first comparison showed exec falling from 187 to 14 ms without the frameworks. Later launches showed the build *with* both at 16 ms warm and 171 ms on the first launch after a reboot. So that first gain was mostly a first-after-install launch against a warm one.

### 3.3 Phone: first launch after install, both builds

Two builds from the same commit, identical except that N links both frameworks and P leaves them out. One sample per cell.

| Build | Launch | exec | UIKit → app delegate | Process start → interactive |
|---|---|---|---|---|
| N | first after install | 124 ms | 66 ms | 440 ms |
| P | first after install | 48 ms | 20 ms | 337 ms |
| N | warm | 17 ms | 23 ms | 265 ms |
| P | warm | 14 ms | — | 274 ms |

- First after install: about −100 ms to interactive, split between exec (−76) and UIKit's start (−46).
- Warm: no difference within noise.
- **This is not the after-reboot condition** §3.2 calls cold. The two differ for N alone (exec 124 against 171 ms), and neither has been compared across builds in the other condition.
- "exec" includes scheduling, paging and earlier initializers, not only dyld.

### 3.4 What brings them in

- `Picker.swift` imports PhotosUI for `PHPickerViewController`, used when an `input type="file"` has a non-empty `accept` made only of `image/…` and `video/…` (LLP 1069.002). The same `Picker` class also runs the document pickers (other `accept` lists, saving, LLP 1069.010), which need only UIKit. Core reaches it as `session.picker` (`Agent.swift`, `DocumentPickers.swift`).
- `Auth.swift` imports AuthenticationServices for `ASWebAuthenticationSession`, behind `openAuthSession` (LLP 1069.006). Core reaches it through `Session.authSessions` and `cancelAuthSessions()`. It is imported on macOS too, where the dyld showed no measurable cost (`QUEUE.md`, 2026-10-05).
- Neither `Package.swift` nor `build.mjs` names either framework: the link comes from Swift's autolinking of the two imports.
- tvOS links neither, judging from the built binaries.
- Other eager links remain (AVFAudio, AVFoundation, MetalPerformanceShaders with its SVG-filter warm-up). They added no images in §3.1, which does not mean they cost nothing.

## 4. What to measure

Each item says what it decides. M1–M3 come before any change; M4 comes with whichever of D or B is tried.

**M1. The launch conditions, four link variants, on a phone.** Release builds of one app with identical data: neither framework, PhotosUI alone, AuthenticationServices alone, both. Each in three conditions: first launch after install, first launch after a reboot, and a later launch. Several blocks in randomised order; keep the raw samples; record the OS build, binary hashes and install method. *Decides* whether the cold cost is real, its size, and whether one framework is most of it.

**M2. One Instruments launch trace per variant**, cold. *Decides* where the time goes: mapping and fixups, initializers and Objective-C registration, or page-ins. That says whether D can help at all.

**M3. The simulator, the same four variants**, on the agent's own launch path (`scripts/agent.mjs ios`), 15 launches each. *Decides* what an agent drive or smoke run gains, which is what D and B are for once E has landed.

**M4. First use.** For D or B: request → visible sheet, and main-thread stalls, for the first photo pick and the first sign-in sheet in a process, on a phone, against today's build. *Decides* whether deferring the cost moves it somewhere a person feels it. E needs no M4: an app that links the capability loads it at launch as today.

The harness and its raw output are kept beside this document so the numbers can be rerun (Q2).

## 5. Options

### E. Link the two by use (LLP 1047.001 D4)

Make the media picker and the sign-in sheet two capability targets, `ExactMediaPicker` and `ExactAuthSession`, beside `ExactGroupedLists`, `ExactMarkdown`, `ExactSurfaces` and `ExactDrag`. The composition names them only when the plan uses them, so an app that never picks media or signs in does not link PhotosUI or AuthenticationServices at all.

- **The picker splits in two.** The PHPicker path moves into `ExactMediaPicker`; the document pickers stay in core, since they need only UIKit. Core's `session.picker` keeps its role as the place the agent's answers and the staged files go (LLP 1069.002 D4, LLP 1069.007); the capability registers the media presenter with it, and with the media capability absent an image-only `accept` falls back to the document picker or is refused by name (Q3).
- **The use-set key.** Rust already has `picker` as its own capability (LLP 1047.001 §8); the media picker needs either its own key (`accept` lists made only of image and video types) or the whole `picker` key. Authentication is "always" in Rust today, decided "from strings and grants"; on Apple the `auth.session` grant (LLP 1069.006) is the natural key for the Swift target.
- **What it costs:** the same slice as each capability before it (LLP 1047.001 §6 step 4): the Swift target and its registration, core's references removed, the composition's `--embed` output, refusal at boot and on a candidate, and two final links, one with each.
- **What it does not fix:** development builds link everything (LLP 1047.001 D6), and those are what the simulator runs for agent drives; an app that does pick media or sign in keeps paying at launch. D and B are for those.
- No new artifact and no run-time loading: the picker and the sheet behave exactly as today wherever they are linked.

### D. A linker flag: `-delay_framework`

The linker in Xcode 27.1 (`ld-27037.1`) documents `-delay_framework name` ("the same as `-framework name` but also specifies that the framework should be delay initialized"), `-delay_library` and `-delay-l`. It documents no `-lazy_framework`; the 2026-10-07 writeup said it does, and I could not find it. Lazy dylib loading appears to have been removed.

- Delay-init still records a load command, so the framework is still mapped and bound at launch. What it can defer is the framework's initializers and Objective-C registration. If M2 shows mapping dominates, D cannot help much; if it shows initializers (UIKit → app delegate was 46 ms of the 100), it may.
- Autolinking adds an ordinary `-framework` for each import, and an ordinary dependency on the same framework is expected to defeat the delay. So D needs `-Xswiftc -Xfrontend -Xswiftc -disable-autolink-framework -Xswiftc -Xfrontend -Xswiftc PhotosUI` (the same for AuthenticationServices) beside `-Xlinker -delay_framework -Xlinker PhotosUI`, in the `swift build` arguments `build.mjs` assembles. An embedder linking through `--embed` needs the same flags.
- **To do:** build with the flags; read the linker's warnings and `otool -l` for the load command's kind; launch in the simulator (M3) and on a phone (M1, both cold conditions). A morning's work.

### B. Load the frameworks at run time through their Objective-C API

`PHPickerConfiguration`, `PHPickerFilter`, `PHPickerViewController` and `ASWebAuthenticationSession` are public Objective-C classes; the Swift types are overlays on them. Swift code can `dlopen` the system framework on first use and reach the classes and selectors by name.

- No static reference may remain, or the framework returns to the link; §6's check proves it.
- The delegate needs no declared conformance: an Objective-C delegate property's protocol is not checked at run time, so an `NSObject` subclass that answers `picker:didFinishPicking:` is enough. `ASWebAuthenticationPresentationContextProviding` is the same.
- The work is exact message signatures, ownership of what crosses (the results array, item providers, the completion block), availability checks and errors.
- Sign-in first: `Auth.swift` is 110 lines over one class. The picker (311 lines, of which the PHPicker part is a fraction) follows only if sign-in is clean.
- B composes with E: the code lives in the capability target, and the frameworks load only when a linked capability is first used.

### A. Move each into an on-demand module

As video, web and sound are (`VideoModule.swift`, `arm(...)` in `build.mjs`): one dylib per capability, `dlopen`ed on first use behind a C interface. E and B together give everything A would at a fraction of the cost: E removes the frameworks from apps that never use them, and B defers them in apps that do, without a C interface, a new artifact, IPA wrapping or a missing-module failure. A is recorded so it is not proposed again; it needs a yes for the new artifact and is not recommended.

### Not options

- **Weak linking.** A weak-linked framework that is present is still loaded at launch; weakness only lets it be absent.
- **Mergeable libraries.** The linker needs a framework's implementation, and the SDK ships only stubs for system frameworks.

## 6. Stop it regressing

Wanted whichever option is chosen, including none:

- **A launch-link check.** After a production iOS link: read the app binary's load commands and fail when a framework is loaded at launch that neither core nor a linked capability names. Each capability target declares the system frameworks it brings; core's list is today's 13 minus the two here once E lands. A new framework is then a reviewed one-line change, not a silent cost. With E, this is also the proof that an app without the media picker links no PhotosUI. Whether it runs in `build.mjs` or the async lane depends on its cost (it reads one binary, so probably the build).
- **The phases in Exact's own report.** Process start → ExactKit's first code, `main` → app delegate, and → first pixel, reported by the native host and readable through the agent's `state`, so a heavy new link shows up the day it lands. I found no such report in the Apple host today (a `firstPixel` lifecycle hook, not timings); §3's phases came from the measured app's own report. Adding one is apparatus and needs a yes.

## 7. Open questions

- **Q1. The order.** This RFC's recommendation: M1 and M2, then E (it is LLP 1047.001's work and helps every production app that uses neither), then D for the simulator, then B only if D fails and M3 or M1 says the remainder matters.
- **Q2. Where the measurement harness lives:** a `scripts/launch-bench.mjs` (apparatus: needs a yes) or a one-off under `llp/research/` with its raw output.
- **Q3. An image-only `accept` without the media capability:** the document picker (it can pick images, less well), or a named refusal as LLP 1047.001 D5 does for every other unlinked capability. The refusal is consistent; the fallback is kinder to an app whose use-set missed it.
- **Q4. Which cold condition counts** against the 100 ms budget: first after install (every App Store update; LLP 1030 bundles aside), first after a reboot, or both reported.
- **Q5. The other eager links** (AVFAudio, AVFoundation, MetalPerformanceShaders and its warm-up): measured in M1's harness now, or left to §6's check.
- **Q6. macOS.** Its AuthenticationServices link showed no measurable cost (`QUEUE.md`); E would remove it from macOS apps without the grant anyway.
