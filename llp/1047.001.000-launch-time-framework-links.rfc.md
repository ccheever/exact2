## 1. Summary

Every iOS app built on ExactKit links PhotosUI and AuthenticationServices, because one Swift file in ExactKit imports each. The loader maps them, and the libraries they link, before `main`, whether or not the app can ever show a photo picker or a sign-in sheet.

Known so far, at screening quality: in the iOS simulator each adds about 0.9 s to process start → `main`, overlapping (§3.1); on an iPhone 15 Pro, leaving both out took about 100 ms off a first-after-install launch to the app's "interactive", and nothing measurable warm, from one sample per cell (§3.3).

This RFC proposes, in order:
1. **Measure** (§4): a link screen, then launches on a phone and in the simulator with enough samples to decide.
2. **Link the two by use** in production (E) and in development (F, ruled R1): two Swift capability targets, selected by two new keys. An app that never picks media or signs in then links neither framework, on a phone and in the simulator, with no change in behaviour where they are linked.
3. **The linker's deferral** (D) is closed at the iOS 17 floor: M0 found the linker emits neither delay-init nor lazy loading there, and delay-init fails the link (§5 D, Appendix A). It survives only per app, for an app that sets its own floor of iOS 27.
4. **B against A**, run-time loading against a loaded module, only if §4 says what remains for apps that use the two matters.
5. **A launch-link check** (§6), so the next heavy import is a reviewed change, not a silent one.

## 2. Why this matters

- **The budget.** `rules/RULES.md` holds cold start to interactive first frame at 100 ms p50. The phone launches measured here took 337–506 ms to the source app's "interactive" with or without the frameworks, so the budget is missed regardless; ~100 ms is the size of the whole budget. This repo's clock for the budget's endpoint is `session.firstDrawMs` (`Session.swift:399`), which §4 uses.
- **The simulator.** Every agent drive, smoke run and feel pass on an iOS simulator launches an app, and about 1 s of each launch is these two frameworks (§3.1). It is paid by development; `QUEUE.md` first recorded it on 2026-10-05.
- **It recurs.** Nothing today stops the next `import` of a heavy framework into ExactKit from adding the same cost silently.
- **Who uses them** (R6): of the repo's 36 apps, one has a file input (`fieldnotes`, `accept="application/json"`, the document picker) and one signs in (`auth-fixture`); none needs the media picker. Under E and F, 35 would link neither PhotosUI nor, apart from the fixture, AuthenticationServices.

## 3. Findings so far

None of the raw samples were kept. The phone's builds came from Exact commit `ddf16a21c` and branch `proto/no-photos-auth-cold`, neither reachable from this repository's remotes, and the variant recipes (how the frameworks were removed) were not recorded. The phone's phases came from the measured app's own launch report, not Exact's: its "exec" is process start → Exact's constructor, and its "interactive" is the app's own mark. Every figure here is a size estimate for §4 to replace.

### 3.1 Simulator: a synthetic app

A one-file iOS app that logs process start → `main`, built with different link lines; iOS 27 simulator.

| Binary links | Images loaded | Process start → `main`, median |
|---|---|---|
| UIKit only (15 launches) | 504 | 168 ms |
| UIKit + the 12 other frameworks the iOS host links (15) | 824 | 1,136 ms |
| UIKit + PhotosUI alone (7) | +297 | +949 ms |
| UIKit + AuthenticationServices alone (7) | +313 | +932 ms |
| UIKit + GameController alone (7) | +8 | not measurable |
| UIKit + each of the other nine alone (7 each) | 0 | not measurable |

- `otool -L` showed each test binary kept its load commands.
- The two frameworks pull in largely the same libraries: all thirteen together add 320 images, so the two overlap almost entirely. No PhotosUI + AuthenticationServices pair without the others was measured.
- The simulator loads through `dyld_sim`, with its own binaries and caching; its times say nothing about a phone. The extra time tracks the extra images.
- The frameworks are linked and not used, so this measures loading only.

### 3.2 Phone: cold against warm

iPhone 15 Pro, iOS 27, Xcode 27.1 RC, an app built against Exact. The first comparison showed exec falling from 187 to 14 ms without the frameworks. Later launches of the build *with* both showed 16 ms warm and 171 ms (506 ms to interactive) on the first launch after a reboot. So that first gain was mostly a first-after-install launch against a warm one.

### 3.3 Phone: first launch after install, both builds

Two builds from one commit, identical except that N links both frameworks and P leaves them out. One sample per cell.

| Build | Launch | exec | UIKit → app delegate | Process start → interactive |
|---|---|---|---|---|
| N | first after install | 124 ms | 66 ms | 440 ms |
| P | first after install | 48 ms | 20 ms | 337 ms |
| N | warm | 17 ms | 23 ms | 265 ms |
| P | warm | 14 ms | — | 274 ms |

- First after install: 103 ms less to interactive. The two phase deltas (exec −76, UIKit's start −46) sum to 122 ms, so the phases overlap or another phase moved the other way; they are not a split of the 103.
- Warm: one sample per build; no difference is visible, which does not establish that there is none.
- **This is not the after-reboot condition** §3.2 calls cold. The two conditions differ for N alone (exec 124 against 171 ms), and the builds have not been compared after a reboot.
- First after install is what an App Store update's first launch resembles, but an in-place update was not measured.

### 3.4 What brings them in

- `Picker.swift` imports PhotosUI (under `canImport(UIKit)`) for `PHPickerViewController`, taken when an `input type="file"` has a non-empty `accept` made only of `image/…` and `video/…` (`Picker.swift:229-240`; LLP 1069.002). The same `Picker` class runs the document pickers and save (`DocumentPickers.swift`), which need only UIKit. `Session.swift:1111-1120` calls it; `Agent.swift:181-183` delivers the agent's answers to it. Under the agent, `show` returns before any OS object is built (`Picker.swift:79-82`).
- `Auth.swift` imports AuthenticationServices for `ASWebAuthenticationSession`, behind `openAuthSession` (LLP 1069.006). `Session.swift:1009` and `:1461` call `authOp` and `cancelAuthSessions()`. `authOp` takes `authSessions` (`Auth.swift:35`) before it checks for the agent's hold (`:48-50`), and the hold, the cancel path and both callback forms (`ASWebAuthenticationSession.Callback`, `.https` and `.customScheme` from iOS 17.4, `callbackURLScheme` below it, `:64-73`) live in the file that imports the framework. macOS imports it too; there the dyld showed no measurable cost (`QUEUE.md`, 2026-10-05).
- Neither `Package.swift` nor `build.mjs` names either framework: Swift's autolinking of the two imports brings them.
- tvOS links neither, according to the source's built binaries; that is not checked here.
- Other eager links remain (AVFAudio, AVFoundation, MetalPerformanceShaders and its SVG-filter warm-up, GameController). They added few or no images in §3.1, which does not mean they cost nothing (R7).

## 4. What to measure

Each step says what it decides and what would count. The harness is a throwaway in the measurer's scratch directory; the raw samples and each variant's recipe (exactly how a framework was removed or deferred) go into Appendix A (R4).

**M0. The link screen** (an hour; no device). For the four variants (neither framework, PhotosUI alone, AuthenticationServices alone, both) and, separately, for D's two flags: the final executable's load commands and their flags (`otool -l`), the linker's warnings, and the effective link line. The same screen lists which source brings each of the other eager frameworks (AVFAudio, AVFoundation, MetalPerformanceShaders, GameController) and, in the simulator, the images each adds (R7); that list seeds §6's declarations. At the iOS 17 floor, does the linker emit a delayed or lazy load at all, or fall back to an ordinary one? *Decides* whether D can exist under R2 (§5 D), and that each M1 variant is the variant it claims to be.

**M1. The phone** (iPhone 15 Pro; a second model if one is free). Release builds of one app with identical data, the four variants. Three conditions, each its own procedure:
- *first launch after install:* reinstall, then one launch;
- *first launch after reboot:* a reboot before every sample, not one reboot per block;
- *warm:* later launches of the same process image, after one discarded launch.

At least seven samples per cell, in randomised blocks; the install method fixed and recorded, with the OS build, the binary hashes, and whether the launch was prewarmed (iOS may prewarm a process before a tap). Each sample records, from the host's existing timings: process start → `main` (`execToMainMs`, `ExactIOS/main.swift:28`), `main` → `didFinishLaunching` (the stamp), and process start → first draw (`firstDrawMs`); and the loaded image count at `main` (`_dyld_image_count()`, logged by the throwaway probe build only). A difference counts when the medians differ by at least 20 ms and each median lies outside the other's interquartile range. The budget is judged against the worse of the two cold conditions (R8). *Decides* whether the cold cost is real in either cold condition, its size against the budget's endpoint, and whether one framework is most of it.

**M2. Attribution** (diagnostic, not a decision by itself). One Instruments launch trace per variant on the phone, in the cold condition M1 shows the larger difference in, and one System Trace per variant in the simulator. *Says* where the time goes: mapping and fixups, page-ins, initializers and Objective-C registration. A deferral (D, B, A) can only recover what is not mapping.

**M3. The simulator**, two runs, because they are two links after E and F:
- the *development agent launch*, `scripts/agent.mjs ios` (development, so F's link), 15 launches per variant;
- the *production-composition smoke* (LLP 1047.001 D6: an app's smoke runs its production composition), 15 launches per variant.
Each records the same timings and the image count. *Decides* what an agent drive and a smoke run gain.

**M4. First use** (for D, B or A only). Request → visible sheet, and the main thread's longest stall, for the first photo pick and the first sign-in sheet in a process, on the phone, against today's build, seven samples each. *Decides* whether deferring the cost moves it somewhere a person feels. A first-use regression over 100 ms, or a visible hitch in the sheet's animation, rules the deferral out for that capability.

**M5. Functional acceptance** (for every option, E and F included: moving the code changes ownership and registration even where the frameworks stay eager). On a device and in the simulator, with the capability linked:
- a media pick: selection, cancellation, multiple selection order and names, the temporary file copied inside the callback and alive until delivered into `app:/tmp/picked/`, HEIC conversion and metadata;
- the document picker and save, unchanged, with and without the media capability linked;
- a sign-in: completion, cancellation, an `https` callback and a custom-scheme one (and the pre-17.4 initializer on an iOS 17 runtime), supersession and the late completion dropped, the 499 and 502 outcomes;
- two sessions in the sample host (`smoke.mjs host`), teardown and reload with a sheet open;
- under the agent, both substitutes answer and neither framework's class is touched (on F's link, they are not even linked);
- with the capability absent, the named refusal at boot and on a candidate (LLP 1047.001 D5);
- macOS unchanged; tvOS still refuses both.

**M6. Build cost.** The incremental Swift rebuild of a touched `Picker.swift` and a touched core file, before and after the split, against the parent's rebuild budgets (LLP 1047.001 §5).

## 5. Options

### E. Link the two by use in production (LLP 1047.001 D4)

Two capability targets, `ExactMediaPicker` and `ExactAuthSession`, beside `ExactGroupedLists`, `ExactMarkdown`, `ExactSurfaces` and `ExactDrag`. An app whose composition names neither links neither framework.

**What stays in core.**
- The `Picker` class, the document pickers, save, the staging directory, and the agent's answers (`Agent.swift:181-183`). The media capability registers a media presenter with `session.picker`; core asks it only when the `accept` is media-only.
- The auth op's ticket handling, the agent's hold (the `ExactEnv.agentMode` check, moved ahead of anything that touches the capability), cancellation bookkeeping and `authDone`. The capability registers the presenter and the live-session table it owns. With the capability absent, an `auth` op that is not held answers 501 with a named reason, as tvOS does today.

**The two keys.**
- **`media_picker`**, a new `Capability` in `runner/src/uses.rs`, set where `Picker` is set (`:272`) when the input's `accept` is a literal non-empty list made only of `image/…` and `video/…` types, **or is computed** (LLP 1047.001 D2 counts a computed value as every arm it can take). `showPicker(id)` takes its element's `accept`. An app with only document inputs links `picker` and not `media_picker`.
- **`auth_session`**, selected by the `auth.session` grant, not the plan: a data source's requests are the source's, as the bake already does for I/O (`bake/src/link.rs:32-44`). It is a name `Capability::from_name` accepts, so the manifest's `link` can name it ahead of use. Rust's auth device link stays "always" (`host/apple/src/link.rs:199`); only the Swift target, which is what imports the framework, follows the key.

**Where each enters.** `appleComposition` and its `SWIFT_CAPABILITIES` table (`link.mjs:7`, `:18-21`); `exact_bake::apple_link` for the grant; the generated composition's `install()`; `Package.swift`'s `capabilities` table; the `--embed` product list and `capabilities.json`. Because the grant ceiling is already a compatibility input (the bake reads `compat.inputs["grantCeiling"]`), a delivered candidate that adds `auth.session` is a binary change, and `deploy.mjs` classifies it so (parent D8).

**Refusal.** An image-only `accept` on a binary without `media_picker` is refused at boot and on a candidate, by name (`Unlinked("media_picker")`), as LLP 1047.001 D5 requires; never a silent fall back to the document picker.

**Cost:** the parent's slice per capability (LLP 1047.001 §6 step 4), twice: the targets and their registration, core's references removed, the keys, the composition and `--embed` output, the refusal, two final links each, and M5.

### F. Development links the two by use too (ruled R1)

Development builds link every capability so any plan runs (LLP 1047.001 D6). For these two the agent does not need them: its substitutes answer before either framework's object is built. So a development link names `media_picker` and `auth_session` only when the app's production composition would (its plan, its grants, its manifest `link`), and every other capability stays linked.

- An agent drive of an app that uses neither drops both frameworks from the simulator launch; that is §2's ~1 s, to be confirmed by M3.
- A plan reloaded in development that newly uses one: under the agent, the substitute answers as before. A person's tap, or a drive with `EXACT_DEVICE=real`, gets the named refusal, whose message says to rebuild.
- Whole-vocabulary fixtures that exercise the real pickers keep an all-linked build (`EXACT_APPLE_LINK=all`), as the parent's D6 already allows.
- An app that uses either still pays in development; D, B or A are for that, if M3 says it matters.

### D. The linker's deferral: closed at the iOS 17 floor; per app above it

M0 ran it (Appendix A, M0.1). At the iOS 17 floor the linker emits neither deferral, so under R2 D is closed for every app on the floor.

- **`-delay_framework`** is documented in `ld.1`. Below iOS 18 the linker warns "delay-init will be ignored … because deployment target version is too low", and it **fails the link** wherever the code names the framework's Objective-C class directly ("use of ObjC class 'ASWebAuthenticationSession' … cannot be delayed when targeting an older OS versions"). At iOS 18 it works for Objective-C references: the load command becomes the `dylib_use_command` (name at offset 28, `loader.h`: "First supported in macOS 15, iOS 18"). The framework is still mapped at launch; only its initialization waits, so it cannot touch the simulator's cost, which tracks images mapped.
- **`-lazy_framework`** is in the linker binary but not in `ld.1`. It is ignored as "too low" at iOS 18 and 26.4, and works at iOS 27: the framework leaves the load commands entirely, replaced by `LC_LAZY_LOAD_DYLIB_INFO` and a `__lazy_load_got` section.
- **Swift overlay types defeat both at any target.** `PHPickerFilter` and `PHPickerConfiguration`, which `Picker.swift` uses, are Swift structs: "nominal type descriptor for PhotosUI.PHPickerFilter … cannot be delayed" (and "cannot be lazy loaded"). Either flag needs the capability's code to reach only the Objective-C classes, which is most of B's work.

**What is left of D.** An app may set a higher floor of its own (`host.ios.minimumOS` in `app.json`; `deploymentTargets`, `build.mjs:120-127`). An app at iOS 27 or later that links a capability could take `-lazy_framework` for it, once the capability's code reaches the framework only through Objective-C classes; that is B's code with the linker doing the loading. It is not proposed now: no app in the repo sets a floor above 17.0, and B, if it is ever built, works at every floor.

Either flag would also need the framework's autolinking suppressed (`-Xfrontend -disable-autolink-framework`), which M0 found `swiftc` accepts; the SwiftPM path through `build.mjs` is untested.

### B. Load the frameworks at run time through their Objective-C API

`PHPickerConfiguration`, `PHPickerFilter`, `PHPickerViewController` and `ASWebAuthenticationSession` are public Objective-C classes. The capability target can `dlopen` the system framework on first use, keep the handle for the process, and reach the classes and selectors by name. Public classes and selectors reached that way are not private API; App Store acceptance is a separate, untested question.

What a prototype must establish, sign-in first:
- whether the frameworks check the delegate and the presentation provider with `respondsToSelector:` or `conformsToProtocol:`; if the latter, `objc_getProtocol` and `class_addProtocol` after `dlopen` are public and B adopts the protocol at run time;
- exact calling conventions for each selector, the retained initializer results, the completion block's lifetime, and strong ownership behind the frameworks' weak delegate and provider properties (`PHPicker.h`, `ASWebAuthenticationSession.h`);
- both callback forms and the pre-17.4 initializer, and the typed errors, resolved dynamically;
- the in-callback copy of the item provider's file and the hop to the main queue (`NSItemProvider` is Foundation and stays typed);
- that no static reference remains, which §6's check proves.

B composes with E: the code is in the capability target, which loads the framework only when first used.

### A. A loaded module per capability

As video, web and sound are (`VideoModule.swift`, `arm(...)` in `build.mjs`): a dylib per capability, `dlopen`ed on first use behind a C interface, with a new arm, IPA wrapping and signing, macOS placement, cache inputs, a missing-module failure and `--embed` support. It costs more than B in packaging and ABI, but keeps compiler-checked calls, protocol conformance, ARC and availability checks inside the module, which B gives up. A is B's comparator: if B's prototype is brittle, A is the deferral. It is a new artifact and needs a yes.

### Not options

- **Weak linking.** A weak-linked framework that is present is still loaded at launch; weakness only lets it be absent.
- **Mergeable libraries.** The linker needs a framework's implementation, and the SDK ships only stubs for system frameworks.
- **Raising the deployment floor** for D. R2 keeps it.

## 6. Stop it regressing

Two pieces of apparatus, both approved (R5).

**A launch-link check.** After a production iOS link, `build.mjs` reads the final executable's load commands (one binary; well under a second) and fails when a framework is in the wrong state. It lands with E holding the first two states; the third is added only when D, B or A lands (R5).
- **absent:** a framework only a capability brings, when the composition does not name that capability;
- **eager-permitted:** core's list, plus the frameworks each linked capability target declares;
- **deferred-required:** a framework a linked capability promises to defer (D: its load carries the delayed flag; B or A: it is not in the load commands at all).

Core's list is derived from a fresh `otool -L` of a one-text production binary when the check lands, not from the unavailable experiment's count; capability frameworks are declared on the targets that import them (GameController and AVFAudio on `ExactSurfaces`, for instance, if that is where they come from). A new framework is a reviewed one-line change to a declaration.

What it does not prove: the binary's direct load commands are not the launch closure (the hundreds of transitive images), and a framework's state says nothing about when it initializes. Those are runtime facts, which M1 and M3 measure with the image count. For an embedder, the guarantee is that Exact's products introduce no load of an undeclared framework; the embedding app may link either framework itself. A development link is checked the same way against F's composition.

**The launch phases on `state`.** iOS already measures process start → `main`, `main` → `didFinishLaunching`, window, first layout and first draw, and prints them under `EXACT_SMOKE=1` (`ExactIOS/main.swift:148-154`); macOS puts `firstPixelMs` on `state` (`ExactMac/main.swift:271`). The iOS agent's `ready` carries only boot, views, error and pid (`ExactIOS/main.swift:120`). Putting the existing phases on iOS's `state` lets a drive see a heavy new link the day it lands. Under R2, a phase an older OS cannot measure is blank.

Neither runs in the five-check gate; the check runs in the production build, and timings stay in the async lane and metrics.

## 7. Order of work

1. **M0**, then **M1** on today's build and the four variants. If M1 shows no cold difference over 20 ms in either condition, E and F still go ahead for the simulator (M3) and the regression check; D, B and A stop.
2. **E and F together**, as one slice per capability (sign-in first: smaller, and its key is the new kind), with M5.
3. **M3** on the result.
