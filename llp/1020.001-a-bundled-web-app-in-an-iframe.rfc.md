# LLP 1020.001: A bundled web app in an iframe

**Type:** RFC
**Status:** Draft
**Systems:** Apple host (the web arm, `host/apple/webarm/WebArm.swift`: a `WKURLSchemeHandler` serving the app's assets; `ExactKit/WebModule.swift`: the read it hands the arm), the web host (unchanged: the parity oracle), Agent API (unchanged), `docs/agent-pitfalls.md`
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Implementer:** Claude (Opus 5.5), on acceptance
**Date:** 2026-10-15
**Related:** LLP 1020 D2 (the bundle-relative `src` and its declared limit: "multi-file local decks wait for scheme-handler serving"), §8 Q1 (Castle's `castle-deck://` origin, served in-process), §10 (one document per row; #106, #135); Rami Maalouf's Exact Draw report (https://github.com/rami-maalouf/exact-draw/blob/main/docs/exact-experience.md, section 002); `issues/20261015-chosen-documents-outlast-the-launch.md` (the same app's other gap)

## 1. Summary

An `iframe` whose `src` is a page in the app's `assets/` runs that page with
its scripts, stylesheets, fonts, workers and lazy chunks on the web, and only
its HTML on Apple. The Apple web arm serves the app's assets under a custom
URL scheme through a `WKURLSchemeHandler`, so every relative URL in the page
resolves to the file beside it, read through the session's asset resolver.
The web host does not change.

## 2. Motivation

Exact Draw embeds Excalidraw, a built web app of JavaScript, CSS, fonts and
asynchronous chunks, in a Contract shell. On the web, `src="assets/editor/index.html"`
works: the build copies `assets/` beside the app's page
(`host/web-js/build.mjs`), so the page's relative URLs load. On macOS and iOS
the arm reads the one HTML file and gives it to WebKit as a document at
`http://exact.localhost/frame/<id>/index.html` (LLP 1020 §10). No server
answers that origin, so every sub-resource fails and the frame is blank. Exact
Draw serves the editor from a Bun process on loopback instead, which the app
cannot start by itself.

This is the case LLP 1020 D2 declared and left for a consumer: a multi-file
local page. Exact Draw is that consumer. A single-file build (everything
inlined) is a workaround, not a fix: a large app's lazy chunks, workers and
wasm do not inline.

## 3. Design

**D1: the app's assets have an origin on Apple.** The arm registers a
`WKURLSchemeHandler` for the scheme `exact-app` on every web view it makes.
A local `src` (schemeless, as now) is loaded as
`exact-app://app/<path>`; `<path>` is its path under the asset root. Every
request to that origin is answered from the app's assets: the page's
`./app.js` is `exact-app://app/editor/app.js`, read from `assets/editor/app.js`.
The origin is the same for every iframe and every launch of the app, as a
web build's origin is the same for every page under it, so a guest's
`localStorage` and IndexedDB persist across launches. A standalone app is its
own process and data store, so the host needs no app id in it; an embedding
app (LLP 1031) shares its data store with its own web views, which do not
register `exact-app`.

`WKURLSchemeHandler` cannot take `http` or `https` (WebKit handles those
itself and refuses the registration), so `http://exact.localhost` cannot be
served this way. Castle shipped the same mechanism for its decks
(`castle-deck://`, LLP 1020 §8 Q1).

**D2: what is served.** Anything under the asset root that the resolver
holds, by path, after the containment check the arm makes now (symlinks
resolved, nothing outside the root). A missing file is a 404 response, and
the host logs it (`exact: iframe <src>: <path> is not in the app's assets`).
The content type comes from the extension, with the types a browser is
strict about named exactly: `text/javascript` for `.js` and `.mjs` (module
scripts refuse other types), `application/wasm` (streaming compilation
requires it), `text/css`, and the font types. Range requests are answered,
for a page's `audio` and `video`. On the web these files are public beside
the app's page already, so serving them to a guest exposes nothing new.

**D3: reads go through the session's resolver.** ExactKit already reads the
top document through `ExactApp.resolver` (`WebModule.swift`) and hands the
bytes to the arm. The arm gains one more entry from ExactKit, a read callback
it calls with a path off the main thread. A delivered generation's assets
and a development client's assets (the dev URL) therefore reach every
sub-resource, as they reach the top document now. The arm stops reading
`EXACT_ASSETS` or the bundle itself.

**D4: the table of LLP 1020 §10, as amended.**

| Guest | macOS | iOS |
|---|---|---|
| Local page (a schemeless `src`) | direct, at `exact-app://app/<path>` | direct when its viewport `<meta>` asks for `width=device-width` at scale 1; otherwise the wrapper, its inner frame at `exact-app://app/<path>` |
| Remote http(s), no `sandbox` | direct (unchanged) | the wrapper (unchanged) |
| Remote with `sandbox`, and `data:`/`about:`/`blob:` | the wrapper (unchanged) | the wrapper (unchanged) |

A local page's `sandbox` is sent as `Content-Security-Policy: sandbox …` on
its response when it is direct, as now, and is the inner frame's attribute
under the wrapper. The guest origin the message checks expect becomes
`exact-app://app` (or `null` when sandboxed without `allow-same-origin`).
A non-HTML local file (a PDF, an image) is served the same way, replacing
the typed-document path of #115.

**D5: what is unchanged.** The web host, the Contract surface (no new tag,
attribute or event), `app:/` sources (LLP 1020 §10, "App files"), remote
guests, the agent's `tree` and `screenshot` of a guest, and the arm's
on-demand load: the handler lives in the web arm's library, so an app with no
`iframe` pays nothing for it.

**What the web does differently, and stays different.** On the web a page in
`assets/` is same-origin with the app's own page: an unsandboxed guest can
reach `window.parent.document`. On Apple it is cross-origin to the wrapper,
and direct on macOS it has no parent. LLP 1020 D2 already accepts the native
arm as the stricter one. An author who wants the web to match writes
`sandbox`.

## 4. Open questions, answered by a probe before building

A one-file `WKWebView` probe with the handler, on macOS 27 and the iOS 27
simulator, loading Excalidraw's production build from a directory:

- **Q1: is `exact-app://app` a secure context?** Excalidraw and other apps
  need `crypto.subtle` and the clipboard, which require one. #135 moved local
  pages to `http://exact.localhost` because WebKit treats loopback as secure
  and refuses `http:` sub-resources from an `https:` page. If a custom scheme
  is not secure in WebKit and no public API makes it so, this design fails and
  the alternative in §5 is the one to measure.
- **Q2: do module scripts, dynamic `import()`, `new Worker()`,
  `WebAssembly.instantiateStreaming` and `fetch` load from the scheme?** Each
  must be checked, not assumed.
- **Q3: does `localStorage` and IndexedDB data under `exact-app://app`
  survive a relaunch** in the app's default data store?
- **Q4: does WebKit enforce `Content-Security-Policy: sandbox` on a direct
  document from a scheme handler,** as it does on a `loadSimulatedRequest`
  document now?
- **Q5: do `http:` sub-resources on loopback still load from the page**
  (#135's case: a page that talks to a local server)?

## 5. Alternatives

- **A loopback HTTP server in the process.** Real `http://127.0.0.1` gives a
  secure context with no questions, but its port changes each launch unless
  fixed, and the port is the origin: the guest's storage would not survive a
  relaunch, and a fixed port collides with other apps. Other local processes
  could also read the app's assets. It is the fallback if Q1 fails.
- **`loadFileURL(_:allowingReadAccessTo:)`.** A `file:` page has an opaque
  origin in WebKit: module scripts and `fetch` of its own files are refused,
  and its storage is not kept. Rejected.
- **A single-file build.** The author's workaround today (the pitfall says
  so). It cannot carry lazy chunks, workers or wasm. Not a fix.

## 6. Verification

- The deck fixture's local page gains a script, a stylesheet, a font and a
  dynamic `import()` beside it (extending the existing smoke's guest, not a
  new fixture). `smoke.mjs macos` and `smoke.mjs ios` check the guest's
  outline and pixels show what each file contributes.
- Exact Draw's editor, moved into its `assets/`, loads and draws on macOS and
  the iOS simulator with its loopback editor server stopped.
- An asset update delivered by `scripts/deploy.mjs` changes a sub-resource's
  bytes in a running macOS client after relaunch (D3).

## 7. What this does not do

It does not give a guest the app's files, storage or grants: a page reaches
`app:/` data only through `message` and the app. It adds no `srcdoc`
attribute (LLP 1020 §5). It does nothing for Linux, which has no `iframe`
(LLP 1020 D5).
