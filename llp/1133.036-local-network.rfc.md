## Summary

`@exact/local-network` finds services on the local network by DNS-SD
(RFC 6763 over Multicast DNS, RFC 6762), the mechanism every platform
ships: Bonjour on Apple, Network Service Discovery on Android, the DNS
client's DNS-SD on Windows, Avahi on Linux. A printer, a NAS, a light, a
media server or another copy of the app advertises a named instance of a
service type (`Desk._wled._tcp.local.`); an app that knows the type lists
the instances, resolves the one the person picks to a host and a port,
and talks to it.

The web has no such API. The W3C's Network Service Discovery was
discontinued in 2017, and its Note says it "should not be referenced or
used as a basis for implementation" ([W3C](https://www.w3.org/TR/discovery-api/)).
So tier 1 is a declared deviation in DNS-SD's own words, which all four
native platforms use:

```
use browseServices, localNetworkStatus, LocalServices, LocalNetworkStatus from "@exact/local-network"

resource network = localNetworkStatus() as shape LocalNetworkStatus
resource found = browseServices(type="_wled._tcp") as shape LocalServices
```

```ts
import { resolveService } from "@exact/local-network";

const light = await resolveService({ name, type: "_wled._tcp" });
return fetch(`http://${light.host}:${light.port}/json/state`);
```

Three decisions carry the module:

1. **Finding is the module's; reaching is `fetch`'s.** The module lists
   and resolves; the app connects with the transports it already has
   (`fetch`, the WebSocket), under a new grant source, `local-network`,
   that admits any URL whose host is a local-network address or a
   `.local` name, decided from the URL alone as every grant is (D5).
   Resolving answers `host`, the string the platform would connect to: a
   name on Apple, which asks apps to connect by name, an address where the
   platform hands one (D4).
2. **The Local Network permission is the network's, not the module's.** On
   iOS and macOS 15 the first connection to a device on the local network
   shows the prompt as surely as a browse does (TN3179), and Chrome asks
   before a public page's first local request. So each host keeps one
   **local-network fact**, which this module answers, and every fetch hop
   and WebSocket open is checked for **prompt risk**, a run-time test of
   its destination apart from the static grant: one asked by a tool
   invocation, a wake or a package's event, whose destination could
   prompt, is refused `person-required` while the permission that
   governs it is undecided and refused unsent while it is denied (D6).
   That closes a hole every app with a LAN origin has today, module or
   not, wherever exact2 sees the destination; on the web the browser
   alone sees a name's address (§11).
3. **Apple will not say.** "There's no general API that returns whether
   the current process has local network access" (TN3179). The state reads
   `unknown` at launch until evidence this launch settles it: a browse, a
   resolve, or a UDP probe that sends nothing, opened only after a reach
   that could have shown the alert (D8). Android, from API 37, has a
   runtime permission, `ACCESS_LOCAL_NETWORK`, with a dialog; the host
   targets API 36 today, under which Android grants it implicitly (D8,
   D9).

**Consumer.** No app in or beside the repository browses the network. This
RFC proposes **Lights** (`apps/lights`), a controller for WLED lights:
WLED is open-source LED firmware that advertises `_wled._tcp` with its
MAC address in TXT and serves an unauthenticated JSON API, and its own
iOS and Android apps find lights exactly this way, so a hand-built
reference exists for the tell and ceiling tests (§10).

**Targets.** iOS, macOS and tvOS (NWBrowser and dnssd), Android
(`NsdManager`), Windows (`DnsServiceBrowse`) and Linux (Avahi), the last
two over the desktop builder LLP 1133.022 proposes; the web reads
`available: false` and reaches a typed address with `fetch` (D18).
Advertising, the other half of DNS-SD, needs a listener on the LAN, which
LLP 1133.005 left here: it is written down and not built (D14).

## 0. What is new here

1. **A grant decided by address space** (D5). Every network grant names
   origins or schemes. `local-network` names the local network, as the
   web's Local Network Access does with `targetAddressSpace: "local"`, and
   as Apple's and Android's permissions do. It is static: the URL's host
   decides, never where a name resolves.
2. **A permission that a data capability can trigger** (D6). Until now a
   request (LLP 1069.007 D1) was a module call. On Apple and the web a
   plain `fetch` to a device on the LAN is one too, so every fetch hop
   gains the origin rule LLP 1133.002 D12 gave module calls, for
   destinations that can prompt.
3. **A state the platform will not report** (D8), read from evidence and
   a probe.
4. **A drive that never touches the LAN.** On this Mac a LocalOnly
   registration (`dns-sd -lo -R`, `kDNSServiceInterfaceIndexLocalOnly`)
   is seen by an ordinary browse and resolves to `localhost.`, and nothing
   goes on the wire (measured 2026-10-26, §14).

## 2. Tier 1

### D1 — DNS-SD's words, a declared deviation

| Name | Kind | Apple | Android | Windows | Linux | Contract | Data code |
|---|---|---|---|---|---|---|---|
| `localNetworkStatus()` | live source; a fact; `sync` on Apple | the host's fact (D6, D8) | the same | the same | the same | yes | yes |
| `browseServices(type=)` | live source; a request; `"origin": "app"` | `NWBrowser`, `.bonjour(type:domain:)` | `NsdManager.discoverServices` | `DnsServiceBrowse` | `ServiceBrowserNew` (`Server2`'s `…Prepare` and `Start`) | yes | yes |
| `resolveService(name=, type=, timeout=)` | live source; a request; `"origin": "app"` | `DNSServiceResolve` (dnssd) | `registerServiceInfoCallback` from API 34, `resolveService` below it | `DnsServiceResolve` | `ServiceResolverNew` | yes | yes |

**The deviation.** No web name exists to follow. The W3C's discontinued
`navigator.getNetworkServices(type)` bundled UPnP with DNS-SD and handed a
page a `url` per service; its Note gives no names worth keeping. The four
platforms agree on DNS-SD's own verbs: Apple *browses* and *resolves*
(`NWBrowser`, `DNSServiceResolve`), Android *discovers* and *resolves*,
Windows calls `DnsServiceBrowse` and `DnsServiceResolve`, Avahi has a
`ServiceBrowser` and a `ServiceResolver`. The names take those verbs in
the web's style: a lower camel case function, keyword options, a
`DOMException` for each failure.

**Options.**

- `type`: a service type, `_<name>._tcp` or `_<name>._udp`, the name 1 to
  15 characters by RFC 6335 §5.1 (letters, digits and hyphens, at least
  one letter, no leading, trailing or doubled hyphen; RFC 6763 §7). It
  must be a type the app's grants list (`net.dns-sd`, D7): iOS refuses a
  browse for a type its `NSBonjourServices` does not list, and browsing
  an arbitrary type needs a managed entitlement Apple grants on request
  ([multicast entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.multicast)).
- The domain is always `local.`: Android's NSD browses only Multicast
  DNS, and no consumer asks for wide-area DNS-SD (§13).
- `name` (resolve): an instance name as `browseServices` answered it.
- `timeout` (resolve): milliseconds to the first answer, default 5,000,
  on the session clock; at most 60,000.

**Errors.** `TypeError` for a malformed `type`; `SecurityError` for a type
no `net.dns-sd` line lists (a literal fails the bake first, D7);
`NotSupportedError` where the target has no implementation (D18);
`NotAllowedError` when the person or the platform refused local network
access, and `NotAllowedError` with `message` `person-required` for an
origin D10 refuses; `NotFoundError` when a resolve finds nothing within
`timeout` or its instance leaves the network; `NetworkError` when the
platform's browser fails (Apple's `.failed`, Android's
`onStartDiscoveryFailed`, Avahi's `Failure` signal, Windows' completion
status).

### D2 — Values, identity and change

**Values.**

- `LocalServices`: `{services: LocalService[]}`.
- `LocalService`: `{name, type}`: the instance name, unescaped UTF-8 of
  up to 63 bytes (RFC 6763 §7.2), and its type.
- `LocalServiceInfo` (resolve): `{name, type, host, hostName, port,
  addresses, txt}`. `host` is what the app puts in a URL (D4); `hostName`
  the target host the SRV record names (`wled-a1b2c3.local.`), where the
  platform reports one; `addresses` the IPv4 and IPv6 addresses the
  platform resolved, excluding IPv6 link-local addresses, which no URL can
  carry because the WHATWG URL has no zone identifier; `txt` the TXT
  record as `TxtEntry[]`.
- `TxtEntry`: `{key, value}`. Keys are lower-cased, since RFC 6763 §6.4
  ignores their case; `value` is `none` for a key with no `=`, and
  otherwise the bytes decoded as UTF-8 with U+FFFD for invalid sequences,
  as `TextDecoder` does. TXT values may be binary (§6.5); a module word
  for raw bytes waits for a consumer.
- `LocalNetworkStatus`: `{available, state, android}` (D8).

**One instance, one row.** An instance is identified by its name and type.
The platforms report it once per interface and address family (NWBrowser's
`interfaceAdded` change flags, Avahi's per-interface `ItemNew`, a result
per network on Android); the module merges those, and an instance is
listed while any interface reports it. The list is ordered by name,
case-insensitively, as a hand-built list of devices is.

This is the platforms' own identity: NWBrowser keys a result by its
endpoint (name, type and domain) and reports its interfaces as a set, and
a connection to that endpoint takes whichever interface answers. RFC 6762
§14 lets two links each hold a different `Desk._wled._tcp.local.`, so a
device on two networks at once can merge two instances into one row, and
a resolve answers the first the platform delivers. That is a declared
limit, the same in the hand-built reference apps (§10); an app that must
tell devices apart checks an identity the device itself states, as
Lights does with WLED's `mac`.

**Change.** A browse answers once the platform has delivered its first
batch (NWBrowser's first results handler call, Avahi's `AllForNow`) or one
second after it started, whichever comes first, so a network with twenty
services settles in one commit rather than twenty; after that each change
is announced as it comes. An instance leaves when the platform says so:
an mDNS goodbye (RFC 6762 §10.1), or its record's expiry when the device
left without one. The list says what the platform says, and the recipe
tells apps that a light switched off at the wall can stay listed until
the cache drops it.

A resolve answers when the platform has the SRV and TXT records and at
least one address, and again whenever any of them changes (a TXT update,
a new address after a DHCP renewal), which is why Android deprecated its
one-shot `resolveService` for a callback: "the returned ServiceInfo may
get stale at any time after resolution"
([`NsdManager`](https://developer.android.com/reference/android/net/nsd/NsdManager)).
A data resource that read it is asked again with the new address, by LLP
1133 D6 rule 2.

### D3 — Readers and lifetimes

- **One platform browse per process and argument group.** Readers of
  `browseServices` with the same arguments, in any session, share one
  `NWBrowser`, one NSD discovery, one Avahi browser. It starts with the
  first reader and stops when the runner reports the group has none left
  (`release(name, args)`, LLP 1133.009 D10 item 12), or at the last
  session's `destroy`. A resolve likewise, per `(name, type)`. Browsing is
  the costliest thing DNS-SD does to a network, and Android's guide asks
  apps to stop it as soon as they no longer need it
  ([NSD](https://developer.android.com/develop/connectivity/wifi/use-nsd)).
- **The foreground.** A browse or a resolve pauses while the app is in the
  background and resumes on return, as each platform's own guidance has
  it: iOS suspends the app, and from Android's T extensions 7 the system
  manages multicast reception only "for apps in the foreground"
  ([`NsdManager`](https://developer.android.com/reference/android/net/nsd/NsdManager)).
  On return the browse answers afresh.
- **Joins.** A reader whose origin may not start a browse (D10) joins one
  already running for the same group and never holds it: when the last
  reader that may start it goes, it stops, and the joiner's read fails
  `NotAllowedError` (`person-required`). LLP 1133.013 D4's rule, "a join
  changes nothing".

### D4 — Unsaid defaults are the platform's

- **Browse, then resolve only what the app uses.** Browsing answers names.
  Resolving every result is "a major Bonjour faux pas" in Apple's words
  ([Apple Developer Forums](https://developer.apple.com/forums/thread/122638));
  an app resolves the instance it is about to use, or the few it shows
  state for.
- **Connect the way the platform connects.** On Apple `host` is the
  `hostName`: Apple calls resolving to an address and connecting to it
  "an anti-pattern" (TN3151) and asks apps to pass the DNS name on, so
  `URLSession` resolves it through mDNSResponder with Happy Eyeballs. On
  Android, Windows and Linux `host` is an address the platform resolved,
  IPv4 first, an IPv6 address in brackets otherwise: Android's NSD hands
  addresses (`getHostAddresses()`, API 34) and only a DNS resolver module
  from November 2021 on resolves `.local` names
  ([AOSP](https://source.android.com/docs/core/ota/modular-system/dns-resolver));
  Avahi's resolver answers an address, and a Linux machine resolves
  `.local` only with nss-mdns installed; Windows' `DNS_SERVICE_INSTANCE`
  carries `ip4Address` and `ip6Address`. The address chosen is one D5
  admits; where the platform resolved none (a device with only a global
  IPv6 address, or only an IPv6 link-local one), `host` is the
  `hostName`, a `.local` name D5 admits. That name is usable only where
  the platform resolves `.local` names: on Linux without nss-mdns, and on
  Android before `NsdServiceInfo.getHostname()` (API 36) reports one, such
  a device is out of this line's reach, a declared limit; an app reaches
  it with a grant that names it. Home networks give a device an RFC 1918
  or a unique-local address in nearly every case.
- **The prompt's words** are the `device.local-network` purpose on Apple.
  Android's dialog shows none (D11).
- **No browse at launch by the module.** A browse starts when something
  reads it; whether the app reads it at launch is the app's choice (LLP
  1133 §0, ruling 9).

## 3. Reaching what was found

### D5 — `local-network`: a grant source for the local network

`net.fetch local-network` admits an `http:` or `https:` URL, at any port,
whose host is:

- an IP literal in the private-network ranges the development-build rule
  already names (`privateNetwork` in `js/bake/src/typescript.mjs`): RFC
  1918 IPv4, link-local IPv4 (169.254.0.0/16), unique-local IPv6
  (fc00::/7) and link-local IPv6 (fe80::/10), an IPv4-mapped IPv6 address
  judged by the IPv4 address it carries; or
- a name ending in `.local`, which RFC 6762 §3 makes link-local: "any DNS
  query for a name ending with '.local.' MUST be sent to the mDNS IPv4
  link-local multicast address".

`net.websocket local-network` admits `ws:` and `wss:` URLs by the same
rule.

**Static, as every grant is.** The URL's host decides, never where a name
resolves: a `GrantSet` is "never derived from a frame, a `Domain`, or a
job queue" (`grants/src/lib.rs`). So a unicast DNS name that resolves to a
LAN address (`nas.home.arpa`) needs a line of its own, and a network that
serves `.local` by unicast DNS, which RFC 6762 Appendix G records some
enterprises do, can resolve a `.local` name elsewhere; both are the
module's declared limits. This test decides admission only. Whether a
reach can show a prompt is a different, run-time test (D6).

**In a development build** (`EXACT_UPDATE_TRUST` unset or `development`,
the test commit `7a31327086` uses), `local-network` also admits loopback:
127.0.0.0/8, `[::1]` and `localhost`. A drive's fixture on this machine
then stands in for a device on the LAN, and a LocalOnly registration,
which resolves to `localhost.`, can be reached (§14). A production build
admits no loopback literal and not `localhost` by this line: loopback is
the most private address space Local Network Access defines, and an app
that serves itself on loopback names that origin. A `.local` name that an
mDNS responder points at 127.0.0.1 is still admitted, since the URL
decides.

**Never in a render.** The render server (LLP 1114.009) drops the line
from a render's grants, as it drops `https://*` there (its D5): a render
runs per request on the operator's server, a route parameter can choose
what it fetches, and with this line a visitor could point that server at
the operator's own network. `Anonymous::new` (`host/render/src/source.rs`)
keeps today every `net.fetch` line whose target does not end in `:`, so
it gains a test that refuses `local-network`. A render leaves such a read
to the client, which makes it after adoption.

**What it derives and requires.** It requires `device.local-network` (the
bake refuses it without, `grant-missing`), because on Apple a reach under
it can show the prompt. On iOS and macOS it derives
`NSAllowsLocalNetworking`, which lets `URLSession` load `http:` from local
hosts ([NSAllowsLocalNetworking](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking));
today only the development client's `host.ios.localNetworking` adds it.
The reach table (LLP 1069.008 D7) lists it as "the local network".

**On the web** the browser's validator applies the same static rule. The
JS runtime passes `targetAddressSpace: "local"` on every fetch whose URL
host is in Local Network Access's local space as written (an address
literal by LNA's table, which adds 100.64.0.0/10 to D5's ranges and
judges an IPv4-mapped address by its IPv4 address, or a `.local` name),
whichever line admitted it, so Chrome checks that the resolved address is local, asks its Local
Network Access permission, and exempts the request from mixed-content
blocking ([LNA](https://wicg.github.io/local-network-access/), "Local
Network Access check"; the prompt from Chrome 142,
[Chrome](https://developer.chrome.com/blog/local-network-access)). It
passes none for a loopback URL: LNA's `Request` constructor defines the
option only for `local`, and a development page on loopback fetching a
loopback fixture is no local network request. Safari and Firefox block an
`http:` request from an `https:` page as mixed content, which is the
web's answer, and the app reports it as it reports any failed fetch.
Chrome gates WebSockets to local addresses on the same permission from
Chrome 147 ([Chrome 147](https://developer.chrome.com/release-notes/147)).

A page the render server serves (LLP 1114) carries a
Content-Security-Policy that names the origins the grants name (`csp` in
`host/render/src/serve.rs`); there it is the boundary, since the web
runtime's admission is parity, not a sandbox (`host/web/navigation.js`).
The line adds `http://*.local:*` and `https://*.local:*` (the `ws` pair
for `net.websocket`). CSP has no source for an address range, and a
scheme source would admit the internet, so a served page reaches a
private address literal only with a grant that names it or a scheme-wide
line; a `.local` name works (§15 question 10). A static web build, which
carries no CSP, has no such limit.

*Rejected:* admitting only the endpoints this session resolved. Admission
would then depend on run-time state, which no grant does; it would refuse
the typed address every discovery screen needs, because "mDNS fails on
guest and corporate networks constantly" (LLP 1023 D7); and the platforms'
own consent is the whole local network, not an endpoint (Android's picker
is the exception, D12). *Rejected:* `net.fetch http:` for these apps. It
admits every host on the internet too, and the reach table cannot say
which the app meant.

### D6 — The host's local-network fact, and every reach that can prompt

On iOS 14 and later and macOS 15 and later, "a local network is an IP
network associated with a broadcast-capable network interface. Such
interfaces include Wi-Fi and Ethernet, but not cellular (WWAN) or VPN";
multicast and broadcast addresses are local too, and "outgoing traffic to
a local network address requires local network access", a check made
"deep in the networking stack" that applies to every API, with a DNS
server or a proxy on the local network exempt. Resolving a `.local` name
and every Bonjour operation need it too, and the first such operation
while the privilege is undetermined shows the alert (TN3179). So a
`fetch` to a device on the person's Wi-Fi is as much a request (LLP
1069.007 D1) as a browse, and LLP 1133 D6 rule 3 forbids a tool
invocation, a wake, or a package's own event (which runs with the
device's origin, `runner/src/runner/modules/events.rs`) to open it.
Chrome asks before a public page's request to a local or loopback
address, and on Android at API 37 the host asks before a local reach
(D9).

**Three tests, kept apart.**

1. **Admission** is D5's static test of the URL, at the grant check.
2. **Prompt risk:** whether this destination, on this target, falls
   under a permission that asks: one whose undecided state shows a prompt
   at the reach. It is a run-time test of the destination, made where the
   connection is opened:
   - **iOS 14+, macOS 15+:** a `.local` name; an address on the subnet of
     a broadcast-capable interface the device is on (`getifaddrs`, by
     interface type, as TN3179 advises), or a link-local, multicast or
     broadcast address; a unicast name the host first resolves to such an
     address, by DNS, which needs no access. An IPv4-mapped address is
     replaced by the IPv4 address it carries before any of these tests.
     Loopback, a private address reached through a router, and a VPN's
     addresses have no risk, nor, on macOS,
     a network an administrator listed in the
     `AllowedEthernetLocalNetworkAddresses` or
     `AllowedWiFiLocalNetworkAddresses` defaults, which "every program can
     access … regardless of its Local Network privilege state" (TN3179,
     macOS 15.5 and later).
   - **Android, the host targeting API 37:** D5's static local test,
     since the host's ask comes before the reach (D9), except an address
     the person chose in the system's picker while Android's per-device
     grant for it holds (D12).
   - **The web:** the destination's address space, as the URL writes it
     (LNA's table for a literal, local for a `.local` name), is less
     public than the page's own (public to local or loopback, local to
     loopback), which is LNA's definition of a local network request, and
     the browser does not answer that space's permission `granted` (D8).
     Chromium asks from 142 and Firefox from 153 ("Firefox requires
     websites to request permission before connecting to devices on your
     local network", [Firefox 153](https://www.firefox.com/en-US/firefox/153.0/releasenotes/)).
     In a browser that answers neither permission name (D8) the state is
     `unknown`, and a tool's reach to a local or loopback literal from a
     more public page is still refused, since such a browser may still
     ask. No grant there can lift it, so the cost is permanent in that
     browser: a tool cannot reach `https://192.168.1.40/`, a loopback
     literal (`http://127.0.0.1` is potentially trustworthy, so mixed
     content does not block it), a LAN literal from an `http:` page, or a
     `wss:` literal. A person's own reach is unaffected (§15 question 3).
     A name the browser resolves into a local space is seen only by the
     browser: §11's amendment.
   - **Elsewhere none:** tvOS and macOS 14 have no local network privacy,
     Windows and Linux none, and Android at API 36 grants it
     implicitly.
3. **Evidence** of the person's decision is the host's fact (D8).

**The rule.** A fetch hop, the first or one a redirect leads to, or a
WebSocket open, asked by an answer whose origin is a tool invocation, a
wake or the device, and whose destination has prompt risk, is checked
before it connects against the permission that governs it: the host's
fact, or on the web the permission of the destination's space
(`local-network` or `loopback-network`, D8). `granted` proceeds;
`unknown` or `prompt` is refused `NotAllowedError` with
`person-required`; `denied` is refused `NotAllowedError`, as LLP
1133.002 D12 fails a denied call, and is not sent. The check sits beside
the grant check every hop already passes: ibex2's `admit_hop` before
each `transport.open`, and its WebSocket open (`vendor/ibex/crates/ibex2/src/stdlib/fetch.rs`,
`task.rs`). The data runtime's host call carries the requesting answer's
origin, which LLP 1133.002 D12 traces by causation; the least privileged
origin in flight is for the calls D12 cannot trace. A person's input and
the app's own foreground code proceed: their reach is the ask (D9).

**One fact per process, the host's.** Each host keeps the state D8 maps
and its evidence. This module reports its browses' and resolves'
outcomes through its package context, and on Apple the host keeps D8's
probe. `localNetworkStatus()` answers the fact. It is not the module's
own state, so an app that never imports the module still has it, and the
rule holds for every app (§12).

**What the web cannot see, and the amendment it needs.** The browser
resolves names and follows redirects inside `fetch`; the web runtime
checks the first URL before and `response.url` after
(`host/web-js/admission.js`), and neither can stop a prompt the browser
shows in between.

- **Redirects:** the redirect gate. A tool-, wake- or device-origin
  `fetch` that would follow redirects goes out with `redirect: "error"`
  while the permission of some space less public than the page's own
  (from a public page `local-network` or `loopback-network`, from a local
  page `loopback-network`) is answered by the browser and not `granted`,
  so the browser never requests the next hop
  ([Fetch](https://fetch.spec.whatwg.org/#http-redirect-fetch)). Both web
  fetch paths apply it (`host/web-js/admission.js`,
  `host/web/http-body.js`), and the latter's early send, `fetchEarly`,
  sends no tool-, wake- or device-origin request (D16 item 2); a caller's
  own `manual` is left alone. The cost: such a fetch that meets a redirect fails as a network failure
  (`failure(x).code` `offline`), and a cross-origin `no-cors` one fails
  before it is sent, since Fetch requires `follow` there. Granting those
  permissions restores both. A WebSocket handshake never follows a
  redirect ([WebSockets](https://websockets.spec.whatwg.org/#opening-handshake)),
  so it needs nothing here. In a browser that answers neither name the
  gate does not apply: a prompt such a browser shows for a redirect it
  follows is the browser's, under the amendment below.
- **Names:** a tool's `fetch` of a public name that resolves into the
  local network (`https://nas.home.arpa`) can show the browser's prompt.
  Refusing every tool-origin fetch to a name while `local-network` is
  `prompt` would close it, but that state is where every web app that
  never reaches the LAN stays, so it would refuse every tool's fetch on
  the web. The prompt is a site permission in the tab the person has
  open, anchored there by the browser. So §11 amends LLP 1133 D6 rule 3
  for the web: a tool invocation never opens a prompt by any call exact2
  can classify; a browser's own prompt for an address only it resolves
  is the browser's (§15 question 3).

**Declared limit on Apple.** A unicast name is resolved by the host for
the check and again by `URLSession` when it connects; an answer that
changes in between escapes the check.

## 4. Permission

LLP 1133.002 §4 (D6–D12), with the one change D6 makes: the permission
covers a data capability's reach as well as the module's calls.

### D7 — Declare: three kinds of line

- **`device.local-network <purposeKey>`**, as built, gaining an Android
  column: `<uses-permission android:name="android.permission.ACCESS_LOCAL_NETWORK"/>`,
  declared and asked only once the host targets API 37. Android says
  "Don't request ACCESS_LOCAL_NETWORK at runtime prior to targeting SDK

  and an app below that has the network implicitly.
- **`net.dns-sd <type>`**, new, one per service type the app browses or
  resolves. It is exact2's own line (`own` in `runner/src/grants.rs`
  strips it before `ibex2` parses the rest) and requires
  `device.local-network`. A literal `type=` in Contract or data code that
  no line lists fails the bake (`grant-missing`); a computed one fails
  `SecurityError` at admission.
- **`net.fetch local-network`**, **`net.websocket local-network`** (D5).

| macOS | the same three | yes (macOS 15 and later) |
| tvOS | `NSBonjourServices`; tvOS is not among the platforms TN3179 lists as having local network privacy | no prompt |
| Android | `ACCESS_LOCAL_NETWORK` once the host targets API 37; with a `net.dns-sd` line, `CHANGE_WIFI_MULTICAST_STATE`, the normal permission `WifiManager.MulticastLock` needs where the system does not manage the lock (D18) | no |

### D8 — Read: `localNetworkStatus()`

- **`available`:** the target has an implementation and a browser: false
  on the web, the terminal, Linux while no `org.freedesktop.Avahi` name is
  on the system bus, and Linux and Windows until the desktop builder lands.
- **`state`**, meaning on every target what LLP 1133.002 D8 says, with
  `unknown` meaning "a reach may ask":

| Platform | `state` |
|---|---|
| iOS 14+, macOS 15+ | `unknown` at launch, then the latest evidence this launch. `granted`: a browse delivered a result, a resolve answered, or the probe is ready. `denied`: a browse or resolve waits with `kDNSServiceErr_PolicyDenied` (−65570), or the probe waits with `localNetworkDenied` (TN3179) |
| the iOS Simulator | `granted`: "The simulator doesn't support local network privacy" (TN3179) |
| macOS 14, tvOS | `granted` |
| Android, the host targeting API 36 or lower | `granted`: apps below 37 holding `INTERNET` have an implicit grant ([Android](https://developer.android.com/privacy-and-security/local-network-permission)) |
| Android, the host targeting API 37 | `ACCESS_LOCAL_NETWORK`'s state, with LLP 1133.002 D8's history in the host's one permission store (LLP 1133.008 D8 item 7), and `android.shouldShowRationale` and `android.permanentlyDenied` |
| web | `permissions.query({name: "local-network"})`, LNA's permission for local addresses, else `local-network-access`, the single permission Chrome asked before 145 split it into `local-network` and `loopback-network` and kept as an alias ([Chrome 145](https://developer.chrome.com/blog/chrome-145-beta)). A browser that answers neither name reads `unknown`: D6 still refuses a tool's reach to a local or loopback literal there, and applies no redirect gate. `loopback-network`, read the same way, governs a loopback destination in D6 and is not the fact |
| Windows, Linux | `granted` |

**Why evidence, and why per launch.** "There's no general API that
returns whether the current process has local network access" (TN3179). A
guess of `prompt` on a first launch would be wrong for a person who
allowed it and reinstalled; evidence kept across launches would go stale
when the person changes it in Settings while the app is closed. Each
launch starts at `unknown`. A `fetch` that succeeds is no evidence:
TN3179 exempts a DNS server or a proxy on the local network, `URLSession`
follows the system's proxy settings, and a private address through a
router or a VPN needs no access, so only Bonjour and the probe, which
can exercise nothing but the privilege, settle the fact.

**The probe.** After the first foreground reach this launch whose own
connection went directly to a local address with prompt risk (D6), so
that the reach itself showed any alert that was due, the host opens a
UDP `NWConnection` that sends nothing, to an address with prompt risk on
that reach's interface that is neither the configured DNS server nor a
proxy, and on no network macOS exempts. It requires that interface
(`NWParameters.requiredInterface`) and prohibits proxies, so a VPN that
captures the local network cannot carry it: its path ready on that
interface is `granted`, waiting with `localNetworkDenied` is `denied`,
and any other unsatisfied path is no evidence; stage 1 checks on a
device that its path is direct and records any relay a profile
configures. TN3179's own way to reach the privilege is to "connect a UDP socket to a local network address.
This triggers the local network alert without generating any network
traffic", and "if the user subsequently changes the Local Network
privilege to grant your program local network access, the system
automatically retries the connection". The host keeps it open while the
app is in the foreground, so the fact follows Settings. It opens only
after a foreground reach by the person or the app's own code on that
interface that could itself show the alert, so it shows no alert that
reach would not have shown, and never for a tool, a wake or a package's
event. With no broadcast-capable network up there is nothing to probe,
and the fact stays where evidence left it. TN3179 states the retry after
a grant and the close after a denial for a TCP connection; stage 1
confirms both transitions for the UDP probe on a device.

**What counts as direct.** The path the reach's connection took, not
the URL's host: TN3179 exempts the connection to a proxy, `URLSession`
follows the system's proxy settings, and a VPN can route a local address
into its tunnel, which TN3179 does not count as a local network. For
`URLSession`, a transaction's `URLSessionTaskTransactionMetrics` shows
`isProxyConnection` false, a `remoteAddress` with prompt risk, and a
`localAddress` on the broadcast-capable interface whose subnet holds
that remote address; for an `NWConnection`, its path reached ready with
no proxy on that interface. A foreground browse or resolve counts on
each broadcast-capable interface it ran on, since Bonjour's own traffic
shows the alert (D9), so a browse that finds nothing still opens the
probe, which settles the fact. A reach through a proxy or a VPN, one to the configured DNS
server, and one whose connection never opened open no probe. Stage 1
shows on a device that a direct local `fetch` opens it and that a local
`fetch` a VPN captures (`includeAllNetworks` set, `excludeLocalNetworks`
not) opens none. D6's test for a tool's hop stays the address test,
which counts the DNS server, proxies and any address it cannot see is
routed elsewhere as prompt risk: over-counting there costs a refusal,
never a prompt.

**A reach that fails while the alert is up.** TN3179 warns that the
system "may deny the operation immediately, before the user has
responded to the alert". Such a `fetch` opens no connection, so it
opens no probe: nothing tells it apart from a failure whose path was
never established, and probing after every failed local URL would show
the alert for a reach a proxy carried. The person's answer is seen by
the next reach that opens a direct connection. TN3179 advises retrying,
so the recipe gives a local `fetch` that fails while the fact is
`unknown` a retry the person can take, and a resource that reads
`localNetworkStatus()` beside its `fetch` is asked again once that reach
changes the fact (LLP 1133 D6 rule 2). A denial in an app that only
fetches is seen by no reach, since a denied reach opens no connection:
the fact stays `unknown` for the launch, and a tool's local hop fails
`person-required` rather than `NotAllowedError`, sending nothing either
way. A browse settles it (`PolicyDenied`). An app's own UI treats
`unknown` as it treats `prompt`: the recipe says explain, then reach.

### D9 — Ask: the reach asks

- **Apple** has no call that asks ("There's no API to explicitly bring up
  the local network alert", TN3179). The first browse, resolve or local
  connection while undetermined shows the alert with the purpose. The
  browse answers at once with an empty list and fills when the person
  allows; a denial fails its readers `NotAllowedError`. A local operation
  from an iOS app in the background while undetermined is denied "without
  presenting the local network alert", and the system does not record
  that decision (TN3179); D10 refuses the origins that would make one.
- **Android, the host targeting API 37:** a foreground reach while
  `prompt` (a browse, a resolve, or a `fetch` or WebSocket to a local
  host other than one the person chose in the picker, D12) first asks
  `ACCESS_LOCAL_NETWORK` through `Activity.requestPermissions`, in LLP
  1133.002 D9's queue of decisions, and then proceeds or fails. So an app whose only reach is a typed
  address asks the same way an app that browses does, and on Apple and
  Android alike the reach is the ask. Under API 36 nothing asks.
- **The web:** a browse is absent; a local `fetch` from a public page
  shows the browser's prompt (Chromium from 142, Firefox from 153).
- **Windows, Linux:** nothing asks. A LAN *listener* would meet Windows
  Firewall's dialog; that is D14's.

### D10 — Who may

`browseServices` and `resolveService` are `"origin": "app"` (LLP 1133.009
D10 item 8): a tool invocation, a wake or a package's event never starts
one, in any state, as they start no device. They may join one already
running (D3). A reach by `fetch` or WebSocket follows D6.

| Origin | `granted` | `unknown`, `prompt` | `denied` |
|---|---|---|---|
| a person's input; the app's own code, foreground | proceeds | proceeds; the reach asks (D9) | a browse or resolve fails `NotAllowedError` and is asked again when the fact changes; a `fetch` goes to the platform, which refuses it |
| a tool invocation; a wake or a headless session; a package's own event (the device's origin) | joins a running browse or resolve; a `fetch` proceeds where the platform runs it | joins; a `fetch` with prompt risk fails `person-required`, one without proceeds (D6) | joins fail `NotAllowedError`; a `fetch` with prompt risk fails `NotAllowedError` unsent, one without proceeds (D6) |
| the development agent | §9 | §9 | §9 |

A person's own `fetch` is never refused up front on a `denied` fact: the
platform refuses it, and the person may have allowed access in Settings
since the evidence was taken, which the reach's outcome or D8's probe
then reports.

### D11 — Explain and recover

The recipe (`docs/recipes/local-network.md`, stage 0):

- While `unknown` or `prompt`, say why beside the list or the button that
  starts it; on Android show the rationale first when
  `android.shouldShowRationale` is true.
- While `denied`, say so in the platform's words and offer
  `openURL("app-settings:")` (LLP 1133.002 D11). On Apple local network
  access is under Privacy & Security, Local Network.
- Read `localNetworkStatus()` in the resource that fetches from the
  device, so that the fetch is asked again when access changes (D8).
- When a local `fetch` fails while the fact is `unknown`, offer a retry:
  on Apple the system may refuse the first reach before the person
  answers the alert, and the next reach is what reports the answer (D8).
- **Always offer a typed address.** Guest and many corporate networks
  isolate clients or drop multicast (LLP 1023 D7), so a list that stays
  empty is not proof the device is absent. The typed address reaches the
  device under the same `local-network` line.
- An empty list is not a failure: say "No lights found on this network",
  never an error.

## 5. Tier 2, tier 3 and the ceiling

### D12 — The platforms' words

| Key | Word | On | Values | Source |
|---|---|---|---|---|
| `apple` | `includePeerToPeer` | `browseServices`, `resolveService` | `bool`, default false: also browse and resolve over Apple's peer-to-peer Wi-Fi, which "only works between Apple devices" (TN3151) | [`includePeerToPeer`](https://developer.apple.com/documentation/network/nwparameters/includepeertopeer); `kDNSServiceFlagsIncludeP2P` for the resolve |

`android.chooseService` is the privacy-preserving path Android 17 offers
an app that needs one device. It is `"origin": "app"` in every state,
as a browse is, and a person's foreground call is admitted while
`ACCESS_LOCAL_NETWORK` is `prompt` or `denied`, since it asks for that
device and not the permission. The host keeps each chosen service's
name and type, not its addresses, which Android says "can change over
time"; it learns the current addresses on the service's network from
`registerServiceInfoCallback`, which works for a chosen service without
the permission, and asks `checkPermissionForService(name, type)` whether
the choice still holds, since "access may be revoked for storage reasons
or by the user" ([`NsdManager`](https://developer.android.com/reference/android/net/nsd/NsdManager)).
A reach to a current address of a service that check answers
`SERVICE_PERMISSION_GRANTED` has no prompt risk and asks nothing (D6,
D9); a timeout, which is also what an unplugged device gives, changes
nothing. `DiscoveryRequest.FLAG_USER_APPROVED_ONLY` finds the chosen
services again without the picker. It is to the
local network what CompanionDeviceManager's chooser is to Bluetooth (LLP
1133.022 D14). It is designed here and built with the host's move to API
37 (§15 question 6): before that move the app has the
whole network implicitly, and the picker would add a dialog a hand-built
app at API 36 does not show. A `fetch` to the chosen device's address is
admitted by `local-network` like any other; under API 37 a reach to an
address the person did not choose, without the permission, times out as
Android documents.

**Peer-to-peer and Wi-Fi Aware.** The roster's row puts both in tier 2.
What each is, and what this RFC does with it:

- **Apple's peer-to-peer Wi-Fi** is a flag on the same browse,
  `apple.includePeerToPeer`, built here. It finds services that another
  Apple device advertises with the same flag, without a shared network.
  Multipeer Connectivity is not a word: Xcode 27 deprecates it in favour
  of Network framework (TN3213).
- **Wi-Fi Aware** is another discovery protocol (NAN publish and
  subscribe), not DNS-SD, and both platforms tie it to pairing and to a
  data path of their own. Apple's (iOS 26, iPhone 12 and later) pairs
  through DeviceDiscoveryUI or AccessorySetupKit and connects through
  Network framework, with the `com.apple.developer.wifi-aware`
  entitlement and `WiFiAwareServices` in Info.plist
  ([Wi-Fi Aware](https://developer.apple.com/documentation/wifiaware));
  Android's (API 26) needs `NEARBY_WIFI_DEVICES` and hands a network
  specifier ([Wi-Fi Aware](https://developer.android.com/develop/connectivity/wifi/wifi-aware)).
  exact2's URL transports cannot use either data path. Since iOS and
  Android both have it, it would be shared words when built, not tier 2,
  and whether the two interoperate is to be measured then. It stays out
  until a consumer asks (§13).
- **Android's Wi-Fi Direct service discovery** (`WifiP2pManager` with
  `WifiP2pDnsSdServiceRequest`) needs `NEARBY_WIFI_DEVICES` and a P2P
  group to connect ([Android](https://developer.android.com/develop/connectivity/wifi/nsd-wifi-direct));
  out likewise.
- **Apple's DeviceDiscoveryUI** pairs an app with its own copy on another
  Apple device (`NWBrowser.Descriptor.applicationService`, tvOS 16 and
  iOS 26), without local network access
  ([DeviceDiscoveryUI](https://developer.apple.com/documentation/devicediscoveryui));
  it finds no Bonjour service of another maker; out.

## 6. Advertising, written down

### D14 — An advertisement is its listener's

Advertising says "I am serving here", so it lives exactly as long as a
listener on the LAN, and LLP 1133.005 left both here ("Listening beyond
loopback … `local-network` … is where it would go", its §11). Written down
so that nobody invents another shape; not built until a consumer listens
on the LAN:

- **The shape.** An option of LLP 1133.005's listener on a LAN address:
  `exactListen("tcp://0.0.0.0:0", { advertise: { type, name, txt } })`.
  The advertisement is registered when the listener is bound and removed
  with it, so its lifetime is the resource's (1133.005 D2), and the
  `listening` event carries the registered name, which the platform may
  change on a conflict (RFC 6763 §9 and RFC 6762 §9; Apple's
  `serviceRegistrationUpdateHandler`, WinRT's `HasInstanceNameChanged`).
- **The calls.** The listener is the executor's socket, not an
  `NWListener`, so Apple registers its port with dnssd's
  `DNSServiceRegister`; Android `NsdManager.registerService`; Windows
  `DnsServiceRegister`, whose registration "is tied to the lifetime of the
  calling process"; Avahi an `EntryGroup`.
- **Permission.** The same `net.dns-sd <type>` line covers it. Registering
  needs local network access on Apple; accepting an incoming connection
  does not (TN3179). Android: "always requires the ACCESS_LOCAL_NETWORK
  permission" ([`NsdManager`](https://developer.android.com/reference/android/net/nsd/NsdManager)).
  Windows Firewall asks the first time an app listens, and gives a
  non-administrator block rules whatever they choose
  ([Microsoft](https://learn.microsoft.com/windows/security/operating-system-security/network-security/windows-firewall/rules)),
  which a LAN listener's RFC must answer before it is built.
- **Who may.** `"origin": "app"`, as a listener's resource is the app's.

### D16 — Seam additions

Each general, each proved by a fixture before Lights uses it:

1. **The host's local-network fact** (D6, D8): one per process on every
   host; read by D6's check; fed by packages through the context
   (`context.localNetwork.report(granted|denied)`), on Apple by D8's
   probe, and on Android at API 37 by the permission store; answered to
   the module's `localNetworkStatus`; set under the agent by `prefer
   permission.local-network` and `--permission local-network=…` (and on
   the web `loopback-network` likewise), as LLP 1133.002 §6's group sets
   geolocation's.
2. **Origin admission for reaches with prompt risk** (D6): the data
   runtime's host call for a fetch or a WebSocket carries the requesting
   answer's origin; each hop's grant check (`admit_hop`, the WebSocket
   open, in ibex2, and the web runtime's for the first URL, with D6's
   redirect gate in both web fetch paths) checks a tool-, wake- or
   device-origin hop whose destination has prompt risk against the
   permission that governs it, `person-required` while undecided and
   `NotAllowedError` unsent while denied; each host supplies the
   prompt-risk test of D6. On the web page-module path (games,
   `--wasm`, the resident development loop), `fetchEarly` in
   `host/web/module-glue.js` sends a GET while the answer is still
   running, before `request` in `host/web/http-body.js` checks it; it
   therefore sends early only a person- or app-origin request, and a
   tool-, wake- or device-origin GET waits for `request`'s checks, so
   neither its first URL nor a redirect is sent before admission. With
   the host's move to API 37, the Android host queues
   `ACCESS_LOCAL_NETWORK`'s decision before a foreground local reach
   while `prompt` (D9).
3. **The grants:** `net.dns-sd` as an own line; the `local-network`
   source for `net.fetch` and `net.websocket` in `grants/src/lib.rs`, its
   `ibex2` mirror, `host/web/navigation.js` and the shared corpus, with the
   development-build loopback rule; the render server's refusal of the
   line and the served page's CSP (D5); the bake's derivations (D7); the
   web runtime's `targetAddressSpace: "local"` for every fetch to a host
   in LNA's local space as written.
4. **An option checked against grant lines:** `"granted": "net.dns-sd"`
   on an option makes a literal argument a bake check and a computed one
   an admission check, as a `path` option is checked against `fs.read`.
5. **Joins** (`"join": true`): a reader whose origin the name refuses
   joins a running argument group instead of failing, and fails when the
   last reader that may hold it goes (D3, D10).
6. **The keyed fixture** of LLP 1133.022 D19 item 2, built by whichever
   module lands first (§9).

LLP 1133.022 D10 item 5 (a Rust host's package implementation and the
desktop loops' dispatch) is that RFC's; the Linux and Windows cells wait
for it. Each addition is apparatus under `rules/RULES.md` and lands with
this ruling.

### D17 — Callers

## 9. The substitute

### D19 — Declared, and the network never touched

Under the agent no implementation is bound, so nothing browses the
network a drive runs on: LLP 1023 D7's rule ("Under `EXACT_AGENT=1`
discovery stands down … a smoke never browses the office network"), and
a drive on an Apple host would otherwise show the system's alert. The
declared substitute answers:

- **The fact:** `{available: true, state: "prompt"}` at launch;
  `prefer permission.local-network granted|denied|prompt|unknown` and
  `--permission local-network=…` set it. On the web target,
  `prefer permission.loopback-network …` sets the loopback space's
  permission that D6 reads, `prompt` at launch.
- **The network:** `prefer extension local-network.browseServices=[…]`,
  the whole simulated network, each entry `{"name", "type", "host",
  "port", "hostName"?, "addresses"?, "txt"?: {"<key>": "<value>"}}`.
  `browseServices(type=t)` answers the entries of type `t` (the keyed
  fixture, D16 item 6); `resolveService` answers the entry its `name` and
  `type` select (`"from": "browseServices"`), `hostName` defaulting to
  `host`, `addresses` to `[host]` when `host` is an address.

| Event | Result |
|---|---|
| a browse or resolve while `prompt` or `unknown`, foreground | a `permission` ticket naming `local-network`, the type and the origin |
| `tap @t allow` | `state` `granted`; the browse answers |
| `tap @t deny` | `state` `denied`; readers fail `NotAllowedError` |
| `tap @t cancel` | `state` unchanged; the request fails `NotAllowedError` |
| a preferred network without an entry a resolve reads | that reader fails `NotFoundError`; its browse re-answers without it |
| a resolve of a name not in the network | `NotFoundError` when the agent clock passes `timeout` |
| a type no `net.dns-sd` line lists | `SecurityError`, as production |
| a tool's, a wake's or a package event's browse or resolve | joins a running group, else `person-required`, as production |
| a tool's, a wake's or a package event's `fetch` hop to a local host | as production (D6): `person-required` while the governing permission is `prompt` or `unknown`, `NotAllowedError` unsent while `denied`, on a target that prompts; under the agent prompt risk is D5's static test, since the substitute reads no interface |

The fixture's `host` is loopback in a drive, which D5's development-build
rule admits, so the app's real `fetch` reaches the drive's fixture
server: the substitute stands in for discovery, never for the device's
own protocol.

**Disclosure:** `state.extensions["local-network"]` lists the browses and
resolves with their readers and origins, the fact and its evidence, and
each local reach refused by D6. **Production:** none of it.

## 10. The consumer: Lights

No app in or beside the repository browses the network, and the apps that
reach a LAN server do it only in development (Excord's fixture on an
iPhone, Harmony's Snapback server, the Agents app's transport). Each of
those would gain a typed address from this module but not a feature a
person asks for. The development launcher of LLP 1023 D7 and D9 would
use `browseServices` for `_exact._tcp`, but it is unbuilt and its own
work. So this RFC proposes a small new app with one job, chosen so that
everything here that can fail is exercised by a device a person can buy:

**Lights** (`apps/lights`) controls WLED lights on the local network.
WLED is open-source firmware for addressable LED strips on ESP32 and
ESP8266 boards, sold preflashed in retail controllers. It suits a first
consumer:

- It advertises `_wled._tcp` on port 80, with one TXT key, `mac`
  (`MDNS.addService("wled", "tcp", 80)` and `MDNS.addServiceTxt("wled",
  "tcp", "mac", …)` in [`wled.cpp`](https://github.com/wled/WLED/blob/main/wled00/wled.cpp)),
  at a host name `wled-<last six MAC digits>.local`.
- Its JSON API is documented ([JSON API](https://kno.wled.ge/interfaces/json-api/)):
  `GET /json/si` answers `info` (`name`, `ver`, `leds.count`, `mac`) and
  `state` (`on`, `bri` 0–255, `seg[].col`); `POST /json/state` with
  `{"on": true, "bri": 128}` changes it. State and info need no
  authentication, and every response carries
  `Access-Control-Allow-Origin: *` ([`wled_server.cpp`](https://github.com/wled/WLED/blob/main/wled00/wled_server.cpp)),
  so the web can reach a typed address.
- **A hand-built reference:** WLED's own native apps find lights this way:
  on iOS `NWBrowser.Descriptor.bonjourWithTXTRecord(type: "_wled._tcp",
  domain: "local.")`, with `_wled._tcp` in `NSBonjourServices`
  ([WLED-iOS](https://github.com/Moustachauve/WLED-iOS)); on Android
  `NsdManager` with `_wled._tcp.` ([WLED-Android](https://github.com/Moustachauve/WLED-Android)).
  The tell test and the ceiling test compare Lights with them.

**What it is.**

- **Grants:** `device.local-network lanPurpose`, `net.dns-sd _wled._tcp`,
  `net.fetch local-network`; a strings table ("Lights finds and controls
  the WLED lights on your network.").
- **Contract:** `localNetworkStatus()`; `browseServices(type="_wled._tcp")`
  read at launch, since finding lights is the app's whole purpose (Apple's
  guidance allows a request essential to the app at launch, LLP 1133.002
  D9); a row per light with its name, an on and off switch and a
  brightness slider; **Add by address** (a field, kept as a persisted

  their `mac`, shown "Not on this network" when absent; while `denied`,
  the platform's words and `openURL("app-settings:")`; while
  `available` is false (the web, Linux without Avahi), the address field
  alone, with a line saying why.
- **Data code (`app.ts`):** `lights(found, added)` resolves each listed
  light (`resolveService`), reads `GET http://<host>:<port>/json/si`, and
  answers `{id, name, on, bri, mac, reachable}` per light; `setLight(id,
  on, bri)` resolves and posts `/json/state`. An added address skips the

- **A fixture:** `apps/lights/fixture/server.ts`, a WLED subset
  (`/json/si`, `/json/state` read and write, CORS `*`) on a loopback port,

**Drives** (under the agent, on the web's JS target, the iOS simulator,

7. On the web: the address field alone from the start; the same as 6.
8. Origins, as runner tests (`as_origin`, as

## 12. What reaches beyond this module

- **Every app** gains D6's origin rule, at every hop of every fetch,
  which changes ibex2's `admit_hop` and WebSocket open (vendored, so the
  change goes upstream too) and the data runtime's host call, which gains
  the origin. Excord's development build reaching its fixture at a LAN
  address from a tool would now be refused until a foreground reach has
  shown access; nothing in the tree does that today.
- **Every web fetch** to a host in LNA's local space as written gains
  `targetAddressSpace: "local"`, whichever line admitted it, and a
  tool-, wake- or device-origin web fetch follows no redirect while the
  browser answers the permission of a space less public than the page's
  with anything but `granted` (D6's redirect gate).
- **Android's move to API 37** makes `ACCESS_LOCAL_NETWORK` a runtime
  permission for every app that reaches the LAN, module or not (D9). The
  host's target is a host decision with its own Play deadline; D16 item 2
  is ready for it, and `adb reverse`, which is loopback, is unaffected.
- **`host.ios.localNetworking`** adds `NSAllowsLocalNetworking` for the
  development client; `local-network` now derives it for any build. The
  two may become one, a host change outside this module.
- **The development launcher** (LLP 1023 D9) can browse `_exact._tcp`
  through this module when it is built.
- **Device testing** (LLP 1133.020): a phone reaching a fixture on this
  Mac still types the LAN address. A fixture that advertises a type of
  its own with `dns-sd -R` would let a development build find it; that is
  apparatus for Charlie to admit or not, not part of this module.
- **Process-wide devices under per-session packages** (LLP 1133.022 §19):
  D3's one browse per process and argument group is a second instance;
  LLP 1133.001 should state the rule once.
