# LLP 1048.004: The HTML-direct render — a page written from the plan and its settled state

**Type:** RFC
**Status:** Draft r1. Charlie ruled on 2026-09-29: "B, yes, after the Web Vitals wins land". He asked for the design now; implementation waits until the coordinator says the Web Vitals work has landed.
**Systems:**
- The render host (`host/render`): a second way to write a JavaScript page's `#exact-root`, chosen per route when the plan allows it.
- The web host's projection (`host/web/src/document.rs`, `css.rs`, `element.rs`): the oracle, and where each fragment comes from.
- The runner (`runner/`): a settle without a view tree or a kernel.
- The web JS build (`host/web-js/build.mjs`): the shell's static classes, which both paths share.

## Summary

Today a served page costs what a device's first frame costs, done on a server:
- a runner boots and commits once per answer;
- each commit builds or updates the instance tree;
- the kernel applies the tree's operations, which means style validation, inheritance and the `testId` index;
- the projection walks the kernel's nodes, turns every style row into CSS text, escapes and joins the strings;
- `page::for_runtime` then reparses those tags to swap inline styles for the shell's classes.

Solid and Svelte write the page as string concatenation over templates compiled ahead of time. This RFC proposes the same shape for exact2, without a second source of truth. At build time, each plan node's constant part (tag, constant attributes, constant style) is written once as an HTML fragment, with its class already chosen. At request time, the runner settles state only: slots, derives and resources, with no tree and no kernel. Then one pass walks the plan's sites over the settled state. It evaluates only the dynamic bindings, selects region arms, expands lists, and appends fragments and escaped values to one string.

Today's render stays the oracle. A differential test renders every served page of every app both ways, from the same settled checkpoint, and requires the same bytes. A route whose plan uses anything the direct path does not cover keeps today's path. The build decides that per route and prints it.

## 1. Why, in numbers

Measured 2026-09-29 on the loaded shared Mac, after the SSR-cost lane's commits. CPU is per page.
- **RealWorld `/`, concurrency 8.** About 6.1 ms with the platform transport and about 5.1 ms with rustls on macOS (LLP 1048.000 D10, "The server's transport"). Solid is about 0.8 ms on a quiet machine. The ratio under the same load is about 5×.
- **Where RealWorld's time goes** (sampled profile, with the transport and the realm set aside):
  - boot about 5%;
  - commits about 25%, of which the instance tree's update is about 45% and the kernel's apply about 50%;
  - the projection about 12%;
  - page composition about 3%;
  - tearing the runner down about 6%.
- **The grid benchmark** (1,000 rows, a 1.9 MB page) is about 130 ms against Solid's 24 on the same load. There the tree and bindings are about 31%, the kernel's apply 24%, the projection 19%, and JSON across the Hermes boundary about 3%.

Removing the tree and the kernel from a served render removes about half of what is left. Writing fragments instead of projecting nodes removes most of the rest. The Hermes realm (about 0.55 ms, LLP 1048.000 D10's fresh realm) and the answers' parsing stay; this RFC changes neither.

## 2. Decisions

**D1 — Scope: JavaScript pages only.** The direct path writes documents whose view ids nobody keeps (`Ids::Any`, `page::for_runtime`). The wasm runtime adopts by digest, ids included, and keeps today's path; it is being retired on the web anyway (LLP 1071 §7).

**D2 — Fragments at build.** For every plan node, the build computes:
- the tag (`tag_for`);
- the constant attributes, after `props_for` and the projection's attribute rules (`value`, `checked`, `href` checked by `navigable`, `data-exact-on` from the node's handlers, `tabindex`);
- the constant style's CSS (`css_text` over the node's constant rows, then `host_css`);
- the class that CSS maps to in the shell's stylesheet (the same table `page::for_runtime` reads).

A node is **static** when none of its rows, props or text reads state; it becomes one fragment string, closing tag included, when its subtree is static too. A node that reads state becomes a template: fragment pieces with holes for its dynamic attributes, style and text.

The fragments are computed by the same functions the projection uses, called on a node built from the plan's constants, never by a second implementation. They are generated into the render binary (bytes the build writes, as `app.plan` is), not computed per server start.

**D3 — Settle without a tree or kernel.** A served render needs the settled state, not the tree built along the way. The runner gains a headless settle: boot evaluates slots, derives and resources, hands out requests, and commits answers to state only. The render host's settle loop is unchanged: the same completion rule, deadline, executor and refusals. The `Held`/`busy`/`refused` bookkeeping and the checkpoint are the same. Only `update_tree` and `apply` are skipped.

What a commit's tree would decide must not be lost:
- which region arm is selected;
- which list rows exist, including a virtualized list's window at the page viewport (LLP 1048.000 D4);
- what a row's key names;
- `into_view` statuses.

The emitter computes these at the end, from the same instance-layer functions (`RegionInst` selection, the collection's window at the viewport), called over settled state. `projects_as_booted` already holds that the settled tree projects as the boot-from-checkpoint tree does, so one pass at the end gives the same document as a tree built commit by commit.

**D4 — One emit pass.** It walks the plan's site index (`SiteIndex`: groups, regions, arms, lists) over the settled state, and for each site:
- a static node appends its fragment;
- a template evaluates its dynamic bindings with the plan VM (`Update::eval`'s evaluator, with the same frames and row scopes), escapes each value, and appends pieces and values;
- a region appends its selected arm;
- a list appends its rows, each with its row scope.

The output is `#exact-root`'s contents as `page::for_runtime` would have left them, classes already chosen. The head (`page_head`), the checkpoint and the digest are made as today.

**D5 — Coverage is decided at build, per route.** The build classifies each route that renders documents as `direct` or `projected`, and prints the reason for each `projected` one: the first plan feature the emitter does not cover. Each feature joins the direct path only with fixtures that pass the differential test (D6). The first set:
- boxes, text, links, buttons, inputs, images;
- regions, lists and virtualized lists;
- constant and dynamic style rows that `css_text` lowers;
- markup pieces (`renderMarkup`).

Features that stay `projected` until they are covered include:
- animations with keyframes (`@keyframes` in the head);
- canvas;
- SVG islands;
- navigation stacks (`route_children`'s hidden and inert routes);
- anything whose projection reads the kernel's computed or inherited state.

A server never switches paths mid-render; the route's classification decides.

**D6 — Proof of equivalence: a differential test over every served page.** The oracle is today's render (`render_as` with `Ids::Any`, then `body_js`).
- **Fast lane, `cargo test`.** For each in-repo app with document routes, its build locations and a set of recorded pages (the checkpoint answers of real renders, kept as fixtures), both paths render from the same checkpoint with a scripted source that answers from the checkpoint. `#exact-root`, the head and the checkpoint must be byte-identical. The same test runs over `host/web-js/conformance/*.contract` plans that declare documents, which cover region, list and row-scope edge cases.
- **Async lane.** The same comparison runs over each app's live sources, and over the bench's three apps (RealWorld, grid, feed) at their `ssrPaths`.
- **In the server, off by default.** An environment flag renders both ways and logs any difference, for a person chasing one on a real app.

A difference is a failure with the first differing byte's element path. It is never "close enough".

**D7 — What does not change.**
- LLP 1048.000 D10's isolation: a fresh runner and a fresh module realm per request.
- The data source, its grants, the executor and the deadline.
- The HTTP contract, the early flush and the checkpoint the client adopts.
- The page's bytes; D6 holds them.

## 3. Costs and risks

- **Two ways to write a document.** The fragments are built by the projection's own functions (D2), and the emitter is the only new code: about 1,000–1,500 lines estimated, most of it the site walk and the template holes. The differential test is what keeps it honest; without it this RFC should not land.
- **Windowing.** A virtualized list's server-side row count comes from its estimated row heights at the page viewport. The emitter must ask the collection code for the window, not recompute it; D6's list fixtures pin it.
- **Inheritance.** Some projection output reads inherited state: `display: block` for a non-inline span, text direction, `lang`. Each such rule is either computed from the plan (the parent chain is static in a fragment) or makes its node `projected` (D5). The kernel's computed inheritance is not reimplemented.
- **Build size.** Fragments add bytes to the render binary, never to the browser's artifacts. RealWorld's 273 nodes are a few tens of KB.
- **Headless settle in the runner.** The runner's commit path gains a mode without a tree. It has to keep refusing a commit whose tree would have failed (`InvalidCollectionFeedback`, poisoning). The emitter reports an instance error as today's render would, and D6 includes those cases.

## 4. Expected result

Estimated from §1's profile, before measuring. RealWorld `/` loses the tree, the kernel and most of the projection, about 40% of a render's CPU after the transport change: roughly 5.1 → 3 ms under today's load, or about 1.3 ms on a quiet machine. What remains is the realm (about 0.55 ms), the answers' parsing and JSON, the settle's bookkeeping and HTTP.

Reaching Solid's 0.8 ms also needs the realm's cost gone. That is a separate proposal: a proven reset, which needs a Hermes heap snapshot or a bake that proves a module keeps no mutable state. This RFC doesn't make that proposal.

The grid page should gain more, since its cost is almost all tree, kernel and projection: an estimated 130 → 40 ms under today's load.

## 5. Alternatives considered

- **Render with the JavaScript runtime under Bun (`--render js`, `host/web-js/render.mjs`).** It already exists, but it builds a DOM and runs the whole runtime. It is not cheaper, and it adds a Node or Bun process to a Rust server.
- **Keep the kernel, drop only the projection's string work.** This saves about 15%, not the half that the tree and kernel hold.
- **Warm realms by default.** This gives up D10's guarantee; Charlie has not ruled it in.

## 6. Stages

Each stage lands only after the five checks, conformance, and the differential test over everything the stage claims.
1. **Fragments and the differential harness, emitter off.** The build writes fragments, and the fast-lane test compares a fragment-only emitter against the projection on fully static documents (RealWorld's not-found page, conformance fixtures).
2. **Headless settle.** Measured alone with the projection still used: its saving and its equivalence (the settled checkpoint is identical).
3. **Templates, regions and lists.** RealWorld's routes become `direct`; the bench's `/`, article, profile and tag pages pass the differential test and are measured.
4. **Virtualized lists and markup.** The feed and grid benchmarks become `direct` where D5 allows.
5. **The remaining features**, one at a time, each with fixtures, or left `projected` with the reason printed.

## 7. Assessment: the fresh realm's cost under D10 (2026-09-29, reading and a microbenchmark; nothing built)

LLP 1048.000 D10 gives each request a fresh module realm. This section asks whether that cost can go while D10's guarantee stays.

**What it costs.** A scratch release test (not committed) made, loaded and dropped Caltrain's TypeScript module 400 times on the loaded Mac. Loading took 0.37–0.41 ms and dropping 0.08–0.09 ms. The RealWorld server's profile splits the load:
- the runtime's construction is about 84%;
- the prelude and the app's bytecode are about 16%.

Construction splits into:
- the interpreted internal JavaScript (Hermes' Promise, async function and iterator polyfills) at about 40%;
- the global object's built-ins at about 32%;
- the GC's heap and its background thread, and the interned strings, at the rest.

Teardown is mostly the GC's own. A Hades background thread is started and joined per realm.

**Options, with costs:**
1. **A heap snapshot (restore a realm made at startup).** This Hermes (static Hermes, `shermes/stable`) has no heap serializer. Upstream removed its old one, and `SerializedValue` is only structured clone of one value between runtimes. Reinstating one would be a Hermes fork that walks every cell kind, the runtime modules and the native function tables, with its own tests. Cost: weeks to months, plus a fork to carry. Not recommended.
2. **Reset a runtime in place.** Hermes has no reset path and no second realm per runtime. `Runtime` owns one global object, created in its constructor, and nothing re-creates it. Not available without the same fork.
3. **Cheaper construction, in build and runtime flags, keeping a fresh realm.** None of these cuts more than about a quarter of a realm's cost.
   - *Runtime flags:* `withIntl(false)`, `withEnableHermesInternal(false)` and a smaller initial heap measured together at about 0.30–0.35 ms against 0.39–0.41 ms (−10–20%, within the machine's noise run to run). A 4 MiB initial heap alone made teardown slower on the first run. Turning off Intl changes what `toLocaleString` does in a render, so it is not free semantically.
   - *Native internal JavaScript:* `HERMESVM_INTERNAL_JAVASCRIPT_NATIVE` (a Hermes CMake option, off in our build) compiles the internal polyfills to native code. It attacks the largest part, about 40%. Estimate: 0.05–0.1 ms a realm, for a Hermes rebuild and the bake's engine digest moving with it.
   - *No concurrent GC:* `HERMESVM_ALLOW_CONCURRENT_GC=OFF` runs Hades on the mutator thread. That removes the thread start and join per realm, which matters for a server making realms per request. A device would lose background collection, so it would be a render-only engine build. Estimate: small, 2–4%.
4. **Realms made ahead, off the request's path.** Built 2026-09-29 (LLP 1048.000 D10, "Realms made ahead"). Each worker makes one never-used realm when it is idle, on its own thread, and drops a finished render's realm after sending the page. D10 holds exactly. CPU is unchanged. The server's render time fell about 0.5 ms at p50 and 3–6 ms at p95.
5. **Warm reuse for modules proven stateless at bake.** Measured earlier at about 14% of a page's CPU (`EXACT_RENDER_REALMS=warm`). The proof would need three parts:
   - *(a) Closures:* a syntactic pass (Oxc, over the bundle before `hermesc`) finds every binding assigned outside its declaring scope's initialization. Eval and `Function` are off, so this is sound for closures.
   - *(b) Objects:* after module initialization, harden the realm (SES-style): freeze the intrinsics, the globals and everything reachable from the module, so an object write throws.
   - *(c) Host state:* the prelude's per-realm state (its calls, parked answers and fetch table) gets a host reset, checked by a test that compares a reused realm's second render with a fresh one's.

   The catch is that real apps fail (a). RealWorld has `let stamp`, written only by mutations, which never run in an anonymous render. Interview keeps replica and identity globals. A rule that admits RealWorld needs a call graph from the render's entry points, which is much harder to make sound. Hardening also breaks libraries that cache lazily, and frozen global regular expressions (`lastIndex`). Cost: 1–2 weeks for (a)–(c) and the differential test, for a gain only on modules that pass. Not recommended before this RFC's direct render.

**Recommendation:**
- Take 4 now for latency (done).
- Take 3's native internal JavaScript and no-concurrent-GC engine for the render host, if a Hermes rebuild is acceptable: an estimated 20–30% of the realm, about 0.1 ms a page.
- Leave 1, 2 and 5.

Solid's 0.8 ms therefore stays out of reach while D10 requires a fresh realm, unless that rule changes for modules that declare themselves stateless. That is Charlie's call, not a mechanism.

## 8. Open questions

- **Q1.** Should a `projected` route warn at build or stay silent? The build prints it in either case; the question is whether a warning should fail `--strict`.
- **Q2.** Should the in-server self-check (D6, third item) run a sampled fraction of production renders? That would be continuous verification at a small CPU cost.
- **Q3. Stream the body as it is emitted** (the web-startup lane, 2026-09-29). Today the early flush sends the head, and the body goes out as one piece once the whole document has been projected. On the grid bench's 1,000-row page the body starts about 110–190 ms after the head, against 45–75 ms for Solid, Svelte and React. That gap is most of exact2's first-paint deficit there: mobile FCP 632 against React's 604 and Svelte's 660; desktop 304 against 132–240. Streaming on today's path gains little. The runner's settle and the kernel's apply, about 70% of the render, must finish before the projection writes its first byte, so flushing the projection in chunks would save only the projection, `for_runtime` and brotli on the first screen. That is roughly a quarter of the render, at the cost of a writer threaded through the document walk and `for_runtime` working per chunk. D4's single emit pass streams for free: it writes `#exact-root` in document order from settled state, so the server can brotli-flush every N KB, the first screenful of rows first, and send the checkpoint last as it does now. The page's bytes don't change, since D6's comparison is over the whole body. So streaming belongs to D4's emitter, not to today's projection.
