# LLP 1152.000: What `re` and Thane do that the JS target does not

**Type:** Research
**Status:** Draft, 2026-10-28. A reading of two engines' source against `host/web-js`, not a measurement. Each candidate below says what to measure before building it.
**Systems:** the web JS target's compiler (`host/web-js/src/emit.rs`) and runtime (`host/web-js/rt.js`: `h`, `P`, the `each` region; `list.js`)
**Author:** Claude (Fable 5.1) for Charlie Cheever
**Date:** 2026-10-28
**Related:** LLP 1152 (the shootout; §2.3 the Krausest lane, which these two sit near the top of); LLP 1071 (the JS target, §1 measured and "Generated code at scale"); LLP 1048.000 and 1048.001 (adoption, which already walks a rendered row by cursor); `bench/dioxus/README.md` (the last web standings); the engines: [`frameworks/keyed/re`](https://github.com/krausest/js-framework-benchmark/tree/master/frameworks/keyed/re) (npm `@zhenre/core` 0.2.0, merged 2026-10-24) and [timlouw/thane](https://github.com/timlouw/thane) (npm `thane` 0.2.0)

## Summary

Both engines sit within a few percent of hand-written vanilla JS on Krausest's table because
the table is DOM-bound: once a framework stops diffing, the wins left are fewer DOM calls
per row built, fewer DOM calls per value changed, and no work on rows that did not change.
Each does the same three things to get there, and the JS target does none of them yet:

1. a row is one `cloneNode` of a compiled prototype, with its dynamic slots wired by
   precomputed paths, not one `createElement` and `setAttribute` per node;
2. a binding is specialised at compile time (a kept `Text` node written with `.data`, an
   attribute with a cached last value), not a generic setter that re-derives the case and
   reads the DOM to guard the write;
3. a keyed list change re-keys nothing that did not change, with fast paths for append,
   one removal and a swap, instead of keying every item and rebuilding the map each time.

The first two are compiler changes the JS target is well placed for, since its compiler
already knows every node's static structure and every binding's name. The third is in
`rt.js`'s `each` region. §3 says where each would show in the shootout's workloads and what
to trace first.

## 1. The two engines

**`re`** (`@zhenre/core`, about 4.5 KB gzipped). `html` tagged templates: the template
string is parsed once per call site into a `<template>` and a slot list (child-index paths
to each dynamic text node or attribute); an instance is `content.cloneNode(true)` and a
walk of the slot paths. Signals are plain objects with a single-subscriber fast path and
push synchronously to DOM subscribers. A signal created while a row renders is marked as
owned by that row, so its binding registers no disposer: the row and the signal die
together. The keyed view (`each.ts`) keeps a `Map<key, entry>` and has fast paths for
empty (`replaceChildren(anchor)`), append of a prefix-preserving tail, no common keys
(replace all), and an imperative O(1) `swap` and `remove` that update the source array
quietly. Rows going into an empty container of 32 or more are built with the container
detached. Its benchmark app keeps a direct reference to each row's label `Text` node and
writes `.data`; events are two delegated listeners on the `tbody`. Its author reports a
geometric mean of 0.95 of vanilla; the maintainer called it the fastest entry of the
Chrome 156 run, "close to vanilla js".

**Thane** (`thane` 0.2.0, a compiler and runtime by Tim Louw; "unchanged bindings are no
longer rewritten" is 0.2.0's headline). Components are compiled: a template string becomes
a `<template>` cloned per component, and `createKeyedReconciler` (`dom-binding.js`) takes
a compiled row prototype plus a `bind(el, item, i)` closure. What is distinctive:

- *Whole batches of rows* are cloned at once: a fragment of `batch.size` prototype rows
  is built once, then `cloneNode(true)` of that fragment yields N rows per call, bound by
  walking `nextElementSibling`.
- *An identity-first pass*: for a same-length update it walks rows by position and skips
  any whose item is the same object, updates in place any whose key matches, and only on
  the first mismatch falls into the keyed paths. Immutable-update patterns (`rows.map`)
  never derive a key for unchanged rows.
- *A lazy key map*: built on the first operation that needs many lookups; a selection or a
  swap scans instead.
- *Fast paths* for pure append (prefix check), one removal (linear scan for the missing
  key), a two-row swap (exactly two mismatches), complete replacement (first and last keys
  both new), then the general path with a kept-run move pass.
- *Index tracking only when a binding reads the index* (`trackIndex`); other lists store
  no position.
- *Guards in the row's update closure* skip writes whose value did not change, in JS,
  without reading the DOM.

Both share: a prototype row cloned, direct text writes, no DOM reads on the update path,
a detached container for a bulk build into an empty list, and no work for rows whose
item is unchanged.

## 2. What the JS target does today

Read from `rt.js` at 27252eb362.

- **Construction.** The compiler emits one `h(parent, tag, cls, attrs, text)` call per
  node (`emit.rs` `node`). `h` is `createElement`, a `setAttribute` for the class, one
  per static attribute, `textContent` for static text, `append`, and `Paint?.list(e)`.
  A heavy-list row (avatar, header, quote, paragraphs of runs, photo grid, link card,
  chips) is a few dozen nodes, so a row is a few dozen `createElement` calls and roughly
  twice as many attribute writes. Adoption of a rendered page walks existing DOM instead
  (`adopt`), which is the cursor-by-path idea already in the runtime, used only for pages
  rendered ahead.
- **Bindings.** Every dynamic prop is `P(e, name, f)`: one effect whose body is a ladder
  of about fifteen cases run on every update (iframe `src` and `sandbox`, `href`
  navigability, `backgroundMaterial`, prop hooks, media props, `text`, `value`,
  `scrollTop`, the boolean-attribute regex, `data-exact-` paint facts, anchor `target`,
  the guest origin). The guard before a write reads the DOM: `e.getAttribute(name) !== v`,
  and for text `e.textContent !== v`, which serialises the subtree. A text write is
  `e.textContent = v`, which drops the old `Text` node and creates a new one.
- **Keyed lists.** The `each` region keeps rows in a `Map` by key, brackets multi-node
  rows in comment anchors (a single-element row is itself), empties the parent at once
  when every row goes, moves only rows off the longest in-order run (`inOrder`, a LIS),
  and inserts runs of new rows as one fragment each. On every change it walks every item:
  `keyAt(i)`, then normalises the key by string concatenation (`typeof k + ":" + k`, an
  allocation per row per pass), builds a fresh `Map`, and runs the LIS over the kept rows.
  A live insert at the top of a 10,000-row list therefore keys 10,000 items and rebuilds a
  10,000-entry map every 250 ms; the bounded window makes that 200.
- **Events.** A listener per element per event through `l()`; the keyboard is delegated at
  the document element and `pointerdown` at the root, so delegation exists in the runtime
  for those two.
- **Signals.** `sig` returns a getter over a graph node; writes conform to the slot's
  declared type (a check per write); `endAll` already skips unsubscribing a leaving row's
  own signals, which is `re`'s owner trick.

## 3. Candidates, in the order to measure them

Each is a hypothesis. The perf program's rule holds: trace the losing metric at the frame
level and predict the movement before building. The traces to take first are a window
shift of the feed on the JS target (`bun scripts/agent.mjs web perf …` by plan site, and a
Chrome trace of one shift), and one live-mode insert on the whole-feed arm.

| # | Candidate | Where it would show | What to measure first |
|---|---|---|---|
| 1 | **Prototype rows.** The compiler emits a `<template>` per row template (it already writes the same markup for a rendered page) and a path list to its dynamic slots; a row instance is one `cloneNode(true)` and a walk of sibling hops, with `Paint?.list` called once for the row. Conditional regions inside a row keep their anchors in the prototype, as adoption expects them. | Every row built: a feed window shift (16 rows of a few dozen nodes), Conduit's feed page, Krausest's create rows. | Script time per row in the shift trace, split between `h` and the bindings. `re` traced `childNodes[i]` at ~0.8 µs per row more than sibling hops, which is the scale of what is at stake per node. |
| 2 | **Specialised bindings.** The compiler knows the prop name, so it emits a per-kind setter: a kept `Text` node written with `.data` and guarded by the closure's last value; a plain attribute with a cached last value; a boolean toggle; `P` only for the names that need the ladder (`src`, `href`, `sandbox`, `value`, media, paint facts). No DOM read on the update path. | Live mode: every visible row's relative time once a second, reaction bumps; Krausest's partial update and select; Conduit's favourite toggle. | Main-thread ms per second in live mode at 0 px/s on the JS target against static mode; the share inside `P`. |
| 3 | **Keyed lists that skip unchanged rows.** Keep the normalised key on the row record; compare item identity before re-keying; fast paths for a prefix append, a one-row prepend (the live insert), one removal and a two-row swap; the LIS only when a kept row is out of order; the map rebuilt only on the general path. | The whole-feed arm's live insert; Krausest's append, remove and swap; any list a stream prepends to (Messages). | Script time of one live insert on the whole-feed arm, by plan site. |
| 4 | **Event delegation for list rows.** One listener per event type on the list's parent for the events rows declare, dispatching by the row the target is in, with the same `:disabled` and inert checks the per-element handlers make. | Memory and setup time of the Krausest table (10,000 rows × 2 anchors) and the whole-feed arm; immaterial for a 50-row window. | Listener count and heap after create 10k rows. |
| 5 | **Batch cloning.** Thane's N-rows-per-`cloneNode`; a refinement of 1 for bootstrap and far-viewport fills. | Window shifts. | Only after 1 lands and its per-row cost is known. |

Not worth taking: a detached container for bulk builds (the JS target already inserts one
fragment per run, so there is one insertion either way; take it only if a trace shows
style work during a shift); `on*` property handlers (one handler per element per event,
no capture, against the runtime's multi-listener semantics); `re`'s quiet writes that move
DOM and then patch the source array silently (right for a benchmark, wrong for a runtime
with commits and a journal).

## 4. What this says about the Krausest entry

An Exact entry built the way the JS target builds today would pay a `createElement` per
cell and a `textContent` per label, and would re-key 1,000 rows on a swap. That is the
Dioxus-class result, not the `re` class. Candidates 1 to 3 are what would move an Exact
entry from "a framework" to "near vanilla" on that table, independent of D3's markup
question. The same three are what the feed's scroll and live-mode columns will show, which
is why the Krausest lane is worth its small cost: it isolates the row-construction and
update costs that the feed mixes with images and layout.

## 5. Confidence

High that the JS target builds and binds as §2 says (read from the code). Medium that
candidates 1 and 2 are the largest costs in a window shift, since the last trace of the
JS target's feed (`bench/dioxus`, 2026-10-03) did not split script time by site. Low on
the size of any gain until the traces in §3 exist. The engines' own numbers are their
authors' and the maintainer's remarks, not a run of ours.
