## 1. Summary and status

A data module may be placed on `main`, which is the default and today's only
behavior, or on a `worker`. One module instance has one executor owner for its
lifetime: its initialization, functions, promise continuations, module-level
variables and disposal run there. The runner, Contract state, layout and UI
commits stay where they are. Placement and language are independent choices:
TypeScript and Rust cross the same boundary with the same inputs, results,
grants and durable data. Placement changes when a call runs and when its answer
commits; it cannot give a worker call the transaction an inline call has (D1, D3).

Charlie asked for the write-up on 2026-09-14 and accepted it the same day,
ahead of the gate at the end of §2: the design is worth building for the story
it lets the platform tell, and the limits will be hit. `rules/NOT-DOING.md`
records the move and its take (§4). The gate is no longer a condition for
building; it is the bar the measurement in §5 step 5 is judged against, so
that a worker is claimed to help only where it is shown to. `main` stays the
default; a module opts in through the manifest (§6).

## 2. What exists, and what the numbers say

Every data source today runs on the thread that owns the runner:

- **Native TypeScript** (`js/src/lib.rs`): `begin` calls into Hermes
  synchronously on the runner's thread, with a raw pointer to the live `Store`
  installed for the duration of the call. An answer that needs no host work is
  `Answer::Now` in the same transaction. A storage `await` returns `Later` with
  a continuation token; the host runs the storage work on its I/O worker, and
  `resume` runs the continuation on the runner's thread again. The 100 ms
  budget is elapsed time checked after the call returns; it preempts nothing.
- **Browser TypeScript** (`host/web/module-glue.js`, `js/web/src/lib.rs`): a
  hidden iframe is a private realm on the page's main thread. Every `answer`
  and `parse` already returns `Later`: the Rust side takes a Store snapshot
  (minus `exact.kept.*`), hands the call to the realm and gets a continuation
  token; the runner enqueues it under a ticket; the host runs the turn from a
  `continue` op; the reply carries the value, the ordered Store writes, the
  names read and whether external storage was read; `parse` applies the writes
  inside `Runner::fulfill`'s checkpointed transaction. The realm serializes its
  own turns. A turn ends at an answer or at a `fetch`, and holds its context
  across storage waits.
- **Rust** (`data/src/mixed.rs`): answers `Now`, inline. In a mixed app the
  composer narrows the Store to each module's own `secret.keep` names
  (`Store::with_grants`); the unit of that scope is the module, not the
  source — the plan declares no per-source grant, and a single-module app is
  never narrowed at all. Fieldnotes' two modules declare the same four grants
  (`app.ts`, `data/src/lib.rs`), so their scopes coincide.
- **Host I/O** (`host/apple/src/executor.rs`, `host/linux/src/executor.rs`):
  one worker thread runs requests and continuation closures in order, queues
  the outcomes and wakes the presenter; the main thread pumps them into
  `Runner::fulfill`. Those closures are already an off-thread path for
  **binary-bound Rust**: a source answers `Later` with
  `Request::continuation`, hands the host a `FnOnce` that owns its inputs
  (`DataSource::continuation`), and `parse` commits the result on the
  runner's thread — Markdown's `open` reads a document that way
  (`apps/markdown/data/src/lib.rs`). Its limits are the reason this document
  exists at all: the closure shares the one I/O thread and runs in order with
  storage; it sees no Store; the replaceable Rust ABI refuses it (LLP 1029.000
  §3), as the portable storage protocol does (LLP 1027.001 D2). No such path
  exists for TypeScript on any host — Hermes and the browser realm are
  owner-bound — which is where a worker module would be the only option.

So most of a worker already exists: a ticketed asynchronous call path, a reply
envelope with writes and read observations, per-module Store scoping, a host
worker with a wake-and-pump path. What does not exist is an executor owner
other than the runner's thread, and (D3) an admission rule that makes a
snapshot taken off that thread safe.

**Measurements** (LLP 1027.001 §6; a 4.17 MB near-limit Fieldnotes backup,
optimized builds, single samples): the largest owner-thread turn was 88.5 ms in
TypeScript and 61.5 ms in Rust, and total owner-thread time 133.9 ms and
84.6 ms. In Chrome, with 1,000 notes of 3,000 UTF-16 units, the library read
had 22–25 ms maximum frame gaps and the TypeScript backup 17–19 ms. At 60 Hz a
25 ms gap drops one frame and an 88.5 ms turn spans five, during an operation
the user started with a button the app disables while it runs (`busy` in
`apps/fieldnotes/app.contract`). No measured workload has yet required a worker
(LLP 1027.001 §6), and the aggregate library size failure in `QUEUE.md` is a
result-size limit a worker would not change.

**The gate** (now the measurement's bar, not a condition for building —
Charlie, 2026-09-14). A worker is shown to help when a real workload, after
the source-level fixes LLP 1027.001 D5 requires first and after the
host-worker closure above has been tried or shown inapplicable (TypeScript, or
a replaceable Rust module), still produces owner-thread turns that break an
interaction the user is in the middle of — typing, scrolling, an animation —
and the measurement names the device, the sample count and the frame gaps. A
single call over 100 ms is not that evidence, and moving work to a worker does
not make it finish sooner; it moves where the wait is.

## 3. Proposed design

### D1 — Placement is per module, chosen when the instance is created, `main` by default

The unit is the module instance, not the function: closures, JS objects, Rust
state, database handles and native pointers stay with their owner, so a
function cannot hop threads per call. `main` stays the default. A host selects
`worker` in the app's existing composition or configuration (the spelling is
§6's), and the same word means the same thing for TypeScript and Rust. A
language, host or placement combination that is not supported refuses visibly
at composition; it never quietly runs on `main`.

`main` and `worker` name placement kinds. The first slice admits one
app-computation worker module per session beside the main-owned sources;
existing host I/O and storage workers are additional. This is an initial
implementation limit. The durable invariant is one executor owner per module
instance, and `worker` must not mean a single global background executor.
Instance identities and the value boundary must accommodate additional owners
when a workload earns them.

Several workers would be useful if interactive search queues behind a long
backup, or independent synchronization and document processing need to make
progress together. Separate module owners address those cases only when the
modules' `secret.keep` lists are disjoint: D3 orders every module that shares
a name into one queue, and a second thread does not make that queue parallel.
Fieldnotes as declared today would get nothing from a second worker. A batch
of independent computations could also benefit from several cores; a bounded
job pool would be a separate extension, preserving each stateful instance's
owner. The return trigger is measured queue delay or a demonstrated throughput
gain, weighed against startup, memory, CPU contention and input latency. Worker
counts remain bounded by the host, with D4/D5's limits applying across owners.
Additional workers and pools remain beyond the first slice.

Changing placement is a replacement (LLP 1029.000 §4): durable state carries,
a live heap does not. Splitting a module so that one expensive function runs
elsewhere is the app's job with the composer that exists; this RFC adds no
splitting, closure capture, worker pools, shared heaps or load balancing.

Placement adds no Contract syntax and gives neither language UI ownership. A
worker call is asynchronous even when the function answers synchronously, so a
source that answers `Now` today takes on the contract every `Later` answer has
had since LLP 1016 D3: the resource keeps its value while pending; a mutation's
answer lands in a later commit than the action that sent it; several sends in
one action commit separately, not together; and a refused reply rolls back its
own settlement only. An action that sets `saving = true` and sends a mutation
commits the slot and the pending state; a later refused answer does not un-set
`saving`. An app that needs those to move together already cannot have it on
the web, where every TypeScript call is `Later`.

### D2 — The worker owns its runtime

**Native.** A host-owned thread constructs, runs and destroys the Hermes
instance and its bindings; the main-thread `DataSource` becomes a proxy that
sends values. Nothing moves a live VM between threads or marks its pointers
shareable to satisfy the compiler. A Rust module on a worker has the same
shape: its thread-affine resources are created and retired on its owner. The
thread is the host's; LLP 1029.000 §4's ban on module-owned threads and
escaping callbacks stands.

**Web.** A [dedicated Web Worker](https://html.spec.whatwg.org/multipage/workers.html#dedicated-workers-and-the-worker-interface)
replaces the iframe for this mode. The prelude's ambient-time and randomness
guards (LLP 1027.000 D3, `js/src/prelude.js`), its ticketed `fetch` and the
storage capability, and the loader's disabled globals (`XMLHttpRequest`,
`WebSocket`, `EventSource`, timers, `requestAnimationFrame` —
`host/web/module-glue.js`) are installed on the worker global before any app
code evaluates; the worker's own `fetch`, storage and timers must not bypass
them. A worker has no DOM, so the loader's uses of `window`, `document` and
iframe construction, and the storage client's ownership, are audited rather
than assumed; the shared SQLite service and scoped host requests stay as they
are. Rust on the web needs a worker-owned wasm instance and memory. No runner
memory and no `SharedArrayBuffer` crosses the boundary. A loader or CSP failure
is a visible refusal. This is trusted app code on another thread, not a
security boundary and not crash isolation.

**Startup.** App initialization still happens after first pixel; baked values
still supply the first frame; native code arrives as bytecode or the admitted
Rust artifact, and the worker adds no compiler. Readiness and candidate
validation become asynchronous where they must, and the UI never waits
synchronously for a worker to start.

### D3 — Values cross; the runner commits

This is the browser's continuation path (§2) on every host, with three changes.

**The envelope** is the browser's, made explicit. A request names the session
and module incarnation, the logical call, the runner ticket, the operation, the
arguments (explicit time and seed inputs included), the admitted scope and a
Store snapshot. A reply carries the same identity, then a value, an error or a
host request, the ordered Store writes, the names read (absent ones included)
and the external-read flag. The logical call survives host-I/O yields; each
runner continuation has its own ticket. Source name plus arguments is not a
call identity — two targets can call one source with the same arguments, and
both executors key parked calls that way today — and neither is a bare ticket
number across incarnations.

**Change 1: the snapshot is taken when the turn starts, from the committed
Store.** Today the browser snapshots when the runner calls `answer` or `parse`,
inside a transaction that has not yet committed, and runs the turn later; a
turn queued behind another therefore reads a Store older than the earlier
turn's commit. Native has no snapshot at all: it works on the live Store
through a pointer, inside the transaction. In worker mode a proxy records the
call and returns `Later`, and only a request the successful commit released is
dispatched (`Runner::run_action` and `settle` hand requests out after the pass
stands; a refusal discards the provisional calls before any app code or host
effect starts). The snapshot is taken on the runner's thread, at dispatch: the
head call of a queue leaves with the Store as committed then, excluding
`exact.kept.*`, and the next call is dispatched in the commit that settles or
refuses the previous reply — the worker never asks for the Store, and no turn
holds a snapshot older than the last commit. App Store calls read and write
that local copy synchronously. The reply's envelope,
ownership and scope are validated, then its writes are applied only through
the runner's settlement transaction: a thrown or refused answer, an invalid
shape or a downstream settlement failure rolls back that transaction's writes,
while a valid application value such as `{ok: false}` is a value. Read and
external-read observations survive an error, as they do today. App code is
never replayed to retry a commit.

**Change 2: turns are ordered across the modules that can conflict.** The
Store is the only state this ordering protects; it locks no SQLite writer and
joins no Store, database and filesystem transaction. The unit of Store scope
is the module (§2): a module can touch only the `secret.keep` names its
grants list, so two modules can conflict only where their lists share a name,
and the composer holds both lists. Start the ordered set with the worker
module, then include every module whose `secret.keep` list overlaps any
member, repeating until no more join (an indirect overlap counts: A with `x`,
B with `x,y` and C with `y` belong together). With today's composer there are
at most two modules, so the set is the worker module alone or both. Every
source of every member enters one FIFO, one turn reserved at a time until its
reply has committed or been refused, and a main-owned member still computes
on `main` but no longer answers inline. A module whose list is disjoint from
the whole set keeps today's dispatch. There is no per-source or per-function
access set, so within the ordered set nothing is treated as non-conflicting
on inspection. Fieldnotes' shared `fieldnotes.revision` puts its TypeScript
and Rust modules in one set: every Fieldnotes source, `library` and `saved`
included, queues behind whichever turn is running, whichever module owns it —
the ordering the app already imposes through `busy`, now applied to every
call. An app that wants an interactive source to keep answering during a long
turn must give it a module with a disjoint `secret.keep` list; the Store
grant partition is the concurrency unit. Queuing only inside each worker
would not do: two modules that share a name would still lose updates.

If additional worker modules are admitted later, overlapping ordered sets
must merge; independent sets may execute concurrently while the runner still
commits their replies. Extra threads in one ordered set do not make its turns
parallel. Store independence also does not remove the ordering imposed by a
shared database or filesystem service.

A resource discovered while a reply settles queues another call; it cannot run
a main-owned member inline and bypass the reservation. Slots, layout and
rendering commit meanwhile, and a resource request they raise waits with its
existing value or pending state.

**Change 3: the same turn boundary on native.** A turn ends at an answer, an
error, or an explicit adapter yield after its microtask checkpoint; `await
Promise.resolve()` alone ends nothing. The browser holds its context across
storage waits and releases the turn at a `fetch`; native storage resumes
through runner continuations. Worker mode exposes one storage and fetch yield
boundary on both: commit the writes made before the host work, park the
continuation, and deliver the completion only with the resumed call's context
installed. A single-owner VM does not by itself stop a late Promise callback
from running under another call's Store scope, so the loader and the
early-installed storage bindings are audited for that. After commit or refusal
the next turn is released; a yielded host request is released only after its
settlement commits, and its completion queues a resume with a fresh snapshot.

**Failure and the retained ticket.** `Runner::fulfill` restores a ticket when
`parse` refuses, and no retry follows: the target stays pending until its
arguments change or it is sent again. A worker that fails therefore needs an
explicit terminal path — fail its queued calls, release its reservation and
clear its pending work together — so a retained ticket neither executes the
call twice nor admits old writes after another turn has advanced the Store.
FIFO alone does not supply this.

**What it needs, and what it is not.** This needs a deferred admission and
dispatch hook; the synchronous `DataSource::answer` plus a snapshot captured
there is not enough. Resolve that hook and the cleanup of rolled-back calls in
the first prototype, before placement is exposed. If it turns out to need
suspended UI transactions or a general scheduler, stop and reconsider scope.
This is serial ordering of executor turns; it is not an atomic multi-send
action and not a transaction spanning an `async` function.

### D4 — Capabilities and sizes stay bounded

Pure URL, text and base64 utilities run on the module's owner. Storage and
network keep app identity, source grants, the existing host workers and
external-read accounting. Native-module factories and handles are audited for
thread ownership. A service that needs the UI thread is an explicit
asynchronous host request; no synchronous callback into the UI may deadlock
against the caller.

Calls and aggregate bytes are bounded before enqueue or serialization —
arguments, snapshots, outstanding I/O, replies and candidate instances — with
capacity reserved for completion and retirement so a full queue can always
drain, and exhaustion refuses new work visibly. Existing byte, heap and shape
limits stay. Owned browser buffers cross by [structured serialization or transfer](https://html.spec.whatwg.org/multipage/structured-data.html#safe-passing-of-structured-data)
without widening the plan's value vocabulary; transfer detaches the sender's
buffer. Host I/O workers stay separate from the module owner, so waiting on
I/O cannot block delivery of its own completion. Main-thread serialization,
receipt, decoding, shape validation and commit are measured: a worker that
computes quickly and returns a result that stalls the UI has not met the
purpose of this option.

### D5 — Cancellation, supersession and replacement keep their meaning

Execution lifetime and whether the UI still wants a result are different
things. Superseded resource work may be removed before it starts; a running
turn holds its reservation until it ends or the failure policy closes its
owner, and its stale reply applies no writes. The runner's newest-send and
assignment rule forgets a mutation's ticket today (`Runner::run_action`,
`enqueue`); a forgotten worker mutation still runs, its reply is dropped and
its Store writes with it, exactly as a forgotten reply's are on the web today.
It is neither coalesced with a later send nor replayed. Dropping a reply undoes
no file write or network request, and a forgotten ticket is not proof that the
worker or a host callback is idle.

Replacement keeps LLP 1029.000 §4's boundary: queued calls, running turns and
host callbacks count as in flight even when their UI ticket was forgotten, and
quiescence is rechecked at commit. A candidate is prepared with effects
withheld; the current instance stays until the candidate is admitted and
ready; carried state is taken at the commit boundary so input during
preparation survives; answers that depended on validation writes are
recomputed once in the live context. The old owner retires only after its
calls and callbacks have ended. Instance lifecycle work moves to the executor
owner; admission and session commit stay on the runner's. A TypeScript-only
replacement still preserves the admitted Rust half of a mixed composition.

Cancellation stops unstarted work and rejects late results. A browser worker
can be terminated; a native thread running Hermes or a native binding must not
be killed, its code must not be unloaded while in use, and the UI thread must
not wait on it. A hung worker stops accepting work, its queued calls fail and
UI input stays available. Retained owners across sessions and replacements are
bounded, and further worker creation is refused at the bound rather than
accumulating abandoned threads; the bound and the recovery behavior are set
before the option is exposed. A thread contains neither an arbitrary native
crash nor an allocation. CPU limits, queue delay, I/O duration and cancellation
stay distinct: the native 100 ms guard checks elapsed time after return,
preempts nothing and covers neither Rust nor the browser, and placement does
not raise it.

## 4. Delivery and the scope trade

Worker placement is another executor over the existing data boundary, never a
Cargo feature on a core crate. A bake includes the worker's loader assets and
binds their bytes to the admitted generation; placement configuration widens no
grant and bypasses no artifact verification; a host without the requested
executor refuses the configuration visibly.

**Ruled (Charlie, 2026-09-14).** The mixed-resource first-frame bake
(LLP 1027.001 D3, in `QUEUE.md`) is not the take: it sits on the same path
this design's own measurement requires (try Rust first; a resource in Rust
needs the bake), so it is built with this work rather than queued (§5 step
0). The take recorded in `rules/NOT-DOING.md`, proposed by the implementer
and Charlie's to swap: Rust on a web Worker waits behind a consumer that
needs it — placement is language-neutral on native from the first slice and
TypeScript-only on the web; a second worker, job pools and load balancing
stay out (D1). Broader API expansion and generalized multi-module scheduling
already wait. The implementation reuses pending answers, scoped storage, the
composer and replacement; it adds no scheduler framework, registry or
blocking check.

## 5. Implementation sequence and proof

0. Route the bake through the declared owners (LLP 1027.001 D3's follow-up):
   `build_mixed` composes the bake's TypeScript module with the app's Rust
   source through the app's own composer, so an exclusively Rust-owned
   resource bakes its first-frame value through Rust with no TypeScript
   placeholder. Prove it with a Rust-owned resource in an app that ships.
1. Resolve D3 against the real runner transactions before any executor work:
   increments to one Store name from a worker and a main member cannot lose
   writes; an action refused after `send` starts no work; a failed reply rolls
   back only its own settlement. Exercise identical calls from two targets,
   queued mutations, indirect Store-scope overlaps and disjoint scopes,
   terminal cleanup of the retained ticket, absent-name reads, storage
   effects that start early, and microtasks around I/O
   resumption. Drive typing that changes resource arguments while a worker turn
   is held, not only an animation with no data dependency. A failure here stops
   the executor work.
2. Build the web TypeScript owner and proxy on the existing ticket path, then
   the native Hermes owner. One worker module per session; `main` and the
   explicit unsupported cases stay intact throughout.
3. Drive Rust through the same contract on web and native. Do not call
   placement language-neutral in the support matrix until both have been
   driven; audit native bindings before claiming every TypeScript module can
   opt in unchanged.
4. Drive Fieldnotes save, backup and restore on both placements while
   scrolling, typing and animating, with the same small and near-limit data;
   compare exact output, durable state, grants, errors and reload behavior
   after the same ordered operations, and test D1's pending and rollback
   differences separately. Fieldnotes routes `backupNotes` to Rust today, so
   the TypeScript proof selects the implementation still in `app.ts`.
5. Measure optimized builds: queue delay, worker CPU and GC, host I/O,
   transfer, runner commit, peak memory, startup, input latency and frame
   gaps, with repeated samples and an idle baseline. The target (Charlie,
   2026-09-14: "don't use a fixed number, base it on the framerate we are
   trying to hit"): no worker-attributable main-thread task longer than one
   frame at the refresh rate the fixture aims at — the device's, read from
   the host (120 Hz on a ProMotion display, 60 Hz elsewhere), never a fixed
   millisecond figure — reported with p50, p95 and maximum frame and
   input-to-paint numbers, per-turn spans, and the Store snapshot and
   persistence costs. The [Long Tasks API's 50 ms threshold](https://www.w3.org/TR/longtasks-1/#sec-terminology)
   cannot establish this. Name devices, refresh rates and sample counts, and
   compare repeated `main` and `worker` runs. A passed 100 ms call check is not
   evidence.
6. Exercise reload during computation and storage, stale tickets,
   cancellation, worker failure, capacity refusal and repeated instance
   retirement. Verify no app JS before first pixel and no duplicated effect,
   through the existing tests, app drivers and the five checks; fleet sweeps
   stay asynchronous.

No prototype or performance result is claimed here. LLP 1027.001 §6 holds the
current numbers. The aggregate library result-size issue in `QUEUE.md` still
needs pagination; a worker does not change that limit.

## 7. As built (2026-09-14)

Everything in §3 landed in one lane the day it was accepted, with two
narrowings recorded in `rules/NOT-DOING.md`'s take: Rust runs on a worker on
native only, and one worker per module. What follows is what the code does,
by file, and what the drives showed.

**The runner** (`runner/src/request.rs`, `runner/src/runner/source.rs`,
`runner/src/runner.rs`, `runner/src/runner/settlement.rs`). `Placement` is
`Main` or `Worker`. A continuation token is now *dispatched*: a host asks
`Runner::dispatch_work(token)` on the runner's thread after the commit that
handed the request out, and the source answers with `Dispatch` — `Run(Work)`,
`Held` (a turn is reserved ahead of it; the host parks the request and asks
`Runner::release_work()` after every later commit), `Host(registry)` (the
browser's turn registry) or `Missing`. `Work` is `Now(FnOnce)` on the host's
I/O worker, as every continuation was before, or `Later(FnOnce(Reply))`: the
I/O worker hands a `Reply` to another owner and moves on; a `Reply` dropped
unsent reports `Aborted`, so a dead owner still ends its ticket and a queue
behind it moves (D3's terminal path). A refused transaction now calls
`DataSource::discard` for every `Later` answer it drops, in `settle` and in an
action's sends (the cleanup of rolled-back calls). `continuation_token` is
gone: `Dispatch::Host` carries the registry token.

**The envelope and the placed source** (`data/src/envelope.rs`,
`data/src/placed.rs`). A turn's reply is an `Outcome::Response` marked
`exact-turn: 1`: the local store's writes in order, its observation count, the
turn's `console` lines, and a value (canonical bytes), the next request (a
yield at `fetch` or the portable storage protocol) or an error by kind. `apply`
commits it inside the runner's transaction: observations, then writes, then
the answer — writes stand under an error, as the browser's do, and the runner
rolls back. `Placed<D>` is the one proxy for both languages: `Placed::new` moves
a `Send` Rust source to its owner at activation; `Placed::built` keeps a
template here and builds the instance on the owner from what the template
knows, which is how `exact_js::Module::placed` works (bytecode, identity,
directories, the bound plan's bytes and the limits cross; the engine is created,
run and destroyed on the owner). A turn stays on the owner through every wait
the source runs itself — the native storage session's, a Rust source's own
worker closures — and ends at an answer, an error, or a request only the host
can run; a `fetch` or portable storage request goes round through the runner
and resumes as a new turn with a fresh snapshot. Validation runs inline, on the
runner's thread, from the template. `Main` is the source, inline, at no cost;
`Worker` on wasm32 refuses visibly at activation.

**The composer** (`data/src/mixed.rs`, `data/host/src/lib.rs`). `Mixed` asks
each child's `placement()` and each child's `secret.keep` names at
construction and builds the ordered sets of D3: a worker child is a set; a main
child joins it when their names overlap; two workers with disjoint names are two
sets. Every call of a member is recorded at `answer` and answered `Later`; at
dispatch the set reserves one turn — a worker child records and dispatches its
own job; a main child computes there and then, on the runner's thread, against
a scoped snapshot, and its envelope goes round like any other reply — and the
next recorded call is `Held` until the reserved turn's reply has gone through
`parse`, whatever it said. A yield's host outcome is recorded as a resume and
takes its own turn. `Storage<D>` forwards placement, dispatch, release and
discard through its token map. Placement is carried by replacement and never
changed by one: a replaced pair is composed again from its children's
placements.

**The hosts** (`host/apple/src/{executor,abi,host}.rs`,
`host/linux/src/{executor,presenter,host}.rs`, `host/web/src/{host,abi}.rs`).
The native executors take `Option<Work>`; `Later` work hands the executor's
outcome channel and wake to a `Reply` and never holds the I/O thread. The
Apple bridge's `emit` and the Linux presenter's `after_commit` dispatch every
continuation, park `Held` requests by token and release them after each commit;
a host swap clears the parked set. The web host does the same in `complete`,
runs `Work::Now` at once and fulfils it in the same batch (a main member's turn
in an ordered set), emits `continue` for `Host` tokens, and reports
`placement` in its logic info so the loader prepares the right realm.

**The web realm** (`host/web/module-glue.js`, `host/web/module-worker.js`,
`js/web/src/lib.rs`, `host/web/storage.js`, `host/web/storage-fs.js`). The
browser module has a placement. Every turn, on either placement, now takes its
snapshot at dispatch (`{op:"dispatch"}` replaces the queued turn's store with
the store as committed; `{op:"discard"}` drops a turn a refused transaction
never released), which closes the stale-snapshot gap §2 named for the iframe
too. `placement: "worker"` prepares a dedicated module Worker instead of the
iframe: the same prelude and its guards, the loader's disabled globals, the
storage capability and the turn discipline, evaluated at the Worker's global
scope by indirect `eval` of the verified text; turns cross as messages; a
`fetch` yields to the page; disposal terminates the Worker. The storage client
evaluates in that guarded global, so it now captures its clock when its module
evaluates rather than reading `Date.now` per write (five sites).

**The manifest and the bake** (`scripts/app.schema.json`,
`contract/cli/src/compat.rs`, `js/bake/src/{lib,resident,main}.rs`,
`host/web/dev.mjs`). `typescript.placement` and `rust.placement`, per platform
under `platforms.<platform>.placement`; `Manifest::placement` resolves them,
`EXACT_TYPESCRIPT_PLACEMENT` and `EXACT_RUST_PLACEMENT` override a bake, and
both enter the compatibility id (`typescriptPlacement`, `rustPlacement`), so a
change is a rebuild. The bake writes `TYPESCRIPT_PLACEMENT` and
`RUST_PLACEMENT` into `module.rs`, typed for the executor crate the platform
links, and the app glue places its modules from them. §5 step 0 landed with it:
`build_mixed_with` composes the bake's TypeScript module with the app's Rust
source through the app's own composer, so a resource only Rust owns bakes
through Rust — Update Lab's `rustConstants` is the proof, answered by nothing
in `app.ts`; the receipt records `rustSources`, and the development producer,
which cannot run Rust, seeds such a resource from the plan the page already
serves (`dev.mjs` passes `previous` and `receipt`), refusing by name when a
source is shared by several resources.

**Consumers.** Fieldnotes ships with `"typescript": { "placement": "worker" }`
and Rust on `main`; Update Lab and Weatherlight place from the manifest's
defaults, on `main`. Both halves of Fieldnotes keep `fieldnotes.revision`, so
the whole app is one ordered set, as D3 said it would be.

**What the numbers say.** On this fixture the web shows no gain from the
worker — the worker rows are the slower ones, in these single runs — and the
reason is the one D4 warned of: the TypeScript compute is not where the
page's main thread goes, while the ordered set adds a round trip per yield
(every storage step of the Rust backup becomes a recorded resume turn with
its own commit once the app is one set) and the library value crosses the
Worker boundary as a message before it is decoded on the page. Typing drops no frames on either placement
at 1×; the backup's long gaps are the Rust backup running in the page's wasm
(on `main` in both rows — Rust on a web Worker is the deferred take) and the
library value coming back: a thousand notes of three thousand characters
cross from the realm as one message, are decoded in wasm, shape-checked and
committed into a thousand rows, whichever thread produced them. The worker
moves the turn; it does not move the commit. The native fixture is the one
where the TypeScript turn itself was the cost (88.5 ms in LLP 1027.001 §6),
and there the turn now runs on its owner thread — but the Mac has no
frame-gap instrument yet, so that claim is not measured here (owed). The bar
Charlie set is one frame at the device's rate; this fixture does not meet it
on either placement in the backup window, and meets it while typing at 1× on
both. Single runs in headless Chrome, whose frame cadence is a fixed 60 Hz:
enough to place the cost, not to rank the placements.
