# LLP 1050.000: Choosing the fill trade-off — never blank by default, fly over by choice

**Type:** RFC
**Status:** Draft (r2; rulings D1–D6 recorded)
**Systems:** Scrolling (LLP 1010 §6.5 the collection, as the one list engine), Runner (`CollectionFeedback` v2, the owed set, pending intervals, retirement), Contract (one `list` attribute), Apple host (collections on the `ScrollPump`, `targetContentOffset`, `KnobDrag`), Web host (`collection-glue.js`, authored jumps), Linux host (`presenter/collection.rs`), Agent (LLP 1012: pending intervals in `state`)
**Author:** Claude (Opus 5.5) for Charlie Cheever

**Date:** 2026-09-24 (r1); r2 the same day, after three reviews and Charlie's rulings

## Summary

Charlie asked, 2026-09-24, whether our collection can let an app choose to
**drop views** (smooth scrolling, rows briefly missing) or **drop frames**
(every row present, late frames). He also asked whether that choice is the best
thing to want, and whether it should be one abstraction or several libraries.

**Rulings (Charlie, 2026-09-24, on the author's recommendations: "ok those are
fine"):**

- **D1: the default is never blank.** A list waits for the rows it shows
  wherever the host can make it wait (`fill-policy="complete"`, the default).
  The per-gesture rule, `fill-policy="auto"`, is opt-in. The default flips only
  after a physical 120 Hz run shows that `auto`'s fling gaps are hard to notice
  and that it removes most of the stutter on heavy lists.
- **D2: a scrollbar-thumb drag waits for its visible rows.** Gaps under a thumb
  appear only under the overload rule (D3), and on the web, where the browser
  owns the scrollbar.
- **D3: a row may take longer than a frame, but never mid-fling.** During user
  motion, a row whose cost is known to exceed the frame is not built. It shows
  as pending until the motion slows or stops, and is then built even if that
  costs a late frame. Resumable rows (building a row across frames) are a
  separate project, taken only when an app needs one.

**The answers to the three questions:**

- **Can an app choose?** Yes: one attribute, `complete` or `auto`. Hosts honour
  it where they can. The web cannot make a user scroll wait (LLP 1050 F1), and
  that is declared, not hidden.
- **Is the choice the best thing to want?** No. It decides only what to give
  up once work overruns a frame. The bigger wins shrink that overrun:
  - one engine with a budget;
  - building the landing zone first;
  - cheaper rows;
  - for wide tables, building only the visible columns.

  The policy is the last lever (§3).
- **One abstraction or several libraries?** One engine with one attribute. The
  hard parts are shared, and our two current engines already disagree (§4).

## 1. The moment the policy governs

A frame is due. The viewport shows part of the list; some rows in it are not
built; building them all would miss the frame. That is the only moment the
policy governs. Everything before it is prefetch: invisible, always under a
budget. Everything after it is one of three outcomes:
- **wait:** a late frame, every row correct;
- **pending:** the frame is on time, with the missing rows' space empty;
- **both:** build some, then present.

A fourth outcome, slowing the fling, stays out: LLP 1010 §6.2 forbids resetting
native momentum, and scroll always wins.

## 2. The two policies

### 2.1 What each owes

The runner computes an **owed set** for each report. Owed rows are built in
this report whatever it costs. Everything else is optional: built in priority
order under the host's `limit`, or left pending.

| | `complete` (default) | `auto` (opt-in) |
|---|---|---|
| Focus and interaction pins (LLP 1010 §6.5) | owed | owed |
| Rows at a jump, restore, find, keyboard page, accessibility or focus move | owed | owed |
| Rows visible while the user drags, scrolls a wheel, or drags the thumb | owed | owed |
| Rows visible while a fling passes over them | owed | optional |
| The fling's landing viewport | owed on arrival | built ahead; owed on arrival |
| Rows changed in view by data (insert, replace, `scrollFollowEnd`) | owed | owed |
| A row known to cost more than a frame, during user motion (D3) | pending | pending |
| At rest | everything visible owed | everything visible owed |

Every other row is optional under both policies: overscan, the lead in the
direction of travel, and the rows behind.

The overload row (D3) is the only way `complete` shows pending on a host that
can wait. At rest, nothing visible is pending under either policy: an app
never settles on a gap. First mount follows LLP 1010 §6.5's bootstrap (at most
16 rows before the first geometry report). It is bounded by boot, not by this
table.

### 2.2 Signals, not causes

Hosts do not classify gestures. Each report carries the raw signals the host
has. The runner maps them to the table:

- **Authored.** The runner already knows its own `scrollTop`, scroll-to-row and
  data changes, and needs no signal for them.
- **Touch or pointer down** (dragging).
- **Decelerating**, meaning a fling is coasting.
- **Knob down.** macOS has `KnobDrag` (`CollectionMac.swift:34–38`). iOS and
  the web have no public signal; there a thumb drag reads as an unknown user
  scroll.
- **Wheel**, with a phase where the platform gives one.
- **A platform rest offset**: `targetContentOffset` on iOS; none elsewhere
  today.
- **Accessibility or focus move.**

Rules:
- A signal a host cannot produce reads as **user scroll, rest here**: owed, as
  a drag.
- An authored move beats a user classification in the same turn.
- A coast whose predicted travel is under one viewport counts as rest here,
  not a fly-over.
- Live resize, rotation and keyboard-inset changes keep the accepted viewport
  coherent (old keys, geometry and hit targets together, LLP 1044.000 §5
  item 3). The new visible rows are owed only when the size settles.

### 2.3 What each host can honour

| Host | A user scroll can wait | Rest offset | Declared deviation |
|---|---|---|---|
| iOS | yes | `targetContentOffset` | none |
| macOS | yes on the main-thread route; on the responsive route (`overscroll-behavior="contain"`), AppKit pauses at `preparedContentRect` (D5, verified in stage 1) | none public; projected from velocity | none if D5 holds; otherwise the responsive route is declared like the web |
| Web | no | none; projected from `scroll` samples, best effort | a user scroll shows the background for at least one frame when fill lags; authored jumps still wait (§6) |
| Linux (ours) | yes | none until it has a fling | none |

Windows and Android stay on `rules/DEFERRED.md`; LLP 1050 §2.5–2.6 record what
their hosts could honour.

### 2.4 What "wait" costs, stated plainly

LLP 1041 §1 says a frame is 1000/H and not a budget. 1044.001 (Astra's draft)
sets an ordinary cold-jump target of correct content at p95 ≤100 ms, with no
event-handling span over 4 ms. `complete` does not meet the 4 ms span: an owed
row is built in the frame that needs it. Today's measured jumps take 25–29 ms
and are never blank (1044.000 final scoreboard). That is the trade D1 accepts.

Closing it needs owed rows to be built off the frame, either by resumable rows
or by moving work off the main thread. 1044.000 §5 item 8 keeps the engine on
the main thread until a 120 Hz run proves otherwise. This RFC amends neither
plan. It records which of their bars the default does not meet, and why.

## 3. Is a policy the best thing to want?

Ranked by what they remove, largest first:

1. **One engine with a budget** (stage 1). Collections build their whole
   window per report with no row limit on any host (LLP 1050 §4). Giving them
   the windowed list's `limit` and pump removes most hitches before any policy
   exists.
2. **Landing first** (stage 4). At release iOS says where a fling stops.
   Building that viewport during the coast turns "arrive at an unbuilt
   region" into "arrive at a built one". It helps `complete` as much as
   `auto`, because the landing is owed on arrival under both.
3. **Cheaper rows.** For wide tables the likely fix is building only the
   visible columns. A 256-column row on a phone shows perhaps 4–10 of them
   (*inference*; the table's time has not been profiled). View reuse can save
   the presenter's share of each built row. 1044.000 measured roughly 0.5 ms
   runner and kernel against 0.35 ms presenter per created view, so reuse is
   worth at most about 40% (`QUEUE.md:135–137`). Each is a later decision (§7).
4. **The policy** (stages 1–4). It decides what to give up once 1–3 are
   exhausted.

## 4. One abstraction, not a library per policy

- **The shared parts are the product.** Keys, the height index, anchor
  correction, focus and interaction pins, `aria-setsize`/`posinset`, logical
  selection and copy, `reachstart`/`reachend`, and the agent's settle are where
  list bugs live. A second library duplicates all of them on four hosts.
- **We already run the counter-example.** The windowed list and the collection
  have drifted: only one has a row budget, a coverage rescue and velocity, and
  Linux wires only one (LLP 1050 §4). `QUEUE.md`'s "One list engine" item
  records the direction to merge them.
- **The strongest opposite case** (Astra and Grok steelmanned it): wrap each
  platform's recycling list for `auto`-style lists, and keep a synchronous
  engine for `complete` lists. That avoids a gesture classifier. It still
  loses. The policies differ only in which visible rows are owed during a
  fling, one row of §2.1's table. Two engines would re-implement everything
  else, and the platform lists cannot hold our runner-owned rows, pins and
  logical selection.
- **What legitimately differs is layout.** Grids, masonry and inverted chat
  are not this engine today (`collection/index.rs:250–285` is one vertical
  interval), and `rules/DEFERRED.md` still refuses virtualList v2. Visible-
  column windowing (§3) would be the first layout extension, taken on its own.

## 5. The author's surface

```
list virtualized=true fill-policy="auto" flex=1
  each m in history.rows key=m.id
    MessageBubble(message=m)
```

- `fill-policy`: `"complete"` (default) or `"auto"`. It is kebab-case like the
  list's other host-policy attributes (`item-height`,
  `estimated-item-height`, LLP 1010 §6.2), which are not CSS either. CSS has no
  such property.
- r1's `smooth` (never wait, even at rest) is dropped: it collided with CSS
  `scroll-behavior: smooth`, and no app has asked for it.
- There is no budget knob. The slice comes from the refresh interval
  (`ScrollPumpIOS.swift:28`: `min(4 ms, max(1 ms, 0.24 × frame))`).
- A pending interval shows the list's own background, as a browser
  checkerboards. r1's authored `pending` block is deferred (§7, later).

## 6. Mechanics

- **The runner stays deterministic and the host owns time**, as on the
  windowed path. The host turns its slice into a row count from measured
  per-row cost (`FillCost.rows(in:)`, `ScrollPumpIOS.swift:44–48`).
- **`CollectionFeedback` becomes version 2.** Today it is version 1
  (`collection/api.rs:89–92`). There are three encoders: web by hand
  (`collection-glue.js:15–24`), Apple by hand (`Collection.swift:20–30`), and
  Linux in Rust (`presenter/collection.rs:669–703`). It gains:
  - the signals of §2.2;
  - `velocity`;
  - `rest`: a platform rest offset, or none;
  - `limit: Option<u32>`, the rows this report may create beyond the owed set.
    `None` means unlimited and `Some(0)` means none. This replaces the
    windowed path's two encodings: Apple's "0 = whole window, n = n−1 extra"
    (`host/apple/src/abi/exports.rs:302–305`) and the web's "0 = whole window,
    n = n extra" (`host/web/src/abi.rs:408`).
- **Build order.** Pins, then the owed set, then the landing viewport (when a
  rest offset exists), then optional visible rows, then the lead, then the
  rows behind. The build stops at `limit`.
- **The reply carries pending intervals**: logical offset ranges of visible
  rows not built. Each is tagged with the collection revision and row epoch
  the existing seam uses (`collection/api.rs:17–39`, `collection/mod.rs:534`),
  so a stale interval is rejected like stale feedback.
  - A reply with pending intervals schedules its own continuation. Hosts must
    not suppress the next report as identical (`Collection.swift:300`,
    `collection-glue.js:130`).
  - Obsolete landing work is cancelled when the rest offset changes or a new
    touch begins.
- **Cost memo (D3).** The runner keeps a per-key cost (kernel nodes created)
  for rows it has built, and a per-template average for new keys. A row whose
  known cost exceeds the host's slice is left out of the owed set during
  motion. A monster row the runner has never built costs one late frame the
  first time. That is honest, and resumable rows are what would remove it.
- **Retirement follows the windowed path's real rule** (`window.rs:696–701`).
  Every leaving row retires when `defer_retirement` is false, which happens
  when the port size, origin or width changes or the pins change
  (`window.rs:777–803`). Otherwise up to `max(2·limit, 4)` retire with a report
  that creates, or once nothing is left to create — and a row more than two
  viewports from what shows retires with any report, a rescue's included:
  travel faster than slices retire (96k pt/s on the iPad) otherwise kept every
  row it passed, 1,750 views and 124 MB of text rasters. A disjoint landing interval
  is retained, bounded to one viewport, until the coast ends or is cancelled.
  As built, a collection's report also retires enough that the rows kept
  past the window never outnumber the window's own (2026-09-26): travel that
  outruns the fill makes every report a rescue (`limit` 0), which retires
  none, and each one kept a viewport more until the list stopped — about a
  thousand rows, each with a canvas's Metal layer and surface, at 48,000 pt/s
  on an iPad (`collection/fill_tests.rs`).
- **Anchors.** No correction is applied against estimated rows while the user
  is dragging or a fling is coasting. That matches iOS today, which drops the
  correction then rather than queuing it (`CollectionIOS.swift:66–69`). After
  rest, a correction applies only if a mounted anchor row actually moved.
- **Pending and input.** A pending interval takes no hits (`pointer-events:
  none`) and is not in the accessibility order. An accessibility, keyboard or
  focus move into it is an owed move (§2.1), so the target row is built before
  it is announced. Selection and copy keep the existing logical path, which
  realizes unmounted rows without publishing them (`runner/src/instance/text.rs:1`,
  `:48`).
- **Web authored jumps wait.** Today the glue assigns `scrollTop`, then commits
  the collection (`host/web/glue.js:802–808`), and the flush waits for the
  next animation frame (`collection-glue.js:69`). That is proposed to change:
  build the target rows first, then assign `scrollTop` in the same task.
- **The agent (LLP 1012).** `state` may list each list's current pending
  intervals, which are a function of the report. Frame counts (holes, late
  frames) stay in host signposts, because the runner neither presents frames
  nor reads a clock. There is no new agent operation: tests of policy use
  runner tests with explicit `limit` and signals. `clock settle` fills the
  owed set and the window as today, whatever the policy.
- **Amendment.** On native hosts, LLP 1010 §6.2's "rows the reader can see are
  never rationed" (`runner/src/runner/lists.rs:92`) is amended in exactly two places: `auto`'s
  fly-over, and D3's overload row. The web's user-scroll deviation is declared
  in LLP 1010.

## 7. Stages

Each stage lands with a measurement against the previous one. No stage adds an
in-repo benchmark app or harness without Charlie's approval (`rules/RULES.md`,
Agents); measurement uses the out-of-repo probes and signposts 1044.000 used.

| Stage | What | Done when |
|---|---|---|
| 1 One engine, `complete` | The QUEUE item: collections get `limit` (v2 feedback), velocity, the coverage rescue, the real retirement rule and the pump on iOS. Web collections pass velocity. On macOS the mounted window becomes `preparedContentRect` (D5). The legacy list is deleted *after* parity, in its own change | 1044.001 Slice F's gates hold on the collection: selection, full copy, focus and interaction pins, nested scrolling and anchors. The collection matches the windowed list's hitch and blank numbers on the 1044.000 probe. The Markdown reader runs on it |
| 2 Web authored jumps | Build, then assign `scrollTop` | An authored web jump never paints the new offset before its target rows exist (web agent test) |
| 3 Overload rule (D3) | Cost memo; costly rows pending during motion under both policies | On the 256-column table (*which input produced the recorded 3–5 fps is to be confirmed first*): no frame longer than two refresh intervals during a fling; correct content ≤500 ms p95 after rest (1044.001's overload bar) |
| 4 `auto`, opt-in | Signals; optional fly-over rows; landing first on iOS, velocity projection elsewhere; background pending band | Runner tests pass for each row of §2.1 with explicit limits. A physical 120 Hz iPhone run reports hitch time and blank area for `complete` vs `auto` on the corpus: the evidence for any default flip (D1) |
| Later, each its own decision | An authored `pending` placeholder; view reuse (with a host reset contract: editors, composition, rasters, media, accessibility focus); resumable rows; visible-column windowing | — |

View reuse landed on iOS first (2026-09-25, `NodePoolIOS.swift`, whose header
is the reset contract). A collection row the batch destroys whole parks its
views, hidden, in the list; a row created in a later batch with the same
shape takes them under its new ids. The runner is unchanged: ids are never
reused. Editors, media, canvases, materials, recognizers, focus, projected
swipe rows and anything in motion make a row ineligible rather than reset.
On listbench's simulator fling it took the presenter's share of a built row
from 1.23 to about 0.7 ms (Time Profiler over the fill slices), leaving the
runner's layout and the batch decode as the larger half.

Linux gains a fling when its host does (LLP 1015). Until then it produces
only wheel and authored signals.
