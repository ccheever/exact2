# LLP 1069.008.000: HealthKit grants — a device row that needs a signature, two prompts, and an App ID prefix

**Type:** RFC
**Status:** Draft r2
**Systems:** Grants (`runner/src/device.rs`'s `DEVICES` and `device_grants`); Bake (`bake/src/reach.rs`: `reach.usage`, `reach.entitlements`); Apple build (`host/apple/build.mjs`: `entitlements()`, the simulator's `__entitlements` section, the device signing profile); Durable store on simulators (LLP 1018: the Keychain's default access group); native modules (LLP 1067), which do the HealthKit work
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-10-05
**Revised:** 2026-10-06, r2: astra and grok's reviews folded (`llp/reviews/rfc-2026-10-06-1069.008.000.*.md`): a write-only app gets its read key too (D1); the Keychain carry-over measured (D3); an explicit App ID profile is preferred and required (D4); macOS gets the usage keys and no entitlement, tvOS gets neither (D5); a Health app's kept answers are neither seeded nor left on disk (D7)
**Related:** LLP 1069.008 (permissions from grants: D1's grammar, D2's table, D4's derived outputs, which this extends); LLP 1069 §5 #8 (contacts, calendars and the like get rows "when a module needs them"); LLP 1067 (Swift native modules); LLP 1018 (`secret.keep` and the Keychain); LLP 1027 D4 (kept answers, which must not carry Health data off the screen); Nathan Brooks' Expo port feedback, 2026-10-05 (`framework-feedback.md` "Derive HealthKit grants into the installed Apple application", "Generate a valid simulator identity"; his fork's repair is in `maintainer-handoff/framework-tracked-diff-from-fa301522.patch`)

## Summary

The Brooks port's Shoe Finder reads a person's recent runs, walks and steps
from Apple Health, through its own Swift module. On main the app does not
build: `device.health` is not a row in `DEVICES`, so the bake refuses it
(`grant-device`). Adding the row is not the one table entry LLP 1069.008 D2
promised for a new device, for three reasons:

1. **HealthKit needs an entitlement in the signature.** Usage strings are
   not enough: without `com.apple.developer.healthkit` in the code signature,
   `HKHealthStore.requestAuthorization` fails. Today no iOS row carries an
   entitlement (`reach.rs`: "iOS needs none today").
2. **HealthKit has two prompts.** `NSHealthShareUsageDescription` (read) and
   `NSHealthUpdateUsageDescription` (write) are separate texts, and D1's
   grammar gives a device grant exactly one purpose key.
3. **HealthKit reads the App ID prefix.** A simulator build is signed ad hoc,
   and main writes its `application-identifier` as the bare bundle id
   (`entitlements(app, null)`). HealthKit takes the part before the first dot
   as the 10-character Team ID prefix and records the app under the
   remainder.

This RFC adds two rows, `device.health-read` and `device.health-write`, an
iOS entitlement column in the device table, a simulator App ID prefix that
keeps old Keychain items readable, and a device-build refusal when the
signing profile lacks the capability. Exact2 gains no Health data API: an
app's native module calls HealthKit, as the Brooks app already does.

## Motivation

**A real app needs it.** Health is the input to the Brooks port's Shoe
Finder: an Expo app at parity on every other screen. Its fork's repair
passes positive and denied trials on the simulator, including Settings ›
Health showing the app under its own name and turning its reads off
(`framework-maintainer-actions.md`, "Derive HealthKit authority into the
installed application").

**The failure modes are bad ones.**
- Missing entitlement: authorization fails at runtime. The app built, signed
  and launched, and nothing said why.
- Missing App Store purpose key: Nathan reports that App Store Connect
  refuses a binary that has the HealthKit entitlement without both purpose
  keys, even one that only reads (ITMS-90683). Not verified here.
- Wrong App ID prefix: the person sees a garbled source name in Health and
  Settings, and the permission rows do not line up with the app.

**The machinery is already there.** LLP 1069.008 derives usage strings,
macOS hardened-runtime entitlements and the web's `Permissions-Policy` from
one grant line, and puts the grant ceiling in the compatibility id, so a
bundle cannot add a device an installed binary lacks. HealthKit needs the
same derivation with one more output column.

## Design

### D1 — Two rows: `device.health-read` and `device.health-write`

```ts
// app.ts
export const grants = `
device.health-read purpose.healthRead
`;
```

| grant | iOS `Info.plist` | iOS entitlement | macOS | web `Permissions-Policy` |
|---|---|---|---|---|
| `device.health-read` | `NSHealthShareUsageDescription` | `com.apple.developer.healthkit` | none | none |
| `device.health-write` | `NSHealthUpdateUsageDescription` | `com.apple.developer.healthkit` | none | none |

- This keeps LLP 1069.008 D1's grammar: one capability, one target, a
  strings key. Each prompt's text is its own key, so each stays truthful and
  translatable.
- The names are a declared deviation (1069.008 D2): the web has no Health
  permission. They follow HealthKit's own share/update split, spelled as
  read and write.
- **One row granted still writes both keys.** If the App Store refusal
  above holds, a binary with the entitlement must carry both. When only
  `device.health-read` is granted, the bake writes `NSHealthUpdateUsageDescription`
  with the read purpose's text, every locale's, as `reach.usage` holds a
  usage key; when only `device.health-write` is, `NSHealthShareUsageDescription`
  takes the write purpose's. iOS shows a prompt only for the direction the
  app asks for, so the borrowed text is never seen. The reach table lists
  the rows granted, which is the truth.

*Rejected:*
- **One `device.health` row with two keys after it** (the fork's form,
  `device.health purpose.healthRead purpose.healthWrite`). It breaks D1's
  one-target grammar for one device, and a read-only app must still write a
  second text it never shows.
- **One `device.health` row with one key for both prompts.** The read prompt
  and the write prompt then say the same thing, and one of them is wrong.

### D2 — The device table gains an iOS entitlement column

`Device` in `runner/src/device.rs` gains `ios_entitlements: &[&str]`, empty
for every row but the two above.

- `reach.rs` collects them for `platform == "ios"` into `reach.entitlements`,
  the same field macOS's hardened-runtime entitlements already use. Each
  platform's bake writes only its own.
- `entitlements()` in `host/apple/build.mjs` adds each one as `true`, for a
  device build and for the simulator's `__entitlements` section alike.
- An app without a Health grant gets the same signature as today. Its
  compatibility id does not move.
- This column is the hook LLP 1069.008's `reach.rs` comment names for push's
  `aps-environment`: the next iOS row that needs an entitlement adds it here.

### D3 — A simulator App ID with a 10-character prefix, old Keychain items kept

A simulator build's `application-identifier` becomes
`SIMULATORX.<bundle id>` (10 characters, a Team ID's shape). Its
`keychain-access-groups` lists that, then the bare bundle id that main
writes today.

- **The prefix is for HealthKit,** which reads the identifier as
  `<Team ID>.<bundle id>`. The fork measured a 9-character prefix
  (`SIMULATOR.`) leaking into Health's source identity, and a 10-character
  one fixing it. Main's bare id splits the same way at its first dot
  (`com.exact.caltrain` as `com` and `exact.caltrain`), so it is the same
  class of misattribution (grok's review).
- **The second group keeps `secret.keep` working across the change.**
  Measured 2026-10-06 on an iOS 26.5 simulator with two ad hoc builds of
  one probe, entitlements in `__TEXT,__entitlements` as `build.mjs` embeds
  them, and ibex2's own queries (`darwin_keychain.mm`: no access group):
  - an item the bare-id build stored reads back under the new identity;
  - the new identity's `set` updates that item in place (the bare-id build
    then reads the new value), so no duplicate appears;
  - a new item goes to `SIMULATORX.<bundle id>`;
  - the bare id is accepted as a second group.
  A device build is unaffected; this is the simulator's ad hoc identity
  only.
- **Every simulator build changes, not just Health apps.** One identity rule
  for every simulator build is simpler than a second rule for Health apps,
  and a prefix is what a signed build has anyway.
- **A device build is unchanged.** Its prefix is the Team ID from the
  provisioning profile.

*Rejected:* writing the Team ID when one is configured on this Mac. A
simulator build would then depend on which Mac built it, and the Keychain
group would move between machines.

### D4 — A device build signs with a profile that allows the entitlement

The provisioning profile a device build signs with lists the entitlements
its App ID allows. The one `profile()` usually finds is the team's
wildcard (`<team>.*`), the profile Xcode installs for any app of the team,
and Apple never allows HealthKit on a wildcard App ID.

- When `reach.entitlements` is not empty, `profile()` takes only a profile
  whose own entitlements include every one of them, which means one for
  this bundle id, and prefers it however new a wildcard is.
- When none on this Mac does, the build stops before signing:

> `grant-device-profile: device.health-read needs com.apple.developer.healthkit, and no development profile on this Mac for <bundle id> allows it (a team wildcard never can). In the Apple Developer portal, register the App ID <bundle id> with HealthKit, make a development profile for it that includes this phone, and install it (or name it with EXACT_PROFILE).`

- `EXACT_PROFILE` (a release, `--unsigned`'s re-signer aside) is checked the
  same way.
- The alternative is a build that signs, installs and launches, then fails
  at its first authorization request. That's the failure this RFC removes.

### D5 — Other platforms

The bake accepts the grant everywhere, because an app is one source on
every host.

- **macOS gets the two usage keys and no entitlement.** HealthKit exists on
  macOS 13 and later, and `isHealthDataAvailable()` reads the OS, not the
  signature (grok's review), so a module's request can run there; without
  its usage key that request ends the app. The entitlement stays off: it is
  restricted on macOS, and a development build signed ad hoc or with a
  wildcard profile that carries one does not launch. A Mac's request then
  fails as unauthorized, which the module handles as unavailable.
- **tvOS gets neither.** HealthKit is not on tvOS. A tvOS build bakes the
  iOS plan (`build.mjs`: `--tvos` bakes as `ios`), so the row says it is
  not on TV and the build drops its keys and entitlement for a tvOS
  destination (both reviews).
- **The web, Linux and Windows** get nothing; there is no Health there.
- iPadOS gets the iOS derivation; Health exists there.

### D6 — Scope: no Health API in exact2

Exact2 ships no Health data source in this RFC. The grant makes the binary
able to ask. An app's native module (LLP 1067) owns the queries: the types,
the date ranges, the statistics.

- This matches LLP 1069.008 D3: a native module's reach is declared, not
  enforced. The runner never sees HealthKit calls.
- A first-party `health` source (TypeScript, typed queries, agent
  substitutes) is a separate RFC, and nothing needs it yet. The Brooks
  module's three reads are the use case to start from.

### D7 — Health answers stay off the disk

A resource that reads the store keeps its last answer for the next launch's
first frame (LLP 1027 D4), in the store's `exact.kept.*` entries. If that
answer carries Health data, the data sits on disk across launches, outside
HealthKit's own protection. The Brooks port found exactly this: its Finder
state read the store, and a fixture-derived Health summary was kept in
`exact.kept.finderState`.

- Main now forgets kept answers that no declared reader seeds at a cold boot
  (`kept::obsolete`, 2026-10-05). That covers a reader removed or made
  transient, not one that is still a reader.
- This RFC's rule: an app with a `device.health-*` grant keeps no answers.
  At every boot it seeds no first frame from `exact.kept.*` and forgets
  every such entry on disk, so an answer kept before the grant was added,
  or by an older build, goes too (both reviews: stopping new writes alone
  left the old ones seeding). Its first frame shows placeholders, as a ready
  source's does. A Health app that wants last launch's numbers on screen at
  once writes them to its own storage, choosing to. Open question 3 asks
  for a finer rule.

## Slices

1. **The Keychain carry-over** (D3): measured, above.
2. **Rows and entitlement column** (D1, D2, D5). Tests in `bake/src/reach.rs`
   for the usage keys, the read-only update key and the iOS entitlements;
   `runner/src/device.rs` for the names.
3. **Simulator identity** (D3). Test: an app that kept a secret under the
   old identity reads it after the change, on a simulator.
4. **Device refusal** (D4), against a profile without HealthKit.
5. **A fixture module and a drive.** A Health-reading Swift module in
   `apps/native-fixture`, authorized and denied on a simulator through
   Settings, with the agent's `tap @t allow` and `deny` (LLP 1069.007).

## Open questions

1. **Is ITMS-90683 real for a read-only HealthKit app?** Nathan reports it
   without a receipt. If App Store Connect accepts the share key alone, D1's
   generated update key goes.
2. **What Health shows for a simulator build** under the new prefix is
   still the fork's measurement, not this repository's; slice 5's drive
   records it.
3. **D7 is coarse.** A Health app keeps none of its answers, even ones with
   no Health data in them. A finer rule needs to know which answers carry
   Health data: a resource flag, or a native call that marks its reply
   sensitive.
4. **Clinical records and background delivery**
   (`com.apple.developer.healthkit.access`,
   `com.apple.developer.healthkit.background-delivery`) are left out. Their
   rows follow D2 when an app needs them.
