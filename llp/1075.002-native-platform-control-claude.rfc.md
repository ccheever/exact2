## Summary

James's patch was not blocked on calling UIKit. Swift in an app's module (LLP
1067.000) already reaches every public API on the main thread. The patch had to
change Exact for three things Exact holds:

- **its UIKit objects:** the route controller and its navigation item, the
  navigation controller, the route's scroll view;
- **its attribute vocabulary:** a schema row and a compiler entry per word;
- **state it shares with UIKit:** bar visibility, the scroll coordinates under a
  title, and which tab's UI stays alive.

His tab work adds a fourth: choosing the containers themselves.

This RFC recommends four things.

1. **Hooks (D1–D4, D9).** The app's one module receives Exact's own UIKit objects
   at defined moments: navigation controllers, route controllers and their
   navigation items, the tab container. A node hook is designed and waits for its
   first case.
   - The app's words travel as `data-*` attributes.
   - Code acts back through the web's verbs, or through a named action where
     there is no authored control.
   - Exact names what it owns and forwards the delegates it keeps.
   - One versioned surface, kept by a fixture app in the smoke.
2. **A public route-content seam (D5).** Route content is a controller that an
   app can place in containers it owns, while one session and its router stay
   the single authority. This is the escape hatch past Exact's containers that
   does not split an app into sessions.
3. **Exact's default containers, built on that seam (D6, D7).** These are a
   navigation bar with one bar per stack (titles first, collapsing large titles
   once the scroll mapping is solved) and a `UITabBarController` with retained
   tabs. The web keeps the same tabs mounted, hidden and inert. Anything that
   changes the content area while the user scrolls is Exact's.
4. **TypeScript by experiment (D10).** Once Stage 1 has built the hooks, bind
   them through NativeScript's engine-independent runtime and answer five
   questions before adopting it. UIKit-first apps with Exact screens stay a
   documented, coarser option (D11).

It declines five primary answers (§4, with the reasons 1075.000 records):

- a NativeScript-style bridge in place of the hooks;
- UIKit mirrored into Rust;
- string property paths in Contract;
- one Exact prop per platform property;
- "patching Exact is expected".

It asks Charlie for six decisions (§8).

## 1. Diagnosis: what James's patches need

| Part of the patch | What it needed | Here |
|---|---|---|

| Reading props in `RouteController.configure`; setting title, large-title mode, back-button mode and a trailing bar button on `navigationItem`; `prefersLargeTitles` | Exact's objects, at the right moment | the `navigation` and `route` hooks (D1) |

About a third of the navigation patch's 99 lines (the bar and navigation-item
configuration, and the press) become app Swift with no Exact change. The rest is
Exact's to build once, for every app.

## 2. Why not a bridge first

A language bridge changes which language calls UIKit. It does not hand anyone
the route controller (1075.000 F1). So James's TypeScript would wait for the same
seams D1 and D5 add, and would then have narrower reach than Swift:

- It reaches only APIs visible to Objective-C (E1).
- A UIKit callback into TypeScript has no path while Exact's runtimes live on
  `exact.owner`, for example a delegate that must return a value (F5, E8).
  Calls from TypeScript into Swift (`native.call`) already exist; callbacks the
  other way do not.
- Native behavior would arrive in TypeScript updates, which the delivery
  classifier treats as non-native (LLP 1030).

Swift reaches Swift-only frameworks, and agents write it readily. James did ask
for TypeScript access as an escape hatch, so D10 runs the experiment once the
hooks exist to bind.

What James asked for is a clean public API with careful breaking changes. That is
a property of the seam, not of the language on either side of it.

## 3. Design

### D1 — Hooks on the app's one module

`ExactModule` (`host/apple/modules/ExactNativeModule.swift`) gains hook methods.
Each runs on the main thread, called by the presenter after the batch that
created or changed its object is applied and before that frame is drawn. A title
set in a hook is therefore in the first frame its route shows (D8 makes that
possible at launch).

```swift
open class ExactModule {
    // views, later, call, destroy — LLP 1067.000, unchanged
    /// Each navigation controller Exact makes, once, before its first route shows.
    open func navigation(_ navigation: ExactNavigation) {}
    /// A route: when it mounts and when its data-* change.
    open func route(_ route: ExactRoute) {}
    /// Exact's tab container (D6), once.
    open func tabs(_ tabs: ExactTabs) {}
    /// Return a container to own the tabs yourself (D5); nil keeps Exact's.
    open func tabContainer(_ tabs: ExactTabContents) -> UIViewController? { nil }
    /// Designed here; added with the first node-level case (§6, Stage 5).
    open func element(_ element: ExactElement) {}
}
```

| Handle | Carries |
|---|---|
| `ExactRoute` | `controller: UIViewController`; `data: [String: String]`; `contentScrollView: UIScrollView?`, the one the route names (D4); `navigation: ExactNavigation?`; `element(_ id:)`, resolved within the route the way LLP 1035.001 D1 scopes a Back control |
| `ExactNavigation` | `controller: UINavigationController`; `showsBar` (D7); `delegate`, forwarded (D4) |
| `ExactTabs` | `controller: UITabBarController`; `delegate`, forwarded (D4) |
| `ExactTabContents` | each tab's content as a controller, the selected tab, and router intents (D5) |
| `ExactElement` | `view: UIView`; `id`; `data`; `click()`, `focus()`, `blur()` (D3) |

Rules:

- **Validity.** A handle is valid while its object lives. Using a stored handle
  after destruction does nothing and writes a journal line, as a module callback
  with a retired nonce is dropped today (LLP 1024 §9).
- **Scope.** The first surface is `navigation`, `route`, `tabs` and
  `tabContainer`. `element` is designed here so its shape is known. It is added
  with the first node-level case, because a stable `UIView` per hooked node
  constrains three things the presenter does:
  - how it draws: inert leaves are bare layers (LLP 1068 §6.1);
  - how it reuses: pooled rows (LLP 1068);
  - where it builds: rows off the main thread (LLP 1072).
- **Element views and reuse, when added.** A node with a declared `data-*` word
  is always a view. When a list row is reused, the hook runs again for the new
  data, and resetting what it set for the old row is the app's job, as a module
  view's `prepareForReuse` is.
- **Agent.** Under the agent, hooks run and the journal names each call, so
  `logs` shows what app code did. Whether a projection appears in its native or
  its authored form under the agent follows LLP 1021 D4, as today.

A hook is not an inheritance point. The presenter's classes stay private, so
nothing outside these handles becomes a promise.

### D2 — `data-*` is the app's vocabulary

HTML's mechanism for an author's own attributes is `data-*`. Admitting it means
a new word never touches `schema.json` or `tags.rs`.

- **Admission.** Contract admits `data-[a-z][a-z0-9-]*` on any element. All of a
  node's `data-*` attributes lower to one aggregate prop, a `dataset` row added
  once, through the `NativeProps` opcode LLP 1024 §9 already built: keys sorted,
  values carried as strings.
- **Declaration.** Each word is declared once in `app.json` (`"data": ["title",
  "trailing", …]`), as the module roster is. An undeclared word is a bake error
  that names the list (LLP 1017 P1: no quiet failures).
- **Web.** The words are real attributes on the element, and the page module
  reads `el.dataset`.
- **Naming.** Words name the app's meaning, not a platform property:
  `data-title`, not `data-ios-large-title`. A platform's hook decides what the
  word means there.

### D3 — Back into Contract

- **`click()` when the native item presents an authored control.** A bar button
  for the authored Compose button, or a header button shown as a bar item, is
  pressed the way a tap presses it (the patch's `presenter.press`). That is also
  the web's `HTMLElement.click()`. Contract's handlers decide.
- **A named action when there is no authored control.** In 1075.001 §3's words,
  a private lookup or a synthetic press is not the general public interface. A
  native control with no authored counterpart needs an action the component
  exports to its platform hooks, dispatched with arguments through the runner's
  normal event path. It is added with the first such case.
- `focus()` and `blur()` follow LLP 1035.001's focus rules.
- Each is queued and delivered after the batch being applied, never during it.
  That keeps them clear of the owner's re-entry rule (1075.000 F5).
- No hook writes Contract state directly. The app's data path stays `call`,
  `later` and topics (LLP 1067.000).

### D4 — Exact lists what it owns, names its scroll view, and forwards its delegates

Exact owns frames, scroll coordinates, and the structure of stacks and tabs. It
measures the content area its containers leave after hooks run (bar heights and
safe-area insets) and lays out inside it, as it does for `env(safe-area-inset-*)`.

- **Static geometry is the app's.** A hook may change a container's static
  geometry, because Exact measures again. Examples: a prompt, a search bar, a
  large title that stays large.
- **Continuous geometry is Exact's.** A hook may not drive geometry that changes
  while the user scrolls (a collapsing title, a hiding search bar) until Exact
  maps that change (D6).
- **The content scroll view is named.** A route names its content scroll view by
  HTML id, the way it names its Back control (`navigationBack="back"`, LLP 1038
  §6): `navigationScroll="list"`. `ExactRoute.contentScrollView` is that view,
  and D6 attaches it to the bar. Nothing searches descendants for it (1075.000
  E7).
- **Delegates are forwarded.** Exact keeps the navigation and tab controllers'
  delegate slots, because it reconciles pops and selection there (LLP 1035.001
  D1, D2).
  - Every delegate call goes on to the app's `ExactNavigation.delegate` or
    `ExactTabs.delegate` after Exact's own handling.
  - Methods Exact does not implement go straight to the app. Custom transition
    animators and interaction controllers are the main ones.
  - A custom transition must still dispatch Back exactly once when it completes
    and never when it is cancelled (Stage 1 acceptance).

| Object | Exact owns | The app may set |
|---|---|---|
| Node view (with `element`) | frame, bounds, center, transform, alpha, `isHidden`; the layer paint Exact draws (background, corner radius and curve, border, shadow, mask); subview order; the gestures and accessibility Exact derives | interactions (context menu, drag and drop, pointer, edit menu); its own gestures, under LLP 1057's precedence; input traits Contract does not set; anything not on the left |
| Scroll view | `contentOffset`, `contentSize`, `contentInset` and its adjustment behavior, `delegate`, `keyboardDismissMode` (a Contract prop), which one is the content scroll view | indicators, deceleration, `scrollsToTop`, anything not on the left |
| Route controller | its view and that view's subviews; how it is presented | the whole `navigationItem`; `toolbarItems` once a toolbar is projected |
| Navigation controller | `viewControllers`, the delegate slot, the pop gestures' delegates, bar visibility (D7), title collapse (D6) | bar appearance, `prefersLargeTitles`, tint; delegate methods, through forwarding |
| Tab container (Exact's) | its tabs and their controllers, selection, the delegate slot | appearance; minimize behavior, which Stage 2 checks; delegate methods, through forwarding |

In development the presenter snapshots the left column around each hook call and
journals each change by name, for example: `route inbox: the hook set
contentInset, which Exact owns`. Production does not check. The table lives in
code beside the hooks.

This revisits LLP 1035.006 12.08, which refuses "an uninspectable native object
bag". That refusal is kept for Contract: no native property names enter it, and
`data-*` values are the app's words. Native code stays in typed Swift, and every
hook call is visible in the journal.

### D5 — The route-content seam: an app may own the containers

Configuring Exact's containers needs a way past them when configuration is not
enough (1075.001 §4). r1's only way past was a UIKit-first app (D11), which
splits an app into sessions that share no live state, against James's wish to
share logic. The middle shape keeps one session, with its router as the single
authority, and presents route content in controllers the app owns.

- **Route content is a controller.** ExactKit vends each route's content as a
  public controller whose view is the route's subtree. Today's private
  `RouteController` is the implementation to promote.
- **The app's container sends intents.**
  - What the person did reaches the router as an intent: `select(tab)`,
    `back()`, `open(url)`. Exact applies the router verb (LLP 1038 D4) and moves
    the controllers.
  - A completed native change updates the router once, and a cancelled one
    leaves it unchanged.
  - The controller tree follows the router without echoing a second event
    (1075.001 §4).
- **Each route has its own content area.** A route lays out in its controller's
  safe area, not the session's viewport. A route in a split-view column or a
  tab is not viewport-sized. This is the same kernel work D6(a) needs for routes
  under a bar.
- **Containment is real.** This means `addChild` and `didMove(toParent:)`,
  appearance transitions, safe-area and keyboard propagation, focus, and
  teardown. The seam is a controller, not a view placed in a box (1075.000 E3).
- **Exact's own containers use it first.** D6's navigation and tab projections
  are built on this seam, not on private presenter classes, so the default and
  the escape hatch cannot drift apart. An app that returns its own container
  from `tabContainer` does what D6's tab projection does.
- **The web has no form of it.** Route content there is DOM. An app that owns
  its iOS container keeps the authored `tablist` for the web (D6), or exports
  page-module hooks of its own (D11).

### D6 — Exact's default containers and the geometry

The rule: if it changes the content area while the user scrolls, or keeps UI
alive off screen, Exact projects it. Both default containers are built on D5.

**The navigation bar, in two steps.**

- **(a) A title and bar items, inline or large but not collapsing.**
  - One visible bar per stack (D7).
  - Each route's content area is its controller's safe area (D5), measured
    after its hooks run. A fixed inset is a constant shift between UIKit's
    offset and CSS `scrollTop` (1075.000 F6).
  - The named content scroll view (D4) is attached for the scroll-edge effect.
  - This is most of what the patch wanted, and the hooks fill the items.
  - A route's first-class title is LLP 1035.001 D9's header-shaped route. This RFC keeps the
    ruling of 2026-09-10: the web paints the authored header and iOS lifts it
    into the bar. A `navigationTitle` prop would have no web form.
- **(b) Large titles that collapse.**
  - This solves LLP 1035.001 D9's open mapping once, in the scroll seam: native available
    area, content origin, a changing inset, and authored assignments and events.
  - Acceptance is 1035.001 D9's fixtures and LLP 1037 F1's checks (1075.000 §6).
  - Until (b) lands, a hook that sets a large title gets a large title that does
    not collapse.

**The tab container.** It is `UITabBarController`, with one navigation controller
per tab and the live tabs' stacks retained. That is LLP 1038 §7's "one navigation
owner per tab".

- **Contract.** Screens become `each` over every visited tab's stack, not only
  the selected one (`stack(nav)`). Each route node carries its tab, as it
  carries `navigationKey`.
- **iOS.**
  - Each tab's routes go to that tab's navigation controller through D5.
  - The authored symbol-over-label `tablist` supplies the items. This is LLP
    1059's shape rule, projecting to the controller instead of to a bar inside a
    box.
  - Reselecting a tab pops it to its root (1038's `select`).
  - The `tabs` hook configures appearance and minimize behavior.
- **Web, macOS and Linux.**
  - Unselected tabs' routes stay mounted, hidden and inert: the existing rule
    (1038 D6), applied to every retained tab.
  - So scroll positions and drafts survive a switch.
  - A switch is a history entry (LLP 1038 D12).
  - The bar is the authored `tablist`: at the bottom on a phone, a rail on a
    desktop (LLP 1039).
- **Lifetime.**
  - Retained means each live tab's current stack. A popped screen is released,
    as UIKit's are.
  - Hiding a tab does not cancel its work. Destroying a route drops its
    callbacks, so none reaches a successor.
  - Values that must outlive a screen belong in state, not in a view that
    happens to be retained.
  - Behavior under memory pressure is tested (Stage 2).

This answers James's "I'm not sure how this all works on web": the same Contract,
retention by hide-and-inert, and the authored bar. Expo Router's native tabs left
the web to "a basic implementation" (1075.000 E6). This does better because the
`tablist` was authored for the web in the first place.

James's "each tab specifies its view controller type" has three answers, in
increasing reach:

- **Structure.** A tab with a stack is a navigation controller.
- **A route-level module.** A tab whose content is genuinely native is a route
  whose content is a module tag whose factory returns a `UIViewController`
  (LLP 1024's factory, one level up). On the web the same tag is a custom
  element.
- **The app's own container,** through D5.

### D7 — One bar per stack

Bar visibility is `ExactNavigation.showsBar`, a property of the stack. It is
never toggled per route across a transition, the toggle DartNative removed to
end its blur flash (LLP 1037 F1). A route without a title leaves the bar empty.
Hiding the bar for one route (a photo viewer) is a later, explicit request with
LLP 1037 F1's checks as its acceptance, not the default. An app that owns its
container (D5) owns this choice too, and that lesson with it.

### D8 — The first frame: two options, measured

Today the module artifact is opened at the paint gate, the turn after the first
drawn frame (LLP 1024 §9). A bar item set one turn late appears as a pop-in.
1075.001 §7 asks that the fix be specified and measured, never a silent move of
work onto the boot path. There are two options:

- **(a) Open the module early.** An app whose `app.json` declares hooks opens
  its module before its first layout. The cost is `dlopen` and the
  initialization of the whole module's Swift image.
- **(b) Link the hooking Swift into the host.** There is no `dlopen` on the boot
  path, but this brings back the static Swift path LLP 1067.000 removed in favor
  of one artifact.

`boot.mjs` and `metrics.mjs` report both for a hooking fixture before one is
chosen. Apps that declare no hooks do not change, and no JavaScript moves before
first pixel either way.

### D9 — One versioned surface

The surface is:

- the hook methods and their handles;
- the route-content seam and its intents (D5);
- D4's table;
- the timing rules in D1 and D3.

The presenter's internals stay free to change.

- **Versioning.**
  - The Swift API is versioned with ExactKit.
  - The module table grows by size, as `prepare_for_reuse` did (offset 104,
    `size ≥ 112`, LLP 1067.000 D2).
  - A removed or changed entry is a new major, refused by name at load, as
    today's "module ABI 1, host ABI 2" is.
- **Kept by a fixture.** `apps/native-fixture` grows a hook module that
  exercises every hook, the seam and D4's conflict journal. `smoke.mjs` runs it
  on iOS, macOS and the web, so a release that breaks a hook fails the smoke
  instead of an app.
- **Deprecation first.** A changed hook ships beside the old one for one release,
  with a journal line naming the replacement, before the old one is removed.

This contradicts `rules/DEFERRED.md` ("No backwards compatibility, at all, before
1.0. No public API stability.") for this surface alone (§8 Q1). Without the
promise, hooks still save the patch's schema and compiler edits, but James's
upgrade concern stands. Naming the boundary and announcing breaks would help.
Only the fixture makes a broken hook fail before an app does.

### D10 — TypeScript, by experiment

James asked for native members from TypeScript as an escape hatch. After Stage 1,
bind D1's and D5's handles into TypeScript through NativeScript's
engine-independent runtime (`napi-ios`, 1075.000 E1), in an experiment that
answers 1075.001 §6's five questions:

1. **Runtime.** Does it run on Exact's Hermes (the pinned, bytecode-only build),
   or need another runtime, and at what cost?
2. **Thread.** Where does native-facing JavaScript run, and how does UIKit get
   an immediate delegate result without re-entering the owner (F5)?
3. **Lifetime.** Who retains a UIKit object or a JavaScript callback, and what
   invalidates a handle on reload, unmount or session end?
4. **Cost.** Do only the apps that use it pay for metadata and bridge code? Build,
   first-pixel, binary and interaction costs are measured.
5. **Limits.** Which APIs need an SDK or metadata rebuild, which still need
   Swift, and how is the author told?

During the experiment, immediate decisions stay in Swift. Question 2 is expected
to decide it: every precedent for synchronous native calls ran the language on
the main thread (E8). If the experiment fails, Swift hooks remain the answer, and
generated selective adapters are compared next (1075.000 E4).

### D11 — The other hosts, and UIKit-first

- **Web.** `modules/web/index.js` may export the same hooks, receiving DOM
  elements (`route(el, data)`, and `element(el, data)` once added). `click()`
  and `focus()` are the DOM's. Most web hooks are empty: a large title has no
  web form, so the authored header paints (LLP 1035.001 D9).
- **macOS.** The same Swift hooks with AppKit objects where the host has them.
  macOS does not project routes, so the route and tab hooks do not run there.
- **Linux.** No module, so no hooks. The authored tree is what renders.
- **Android, later.** Kotlin hooks with the same names.
- **UIKit-first.** A UIKit app with Exact screens is a documented adoption path:
  `ExactApp`, `ExactSession`, `ExactView`, and commands to
  `ExactSessionDelegate`. That shape is already driven by `smoke host-ios`
  (1075.000 F10). It is the coarse option.
  - Each surface is a session.
  - Sessions share the app's durable store (LLP 1031) but no live state.
  - The shell is laid out per platform.

  The documentation says so, and states the per-session cost, measured before
  the page is written. D5 is the fine-grained option.

## 4. What this declines

| Option | Declined as the primary answer because | Kept for |
|---|---|---|
| NativeScript-style bridge instead of hooks | It needs D1's and D5's objects anyway (F1). It reaches only APIs visible to Objective-C (E1). UIKit callbacks into TypeScript have no path while runtimes live on `exact.owner` (F5, E8). It brings metadata and FFI weight, and native behavior in TypeScript updates. | D10's experiment, binding the same handles, after Stage 1 |
| UIKit mirrored into Rust | It exists (`objc2-ui-kit`, E2) and is the wrong language for app code: `unsafe` throughout, reaches only APIs visible to Objective-C, few examples. | Implementations inside Exact |
| String property paths or setters in Contract | Untyped, set properties only (a bar button needs an action), and the bag LLP 1035.006 12.08 refuses (E5). | Nothing |
| One Exact prop per platform property | It is James's current problem: a framework change per request. | Behavior every app wants and Exact must project anyway (titles, tabs) |
| "Patching Exact is expected" | The cost is rebasing, not writing (1075 §2.2, F9's ids). | Changes to containment, which come upstream as PRs we land |

## 5. James's two patches under this RFC

The navigation patch, once Stage 1 and D6(a) land. In Contract:

```
column navigationKey=`${e.id}` navigationScroll="list" data-title="Inbox" data-trailing="compose" data-trailing-symbol="square.and.pencil"
  scroll id="list"
    …
  button id="compose" press=newMessage
```

In `modules/apple/App.swift`:

```swift
final class App: ExactModule {
    override func navigation(_ navigation: ExactNavigation) {
        navigation.showsBar = true
        navigation.controller.navigationBar.prefersLargeTitles = true   // stays large until D6(b)
    }
    override func route(_ route: ExactRoute) {
        let item = route.controller.navigationItem
        item.title = route.data["title"]
        item.backButtonDisplayMode = .minimal
        if let id = route.data["trailing"], let symbol = route.data["trailing-symbol"] {
            item.rightBarButtonItem = UIBarButtonItem(image: UIImage(systemName: symbol),
                primaryAction: UIAction { _ in route.element(id)?.click() })
        } else {
            item.rightBarButtonItem = nil
        }
    }
}
```

The tab patch becomes D6's container, built in Exact on D5, with the `tabs` hook
for what the controller offers beyond structure. If James's tabs need controllers
Exact does not project, his app returns its own container from `tabContainer`.
Exact still owns the routes and the router, and the web still gets the authored
`tablist`.

Neither change lands in the app as a patch. The next static case (a context menu
on a row, `textContentType` on a field, a search controller) is a hook, not a
release. The first such node-level case is what adds `element`.

**Stage 0 — reproduce.** James's two cases are reproduced at a pinned revision,
in his app or a fixture, with the probes in 1075.000 §6, before anything is
attributed.

  - D4's conflict journal and delegate forwarding;

  - The patch's title, trailing button and minimal Back run as app Swift with no
    Exact edit.

  - First-pixel numbers are reported for D8 (a) and (b).
  - An undeclared `data-` word fails the bake by name.

**Stage 2 — the seam and tabs.**
- Scope: D5; D6's tab container built on it; retained tabs on every host; the
  `tabs` and `tabContainer` hooks.
- Acceptance:
  - A scroll offset, a draft and a pushed screen survive a switch away and back,
    on iOS and the web.

  - An inactive tab updated while hidden shows the update when selected.
  - Unmount and remount work.
  - A session destroyed with work outstanding delivers no late callback to a
    successor.
  - Memory is measured with every tab visited, and under a memory warning.
  - A custom controller hosting one route works through public API only.
  - Minimize behavior is checked for whether it moves the content area.

**Stage 3 — the bar.**
- Scope: D6(a) and D7, then D6(b).

  - LLP 1035.001 D9's assignment fixtures (header heights 74, 106 and 148) against the

## 7. Costs and risks

- **The seam is the largest piece (D5).** Per-route content areas and real
  containment are kernel and presenter work, and they widen what D9 must keep
  stable.
- **A promise to keep (D9).** Every presenter change near a hooked object or the
  seam pays review and fixture time.
- **Forwarded delegates can disturb pop reconciliation.** Stage 1's transition
  check guards it.
- **Hooks can still misbehave in ways Exact cannot see.** A gesture that steals
  touches is one example. The journal helps diagnose; it does not prevent.
- **Retained tabs hold memory**, as UIKit's do.
- **A first-frame cost for hooking apps (D8),** whichever option is chosen.
- **`data-*` is a channel of strings.** Declaration and the bake check bound it.

## 8. Decisions for Charlie

1. **Compatibility.** Should the hooks and the seam (D9) be the one public
   surface, with deprecation before removal, despite `DEFERRED.md`? Or hooks
   without a promise?
2. **`data-*`.** Admit it in Contract, with declared words (D2)?
3. **First frame.** Open a hooking app's module early (D8 a), or link its hooks
   into the host (D8 b), chosen after measuring both?
4. **Titles.** Keep 2026-09-10's ruling, as recommended here (titles through LLP 1035.001
   D9's header-shaped route, items through hooks)? Or admit a title prop like James's?
5. **Retained tabs.** Render every visited tab's stack and keep it mounted (D6),
   accepting the memory?
6. **The seam first.** Build Exact's tab container on the public route-content
   seam (D5) rather than privately? It costs more up front, and it keeps the
   default and the escape hatch from drifting apart.

## 10. Relation to 1075.001

r1 was written after reading 1075 and 1075.000, and without reading 1075.001.
r2 was revised after reading it.

**Agreed from the start:**
- Swift hooks that hand app code Exact's real UIKit objects, with Apple's names,
  behind a small supported boundary.
- Configuration first.
- UIKit containers for tabs, with state retained and reproduced first.
- No UIKit mirror in Rust.
- No patching as the interface.
- No more one-off props as the only answer.
- TypeScript after Swift.
- Revisiting LLP 1035.006 12.08 and `DEFERRED.md`'s rule for one narrow surface.

**Taken from 1075.001 in r2:**

| From 1075.001 | Here |
|---|---|
| §4: an app may supply controllers or own its container; one logical navigation state; the session shapes | D5, and D6 built on it; D11's sharper account of UIKit-first |
| §3: an intentional delegation boundary, not an overwritten delegate | D4's forwarding |
| §3: an explicit way to name the route's content scroll view | D4's `navigationScroll` |
| §3: exposing every internal view at first is premature | D1's narrower first surface |
| §6: the NativeScript interop experiment and its five questions | D10 |
| §7: a deliberate first-frame construction path, host-linked Swift among the options | D8 (b) |
| §5: operation lifetime and memory pressure | D6's lifetime rules |
| §9: keyboard, inactive tabs, destruction with work outstanding | §6's acceptance |

**Still different:**

- **Geometry.** 1075.001's sketch has the app call `setNavigationBarHidden` and
  `setContentScrollView` on Exact's scroll view. That is LLP 1035.001 D9's stopped mechanism
  (1075.000 F6) plus the per-transition toggle LLP 1037 F1 warns against.
  Taken literally, it gives an inset two owners, which its own "one owner per
  inset" invariant rules out. Here bar visibility belongs to the stack (D7) and
  continuous geometry belongs to Exact (D6).
- **How app data reaches a hook.** 1075.001 says it must and leaves the
  mechanism open; its example hard-codes the title. Here it is `data-*` (D2).
- **How the promise is kept.** 1075.001 asks to identify the boundary and
  announce intentional source breaks. Here a size-versioned table, a fixture in
  the smoke and deprecation before removal make a broken hook fail before an
  app does (D9).
- **Presses.** Both avoid synthetic presses as the general interface. Here
  `click()` stays the right call when a native item presents an authored
  control, and a named action covers the rest (D3).
