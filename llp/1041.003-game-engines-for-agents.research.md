## Recommendation

**Track PlayCanvas and Babylon.js actively; retain Godot as the native-capable
control and Three.js as the renderer control.** The full-game follow-up in
§7 is now actual implementation and independent gameplay evidence: PlayCanvas
and Babylon pass the complete suite; Godot completes the physical winning
route but fails a large clock advance after restart; the Three.js/Cannon
implementation fails collision and crate gameplay. Those failures belong to
these implementations and adapters, not every possible use of those engines.

For the next **source-driven agent experiment**, start from the working
Babylon game, and keep PlayCanvas beside it as the smaller web payload.
Do not select an engine from the small timing sample alone, or treat an
untested vendor MCP workflow as the cause of a source-code trial result.

Do not keep all ten in a recurring matrix. **Defold is the first engine to
reopen when 2D becomes an actual consumer; Phaser is the web-only 2D
alternative.** Unity is a release-triggered watch, especially its new CLI
and Pipeline tooling. LÖVE, KAPLAY and Pygame have useful lessons, but no
recurring evaluation slot for the present product.

This is a **research tracking decision**, not an engine adoption decision.
Sections 2–3 preserve the earlier microfixture results; §7 reports the full
Lanterns follow-up and separates independent model attempts from evaluator
reruns. Full native/phone performance and vendor-hosted agent workflows remain
unmeasured. Five replays of one solution are still not five agent attempts.

## 1. What agentic use means here

An agent must be able to edit a real project, run the changed game, drive
input, inspect authoritative state, and produce a proof that would fail
if its change were wrong. The useful comparison has five separate costs:

1. **Setup:** engine downloads, accounts, imports, editor connection and
   adapter authoring. Amortize these separately from subsequent edits.
2. **Authoring:** source and scene changes the agent can express and review.
3. **Control:** inputs, fixed steps, timers, animation and physics under a
   known clock. A headless flag alone supplies none of these guarantees.
4. **Evidence:** live object state, failures, logs and targeted pixels.
   A custom JSON mirror that agrees with itself is insufficient.
5. **Shipping:** the actual web/native game, its assets, size, first world
   frame, memory and frame-time distribution on the intended hardware.

An MCP server improves tool access; it does not establish correctness,
determinism, cheap iteration or a controlled world clock. Conversely, an
engine without MCP can be easy to use through text files, a CLI and a
small app-specific inspection function. Both paths deserve a fair trial.

## 2. First pass: microfixture method and fleet

Three research workers used the same inherited model and separate Linux
machines, with procedural geometry and no external art. The fixtures
were constructed separately for browser 3D, browser 2D and native 2D;
they are not equivalent implementations of Lanterns. Godot's probe was
2D, so it supplies no head-to-head Godot-versus-browser-3D performance result.

| Fleet machine | Assigned work | Preflight |
|---|---|---|
| `expose-builder-pixel` | Three.js, Babylon, PlayCanvas; Unity CLI inventory | load 0.54; 247 GB available RAM; 36 GB free disk |
| `expose-builder-pixel-a` | Phaser, KAPLAY | load 0.04; 126 GB available RAM; 100 GB free disk |
| `expose-builder-nothing` | Godot, LÖVE, Defold, Pygame | load 0.12; 125 GB available RAM; 313 GB free disk |

The minisforum had no free disk and was excluded. SSH aliases were stale;
the live Tailscale addresses reached the builders. Existing checkouts
were not cloned or modified. Each lane used an isolated temporary
directory; compact source and evidence are retained with this research.
The run occurred September 17 Pacific time / September 18 UTC.

**Baseline:** move a procedural player through three collectibles, advance
explicit ticks, read real engine objects, reset, and repeat the proof five
times. Browser 3D rendered through Chromium/SwiftShader; native headless
probes did not establish rendered output. The lanes' ticks and input
routes differ and are identified with their results.

**Held-out change H1:** after a lane reported its baseline ready, disclose
a fourth collectible beyond the old endpoint. Holding the action must
not collect it; release and press again to collect. Save, reset, restore,
and assert the collected set and player position. Baselines were frozen
before the edit. The task was withheld from initial fixture construction,
but its implementation and proof were written by the same worker; it is
not a blinded independent evaluation. App snapshots are not full engine
world serialization or durable save-game testing.

Each fix loop was capped at three rounds. Repeated executions measure
runtime repeatability. No model token usage was measured, engine setup
budgets differed, and shared fixture code made per-engine authoring times
inseparable in some lanes. We therefore report no comparable prompt-to-
proof distribution or independent agent success rate.

**The proofs had to earn trust.** Babylon initially exposed correct object

Six successful 3D screenshots and two 2D screenshots were inspected;
an additional failed Babylon image exposed the readiness bug. Native
probes required no pixel inspection. Capturing or inspecting an image is
not a pixel assertion, and no visual-equivalence score was measured.

## 4. What each engine offers an agent

### 3D group

| Engine | Agent-facing strength | Main qualification | Tracking decision |
|---|---|---|---|
| **Godot** | Scriptable scenes and a CLI make it a credible full-engine baseline, including native export workflows. | A headless script and fixed application ticks do not prove a seekable physics/animation world. The first-pass probe used 2D nodes; §7 adds the full 3D game. | Keep the already-approved twin. |
| **Three.js** | Direct JavaScript objects make scene edits, state assertions and a browser loop accessible. | It is the renderer baseline; collision, game lifecycle, saves and most proof instrumentation remain application work. | Keep as the minimal web baseline. |
| **PlayCanvas** | Code-based Engine skills plus an official Editor MCP covering editing and verification. The documented runtime workflow includes state queries and injected input. | The Editor workflow needs an open project/session, local connection and launch permissions. Our code fixture did not test that workflow. | First additional engine to track. |
| **Babylon.js** | A substantial code-first 3D engine with direct scene access; official graph-editing MCP tools and an experimental Inspector CLI. | Graph editing is not the same capability as gameplay input or deterministic runtime control. The first-pass fixture exercised neither; §7 adds Havok but not the vendor agent tools. | Second additional engine to track. |
| **Unity** | C#, batch tests, manual physics stepping, and now official agent tooling rather than only third-party bridges. | Editor provisioning and Pipeline setup are part of the cost; no Unity game was run here. | Watch on a concrete tooling or product trigger. |

**PlayCanvas:** its official [Editor MCP documentation](https://developer.playcanvas.com/user-manual/editor/mcp-server/)
describes entity/component/script/asset access, launching, runtime state,
logs, screenshots and keyboard/mouse/touch injection. That is close to the
edit–drive–inspect loop this project wants. It operates through the
currently connected Editor and existing login; the tested direct Engine
path has no such session requirement. Separately, its
[code-based skills](https://developer.playcanvas.com/user-manual/getting-started/use-playcanvas-skills/)
cover scene construction, model inspection, animation, game state and
runtime verification. This combination earns a trial, not an unmeasured
claim that its agents outperform the others.

**Babylon:** the [official MCP documentation](https://github.com/BabylonJS/Documentation/blob/master/content/toolsAndResources/mcpServers.md)
describes editor connections for materials, geometry, particles, GUI and
related graphs. Its [Inspector CLI announcement](https://forum.babylonjs.com/t/inspector-cli-for-ai-agents/63243)
is another promising direction, with experimental maturity. These are
distinct interfaces, not a demonstrated replacement for the game's
agent driver. Babylon remains valuable as a counterexample to rebuilding
3D facilities ourselves; a renderer-only Three.js comparison would miss
that question.

**Unity:** the [experimental CLI](https://docs.unity.com/en-us/unity-cli/unity-cli-reference)
lists structured commands, test runs, connected-editor commands and MCP;
its [official plugin](https://docs.unity.com/en-us/ai/unity-plugin/about-unity-plugin)
supports Codex and other agents. The [Pipeline package](https://docs.unity.com/en-us/unity-production-pipeline/local-tools-cli/unity-pipeline-package)
provides a local HTTP interface and requires Editor setup. CLI
`1.0.0-beta.10` ran on the fleet; its inventory returned no installed
Editors and `status` returned `STATUS_NO_INSTANCES`. This is a measured
environment gap, not evidence that Unity cannot be automated.

Unity's [manual physics API](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Physics.Simulate.html)
also prevents an easy strawman: explicit simulation steps already exist.
They do not invoke `FixedUpdate`, so driving only physics does not advance
all gameplay. Unity's [web limitations](https://docs.unity3d.com/6000.0/Documentation/Manual/webgl-technical-overview.html)
explicitly say web physics results need not match other platforms. Fixed
steps are not proof of cross-host equality.

### 2D group

| Engine | Agent-facing strength | Main qualification | Tracking decision |
|---|---|---|---|
| **Defold** | Text resources, command-line builds, and official automation/AI-agent documentation. Debug runtime inspection and input have a supported HTTP route. | Its fixture did not build within this run's fix budget; the advertised bridge remains untested here. | First revisit when a native-and-web 2D consumer exists. |
| **Phaser** | Source-first browser workflow; the probe drove real keyboard events through the engine. Official Editor MCP and a separate Game Agent service now exist. | A source fixture, the Editor workflow and a hosted generation service have different setup and model costs. | Preferred web-only 2D comparison when that scope opens. |
| **LÖVE** | Small Lua surface and explicit Box2D stepping; unusually direct physics proof in this run. | World/HUD/assets/delivery and the inspection protocol remain application work; desktop headless success says nothing about the target phone. | Learn from its clock ownership; no ongoing slot. |
| **KAPLAY** | Compact JavaScript composition and easy object inspection. | Our input route was an application boolean, and debugger stepping does not establish portable control over every subsystem. | Revisit for a deliberately tiny web game. |
| **Pygame** | Simple Python state, sprites and collision queries make logic easy to inspect and test. | This probe supplies no evidence for the web/mobile shipping path or a broader scene/asset pipeline. | Useful prototyping/control case; no ongoing slot. |

Defold is the significant surprise. Its [engine service](https://defold.com/manuals/engine-service/)
documents a debug Automation Bridge with runtime inspection, input and
capture. Its [AI-agent manual](https://defold.com/manuals/ai-agents/)
describes vendor-neutral HTTP/OpenAPI integration. It should not be
marked down merely for lacking an official MCP wrapper. These facilities
make it a serious 2D candidate even though our setup failed.

Phaser's [Editor MCP](https://docs.phaser.io/phaser-editor/ai/mcp-server)
and [Game Agent MCP](https://www.phaser.io/news/2026/07/phaser-game-agent-mcp-setup)
are different products. The latter uses an authenticated hosted build
service; comparing its bundled model against our common model would
confound engine and agent quality. The local engine fixture is the
appropriate common-model control.

The smaller engines' relevant primitives are documented directly:
[Godot's CLI](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html),
[Three.js objects](https://threejs.org/docs/pages/Object3D.html),
[LÖVE world stepping](https://www.love2d.org/wiki/World%3Aupdate),
[KAPLAY debugger control](https://kaplayjs.com/docs/api/ctx/debug/) and
[Pygame sprites/collisions](https://www.pygame.org/docs/ref/sprite.html).
Godot also explicitly qualifies its
[physics determinism](https://docs.godotengine.org/en/stable/tutorials/physics/physics_introduction.html).

## 5. Implications for Exact

The distinction is not "other engines need screenshots; Exact has state."
Every successful probe could inspect live objects, and several vendors
now expose runtime inspection and input to agents. The parent research's
comparative claims should be read in that light.

Exact's opportunity is narrower and testable: **one dependable contract
for input, time, state, errors and evidence across hosts**, with a cheap
edit loop. The comparison must include the cost of maintaining Exact's
adapter and missing engine features. Giving every competitor a custom
driver while treating Exact's driver as free would reverse the bias
rather than remove it.

Keep three properties separate: same-host replay, the equivalence of a
large clock advance to many fixed ticks, and cross-host simulation
equality. The first pass established only limited same-host microfixture
repeatability; §7 adds full-game same-host checks. Neither establishes
cross-host physics parity, animation determinism,
audio scheduling, asset-import fidelity, phone performance or complete
world serialization for any engine, including Exact.

## 6. What would change the recommendation

The full-game follow-up in §7 covers the common-model source workflow.
The next comparison should exercise each engine's best documented vendor
automation route, more change tasks, native exports and real target hardware.
Keep adapter construction separate; use fresh agent sessions, common budgets
and randomized order.
Have a separately authored evaluator reject regressions, including a
negative control. Count unsuccessful trials and interventions as well as
successful durations. Report pixel *inspection* separately from captures.

Before calling the shortlist selected on performance, report:

- Cold and warm prompt-to-passing-proof distributions, independent success
  counts, human interventions, pixel dependence and adapter maintenance.
- The game bundle plus identical assets, compressed; native installed
  size separately. A package archive or editor installation is neither.
- First title/world frame, steady memory, and frame p50/p95 on the same
  real GPU and phone, with warmed versus cold caches named.
- Explicitly stepped input, timers, animation and physics; an actual
  save/load across process restart; and cross-host state comparisons.

**Drop PlayCanvas** if its session/Editor machinery costs more than the
runtime tools save on those tasks. **Drop Babylon** if it adds no useful
coverage beyond Three.js while costing more to keep current. **Reopen
Unity** when a provisioned, licensed fleet Editor can run the same tasks
through the official CLI/Pipeline path, or a native production requirement
makes its ecosystem material. **Reopen Defold/Phaser** when 2D is assigned;
that replaces a recurring 3D slot rather than creating an ever-growing
engine matrix.

## 7. Full-game follow-up: actual Lanterns implementations

Charlie authorized “ok do full games.” Four implementation lanes used three
fleet builders, the same [level and game contract](../experiments/game-engine-comparison/full/BRIEF.md),
and the same 162,852-byte animated Fox glTF. Each implementation owns its
engine objects and physics; there is no shared simulation that merely renders
through four libraries. The games have twelve lanterns, a three-minute dusk,
real collision, a movable crate, two jumps to the ledge, imported animation,
title/HUD/pause/sound/touch controls, win/loss/restart, and persistent saves.
The [full source and evidence](../experiments/game-engine-comparison/full/README.md)
are retained. Build artifacts and dependencies are ignored by Git.

### Gameplay versus automation qualification

The independently authored evaluator drives ordinary input, reads live bodies,
and completes the actual crate/ledge route. It never teleports, fills the lit
set, or calls a debug-win operation. Ten aggregated cases include actual browser
keyboard events, collision, reload persistence, terminal states, and equivalence
of a 60-tick batch to sixty individual ticks for **both player and crate**.

| Engine / physics | Final independent cases | Complete human game evidence | Change-trial eligibility |
| --- | ---: | --- | --- |
| Babylon 9.27.0 / Havok 1.3.10 | **10/10** | Physical all-twelve victory, timed loss, restart, persistence; desktop/touch UI | Yes |
| PlayCanvas 2.22.2 / Ammo 0.0.11 | **10/10** | Same complete route/lifecycle; desktop/touch UI | Yes |
| Godot 4.7.2 / native character and rigid bodies | **9/10** | Physical victory; normal non-agent game naturally loses at tick 10,800 in 182.316 s | No: large clock request times out late in the sequential suite |
| Three.js 0.186.0 / cannon-es | **7/10** | Builds and renders; movement/jump/save/loss pass, but wall/crate/winning route fail | No: physical gameplay is incomplete |

These are outcomes of one implementation per engine, **not engine capability
limits**. Babylon's first run caught a real Havok reset bug: changing the mesh
mirror did not move the body. Correcting the physics teleport/reset path made
the complete suite pass. Godot's isolated 10,800-tick proof passes in 3.018 s,
but the same operation after a completed/restarted game times out at 60 s. Its
subsequent batch-equivalence case passes. Preserve that distinction rather than
calling either the isolated proof or the complete suite universally correct.
Three's wall collision after reset and ineffective crate contact remain
unresolved. After the initial stop, Charlie explicitly authorized one further
sleep/reset repair round. Keeping the motor awake and refreshing Cannon's cached
bounds/transforms on reset/load/respawn still produced **7/10**, with the same
three failures. The rebuilt browser entry was verified. The unproven patch was
reverted; [its exact diff and full-suite evidence](../experiments/game-engine-comparison/full/evidence/three-authorized-extra-round/)
are retained. That additional round is exhausted; the tracking recommendation
and change-trial qualification remain unchanged.

Actual UI checks used Start/Pause/Save/Load/Sound buttons, keyboard, and
390×844 touch controls. A PlayCanvas countdown rollover displayed `2:00`
with about 179.2 s remaining; the delivered source now rounds the whole remaining
second count before formatting, and passed UI plus all ten gameplay checks
again. This one-line correction happened **after trial starters were frozen**.
Godot's portrait view is letterboxed and its direction glyphs appear as missing
characters with the headless fallback font. Its human default walk is 2.4,
with Shift/API run 4.5; that is a documented deviation from the common 4.5
movement target. The browser engines use the common speed directly.

### Fresh agent changes, independently scored

[The fixed protocol](../experiments/game-engine-comparison/full/TRIALS.md)
requested two tasks, twice independently per engine: add a thirteenth lantern
on a new reachable platform; or keep twelve and require returning home before
nightfall, including persistence of the pending return. Fresh Codex sessions
used `gpt-5.6-sol`, high reasoning, warm dependencies and a 15-minute wall ceiling.
Implementation authors were not the trial sessions. There was no token ceiling;
actual usage is retained. The external evaluator ran after each final answer,
without feeding its failures back for another repair in that attempt.

Only the two qualified starters entered: **eight actual attempts, eight external
functional passes, seven protocol-compliant successes**.
The other eight planned attempts were **not run**, not counted as model failures
or successes. Qualification was 2/4 implementations; conditional change success
was 8/8 functionally, or 7/8 with the repair budget enforced. Neither is a
population success-rate estimate.

Tasks ran A1,B1,B2,A2 for each engine, with engines in parallel—not randomized
engine order. Starter code, documentation and existing helper tests differ;
Babylon already included a useful full-route helper. Those differences, plus
only two task types and two replicates, prevent attributing all timing variance
to the engine itself. This tests the supplied source workflow, not Editor MCP,
vendor skills, hosted agents, or total initial implementation cost.

### The evaluator also needed verification

A standalone repro found that this Bun/Playwright combination returned from
`waitForFunction(async predicate)` after 16.5 ms while a flag scheduled for 1200 ms
was still false. An apparent PlayCanvas save failure was therefore unreliable.
The evaluator now awaits readiness responses in a bounded host-side loop.
Affected baselines, completed trials and startup measurements were rerun on
unchanged submissions; old reports remain, and reruns are not new agent attempts.
The body-equivalence case was also strengthened globally to include the crate.
[Evaluator corrections and the repro](../experiments/game-engine-comparison/full/harness/EVALUATOR.md)
record both changes. The unchanged Babylon baseline correctly fails the
return-home evaluator at immediate victory, providing a negative control.

Five completed fresh Chromium launches per engine ran on the **same pixel
builder**, localhost, 1280×800, warm OS cache and SwiftShader. The payload column
is gzip of the exported files excluding source maps, not an optimized engine
floor or measured network download. Implementations use different scene/import
choices. Godot required a separate final launch after the whole-run time ceiling

| PlayCanvas | 4.40 / 1.18 | 636 | 961 | 50.0 / 66.7 | 943 |

Readiness is the adapter's asset-ready condition. Started-paint opportunity is

browser overhead and potentially shared-page double counting; JS heap alone
would omit substantial Wasm/GPU memory. These are software-renderer diagnostics,
not a shipping frame-rate ranking. Three's incomplete game is not admitted as
an equivalent performance candidate. PlayCanvas measurements precede the
cosmetic countdown correction; the frozen byte hashes identify that exact build.

### What this changes

The full games justify actively tracking **both PlayCanvas and Babylon** on
observed gameplay and independent edits, rather than MCP descriptions alone.
