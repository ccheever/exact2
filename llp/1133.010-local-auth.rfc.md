## Summary

`@exact/local-auth` lets an app ask the person in front of the device to
prove they are its owner, with Face ID, Touch ID, Optic ID, a fingerprint
or face on Android, or the device's passcode, on iOS, macOS and Android
first. It has two halves, because the platforms give two things of very
different strength:

- **A check,** `authenticate(reason=)`: the platform's sheet, and an answer
  the app's code acts on. It gates a screen. A process that is tampered
  with can flip its answer, so it protects nothing at rest.
- **A secret only a person present can read:** a `secret.keep` name whose
  grant line carries a policy, `secret.keep discord-token user-presence
  optional`. The platform's keystore releases the bytes only after the
  check: the Secure Enclave for a keychain item with access control on
  Apple, the Keystore for a key that needs authentication on Android.
  Data code reads it with `await store.unlock(name, { reason })`, a
  request that shows the sheet. Its bytes are never in the runner's store:
  not in the boot snapshot, a carry, a per-call snapshot, the journal or
  the agent's state. With `optional`, the person chooses whether the name
  is locked (`store.protect`, `store.unprotect`), and every write of it is
  kept the way the person chose.

```
use authenticate, localAuthStatus, LocalAuthStatus from "@exact/local-auth"

resource lock = localAuthStatus() as shape LocalAuthStatus
mutation unlocked as shape LocalAuthentication then reveal
action unlock
  send unlocked = authenticate(reason="reason.unlock")
```

```ts
// grants: 'secret.keep discord-token user-presence optional', 'device.local-auth purpose.lock'
const token = await store.unlock('discord-token', { reason: 'reason.unlock' });
```

The web has no local authentication of its own: WebAuthn's user
verification is the nearest thing, and serving either half from it costs a
passkey registered for the purpose. The web cell is `later`, to be filled
over the passkeys module (wave 2's next), and until then the module answers
`available: false` there and a locked secret is refused, never kept as a
plain one (D15).

The consumer is Excord, the Discord client, which keeps a token that is
the whole of Charlie's main account. "Lock Excord", as WhatsApp, Signal and
Telegram offer, keeps that token, and every token the gateway rotates in,
behind presence: a cold launch shows nothing of the account until the
sheet passes, and every return from the background shows the lock screen
and asks `authenticate` (§9).

## 0. What is new here

LLP 1133 D5 named this module "a parameter of `secret.keep`", and LLP
1133.000 §3.1 gave it a tier 1 `authenticate(reason=)` beside it. Writing
it out shows five things the parent RFCs did not settle, each answered
below and each a question for Charlie in §12:

1. **The store holds every secret's bytes in memory and copies them out**
   (the boot snapshot, a dev reload's carry, each worker's and logic
   module's per-call snapshot; LLP 1018 D1, `runner/src/store.rs`); reading
   a presence secret shows a sheet and blocks its caller. So a presence
   name is held in the runner as a name, a policy and a state, never as
   bytes; its value is a request's answer and nothing else (D5). Kept
   answers, which show the last launch's data before data code runs, are
   not shown while a name is locked (D5).
2. **The sheet and the bytes have different owners.** The module's reply
   route is inspected, journaled and shown to the agent (LLP 1133 D6 rule
   1); a secret must never travel it (LLP 1018 D5). The store must not show
   UI of its own, or the sheet has two owners. So the module authenticates
   and the host's presence backend keeps: the backend hands a platform
   object (an `LAContext`, a `CryptoObject`) to the bound implementation in
   the same process, and returns the value to the runner on the store's
   own path (D13).
3. **macOS's keychain cannot gate an item exact2 writes today.** exact2's
   Mac secrets are in the file-based login keychain (LLP 1018 D7); access
   control with biometry needs the data-protection keychain, whose access
   group needs entitlements a provisioning profile authorizes ([TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)).
   A Mac build without a profile cannot keep a locked secret, and says so
   rather than keep it ungated (D7).
4. **Moving a secret between locked and plain is a transition the host
   must make safe.** Store writes persist after commit and cannot be
   refused (`host/apple/src/persistence.rs`), so an app that copied a
   token to a locked name and then forgot the plain one could leave it
   ungated, or lose it, on a failure or a crash. The host owns the move,
   records its intent first, and resolves a half-done move toward locked
   (D4).
5. **Presence is not delegable.** LLP 1133's direction lets agents come to
   grant agents a capability the platform granted the app (§0 ruling 10;
   LLP 1133.002 D12). A presence check is a person's act at a moment;
   nothing an agent holds can satisfy it, and no reuse window carries it
   from a person's call to a tool's (D12).

## 1. Tier 1

### D1 — The names

There is no web API for local authentication. The nearest is WebAuthn's
user verification: an authenticator's check, "biometric or PIN", reported
in the assertion's `UV` flag, requested with `userVerification:
"required"`, with `PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable()`
as its feature test ([WebAuthn §5.1.7, §6.2.3](https://www.w3.org/TR/webauthn-3/)).
It is a ceremony over a credential the relying party registered, not a
local check. So the names are a **declared deviation**, the words Apple's
LocalAuthentication and Android's BiometricPrompt share, with WebAuthn's
meaning of "user verification" as the default policy:

| Name | Kind | Meaning | Contract | Data code |
|---|---|---|---|---|
| `authenticate(reason, biometricOnly)` | send; a request | the platform's sheet; answers when the person passes, fails otherwise | `send x = authenticate(reason="…")` | `await authenticate({ reason })` |
| `localAuthStatus()` | live source; a fact; `sync` | what this device can do now, and the biometry permission (D12) | `resource s = localAuthStatus()` | `await localAuthStatus()` |
| `store.has(name)` | the store; synchronous | a value is kept under the name, locked or not | — | `store.has('x')` |
| `store.locked(name)` | the store; synchronous; a device read | the name is kept under its presence policy, or awaits a move to it (D4) | — | `store.locked('x')` |
| `store.unlock(name, { reason })` | the store; a request | the value: after the sheet when locked, at once when not; `null` when nothing is kept | — | `await store.unlock('x', { reason })` |
| `store.protect(name)`, `store.unprotect(name, { reason })` | the store; `unprotect` a request | for an `optional` name, lock it or unlock it for good (D4) | — | `await store.protect('x')` |

`reason` is a strings key (LLP 1060), as geolocation's `purposeKey` is
(LLP 1133.002 D10): the text is translated with the app's others, and the
bake checks the key. Apple shows it under the app's name on the Touch ID
and passcode sheets, not on Face ID's ([Logging a user into your app with
Face ID or Touch ID](https://developer.apple.com/documentation/localauthentication/logging-a-user-into-your-app-with-face-id-or-touch-id));
Android shows it as the prompt's title, which `BiometricPrompt.Builder`
requires ([`setTitle`](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt.Builder#setTitle(java.lang.CharSequence))).

**Values.**

| Shape | Fields |
|---|---|
| `LocalAuthentication` | `timestamp` (ms since the epoch); `android` (`authenticationType`, D10) |
| `LocalAuthStatus` | `available`: the default policy can be evaluated now (a device credential is set, or biometry is enrolled and the policy is biometric); `biometry`: `faceID`, `touchID`, `opticID`, `other` or `none`; `deviceCredential`: a passcode, PIN, pattern or password is set; `state`: the biometry permission, `granted`, `prompt`, `denied` or `unknown` (D12); `presenceSecrets`: this target can keep a locked secret (D7, D15); `apple`, `android` (D10) |

`biometry` is Apple's `LABiometryType`
([biometryType](https://developer.apple.com/documentation/localauthentication/lacontext/biometrytype)).
Android does not name the modality, so it reads `other` when a biometric
of the allowed class is enrolled, and the platform's own label for it
("Use fingerprint", "Use face") is a tier 2 field (D10), which is what a
hand-built Android app shows.

**Errors.** In Contract, `failure(…).code`; in TypeScript and Rust a
rejection `{code, message}`, as LLP 1133.002 D1 does:

| Code | Apple ([`LAError.Code`](https://developer.apple.com/documentation/localauthentication/laerror-swift.struct/code)) | Android (`BiometricPrompt` errors) |
|---|---|---|
| `USER_CANCEL` | `userCancel`, `userFallback` | `ERROR_USER_CANCELED`, `ERROR_NEGATIVE_BUTTON` |
| `SYSTEM_CANCEL` | `systemCancel`, `appCancel` | `ERROR_CANCELED`, `ERROR_TIMEOUT` |
| `AUTHENTICATION_FAILED` | `authenticationFailed` | (failed attempts are not terminal on Android; the prompt ends in `LOCKOUT` or a cancel) |
| `LOCKOUT` | `biometryLockout` | `ERROR_LOCKOUT`, `ERROR_LOCKOUT_PERMANENT` |
| `NOT_AVAILABLE` | `biometryNotAvailable`, `biometryNotEnrolled`, `passcodeNotSet`, `biometryNotPaired`, `biometryDisconnected`, `companionNotAvailable`, `watchNotAvailable` | `ERROR_HW_UNAVAILABLE`, `ERROR_HW_NOT_PRESENT`, `ERROR_NO_BIOMETRICS`, `ERROR_NO_DEVICE_CREDENTIAL`, `ERROR_SECURITY_UPDATE_REQUIRED` |
| `PERMISSION_DENIED` | a biometric-only policy after the person refused Face ID (D12) | — |
| `PERMISSION_DENIED`, message `person-required` | `notInteractive`, and every tool, wake or headless origin (D12) | the same |
| `NotSupportedError` | — | — (the web; a target without the module; a locked secret where `presenceSecrets` is false) |

The platform's own code and message travel as tier 2 (`apple.code`,
`android.code`), so an app that needs the finer case has it.

**Declared deviations.**

- The names themselves (above).
- Errors are domain codes, not WebAuthn's single `NotAllowedError`, which
  merges cancel, failure and lockout on purpose so a web page learns less
  ([WebAuthn §6.3.3](https://www.w3.org/TR/webauthn-3/)). A local check has
  no such reason, and a hand-built app shows a different screen for a
  cancel than for a lockout.
- `store.unlock`, `protect` and `unprotect` return promises where
  `store.get` is synchronous: each may wait on a person or on the host.

### D2 — What each half guarantees, and what it does not

This is the module's security model, and the reason it has two halves.

| | `authenticate()` | a locked secret |
|---|---|---|
| What it establishes | the platform told the app's code that a person passed its check, moments ago | the platform's keystore released the bytes only after its check |
| Who enforces it | the app's own code, acting on a result | the keystore, outside the app's process: on Apple the Secure Enclave, which "passes back a pass/fail result that gates keychain item access" ([Apple](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id)); on Android the Keystore, whose key with authentication required cannot be used without the authenticator's token ([`setUserAuthenticationRequired`](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUserAuthenticationRequired(boolean))) |
| Against the app's own process tampered with (a hook, a debugger, a modified build) | nothing: the result is a value in memory | the bytes stay closed: the process cannot decrypt without the check |
| Against the operating system or the keystore compromised | nothing | holds only where the keystore is hardware: the Secure Enclave; Android's TEE or StrongBox. A software keystore (an emulator, `android.securityLevel` `software`) is enforced by the OS alone |
| Integrity | — | none: a write needs no check (D5), so a compromised process can replace the value, though not read it |
| Use it for | showing a screen; confirming an action no server needs to trust | a token, a key, anything that must stay closed at rest |
| Do not use it for | protecting data; proving anything to a server | proving anything to a server (that is attestation's and passkeys', LLP 1133.000 §3.1) |

OWASP's mobile testing guide calls the first "event-bound" and recommends
the second for anything sensitive ([MASTG-BEST-0036](https://mas.owasp.org/MASTG/best-practices/MASTG-BEST-0036/)).
The recipe says which to use, and an agent writing an app is told the same
in `docs/contract-for-agents.md`.

**Per host, what a locked secret guarantees:**

| Host | Kept as | Enforced by | Notes |
|---|---|---|---|
| iOS, iPadOS | a generic-password item in the data-protection keychain with a `SecAccessControl` (D6) | the Secure Enclave | `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly`: never in a backup restored to another device, and deleted when the passcode is removed ([the constant](https://developer.apple.com/documentation/security/ksecattraccessiblewhenpasscodesetthisdeviceonly)) |
| macOS | the same, in the data-protection keychain, which needs a provisioned build (D7) | the Secure Enclave on a Mac with one (Apple silicon, T2); the system's keychain service otherwise | a Mac without Touch ID asks for the login password under `user-presence` |
| Android | ciphertext in a private directory of its own, decrypted by a Keystore key of its own that requires authentication for every use (D6) | the TEE, or StrongBox when the line asks (D10); the OS alone on a device with neither, which `android.securityLevel` reports | the key is "irreversibly invalidated once the secure lock screen is disabled" ([Keystore](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUserAuthenticationRequired(boolean))) |
| web | refused (D15) | — | never a `localStorage` value in its place |
| Linux, Windows | `later`; refused until then | — | never the plain `0600` file in its place |
| under the agent | the agent's own memory or scratch store | nothing: tickets answer (§7) | never a real keychain item or Keystore key |

The simulator and the emulator prove the flow and the refusals, not the
hardware: the iOS simulator has no Secure Enclave and the emulator's
Keystore is software. The hardware rows are proved on devices (§9 drive
10).

**What it never guarantees:**

- **That the person is the owner.** Anyone enrolled, or anyone who knows
  the passcode, passes `user-presence`. `biometry-current-set` narrows that
  to the biometrics enrolled when the secret was kept (D4).
- **What happens to the value after.** `unlock` hands the bytes to the
  app's data code, which keeps them in memory for as long as it chooses,
  and may use them from any caller, a tool's included. Presence gates the
  read, not the use.
- **That an answer derived from it stays closed.** The runner cannot tell
  a token from any other string in an answer, so an answer that carried
  the value would be kept, journaled and shown like any other. Keeping
  secrets out of answers is the app's obligation, as LLP 1018 D5 makes it
  for every secret; Excord's stage 0 test checks its own (§11).
- **Anything about the server's view.** A server that must know a person
  was present needs a signature it can check: a passkey (wave 2, next) or
  an attested key. A presence-gated signing key in the Secure Enclave is
  LLP 1069.005 D1b's "after a security review", and stays out (§8).

### D3 — Unsaid defaults are the platform's

| Default | Apple | Android | Source |
|---|---|---|---|
| `authenticate`'s policy | `deviceOwnerAuthentication`: biometry, Watch or passcode | `BIOMETRIC_WEAK \| DEVICE_CREDENTIAL` on API 30 and later; `setDeviceCredentialAllowed(true)` on API 29 | Apple's own sample evaluates `deviceOwnerAuthentication`; both match WebAuthn's "user verification", any method the authenticator has |
| `biometricOnly=true` | `deviceOwnerAuthenticationWithBiometrics` | `BIOMETRIC_WEAK`, with a negative button the platform labels "Cancel" from API 36.1 and the module labels with the platform's `android.R.string.cancel` before | [`LAPolicy`](https://developer.apple.com/documentation/localauthentication/lapolicy); [`setNegativeButton`](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt.Builder#setNegativeButton(java.lang.CharSequence,%20java.util.concurrent.Executor,%20android.content.DialogInterface.OnClickListener)) |
| reuse of the device's own unlock | none (`touchIDAuthenticationAllowableReuseDuration` 0) | none | [the property](https://developer.apple.com/documentation/localauthentication/lacontext/touchidauthenticationallowablereuseduration) defaults to 0 |
| the fallback and cancel titles | the system's | the system's | — |
| a locked secret's accessibility | `WhenPasscodeSetThisDeviceOnly` | `setUnlockedDeviceRequired(true)` on API 35 and later only | Apple's sample for this very use; Android warns that on Android 12 to 14 a weak-biometric unlock does not re-authorize such keys and profiles sharing their parent's lock fail, "fixed in Android 15" ([`setUnlockedDeviceRequired`](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUnlockedDeviceRequired(boolean))); per-use authentication already requires the person below 35 |
| a locked secret's key | — | a Keystore key pair per name, whose private half needs authentication for every use; the public half encrypts, which needs no person, since "public key operations are not restricted" ([Keystore](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUserAuthenticationRequired(boolean))) | so a write never shows the sheet (D5) |
| when to ask | the app's choice (LLP 1133 §0 ruling 9) | the same | the recipe recommends asking at launch and on return for an app lock, as the platforms' own apps do |

`BIOMETRIC_WEAK` for the check, where a locked secret needs
`BIOMETRIC_STRONG`, is the platform's own split: the builder's default is
`BIOMETRIC_WEAK` "for non-crypto authentication, or BIOMETRIC_STRONG for
crypto-based authentication"
([`setAllowedAuthenticators`](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt.Builder#setAllowedAuthenticators(int))).
So on a phone whose face unlock is Class 2, the check accepts a face and a
locked secret asks for a fingerprint or the PIN, as a hand-built app's
would.

## 2. Presence secrets

### D4 — The policy is in the grant line; the host owns every move

```
secret.keep discord-token user-presence optional
```

A `secret.keep` line may carry one policy word after the name, then
`optional`, then platform words (D10). Each policy is a shared word that
both native platforms have:

| Policy | Meaning | Apple `SecAccessControlCreateFlags` | Android `setUserAuthenticationParameters(0, …)` |
|---|---|---|---|
| `user-presence` | biometry or the device credential; survives a change of enrolment | `userPresence` | `AUTH_BIOMETRIC_STRONG \| AUTH_DEVICE_CREDENTIAL`, which keeps the key valid across enrolment |
| `biometry-any` | biometry only; survives a change of enrolment | `biometryAny` | `AUTH_BIOMETRIC_STRONG`, `setInvalidatedByBiometricEnrollment(false)` |
| `biometry-current-set` | biometry only; lost when enrolment changes | `biometryCurrentSet` | `AUTH_BIOMETRIC_STRONG`, `setInvalidatedByBiometricEnrollment(true)` |
| `device-credential` | the passcode, PIN, pattern or password only | `devicePasscode` | `AUTH_DEVICE_CREDENTIAL` |

Sources: [`SecAccessControlCreateFlags`](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags);
[`setUserAuthenticationParameters`](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUserAuthenticationParameters(int,%20int))
(API 30) and [`setInvalidatedByBiometricEnrollment`](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setInvalidatedByBiometricEnrollment(boolean)).

**Mandatory or the person's choice.** Without `optional`, the name is
always locked: every write is kept under the policy. With `optional`, the
name is plain until the app calls `store.protect(name)`, and locked until
it calls `store.unprotect(name, { reason })`; either way, every
`store.set` of the name is kept in the state it is in. So an app whose
token rotates (Excord's gateway issues a new one at `READY`) writes it with
`store.set` as before, and a locked name never gains a plain copy.

**Why the grant and not each write.** LLP 1133.000 sketched
`secret.keep(…, requireUserPresence=)` as an argument. The grant is better
for four reasons:

- **It cannot be forgotten at one call site.** Every write of the name,
  from any code path, is kept by the host in the name's state; an argument
  missed on one `store.set` would keep the token ungated, silently.
- **The host knows before boot,** without reading the platform, which
  names hold no bytes in the runner (D5), and the bake knows which names
  need `device.local-auth` and, on macOS, a profile (D7).
- **It is reviewable.** The grant set is the app's statement of authority
  (LLP 1018 D3); a reader sees which secrets are gated where the others are
  listed.
- **The grammar is the existing one.** `secret.keep <name>` grows words;
  no Contract or store signature changes for a plain name.

**Refusals at bake,** by name: a policy word that is not one of the four,
or a word out of order (`grant-policy-unknown`); `optional` without a
policy; a presence line without a `device.local-auth` line in the same app
(`grant-missing`, naming the line), since Face ID will not run without
`NSFaceIDUsageDescription` (D12); a name both kept and held (LLP 1133.007
D8's `secret-name-twice`, unchanged); a source-scoped grant that names a
presence name with another policy than the app's line
(`grant-policy-conflict`).

**Moves are the host's, recorded before they begin.** `protect`,
`unprotect` and a change of policy between versions each move a value
between the plain backend and the presence backend. Neither backend can
make both changes at once, and store writes persist after commit with no
way to refuse (`host/apple/src/persistence.rs`). So the host makes every
move itself, in this order:

1. it records the name's intended state, `locked` or `plain`, in its own
   plain store under the runner-owned name `exact.presence.<name>` (a
   prefix no grant may name and the runner owns, beside `exact.kept.` and
   `exact.state.`), and
   waits for that write to be durable;
2. it writes the value in the intended state and waits for that;
3. it deletes the value in the other state;
4. it switches the name's occupancy (D5) and settles the call.

**One queue per name.** The host runs every operation on a presence name,
`set`, `forget`, `unlock`, `protect`, `unprotect` and a failed write's
retry, through one queue for that name, in order. So a move is never
interleaved: a `set` that arrives during `protect` waits and is then kept
locked, never written plain beside the new copy or deleted as the old
one; an `unlock` during a move waits for it, and never answers `null`
because occupancy is between states. Excord's gateway rotating its token
while the person turns the lock on is this case (§9, drive 4).

**Reconciliation resolves toward locked.** At boot the host reconciles each
presence name against its line and record, without reading a locked copy:

- a plain copy beside a locked one: the plain copy is deleted, whatever
  the record says, since a plain copy may never outlive a locked one;
- a locked copy alone where the record says `plain` (an `unprotect`
  interrupted after step 1): the record is reset to `locked`, durably. The
  lock stays on, the switch shows it on, and only a new `unprotect`
  removes it; an `unlock` never does;
- a plain copy alone where the record or a mandatory line says `locked`
  (a `protect` interrupted after step 1, or an update that added a lock):
  the name's occupancy is **`pending`**. The move (steps 2 and 3) runs
  after the module has loaded, since on Android it generates a key through
  the bound implementation's hatch (D6, D13), and an `unlock` waits for it
  on the name's queue. A pending name is not yet locked: its plain copy is
  on disk as it was before, and D2's guarantee holds only once the move
  has finished. Until then the copy is kept out of the runner like a
  locked value: every plain-store read that feeds the runner (the boot
  snapshot, the post-pixel activation and each store refresh,
  `host/apple/src/activation.rs`, `host/linux/src/system_support.rs`)
  omits a pending or locked name, and the `Store` drops bytes for such a
  name if a read carries them. The move reads the copy in the host, off
  that path;
- a pending name whose move cannot be made (no device credential; a Mac
  without a profile): the plain copy is **deleted**, and the name reads
  absent, so the app signs in again. A copy the app's line or the person
  said must be locked is never kept ungated for want of a way to lock it,
  as `WhenPasscodeSetThisDeviceOnly` items are deleted when the passcode
  is.

A person's "turn the lock off" interrupted by a crash therefore leaves the
lock on, and nothing interrupted ever leaves a plain copy of a locked name
where the runner or the app can read it.

**A name's policy changes between versions.** The record and the line
decide, through the same reconciliation:

- **plain to presence** (a mandatory line, or an `optional` name the app
  protects at launch): as the `pending` case above. Nothing is moved
  before first pixel; the launch after the update reads the name as
  `pending`, with `store.locked` true, and its first `unlock` waits for the
  move and then shows the sheet. A `protect` called in a running session
  is D5's: it rejects and leaves the name plain when the move cannot be
  made;
- **presence to plain:** the locked item is not read; `has` reads false,
  the record is cleared, and the next `set` replaces it. An update that
  removes a lock costs a sign-in, never a silent copy;
- **one policy to another:** as presence to plain: the old item is
  forgotten unread.

### D5 — A presence name holds no bytes in the runner

The store's guarantee (LLP 1018 D1) is that a granted secret is in the
snapshot the host reads before boot, so the first frame knows the person.
The runner's `Store` keeps those bytes in memory and copies them into the
boot snapshot, a reload's carry and every per-call snapshot
(`runner/src/store.rs`, `snapshot`; `logic/abi/src/lib.rs`;
`js/web/src/lib.rs`). A presence name is held differently:

- **The runner holds its occupancy,** not its bytes: per name, the policy
  and whether the value is absent, plain, pending (D4) or locked;
  `store.locked` is true for pending and locked alike. Locked or pending
  occupancy counts as a kept secret wherever the runner asks whether the
  launch opened with one (`opened_with_secrets`, `runner/src/store.rs`),
  and everything below that says "locked" applies to a pending name too,
  except D2's guarantee, which waits for the move. The host fills it at
  boot from the reconciliation (D4) and from queries that cannot prompt:
  on Apple a noninteractive existence probe of each indexed account,
  where "not found" means absent and any refusal means kept; on
  Android the ciphertext file's presence. The carry and the per-call
  snapshots carry occupancy only, as a field of their own: an empty byte
  string is not a locked name, and a carried launch does not read the
  host again.
- **A plain-state `optional` name** is an ordinary secret: its bytes are
  in the snapshot as LLP 1018 says, since the person chose no lock.

| Where a plain secret goes | A locked name's value |
|---|---|
| the runner's `Store`, the boot snapshot, a carry, a per-call snapshot | never; its occupancy only |
| `store.get(name)` | throws `InvalidAccessError`, "a locked secret is read with `store.unlock`", so an app never mistakes a locked token for none |
| a `StoreWrite` after commit | the write carries the value to the host's presence backend, which keeps it and drops it; the runner keeps none |
| the journal, `state`, a crash report | its name, policy and state only |
| bake | the bake's store is empty (LLP 1018 D4): `has` and `locked` read false, and `unlock` refuses at bake |

**Kept answers.** LLP 1027 D4 shows, before a TypeScript source is ready,
the answer it kept from the last launch. For a locked app that answer is
the account's content, shown before the person has passed the sheet. So
**while any presence name is locked or pending at boot, the runner shows no kept
answer for that launch:** each source shows its compiled placeholder until
data code answers. Answers are still kept, for a launch with no lock.
Every read of a presence-granted name, `has`, `locked` and `unlock`, is a
device read, as entropy is (LLP 1069.005 D2): the bake compiles no value
for an answer that made one, so the placeholder is the Contract's `else`,
which the app writes as a neutral launch surface, not as "signed out"
(§9).

**The operations.**

- **`store.has(name)`, `store.locked(name)`,** synchronous, from
  occupancy. They work for plain names too (`locked` is then false).
- **`await store.unlock(name, { reason })`:** a request (LLP 1069.007 D1)
  when the name is locked. It is admitted as LLP 1133.002 D14 admits a
  module request (the grant, the target, the origin, the queue of
  decisions), then the presence backend has the bound implementation show
  the sheet and reads (D6, D13). It answers the value, `null` when nothing
  is kept or the platform has dropped the item (the occupancy then reads
  absent), or fails with D1's codes. The value is the promise's result
  alone, delivered on the store's completion path (D13): it does not enter
  the runner's `Store`, so a later `get` throws and a later `unlock` asks
  again. On a plain-state name `unlock` answers the value at once, with no
  sheet, so an app's code reads an `optional` name one way.
- **`store.set(name, value)`** keeps the value in the name's state and
  never shows the sheet: on Apple, adding an item with access control asks
  nothing; on Android the public key encrypts (D3). It throws
  `NotSupportedError` at once when the name would be locked and
  `localAuthStatus().presenceSecrets` is false or no device credential is
  set (the platforms refuse such an item: `WhenPasscodeSetThisDeviceOnly`
  stores nothing without a passcode, and a Keystore key that needs
  authentication "can only be generated if secure lock screen is set up").
  A write the platform refuses later is journaled and retried on the
  name's queue, as every failed store write is retried (`persistence.rs`).
  Occupancy stays as it was: a failed overwrite leaves the previous locked
  value in place and readable with `unlock`, and only a first write that
  never lands, or the platform reporting the item gone, makes it absent.
- **`await store.protect(name)`** (an `optional` name): D4's move to
  locked. It needs no person; it resolves when the move is durable, and
  rejects, leaving the name plain, when the platform refuses (no device
  credential, no profile on macOS).
- **`await store.unprotect(name, { reason })`:** a request: the sheet,
  then D4's move to plain.
- **`store.forget(name)`** removes the value in whichever state, asking
  nothing, and clears the record.

**One name per sheet.** `unlock` reads one name. A hand-built app that
needs several secrets behind one sheet keeps them as one item; an app here
keeps them as one value (a record as JSON, as LLP 1018 D3 keeps a session),
which costs one sheet on both platforms. Several names in one call would
cost one sheet on Apple (one evaluated `LAContext` serves several items,
[`kSecUseAuthenticationContext`](https://developer.apple.com/documentation/security/ksecuseauthenticationcontext))
and one per name on Android, where an authentication authorizes one
cryptographic operation; the module does not promise what one platform
cannot keep.

**No reuse across calls.** Each `authenticate`, `unlock` and `unprotect`
evaluates afresh. No evaluated context outlives the call that evaluated
it, so no later caller, and in particular no tool (D12), inherits a
person's check. Apple's reuse of the device's own Touch ID unlock is a
tier 2 word, off unless written, and is the platform's rule, not a reuse
of the app's check (D10).

### D6 — Each platform's mechanism

**Apple.** One generic-password item per name and generation, in the data-protection
keychain (`kSecUseDataProtectionKeychain`), its `kSecAttrService` the app's
store service plus `.presence`, so the plain items' code (`ibex2`'s
`KeychainStore`) never meets one. `kSecAttrAccessControl` is
`SecAccessControlCreateWithFlags(kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly,
<the policy's flag>)`. An `unlock`:

1. the bound implementation evaluates an `LAContext` against the item's
   access control,
   [`evaluateAccessControl(_:operation:localizedReason:reply:)`](https://developer.apple.com/documentation/localauthentication/lacontext/evaluateaccesscontrol(_:operation:localizedreason:reply:))
   with `.useItem`, which shows the sheet (D13);
2. the backend reads the item with `kSecUseAuthenticationContext` set to
   that context, which "will succeed without asking user for
   authentication", off the main thread, since `SecItemCopyMatching`
   "blocks the calling thread" ([SecItemCopyMatching](https://developer.apple.com/documentation/security/secitemcopymatching(_:_:)));
3. the context is invalidated (`invalidate()`), and the value goes to the
   runner (D8).

A `set` of a locked name never shows the sheet and never destroys the old
value before the new one is durable. The generation is part of the
item's primary key, its `kSecAttrAccount` being `<name>#<generation>`,
since a second item with the same service and account would be refused as
a duplicate ([`errSecDuplicateItem`](https://developer.apple.com/documentation/security/errsecduplicateitem)).
A `set` adds the new value under the next generation, then deletes the old
item by its exact account, neither of which asks for the person.
Reconciliation probes indexed accounts without permitting authentication,
keeps the highest generation and deletes the rest. Before adding a keychain
item, the host writes an empty marker under `<name>#<generation>` in its
`exact.presence.items` kv scope. Deletion removes the keychain item before
its marker. A crash before the add or after deletion leaves a marker whose
probe confirms absence; a crash after the add leaves a discoverable item.
Only `errSecItemNotFound` removes a candidate: an unavailable keychain is
not an absent secret. If any probe fails, reconciliation keeps the name
pending and retires no generation. Queued operations wait for a successful
probe; the runner schedules a retry even while idle, and a new request
retries immediately.
A failed add leaves the old generation readable (D5).

An attributes-only enumeration is unsuitable: on iOS 27.0.1 it presents
Face ID before the app's explicit unlock. Apple's
[Security implementation](https://github.com/apple-oss-distributions/Security/blob/main/keychain/securityd/SecDbKeychainItem.m)
checks an item's access constraints even when secret data is not requested.
The host uses `kSecUseAuthenticationUIFail` for its existence probes so
ExactKit needs no LocalAuthentication dependency. Development installs
created before this index need their lock disabled before upgrading and
re-enabled afterward, or a fresh login after reinstalling.

An item the platform has dropped (the passcode removed; a
`biometryCurrentSet` item after enrolment changed) reads as not found, and
`unlock` answers `null`.

**Android.** Per name, one Keystore key pair under an alias of the app's
(`exact.presence.<name>`), generated at the name's first locked write from
its line alone: RSA with OAEP padding, `setUserAuthenticationRequired(true)`,
`setUserAuthenticationParameters(0, <the policy's types>)`, StrongBox when
the line says so, `setUnlockedDeviceRequired(true)` on API 35 and later
(D3), generated off the main thread after the bound implementation's
key entry has configured the builder on the main thread. Per name, a file
in a directory of its own, beside but outside the
plain secrets' directory (whose files the Linux host reads whole at boot,
`host/linux/src/system_support.rs`), holding an AES-GCM data key wrapped by
the public key and the value sealed under it; a `set` writes a new file
beside it and renames it over the old one, so the old value is readable
until the new one is durable. A key whose generation
parameters no longer match the line (a policy or StrongBox word changed)
is a policy change (D4): the old key and file are deleted unread. An
`unlock`:

1. the backend initialises a decrypting `Cipher` over the private key;
2. the bound implementation shows `BiometricPrompt` with that cipher as its
   `CryptoObject`, with the policy's authenticators (D13);
3. on success the backend unwraps the data key and opens the value, on a
   background executor, and zeroes the data key;
4. a `KeyPermanentlyInvalidatedException` at step 1 means the platform has
   dropped the key: the backend deletes the key and that name's file, and
   answers `null`.

`DEVICE_CREDENTIAL` with a `CryptoObject` is API 30 and later; on API 29
(`minimumOS` `"10"`), `presenceSecrets` is false and a locked write
throws `NotSupportedError`. The presence directory is excluded from Auto
Backup and device transfer (`fullBackupContent` and `dataExtractionRules`,
which the manifest gains), since a restored ciphertext without its key
could never open.

**Reinstalling.** iOS keeps keychain items after an app is deleted; LLP
1018 D7 owes a first-launch wipe for plain secrets, not built yet. Presence
items join it when it is built, and the stage that builds the Apple
backend builds it if no one has (§11). Android removes the app's keys and
files with the app.

### D7 — macOS needs a provisioned build

The data-protection keychain's access groups come from the app's
code-signing entitlements, which "must be authorized by a provisioning
profile", and "protecting an item with biometrics (Touch ID and Face ID)"
requires that keychain ([TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)).
exact2's Mac builds use the file-based login keychain (LLP 1018 D7), and
only the widget cohort plans a profile (LLP 1126.001 WP16 Q5).

So on macOS:

- a build with a profile that authorizes `keychain-access-groups` (or the
  application identifier) keeps locked secrets as D6 says, and the bake
  derives the entitlement from the presence lines;
- a build without one reads `presenceSecrets: false`: a mandatory name's
  `set` throws `NotSupportedError`, an `optional` name stays plain and
  `protect` rejects; `authenticate` works, since evaluating a policy needs
  no keychain;
- a release build with a mandatory presence line and no profile is refused
  at bake (`grant-needs-profile`), so nothing ships that cannot keep what
  it grants;
- **it never falls back** to the file-based keychain, whose access model
  is an application ACL with no presence check.

`host/apple/build.mjs` already finds a team identity for iOS devices; a Mac
profile is a new input, which Charlie supplies for the Mac drives, as
WP16's does.

### D8 — The sheet's thread, and one at a time

**Never before first pixel, never on the main thread.** Boot reads only
occupancy (D5), and no move of D4 runs before the module has loaded. The sheet is shown by
the platform's own presentation; the read that follows runs off the main
thread (D6); the value reaches the runner on its thread by the store's
completion path (D13). A TypeScript source placed on a worker awaits a
promise like any other; the runner never waits.

**Apple.** `evaluatePolicy` and `evaluateAccessControl` reply on a private
queue; the implementation hops to the main thread to settle the call. The
platform presents the sheet over the app's active window. On iPad with
several scenes the sheet follows the system's choice of window; the
module does not pick one.

**Android.** The runner runs on its own thread (`Owner.kt`). An `unlock`
reaches the reader's presence backend by a request kind of its own, not
the module slot's kind 11, which carries JSON to `Extensions.call` and
answers on the module route the runner journals. The backend holds the
`Cipher`, calls the bound implementation's authenticator entry in the same
process on the main thread of the resumed `ExactActivity`, with the main
executor for its callback, decrypts on a background executor, and answers
the value on the store's completion path. `authenticate`, whose answer is
no secret, keeps kind 11. A request while the activity is not resumed
fails `SYSTEM_CANCEL` at once rather than wait for a resume that may not
come. The platform cancels a prompt when its activity is recreated, and
advises a retained fragment to survive configuration changes
([`authenticate`](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt#authenticate(android.os.CancellationSignal,%20java.util.concurrent.Executor,%20android.hardware.biometrics.BiometricPrompt.AuthenticationCallback)));
`ExactActivity` handles rotation, size, density and the other common
changes itself (`host/android/app/src/main/AndroidManifest.xml`), so the
prompt survives them, and a recreation that does happen settles the call
`SYSTEM_CANCEL`.

**One sheet at a time.** `authenticate`, `unlock` and `unprotect` join LLP
1133.002 D9's queue of decisions, so a Face ID sheet never opens over a
location prompt or another sheet. Unlike a permission decision, a presence
check is never shared: two queued `unlock`s show two sheets, one after the
other, since each authorizes one operation (D5). A call cancelled while
queued leaves the queue; a call cancelled while its sheet is up cancels the
sheet (`LAContext.invalidate()`, the `CancellationSignal`), and a value
that arrives for a call already cancelled is dropped by the backend, never
delivered.

**Leaving the foreground.** The platforms cancel the sheet when the app
leaves the foreground; the call fails `SYSTEM_CANCEL`, and the app asks
again on return if it wants to (the recipe's lock screen does).

**A hatch cannot weaken a gate.** The fields the module owns are the
security of the call. Unlike LLP 1133 D3's detection, the module sets them
again after the hatch returns, so an app's code that relaxed one (no
authentication on the key, interaction allowed while a tool is the origin)
has no effect, and a development build names the change in the journal.
The key hatch is the presence backend's, called through the bound
implementation's entry (D13).

## 4. Permission: one grant line, one state, presence not delegable

### D12 — LLP 1133.002 §4 for this module

**Declare.** `device.local-auth <purposeKey>`:

| Target | Derived | Does the system show the purpose? |
|---|---|---|
| iOS, iPadOS | `NSFaceIDUsageDescription` | yes, the first time the app uses Face ID; "without this key, the system won't allow your app to use Face ID", and Touch ID needs no such string ([Apple](https://developer.apple.com/documentation/localauthentication/logging-a-user-into-your-app-with-face-id-or-touch-id)) |
| macOS | nothing (Touch ID asks no permission) | — |
| Android | `android.permission.USE_BIOMETRIC`, a normal permission granted at install | — |
| web | nothing until its cell is filled | — |

A binding call, a Contract use of the module, or a presence line with no
`device.local-auth` line refuses at bake (`grant-missing`).

**Read.** `localAuthStatus().state` is the biometry permission, which only
Face ID has:

| Platform state | `state` |
|---|---|
| Face ID, the app has not used it | `prompt` |
| Face ID, used and allowed | `granted` |
| Face ID refused for the app (`canEvaluatePolicy` of a biometric policy fails `biometryNotAvailable` while `biometryType` is `faceID`) | `denied` |
| Touch ID, Optic ID on visionOS when built, Android, macOS | `granted` (nothing to ask) |
| no biometry | `granted`, with `biometry: none` |
| web | `unknown` |

Apple gives no call that tells `prompt` from `granted`, so the Apple
implementation keeps, in its own defaults, whether an evaluation that could
use Face ID has completed, as geolocation's Android implementation keeps
its history (LLP 1133.002 D8). The status is asked again on a return to
the foreground, since the person can change it in Settings.

**What a denial means.** Refusing Face ID does not stop the module:
`deviceOwnerAuthentication` and `user-presence` fall back to the passcode.
Only a biometric-only call or policy fails, `PERMISSION_DENIED`. So
`available` stays true under `denied` when a passcode is set.

**Ask.** There is no separate request: the platform asks at the first
evaluation that would use Face ID, inside `authenticate`, `unlock` or
`unprotect`. Admission (LLP 1133.002 D14) treats such a call as one that
may show a dialog in every state, since the presence sheet is itself
system UI.

**Explain and recover.** The app's own UI, and `openURL("app-settings:")`
to the app's page in Settings (LLP 1133.002 D11).

**Origin.** Every call carries its origin (LLP 1133.002 D12):

| Origin | `authenticate`, `unlock` of a locked name, `unprotect` | `store.has`, `locked`, `set`, `protect`, `forget` | `localAuthStatus` |
|---|---|---|---|
| a person's input; the app's own code in a foreground session | shows the sheet (D8) | proceed | answers |
| a tool invocation (LLP 1111) | fails `PERMISSION_DENIED`, `person-required`, before reaching the platform, in every state | proceed under the app's grant | answers |
| a background wake (LLP 1114.001); a headless session | fails `person-required` | proceed | answers |
| the development agent | §7 | §7 | §7 |

**Presence is not delegable.** LLP 1133.002 D12's direction lets an agent
come to hold, and pass on, authority the platform granted the app. A
presence check is not such authority: it is a person's act at a moment,
on this device. No delegation record, no reuse window and no earlier
check by a person satisfies it for a tool. This is why D5 keeps no
evaluated context across calls, why Touch ID's unlock reuse is refused to
a tool's call before it reaches the platform, and why a hatch cannot clear
`interactionNotAllowed` (D11). A tool that needs what a locked secret
guards asks the person through the app's own UI, which then calls
`unlock` from the person's input.

## 5. Packaging and callers

### D13 — The module authenticates; the host's backend keeps

**`@exact/local-auth`** is an extension package (LLP 1133.001), as
geolocation is:

```
packages/local-auth/
  package.json        "@exact/local-auth"; exports ".", "./apple", "./android"
  exact.json          the interface: authenticate, localAuthStatus, their shapes,
                      the substitute, the permission, and the authenticator entry
  test/               the conformance suite and its fixture app
  apple/              exact.json, LocalAuth.swift
  android/            exact.json, LocalAuth.kt
```

**Locked secrets are exact2's vocabulary:** a data capability (LLP 1133
D5), in the grant grammars, the runner's `Store` (occupancy, D5), the
runtimes' `store`, and a presence backend in each native host's own code,
because their values must stay below the data seam (LLP 1018 D5) and the
module's reply route is inspected and journaled (LLP 1133 D6 rule 1).

**The backend is native host code, and the value has a path of its own.**
It must hand a platform object to the module in the same process: an
`LAContext` on Apple, a `CryptoObject` over a `Cipher` on Android. Neither
crosses a JSON body. So the Apple backend is Swift in `ExactKit` and the
Android backend Kotlin in the reader, each keeping the item or key and
never showing UI. Each answers an `unlock` on the **store's completion
path**: a host-to-runner call, new with this RFC, that hands the value to
the waiting `unlock` promise and to nothing else. It is not the module
route, is never journaled with its value, and never enters `Store`'s
values. Plain secrets stay where LLP 1018 put them.

**The authenticator entry.** The interface declares, beside its names, an
entry the backend calls in the same process:

```json
"authenticator": {
  "apple": "evaluate(accessControl: SecAccessControl, reason: String, origin: Origin) async throws -> LAContext",
  "android": "authenticate(crypto: BiometricPrompt.CryptoObject, authenticators: Int, reason: String, origin: Origin): CryptoObject",
  "android-key": "configure(builder: KeyGenParameterSpec.Builder)"
}
```

The signatures are each language's, not LLP 1133.001's JSON types: the
entry is in-process native code, and the build checks it as it compiles
the implementation. So the system sheet has one owner: one queue (D8), one
permission history and one origin rule (D12), one set of tier 2 words and
one set of hatches (D10, D11), one substitute (§7). An implementation that
replaces the endorsed one (LLP 1133.001 D4) implements the entry too; its
suite checks it (D16). A replacement is native code compiled into the app,
which could read the keychain itself in any case (LLP 1133.001 D9: a
native dependency is trusted with the app).

An app with a presence line must depend on `@exact/local-auth`; the bake
refuses otherwise and names the dependency line, as `exact add` writes it.

*Rejected:*

- **The whole module as an extension,** with `getSecret` as a module
  call. The value would travel the module's reply route, which the runner
  reads, counts and shows in `state.extensions`; keeping it out would need
  a redacted lane in the seam every module uses.
- **The store authenticating by itself** (an `LAContext` in `ibex2`, a
  `BiometricPrompt` in the reader). The sheet would then have two owners:
  two permission histories, the origin rule written twice, tier 2 words on
  `authenticate` with no counterpart on `unlock`, and a hatch that reaches
  one of them.
- **The whole module as vocabulary.** `authenticate` needs nothing only
  the runner has; LLP 1133 D5's default holds for it.

**What this amends in LLP 1133.001.** D1: an interface may declare an
authenticator entry that one of exact2's data capabilities calls in
process. It lets anyone replace this module's implementation, as D4
promises for every module; it does not let a third party add a data
capability, which stays exact2's vocabulary (LLP 1133 D5). D8's "no
private seam" holds for what the entry is: a public part of this
interface, which any implementation of it serves.

### D14 — Callers

| Name | Contract | Data code | Request | `sync` |
|---|---|---|---|---|
| `authenticate` | a send | the binding | yes, always | no |
| `localAuthStatus` | a live source | the binding; `localAuthStatusSync()` where the host has `call` | no | yes on Apple; the web and Android answer asynchronously (LLP 1133.002 D14) |
| `store.has`, `store.locked` | — | the store | no | yes, every host |
| `store.unlock`, `store.unprotect` | — | the store | yes, when the name is locked | no |
| `store.protect` | — | the store | no | no (it waits for the host) |

Contract never reads a secret (LLP 1133 §7). An app whose Contract needs
to know the session is locked reads a source its data code answers from
`store.locked`, as Excord's `loadSession` does (§9). The TypeScript
declaration gains the five operations on `Store`, and `get`'s refusal
of a locked name; the Rust `Store` gains
the same. `unlock` and `unprotect` return requests, as `exact_data`'s
other device reads do; `protect` returns a plain future the host settles,
with no ticket and no sheet.

### D15 — Every target

| Target | `authenticate`, `localAuthStatus` | Locked secrets |
|---|---|---|
| iOS, iPadOS | LocalAuthentication | the data-protection keychain with `SecAccessControl` |
| macOS | LocalAuthentication | the same, with a profile (D7); refused without |
| Android | `BiometricPrompt`, `BiometricManager` (API 29 and later) | Keystore, API 30 and later |
| web | later: WebAuthn user verification, over the passkeys module | later: WebAuthn's `prf` extension, over the passkeys module |
| visionOS | later: Optic ID through the same LocalAuthentication | later |
| tvOS, watchOS | absent (no biometry; watchOS's wrist detection is `apple.policy` on a watch app, later) | absent |
| Windows | later: Windows Hello, [`UserConsentVerifier`](https://learn.microsoft.com/uwp/api/windows.security.credentials.ui.userconsentverifier) | later: a Hello key, [`KeyCredentialManager`](https://learn.microsoft.com/uwp/api/windows.security.credentials.keycredentialmanager) |
| Linux | later: polkit's authentication agent; fprintd where present | absent until a secret service with presence exists |
| Expose | later, when it is a host | later |
| terminal | absent | absent |

**Why the web is `later`, not built now.** WebAuthn can serve both halves:
`authenticate` as an assertion with `userVerification: "required"` over a
credential the page registered for the purpose, checked by the page
itself; a locked secret as a value sealed under a key from the
credential's `prf` extension output, which the authenticator releases only
after verifying the person ([WebAuthn §10.1.4](https://www.w3.org/TR/webauthn-3/#prf-extension)).
Three things make it a module of its own: registering means a "create a
passkey" dialog that names the site, the opposite of the platform sheet a
person expects for unlocking an app, and a tell; `prf` support varies by
browser and by credential manager; and a synced passkey makes "this device
only" untrue. The passkeys module (LLP 1133.000 §4, next in wave 2) builds
`credentials.create` and `get`; the web cell is filled over it, when an app
asks for a lock on the web.

**Until then** the web answers `available: false` and `presenceSecrets:
false`, `authenticate` fails `NotSupportedError`, a mandatory name's `set`
throws `NotSupportedError`, and an `optional` name stays plain, with
`protect` rejecting. exact2 never keeps a locked name's value ungated for
the app.

An app that builds a target with a `later` cell marks the module optional
there (LLP 1124 D9).

### D16 — Cost and conformance

**Cost.** An app that uses neither half links nothing of it: no
LocalAuthentication, no `USE_BIOMETRIC`, no Info.plist key (LLP 1047.001).
An app that uses it loads the module with the app's module, after first
pixel; the presence backend is linked only into an app with a presence
line. Stage 1 measures both with LLP 1047's probe and records them here.

**Conformance** (LLP 1133.001 D7), on each platform with the
implementation bound: availability and the status's fields; each error
code from the platform's own means (a cancelled sheet, a lockout, no
enrolment); an `unlock` that answers what `set` kept; `get` refusing a
locked name; a locked name's bytes absent from the runner's store, the
boot snapshot, a carry and the per-call snapshots; each move of D4
interrupted at each step and reconciled at the next boot; an invalidated
item answering `null`; on the real keychain, a locked overwrite whose
add failed unlocking the previous value and one interrupted between its
add and its delete unlocking the newest, and on the real Keystore, one
interrupted before its rename unlocking the previous file; a tool-origin call failing before the platform is
asked; the authenticator entry, and the out-of-tree and replacement tests
of LLP 1133.001 D8 with it. The iOS simulator enrols and matches Face ID
from its Features menu, and the suite drives it there; Android's emulator
touches an enrolled fingerprint with `adb emu finger touch <id>`. A Mac's
Touch ID and a phone's are driven by hand.

## 7. Under the agent: the substitute

**Shape:** `localAuthStatus` is a fact; `authenticate`, `store.unlock` of
a locked name and `store.unprotect` are requests (LLP 1069.007 D1).

**Facts.** `localAuthStatus`'s `state` is set by `prefer
permission.local-auth granted|denied|prompt` and `--permission
local-auth=…`, as geolocation's is; the rest by `prefer extension
local-auth.localAuthStatus=…`, which refuses a `state` field. The default:
`{available: true, biometry: "faceID", deviceCredential: true, state:
"prompt", presenceSecrets: true}`, with target restrictions applied (the
web reads `available: false` and `presenceSecrets: false`; an Android
build at API 29 reads `presenceSecrets: false`; a Mac build without a
profile reads `presenceSecrets: false`), so a drive sees each target's
real limits (LLP 1133.002 §6).

**Tickets.**

| Event | Result |
|---|---|
| a request while `state` is `prompt` and the policy can use biometry | a `permission` ticket; `allow` sets `granted`, `deny` sets `denied` and continues to the passcode where the policy allows it, else fails `PERMISSION_DENIED` |
| then, or at once while `granted` or `denied` | a `presence` ticket in `pending`, its `args` naming the call, the name, the policy, the reason's text and the origin |
| `tap @t allow` | `authenticate` answers; `unlock` answers the agent store's value, or `null` when it keeps none; `unprotect` moves the value to plain |
| `tap @t cancel` | fails `USER_CANCEL` |
| `tap @t fail` | fails `AUTHENTICATION_FAILED` |
| `tap @t lockout` | fails `LOCKOUT` |
| `tap @t invalidated` (`unlock` only) | the agent store drops the item, as the platform would; answers `null`, and `has` reads false |
| a tool-origin or wake-origin call | as production: `person-required`, no ticket |

There is no `prefer` that answers a presence ticket: each check in a drive
is a tap, so a drive's transcript shows every place a person would be
asked.

**The presence backend under the agent is always the agent's store.**
Under the agent the store is memory, or the drive's scratch tree (LLP 1018
D6), and a presence name is kept there with its policy and state recorded.
A ticket's `allow` releases only a value the drive itself wrote. Where an
agent drive reads the real plain store (`EXACT_STORE=real` on Apple),
presence names are still the agent store's, so the substitute never
answers for a real keychain item or Keystore key. `--bind local-auth`
binds the real implementation under the agent, as LLP 1133.002 stage 2
binds geolocation: the real sheet then answers instead of a ticket, and
the value still comes from the agent store. Real items are exercised only
by the conformance suite's fixture outside the agent, and by hand (§9).

**Disclosure.** `state.extensions` lists `local-auth`, its binding per
target and each call's origin and outcome; `state`'s store list shows a
presence name as `locked, user-presence`, `pending`, `plain` or `absent`, never a
value; the journal names the call, never the value.

**Declared, not built in.** As LLP 1133.002 §6 built it: each name's
`substitute` and the interface's `permission` in `exact.json`; the
`presence` ticket's choices; the store operations' substitute, which the
runner owns because the store is its, is declared in the same file under
the authenticator entry.

**Production:** none of it.

## 8. What stays out

- **The web, Windows, Linux and visionOS cells** (D15).
- **A presence-gated signing key** (Secure Enclave `privateKeyUsage`, a
  Keystore signing key with authentication): LLP 1069.005 D1b's security
  review, with passkeys and attestation.
- **Several locked secrets behind one sheet** (D5).
- **An app-password factor** (`applicationPassword`).
- **A delay before an app's return lock**, until a host gives a
  sleep-inclusive interval (§9).
- **Hiding the app's content in the app switcher** while locked: a screen
  module's (LLP 1133.000 §3.3), reachable through the app's hatch now.
- **Presence for background work**: a wake never shows a sheet (D12).
- **A delegation rule that could satisfy presence**: there is none to
  write (D12).

## 9. The consumer: Excord

Excord (`apps/excord`, its `llp/0001`) is a Discord client signed in to
Charlie's main account. It keeps the account's token with `secret.keep
discord-token` (and `fixture-token` against its fixture), and the token is
the whole account: a copy of it is a session anyone can use. Messaging apps
offer a lock for this reason: WhatsApp's "Require Face ID", Signal's
screen lock, Telegram's passcode lock. Excord's lock is stronger than
theirs, which gate the screen, because it gates the token itself.

**It gains:**

- its two `secret.keep` lines become `secret.keep discord-token
  user-presence optional` and `secret.keep fixture-token user-presence
  optional`, and it grants `device.local-auth purpose.lock`; a strings
  table with `purpose.lock` ("Excord uses Face ID to unlock your Discord
  session.") and `reason.unlock` ("Unlock Excord");
- a dependency, `"@exact/local-auth": "file:../../packages/local-auth"`,
  in its `package.json`, and on Android a `host.android` block in
  `app.json`;
- **a Lock Excord switch** in the account menu, shown while
  `localAuthStatus().available` and `presenceSecrets`, labelled by
  `biometry` ("Require Face ID", "Require Touch ID") and on Android by
  `android.label`. Turning it on sends `authenticate(reason=)` first, as
  WhatsApp asks before enabling, then `await store.protect(tokenKey)`;
  the switch shows on only when `protect` resolves. Turning it off is
  `await store.unprotect(tokenKey, { reason })`, which shows the sheet.
  The switch reads `store.locked`, so after a crash it shows what the
  host reconciled (D4);
- **the token's own writes are unchanged:** `perform` keeps the rotated
  token with `store.set(tokenKey, …)` (`apps/excord/live.ts`), and the
  host keeps it locked while the lock is on;
- **at launch,** `loadSession` reads `store.locked`. While it is true the
  session answers `{ready: false, locked: true}`, so the gateway, which
  waits on `session.ready`, opens no socket, and no kept answer shows the
  account (D5); the session's `else` placeholder is a blank launch
  surface, not the sign-in form. A `task` keyed to the launch, while
  `session.locked`, sends `unlockSession`, a mutation whose data code
  calls `store.unlock`: the sheet shows right after the first data answer.
  Success sets the token in the module's state and refreshes `session`;
  a cancel leaves the lock screen with an Unlock button that sends the
  mutation again; `null` (the platform dropped the item) shows the sign-in
  screen with "Sign in again";
- **on every return** from the background (WhatsApp's default,
  "Immediately"), the lock screen covers the transcript and its Unlock
  button sends `authenticate`. A return is an event, and a task's gate is
  a state that is already `visible` at launch, so the task on
  `exactPage().visibilityState == "visible"` runs at launch and at every
  return. Its action skips its own first run (`launched`), the guard
  `docs/agent-pitfalls.md` gives because a latch on `hidden` misses a
  return that lands before the hide's action runs, and it locks only while
  the session is unlocked (`session.ready`): a return to the launch's own
  lock screen, after a cancelled sheet, changes nothing. A cold launch runs
  `unlockSession` alone. On return the token is already in
  memory and the gateway stays open, as a hand-built client's would. On
  Android this needs the page's visibility, which the reader does not yet
  report (LLP 1133.000 §2, "Android answers defaults"); stage 2 adds it.
  A delay before the lock ("after 1 minute") is left out: Android's
  runner clock is monotonic and stops in deep sleep
  (`host/linux/src/canvas/reader.rs`), so it would need a sleep-inclusive
  interval (`SystemClock.elapsedRealtime`) from the host;
- on the web, no switch: `presenceSecrets` is false there, and the token
  stays plain.

Excord's own LLP records the feature as an amendment to its §2, with this
document as its reason.

**Acceptance drives,** under the agent on macOS, the iOS simulator and the
Android emulator, against the fixture backend (ticket ids are read from
`state.pending`; `@p`, `@q`, `@t` stand for them):

1. Signed in, `--permission local-auth=prompt`: open the account menu, `tap
   lock-switch`, `tap @p allow` (the Face ID permission), `tap @q allow`
   (the check): the switch is on; the store list shows `fixture-token:
   locked, user-presence`.
2. Relaunch with the same scratch store: no frame before the first data
   answer shows a channel, a message or the sign-in form (each frame read
   with `tree` from the first); `state.streams` shows no gateway socket;
   `pending` holds a `presence` ticket whose origin is the app's own code;
   it is the only ticket; `tap @t allow`: the channels load and the
   gateway identifies once.
3. Relaunch; `tap @t cancel`: the lock screen with Unlock; `tap unlock`,
   `tap @t allow`: the channels load.
4. Unlocked, the fixture's gateway sends a `READY` with a new token: the
   store list still shows only `fixture-token: locked`; relaunch, `tap @t
   allow`: the gateway identifies with the new token. Then, from plain,
   `tap lock-switch` and deliver a `READY` while `protect` is between its
   steps (a fault point holds it): after it settles the store list shows
   only `fixture-token: locked`, and a relaunch identifies with the new
   token.
5. Signed in and unlocked: `prefer visibility-state hidden` then
   `prefer visibility-state visible`, with no clock step between: the
   lock screen; `tap unlock`, `tap
   @t allow`: the transcript returns and `state.streams`
   shows the same socket, never closed.
6. Relaunch; `tap @t invalidated`: the sign-in screen with "Sign in
   again", and the store list shows `fixture-token: absent`.
7. Unlocked: `tap lock-switch` (off), `tap @t allow`: the store list shows
   `fixture-token: plain`; relaunch shows the transcript with no ticket.
8. The moves, interrupted: the agent store's fault points (stage 0) stop
   `protect` after its record and after its write, and `unprotect` after
   its record and after its plain write; at each, relaunch: the store list
   shows `pending` after `protect`'s record and `locked` after the other
   three, never both copies, and the switch shows on. After
   `unprotect`'s record, also `tap @t allow` on the launch's ticket and
   relaunch again: still `locked`, with a ticket. A locked `set` the fault
   point fails: `locked` stays true and `unlock` answers the previous
   token; when the retry lands, the new one. A `protect` interrupted after
   its record, then a relaunch: the name reads pending, no frame before
   the first data answer shows a channel or a message, and no token bytes
   are in a per-call snapshot, the carry or `state` before the move or
   after it; with the device credential then withdrawn (`prefer extension
   local-auth.localAuthStatus=` the full default status with
   `deviceCredential` false), the move is
   impossible, the copy is deleted and the name reads absent.
9. On the web: no lock switch; `state.extensions` shows `local-auth`
   unavailable, and `protect` in the fixture's test rejects
   `NotSupportedError`.
10. By hand, against the real implementations (Charlie): on an iPhone with
    Face ID, the permission prompt with `purpose.lock`'s text, then the
    lock on relaunch, on a return, and on a return after the phone has
    slept; removing the passcode
    in Settings, then relaunching, shows "Sign in again". On a Mac with
    Touch ID and a profile, the same. On an Android phone, the prompt with
    a fingerprint and with the PIN, and the return lock, including after
    the phone has slept.

Drives 1–9 run the substitute; the conformance suite (D16) runs the real
implementations on the simulator and the emulator.

## 11. Building it

Each stage lands green under the six checks and is driven before the
next.

0. **The secret's seam, with no device code.** First, and building stops
   if it cannot hold: the runner's occupancy for presence names, and tests
   that a locked name's bytes never reach the `Store`'s values, the boot
   snapshot, a per-call snapshot (the module ABI, the web's wasm and
   worker dispatch), a carry, the journal or `state`, on every runtime
   (the Rust runner, Hermes, the web's JS runtime and its worker), and
   that no kept answer shows, and `get` throws, on a launch that begins
   locked or pending. Then: the
   policy words, `optional` and their refusals in the four grant parsers;
   `device.local-auth`; the five store operations and `get`'s refusal on
   every runtime, with the TypeScript and Rust declarations; the agent
   store's presence backend with D4's moves, the per-name queue, the
   reconciliation and fault points for drives 4 and 8; `@exact/local-auth`'s `exact.json` and the
   endorsed implementations' declarations; the authenticator entry's
   declaration; the substitute and tickets of §7; the origin rule for
   presence; Excord's Contract, `app.ts` and strings, with a test that its
   session answer carries no token. Driven: §9's drives 1–8 on macOS
   under the agent, drive 9 on the web.
   **As built (2026-10-23).**
   - *Grants.* The four parsers read `secret.keep <name> <policy>
     [optional] [platform words]` (`grants/src/presence.rs`, mirrored in
     `ibex2`'s `grant.rs`; `Grants::presence`; `module_secret_names`), as
     does the browser's validator (`host/web/navigation.js`), which the
     shared corpus checks; each refuses `grant-policy-unknown` and an
     `exact.presence.` name. The bake (`bake/src/reach.rs`) refuses
     `grant-missing` for a presence line without `device.local-auth` or
     without the `@exact/local-auth` dependency, and
     `grant-policy-conflict` between the TypeScript and Rust sources.
     `device.local-auth` is a row of the device table:
     `NSFaceIDUsageDescription` on iOS, `USE_BIOMETRIC` on Android,
     nothing on macOS, the web and tvOS.
   - *The store.* Occupancy is a runner-owned entry,
     `exact.presence.<name>` (`absent`, `plain`, `pending`, `locked`), and
     `exact.presence.` alone says the host keeps locked secrets now
     (`runner/src/store/presence.rs`). A deviation from D5's "a field of
     their own": the entries travel in the one list every snapshot, carry
     and per-call snapshot already is, so no seam changed shape; an empty
     value is still never a locked name. The `Store` drops a locked or
     pending name's bytes from any snapshot, refresh or carry; `get`
     refuses it (`InvalidAccessError`; a Rust source's answer that read it
     fails, in process and across the logic-module seam); a locked `set`
     carries its value to the backend and keeps none, and is refused at
     once (`NotSupportedError`) where no locked secret can be kept. A
     launch that begins locked or pending shows no kept answer
     (`seed_kept`, with a journal line). The per-call snapshots (the logic
     ABI, data workers' envelope, the web's wasm worker dispatch) take
     `Store::call_snapshot`: values and occupancy of the granted names.
   - *The backend.* `exact_runner::presence::Backend` is D4's logic over a
     host's `Vault` (the plain store, the records, the locked items): one
     queue per name, each move in D4's order with its intent recorded
     first, the boot reconciliation toward locked, the newest generation
     kept, a refused write retried a second later while the previous value
     stays readable. A deviation from D13's placement: the moves are Rust
     shared by every host rather than written again in Swift and Kotlin;
     each host supplies the vault's primitives (stage 1, Apple's keychain;
     stage 2, Android's Keystore), and the sheet stays the module's. The
     runner holds the backend, routes every committed write of a presence
     name to its queue, and adopts its occupancy at the start of each
     commit; a move the app asked for asks no reader again (its call's
     answer tells the app), so a socket's resource is not reconnected.
     Under the agent the vault is the drive's own store
     (`host/apple/src/presence_secrets.rs`): plain copies in its secret
     store, records and locked items in its kv store (`exact.presence`,
     `exact.presence.agent`), in memory or the named drive's scratch tree.
   - *The calls.* `store.unlock`, `protect` and `unprotect` are long native
     calls whose body is `{"presence": …}`, answered by the runner on the
     store's path (`runner/src/runner/modules/presence.rs`), never by a
     module; the journal names the call and how it ended, the reply's size
     and never its value. A tool's or a wake's `unlock` or `unprotect` of a
     locked name fails `person-required` before anything is asked.
   - *The runtimes.* Hermes: door ops 18 to 20 and the five operations,
     from a helper in `js/src/binary.js` (`prelude.js` is at its line
     cap); the web's wasm realm and worker read occupancy from the call's
     snapshot; the web JS target's store refuses a name that must be
     locked (`NotSupportedError`) and keeps an `optional` one plain, with
     `protect` rejecting. The TypeScript `Store` declares the five; Rust
     has `Store::has`, `locked`, `read` and `exact_data::presence`'s
     request builders and reply reader.
   - *The substitute,* declared in `exact.json`: `check` (the `presence`
     ticket, `allow`, `fail`, `lockout`, `cancel`, and `unless` the status
     says nothing can be checked, `NOT_AVAILABLE`); `permission.asks`
     (only Face ID asks); `permission.continues` (a denial fails only a
     `biometricOnly` call); `facts` (`presenceSecrets` is the session's);
     `web` (the web's status, read by the JS runtime); a name's `origin:
     "person"` (`PERMISSION_DENIED`, `person-required`, for a tool or a
     wake, before any ticket); and `authenticator.substitute`, the store
     checks' ticket and codes, with `invalidated` for `unlock`. Driver
     faults stop a move after a step as a crash would
     (`exact-presence:<op>.<step>`), hold one there
     (`exact-presence:hold.<op>.<step>`, `hold.move`), or refuse a locked
     write (`exact-presence:set`), armed with the agent's `fail fetch`.
   - *The web* gained an implementation (`web/`) that answers D15's status
     and `NotSupportedError`, so a page outside the agent says what the
     substitute says under it; without one the status failed and showed

   - *Excord:* the grants, a strings table, the account menu's Lock switch
     (shown only where `presenceSecrets`), the lock screen, the launch's
     unlock, the return lock, and "Sign in again" on its sign-in screen

     `/control/rotate-token` and `identify_token`. Its session answer

   - *Tests:* the backend's moves and reconciliation

## 12. Rulings (Charlie, 2026-10-23: "Accept all (Recommended)")

Each question below was ruled as recommended.

1. **The policy in the grant line** (D4), with `optional` for a lock the
   person chooses, not an argument to each write. *Recommended: yes
   (80%).* A per-write argument can be missed on one path and keeps a
   token ungated with no sign; the grant is enforced on every write,
   including a rotated token's, and is known before boot.
2. **The module authenticates; the host's backend keeps** (D13), with the
   authenticator entry as a public part of this interface and a store
   completion path that carries a value to its caller alone.
   *Recommended: yes (75%).* The alternatives put a secret on the
   journaled module route or give the system sheet two owners.
3. **No kept answer on a launch that begins locked** (D5), at the cost of
   placeholders until data code answers for a locked app. *Recommended:
   yes (85%).* Otherwise the lock screen arrives after the last launch's
   messages.
4. **The web is `later`, over passkeys** (D15), and refuses a locked
   secret meanwhile rather than keep it in `localStorage`. *Recommended:
   yes (85%).*
5. **macOS locked secrets need a provisioned build** (D7), and a Mac
   provisioning profile becomes a build input. *Recommended: yes (85%);
   the alternative, the file-based keychain, has no presence check to
   offer.* Ruled on its own first (Charlie, 2026-10-23: "Allow it").
6. **Presence is not delegable** (D12), whatever delegation rule LLP 1111
   later writes. *Recommended: yes (90%).*
7. **An impossible move deletes the plain copy** (D4): a name the line or
   the person said must be locked, whose plain copy cannot be moved (no
   device credential, a Mac without a profile), is deleted, and the app
   signs in again. *Recommended: yes (80%).* Keeping it on disk would
   keep a readable token while the app shows a lock; the platforms
   themselves delete passcode-bound items when the passcode goes.
8. **Excord's lock as the consumer** (§9), amending Excord's `llp/0001`.
   *Recommended: yes (75%); the alternative, Fieldnotes' lock as Apple's
   Journal app has, exercises only the check, since Fieldnotes keeps no
   secret worth gating.*
