## Summary

`@exact/local-auth` lets an app ask the person in front of the device to
prove they are its owner, with Face ID, Touch ID, Optic ID, a fingerprint
or face on Android, or the device's passcode, on iOS, macOS and Android
first. It has two halves, because the platforms give two things of very
different strength:

- **A check,** `authenticate(reason=)`: the platform's sheet, and an answer
  the app's code acts on. It gates a screen. A process that is tampered
  with can flip its answer, so it protects nothing at rest.
- **A secret only a person present can read:** a `secret.keep` name whose
  grant line carries a policy, `secret.keep discord-token.locked
  user-presence`. The platform's secure hardware releases the bytes only
  after the check: the Secure Enclave for a keychain item with access
  control on Apple, the Keystore's TEE or StrongBox for a key that needs
  authentication on Android. Data code reads it with `await
  store.unlock(name, { reason })`, a request that shows the sheet; it is
  never in the boot snapshot, a carry, a kept answer, the journal or the
  agent's state.

```
use authenticate, localAuthStatus, LocalAuthStatus from "@exact/local-auth"

resource lock = localAuthStatus() as shape LocalAuthStatus
mutation unlocked as shape LocalAuthentication then reveal
action unlock
  send unlocked = authenticate(reason="reason.unlock")
```

```ts
// app.ts: grants 'secret.keep discord-token.locked user-presence', 'device.local-auth purpose.lock'
const token = await store.unlock('discord-token.locked', { reason: 'reason.unlock' });
```

The web has no local authentication of its own: WebAuthn's user
verification is the nearest thing, and serving either half from it costs a
passkey registered for the purpose. The web cell is `later`, to be filled
over the passkeys module (wave 2's next), and until then the module answers
`available: false` there and a presence secret is refused, never kept as a
plain one (D15).

The consumer is Excord, the Discord client, which keeps a token that is
the whole of Charlie's main account. "Lock Excord", as WhatsApp, Signal and
Telegram offer, keeps that token behind presence: a cold launch shows the
sheet before the gateway can open, and a return from the background after a
minute shows the lock screen and asks `authenticate` (§9).

## 0. What is new here

LLP 1133 D5 named this module "a parameter of `secret.keep`", and LLP
1133.000 §3.1 gave it a tier 1 `authenticate(reason=)` beside it. Writing
it out shows four things the parent RFCs did not settle, each answered
below and each a question for Charlie in §12:

1. **The store reads secrets before boot, synchronously, on the main
   thread** (LLP 1018 D1, D6); reading a presence secret shows a sheet and
   blocks its caller. A presence secret therefore cannot be a store value
   at all: it is a request, read after first pixel, off the main thread
   (D5, D8).
2. **The sheet and the bytes have different owners.** The module's reply
   route is inspected, journaled and shown to the agent (LLP 1133 D6 rule
   1); a secret must never travel it (LLP 1018 D5). The store must not show
   UI of its own, or the person sees two owners of one sheet. So the
   module authenticates and the store keeps: a narrow, public entry by
   which a host's data capability asks the bound implementation for an
   authenticated context (D13). It is the first data capability served by
   a package, and amends LLP 1133.001.
3. **macOS's keychain cannot gate an item exact2 writes today.** exact2's
   Mac secrets are in the file-based login keychain (LLP 1018 D7); access
   control with biometry needs the data-protection keychain, whose access
   group needs entitlements a provisioning profile authorizes ([TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)).
   A Mac build without a profile cannot keep a presence secret, and says
   so rather than keep it ungated (D7).
4. **Presence is not delegable.** LLP 1133's direction lets agents come to
   grant agents a capability the platform granted the app (§0 ruling 10;
   LLP 1133.002 D12). A presence check is a person's act at a moment;
   nothing an agent holds can satisfy it, and no reuse window carries it
   from a person's call to a tool's (D12).

## 1. Tier 1

### D1 — The names

There is no web API for local authentication. The nearest is WebAuthn's
user verification: an authenticator's check, "biometric or PIN", reported
in the assertion's `UV` flag, requested with `userVerification:
"required"`, with `PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable()`
as its feature test ([WebAuthn §5.1.7, §6.2.3](https://www.w3.org/TR/webauthn-3/)).
It is a ceremony over a credential the relying party registered, not a
local check. So the names are a **declared deviation**, the words Apple's
LocalAuthentication and Android's BiometricPrompt share, with WebAuthn's
meaning of "user verification" as the default policy:

| Name | Kind | Meaning | Contract | Data code |
|---|---|---|---|---|
| `authenticate(reason, biometricOnly)` | send; a request | the platform's sheet; answers when the person passes, fails otherwise | `send x = authenticate(reason="…")` | `await authenticate({ reason })` |
| `localAuthStatus()` | live source; a fact; `sync` | what this device can do now, and the biometry permission (D12) | `resource s = localAuthStatus()` | `await localAuthStatus()` |
| `store.has(name)` | the store; synchronous | whether a value is kept under a granted name, without reading it | — | `store.has('x')` |
| `store.unlock(name, { reason })` | the store; a request | a presence secret's value, after the sheet; `null` when nothing is kept | — | `await store.unlock('x', { reason })` |

`reason` is a strings key (LLP 1060), as geolocation's `purposeKey` is
(LLP 1133.002 D10): the text is translated with the app's others, and the
bake checks the key. Apple shows it under the app's name on the Touch ID
and passcode sheets, not on Face ID's ([Logging a user into your app with
Face ID or Touch ID](https://developer.apple.com/documentation/localauthentication/logging-a-user-into-your-app-with-face-id-or-touch-id));
Android shows it as the prompt's title, which `BiometricPrompt.Builder`
requires ([`setTitle`](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt.Builder#setTitle(java.lang.CharSequence))).

**Values.**

| Shape | Fields |
|---|---|
| `LocalAuthentication` | `timestamp` (ms since the epoch); `android` (`authenticationType`, D10) |
| `LocalAuthStatus` | `available`: the default policy can be evaluated now (a device credential is set, or biometry is enrolled and the policy is biometric); `biometry`: `faceID`, `touchID`, `opticID`, `other` or `none`; `deviceCredential`: a passcode, PIN, pattern or password is set; `state`: the biometry permission, `granted`, `prompt`, `denied` or `unknown` (D12); `presenceSecrets`: this target can keep a presence secret (D7); `apple`, `android` (D10) |

`biometry` is Apple's `LABiometryType`
([biometryType](https://developer.apple.com/documentation/localauthentication/lacontext/biometrytype)).
Android does not name the modality, so it reads `other` when a biometric
of the allowed class is enrolled, and the platform's own label for it
("Use fingerprint", "Use face") is a tier 2 field (D10), which is what a
hand-built Android app shows.

**Errors.** In Contract, `failure(…).code`; in TypeScript and Rust a
rejection `{code, message}`, as LLP 1133.002 D1 does:

| Code | Apple ([`LAError.Code`](https://developer.apple.com/documentation/localauthentication/laerror-swift.struct/code)) | Android (`BiometricPrompt` errors) |
|---|---|---|
| `USER_CANCEL` | `userCancel`, `userFallback` | `ERROR_USER_CANCELED`, `ERROR_NEGATIVE_BUTTON` |
| `SYSTEM_CANCEL` | `systemCancel`, `appCancel` | `ERROR_CANCELED`, `ERROR_TIMEOUT` |
| `AUTHENTICATION_FAILED` | `authenticationFailed` | (failed attempts are not terminal on Android; the prompt ends in `LOCKOUT` or a cancel) |
| `LOCKOUT` | `biometryLockout` | `ERROR_LOCKOUT`, `ERROR_LOCKOUT_PERMANENT` |
| `NOT_AVAILABLE` | `biometryNotAvailable`, `biometryNotEnrolled`, `passcodeNotSet`, `biometryNotPaired`, `biometryDisconnected`, `companionNotAvailable`, `watchNotAvailable` | `ERROR_HW_UNAVAILABLE`, `ERROR_HW_NOT_PRESENT`, `ERROR_NO_BIOMETRICS`, `ERROR_NO_DEVICE_CREDENTIAL`, `ERROR_SECURITY_UPDATE_REQUIRED` |
| `PERMISSION_DENIED` | a biometric-only policy after the person refused Face ID (D12) | — |
| `PERMISSION_DENIED`, message `person-required` | `notInteractive`, and every tool, wake or headless origin (D12) | the same |
| `NotSupportedError` | — | — (the web; a target without the module; a presence secret where `presenceSecrets` is false) |

The platform's own code and message travel as tier 2 (`apple.code`,
`android.code`), so an app that needs the finer case has it.

**Declared deviations.**

- The names themselves (above).
- Errors are domain codes, not WebAuthn's single `NotAllowedError`, which
  merges cancel, failure and lockout on purpose so a web page learns less
  ([WebAuthn §6.3.3](https://www.w3.org/TR/webauthn-3/)). A local check has
  no such reason, and a hand-built app shows a different screen for a
  cancel than for a lockout.
- `store.unlock` returns a promise where `store.get` is synchronous: a
  presence secret is a request.

### D2 — What each half guarantees, and what it does not

This is the module's security model, and the reason it has two halves.

| | `authenticate()` | a presence secret |
|---|---|---|
| What it establishes | the platform told the app's code that a person passed its check, moments ago | the platform released the bytes only after its check |
| Who enforces it | the app's own code, acting on a result | the Secure Enclave, which "passes back a pass/fail result that gates keychain item access" ([Apple](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id)); on Android the Keystore, whose key with authentication required cannot be used without the authenticator's token ([`setUserAuthenticationRequired`](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUserAuthenticationRequired(boolean))) |
| Against a tampered process (a hook, a debugger, a modified build) | nothing: the result is a value in memory | holds: without the check the hardware does not decrypt |
| Use it for | showing a screen; confirming an action no server needs to trust | a token, a key, anything that must stay closed at rest |
| Do not use it for | protecting data; proving anything to a server | proving anything to a server (that is attestation's and passkeys', LLP 1133.000 §3.1) |

OWASP's mobile testing guide calls the first "event-bound" and recommends
the second for anything sensitive ([MASTG-BEST-0036](https://mas.owasp.org/MASTG/best-practices/MASTG-BEST-0036/)).
The recipe says which to use, and an agent writing an app is told the same
in `docs/contract-for-agents.md`.

**Per host, what a presence secret guarantees:**

| Host | Kept as | Enforced by | Notes |
|---|---|---|---|
| iOS, iPadOS | a generic-password item in the data-protection keychain with a `SecAccessControl` (D6) | the Secure Enclave | `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly`: never in a backup restored to another device, and deleted when the passcode is removed ([the constant](https://developer.apple.com/documentation/security/ksecattraccessiblewhenpasscodesetthisdeviceonly)) |
| macOS | the same, in the data-protection keychain, which needs a provisioned build (D7) | the Secure Enclave on a Mac with one (Apple silicon, T2); the system's keychain service otherwise | a Mac without Touch ID asks for the login password under `user-presence` |
| Android | ciphertext in the app's private storage, decrypted by a Keystore key that requires authentication for every use (D6) | the TEE, or StrongBox when asked (D10); software on a device with neither (an emulator), which `android.securityLevel` reports | the key is "irreversibly invalidated once the secure lock screen is disabled" ([Keystore](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUserAuthenticationRequired(boolean))) |
| web | refused (D15) | — | never a `localStorage` value in its place |
| Linux, Windows | `later`; refused until then | — | never the plain `0600` file in its place |
| under the agent | the agent's own memory or scratch store | nothing: tickets answer (§7) | never a real keychain item or Keystore key |

**What it never guarantees:**

- **That the person is the owner.** Anyone enrolled, or anyone who knows
  the passcode, passes `user-presence`. `biometry-current-set` narrows that
  to the biometrics enrolled when the secret was kept (D4).
- **What happens to the value after.** `unlock` hands the bytes to the
  app's data code, which keeps them in memory for as long as it chooses,
  and may use them from any caller, a tool's included. Presence gates the
  read, not the use.
- **Anything about the server's view.** A server that must know a person
  was present needs a signature it can check: a passkey (wave 2, next) or
  an attested key. A presence-gated signing key in the Secure Enclave is
  LLP 1069.005 D1b's "after a security review", and stays out (§8).

### D3 — Unsaid defaults are the platform's

| Default | Apple | Android | Source |
|---|---|---|---|
| `authenticate`'s policy | `deviceOwnerAuthentication`: biometry, Watch or passcode | `BIOMETRIC_WEAK \| DEVICE_CREDENTIAL` on API 30 and later; `setDeviceCredentialAllowed(true)` on API 29 | Apple's own sample evaluates `deviceOwnerAuthentication`; both match WebAuthn's "user verification", any method the authenticator has |
| `biometricOnly=true` | `deviceOwnerAuthenticationWithBiometrics` | `BIOMETRIC_WEAK`, with a negative button the platform labels "Cancel" from API 36.1 and the module labels with the platform's `android.R.string.cancel` before | [`LAPolicy`](https://developer.apple.com/documentation/localauthentication/lapolicy); [`setNegativeButton`](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt.Builder#setNegativeButton(java.lang.CharSequence,%20java.util.concurrent.Executor,%20android.content.DialogInterface.OnClickListener)) |
| reuse of the device's own unlock | none (`touchIDAuthenticationAllowableReuseDuration` 0) | none | [the property](https://developer.apple.com/documentation/localauthentication/lacontext/touchidauthenticationallowablereuseduration) defaults to 0 |
| the fallback and cancel titles | the system's | the system's | — |
| a presence secret's accessibility | `WhenPasscodeSetThisDeviceOnly` | `setUnlockedDeviceRequired(true)` (API 28) | Apple's sample for this very use |
| a presence secret's key | — | a Keystore key pair whose private half needs authentication for every use; the public half encrypts, which needs no person, since "public key operations are not restricted" ([Keystore](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUserAuthenticationRequired(boolean))) | so a write never shows the sheet (D5) |
| when to ask | the app's choice (LLP 1133 §0 ruling 9) | the same | the recipe recommends asking at launch and on return for an app lock, as the platforms' own apps do |

`BIOMETRIC_WEAK` for the check, where a presence secret needs
`BIOMETRIC_STRONG`, is the platform's own split: the builder's default is
`BIOMETRIC_WEAK` "for non-crypto authentication, or BIOMETRIC_STRONG for
crypto-based authentication"
([`setAllowedAuthenticators`](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt.Builder#setAllowedAuthenticators(int))).
So on a phone whose face unlock is Class 2, the check accepts a face and a
presence secret asks for a fingerprint or the PIN, as a hand-built app's
would.

## 2. Presence secrets

### D4 — The policy is in the grant line

```
secret.keep discord-token.locked user-presence
```

A `secret.keep` line may carry one policy word after the name. Each is a
shared word that both native platforms have:

| Policy | Meaning | Apple `SecAccessControlCreateFlags` | Android `setUserAuthenticationParameters(0, …)` |
|---|---|---|---|
| `user-presence` | biometry or the device credential; survives a change of enrolment | `userPresence` | `AUTH_BIOMETRIC_STRONG \| AUTH_DEVICE_CREDENTIAL`, which keeps the key valid across enrolment |
| `biometry-any` | biometry only; survives a change of enrolment | `biometryAny` | `AUTH_BIOMETRIC_STRONG`, `setInvalidatedByBiometricEnrollment(false)` |
| `biometry-current-set` | biometry only; lost when enrolment changes | `biometryCurrentSet` | `AUTH_BIOMETRIC_STRONG`, `setInvalidatedByBiometricEnrollment(true)` |
| `device-credential` | the passcode, PIN, pattern or password only | `devicePasscode` | `AUTH_DEVICE_CREDENTIAL` |

Sources: [`SecAccessControlCreateFlags`](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags);
[`setUserAuthenticationParameters`](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUserAuthenticationParameters(int,%20int))
(API 30) and [`setInvalidatedByBiometricEnrollment`](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setInvalidatedByBiometricEnrollment(boolean)).
Platform words may follow the policy on the same line (D10).

**Why the grant and not each write.** LLP 1133.000 sketched
`secret.keep(…, requireUserPresence=)` as an argument. The grant is better
for four reasons:

- **It cannot be forgotten at one call site.** Every write of the name,
  from any code path, is kept under the policy by the host; an argument
  missed on one `store.set` would keep the token ungated, silently.
- **The host knows before boot,** without reading the platform, which
  names are never in the snapshot (D5), and the bake knows which names
  need `device.local-auth` and, on macOS, a profile (D7).
- **It is reviewable.** The grant set is the app's statement of authority
  (LLP 1018 D3); a reader sees which secrets are gated where the others are
  listed.
- **The grammar is the existing one.** `secret.keep <name>` grows a word;
  no Contract or store signature changes for a plain name.

An app that lets the person choose (Excord's switch, §9) grants two names
and moves the value between them, which is what a hand-built app does with
two keychain items.

**Refusals at bake,** by name: a policy word that is not one of the four
(`grant-policy-unknown`); a presence policy without a `device.local-auth`
line in the same app (`grant-missing`, naming the line), since Face ID
will not run without `NSFaceIDUsageDescription` (D12); a name both kept
and held (LLP 1133.007 D8's `secret-name-twice`, unchanged).

**A name's policy changes between versions.** The host enforces the line
it was built with:

- **plain to presence:** after first pixel, the host moves a plain item
  under that name to the policy (it reads it without a person, keeps it
  gated, then forgets the plain one), so an update that adds a lock keeps
  the person signed in and leaves no plain copy;
- **presence to plain:** the gated item is not read; `has` reads false,
  and the next `set` replaces it. An update that removes a lock costs a
  sign-in, never a silent copy;
- **one policy to another:** as presence to plain: the old item is
  forgotten unread.

### D5 — A presence secret is never a store value

The store's guarantee (LLP 1018 D1) is that a granted secret is in the
snapshot the host reads before boot, so the first frame knows the person.
A presence secret is the opposite case, and every place a store value can
reach is closed to it:

| Where a plain secret goes | A presence secret |
|---|---|
| the boot snapshot (LLP 1018 D1) | never; the host records only whether one is kept (`has`) |
| a worker's or the module ABI's per-call snapshot (LLP 1133.007 D8) | never |
| a dev reload's carry (`Carried.store`) | never |
| `store.get(name)` | throws `InvalidAccessError`, "a presence secret is read with `store.unlock`", so an app never mistakes a locked token for none |
| a kept answer (`exact.kept.*`) | the answer may be kept, as any answer is; the value itself is never in it, since no answer may carry a secret (LLP 1018 D5) |
| the journal, `state`, a crash report | its name and policy only |
| bake | the bake's store is empty (LLP 1018 D4); `has` reads false, and `unlock` refuses at bake as a device read |

**The operations on a presence name:**

- **`store.has(name)`,** synchronous, from the snapshot. The host learns it
  without reading the value and without any chance of a prompt: on Apple an
  attributes-only query under an `LAContext` whose
  [`interactionNotAllowed`](https://developer.apple.com/documentation/localauthentication/lacontext/interactionnotallowed)
  is true, on Android the ciphertext's presence. `has` works for plain
  names too.
- **`await store.unlock(name, { reason })`:** a request (LLP 1069.007 D1).
  It is admitted as LLP 1133.002 D14 admits a module request (the grant,
  the target, the origin, the queue of decisions), then shows the sheet
  through the bound local-auth implementation (D13), then reads. It
  answers the value, or `null` when nothing is kept or the platform has
  dropped the item (D6), or fails with D1's codes. The value is the
  promise's result alone: it does not enter the runner's `Store`, so a
  later `store.get` or `unlock` does not see it, and nothing outlives the
  call but what the app's code keeps.
- **`store.set(name, value)`** keeps it under the policy and never shows
  the sheet: on Apple, adding an item with access control asks nothing; on
  Android the public key encrypts (D3). It rides the commit as every store
  write does (LLP 1018 D1). It throws `NotSupportedError` at once when
  `localAuthStatus().presenceSecrets` is false (D7, D15) or no device
  credential is set (the platforms refuse such an item:
  `WhenPasscodeSetThisDeviceOnly` stores nothing without a passcode, and a
  Keystore key that needs authentication "can only be generated if secure
  lock screen is set up"). A write the platform refuses later is journaled
  and `has` reads false after it, as LLP 1018 D6 treats a failed write.
- **`store.forget(name)`** removes it, asking nothing.

**One name per sheet.** `unlock` reads one name. A hand-built app that
needs several secrets behind one sheet keeps them as one item; an app here
keeps them as one value (a record as JSON, as LLP 1018 D3 keeps a session),
which costs one sheet on both platforms. Several names in one call would
cost one sheet on Apple (one evaluated `LAContext` serves several items,
[`kSecUseAuthenticationContext`](https://developer.apple.com/documentation/security/ksecuseauthenticationcontext))
and one per name on Android, where an authentication authorizes one
cryptographic operation; the module does not promise what one platform
cannot keep.

**No reuse across calls.** Each `authenticate` and each `unlock`
evaluates afresh. No evaluated context outlives the call that evaluated
it, so no later caller, and in particular no tool (D12), inherits a
person's check. Apple's reuse of the device's own Touch ID unlock is a
tier 2 word, off unless written, and is the platform's rule, not a reuse
of the app's check (D10).

### D6 — Each platform's mechanism

**Apple.** One generic-password item per name, in the data-protection
keychain (`kSecUseDataProtectionKeychain`), its `kSecAttrService` the app's
store service plus `.presence`, so the plain items' code (`ibex2`'s
`KeychainStore`) never meets one. `kSecAttrAccessControl` is
`SecAccessControlCreateWithFlags(kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly,
<the policy's flag>)`. An `unlock`:

1. the bound implementation evaluates an `LAContext` against the item's
   access control,
   [`evaluateAccessControl(_:operation:localizedReason:reply:)`](https://developer.apple.com/documentation/localauthentication/lacontext/evaluateaccesscontrol(_:operation:localizedreason:reply:))
   with `.useItem`, which shows the sheet (D13);
2. the store reads the item with `kSecUseAuthenticationContext` set to that
   context, which "will succeed without asking user for authentication",
   off the main thread, since `SecItemCopyMatching` "blocks the calling
   thread" ([SecItemCopyMatching](https://developer.apple.com/documentation/security/secitemcopymatching(_:_:)));
3. the context is invalidated (`invalidate()`), and the value goes to the
   caller (D8).

An item the platform has dropped (the passcode removed; a
`biometryCurrentSet` item after enrolment changed) reads as not found, and
`unlock` answers `null`.

**Android.** Per policy, one Keystore key pair under an alias of the app's
(`exact.presence.<policy>`), generated at the first write of a name with
that policy: RSA with OAEP padding, `setUserAuthenticationRequired(true)`,
`setUserAuthenticationParameters(0, <the policy's types>)`,
`setUnlockedDeviceRequired(true)`. Per name, a file in the store's private
directory holding an AES-GCM data key wrapped by the public key and the
value sealed under it. An `unlock`:

1. the store initialises a decrypting `Cipher` over the private key;
2. the bound implementation shows `BiometricPrompt` with that cipher as its
   `CryptoObject`, with the policy's authenticators (D13);
3. on success the store unwraps the data key and opens the value, on a
   background executor;
4. a `KeyPermanentlyInvalidatedException` at step 1 means the platform has
   dropped the key: the store deletes the key and every file sealed under
   it, and answers `null`.

`DEVICE_CREDENTIAL` with a `CryptoObject` is API 30 and later; on API 29
(`minimumOS` `"10"`), `presenceSecrets` is false and a presence write
throws `NotSupportedError`. The files are excluded from Auto Backup and
device transfer (`dataExtractionRules`), since a restored ciphertext
without its key could never open.

**Reinstalling.** iOS keeps keychain items after an app is deleted, and
LLP 1018 D7 owes a first-launch wipe for plain secrets. Presence items join
that wipe. Android removes the app's keys and files with the app.

### D7 — macOS needs a provisioned build

The data-protection keychain's access groups come from the app's
code-signing entitlements, which "must be authorized by a provisioning
profile", and "protecting an item with biometrics (Touch ID and Face ID)"
requires that keychain ([TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)).
exact2's Mac builds use the file-based login keychain (LLP 1018 D7), and
only the widget cohort plans a profile (LLP 1126.001 WP16 Q5).

So on macOS:

- a build with a profile that authorizes `keychain-access-groups` (or the
  application identifier) keeps presence secrets as D6 says, and the bake
  derives the entitlement from the presence lines;
- a build without one reads `presenceSecrets: false`, and a presence
  `set` throws `NotSupportedError`; `authenticate` works, since evaluating
  a policy needs no keychain;
- a release build with a presence line and no profile is refused at bake
  (`grant-needs-profile`), so nothing ships that cannot keep what it
  grants;
- **it never falls back** to the file-based keychain, whose access model
  is an application ACL with no presence check.

`host/apple/build.mjs` already finds a team identity for iOS devices; a Mac
profile is a new input, which Charlie supplies for the Mac drives, as
WP16's does.

### D8 — The sheet's thread, and one at a time

**Never before first pixel, never on the main thread.** Boot reads only
`has` (D5). The sheet is shown by the platform's own presentation; the
read that follows runs off the main thread (D6); the answer reaches the
runner on its thread, as a module's answer does (LLP 1067.000 D4). A
TypeScript source placed on a worker awaits a promise like any other; the
runner never waits.

**Apple.** `evaluatePolicy` and `evaluateAccessControl` reply on a private
queue; the implementation hops to the main thread to settle the call. The
platform presents the sheet over the app's active window. On iPad with
several scenes the sheet follows the system's choice of window; the
module does not pick one.

**Android.** `BiometricPrompt.authenticate` is called on the main thread of
the resumed `ExactActivity`, with the main executor for its callback, and
the decryption runs on a background executor. The reader's module slot
(request kind 11, LLP 1133.002 §11 stage 4) carries the call from the
runner's thread. A request while the activity is not resumed fails
`SYSTEM_CANCEL` at once rather than wait for a resume that may not come.
The platform cancels a prompt when its activity is recreated, and advises
a retained fragment to survive configuration changes
([`authenticate`](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt#authenticate(android.os.CancellationSignal,%20java.util.concurrent.Executor,%20android.hardware.biometrics.BiometricPrompt.AuthenticationCallback)));
`ExactActivity` handles rotation, size, density and the other common
changes itself (`host/android/app/src/main/AndroidManifest.xml`), so the
prompt survives them, and a recreation that does happen settles the call
`SYSTEM_CANCEL`.

**One sheet at a time.** `authenticate` and `unlock` join LLP 1133.002
D9's queue of decisions, so a Face ID sheet never opens over a location
prompt or another sheet. Unlike a permission decision, a presence check is
never shared: two queued `unlock`s show two sheets, one after the other,
since each authorizes one operation (D5). A call cancelled while queued
leaves the queue; a call cancelled while its sheet is up cancels the sheet
(`LAContext.invalidate()`, the `CancellationSignal`).

**Leaving the foreground.** The platforms cancel the sheet when the app
leaves the foreground; the call fails `SYSTEM_CANCEL`, and the app asks
again on return if it wants to (the recipe's lock screen does).

## 4. Permission: one grant line, one state, presence not delegable

### D12 — LLP 1133.002 §4 for this module

**Declare.** `device.local-auth <purposeKey>`:

| Target | Derived | Does the system show the purpose? |
|---|---|---|
| iOS, iPadOS | `NSFaceIDUsageDescription` | yes, the first time the app uses Face ID; "without this key, the system won't allow your app to use Face ID", and Touch ID needs no such string ([Apple](https://developer.apple.com/documentation/localauthentication/logging-a-user-into-your-app-with-face-id-or-touch-id)) |
| macOS | nothing (Touch ID asks no permission) | — |
| Android | `android.permission.USE_BIOMETRIC`, a normal permission granted at install | — |
| web | nothing until its cell is filled | — |

A binding call, a Contract use of the module, or a presence line with no
`device.local-auth` line refuses at bake (`grant-missing`).

**Read.** `localAuthStatus().state` is the biometry permission, which only
Face ID has:

| Platform state | `state` |
|---|---|
| Face ID, the app has not used it | `prompt` |
| Face ID, used and allowed | `granted` |
| Face ID refused for the app (`canEvaluatePolicy` of a biometric policy fails `biometryNotAvailable` while `biometryType` is `faceID`) | `denied` |
| Touch ID, Optic ID on visionOS when built, Android, macOS | `granted` (nothing to ask) |
| no biometry | `granted`, with `biometry: none` |
| web | `unknown` |

Apple gives no call that tells `prompt` from `granted`, so the Apple
implementation keeps, in its own defaults, whether an evaluation that could
use Face ID has completed, as geolocation's Android implementation keeps
its history (LLP 1133.002 D8). The status is asked again on a return to
the foreground, since the person can change it in Settings.

**What a denial means.** Refusing Face ID does not stop the module:
`deviceOwnerAuthentication` and `user-presence` fall back to the passcode.
Only a biometric-only call or policy fails, `PERMISSION_DENIED`. So
`available` stays true under `denied` when a passcode is set.

**Ask.** There is no separate request: the platform asks at the first
evaluation that would use Face ID, inside `authenticate` or `unlock`.
Admission (LLP 1133.002 D14) treats such a call as one that may show a
dialog in every state, since the presence sheet is itself system UI.

**Explain and recover.** The app's own UI, and `openURL("app-settings:")`
to the app's page in Settings (LLP 1133.002 D11).

**Origin.** Every call carries its origin (LLP 1133.002 D12):

| Origin | `authenticate`, `unlock` | `store.has`, `set`, `forget` | `localAuthStatus` |
|---|---|---|---|
| a person's input; the app's own code in a foreground session | shows the sheet (D8) | proceed | answers |
| a tool invocation (LLP 1111) | fails `PERMISSION_DENIED`, `person-required`, before reaching the platform, in every state | proceed under the app's grant | answers |
| a background wake (LLP 1114.001); a headless session | fails `person-required` | proceed | answers |
| the development agent | §7 | §7 | §7 |

**Presence is not delegable.** LLP 1133.002 D12's direction lets an agent
come to hold, and pass on, authority the platform granted the app. A
presence check is not such authority: it is a person's act at a moment,
on this device. No delegation record, no reuse window and no earlier
check by a person satisfies it for a tool. This is why D5 keeps no
evaluated context across calls, why Touch ID's unlock reuse is refused to
a tool's call before it reaches the platform, and why a hatch cannot clear
`interactionNotAllowed` (D11). A tool that needs what a presence secret
guards asks the person through the app's own UI, which then calls
`unlock` from the person's input.

## 5. Packaging and callers

### D13 — The module authenticates; the store keeps

**`@exact/local-auth`** is an extension package (LLP 1133.001), as
geolocation is:

```
packages/local-auth/
  package.json        "@exact/local-auth"; exports ".", "./apple", "./android"
  exact.json          the interface: authenticate, localAuthStatus, their shapes,
                      the substitute, the permission, and the authenticator entry
  test/               the conformance suite and its fixture app
  apple/              exact.json, LocalAuth.swift
  android/            exact.json, LocalAuth.kt
```

**Presence secrets are exact2's vocabulary:** a data capability (LLP 1133
D5), in the grant grammars, the runner's `Store`, the runtimes' `store`
and each host's backend, because their values must stay below the data
seam (LLP 1018 D5) and the module's reply route is inspected and journaled
(LLP 1133 D6 rule 1).

**The authenticator entry joins them.** An interface may declare an entry
that a host's data capability calls, not data code:

```json
"authenticator": {
  "apple": "evaluate(accessControl: SecAccessControl, reason: String, origin: Origin) async throws -> LAContext",
  "android": "authenticate(crypto: BiometricPrompt.CryptoObject, authenticators: Int, reason: String, origin: Origin): CryptoObject"
}
```

The store holds the item or the key and never shows UI; the bound
implementation shows the sheet and never sees a value. So the system sheet
has one owner: one queue (D8), one permission history and one origin rule
(D12), one set of tier 2 words and one hatch (D10, D11), one substitute
(§7). An implementation that replaces the endorsed one (LLP 1133.001 D4)
implements the entry too; its suite checks it (D16). A replacement is
native code compiled into the app, which could read the keychain itself
in any case (LLP 1133.001 D9: a native dependency is trusted with the app).

An app with a presence line must depend on `@exact/local-auth`; the bake
refuses otherwise and names the dependency line, as `exact add` writes it.

*Rejected:*

- **The whole module as an extension,** with `getSecret` as a module
  call. The value would travel the module's reply route, which the runner
  reads, counts and shows in `state.extensions`; keeping it out would need
  a redacted lane in the seam every module uses.
- **The store authenticating by itself** (an `LAContext` in `ibex2`, a
  `BiometricPrompt` in the reader). The sheet would then have two owners:
  two permission histories, the origin rule written twice, tier 2 words on
  `authenticate` with no counterpart on `unlock`, and a hatch that reaches
  one of them.
- **The whole module as vocabulary.** `authenticate` needs nothing only
  the runner has; LLP 1133 D5's default holds for it.

This entry amends LLP 1133.001 D1: an interface may declare a host-facing
entry beside its names, in the same public package format, so a third
party can serve a data capability the same way. It stays in exact2's
library, not in a private table: LLP 1133.001 D8 holds.

### D14 — Callers

| Name | Contract | Data code | Request | `sync` |
|---|---|---|---|---|
| `authenticate` | a send | the binding | yes, always | no |
| `localAuthStatus` | a live source | the binding; `localAuthStatusSync()` where the host has `call` | no | yes on Apple; the web and Android answer asynchronously (LLP 1133.002 D14) |
| `store.has` | — | the store | no | yes, every host |
| `store.unlock` | — | the store | yes, always | no |

Contract never reads a secret (LLP 1133 §7). An app whose Contract needs
to know the session is locked reads a source its data code answers from
`store.has`, as Excord's `loadSession` does (§9). The TypeScript
declaration gains `has` and `unlock` on `Store`; the Rust `Store` gains the
same, `unlock` returning a request as `exact_data`'s other device reads do.

### D15 — Every target

| Target | `authenticate`, `localAuthStatus` | Presence secrets |
|---|---|---|
| iOS, iPadOS | LocalAuthentication | the data-protection keychain with `SecAccessControl` |
| macOS | LocalAuthentication | the same, with a profile (D7); refused without |
| Android | `BiometricPrompt`, `BiometricManager` (API 29 and later) | Keystore, API 30 and later |
| web | later: WebAuthn user verification, over the passkeys module | later: WebAuthn's `prf` extension, over the passkeys module |
| visionOS | later: Optic ID through the same LocalAuthentication | later |
| tvOS, watchOS | absent (no biometry; watchOS's wrist detection is `apple.policy` on a watch app, later) | absent |
| Windows | later: Windows Hello, [`UserConsentVerifier`](https://learn.microsoft.com/uwp/api/windows.security.credentials.ui.userconsentverifier) | later: a Hello key, [`KeyCredentialManager`](https://learn.microsoft.com/uwp/api/windows.security.credentials.keycredentialmanager) |
| Linux | later: polkit's authentication agent; fprintd where present | absent until a secret service with presence exists |
| Expose | later, when it is a host | later |
| terminal | absent | absent |

**Why the web is `later`, not built now.** WebAuthn can serve both halves:
`authenticate` as an assertion with `userVerification: "required"` over a
credential the page registered for the purpose, checked by the page
itself; a presence secret as a value sealed under a key from the
credential's `prf` extension output, which the authenticator releases only
after verifying the person ([WebAuthn §10.1.4](https://www.w3.org/TR/webauthn-3/#prf-extension)).
Three things make it a module of its own: registering means a "create a
passkey" dialog that names the site, the opposite of the platform sheet a
person expects for unlocking an app, and a tell; `prf` support varies by
browser and by credential manager; and a synced passkey makes "this device
only" untrue. The passkeys module (LLP 1133.000 §4, next in wave 2) builds
`credentials.create` and `get`; the web cell is filled over it, when an app
asks for a lock on the web.

**Until then** the web answers `available: false` and `presenceSecrets:
false`, `authenticate` fails `NotSupportedError`, and a presence `set`
throws `NotSupportedError`. An app that wants its token kept on the web
anyway grants a plain name too and chooses, in its own code, which to
write. exact2 never chooses the weaker one for it.

An app that builds a target with a `later` cell marks the module optional
there (LLP 1124 D9).

### D16 — Cost and conformance

**Cost.** An app that uses neither half links nothing of it: no
LocalAuthentication, no `USE_BIOMETRIC`, no Info.plist key (LLP 1047.001).
An app that uses it loads the module with the app's module, after first
pixel; the store's presence backend is part of the host's store and costs
a binary with no presence line nothing that runs. Stage 1 measures the
implementation's size with LLP 1047's probe and records it here.

**Conformance** (LLP 1133.001 D7), on each platform with the
implementation bound: availability and the status's fields; each error
code from the platform's own means (a cancelled sheet, a lockout, no
enrolment); an `unlock` that answers what `set` kept; `get` refusing a
presence name; a presence name absent from the boot snapshot and the
per-call snapshots; the policy enforced on every write path; an
invalidated item answering `null`; a tool-origin call failing before the
platform is asked; the authenticator entry. The iOS simulator enrols and
matches Face ID from its Features menu, and the suite drives it there;
Android's emulator touches an enrolled fingerprint with `adb emu finger
touch <id>`. A Mac's Touch ID and a phone's are driven by hand.

## 7. Under the agent: the substitute

**Shape:** `localAuthStatus` is a fact; `authenticate` and `store.unlock`
are requests (LLP 1069.007 D1).

**Facts.** `localAuthStatus`'s `state` is set by `prefer
permission.local-auth granted|denied|prompt` and `--permission
local-auth=…`, as geolocation's is; the rest by `prefer extension
local-auth.localAuthStatus=…`, which refuses a `state` field. The default:
`{available: true, biometry: "faceID", deviceCredential: true, state:
"prompt", presenceSecrets: true}`, with target restrictions applied (the
web reads `available: false` and `presenceSecrets: false`; an Android
build at API 29 reads `presenceSecrets: false`; a Mac build without a
profile reads `presenceSecrets: false`), so a drive sees each target's
real limits (LLP 1133.002 §6).

**Tickets.**

| Event | Result |
|---|---|
| `authenticate` or `unlock` while `state` is `prompt` and the policy can use biometry | a `permission` ticket; `allow` sets `granted`, `deny` sets `denied` and continues to the passcode where the policy allows it, else fails `PERMISSION_DENIED` |
| then, or at once while `granted` or `denied` | a `presence` ticket in `pending`, its `args` naming the call, the policy, the reason's text and the origin |
| `tap @t allow` | `authenticate` answers; `unlock` answers the agent store's value, or `null` when it keeps none |
| `tap @t cancel` | fails `USER_CANCEL` |
| `tap @t fail` | fails `AUTHENTICATION_FAILED` |
| `tap @t lockout` | fails `LOCKOUT` |
| `tap @t invalidated` (`unlock` only) | the agent store drops the item, as the platform would; answers `null`, and `has` reads false |
| a tool-origin or wake-origin call | as production: `person-required`, no ticket |

There is no `prefer` that answers a presence ticket: each check in a drive
is a tap, so a drive's transcript shows every place a person would be
asked.

**The agent's store never holds a real item.** Under the agent the store
is memory, or the drive's scratch tree (LLP 1018 D6), and a presence name
is kept there with its policy recorded. A ticket's `allow` releases only a
value the drive itself wrote. Where an agent drive reads a real store
(`EXACT_STORE=real` on Apple), presence names are not in it: `has` reads
false and `set` throws `NotSupportedError`, so the substitute never
answers for a real keychain item or Keystore key. With the implementation
bound under the agent (`--bind local-auth`, as LLP 1133.002 stage 2 binds
geolocation), the real platform shows its real sheet and a person answers
it; no ticket stands in.

**Disclosure.** `state.extensions` lists `local-auth`, its binding per
target and each call's origin and outcome; `state`'s store list shows a
presence name as `kept, user-presence` or `absent`, never a value; the
journal names the call, never the value.

**Declared, not built in.** As LLP 1133.002 §6 built it: each name's
`substitute` and the interface's `permission` in `exact.json`; the
`presence` ticket's choices; `unlock`'s substitute, which the runner owns
because the store is its, is declared in the same file under the
authenticator entry.

**Production:** none of it.

## 8. What stays out

- **The web, Windows, Linux and visionOS cells** (D15).
- **A presence-gated signing key** (Secure Enclave `privateKeyUsage`, a
  Keystore signing key with authentication): LLP 1069.005 D1b's security
  review, with passkeys and attestation.
- **Several presence secrets behind one sheet** (D5).
- **An app-password factor** (`applicationPassword`).
- **Hiding the app's content in the app switcher** while locked: a screen
  module's (LLP 1133.000 §3.3), reachable through the app's hatch now.
- **Presence for background work**: a wake never shows a sheet (D12).
- **A delegation rule that could satisfy presence**: there is none to
  write (D12).

## 9. The consumer: Excord

Excord (`apps/excord`, its `llp/0001`) is a Discord client signed in to
Charlie's main account. It keeps the account's token with `secret.keep
discord-token` (and `fixture-token` against its fixture), and the token is
the whole account: a copy of it is a session anyone can use. Messaging apps
offer a lock for this reason: WhatsApp's "Require Face ID", Signal's
screen lock, Telegram's passcode lock. Excord's lock is stronger than
theirs, which gate the screen, because it gates the token itself.

**It gains:**

- grants, per backend: `secret.keep discord-token.locked user-presence`
  beside `secret.keep discord-token` (and the fixture's pair), and
  `device.local-auth purpose.lock`; a strings table with `purpose.lock`
  ("Excord uses Face ID to unlock your Discord session.") and
  `reason.unlock` ("Unlock Excord");
- a dependency, `"@exact/local-auth": "file:../../packages/local-auth"`,
  in its `package.json`;
- **a Lock Excord switch** in the account menu, shown while
  `localAuthStatus().available` and `presenceSecrets`, labelled by
  `biometry` ("Require Face ID", "Require Touch ID") and on Android by
  `android.label`. Turning it on sends `authenticate(reason=)` first, as
  WhatsApp asks before enabling, then data code keeps the in-memory token
  under the locked name and forgets the plain one. Turning it off unlocks
  the locked name (the sheet), keeps it under the plain name and forgets
  the locked one;
- **at launch,** `loadSession` reads `store.has` of the locked name. While
  it is kept, the session answers `{ready: false, locked: true}` at once,
  so the first frame is the lock screen and the gateway, which waits on
  `session.ready`, opens no socket; the lock screen's resource then calls
  `store.unlock`, which shows the sheet right after first pixel. Success
  sets the token and answers `ready`; a cancel leaves the lock screen with
  an Unlock button that asks again; `null` (the platform dropped the item)
  shows the sign-in screen with "Sign in again";
- **on return** from the background after a minute or more hidden
  (`exactPage().visibilityState`), the lock screen covers the transcript
  and its Unlock button sends `authenticate`: the token is already in
  memory and the gateway stays open, as a hand-built client's would;
- on the web, no switch: `available` is false there, and the token stays
  under the plain name.

Excord's own LLP records the feature as an amendment to its §2, with this
document as its reason.

## 12. Questions for Charlie

1. **The policy in the grant line** (D4), not an argument to each write.
   *Recommended: yes (80%).* A per-write argument can be missed on one path
   and keeps a token ungated with no sign; the grant is enforced on every
   write and known before boot.
2. **The module authenticates; the store keeps** (D13), with the
   authenticator entry as a public part of LLP 1133.001's package format.
   *Recommended: yes (75%).* The alternatives put a secret on the
   journaled module route or give the system sheet two owners.
3. **The web is `later`, over passkeys** (D15), and refuses a presence
   secret meanwhile rather than keep it in `localStorage`. *Recommended:
   yes (85%).*
4. **macOS presence secrets need a provisioned build** (D7), and a Mac
   provisioning profile becomes a build input. *Recommended: yes (85%);
   the alternative, the file-based keychain, has no presence check to
   offer.*

   later writes. *Recommended: yes (90%).*
6. **Excord's lock as the consumer** (§9), amending Excord's `llp/0001`.
   *Recommended: yes (75%); the alternative, Fieldnotes' lock as Apple's
   Journal app has, exercises only the check, since Fieldnotes keeps no
   secret worth gating.*
