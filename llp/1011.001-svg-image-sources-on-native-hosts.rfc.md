## Summary

An SVG file named as an image source (`image "assets/wordmark.svg"`, `app:/data/logo.svg`, a remote URL) draws on the web and on nothing else: the native raster loaders decode with ImageIO and with PNG and JPEG decoders, none of which reads SVG, so the node measures 0 on its unknown axis and paints nothing. Since 2026-10-19 the compiler warns (`lower-image-svg`) and names the two routes that work everywhere, an inline `svg` element or an icon token. This RFC makes the file itself work, the way a browser's `<img src="x.svg">` works: **a picture, rasterized at the size it is drawn, with no scripts, no external references and no interaction.** The pieces are three, and two already exist: one parser reads the file into the kernel's own SVG nodes in a scratch kernel; the kernel's resolver turns them into the `Scene` every host already consumes; each host rasterizes the scene at the drawn size the way it already rasterizes an island, and its raster loader takes those pixels as it takes a decoded PNG. The web host changes nothing. Two deviations from the browser are declared, not hidden: animation inside the file is ignored (§3), and a file with a `viewBox` and no size takes the `viewBox`'s size as its natural size (D1).

## 1. Motivation

A wordmark, a logo, a product illustration and a designer's export are SVG files. On the web they are images; a lane porting a shop app found them blank on iOS with no diagnostic, and inlined the paths by hand. LLP 1011 §6 lists "SVG sources on Apple" as not built, and Linux is in the same state. The alternatives the lane has today both change what the author writes: inlining turns a file into Contract source, so a designer's re-export is a code edit, and an icon token takes one monochrome shape only.

The web is the oracle (`rules/RULES.md`). A browser treats an SVG `<img>` as a picture: its natural size comes from `width` and `height`, a `viewBox` alone gives it a ratio, it is rasterized at the concrete object size `object-fit` chooses times the device scale and again after a resize, scripts do not run, external resources do not load, and links and `:hover` do nothing. That is a near-complete specification of the behaviour, and it fits the raster pipeline the native hosts have: decode at the laid-out size, re-ask after a resize, budget pixels, cache.

## 2. Decisions

### D1. An SVG image source is a picture, sized as the browser sizes it

An SVG file named by an image source is decoded to pixels at the drawn size and handled from there as any raster: `object-fit`, clipping, `load` and `error`, the budget, the queue and the cache all apply unchanged. It is not a vector layer hosted by the image node. A vector layer would be crisper under magnification, which an image never does, and it would give the image node a second kind of content with its own sizing, clipping and memory rules.

**Natural size.** A file with absolute `width` and `height` has them as its natural size, in CSS pixels taken as layout units (LLP 1011 §1). A file with one absolute dimension and a `viewBox` has the other from the `viewBox`'s ratio. A file with a `viewBox` and no absolute size has a ratio and no size in the browser, where an `<img>` of it takes its containing block's width (CSS 2.1 §10.3.2); the kernel's seam carries a width and height pair and no ratio, so **such a file reports the `viewBox`'s width and height, in user units, as its natural size: a declared deviation** (LLP 1001's manner), to be lifted when the seam carries a ratio. A file with neither has the browser's 300×150. Percentage dimensions count as absent.

**Decode size.** The raster is planned at the concrete object size `object-fit` chooses for the box, in points, times the display scale (`requestedPixel`'s scale), bounded by the pipeline's caps (4,096 px on an axis, the budget) and **not by the natural size**: a 24-unit logo in a 96-point box at 3× is drawn at 288 pixels, where a bitmap would be enlarged. Under `fill`, CSS's initial value, the concrete object size is the box itself, so the raster is the box's pixel size on both axes and the file's `preserveAspectRatio` letterboxes inside it, as the browser does; under `contain`, `cover`, `scale-down` and `none` the concrete object size keeps the natural ratio and the raster is placed as any raster is. The re-ask after a layout change triggers on either axis moving past the 25% band, not the longest side alone, since under `fill` a ratio change is a different picture.

### D2. One parser, into the kernel's own SVG nodes, in the core

A new crate, `svg-file` (beside the kernel, which it depends on), reads an SVG document into the SVG node types the kernel already has (`NodeType::Svg`, `SvgPath`, `SvgCircle`, `SvgGroup`, `SvgLinearGradient`, … , `host/apple/src/host.rs` `kind_for`'s list) in a **scratch kernel of its own**: the XML attribute names are the Contract attribute names, so the parser's job is XML tokenizing, entity decoding, `style=""` splitting and the same value lowering the compiler applies to an inline `svg` (`contract/lower/src/svg.rs`), applied as `StyleValue::Text` and props. The `d` grammar is the kernel's (`kernel/src/svg/path.rs`). The icon reader (`contract/lower/src/icon_svg.rs`) has a permissive tokenizer and the inherited-paint walk for its one-shape case; the crate's tokenizer is strict where the icon reader is not (closing tags must match), and the icon reader becomes a client of the crate, keeping its template restriction. The crate is a plain dependency of the Apple and Linux hosts and of the compiler, never a loaded module: the resolver takes a `&Kernel` (`kernel/src/svg/scene.rs:258`) and the scene serializer lives in the core, so a module would compile the kernel whole (LLP 1036.000 §12) or fail at first use in a fixed-plan production build that left it out. The parser is on the order of a thousand lines; that is the size an app pays (LLP 1047), whether or not it names an SVG image, until the host's optional tiers hold the kernel-dependent code too.

**The subset is a file's, not Contract's.** Everything the inline `svg` draws (LLP 1055.000 D2 table: shapes, paths, groups, transforms, opacity, solid paint, gradients, `clipPath`, `mask`, `pattern`, filters, `defs`, `symbol`, `use`, `text` with the host's fonts, nested viewports) draws from a file. Beyond that, what a designer's export carries and a browser draws: a `style` element with type, class and id selectors and no combinators, applied as presentation attributes are (LLP 1055.000 §7 refuses `style` in authored Contract because Contract's own style sets are the stylesheet; a file has no other stylesheet); `switch`, taking the first child whose conditions pass; `em` and `rem` resolved against 16 px; attributes and elements in foreign namespaces (Illustrator's, Inkscape's) ignored. As a browser does for an image: `script` is dropped; `a` draws its content and links nowhere; an external reference (`href` into another file, an `image` element naming a URL, `@import`) is dropped and the file still draws. What the inline `svg` refuses for good (LLP 1055.000 §7's first list) the file drops too, each with a warning naming the element.

**Bounds, since a remote file is untrusted.** A DOCTYPE's internal entity declarations are refused (the five predefined entities and numeric references are read); the parser takes at most 50,000 elements nested at most 256 deep (the kernel's tree, 128). A `use`, a marker at each vertex, and a mask or pattern resolved for each element that names it multiply what a few kilobytes draw, so the scene resolver (`kernel/src/svg/scene/budget.rs`) charges what it makes as it makes it, before a host draws it, and stops at the first of four limits: 1,000,000 units of expansion (an item, a text chunk or run, a filter primitive 8; a path segment, a gradient stop, a dash-array entry, or a value a primitive carries 1; a character of text 8: 125,000 elements, fewer with long paths); 100,000 dashes over all stroked paths; 2.5 GiB of offscreen surfaces (filter, mask and pattern islands, and Apple's bitmaps of a pattern- or gradient-painted area, at a device scale of 3 and at most 4,096² pixels each, with a filter's `f32` working images); and 10⁹ steps of filter work (a primitive's pass over an island pixel, one per octave, kernel cell or window pixel for the primitives whose work grows with a parameter). A scene past one draws nothing and names it (`Scene::over`); an image past one is the named `error` (on Apple its message; Linux, which sends no image events, refuses the decode and logs it). An inline `svg` resolves through the same resolver, so it has the same limits. The surface limit is Linux's cost: it admits `apps/svg-gallery`'s `fx-huge-region`, a drop shadow and a mask far larger than the drawing (2.35 GB at 3×), because Linux sizes a filter's island to its region up to the side cap; Apple caps an island at 16,777,216 pixels and a filter's work at 128 MiB (`SvgIsland.cap`, `budget`) by drawing it smaller. Not charged, since only the host knows their size: the layers a host composites for opacity, blending and clipping, one the size of its target at each level of nesting, and the magnification of what draws inside an island the host rounds up (a pattern tile smaller than a pixel). Linux draws no path, stroke or clip reaching past ±2³⁰ device pixels: tiny-skia 0.12 panics past about ±2³¹, which a file's coordinates, `viewBox` or `stroke-width` can reach (`host/linux/src/raster/reach.rs`). A parse failure is the `error` "not an SVG this host reads", with the line and the element.

### D3. The resolved scene, rasterized as an island is

The parsed nodes go through `kernel::svg::scene::resolve` into a `Scene` (LLP 1055.000 D1), with the file's root as the viewport at the concrete object size in CSS pixels (D1), so percentages, the `viewBox` and `preserveAspectRatio` resolve as the browser resolves them, and the device scale is one transform over the whole scene, so a file with absolute coordinates and no `viewBox` is scaled as a browser scales it on a 3× screen. Each host rasterizes the scene the way it rasterizes an island today (LLP 1055.000 §0, stage 8 as built: `host/svg-raster` does the pixel work after rasterization, and each host rasterizes an island's source with its own rasterizer): Apple builds the scene's layers as the `svg` op's JSON builds them and renders them with Core Animation's `render(in:)` into a bitmap (`SvgIsland.render`), so text, gradients and clips come along and antialias as the rest of Apple's SVG does; Linux paints the scene through `paint/svg.rs` into a tiny-skia pixmap. The result is each host's own SVG drawing at the box's pixel size, which is what a browser's `<img>` is on that platform too. A single Rust rasterizer shared by both hosts is the cleaner shape and the one D2 first named; it is not chosen here because the hosts did not build islands that way, and an SVG image should not be the thing that forks how a host draws SVG.

**Which thread.** Apple's `SvgFilterLive` already renders a sub-scene off the main thread when it has no text and on the main thread when it has, where the session's fonts are; an SVG image follows the same rule, so a wordmark of paths costs the main thread nothing and a file with `text` costs it one render. Linux's painter and text engine are the paint thread's (`Rc`, `RefCell`), so Linux paints a scene with text on the paint thread and one without on the decode worker. An island's intermediate allocations (a filter's 128 MiB work cap, mask and pattern surfaces) are the island cap's, not the raster reservation's; the finished bitmap enters the raster budget. The costs are measured in implementation on a designer's export with thousands of paths, not estimated here.

### D4. The loader seam

Apple: `RasterInput.open` is unchanged (the file's bytes reach the spool as today). `RasterMetadata.read` recognizes an SVG from its first bytes (`<?xml`, `<svg`, a BOM, leading whitespace and comments allowed, as browsers sniff; the file name decides nothing) and answers the natural size of D1; `deep` and `hdr` are false. `RasterDecodePlan` gains the SVG case: the plan's pixel size is D1's decode size, allowed above the natural size and, under `fill`, both axes of the box; the decode key carries both axes. The decode step, where ImageIO would draw a thumbnail, parses and resolves in Rust (`exact_svg_image_scene(bytes, len, width, height, scale)` in the host's own Rust crate, the same JSON the `svg` op carries) and renders it as D3 says, then enters the bitmap into the pipeline as any decoded bitmap: pinned, budgeted, evicted, cached. The parsed document is kept per source while any view shows it, so a resize re-asks only the rasterization. Linux: `host/linux/src/image.rs` gains the same recognition beside PNG and JPEG, the same plan rules, and paints as D3 says, keeping its budget and cache (LLP 1010 §6.3).

### D5. The build check

A bundled `.svg` under `assets/` that a literal image source names is parsed at build by the compiler, which already reads asset SVGs for icon tokens and owns `lower-image-svg`: a feature the parser drops is a warning naming the element and the fix; a file the parser refuses is an error with the reason, on a build that ships a native target (a web-only build draws the browser's picture and is not refused). A remote or `app:/` SVG cannot be checked at build and is handled at run time as D2 says. The `lower-image-svg` warning is retired when D4 lands on both native hosts.

### D6. The web

Unchanged: the browser draws the file. Chrome is the oracle for the conformance row (§4); the deviations of §3 are recorded against it, not excused by another browser.

## 3. What this refuses, and the two declared deviations

Refused:
- A vector image node, or any new vocabulary: an SVG image is `image`, and the author writes what the web takes.
- Interaction, links, scripts and external loads inside an image, as a browser refuses them.
- A rasterizer of its own: an SVG image is drawn by the host's SVG drawing, as an island is, so a picture and the same content inlined never differ on one host.
- Growing the icon token's one-shape subset: a token stays a template glyph; a picture is an image.
- Using Xcode's asset-catalog SVG support: it covers bundled assets on iOS only, through a renderer that is not the one inline SVG uses.

Deviations, declared:
- **Animation inside the file is ignored.** Browsers render an `<img>` in SVG Integration's *secure animated* mode and animate SMIL and CSS animation in it; here the animation elements are dropped and every value is its static one. A picture that must move is an inline `svg`. The reason is cost and determinism: an animated image would re-rasterize every frame through the raster pipeline. Charlie to accept (§6).
- **A `viewBox` without a size reports the `viewBox` as the natural size** (D1), where the browser gives such an image its container's width. Lifted when the intrinsic seam carries a ratio.

## 4. Verification

- `svg-file`'s own tests: the parser against the SVG files the repo already holds (`apps/svg-gallery`'s fixtures, the icon fixtures), round-tripped through the resolver to the same `Scene` an inline `svg` of the same content produces; a `style` element with classes; `switch`; a foreign namespace; a `script`; an external `image`; a DOCTYPE with an entity declaration (refused); a `use` fan-out past the cap (refused); malformed XML (the named `error` with its line).
- **Every `svg-gallery` fixture drawn as an `image` beside the same fixture inline, on each native host, compared pixel-wise**: §3's invariant as a check, run by the native parity smoke LLP 1055.000 §5 already defines (`scripts/smoke.mjs svg`), with Chrome's picture as the oracle for the image rows at three sizes and three `object-fit` values.
- `RasterImageTests` (Apple) and `host/linux/src/image/decode_tests.rs`: the natural size from `width`/`height`, from one dimension and a `viewBox`, from a `viewBox` alone (the declared deviation), and the default; sniffing by bytes with a `.svg` name on a PNG; a plan above the natural size at 3×; a `fill` plan at the box's two axes; a file with a `script` draws without it.
- `RasterLoaderTests`: an SVG decodes at the box's pixel size, again after a resize past the band on either axis, under the budget as any raster, and a source replaced while an Apple render is pending lands the right picture.
- The agent: `bun scripts/agent.mjs macos "screenshot out.png"` on `apps/svg-gallery` with an image row added, and `state` showing the loader's `variant` and pixels.

## 5. Costs

The parser is the only new code of size: on the order of a thousand lines of Rust with the strict tokenizer, attribute lowering, the `style` element's selectors and the scratch kernel, part of it moved from `icon_svg.rs`. The resolver, the scene serializer and each host's island rasterization exist. Each loader seam is about two hundred lines, with the plan's SVG case and, on Apple, the hop to the main thread for a scene with text. Every native app carries the parser (D2). A decode is a parse plus the host's rasterization at the box's size; the numbers are measured in implementation (D3).

## 6. Open questions

1. **The animation deviation** (§3): accept ignoring animation inside an SVG image, with an inline `svg` as the route for a moving picture?
2. **The size deviation** (D1): accept the `viewBox` as the natural size until the intrinsic seam carries a ratio, or carry the ratio now (a kernel change touching every host's `exact_intrinsic`)?
3. **A per-app opt-out of the parser's size** for an app that names no SVG image and counts bytes, once the host's optional tiers can hold kernel-dependent code.

## 7. Stages

As built on 2026-10-20: stages 1 and 3. The parser crate is `host/svg-file` (`exact-svg-file`, in the gate's `default-members`); the Apple seam is `host/apple/src/svg_image.rs` (`exact_svg_image_header`, `exact_svg_image_scene`, `exact_svg_image_free`) and `RasterImage.decodeSVG`, with the plan's `scale` and the worker's rebuild of an SVG plan from the work's own size, which under `fill` is the box's. The icon reader still has its own tokenizer (stage 1's move is not done).

Stage 2, built the same day: the Linux seam is `host/linux/src/image/svg.rs` and `paint/picture.rs`. The raster inspector sniffs an SVG by its bytes before the PNG check (a prefix read a raster never pays), the plan is the box's own pixels (both axes under `fill`, the natural ratio at the fitted size otherwise, up to the island's 4,096 a side) with no bucket, no part and no larger picture standing in, and the re-ask band is judged on either axis. The decode worker parses and resolves the scene at the CSS size the plan's pixels are at the device scale (the scale noted per request, since the key carries none) and paints a picture without text itself, with a text engine of its own; a picture with text waits with its permit for the presenter's thread, which paints it with the session's fonts at its next poll (`Images::paint_with`). `host/linux/src/image/svg_tests.rs` covers the header, the plan, the band, and both paths through the loader. The compiler's `lower-image-svg` warning retired here rather than at stage 4: it named Linux as blank, which was its last true claim; stage 4's build check still owes. The parity smoke's image rows are not built on either host; a scratch app's wordmark was driven on the Linux host instead (§4's agent check).
