# LLP 1011.001: SVG image sources on the native hosts

**Type:** RFC
**Status:** Draft r1
**Systems:** Kernel (`kernel/src/svg`: the SVG node types, `scene.rs`'s resolved `Scene`); a new parser crate for SVG files; the raster loaders (Apple `host/apple/Sources/ExactKit/RasterLoader.swift`, `RasterInput.swift`, `RasterImage.swift`; Linux `host/linux/src/image.rs` and `image/`); each host's island rasterization (Apple `SvgIsland.swift` `render`, Linux `paint/svg.rs`; the island module `host/svg-raster`, LLP 1055.000 D2); the bake's asset gate (`bake/src/receipt.rs`); the compiler's `lower-image-svg` warning (`contract/lower/src/symbols.rs`)
**Author:** Claude (Fable 5.1) for Charlie Cheever
**Date:** 2026-10-19
**Related:** LLP 1011 §4 and §6 (an SVG image source on Apple is the `error` "not an image format this host decodes", declared not built); LLP 1055.000 D1 (one resolved scene, computed in Rust), D2 (islands: a subtree rendered to pixels by the rasterizer each host has), §7 (what SVG refuses, where "an SVG file as an `image` source" waits for a consumer; `style` elements are refused for good); LLP 1121 D10 and `contract/lower/src/icon_svg.rs` (an icon token's SVG read at build, one monochrome shape); LLP 1010 §6.3 (the raster budget and queue); LLP 1047 (optional capability is a loaded module, never a feature on a core crate); `issues/20261019-svg-image-asset-blank-on-apple.md`; `rules/RULES.md` "the web is the standard"

## Summary

An SVG file named as an image source (`image "assets/wordmark.svg"`, `app:/data/logo.svg`, a remote URL) draws on the web and on nothing else: the native raster loaders decode with ImageIO and with PNG and JPEG decoders, none of which reads SVG, so the node measures 0 on its unknown axis and paints nothing. Since 2026-10-19 the compiler warns (`lower-image-svg`) and names the two routes that work everywhere, an inline `svg` element or an icon token. This RFC makes the file itself work, the way a browser's `<img src="x.svg">` works: **a picture, rasterized at the size it is drawn, with no scripts, no external references and no interaction.** The pieces are three, and two already exist: one parser reads the file into the kernel's own SVG nodes; the kernel's resolver turns them into the `Scene` every host already consumes; each host rasterizes the scene at the requested pixel size the way it already rasterizes an island, and its raster loader takes those pixels as it takes a decoded PNG. The web host changes nothing.

## 1. Motivation

A wordmark, a logo, a product illustration and a designer's export are SVG files. On the web they are images; a lane porting a shop app found them blank on iOS with no diagnostic, and inlined the paths by hand. LLP 1011 §6 lists "SVG sources on Apple" as not built, and Linux is in the same state. The alternatives the lane has today both change what the author writes: inlining turns a file into Contract source, so a designer's re-export is a code edit, and an icon token takes one monochrome shape only.

The web is the oracle (`rules/RULES.md`). A browser treats an SVG `<img>` as a raster at its paint size: its intrinsic size comes from `width`, `height` and the `viewBox`; it is rasterized at the layout size times the device scale, and again after a resize; scripts do not run, external resources do not load, `:hover` and links do nothing (HTML "image request" in secure static mode). That is a complete specification of the behaviour, and it fits the raster pipeline the native hosts have: decode at the laid-out size, re-ask after a resize, budget pixels, cache.

## 2. Decisions

### D1. An SVG image source is a picture

An SVG file named by an image source is decoded to pixels at the requested size and handled from there as any raster: `object-fit`, clipping, `load` and `error`, the budget, the queue and the cache all apply unchanged. It is not a vector layer hosted by the image node. A vector layer would be crisper under magnification, which an image never does, and it would give the image node a second kind of content with its own sizing, clipping and memory rules. Pixel density is handled where it is for every raster: the decode size is the box times the display scale (`requestedPixel`), so a 2× or 3× screen gets a 2× or 3× raster.

### D2. One parser, into the kernel's own SVG nodes

A new crate, `svg-file` (under `host/`, beside `svg-raster`), reads an SVG document into the SVG node types the kernel already has (`NodeType::Svg`, `SvgPath`, `SvgCircle`, `SvgGroup`, `SvgLinearGradient`, … , `host/apple/src/host.rs` `kind_for`'s list) with the props the compiler emits for an inline `svg`: the XML attribute names are the Contract attribute names, so the parser's job is XML tokenizing, entity decoding, `style=""` splitting and the same value lowering the compiler applies (`contract/lower/src/svg.rs`). The `d` grammar is the kernel's (`kernel/src/svg/path.rs`, which Linux and the Apple icon paths already use). The icon reader (`contract/lower/src/icon_svg.rs`) has the tokenizer and the inherited-paint walk for its one-shape case; this crate generalizes it and the icon reader becomes a client of it.

Scope is the inline `svg`'s scope (LLP 1055.000 D2 table): shapes, paths, groups, transforms, opacity, solid paint, linear and radial gradients, `clipPath`, `mask`, `pattern`, filters, `defs`, `symbol`, `use`, `text` with the host's fonts, nested `svg` viewports. What the inline `svg` refuses (LLP 1055.000 §7) the file refuses too. In addition, as a browser does for an image: `script` is dropped; `a` draws its content and links nowhere; an external reference (`href` to another file, an `image` element naming a URL, `@import`) is dropped and the file still draws; a `style` element is dropped, as the inline `svg` refuses it for good (LLP 1055.000 §7; presentation attributes and `style=""` on elements are read); SMIL and CSS animation are sampled at time 0 (LLP 1055.000 D15, D16: an island is pixels). A parse failure is the `error` "not an SVG this host reads", with the line and the element.

### D3. The resolved scene, rasterized as an island is

The parsed nodes go through `kernel::svg::scene::resolve` into a `Scene` (LLP 1055.000 D1), with the file's root as the viewport sized to the requested pixel size, so percentages and the `viewBox` resolve as the browser resolves them for an image of that size (`preserveAspectRatio` honoured; the default `xMidYMid meet` letterboxes within the box, and `object-fit` then places the raster, which keeps a transparent border exactly where the browser keeps one). Each host rasterizes the scene the way it rasterizes an island today (LLP 1055.000 D2 as built: `host/svg-raster` does the pixel work after rasterization, and "each host rasterizes an island's source with the rasterizer it already has"): Apple builds the scene's layers as the `svg` op's JSON builds them and renders them with Core Animation's `render(in:)` into a bitmap (`SvgIsland.render`), so text, gradients and clips come along and antialias as the rest of Apple's SVG does; Linux paints the scene through `paint/svg.rs` into a tiny-skia pixmap. The result is each host's own SVG drawing at the box's pixel size, which is what a browser's `<img>` is on that platform too. A single Rust rasterizer shared by both hosts is the cleaner shape and the one D2 first named; it is not chosen here because the hosts did not build islands that way, and an SVG image should not be the thing that forks how a host draws SVG.

### D4. The loader seam

Apple: `RasterInput.open` is unchanged (the file's bytes reach the spool as today). `RasterMetadata.read` recognizes an SVG from its first bytes (`<?xml`, `<svg`, a BOM, leading whitespace and comments allowed, as browsers sniff) and answers the natural size from `width` and `height`, else the `viewBox`, else the browser's 300×150 default; `deep` and `hdr` are false. `RasterDecodePlan` plans the usual 8-bit sRGB variant at `maxPixel`. The decode step, where ImageIO would draw a thumbnail, asks the module for the scene (`exact_svg_file_scene(bytes, len, width, height)`, the same JSON the `svg` op carries, parsed and resolved in Rust) and renders it on the main thread as an island is rendered, at most one frame late, then hands the bitmap back to the decode worker, which enters it into the pipeline as any decoded bitmap: pinned, budgeted, evicted, cached. The parser lives in `libexact_svg.dylib`, the island module ExactKit already opens on demand (`SvgRasterModule`), as one more symbol; a plan whose strings name an `.svg` image source has it prewarmed at boot as a plan with islands does, and a computed source opens it at first use (measured and logged, as the island load is). Linux: `host/linux/src/image.rs` gains the same recognition beside PNG and JPEG, calls the crate directly, paints the scene into a pixmap on its decode thread, and keeps its budget and cache (LLP 1010 §6.3).

### D5. The build gate

A bundled `.svg` under `assets/` that an image source names is parsed at bake (`bake/src/receipt.rs`, beside the name gate), and a feature the parser drops is a warning naming the element and the fix; a file the parser refuses fails the build with the reason. A remote or `app:/` SVG cannot be checked at build and is handled at run time as D2 says. The compiler's `lower-image-svg` warning is retired when D4 lands on both native hosts.

### D6. The web

Unchanged: the browser draws the file. The web's picture is the oracle for the conformance row (§4).

## 3. What this refuses

- A vector image node, or any new vocabulary: an SVG image is `image`, and the author writes what the web takes.
- Interaction, links, scripts and external loads inside an image, as a browser refuses them.
- Live animation inside an image: sampled at time 0, as the browser's `<img>` does not animate SMIL either in secure static mode (Chrome does; Safari does not; the deterministic choice is the still frame, and an animated picture is an inline `svg`).
- A rasterizer of its own: an SVG image is drawn by the host's SVG drawing, as an island is, so a picture and the same content inlined never differ on one host.
- Growing the icon token's one-shape subset: a token stays a template glyph; a picture is an image.

## 4. Verification

- `svg-file`'s own tests: the parser against the SVG files the repo already holds (`apps/svg-gallery`, the icon fixtures), round-tripped through the resolver to the same `Scene` an inline `svg` of the same content produces.
- A conformance row: a page with an `.svg` image at three sizes and three `object-fit` values on the web, macOS, iOS and Linux, compared pixel-wise to Chrome's picture within the tolerance the island rows use (`host/web-js/conform.mjs`).
- `RasterImageTests` (Apple) and `host/linux/src/image/decode_tests.rs`: an SVG gives its natural size from `width`/`height`, from the `viewBox` alone, and the default when it has neither; a file with a `script` draws without it; a file naming an external image draws without it; malformed XML is the named `error`.
- `RasterLoaderTests`: an SVG decodes at the box's pixel size, again after a resize past the 25% band, and under the budget as any raster.
- The agent: `bun scripts/agent.mjs macos "screenshot out.png"` on `apps/svg-gallery` with an image row added, and `state` showing the loader's `variant` and pixels.

## 5. Costs

The parser is the only new code of size: on the order of eight hundred lines of Rust with the tokenizer, attribute lowering and the `style=""` reader, half of it moved from `icon_svg.rs`. The resolver and each host's island rasterization exist. Each loader seam is about a hundred and fifty lines, the Apple one with its hop to the main thread. The module grows by the parser's size for apps that name an SVG image; an app that does not pays nothing (LLP 1047). A decode is a parse plus a software rasterization at the box's size, off the main thread; a wordmark at 300×80 points at 3× is under a millisecond of rasterization, and a full-screen illustration is comparable to decoding a JPEG of that size.

## 6. Open questions

1. **The main thread on Apple.** Core Animation's `render(in:)` is where islands are rasterized, on the main thread; an SVG image's decode then costs the main thread its rasterization (a wordmark: well under a millisecond; a full-screen illustration: a few), where a JPEG's decode costs it nothing. Accept it for the first stage, or move Apple's island rasterization to a background `CGContext` drawing the scene with Core Graphics directly (which LLP 1055.000 D2 lists for gradients already)? The second is the better end state and is a change to islands, not only to images.
2. **Sniffing by content or by name.** A browser decides by the HTTP `Content-Type` or the file's bytes, never the extension. D4 sniffs bytes. Should a `.svg` name with non-SVG bytes be the `error` the bytes give (as proposed), or the file-name's?
3. **The still frame.** Time 0 for sampled animation matches Safari and WebKit's secure static mode; Chrome animates. Charlie to rule, or the conformance row takes Safari as the oracle for this one cell.
4. **Linux first or Apple first.** Apple has the consumer; Linux has the simpler seam. Both land before `lower-image-svg` retires.

## 7. Stages

1. `svg-file`: the parser into kernel nodes, with the icon reader moved onto it; tests against the repo's SVG fixtures.
2. The Linux loader seam: the parsed file through the resolver and the painter into a pixmap; the conformance row on Linux.
3. The scene entry in the island module (`exact_svg_file_scene`), the Apple loader seam and its main-thread render, the module prewarm, `RasterImageTests` and `RasterLoaderTests`; the conformance row on macOS and iOS.
4. The bake gate and the warning's retirement; LLP 1011 §4 and §6 amended to say "built".
