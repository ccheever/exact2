## Summary

James patched Exact to get UIKit's navigation bar and is patching it again for a
tab controller (LLP 1075). Codex and Claude each wrote a recommendation, and
after one round of revisions they agree on most of the design. This is the one
plan to rule on and build from. The two recommendations stay as the record of
the argument.

The plan:

1. **Hooks.** The app's one Swift module (LLP 1067.000) receives Exact's own
   UIKit objects at defined moments: a navigation controller when it is built, a
   route when it is built, changed and ended, and the tab container. The app's
   own words reach a hook as `data-*` attributes. A hook acts back by clicking
   an authored control.
2. **Ownership.** Exact lists what it owns on each object, checks that in
   development builds, and forwards the delegates it keeps.
3. **A public seam.** Route content is a controller that an app can place in
   containers it owns, with one session and one router. Exact's own containers
   are built on the same seam.
4. **Exact builds the two hard containers.** A navigation bar, one per stack,
   with fixed titles first and collapsing large titles later. A
   `UITabBarController` whose tabs stay alive, with the same tabs kept hidden
   and inert on the web.
5. **One small surface, kept.** A fixture exercises all of it. A break is
   deliberate and says what to change. Nothing is deprecated: the old form is
   deleted.
6. **TypeScript by experiment,** once the hooks exist to bind.

It needs six rulings from Charlie (§2), then an implementer and a date.

Against 1075.002 r2 it makes five corrections, each a point where 1075.001 was
right (§1.2). Two of them were errors of fact. It adds three things neither
recommendation covered: what the agent can drive (§3.4), a first frame that
runs no app code (Q3), and how fast a hook edit shows (§6).

Two costs were measured for this plan, on a Mac (§6). Opening a module the
system has already seen takes about 2 ms, and recompiling one after a one-line
edit takes 1.3–1.7 s a slice. Nothing has been measured on a device, and
nothing here is built.

## 1. Where the two recommendations stand

### 1.1 Agreed

- Swift hooks hand app code Exact's real UIKit objects, under Apple's names,
  behind a small supported boundary, in the app's existing module.
- Hooks alone do not finish the job. Correct navigation geometry and retained
  tabs are Exact's to build.
- An app can also own a screen or a container, with Exact content inside it.
  Waiting for a new Exact projection is never the only route.
- `data-*` carries the app's words from Contract to a hook as one aggregate,
  and they are real attributes on the web.
- A hook acts through scoped `click()`, `focus()` and `blur()`, queued until
  the batch has been applied. No hook writes Contract state.
- Exact keeps the delegate slots it needs, and the app gets a deliberate way
  to take part. In r2 that is forwarding.
- One bar per stack comes first. Hiding the bar for one route comes later, as
  an explicit request.
- The title's source stays LLP 1035.001 D9's authored header.
- James's two cases are reproduced before a cause is assigned.
- TypeScript comes after the Swift seams, by experiment. No UIKit mirror in
  Rust, no UIKit calls from Contract, and patching is not the interface.
- This surface gets a narrow exception to "No public API stability", held by a
  fixture.

### 1.2 Five corrections to 1075.002 r2

Each is 1075.001's point.

| r2 said | This plan | Why |
|---|---|---|
| D9: a changed hook ships beside the old one for a release | No overlap. The commit that adds the new form deletes the old one | An error of fact in r2, which named only `DEFERRED.md` as the rule it touched. `RULES.md` forbids the overlap itself: "Delete; don't deprecate. No compat shims, no migration paths, no legacy branches before 1.0." |
| D8: `boot.mjs` and `metrics.mjs` report the first-frame options | Native startup is measured on macOS and on a device | An error of fact in r2. `boot.mjs` parses `host/web/index.html` and counts the modules it imports. It cannot see a `dlopen` |
| D1: a node with a declared `data-*` word is always a view | An attribute never makes a view. The `element` hook names the words it wants, and only nodes carrying those become views | Flat leaves exist so that a list row's plain boxes cost a layer each, not a view (LLP 1068 §6.1) |
| D4: snapshot what Exact owns around each hook call | Before each batch, a development build compares what Exact owns with what Exact last wrote | A check around the call misses a change made later, from a callback or a timer. It is still detection, not enforcement |
| D1: every hook runs after its batch is applied and before the frame is drawn | The navigation hook runs when the controller is built, before any child is laid out. A route has build, update and end | LLP 1035.001 D9's prototype: with navigation installed late, the large title started compact at 116 instead of expanded at 168 |

### 1.3 Still different

- **`data-*`:** declared words (r2) or an open vocabulary (1075.001). Q2.
- **The first frame:** 1075.001 §7 favors opening the module early. This plan
  recommends a third option that neither document had. Q3.
- **Order:** r2 builds tabs before collapsing titles; 1075.001 §9 proves them
  in one phase. Q4.

### 1.4 Missing from both

- **The agent cannot drive what a hook creates,** unless the hook's control
  stands for an authored one (§3.4).
- **A first frame with no app code on the boot path** (Q3, option c).
- **How fast a hook edit shows.** Neither document measured it (§6).

## 2. Decisions for Charlie

Each has a recommendation. Q2, Q3 and Q4 are where the two recommendations
differ. Q1, Q5 and Q6 are agreed between them and are still his to make.

### Q1 — The promise

**Recommended:** the surface in §3.9 is named and kept. A change to it is
deliberate: it lands as one commit that also changes the fixture and says in
its message what to change. There is no overlap window and no shim.

- **What it changes in the rules.** `DEFERRED.md` says "No public API
  stability. Names change." This surface gets a narrow exception: its names
  change only on purpose. "No backwards compatibility" stands, because nothing
  old keeps working. "No migration guides" stands too: the breaking commit's
  message and its diff of the fixture's hook module are the note, and
  `git log -p` on that file lists every break with a worked before and after.
- **Why it is enough for James.** The app's Swift is compiled with the host's
  glue (`host/apple/modules/ExactNativeModule.swift`) on every build. So a
  break is a compile error at the line to change. The cost he named was
  rebasing a presenter patch across three files every release (1075 §2.2).
- **Alternative:** hooks with no promise. They still save the schema, compiler
  and presenter edits, and his upgrade concern stands.

### Q2 — `data-*`: declared words, or open

Both recommendations admit `data-*` (§3.3). They differ on whether a word must
be declared.

- **A, declared (recommended).** `app.json` lists the words
  (`"data": ["title", "trailing"]`), beside the module roster.
  - A word the list lacks fails the bake by name.
  - The build writes typed keys for the Swift module from the same list, so a
    hook reads `route.data[.title]`. A misspelling fails a build, in Contract
    or in Swift. The web's page module is plain JavaScript today and gets no
    such check.
  - Cost: one manifest key, one bake check where the compiler already reads
    the roster, and one generated Swift file per build (built, not committed).
- **B, open (1075.001 §3).** Any `data-*` word is legal, as in HTML, with
  optional validation. This plan adds that typed keys could still be generated
  for B, from the words the Contract uses. That catches a hook reading a word
  nothing writes. It does not catch a misspelled word in Contract when the
  right spelling also appears.

The reason for A: Contract refuses every unknown attribute today, and an open
`data-*` would be the one place a typo compiles. The reason for B is HTML,
where `data-*` needs no declaration. B is the fallback if a second list in the
manifest is unwanted.

### Q3 — The first frame

Today the module artifact is opened in the turn after the first drawn frame
(LLP 1024 D3, LLP 1067.000 D8). So at a cold launch, whatever a hook sets
arrives a turn after first pixel.

| Option | Runs before first pixel | A cold launch's first frame | Cost |
|---|---|---|---|
| **(a)** Open the module early, for apps that declare hooks (r2 D8; favored by 1075.001 §7 if it fits a budget) | The app's Swift | Complete | About 2 ms to open on a Mac (§6), plus whatever the app's code does. `RULES.md`: "The boot path executes and compiles nothing." A freshly built artifact's first load, 119–380 ms, also moves before first pixel in development |
| **(b)** Link the hooks into the host (r2 D8) | The app's Swift | Complete | LLP 1067.000 declined it as alternative D: it reverses LLP 1024 D3, and every hook edit relinks the app |
| **(c)** Run nothing early (new here) | Nothing of the app's | The title and whatever else Exact projects from the authored header. What only a hook sets arrives a frame or two later | Needs LLP 1035.001 D9's header-shaped route in Stage 1, in its fixed form (§3.7) |

**Recommended: (c), then measure.**

- It is today's loading order, unchanged, and it keeps the boot rule whole.
- The gap exists only at a cold launch. From then on the module is loaded, and
  every hook runs before its object's first frame.
- The gap is short. On a Mac the load starts 5.7–8.9 ms after first pixel
  (LLP 1067.000 D8; 9.8 ms on the iOS simulator) and the open takes about 2 ms
  (§6). So what a hook sets shows a frame or two after the first. A phone is
  unmeasured.
- Its cost is real where a hook sets geometry. Whether a stack has a bar, and
  whether its title is large or inline, change the content area. If only a
  hook knows either, the content moves once, a frame or two into a cold
  launch.
  - So under (c) those two come from the plan. A stack shows a bar from its
    first frame when its first route is header-shaped (§3.7), and Stage 1
    settles how the plan says large or inline.
  - A development build journals a hook that changes the content area at
    launch.

Stage 1 films a cold launch on a phone and measures the module's open there.
Rule on (a) only if the film shows something a person can see. The measured
open is small, so the objection to (a) is the rule, not the time: once app
code may run before first pixel, Exact no longer bounds what runs there. (b)
stays declined.

### Q4 — Order

**Recommended:** the seam and tabs are Stage 2, and collapsing large titles are
Stage 3. 1075.001 §9 proves retained tabs, collapsing-title coordinates and
app-owned composition in one phase.

- Collapse stopped after three rounds on 2026-09-10 (LLP 1035.001 D9). Under
  `RULES.md` a stopped fix loop is escalated or descoped, not run a fourth
  time. Stage 3 is that escalation, and it starts from a written design for
  the mapping.
- Tabs and the seam are known work, and they are James's second patch.
- Stage 1's fixed bar already gives him his first patch, without the collapse.
- 1075.001 is right that a hooks-only milestone does not finish the job. Stage
  1 here is not the end.

The TypeScript experiment starts after Stage 1 and runs beside Stages 2 and 3
if someone is free. It needs only the hook handles to bind, and it gates
nothing. 1075.001 would start it after the whole ownership proof.

### Q5 — Retained tabs, on the public seam

**Recommended:** yes to both halves.

- **Keep every visited tab's stack mounted.** LLP 1038 §7 deferred this until
  "a measured Interview complaint about a tab forgetting its place". James's
  report is that kind of complaint, and Stage 0 confirms whether his case is
  this one. The cost is memory, as UIKit's own tabs cost.
- **Build Exact's navigation and tab containers on the seam an app gets**
  (§3.6), not on private classes with the seam added later. It costs more up
  front, and it keeps the default and the escape hatch from drifting apart.
  This half is r2's. 1075.001 asks for the app-owned path and is silent on
  what Exact's own containers are built on.

### Q6 — Titles

**Recommended:** keep the ruling of 2026-09-10. There is no `navigationTitle`
prop (LLP 1038 §7: "A `navigationTitle`: 1035.001 D9 stays the path").

- The title is the authored header. The web paints it and iOS lifts it into
  the bar.
- An app that wants only a native title, as James's patch does, sets it in a
  hook from a `data-title` word. Under Q3 (c) that title shows a frame or two
  after the first, at a cold launch only.

Both recommendations agree. It is listed because a user has now written the
prop that ruling declined (1075 §6).

## 3. The design

Names and signatures below are sketches. None of this exists yet.

### 3.1 Two levels of control

- **Configure what Exact builds.** Hooks receive Exact's objects (§3.2–3.5).
- **Own a screen or a container** (§3.6), when configuring is not enough:
  - a native screen as one route;
  - the app's own container around Exact's routes;
  - a UIKit app with Exact sessions as screens, which works today.

What decides whether Exact must build something itself: it changes the content
area while the user scrolls, or it keeps UI alive off screen. That rule covers
objects Exact owns. It is not the only way to a platform feature, and the
second level is why (1075.001 §4).

### 3.2 Hooks and their moments

```swift
open class ExactModule {
    // views, later, call, destroy: LLP 1067.000, unchanged

    /// A navigation controller Exact built. Once, before any route in it is laid out.
    open func navigation(_ navigation: ExactNavigation) {}
    /// A route. When its controller is built (`route.isNew`), and again whenever
    /// its data-* or its projected header change; each time before the frame
    /// that shows it is drawn.
    open func route(_ route: ExactRoute) {}
    /// A route's controller is leaving for good.
    open func routeEnded(_ route: ExactRoute) {}
    /// Exact's tab container (Stage 2). Once, before its tabs are laid out.
    open func tabs(_ tabs: ExactTabs) {}
    /// Return a container to own the tabs yourself (§3.6); nil keeps Exact's.
    open func tabContainer(_ contents: ExactTabContents) -> UIViewController? { nil }
}
```

| Handle | Carries |
|---|---|
| `ExactNavigation` | `controller: UINavigationController`; `showsBar` (§3.7); `delegate`, forwarded (§3.5) |
| `ExactRoute` | `controller: UIViewController`; `data`; `contentScrollView`, the one the route names (§3.5); `navigation`; `element(_ id:)`, resolved inside the route as LLP 1035.001 D1 resolves a Back control; `isNew` |
| `ExactTabs` | `controller: UITabBarController`; `delegate`, forwarded |
| `ExactTabContents` | each tab's content as controllers, the selected tab, and the router intents (§3.6) |
| `ExactElement`, later | `view: UIView`; `id`; `data`; `click()`, `focus()`, `blur()` |

- **Moments.** Every hook runs on the main thread.
  - `navigation` runs when Exact builds the controller, before any child is
    laid out. The host already installs its first navigation owner before
    child frames (`NavigationHost.installInitialOwner`), which is what D9's
    prototypes found necessary.
  - `route` runs at build, and again when its `data-*` or its projected
    header (§3.5) change.
  - `routeEnded` runs when the controller is dropped. A plan reload ends every
    route and builds again (LLP 1024 D6).
- **At a cold launch under Q3 (c),** the module loads a turn after first pixel.
  Each hook then runs once for every object already live, in the order they
  were built. After that, hooks run at the moments above.
- **Identity.** A route's handle is its session and its `navigationKey`, which
  is a router entry's id where the app uses the router (LLP 1038 D6). It is
  never a position.
- **Validity.** A handle is valid while its object lives. A stored handle used
  later does nothing and writes a journal line, as a module callback with a
  retired nonce is dropped today.
- **The first surface** is `navigation`, `route` and `routeEnded`. `tabs` and
  `tabContainer` come with Stage 2.
- **`element` comes with its first case.** A stable view per hooked node
  constrains how the presenter draws, reuses and builds rows (LLP 1068, LLP
  1072). When it comes, the module names the words its `element` hook wants,
  once, as it names its view roster, and only nodes carrying one of those words
  become views. On a reused list row the hook runs again for the new data, and
  undoing what it set for the old row is the app's job, as `prepareForReuse`
  is a module view's.
- **The journal** names each hook call, so `logs` shows what app code did.
- **Not an inheritance point.** The presenter's classes stay private.

### 3.3 `data-*`

- Contract admits `data-[a-z][a-z0-9-]*` on any element.
- A node's words lower to one aggregate prop, a `dataset` row added once,
  through the `NativeProps` opcode LLP 1024 §9 built: keys sorted, values
  carried as strings. A new word never touches `schema.json` or `tags.rs`.
- On the web the words are real attributes, and the page module reads
  `el.dataset`.
- A word names the app's meaning, not a platform property: `data-title`, not
  `data-ios-large-title`. Each platform's hook decides what it means there.
- An attribute alone never turns a flat leaf into a view (§1.2).
- It is not an animation channel. A word that changes every frame is a defect,
  as LLP 1024 §9 says of module props.
- Whether a word must be declared is Q2.

### 3.4 Back into Contract, and what the agent can drive

- **`click()`** presses an authored control the way a tap does, and is the
  web's `HTMLElement.click()`. Contract's handlers decide what happens.
- `focus()` and `blur()` follow LLP 1035.001's focus rules.
- Each is queued and delivered after the batch being applied, never during it,
  which keeps it clear of the owner's re-entry rule (F5).
- No hook writes Contract state. The app's data path stays `call`, `later` and
  topics (LLP 1067.000).

**The agent** (new here). The agent drives the authored tree. A target is a
`testId` or a view id, and on iOS a `tap` is a hit test and a direct call on a
node (LLP 1012 §1). A bar button made in a hook is not a node, so `tree` does
not list it and `tap` cannot reach it.

- **So a hook-made control that does something stands for an authored
  control, and calls its `click()`.** The agent taps the authored control and
  runs the same handler. The web has the control, which it needs anyway. This
  is why `click()` is the default.
- **A named action** covers a native control with no authored counterpart.
  r2 D3 adds it with its first case, and 1075.001 leaves it open. This plan
  adds a requirement for that case: the action appears in `tree` on the node that
  exports it, and the agent invokes it as a form of `tap` on that node,
  delivered as `recognized`. It is never a tenth operation (`DEFERRED.md`,
  Agent API). LLP 1012 says an agent never runs an action by name, so that
  sentence is amended in the same decision or the case is refused.
- **What a finger does to a hook-made control** is checked by the UIKit
  XCTests' real touches. Under the agent the authored header paints, as LLP
  1035.001 D9 proposed under LLP 1021 D4's rule, and hooks still run and are
  journaled.

### 3.5 What Exact owns

Exact owns frames, scroll coordinates and the structure of stacks and tabs. It
measures the content area its containers leave after hooks run (bar heights,
safe-area insets) and lays out inside it, as it does for
`env(safe-area-inset-*)`.

| Object | Exact owns | The app may set |
|---|---|---|
| Node view (with `element`, later) | frame, bounds, center, transform, alpha, `isHidden`; the layer paint Exact draws; subview order; the gestures and accessibility Exact derives | interactions (context menu, drag and drop, pointer, edit menu); its own gestures, under LLP 1057's precedence; anything not on the left |
| Scroll view | `contentOffset`, `contentSize`, `contentInset` and its adjustment behavior, `delegate`, `keyboardDismissMode`; which one is the content scroll view | indicators, deceleration, `scrollsToTop`; anything not on the left |
| Route controller | its view and that view's subviews; how it is presented | the `navigationItem`, over the defaults Exact projects from an authored header; `toolbarItems` once a toolbar is projected |
| Navigation controller | `viewControllers`, the delegate slot, the pop gestures' delegates, bar visibility (§3.7), title collapse (Stage 3) | bar appearance, `prefersLargeTitles`, tint; delegate methods, through forwarding |
| Tab container (Exact's) | its tabs and their controllers, selection, the delegate slot | appearance; minimize behavior, once Stage 2 has checked whether it moves the content area; delegate methods, through forwarding |

- **Exact never writes the right-hand column.** So an ordinary update cannot
  reset what a hook set there.
- **Static geometry is the app's.** A hook may change a container's static
  geometry (a prompt, a search bar that stays put), because Exact measures
  again.
- **Continuous geometry is Exact's.** A hook may not drive geometry that
  changes while the user scrolls (a collapsing title, a hiding search bar)
  until Exact maps that change (Stage 3).
- **The content scroll view is named.** A route names it by HTML id,
  `navigationScroll="list"`, the way `navigationBack="back"` names its Back
  control. It is one new prop of Exact's own. Nothing searches descendants for
  the scroll view (E7).
- **Delegates are forwarded.** Exact keeps the navigation and tab controllers'
  delegate slots, because it reconciles pops and selection there (LLP 1035.001
  D1, D2).
  - Each call goes on to the app's delegate after Exact's own handling.
  - Methods Exact does not implement go straight to the app. Custom transition
    animators are the main ones.
  - A custom transition still dispatches Back exactly once when it completes
    and never when it is cancelled.
- **Projected defaults.** Where Exact projects an authored header into the
  navigation item (§3.7), it writes when the authored source changes and then
  runs the route hook. So what the hook sets is what the frame shows.
- **The development check.** Before applying each batch, a development build
  compares each property Exact owns on a hooked object with what Exact last
  wrote. It journals a difference once, by name: `route inbox: contentInset
  changed outside Exact, which owns it`.
  - It sees a change from any source, including one made long after a hook
    returned.
  - It is detection only. Production does not check, and a change made and
    undone between two batches is not seen.

This revisits LLP 1035.006 12.08, which refuses "an uninspectable native object
bag". The refusal is kept for Contract: no native property name enters it.
Native code stays typed Swift, and every hook call is in the journal.

### 3.6 The route-content seam

One session and its router stay the single authority, and route content is
shown in controllers the app owns.

- **Route content is a controller** that ExactKit vends, with the route's
  subtree as its view. Today's private `RouteController` is the implementation
  to put behind a public type.
- **The app's container sends intents:** `select(tab)`, `back()`, `open(url)`.
  Exact applies the router verb (LLP 1038 D4) and moves the controllers. A
  completed native change updates the router once, and a cancelled one leaves
  it unchanged. The controller tree follows the router without echoing a
  second event.
- **Each route has its own content area.** It lays out in its controller's
  safe area, not the session's viewport. This is the same kernel work a route
  under a bar needs.
- **Containment is real:** `addChild` and `didMove(toParent:)`, appearance
  transitions, safe-area and keyboard propagation, focus and teardown (E3).
- **A native scroll subtree** the app owns either exchanges coordinates with
  Exact explicitly or stays wholly native (1075.001 §4).
- **A native screen** is a route whose content is a module tag whose factory
  returns a `UIViewController` (LLP 1024's factory, one level up). On the web
  the same tag is a custom element.
- **The web has no form of the seam.** Route content there is DOM. An app that
  owns its iOS container keeps the authored `tablist` for the web.
- **A UIKit app with Exact screens** is the coarse option and works today:
  `ExactApp`, `ExactSession` and `ExactView`, driven by `smoke host-ios`
  (F10). Each surface is a session. Sessions share the durable store (LLP
  1031) and no live state. It is documented as an adoption path, with its
  per-session cost measured first.

### 3.7 Exact's containers

**The navigation bar.**

- **One bar per stack.** Visibility belongs to the stack and is set when the
  stack is built. A route fills the bar or leaves it empty, and the bar is
  never toggled per route across a transition (LLP 1037 F1).
  - `ExactNavigation.showsBar` defaults to whether the stack's first route is
    header-shaped, and the `navigation` hook may set it.
  - Hiding the bar for one route (a photo viewer) is admitted later, as an
    explicit request that passes F1's checks and the cancelled-pop case. One
    bar per stack is the first step, not a permanent limit (1075.001 §5).
  - An app that owns its container owns this choice.
- **Fixed first (Stage 1).** A title and bar items that do not move the
  content area while the user scrolls: an inline title, or a large title that
  stays large if UIKit holds it still with no content scroll view attached.
  The content area is the controller's safe area, measured after hooks. A
  fixed inset is a constant shift between UIKit's offset and CSS `scrollTop`.
  That is F6's inference, and Stage 1 confirms it against the browser.
- **The title's source is the authored header** (LLP 1035.001 D9's
  header-shaped route). The web paints the header. iOS lifts its heading into
  the bar and does not paint it. The agent sees the authored one. D9 left open
  what the header's buttons become. Stage 1 answers it, because a button in a
  header that iOS does not paint is otherwise out of a finger's reach.
- **Collapsing large titles (Stage 3)** need D9's single mapping of native
  available area, content origin, a changing inset, and authored assignments
  and events. D9's three rounds are spent. Stage 3 opens with that mapping
  written down and gets three rounds. If it stops again, a large title that
  does not collapse stays the supported behavior.

**The tab container.** `UITabBarController`, one navigation controller per tab
(LLP 1038 §7's "one navigation owner per tab"), with each live tab's stack
retained.

- **Authoring is settled first in Stage 2,** following the web where it has an
  answer. r2 rendered every visited tab's stack and named the tab on each
  route row. The web's own structure for tabs is ARIA's: a `tab` names its
  `tabpanel` with `aria-controls`. The kernel carries neither yet.
- **iOS.** The authored symbol-over-label `tablist` supplies the items. That
  is LLP 1059's shape rule, projecting to the controller and no longer to a
  bar inside a box. Reselecting a tab pops it to its root (LLP 1038's
  `select`). The `tabs` hook sets appearance and minimize behavior.
- **Web, macOS and Linux.** Unselected tabs stay mounted, hidden and inert,
  which is LLP 1038 D6's rule applied to every retained tab. A switch is a
  history entry on the web (D12). The bar is the authored `tablist`.
- **Lifetime.**
  - Retained means each live tab's current stack. A popped screen is released.
  - Hiding a tab does not cancel its work. Destroying a route drops its
    callbacks, so none reaches a successor.
  - A value that must outlive a screen belongs in state, not in a view that
    happens to be retained. Surviving a process restart is a separate feature
    and is not implied.
  - Memory is measured with every tab visited and under a memory warning. Any
    later eviction has to define restoration (1075.001 §5).

### 3.8 The first frame

As Q3 is ruled. Under (c), a cold launch goes in this order:

1. Exact builds the containers and the first routes from the plan, with the
   bar and title its own projection gives. That is the first frame.
2. The turn after it is drawn, the module loads, as it does today.
3. The hooks run for what is live (§3.2).

### 3.9 The surface and how it is kept

- **The surface** is the hook methods and their handles, the seam and its
  intents, §3.5's table, and §3.2's moments. The presenter's internals stay
  free to change.
- **A break is a compile error** in the app's module (Q1).
- **The module table grows by size,** as `prepare_for_reuse` did (offset 104,
  `size ≥ 112`; LLP 1067.000 D2). A removed or changed entry is a new major,
  refused by name at load, as "module ABI 1, host ABI 2" is today.
- **A fixture keeps it.** `apps/native-fixture` grows a hook module that
  exercises every hook, the seam and the development check.
  - `smoke.mjs` drives it on iOS, macOS and the web.
  - The UIKit XCTests cover what needs a real touch.
  - Today the smoke is not in the per-commit async lane; the XCTests are, for
    commits under `host/apple`. So Stage 1 puts a test that builds and runs
    the fixture's hooks where that lane already looks. A break is then
    attributed to its commit, and no check is added.

### 3.10 TypeScript, by experiment

After Stage 1, bind the hook handles into TypeScript through NativeScript's
engine-independent runtime (`napi-ios`, E1) and answer five questions
(1075.001 §6, r2 D10):

1. **Runtime.** Does it run on Exact's pinned, bytecode-only Hermes, or need
   another runtime, and at what cost?
2. **Thread.** Where does native-facing JavaScript run, and how does UIKit get
   an immediate delegate result without re-entering the owner (F5, E8)?
3. **Lifetime.** Who retains a UIKit object or a JavaScript callback, and what
   invalidates a handle on reload, unmount or session end?
4. **Cost.** Do only the apps that use it pay? Build, first-pixel, binary and
   interaction costs are measured. Native behavior would also arrive in
   TypeScript updates, which the delivery classifier treats as non-native (LLP
   1030).
5. **Limits.** Which APIs need an SDK or metadata rebuild, which still need
   Swift, and how is the author told?

Immediate decisions stay in Swift during the experiment. If it fails, Swift
hooks remain the answer and generated selective adapters are compared next
(E4).

The experiment adopts nothing. `DEFERRED.md` says nothing runs JavaScript above
the data seam, "not in Contract, not in the tree, not before first pixel", and
TypeScript that configures UIKit objects is in the tree. Adopting it would be
a separate ruling on that line.

Its strongest argument is iteration (new here). A Swift hook edit is a module
rebuild and an app restart (LLP 1024 D6). A TypeScript edit today reloads in
place and carries state. Whether hook code bound to live UIKit objects could
do the same is question 3. The compile is quick (§6), so what Stage 1 has to
measure is the restart and getting back to the screen.

### 3.11 The other hosts

- **Web.** `modules/web/index.js` may export the same hooks, receiving DOM
  elements. `click()` and `focus()` are the DOM's. Most web hooks are empty,
  because the authored header and `tablist` already paint.
- **macOS.** The same Swift hooks, with AppKit objects where the host has
  them. macOS does not project routes, so the route and tab hooks do not run
  there.
- **Linux.** No module, so no hooks.
- **Android, later.** Kotlin hooks with the same names.

### 3.12 James's navigation patch under this plan

In Contract, with the header the web needs anyway:

```
column navigationKey=`${e.id}` navigationScroll="list" data-trailing="compose"
  header
    text "Inbox" aria-level=1
    button id="compose" press=newMessage aria-label="New message"
      image "symbol:compose"
  scroll id="list"
    …
```

In `modules/apple/App.swift`:

```swift
final class App: ExactModule {
    override func navigation(_ navigation: ExactNavigation) {
        navigation.controller.navigationBar.prefersLargeTitles = true   // stays large until Stage 3
    }
    override func route(_ route: ExactRoute) {
        let item = route.controller.navigationItem                      // the title is already "Inbox"
        item.backButtonDisplayMode = .minimal
        item.rightBarButtonItem = route.data[.trailing].map { id in
            UIBarButtonItem(image: UIImage(systemName: "square.and.pencil"),
                            primaryAction: UIAction { _ in route.element(id)?.click() })
        }
    }
}
let exactModule: ExactModule.Type = App.self
```

`route.data[.trailing]` is a typed key, as under Q2 A. The part of his 99-line
patch that configured the bar and its item, about a third of it, becomes this.
The rest (the bar, the content area, the scroll mapping) is Exact's to build
once, for every app. Nothing lands in his app as a patch, and the agent drives
the screen through the authored Compose button.

One gap under Q3 (c): this hook asks for large titles, which is geometry. On the launch screen the hook runs a frame or two after the first,
so the content moves once unless the plan already says large. Every later
screen is right from its first frame. Stage 1 films exactly this.

## 4. Stages and acceptance

**Stage 0 — reproduce and measure what already exists.**
- James's two cases at a pinned revision, in his app or a fixture, with
  1075.000 §6's probes: which tab state is lost, and under which authoring
  pattern.
- An existing module's open time on an iPhone (`apps/recorder`), on a warm
  launch and on the first launch after install.

**Stage 1 — hooks and the fixed bar.**
- Scope, first half: `data-*`; `navigation`, `route` and `routeEnded` with
  §3.2's moments; `click()`; the named content scroll view; one bar per stack
  with the content area measured again; delegate forwarding; the development
  check; the fixture and its per-commit test.
- Scope, second half: the header-shaped route for a fixed bar, with the answer
  to what a header's buttons become. If Q3 is ruled (a), this half may follow
  Stage 2.
- Acceptance:
  - The patch's title mode, trailing button and minimal Back run as app Swift,
    with no Exact edit.
  - Under Q2 A, an undeclared `data-` word fails the bake by name and a
    misspelled key fails the Swift build.
  - A stack built after the module loads has its bar in place before its
    first child is laid out.
  - `scrollTop` 0 and 80 under a fixed bar match the browser.
  - A real touch on the hook's bar button runs the authored control's handler.
    The agent's `tap` on the authored control runs the same one, and `logs`
    names each hook call.
  - A deliberate write to something Exact owns is journaled by name.
  - A custom push and pop animation, through the forwarded delegate,
    dispatches Back once on completion and never on cancellation.
  - A header-shaped route's title is in the first frame of a cold launch, with
    no app code run before first pixel. The authored header paints on the web
    and under the agent.
  - The fixture passes on iOS, macOS and the web.
  - An app with no hooks runs no new code, and its rows in `metrics.mjs` do
    not move.
- Measured for Q3 and §3.10: a cold launch filmed on a phone with and without
  hooks, and the time from a one-line hook edit to seeing it, on a simulator
  and on a phone.

**Stage 2 — the seam and tabs.**
- Scope: §3.6; the tab container built on it; retained tabs on every host;
  the `tabs` and `tabContainer` hooks.
- Acceptance:
  - A scroll offset, a draft and a pushed screen survive a switch away and
    back, on iOS and the web. Reselecting pops to root.
  - A tab updated while hidden shows the update when selected. Unmount and
    remount work.
  - A session destroyed with work outstanding delivers no late callback to a
    successor.
  - Memory is recorded with every tab visited, and under a memory warning.
  - A custom controller hosts one route, and a tab's root is a native
    controller, through public API only.
  - Minimize behavior is checked for whether it moves the content area.
  - The same Contract's URLs and history work on the web.

**Stage 3 — collapsing large titles.**
- Scope: D9's mapping, written first (§3.7).
- Acceptance:
  - D9's assignment fixtures against the browser: `scrollTop` at the top,
    middle and end, at header heights 74, 106 and 148, across a header resize
    and a title change.
  - Its gestures: short and overflowing lists, collapse, pull-to-top, and a
    held then cancelled sheet drag.
  - LLP 1037 F1's mixed-stack blur, Back-identity and bar-tap checks.
  - Push and cancelled pop with the keyboard up.

**Stage 4 — the TypeScript experiment (§3.10).** It starts after Stage 1. Its
answers are recorded whichever way they come out.

**Stage 5 — more hooks, on demand.** `element` and the named action each come
with a first case. Scene and app events (URLs, user activity, phase) come
after that.

### 5.2 Risks

- **Stage 1 is the largest stage.** It now carries the fixed bar and the
  header-shaped route as well as the hooks.
- **The seam is the largest single piece.** Per-route content areas and real
  containment are kernel and presenter work, and they widen what the surface
  has to keep.
- **The surface is a standing cost.** Every presenter change near a hooked
  object pays review and fixture time.
- **Forwarded delegates can disturb pop reconciliation.** Stage 1's transition
  check guards it.
- **A hook can misbehave where Exact cannot see,** for example with a gesture
  that steals touches. The journal helps diagnose it and prevents nothing.
- **Retained tabs hold memory,** as UIKit's do.
- **Stage 3 may stop again.** Large titles then stay uncollapsed.

## 6. Measured, and not

Measured on 2026-10-01 on this Mac (18 cores, load average 8–10), with scratch
scripts that were not added to the repo:

- **Compile:** `swiftc` with the build's own flags (`moduleArgs` in
  `host/apple/build.mjs`) on copies of two apps' module sources,
  `native-fixture` (520 lines with the host's glue) and `recorder` (693).
- **Open:** `dlopen` of the macOS artifact those compiles made, in a fresh
  process with AppKit already loaded, then the table's first call.

| What | Result |
|---|---|
| Recompile the module after a one-line edit | 1.3–1.7 s per slice, 12 runs. An iOS build compiles two slices: the target's, and a macOS one to check the roster |
| First compile with a cold module cache | 4.5–9.0 s per slice |
| Open an artifact the system has already seen | 1.7–2.4 ms, 30 loads |
| Open a fresh copy for the first time | 119–380 ms, 6 loads. LLP 1067.000 D8 recorded 164 ms for the same event |
| The table's first call | about 0.1 ms or less |

Already on record (LLP 1067.000 D8): the artifact starts loading 5.7–8.9 ms
after first pixel on macOS and 9.8 ms after it on the iOS simulator.
