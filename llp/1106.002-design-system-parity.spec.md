## Lengths and scaling

[observed] `withUniwindConfig` uses `polyfills: { rem: 14 }`. The body's default text size is independently 16. These numbers are not inconsistent: layout utilities can use rem while the authored text scale uses explicit px values. The desktop clone's 16 px root and 12–20 interface-size preference do not apply to this mobile app.

[inferred] Set the mobile Contract root to 14 with the existing `setRootFontSize` command when implementing rem-based styles. Retain each source's explicit point/px number. Do not convert a literal 16-point body size to 1rem, and do not change the root rem when the user changes the mobile base-font preference. Port `resolveTextScaleVariables` and native typography calculations into mobile presentation values instead.

| Source quantity | Planned Exact value at normal scale |
| --- | --- |
| 1rem | 14 logical layout units |
| 0.25rem | 3.5 |
| 0.5rem | 7 |
| 0.75rem | 10.5 |
| 1.5rem | 21 |
| 2rem | 28 |
| 3rem | 42 |
| Explicit 16px body font | 16, independent of root rem |
| `min-h-8` work-log row | 28, explicitly confirmed by layout.ts |

[observed] `global.css` does not define a global spacing or radius override. The conversion table is rem arithmetic, not a claim that every named utility uses that unit. Read each component's classes and resolved dependency styles before translating a utility. Inline widths, safe-area values, native bar heights and measured keyboard values remain their own quantities. An apparent CSS reset or React Native default never changes Exact's CSS defaults; author the required box behavior explicitly.

### User preference and accessibility scaling

[observed] `appearancePreferences.ts` defines baseFontSize default 16, rounded and clamped to 11–22 with step 1. For a normalized base `b`, text-role font size is `max(8, round(authoredSize × b / 16))`; line height is `max(10, round(authoredLineHeight × b / 16))`. Preserve the distinction between an explicit code/terminal override and `null`, which means derive from base.

| Quantity | Planned calculation/value |
| --- | --- |
| Code default and clamp | 12; round and clamp to 8–18; step 1 |
| Derived code size | `normalizeCodeFontSize(round(12 × b / 16))` |
| Terminal default and clamp | 10.5; clamp to 6–14; UI step 0.5 |
| Derived terminal size | `normalizeTerminalFontSize(round(10.5 × b / 16 × 2) / 2)` |
| Markdown body | `b`; line height `max(18, round(23 × b / 16))` |
| Markdown headings h1–h6 | `max(minimum, round(authored × b / 16))`, authored `[21,19,17,15,15,15]`, minima `[16,14,13,12,12,12]` |
| Markdown small | `max(10, round(14 × b / 16))` |
| Markdown code block | `max(10, round(13 × b / 16))`, line height font size + 6 |
| Code word break | False unless stored value is exactly true |

The terminal limits come from [`apps/mobile/src/features/terminal/terminalPreferences.ts`](https://github.com/pingdotgg/t3code/blob/365aa87982/apps/mobile/src/features/terminal/terminalPreferences.ts#L1). Directly stored terminal sizes are clamped but not rounded to half points by normalization; the half-point snapping belongs to derivation and UI stepping.

[observed] Mobile layout separately reads the OS font scale when predicting work-log row heights. Its estimated height is `max(28, ceil(scaledFootnoteLineHeight × fontScale))`; it promises a fixed 28 only when `fontScale <= 1` and the line height is at most 28. [inferred] Match the user's OS text setting on both apps, and avoid applying OS scale twice to native text. Actual UIKit glyph/line metrics still need measurement.

### Dense code geometry

[observed] The unscaled mobile code surface is rowHeight 22, gutterWidth 46, codePadding 7, textVerticalInset 2, code font 12 and line-number font 11. `resolveMobileCodeSurface` changes only font size, line-number size and row height when the code preference changes. For normalized code size `c`, line-number size is `max(8, round(11 × c / 12))` and row height is `max(14, round(22 × c / 12))`. Gutter, padding and vertical inset remain fixed.
