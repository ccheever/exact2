## Summary

LLP 1041.010 sorted Unreal's lead into "out of reach" and "we win by construction." Charlie's
follow-up: is any of the out-of-reach column *cheaper than it looks* — either because of a
decision this tree already made, or because it only recently became possible at all?

Six candidates, in two groups. The strongest structural one is **cluster-LOD geometry without the
software rasterizer** (O1): the half of Nanite that delivers the feature is an offline bake plus
GPU culling, it fits the baked, digest-addressed asset pipeline already wanted, and — checked
today — the half that *doesn't* fit is blocked by hardware on three of this tree's four hosts, so
the awkward two-path design mostly resolves itself. The strongest new-because-of-AI one is not a
renderer feature at all: **generated content attacks U2, the content moat, which is the part of
Unreal's lead that was previously only purchasable** (O5).

The most useful output may be O6, a prioritization rule rather than a feature: implementing
published technique is now the cheap part, so the binding cost is the *oracle*. Work with a
number to check against gets dramatically cheaper; work whose oracle is human taste does not move
at all.

Nothing here is measured, and nothing here is a proposal. Three claims were checked against
vendor documentation on 2026-09-19 and are cited; the rest is reasoning from the corpus.

## 1. What this is

A speculative companion to LLP 1041.010, written because that document's §2 ("out of reach") is
easy to read as a flat wall when it is not. It is research in the sense `rules/RULES.md` means:
no implementer, no date, no scope change requested. Where a claim was checked it says so and
links the source; where it was not, it is marked.

The test applied to each candidate is the one LLP 1041.003 §1 already uses — not "could this be
built" but "does this get an agent closer to closing the loop without a human's eyes, at a cost
this repo's budgets can carry."

## 2. Opportunities that follow from decisions already made

- **O1. Cluster-LOD geometry, without the software rasterizer.** Nanite is two separable
  mechanisms: a cluster hierarchy (meshlets built by recursive group-and-simplify into a LOD DAG,
  selected and culled on the GPU) and a compute-shader rasterizer for sub-pixel triangles writing
  a visibility buffer. The first delivers the *feature* — no authored LOD chains, no draw-call
  budget, no artist decisions about triangle counts. The second is a performance optimization for
  extreme density.

  Three things make the first cheap here. The DAG build is an offline bake whose output is
  immutable and content-addressed, which is the shape LLP 1041.007.000 and F9 already want, and
  which LLP 1041.009 D4 already separates from entity slots. `meshoptimizer` supplies meshlet
  building and border-locked simplification, so the bake is assembly rather than research.
  And [Bevy has a virtual-geometry implementation on wgpu](https://jms55.github.io/posts/2025-03-27-virtual-geometry-bevy-0-16/),
  permissively licensed and readable — to be read, not depended on, per F26.

  The second mechanism is where it stops, and the reason is better than expected. It needs 64-bit
  atomic min/max on buffers or textures. Bevy's implementation
  [requires `SHADER_INT64_ATOMIC_MIN_MAX`](https://bevy.org/news/bevy-0-15/) and panics on
  hardware without it. WebGPU has no such feature in core
  ([gpuweb#5071](https://github.com/gpuweb/gpuweb/issues/5071) is open), and `gpu/Cargo.toml`
  pins wgpu 30 with the `webgpu` backend for the web build. Apple's
  [feature set tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) put 64-bit
  atomic min/max on buffers and textures at GPU family Apple8 **and macOS only**, with the full
  set from Apple9 on all platforms *(the chip-to-family mapping was not verified; check the table
  before relying on it)*. Linux is the headless fleet host, where readback may run on software
  Vulkan (F18) and certainly will not have it.

  So on this tree's four hosts the software raster is available on recent macOS, conditionally on
  recent iOS, and not on web or the fleet. That argues for **clusters plus hardware raster, one
  path on every host** — which keeps F3's one-representation-two-executors habit intact instead of
  breaking it, and is a simpler answer than the native/web split this looked like at first.
  Bevy's status is experimental, not production, on its own account; that is a caution about
  maturity, not about the technique.

- **O2. Baked GI is cheaper for this tree than for Epic, and for a non-obvious reason.** Lumen
  exists substantially because bake times destroy a *human* iteration loop. That constraint does
  not bind here: `rules/RULES.md` §Loop shape already says run everything and block on almost
  nothing, with slow verification running async on fleet hardware. Meanwhile F22 already commits
  to a reference path tracer as the renderer's correctness oracle and already notes it doubles as
  a lightmap baker. The expensive artifact is therefore owed twice before GI is discussed at all;
  probe-based irradiance for dynamic objects on top of it is a third use of something already
  paid for. The result is not Lumen — no fully dynamic global illumination, and relighting means
  rebaking — but it is most of what a small game wants from it, and it lands on the side of the
  build/runtime line this repo prefers.

- **O3. Do not chase Unreal's netcode; take the one Unreal cannot have.** LLP 1041.010 U4 records
  that this tree has no networking and correctly calls the replication gap unanswerable. But
  replication with client prediction and rollback is enormous *because* the simulation underneath
  is not deterministic. Deterministic lockstep is small, and its preconditions are exactly F13 and
  F14 — fixed timestep, seeded randomness as an explicit input, a world hash that already has to
  exist for cross-host parity. Its costs are real and different (input latency, no late join
  without a state transfer, every client simulating everything), and they rule out the genres
  Unreal's model was built for. The point is only that U4 should not be read as "networking costs
  what it costs Epic." If a multiplayer consumer ever appears, the cheap door is a different door.

## 3. Opportunities that are new

- **O4. Blender, headless, as a build-time asset compiler.** F17's "agents are bad at Blender and
  good at code" is true of Blender's *interface*, not of Blender. `bpy` is text, `blender
  --background --python` is a scriptable non-interactive process, and the useful operations — 
  remeshing, UV unwrapping, decimation, baking, glTF export — are callable from it. Invoked by
  the asset bake it is the same shape as a shader compiler: a build-time tool, not runtime
  apparatus, not a check, and nothing an app links. Cycles is additionally a ready-made path
  tracer, which is relevant to F22's oracle and to O2's baker.

  Two cautions. It is a large external dependency to provision on the fleet, and `rules/RULES.md`
  §Agents is deliberately hostile to added apparatus — this needs a human saying so, like any
  addition. And determinism across Blender versions is unestablished; a bake step in the parity
  story would need pinning and its own fixtures. **F17 is worth amending rather than deleting**:
  the claim should be about GUI-shaped authoring, not about the tool.

- **O5. Generation attacks U2, which is the actual moat.** LLP 1041.010 U1 (the default look) and
  U2 (the content library) are usually collapsed together, and they should not be. U1 needs taste
  and does not move (§4). U2 is an inventory — meshes, materials, animations, audio — that was
  previously acquirable only by purchase or by staffing artists, and is the part of Unreal's lead
  that generation attacks directly: text-to-3D, PBR material synthesis, text-to-motion, and video
  mocap. F20 already names text-to-motion and flags retargeting as one of skeletal animation's two
  real costs; video-derived motion is the newer half of that answer. F17's procedural route
  (SDFs, vector art, shaders as art, synthesized audio) is the same bet made without models, and
  the two compose rather than compete. Open question in §5 Q1: whether either holds at the content
  volume where an Unreal user reaches for a marketplace.

- **O6. The rule the other five are instances of: implementation is cheap now, so the binding
  cost is the oracle.** F21's correction — "a comparable renderer is feasible; 'years' was a
  human-team prior" — is this observation applied once. Stated generally: converting published
  technique into working code is the part that got dramatically cheaper, so what remains expensive
  is knowing whether the result is right. That predicts which parts of Unreal's lead close and
  which do not, and it agrees with F22's insistence that the renderer's real problem is
  verification.

  Work with a number to check against gets cheap: PBR against a white-furnace test and a
  path-traced reference, a pose against a bone position at time *t* (F20, under the seekable
  clock), a simulation against a world hash (F14), a scene against a fixture. Work whose oracle is
  a human eye does not get cheaper at all. **As a prioritization rule: prefer the subsystem with
  the numerical oracle, every time, and treat "what is the oracle" as the first question asked of
  any candidate in §2 or §3.**

## 4. What does not move

- **The default look (U1, F23).** Art direction's oracle is taste. Nothing in §2 or §3 touches it,
  and O6 says why. This remains the honest answer to "as good as Unreal."
- **Platforms and consoles (U3).** A ruled exclusion in `rules/NOT-DOING.md`, not a cost estimate.
- **The device long tail (F23).** Unchanged: shrunk by the exclusions, not by anything here.
- **Unreal's own systems at Unreal's scale** — World Partition, virtual texturing, the replication
  stack (U6, U4). O1 and O3 are *different, smaller* answers to adjacent problems, not cheap
  versions of those.

## 5. Open questions

1. **Does O5 hold at volume?** LLP 1041.000's test game is small enough that generated and
   procedural content is plausible. Whether an agent-authored pipeline survives at the size where
   an Unreal user reaches for Fab is untested by anything in this series.
2. **What is O1's first falsifying test?** Probably the cheapest experiment in this document: bake
   one glTF into a cluster DAG offline, select and cull on the GPU with hardware raster, and
   compare frame time and triangle throughput against the naive draw on one real GPU. It needs no
   engine, no renderer and no lane — but it also needs a consumer before it is worth anyone's
   time, per the series' own habit of refusing specs without one.
3. **Is O2's probe step actually small?** The path tracer is owed regardless; probe placement,
   storage and leak handling are the part that is not, and no estimate here is grounded.
4. **Does O4 survive the apparatus rule?** A build-time Blender dependency is exactly the kind of
   addition `rules/RULES.md` §Agents says an agent may not make unilaterally. It is written here
   as an observation, not a request.
5. **Would O3's constraints rule out the games this lane wants?** Lockstep forbids late join and
   hidden information handled naively. LLP 1041.000 is single-player, so the question is unforced
   today.

## Confidence

**High** on what was read from this tree on 2026-09-19: the wgpu 30 / `webgpu` pin in
`gpu/Cargo.toml`, LLP 1009 D5's actual wording, `rules/RULES.md` §Loop shape and §Agents, and
every LLP 1041 finding cited.

**Medium** on the vendor claims checked today and linked in O1 — Bevy's meshlet feature and its
`SHADER_INT64_ATOMIC_MIN_MAX` requirement, WebGPU's lack of 64-bit atomics, and Apple's family
Apple8/Apple9 split. These were read from documentation and release notes, not run. The
chip-to-family mapping in particular was **not** verified and is the most likely error in this
document.

**Low** on every cost characterization — "small," "cheap," "assembly rather than research." No
experiment in §5 was run. O2's probe step and O3's lockstep sizing are reasoning by analogy, and
O5 is an expectation about generated content at a volume nobody here has attempted.

## Follow-up (2026-09-20): O1's falsifying test was run

§5 Q2 was run on 2026-09-20 at Charlie's request, as a standalone experiment:
`experiments/cluster-lod/` on branch `lane/cluster-lod` (own Cargo workspace, outside the five
checks, not on `main`). Its README is the record; this section is the summary. Coding by astra,
two rounds of mutually blind review by grok and a fresh astra session, every headline number re-run
by the orchestrator on an Apple M5 Max.

**O1 holds.** Clusters plus hardware raster, one path, core WebGPU only
(`Features::empty()`, `Limits::default()`), runs natively on Metal and in Chrome from the same Rust
and the same WGSL:

- *Bake is assembly, not research.* Vendored meshoptimizer v1.2 + `clusterlod.h` behind a small C++
  shim: 16.86 M triangles (Smithsonian "George Washington", CC0) → 58 s, ~37 bytes per source
  triangle, paged ≤ 32 MiB coarse-first, byte-identical across repeats. Per-vertex AO bakes in 12 s.
- *The win is scale, and it is large.* Total GPU time per frame (selection + main + shadow,
  2560×1440, 1 px error, cluster and naive interleaved, naive = indexed, cache-optimized, equally
  frustum-culled): Washington ×400 13.5 ms against 917 ms (68×; 8.7 against 769 ms, 89×, in the
  orchestrator's rerun on a loaded machine); Dying Gaul ×400 1.5 against 162 ms (109×); ×5,000
  9.0 against 2,510 ms (280×) and 89 against 10,313 ms (115×). CPU stays under 1 ms per frame and
  independent of instance count. A 25-statue avenue (421 M source triangles) presents at 120 Hz in
  a window — interval p50 8.33 ms, 12–45 of 600 frames late across runs on a shared machine — where
  the naive path drops ~1,200.
- *It does not win everywhere, and the first headline hid that.* One statue filling the screen,
  shadows off, LOSES: Gaul 1.83 against 1.32 ms, Washington 5.87 against 2.29 ms, because GPU
  selection for a near instance (≈3 ms: its candidate range is the whole cluster table) dominates.
  With shadows on the single statue wins 1.5–2× only because cluster shadows are cheap. Selection
  cost is the known headroom; the baked BVH (emitted, validated, unread) is the hook for it. The
  main-pass-only ratio the experiment first reported was flattering; the second review round
  caught it.
- *Web.* 152 KB gzipped wasm; first frame from page 0 alone in 0.7–0.9 s (Dying Gaul) and 2.2 s
  (Washington), full detail in 1.0–1.4 s / 4.0 s on localhost; Chrome canvas equals the native render
  to ≤ 3/255. Pages stream coarse-first with cuts kept watertight under partial residency.

**Corrections to O1's text.** (a) Bevy (≥ 0.15) needs 64-bit atomics for its *hardware* pass too —
since 0.16 as storage-texture atomics — so it has no non-atomic path at all today. (b) Bevy is the
wrong source for the bake: its DAGs are coarser than the reference (bevy discussion #14998) and need
METIS; `clusterlod.h` is the maintained, dependency-free reference and what the experiment used.
(c) If a software rasterizer is ever wanted on hosts without 64-bit atomics, core WGSL's
`atomic<u32>` allows a deterministic two-pass form (atomicMax depth, then atomicMax id where depth
equals the winner) at roughly twice the raster work. Unmeasured.

**O6 showed up twice, and the second time it bit the orchestrator.** The implementation compiled
and passed first try; what took the day was the oracle. The first crack oracle ("every edge used
exactly twice") was green on one fixture and failed 378 of 10,815 cuts across 21 — and was itself
wrong: it tests *manifold*, not *watertight*. Every failing edge was a balanced pinch (incidence 4,
net winding 0; zero non-zero-winding edges in 614 M triangle occurrences). A "fix" built on the
strict oracle cost 30–80× in the far field and removed no hole, because there were none. The claim
is now the correct one — every group transition preserves the oriented boundary 1-chain, so every
cut of a closed mesh is closed — and both review families failed to construct a counterexample.
The lesson generalizes: *an oracle is a specification, and a wrong specification is cheaper to
write than a wrong implementation and more expensive to discover.*

**What this does not establish.** iOS and Linux/Vulkan were not run. All pages are resident (the
hero needs ~0.9 GB of GPU memory); eviction and digest-addressed streaming from an origin are
unbuilt. LOD switches are discrete (measured popping is below the naive path's own frame-to-frame
change at 1 px, but there is no zero-pop guarantee). No occlusion culling. Skinned, alpha-tested and
aggregate geometry are out of scope, as they are for the technique. The look still needs a human
eye (§4): lighting and framing were iterated against stills by an agent, and that is not taste.
