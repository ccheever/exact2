# LLP 0492.001: M-D's layout-motion budget — classification, and the re-derivation the measurement forced

**Type:** Decision
**Status:** Draft (agent-proposed; the gates below land enforcing this reading, and overturning it is a manifest edit plus a re-run of two registered checks)
**Systems:** Motion, Kernel, Layout, Verification
**Author:** Claude (Opus 5) for Charlie Cheever
**Date:** 2026-08-26
**Revised:** 2026-08-26
**Related:** RFC 0492 §4.4 (the sink taxonomy and the per-binding budget claim — the text this decision applies), RFC 0492 §5 M-D (the gated workstream and its four named customers), RFC 0491 §7.4 r15 (the ownership transfer that made the number 0492's), RFC 0491 WS-H (`kernel/src/dirty_set.rs`, the instrument this reads), RFC 0496 §4.4 (gates that prove themselves), LLP 0486 (the "doctrine with no instrument" failure mode M-D's gate is written against), `issues/20260826-ws-h-patch-to-receipt-cost-flat-in-k.md`

## 0. What this decides

RFC 0491 §7.4 r15 transferred three things to RFC 0492: the ≤1 ms / ≤64-node
number, **the classification of which animations may claim the ≤64 budget**, and
M-D's gate. The instrument landed 2026-08-26 (`kernel-p5-dirty-set-instrument`,
green) and deliberately gates no threshold. This document is 0492 exercising the
transfer.

It decides four things:

1. The ≤1 ms and ≤64-node halves of the budget are **separate claims with
   separate scopes**, and only one of them discriminates today.
2. Classification is by **binding shape**, not by gesture name.
3. **`reorder` stays a named M-D customer and is exempt from the scalar
   ≤64-node bound**, under §4.4's own symbolic-bound rule — it is not an
   exclusion with its own path, and it is not a case that must be made to fit.
4. The target's founding premise — "these four customers all reduce to a k-node
   dirty set, k ≪ n" — is **false for two of the seven measured cases**, and is
   re-derived here in the open rather than quietly missed.

## 1. The measurement

`kernel-p5-dirty-set-instrument` over the pinned 1K fixture
(`kernel/benches/fixtures/exact-native-layout-1k-v1.json`,
sha256 `9f321b2a…`), n = 1000, release build, 5 repeats per case, affected-set
sizes asserted identical across repeats. Sizes are from the committed pin
(`docs/kernel-refresh/p5/dirty-set-expectations.json`); timings measured
2026-08-26 on `expose-builder-pixel` (Hetzner, 96 cores, Linux, load ≈ 1).

| case | k | k/n | patch→receipt median |
| --- | ---: | ---: | ---: |
| `keyboard-avoidance` | 1 | 0.1 % | 231.3 µs |
| `single-leaf-width` | 3 | 0.3 % | 237.2 µs |
| `container-size` | 4 | 0.4 % | 238.9 µs |
| `single-leaf-height` | 5 | 0.5 % | 238.7 µs |
| `root-resize` | 741 | 74.1 % | 322.5 µs |
| `reorder` | **999** | **99.9 %** | 257.6 µs |
| `paint-only` (negative control) | 0 | 0 % | 229.5 µs |

Two facts fall out of that table, and both change what M-D's gate should be.

### 1.1 `reorder` is not k ≪ n — and cannot be made so

RFC 0491 suspected it; the number confirms it at 999 of 1000.

Read the case honestly before generalising from it. `PatchCase::Reorder`
reverses the children of `widest_internal(fixture)`. On this fixture every
internal node has branching factor 4 and the tie-break is *strictly greater*,
so `widest_internal` returns **the root**. The measured case is therefore a
top-level reversal of the root's four subtrees — each ≈ 250 nodes — which
relocates all 999 descendants. **999 is the worst instance of the class, not a
typical reorder**, and a lane that quotes "reorder is k=999" without that
sentence is over-claiming.

The classification does not depend on that caveat, because the class is
unbounded for a structural reason rather than a fixture reason: a reorder's
affected set is the union of the subtrees displaced between the source and
destination index. It scales with the cardinality of the collection and with
per-item subtree extent. **There is no tree shape in which a general reorder is
bounded by a constant independent of n.** Moving row 3 to row 40 in a
100-row list relocates 37 rows and everything under them, on any renderer, in
any framework, by definition of what a reorder is.

RFC 0492 §4.4 already anticipated exactly this and wrote the rule:

> the **static bound** may be symbolic for dynamic collections
> (`base + rows × perRow`-shaped — **a scalar bound over an unbounded `each` is
> either wrong or vacuous**)

Applying the scalar 64 to `reorder` is, in the RFC's own words, wrong or
vacuous. The §4.4 escape hatch is not a concession invented to rescue a missed
target; it is pre-existing accepted text that this measurement selects.

### 1.2 The ≤1 ms half is satisfied by every case — and discriminates nothing

Every case lands between 229.5 µs and 322.5 µs. `reorder` at k=999 costs
**8 % more** than `keyboard-avoidance` at k=1. `paint-only`, which moves no
geometry at all, still costs 229.5 µs.

This is not noise, and it is not a property of the box. It is visible in the
code: `Kernel::publish_layout_changes` calls `get_layout_tree_nodes(root)` — a
**complete subtree walk** — and diffs every node's absolute frame against
`last_layout_frames`, then builds a `HashSet<ViewId>` over all of them. The
instrumented patch→receipt endpoint is **O(n) by construction, independent of
k**. WS-H's "per-frame work proportional to change" is not yet realised in this
endpoint; the instrument proves the affected *set* is sparse, not that the
*work* is.

The consequence for M-D is uncomfortable and should be stated plainly: **at
n = 1000 on this hardware class, a ≤1 ms timing gate passes a k=0 patch and a
k=999 patch alike.** It measures the machine, not the binding. A full pass costs
≈ 230 µs per 1,000 nodes, so the timing claim starts discriminating somewhere
around n ≈ 4,000 — or as soon as WS-H makes the work track k.

That is filed as `issues/20260826-ws-h-patch-to-receipt-cost-flat-in-k.md` and
commissioned back to RFC 0491 as scheduled kernel skip-work under §7.4's own
rule ("further kernel skip-work is commissioned as scheduled work, with 0492 as
the customer"). It is **not** a reason to weaken or postpone M-D's gate.

### 1.3 Gesture names are the wrong unit of classification

`keyboard-avoidance` measured **k=1**, the sparsest case in the table. That is
not a property of keyboard avoidance. It is a property of this fixture: the root
is a flex column whose children carry authored point heights, so nothing's
geometry depends on the root's height, and shrinking the root by 320 pt moves
exactly one frame — the root's own. Put a single `flex: 1` child under that root
and the identical gesture is k ≈ n.

So the naming cuts both ways: a gesture everyone assumed was sparse can be
dense, and RFC 0491's own framing — "**which animations** may claim the ≤64
budget" — asks the question at the wrong granularity. The answer cannot be a
list of gesture names. It has to be per **binding**, measured, which is exactly
what §4.4's per-binding budget claim already demands:

> a layout-targeting binding carries a compiler-checkable affected-set bound;
> the kernel supplies the affected-set measurement; the claim is verified the
> same three ways a contract block is

This decision therefore classifies *binding shapes* and enforces *measured
per-binding* claims against them. It never says "keyboard avoidance is a ≤64
gesture."

## 2. The ruling

### 2.1 The budget is two claims, not one

`≤1 ms / ≤64 nodes` is read as §4.4 already reads it — two semantics,
deliberately separate:

- **The static affected-set bound.** `≤64` is the **scalar instance** of that
  bound, and binds only bindings whose affected set is bounded independently of
  collection cardinality. For dynamic collections the bound is **symbolic** per
  §4.4, and must be *sound*, *tight*, and *parametric* (§2.3).
- **The timing claim.** `≤1 ms` on the patch-application → receipt-publication
  endpoint binds **every** layout-targeting binding regardless of class, and is
  always separately measured — "a node-count bound never proves elapsed time."

Neither half is a proxy for the other, and §1.2 shows why that matters right
now: today the node-count half is the **only** half that says anything about the
binding rather than about the host.

### 2.2 Three binding classes

| class | rule | measured members |
| --- | --- | --- |
| **`point-patch`** | affected set bounded by a constant independent of n; claims the scalar **≤64**; claims ≤1 ms | `keyboard-avoidance` (1), `single-leaf-width` (3), `container-size` (4), `single-leaf-height` (5) |
| **`collection-extent`** | affected set scales with the displaced extent of a dynamic collection; **exempt from the scalar bound**, owes a symbolic bound per §2.3; claims ≤1 ms unchanged | `reorder` (999) |
| **`viewport-global`** | available space changed at the root, so the affected set is the visible tree by construction; not a frame-budgeted motion binding and **not one of M-D's four customers**; claims ≤1 ms | `root-resize` (741) |

Plus `not-a-layout-binding` for the instrument's negative control
(`paint-only`), which must measure exactly **k = 0** — a paint mutation that
moved geometry would mean the instrument, not the budget, is broken.

`viewport-global` is a declared exclusion **with a reason and a citation**, not
a silent miss: a live window or root resize is host-driven, not authored motion,
and RFC 0491 §4.4 / LLP 0543 §11 already sanction a bounded servicing wait for
exactly that path. It is in the table because the instrument measures it, not
because M-D owns it.

**Wrapping and grid reorder are the second declared exclusion (RULED
2026-08-26).** Reorder in a line-broken container — `flex-wrap`, CSS Grid
auto-placement — is **not an M-D v1 customer, and not silence**. It follows the
`viewport-global` precedent exactly: a named exclusion carrying its citation and
its *measured* counterexamples (§2.3.1), rather than a stretched bound or an
omission. The reasoning is §4.4's own: a permutation there changes line breaking,
so the affected set is structurally unbounded and the excess grows with the
collection. A bound would be "either wrong or vacuous" — precisely the sentence
§4.4 uses to refuse a scalar bound over an unbounded `each`. Building a v1 bound
family for a regime whose *mechanism* is global re-layout, at the end of this
lane, would have produced exactly the unsound-but-tight bound this ruling refused
to build for the linear case.

The exclusion is machine-enforced in **both directions**, which is what makes it
a ruling rather than a shrug: a regime the sweep measures out of domain but
nobody declared is a red (silence), and a declared exclusion with no measured
counterexample behind it is also a red (assumption). Each declaration carries a
reason, a citation, and a **named re-entry condition** — the exclusion lifts when
someone builds the wrapping/grid bound family and its own sweep. Tracked in
`issues/20260826-md-reorder-bound-undefined-for-wrapping-collections.md`.

### 2.3 What a `collection-extent` binding owes instead

The exemption is from the *scalar* bound only. In exchange the binding carries a
symbolic bound in §4.4's `base + rows × perRow` shape, machine-checked to be all
of:

1. **Sound** — `bound ≥ k` at **every** point of a measured family, not at one
   point. A single measurement is an inequality that happened to hold.
2. **Attained** — the family's *tightest* point carries no more than
   `maxSlackNodes` (3) of slack. This is tightness in the standard sense: a
   bound is tight when something reaches it.
3. **Below the collection's own extent** — at every point,
   `bound ≤ base + rows × perRow`. A formula predicting more relocation than the
   collection contains has stopped describing the binding.
4. **Parametric on both cardinality axes** — doubling `movedRows` and doubling
   `perRow` must each strictly grow the bound.
5. **Domain-bounded** — see §2.3.1.
6. **Structural** — the expression may reference only `base`, `movedRows`,
   `perRow`, `rows`. A bound may never read a measured field. Without this rule
   `affectedSetSize + epsilon × movedRows` passes sound, attained *and*
   parametric while predicting nothing: it consumes the answer it claims to
   predict. (Found in review, not by us.)

**Why attainment rather than per-point tightness**, since the first draft got
this wrong: `movedRows` is the displaced **span**, which is sound but
deliberately loose for a non-contiguous permutation — a double swap at both ends
of a 128-row collection spans all 128 while relocating four items, so the bound
reads 512 against a measured `k = 10`. Demanding per-point tightness there would
push an author toward a narrower `movedRows` that is **unsound** for a
reversal's stationary middle row, which keeps its index but not its offset. That
is precisely the soundness-for-tightness trade this ruling refuses, so vacuity is
caught by attainment and the extent ceiling instead.

`reorder`'s bound is `base + movedRows × perRow` with `base = 0`, and both
`rows` and `perRow` for the pinned instance are **derived from the fixture**
rather than declared — otherwise a regressed `k` could be cleared by fitting
`perRow`, which review demonstrated.

#### 2.3.0 Define parameters structurally, never nominally

§1.3 recorded that classifying by **gesture name** is unsound, because the
affected set is a property of the (patch shape × tree shape) pair rather than of
what the gesture is called. The same lesson applies one level down, to the
bound's own parameters, and it was learned the same way — by a definition that
looked obviously right and was wrong on a case nobody had enumerated.

`movedRows` is defined **structurally from the permutation**: the span between
the first and last displaced index. It is *not* `|from - to| + 1`, the rule the
operation's name suggests. Two measured cases kill the nominal reading:

- a **non-contiguous** permutation (two disjoint adjacent swaps at opposite ends)
  has no single `from`/`to` at all, yet displaces items across the whole span;
- a **reversal of an odd collection** leaves the middle item's *index* unchanged
  while its *offset* moves, because the multiset above it changed. A definition
  counting "items whose index changed" is therefore **unsound**, and it is the
  definition almost everyone writes first.

The general rule, and it is the same rule §1.3 states about gestures: **a
parameter must be computed from the structure it claims to describe, never
inferred from the name of the operation that produced it.** A name is a label
someone chose; the structure is what the layout engine actually sees.

`perRow` follows the same discipline — it is the **maximum** per-item subtree
extent, not the average. The average is unsound and one heavy row in a hundred
proves it (a bound of 20 against a measured 501); the maximum over-counts the
small items, which is what the attainment rule in §2.3 is designed to tolerate.

#### 2.3.1 A bound without a domain is not a bound

`base + movedRows × perRow` is **exact** across the measured in-domain family:
120 points over cardinalities {7, 8, 33, 128} (odd included, so a reversal has a
stationary middle), uniform and heterogeneous per-item extents, root and
three-deep-nested containers with following siblings, and five permutation
shapes including a non-contiguous one.

It is **unsound outside that domain**, and this is measured rather than
suspected:

| regime | permutation | bound predicts | measured `k` |
|---|---|---:|---:|
| `flex-row` + `flex-wrap: wrap`, 10 items | move 2 → 3 (**adjacent**) | 2 | **7** (34 of 90 moves violate) |
| CSS Grid `auto-flow: row`, 60 items with spans | move 0 → 1 (**adjacent**) | 2 | **61** |
| the same grid with `auto-flow: row dense` | move 0 → 1 | 2 | 4 |

Two things follow, and both matter more than the numbers:

- **The domain is single-axis, non-wrapping flow containers under a pure
  permutation.** A permutation in a line-broken container changes *line
  breaking*, so items far outside the moved range relocate and the excess grows
  with the collection instead of being absorbed by any constant. Reorder inside a
  wrapping or grid collection is therefore a **declared exclusion for M-D v1**
  (RULED 2026-08-26, §2.2) — named, cited, counterexample-backed, and carrying a
  re-entry condition — never a covered case and never a silent one.
- **Dense grid packing is the *safer* flow, not the more dangerous one.**
  `row dense` back-fills the hole the permutation opened and re-synchronises the
  grid: it measures **k = 4** where plain `auto-flow: row` measures **k = 61** on
  the identical adjacent move. The intuition runs the other way, and **a lane
  that guarded dense would be guarding the wrong regime** — or worse, would
  "improve" this ruling by excluding dense and admitting sparse. It is recorded
  in the sweep, in the manifest's `excludedRegimes["grid-auto-flow-row"]
  .denseInversion`, and here, because a counterintuitive fact that lives in one
  place gets lost and then re-derived expensively.

The gate enforces the domain: a `collection-extent` bound with no declared
`domain` is red; a sweep point outside the domain is red; a sweep carrying **no**
out-of-domain counterexample is red (a domain restriction with no measured
regime outside it is an assumption, not a boundary); a counterexample that stops
violating is red; and claiming a counterexample's layout mode as in-domain is
red.

**Why `base` is 0 and why that is now a measurement.** An earlier revision
declared `base = 8` for an ancestor chain the family could not exercise, because
its reordered container was always the root. Both reviewers called it a magic
number, and one showed the tightness cap had silently fitted it anyway. The sweep
now reorders a container nested three levels deep with a following sibling at
every level, and the ancestors and siblings **do not move**: a pure permutation
preserves the container's content extent, so nothing above or after it can shift.
`base = 0` is the measured value.

### 2.4 The anti-escape rule

The obvious way to defeat this ruling is to reclassify a binding that fails
≤64 as `collection-extent`. So the classification is not free: **a
`collection-extent` binding must measure k > 64 on the pinned fixture.** If its
measured affected set already fits the scalar bound, the exemption is unearned
and it is a `point-patch`.

This is fail-closed in both directions. It blocks the escape, and it also
catches the opposite failure — a case that silently stopped exercising its
collection (a `reorder` that became a no-op would drop to a small k and redden
as an unjustified `collection-extent`, instead of passing as a flatteringly
sparse number).

### 2.5 Coverage of M-D's four customers is declared, not assumed

§5 M-D names four customers: shared-element/FLIP, reorder animation,
container-size motion, keyboard avoidance. Three have instrument cases.
**Shared-element/FLIP has none**, by design — it consumes RFC 0491 WS-C commit
receipts as its before/after geometry rather than issuing a layout patch, so it
is not a `PatchCase`. It is recorded as `unmeasured` with that reason and is
**not** counted as covered. A customer missing from the coverage map entirely is
a red.

## 3. The premise correction, stated plainly

RFC 0491 r6 introduced this target under the reduction:

> Shared-element/FLIP transitions, reorder animation, container-size motion, and
> keyboard avoidance all reduce to: re-solve layout for a k-node dirty set,
> k ≪ n.

For `reorder` that reduction is false — categorically, not marginally. RFC 0491
r15 already hedged it ("reorder and keyboard avoidance are not obviously k ≪ n")
and handed the adjudication here. The honest re-derivation: **the reduction holds
for point patches, and ≤64 is the scalar bound for that class.** The number is
not lowered, widened, or waived; its *scope* is stated for the first time,
because until 2026-08-26 nobody had measured which cases it applied to.

Two rules this decision refuses to break, for the record:

- It does not re-baseline anything to reach green. The affected-set pin is the
  kernel's own measurement and stays exactly as `kernel-p5-dirty-set-instrument`
  wrote it.
- It does not park a permanently-red check in a per-push gate. The half that is
  deterministic and portable runs on every push; the half that is
  host-dependent runs in the milestone profile and says so.

## 4. The gates

| check | enforces | determinism | profile |
| --- | --- | --- | --- |
| `motion-md-affected-set-budget` | §2.2 classification, the scalar ≤64 for `point-patch`, §2.3's sound/tight/parametric symbolic bounds, §2.4's anti-escape rule, §2.5's customer coverage, and fail-closed on any unclassified or vanished binding | deterministic; reads the committed instrument pin, no build | `governance` (and `governance-fast` by the ≤60 s membership rule), `motion`, `motion-md` |
| `motion-md-relayout-timing-budget` | the ≤1 ms patch→receipt claim, live, release-built | host-dependent | `motion-md` only — deliberately **not** `governance` |

The timing gate is registered honestly rather than flatteringly: its notes record
that at n = 1000 the margin is 3–4× and it does not discriminate on k until
`issues/20260826-ws-h-patch-to-receipt-cost-flat-in-k.md` is fixed. It is a
regression bound on layout cost, not a proof of proportionality, and calling it
the latter would be exactly the LLP 0486 failure mode M-D exists to refuse.

Both land with a planted-defect run per RFC 0496 §4.4 — see §5 of this document.

## 5. Planted-defect proof (RFC 0496 §4.4, run 2026-08-26 before landing)

Recorded in full in the registry notes of the three checks. Fifteen defects were
planted — in the kernel, in the phase-5 case harness, in the sweep, in the pinned
fixture, in the sweep pin and in the classification manifest — each proven red,
and every check proven green on the unmodified tree.

Two are worth naming here because they are the ones that establish the gate is
anchored to behaviour rather than to JSON:

- A kernel over-invalidation (`last_layout_frames.clear()` inside
  `Kernel::set_style`) reddens four point-patch bindings **through** a
  `--write-expectations` re-pin that the upstream instrument accepts. **You
  cannot re-pin your way past this gate.**
- Making `ReorderOp::Reverse` under-report `movedRows` drifts the sweep pin red;
  re-pinning past *that* turns the bound **unsound** at every reversal point.

## 6. What review changed

Both families returned **NOT READY** on the first revision of the parametric
bound, and they were right. Recorded because the corrections are the substance:

- Both independently found the **flex-wrap unsoundness**; one produced a
  1025-vs-24 case on a 128-item chip row. The bound gained a measured domain.
- One found that the sweep-point spread put the **measured `affectedSetSize` into
  the bound's own namespace**, so a bound could read the answer it claimed to
  predict. The evaluator now allowlists structural parameters.
- One found the pinned instance's `perRow` was a **free variable** — a regressed
  `k` could be cleared by fitting it. It is now derived from the fixture.
- One found `maxSlackNodes: "16"` (a string) **silently disabled** the tightness
  rule. Class-schema types are now validated fail-closed.
- One found the exclusion class was a **24-character escape hatch**. A named M-D
  customer can no longer be classified into it.
- One found the original 36-point family was a **tautology**: in a fixed-height
  non-wrapping column the identity cannot fail. The family now spans odd
  cardinalities, heterogeneous extents, nested containers and non-contiguous
  permutations, and carries counterexamples outside its own domain.
- One found **dense grid packing is the safer flow**, inverting the assumption a
  reader would have made.

### 6.1 Four general shapes worth carrying past this lane

Three of these nearly shipped. Each is a *class* of failure, not a detail of
this bound:

1. **A bound whose namespace admits the measurement it bounds.**
   `affectedSetSize + ε × movedRows` passed sound, attained *and* parametric
   while predicting nothing — the purest form of a gate that cannot fail. Cure:
   allowlist structural parameters only; a validator must never be able to read
   its own answer key.
2. **A wrong-typed constraint that defaults to OFF.** `maxSlackNodes: "16"` as a
   string made `Number.isFinite` false and silently disabled the tightness rule.
   Cure: validate constraint field types fail-closed — a malformed safeguard is
   a red, never a no-op.
3. **A family that cannot disagree.** The original 36-point sweep was one bit
   restated 36 times, in a regime where the identity `k = movedRows × perRow`
   holds by construction, across only 27 distinct coordinates. Cure: a family
   must contain regimes capable of falsifying the claim — which is why this one
   now carries its own counterexamples.
4. **A constant silently fitted by the check that validates it.** `base = 8` was
   "declared, not fitted" — but the tightness cap it was measured against made
   slack at every point exactly `base`, so the data could not contradict it. Cure:
   a constant the check derives from the data it validates is not evidence;
   measure it in a regime that can move it (here, a nested container), or set it
   to the measured value.

## 6. What would overturn this

- A measurement showing `reorder`'s affected set bounded independently of
  collection cardinality on some tree shape. (Nobody expects this; it would mean
  the reorder is not relocating siblings.)
- An author ruling that M-D's four customers must each meet a scalar bound, in
  which case `reorder` becomes a declared exclusion from M-D with its own
  execution path — defensible, but it costs one of the four customers, and §4.4
  would then need its symbolic-bound sentence retracted.
- WS-H landing k-proportional work, after which the ≤1 ms gate becomes
  load-bearing and §1.2's caveat is deleted rather than carried.
- A derived bound family for line-broken containers, which would close
  `issues/20260826-md-reorder-bound-undefined-for-wrapping-collections.md`
  and shrink §2.3.1's domain restriction rather than leaving it standing.
