## Summary

EXFF made the first *paint* JS-free; this RFC makes the first
*interactions* JS-free — for the manifest's `plan-pure` class. The
boot artifact carries the route's plan; the native **Rust plan
engine** (which owns cells, scheduling, tree, and host-ops
permanently — before, during, and after Hermes exists) evaluates it,
presents, and services plan-pure actions live. Hermes boots
concurrently; its readiness **admits a PHI provider** through the
0514 M1 seam — typed calls, outcomes, capabilities, and reactive
publications cross; ownership never does. A JS-requiring handler
fired pre-activation gets the **declared pending affordance**
(disabled/busy, tree-visible, never a silent drop or sync wait);
routes may opt down to route-ineligibility. For plan-pure first screens the `evaluation` slice becomes plan-eval
(**≤20 ms provisional**, including tree build and layout per the
parent §4 path rule); commit→present stays its own slice at the
parent cap — and R3's interactive envelope stops depending on JS at
all.

## Prerequisites (explicit; r1 understated them)

1. The 0413.001 composition driver landed (in flight).
2. **Generic route Plan production and admission** — the landed dev
   projection is fixture-specific; the runner cutover gates are
   unpassed. This RFC does not start until producing/admitting a plan
   payload for an arbitrary route is real.
3. The **activation classifier** — a fail-closed **total pre-provider
   execution-closure certificate** via 0485's
   `PlanAdmissionCertificate` lineage: handler purity is necessary,
   not sufficient — derives, cells, resources, tasks, lifecycle code,
   theme/reactive reads, and capability routes that execute before
   provider activation are ALL in the certificate's domain
   (unclassifiable ⇒ JS-requiring). Lands as part of the parent §6
   manifest.
4. Native Plan lowering/admission for the payload row family
   (lockstep amendment — shape owner-confirmed).
5. **A commissioned two-stage EPPM/PHI amendment** — the landed 0514
   boot ABI requires provider callbacks and the ready registry BEFORE
   `cn_host_boot_plan`, so delayed admission as such contradicts it.
   The amendment pre-admits **dormant provider identities** (ABI
   satisfied), proves boot cannot reach them, then **atomically
   activates** them at Hermes readiness with generation fencing and
   receipts.

This RFC **discharges LLP 0307 §14's plan-runner generation join** —
the reserved successor slot — rather than creating a parallel one.

## Design sketch

1. **Boot:** host boot → admission (composition + plan payload +
   dormant provider identities — **admission** is the dormant
   identity/certificate stage) → plan engine evaluates → present →
   live for `plan-pure` → Hermes readiness **activates** the
   pre-admitted provider (activation is the Hermes-readiness stage;
   the two words are reserved per the two-stage amendment) →
   JS-requiring handlers arm.
2. **Pre-attach policy (decided):** default disabled/busy pending
   affordance with the declared visual state; per-route
   opt-down to ineligibility (the route then boots on the existing
   path); capture-and-replay rejected v1.
3. **Consistency law:** 0307 §13 extends — the enumerated allowed
   difference pre-admission is *pending JS-requiring effects*,
   nothing else; the affordance state is tree-visible (LLP 0560).
4. **Budgets:** plan-eval slice ≤20 ms provisional pending M0; the
   fail-loud report's boot-mode field says which path ran.
