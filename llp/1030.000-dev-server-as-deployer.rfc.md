## Summary

Charlie's questions, 2026-09-03, after LLP 1030: *"How should we
implement this? A vite server for bundling stuff and orchestrating all
these things? I want the one URL for every platform that you can just
load. That seems like it dovetails with this. Maybe the dev server
should even trigger a build and deployment for native apps so that's
not a second thing you need to do? Is that crazy?"* And: *"we should
give people options for how they want to deploy. Default should be ~
continuous deployment across all platforms simultaneously, but we'll
have to consider stuff like how updates won't reach all app users
instantly … esp if the developer chooses to use stripped down binaries
… Or stuff embedded in brownfield apps … sometimes people might just
prefer to deploy to diff platforms manually or on some schedule. We
need to support all flavors of this."*

The answers, as revised by the panel:

- **Not Vite. `dev.mjs` is the one dev server, and it classifies on
  every edit** (D1, D5). Rolldown, ruled in LLP 1027, is the bundler,
  as a library inside the bake. The app is a plan, a wasm, bytecode,
  and files; the loop that moves them is `{seq}` over SSE, which
  exists; and the thing the dev server adds is the classifier's table
  printed on each save — "this icon edit is live on the web and a
  binary on iOS" — before anyone deploys anything.
- **One URL is the app on every platform, with its dev and production
  truths kept apart** (D2). In production the HTTPS origin is the web
  app, the update manifest per stream, and the deep-link authority,
  and a phone opens the native app from it because the app's binary
  claims the domain. In development a LAN URL is typed or scanned into
  a dev client or the launcher; no universal link is claimed there,
  because none can be.
- **`exact deploy` is one verb in a separate process** (D3, D5). It
  bakes, classifies per platform and stream, prints the table, and —
  with `--yes` and by policy — publishes bundles to the origin. It
  shares one library with `dev.mjs` and holds credentials the dev
  server never sees. Building and submitting binaries from the same
  verb is not crazy — 1026 D13 already said an update is bake plus an
  upload, a thing an agent can do — but it is four distribution lanes
  that the current `build.mjs` is not, and it is deferred to a later
  number with the landing affordance, reach, and brownfield (§6).
- **Policies cover every flavor** (D4): continuous everywhere is the
  default — **ruled 2026-09-03** — for the origin, the bundle, and the
  binaries alike, with the store's own phased rollout as the default
  brake where a store offers one; the panel's case for holding store
  binaries at `internal` is recorded beside the ruling (§5 Q1). Manual,
  scheduled, per-platform,
  channels by origin, `L = 0` for the stripped build, and the
  brownfield host are settings, not modes.
- **The users a change has not reached** are 1030 D5's model with
  tooling stated at its real strength (D6): the `delivery` resource
  and two commands, background refresh as host metadata, the sunset
  card as a file.

## 1. Design

### D1 — Not Vite: `dev.mjs` is the server, Rolldown is the bundler, the deck is where a Vite app lives

Vite is a dev server for browser JavaScript applications: it serves
ESM on demand, transforms per module, and hot-replaces modules in a
running page. None of that is the shape of an exact2 app. The web
host is a wasm plus a fixed `glue.js` (LLP 1007) and, since LLP 1027
D6, one JavaScript file for the app's logic; a change to that file is
a module change — a restart with carry, not a module hot-swap (1026
D4; `rules/NOT-DOING.md` §Runtime: no hot revision surfaces). The
loop that already moves all of this is `dev.mjs`: watch, compile,
bake, serve `dist/` and the envelope, push `{seq}` and `{rebuilt}`
over SSE. It is the orchestrator of the dev loop today; this document
grows it, it does not replace it.

What Rolldown does, it does inside the bake (1027 §10 Q1, ruled).
Vite 7 is Rolldown underneath, so nothing is lost by using the engine
and not the server.

Where a Vite app legitimately lives: a **deck** (LLP 1020) — the
developer's own web content in a webview, served from a URL on the
same origin, updated by a page load. exact2 serves its URL and knows
nothing of its toolchain.

### D2 — One URL, two truths: production and development

LLP 1023 D1 stands: for an app URL `U`, a browser gets the web app and
an exact client gets the envelope, by `Accept`. The panel corrected
r1's claim that a landing affordance makes the dev and production
cases one mechanism. They are two, and each is honest:

- **Production.** `U` is an HTTPS origin baked into the binary (1026
  D12). It serves the web app at the root, the update manifest per
  stream at `U/.exact/<compatibilityId>/exact.json` (1030 D3a — a
  static host cannot pick a cohort's manifest without a distinct
  path), and `/.well-known/apple-app-site-association` and
  `assetlinks.json` generated by bake from the manifest's bundle ids,
  team, and signing certificates (for Android, the Play App Signing
  certificate, not the upload key). The app's own binary carries the
  associated-domains entitlement for `U` (host metadata, a binary);
  Apple's CDN fetches the association file over HTTPS with no
  redirects and caches it on the order of a day; a link tapped from
  another app, or a cross-domain link in Safari, opens the native app.
  Same-domain navigation and a typed or pasted `U` usually stay in
  Safari — a Smart App Banner on the web page is the honest affordance
  there. Adding or removing a domain is expansion before
  contraction (1030 D5). **The URL is the app**, 1023's sentence, for
  the web, the manifest, and the deep link alike.
- **Development.** `dev.mjs` is HTTP on the LAN (`dev.mjs:38, 223–
  234`). Apple will not fetch an association file from it and no
  universal link exists. The phone's way in is a typed or scanned URL
  into the app's dev client or the launcher (1023 Stage 3, 1026 D8),
  which fetches the envelope by `Accept` and subscribes. No landing
  affordance is claimed, and none is needed: the developer controls
  both ends.
- **The launcher's own domain**, if it ever ships broadly, is a third
  case: a generic launcher cannot claim arbitrary customer domains
  because its entitlement is signed into its binary; it would own one
  exact-controlled link domain that maps to app URLs. Deferred with
  the launcher (§6).

### D3 — `exact deploy`: bake, classify, print, then publish bundles

`exact deploy` is a script beside `scripts/app.mjs`, resolving the app
the same way, sharing its library with `dev.mjs`, and running as its
own process. In order:

1. **Snapshot.** Deploy from an immutable source snapshot — a commit
   or tree — into a run-specific staging directory, never from the
   editor's mutable working state and never from the dev server's
   shared `dist/` (`dev.mjs:39–45`), which a later save can overwrite
   mid-publish. A dry run and its `--yes` are the same snapshot, or
   the second refuses.
2. **Bake everything** — the plan, the bytecode, the modules and their
   per-target artifacts, the assets, the association files, the host
   files from the manifest, the build receipt — and compute every
   digest (1030 D1).
3. **Classify** (1030 D3): for each platform, the origin row, a row
   per live stream with the snapshot checked against that cohort's
   compatibility id, and the binary row. The output is a table the
   developer reads:

   ```
   release r-2026-09-03-14 · snapshot 7f3a…
   origin          web app, favicon, AASA        → publish (atomic web root)
   ios  stream a1b2 (L=A, E={hermes})
        plan, board.hbc                          → bundle seq 44
        aurora.wgsl (interface unchanged)        → bundle seq 44 (asset; interface digest unchanged)
        icon                                     → binary
        data/ (Rust, not opted in)               → binary; the snapshot's plan needs no new source → bundle still publishable
   macos stream c9d0 (L=A, E={hermes})            → bundle seq 44
   linux stream e1f2 (L=0)                        → binary only
   binary needed: ios, macos, linux — a later verb (§6); this run publishes the origin and two bundles
   ```

4. **Dry-run is the default.** The table is the output; `--yes`
   executes what the policy allows; `--only bundle`, `--only origin`,
   and `--platform ios` narrow it, and `--only bundle` refuses a
   stream whose snapshot did not pass its cohort's check.
5. **Publish** through an **origin adapter** with the properties the
   panel named: content-addressed files first (assets, modules,
   bytecode, plan, each under its digest, `Cache-Control: immutable`),
   then the signed per-stream `exact.json` (`no-store`) written with a
   conditional put — compare-and-swap on the previous head — so two
   publishers cannot interleave, and `seq` per stream is allocated by
   reading that head, never from a local file. The web app publishes
   the same way: a complete immutable release first and one atomic root
   pointer last, well-known files `no-store`. A client fetching mid-publish sees either the old
   head, whose files are all present, or the new one, whose files are
   all present — provided the blobs are reachable where the head is:
   the publisher reads every blob back from the origin before writing
   the head, and a client that still misses a blob at a lagging CDN
   edge keeps its last good head and retries, which is 1023 D3's
   whole-or-absent rule on the client side. A failed step leaves the
   previous head in place; there is nothing to roll back because
   nothing was replaced.
6. **Record.** The origin **is** the ledger: the last published
   snapshot for a stream is that stream's head, read back over HTTPS
   by the next classify. There is no committed `deploy.lock`. Not
   because a lockfile is a generated file — `Cargo.lock` is committed
   — but because a file every deploy rewrites merge-conflicts across
   worktrees, cannot allocate a monotonic `seq` across two machines,
   and drifts from the origin, which then lies to the classifier. The
   release id and the receipts are written beside the published files
   as immutable records.

Signing uses the private key named by reference in the manifest (D8)
and held where D8 says; the binary holds only verification keys (1030
D1).

**Web-root implementation (Codex, 2026-09-04).** The supported writable
origin is a directory served with `bun host/web/serve.mjs --origin <dir>`
(or that same HTTP handler behind TLS). Copying the directory to an arbitrary
static host is not a supported publication: it would omit the pointer routing
and cache policy. No generated server configuration is assumed.

A bake's complete public inventory, original digests, and encoding version name
`.exact/root/web/releases/<sha256>/` (below the non-cohort `root/web` pointer
directory, so a native channel named `web` cannot collide). Every payload is
immutable, including the index and
native envelope. The publisher reads each uploaded file back before committing
`.exact/root/web/exact.json` through the same held lock/conditional head operation
as native streams. This pointer carries the full inventory and payload digests.
It is the only mutable web publication state. Classification compares the entire
inventory, including removals; even a matching old fixed-file root needs a first
atomic publication. Corrupt existing immutable bytes refuse replacement.

The server reads one pointer for a canonical response. The selected index gives
all relative browser URLs its immutable base; the native envelope's plan/asset
cards name immutable paths directly. Exact binds its own absolute local
`/assets`, `/deck`, and `/shaders` references to that base, including image, font,
and iframe sources. GPU imports and shader requests stay beside their immutable
module. Ordinary network/data requests retain their authored meaning. Authored
deck HTML is opaque: its relative subresources stay in its release; explicit
absolute URLs inside it retain web semantics and may intentionally read mutable
external or canonical resources. The publisher does not rewrite user HTML/JS.

Canonical aliases are conveniences, never URLs in the generated live graph.
Names omitted from the current inventory return a no-store 404, including AASA,
even if older fixed files remain on disk. Previous immutable paths are retained
for readers who already opened that release; no garbage collector is introduced.
Payload URLs receive `public, max-age=31536000, immutable`; canonical responses,
404s, well-known routes, and mutable pointers receive `no-store`. The browser and
native Accept variants use `Vary: Accept`, and AASA is served without a redirect.
Failure injection before and after every payload/pointer write, concurrent HTTP
graph readers, removed assets/AASA, and a real deployed Caltrain browser/deck
drive verify this transaction rather than treating index-last as sufficient.

### D4 — Policies: one configuration, every flavor

The deploy configuration is the `[deploy]` section of the app manifest
(1030 D2 — policy, not identity). Every flavor Charlie named is a
value, not a mode:

| Knob | Values | Default |
|---|---|---|
| `origin` | `continuous` · `manual` · `{ schedule }` | `continuous` |
| `bundles` | `continuous` · `manual` · `{ schedule }` | `continuous` |
| `binaries.<platform>` | `continuous` · `manual` · `{ schedule }` · `off` — acted on by the binary verb of §6 | `continuous` |
| `release.<platform>` | `automatic` (release on approval) · `internal` (TestFlight internal testers, a package feed) · `manual` (submit, a human promotes) | `automatic` — **ruled 2026-09-03: continuous everywhere**; the panel's case for `internal` is §5 Q1 |
| `release.<platform>.phased` | `true` — use the store's phased rollout (App Store: 1 % → 100 % over seven days, pausable; Play: staged rollout by percentage) · `false` | `true` where the store offers it |
| `store.<platform>` | `L = 0` · `L = A` (1030 D4) | `A`; `0` never by default |
| `streams` | the live list, each `(channel, compatibilityId)`; retire by deleting a line | the current cohort per channel |
| `channels` | named origins or prefixes — `dev`, `beta`, `prod` — a binary bakes one in | one |
| `activate` | `next-launch` · `app-decides` | `next-launch` |
| `check.background` | `true` — **host metadata**: sets the background mode and task identifier in the binary (1030 D5) | `true` on iOS |
| `sunset.<stream>` | `{ message, store }` | none |
| `brownfield` | `true` — bundles only, against a host descriptor (§6) | `false` |

**Continuous, all platforms, simultaneously — the default, honestly
stated.** One `exact deploy --yes` (from a machine that is always on,
a scheduled routine, or a developer's terminal) publishes one release
to the origin and to every live stream whose cohort check passed *in
one run* — the web and every native cohort see the same release id.
"Simultaneous" is true of the publish and false of the arrival: the
web is a fresh load away, the bundle is next launch, and the tail is
1030 D5's. Where a change needs a binary the table says so, and the
binary lanes (§6) act on `binaries.<platform>` and `release.<platform>`
when they exist.

**What makes continuous-to-production sane**, since the panel argued
against it (§5 Q1): a binary is submitted only from a snapshot whose
five checks and fleet smoke are green on every host; the store's
**phased rollout** is on by default, so a released binary reaches a
few percent of automatic-update users first and one call pauses it;
a bad binary whose fault is in a bundle layer is fixed by the next
bundle in minutes, and one whose fault is native is a new submission
with an expedited-review request, which is the same recovery a manual
release would have had; and the first submission of a new app or a
new version still stops on what the console wants from a human —
export compliance, privacy answers, agreements — and the table says
so rather than pretending it went through.

**Manual** is `exact deploy` with the table and `--yes`. **Scheduled**
is a routine that runs it (cron, CI, a `/schedule` agent) with the
policy deciding what it may do unattended — the common shape is
`bundles: continuous, binaries: { schedule: weekly }, release:
internal`. **Per platform** is each platform's own row. **A channel**
is an origin or a prefix; the TestFlight binary bakes in `beta`, the
store binary bakes in `prod`, and promotion is a **new signed head
for the destination stream** — `seq` is signed per stream (1026 D11),
so files are not copied between channels, they are re-published there
by the same verb — no per-user targeting, no service. **The stripped
binary** is `store: 0` for that platform, and the classifier reports
every change to it as a binary. **The brownfield app** is §6.

### D5 — The dev server classifies; a separate process publishes

"Maybe the dev server should even trigger a build and deployment for
native apps so that's not a second thing you need to do? Is that
crazy?" The panel's answer, which this document adopts: **one verb is
not crazy; one process is.** The pieces of a native lane exist as
scripts an agent runs — `host/apple/build.mjs` builds, signs with the
development identity it finds, writes `Info.plist` and entitlements,
installs on a simulator or a phone; the fleet builds Linux (LLP 1015);
1026 D13 hosts `dev.mjs` behind a proxy. What is missing is real
distribution — four lanes, each a different signing identity, profile,
entitlement set, and upload (§6) — and the policy that decides when a
lane runs.

What lands here:

1. **`dev.mjs` prints the classifier's table on every edit** — the
   conservative path form immediately, the exact form after producers
   finish (1030 D3). This is the gift Charlie asked for: while
   editing, the developer learns that the icon they just changed is a
   binary on iOS and live on the web. `dev.mjs` never publishes and
   never holds a credential; it is a LAN-facing process bound to
   `0.0.0.0` (`dev.mjs:38`) and stays one.
   *Implemented 2026-09-05: the build receipt is the sole compatibility
   authority. Dev imports the same artifact comparison as deploy; the
   resident compiler updates the candidate plan graph, and complete static
   generations supply asset digests and reflected shader interfaces.
   Native targets retain their last actual receipt. Compiler input changes
   are reported as pending until rebuilt; absent targets are unbuilt,
   never assigned guessed compatibility ids. Binary and bundle results
   are independent. See 1030 D3 for the conservative prior-demand scope.*
2. **`exact deploy --watch`** is the continuous publisher: a separate,
   least-privileged process that watches the deploy branch (or the
   local commits, for a laptop), snapshots, bakes, classifies, and
   publishes what the policy allows. Same library, different process,
   different credentials, an immutable snapshot per run. A
   notarization that takes minutes (§6, later) can never take down
   `{seq}`, and a 200 ms debounce (`dev.mjs:117`) can never publish
   half an edit.
3. **One code path.** The terminal, `--watch`, and a scheduled routine
   call the same library; there is no "CI mode." What CI adds is a
   machine that is always on and a place credentials can live.
4. **Everything is in `logs`** — the table, what was published, the
   heads before and after — and a failed step leaves the previous head
   in place (D3).

### D6 — Propagation tooling, at its real strength

- **The `delivery` resource and its two commands** (1030 D7): the app
  reads that an update is staged and activates it when it chooses; the
  agent's `state.delivery` mirrors it, and `scripts/smoke.mjs` asserts
  it.
- **Background check** is host metadata (D4 `check.background`):
  `BGAppRefreshTask` on iOS, opportunistic and quota-limited; a timer
  while the app runs on desktop. It stages; it never activates.
- **`check now`** is a host call the app's native side or a brownfield
  host may make; a developer's own push is a nudge to it. exact2 sends
  no pushes and relays none.
- **The sunset card** is published into a stream's head by `exact
  deploy` when the configuration names it; an advisory retirement
  notice, reaching only clients that still check and contain the
  reader.

### D7 — Where things live

- **The app manifest** (1030 D2) is one JSON file at the app's root
  beside `app.contract` and `Cargo.toml` — `app.json` for this text —
  and it is a **superset of the W3C Web App Manifest**: the web's own
  names for exactly this metadata (`name`, `short_name`, `icons`,
  `display`, `theme_color`, `background_color`, `start_url`, `id`),
  which the web host emits as `manifest.json` by copying, extended
  with typed top-level keys: `app` for identity and the origin;
  `host.ios`, `host.macos`, `host.linux`, `host.web` for 1030 D1's
  host-metadata row; `deploy` for policy (D4). Bake generates every
  platform file from the first two; nothing generated is committed;
  a JSON Schema validates it at bake and in the editor. The `app` key
  is the one source of the bundle id and the app id that `build.mjs:
  48–49` and `scripts/app.mjs:24–27` derive separately today. Why
  JSON and not TOML (r1's reflex, `Cargo.toml` being next door): the
  web is the standard and its manifest is JSON; the repo's one
  declaration authority (`kernel/tables/schema.json`), `format.json`,
  and the envelope are JSON; both the Rust bake and the Node scripts
  parse it with no dependency; and agents write it with fewer
  mistakes than TOML's arrays of tables. The one loss is comments;
  the manifest stays small and its reference is this document.
- **The build receipt** (1030 D2) is written by whatever produced a
  binary — today `build.mjs` — beside it: toolchain, SDK, profile,
  identity, entitlements as signed, the compatibility id. Not
  committed; published with the binary's records.
- **Secrets** — the bundle signing key, and later the App Store
  Connect and notarization credentials — live in the publisher's
  keychain on a developer's Mac and in a least-privilege secret store
  for the cloud (1026 D13's key custody), named in `[deploy]` by
  reference, never by value, and never readable by `dev.mjs`. One
  custody system, separate credentials per purpose, and signing done by
  an isolated signer the publisher calls — the LAN process never signs
  and never uploads; `exact deploy` refuses a step whose secret it
  cannot find and says which.
- **The origin** is any static host with a conditional-put primitive
  behind the adapter (S3-style object stores have one; a plain
  directory does, with a lock file, for one writer). The dev server in
  dev; the cloud in 1026 D13's shape. Per-stream directories under
  `.exact/`, well-known at the root, the web app at the root.

## 2. Costs and budgets

- **The dev loop.** The exact comparison follows the producers. Pending
  native input hashes are refreshed outside the resident plan-edit path;
  each candidate uses the compiler graph and complete static inventory. The asset row adds a fetch by digest on native, the size of
  the asset. The 100 ms edit-to-present budget is untouched
  (`rules/RULES.md` §Time budgets); nothing this document adds blocks
  the loop.
- **A deploy.** Bake (seconds), the upload (seconds), a conditional
  put per stream. Not on any budget; printed.
- **Checks.** None added. `scripts/smoke.mjs` gains one drive: edit an
  image, `{seq}`, the native client shows it; and one read:
  `state.delivery` on four hosts.

## 3. What this refuses

- **A service.** No per-user targeting, no cohorts by identity, no
  update console, no analytics beyond a log the developer owns
  (1026 §7, `rules/NOT-DOING.md`). Channels are directories.
- **Vite as the server** (D1). The deck is where it lives.
- **The dev server as a publisher** or a credential holder (D5).
- **A committed ledger** (D3).
- **Copying a signed head between channels** (D4).
- **Push delivery** (D6).
- **Pretending the LAN URL is a universal link** (D2), or that a
  platform can take a change live when it cannot (1030 D10).

## 4. Staging

Each stage is verified by driving an app with the agent API and
reading `state`; an implementer and a date are owed before any is a
spec. In dependency order:

1. **The asset row, with shaders packaged** (1030 D10, D8; 1023 D4's
   owed slice). `{seq}` names changed asset digests; the native hosts
   fetch by digest, cache, and re-render; fonts re-register. The
   shader packaging is in this stage (ruled 2026-09-03): `SOURCE`
   leaves the generated Rust, the GPU crate loads WGSL by digest at
   `bind` and swaps in a candidate pipeline only if it validates, the
   reflection stays and now emits the interface digest (generated
   interface minus source, plus overrides, fragment outputs, device
   features). Verified: edit `caltrain.png`, the macOS and iOS dev
   clients repaint in one `{seq}`; the web page the same; edit
   `aurora.wgsl`'s color, the surface shows it in one `{seq}` on the
   web, macOS, and iOS; edit its bindings, every client says "rebuild
   the native host"; the compatible-and-incompatible shader fixture
   passes on the browser, Metal, and Vulkan.
   **Landed 2026-09-04.** `dev.mjs` watches `assets/`, `deck/`, and
   `gpu/shaders/`, mirrors them into `dist/` at startup, and on an edit
   copies the file, digests it, classifies a `.wgsl` by its interface
   digest (`exact-gpu-reflect digest`), and pushes `{seq, digest,
   assets: [{name, sha256, bytes, interface?}]}` with a carrier line per
   row; the page refreshes what referenced it by name (an `img`
   re-fetches and the refresh completes at decode, a shader goes to the
   GPU module, a deck frame reloads, a font restarts from the current
   plan); `ExactApp` fetches each row over the `PlanURL` connection,
   verifies the digest, and hands it to every session, which repaints
   an image and registers a shader — swapped in when its interface is
   the binary's, refused by name otherwise. Verified by driving
   (`scripts/agent.mjs` over a dev server, the web page and the macOS
   app connected to it): `caltrain.png` inverted — both repaint in one
   `{seq}`; `glass.wgsl`'s sky turned red — the page and the Metal
   layer show it in one `{seq}` (about four fifths of the pixels on
   each); a binding added to `glass.wgsl` — macOS refuses by name with

## 7. Exact2 Go and custom development clients — implementation direction

**Added:** 2026-09-06, Codex, from Charlie's request to capture the
Exact2 Go discussion and start building. This section is a proposed
implementation sequence within this Draft; it does not mark the broader
RFC accepted. The first slice below has an implementer and a date.

### The experience

Start development locally or in a cloud workspace and receive one app
URL. A browser opens the website. A native client opens that same address
through D2's envelope discovery and follows development changes. The web
page should eventually offer explicit actions to open an installed client
or install a compatible one, with build progress when necessary. The URL
identifies the app; the opening action selects the client.

Two native products share that loader:

- **Exact2 Go:** a generic client with a declared set of standard native
  capabilities and executors. First target: Contract, TypeScript logic,
  and assets. A new app need not have been compiled into Go. Apps get
  separate storage and admitted capabilities (1026 D5); knowing an app id
  confers no access to another app's secrets. Runtime/bytecode compatibility
  is checked before replacement. A missing capability or incompatible
  runtime offers the custom-client path and explains the requirement.
- **Custom development client:** an app's own runtime, native dependencies,
  name, icon, and entitlements, built for its platform. It follows the same
  app URL. Compatible plans, assets, and executable modules arrive through
  the loader; a native dependency, entitlement, or runtime change requires
  a new binary. Native Rust app logic remains binary-bound unless the app
  has an implemented portable executor for it (1029).

Neither product promises a standard API before its implementation exists.
Go's capability set is a published boundary, not "every basic app."

### Builders and opening links

The dev workflow requests builds from a configured executor: local,
an existing fleet machine, or a cloud provider. D5's process boundary
holds: the public artifact server does not acquire signing credentials.
The builder uses a captured source revision and the existing build receipt;
it reuses an artifact only when target, compiled inputs, native metadata,
and signing/distribution requirements match. A finished older request must
not be presented as the client for a newer incompatible revision.

The first remote builder should run the existing scripts on a fleet Mac.
EAS is a candidate adapter requiring an actual Rust/Swift packaging spike.
A remote workspace needs an HTTPS address reachable by each client, with
the envelope, assets, and event stream reachable under the same origin.
Authentication and reconnect behavior must be proved with that deployment.
The agent carrier remains private (1012); connecting a phone does not
expose its control API to the internet.

An arbitrary development URL is not automatically an OS deep link (D2).
The first entry is an explicit URL argument or the existing native dev
menu. Web opening actions and QR entry follow with the launcher. iOS
installation requires an appropriate signing/profile/distribution path;
direct macOS downloads require the packaging and signing work in §6.
