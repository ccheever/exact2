## Summary

Local notifications exist (`rules/DEFERRED.md`, 2026-10-04): Contract's
`showNotification(title=, body=, tag=, showTrigger=, navigate=)` and
`closeNotification(tag)` post through `UNUserNotificationCenter` on macOS
and iOS and through `new Notification` on the web, and a click opens the
`navigate=` route (LLP 1114.001 D1). The roster ranks "notifications,
completed" second in wave 1 (LLP 1133.000 §4). This RFC completes the
module and builds its first stage for the T3 Code clone, which today keeps
190 lines of its own Swift because the built module cannot do four things:

1. **Post without a sound.** The Apple host always sounds
   (`Notify.swift:54` sets `content.sound = .default`; `:139` presents with
   `.sound`). The clone's notification is the reference's
   `new Notification(title, { silent: true })`, and it plays its own sound.
2. **Deliver a click to an app with no router.** The click is delivered only
   as `navigate` to a navigation root, and the clone's window has none.
3. **Post from data code.** Whether a thread notifies is decided in the
   clone's TypeScript, and a host command cannot run there.
4. **Badge the app icon and read the permission.** Both are refused
   (`rules/DEFERRED.md:550-575`: "badges … and a readable permission fact").

What this RFC proposes:

- **`@exact/notifications`**, a standard-library package (LLP 1133 D5's
  default), into which `showNotification` and `closeNotification` move from
  `HOST_COMMANDS`. Its names, by the web's: `showNotification` with
  `silent=` and `data=` added, `closeNotification`, `setAppBadge` and
  `clearAppBadge` (the Badging API), the permission fact
  `notificationStatus()`, the request `requestNotificationPermission()`,
  and the event `notificationclick`.
- **A click without `navigate=`** is a `notificationclick` event, carrying
  the notification's tag and `data`, delivered in order and once to the
  handler on the app's root node, held across a cold launch on macOS and
  iOS (on the web a notification lives as long as its page).
- **Data code calls every send** through the generated binding (LLP 1133
  D6): `await showNotification({ title, body, tag, silent: true })`.
- Three seam additions every later module can use: a **send that answers
  nothing** is a statement in an action, as a host command is today; a
  module may declare an **event**, the bounded and ordered delivery LLP 1133
  D6 rule 7 asks for, with an origin rule and a rule for delivery that
  starts the app; and the agent's substitute gains **declarative forms**
  for a keyed list, a value and per-name permission.
- Targets: **web, macOS, iOS** in stage 1. Actions and replies come in
  stage 2 (the Caltrain departure reminder's Snooze), Android and Windows in
  stage 3, each declared here (§8) and each ruled by its own amendment.

## 2. Tier 1

### D1 — The Notifications API's names, and the Badging API's

| Name | Kind | The web's | Deviation |
|---|---|---|---|
| `showNotification(title=, body=, tag=, silent=, data=, showTrigger=, navigate=)` | send, answers nothing; a request while `prompt` (Q4) | [`ServiceWorkerRegistration.showNotification(title, options)`](https://notifications.spec.whatwg.org/#dom-serviceworkerregistration-shownotification), `NotificationOptions` `body`, `tag`, `silent`, `data`, `navigate` | `title` is a keyword like the options (LLP 1133.002 D13); `data` is a string, not any structured-clonable value (a Contract value has no clone, and a string survives the platform's `userInfo` and a cold launch); `showTrigger` is the abandoned Notification Triggers draft's member, epoch milliseconds (built) |
| `closeNotification(tag=)` | send, answers nothing | `getNotifications({tag})`, then `close()` on each | one call by tag, shown or scheduled (built) |
| `setAppBadge(contents=)` | send, answers nothing | [`navigator.setAppBadge(contents)`](https://w3c.github.io/badging/#setappbadge-method), exposed to windows and workers | none |
| `clearAppBadge()` | send, answers nothing | [`navigator.clearAppBadge()`](https://w3c.github.io/badging/#clearappbadge-method) | none |
| `notificationStatus()` | live source, a fact | `Notification.permission`; `navigator.permissions.query({name: "notifications"})` | the module's permission fact in LLP 1133.002 D8's shape; the web's `default` reads `prompt` |
| `requestNotificationPermission()` | send, a request, answers `NotificationStatus` | `Notification.requestPermission()` | named for the module: imported names share the app's namespace (`contract-use-duplicate`), and a bare `requestPermission` would collide with the next module's |
| `notificationclick` | event (D6), on the app's root node | [`notificationclick`](https://notifications.spec.whatwg.org/#activating-a-notification), with `NotificationEvent`'s `notification.tag`, `notification.data` and `action` | delivered to the app's root, the one place every exact2 app has, where the web delivers it to the service worker's global scope or as `click` to the page's `Notification` object |

**`silent`.** The Notifications API's `silent` is a nullable boolean whose
default, null, leaves sound and vibration to the platform; true means none
([options](https://notifications.spec.whatwg.org/#dom-notificationoptions-silent)).
Measured 2026-10-21 in Chrome 155, Chromium 156, Firefox 157 and WebKit 27.2
(Playwright, macOS 26.6.2): each constructs `new Notification("t",
{silent: true, tag: "a"})` and reads back `silent` true.

**`setAppBadge(contents)`.** `contents` is an option of a non-negative
integer: absent sets a flag (a badge with no number), `0` clears, as the
Badging API's [`contents`](https://w3c.github.io/badging/#dfn-badge)
does. It converts as the spec's `[EnforceRange] unsigned long long` does
([Web IDL](https://webidl.spec.whatwg.org/#abstract-opdef-converttoint)):
NaN and the infinities refuse `TypeError`; otherwise the number is
truncated toward zero first (`2.9` is `2`, and `-0.5` is `0`, which
clears), and a result outside 0 to 2^53−1 refuses `TypeError`. The bake
applies the same conversion to a literal. **A badge is best effort,** as
the spec allows: the call resolves when the platform accepts it, and
whether a badge shows is the platform's (an installed web app or not, the
person's badge setting on iOS). The badge is the app's, not a session's:
an embedded host with two sessions shows the last value either set, as two
documents of one
web app share one badge.

**What a send answers.** `showNotification`, `closeNotification`,
`setAppBadge` and `clearAppBadge` answer nothing (D5). From data code each
is a Promise that settles when the platform accepts or refuses the call, as
the web's do, and rejects with the errors below. From Contract each is a
statement; a refusal is a journal line, as today
(`showNotification: refused: denied`).

**Errors,** by the web's names: `NotSupportedError` where the target has no
such capability (LLP 1133 D8; §8); `NotAllowedError` where the permission is denied
; `TypeError` for bad arguments, which
the bake refuses first wherever the value is literal.

### D4 — Access hatches

| Platform | Object | Moment | The module owns |
|---|---|---|---|
| Apple | `UNUserNotificationCenter.current()` | once, when the module is first used | the delegate, which is the host's (D7) |
| Apple | `UNMutableNotificationContent` | before each post | `title`, `body`, `userInfo["exact"]`, the request identifier, and `sound` when `silent=true` (nil, so a silent post stays silent); the app may set anything else: a named `sound` on a post that is not silent, attachments, `launchImageName`, and `categoryIdentifier` until stage 2 owns it |
| Apple | the foreground presentation of each notification | in `willPresent`, before the host completes | the host proposes `[.banner, .list]`, and `.sound` unless the post was silent; the app's hatch may return other options, and its answer is final (the author's native code wins, LLP 1115) |
| Apple | each response | in `didReceive`, after the host's own handling (D7) | the hatch observes it; the host calls the completion handler, once |
| Android (stage 3) | `Notification.Builder` | before each post | title, text, channel, content intent, tag |
| Windows (stage 3) | `AppNotificationBuilder` | before each post | text, audio, launch arguments |

**Completion is the host's.** Apple's delegate calls each take a completion
handler that must be called once, and `willPresent`'s argument decides the
presentation ([Apple](https://developer.apple.com/documentation/usernotifications/unusernotificationcenterdelegate/usernotificationcenter(_:willpresent:withcompletionhandler:))).
So the hatch is not a second delegate: it is a protocol the app's native
code implements, `NotificationHatch`, with
`willPresent(_ notification:, proposed:) -> UNNotificationPresentationOptions`
and `didReceive(_ response:)`, set once for the app (the centre is the
app's, not a session's). The host calls the first inside its own
`willPresent` and completes with the answer; it calls the second after
delivering the click, then completes. Neither can complete twice, and a
hatch that never answers cannot stall the system.

A development build compares what the module owns after the content hatch
with what it wrote and names a change in the journal (LLP 1133 D3). The web
has no hatch.

## 4. Seam additions

### D5 — A send that answers nothing is a statement

Today a module send needs a mutation, `send m = name(…)`, and the mutation
needs `as shape` what the send answers (`contract/cli/src/modules.rs:86-120`,
`contract-module-answers`). A notification answers nothing, and the built
command is a statement. So a declaration's send may say `"answers": null`,
and then:

- Contract calls it as a statement in an action, with keyword arguments:
  `showNotification(title="Build finished", tag=t.id, silent=true)`. The
  written form of today's command is unchanged; the app adds
  `use showNotification from "@exact/notifications"`.
- `send m = name(…)` to it is refused (`contract-module-answers`: it
  answers nothing), and a statement call to a send that answers something
  is refused (`contract-module-kind`: a mutation sends it).
- Its outcome is a journal line (`<name>: shown`, `refused: <reason>`).
  Data code's binding returns `Promise<void>`.

This amends LLP 1133.002 D13.

### D6 — A module may declare an event

LLP 1133 D6 rule 7: a value coalesces, so a module whose events must each
arrive declares a bounded event protocol. A click is such an event: two
clicks on two threads' notifications are two openings. The declaration:

```json
{ "event": "notificationclick", "on": "root", "raised": "activation",
  "args": ["string", "NotificationEvent"], "hold": 16 }
```

`NotificationEvent` is `{tag, data, title, body}`; stage 2 adds `action`
and `reply`.

- **Contract.** The app imports the event with its shape and handles it
  with an attribute on its root component's outermost node, as
  `navigate=` is written on a navigation root:
  `column notificationclick=opened …`, where `action opened(tag: string)`
  or `action opened(tag: string, e: NotificationEvent)`. A second handler
  in the app, or one on another node, is refused
  (`contract-event-root`). Like `key`'s optional `KeyboardEvent`
  (`docs/contract-grammar.md`, "Keys"), the second parameter is optional.
- **Order and count.** Each event is delivered once, in the order the
  platform reported them, each as its own commit. None is coalesced.
- **Origin.** An event's origin is not the module's to claim. The
  declaration says which platform callback raises it, and the origin
  follows LLP 1133.002 D12's causation rule from there:
  - a **platform activation**, a callback the platform makes only for a
    person's act on its own UI (Apple's `didReceive` with the default
    action, a browser's `click` on a notification, Android's content
    intent, Windows' `NotificationInvoked`), has a person's input as its
    origin. Only the host raises these (D7), so a package cannot mint one;
  - an event a package raises through `emit` has the device's origin: the
    least privileged, as a module's topic re-ask has (D12), so a request it
    leads to while `prompt` fails `person-required`.
  `notificationclick` is the first kind.
- **Held, and bounded.** An event that arrives before the session's first
  commit, or while the root's handler is not mounted, is held, up to
  `hold` (16 for this module), and delivered in order once the handler is
  mounted. Past the bound the oldest is dropped and journaled
  (`notificationclick: dropped (<tag>)`). An event no handler hears within
  the session's life is journaled when the session ends.
- **Launch.** An event that starts the app is held from launch, before the
  session boots (D7), and delivered after first pixel, never before it
  (`rules/RULES.md`, the boot path). This is the rule for cold-start
  delivery that LLP 1069.007's "Not in this RFC" waited for, and LLP
  1133.000 §4 asked notifications to propose: **an event the platform
  delivers to a closed app is held by the host from launch and delivered
  once, in order, after first pixel, to the handler the module's
  declaration names; it never runs app code before first pixel.**
- **Implementations** raise an event of the second kind through the module
  context, beside `changed`: `emit(name, args)`. The runner checks the
  arguments against the declaration, as it checks an answer.
- **An activation event is bound, not emitted.** For an event declared
  `"raised": "activation"`, the implementation never calls the event: it
  hands the host what the platform will call back, and the host listens.
  The module context offers, per platform:
  - **Apple:** `activation(name, args) -> [AnyHashable: Any]`, the
    `userInfo` entry the implementation puts on the content it posts. It
    names the session, process, event and arguments; ExactKit's delegate
    (D7) reads it in `didReceive` and raises the event. Content without it
    raises nothing.
  - **Web:** `activation(target, type, name, args)`: the host adds the
    listener to the object the implementation made (here, the
    `Notification`, type `click`), and raises the event only for an event
    whose [`isTrusted`](https://dom.spec.whatwg.org/#dom-event-istrusted)
    is true, so a script's synthetic `dispatchEvent` raises nothing.
  - **Android, Windows (stage 3):** a host-made `PendingIntent` and
    activation arguments, by the same pattern.
  The runner gives a person's origin only to an event that arrives through
  these. The external fixture of stage 0 declares an activation event of
  its own and is driven through the same calls, so a third party's module
  binds activations exactly as `@exact/notifications` does.
- **The agent** sees held and delivered events in `state.extensions`, and a
  drive raises one as §7 says.

This amends LLP 1133 D6 rule 7 and LLP 1069.007 ("Not in this RFC": lossless
events and cold-start delivery).

### D7 — The host keeps the one delegate; the click goes to the posting session

A platform has one notification delegate per process, and it must be set
before launch finishes to hear a click that starts the app
(`UNUserNotificationCenterDelegate`; LLP 1114.001 D1). A module instance is
made when its session boots, which is later. So the host keeps the
delegate, as it does today (`installNotificationClicks`, set in each
adapter's launch: `ExactMac/main.swift:550`, `ExactIOS/main.swift:182`),
and the module's implementation is handed the clicks:

- The Apple implementation puts `context.activation("notificationclick",
  [tag, event])` in `userInfo` (D6), with `silent` and `navigate` if given.
  The session's owner and process identities in it are those
  `Notify.swift:50-52` writes today.
- On a click (`UNNotificationDefaultActionIdentifier`), the host's delegate
  finds the session as it does now (`Notify.swift:98-126`). With
  `navigate`, it opens the location (launch location or warm `navigate`,
  unchanged) and no `notificationclick` is raised: the location already says
  where the click goes, and one click has one meaning. Without, it raises
  `notificationclick` with the tag and `data` on that session, held per D6
  if the session has not booted. A notification posted by a previous
  process goes to the session with its label, else the first live one, as
  today.
- On the web the implementation makes the `Notification` and calls
  `context.activation(notification, "click", "notificationclick", [tag,
  event])`; the host's listener focuses the window, then navigates or
  raises the event. A page's
  notification lives as long as its page
  ([lifetime](https://notifications.spec.whatwg.org/#lifetime)): a click
  after the page has closed does nothing, as LLP 1114.001 D1 already
  declares, and there is no launch on the web. A persistent notification
  needs a service worker, which the JS target does not have; it is the web
  cell's later step (§8).

So the delegate stays in ExactKit, and the package reaches it only through
the context's `activation`.

## 6. Permission

LLP 1133.002 §4's stages, for this module.

**Declare.** The grant is built: `device.notifications <strings key>`
(`runner/src/device.rs`). It derives nothing on Apple (the system prompt
has a fixed text, and no usage key exists) and on the web (no
`Permissions-Policy` feature governs notifications). Stage 3 adds the
Android column (`android.permission.POST_NOTIFICATIONS`) and nothing on
Windows. `setAppBadge` needs no grant of its own and never asks: iOS shows
a badge only under the `.badge` authorization the notification request
carries (D2), Safari's web apps only with notification permission, and
Chrome and macOS's Dock tile need none.

**Read.** `notificationStatus()` answers `{available, state, badge}` and
the platform's words (D3):

| Platform state | `state` |
|---|---|
| Apple `notDetermined` | `prompt` |
| Apple `authorized`, `provisional`, `ephemeral` | `granted` (`apple.authorizationStatus` names which) |
| Apple `denied` | `denied` |
| web `Notification.permission` `default` | `prompt` |
| web `granted`, `denied` | the same word |
| Android 13+ never asked, rejected once, revoked | `prompt`, as geolocation's history decides (LLP 1133.002 D8) |
| Android 13+ permanently denied, or `areNotificationsEnabled()` false after a grant | `denied` |
| Android below 13 | `granted`, or `denied` when `areNotificationsEnabled()` is false |
| Windows `Enabled` | `granted` |
| Windows `DisabledForApplication`, `DisabledForUser`, `DisabledByGroupPolicy`, `DisabledByManifest` | `denied` (Windows never prompts) |
| Windows `Unsupported` | `unknown`, and `available` false |
| the Notification portal | `unknown` (it has no query) |

`badge` is `true` where the target implements the badge call: Apple, the
web's `"setAppBadge" in navigator`; `false` on Android (no app badge) and
wherever the call is `NotSupportedError`. It says nothing of whether a
badge will show (D1, best effort); on iOS `apple.badgeSetting` says that. `available` is false where
the target has no implementation or no notification centre (macOS outside
an app bundle, `Notify.swift:76-85`).

The state changes by itself (the person turns notifications off in
Settings). Apple has no change callback, so the implementation reads
`getNotificationSettings` again when the app becomes active, and announces
a change. The web follows `PermissionStatus`'s `change` (all four engines
expose `onchange` on it, measured 2026-10-21; the probe did not change a
permission) and reads again on `visibilitychange`, as geolocation's does. Android reads again on `onResume`.

**No synchronous form.** Apple's `getNotificationSettings` answers only
asynchronously, so no target has a synchronous path for the status, and the
module declares no `sync` name (LLP 1133 D6 rule 4).

**Ask.** `requestNotificationPermission()` is a request (LLP 1069.007 D1):
Apple's `requestAuthorization(options:)` with D2's options; the web's
`Notification.requestPermission()`; Android 13+'s `requestPermissions`
for `POST_NOTIFICATIONS`; Windows answers the status at once. It answers
the new status. While `granted` or `denied` it asks nothing and answers the
status, as each platform does. Origins follow LLP 1133.002 D12: a tool
invocation's or a wake's request while `prompt` fails `NotAllowedError`,
reason `person-required`. Firefox and Safari ask only inside a user
activation, so on the web a request outside one is refused by the browser,
and the answer is the unchanged status.

**`showNotification` while `prompt`** asks first (Q4), as every host does
today: it is a request in that state, so a tool invocation's fails
`person-required` rather than prompt. While `denied` it refuses
`NotAllowedError`. The runner neither holds nor refuses `closeNotification`,
`setAppBadge` or `clearAppBadge` for permission; a platform's own refusal
still propagates (the Badging API lets a browser require permission, and
then both badge calls reject `NotAllowedError`,
[setting the badge](https://w3c.github.io/badging/#setting-the-application-badge);
WebKit accepts the call before display permission,
[WebKit](https://webkit.org/blog/13878/)). The web's `showNotification`
rejects `TypeError` unless permission is already granted; exact2 keeps today's behaviour,
which `new Notification` in a page approximates (it fires `error`), as a
declared deviation, so an app that posts on a person's press needs no
separate request.

**Explain and recover:** the app's own UI, and `openURL("app-settings:")`
(LLP 1133.002 D11), which on macOS opens Notifications settings for the app
here rather than Location Services.

## 7. The substitute

**Shape:** `notificationStatus` is a fact; `requestNotificationPermission`
is a request, and so is `showNotification` while `prompt`;
`closeNotification`, `setAppBadge` and `clearAppBadge` are effects with
nothing to answer.

- **The fact.** `state` is set by `prefer permission.notifications
  granted|denied|prompt` and `--permission notifications=…`, as
  geolocation's is. The default is `prompt`, `available` true, `badge`
  true.
- **Requests.** While `prompt`, a request from a foreground origin holds a
  `permission` ticket: `tap @t allow` sets `granted` and continues (a
  pending `showNotification` is then listed, and
  `requestNotificationPermission` answers the status); `deny` sets
  `denied`; `cancel` leaves `prompt`. A refused post is a journal line; the
  request answers the unchanged status.
- **Posts** are listed in `state.notifications`, never shown, as today,
  with `silent`, `data` and `delivered` added to each entry: `{title,
  body, tag, silent, data, showTrigger, navigate, delivered, ref}`. An
  entry with a `showTrigger` is `delivered: false` until the agent clock
  passes it (`clock +N`), as the system would show it then.
- **The badge** is `state.badge`: `null`, a number, or `"flag"`. It is the
  app's (D1), so the substitute keeps it where the host keeps app-wide
  state (ExactKit's `ExactApp`, the web page's runtime), not in a session's
  runner; every session's `state.badge` reads the one value. A drive on
  the sample host (`smoke.mjs host`) sets it in session `a` and clears it
  in session `b`.
- **A click** is `tap @<ref>` on a delivered entry: the existing
  operation on a new kind of target, so no operation is added (LLP 1133
  §7). It does what the platform's click would: opens `navigate`, or raises
  `notificationclick` with the tag and `data` as an activation (D6), and
  removes the entry. A tap on an entry not yet delivered is refused by
  name. A launching click is the launch flag `--notification '<json>'`,
  whose value is the whole listed entry (`{tag, data, title, body,
  navigate}`, as `state.notifications` printed it before the app quit),
  so a fresh runner needs nothing from the session that posted it; it
  goes to the first session, or the one `--session` names, and is held
  from boot as D6 says. Stage 1's drive posts, reads the entry, ends the
  app, and relaunches it with that entry.
  Today's way to check a `navigate` click, `type` into the navigation root
  (LLP 1114.001 D1), still works.
- **Disclosure:** the entries' title, body, tag and data, which are the
  app's own text. **Lifetime:** an entry lives until replaced by tag,
  closed, or tapped. **Production:** none of it.

**Declared, not built in.** As geolocation's is (LLP 1133.002 §6), all of
this is in `exact.json`, so a third party's notifications module could
declare the same. Geolocation's forms do not cover it (its `request` is
`always` or `when-prompt` for sources only, and a denied state refuses
every call, `runner/src/runner/modules.rs:303-327`), so the declaration
gains, for every module:

- per name, `"permission"`: `"asks"` (holds a ticket while `prompt`,
  refuses while `denied`: `showNotification`), `"request"` (asks while
  `prompt`, answers the status in every state:
  `requestNotificationPermission`), or `"none"` (never held or refused:
  `closeNotification`, `setAppBadge`, `clearAppBadge`);
- a keyed list in the agent's state: `"list": {"state": "notifications",
  "key": "tag"}` on a send adds an entry, replacing one with its key;
  `"unlist": "tag"` removes it; each entry carries a `ref`, and `"tap"`
  names the event a `tap @ref` raises (or the `navigate` field it opens)
  and retires the entry;
- a value in the agent's state: `"set": {"state": "badge", "scope":
  "app", "from": "contents", "absent": "flag", "zero": null}`, and `"set":
  {"state": "badge", "scope": "app", "value": null}` for `clearAppBadge`;
  `"scope": "app"` keeps the value in the host's app-wide state rather
  than the session's runner.

`runner/src/notify.rs`'s rule moves into these declarations, and stage 0
proves them with the seam test LLP 1133.001 D8 requires: a fixture module
outside the tree declares the same forms and answers a drive.

## 9. Push, designed here

The roster designs push registration in this RFC and builds it when an app
with a backend asks (LLP 1133.000 §3.6; `apps/messages/service.ts`). The
design, in one paragraph: a send `subscribePush()` answers the platform's
own credential (an APNs device token, an FCM registration token, a Web
Push `PushSubscription`'s endpoint and keys) with its rotation as a live
source, which the app gives its own server, as LLP 1126 gives a Live
Activity's token; exact2 sends nothing and relays nothing (LLP 1030.000
D6). A received push that shows a notification is the system's, and its
click is D6's event. A data-only push that runs app code needs LLP
1114.001 stage 2's wake. Its entitlement (`aps-environment`) is a grant
line of its own (LLP 1069.008 D4). Nothing of it is built here.

The package links only into an app that imports it (LLP 1047.001); an app
that does not pays nothing. The host's delegate install at launch exists
already. Nothing runs before first pixel: the status is read when first
asked, and a launching click is delivered after first pixel (D6). The
binary delta of the fixture with and without the package, by LLP 1047's
probe, cannot be measured before the package exists: it is measured in
stage 1, recorded here, and stage 1 is not accepted without it (Q8).
