## Summary

Local notifications exist (`rules/DEFERRED.md`, 2026-10-04): Contract's
`showNotification(title=, body=, tag=, showTrigger=, navigate=)` and
`closeNotification(tag)` post through `UNUserNotificationCenter` on macOS
and iOS and through `new Notification` on the web, and a click opens the
`navigate=` route (LLP 1114.001 D1). The roster ranks "notifications,
completed" second in wave 1 (LLP 1133.000 §4). This RFC completes the
module and builds its first stage for the T3 Code clone, which today keeps
190 lines of its own Swift because the built module cannot do four things:

1. **Post without a sound.** The Apple host always sounds
   (`Notify.swift:54` sets `content.sound = .default`; `:139` presents with
   `.sound`). The clone's notification is the reference's
   `new Notification(title, { silent: true })`, and it plays its own sound.
2. **Deliver a click to an app with no router.** The click is delivered only
   as `navigate` to a navigation root, and the clone's window has none.
3. **Post from data code.** Whether a thread notifies is decided in the
   clone's TypeScript, and a host command cannot run there.
4. **Badge the app icon and read the permission.** Both are refused
   (`rules/DEFERRED.md:550-575`: "badges … and a readable permission fact").

What this RFC proposes:

- **`@exact/notifications`**, a standard-library package (LLP 1133 D5's
  default), into which `showNotification` and `closeNotification` move from
  `HOST_COMMANDS`. Its names, by the web's: `showNotification` with
  `silent=` added, `closeNotification`, `setAppBadge` and `clearAppBadge`
  (the Badging API), the permission fact `notificationStatus()`, the request
  `requestNotificationPermission()`, and the event `notificationclick`.
- **A click without `navigate=`** is a `notificationclick` event, carrying
  the notification's tag, delivered in order and once to the handler on the
  app's root node, held across a cold launch.
- **Data code calls every send** through the generated binding (LLP 1133
  D6): `await showNotification({ title, body, tag, silent: true })`.
- Two seam additions every later module can use: a **send that answers
  nothing** is a statement in an action, as a host command is today, and a
  module may declare an **event**, the bounded and ordered delivery LLP 1133
  D6 rule 7 asks for, with a rule for delivery that starts the app.
- Targets: **web, macOS, iOS** in stage 1. Actions and replies come in
  stage 2 (the Caltrain departure reminder's Snooze), Android and Windows in
  stage 3, each declared here (§8).

§12 lists the questions. The four that change the design are packaging

## 2. Tier 1

### D1 — The Notifications API's names, and the Badging API's

| Name | Kind | The web's | Deviation |
|---|---|---|---|
| `showNotification(title=, body=, tag=, silent=, showTrigger=, navigate=)` | send, answers nothing; a request while `prompt` (Q4) | [`ServiceWorkerRegistration.showNotification(title, options)`](https://notifications.spec.whatwg.org/#dom-serviceworkerregistration-shownotification), `NotificationOptions` `body`, `tag`, `silent`, `navigate` | `title` is a keyword like the options (LLP 1133.002 D13); `showTrigger` is the abandoned Notification Triggers draft's member, epoch milliseconds (built) |
| `closeNotification(tag=)` | send, answers nothing | `getNotifications({tag})`, then `close()` on each | one call by tag, shown or scheduled (built) |
| `setAppBadge(contents=)` | send, answers nothing | [`navigator.setAppBadge(contents)`](https://w3c.github.io/badging/#setappbadge-method), exposed to windows and workers | none |
| `clearAppBadge()` | send, answers nothing | [`navigator.clearAppBadge()`](https://w3c.github.io/badging/#clearappbadge-method) | none |
| `notificationStatus()` | live source, a fact | `Notification.permission`; `navigator.permissions.query({name: "notifications"})` | the module's permission fact in LLP 1133.002 D8's shape; the web's `default` reads `prompt` |
| `requestNotificationPermission()` | send, a request, answers `NotificationStatus` | `Notification.requestPermission()` | named for the module: imported names share the app's namespace (`contract-use-duplicate`), and a bare `requestPermission` would collide with the next module's |
| `notificationclick` | event (D6), on the app's root node | [`notificationclick`](https://notifications.spec.whatwg.org/#activating-a-notification), with `NotificationEvent`'s `notification.tag` and `action` | delivered to the app's root, the one place every exact2 app has, where the web delivers it to the service worker's global scope or as `click` to the page's `Notification` object |

**`silent`.** The Notifications API's `silent` is a nullable boolean whose
default, null, leaves sound and vibration to the platform; true means none
([options](https://notifications.spec.whatwg.org/#dom-notificationoptions-silent)).
Measured 2026-10-21 in Chrome 155, Chromium 156, Firefox 157 and WebKit 27.2
(Playwright, macOS 26.6.2): each constructs `new Notification("t",
{silent: true, tag: "a"})` and reads back `silent` true.

**`setAppBadge(contents)`.** `contents` is an option of a non-negative
integer: absent sets a flag (a badge with no number), `0` clears, as the
Badging API's [`contents`](https://w3c.github.io/badging/#dfn-badge)
does. A negative or fractional number refuses `TypeError`, the spec's
`[EnforceRange]`. The badge is the app's, not a session's: an embedded host
with two sessions shows the last value either set, as two documents of one
web app share one badge.

**What a send answers.** `showNotification`, `closeNotification`,
`setAppBadge` and `clearAppBadge` answer nothing (D5). From data code each
is a Promise that settles when the platform accepts or refuses the call, as
the web's do, and rejects with the errors below. From Contract each is a
statement; a refusal is a journal line, as today
(`showNotification: refused: denied`).

**Errors,** by the web's names: `NotSupportedError` where the target has no
such capability (LLP 1133 D8; §8); `NotAllowedError` where the permission is denied
or a badge needs one the app lacks; `TypeError` for bad arguments, which
the bake refuses first wherever the value is literal.

## 4. Seam additions

### D5 — A send that answers nothing is a statement

Today a module send needs a mutation, `send m = name(…)`, and the mutation
needs `as shape` what the send answers (`contract/cli/src/modules.rs:86-120`,
`contract-module-answers`). A notification answers nothing, and the built
command is a statement. So a declaration's send may say `"answers": null`,
and then:

- Contract calls it as a statement in an action, with keyword arguments:
  `showNotification(title="Build finished", tag=t.id, silent=true)`. The
  written form of today's command is unchanged; the app adds
  `use showNotification from "@exact/notifications"`.
- `send m = name(…)` to it is refused (`contract-module-answers`: it
  answers nothing), and a statement call to a send that answers something
  is refused (`contract-module-kind`: a mutation sends it).
- Its outcome is a journal line (`<name>: shown`, `refused: <reason>`).
  Data code's binding returns `Promise<void>`.

This amends LLP 1133.002 D13.

### D6 — A module may declare an event

LLP 1133 D6 rule 7: a value coalesces, so a module whose events must each
arrive declares a bounded event protocol. A click is such an event: two
clicks on two threads' notifications are two openings. The declaration:

```json
{ "event": "notificationclick", "on": "root",
  "args": ["string", "NotificationEvent"], "hold": 16 }
```

- **Contract.** The app imports the event with its shape and handles it
  with an attribute on its root component's outermost node, as
  `navigate=` is written on a navigation root:
  `column notificationclick=opened …`, where `action opened(tag: string)`
  or `action opened(tag: string, e: NotificationEvent)`. A second handler
  in the app, or one on another node, is refused
  (`contract-event-root`). Like `key`'s optional `KeyboardEvent`
  (`docs/contract-grammar.md`, "Keys"), the second parameter is optional.
- **Order and count.** Each event is delivered once, in the order the
  platform reported them, each as its own commit with the origin of a
  person's input (LLP 1133.002 D12). None is coalesced.
- **Held, and bounded.** An event that arrives before the session's first
  commit, or while the root's handler is not mounted, is held, up to
  `hold` (16 for this module), and delivered in order once the handler is
  mounted. Past the bound the oldest is dropped and journaled
  (`notificationclick: dropped (<tag>)`). An event no handler hears within
  the session's life is journaled when the session ends.
- **Launch.** An event that starts the app is held from launch, before the
  session boots (D7), and delivered after first pixel, never before it
  (`rules/RULES.md`, the boot path). This is the rule for cold-start
  delivery that LLP 1069.007's "Not in this RFC" waited for, and LLP
  1133.000 §4 asked notifications to propose: **an event the platform
  delivers to a closed app is held by the host from launch and delivered
  once, in order, after first pixel, to the handler the module's
  declaration names; it never runs app code before first pixel.**
- **Implementations** raise an event through the module context, beside
  `changed`: `emit("notificationclick", [tag, event])`. The runner checks
  the arguments against the declaration, as it checks an answer.
- **The agent** sees held and delivered events in `state.extensions`, and a
  drive raises one as §7 says.

This amends LLP 1133 D6 rule 7 and LLP 1069.007 ("Not in this RFC": lossless
events and cold-start delivery).

### D7 — The host keeps the one delegate; the click goes to the posting session

A platform has one notification delegate per process, and it must be set
before launch finishes to hear a click that starts the app
(`UNUserNotificationCenterDelegate`; LLP 1114.001 D1). A module instance is
made when its session boots, which is later. So the host keeps the
delegate, as it does today (`installNotificationClicks`, set in each
adapter's launch: `ExactMac/main.swift:550`, `ExactIOS/main.swift:182`),
and the module's implementation is handed the clicks:

- The Apple implementation writes `userInfo["exact"]` with the posting
  session's owner identity and process identity (both from the module
  context), the tag, and `navigate` if given, as `Notify.swift:50-52`
  writes today.
- On a click (`UNNotificationDefaultActionIdentifier`), the host's delegate
  finds the session as it does now (`Notify.swift:98-126`). With
  `navigate`, it opens the location (launch location or warm `navigate`,
  unchanged) and no `notificationclick` is raised: the location already says
  where the click goes, and one click has one meaning. Without, it raises
  `notificationclick` with the tag on that session, held per D6 if the
  session has not booted. A notification posted by a previous process goes
  to the session with its label, else the first live one, as today.
- On the web the page's `Notification` `click` listener does the same: it
  focuses the window, then navigates or raises the event.

So the delegate stays in ExactKit, and the package reaches it only through
the `userInfo` keys it writes and the context's `emit`.

## 6. Permission

LLP 1133.002 §4's stages, for this module.

**Declare.** The grant is built: `device.notifications <strings key>`
(`runner/src/device.rs`). It derives nothing on Apple (the system prompt
has a fixed text, and no usage key exists) and on the web (no
`Permissions-Policy` feature governs notifications). Stage 3 adds the
Android column (`android.permission.POST_NOTIFICATIONS`) and nothing on
Windows. `setAppBadge` needs no grant of its own: the badge is part of the
notification permission on every platform that asks for one.

**Read.** `notificationStatus()` answers `{available, state, badge}` and
the platform's words (D3):

| Platform state | `state` |
|---|---|
| Apple `notDetermined` | `prompt` |
| Apple `authorized`, `provisional`, `ephemeral` | `granted` (`apple.authorizationStatus` names which) |
| Apple `denied` | `denied` |
| web `Notification.permission` `default` | `prompt` |
| web `granted`, `denied` | the same word |
| Android 13+ never asked, rejected once, revoked | `prompt`, as geolocation's history decides (LLP 1133.002 D8) |
| Android 13+ permanently denied, or `areNotificationsEnabled()` false after a grant | `denied` |
| Android below 13 | `granted`, or `denied` when `areNotificationsEnabled()` is false |
| Windows `Enabled` | `granted` |
| Windows `DisabledForApplication`, `DisabledForUser`, `DisabledByGroupPolicy`, `DisabledByManifest` | `denied` (Windows never prompts) |
| the Notification portal | `unknown` (it has no query) |

`badge` is `true` where a badge will show: Apple's `badgeSetting` is
`enabled` (iOS), or always on macOS (§12 Q5); the web's `"setAppBadge" in
navigator`; `false` on Android (no app badge). `available` is false where
the target has no implementation or no notification centre (macOS outside
an app bundle, `Notify.swift:76-85`).

The state changes by itself (the person turns notifications off in
Settings). Apple has no change callback, so the implementation reads
`getNotificationSettings` again when the app becomes active, and announces
a change. The web follows `PermissionStatus`'s `change` (measured present in
all four engines, 2026-10-21) and reads again on `visibilitychange`, as
geolocation's does. Android reads again on `onResume`.

**Ask.** `requestNotificationPermission()` is a request (LLP 1069.007 D1):
Apple's `requestAuthorization(options:)` with D2's options; the web's
`Notification.requestPermission()`; Android 13+'s `requestPermissions`
for `POST_NOTIFICATIONS`; Windows answers the status at once. It answers
the new status. While `granted` or `denied` it asks nothing and answers the
status, as each platform does. Origins follow LLP 1133.002 D12: a tool
invocation's or a wake's request while `prompt` fails `NotAllowedError`,
reason `person-required`. Firefox and Safari ask only inside a user
activation, so on the web a request outside one is refused by the browser,
and the answer is the unchanged status.

**`showNotification` while `prompt`** asks first (Q4), as every host does
today: it is a request in that state, so a tool invocation's fails
`person-required` rather than prompt. While `denied` it refuses
`NotAllowedError`. The web's `showNotification` instead rejects `TypeError`
unless permission is already granted; exact2 keeps today's behaviour,
which `new Notification` in a page approximates (it fires `error`), as a
declared deviation, so an app that posts on a person's press needs no
separate request.

**Explain and recover:** the app's own UI, and `openURL("app-settings:")`
(LLP 1133.002 D11), which on macOS opens Notifications settings for the app
here rather than Location Services.

## 7. The substitute

**Shape:** `notificationStatus` is a fact; `requestNotificationPermission`
is a request, and so is `showNotification` while `prompt`;
`closeNotification`, `setAppBadge` and `clearAppBadge` are effects with
nothing to answer.

- **The fact.** `state` is set by `prefer permission.notifications
  granted|denied|prompt` and `--permission notifications=…`, as
  geolocation's is. The default is `prompt`, `available` true, `badge`
  true.
- **Requests.** While `prompt`, a request from a foreground origin holds a
  `permission` ticket: `tap @t allow` sets `granted` and continues (a
  pending `showNotification` is then listed); `deny` sets `denied` and
  refuses it; `cancel` leaves `prompt` and refuses it.
- **Posts** are listed in `state.notifications`, never shown, as today,
  with `silent` added to each entry: `{title, body, tag, silent,
  showTrigger, navigate, ref}`.
- **The badge** is `state.badge`: `null`, a number, or `"flag"`.
- **A click** is `tap @<ref>` on a listed notification: the existing
  operation on a new kind of target, so no operation is added (LLP 1133
  §7). It does what the platform's click would: opens `navigate`, or raises
  `notificationclick` with the tag, and removes the entry. A launching click
  is the launch flag `--notification <tag>`, which holds the event from
  boot as D6 says. Today's way to check a `navigate` click, `type` into the
  navigation root (LLP 1114.001 D1), still works.
- **Disclosure:** the entries' title, body and tag, which are the app's
  own text. **Lifetime:** an entry lives until replaced by tag, closed, or
  tapped. **Production:** none of it.

The substitute is declared in `exact.json`, as geolocation's is (LLP
1133.002 §6, "Declared, not built in"); `runner/src/notify.rs`'s listing
moves there.

## 9. Push, designed here

The roster designs push registration in this RFC and builds it when an app
with a backend asks (LLP 1133.000 §3.6; `apps/messages/service.ts`). The
design, in one paragraph: a send `subscribePush()` answers the platform's
own credential (an APNs device token, an FCM registration token, a Web
Push `PushSubscription`'s endpoint and keys) with its rotation as a live
source, which the app gives its own server, as LLP 1126 gives a Live
Activity's token; exact2 sends nothing and relays nothing (LLP 1030.000
D6). A received push that shows a notification is the system's, and its
click is D6's event. A data-only push that runs app code needs LLP
1114.001 stage 2's wake. Its entitlement (`aps-environment`) is a grant
line of its own (LLP 1069.008 D4). Nothing of it is built here.

## 10. Building it

Each stage lands green under the six checks and is driven before the next.

**Stage 0 — the seams.** Answerless sends (D5) and module events (D6) in
the declaration reader, the compiler (`contract/cli/src/modules.rs`), the
runner's admission and the TypeScript and Rust bindings, proved by a
fixture module in `packages/notifications/test`, before any notification
code moves. Under the agent, `tap @ref` on a listed entry.

**Stage 1 — the package, on web, macOS and iOS.**

- `packages/notifications`: `exact.json` (D1), `apple/` (Swift, from
  `Notify.swift`'s posting half), `web/` (from `notify-glue.js`), the
  conformance fixture.
- `showNotification` and `closeNotification` leave `HOST_COMMANDS`,
  `expr.rs`'s fixed slots and `compat.rs`'s command table; the compat id's
  command digest moves once. `runner/src/notify.rs`'s rule becomes the
  package's declaration and admission. The corpus, `docs/reference.md`'s
  "Notifications", `docs/contract-grammar.md:2141` and the `contract vocab`
  entries follow.
- ExactKit keeps the delegate (D7) and raises `notificationclick`.
- `silent`, the badge, the status and the request on each of the three.
- Drives: the fixture on the web and on a macOS bundle and an iOS
  simulator by the agent; by hand once on each, a silent post (no sound), a
  click with the app running and one that launches it, a badge count, the
  flag and its clearing, a denial in Settings read back; then the T3 Code
  clone's app PR drives the consumer (§13).

**Stage 2 — actions and replies.** `actions=[{action, title}]`,
`notificationclick`'s `action` and `reply`, `requireInteraction`; Apple's
`UNNotificationCategory` registered at launch from the plan's literal
actions; the Caltrain departure reminder's Snooze (LLP 1133.000 §4).
Ruled with its own amendment to this RFC.

**Stage 3 — Android and Windows**, per §8, each with its compile check
(LLP 1133.002 §10 stage 4's for Android).

## 11. What stays out

- Repeating schedules: `rules/DEFERRED.md` refuses them; a daily reminder
  posts the next one when the app runs. The Habits app is the likely
  consumer.
- Push delivery and a data-only push's wake (§9; LLP 1114.001 stage 2).
- Critical alerts and communication notifications (Apple entitlements).
- A custom sound file, `image`, `icon`, `vibrate`, `renotify`, `data`,
  `getNotifications()`: tier 3 or the web's names, each when a consumer
  asks.
- A notification's click from a tool invocation: there is none; a tool
  may post (it carries its origin), and `prompt` refuses it.
- Data code hearing a click: events go to Contract actions, which may
  then call data code.

## 12. Questions for the ruling

1. **Packaging.** (a) `@exact/notifications`, and `showNotification` and
   `closeNotification` move into it (recommended): LLP 1133 D6 says
   `HOST_COMMANDS` "stops growing", so the badge, the status and the
   request cannot join it, and a module split between the package and the
   vocabulary would split one centre's state, which LLP 1133 D2 rejects.
   (b) Exact2's vocabulary, grown: four new host commands, a reserved
   source for the status, and a new data-code route for vocabulary; this
   keeps today's Contract text but builds a second permission and binding
   mechanism beside the package one.
2. **Answerless sends as statements** (D5). Recommended: yes. Without it,
   every post in Contract needs a mutation that holds nothing.
3. **Module events** (D6): the root attribute, the hold of 16, delivery
   after first pixel, and the cold-start rule as LLP 1069.007's amendment.
   Recommended: yes.
4. **`showNotification` while `prompt`.** (a) It asks, as today
   (recommended), a declared deviation from the web's rejection; (b) it
   rejects `NotAllowedError` until `requestNotificationPermission` is
   granted, as the web does, which changes every existing app's first
   post.
5. **The Mac's badge.** (a) `NSDockTile.badgeLabel` (recommended): what
   AppKit apps and the reference (Electron's `app.setBadgeCount`) use; it
   shows without a notification grant. (b) `setBadgeCount`, which follows
   the person's badge setting for the app and needs the `.badge`
   authorization. Whether the Notifications "Badge application icon"
   setting hides a Dock tile label is measured in stage 1 and recorded.
6. **Targets and stages:** stage 1 on web, macOS and iOS now; stage 2 and
   stage 3 as §10. Recommended: yes.
7. **The `rules/DEFERRED.md` record.** Proposed, with no take offered:
   "**Expanded** (<ruler>, <date>; LLP 1133.004): the notifications module
   completed in stage 1: `silent`, a click delivered as `notificationclick`
   to the app's root, posting from data code, the app badge by the Badging
   API's names, and notifications' permission fact and request. Consumer:
   the T3 Code clone's thread notifications. Still refused: push delivery,
   repeating schedules, and actions and replies until stage 2's ruling."

## 14. Cost

The package links only into an app that imports it (LLP 1047.001); an app
that does not pays nothing. The host's delegate install at launch exists
already. Nothing runs before first pixel: the status is read when first
asked, and a launching click is delivered after first pixel (D6). Stage 1
measures the binary delta of the fixture with and without the package by
LLP 1047's probe and records it here.
