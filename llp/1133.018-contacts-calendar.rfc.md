## Summary

Two modules, one RFC, because they ask the same four questions and answer
them alike. `@exact/contacts` lets the person choose contacts to give the
app, and lets an app with access read the address book. `@exact/calendar`
lets the person add an event through the system's own editor, and lets an
app with access read and write the person's calendars. Both run on the
web, iOS, macOS and Android first, with every other target of LLP 1133 D8
a visible `later` or `absent`.

```
use selectContacts, ContactInfo from "@exact/contacts"
use calendarStatus, calendarEvents, showEventEditor, CalendarEvent,
  EventEditorResult from "@exact/calendar"

mutation invited as shape ContactInfo[] then addGuests
mutation added as shape EventEditorResult then noted
action invite
  send invited = selectContacts(properties=["name", "email"], multiple=true)
action addToCalendar
  send added = showEventEditor(event=CalendarEvent(title=item.title,
    start=item.startDate, duration="PT1H"))

resource status = calendarStatus()
resource theirs = calendarEvents(start=dayStart, end=dayStart + 86400000)
```

```ts
import { calendarEvents } from "@exact/calendar";

// How many of the person's events fall on each day of the six weeks shown.
const days = new Map<number, number>();
let after: string | undefined;
do {
  const page = await calendarEvents({ start, end, after, limit: 500 });
  for (const e of page.events) days.set(dayOf(e.utcStart), (days.get(dayOf(e.utcStart)) ?? 0) + 1);
  after = page.next ?? undefined;
} while (after);
```

Contacts' tier 1 is the W3C Contact Picker API's `navigator.contacts.select`
([Contact Picker](https://www.w3.org/TR/contact-picker/)), the one
capability of either module the web has. Reading the address book is a
declared deviation, in the picker's own shape. The calendar has no web
API (the W3C's was discontinued in 2014,
[Calendar API](https://www.w3.org/TR/calendar-api/)), so its tier 1 is a
deviation whose data model is iCalendar's
([RFC 5545](https://www.rfc-editor.org/rfc/rfc5545)), spelled as
JSCalendar, iCalendar's JSON form, spells it
([RFC 8984](https://www.rfc-editor.org/rfc/rfc8984)).

The modules answer four questions every personal-data module after them
will meet (§0):

1. **A pick is a copy; a store is a grant.** A picker needs no
   permission on any platform, answers values the app then owns, and
   never reads or changes the permission. Access to the store is a grant
   line and a state, and its answers carry identifiers and stay live.
2. **A permission state that changes what a granted read answers is a
   fact every caller sees.** iOS 18's limited contacts and iOS 17's
   write-only calendars are `access` in the status, beside `state`, on
   every target, because a caller that cannot see them takes a partial
   answer for the whole.
3. **A store change is a topic.** Each platform's change notification
   asks every reader again, coalesced, and the foreground asks once more.
4. **The store stays in the platform.** Every read is a bounded page,
   fetched off the main thread; what the runner holds is what the app
   shows; and no answer that read the person's store is ever kept for the
   next launch.

The consumer is the Calendar example (`examples/calendar`), which today
shows only the calendar it keeps itself. It gains the person's own events
beside its items, guests picked from contacts, and "Add to Calendar" (§11).

## 0. What is new here

Writing these modules out against the seam the earlier modules built
shows four things that seam does not yet answer. Each is decided below
and is a question for Charlie in §15.

1. **Pickers and access are different authorities.** The platforms'
   pickers (`CNContactPickerViewController`, Android 17's contact picker,
   `EKEventEditViewController` on iOS 17, Android's calendar insert
   intent) need no permission, and their whole point is that the app
   never sees what the person did not choose. Geolocation's model has one
   capability and one permission. Here a module has two paths whose
   results differ in kind: a pick is a copy with no identity, a read is a
   live view of the store (D4).
2. **The platforms have states that change answers, not only prompts.**
   Under iOS 18's limited access a contacts query answers only the
   contacts the person shared; under write-only access EventKit's reads
   "don't return any events"
   ([requestWriteOnlyAccessToEvents](https://developer.apple.com/documentation/eventkit/ekeventstore/requestwriteonlyaccesstoevents(completion:))).
   LLP 1133.002 D8 sends every extra state to tier 2. A state that makes
   an empty answer look like a true one cannot be tier 2 (D5).
3. **A store is large, and its changes are not described.** An address
   book holds thousands of contacts; `EKEventStoreChanged` says only that
   something changed and that "you should refetch all EKEvent and
   EKReminder objects you have accessed"
   ([EKEventStoreChanged](https://developer.apple.com/documentation/foundation/nsnotification/name-swift.struct/ekeventstorechanged)).
   The module seam carries JSON on the main thread within the native
   module request's 4 MiB (LLP 1133.006 D8 item 1). So reads are bounded
   pages, and a change re-asks pages, never the store (D6, D7).
4. **exact2 itself would copy the person's data.** A data-code source
   that calls a module binding is a store reader
   (`js/src/door.rs`, `observe_external_read`), so on a native host its
   answer is kept under `exact.kept.<resource>` in kv files beside the app's own
   (LLP 1027 D4, `runner/src/runner/kept.rs`) and shown at the next launch
   before the module loads. For a forecast that is the point. For the
   person's contacts it is a copy no author asked for, at rest, shown after
   the person may have revoked access. So an answer that read either
   store is never kept (D8).

## 1. What exists

**Nothing of either.** No grant row names contacts or calendars
(`runner/src/device.rs`); the roster gives each a row (LLP 1133.000 §3.8)
and nothing more.

**The Calendar example** (`examples/calendar`) is one calendar for iOS,
macOS and the web: a Rust data crate that keeps events, todos and
stickers in its own SQLite file, computes month pages with an in-memory
index, and says so in its grant: "The app needs only its own SQLite file,
never the device's calendar database" (`data/src/lib.rs`). Its README
puts "calendar sync, recurrence and notifications" out of scope. It has
two app modules of its own (`calendar-input-root`, `calendar-drag-handle`)
in Swift, and no Android crate.

**The seam** this RFC uses as the earlier modules built it: packages and
their binding (LLP 1133.001); admission before dispatch, also under the
agent, with an implementation as its own substitute (LLP 1133.006 D8,
LLP 1133.008 D8 item 9); the package context's session clock, foreground
fact and orderly end (LLP 1133.009 D10 items 1–3); `"origin": "app"` and
`"foreground": true` (item 8); grants per name (item 9);
`release(name, args)` (item 12); `app:/tmp/<extension>/` with no grant
(LLP 1133.008 D8 item 4); one Android permission history in the host's
`ExtensionContext` (item 7); and, from LLP 1133.015 D16, the
presentation anchor, `"kept"` on a module source, an answer's `stale`

## 2. Tier 1

### D1 — Contacts: the Contact Picker's names, and the store in its shape

| Name | Kind | Meaning | Web | Contract |
|---|---|---|---|---|

| Shape | Fields |
|---|---|
| `ContactInfo` | the Contact Picker's five, each a list, present only when asked ([ContactInfo](https://www.w3.org/TR/contact-picker/#contacts-manager-select)): `name: string[]`, `email: string[]`, `tel: string[]`, `address: ContactAddress[]`, `icon: string[]`; and `id: option<string>` (D4) |

`properties` takes the spec's `ContactProperty` values: `address`,
`email`, `icon`, `name`, `tel`. `id` is the platform's persistent
reference on a store read: Apple's `CNContact.identifier`, which "can be

contact on the current device"
([identifier](https://developer.apple.com/documentation/contacts/cncontact/identifier));
Android's `CONTENT_LOOKUP_URI`, which "should be used to create shortcuts
or otherwise create long-term links to contacts"
([Contacts](https://developer.android.com/reference/android/provider/ContactsContract.Contacts)).

**Errors** are the spec's and Media Capture's `DOMException` names, as
LLP 1133.009 D1 answers them: `SecurityError` (the web's call without
transient activation), `InvalidStateError` (a picker already showing; not
a top-level page), `TypeError` (`properties` empty or naming one this
target's picker cannot answer), `NotAllowedError` (denied, or a caller
the origin rule refuses, `message` `person-required`), `NotSupportedError`
(no picker or no store on this target), `NotFoundError` (an `id` the
store no longer holds), `AbortError`, `UnknownError`.

**Declared deviations,** each with its reason:

- **Names are prefixed:** `selectContacts` and `getContactProperties`
  for `contacts.select` and `contacts.getProperties`, as the camera
  writes `stopTrack` for `track.stop()`. Reason: an imported Contract
  name is one identifier, and `select` alone would collide.
- **An icon is a file, not a `Blob`:** each `icon` is an `app:/tmp/contacts/<n>.<ext>`
  path the module writes with no grant (LLP 1133.008 D8 item 4), shown
  by an `img`. Reason: neither a Contract value nor a module request
  carries images, as the camera's photo is a path.
- **The store is a deviation.** The web has no address book API. Its
  names are `queryContacts` and `contactsStatus`, its values the
  picker's `ContactInfo`, so a pick and a read are one shape and an app
  moving from one to the other changes the call, not its views.
- **`id`** is added to `ContactInfo`. A pick answers `none` (D4).

Section numbers are RFC 8984's, then RFC 5545's. `CalendarInfo` is `id`,
`title`, `color` (a CSS colour), `writable`, `isDefault` and `source`
(the account's name), after JMAP Calendars' Calendar object.
`EventEditorResult` is `action: enum<saved|canceled|deleted|unknown>`.
`EventPage` is `events: CalendarEvent[]`, `next: option<string>`.
`CalendarStatus` is `available: bool`, `state`, `access:
enum<full|write-only|none|unknown>`, `editor: bool` (this target has
`showEventEditor`), `apple`, `android`.

**Why JSCalendar's spelling.** iCalendar is the model every calendar
store speaks (EventKit's `calendarItemExternalIdentifier`, Android's
`UID_2445` "for events added from the RFC 2445 iCalendar format",
CalDAV), so its distinctions are the ones a calendar app needs: local
time with a zone, floating time and all-day dates (§3.3.5), an
occurrence's identity in a series (`RECURRENCE-ID`). Its text form is not
a value; JSCalendar is the IETF's JSON form of the same model, a
Proposed Standard, in camelCase, whose `timeZone: null` is floating time
as RFC 5545's form 1 is. JMAP Calendars, still a draft, adds the computed
`utcStart` and `utcEnd` that a range query and a Contract layout need
([JMAP Calendars §5](https://datatracker.ietf.org/doc/draft-ietf-jmap-calendars/)).
The draft's 2.0 revision of JSCalendar is not yet an RFC; this module
follows RFC 8984 and moves with an RFC, not a draft.

**What each answer means.**

- **Occurrences, not series.** `calendarEvents` answers each occurrence
  of a recurring event in the range, as EventKit's
  `events(matching:)` and Android's `Instances` table give them
  ([Instances](https://developer.android.com/reference/android/provider/CalendarContract.Instances)),
  each with the series' `id` and its own `recurrenceId`. The rule
  itself is not answered (D9 for Apple's, §13).
- **Time.** `start` and `end` of a query are instants, ms since the
  epoch. A floating or all-day event is placed in the device's time zone,
  as EventKit returns them "in the default time zone"
  ([predicateForEvents](https://developer.apple.com/documentation/eventkit/ekeventstore/predicateforevents(withstart:end:calendars:)))
  and as Android's all-day events, stored at a UTC midnight
  ([Events](https://developer.android.com/reference/android/provider/CalendarContract.Events)),
  are read back as local dates.
- **A range is at most four years.** EventKit's predicate "matches only
  those events within a four-year time span" and silently shortens a
  longer one; the module refuses a longer range by name
  (`calendar-range-too-long`) on every target, so no target answers a
  shorter range than was asked.
- **Ids.** `id` is Apple's `eventIdentifier` and Android's `Events._ID`.
  Apple's "most likely changes" when the event moves to another calendar
  ([eventIdentifier](https://developer.apple.com/documentation/eventkit/ekevent/eventidentifier));
  `uid` is the cross-device one and need not be unique
  ([calendarItemExternalIdentifier](https://developer.apple.com/documentation/eventkit/ekcalendaritem/calendaritemexternalidentifier)).
- **Writes are of single events.** `saveEvent` takes an event without
  recurrence; `saveEvent` and `removeEvent` refuse an occurrence of a
  recurring series (`NotSupportedError`) until a consumer needs spans
  (§13).

**Declared deviations,** all of the module, since the web has none of
it. The one the web can do is `showEventEditor`: an `.ics` file of the
event, which the browser downloads and the system offers to its calendar
(D15). It is common practice, not a standard; no web API adds an event.

## 3. Pickers and access

### D4 — A pick is a copy; access is a grant

The two paths are different authorities, and the module keeps them
apart.

**A pick** (`selectContacts`, `showEventEditor`) is the person's act at a
moment. On every platform it needs no permission:
`CNContactPickerViewController` "does not need access to the user's
contacts and the user will not be prompted"
([CNContactPickerViewController](https://developer.apple.com/documentation/contactsui/cncontactpickerviewcontroller));
Android's picker lets an app "select one or more contacts without
requiring `READ_CONTACTS`"
([ContactsPickerSessionContract](https://developer.android.com/reference/android/provider/ContactsPickerSessionContract));
EventKitUI "presents chooser and editor UI outside of your app's process
on iOS 17 and later", usable "without requesting write-only or full
calendar access"
([Accessing the event store](https://developer.apple.com/documentation/eventkit/accessing-the-event-store));
Android's insert intent needs no permission at all
([Calendar intents](https://developer.android.com/identity/providers/calendar-provider#intents)).
So:

- **No grant line.** A pick derives nothing: no usage string, no
  Android permission, no entitlement, as `showOpenFilePicker` derives
  none (LLP 1069.010). An app that only picks asks for nothing.
- **No state.** A pick neither reads nor changes `contactsStatus()` or
  `calendarStatus()`. It works under `denied`, which is the platforms'
  own advice: use the picker where it serves.
- **A copy, with no identity.** A picked contact's `id` is `none`, on
  every target, and its values are the app's from then on, to keep in
  its own storage. Android's session URI "grants temporary read
  permission", and the app "has to persist the contact data"
  ([contact picker](https://developer.android.com/about/versions/17/features/contact-picker));
  the web's `ContactInfo` has no identifier. A pick is never live: the
  person's later edits to the contact do not reach it. Apple's picked
  `CNContact` does carry an `identifier`; it is the tier 2 result word
  `apple.identifier` (D9), useful only to an app that also has access.
- **The editor's answer says nothing of the event.** On iOS 17
  "inspecting the properties of the dismissed controller … doesn't return
  any useful information. The app isn't aware of the changes"
  ([sample](https://developer.apple.com/documentation/eventkit/accessing-calendar-using-eventkit-and-eventkitui)).
  So `showEventEditor` answers only `action`, and `unknown` where the
  platform reports nothing (D15).
- **Origin.** A pick opens system UI, so it is `"origin": "app",
  "foreground": true` (LLP 1133.009 D10 item 8): any of the app's own
  foreground code may open it, and a tool invocation or a wake fails
  `NotAllowedError`, `person-required`, in every state (LLP 1133 D6 rule
  3). The web adds its own rule, transient activation, and a call that
  reaches the page outside it fails `SecurityError` (D15).

**Access** (`queryContacts`, `calendars`, `calendarEvents`, `saveEvent`,
`removeEvent`) is a grant the platform keeps: a grant line, a state, a
prompt, the origin table of LLP 1133.002 D12 (D11). Its answers carry
`id`, are live (D7), and are the store's, not the app's: they are never
kept (D8).

**One picker at a time.** A second `selectContacts` while one shows fails
`InvalidStateError`, as the spec's does; a pick asked while a permission
prompt shows waits in LLP 1133.002 D9's queue, behind it.

*Rejected:* a pick that answers ids the app can re-read. An id is a
reference into the store; following it needs access, and an app that
had access would query, not pick. Answering one from a pick would let an
app that later gains access join its old picks to the store silently,
which is the tracking a pick exists to prevent.

### D5 — A state that changes what a granted read answers is a fact

LLP 1133.002 D8 gives every module `state` (`granted`, `prompt`,
`denied`, `unknown`) and sends "more states than these" to tier 2. These
modules show that a platform's extra state is one of two kinds:

- **It changes how to ask:** Apple's `restricted`, Android's rationale
  and permanent denial. A caller that ignores it still reads true
  answers. Tier 2, as LLP 1133.002 D8 says.
- **It changes what a granted read answers:** geolocation's approximate
  authorization, iOS 18's limited contacts, iOS 17's write-only
  calendars. A caller that cannot see it reads a subset as the whole
  ("no contact named Ana"; "no events today"). **A shared word in the
  status,** on every target, whichever platforms have it today, beside
  `state`: geolocation's `accuracy`, and here `access`.

So `access` reads, on every target:

| `access` | Contacts | Calendar |
|---|---|---|
| `full` | the whole store | read and write every calendar |
| `limited` | only the contacts the person shared; a query answers those, and "your app has automatic access to contacts it creates" ([Accessing the contact store](https://developer.apple.com/documentation/contacts/accessing-the-contact-store)) | — |
| `write-only` | — | new events only; every read fails (below) |
| `none` | `state` is not `granted` | the same |
| `unknown` | the target has no store (`available` false) | the same |

A target without the state answers `full` while granted. Neither state is
silent in a read:

- **Limited** is a correct answer to a narrower question, so a read
  proceeds and answers the shared subset; the app reads `access` to
  offer "Share more contacts". Expanding it is Apple's mechanism alone,
  so it is tier 2 (D9): `ContactAccessButton` as a view, and
  `contactAccessPicker` as a send.
- **Write-only** would answer every read with nothing, which is never a
  correct answer. So a read under write-only is a request to raise it
  where the app has the full line (D11: Apple prompts to upgrade, and
  the read then proceeds), and otherwise fails `NotAllowedError` with
  `message` `write-only`, never an empty page.

Apple's `restricted` stays tier 2 (`apple.authorizationStatus`), as
geolocation's does. Android 11's "Only this time" does not arise: it is
offered for location, microphone and camera only
([one-time permissions](https://developer.android.com/training/permissions/requesting#one-time)).

This amends LLP 1133.002 D8's last sentence: an extra state that changes
what a granted call answers is a shared word in the module's status; one
that changes only the asking is tier 2.

## 4. Stores

### D6 — Bounded pages, fetched off the main thread; the runner holds what is shown

**Every read is a bounded query.** `queryContacts` and `calendarEvents`
answer a page: at most `limit` items (contacts: default 100, at most
1,000; events: default 500, at most 2,000), and `next`, an opaque cursor
to pass as `after` for the page after it, `none` at the end. A query
names what it reads, so nothing else is fetched or crosses:

- `properties=` for contacts, as the picker asks per property and as
  `CNContactFetchRequest` needs its keys
  ([CNContactFetchRequest](https://developer.apple.com/documentation/contacts/cncontactfetchrequest))
  and Android's query its projection. An `icon` is a thumbnail written
  to `app:/tmp/contacts/` (D1), never bytes in the answer.
- `text=` (a name, email or phone matched as the platform's search
  does: `predicateForContacts(matchingName:)`, Android's
  `CONTENT_FILTER_URI`), `ids=`, or neither for the whole store in
  order.
- `start`, `end`, `calendars=` for events.

A page's answer stays within the module request's bound (LLP 1133.006 D8
item 1); the limits above keep a page of names, emails and numbers in
tens of kilobytes. A development build checks each answer against its
`limit`, as it checks every reply against its declaration (LLP 1124 D5).

**A cursor is a key, not an offset.** `next` names the last item's sort
key and id, and the next page starts after it. So a page asked again
after the store changed starts after the same contact or occurrence, not
at a shifted offset, and the module holds no platform cursor between
calls: no handle, nothing to dispose, nothing to leak when a reader goes.

**Off the main thread.** Every package entry is on the main thread
(`ExactPackage.swift`), and both platforms say not to query a store
there: "because `CNContactStore` fetch methods perform I/O, it's
recommended that you avoid using the main thread"
([CNContactStore](https://developer.apple.com/documentation/contacts/cncontactstore));
`events(matching:)` "is synchronous. For asynchronous behavior, run the
method on another thread"
([events(matching:)](https://developer.apple.com/documentation/eventkit/ekeventstore/events(matching:)));
Android's `Instances.query` "is a blocking function and should not be
done on the UI thread". So each implementation fetches on its own queue
and replies on the main thread, as `later` allows.

**Transit, not state.** A reply to data code's binding call passes the
runner as every module body does (LLP 1133 D6 rule 1): admitted,
journaled by name, arguments and size, never by value, and then given to
the data runtime. The runner keeps none of it. What data code returns is
the resource's answer, and only that is state: the Calendar's month
dots are a few numbers per day, read from pages the runner saw once and
let go. Data code that needs the whole store (to deduplicate, to export,
to send to the app's server) walks the pages.

*Rejected:*

- **A snapshot file** (the store copied into an `app:/` SQLite or JSON
  file that data code opens with `storage.sqlite`). It copies the
  person's whole store into the app's container, outside the platform's
  permission, where it outlives a revocation.
- **A native cursor as a handle** (`handle<cursor>` over a platform
  `Cursor` or enumeration). It ties an open platform resource to a
  reader's lifetime, needs `dispose` on every path, and is invalidated by
  every change; a key cursor needs none of it.
- **Change history as tier 1.** Apple's `CNChangeHistoryFetchRequest`
  enumerator is unavailable in Swift (`NS_SWIFT_UNAVAILABLE`,
  [enumeratorForChangeHistoryFetchRequest](https://developer.apple.com/documentation/contacts/cncontactstore/enumeratorforchangehistoryfetchrequest:error:)),
  EventKit has none, and Android approximates one with
  `CONTACT_LAST_UPDATED_TIMESTAMP` and a 30-day `DeletedContacts` log. A
  sync engine needs every change, which LLP 1133 D6 rule 7 says a live
  value cannot promise; it waits for a consumer and a batch protocol
  (§13).

### D7 — A store's change is a topic

Each module has one topic for its store (`contacts`, `calendar`). Every
live name that reads the store watches it; `contactsStatus` and
`calendarStatus` watch it too, since a change of access arrives the same
way.

- **Observing follows readers.** An implementation observes the store
  while any live name of its module has a reader, and stops at
  `release(name)` of the last (LLP 1133.002 D5): Apple's
  `CNContactStoreDidChange`, "posted when changes occur to the contact
  store"
  ([CNContactStoreDidChange](https://developer.apple.com/documentation/foundation/nsnotification/name-swift.struct/cncontactstoredidchange)),
  and `EKEventStoreChanged`, which "is posted on the main actor"; Android's
  `registerContentObserver` on `ContactsContract.Contacts.CONTENT_URI`
  and `CalendarContract.Events.CONTENT_URI`, with descendants
  ([registerContentObserver](https://developer.android.com/reference/android/content/ContentResolver#registerContentObserver(android.net.Uri,%20boolean,%20android.database.ContentObserver))).
- **A notification is announced, coalesced.** On a notification the
  implementation announces its topic (`context.changed`), and every
  reader is asked again under its own last origin (LLP 1133.002 D12). A
  sync posts many notifications; while the re-asks one announcement
  caused are in flight, further notifications set a mark, and one more
  announcement follows the last of them landing. So a storm of a
  thousand notifications costs at most two rounds of pages.
- **The foreground asks once more.** Observers do not run while an Apple
  app is suspended, and nothing is delivered to an Android process that
  is not running. So on each return to the foreground (the context's
  foreground fact, LLP 1133.009 D10 item 3) an implementation with
  readers announces once. A page asked again is bounded (D6), so this
  costs one round of pages per return.
- **Access changing is a change.** A grant raised from write-only to full
  posts `EKEventStoreChanged` (TN3153), after which EventKit needs
  `reset()` "to receive data after they grant access"
  ([requestFullAccessToEvents](https://developer.apple.com/documentation/eventkit/ekeventstore/requestfullaccesstoevents(completion:)));
  the implementation resets and announces. A grant changed in Settings
  is read again on return to the foreground, as LLP 1133.002 D8 does on
  Android. iOS is observed to end an app whose Contacts or Calendars
  permission the person changes in Settings, though Apple does not
  document it ([forum thread](https://developer.apple.com/forums/thread/64740));
  the module assumes neither.
- **Now and next.** An agenda that shows "now" changes when an event
  starts with no store change. `calendarEvents`' answer names, as its
  `stale` time (LLP 1133.015 D16 item 2), the next start or end inside
  its range after the session's now, and the runner asks it again then.

Nothing is delivered while the app is closed: Android's
`JobInfo.TriggerContentUri` would, and waits for the background module
(§13).

### D8 — No answer that read the person's store is kept

Every name of both modules that answers from the store or a pick is
declared `"kept": "never"`, extending LLP 1133.015 D16 item 4's word
(`"kept": true` keeps a module source's answer). It means:

- **The name's own answer is never kept,** as an undeclared module
  source's is not.
- **Neither is any answer that read it.** A data-code resource whose
  answer called such a name, at any depth of its `await`s, is marked by
  that call as it is marked a store reader today (`js/src/door.rs`), and
  `keep_answer` keeps nothing for it and forgets what it kept before, in
  the same commit (`runner/src/runner/kept.rs`). Its kept entry is
  neither seeded at boot nor carried by a reload.

**Why.** A kept answer is written to the kv store under
`exact.kept.<resource>`, at most 256 KiB, read at the next launch and
shown before the module has loaded (LLP 1027 D4). For these stores
that is:

- **a copy no author made.** The app's author decided to read the
  person's contacts and show some; exact2 would decide, on its own, to
  write them to disk outside the platform's permission. LLP 1133.010 D5
  refuses the same for a locked launch's account content.
- **shown after a revocation.** The module loads after first pixel
  (216 ms after it under the agent in Weatherlight's macOS build, LLP
  1133.002 D16), so a person who turned off the app's access would see
  their contacts for that long at every launch until the kept entry is
  replaced; iOS is observed to end an app whose permission changes in
  Settings (D7), so the next launch is where a revocation meets it.

*Rejected:* keeping an answer while the platform's state reads `granted`
at boot. The state is the package's to read, and the package's code does
not run before first pixel (`rules/RULES.md`, the boot path); the host
would need its own copy of every module's status call.

**Cost.** A resource fed by either store shows its placeholder on the
first frame and its answer when the module answers. The recipe says to
read the store in a resource of its own, so the app's own data keeps its
kept answer: the Calendar's month keeps its first frame and only the
person's events arrive after it (§11). Stage 2 measures the time from
first pixel to the first store answer on an iPhone simulator.

Picked contacts are the app's own copy, which it keeps in its storage by
its own choice (D4); keeping them is the app's act, under its grant.

**Declare.** A pick needs no line (D4). Access does:

`WRITE_CALENDAR` derived only when a write name is used is new: a
derivation conditioned on the names the bake finds, as the temporary
accuracy dictionary is derived from the `purposeKey`s used (LLP 1133.002
D10). Since iOS 17, an app with neither calendar key "automatically
denies any access request" ([Accessing the event store](https://developer.apple.com/documentation/eventkit/accessing-the-event-store)),
so no binary asks without its string, and the bake refuses a store name
without its line (`grant-missing`, per name, LLP 1133.009 D10 item 9).

**The two calendar lines may stand together,** unlike geolocation's pair
(LLP 1133.002 D7): they are two levels of one store, and Apple's path
between them is an upgrade. With both, `saveEvent` while `prompt` asks
write-only (the least that serves it), and a read asks full. With only
the write-only line, a read fails `NotAllowedError` (`write-only`, D5).

**Write-only on Android is a ceiling the module keeps.** Android has no
write-only state that serves: an insert "must include `CALENDAR_ID`"
([Calendar Provider](https://developer.android.com/identity/providers/calendar-provider)),
the `_ID` of a calendar row, and reading the calendars needs
`READ_CALENDAR`. So under the write-only line alone the Android
implementation asks both in one request, which shows the calendar
group's one dialog either way, reads calendars only to find where to
write, and refuses every read as Apple does: `access` reads `write-only`.
It is a ceiling where the module can keep it, as geolocation's iOS
approximate line is (LLP 1133.002 D7): the person's dialog says
"calendar" either way, and the app is held to less than it was granted.

**Android 17 and Play.** For apps targeting API 37, Google Play allows
`READ_CONTACTS` only where the picker cannot serve the app's core
function, mandatory from 2027-01-27
([Play Console help](https://support.google.com/googleplay/android-developer/answer/16935362)).
The host targets API 36 today (`host/android/app/build.gradle.kts`); the
recipe says to pick unless the app's purpose is the address book.

   "relative to" a rect of a view
   ([showRelative](https://developer.apple.com/documentation/contactsui/cncontactpicker/showrelative(to:of:preferrededge:))),
   and on iPad a picker or editor is a popover with a source. So the
   context gains `anchor`: the frame, in the session's window, of the node
   whose person's input made the commit that caused the call (the button
   pressed), `nil` when no input caused it. The runner passes, with the
   origin, the node the input event targeted, and the host turns it into
   a frame. With no anchor, a Mac popover shows from the window's
   centre and an iPad sheet as a form sheet.
2. **An activity's result on Android.** `ExtensionContext` gains
   `startActivityForResult(intent, done(resultCode, data))`, through the
   host's `ExactActivity.onActivityResult`, which nothing forwards today.
   A result that reaches an activity recreated meanwhile settles the
   pending call; one lost with the process has no caller left, since the
   session ended with it.
3. **`"kept": "never"`** (D8): a name's answer, and every answer that read
   it, is never kept, and its kept entry is forgotten with the commit.
4. **A typed sheet ticket.** LLP 1133.015 D16 item 5 holds a sheet as a
   ticket with fixed choices. A pick's answer is which contacts, so a
   sheet may declare `"typed"`: `type @t c2,c5` answers it with those
   fixture ids, as `type @t 48.8,2.3` answers a position ticket (LLP
   1133.002 §6); `tap @t cancel` answers the sheet's cancel.

And one in the grant table: **a derivation conditioned on the names
used** (D11's `WRITE_CALENDAR`), a column the bake fills from the names
it found, in `runner/src/device.rs`.

## 10. The substitute

**The implementation is its own substitute** (LLP 1133.006 D8 item 4), in
LLP 1133.008 D8 item 9's split: under the agent the runner admits each
call and holds the permission ticket and each sheet's ticket, and the
implementation then runs, told so, over its fixture store, reading no
store of the person's and presenting nothing. The declared `permission`
(`contacts`, `calendar`) stays the runner's, so tickets,
`prefer permission.contacts`, `--permission calendar=…` work as
geolocation's do (LLP 1133.002 §6).

**The fixtures** are one file per module, read by every implementation:
`packages/contacts/fixture/contacts.json` (twelve contacts in
`ContactInfo`'s shape with fixed ids, two with icons, one with no email,
and a `limited` list of the four a limited grant shares) and
`packages/calendar/fixture/calendar.json` (three calendars, one not
writable; events in 2026-09 and 2026-10 in `CalendarEvent`'s shape: timed,
all-day, floating, and the occurrences of a weekly series listed one by
one with their `recurrenceId`, so no implementation expands a rule).
Queries over them are the conformance suite's: a case-insensitive
substring of a name, email or number; overlap with `[start, end)` by
`utcStart` and `utcEnd` in the session's time zone; the platform's order
replaced by the fixture's; key cursors as D6 says. The suite holds the
three implementations' answers equal to its own expected pages, as the
recorder's smoke holds its signal equal (LLP 1133.009 §10).

**Under the agent, on every target with an implementation:**

| Event | Result |
|---|---|
| `selectContacts` | a `pick` ticket, its `args` naming the properties and `multiple`: `type @t c2,c5` answers those fixture contacts with the properties asked (icons copied to `app:/tmp/contacts/`), `id` `none`; `tap @t cancel` answers `[]`; more than one id with `multiple` false is refused by the driver |
| `showEventEditor` | an `editor` ticket, its `args` the event: `tap @t save` adds the event to the fixture's default calendar, announces `calendar` and answers `saved`; `tap @t cancel` answers `canceled` |
| a read while `prompt` | a `permission` ticket; `allow` sets `state` `granted` and `access` by the line (`full`, or `write-only` under the write-only line alone); the read continues |
| `prefer extension contacts.contactsStatus={"access":"limited"}` | reads answer the fixture's `limited` contacts; `showContactAccessPicker` holds an `access` ticket whose `type @t c7` adds to them and announces |
| `prefer extension calendar.store="assets/other-calendar.json"` | the fixture store replaced, as a person editing elsewhere would; `calendar` announced |
| `saveEvent`, `removeEvent` | change the fixture store for the session, and announce |
| a tool-origin or wake-origin call | as production (D11) |

A ticket is retired as LLP 1133.002 §6 says. The fixture store is the
session's: a relaunch under the agent starts from the file again, so a
drive is the same on every run.

On a target with no implementation (Linux and Windows today) the declared
part answers under the agent (the statuses, `available` false;
`getContactProperties` `[]`) and every other name fails
`NotSupportedError`, as in production.

*Rejected:* a declared collection substitute the runner evaluates (a
fixture file with filter, range and cursor rules in the declaration), so
that one runner path answers every store module on every host, Linux
included. It would be the first query engine in the runner, written for
two modules before photos, health and reminders show what the shared
rules are; the implementations' fixture paths are small and the suite
holds them equal. Revisit when a third store module is written.

**Disclosure:** `state.extensions` lists each module's binding, readers
with their arguments, pages answered (counts and sizes, not values), the
fixture in use, each sheet's ticket and each answer's origin.

**Production:** none of it.

## 11. The consumer: the Calendar example

A calendar app that cannot see the person's calendar is the plainest
ceiling a hand-built one would not have: Apple's Calendar app and every
third-party one on iOS show the system's calendars. The example gains
three small features, each driving one path:

- **The person's events** beside its own. A grant line `device.calendar
  calendarPurpose` and a strings table for it (it has none). A "Show my
  calendars" switch in the inspector, shown while
  `calendarStatus().available`. While on and granted, the selected
  day's agenda adds a section of the person's events, read in Contract as
  `calendarEvents(start=day, end=day + 86400000)` with each calendar's
  colour; and the month shows a dot on each day that has one, answered
  by a Rust source, `calendarDeviceDays(month, show)`, which reads the
  six weeks shown through the generated binding, page by page, and
  answers a count per day. The month's own pages (`calendarMonths`) do
  not read the store, so they keep their kept answer and first frame; the
  dots and the section arrive when the module answers (D8). While
  `denied`, the section says so with a button that opens `app-settings:`.
  `data/src/lib.rs`' grant comment changes with it.
- **Guests from contacts.** An "Invite…" button in the editor sends
  `selectContacts(properties=["name", "email"], multiple=true)` and lists
  the picked names on the item. The guests are the app's copy (D4), kept
  in a new `guests` table of its SQLite file; existing data keeps its
  schema, as the README promises.
- **Add to Calendar.** A row action on an item sends `showEventEditor`
  with the item's title, start, duration or all-day, and notes.

It needs no write and no limited access, so the write-only line, the
limited state and `queryContacts` are driven on the conformance suite's
fixture app (`packages/*/test/fixture`) and on `apps/module-fixture`,
which drove geolocation on Android.

**Android.** The example has no Android crate, and its two input modules
are Swift (`calendar-input-root`, `calendar-drag-handle`); its drag needs
Android's hosted views to take touches (LLP 1133.008 D8 item 6). So on
Android the drives run on `apps/module-fixture`, which gains both
modules' names, and the Calendar's Android crate waits for its own
modules (§15 question 7).

**Acceptance drives,** on the web, iOS and macOS under the agent with
`--epoch 2026-09-16T12:00:00Z` (ticket ids from `state.pending`, `@p` and
`@q` standing for them):

1. `--permission calendar=prompt`; `tap show-my-calendars`; `tap @p
   allow`; `clock settle`: the agenda's section lists the fixture's
   events for 16 September, and the month dots on the fixture's days.
2. `prefer extension calendar.store="assets/other-calendar.json"`: the
   section and the dots are asked again once, and show the other store.
3. `tap invite`; `type @q c2,c5`: two guests on the item; relaunch with
   the same `--storage`: the guests are there; `tap invite`, `tap @q
   cancel`: unchanged.
4. `tap add-to-calendar`; `tap @q save`: `saved`, and with the switch on
   the event appears in the agenda's section without a tap (announced).
5. `prefer permission.calendar denied`: the denied line; the app's own
   items unchanged; `granted` again: the section returns.
6. After drive 1, relaunch with the same `--storage`: the first frame's
   `tree` shows the month and the app's own items and no section or dot;
   after `clock settle`, both.
7. On the web, `calendarStatus().available` is false: no switch;
   `getContactProperties()` is `[]` in desktop Chromium: no "Invite…"; Add
   to Calendar downloads an `.ics` whose `VEVENT` the suite parses.

And on `apps/module-fixture` and the suites' fixtures: the write-only
line (a read refused `write-only`; with both lines, a read raises); the
limited state and the access picker on iOS; key cursors across a change;
a storm of fixture changes costing at most two rounds (D7); a tool-origin
pick failing `person-required`.

**By hand**, on real devices: on an iPhone with iOS 18 or later, the
contacts prompt's limited choice, the access button and the picker; the
calendar editor and an event added in Calendar appearing in the section;
revoking in Settings and returning. On an Android 17 phone, the system's
picker with several contacts; on an Android 16 phone, the one-contact
fallback; the insert intent in the phone's calendar app.

## 12. What this amends

- **LLP 1133.002 D8:** an extra permission state that changes what a
  granted call answers is a shared word in the status (D5); one that
  changes only the asking stays tier 2.
- **LLP 1133.015 D16 item 4:** `"kept"` takes `"never"`, which reaches
  the answers that read the name (D8).
- **LLP 1027 D4:** an answer that read a `"kept": "never"` name is not a
  kept answer, whatever else it read.
- **LLP 1133.015 D16 items 3 and 5:** the anchor beside the window, and a
  typed sheet ticket (D13).
- **LLP 1133.001 D1:** `"kept": "never"` and a sheet's `"typed"` in a
  declaration.
- **LLP 1133.000 §3.8:** contacts' row gains Android 17's picker and
  limited access as a shared fact; calendar's gains JSCalendar's shape,
  write-only access and the system editor, with reminders out.
- **`examples/calendar`:** its README's scope and its grant comment.

## 13. What stays out

Each until a consumer asks:

- writing contacts, groups and containers; the system's contact card and
  its new-contact editor;
- recurrence written or edited by span; alarms; attendees; reminders
  (reachable now through the `EKEventStore` hatch, under the app's own
  usage string);
- a change history or batch protocol for a sync engine (D6);
- delivery while the app is closed (D7), with the background module;
- an app's own calendar account as a sync adapter; subscribed calendars;
- JSCalendar 2.0's changes, until it is an RFC;
- the tvOS, visionOS, watchOS, Windows and Linux cells (D15).

## 15. Questions for Charlie

1. **No answer that read either store is kept** (D8), at the cost of a
   placeholder for those resources until the module answers.
   *Recommended: yes (85%).* The alternative writes the person's data to
   disk without the author asking and shows it after a revocation.
2. **A state that changes what a granted read answers is a shared word**
   (D5), amending LLP 1133.002 D8, with write-only refusing reads rather
   than answering empty. *Recommended: yes (80%).*
3. **A pick is a copy with no id and needs no grant line** (D4).
   *Recommended: yes (85%).*
4. **Write-only on Android as a ceiling the module keeps** over both
   calendar permissions (D11). *Recommended: yes (70%); the alternative,
   write-only absent on Android, leaves a portable "add silently" with no
   Android path, and Android's dialog is the same either way.*
5. **The implementation as its own substitute, over a fixture file**
   (§10), not a declared collection the runner evaluates. *Recommended:
   yes (70%), revisited at the third store module.*
6. **The web's and the Mac's editor is an `.ics` file** (D15).
   *Recommended: yes (70%); on the Mac a portable app that wants no tell
   declares write-only and saves.*
7. **The consumer is the Calendar example** (§11), with Android driven on
   `apps/module-fixture` until the example's own modules reach Android.
   *Recommended: yes (75%).*
8. **A tool may read the stores and write the calendar under the app's
   grant** (D11), as it may read a granted position. *Recommended: yes
   (65%); the alternative, `"origin": "app"` on `saveEvent` and
   `removeEvent`, would forbid the "add this to my calendar" an
   assistant's tool exists for, before LLP 1111 has a delegation rule to
   narrow it.*
9. **`rules/DEFERRED.md`:** an "Expanded" record for contacts and
   calendar, with the take named or waived. *Recommended: no take, as the
   wave's other modules were ruled; the record names §13's list as still
   out.*
