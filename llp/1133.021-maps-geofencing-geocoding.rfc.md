## Summary

Three modules of LLP 1133.000's wave 3, written as one RFC because they
share a coordinate, a permission and a consumer path: a place is found
(geocoding), shown (maps), and watched (geofencing).

**`@exact/maps`** is a package view, `exact-map`: MapKit on iOS, macOS
and tvOS, the Maps SDK for Android, and on the web the raster tiles an
app names, drawn by the package. The web has no map standard, so tier 1
takes the words every web map library shares (a centre, a Web Mercator
`zoom`, markers, `moveend`); rotation and tilt are the platforms' words. It replaces
`apps/map-demo`'s own native module.

```
use MapCamera, MapMarker from "@exact/maps"

component Stores
  state zoom = 15
  state selected = ""
  action pick(id: string)
    selected = id
  action moved(c: MapCamera)
    zoom = c.zoom
  view
    exact-map latitude=37.7946 longitude=-122.4040 zoom=zoom
        markers=[{id: "ferry", latitude: 37.7955, longitude: -122.3937, title: "Ferry Building"}]
        selected=selected change=pick moveend=moved aria-label="Map of stores"
```

**`@exact/geocoding`** turns an address into places and a coordinate into
places: MapKit's geocoding requests on Apple (Core Location's
`CLGeocoder` before 26), the platform's `Geocoder` on Android. The web,
Linux and Windows have no platform geocoder, and the module says so
(`available` false) rather than send the person's position to a service
the app did not choose. Weatherlight names the city it is following.

```
use reverseGeocode, Place from "@exact/geocoding"

mutation named as shape Place[] then labelled
action arrived
  …
  send named = reverseGeocode(latitude=p.coords.latitude, longitude=p.coords.longitude)
```

**`@exact/geofencing`** keeps circular regions the platform watches while
the app is closed, and wakes the app when the device enters or leaves
one: `CLMonitor` on iOS (a launch) and macOS (while running), Play
services' geofencing on Android. The names are the W3C Geofencing API's
(`geofenceenter`, `geofenceleave`, a circular region's `latitude`,
`longitude`, `radius`); since no browser shipped it, the web cell is
absent and the module is a declared deviation. Its events are LLP
1133.017 wake events, raised by a region carrier the host keeps, into a
session the host boots with no view. It needs background location
("Always" on Apple, "Allow all the time" on Android), a grant line beyond
geolocation's. Caltrain gains "Next trains when I arrive".

```
use addGeofence, removeGeofence, geofences, Geofence, GeofenceEvent from "@exact/geofencing"

resource fences = geofences() as shape Geofence[] else empty()
mutation watched as shape Geofence

action notifyOnArrival(s: Station)
  send watched = addGeofence(name="station:" + s.id, latitude=s.lat, longitude=s.lon, radius=200)
action geofenceenter(e: GeofenceEvent)
  send told = arrivalNotice(e.geofence.name, e.timestamp)
```

What this needs of the seams, and proposes for ruling (§9): typed and
list props on a package view, declared events with typed arguments, and
parts the agent can tap; Android hosted views that take touches (LLP
1133.008 D8 item 6, accepted and not built); a region carrier the host
keeps on Apple and a package's own receivers over a store the host
keeps on Android, in LLP 1133.017 D8's shape; Android's headless
session, which
LLP 1133.017 D7 ruled and its stage 3 did not build; a permission that
requires another; package configuration in `app.json`; and a data-code
answerless send that settles from the implementation's reply, which LLP
1133.004 specifies and its stage 0 did not build.

## 0. What is new here

1. **A view package with no device.** Camera's view (LLP 1133.008) shows
   a track; a map shows the network's tiles and the platform's map data.
   It needs no permission, and its substitute is the implementation itself
   drawing deterministic tiles (§12).
2. **A package view with record props and its own event.** Until now a
   package view's props are strings and its events are the element's nine
   (`ExactPackageEvents`). A map's markers are a list and its camera is a
   record; `moveend` is an event no element has.
3. **The first module that wakes the app for a reason other than time.**
   LLP 1133.017 D9 named geofencing among the modules that would declare
   wake events "and add, where it needs one, an entry point the host
   keeps". This is that entry point: a region carrier.
4. **Background location as a grant.** LLP 1133.002 asked for none, and
   its D12 table says a wake's `watchPosition` fails
   `POSITION_UNAVAILABLE`. Geofencing still reads no position: the
   platform watches the regions, and the app hears only that a boundary
   was crossed. But both platforms grant that only to an app with
   background location, so the grant is new (D13).
5. **A module whose web cell is absent by design.** Geocoding on the web
   would mean exact2 choosing a third party to receive the person's
   position; the module refuses that choice (D7).

## 1. What exists

**`apps/map-demo`** is a store map: four pins, a selected one, buttons
that select a pin without the map, and on a TV, where there is no pinch,
zoom buttons. Its map is the app's own native module, `native-map`
(LLP 1024): `modules/apple/NativeMap.swift` (an `MKMapView`, its pins
reused as `MKMarkerAnnotationView`s, a snapshot by `MKMapSnapshotter`
for the agent, no rotation or pitch on tvOS) and `modules/web/index.js`
(OpenStreetMap's raster tiles from `tile.openstreetmap.org`, Web Mercator
projection, pins as buttons, drag and wheel, the attribution). Pins are
one string prop, `id|latitude|longitude|title` joined with `;`; the span
is degrees of latitude; `change` says which pin was selected. It has no
Android crate. Its Linux crate builds, and the Linux host draws nothing in a
native view's box (`host/linux/src/paint/native.rs`). Its zoom
buttons halve and double the app's `span`, which a person's pinch does
not change, so after a pinch the next button press jumps back.

**Package views** (LLP 1133.008 D8 items 1 and 2, built): an interface
declares each tag with its props, events and `displayed`; Apple's
implementation serves `view(_:id:props:events:)` returning an
`ExactPackageView` whose `setProps` takes `[String: String]`; events are
`ExactPackageEvents`' nine (`press`, `change`, `hover`, `focus`, `blur`,
`key`, `submit`, `load`, `message`) and an intrinsic size; Android's
extension builds its own hosted views, which take `performClick()` only
(`host/android/README.md`); the bake does not yet check props or events.

**Geolocation** (LLP 1133.002, built): `@exact/geolocation` with
`device.geolocation` and `device.geolocation-approximate`, the permission
`geolocation`, `geolocationStatus()`, the one-request queue, origins and
tickets. Weatherlight follows the person's position with the approximate
line and labels it "Current location"; its city search is Open-Meteo's
geocoding API over `net.fetch`.

**Wakes** (LLP 1133.017, built on iOS and macOS): wake events
(`"raised": "wake"`, a `budget`), origin `wake`, one invocation at a time,
D6's refusals, the host's store of wake requests and `woke(_:)`, the
headless boot on iOS, `context.wake(name, args, id:, ended:)`, the
declared list with a tap that raises a wake (`state.backgroundSync`),
`--wake` for a cold wake. On Android the worker is the package's, not
the host's, and **no headless session exists**: a worker that runs with
no activity finds no session.

**Notifications.** Harmony posts through the built-in `showNotification`
on Apple and on the web while the page is open; `@exact/notifications`
is not built, and Android has no notification path.

**Caltrain** answers its board from Rust data (`board(stationId,
direction, nowMs)`), knows every station's coordinate, and reads no
position today: its location is `defaultLocation()`.

## Part I — `@exact/maps`

## 2. Tier 1

### D1 — `exact-map`, by the web map libraries' words

No W3C or WHATWG document specifies a map. The words below are the ones
the web's map libraries share, so a web developer reads them without a
glossary: Leaflet, MapLibre GL JS and Google's Maps JavaScript API all
place a camera by a centre and a `zoom`, and raise an event when it has
settled (Leaflet and MapLibre `moveend`, Google `idle`). It is a declared
deviation (LLP 1133 D1): exact2's own element name, `exact-map`, on the
pattern of `exact-camera`.

**Rotation and tilt are tier 2.** A raster tile is drawn north-up and
flat, so the web cell cannot rotate or pitch the camera without turning
its labels with it, and tvOS's map does neither. A tier 1 `heading` that
the web ignored would make `moveend` report one camera while the prop
said another. So tier 1 is what every cell can keep: a centre and a zoom.
MapKit's and the Maps SDK's rotation and tilt are their platforms' words
(D4), and the person's own rotate and pitch gestures stay on where the
platform has them (D2).

**Props:**

| Prop | Type | Meaning |
|---|---|---|
| `latitude`, `longitude` | `number` | the camera's centre, degrees (WGS 84) |
| `zoom` | `option<number>` | Web Mercator zoom: at zoom *z* the world is 256 × 2^*z* points wide, as Google defines it for both its web and Android maps ([camera and view](https://developers.google.com/maps/documentation/android-sdk/views#zoom)); unsaid, 12 |
| `markers` | `option<MapMarker[]>` | `{id: string, latitude: number, longitude: number, title: option<string>}` |
| `selected` | `option<string>` | the selected marker's `id`, `""` for none |

**Events:**

| Event | Argument | When |
|---|---|---|
| `change` | `string`: the selected marker's `id`, or `""` | the person selects or deselects a marker (not when `selected` is written) |
| `moveend` | `MapCamera` `{latitude, longitude, zoom, apple, android}` | the camera has stopped moving, whoever moved it |

**A camera prop moves the map when its value changes.** The person's pan,
pinch or rotation is not undone by a prop that did not change, as a
hand-built map keeps the person's camera; writing a new value moves the
map there, animated as the platform animates a programmatic move. Only
the props whose values changed are applied: a new `zoom` zooms about the
camera's current centre, wherever the person panned it, and a new value
equal to the camera's current one moves nothing, so an app that writes
back what `moveend` reported does not jolt the map. An app that wants to
start from where the person is reads `moveend` (map-demo's zoom buttons,
§13). This is a declared deviation from Contract's
controlled props, stated in the interface, because a map whose every
gesture the app must echo would fight the person at 60 Hz.

**Markers** are the platform's own: an `MKMarkerAnnotationView` on Apple
(red balloon, title below), a default `Marker` on Android, a pin on the
web. Each is an accessibility element labelled by its `title`, as each
platform's map makes them. Selecting one is the platform's gesture (a
tap, a click, a remote's select on tvOS); the selected marker is the
platform's selected annotation.

**Accessibility.** `aria-label` names the map; the markers are its
children in the accessibility tree, in `markers` order. A map is a hard
thing to use without sight, so the recipe asks that every action a map
offers also exist outside it, as map-demo's buttons do.

### D2 — Unsaid defaults are the platform's

| Unsaid | Apple | Android | web |
|---|---|---|---|
| map style | `MKStandardMapConfiguration` with the system's appearance (dark in Dark Mode) | Google's normal map, following the system's dark theme where the SDK does | the app's tile source (D3) |
| points of interest, traffic, buildings | MapKit's defaults | the SDK's defaults | whatever the tiles draw |
| controls | compass when rotated, scale while zooming, as `MKMapView` shows them | the SDK's zoom-control and compass defaults | the package's zoom buttons (no platform has an opinion) |
| gestures | pan, pinch, rotate, pitch (none of rotate or pitch on tvOS) | pan, pinch, rotate, tilt | drag, wheel, pinch, keyboard arrows and `+`/`-` |
| attribution | MapKit's legal label | Google's logo | the source's attribution, bottom right (D3) |
| marker colour | MapKit's red | Google's red | the package's red pin |

### D3 — The web's tiles are the app's to name

The web has no platform map service. A hand-built web app chooses one:
Google's or Apple's (both need a key from the developer's account), a
paid tile host, or OpenStreetMap's community servers. exact2 does not
choose for every app, because the choice carries a policy the app must
keep. OpenStreetMap's servers ask a distinct identifying User-Agent, a
valid Referer from web pages, a visible attribution, cached tiles honoured
for at least seven days, no bulk or offline download, and they may block
heavy users ([tile usage policy](https://operations.osmfoundation.org/policies/tiles/));
a framework that defaults every app to them spends that goodwill on apps
whose authors never read it.

So the web implementation draws raster tiles from a source the app names
in `app.json`, the package configuration this RFC adds (§9 item 7):

```json
"packages": {
  "@exact/maps": {
    "web": {
      "tiles": "https://tile.openstreetmap.org/{z}/{x}/{y}.png",
      "attribution": "© OpenStreetMap contributors",
      "maxZoom": 19
    }
  }
}
```

An app with no `tiles` fails the web build (`maps-tiles-missing`, naming
the key), so no map ships showing grey squares. The package draws XYZ
tiles in Web Mercator ([slippy map tilenames](https://wiki.openstreetmap.org/wiki/Slippy_map_tilenames)),
which is map-demo's `index.js` made a package: the browser fetches each
tile as an image, with the page's own Referer and the browser's
User-Agent, and its HTTP cache keeps them. map-demo keeps OpenStreetMap,
its own choice, with its attribution.

## 3. Tier 2, tier 3 and the ceiling

### D4 — The platforms' words

Each implementation adds options under its platform's key (LLP 1133 D2),
named as the platform names them:

- **The camera.** `apple.heading` and `apple.pitch` (`MKMapCamera`'s, iOS
  and macOS; tvOS keeps 0), `android.bearing` and `android.tilt`
  (`CameraPosition`'s), each a prop and each reported in `moveend`'s
  `apple` or `android` record.
- **`apple.`** `mapType` (`MKMapType`'s `standard`, `satellite`,
  `hybrid`, `mutedStandard`), `pointOfInterestFilter` (categories, by
  `MKPointOfInterestCategory` names), `showsTraffic`, `emphasisStyle`
  (`MKStandardMapConfiguration`, iOS 16, macOS 13, tvOS 16,
  [MKStandardMapConfiguration](https://developer.apple.com/documentation/mapkit/mkstandardmapconfiguration)),
  and per marker `apple.markerTintColor`, `apple.glyphText`
  ([MKMarkerAnnotationView](https://developer.apple.com/documentation/mapkit/mkmarkerannotationview)).
- **`android.`** `mapType` (`GoogleMap`'s `normal`, `satellite`, `hybrid`,
  `terrain`), `mapId` (a cloud style), and per marker `android.snippet`,
  `android.hue`.

Look Around (`MKLookAroundViewController`, iOS 16 and macOS 13, not tvOS),
overlays and the person's own location are tier 2 or later, each when a
consumer asks (§11).

### D5 — Access hatches

| Target | Object | Moment | The module owns |
|---|---|---|---|
| Apple | the `MKMapView` | after the view is made and each time props are applied | `delegate`, the annotations it added, `region`/`camera` while a prop move is in flight; the app may set the rest (`preferredConfiguration`, overlays it adds itself) |
| Android | the `GoogleMap` | at `onMapReady`, after the module's own setup | the marker click and camera-idle listeners, the markers it added |
| web | none: the package's own drawing | — | — |

### The ceiling test

A hand-built iOS map is an `MKMapView` with annotations and a delegate;
`exact-map` is the same object, and its hatch reaches the rest. A
hand-built Android map is a `MapView` with markers; the same. What a
person who knows the platform would notice before this RFC: on Android,
no map at all (map-demo has no Android crate), and once one exists,
a map that cannot be panned until hosted views take touches (§9 item 4).

## Part II — `@exact/geocoding`

## 4. Tier 1

### D6 — The names, a declared deviation

The web has no geocoder. The names are the roster's and every platform's
verbs:

| Name | Kind | Arguments | Answers |
|---|---|---|---|
| `geocode` | send | `address: string` | `Place[]` |
| `reverseGeocode` | send | `latitude: number`, `longitude: number` | `Place[]` |
| `geocodingStatus` | source, live | — | `{available: bool}` |

Both are sends, not sources, because both platforms ration them: Apple
asks for "at most one geocoding request for any one user action" and
"not more than one" a minute for a moving device
([CLGeocoder](https://developer.apple.com/documentation/corelocation/clgeocoder)),
and a resource re-asked on every invalidation would break that without
the app seeing why. Data code calls both in Promise form (LLP 1133.002
D13).

**`Place`:**

| Field | Type | Apple (26 and later) | Android |
|---|---|---|---|
| `latitude`, `longitude` | `number` | `MKMapItem.location` | `Address.getLatitude`, `getLongitude` |
| `name` | `option<string>` | `MKMapItem.name` | `getFeatureName` |
| `fullAddress` | `option<string>` | `MKAddress.fullAddress` | the address lines, joined by `", "` |
| `city` | `option<string>` | `MKAddressRepresentations.cityName` | `getLocality` |
| `countryCode` | `option<string>` | `MKAddressRepresentations.regionCode` | `getCountryCode` |
| `country` | `option<string>` | `MKAddressRepresentations.regionName` | `getCountryName` |
| `apple` | `option<ApplePlace>` | `shortAddress`, `cityWithContext` | — |
| `android` | `option<AndroidPlace>` | — | `adminArea`, `subAdminArea`, `subLocality`, `thoroughfare`, `subThoroughfare`, `postalCode` |

Structured street fields are Android's tier 2, not tier 1, because Apple
no longer offers them: `MKPlacemark` and `MKMapItem.placemark` are
deprecated in 26.0 in favour of `MKAddress` and
`MKAddressRepresentations`, which carry formatted strings, a city and a
region ([MKAddressRepresentations](https://developer.apple.com/documentation/mapkit/mkaddressrepresentations)),
and `CLPlacemark`'s properties are deprecated in 27.2
([CLPlacemark](https://developer.apple.com/documentation/corelocation/clplacemark)).
A tier 1 that promised a postal code would be a promise Apple's current
API does not keep.

**Before 26 on Apple** (every app here targets iOS 17 and macOS 14),
`CLGeocoder`, deprecated in 26.0 ("Use MapKit"), answers instead, and the
same fields come from its `CLPlacemark` (`name`, `locality`,
`isoCountryCode`, `country`, the formatted postal address). Both paths
are the platform's; the implementation picks by `#available`.

### D7 — Where there is no platform geocoder, there is no geocoder

On the web, Linux and Windows `geocodingStatus().available` is false and
both sends fail `NotSupportedError`. A hand-built web app geocodes through
a service whose terms its author accepted (Google's, Apple's, a paid one,
OpenStreetMap's Nominatim); Nominatim's own policy allows at most one
request a second, forbids autocomplete, and asks that it not be built into
platforms as their generic geocoder
([Nominatim usage policy](https://operations.osmfoundation.org/policies/nominatim/)).
An app that wants a web geocoder calls its chosen service with `fetch`
under its own `net.fetch` grant, as Weatherlight already does for its
city search. Windows' platform geocoder, `MapLocationFinder`, is
deprecated with the Bing Maps service behind it
([MapLocationFinder](https://learn.microsoft.com/uwp/api/windows.services.maps.maplocationfinder)),
and Linux's Location portal answers positions only
([Location portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Location.html)).

### D8 — Limits, failures and unsaid defaults

- **Results.** Apple answers its items; Android's `Geocoder` is asked for
  5 results to `geocode` and 1 to `reverseGeocode`, within Google's advice
  of 1 to 5 ([Geocoder](https://developer.android.com/reference/android/location/Geocoder));
  `android.maxResults` overrides. No match answers `[]`, not a failure.
- **Language.** The device's locale, as each platform defaults;
  `apple.preferredLocale` and `android.locale` override.
- **Failures,** with DOMException's names: `NotSupportedError` (absent, or
  Android's `Geocoder.isPresent()` false), `NetworkError` (no connection;
  both platforms reach a server), `QuotaExceededError` (Apple's
  `CLError.network` throttling, MapKit's `MKError.loadingThrottled`),
  `AbortError` (a superseded mutation cancels the request:
  `MKGeocodingRequest.cancel()`, `CLGeocoder.cancelGeocode()`; Android's
  listener answer is dropped).
- **Android.** API 33 and later use the listener forms
  (`getFromLocation(…, GeocodeListener)`); before 33 the synchronous form,
  deprecated in 33, runs off the main thread, since it "may hit the
  network".

### D9 — Tier 2 and tier 3

`apple.` and `android.` fields of D6; Apple's `MKGeocodingRequest.region`
as `apple.region` (a hint for which match wins) when a consumer asks.
Hatches: none. A geocoder request has nothing the app needs to touch
that its options do not reach.

**Permission.** None: neither platform asks the person, and a hand-built
app declares nothing. What it sends to Apple or Google is the app's to
say in its store privacy answers; the recipe says so.

## Part III — `@exact/geofencing`

## 5. Tier 1

### D10 — The W3C Geofencing API's names, a declared deviation

The W3C's Geofencing API is a Working Group Note no browser ships
([Geofencing API](https://www.w3.org/TR/geofencing/)), so the web lacks
the capability and the module is a declared deviation. Its words are
still the nearest the web came, and they are better than a coined
`watchRegion` (the roster's sketch), which reads as a live source like
`watchPosition` when a geofence is the opposite: it outlives the app.
So: a circular region's `latitude`, `longitude` and `radius`; the events
`geofenceenter` and `geofenceleave`; a list of the app's geofences.

| Name | Kind | Arguments | Answers |
|---|---|---|---|
| `addGeofence` | send, `request: when-prompt` | `name: string`, `latitude: number`, `longitude: number`, `radius: number` (metres, `min` 100) | `Geofence` |
| `removeGeofence` | send, answerless | `name: string` | — |
| `geofences` | source, live | — | `Geofence[]` |
| `geofencingStatus` | source, live | — | `GeofencingStatus` |
| `geofenceenter`, `geofenceleave` | events on the root, `"raised": "wake"`, `budget` 30 000 ms, `hold` 16 | `GeofenceEvent` | — |

`Geofence` is `{name, latitude, longitude, radius, inside: option<bool>}`;
`inside` is the last state the platform reported, `none` until it has.
`GeofenceEvent` is `{geofence: Geofence, timestamp: number, android:
option<AndroidGeofenceEvent>}` (the triggering location, Android's only).
No tier 1 field carries a position: Apple's `CLMonitor` event names a
condition, a state and a date, not a fix, so a position in the event
would be Android's alone.

**Deviation from the Note:** the Note's `Geofence` has an `id` the user
agent assigns and a `name` the page gives. Here `name` is the key, unique
per app: re-adding a name replaces its region. A wake must find the
geofence it is about after the process that added it is gone, and both
platforms key regions by the app's string (`CLMonitor`'s identifier,
Android's request id).

### D11 — What a geofence is

- **Circular only,** as the Note's one region type, Apple's
  `CLMonitor.CircularGeographicCondition` and Android's `Geofence`.
- **Twenty per app, on every target.** Core Location "prevents any single
  app from monitoring more than 20 conditions of any type simultaneously"
  ([Apple](https://developer.apple.com/documentation/corelocation/monitoring-the-user-s-proximity-to-geographic-regions));
  Android allows 100 ([geofencing](https://developer.android.com/develop/sensors-and-location/location/geofencing)).
  The lower limit is tier 1, so an app does not lose fences moving to
  iOS: the 21st `addGeofence` fails `QuotaExceededError`, and
  `android.limit` raises it to 100 on Android.
- **At least 100 metres.** Android recommends a radius of 100 to 150 m
  for reliable results (the same page). A literal below 100 is refused at
  bake (`contract-module-bound`, as LLP 1133.017's interval floor is); a
  computed one is raised to 100 with a journal line.
- **A fence added while the device is inside raises `geofenceenter`**
  once the platform knows: Android's `INITIAL_TRIGGER_ENTER`, Apple's first
  event of the condition with state `satisfied` (an initial state is
  `unknown`). An app
  that asks to be told on arrival while already there wants to be told.
- **Late, not instant.** Android delivers background transitions "every
  couple of minutes" (the same page); Apple promises no latency. The
  recipe says a geofence is for "around here", not for a doorway.
- **Collapsed while undelivered.** The host keeps one undelivered
  transition per fence, the latest (D14): an enter and a leave that both
  happened while the app could not run deliver the leave, with its time.
- **Dwell** (Android's `GEOFENCE_TRANSITION_DWELL`) is Android's tier 2,
  `android.loiteringDelay`, which raises `geofenceenter` after the delay
  instead of at entry; Apple has no equivalent.

### D12 — Unsaid defaults are the platform's

The platform watches with the power it chooses: Apple's region
monitoring and Google's geofencing both trade latency for battery, and
neither takes an accuracy option. exact2 starts no location updates to
make a fence faster; a hand-built app does not either.

## 6. Permission

### D13 — LLP 1133.002 §4, with background location

**Declare.** A new grant line, `device.geolocation-background
purposeKey`, which requires `device.geolocation` (refused at bake
otherwise by LLP 1133.033 D3's `grant-needs`, naming the line) and is refused beside
`device.geolocation-approximate` (`grant-conflict`):

| Target | Derived | Why |
|---|---|---|
| iOS | `NSLocationAlwaysAndWhenInUseUsageDescription` from its purpose, beside `device.geolocation`'s `NSLocationWhenInUseUsageDescription` | `requestAlwaysAuthorization()` needs both keys ([Apple](https://developer.apple.com/documentation/corelocation/cllocationmanager/requestalwaysauthorization())) |
| macOS | `device.geolocation`'s keys (LLP 1133.002 D6) | a Mac app's location authorization is one grant; the stage confirms the Always request asks nothing more |
| Android | `ACCESS_BACKGROUND_LOCATION`, beside `ACCESS_FINE_LOCATION` and `ACCESS_COARSE_LOCATION`; and `RECEIVE_BOOT_COMPLETED` for the package's boot receiver (D14) | Android's geofencing needs fine and, from API 29, background location ([geofencing](https://developer.android.com/develop/sensors-and-location/location/geofencing)) |
| web | nothing | absent |

Approximate is refused because neither platform watches regions under
it: with reduced accuracy "your app can't use region monitoring"
([CLAccuracyAuthorization.reducedAccuracy](https://developer.apple.com/documentation/corelocation/claccuracyauthorization/reducedaccuracy)),
and Android's geofencing requires `ACCESS_FINE_LOCATION`. An app that
asked for approximate positions and wants a fence has asked for two
things the platforms will not give together; the bake says so rather
than the fence failing on a device.

The line is in `grantCeiling`, so adding it is a binary change (LLP
1069.008 D5).

**Read.** `geofencingStatus()` answers `{available, state, apple,
android}` with LLP 1133.002 D8's states. The permission is
`geolocation-background`; its state is:

| Platform | `state` |
|---|---|
| Apple `authorizedAlways` with full accuracy | `granted` (provisional Always included, below) |
| Apple `notDetermined`; or `authorizedWhenInUse` and the Always request not yet made | `prompt` |
| Apple `authorizedWhenInUse` after the Always request was made; `denied`; `restricted`; reduced accuracy | `denied`, with `apple.authorization` and `apple.accuracyAuthorization` naming which |
| Android fine and background granted | `granted` |
| Android background not granted, and a request could still show the dialog or the settings page | `prompt` |
| Android background permanently denied, or fine denied (LLP 1133.002 D8's history) | `denied` |
| web, tvOS | `available` false, `state` `unknown` |

Apple's "the Always request was made" is a history the implementation
keeps in its preferences, as LLP 1133.002 D8 keeps Android's, because
"Core Location limits calls to" it: "After your app calls this method,
further calls have no effect" (`requestAlwaysAuthorization()`). The state
is read again at `locationManagerDidChangeAuthorization` and, on Android,
at `onResume`.

**Ask.** `addGeofence` asks when the state is `prompt` (`request:
when-prompt`), from a foreground origin, through the one-request queue
(LLP 1133.002 D9), as one queued request. What it calls is each
platform's own sequence, not geolocation's request followed by another:
on Apple one call, `requestAlwaysAuthorization()`, whatever
`geolocation`'s state; on Android two decisions in order. Calling
geolocation's `requestWhenInUseAuthorization()` first on iOS would spend
provisional Always, the path by which a closed app can first hear an
event, on an immediate upgrade prompt whose decline sticks.

- **iOS, from `notDetermined`:** `requestAlwaysAuthorization()` shows the
  When In Use dialog at once; "Allow While Using App" grants "a
  Provisional Always authorization", and a second prompt "displays when
  Core Location prepares to deliver an event to your app", "typically …
  when your app isn't running" (the same page). The state reads `granted`
  between the two, and a fence's first event may never reach the app if
  the person then keeps When In Use; the next read says `denied`. This is
  Apple's design and the module does not hide it.
- **iOS, from When In Use** (an app that asked for geolocation before):
  the same call "immediately prompts the user to request Always
  permission".
- **Android:** fine and coarse first, if not granted (LLP 1133.002 D9);
  then `ACCESS_BACKGROUND_LOCATION` alone, since a request for both at
  once on Android 11 and later is ignored; there the request opens the
  app's location settings page rather than a dialog, where the person
  chooses "Allow all the time"
  ([background location](https://developer.android.com/develop/sensors-and-location/location/permissions/background)).
  The request settles when the activity resumes and the permission is
  read again. `android.backgroundPermissionOptionLabel`
  (`PackageManager.getBackgroundPermissionOptionLabel()`, API 30) is in
  the status, so the app's own explanation names the option in the
  device's words, as Android asks apps to do.

- **macOS:** `requestAlwaysAuthorization()`, one decision.

On Android a request whose first step is denied fails
`PERMISSION_DENIED` without the second. `geolocation`'s state is the same permission
`@exact/geolocation` reads: the two modules share it, and a change one
causes is announced to both readers (LLP 1133.002 D8).

**Explain and recover** as LLP 1133.002 D11: the app's own screen, the
purpose on Apple's prompt, `openURL("app-settings:")`.

**Origin** (LLP 1133.002 D12):

| Origin | `addGeofence`, `granted` | `addGeofence`, `prompt` | `removeGeofence`, the reads |
|---|---|---|---|
| a person's input; the app's own code, foreground | proceeds | asks | proceeds |
| a tool invocation | proceeds under the app's grant | fails `person-required` | proceeds |
| a wake | proceeds (re-arming a fence from its own event is common) | fails `person-required` | proceeds |
| the development agent | §12 | §12 | §12 |

A tool may add a fence: it shows nothing and reaches no position, and
the person granted background location to the app. LLP 1133.002 D12's
direction narrows it when delegation is written.

## 7. Wakes

### D14 — The region carrier, kept by the host

LLP 1133.017 D8's reasons hold here, and harder. On iOS, a relaunch for a
region event must "recreate the monitor with the same identifier"
([Apple](https://developer.apple.com/documentation/corelocation/monitoring-the-user-s-proximity-to-geographic-regions)),
and a `CLServiceSession` held for Always "immediately upon launch in the
background"
([background updates](https://developer.apple.com/documentation/corelocation/handling-location-updates-in-the-background)),
before a package's Swift loads with the app's module after first pixel.
So on Apple the host keeps the entry point and parses the platform's
event, as it keeps the transfer carrier (LLP 1133.017 D8, D10).

On Android the split is the other way, as LLP 1133.017's Android worker
already is (its §14 stage 3: "the worker is the package's"). A geofence
broadcast can be read only through Play services
(`GeofencingEvent.fromIntent`), which the host's Canvas library does not
link and must not, or every app's graph would carry it. A package's
Kotlin compiles into the app module beside its Maven libraries
(`host/android/app/build.gradle.kts`, `-PextensionDirs`, `-Pmaven`), so
the receiver is the package's own class, and what the package cannot do
alone is declare it: the implementation's `exact.json` names its
receivers, and the build writes them into the manifest it already
derives from grant lines (§9 item 5). What the host keeps on Android is
the store, which a receiver reaches with no session, and the wake that
delivers the store's transitions into a session.

The context gains `context.regions`, which a third party's region module
reaches the same way:

| Platform | What the host keeps | A package asks |
|---|---|---|
| iOS | one `CLMonitor` named `<bundle id>.regions` and, from iOS 18, a `CLServiceSession` requiring Always, both made at `application(_:didFinishLaunchingWithOptions:)` when the host's region store is not empty, the monitor's `events` iterated for the life of the process | `context.regions.add(name, latitude, longitude, radius)`, `remove(name)`, `list()`; events reach the package through `woke(_:)` |
| macOS | the same monitor, while the process runs: "The system doesn't launch Mac apps to deliver region-related notifications" (the same page) | the same |
| Android | the region store, readable and writable from any process state through a static entry (`ExactRegions.store(context)`) with no session; the region wake, booted from a transition the store holds | the package's own receivers, declared in its `exact.json` and written into the manifest by the build. The geofence receiver (a mutable `PendingIntent`, since Play services fills it in) parses with Play services, writes the transitions to the store, then asks the host for a region wake (`ExactRegions.wake(context)`). The boot receiver only re-arms the store's fences and wakes nothing (Re-arming, below) |
| web, Linux, Windows, tvOS | none | — |

**The store is the truth.** The host keeps each fence (name, region,
`inside`, the session's label) and each undelivered transition (its kind
and time), in its own directory under the app's support files, readable
before a session boots, as LLP 1133.017 D10 keeps a transfer's record.
`geofences()` answers from it. Android needs this most: Play services has
no call that lists an app's geofences, and drops them at reboot, when the
app's data is cleared, and at `GEOFENCE_NOT_AVAILABLE` (location turned
off), after which "the app must re-register"
([geofencing](https://developer.android.com/develop/sensors-and-location/location/geofencing)).

**A transition, in order:**

1. **iOS.** The system launches the app in the background (or the running
   process hears it). The host makes the monitor again from its store
   before anything else, takes the service session, and reads the event.
   It writes the transition to the store, sets the fence's `inside`, and
   takes `beginBackgroundTask(withName:expirationHandler:)`, whose time
   bounds the wake
   ([Apple](https://developer.apple.com/documentation/uikit/uiapplication/beginbackgroundtask(withname:expirationhandler:))).
   **Android.** Play services broadcasts to the package's receiver, which
   calls `goAsync()`: a broadcast that is not a foreground one may run "for
   30 seconds or even a bit more" after it
   ([BroadcastReceiver.goAsync](https://developer.android.com/reference/android/content/BroadcastReceiver#goAsync())).
   It parses the intent (`GeofencingEvent.fromIntent`) and writes each
   transition to the store at once, before any session exists, so a
   process that dies afterwards loses nothing the store did not record;
   then it asks the host for a region wake and finishes its
   `PendingResult` when that wake ends or its time does.
2. The host starts a wake of kind `region` (LLP 1133.017 D5): it boots the
   fence's session with no view if none is live (LLP 1133.017 D7), and
   tells the package through `woke` on that session's instance, after the
   boot, as LLP 1133.017 D8 has it; the package raises `geofenceenter` or
   `geofenceleave` with `context.wake(name, args, id:, ended:)`, one
   invocation per stored transition, one at a time. A wake launch is one
   whether or not iOS connects a scene: as LLP 1133.017 §14 stage 2 found,
   a background relaunch may connect one that draws nothing, and the wake
   opens the module and delivers without waiting for a first pixel that
   will not come. On Android, until the headless session lands (§9 item
   6), a process with no session keeps the transition in the store.
3. When the invocation ends `completed`, the transition is delivered and
   deleted from the store. When it ends `expired` or `superseded`, or the
   process dies first, or (Android, for now) no session could boot, it
   stays, and is delivered when a later launch draws its first pixel
   (LLP 1133.004 D6), with its original `timestamp`. An app judges a stale arrival by that time (Caltrain
   ignores one older than ten minutes, §13).
4. The host ends the wake as LLP 1133.017 D6 says (an app that posts
   from its handler posts through a data-code answer the invocation owns,
   §13), and then ends the background task; on Android the receiver
   finishes its `PendingResult`.

**Before the device's first unlock** no wake runs (LLP 1133.017 D6), and
Apple says monitoring itself "can only occur after the user unlocks the
device after a reboot".

**Re-arming.** On Android, the package's boot receiver (`BOOT_COMPLETED`
is one of the broadcasts an app may still receive in its manifest,
[exceptions](https://developer.android.com/develop/background-work/background-tasks/broadcasts/broadcast-exceptions))
adds the store's fences again, without `INITIAL_TRIGGER_ENTER`, so a
re-arm raises nothing for a fence the device was already inside; so does
every launch. A re-arm raises no event, runs no app code and boots no
session: it is the package's Kotlin over the host's store. On Apple the
monitor keeps its conditions across launches; whether they survive a
reboot is measured (stage 2, §14), and at every launch the host adds the
store's fences the monitor's `identifiers` lack, and only those, since
adding a condition again would start its state from `unknown`.

**What is missed, declared.** A fence crossed while it is not watched is
missed: after a reboot and before a re-arm; while location services are
off, and on Android until the next launch or boot after they are turned
on again, since Play services drops the fences at
`GEOFENCE_NOT_AVAILABLE` and only a re-arm restores them (stage 3 drives
it: off, on, the app closed, then a launch); on macOS whenever the app is not running or the Mac is asleep
("condition monitoring works only while the app is running … and the
user's system is awake", the same Apple page), since `lastEvent` records
an event the app was delivered, not one that happened while nobody
listened ([Meet Core Location Monitor](https://developer.apple.com/videos/play/wwdc2023/10147/));
and, on iOS, possibly after the person force-quits the app, which stage 2
measures on a person's iPhone, since a force-quit app is not relaunched
for background transfers (LLP 1133.017 D10) and Apple's condition
monitoring page does not say. The app never hears of a crossing it
missed; a later state reaches it as the platform's next event.

**A view that arrives mid-wake** attaches to the booted session (LLP
1133.017 D7). The wake's invocation keeps its origin.

### D15 — How a geofence event reaches data code

As LLP 1133.017 D11: a Contract action on the root handles the event and
sends a mutation; data code never hears it directly. Caltrain's handler
asks its Rust data for the board at the fence's station under the wake's
origin, and posts a notification from the answer (§13).

## 9. Packaging and callers

### D18 — Three packages, all extensions

```
packages/maps/          "@exact/maps": the view, MapCamera, MapMarker; apple/ (MapKit), android/ (Maps SDK), web/ (tiles)
packages/geocoding/     "@exact/geocoding": apple/ (MapKit, CLGeocoder), android/ (Geocoder), web/ (available: false)
packages/geofencing/    "@exact/geofencing": apple/ (over context.regions), android/ (Play services location), web/ (available: false)
```

Three, not one, because each is a different cost: the map links MapKit
or the Maps SDK and a key; geocoding links nothing new on either
platform; geofencing links Play services location and adds a grant line,
a background permission and host entry points. An app that wants a
city's name should not ask for "Allow all the time". Geofencing is not
folded into `@exact/geolocation` for the same reason (§15 question 1).

**Android's libraries** join the one locked, verified Gradle graph (LLP
1133.008 D8 item 5): `com.google.android.gms:play-services-maps` and
`com.google.android.gms:play-services-location`, at the versions on
Google's Maven repository when the stage builds
([release notes](https://developers.google.com/android/guides/releases)).
Both require Google Play services on the device; on one without it the
map shows the SDK's own message and `geofencingStatus().available` is
false. Geocoding uses `android.location.Geocoder`, the platform's.

**The Maps SDK needs a key** in the manifest's
`com.google.android.geo.API_KEY` metadata
([set up](https://developers.google.com/maps/documentation/android-sdk/config)).
The key is restricted by package name and signing certificate in Google
Cloud, but Google advises keeping it out of version control, so
`app.json` names the environment variable that holds it, never the key:
`"packages": {"@exact/maps": {"android": {"apiKey": {"env":
"EXACT_GOOGLE_MAPS_API_KEY"}}}}`. A release build with the variable unset
fails (`maps-key-missing`); a development build warns and shows the SDK's
blank map. The Maps SDK's mobile map loads carry no charge
([pricing](https://developers.google.com/maps/billing-and-pricing/pricing)).

**The seam additions,** each general, each proved by an out-of-tree
fixture before a package uses it (LLP 1133.001 D8), each apparatus under
`rules/RULES.md` that lands with this ruling:

1. **Typed package-view props.** A prop declared as a record or a list
   (`MapMarker[]`) reaches the implementation as its JSON, under the
   prop's name, in the same `setProps` map; the bake checks each prop's
   type against the declaration (`contract-view-prop`), which closes
   LLP 1133.008's open "the bake does not yet check props".
2. **Declared package-view events.** A view declares events beyond the
   element's nine, with typed arguments (`{"event": "moveend", "args":
   ["MapCamera"]}`); the implementation raises one with
   `events.emit("moveend", json)` on Apple, the same on Android and the
   web; the Contract handler receives the typed record.
3. **Parts a drive can tap.** A package view answers the rectangle of a
   named part (`part(_ name: String) -> CGRect?` on Apple, `part(name)`
   on the web), so `tap map/ferry` (LLP 1075.003.000.001 §3.5) aims real
   input at the platform's own marker, and `tree` lists the parts. Where
   the host has no real-pointer carrier for parts (Android, iOS without
   `--touch platform`), the tap answers `unsupported`, as it does today.
4. **Android hosted views take touches** (LLP 1133.008 D8 item 6, ruled,
   not built): the reader forwards a pointer sequence that lands on a
   hosted view and no exact2 gesture claims to that view's
   `dispatchTouchEvent`. A map that cannot be panned is not a map, so the
   Android map stage builds it, and the camera's tap to focus gains it.
   With it, **a hosted view hears its activity's lifecycle**: Google's
   `MapView` must be told `onCreate`, `onStart`, `onResume`, `onPause`,
   `onStop`, `onDestroy`, `onSaveInstanceState` and `onLowMemory`
   ([MapView](https://developers.google.com/android/reference/com/google/android/gms/maps/MapView)),
   which the session's foreground fact and `destroy` do not carry.
5. **The region carrier** (D14): on Apple the host's monitor and service
   session; on Android the package's receivers, declared in the
   implementation's `exact.json` (`"receivers": [{"class", "actions",
   "permission"}]`) and written by the build into the manifest it derives
   from grant lines; on both, the host's region store with a sessionless
   entry, `context.regions`, the transition records and their
   redelivery, and the wake of kind `region`. An entry point is a change
   a person accepts (LLP 1133.017 D9).
6. **Android's headless session** (LLP 1133.017 D7, ruled, not built): a
   session booted on the reader's owner thread with no activity, and an
   activity attaching to it. Geofencing's Android cell needs it; until it
   lands, a transition whose process has no session is kept and
   delivered when a later launch draws (D14 step 3), which is a visible
   gap on Android, recorded in §10.
7. **Package configuration in `app.json`** under `packages.<name>.<target>`,
   declared by the interface (`"config": {"web": {"tiles": "string", …}}`),
   read at bake and written into the bundle, refused at bake when a
   declared required key is absent. LLP 1133.017 D13's
   `background-transfer.apple` words are the same thing, not yet built,
   and take this form.
8. **A permission that requires another.** An interface's `permission`
   names one it requires (`"requires": "geolocation"`), so the bake
   refuses the grant line without its base, a change to either is
   announced to both permissions' readers, and the substitute couples the
   two (§12). How the platform is asked stays the implementation's (D13:
   one call on Apple, two decisions on Android), inside one queued
   request.
9. **A tap that chooses its event by a field.** LLP 1133.004 §7's
   declared tap raises one event; a geofence's raises `geofenceenter` or
   `geofenceleave` by its entry's `inside`, and flips it:
   `"tap": {"as": "wake", "event": {"by": "inside", "false":
   "geofenceenter", "true": "geofenceleave"}}`.
10. **A data-code answerless send settles from the implementation's
    reply** on the real route, as LLP 1133.004 specifies and its stage 0
    did not build (§13): the call is the caller's owned work until the
    reply, so a wake does not end on a handoff.

beyond what it already links, no Play services, no grant line, no region
receiver. The map's package loads with the app's module after first pixel
and is never a first-frame tag (LLP 1133.008 D8 item 1); a map in the
first screen shows its box until then, and the stage measures how long
on an iPhone and a Pixel. Play services' maps and location artifacts are
measured in the APK by LLP 1047's probe when the Android stages build.
The region carrier's launch cost is a `CLMonitor` made and a store read,
only when the store is not empty; stage 2 measures it, and a geofence
wake's boot is the wake's own cost (LLP 1133.017 D18).

## 11. What stays out

- **The person's own location on the map** (`showsUserLocation`): no
  consumer; when one asks, it reads `@exact/geolocation`'s permission and
  never asks by itself.
- **Overlays** (polylines, polygons, circles), **Look Around**, **map
  snapshots** as a name (the agent's screenshot needs none), **directions**,
  **local search** (`MKLocalSearch`), **clustering**: each when a consumer
  asks.
- **Custom marker views** (a Contract subtree as a marker): it would put
  a kernel layout inside a platform view, the hardest seam there is, for
  no consumer.
- **Beacon conditions, visits and significant-change launches**: each a
  different reason to wake; each its own module over the same carrier.
- **Continuous background location** (`UIBackgroundModes` `location`, a
  foreground service on Android): no consumer, and geofencing needs none.
- **A default web tile source, a web geocoder** (D3, D7).

## 12. The substitute

**`@exact/maps`: the implementation, with plain tiles.** A map needs no
permission and no device, so the interface is `"substitute":
"implementation"` (LLP 1133.008 D8 item 9): under the agent the real
platform view runs, MapKit, the Maps SDK or the web package, with its
markers, gestures, selection and `moveend`. Its tiles are the one thing
that is not deterministic, and fetching them from a drive would be the
automated load OpenStreetMap's policy refuses. So under the agent the
implementation replaces the map's content with plain tiles, a flat colour
with a graticule each zoom's tile edges draw, through each platform's own
replacement path (`MKTileOverlay` with `canReplaceMapContent` on Apple; a
`TileOverlay` over map type `none` on Android; the package's own tiles
on the web). Screenshots are stable and offline, and every marker is
still the platform's. `prefer extension maps.tiles=live` draws the real
map, for a person reading a screenshot.

- **Parts:** each marker is a part named by its `id` (§9 item 3):
  `tap map/ferry` is real input at the marker, on the web, macOS and iOS
  with `--touch platform`.
- **`state.extensions`** lists each map's camera, its markers and the
  selected one, so an Android drive, which cannot tap a part, reads the
  selection a button made.
- **Disclosure:** the camera, the marker ids, whether tiles were plain or
  live.

**`@exact/geocoding`: declared facts.** `geocodingStatus` defaults to
`{available: true}`, except where the target is absent (LLP 1133.002 D14
step 2: a web drive reads `available` false). The sends answer from a
preferred value: `prefer extension
geocoding.reverseGeocode=[{"latitude":48.8566,"longitude":2.3522,"city":"Paris","countryCode":"FR","country":"France"}]`,
the same for `geocode`; `{"error":"NetworkError"}` fails each call with
that code; omitted `option` fields are `none`. With none preferred, a
call answers `[]` and the journal says so. `--bind geocoding` runs the
platform under the agent for the conformance suite.

**`@exact/geofencing`: declared facts and wakes,** in LLP 1133.017 §10's
shape. No geofence event fires by itself, on any `clock`.

- **Permission.** `geolocation-background` is a permission of its own,
  set by `prefer permission.geolocation-background granted|denied|prompt`
  and `--permission geolocation-background=…`, defaulting to `prompt`. It
  requires `geolocation` (§9 item 8): `granted` sets `geolocation`
  `granted` and `precise`; `geolocation` set to `prompt` or `denied` sets
  `geolocation-background` the same. An `addGeofence` while `prompt`, from
  a foreground origin, holds one `permission` ticket per decision the
  drive's target makes (D13): on iOS and macOS one, for
  `geolocation-background`, whose `allow` grants both; on Android, and on
  a target with no implementation, one for `geolocation` if that is
  `prompt`, then one for `geolocation-background`. `tap @t allow`, `deny`
  and `cancel` answer each as LLP 1133.002 §6 says, and a denied first
  ticket fails the call `PERMISSION_DENIED` with no second.
- **Fences** are listed in `state.geofences` by the declared list form
  (LLP 1133.004 §7): `{name, latitude, longitude, radius, inside, ref}`.
  `addGeofence` lists one with `inside` `none`; `removeGeofence` unlists
  it; `geofences()` answers the list. The 21st fails `QuotaExceededError`.
- **A warm wake** is `tap @<ref>`: `geofenceenter` when `inside` is not
  `true`, else `geofenceleave`, raised as a wake by the host's wake path
  (the session marked hidden, timers stopped, the invocation's origin
  `wake`), and `inside` flipped (§9 item 9). `clock settle` settles it;
  `clock +N` past 30 000 ms expires it with owned work pending.
- **A cold wake** is `--wake '<entry>'`, the entry as `state.geofences`
  printed it with an `event` field: the host boots headless through the
  same handler a region event reaches, raises the event, and attaches the
  window after the wake ends.
- **An undelivered transition** is `--wake` with `"deliver": "launch"`:
  the entry is stored as a transition and delivered after first pixel of
  a launch with a view, with its `timestamp`.
- **Not chosen:** moving the preferred position (`prefer extension
  geolocation.watchPosition=…`) across a fence's boundary to raise its
  event. It reads well, but it would make a geofence depend on a position
  the app never asked for, and the drive would need the geometry; the tap
  names the transition the drive means.

**Disclosure:** fence names, regions, `inside`, origins and outcomes.
**Production:** none of it. `--bind geofencing` runs the platform under
the agent, which the iOS simulator can drive with a simulated location
(`xcrun simctl location`, stage 2).

### Caltrain: next trains when I arrive

Caltrain's station screen gains a switch, "Next trains when I arrive". On,
it adds a 200 m geofence around the station; arriving there posts a
notification with the next departures each way, computed from Caltrain's
own schedule, as a commuter app does for a regular stop. The switch reads
the fence from `geofences()`, so the platform's list is the only state.
Off, it removes the fence. The feature is new; Caltrain asks for no
position today, and this asks for none either: the platform watches the
region, and the app hears only the arrival.

```
use addGeofence, removeGeofence, geofences, geofencingStatus,
  Geofence, GeofenceEvent, GeofencingStatus from "@exact/geofencing"
use requestNotificationPermission, NotificationStatus from "@exact/notifications"
…
  resource fences = geofences() as shape Geofence[] else empty()
  resource fencing = geofencingStatus() as shape GeofencingStatus else empty()
  mutation asked as shape NotificationStatus then fence
  mutation watched as shape Geofence
  mutation told as shape ArrivalNotice
  state arriving = ""
  state arrivingLat = 0
  state arrivingLon = 0
  // The person's press asks for notifications first: a wake may post only
  // under a grant it already has (LLP 1133.017 D6), and asks nothing.
  action arriveOn(s: Station)
    arriving = s.id
    arrivingLat = s.lat
    arrivingLon = s.lon
    send asked = requestNotificationPermission()
  action fence
    match asked
      case some(n)
        if n.state == "granted"
          send watched = addGeofence(name="station:" + arriving, latitude=arrivingLat, longitude=arrivingLon, radius=200)
      case none
        arriving = arriving
  action arriveOff(s: Station)
    removeGeofence(name="station:" + s.id)
  // Data code posts and answers once the platform has the post, so the
  // wake's invocation owns the post until it lands.
  action geofenceenter(e: GeofenceEvent)
    send told = arrivalNotice(e.geofence.name, e.timestamp)
```

`Station` gains `lat` and `lon`, which the data crate already holds for
every station (`apps/caltrain/data/src/lib.rs`). `arrivalNotice` is Rust
data, a mutation's source: it reads the station from the fence's name;
if the event is more than ten minutes old (a transition delivered at a
later launch, D14) it answers `{posted: false}` at once; otherwise it
takes the next two departures each way from `board` at the current time
(the event's time decides freshness, never which trains are shown), and
answers `Answer::Later` with `@exact/notifications`' `showNotification`
request, through the binding Rust data code already has for a module
name (`data/src/modules.rs`), parsing the platform's acceptance into
`{posted: true}`. So the post is the mutation's answer, which the wake's
invocation owns, and the wake does not end while the post is in flight
(LLP 1133.017 D6's "done"). In a wake, the post is admitted only while
notifications are `granted`; otherwise it fails without asking (LLP
1133.004 §6, origins), and the answer says so. Its grants gain `device.geolocation
purpose.location`, `device.geolocation-background purpose.arrival` and
`device.notifications purpose.notifications`. While `fencing.state` is
`denied` the switch is off with "Allow location all the time in Settings
to use this" and an Open Settings button (LLP 1133.002 D11). Where
`fencing.available` is false (the web, tvOS, Linux, Windows) the switch is
not shown.

**Notifications are `@exact/notifications`** (LLP 1133.004, accepted;
its stage 1, web, macOS and iOS, is owed and not built), because the
built-in `showNotification` asks for authorization when it posts
(`host/apple/Sources/ExactKit/Notify.swift`), and a wake cannot ask: on a
fresh install the first arrival would be lost. So the switch asks first,
from the person's press, as Harmony's ruled feature does (LLP 1133.017
§11), and adds the fence only once notifications are granted; the
post's own admission refuses it if they no longer are. Caltrain's geofencing stage
therefore follows LLP 1133.004's stage 1. Android has no notification
path until LLP 1133.004's Android stage: there the feature's drives run
to the notice and stop, and the device cell is not complete until both
Android's headless session and its notifications land (§15 question 5).

**Why the post is data code's.** Contract's `showNotification` is a
statement that answers nothing, and on Apple it returns before
UserNotifications' `add(_:)` completes (`Notify.swift`); nothing would
hold the wake for it, and a guard on a `notificationStatus` resource
could read `empty()` in a cold wake, whose resources are not the wake's
work (LLP 1133.017 D11), and drop an arrival the person was granted. The
data-code form settles when the platform accepts the post, as LLP
1133.004 specifies, so it is owned, awaited and admitted in one place.

**That settling is not built, and this RFC needs it** (§9 item 10). On
the real route the runner hands an answerless send to the host and
answers the data-code call at once (`module_effect`'s `Route::Real` arm,
`runner/src/runner/modules/declared.rs`, returns `Effect::Now(null)`;
the host's later reply only journals a refusal). A wake would then
complete, its transition be deleted (D14 step 3) and its background
task end before `add(_:)` has run. So a data-code call of an answerless
send settles from the implementation's reply, and
`@exact/notifications` replies from the platform's completion (on
Apple, `add`'s completion handler). Until a reply comes the
call is the invocation's work; at the budget it expires, and the
transition stays.

**An unread state is not `prompt`.** A cold wake's process has read no
notification settings: LLP 1133.004 reads them asynchronously, when the
app becomes active, which a headless wake never does (LLP 1133.017 D7),
and the runner's state for a permission no one has read is `prompt`
(`runner/src/runner/modules/permits.rs`). A wake's post is not the
app's, so before the send the host asks the implementation's status
source and refuses the send while it answers `prompt`
(`host/apple/modules/ExactExtensions.swift`, the `admit` branch); that
refusal is the reply the call settles from. So `@exact/notifications`'
status source, asked before any settings are read, reads them
(`getNotificationSettings`) and answers from that completion, never from
an empty cache, mapping them as LLP 1133.004 §6 does (`authorized`,
`provisional` and `ephemeral` are `granted`). The post runs while the
answer is `granted` and otherwise fails `NotAllowedError` without
asking. Deletion stays D14's: the invocation completes, and the
transition is deleted, on `{posted: true}`, on `{posted: false}` (a
stale arrival) and on that refusal; when no answer comes within the
budget it expires, and the transition stays. Under the agent the state
is the drive's (`--permission notifications=granted` on a cold wake,
since the platform's grant outlives the process); on an iPhone the
status source's read is what drive 12's device cell checks.

**Drives** (`packages/geofencing/test/caltrain.mjs`):

10. **Turn it on.** Open Palo Alto, `tap arrive-switch` → a

## 15. Rulings (Charlie, 2026-10-26: "Accept, with Play services (Recommended)")

Each question below was ruled as recommended. Among them:

- **Question 3:** Android's geofencing is Play services'
  (`play-services-location`'s `GeofencingClient`), not the platform's
  `LocationManager.addProximityAlert`. LLP 1133.002 D3 chose
  `LocationManager` over Play services for geolocation because it needs
  no dependency; that choice stands for geolocation, and its paragraph
  now records this amendment: a module whose platform guide teaches
  Play services, and whose features exist only there, links it.
- **Question 7:** the Android Maps key comes from the environment
  variable `app.json` names, and LLP 1133.020 §3.2 gains the key, restricted
  to each app's package and signing certificate.
- **Question 8:** `rules/DEFERRED.md` records the expansion as a waiver:
  the ruling names no take. The background expansion's "still refused"
  narrows from background location and geofencing to continuous
  background location.


1. **Geofencing as its own package** (D18), or folded into
   `@exact/geolocation` 1.1? *Recommended: its own (80%).* It links Play
   services location, adds a grant line, a background permission and host
   entry points; an app that wants a position should pay none of that.
2. **The W3C Note's names** (`addGeofence`, `geofenceenter`,
   `geofenceleave`) over the roster's `watchRegion`, `enter`, `exit`
   (D10)? *Recommended: the Note's (75%):* they are the only web words
   for the thing, and `watch…` reads as a live source that ends with its
   reader, which a geofence is not.
3. **Play services geofencing on Android** (D18), or the platform's
   `LocationManager.addProximityAlert`? *Recommended: Play services (75%):*
   Android's own geofencing guide teaches it, and it carries dwell,
   responsiveness and an initial trigger; the platform call needs no
   library and works without Play services, but has none of the three.
   Either way the receivers are the package's and the store is the
   host's (D14).
4. **The web's tiles named by the app** (D3), with no exact2 default?
   *Recommended: yes (80%).* The alternatives: OpenStreetMap by default
   (map-demo's choice made everyone's, against the spirit of its policy);
   MapKit JS or Google's JavaScript map (each needs a key from the
   developer's account, so still the app's choice, and a script from a
   third party in every page that shows a map).
5. **Caltrain's arrival notice** as geofencing's consumer, accepting that

7. **The Android Maps key from an environment variable** (D18) and a
