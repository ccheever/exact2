# LLP 1017.003: Component-owned resources, mutations, and tasks

**Type:** RFC
**Status:** Implemented (2026-09-09)
**Systems:** Contract syntax/types/lowering, plan format, runner instances/VM/data seam, host verification
**Author:** Charlie Cheever / Codex
**Implementer:** Codex, starting 2026-09-09
**Date:** 2026-09-09
**Related:** LLP 1017 P4c; LLP 1017.000 P4c (amended); LLP 1005; LLP 1016; LLP 1027; LLP 1031

## Summary

A child component can declare the existing `resource`, `mutation`, and `task`
forms. Its mounted instance owns their lifetime. The runner keeps one clock,
one data source, and the current host request/reply protocol. The compiler
continues producing a closed plan; nothing executes application JavaScript
before the baked first frame.

This removes `type-child-resource`. It also gives effectful children a real
mount boundary rather than lifting a conditional child's work into permanent
root declarations. Fleet's account-usage, refreshing transcript, and animated
status components are the motivating consumer: their parent should supply
identity/props, not implement each child's fetching and timers.

Charlie requested this proposal, a direction panel, implementation, commit,
and push. That authorizes this LLP and the panel despite the default process
restriction. General-purpose shared caching/Aquifer and arbitrary async task
syntax remain outside this change; the existing forms become composable.

## Why the current rule exists

`contract/types/src/lib.rs` refuses resources, mutations, and tasks in every
non-root component. LLP 1017.000 states “a row must not open N requests, and
only the root has a clock.” The implementation has instance-owned row slots,
but resources, pending bits, and timer registrations are runner-wide arrays.
The restriction is a coherent implementation boundary, not a lasting language
principle. One scheduler can run many owned tasks. Data-source caching and
parent-owned shared data remain available to authors who want shared work.

## Proposed semantics

### D1 — Ownership follows the mounted component instance

Each component use owning state, resources, mutations, or tasks has a compiler-created, nonvisual lifetime scope.
It exists while that use exists, including inside `when`, `match`, and keyed
`each`. Two uses are independent even when their props are equal. Reordering
an existing key preserves its scope; removal destroys it; reusing the same key
later creates a new lifetime. Nested component instances have nested scopes.

The compiler emits `RegionKind::Scope`, one always-active arm with no layout
node, in the existing instance tree. Scope identity is a fresh allocation,
never a source path, DOM id, or a key alone. View-only components retain their
inlining path. All of a child's owned state shares its mount lifetime. This
intentionally replaces P4c's singleton-child root-slot carry: child state now
restarts on unmount and whole-plan reload even without effects. Root state
retains its existing carry rules; adding an effect no longer changes the
child's state-lifetime semantics.

### D2 — Resources are per-instance subscriptions

Arguments evaluate in the owning instance's current lexical/prop environment.
The existing data-source seam supplies the values and typed placeholders.
`answer_scoped` receives a fresh call context, preserved through every
`parse_scoped` continuation. Native Hermes and browser adapters key parked
work by that context; source name plus arguments cannot distinguish equal-arg
siblings. Ordinary synchronous Rust sources use the default delegation to
`answer`/`parse`. Terminal, superseded, and unmounted calls release their
executor state through `cancel_scoped`, after commit so pre-walk rollback can
retain the previous call. This changes no host request ABI. Unchanged arguments reuse that instance's settled/pending result;
changed arguments supersede the previous request and observe its new pending
state. `refresh` names the instance's resource. Sibling instances cannot read
or refresh one another's same-named declaration.

An optional `else <expr>` after `as shape T` supplies a typed first-pending
value, evaluated in the owning lexical environment only when no previous or
matching baked value exists. Example: `resource usage = fleetUsage(account)
as shape list<Choice> else []` (one declaration line). This also works for
root resources. A first `Later` without such a value remains an explicit data
refusal; there is no implicit null, retyping, or suspense. Bake can record a
fallback as a placeholder without executing the request, and runtime boot
must start that work when its source is ready.

There is no new implicit cross-instance cache: the source is allowed to cache
or share work, and a parent can still pass a shared resource down. Introducing
a cache without an explicit identity/purity contract would incorrectly merge
source calls that consult the store, clock, random source, or credentials.
This proposal permits composition without inventing that policy.

### D3 — Mutations belong to the initiating instance

Each instance has its own mutation result and pending state. `send` captures
the originating instance and its arguments, using the existing request ticket
protocol. A later completion publishes only if that lifetime and request are
still current. An unmounted instance does not receive its old result, and a
new instance with the same list key cannot inherit it. Unmount does not claim
to undo a server-side mutation that was already dispatched.

### D4 — Tasks use the shared deterministic clock

The existing task grammar and action semantics apply inside children. A
periodic registration begins when its instance mounts, first due at mount time
plus its interval. It fires in that instance's live lexical environment.
Reordering does not restart it; unmount removes it; remount starts fresh.
Simultaneous timers order by `(due time, plan timer index, lifetime id)`. Large clock seeks retain the
existing bounded catch-up/refusal behavior. Hidden-but-mounted views keep their
tasks; a branch that removes the component unmounts them.

### D5 — Teardown fences work, without widening the host API

Ownership includes a fresh lifetime token. Request tickets remain unique within
the runner. Teardown drops owned values, timers, and not-yet-dispatched work;
late replies to obsolete tickets do not parse/publish into new UI state.
Already dispatched requests may finish at the host; logical cancellation is
guaranteed, transport abortion is not newly promised. Cleanup must leave no
live runner registration solely because a component once existed.

### D6 — Bake, reload, and atomic failure stay explicit

Bake evaluates mounted synchronous resources from their actual prop/row args,
and uses the existing placeholders for external/store-dependent work. It never
starts I/O or fires a task. A `resource_boot` table records each owned resource's declaration, full
outer-to-inner authored keyed path, actual args, value, and reader/placeholder
provenance. Boot accepts only matching declaration + path + args; equal-arg
siblings never share an entry. Lifetime tokens are not serialized. Root
`initial` remains root-only. Owned answers are not carried or durably kept.
Real boot still drives fresh external work.

A whole-plan reload retains the existing root carry rules; instance effects
restart. No source-address matching or new persistence mechanism is introduced.
Failures before instance-tree mutation preserve existing transaction rollback,
including instance-local writes. A source/shape error after the walk starts
retains the existing poison-and-restart boundary; this change does not promise
a transactional clone of the tree. A normal first `Later` with its fallback is
not an error. Stale host outcomes are inert. Store readiness/change invalidation reaches mounted child resources; root and
scoped readers settle against the final store revision under a bounded fixpoint.

## Implementation direction to review

1. Extend component expansion with owned declarations and a nonvisual scope;
   type-check child bodies independently, then check their expanded use context.
2. Add ownership to the generated plan declaration tables, using
   `plan/tables/format.json` as authority; extend validating decode checks and
   compiler identity/format expectations. No hand-maintained parallel schema. Resources carry owner and fallback code;
   timers carry owner and live capture-argument code; mutation ownership follows
   its result slot. Decode validates scope owners, timer arity and snapshot
   keys/args/value shape and uniqueness.
3. Extend instance frames with lifetime-owned values/pending data; route VM reads,
   writes, refresh/send effects, and scheduled actions through those frames.
4. Settle resources in a scope's actual environment before publishing dependent
   view bindings. Reconcile live registrations with the instance tree, and fence
   replies using ticket + lifetime. Preserve store/readiness/bake behavior.
5. Reuse the host ABI and give source adapters distinct per-call continuation
   identities; verify with Rust and real web/native
   consumers. Move one real Fleet component's declarations into the child as a
   downstream proof, without changing the already-delivered pinned build in place.

## Required verification

Existing five checks remain the checks: workspace build/test, clippy+format,
staged caps, and boot graph. Focused tests must exercise:

- two fixed instances with different props; same resource/mutation names isolated;
- unchanged args, changed props, explicit refresh, and reversed reply order;
- children inside `when`, `match`, nested `each`, slots, and provider contexts;
- keyed reorder preserves state/work; remove/reinsert same key rejects old work;
- mounting timers late, live prop capture, simultaneous timer ordering, teardown;
- mutation isolation, stale completion, pending state, and action rollback;
- store dependence/readiness, bake with distinct instances, and reload reset;
- synchronous resources determining whether further children exist;
- late first-pending mounts with a typed fallback; missing/wrong fallbacks refuse;
- equal-argument repeated instances with distinct baked answers;
- malformed ownership in a decoded plan is refused rather than panicking;
- observable child data/actions/timers in the existing host agent operations.

## Panel questions

1. Is explicit lifetime ownership the right direction, and is there a smaller
   implementation that still handles conditional/keyed/nested composition?
2. Should every stateful child get a lifetime scope now, or only effectful ones?
3. Can existing row frames safely carry owned effects without a second tree?
4. What is the correct bake representation for per-instance resource values?
5. What teardown, rollback, store, or pending-state edge is missing?
6. Is leaving cross-instance deduplication to the data source the right boundary?

## Panel discussion and dispositions

Independent reviews are complete: [Sol](reviews/1017.003-component-owned-effects.sol.md),
[Grok](reviews/1017.003-component-owned-effects.grok.md), and
[Claude Fable](reviews/1017.003-component-owned-effects.claude.md).
All favor component-owned effects in the existing tree. The shared final
round resolved the dispositions now incorporated above: explicit scope,
all state-owning children, an authored fallback, path-qualified snapshots,
live timer captures, and the existing poison boundary. All three reported no remaining direction blocker. Grok withdrew its proposed
pending-without-value model in favor of Claude's explicit fallback; Claude
accepted Sol's all-stateful scope rule and path-qualified snapshots; Sol
accepted the fallback for late mounts. Claude records the nonblocking cost of
losing singleton-child reload carry. That cost is accepted to give composition
one mount rule. Implementation is complete; the regression suites below exercise
the agreed behavior.

## Implementation evidence

`contract/cli/tests/owned_effects.rs`, `owned_store.rs`, and
`owned_dependencies.rs` exercise compiled/baked components, instance-local
requests and mutations, mount-time timers, keyed identity, store fixpoints,
rollback, readiness, forward fallbacks, and live host delivery facts.
`runner/tests/scoped_effects.rs` exercises the runtime seams directly; plan
and lowering tests validate ownership and malformed inputs.

`js/tests/castle.rs` and `js/web/tests/browser.rs` drive real Hermes and
Chromium/wasm executors through the same child Contract fixture. Equal-argument
siblings complete chained requests in reverse order; superseding one call
leaves its sibling intact. Both retain the baked first frame without executing
application JavaScript before first pixel.

Fleet's separate consumer branch moves the usage request and five-minute poll
into `UsageDetails`, with an explicit `else []` loading value. Its data tests
verify teardown and stale replies; the browser test delays a request across
close/reopen, and the rebuilt macOS app passes its navigation/screenshot smoke.
The existing delivered Fleet build remains pinned until separately rebuilt.
