## Summary

A terminal entry should also work as a command-line program: you run it, it
prints, it exits, and a script uses its output and exit status.

```sh
harness --print --prompt "why does the smoke fail?" > answer.txt
todo --print /active                  # the location /active, printed once
todo --json /done | jq .derives.left  # the settled state as JSON
```

- **Print mode** (D1): `--print`, `--json`, or a non-TTY stdin or stdout; a
  `role="log"` streams settled rows as cell text, the rest is written at exit.
- **Done is LLP 1113 D3 under D5's command-line column** (D2); every
  cooperative exit after boot fires `beforeunload` without a prompt, as
  closing a tab does.
- **argv is a URL** (D3); `--prompt` is literal model input (D4).
- **The exit status is the active `head`'s `status`** (D8), under a
  precedence table (D2). **Only a terminal plan prints** (D9).

## 2. Decisions

### D1 — Print mode: lay out at the width, stream the log, write the rest once

| `--drive` | `--print` / `--json` | stdin | stdout | mode |
|---|---|---|---|---|
| given | either | any | any | exit 2: a drive and print mode don't combine |
| given | neither | any | any | headless drive, as today (D3) |
| — | either | any | any | print |
| — | neither | any | not a TTY | print |
| — | neither | not a TTY | TTY | print |
| — | neither | TTY | TTY | interactive, at the location (D3) |

A location on a TTY (`todo /active`) opens the interactive app there, as
`vim file` opens an editor. In this slice no entry reads stdin (§6).

In print mode:
- **The offer.** Width `--columns N`, else the TTY's, else `COLUMNS`, else 80;
  height max-content, as inline mode (`host.rs:208-213`). A percentage height
  against that indefinite parent is `auto` (`taffy/src/util/resolve.rs:31-34`,
  Taffy's result, not CSS's root rule), so todo's `height="100%"` column
  (`terminal.contract:40`) and its `scroll flex=1 min-height=0` (`:60`) take
  their content height; §3 tests a list longer than 24 rows.
- **The height fact stays CSS px**: `exactViewport().height` is `rows × ROW`
  (`host.rs:137`), `rows` the TTY's when stdout is one, else 24, so the
  harness's `viewport.height / 16` (`terminal.contract:102`) still works.
- **The bytes.** With no `role="log"` (todo), `render(0, document_rows())`
  once at exit, as the `document` verb does (`cli.rs:119-123`). With a log,
  its settled children up to the first busy one as `render_settled` lays them
  out (`host.rs:339`), as they settle; the host then publishes `printed` as
  inline mode does (`term.rs:650`), so the app's retire task runs. At exit the
  live rows below that prefix, once. Each row is `row_sgr` (`grid.rs:248`)
  when D6 says SGR, else that row of `grid.text()` split on `\n`
  (`grid.rs:233-243`), each followed by `\n`. None of inline mode's
  sequences: no `ENTER_INLINE`, cursor moves or redraws (`term.rs:387`).
- **The surface record** `exactSurface("terminal")`, `mode: "inline"`, is
  published before the first frame (`term.rs:617`), not left as the empty
  fill (`surface_record.rs:99-102`).
- **No interaction**: no terminal query, key, mouse or alternate screen.

### D2 — Done is LLP 1113 D3 under D5's command-line column

LLP 1113 D3 is the shared settle procedure. Its D5 command-line column cites
this list as its authority; this list is normative for that column.

- **Activation, the sampled frame and surface sync** don't apply: no
  `data_activating`, first-pixel step, motion engine or canvas surface here.
- **The data pass** is the fixpoint below, with no round cap; timers fire on
  the wall clock. **Images** decode in the commit (`host.rs:257`); nothing waits.
- **The ends** are done, or `--timeout` (exit 124), with no `settled` record.
  **Replies'** `clock` is the runner clock, elapsed since boot.

**What holds a run.** Requests, as `has_pending` counts them
(`commit.rs:1124-1135`). One-shot work, by a new runner query (§3): a timer
row with `once` whose `next_ms` is finite (a spent one is set to infinity,
`commit.rs:451-454`), a finite `then_due`, or a finite `queues.next_due`. A
`then` is not in `pending`, since fulfilment removes the request before
arming it (`commit.rs:1217-1224`). `timer_due_ms` (`gates.rs:95-106`) is only
the wake hint: it includes `every` and `frame` timers, which hold nothing, so
the harness's `every(100, step)` spinner (`terminal.contract:105-106`) can't
keep a command alive. **Busy** is any node in the whole tree whose kernel
boolean `accessibilityBusy` (the lowered `aria-busy`) is true. `host.rs:389`
reads that flag only on the log's children, for D1's settled-prefix cut; the
done test walks every node, because the harness's live column, which holds
the silent start (§3), is not a log child.

**The fixpoint.** A pass applies pending announcements, advances the runner
to the milliseconds since boot (as today's loop passes `start.elapsed()`,
`cli.rs:204`, `:209`), firing every timer and continuation due by then, and
lays out the commits. A runner error ends the fixpoint (D8). The host
repeats passes until one commits nothing, then tests done: nothing held, no
node busy; otherwise it sleeps until the next wake or due time.
So after the 1 ms `ask` fires and `submit` announces, the next pass puts
`session.busy` in the tree before the test. A data module's thread is
invisible to `has_pending`, so an app that works on a thread keeps a node
`aria-busy` while it works (§3). Catalog threads wake the loop and hold nothing.

**Shutdown: one sequence for every cooperative exit after boot.** HTML's
close procedure runs `beforeunload` and decides separately whether to prompt.
A cooperative exit (done, `close()`, a runner error, timeout, signal, EPIPE)
is that close:

1. Fire `beforeunload` on every node that declares it; no confirmation can
   be shown, so `preventDefault()` cancels nothing.
2. Dispatch no further action and fire no timer.
3. Wait in a loop that applies announcements and fires no timers, returning as
   soon as no node is busy, or after one second.
4. Capture the outcome (below), write the final output (D1, D7) and exit.

On done, step 3 returns at once; with no `beforeunload`, steps 1–3 are
skipped; `close()` runs this after its own commit; the harness's
`beforeunload=stop` sends `interrupt()`, whose announcement clears
`session.busy` in step 3 (§3).

**The forced exit** is `force_exit(status) -> !` over `libc::_exit`, the
crate's one `#[allow(unsafe_code)]` against `#![deny(unsafe_code)]`
(`lib.rs:23`; `libc` 0.2.189, already locked, becomes direct). Not
`std::process::exit`, which runs `rt::cleanup` and flushes stdout (pinned
1.97.0 `std/src/process.rs:2537`, `rt.rs:139`, `io/stdio.rs:727`). It runs no
flush, handler or destructor, so `beforeunload` may not have run and an exit
inside `interrupt()` can skip `kill_group`, moot here since shell and write
tools are refused (D8). Cooperative exits keep normal cleanup.

**The termination record.** One record, shared by the loop, the signal
handler and both watchdogs, holds every termination cause and when it was
recorded. The loop records a cause between passes; a watchdog records the
cause it enforces when it fires, so it never finds the record empty. Every
exit, cooperative or forced, takes its status from the record by the
precedence below; no watchdog hard-codes a status.

- **Timeout.** The deadline is process start + `--timeout`, as GNU
  `timeout`'s is (default 120 s; `0` disables this deadline only, Q2). The
  loop records it at its next pass and starts shutdown. The watchdog fires at
  the deadline + 2 s, records the timeout if the loop hasn't (a blocked write,
  a synchronous source call, a stuck `interrupt()`), and forces the exit.
- **Signal.** The handler records the first SIGINT or SIGTERM and its
  receipt time; the signal watchdog forces the exit at that receipt + 2 s,
  whatever `--timeout` says. A second SIGINT or SIGTERM calls `force_exit`
  at once with the first signal's status.
- **Before boot** (compile, decode), a firing watchdog writes D7's `exit`
  object (with `--json`) or its stderr line, then forces the exit.

So a timeout at T with no signal, while a streamed row's write is blocked,
exits 124 at T+2 s; a timeout at T, then SIGTERM at T+0.5 s, exits 143 at
T+2 s, because the timeout watchdog reads the record.

**The captured outcome and its delivery are separate.** Step 4 captures the
outcome, which `--json`'s `exit` describes (D7); delivery is the final write.
A completed write exits with the captured status. A signal or timeout during
it stops the write and exits with that cause's status; a write error does the
same with its own. So a complete JSON object with a non-zero process status
means "outcome captured, delivery aborted". Plain text has no completion
marker (every row ends in `\n`), so a non-zero status is the only sign.

**Precedence.** Decided at step 4, among the causes recorded so far:

| Rank | Cause | Status | `exit.reason` |
|---|---|---|---|
| 1 | SIGINT, SIGTERM (the first received) | 130, 143 | `signal` |
| 2 | `--timeout` | 124 | `timeout` |
| 3 | EPIPE before the final write | 141 | `epipe` |
| 4 | a runner error (D8) | 1 | `error` |
| 5 | `close()`, or done, with a head `status` | 1 | `closed` or `settled`, with `exit.head` |
| 6 | `close()`, or done, without one | 0 | `closed` or `settled` |

During the final write, a signal or timeout gives its rank-1 or rank-2
status, EPIPE 141, another write error 1 (on stderr), replacing the captured
status. External causes outrank the app's answer because they cut it short;
any of them can leave a partial line or object, then nothing more.

### D3 — argv is a URL, by one table

For an app's own binary (`harness`), every argument is the command line. For
`exact-terminal`, the first positional argument is the entry's `.contract` or
`.plan`, and the rest follow the table. One left-to-right scan:

| argument | meaning |
|---|---|
| `--print`, `--json`; `--color=auto\|always\|never` | host flags without a separate value, anywhere; another `--color` value exits 2 |
| `--columns N`, `--timeout S`, or `--columns=N`, `--timeout=S` | host flags with a value, anywhere; both spellings are reserved |
| `--size CxR`, `--inline`, `--fullscreen` | today's meaning on the interactive and drive rows; with print mode, exit 2 |
| `-h`, `--help` | the host's flags and the entry's route patterns, exit 0 |
| `--drive` | everything after it is the agent's headless operations (LLP 1101 D8) |
| `--` | everything after it is a positional word, even `/…` or `-x` |
| a word starting with `/`, before `--` | the location, through `location_of` (LLP 1038 D8); at most one; never mixed with other positional words |
| any other positional word | one path segment, through `encode_route_segment` (`route/src/table.rs:448`) |
| `--name value`, `--name=value` | the query parameter `name=value`, for any name the host doesn't reserve; `--name` always takes the next argument, even one starting with `-`; `--name` last, or `--name=`, is empty |
| any other `-x` | exit 2 |

**Encoding.** `encode_uri_component` (`route/src/location.rs:112`), so a space
is `%20`. Query flags append after a `/…` location's own query, and
`searchParam` returns the first value (`:165-180`), so the location's wins.

| Invocation | Result |
|---|---|
| `harness --print --prompt "why?"` | print, `/?prompt=why%3F` |
| `harness --print --prompt "/model gpt"` | print, the literal text `/model gpt` asked of the model (D4) |
| `harness </dev/null` (stdout a TTY) | print, `/` |
| `todo active` (TTY) | interactive, `/active` |
| `todo --print '/?x=one' --x two` | print, `/?x=one&x=two`; `searchParam(…, "x")` is `one` |
| `todo --columns=100 --print` | print at 100 columns |
| `todo -- /tmp/milk` | `/%2Ftmp%2Fmilk` (one segment) |
| `todo /a b`, `todo --json --drive print`, `todo --print --size 80x24`, `todo --color=red`, `todo ..` | exit 2 |
| `todo --prompt` | `/?prompt=` |

**Also exit 2, before boot:** a malformed host flag; a second `/…`; a word
`encode_route_segment` refuses (`""`, `.`, `..`; `table.rs:448-455`); a path
other than `/` for a plan with no router (a query on `/` is allowed:
`match_pattern_index` strips it, `table.rs:170`); a location no route
matches. The runner exposes a pre-boot match over the plan's table
(`RouterContext::from_plan` is `pub(super)`, `router.rs:93`; §3), called
before `Runner::boot`, so nothing boots at the fallback `/`. A declared
not-found route matches, boots, and its `head status=404` exits 1 (D8).

**Linux stays as it is** (`app.rs:45-50`); both send `/…` through
`location_of`. **`--drive`**: the verbs collide with words (`todo tree`), so
they move behind it (Q4). *Rejected: a CLI grammar in Contract.*

### D4 — A command starts from its location

**Reads need nothing new**: a derive or resource argument reads a route
parameter or `searchParam(top(nav), …)`, filled before slot initializers
(LLP 1038 D5).

**An action runs from a gated one-shot task** (LLP 1092 D7–D8):

```contract
derive launchPrompt = searchParam(top(nav), "prompt")
state asked = false
task ask when launchPrompt != "" and not asked
  after(1, askLaunch)
action askLaunch
  asked = true
  send submitted = submitPrompt(launchPrompt)
```

The gate arms a timer due 1 ms after boot; the armed `after` holds the run
(D2), a pass fires it, and the next applies the send's announcement.

**`--prompt` is literal model input.** `submitPrompt(text)`, a new harness
mutation, queues it by `submit`'s non-command branch (`commands.rs:21-30`),
skipping the `/` check, so `/model gpt` or `/tmp/a.md: explain` is asked of
the model. Slash commands stay keyboard-only, so `/stress`, whose worker never
sets `turn`, can't start from a command line.

**Why this location may act.** It runs one model turn under D8's refusals,
and D9 makes a `terminal` plan unbootable elsewhere (the plan, not the
source: a GUI compile of `terminal.contract` boots on a GUI host). *Rejected:
every action as a subcommand*: it makes every action public (LLP 1111).

### D6 — Output follows the terminal's conventions, and the app is told by web facts

- **SGR or plain.** `--color=auto` writes SGR to a TTY, plain otherwise;

- **Plain images** take the unavailable-image branch, their alt text as a

- **`update`, a new `exactViewport` field**, CSS Media Queries 4's `none`,

  written. Unset is `"fast"`, so other screen hosts need no edit; the web

  (`runner/src/viewport.rs`), the terminal host, `host/web-js/facts.js:27` and

- **Place and time are the Linux host's**: `zone::launch_place`'s non-agent

- **The scheme is two channels.** The painter's `light-dark()` flag stays
  dark (`host.rs:99`, `:156`); the fact the app reads stays
  `Preferences::default()` (`viewport.rs:169-180`), since print mode calls no
  `set_preferences` and sends no OSC 11. Print mode's `prefer`, for LLP 1112
  D9's command-line cell:
  `prefers-color-scheme: light`, `prefers-reduced-motion: no-preference`,
  `prefers-reduced-transparency: no-preference`, `prefers-contrast:
  no-preference` (`Preferences::NONE`, `viewport.rs:289-291`),

### D7 — `--json` is the settled `state`, with the terminal's sections

`--json` suppresses every frame, streamed rows included, and writes one
object followed by `\n`: the runner's `state` (`runner/src/agent.rs:722-966`),
which already carries a top-level `head` object (`:915-934`), plus
`navigation{url}`, the launch location as resolved, and
`exit{status, reason, head, message}`. `reason` is the cause D2's precedence
picked: `settled`, `closed`, `timeout`, `signal`, `epipe`, `usage` or `error`.
`exit.head` is the active head's `status` code or null, so a settled run
whose head says 503 is `reason: "settled"`, `head: 503`, `status: 1`, and
`close()` under that head is `reason: "closed"`, `head: 503`, `status: 1`. A
runner error is `reason: "error"`. `message` accompanies `usage`, `error` and
`signal`.

It is the captured outcome, taken at step 4 of D2's shutdown, after the
`beforeunload` commits and the grace. When the write completes, the process
exits with `exit.status`; when a later cause aborts the write, the process
status is that cause's (D2), so a complete object can disagree with it, and
then says what was captured, not what the process returned. A pre-boot exit
writes the `exit` object alone, since there is no runner. Two examples,
abbreviated (the real object has every `state` section):

```json
{"clock": 1840, "slots": {"filter": "done"}, "derives": {"left": 2}, "pending": [],
 "navigation": {"url": "/done"}, "exit": {"status": 0, "reason": "settled", "head": null}}
{"exit": {"status": 2, "reason": "usage", "head": null, "message": "no route for /x"}}
```

**What it reveals.** Slots, derives and resources as they are; only store
values stay out (`agent.rs:907`). `keyDraft` stays empty: no keys are read.

### D8 — The exit status is the head's `status`

| Status | When (D2's precedence decides between them) |
|---|---|
| 0 | done or `close()`, and the active head has no `status` |
| 1 | the active head's `status` is 404, 410 or 503 at exit; a runner error (an action, timer or announcement refused, now reported; it ends the fixpoint, D2); boot, compile or plan decode failed (the panic becomes this); a write error other than EPIPE |
| 2 | usage, before boot (D3) |
| 124 | `--timeout` passed, recorded by the loop or by its watchdog (GNU `timeout`'s code) |
| 130, 143 | SIGINT, SIGTERM, including one that aborts the final write |
| 141 | stdout closed (EPIPE): stop writing and exit quietly; never a panic |

On a head status, stderr gets one line, `<app>: status 503 at /…`.

**Why the head.** LLP 1016 D4 makes failure data, so only the app knows it
failed, and LLP 1048.003 gives it the field: the render host makes it a
page's HTTP status, the command line its exit status, so one authored signal
answers for a page, a picture (LLP 1112) and a command. It is read from the
tree at exit, so a recovered failure clears and `--json` agrees with plain
output. *Rejected:* `role="alert"` (urgent, not failed) and `close(status)`
(only for an app that closes itself; `window.close()` takes no argument).

**The harness's failures.** An error entry sets the session's `failed` (new,
§3), cleared when the next turn starts; while it holds, the harness shows
`head status=503`: a failed `providers::route` (no turn) or a model error.
**Approvals:** under `update == "none"` a tool that needs approval
(`tools.rs:109`) is refused, not awaited; the turn stops with an error entry
and the run exits 1. (`claude -p` denies and lets the model go on; stopping
tells a script the answer is incomplete.)

### D9 — Only a terminal plan prints, and the plan says it is one

**Prerequisite work this RFC includes.** The plan header gains a `surface`
field (`gui` or `terminal`), and the format version becomes 6.
`compile_path_terminal` writes `terminal`; every other path writes `gui`.
Every host checks the field before boot, before any data module exists: the
terminal host refuses a `gui` plan; Linux (and Windows, which boots through
it), Apple, the wasm web host, the JS target's build, the render host and
delivery refuse a `terminal` plan, by name. `cli::run` therefore takes a
constructor for the data module and calls it after the check
(`apps/harness/host/src/main.rs:10`). The five `screen.rs` sites move to
`compile_path_terminal` (§3). D4's claim covers plans whose header says
