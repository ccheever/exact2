## 1. Question and status

Can Rust, TypeScript and Contract use application data with less copying,
serialization and allocation? Would a shared object heap be a good way to do it?

**Extended question, 2026-09-20:** after bounding a resource answer, what still
makes an ordinary interaction grow with the application's accumulated data?
[§11](#11-bounded-work-throughout-an-application-2026-09-20) follows reads,
writes, transfer, settlement, presentation and retirement through the existing
apps. It extends this research rather than allocating a competing performance
document. [LLP 1027.004](1027.004-bounded-resource-answers.plan.md) owns the
bounded-answer work; [LLP 1010 §6](1010-scrolling-v1.spec.md)
and [LLP 1041](1041-graceful-overload.rfc.md) own collections and overload.
Their implementation status and the existing scope trades remain unchanged.

Charlie requested this research write-up on 2026-09-18 after discussing the
current data seam and shared-memory alternatives. This records inspected code,
previous measurements and implementation hypotheses. F5 records the initial
probe; §9 records the resumed implementation campaign. It selects no library,
changes no ABI, and promises no speedup over React Native or another framework.

**Direction updated by Charlie, 2026-09-18:** plan to try all three progressively
deeper implementations and also experiment with the mutable heap. A successful
early candidate does not cancel later experiments. Codex owns the experiment
plan in §7; no prototype execution is claimed by this planning update.

A, B and C are an incremental sequence: cheaper conversion, retained immutable
views, then a common binary backing representation. A remains the ingestion path
for ordinary JS values; C can replace B's internals while retaining its view API.
D is a separate mutable-heap experiment, not a necessary fourth layer. Measurements
will decide what to ship, rather than whether to attempt each direction.
`rules/DEFERRED.md` records this bounded experimental exception. Production
adoption, public APIs and unrestricted cross-runtime objects remain undecided.

**Plan correction after Fable's review, 2026-09-18:** first remove avoidable
costs within the current representation, then measure answer granularity and
identity reuse. Compare A–D against that improved baseline. All four research
directions remain requested, but they are not four equally justified production
projects. Independently verified local fixes need not wait for the entire research
campaign to ship. The initial A work drops the scheduled direct JSI walk and
JS-written binary encoder; those return only if the improved baseline identifies
remaining conversion costs. D starts outside the production Value/runner/ABI.

## 2. Findings

### F1. Common state semantics do not mean common object memory

Contract UI state, derived values and resource results live in the runner.
[`Value`](../plan/src/value.rs) is a Rust enum with reference-counted strings,
lists, records and options. [`Store`](../runner/src/store.rs) is a granted map
of strings with a write journal; the host handles persistence. SQLite and files
are separate durable capabilities. Temporary JS objects belong to their engine.

Rust and TS can implement operations against the same durable data, as Fieldnotes
does with TS note editing and [Rust backup](../apps/fieldnotes/data/src/lib.rs).
That does not give either implementation arbitrary access to the other's heap
or direct ownership of the UI tree. LLP 1027.001 §2 makes this distinction explicit.

### F2. The TS seam performs several representations of the same data

The ordinary native result path is approximately:

```text
JS result -> JSON text -> serde_json::Value -> exact_plan::Value -> runner commit
```

The [prelude](../js/src/prelude.js) serializes the result; the native executor's
[`Module::step`](../js/src/lib.rs) parses it; [`from_json`](../js/value/src/lib.rs)
constructs shape-checked runner values. Arguments take the reverse route through
JSON. Large native strings already bypass JSON string escaping via captured
UTF-16 data; that path still extracts, converts and allocates strings.
The [browser adapter](../js/web/src/lib.rs) also exchanges JSON bytes.

This is evidence of removable work, not proof that a handwritten converter wins.
Engine JSON routines can be efficient; many small property calls can cost more.
Direct linked Rust can use the runner's Value interface, but replaceable Rust
modules have a byte boundary too. Language and executor placement both matter.

### F3. A targeted optimization has already paid off

[LLP 1027.001 §6](1027.001-language-parity.spec.md#6-implementation-record)
records a 4,170,766-byte Fieldnotes backup whose final native TS result transfer
took about 259 ms in the original diagnostic path and 14.3 ms after the
large-string optimization. The original JSON message expanded to about 8.33 MB.
The earlier diagnostic continued past the call guard; the follow-up retained it.
These are historical individual samples, not a new controlled comparison here,
latency percentiles, or evidence that transfer is now every workload's bottleneck.

They justify examining representation costs before introducing a common heap.
They do not establish the size of any remaining gain.

### F4. Shared bytes and shared JS objects are different proposals

JSI can expose native-owned objects through property hooks and buffers through
an explicit lifetime. Browser JS can view Wasm linear memory. Neither means an
arbitrary JS object is a Rust struct, or that both runtimes share a collector.
[JSI interfaces](https://github.com/facebook/react-native/blob/main/packages/react-native/ReactCommon/jsi/jsi/jsi.h)
and [Wasm memory](https://developer.mozilla.org/en-US/docs/WebAssembly/Reference/JavaScript_interface/Memory/buffer)
provide mechanisms, not an Exact ownership model.

Typed accessors over one encoded buffer are an established alternative to
materializing a second object graph: see FlatBuffers' [Rust](https://flatbuffers.dev/languages/rust/)
and [TypeScript](https://flatbuffers.dev/languages/typescript/) interfaces.
These are feasibility references, not a dependency selection. Exact's current
canonical Value encoding is not automatically an indexed random-access format.

### F5. Avoidable work and answer granularity need separate experiments

The diagnostic behind Fable's review is recorded, with raw samples, exact
revisions and correctness checks, in `target/value-transfer-probe-20260918/`.
That directory is local, like the repository's other diagnostics: `env.txt`
holds the identities and `summary.txt` the ranges. Claude (Opus 5) ran it on
2026-09-18:
- **Machine:** Apple M5 (Mac17,3), macOS 27.0.
- **JS:** the standalone Hermes CLI, release 1.0.0 with bytecode 99, the same
  bytecode version as the executor's `prelude.hbc`.
- **Rust:** release build, rustc 1.97.0, against HEAD `d6b3431`'s `exact-plan`
  and `exact-js-value`; the probed files are unmodified.
- **Payload:** a synthetic subset of Messages' `Conversation` shape, with
  simplified decoration derived from `app.ts`. It includes the detailed message
  records but omits several top-level application fields. This is not an in-app
  full-conversation measurement.
- **Samples:** medians in ms. Hermes has 25 per step (5 fresh processes × 5
  blocks of 500, 20 or 1 repetitions, because the CLI clock has 1 ms
  resolution). Rust has 15 per step. Ranges are shown at 25,000 messages.

Checks:
- The on-demand path replacer matched the shipped one's text and captures
  exactly: six cases with 10 captures. The cases cover nested records and
  lists, a subtree reached three times, a `toJSON` result, a direct string
  answer, the 65,535/65,536 boundary and an application `Array.prototype.toJSON`.
- The direct decoder's Value equalled `from_json`'s at every size, and it
  refused the same five malformed variants: a missing field, an extra field, a
  wrong type, a `null` number and a number for a string.
- Not yet covered (A): duplicate keys, numeric limits, nesting depth, malformed
  text and captured-string restoration.
- The payload generator and these cases can seed lane A's fixture and oracle (§8).

These measurements are recorded, not independently reproduced, and not in-app.
They omit:
- the shim's UTF conversion;
- the app's lean VM (the CLI was used instead);
- browser JS/Wasm (the browser adapter has no capture replacer);
- memory.

The full-pass sizing row still walks the whole answer; a check bounded at the
cap, as A requires, would not. Do not sum these phases into a claimed
application latency, and do not assume every resource triggers kept-answer work.

Messages does trigger it:
- In the inspected working checkout, Messages marks its conversation resource
  as a reader. The native hook observes the external read before bake-time
  refusal, and the existing test in `apps/messages/apple/src/snapback_tests.rs`
  asserts the chat reader flag.
- Deferred native loading sets `keeps_answers`.
- So at 1,000 messages, each fresh chat answer spends about 4 ms encoding a
  kept answer that the 8 KiB cap then refuses.

Source inspection confirms the removable operations: the native replacer in
`js/src/prelude.js` allocates a full path per visited value; `Module::step` builds
a JSON tree before `from_json`; `runner/src/runner/kept.rs` encodes before testing
the 8 KiB cap. Messages' `conversation` counts replies by filtering all rows
inside its row map. `snapshot` deep-copies all persisted records and `persist`
compares a complete snapshot even for small edits. These are separate costs from
the byte format. App persistence edits must preserve durable atomicity and rollback.

The data-source seam returns a complete Value per answer. The outer-region memo
in `runner/src/instance/dependencies.rs` conservatively compares allocation
identity for compound values. Faster whole-answer conversion does not make a
single-row edit proportional to that edit. Retaining equal subtrees can help,
but requires checking which identities the actual memo observes: equal row Rcs
inside a newly allocated resource root do not by themselves preserve that root's
identity. Ordinary keyed row bodies already use the bit-preserving recursive
`same_item`/`equivalent` comparison in that same file. Collection windows have a
separate update path that can update mounted rows unconditionally. Therefore the
claim that fresh allocations defeat all row skipping is too broad. Measure skipped
evaluation and settlement, not just reused allocations; do not add a second deep
comparison that duplicates work without improving the actual consumer path.

## 3. Implementation possibilities

These are candidates for experiments, not accepted APIs. They can be combined,
but each should be measured separately before attributing a gain.

### A. Reduce conversion while keeping separate values

First retain built-in JSON.stringify, construct capture paths only for large
strings, decode directly into shape-checked runner values, and stop oversized
kept-answer encoding at its budget. The size check must itself be bounded and
include arguments, hex expansion and the separator; a full pre-encoding pass
would preserve much of the unwanted work. Direct decoding must integrate the
reply envelope and captured strings, not merely benchmark a standalone parser.

A direct native JSI walk and a JS-written binary encoder are deferred subcandidates,
not initial deliverables. Revisit them only if the improved application baseline
still spends material time converting. The reported binary encoder loss is evidence
against that implementation on Hermes, not against every typed-buffer workload.

Existing declared shapes could guide conversion. Any generated adapters would
derive from those shapes at build time, not introduce a second schema authority
or runtime compilation. A larger byte-boundary change also needs its ABI and
delivery consequences assessed under LLP 1029.000.

For these deferred converters the semantic difficulty is significant: JSON determines getter and
`toJSON` execution, omitted properties, array holes, undefined, unusual numeric
values, cycles and failures. Direct conversion must either preserve observable
behavior or explicitly propose a narrower source-value contract. Reading a
getter twice or observing properties in a different order can change the program.
Unicode refusal, exact field validation and error rollback remain relevant.
Keeping stringify avoids reimplementing its JS semantics. The direct JSON decoder
still needs differential checks for missing/extra fields, duplicate keys, numeric
limits, nesting, null/options, malformed input and captured-string restoration.

This candidate retains ordinary TS values and the existing runner model. It is
the smallest architectural step; Fable's diagnostic supports it, with integrated
measurements still pending.

### B. Retained immutable values with lazy language views

One possible first step is to retain a runner value or frozen data snapshot and
give TS a handle-backed view. Rust and Contract use the underlying value; TS
materializes only fields it reads. Returning an unchanged admitted view could
reuse the retained value instead of serializing the collection again.

For example, reading three fields from a 25,000-message result should not require
constructing 25,000 ordinary JS records. Scanning every field may favor an explicit
materialization or bulk operation instead. Normal JS objects returned by existing
sources would still need conversion; sharing pays most when data is reused.

This representation could initially remain a Rust-owned graph on native. It
would not automatically be portable to a separate module, thread or browser
realm. Current `Rc` values cannot simply be sent to a worker, and native pointers
cannot become module ABI values. Views also need explicit decisions about array
methods, enumeration, identity, equality and interoperability with JS libraries.

### C. Immutable typed buffers readable by both languages

A more substantial candidate stores a frozen snapshot in an indexed binary
representation with Rust and TS accessors. Publishing a snapshot shares or
transfers a buffer plus metadata where the executor boundary permits it.
Contract's evaluator would need to read that representation without eagerly
rebuilding the existing Value graph; otherwise much of the intended gain is lost.

This adds format, validation and accessor work, but could avoid repeated whole
graph allocation and improve locality. It does not eliminate initial API JSON
parsing, encoding ordinary JS results, string decoding or validation. Updates
could initially replace a complete snapshot. Chunking or structural sharing is
a separate cost/benefit question: immutable does not by itself make a one-record
update cheap, and a contiguous flat buffer may require a full rebuild.

Same-thread browser JS/Wasm views do not require cross-thread shared memory.
Memory growth and view lifetimes still need handling. Worker transfer may detach
the sender's buffer; simultaneous shared access introduces publication and
synchronization requirements. Browser [SharedArrayBuffer](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)
also has deployment restrictions, including cross-origin isolation for sharing
between workers. Exact's embedded web content makes that a compatibility question,
not a header to turn on silently. A portable API may use a copy on some hosts.

### D. A unified mutable object heap

Allowing arbitrary JS and Rust objects to share identity, references and mutation
would require a common policy for reclamation, cross-language cycles, rooting,
thread access, publication and JS object semantics. It need not require one
particular collector, but it does require coordinated lifetime management.

It would also need a transactional answer to writes during failed actions and
stale async completions, plus a replacement story for objects tied to old modules.
Agents reducing implementation effort does not remove those runtime obligations.
It is explicitly included in the experiment plan even if A–C perform well. Begin
with a shared mutable heap of declared application records, lists and references,
accessed by Rust and TS, with one mutation owner and transaction-controlled writes.
This tests shared identity, aliasing and mutation without claiming that arbitrary
JS closures, prototypes and native objects have become ordinary shared objects.
That distinction must appear in the result: a managed data heap is a useful
candidate, but is not proof of a fully unified engine heap.

### D1. Costs that can remain in a correct implementation

Correctness eliminates dangling pointers and inconsistent commits; it does not
make ownership, transactions or object access free. Depending on the design:

- Handles, wrappers and type checks can make each field access slower than an
  ordinary JS object or Rust struct. Browser engines specialize normal property
  access; a custom representation may lose some of that advantage. See V8's
  [property implementation](https://v8.dev/blog/fast-properties) as an example,
  not a claim about measured Hermes behavior.
- Reclamation needs work: tracing/root tracking, reference-count updates, explicit
  lifetimes, or some combination. Cycles need a policy. Reducing duplicate graphs
  can save memory, but shared roots can retain data longer; metadata, fragmentation
  and collection headroom can offset savings. Concurrent collection moves some
  work off-thread but still has overhead; [V8's write barriers](https://chromium.googlesource.com/v8/v8/+/HEAD/src/heap/WRITE_BARRIER.md)
  illustrate one collector's bookkeeping, not a required Exact implementation.
- A single mutation owner avoids simultaneous writers but serializes their work.
  Concurrent writers instead require synchronization/publication machinery and
  can suffer contention. Sharing between languages does not itself require locks.
- Rollback and coherent UI reads need staged writes, undo records, versions or
  another transaction mechanism. A valid mutation must still notify the runner
  of changed data; a pointer to an object does not perform invalidation for free.
- A common layout may sacrifice a layout preferred by one language. Immutable
  packed buffers can beat a pointer-rich mutable heap for full scans, while a
  heap can win on frequent small edits. Neither ordering is assumed in advance.
- Engine integration couples upgrades and debugging to more runtime machinery.
  Native collector integration, if attempted, is a different experiment from
  browser wrappers over Wasm memory: page JS cannot install a collector extension
  into the browser engine. A common API can still need different implementations.

The hypothesis is a workload-dependent net gain: avoided transfers, duplicated
graphs and rebuilds exceed access, mutation and lifetime costs. Compare a
conversion-heavy workload against compute-heavy local loops and high-churn
mutation, including p95/p99 latency and retained memory. An opt-in shared data
type can preserve ordinary local objects if a universal representation loses.

## 4. Questions a shared representation must answer

- **Ownership and retirement:** Who retains a snapshot across await, cancellation,
  reload and module replacement? Does dropping a view release its backing data?
  A tiny slice can pin an entire history; GC finalization alone gives no prompt
  memory-release guarantee. Account for retained bytes and bound retained versions.
- **Publication:** For B/C, frozen data becomes visible through the runner's existing
  commit. A TS proxy described as read-only is insufficient if another alias can
  still write its buffer. A candidate must prevent mutation of published data
  and preserve failure rollback and stale-result refusal. D instead needs
  transaction-controlled mutation and coherent committed reads of its shared objects.
- **Permissions:** Handles cannot reveal sibling sources' data or bypass Store
  grants. Do not expose all runner Wasm memory to a less-trusted module merely
  to save a copy. Validate the admitted scope, session and incarnation at entry.
- **Validation and replacement:** Buffer offsets, sizes, nesting, shapes and
  Unicode need bounded validation before access. Frozen validated data may allow
  reuse of validation; writable aliases invalidate that reasoning. Reload must
  not leave dangling views or silently retain retired executable code.
- **Portability:** Distinguish sharing an allocation within one owner, sharing
  between threads, and passing values between independent Wasm memories. A
  process-local handle is not a durable value, a baked value or a wire pointer.
- **Accounting:** Include native backing stores as well as JS heap size. Fewer JS
  allocations may only relocate memory; keeping both encoded data and materialized
  objects may increase peak usage. Shape validation and commit remain real work.

These questions preserve the ownership and settlement boundaries in LLP 1027.001,
1027.002 and 1029.000. A snapshot would be another representation of data under
the existing runner, not a second independently reactive application-state graph.

## 5. Evidence to collect before selecting an implementation

Use existing consumers and tooling, with temporary diagnostic instrumentation
where necessary. No new benchmark application, blocking check or scheduler is
needed for the comparison. Capture the exact commit plus working-tree changes,
build profile, engine/browser version, hardware, placement, fixture and raw results.

| Workload | What it distinguishes |
|---|---|
| Small Caltrain-style resource calls | Fixed overhead and small-value regressions |
| Messages at 25, 1,000 and 25,000 records | First construction, repeated unchanged results, sparse visible-row reads, full scans |
| A single message edit and history prepend | Rebuild cost, reuse, ordering and retained versions |
| Fieldnotes near-limit backup and Unicode data | String conversion, escaping, refusal behavior and transient memory |
| Cancellation, failed commit and repeated reload | Lifetime, stale handles, rollback and recovery |

Compare the current implementation, improved A baseline, granularity controls,
and B/C/D through the stages in §7. Treat smaller/paged answers as a first-class
comparison; avoiding a full-history result may beat optimizing its transport.
Do not count virtualized views as evidence that input data is O(window).

Measure API parsing/source computation, encoding, boundary transfer, decoding,
validation, runner settlement and UI update separately where attribution permits.
Report end-to-end time, maximum owner-thread stall, peak/retained memory and bytes
copied as well. Use repeated release runs, state sample counts and summarize
distributions; one fast call or a GC event outside the timer is not a result.
Browser frame gaps and native owner-thread stalls are different measurements;
neither alone proves physical-display frame rate. Keep startup and first-pixel
costs visible, including adapter code size and when the first snapshot is built.

Correctness comparisons should use exact values and existing app drives, plus
the conversion edge cases in A and lifetime cases in §4. Run the web comparison
early; a native-only win is not cross-platform evidence. Worker placement is a
separate variable under LLP 1027.002; do not silently compare inline JSON against
off-thread binary processing and attribute the entire change to representation.

Select shared-representation production candidates only after reporting whole-workload
gains, regressions and maintenance cost across all four experiments. Local fixes
can ship independently after their own verification. Trying every
direction does not commit to shipping every layer. If materialization, full
scans, reclamation or retention erase a gain, record that result and retain the
better representation for that workload. A correct negative result completes
an experiment; a faster microbenchmark alone does not select a production design.

## 6. Confidence and follow-up

High confidence: the inspected paths perform JSON conversion; shared durable
storage is not a shared heap; the runner has a bounded value vocabulary and owns
commits. The backup numbers are attributed historical evidence. High confidence
at probe level (F5): on-demand capture paths, direct decoding and a bounded
kept-answer check remove most of their phases' cost with identical outputs.
Medium confidence: the in-app size of that gain, and whether identity reuse or
retained views remove further work.
Unknown: net performance, memory savings, portability cost and whether an existing
binary format is preferable to a small representation derived from plan shapes.

The experiment sequence is planned below. Implementation sub-LLPs can record
concrete choices when each stage begins, including its date, semantic changes and
measurement targets. Do not reserve numbers or treat the research header as
acceptance of a production API. Experimental scope is admitted; the subsequent
campaign results are recorded in §9.

For the 15-document working-set budget, this research replaces only the
`current/` link to LLP 1027.001. That document remains governing context, linked
above; its status and outstanding follow-ups are unchanged. The new research
lives beside the other exact2 LLPs, not in `llp/research/`, which contains the
predecessor's documents.

## 7. Planned experiments: all four directions

**Owner:** Codex. **Plan date:** 2026-09-18. **Execution:** resumed, with isolated
implementations and measurement probes; actual results and limitations go in §9.
The goal is a comparative result for every candidate,
including the heap, followed by a production recommendation. There is no promised
speedup, ship date or automatic promotion to the default runtime.

| Stage | Bounded deliverable | Comparison |
|---|---|---|
| 0. Baseline | Reproduce current Messages/Fieldnotes behavior, confirm kept-answer trigger, and capture phase timings and memory | Frozen source, actual app engines, small-call controls; supplied CLI timings remain diagnostic |
| 1. A: local fixes | Lazy capture paths, direct JSON decoding, bounded kept-answer encoding; separately fix Messages reply counting and snapshot work | Independent attribution for seam and app fixes, same results and validation, native and browser |
| 1a. Identity reuse | Reuse equal immutable subtrees on answer arrival where useful | A alone versus A plus reuse; unchanged answer, one-row edit, prepend; count actual memo hits and settlement work |
| 1b. Granularity | Existing-consumer viewport pages first; prototype keyed deltas if paging leaves a measured need | Same visible behavior and edits; include producer, transport, validation and settlement costs |
| 2. B: immutable views | Retained typed snapshot, TS field/list access, unchanged return, explicit materialization and lifetime accounting | Sparse reads, repeated reuse, full scans, one-field updates, reload retention |
| 3. C: typed buffers | Replace the view's backing representation with a validated indexed buffer; Contract reads it without eagerly rebuilding a second graph | Initial encoding, reuse, string access, full scans, replacement/chunking costs and peak memory |
| 4. D: mutable heap | First a bounded Rust/TS heap probe outside production Value, runner and ABI; shared aliases, one writer, transactions and reclamation | Repeated cross-language edits/reads; local-loop overhead, rollback, cyclic data and retirement; charge snapshot publication into the runner |
| 5. Synthesis | Raw evidence, correctness outcomes, platform limits, complexity/size cost and recommended combination | All four candidates, current/A baselines and granularity controls |

Identity reuse is still O(N) if it compares a fresh whole answer, and it does not
recover the producer/encoding/allocation work already spent. Match keyed rows
across prepend/reorder and preserve bit-level numeric semantics. A keyed delta
only makes transport O(changed); copying a flat list, global decoration, validating
the whole result or settling the whole UI can remain O(N). State the complexity
of each stage. Paging must preserve ordering, scroll anchors and edits outside
the visible window. These controls address work volume independently of format.

Reuse A for ordinary-object ingestion in B/C where it wins. Preserve the view
surface from B while experimenting with C, but keep enough isolation to attribute
costs to each representation. D may reuse adapters and lifetime diagnostics; its
mutable identity is evaluated separately from immutable snapshots. No core Cargo
feature or permanent matrix of four production runtimes is implied. Use isolated
experimental work and existing consumer/test entry points; retain evidence and
remove superseded prototypes after the comparison.

Start each candidate on web and native macOS, then run any proposed shipping
candidate on iOS/Linux before claiming cross-platform viability. Native-only
findings remain useful and labeled. Keep engine, placement and workload constant
within each A/B comparison. Multi-thread access is a separately labeled extension
to the single-owner heap probe, not a shortcut to a better timing result.

For D, explicitly define which references the heap can contain, which are strong
or weak, how roots are retained, how cycles are reclaimed or refused, and what
identity survives a commit. Demonstrate two aliases observing the same committed
mutation; an aborted action exposes no partial update; a stale async writer cannot
alter a replacement session. Include reachable/unreachable cycles, repeated
allocation/deletion, held references across await, reload and teardown. If the
prototype refuses cycles, record that limit and leave cycle collection unproven.
Do not call this arbitrary JS/native object unification.

Separate an operation-shaped API (`get`, `set`, typed handles) from an optional
property-style JS wrapper to measure the wrapper cost. Measure reclamation over
the full lifecycle, not just allocation speed before a collection. If a full
engine-integrated heap is considered after this probe, first record what the
bounded heap failed to answer and the separate browser feasibility limits.

Every stage reports results and limitations even when it loses. Apply the
repository's three-round fix-loop limit to each concrete failure; record a
blocked case and continue independent experiments instead of iterating forever.
Success in A does not skip B/C/D research. An infeasible host path is documented with its
specific obstacle, never counted as a successful implementation. Production
adoption of shared representations waits for the comparative report. Local fixes
do not wait for heap research. The initial scope trade is removing the planned
direct-JSI converter and JS binary encoder from A, and automatic core integration
from D. Any broader heap integration must first identify the measured workload
and how it preserves immutable committed runner values.

### D: mutable heap — a narrow benefit, substantial costs

The isolated Rust-owned heap ran through real Linux Hermes, using explicit handle
operations and property wrappers. At each of 25/1,000/25,000 rows, 63 checks and

changing the immutable runner contract. The useful measured property is retained
ownership; the mutable shared heap has not been shown necessary to obtain it.

## 11. Bounded work throughout an application, 2026-09-20

### Question and evidence boundary

An app should remain pleasant after a year of use. Sending one message or opening
one note should depend chiefly on the requested and changed data, with appropriate
index lookup costs. A fast runner does not establish this property for an app.

Charlie requested this research after discussing that gap. The findings below
come from inspecting the working tree based on
`8527193d35b2b2cc50aa1ee54186bced317a8db0` on 2026-09-20, including the existing
staged Apple/collection work. Messages' and Fieldnotes' cited source files were
unchanged relative to that commit. Previously recorded experiments are labeled
and linked; no new large-data or physical-device experiment was run for this
extension. The investigation suggestions in §12 are hypotheses to test, not
implemented APIs, assigned work or additional release gates.

### F6. Bounds must survive each stage

```text
storage / producer -> answer construction -> value transfer -> runner settlement
                  -> host views / measurement / layout -> paint -> retirement
```

Let N be total logical records, D the records an operation changes, K the supplied
page size, V the mounted viewport plus overscan/pinned rows, and B the bytes a
particular stage processes or retains. These are separate quantities. Bounding V
does not bound N or B; bounding K does not bound the complexity of one row.

Three questions apply independently at every stage:

| Bound | Question | What a smaller mounted tree does not prove |
|---|---|---|
| Work per operation | How many records, keys and bytes are read, copied, compared or changed? | That a query or snapshot avoids the full dataset |
| Uninterrupted time | How long before another input or frame can be serviced? | That one row, transaction or destructor is short |
| Retained memory and backlog | What survives across views, requests and generations? | That decoded images, old answers and queued payloads are bounded |

A useful target for an indexed page query is O(log N + K + B_page), with row
decoration costs stated separately. A small write should process its changed
records and required index/aggregate updates, without a hidden complete-model
copy. These are consumer targets, not universal complexity promises: deleting a
conversation changes many records; arbitrary substring search may inspect much
of a notebook; maintaining a sorted array can shift many entries.

### F7. Messages bounds its main answer but still reconstructs durable state

[`conversation`](../apps/messages/app.ts) resolves a cursor and decorates at most
200 main-transcript rows, with adjacent rows for boundary styling and maintained
indexes for reply counts and last-outgoing identity. This is meaningful progress.
Selection, reactions and the separate reply answer have their own sizes; 200 main
rows do not make the entire answer a fixed byte quantity. The retained TS history
also remains proportional to N. [LLP 1027.004 §3 D4/D5](1027.004-bounded-resource-answers.plan.md#d4-producer-bounds-for-each-consumer)
records the intended bound and its exceptions.

With the replica enabled, the mutation wrapper then takes a different path:

1. `snapshot()` walks all people, live threads and recoverable messages, and
   JSON-copies every record to detach it from the mutable application model.
2. [`MessagesReplica.persist`](../apps/messages/snapback-client.ts) visits the
   union of held and candidate keys and compares their canonical values.
3. It admits the changed records as one durable mutation. After success,
   `new Map(this.held)` copies the entire held map before applying those changes.
4. `restore()` rebuilds the model and indexes at initial load and when the sync
   path replaces its records; failure recovery also restores committed state.

Consequently a small mutation includes at least a whole-record-set traversal,
plus serialization proportional to stored payload bytes. Returning only a page
afterward does not remove that work. The wrapper deliberately exempts ordinary
conversation and other pure reads from persistence; that repair should remain.

The candidate improvement is explicit changed-record production, incremental
indexes and committed-state updates. It needs failure recovery without relying
on copying the full model on every successful write. The source's current
512-record admission cap also requires a decision for larger deletes/recoveries.
Merely splitting an atomic operation into batches changes partial-failure,
visibility and restart semantics. No such semantic change is selected here.
These costs belong to this application/replica integration; they are not evidence
that either Exact or Snapback intrinsically requires whole-history updates.

### F8. Fieldnotes reads every body to answer a library query

[`notes` and `library`](../apps/fieldnotes/app.ts) select every note's id, title,
body and pinned flag, construct excerpts, lowercase title/body text, and filter
in TypeScript. A search change repeats that path. Saving an existing note uses a
targeted SQL update, but the resulting library refresh fetches all bodies again.
The [Contract resource](../apps/fieldnotes/app.contract) depends on query and save/
service revisions, so the read path matters to both search and editing.

The app permits 1,000 notes, each with up to 20,000 UTF-16 units of body text.
The previously recorded Chrome reproduction in [queue](../queue/) under
“Fieldnotes aggregate library size” exceeds the 16 MiB query-result limit with
legal per-note data. That failure was not rerun for this extension. The inspected
unbounded SELECT still explains how a notebook can outgrow its reading path.

Candidate resource boundaries are:

| Operation | Data requested or changed |
|---|---|
| Open or scroll the library | A cursor page of summaries with stable ordering |
| Open a note | The selected note's body and edit identity |
| Save a note | That note and its summary/search index entries |
| Search | Storage-side search with a bounded result page |
| Export the notebook | All records through a consistent, bounded-memory read |

SQL filtering prevents transferring all bodies, but `LIMIT` alone does not prove
bounded query work. Query planning and indexing need measurement. A full-text
index also does not automatically preserve today's lowercase substring matching:
Unicode behavior, tokenization, partial matches, ordering and counts are product
semantics to settle. Pagination must retain draft/version guards and correct
selection when concurrent edits change the list.

### F9. Viewport bounds and worker placement leave temporal gaps

[LLP 1010 §6](1010-scrolling-v1.spec.md) distinguishes input data from mounted UI
and decoded raster storage. Its dated AppKit work fills offscreen rows between
frames, but visible rows after an urgent scroll are created synchronously; UIKit
does not yet use the same rationed presenter path in that record.

[LLP 1044's 2026-09-19 continuation](1044-markdown-scroll-gap.research.md) records
a row-creation fill unit at 2.6 ms median and 7 ms p99. The dated “A jump lands on
rows built synchronously” [queue entry](../queue/) reports 30–55 ms to fill a
scrollport after a distant jump. These are historical, workload-specific results,
not fresh measurements or cross-host guarantees. The mechanism matters even if
later timings improve: a limit on extra rows does not bound urgent visible work,
and yielding between rows cannot preempt one expensive row.

At 120 Hz the entire frame interval is 8.33 ms, shared by all work needed to
present it. A timer checked after a 30 ms operation returns cannot protect that
frame. Candidate remedies include smaller safe fill units, reuse of already
measured/shaped content, and explicit presentation behavior while filling. A
placeholder or previous complete view must not silently change selection,
hit-testing or the apparent reading location. Expensive old-tree/answer destruction
belongs in the same investigation as construction.

[Worker placement](1027.002-optional-worker-execution.rfc.md) moves computation;
it does not remove transfer, settlement, layout or UI-thread work. Nor does a
bounded answer prevent many completions from becoming ready together.
[LLP 1041 §8.4](1041-graceful-overload.rfc.md#84-bounded-native-http-admission-and-completion-pumping)
already records native count/byte admission and one completion or refusal per
pump. The remaining question is the cost of an individual settlement and its
presentation, including retained and retired generations. One completion per turn
is not a duration bound on that turn.

### F10. Overload behavior is part of correctness

For ordinary browsing, long-lived in-memory history is distinct from durable
history on disk. Measure model data, runner answers, key indexes, mounted views,
decoded images, queued/running/completed payloads and retiring owners separately.
Peak memory includes overlap while replacing an answer; a cache entry removed
from a table may still be held by a view or in-flight operation.

Backup, import, synchronization and index construction can legitimately require
O(N) total work. The research target is usable foreground interaction, explicit
progress/failure and bounded working memory while that work proceeds. Incremental
export must preserve one coherent snapshot; smaller reads must not silently mix
versions. Existing backup formats and size refusals remain in force.

Superseded read interest may be retired; admitted durable effects retain their
ordered outcome or visible pending state. Cancellation of interest is not rollback
of an executed write. Under sustained overload, finite memory requires an explicit
admission, coalescing, backpressure or refusal policy appropriate to the operation.
These boundaries already belong to [LLP 1041 §3](1041-graceful-overload.rfc.md#3-proposed-runtime-contract)
and [LLP 1016](1016-async-data-settlement.rfc.md); this research adds no scheduler
or second state graph.

## 12. Suggested investigation order

The next useful comparisons use the existing applications and diagnostics:

1. **Messages small writes:** compare the present snapshot/diff path with explicit
   changed records, including committed-map publication, save failure, offline
   reopening and sync application. Separately decide bulk-operation semantics.
2. **Fieldnotes reads:** separate summary pages from selected bodies, preserve
   search behavior, and show that every admitted notebook remains readable.
3. **Native collection settlement:** exercise distant jumps, one very long or
   richly styled row, resize and input during completion bursts. Measure urgent
   work and retirement as well as incremental offscreen filling.
4. **Lifetime:** repeat traversal, document changes and replacement until retained
   ownership stabilizes or its growth is explained. Include delayed and stale
   completions, image pins and failed operations.

Vary N while holding page size, viewport and ordinary row payloads fixed; vary
payload size/row complexity separately. Messages stress can use its existing
1,000/10,000/100,000-record cases. Fieldnotes stays within its declared 1,000-note
and per-note limits, including the aggregate boundary case. Do not enlarge product
limits merely to produce a chart. Keep full-answer controls and verify equivalent
visible content; avoid claiming a win obtained by dropping data or work.

Record work counts/bytes where observable, queue age, longest uninterrupted
operation, input-to-updated-content p50/p95/p99 and misses against the observed
display cadence. Distinguish DOM acceptance, frame opportunity, physical display,
host input and synthetic agent input. Pair comparable builds/devices and retain
failures; do not add separately measured stage percentiles into a fictitious total.
Report peak and settled memory separately and identify uninstrumented allocations.
Use the existing agent and metrics paths; any extra instrumentation follows the
repository's authorization rule, not an implied new framework or blocking check.

The app owns efficient query/mutation shapes and indexes. Exact owns correct
settlement, bounded host queues/lifetimes and the means to diagnose the full path.
Candidate reusable resource patterns should be earned by these repairs. A shared
heap, new ABI, general pool or universal data framework is not a prerequisite.

## 13. Confidence and open questions

**High confidence from source inspection:** the Messages successful-write path
still traverses/copies whole-model state; Fieldnotes still transfers all bodies
for a library query; row counts alone do not bound bytes or one operation's time.
**Measured but scoped:** §9's page-versus-whole-answer results, LLP 1044's native
scroll work, and the queue's Fieldnotes failure/jump timings have the limitations
stated in their original records. **Unmeasured:** end-to-end speedups from the
candidate changes above, a universal frame-rate claim, and flat process memory
across all four hosts. No source inspection substitutes for those runs.

Questions for the first selected consumer: how to preserve durable failure and
bulk-delete semantics without full snapshots; which search semantics/index to
retain; what to present during an urgent fill that exceeds a frame; how to bound
one large text row and retirement work; and whether full in-memory durable models
remain acceptable after small-operation costs are fixed. A successful result
would show ordinary interaction costs tracking requested/changed content while
background whole-dataset work makes progress, without compromising application
meaning. It would not claim arbitrarily large apps fit in constant memory.
