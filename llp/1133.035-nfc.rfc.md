## Summary

`@exact/nfc` reads and writes NFC tags that hold an NDEF message, the NFC
Forum's format for a URL, some text or an app's own record. Its tier 1 is
Web NFC's `NDEFReader`: `scan`, `write`, `makeReadOnly`, and the `reading`
and `readingerror` events.

**Only Chrome on Android ships Web NFC.** Chrome added it in version 89
("Web NFC is available on Android in Chrome 89", [Chrome](https://developer.chrome.com/docs/capabilities/nfc)).
Safari, Firefox and Chrome on the desktop have none, and so neither does any
browser on iOS (MDN: "not Baseline because it does not work in some of the
most widely-used browsers"). The web cell is therefore one browser on one
platform, and everywhere else on the web the module answers `available`
false. Tier 1 still takes the web's names, because they are the only shared
words that exist and they fit the two platforms well: a scan that reports
each tag it reads, a write that waits for the next tag, and records typed
`url`, `text`, `mime` or an external type.

The platforms are Core NFC on the iPhone and `android.nfc` on Android. They
differ in the thing that decides the most: **who draws the moment of
waiting for a tag.** iOS always presents its own sheet while a reader
session runs, and the app supplies its message. Android and Chrome draw
nothing, and a hand-built app draws its own "hold near the tag" panel. The
module tells the app which is true (`readerUI`, D10), so an iOS app draws no
second prompt under the sheet and an Android app is not left with none.

```
use scan, abortScan, nfcStatus, reading, NFCStatus, NDEFReading, NDEFScanEnd from "@exact/nfc"

resource nfc = nfcStatus() as shape NFCStatus
mutation scanned as shape NDEFScanEnd

action startScan
  send scanned = scan(once=true, apple.alertMessage="Hold your iPhone near the sticker in the book.")
action tagRead(r: NDEFReading)
  send found = bookForTag(r.id)
```

```ts
import { ndefRecords } from "@exact/nfc";

// The bytes of a reading are data code's; Contract gets its id and its text.
export async function bookForTag(reading: string) {
  const records = await ndefRecords({ reading });
  const own = records.find((r) => r.recordType === "com.exact.shelf:book");
  return own ? new TextDecoder().decode(own.data) : "";
}
```

Tier 2 reaches each platform's tag types, identifiers and raw commands
(ISO 7816 APDUs, MIFARE commands, Android's `transceive`), Android's reader
flags, and Android's host card emulation, which is designed here and built
when a consumer asks (D13). Tier 3 hands the app's native code the reader
session and each tag.

**Consumer.** No app reads a tag today. This RFC proposes **Tag this book**
in Shelf (`apps/shelf`, the reading tracker): put an NFC sticker in a
physical book, write it from the book's screen, and tapping Scan and then
the book opens that book in Shelf. The sticker carries the book's public
Open Library link, so any phone without Shelf opens the book's page (§11).

**Targets.** Web (Chrome on Android), iOS and Android. macOS, tvOS,
watchOS and visionOS are absent, since Core NFC lists none of them. Windows
and Linux are `later`, each with its reason (D18). **No simulator or
emulator has an NFC radio**, so every drive under the agent runs the
module's substitute, and real reads and writes are a device checklist run
by a person (§11, §12).

## 1. What exists

Nothing reads or writes NFC: no host, package or app calls Core NFC,
`android.nfc` or `NDEFReader`. Passkeys mention NFC only as a security key's
transport, which the platform's own authenticator UI handles (LLP 1133.011
D2's table).

**The seams this module uses as built:** a package's event on the app's
root, held and delivered in order (LLP 1133.004 D6, `contract-event-root`);
`"gesture": true` on the web (LLP 1133.013 D12 item 5); a request let go is
cancelled at the implementation (LLP 1133.016 D15 item 2); `"origin": "app"`
and `"foreground": true` (LLP 1133.009 D10 item 8); the Android context's
`activity`, `resumed()` and `foreground(shown)`
(`host/android/canvas/src/main/java/dev/exact/canvas/Extensions.kt`); the
declared substitute and its tickets (LLP 1133.002 §6).

**What it needs that is accepted and not built:** the `bytes` declaration
type (LLP 1133.006 D8 item 1) and the refusal of bytes in Contract
(`contract-module-bytes`, LLP 1133.022 D19 item 4). Whichever module lands
first builds them; this one builds them in its stage 0 if neither has.

**Deep links.** A tag that opens an app the person has not opened is a
deep link, not this module (D9, §14). Shelf's root already takes a link
through `navigate=follow`.

`recordType` takes Web NFC's values ("The record type string"): `empty`,
`text`, `url`, `absolute-url`, `mime`, `smart-poster`, `unknown`, an
external type `domain:type` (`com.exact.shelf:book`), or a local type
`:name` inside a smart poster or an external record. Each platform's NDEF
parser gives the same fields: Core NFC's `NFCNDEFPayload` (`typeNameFormat`,
`type`, `identifier`, `payload`) and Android's `NdefRecord` (`getTnf`,
`getType`, `getId`, `getPayload`); the implementations map a type name
format and type to `recordType` by the specification's table.

### D2 — Text in Contract, bytes in data code

**Contract has no bytes** (LLP 1133.006 D8 item 1 gives `bytes` to data
code), and a record's payload is bytes. Most tags people meet hold a URL or
some text, and an app reacts to those in its UI. So the reading Contract
receives carries each record's **`text`**, decoded by the module, for the
three record types whose data Web NFC's `NDEFRecordInit` already takes as a
string ("Data mapping"):

- `url` and `absolute-url`: the URL, with the URI record's prefix byte
  expanded (`0x04` is `https://`);
- `text`: the text, decoded as its status byte says (bit 7 clear UTF-8,
  set UTF-16BE), with `encoding` and `lang` from the record;
- `smart-poster`: the URL of its URI record, which is what a reader of a
  poster opens.

Every other record's `text` is `none`, and its bytes are data code's:
`ndefRecords(reading=)` answers the reading's records with `data`, by the
reading's id. The module keeps a session's last 16 readings (the event's
`hold`, D8) until the session ends; an id it no longer keeps fails
`NotFoundError`. `ndefRecords` carries bytes, so the bake refuses it in
Contract by name (`contract-module-bytes`).

`write` takes `data` as a string for `text`, `url` and `absolute-url`, so
Contract writes a link or a note. A `mime` or external record's bytes come
from data code.

*Rejected:* the bytes in the event, base64-encoded as a string. Contract
would then hold an encoding it cannot decode, and LLP 1133.022 D15 settled
that a byte-valued name is data code's, not a string in disguise.

### D3 — Errors

Web NFC's names, where its algorithms name one:

| Error | When |
|---|---|
| `NotSupportedError` | no implementation or no NFC hardware (`available` false); a tag that "does not expose NDEF technology for formatting or writing", for `write` and `makeReadOnly` |
| `NotAllowedError` | the permission is `denied`; `overwrite=false` and the tag holds records ("If overwrite is false, read the tag…"); `message` `person-required` for a caller the origin rule refuses (D15) |
| `NotReadableError` | the platform refuses NFC for a setting the person controls: `message` `radio-off` while `radio` is `off` (Android), or Core NFC's `readerErrorRadioDisabled` |
| `NetworkError` | a transfer that fails ("If the transfer fails, reject"); `message` names the cause where the platform gives it: `read-only`, `too-small`, `lost`, `failed` |
| `AbortError` | `abortWrite`, a write let go, a write replaced by a newer one (D7), the app leaving the foreground (D6) |
| `InvalidStateError` | a call from a page that is not top-level (the web, which an Exact page never is) |
| `NotFoundError` | `ndefRecords` for a reading no longer kept |
| `TypeError` | a record that cannot be encoded: a `url` that is not a URL, an empty message, a `data` of the wrong kind |

The specification names no error for a read-only tag or one too small for
the message, only `NetworkError` for any failed transfer. Core NFC names
both (`ndefReaderSessionErrorTagNotWritable`, `…TagSizeTooSmall`), and
Android lets the implementation check `Ndef.isWritable()` and
`getMaxSize()` first, so the cause goes in `message` and the name stays the
web's. Stage 1 records what Chrome raises for each on a phone.

### D4 — Declared deviations

Each with its reason:

- **A scan answers when it ends.** The web's `scan()` resolves when
  scanning starts and is stopped through an `AbortSignal`. A Contract value
  holds no signal, and a scan that iOS ends by itself (its sheet's Cancel,
  its timeout) must reach the app, or the app's "Scanning…" never clears.
  So `scan` stays pending while it scans and answers `NDEFScanEnd`; `pending(scanned)`
  is the web's "started and not stopped"; failures to start reject at once
  with D3's errors. `abortScan()` stops the session's scans, and a scan
  whose call is let go (a superseded mutation, LLP 1133.016 D15 item 2)
  stops too.
- **`once`, a shared word the web lacks.** iOS has a mode that ends the
  session after its first read, and Apple's own sample scans that way ("The
  app configures the reader session to invalidate the session after reading
  the first tag", [Building an NFC Tag-Reader App](https://developer.apple.com/documentation/corenfc/building-an-nfc-tag-reader-app));
  a web page does it by aborting in its `reading` handler. `once=true`
  ends the scan after its first reading, on every target, without a round
  trip through the app. The default is the web's: `false`.
- **`text` on a record, and bytes by id** (D2).
- **No shorthands for `write`.** The web also takes a string (a text
  record) or a buffer (a `mime` record of `application/octet-stream`); a
  record says the same, and a Contract argument takes one type.
- **A write answers `NDEFWriteResult`.** The web's resolves `undefined`.
  Contract needs a value to show that the write finished
  (`docs/contract-grammar.md`, `pending`); the serial number is what
  Android and the web know of the tag written.
- **A written tag is not also read.** The web dispatches `reading` for a tag
  it writes, and its own text calls that "not … the intended behavior" and
  shows an `ignoreRead` flag to undo it ("General information about writing
  data"). Here a tag that arrives while a write waits is written, and no
  reading is raised for it.
- **`readerUI`, a shared word** (D10).
- **Errors' causes in `message`** (D3).

## 3. One reader per process

### D6 — The registry, claims, and the foreground

Each platform has one reader per process, while package instances are per
session (LLP 1133.009 D10) and an app may embed two sessions (LLP 1031
D10). Core NFC allows one reader session in the whole system: "Only one
reader session of any type can be active in the system at a time. The
system puts additional sessions in a queue" ([NFCReaderSession](https://developer.apple.com/documentation/corenfc/nfcreadersession-swift.class)).
Android's reader mode belongs to one activity. A page's `NDEFReader`s share
the page's adapter. So the module keeps **one registry per process**, as
LLP 1133.022 D4 keeps the pads and D15 the Bluetooth links:

- **A scan is a claim** by one session's instance. The registry runs the
  platform's reader while any scan or write claim lives, and stops it when
  the last ends. `abortScan` and a session's `destroy` end only that
  session's scans.
- **A reading goes to every session with a live scan**, as Web NFC fires
  `reading` "at each NDEFReader instance … in the activated reader
  objects". Each such session gets its own reading id.
- **One write at a time per process.** Web NFC keeps "a maximum of one NDEF
  message … set for writing for an origin", and a write "replaces all
  previously configured write operations". So a write (or `makeReadOnly`)
  from any session replaces a waiting one, which fails `AbortError`.
- **On iOS, one sheet** serves every claim: its message is the newest
  claim's `apple.alertMessage`. When the person cancels it, every claim ends
  (`cancelled`, and a waiting write `AbortError`).

**The foreground.** NFC works only while the app is in the foreground, on
every platform: reader mode needs the activity resumed, and Web NFC
suspends while the page is hidden ("Handling visibility change"). The
module follows each platform's rule and makes them one where they differ:

| | Web, Android | iOS |
|---|---|---|
| a scan, when the app leaves the foreground | suspended, and resumed on return with no new call (the web's "resume NFC"; Android re-enables reader mode in `resumed()`) | ended by the system; it answers `interrupted` with the platform's code. The app shows Scan again; the module never re-presents a sheet the person did not ask for |
| a waiting write or `makeReadOnly` | fails `AbortError` (the web's "Attempt to abort a pending write operation") | the same |
| a scan started while `radio` is `off` | fails `NotReadableError` `radio-off` (Android checks `isEnabled()` first); a scan running when the radio goes off is suspended until it comes back | Core NFC's `readerErrorRadioDisabled`, the same error |

`scan`, `write` and `makeReadOnly` are `"foreground": true`, so a call
while the app is in the background fails `NotAllowedError` at admission
(LLP 1133.009 D10 item 8) rather than wait.

### D7 — Writing

A write waits for the next tag. On iOS the sheet appears and says so in the
app's words; on Android and the web the app shows its own panel (D10). When
a tag arrives:

1. if several tags are in the field, nothing happens and polling restarts
   (D5);
2. if `overwrite` is false, the tag is read, and a tag holding records
   fails `NotAllowedError`;
3. the tag's NDEF state is checked: Core NFC's `queryNDEFStatus` (`readWrite`,
   `readOnly`, `notSupported`, and the capacity), Android's `Ndef.isWritable()`
   and `getMaxSize()`, or `NdefFormatable` for an unformatted tag; a
   read-only tag fails `NetworkError` `read-only`, a message larger than the
   capacity `NetworkError` `too-small`, a tag with no NDEF support
   `NotSupportedError`;
4. the message is written (`NFCNDEFTag.writeNDEF`, `Ndef.writeNdefMessage`
   or `NdefFormatable.format`), and the write answers the tag's serial
   number.

Android's writes block and "must not be called from the main application
thread" ([Ndef](https://developer.android.com/reference/android/nfc/tech/Ndef#writeNdefMessage(android.nfc.NdefMessage))):
the implementation writes on the reader callback's thread and replies on the
main thread. A tag lost before the write completes fails `NetworkError`
`lost`.

**`makeReadOnly`** waits for a tag the same way and locks it: Core NFC's
`writeLock` ("a permanent action that you cannot undo",
[writeLock](https://developer.apple.com/documentation/corenfc/nfcndeftag/writelock(completionhandler:))),
Android's `Ndef.makeReadOnly()` ("a one-way process and cannot be
reverted!"), the web's `makeReadOnly()` (Chrome 100 and later). A tag that
cannot be locked (`canMakeReadOnly()` false) fails `NotSupportedError`. The
recipe has the app confirm first with its own alert dialog.

### D8 — Readings, their events, and their origin

A tag that arrives during a scan, with no write waiting, is read, and the
module raises `reading` on the app's root with an `NDEFReading` (LLP
1133.004 D6): held while no handler is mounted, up to 16, delivered once and
in order, each its own commit. A tag that carries no NDEF raises
`readingerror` instead (Web NFC fires it when a tag "does not expose NDEF
technology for reading or formatting"). A `once` scan ends after its first
`reading`, not after a `readingerror`.

**A reading has the device's origin,** as every event a package raises does
(LLP 1133.004 D6: "a package cannot mint" a person's origin). A tag in the
field is usually a person's hand, but it can also be a tag left under the
phone, and the module cannot tell the two apart. The commit a reading makes
may read state, navigate and call data code; it cannot start a device or
open system UI (`scan`, `write` and `makeReadOnly` are `"origin": "app"`),
so writing back to the tag just read takes a press ("Update the tag",
then hold it near again) or tier 3 (D14).

### D9 — A tag outside a scan is the system's

The module claims nothing while
no scan or write runs, so a hand-built app's behaviour holds: iOS reads a
URL tag in the background on an iPhone XS or later and shows a notification
([Adding Support for Background Tag Reading](https://developer.apple.com/documentation/corenfc/adding-support-for-background-tag-reading)),
and Android dispatches the tag to whichever app filters for it. Neither
reaches a closed app through this module:

- on iOS, the background read opens an app only for a universal link
  ("Background tag reading doesn't support custom URL schemes. Use
  universal links instead"), and delivers it as the `NSUserActivity` a
  universal link already is;
- on Android 16 and later, "scanning NFC tags that store web links …
  triggers the `ACTION_VIEW` intent instead of the `ACTION_NDEF_DISCOVERED`
  intent", and Android 17 first shows an "open link" notification
  ([NFC basics](https://developer.android.com/develop/connectivity/nfc/nfc)).

So **a tag that opens an app is a deep link** on both platforms: a
universal link or a verified App Link that the app's navigation root
receives (LLP 1038 D8). That needs a public origin with the association
files (LLP 1133.020 §3.1) and Android App Links (LLP 1133.000 §2's deep
links row: not built), and it is the deep links' work, not this module's
(§14).

## 4. Who draws the wait

### D10 — `readerUI`: the system's sheet, or the app's panel

| Target | While a scan or write waits | `readerUI` |
|---|---|---|
| iOS | the system's sheet, always, with the app's `alertMessage`; it covers the app until the session ends | `system` |
| Android | nothing: reader mode has no UI | `app` |
| web (Chrome on Android) | nothing beyond the browser's permission prompt | `app` |

A hand-built iOS app shows a Scan button and lets the sheet do the rest;
drawing its own "hold near the tag" behind the sheet would be a second
prompt no iOS app has. A hand-built Android app shows its own panel with
the same words and a Cancel button, because the platform shows nothing and
a person otherwise cannot tell that the phone is waiting. So `nfcStatus()`
carries `readerUI`, and the recipe (`docs/recipes/nfc.md`) gives the
pattern: while `pending(scanned)` and `readerUI` is `app`, show a sheet
with the instruction and a Cancel button that sends `abortScan()` (or
`abortWrite()`); on iOS show nothing more.

*Rejected:* a package view that draws the panel on Android and the web. Its
words would be the module's rather than the app's, its look would be one
guess at what an Android app shows when Android itself shows nothing, and
an app could not lay it out. The app's own sheet, in its own words, is what
a hand-built Android app has.

*Rejected:* imitating iOS's sheet on Android. It would be an iOS tell on
Android.

## 5. Tier 2 and tier 3

listing `D2760000850101` makes a MIFARE DESFire tag's NDEF application

### D13 — Android's host card emulation, designed and not built

Android lets an app act as a contactless card: a `HostApduService` the
system starts when a reader selects one of its application identifiers,
"if it is not already running", which "executes the transaction in the
background" ([Host-based card emulation](https://developer.android.com/develop/connectivity/nfc/hce)).
The roster names it as this module's tier 2. Its shape, so that it fits
when a consumer asks:

- **Declared in app.json,** `host.android.nfc.cardEmulation`: application
  identifiers in the `other` category only, a description from the app's
  strings, and `requireDeviceUnlock`. The bake writes the `<service>` with
  `BIND_NFC_SERVICE` and its `apduservice.xml`, the service class being
  the implementation's. The `payment` category stays out: it needs the
  default wallet role, and Android allows one payment group at a time.
- **Foreground first.** While a send `android.emulateCard()` is pending and
  the app is resumed, the implementation registers the identifiers
  (`CardEmulation.registerAidsForService`) and prefers its service
  (`setPreferredService`, which "must currently be in resumed state"); it
  removes both when the send ends. Registering only then keeps a
  statically listed identifier from making Android ask the person which app
  should answer whenever another app lists the same one.
- **Each command APDU reaches the app's data code** through the runner's
  `invoke` (LLP 1133.016 D15 item 1), whose answer is the response APDU.
  `processCommandApdu` runs "on the main thread", and the service may
  "return null" and answer later with `sendResponseApdu()`, so the runner's
  hop does not block it.
- **Out of this first form:** answering while the app is closed, which
  needs a session with no view (LLP 1133.017 D7) to answer within a
  reader's time limit; Apple's `CardSession`, whose entitlement Apple
  grants case by case, for apps in the European Economic Area and some other
  regions, under an agreement ("Use of this entitlement is managed by
  Apple", [CardSession](https://developer.apple.com/documentation/corenfc/cardsession));
  and Windows, whose `SmartCardEmulator` is in the Windows Mobile SDK only.

No app needs it now. §16 question 5 asks whether to build it anyway.

## 7. Permission

### D15 — LLP 1133.002 §4 for NFC

**Declare.** `device.nfc <purposeKey>`. Derived:

| Target | Derived | Does a prompt show the purpose? |
|---|---|---|
| iOS, iPadOS | `NFCReaderUsageDescription` (required: "If the app attempts to read a tag without providing this key and string, the app exits"); the entitlement `com.apple.developer.nfc.readersession.formats` with `TAG`, the one value Apple documents ("Allows read and write access to a tag"); with `host.ios.nfc`, its two arrays (D11) | no: iOS asks nothing for NFC; the sheet shows `alertMessage` |
| Android | nothing in the grant column: `android.permission.NFC` ("Protection level: normal", no prompt) and `<uses-feature android:name="android.hardware.nfc" android:required="false"/>` are in the Android implementation's own manifest, which the reader's merge carries, as gamepad's `VIBRATE` is (LLP 1133.022 D9) | — |
| web | nothing: Web NFC defines no Permissions Policy feature, and runs only in a top-level context, which an Exact page is | no (Chrome's prompt names the site) |
| macOS, tvOS, Windows, Linux | nothing | — |

The grant row is `nfc`, with no web policy feature and `tvos: false`. Its
entitlement has a value, an array, where the table's `ios_entitlements`
are booleans today (`runner/src/device.rs`): the row gains a valued
entitlement (D16 item 3). A device build also needs the NFC Tag Reading
capability on the App ID ("Adds the NFC tag-reading feature to the App
ID"), which the signing profile must carry: LLP 1133.020 §3.3 gains the
step for `com.exact.shelf`.

**Read.** `nfcStatus()` answers four facts, kept apart:

- `available`: the target can read tags at all. The web: `"NDEFReader" in
  window`. Apple: `NFCNDEFReaderSession.readingAvailable` ("whether the
  device supports NFC tag reading"), false on the simulator. Android:
  `NfcAdapter.getDefaultAdapter(context)` is not null ("null if no NFC
  adapter exists"). An app hides its NFC feature only when this is false.
- `radio`: `on`, `off` or `unknown`. Android reads `NfcAdapter.isEnabled()`
  and follows `ACTION_ADAPTER_STATE_CHANGED`, and reads it again on
  `resumed()`. iOS has no switch the app can read, and the web none:
  `unknown`. An app says "Turn on NFC" on `off` and offers
  `openNFCSettings()`.
- `state`, as LLP 1133.002 D8 defines it, whether a call needs the person to
  allow more than the act itself:

| Platform | `state` |
|---|---|
| web | `PermissionStatus.state` for `nfc`, followed through its `change` event |
| iOS | `granted`: there is no permission; each sheet is the person's consent to that scan |
| Android | `granted`: a normal permission, granted at install |

- `readerUI` (D10).

**Ask.** On the web, the first `scan`, `write` or `makeReadOnly` while
`prompt` shows Chrome's prompt, which needs the press's activation; each is
`"gesture": true` (LLP 1133.013 D12 item 5), so a Contract send runs inside
the press's dispatch. Chrome's activation is a span of time after the press
(HTML's transient activation), so a data-code call a press caused also
reaches the page in time; stage 1 checks it in Chrome on a phone. A denial
fails `NotAllowedError`. iOS and Android ask nothing.

**Who may.** `nfcStatus` is a fact any caller reads. `scan`, `write` and
`makeReadOnly` start the radio and on iOS open system UI, so each is
`"request": true`, `"origin": "app"` and `"foreground": true`: a tool
invocation's, a wake's or a reading's fails `NotAllowedError`
`person-required` in every state (LLP 1133.009 D10 item 8; D8 for readings).
The tier 2 commands and `android.emulateCard` are the same. `abortScan`,
`abortWrite` and `ndefRecords` stop something or read what the session
already has, and any caller may. `openNFCSettings` is not open to tools, as
`app-settings:` is not (LLP 1133.002 D11).

**Recover.** On Android, `openNFCSettings()` while `radio` is `off`. On the
web, a denied site is the browser's setting, which the app explains.

Abridged declaration:

```json
{
  "kind": "interface", "name": "@exact/nfc", "version": "1.0.0",
  "grants": ["device.nfc"],

    { "source": "nfcStatus", "live": true, "answers": "NFCStatus",

      "gesture": true, "options": { "once": "option<bool>" }, "answers": "NDEFScanEnd",
      "substitute": { "ticket": "scan", "cancel": { "reason": "cancelled" } } },
    { "send": "abortScan", "answers": null },
    { "send": "write", "request": true, "origin": "app", "foreground": true,
      "gesture": true, "options": { "message": "NDEFMessageInit",
        "overwrite": "option<bool>" }, "answers": "NDEFWriteResult",
      "substitute": { "ticket": "write", "cancel": { "error": "AbortError" } } },
    { "send": "makeReadOnly", "…": "as write, without options" },
    { "send": "abortWrite", "answers": null },
    { "send": "ndefRecords", "options": { "reading": "string" }, "answers": "NDEFRecord[]" },
    { "event": "reading", "on": "root", "args": ["NDEFReading"], "hold": 16 },
    { "event": "readingerror", "on": "root", "args": [], "hold": 16 }
  ],
  "substitute": { "arrival": { "field": "field", "from": "tags",
    "raises": ["reading", "readingerror"], "settles": ["write", "makeReadOnly"],
    "ends": { "scan": "once" } } }
}
```

Apple's implementation declares `"substitute": {"nfcStatus": {"readerUI":
"system"}}` and the web's `{"state": "prompt"}` (item 1).

**Seam additions,** each general and proved by the out-of-tree fixture
first (LLP 1133.001 D8):

1. **A substitute default per target.** An implementation's declaration may
   override fields of the interface's substitute default for the target it
   binds, so a drive on the iOS simulator reads `readerUI` `system` and lays
   out what an iPhone shows, and a web drive starts at `prompt`. Any module
   whose facts differ by platform (Bluetooth's `radio`, a status's `state`)
   can use it.
2. **An arrival in the declared substitute.** A preferred value may stand
   for something arriving rather than a fact: setting `nfc.field` to a
   fixture tag's id brings that tag into the field. The substitute then
   applies the declaration's `arrival` rule: it settles the process's
   waiting `write` or `makeReadOnly` against the tag (writing the fixture's
   records, or failing as the tag's `write` field says, §10), or else
   raises `reading` (or `readingerror`) to every session with a waiting
   `scan`, giving each a reading id, and ends `once` scans with `read`.
   LLP 1133.022 §9 raises `gamepadconnected` from a preferred change; this
   is the same mechanism, stated once.
3. **A valued entitlement in the grant table:** a row's iOS entitlement may
   have an array value (`["TAG"]`), and app.json's `host.ios.nfc` arrays
   reach `Info.plist`.
4. **The bytes type and its Contract refusal,** if LLP 1133.006 and
   1133.022 have not built them (§1).

### D17 — Callers

Contract reads `nfcStatus`; sends `scan`, `abortScan`, `write` (with
`text`, `url` and `absolute-url` records), `makeReadOnly`, `abortWrite`;
and hears `reading` and `readingerror` on its root. Data code calls every
name through the binding, and alone `ndefRecords`, the tier 2 commands and
a `write` with bytes. Requests: `scan`, `write`, `makeReadOnly`,
`android.emulateCard`. `sync`: `nfcStatus`, on Apple through `call`.

## 10. The substitute

A **declared substitute** (LLP 1133.002 §6). No simulator or emulator has an
NFC radio, so it is the only way an agent drives a tag on any target, and a
production build reaches none of it.

- **Status:** the default of D16, with the bound target's overrides (D16
  item 1). `prefer permission.nfc granted|denied|prompt` and `--permission
  nfc=…` set `state`; `prefer extension nfc.nfcStatus=…` sets
  `available`, `radio` and `readerUI`.
- **Tags:** `prefer extension nfc.tags=[…]`, each `{"id", "serialNumber",
  "records": [{"recordType", "mediaType", "id", "data"}], "ndef": true,
  "write": "ok"}`: `data` a string for `text`, `url` and `absolute-url`, and
  `{"base64": "…"}` otherwise; `ndef` false for a tag that holds no NDEF;
  `write` one of `ok`, `read-only`, `too-small`, `lost`, `not-ndef`, how a
  write to it ends. The substitute does not model a tag's capacity: the
  device checklist checks real sizes.
- **The field:** `prefer extension nfc.field=<id>` brings that tag into the
  field; `=clear` takes it away. A change to another id, or a clear and the
  same id again, is a new arrival (D16 item 2).

| Event | Result |
|---|---|
| `scan` while `granted`, from the app's foreground origin | a `scan` ticket in `state.pending`; the send waits |
| `scan` or `write` while `prompt` | a `permission` ticket first; `allow` sets `granted` and continues |
| a tag arrives, a write waiting | the write settles by the tag's `write` field; on `ok` the fixture's tag holds the written records (or is locked, for `makeReadOnly`), and no reading is raised |
| a tag arrives, a scan waiting | `reading` (or `readingerror` for `ndef` false) to every session with a waiting scan; a `once` scan answers `{reason: "read", reading}` |
| `tap @t cancel` on a `scan` ticket | the person's Cancel on iOS's sheet: the scan answers `cancelled` |
| `tap @t timeout` on a `scan` ticket | the system's end: the scan answers `timeout` |
| `tap @t cancel` on a `write` ticket | `AbortError` |
| `abortScan()`, `abortWrite()` | as production |
| `ndefRecords(reading=)` | the records of the tag as it was when read, `data` decoded from the fixture |
| the app leaves the foreground | as D6, by the bound target's `readerUI`: a scan on `system` ends `interrupted`, on `app` suspends |
| a tool's, a wake's or a reading's `scan` or `write` | `person-required`, as production |

- **Disclosure:** `state.extensions.nfc` lists the fixture's tags as they
  are now, the field, each scan (session, origin, `once`, waiting or
  suspended), the waiting write, and each reading (its id, its tag, the
  sessions it went to).

## 11. The consumer: Shelf's Tag this book

No app in or beside the repository reads a tag. The smallest real one is a
book tag: an NFC sticker inside the cover of a book you own, written once
from the book's screen. It is the commonest thing people do with NFC
stickers (a tag that names an object), the stickers cost little and need
no account, and it needs every part of tier 1 that can fail: a write that
waits for a tag behind the system's sheet or the app's panel, a read that
navigates, an app's own record read in data code, a tag the app did not
write, a locked tag, and absence on every browser but one. Shelf is the
right app because it already owns the objects (books, each with a route,
`/book/:id`), already speaks Open Library (Discover adds books by their
Open Library work key, `sourceKey`), and is the repository's recipe for an
iPhone app, so its NFC screens are the ones other apps will copy.

**The tag** holds two records, written from `app.ts`:

1. a `url` record with the book's Open Library page,
   `https://openlibrary.org` + `sourceKey`, when the book has one. It comes
   first because iOS's background reading and Android's dispatch read the
   first URI record, so a phone without Shelf opens the book's public page;
2. an external record `com.exact.shelf:book` whose data is the book's id in
   UTF-8, so every book can be tagged, including those added by hand, and
   Shelf finds this copy even when two editions share a work.

**Shelf gains:**

- `"@exact/nfc": "file:../../packages/nfc"` in a `package.json`; the grant
  `device.nfc nfcPurpose`; strings for the purpose, the sheet's messages
  and the panel;
- `resource nfc = nfcStatus()`; nothing below shows while `available` is
  false;
- on a book's screen, a **Tag This Book** row, which runs the data
  mutation `tagBook(id)`: it builds the two records and calls `write` with
  `apple.alertMessage` "Hold your iPhone near the sticker in the book." and
  `apple.doneMessage` "Tagged". While it waits and `readerUI` is `app`, a
  sheet says "Hold your phone near the sticker in the book" with Cancel
  (`abortWrite()`). Success shows "Tagged" on Android and the web (iOS's
  sheet said it); a failure shows the cause in an alert: "This tag is
  locked", "This tag is too small", "Hold the phone still until it's done",
  "This tag can't store a link";
- in the library's header, a **Scan** button: `send scanned =
  scan(once=true, apple.alertMessage="Hold your iPhone near the sticker in
  the book.")`, with the same sheet and Cancel (`abortScan()`) on Android
  and the web;
- on the root, `reading=tagRead`: `tagRead` sends `found = bookForTag(r.id)`,
  whose data code reads the external record, else matches the `url`
  record's work key against `sourceKey`; its `then` opens the book
  (`nav = go(nav, path("book", id))`), or for a tag that names no book on
  the shelf shows an alert "Not on Your Shelf" with the link and an Open
  Link button (`openURL`, from that press). `readingerror=unread` shows
  "This tag can't be read";
- while `radio` is `off` (Android), the Scan and Tag rows read "Turn On
  NFC" and send `openNFCSettings()`; while `state` is `denied` (the web), a
  line says NFC is blocked for this site.

**Drives,** under the agent on the web's JS target, the iOS simulator,
macOS, the Android emulator and the Windows host headless on the NucBox
(`bun scripts/agent.mjs windows --app shelf`); tickets from
`state.pending`. Setup: `prefer extension nfc.tags=[{"id":"blank","records":[]},{"id":"dune","records":[{"recordType":"url","data":"https://openlibrary.org/works/OL893415W"}]},{"id":"locked","records":[],"write":"read-only"},{"id":"card","ndef":false}]`
and a library holding Dune with that key.

1. Open Dune; `tap tag-book`: a `write` ticket. On the iOS simulator the
   tree shows no panel (`readerUI` `system`); elsewhere the panel. `prefer
   extension nfc.field=blank`: "Tagged"; `state.extensions.nfc.tags` shows
   `blank` with the URL record and the external record holding Dune's id.
2. Back to the library; `prefer extension nfc.field=clear`; `tap scan`; `prefer
   extension nfc.field=blank`: Dune's screen; the scan answered `read`;

## 14. What reaches beyond this module

- **A tag that opens the app is a deep link** (D9). iOS opens an app from a
  tag only for a universal link, and Android 16 sends a tag's web link to
  `ACTION_VIEW`, so a tag reaches a closed app only through Associated
  Domains on Apple and verified App Links on Android, behind a public
  origin. Android App Links are unbuilt (LLP 1133.000 §2) and the public
  origin is unruled (LLP 1133.020 §3.1); the deep links' own work, not this
  module's, would make any app's tag open it.
- **Substitute defaults per target** (D16 item 1): today a drive on the iOS
  simulator reads the interface's defaults, which are no platform's. Every
  module whose status differs by platform can use them.
- **An arrival in the substitute** (D16 item 2) states once what LLP
  1133.022 §9 does for pads.
- **A device-origin event cannot start a device** (D8). It is right for a
  tag and for a pad, and it rules out the same-touch read-and-write that
  Core NFC's sessions are built for; a later module may want a narrow
  exception (a write to the tag that raised the reading, within the
  session that the person started).
- **The grant table's valued entitlements** (D16 item 3), and the App ID
  capabilities a device build needs, which the build does not set:
  passkeys' Associated Domains and this module's NFC Tag Reading are both
  manual steps in LLP 1133.020 §3.3.
- **The Rust hosts have no package dispatch** (LLP 1133.022 D10 item 5);
  Windows' cell waits on it, as every module's does.
