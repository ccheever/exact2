## 1. Summary

Charlie asked for this on 2026-10-05. The plan runs in four parts:

- **Swap.** Replace cosmic-text with Parley everywhere exact2 lays out text off Apple and off the web. On a branch, behind the unchanged measurer seam.
- **Fill the gaps.** Close the gaps LLP 1085 found in Parley: base direction, font admission, ellipsis and clamp, Devanagari line advance, Khmer U+200B.
- **Stay Rust.** Keep the stack Rust from font file to glyph position.
- **Measure.** Compare the result with main on Linux, on Android phones and under Expose.

Then land it or drop it by criteria written here, before any number comes in (§6).

The experiment is worth running for parity, memory and re-layout. It is probably not worth running for scroll speed:

- 1085 F8: shaping and breaking are about 5% of a Linux scroll's main thread.
- `android/text` replaced cosmic-text's measuring with Minikin on a phone. Fling fps, fling CPU, cold start and PSS did not move (§2).

The predictions in §2 are stated so that the measurements can prove them wrong.

Landing this changes `exact-linux` on main. The Android parts stay on `android/explore` until Android is admitted (DEFERRED: Android is not on the doing-list). Running the experiment admits nothing.

## 2. What we already know, and what we predict

**From LLP 1085** (Mac Studio; pinned Noto fonts; Chrome 154 as the oracle):

| Measure | cosmic-text | Parley |
|---|---|---|
| Shaping time | baseline | ~1.7× faster |
| Re-breaking at a new width | baseline | 2.5–3× faster |
| Heap per shaped paragraph | baseline | ~¼ |
| Line starts equal to Chrome's | 86–99% | 98–99.8% with `CHROMIUM_LINE_BREAK_OVERRIDE` |
| Code size over a shared base | +1.07 MB | +0.94 MB |

F8 (Linux heavy-list scroll): shaping and breaking are 5.2–5.5% of main-thread CPU on the GPU painter, and 1.4–1.5% on the CPU painter.

**From `android/text`** (2026-10-04, Nothing Phone (4a) Pro, Rust vs platform):

- **What changed.** Minikin measured with `Paint.getTextRunAdvances`, and cosmic-text still broke lines.
- **What did not move:**
  - cold start content medians (e.g. heavy 200 / 198.5 ms);
  - fling fps (heavy 118.7 / 118.7);
  - fling CPU (heavy 1125 / 1146 ms/s);
  - PSS (crypto 121 / 123 MB).
- **What did move:** boot-thread text work fell, from 43.8 to 12.9 ms on xheavy. That time was font fallback and declared-face parsing, and it overlapped activity setup.

So a phone's scroll is not limited by shaping.

**Predictions** (§7 records them against the results):

- P1 **Scroll: no change beyond noise.** Fling fps, CPU and jank on Android; the scroll CPU share on Linux. Within F8's ~2.5–3% on the Linux GPU painter.
- P2 **Re-layout gets faster.** A width change (Linux window resize; Android rotation) re-breaks every visible paragraph. Text's share of that frame should fall by about half.
- P3 **Memory falls.** Text's resident heap falls, visibly so for the giant Markdown document. On Android, native heap is 76 MB against Views' 31 on the crypto fling. What share of that is shaped text is unknown and is measured first (§5, stage 0).
- P4 **Boot changes only through font handling.** Parley does not by itself make fallback or face parsing cheaper. Any gain there comes from the catalog work in G8.
- P5 **Parity improves.** Chrome line-start agreement rises in ordinary paragraphs (URL `/` and hyphen-digit breaks). No script gets worse in the text-flow corpus.
- P6 **Size is about even.** Within ±0.2 MB of main.

## 3. "Fully Rust"

The C/C++ text stack Charlie remembered is FreeType + HarfBuzz + Skia, which Expose's LLP 0006 names for Expose. In exact2's own stack, each of those layers already has a Rust equivalent, and the Parley stack uses it. Nothing needs porting.

| Layer | Today (cosmic-text) | With Parley | C/C++ it avoids |
|---|---|---|---|
| Font discovery | fontdb directory scan | the same scan feeding `fontique::Collection::register_fonts`; fontique's `system` feature **off** | fontconfig |
| Matching and fallback | cosmic's list plus `catalog.rs` | fontique's CSS matching plus the host's per-script list | fontconfig |
| Shaping | harfrust | harfrust (the official Rust port of HarfBuzz) | HarfBuzz |
| Bidi and segmentation | unicode-bidi, unicode-linebreak | ICU4X (Rust); `complex-scripts` data **off** (DEFERRED) | ICU4C |
| Outlines and raster | swash, skrifa | swash, skrifa | FreeType |
| Paint (Linux, Expose) | vello, tiny-skia | unchanged | Skia |

**Two places stay non-Rust, and both are out of scope:**

- **Android's Canvas host.** It hands positioned glyph runs to HWUI, which draws them with Skia through `Canvas.drawGlyphs`. That is the platform's own renderer, not a dependency of ours. Replacing it is LLP 1076's question; the GPU painter is the Rust path, and it exists.
- **Expose's own system text** (LLP 0006). It belongs to Expose. This experiment is evidence for that decision, not the decision itself.

**Gate:** in `cargo tree -e normal,build` for `exact-linux` on `aarch64-linux-android` and `x86_64-unknown-linux-gnu`, the switch adds no `*-sys` crate, no `cc`/`cmake` build dependency, and no build script that compiles C. A crate name is not proof of language: each new crate's build script, if it has one, is read.

## 4. The swap

**Branches.**
- `text/parley` starts from origin/main in its own worktree on expo-build-1000, with a private `CARGO_TARGET_DIR`.
- Android builds use `text/parley-android`, a merge of `text/parley` into `android/explore`, remade when either moves. Its baseline is `android/explore` at the same commit.
- `android/text` (Minikin) is not merged into either. It stays a separate arm (§8 Q1).

**Vendoring.**
- Pin the newest `parley` and `fontique` on the day stage 1 starts (0.11.1 at the time of writing).
- Vendor them as complete crates.io archives, each with an `EXACT-PATCHES.md`, as cosmic-text is today.
- Every patch also goes upstream as an issue or a PR. LLP 1085's eight questions go to Nico Burns at stage 0.
- `vendor/cosmic-text` and the `[patch]` entries in `game/` and `snapback4/` are deleted when the branch lands, not kept beside Parley. The two are never linked together in a shipped build.

**Behind the seam** (LLP 1001 §6 is unchanged):

- **Shaping and breaking.** `ShapedSource` becomes a Parley `Layout`, built once per paragraph through the ranged builder, one `push` per run. `Paragraph` becomes `break_all_lines` and `align` per width.
- **Content widths.** Min- and max-content come from `calculate_content_widths` only where they agree with Chrome. Its documentation warns that mixed-direction text is approximate, so stage 1 compares min- and max-content against Chrome, bidi cases, preserved whitespace and `text-indent` included. Where it is wrong, the host keeps today's width-zero wrap for that case, or the error is a gap. Its speed is not credited until then.
- **Storage, proved first.** Parley keeps shaping and line data together in one `Layout`, and justification rewrites cluster advances. The host today shapes once and keeps several widths of one paragraph at the same time. Whether that costs a copy of the `Layout` per width, or a different arrangement, decides much of the memory and re-layout case. Stage 1 therefore opens with a spike (§5), not the whole rewrite.
- **Unchanged structure.** The paragraph stamps, the width cache, the residency accounting and the worker handoff in `transfer.rs` keep their shape. They hold `Layout`s. The handoff needs `Layout` to be `Send`, which stage 1 checks first.
- **Line box.** The host's line box stays its own: the strut plus each face's ascent, descent and gap, not Parley's `MetricsRelative(1.0)`, which gives 22 px against Chrome's 24 for Devanagari. The host's line-box pass keeps growing a line for a taller fallback face (LLP 1015 §3; the 22-against-24 px Devanagari case). It reads the metrics of Parley's runs.
- **Glyph output.** Glyph runs for the GPU painter, the CPU painter (swash) and the Canvas host's `FONT`/`GLYPHS` ops come from Parley's positioned runs. The Canvas host needs each face's file path and index, so the catalog keeps a map from face to file.
- **Text-flow input.** `exact-textflow` takes logical clusters from `Run::clusters()` and stops sorting cosmic's visual glyphs back into logical order. It keeps breaking lines itself.
- **Canvas 2D.** `canvas2d/text.rs` (`fillText`, `measureText`) moves too.
- **The font cache.** `text/font_cache.rs` restores each face's metadata and weight axis from a cached listing without opening the files. fontique's `register_fonts` takes font bytes and parses them. A naive bridge would bring back the cold-start cost the cache removed (cosmic patch 6) and keep every face's bytes resident. The design: register from the cached listing with file-backed (memory-mapped) blobs, parsing lazily or not at all, or a fontique change that admits a face described ahead of time. Validated in stage 1 with an empty and a populated cache, on a phone.
- **Windows.** `exact-windows` takes its text from `exact-linux`, and cosmic-text picks a Windows fallback list there. Its discovery and fallback move with the Linux ones, and stage 3 checks it: ordinary text, emoji, CJK and a resize, built for Windows and run where a Windows machine is available.
- **Inventory first.** Stage 0 lists every cosmic-text call the host makes, including any hit-testing or cursor geometry for links and inputs, so nothing is found missing late.

**Gaps.** Each closes with a test that compares against Chrome, or against today's behaviour where Chrome is not the reference:

- **G1 Base direction.** Thread a base level through the builder to `BidiResolver::resolve`. Accept: LLP 1053's cases (`abc אבג` and `Exact הוא מנוע` under `rtl`) order as Chrome does.
- **G2 Font admission.** Refuse a face whose `unitsPerEm` is 0, or one with `bhed` and no `head`, when it is registered. The host does it, and fontique gets a PR. Accept: the `transfer_tests/font_admission.rs` cases, ported.
- **G3 Ellipsis and `line-clamp`.** Ordinary paragraphs clamp today through cosmic-text's `Ellipsize` (`shaping.rs`, `text.rs`); the flow walker clamps on its own. With Parley, the ordinary path needs its own clamp: in the host's line pass or in `exact-textflow` over Parley's clusters, which already builds "…". Accept: 1085 F4's clamp and ellipsis cases match Chrome as cosmic does today.
- **G4 Devanagari line advance.** A line's advance is larger than the sum of its runs (`क्षत्रिय श्रृंखला द्विज`: 109.88 against 106.68 px). Trace and fix it in Parley. Accept: F4's cases break where Chrome does.
- **G5 South-East Asian scripts without dictionaries.** Plain Parley breaks Khmer before each U+200B, where UAX #14 (LB7/LB8) and Chrome break after it. It also adds break opportunities cosmic-text does not: in Thai 7 against 0, in Myanmar 97 against 0 (1085 F3, width-0 set). DEFERRED's ruling is that without a segmenter these scripts break only at spaces. Accept: on the width-0 set (q5's engine comparison; the in-repo `textflow` corpus drives the walker's own breaker and does not test the engine), per script, no more missing or extra opportunities than cosmic-text has. That set is used only to accept this gap. The veto is §6's rendered line starts.
- **G6 Blink's break table in ordinary paragraphs.** Turn on `CHROMIUM_LINE_BREAK_OVERRIDE`, with the same table `textflow/src/chrome.rs` carries, so the two paths agree. This changes behaviour on purpose: Chrome's breaks instead of UAX #14's after `/`. It is listed as such.
- **G7 System fonts without fontconfig.** fontdb's scan, or the host's cached listing, feeds fontique. The per-script fallback list moves from cosmic's `unix.rs` and `catalog.rs`. Android keeps its current choice of family (`EXACT_FONT`, Roboto for sans-serif). Accept: 1085 F4's emoji and fallback cases, and every app's screenshots (§5).
- **G9 Cosmic's other three patches.** `vendor/cosmic-text` carries six patches, not the three LLP 1085 counted. Besides admission, span storage and base direction: a soft hyphen draws the face's `-` at a break, as Chrome does; CSS `text-indent` on the first line; and the weight-axis cache (the font-cache item above). Indent maps to Parley's `Layout::set_text_indent`; the soft hyphen needs a patch or the host's line pass. Accept: `css_tests.rs`'s soft-hyphen and indent cases, ported.
- **G8 What the host does to compensate for cosmic-text.** Find out whether fontique's CSS matching retires `snap_weight` and the serif and sans resolution in `catalog.rs`. Delete them if it does; keep them if it does not.

Fix loops get three rounds per gap (RULES). After that, the gap is stopped and reported. It is not iterated.

**Tests.** The host's 174 text tests split in two:

- Those that pin CSS behaviour are ported unchanged in meaning.
- Those that pin cosmic-text's structures (span capacity, shaped-line sharing, glyph batches) are replaced by tests of the same property on Parley's structures: bounded memory per paragraph, sharing, batching.

The branch passes the five checks, and `cargo test -p exact-linux --lib --tests --no-fail-fast`, at each stage's end.

## 6. Measurement, and the rule for deciding

**Discipline.**
- Baselines and branch builds run in one session, A/B interleaved, on the same device. Thermals are noted.
- At least three runs per arm. Report the median and the range.
- A difference counts only if it falls outside the range of the baseline's own repeats.
- Baselines are re-run at the end to check for drift.
- Timings use instructions retired or thread CPU where a machine is shared. Wall-clock counts only on an idle machine.

**The matrix** (minisforum is idle Linux; expo-build-1000 is shared):

| Dimension | Linux headless (minisforum; CPU and GPU painters) | Android phones (bench harness `~/bench/android/bin`) | Expose phones |
|---|---|---|---|
| Parity | Chrome line starts, rendered, per script (1085 F3 corpus plus each script's cases, 4 widths); min- and max-content against Chrome (bidi included); the width-0 set for G5 only; LLP 1053 and F4 cases; every app's screenshots diffed, each difference explained | the same app screenshots, Canvas host | the same, if run |
| Scroll | F8's timers, heavy list, 200 steps | fling fps, ms/s, jank (`bench.py`, `daily_table.py`) | frame pacing |
| Re-layout | resize sweep of the heavy list and Markdown: text work per resize | rotation: config change to first frame (atrace `layout`), with text CPU in that frame recorded beside it | rotation, if supported |
| Memory | RSS, and text memory including the engine's own retained scratch and caches (not only the host's residency counter), after the giant Markdown document; the heavy list fully scrolled | `dumpsys meminfo` native heap and PSS after a fling | RSS |
| Start | boot to first pixel (`metrics.mjs`) | cold start content medians (`cold.py`); boot-thread text work | first frame |
| Size | stripped release binary, x86_64 and aarch64 | `.so` and APK | binary |
| Build | `metrics.mjs` warm gate and touch-one-line | — | — |

Android's rotation is an activity restart, so it shows whether a user waits longer, not text's share. P2 is decided by the Linux resize sweep. The F8 timers are a temporary patch, as 1085 F8's were: applied to both arms and never committed. The Chrome comparison runs from `~/bench/dioxus/q5`, outside the repo (§8 Q2).

**The rule** (fixed now):

- **Land** when all of these hold:
  - Parity is no worse anywhere: rendered line starts agree with Chrome at least as often as main's, per script, at every width and input; intrinsic widths too; the bidi cases right, every screenshot difference explained and accepted.
  - The rewritten tests pass.
  - Nothing regresses beyond noise in scroll, start, build, text memory or re-layout, on any surface measured.
  - Size grows by no more than 0.25 MB stripped (size is deterministic, so it gets an allowance, not a noise band).
  - At least one material win: text memory down by a quarter or more, or text work per re-layout down by a third or more, on Linux or Android.
- **Drop** when parity cannot be brought to main's within the gaps' fix rounds, or when no material win shows. If it is dropped, take LLP 1085 §Recommendation 4's two cheaper changes on cosmic-text instead:
  - Blink's table through the text-flow walker;
  - the size of a `ShapeLine`.

  The branch is parked, not deleted.
- **Mixed** (a win on one surface or metric, a material cost on another): §7 lays it out and Charlie decides.

**The predictions:**
- **P1, scroll unchanged: wrong, in Parley's favour.** Text work fell by a quarter, and main-thread CPU by 5% beyond noise.

- **P5, parity improves: confirmed.** The branch is at least main on every row.
- **P6, size about even: confirmed.** 24 KB smaller.

**The rule (§6).** Each condition holds on Linux:
- parity no worse anywhere;
- the rewritten tests pass;
- no regression beyond noise in scroll, start, text memory or re-layout;
- size within 0.25 MB;
- one material win: text memory down by two thirds, against the quarter required.

**What the rows show:**
- **Fling:** no fps, CPU or jank row moves beyond base's run-to-run range by more than 0.5 fps or 3%, and the few that fall outside it are as often better as worse. xheavy's fastest segment first read 0.4–2.0 fps lower on all three phones, as it had on 2026-10-06. Over nine pairs on each 10 Pro XL it reads +0.5 and −1.3, both inside base's range, and its late and janky frames are inside the range too. The Pixel 10a's crypto CPU read +5.5% after three pairs and +1.4% after nine, inside base's range. The 10a is the noisy phone: one fling segment's CPU ranges from 700 to 1,300 ms/s.
- **Memory:** native heap and its allocations do not move (+0.3–0.5 MB). The `Unknown` row (anonymous memory outside the malloc heap) falls by 15% on heavy, 11% on xheavy and 3% on crypto, outside base's range on every phone. Total PSS falls by 2–4% on heavy. Heavy's drop is about 8 MB, the size of Linux's text-residency drop (12.0 → 4.0 MB), which suggests where the text cache lives on Android. That is not proven. The 10a's xheavy native heap reads 165–200 MB in both arms, bimodally. Parley's median first read 21 MB higher, with two of three runs at 191–198 MB; over seven pairs the medians are 166.7 and 170.6.
- **Cold start:** of the first set's 30 rows (five apps, content and total, three phones), 29 are inside base's range, and the one outside is faster. Phone B's daily is the largest: +13 ms total in the drift set, +5 ms (inside the range) in the first.

The cold-start content time a user sees (above) does not move.
- **Rotation:** exact's own work is the depth-0 `exact …` slices on any thread, less the platform's image decoding. It is 9–22 ms of a rotation, against hundreds of ms of process CPU spent re-decoding images and compiling pipelines. Heavy moved −17% on one phone and +15% on the identical other. As on Linux, text is not what a re-layout costs here.

## 8. Open questions

1. **Minikin as a third arm on Android?** `android/text` makes Android's own text stack switchable. A Parley result answers "which Rust engine". It does not answer "Rust or the platform on Android", which trades one engine everywhere (the same breaks as Linux and the web oracle) for the phone's own fonts and fallback. The proposal: measure `EXACT_TEXT=platform` as a third arm in stage 3 if `android/text` merges into `text/parley-android` with little work, and otherwise leave it out.
2. **A checked-in Chrome parity check.** LLP 1085's comparison would become a corpus in the repo, alongside `textflow/tests/corpus`, and a test the gate runs. That is new apparatus, which needs Charlie's yes. Without it, the comparison stays in `~/bench/dioxus/q5`.
3. **Upstream or a fork.** If Linebender declines G1, G2, G4 or G5, the vendored patches stay, as cosmic-text's do. That is acceptable, but it should be known before landing.
4. **`complex-scripts`** (Thai, Lao, Khmer and Myanmar words; +4.7 MB). Out of scope here. If it is wanted later, it is a separately loaded artifact, never a cargo feature.
5. **The painter, which this does not decide.** "Fully Rust" costs nothing in shaping and layout. In drawing it may cost speed and polish: on the Linux CPU painter, glyph raster and blending are 16–17% of a scroll's main thread (1085 F8), and Skia's glyph caching and GPU text are more mature than vello's. Expose's LLP 0006 tunes small text (pixel fitting, gamma-correct blending, stem darkening); whether exact2's painters do is unverified. Expose should draw the glyphs exact2 positioned, never shape again, or measurement and pixels can disagree. Each of these is a painter question (vello and tiny-skia against Skia), not cosmic-text against Parley. A Parley result says nothing about them.
