## Context

[observed] The desktop root is `examples/t3-code/app.contract`.
`exact_js_bake::build` takes an app directory and reads its `app.contract`.
The calendar's iOS build includes its macOS build script, so it demonstrates a
shared Contract, not a platform-selected filename.

## Options

1. Replace the desktop root with a platform branch. This couples every mobile
   change to Daehyeon's UI and violates the handoff's ownership boundary.
2. Invent an `app.ios.contract` lookup. That requires a forbidden framework change.
3. Give mobile its own directory while importing shared data logic. This uses
   the existing app-directory input and keeps the two front ends independently built.

## Decision

[confirmed] The handoff selects option 3, subject to M0 proving parent imports.
`examples/t3-code/mobile/ios` is a member of Exact's root Cargo workspace.
Its build script calls `exact_js_bake::build(Path::new(".."), "ios")`.
Its manifest identifies `com.exact.t3code.ios`, admitting iPhone and iPad.
There is no separate mobile Cargo workspace or unused web shell.

[observed] The initial files came from `bun scripts/exact.mjs new`, then the
generated Apple crate became `ios`. The generated standalone workspace, web
crate and wrapper were removed because this app is a root workspace member.
No change to the generator was required.

## Shared TypeScript

[observed] Direct `../r10-connect-pairing` imports work under Bun but fail in
the native bake with TS2307. `js/bake/src/lib.rs` captures only app-local files;
its `typescript.sources` mounts refuse an ancestor containing the app. Gap 001
records the reproduction and a bounded capture proposal.

[confirmed] The handoff permits a copied-source workaround when the bake
refuses the import. `mobile/shared/r10-connect-pairing.ts` preserves the exact
body from base `ca398fe0c4bec86f163c152fa6717531954ed80a`, preceded by a GAP 001
comment and source identity. `LICENSE-T3` is retained. No parser logic is forked.
The entry tests verify a hosted pairing link and the empty bake answer. The
native bake, iPhone launch and field-edit drive passed with this fallback. The
answer appears in state and in the screenshot; no pending or failed requests remain.

## Consequences

The mobile crate has its own plan and bytecode. Desktop source remains in its
existing directory. When an adopted base changes a copied source, first refresh its copy and
source SHA, verify that body against the new revision, then rebuild mobile and
rerun the affected screens. The entry test compares the parser bodies so a stale
copy fails the mobile tests. Rebuilding alone does not update a copy. Simulator, runtime, evidence and review progress are local
notes until the relevant milestone can be published with verified results.

## Viewer build output

[observed] On this Mac, Bun 1.4.2 initializing stdout through the viewer's Rolldown import changes an inherited pipe to nonblocking mode. A bounded reproduction records the parent descriptor flags changing and a later write failing with errno35 after 65,472 bytes. This explains the mobile build script's repeated failure while printing Cargo watch lines. The shared bake helper already captures its child output.

[decision] The mobile [build script](../examples/t3-code/mobile/ios/build.rs) captures the viewer process's stdout and stderr, replays both streams and retains the child's failure status. The child cannot change the descriptors Rust subsequently uses for Cargo directives. The isolated comparison passes seven assertions for unchanged parent flags, exact output and exit7 preservation. Plain Cargo builds again without a verbose-output workaround. No framework code or blanket retry was added. Reproduction logs and the conditional upstream handoff are under `.context/t3-code-ios/build-stdout-probe/` and `exact-main-handoffs/build-script-stdout-eagain.md`.
