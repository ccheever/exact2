## Summary

The survey (LLP 1069 §4 B1) claimed that exact2 can make every device
capability drivable by an agent, and that Expo can't. This RFC states the
rule that makes the claim true, says which existing operation carries each
case, and puts one open question to Charlie.

**The rule.** A device capability is admitted in one of two shapes, and
each shape has a substitute under agent mode:

- **A fact.** Examples: reduced motion, locale, zone, online, visibility,
  a permission's state, a position being watched. The host reports it,
  and the runner re-answers the readers in one commit (LLP 1039's shape).
  In agent mode the value comes from the driver, never from the machine.
- **A request.** Examples: pick media, share, sign in, ask permission,
  get one position. The runner hands out a ticket, and the host answers
  it later (LLP 1016, 1067). In agent mode the host never shows the OS's
  surface. The request waits in `state.pending` until the agent answers
  it, or a fixture the driver named answers it at once.

No capability takes a third shape. A host API that shows system UI with
no ticket, or reads a device value that is not a fact, can't be
substituted, so it can't be tested.

**The operations.**

- **Answering a request uses `tap` and `type`.** It is the user's input to
  a system surface: choosing Allow, choosing photos, finishing sign-in. A
  request's ticket becomes an addressable target, like the navigation
  root is for a location (LLP 1038 D11).
- **Setting a fact mid-run is the open question.** `prefer` does it today
  for three display preferences and is a ninth operation, awaiting
  Charlie's ruling. §3 sets out four ways to resolve it. Each sibling
  says "the fact-setting operation" and works under any of them.

**Today's instances fall short in three places:**

- The web glue reports the machine's date, locale, zone and a fresh
  launch seed even under `?agent=1` (`host/web/glue.js`, the
  `exact_set_time` and `exact_set_place` calls).
- 1027.000.000 D3's `EXACT_AGENT_EPOCH`/`EXACT_AGENT_TZ` are not built:
  there are no hits in `host/` or `scripts/`.
- `state.pending` lists requests but gives the agent no way to answer one.

Fixing these three is the first slice (§5).

## 1. Why this is worth a rule

In an Expo app, device capabilities are tested through the platform:

- **Permission dialogs** belong to SpringBoard or the Android system UI.
  XCUITest reaches them through `addUIInterruptionMonitor` or the
  springboard application. Maestro and Detox pre-grant with
  `simctl privacy` or `launchApp: permissions`. None of these works on the
  web, on macOS, or on a physical phone in the same form.
- **Location** is `xcrun simctl location`, an Android emulator console
  command, or Maestro's `setLocation`. Each is simulator-only and
  per-platform.
- **Push notifications** are `simctl push` with a payload file, and there
  is no Android or web equivalent in the same script.
- **The photo picker** runs out of process (PHPicker). A test seeds the
  library with `simctl addmedia` and taps through another process's UI.
- **Waiting.** All of it runs on wall time. A test waits for a dialog to
  appear with a timeout, which is the flake LLP 1012 §2 removed from
  everything the runner owns.

exact2 already has the pieces that make this unnecessary:

- The runner does no I/O (LLP 1016 D1), so every answer arrives through
  one seam the host controls.
- The clock is the agent's.
- `state` reports what is pending.
- The store is empty in agent mode (LLP 1012, LLP 1018 amendment), which
  is the precedent for "agent mode reads nothing from the machine".

The rule extends that to the device. The same script then runs on four
hosts, on the agent's clock, with nothing presented by the OS.

**What it does not test is the OS's surface itself:** that PHPicker
opens, or that the permission string reads well. D8 keeps a way to see
the real thing.

## 2. Decisions

### D1 — Two shapes: a fact or a request

Every capability in LLP 1069.000–.006, and every later one, declares
which shape it is before it is built:

| shape | carried by | agent mode |
|---|---|---|
| fact | a reserved source's fields (`exactViewport`, `exactTime`, or the new fact of 1069.000), re-answered by a `Runner::set_*` in one commit | the value comes from the driver, at launch and on change (D2) |
| request | a ticket: an HTTP-shaped request (LLP 1016), an `exact-native:` request (LLP 1067), or a command whose outcome returns as an event | the host holds it for the agent (D3) or answers it from a fixture (D4) |

A capability can have both shapes. A permission's state is a fact
(`granted`, `denied` or `prompt`, the Permissions API's names). Asking for
it is a request. A watched position is a fact. `getCurrentPosition` is a
request, and a substitute answers it from that fact.

A capability that fits neither shape doesn't get a substitute. It gets a
redesign.

*Rejected: an agent operation per capability* (`location`, `permission`,
`pick`). That is the old repo's route to eighty wire names
(`rules/DEFERRED.md` §Agent API).

### D2 — Facts come from the driver in agent mode

Under `?agent=1` / `EXACT_AGENT=1`, a host reads no device fact from the
machine:

- **At launch,** the driver passes every fact with a documented default.
  It generalizes 1027.000.000 D3 from two flags to all of them:
  - `--epoch`, `--time-zone`, `--locale` and `--seed`;
  - the preferences;
  - `--online`;
  - `--permission <name>=<state>`.

  The defaults are fixed values (`UTC`, `en-US`, seed 1, online, every
  permission `prompt`), so screenshots are the same on every machine. A
  capability's LLP names its fields and defaults.
- **Mid-run,** the fact-setting operation changes one or more fact
  fields. It calls the same `Runner::set_*` the host's own observer calls,
  so the path tested is the path shipped: one commit, the readers
  re-answered.
- **The reply** gives every fact as the runner now holds it, so the agent
  reads what took effect and not what it asked for. `prefer` already
  replies this way.
- **`state`** gains `device{…}`: the facts' current values, beside
  `store`. A secret-shaped fact, such as a push token, shows its presence
  only, as `store` does.

A production launch never reads the agent's values. A test asserts that
a non-agent boot reports the machine's values, as 1027.000.000 D3 asks.

### D3 — A device request waits for the agent

In agent mode, a host's arm for a request-shaped capability does not call
the OS. It holds the ticket and reports it:

- **`state.pending`** entries gain `device: {capability, args}` for
  device requests. For example: `{"name": "avatar", "ticket": 7,
  "device": {"capability": "pick", "args": {"accept": ["image/*"],
  "multiple": false}}}`. The arguments are the app's, so an agent can
  check that the app asked for the right thing.
- **`clock settle`** does not wait for a device request. Waiting would
  hold the call to its twenty-second deadline for an answer only the
  agent can give. It returns at once with `settled: false, reason:
  "device"` and the tickets. Network requests keep their wait (1012 §2).
- **`clock +N`** fires no timeout the host doesn't own. If the app wants a
  timeout on a picker, it authors a timer, which the clock drives as
  usual.
- **The journal** gets `device pick 7 held (agent)` when the ticket is
  held, and `device pick 7 answered: 1 item` or `… cancelled` when it
  ends.

### D4 — Answering is `tap` or `type` on the ticket

A pending device request is a target. The CLI writes it `@7`, and the wire
form is `{"ticket": 7}` in place of `id`. Driver resolution refuses a
ticket that is not pending, by name, as it refuses a stale view id.

- **`tap @7 <choice>`** answers a request whose surface is a choice:
  - `allow` or `deny` for a permission (which also sets the permission
    fact);
  - `cancel` for any request (a picker dismissed, a share sheet closed,
    a sign-in abandoned), which the app sees as the platform's own
    cancellation: `AbortError` on the web's vocabulary, a failed answer
    with that name on the seam.
- **`type @7 <json>`** answers a request whose surface produces a value.
  The value is validated against the capability's result shape:
  - picked items: fixture files by path, which the host copies into
    `app:/tmp` as the real picker's result would be;
  - the callback URL of an auth session;
  - a position;
  - a share's `completed` target.

This is `tap` and `type` addressing something other than a view. LLP 1038
D11 did the same for the navigation root, where text is a location, so it
adds a target form and no operation. Each answer carries `delivery:
"substituted"`, a fifth value beside `platform`, `recognized`,
`activation` and `unsupported`, so a transcript never passes a
substituted answer off as a real one.

**Fixtures instead of the agent.** `--answer <capability>=<file|choice>`
at launch answers every request of that capability at once. For example,
`--answer pick=fixtures/cat.jpg` or `--answer share=completed`. A smoke
that is not about the picker then doesn't stop at it. A fixture's answers
go through the same host path as `type @ticket` and journal the same
lines. With no fixture, the request waits (D3). The default is never a
silent success.

### D5 — Where the substitute lives, per carrier

**The web carrier** uses the browser's own override where CDP has one, so
the app's real code path runs (`delivery: "platform"`):

| fact or request | CDP |
|---|---|
| display preferences | `Emulation.setEmulatedMedia` (what `prefer` uses) |
| locale, zone | `Emulation.setLocaleOverride`, `Emulation.setTimezoneOverride` |
| online | `Network.emulateNetworkConditions` with `offline` |
| visibility | `Page.setWebLifecycleState`, or `Emulation.setFocusEmulationEnabled` for focus |
| permissions | `Browser.setPermission` / `grantPermissions` |
| position | `Emulation.setGeolocationOverride` |
| file/media picker | `Page.setInterceptFileChooserDialog`, then `DOM.setFileInputFiles` on `Page.fileChooserOpened` |

Where there is no override, the glue holds the request in agent mode and
the driver answers it through the page. The web share sheet and an OAuth
popup or redirect are the two known cases. Date and seed come from launch
values, not from `Date.now()` and `crypto.getRandomValues`. The glue
reads these today (the §Summary gap).

**Apple and Linux** have no override API. The host's capability arm
checks agent mode and never reaches UIKit, AppKit or the OS:

- a picker does not present PHPicker;
- a share does not present `UIActivityViewController`;
- a sign-in does not start `ASWebAuthenticationSession`;
- a location request does not start `CLLocationManager`.

The check sits in one place per arm, at the top, the way `agentMode`
already gates the session's timers (`Session.swift`). The simulator's
own tools are not used: `simctl location`, `simctl privacy` and
`simctl push` work only on the simulator, not on macOS, Linux or a
phone, and not on the agent's clock.

**A native module** (LLP 1067, 1016.002) whose capability is the app's
own follows the same rule through its seam:

- In agent mode, `native.later` requests are held and listed with
  `device: {capability: "native", args: <the request>}`.
- `native.watch` topics become facts the agent can announce, through the
  fact-setting operation by topic name.

The module's Swift or page code doesn't run in agent mode unless D8's
opt-out is set.

### D6 — What the existing operations carry, by capability

| capability (LLP) | shape | the agent |
|---|---|---|
| preferences, locale, zone, font scale, visibility, online (1069.000) | fact | launch flags; the fact-setting operation |
| form controls (1069.001) | UI, not device | `tap` / `type` on the control's node; nothing new |
| media picker (1069.002) | request | `type @t ["fixtures/a.jpg"]`, `tap @t cancel`; `--answer pick=…` |
| share (1069.003) | request | `tap @t cancel`; `type @t "completed"`; `--answer share=completed` |
| SSE / WebSocket (1069.004) | request whose answers keep coming | network, not device: the carriers' existing HTTP path, or a local server the smoke starts; `pending` shows the open stream |
| randomness (1069.005) | fact (the seed) | `--seed`; the same seed gives the same ids |
| auth session (1069.006) | request | `type @t "app://callback?code=…"`; `tap @t cancel` |
| permission (1069.008, and any capability that asks) | request, then fact | `tap @t allow` or `deny`; `--permission name=state`; the fact-setting operation to revoke mid-run |
| position (survey §5 #14) | fact when watched, request when one-shot | the fact-setting operation; a one-shot is answered from the fact |
| notification tap (survey §5 #9) | an incoming location | `type <navigation root> "/thread/9"` (LLP 1038 D11), already built |
| scheduled notification (survey §5 #9) | request, then a fact (the schedule) | `state.device.scheduled`; `clock +N` past its time delivers it, as a timer |

### D7 — What a capability LLP must say

Every sibling, and every later capability LLP, carries a **Substitute**
paragraph with:

1. The shape (D1).
2. For a fact: the field names, the launch flag and the default.
3. For a request: the `capability` name in `pending`, its `args`, the
   result shape `type` accepts, the choices `tap` accepts, and the
   fixture form.
4. The web carrier's override, if CDP has one.

A capability LLP without this paragraph isn't ready to build.

### D8 — The real surface, on purpose

`EXACT_DEVICE=real` (the driver's `--device real`) turns substitution off,
following `EXACT_STORE=real`'s precedent. With it:

- the OS's dialogs and sheets appear;
- the machine's facts are read;
- `delivery` says `platform`.

It is for a person, or for a check that a string or a sheet looks right.
No smoke uses it, because it cannot be deterministic.

## 3. `prefer`, and the question for Charlie

`prefer` was built as a ninth operation (LLP 1061 D5) without taking one
of the eight off. `rules/DEFERRED.md` records it as open. This RFC widens
the question: the operation that sets display preferences is also the one
that sets every other device fact (D2). Four resolutions fit:

- **P1 — Keep a ninth, and make it general.** The ninth operation sets any
  fact by its web name. It could be renamed from `prefer` to something
  like `device`. It stays one operation however many facts there are,
  which the "count is the cost" rule cares about. It still needs one of
  the eight taken off, or the rule changed.
- **P2 — Fold into `clock`.** `clock` already moves the date, which is a
  fact, and it is the operation for "the world moves under the app, not
  the user". `clock set prefers-reduced-motion=reduce online=false`
  commits the facts at the current time, and `clock +N set …` commits them
  at a later time. This keeps eight. The cost is that `clock` gains a
  second verb.
- **P3 — Fold into `type` on a reserved target.** `type @device
  {"prefers-reduced-motion":"reduce"}` treats a settings change as the
  user's input to the Settings app. That is the same reading D4 gives a
  system dialog, and `type` on the navigation root is the precedent. This
  keeps eight. The cost is that "type" reads oddly for "go offline".
- **P4 — Launch values only.** Remove `prefer`, and set facts only by
  launch flag. This keeps eight and is simplest, but a fact that changes
  mid-run can't be tested. That is the path most likely to break: the
  re-answer commit, a reader that caches, motion started before the
  preference flipped.

D2 through D7 hold under any of the four. Only the spelling of "the
fact-setting operation" changes.

## 4. What this costs

- **Runner:** a `device` field on pending entries, a `device` section in
  `state`, and `settle`'s new reason. There is no new request type: a
  device request is a request.
- **Driver:** the ticket target form, `--answer`, and the launch flags,
  one per fact as each capability lands.
- **Web carrier:** CDP calls it already knows how to make. The glue's
  launch values come from the page's agent parameters.
- **Apple and Linux:** one agent-mode branch at the top of each capability
  arm, written with the arm. Nothing is retrofitted, because no arm
  exists yet except the date, place and preferences.
- **No new check,** script or file. `smoke.mjs` gains steps as
  capabilities land.

## 5. First slice

1. **The existing facts' substitutes:**
   - 1027.000.000 D3's `--epoch` and `--time-zone`;
   - plus `--locale` and `--seed`;
   - on every host;
   - with the web glue reading them under `?agent=1`, in place of
     `Date.now()`, `navigator.language` and `crypto.getRandomValues`.

   Held by: two runs of the smoke with the same flags give the same
   `state` and the same screenshots.
2. **`pending` entries gain `device`.** `clock settle`'s `reason:
   "device"`, the ticket target, `tap @t cancel`. There is no device
   capability yet to answer, so the test is a runner test with a
   synthetic device request.
3. **Charlie's ruling on §3.** Then the fact-setting operation takes its
   final spelling, and `online` and `visibility` (from 1069.000) arrive
   through it.

Each capability sibling brings its own substitute with it (D7).

## Not in this RFC

- **Recording and replaying a session.** That remains ✕ in
  `rules/DEFERRED.md` §Agent API. Substituted inputs keep it possible
  (1069.009); this RFC does not build it.
- **Testing the OS surface itself.** See D8.
- **Pasteboard reads.** `rules/DEFERRED.md` lists `pasteboard` among the
  agent operations not shipping. If a clipboard-read capability is
  admitted, it is a request under D1 and needs no operation.
