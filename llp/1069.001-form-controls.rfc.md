## Rulings (Charlie, 2026-09-27)

- **Q1: `select` and `option` are admitted.** `rules/DEFERRED.md` §Components now reads the tag count as a guard against invented components, not HTML's own elements.
- **Q2: rename the text field's per-keystroke `change` to `input`,** and let `change` mean commit, as HTML does.
- **Q3: a plain checkbox on iOS is Safari's square.** The `switch` attribute gives a `UISwitch`.

## Summary

Every settings screen needs a switch, and exact2 has none. The apps draw
their own:

- **Messages:** "Hide Alerts" is a `button role="switch"` holding a
  64×28 grey-or-green box with an absolutely positioned 36×24 thumb
  (`apps/messages/contact-details.contract:157-183`).
- **Typetour:** it hand-draws toggle rows.
- **The Bluesky port:** its theme chooser is a column of `role="radio"`
  buttons with a checkmark symbol (`screens.contract:600`).

None of these behave like the platform's controls. They have no drag on the
thumb, none of the platform's haptic, and none of VoiceOver's "switch
button, on". They are also wrong in dark mode unless the author remembered
`light-dark()`.

The kernel already has a `Toggle` node type and a `toggleValue` prop. The
web host maps it to `<input type=checkbox>` (`host/web/src/element.rs:208,
533, 609`). Nothing lowers to it, and no native host presents it.

This RFC adds the controls HTML already names. The Contract vocabulary
is a subset of HTML's:

```
input type="checkbox" checked=chat.muted change=setMuted aria-label="Hide Alerts"
input type="checkbox" switch checked=chat.muted change=setMuted aria-label="Hide Alerts"
input type="range" min=0 max=100 step=1 value=volume input=preview change=setVolume
input type="date" value=due min="2026-01-01" change=setDue
input type="time" value=alarm change=setAlarm
select value=theme change=setTheme aria-label="Theme"
  option value="system"
    text "System"
  each t in themes key=t.id
    option value=t.id
      text t.name
```

Each control is presented as the platform's own:

| Contract | web | iOS | macOS | Linux |
|---|---|---|---|---|
| `input type=checkbox` | `<input type=checkbox>` | a checkbox drawn as Safari draws it | `NSButton` (checkbox) | painted |
| `… switch` | `<input type=checkbox switch>` | `UISwitch` | `NSSwitch` | painted |
| `input type=range` | `<input type=range>` | `UISlider` | `NSSlider` | painted |
| `input type=date\|time\|datetime-local` | the element | `UIDatePicker` (`.compact`) | `NSDatePicker` (text field and stepper) | a text field that takes the ISO form |
| `select` / `option` | `<select>` | `UIButton` with a menu (`changesSelectionAsPrimaryAction`) | `NSPopUpButton` | a button and LLP 1021's popover |

Contract owns the value, as it does for `input` text today. The platform
owns the control: its look, recognition, motion and accessibility.
`appearance: none` (CSS) hands the look back to the author.

## Motivation

- **The hand-drawn versions cost every app the same work, and they are
  worse.** The Messages switch is 25 lines of layout, and it still doesn't
  track a finger or animate the thumb the way `UISwitch` does. A native
  switch is one line.
- **The web already has these names.** A `<div role=switch>` is what an
  author writes when the platform lacks a control. The platform has one.
- **Ports keep asking.** LLP 1069 §3 lists settings in the Bluesky port and
  in Messages. The grnl port (LLPs 1061–1066) built its record controls by
  hand as well.

## Design

### D1 — Names: HTML's, and only the subset below

`input` gains the `type` values `checkbox`, `range`, `date`, `time` and
`datetime-local`. Two tags are added: `select` and `option`. The attributes
are HTML's:

- `checked`: a bool, checkbox only.
- `value`: a string on the wire, typed per control (D4).
- `min`, `max`, `step`: range and the date types.
- `disabled`.
- `switch`: a bool, checkbox only.

**`switch`** is the attribute WebKit ships (Safari 17.4). It is proposed to
WHATWG HTML (whatwg/html#9546). A browser without it draws a checkbox with
`role=switch` semantics, which is the fallback HTML specifies. The attribute
lowers to `accessibilityRole = "switch"` as well, so ARIA sees it either
way. The ARIA spelling, `role="switch"` on a checkbox, is accepted as the
same thing. The name follows the HTML attribute where one exists and ARIA
where it doesn't, as the rest of `tags.rs` does.

**`type` must be a literal** on `input`. The compiler picks the node type
from it: text types lower to `TextInput`, and these five lower to `Control`
(D2). A bound `type` is a compile error naming the literal forms. That is
the same rule the router applies to a location (LLP 1038 D3).

**Not in this RFC:**

- **`radio`.** It needs a group (`name`), and the idioms it serves already
  have shapes. A tablist projects to a segmented control (LLP 1059). A
  list of rows with `aria-checked` and a checkmark symbol is the iOS
  Settings idiom Bluesky uses. `select` covers the compact case. Radio can
  return when an app needs a native radio group; macOS has one.
- **`number`.** `input type=text inputmode=numeric` already brings up the
  keyboard. `UIStepper` is not what the web draws for `number`.
- **`color`, `month`, `week`, `file`.** `file` is LLP 1069.002, media only.
- **`select multiple`, `optgroup`, `datalist`, `form`, `label for=`.**
  `aria-label` names a control.

**No trade.** `rules/DEFERRED.md` §Components now reads the tag count as a
guard against invented components: a built-in tag is an HTML element with
HTML's meaning, and `select` and `option` are admitted on that reading. The
five `type` values add no tag.

*Rejected:* a `select` whose options are an attribute value
(`options=list`). It loses `each`, per-option `disabled` and text children.

### D2 — One `Control` node type replaces `Toggle`

The kernel's `Toggle` (id 8) becomes `Control`. Its `type` prop (the
existing prop 15) says which widget it is. The `toggleValue` prop is
renamed `checked`: the schema spells props as DOM properties do, and the
repo deletes rather than deprecates.

A `Control` is a **measured leaf**. It lays out like an image (LLP 1011): an
intrinsic size, overridden by any CSS width or height. It holds no layout
children. A `select`'s `option` children are nodes in the tree: `each` and
keys work, and the agent sees them. They carry a fixed `display: none`,
which is what a closed `<select>` does with its options. The host reads
their `value`, text and `disabled` to build the menu.

`option` lowers to a `Text` node with `SemanticTag = "option"` and a `value`
prop. No new node type is needed.

### D3 — Intrinsic size is the platform's, because CSS says it is

CSS leaves a native control's size to the user agent. Under `appearance:
auto` (CSS UI 4 §7.2) a widget's intrinsic size is "UA-defined". Chrome's
checkbox is 13×13 with a 3/3/3/4 px margin. Safari iOS's is 16×16.
`UISwitch` is 51×31 and `NSSwitch` 38×22.

So each host reports its own intrinsic size, and **this is not a deviation
from the web standard**. It is the part of CSS that defers to the platform.
The parity oracle for a control's *box* is the author's CSS. The oracle for
its *content* is the platform.

- **Apple and Linux:** the host registers one intrinsic size per
  `(type, switch, control-size)` at boot, through the measure callback
  image already uses. A `select` measures its widest option label plus the
  button's chrome. A date control measures the formatted value in the
  locale (LLP 1069.000's `locale`, `exactTime`).
- **Web:** the browser lays these out, as it does every node.

A layout that sets explicit sizes (`width="100%"` on a range, a row with
`justify-content: space-between` holding a switch) looks the same
everywhere. That is the case the fixtures pin.

### D4 — Values are controlled, as `input` text is today; payloads are typed

Today `input value=query change=setQuery` is controlled. The host shows the
keystroke at once, the action writes the slot, and the next commit
reconciles. Controls follow the same rule:

- The host moves the control immediately: the switch flips, the thumb
  follows the finger.
- The event carries the new value.
- The committed `checked`/`value` is authoritative. An action that refuses
  the change (writes nothing) snaps the control back on the same commit.

A control without a bound `checked`/`value` holds its own state, as an
uncontrolled HTML control does.

Payloads are typed so an action's parameter is not a string to parse:

| control | payload |
|---|---|
| checkbox, switch | `bool` |
| range | `number`, already clamped to `min`/`max` and snapped to `step` by the host |
| date / time / datetime-local | `string` in HTML's value format (`2026-09-27`, `14:30`, `2026-09-27T14:30`), no zone |
| select | `string`, the chosen option's `value` |

`Event::Change(String)` becomes `Event::Change(Value)`. The runner checks
the payload against the control's type (`invalid_payload`) and refuses a
mismatch by name.

**Events.** `change` fires when the value is committed: a checkbox
toggles, a range is released, a date is picked, an option is chosen. That is
HTML's `change`. `input` fires continuously while a range thumb moves. That
is HTML's `input`, and on the other controls it fires with `change`.

**The text field follows HTML too.** Today a text `input`'s `change` fires
per keystroke, from the DOM's `input` event. That is React's `onChange`,
not HTML's. It is renamed: the per-keystroke event is `input`, and
`change` takes HTML's meaning, commit on blur or Enter. The old meaning is
deleted, not kept beside it. Every `change=` on a text input in `apps/`
(and in Bluesky, Weird Castle and grnl outside the repo) becomes
`input=`, a mechanical edit in the same change.

### D5 — Presentation: projected, like the tablist

The Apple presenters build the platform control inside the node's box, the
way `SegmentsIOS.swift` builds `UISegmentedControl` in a tablist's box
(LLP 1035.001 D10). Selection and activation stay authored; the control
reports and the plan decides.

- **iOS checkbox (no `switch`).** UIKit has no checkbox. Draw it as
  Safari iOS does: a rounded square, filled with `accent-color` and a
  checkmark when checked. The trait is `.button` plus the checked state, so
  VoiceOver reads it as Safari's does. A small custom view, not a
  `UISwitch`: the web draws a square here, and an author who wants a switch
  writes `switch`.
- **iOS `select`.** A `UIButton` configured as a pop-up button
  (`showsMenuAsPrimaryAction`, `changesSelectionAsPrimaryAction`) with one
  `UIAction` per option. That is iOS 15's native pop-up button. The menu
  is rebuilt when the options change.
- **Dates on Apple.** `UIDatePicker` in `.compact` style shows the value
  in place and opens the calendar or wheel. On macOS it is
  `NSDatePicker(.textFieldAndStepper)`, with the calendar in a popover on
  click. Both format with the reported locale and never apply a time zone,
  because HTML's values carry none.
- **Web.** The elements themselves. `element.rs` already maps `Toggle` to
  `input`. Add `select`/`option` and the `type`, `min`, `max`, `step` and
  `switch` attributes.

### D6 — Styling: `appearance` and `accent-color`

These are two CSS rows, both inherited as CSS has them:

- **`accent-color`** tints the control: `UISwitch.onTintColor`,
  `UISlider.minimumTrackTintColor`, the checkbox fill,
  `NSButton.contentTintColor`, and the date picker's `tintColor`. It takes
  `light-dark()` pairs (LLP 1034).
- **`appearance: auto | none`.** `auto` is the default and draws the
  platform control. `none` draws nothing native. The node is then an
  ordinary box the author styles, and it keeps its events, value and
  accessibility role.

  For a checkbox this is exactly the web's idiom for a custom checkbox.
  A control is a leaf, so a custom look can't have child boxes: the
  author paints it with `background-color`, `border` and
  `background-image` (LLP 1066), or keeps decoration in sibling boxes.
  (The web would use `::before`/`::after`, which Contract doesn't have.)
  Messages should simply drop its hand-drawn switch for `switch` with
  `appearance: auto`. A custom `select` is CSS's
  `appearance: base-select` (Chrome 135+), whose options are laid-out
  boxes in a popover. That's a later step, and it maps onto LLP 1021's
  popover.

Other CSS on a control (padding, border, background, font) applies to
its box as the kernel lays it out. Inside the control, the platform decides,
as a browser does.

### D7 — Linux paints them

Linux has no platform controls. The painter draws each one with vello or
tiny-skia from the kernel box and the value, sized as Chrome's defaults:

- **Checkbox:** a 13×13 rounded square.
- **Switch:** a pill with a thumb.
- **Range:** a 129 px track with a 16 px thumb that follows `pan`.
- **Date:** a text field. `type` enters the ISO form and it's validated on
  commit. No calendar popup in the first slice.
- **Select:** a button with a chevron that opens LLP 1021's light-dismiss
  popover, with the options as rows.

`accent-color` applies. Keyboard: Space toggles, arrows step a range or
move within a select, Enter commits.

### D8 — Accessibility comes from the control

A native control carries its own accessibility:

- `UISwitch` reads "switch button, on".
- `NSPopUpButton` reads "pop up button".
- The DOM's elements carry their roles.
- `aria-label` names each one, as today.

The kernel's `accessibilityChecked` prop is set from `checked`, so the
agent's `tree` shows the state on every host, Linux included. There, roles
are used only for input routing, and AT-SPI is out of scope.

### D9 — The agent drives them with `tap` and `type`

No new operation is needed. The agent uses the operations it already has:

- **Checkbox:** `tap checkbox-id` toggles it through the control's own
  activation.
- **Range, date, time:** `type slider-id 40`, `type due 2026-10-01` and
  `type alarm 14:30` set the value in HTML's value format. They fire
  `input` then `change`, as the platform would on release.
- **Select:** `type theme-select dark` chooses by option `value`, and
  `tap` on the control opens its menu.

`tree` shows `checked`/`value`, and the options as children. Everything
these controls touch is inside the app, with no device fact or permission,
so LLP 1069.007's substitutes and LLP 1069.008's grants don't apply
(LLP 1069.007 D6: "UI, not device").

## As built: slice 1 (2026-09-27)

Built by Claude (Opus 5.5): checkbox and switch, and the text field's
rename. Where it differs from the design above, the build says so here.

- **The rename (D4).** `input=` is a new handler; a text field sends it per
  keystroke and `change` on commit (the DOM's own `change` on the web; end
  of editing or Enter on Apple and Linux, which remember the field typed
  into since it took the focus). Every text `change=` in `apps/` and
  `contract/corpus` became `input=`, except two that mean commit: the
  `open-file` fields of `apps/llp` and `apps/markdown`, which
  `ExactSession.change(testId:)` delivers a path into. The compiler cannot
  tell the old meaning from the new, since `change=` on a text field is
  still valid, so it names no fix; `onChange`, `onChangeText` and
  `onInput` are refused with `input`. The agent's native `type` sends
  `input` then `change`; on the web it types, which sends `input` alone.
- **Payloads (D4).** Not `Event::Change(Value)`: `Event::Input` and
  `Event::Change` carry a `ControlValue` (`Text` or `Checked`), and the
  runner refuses a checkbox's text or a field's bool as `InvalidEvent`.
  ABI kinds: 23 is a text `input`, 24 and 25 a checkbox's `change` and
  `input` with `true`/`false`.
- **Lowering (D1, D2).** `input type="checkbox"` is `Control`, with ARIA's
  `checkbox` role and Chrome's UA margins (3 3 3 4) as fixed rows; `switch`
  (a bare word, as `scroll document` is) or `role="switch"` sets the role
  to `switch`, which is how every host knows. `checked` is refused off a
  checkbox, `switch` off an `input`, and a bound `type` with
  `lower-input-type`. `checked` is also bound to `accessibilityChecked`.
- **Size (D3).** A `Control` is a measured leaf with no natural ratio. The
  kernel's default until a host reports is Chrome's 13×13 checkbox and
  Safari's 38×22 desktop switch; Linux paints at those sizes and reports
  nothing. Apple reports the control's `intrinsicContentSize` after the
  batch (UISwitch 61×28 on iOS 26, NSSwitch 38×22).
- **Presentation (D5, D6, D7).** Web: the real element; the base sheet's
  `all: unset` is undone for checkboxes with `appearance: auto`. Chrome
  has no `switch` and draws the checkbox HTML specifies as the fallback.
  iOS: `UISwitch`, or `ExactCheckbox`, a 16×16 square drawn as Safari's
  (trait `.button`, value checked/unchecked). macOS: `NSButton` checkbox or
  `NSSwitch`. `accent-color` tints UISwitch, the iOS square and the
  NSButton; NSSwitch has no tint API and follows the system accent.
  Linux: painted in `paint/control.rs`, the off track UIKit's translucent
  `systemFill`; an unbound checkbox's state is kept by the presenter.
  `appearance: none` removes the native control everywhere.
- **Controlled (D4).** Each host shows the committed `checked` after the
  action: the web restores `el.checked`, Apple re-reads the prop, Linux
  paints the kernel's value.
- **Agent (D9).** `tap` toggles: a real click on the web and Linux, the
  control's own activation on Apple (`delivery: host-activation`,
  `native: control`). The tree transcript prints `checked=`.
- **Consumers.** Messages' "Hide Alerts" is a `switch` (a
  `setThreadMuted(muted)` action sends the toggle only for a different
  state); typetour's Airplane Mode and Bluetooth rows are switches tinted
  to its monochrome.
- **Not built in this slice:** the fixture page under `scripts/fixtures/`
  and the `smoke.mjs` step (they add apparatus, which needs a human's
  word); keyboard Space on Linux; `input`/`change` from Linux key typing is
  covered, but no Linux control takes focus.

## As built: slice 2, `select` and `option` (2026-09-27)

- **Lowering (D1, D2).** `select` is the kernel's `Control` with `type`
  `select` (a fixed prop; an authored `type` or `checked` is refused) and
  ARIA's `combobox` role; `option` is a `Text` with `SemanticTag =
  "option"`, a fixed `display: none`, and its label as the positional or
  as text children. HTML's content model is checked when the view
  compiles (`lower-option-parent`): an `option` outside a `select`, or
  anything but an `option` in one, is refused; `each`, `when` and
  `match` pass through, so keyed options work.
- **Kernel.** A `Control` may hold children and never lays them out
  (`lays_out_children`), so the options are nodes the agent's `tree`
  shows and layout never sees. `exact_kernel::control` names each
  control's kind (`ControlKind`) and reads a select's options
  (`Kernel::select_choices`: value, else the label, as HTML; the label is
  the option's text with white space collapsed; a disabled select
  disables every option) and the one it shows (`select_chosen`: the one
  its `value` names, or the first enabled one when it has no `value`).
- **Payload (D4).** `input` and `change` carry the chosen option's value,
  a `string`. The runner holds every host to HTML: a value no enabled
  option has is refused as `RunnerError::InvalidValue` with the options
  named, and a checkbox's bool at a select as `InvalidEvent`. ABI kinds
  are the text field's (1 and 23); no new kind.
- **Web.** The real `<select>` and `<option>`: an option's
  `display: none` is left out of its style, as a hidden `<option>` would
  drop out of the browser's menu. The committed value is shown again
  after the options change and after an action that refused
  (`settleValue`, in `navigation.js`, which the boot graph already
  counts). Chrome's own look and size: the UA sheet's select is not reset.
- **iOS.** A `UIButton` with `showsMenuAsPrimaryAction` and
  `changesSelectionAsPrimaryAction` (the pop-up indicator), one
  `UIAction` per option, disabled options disabled; `accent-color` is its
  tint. Its reported size is its widest option's, as HTML sizes a select,
  measured on a probe button. The options come from the kernel through
  `exact_select_options` (JSON, not a batch), and the menu is rebuilt only
  when they or the choice change. The options are not views: the Apple
  host projects neither an `option` nor its runs (they painted, before,
  as `display: none` text does not hide on Apple).
- **macOS.** An `NSPopUpButton` with items built by hand (equal titles
  would merge) and `autoenablesItems` off; its size is its cell's, which
  fits the widest item where `intrinsicContentSize` truncated it.
- **Linux (D7).** Painted as a rounded field with the chosen label and a
  chevron; a press opens a menu painted over the frame (the rows in the
  select's font, the chosen one filled with the accent), placed below the
  select or above it at the viewport's edge. A press on a row chooses it;
  anywhere else closes the menu, as light dismiss does. Linux reports the
  select's size (widest label, chevron and padding) through the kernel's
  intrinsic size, as the Apple hosts do. Not LLP 1021's popover: the
  menu's rows are not nodes, so it is the host's.
- **Agent (D9).** `type <select> <value>` chooses as the menu would
  (`input` then `change`), refused by name where no enabled option has the
  value, on every host. `tap` opens the menu on the web (a click), macOS
  (the pop-up's own `performClick`, tracked modally while the agent's
  requests still run; `type` closes it with the choice) and Linux; on iOS
  it opens nothing and says so (`delivery: unsupported`): UIKit presents a
  button's menu only under a finger, and one opened by
  `performPrimaryAction` could be neither seen nor closed by the carrier.
- **Consumer.** Type Tour's Display & Text Size page has an Appearance
  select (Automatic, Light, Dark) that calls `setScheme`, the Bluesky
  theme picker's shape. Type Tour gains a Linux crate
  (`apps/typetour/linux`), the same shape as every other app's, so the
  painted controls have a consumer to drive.

## As built: slice 3, `input type=range` (2026-09-27)

- **Schema and lowering (D1).** `min`, `max` and `step` are props (211,
  212, 213), strings as HTML writes them, shared with the date types. A
  range's `value`, `min`, `max` and `step` may be numbers: a literal is
  written as its string and a bound number goes through `toString` when
  the view compiles. The tag carries Chrome's UA margin (2 px) and ARIA's
  `slider` role; `input` and `change` carry a `number`.
- **Rules (D4).** `exact_kernel::Range` is HTML's sanitization: `min` 0
  and `max` 100 by default, a `max` below `min` is `min`, `step` 1 by
  default and none for `any`, the value clamped and snapped to the nearest
  step from `min` (half up, a step past `max` steps back), and the
  midpoint when there is no value. The runner applies it to whatever a
  host sends (text, on the text field's ABI kinds), so the action gets the
  number every host would; text that is not a number is `InvalidValue`.
- **Web.** The real element; `min`/`max`/`step` are its attributes, and
  the reset is undone for it as for the checkbox. `input` and `change` are
  the browser's.
- **iOS.** A `UISlider`: `input` as it moves (once per snapped value),
  `change` on touch-up, `accent-color` its minimum track. **macOS.** An
  `NSSlider`, continuous: `input` while the mouse is down, `change` when
  it lifts. Both report Chrome's 129 px width (a slider has no natural
  one) and their own height, and a slider's track spans its box, as the
  web's does, where CSS makes the box wider.
- **Linux (D7).** Painted: a translucent track filled with the accent to a
  16 px thumb. A press puts the thumb under the pointer (`input` then
  `change`). Dragging the thumb is not built.
- **Agent (D9).** `type <range> <n>` sets the value (`input` then
  `change`), refused where `n` is not a number; `tap` is a click at the
