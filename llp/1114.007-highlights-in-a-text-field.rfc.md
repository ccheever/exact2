## 0. Round 1, and what r2 changed

Grok raised no concerns and kept both recommendations. Astra raised one.

- **Astra C1 (a range list carries no freshness): taken.** True: the
  runner sends a binding only when its value changes (`instance.rs:851`
  skips one equal to the last), so a list equal to the previous one,
  computed for new text, never reaches the host. Replacing `@alice` with
  `@carol` gives the same `{mention, 0, 6}`; r1's D3 would have dropped or
  shifted the old ranges and never received them again. r2 makes
  `highlights` a record of the text the ranges describe and the ranges
  (D1). The host paints a record that matches the field's text as given,
  and otherwise reconciles it to the current text, provisionally (D3).
  r1's per-edit shifting state is gone; D3 is one rule over two strings.
- **Astra's ruling question: added** as §6 Q3, recommended yes.

## 1. Summary

A `textarea` takes `highlights`: a list of `{ name, start, end }` ranges in
UTF-16 offsets, with the text they were computed for. Ranges for the
field's current text paint as given; ranges for an earlier text paint
adjusted to it until the app's next set arrives. Each name is painted by a
`highlight` declaration, which is the app's `::highlight(name)` rule and takes only the
properties CSS allows there (colour, background colour, text decoration, text
shadow). Highlights paint and never lay out, so the field measures, wraps and
edits exactly as it does without them. The value stays a plain string (LLP
1045 D1). On the web this is the platform's own API: `createValueRange()` on
the field, a `Highlight` per name, `CSS.highlights`. On Apple it is TextKit
2's rendering attributes, which are TextKit's paint-only layer. The Bluesky
composer uses it to colour @mentions, links and #tags while the person types.

## 2. What Bluesky does

The composer colours `@handle`, URLs and `#tag` in the link colour as they
are typed. On native (`social-app`,
`src/view/com/composer/text-input/TextInput.tsx`), every change builds a
`RichText` from `@bsky/sdk` and runs `detectFacetsWithoutResolution()`. The
segments are then rendered as nested `<Text>` children of the React Native
`TextInput`, and the only style they set is `color` (lines 74-76 and
188-198). On the web (`TextInput.web.tsx`), the composer is a TipTap
(ProseMirror) `contentEditable` editor with a `Mention` extension. The
posted record carries the plain text and facets in UTF-8 byte offsets. The highlighting is decoration
only: nothing in the text changes.

`source.md` lists this as "styled runs in an editable textarea". It is
narrower than styled runs. Bluesky colours ranges and never changes a font,
weight or size inside the composer, so a paint-only layer covers it.

## 3. What exact2 has today

- **A field holds a string and nothing else.** `textarea` and `input` lower
  to the kernel's `TextInput` (`contract/lower/src/tags.rs:130-144`), which
  cannot hold children (`contract/lower/src/lib.rs:1038-1043`). The kernel
  measures its value as one run.
- **No range styling on any host.** The web writes a real `<textarea>`
  (`host/web/src/element.rs`, `host/web-js/src/rows.rs:609`). iOS is a
  `UITextView` on TextKit 2 (`IOS/TextAreaIOS.swift:229-232`) whose storage
  attributes are touched only for line height and kern
  (`TextAreaIOS.swift:168-174`). macOS is an `NSTextView` made with
  `usingTextLayoutManager: true` and `isRichText = false`
  (`Mac/TextAreaMac.swift:165-168`). Linux paints the value as one
  cosmic-text paragraph (`host/linux/src/paint.rs:1034-1068`). The terminal
  paints one style per field (`host/terminal/src/paint.rs:630-700`).
- **The one styled editable field is the Markdown editor** (`textarea
  markup="markdown"`, LLP 1045). `markup` takes only `"markdown"` or `"none"`
  (`contract/lower/src/lib.rs:1331-1344`). Its web side swaps the textarea for
  a `contentEditable` editor in its own on-demand wasm (`host/web-js/rt.js:1097-1122`);
  its Apple side sets attributes on the native storage and skips while text is
  being composed (`host/apple/Sources/ExactMarkdown/MarkupEditor.swift:1-5`).
  It cannot serve a composer: it reads `*`, `_` and backticks as Markdown,
  and does not style `@handles`.
- **The Custom Highlight API is already used once,** for list text selection
  on the web (`host/web/list-selection.js:17,78`).
- **No prior decision.** LLP 1069's survey and the Bluesky LLPs (1054.*) say
  nothing about composer highlighting. `rules/DEFERRED.md` does not list it.
  LLP 1035.006 row 03.12 ("Rich text and writing tools") is unchecked, and
  this RFC does not check it: highlights are not rich text.

## 4. What the web does

There is no styled `<textarea>`. Until 2026 an app had three roads:

1. **`contentEditable`**, as Bluesky's TipTap composer and exact2's Markdown
   editor do. It is a document editor with its own selection, IME and paste
   behaviour, and it is not a form control.
2. **A mirror**: a styled `div` behind a textarea whose text is transparent,
   kept in step by copying font, padding, wrapping and scroll. It drifts when
   any metric differs.
3. **The [CSS Custom Highlight API](https://drafts.csswg.org/css-highlight-api-1/)**
   (`Range`s in a `Highlight`, registered in `CSS.highlights`, styled with
   `::highlight(name)`). It changes no DOM. Baseline since 2025 (Chrome 105,
   Safari 17.2, Firefox 140). It could not reach a field, because a `Range`
   cannot point into a textarea's value
   ([csswg-drafts#4603](https://github.com/w3c/csswg-drafts/issues/4603)).

**OpaqueRange closes that gap.** `textarea.createValueRange(start, end)`
returns an `OpaqueRange` over the value, in the same UTF-16 units as
`selectionStart`. It is an `AbstractRange`, so `new Highlight(range)` takes
it. Its offsets shift with incremental edits (typing, `setRangeText`); a
wholesale `value` write resets them. Status, as of 2026-10-08:

- Chrome 152 shipped it (stable 2026-08-25), enabled by default.
- WebKit's standards position is "support"
  ([WebKit/standards-positions#541](https://github.com/WebKit/standards-positions/issues/541));
  Mozilla's is "positive"
  ([mozilla/standards-positions#1289](https://github.com/mozilla/standards-positions/issues/1289)).
  Neither has shipped it.
- WHATWG stage 2 ([whatwg/html#11478](https://github.com/whatwg/html/issues/11478)).
  csswg-drafts#4603 was closed on 2026-10-01 as covered by it.

`::highlight()` accepts only properties that do not affect layout: `color`,
`background-color`, `text-decoration` and its longhands, `text-shadow`, and
the stroke and fill colours
([css-pseudo-4 §3.2](https://drafts.csswg.org/css-pseudo-4/#highlight-styling)).
So a highlight can never move a line break. That rule is what makes the
design below cheap on every host.

## 5. Design

### D1. The shape: ranges over the value, painted by name

- **(a) Styled runs as the value** (a rich value type, or children in a
  field). LLP 1045 D1 refused this. It would put a new value type on every
  seam and a serializer between the person and their text.
- **(b) A new `markup` value** (`markup="facets"`). This bakes one app's
  grammar into the kernel, and Contract cannot change the grammar.
- **(c) Ranges the app computes, painted by name.** The app owns the
  detection, and the host only paints.

**Recommendation: (c).** It is the web's shape and leaves D1 standing.

```text
highlight mention
  color="light-dark(#1083fe, #208bfe)"
highlight link
  color="light-dark(#1083fe, #208bfe)"

textarea id="composer" value=draft change=edit highlights=draftHighlights …
```

`draftHighlights` is the record `{ value: string, ranges: list<Highlight> }`,
where `value` is the text the ranges were computed for and `Highlight` is
the record `{ name: string, start: number, end: number }`. The clone's
detector returns it whole: `{ value: draft, ranges: … }` (D3 says why the
text is part of it). `highlight <name>` is a
top-level declaration like `style`, in the place where the web would put a
`::highlight(name)` rule. Its body takes only the properties `::highlight()`
admits. Any other property is refused, with the reason that it would move
text.

- A range is clamped to its `value`, as `setSelectionRange` clamps.
- Overlapping ranges paint in list order, so a later range wins. This
  follows the highlight API's priority-then-registration order with every
  priority equal.
- A name with no declaration paints nothing and is reported once in `logs`.

The kernel gets one `str` prop that is paint-only, not `measure`. The
lowering encodes the record into it, because the schema's props are scalars.
The encoding is the implementer's choice.

### D2. Where it applies

- **`textarea`.** Built.
- **`input`.** Refused by the compiler for now with a named reason
  (`highlights` is built for `textarea`). OpaqueRange covers both, but the
  native single-line fields (`UITextField`, and macOS's shared field editor)
  need a different path, and no consumer asks.
- **`textarea markup="markdown"`.** Refused. The Markdown styler owns that
  field's paint.

### D3. Each range set names the text it describes

The app recomputes ranges after each `change`. On native that recompute
crosses to the data module and arrives later than the keystroke, so for a
moment the host holds ranges for an earlier text. And the runner sends a
binding only when its value changes (`runner/src/instance.rs:851`), so a
bare list cannot say which text it is for: replacing `@alice` with
`@carol` computes the same list, and no update arrives. That is why the
record carries `value`. New text always makes a new record, even when its
ranges are equal, and the host can always tell whether what it holds is
current.

The host applies one rule, on every host, each time the record or the
field's text changes:

- **Authoritative.** When the record's `value` equals the field's text,
  its ranges are painted as given.
- **Provisional.** Otherwise the record's ranges are reconciled to the
  field's text. The two strings differ in one span, after their common
  prefix and before their common suffix. Each range is adjusted as the DOM
  adjusts a live `Range` when that span's text is replaced: a range before
  it stays, one after it moves by the change in length, and a boundary
  inside it moves to its start. That is also what OpaqueRange does for an
  edit. A provisional range covers the characters it covered, never a
  neighbour's, and the app's next record replaces it.
- An app write to `value` needs no case of its own. The record either
  matches the new text or is reconciled to it.

The paint is a function of the record and the field's text alone, so the
host keeps no edit history, and the agent can check the result (D6).

### D4. Per host

| Host | How | Notes |
|---|---|---|
| Web, Chrome 152+ | `createValueRange` per range of D3's list; one `Highlight` per name in `CSS.highlights`; each `highlight` declaration emitted once as a `::highlight(name)` rule | The host rebuilds the ranges from D3's list on each `input`; OpaqueRange's own shifting is the same adjustment in between. Highlight names are scoped by a prefix so two apps or fields never collide. |
| Web, no OpaqueRange (Safari 27, Firefox) | Paints nothing | The text and editing are unchanged. See Q2. |
| iOS, tvOS, macOS | TextKit 2 rendering attributes on the field's `NSTextLayoutManager` (`setRenderingAttributes(_:for:)`), mapped from the declaration: `.foregroundColor`, `.backgroundColor`, `.underlineStyle`/`.underlineColor`, `.strikethroughStyle` (`text-shadow` only if TextKit honours `.shadow` as a rendering attribute, to verify in the first slice) | Rendering attributes paint without touching the text storage. So no `typingAttributes` bleed (typing after a mention stays plain), no undo entries, and no change to the value write-back (`TextAreaIOS.swift:316-331`). Not applied while text is being composed (`markedTextRange`, `hasMarkedText()`), the same guard as LLP 1045. Applied after composition ends. |
| Linux, Windows | The field's paragraph is built from runs instead of one spec, with each run's colour and decoration, as inline `text` runs already paint | The value, measurement and editing are untouched (`paint.rs:1034-1068`). |
| Terminal | Each cell takes the range's colour and underline | The terminal already paints styled cells. It is cheap, but it waits for a consumer, and until one asks the host ignores the prop. |

**Unknown, to settle in the first slice:** whether a TextKit 2 rendering
attribute's range survives an edit inside it, or must be reapplied after each
edit. The host reapplies after each edit either way, from D3's list.

### D5. Offsets

UTF-16 code units, as `selectionStart`, `slice` and `indexOf` already are
(`docs/contract-grammar.md:1015`, `:519`). Bluesky's facets are UTF-8 byte
offsets. The clone converts them in its data module, which is where it
computes the facets anyway.

### D6. The grant, the clock, the agent

- **Grant:** none. This is paint only and reaches no device or network.
- **Data modules:** unchanged. The clone's detector is a pure function of
  the draft, with no clock or timer (LLP 1027.000).
- **The agent:**
  - `type composer "hi @alice.bsky.social"` drives the field as today.
  - `tree` shows the `highlights` prop as the app set it.
  - `screenshot` shows the paint. Chrome is the oracle for it, as for every
    other paint (on Chrome 152+, the agent's web host).
  - `state` reports, per field, the ranges the host paints and whether
    they are authoritative or provisional (D3), so a test can tell a stale
    range from a fresh one without pixels.
  - No new operation.

## 6. Questions for Charlie

1. **A `highlight` declaration, or `style` blocks reused by name?** Reusing
   `style` needs no new syntax. But a `style` admits every property, and a
   field would then have to ignore the ones that move text, silently.
   **Recommended:** the `highlight` declaration. Its body is checked against
   `::highlight()`'s list, so a mistake fails the build.
2. **Browsers without OpaqueRange: paint nothing, or a mirror?** Because
   highlights cannot change layout, a mirror would match the field's lines
   exactly. It is still a second text layer to keep in step: scroll, IME
   underline and selection colour. WebKit and Mozilla both support the
   proposal. **Recommended:** paint nothing, and revisit if Safari has not
   shipped OpaqueRange by the time the clone's web build has users.
   Both reviewers agree.
3. **Are highlights snapshots tied to one value of the field, with the
   host's adjusted ranges only provisional?** Astra asked for this ruling,
   so the boundary between the app and the host is fixed before the API
   is. The alternative is that the host owns the ranges between updates,
   as r1 had it; Astra showed that loses an equal list for new text, and
   no other fix fits the runner's equal-value rule without a change to
   the runner. A second alternative is a revision number in place of the
   text, which is shorter on the seam, but a field has no revision today
   and the app would have to thread one through `change`. **Recommended:**
   yes, with the text as the tie (D1, D3). The cost is the draft crossing
   the seam twice per keystroke, which is small for a composer.

## 7. What the clone does after

- **The detector.** The data module gets a `highlights(draft)` function. It
  runs `RichText`'s `detectFacetsWithoutResolution()`, as Bluesky does, and
  returns `{ value: draft, ranges }`, the ranges in UTF-16 and
  named `mention`, `link` and `tag`. The clone keeps the byte-offset facets
  for the post record.
- **The composer.** The composer's `textarea` (`sheets.contract` in the
  clone) takes `highlights=…` and declares three `highlight`s.
- **Verified by:**
  - `type composer "hi @alice.bsky.social see https://bsky.app #art"`;
  - `state`, which shows three authoritative ranges at the right offsets;
  - `screenshot` on web (Chrome), iOS and macOS, compared with Chrome;
  - typing inside a mention and then deleting it, so the range is
    provisional, stretches, and then goes;
  - replacing `@alice` with `@carol` in one edit, so an equal range list
    for new text still arrives and paints.

## 8. Effort and complexity

**exact2: M.**
- **Easy:** the Contract attribute and declaration, the schema prop, and the
  web path, which is a few dozen lines over APIs the web host already uses
  once.
- **Moderate:** D3's reconciliation, a pure function of two strings and
  a list that every host needs, tested once against a table of edits.
- **Hard:** making TextKit 2 rendering attributes hold across edits and
  composition on both UIKit and AppKit.
  That is where the time goes, and it needs a person typing with Japanese
  IME on an iPhone, not only the agent.
- **Linux:** S. It builds the field's paragraph from runs.

**Clone: S.** The facet detector already exists in `@bsky/sdk`. The
clone adds one function, one attribute and three declarations.

## 9. Not in scope

- **Styled runs that change metrics** (bold, size or font in a field). That
  is rich text: LLP 1035.006 row 03.12, and refused as a value by LLP 1045
  D1.
- **`input` on native** (D2).
- **The mention typeahead,** which is the clone's popover over the field. It
  can be placed today from the caret's offset, or with OpaqueRange's
  `getBoundingClientRect` once that is wanted.
- **Highlights' accessibility semantics** (`Highlight.type`, for spelling or
  grammar). The facets are not announced, as Bluesky does not announce them.
