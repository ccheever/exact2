## 0. r3: the narrowing

On 2026-10-18 this RFC was widened, without approval, into a decoration editor: inline
fonts, block layout and markers, hidden source, atomic chips, a checkbox `toggle`, an
`"undo"` mode on `setRangeText`, and a `contentEditable` field on the web. Three blind
reviews (GPT-6 Astra, Grok 4.7, Fable) all said rework. They found a second Markdown
editor beside LLP 1045's with different caret and hiding rules, a `<textarea>` replaced
by a `div` in Safari and Firefox even for paint-only spans, hidden-range editing left to
each browser, prefix/suffix reconciliation that can leave stale metadata over new text
(`aaa` to `aaaa`), DOM names given meanings the DOM's do not have, and no approval on
record. Charlie ruled the same day: back to r2's paint-only highlights, kept under the
names that landed (`decorations`, `decoration`, `TextDecorations`), with `rangeFrame`
kept and tightened (D7). T3 Code's Markdown composer moves to LLP 1045's
`markup="markdown"` editor.

Removed, from the code and this document: blocks, hidden ranges, atoms and their marker
vocabulary; the checkbox's `ToggleEvent` (`toggle` is a popover's alone again, host
dispatch kind 50 `open`/`closed`); the `contentEditable` field; decorated intrinsic
measurement; and `setRangeText(…, "undo")`. LLP 1069.001's "no undo step, for now"
stands for plain fields. On LLP 1045's Markdown editor each `setRangeText` is one undo
step, as a `format` is, with no flag (LLP 1045 D1, D6, 2026-10-19).

## 1. Summary

A `textarea` takes `decorations`: a `TextDecorations(value, spans)` record, the text the
spans were computed for and a list of `TextDecorationSpan(name, start, end)` in UTF-16
offsets. Spans for the field's current text paint as given; spans for an earlier text
paint adjusted to it until the app's next record arrives. Each name is painted by a
`decoration` declaration, which is the app's `::highlight(name)` rule and takes only the
properties CSS allows there. Decorations paint and never lay out, so the field measures,
wraps, edits and undoes exactly as it does without them. The value stays a plain string
(LLP 1045 D1). On the web this is the platform's own API: `createValueRange()` on the
field, a `Highlight` per span, `CSS.highlights`. On Apple it is TextKit 2's rendering
attributes, TextKit's paint-only layer. The Bluesky composer uses it to colour @mentions,
links and #tags while the person types.

## 2. What Bluesky does

The composer colours `@handle`, URLs and `#tag` in the link colour as they are typed. On
native (`social-app`, `src/view/com/composer/text-input/TextInput.tsx`), every change
builds a `RichText` from `@bsky/sdk` and runs `detectFacetsWithoutResolution()`; the
segments are rendered as nested `<Text>` children of the React Native `TextInput`, and the
only style they set is `color`. On the web (`TextInput.web.tsx`) the composer is a TipTap
`contentEditable` editor with a `Mention` extension. The posted record carries the plain
text and facets in UTF-8 byte offsets. The highlighting is decoration only: nothing in the
text changes, and no font, weight or size changes inside the composer, so a paint-only
layer covers it.

## 3. What the web does

There is no styled `<textarea>`. An app had three roads: `contentEditable` (a document
editor with its own selection, IME and paste behaviour, not a form control); a mirror (a
styled `div` behind a transparent textarea, which drifts when any metric differs); and the
[CSS Custom Highlight API](https://drafts.csswg.org/css-highlight-api-1/), which changes no
DOM but could not reach a field, because a `Range` cannot point into a textarea's value
([csswg-drafts#4603](https://github.com/w3c/csswg-drafts/issues/4603)).

OpaqueRange closes that gap. `textarea.createValueRange(start, end)` returns an
`OpaqueRange` over the value, in the same UTF-16 units as `selectionStart`; it is an
`AbstractRange`, so `new Highlight(range)` takes it. Chrome 152 shipped it (2026-08-25);
WebKit's standards position is "support" and Mozilla's "positive"; neither has shipped it
(as of 2026-10-08).

`::highlight()` accepts only properties that do not affect layout: `color`,
`background-color`, `text-decoration` and its longhands, `text-shadow`, and the stroke and
fill colours ([css-pseudo-4 §3.2](https://drafts.csswg.org/css-pseudo-4/#highlight-styling)).
A highlight can never move a line break, and that is what makes the design cheap on every
host.

## 4. Design

### D1. Spans the app computes, painted by name

The app owns the detection; the host only paints. Styled runs as the value (LLP 1045 D1
refused it) and a new `markup` value (it would bake one app's grammar into the kernel)
were the alternatives.

```text
decoration mention color="light-dark(#1083fe, #208bfe)"
decoration link color="light-dark(#1083fe, #208bfe)" text-decoration="underline"

component Composer
  state draft = ""
  derive marks = TextDecorations(value=draft, spans=facets(draft))
  view
    textarea id="composer" value=draft input=edit decorations=marks
```

`decoration <name>` is a top-level declaration, scoped and imported like `style`, in the
place where the web would put a `::highlight(name)` rule. Its body takes what
`::highlight()` admits and the kernel has rows for: `color`, `background-color`,
`text-decoration` (`text-decoration-line`), `text-shadow`. Any other property is a compile
error that names these (`lower-decoration-style`); it would move text.

- A span is clamped to its `value`, as `setSelectionRange` clamps; an empty one paints
  nothing.
- Overlapping spans paint in list order, so a later span wins: the highlight API's order
  of registration with every priority equal.
- A name with no visible declaration paints nothing and is reported once in `logs`.

The kernel has two paint-only `str` props: `decorations`, the record as named JSON, and
`decorationStyles`, the compiler's table of the declarations visible in the field's source
file, as `[style id, literal]` rows. Neither is measured.

### D2. Where it applies

- **`textarea`.** Built.
- **`input`.** Refused (`lower-decoration-field`). OpaqueRange covers it, but the native
  single-line fields need a different path, and no consumer asks.
- **`textarea markup="markdown"`.** Refused. The Markdown editor owns that field's paint;
  app-supplied highlight ranges on it are LLP 1045's follow-up (QUEUE).

### D3. Each record names the text it describes

The app recomputes spans after each `input`; on native that crosses to the data module and
arrives later than the keystroke. The runner sends a binding only when its value changes,
so a bare span list could not say which text it is for: replacing `@alice` with `@carol`
computes the same list. The record therefore carries `value`, and new text always makes a
new record.

One rule, on every host, each time the record or the field's text changes:

- **Authoritative.** When the record's `value` equals the field's text, its spans paint as
  given.
- **Provisional.** Otherwise each span is reconciled to the field's text. The two strings
  differ in one replacement, after their common prefix and before their common suffix
  (never splitting a surrogate pair). Each boundary moves as DOM moves a live `Range`'s
  when that text is replaced: one before it stays, one after it moves by the change in
  length, one inside it moves to its start. The app's next record replaces the result.

Common prefix and suffix cannot recover edit identity in repeated text (`aaa` to `aaaa`
places the insertion at the end). For paint that is tolerable: the span is provisional and
the next record corrects it. The rule is `Decorations::resolve` in
`kernel/src/text/decorations.rs`, shared by Apple and Linux through Rust; the web's
`decorations.js` mirrors it, since the JS target links no kernel, and is tested against the
same table.

### D4. Painting never edits

Restyling never makes an undo entry, never changes the value, and is deferred while an input
method composes: a host does not repaint between `compositionstart` and `compositionend`
(marked text on Apple), and catches up when the composition commits, a commit that changes
no text included. Linux and Windows have no input-method composition.

### D5. Per host

| Host | How |
|---|---|
| Web, with `createValueRange` (Chrome 152+) | `decorations.js`, loaded after first paint by the first decorated field: one `Highlight` per span over `createValueRange(start, end)` in `CSS.highlights`, and one `::highlight()` rule per span from its declaration. The `<textarea>` is the browser's throughout. |
| Web, without it (Safari, Firefox) | Paints nothing. The textarea, its text and editing are unchanged. No mirror and no `contentEditable` stand in (r2 §6 Q2, ruled). |
| macOS, iOS, tvOS | `FieldDecorations.swift`: colours as rendering attributes on the field's `NSTextLayoutManager` (`addRenderingAttribute(_:value:for:)`, applied again to each fragment TextKit lays out anew through `renderingAttributesValidator`). TextKit 2 draws a rendering attribute's `.foregroundColor` and `.backgroundColor` but not its `.underlineStyle` or `.strikethroughStyle` (verified on macOS 27), so the field draws those lines itself under the range's visual segments, at its font's underline position. No `typingAttributes` bleed, no undo entry, no change to the value write-back. Not applied while `hasMarkedText()` / `markedTextRange`. |
| Linux, Windows | The field's paragraph is built from runs, each with the field's font and a span's colour, background and line, so every advance is the plain field's. |
| Android, terminal | Paint nothing yet (QUEUE); the source and editing are unchanged. |

Only the web paints `text-shadow`: whether TextKit 2 draws a `.shadow` rendering attribute
is unverified, and the Linux painter has no shadow for a field's run.

### D6. Offsets

UTF-16 code units, as `selectionStart`, `slice` and `indexOf` are. Bluesky's facets are
UTF-8 byte offsets; the clone converts them in its data module.

### D7. `rangeFrame`

`rangeFrame(id, start, end) -> Geometry`, actions only, beside `frame(id)`: DOM's
`Range.getBoundingClientRect()` for a textarea's range. It places a mention popover at the
caret (`rangeFrame("composer", caret, caret)`). It is re-approved on its own, not as part of
decorations.

- UTF-16 offsets into the field's value, truncated toward zero. A non-finite or negative
  offset, `start > end`, or `end` past the value's length gives `unavailable`; nothing is
  clamped.
- Collapsed, the caret's rectangle at that offset where the caret is painted: width 0, the
  height of the text there (its font's content area, as Chrome measures it; 2026-10-20,
  theme2's 18:18 ruling, which was "the line's height"); an empty line's caret on that
  line, an empty field's at its start (theme2's 18:42 ruling). Chrome's `createValueRange`
  answers those at the preceding text's end and with a zero rectangle at the viewport's
  origin, so the web measures them from a copy of the field's text laid out in its box. Otherwise one viewport-space union box of its line fragments'
  text boxes, an empty box (a line break's) counted only when every box is empty.
- Untrimmed when scrolled out or clipped by the field, as `frame`. Reading never focuses,
  selects or scrolls.
- `unavailable` also when the field is missing or hidden, while text is composed, or on a
  host with no reader: Android (whose field is the platform's own), the terminal, and for a
  plain textarea a browser without `createValueRange`. `provisional` as `frame`'s, while
  layout is.
- Linux and Windows read the field as they last painted it (2026-10-20, theme2's 17:27
  ruling): its text boxes (its glyphs across, their font's content area down), at the field's paint origin, bounded under the
  transform it was painted with; a field placed by a perspective is `unavailable` there.
  Windows reads by construction (the same presenter), not yet run on Windows.
- A plain `textarea` and `textarea markup="markdown"` (source offsets) both answer, on the
  web (`createValueRange`; the Markdown editor's own source mapping), on Apple (the
  field's TextKit 2 layout) and on Linux (whose Markdown field paints its source). An
  `input` is unavailable.
- It reads the layout last drawn: `setRangeText` then `rangeFrame` in the same action
  measures the old text.

### D8. The grant, the clock, the agent

No grant: this is paint only. The detector is a pure function of the draft. `type` drives
the field as today; `tree` shows the `decorations` prop as the app set it; `screenshot`
shows the paint (Chrome is the oracle); `state.decorations` reports, per field, the spans a
native host paints and whether they are provisional (Apple, Linux).

## 5. Ruled

- **A `decoration` declaration, not `style` blocks reused by name** (r2 Q1): its body is
  checked against `::highlight()`'s list, so a mistake fails the build.
- **Browsers without OpaqueRange paint nothing** (r2 Q2).
- **A record is a snapshot of one value; the host's adjusted spans are only provisional**
  (r2 Q3).

## 6. Still open

- Revisit painting nothing if Safari has not shipped OpaqueRange by the time the clone's
  web build has users.
- `text-shadow` on native hosts.
- Android and the terminal (QUEUE).
- App-supplied highlight ranges on LLP 1045's Markdown editor, for T3 Code's composer
  (QUEUE; LLP 1045's to decide).

## 7. Acceptance

- `@alice` then `@carol` in one edit: an equal span list for new text still arrives and
  paints.
- Typing before, inside and after a span; a span is provisional and adjusted until the next
  record; astral characters stay whole.
- The field is still a `<textarea>` on the web; Apple's text storage and undo history are
  untouched; Linux's advances equal the plain field's.
- Composition is not repainted mid-edit.
- `rangeFrame`: a caret rectangle when collapsed, a union box otherwise, `unavailable` out of
  range or while composing, on the web, on macOS and iOS, and on Linux.

## 8. Not in scope

- Styled runs that change metrics (bold, size or font in a field): rich text, LLP 1035.006
  row 03.12, refused as a value by LLP 1045 D1.
- Hidden source, chips and block layout in a plain field: LLP 1045's editor.
- Highlights' accessibility semantics (`Highlight.type`). The facets are not announced, as
  Bluesky does not announce them.
