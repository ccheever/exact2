## Summary

Today an app says what it may reach in two unconnected places:

- **Grant lines** in its data sources: TypeScript's `export const grants`,
  and Rust's `fn grants()`. The bake already unions them into the
  compatibility id's `grantCeiling` (`bake/src/compat.rs`).
- **Hand-written `Info.plist` keys** under `host.ios.permissions` and
  `host.macos.permissions` in `app.json`. These are copied verbatim, checked
  by nothing, and unrelated to any grant.

This RFC makes the grant the only declaration. The rest is derived from it:

```ts
// app.ts
export const grants = `
net.fetch https://api.example.com
device.microphone purpose.microphone
device.speech-recognition purpose.speech
`;
```

```json
// strings/en.json
{ "purpose.microphone": "Records your journal entries.",
  "purpose.speech": "Turns your recordings into text on this device." }
```

From those lines the bake writes:

- the iOS and macOS usage strings, one `.lproj/InfoPlist.strings` per
  translation;
- the hardened-runtime entitlements a notarised Mac build needs;
- the web's `Permissions-Policy`, with a denial for every feature not
  granted;
- one printed table of **what this app can reach**, which the deploy dry run
  and the install page both show.

A first-party device capability refuses at call time without its grant, as
`fetch` already does. A native module states what it reaches through the
source that owns it. A device grant that a bundle adds changes the grant
ceiling, so the classifier already sends it to a binary release, which is
where an `Info.plist` has to change.

## Motivation

**A notarised Mac build of grnl can't hear.** `exact release` signs with
`--options runtime` (`scripts/exact.mjs:225`) and passes no entitlements
file. Under the hardened runtime, microphone access needs
`com.apple.security.device.audio-input`, whatever `Info.plist` says. The
development build works, the release is silently refused, and nothing in
the repository connects the two. `host.macos.permissions` (393b784c, found
porting grnl, F9/F14) fixed the usage string only.

**Nothing checks the strings against use.**
- On iOS, touching a protected resource without its usage key terminates
  the app. A missing key surfaces as a crash on first use, on a device.
- An extra key is a claim that App Review reads and nobody else does.
- Today `host.ios.permissions` is an open object: any key, any text.

**The grant ceiling already does the hard part.** D3a put the grant ceiling
into the compatibility id, and the deploy classifier refuses a bundle whose
grants are not a subset of the installed binary's (`scripts/app.mjs`, the
`grantCeiling` check). A permission is exactly that kind of fact: the text
is inside the signed binary, and an update can't add it. The mechanism
exists. The declaration just never reached it.

**The web half exists too.** The render server derives the pages' CSP
`connect-src` from `net.fetch` lines (`host/render/src/serve.rs`, `csp()`).
`Permissions-Policy` is the same derivation with a different header.

**Expo spreads this across config plugins** and hand-written `infoPlist`
entries, and prints no summary. One declaration with a readable result is
something exact2 can offer and Expo doesn't (LLP 1069 §4).

## Design

### D1 — `device.<name> <purpose-key>`: a grant family, named by the web

A device grant is one line: `device.` followed by a web Permissions API name,
then a strings key.

- It is an exact2 grant like `surface.read`. `io_grants` strips it before
  `ibex2` parses the rest, so the vendored grammar is unchanged.
- The grammar rule stays "one capability, one target, nothing after". The
  target is a key, not prose. That keeps the line one line, and the text
  translatable.
- The bake refuses a key the base strings table (LLP 1060 D1) lacks, with
  the id `grant-purpose`. Every refusal is reported in one run, as the
  strings checks are.
- Grant names come from the Permissions Registry where one exists. A name
  the web lacks is a declared deviation, listed in D2's table with its
  reason.

*Rejected:*
- **A quoted purpose inside the grant line.** It breaks the one-target
  grammar that refuses a split typo, and it can't be translated.
- **A `permissions` object keyed by grant.** That's a second declaration to
  keep in step with the first, which is the problem this RFC removes.

### D2 — One table maps a name to every host's spelling

The table lives in the bake, as data: `bake/src/`, beside `compat.rs`.

| grant | iOS `Info.plist` | macOS `Info.plist` + hardened-runtime entitlement | web `Permissions-Policy` | notes |
|---|---|---|---|---|
| `device.microphone` | `NSMicrophoneUsageDescription` | same + `com.apple.security.device.audio-input` | `microphone` | grnl, through a Swift module |
| `device.camera` | `NSCameraUsageDescription` | same + `com.apple.security.device.camera` | `camera` | camera stays deferred (`rules/DEFERRED.md`); the row exists so a native module can declare it |
| `device.geolocation` | `NSLocationWhenInUseUsageDescription` | `NSLocationUsageDescription` + `com.apple.security.personal-information.location` | `geolocation` | LLP 1069 §5 #14 |
| `device.notifications` | none (iOS's prompt text is fixed) | none | none (not policy-controlled) | the grant still gates the request; push adds `aps-environment` when LLP 1069 §5 #9 lands |
| `device.speech-recognition` | `NSSpeechRecognitionUsageDescription` | same | none | **deviation:** the web has no name; its speech API is gated by `microphone` |
| `device.photos-add` | `NSPhotoLibraryAddUsageDescription` | same | none | **deviation**, same reason: saving to the library |

- The web's feature names fill the policy-controlled column. A row the web
  lacks is marked, never invented.
- **The picker needs no grant.** PHPicker and `NSOpenPanel` run out of
  process and hand back only what the user chose (LLP 1069.002). Reading the
  whole library would be a `device.photos` row, and nothing asks for it.
- **`auth.*` lines derive through the same table** (LLP 1069.006 D2, D8).
  They are not `device.*` rows, since they carry no purpose text:

  | grant | Apple | web |
  |---|---|---|
  | `auth.callback https://host/path` | associated domain `webcredentials:host` | none |
  | `auth.callback scheme:/path` | none (not registered, on purpose) | none |
  | `auth.apple <client id>` | `com.apple.developer.applesignin` | none |
  | `auth.passkey <rp id>` | associated domain `webcredentials:<rp id>` | none |

- Contacts, calendars and Bluetooth get rows when a module needs them
  (LLP 1069 §5 #8). Adding a row is one table entry with no host code.

### D3 — Who declares, and who enforces

**First-party capabilities are enforced.** A host capability that exact2
ships reads the running grant set before it acts, and refuses by name when
the grant is missing. Examples are geolocation (§5 #14) and notifications
(§5 #9). `net.fetch` already works this way. The refusal is a failed
answer, which is data (LLP 1016 D4). The agent's `logs` names it.

**Native modules are declared, not enforced.** A Swift or Rust module
(LLP 1067) or a view module (LLP 1024) calls platform APIs directly, where
no runner check can reach. It declares through **the source that owns it**:

- the TypeScript module that activates it (LLP 1067 D2), or
- the Rust source that constructs it,

using the same `grants` string. The OS is the enforcer: its prompt, and its
refusal when the key is missing. The declaration's job is to make sure the
binary carries what the OS asks for, and that the reach table says it.

- The bake's rule is simple. A build whose union has a `device.*` line gets
  that row's keys and entitlements. A build without the line gets none.
- An undeclared microphone in a Swift module still builds, then fails on
  first use as it does today. The bake doesn't read the linked binary's
  imports (`AVAudioSession`, `CLLocationManager`) to catch it (ruled); that
  comes back only if the crash-on-first-use class shows up in practice.

*Rejected:* a `grants` argument on `swift_native()` in `build.rs`. That's a
third place to declare, and it describes the Swift, not what the app
reaches.

### D4 — The derived outputs, and the keys this deletes

**`infoPlist` and `macInfoPlist`** (`host/apple/build.mjs`):
- They write each row's keys from the receipt's grant ceiling, which is
  already read at `buildReceipt.compat` before the bundle is assembled.
- The text comes from the base table.
- Every other table in `strings/` writes `<tag>.lproj/InfoPlist.strings`
  with the translated purposes. A translation that lacks a key falls back to
  the base, as `t` does.
- `CFBundleLocalizations` lists the tags.

**`entitlements()` and `exact release`:**
- The iOS device entitlements gain any row entitlements that iOS needs
  (today none; push's `aps-environment` later).
- `exact release` passes `--entitlements` with the hardened-runtime rows
  when the ceiling has any. That fixes the Motivation's microphone.
- The file is generated and never committed, like the iOS one.

**Deleted, not deprecated:**
- `host.ios.permissions` and `host.macos.permissions` leave
  `scripts/app.schema.json` and both plist writers
  (`host/apple/build.mjs:497`, `:665`). grnl, outside the repo, changes its
  one line (ruled).
- A manifest that still has them fails schema validation. Its error names
  the grant form to use instead.
- `host.ios.localNetworking` stays. It is the development client's reach to
  the dev server, not the app's, and a production bake never writes it.
- `urlSchemes` and `associatedDomains` stay too. They are routing (LLP 1038
  D8), not permissions.

**`host.ios.backgroundModes` becomes `device.*` rows with audio** (ruled),
not before. A background mode is one line of an app's reach that an update
can't add, so `device.background-audio` and its siblings are rows in D2's
table when LLP 1069 §5 #15 lands. No app sets a mode today
(`apps/caltrain/app.json` sets `[]`; `build.mjs:495` copies it through).

### D5 — The compatibility id follows for free, plus the purposes' digest

`device.*` lines are grant lines, so they are already in `grantCeiling`.
Two things follow:

- **A bundle that adds a device grant fails the classifier's containment
  check against every installed binary.** The deploy table then says a
  binary release is required, which is true: the `Info.plist` must change.
  No new classifier row is needed.
- **A purpose's text is binary-coupled too**, because it is in the
  `Info.plist`. The compat inputs therefore gain `grantPurposes`: a digest
  of every locale's text for every granted key. Editing a purpose, or its
  translation, classifies as a binary change and never as a silent OTA that
  leaves the plist stale. The other strings in `strings/` stay OTA-able, as
  LLP 1060 has them.

### D6 — The web: `Permissions-Policy` beside the CSP

**Render server.** `serve.rs` gains `permissions_policy(grants)`, beside
`csp()`:
- `feature=(self)` for each granted row that has a web name;
- `feature=()` for every other feature in the table.

A page's own code can then never reach an ungranted feature, which is the
same promise the CSP makes for `connect-src`.

**A static dist** (`host/web/build.mjs`, served by any static host) can't
send headers, and `Permissions-Policy` has no `<meta>` form. It gets no
enforcement and says so in the reach table (D7).

*Adjacent, not here:* the static dist could carry the CSP as a `<meta
http-equiv>`, which does exist. Whether it should is a web-host question
for LLP 1048's owner.

The iframe's `allow` attribute stays deferred (`rules/DEFERRED.md`,
LLP 1020 §5). An `iframe` inherits none of these features.

### D7 — What this app can reach: one table, printed and published

The bake prints the union as a table, and both existing surfaces show it.
The **deploy dry run** (`scripts/deploy.mjs`, whose table is already its
whole output) gains the section. The **install page**
(`/.exact/install/`, LLP 1030.003 D6a) gains a plain-language list, using
the base-locale purposes:

```
reach                          purpose                                    enforced by
net.fetch api.example.com      —                                          runtime (all hosts), CSP (served web)
sqlite.open app:/data/notes.db —                                          runtime
device.microphone              "Records your journal entries."            OS prompt; declared by module `recorder`
device.geolocation             "Shows the weather where you are."         runtime + OS prompt; Permissions-Policy (served web)
```

- The **"enforced by"** column is what keeps the table honest. It says
  whether the runtime checks a line or whether the line is a native
  module's declaration (D3).
- The install page is generated public UI outside the app's boot graph, so
  it costs no first-pixel bytes.

Two kinds of line appear that are not `device.*`:

- **`auth.*`** (LLP 1069.006): "signs in at bsky.social", enforced by the
  host's `exact-auth:` arm.
- **The file picker** (LLP 1069.002 D4): "picks files (`image/*`,
  `application/json`)", derived from `input type=file` in the plan, not
  from a grant; the user's selection is the consent.

This adds no new file and no new command.

### D8 — Linux

Linux has no prompt and no usage-string mechanism. The first-party runtime
check (D3) is the whole enforcement there. The table's columns for Linux
are empty, and the reach table still lists every line. Portals (Flatpak's
`xdg-desktop-portal`) are left until there is a packaged Linux consumer.

## What stays out

- **Asking for more at runtime, and grants per user or per install.** A
  grant set is fixed at creation (`vendor/ibex2/src/grant.rs`), and durable
  capability grants are deferred (`rules/DEFERRED.md`). A device grant is a
  ceiling. The OS prompt is where the user says yes, per install.
- **Prompt timing.** When to ask is each capability's own design, for
  example a request that asks on first use. This RFC only makes sure the
  binary can ask.
- **Checking the binary for undeclared APIs** (ruled out for now, D3).

4. **Web and the reach table:** `Permissions-Policy` in `serve.rs`, and

grnl is the first consumer: it moves its `host.macos.permissions` to
`device.microphone` and `device.speech-recognition`.

## Substitute

Grants have none: a grant is a build-time ceiling, not a device input. The
prompt a granted capability shows is a request, answered under the agent
with `tap @t allow` or `deny` and preset with `--permission <name>=<state>`;
the state is a fact `prefer permission.<name>` sets (LLP 1069.007 D2, D4).

## Decided

1. The purpose is a strings key (LLP 1060); a literal is refused (D1).
2. No scan of a linked binary's imports; add it later if needed (D3).
3. `backgroundModes` becomes `device.*` rows with audio, not before (D4).
4. `host.macos.permissions` is deleted and grnl changes one line; the Mac
   release entitlement is fixed now, on its own (D4, slice 2).
