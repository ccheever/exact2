## 1. Decision

An application should stay pleasant after a year of use: opening a note or sending a
message should cost what that operation names, not what the app has accumulated.
[LLP 1027.004](1027.004-bounded-resource-answers.plan.md) bounded the *answer*. This
plan bounds what is left — the producer, the durable write, and the native fill —
in the consumers that have the problem, in this order:

1. **Fieldnotes stops sending every body to answer a library query.** It is the only
   place where legal, admitted data makes an app *unusable* rather than slow: a
   notebook of 1,000 notes at the per-note cap returns
   `query result exceeds 16 MiB limit` and will not open.
2. **The browser file store stops reading every file to perform one operation**, and
   Fieldnotes stops exporting the whole database to answer a read.
3. **A Messages write, and its three-second sync tick, stop touching the whole record
   set.** This is the one that grows with ordinary use.
4. **Native filling gets one collection path and a presentation policy**, and iOS
   gets the rationed presenter macOS already has.

**The trade.** Generic mechanism waits. No page cache, keyed delta, FTS5 index,
stored search projection, shared view, typed buffer, shared heap, scheduler, second
state graph, benchmark app, new script or sixth check. No schema migration. §8 lists
what comes off; §9 lists what stays O(N) and says so out loud.

**If only one thing gets built, build slice 1.** It turns a notebook that cannot be
opened into one that can, and it is one SQL change, one new source and one contained
Contract change.

### F7b. A Messages write pays four whole-record-set passes, and the idle tick pays two more

A single sent message runs:

1. `snapshot()` builds a record for every person, every message in every live thread
   and every recoverable message, then round-trips each through
   `JSON.parse(JSON.stringify(…))` to detach it (`apps/messages/app.ts:400-409`).
2. `persist` walks the union of held and candidate keys and computes `canonical()` —
   a key-sorting `JSON.stringify` — for **both sides of every key**
   (`apps/messages/snapback-client.ts:96-98`).
3. `new Map(this.held)` copies the whole held map after admission (`:116`).
4. On failure, `restore(client.initial())` rebuilds the model and every index
   (`app.ts:477`).

The larger cost is not a write at all. `apps/messages/app.contract:534` runs
`every(3000, synchronize)`, and `sync` throttles at exactly 3,000 ms, so every tick
does work. Its `finally` runs unconditionally:

```ts
const current=await this.read();                                                  // :188
const changed=canonical([...current].sort())!==canonical([...this.held].sort());  // :189
```

`read()` (`:66-84`) pages **every** durable record out of storage and rebuilds the
map; line 189 then canonically serializes every record **twice**. An open, idle
Messages pays that every three seconds, forever. The neighbouring measurement is
[LLP 1027.003 §F5](1027.003-value-transfer-and-shared-storage.research.md#f5-avoidable-work-and-answer-granularity-need-separate-experiments):
the whole-record `persist` comparison was 294 ms (275–375) at 25,000 rows on an M5,
and `snapshot`'s detach 50.0 ms. This is a source-inspection claim about the shape of
that work, not a new measurement.

### F11. Browser storage does whole-file work for every operation

Found by [LLP 1027.003.001 §3](1027.003.001-bounded-application-work-astra.plan.md),
verified here. These are declared initial limitations of
[LLP 1027 D10](1027-typescript-data-sources.rfc.md), not defects in SQLite:

1. **Every non-query storage op exports and rewrites the whole database.**
   `persist()` runs `sqlite3_js_db_export` over the entire database and
   `atomicWriteFile`s it (`host/web/storage-worker.js:113-123`); `dispatch` calls it
   after every op that is not a query (`:189`). `open` reads and deserializes the
   whole file (`:140-150`).
2. **Fieldnotes turns a read into a write.** `withDatabase` opens per operation and
   `database()` runs `CREATE TABLE IF NOT EXISTS` each time
   (`apps/fieldnotes/app.ts:28-37`) — an `execute`. So **a library read exports the
   whole database today.**
3. **Every file-store operation enumerates every file, contents included.** `run()`
   issues `store.getAll()` and materializes a Map of all records before the operation
   inspects one (`host/web/storage-fs.js:166-167`) — including the `atomicWriteFile`
   that (1) performs. The two compound.

This bounds what slices 1 and 3 can honestly claim on web, and it is why slice 2
exists. It does **not** license replacing the browser SQLite backend here (§8).

## 3. Slice 1 — Fieldnotes answers with summaries, and bodies are their own resource

### D1: No new columns, and no migration

r1 proposed stored `excerpt` and `search` columns; 1027.003.001 proposed neither but
paid for it with a pager and a chunked candidate scan. r2 stores nothing. The excerpt
comes from a bounded prefix and search keeps its exact predicate (D3).

`rules/RULES.md` says delete, don't deprecate. A schema change to a notes app means
either losing a developer's notes or writing the migration the rules refuse. Not
needing one is the better answer, and it removes r1's open question outright.

### D2: One summary answer, and no pager

The notebook is capped at 1,000 notes (`apps/fieldnotes/app.ts:89`), so the row count
is already bounded. What is unbounded is the **bodies**. The library answer therefore
drops `body` and keeps every matching note:

```sql
SELECT id, title, pinned, substr(CAST(body AS BLOB), 1, 600) FROM notes
 ORDER BY pinned DESC, id DESC
```

**Why a BLOB.** SQLite's `substr` over a TEXT value stops at an embedded NUL. Verified
by running it: `substr(char(0) || 'visible', 1, 20)` returns the empty string, while
the same over `CAST(… AS BLOB)` returns all eight bytes. `validate`
(`apps/fieldnotes/app.ts:48-50`) checks only lengths, and `parseBackup` accepts any
string, so a restored backup can carry NUL and a TEXT prefix would silently show
`'An empty page.'` for a note that has text. Taking bytes also makes the budget exact
rather than "up to three bytes a character". The bytes arrive as a `Uint8Array`
(`host/web/storage-worker.js:88-92`), are decoded non-fatally, and a trailing
replacement character produced by cutting a multi-byte sequence is dropped when — and
only when — the full 600 bytes came back.

600 bytes is at least 200 UTF-16 units for any encoding (three-byte characters are the
worst case at one unit per three bytes), so the prefix always carries at least twice
the 100 units the excerpt needs.

**The budget.** `storage-worker.js:85-99` charges 24 bytes a cell plus the value, so
the whole answer is at most 1,000 × (4 × 24 + id + 3 × 160 + 600) ≈ 1.2–1.4 MB against
the 16 MiB result limit — not the 600 KB r2 claimed, which mixed UTF-16 units with
bytes and omitted the cell charge. `total` stays a separate `SELECT count(*)`, which is
what the header shows (`apps/fieldnotes/app.contract:160`). The `Note` shape loses
`body`; the sidebar stays one scrolling list, unchanged for the reader.

**The prefix is not always enough, and r3 does not pretend otherwise.** Both reviews
rejected r2's claim that a short prefix only ever yields a shorter preview. A body of
200 spaces followed by `Meeting notes for Tuesday` collapses to `" "` — **none of the
real text**. That is wrong content, not a cosmetic difference. So:

1. Compute each excerpt from its decoded prefix, exactly as today
   (`body.replace(/\s+/g,' ').slice(0,100) || 'An empty page.'`).
2. Collect the ids whose collapsed prefix is shorter than 100 UTF-16 units **and**
   whose prefix came back truncated (a full 600 bytes).
3. If that set is non-empty, re-read those bodies in chunks of 25
   (`SELECT id, body FROM notes WHERE id IN (…)`, at most 25 × 60 KB ≈ 1.5 MB a chunk)
   and recompute their excerpts from the whole body.

In an ordinary notebook step 2's set is empty and step 3 issues no query at all. In an
adversarial one it degrades to reading every body in bounded chunks — slower than
today, but still never a refused answer. That degradation is declared in §9.

**The surrogate cut.** `.slice(0,100)` can cut a surrogate pair, and `serde_json`
rejects a lone-surrogate escape, so such an answer fails to decode — a pre-existing
defect that contradicts S1's promise that every admitted note is reachable. r3 backs
the cut off a bisected pair, so the excerpt is 99 units instead of a broken 100, and
declares that correction. SQLite's `substr` itself never splits a code point: over
TEXT it counts code points (`substr('a😀b',1,2)` returns `a` plus the whole emoji,
verified), and over a BLOB the decode step handles the boundary.

### D3: Search keeps its exact predicate, scanned by keyset on one connection

The predicate stays
`(title + '\n' + body).toLowerCase().includes(query.toLowerCase())`. SQLite's `LIKE`
and `lower()` fold ASCII only; JavaScript folds the whole of Unicode. Substituting SQL
matching, tokenised search or FTS would quietly change what search means for
non-ASCII text, and that is a product decision nobody has made.

**An empty query never takes this path.** `''.includes('')` is true of every row, so an
empty query is answered by D2's single statement and no body is read. Only a non-empty
query scans.

**Keyset, not OFFSET.** r2 chunked with `LIMIT 50 OFFSET ?`. Both reviews rejected it:
with no `(pinned, id)` index each chunk is a full table walk plus a skip, so twenty
chunks cost on the order of N²/50 row visits and twenty whole-body scans where today
there is one — slower than the path it replaces, while holding the lease. r3 scans by
keyset on the primary key instead:

```sql
SELECT id, title, pinned, body FROM notes
 WHERE id < ? ORDER BY id DESC LIMIT 50
```

`id` is `INTEGER PRIMARY KEY`, so this is a rowid walk: one pass, no sort, no new
index. Each chunk is filtered, its summaries accumulated and **its bodies dropped**
before the next chunk is read. At most 50 × 3 × (160 + 20,000) bytes of text a chunk,
about 3 MB, well inside the 16 MiB budget.

**Ordering, and why `id` order is the right scan order.** The answer must be ordered by
`(pinned DESC, id DESC)`, but the *scan* is ordered by `id` alone and the accumulated
summaries — at most 1,000 of them — are sorted at the end in TypeScript. This is not
only simpler: it is what makes the scan safe. Astra's counter-example was a concurrent
pin moving a row between the two `pinned` groups, which makes an already-passed row
reappear or a not-yet-seen row vanish. A pin cannot move a row in `id` order, so a
keyset scan on `id` is stable under it by construction, and needs no cross-chunk
revision guard. An insert during a scan lands at a higher id the scan has already
passed, so a note created mid-search is absent from that answer — the same snapshot
semantics today's single statement has.

**The lease.** The scan runs on one connection, without an explicit read transaction.
Grok suggested wrapping it in `BEGIN` so completeness would not depend on who else
writes. That is not portably available and would cost more than it buys: the storage
seam's write transaction accepts execute commands only, the worker refuses anything but
a single statement (`host/web/storage-worker.js:35-53`), and any `execute` triggers a
whole-database export on web (F11) — the cost D5 exists to remove. The keyset-on-`id`
ordering below is what makes the scan safe without one. That contradicts
D5's "keep the lease short" unless D5 is scoped, so it is: D5's rule governs ordinary
reads, and this scan is the one declared exception. On web the connection is an
exclusive Web Lock (`host/web/storage-fs.js:57-82`, `ifAvailable: true`), so another
tab's `sqlite.open` gets `EBUSY` for the length of a maximal scan; on native
`ibex2-sqlite` uses SQLite locking with a 5 s busy timeout, so the Rust `backupNotes`
owner waits rather than fails. Both windows are declared in §9. They are shorter than
r2's OFFSET design and longer than today's single statement.

Typing in the editor is Contract state, not a source call, so it is unaffected. What
the held transaction does delay is another Fieldnotes source — a save, or opening a
different note. Fieldnotes declares `"typescript": {"placement": "worker"}`
(`apps/fieldnotes/app.json`), so on web the scan runs off the UI thread; on native the
executor may dispatch inline, so there the cost lands wherever that executor runs.

### D4: Opening a note is its own resource, and every editor field is qualified

The list button carries the body today — `press=edit(note.id, note.title, note.body,
note.pinned)` (`app.contract:212`) — which is the only reason the body is in the
answer. r2 replaced it with a `note` resource behind a single `touched` flag. **Both
reviews broke that design**, and r3's replacement is shaped by what they broke.

What r2 got wrong, all of it confirmed against the source:

- **One flag erases the fields you did not type in.** With `editorBody = touched ?
  body : opened.body` and `edit` never seeding `body`, typing a title flips *body and
  pinned* to their stale `""` and `false`. Saving then empties the note and unpins it.
- **The reference baseline vanished.** `reference*` still fell back to `original*`
  (`app.contract:47-49`), which `edit(id)` no longer wrote, so every freshly opened
  note was instantly `dirty` and the sidebar stayed disabled — and `discard` could not
  clear it.
- **A pending resource keeps its committed value** (LLP 1016 D3). Opening B while A is
  loaded showed *A's text under B's title*, and a keystroke before B arrived would
  write A's text over B.
- **`note("")` throws.** `id("")` fails its regex (`apps/fieldnotes/app.ts:45`).

r3:

- `action edit(id)` → `noteId = id; version = version + 1; confirmDelete = false`, and
  clears **three** flags: `titleTouched`, `bodyTouched`, `pinnedTouched`.
- `resource opened = note(editingId, saveRevision, serviceRevision) as shape Opened`,
  keyed on `editingId` — not `noteId` — so a new note keeps its identity after
  `saveNote` returns its id. It answers `{id, title, body, pinned, found}`, echoing the
  requested id, from `SELECT title, body, pinned FROM notes WHERE id = ?`. The empty id
  is handled **before** `id()` and answers `Now` with an empty record and no storage
  call, the way `library` already answers during bake.
- `derive openedReady = opened.id == editingId` — every editor derive is qualified by
  it, so a stale or pending answer is never shown.
- `derive referenceTitle = match saved { case some(s) => s.version == version and not
  s.failed ? s.title : loadedTitle, case none => loadedTitle }` where
  `derive loadedTitle = openedReady ? opened.title : ""`; body and pinned the same.
  `original*` are deleted.
- `derive editorTitle = titleTouched ? title : referenceTitle`; body and pinned the
  same. With no flag set, `editor* == reference*`, so `dirty` is false on a clean open
  — the defect the reviews found.
- `changeTitle`, `changeBody` set their own flag; `togglePin` sets `pinned = not
  editorPinned` (the **displayed** value) and its flag. `discard`, `edit`, `newNote`,
  `remove` and `restore` clear all three.
- The title, body and pin controls are disabled while `editingId != "" and not
  openedReady`, so no keystroke can be applied to an unloaded body.
- `save` sends `saveNote(editingId, editorTitle, editorBody, editorPinned, version)`.

Binding an editable field to a derive is legal — `value=` lowers as an ordinary prop
binding over any expression (`contract/lower/src/lib.rs:1327`). r2 cited
`app.contract:186` as precedent; that field is `readonly=true`, so it was not evidence
and the citation is withdrawn. No app binds an editable field to a derive today, so S1
verifies it by driving the app, not by reading the compiler.

The existing `version` generation guard and the save-to-deleted-id failure behaviour
are unchanged (`app.contract:44-52`, `app.ts:83-94`). Searching must not clear a draft
or refresh a body underneath edits; pinning may move a note in the list, and the editor
still owns its id.

### D5: A read stops exporting the database

Hoist `CREATE TABLE IF NOT EXISTS` out of the per-operation path: run it once per
process, and again only when a statement fails with a missing-table error, then retry.
An ordinary `library` or `note` read then issues no `execute`, so `storage-worker.js`
performs no `persist` and no whole-database export.

Scoped, after review, to exactly what it covers:

- **The first operation in a process still exports**, because the lazy `CREATE` is an
  `execute`. S1.6 is therefore stated as "after process-local schema init", not "a read
  never exports".
- **`restoreNotes` and `deleteNote` join the retry**, and the retry replays the **whole
  transaction** — `DELETE FROM notes` plus its inserts (`app.ts:128`) assumes a table
  that a deleted file will not have, and web's `open` deserialises an empty database
  without one (`host/web/storage-worker.js:144-152`). Match both the native
  `"SQLite: …"` message and the worker's bare one when detecting it.
- **The Rust `backupNotes` owner is not covered.** It runs its own
  `CREATE TABLE IF NOT EXISTS` on every call (`apps/fieldnotes/data/src/lib.rs:71-72`),
  so a backup still exports. D5 is not claimed for that path.
- Ordinary leases stay per operation, so the Rust owner can acquire the file. D3's
  search transaction is the one declared exception.

### S1 — acceptance

Extending `apps/fieldnotes/apple/tests/notebook.rs` (which already has `library` and
`save` helpers) and `apps/fieldnotes/web/tests/worker.rs`. That file is 1,002 lines
against the 1,500-line cap; the additions go in a sibling test file rather than raising
the cap. Every criterion below was rewritten after review to close a hole where it
would have passed with its defect present.

1. **The recorded failure is gone.** A notebook of 1,000 notes at the 20,000-unit body
   limit answers `library` with `ready: true`, the correct `total`, every note
   reachable, and no `query result exceeds 16 MiB limit`. Seed the aggregate boundary
   directly in isolated storage; the 4 MB backup limit must not become the fixture's
   accidental notebook limit.
2. **The answer is summary-only and bounded.** `library`'s answer bytes at 100 and at
   1,000 maximal notes scale with the note count, not the byte count. Bytes, not time
   — `timed_answer` in `apps/messages/apple/tests/window.rs:303` shows the shape, and
   bytes are deterministic.
3. **Search is unchanged in meaning.** A differential fixture whose every result equals
   today's implementation's on the same notebook: a non-ASCII uppercase needle (Turkish
   `İ`, Greek final sigma, `ß`), an empty needle (which must take the single-statement
   path and read no body), title-only, body-only, and a match spanning the `\n` join.
   Also: a note inserted mid-scan is absent rather than duplicated, and a note pinned
   mid-scan still appears exactly once.
4. **Excerpts are unchanged, including where the prefix is not enough.** Every note in
   the fixture matches today's excerpt byte for byte: an empty note (`An empty page.`),
   a whitespace-only note (`" "`, *not* the empty-page fallback), a leading-whitespace
   note, **a body of 200 spaces then real text** (the case that forced the second
   pass), a body with a leading NUL and one with an interior NUL, and a body whose
   100th UTF-16 unit is a high surrogate — which must produce a decodable answer.
5. **Editing is unchanged, and a clean open is clean.** Open A without editing:
   `dirty` is false and B's button is enabled. Open B while A is loaded: B's chrome
   never shows A's text, and the controls are disabled until B arrives. Then: edit,
   save, discard (which clears dirty), pin as the first interaction, title-only edit
   preserving the body, body-only edit preserving the pin, a save to a deleted id, a
   new note saved then edited then discarded, and a failed save preserving the draft.
6. **A read performs no database export.** Counted at the worker seam, stated as:
   after process-local schema init, a `library` or `note` query issues no `execute` and
   triggers no `persist`. The first operation in a process is expected to export and is
   asserted to, so a warmup cannot hide it.
7. **`restoreNotes` and `deleteNote` survive a missing table**, replaying the whole
   transaction after the retry.
8. Web and headless-Linux Fieldnotes drives pass with existing testIds, and the drive
   is what verifies that an editable field bound to a derive actually round-trips.

## 4. Slice 2 — The browser file store stops reading everything

`run()` in `host/web/storage-fs.js` loads every record, contents included, before any
operation inspects one (`:166-167`). Point operations — `readFile`, `stat`,
`writeFile`, `atomicWriteFile`, `remove` — must fetch only the target and the ancestor
records they need, inside the same transaction, with the same app scoping, Web Locks,
atomic publication and failure behaviour.

Directory operations are **not** exempt. r2 allowed them a full-enumeration fallback,
which Astra rejected: `readdir` filters after materialising the whole store
(`:207-212`), so listing a tiny directory still loads an unrelated large database.
They use path-bounded key ranges — `getAllKeys()` over an `IDBKeyRange` on the path
prefix — and fetch contents only where the operation actually needs them. File removal
and recursive directory removal are distinguished.

Keep the existing callback shape: `run` takes the paths or range an operation needs.
No new file API, no diagnostic service.

**S2:** the existing browser storage tests pass unchanged; a point read of one file in
a store holding many large files transfers only that file; **a directory listing in
that same store transfers no unrelated file's contents** — both counted as bytes at
the IndexedDB seam, so neither passes with the amplification intact. Directory
operations keep their current results.

**This slice does not replace browser SQLite persistence.** Removing whole-file import
and export needs page-backed persistence, not another cache over
`sqlite3_js_db_export`, and it must answer ordinary `storage.fs` access, cross-tab
ownership, quota failure, crash recovery and existing durable data. §8 names it as the
next storage priority and leaves it there.

## 5. Slice 3 — A Messages write pays for the records it changed

### D6: The idle tick stops re-reading everything (slice 3a)

`sync`'s `finally` re-reads every durable record and canonically serialises the whole
history twice, on every tick, whether or not anything happened
(`apps/messages/snapback-client.ts:188-189`).

r2 proposed skipping that when the watermark had not advanced. **Both reviews rejected
the signal**, with two different counter-examples, both verified:

- `observe_store` durably clears the old partition, and then `/schema` can throw
  (`snapback-client.ts:139-148`). No watermark advanced, no record was applied, no
  outbox entry settled — and the model still shows the old conversations.
- Catch-up after a reset can finish on the *same numeric watermark* it started from
  (`:144-155`), so "did not advance" is true while records were applied.

r3 therefore uses a **reconciliation-owed latch**, not a comparison:

- `acquire` sets it on any of: a store reset, a backend adoption, a page that applied
  any record, a snapshot catch-up. `sync` also sets it when an outbox entry settles.
- It **survives exceptions** — a throw anywhere in `acquire` leaves it set — and it
  survives across ticks, so a failed re-read is retried on the next tick rather than
  leaving the model permanently stale.
- It is cleared only after a successful re-read *and* model publication.
- When it is clear, the tick issues no record query and performs no canonical
  comparison. Status and queued-count updates are already their own cheap calls
  (`:186-187`) and are unaffected.

This lands alone, ahead of the journal.

### D7: A write produces its changed records (slice 3b)

Replace `persist(completeRecords)` with an edit batch: record keys mapped to
replacement payloads or explicit deletion, where an omitted key means unchanged.

**r2's funnel was wrong, and this is the most important correction in r3.** r2 claimed
every membership change funnels through `insertMessage`, `replaceThread`,
`removeMessages`, `archiveMessages` and `refreshPreview` plus the container writes.
Both reviews independently enumerated durable mutations that do not:

| Path | Record it changes |
|---|---|
| `markRead` (`app.ts:284`) | `person:*` `unread`, written directly |
| `setConversationUnread` (`:285-289`) | `person:*` `unread`, written directly |
| `react` (`:381-383`) | `message:*` `reactions`, mutated in place |
| `sendMessage` (`:353`), `advanceReplies` (`:375`) | `person:*` `preview`/`time`/`unread`, bypassing `refreshPreview` |
| `advanceReplies` (`:365`) | every outgoing message's `delivery`, on the 300 ms tick |
| `expireDeleted` (`:117-121`), reached from `recentlyDeleted` (`:259-260`), which is **not** in the persist bypass at `:470-473` | recovery `message:*` rows |
| `ensureConversation` (`:196-209`) | `people.unshift` and `groups.set` beside `replaceThread` |

And r2's §9 claimed rollback made a missed key safe. **That is false**: a missed key
raises nothing, the batch is empty, `persist` returns, and the change is silently lost
at the next reopen. Instrumenting r2's list would have shipped that.

So r3 does not hook mutation sites. It declares footprints per **source**, which is a
small auditable table beside twenty handlers rather than an invariant spread over every
field write:

- Each source handler declares the record keys its arguments let it touch —
  `markRead(id)` → `person:${id}`; `react(id, messageId, …)` → that message's key;
  `advanceReplies` → the people and outgoing messages it advanced; `recentlyDeleted` →
  the recovery rows `expireDeleted` dropped.
- **A debug-only verifier** recomputes the whole snapshot after each mutation and fails
  loudly when it disagrees with the journal's claim. It is the deterministic gate: in a
  debug or test build a missed key is a hard failure at the mutation that caused it,
  not a lost record discovered at reopen. It compiles out of release.
- S3's durable-equivalence property covers **every** source, so a newly added source
  with no declared footprint fails there too.

The rest of the batch mechanics:

- The mutation prepares candidate records **without mutating the committed model**,
  validates shape, key length, payload bytes and the record count, then admits one
  atomic `putRecords` exactly as today.
- **Detachment is load-bearing, not hygiene.** Grok's second failure: if `held` is
  updated in place *and* its entries alias live model objects, then `react` mutating
  `m.reactions` already corrupts `held`, so when `persist` throws before `admit`, the
  rollback at `app.ts:477` rewinds to an image that already contains the change — the
  UI keeps it, the error is recorded, and the next mutation finds `canonical` equal and
  never retries. Prepared records are therefore detached at preparation time, exactly
  as `snapshot()` detaches today but only for touched keys, and `held` only ever stores
  detached values. Only then does in-place `held` update replace `new Map(this.held)`.
- A no-op mutation produces no durable batch. A canonical comparison of a *touched* key
  is allowed to avoid a redundant write; discovering changes by enumerating the model
  is not.
- `seed()` keeps whole-model semantics — it is the first write of a fresh store.
- Pure reads keep their existing bypass (`app.ts:470-473`). `recentlyDeleted` is not in
  it and must not be added to it: it expires recovery rows, which is a durable change.

Three bookkeeping repairs that 1027.003.001 identified and r3 adopts: **stable person
order positions** (person records persist array positions at `app.ts:402-404`; assign a
stable position on insertion rather than renumbering everyone after a prepend), a
**tracked outgoing set** so `advanceReplies` stops visiting every outgoing message on
the 300 ms tick, and **local transient rollback** replacing the whole `pending` map
copy at `app.ts:474`.

**Failure and bulk semantics.** Before durable admission, a failure discards the
prepared edit and leaves the draft and committed model intact. After admission, a
publication failure recovers from durable state and is never reported as an unexecuted
write that is safe to repeat with a new id; an uncertain outcome stays pending until
reconciliation. Whole `restore()` stays as exceptional recovery and initial load, and
stops running after successful small writes. A bulk delete, recovery or purge is
**preflighted**: if its complete effect exceeds 512 changed records — records, not
messages (`snapback-client.ts:105`) — it is refused whole, with an explanation. It is
not split into separately committed batches, the cap is not raised, and no prefix is
silently deleted.

### S3 — acceptance

Extending `apps/messages/snapback.test.ts` (which already drives the actual Wasm
device, SQLite and server, and injects a failed durable commit) and the native
draft/reopen and refused-save cases in `apps/messages/apple/src/snapback_tests.rs`
(whose `one_ui_edit_is_one_mutation_and_refused_batches_leave_no_partial_edits` reads
the outbox with `op:'queued'` at `:333` and `:352`). Each criterion below was rewritten
to close a hole the reviews found.

1. **The idle tick is silent, and a reset tick is not.** With no local edit and an
   empty server page, ten consecutive `syncMessages` ticks issue zero record queries
   and perform zero canonical comparisons. **A reset/catch-up fixture** — a replaced
   server store, where the watermark ends where it began — performs exactly one re-read
   and one model publication. A tick whose `/schema` fetch throws after
   `observe_store` leaves the latch set, and the next tick reconciles.
2. **A write admits what it changed**, at 1,000 and at 25,000 stored records, for a
   send, a reaction, **a mark-read**, a mark-unread, a draft edit, a mute, a delete and
   a recovery. The unread and reaction cases exist because r2's design would have
   admitted nothing for them.
3. **The debug verifier is the gate.** With the verifier armed, the scripted sequence
   in (4) runs with no disagreement between the journal and a recomputed snapshot. A
   deliberately undeclared source footprint must fail it at the mutation. The 3×
   warm-minimum ratio at `window.rs:329-340` is also recorded, but as a weak
   regression signal only — thread-splice cost can fail a correct journal, and a
   leftover whole-model pass can hide under construction cost. It does not certify
   anything on its own.
4. **Durable equivalence over every source.** A scripted sequence of sends, deletes,
   recoveries, recovery expiry through `recentlyDeleted`, reactions, mark-read,
   mark-unread, draft edits, mutes, blocks, contact and group creation, and delivery
   advancement, after which the store's contents equal what today's whole-model
   `persist` writes.
5. **Failure paths hold.** A mutation that changes the model and then fails **before**
   admission leaves no trace in `held` and the rollback restores the pre-mutation

### D10: What a distant jump shows — ruled, then corrected by review

**Charlie handed this decision to me on 2026-09-20.** r1 argued against publishing
estimated geometry; 1027.003.001 argued for it with strict rules. **The ruling stands:
publish provisional row space rather than hold the frame.** But r2's reasoning for it
was wrong in a way both reviews caught, and the correction changes what has to be
built.

**What r2 got wrong.** It argued that the platform moves the scroll offset regardless,
so the viewport arrives empty and filling in anchor order only reorders an unavoidable
hole. That is not what happens. `ListWindow::ration` never budgets the rows the
scrollport shows (`runner/src/instance/window.rs:563-567`), `exact_list` treats a
limit of 0 as unlimited (`host/apple/src/abi.rs:1420-1423`), and UIKit's
`scrollViewDidScroll` → `syncLists()` always passes 0. So today a jump builds its whole
scrollport in one report and **the rows are never blank — the frame is late**, exactly
as `QUEUE.md` records at 30–55 ms. There is no hole to reorder. The LLP 1002 D4
citation is withdrawn: "scroll always wins" governs pan-versus-scroll arbitration
(`NodeViewIOS.swift:1186-1187`), not whether a viewport may present without rows.

That makes r2's three constraints vacuous: no placeholder exists to make legible, and
"no placeholder unless the work exceeds one opportunity" can never fire while visible
creation is unlimited. Astra added a fourth hole — an anchor that is ready in 1 ms with
a visible remainder that takes five frames would be forbidden provisional content while
most of the viewport is unavailable.

**What r3 builds.** The policy is not prose over the existing fill path; it is a change
to that path:

1. **Budget visible creation.** `ration` stops exempting the scrollport, and iOS stops
   passing limit 0. Without both, nothing else in this section can happen.
2. **The threshold is the whole visible region, not the anchor.** Provisional space is
   published only when the complete visible set cannot be built within one frame
   opportunity — so ordinary short jumps still present complete, and a fast anchor with
   slow neighbours is covered.
3. **Prepare the destination anchor first**, then outward. The 32 px provisional
   estimate (`runner/src/instance/collection/mod.rs:22`) keeps serving the scrollable
   **extent**; it is never painted as content.
4. **Provisional space is not content.** It is never a selection endpoint or an
   accessibility target, no action dispatches through its geometry, and old rows are
   never painted at a new location.
5. **Anchor immobility has a declared exception.** If rows below the anchor shrink on
   measurement, the new maximum offset can fall below the anchor-preserving offset and
   `restore_anchor` clamps to that maximum
   (`runner/src/instance/collection/index.rs:307-317`), moving the anchor on screen.
   End-following does the same by design. Both are stated rather than promised away.

Construction proceeds through generation-qualified preparation: a row publishes only
when its values, subtree and geometry are coherent, superseding geometry discards
obsolete preparation before publication, and there is one desired window and one
candidate per owner rather than a queue of abandoned destinations. Selection stays
keyed logical text and copy continues through logical row projection. Resource
settlement stays atomic — the native executor already drains one completion or refusal
per pump ([LLP 1041 §8.4](1041-graceful-overload.rfc.md#84-bounded-native-http-admission-and-completion-pumping))
— and presentation may lag a complete committed answer.

**This is the largest slice**, and the only one that changes the runner and both Apple
presenters. It does not start until slices 1–3 land.

## 13. Implementation, 2026-09-20 — slice 1 is blocked on the executor

Implementation started after r3. It stopped at the repository's three-round fix limit
on one blocker, which is recorded here rather than worked around.

### What landed

**A contract compiler fix, with a regression test.** A `derive` of bool type could not
be used as a ternary condition, though a `state` of bool type could: the derive
fixpoint starts every derive at `Ty::Unknown`, and `Expr::Ternary` — unlike
`Expr::Binary` beside it — had no deferral for an operand still `?`, so round one
returned a hard `type-condition` error. Naming the type in the message makes the round
defer it the way the binary case already did, and the strict pass still reports a
condition that never types. `contract/types/src/lib.rs`, with the case and its
still-refused negative in `contract/cli/tests/instance.rs`. D4 needs this; so would any
contract deriving a flag and branching on it.

### The blocker: two storage-backed source calls cannot overlap

D4 splits the selected note's body out of the library answer. Every arrangement of that
split puts two source calls in flight at once, and the second one fails with
*"the answer is pending on nothing: no host operation will resolve it"*
(`js/src/prelude.js:258`).

The mechanism, established by running it:

- `lockPaths` refuses a concurrent open of the same database with `EBUSY`
  (`host/web/storage-fs.js:80-84`, `ifAvailable: true`). Fieldnotes' `serial()` gate
  (`apps/fieldnotes/app.ts:19-24`) exists so that never happens.
- The prelude judges liveness **per call**: a call with no ticket of its own and no
  storage request outstanding is stuck, even when it is waiting on another call of the
  same module that does have one (`settle`, `js/src/prelude.js:252-259`).
- So a source call that awaits the gate is reported stuck. Concurrent calls are fine —
  Caltrain runs several fetches — but each must issue **its own** host request before
  yielding. A call awaiting another call cannot.

Three arrangements were tried and each has a reachable overlap:

| Arrangement | Where it overlaps |
|---|---|
| `resource opened = note(editingId, saveRevision, serviceRevision)` | Every save or service call invalidates both resources in one commit |
| `resource opened = note(editingId)` | `Runner::boot_carrying` requests `library` and a carried `editingId` together; and a save that creates a note changes `editingId` and `saveRevision` at once |
| One resource, `library(query, editingId, …)` | `remove` and `restore` send a mutation **and** change the selection in the same commit |

Bypassing the gate makes all eleven Fieldnotes tests pass on macOS, which is why it is
worth saying plainly that this is *not* a fix: native SQLite has a 5 s busy timeout, so
the second connection waits, while web refuses it outright. A green native suite would
have hidden a web-only failure.

### What this costs, and the three ways out

The library-answer repair itself — summaries only, the BLOB prefix, the keyset search —
is written and works. It is the actual fix for the recorded 16 MiB failure. Only the
editor's body split is blocked, and without it the body has nowhere to come from.

The working revision is kept outside the repository, under this session's scratchpad,
rather than committed half-finished. The tree is back to a state where
`cargo test -p fieldnotes-apple` passes 11 of 11.

1. **Make the prelude's liveness rule module-wide.** A call is stuck only when
   *nothing* in the module has work outstanding. This is the correct rule and it
   degrades to today's once everything else settles. It is not a one-line change:
   `ticket == 0` already means "waiting on storage" and is answered with
   `Request::continuation(call)` (`js/src/lib.rs:694`), which the host resolves by
   finding that call's storage work (`:836`). A third state — waiting on the module —
   needs its own release path. This is LLP 1027.001/1016 territory and wants its own
   decision.
2. **Let the app hold one database lease for its lifetime**, so no second open is ever
   attempted and no gate is needed. Refused here: the Rust `backupNotes` owner opens
   the same path in the same process and would be locked out forever.
3. **Restructure the Contract so a mutation and a selection change never land in one
   commit** — `remove` and `restore` would stop clearing the selection themselves and
   let it fall out of the mutation's result. This keeps the split without touching the
   executor, but it is a fourth attempt at the same problem and the limit was reached.

**My recommendation is (1)**, with (3) as the fallback if the executor change is judged
too large for this campaign. Both are Charlie's call; slices 2–4 are unaffected and can
proceed either way.


### Implementation correction, 2026-09-21

The native per-call liveness finding above remains valid, but the browser conclusion
was incomplete. Both `host/web/module-glue.js` and `module-worker.js` serialize the
whole storage-backed call, including each ticket-zero continuation and connection
close. Concurrent Fieldnotes `library`/`openNote` requests therefore do not overlap
browser database leases. The existing browser protocol test now exercises that pair
on both placements; the native tests exercise independent read continuations.

Fieldnotes now scans immutable IDs in 32-row storage replies, returns only previews,
and loads a selected body through an explicit `openNote` action. This preserves the
editor's loaded snapshot and unsaved draft across changed-code reloads, covered by
the normal persistent browser drive. A selected-body resource exposed a different
reload problem: a new module could not answer non-default boot arguments immediately.
The action keeps the loaded value in the carried mutation slot and needs no boot read.

The 1,000-note, 20,000-UTF-16-unit fixture now opens and searches on native and web.
This is a narrower implementation than the planned BLOB-prefix optimization: it still
reads all bodies, in bounded replies, and pages are independent reads rather than one
cross-window snapshot. Backup retains its existing coherent read and separate limit.
Schema initialization and browser persistence costs remain follow-up work. No generic
executor liveness change or new storage lifetime is introduced.


### Schema reads, 2026-09-21

Both Fieldnotes language implementations now query `sqlite_schema` before issuing
`CREATE TABLE IF NOT EXISTS`. This differs from D5's proposed process-local cache:
it checks the current opened file, so an empty replacement or deleted database is
initialized without error-string matching or replaying a failed mutation. TypeScript
checks and works on the same connection. Rust's portable backup checks in one read
request, then opens for its existing single-statement snapshot; it does not retain a
connection between source turns.

The browser drive marks the database file's modification timestamp before reads and
checks that Rust backup/library refresh, selected-body loading, search and changed-code
reload leave it unchanged. Native tests cover initialization after file deletion for
all database-backed TypeScript operations and repeated Rust backups, plus refusing a
corrupt database without overwriting it. Backups still write their separate backup
file. Browser exports for actual database mutations and whole-file IndexedDB scans
remain unfinished work; this app change does not alter that backend.


### Bounded preview reads, 2026-09-21

Unfiltered Fieldnotes lists now fetch `substr(body,1,200)` and a byte-length comparison
with the original body. A truncated prefix whose JavaScript whitespace-normalized
text is shorter than 100 UTF-16 units triggers a full-row read, at most 32 rows per
reply. This deliberately uses TEXT rather than D2's BLOB decode: SQLite stopping at
an embedded NUL makes the byte-length comparison report truncation, so an insufficient
prefix falls back to the full body instead of silently losing text. BOMs and actual
replacement characters remain ordinary input; no per-row decoder is needed.

The initial answer contains only prefixes, and at the admitted 1,000-note limit fits
below the storage reply cap. In a notebook where every prefix needs fallback, every
body is still read in bounded replies. Full fallback rows replace title/body/pin
together; a row deleted before its fallback is omitted. No cross-query snapshot is
claimed. Nonempty exact search and backup behavior are unchanged.

Native fixtures compare unfiltered previews with the full-body search path for
Unicode whitespace, embedded NULs, BOM, replacement characters and surrogate
boundaries. Native and browser fixtures also cover a notebook where every maximal
body needs fallback. A normal preview avoids transferring full bodies into app
logic; this does not claim SQLite avoids reading every body page internally or that
the browser stops loading the full database file.

Five alternating pairs on this Mac measured the maximum-size ordinary notebook's
native library calls at 75.2 → 28.6 ms (dev-derived test profile), and browser worker
calls at 123.1 → 57.3 ms. The ten-note control was effectively unchanged. The
all-fallback fixture trades about 5% browser / 6% native latency for this ordinary
list gain; it remains correct and bounded. These are source-call measurements, not
physical frame claims. Evidence: `/tmp/exact-fieldnotes-previews-c4abfe98/`.


### Targeted browser file reads, 2026-09-21

The filesystem backend now fetches only the requested record for `readFile`, `stat`
and `realpath`. `readdir` fetches the directory record and descendant keys in one
readonly transaction, filters direct children, and never materializes their file
contents. The key range preserves Unicode names, including U+FFFF, while excluding
adjacent sibling prefixes. Returned read buffers use IndexedDB's existing per-read
structured clone; no second buffer copy is needed. The browser fixture mutates and
detaches one read buffer and confirms that another read and persisted bytes remain
independent, alongside missing-path/type errors and Unicode directory membership.

Grants, path normalization, Web Locks, write snapshots and transaction completion
remain on their existing paths. At this stage, filesystem mutations still scan full records, and
`stat`/`realpath` still read their target record's contents; the improvement removes
unrelated file data. No persisted format or schema migration is introduced.


### Targeted browser file writes, 2026-09-21

Writes (including atomic replacement) and appends now read the target and its parent;
copies read the source, destination and destination parent. Those reads and the
resulting changes still share one write transaction. Input bytes are still captured
before waiting for locks or opening IndexedDB. At this stage, directory creation,
removal and rename still scan full records; SQLite exports its whole database on a mutation.

The existing browser fixture covers call-time snapshots after input mutation and
buffer detachment, missing parents and wrong file kinds, replacement, failed copies,
concurrent appends and SQLite leases. It also counts record contents returned by
IndexedDB while reading, listing, writing, appending and copying small files beside a
1 MiB unrelated file; those operations must not load that unrelated file.

Five alternating headless Chrome pairs with a 64 MiB unrelated file measured a 1 KiB
write at 19.9 → 0.4 ms, append at 20.0 → 0.5 ms, copy at 20.4 → 0.4 ms and 4 MiB atomic
replacement at 23.1 → 5.4 ms. Without that unrelated file, 4 MiB replacement stayed
flat (5.6 → 5.5 ms). These are filesystem call timings, not app frame or physical
120 Hz results. Evidence: `/tmp/exact-browser-writes-8673601a/`.


### Targeted browser directory operations, 2026-09-21

The remaining whole-store reads are removed. `mkdir` fetches its ancestor chain;
`rm` fetches the parent and exact/subtree keys, never the removed file contents.
`rename` fetches source, destination and their parents, the source subtree records
that must move, and destination subtree keys for the nonempty-directory check. All
requests and changes share one transaction, including failures after writes begin.
Moves remain proportional to the moved subtree, and removal to the removed key set.

The browser fixture now covers missing/wrong parents, root creation, overlapping
paths, existing destinations, Unicode descendants, adjacent prefixes, and a failure
injected after a move starts writing. It checks that the aborted move restores both
the source subtree and destination. The IndexedDB byte counter now covers directory
creation, rename, recursive removal and deletion of the large file itself.

Five alternating headless Chrome pairs with an unrelated 64 MiB file measured
creation at 19.2 → 0.6 ms, rename at 19.0 → 0.6 ms, recursive removal at 18.8 → 0.4 ms,
and deletion of a 4 MiB file at 21.2 → 1.5 ms. The no-unrelated-file control was flat
or faster. These are filesystem call timings, not physical frame evidence. The
persistent format, grants and locks are unchanged; browser SQLite whole-database
export remains. Evidence: `/tmp/exact-browser-directories-65a5fe36/`.


### Messages idle reconciliation, 2026-09-21

`MessagesReplica` now keeps a reconciliation-owed flag. Store observation, backend
adoption and outbox settlement mark it before dispatch, because failures can follow
committed changes. Successful apply marks it for queued predictions, touched tables,
snapshots/catch-up or acknowledgements; refused apply also marks it, since the device can commit a
store reset before returning an error. An idle successful apply leaves it alone.

The final sync step still updates queued count and status. It rereads and compares
records only while reconciliation is owed, clearing the flag after a successful
read and synchronous model publication. The held snapshot advances after publication,
so a callback failure retries on the next tick instead of hiding the unapplied model.
Local `persist` still diffs a complete snapshot; changed syncs still read all records.

The real Wasm-device/SQLite/server fixture verifies idle online/offline ticks perform
zero record queries, remote changes survive failed rereads and failed publication,
an apply that commits before losing its reply still refreshes the model, and a
server replacement clears the old model even when schema fetching fails after
the reset. Catch-up to the same numeric watermark then publishes the replacement
model. Existing offline writes, lost receipts and failed commits still pass.

Five alternating pairs with 5,000 records measured online idle sync at 49.8 → 2.5 ms
and offline at 47.0 → 0.10 ms, with record queries falling from ten to zero. At 1,000
records online calls measured 11.1 → 2.0 ms. The probe uses Bun, the published Wasm
device, SQLite and a local server; these are replica-call measurements, not native
frame or browser persistence timings. Evidence: `/tmp/exact-messages-idle-2e4358e7/`.


### Messages browser no-op metadata persistence, 2026-09-21

The Wasm device drains unchanged acquisition/watermark metadata after an idle apply.
`browserCore` now checks small metadata-only batches against SQLite before writing:
at most 32 changes and 8,192 UTF-16 code units of keys/values. A read-only CTE compares
the last value for each key, including deletion/absence, using null-safe equality.
If every final value is already durable, it skips the write. Otherwise it commits
the original ordered batch. Data-bearing and larger batches bypass the comparison.
The bound keeps the extra request small and independent of stored history size.

The browser SQLite lease excludes other owners between comparison and commit. No
new cache, storage format or device protocol is introduced. A failed comparison or
write uses the existing reconstruction from durable SQLite; the real-device fixture
checks both, alongside unchanged/changed metadata, the large-batch bypass and idle
sync with no persistence transactions. Receipt/reset/publication recovery still passes.

Five alternating pairs through the real browser SQLite worker measured unchanged
apply at 10.6 → 0.4 ms for 5,000 records, and 3.8 → 0.3 ms for 1,000. Persistence
transactions fall from one to zero per apply, with unchanged file timestamps. Actual
metadata writes were flat at these sizes (11.6 → 11.3 ms and 3.7 → 3.8 ms); the ten-row
control traded 0.4 → 0.8 ms for the added comparison. These are isolated apply calls,
not whole-sync or physical frame measurements. Actual writes still export the whole
database. Evidence: `/tmp/exact-messages-drain-72a54324/`.
