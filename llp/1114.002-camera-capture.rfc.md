## 1. Summary

The web takes a photo with one attribute: `<input type=file accept="image/*"
capture="environment">`. A phone's browser opens its camera and hands back
the photo as the input's file. A desktop browser has no camera control and
shows its ordinary file chooser. This RFC admits that attribute on exact2's
file input with the web's meaning. On iOS the host presents the system
camera (`UIImagePickerController` with `.camera`) and delivers the photo
through the picker's existing path, as a `Picked` JPEG in
`app:/tmp/picked/`. On macOS it is ignored, as desktop Safari ignores it. On
tvOS, Linux and Windows nothing changes: the picker is already refused there.
A `capture` input needs a `device.camera` grant, which writes
`NSCameraUsageDescription`. Under the agent the camera is the picker's
substitute: `type @t fixture.jpg`.

This is not the camera module `QUEUE.md:55` describes (a live viewfinder,
`start`/`stop`/`capture`/`flip`, as an app native module). It is the
"take one photo and hand it back" case that most apps need. The two share
the grant and the substitute, and neither replaces the other (§5 D7).

It reverses one sentence of `rules/DEFERRED.md`, which Charlie wrote on
2026-10-02: "no `capture` on the picker (the camera is a native module)".

## 2. What Bluesky does

The source says the composer has a camera button that opens the system
camera and attaches the photo. That is right on iOS and Android, with these
corrections (social-app `main` at `35fd4fba`):

- **The button is native only.** `OpenCameraBtn.web.tsx` returns `null`, so
  bluesky.app has no camera button. `OpenCameraBtn.tsx` shows it for
  `IS_NATIVE || IS_WEB_MOBILE`, but the web build never loads that file. A
  phone's browser still offers "Take Photo" from the ordinary photo picker,
  because that is what iOS Safari's file input does.
- **It is `expo-image-picker`'s `launchCameraAsync({mediaTypes: 'images'})`**
  (`src/lib/media/picker.tsx`), which on iOS is `UIImagePickerController`
  with `sourceType = .camera`. One photo comes back. Video capture is not
  used.
- **It asks for permission first** (`useCameraPermission`,
  `requestCameraAccessIfNeeded`), and shows its own "enable it in Settings"
  prompt when the answer is no.
- **It saves the photo to the library** (`MediaLibrary.createAssetAsync`)
  when it has photo permission. That is a separate feature (§9).
- **The avatar and banner menus have "Upload from Camera" too**
  (`UserAvatar.tsx:395`, `UserBanner.tsx:61`). They pass `aspect: [1, 1]`
  and `[3, 1]`, which `expo-image-picker` applies only on Android, with
  `allowsEditing`. On iOS the photo is not cropped. Then it is compressed to
  2000 px and 1 MB (`IMAGE_SIZE_CONFIG_2K_1MB`).

The source's "simplest version" is the right one, and this RFC follows it.

## 3. What exact2 has today

- **The refusal.** `input type="file"` with `capture` fails lowering with
  `lower-picker-capture` (`contract/lower/src/controls.rs:209-214`).
  `capture` on any other element is `lower-attr-tag` (`:186-195`). The
  quoted reason, `PICKER_ADMISSION` (`:201`), still says "and no camera".
  `rules/DEFERRED.md:175-176` now says "no `capture` on the picker (the
  camera is a native module, §Components, 2026-10-02)". The two have
  drifted; this RFC replaces both.
- **The picker** (LLP 1069.002 §As built). `accept` and `multiple` are
  kernel props 209 and 210 (`kernel/tables/schema.json:1247-1257`). The
  runner reads them into a `PickerRequest` (`runner/src/runner/picker.rs:256`)
  and, under the agent, holds a `pick` (`:280`). iOS presents
  `PHPickerViewController` (`Picker.swift:224-245`). macOS presents
  `NSOpenPanel` (`:294`). tvOS refuses (`:217-220`). Linux and Windows
  refuse with `picker: refused: unavailable` and fire `cancel`
  (`host/linux/src/presenter/picker.rs:24`). The web calls the element's
  own `showPicker()`. Every picked file is copied into `app:/tmp/picked/`,
  described, and delivered as `change` (`Picker.swift:112-145`).
- **The grant row exists.** `device.camera` maps to
  `NSCameraUsageDescription` on iOS and macOS, the
  `com.apple.security.device.camera` entitlement, and the web's `camera`
  policy feature (`runner/src/device.rs:70-78`; LLP 1069.008 D2). Its
  comment says "Camera stays deferred; the row exists so a native module can
  declare it." Nothing first-party checks it.
- **The pattern for a first-party grant check** is `showNotification`:
  `runner/src/notify.rs:120-143` refuses into the journal when the grants
  name no `device.notifications`.
- **No camera anywhere.** No host code calls `UIImagePickerController`,
  `AVCaptureDevice` for video, or `getUserMedia` (`rg` over `host/`). The
  only `AVCaptureDevice` use is the recorder app's microphone
  (`apps/recorder/modules/apple/Recorder.swift:96`).
- **No permission fact or prompt substitute.** LLP 1069.007 D2 and D6
  design `permission.<name>` and `--permission`; neither is built (no hits
  in `runner/src` or `scripts/agent.mjs`).
- **The camera module** in `QUEUE.md:55` has no RFC yet.

## 4. What the web does

[HTML Media Capture](https://www.w3.org/TR/html-media-capture/) (W3C
Recommendation, 2018) adds one attribute to `<input type=file>`:

- `capture` is an enumerated attribute whose keywords are `user` (the
  front camera) and `environment` (the rear). Its missing value default and
  its invalid value default are both "implementation-specific". So a bare
  `capture` means "a camera, whichever the browser picks".
- When it is present, the user agent SHOULD invoke "a file picker of the
  specific capture control type": a camera for `image/*`, a camcorder for
  `video/*`, a microphone for `audio/*`. If `accept` names no type with a
  capture control, the user agent MUST act as if there were no `capture`.
  If the preferred facing mode is unsupported it can fall back to its
  default.
- The user agent MUST NOT save the captured media to storage on its own.
  The page gets the file through the input, like any pick.
- The spec names no permission model and no Permissions Policy feature. The
  capture runs in the browser's or the OS's own UI, outside the page.

In practice, Safari on iOS and Chrome and Firefox on Android open the camera.
Desktop browsers have no capture control and show the file chooser, which
the spec allows. Without `capture`, iOS Safari's file input already offers
"Take Photo" in its menu; `capture` only skips the menu.

## 5. Design

### D1 — The attribute is HTML's: `capture`, `capture="user"`, `capture="environment"`

`capture` becomes a kernel string prop beside `accept` and `multiple`, and
lowering admits it on `input type="file"` only. It is a literal, as
`accept` is, so the bake can bound it. A bare `capture` is the empty string.

```
input type="file" accept="image/*" capture="environment" testId="camera"
    display="none" change=attach cancel=noPhoto
button press=takePhoto aria-label="Camera"
  image "symbol:camera"

action takePhoto
  showPicker("camera")
```

Lowering refuses, each by name with the DEFERRED sentence that bounds it:

- a `capture` value other than empty, `user` or `environment`, or a bound
  one (`lower-picker-capture`);
- `capture` when `accept` names any video type
  (`lower-picker-capture-video`). DEFERRED keeps video recording out until a
  consumer asks, and Bluesky's camera takes photos only.

Three differences from HTML, declared: HTML's invalid value is not an
error, HTML lets `accept` include video, and HTML ignores `capture` where
`accept` has no image type. The refusals keep a typo or a
deferred feature from passing silently, and a later widening is one
DEFERRED line and one check.

`accept` with no image type (a `file_handlers` type alone) and `capture`
is refused too (`lower-picker-capture`): HTML says it means no camera,
so the attribute could only be a mistake.

`multiple` with `capture` is allowed and delivers one photo. A camera takes
one at a time, and iOS Safari does the same.

### D2 — iOS presents the system camera and delivers through the picker's path

When the input has `capture` and `accept` names an image type, `present`
(`Picker.swift:224`) takes a new first branch:

1. **No camera** (`UIImagePickerController.isSourceTypeAvailable(.camera)`
   is false, as on every simulator and some iPads): fall back to the
   picker without `capture`, PHPicker, as the spec allows. The journal
   says `picker: no camera; the photo library instead`.
2. **Denied or restricted** (`AVCaptureDevice.authorizationStatus(for:
   .video)`): journal `picker: refused: camera denied`, fire `cancel`. The
   app cannot yet tell why it was cancelled (§6 Q3).
3. **Otherwise** present `UIImagePickerController` with `sourceType =
   .camera`, `mediaTypes = [UTType.image.identifier]`, `allowsEditing =
   false`, and `cameraDevice` `.front` for `user`, `.rear` for
   `environment` or a bare `capture`, falling back to the other when
   `isCameraDeviceAvailable` says no. A first use with the status
   `.notDetermined` shows the OS prompt with the app's
   `NSCameraUsageDescription`, as `UIImagePickerController` does on its own.
4. **The photo.** `info[.originalImage]` is drawn upright
   (`UIGraphicsImageRenderer`, scale 1, so its size is the sensor's) and
   written with ImageIO as a JPEG at quality 0.9 with no metadata copied:
   the settings D6's HEIC conversion already uses (`Picker.swift:172`). It
   is staged in the temporary directory and handed to `deliver` with the
   name `image.jpg`, which is what iOS Safari calls a camera photo. From
   there it is a pick: `pickedPath`, the copy into `app:/tmp/picked/`,
   width and height from the header, and `change` with one `Picked`.
5. **Cancel** (`imagePickerControllerDidCancel`) fires `cancel`.

The photo is never saved to the library, as the spec requires. An app that
wants it there asks for that separately (§9).

*Rejected:* honouring `capture` with `AVCaptureSession` and a viewfinder of
exact2's own. That is the camera module (D7), and a custom UI the web
doesn't have.

### D3 — Every other host does what its browser does

| host | with `capture` | why |
|---|---|---|
| web, phones | the browser's camera (Safari on iOS, Chrome and Firefox on Android) | the attribute reaches the `<input>`, as `accept` does |
| web, desktop | the browser's file chooser | the browser ignores it |
| iOS | the system camera (D2), PHPicker when there is none | |
| macOS | `NSOpenPanel`, as without `capture` | desktop Safari ignores it; AppKit has no camera picker. Continuity Camera is §9 |
| tvOS | refused, as every pick is (`Picker.swift:217`) | no camera, no picker |
| Linux, Windows | refused, as every pick is (`picker: refused: unavailable`, then `cancel`) | no desktop picker yet (LLP 1069.002 Q4); the substitute answers |
| terminal | no file input | |

Both web hosts take the attribute through their existing prop path, so a
`capture` input is an ordinary `<input type=file capture>`. `showPicker()`
on such an input must open the camera on iOS Safari and Chrome on Android,
as a click does. That is checked on a phone in slice 1, not assumed.

### D4 — The grant: `device.camera`, required by the bake

A `capture` input needs a `device.camera <purpose-key>` line in the app's
grants (LLP 1069.008 D1). The bake refuses a plan with a `capture` input and
no such line (`bake-picker-capture-grant`), and says which line to add.

- **Why the bake, not the runtime.** iOS terminates an app that opens the
  camera without `NSCameraUsageDescription`. The bake is the one place that
  can make sure the key is there, and LLP 1069.008 derives the key from the
  grant only.
- **The runtime checks too,** as `showNotification` does
  (`runner/src/notify.rs:142`). A plan compiled without an app, or a grant
  set that changed, refuses into the journal with `picker: refused: the
  grants name no device.camera` and fires `cancel`.
- **What the grant writes:** `NSCameraUsageDescription` on iOS and macOS,
  `com.apple.security.device.camera` on a notarised Mac build, and
  `camera=(self)` in the web's `Permissions-Policy` (`runner/src/device.rs:70-78`).
  macOS gets a key and an entitlement it won't use, since it ignores
  `capture`. That is one harmless line, and splitting the row per host
  would be a second table.
- **The web needs no grant to capture.** The spec ties `capture` to no
  policy feature, and the browser's camera UI is outside the page. The
  policy line the grant writes is a side effect, and it is the one a later
  `getUserMedia` (the camera module's web side) would need. Slice 1 checks
  that `camera=()` does not block `capture` on either phone browser.
- **The reach table** (LLP 1069.008 D7) lists "takes photos (`capture`)"
  beside "picks files (`accept`)".
- **The `device.camera` comment** in `runner/src/device.rs:70` changes to
  name both users.

*Rejected:* deriving the key from the tag's presence, with the purpose as
an attribute. LLP 1069.008 made the grant the only declaration, and a
second one is what it removed.

### D5 — The agent's view: the picker's substitute, with `capture` in the hold

Nothing new in the driver. Under the agent `showPicker` on a `capture`
input holds a `pick` as today (`runner/src/runner/picker.rs:280`), and the
hold's args gain `capture` (LLP 1069.007 D3):

```
state.pending: [{ticket: 7, device: {capability: "pick",
  args: {id: "camera", accept: ["image/*"], multiple: false, capture: "environment"}}}]
```

- **Answer:** `type @7 scripts/fixtures/picker/oriented-gps.jpg`, a fixture
  image in place of the camera, through the same copy, conversion and
  `change`. `tap @7 cancel` fires `cancel`. The journal says `device pick 7
  answered: 1 file`, as for any pick.
- **One file.** A capture hold takes exactly one path, even with
  `multiple`, as the camera gives one (D1). More is refused before the hold
  is spent, as a wrong count is today.
- **Fixtures** (`--answer pick=…`, LLP 1069.007 D4) answer a capture hold
  like any pick, when that flag is built.
- **Denied.** When LLP 1069.007's `permission` fact is built, `prefer
  permission.camera denied` makes the next capture fire `cancel` with D2's
  journal line, so a test can drive the denied path. Until then it can't.
- **Replay** (LLP 1069.009 D1): the answer is a `dispatch` of `change` with
  the `Picked` record, and the photo is a fixture file, as with any pick.
- **What the substitute doesn't cover:** the real camera sheet, the OS
  prompt, and the front/rear choice. Those are checked once on a phone
  (§7).

### D6 — `rules/DEFERRED.md` moves one sentence

`rules/DEFERRED.md:175-176` says: "Still no picker for any file, and no
`capture` on the picker (the camera is a native module, §Components,
2026-10-02)." It becomes:

> Still no picker for any file. `capture` on the picker takes a photo with
> the system camera (LLP 1114.002, Charlie, 2026-10-…); video capture and
> a viewfinder stay out (the camera module, §Components).

`PICKER_ADMISSION` (`controls.rs:201`) is re-quoted from the new text.
RULES asks for a take or a waiver (`rules/RULES.md:47`). §6 Q1.

### D7 — Relation to the camera module in `QUEUE.md:55`

| | `capture` (this RFC) | the camera module (QUEUE) |
|---|---|---|
| what it is | the system camera sheet, one photo back | a live preview in the app's layout, with the app's own controls |
| shape | an attribute on the file input | an app native module (LLP 1067.000), `<camera-preview>` |
| output | a `Picked` in `app:/tmp/picked/` | `capture` writing to `app:/camera/` |
| hosts | iOS; phone browsers; ignored elsewhere | web (`getUserMedia`), iOS, macOS |
| grant | `device.camera` | `device.camera` |
| agent | the picker's substitute | its own substitute, plus a preview snapshot |

They don't conflict and neither subsumes the other. `capture` serves a
"Camera" button. The module serves an app whose screen *is* a camera (a
scanner, a video call, a custom shutter). DEFERRED's 2026-10-02 ruling
chose the module because a camera sheet looked like a host feature the
module would cover. It does cover it, but at the cost of a native module,
a page module for the web, and custom UI in every app that wants one photo.
`capture` costs one attribute and no app code. The module's RFC can then
drop its "one photo" case and focus on the viewfinder.

## 6. Questions for Charlie

1. **Move DEFERRED's "no `capture` on the picker"?** Recommended: yes, with
   D6's text and the take waived. It is one attribute with the web's
   meaning, and the module stays as QUEUE has it.
2. **Video capture (`accept="video/*" capture`).** Recommended: refused for
   now (D1). `UIImagePickerController` would record video with a few more
   lines, but that is the "video recording" DEFERRED keeps out, and no
   consumer asks.
3. **Telling the app why a capture was cancelled.** HTML's `cancel` carries
   no reason. Bluesky shows "enable the camera in Settings" when access is
   denied. Recommended: no reason on `cancel`. The app reads the permission
   state through LLP 1069.007's `permission.camera` fact once it is built,
   as a page uses `navigator.permissions.query({name: "camera"})`. Until
   then the clone shows a generic "Couldn't open the camera" note on
   `cancel` after a capture.

## 7. What the clone does after

- **Composer.** One hidden input,
  `accept="image/jpeg,image/png" capture="environment"`, beside the existing
  library input, and the camera button calls `showPicker` on it. Its
  `change` goes to the same `attach` action. `compressImage` then shrinks
  the 12 MP photo to Bluesky's 4000 px and 2 MB. Bluesky shows the button on
  native only. An exact2 app has no fact that says whether a camera exists
  (`exactPage()` carries `hasFocus` only, `docs/contract-grammar.md:1149`),
  so the clone shows it everywhere. That is safe: where there is no camera,
  the button opens the file chooser or the library, which the spec allows.
- **Avatar and banner.** "Upload from Camera" menu items, the same input,
  then crop (LLP 1114.003) and compress at 2000 px and 1 MB.
- **Grants.** `device.camera purpose.camera` and a strings entry ("Bluesky
  uses the camera to take photos for your posts and profile.").
- **Verified by:**
  - an agent drive on the web, macOS, iOS simulator and Linux: tap the
    button, `state.pending` shows the hold with `capture`, `type @t
    oriented-gps.jpg` attaches a 48×64 image, `tap @t cancel` attaches
    nothing;
  - on an iPhone, by hand: the rear camera opens, the photo attaches
    upright, the prompt shows the purpose text, and a denied camera cancels
    with the journal line;
  - on iOS Safari and Chrome on Android, the web build's button opens the
    camera, with `Permissions-Policy` both with and without the grant.

Clone size: **S**, about two hours with the device pass.

## 8. Effort and complexity

**exact2: S–M, about a day and a half.**

- *Easy:* lowering and the schema prop (one prop, two checks, tests in
  `contract/cli/tests/it/picker.rs`); the runner's request and hold carry
  one more field; the runtime grant check copies `notify.rs`; the web needs
  no code beyond the prop reaching the DOM; the substitute is unchanged
  but for the args and the one-file rule; the docs paragraph.
- *Moderate:* the bake check, which needs the plan's file inputs and the
  grant ceiling in one place (`bake/src/reach.rs:26` has the ceiling); the
  iOS branch, about 80 lines of Swift: availability, authorization, the
  delegate, drawing upright, writing the JPEG off the main thread.
- *Hard:* only verification. The simulator has no camera, so D2's real
  branch runs only on a phone, and the web's behaviour runs only on phone
  browsers. Neither is in any automated lane; slice 1 records a manual
  pass, as LLP 1069.002 §As built did for PHPicker.

**Clone: S.** No ruling of an earlier LLP is reversed except DEFERRED's
2026-10-02 sentence (Q1), and LLP 1069.002's "Not in this RFC: A camera and
`capture`", which this RFC supersedes for photos.

## 9. Not in scope

- The camera module: a viewfinder, `getUserMedia`, `AVCaptureSession`
  (`QUEUE.md:55`).
- Video and audio capture (Q2).
- Saving the photo to the library. `device.photos-add` exists as a grant row
  (`runner/src/device.rs`) but there is no command; it would be its own RFC.
- Copying iOS Safari's "Take Photo" item into the native picker without
  `capture`. PHPicker has no camera item, and the app writes `capture` for
  a camera button.
- Continuity Camera on macOS (an iPhone as the Mac's camera through
  `NSMenuItem`'s import from device), and a camera on Linux or Windows.
- Cropping in the camera sheet (`allowsEditing`). Cropping is LLP 1114.003,
  in Contract.
