# LLP 1016.000: Answers that keep coming

**Type:** RFC
**Status:** Implemented 2026-09-27: server-sent events (LLP 1069.004 slices 1–2) and a receive-only WebSocket (slice 3); web JS TypeScript bidirectional slice 2026-10-13 (D7); native TypeScript on Apple and Linux 2026-10-15 (D7)
**Systems:** Runner (a resource whose answer is a sequence; settlement per reply; the forget path ends it), Data seam (`Answer`, `Request`, the reply channel), Web host (`fetch` body streams, `EventSource`, `WebSocket` in the glue, never in the module realm), Apple host and Linux host (the executor keeps a response open; `ibex2` transports), Grants (`net.fetch`, `net.websocket`), Agent API (`clock settle` and a stream's replies), Contract (one resource form)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-24
**Related:** LLP 1016 D1 (the runner does no I/O), D2 (the host executes and delivers on the runner's thread), D4 (failure is data), D5 (one request per resource, the newest arguments win), §5 ("streaming and sockets … later"); LLP 1027 (the deferred list: "WebSocket and streams (a trigger)"); LLP 1041 D2 (every bound has an overload policy), D4 (cancellation protects identity), §8.4 (native HTTP admission); LLP 1012 §2 (`clock settle`); `rules/DEFERRED.md` (the doing-list bar; push *delivery* of updates is refused, which is a different thing)

## Summary

Every resource answers once. A source returns `Answer::Now` or
`Answer::Later(Request)` (`runner/src/request.rs:29-35`), the host runs the
request, and one outcome comes back to one ticket. Host work that hands its
reply to another owner does so through a `FnOnce(Reply)`
(`runner/src/request.rs:355-360`), so the type itself says one. The web
module realm deletes `WebSocket` and `EventSource` before app code runs
(`host/web/module-glue.js:113`, `host/web/module-worker.js:37`).

So live data is a timer. This RFC proposes a resource whose answer is a
**sequence**: each reply commits as its own settlement, and the stream ends
at a final reply, a close, a failure, or when the runner forgets the ticket.
The runner still does no I/O. The host keeps a response or socket open and
delivers each message the way it delivers a single reply today.

## Motivation

The Crew port report (2026-09-24), item D9: Crew's daemon publishes run
events on `GET /api/events` (server-sent events). With no push transport,
the port polls `GET /api/state` (190 KB) every two seconds. That poll ran
into two other defects in the same report:

- **F3.** A poll changes a resource's arguments, the runner forgets the old
  ticket, and the old job kept its executor slot. When one answer took longer
  than the poll interval, capacity drained and later asks were refused.
- **F4/F6.** The 190 KB body is the one that stalled under worker placement.
  A stream of small events would never have sent it.

LLP 1016 §5 put streaming and sockets later, pending a consumer; LLP 1027
lists "WebSocket and streams" as waiting on a trigger. A developer porting a
real app to exact2 who has to replace their event stream with a poll of the
whole state is that trigger. Weird Castle's relay (its `llp/0002`) is the
other one named in 1016 §5.

## Design

### D1 — A stream is a resource; each reply is a settlement

A source may answer `Answer::Stream(Request)`. The host opens it and
delivers zero or more messages to the same ticket. Each message is parsed by
the source's `parse`, exactly like a single reply, and commits as a
settlement pass (LLP 1016 D5: derives recompute, and resources whose
arguments changed ask again). The resource's value is the last message's.
`pending(resource)` is true until the first message arrives, then false.

A `Final` message, a close from the far side, or a `Failed` outcome ends the
stream. Failure is data (LLP 1016 D4): the source shapes it and the resource
keeps its last value.

*Rejected:* a `subscription` slot kind beside `resource` and `mutation`. The
app reads a stream exactly as it reads a resource, and `pending`, `refresh`
and the kept first frame all already mean the right thing for it.

### D2 — Interest ends a stream, through the forget path

When a stream resource's arguments change, or the resource leaves the plan,
the runner forgets the ticket (LLP 1016 D5), and a forgotten stream ends at
the host. That is the same forget-and-abort path the Crew report's F3 fix
adds for single requests. A late message on a forgotten ticket is dropped,
as it is today (`runner/src/runner/commit.rs:585`). `refresh` closes the
stream and opens a new one.

*Rejected:* explicit `open`/`close` statements in Contract. Interest is
already declared by arguments and presence; a second lifetime would drift
from the first.

### D3 — Per-surface transports, grants unchanged

| surface | server-sent events and streamed bodies | WebSocket |
|---|---|---|
| web | the glue's `fetch` reads `response.body` (an SSE parser over it), keeps its `AbortController` | the glue opens it; the module realm still has no `WebSocket` |
| Apple | `ibex2`'s `DarwinTransport` already hands bodies off in 64 KiB pieces (`vendor/ibex/crates/ibex2/src/transport/darwin.rs:70-73`); the executor delivers per message instead of collecting | a new `ibex2` transport |
| Linux | the `ibex2` rustls transport, read incrementally | the same |

Admission is the grant the request already needs. A streamed `GET` is a
`fetch` to an origin, admitted by `net.fetch`. A socket needs `net.websocket
<origin>`, which `ibex2` already parses (`vendor/ibex/crates/ibex2/src/grant.rs:106-107,
142`). Every reconnect is admitted again. Native fetch admits each redirect
hop before contact; the web follows a stream's redirects and checks only its
final response URL, with LLP 1071's intermediate-hop deviation. Messages never
reach the module except as parsed replies, so
the glue owns the socket and the module realm stays free of network
objects.

*Rejected:* exposing `EventSource`/`WebSocket` in the module realm. It would
make the module the I/O owner and break LLP 1016 D1 on the web alone.

### D4 — Bounds: coalesce to the latest, never queue without limit

A stream counts as one ticket on its lane for as long as it is open, with a
per-message byte ceiling (the existing response ceiling) and no charge for
messages already committed. If messages arrive faster than the runner
settles, the host keeps only the newest undelivered message per ticket:
display data coalesces, which LLP 1041 D2 permits ("display notifications
may coalesce"). A source that needs every message (an append-only log) says
so, and its backlog is bounded; past the bound the stream ends with a
visible failure, never a silent drop (LLP 1041 D2).

*Rejected:* backpressure to the server. SSE has no flow control, and
coalescing is what a view wants anyway.

### D5 — The agent drives streams deterministically

In agent mode a stream's messages are host events like any reply. An open
stream is not "in flight" for `clock settle` once its first message has
landed; otherwise `settle` would never end. `state` lists open streams with
their message counts. The fake transports in the executor tests grow a
scripted stream, so the runner half is tested without a socket.

### D6 — Until then: a long poll with a cursor

No code is needed for the interim pattern, and it removes the full-state
poll. The server holds `GET /changes?since=<cursor>` open until something
changes. The source answers with the change set and the new cursor, the
cursor lives in app state, and the change of argument re-asks. Snapback's
client is built this way (`GET /changes`, the long poll:
`issues/closed/20260913-snapback4-native-module-for-exact2-hosts.md:39`).
With F3 fixed, a forgotten long poll no longer holds a slot.

## Cost and what it touches

- **Runner:** an `Answer::Stream` variant, a ticket that survives its first
  fulfil, and a message counter in `state`. The settlement pass itself does
  not change.
- **Data seam:** `Work::Later`'s reply becomes callable more than once for a
  stream ticket, or a second reply type.
- **Hosts:** the web glue's streamed reader and SSE parser; the Apple and
  Linux executors deliver per message; one new `ibex2` transport per surface
  for WebSocket.
- **Contract:** none if D1 holds, since a source decides whether it streams.
- **Tests:** the fake transports, a runner test with three messages then a
  close, and `clock settle` with an open stream.

## As built (Claude (Opus 5.5), 2026-09-27)

LLP 1069.004 slices 1–2 build D1–D5 for server-sent events and slice 3 for
WebSocket; its "As built" sections are the detail. Where this RFC is
spelled differently:

- **D1.** A Rust source answers `Answer::stream(request)`, a constructor
  that returns `Later` with `Request::stream` set (so every forwarding
  source carries it), not a new variant. Messages are
  `Outcome::Message { event, id, data, coalesced }`; anything else ends the
  stream. TypeScript: `fetch(url, { exactStream: (event) => value })`, the
  mapper answering each event and the end, now.
- **D3.** Natively a stream opens and reads on its own thread with its own
  transport, not on an I/O worker.
- **D4.** Coalescing is the only mode, and on trial (1069.004 Decided 3); a
  log re-asks from its `Last-Event-ID` cursor across a gap, which the
  runner allows a message's parse to do. A stream counts against a bound of
  16 open streams and its lane's bytes, not the lane's request count.
- **D5.** `state.pending` lists a stream only until its first message;
  `state.streams` lists open streams with message and coalesced counts.
- **D3, WebSocket (slice 3).** A stream whose URL is `ws:`/`wss:` is a
  socket, admitted by `net.websocket` on every open; nothing else marks
  it (Rust `Answer::stream(Request::get("wss://…"))`, TypeScript
  `fetch("wss://…", { exactStream })`). It only listens: no method,
  headers, body or outbound frame, on any host. Each text message is a
  message; the far side's close (`the socket closed (code)`), a binary
  message or one over the ceiling ends it. The web glue owns the
  `WebSocket`; Apple uses `NSURLSessionWebSocketTask` and Linux a new
  rustls client, both in `vendor/ibex/crates/ibex2` (patch 2). A cursor is a query
  parameter (Jetstream's `cursor`), re-asked the same way as SSE's.
- **The web build (2026-10-04).** The JS target (LLP 1071) runs a stream
  through the wasm host's own reader (`host/web/http-body.js` `request`),
  for a Rust source's `Answer::stream` and a TypeScript `exactStream`
  alike, so admission, coalescing and the end are the same on both web
  targets; its runtime keeps the ticket per message and closes a stream
  once the commit that let its ticket go stands. A TypeScript stream's
  `fetch` must be made while the answer is asked, before its first
  `await`: the page has no turn to tie a later one to, and says so.
- **Beyond D7's web JS TypeScript slice, not built:** outbound frames and
  binary frames. Worker-placed TypeScript streams and native modules that
  stream remain unbuilt.

## D7 — Bidirectional sockets (Charlie, 2026-10-13, ruling 10)

“websocket send: mapper gets socket handle, send from a mutation; ordered
never-coalesced protocol frames vs coalescible snapshots; LLP 1016.000
amendment first — for now”. Consumers: T3 Code's subscribe, Ack and Ping
protocol, then the queued Supabase/Convex consumers. This supersedes D4's
coalescing-only WebSocket and the outbound-frame refusal above.
Implementer: Codex, websocket issue lane, 2026-10-13.

The mapper is `exactStream(event, socket)`. Its socket belongs to that
resource incarnation; keeping the handle in module state does not keep its
resource alive. The same handle accompanies `open`, every `message`, and
`close` (`code`, `reason`, `wasClean`). Binary messages have ArrayBuffer data;
text messages have string data. A transport refusal remains an `error`.
SSE keeps its existing mapper and coalescing behavior. A caller's abort
signal reaches the mapper as an `error` of kind `Aborted` while the resource
is still held; a forgotten resource receives no further mapper calls.

A mutation's synchronous source may call `socket.send(string | ArrayBuffer |
ArrayBufferView)`. Sending from a resource, the mapper, an overlay, or an
async continuation refuses. The source can save handles by its resource's
application identity; the host never looks up a socket by URL (two equal
URLs can belong to different resources). `readyState` and `bufferedAmount`
are read-only. `close(code, reason)` is also mutation-only; it accepts 1000
or 3000–4999, and at most 123 UTF-8 bytes, as the browser does. It does not
refresh the resource. Reconnect remains the app's decision.

Frames are copied when `send` is called, staged with the mutation, and sent
only after its commit stands. A thrown source, malformed answer, async
answer after staging, or refused commit sends none of its staged frames.
A mutation that stages socket operations answers with a value now: not a
promise, not a stream answer, and it makes no `fetch`. Socket operations
and a fetch in one mutation refuse whichever comes second, in either
order, and the mutation with it, before either effect leaves: no frame is
sent and no request starts.
A mutation may stage at most 256 operations and 1 MiB of payload. Admission
also checks the transport's buffered bytes against 1 MiB. Overload throws
`QuotaExceededError`, never coalesces or silently drops. If transport state
changes before publication, the host reports the failed send in the journal.
`send` before OPEN or after disposal throws `InvalidStateError`; unlike a
browser's silent send after closing, a stale runner handle always refuses.
The existing `net.websocket` grant is checked on open and publication.

Incoming protocol frames are never coalesced: each is mapped in arrival
order, then its shaped snapshot settles. A host may coalesce only those
snapshots after mapping every frame. The first slice settles every snapshot.
Its incoming queue holds at most 256 frames and 1 MiB (as well as each
request's response ceiling); overflow maps all frames already accepted into
the queue in order, then ends the stream with a visible Refused error.
Forgetting the ticket aborts it and invalidates its handle before further
delivery. `state.streams` retains the ticket and records socket
state, buffered bytes and sent-frame count; the journal records sends/close.

### Decided under Charlie's delegation, 2026-10-15, after Astra's review

1. **`bufferedAmount`, on every host,** is a snapshot of the transport's
   buffered bytes taken fresh at the start of each turn of the module (each
   mapper or mutation entry), plus the bytes this mutation has staged on
   that socket, which leave it if the mutation is refused or rolled back.
   Publication's admission stays authoritative. A count refreshed only by
   publication would stall a sender that stopped at a full reading, since
   nothing would refresh it; per turn, it is WHATWG's
   ([`bufferedAmount`](https://websockets.spec.whatwg.org/#dom-websocket-bufferedamount)):
   the count at the task boundary plus the task's sends.
2. **Socket operations and a fetch in one mutation** are refused on every
   host, whichever comes first, before either effect (above).

### As built, and declared host deviations

The TypeScript adapter on the web JS target implements D7 (2026-10-13).
Native TypeScript (Hermes) implements it on Apple and Linux (2026-10-15;
one Rust bridge serves AppKit and UIKit; driven on macOS and on the Linux
host, not yet on an iOS simulator), through one seam: the prelude stages a mutation's operations
on its call and hands them to the host door (op 14) only with an answer
given now; the module stages them on the runner's `Store` by the resource
that owns each socket; the runner addresses them to that resource's open
stream ticket (`SocketSend`) and keeps them in the commit's checkpoint, so a
refused commit sends nothing; after the commit, the host lets go of the
tickets the runner released, then hands each batch to the executor, which
checks it whole and sends it on ibex2's `MessageSender` (URLSession on
Apple, the portable transport elsewhere). A request's `socket` flag opts
the executor's reader into D7; Rust sources' streams stay listeners. The
native slice differs from the web JS target in these ways:

- The handle's `readyState` is what the mapper has seen: 0 until `open`,
  1 until the end or release, then 3; a staged `close` shows no 2.
- `bufferedAmount`'s turn snapshot is the runner's: before each mutation's
  and mapper's turn it reads every open socket's buffered bytes from the
  executor (`Runner::set_socket_reader`) into the store, which the module
  reads through door op 15. The check at publication also bounds the
  transport's buffer at 256 frames, the count past which both ibex2
  transports close the connection rather than queue (WHATWG's "full").
- A mutation's fetch is only recorded until its answer is handed to the
  runner, so the module withdraws a refused mutation's fetches (door op
  16). The web JS target starts a mutation's fetch after its source returns
  for the same reason.
- A caller's abort signal makes the handle stale at once, but the stream
  runs on, and the mapper gets no `Aborted` event, until the runner lets
  its ticket go.
- The grants are fixed for the executor's life, so the open's admission
  is the publication's.
- The receive queue's 256 frames and 1 MiB are the stream's own, beside
  its lane reservation (one message's ceiling).
- Releasing the resource sends a 1000 close (unless a mutation already
  closed it) and aborts the stream 250 ms later, or sooner when the far side
  answers, as the web's release closes it; frames arriving meanwhile are
  dropped. Retiring the executor sends the close and aborts at once, which the
  portable transport may cut off; a process that exits drops its
  connections, which a server reads as 1006.

Web wasm, Rust sources and worker-placed TypeScript remain receive-only.
On wasm the shared prelude passes the mapper a handle that never opens
(its host sends no `open`), so `send` refuses. No ambient WebSocket
constructor, kernel row, plan format, grant kind or cargo feature is added.
