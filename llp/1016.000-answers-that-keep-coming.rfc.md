# LLP 1016.000: Answers that keep coming

**Type:** RFC
**Status:** Implemented 2026-09-27: server-sent events (LLP 1069.004 slices 1–2) and a receive-only WebSocket (slice 3); web JS TypeScript bidirectional slice 2026-10-13 (D7); native TypeScript on Apple and Linux 2026-10-15 (D7); the mapper's replies 2026-10-17 (D7 amendment of 2026-10-16); a resource's answer's sends 2026-10-18 (D7 amendment of 2026-10-18); a byte stream 2026-10-23 (the amendment of 2026-10-23, ruled with LLP 1133.003)
**Systems:** Runner (a resource whose answer is a sequence; settlement per reply; the forget path ends it), Data seam (`Answer`, `Request`, the reply channel), Web host (`fetch` body streams, `EventSource`, `WebSocket` in the glue, never in the module realm), Apple host and Linux host (the executor keeps a response open; `ibex2` transports), Grants (`net.fetch`, `net.websocket`), Agent API (`clock settle` and a stream's replies), Contract (one resource form)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-24
**Related:** LLP 1016 D1 (the runner does no I/O), D2 (the host executes and delivers on the runner's thread), D4 (failure is data), D5 (one request per resource, the newest arguments win), §5 ("streaming and sockets … later"); LLP 1027 (the deferred list: "WebSocket and streams (a trigger)"); LLP 1041 D2 (every bound has an overload policy), D4 (cancellation protects identity), §8.4 (native HTTP admission); LLP 1012 §2 (`clock settle`); `rules/DEFERRED.md` (the doing-list bar; push *delivery* of updates is refused, which is a different thing)

## Summary

Every resource answers once. A source returns `Answer::Now` or
`Answer::Later(Request)` (`runner/src/request.rs:29-35`), the host runs the
request, and one outcome comes back to one ticket. Host work that hands its
reply to another owner does so through a `FnOnce(Reply)`
(`runner/src/request.rs:355-360`), so the type itself says one. The web
module realm deletes `WebSocket` and `EventSource` before app code runs
(`host/web/module-glue.js:113`, `host/web/module-worker.js:37`).

So live data is a timer. This RFC proposes a resource whose answer is a
**sequence**: each reply commits as its own settlement, and the stream ends
at a final reply, a close, a failure, or when the runner forgets the ticket.
The runner still does no I/O. The host keeps a response or socket open and
delivers each message the way it delivers a single reply today.

## Motivation

The Crew port report (2026-09-24), item D9: Crew's daemon publishes run
events on `GET /api/events` (server-sent events). With no push transport,
the port polls `GET /api/state` (190 KB) every two seconds. That poll ran
into two other defects in the same report:

- **F3.** A poll changes a resource's arguments, the runner forgets the old
  ticket, and the old job kept its executor slot. When one answer took longer
  than the poll interval, capacity drained and later asks were refused.
- **F4/F6.** The 190 KB body is the one that stalled under worker placement.
  A stream of small events would never have sent it.

LLP 1016 §5 put streaming and sockets later, pending a consumer; LLP 1027
lists "WebSocket and streams" as waiting on a trigger. A developer porting a
real app to exact2 who has to replace their event stream with a poll of the
whole state is that trigger. Weird Castle's relay (its `llp/0002`) is the
other one named in 1016 §5.

## Design

### D1 — A stream is a resource; each reply is a settlement

A source may answer `Answer::Stream(Request)`. The host opens it and
delivers zero or more messages to the same ticket. Each message is parsed by
the source's `parse`, exactly like a single reply, and commits as a
settlement pass (LLP 1016 D5: derives recompute, and resources whose
arguments changed ask again). The resource's value is the last message's.
`pending(resource)` is true until the first message arrives, then false.

A `Final` message, a close from the far side, or a `Failed` outcome ends the
stream. Failure is data (LLP 1016 D4): the source shapes it and the resource
keeps its last value.

*Rejected:* a `subscription` slot kind beside `resource` and `mutation`. The
app reads a stream exactly as it reads a resource, and `pending`, `refresh`
and the kept first frame all already mean the right thing for it.

### D2 — Interest ends a stream, through the forget path

When a stream resource's arguments change, or the resource leaves the plan,
the runner forgets the ticket (LLP 1016 D5), and a forgotten stream ends at
the host. That is the same forget-and-abort path the Crew report's F3 fix
adds for single requests. A late message on a forgotten ticket is dropped,
as it is today (`runner/src/runner/commit.rs:585`). `refresh` closes the
stream and opens a new one.

*Rejected:* explicit `open`/`close` statements in Contract. Interest is
already declared by arguments and presence; a second lifetime would drift
from the first.

### D3 — Per-surface transports, grants unchanged

| surface | server-sent events and streamed bodies | WebSocket |
|---|---|---|
| web | the glue's `fetch` reads `response.body` (an SSE parser over it), keeps its `AbortController` | the glue opens it; the module realm still has no `WebSocket` |
| Apple | `ibex2`'s `DarwinTransport` already hands bodies off in 64 KiB pieces (`vendor/ibex/crates/ibex2/src/transport/darwin.rs:70-73`); the executor delivers per message instead of collecting | a new `ibex2` transport |
| Linux | the `ibex2` rustls transport, read incrementally | the same |

Admission is the grant the request already needs. A streamed `GET` is a
`fetch` to an origin, admitted by `net.fetch`. A socket needs `net.websocket
<origin>`, which `ibex2` already parses (`vendor/ibex/crates/ibex2/src/grant.rs:106-107,
142`). Every reconnect is admitted again. Native fetch admits each redirect
hop before contact; the web follows a stream's redirects and checks only its
final response URL, with LLP 1071's intermediate-hop deviation. Messages never
reach the module except as parsed replies, so
the glue owns the socket and the module realm stays free of network
objects.

*Rejected:* exposing `EventSource`/`WebSocket` in the module realm. It would
make the module the I/O owner and break LLP 1016 D1 on the web alone.

### D4 — Bounds: coalesce to the latest, never queue without limit

A stream counts as one ticket on its lane for as long as it is open, with a
per-message byte ceiling (the existing response ceiling) and no charge for
messages already committed. If messages arrive faster than the runner
settles, the host keeps only the newest undelivered message per ticket:
display data coalesces, which LLP 1041 D2 permits ("display notifications
may coalesce"). A source that needs every message (an append-only log) says
so, and its backlog is bounded; past the bound the stream ends with a
visible failure, never a silent drop (LLP 1041 D2).

*Rejected:* backpressure to the server. SSE has no flow control, and
coalescing is what a view wants anyway.

### D5 — The agent drives streams deterministically

In agent mode a stream's messages are host events like any reply. An open
stream is not "in flight" for `clock settle` once its first message has
landed; otherwise `settle` would never end. `state` lists open streams with
their message counts. The fake transports in the executor tests grow a
scripted stream, so the runner half is tested without a socket.

### D6 — Until then: a long poll with a cursor

No code is needed for the interim pattern, and it removes the full-state
poll. The server holds `GET /changes?since=<cursor>` open until something
changes. The source answers with the change set and the new cursor, the
cursor lives in app state, and the change of argument re-asks. Snapback's
client is built this way (`GET /changes`, the long poll:
`issues/closed/20260913-snapback4-native-module-for-exact2-hosts.md:39`).
With F3 fixed, a forgotten long poll no longer holds a slot.

## Cost and what it touches

- **Runner:** an `Answer::Stream` variant, a ticket that survives its first
  fulfil, and a message counter in `state`. The settlement pass itself does
  not change.
- **Data seam:** `Work::Later`'s reply becomes callable more than once for a
  stream ticket, or a second reply type.
- **Hosts:** the web glue's streamed reader and SSE parser; the Apple and
  Linux executors deliver per message; one new `ibex2` transport per surface
  for WebSocket.
- **Contract:** none if D1 holds, since a source decides whether it streams.
- **Tests:** the fake transports, a runner test with three messages then a
  close, and `clock settle` with an open stream.

## As built (Claude (Opus 5.5), 2026-09-27)

LLP 1069.004 slices 1–2 build D1–D5 for server-sent events and slice 3 for
WebSocket; its "As built" sections are the detail. Where this RFC is
spelled differently:

- **D1.** A Rust source answers `Answer::stream(request)`, a constructor
  that returns `Later` with `Request::stream` set (so every forwarding
  source carries it), not a new variant. Messages are
  `Outcome::Message { event, id, data, coalesced }`; anything else ends the
  stream. TypeScript: `fetch(url, { exactStream: (event) => value })`, the
  mapper answering each event and the end, now.
- **D3.** Natively a stream opens and reads on its own thread with its own
  transport, not on an I/O worker.
- **D4.** Coalescing is the only mode, and on trial (1069.004 Decided 3); a
  log re-asks from its `Last-Event-ID` cursor across a gap, which the
  runner allows a message's parse to do. A stream counts against a bound of
  16 open streams and its lane's bytes, not the lane's request count.
- **D5.** `state.pending` lists a stream only until its first message;
  `state.streams` lists open streams with message and coalesced counts.
- **D3, WebSocket (slice 3).** A stream whose URL is `ws:`/`wss:` is a
  socket, admitted by `net.websocket` on every open; nothing else marks
  it (Rust `Answer::stream(Request::get("wss://…"))`, TypeScript
  `fetch("wss://…", { exactStream })`). It only listens: no method,
  headers, body or outbound frame, on any host. Each text message is a
  message; the far side's close (`the socket closed (code)`), a binary
  message or one over the ceiling ends it. The web glue owns the
  `WebSocket`; Apple uses `NSURLSessionWebSocketTask` and Linux a new
  rustls client, both in `vendor/ibex/crates/ibex2` (patch 2). A cursor is a query
  parameter (Jetstream's `cursor`), re-asked the same way as SSE's.
- **The web build (2026-10-04).** The JS target (LLP 1071) runs a stream
  through the wasm host's own reader (`host/web/http-body.js` `request`),
  for a Rust source's `Answer::stream` and a TypeScript `exactStream`
  alike, so admission, coalescing and the end are the same on both web
  targets; its runtime keeps the ticket per message and closes a stream
  once the commit that let its ticket go stands. A TypeScript stream's
  `fetch` must be made while the answer is asked, before its first
  `await`: the page has no turn to tie a later one to, and says so.
- **Beyond D7's web JS TypeScript slice, not built:** outbound frames and
  binary frames. Worker-placed TypeScript streams and native modules that
  stream remain unbuilt.

## D7 — Bidirectional sockets (Charlie, 2026-10-13, ruling 10)

“websocket send: mapper gets socket handle, send from a mutation; ordered
never-coalesced protocol frames vs coalescible snapshots; LLP 1016.000
amendment first — for now”. Consumers: T3 Code's subscribe, Ack and Ping
protocol, then the queued Supabase/Convex consumers. This supersedes D4's
coalescing-only WebSocket and the outbound-frame refusal above.
Implementer: Codex, websocket issue lane, 2026-10-13.

The mapper is `exactStream(event, socket)`. Its socket belongs to that
resource incarnation; keeping the handle in module state does not keep its
resource alive. The same handle accompanies `open`, every `message`, and
`close` (`code`, `reason`, `wasClean`). Binary messages have ArrayBuffer data;
text messages have string data. A transport refusal remains an `error`.
SSE keeps its existing mapper and coalescing behavior. A caller's abort
signal reaches the mapper as an `error` of kind `Aborted` while the resource
is still held; a forgotten resource receives no further mapper calls.

A mutation's synchronous source may call `socket.send(string | ArrayBuffer |
ArrayBufferView)`. Sending from an overlay refuses; a resource's answer,
an async continuation and the mapper send only as the amendments of
2026-10-16 and 2026-10-18 below allow. The source can save handles by its resource's
application identity; the host never looks up a socket by URL (two equal
URLs can belong to different resources). `readyState` and `bufferedAmount`
are read-only. `close(code, reason)` follows `send`'s rules; it accepts 1000
or 3000–4999, and at most 123 UTF-8 bytes, as the browser does. It does not
refresh the resource. Reconnect remains the app's decision.

Frames are copied when `send` is called, staged with the mutation, and sent
only after its commit stands. A thrown source, malformed answer, or
refused commit sends none of its staged frames. A mutation that stages
socket operations answers with a value now: not a stream answer, and it
makes no `fetch`. (By the amendment of 2026-10-18, one that answers with
a promise is an answer in flight, and what it staged goes as that
answer's.) Socket operations
and a fetch in one mutation refuse whichever comes second, in either
order, and the mutation with it, before either effect leaves: no frame is
sent and no request starts.
A mutation may stage at most 256 operations and 1 MiB of payload. Admission
also checks the transport's buffered bytes against 1 MiB. Overload throws
`QuotaExceededError`, never coalesces or silently drops. If transport state
changes before publication, the host reports the failed send in the journal.
`send` before OPEN or after disposal throws `InvalidStateError`; unlike a
browser's silent send after closing, a stale runner handle always refuses.
The existing `net.websocket` grant is checked on open and publication.

Incoming protocol frames are never coalesced: each is mapped in arrival
order, then its shaped snapshot settles. A host may coalesce only those
snapshots after mapping every frame. The first slice settles every snapshot.
Its incoming queue holds at most 256 frames and 1 MiB beyond one message's
response ceiling, so one frame within the ceiling always fits an empty queue;
overflow maps all frames already accepted into the queue in order, then ends
the stream with a visible Refused error.
Forgetting the ticket aborts it and invalidates its handle before further
delivery. `state.streams` retains the ticket and records socket
state, buffered bytes and sent-frame count; the journal records sends/close.

### Decided under Charlie's delegation, 2026-10-15, after Astra's review

1. **`bufferedAmount`, on every host,** is a snapshot of the transport's
   buffered bytes taken fresh at the start of each turn of the module (each
   mapper or mutation entry), plus the bytes this mutation has staged on
   that socket, which leave it if the mutation is refused or rolled back.
   Publication's admission stays authoritative. A count refreshed only by
   publication would stall a sender that stopped at a full reading, since
   nothing would refresh it; per turn, it is WHATWG's
   ([`bufferedAmount`](https://websockets.spec.whatwg.org/#dom-websocket-bufferedamount)):
   the count at the task boundary plus the task's sends.
2. **Socket operations and a fetch in one mutation** are refused on every
   host, whichever comes first, before either effect (above). On the web a
   fetch from a continuation that runs after the mutation's source returned
   is the module's, not the mutation's (the page has no turn to tie it to,
   as for a stream's fetch); natively the call owns it, so it is refused.
   (The amendment of 2026-10-18 keeps this for every mutation's
   synchronous source; an answer in flight's later turns may both fetch
   and send.)

### Amendment: the mapper answers its own frames (Charlie, 2026-10-16)

Charlie's ruling on `issues/20261017-socket-reply-in-the-frames-turn.md`
(Option 1; this amendment precedes the build). T3 Code's protocol answers
frames as they arrive, an `Ack` for each `Chunk` and a `Pong` for each
`Ping`, and subscribes on `open`, as a browser client does in its handlers;
a mutation could only answer a runner's turns later.

- The mapper may `send` and `close` on the socket it was handed, during
  `open` and `message` only. On `error` and `close` the handle is already
  CLOSED and refuses as before; a resource, an overlay, an async
  continuation and another socket's handle still refuse as the mapper's
  replies (the amendment of 2026-10-18 lets an answer's turns send).
- What a mapper call stages is sent once the commit that settles that
  frame's snapshot stands, in arrival order and ahead of later mutations'
  frames. Snapshots may coalesce; staged operations never do: a commit
  that settles N frames sends all N frames' operations, and its refusal
  sends none of them.
- A throw, a malformed snapshot or a refused commit sends nothing, and the
  journal says so as it does for a mutation. D7's bounds apply per mapper
  call (256 operations, 1 MiB, the transport's buffered bytes); overload
  fails that snapshot. The call makes no `fetch`.

As built (2026-10-17), on the hosts D7 covers:

- **Native TypeScript (Apple, Linux).** The prelude keeps a mapper call's
  operations apart from its stream's answer and hands them through door
  op 14 as the call returns, however it ended; `Module::message` stages
  them on the store; once the snapshot conforms, the runner addresses them
  to that frame's own stream ticket as a `SocketSend` whose origin is the
  resource's mapper (`SocketOrigin::Mapper`), kept in the frame's commit
  checkpoint. An operation on any other resource's socket refuses the
  frame.
- **A socket no resource owns** (a mutation's stream) takes none of its
  mapper's replies, on either kind of host: the frame fails with
  `InvalidStateError: the socket is not open`.
- **Web JS target.** A mapper call's operations ride its frame's answer
  as effects; `reply` in `host/web-js/rt.js`, through which `land` commits
  a stream message, queues them with the commit's outgoing work, which
  runs only if the commit stands.
- **Journal.** A frame that staged operations and did not stand (or whose
  answer reopened the stream), and a batch the host refuses at
  publication, read `mapper <resource> failed: <why>; socket frames were
  refused` (a mutation's: `send <mutation> failed: …`; natively, a
  mutation's stream names its source). Sent operations read `socket send:
  N bytes (<resource>)`.
- **Bounds.** Overload throws `QuotaExceededError` from `send` or `close`,
  as in a mutation (`socket mapper call exceeds 256 operations`, `… 1 MiB`,
  `socket buffer exceeds 1 MiB`), and fails the snapshot even when the
  mapper catches it. `bufferedAmount` counts what the call has staged.
  Publication checks each call's batch whole, as a mutation's.
- **Fetch.** `fetch` in that call rejects (`fetch() is unavailable in a
  socket's mapper: it answers each frame now`); no request starts.
- **Coalescing.** No host coalesces a socket's snapshots: each frame
  commits on its own, so each commit sends one frame's operations, and
  the batches reach the host in commit order.
- The web's wasm host and Rust sources stay as below: on wasm the handle
  never opens, so its mapper has no turn to send in; Rust sources have no
  handle.

### Amendment: an answer sends on its module's sockets (2026-10-18)

An answer that waits on a server's reply could not send the request it
waits on: a resource's answer refused, and so did a mutation that answered
with a promise, so the request went out from a mutation that the app ran
on a timer. The T3 Code clone's transport ran that timer every 16 ms while
any answer waited, its commands among them (mutations that await their
reply), and under the agent driver a clock step with the timer due waited
for every answer in flight, up to 20 s. An answer now sends its own
request and awaits the reply.

- **Who sends.** An answer in flight may `send` and `close` on a handle
  whose socket a stream resource of the same module owns and that is
  OPEN: a resource's answer, and a mutation's whose source answers with a
  promise, from that source on. A mutation whose source answers now keeps
  D7's rules above. The answer sends in its turns: its source's call, and
  each delivery of a fetch or storage step of its own, with the
  microtasks each drains. An answer may both fetch and send, but a
  mutation's synchronous source still may not do both.
- **Continuations.** Code that resumes from an await sends as the
  answer it began in, whichever turn drains it (LLP 1133.002 D14, from
  2026-10-18: the bundle lowers `async` through a helper that restores
  the answer at each resumption). A waiting answer that a mapper's frame
  settles sends its next request as itself when it is asked again; one
  whose reply another answer's turn settles sends as itself in that turn.
  A fetch made there is its own too. Code that resumes from an explicit
  `.then` callback, outside an `async` function, runs as the turn that
  drains it.
- **When they go out.** An answer is not a commit, but its turns run in
  one: each turn's operations are one batch, in the order its code made
  them, that goes out once the commit that ran the turn stands, behind
  earlier turns' batches and ahead of later ones. Nothing coalesces them,
  and nothing the answer does afterwards (a value, a failure, an answer
  outside its shape) takes them back. A refused commit takes them back,
  says so in the journal, and lets go of the answers it asked (natively,
  with their fetches). The code is not told, as it is not told of a batch
  the host refuses at publication: a protocol that awaits a reply times
  out.
- **An answer let go.** An answer the runner lets go (new arguments, a
  refresh, a newer send of the same mutation, its region ending) has no
  more turns: what it sent stays sent (LLP 1041 D4: cancellation does not
  undo a remote write), and nothing more goes out as its own. One the
  commit that asked it refused is let go with that commit's batches
  taken back. Its code that resumes later, from its rejected fetches or a
  promise of other work, is still its own, so its sends refuse. An answer
  asked again sends again; a protocol that must not repeat a request keys
  it.
- **Bounds.** D7's bounds apply per answer, over all its turns: 256
  operations and 1 MiB of payload, and the transport's buffered bytes.
  Overload throws `QuotaExceededError` from that call; what the answer
  sent before stands, and the answer is not failed.
- **`bufferedAmount`** in an answer's turn is the transport's bytes as the
  turn began, plus what earlier turns staged that the host has not yet
  taken, plus what this turn has sent on that socket. Publication's
  admission stays authoritative. Natively a mutation's and a mapper's turn
  now count earlier turns' untaken batches too, refining decision 1 of
  2026-10-15 there; the web JS target's do not.
- **Refusals.** A handle that is not OPEN, or whose socket no resource of
  this module owns (a mutation's stream, or another module's), throws
  `InvalidStateError`, and so does an operation after the answer's own
  `close` of that socket. A mapper still sends only on its own socket
  while it answers `open` or a `message`; an overlay, background work and
  a call made for no target (a bake) still refuse.
- **Journal.** Sent operations read `socket send: N bytes (<the socket's
  resource>)`. A batch the runner refuses, the host refuses, or a refused
  commit takes back reads `answer <resource or mutation> failed: <why>;
  socket frames were refused`, naming the answer whose turn sent it.

As built (2026-10-18), on the hosts D7 covers:

- **Native TypeScript (Apple, Linux).** The module tells the prelude a
  call's role (`__exact_call`'s third argument: a resource's answer, a
  mutation, or neither). The prelude hands an answer's operation through
  door op 17 as `send` or `close` is called, and a mutation whose source
  answered with a promise hands what it staged there as the source
  returns; door op 15 adds the turn's sent bytes to the turn's snapshot.
  `Module::begin` and `Module::resume` stage a turn's answer operations on
  the store apart from a mutation's staged ones, whatever the turn's step;
  the runner addresses them after the ask (`Runner::query`), the send
  (`ask_send`) or the delivery (`fulfill_inner`) that ran the turn, as a
  `SocketSend` whose origin is `SocketOrigin::Answer`, kept in the commit's
  checkpoint (`Runner::refuse_batches`). The turn snapshot
  (`Runner::snapshot_sockets`) is taken before every ask too, and adds the
  batches the host has not taken.
- **Web JS target.** A resource's answer sends only from its source's
  synchronous call, the one turn the page can tie to it, and a mutation
  whose source answers with a promise only from that call too. A
  continuation refuses, as before: the page cannot tell whose continuation
  runs, so a let-go answer's code could send. The call's operations ride
  the answer to the commit's outgoing work (`Out` in `host/web-js/rt.js`).
  Its `bufferedAmount` is the browser's count plus what the call has sent,
  as a mutation's is: batches of earlier turns in the same commit are not
  counted.
- Worker-placed TypeScript, the web's wasm host and Rust sources stay
  receive-only, as below.

### Amendment: a byte stream (2026-10-23)

Ruled with LLP 1133.003 (§16 question 3; Daehyeon Mun, 2026-10-23) and
recorded in its `rules/DEFERRED.md` entry. Consumer: the T3 Code clone's
iOS device stream, serve-sim's `GET …/stream.avcc`, an HTTP body of binary
envelopes that neither server-sent events nor a WebSocket carry.

- **What it is.** A TypeScript source's `fetch(url, { exactStream })` to
  an `http:` or `https:` URL whose response is 2xx and not
  `text/event-stream` gives its mapper `message` events whose `data` is an
  ArrayBuffer: the bytes read since the mapper's last turn, at arbitrary
  boundaries. Several transport reads join into one message, so the
  number of turns follows the mapper's pace, not the transport's
  chunking; no byte is dropped, reordered or coalesced (`coalesced` is
  0). A response that is not 2xx is still the one answer, as before.
- **Bound.** At most 1 MiB, or the stream's response ceiling where that
  is smaller, waits for the mapper. A read that would
  pass it ends the stream after the bytes already waiting, with a
  `Refused` error (`byte stream receive queue exceeds 1 MiB`, or `… the
  response ceiling`). The body's end is a `Network` error, `the byte
  stream ended`, as an event stream's is.
- **Who reads it.** TypeScript only: the prelude marks an HTTP stream
  `bytes` (`Request::bytes`), and the web JS target's adapter opts its
  reader in. A Rust source's stream, and the web's wasm host, still take
  such a body as the one answer.
- **What is no byte stream.** A response with no body, the Fetch
  standard's null body statuses (204 and 205 among the 2xx) or one to a
  `HEAD`, is the one answer, as the web's `response.body` is null for it.
- **The request.** Whether a stream is events or bytes is known only from
  the response, so a byte stream's request is a stream's: it carries
  `Accept: text/event-stream` unless the source names an `accept` header.
  A source whose server negotiates by `Accept` names its own
  (`headers: { accept: 'application/octet-stream' }`). Dropping the
  default for byte streams would drop it from every TypeScript event
  stream's request too.

As built (2026-10-23):

- **Native (Apple, Linux).** The stream's reader (`executor_bytes.rs`)
  appends each read to the one message of its ticket the runner has not
  taken, under the executor's lock. The module hands a binary message to
  the mapper as an ArrayBuffer the prelude makes its size and the host
  fills through the bytes door (op 9; `js/src/binary.js`), for a socket's
  binary frame too;
  the JSON beside it names only the size. Base64, decoded byte by byte in
  the interpreter, cost 1.8 ms of the main thread per 12 KB message (11%
  of a core for one 60 fps stream); the door costs microseconds.
- **Web JS target.** `http-body.js` `readBytes` joins the reads that
  land before the page's next task into one message.
- **Throughput.** LLP 1133.003 §9's gate measured this path with three
  60 fps H.264 streams on macOS and the web; its numbers are recorded
  there (§15, stage 0). A development build's agent reads them with
  `perf streams [start]`: per stream, its message, commit and decode
  rates, the time from the transport's receipt to the mapper's entry, to
  each decode and to the commit standing, and its share of the data
  executor (`runner/src/stream_timing.rs`, `host/web-js/ts-stream.js`).
  Production trust refuses it, as it refuses `perf`.

### As built, and declared host deviations

The TypeScript adapter on the web JS target implements D7 (2026-10-13).
Native TypeScript (Hermes) implements it on Apple and Linux (2026-10-15;
one Rust bridge serves AppKit and UIKit; driven on macOS, the Linux host
and, 2026-10-18, an iOS simulator), through one seam: the prelude stages a mutation's operations
on its call and hands them to the host door (op 14) only with an answer
given now (an answer's go through op 17 as each is made, by the amendment
of 2026-10-18); the module stages them on the runner's `Store` by the resource
that owns each socket; the runner addresses them to that resource's open
stream ticket (`SocketSend`) and keeps them in the commit's checkpoint, so a
refused commit sends nothing; after the commit, the host lets go of the
tickets the runner released, then hands each batch to the executor, which
checks it whole and sends it on ibex2's `MessageSender` (URLSession on
Apple, the portable transport elsewhere). A request's `socket` flag opts
the executor's reader into D7; Rust sources' streams stay listeners. The
native slice differs from the web JS target in these ways:

- The handle's `readyState` is what the mapper has seen: 0 until `open`,
  1 until the end or release, then 3; a staged `close` shows no 2.
- `bufferedAmount`'s turn snapshot is the runner's: before each mutation's,
  mapper's and answer's turn it reads every open socket's buffered bytes
  from the executor (`Runner::set_socket_reader`) into the store, with the
  batches the host has not taken, which the module reads through door op
  15. The check at publication also bounds the
  transport's buffer at 256 frames, the count past which both ibex2
  transports close the connection rather than queue (WHATWG's "full").
- A mutation's fetch is only recorded until its answer is handed to the
  runner, so the module withdraws a refused mutation's fetches (door op
  16). For the same reason the web JS target, in a module that holds a
  socket, captures a mutation's request when `fetch` is called and starts
  it after the source returns.
- A caller's abort signal makes the handle stale at once, but the stream
  runs on, and the mapper gets no `Aborted` event, until the runner lets
  its ticket go.
- The grants are fixed for the executor's life, so the open's admission
  is the publication's.
- A frame published after the far side closed, but before the reader has
  seen the close, is accepted and dropped by the transport, as a browser
  accepts a send until its close event runs; the stream then ends with
  that close. A transport that fails partway through a batch leaves what
  it took sent, and the journal says after how many operations.
- The receive queue's bound (256 frames, and 1 MiB beyond one message's
  ceiling) is the stream's own, beside its lane reservation of that ceiling.
- Releasing the resource sends a 1000 close (unless a mutation already
  closed it) and aborts the stream 250 ms later, or sooner when the far side
  answers, as the web's release closes it; frames arriving meanwhile are
  dropped. Retiring the executor sends the close and aborts at once, which the
  portable transport may cut off; a process that exits drops its
  connections, which a server reads as 1006.

A socket's grant may name a whole scheme (`net.websocket ws:` or `wss:`,
LLP 1016 D6 as amended 2026-10-17), so a socket reaches a server whose host
and port the app learns at run time. `state.streams` names the line that
admitted each stream (`grant`), on every host.

Web wasm, Rust sources and worker-placed TypeScript remain receive-only.
On wasm the shared prelude passes the mapper a handle that never opens
(its host sends no `open`), so `send` refuses. No ambient WebSocket
constructor, kernel row, plan format, grant kind or cargo feature is added.

The byte stream (the amendment of 2026-10-23) differs by host so:

- **The web's wasm host, Rust sources and worker-placed TypeScript** (a
  native worker's request is never `bytes`, `data/src/envelope.rs`) take a
  2xx body that is not events as the stream's one answer, as before it.
- **Reads.** Natively the reader reads at most the bound at a time, so a
  read never passes it alone. A browser may hand the web JS target one
  read longer than the bound; it goes to the mapper at once in pieces of
  the bound, after what was waiting, and the rest waits as a read of its
  own.
- **Turns.** Natively the bytes join until the runner takes the message;
  on the web JS target, until the page's next task, the mapper being
  synchronous there.
