## Summary

`@exact/passkeys` lets an app register a passkey for an account on its
own server and sign in with it, on the web, iOS, macOS and Android first.
Its tier 1 is WebAuthn's, the W3C's
[Web Authentication Level 3](https://www.w3.org/TR/webauthn-3/):
`credentials.create({publicKey})`, `credentials.get({publicKey,
mediation})` with conditional mediation (the passkey offered in a
username field's suggestions), `PublicKeyCredential`'s feature tests
and its three signal methods. Tier 2 reaches AuthenticationServices on
Apple (`ASAuthorizationPlatformPublicKeyCredentialProvider`, the security
key provider, `ASAuthorizationController`'s request options) and
Credential Manager on Android (`CreatePublicKeyCredentialRequest`,
`GetCredentialRequest`); tier 3 hands over each platform's controller
and request objects.

```ts
// grants: 'net.fetch https://auth-fixture.exact.test', 'auth.passkey auth-fixture.exact.test'
import { credentials } from "@exact/passkeys";

const options = await (await fetch(`${api}/passkey/sign-in`, { method: "POST" })).json();
const response = await credentials.get({ publicKey: options });   // the platform's sheet
const signed = await fetch(`${api}/passkey/verify`, { method: "POST", body: JSON.stringify(response) });
```

```
use getClientCapabilities, ClientCapabilities from "@exact/passkeys"

resource caps = getClientCapabilities() as shape ClientCapabilities
mutation signedIn as shape Account then home
action signIn
  send signedIn = signInWithPasskey()
```

Three decisions carry the module:

- **A ceremony's response is a proof, so it never enters the plan.**
  Data code calls `create` and `get`, sends the response to its server
  and answers only what the server returns, as an OAuth code is spent in
  the source and never reaches `state` (LLP 1069.006). Contract reads the
  capabilities; it cannot call a ceremony (D1, D12).
- **The relying party is a domain, and the bake derives its association
  from the grant.** `auth.passkey <rp id>` writes Apple's
  `webcredentials:` entitlement and, when the RP ID is the app's own
  origin, the `webcredentials` entry of its `apple-app-site-association`
  and the `get_login_creds` statement of its `assetlinks.json`; it prints
  what another domain must serve, and the origins its server must accept
  (D6).
- **A ceremony is a person's act.** It runs from a person's input or the
  app's own foreground code; a tool invocation or a wake fails
  `person-required` before the platform is asked, in every state (D8).

The consumer is `apps/auth-fixture`, exact2's sign-in fixture, which
gains "Create a passkey" and "Sign in with a passkey" against a relying
party in its fixture server that verifies each response by WebAuthn's own
algorithm (§10). No app in the repository owns accounts: every app that
signs in signs in to someone else's service, whose passkeys are bound to
that service's domain and cannot serve a third-party client. The product
consumer it unblocks is Snapback's password identity
(`snapback4/README.md`), whose server would become the relying party;
that is an ask of Snapback, for Charlie (§13).

Local-auth (LLP 1133.010) would fill its web cell over this module: §7
says what it needs, provides it as an in-process entry so that a PRF
output never travels the module's reply route, and names what it costs. The sign-in module,
a sibling RFC to come, takes federated identity; §8 draws the line.

## 0. What is new here

The modules before this one asked a platform for a reading (a position,
a level) or for an object (a camera, a recorder). A passkey ceremony is
different in four ways, each settled below and each a question in §13:

1. **The answer is a credential.** An assertion is a signature over a
   server's challenge, as good as a password for as long as that
   challenge is open. LLP 1018 D5 keeps credentials below the data seam,
   and a Contract `send` would put the response into a mutation's answer,
   which `state` shows the agent and the tools (D12).
2. **The capability depends on a domain the build does not control.** A
   native ceremony succeeds only if the RP ID's domain serves an
   association file naming this build: its team and bundle id on Apple,
   its package and signing certificate on Android. The development loop
   is loopback, and a loopback address is not a valid RP ID (D6, D14).
3. **A PRF output is a key.** The `prf` extension answers 32 bytes the
   authenticator derives after verifying the person, which local-auth
   would seal a secret under. The module's reply route is read by the
   runner (LLP 1133 D6 rule 1), so no answer of `create` or `get` carries
   one; the output has a path of its own (D10, §7).
4. **A result can be orphaned.** Once the platform has made a passkey,
   cancelling the call does not unmake it. A registration the app never
   delivers to its server leaves a passkey in the person's credential
   manager that the server will never accept (D11).

## 1. Tier 1

### D1 — WebAuthn's names, in the JSON forms

The interface declares:

| Name | Kind | Meaning | Contract | Data code |
|---|---|---|---|---|
| `credentials.create({publicKey, mediation})` | send; a request | register a credential; `mediation: "conditional"` is a passkey upgrade after a password sign-in (D3) | — | `await credentials.create({ publicKey })` |
| `credentials.get({publicKey, mediation})` | send; a request | an assertion; `mediation: "conditional"` offers passkeys in a field's suggestions and waits for a pick | — | `await credentials.get({ publicKey, mediation })` |
| `getClientCapabilities()` | live source; a fact; `sync` on Apple | what this target can do now (below) | `resource caps = getClientCapabilities()` | `await PublicKeyCredential.getClientCapabilities()` |
| `isUserVerifyingPlatformAuthenticatorAvailable()`, `isConditionalMediationAvailable()` | binding functions over `getClientCapabilities` | the web's two older feature tests | — | `await PublicKeyCredential.isConditionalMediationAvailable()` |
| `signalUnknownCredential`, `signalAllAcceptedCredentials`, `signalCurrentUserDetails` | sends; not requests | tell the credential manager what the server knows: a credential it does not recognize, the full list it accepts for a user, a user's new name | — | `await PublicKeyCredential.signalUnknownCredential({ rpId, credentialId })` |

Sources: `create` and `get`, [§5.1.3](https://www.w3.org/TR/webauthn-3/#sctn-createCredential)
and [§5.1.4](https://www.w3.org/TR/webauthn-3/#sctn-getAssertion);
the options, [§5.4](https://www.w3.org/TR/webauthn-3/#dictionary-makecredentialoptions)
and [§5.5](https://www.w3.org/TR/webauthn-3/#dictionary-assertion-options);
the feature tests, [§5.1.6](https://www.w3.org/TR/webauthn-3/#sctn-isUserVerifyingPlatformAuthenticatorAvailable)
and [`isConditionalMediationAvailable`](https://www.w3.org/TR/webauthn-3/#dom-publickeycredential-isconditionalmediationavailable);
`getClientCapabilities`, [§5.1.7](https://www.w3.org/TR/webauthn-3/#sctn-getClientCapabilities);
the signal methods, [§5.1.10](https://www.w3.org/TR/webauthn-3/#sctn-signal-methods).

**The JSON forms.** `publicKey` is `PublicKeyCredentialCreationOptionsJSON`
or `PublicKeyCredentialRequestOptionsJSON`, the forms
`parseCreationOptionsFromJSON` and `parseRequestOptionsFromJSON` read
([§5.1.8](https://www.w3.org/TR/webauthn-3/#sctn-parseCreationOptionsFromJSON),
[§5.1.9](https://www.w3.org/TR/webauthn-3/#sctn-parseRequestOptionsFromJSON)),
with every buffer a base64url string; the answer is the credential's
[`toJSON()`](https://www.w3.org/TR/webauthn-3/#dom-publickeycredential-tojson),
`RegistrationResponseJSON` or `AuthenticationResponseJSON`. That is what
a relying party's server sends and reads, what LLP 1124 D5's JSON body
carries without a bytes type, and what Android's Credential Manager takes
and returns itself (`requestJson`, `registrationResponseJson`,
`authenticationResponseJson`,
[Create passkeys](https://developer.android.com/identity/passkeys/create-passkeys),
[Sign in with passkeys](https://developer.android.com/identity/passkeys/sign-in-with-passkeys)).

**`ClientCapabilities`** is the record of
[§5.8.7](https://www.w3.org/TR/webauthn-3/#enum-clientCapability), each
key an `option<bool>`, `none` where the target does not say (the spec's
absent key): `conditionalCreate`, `conditionalGet`, `hybridTransport`,
`passkeyPlatformAuthenticator`, `userVerifyingPlatformAuthenticator`,
`relatedOrigins`, `signalAllAcceptedCredentials`,
`signalCurrentUserDetails`, `signalUnknownCredential`; `extensions`, a
record of `prf`, `largeBlob` and `credProps` for the spec's
`extension:<id>` keys; `preferImmediatelyAvailableCredentials`, the shared
word below, true on Apple and Android and false on the web (a declared
deviation: it is not among Level 3's capability keys); and `available`, LLP 1133 D8's feature test: this
target has an implementation and a platform credential manager.

**Errors** are WebAuthn's `DOMException` names
([§5.1.3.1](https://www.w3.org/TR/webauthn-3/#sctn-create-request-exceptions),
[§5.1.4.3](https://www.w3.org/TR/webauthn-3/#sctn-get-request-exceptions)),
in Contract `failure(…).code` and in data code a `DOMException`, as LLP
1133.006 D8 item 2 rejects:

| Name | When | Apple ([`ASAuthorizationError`](https://developer.apple.com/documentation/authenticationservices/asauthorizationerror)) | Android (`androidx.credentials.exceptions`) |
|---|---|---|---|
| `NotAllowedError` | the person cancelled, no credential matched, or the platform declined; one name on purpose, so an RP cannot learn which ([§5.1.3](https://www.w3.org/TR/webauthn-3/#sctn-createCredential), step 22) | `canceled` (which Apple also returns when `preferImmediatelyAvailableCredentials` finds nothing), `failed`, `notHandled`, `deviceNotConfiguredForPasskeyCreation` (iOS 26 and macOS 26, `ios(19.0)` in the SDK's header) | `CreateCredentialCancellationException`, `GetCredentialCancellationException`, `NoCredentialException`, `CreateCredentialNoCreateOptionException`, `*InterruptedException`, a DOM error of that name |
| `NotAllowedError`, message `person-required` | a tool, a wake or a headless session (D9) | — | — |
| `InvalidStateError` | `excludeCredentials` matched a credential the person already has | `matchedExcludedCredential` (iOS 18, macOS 15) | `CreatePublicKeyCredentialDomException` with that DOM error |
| `SecurityError` | the RP ID is not granted, not this page's registrable suffix on the web, or not associated with this build | `failed` for an RP ID the build is not associated with (stage 2 records the underlying error) | a DOM error of that name |
| `AbortError` | the call ended: its mutation was superseded, the session closed, or a modal ceremony replaced a conditional one (D9) | `cancel()` | coroutine cancellation |
| `NotSupportedError` | no implementation, no credential manager, or a word this target lacks | — | `*ProviderConfigurationException` |
| `ConstraintError` | a required resident key or user verification cannot be met | — | a DOM error of that name |

The platform's own code travels as tier 2 (`apple.code`,
`android.type`), so an app that must tell a cancel from no credential on
a native target can; the shared names keep the web's merge.

**Declared deviations,** each because a name here is a function that
answers, not a browser object:

- **The JSON forms in and out.** The web's `create` takes buffers and
  answers a `PublicKeyCredential`; here both are its JSON. A web
  developer's `parseCreationOptionsFromJSON`, `create`, `toJSON()` is one
  call. The web implementation does the parsing and `toJSON()`, with the
  spec's algorithms where a browser lacks them.
- **Imported, not global.** `credentials` and `PublicKeyCredential` are
  the binding's exports, since data code may not touch `navigator` (LLP
  1133 D6 rule 5); the binding groups the declared names under the web's
  two objects.
- **Data code alone calls a ceremony** (D12).
- **`getClientCapabilities` is a live source,** re-read when the app
  returns to the foreground, since the person can turn a credential
  manager on in Settings.
- **`preferImmediatelyAvailableCredentials`,** a shared word on `get`:
  both native platforms have it under that name
  ([`performRequests(options:)`](https://developer.apple.com/documentation/authenticationservices/asauthorizationcontroller/performrequests(options:)),
  `GetCredentialRequest`); with it, a `get` that finds no credential on
  the device fails `NotAllowedError` with no sheet. The web has no such
  option in Level 3 and fails it `NotSupportedError`, so an app that
  writes it reads `getClientCapabilities().preferImmediatelyAvailableCredentials`
  first.

### D2 — What a ceremony proves

| | Registration | Assertion |
|---|---|---|
| What the server learns | a new public key, its credential id, the authenticator's flags (user present, user verified, backup eligible and state) and, if asked and given, an attestation | that the holder of that key signed this challenge, with those flags |
| Who checks it | the app's server, by [§7.1](https://www.w3.org/TR/webauthn-3/#sctn-registering-a-new-credential): the challenge it issued, the `origin` in `clientDataJSON`, the RP ID's hash, the flags | the app's server, by [§7.2](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion), with the stored public key |
| Who it is | whoever passes the credential manager's check: biometry or the device credential under user verification | the same, on whichever device holds the passkey: a synced passkey is on every device of the person's credential manager |
| Secret? | no: a public key | a one-time proof, good while the server's challenge is open |

The module never verifies a response; it carries the platform's to the
data code that asked. A server that skips §7's checks is not protected
by anything here. The fixture's server does every check (§10), and
`docs/recipes/passkeys.md` points a server author at §7 and at the origin
list of D6.

### D3 — Conditional mediation, both ways

**Conditional `get`** offers the person's passkeys in the suggestions of
a field whose `autocomplete` ends in the token `webauthn` (`autocomplete="username
webauthn"`, [§5.1.4.1](https://www.w3.org/TR/webauthn-3/#GetAssn-ConditionalMediation-Interact-FormControl)),
and settles when the person picks one. The app starts it when the
sign-in screen shows; it shows nothing by itself:

| Target | Mechanism |
|---|---|
| web | `navigator.credentials.get({mediation: "conditional"})`; the browser reads the field's token |
| iOS | [`performAutoFillAssistedRequests()`](https://developer.apple.com/documentation/authenticationservices/asauthorizationcontroller/performautofillassistedrequests()) (iOS 16), which offers passkeys in the QuickType bar of a field whose content type is `.username`; the host already maps `"username webauthn"` to `.username` (`host/apple/Sources/ExactKit/Autofill.swift`) |
| macOS | absent: the method is unavailable on macOS (`ASAuthorizationController.h`); `conditionalGet` reads false and the call fails `NotSupportedError`, so the app shows its button |
| Android | [`pendingGetCredentialRequest`](https://developer.android.com/identity/autofill/credential-manager-autofill) on the field's `EditText` (Android 15, `androidx.credentials` 1.5); below API 35, `conditionalGet` reads false |

On Android the reader's fields are the framework's own `EditText`s
(`Fields.kt`), so the request attaches to the real view; the field's
autofill hint today takes the last token of `autocomplete`, which for
`"username webauthn"` is `webauthn`, so the hint drops a trailing
`webauthn` as the Apple mapping does (stage 3).

**Conditional `create`** is a passkey upgrade: after a password sign-in,
the credential manager may add a passkey for the account with no
prominent UI, or fail with none
([§5.1.3](https://www.w3.org/TR/webauthn-3/#sctn-createCredential);
Apple's [`requestStyle`](https://developer.apple.com/documentation/authenticationservices/asauthorizationplatformpublickeycredentialregistrationrequest/requeststyle-swift.enum)
`.conditional`, iOS 18 and macOS 15; Android's `isConditional`,
`androidx.credentials` 1.6). Its failure is never shown; the app tries
again at the next password sign-in, as Apple advises.

that ignores one; nothing refuses it.

### D5 — Access hatches

| Target | Object | Moment | The module owns | The app may |
|---|---|---|---|---|
| Apple | each `ASAuthorizationPlatformPublicKeyCredentialRegistrationRequest`, `…AssertionRequest` and security-key request | after the words are set, before the controller is made | `relyingPartyIdentifier`, `challenge`, `userID`, `name`, `allowedCredentials`, `excludedCredentials`, `requestStyle` | set what the words lack |
| Android | the `GetCredentialRequest` or `CreatePublicKeyCredentialRequest` | before the call; the hatch returns a replacement, since both are immutable | the options' `requestJson`, the credential options, the call's `Activity` | set the request's fields the words lack |
| Web | none | — | — | — |

**No hatch adds a credential type.** Apple's controller takes its
requests at construction (`initWithAuthorizationRequests:`, and
`authorizationRequests` is read-only, `ASAuthorizationController.h`), and
a request the module did not make would complete with a credential the
module has no way to deliver below the data seam. So the controller is
the module's alone, and Android's hatch may not add a credential option;
a sheet that offers more than passkeys waits for §8.

**A hatch cannot change whom the ceremony is for.** After the hatch
returns, the module sets the fields it owns again, as LLP 1133.010 D11
does, so a hatch that rewrote the RP ID or the challenge has no effect
and a development build names the change in the journal. The platform
would refuse an unassociated RP ID in any case; the re-assertion keeps
the grant check of D6 the only authority.

### D6 — The relying party: the grant, the association, the origins

**The grant** is `auth.passkey <rp id>`, the line LLP 1069.008 D2
already names, one per RP ID the app may use: a registrable domain (`example.com`, `login.example.com`), or `localhost` for development on the web. Admission refuses a ceremony
whose `publicKey.rp.id` or `publicKey.rpId` is not a granted line
(`SecurityError`, naming the line), before the platform is asked; an
omitted RP ID is the web's default, the page's effective domain, which
must be granted too, and on native targets an omitted RP ID refuses,
since there is no page. `auth.*` lines are exact2's and are stripped
before `ibex2` parses the rest, as `auth.session` is
(`runner/src/request.rs`).

**The derivations,** through LLP 1069.008's table:

| From `auth.passkey <rp id>` | Apple | Android | Web |
|---|---|---|---|
| the build's claim | `com.apple.developer.associated-domains` gains `webcredentials:<rp id>` ([the entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.associated-domains)); a development build writes `webcredentials:<rp id>?mode=developer`, so the device reads the file from the domain itself rather than Apple's CDN, and a release build never does | — (Android reads the domain's file; the manifest declares nothing for passkeys) | — |
| the domain's file, when `<rp id>` is the host of the app's `app.origin` | `/.well-known/apple-app-site-association` gains `webcredentials.apps` = `<team>.<bundle id>` | `/.well-known/assetlinks.json` gains a statement with `delegate_permission/common.get_login_creds` for the package and every certificate fingerprint the app lists ([prerequisites](https://developer.android.com/identity/credential-manager/prerequisites)); `handle_all_urls` only when the app also claims App Links | — |
| another domain | the bake prints the entry that domain must serve | the bake prints the statement that domain must serve | the page's origin must be the RP ID or under it, or be listed in the RP ID's `/.well-known/webauthn` ([§5.11](https://www.w3.org/TR/webauthn-3/#sctn-related-origins)), which the bake prints |
| `localhost` | nothing: no association names it; a native ceremony for it refuses `SecurityError` at admission | the same | the browser's own rule |

Both files are served by the app's origin (`host/web/build.mjs` writes
the association file's `webcredentials` for an auth callback today; LLP
1082 owes `assetlinks.json`), over HTTPS with no redirect, as both
platforms require ([Supporting associated domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains);
[prerequisites](https://developer.android.com/identity/credential-manager/prerequisites)).
The web build, which writes the files, signs no APK, so the Android
certificates are an input: `app.json`'s `host.android.certificates`, a
list of SHA-256 fingerprints (the debug key, the upload key, Play App
Signing's), to which an Android build adds its own signing certificate
when it publishes; one file serves them all. A Play signing key the
developer has not listed is named by the bake as missing.

**The origins the server must accept.** A response's `clientDataJSON`
carries an `origin` the server compares with a list of its own
([§7.1](https://www.w3.org/TR/webauthn-3/#sctn-registering-a-new-credential),
step 9). That list is per target:

- the web: the page's origin;
- Android: `android:apk-key-hash:<base64url SHA-256 of the signing
  certificate>`, one per certificate that signs the app, which "your app
  server" must allow-list
  ([Create passkeys](https://developer.android.com/identity/passkeys/create-passkeys));
  the debug keystore, the release key and Play App Signing's key are
  three different origins;
- Apple: the value AuthenticationServices writes, which Apple's
  documentation does not state; stage 2 records it from a real ceremony
  and the recipe gives it.

The bake prints, per target it builds, the origin it can compute (the
Android certificate it signs with) and names the ones it cannot (a Play
signing key the developer supplies). `pending` shows a ticket's origin
under the agent, so a drive's server sees the same strings (§10).

**macOS needs a provisioned build.** Associated domains are part of the
app's identifier ("adds the associated domains feature to your app ID",
[Supporting associated domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains)),
and on macOS "restricted entitlements must be authorized by a
provisioning profile" ([TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles)).
exact2's Mac development builds are signed ad hoc with no profile. So a
Mac build without one reads `available: false`, and its ceremonies fail
`NotSupportedError`; a release bake with an `auth.passkey` line and no
Mac profile refuses (`grant-needs-profile`, LLP 1133.010 D7's refusal).
The profile is the build input local-auth asks for (LLP 1133.010 §12
question 5), not a second one. Stage 2 confirms on a real Mac that the
entitlement is refused without a profile; if it is not, this paragraph
is withdrawn.

## 4. Permission and origin

### D7 — No permission; the ceremony is the consent

No platform asks a permission for passkeys: the sheet is the person's
consent, and user verification is the credential manager's, not the
app's. So LLP 1133.002 §4 applies as follows:

- **Declare:** `auth.passkey <rp id>` (D6); no `device.*` line and no
  purpose string. iOS asks for no `NSFaceIDUsageDescription` for a passkey,
  since Face ID runs in the system's process, not the app's.
- **Read:** there is no `state`. `getClientCapabilities` is the fact,
  with `available` (D1).
- **Ask:** each ceremony shows the platform's sheet, through D9's rules.
- **Explain and recover:** the app's own UI. Where `available` is false
  (no credential manager; on Android, `android.providerConfigured`
  false), the app shows its other sign-in, as a hand-built app does;
  exact2 adds no screen of its own.

The interface declares no `permission`, so the agent's `prefer
permission.passkeys` refuses by name.

### D8 — Origin: a person's act, never delegable

Every call carries its origin (LLP 1133.002 D12). Names are declared
with LLP 1133.009 D10 item 8's `"origin": "app"` and `"foreground":
true` where this table says:

| Origin | `create`, `get` (modal or conditional) | `signal*` | `getClientCapabilities` |
|---|---|---|---|
| a person's input; the app's own foreground code | proceeds (D9) | proceeds | answers |
| a tool invocation (LLP 1111) | fails `NotAllowedError`, `person-required`, before the platform is asked | fails `person-required` | answers |
| a background wake; a headless session | fails `person-required` | fails `person-required` | answers |
| the app in the background | fails `NotAllowedError` (`"foreground": true`) | proceeds | answers |
| the development agent | §10 | §10 | §10 |

**A ceremony is a person's act,** as a presence check is (LLP 1133.010
D12): no delegation record, reuse window or earlier ceremony by the
person satisfies one for a tool. Conditional `create` shows no UI, and
is refused to a tool all the same: it writes a credential into the
person's credential manager, and the platforms admit it only shortly
after the person signed in. The signal methods show no UI either, and
are refused to a tool because they remove or rename the person's
passkeys, which no app call can undo. An agent that needs the person
signed in asks through the app's own UI, whose button then calls `get`
from the person's input.

### D9 — No press on the web; one sheet at a time

**The web asks for no activation.** WebAuthn Level 3 asks for transient
activation only when the caller is a cross-origin frame
([§5.1.3](https://www.w3.org/TR/webauthn-3/#sctn-createCredential),
step 2; `get` asks for none), and WebKit, whose platform authenticator
once required a user gesture, removed that requirement for both
ceremonies in December 2023 ([bug 264444](https://bugs.webkit.org/show_bug.cgi?id=264444),
271656@main). So a ceremony reaches `navigator.credentials` by the
ordinary asynchronous path every module's web call takes: admission in
the page's runner, then the page module, loaded at its first call, from
data code on the main placement or a worker. exact2 adds no rule for
the press. A browser older than that change refuses a ceremony that is
not on a press's call stack with `NotAllowedError`, which the app shows
as any refusal; nothing here works around it.

**A challenge is never fetched by a resource.** A resource's answer is
kept across launches (LLP 1027 D4) and a challenge is single-use, so the
recipe fetches the options in the mutation that calls the ceremony.

**One ceremony at a time,** in LLP 1133.002 D9's queue of decisions, so a
passkey sheet never opens over a location prompt or a Face ID check, and
never shared: two queued `get`s show two sheets, since each answers its
own challenge. A conditional `get` is not a sheet and does not hold the
queue; a modal `create` or `get` that arrives while one is pending ends
it with `AbortError` first, as a browser allows one pending request and
iOS one controller per AutoFill-assisted request, and the app starts it
again when the sheet is done (the recipe's task does). A second
conditional `get` replaces the first likewise.

**Lifetimes.** A ceremony's lifetime is its call's (LLP 1133 D6 rule
2): a superseded mutation, a session's end (LLP 1133.009 D10 item 1's
`destroy`) or a conditional request's screen leaving cancels it,
`AbortSignal` on the web, `cancel()` on Apple, the coroutine on
Android; the platforms cancel a sheet when the app leaves the
foreground, and the call fails `NotAllowedError`.

### D10 — `@exact/passkeys`, an extension

```

```

The interface declaration, abridged, in LLP 1133.002 D13's form with LLP
1133.009 D10's additions and this RFC's:

```json
{
  "kind": "interface", "name": "@exact/passkeys", "version": "1.0.0",
  "grants": ["auth.passkey"],
  "groups": { "credentials": ["create", "get"],
              "PublicKeyCredential": ["getClientCapabilities", "signalUnknownCredential",
                "signalAllAcceptedCredentials", "signalCurrentUserDetails"] },
  "names": [
    { "send": "create", "request": true, "contract": false,
      "origin": "app", "foreground": true,
      "grants": { "publicKey.rp.id": "auth.passkey" },
      "options": { "publicKey": "json<PublicKeyCredentialCreationOptionsJSON>",
                   "mediation": "option<enum<optional|conditional>>" },
      "answers": "json<RegistrationResponseJSON>", "handles": { "id": "credential" } },
    { "send": "get", "request": true, "contract": false,
      "origin": "app", "foreground": true,
      "grants": { "publicKey.rpId": "auth.passkey" },
      "options": { "publicKey": "json<PublicKeyCredentialRequestOptionsJSON>",
                   "mediation": "option<enum<optional|conditional>>",
                   "preferImmediatelyAvailableCredentials": "option<bool>" },
      "answers": "json<AuthenticationResponseJSON>" },
    { "source": "getClientCapabilities", "live": true, "answers": "ClientCapabilities",
      "sync": { "name": "getClientCapabilitiesSync", "from": "read" } },
    { "send": "signalUnknownCredential", "contract": false, "origin": "app",
      "grants": { "rpId": "auth.passkey" },
      "options": { "rpId": "string", "credentialId": "string" } }
  ],
  "entries": { "web": { "lock": "LLP 1133.010 D13's entry, §7 here" } }
}
```

`json<T>` names a WebAuthn JSON dictionary the module passes whole: the
bake checks only that it is an object, and the platform checks the rest,
as a browser does. The Rust binding takes and answers
`serde_json::Value` for it, the TypeScript binding the dictionary's type
from the DOM's own declarations.

**Seam additions,** each general, each proved by the out-of-tree fixture
before this package uses it (LLP 1133.001 D8):

1. **`"contract": false`:** a name callable from data code alone. The
   compiler refuses a Contract `use` of it by name
   (`module-name-data-only`), so its answer never becomes a mutation's
   value in `state`. This module's reason is D12's; `secret.keep`'s
   values have the same rule as vocabulary.
2. **A grant matched by an argument's value:** LLP 1133.009 D10 item 9's
   grants per argument, with the line's target compared to the value
   (`publicKey.rp.id` to `auth.passkey <rp id>`), as `auth.session`
   compares a URL today (`runner/src/auth.rs`).
3. **Binding groups:** the generated binding exports the declared names
   under the web's objects (`credentials.create`,
   `PublicKeyCredential.getClientCapabilities`), and the plain names
   beside them.
4. **Android fields offered to an implementation:** the reader hands the
   bound implementation each `EditText` it makes whose `autocomplete` ends
   in `webauthn`, and tells it when one goes, so a conditional `get` sets
   `pendingGetCredentialRequest` on the real view (D3).

**No answer carries a PRF output.** Every implementation removes
`clientExtensionResults.prf.results` from a `create` or `get` answer
before it leaves the implementation and keeps `prf.enabled`, so a key the
authenticator derived never travels the module's reply route, which the
runner reads (LLP 1133 D6 rule 1), nor reaches data code, where the app
could put it in an answer. The one path for PRF output is the in-process
entry of §7. An app that wants PRF output in its own data code (an
end-to-end encrypted app's key, say) waits for a consumer and a ruling
that admits a secret to the module route. Every implementation also
applies §7 item 3's rule for a lock's marked user handle, whether or not
the app has a lock, since the passkey may have synced from one that
does.

Reused as they are: LLP 1133.009 D10's orderly end (item 1), foreground
(item 3), origin (item 8), grants per argument (item 9) and handles
(item 10, D11 below); LLP 1133.008 D8 item 5's one locked Gradle graph,
which resolves `androidx.credentials:credentials` and
`credentials-play-services-auth` (1.6.0, the current stable,
[releases](https://developer.android.com/jetpack/androidx/releases/credentials))
with the host's AndroidX; LLP 1133.010 D13's entry, for §7.

*Rejected:*

- **exact2's vocabulary,** a reserved request URL as `openAuthSession`
  is. That was the right home for an OAuth session, which needs a popup
  page, a callback route and a CSP-safe script only the host has (LLP
  1069.006). A passkey needs nothing only the runner has; LLP 1133 D5's
  default holds.
- **A redacted reply lane** for the response. The runner already
  journals a module call's name and outcome, never its body
  (`runner/src/runner/modules.rs`), and `state.extensions` shows no
  answer; what would expose a response is a Contract value, which item 1
  forbids.
- **Contract `send`s whose answer the runner withholds** from `state`.
  A mutation's answer is a value the view reads; a value the view may
  read but the agent may not is a second kind of state.

### D11 — A registration delivered or disposed

A `create` that the platform completed is a passkey in the person's
credential manager, whatever happens to the call. Two windows can orphan
it, and exact2 owns only the first:

- **Before data code has the response.** The answer is provisional until
  the runner delivers it to the awaiting call (LLP 1133.009 D10 item 10,
  with the credential id as the handle). When the runner drops it (the
  call's mutation was superseded or its session ended while the sheet was
  up, or after the sheet closed and before the reply reached the call),
  no server can have seen it, so the runner calls `dispose` on the
  implementation, which tells the credential manager the RP does not know
  the credential: `signalUnknownCredential` on the web,
  `reportUnknownPublicKeyCredential` on Apple (`ASCredentialDataManager`),
  `SignalUnknownCredentialRequest` on Android, where the target has it
  (D13). Elsewhere the journal names the orphan. Disposal is best effort:
  a credential manager may ignore a signal.
- **After data code has it.** Once delivered, the response is the app's,
  and the runner never disposes it: the data code may already have posted
  it, and a lost reply can follow a registration the server kept, so
  "unknown" could be false. A supersession or a failed post from then on
  is reconciled by the server's list, which the recipe passes to
  `signalAllAcceptedCredentials` after every sign-in, the signal whose
  answer is the server's own truth. A first registration whose post
  failed leaves no account to sign in to; when the person later picks
  that passkey, the server answers that it does not know the credential,
  and the recipe passes the assertion's id to `signalUnknownCredential`,
  the use WebAuthn gives that signal
  ([§5.1.10.2](https://www.w3.org/TR/webauthn-3/#sctn-signalUnknownCredential)).

An assertion dropped the same way is simply dropped: its challenge
expires on the server.

### D12 — Callers: data code alone for a ceremony

| Name | Contract | Data code | Request | `sync` |
|---|---|---|---|---|
| `credentials.create`, `credentials.get` | refused (`module-name-data-only`) | the binding | yes | no |
| `getClientCapabilities` | a live source | the binding; `getClientCapabilitiesSync()` where the host has `call` | no | Apple; elsewhere asynchronous |
| `signal*` | refused | the binding | no | no |

**Why data code alone.** A Contract `send` answers a mutation, whose
value is in `state`: the agent reads it, and a tool invocation can read
it (LLP 1111). An
assertion is good for as long as its challenge is open, so a value a
tool can read is a credential a tool can spend. LLP 1069.006 keeps an
OAuth code out of `state` the same way, and LLP 1018 D5 keeps every
credential below the data seam. So a ceremony runs in a mutation's data
code, which sends the response to the server and answers the account,
never the response; the recipe shows it, and the fixture's test checks
that no answer carries a response (§10). The rule binds exact2, not the
app: data code that returns a response in its own answer leaks it, as
data code that returns a token does (LLP 1133.010 D2).

### D14 — Development needs a domain

A native ceremony asks the credential manager to check the RP ID's
association file, so a development drive against the real platform needs
the fixture's relying party at an HTTPS domain that serves both files
naming the development build:

- **Apple** accepts `webcredentials:<domain>?mode=developer` in a build
  signed with a development profile: the device fetches the file from the
  domain directly, with "any valid SSL certificate … including a
  certificate that the system doesn't trust", once the person opts in on
  the device ([Supporting associated domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains)).
  The file lists the app by `<team>.<bundle id>`, and exact2's simulator
  builds sign with no team (`host/apple/build.mjs`'s `SIMULATOR_PREFIX`),
  so the simulator drive needs a team-signed build or an entry for that
  prefix; stage 2 establishes which, and whether the simulator keeps a
  passkey at all, which Apple's documentation does not say. A phone's
  development profile must carry the Associated Domains capability, as
  the Mac's does (D6).
- **Android** checks `assetlinks.json` at the domain over HTTPS with no
  redirect ([prerequisites](https://developer.android.com/identity/credential-manager/prerequisites)),
  with the debug certificate's fingerprint for a debug build. The fixture
  needs a public domain with a trusted certificate.
- **The web** accepts `localhost` as an RP ID on `http://localhost` (a
  secure context). exact2's development server prints
  `http://127.0.0.1:<port>`, and an IP address is not a valid RP ID
  ([§5.1.3](https://www.w3.org/TR/webauthn-3/#sctn-createCredential),
  step 7: the origin's effective domain must be a valid domain), so for an
  app that grants `auth.passkey localhost` it prints the `localhost` URL.

Under the agent none of this is needed: the substitute (§10) answers
every ceremony with no platform and no domain. The real drives need one
public HTTPS origin exact2 controls, for the fixture's relying party
(§13 question 4).

## 7. What local-auth needs from passkeys

LLP 1133.010 D15 keeps local-auth's web cell `later`, to be filled over
this module: `authenticate` as an assertion with user verification
required, and a locked secret as a value sealed under a key from the
`prf` extension's output, which the authenticator releases only after
verifying the person ([§10.1.4](https://www.w3.org/TR/webauthn-3/#prf-extension)).
This module can serve that cell, on these terms, and local-auth's own
RFC decides whether the cell is worth their cost. The entry is specified
here and built with that cell, at local-auth's ruling; §11's stages do
not build it.

**What this module provides:**

1. **The lock's ceremonies on an in-process entry, never on the module
   route.** The web implementation exposes `entries.web.lock`, the web
   arm of LLP 1133.010 D13's authenticator entry, which local-auth's web
   presence backend calls in the page: `register(name, salt, origin)`
   makes the lock's credential under a marked user handle (item 3) and
   evaluates `prf` (with a `get` right after, where the authenticator
   does not evaluate at creation); `derive(credentialId, salt, origin)`
   asserts with `allowCredentials` of that one id; and `discover(salt,
   origin)` asserts with an empty `allowCredentials` and answers only when
   the person picks a passkey whose user handle carries the marker, which
   is how a second device that the lock's passkey synced to learns its
   credential id once. Each answers the credential id and the 32-byte
   output to that backend alone. The backend keeps the id below the data
   seam (never in the unlocked value, a ticket, a journal body or a
   module answer), derives the sealing key, and answers `store.unlock` on
   the store's completion path. Neither
   is a `credentials.create` or `get` call: no module answer, ticket,
   journal body or `state` field carries the output (D10), and data code
   never sees it.
2. **The options a lock needs:** `authenticatorAttachment: "platform"`,
   `userVerification: "required"`, a name the person recognizes ("Excord
   lock"), and the page's own host as the RP ID, never a parent domain,
   which any sibling host could assert. Credentials are scoped to their
   exact RP ID, so where the app's sign-in uses another RP ID (its
   `auth.passkey` lines; `example.com` beside a page at `app.example.com`)
   a sign-in `get` never offers the lock; where sign-in uses the page's
   host too, the two share it, at the cost below. The challenge is
   random and local: no server verifies a lock's ceremony; the PRF output is the
   proof, since only the authenticator can produce it.
3. **A lock's credential is recognizable on every client, by its user
   handle.** Its `user.id` begins with a fixed marker (the bytes of
   `exact-lock:`, then 16 random bytes), which needs no local record, so
   this module recognizes it on any device and in any app built on it,
   including a device the passkey synced to that never registered it.
   On every target, this module:
   - refuses a data-code `create` whose `user.id` carries the marker
     (`NotAllowedError`);
   - never delivers an assertion whose `userHandle` carries it: a `get`
     whose person picked the lock's passkey fails `NotAllowedError`, so
     data code and its server never learn the lock's credential id; and
     withholds, the same way, an assertion with no `userHandle` from a
     `get` with an empty `allowCredentials`, where WebAuthn requires one
     ([§5.2.2](https://www.w3.org/TR/webauthn-3/#iface-authenticatorassertionresponse)),
     so a nonconforming authenticator cannot leak a lock's id;
   - refuses `signalAllAcceptedCredentials` and
     `signalCurrentUserDetails` for a marked user handle.

   `signalUnknownCredential` names only a credential id, which data code
   can learn only from an assertion this module delivered, and it never
   delivers a lock's. So no code built on this module can hide or delete
   a lock's credential.
4. **The facts:** `getClientCapabilities().extensions.prf` and
   `userVerifyingPlatformAuthenticator`, which local-auth reads to answer
   `presenceSecrets`; an absent key is unknown, so `presenceSecrets`
   reads false until a registration reports `prf.enabled`.
5. **The origin rule** (D8), which is local-auth's own (presence is not
   delegable), and **one sheet at a time** (D9), the same queue.
6. **The substitute:** local-auth's presence tickets answer a lock's
   ceremonies, not this module's `passkey` tickets; the entry's
   substitute is declared by local-auth, as its store operations' are.

**What it costs, which this module cannot remove,** and which local-auth's
web cell must state or decline:

- **Where sign-in uses the page's host, the lock's credential is a passkey
  of the site.** A platform authenticator in Safari or Chrome makes a
  discoverable, synced passkey whatever `residentKey` says, so the lock's
  credential appears beside the person's sign-in passkeys in a
  conditional or modal `get` with an empty `allowCredentials`, under the
  name the backend gave it. Item 3 makes picking it a refusal, not a
  sign-in, but the picker shows it.
- **Code not built on this module is not bound by item 3.** Another
  client of the same RP ID (a page the app's developer wrote by hand, a
  native app on another stack) can receive the lock's assertion and
  signal it unknown, and a person can delete the passkey in their
  credential manager. Either way the sealed value can no longer be
  opened, and the app signs in again, as LLP 1133.010 D4 resolves a lock
  it cannot keep: closed, never ungated.
- **"This device only" does not hold.** A synced passkey takes the lock
  to the person's other devices with their credential manager;
  `hints: ["client-device"]` is a preference, not a guarantee.
- **The registration dialog names the site:** "create a passkey for
  this site", which is the web's own way to guard a secret with the
  person's biometry, not a tell on the web.

## 8. Where passkeys end and sign-in begins

The sign-in module (LLP 1133.000 §3.1: FedCM's shape, Sign in with
Apple and Google) is a sibling RFC to come. The line:

- **Passkeys own the app's own credentials,** WebAuthn public-key
  credentials for a relying party whose domain the app's server answers
  for: the ceremony, the association, the origins, the signals.
- **Sign-in owns federated identity:** an identity provider vouching for
  the person to the app, through FedCM's `IdentityCredential` on the web,
  `ASAuthorizationAppleIDProvider` on Apple and Credential Manager's
  Google ID options on Android, with App Review's rule that Sign in with
  Apple accompany other social logins. `openAuthSession` (LLP 1069.006)
  stays the system-browser OAuth flow it is.
- **The native request is shared, and passkeys own it.** On both native
  platforms one request carries several credential types and shows one
  sheet: `ASAuthorizationController(authorizationRequests:)` takes a
  passkey request beside an Apple ID request and a password request, and
  `GetCredentialRequest` takes a list of options. A hand-built app that
  offers a passkey and Sign in with Apple shows one sheet; two modules
  making two controllers would show two, a tell, and would fail the
  ceiling test. So `credentials.get` and its implementation own the
  controller and the `GetCredentialRequest`, and the sign-in RFC adds its
  request types as members of `get`'s options (`apple`, `google`, and
  `identity` on the web, by the Credential Management API's own shape) that
  this module's implementation passes in the same platform request and
  answers with the credential the person picked. Until then, a member this
  module does not declare is refused by name, and no hatch adds one (D5).
- **Whether the web can combine them** is the sign-in RFC's to establish
  against FedCM and the Credential Management specification; this
  module promises nothing about it.
- **Saved passwords,** when an app asks for them in a sheet, join
  passkeys' `get` (the same relying party, the same sheet), not sign-in.

## 9. The substitute

**Shape:** `getClientCapabilities` is a fact; `create` and `get` are
requests (LLP 1069.007 D1); the signal methods are sends the substitute
records and answers at once. The module is not its own substitute (LLP
1133.006 D8 item 4): its implementation touches the person's credential
manager wherever it points.

**The fact.** `prefer extension passkeys.getClientCapabilities=…`
(fields laid over the default). The default: `available: true` and every
capability true, with each target's restrictions applied (macOS
`conditionalGet: false`; Android `extensions.prf: none`; the web
`preferImmediatelyAvailableCredentials: false`; a Mac build
without a profile `available: false`), so a drive sees each target's real
limits (LLP 1133.002 §6).

**Tickets.** Each ceremony, once admitted, holds a `passkey` ticket.
Its `args` name the ceremony (`create` or `get`), the mediation, the RP
ID, the origin this target's platform would put in `clientDataJSON` (D6),
the options as written, and the call's origin.

| Answer | Result |
|---|---|
| `type @t <ResponseJSON>` | the call answers it; the substitute checks only that it is a JSON object whose `type` is `public-key` |
| `tap @t cancel` | `NotAllowedError`, `apple.code` `canceled`, `android.type` the cancellation |
| `tap @t none` (`get`) | `NotAllowedError`, as cancel, with the platform's no-credential detail |
| `tap @t excluded` (`create`) | `InvalidStateError` |
| a modal ceremony while a conditional `get` is held | the conditional ticket retires with `AbortError`; the new one is held |
| a tool-origin or wake-origin ceremony | as production: `person-required`, no ticket |
| a superseded `create` whose ticket is answered | the answer is dropped and `dispose` is recorded in the journal (D11) |

There is no `prefer` that answers a ceremony: each one in a drive is an
answer, so a transcript shows every sheet a person would see.

**The software authenticator.** A response the fixture's server will
accept must be signed over its challenge. `packages/passkeys/test/authenticator.mjs`
is a software authenticator for drives and tests, outside the runner: given a
ticket's `args`, it makes a `RegistrationResponseJSON` (an ES256 key it
keeps in a file the drive names, `none` attestation, user present and
verified) or an `AuthenticationResponseJSON` signed by that key. A drive
reads the ticket from `state.pending`, runs it, and types the output.
The runner knows no authenticator: the substitute holds and answers, as
the declaration says, and the authenticator is test apparatus of the
package, as the OAuth fixture's approval page is of `auth-fixture`.

**Disclosure.** `state.extensions` lists `passkeys`, its binding per
target, each ceremony's kind, RP ID, origin and outcome, and the held
tickets; never a response's bytes. The journal names the ceremony and
its outcome.

**Declared, not built in,** in `exact.json`, as LLP 1133.002 §6 builds
it. `--bind passkeys` binds the real implementation under the agent, as
geolocation's stage 2 binds its: the real sheet answers instead of a
ticket.

**Production:** none of it.

## 10. The consumer: the auth fixture

`apps/auth-fixture` is exact2's sign-in fixture (LLP 1069.006): an app
and a fixture server (`fixture.mjs`) that implements an AT
Protocol-style OAuth authorization server, verifying every message as a
real server would. It gains passkeys, as a small relying party beside
it:

## 13. Rulings (Charlie, 2026-10-23: "Accept all (Recommended)")

Each question below was ruled as recommended, question 4 as its ruling
says.

1. **A ceremony is data code's alone** (D12, D10 item 1), refused to
   Contract by name, so a response never becomes a value in `state`.
   *Recommended: yes (80%).* The alternative, a Contract `send` whose
   answer is hidden from the agent, makes a second kind of state; an
   OAuth code is already kept out the same way.
2. **The grant derives the association** (D6): `auth.passkey <rp id>`
