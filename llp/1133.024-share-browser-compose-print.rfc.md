## Summary

Four modules of LLP 1133.000's wave 3, written as one RFC because each is
a hand-off between the app and the system's own UI, and the four meet the
same questions: where the system's code runs, what the app learns
afterwards, and what the agent holds in the system's place.

| Module | What the author writes | Tier 1 | Packaging | Consumer |
|---|---|---|---|---|
| **share target** | `"share_target": {…}` in `app.json`; a route that reads `searchParam(e, "text")` and `sharedFiles(e, "files")` | the Web App Manifest's `share_target` ([Web Share Target](https://w3c.github.io/web-share-target/)) | exact2's vocabulary: the manifest, the router and the host | Fieldnotes: "Save to Fieldnotes" from another app's share sheet |
| **in-app browser** | `send opened = openBrowser(url=u)` | a declared deviation; the web has no in-app browser, and its cell is `window.open` | `@exact/in-app-browser` | Excord: a message's link preview opens over the app on a phone |
| **compose** | `send sent = composeEmail(to=…, subject=…, attachments=[…])`, `composeMessage(…)` | shared words, named as `mailto:` and `sms:` name their fields ([RFC 6068](https://www.rfc-editor.org/rfc/rfc6068), [RFC 5724](https://www.rfc-editor.org/rfc/rfc5724)), which are the web's cell | `@exact/compose` | the Calendar example: "Email the invitation" to the guests it picked, with the event's `.ics` |
| **print** | `send printed = print(element="#note-print", title=t)` | `window.print()` ([HTML](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#printing)), of one element, a declared deviation; breaks by [CSS Fragmentation](https://www.w3.org/TR/css-break-3/)'s names | `@exact/print`, over a seam every package gets | Fieldnotes: File ▸ Print… (⌘P) prints the note |

Six decisions carry the design (§0): a received share is a location, as
the web's is; on Apple the share extension runs no app code and leaves
the share in an inbox the app claims, so nothing writes the app's store
but the app; on Android a share brings the app's one task forward rather
than starting a second session; the in-app browser is a package send,
not an argument of `openURL`; the composers are shared words with the URL
schemes as their web cell; and printing is LLP 1093's cut run over
pages, after a new unpublished layout of the element at the page's
width, with Chrome as the oracle where line boxes are fixed.

Every target with a host has a cell (§15). Web, iOS, macOS and Android
have all four. Windows has the browser, email and print now, and the
share target once its package identity lands (LLP 1115.004 D15). The
Linux host has no desktop session yet, so the browser, compose and the
print dialog wait for one; no Linux desktop receives shares; and
print's pagination runs there headless under the agent now. tvOS has
none of the four.

## 0. What is new here

1. **A received share is a location, not an event.** The web delivers a
   share as a navigation to the manifest's `action` with the shared
   members as query parameters. exact2 already delivers every incoming
   URL that way (LLP 1038 D8): the launch location when cold, one
   `navigate` when running. So a share reaches the app by the path a
   universal link takes, on every host, and files, which a URL cannot
   carry safely, travel by an opaque token whose files the host sets in
   the runner as a fact, arriving after the text (D2, D3).
   This keeps LLP 1114.006 D2–D3.
2. **On Apple the extension is a producer, not a second session.** LLP
   1126 D12 admits a share extension as a hosted surface "when an app
   needs it", running the existing presenter in the presenter-free
   composition. That composition does not run the UIKit presenter today
   (`ExactKit` is not built extension-safe, and calls
   `UIApplication.shared` in about fourteen places), and LLP 1126 D8's
   second writer to the store is not built either. A share target does
   not need either: the extension shows a compose sheet (the system's on
   iOS, an AppKit one on the Mac), writes the share into an inbox in the
   App Group under names it chose, and ends; the app claims it at its
   next launch or foreground, or at once when it is running. The
   extension links nothing of Exact's, so it is outside LLP 1126 D8's
   cohort, which this amends, and the app stays the store's only writer
   (D4). An authored composer inside the share sheet is LLP 1126 D12's
   path and waits for an app that needs one (§18).
3. **Android has one session a process, so a share comes to the app's
   task.** `ACTION_SEND` starts the receiving activity in the sender's
   task by default, where a second `ExactActivity` would take over the
   app's one host. An app that declares `share_target` instead marks its activity
   `singleTask`, and the share arrives as `onNewIntent` (warm) or the
   launch intent (cold), converted to the same location (D5).
4. **The in-app browser is a package send.** LLP 1114.004 proposed
   `openURL(url, popup=true)`, by `window.open`'s own word. Since then LLP
   1133 made modules packages with platform words, hatches, admission and
   a declared substitute, and the in-app browser needs all of them (a
   reader mode, Android's partial height; the `SFSafariViewController`
   handed to the app's Swift; a ticket under the agent; refusal to a
   tool). The embedder still decides every open that leaves the app, as
   it does for `openURL` (D11, D22 item 7).
5. **The composers are shared words.** iOS, macOS, Android and the Linux
   portal all prefill recipients, subject and body and carry attachments;
   the web carries no attachment. So `composeEmail` and `composeMessage`
   are tier 1 shared words (LLP 1133 D1), spelled with the URL schemes'
   field names, and the URL schemes are their web cell (D14).
6. **Printing is pagination the kernel half does.** LLP 1093 built CSS
   fragmentation for multi-column: a cut over the laid-out flow, by
   Chrome's rules, with the host's line boxes, translating fragments
   rather than laying out again. A printed page is a fragmentainer like a
   column. What is missing is a layout of the element apart from the
   screen's, at the page's width, which the kernel gains as one new
   entry; the cut then runs over it at the page's height, and each host
   paints the pages into its print context. The web prints with the
   browser's own fragmentation, and Chrome is the oracle for the cut on
   fixed-line fixtures, as for columns (D18, D20). `rules/DEFERRED.md`
   keeps "paged media and `@page`" out; this moves printing in and keeps
   `@page` out (§19).
7. **Seam additions,** each general and each proved by the out-of-tree
   fixture before a package uses it (LLP 1133.001 D8): an element-typed
   option; a file provider on Android for `app:/` files, which compose's
   attachments and `share(files=)` on Android both need; print pages
   from the host; and the painted hosts' first package implementations,
   which Linux's and Windows's cells need (D22).

## 1. What exists

- **Sending a share** is built (LLP 1069.003, LLP 1125 D12): `share(title=,
  text=, url=, files=)` through one runner rule (`runner/src/share.rs`),
  `UIActivityViewController` on iOS, `NSSharingServicePicker` on macOS,
  `navigator.share` on the web, an `ACTION_SEND` chooser on Android with
  no files (no `FileProvider`, `host/linux/src/presenter/requests.rs`),
  and refused on Linux and Windows. Under the agent it is a held request
  (`tap @t shared`).
- **Receiving a share** is nothing on any host. `share_target` is not in
  `scripts/app.schema.json` (which refuses unknown keys), though
  `scripts/deploy.mjs` already rewrites a manifest's `share_target.action`.
  LLP 1114.006 (Draft r2, 2026-10-08, unassigned) designed it before LLP
  1126 and LLP 1133.
- **Incoming URLs** are one path (LLP 1038 D8): iOS's
  `scene(_:openURLContexts:)` and `connectionOptions.urlContexts`,
  macOS's `application(_:open:)`, `protocol_handlers`, and
  `Session.openURL`, which makes a URL the launch location before boot and
  a `navigate` after. Android reads no incoming intent but the agent's
  extra (`MainActivity.kt`).
- **An Apple extension** exists: the widget extension of LLP 1126, packaged
  by `host/apple/widgets.mjs` (an `.appex` in `PlugIns/`, `XPC!`, the
  `-application-extension` compile with `_NSExtensionMain`, the App Group
  `group.<app id>`, a shared Keychain group, two device profiles chosen by
  `entryProfiles`, the Mac's sandboxed extension entitlements). It is
  widget-specific: the extension's name, id and extension point are fixed,
  and `entryProfiles` assumes one extension id.
- **The store across processes** (`host/apple/src/store.rs`): the app is
  the only writer; a commit bumps a counter in the group and posts a Darwin
  notification; the app re-asks its store readers on the ping or at
  foreground (`WidgetStoreObserver`). An extension never writes.
- **`openURL`** opens http, https, mailto and tel and the schemes
  `open_url.schemes` declares, on iOS, macOS, the web and Android; Linux
  and Windows journal it as unsupported. It does not pass the runner's
  command door. **No in-app browser** exists anywhere, and the Android
  reader has no AndroidX library.
- **The auth session** (`openAuthSession`, LLP 1069.006) is
  `ASWebAuthenticationSession` on Apple and a popup on the web; Linux,
  Android and Windows answer 501.
- **Mail and messages:** `mailto:` through `openURL` and links on every
  host that opens URLs, `sms:` only as a declared scheme on Apple and the
  web's JS target. No composer and no attachment anywhere.
- **Printing:** nothing. No `window.print`, `UIPrintInteractionController`,
  `NSPrintOperation` or `PrintManager`; no ⌘P in the Mac host. LLP 1093
  §5 says "exact2 does not print". The kernel's cut (`kernel/src/
  fragment.rs`) fragments a flow into intervals at a height, by Chrome's
  appeal order, with the host's line boxes (`TextMeasurer::lines`), and
  publishes the record (`Kernel::fragments`).
- **The seam** this RFC uses as the earlier modules built it: packages and
  their binding (LLP 1133.001); admission before dispatch, also under the
  agent, with an implementation as its own substitute (LLP 1133.006 D8);
  the package context's session clock, foreground fact and orderly end
  (LLP 1133.009 D10); `"origin": "app"` and `"foreground": true`; grants
  per name; `release(name, args)`; handles provisional until delivered;
  the presentation anchor and the window (LLP 1133.015 D16 item 3, LLP
  1133.018 D13 item 1); a sheet held as a ticket (LLP 1133.015 D16 item
  5); Android's `startActivityForResult` (LLP 1133.018 D13 item 2); and
  Maven libraries in the one locked Gradle graph (LLP 1133.001 D9 as
  amended).

# Part I — Share target

## 2. Tier 1

### D1 — The declaration is the manifest's `share_target`, as the web writes it

`app.json` is a Web App Manifest already (`name`, `start_url`,
`file_handlers`, `protocol_handlers`). The share target is its member,
written as the web writes it:

```json
"share_target": {
  "action": "/share",
  "method": "POST",
  "enctype": "multipart/form-data",
  "params": {
    "title": "title", "text": "text", "url": "url",
    "files": [{ "name": "files", "accept": ["text/plain", ".txt", "image/*"] }]
  }
}
```

- `action` and `params` are required; `method` is `GET` (the default) or
  `POST`; `enctype` is `application/x-www-form-urlencoded` (the default)
  or `multipart/form-data`
  ([Web Share Target](https://w3c.github.io/web-share-target/), an
  unofficial early draft). `params.files`, each entry a `name` and an
  `accept` list, is not in that draft but in Chromium, the one
  implementation, and needs `POST` and `multipart/form-data`
  ([Chrome](https://developer.chrome.com/docs/capabilities/web-apis/web-share-target);
  [MDN](https://developer.mozilla.org/docs/Web/Progressive_web_apps/Manifest/Reference/share_target)).
- **The bake checks it.** `action` is a path one of the app's routes
  matches, or the build fails, as a route literal fails. Each `accept`
  entry maps to a UTI on Apple (`DOCUMENT_UTIS` in `scripts/app.mjs`,
  plus `image/*`, `video/*`, `audio/*`), a MIME pattern on Android and a
  file type or data format on Windows, or the build fails, as
  `file_handlers` does.
- **Platform words** sit under the platform's key inside the member
  (D6); the web manifest the build publishes leaves them out.

Receiving needs no grant line. The person's choice of the app in another
app's share sheet is the consent, as picking a file is (LLP 1069.002);
reading what was shared needs `fs.read app:/tmp`, the grant the picker's
files already need. LLP 1069.008 D7's reach table gains the row "receives
shares", derived from the member.

### D2 — A share is one location: `action`, with the shared text as query parameters

The host that receives a share composes one location: `action`, with each
shared member under the parameter name `params` gives it, a member not
shared left out (`/share?title=…&text=…&url=…`), and delivers it as LLP
1038 D8 delivers any incoming URL: the launch location when the share
starts the app, one `navigate` when it is running. The app matches the
route and reads `searchParam(e, "text")`; the action on its navigation
root chooses `go` or `open`, as it does for a notification's click.

This is what the web does for `GET`, so a web share and a native share
reach the app identically, and the first frame of a cold share is the
route that shows it.

**Shared text is untrusted.** Any app can share anything, and any link
can spell `/share?text=…`, as on the web. The route shows what arrived
for the person to confirm or edit before the app keeps it, which is
Android's guidance ("let them confirm and edit the shared content before
your app uses it", [Receive simple data](https://developer.android.com/training/sharing/receive)).
A link often arrives in `text` rather than `url` (Chrome's note above;
Android has no URL extra), so a route reads both.

*Rejected:* a `share` event on the root carrying a record (a second
delivery path, and a payload shape the web does not have); a reserved
source the app reads after launch (a fact whose lifetime, "used up when?",
is apart from the screen that shows it). Both were LLP 1114.006 D2's
alternatives.

### D3 — Files are stashed by the host and read by token

A URL cannot carry a file, and a path in one is forgeable by any link. So
the host that receives a share copies each file into
`app:/tmp/shared/<n>.<ext>`, named from the launch seed and a counter and
never from the sender, as the picker names its files (LLP 1069.002 D4);
the sender's file name is only `Picked.name`. It reads the `Picked`
metadata as the picker does (name, type, size, and a picture's
dimensions), and the picker's conversion rule applies (LLP 1069.002 D6:
a HEIC photo shared to a target whose `accept` lacks `image/heic`
becomes JPEG, on the app's side).

**The location does not wait for the files.** The host draws an opaque
token for each `params.files` member from the launch seed's stream and
composes the location with it as that member's parameter
(`/share?text=hi&files=k7Q2xR…`), delivered at once as D2 says. The
files enter the runner as a fact, by LLP 1069.009 D1's setter shape:
`set_shared(token, files, dropped, pending)`, `pending` the number still
being copied. The host sets each token before the location arrives (on a
cold share with the boot's other facts, so the first frame is the
share's route with its text), copies, reads and converts off the main
thread, and sets the token again as files land, with `pending` 0 once
all have, bounded at five seconds, after which the rest are counted as
dropped. The setter calls are the recorded input, carrying the `Picked`
records as the picker's `change` does, so a replay rebuilds the same
tokens and lists, with the bytes as fixtures. The app reads the files
with one function beside `searchParam`:

```
sharedFiles(entry: Entry, name: string): SharedFiles   // { files: Picked[], dropped: number, pending: number }
```

It answers the files set under the token in `entry`'s `name` parameter,
how many are still arriving, and how many the host left out (a type
outside `accept`, a stream that could not be read, a file over the 64 MB
that an outgoing share also refuses, LLP 1125 D12), so the route shows
the text at once and a placeholder for each file still arriving, as a
hand-built share screen does, and says when a share arrived short. A
token not set this launch (a written link, an earlier launch's) answers
no files: a restored screen that still shows an old share's location
shows an empty share, never a second delivery. Files and tokens last
until the next launch, which empties `app:/tmp/shared/` before it copies
anything of its own. This is LLP 1114.006 D3 with the cap, the count and
the files that arrive after the text added.

## 3. Per host

### D4 — Apple: an extension that writes an inbox, and an app that claims it

iOS and macOS list an app in other apps' share sheets only through a share
extension (`com.apple.share-services`), a separate binary in the app's
`PlugIns/`. "There is no direct communication between an app extension
and its containing app; typically, the containing app isn't even running
while a contained extension is running", and only a Today widget may ask
the system to open its app
([App Extension Programming Guide](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionOverview.html)).
So the share crosses through the App Group's shared container, which both
can read and write ([Sharing data](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html)).

**The extension is the host's, and runs no app code.** One Swift
extension, the same for every app, parameterized by its `Info.plist`:

1. **It shows a compose sheet as a hand-built app's does:** the app's
   name, the shared text editable, a preview of the first attachment,
   Cancel and Post, whose title is the app's word (D6). On iOS that is the
   system's `SLComposeServiceViewController`, which Xcode's share extension
   template uses ("the system-provided compose view controller builds in
   some support for common tasks, such as previewing and validating
   standard items",
   [Share](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Share.html)).
   AppKit has no such class, so on macOS it is the host's own
   `NSViewController`, as Xcode's macOS share extension template builds
   one: a text view, a thumbnail of the first attachment, and Cancel and
   Post as the sheet's buttons, with AppKit's controls throughout.
2. **On Post it writes the share** to `<group>/shares/<uuid>/`: each
   attachment conforming to an accepted UTI streamed to disk as `<n>.<ext>`
   (a counter and the UTI's extension, never the sender's name) with
   `NSItemProvider.loadFileRepresentation(forTypeIdentifier:)` and never
   decoded; a `public.url` of http or https as `url`; the sheet's text as
   `text`; the item's `attributedTitle` as `title`; then `share.json` last
   (`{"v":1, "title", "text", "url", "files": [{"file", "name", "type", "member"}], "dropped": {member: count}}`,
   `file` the stored name, `name` the sender's, for `Picked.name`, and
   `dropped` what the extension left out, D3's count), by write-and-rename, so a directory without it is incomplete and
   ignored. It posts the Darwin notification `<app id>.shares` and calls
   `completeRequest(returningItems:)`. The claim refuses a record whose
   `file` is not one path segment of that form.
3. **It never opens the app.** Opening the containing app from a share
   extension is unsupported: only a Today widget may (above), and the
   responder-chain workaround some apps ship is outside the API and has
   broken across releases. A share therefore waits for the app.

**The app claims the inbox** at three moments: at launch, before boot,
where the oldest complete share becomes the launch location and the rest
queue as `navigate` events after the first frame (LLP 1038 D8's order for
pre-boot URLs); at each foreground; and, while it runs, on the Darwin
notification, which on the Mac, where the app is usually open, makes a
share arrive at once. Claiming moves each share's files into
`app:/tmp/shared/` under D3's launch-scoped names, never the inbox's own
(two shares may each hold a `1.jpg`); both containers are on one volume,
so a move is a rename. It then deletes the share's directory, and delivers it as D2 and D3 say.
Before boot the claim does only that: it reads `share.json`, renames,
draws the tokens and composes the location. The metadata read and the
picker's HEIC conversion (`Picker.swift`, a decode and re-encode at full
size) run off the main thread after it, arriving by D3's `set_shared`,
so a photo's conversion never sits before the first frame. This is host
code, not app code: no app JavaScript runs before first pixel
(`rules/RULES.md`).

**Against LLP 1126, and what it amends there.**

- **Outside the cohort** (D8 there amended, §17). LLP 1126 D8 has the app
  and every extension link one framework and share one compatibility id.
  This extension links no Exact runtime (no `ExactCore`, no kernel, no
  Hermes) and opens neither the store nor the update store, so it is
  outside the cohort: it ships inside the app's bundle, built and signed
  with it, and its one contract with the app is `share.json`'s versioned
  shape, which this RFC owns.
- **The app owns the store** (D8): the extension writes only its inbox,
  and the stored names (step 2) keep every write inside it, so there is
  no second writer.
- **A versioned inbox record.** `share.json` is the same for every app,
  never per-app generated Swift, so an inbox written by one version is
  claimed by the next. It is this RFC's record, not D9's envelope, which
  is the Live Activity's.
- **A hosted surface** (D12): the composer inside the share sheet is the
  system's or the host's, so nothing needs the presenter in an extension.
  An authored one, which LLP 1126 D12 would run as the presenter in the
  presenter-free composition, stays out (§18).
- **What development sees** (D14): the agent drives the claim path (D9),
  and an XCTest drives the extension's controller with a stub
  `NSExtensionContext`.

**Memory.** Apple says only that extensions' limits are "significantly
lower than the memory limits imposed on a foreground app"
([Creating an App Extension](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionCreation.html)).
The extension links Foundation, UIKit or AppKit, Social and
UniformTypeIdentifiers, streams files without decoding them, and holds
nothing but the sheet. Stage 2 records its peak resident memory sharing
ten 48 MP photos.

**Packaging.** `host/apple/widgets.mjs`'s parts are reused, not copied:
the App Group (`group.<app id>`, the one the widget extension uses), the
entitlements and the Mac's sandboxed extension entitlements, the appex
compile (`-application-extension`, `_NSExtensionMain`), and the signing
order (extension first, then the app). They move into a module for
extensions of any kind (`host/apple/extensions.mjs`, beside
`widgets.mjs`, which keeps only what is WidgetKit's); `entryProfiles`
learns a list of extension ids (`<app id>.widgets`, `<app id>.share`), each
needing its own profile on a device. The extension's `Info.plist`:
`NSExtensionPointIdentifier` `com.apple.share-services`,
`NSExtensionPrincipalClass`, and an `NSExtensionActivationRule` derived
from `params` (text when `text` is mapped, a web URL when `url` is, each
accepted file type with no count cap, as the web has none) unless the app
writes its own (D6). Built only for an app that declares `share_target`;
tvOS has no share sheet, so the bake skips it there and says so.

### D5 — Android: intent filters on the one activity, which comes forward

The build derives intent filters on the app's activity from the member
([Receive simple data](https://developer.android.com/training/sharing/receive)):
`ACTION_SEND` with `text/plain` when `text` or `url` is mapped, and
`ACTION_SEND` and `ACTION_SEND_MULTIPLE` with each `accept` MIME pattern
for `files`, written into the generated manifest the build already writes
for permissions (`host/android/app/build.gradle.kts`).

**One task.** Android starts the receiving activity in the sender's task
unless the activity says otherwise ("a new activity, by default, is
launched into the task of the activity that called `startActivity()`").
The process has one session (LLP 1133.017 D7), and a second
`ExactActivity` adopts that one host and releases the reader of the
first (`ExactActivity.onCreate`), so a share would take the app's only
session into the sender's task. An app that declares `share_target` therefore has
`android:launchMode="singleTask"` on its activity: a share brings the
app's task forward and arrives as `onNewIntent`, or as the launch intent
when the app was not running
([Tasks and the back stack](https://developer.android.com/guide/components/activities/tasks-and-back-stack)).
The share is one location (D2), so the router does the rest; Back follows
the app's own stack and then the system's.

**Conversion.** `EXTRA_SUBJECT` or `EXTRA_TITLE` is `title`; `EXTRA_TEXT`
is `text` (Android has no URL extra, so a shared link is in it); each
`EXTRA_STREAM` content URI is copied into `app:/tmp/shared/` off the main
thread through the grant the intent carries, arriving by D3's
`set_shared` after the location. A type outside `accept`, a stream that
cannot be read, or one over the cap is left out, journaled and counted in
`dropped` (D3), as are copies past D3's five seconds. A cold share is the
launch location whether or not it carries files: the first frame is its
route with its text, and the copies never hold that frame, which keeps
the launch inside the cold-start budget (`rules/RULES.md`).

### D6 — The platforms' words, and the other targets

**Platform words** in the member, under the platform's key, checked at
bake as LLP 1133 D2 says:

| Key | Word | Values | Beats |
|---|---|---|---|
| `apple` | `NSExtensionActivationRule` | Apple's activation dictionary (`NSExtensionActivationSupportsText`, `NSExtensionActivationSupportsWebURLWithMaxCount`, `NSExtensionActivationSupportsImageWithMaxCount`, `NSExtensionActivationSupportsMovieWithMaxCount`, `NSExtensionActivationSupportsFileWithMaxCount`, `NSExtensionActivationSupportsAttachmentsWithMaxCount`) or a predicate string ([Action Extension Keys](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/AppExtensionKeys.html)) | the derived rule |
| `apple` | `postTitle` | a strings key: the compose sheet's post button | "Post" |
| `android` | `mimeTypes` | MIME patterns for the filters | the derived patterns |
| `windows` | `dataFormats` | `Text`, `Uri`, `StorageItems`, `Bitmap`, `Html`, `Rtf` ([Receive content](https://learn.microsoft.com/windows/apps/develop/windows-integration/integrate-sharesheet-receive)) | the derived formats |

**Tier 3.** On Android the app's Kotlin is handed the incoming `Intent`
before the host converts it (`shareIntent`, an app-scope hatch, LLP
1075.003.000.001), for an extra the conversion does not read. On Apple
the extension runs no app code, so there is none; the web has none.

**The web.** The browser navigates to `action` with the members as query
parameters, which is D2's location as it stands, for `GET`. Only an
installed app is a target, in Chromium (Android, ChromeOS and desktop);
Safari and Firefox have none. A `POST` share, with files or without,
needs a service worker to take the form, since the page cannot read the
body of the navigation that loaded it and exact2's page server
answers `POST` with 405 (`host/render/src/serve.rs`); LLP 1030 D1 refuses
a service worker in v1. So the published web member is always `GET` with
the text members only, whatever `method` the app writes for the native
hosts, and the build says so when it rewrites `POST` or drops `files`
(§19, question 4).

**Windows.** A packaged app's share target, `uap:ShareTarget` in the
package manifest, arrives as an activation whose kind is `ShareTarget`,
with a `ShareOperation` whose data the app reads and then reports
complete ([Receive content](https://learn.microsoft.com/windows/apps/develop/windows-integration/integrate-sharesheet-receive)).
It needs package identity; LLP 1115.004 D15 gives exact2's Windows apps a
sparse package for exactly this, registered by the installer of its
stage S3. The host reads the activation at launch (or, warm, from the
redirected activation of the running instance), copies `StorageItems`
into `app:/tmp/shared/`, delivers D2's location and calls
`ReportCompleted`. Until S3 lands the bake publishes no share target for
Windows and says why.

**Linux:** absent. No desktop standard receives a share (the portals
send), and the Linux host runs headless or on KMS. A location on the
command line already arrives (LLP 1038 D8), which the agent uses.

**tvOS:** absent; it has no share sheet.

### D9 — Under the agent

The shape is **an incoming location**, the row LLP 1069.007 D6 already has
for a notification's click.

  (LLP 1038 D11). **Cold:** `--url "/share?text=hi"`. Both are built.
- **Files:** a share is a URL in the `share:` scheme, which only the
  driver speaks: `type <root> "share:?text=hi&files=scripts/fixtures/picker/photo.heic"`,

### D10 — Packaging, callers, cost, substitute and consumer

**Packaging: exact2's vocabulary** (LLP 1133 D5), for three reasons a
package cannot meet. The declaration is the manifest's, from which the
bake derives the extension's `Info.plist`, Android's filters and
Windows's package manifest, as it derives `file_handlers`'; delivery is
the router's (D2); and the code that receives a share runs before any
package loads (the claim before boot) or in a binary that links no
runtime at all (the extension).

**Callers.** `sharedFiles` is a plan function, read in Contract and passed
to data code as an argument, synchronous on every target (a table
lookup), never a request. The share itself is a location; nothing calls
it.

**Cost.** An app that does not declare `share_target` gets nothing: no
extension, no filter, no claim. One that does gets, on Apple, the
extension (Swift over system frameworks only; its size is recorded in
stage 2 by LLP 1047's probe) and one directory read before boot, which
the boot metric measures; on Android, two filters and nothing until a
share arrives.

**Grant and substitute.** No grant line (D1). The substitute is the
agent's incoming location (D9), LLP 1069.007 D6's row for an incoming
URL; nothing is held.

**Consumer: Fieldnotes, "Save to Fieldnotes".** Fieldnotes declares
`share_target` with `action: "/share"`, `title`, `text`, `url`, and files
of `text/plain`, `.txt` and `.md`. Its `/share` route opens a new note
whose title is the shared title and whose body is the text, the link and
each file's text, for the person to edit and save, or cancel. That is the
acceptance drive on iOS, macOS and Android (Fieldnotes gains an Android
crate), on the web for text in installed Chromium, and on Windows once
LLP 1115.004 S3 lands (Fieldnotes gains a Windows crate, which §13 needs
too).

# Part II — In-app browser

## 5. Tier 1

### D11 — `openBrowser(url)`, a declared deviation

The web has no in-app browser: a page can open another browsing context,
not present one over itself. So tier 1 is a declared deviation (LLP 1133
D1), one send of `@exact/in-app-browser`:

```
send opened = openBrowser(url=link.url)
```

- `url` is an absolute `http` or `https` URL; anything else refuses with
  `TypeError`, and the app opens it with `openURL`.
- It answers `{action}`: `"dismissed"` when the platform reports that the
  person closed the page, which only iOS does; `"opened"` where the host
  handed the page to the system and learns nothing more.
- `inAppBrowserStatus()` is the module's fact: `available` (LLP 1133 D8),
  false on Linux and tvOS (D12), where the send refuses with
  `NotSupportedError`; and `overApp`, whether the page will be presented
  over the app (iOS; Android when a Custom Tabs provider resolves, read
  again at each foreground) or open in the browser beside it (macOS,
  Windows, the web, Android without a provider), which is what an app
  branching on the fact needs.
- **The embedder decides.** A session's delegate decides navigation that
  leaves the surface (LLP 1031 D5: `Session.follow` hands a non-route
  link to the delegate's `openURL`). So the implementation asks the
  delegate before it presents or launches, through the context (D22 item
  7); a refusal answers `NotAllowedError`. The stock adapters approve; on
  the web, which has no delegate, the browser's popup policy is the only
  check.
- The app never reads the page, its URL after navigation, or its
  cookies, on any host. That is what the platforms give (on iOS,
  "interactions with the web interface aren't visible to your app, and
  you can't access AutoFill data, browsing history, or website data"),
  and what a person who sees the browser's chrome expects. A page the app reads is an `iframe`
  (LLP 1020), and a sign-in is `openAuthSession` (LLP 1069.006).

**Why not `openURL(url, popup=true)`.** LLP 1114.004 recommended it, by
`window.open`'s own word. It predates LLP 1133. An in-app browser needs
what packages give and `openURL` cannot: platform words (reader mode,
Android's partial height), hatches (the controller handed to the
app's Swift), admission (a tool cannot open one), a substitute (a held
ticket), and a package that an app which never opens a link does not
link. `openURL` is a host command that does not pass the runner's door,
and LLP 1133 D6 freezes that list. `openURL` stays the command that
leaves the app. The package is not `@exact/browser`, which is the
partitioned iframe's site data (LLP 1020.002 D4).

**Why not `link target=`.** HTML's `target` names a browsing context, not
its presentation. A link that opens in the app is a `link href=u
press=openLink(u)`, whose action sends `openBrowser`; the `href` keeps the
link's role, its context menu and its web behaviour.

  `"opened"`; a web view in a sheet would be the tell.
- **Android:** a Custom Tab
  ([Custom Tabs](https://developer.chrome.com/docs/android/custom-tabs)):

- **tvOS:** absent. SafariServices is not on tvOS, and the platform has
  no browser.

# Part III — Compose

## 8. Tier 1

### D14 — `composeEmail` and `composeMessage`, shared words

LLP 1133.000's row put the composers at tier 2 under `mailto:` and `sms:`
through `openURL`. They are tier 1 here, as shared words (LLP 1133 D1):
iOS, macOS, Android and the XDG portal all take recipients, a subject, a
body and attachments, and a module whose common use is reached only by
two platform keys fails the ceiling test. The URL schemes stay, as the
web's cell and as the fallback where no composer exists. The fields are
spelled as `mailto:` and `sms:` spell them
([RFC 6068](https://www.rfc-editor.org/rfc/rfc6068) §2;
[RFC 5724](https://www.rfc-editor.org/rfc/rfc5724) §2.2). `@exact/compose`:

```
send sent = composeEmail(to=emails, cc=[], bcc=[], subject=t, body=b, attachments=["app:/tmp/invite/a.ics"])
send sent = composeMessage(to=numbers, body=b, subject=t, attachments=[])
```

- `to`, `cc`, `bcc` are lists of strings; `subject` and `body` plain
  text; `attachments` the files `share(files=)` takes (`app:/` paths and
  `#id` pictures, LLP 1125 D12). Every field may be empty: the composer
  opens with what is given, for the person to finish.
- Each answers `{action}`: `"sent"`, `"saved"` (a draft), `"cancelled"`,
  `"failed"`, where the composer reports its result, and `"opened"` where
  the host handed it to another app and learns nothing more.
- `composeStatus()` is the module's fact: `available`, `email`,
  `emailAttachments`, `emailCopiesWithAttachments` (whether `cc` and
  `bcc` keep their roles in a mail that also has attachments; without
  attachments every host keeps them), `message`, `messageSubject`,
  `messageAttachments`, each true where this host can do it now. It is read again at each
  foreground, since a Mail account added in Settings changes it. A send
  carrying a field the fact says this host cannot carry refuses with
  `NotSupportedError` rather than dropping it, so an app that needs an
  attachment checks first and falls back to `share(files=)` where that
  carries files (not Windows, D15).
- The person sends. Nothing here sends mail or a message without them, on
  any host; that is a server's job.

## 9. Per host

### D15 — The system's composers, or the URL schemes

- **iOS, email:** `MFMailComposeViewController` when `canSendMail()`
  ([MFMailComposeViewController](https://developer.apple.com/documentation/messageui/mfmailcomposeviewcontroller)):
  recipients, subject, plain body, each attachment by
  `addAttachmentData(_:mimeType:fileName:)` (read off the main thread,
  the type from the file's UTI), presented from the context's
  presentation; its result is the answer. When no Mail account is set
  up, `canSendMail()` is false and the cell is a `mailto:` URL through
  `UIApplication.open`, which opens the person's default mail app,
  answering `"opened"`; `emailAttachments` is then false.
- **iOS, message:** `MFMessageComposeViewController` when `canSendText()`
  ([MFMessageComposeViewController](https://developer.apple.com/documentation/messageui/mfmessagecomposeviewcontroller)),
  with `subject` when `canSendSubject()` and attachments by
  `addAttachmentURL(_:withAlternateFilename:)` when
  `canSendAttachments()`; its result is the answer.
- **macOS:** a mail with no attachment is a `mailto:` URL through
  `NSWorkspace`, which keeps `cc` and `bcc`. One with attachments is
  `NSSharingService(named: .composeEmail)`, and a message is
  `.composeMessage`
  ([NSSharingService](https://developer.apple.com/documentation/appkit/nssharingservice)),
  with `recipients` and `subject` set and the body and the attachments'
  file URLs as the items; `canPerform(withItems:)` is the fact. The
  service has one `recipients` list and no roles, so a mail with
  attachments and a `cc` or `bcc` refuses with `NotSupportedError`
  (`emailCopiesWithAttachments` is false): putting a `bcc` among the
  visible recipients would disclose it. The delegate's `didShareItems`
  answers `"opened"` (the compose window is Mail's or Messages's),
  `didFailToShareItems` `"failed"`. Messages takes no subject, so
  `messageSubject` is false.
- **Android, email:** with no attachment, `ACTION_SENDTO` on a `mailto:`
  URI, which only email apps handle; with attachments, `ACTION_SEND` or
  `ACTION_SEND_MULTIPLE` with `EXTRA_STREAM` content URIs from the host's
  file provider (D22 item 2), the read grant on each, and a `mailto:`
  selector, so only email apps answer. Recipients, subject and body are
  `EXTRA_EMAIL`, `EXTRA_CC`, `EXTRA_BCC`, `EXTRA_SUBJECT` and `EXTRA_TEXT`
  ([Common intents: email](https://developer.android.com/guide/components/intents-common#Email)).
  Email apps return no result, so it answers `"opened"`; the fact is
  whether an activity resolves, which needs a `queries` entry for
  `SENDTO mailto:` (D22 item 6).
- **Android, message:** `ACTION_SENDTO` on `smsto:` with `sms_body`; with
  attachments, `ACTION_SEND` with `EXTRA_STREAM`, `sms_body` and
  `subject`, addressed to the default SMS app
  ([Common intents: text messaging](https://developer.android.com/guide/components/intents-common#Messaging));
  `"opened"`.
- **Windows, email:** with no attachment, a `mailto:` URL through the URI
  launcher, which opens the default email app
  ([Launch the default app for a URI](https://learn.microsoft.com/windows/apps/develop/launch/launch-default-app));
  `"opened"`. With attachments, Simple MAPI's `MAPISendMailW`, which
  opens the registered mail client's compose window with the files
  attached
  ([MAPISendMailW](https://learn.microsoft.com/windows/win32/api/mapi/nc-mapi-mapisendmailw)),
  answering by its result (`"sent"` or `"cancelled"`, as the client
  reports). Only a mail client that registers as the system's Simple
  MAPI client answers it, and current Windows's own mail apps often do
  not, so `emailAttachments` false is the expected Windows result. A
  send with attachments is then refused with `NotSupportedError` (D14),
  and `share(files=)` is no fallback, since Windows sends no shares
  (§1): the app leaves the attachment's action out there. Stage 6
  records which clients on the NucBox register.
- **Windows, message:** absent. Windows has no SMS composer an app can
  count on; the `ms-chat:` scheme the URI page lists opens a Messaging
  app that the fact cannot find installed, and stage 6 checks it on the
  NucBox.
- **Web:** a `mailto:` URL composed from the fields, percent-encoded as
  RFC 6068 §2 says, assigned to `location.href`, answering `"opened"`;
  attachments absent. A message is not offered on the web (`message`
  false), by choice: a desktop browser has no `sms:` handler and fails
  silently, and the page cannot tell a phone's browser, which has one,
  from it. An app that wants the phone case writes an `sms:` link.
- **Linux:** later, with a desktop host. The Linux host today has no
  desktop session (KMS or headless), so nothing can show a composer. The
  XDG Email portal (`ComposeEmail` with `addresses`, `cc`, `bcc`,
  `subject`, `body` and `attachment_fds`,
  [Email](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Email.html))
  is the cell then.
- **tvOS:** absent; MessageUI is not on tvOS.

# Part IV — Print

## 11. Tier 1

### D17 — `print(element, title)`: `window.print()` of one element

`window.print()` prints the document
([HTML: printing](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#printing)).
An exact2 app's document is its screen, with its controls, and printing
the screen is not what a hand-built app does: an iOS app hands the print
system a renderer of its content, a Mac document prints the view it
chooses, and an Android app writes the document it prints. So the tier 1
name is `window.print()` of one element, a declared deviation, as
`@exact/print`:

```
send printed = print(element="#note-print", title=fields.title)
```

- `element` names one node by `id`, a new option type (D22 item 1); no
  such node refuses with `NotFoundError`. It may be `hidden` on screen:
  the print pass lays the element out shown, its own `hidden` ignored and
  its descendants' kept. So an app prints a view made for paper (a title
  and paragraphs) and never shows it, which on the web is what an
  `@media print` sheet does.
- `title` names the print job (and the default file name of Save as PDF).
- It answers `{action}`: `"printed"` when the job was handed to the print
  system, `"cancelled"` when the person cancelled, and `"opened"` on the
  web, where the browser does not say. An error rejects with
  `OperationError`.
- `printStatus()` is the fact: `available`.
- Saving a PDF is the system's: the Mac's print panel's PDF menu, iOS's
  share action in the print preview, Android's Save as PDF printer and
  the browser's destination. A PDF of an element without the print UI is
  not here (§18).

## 12. Pagination

### D18 — A print layout at the page's width, cut at its height

1. **The page is the platform's.** Paper size and the printable area come
   from the print system the person is using: `UIPrintPageRenderer`'s
   `paperRect` and `printableRect`, the Mac's `NSPrintInfo`, Android's
   `PrintAttributes` (media size and minimum margins), the printer's
   device context on Windows. There is no `@page`; the platform's paper
   and margins are what a hand-built app prints with.
2. **The print layout, a new kernel entry.** Nothing in the kernel does
   this today: `measure_height_targets` measures owners under a view root
   and replaces the live environment, and a `display: none` subtree lays
   nothing out. So the kernel gains one entry, `print_layout(element,
   page)`: a second layout engine over the element's subtree alone, with
   its own node map, the element as its root and shown (its own `hidden`
   ignored), its inherited style taken from its ancestors' styles, and
   as its environment the page's printable area as viewport, the light
   scheme, no motion (every transition at its end) and scroll offsets at
   zero. Inherited values resolve in that environment, not on screen: a
   `light-dark()` colour (`ColorValue::LightDark`, or `ColorValue::Wide`
   for a wide-gamut pair, `kernel/src/style/wide.rs`) or a role's colour
   (`--exact-canvas-text`, `kernel/src/style/roles.rs`) takes its light
   half, as `ColorValue::resolve(false)` (`kernel/src/style.rs`) does, so
   a note printed from a dark screen prints dark ink on white.
   The screen's used colours are never the print pass's inherited style.
   It reads the arena's styles and writes nothing back:
   the screen's engine, its viewport and its published frames are
   untouched. It is built when printing and dropped after.
3. **Pages, by LLP 1093's cut.** LLP 1093's cut (`kernel/src/fragment.rs`
   and `fragment/cut.rs`) runs today only inside a multi-column
   container, over its flow thread. The print layout's root becomes a
   fragmentation context of its own whose fragmentainers are pages of
   the printable height, walked by the same code: the same legal break
   points, Chrome's appeal order, `orphans` and `widows`, `break-inside:
   avoid`. What it writes back (the used heights `settle` sets) lands in
   the print engine only. The monolithic rule is LLP 1093's, stated once:
   what is monolithic in Chrome too (an image, a control, a scroll
   container, LLP 1093 D3) and what the kernel alone keeps monolithic (a
   definite height, a decorated box, a row flex container, a grid, LLP
   1093 D10) stay so, and one taller than a page starts a page and is
   clipped at its bottom, as LLP 1093 D4 lets it overflow a column. CSS
   lets a user agent slice such a box as a last resort (CSS Fragmentation
   §4.4); that is out (§18), and a print view is a block flow of text and
   images, as Fieldnotes' is. The schema's `break-before`, `break-after`
   and `break-inside` admit `page` and `avoid-page` (refused by the
   compiler today). In the print layout they act on pages as `column` and
   `avoid-column` act on columns. On screen they do nothing, inside a
   multi-column container too: "if the flow is not paginated, they have
   no effect", and a forced break "not contained within a matching type
   of fragmentation context" has none
   ([CSS Fragmentation](https://www.w3.org/TR/css-break-3/) §3.1, §4.3).
   **A multi-column box inside a print element** is a fragmentation
   context nested in the pages, which LLP 1093 D10 item 2 keeps
   monolithic (`kernel/src/fragment.rs`). It stays so here, by LLP 1093
   D3's rule: a box that does not fit moves whole to the next page, and
   one taller than a page starts there, lays out its columns, and is
   clipped at the page's bottom like any monolith; a `page` break inside
   it is not honoured.
   CSS would continue it as another row of columns on the next page
   (§2.2), and that waits (§18). The print pass journals each box it
   clipped and each page break it could not honour, by element, and the
   agent's `state` shows them, so an app finds out under its drive, not
   on paper.
4. **Translation, not layout.** Every page has the same width, so no line
   changes between pages: the cut chooses which lines go on which page
   and translates boxes, as it does for columns.
5. **Again on a new paper.** iOS's preview and Android's print dialog
   change paper while open; each change runs the pass again. A commit
   while the print UI is open does not: the pages are the element as it
   was when the person asked.
6. **Backgrounds print.** A native app prints what it draws. The browser
   drops backgrounds by default; the web cell sets `print-color-adjust:
   exact` on what it prints so the two agree
   ([CSS Color Adjustment](https://www.w3.org/TR/css-color-adjust-1/)).

The pass's result is the page list: per page, the boxes and fragments on
it with their translations, which each host paints (D19). The web prints
with the browser's own fragmentation. Chrome is the oracle for the cut
only where line boxes are fixed, as LLP 1093 §4 compares columns (D20):
the kernel takes each host's line boxes, so a proportional note breaks
where that host's lines fall, not where Chrome's do.

  painter of the layout record, so a page is drawn by presenter views
  built for that page off screen and rendered into the print context
  (`CALayer.render(in:)`). Stage 0 measures this against three criteria:
  text stays vector in a saved PDF, the page matches the screen's
  painting of the same vocabulary, and a page of text draws in under 50
  ms. If it fails one, the alternative is `ExactSnapshot`'s nodes drawn

  snapshot painter). That painter has a smaller vocabulary (text, images,

  the new attributes and reports the page count; `onWrite` starts each

  structure with `Canvas.drawRenderNode` (`Player.kt`), which a software

  of its own rather than the live view's, into a `RenderNode` and
  rendered by `HardwareRenderer` into an `ImageReader` (API 29, the
  reader's minimum) at the printer's resolution, capped at 300 dpi; the
  result is copied to a software bitmap and drawn onto the PDF page, as
  Windows prints a raster. Vector text on Android needs a software interpreter of the op
  stream, which this RFC does not stage. The job's state answers.
- **Windows:** `PrintDlgExW` for the printer and its device context
  ([PrintDlgEx](https://learn.microsoft.com/previous-versions/windows/desktop/legacy/ms646942(v=vs.85))),
  the page size from the context, then `StartDocW`, and per page
  `StartPage`, the painted presenter's raster of the page at the
  printer's resolution (capped at 300 dpi) drawn with `StretchDIBits`,
  and `EndPage`; then `EndDoc`
  ([StartDocW](https://learn.microsoft.com/windows/win32/api/wingdi/nf-wingdi-startdocw);
  [GDI printing](https://learn.microsoft.com/windows/win32/printdocs/gdi-printing)).
  Raster text is the cost of the painted presenter; a vector path is an
  improvement this RFC does not stage.
- **Web:** the JS target clones the element into a print root inside
  `#exact-root`, so the app's rules, which are scoped `#exact-root#exact-root
  .cN` (`host/web-js/src/emit.rs`), and the host's resets still match it;
  the root carries `color-scheme: light`, `print-color-adjust: exact`,
  and the properties the element inherits from its parent, so a subtree
  that inherited its type keeps it once moved. Those that do not depend
  on the scheme (`font-family`, `font-size`, `font-weight`, `direction`
  and the like) are copied as the parent computes them, a unitless
  `line-height` as specified; those that do (`color`) are copied as the
  parent's specified value (`light-dark()`, `var(--exact-*)`), so they
  resolve in the light scheme as D18 says, rather than as the dark
  screen's used colour. The element's own `hidden` is dropped. A print
  style hides the root's other children and sets `html`, `body` and
  `#exact-root` to `height: auto` and `overflow: visible`, so a long
  element runs on past one viewport; `document.title` is the title for
  the job; it calls `window.print()`, and on `afterprint` removes the
  print root and the print style and restores the title.
  Clone, not move, so the screen is untouched; a clone carries no canvas
  pixels, so a `canvas` prints blank (§18). A nested-typography fixture
  is in stage 7's drive.
- **Linux:** later, with a desktop host: today there is no desktop session and no

  ([Print](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Print.html))

- **tvOS:** absent; UIKit's printing is not on tvOS.

   rather than LLP 1126 D12's presenter in an extension now, which amends
   LLP 1126 D8: such an extension is outside the cohort. *Recommended:*
   yes; the authored composer waits for an app that needs one.
2. **It never tries to open the app** (D4). A share waits for the next
   launch or foreground, except where the app is running (usually so on
   the Mac), where the ping delivers it at once. *Recommended:* yes; the
   workaround is outside the API.
3. **Android's activity becomes `singleTask` for an app with
   `share_target`** (D5). It changes such an app's task behaviour
   everywhere, not only for shares. *Recommended:* yes; one session a
   process allows nothing else.
4. **Web file shares wait for a service worker** (D6), which LLP 1030 D1
   keeps out of v1. *Recommended:* defer, with the web's files cell
   waiting; text shares ship now.
5. **The in-app browser is a package send, `openBrowser`,** superseding
   LLP 1114.004's `openURL(popup=true)` (D11). *Recommended:* yes. This
   also reverses LLP 1069 §5's "Not now: an in-app browser".
6. **Printing comes in from `rules/DEFERRED.md`.** DEFERRED keeps "paged
   media and `@page`" out of the multi-column entry. This moves printing
   (a print layout, the cut over pages, `page` and `avoid-page`) in, with
   Fieldnotes as the consumer and Chrome as the oracle on fixed-line
   fixtures, and keeps `@page` and slicing a monolithic box out.
   *Proposed DEFERRED text:* "Still out: column-span, regions, `@page`
   (page size, margins and page-margin boxes), `box-decoration-break:
   clone`…; printing an element is LLP 1133.024." *Recommended:* yes.
7. **A Rust implementation slot for the painted hosts** (D22 item 4) is
   the first package code on Linux and Windows, and every later module
   with a Linux or Windows cell uses it. *Recommended:* build it with this
   RFC's Windows cells, since three of the four need it.
8. **A file provider on Android** (D22 item 2) also gives `share(files=)`
   its files. *Recommended:* yes.
9. **`canShare` answers wrongly on two hosts** (found reading the share
   code): true on tvOS, which has no share sheet, and false on Android,
   which shares text. Not this RFC's; a `QUEUE.md` line.

## 20. Build plan

Each stage lands with its drive green on each target it names. Linux is
driven headless; Windows by cross-check and on the NucBox over SSH
(`bun scripts/agent.mjs windows --app <app> …`, `docs/testing.md`).

**Stage 0 — probes.** Apple's page painter against D19's three criteria
(a page of Fieldnotes' text, an image and a grouped list through
`CALayer.render(in:)` into a PDF context, the text extracted from the
saved PDF; under the snapshot fallback, a page with a control refused by
name); the extension's memory sharing ten 48 MP photos on a simulator;
an Android page replayed through `HardwareRenderer` into a bitmap on a
`PrintedPdfDocument`: a page over one second or a document over 4 MB a
page drops the cap to 150 dpi, and a failure at 150 dpi leaves Android's
print cell `later`, waiting on the software interpreter. Each a
throwaway program whose result goes into the stages below.

**Stage 1 — the share target's declaration and delivery.** The schema's
`share_target`, the bake's checks, the token table, `sharedFiles`, the
`share:` drive form, and the claim path from a pending share on the four
hosts the drive names. Drive: Fieldnotes' `/share` route on the web, macOS, iOS and Linux
headless by `type <root> "share:?text=…&files=…"`, and `--url` cold;
`cargo test` on the token, the claim, and a cold share whose first frame
shows its text with its files `pending`.

**Stage 2 — the Apple share extension.** `host/apple/extensions.mjs`, the
extension, the inbox, and the claim at launch, at foreground and on the
ping. Drive: the extension's XCTest with a stub context writing an
inbox; Fieldnotes on an iOS simulator and macOS claiming it, cold and
warm; sharing from Safari and Photos on the simulator by hand; size and
boot time recorded. `--tvos --no-install` builds without the extension.

**Stage 3 — Android and the web.** The derived filters, `singleTask`,
`onNewIntent`, the copy. Drive: `adb shell am start -a … SEND` with text,
and with a pushed file, to Fieldnotes on an emulator, cold and warm; the
web manifest's `share_target` in an installed Chromium by hand.

**Stage 4 — the in-app browser.** The package, its cells, and the
embedder's decision (D22 item 7). Drive: Excord under the agent on iOS
(`tap` an embed, `tap @t dismissed`) and Android (`tap @t opened`), and
on macOS and the web, where `overApp` is false and the embed follows its link; the sample
host's session refusing a URL outside its list (`smoke.mjs host`); by
hand on an iOS simulator (Done answers `dismissed`) and an Android
emulator with Chrome; `androidx.browser`'s size recorded. Windows's
cell comes with stage 6.

**Stage 5 — compose.** The package, the file provider, `queries` with a
scheme. Drive: the Calendar example under the agent on iOS, macOS, the
web and Android (its Android crate); on an iOS simulator by hand (it has
no Mail account, so the `mailto:` path, and Messages's composer);
`share(files=)` with a file on the Android emulator.

**Stage 6 — the painted hosts.** The Rust implementation slot (D22 item
4), proved by the out-of-tree fixture on Linux headless; Windows's
browser and compose cells. Drive: `agent.mjs windows --app excord` and
the compose fixture on the NucBox, with which mail clients register for
Simple MAPI recorded.

**Stage 7 — print.** The schema's `page` values, the kernel's
`print_layout` and the cut over pages, the package and its cells,
Windows's and Linux's on stage 6's slot. Drive: the oracle's fixed-line
fixtures (Chrome's `printToPDF` against the kernel on Linux headless); a
web fixture whose print element inherits its type and its colour from an
ancestor, printed from a dark screen, whose pages show that type in the
light scheme's ink; a two-column box taller than a page, clipped and
journaled; Fieldnotes' long note under the agent (`screenshot @t pages.png`) on the
web, macOS, iOS, Android, Windows and Linux headless, checked as D20
says; printing to PDF by hand from the Mac's panel, the iOS simulator's
preview, Android's Save as PDF and Microsoft Print to PDF on the NucBox,
the pages checked against the agent's.

**Stage 8 — the share target on Windows,** after LLP 1115.004 S3: the
package manifest's `uap:ShareTarget`, the activation, the copy. Drive:
sharing text and a file to Fieldnotes from Edge on the NucBox by hand,
and the agent's `share:` form there.
