## Summary

The publisher, the store, and the macOS/Linux clients all exist and the
signature seam is real: a head `scripts/deploy.mjs` signed in Node is
verified byte-for-byte in `update/tests/publisher.rs`, and the store
lane's origin drive (fresh install current, seq 1 stages, digest/seq/
cohort/key/channel refusals, two-crash demote, `deliveryActivate` with
carry) ran on both hosts. What the review found is not that the landing
is a sketch. It is that four structural properties the RFCs paid for —
an immutable snapshot, whole-or-absent on the origin, an anti-rollback
floor the binary itself knows, and a transactional bundle generation
across embedded sessions — are not what the code does, and that each of
those is a choice about ownership or layout, not a missed `if`.

Straightforward defects are filesystem issues dated 2026-09-04. This
document is the four structural mismatches, the RFC sentences they
disagree with, and which side should move.

The working set was 15 of 15. Joining it archives the overlay link
for `1032-javascript-in-wasm-measured.research.md` (measured, cited by
1029; the file stays in `llp/`).

## 1. What is actually solid

- **Canonical bytes.** Node `JSON.stringify(sortKeysDeep(rest))` and
  Rust `canonical_bytes` agree on the publisher fixture (sorted ASCII
  keys, no whitespace, signature stripped, integers). The leftover
  seam is U+2028/U+2029 in a sunset message, not a production envelope.
- **Fail-closed on the wire.** Wrong app, cohort, channel, seq below
  the *selected* floor, unsigned when keys are present, digest/length
  mismatch, unsafe asset names, non-http(s) URLs. Crash recovery as
  tested — two failed boots, last good, then entry zero, demoted
  digest not restaged — matches 1026 D11.
- **Selection is a stat and a read.** The check is off the boot path.
  Entry zero is never in the store. A frozen unknown codec writes
  nothing. Apple and Linux share `exact_update::Client`.
- **Path containment** on `serve.mjs` holds (`..`, NUL, symlink, `.lock`
  unserved). `DirectoryOrigin.path` has lexical containment but follows
  symlinked components; that is ticketed. No private key is in the tree.
  The deploy smoke's throwaway key is temp-dir `keygen` plus a public-half
  swap, restored in `finally`.
- **The web host does not pretend.** No store, no check, no activate.
  Caltrain's banner is `when delivery.staged`; the web answer never
  stages. Bake still writes `L = A` for web (`compat.rs` default when
  `deploy.store.web` is unsaid) — QUEUE already names that lie.

## 2. Two layouts on the origin, the client follows one

1030.000 D3 item 5 paid for content-addressed blobs (`Cache-Control:
immutable`) and a `no-store` head, so a client mid-publish sees the
old head whose files are all present, or the new one — "nothing was
replaced." D7 also keeps `app.plan` and `assets/<name>` beside the
head. The publisher does both: it writes `.exact/blobs/<sha256>` and
reads them back, then signs a head whose cards are `url: "./app.plan"`
and `url: "./assets/" + name`, and overwrites those paths *before*
`putHead`.

The store's identity for a file is `resolve_url(head_url, card.url)`
plus digest. It never requests `.exact/blobs/`. Until the signed URL
is the blob, blobs-first does not give whole-or-absent. A crash
between the stream puts and the head swap leaves the previous head
standing with its payload replaced; the blobs still hold the old
bytes and nothing points at them.

Ticket: `issues/20260904-stream-files-overwritten-before-head.md`.

The document change, if we keep named copies for humans, is to say
so: the cards are blob URLs; `./app.plan` is a convenience written
*after* the head, or not at all. The other honest layout is an atomic
swap of a seq-unique stream directory. Mixing the two, with the
client on the mutable half, is how D3 item 5 became a comment.

Related, and a document correction rather than a ticket: 1030 D3a and
1030.000 D2 write the head at `U/.exact/<compatibilityId>/exact.json`.
Landed code, D7, and `store::head_url` use
`U/.exact/<channel>/<compatibilityId>/exact.json`. Publisher and
client agree with each other. The RFCs should absorb the channel
segment; the code should not move.

## 3. The anti-rollback floor is not a baked fact

1026 D11: the client refuses a bundle whose `seq` is below the
selected one's. `Embedded::seq` is "the seq of the bundle the binary
embeds: the anti-rollback floor for a client that has taken no
update." `Baked::from_compat` hardcodes 0. `compat.json` has no seq
field. `record.seq` is written on `Current` and never consulted as a
floor. Store tests pass a non-zero `EMBEEDED_SEQ` into `Store::open`
directly and never drive the production `Baked` path against a lower
published seq.

A binary that keeps its stream (1030 D9, a painter-only host fix)
cannot state "I already am seq 41." Reconstructing the floor from the
origin after the first check is the window: entry zero, floor 0, any
historically signed head is admissible, including an older plan.

Ticket: `issues/20260904-baked-seq-always-zero.md`.

The document change is to put the embedded stream seq next to the
compatibility id in `compat.json` — policy-adjacent identity, like
the channel, not in the id itself (a new binary of the same cohort
can ship a higher floor without moving the stream). The binary
pipeline 1030.000 §6 deferred is what would have given bake a seq to
write; without it, `exact deploy` and `build.mjs` do not share a
release, and the floor stays 0. That is why this is not only "set the
field": the producer of the binary does not yet know the seq of the
bundle it embeds.

## 4. The snapshot is a git status of the app dir

1030.000 D3 item 1: deploy from an immutable source snapshot — a
commit or tree — into a run-specific staging directory, never from
the editor's mutable working state and never from the dev server's
shared `dist/`. The bake output does go to `target/deploy/<release>/web`.
The *source* is the live workspace. `snapshotOf` records `HEAD` of
`app.dir` and `git status --porcelain -- .` there. Uncommitted
changes under `kernel/`, `host/`, `runner/`, `glue.js` bake into a
release labeled as that HEAD. `--snapshot` only checks a prefix of
HEAD; it does not materialize the sha.

Ticket: `issues/20260904-deploy-snapshot-is-working-tree.md`.

Two honest options, and they are a decision, not a missed `git archive`:

- **Status the tree bake actually reads** (the cargo workspace, plus
  exact2 when the app is outside). `--dirty` names that tree. Cheap.
  Still racy between status and bake.
- **Extract the commit** into the run directory and bake that. Matches
  the RFC letter. Costs a worktree or `git archive` of two repos when
  the app is Weird Castle.

The RFC should pick one. The current behavior is neither.

## 5. One app-owned resolver cannot represent N pinned generations

LLP 1031 deliberately has both an app owner and session owners. D1 gives
`ExactApp` one update store and one asset resolver. D11 says a candidate is
applied to every attached session “each transactionally, each pinning the
generation it kept.” Those statements conflict as soon as one of two sessions
accepts a plan and the other refuses it: there are two running generations,
but only one app-level asset namespace, selected store entry, delivery status,
and first-pixel/crash identity.

The landing exposes the conflict before the two-session case. `Store::activate`
promotes and persists pending, then marks it running, before the host has
decoded the plan. Linux installs overrides and only then calls `reload`; Apple
commits in Rust, installs the selected entry's assets into a global insert-only
map, then calls `apply` on sessions sequentially. A refusal leaves committed
store and asset state ahead of at least one runner. Removed assets also survive
because neither override map is replaced as a generation.

Ticket: `issues/20260904-bundle-activation-commits-before-host-accepts.md`.
The Linux cold-start and Apple ABI leaf defects remain separately ticketed.

There are two coherent designs:

- **App-wide two-phase activation.** Prepare the candidate plan and its
  generation-scoped resolver for every attached session without changing any
  visible runner, store record, or shared resolver. If all prepare, swap all
  sessions and the app selection as one main-thread commit; if any refuse,
  discard every candidate. New sessions during preparation either join the
  transaction or wait. This is the smaller v1 model and amends D11's
  per-session pinning sentence.
- **Real per-session pinning.** A session owns its running entry and an asset
  resolver pinned to that entry; the app store owns downloaded candidates and
  a default selection only. Status, crash accounting, first-pixel blessing,
  garbage collection, and newly made sessions all name a generation. This
  preserves D11 but materially changes D1 and the store record.

“Apply sequentially and let each keep what it kept” is not a third design while
assets and store state stay app-global. Refusing live activation whenever more
than one session exists would be honest but would make the flagship embedding
fixture incapable of the behavior D11 promises.

Questions that must be resolved before the ticket is implemented:

1. Can a runtime prepare a carried `Runner` and first batch without replacing
   the live one, or does the ABI need an explicit prepare/commit/discard trio?
2. Does first-pixel bless the app-wide transaction once, or each session's
   generation independently? What happens to an unmounted session?
3. Which generation does a session created during activation boot?
4. When may an entry and its digest-addressed assets be collected?

## 7. Confidence

High on §2 and the Linux asset-boot miss: read against the publisher,
the store's `obtain`, Apple `useAssets`, and Linux `select_update`.
High on §3's code path; medium on how often a later binary is
installed against an older origin in v1 (the binary lanes are unbuilt,
so the window is a dev `cargo build` plus a previously published
stream). High on §4's git-status scope; the extract-vs-status decision
is unmade. High on §5's contradictory owners and commit ordering; medium
on which of its two coherent designs should win, which is deliberately left
for the RFC author.
