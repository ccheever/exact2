## Summary

A desktop app built with exact2 cannot start a program. The T3 Code clone
starts six, all from its own Swift: the `t3` server, which it keeps alive
and restarts; `t3 --version`; `tar`, to unpack the server's runtime; the
login shell, to learn the person's `PATH` (three times, for three
callers); `tailscale status --json`; and `ssh`, for configuration, a
remote launch and tunnels. With them come reads and writes under `~/.t3`
and `~/.ssh`, which no grant can name, and an SSH password field whose
value must reach `ssh` without passing through the app's state. That is
3,882 lines of Swift (§13), and the reference app does the same from
Node's `child_process` in Electron's main process.

This RFC proposes one module, `@exact/child-process`, for macOS, Linux and
Windows, with one Rust implementation in the data executor:

- **A child process is a stream resource** (D2). Data code returns
  `spawn(command, args, options)` as a resource's answer, as it returns
  `fetch(url, { exactStream })` for a WebSocket today. Its mapper receives
  `spawn`, ordered `stdout` and `stderr` chunks, and `exit` with the code
  or signal. It writes stdin through the handle it is given, under LLP
  1016.000 D7's rules for a socket's `send`. Releasing the resource sends
  `SIGTERM`, then `SIGKILL` after a grace period. The names are Node's,
  since the web has none (D1).
- **A one-shot run** (D3): `await execFile(file, args, options)` answers
  `{ stdout, stderr, code, signal }`, with a timeout the host keeps.
- **A kept service** (D4): `spawn`'s `exactRestart` and `exactReady`
  options restart the child with backoff while the resource is held and
  report readiness by polling a URL, so restart and readiness need no
  timers in data code.
- **The login shell's environment** (D5): `loginShellEnvironment()`
  answers the variables the app's grants name, captured once per launch.
- **Which programs** (D7): `process.spawn` grant lines name each program:
  a bundled helper, an absolute path, a home or app path, or a name looked
  up on the login shell's `PATH`.

Beside it, two pieces other apps can use:

- **Home paths** (D6): `home:/.t3/userdata` is a path that `fs.read`,
  `fs.write`, `storage.fs` and `process.spawn` take, beside `app:/` and
  `doc:/`, on the same three desktops.
- **A secret field** (D8): `input type="password" secret="ssh.password"`
  keeps what the person types in the secret store, in memory only. It
  never enters Contract state, the journal or the agent's output, and data
  code reads it with `store.get`.

iOS, tvOS, Android and the web answer every name of the module, and every
`home:` path, with `NotSupportedError`, and the module's `available` fact
is false there (§8). The secret field is not desktop-only: it lands on
every host that has a password field.

## 0. What a ruling would decide

§12 lists the questions. The four that change the design are packaging
(Q1: exact2's vocabulary, imported from `@exact/child-process`), which
programs a grant may name (Q2: whether system binaries may be spawned or
only bundled helpers), supervision as `spawn` options rather than an
`app.json` list (Q3), and the secret field's form (Q5).

## 1. What exists, and what the consumer needs

### 1.1 In exact2

- **Nothing starts a program for an app.** Shipped host code launches a
  process in two places only: the Mac host relaunching its own executable
  (`host/apple/Sources/ExactKit/Relaunch.swift:33-38`) and the terminal
  host's `open` or `xdg-open` for `openURL`
  (`host/terminal/src/term/unix.rs:296-308`). `host.macos.resources`
  copies a helper tree into the bundle (`host/apple/assets.mjs:461-516`)
  and LLP 1069.008 D9 signs a helper with a hardened-runtime exception
  (`runtime.allow-jit Helpers/node/bin/node`), but "nothing launches or
  supervises it. A native module can"
  (`issues/20261015-chosen-documents-outlast-the-launch.md:43`).
- **A bidirectional stream exists.** LLP 1016.000 D7 gives TypeScript
  sources a WebSocket whose mapper receives ordered frames and whose handle
  sends, staged with the commit that made them, bounded at 256 operations
  and 1 MiB, refused after release, and listed in `state.streams`. It is
  built on the web JS target and in native TypeScript on Apple and Linux,
  over `ibex2`'s transports (URLSession on Apple, rustls elsewhere,
  `transport/windows_connect.rs` on Windows). A process's stdin and stdout
  are the same shape: ordered bytes each way and an end.
- **Path grants** are `app:/…`, `doc:/…` or an absolute path fixed at bake
  (`PathPrefix::new`, `grants/src/lib.rs:69-93`, mirrored in `ibex2`'s
  `grant.rs`). `~` has no spelling, and a home directory differs per
  person, so `~/.t3` cannot be named. The executor's `fs` was written with
  that case in mind ("the package that cannot read `~/.ssh`",
  `vendor/ibex/crates/ibex2/src/stdlib/fs.rs:9-12`), and the web's
  `storage.fs` refuses every path but `app:/`
  (`host/web/storage-fs.js:21-23`).
- **A password field's value is the app's.** Its value is never agent
  output (`tree` shows `•••`), but "what the app stores (`state.slots`, its
  data module) is the app's own" (`docs/contract-for-agents.md:3879-3884`),
  and the field is bound to state like any text field
  (`apps/unsaid/app.contract:252`; `runner/src/agent.rs:393-396`: "The
  app's own state still holds the value"). LLP 1133 §7 refuses
  "a secret, key or token as a Contract value", and LLP 1018 D5 keeps a
  token below the data seam; neither has a field that types into that
  place.
- **`rules/DEFERRED.md`** has no entry for processes, spawning, shells or
  the home directory: nothing refuses them by name, and nothing admits
  them. Its nearest entries keep ambient WebSocket globals refused
  (`:475-483`) and durable capability grants refused (`:504-511`); this
  RFC adds neither. LLP 1133.000 lists no such module; it mentions
  "desktop-process work" once, as where reveal-in-Finder waits
  (`llp/1133.000-the-roster.rfc.md:110-114`).
- **One executor on three desktops.** `ibex2` runs fetch, WebSocket,
  `fs` and `env` for Apple, Linux and Windows; the executor core is shared
  by Apple and Linux (`host/linux/src/executor.rs:8` compiles
  `host/apple/src/executor_core.rs`), and the Windows host builds on the
  Linux one (`host/windows/Cargo.toml:10`). `env.read <NAME>` parses and
  `ibex2` reads it (`vendor/ibex/crates/ibex2/src/host.rs:633-658`), but no
  data executor exposes it to TypeScript.

## 2. Tier 1

### D1 — The web has no process: Node's `child_process` names, a declared deviation

No browser can start a program, and none will. Following LLP 1133 D1, the
module takes the name its platforms share most widely and says so: Node's
`child_process`, which a TypeScript author who has written a CLI or an
Electron main process already knows
([Node](https://nodejs.org/api/child_process.html)). The names are
`spawn`, `execFile`, and the options `cwd`, `env`, `stdio`, `encoding`,
`timeout`, `maxBuffer` and `killSignal`; the events are `spawn`, `exit`
and `error`; the child's methods are `write` (Node's `child.stdin.write`),
`end` (`child.stdin.end`) and `kill(signal)`; its fields are `pid`,
`exitCode` and `signalCode`.

The shape is Exact's, as a WebSocket's is: a child is a resource's answer
and its events reach a mapper, not an `EventEmitter`, because a resource's
value is what the mapper returns (LLP 1016.000 D1) and a data module has
no timers or listeners that outlive an answer. These are the deviations,
each declared:

| Node | Here | Why |
|---|---|---|
| `child.stdout.on('data', f)`, `child.on('exit', f)` | one mapper, `exactStream(event, child)` | a child is a stream resource (D2) |
| `spawn` returns the child at once | the child arrives with the `spawn` event | the runner does no I/O; the host spawns after the answer commits |
| `exec(command)` and `shell: true` | refused | a shell line runs any program, which no grant could bound (D7) |
| `fork`, an `ipc` channel, extra `stdio` slots, `detached`, `unref()`, `uid`, `gid` | refused | §11 |
| `stdio: "inherit"` | refused | an app has no terminal to inherit |
| `util.promisify(execFile)` | `execFile` returns a promise | LLP 1133 D6: TypeScript gets the Promise form |
| `child.kill()` on Windows sends no signal | the same, said: `SIGTERM` and `SIGKILL` both terminate | Windows has no signals ([Node](https://nodejs.org/api/child_process.html#subprocesskillsignal)) |

### D2 — A child process is a stream resource

```ts
import { spawn } from "@exact/child-process";

let tail = "";   // the server's last output, for a failure report

export function answer(source: string, args: unknown[], store: Store, storage: Storage) {
  if (source === "server") {
    const [runtime, envelope, env] = args as [string, string, Record<string, string>];
    return spawn(runtime, ["--bootstrap-fd", "0"], {
      env,
      encoding: "utf8",
      exactStream(event, child) {
        if (event.type === "spawn") { child.write(envelope + "\n"); child.end(); }
        if (event.type === "stdout" || event.type === "stderr") tail = (tail + event.data).slice(-65536);
        return { phase: event.type, pid: child.pid, exitCode: child.exitCode };
      },
    });
  }
}
```

- **Lifetime is the resource's.** The host spawns when the answer commits
  and the child lives while the resource is held. New arguments,
  `refresh`, or the resource leaving the plan release it (LLP 1016.000
  D2). A child the app keeps for its whole run is a resource the root
  view reads.
- **Events,** each mapped in order, none coalesced, as a socket's frames
  are (LLP 1016.000 D7):
  - `{type: "spawn", pid}`, once per incarnation (D4 restarts make more);
  - `{type: "stdout" | "stderr", data}`: a chunk as the pipe gave it, at
    most 64 KiB, a string under `encoding: "utf8"` (decoded across chunk
    boundaries), otherwise an `ArrayBuffer`. Chunks are not lines; a
    mapper that needs lines keeps the remainder;
  - `{type: "exit", code, signal}`: one of the two is `null`, as Node's
    `exit` gives them; the stream ends after it unless D4 restarts;
  - `{type: "error", kind, message}`: the program could not be started
    (`NotFound` for `ENOENT`, `Refused` outside the grants, `Unsupported`
    where the module is absent), or the stream failed. It ends the stream.
- **Writing stdin.** `child.write(string | ArrayBuffer | ArrayBufferView)`
  and `child.end()` follow `socket.send` and `socket.close` exactly: the
  mapper may write while it answers `spawn`, `stdout` or `stderr`; a
  mutation, and an answer in flight of the same module, may write on a kept
  handle; bytes are copied at the call, staged with the commit, and sent
  only if it stands; 256 operations and 1 MiB per turn;
  `QuotaExceededError` past that; `InvalidStateError` after `end`, after
  exit or after release. A child spawned with `stdio[0]: "ignore"` has no
  stdin and its `write` refuses.
- **Reading has backpressure.** Unlike a server's frames, a pipe can wait:
  when the stream's receive queue holds 256 chunks or 1 MiB, the host stops
  reading the child's pipes, and the child blocks on its next write until
  the runner catches up. Nothing is dropped and the stream does not fail.
- **Release** (the resource let go, `child.kill`, or app quit): the host
  sends `killSignal` (default `SIGTERM`) to the child's process group,
  then `SIGKILL` after `exactForceKillAfter` milliseconds (default 5000,
  the reference's and the clone's grace; 0 sends `SIGKILL` at once). A
  released child's later output is dropped and its mapper is not called
  again, as a forgotten ticket's messages are dropped
  (`runner/src/runner/commit.rs`). `child.kill(signal)` takes `SIGTERM`,
  `SIGINT`, `SIGHUP`, `SIGQUIT`, `SIGUSR1`, `SIGUSR2` or `SIGKILL` and does
  not release the resource: the mapper sees the `exit`.
- **The options:** `cwd` (a `home:`, `app:` or absolute path; default
  `home:/`; D6), `env` (the child's whole environment, as Node's
  replaces it; omitted, the app's own environment), `stdio` (each of the
  three `"pipe"` or `"ignore"`; default all `"pipe"`), `encoding`
  (`"utf8"` or `"buffer"`, the default), `killSignal`,
  `exactForceKillAfter`, and D4's two.
- **State and journal.** `state.streams` lists each child as it lists a
  socket, with `kind: "process"`, the grant line that admitted it, its pid,
  bytes each way, restarts and its exit. The journal records spawn, exit
  and kill, never arguments or environment values, which may carry tokens.

### D3 — A one-shot run: `execFile`

```ts
import { execFile } from "@exact/child-process";
const { stdout } = await execFile("path:tailscale", ["status", "--json"], { timeout: 1500, encoding: "utf8" });
```

`execFile(file, args, {cwd, env, input, timeout, maxBuffer, encoding,
killSignal})` answers `{stdout, stderr, code, signal}` once the child
exits. It is a step of an answer, as a `fetch` is, so a resource or a
mutation may await it and keep its context (LLP 1133.002 D14).

- **Node's rules:** a non-zero exit, a signal, a timeout or output past
  `maxBuffer` (default 1 MiB, Node's) rejects with an error that carries
  `code`, `signal`, `stdout` and `stderr`; a timeout kills with
  `killSignal`, then `SIGKILL` after 5 s.
- **`input`** (a string or bytes) is written to stdin, which is then
  closed: `execFileSync`'s option, added to the asynchronous form, since
  the clone's remote launch writes a script to `ssh`'s stdin. Without it,
  stdin is empty.
- **The timeout is the host's,** as `fetch`'s `exactTimeout` is: data code
  has no timers (`AbortSignal.timeout()` refuses).

### D4 — A kept service: restart and readiness as `spawn` options

```ts
return spawn(runtime, ["--bootstrap-fd", "0"], {
  env,
  exactRestart: { when: "on-failure", delay: 500, maxDelay: 10000, preventExitStatus: [78] },
  exactReady: { url: `http://127.0.0.1:${port}/.well-known/t3/environment`, interval: 100, timeout: 60000 },
  exactStream(event, child) { … },
});
```

- **`exactRestart`** restarts the child while the resource is held, after
  it exits: `when` is `"on-failure"` (a non-zero code or a signal other
  than one the host sent) or `"always"`; the n-th consecutive restart waits
  min(`delay` × 2ⁿ, `maxDelay`) milliseconds; an exit code in
  `preventExitStatus` ends the stream instead. The names follow systemd's
  `Restart=`, `RestartSec=`, `RestartMaxDelaySec=` and
  `RestartPreventExitStatus=`, in milliseconds; the doubling is the
  clone's and the reference's, where systemd interpolates over
  `RestartSteps=`.
- **Each incarnation** begins with its own `spawn` event, which carries
  `restarts: n`, so the mapper writes the bootstrap envelope again; the
  handle is the same object and its `pid` changes.
- **`exactReady`** polls `GET url` every `interval` milliseconds, each
  probe with a 1 s limit, until a 2xx answer, then emits `{type: "ready"}`
  and resets n. If `timeout` passes first it emits `{type: "ready-timeout"}`
  and starts another round, as the clone does. The URL is admitted by the
  app's `net.fetch` grants, like any fetch; a loopback URL needs
  `net.fetch http://127.0.0.1` or `net.fetch http:`.
- **No timers in data code.** The clone's two loops become two options.
  Choosing the port and writing the envelope stay the app's.

A service lives as long as the resource that answers it, so it needs no
second lifetime: LLP 1016.000 D2 rejected explicit `open` and `close` for
the same reason.

### D5 — The login shell's environment

A GUI app on macOS starts with launchd's short `PATH`
(`/usr/bin:/bin:/usr/sbin:/sbin`), not the one the person's shell builds,
so `tailscale`, `node` or Homebrew's tools are not found. Electron apps read
the login shell's environment for this, as T3 Code does.

```ts
import { loginShellEnvironment } from "@exact/child-process";
const login = await loginShellEnvironment();   // { PATH: "/opt/homebrew/bin:…", SSH_AUTH_SOCK: "…" }
```

- **What it answers:** the variables the app's grants name with
  `env.read login:<NAME>`, one line per name, from the login shell. An
  unnamed variable is absent, even if the shell sets it: a login
  environment carries the person's tokens as often as their `PATH`.
  `env.read <NAME>` keeps its meaning, the app's own environment, which
  `appEnvironment()` answers the same way, so the app can merge the two as
  the clone does.
- **How the host captures it,** once per launch and after first pixel, on
  the first call: `$SHELL -ilc` with a start and an end marker around each
  name (`printenv` between them), stdin `/dev/null`, a new session so the
  shell has no terminal, and a 5 s limit; then `/bin/zsh` if `$SHELL`
  gave no `PATH`; on macOS then `launchctl getenv PATH` with 2 s. The
  clone's algorithm (`T3LocalShellEnvironment.swift:84-130`), moved into
  the host, so the clone's three separate captures become one.
- **The login shell needs no `process.spawn` line.** The host runs the
  person's own shell with a fixed command line; the app chooses neither.
- **Windows** has no login shell: a process started from Explorer already
  has the person's environment. It answers the named variables from the
  app's own environment.
- **Linux** captures as macOS does, without `launchctl`.

### D6 — Home paths: `home:/`

`home:/` names the person's home directory, as `app:/` names the app's
storage: `fs.read home:/.ssh`, `fs.write home:/.t3/userdata`,
`process.spawn home:/.t3/runtime/versions`. `storage.fs` takes `home:`
paths wherever it takes `app:` paths, and `spawn` takes them for `cwd` and
the program.

- **The home directory** is `getpwuid(getuid())->pw_dir` on macOS and
  Linux (not `$HOME`, which a launcher may set) and the profile known
  folder (`FOLDERID_Profile`) on Windows.
- **Coverage is by whole names after realization,** as for any path grant
  (`GrantSet::realized_fs`): a symlink under a granted prefix that leads
  outside it is outside it. `fs.read home:/.ssh` covers
  `home:/.ssh/config` and not `home:/.ssh2`.
- **`home:/` alone is refused** (`home-grant-whole`). LLP 1069.010
  rejected "absolute paths and grants widened to `/`" because "the grant
  would stop meaning anything"; a line naming the whole home directory is
  that grant for the person's files. A line names a subtree:
  `home:/.ssh`, `home:/.t3`, `home:/Applications`.
- **Why `home:` and not that rejection's other half.** LLP 1069.010 also
  noted that such grants work "unsandboxed on the Mac and nowhere else".
  That is this module's target set: `home:` is declared on macOS, Linux and
  Windows and absent everywhere else (below), and a chosen document stays a
  `doc:` handle on every target.
- **`cwd` needs no line.** A child's working directory is any `home:`,
  `app:` or absolute path: the grant bounds the data code's own reads and
  writes, and a child reads what its program reads.
- **Absent:** iOS, tvOS, Android and the web have no home directory an app
  may read. A grant line with `home:` builds there and its operations
  refuse with `NotSupportedError`. A sandboxed macOS build (none today
  but widgets, `host/apple/widgets.mjs`) refuses the line at bake: the
  sandbox's container is not the person's home.

### D7 — Which programs: `process.spawn` lines

Every program a child runs is named by a grant line, `process.spawn
<target>`, one target per line. The target is one of:

| Target | Example | Resolves to |
|---|---|---|
| a bundled helper, as LLP 1069.008 D9 names one | `Helpers/t3/bin/t3` | that file under the bundle's `Contents/` on macOS; Linux and Windows bundle no helpers today (only `host.macos.resources` exists), so there the line is refused at bake until they do |
| an absolute path | `/usr/bin/ssh`, `/usr/bin/tar` | that file |
| a home or app path, a file or a directory | `home:/.t3/runtime/versions` | any executable at or under it, by whole names |
| a name on the login `PATH` | `path:ssh`, `path:tailscale` | the first executable of that name on D5's `PATH` at the moment of the spawn, as Node resolves `spawn("ssh")` |

- **The program in a `spawn` call** is written as its line's target is
  (`spawn("path:ssh", …)`, `spawn("home:/.t3/runtime/versions/1.2.0/t3",
  …)`), so the call and the grant read alike.
- **Arguments are free.** A grant names a program, not what it is told.
  A line naming a shell or an interpreter (`path:sh`, `path:node`,
  `/bin/zsh`) therefore admits any program, and the reach table says so,
  as it says a scheme-wide `net.fetch`.
- **Why system binaries are allowed** (Q2). The consumer's programs are a
  bundled server it unpacks into `~/.t3`, the system's `ssh` and `tar`,
  and `tailscale` wherever the person installed it. With bundled helpers
  only, the module would not serve its consumer, and an app that wants
  `ssh` would bundle its own copy, which is worse for the person: it is
  not the `ssh` their configuration and agent are written for. A desktop
  app outside the Mac App Store may already run any program from native
  code (LLP 1069.008: native modules are "declared, not enforced"); the
  grant makes the data code's programs declared, enforced and visible.
- **What the line derives:** nothing in a manifest on macOS, Linux or
  Windows; a hardened-runtime child needs no entitlement to be spawned.
  A sandboxed macOS build refuses every `process.spawn` line, since a
  sandboxed app's child inherits its sandbox and could not read `~/.ssh`.
  A `process.spawn` or `home:` line changes the grant ceiling, so the
  deploy classifier calls for a binary release, as a `runtime.*` line does.

### D8 — A secret field: `input type="password" secret=`

```
input type="password" secret="ssh.password" autocomplete="current-password" submit=answer("submit")
```

- **Where the value lives.** Each edit goes to the secret store's name
  `ssh.password`, held in memory and never persisted: not in Contract
  state, the store's slots, the journal, `carry`, the agent's `state`, or
  a crash report. The app's grants need `secret.hold ssh.password`, a
  sibling of `secret.keep` for a value kept only until the app exits or
  forgets it.
- **What Contract sees.** The field fires `input`, `change` and `submit`
  as any text field does; the event's `value` is `""` and it carries
  `length`, so the app can enable Continue when something is typed. `bind=`
  and `value=` are refused beside `secret=` (`secret-field-bound`): there
  is no Contract value to bind.
- **What data code does.** A mutation the submit runs reads
  `store.get("ssh.password")` and passes it on (to the child's environment
  for `SSH_ASKPASS`, to stdin, to a `fetch` body) and calls
  `store.forget("ssh.password")`, which also empties the field. `store.set`
  on a held name replaces the field's text, which is how the app clears it
  after a failed attempt.
- **The agent** types into it as into any password field (`type
  ssh-password-field "…"`); `tree` shows `•••` and `state.secrets` shows
  `ssh.password: held, 9 characters`, never the text.
- **Every host with a password field implements it:** web, macOS, iOS,
  Linux, and Android and Windows as their text fields arrive. On the web
  the page's glue holds the text, and the data module's `store.get` reads
  it from there, so it never enters the runtime's store.
- **Askpass, fully below data code,** is left out (§11): a host-supplied
  `SSH_ASKPASS` helper that reads a held secret over a pipe would keep the
  password out of the child's environment too. The reference and the clone
  both pass it in the environment, which other processes of the same user
  can read (`ps -E` on macOS, `/proc/<pid>/environ` on Linux); D8 keeps
  the clone's behaviour and moves the field out of app Swift.

### D9 — Unsaid defaults are the platform's

| Default | Value | Source |
|---|---|---|
| A child's process group | its own (`setpgid(0, 0)`, Rust's `CommandExt::process_group(0)`), so a signal to the group reaches what the child starts; the login shell of D5 gets a new session (`setsid`) so that it has no controlling terminal | POSIX [`setpgid`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/setpgid.html); the clone's login shell uses `POSIX_SPAWN_SETSID` |
| A child's console on Windows | none (`CREATE_NO_WINDOW`) | a GUI app's child flashes no console window |
| Children at app quit | every child released as in D2, the quit waiting at most 5 s | macOS `applicationShouldTerminate`; the clone waits 5.5 s |
| Children after a crash | Linux: `PR_SET_PDEATHSIG(SIGKILL)`; Windows: a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; macOS has neither, so the host records each child's pid and start time in app storage and reaps a leftover at the next launch, checking both, as the clone's pid file does | `prctl(2)`, job objects |
| File descriptors | only stdin, stdout and stderr are inherited (Apple's `POSIX_SPAWN_CLOEXEC_DEFAULT`; on Linux, every other descriptor closed in the child before `exec`; on Windows, an explicit handle list, `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`) | the app's sockets and files, some opened by libraries without close-on-exec, stay its own |
| Signals | the child starts with default dispositions and an empty mask (`POSIX_SPAWN_SETSIGDEF`, `SETSIGMASK`) | the app's own handlers do not leak |
| `cwd` | `home:/` | a Terminal starts there; the app's bundle is read-only |

## 4. Packaging and callers

### D12 — exact2's vocabulary, imported from `@exact/child-process`

LLP 1133 D5's default is a host extension. This module is exact2's
vocabulary, a data capability like `fetch`, for three reasons:

1. **The stream is the executor's.** A child's ordered output with stdin
   writes staged per commit is LLP 1016.000 D7's machinery, which lives in
   the runner and `ibex2`'s executor. An extension answers through the
   native slot, which has no ordered events (LLP 1124 §5 refuses value
   streams; LLP 1133 D6 rule 7).
2. **One Rust implementation for three hosts.** `ibex2` is already the
   executor on macOS, Linux and Windows, with grants parsed and checked in
   one place (`grant.rs`). Linux and Windows have no module slot an
   extension could load into.
3. **The secret stays below the data seam** (LLP 1018 D5). An extension's
   arguments are Contract values; a child's environment holding a password
   must not be one.

The names are still imported (LLP 1133 D6; LLP 1133.001 D8): the package
`@exact/child-process` holds an interface declaration whose implementation
on `macos`, `linux` and `windows` is the executor, and none elsewhere.
The bake's binding table names implementations for Apple, Android and the
web only (`js/bake/src/typescript.mjs:968-1002`); stage 0 adds the
executor as the implementation on `macos`, `linux` and `windows`. So the
bake finds module use the way it finds geolocation's, refuses a call
without its grant (`grant-missing`), types the binding, links the
transport only into apps that import it (LLP 1047.001), and binds the
absent answer on every other target. A Contract app reaches a child only
through the resource its data code answers; the module has no Contract
names, as `fetch` has none.

### D13 — Callers

| Name | Caller | Request (LLP 1069.007 D1)? | `sync`? |
|---|---|---|---|
| `spawn` | a resource's answer (a stream) | no: it opens no system UI | no |
| `execFile` | any answer's step | no | no |
| `loginShellEnvironment`, `appEnvironment` | any answer's step | no | no |
| `available` | a fact, on every target | no | yes, where the host has `call` |
| `secret=` | a Contract attribute | no | — |

A tool invocation (LLP 1111) may run any of them: none opens a prompt, so
LLP 1133 D6 rule 3's `person-required` does not apply. Every call carries
its origin to the journal.

**Rust sources** get the same three as typed requests in
`exact_data`, as `fetch` has them: `execFile` and the environment reads
answer once; `spawn`'s stream is receive-only for a Rust source until Rust
sources get D7's send path, a gap shared with WebSockets
(`docs/reference.md`, "Remaining host gap").

## 5. The ceiling test

Common uses of a child process in desktop apps, by Node's API and the
platforms' (`Process`, `posix_spawn`, `CreateProcessW`), and the tier that
reaches each:

| Use | Tier |
|---|---|
| start a program with arguments, environment, cwd | 1 (`spawn`, `execFile`) |
| stream its output; write its input; close input | 1 |
| exit code, terminating signal | 1 |
| stop it gracefully, then forcibly | 1 (release, `kill`) |
| a timeout, an output limit | 1 (`execFile`) |
| keep a service alive with backoff; wait until it serves | 1 (D4) |
| find a program on the person's `PATH` | 1 (`path:`) |
| the login shell's environment | 1 (D5) |
| a child's priority or QoS | 2 (D10) |
| a new console process group on Windows | 2 (D10) |
| a pseudo-terminal (`node-pty`, `forkpty`) | out: the terminal module's (B5) |
| a shell command line (`exec`, `shell: true`) | out: D7 |
| an IPC channel, extra pipes (`fork`, `stdio[3]`) | out until a consumer asks |
| a daemon that outlives the app (`detached`, `unref`) | out: a login item's (LLP 1133.000 §3.11) |
| another user's identity (`uid`, `gid`, `sudo`) | out |
| resource usage, `wait4` accounting | out until a consumer asks |
| elevate on Windows (`runas`) | out |

Out on purpose: the last seven, each with its reason. No use the consumer
needs is outside tiers 1 and 2.

## 6. Permission and grant

There is no platform prompt to start a program on any desktop: the grant
is the whole permission (LLP 1069.008 D8, Linux's rule, holds on all
three). The module's permission state is therefore `granted` where the
module is available and the line is present, and an ungranted call fails
`Refused` naming the line it needed. Grant lines:

| Line | Admits |
|---|---|
| `process.spawn <target>` | starting that program (D7) |
| `fs.read home:/…`, `fs.write home:/…` | `storage.fs` under that home path, never the whole home directory (D6) |
| `env.read login:<NAME>` | one variable of the login shell's environment (D5) |
| `secret.hold <name>` | a field's held secret and `store.get`/`forget` of it (D8) |

The reach table lists every line; a production build's `exact release`
prints the `process.spawn` targets beside the hardened-runtime ones.

What a child does is still subject to the platform's own permissions, and
they are the app's: macOS attributes a child's access to a protected
location (Desktop, Documents, a removable volume) to the app that started
it, its responsible process, so the system's prompt names the app and the
grant the person gives is the app's. The module adds nothing to that
prompt and answers none of it (LLP 1133.002 D12).

## 7. The substitute

- **A real child under the agent by default.** A drive runs the program,
  as it opens a real socket: LLP 1069.007 D6 classes SSE and WebSocket as
  "network, not device", answered by "a local server the smoke starts",
  and a child is the same kind of thing. An agent driving a desktop app
  with a local server needs that server. `clock settle` does not wait on a child after
  its `spawn` event, as it does not wait on an open stream after its first
  message (LLP 1016.000 D5).
- **A substitute program per target:** `--process <target>=<file>` on the
  agent driver (`agent.mjs macos --process path:ssh=fixtures/fake-ssh …`)
  runs that executable instead, with the same arguments, environment and
  pipes; `state.processes` says which ran. This replaces the clone's
  `T3_SSH_COMMAND` and `T3_EDITOR_PATH` doubles with one framework form.
- **`loginShellEnvironment`** under the agent answers the drive's
  `--login-env NAME=value` lines, or the app's own environment for the
  named variables when none is given, so a drive never runs the person's
  shell.
- **`home:`** under the agent is a scratch directory the drive names
  (`--home <dir>`), empty by default, so a drive never reads the person's
  `~/.ssh`. This replaces `T3_SSH_HOME` and `T3_LOCAL_HOME`.
- **A production bake** reaches none of it.

## 9. Security

- **What a grant bounds:** which programs data code starts, and which home
  paths it reads and writes. It does not bound arguments (D7) or what the
  program does: a granted `ssh` connects anywhere the person's
  configuration lets it.
- **Who can call:** only the app's own data code. A reply from a server
  (a `fetch` answer, a socket frame) can reach `spawn` only through the
  app's code, which chooses the program from its granted lines.
- **What never leaves the executor:** environment values and arguments are
  not journalled (D2); a held secret is never in state (D8).
- **Distribution:** a Mac App Store build is sandboxed and refuses every
  line of this module at bake (D6, D7). Developer ID builds, the only kind
  exact2 ships for macOS today, are not sandboxed.

## 10. Building it

Each stage lands with its drive.

- **Stage 0, the seam:** the grant grammar (`process.spawn`, `home:`,
  `env.read login:`, `secret.hold`) in both grammars; the package's
  declaration; the bake's use discovery, binding and `grant-missing`; the
  absent answer on every other target; the agent's substitute forms (§7).
- **Stage 1, macOS and Linux:** `ibex2`'s process transport (spawn,
  pipes with backpressure, the process group, release, the pid record on
  macOS, `PR_SET_PDEATHSIG` on Linux); `spawn`'s stream through D7's
  machinery in native TypeScript; `execFile`; D4's restart and readiness;
  D5's capture; `home:` in `storage.fs`. Drive: a fixture app under
  `apps/` or the tests' fixtures that spawns a helper echo program, writes
  its stdin, restarts it, and reads `home:`, on macOS and the Linux host.
- **Stage 2, the secret field:** `secret=` on web, macOS, iOS and Linux;
  `secret.hold`; `state.secrets`. Drive: a fixture form on each.
- **Stage 3, Windows:** the same Rust over `CreateProcessW` and a job
  object, checked by tier 2's cross-target `cargo check` on this Mac and
  driven on a Windows machine before it is claimed (LLP 1027.006 qualifies
  native TypeScript there first).
- **The consumer** (after stage 2, an app PR): the clone's tasks C2
  (`ssh-in-ts`) and C3 (`local-server-logic-in-ts`, which also waits on
  B9's local listener for the `t3 app` socket and port choice).

## 12. Questions for the ruling

1. **Packaging** (D12). (a) exact2's vocabulary, a data capability in the
   executor, with names imported from `@exact/child-process`
   (recommended). (b) A host extension with a Rust implementation: it
   would need ordered events and a secret-carrying argument the extension
   seam does not have, and a module slot on Linux and Windows. (c) The
   names imported from `node:child_process`: more familiar, but it
   promises Node's `EventEmitter` and streams, which an author would write
   and the bake would have to refuse.
2. **Which programs** (D7). (a) Bundled helpers only: the consumer cannot
   use it (its server lives in `~/.t3`, and it needs the system's `ssh`).
   (b) Helpers and absolute paths. (c) (b) plus `home:` and `app:` paths
   and names on the login `PATH`, one line per program (recommended): what
   the consumer runs, each line in the reach table.
3. **Supervision** (D4). (a) `spawn` options, the service living with its
   resource (recommended). (b) An `app.json` `services` list the host
   starts at launch: a second lifetime, started before the app's code can
   choose a port or write an envelope.
4. **The login environment** (D5). (a) Named variables only, `env.read
   login:<NAME>` (recommended). (b) The whole environment under one line.
5. **The secret field** (D8). (a) `input type="password" secret=<name>`
   with `secret.hold` (recommended). (b) The field's value travels with
   its `submit` event to a mutation as a redacted argument: no new store
   name, but a value class Contract does not have. (c) No field: the value
   stays in state, as the reference keeps it in React state.
6. **Scope of this ruling:** stages 0 to 2 on macOS, Linux, and (for the
   field) web and iOS; Windows in stage 3 when it can be driven.
   Recommended: yes.
7. **The `rules/DEFERRED.md` record.** Nothing refuses processes by name,
   so this admits a capability rather than reversing a refusal. No take is
   offered; this asks for a waiver (`rules/RULES.md`, Scope). Proposed
   text: "**Admitted** (<ruler>, <date>, waived; LLP 1133.005): desktop
   processes (`spawn`, `execFile`, supervision, the login environment),
   `home:` paths and a password field's held secret, on macOS, Linux and
   Windows; absent elsewhere. Consumer: the T3 Code clone's local server
   and SSH environments. Still refused: a pseudo-terminal, shell command
   lines, daemons that outlive the app, and processes on iOS, Android and
   the web."

## 14. Cost

An app that does not import the module links none of it: the process
transport is a module of `ibex2` reached only from the binding (LLP
1047.001), and no grant line derives anything. An app that does adds the
transport's code (an estimate before stage 1: 1,000 to 1,500 lines of Rust
shared by three hosts, 100 to 200 per host for quit and crash handling)
and nothing before first pixel: the login shell is captured on the first
call, after first pixel. Stage 1 measures the binary cost with LLP 1047's
probe and records it here.
