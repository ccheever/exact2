# LLP 1048.006: The reader's viewport — a served page laid out for the screen it is read on

**Type:** RFC
**Status:** Accepted, built (2026-10-02). Charlie asked for it on 2026-10-02: the render host laid every page out for an assumed 390×844, so a layout that reads `exactViewport` could shift on a desktop when the runtime took over.

**Author:** Claude (Opus 5.5) for Charlie Cheever

**Date:** 2026-10-02

## Summary

A served page whose plan reads `exactViewport()` is now rendered at the reader's viewport, as near as the request tells:
1. the browser's client hints, `Sec-CH-Viewport-Width` and `Sec-CH-Viewport-Height`, and the preference hints `Sec-CH-Prefers-Color-Scheme`, `-Reduced-Motion` and `-Reduced-Transparency`, which every such page asks for with `Accept-CH`;
2. else the class its user agent names: a desktop browser (`Sec-CH-UA-Mobile: ?0`, which Chromium sends unasked, or a desktop `User-Agent`) is laid out at 1280×800; a phone, or a client that says nothing, at the manifest's `pageViewport` (390×844 unless declared), as before.

A page the server keeps (`render=cached`) is kept per **viewport class**, not per width. The classes come from the plan itself: two viewports are one class when every comparison the plan makes on each fact it reads gives the same answer for both. The grid's `viewport.width <= 700` makes two classes, so one kept page serves every phone and another serves every desktop. A plan that reads no viewport fact renders, keeps and answers exactly as before: no hints asked for, no `Vary`, one kept page.

## 1. The decisions

**D1 — Only plans that read the viewport.** At server start the host walks every code body of the plan (`Plan::each_code`, the VM's own decoder) for `LoadResource` of an `exactViewport` resource. A plan with none renders at `pageViewport` as LLP 1048.000 D4 says, and its responses carry nothing new. RealWorld and the feed are such plans.

**D2 — The viewport a request is rendered at.** In order:
- **Width and height:** `Sec-CH-Viewport-Width` (or the older `Viewport-Width`) and `Sec-CH-Viewport-Height`, CSS pixels, accepted between 100 and 10,000. Without them, the class the user agent names: `Sec-CH-UA-Mobile: ?0`, or a `User-Agent` that starts with `Mozilla/` and names no phone (`Mobi`, `Android`, `iPhone`, `iPod`), is a desktop, laid out at **1280×800** (a common laptop window: wider than any phone or tablet breakpoint, narrower than most desktops). Anything else, a client that says nothing included (a crawler, `curl`), gets `pageViewport`, mobile-first, as before. A width without a height takes its class's height.
- **Preferences:** `Sec-CH-Prefers-Color-Scheme: "dark"`, `Sec-CH-Prefers-Reduced-Motion: "reduce"` and `Sec-CH-Prefers-Reduced-Transparency: "reduce"` set those facts; without them, no preference, as before. `prefersContrast` has no client hint and stays `no-preference`.
- **Not DPR.** `exactViewport` holds no device pixel ratio, so nothing asks for `Sec-CH-DPR`.

**D3 — What a page asks for and varies by.** Every page response of such a plan, buffered or flushed, carries:
- `Accept-CH:` the hints for the facts the plan reads (the grid: `Sec-CH-Viewport-Width` alone), so a Chromium browser sends them from its next request to the origin on;
- `Vary:` those hints, plus `Sec-CH-UA-Mobile` and `User-Agent` when the size is read, because the fallback chose by them. A shared cache that keys on all of them keeps a copy per user agent; one in front of this server should key on the hints instead, or not keep these pages.

They go beside the CSP and the `Permissions-Policy`, from one string made at server start; the CSP and the head are unchanged.

**No `Critical-CH`.** `Critical-CH` would make a Chromium browser that has never seen the origin retry its first navigation with the hints, which costs that reader a round trip (150 ms on the mobile profile) before anything is drawn. The user-agent class of D2 already puts a first-visit desktop on the desktop side of any breakpoint between the widest phone and 1280 px, and a phone on the phone side, so the retry would buy the exact width only for layouts that break between 1280 px and the real window. A later navigation carries the exact width anyway.

**D4 — Kept per class.** For each fact the plan reads, the walk of D1 records how it is read:
- **compared with a constant**: `LoadResource`, `Field`, a constant (`Number`, `Str`, `Bool`), then a comparison (`Lt`, `Le`, `Gt`, `Ge`, `Eq`, `Ne`), or the constant first and the comparison mirrored. None of these instructions may be a jump's target, so the compared value is exactly the fact and the constant. A derive that compares (`derive narrow = viewport.width <= 700`) is read this way; everything that then reads `narrow` reads a boolean.
- **any other way**: arithmetic on the width, a field passed to a component, the record itself.

A kept page's key is its target plus its **class**: for a compared fact, the answers of its comparisons in the request's viewport (one bit each); for a fact read another way, its value. Two requests of one class render the same document, because every reading the plan makes of the viewport gives the same answer, so the second is a hit. The cache's bound is unchanged (`MAX_CACHED_PAGES`, `MAX_CACHE_BYTES`). A plan with N distinct comparisons on the width has at most N+1 classes of width; one that reads the width another way is kept per width, still within the bound.

**D5 — What does not change.** Pages made at build (`render=build`) are files, laid out at `pageViewport` (LLP 1048.000 D4). `--compare` and `--build` render at the manifest's viewport. The checkpoint holds no viewport: the runtime answers `exactViewport` from the page it runs in, and now finds the document already laid out for it.

## 2. Measurements

The bench grid (`apps/grid`, exact2-js-opt's contract: `derive narrow = viewport.width <= 700`, then `row … align-items=(narrow ? "stretch" : "flex-start") flex-direction=(narrow ? "column" : "row")`), exact2 at origin/main (f14985fe) against the same commit with this change, side by side on the bench's profiles, medians (2026-10-02, a loaded machine): desktop 15 runs, mobile 9.

| profile | build | FCP | LCP | TTI | CLS (load) | elements restyled at takeover |
|---|---|---|---|---|---|---|
| desktop 1350×940 | main | 188 | 188 | 227 | 0.000 | 1 (the row: column → row, stretch → flex-start) |
| desktop 1350×940 | this | 188 | 188 | 233 | 0.000 | 0 |
| mobile 412×823 | main | 512 | 512 | 1583 | 0.000 | 0 |
| mobile 412×823 | this | 484 | 484 | 1574 | 0.000 | 0 |

"Restyled at takeover": every element under `#exact-root` is compared — box, `flex-direction`, `align-items` — between the page with its script off (what first paint lays out) and the page once the runtime is up (`firstpaint`, a scratch probe). On main a desktop reader's first paint is the phone layout and the runtime restyles the row when it takes over; CLS stays 0 there only because, at load, the row's one child fills it either way (a size change in place is not a layout shift). With the detail panel beside the table, the same restyle would move it. With this change the served document is the runtime's layout, and nothing is restyled.

The desktop request carried no width hint (each run is a fresh profile, a first visit): `Sec-CH-UA-Mobile: ?0` chose the desktop class (D2), on the wide side of 700. The phone profile's emulated Chrome still says `?0`, and its user agent names a phone, which wins (D2), so it got the phone class.

Server CPU per page (both servers driven at once, concurrency 8, the grid's `/`): 71.95 → 72.10 ms with a desktop's headers, 71.25 → 71.15 ms with none (ratio 0.99–1.00). The plan's walk is made once at server start; a request reads at most six headers.

A kept page per class (the test `a_page_is_rendered_for_its_reader_s_viewport_and_kept_per_class`; checked on the grid's render host with a lifetime): widths 1000 and 1440 share one kept page, 600 makes the second.
