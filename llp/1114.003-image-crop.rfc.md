## 1. Summary

Bluesky crops an avatar to a square, a banner to 3:1, and, optionally, a
post's image to any box. Then it compresses the result. Exact2 can compress
(`storage.fs.compressImage`, LLP 1069.002 A1) but not crop, and A1's ruling
keeps cropping out.

This RFC adds one option to `compressImage`: `crop`, a rectangle in the
picked image's upright pixels, named as `DOMRect` names it (`{x, y, width,
height}`). The host draws that rectangle instead of the whole image, then
runs A1's search unchanged. The web does it with `drawImage`'s source
rectangle, Apple with the same ImageIO draw A1 already does. The crop UI is
the app's, written in Contract: a fixed frame with `transformDragFor` for
an avatar's square or a banner's 3:1, or corner handles with `pan` for a
free crop. The agent drives that UI with the operations it already has.

One decode and one lossy encode, not two. No new call, grant, queue,
limit or host UI. It reverses one parenthetical of Charlie's 2026-10-08
ruling, which reopened D6 for compression and kept "cropping" out.

## 2. What Bluesky does

The source says Bluesky has a crop tool when attaching images
(`EditImageDialog.tsx`), square for avatars and 3:1 for banners. Corrected
against social-app `main` at `35fd4fba`:

- **On iOS and Android it is a native crop sheet,** not
  `EditImageDialog`. `EditImageDialog.tsx` returns `null`. Native calls
  `openCropper` (`src/lib/media/picker.tsx`), which is Bluesky's own
  `@bsky.app/expo-image-crop-tool` (a native module; on iOS a
  TOCropViewController-style sheet), with `format: 'jpeg'`.
  - Avatar: `openCropper({imageUri, shape: circular ? 'circle' :
    'rectangle', aspectRatio: 1})`, then `compressIfNeeded(…,
    IMAGE_SIZE_CONFIG_2K_1MB)` (`UserAvatar.tsx:423-430`).
  - Banner: `openCropper({imageUri, aspectRatio: 3 / 1})`, then the same
    compression (`UserBanner.tsx:89-95`).
  - Post images: `cropImage` in `src/state/gallery.ts:115` calls
    `openCropper({imageUri})` with no aspect: a free crop. It is native
    only (`if (!IS_NATIVE) return img`).
- **On the web it is `EditImageDialog.web.tsx`,** a dialog over
  `react-image-crop` with an optional `aspectRatio` and `circularCrop`.
  Save calls `manipulateImage` (`gallery.ts:149`), which crops the
  *original* with `expo-image-manipulator` (a canvas on the web) to a
  **PNG**, in source pixels from the percentage crop. The avatar and banner
  use it with `aspectRatio={1}` and `{3}`; then `compressImage(image,
  IMAGE_SIZE_CONFIG_2K_1MB)` (`UserBanner.tsx:121`).
- **The composer keeps the source and the transformed image apart**
  (`ComposerImage.source` and `.transformed`), so re-editing starts from the
  original.
- **The sizes:** avatar and banner 2000 px and 1,000,000 bytes; posts 4000
  px and 2,000,000 bytes (`src/lib/constants.ts`, `IMAGE_SIZE_CONFIG_2K_1MB`,
  `IMAGE_SIZE_CONFIG_POSTS`).
- **The camera path doesn't crop on iOS.** `openCamera({aspect: [3, 1]})`
  passes an Android-only option (LLP 1114.002 §2).

So Bluesky's own web path is exactly this RFC's shape: the UI in the page,
a rectangle in source pixels, the pixels cut by a canvas. Its one waste is
the PNG in between, which this RFC folds away.

## 3. What exact2 has today

- **`compressImage`** (LLP 1069.002 A1, built 2026-10-08):
  `storage.fs.compressImage(from, to, {maxDimension, maxBytes})`
  (`storage.d.ts:34`). The search is `data/src/image.rs:79`; it works over
  the **oriented** source size. The Apple codec reads the header, then for
  each size draws the oriented thumbnail into an exact `w × h` sRGB bitmap
  on white (`data/src/image/apple.rs:204-296`, `draw` at `:298`). The web
  decodes with `createImageBitmap(blob, {imageOrientation: 'from-image'})`
  (`host/web/storage-image.js:140`) and draws with
  `context.drawImage(bitmap, 0, 0, w, h)` (`:191`) on an `OffscreenCanvas`
  (`:153`). Ibex carries the call as opcode 121 with four values, and the
  embedder's codec is `Fn(&[u8], u32, u64, Instant)`
  (`vendor/ibex/crates/ibex2/src/stdlib/fs_image.rs:24-25`). Linux, Windows
  and Android refuse it `unsupported`.
- **The ruling that keeps cropping out.** LLP 1069.002 §"D6 reopened
  (Charlie, 2026-10-08)": "Everything else D6 rules out (cropping, editing,
  a size limit the host imposes) stays out." D6 itself: "No other
  transforms at pick: no resizing, compression, cropping or size limit …
  Image editing stays out (LLP 1045 §5)." A1.8 lists "Crop, rotate or any
  edit" as not in A1. `rules/DEFERRED.md` says nothing about cropping or
  compression, and LLP 1045 §5 bounds the Markdown editor's design, not the
  platform.
- **The picked size is upright.** `Picked.width` and `height` have the
  orientation applied (LLP 1069.002 D3; `Picker.swift` `pixels`), which is
  the space a crop rectangle must be in.
- **`transformDragFor` exists** (LLP 1057.000; `docs/contract-for-humans.md`
  §direct manipulation). A handle names a target by `id`; the host pans and
  pinches the target natively during the gesture and reports
  `transformgeometry(bw, bh, pw, ph)` and `transformrelease(x, y, scale,
  vx, vy, vscale)`. The photo viewer in `apps/interaction-gallery/app.contract:467-469`
  is the working fixture: a clip box with `overflow="hidden"`, a target
  with `translate` and `scale` bound to state, and an action that clamps
  the pan after release (`photoClamp`, `:4`). The target's shape is strict
  (`docs/agent-pitfalls.md:365`).
- **`pan`** gives `(dx, dy)` since the last event on any node
  (`docs/contract-grammar.md:825`), and `pointerdown`/`pointermove`/`pointerup`
  hand a `PointerEvent`. Either can drive a crop handle. `aspect-ratio` and
  `object-fit` are rows (`kernel/tables/schema.json`).
- **A crop UI as a view module** exists: `apps/photo-editor`
  (`<photo-editor>`, LLP 1024), with crop corners and edges in UIKit, AppKit
  and Pointer Events (`modules/web/index.js:197-211`). It reports the crop
  as text and writes no image.

The source's claim that the crop box can be "authored in Contract with a
transform-drag box, which exact2 already supports" is right for a fixed
frame. A resizable box is written with `pan` on its handles instead (§5 D4).

## 4. What the web does

The web has no "crop this file" API. A page crops with the canvas:

- [`drawImage(image, sx, sy, sw, sh, dx, dy, dw, dh)`](https://html.spec.whatwg.org/multipage/canvas.html#dom-context-2d-drawimage):
  the source rectangle `sx, sy, sw, sh` is drawn into `dx, dy, dw, dh`. A
  source rectangle outside the image is clipped to it, and the destination
  is clipped in proportion.
- [`createImageBitmap(image, sx, sy, sw, sh, options)`](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#dom-createimagebitmap)
  also takes a source rectangle, with `resizeWidth`, `resizeHeight` and
  `imageOrientation`.
- [`OffscreenCanvas.convertToBlob({type, quality})`](https://html.spec.whatwg.org/multipage/canvas.html#dom-offscreencanvas-converttoblob)
  or `HTMLCanvasElement.toBlob` encodes the result.
- The rectangle's names are `DOMRect`'s: `x`, `y`, `width`, `height`
  ([Geometry Interfaces](https://drafts.fxtf.org/geometry/#DOMRect)).

The crop *UI* is the page's own: `react-image-crop` on bluesky.app, a
`<div>` with handles and pointer events. That is the shape this RFC keeps:
UI in the app, pixels cut by the platform.

## 5. Design

### Options

| | (a) a data-module call | (b) a native crop sheet | (c) an app Swift module |
|---|---|---|---|
| the UI | Contract (D4) | the host's sheet | the clone's Swift, AppKit and JS |
| the web | `drawImage` with a source rect, as bluesky.app does | nothing: the web has no crop sheet, so a JS one of exact2's | the clone's page module |
| who it serves | every app | every app | the clone |
| agent | drives the Contract UI; the codec is real under `--storage` | a substitute that answers a rectangle; the sheet itself undriven | the module's props and events only |
| exact2 work | an option on an existing call | a sheet per host, plus a new command and its hold | none |
| rulings | reverses "cropping stays out" | the same, and a host UI the web lacks | none |

- **(a) is recommended,** in the form D1 gives it. It keeps the UI where
  the agent can see and drive it, and where the app can style it (a
  circle mask, a 3:1 frame). The pixel work is A1's, with one rectangle
  more. It is what bluesky.app does on the web.
- **(b) is rejected.** Apple ships no crop sheet for an arbitrary image:
  `UIImagePickerController.allowsEditing` crops only its own pick or capture
  to a fixed square, and PHPicker and AppKit have none. TOCropViewController
  is a third-party library. So (b) means exact2 writing or vendoring a crop
  UI per host, plus one for the web, against "the web is the standard". It
  would also be the one image UI the agent can't drive.
- **(c) is possible today without a ruling,** and `apps/photo-editor` is
  the precedent for the UI. But the clone would write the UI three times
  (UIKit, AppKit, Pointer Events) and the encode twice (ImageIO, canvas),
  duplicating A1's codec, and no other app gains anything. It is the
  fallback if (a) is refused.

### D1 — `crop` is an option on `compressImage`, not a second call

```ts
export interface CompressImageOptions {
  readonly maxDimension: number;
  readonly maxBytes: number;
  /** The part of the image to keep, in its upright pixels (orientation
   * applied, as `Picked.width`/`height` are). Default: the whole image. */
  readonly crop?: { readonly x: number; readonly y: number;
                    readonly width: number; readonly height: number };
}
```

```ts
// An avatar: the square the person framed, at Bluesky's 2000 px and 1 MB.
const out = await storage.fs.compressImage(pick.path, "app:/tmp/upload/avatar.jpg",
  { maxDimension: 2000, maxBytes: 1_000_000, crop: { x: 412, y: 0, width: 3024, height: 3024 } });
```

- **Why an option.** Bluesky always compresses after it crops, and so will
  every upload. As one call the source is decoded once and encoded lossily
  once. As two calls (`cropImage` to a JPEG, then `compressImage`) the
  photo is JPEG-encoded twice; to a PNG, as bluesky.app does, a 12 MP crop
  is a 15–25 MB intermediate file that A1 then reads back under its 64 MiB
  cap. One call also needs no new opcode, queue entry, grant, failure
  table or right to write: A1.5's machinery covers it as it is.
- **The result** is A1's record. `width` and `height` are the encoded
  size, so the app sends Bluesky's `aspectRatio` from them.
- **A Rust source** passes `"crop": {"x", "y", "width", "height"}` in the
  same request (A1.1).

*Rejected:* a standalone `fs.cropImage(from, to, rect)`. It is the
two-call cost above, and it needs a format choice A1 doesn't. An app that
wants a cropped file without a size budget passes `maxDimension: 8192` and
a large `maxBytes`.

### D2 — The rectangle: upright pixels, checked, clipped, rounded

- **Space.** The source's upright pixels: EXIF orientation applied, as
  `Picked` reports and as both codecs already decode. An app computes the
  rectangle from `Picked.width`/`height` and its frame, never from the
  stored orientation.
- **Checked at the call** with the other options, before anything is
  queued (A1.1): each of the four is a finite number, `width` and `height`
  greater than 0. Otherwise a `TypeError` that takes no queue slot.
- **Clipped to the image** after the header is read, as `drawImage` clips a
  source rectangle. A rectangle that misses the image entirely fails with a
  new code, `outside` (`compressImage: outside: the crop misses the
  4032×3024 image`).
- **Rounded** edge by edge to whole pixels (`round(x)`, `round(x + width)`,
  the same for `y`), at least one pixel each way. Contract arithmetic gives
  fractions, and a 1:1 frame should give a square, which rounding edges
  rather than sizes keeps to within a pixel.
- **Then A1.2 runs on the rectangle's size** in place of the image's:
  `contain(cropW, cropH, maxDimension)` and the same search. A crop is never
  upscaled, as an image isn't.
- **Limits stay A1.5's.** The source-pixel limit applies to the whole
  image, since both codecs decode it (below). The bitmap is at most
  `w × h`.

### D3 — Per host: one more rectangle in the draw each codec already does

| host | how |
|---|---|
| web (all carriers) | `storage-image.js` decodes the oriented bitmap as now (`:140`) and draws `context.drawImage(bitmap, x, y, cropW, cropH, 0, 0, w, h)` in place of `drawImage(bitmap, 0, 0, w, h)` (`:191`). `createImageBitmap`'s own source rectangle is not used: the codec already holds the oriented bitmap, and one rectangle in one place keeps the web and Apple alike. |
| iOS, macOS, tvOS (Apple) | `draw` (`apple.rs:298`) asks ImageIO for the oriented thumbnail at `ceil(max(W, H) × w / cropW)` on its long side (never above the source), and draws it into the `w × h` context offset by the scaled rectangle, so the context's bounds cut it (Core Graphics' origin is bottom-left, so `y` is flipped). Memory stays inside A1.5's bound: the thumbnail is at most the source's pixels. |
| Linux, Windows, Android | `unsupported`, as A1 (A1.3). |
| terminal | no picker, no images to crop. |

The wire: opcode 121 carries the four values plus four more (`NaN` for no
crop), and `ImageCodec` takes an `Option<CropRect>`. That changes Ibex
patch 9, which A1 introduced; no new patch.

### D4 — The crop UI is Contract, with the gestures that exist

No new tag. Two shapes cover Bluesky.

**A fixed frame (avatar 1:1, banner 3:1).** The frame stays still; the
person moves and pinches the photo under it, as iOS Photos and the crop
sheets do. This is the interaction gallery's photo viewer with a different
clamp:

```
box testId="crop-frame" width="100%" aspect-ratio="1" position="relative" overflow="hidden" padding=0 border-width=0 box-sizing="border-box" border-radius="50%"
  box id="crop-photo" width="100%" height="100%" position="relative" padding=0 border-width=0 margin=0 box-sizing="border-box" translate=`${panX}px ${panY}px` scale=zoom transition="translate -exact-spring(300, 30, 1), scale -exact-spring(300, 30, 1)"
    image pick.path width="100%" height="100%" object-fit="cover" aria-label="Your new avatar"
    box transformDragFor="crop-photo" transformgeometry=frameGeometry transformrelease=released touch-action="none" position="absolute" left=0 top=0 width="100%" height="100%" testId="crop-handle" aria-label="Move and zoom the photo"
```

With the frame `F × G` (from `transformgeometry`), the photo `W × H`
(`Picked`), the cover scale `c = max(F / W, G / H)` and the release's
`x, y, s` (`s` clamped to at least 1, the pan clamped so the photo still
covers the frame: `|x| ≤ (W·c·s − F) / 2`), the rectangle is:

```
fn cropX(W, F, c, s, x) = W / 2 - x / (c * s) - F / (2 * c * s)    // width F / (c * s)
fn cropY(H, G, c, s, y) = H / 2 - y / (c * s) - G / (2 * c * s)    // height G / (c * s)
```

The banner is the same with `aspect-ratio="3"` and no `border-radius`.
`border-radius="50%"` only shows a circle; Bluesky uploads the square too.

**A free crop (a post's image).** The photo is fitted (`object-fit:
contain`) and still. A box over it has four corner handles, each `pan=
moveCorner("tl")` and so on; the action adds the move to that corner's
edges in state, clamped to the photo and to a minimum size, and keeps an
aspect if one is chosen. The dimming outside the box is the box's own
`box-shadow: 0 0 0 100vmax rgba(0,0,0,.55)`, as `apps/photo-editor`'s
web module does. Each move is a runner commit, as a drawing surface's is.

**Where the rectangle lives.** In state beside the picked path, as
Bluesky's `ComposerImage` keeps `source` and `transformed`. The preview
shows the original under the same transform, so nothing is written until
upload, and re-editing starts from the original. At upload the app calls
`compressImage` with the rectangle.

`docs/contract-for-agents.md` gains both shapes as a short recipe; a
corpus fixture holds the free crop.

### D4a — Not built here: a crop component in Contract

Both shapes are app code, about 60 lines each. If a second app writes
them, a shared component is worth it. That is `use` across apps, which
QUEUE holds.

### D5 — The agent's view

There is no device and no substitute (A1.6): the codec runs for real under
`--storage` on macOS, iOS and the web, and is `unsupported` on Linux.

- **The UI** is driven with operations that exist: `tap crop-handle drag
  -80 0`, `tap crop-handle pinch 1.6`, `tap corner-tl drag 30 40` (LLP
  1012; `docs/contract-for-agents.md:1608`). `state` shows the rectangle the
  app holds; `screenshot` shows the frame.
- **The codec** is checked through the app: after "Save", `state` shows the
  result's `width` and `height`.
- **The fixture** is `scripts/fixtures/picker/oriented-gps.jpg` (stored
  64×48, EXIF orientation 6, red over blue; upright it is 48×64, blue on the
  left, A1.6). `crop {x: 0, y: 0, width: 24, height: 64}` must come back
  24×64 and all blue. A codec that cut the stored 64×48 image before
  turning it gives a different size and red in it. That one case checks the
  coordinate space on both codecs.
- **Replay** (LLP 1069.009): nothing new. The gestures are dispatches and
  the codec is computation.

### D6 — The amendment: LLP 1069.002 A2

LLP 1069.002 gains §Amendment A2, "a source rectangle on
`compressImage`", and its ruling section changes:

> **D6 reopened again (Charlie, 2026-10-…):** `compressImage` takes an
> optional `crop` rectangle, in upright pixels, applied before A1's search.
> Rotation, filters and any other edit stay out, and so does a crop at pick
> time. The design is §Amendment A2 (LLP 1114.003).

A1.8's "Crop, rotate or any edit" becomes "Rotate or any edit other than
A2's crop". D6's sentence "No other transforms at pick" stays true: the
crop is a step the app asks for after the pick, as A1 is. A2's tests
extend A1.7's suites: the pure clip-and-round function in `exact-data`
(edges, fractions, a miss, a one-pixel crop); the fixture case above on
macOS, the iOS simulator, and Chrome, Firefox and WebKit; the `TypeError`s
on every carrier; `outside`.

## 7. What the clone does after

- **Avatar and banner** (item 72): after the pick (or the camera, LLP
  1114.002), a crop screen with the fixed frame, 1:1 shown as a circle and
  3:1. "Save" calls `compressImage` with the rectangle at 2000 px and
  1,000,000 bytes, then `uploadBlob` and the profile update.
- **Post images** (item 66): an "Edit" button on each attached image opens
  the free crop. The rectangle is kept with the draft image and applied by
  the `compressImage` call that already runs at upload (4000 px, 2 MB).
- **Verified by:** an agent drive on the web, macOS and the iOS simulator
  with `--storage`: pick the fixture, drag and pinch, save; `state` shows
  the rectangle and the record; the uploaded blob (against a stub PDS) is
  24×64 and blue for the fixture's left half. Then one pass by hand on a
  phone with a real photo, and the avatar checked in the official app.

Clone size: **M.** About a day: the two crop screens (most of it), the
draft model change, and the drives.

## 8. Effort and complexity

**exact2: S–M, about a day.**

- *Easy:* the d.ts and the option checks on four carriers (each already
  checks two options); the web's draw (one line, plus the clip); the pure
  clip-and-round function and its tests; the docs recipe.
- *Moderate:* the Apple draw. The thumbnail's scale and the offset in a
  bottom-left space are easy to get a pixel wrong, which is why D5's
  fixture is asymmetric. Ibex patch 9's wire and codec signature change,
  in vendored code with its own tests (A1.7).
- *Not touched:* A1.5's right to write, the waiter, the queue. Those were
  most of A1's review rounds, and a rectangle changes none of them.

**Clone: M.** Most of the work is the UI, which is the point.

No earlier ruling is reversed but the parenthetical in LLP 1069.002's "D6
reopened" (Q1). Nothing in `rules/DEFERRED.md` names cropping.

## 9. Not in scope

- Rotation, flips, filters, adjustments, drawing or text on images.
- A crop sheet in any host (option b).
- Cropping video.
- A shared crop component (D4a).
- A circle as the uploaded shape: the frame only shows one, as Bluesky's.
- Linux, Windows and Android codecs (A1.3).
- Cropping at pick time, or any edit the host makes without the app asking
  (D6 stays).
