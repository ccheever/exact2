## Summary

`@exact/sign-in` lets an app sign a person in with an identity provider,
Sign in with Apple and Sign in with Google first, and hand the
provider's ID token to the app's own server, which verifies it and keeps
the account. It covers the web, iOS, macOS and Android first.

Its tier 1 is FedCM's: an `identity` member on the Credential Management
API's `credentials.get`, whose `providers` name each provider by a
`configURL` and a `clientId`, in `"passive"` mode (offered without a
press) or `"active"` mode (from a button), answering an
`IdentityCredential` whose `token` is the provider's. The call is
`@exact/passkeys`' `get` (LLP 1133.011 §8): passkeys owns the shared
native credential request, and this module adds its request types to it,
so one sheet can offer a passkey and Sign in with Apple, as a hand-built
app's does.

```ts
// grants: 'auth.apple com.example.web', 'auth.google 1234-web.apps.googleusercontent.com', 'net.fetch https://api.example.com'
import { credentials } from "@exact/passkeys";

// When the screen shows: a single-use nonce from the app's server, kept for the press.
const { nonce } = await (await fetch(`${api}/sign-in/nonce`, { method: "POST" })).json();
// At the press, with nothing awaited before the call:
const credential = await credentials.get({
  identity: { mode: "active", providers: [{
    configURL: "https://appleid.apple.com", clientId: "com.example.web", params: { nonce },
    web: { redirectURI: `${api}/sign-in/return` } }] },   // the server's return route (D3)
});
const account = await fetch(`${api}/sign-in/identity`, { method: "POST", body: JSON.stringify(credential) });
```

```
use getIdentityCapabilities, IdentityCapabilities from "@exact/sign-in"

resource caps = getIdentityCapabilities() as shape IdentityCapabilities
mutation prepared as shape Ready
mutation signedIn as shape Account then home
task prepare mount
  send prepared = prepareSignIn()            // data code fetches and keeps a nonce
action appleSignIn
  send signedIn = signIn("apple")            // data code calls get at once, then posts the credential
view
  if caps.providers.apple.active
    exact-sign-in-button provider="apple" press=appleSignIn testId="apple-sign-in"
```

Five decisions carry the module:

- **The provider's token is a credential, so it never enters the plan.**
  Data code receives it, posts it to the server and answers the account,
  as a passkey assertion is spent (LLP 1133.011 D12). Contract reads the
  capabilities and shows the provider's button; it never calls `get`.
- **Passkeys own the request; sign-in adds its types to it.** `identity`
  is a member of passkeys' `get`, declared by this package, as FedCM's
  WebIDL adds `identity` to `CredentialRequestOptions` by a partial
  dictionary. On Apple and Android this package's implementation hands
  passkeys' implementation the platform request objects for `identity`,
  through a table the packages share per session, and gets back the
  credential the person picked (D10).
- **Each provider is reached the way its own documentation says, on each
  target.** There is no common mechanism under FedCM's names: Apple is a
  system sheet on Apple; Google is a system sheet on Android and a browser
  session on Apple (as Google's own iOS SDK is). On the web both are the
  provider's authorization page in a popup, through the host's auth
  session: the provider answers the app's server, which hands the page a
  single-use handle, so no provider's script runs in the page (D3).
- **An active request is made from the press, as FedCM's is.** The
  provider's own button, `exact-sign-in-button`, is a view whose press is
  an event the app's action answers, there because the HIG and Google's
  branding ask for the provider's button. On the web the button also opens
  the popup window at the press, inside its activation, and the request
  the action makes navigates it (D5).
- **A sign-in is a person's act.** A tool invocation or a wake fails
  `person-required` before any provider is asked (D9).

The consumer is `apps/auth-fixture`, as for passkeys: no app in the
repository owns accounts, and a sign-in serves the app's own server. The
fixture server gains an identity route that verifies an ID token by the
provider's rules, the web's return route, and a fixture identity provider
that signs tokens for drives (§10). Snapback's identity would be the
product consumer (§13).

## 0. What is new here

1. **Federated identity has no common mechanism.** Geolocation and
   passkeys each have one platform framework per target. Sign-in has a
   framework per provider per target, and some cells are a browser flow,
   some a system sheet. Tier 1 names one call;
   the implementations route it (D3).
2. **The web's own API does not reach the providers.** FedCM is a W3C
   Working Draft shipped in Chromium only (Chrome 108); Firefox has not
   shipped it and Mozilla's position is neutral
   ([standards-positions #618](https://github.com/mozilla/standards-positions/issues/618));
   WebKit has taken no position
   ([#309](https://github.com/WebKit/standards-positions/issues/309)).
   Google documents FedCM only through its Google Identity Services
   script ([FedCM migration](https://developers.google.com/identity/gsi/web/guides/fedcm-migration)),
   and Apple is not a FedCM identity provider. So the web cell runs each
   provider's authorization-code flow in a popup, and FedCM is the shape,
   not the mechanism (D1).
3. **A sign-in needs a button the provider designs, and on the web a
   popup that opens in the press's activation.** A popup opened after an
   `await` is blocked (LLP 1069.006 D4). Passkeys removed its activation
   rule because WebAuthn no longer needs one (LLP 1133.011 D9); a sign-in
   on the web does (D5).
4. **Some of an answer comes only once.** Apple shares the person's name
   with the app the first time they sign in, and never again unless they
   disconnect the app
   ([Authenticating users](https://developer.apple.com/documentation/signinwithapple/authenticating-users-with-sign-in-with-apple)).
   An answer exact2 drops is lost for good (D12).
5. **The web needs the app's server.** Apple posts its answer to a server
   when a name or email is asked (`form_post`), and Google's web client
   exchanges its code with a secret only a server keeps, so on the web the
   provider's answer reaches the app's server before the page (D3).

## 1. Tier 1

### D1 — FedCM's names, on passkeys' `get`

The interface declares:

| Name | Kind | Meaning | Contract | Data code |
|---|---|---|---|---|
| `identity` on `credentials.get` | a member of `@exact/passkeys`' `get` (D10); a request | sign in with one provider (active) or offer one or more (passive) | — (`get` is data code's alone) | `await credentials.get({ identity, mediation })` |
| `getIdentityCapabilities()` | live source; a fact; `sync` on Apple | which providers this target can offer, in which mode, and whether beside a passkey | `resource caps = getIdentityCapabilities()` | `await getIdentityCapabilities()` |
| `preventSilentAccess()` | send; not a request | the next `get` may not sign in without UI | — | `await preventSilentAccess()` |
| `exact-sign-in-button` | view | the provider's own button; its `press` is an event the app's action answers by calling `get` (D5) | `exact-sign-in-button provider="apple"` | — |

**The request** is FedCM's `IdentityCredentialRequestOptions`
([FedCM](https://w3c-fedid.github.io/FedCM/), the Editor's Draft):

| Member | Type | Meaning here |
|---|---|---|
| `providers` | a list of `{configURL, clientId, loginHint?, domainHint?, fields?, params?}` | one provider in `"active"` mode, as FedCM requires; one or more in `"passive"` |
| `mode` | `"passive"` (the default) or `"active"` | passive: offered with no press, in a system sheet where the target has one; active: made from a press (D5) |
| `context` | `"signin"` (the default), `"signup"`, `"use"`, `"continue"` | the wording of the sheet and of the button: Apple's button type, Google's button text |
| `mediation` (on `get`) | `"optional"` (the default), `"required"`; `"silent"` and `"conditional"` refused | Credential Management's, as far as the cells keep them: `optional` leaves automatic selection off, and tier 2's `android.autoSelectEnabled` turns it on (D4); `required` shows UI even then. `"silent"` promises no UI or a failure, and no cell has a documented mechanism that cannot fall back to UI (Google's automatic sign-in shows One Tap or the account chooser when its conditions fail, [automatic sign-in](https://developers.google.com/identity/gsi/web/guides/automatic-sign-in-sign-out)), so it fails `NotSupportedError` until one does. `"conditional"` beside `identity` fails `NotSupportedError`, as Chromium does |

A provider's members:

- **`configURL`** names the provider. Google's is its FedCM
  configuration, `https://accounts.google.com/gsi/fedcm.json`, the URL
  `https://google.com/.well-known/web-identity` lists. Apple publishes no
  FedCM configuration, so its name is its OpenID issuer,
  `https://appleid.apple.com` (a declared deviation). Any other value fails
  `NotSupportedError` until a consumer asks for another provider (§12).
- **`clientId`** is the client registered with the provider for the
  token's audience on the web: Apple's Services ID, Google's web client
  ID. It must be granted (D8). The native targets' audiences differ (D8),
  and the bake prints the list the server must accept.
- **`params.nonce`** binds the token to a challenge the server issued.
  FedCM moved `nonce` into `params`; Chrome deprecates the top-level
  member. The server issues one raw nonce, and the module makes each
  provider's `nonce` claim the same function of it on every target, so
  the server checks one rule per provider: **Google's claim is the raw
  nonce** (Android's `setNonce` and the `nonce` parameter of Google's
  authorization request, on Apple and on the web, echo it), and **Apple's
  claim is one form on every Apple cell.** Apple's native
  `ASAuthorizationOpenIDRequest.nonce` is placed in the token as set;
  whether Apple's REST authorization, the web cell (D3), places its
  `nonce` parameter as given or hashed, Apple's reference does not say.
  Stage 1 records the web's claim from a real token: if it is the raw
  nonce, the native request gets the raw nonce; if it is the SHA-256 in
  hex, the native request gets that hash, so Apple's claim is the hash on
  every target. The recipe and the fixture server state the rule stage 1
  records, and a hermetic test holds the module to it.
- **`fields`** (`"name"`, `"email"`, `"picture"`) are what the person is
  asked to share; on Apple they are `requestedScopes` (`fullName`,
  `email`). Google's token carries all three whatever is asked.
- **`loginHint`** and **`domainHint`** reach Google as `login_hint` and
  `hd` (Android: `setHostedDomainFilter`); Apple has neither, and they are
  inert there.

**The answer** is the `IdentityCredential`'s JSON form:

```json
{ "type": "identity", "id": "", "configURL": "https://appleid.apple.com",
  "isAutoSelected": false, "token": { … the provider's … },
  "handle": "c7…",
  "apple": { "user": "001234.abcd…", "realUserStatus": "likelyReal" } }
```

FedCM types `token` as `any`, the identity provider's to define. On the
native targets each provider's token is the shape its own API answers, so
a server verifies it the way the provider documents; on the web the
provider has already answered the server:

- **Google, natively:** the ID token, a JWT string, as Android's
  `GoogleIdTokenCredential.idToken` is.
- **Apple, natively:** the shape Apple's web flows answer,
  `{authorization: {code, id_token, state}, user?: {email, name:
  {firstName, lastName}}}`
  ([Configuring your webpage](https://developer.apple.com/documentation/signinwithapple/configuring-your-webpage-for-sign-in-with-apple)),
  built from `ASAuthorizationAppleIDCredential` (`identityToken`,
  `authorizationCode`, `email`, `fullName`). `user` is present only on
  the first authorization, as Apple gives it. The `code` is what the
  server exchanges for the refresh token it must revoke when the account
  is deleted (D2).
- **Either provider, on the web:** `{relay: "<handle>"}`, the app
  server's single-use handle for the answer the provider sent it (D3),
  which the server redeems.

**Errors** are FedCM's and Credential Management's `DOMException` names,
with the platform's own code as tier 2 (`apple.code`, `android.type`):

| Name | When | Apple | Android |
|---|---|---|---|
| `NetworkError` | the person dismissed the sheet or closed the popup (the host's 499, LLP 1069.006 D4), or no account was available; one name, as FedCM uses it, so the app cannot learn which | `canceled` (including `preferImmediatelyAvailableCredentials` finding nothing) | `GetCredentialCancellationException`, `NoCredentialException` |
| `NotAllowedError` | the get also has `publicKey`, and the person cancelled (passkeys' name for the shared sheet, LLP 1133.011 D1); the app is in the background | as above | as above |
| `NotAllowedError`, message `person-required` | a tool, a wake or a headless session (D9) | — | — |
| `SecurityError` | `clientId` is not granted (D8) | — | — |
| `AbortError` | the call ended: its task or mutation was superseded, the session closed or the screen left (D5) | `cancel()` | coroutine cancellation |
| `NotSupportedError` | no implementation, a provider or mode this target lacks (D3), `identity` beside `publicKey` where the target cannot combine them (below), `"active"` with several providers or beside `publicKey`, `mediation` `"silent"` or `"conditional"` | — | `GetCredentialUnsupportedException`, `GetCredentialProviderConfigurationException` |
| `IdentityCredentialError` | the provider refused (its `error` and `url`), as FedCM's; on the web, an `error` the return route passes back that is not a cancellation, which is `NetworkError` (D3) | `failed`, `invalidResponse` | `GoogleIdTokenParsingException` |
| `NotAllowedError`, message `busy` | another auth session of the runner is held (D6): Google on Apple, either provider on the web; on the web, another ceremony holds the one-sheet queue at the press (D5) | — | — |
| `NotAllowedError`, message `activation` | on the web, a call with no window waiting from the provider's button reached the popup after the press's activation lapsed, or the browser blocked the popup (LLP 1069.006 D4's 428) (D5) | — | — |

**`identity` beside `publicKey`.** Credential Management Level 1 lists
`identity` and `public-key` as types that may not share a `get`, and
rejects the pair `NotSupportedError` (§2.5.1, "Request a Credential",
step 8.3; the credential type registry). Chromium today forwards the call
to WebAuthn and drops `identity` silently. On the web this module follows
the specification: the pair fails `NotSupportedError`, and the app shows
the passkey and the provider separately, as a web page does. On Apple and
Android one platform request holds both and shows one sheet, so the pair
is the hand-built app's behaviour there, for exactly these: a passkey with
passive Apple on Apple, and a passkey with passive Google on Android. An
active request is a press's own, and is never combined: `publicKey` beside
`mode: "active"` fails `NotSupportedError` on every target, as does a
provider the target cannot put in the shared request (D3).
`getIdentityCapabilities()` says which, per provider and mode.

**`getIdentityCapabilities()`** answers `IdentityCapabilities`:

```
{ available: bool,                       // LLP 1133 D8: an implementation is bound
  providers: {
    apple:  { active: bool, passive: bool, withPublicKey: bool },
    google: { active: bool, passive: bool, withPublicKey: bool } } }
                                         // withPublicKey: passive, beside a passkey, in one sheet
```

It is a declared deviation: FedCM's feature test is `"IdentityCredential"
in window`, which says nothing per provider, and the app needs to know
which buttons to show. It is live: re-read on a return to the foreground,
since the person can sign in to a Google account or remove one meanwhile.

**`preventSilentAccess()`** is Credential Management's
`navigator.credentials.preventSilentAccess()`: after it, no `get` signs
in without UI until the person signs in again with UI. The platforms'
own call is weaker: Android's `CredentialManager.clearCredentialState()`
"will notify all credential providers that any stored credential session
for the given app should be cleared"
([implementation guide](https://developer.android.com/identity/sign-in/credential-manager-siwg-implementation)).
So the Android implementation calls it and also keeps its own flag, in
its own storage, that turns automatic selection off
(`setAutoSelectEnabled(false)`) until a sign-in that showed UI succeeds.
On Apple and the web it does nothing, since neither signs in without UI. The recipe calls it at
sign-out.

**Declared deviations,** each with its reason:

- **Imported, not global,** as passkeys' (LLP 1133 D6 rule 5): `get` from
  `@exact/passkeys`, the rest from `@exact/sign-in`.
- **The JSON form of the answer,** as passkeys' (LLP 1133.011 D1).
- **Apple's `configURL`** is its issuer (above).
- **`getIdentityCapabilities`** (above).
- **The web cell is each provider's authorization-code flow in a popup,
  through the app's server, not FedCM** (D3), and its token is the
  server's handle (above).

### D2 — What a sign-in proves

| | Google | Apple |
|---|---|---|
| The token | an ID token, signed by Google (`https://www.googleapis.com/oauth2/v3/certs`) | an ID token, signed by Apple (`https://appleid.apple.com/auth/keys`), and an authorization code good for five minutes |
| The server checks | the signature, `iss` (`https://accounts.google.com`), `aud` among its client IDs (D8), `exp`, and `nonce` equal to the raw nonce it issued ([OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)) | the same, with `iss` `https://appleid.apple.com`, `aud` its bundle ID or Services ID, and `nonce` equal to the form stage 1 records for every Apple cell (D1): the raw nonce or its SHA-256 in hex ([Authenticating users](https://developer.apple.com/documentation/signinwithapple/authenticating-users-with-sign-in-with-apple)) |
| Who it is | `sub`, stable per Google account; Android's `uniqueId` | `sub`, the same as the credential's `user`, stable per team; the email may be a private relay address |
| Secret? | a bearer credential until `exp` | the same; the code is a credential until exchanged |

On the web the server first redeems the credential's handle at its own
return route (D3), which holds the ID token (and Apple's `code` and
`user`) the provider sent it, and then makes the same checks.

The module never verifies a token; it carries the provider's to the data
code that asked, as passkeys carry a response (LLP 1133.011 D2). The
recipe, `docs/recipes/sign-in.md`, gives the server's checks, and two
duties a hand-built app's server has:

- **Apple's account deletion.** An app that offers account creation must
  offer deletion (Guideline 5.1.1(v)), and "if your app offers Sign in
  with Apple, you'll need to use the Sign in with Apple REST API to revoke
  user tokens when deleting an account"
  ([Apple, 2022](https://developer.apple.com/news/?id=12m75xbj)). The
  server exchanges the first `code` for a refresh token with a client
  secret it signs, keeps it, and revokes it at deletion. The module's part
  is to deliver the code.
- **The name arrives once.** The server keeps `user.name` from the first
  authorization; later tokens do not carry it.

Sources for each cell:

- **Apple on Apple:** one controller takes "additional assertion
  requests in the array, such as passwords and the Sign in with Apple
  service. The sheet displays whatever credentials the device has for
  those types" ([Supporting passkeys](https://developer.apple.com/documentation/authenticationservices/supporting-passkeys));
  "you'll get the same delegate callback regardless of which credential
  type is used" ([Meet passkeys](https://developer.apple.com/videos/play/wwdc2022/10092/)).
  `ASAuthorizationAppleIDProvider` is on iOS 13, macOS 10.15, tvOS 13,
  watchOS 6 and visionOS 1.
- **Apple on the web:** the REST flow, `GET
  https://appleid.apple.com/auth/authorize`, whose answer goes to the
  `redirect_uri`, and "if you requested any scopes, the value [of
  `response_mode`] must be `form_post`"
  ([authorization request](https://developer.apple.com/documentation/signinwithapplerestapi/request-an-authorization-to-the-sign-in-with-apple-server.)),
  so a static page cannot receive it. The `redirect_uri` must be a return
  URL registered for the Services ID on a verified domain, never
  `localhost` or an IP address: it is the app server's return route.
  Sign in with Apple JS, the in-page alternative, is a script in the page
  (§13 question 3).
- **Apple on Android:** Apple ships no Android SDK. Its documented route
  is a browser tab to `/auth/authorize` whose `form_post` lands on the
  app's server, which then "redirect[s] the custom URL scheme to give
  control back to the app"
  ([other platforms](https://developer.apple.com/documentation/signinwithapple/incorporating-sign-in-with-apple-into-other-platforms)).
  It needs `openAuthSession`'s Android arm (Custom Tabs, not built,
  LLP 1133.000 §2) and a server route exact2 cannot provide. `later`.
- **Google on Android:** `GetGoogleIdOption` is the bottom sheet;
  Google recommends asking first for "authorized accounts" and, on
  `NoCredentialException`, for all accounts
  ([implementation guide](https://developer.android.com/identity/sign-in/credential-manager-siwg-implementation)).
  `GetSignInWithGoogleOption` is "a request … from an explicit 'Sign in
  with Google' button"; the request carrying it must contain "exactly
  one `GetSignInWithGoogleOption` and no other options"
  ([codelab](https://codelabs.developers.google.com/sign-in-with-google-android)),
  so active Google is never combined. The documentation says the bottom
  sheet "can also include other sign-in options such as passkeys and
  passwords" ([overview](https://developer.android.com/identity/sign-in/credential-manager-siwg));
  stage 3 confirms a passive Google option beside a passkey option in one
  request on a device.
- **Google on Apple:** Google's iOS and macOS SDK, GoogleSignIn, is a
  browser flow over AppAuth, which authenticates "using
  `ASWebAuthenticationSession`" ([AppAuth-iOS](https://github.com/openid/AppAuth-iOS)),
  with an iOS-type client ID whose reversed form is the redirect scheme
  ([start integrating](https://developers.google.com/identity/sign-in/ios/start-integrating)).
  There is no system provider for Google on Apple, so a hand-built app
  shows the browser session's sheet, and so does this module (D6).
- **Google on the web:** the OpenID Connect authorization-code flow for
  a web application client
  ([OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect),
  [web server applications](https://developers.google.com/identity/protocols/oauth2/web-server)),
  whose code is exchanged with the client secret Google issues to that
  client, so on the app's server. Google's in-page sign-in, One Tap and
  its button, is the Google Identity Services script, with FedCM inside it
  in Chromium
  ([reference](https://developers.google.com/identity/gsi/web/reference/js-reference));
  calling FedCM with Google's configuration directly works in Chromium but
  is undocumented, and Google's implicit flow is "provided only for
  legacy support".

**The web's return route.** On the web both providers answer the app's
server, as the IETF's guidance for browser-based applications has a
backend do
([browser-based apps](https://datatracker.ietf.org/doc/draft-ietf-oauth-browser-based-apps/),
"Backend For Frontend"), and the page holds only a handle:

1. **When the screen shows,** data code fetches a single-use nonce from
   its server, as on every target, and keeps it.
2. **At the press,** `get` reaches the web implementation inside the
   press's activation (D5), which makes a `state` from the system's random
   source and the authorization URL. Apple's:
   `https://appleid.apple.com/auth/authorize` with the Services ID,
   `redirect_uri` the provider's `web.redirectURI` (D7),
   `response_type=code id_token`, `response_mode=form_post`, `scope` from
   `fields` (`name email`), `state` and `nonce`. Google's:
   `https://accounts.google.com/o/oauth2/v2/auth` with the web client,
   the same `redirect_uri`, `response_type=code`, `scope=openid email
   profile`, `state`, `nonce`, `login_hint` and `hd`. It opens the URL
   through the host's auth session (D10 item 3), whose `state` is the same
   value, with the page's own callback, `https://<origin>/.exact/auth/callback`: LLP 1069.006 D4's
   popup, callback page, return channels and bound, as built.
3. **The provider answers the return route** on the app's server: Apple
   posts `code`, `id_token`, `state` and, the first time, `user`; Google
   redirects with `code` and `state`. The route keeps the answer, for
   Google the ID token it gets by exchanging the code at
   `https://oauth2.googleapis.com/token` with its secret (dropping the
   access token; it never asks `access_type=offline`), under a handle of
   at least 128 bits from a secure random source, single-use and expiring
   within minutes. It answers `303 See Other` to the page's callback, a
   URL it is configured with and never one the request names, carrying
   `state` and `relay=<handle>`, or `state` and the provider's `error`.
4. **The page's callback** returns the URL on LLP 1069.006 D4's channels;
   the host's auth session matches its scheme, host, path and `state`
   (D3 there); the implementation answers `{relay}` as the token, or
   fails with the error: `NetworkError` for one that means the person
   cancelled (Apple's `user_cancelled_authorize`, Google's
   `access_denied`), `IdentityCredentialError` for any other (D1).
5. **Data code posts the credential** as on every target, and the server
   redeems the handle once and checks the ID token it kept by D2, its
   nonce against the one issued to this client.

The handle is a bearer credential while it lives, as an authorization
code is, and travels as `openAuthSession`'s code does: in the callback
URL only, which the callback page replaces, under `no-referrer`, never in
the journal or `state` (LLP 1069.006 D1, D4). A handle redeemed by a
client other than the one that asked fails the nonce check, since the
nonce is the asking client's. Google's request needs no PKCE challenge:
the client is confidential and the server checks the OpenID Connect nonce
it issued to this client, which RFC 9700 lets a confidential OpenID
Connect client use instead (§2.1.1, with §4.5.3.2's precautions), though
it recommends PKCE as well. A server that wants PKCE mints the verifier
when it issues the nonce, keeps it for its exchange, and passes the S256
challenge in `params` (`code_challenge`), which the module forwards to
Google; nothing is computed at the press.

The return route is the app's: exact2 runs no server. The recipe gives
it, and the fixture server implements it (§10). The providers' web
clients register the route, not the page, as their redirect URI.

**Not the web's mechanism, the web's names.** No cell calls
`navigator.credentials.get({identity})` today. The names stay FedCM's
because they are what an author or an agent who knows the web writes,
and because an identity provider with a documented FedCM configuration would be a pass-
through on the web cell when a consumer asks (§12).

**A target without a cell** answers the capability `false` and fails the
call `NotSupportedError`; a passive request leaves the provider out, as
FedCM leaves out a provider whose login status is logged-out in passive
mode, and fails `NetworkError` if none is left.

## 3. The button, the press, and the browser session

### D5 — `exact-sign-in-button`, and an active request from the press

An active request is made from a press, as FedCM's active mode is called
in a click handler. The provider's own button, `exact-sign-in-button
provider="apple"` (or `"google"`), is a package view (LLP 1133.008 D8
item 1) whose `press` event the app's action answers by calling `get`.
The view makes no request itself. Natively a request from any other
control works the same way; on the web the button also opens the popup's
window (below).

**Why the provider's button.** The HIG asks for Apple's: a system button
(`ASAuthorizationAppleIDButton`), whose style only its corner radius may
change, or a custom one under rules App Review checks
([HIG](https://developer.apple.com/design/human-interface-guidelines/sign-in-with-apple)).
Google's branding guidelines fix the "G" logo's size, colour and
proportions on any custom button
([branding](https://developers.google.com/identity/branding-guidelines)).
A `button` the author draws with the words "Sign in with Apple" is a
tell, and may be a rejection.

**The view, per target:**

| | Apple | Google |
|---|---|---|
| iOS, macOS | `ASAuthorizationAppleIDButton` | Google's standard button, drawn by the view from Google's published logo and text |
| Android | later (D3) | Google's standard button, drawn by the view |
| web | Apple's button, drawn by the view from the artwork Apple publishes, to the HIG's rules for a custom button | Google's standard button, drawn by the view |

The artwork is carried in the package and loads nothing from a provider.
The view's attributes: `provider`, and tier 2 words for what each
provider's button offers (`apple.cornerRadius`; Google's `theme`, `shape`
and `text`, as Google's branding offers them). Width and height are the
author's CSS (author > platform), within each provider's minimum (Apple's
140 by 30 points).

**On the web, the button opens the popup.** FedCM's active mode needs
transient activation, and so does a popup. LLP 1069.006 D4 records that
Safari lets `window.open` through only on the press's own call stack, and
the web host opens `openAuthSession`'s popup there (`host/web/glue.js`).
A data-code `get` does not run there: data code reaches a page module
through a promise (`host/web-js/modules.js`'s `viaImplementation`) even
when the module is loaded. So the provider's button opens the window
itself:

1. **At the press,** in its own click handler and before it delivers
   `press`, `exact-sign-in-button` opens a named popup on `about:blank`,
   inside the press's activation, and gives it to the host's auth session
   as the window waiting for that press's request. Under the agent it
   opens nothing, since the session is held (§9).
2. **The press's action** calls `get`. Its call reaches sign-in's
   implementation later, through promises,
   and the implementation opens the authorization URL through the host's
   auth session (D10 item 3), which navigates the waiting window to it.
   Navigating a window the page already holds needs no activation.
3. **A window no request claims** by the time the press's action settles
   is closed, so a press whose action does not sign in leaves nothing
   open.

The recipe keeps two conditions: the nonce is fetched before the press
(D3's step 1), and the action makes the call with nothing awaited before
it, so the window waits only for the call's own dispatch. A request made
from any other control has no window waiting; the auth session opens one
when the call arrives, which a browser allows only if the press's
activation is still current then (Chromium and Firefox measure it by
time; Safari may not), and otherwise the call fails `NotAllowedError`,
message `activation`, and opens nothing, as after `openAuthSession`'s
428. So on the web the recipe signs in from the provider's button. A
worker-placed source cannot open a popup, so the web bake refuses worker
placement in an app with an `auth.apple` or `auth.google` line, as it
refuses one with `auth.session` (LLP 1069.006, after review item 2).

**Passive requests** run when made, from a task when the screen shows,
as a conditional passkey `get` does (LLP 1133.011 D3), and need no
activation: FedCM's passive mode needs none, and the bottom sheet and
Apple's immediately-available sheet are shown without a press. The web
has none (D3).

**The one-sheet queue.** An active request is a ceremony in LLP 1133.011
D9's queue, as passkeys' modal `get` is: one sheet at a time, never over
a location prompt or a Face ID check. Natively it waits for the sheet
ahead of it, and a pending passive request of this session ends with
`AbortError` first, as a modal passkey `get` ends a conditional one (the
recipe's passive task does not start again until the active request
settles). On the web it cannot wait, since waiting spends the
activation: a press that finds the queue held fails `NotAllowedError`,
message `busy`, and opens nothing. The popup holds the queue until the
host's auth session settles it: a callback, the person closing it (499
after the grace period) or the bound (LLP 1069.006 D4).

**Lifetimes.** A request lives as its call does (LLP 1133 D6 rule 2): the
screen leaving, its task's or mutation's supersession or the session's
end cancels it (D10 item 4), which closes its sheet or popup, and it
fails `AbortError`.

### D6 — Google on Apple, and the web, through the host's auth session

Google has no system provider on Apple, and its own SDK runs the OAuth
2.0 authorization-code flow with PKCE in `ASWebAuthenticationSession`.
The Apple implementation does the same:

1. A `code_verifier` from the system's random source, its S256
   challenge, a `state`.
2. The authorization request to
   `https://accounts.google.com/o/oauth2/v2/auth` with the iOS client
   (`apple.clientId`, D8), `redirect_uri` its reversed form
   (`com.googleusercontent.apps.<id>:/oauth2redirect`, the path the iOS
   client registers, confirmed at stage 2), `scope=openid email profile`,
   the nonce, `login_hint` and `hd`.
3. The host's auth session, reached by the same runner path an
   `openAuthSession` request takes (`runner/src/auth.rs`: the hold under
   the agent, supersession of a forgotten ticket, the callback's scheme,
   host, path and `state` matched), which the implementation calls through
   its context (D10 item 3) rather than opening `ASWebAuthenticationSession`
   itself. Its grant check is against an allowlist the runner derives
   (D8), not the app's `auth.session` and `auth.callback` lines, which an
   app with only `auth.google` lines does not have; and the build links
   `ExactAuthSession`, the host's arm of the session, as an `auth.session`
   grant links it today.
   Within a runner one auth session is live at a time: `arm` today pushes
   a second session of the same target beside the first, and changes to
   refuse a new session while another session's ticket is still held
   (409, which a sign-in reports as `NotAllowedError` `busy`); a session
   whose ticket the runner forgot is dropped and the new one starts, as
   LLP 1069.006 D3 keeps a double tap from answering 409. So a sign-in's
   browser session and the app's `openAuthSession` never open together,
   whichever came first. When the sign-in's call ends, its `cancel(call)`
   (D10 item 4) forgets the session's ticket, so `forgotten()` cancels
   the sheet and frees the runner for the next session. Two runners
   sharing a window are not arbitrated (§8).
4. The code exchanged at `https://oauth2.googleapis.com/token` with the
   verifier and no secret, which Google does not issue to an iOS client.
   The implementation keeps the verifier and the response to itself and
   answers the `id_token` alone; the access token in the same response is
   dropped there, and no `access_type=offline` is ever asked, so no
   refresh token exists.

The two endpoints are the implementation's allowlist (D8), and it reaches
nothing else.

**On the web** the same path carries both providers (D3's return route).
The host's auth session there is `openAuthSession`'s JS-target arm
(`host/web-js/auth.js` and the web host's `auth-glue.js`), which already
holds one session per window and answers 409 to another target's, so a
sign-in's popup and the app's `openAuthSession` never open together
either. The implementation exchanges nothing: the server does (D3). The
journal records the session and the exchange by outcome, never a URL with
a code in it (LLP 1069.006 D7's disclosure rule).

**How sign-in relates to `openAuthSession` and the loopback.**
`openAuthSession` (LLP 1069.006) stays the general OAuth path: any
provider, with the protocol (discovery, PKCE, PAR, DPoP, tokens) in the
app's own data code and its result an authorization code the source
spends. Sign-in is narrower: two providers whose sign-in has a platform or
provider-documented form, answering an ID token. Where a sign-in provider
has no system sheet (Google on Apple, both on the web), sign-in uses the
same host session as its transport, so there is one implementation of the
browser session and its rules on each host. LLP 1133.005 §6's loopback
callback on macOS serves providers that require a desktop client's
loopback redirect (Codex's sign-in); Google's iOS-type client takes a
private-use scheme on macOS as GoogleSignIn does, so sign-in does not use
the loopback.

**macOS needs a provisioned build, and Developer ID may not carry it.**

profile (TN3125, as LLP 1133.011 D6 cites). Apple's table of macOS
capabilities lists Sign in with Apple under the App Store's distribution
and not under Developer ID
([supported capabilities](https://developer.apple.com/help/account/reference/supported-capabilities-macos)),
and `exact release` signs Mac builds with a Developer ID
(`scripts/exact.mjs`). So on macOS:

- a development build with a profile that carries the capability offers
  Apple natively; the profile is LLP 1133.010 D7's Mac input, not a second
  one;
- a build without one, and a Developer ID release build if stage 2
  confirms the table, read `providers.apple` false, and the app shows its

- **the entitlement follows the signing, not the grant:** the build
  writes `com.apple.developer.applesignin` only into a slice whose
  profile authorizes it, and omits it from every other, since an
  unauthorized restricted entitlement makes the system refuse to launch
  the app. An `auth.apple` line kept for the web never puts it on a Mac
  slice that cannot carry it; stage 2 launches such a build and signs in
  with Google;
- Google on macOS needs no entitlement and works in every build.

### D8 — The grants, the audiences, the derivations

**Two grant lines,** exact2's, stripped before `ibex2` as `auth.session`
is (`runner/src/request.rs`), one per client the app uses:

- **`auth.apple <client id>`**, as LLP 1069.008 D2 names it: the app's
  Services ID for the web. An `auth.apple` line on an Apple target writes
  `com.apple.developer.applesignin` = `["Default"]` to the entitlements of
  each slice whose signing authorizes it (D7).
- **`auth.google <client id>`**: each Google client the app uses, the web
  (server) client and the iOS client.

On Apple targets both kinds of line link `ExactAuthSession` where a
provider uses the host's session (Google), and on the web both bundle the
host's auth session (`host/web-js/auth.js`), load its glue after first
paint and write its callback page, as an `auth.session` line does. They
derive nothing into the app's grant string: a derived `auth.callback`
there would become `authCallback()`'s answer when it is the first
private-use line (`carrier_callback`, `runner/src/auth.rs`), and a derived
`net.fetch` would let data code post to the token endpoint. Instead the
runner derives, from the request's granted client ids, the set a session
this module opens is admitted against:

- **Google on Apple,** from `apple.clientId` (which must be a granted
  line): the authorization origin `https://accounts.google.com` and the
  one callback `com.googleusercontent.apps.<id>:/oauth2redirect` for that
  client;
- **on the web,** for the provider's granted `clientId`: its
  authorization origin (`https://appleid.apple.com` or
  `https://accounts.google.com`) and the page's own callback,
  `https://<origin>/.exact/auth/callback`.

The runner (on the web, the JS runtime's `auth.js`, which keeps
`runner/src/auth.rs`'s rules) passes that set to `check_grants` as the
admitted lines for a session the host's context opens for this module;
data code cannot open a session in that mode, and the package supplies no
list, so a package cannot widen what it may open. The token endpoint
`https://oauth2.googleapis.com/token` is the only place the Apple
implementation's own exchange posts; the web implementation posts
nowhere.

Admission refuses a request whose provider's `clientId` (and on Apple,
`apple.clientId`) is not a granted line, or on the web whose
`web.redirectURI` is outside the `net.fetch` lines (D7), `SecurityError`,
naming it, before anything opens: LLP 1133.011 D10 item 2's grant matched by an
argument's value. A binding call or a view with no line refuses at bake
(`grant-missing`).

**The audiences the server must accept.** The token's `aud` differs by
target, as a passkey's origin does (LLP 1133.011 D6), and the bake prints
the list for each target it builds:

| | web | Apple targets | Android |
|---|---|---|---|
| Apple | the Services ID | the app's bundle ID (`app.id`); the native request names no client | — |
| Google | the web client ID | the iOS client ID (`apple.clientId`) | the web client ID, passed as `setServerClientId` |

**What the bake derives and prints:**

- **Apple targets:** the entitlement; for Google, nothing in `Info.plist`,
  since the session captures its own callback and a private-use scheme
  needs no `CFBundleURLTypes` (LLP 1069.006 D2).
- **Android:** nothing in the manifest. Google matches an Android client
  by package name and signing certificate, registered in Google Cloud, so
  the bake prints the package and the SHA-1 fingerprint of each signing
  certificate. Passkeys' `host.android.certificates` lists SHA-256
  fingerprints (LLP 1133.011 D6), from which SHA-1 cannot be derived, so
  each entry takes the certificate itself or both fingerprints, and the
  bake names an entry with SHA-256 alone as missing its SHA-1.
- **Web:** nothing in the Content Security Policy or `Referrer-Policy`:
  no provider's script, frame or request runs in the page, and the popup
  is a window of its own. The callback page is `openAuthSession`'s, with
  its `no-referrer` (LLP 1069.006 D4). The bake prints that each
  provider's web client registers the app server's return route as its
  redirect URI, and refuses worker placement (D5).
- **App Review 4.8.** An app that uses a third-party login for its
  primary account must also offer an equivalent login that limits data
  to name and email, lets the person keep their email private, and does
  not track them without consent, with exceptions (the company's own
  accounts, an education or enterprise app, a client for a specific
  third-party service). Sign in with Apple meets it; the guideline no
  longer names it. A build for an Apple target with an `auth.google` line
  and no `auth.apple` line prints the guideline and its exceptions. It is
  never a refusal: whether an app's login is its primary account is the
  developer's reading.

### D9 — Permission and origin

**No permission.** Neither provider asks a permission: the sheet or the
popup is the person's consent. So LLP 1133.002 §4 applies as for passkeys
(LLP 1133.011 D7): declare the grant lines; read `getIdentityCapabilities`,
which is the fact; ask by the request; explain and recover in the app's
own UI. The interface declares no `permission`, and `prefer
permission.sign-in` refuses by name.

**Origin.** Names are declared with LLP 1133.009 D10 item 8's `"origin":
"app"` and `"foreground": true` where this table says:

| Origin | `get` with `identity` (active, passive) | `preventSilentAccess` | `getIdentityCapabilities`, `getCredentialState` |
|---|---|---|---|
| a person's input; the app's own foreground code | proceeds | proceeds | answers |
| a tool invocation (LLP 1111) | fails `person-required`, before anything opens | proceeds | answers |
| a background wake; a headless session | fails `person-required` | proceeds | answers |
| the app in the background | fails `NotAllowedError` | proceeds | answers |
| the development agent | §9 | §9 | §9 |

An active request's origin is that of the commit that made it, a press's
for the recipe's action. A tool cannot start a sign-in for a person to
complete: the token would reach data code a tool's commit started. A
sign-in is a person's act, as a passkey ceremony and a presence check are
(LLP 1133.010 D12): no delegation record, reuse window or earlier sign-in
satisfies one for a tool. `preventSilentAccess` only takes away a silent
sign-in, so a tool that signs the person out may call it.

### D10 — `@exact/sign-in`, an extension beside passkeys

```
packages/sign-in/

                      pins "@exact/passkeys" exactly
  exact.json          the interface: the identity member, the fact, preventSilentAccess, the view

  android/            exact.json (its Maven coordinates), SignIn.kt, the Google button's artwork
  web/                exact.json, index.js, both providers' button artwork
```

The interface declaration, abridged, in LLP 1133.002 D13's form with LLP
1133.009 D10's and LLP 1133.011 D10's additions and this RFC's:

```json
{
  "kind": "interface", "name": "@exact/sign-in", "version": "1.0.0",
  "uses": "@exact/passkeys@1.0.0",
  "grants": ["auth.apple", "auth.google"],
  "members": {
    "@exact/passkeys#get": {
      "identity": { "type": "IdentityCredentialRequestOptions",
        "grants": { "providers[].clientId": ["auth.apple", "auth.google"] },
        "origin": "app", "foreground": true,
        "answers": "IdentityCredentialJSON", "handles": { "handle": "identity" } } } },
  "names": [
    { "source": "getIdentityCapabilities", "live": true, "answers": "IdentityCapabilities",
      "sync": { "name": "getIdentityCapabilitiesSync", "from": "read" } },
    { "send": "preventSilentAccess", "contract": false }
  ],
  "views": ["exact-sign-in-button"]
}
```

**Seam additions,** each general, each proved by the out-of-tree fixture
before this package uses it (LLP 1133.001 D8):

1. **A member on another interface's name.** `"members"` declares an
   option on a name another interface owns, and the answer type it adds,
   as WebIDL's partial dictionary lets FedCM add `identity` to
   `CredentialRequestOptions`. The interface must `use` the owner, pinned
   exactly (LLP 1133.009 D3's rule for a shared surface); the bake types
   the member only in an app that depends on both, refuses a member two
   packages declare (`module-member-twice`), and the owner's answer
   becomes the union, told apart by `type` (`"public-key"`,
   `"identity"`). The member's grants, origin and foreground rules join
   the owner's at admission. The body still names the owner's name
   (`"extension": "passkeys", "send": "get"`), so the runner routes it to
   passkeys' implementation, which owns the request.
2. **A credential request table, one per session, shared by packages.**
   A package's context is its own (`host/apple/compose.mjs` makes an
   `ExactPackageContext` per package, at that package's first call;
   Android's `Extensions.kt` likewise), so a table on it is invisible to
   another package. The table is a registry in `ExactPackage`, the module
   every package's Swift already imports, keyed by the context's
   `session`, and each context reaches its session's one table; on Android,
   a class the host compiles into the same APK. `ExactPackage` imports
   Foundation alone and sees nothing of ExactKit, so the table holds
   nothing ExactKit owns, as LLP 1133.009 D3's track table holds ids and
   callbacks.

   An implementation that declares members registers a handler for each
   (`ExactCredentialMember`: from a member's options, the platform's
   request objects; from the credential the person picked, the answer).
   The owner's implementation, given a call with that member, asks the
   handler for its request objects, adds them to its one controller or
   `GetCredentialRequest`, and hands the handler the credential when the
   person picked one of its types. The protocol passes the platform's
   objects as `NSObject` (every `ASAuthorizationRequest` and
   `ASAuthorizationCredential` is one) and `Any` on Android, so
   `ExactPackage` links no framework, and each side casts to the types it
   built. A member a target cannot put in the shared request (active
   Google anywhere; any member on the web) is handed whole to the handler,
   which runs it alone, still in the owner's queue and lifetime.

   **The framework.** `host/apple/link.mjs` admits AuthenticationServices
   only through `ExactAuthSession`, so that its launch cost is paid only
   where it is used. A package that links a framework that check names
   declares it in its implementation's `exact.json` (`"frameworks":
   ["AuthenticationServices"]`), and the check admits a declared framework
   wherever a package that declares it is bound. Passkeys' and this
   package's Swift then import AuthenticationServices themselves. The
   rule is general: a package that links PhotosUI or SwiftUI meets the
   same check.

   **Loading.** A call whose body carries a member is admitted only once
   the member's implementation is loaded and registered: admission makes
   that package's adapter (natively) or loads its page module (the web,
   `host/web-js/modules.js`, which today loads an implementation at its
   own names' first use) before the owner runs. On the web an
   implementation that declares a member also loads its owner's page
   module, and the host's auth glue, when its own loads, so a press finds
   them loaded and the window the button opened waits only for the call's
   dispatch (D5). A member no bound
   implementation registered is refused by name, as LLP 1133.011 §8 says.

   **Conformance.** Passkeys' suite gains "a registered member's requests
   are in the one platform request, and its credential reaches its
   handler" and "an unregistered member is refused", so an implementation
   that replaces passkeys' for a target must carry members. The protocol
   is public: a third party's identity provider on Android's Credential
   Manager, whose custom credential types any provider may define, would
   register the same way. This is what LLP 1133.011 §8 asks: "the
   sign-in RFC adds its request types as members of `get`'s options …
   that this module's implementation passes in the same platform
   request".
3. **The host's auth session for an implementation:** the context's
   `authSession.open(url:, callback:, state:, ephemeral:)` submits the
   same request an `openAuthSession` call does, through the runner's
   `runner/src/auth.rs` path with its hold under the agent and its
   supersession, checked against the set the runner derives for this
   module (D8) rather than the app's lines. The composed adapter, which
   the build writes inside the app's module and which sees ExactKit, wires
   the entry to the host's `Auth.swift` arm, so the package imports
   nothing of it. On the web the entry is the JS runtime's
   `openAuthSession` path (`host/web-js/auth.js` and the web host's
   `auth-glue.js`), which gains one thing: a session may adopt the window
   the provider's button opened at the press and navigate it, instead of
   opening its own (D5). One session is live per runner, across
   `openAuthSession` and every implementation (D6). (Two runners sharing
   one window, as the Mac embedding fixture's two sessions do, are not
   arbitrated: §8.)
4. **A data-code call's lifetime and handles, tracked.** A request from
   data code is answered outside the runner today: its reply reaches the
   answer that made it without the runner seeing it dropped, and nothing
   tells the implementation when that answer ends (`QUEUE.md`, "A
   data-code module call's handles and argument groups are not tracked";
   LLP 1133.009's as-built note on item 10). A sign-in's sheet or popup
   lives for minutes, so its task's supersession must reach it. The data
   runtimes report each module call's owning answer, the runner keeps the
   call open until that answer settles or is forgotten, and a forgotten
   answer sends the implementation `cancel(call)` while it has not
   finished (`cancel()` on the controller, the coroutine, and for a
   browser session or a popup the forgetting of its ticket, D6).
   `dispose(handles)` runs only for a reply the implementation made that
   was not delivered to the data code: after delivery the runner never
   disposes, since the data code may already have posted the credential,
   which is LLP 1133.009 D10 item 10's cut and LLP 1133.011 D11's rule. A
   member's handles are watched on the member's answer and disposed to the
   member's implementation, not the owner's. Passkeys' `create` and
   conditional `get` need the same lifetime (LLP 1133.011 D9's
   cancellation, D11's disposal before delivery), so the item lands with
   whichever of the two modules' stage 0 comes first. Proved by
   superseding one task while another call in the same session stays live.

Reused as they are: passkeys' `"contract": false` (D10 item 1), its grant
matched by value (item 2), its binding groups (item 3); LLP 1133.009 D10's
orderly end (item 1), foreground (item 3), origin (item 8), handles
(item 10, carried to data-code calls by item 4 here, D12 below); LLP 1133.008 D8 item 5's one locked Gradle graph,
which resolves `com.google.android.libraries.identity.googleid:googleid`
(1.2.1, [releases](https://developers.google.com/identity/android-credential-manager/releases))
beside passkeys' `androidx.credentials` 1.6.0.

*Rejected:*

- **Sign-in's types inside `@exact/passkeys`,** declared and implemented
  there, as Media Capture declares both kinds of track (LLP 1133.009 D3).
  It is the smaller change, but every passkeys app would link
  `googleid`, and nobody but passkeys' author could add a provider.
- **A second controller in this package.** Two modules showing two
  sheets is the tell LLP 1133.011 §8 rules out.
- **Sign-in on `openAuthSession`'s reserved URL,** as LLP 1069.006 D8
  sketched for Sign in with Apple: Apple's native sheet answers a
  credential, not a callback URL, and the request must share passkeys'
  controller. The auth session is a transport this module uses (D6), not
  its home.
- **FedCM called directly on the web** for Google: it works in Chromium
  only and Google does not document it.
- **The providers' scripts in the page** (r4's web cell: Sign in with
  Apple JS and Google Identity Services, with One Tap and Google's
  button): each would run with the page's authority, which in an exact2
  page reaches the data realm and its grants, since that realm is an
  authoring boundary and not a sandbox (`host/web/module-glue.js`, LLP
  1027). Ruled out (§13 question 3).

### D12 — Callers, and an answer dropped

| Name | Contract | Data code | Request | `sync` |
|---|---|---|---|---|
| `get` with `identity` | refused (`module-name-data-only`, passkeys') | `credentials.get` from `@exact/passkeys` | yes | no |
| `getIdentityCapabilities` | a live source | the binding | no | Apple, through `call` |
| `preventSilentAccess` | refused | the binding | no | no |
| `getCredentialState` (Apple) | a live source | the binding | no | no |
| `exact-sign-in-button` | a view | — | — | — |

**Why data code alone,** as passkeys: a mutation's answer is in `state`,
which the agent and a tool read (LLP 1111), and an ID token is a bearer
credential until it expires. So the recipe's action makes the request,
posts the credential to the server, keeps the session with `secret.keep`
and answers the account, never the token. The rule binds exact2, not the
app (LLP 1133.010 D2).

**An answer dropped is gone.** A credential is provisional until the
runner delivers it to the awaiting call (LLP 1133.009 D10 item 10). One
dropped before then (the task superseded, the session ended, between the
sheet closing and the reply reaching the call) reached no server. Nothing
can undo it on the device: Apple revokes only from a server with the
code, and a Google token expires by itself. The answer carries an opaque
`handle` of its own (never the token, and not FedCM's empty `id`), which
the recipe leaves out of what it posts; a drop reaches the implementation's
`dispose` through D10 item 4, which records it in the journal.
For Apple's first authorization it loses the name for good, since Apple
does not send it again; the recipe has the server ask for a name when a
new account's token comes without one. On the web the provider's answer
is already at the server: a dropped handle expires unredeemed, and the
recipe's return route keeps Apple's first `user` by the `sub` of the ID
token it arrived with, once that token passes D2's checks, so the web
loses no name.

## 7. Cost

An app that does not use the module links none of it. One that does:

- **Apple:** AuthenticationServices, which passkeys and `openAuthSession`
  link already when used, and the Google logo asset.
- **Android:** `googleid` and `credentials-play-services-auth`, the
  second already passkeys'. Stage 3 measures the APK with LLP 1047's
  probe.
- **Web:** a page module and the providers' button artwork, loaded after
  first pixel and never on the boot path (`rules/RULES.md`), and the host's
  auth session, which `openAuthSession` already loads after first paint.

**No third-party script.** The page's Content Security Policy admits only
the host's own scripts, by `'self'` and by the SHA-256 of each inline one
(`host/render/src/serve.rs`'s `csp()`), and this module leaves it so. The
providers' pages run in their own popup window, a separate browsing
context of their origin, and their answer reaches the app's server, not
the page; the page holds only the single-use handle (D3). The cost is the
server's return route, and One Tap and Google's FedCM, which exist only as
Google's script (§13 question 3).

## 9. The substitute

**Shape:** `getIdentityCapabilities` and `getCredentialState` are facts;
`get` with `identity` is a request (LLP 1069.007 D1); `preventSilentAccess`
is a send the substitute records. The module is not its own substitute
(LLP 1133.006 D8 item 4): its implementation reaches the person's
accounts wherever it points.

**The facts.** `prefer extension sign-in.getIdentityCapabilities=…` and
`…getCredentialState=…`, fields laid over the default. The default
applies each target's cells (D3, D7): each provider's `active` and
`passive` and `withPublicKey` as D3's table has them, Apple
false on a Mac build without a profile; `getCredentialState` answers
`authorized`.

**Tickets.** A `get` holds one ticket, whatever its members: passkeys'
ticket, renamed `credential` (§8). A request holds it when admitted: a
passive one when its task makes it, an active one at the press that makes
it. Its `args` name each member: for `identity`, the mode, each
provider's `configURL`, `clientId`, the audience this target's token would
carry (D8), the nonce, the fields, the call's origin, and on the web the
token's form (`relay`) and `web.redirectURI`.

| Answer | Result |
|---|---|
| `type @t <IdentityCredentialJSON>` | the call answers it; the substitute checks that `type` is `identity` and `configURL` one of the request's |
| `tap @t cancel` | `NetworkError` (`NotAllowedError` with a `publicKey` member), `apple.code` `canceled` |
| `tap @t none` (passive) | `NetworkError`, as no account |
| a press while another ceremony holds the queue | as production: natively it waits; on the web `NotAllowedError` `busy`, no ticket |
| a tool-origin or wake-origin request | as production: `person-required`, no ticket |
| a task superseded while its ticket is held | the answer is dropped, and the journal records it (D12) |

**The fixture identity provider.** `packages/sign-in/test/idp.mjs`,
test apparatus of the package as passkeys' `authenticator.mjs` is: given
a ticket's `args`, it signs an ID token with a fixture key it keeps in a
file the drive names, with the provider's real `iss`, the args' audience
and nonce, and a fixture `sub` and email, and wraps it in the provider's
token shape (for Apple, with a fixture `code` and, when asked, a first
authorization's `user`). For the web it answers as the provider would:
it posts Apple's `form_post`, or Google's redirect with a fixture code
that the fixture server exchanges at `idp.mjs`'s token stub, to the
fixture server's return route, takes the handle from the `303`'s
`Location`, and wraps it as `{relay}`, so a web drive goes through the
route. The fixture server trusts that key, and that token stub, under the
agent and only there. The runner knows no identity provider.

**Disclosure.** `state.extensions` lists `sign-in`, its binding per
target, each held request (provider, mode, origin), each ticket's
outcome, never a token. The journal names the provider and the outcome.

**Production:** none of it.

## 10. The consumer: the auth fixture

No app in the repository owns accounts; every app that signs in signs in
to someone else's service (Bluesky through `openAuthSession`, Excord
through Discord's own login). A sign-in serves the app's own server, so
the consumer is exact2's sign-in fixture again, `apps/auth-fixture`, which
LLP 1133.011 §10 extends with passkeys:

- **The server** (`fixture.mjs`) gains `POST /sign-in/nonce` (single-use,
  with an expiry, bound to the client that asked); `/sign-in/return`, the
  web's return route (D3: Apple's `POST`, Google's `GET`, the handle, the
  `303` to the configured callback); and `POST /sign-in/identity`, which
  redeems a handle once or takes a native token, and verifies the token
  by D2's checks: the signature against the provider's keys (the fixture
  key under the agent; Apple's and Google's published keys in the real
  drives), `iss`, `aud` among the audiences the bake printed, `exp`, the
  nonce; for Apple it keeps the first `user.name`, and records the `code`
  as the place a real server would exchange it.
- **The app** gains `auth.apple` and `auth.google` lines, the dependency
  `"@exact/sign-in": "file:../../packages/sign-in"`, and on its sign-in
  screen:
  - `exact-sign-in-button provider="apple"` and `provider="google"`,
    shown by `caps.providers`, each `press` an action;
  - a task that fetches and keeps a nonce when the screen shows; each
    button's action calls `get` with it at once (on the web with
    `web.redirectURI` the fixture server's return route) and, when it
    settles, posts the credential, keeps the session and answers the
    account; a settled request of either outcome fetches a fresh nonce;
  - on Apple and Android, a task that makes a passive `get` with the
    passkey and the target's passive provider, so one sheet offers both;
  - the account screen's name, from the server;
  - `preventSilentAccess` at sign-out.
- **A test** that no answer, kept answer, journal line or `state` field
  holds a token, a code or a return route's handle.

**Acceptance drives,** under the agent on the web, the iOS simulator, the
Android emulator and a macOS build with a profile ("answer" means: run
`idp.mjs` on the ticket's `args` and `type @t` its output):

1. `tap apple-sign-in`; a ticket is held whose `args` carry this target's
   audience; answer with a first authorization: the server verifies and
   the account shows the name. (Android: the button is absent and
   `caps.providers.apple.active` false.)
2. Sign out, `tap apple-sign-in`, answer without `user`: the same account,
   the name kept by the server.
3. `tap google-sign-in`; answer: signed in. On iOS and macOS the ticket's
   `args` show the iOS client's audience.
4. On iOS, macOS and Android, signed out: the passive task holds one
   ticket with a `publicKey` and an `identity` member; answer it with an
   identity credential: signed in. On the web, the same task's `get`
   fails `NotSupportedError` with no ticket, and the app shows both
   buttons.
5. `tap @t cancel` on a held ticket: no error line; the buttons show
   again, with a fresh nonce.
6. `tap apple-sign-in`, leave the screen before answering, then answer: the
   answer is dropped, the journal records it, and the server signed no one
   in (on the web its return route holds an answer that is never
   redeemed).
7. A Contract file that `use`s `credentials.get`: refused,
   `module-name-data-only`. A provider whose `clientId` is not granted:
   `SecurityError` before any ticket. A Mac build without a profile:
   `caps.providers.apple.active` false.
8. Once LLP 1111's door produces a tool origin: a tool's sign-in fails
   `person-required`. Until then the runner's test of the origin rule
   stands in.

**Outside the agent,** against the real Apple and Google clients Charlie
creates (§13 question 6). Google's web client may return to a local
