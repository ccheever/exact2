## 1. What stage 1 fixed, and every package here respects

- **No WidgetKit, SwiftUI or ActivityKit at an ordinary launch.** Only the
  extension links `ExactSnapshot` (a `--widget-gallery` development build
  is the one exception, `Package.swift`); the app reaches `WidgetCenter`
  through the demand-loaded `ExactWidgetReload.framework`, and ActivityKit
  through an arm loaded the same way. `assertCapabilityFrameworks`
  (`link.mjs`) names PhotosUI, AuthenticationServices and SwiftUI today;
  stage 2 adds WidgetKit and ActivityKit for the app executable.
- **The store-change counter.** The app is the one writer
  (`EXACT_WIDGET_WRITER`, `store.rs`): a commit flushes kept answers
  (`flush_kept`), advances `widget-store-generation` by read-add-rename,
  unlocked, and posts a Darwin ping; a refresh captures the counter before
  reading account data and re-checks it before delivery
  (`WidgetTimelineCache`). A second writer is §5 Q1.
- **The ping reloads timelines only.** `WidgetContainer.storeObserver` calls
  `reloadTimelines`; nothing re-asks the running session, and
  `activate_data` returns early once activated. The re-ask (LLP 1126 §0,
  question 6) is WP12.
- **The 900 ms deadline.** A refresh, boot included, has 900 ms from leaving
  the queue (`Timeline.swift`). An intent's handler runs under the same
  deadline from the intent's arrival.
- **The snapshot vocabulary v1** (`SnapshotStyle.swift`, the `snapshot`
  columns of `kernel/tables/schema.json`). Stage 2 adds the button's and
  the toggle's rows and nothing else; placements and complications draw
  from the same vocabulary.
- **`snapshot_viewport`.** The one fact a render reads is its content size,
  through the reserved inject (`snapshot/entry.rs`). A placement's slot and
  a complication's family answer it the same way; the slot is the identity
  (D9), never a value the author switches on.
- **The iOS 27 trap.** An interpolated `configurationDisplayName` traps the
  extension while iOS loads its bundle (`_assertionFailure` under
  `WidgetBodyAccessor.updateBody`) and the widgets never appear in Add
  Widget. Every string the bake writes into generated Swift is a literal
  the manifest has checked (`manifest/widgets.rs`); the activity
  configuration and the stage 3 bundles keep that rule.

Two stage-0 facts bound stage 2: `simctl push` refuses a Live Activity
update (`UNErrorDomain 1401`), so the push gate runs on a device against
real APNs; and the expanded Island's pixels did not capture on the simulator
in three tries though its accessibility tree did (LLP 1126.000 §1.1).

**ActivityKit's limits**, from [Displaying live data](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)
and [push updates](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications):
static and dynamic data together under 4 KB, pushes included; active for
eight hours, then on the Lock Screen up to four more; an hourly push budget
that priority-5 pushes do not count against, throttled past it unless
`NSSupportsLiveActivitiesFrequentUpdates` is set and the person has not
turned frequent updates off; `stale-date` makes the system's `isStale`;
`dismissal-date` bounds the Lock Screen's four hours; the system decodes the
state with default JSON strategies. `NSSupportsLiveActivities` on the app
enables all of it.

## 2. Stage 2's work packages

Stage 2 ships Live Activities and interactive widgets for Interview (an AI
answer being written, advanced by push; an upvote or "mark read" as a
widget's intent) with Caltrain as the in-tree fixture (a departure activity
the app starts, updates and ends; a service-alert activity, so two kinds run
at once; a favourite-station toggle). Each package lands on its own,
reviewed blind by two families.

### WP8 — Activity entries, the envelope and the bake (D2, D9)

- `app.json` takes `live_activities` in place of stage 1's reservation: kind,
  root component, state shape, preview state, optional `title` and
  `description` (the label rule), `push: true` for an entry a server
  advances and `frequent: true` for one that needs the frequent-update
  budget. The root's placements are D9's named slots, one component:
  `lockScreen`, `compactLeading`, `compactTrailing`, `minimal`, and
  `expanded`'s `leading`, `trailing`, `center` and `bottom` (Apple's
  `DynamicIslandExpandedRegion` positions). Each slot is laid out on its own
  at the width the system gives that region, its height
  `fit_content_height`, reading `snapshot_viewport` for that slot; one
  session per activity, not per slot. The state arrives as a props slot
  (`snapshot_state`, found by name as `snapshot_props` is); no refresh
  function exists, and the render stays read-only.
- The envelope: one Swift `ActivityAttributes` for every Exact activity
  (kind, the generation digest it was started under, the state shape's
  digest), whose `ContentState` is the digest and the state as JSON. The bake
  emits the shape's TypeScript type and JSON Schema
  (`<out>/activities/<kind>.schema.json`), and refuses a preview state whose
  encoded attributes and state exceed 4 KB, naming the bytes; the sends
  refuse an oversized state at runtime the same way.
- Shapes of alive activities (D9): stage 1 keeps every published generation
  (`WidgetContainer.pin` reads only `current`); an activity's attributes
  name its own, the extension renders from that generation, and a
  generation is reclaimable only while no alive activity names it. A state
  the plan cannot decode renders the last decodable state the extension
  kept for that id (a per-id file in the group's cache, as the timeline
  cache keeps) in the driver's own outdated presentation (`isStale` is the
  system's, from `stale-date`). Not promised: a last good state when none
  was ever kept (the placeholder shows), and anything across a
  compatibility-changing binary update (§5 Q6).
- Done when Caltrain's two activities bake to plans with every slot, a slot
  that reads the clock, navigates or takes input fails with stage 1's
  edits (a committing handler is WP11's), an unknown key and an oversized
  preview each fail with their edit, and the schema validates the preview
  (tests in `contract/cli`). Depends on nothing in flight.

### WP9 — Start, update and end from the app; the update token (D9)

- Three sends, baked into the app's plan on every host: start (kind, state;
  answers an id), update (id, state, optional alert and stale date), end
  (id, final state, dismissal policy). The Apple arm performs them; every
  other host refuses at runtime as `commands.rs` refuses a command it does
  not link ("… is not linked into this artifact"). Caltrain builds and runs
  everywhere, as today.
- The arm (`libexact_activity.dylib`, wrapped as the reload arm is) loads at
  the first send and at the first demand of the reserved source
  `exactActivities()` (§5 Q2), then enumerates `Activity.activities` and
  subscribes `activityUpdates`, each activity's `pushTokenUpdates` (the
  first token arrives asynchronously, and rotates) and
  `activityStateUpdates`; the source lists id, kind, state, `activityState`
  and token, plus `frequentPushesEnabled`, and answers an empty list on
  every host without ActivityKit, so a shared data module runs unchanged.
  The data module sends tokens to its own backend; exact2 sends nothing and
  relays nothing (LLP 1030.000 D6).
- Packaging (WP13 writes it): `NSSupportsLiveActivities`, `aps-environment`
  for `push: true`, `NSSupportsLiveActivitiesFrequentUpdates` for
  `frequent: true`. The refusals by their controls: no reader of
  `pushToStartTokenUpdates`, no `registerForRemoteNotifications`, no
  `remote-notification` background mode, no `app.json` key for either; an
  async-lane test asserts the symbols and plist keys absent from the app
  and its extension.
- Done when the agent drives Caltrain on a simulator (`tap start-activity`,
  `tap delay-train`, `tap end-activity`) and `state` shows the activity's
  state change after the explicit update, not a ticking `time`; relaunching
  the app with an activity alive lists it with its token without a send;
  and Interview, on Charlie's iPhone, reports a token its backend accepts
  and a token rotation after a relaunch. Depends on WP8, WP13. Needs
  Charlie: the App ID's Push Notifications capability; an APNs key (`.p8`)
  in Interview's backend, never in either repository.

### WP11 — Interactive widgets: the generic intent (D7)

- The profile admits a `button` or `toggle` (`type="checkbox"`,
  `role="switch"`) whose handler commits a mutation or a persisted write and
  neither navigates nor takes input; `snapshot-effect` stays the render's
  edit, `snapshot-handler` narrows to those two refusals. The driver emits
  `Button(intent:)` and `Toggle(isOn:intent:)` with one generic intent
  (`ExactIntent`), generated once: the kind, the action name, the node's
  stable key (the row key path, not a node id, so a repeated row's action
  survives a fresh boot), its arguments, a toggle's new Boolean, and the
  plan's digest.
- Execution: a headless session boots the entry's plan from its generation,
  re-finds the node by key, and dispatches a press or a `change` with the
  Boolean (`HeadlessSession` gains `change`; `press` dispatches a press
  only). The commit is published, through Q1's transaction, before
  `perform` returns, so the system's guaranteed reload reads it; a digest
  the installed plan does not know is refused without running anything.
  The process that performs a widget's intent is §5 Q1; the executor is
  one, whichever process hosts it, and WP14's gallery tap invokes it.
- A Live Activity control (the expanded and Lock Screen slots, where Apple
  admits them) is a `LiveActivityIntent`, performed in the app's process
  whatever Q1 decides, since the sends are the app's (Apple: "the system
  launches your app process without opening the app"). Its intent carries
  the activity's id; the handler reads `snapshot_activity` (the id and the
  current state, a reserved inject as `snapshot_viewport` is) and, after
  its commit, may call WP9's update or end with that id. A Live Activity has
  no timeline reload: a handler that commits and sends nothing changes
  nothing visible, and the bake says so.
- Done when Caltrain's favourite toggle flips on the Home Screen with the
  app not running and with it running, on an iOS 17 runtime and on iOS 27,
  with the archived intent discovered, its parameters round-tripped and the
  performing process recorded in each run; a control on one of two alive
  instances of Caltrain's departure activity changes that instance's
  visible state and not the other's; and Q1's acceptance list passes.
  Depends on WP9, WP12, WP13, the ceiling reading and Q1.

## 5. Open questions, each with a recommendation

1. **Which process performs a widget's intent (WP11).** Charlie's, because
   the accepted RFC has answered it: D7 says the intent "runs the handler
   in the extension, commits, and reloads the surface"; D8 that "an intent
   commits in the extension while the app may be running" and "the store's
   writes stay transactional across processes". Option B keeps those
   sentences; option A amends them.
   Apple ([Adding interactivity](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities)):
   "By default, the system runs the app intent in the same process as the
   widget extension", in the background, on every iOS since 17; it runs in
   the app's process if it conforms to `LiveActivityIntent` (iOS 17+, not
   macOS; "launches your app process without opening the app"),
   `AudioPlaybackIntent` or `ForegroundContinuableIntent`, or if
   `openAppWhenRun` is true (then the app opens; deprecated at 26, and an
   error when set true inside an extension). On iOS 26 `supportedModes =
   [.background]` on an intent in the app target launches the app in the
   background. No page documents that launch's time or memory limit.
   *The transaction, a prerequisite under either option.* Stage 1's write
   path is last-write-wins per key (`Platform::write`: a persisted state
   now, a kept answer on a private thread, the counter after
   `flush_kept`), so two upvotes in flight can lose one even in one
   process. Either option builds: fresh reads or conflict detection by
   revision from the session's snapshot read through publication;
   coordination with every active session (WP12's re-ask); one atomic
   publication of the write set and its revision (staged, one rename);
   cancellation before publication, so a deadline leaves nothing; and the
   per-key KV restructured as that needs.
   - *A, the app's process* (`LiveActivityIntent` on 17–25, `supportedModes`
     on 26): one writer process. Costs: a background app launch on a cold
     tap, booting no presenter, measured on the 13 Pro Max; on the Mac,
     where `LiveActivityIntent` does not exist, intents become links until
     macOS 26 (D7's "act without opening the app" given up on macOS 14–25);
     if the cold launch misses D8's one-second line, the successor is B or
     a `widgetURL`; and the amendment of D7 and D8.
   - *B, the extension's process:* D7, D8 and §1.4's measured extension
     budget hold. Costs: the extension's boot endowed with the group store
     for writing (`boot_entry` endows nothing; stage 1's refresh reads
     through links); the lock in the group, held from the snapshot read
     through `flush_kept` and the counter, taken by the app per transaction
     too; the extension publishing the counter and the ping.
   - *C, a journal the app applies:* rejected by both reviews; the reload
     shows what the store does not hold, and the app may not be running.
   The acceptance, either way: two intents in flight with an app write
   (none lost, the counter moved once per commit), a timeout with no
   partial write, a cold process, a repeated-row action, a switch's Boolean
   change, and the performing process recorded.
   *Recommendation:* B, at 80%. With the transaction owed either way, A
   buys one writer process at the price of an amendment, the Mac, and a
   cold launch nobody has measured; B's own cost is a writing endowment
   where stage 1 already reads. Rejected in part from r1: "set
   `supportedModes` to background on iOS 18" — the property is iOS 26; but
   an extension-only intent needs no mode, since it runs in the background
   on every iOS since 17, and `openAppWhenRun`'s error is for setting it
   true there. r2's note that B had "no documented background mode before
   26" was wrong and is withdrawn.
   *Decided (supervisor, 2026-10-18):* B, which keeps D7 and D8 as
   accepted. Charlie may overrule it in favour of A's amendment.

   untried. *Recommendation:* the restricted access group with profiles,

   account entries, as a locked phone does.
   Rejected from r1's reviews: "macOS 15 allows a `group.` container only

6. **An alive activity across a compatibility-changing binary update
   (WP8).** `WidgetContainer.pin` refuses a generation of another cohort
   (line 40), rightly: the new binary's plan format or kernel schema may
   differ, so keeping the old directory gives no decoder for it. D9's
   promise ("the app keeps the shape of every activity it still has
   alive") holds within a cohort, where a delivery keeps the old generation
   and the extension renders from it; across cohorts it cannot be kept by
   rendering. Options: (a) the extension shows the activity's placeholder
   in the outdated presentation until the app runs, and the app, at its
   first launch in the new cohort, ends every activity of the old one and
   restarts those whose data it still holds; (b) the extension carries the
   previous cohort's runtime beside its own, refused by the budget.
   *Recommendation:* (a), at 85%, as an amendment to D9's fallback
   sentence; Charlie's because it amends an accepted decision. WP15 holds
   the acceptance.
