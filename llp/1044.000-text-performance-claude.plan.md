## 1. Decision

Measured on one M5 MacBook Air at 60 Hz, 2026-09-21 (§3): **ordinary reading
already ties Legend** — trackpad at 900 and 3,600 pt/s, wheel and reversals are
within noise — and Exact is far ahead on documents Legend cannot handle: a 1 MiB
table (52.7 fps against 2.1), a 1 MiB code block (59.9 against 22.3), thousands
of tiny blocks (55.4 against 18.3, and Legend blanks). Exact never showed a
blank viewport; Legend does after jumps and in fast flings.

Exact loses, or fails outright, in eight places. Each has a measured cause:

| # | Where | Measured | Cause |
|---|---|---|---|
| L1 | Dense inline styling | 37–42 fps against Legend's 59.7; the same text without markup, 60.0 | every inline run is a batch op, a JSON dictionary and a `NodeView`; 32,885 native views for one 4,096-repetition paragraph (1044.001 §4.3) |
| L2 | One giant block: resize and open | resize of a 1 MiB paragraph 3.6 fps, of a 1 MiB code block 6.2 fps (Legend 56); a 4 MiB paragraph 2.2 s to open, 1.9 s per width (1044.001 §4.2) | the whole paragraph is shaped, laid out and indexed on the main thread per width |
| L3 | An overflowing unbreakable line | a 64 KiB word renders **nothing** | the worker raster is sized to the line's full ink width, the surface cannot be made, and nothing falls back to `draw` |
| L4 | Fast flings, 12,000 pt/s | 50.6–58.8 fps with load, against Legend's 58.5–59.8 and a stock `NSTextView`'s 56.4 | row construction near the frame under a contended CPU; an unlimited synchronous fill when the pump falls behind |
| L5 | Live resize of an ordinary document | 55.0 fps against 58.8 | every visible paragraph re-rasterized whole, serially, on the main thread, per width |
| L6 | Memory | 80 / 117 MB (opened / after ten jumps) against 62 / 80 | 39 whole-paragraph BGRA rasters (42 MB) and twice Legend's heap |
| L7 | Malformed inline Markdown | 64 KiB of unmatched `[x` parses in 0.45–3.6 s (1044.001 §4.6) | each unmatched opener rescans the rest of the paragraph |
| L8 | Application size | one text edit in a 50,000-node tree lays out in ~52 ms, 10,000 nodes ~11 ms (1044.001 §4.5) | layout and publication walk every live descendant |

And two hosts have the pre-repair shape: UIKit fills the whole window inside the
scroll callback and paints text on the main thread; the web forces a layout per
scroll event in its list sync.

**The end state (§5): text is data until it is pixels, and the frame never
waits for it.** A paragraph crosses every boundary as one value; its runs are
never objects; it is prepared off the main thread and ahead of need; what the
main thread does for it per frame is bounded by what is visible, never by the
paragraph or the document; nothing that runs per batch visits more than the
batch touched; and every host has the same shape.

**The order (§6)**, by what a person feels and what the evidence supports:
S1 paragraphs as one presenter (L1, part of L4 and L6); S2 correctness and
pathology fixes (L3, L7); S3 bounded visible work — fill, shape-ahead, resize and
giant blocks (L2, L4, L5); S4 memory (L6); S5 iOS; S6 application-size locality
(L8); S7 the web; S8 the batch format, only if S1 leaves it expensive; S9 one
collection path. **If only one slice is built, build S1** — both independent
plans chose it.

## 3. Where Exact stands

### 3.1 The probe

A black-box probe (`scrollbench`, kept out of the repository, §8) launches either
app with the same file, places a 900×700 window through Accessibility, and drives
it through the **window server**: `CGEvent` scroll input posted at the HID tap
with the pointer over the window, so AppKit's responsive scrolling engages as it
does under a finger; the pointer and the frontmost app are restored after each
trial. It records the window with ScreenCaptureKit and counts only frames whose
content changed, estimating each frame's scroll shift from its ink profile and
the longest band with no ink. Trackpad input is phased with momentum; wheel input
is unphased; jumps set the scroller through Accessibility; resize sets the width
through Accessibility at 60 steps a second. Exact and Legend alternate trial by
trial under one timing lock shared with the other lane; a trial is rejected if a
human touched the machine. **All numbers are 60 Hz presented frames on this
machine; none is a 120 Hz claim.** Exact is `9dbaded0`; Legend Markdown is
`2b7b91d9`, ARM64 Release with the lane's one build-only edit. The corpus is the
40 largest `llp/*.md` (2,556,440 bytes); generated documents use seed 1044.

## 4. Why

### 4.1 Rich text is per-run construction (L1)

Inside the fill pump on the dense document (710 main-thread samples), Swift
`Presenter.apply` is 49% — dynamic casts of `[String: Any]` 18%,
`NavigationHost.sync` 15%, JSON parse and bridging 14%, dictionary lookups 11% —
and Rust `exact_list` 27%. The markup-free twin prices the runs: per two-row fill
slice, **plain 1.18 ms, dense 5.64 ms**; `apply` 0.57 against 2.91; `exact_list`
0.55 against 2.43. Inside `exact_list`, the Rust share is mostly CoreText through
the measure callback — building the sixty-run attributed string and
`CTTypesetterCreateWithAttributedString` — plus the runner creating an instance
per run. Every run is a `create` op decoded by `JSONSerialization`
(`Bridge.swift:51-56`), becomes a `NodeView` — an `NSView`, never mounted
(`NodeText.swift:24-34`) — read back only to rebuild the `Run` the Rust host
already built for measurement (`NodeText.swift:82-113`), and is visited by
`NavigationHost.sync`'s loop over every view after every batch
(`NavigationMac.swift:28-43`). Skipping that loop outright — an upper bound —
gained 1.9 fps on dense text and 3.9 on the table: worth fixing, not sufficient.
iOS runs three such loops per batch (`IOS/PresenterIOS.swift:592-594`).

### 4.2 Giant blocks are whole-paragraph work on the main thread (L2)

1044.001 §4.2: a 1 MiB paragraph's cold layout is 60 ms and a new width 24 ms in
the bare engine, and the reader pays about 0.5 s per width with its runner,
kernel, first-paint ink index and raster included; 4 MiB costs 2.2 s to open.
Rasters above 4,096 points fall back to strips (`TextRasterMac.swift:34`), which
avoids a giant bitmap but not a giant layout. Legend reflows its 1 MiB code block
at 56 fps; Exact wraps code (`white-space: pre-wrap`,
`apps/markdown/app.contract:207`) and re-breaks all of it per width.

### 4.3 The raster path has no fallback (L3)

`TextRasterizer.render` sizes its surface to the union of every line's ink bounds
(`TextRasterMac.swift:115-147`). A line that overflows its box by half a million
points asks for a surface no IOSurface can be; `render` returns nil,
`showTextRaster` ignores the nil (`:201-204`), the paragraph still claims
`rastersText`, and `draw` never runs. The pump asks again on its next slice.

### 4.4 Fast flings and resize are headroom (L4, L5)

At 12,000 pt/s the main thread is busy 6% of the time and no signposted interval
exceeds 8.3 ms, yet the Hitches instrument records long app updates with few
samples inside them: the process is waiting on AppKit's main-thread synchronizer
and the render server while other processes hold the CPU. The same build
presented 58.8 fps at load 6 and 50.6 at 13; Legend 59.8 and 58.5 (1044 F9).
Worker rasterization helps — turning it off gave 56.6 against 58.3–59.3 — and
stays. When the pump's two-rows-per-slice falls behind a fling (about 100 rows a
second), `scrolled()` calls an unlimited `syncLists()` (`PresenterMac.swift:353-369`)
that builds the whole window inside the synchronizer. During a live resize,
synchronous `TextRasterizer.render` is 29% of all main-thread samples: every
visible paragraph re-rendered whole, serially, per width, because the raster key
includes the paragraph's size (`TextRasterMac.swift:67-70`).

### 4.5 Memory (L6)

`footprint` after ten jumps: Exact 117 MB — heap 60 MB, IOSurface 42 MB in 39
regions; Legend 80 MB — heap 30, IOSurface 19 in 10. Exact keeps a whole
paragraph's BGRA raster for every paragraph within 1,600 points of the scrollport
(`PresenterMac.swift:263`), for text that is almost always one colour. 1044.001
§4.2 adds that text residency counts entries, not bytes: a 4 MiB paragraph's
accounted cold admission reached 366 MiB against a 64 MiB target.

### 4.6 Parser and application size (L7, L8)

Unmatched `[` and `<` each search the remaining suffix
(`apps/markdown/parse/src/inline.rs:219, 241, 353`); the parse runs on the data
worker, so it delays opening rather than scrolling, and a stale parse still
occupies the lane. Kernel layout of a fixed-size edit grows with the live tree
because publication walks every descendant (1044.001 §4.5).

## 5. The end state

1. **A paragraph is one presenter and one value.** The kernel keeps inline `text`
   children — CSS inline semantics, events and identity are unchanged — but the
   Apple host sends a paragraph as one op carrying its runs (text, resolved
   style, `href`, node id), and the presenter keeps a run table for links,
   selection, accessibility and the agent's `tree`. No native object per textual
   run. Genuine inline controls remain controls.
2. **Prepared text, one geometry.** A paragraph is shaped once per metric
   identity (content revision, metric styles, font catalog, direction, wrapping),
   off the main thread and ahead of need; measuring, painting, hit-testing and a
   colour change all read that geometry. CoreText objects stay with the worker
   that made them; the main thread receives line ranges, extents and pixels.
3. **The main thread's per-frame text work is bounded by what is visible.** The
   pump fills visible rows first, then a directional band scaled by velocity,
   under a time budget, never alternating away from a shrinking lead. A
   synchronous fill during a user scroll builds only rows that intersect the
   scrollport. A giant block is presented a viewport at a time: whole-paragraph
   preparation may be O(bytes) on a worker; glyphs, ink index and pixels
   materialize for the viewport. A resize keeps the accepted result until the
   new width's visible text is ready, and never rasterizes serially on the main
   thread.
4. **Every raster has a fallback and a budget.** Surfaces are clipped to what can
   be seen; when one cannot be made, the view draws. Rasters are kept about a
   viewport around the scrollport, single-colour text as an 8-bit coverage mask,
   and every text cache is bounded in bytes by the residency that owns it.
5. **Nothing per batch visits more than the batch touched**, and layout
   publication visits dirty subtrees and proven containment boundaries, not every
   descendant.
6. **Parsing is linear** in the input and cancellable when superseded.
7. **Every host has the same shape.** iOS gets the pump, the budget and worker
   rasters; the web reads row geometry from `ResizeObserver` entries and fills
   from `requestAnimationFrame` under a budget. The web's giant-paragraph cliff is
   the browser's own (1044.001 §4.4) and is attacked only through the bounded
   experiment in S7.
8. **The engine stays on the main thread** until a physical 120 Hz run under load
   shows main-thread misses after S1–S7 (LLP 1022 stays parked until then).

What stays O(N) on purpose: the source and parsed document, complete parse,
Unicode and bidi preparation, the initial key and height index, full-document
copy and search. None of it may run per frame, per scroll tick, per cache hit or
per intermediate width.

## 6. The path

Each slice ends with the five checks passing on the integrated commit and its
rows of §7 measured on the probe against Legend, interleaved, on this machine.
Three fix rounds per slice, then stop and bring the trade to Charlie
([RULES](../rules/RULES.md)).

**S1 — one presenter per paragraph** (L1; part of L4, L6). Host: one paragraph
op carrying the run array for a text node whose children are inline text
(`host/apple/src/host.rs` `commit_into`/`create`, `batch.rs`); no per-run
`create`/`props`/`style` ops. Presenter: `Spec` built from the run array
(`NodeText.swift`), a run table for links, selection and accessibility
(`TextSelectionMac.swift`, iOS equivalents), the agent's `tree` from the run
table; no `NodeView` per textual run on either Apple host. `NavigationHost.sync`
visits only the nodes a batch touched and subtrees whose route inertness changed;
iOS's `segments`/`menus`/`swipeActions` passes read the chrome index the Mac
keeps (`PresenterMac.swift:139-182`). A colour-only change does no line breaking.
**Done when:** the 4,096-repetition fixture mounts ≤ 150 native views (32,885
today); the dense document's `apply` per fill slice is within 1.5× of its plain
twin's; dense inline scrolls at ≥ Legend's fps with hitch time ≤ Legend's on
the probe; the corpus does not regress; selection, copy, link and agent fixtures
pass unchanged.

**S2 — correctness and pathology fixes** (L3, L7). Clip a raster's surface to the
node's box plus its authored overflow allowance and fall back to `draw` whenever a
surface cannot be made (`TextRasterMac.swift`). Make delimiter matching linear:
brackets, autolinks and backtick runs keep their failure information instead of
rescanning the suffix (`apps/markdown/parse/src/inline.rs`), with the existing
parser tests unchanged; make a superseded open cancellable at scan checkpoints
(`apps/markdown/data/src/lib.rs`). **Done when:** 64 KiB of one unbreakable word
shows its first line, clipped, as a browser does; the malformed 8→64 KiB fixtures
grow ≤ 2.5× per doubling and 64 KiB parses in ≤ 10 ms; the next file after a
superseded parse opens within the ordinary target.

**S3 — bounded visible work** (L2, L4, L5). (a) The pump: a time budget per slice
(4 ms at 60 Hz, 2 at 120), velocity-scaled asymmetric extent in `ListWindow`
(`runner/src/instance/window.rs:371`), and the synchronous path limited to
scrollport rows (`PresenterMac.swift:353-369, 422-449`). (b) Shape-ahead: the
host names the text of rows the next slice will create; the presenter shapes them
on the text workers into the residency's shape cache, so measuring them is a
lookup. (c) Resize: re-break visible paragraphs, rasterize them in parallel on
the workers, keep the accepted raster until the new one is ready. (d) Giant
blocks: extend the existing region service (`RegionService.swift`,
`host/apple/src/content_region/`) to reader paragraphs over a size and run
threshold — preparation on the worker, viewport glyphs and ink, an explicit
pending state that is never shown as content — with its per-glyph-run scan of
authored runs indexed first (`RegionWorkerLayout.swift:111`). **Done when:** the
12,000 pt/s fling and the corpus resize are ≥ Legend's fps with hitch time ≤
Legend's at matched load; no `CTTypesetterCreate*` on the main thread in steady
scrolling (Time Profiler); resizing the 1 MiB paragraph and code block keeps ≥ 55
fps with correct text within 500 ms of the last width; a 4 MiB paragraph shows
its first correct viewport within 500 ms p95; no blank band over 250 points in
any ordinary scenario.

**S4 — memory** (L6). Raster residency about one viewport around the scrollport;
single-colour text as an 8-bit coverage surface tinted by its layer; text caches
charged in bytes — measured-break arrays included — against the residency's
existing target (`TextResidency.swift`, `Text.swift:470`). **Done when:** the
footprint after the ten-jump traversal is ≤ Legend's, with the fling bar still
met.

**S5 — iOS.** Port the pump, budget, shape-ahead and worker rasters to
`PresenterIOS`/`NodeViewIOS`, sharing the platform-neutral parts. **Done when:**
on the simulator a scroll's synchronous report never builds more than the
scrollport (counted); on the attached iPhone 17 Pro Max the reader holds its
refresh rate at 3,600 pt/s — which needs real touch input (§8).

**S6 — application size** (L8). Dirty-subtree layout publication and definite-size
containment boundaries, with conservative propagation for intrinsic, percentage,
baseline, overflow and exclusion dependencies (`kernel/src/layout.rs`,
`host/apple/src/host.rs` emission). **Done when:** 1044.001's probe with unrelated
text behind definite containment costs ≤ 2 ms per edit at 100 through 50,000
nodes, and Caltrain, Markdown and Fieldnotes keep their geometry.

**S7 — the web.** Batch the list sync's reads before its writes and coalesce to
`requestAnimationFrame` (`host/web/glue.js:206-225`); then 1044.001's bounded
giant-paragraph experiment (its slice D) with its three-round stop rule. **Done
when:** a Chrome trace of the reader scrolling shows no forced layout from the
list sync; the giant-paragraph experiment either meets 1044.001 §7.4 or reports
its unsupported cases to Charlie.

**S8 — the batch format**, only if, after S1, JSON decode and dynamic casts are
still over 15% of `apply` on the corpus: a schema-decoded op stream in place of
`JSONSerialization` and `[String: Any]`, schema in `kernel/tables/schema.json`.

**S9 — one collection path.** Move the reader to the shared collection feedback
once selection, full copy, focus pins and nested scrolling match, and delete the
legacy `estimated-item-height` path (1044.001 §7.6).

**S10 — the compact document** (L6), added while S4 ran. The Markdown document's
values share their strings and release the parsed form as they are built
(`apps/markdown/parse/src/value.rs`), with the Contract shapes unchanged.

**S11 — a dense row inside the slice** (L1, L4), added after S3 (e): a report is
indivisible, and a dense row's still cost 4.0 ms p50, 6.5 p95. About a fifth of
its profile samples were bookkeeping: an idle motion engine walking every node per
commit, SipHash and BTree order on node keys. **Done when:** `exact_list` per dense row ≤ 3 ms p95 and the fill slice
≤ 4 ms p95, with no probe scenario regressing.

**S12 — tables of many small cells** (L2, L4), added after measuring 1044.001
§4.7's wide tables on `main`: every visible cell got its own IOSurface on the main
thread, the text cache evicted on every admission once 64,000 cells passed its
4,096 entries, and the scroll callback had to finish the fill. **Done when:** 32
columns × 2,000 rows scroll at ≥ 55 fps (≥ 45 flung); 64- and 256-column tables
resize at ≥ Legend's fps and open no later than Legend.

**S13 — batches read at memory speed** (L1, L4), the rest of S8. S8's typed batch
is still parsed by Foundation's `JSONDecoder`, and each value is tried as a number,
string, bool, array and object in turn. On the dense document decoding cost twice
what applying did (18% of the main thread). A decoder for the batch's own shapes
over the same JSON wire. **Done when:** decoding takes ≤ 20% of today's samples on
the dense document and no probe scenario regresses.

**S14 — small text draws** (L4), added after S12. A raster surface costs an
IOSurface and a render-server registration before a glyph shows, which a table
cell's few glyphs never repay. **Done when:** 32 columns × 2,000 rows scroll at
≥ 55 fps and no other probe scenario or the traversal footprint regresses.

## 8. Not doing, and what it costs

- **No new check, script, registry or benchmark app in the repository.** The
  probe that produced §3 stays out of the tree, as the lane's probes did; it is
  run by the owner of §3's measurements for every slice. 1044.001 §8 asks Charlie
  to approve three small additions to existing diagnostics; that request stands as
  written and nothing here assumes the answer. A 120 Hz iPhone measurement needs
  real touch input — a person, or an XCUITest runner, which would be new
  apparatus and needs Charlie's approval.
- **No runtime-owner thread** (§5 item 8), no parallel layout, no second state
  graph, no new worker pool — the region service and the text-raster workers are
  the text workers, converged.
- **No Pretext-style breaker, runtime font parsing or new shaper** (LLP 1043 §5).
- **No change to Contract or the CSS model.** Code blocks keep
  `white-space: pre-wrap`; an unbreakable word overflows as CSS says; the reader's
  4 MiB admission stays.
