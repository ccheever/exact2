# LLP 1027.000: Explicit time and randomness in data sources

**Type:** RFC
**Status:** Active (implemented 2026-09-04; accepted by Charlie Cheever: "ok. want to go fix all those for me pls?")
**Systems:** Runner (data-source arguments and caching), TypeScript executor, Bake, Web host, Agent API
**Author:** Codex, at Charlie Cheever's request
**Date:** 2026-09-04
**Revised:** 2026-10-28 (D1: an answer's own timers)
**Implementer:** Codex, 2026-09-04
**Related:** LLP 1027 D1a/D4/D6/D10; LLP 1005 §3/§6; LLP 1012 §2; LLP 1018 D4; issues/closed/20260904-data-sources-read-ambient-time.md; rules/RULES.md §Scope

## Summary

The UI clock is controlled, but a TypeScript answer can read the machine's
clock and random generator without declaring either input. Fix that boundary.
The first landing makes time and random seeds ordinary source
arguments and refuses ambient reads in the TypeScript executor, including
module initialization and asynchronous continuations.

Charlie accepted this direction by asking to fix all the described findings
after the explicit-input recommendation on 2026-09-04. It amends LLP 1027
D1a's unimplemented `Date.now` shadow: merely substituting
the runner's clock does not establish the timestamp's meaning, expose a
resource dependency, or settle bake and cache behavior. The native and browser
executor landings and their verification are recorded below; the same boundary
applies to every executor.

## Evidence

On 2026-09-04, a temporary harness compiled the current `js/src/shim.cc`
against the lean Hermes VM selected by `js/build.rs`. It loaded the current
`js/src/prelude.js` as HBC, then this module as HBC, and called the existing
`__exact_call("probe", "[]", "")` entry twice:

```js
globalThis.exact = {
  abi: 1, appId: "probe", grants: "",
  answer() { return { wall: Date.now(), random: Math.random() }; }
};
```

Both calls succeeded. `wall` was an epoch timestamp from the machine and
the two random results differed, although no runner time or random input
was supplied. This proves the native executor/prelude gap; it is not a
measurement of a complete browser TypeScript application. See
`js/src/shim.cc::exact_js_create`, `js/src/prelude.js::__exact_call`, and
`js/src/lib.rs`'s call into the prelude. LLP 1027's stage-3 note already
lists the clock shadow as owed.

## Accepted design

### D1 — Declare the inputs through the existing seam

A time-dependent source takes the time it needs as a numeric argument.
A randomized calculation takes an explicit seed or a previously supplied
random value. Examples are `remaining(deadlineEpochMs, nowEpochMs)` and
`choose(items, seed)`. The source's shape/signature and argument equality
remain the mechanisms the compiler and runner already use.

An application owns any changing clock slot or seed it passes. A timer can
update that slot using the existing task/action model. There is no new
subscription graph, PRNG state inside the executor, timer binding, or agent
operation. A seed-dependent helper is a pure function in the app's data
code; it does not become another app-specific runner stdlib entry.

> **Amended 2026-10-28 (Daehyeon Mun: T1, approved 2026-10-24, reconfirmed
> 2026-10-28): an answer may wait on its own timer.** Inside an
> answer, `setTimeout(fn, ms, ...args)`, `clearTimeout(id)` and
> `AbortSignal.timeout(ms)` are the web's. `setInterval`,
> `requestAnimationFrame`, `requestIdleCallback`, `performance.now()` and
> the reads D3 lists stay refused: a timer measures a delay and reads no
> clock, so time is still an argument and D2 is unchanged.
>
> *Why.* Ported flows wait in the middle of an answer: the T3 Code clone's
> delete waits 180 ms after closing its toast, its bootstrap retries sleep
> between attempts, its recorder races two frames against a timeout, and its
> fetches carry `AbortSignal.timeout`. A gated task (LLP 1092) cannot express
> a wait inside an answer without splitting each flow at its sleep, and the
> recorder's injected timers have no Contract form. The only other way, an
> app-owned native sleep, runs on one platform and outside the agent's clock.
> This reverses the 2026-10-08 ruling under D3 ("module timers remain
> refused"), whose consumer, a debounce, moved to gated tasks. Accepted with
> it: at bake timers fire at once (below); only answers arm them, so
> background work (LLP 1097) refuses one; `setInterval` stays refused.
>
> *Lifetime.* A timer belongs to the answer that armed it: a resource's
> answer, a send, a tool handler. Arming one anywhere else (module
> initialization, a stream's mapper, an overlay, background work, an answer
> that has given its value) refuses. When the answer gives its value, fails
> or is let go, its remaining timers are cleared and their callbacks never
> run.
>
> *Clock.* A timer is due at the runner's clock as its call began plus its
> delay. An answer that awaits only its own timers hands the runner a
> continuation due at the earliest (`Request::due_ms`). The runner keeps it
> back as no I/O (`has_pending` and `clock settle` do not wait on it) until an
> advance reaches it, after the tasks, `then`s and re-asks due at the same
> time, and then hands it to the host, which settles it as any continuation.
> One callback runs a turn, so the microtasks it queues run before the next,
> as a browser runs them between tasks. An answer that also awaits other
> answers' work (a shared fetch) goes to the host as such a wait always has,
> and the advance that reaches its timer releases it (`Request::wake_ms`):
> whichever comes first asks it again. Under the agent, `clock +N` and
> `clock settle` fire it, and a jump lands each released continuation before
> it goes on; on a device, the host's wake for the runner's next deadline
> (`timer_due_ms`) does.
>
> *Fetches.* Natively an answer waits on one thing at a time, and a fetch it
> awaits goes first, so a timer raced against that fetch, or one that calls
> `abort()`, runs after the fetch lands; the journal says so once per
> answer. Making that race real would let an answer resume while its fetch
> is still in flight, which the runner's one-request-per-target model does
> not have. A fetch whose `signal` is an `AbortSignal.timeout` carries the
> time left as its deadline on the host (`exactTimeout`), on real time, and
> the signal aborts with `TimeoutError` when that passes. The web JS target,
> whose answers run in the page, races them for real; its timers are
> entries of the page clock's timers.
>
> *Bake.* There is no clock at bake: each timer fires at once, on a clock
> that moves to its due time, so an answer that waits still compiles. An
> answer that runs more than 1,000 timers there is refused.
>
> *Where.* Hermes (every native host) through the prelude
> (`js/src/binary.js` `timers`) and the runner
> (`runner/src/runner/advance/data_timers.rs`); the wasm web target's module
> realm and worker; the web JS target (`host/web-js/ts-fetch.js`). The Lean
> semantics model Contract, not a data module's time, so `contract-difftest`
> is unaffected.

### D2 — Keep elapsed time and epoch time distinct

Contract's existing `now()` is the runner's elapsed clock. JavaScript
`Date.now()` normally denotes milliseconds since the Unix epoch. Returning
elapsed zero from `Date.now()` would silently mean January 1970.

The caller must pass the domain the source expects; argument names should
say `elapsedMs` or `nowEpochMs`. This proposal adds no wall-clock provider.
An app needing a fresh production UTC timestamp must obtain it as an
explicit host/service input, with its test substitute and refresh policy
specified when that capability is implemented. A fixed epoch in a test
must never become the default production clock accidentally.

### D3 — Refuse ambient reads before any module code executes

Refuse `Date.now()`, zero-argument `new Date()`, callable `Date()`,
`Math.random()`, and `Intl.DateTimeFormat`'s `format`/`formatToParts` with
an omitted or `undefined` timestamp. These Intl defaults also read machine
time. The error names the API and tells the author to pass time or a seed.
Explicit-value date calculations retain their normal
semantics, such as `new Date(epochMs).getUTCHours()`; this is not permission
to rename local-time operations as UTC or to reimplement all of Date.

The restriction applies at module initialization, in `answer`, and after
every `await`, under bake and runtime alike. It covers ordinary aliases,
destructuring, computed property access, and access through the module's
global object. Installing a guard after the app has captured the original
function is too late. A probe must establish the actual boundary; searching
source text for `Date.now` is insufficient.

> **Added 2026-10-05 (the Signal clone: `Date.now()` passed its Bun tests and
> threw on iOS).** The runtime refusal stays the boundary. Every build also
> refuses a *direct* use in a module `app.ts` reaches (`Date.now()`, `Date()`,
> zero-argument `new Date()`, `Math.random()`, `performance.now()` and the
> timers), by file and line with the runtime's words, from the bundler's
> syntax tree (`js/bake/src/typescript.mjs` `ambientRefusals`, in the native
> bake's two compilers and the web build). It is the early warning a Bun
> test cannot give, not the guard: an alias still reaches the runtime's.
> Since 2026-10-28 `setTimeout` is not among the timers it refuses (D1).

On native, install guards in the prelude before evaluating the app. On the
web, supply module-scoped guarded builtins through the module loader and
test the aliases above. Do not patch the page's global Date/Math: host
deadlines, other scripts, and iframe guests keep their own environment.
If the browser wrapper cannot mediate a form, refuse it at the authoring
boundary or report that executor unsupported; do not claim parity from a
Hermes-only test. This is an authoring contract for trusted app modules,
not a claim that a same-page JavaScript wrapper sandboxes hostile code.

**Failure parity (Charlie, 2026-10-08; implemented 2026-10-13):** module
timers remain refused (reversed for an answer's own timers on 2026-10-28:
D1). In a running session, a TypeScript answer that throws,
rejects, or misses its result shape fails its resource and keeps the last value
or declared placeholder. The input or action that asked it commits;
`failure(resource).code` is `error` for the module's own error and preserves a
classified failure it lets through. A synchronous or queued send that fails
ends unsent, keeps its previous result, and runs no `then`; the journal names
the failure. An older reply cannot overwrite it, and the next queued send can
run. Module initialization, bake, replacement validation and an unknown source
still refuse. With no previous value or placeholder, a resource cannot settle.

### D4 — Bake, caching, retries, and reload keep their existing meaning

Constant arguments may still be baked. An ambient read fails visibly during
bake; catching that error must not turn an implicit machine clock into a
compiled value. A dynamic time/seed argument uses the existing resource
argument comparison to request a new answer. Advancing the clock alone
does not implicitly subscribe every resource to every frame.

After `await`, the answer still has its invocation's explicit arguments.
An answer requiring newer time must be requested with newer arguments;
settlement must not substitute whichever session time happens to be current.
Stale-ticket refusal, carried slots, and matching-resource carry continue to
work without a hidden random stream that must be rewound or migrated.

Determinism is conditional on the supplied inputs and external outcomes.
This does not freeze network replies, control an iframe's clock (LLP 1020
D4), or sandbox trusted Rust providers. Rust providers follow the same
explicit-input contract, but ordinary native Rust can still call OS APIs.
Locale/timezone-dependent formatting needs explicit policy separately;
this change alone does not prove it identical across hosts. Seeds for
repeatable UI calculations do not replace secure entropy for credentials.

## Alternative: runner-backed ambient APIs

Keeping `Date.now()` and `Math.random()` is more convenient for existing
libraries. A correct version needs an explicit epoch anchor, logical time
and entropy supplied before module initialization, dependency tracking for
reads, nonconstant bake behavior, and specified ownership across concurrent
async answers, retries, and reloads. A single mutable global context can
otherwise let one continuation read another call's time or random stream.

That remains a viable alternative to this amendment. The recommendation is
explicit arguments first because they reuse the existing source signatures,
cache keys, and state ownership. Choose the ambient API design when a named
library or application makes its ergonomic benefit worth that machinery.

## Landing and verification

1. Add meaningful executor regressions using the existing JS fixture/toolchain:
   ambient reads refuse in initialization, an answer, and after a fulfilled
   fetch; explicit time/seed computations succeed and repeat identically.
2. Install guards before the module. Prove normal aliases cannot bypass them;
   keep explicit UTC date arithmetic working. Run bake and direct calls.
3. Drive a runner fixture: hold time/seed fixed, refresh, advance a declared
   clock argument, and reload with carry. Check values, request counts, and
   compiled-value eligibility, including stale async completion.
4. Hold every advertised executor to the same fixture. Record unsupported
   targets honestly; the native engine currently only links on macOS.
5. Rerun relevant existing tests, the five checks, and the existing metrics
   for boot/update/edit costs. Add no check, benchmark registry, or runtime
   feature flag. Update LLP 1027's as-built notes only after the landing.

## As built — 2026-09-04

`js/src/prelude.js` guards the module's private Hermes globals before app
bytecode runs. `Date.now` and `Math.random` refuse; a constructor proxy
refuses zero-argument construction and callable Date, including calls with
arguments (which normally still read the current time). Explicit-value
construction delegates to Hermes itself. The prototype's constructor also
points at the guard, so `new Date(0).constructor` cannot recover the original.
Guarded properties cannot be overwritten or removed. No host-page builtin,
runner API, source signature, plan format, or seed state was added.

Review found a further native-time path in `Intl.DateTimeFormat`. Its
prototype's bound `format` getter and `formatToParts` method are now guarded
before the app loads, including aliases captured during initialization.
Omitted and `undefined` timestamps refuse. Explicit timestamps, including
zero, still delegate to Hermes. The bound format function retains its
identity across getter reads. This guards default clock reads; it does not
establish a new locale/timezone policy or add Intl to engines without it.

`js/tests/inputs.rs` executes the real Rolldown → HBC → lean Hermes path:

- Twenty-five forms, including captured/destructured aliases, computed global
  names, bound calls and constructors, and `Reflect.construct`, refuse at
  module initialization, in ordinary answers and after a fulfilled fetch.
  An uncaught initialization read refuses module loading. A caught refusal
  exposes its diagnostic, never the machine's clock or entropy. The Intl
  cases include omitted/undefined values, bound aliases, a captured format
  getter and the prototype parts method.
- The same ambient answers fail during `contract::bake`; explicit boot
  inputs produce identical encoded plans and compiled values. Date identity,
  explicit UTC dates, parse/UTC operations and explicit `undefined` retain
  their native behavior. Explicit Intl formatting and parts for timestamps
  zero, positive and negative work with an explicit locale and UTC zone.
- Fixed explicit inputs repeat across calls and unload/load. Interleaved
  async calls settle in reverse order with their original arguments.
- A real compiled Contract and runner preserve values and call counts under
  refresh, clock advance without a subscription, explicit time/seed changes,
  matching-resource reload carry, and stale async replies including reload.

`cargo test -p exact-js` passes all 18 integration tests on macOS arm64 with
the configured lean Hermes and Rolldown. The six new tests complete in
roughly four seconds including the Intl regressions on this machine; that is
test execution, not an application
startup measurement. No pre-pixel path was changed.

**Executor scope (updated Codex, 2026-09-07):** native Hermes executes on macOS
and provisioned iOS targets; `js/build.rs` produces a named refusing stub for

in a private iframe realm after first paint. Real Chrome now runs all 25 forms

sweep now passes all 25 forms at initialization, in direct answers and after

**The web build (2026-10-04, x2apps data lane):** the JS target bundles
`app.ts` into the page, where the guards above never ran, so an app that read
the clock worked on the web and failed on a device. Its bundler now injects
module-scoped `Date`, `Math`, `Intl`, timers and `performance`
(`host/web-js/ts-fetch.js`) into the app's own modules, as D3 asks, and the
page's builtins stay untouched; `host/web/request-refusal.test.mjs` runs this
document's alias fixture through them. Hermes and the module realms now refuse
timers and `performance.now()` by name too.
