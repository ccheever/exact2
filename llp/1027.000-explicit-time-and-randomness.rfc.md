# LLP 1027.000: Explicit time and randomness in data sources

**Type:** RFC
**Status:** Draft
**Systems:** Runner (data-source arguments and caching), TypeScript executor, Bake, Web host, Agent API
**Author:** Codex, at Charlie Cheever's request
**Date:** 2026-09-04
**Revised:** 2026-09-04
**Related:** LLP 1027 D1a/D4/D6/D10; LLP 1005 §3/§6; LLP 1012 §2; LLP 1018 D4; issues/20260904-data-sources-read-ambient-time.md; rules/RULES.md §Scope

## Summary

The UI clock is controlled, but a TypeScript answer can read the machine's
clock and random generator without declaring either input. Fix that boundary.
The recommended first landing makes time and random seeds ordinary source
arguments and refuses ambient reads in the TypeScript executor, including
module initialization and asynchronous continuations.

This is a **proposal**, not an implementation or an acceptance. It proposes
amending LLP 1027 D1a's unimplemented `Date.now` shadow: merely substituting
the runner's clock does not establish the timestamp's meaning, expose a
resource dependency, or settle bake and cache behavior. D1a remains the
accepted direction until this amendment is accepted. The associated issue
tracks the defect whichever solution is chosen.

## Evidence

On 2026-09-04, a temporary harness compiled the current `js/src/shim.cc`
against the lean Hermes VM selected by `js/build.rs`. It loaded the current
`js/src/prelude.js` as HBC, then this module as HBC, and called the existing
`__exact_call("probe", "[]", "")` entry twice:

```js
globalThis.exact = {
  abi: 1, appId: "probe", grants: "",
  answer() { return { wall: Date.now(), random: Math.random() }; }
};
```

Both calls succeeded. `wall` was an epoch timestamp from the machine and
the two random results differed, although no runner time or random input
was supplied. This proves the native executor/prelude gap; it is not a
measurement of a complete browser TypeScript application. See
`js/src/shim.cc::exact_js_create`, `js/src/prelude.js::__exact_call`, and
`js/src/lib.rs`'s call into the prelude. LLP 1027's stage-3 note already
lists the clock shadow as owed.

## Proposed design

### D1 — Declare the inputs through the existing seam

A time-dependent source takes the time it needs as a numeric argument.
A randomized calculation takes an explicit seed or a previously supplied
random value. Examples are `remaining(deadlineEpochMs, nowEpochMs)` and
`choose(items, seed)`. The source's shape/signature and argument equality
remain the mechanisms the compiler and runner already use.

An application owns any changing clock slot or seed it passes. A timer can
update that slot using the existing task/action model. There is no new
subscription graph, PRNG state inside the executor, timer binding, or agent
operation. A seed-dependent helper is a pure function in the app's data
code; it does not become another app-specific runner stdlib entry.

### D2 — Keep elapsed time and epoch time distinct

Contract's existing `now()` is the runner's elapsed clock. JavaScript
`Date.now()` normally denotes milliseconds since the Unix epoch. Returning
elapsed zero from `Date.now()` would silently mean January 1970.

The caller must pass the domain the source expects; argument names should
say `elapsedMs` or `nowEpochMs`. This proposal adds no wall-clock provider.
An app needing a fresh production UTC timestamp must obtain it as an
explicit host/service input, with its test substitute and refresh policy
specified when that capability is implemented. A fixed epoch in a test
must never become the default production clock accidentally.

### D3 — Refuse ambient reads before any module code executes

Refuse `Date.now()`, zero-argument `new Date()`, callable `Date()`, and
`Math.random()` with an error naming the API and telling the author to pass
time or a seed. Explicit-value date calculations retain their normal
semantics, such as `new Date(epochMs).getUTCHours()`; this is not permission
to rename local-time operations as UTC or to reimplement all of Date.

The restriction applies at module initialization, in `answer`, and after
every `await`, under bake and runtime alike. It covers ordinary aliases,
destructuring, computed property access, and access through the module's
global object. Installing a guard after the app has captured the original
function is too late. A probe must establish the actual boundary; searching
source text for `Date.now` is insufficient.

On native, install guards in the prelude before evaluating the app. On the
web, supply module-scoped guarded builtins through the module loader and
test the aliases above. Do not patch the page's global Date/Math: host
deadlines, other scripts, and iframe guests keep their own environment.
If the browser wrapper cannot mediate a form, refuse it at the authoring
boundary or report that executor unsupported; do not claim parity from a
Hermes-only test. This is an authoring contract for trusted app modules,
not a claim that a same-page JavaScript wrapper sandboxes hostile code.

### D4 — Bake, caching, retries, and reload keep their existing meaning

Constant arguments may still be baked. An ambient read fails visibly during
bake; catching that error must not turn an implicit machine clock into a
compiled value. A dynamic time/seed argument uses the existing resource
argument comparison to request a new answer. Advancing the clock alone
does not implicitly subscribe every resource to every frame.

After `await`, the answer still has its invocation's explicit arguments.
An answer requiring newer time must be requested with newer arguments;
settlement must not substitute whichever session time happens to be current.
Stale-ticket refusal, carried slots, and matching-resource carry continue to
work without a hidden random stream that must be rewound or migrated.

Determinism is conditional on the supplied inputs and external outcomes.
This does not freeze network replies, control an iframe's clock (LLP 1020
D4), or sandbox trusted Rust providers. Rust providers follow the same
explicit-input contract, but ordinary native Rust can still call OS APIs.
Locale/timezone-dependent formatting needs explicit policy separately;
this change alone does not prove it identical across hosts. Seeds for
repeatable UI calculations do not replace secure entropy for credentials.

## Alternative: runner-backed ambient APIs

Keeping `Date.now()` and `Math.random()` is more convenient for existing
libraries. A correct version needs an explicit epoch anchor, logical time
and entropy supplied before module initialization, dependency tracking for
reads, nonconstant bake behavior, and specified ownership across concurrent
async answers, retries, and reloads. A single mutable global context can
otherwise let one continuation read another call's time or random stream.

That remains a viable alternative to this amendment. The recommendation is
explicit arguments first because they reuse the existing source signatures,
cache keys, and state ownership. Choose the ambient API design when a named
library or application makes its ergonomic benefit worth that machinery.

## Landing and verification

1. Add meaningful executor regressions using the existing JS fixture/toolchain:
   ambient reads refuse in initialization, an answer, and after a fulfilled
   fetch; explicit time/seed computations succeed and repeat identically.
2. Install guards before the module. Prove normal aliases cannot bypass them;
   keep explicit UTC date arithmetic working. Run bake and direct calls.
3. Drive a runner fixture: hold time/seed fixed, refresh, advance a declared
   clock argument, and reload with carry. Check values, request counts, and
   compiled-value eligibility, including stale async completion.
4. Hold every advertised executor to the same fixture. Record unsupported
   targets honestly; the native engine currently only links on macOS.
5. Rerun relevant existing tests, the five checks, and the existing metrics
   for boot/update/edit costs. Add no check, benchmark registry, or runtime
   feature flag. Update LLP 1027's as-built notes only after the landing.

## Open decision

Accept explicit inputs plus clear refusal as the first fix, or retain
runner-backed ambient APIs and pay for the context/dependency design above?
The fix is requested; this API choice has not been ratified. No implementer
or implementation date is assigned by this draft.
