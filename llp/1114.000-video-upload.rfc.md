# LLP 1114.000: Uploading a video — file parts, progress, and a transcode

**Type:** RFC
**Status:** Draft, 2026-10-08. Not reviewed.
**Systems:** `exactBodyFrom` on every executor (the runner's `Request::body_from`, `runner/src/request.rs`; the native reader, `host/apple/src/executor_body.rs`, which Linux shares; the web's two carriers, `host/web/http-body.js` and `host/web-js/ts-fetch.js`, over `host/web/storage-fs.js` `requestBody`); the transports (`vendor/ibex/crates/ibex2/src/transport/darwin_http.mm`, `rustls_http.rs`); device topics (LLP 1016.002) for progress; a new `storage.fs.compressVideo` (an Amendment A3 to LLP 1069.002; A2 is LLP 1114.003's crop), carried as a long request (LLP 1067 D1) and run on Apple by AVFoundation in an on-demand artifact; the agent's `state`

**Implementer:** unassigned until ruled

## 1. Summary

Bluesky uploads a video in parts: it asks the video service for a job, sends
the file in parts of a size the service names, four at a time, and finishes the
job. Before that it shrinks a large video to about 1080p at 3 Mb/s. Exact2 can
send a whole app file as a request body (`exactBodyFrom`, at most 64 MiB), but
not a part of one. It reports no upload progress, and it has no video
transcode.

This RFC proposes three stages that each land on their own:

1. **A byte range of a file as a body.** `exactBodyFrom` takes `{path, start,
   end}` as well as a path, sliced as `Blob.slice` slices. With it the clone
   uploads any video the service accepts. The 64 MiB cap stays: a part is far
   smaller.
2. **Progress.** The clone gets a progress bar from counting parts, with no
   new capability. Byte progress, if wanted, is a named observation with XHR's
   `ProgressEvent` fields, read through a device topic.
3. **`storage.fs.compressVideo`.** A sibling of `compressImage`, run as a
   long request so it can take minutes, report progress and be cancelled.
   AVFoundation does it on Apple. The web passes the file through at first;
   Linux and Windows answer `unsupported`.

Stage 1 is small and unblocks the feature. Stage 3 is the large one, and it
needs a ruling, because LLP 1069.002 A1.8 leaves video out of A1.

## 2. What Bluesky does

The source's account is older than Bluesky's current client. As of
2026-10-08 (`bluesky-social/social-app` main, and the `app.bsky.video`
lexicons in `bluesky-social/atproto`):

- **Limits.** `VIDEO_MAX_SIZE` is 300 MB (ISO megabytes) and
  `VIDEO_MAX_DURATION_MS` is 10 minutes (`src/lib/constants.ts`). The
  `app.bsky.embed.video` record says "up to 300 MB (formerly 100 MB)". The
  source's 100 MB and 3 minutes are the old limits. Accepted types are
  `video/mp4`, `video/mpeg`, `video/webm`, `video/quicktime` and `image/gif`.
- **Compression.** `@bsky.app/video-compressor`, not `react-native-compressor`
  (`src/lib/media/video/compress.ts`). Target 3,000,000 b/s, longer side at
  most 1920, at most 30 fps, codec `auto`. An accepted type under 25 MiB is
  passed through unchanged. On the web (`compress.web.ts`) it is Mediabunny
  over WebCodecs. It passes the file through when WebCodecs is missing, the
  file is small, or compression throws.
- **Upload.** Multipart, not one POST (`src/lib/media/video/multipart/`):
  1. A service-auth token from the PDS (`com.atproto.server.getServiceAuth`,
     `lxm` `com.atproto.repo.uploadBlob`), cached and refreshed a minute
     before it expires.
  2. `app.bsky.video.startUpload` with `sizeBytes`, `mimeType` and the
     advisory `durationMs`, `width`, `height`. The answer names `jobId`,
     `partSizeBytes`, `partCount` and `expiresAt`.
  3. `app.bsky.video.uploadPart?jobId=…&partNumber=…` per part, as
     `application/octet-stream`. "Content-Length must match [the part's
     expected size] exactly." Parts are idempotent. Four upload at once, each
     with 5 attempts and a 120 s timeout. The client reads each part as a byte
     range of the file (`readChunk.ts`: expo-file-system's `File`, `offset`,
     `readBytes`; the web slices the `Blob`). Parts must be at least 5 MiB
     except the last (R2 and S3's minimum).
  4. `app.bsky.video.finishUpload`, then `getUploadStatus` to recover, and
     `getJobStatus` until the transcode is done. `abortUpload` on cancel.
  5. The post embeds `app.bsky.embed.video`: the blob, `aspectRatio`, `alt`,
     and `captions` (up to 20 WebVTT files of at most 20 KB each; LLP
     1114.005).
- **Progress.** Per part, from `XMLHttpRequest`'s `upload` `progress` event
  (`uploadPart.ts`), summed over parts.
- The single-POST `app.bsky.video.uploadVideo` the source describes is still
  in the lexicons, beside the multipart five.

## 3. What exact2 has today

- **Picking a video.** `input type=file accept="video/*"` gives
  `app:/tmp/picked/<n>.<ext>` with `type`, `size`, `width`, `height` and
  `duration` (LLP 1069.002 D3). On iOS an `accept` without `video/*` asks
  PHPicker for `.compatible` video, which is H.264 at the source's size
  (`host/apple/Sources/ExactKit/Picker.swift:236`). Nothing makes it smaller.
- **`exactBodyFrom`.** `fetch(url, {exactBodyFrom: "app:/…"})` sends a whole
  app file, under `fs.read`, at most 64 MiB (`runner/src/request.rs:119-120`;
  `docs/reference.md:381`). The source is right that it exists.
  - **Natively** the worker reads the whole file into the request on a reader
    thread before sending (`host/apple/src/executor_body.rs:10-14`). It
    checks `stat` against the cap first (`:204`). At most four readers run at
    once (`:86`). Linux uses the same file. The transport then copies the
    bytes again: Darwin into an `NSData` `HTTPBody`
    (`darwin_http.mm:347`), and rustls/ureq from the slice
    (`rustls_http.rs:469`). Windows refuses it.
  - **On the web** a picked entry is the browser's own `File`, so the body is
    a `Blob` the browser streams from disk. The cap there is the same
    constant, checked before the `Blob` is made (`host/web/storage-fs.js:407-427`).
    Both carriers (`http-body.js:185-202`, `ts-fetch.js:15-35`) send it with
    `fetch`.
- **No byte range.** There is no part of a file as a body, and no ranged
  `readFile` (`vendor/ibex/crates/ibex2/src/bindings/storage.d.ts:14`). A
  clone could read the whole file and slice it in JavaScript today, but that
  is what `exactBodyFrom` exists to avoid (a 2 MB photo already broke the
  100 ms step; LLP 1108 D6).
- **No progress.** No transport reports bytes sent. The Darwin delegate
  implements no `didSendBodyData` (`darwin_http.mm`). LLP 1069's survey says
  so: "No upload/download tasks with progress"
  (`llp/1069-expo-sdk-survey.research.md:166`).
- **Cancelling.** `fetch` takes `signal`, and a replaced answer's fetch
  rejects `Aborted` natively and in the web's wasm realm. On the JS target the
  fetch runs to completion instead (`docs/reference.md:517-521`).
- **Long work.** `native.later` is a long call carried as a request, outside
  the 100 ms step, forgotten when a newer answer replaces it (LLP 1067 D1).
  Device topics let native code say "this changed" so watching answers are
  asked again (LLP 1016.002 D1).
- **`compressImage`** is the model for a transcode call
  (`data/src/image.rs:1-8`; LLP 1069.002 A1). It does not fit a video as
  built. It runs as an Ibex fs op with a 20 s trial budget and a 30 s waiter
  (A1.5), and it has no progress and no cancel (A1.8).
- **Concurrency.** The Darwin transport keeps four sessions
  (`darwin_http.mm:374`) and the executor four file readers. That matches
  Bluesky's four parts in flight. Parallel parts need the independent lane
  (`exactIndependentHttp`), since an ordered source's fetches wait in one
  FIFO (`docs/reference.md:391-394`).

## 4. What the web does

- **A part of a file:** [`Blob.slice(start, end)`](https://w3c.github.io/FileAPI/#dfn-slice),
  then `fetch(url, {method: "POST", body: part})`. The browser reads the slice
  from disk and sends a `Content-Length`. Node has the same shape for a path:
  [`fs.openAsBlob(path)`](https://nodejs.org/api/fs.html#fsopenasblobpath-options).
- **Upload progress:** only `XMLHttpRequest`'s
  [`upload`](https://xhr.spec.whatwg.org/#the-upload-attribute) object, whose
  `progress` events are [`ProgressEvent`](https://xhr.spec.whatwg.org/#interface-progressevent)s
  with `loaded`, `total` and `lengthComputable`. `fetch` has no upload
  progress. A [streamed request body](https://fetch.spec.whatwg.org/#dom-requestinit-duplex)
  (`duplex: "half"`) lets a page count bytes as the stream is pulled, but only
  Chromium ships it, only over HTTP/2 or later, and it sends no
  `Content-Length`, which `uploadPart` refuses.
- **Transcoding:** [WebCodecs](https://www.w3.org/TR/webcodecs/) decodes and
  encodes frames. It neither reads nor writes a container, so a page brings
  its own demuxer and muxer (Bluesky's is Mediabunny).
  [`MediaRecorder`](https://www.w3.org/TR/mediastream-recording/) records a
  stream in real time. A 3-minute video takes 3 minutes, and the container and
  codec vary by browser.
- **Cancelling:** `AbortSignal`, for `fetch` and XHR alike.

## 5. Design

### D1 — Three stages; the 64 MiB cap stays

The source asks for bodies over 64 MiB. Bluesky's multipart upload doesn't
need them: each part is `partSizeBytes`, which the service chooses, and R2 and
S3's 5 MiB minimum puts parts in the megabytes. The clone checks that
`partSizeBytes` is at most 64 MiB and refuses the upload if not.

Raising the cap natively would mean streaming the body from the file, because
today's reader holds the whole body in memory and the transport copies it
(§3). A 300 MB body would cost about 600 MB at peak, enough for iOS to end the
app. What raising it would take, for the record:

- Darwin: `uploadTask(with:fromFile:)` or an `HTTPBodyStream`.
- ureq: a reader body.
- The web: nothing, since its body is already a file-backed `Blob`.

**Recommended:** keep 64 MiB. Lift it, with streaming, when an app must send
one body that large. That would be the single-POST `uploadVideo`, which the
clone doesn't need.

### D2 — A byte range of a file as a body (stage 1)

**Options:**

- **R1 — `exactBodyFrom: {path, start, end}`.** TypeScript adds the object
  form beside the string. Rust adds `Request::body_from_range(path, start,
  end)`. `start` and `end` follow `Blob.slice`: `end` is exclusive, a
  negative value counts from the end, and both clamp to the file's size.
  - Natively the reader opens the file through the same handles, seeks, and
    reads `end - start` bytes, at most 64 MiB, in its 1 MiB chunks (the
    `AppDirectories::open_file` path, `executor_body.rs`).
  - On the web, `requestBody` returns `blob.slice(start, end, "")`. It
    makes no copy.
  - Grants, refusals, the deadline and abort are `exactBodyFrom`'s, unchanged.
  - About 150 lines with tests.
- **R2 — `storage.fs.openAsBlob(path)` and `blob.slice()`,** with a `Blob`
  body. This is the web's and Node's own shape. It needs LLP 1108 D5's native
  `Blob` (slice 3, about 1,100 lines, behind an RFC that is NOT READY), plus a
  file-backed `Blob` in the host store.
- **R3 — read the whole file in JavaScript and slice it.** This works today
  but defeats `exactBodyFrom`. A 60 MB video crosses the bridge, and the
  100 ms step breaks.

**Recommended: R1 now.** It extends a call that just landed, on every
executor that has `exactBodyFrom`. If R2 lands later, R1 goes ("delete; don't
deprecate"). Its slice semantics are R2's, so the migration is mechanical.

### D3 — Progress (stage 2, optional)

**Options:**

- **P0 — count parts.** The clone's own state machine knows how many parts
  have answered. With 5 MiB parts, a 60 MB video moves the bar in twelve
  steps. Exact2 does nothing.
- **P1 — a named observation.** `fetch(url, {…, exactProgress: "video"})`
  (Rust: `Request::progress("video")`) has the host keep
  `{loaded, total, lengthComputable}` for the latest request under that name,
  using `ProgressEvent`'s field names. It announces the device topic
  `progress:video` at most once per frame. A resource answers
  `progress("video")`, which reads the current value and watches the topic,
  so it is asked again when it moves (LLP 1016.002 D1: push invalidates, the
  answer stays a pull). This fits a multi-step upload: the mutation that
  starts, sends and finishes runs as one answer, while a separate resource
  shows the bar. `compressVideo` reports under the same mechanism (D4).
  - Web: the carrier sends a request that has `exactProgress` through
    `XMLHttpRequest` instead of `fetch`, with the same `Blob` body, and
    reads `upload.onprogress`. XHR exists in workers too. Registering an
    upload listener makes the request preflighted under CORS, as Bluesky's
    own client is.
  - Apple: `urlSession(_:task:didSendBodyData:totalBytesSent:totalBytesExpectedToSend:)`
    on the delegate `darwin_http.mm` already installs.
  - Linux: a counting reader over the body handed to ureq.
  - Windows: none, since it refuses `exactBodyFrom` anyway.
- **P2 — an answer that keeps coming** (LLP 1016.000). The upload `fetch`,
  returned as the answer, would map each progress event and then the reply.
  Rejected: a multipart upload is many requests and a finish, not one answer.
- **P3 — `XMLHttpRequest` in the runtime.** Rejected: its callbacks can't
  reach the view, because an answer settles once, so P1's plumbing would be
  needed anyway.

**Recommended: P0 for the clone now. P1 when an app needs byte progress** (one
large body, or a slow link where a 5 MiB part takes a minute). No clock is
read: the host counts bytes, and a frame paces the announcements, not a timer
in the module (LLP 1027.000).

### D4 — `storage.fs.compressVideo` (stage 3, LLP 1069.002 Amendment A3)

```ts
compressVideo(from: string, to: string, options: {
  maxDimension: number;  // integer 1..3840: the longer side, in pixels
  bitrate: number;       // integer: the video's average bits per second
  frameRate?: number;    // at most this many frames per second; default the source's
  progress?: string;     // a name for D3's observation
  signal?: AbortSignal;
}): Promise<{ path: string; type: "video/mp4"; size: number;
              width: number; height: number; duration: number }>;
```

**Options:**

- **T1 — this call,** next to `compressImage`. The app decides when to call
  it, with `Picked.size` and `duration`, as Bluesky does at 25 MiB. Recommended.
- **T2 — transcode at pick,** as `UIImagePickerController.videoExportPreset`
  does. Rejected: LLP 1069.002 D6 rules out transforms at pick, PHPicker has
  no preset, and the web can't.
- **T3 — an app Swift module** (LLP 1067) in the clone. This needs no ruling,
  but it only works on Apple, it is the clone's alone, and the web has no
  equivalent. It is the fallback if A3 is declined.

**How it runs.** It runs as a long request (LLP 1067 D1, `Work::Later`), not
as an Ibex fs op. A1.5's 20 s trial budget and 30 s waiter can't hold a
transcode of several minutes of video. Being a request gives the rest for free:
- the ticket and `pending(x)`;
- an answer that replaces it aborts it, as does its `signal`;
- the I/O worker is not held while it runs.

Progress is D3's P1 observation, with `loaded` and `total` in seconds of the
source. Grants: `fs.read` on `from` and `fs.write` on `to`, as for
`compressImage`. The output is written beside `to` and renamed, so a cancel or
a failure leaves no partial file.

**Per host:**

| Host | What runs |
|---|---|
| iOS, macOS | Swift, in an artifact loaded at the first call (the video arm's `libexact_video.dylib` already links AVFoundation and loads on demand; LLP 1042 §2). `AVAssetReader` to `AVAssetWriter`: H.264 High at `AVVideoAverageBitRateKey`, the longer side scaled to `maxDimension`, frames dropped above `frameRate`, the track's `preferredTransform` kept, AAC audio, `shouldOptimizeForNetworkUse` so the `moov` box comes first. HDR (HLG or Dolby Vision from an iPhone) is converted to SDR BT.709 for an 8-bit H.264 output; that conversion must be verified on a device. `AVAssetExportSession` was considered and rejected: its presets don't set a bitrate. |
| tvOS | `unsupported`. It has no picker. |
| Web | **W0, recommended first:** `unsupported`, so the app uploads the original, as Bluesky's web client does without WebCodecs. **W1, later:** WebCodecs with an MP4 muxer, shipped as a module artifact loaded at the first call and run in a worker. **W2, rejected:** `MediaRecorder`, because it records in real time. |
| Linux, Windows | `unsupported`: no codec in the tree, as for `compressImage` (A1.3). |
| Terminal | `unsupported`. |

**Failures** use `compressImage`'s form (`compressVideo: <code>: <detail>`):
- `invalid`: a bad option, as a `TypeError`;
- `unsupported`;
- `undecodable`;
- `aborted`;
- `failed`: the writer's error, with its text;
- a filesystem code.

**Not in A3:** trimming, cropping, rotating, HEVC or WebM output, keeping HDR,
a maximum duration (the app checks `Picked.duration`), and a source-size cap.
The source's size is bounded by the device's disk, since the reader streams the
file.

### D5 — Cancelling an upload

The clone cancels by sending `abortUpload` and by abandoning the answer.
Natively and in the web's wasm realm, the parts in flight reject `Aborted`. On
the JS target they run to completion (§3), and the service's abort makes them
harmless (`UploadAborted`). That difference is the JS target's existing one
and is not widened here. A stage-2 XHR carrier honours `signal` with
`xhr.abort()`.

### D6 — Grants

No new grant:
- `fs.read app:/tmp/picked` for the parts and the transcode's source;
- `fs.write app:/tmp` (or `app:/cache`) for the transcode's output;
- `net.fetch https://video.bsky.app` and the PDS.

For a PDS the clone learns at sign-in, see LLP 1114.009. Progress needs
no grant: it reports the app's own requests.

### D7 — The agent's view

- **Picking.** `type @t <file>` answers the picker natively, and `tap
  <input> drop <file>` answers it on the web (LLP 1069.002 D9, LLP 1069.007
  D4). The fixture is `apps/video-player/assets/motion.mp4` (10 s).
- **Parts.** A drive uploads to a stub of the five `app.bsky.video`
  procedures that checks each part's `Content-Length` and bytes. The stub is
  the clone's, not Exact2's. `fail fetch <prefix> times 1` fails one part to
  exercise its retry.
- **Progress.** With P1, `state.progress` lists each name's `{loaded, total,
  lengthComputable}`.
- **Transcode.** The drive checks the result's fields, plays the output in a
  `video`, reads `state.media`'s `duration` and `videoWidth`, and cancels by
  changing the answer's arguments, then checks that no file was left. This
  runs on macOS and the iOS simulator. On the web and Linux the drive expects
  `unsupported`, and the clone falls back to the original.

## 6. Questions for Charlie

1. **Amendment A3: reopen LLP 1069.002 D6 for `compressVideo`?** A1.8 left
   video out. *Recommended: yes, as D4.* It would run on Apple, the web would
   start at W0 (pass the original through), and Linux and Windows would answer
   `unsupported`. Without it, the clone uploads originals up to 300 MB. That
   works for short or 1080p clips, but a minute of 4K from an iPhone is
   roughly 170 MB or more (Apple's own Camera settings figures, approximate),
   so longer 4K clips are refused.
2. **A range now (R1), or wait for `Blob` (R2)?** *Recommended: R1 now*, to
   be replaced by R2 if LLP 1108 D5 lands.
3. **Byte progress (P1), or count parts (P0)?** *Recommended: P0 now. Build
   P1 when an app needs it.*
4. **Keep the 64 MiB cap?** *Recommended: keep it (D1).*

## 7. What the clone does after

**After stage 1** (about a day, as the source estimates):
- the composer's video button (`accept="video/mp4,video/quicktime,video/webm"`);
- a preview `video` on the picked path;
- a 10-minute and 300 MB check from `Picked`;
- `getUploadLimits`, then the service-auth token;
- `startUpload`, then the parts with `exactBodyFrom: {path, start, end}`,
  four on the independent lane;
- `finishUpload`, with `getUploadStatus` recovery;
- `getJobStatus` polled from a Contract `task` (a data module has no timers;
  LLP 1027.000);
- the post with `app.bsky.embed.video` (blob, `aspectRatio` from `Picked`, and
  `alt`);
- a part-count progress bar;
- cancel through `abortUpload`.

**Verified** first by a drive on the web and the iOS simulator against the
stub (D7). Then one live post from a test account, with Charlie's OK, which
the drive deletes.

**After stage 3:** the clone calls `compressVideo` when the file is over
25 MiB or isn't an accepted type, shows its progress, and uploads the result.
It is verified on macOS, the simulator and a physical iPhone, with a 4K HDR
clip among the fixtures the drive picks.

## 8. Effort and complexity

| Stage | Exact2 | Size | Hard part |
|---|---|---|---|
| 1. Ranged body | Native reader seek, web `slice`, Rust builder, both web carriers, docs, tests | **S** (about 150 lines) | Nothing new. The refusals and the reader-thread bounds already exist. |
| 2. Byte progress (if ruled) | XHR carrier on the web, Darwin delegate callback, ureq counting reader, the observation and topic, `state.progress` | **M** (about 400 lines) | Pacing announcements per frame across three transports. Two web carriers. |
| 3. `compressVideo` | Long-request plumbing for a built-in call, the Swift writer pipeline, the artifact's entry point, the A3 text, tests | **L** (about 600 lines plus device time) | HDR to SDR, rotation, variable frame rate, audio-only and video-only files, cancelling mid-write, memory on a phone. These are verifiable only on devices. |
| 3 web (W1, later) | A muxer artifact and a WebCodecs pipeline in a worker | **M** | Codec support differs by browser. The artifact's size. |

Clone work: about a day after stage 1, and half a day after stage 3. Stage 1
alone makes the feature usable. Stage 3 makes it usable for long or 4K video.

## 9. Not in scope

- Background uploads that survive the app being suspended (a background
  `URLSession`).
- Resuming an upload across launches.
- Download progress and `exactSaveTo` (LLP 1108 slice 2).
- Recording video (the camera module, `rules/DEFERRED.md`).
- Trimming or editing.
- Uploading captions, which is a small `uploadBlob`. Picking a `.vtt` file is
  LLP 1114.005 D5.
- Raising the 64 MiB cap (D1).
