# LLP 1016.001: `then` — an action after a mutation's answer lands

**Type:** RFC
**Status:** Implemented 2026-09-26 (Seth's direction: "fix all these gaps in Exact2")
**Systems:** Contract (`mutation … then action`), Plan (`mutations.then`), Runner (the armed continuation, fired through `advance`)
**Author:** Claude (Opus 5.5) for Seth Webster
**Date:** 2026-09-26
**Related:** LLP 1016 §5 ("`then`/completion callbacks and actions branching on a payload" left out); LLP 1017 P2 (`if` and `match` statements, which since let an action branch); QUEUE.md, "What RealWorld found in Contract" (1); grnl's FRICTION.md F15


**Ruled (Charlie, 2026-09-27, after the review of PR #47):** a `then` action runs **once after the answers that landed before the host next advances, reading the latest**. It does not run once per answer. The action takes no parameters, so running it again would repeat the same work (a double navigation), and once is what its uses (navigate after sign-in, clear a form) want. "After each answer" below is read that way. A `then` action that can send its own mutation is refused at compile time (`issues/20260927-then-coalesces-and-can-spin.md`). If a consumer ever needs per-answer behaviour, it is a different feature: `then action(answer)`, with the answer as a parameter.

## Summary

`mutation session as shape Session then signedIn` runs the action
`signedIn` after each answer to `session` lands. The action takes no
parameters: it reads the answer from `session`, as the view does. It is a
commit of its own, made when the host next advances the clock, which the
host does at once because the answer arms it with a due time already past.

## Motivation

LLP 1016 left completion callbacks out for two reasons: login and checkout
did not need them ("the view routes on the cell"), and actions could not
branch on a payload. The second reason no longer holds (LLP 1017 P2). The
first held for those two flows. Two later apps show where it stops holding:

- **RealWorld:** a redirect after sign-in or publish is a 100 ms
  `task … every` that compares stamps.
- **grnl:** capture moves to the Reader once an entry is filed. "Set this
  session aside" is a stamp comparison (`cleared = beganStamp`), not an
  assignment, because nothing can run when `began` answers.

Both are navigation and state resets. Neither is a value the view can
derive, because the reset has to stay reset after the answer.

## Design

### D1 — A clause on the declaration, not on each `send`

The continuation belongs to the mutation, so every send of it behaves the
same. A per-send `then` would let two sends of one mutation disagree about
what an answer means.

### D2 — The action takes nothing and reads the slot

"The reply is data" (LLP 1016) stands. The answer is in the mutation's slot
before the continuation runs. A failure the source shapes is an answer like
any other; one the source cannot take (released, LLP 1016 D5 as amended by
f05a95c0) is not, and runs nothing. `then` naming an unknown action is
`analyze-unknown-action`; one with parameters is `analyze-handler-arity`.

### D3 — Its own commit, through the timer path

The answer's commit (a `send` answered now, or a `fulfill`) stands on its
own. Its `then` is armed only once that commit stands, with the runner's
current time as its due time. `timer_due_ms` reports it, so every host
advances at once, and `advance` runs it as one commit. Where it ties with a
timer, the continuation goes first, because its answer landed first. Hosts
and the agent clock need no change.

- A refused continuation leaves the answer standing and is journaled like a
  refused timer.
- A continuation that sends its own mutation, answered now, re-arms itself.
  `TIMER_FIRE_LIMIT` stops that loop loudly.
- A dev reload does not carry an armed continuation. It restarts, as timers
  do.

*Rejected:* running the continuation inside the answer's commit. That makes
one commit's size depend on what the answer causes. A refusal would also
roll back the answer.
