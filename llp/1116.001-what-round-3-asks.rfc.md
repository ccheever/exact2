Against Expo the goal is met on every axis. Against React and SwiftUI, Exact2 is faster but not
yet cheaper or preferred. The round-3 evidence names why:

1. **Brand.**
   - The comparison apps on the web have an identity: a palette, a typeface, a tinted page, a
     timer ring, icon tiles, eyebrow labels.
   - Exact2's apps are clean, neutral and Apple-like. Graders score them a point lower: "B has
     the more polished, web-native UI", "looks generic".
   - The mechanism to brand an app already exists. `accent-color` on the root tints every
     control, tab, progress bar and link on every host (`--exact-accent` on the web, the tint
     on iOS). But nothing tells builders to use it, and the core's "leave colours unsaid" tells
     them not to.
2. **The token floor on small apps.**
   - On the web's small apps, Exact2 builders read about 30 KB before writing: `start-here`
     (14.2 KB) and two or three recipes, all in the first command. Codex also loads `AGENTS.md`.
   - They then take about 50% more steps than React builders (22–28 against 15–18), and carry
     about 16k more tokens of context on each.
   - Exact2 builders write *less* output. The gap is all input: tip-splitter 0.99M against
     0.41M, focus-timer 0.95M against 0.39M.
3. **Structure.** Muse builders still put a whole app on one screen (polls: every poll's options
   and bars inline on the home list) despite the core's sentence that a multi-field create is a
   sheet. A sentence does not lay down a list, a detail and a sheet; a working pattern would.
4. **Three host bugs and a regression:**
   - **A results screen opens scrolled, its top under the navigation bar** (trivia-quiz, 2 of 2
     runs). This is likely LLP 1116.000 D1.2/D1.3's inset and scroll-position change, when a
     screen's content is replaced in place. A lane started 2026-10-11.
   - **Swipe-to-delete does not work in a grouped row on iOS** (grocery-list).
   - **The web's date and time inputs have no border** (event-rsvp). LLP 1116 D1 styled text
     fields and selects, not them.
   - **A big readout does not shrink to fit at large Dynamic Type sizes** (stopwatch at AX5
     shows ":48."). UIKit's readouts use `adjustsFontSizeToFitWidth`.

## 1. Decisions

### D1 — the bugs

1. **A new screen shows its top.** A route push, or the view under a scroller's root swapped
   for another (results after a quiz), scrolls to the content's top, below the bar. A list whose
   data refreshes keeps the reader's place, and a long chat still opens at its end (LLP 1116.000
   D1.3). There is a lane and an XCTest.
2. **Swipe actions work in a grouped row on iOS.** Reproduce with grocery-list. If the
   `list-rows` recipe's scroll-snap swipe cannot be the native one inside a grouped row, the
   grouped list hosts UIKit's own trailing swipe actions (`UIContextualAction`) for a row that
   names them.
3. **Date and time inputs take the field look on the web**, as text fields and selects do.
4. **A readout fits its line.** A text with `white-space: nowrap` and a line too narrow for it
   shrinks to fit, down to a floor, as `adjustsFontSizeToFitWidth` with a minimum scale does.
   - It is written as `-exact-fit="shrink"`. CSS has no such property, and `-exact-` is the
     prefix for what CSS cannot say.
   - It is opt-in on the readout; the `numeric-readout` recipe uses it.
   - There is no size-cap fallback.

### D2 — brand in a few lines

- **The accent.** The core's design rule gains one sentence: pick the app's accent once with
  `accent-color` on the root. Every control, selected tab, progress bar, link and
  `exact:content` part follows it on every host, as a hand-built iOS app's tint does.
  Destructive and status colours keep their meaning.
- **No typeface step.**
- **A page tint is web-only and scoped explicitly.** On iOS the system background stays.
- **`exact:content` gains a `RingProgress`.** It is a circular determinate progress around a
  value, with the platform's progress semantics, in the accent. Focus-timer and water-tracker
  lost a ring to a bar.
- **The components draw state as a second colour:** done against not done, over against under,
  in the system greens, reds and greys.
- **The brand ships in the patterns (D3).** A builder who starts from `one-screen` or
  `dashboard` already has the accent, a filled summary and a ring. No paragraph is added to the
  early read.

### D3 — starter patterns

`bun exact.mjs pattern <name>` writes a working, tested starting app into the current app
directory: `app.contract`, `app.ts` and `app.test.contract`. It refuses to overwrite an edited
file unless given `--force`. `bun exact.mjs pattern` lists the patterns:

- `one-screen`: today's template.
- `list-detail`: a list, a pushed detail, a sheet to create, an alert to delete, persisted.
- `tabs`: two tabs, each a stack.
- `dashboard`: an `exact:content` summary, stat bars and a recent list over a source.
- `rest`: `list-detail` over the REST recipe's server, with the save lifecycle.

Each pattern compiles, passes its tests on the web and iOS, and passes `no-tells`.
`AGENTS.md` and the core say "start from a pattern" in one line each.

- **Each pattern replaces the recipe it covers.** The core's lookup line for that topic names
  the pattern, so a builder reads one or the other, never both.
- **`one-screen` and `dashboard` carry a width-aware web composition:** a bounded centred
  surface for a calculator or timer, and a two-column layout when wide.
- **Simple apps stay simple.** `one-screen` is short, and deleting what an app doesn't need
  costs little.

This replaces reading `navigation-stack` and re-typing its skeleton, which is the largest
recipe read. It also gives Muse builders the list, detail and sheet structure that one
sentence did not.

### D4 — the token floor

1. **The first command's total goes down.** The budget is the core, `AGENTS.md` and the
   recipes read with them, measured as bytes and as tokens carried per step. The core goes to
   10 KB or less. Keep the idea, the workflow, the one-screen example,
   the data module's essentials, the test essentials, the top five pitfalls and the lookup
   lines. The rest goes to recipes: the iOS driver's detail, the long pitfall list, and the
   tests' full grammar. Each moved item keeps a one-line pointer.
2. **`content-design` goes to 60 lines or less.** It is the library's call and the rules, now
   that the library draws the parts.
3. **`contract vocab` takes several names in one call** (`vocab formatDate slice tabular-nums`),
   so a build's lookups are one step, not five.
4. **`AGENTS.md` lists the patterns, the recipes index and `--help`;** nothing it repeats from
   the core.
5. **Types regenerate themselves.** `contract build`, `test` and `web` rerun
   `contract types app.contract -o app.contract.d.ts` when a source's signature changed. That is
   a step builders repeat today, and a type error when they forget.
6. **Round 4 attributes the surplus steps** to lookup, repair, build and verification, before
   any further machinery is chosen.
