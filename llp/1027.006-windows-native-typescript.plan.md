# LLP 1027.006: Windows native TypeScript through the pinned lean VM

**Status:** Reviewed for implementation; runtime qualification is outstanding.
**Implementer:** Codex (`exact_windows`). **Date:** 2026-10-04.
**Consumer:** A bounded ordinary Windows TypeScript app, described below.
**Authority:** Charlie's request to make Exact/Skirmish/Ibex work on Windows,
including reviewed engine gaps and needed toolchains; parent's next-increment
assignment after the accepted SDK 39018 consumer and optimized A/B cost run.
**Related:** LLP 1027 D3–D6/D9, LLP 1027.001, LLP 1015, LLP 1036/1086.

**Decision update (Charlie, 2026-10-06):** Exact moves now to Ibex 2's
split crates and their pinned, attested Hermes `260318099.0.4` bundles. This
supersedes this plan's old `260318099.0.0` pin and its “no engine upgrade” /
“pins do not change” constraints: delaying the move would only make it
gnarlier. The remaining constraints still hold. In particular, offline Cargo
builds may neither download nor compile Hermes; the install-once
`hermes-lean-sys-installer` plus `HERMES_LEAN_SYS_OFFLINE` is that boundary,
and the Windows VM remains lean, debugger-off, and Intl-enabled. Windows is an
E2 qualification target after Ibex publishes the v4 bundle.

## Problem and retained contracts

At SDK `39018dfa4`, Windows `exact-js` is always unlinked. `js/build.rs` returns
before `exact_js_engine`, `ENGINE_LINKED` is false, and linked producer tests
return early. `js/bake::build_sources` additionally rejects `windows`. The native
Skirmish success proves its Rust/game path, not native TypeScript execution.

**Historical baseline (before the 2026-10-06 decision):** Exact pinned vanilla
Hermes `6badada762121682b5481b6124e6c3a991ae6046` (`260318099.0.0`) and the
bytecode-only `hermesvmlean_a` archive. The installed
standalone Ibex v2 engine is `.0.4`/`d412d3bd…`, with full `hermesvm_a.lib` and a
source-runtime contract. It is useful toolchain evidence, not an acceptable
replacement archive. The preserved older Windows `.0.0` installations also
contain the full VM, not lean. None will be overwritten or repurposed.

The pinned source's `lib/CMakeLists.txt:170` defines `hermesvmlean_a`, excludes
the parser/frontend/optimizer objects of the full VM, and includes an MSVC lean
shared-link branch. This is evidence of a candidate target, not a Windows link
or execution claim. Actual archive/shim/consumer qualification is required.

Keep the existing source boundary: TypeScript is app logic below the one
DataSource seam. Native clients execute baked HBC only, never transpile or
compile source at boot. First pixel uses baked values before app JS activation.
Apart from the 2026-10-06 Ibex/Hermes decision above, no Ibex runtime/ESM
loader, JIT, new core feature switch, signed Windows update store, or general
Windows app-shell generator enters this slice.

## 1. Provision one separate, verifiable Windows lean installation

Use x86_64-pc-windows-msvc only in this increment. Export the exact existing
Hermes pin into a separate cache below `%LOCALAPPDATA%/Exact/hermes/`, leaving
the existing Ibex source/build/install roots unchanged. A bounded setup helper
may reuse the existing pinned source object/export, but verifies its commit and
never resets an existing checkout. It builds `hermesvmlean_a`, `jsi`,
`boost_context`, and the matching host `hermesc`; it does not install the full
VM or standalone CLI. No download/compiler work runs inside Cargo's build.rs.

The helper is one Windows provisioning script under `js/`, using the existing
Visual Studio/CMake/Ninja installation. Its exact invocation and cache root are
documented. Keep bounded build parallelism at the parent's current job limit.
An interrupted/incomplete install must be refused, not mistaken for a valid
cache; stage it separately, validate the complete payload, then publish it.

The install contains `hermes-headers/`, `windows-static/{hermesvmlean_a,jsi,
boost_context}.lib`, `hermesc.exe`, and a receipt. Validate before linking:

- exact source commit, target triple/architecture, lean archive role, bytecode
  version reported by the paired compiler, and the actual archive/compiler
  SHA-256 values;
- a sorted, hashed complete header inventory and the same headers used to build
  the archives; no independently selected header directory;
- CMake/compiler identity and effective flags, including Release, MSVC runtime
  linkage and iterator-debug ABI, JIT off, Intl policy, debugger policy, and
  required Windows system libraries. Use one verified CRT policy for engine,
  shim and Rust linkage; do not infer it from a directory name;
- existing Exact shim ABI expectations through actual compilation and runtime
  tests, plus refusal of source text by the linked lean VM.

Record the measured payload digests after provisioning. No receipt is an
authentication claim about an arbitrary user-selected engine; the receipt is
the local build/input identity boundary. Missing files, mismatches, full-VM
substitution, unsupported arch/ABI and incompatible compiler refuse by name.

## 5. Qualification and stopping points

1. Resolver/receipt tests: valid complete install; changed/missing archive,
   header or compiler; wrong pin/bytecode/target/CRT/lean role; malformed receipt;
   explicit stub; spaces/Unicode; unchanged versus changed input invalidation.
   Refusals occur before accepted artifacts are replaced or linked.
2. Existing actual `exact-js` and `exact-js-bake` linked tests execute on Windows:
   Caltrain/reference answers, retained state, explicit time/randomness, ambient
   init refusal, interruption, prelude/storage bindings, one-shot/resident
   equality, candidate rejection and recovery. Report previously skipped cases
   that really ran. Genuine Unix shell tests stay Unix; no fake linked pass.
3. Qualify the concrete native/browser app above, copied-package source/compiler
   independence, first-pixel behavior, fresh Runner/VM carry restoration, actual
   screenshots and owned cleanup.
4. Run the repository gates, affected formatting, caps/boot and existing
   non-Windows compile checks available on this host. Re-run a focused ordinary
   Rust Skirmish consumer only if the changed dependency/build graph intersects
   it; no automatic repin, game save format or gameplay changes.

Each bounded repair loop gets at most three rounds, then report the concrete
blocker for parent review. A failed lean build cannot be solved by quietly
substituting full Hermes or changing the pinned version. Native TS availability
is claimed only after the real app's post-paint action/restore path passes.
