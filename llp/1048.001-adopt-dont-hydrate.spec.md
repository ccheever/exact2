# LLP 1048.001: Adopt, don't hydrate — keep the server's DOM, rebuild only the tree

## Summary

Phase 2 of LLP 1048. Phase 1's runtime replaces the server's DOM with an equal
one. Phase 2 keeps it:

1. Contract evaluation rebuilds the tree from the page's document checkpoint.
2. The runtime proves that its canonical document equals the page's.
3. It binds the existing elements and restores the host state they need.

The DOM isn't rebuilt, and nothing is lost in between. The runtime's own work —
evaluating Contract — still runs; "no code re-runs" was r1's overstatement.

When the runtime loads becomes a per-page policy: now, when idle, when visible,
on first interaction (that event is replayed with its semantics), or never.
Navigation between rendered routes reuses their answers when their identity
matches.

## 1. The document checkpoint

Phase 1's embedded answers grow into a checkpoint: the state the document was
projected from. It is not the dev loop's `Carried` (`runner/src/runner/carry.rs`),
which is reload state — it keeps only root slots, omits pending answers,
restarts timers and replaces the store. The checkpoint holds:

- **Answers.** Every resource the document read: source, arguments, logic and
  artifact identity, the answer, and a freshness stamp.
- **Pending.** The resources still pending at the deadline, which render
  placeholders.
- **Location and time.** The router location and the render time (LLP 1048.000
  D5).
- **Row state.** Row slots, when the document holds any. A first frame has only
  initializers, so this is empty in phase 2 and exists for later checkpoints.
- **Never a store.** The device's store applies after adoption as an ordinary
  update, and a checkpoint never overrides it.

It is encoded canonically — names as strings, values in the plan's value
encoding (`plan/src/value.rs`) — and embedded as inert data.

## 2. Decisions

**D1 — Boot from the checkpoint.** `exact_boot_checkpoint(checkpoint, launch,
width, height)` seeds answers through the kept-answers path (as phase 1 does)
and returns the first batch.

**D2 — The canonical document digest.** SHA-256 over:
- the plan digest;
- the launch location;
- the checkpoint bytes;
- the canonical document: the parsed DOM's normalized serialization, excluding
  runtime incarnation ids such as reorder runtimes
  (`host/web/src/reorder_drag.rs:12`).

The preimage excludes the digest's own field. The renderer writes the digest
beside the checkpoint; the client computes it from its own first batch,
projected the same way, before touching the DOM.

**D3 — Adoption.** On a digest match:
- **DOM:** for each `create` in the first batch, find `[data-view=<id>]`
  through a one-pass index. The first batch's props, style and children are
  already in the DOM and aren't reapplied.
- **Host state**, restored separately from DOM mutation — everything
  `applyProps` and `attach` initialize (`glue.js` ~387, ~431, ~496):
  - listeners;
  - authored inertness;
  - autofocus;
  - scroll-follow state;
  - list and context bookkeeping;
  - the readiness state that disables controls.
- **Later batches** apply normally.

On a mismatch, the glue replaces the DOM once, journals the first differing
node, and remaps queued events (D5). The agent's `state` reports
`adopted: true | false`.

**D4 — Activation policies.** The route's `activate=`, or the inferred default:

| Policy | When the runtime loads and adopts | Default for |
|---|---|---|
| `eager` | Preloaded; adopts when ready | pages needing a runtime |
| `idle` | After `requestIdleCallback` following load | — |
| `visible` | When an element needing the runtime enters the viewport | — |
| `interaction` | On the first interaction with an element that has handlers; the event is replayed (D5) | — |
| `never` | Never: no glue, no wasm, no checkpoint | pages needing no runtime |

A page needs the runtime if it has handlers, timers, pending sources, client
holes, or host capabilities that need runtime work (canvas surfaces,
virtualized collections). The renderer marks elements needing it with
`data-exact-on`.

**D5 — Semantic replay.** Before adoption, the boot glue records events as the
live glue would interpret them:
- `press` from `click`;
- `change` from `input`, with IME composition respected;
- `submit` from Enter or a form submit, with the composition check;
- focus and blur.

It records them against view ids. After adoption they replay in order through
`exact_dispatch`, exactly once. Text typed before adoption is already in the
live input and replays as one `change`; selection is preserved.

On a mismatch, targets remap by instance path. An event whose target no longer
exists is dropped and journaled. If activation fails (the wasm fails to load, or
boot is refused), the document stays usable as HTML — links still work — and the
failure is reported. Controls the live glue would disable until readiness
(`glue.js` ~431) are marked disabled in the document only while activation is
pending.

**D6 — Placeholders, never refusals (LLP 1048 D6).** In the runner, a resource
whose source cannot answer at the current stage takes its placeholder, with
`pending(x)` true, and boot never refuses because of it (today it does,
`runner/src/runner/settlement.rs` ~380). The placeholder is declared (LLP
1048.003 D6) or the shape's empty value.

**D7 — Navigation data.**
- **Reuse.** When the router navigates in-app, a published answer is reused only
  if its source, arguments, logic identity, freshness and principal all match.
  Interview asks for arrays of parameters from its retained navigation stack
  (`app.contract` ~208), so a direct visit and an in-app visit can differ in
  arguments. A miss asks the source.
- **Build-stage answers** come from the destination's published checkpoint.
- **Request-stage answers** come from the server's uncached data endpoint,
  `GET <location>?__exact=data`. It is a separate representation from HTML,
  with its own content type and never cached with pages, and follows LLP 1048
  D3's rules.
- **Prefetch** fires on hover over a same-origin link and at idle for visible
  links. It is bounded in count and bytes.

**D8 — Static-only sites.** `never` pages may emit Speculation Rules
(`prerender`, `moderate`) and opt in to cross-document view transitions.

**D9 — Native hosts are unchanged.** They boot from the baked plan with no
network wait.

## 3. Verification

- **Equality:** the agent's `tree` and `state` are identical before and after
  adoption, for every app and rendered location. A forced mismatch takes the
  replace path, journals the first differing node and remaps queued events.
- **Replay:** a click, typed text (including IME composition), a checkbox and a
  submit before adoption produce the same state as the same events after it,
  under `interaction` and `idle`. Nothing replays twice.
- **Host state:** inertness, autofocus, scroll-follow and disabled-until-ready
  behave the same after adoption as after a fresh build.
- **Cost:** time to interactive and bytes before interaction, for `eager`,
  `interaction` and `never`. `never` pages transfer no wasm, glue or checkpoint.
- **Navigation:** matching answers are reused, mismatched ones re-ask, and
  prefetch stays within its bounds.
