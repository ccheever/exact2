# LLP 1048.001: Adopt, don't hydrate — resume a rendered page from its carried state

**Type:** Spec
**Status:** Draft
**Systems:** Runner (`Carried` as canonical bytes, booting from them, placeholders instead of boot refusals); web host (adoption, activation policies and event replay in the boot glue; a digest); build (payload files beside rendered pages); Router (navigation payloads and prefetch)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Implementer:** assigned by Charlie at phase 2 kickoff
**Date:** 2026-09-23
**Related:** LLP 1048 (parent: D4–D7, D11), 1048.000 (rendered pages; this replaces its D6), 1048.003 (placeholders, route `activate=`), 1005 §8 (the dependency table), 1007 §6 (carry and restart), 1016 (settlement), 1038 (router), 1047 (runtime size)

## Summary

Phase 2 of LLP 1048. A rendered page carries the runner state it was rendered
from. The runtime boots from that state, proves by digest that its first batch
equals the page, and binds to the existing elements instead of rebuilding them.
There is no second render and no silent mismatch.

When the runtime loads is a per-page policy: now, when idle, when visible, on
the first interaction (with that event replayed), or never — a page with
nothing interactive ships no runtime at all. Rendered routes also publish their
carried answers, so in-app navigation to them needs no source call.

## 1. The payload

- `Carried` (`runner/src/runner/carry.rs`) gets a canonical byte encoding:
  names as strings, values in the plan's value encoding
  (`plan/src/value.rs`), in a fixed field order.
- A header precedes it: the plan digest, the launch location, and the digest
  of the first batch the renderer serialized.
- The page embeds it as inert data:
  `<script type="application/vnd.exact.carry" id="exact-carry">`, base64. It is
  not script.
- The same bytes are written beside the page as `exact.carry` (D7).
- `Carried` omits pending resources and row slots. A first frame has no
  row-slot writes, and pending resources render placeholders (D6), so nothing
  is lost.
- The renderer reports payload bytes per page.

## 2. Decisions

**D1 — Boot from the payload.** A new export,
`exact_boot_carried(payload, launch, width, height)`, calls
`Runner::boot_carrying`, which already keeps slots, matching resource answers
and the clock, and refuses nothing a carried value cannot satisfy. It returns
the first batch as `exact_boot` does.

**D2 — The digest.** SHA-256 over the plan digest, the launch location, the
payload bytes and the first batch's bytes. The renderer writes it into the
payload header; the client recomputes it from its own first batch before
touching the DOM.

**D3 — Adoption.** On a digest match, the glue walks the first batch:
- for each `create`, it looks up `[data-view=<id>]` (through an index built in
  one pass), attaches handlers and listeners exactly as `attach` does, and
  registers the element in `views`;
- the first batch's `props`, `style` and `children` ops are already in the DOM
  and are skipped;
- every later batch applies normally.

On a mismatch, the glue builds off-document and swaps once (LLP 1048.000 D6),
then logs a journal line with the first differing op. The agent's `state`
reports `adopted: true | false`.

**D4 — Activation policies.** The route's `activate=` (LLP 1048.003 D5), or the
inferred default:

| Policy | When the runtime loads and adopts | Default for |
|---|---|---|
| `eager` | Preloaded; adopts as soon as it is ready | pages with handlers, timers or pending sources |
| `idle` | After `requestIdleCallback` following load | — |
| `visible` | When any element with handlers enters the viewport | — |
| `interaction` | On the first pointerdown, keydown, focusin, input or submit on an element with handlers; the event is replayed (D5) | — |
| `never` | Never: no glue, no wasm, no payload | pages with no handlers, timers, pending sources or client holes |

The renderer marks elements with handlers `data-exact-on`, so the boot glue
knows which to watch without the runtime.

**D5 — Event replay.** Before adoption, a small boot-glue listener captures
events on marked elements into a queue: target view id, kind, payload (input
values, key names).
- It prevents the default action only where the handler would have (submit, and
  Enter in a field with a `submit` handler).
- After adoption, the queue replays in order through `exact_dispatch`.
- Text typed before adoption is already in the live input and is reported as
  one `change`.
- The listener is host glue, counted by `boot.mjs` and budgeted in bytes.

**D6 — Placeholders, never refusals (LLP 1048 D6).** In the runner, a resource
whose source cannot answer at the current stage takes its placeholder, with
`pending(x)` true, and boot never refuses because of it. The placeholder is the
one declared with the resource (LLP 1048.003 D6) or its shape's empty value. The
router's launch fallback (`runner/src/runner/router.rs` ~230–236) already
refuses to `/` for an unknown location; that is unchanged.

**D7 — Navigation payloads.** When the router navigates in-app to a rendered
location:
- a host-side source answers that route's build-provenance resources from the
  location's `exact.carry` file;
- request-provenance resources ask the request renderer's data endpoint (LLP
  1048.002 D7);
- the glue prefetches `exact.carry` on `pointerenter` of a same-origin link, and
  at idle for links in the viewport;
- an unrendered destination asks its sources as today.

**D8 — Static-only sites.** Pages whose policy is `never` may emit Speculation
Rules (`<script type="speculationrules">` prerendering same-origin links at
`moderate` eagerness). Chromium then prerenders the next page; other browsers
ignore the rules. Cross-document view transitions (`@view-transition
{ navigation: auto; }`) are opt-in per app.

**D9 — Native hosts are unchanged.** They boot from the baked plan with no
network wait. The payload format is platform-neutral, so a native deep link can
resume page state later — not in scope here.

## 3. Verification

- **Equality:** the agent's `tree` and `state` are identical before and after
  adoption, for every app and rendered location. A forced mismatch (changed
  data) takes the swap path and journals the first differing op.
- **Replay:** a click, typed text, a checkbox toggle and a submit before
  adoption produce the same state as the same events after it, under
  `interaction` and `idle`.
- **Cost:** time to interactive and bytes before interaction, for `eager` vs
  `interaction` vs `never`, at 150 ms RTT and 6 Mbit/s. `never` pages transfer
  no wasm, glue or payload.
- **Navigation:** clicks between rendered routes make no source call and one
  `exact.carry` fetch each (or none when prefetched). Back and forward are
  correct.
