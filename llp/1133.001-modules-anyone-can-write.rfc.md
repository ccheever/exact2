## Summary

Anyone can write a module, and anyone can add a platform to someone else's
module, without asking exact2. The standard library is built on the same
seam, with no private one.

A module is split the way the web splits an API from its engines:

| Package | Holds | Written by |
|---|---|---|
| **Interface** (`@exact/camera`) | tier 1's names, types, meaning and errors; the words several platforms share; the agent substitute; the conformance suite | whoever designs the module |
| **Implementation** (`@exact/camera/android`, `@acme/camera-foo`) | one platform's native code and views, its own words and access hatches with their substitutes; the interface range it implements | anyone |
| **Host** (`@acme/foo-host`, id `foo`) | a platform id, its tier 2 key, its targets, and the layout its implementations use | whoever ports Exact to the platform |

All three are npm packages, resolved as LLP 1091 D9 already resolves
Contract packages. An interface may carry implementations under subpaths;
those are *endorsed*, which means only that the interface's author ships
them. An app opts into another implementation by depending on it directly.
For each interface and target the build binds exactly one implementation,
or shows the absence (LLP 1133 D8).

Distribution takes npm's registry and nothing else of the npm toolchain's
looseness. Bun fetches; Exact checks what was fetched and compiles module
code itself. Swift, Rust and Kotlin are compiled from the package's files
by the builders exact2 already has. Neither SwiftPM nor Gradle resolves
anything for a module, and every native path is generated, never typed
(D9).

Conformance is the bar, not approval: an implementation that passes the
interface's suite on its platform is that module on that platform.

The precedents are WebIDL with web-platform-tests, where an engine
implements an API by matching the interface and passing the tests
([WebIDL](https://webidl.spec.whatwg.org/),
[web-platform-tests](https://web-platform-tests.org/)), and Flutter's
federated plugins: an app-facing package, a platform interface, and
per-platform packages anyone may publish
([Flutter: federated plugins](https://docs.flutter.dev/packages-and-plugins/developing-packages#federated-plugins)).

## 1. Why

LLP 1124 makes an extension a directory found by name in the app's
`extensions/`, then exact2's (D2), with one implementation per host in a
table exact2 owns (D6). That serves exact2 and one app. It does not serve:

- **a third party's module**, used by many apps: there is no way to depend
  on it, version it, or update it;
- **a new platform for an existing module**: the implementation must be
  added inside the module's own directory, so the module's author decides
  whether a platform exists;
- **a better implementation** for a platform the module already has: the
  app must fork the module;
- **a new host**: the per-host table is exact2's.

Each of these needs permission from whoever owns the directory. This RFC
removes the need, and in doing it chooses how module code travels and is
built. The criteria for that choice are, in order: correctness, an
agent's efficiency writing an app, and speed, above all the wall-clock
time of development.

## 2. Design

### D1 — Three kinds of package

Each is a directory with a `package.json` and an `exact.json` whose `kind`
says which it is.

**An interface** (`kind: "interface"`) holds:

- the declaration: LLP 1124 D1's `extension.json` contents, with types
  grown to nested records, lists and string enums (a position is a record,
  Android's `Priority` an enum);
- **tier 1** and the **shared words**: options and sources that several
  platforms have and the web lacks (approximate location is one), named
  once by the interface;
- **the substitute** for its own names, declared: each source's agent
  default and each request's choices (LLP 1069.007 D1, LLP 1124 D7), which
  the runner answers on any host;
- **the conformance suite** (D7);
- optionally, implementations under subpaths (`./apple`, `./android`,
  `./web`), each an implementation in the sense below.

**An implementation** (`kind: "implementation"`):

```json
{
  "kind": "implementation",
  "implements": "@exact/camera@^2.3",
  "platform": "android",
  "targets": ["android"],
  "options": { "takePhoto": { "flashMode": ["auto", "on", "off"] } },
  "names": [
    { "send": "captureBurst", "targets": ["android"], "request": false,
      "args": { "count": "number" }, "substitute": { "answer": "done" } }
  ],
  "views": ["exact-camera"],
  "hatches": ["captureSession"],
  "sources": { "kotlin": ["android/"] },
  "artifacts": []
}
```

- `implements` is a semver range over the interface (D6).
- `targets` are the host's targets it covers: an `apple` implementation may
  cover `ios` and `macos` but not `tvos`.
- `options` are its tier 2 words on the interface's calls (D3).
- `names` are its platform-only sources and sends, **each with its own
  targets, default and substitute**, whether it is a request (LLP 1069.007
  D1), and the targets that answer it synchronously, if any (LLP 1133 D6),
  so the bake can type them and an agent can drive them on every target
  without compiling this native code (D2). An interface declares the same
  for its own names.
- `views` are the custom-element tags it serves (LLP 1024's roster, which
  `app.json` `modules` lists for an app's own module today): a camera's
  preview, a map, a waveform. An interface names the views every
  implementation serves.
- `hatches` are the objects it hands to the app's native code (LLP 1133
  D3).
- `sources` names its native source by language; `artifacts` pins
  prebuilt native libraries (D9).

**A host** (`kind: "host"`) holds its platform id, its tier 2 key, its
targets, the source layout its implementations use, and which of exact2's
builders compiles them (D5).

**As built, `views` (2026-10-23, with LLP 1133.008 D8 items 1 and 2):** the
bake reads `views` from the `exact.json` of each package the app depends on
directly, which is the `dependencies` of the nearest `package.json` above
the app (`contract/cli/src/package_views.rs`). An interface's `views` is an
object of declarations: `props` (a prop marked `"binds": true` binds a
device), `events`, and `"displayed": true` for a view that hears whether it
is displayed. An implementation's is the list of tags it serves, or
declarations of its own. A tag declared by two packages, or by a package and
`app.json` `modules`, is `bake-view-twice`, naming both. A tag that no
package and no `modules` entry declares is still `bake-unknown-module` (LLP
1024): the RFC's `bake-view-unknown` would be a second id for the same
refusal. Its message lists the packages' views and, where one of exact2's
standard modules serves the tag, the `exact add` that adds it. Each placed
tag becomes a row of the plan's `views` table, and each host makes it
through the implementation's instance in its session (LLP 1133.008 §13,
stage 0). The bake does not yet check a placed view's props and events
against its declaration. The fixture is `packages/fixtures/swatch`
(`@fixture/swatch`), outside the workspaces glob, installed by `file:` into
an app `exact new` makes.

### D2 — Names are imported from the package that owns them

Every module's names are imported (LLP 1091), exact2's as well as a third
party's (LLP 1133 D6, ruled §0):

```
use getCurrentPosition, watchPosition from "@exact/geolocation"
use captureDepth from "@exact/camera/apple"
use captureDepth as captureFooDepth from "@acme/camera-foo"
```

- **Tier 1 and shared words** come from the interface.
- **A platform's own sources and sends** come from the implementation that
  declares them: the interface's subpath for an endorsed one, the package's
  name for any other.

The reason is correctness. One plan serves every target, and each name in
it has exactly one declaration (LLP 1091 D7). If platform-only names were
imported from the interface and found in whichever implementation is bound,
Apple's `captureDepth` and Foo's `captureDepth` would be one name with two
declarations. A later interface minor adding its own `captureDepth` would
then change what an existing import means, which D6's additive minor
promises never to do. Imported from their owners, they are three
declarations, and the collision is the loader's existing case: rename one
with `as` (`contract-use-duplicate`, `contract/cli/src/sources.rs`).

Five rules make it hold:

1. **An implementation import binds.** On every target the imported
   *name* covers, the implementation that declares it must be the bound one
   (D4); otherwise the bake refuses (`bake-implementation-unbound`), naming
   the import, its package and the bound one. A stale import after a swap is
   a build error, never a name silently inert on the platform it was written
   for. Where `app.json` binds another implementation for a target on
   purpose, the author has spoken: the name follows rule 4 there, and
   `state.extensions` says so.
2. **Reading a declaration never links.** The bake reads
   `@exact/camera/apple`'s `exact.json` on every target to type its
   names and answer their substitute; Apple code links only into Apple
   targets where it is bound.
3. **One runtime owner.** Both import paths reach the same implementation
   instance, its watch table and its native objects; an import never
   creates a second provider. So a watch started by a tier 1 call is
   stopped by a tier 2 one, which is what LLP 1133 D2's rejection of
   per-platform modules protects. This is the composed module's invariant
   (D5), not only LLP 1067.000's one instance per session.
4. **Elsewhere, a platform-only name is a tier 2 name** (LLP 1133 D2): on a
   target the implementation does not cover, it answers its declared
   default or refuses by name, and `state.extensions` says which.
5. **Promotion breaks.** When an interface adopts a name an implementation
   declares, the implementation dropping its own breaks every import of it,
   so the adoption is a major version of the implementation (D6), and the
   refusal an app then meets says the name is now the interface's.

An agent will often write the interface import first. The refusal names
the line to write (LLP 1091's `contract-use-missing` path, which `contract
fmt --uses` applies), so the cost is one round trip.

### D3 — A platform's words belong to its implementation

Tier 1 and the shared words are the interface's. Each platform's words are
its implementation's: the options under its key on a tier 1 call
(`foo={…}`), extra result fields, its own sources and sends (D2), and its
tier 3 access hatches.

So a new platform is as deep as its implementer makes it, and the
interface's author never reviews a word for a platform they don't ship.
The bake checks an app's `foo={…}` against the implementation bound for
each `foo` target (D4), as LLP 1124 D3 checks a field, and refuses a word
it lacks. An app that swaps implementations is told at bake, by name,
which of its words the new one lacks.

### D4 — The app opts in; the build binds one per target

For each interface the app uses (by an interface import, or by an
implementation import alone) and each target it builds, the build binds
one implementation, in this order:

1. the one the app names in `app.json`, by target:

   ```json
   "implementations": { "@exact/camera": { "android": "@fast/camera-android" } }
   ```

2. else the one among the app's **direct** dependencies that covers the
   target;
3. else the one the interface carries for it;
4. else none: the build refuses (`bake-extension-platform`, LLP 1124 D9)
   unless the app marks the module optional, and then the absence is
   visible (the `available` fact, `NotSupportedError`, LLP 1133 D8).

Binding is per target, not per platform, because availability is:
an Apple implementation may cover `ios` and not `macos`, and one name in it
may exist only on `ios`. The tier 2 key stays the platform's (`apple`),
because the words are the framework's (LLP 1133 D2).

The build refuses by name:

- two direct dependencies covering one target, until `app.json` names one
  (`bake-implementation-ambiguous`); an endorsed implementation and a
  direct dependency are not ambiguous, and the app's dependency wins
  (LLP 1115: what the author writes wins);
- an implementation whose range excludes the interface's version, or whose
  declaration contradicts it (`bake-implementation-mismatch`);
- two installed versions of one package that carries native code
  (`bake-package-twice`): npm allows it, while a Cargo graph and one Swift
  module do not (D9).

A dependency of a dependency never supplies native code: "without
permission" means anyone may publish and the app may opt in, not that a
transitive package may inject Swift. Neither does a Contract library: LLP
1091 D11 stays (a library cannot declare native modules), so a re-export
can carry a name but never a binding.

The plan's extension table (LLP 1124 D4) records each binding: interface,
target, implementation, both versions, the SHA-256 of both declarations,
and the content hash of the native files compiled. `state.extensions` shows
it, with each name's declaring package and whether an answer was native,
substituted or a default.

This replaces LLP 1124 D2's listing: `package.json` is the list, and
`app.json` names only a choice the build cannot make alone and an optional
module.

### D5 — Platforms are open; builders are exact2's

A host package declares:

| Field | Example | Use |
|---|---|---|
| `platform` | `foo` | the id implementations name. Any host picks a short id, exact2's included, and none is reserved: an id need only be unique among the hosts one app builds for, and two hosts claiming one id in one app are refused by name (`bake-host-twice`) |
| `key` | `foo` | the tier 2 key (`apple` covers `ios`, `macos`, `tvos`) |
| `targets` | `["foo"]` | what `app.json`'s per-target lists name |
| `layout` | `{"rust": "foo/"}` | where an implementation keeps its source for this host |
| `builder` | `rust-static` | which of exact2's builders composes them into the app's one module |
| `grants` | how a grant becomes this platform's permission declaration | LLP 1069.008's table, extended per host |

A host declares data, never a program. A host-supplied build step would be
an install script by another name, and new apparatus (`rules/RULES.md`).
A host whose build is its own, outside exact2 (the ESP32 port, LLP 1124
§1), reads the same layout. A host needing a builder exact2 does not have
is a change to exact2 that a person accepts.

exact2's own hosts declare theirs the same way, so LLP 1124 D6's table
becomes their host files. The module artifact does not change: one per
app, loaded after first pixel, every entry on the main thread, never
fetched (LLP 1024 D3, LLP 1067.000).

### D6 — Interfaces grow by additions that change nothing

An interface's version is semver, replacing LLP 1124 D1's integer.
Implementations name a range (`@exact/camera@^2.3`).

- **Minor:** a new option, field, source, send, word or error that changes
  nothing for an existing caller or implementation: a new option's default
  is the behaviour an implementation that does not know it already has; a
  new result field is optional to read; a new enum value arrives only when
  the app asks for it. An older implementation stays conformant.
- **Major:** anything else.

A word with a default and a platform that implements it are different
facts. An app writing a word newer than the bound implementation's range
on a target is refused (`bake-implementation-minor`), naming the word, the
target and the implementation, because otherwise the word is silently
ignored there. A source newer than the implementation answers its default,
and the `available` fact and `state.extensions` say so.

Flutter's `plugin_platform_interface` exists for the same reason: it makes
implementations extend the platform interface, so a method added with a
default does not break every implementation
([plugin_platform_interface](https://pub.dev/packages/plugin_platform_interface)).
This closes LLP 1124's open review finding on an additive change without a
version bump, and its question 5.

### D7 — Conformance is the bar

An interface's suite has two parts:

- **The shape check,** which every build makes: the implementation's
  declaration against the interface's (D4), and in development builds each
  reply against the declaration (LLP 1124 D5).
- **Behaviour tests:** authored tests (`scripts/agent-test.mjs`) over a
  fixture app, run on the platform with the implementation bound. A
  substitute bypasses the module (LLP 1124 D7), so a substituted run proves
  nothing about native code. The tests check what holds on any device:
  availability, the declared errors, defaults, answer shapes, ordering, a
  watch that stops when cleared. A request that opens system UI is
  answered by the host's own means (`xcrun simctl privacy grant`, `adb
  shell pm grant`), which the host package names.

`exact module test <interface> --platform <id>` runs both. Passing a
version of the suite is what makes an implementation that module on that
platform. Nothing records it centrally: the implementation names the suite
version it passes, and anyone can run it again. Passing is evidence of
behaviour, not of safety.

An interface's minor adds its tests with its words, so an implementer sees
exactly what a new minor asks of them.

### D8 — The standard library uses this seam and no other

exact2's modules are `@exact/<name>` packages in its Bun workspace,
`packages/` (`package.json` already has `"workspaces": ["packages/*"]` and
`@exact/reading`), each an interface carrying its endorsed implementations.
`exact:` keeps its LLP 1091 D8 meaning, Contract compiled into the
compiler (`exact:motion`).

An app depends on a standard module as on any package. While an app
outside the repo consumes exact2 by path (as its Cargo `[patch]` and
`$schema` do today, `game/new.mjs`), the dependency is a path into that
checkout, `"@exact/geolocation": "file:<exact2>/packages/geolocation"`, so
the module can never differ from the SDK whose Swift and Rust it compiles
against. The bake's refusal for a missing one names that line, and `exact
add <module>` writes it; `exact new` writes none, since an app depends only
on what it uses. Once modules are published, the same line is a version.

Two tests that the seam is public:

- **Out of the tree:** an exact2 module, packed with `npm pack` and
  installed into an app outside the repo, builds unchanged.
- **Replaced:** a fixture implementation outside the tree replaces an
  endorsed one for one target without a change to exact2 or the interface.

A standard module that needs anything else is refused until the seam gives
it to everyone.

Runner vocabulary (LLP 1133 D5's exception: `video`, sounds, MIDI,
`exactPage`) stays exact2's, because it lives in the kernel and the runner.

### D9 — Distribution: npm's registry, Exact's rules, exact2's builders

A package system does three jobs, and the frustrations of SwiftPM and
Gradle are in the second and third, not the first. Exact takes the first
from npm and does the other two itself.

**The registry is npm's.** Any npm registry, a `github:` or `file:`
dependency, or a workspace: LLP 1091 D9's one mechanism, ruled 2026-10-04,
already built for Contract (`contract/cli/src/resolve.rs`) and for
TypeScript (LLP 1027 D5, 2026-10-16). Anyone publishes; nothing is
approved. A second carrier for native code is the second package system
1091 §6 rejected. Exact runs no registry; an index over npm (docs, which
targets have implementations, suite results) may come later and gates
nothing.

**Bun fetches; Exact checks what it fetched.**

- A package that carries native code pins its dependencies exactly; a
  range there is refused.
- One version of each such package per app (D4).
- What is installed must be what `bun.lock` says. The build refuses
  otherwise, by name, and the dev loop reinstalls with
  `--frozen-lockfile` when `node_modules` is older than `bun.lock`. Today
  nothing notices: this checkout's `node_modules/snapback4` is 0.2.30
  while `bun.lock` pins 0.4.29.
- No lifecycle scripts. An app's `package.json` sets
  `"trustedDependencies": []` (Bun runs a dependency's scripts only for
  that list: [Bun lifecycle scripts](https://bun.com/docs/pm/lifecycle)),
  and a module package must work without one. An agent never adds a
  package to that list to clear an error.

**exact2's builders compile module code; nothing resolves it again.**

| Language | How it is built | Not |
|---|---|---|
| Swift | the package's files join the app's `swiftc` call (`host/apple/build.mjs:1113`), each package as its own Swift module so two packages' `Camera` types cannot collide; the app's own Swift stays `ExactAppModules` | SwiftPM |
| Rust | the build generates the manifest: a path dependency from the resolver's canonical location, exact2's crates injected from the SDK checkout in use, `[patch]` from that checkout; the lock seeded from the SDK lock (`lockSeed`, LLP 1086.000.000), then `--locked --offline` | a `Cargo.toml` an author writes into `node_modules`, or a module naming `exact-*` crates |
| Kotlin | source sets of the one Android project, whose repositories stay Google and Maven Central only (`host/android/settings.gradle.kts`) | a module adding a repository or a Gradle plugin |
| JavaScript (web) | the page module, as `modules/web/index.js` is | |

**Prebuilt native libraries** (an `.xcframework`, an `.aar`, a Maven
`.jar`, a SwiftPM binary target) are pinned in `artifacts` as `{url,
sha256}` and fetched by the same step that fetches locked Cargo sources
(`cargo fetch --locked`, `scripts/app.mjs`), into a cache keyed by the
hash. They are never resolved transitively: a library a module needs is
named in its manifest. Bazel's `rules_jvm_external` fetches Maven artifacts
this way without Gradle.

**Amended by LLP 1133.008 D8 item 5 (ruled 2026-10-23, built the same
day):** an Android implementation's libraries on Google's Maven and Maven
Central are named as coordinates (`"maven"`) and resolve in the one
Android project's Gradle graph with the reader's own AndroidX, held by
Gradle's dependency locking and verification, the app's `gradle.lockfile`
and `gradle-verification.xml` beside its other locks (`host/android/
README.md`, "Maven libraries"). A pinned file closure would carry a second
AndroidX beside Compose's. `artifacts` stays for a library not on those
repositories.

**As built, the Rust row for Linux and Windows (2026-10-26, LLP 1133.022
D10 item 5, ruled "Build it now"):** no manifest is generated yet. The
build that bakes the app's Linux or Windows crate (`js/bake`, and the game
shells' entries) binds each interface the plan names by D4's order
(`contract/cli/src/native/packages.rs`), reads the implementation's
`"sources": {"rust": [root]}` and `"class"`, and writes the root into the
crate as a `#[path]` module, as an app's hatches join it (LLP
1075.003.000.001 §5); its submodules resolve beside it. The class
implements `exact_linux::package::Package`, and the host serves every
body naming its extension on the window's loop (`exact_linux::Composed`,
`exact_windows::run_composed`). What follows from that choice:

- A package's Rust names only crates the app's crate already has:
  `exact_linux` (which re-exports `serde_json`'s `json!` and `Value` as
  `exact_linux::package::{json, Json}`) and the standard library. A
  package needing another crate waits for the generated manifest above;
  the first one is where it lands.
- Linux and Windows answer only `later` forms; a synchronous name answers
  `NotSupportedError`. One instance per extension per session, made at its
  first body and destroyed when the window closes; session ids are `"1"`.
- An Android build composes none: its implementations are Kotlin.
- A Rust-data app's own generated entry (`contract::native::
  rust_hatch_entry`, the `apps/*/linux/build.rs` shells) does not compose
  packages yet; TypeScript apps and games do.

`packages/fixtures/tally` is the proof: an app made outside the repo binds
its Linux implementation and answers a real call headless (`bun
packages/fixtures/tally/test/linux.mjs`).

**Compiled output is cached by content.** A hash of the package
directory's bytes (`bun.lock`'s sha512 where it has one; `file:` and
workspace entries have none), with the target, the toolchain and the
flags, keys the package's compiled output in `~/.cache/exact/`, as
`~/.cache/exact/apple-modules` keys the host's Rust by its inputs (`host/
apple/modules.mjs`). A module package compiles once per target and
toolchain on a machine. A production build still compiles what it ships.

**Gradle stays for the final Android packaging** (dexing, resources,
manifest merging, signing) in this RFC. Whether a direct `kotlinc`, `d8`
and `aapt2` path should replace it for the development loop is a
measurement first (§8 question 5).

These hold whatever is chosen above:

- Native code is compiled into the app and never delivered later (LLP 1024
  D3). Fetching a tarball to compile is a build input, as `cargo fetch` is.
- The build reads only installed and fetched files; compiling never
  touches the network.
- Depending on a package with native code trusts its author with code that
  runs when the app builds (a Rust `build.rs`, a Swift compile). `bun.lock`
  buys integrity, not safety, and Exact does not claim otherwise.

## 3. What exact2 changes

1. `contract/cli`: the `exact.json` readers; module specifiers in `use`
   (a loader origin built from a JSON declaration, beside `resolve.rs`'s
   compiled-in and file origins); sources and sends as importable
   declarations; declaration identity carried through checking and
   dispatch, replacing LLP 1124 D3's search by bare name and its
   `bake-extension-twice`; the binding of D4 and its refusals.
2. `scripts/app.schema.json`: `implementations`; a package's `views` join
   the app's module roster (LLP 1024).
3. The plan's extension table gains the binding (D4).
4. Each host's module build: per-package Swift modules, the generated Rust
   manifest, Kotlin source sets, the generated dispatcher (D5, D9).
5. The data-code bindings LLP 1133 D6 describes, generated from the
   declaration (TypeScript into the bake's generated types, Rust beside the
   generated manifest), and the runner's inspection of each native body in
   `Runner::native_work`.
6. The checks of D9's second paragraph, in the build and the dev loop.
7. `scripts/deploy.mjs`: install from the captured `bun.lock` before
   asserting the Cargo closure. Today it asserts at line 581 and installs at
   585–589, so a Rust crate inside a package cannot resolve in a clean
   capture. Capture module packages' bytes too, so an unpublished version
   cannot make a snapshot unbuildable.
8. `scripts/exact.mjs`: `exact module new`, `exact module test` (D7),

  extensions live) is answered by D8 and D9, question 4 (a host's
  implementation and the app's) by D4's order, question 5 by D6.
- **LLP 1133** (r3 has taken these): D2's platform-only names are
  imported from the implementation (D2 here); D5's modules are `@exact/*`

- **LLP 1091:** D9 carries native modules as well as Contract, with D4's
  stricter rules for packages that carry native code (one version, exact
  pins, direct dependencies only). D8 and D11 are unchanged.
- **LLP 1086** line 179 ("no npm packages yet") and line 200 ("no npm

## 5. What stays refused

- A registry, review or approval run by exact2 for a module or a platform.
- Native code over the network, or a module roster that changes on iOS
  after review (LLP 1024 D3).
- Native code from a transitive dependency or a Contract library.
- A native path an author writes into `node_modules`.
- A host package that runs a program at install or build.
- SwiftPM or Gradle resolving a module's dependencies.
- Two implementations of one interface bound on one target; two versions of
  one native package in one app.
- A word silently ignored because the bound implementation predates it
  (D6).

## 6. Worked case: camera on a new platform

exact2 ships `@exact/camera@2` with implementations for `apple`, `android`
and `web`. Foo ships.

1. Someone publishes `@acme/foo-host`: its key `foo`, its target, its
   layout, a builder exact2 has (D5).
2. Someone else publishes `@acme/camera-foo`: `implements:
   "@exact/camera@^2.0"`, `platform: "foo"`, its Foo words
   (`foo={hdrMode: …}`), a Foo-only `captureDepth` with its substitute, the
   `exact-camera` view, and a hatch on Foo's capture object.
3. They run `exact module test @exact/camera --platform foo` and
   name the suite version it passes.
4. An app adds both as dependencies. Its `use takePhoto from
   "@exact/camera"` is unchanged; the build binds `@acme/camera-foo` for
   `foo` (D4, step 2). `use captureDepth from "@acme/camera-foo"` reaches
   the Foo-only send.
5. Before step 2, an app that marked camera optional could already be
   driven on Foo by an agent: the interface's substitute answers, and
   `state.extensions` says the module is unbound there.

Nobody at exact2 was asked.

## 7. The panels

Each round was blind and read-only: each panellist read the repository and
the drafts and answered alone.

**Distribution:**

| | Recommendation | Confidence |
|---|---|---|
| GPT-6 Astra, max | npm through Bun as the one carrier; native package managers underneath for third-party libraries; one captured selection shared by every build stage | 85% |
| Grok 4.7, xhigh | one Bun package per kind; compilers consume files and resolve nothing; a generated Cargo manifest; direct dependencies only | 76% |
| Claude Fable 5.1, xhigh | npm through Bun, because LLP 1091 D9 already chose it; `@exact/*` packages; refuse skew between the lock, the tree and the compiled code | 75% |

All three rejected path and git only (no resolver), each language's own
package manager (three registries and four lockfiles per platform-adder;
Tauri's documented version skew), an exact2 registry (the central office,
for nothing native linking needs), and the `snapback4` hybrid (two pins
kept in step by hand). Their predicted failures are in D9 and §3: a Rust
crate in a package failing in a clean deploy (Astra, Fable), a module
naming exact2's crates by version or path (Grok), and the compiled native
code differing from the declaration the plan records (Fable).

**Where a platform's own names are imported from,** two rounds:

| | Round 1 | Round 2 |
|---|---|---|
| GPT-6 Astra, max | the implementation, bound per target, stable declaration identity, one runtime owner (88%) | the implementation; rule 1 judged by the name's targets; promotion is breaking (84%) |
| Claude Fable 5.1, xhigh | the implementation, as a binding constraint (75%) | the implementation; rule 1 yields where `app.json` binds another on purpose (80%) |
| Grok 4.7, xhigh | the interface plus the platform key, filled from the bound implementation (74%) | the implementation; `contract fmt --uses` rewrites stale imports after a swap (80%) |

The key form keeps a name stable across a swap and uses one form for
endorsed and third-party implementations. It loses on correctness: a
replacement may declare a platform-only name with the same spelling and
type and another meaning, which no suite checks because the name is not
the interface's, and one key can span targets bound to different
implementations, giving one imported name two declarations in one plan.
In the common case the two forms write the same line, since an endorsed
implementation is the interface's platform subpath (Fable).

**`@exact/*` or `exact:`** (round 2): all three for `@exact/*` (Astra 85%,
Grok 83%, Fable 70% with the SDK supplying a missing package; 90% against
`exact:` for native modules). D8's `file:` dependency into the SDK keeps
Fable's point (the module cannot differ from the SDK) without a second
lookup rule.

## 8. Rulings (Charlie, 2026-10-18)

"recs mostly look ok":

1. **The model:** interface, implementation and host packages, with
   conformance rather than approval.
2. **Platform-only names** come from the implementation that declares them,
   with D2's five rules as amended in round 2.
3. **Distribution** as D9: npm's registry; Bun fetching under Exact's
   checks; exact2's builders compiling module code, with no SwiftPM or
   Gradle resolution; prebuilt libraries pinned by hash; compiled output
   cached by content.
4. **`@exact/*`** for standard modules, with D8's dependency; `exact:` stays
   compiled-in Contract.
5. **Gradle:** measure how much of a warm, one-line Android rebuild is
   Gradle's configuration and daemon rather than compiling, before
   deciding anything; a direct `kotlinc` and `d8` path for the development
   loop would be its own RFC.
6. **LLP 1124's r2 takes D1–D6 here,** with Douglas Lowder; 1124 stays the
   seam's document and this one the ecosystem's.
7. **No platform is blessed** (LLP 1133 §0): no host id is reserved (D5),
   and a module is complete for the targets it declares.
