## Summary

LLP 1016.000 is the design. It adds a resource whose answer is a sequence:
each message commits as its own settlement, and the stream ends at a close,
a failure, or when the runner forgets the ticket. This plan lands it in
three slices. It does not reopen the design.

1. **The runner half, with no network.** `Answer::Stream`, a reply that can
   be delivered more than once, settlement per message, forget ends it,
   `clock settle` treats an open stream as quiet after its first message.
   Held by a scripted fake transport.
2. **Server-sent events on every host.** A streamed `fetch` body with an SSE
   parser: in the web glue over `response.body`, and in the native executor
   over `ibex2`'s existing `StreamingResponse`. Admitted by `net.fetch`, no
   new grant. Crew's event stream is the consumer.
3. **WebSocket.** Opened by the web glue and by a new `ibex2` transport on
   Apple and Linux, admitted by the `net.websocket` grant that `ibex2`
   already parses. Bluesky's Jetstream is the consumer.

No `rules/DEFERRED.md` trade: nothing there refuses live data for apps
(ruled). Its only "push" is update delivery.

Streamed `fetch` bodies as a `ReadableStream` in the module realm are **not**
part of this. A source never sees bytes, only parsed messages (1016.000 D3).

## What changed on main since 1016.000 (2026-09-24)

1016.000's design holds. Four things landed since, and they make it cheaper:

- **Device topics (LLP 1016.002, implemented 2026-09-26).** The runner
  already accepts pushes that arrive between pumps. It queues them
  deduplicated, wakes the host, and applies them before replies. 1016.002
  D1 rejected value streams *for device data* and named 1016.000 as "the
  design for network sources, where the value is only in the message". The
  division is settled: a device topic invalidates and the source re-asks; a
  network message carries its value. Slice 1 reuses the wake path, not the
  topic queue.
- **`native.later` (LLP 1067).** A long native call is a request to
  `exact-native:`, run on the independent HTTP lane with a 1 MiB ceiling
  and handed off, so no I/O worker waits for it. Slice 2's native stream
  should use the same lane and the same hand-off. An open SSE response then
  counts as one ticket and holds no worker thread. 1067 answers once and
  defers partial results to this plan. A native module that streams (words
  as they are transcribed) is the same `Answer::Stream` with the module as
  the transport. It is named here as a later consumer, not built.
- **The independent lane and hand-off.** `HttpScheduling::Independent`
  (`runner/src/request.rs:46`) and `Work::Later(Box<dyn FnOnce(Reply)>)`
  (`request.rs:401`) exist. `Reply` is `FnOnce` and reports `Aborted` when
  dropped unsent (`request.rs:366-390`). A stream needs a reply that can
  send many times and then ends. That is the one data-seam type change
  (slice 1).
- **Forget aborts on every host.** The native executor aborts held HTTP
  when a ticket retires (`host/apple/src/executor_tests.rs:339`,
  `retirement_aborts_held_http…`), and Linux shares the executor. The web
  glue does the same after each batch (`letGo`: a safe read whose ticket
  `exact_request_active` no longer holds is aborted), and its `clock
  settle` waits only on held tickets, so a forgotten stream's reader ends
  and never holds the agent. This was slice 2's web prerequisite, fixed on its own (ruled; `web: let go of requests the runner forgot`).

Worker placement (LLP 1027.002) changes nothing for the design. `parse` runs
where the source's other parses run. Each message is one turn and commits
through the runner, as a single reply does today.

   append mode comes back if it doesn't.

Streams are network, not device (LLP 1069.007 D6). Under the agent they run

## Slices

Each slice lands alone, passes the five checks, and names what holds it.

### Slice 1 — the runner half, no network

- **Runner.** `Answer::Stream(Request)` beside `Now` and `Later`
  (`request.rs:31`). A stream ticket stays in `pending` after its first
  fulfil. Each fulfil parses and commits as a settlement pass (1016.000
  D1). `pending(r)` is false from the first message. A late message on a
  forgotten ticket is dropped, as today (`commit.rs:575`). `refresh`
  forgets and re-asks.
- **Data seam.** A reply that can be sent many times, with the final send
  distinct (`Outcome` plus an end mark, or a `Stream` reply type beside
  `Reply`). A drop with no end sends `Aborted` once, as `Reply` does.
- **Bounds (1016.000 D4).** One ticket on its lane while open; the existing
  response ceiling per message; the newest undelivered message per ticket
  is kept. Coalescing happens host-side before delivery, and the runner
  keeps a count.
- **Agent (1016.000 D5).** `clock settle` counts a stream as in flight only
  until its first message. `state` lists open streams with a message count
  and the coalesced count. No new operation.
- **Held by:** the executor's fake transports grow a scripted stream; a
  runner test sends three messages then a close, and asserts three commits
  and a final value; a forget-mid-stream test asserts the host abort and
  no commit after; a `clock settle` test with an open stream returns
  settled.

### Slice 2 — server-sent events on every host

- **Prerequisite (web), done.** The glue aborts a request the runner no
  longer holds, after each batch, through `exact_request_active` (above).
  What stays for the stream: stop counting it for `clock settle` after
  its first message, though its ticket stays held.
- **Web.** The request arm reads `response.body` incrementally and parses
  SSE (`data:`, `event:`, `id:`, `retry:`; UTF-8; blank-line dispatch). It
  delivers each event to the ticket and keeps the `AbortController`. The
  module realm keeps deleting `EventSource` (`module-glue.js:136`,
  `module-worker.js:44`).
- **Apple and Linux.** The native executor reads `StreamingResponse`
  incrementally on the independent lane, handed off (LLP 1067 D3), with the
  same parser as a small shared Rust function. One parser for the render
  host too, when it needs one.
- **Reconnect.** A dropped connection ends the stream with a shaped
  failure. The source's own `refresh` (or a `then`, LLP 1016.001) reopens
  it, with `Last-Event-ID` passed as an argument. The host does not
  reconnect on its own: a hidden retry loop would be a second lifetime
  (1016.000 D2).
- **Contract.** None; the source decides whether it streams. TypeScript
  sources get the streaming form in the prelude's `fetch` answer: exact
  spelling to be pinned in the spec, the smallest that marks a request as
  a stream.
- **Held by:** a web test and a native executor test against a local SSE
  peer (`stream_tests.rs` already runs real HTTP peers for both socket
  transports); `apps/exact-live` switches job progress from polling to SSE
  against a local server, driven by
  `smoke.mjs web|macos|ios|linux --app exact-live` with `clock settle`
  green while the stream is open.
- **The trial (Decided 3):** Crew's chat through a forced disconnect, the
  cursor re-ask shown whole in `tree` and judged by a person.

### Slice 3 — WebSocket

- **Grant.** `net.websocket <origin>` is already parsed and checked
  (`vendor/ibex2/src/grant.rs:107-155`, with a test that a fetch grant does
  not admit a socket). A reconnect is admitted again.
- **Web.** The glue opens the socket; the module realm keeps no
  `WebSocket`. Inbound text frames are messages; binary frames are refused
  with a shaped failure until a consumer needs them.
- **Apple and Linux.** A new `ibex2` WebSocket transport over the existing
  TLS stack (rustls on Linux, the Darwin transport on Apple). One ticket
  per socket, on the independent lane.
- **Sending.** 1016.000 has no outbound frame, and this slice doesn't add
  one on its own. Jetstream is receive-only. Messages' send path is an
  ordinary `mutation` over HTTP. A socket that must carry client frames
  needs a design line in 1016.000 first.
- **Held by:** an `ibex2` transport test against a local WebSocket peer
  (upgrade, text frames, close, over-limit frame); the web glue's socket
  under the agent; one consumer driven by the smoke. That is Bluesky's
  Jetstream feed (outside the repo, `EXACT_APP_DIR`) or an in-repo
  fixture if that app cannot be run by the async lane.

## As built — slice 1 (Claude (Opus 5.5), 2026-09-27)

- **The answer.** A Rust source writes `Answer::stream(request)`. It is a
  constructor, not a fourth variant: it returns `Answer::Later` with the new
  `Request::stream` set, and moves a request still on the ordered lane to
  the independent one with a 1 MiB per-message ceiling (a stream on the
  ordered FIFO would hold everything behind it, so answering one is the
  explicit promise LLP 1041 §8.4 asks for). Every forwarding source (the
  worker envelope, mixed and placed sources, the Rust module ABI as result
  tag 9) carries the flag with no new match arm. *Deviation from 1016.000
  D1's spelling, for that reason.*
- **The message.** `Outcome::Message(Message { event, id, data,
  coalesced })`. A message to a stream's ticket commits as its own
  settlement and keeps the ticket; any other outcome (a response that is
  not an event stream, a failure, the far side's close) ends it through the
  ordinary reply path. A message whose parse fails, or asks again, ends the
  stream the way a failed reply ends a request (`release_failed`).
- **Reply.** `Reply::stream(deliver)` sends any number of `message`s then
  one `send`; a drop with no end sends `Aborted` once. `Reply::new` keeps
  answering once (a message to it is its one answer).
- **Pending and settle.** `pending(r)` and `has_pending()` count a stream
  only until its first message. `holds(ticket)` stays true while it is
  open, so hosts keep it running; an argument change, `refresh`, an answer
  now, or leaving the plan lets it go through the forget path, and a late
  message is dropped with the usual journal line.
- **State.** `state.pending` lists what is in flight (a stream until its
  first message); `state.streams` lists every open stream with `messages`
  and `coalesced`. The macOS agent counts `state.pending`, so its `settle`
  needed no change.
- **Coalescing.** In the native executor: a stream keeps at most one
  undelivered message; a newer one replaces it and carries the count it
  replaced in `coalesced`, which the runner sums per ticket.
- **Held by:** `runner/src/runner/stream_tests.rs` (three messages then a
  close commit four times; forget mid-stream and a late message dropped;
  refresh reopens; coalesced counts; a bad message ends it; a 404 ends it)
  and `host/apple/src/executor_stream_tests.rs`, the executor's scripted
  stream (a fed body: three messages then a close with both independent
  workers free; coalescing to the newest; forget aborts the read and
  releases the reservation; a non-event response is the one answer; an
  event over the ceiling is refused; an ordered stream is refused).

## As built — slice 2 (Claude (Opus 5.5), 2026-09-27)

- **Native (Apple, Linux).** A stream never enters the lane's worker
  queue. It is admitted at once and opened on a thread of its own with a
  transport of its own (`host/apple/src/executor_stream.rs`), then read
  there. *Changed from the plan's "on the independent lane, handed off":*
  Exact Live's 128 held replies occupy both independent workers until
  release, and a stream queued behind them opened 15 s late; a worker's
  Darwin session pool (four leases) would be shared the same way. A stream
  is bounded apart: at most 16 open, its ceiling charged to the independent
  lane's bytes, never to its 128-count (*deviation from 1016.000 D4's "one
  ticket on its lane"*: a stream must neither starve nor be starved by a
  lane of held replies). Forgetting aborts the read (the server sees the
  connection close); retirement aborts every stream. One parser,
  `EventStream`, the HTML rules; the Linux host shares it by path.
- **Web.** `http-body.js` reads `response.body` through the same parser
  (`eventStream`) when the op says `stream` and the reply is 2xx
  `text/event-stream`; each read's events are delivered as one message,
  the newest, with the rest counted as `coalesced`. A message is ABI kind
  8 (`event`, `id`, `coalesced` as header lines, the data as the body).
  After a stream's first message the glue drops it from `inflight`, so
  `clock settle` stops waiting on it; `letGo` still aborts it when the
  runner lets the ticket go. The module realm still has no `EventSource`.
- **Reconnect.** The host never reconnects. A source reopens by answering
  a new stream: from `refresh`, from its next ask, or from a message's own
  parse (a gap: `Answer::stream` with `Last-Event-ID`), which the runner
  takes as one more round and lets the old ticket go.
- **TypeScript.** `fetch(url, { exactStream: (event) => value })`: the
  mapper turns each event, and the end, into the answer, now; the fetch's
  promise never settles. An event is `{ type, data, lastEventId,
  coalesced }`; the end is `{ type: "error", kind, message, status }` (a
  failure, the far side's close, or a reply that was not an event stream,
  with its body as `data`). The generated declarations type it
  (`StreamEvent`, a `fetch<T>` overload). Hermes maps through
  `__exact_message` on the source's thread; the browser's iframe realm maps
  synchronously in the same call (`op: "message"`), never as a turn.
  **Not built: worker placement** (Hermes owner or browser Worker): a
  message there would be a turn, and the runner keeps one ticket per
  target; the Worker realm refuses with a named error.
- **Consumer: Exact Live.** `resource jobLog = jobEvents(waveId)`: the job
  fixture's `/api/events?wave=N` (control origin, `net.fetch`) sends one
  event per change with the wave's counts and the log entries past the
  reader's cursor; `Last-Event-ID` resumes from it. The source keeps a
  cursor; a gap re-asks from it, and `Reconnect` (`refresh jobLog`) resumes
  after a drop. `EXACT_LIVE_JOB_ORIGINS` builds against a loopback fixture.
- **Held by:** `executor_stream_tests.rs` (plus: a stream opens while both
  workers hold replies; streams have their own bound; a local SSE peer on
  the platform transport arrives message by message; forgetting it closes
  the peer's connection), `http-body.test.mjs` (the parser; a stream
  delivers each read's newest event then its end), `js/tests/it/castle.rs`
  (the TypeScript mapper, alone and through the runner), `js/web`'s
  routing test, `exact-live-data`'s cursor test, and
  `scripts/smoke-stream.mjs`, run by `smoke.mjs web|macos|linux --app
  exact-live`: stream opens with held lanes, the log is whole after
  release, `clock settle` is settled with the stream open, a forced drop
  then `Reconnect` resumes whole with no duplicate, and a newer wave's
  forget closes the old connection.
- **The trial, measured (2026-09-27, one run each, loopback, 128 lanes):**

  | host | entries | messages delivered | coalesced | gaps → cursor re-asks | whole after release | settle, stream open | reconnect whole |
  |---|---|---|---|---|---|---|---|
  | web (Chrome) | 135 | 4 | 116 | 2 | 98 ms | 0 ms | 45 ms |
  | macOS | 131 | 6 | 116 | 4 | 89 ms | 1 ms | 46 ms |
  | Linux (headless, on the Mac) | 131 | 3 | 128 | 1 | 5999 ms | 4 ms | 10 ms |

  Coalescing dropped ~90% of events and cursor re-asks made the log whole
  every time, with each replay one event. Linux's 6 s is its agent
  pumping one completion per stdin line (the smoke polls every 40 ms), not
  the stream. Whether this "feels right" for a chat is still the person's
  call (Decided 3); nothing here reads a chat.

## As built — slice 3 (Claude (Opus 5.5), 2026-09-27)

- **The spelling is the URL.** A stream whose URL is `ws:` or `wss:` is a
  WebSocket; `http:`/`https:` is server-sent events. Rust: `Answer::stream(
  Request::get("wss://…"))`; TypeScript: `fetch("wss://…", { exactStream })`
  (no prelude change). The request's method, headers and body are not sent
  on any host, since a browser's `WebSocket` cannot send them; a cursor is a
  query parameter (Jetstream's `cursor`), never a header.
- **Messages.** Each text message is an `Outcome::Message` with an empty
  `event` and `id` (TypeScript sees `type: "message"`). Every other end is
  a failure, worded the same on every host: `the socket closed (1000)` (or
  `(code: reason)`) when the far side closes, `(1006)` for a connection
  dropped without a close; `the socket did not open` (natively with `:
  HTTP 404` and the like) for a refused handshake; a binary message, or one
  over the per-message ceiling, is `Refused`. Forgetting closes the socket.
- **Grant.** `net.websocket <origin>`, checked on every open (a reconnect
  included); a `net.fetch` grant for the same host admits no socket. The
  render host's CSP adds socket origins to `connect-src`.
- **Web.** `http-body.js`'s `readSocket`: the glue opens the `WebSocket`,
  never the module realm. Messages that arrive before the last was handed
  to the runner (one macrotask) coalesce to the newest.
- **Apple.** `ibex2`'s `NSURLSessionWebSocketTask` transport (an ephemeral
  session per socket; redirects refused; the platform answers pings and
  refuses an over-limit message). **Linux.** A new `ibex2` client over
  TCP and rustls with the same trust store as the HTTP transport. Both are
  `vendor/ibex2` patch 2. On the native executor a socket is a stream like
  any other: its own thread, the same 16-stream bound, the same coalescing.
- **Consumer: Exact Live's `jobFeed = jobFrames(waveId)`.** The job
  fixture's control listener upgrades `/api/frames?wave=N[&cursor=K]` and
  sends one text frame per change carrying the newest sequence as `cursor`,
  Jetstream's shape. The source is `jobEvents`'s, reading frames: a gap
  re-asks with `&cursor=`, and `Reconnect` resumes after a drop. Its origin
  is the build's control origin as `ws:`/`wss:`, and its grant is compiled
  from the same `job-origins.txt` line.
- **Fixed on the way (slice 2's web settle):** the glue counted a stream's
  whole-life promise in flight until its first message, so a `clock settle`
  already racing it waited out its 15 s deadline when that message landed
  during the wait. What is counted now ends at the first message.
- **Held by:** `ibex2`'s `transport::websocket::tests` (a local peer:
  upgrade, fragments, a ping answered, extended length, the closing
  handshake, over-limit, binary, a refused handshake, a drop, an abort) on
  both transports, and `stdlib::websocket::tests` (the grant);
  `executor_stream_tests.rs` (a local socket message by message then its
  close; a fetch grant refused; binary refused; forgetting closes it);
  `http-body.test.mjs` (the glue's socket: a burst coalesced, the close, a
  binary refusal, an abort seen by the peer); `js/tests/it/castle.rs` (the
  TypeScript spelling); `exact-live-data`'s socket cursor test; and
  `scripts/smoke-stream.mjs`, which now drives `jobFeed` beside `jobLog`
  through every step (open with held lanes, whole after release, settle,
  drop and cursor resume with no duplicate, forget closes it).

  | host | socket messages | coalesced | gaps → cursor re-asks | whole after release |
  |---|---|---|---|---|
  | web (Chrome) | 9 | 106 | 3 | 105 ms |
  | macOS | 8 | 121 | 4 | 94 ms |
  | Linux host on the Mac | 5 | 127 | 3 | 5874 ms |

  (One run each, loopback, 128 lanes; the web drive passed six runs in a
  row after the settle fix, macOS three, Linux two.)
- **The public Jetstream, by hand (2026-09-27, not in any check):** both
  `ibex2` transports on this Mac opened
  `wss://jetstream2.us-east.bsky.network/subscribe?wantedCollections=app.bsky.feed.post`
  (rustls in 0.45 s, Darwin in 1.3 s), read five commits, and reopened
  with `&cursor=<time_us>`, which replayed from that event.
- **Not verified:** a real Linux machine (the Linux host on the Mac runs
  the Darwin transport; the rustls client ran only in `ibex2`'s tests and
  the Jetstream run above, on the Mac); iOS (the same Objective-C++, not
  built here); Exact Live against the public job service, which has no
  `/api/frames` until its fixture is redeployed.

## Not in this plan

- `ReadableStream` in the module realm (user sources, BYOB, piping;
  `fetch.js:42`). A source sees parsed messages, never bytes.
- Streaming answers from native modules (grnl's partial transcription).
  They use the same runner half and are named as the next consumer.
- Outbound socket frames, binary frames, and an append-only mode (unless
  the trial fails).
- Server-side anything: the render host (LLP 1048) serves pages, not event
  streams.
