## Summary

Three modules of LLP 1133.000 §3.9's "later" row, in one RFC because
they share a shape: a person picks a device plugged into the computer,
the app opens it, and bytes go back and forth that only the app's own
code understands.

- **`@exact/serial`** is Web Serial: `requestPort`, `getPorts`, a port's
  `open` with its line settings, signals (DTR, RTS, break), and bytes in
  and out. A board's log, a GPS receiver, a scale, a modem.
- **`@exact/hid`** is WebHID: `requestDevice` by usage or vendor,
  `open`, and input, output and feature reports. A notification light, a
  macro pad's LEDs, a foot pedal, a vendor's configuration report.
- **`@exact/usb`** is WebUSB: `requestDevice` by vendor or class,
  `open`, configurations and interfaces, and control, bulk and interrupt
  transfers. A firmware updater, a device with no class driver.

**Who has them.** The web's three APIs are Chromium's alone: Chrome,
Edge and Opera on the desktop ship all three; Chrome on Android ships
WebUSB only; Safari and Firefox ship none
([MDN: Web Serial](https://developer.mozilla.org/en-US/docs/Web/API/Web_Serial_API),
[WebHID](https://developer.mozilla.org/en-US/docs/Web/API/WebHID_API),
[WebUSB](https://developer.mozilla.org/en-US/docs/Web/API/WebUSB_API)).
So every iOS browser has none. Natively, macOS, Windows and Linux
reach all three through their own device APIs, and Android serial and
USB (§10); Android's HID is absent, as Chrome on Android's is, because
reaching a HID device there takes its driver from the system (D11).
iOS, iPadOS and tvOS give an app none of them: an iPad's only path is a
driver the app's maker builds with DriverKit, tied to its own vendor ID
(D21).

**The deep choices:**

1. **One shape across the three (D1–D6).** Each module's values are
   bytes, so they are data code's (D4, as Bluetooth's are, LLP 1133.022
   D15). Each device is one per process, opened once and leased to each
   session that opens it (D5, as Bluetooth's links are). Each module
   refuses, on every target, what its web blocklist refuses, and HID
   also refuses game controllers, which `@exact/gamepad` owns (D6, D11).
2. **Who chooses the device (D2, D3).** On the web, the browser's
   chooser is the only way in. On macOS, Windows and Linux no platform
   asks the person anything, and a hand-built app shows its own list of
   ports or finds its device by vendor and product. So the modules keep
   the web's chooser as `requestPort`/`requestDevice` on every target
   that can draw one, and add one declared deviation where the platform
   has no consent to give: `attachedPorts(filters=)` and `attachedDevices(filters=)`,
   the devices plugged in now, which `open` accepts directly.
3. **Serial input loses nothing (D8).** A board's log is a byte stream,
   not a sampled value. A port has one reader, as a web `ReadableStream`
   has; each answer is every byte since the last delivered answer, from
   the first byte after `open`, a later reader starting where the last
   was delivered; and the implementation stops
   reading the operating system while that reader's unread bytes reach a
   bound sized to the line's rate, as the web stream's backpressure
   does, so a slow commit delays bytes and does not drop them.

```ts
import { serialInput, write } from "@exact/serial";

// Every byte the board sent since this reader's last delivered answer.
const { data, errors } = await serialInput({ connection, interval: 100 });
await write({ connection, data: new TextEncoder().encode("help\r\n") });
```

```ts
import { sendFeatureReport } from "@exact/hid";

// blink(1): feature report 1, "fade to RGB" ('c'), red, over 300 ms.
await sendFeatureReport({ connection: light, reportId: 1,
  data: Uint8Array.of(0x63, 0xff, 0x00, 0x00, 0x00, 30, 0x00) });
```

**Consumers.** None exists. This RFC proposes two (§12):

- **Excord's mention light** (HID): while Excord's count of unread
  mentions is above zero, a USB notification light on the desk glows red
  (a ThingM [blink(1)](https://blink1.thingm.com/), whose protocol is
  [public](https://github.com/todbot/blink1/blob/main/docs/blink1-hid-commands.md)).
  Excord already derives the count (`mentionTotal`, `apps/excord/app.contract`).
- **Bench** (`apps/bench`, new; serial and USB): a serial monitor for a
  development board, and a DFU firmware updater. Neither is asked for by
  an app today; both are proposed as the smallest real tools that use
  the modules whole (§12.2). The updater is one of
  WebUSB's own motivating cases ("device updates and diagnostics",
  [WebUSB §2.3](https://wicg.github.io/webusb/#app-updates-and-diagnostics))
  over USB's standard firmware class.

**Targets.** web (Chromium), macOS, Android, Windows and Linux for all
three, except HID on Android; iOS, iPadOS and tvOS absent, with the reasons (D21). Windows and
Linux ride the Rust host builder and the desktop loops' package
dispatch, which LLP 1133.022 D10 item 5 specifies and Charlie ruled
built now (2026-10-26).

## 1. What exists

**Nothing reads a serial port, a HID device or a USB device for an app.**
No host, package or app calls IOKit's serial, HID or USB families,
`android.hardware.usb`, `navigator.serial`, `navigator.hid`,
`navigator.usb`, Win32's HID, WinUSB or COM functions, or Linux's
hidraw, tty or usbfs nodes for an app. The hosts read **game pads**
(LLP 1133.022 §1: GameController, Android input events, the Gamepad API,
evdev, XInput), and **keyboards and pointers** through the platform's
input events. Neither is this RFC's.

**The seams it uses as built:** the package context (`destroy`, `now()`,
foreground, `origin`, `emit`, `ExactPackage.swift`); polled live sources
and the batch with a runner-held cursor (`runner/src/runner/modules/samples.rs`,
LLP 1133.013 D5); `handle<kind>`, provisional until delivered
(`handles.rs`); `release(name, args)`; cancelling a released send (LLP
1133.016 D15 item 2); `"gesture": true` on the web; Android's one
permission history (LLP 1133.008 D8 item 7); bytes
in a declaration (LLP 1133.006 D8 item 1); the declared substitute.

**The seams it uses that are accepted, not built** (each built by the
RFC that owns it; this one adds only what §9 lists):

| Seam | Where | State |
|---|---|---|
| `rust-static` and the desktop loops' package dispatch: a package's `linux/` or `windows/` crate, its trait and context, on the loop's thread | LLP 1133.022 D10 item 5 | accepted 2026-10-26; LLP 1133.022's build makes them first |
| a data reader's own cursor, landing with the commit that delivers it | LLP 1133.022 D19 item 5 | accepted 2026-10-26 |
| the substitute's event track, keyed fixture and chooser ticket | LLP 1133.022 D19 items 1–3 | accepted 2026-10-26 |
| the bytes refusal in Contract, `contract-module-bytes` | LLP 1133.022 D19 item 4 | accepted 2026-10-26 |

**The Linux host** draws to DRM/KMS or a buffer with evdev input, and
has no window system, session bus or portal (`host/linux/src/lib.rs`;
LLP 1133.025 D14). It is a kiosk's host, which is where serial and HID
devices are most common: a till's scale and receipt printer, a lab's
instrument. It presents an alert-shaped `alertdialog` and a menu, and
"a chooser, a sheet and a dialog its author lays out are not presented
yet" (`host/linux/src/presenter/top.rs`, LLP 1115.001 D10).

**No drive opens a real device it did not create:** the Mac a drive
runs on has a person's own devices attached. On 2026-10-26 Core HID's
`HIDVirtualDevice(properties:)` returned nil in an unentitled process
here, and the same probe signed with
[`com.apple.developer.hid.virtual.device`](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.hid.virtual.device)
was killed at launch: the entitlement needs a provisioning profile that
grants it. So macOS has no virtual HID device for a drive (§11).

# Part A — What the three share

## 2. One shape

### D1 — Three packages, three web APIs

Three extensions (LLP 1133 D5), each the web API of its name, because
their names collide (`requestDevice` and `getDevices` are both WebHID's
and WebUSB's) and because an app that drives a light should not link
the USB stack. Each package has `web/`, `apple/` (macOS), `android/`,
`windows/` and `linux/` implementations.

The web's object methods become functions over an id or a handle, as
LLP 1133.022 D13 made Bluetooth's:

| Web | Here |
|---|---|
| a `SerialPort`, `HIDDevice` or `USBDevice` object | a record with an `id`, the web object's attributes, and, for serial, a `name` (D7) |
| `port.open(options)`, `device.open()` | `open(port=, …)` or `open(device=)`, answering a `handle<serial>`, `handle<hid>` or `handle<usb>` (D5) |
| `port.close()`, `device.close()` | `close(connection=)` |
| `port.forget()`, `device.forget()` | `forget(port=)`, `forget(device=)` |
| `navigator.serial.getPorts()` and the `connect`/`disconnect` events | `getPorts()`, a live source that re-answers on either |
| errors as `DOMException` names | the same names as `failure(…).code` in Contract and `{code, message}` in data code |

### D2 — The chooser, by platform

`requestPort` and `requestDevice` are a person choosing one device. Who
draws the choice, and what it gives the app:

| Target | Chooser | What the choice gives |
|---|---|---|
| web (Chromium) | the browser's, inside a press (`"gesture": true`; the specifications require transient activation, `SecurityError` otherwise) | that device, for the origin, until `forget` |
| macOS | **the module's own sheet**: the matching devices, by name, updating as they are plugged in, with Cancel, in the platform's list style; Apple draws no chooser for these families | that device, remembered by the module (`getPorts`) |
| Android | the module's own list when more than one device matches, then **the system's USB permission dialog** for the chosen one ([`requestPermission`](https://developer.android.com/develop/connectivity/usb/host)); one match goes straight to the dialog | that device, until it is unplugged ("until the device is disconnected", the same page) |
| Windows | [`DevicePicker`](https://learn.microsoft.com/uwp/api/windows.devices.enumeration.devicepicker) over the device-interface selector the filters make, on the window thread | that device, remembered by the module |
| Linux | none: the painted presenter does not present a chooser yet (LLP 1115.001 D10); `requestPort` and `requestDevice` fail `NotSupportedError`, and the app lists `attachedPorts`/`attachedDevices` itself (D3) | — |

The sheet is LLP 1133.022 D14's settled answer for Bluetooth on Apple,
drawn the same way: not a package view, presented by the implementation
as the contacts picker presents its controller. A filter that matches
nothing still opens the chooser, empty, so the
person sees that their device is not there. Cancel fails `NotFoundError`
for serial (as Web Serial says) and answers an empty list for HID (as
WebHID's `requestDevice` resolves an empty sequence), and for USB fails
`NotFoundError` (WebUSB).

`getPorts()` and `getDevices()` answer the devices the person chose, or
the app opened from the attached list, and has not forgotten: the
browser's own list on the web; elsewhere the module's record (vendor,
product, serial number where the device has one, and the platform's
location), kept in the app's store and matched again when the device is
plugged in. A remembered device that is unplugged stays in the list with
`connected` false, as Web Serial's `SerialPort.connected` reads.

### D3 — The attached list: a declared deviation where nothing asks

On macOS, Windows and Linux an app may open any serial port, any HID
collection the system has not claimed, and any USB device bound to a
user-space driver, without asking anyone: a sandboxed Mac app needs the
[`com.apple.security.device.usb`](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.device.usb)
or serial entitlement, which "allow[s] your sandboxed app to interact
with USB devices", and exact2's Mac apps are hardened, not sandboxed;
Windows' Win32 device functions take no capability; on Linux the device
file's mode, which udev sets, is the only gate. Android lists every
device without asking and asks per device at open.

A hand-built app on those platforms does not show a browser's chooser.
A serial monitor has a port menu in its toolbar that changes as boards
are plugged in; a notification light's app finds the light by its vendor
and product. Making the person pick from a chooser every first time
would be a tell. So each module adds, on those four targets only:

- **`attachedPorts(filters=)`** (serial) and **`attachedDevices(filters=)`**
  (HID, USB): a live source of the matching devices plugged in now,
  re-answering on every attach and detach. HID's and USB's `filters` are
  required and must not be empty, as their `requestDevice`'s are, so an
  app names what it wants and never sweeps every device on the bus (a Mac
  has a dozen vendor HID collections of its own). Serial's are optional,
  since a port menu lists every port.
- **`open` accepts an attached device's id** as it accepts a chosen one,
  and the device joins `getPorts()`/`getDevices()`.

On the web each fails `NotSupportedError`, and `serialStatus()`'s
`attachedList` (D17) reads false there, so an app shows "Choose a
port…" instead of a menu. On Android `open` of an attached device
without permission shows the system dialog first (D17).

*Rejected:* answering `getPorts()` with every attached port where nothing
asks. Web code reads `getPorts()` as "what the person allowed" and opens
the first entry at load; on a Mac that is `/dev/cu.Bluetooth-Incoming-Port`,
and for HID an internal Apple collection. The deviation is a separate
name so that web code keeps its meaning.

### D4 — Bytes are data code's

Reports, transfers and serial data are bytes, and Contract has no bytes
type. As LLP 1133.022 D15 settles for GATT values, every name whose
answer or option carries bytes is data code's (`DataView` in
TypeScript, `Vec<u8>` in Rust, base64 on the wire, LLP 1133.006 D8
item 1), and the bake refuses it in Contract (`contract-module-bytes`).
Contract reads the status, the device lists, a connection's state and
signals, and what the app's data code makes of the bytes (a log's
lines, a light's colour). That is how a hand-built app is layered: a
protocol between the device and the view.

### D5 — One device per process, leased to each session

A device is opened once per process and each session's `open` is a
lease on it, as LLP 1133.022 makes a Bluetooth link: a `handle<kind>`
(LLP 1133.009 D10 item 10), provisional until the runner delivers it,
closed if the runner drops the reply, and closed for every handle a
session holds at its end (`destroy`). The process's open lasts while
any lease does. What a lease may share differs by family, and follows
what the platform and the web allow:

| Module | A second `open` of one device, from any session | Why |
|---|---|---|
| serial | fails `InvalidStateError` while another connection is open | on the web `open()` rejects `InvalidStateError` unless the port is closed; natively the module sets `TIOCEXCL` on POSIX, after which another process's open fails `EBUSY` ([tty_ioctl](https://man7.org/linux/man-pages/man4/tty_ioctl.4.html)), and on Windows a communications resource is opened with "dwShareMode … zero (exclusive access)" ([CreateFile](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-createfilew)); one line setting at a time |
| HID | a new lease on the shared open; each lease's readers see every input report | the OS shares a HID collection among clients; reports fan out |
| USB | a new lease on the shared open; `claimInterface` is exclusive per interface, and a claim held by another lease fails `NetworkError`, as a second browser tab's does | one claim per interface on every platform |

`close` and `destroy` end their own leases only; `forget` ends every
lease on the device, and other holders then read `connected` false and
fail `NetworkError` on their next call. Unplugging ends the process's
open; each lease reads `connected` false and its readers end (D8, D12).

### D6 — What no target offers

Each module applies its web blocklist on every target, so a device the
browser refuses is refused everywhere, and an app cannot do natively
what its web build cannot:

- **HID:** WebHID's [blocklist](https://github.com/whatwg/hid/blob/main/blocklist.txt):
  the FIDO usage page (`0xF1D0`) and, on the Generic Desktop page, the
  pointer, mouse, keyboard, keypad and system-control collections, with
  its vendor-specific entries. Plus **game controllers** (Generic Desktop
  joystick `0x04`, gamepad `0x05`, multi-axis `0x08`), which WebHID
  allows and this module does not: `@exact/gamepad` owns pads through the
  host's one registry (LLP 1133.022 D4), so a device with any
  game-controller collection is not offered at all. A declared deviation
  (D11).
- **USB:** WebUSB's protected interface classes (audio `0x01`, HID
  `0x03`, mass storage `0x08`, hub `0x09`, smart card `0x0B`, video
  `0x0E`, audio/video `0x10`, wireless controller `0xE0`) cannot be
  claimed, and its [device blocklist](https://github.com/whatwg/usb/blob/main/blocklist.txt)
  hides those devices. And **`@exact/usb` never detaches a kernel
  driver**: an interface the system's driver holds (a CDC serial port, a
  printer) fails `NetworkError` at claim (D14). On Android, where apps
  reach no kernel driver, `@exact/serial` detaches `cdc_acm`, whose job
  it takes over (D18).
- **Serial:** Web Serial's blocklist names Bluetooth service UUIDs only;
  Bluetooth RFCOMM ports are out (§15).

The blocklists are copied into each package at a pinned revision and
updated by hand, as a browser does.

# Part B — The three modules

## 3. Serial

### D7 — The names

| Name | Kind, caller | Answers |
|---|---|---|
| `serialStatus()` | live source; Contract and data | `{available, attachedList, state}` (D17) |
| `requestPort(filters=, allowedBluetoothServiceClassIds=)` | send, in a press; Contract and data | a `SerialPortRecord`, or `NotFoundError` on Cancel |
| `getPorts()` | live source | `SerialPortRecord[]`, remembered ports, each with `connected` |
| `attachedPorts(filters=)` | live source; not on the web (D3) | `SerialPortRecord[]` |
| `open(port=, baudRate=, dataBits=8, stopBits=1, parity="none", bufferSize=255, flowControl="none")` | send | `{connection: handle<serial>, port, options}` |
| `serialConnection(connection=)` | live source | `{open, connected, options}` |
| `setSignals(connection=, dataTerminalReady=, requestToSend=, break=)` | send; Contract and data | nothing |
| `getSignals(connection=)` | read | `{dataCarrierDetect, clearToSend, ringIndicator, dataSetReady}` |
| `serialInput(connection=, interval=100)` | byte-stream source, one reader per connection (D8, D19 item 2); data only | `{data, errors, done}` |
| `write(connection=, data=)` | send; data only | nothing, once the OS accepted the bytes |
| `close(connection=)`, `forget(port=)` | send | nothing |

A `SerialPortRecord` is `{id, usbVendorId, usbProductId, name,
connected, granted}`: Web Serial's `SerialPortInfo` (`getInfo()`) and `connected`,
plus `id`, `granted` (D17) and a `name` the web does not give. A native port menu shows
names ("USB JTAG/serial debug unit", "Bluetooth-Incoming-Port"), so
`name` is the USB product string where the port is a USB device's, or
the platform's port name (`cu.usbmodem1101`, `COM3`, `ttyACM0`); on the
web it is empty. `filters` are Web Serial's `{usbVendorId,
usbProductId}`.

`open`'s options and their defaults are Web Serial's
`SerialOptions`: `baudRate` required; `dataBits` 7 or 8; `stopBits` 1
or 2; `parity` `none`, `even`, `odd`; `flowControl` `none` or
`hardware`; `bufferSize` above zero, the size of each read from the
OS, as on the web (D8 says what bounds the retained bytes).
An invalid option fails `TypeError`; a port already open fails
`InvalidStateError`; an OS refusal fails `NetworkError`, as the
specification's `open()` steps say. Each target's own maximum
`bufferSize` and baud rates are checked as the specification
allows ("larger than the implementation is able to support").

### D8 — Reading loses nothing

A serial port is a stream: a board's log line split across two answers
must arrive whole, and a byte missed is a corrupt line. The web gets
this from a `ReadableStream` with one reader and backpressure: the
stream is set up with its `highWaterMark` at the port's `bufferSize`,
and its pull step reads the OS for "up to desiredSize bytes", so the
browser reads only while the queue has room
([Web Serial, `readable`](https://serial.spec.whatwg.org/#dom-serialport-readable)).
Here:

- **A byte stream, not a sample.** `serialInput` is a polled source
  (LLP 1133.009 D10 item 7) of a new kind, `"stream"` (D19 item 2), not
  LLP 1133.013 D5's `"samples"`: there is no "latest value", no grid and
  no `dropped`. Its cursor is a position in the connection's stream in
  which each byte and each of D9's non-fatal errors is one unit, so an
  answer holding only an error still moves it; an error's `at` is its
  byte offset.
- **One reader per connection.** The reader is keyed by the `connection`
  argument alone, whatever its `interval`; a second data resource
  reading the same connection fails `InvalidStateError` ("locked"), as a
  second `getReader()` throws on the web, and the same resource changing
  its `interval` stays the one reader with its cursor. The reader is
  identified as LLP 1133.022 D19 item 5 identifies a data reader, and
  its cursor lands only with the commit that delivers its answer.
- **Each answer is every byte since the delivered cursor.** The runner
  asks every `interval` (default 100 ms, at least 50) while the reader
  reads, passing the delivered cursor as `after`. The first ask passes
  none, which means from the connection's position: for its first
  reader every byte since `open`, so a board's boot log that arrived
  before the first poll is read, and for a later reader every byte no
  earlier reader was delivered. A reader's release carries its
  delivered cursor (D19 item 2), and the implementation frees through
  it; that is the connection's position. The answer carries `data` and
  `errors`, D9's non-fatal errors at their byte offsets. An answer the
  runner discards is answered again from the same cursor: nothing is
  consumed until delivered.
- **Backpressure.** The implementation keeps the bytes after the
  delivered cursor, and stops reading the OS while they reach the
  **retained bound**; it frees bytes as each delivered cursor arrives
  with the next poll. Bytes then wait in the OS's and the device's
  buffers, and with `flowControl: "hardware"` the port deasserts RTS, as
  on the web. The retained bound is the larger of `bufferSize` and two
  seconds of the line at its baud rate (`baudRate / 10 * 2` bytes: 23 KB
  at 115,200 baud), at most 16 MiB. The web reads continuously, so its
  255-byte default suffices there; a polled reader holding bytes until a
  commit delivers them needs the line's rate times the time between
  deliveries, and two seconds covers twenty missed 100 ms polls. A port
  without flow control that outruns a reader stalled longer than that
  loses bytes in the UART, not in exact2, as it would on the web, and
  the OS reports it as an overrun (D9). A declared deviation: on the web
  `bufferSize` is also the stream's high-water mark.
- **The end.** A fatal error or a close ends the stream: the last answer
  carries `done: true`, and the reader's next read fails
  `InvalidStateError` until the app opens the port again.

At 115,200 baud this is one commit per `interval` (ten a second at the
default), not one per OS read. Each answer is stamped on the session
clock; serial has no device time.

*Rejected:* the batch with `history` and `dropped` of LLP 1133.013 D5,
which keeps the latest values and counts the rest dropped. It suits a
sensor's samples, where the newest supersedes the old; a byte stream has
no newest byte.

`write` sends bytes in order per connection; it answers when the OS has
accepted them (`write(2)` returned on POSIX, `WriteFile` completed on
Windows, the bulk transfer completed on Android), as the web's
`WritableStreamDefaultWriter.write` resolves when the sink took the
chunk. A write released before it completes is cancelled where the
platform can (LLP 1133.016 D15 item 2): bytes already accepted are sent.

### D9 — Signals, errors and closing

`setSignals` and `getSignals` are Web Serial's: DTR, RTS and break out;
DCD, CTS, RI and DSR in. They are booleans, so Contract may send and
read them. Bench's **Reset board** button is two `setSignals` 100 ms
apart, RTS asserted and then released, which holds the chip's reset
line low and lets it go on boards wired as Espressif's are ("DTR and RTS
control lines are in turn connected to GPIO0 and EN",
[Espressif](https://docs.espressif.com/projects/esptool/en/latest/esp32s3/advanced-topics/boot-mode-selection.html)).
Where a transport cannot carry a signal (CDC-ACM has no CTS), it reads
false, and the implementation's conformance notes say which.

Errors, as Web Serial classifies them. A declared deviation: on the
web a non-fatal error errors the `readable`, and the page gets a new one;
a polled source has no stream object to replace, so here each non-fatal
error is an entry in the answer at its byte offset, and reading goes
on, which is what a web reader that takes the new `readable` sees.

| Error | Web | Here | Source |
|---|---|---|---|
| `BreakError`, `FramingError`, `ParityError`, `BufferOverrunError` | non-fatal: the readable errors, a new one follows | an entry in `errors` at its offset; reading continues | POSIX `PARMRK` marks; Windows `ClearCommError` (`CE_BREAK`, `CE_FRAME`, `CE_RXPARITY`, `CE_OVERRUN`); CDC-ACM's `SERIAL_STATE` notification |
| `NetworkError` | fatal: the port was unplugged | `done: true`; the connection reads `connected` false | `read` fails `EIO` or `ENXIO`, or reads end of file, on POSIX; `ERROR_ACCESS_DENIED` or `ERROR_BAD_COMMAND` on Windows; the device detached on Android |
| `UnknownError` | non-fatal OS error | an entry in `errors` | any other |

`close` ends the reader with `done: true` and closes the port when its
lease is the last. An unplugged port's connection stays a handle reading
`connected` false; plugging the same port in again does not reopen it,
as on the web.

## 4. HID

### D10 — The names

| Name | Kind, caller | Answers |
|---|---|---|
| `hidStatus()` | live source | `{available, attachedList, state}` |
| `requestDevice(filters=, exclusionFilters=)` | send, in a press | `HIDDeviceRecord[]`, empty on Cancel |
| `getDevices()`, `attachedDevices(filters=)` | live sources | `HIDDeviceRecord[]` |
| `open(device=)` | send | `{connection: handle<hid>, device}` |
| `inputReports(connection=, reportId=, interval=100, history=16)` | polled batch source; data only | `{reports: [{reportId, data, at}], dropped, interrupted}` |
| `sendReport(connection=, reportId=, data=)`, `sendFeatureReport(…)` | send; data only | nothing |
| `receiveFeatureReport(connection=, reportId=)` | call; data only | `DataView` |
| `close(connection=)`, `forget(device=)` | send | nothing |

A `HIDDeviceRecord` is `{id, vendorId, productId, productName,
collections, connected, granted}`: WebHID's `HIDDevice` attributes and
D17's `granted`, with `collections` its `HIDCollectionInfo` tree (usage page, usage, type,
report ids and their items' sizes and counts) as plain numbers and
strings, which Contract may read. `filters` and `exclusionFilters` are
WebHID's `{vendorId, productId, usagePage, usage}`; `requestDevice`'s
are required, as WebHID's are. `reportId` is 0 for a device that uses
no report ids, as WebHID says. A report the device does not define, or
a blocked one (D11), fails `NotAllowedError`; a send while the
connection is closed fails `InvalidStateError`.

### D11 — What HID never offers, and why

A device is offered (in a chooser or an attached list) by its
**top-level collections**, with two rules.

- **The blocklist is applied per report, as WebHID applies it.** A
  report in a collection on WebHID's blocklist (keyboards, mice, keypads,
  system controls, security keys) is a *blocked report*: an input one is
  dropped before it reaches any batch, and a send or `receiveFeatureReport`
  of one fails `NotAllowedError`
  ([WebHID §15](https://wicg.github.io/webhid/#blocklist), and its
  input-report and send steps). A device whose every collection is
  blocked is not offered; one with an allowed collection is, so a
  keyboard's separate lighting collection stays reachable on Windows and
  Linux (macOS is stricter, below). The filter is
  the module's own, in its read loop and before each send, on every
  target, because the platform's handle can span an interface that holds
  several collections: an `IOHIDDevice` on macOS and a `hidraw` node on
  Linux are each one interface.
  Windows enumerates each top-level collection as a device of its own
  ([HID collections](https://learn.microsoft.com/windows-hardware/drivers/hid/opening-hid-collections)),
  so a blocked one there is never opened at all. An interface with more
  than one report structure prefixes its reports with report ids (HID
  1.11's Report ID item), which is what places each report in its
  collection.
- **A device with any game-controller collection is not offered at
  all**, since its other collections drive the same pad.

Each platform also guards the blocklist's groups by its own rules, and
on macOS that makes the module stricter:

- **macOS:** opening a keyboard needs the person's Input Monitoring
  approval ("Interacting with certain HIDs, such as keyboards, require
  user approval", [Communicating with HID devices](https://developer.apple.com/documentation/corehid/communicatingwithhiddevices)),
  which the module never asks for, so an `IOHIDDevice` that holds a
  keyboard or keypad collection is not offered on macOS, its other
  collections included.
- **Windows:** the system's keyboard and mouse mappers hold those
  collections ([keyboard and mouse HID clients](https://learn.microsoft.com/windows-hardware/drivers/hid/keyboard-and-mouse-hid-client-drivers)),
  and WinRT's HID API calls keyboards and mice "system reserved devices"
  ([Windows.Devices.HumanInterfaceDevice](https://learn.microsoft.com/uwp/api/windows.devices.humaninterfacedevice)).
- **Linux:** a keyboard is an evdev device the compositor or the kiosk
  host reads. Its `hidraw` node is the whole interface, and reading it
  does not take the keyboard from the host, so a node that also holds an
  allowed collection is offered, and the keyboard's reports are dropped
  as above.
- **Android: absent.** Android reaches a USB HID device only by
  claiming its interface with `force=true`, which detaches the kernel's
  HID driver ("true to disconnect kernel driver if necessary",
  [UsbDeviceConnection](https://developer.android.com/reference/android/hardware/usb/UsbDeviceConnection#claimInterface(android.hardware.usb.UsbInterface,%20boolean))),
  and can read the report descriptor that says what the interface is
  only after the person's permission and that claim (HID 1.11 §7.1;
  usbfs claims an interface for a request addressed to it,
  `check_ctrlrecip` in
  [devio.c](https://github.com/torvalds/linux/blob/master/drivers/usb/core/devio.c)).
  Whether the driver it would detach is giving the system input cannot
  be known beforehand: a keyboard or a pad need not use the boot
  subclass, and a receiver's paired keyboards and mice appear under
  their own product ids, through an interface with no input device of
  its own (Logitech's receivers,
  [hid-logitech-dj.c](https://github.com/torvalds/linux/blob/master/drivers/hid/hid-logitech-dj.c)).
  A detached driver returns when the interface is released, but not when
  the process dies holding it (`usbdev_release` in devio.c). So
  `hidStatus().available` is false on Android, as WebHID is absent from
  Chrome on Android. A Bluetooth HID device on Android is absent too: the
  system binds it as input.

  *Rejected:* listing HID interfaces by vendor and product, excluding
  boot keyboards and mice and anything Android's `InputManager` reads,
  then claiming to read the descriptor: neither test is complete, so a
  person's keyboard or receiver could stop working until replugged.

Pads are refused because `@exact/gamepad` already reads them through one
registry per process (LLP 1133.022 D4), with their lights and rumble
(D6 there), and a second reader writing a pad's output reports would
fight the registry for its motors and light. A pad's raw reports are
therefore out on every target: gamepad's tier 3 hatches give the
platform's pad objects, not its reports (LLP 1133.022 D8). A declared
deviation: WebHID offers pads, and on the web this module refuses a
device with a game-controller collection before the chooser shows it
(an `exclusionFilters` entry per pad usage, added to the app's own).

### D12 — Input reports are a batch

Input reports are a device's state, sent when it changes or at its
interval: the newest matters most, and a slow reader may skip. So
`inputReports` is LLP 1133.013 D5's batch with the runner's cursor, as
LLP 1133.022 D15 makes a characteristic's notifications: the first
answer the latest report, each later one every report since the
reader's last delivered answer, at most `history` (default 16, at most
1,024), `dropped` counting the rest, `interrupted` while delivery paused
(an unplug). Several readers may read one
connection, each with its own cursor (LLP 1133.022 D19 item 5). The
first reader of a connection starts the platform's input callback
(`IOHIDDeviceRegisterInputReportCallback`, an overlapped `ReadFile`
loop, a `read(2)` loop on `hidraw`); the last `release(name, args)` stops it.

Output and feature reports are sends in order per connection, answered
when the platform's call returns: `IOHIDDeviceSetReport` with
`kIOHIDReportTypeOutput` or `…Feature`; `WriteFile` or
`HidD_SetOutputReport`, and [`HidD_SetFeature`](https://learn.microsoft.com/windows-hardware/drivers/ddi/hidsdi/nf-hidsdi-hidd_setfeature);
`write(2)` and `HIDIOCSFEATURE` on `hidraw`
([hidraw](https://docs.kernel.org/hid/hidraw.html)).

| `requestDevice(filters=, exclusionFilters=)` | send, in a press | a `USBDeviceRecord`, `NotFoundError` on Cancel |
| `getDevices()`, `attachedDevices(filters=)` | live sources | `USBDeviceRecord[]` |

A `USBDeviceRecord` is WebUSB's `USBDevice` attributes (`usbVersion…`,
`deviceClass`, `deviceSubclass`, `deviceProtocol`, `vendorId`,
`productId`, `deviceVersion…`, `manufacturerName`, `productName`,
`serialNumber`, `configuration`, `configurations` with their interfaces,
alternates and endpoints) plus `id`, `connected` and `granted` (D17); all are numbers and
strings, which Contract may read. On Android `serialNumber` is null
until the device is granted, since
[`UsbDevice.getSerialNumber`](https://developer.android.com/reference/android/hardware/usb/UsbDevice#getSerialNumber())
throws `SecurityException` without permission; a filter's
`serialNumber` there matches an ungranted device on its other fields,
and `open`, after the system dialog, fails `NotAllowedError` when the
granted device's serial number is not the filter's. `setup` is WebUSB's
`USBControlTransferParameters` (`requestType` `standard`, `class` or
`vendor`; `recipient` `device`, `interface`, `endpoint` or `other`;
`request`, `value`, `index`), and `status` its `USBTransferStatus` (`ok`,
`stall`, `babble`). Filters are WebUSB's `{vendorId, productId,
classCode, subclassCode, protocolCode, serialNumber}`, required.

The errors are WebUSB's: a transfer on an unclaimed interface or a
closed device fails `InvalidStateError`; a control transfer whose
recipient is an interface the connection has not claimed fails
`InvalidStateError`; a protected interface fails `SecurityError`; an OS
failure `NetworkError`. A transfer is a call, not a source: data code
that reads an interrupt endpoint calls `transferIn` again on each
answer, as web code does. A pending transfer whose reply no one reads
is aborted where the platform can (LLP 1133.016 D15 item 2):
`IOUSBHostPipe`'s abort, `WinUsb_AbortPipe`, and usbfs's
`USBDEVFS_DISCARDURB` on Linux and Android (D14), control transfers
included. Aborting never closes the connection.

### D14 — Each platform's USB, and the driver rule

| Target | Opens | A device it cannot open |
|---|---|---|
| macOS | [`IOUSBHostDevice`](https://developer.apple.com/documentation/iousbhost/iousbhostdevice) and [`IOUSBHostInterface`](https://developer.apple.com/documentation/iousbhost/iousbhostinterface), macOS 10.15+, with their pipes; the module never asks to capture an interface a kernel driver holds | an interface a driver holds (a CDC port: `AppleUSBCDCACM`): `NetworkError` at claim |
| Windows | **WinUSB** (`WinUsb_Initialize` on the device interface's file), Microsoft's user-mode driver for a generic device ([WinUSB](https://learn.microsoft.com/windows-hardware/drivers/usbcon/using-winusb-api-to-communicate-with-a-usb-device)) | a device not bound to `winusb.sys`: not offered. A device's maker binds it with Microsoft OS descriptors ([automatic WinUSB](https://learn.microsoft.com/windows-hardware/drivers/usbcon/automatic-installation-of-winusb)); otherwise a person installs the binding, as [Chrome's WebUSB guide](https://developer.chrome.com/docs/capabilities/usb) says |
| Linux | usbfs, `/dev/bus/usb/BBB/DDD`, with `USBDEVFS_CLAIMINTERFACE` and the URB ioctls ([usbfs](https://docs.kernel.org/driver-api/usb/usb.html)); never `USBDEVFS_DISCONNECT` | an interface a kernel driver holds: `NetworkError`; a node udev left unreadable: `NotAllowedError` (D17) |
| Android | [`UsbManager`](https://developer.android.com/reference/android/hardware/usb/UsbManager) for the list, the permission and the `UsbDeviceConnection`; its file descriptor's I/O by usbfs, as on Linux, in the host (below); never `USBDEVFS_DISCONNECT` | an interface the kernel's driver holds: `NetworkError` |

**Android's I/O is usbfs, in the host.** Android's public calls lose
what WebUSB answers: `controlTransfer` and `bulkTransfer` return a
length or "negative value for failure"
([UsbDeviceConnection](https://developer.android.com/reference/android/hardware/usb/UsbDeviceConnection)),
a `UsbRequest`'s completion keeps the URB's length and drops its status
(`usb_request_wait` in
[libusbhost](https://android.googlesource.com/platform/system/core/+/refs/heads/main/libusbhost/usbhost.c)),
so a failed bulk transfer reads as a short success, and there is no
endpoint clear-halt and no public reset (`resetDevice` is a hidden
system API,
[UsbDeviceConnection.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/hardware/usb/UsbDeviceConnection.java)).
The connection's file descriptor is public
(`UsbDeviceConnection.getFileDescriptor`) and is a usbfs node, so the
Android host's Rust issues on it the ioctls the Linux implementation
issues on its own node: URBs with their status, `USBDEVFS_CLEAR_HALT`,
`USBDEVFS_RESET`, `USBDEVFS_DISCARDURB`. Chromium's WebUSB on Android
does the same
([usb_device_handle_android.cc](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/services/device/usb/usb_device_handle_android.cc)
over
[usb_device_handle_usbfs.cc](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/services/device/usb/usb_device_handle_usbfs.cc)).
It is the host's code, one per process with the permission broker (D19
item 1), in the library the Android app already loads
(`libexactcanvas`, built from `host/linux/src/canvas` and loaded by
`host/android/canvas/.../Native.kt`), so no package carries native code
(LLP 1133.001's Kotlin row). Android then answers as Linux does.

*Rejected:* Kotlin's public calls alone, recovering a stall from the
endpoint's halt bit: a disconnect, babble or protocol error sets no halt
and still read as `ok`, and `clearHalt` and `reset` stay out of reach.

**Windows.Devices.\* is not used for I/O.** The roster names it, and
each of its three APIs needs a device capability in a packaged app's
manifest: `<DeviceCapability Name="usb"/>` for `Windows.Devices.Usb`,
which also reaches only WinUSB devices and refuses eight device classes
([Windows.Devices.Usb](https://learn.microsoft.com/uwp/api/windows.devices.usb));
`humanInterfaceDevice` for `HidDevice`, which also refuses the keyboard,
consumer, digitizer and sensor pages
([Windows.Devices.HumanInterfaceDevice](https://learn.microsoft.com/uwp/api/windows.devices.humaninterfacedevice));
and `serialCommunication` for `SerialDevice`, "required to use the
SerialDevice class"
([SerialDevice](https://learn.microsoft.com/uwp/api/windows.devices.serialcommunication.serialdevice)).
The Windows host is unpackaged (LLP 1115.004 D15), so it can declare
none of them. Win32's WinUSB, `hid.dll` and COM functions need no
capability, and are what the Windows implementations use: the COM
functions
([SetCommState](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-setcommstate),
[EscapeCommFunction](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-escapecommfunction))
and `hid.dll`, and WinRT only for the `DevicePicker` and its selectors.
Enumeration and plug events are Configuration Manager's
([CM_Get_Device_Interface_List](https://learn.microsoft.com/windows/win32/api/cfgmgr32/nf-cfgmgr32-cm_get_device_interface_listw),
[CM_Register_Notification](https://learn.microsoft.com/windows/win32/api/cfgmgr32/nf-cfgmgr32-cm_register_notification)).

Isochronous transfers are out until a consumer asks (§15).

### D17 — LLP 1133.002 §4 for the three

| Target | `state` | A record's `granted` |
|---|---|---|
| web | `granted`, or `denied` where the policy or the browser's setting blocks the API | true for every remembered device |
| macOS, Windows | `granted` | true |
| Linux | `granted` | false for a node the process cannot open (`EACCES`): `open` would fail `NotAllowedError`, and the recipe names the udev rule ([udev](https://man7.org/linux/man-pages/man7/udev.7.html)) |

dialog has no "don't ask again", so `state` stays `prompt` and the

**Who may.** Every status, `getPorts`, `getDevices`, the attached lists
and the records are facts any caller reads. `requestPort` and
`requestDevice` open a chooser, so a tool's or a wake's fails
`person-required`; on the web they must run in a press. `open` is
`"origin": "app"`, `"foreground": true` (LLP 1133.009 D10 item 8):
starting a device needs the person present, and on Android `open` may
show a dialog. Every write, report and transfer, `setSignals`,
`claimInterface`, `selectConfiguration` and their kin are
`"origin": "app"` alone: a tool does not send bytes to a device (a
heater's controller, a door's relay) in the person's name, while the
app's own code keeps driving a connection the person opened when the
app is not in front, which is the point of a mention light. A tool's
read of a connection the app already reads joins it as it runs and
never holds it; serial input has one reader (D8), which a tool may not
be.

**Foreground.** An open connection keeps reading and writing while the
app is hidden on macOS, Windows and Linux, where a desktop app runs on
(a serial monitor logs behind the editor). On Android the connection
stays open while the process lives, and the module keeps reading while
the process runs; when the system freezes a cached process, readers
answer `interrupted` on return, and serial input resumes, losing nothing
the device's buffer held (D8). A background serial logger on Android is
LLP 1133.033's foreground service, out here.

**Recover.** `openURL("app-settings:")` has nothing to change on any
target. On the web the recipe explains the browser's site setting; on
Linux it names the udev rule; on Android the person unplugs and plugs
in again, or the app asks again.

## 9. Packaging, seams and callers

### D18 — The packages

```
packages/serial/            "@exact/serial"
  exact.json                D7's names and shapes, the grant, the substitute
  test/                     the conformance suite; a fixture app
  web/ apple/ android/ windows/ linux/
packages/hid/  (the same, D10, without android/)
packages/usb/  (the same, D13)
```

Each `apple/` is Swift in the module's dylib, linking IOKit (and
IOUSBHost for USB); none links Core HID, which is macOS 15+ while
exact2's Mac apps start at 14 (`host/apple/Package.swift`). Each
`android/` is Kotlin source in the one Android project, needing no Maven
library (`android.hardware.usb` is the platform's). Each `windows/` and
`linux/` is a Rust crate, compiled by `rust-static` and called by the
desktop loop's dispatch (§1's table): Windows' with `windows-sys`
features for HID, WinUSB, the COM functions and Configuration Manager,
and WinRT's `DevicePicker` from the `windows` crate. The three packages share no native code: 1133.001 forbids
native code from a transitive package. What each needs once per process
on Android is the host's (D19 item 1): the permission broker and the
usbfs I/O.

**Android serial is CDC-ACM in Kotlin.** Android exposes no serial
device to apps below API 37, and its API 37 `SerialManager` answers a
file descriptor whose line settings need `tcsetattr`, which
`android.system.Os` does not offer
([Os](https://developer.android.com/reference/android/system/Os)); a
JNI shim would be the first native code in an Android package, against
LLP 1133.001's Kotlin row. So the implementation speaks the USB CDC-ACM
class itself on every API level, in Kotlin, its transfers through the
host's usbfs I/O as `@exact/usb`'s are (D14):
`SET_LINE_CODING` for baud, bits and parity, `SET_CONTROL_LINE_STATE` for
DTR and RTS, `SEND_BREAK`, the data interface's bulk endpoints, and
`SERIAL_STATE` notifications for the inputs (the PSTN subclass document in CDC 1.2).
It claims the two CDC interfaces with `force=true`, since
Android's own `cdc_acm` driver, where the kernel has one, gives apps
nothing, and releases them at `close`, which gives that driver the port
back (Android's `releaseInterface` issues `USBDEVFS_CONNECT`); after a
crash the port stays without it until replugged, which no app on
Android misses. Vendor bridges (FTDI, Silicon Labs CP210x, WCH CH34x) speak
their own protocols and are not offered on Android until a consumer's
board needs one (§15). The ESP32-S3's built-in USB serial is CDC-ACM
([Espressif](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/usb-serial-jtag-console.html)).

### D19 — Seam additions

Beyond the items of §1's table that this RFC inherits:

1. **The Android host's USB broker.** `UsbManager.requestPermission`
   takes a `PendingIntent` and answers by broadcast; two packages asking
   for one device show two dialogs. The host keeps one receiver and one
   pending request per device, in the package context
   (`context.usb.requestPermission(device) -> Boolean`), and fans attach
   and detach broadcasts out to every package that listens, so serial
   and USB on one composite board (a CDC port and a DFU interface, as
   many development boards have) ask once. It also does a connection's
   I/O (D14): `context.usb.transfer`, `clearHalt`, `reset` and `cancel`
   over the connection's file descriptor, in the host's Rust, each
   answering WebUSB's status. A one-per-process object kept
   by the host, as LLP 1133.025 D11 item 2 (in Review) proposes for the
   hot keys.
2. **A byte-stream source.** A declaration's `"stream": {"key":
   "connection"}` makes a polled source the runner treats as D8 says:
   one reader per value of the named argument, whatever the others
   (a second fails `InvalidStateError`); the reader's delivered cursor
   passed as `after` from its second ask, none on its first, and with
   its `release(name, args)`, so that the next reader of the connection
   starts where this one was delivered; no samples
   generator, no `history` and no `dropped`; and a substitute fed by the
   event track (LLP 1133.022 D19 item 1) as one byte string per event.
   It needs LLP 1133.022 D19 item 5's data-reader identity and cursor
   landing; the samples machinery (`samples.rs`) is not reused, since its
   first answer is the latest value with an empty batch.
3. **The test build's injected device.** A development build reads
   `EXACT_DEVICE_FIXTURE` (a path) and offers what it names beside the
   platform's devices: a serial port at a pseudo-terminal's path, opened
   with the same termios code as a real port; a HID or USB device whose
   reports and transfers go to an in-process fake below the module's
   platform calls. A release build compiles none of it. It is how a
   drive exercises a native implementation without a real device (§11).
4. **A keyed fixture's sequence.** Where LLP 1133.022 D19 item 2's
   fixture value at a key is a list, the substitute answers its entries
   one per call in order and then repeats the last, and
   `state.extensions.<module>` shows how far each list has gone. Any
   device whose answer to one request changes as it is driven uses it.

### D20 — Callers

Contract reads every status, device list, record and
`serialConnection`, and sends `requestPort`/`requestDevice` (from a
press), `open`, `close`, `forget`, `setSignals`, `claimInterface`,
`releaseInterface`, `selectConfiguration`, `selectAlternateInterface`,
`clearHalt` and `reset`. Data code calls everything, and alone the bytes
names (D4). Each status is `sync` on macOS, Windows and Linux.

### 12.2 Bench (serial and USB)

No app in the repository reads a board, and none asks to. **Bench**
(`apps/bench`, new; macOS, Windows, Linux, Android, the web) is the
smallest real tool that uses serial and USB whole: a serial monitor, and
a firmware updater for boards in USB DFU mode. The board its drives name
is an ESP32-S3, the chip of the out-of-tree port LLP 1124 §1 describes,
whose built-in USB serial port is CDC-ACM.

**The serial monitor (serial):**

- A toolbar: the **port menu** (`attachedPorts()` on native; on the web
  **Choose port…** and the remembered ports from `getPorts()`), the
  **baud rate** (115,200 by default; a menu of the standard rates), the
  line ending (none, LF, CR, CR LF), **Connect**/**Disconnect**, and
  **Reset board** (D9).
- The log: lines in the platform's monospaced font, with timestamps,
  following the end unless the person scrolls up; **Clear**; a send
  field whose Return writes the line with the chosen ending.
- **Data code (`serial.ts`):** reads `serialInput` at 100 ms,
  decodes UTF-8 across answers (a code point split
  between two answers stays whole), splits lines, keeps the last 10,000
  in its own store and answers the visible window; marks D9's errors in
  the log ("— break —").
- **States:** `available` false: "This browser has no serial ports";
  a port unplugged: "Disconnected", and Connect again when it returns;
  a port held elsewhere: "In use" from `InvalidStateError` (another
  session of Bench, D5) or `NetworkError` (another program, refused by
  `TIOCEXCL` or Windows' exclusive open);
  `granted` false on Linux: the udev line.

**The firmware updater (USB):** for a board in DFU mode: an STM32 in its
system bootloader (DfuSe, ST's extension of DFU 1.1,
[AN3156](https://www.st.com/resource/en/application_note/an3156-usb-dfu-protocol-used-in-the-stm32-bootloader-stmicroelectronics.pdf)),
or any device whose firmware has a DFU 1.1 interface (TinyUSB's DFU
class, [TinyUSB](https://docs.tinyusb.org/en/latest/)). A person chooses
a `.bin` and the board, and Bench writes it with a progress bar.

- **Contract:** the DFU interfaces from `attachedDevices(filters=[{classCode: 0xFE, subclassCode: 0x01}])`
  (the application-specific class, DFU subclass, [class codes](https://www.usb.org/defined-class-codes));
  on the web **Choose board…**; the file from an `input type="file"`,
  as Excord's composer takes its attachments; **Update**.
- **Data code (`dfu.ts`):** DFU 1.1 over control transfers to the
  interface: `GET_STATUS`, `CLR_STATUS`, `DNLOAD` in `wTransferSize`
  blocks with `bwPollTimeout` waits, the zero-length `DNLOAD` that ends
  it, and manifestation; DfuSe's set-address and erase commands for an
  STM32. Unit-tested in Bun against a fake device that follows the DFU
  state machine.
- **States:** a Windows board not bound to WinUSB is not listed, and the
  page says how to bind it (D14); the board leaves DFU mode on success
  and the list empties.

Why Bench rather than waiting: a serial monitor is the everyday tool of
anyone with a development board on a desk, and it exercises
everything in serial that can fail (an unplugged board, a held port, a
fast log, signals); DFU is USB-IF's class standard for firmware
updates, which ST's system bootloader and TinyUSB both implement, so one
small updater covers many boards, and it
exercises WebUSB's core: a filter by class, claiming an interface,
alternate settings, and control transfers in both directions. It does
not exercise bulk or interrupt transfers; the conformance suite does.
§17 question 2 asks whether USB is built for Bench now.

## 14. What reaches beyond these modules

- **The desktop loops' package dispatch** (LLP 1133.022 D10 item 5) is
  ruled and owned by that RFC's build; this RFC's Windows and Linux
  stages wait on it. The Linux kiosk host is where serial and HID devices
  are most common, so it is the dispatch's second user after gamepad.
- **A chooser on the painted hosts** (LLP 1115.001 D10). Linux has none;
  Windows has the system's `DevicePicker` only because WinRT offers one.
  Bluetooth's Linux cell (LLP 1133.022 D20) waits on the same thing.
- **The Android host's USB broker** (D19 item 1) is a host service any
  later USB-backed module on Android would share.
- **Windows' WinRT device APIs are unusable unpackaged.** Every device
  module on Windows (Bluetooth's GATT client too, which LLP 1133.022 plans
  over WinRT) should check, before it is built, that its WinRT calls need
  no package capability; serial, HID and USB do, so this RFC uses Win32.
  If the Windows host ever becomes packaged (LLP 1115.004 D15's sparse
  package), each module's capability is derived from its grant row.
- **The test build's injected device** (D19 item 3) is general: any
  module whose platform has no virtual device can use the same switch.
