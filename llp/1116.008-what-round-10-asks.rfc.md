## D1. The app's server: one lifecycle, never silent

- `test` and `verify` start the app's server on an empty database whenever the app has one. Whether the
  server reads `DB` is judged over the code it runs (its entry and the local modules it imports), not one
  spelling in one file. When it does not, the run stops before the first test with one line naming the
  entry and the fix (`new Database(process.env.DB ?? 'data.db')`), never a silent run without a server.
  The entry is the one app.json's `commands.server` names, else `server.ts`.
- `agent` starts the app's server for a drive when nothing answers at app.ts's `API`, on a database of its
  own kept with the drive's `--storage` name (so a second drive on that name sees the first's data, as the
  client's storage does), never the dev one; it says so in one line and stops only what it started.

Measure: no diary loses time to a missing server.

## D2. Fewer steps: screenshots and the dev server

- **`verify`'s captures are the screenshots.** They already cover the first screen and every test end, light
  and dark, phone and desktop. `verify --shots <dir>` also copies them there, named by screen; start-here
  and `AGENTS.md` say in one line that a screen you want captured is a test's end, and that one drive takes
  any others (`resize`, `prefer prefers-color-scheme dark` and `screenshot` in one drive).
- **No dev server to check the app.** `web --help` stops teaching the background recipe (builders followed
  it into five steps); it says the dev loop is for a person and `verify`, `test` and `agent` serve their own.
  `verify` ends by naming the command a person opens the app with.
- **Never a stale build.** `test ios` and `verify ios` rebuild when the sources changed since the build they
  would run, and say so; two builds started together don't leave either stale (polls, unit-converter).
- A test's own `screenshot` steps join `verify --shots`, so a state mid-journey is captured without a drive.

Measure: commands per build (r10: GPT median 36, Muse 61); screenshot drives and dev-server steps in the
logs.

## D3. A fixed control under the bar goes with an inline title

A large title over fixed content between the bar and a scroller never collapses (LLP 1115.000 D11 keeps
it still, so nothing sits under the bar); the winning SwiftUI team-kanban kept its persona control fixed
under an inline title. start-here's header pitfall says so in a line: a fixed control under the bar goes
with `aria-level=2`; one that may scroll away goes in the list's first section. `pattern rest` and
`rest-backend` keep their switcher fixed and their title inline. The bar's material over the fixed band
(team-kanban: "cards clip hard under the control") is D11's; QUEUE.

## D4. The swipe row swipes as UIKit's

In an iOS grouped list, a row whose actions UIKit draws (`swipeContent`, LLP 1116.001 D1) opens them on a
short swipe, as a native list does: the row's own horizontal snap scroll yields to the list's swipe there.
(grocery-list: "needs a longer drag than native".)

## D5. The stepper's bounds hold for a typed value

On iOS and the Mac, a number input with a stepper clamps a typed value to `min` and `max` when the edit
commits (`change`), as the stepper itself does; the web keeps the browser's own validation. (grocery-list:
250 saved past a max of 99.)

## D6. RoundButton's light hues, the Clock's way

`RoundButton` with a light hue (green, mint, teal, cyan, yellow, orange) draws the tinted style, the hue at
low opacity under label-coloured ink, as the Clock app's Start does, instead of a saturated fill under black
(trivia). Saturated hues keep the filled style under white. It passes `check` in both schemes, and it is compared by
screenshot with UIKit's own tinted button on the same OS before it lands; an authored fill, foreground or
style wins.

## D7. The iOS check judges a menu's label as the platform's ink

A picker's or menu button's label drawn in the accent is the platform's control label, judged at 3:1 as a
button's title already is (LLP 1116.007 D3.10), not as body text at 4.5:1 (countdowns, expense-tracker:
indigo at 3.9:1 in dark). Only labels the platform draws; text an author colours with the accent is judged
as it is. And a platform default passes `check`: the web's `destructive=true` button had ink that failed
it, so team-kanban's builder removed the semantics (and lost points for a Delete that wasn't destructive).

## D8. The keyboard never covers what the person is working with

On iOS: the focused field scrolls above the keyboard and above content pinned to the bottom of the screen
(book-club: the bottom button covered the Author field); the scroller's bottom inset grows by the keyboard,
so every control under the field (a Save) can be scrolled to (expense-tracker: Save sat under the keyboard,
and a tap typed "2"); a keypad with no Return key gets the Done bar (expense-tracker: "never appeared").
The keyboard-and-focus recipe shows a live result beside or above its input, so typing doesn't hide it
(unit-converter), rather than scrolling arbitrary text into view; `verify` checks a test that ends with the
keyboard up as it is shown, keyboard and all.

## As built (2026-10-12)

Four lanes, merged on `bake/1116.008-integration`; lane log `~/bakeoff/lanes-1116.008.md`.

- **D1.** Whether the server reads `DB` is judged over its entry and the local modules it imports (five
  spellings: `process.env.DB`, `Bun.env.DB`, `import.meta.env.DB`, `env["DB"]`, `const { DB } =
  process.env`). When none does, `test` and `verify` stop before the build with one line on stderr naming
  the entry and both fixes. `agent` starts the app's server when nothing answers at `API`, on
  `.exact/agent/<storage>/db.sqlite` (an empty one removed after, without `--storage`), shares it between
  overlapping drives through a lease in `.exact/agent-server/`, stops only what a drive started, and says
  so in one line.
  *Amended 2026-10-26 (LLP 1142 §13 D13):* a declared `fixture/` or `fixtures/` server with a literal
  loopback `origin` gets a stable development port in 4790–5789 from the real app directory. Builds
  and drives use the same selection. An explicit backend, a saved `.exact/backend-origin`, a server
  command's `--port`, then `PORT` take precedence. A drive reuses a fixture only when its launch
  record, origin, listening process, command and directory agree; an unknown listener is refused,
  including one running the same entry. Ordinary app servers keep their authored ports and lifecycle.
- **D2.** `verify --shots <dir>` copies every capture, a test's own `screenshot` steps included
  (`<host>-t<n>-<name>.png`); a passing `verify` ends with `open it: bun exact.mjs web` (or `ios --run`).
  `web --help` no longer prints the background recipe. A stale prebuild came from an edit made during the
  build looking older than the receipt, which is written at the end; the receipt now records the build's
  start, and a check waits for a build another process claimed. *Amended 2026-10-16* (the euxy port,
  friction item 11): an Apple build compiles the app's `modules/apple/*.swift` from a copy taken as it
  begins (`host/apple/arms.mjs` `snapshotSources`; the arm cache and diagnostics keep the author's
  paths), so a Swift edit made meanwhile is the next build's instead of failing this one with swiftc's
  "input file … was modified during the build". start-here, `AGENTS.md` (1,280 bytes) and
  the tests recipe say a screen to capture is a test's end and one drive takes any others.
- **D3.** start-here's header pitfall: a fixed control under the bar goes with `aria-level=2`; one that may
  scroll away goes in the list's first section. `pattern rest` and `rest-backend` keep the switcher fixed
  under an inline title. The bar's material over the fixed band is QUEUE (LLP 1115.000 D11).
- **D4.** Not a host bug. In a grouped list the row's own scroll is already stilled; about twenty gestures
  open or don't open a hand-built `UICollectionView` list and Exact's alike. The grader's "short swipe"
  started on the row's checkbox (its label matched), which moves nine points in both. A test holds the
  stilled scroll.
- **D5.** `NumberStepping.clamped` in `Presenter.commitEdit` (iOS and the Mac): a typed number past a bound
  is written back as the bound, with an `input` and then the `change`.
- **D6.** A light hue in `RoundButton` is UIKit's tinted button (`buttonStyle="tinted"`) with label ink;
  compared by screenshot with UIKit's own tinted buttons on iOS 27 (same fill; UIKit's hue ink reads
  1.3–1.9:1, which `check` refuses). On the Mac a light hue draws neutral (`tinted` is a push stand-in).
- **D7.** The iOS check marks a title under any `UIButton` (a `select`'s pop-up) as the control's label.
  `destructive=true` on an ordinary button now draws red on iOS (red ink, or a red fill under white) and
  the Mac (`hasDestructiveAction`); in light mode the red under a gray, bordered or tinted fill is deepened
  to pass 3:1 on iOS (`#f0302f`) and the web (12% toward black). An authored colour wins.
- **D8.** iOS: `Presenter.pinnedCover` leaves out an absolute bottom bar's height when it reveals the
  focused field, and `PinnedRoom` gives the scroller that room while the keyboard is up; decimal, number and
  phone pads always get the Done bar; the sheet's strip behind it takes the list's colour; on a simulator a
  capture taken with the keyboard up includes it (`withKeyboard`, from `simctl io`). The keyboard-and-focus
  recipe puts a live count beside its field. QUEUE: a sticky bottom bar after the keyboard resizes the
  viewport, and a phone's captures without the keyboard.
