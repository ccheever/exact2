## Summary

The agents built and drove each module under the agent, in browsers,
on macOS and on iOS simulators. Some ran on one iPhone 17 Pro Max and one
Pixel 5. What is still unchecked needs other devices, a person, or real
store and identity accounts. This plan is the work that remains:

- the devices to gather;
- the accounts to set up, and where their IDs go;
- the order to test the modules in;
- how to report what you see.

The steps themselves live in each package's checklist. This document
says which checklist to run on which device, and what blocks each one.

## 2. One-time setup

1. Clone the repo and `bun install --frozen-lockfile`. Read
   `rules/RULES.md` and `docs/testing.md`.
2. **Apple devices.** `bun host/apple/build.mjs --ios --device <app>-apple --run`
   builds, signs with your Mac's team profile, and installs on a
   connected iPhone. Over SSH the signing step fails. Run the build
   from Terminal.app on the Mac the phone is connected to. On the iPhone, turn
   on Developer Mode, trust the Mac, and allow each app's Local Network
   prompt.
3. **Android devices.** You need the Android SDK with platform 37.2,
   NDK 27.1 in `ANDROID_NDK_HOME`, and JDK 17 in `JAVA_HOME`
   (`host/android/README.md`). Then `bun scripts/agent-android.mjs build <app> --apk`
   and `adb install -r` the APK it names. Play Protect may block installs
   over USB. If it does, turn off its check for the session
   (`adb shell settings put global verifier_verify_adb_installs 0`) and
   restore it afterwards (`adb shell settings delete global verifier_verify_adb_installs`).
4. **Excord's test server**, for local-auth. Run it on the Mac:
   `bun apps/excord/fixture/server.ts --world transcript --port <port>`, where `<port>` is
   the checkout's own, which a development build bakes (`bun scripts/agent-launch.mjs
   --fixture-port --app excord` prints it).
   - **Android:** add `adb reverse tcp:<port> tcp:<port>`.
   - **iPhone:** add `--host <the Mac's LAN address>` (`ipconfig getifaddr en0`), and build
     Excord with `EXACT_BACKEND_ORIGIN=http://<that address>:<port>`.

   Only a development build accepts the LAN address
   (`packages/local-auth/test/device-checklist.md`).
5. **Drive a phone from the Mac** with the agent where a checklist says
   so: `bun scripts/agent.mjs ios --device --app <app> …` for a connected iPhone, or
   `ANDROID_SERIAL=<serial> bun scripts/agent.mjs android --app <app> …` for an Android phone, with `--bind <module>` to use the real implementation rather than the
   agent's stand-in.

## 3. Accounts to set up

Passkeys, sign-in and purchases can be tested on real devices only once
these accounts exist. Create them in the order below. Client IDs, product
IDs and team IDs are not secrets: record them in section 7's table and
commit it. Client secrets and signing keys are secrets. Give them to
Charlie privately, and never commit them or paste them in Slack.

### 3.1 The public origin

Passkeys and the web's sign-in return route need one public HTTPS
domain. Charlie approved it on 2026-10-26: *"sure, yes deploy
exact-auth-fixture.expo.app if you want"*. It is
`https://exact-auth-fixture.expo.app`, on EAS Hosting, deployed and
checked by `bun apps/auth-fixture/origin.mjs` as an account with access
to `ccheever` (`eas login`, or `EXPO_TOKEN`). It is not deployed yet:
`eas` on this Mac is logged in as `ccheever`, and the deploy waits for
Charlie to run that command. Once deployed it serves:

- `/.well-known/apple-app-site-association`: `webcredentials` for
  `CUW59GZ74D.com.exact.authfixture`, and `SIMULATORX.com.exact.authfixture`
  for a simulator build;
- `/.well-known/assetlinks.json`: `get_login_creds` for
  `com.exact.authfixture`, signed by this Mac's Android debug key;
- `POST /passkey/…`: the auth fixture's passkey relying party, which keeps
  no state: each passkey is a record the app holds, signed with a key kept
  in the project's EAS environment.

`bun apps/auth-fixture/origin.mjs --check` checks all three. A return URL
or domain in 3.2 to 3.4 may name it.

### 3.2 Google test accounts and Google Cloud

1. Create three Google accounts used only for testing:
   - one signed in on each Android test phone;
   - one for the web;
   - one that has never used the app, for first-sign-in steps.

   Never use a personal account.
2. In Google Cloud, create a project for exact2 testing. Configure the
   OAuth consent screen with the publishing status **Testing**, and add
   the three accounts as test users.
3. Create the OAuth clients LLP 1133.014 §13 question 6 names:
   - **Web:** its authorized redirect URI is `https://<origin>/sign-in/return`.
     It has a client secret, so give the secret to Charlie privately.
   - **iOS:** bundle ID `com.exact.authfixture`.
   - **Android:** package `com.exact.authfixture` and the SHA-1 of the
     debug signing certificate the Android build uses
     (`keytool -list -v -keystore ~/.android/debug.keystore`, password
     `android`). Make one Android client for each machine whose debug
     key builds the APK.
4. Sign each Android test phone into its test account (Settings,
   Passwords and accounts). Credential Manager offers only accounts on the device.
5. **Attestation (LLP 1133.028 §11 question 3):** enable the Play
   Integrity API in the same project, and create a service account with
   a JSON key. Give the key to Charlie privately; the auth fixture's server
   reads its path from `EXACT_PLAY_INTEGRITY_KEY`. Record the project's
   number (not a secret) in section 7.
6. **Maps (LLP 1133.021 §15 question 7):** enable the Maps SDK for
   Android in the same project and create an API key restricted to
   Android apps, listing each app's package (`com.exact.mapdemo` first)
   with the SHA-1 of each debug certificate that builds it (step 3's
   `keytool` line). Give the key to Charlie privately; a build reads it
   from `EXACT_GOOGLE_MAPS_API_KEY`, and it never enters the repo.

### 3.3 Apple Developer and App Store Connect

You need to be a member of the Apple Developer team that signs the
builds. Then:

1. **Sign in with Apple:**
   - Enable the Sign in with Apple capability on App ID `com.exact.authfixture`.
   - Create a **Services ID** for the web, for example `com.exact.authfixture.web`.
   - Set the Services ID's domain to the origin, and its return URL to
     `https://<origin>/sign-in/return`. Apple refuses `localhost` and IP addresses.
2. **Passkeys:** enable Associated Domains on `com.exact.authfixture`.
   The build writes `webcredentials:<origin>`. The association file on the origin names
   `<TEAM ID>.com.exact.authfixture`.
3. **Sandbox testers:** in App Store Connect, under Users and Access,
   then Sandbox, create two sandbox Apple Accounts. Sign one into the test
   iPhone under Settings → Developer → Sandbox Apple Account, never as
   the phone's main Apple Account.
4. **Attestation and the age range (LLP 1133.028 §11 question 3):**
   - Enable App Attest on `com.exact.authfixture`.
   - Enable Declared Age Range on `com.exact.excord`.
   - Regenerate the development profiles that carry them.
5. **Purchases (LLP 1133.015 §13, "Accounts"):**
   - Create an app record for `com.exact.weatherlight`.
   - Create Weatherlight's catalogue products with exactly these IDs:
     - `plus.monthly` and `plus.yearly`: auto-renewable subscriptions in one subscription group;
     - `tip.small`: a consumable.
   - Sandbox purchases need the Paid Apps agreement active on the team.
6. **NFC (LLP 1133.035 D15):** enable NFC Tag Reading on App ID
   `com.exact.shelf` ("Adds the NFC tag-reading feature to the App ID"),
   then regenerate its development profile. A device build of Shelf carries
   the entitlement `com.apple.developer.nfc.readersession.formats`, which a
   profile without the capability refuses. Charlie's step: it needs the
   team's account.

### 3.4 Google Play Console

Play Billing answers only for a package uploaded to a Play track.

1. Create an app for `com.exact.weatherlight`, and create the same three
   products:
   - `plus.monthly` and `plus.yearly`: subscriptions, each with one base plan;
   - `tip.small`: a one-time product.
2. Set up internal testing. Add the Google test accounts as testers, and
   as **license testers** (Settings, License testing). Each tester opens
   the opt-in link once on their phone.
3. **Attestation and the age range (LLP 1133.028):** create apps for
   `com.exact.authfixture` and `com.exact.excord`, link the Play Integrity
   Cloud project to the first, and leave Excord's age bands at Play's
   defaults. Upload each to the internal track when its stage 3 reaches a
   phone.
4. Upload a release build of Weatherlight to the internal track. Follow
   [Google's testing guide](https://developer.android.com/google/play/billing/test)
   for which installed builds Play Billing will serve. Record which you used
   in your results.
4. **Alarms (LLP 1133.030 D9).** An app whose grants include
   `device.alarms` declares `FOREGROUND_SERVICE_SYSTEM_EXEMPTED`: its
   ringing service runs with type `systemExempted`. Before uploading such
   an app to any track, fill in its foreground service declaration (App
   content, Foreground service permissions): the type, "an alarm the
   person set rings until they stop it", and a short video of a ring
   and its Stop. Play reviews the declaration; the code needs nothing
   more ([foreground service types](https://support.google.com/googleplay/android-developer/answer/13392821)).

## 5. How to run one

1. `git pull` and note the commit. Every result names the commit it ran.
2. Build the app the checklist names, for the device, from that
   commit. A build older than its sources is refused by the driver;
   rebuild.
3. Do the checklist's steps in order. Each step says what you should see.
   A step that shows something else is a failure. Note the step number,
   what you did, and what you saw.
4. Where a step reads state, use `bun scripts/agent.mjs ios --device --app <app> state logs` (on Android, `android` with
   `ANDROID_SERIAL` set)
   on a development build. Use `adb logcat -s exact` on Android.
   Read state rather than screenshots wherever you can.
5. When you are done with a device:
   - delete any recordings, photos and contacts the steps made;
   - uninstall the test apps;
   - sign out of the sandbox and test accounts if the phone is shared;
   - restore any setting you changed (Play Protect, Auto-Lock, the passcode).

## 6. Reporting

- **A pass:** add a line to the module's row in section 8: device, OS,
  commit, "pass".
- **A failure:** put the steps to reproduce, the device and OS, the
  commit, and what you saw (state and log lines) in `QUEUE.md`. Name the
  module and the checklist step, and add a line to section 8 pointing at it.
- **Screenshots:** a failure may need one. Take it of the app under test
  only, with test accounts, and keep anything personal out of it.
- **When a module passes on every device in its row,** post it to
  #exact-users-group with its manual-testing steps, so others can try it.
