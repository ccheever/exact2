## Summary

Contract's useful additions should stay. Records, locals, reusable actions,
ordinary string operations and imported capabilities let applications express
their work directly. Keep `if`/`for`, keyed identity, immutable values, pure
derives, explicit effects, and the boundary between views and data code.

The simplification target is the set of rules an author must combine to write
an ordinary feature correctly. Five changes are worth pursuing, separately:

| | Proposal | What it would remove | Recommendation |
|---|---|---|---|
| D1 | Give reads after writes one diagnostic policy across action boundaries | Extracting statements into an action changes a warning into an error | Prototype first; keep snapshot semantics |
| D2 | Refuse a send and assignment to the same nonqueued mutation on one path | Source order appears to matter, but a reset can discard the new reply in either order | Census intentional uses, then implement if their replacements remain clear |
| D3 | Deliver a mutation's reply as its continuation's argument | Matching an optional slot to retrieve the reply that caused the callback | Prototype the small semantic extension |
| D4 | Let component instances own requests and timers | A reusable feature must move its behaviour into the application root | Prototype on a timer and an editor; largest potential gain and cost |
| D5 | Resolve ordinary host commands through imports | A growing global command vocabulary reserves application action names | Pilot one command through the existing module machinery |

These are independent choices, not a package to approve together. Start with
D1 and D2. Measure D3 before committing to the larger ownership work. D5 can
proceed independently when it deletes a special resolution path.

An improvement may be established by a removed exception, by fewer mistakes
on representative tasks, or by less work to complete those tasks. Report which
claim the evidence supports. A shorter document or fewer lines of application
code alone establishes none of them.

## 1. Evidence and limits

The drafting baseline is `d687090088d93f0896b836430b6758774fbb40d9`.
After building `contract`, six small programs were compiled with
`target/debug/contract build <file> --json -o <plan>`:

| Program | Observed compiler result |
|---|---|
| Assign `count`, then read it into `seen` in the same action | Success with `analyze-read-after-assign` warning |
| Put that read in `follow()`, called after the assignment | `analyze-call-stale-read` error |
| Assign `saved = none`, then `send saved = save()` | Success, no diagnostics |
| Give `then finish` a typed reply parameter | `analyze-handler-arity` error: an answer passes no arguments |
| Put a timer in a child component | `type-child-resource` error |
| Declare an action `close`, then call it | `syntax-call-ambiguous` error: the name is also a host command |

These are compiler observations, not an authoring study or proof of runtime
behaviour. The relevant existing tests are in
[`warnings.rs`](../contract/cli/tests/it/warnings.rs),
[`calls.rs`](../contract/cli/tests/it/calls.rs) and
[`mutation.rs`](../contract/cli/tests/it/mutation.rs).
In particular, `the_newest_send_wins_and_an_assignment_forgets` covers an
intentional logout that sends a request and forgets its reply. D2 must account
for that use, not silently remove it.

That regression was run while drafting:
`cargo test -p contract --test it the_newest_send_wins_and_an_assignment_forgets`
passed (one test). No proposed behaviour has been implemented or measured.

Earlier evidence gives three reasons to proceed carefully:

- LLP 1035.005.000 counted 1,304 explicit `writes` names on 553 actions.
  Removing them was a concrete reduction in bookkeeping. Its record and local
  proposals similarly replaced identifiable application work.
- LLP 1091.002 records a T3 Code root of 2,998 lines, with its view already
  extracted. `members` makes that source manageable across files, but every
  file still shares one component's scope. Many of that app's requests are
  application-wide; child ownership would not make them all local.
- LLP 1116.015's `if`/`for` and method-syntax A/B found no measurable
  productivity change. LLP 1116.013's smaller first read moved knowledge into
  more lookups and was not adopted. Neither renaming nor compressing the guide
  is a demonstrated answer to the remaining complexity.

The counts above are those documents' historical observations. This draft has
not repeated their app census or agent experiments on the current repository.

## 2. Proposed changes

### D1. One rule for a snapshot read, wherever its statements live

Keep the action's starting snapshot and atomic commit. The proposed rule is:
**if a path has already scheduled a write to a value, a later read of that value
must name an explicit local or parameter.** Apply the same rule in the action
body and through calls; refuse the ambiguous read in both places.

For the new value:

```contract
action advance
  let next = count + 1
  count = next
  show(next)
```

For the old value, bind `let before = count` before the write and pass `before`.
Neither repair changes the meaning of an assignment or commits a partial action.
The diagnostic must offer both intentions; automatically choosing the new value
would change correct snapshot programs.

Use one analysis for direct and called reads. Equivalent extraction or inlining
must preserve acceptance and diagnostic severity. Exclusive paths and reads of
fields a record copy leaves unchanged remain safe because their reads and writes
do not overlap. A derive that depends on the written field must not hide the
dependency: show that dependency in the diagnostic and offer a local captured
before the write. Resource answers and request status remain settled observations;
this proposal does not re-evaluate them within an action.

The same rule applies to conditions. A sequence of `if phase == ...` branches
that intentionally tests the starting phase can bind it once before any write.
This deliberately removes the current special exemption for some such chains.

**Cost and decision.** This rejects some correct programs and can add locals and
parameters. Census those cases before adopting it. The minimum gain is one rule
whose meaning survives extracting a helper; an authoring gain is a separate
claim. If the repair mostly produces scaffolding or moves mistakes elsewhere,
retain the current behaviour and report that D1 failed its simplification test.
Changing all action reads to sequential reads is considered in §5, not bundled
into this diagnostic change.

### D2. Separate sending work from forgetting its reply

A nonqueued mutation currently admits both an assignment and a send in one
action. Assignments commit after sends, so `saved = none` can forget the new
request even when the reset is written first. A common attempt to clear an old
error therefore changes request ownership.

Propose refusing an assignment and a send to the same **nonqueued** mutation
on any reachable path through one action, including its calls, regardless of
their textual order. Exclusive branches remain valid. The message names both
sites and explains the intent-specific repair:

- Clearing an old error before a retry: keep the send and hide the old result
  while `pending(saved)`. Request failures use `failure(saved)`.
- Signing out: forget the sign-in mutation and send the logout operation through
  a separate mutation. The sign-in reply must remain unable to restore a session.
- Dismissing an answer without sending: the existing assignment remains valid.

Do not recommend `queue` merely to silence this error. A queued mutation has
different guarantees: an assignment clears its displayed answer without dropping
queued work. Changing a request's scheduling policy changes the application.
Queue behaviour and newest-wins behaviour both stay in this pass.

Before implementation, classify every affected application action, including
intentional send-and-forget uses. Preserve observable request and storage effects
in the replacement, not just the visible screen. If a use has no clear rewrite,
resolve it in this RFC before accepting D2; do not silently turn a forgotten
request into a tracked one or claim external work has been rolled back.

**Cost and decision.** An intentional use may need another mutation declaration.
Measure that cost against eliminated silent reply loss. D2 is a narrow removal
of an ambiguous combination; it does not claim to unify the whole mutation model.

### D3. A continuation receives the reply that caused it

Make `then` follow the event-handler convention: its action may receive the
delivered value as an argument, or ignore that argument.

```contract
shape Saved
  ok: bool
  error: string

component Editor
  state draft = ""
  state error = ""
  mutation saved as shape Saved then afterSave

  action afterSave(reply: Saved)
    if reply.ok
      draft = ""
    else
      error = reply.error
```

This is a proposed fragment, not code accepted by today's compiler. Its handler
needs no `match saved { case some(...) ... }`: there was an admitted reply to
deliver. The mutation slot remains optional for the view before any reply exists.

Capture the admitted reply when arming the continuation. Run the continuation
as its own transaction through the existing clock. Preserve current supersession,
forgetting and reload rules: capturing a value does not revive a continuation
whose request lost ownership. A queued send still waits for its predecessor's
continuation, and delivers that predecessor's reply. A shaped domain refusal is
a reply; a request that fails without an admitted value runs no `then`.

Zero-parameter handlers ignore the payload, just as handlers can ignore event
arguments. Self-send refusal, effects, rollback and queue ordering stay as they
are. Do not introduce general `await`, per-send callbacks or implicit reactions.

**Cost and decision.** This changes continuation payload storage, the compiler's
arity rule, both executors and the semantic model. It must demonstrably remove
optional-slot handling in real continuations without making late replies easier
to misuse. If the removed code is negligible or almost every handler still needs
extra ownership bookkeeping, defer it and spend the effort on D4.

### D4. Give a component's behaviour the component's lifetime

Propose allowing a component instance to own resources, mutations and tasks,
using the existing declarations. State and its supporting behaviour could then
be extracted together. The root would be the instance that lives for the session,
rather than a different kind of component for these declarations.

Prototype this first on two features: a press-and-hold control with a timer, and
an editor opened for a keyed record with a read, a draft and a save continuation.
Use real app code where available. Do not begin by moving all of T3 Code's root.

The proposed lifetime rules are:

- Identity is the existing component instance identity, including enclosing
  keyed regions and route entries. Reordering a retained key retains its work.
  Destroying and recreating the same key gives a new owner generation.
- A task mounts with its instance. Gates and task keys retain their current
  meanings. Destroying the instance removes its timers, queued sends and armed
  continuations, and releases its outstanding request ownership.
- A late answer cannot commit into a destroyed owner or a successor with the
  same key. Releasing ownership does not undo external effects already performed.
  Work that must survive closing a screen belongs to an ancestor that survives,
  reached through the existing action props or injection.
- Hidden and destroyed are distinct. A retained route remains an owner even
  when another route covers it. A timer that should stop while hidden says so
  with its existing gate; a host's incidental view recycling is not destruction.
- A resource re-asks for changed arguments within its owner. `refreshes` names
  resources in that same owner. Shared resources and durable write sequences
  remain in a stable ancestor; there is no implicit global request deduplication.
- New instances can present only baked values or declared fallbacks before
  data arrives. Dynamic props must not introduce synchronous I/O before first
  pixel. The prototype must demonstrate fallback and bake behaviour explicitly.

This permits one request per mounted row if an author puts a resource in every
row. That is a real cost, not something the design may conceal. Drive a long
virtualized list and use existing per-site request and work counts to show what
opens, remains retained and closes. The treatment of offscreen keyed instances
must follow logical instance lifetime, not whichever native views are allocated.
If current instance retention cannot bound that work, the ownership proposal is
not ready; adding a second notion of mount is not an acceptable quick repair.

**Cost and decision.** This is the largest change: instance storage, request
identity, settlement, timers, baking, inspection, both executors and proofs.
It is a refinement of LLP 1035.005.000 D5's request-ownership work. Accept the
direction only after the two prototypes remove root wiring and pass lifecycle
tests. Keep `members` for large app-wide owners; shrinking a file is not the
criterion. Do not add a new controller, store or owner-block syntax in this pass.

### D5. Let imports determine command identity

The module system already imports capabilities by declaration identity. Ordinary
host commands still live in `HOST_COMMANDS`, and their spelling takes precedence
over an application's action call. A local `close()` can therefore be refused
because a window command has that name.

Pilot importing one ordinary command, `focus`, through the existing package
interface and alias mechanism. The package name is to be selected with the
implementation. A local action and a host command can then have distinct lexical
bindings, with an explicit `as` alias when both are needed. The compiler resolves
the declaration before choosing how to lower the call.

Preserve the command's existing runner operation, event timing, node targeting,
rollback boundary and host implementation. A command that acts during the
current event must not become an asynchronous module request. The current module
AST already represents sends without answers as statements; the prototype must
show whether that representation can carry this command's timing without a
second dispatch route. If it cannot, leave the pilot unshipped.

For a migrated command, delete its ambient spelling and provide a diagnostic
that names the import. Do not keep an alias indefinitely or permit new built-ins
to capture old calls. Migrate commands in coherent groups only when each step
removes a special case. Sounds, sequences and other runner-owned timing retain
their representation unless the same guarantees can be expressed by the shared
mechanism; their keyword count is not a reason to move them.

**Cost and decision.** There is one more import to write, but one fewer naming
precedence rule. Require identical command traces and working `use ... as ...`
before extending the pilot. This is compiler and package consolidation, not a
promise that native capability implementations become smaller.

## 3. Measuring whether a change helps

### 3.1 Freeze the claim before implementing the change

For each selected decision, record in this document the starting commit,
representative tasks, expected behaviour, primary outcome and stopping budget.
Use existing compiler fixtures, authored app tests, `verify`, `agent`, `perf`,
the semantics tools and the authoring bake-off. No new service, registry or
blocking check is proposed. Add focused cases to their existing suites only
when an implementation is selected.

| Decision | Deterministic evidence | Authoring task | What would count against it |
|---|---|---|---|
| D1 | Extracting or inlining the same effective statements preserves acceptance and severity; explicit old/new-value repairs preserve intended outputs | Reuse an update action, then change its caller | Extra captures and arguments cost more than the inconsistency did |
| D2 | Both source orders and calls are diagnosed; retries, logout and queue behaviour retain their required effects | Add retry and error dismissal to a save flow | Repairs lose logout effects, alter scheduling, or need unrelated state |
| D3 | Each owned continuation receives its admitted payload; superseded work stays suppressed | Handle success and domain refusal, then add a queued save | Stale-owner mistakes increase or optional-slot code is merely relocated |
| D4 | Retained keys retain work; destruction suppresses late commits; recreation cannot receive old replies | Extract a timer control and keyed editor, then mount two independent copies | Ownership leaks, hidden polling, duplicate requests, or more lifetime rules |
| D5 | Aliasing changes no command trace; adding an unused command changes no application's binding | Extract and rename a component action that collides with a host name | Timing changes or a second command-dispatch mechanism remains |

Count the entire application change: Contract, data code, declarations, props,
injects and helpers. Record the root wiring removed, explicit captures added,
and files a feature edit touches. Counts are explanatory evidence; fewer lines
are not a target an implementation may satisfy by moving work out of view.

### 3.2 Test repair and maintenance as well as first construction

For a change that passes deterministic tests, compare the baseline with that
one change. Start with four development tasks, two model families, one run per
arm: 16 sessions. If the result justifies confirmation, use four held-out tasks
with two repetitions per family and arm: 32 further sessions. These are bounded
experiments, not a standing benchmark fleet or a claim of statistical power.

Each task has an observable feature requirement and a follow-up modification
written before the runs. Include a normal case, a deliberate old-value or
cancellation case, a component extraction, and an adverse completion order.
Keep task-specific tests unavailable to the builder until grading, while keeping
the ordinary compiler diagnostics and app-driving tools available. A refusal
alone is not a successful repair: the finished feature must work.

Pin the toolchain, model version and effort, source commits, app seeds, task
budgets and grading drives. Start each session fresh. Randomize arm order within
task and family; do not let a builder carry the first solution into the second
arm. Give each arm accurate documentation of comparable scope. Keep unrelated
documentation, library, compiler and platform changes out of the comparison.
If existing bake-off tooling cannot run this comparison as written, record the
gap rather than silently substituting a one-shot syntax-guess exercise.

Report, separately for each family:

1. Correct completions within the fixed task budget, including hidden behavioural
   checks and the follow-up modification. List every failure and timeout.
2. Active time and tool turns to the first behaviourally correct solution;
   include repair iterations and documentation lookups. Report timeouts at the
   budget alongside completion counts, not as excluded fast successes.
3. Total and fresh tokens. Total tokens include context re-sent after a lookup;
   moving prose into more lookups must not appear as a saving.
4. Mistakes by mechanism: starting versus new values, forgotten replies, stale
   owners, duplicate requests and name collisions. Count escaped behavioural
   mistakes separately from compiler refusals.
5. The application bookkeeping counts from §3.1, plus runtime work counts for
   the same frozen drive. Wall-clock performance is measured separately.

Show paired task results and uncertainty, not just a pooled average. Declare the
interval method before the runs; estimate 95% intervals with task as the sampling
unit and repetitions nested within it. Repetitions of one task are not independent
task samples. With four held-out tasks, a result will often be inconclusive; say
so. Improvement in agents does not establish
improvement for human authors. A small human exercise may provide qualitative
evidence, reported separately with participants and prior experience stated.

### 3.3 Decide what the result permits us to claim

The following are proposed decision thresholds, not measured effects:

- **Correctness:** all named semantic and lifecycle cases pass. A lost write,
  cross-owner reply, changed command timing or new unbounded work blocks the
  slice. No observed drop in held-out correct completions is acceptable without
  understanding every differing task; equality in a small sample is not proof
  of non-regression.
- **Measured authoring gain:** target at least 15% lower median paired active
  time on correctly completed held-out tasks, with no lower completion rate,
  and an uncertainty interval that excludes no improvement. Report each model
  family; a pooled win must not conceal a family's regression. Tokens and tool
  turns explain the result, rather than replacing the primary measure after it
  has been observed. Small samples may not clear this bar.
- **Structural simplification:** a documented exception or implementation path
  is removed, the named extraction tests pass, and the work has not moved into
  an application helper or another runtime. This can support acceptance even
  with inconclusive timing, but only as an explicit design judgment. Say
  “one rule removed; authoring benefit unproven,” not “15% easier.”
- **Failure or ambiguity:** revise within the repository's three-round limit,
  defer the slice, or ask Charlie to choose the trade. Do not keep sampling
  until a favourable comparison appears. Once held-out failures inform a
  revision, those tasks are development evidence; any fresh confirmation set
  and its budget must be declared before another run.

## 4. Implementation and acceptance boundaries

This document authorizes no language change by itself. On selection, assign one
slice an implementer and date, state its corpus breakages and repairs, then
prototype it. Amend the governing LLPs and current reference at acceptance,
clearly distinguishing intentional language changes from regressions.
Any expansion of deferred scope names its trade or obtains Charlie's waiver
before implementation; writing this draft does not admit that expansion.

For D1/D2, run compiler tests and behavioural tests of repaired applications.
For D3/D4, change the operational semantics with the runtime and exercise the
runner and web JS target against independent expected traces. Update the Lean
proofs affected by the change; `contract-difftest quick` is a useful additional
check, not evidence that an incorrectly changed specification is correct.
For D5, compare command order and timing on the web and an affected native host.
Use the six existing checks and run the relevant host tests before landing.
Build, launch and drive affected applications; successful compilation is not
application validation.

Preserve the boot and edit-loop budgets, deterministic clocks, bounded work,
closed values and explicit effects. No compatibility branch, extra language mode
or additional blocking check is part of the pass. A prototype may be discarded.
Pre-1.0 source changes replace the old form with a clear diagnostic and a
reviewed application update.

Working-set trade: remove the links to the older LLP 1114 umbrella and LLP 1095
on platform colours so this draft and the concurrently authored LLP 1150 fit
in `llp/current/`. Both older documents and their outstanding proposals remain
in the corpus with their status unchanged. The working set stays at 15.

## 5. Alternatives and open decisions

**Sequential reads inside an atomic action.** This could make composed updates
behave as imperative programmers expect while preserving one externally visible
commit. It is a plausible larger simplification, but it changes intentional
snapshot programs and raises new questions: whether derives recompute during
the action, whether resource observations stay fixed, how command arguments see
writes, and how much repeated derivation costs. Do not quietly make only direct
state reads sequential and leave derives stale. Revisit it if D1 leaves frequent
composition failures; compare a complete model against snapshots on the same
tasks. This draft recommends retaining snapshots for the first pass.

**Queue every mutation.** Keep the choice explicit. Sign-in supersession and
ordered write logs have different requirements; a universal queue can serialize
obsolete work and delay the latest intent. D2 is not a reason to change defaults.

**Return to `when`/`each`, add aliases, or respell options.** Keep `if`/`for` and
one spelling per construct. Absence remains `option` in this pass. LLP 1116.016's
separate absence proposal has its own evidence requirements. Neither a keyword
change nor another spelling addresses action composition or request ownership.

**Shrink the guides first.** Remove obsolete advice after its cause is removed.
Keep the reference accurate throughout. LLP 1116.013 already shows that moving
knowledge out of the first read can merely increase later work.

The decisions for Charlie are:

1. Start with D1/D2's corpus census and bounded prototypes, keeping snapshot
   semantics? Recommended: yes; decide each independently from its findings.
2. Prototype payload continuations (D3), then component ownership (D4) if the
   extraction cases justify its cost? Recommended: yes, in that order.
3. Permit the command-import pilot (D5) only if it reuses existing execution
   and removes special name resolution? Recommended: yes.
4. Accept a demonstrated rule reduction when authoring measurements are
   inconclusive? Recommended: case by case, with the unproven benefit explicit.
5. Use the bounded experiment and stopping rules in §3 rather than requiring
   every slice to improve a whole-app token score? Recommended: yes.
