## Amendment A1 (2026-10-08): `storage.fs.compressImage`

**Status:** approved by Charlie 2026-10-08, via the lead. Design r4, after
three review rounds (§A1.9). §A1.10 records what landed.

### Why

Bluesky's composer shrinks every picked image before upload
(`social-app/src/lib/media/image/compress.ts`). The lexicon's blob limit is
2 MB (`app.bsky.embed.images`: "May be up to 2 MB, formerly limited to 1
MB"). A phone photo is 3–12 MB, so the clone has to refuse most photos
outright. Under D6 a module could do this only by decoding and encoding
JPEG in JavaScript, with every byte passing through `readFile`. The
platforms already have the codecs.

### A1.1 The call

```ts
interface FileSystem {
  // … the existing members …
  compressImage(from: string, to: string, options: CompressImageOptions): Promise<CompressedImage>;
}
export interface CompressImageOptions {
  readonly maxDimension: number; // integer, 1..8192: the longer side's limit, in pixels
  readonly maxBytes: number;     // integer, 1..67108864: the encoded file's limit
}
export interface CompressedImage {
  readonly path: string;         // `to`
  readonly type: "image/jpeg";
  readonly size: number;         // bytes at `path`, <= maxBytes
  readonly width: number;        // pixels, orientation applied
  readonly height: number;
}
```

```ts
// Bluesky's post limits; avatars and banners pass 2000 and 1_000_000.
const out = await storage.fs.compressImage(pick.path, `app:/tmp/upload/${n}.jpg`,
  { maxDimension: 4000, maxBytes: 2_000_000 });
const body = await storage.fs.readFile(out.path);   // then uploadBlob
```

- **It is an `fs` member,** like `copyFile`: two paths, read on the first and write on
  the second. It joins the module's one storage queue (LLP 1097 D3), so it
  runs in order after the operations issued before it. It
  is refused where storage is: at bake, and in a drive with no scratch
  store. Its refusals carry the same `{kind: "Unavailable", code}` as
  every other storage call. It takes no new grant. The app must hold `fs.read` on `from` and
  `fs.write` on `to`; Bluesky's are `fs.read app:/tmp` and `fs.write
  app:/tmp`.
- **The options are checked and copied at the call,** before anything is
  queued: a bad one rejects the promise with a `TypeError` that never takes
  a queue slot, and changing `options` after the call changes nothing. The
  native prelude and the JS target check them themselves; the web's
  `storage-fs.js` checks them again for its other callers.
- **The caller names `to`,** as with `copyFile` and `rename`. The host
  mints no name. Under LLP 1027.000 a name is
  the app's to derive from its seed. Writing to a known path also lets the app replace or
  remove the file. `to` is replaced atomically; `from === to` is allowed
  (the source is read in full before anything is written).
- **App files only.** Both paths must be `app:/` paths, checked before any
  other routing: a `doc:/` path or a native disk path (Windows) is refused
  with `compressImage: needs app:/ paths` (`failed`) on every carrier,
  before the document and native-disk branches each host has for other
  `fs` operations. A chosen document is never overwritten by this call.
- **The result shares `Picked`'s image fields** (`path`, `type`, `size`,
  `width`, `height`); it has no `name` or `duration`, so it is not a
  `Picked`. An app that shows the original name keeps it from the pick.
- **The app chooses the numbers.** Nothing in exact2 knows Bluesky's 4000
  and 2 MB.
- **It always re-encodes,** even when the source already fits. That is
  what strips a JPEG's GPS block. An app that wants to skip the call compares
  `size`, `width` and `height` with its limits first, as Bluesky's
  `compressIfNeeded` does.
- **A Rust source** asks for it with `exact_data::storage::request(
  "fs.compressImage", {"path", "destination", "maxDimension", "maxBytes"})`.
  The reply is the same record as JSON; a failure is the message.
- **On the wire to Ibex** (opcode 121) the call is four values: the two
  paths and the two limits as numbers. Ibex answers the raw string
  `"width\theight\tsize"` (not through `install.cc`'s `stat` converter,
  which takes only opcodes 113 and 116), and the prelude's wrapper splits
  it and adds `path` and `type`. The web's capability takes the same four
  values from the prelude and answers the record.

### A1.2 The algorithm: Bluesky's, run in the host

The search is `compressImage` in `compress.ts`, as it is today. Here it is restated over the
**oriented** source size `W × H`:

```
dim = maxDimension; lo = 0; hi = 101; shrinks = 0; best = none
while hi - lo > 1:
  if shrinks >= 4: break
  (w, h) = (W, H) if W <= dim and H <= dim
           else scale s = dim / max(W, H); (max(1, floor(W*s)), max(1, floor(H*s)))
  q = round((lo + hi) / 2)               // JS Math.round: halves go up
  if q <= 13:                            // 51, 26, 13: give up on this size
    lo = 0; hi = 101; shrinks += 1; dim = floor(dim * 0.8); continue
  bytes = jpeg(resize(source, w, h), quality q / 100)
  if len(bytes) <= maxBytes: lo = q; best = bytes (w, h)
  else: hi = q
return best, or fail `unfit`
```

The fidelity details follow `compress.ts` exactly:

- The fourth shrink ends the loop before its size is tried. The sizes
  tried are `maxDimension`, then each one `floor(previous × 0.8)`, four in
  all: 4000, 3200, 2560 and 2048, never the ~1638 its comment mentions;
  from 333 they are 333, 266, 212 and 169 (not `floor(333 × 0.8^k)`,
  which gives 213 and 170).
- A size whose 51 and 26 both miss gives up on that size and shrinks. Once a quality fits, `lo` is at
  least 26, so the search never shrinks again and climbs to the best quality that fits
  (about seven encodes).
- Size is the encoded byte length. Bluesky estimates it from the base64
  length (`round(len × 3 / 4)`), which can overstate it by up to two bytes. Our check is the
  exact one.
- Quality is the platform's own scale. On iOS, `expo-image-manipulator`'s
  `compress` is ImageIO's `kCGImageDestinationLossyCompressionQuality`. On
  the web it is `toBlob`'s quality. Each of our hosts passes `q / 100` to
  the same parameter.

**One declared deviation:** a side is never 0. `compress.ts` would ask for
an `8000 × 1` source at 4000 as `4000 × 0`, and for any source at a
dimension that shrinks to 0, and fail there with a codec error. Here each
side is at least one pixel: the sliver is tried at `4000 × 1`, and a
`maxDimension` of 1 tries `1 × 1` at each of its four sizes and is `unfit` if even
that misses. Generalizing the option range makes these reachable; Bluesky's
own numbers never reach them.

**The search runs in the host, in one call.** The alternative was a module-side
loop over a single-quality primitive. The host is better because:

- No image bytes cross into JavaScript. A trial is only a length, and the
  module never holds a 2 MB buffer just to measure it.
- The source is decoded once per size, not once per trial. Natively that
  is one ImageIO thumbnail decode, and the seven quality trials encode the
  same bitmap.
- One storage operation keeps the queue's order and the answer's pending
  state simple. Fifteen round trips, each a queued storage step, would hold
  the queue as long and cost an executor turn each.
- The same algorithm on every host is a spec this section fixes. A test
  checks it against recorded trial sequences (A1.7).

The cost is that an app cannot pick a different search. That is a later
option (`quality` alone), not something this needs.

### A1.3 Per host

| host | where it runs | how |
|---|---|---|
| iOS, macOS (TypeScript) | Ibex's pool worker, off the JS thread | The prelude's `fs.compressImage` reaches Ibex as a new async fs op (opcode 121, **Exact patch 9**; patch 8 is the Android Hermes target). Ibex admits both paths, reads the source through its app-directory handles with a cap, calls the codec the embedder installed (`Context::set_image_codec`), and writes the result with its atomic write while it holds the call's right to write (A1.5). exact-js installs `exact_data::image::compress`, on Apple only: elsewhere Ibex has no codec and refuses before reading the source. |
| iOS, macOS (Rust source) | the host worker that runs storage continuations | `exact-data-host`'s native adapter takes `fs.compressImage` and calls the same Ibex function with the same codec |
| the codec on Apple | — | Rust FFI to ImageIO and Core Graphics, no Swift, inside its own autorelease pool (the workers are long-lived Rust threads): `CGImageSourceCreateWithData` with `kCGImageSourceShouldCache` false; the header's size and orientation from `CGImageSourceCopyPropertiesAtIndex`, checked before any decode; per size, `CGImageSourceCreateThumbnailAtIndex` (`…FromImageAlways`, `…WithTransform` for orientation, `…ThumbnailMaxPixelSize` = the long side, uncached, and `kCGImageSourceDecodeRequest` = `kCGImageSourceDecodeToSDR`, so an HDR source, PQ, HLG or gain map, is tone-mapped while decoding rather than clipped by the 8-bit draw, as `RasterImage.swift` decodes for SDR), drawn into an opaque 8-bit **sRGB** `CGBitmapContext` of exactly `w × h`, filled white first, with high-quality interpolation. That draw is a second scale: the thumbnail's size is ImageIO's rounding, not `floor()`, and this gives the exact size A1.2 names. The last size's bitmap is released before the next is decoded. Each trial: `CGImageDestinationCreateWithData` (`public.jpeg`) + `AddImage` with only `kCGImageDestinationLossyCompressionQuality`. It decodes what ImageIO decodes: JPEG, PNG, HEIC/HEIF, WebP, GIF (the first frame), TIFF. |
| web, all three carriers | the page, or the module's worker when it is placed there | `storage-fs.js` `compressImage`, used by the wasm host's realm (`storage.js`, over the prelude), the JS target (`ts-data.js`) and Rust storage requests (`storage-request.js`); each refuses a non-`app:/` path before its document branch. It reads the entry as a `Blob` in one IndexedDB transaction (a picked entry is already the `File`, D5) and lazily imports `storage-image.js`, so nothing loads before first pixel. **It reads the header before decoding** (A1.5); HEIF and AVIF are `undecodable` on the web (their size cannot be bounded before decoding, A1.5; Safari hands a HEIC pick over as JPEG under a JPEG/PNG `accept`, D6, and Chrome decodes no HEIC). Then `createImageBitmap(blob, {imageOrientation: "from-image"})` (retried without the option where a browser refuses that enum value; current engines apply EXIF orientation by default), an `OffscreenCanvas(w, h)` with `{alpha: false}`, filled white, then `imageSmoothingQuality = "high"` and `drawImage`, then `convertToBlob({type: "image/jpeg", quality: q / 100})`. Without `OffscreenCanvas` it uses a `<canvas>` and `toBlob` where there is a `document`, and is `unsupported` in a worker; a missing 2D context, a null `toBlob` and a blob whose type is not `image/jpeg` (a browser that falls back to PNG) are `unsupported` too. The deadline's clock is `storage-environment.js`'s `now`, captured when that module is evaluated, which in a worker is before the prelude replaces `Date.now`. |
| Linux, Windows, Android | — | **Refused:** `compressImage: unsupported: no JPEG encoder on this host`. The workspace has no JPEG encoder outside Apple and the browser. The `image` and `zune-jpeg` crates appear only in manifests and lockfiles outside the workspace (`game/`, `bench/…`), not in the root `Cargo.lock`, and the Linux host decodes only PNG itself (`host/linux/src/image/jpeg.rs`: other formats refuse off Android). Android could use `AImageDecoder` with `AndroidBitmap_compress`, which is deferred. An app treats `unsupported` as "upload the original if it fits, else say no", which is the clone's current behaviour. |

**Colour:** the output is sRGB on every host, as the web's canvas is. A
Display P3 photo is converted, and an HDR one is tone-mapped to SDR by
the platform's decoder; a grey or CMYK one becomes RGB. This keeps hosts alike
rather than keeping wide gamut on Apple only.

**Metadata:** none of the source's is written: no EXIF, GPS, TIFF, IPTC,
XMP or orientation tag. The encoder writes its own JFIF header and may
write an sRGB profile, density, a colour-space and size EXIF, and (ImageIO)
an empty Photoshop IRB of its own. Those describe the new file, not the
photo or where it was taken.

**Transparency** becomes white on every host, an explicit choice: white
is filled before the image is drawn. The canvas standard composites onto
black when the format has no alpha, and so does a bare ImageIO JPEG
encode. A transparent PNG logo turning black is the familiar bug, and
white is what a person expects.

### A1.4 Failures

| code | when | message (native) |
|---|---|---|
| `TypeError` (rejected, nothing queued) | `from` or `to` is not a string; `options` is missing, or a limit is not an integer in range | `storage.fs.compressImage(): maxDimension must be an integer from 1 to 8192` |
| `denied` | no `fs.read` on `from`, or no `fs.write` on `to`. Both are checked before anything is read. | `denied: fs.write` |
| `ENOENT`, `ENOTDIR`, `EISDIR`, `failed` | the source is missing or a folder; `to`'s folder is missing: the code `readFile` and `atomicWriteFile` give on that host | the filesystem's |
| `failed` | a path is not `app:/` | `compressImage: needs app:/ paths` |
| `too-large` | the source is over 64 MiB, or its header says more than 64 Mi pixels (`exact_raster::MAX_ENCODED_BYTES`, `MAX_SOURCE_PIXELS`) | `compressImage: too-large: 9000×9000 pixels is over 67108864` |
| `undecodable` | not an image the platform decodes, corrupt, or (on the web) a header whose size is not read there, HEIF and AVIF included | `compressImage: undecodable: …` |
| `unfit` | no trial fits `maxBytes` within the search | `compressImage: unfit: no JPEG of this image fits 1000 bytes` |
| `timeout` | the codec's 20 s ran out, or the waiter's 30 s did and nothing was written (A1.5) | `compressImage: timeout: …` |
| `unsupported` | the host has no codec (A1.3), or the browser encodes no JPEG | `compressImage: unsupported: no JPEG encoder on this host` |

Natively the code is read from the message (`compressImage: <code>: `),
as the prelude reads `denied: ` today. The web sets `code` directly. A
Rust source gets the message. On any failure `to` is left as it was.

### A1.5 Limits

- **Input:** 64 MiB and 64 Mi source pixels. The file size is checked
  (`stat`) before the file is read, and the read itself is capped: Ibex
  reads the opened descriptor through `take(64 MiB + 1)`
  (`AppDirectories::read_capped`), so a file replaced or grown since
  `stat` is `too-large` without being read whole. The web's `Blob` is
  immutable and its size is checked before it is decoded. An entry is one
  IndexedDB record, read whole by any operation on it (`stat` too), so
  there the size check precedes the `Blob` and the decode, not the
  record's read; a byte entry got there through a write of those bytes. The pixel count is
  checked from the **header, before anything is decoded**: natively from
  ImageIO's properties, which read only the header; on the web by
  `storage-image.js` reading, within the first 256 KiB
  (`exact_raster::MAX_HEADER_BYTES`), the size of JPEG (its frame header,
  segment by segment), PNG (IHDR), GIF (the larger of its screen and its
  first image descriptor), WebP (the larger of a `VP8X` canvas and its
  first frame, `VP8 `, `VP8L` or `ANMF`) and BMP (signed 32-bit sides, or
  the 12-byte core header's 16-bit ones). A side that is not a positive
  integer, a size not found, and any other format, HEIF and AVIF included,
  are `undecodable` and never reach `createImageBitmap`: a HEIF/AVIF
  container's `ispe` need not be the coded frame's size, and Firefox
  decodes the frame before comparing them. The decoded size is checked
  again after.
- **Memory.** What the host allocates itself: the source bytes (≤ 64
  MiB), one `w × h × 4` sRGB bitmap at a time (≤ 256 MiB at 8192²; 61 MiB
  at Bluesky's 4000), the best JPEG so far (≤ `maxBytes`), and the trial
  being measured, which is **not** bounded by `maxBytes` (a trial that
  misses is larger by definition): it is what the encoder makes of the
  `w × h` bitmap at that quality, and it is dropped as soon as its length
  is compared, as the web's trial `Blob` is. What the codec allocates is
  its own: ImageIO subsamples JPEG and HEIC while decoding a thumbnail, so
  those stay near the thumbnail's size; PNG, GIF, TIFF and WebP may be
  decoded whole first, up to the pixel limit (64 Mi pixels, 256 MiB at 8
  bits, more at 16). Nothing is cached between sizes. On the web the
  browser decodes the whole bitmap, at most 64 Mi pixels by the header
  check, and the bitmap is closed in a `finally`.
- **Time, and a result after the wait has run out.** Natively a TypeScript
  call has a waiter: exact-js waits on Ibex for a storage step for 30 s
  (`js/src/storage.rs`), then fails the answer and moves the queue on.
  The pool job cannot be cancelled mid-trial (ImageIO has no cancel), so
  the write is guarded instead, by the call's **right to write**
  (`CommitGate`):
  - Ibex registers it when the prelude issues the call to Ibex, which is
    when the call reaches the head of the module's queue, on the JS
    thread, before any waiter for it can start (`ibex2_async_begin`).
  - The write happens holding it: `write`, `sync` and `rename` all run
    under its lock, after checking it has not been taken away.
  - A waiter whose 30 s run out first calls `Context::abandon_image_work`.
    Every call that has not begun its write loses the right: it writes
    nothing, ever. A call in the middle of its write holds the lock, so
    giving up waits for that write to end. A call that has written keeps
    its right, marked written, **until the owner takes its completion**
    from the queue (`take_task`), not merely until its job ends; and after
    giving up the waiter looks at the queue once more. So a waiter that
    gives up after a write, or just as one completes, finds a result, not
    nothing, and waits for it (5 s more, then looks again) instead of
    failing it.
  - Only when it took a right away and no completion is ready does the
    waiter fail the step, with `compressImage: timeout: the storage wait
    ran out; nothing was written`, code `timeout`
    (`__exact_storage_failed` now takes the code its message names, which
    leaves every other waiter failure `failed`). For an answer the whole
    answer fails and the queue moves on, as exact-js already did for any
    step whose wait ran out (`__exact_storage_failed`); for a compression
    that is now safe, since it can no longer write. For background work (a
    call an answer started and did not await) and for a call the runner
    let go of, which used to stall the queue on any such failure, the
    compression is now failed through the prelude
    (`__exact_background_failed`, `__exact_let_go`'s failure): its
    rejection runs, the queue moves on, and a let-go call keeps the rest
    of its storage, delivered on. Only a compression that lost its right
    is failed so: the prelude checks that the operation in flight is a
    `compressImage` and that the waiter said it took the right. Any other
    operation there may still write, so its queue still waits, as before.
    Two waiters can watch one call (a forgotten answer's, still running,
    and the let-go chain's), so a waiter that finds the right already
    taken reports it taken too.
  - Not changed, and outside this amendment: on the answer path an
    ordinary write whose wait runs out still lets the queue move on while
    it may yet land, as on `origin/main` (QUEUE).
  - A module unloaded with a call in flight, and an Ibex runtime shut down
    with one, take its right away the same way (`Session`'s drop,
    `RuntimeState::shutdown`); a write already under way finishes, as any
    storage in flight at teardown does (LLP 1097 D10).

  So no result lands after the guest was told the call failed, and later
  storage never meets a late write; this replaces r2's fixed 24 s margin,
  which a stalled `sync` could outrun, and r3's removal of the right when
  the job ended, which a completion arriving just before the waiter gave
  up could slip past. The codec also stops itself: it
  starts no decode or trial 20 s (`TRIAL_BUDGET`) after the pool job
  began, and ends `timeout`, so a slow search returns well inside the
  wait. A Rust source's request has no waiter that gives up (the host
  worker runs it to its end) and no right to take away; nor has the web.
  Both keep the 20 s trial budget, counted from the start of the work;
  the web checks it again after reading the header, before decoding.
- **One at a time per module:** storage's queue serializes it. Four images
  are four calls.
- **Across tabs on the web:** like `writeFile`, the result replaces `to`
  last-writer-wins; the path lock is held for the write, not across the
  seconds of encoding, so another tab's storage is not refused `EBUSY` for
  that long. The module's own queue keeps its own order.

### A1.6 Agent and fixtures

This is computation on the module's own files, not a device capability.
Nothing is held and there is no substitute. Under `--storage <name>` a
drive runs the real codec on macOS, iOS and the web, and gets
`unsupported` on Linux. Without a scratch store it is refused as all
storage is (`agent`). The fixtures are
`scripts/fixtures/picker/oriented-gps.jpg`, a small JPEG stored 64×48
with EXIF orientation 6 (rotate 90°), red over blue, with a GPS block and
a capture date (a correct result is 48×64, blue on the left, with no
orientation, GPS or capture date), and
`scripts/fixtures/picker/compress-trials.json`, trial sequences recorded
from a verbatim copy of `compress.ts`'s loop with a stand-in encoder. A
poorly compressing image (noise) that exercises the shrinks is generated
by each test, not committed.

### A1.7 Tests

- **Ibex (patch 9):** `compress_image` with a stand-in codec. Read and
  write denial are reported before the codec runs. A source over the limit
  is `too-large`, from `stat`, and a file larger than the cap is read only
  to the cap and refused. A failing codec leaves `to` untouched, and in
  place leaves the source. A waiter that gives up while the codec runs
  takes the right to write away: the result is `timeout` and writes
  nothing; giving up after the write finds it written, and keeps finding
  it until the completion is taken; giving up during a write waits for
  it; shutdown takes an unwritten call's right away. The codec is handed the trial deadline. Non-`app:/`
  and `doc:/` paths are refused, and so is a missing codec
  (`unsupported`). The opcode table includes 121.
- **`exact-data` (every platform):** the search is a pure function over an
  `encode(w, h, q)` closure, checked against the recorded sequences: fits
  at 51 then climbs; 51 and 26 miss and the size shrinks; four shrinks give
  `unfit`; the 333 tower; a portrait; an already-small source is not
  upscaled. The one-pixel deviation has its own cases. The same table is
  checked in Bun against `storage-image.js`'s search.
- **`exact-data` (macOS, and the iOS simulator):** the fixture comes back
  48×64, JPEG, without orientation, GPS or capture date, blue at its top
  left. A smaller limit scales it; a one-pixel limit gives 1×1. Noise
  shrinks to fit a small budget. A transparent pixel becomes white.
  Non-image bytes are `undecodable`; a frame header claiming 9000×9000 is
  `too-large` before decoding; a passed deadline starts nothing; the HEIC
  and PNG picker fixtures decode. On iOS the same test binary is built for
  `aarch64-apple-ios-sim` and run with `xcrun simctl spawn <udid>
  <binary> image`, so iOS's ImageIO answers too.
- **exact-js (macOS):** a TypeScript module calls
  `storage.fs.compressImage` on the fixture in `app:/data` (Hermes, the
  prelude, opcode 121, the codec) and gets the record. Then each refusal
  by name and code: `denied`, `ENOENT`, `undecodable`, `unfit`, `failed`
  for a `doc:/` destination, and a `TypeError` for a bad or missing
  option.
- **exact-js, giving up (macOS):** with the storage wait shortened to 1 ms
  (`Module::set_storage_wait`, a test hook), a compression of 2000×1500

## Summary

The picker was admitted on 2026-09-21 (LLP 1045 D10) and never built. The
only picker today is the macOS document panel (`DocumentsMac.swift`), which
serves `file_handlers`. A search over `host/`, `contract/lower/src`,
`runner/src` and `js/src` for `upload(`, `PHPicker`, `fileinput` and
`accept` finds no picker: the hits are a GPU texture `upload`
(`host/linux/src/gpu/images.rs:45`) and a socket `accept`
(`AgentIOS.swift:83`).

This RFC builds it with the web's spelling:

```
input type="file" accept="image/*,video/*" multiple testId="attach"
    change=attach display="none"
button press=choose aria-label="Add photo"
  image "symbol:photo"

action choose
  showPicker("attach")

action attach(files: list Picked) writes drafts
  ...
```

- **D1–D2, the tag and the command.** `input type=file` is the tag;
  `showPicker(id)` is `HTMLInputElement.showPicker()`. D10's
  `upload(id, "image")` becomes these two: the kind moves into `accept`.
- **D3, the value.** `change` carries a list of records: an
  `app:/tmp/picked/…` path, the name, the MIME type, the size and, for
  media, the pixel size and duration.
- **D4–D5, the bytes.** Native hosts copy them into `app:/tmp/picked/`
  before `change` fires; on the web the browser's `File` backs the entry.
  The runner never sees bytes.
- **D6, the formats.** iOS Safari's rule: HEIC becomes JPEG only when
  `accept` excludes it.
- **D7, previews.** `image` and `video` take an `app:/` source.
- **D9, the substitute.** A held picker is answered with `type @t <path>…`
  on every host, Linux included.

`accept` is bounded by the compiler: media types, or the types the
manifest's `file_handlers` declares (D1). `capture` is refused, so there is
no camera, and no picker takes "any file".

## Motivation

Three admitted consumers:

- **Interview (LLP 1045).** Captioned figures: pick, store or upload, then
  `format(id, figure(url))` inserts `![](url)` with the caret in the
  caption.
- **Bluesky** (`bluesky-exact2`, admitted 2026-09-27). Compose attaches up
  to four images or one video. `app.bsky.embed.images` wants each image's
  `aspectRatio` beside its blob, so D3 reports the pixel size and the app
  never decodes a file just to post it.
- **Fieldnotes' import** (LLP 1069.010 D3). A backup `.json` chosen by the
  person, copied into `app:/tmp`: the same element with `accept` from
  `file_handlers`.

`expo-image-picker` is among the most used Expo packages (LLP 1069 §2.2).

## Design

### D1 — The tag is HTML's: `input type=file` with `accept` and `multiple`

The kernel's input node gains `type=file` and two props, `accept` (the MIME
list as HTML writes it) and `multiple`. No new node type.

A visible file input presents as the platform's own button: the browser's
"Choose File" control on the web, a system button titled by `aria-label` on
Apple. Almost every app hides it and opens it from its own button (D2), as
on the web.

**`accept` may name:**

- `image/*`, `video/*`, `image/<subtype>`, `video/<subtype>`;
- a MIME type or extension that a `file_handlers` entry in `app.json`
  declares (`rules/DEFERRED.md`, widened 2026-09-27 with LLP 1069.010).

**The bake refuses**, each citing `rules/DEFERRED.md`'s sentence:

- an `accept` that is not a literal, or is missing;
- any other type, `*/*`, or an extension no `file_handlers` entry names;
- `capture`.

Widening further is a DEFERRED line and a bake change, never an attribute
value.

*Rejected:* D10's `upload(id, "image" | "video")` with no element. Its
value has no node to arrive on (`Outcome.commands` is fire-and-forget), so
it would need a "command with a reply" path nothing else uses. The element
gives the value a home and the agent a target, and matches what a web
author writes. D10's text points here.

### D2 — `showPicker(id)` opens it

`showPicker` joins `focus`, `selectText` and `blur` in `HOST_COMMANDS`
(`contract/types/src/checks.rs:682`): a command naming an element by id,
issued from an action. On the web the glue calls
`HTMLInputElement.showPicker()`.

**User activation.** Browsers allow `showPicker()` only under transient user
activation. The glue runs commands inside the input dispatch, so a
`showPicker` in a pressed action works on the web. Native hosts don't
enforce activation: a picker opens from any action, a timer or an answer
included (ruled). On the web the same `showPicker` outside a press is
refused by the browser (`NotAllowedError`), journaled as `picker: refused:
NotAllowedError`, and fires `cancel`. The authoring guide says so; nothing
in the compiler or the hosts enforces it.

A second `showPicker` while one is open does nothing and journals it.
Cancelling fires HTML's `cancel` event on the input (a new `EventKind`), so
a compose screen can clear its "choosing…" state.

### D3 — `change` carries a list of `Picked` records

| field | type | always | notes |
|---|---|---|---|
| `path` | string | yes | `app:/tmp/picked/<id>.<ext>`; `<id>` from the launch seed and a counter (LLP 1027.000), never the user's file name |
| `name` | string | yes | the original name, for display (`IMG_0412.HEIC`) |
| `type` | string | yes | the MIME type of what is at `path` (after D6) |
| `size` | number | yes | bytes at `path` |
| `width`, `height` | number | images and video | pixels, orientation applied (EXIF, or the track transform) |
| `duration` | number | video | seconds |

`Picked` is a shape the compiler supplies, as `exactViewport`'s is, so
`action attach(files: list Picked)` type-checks. Without `multiple` the list
has one element, in the order the user selected.

- **Apple.** Pixel size from the ImageIO header (no decode) or `AVAsset`'s
  track: microseconds.
- **Web.** `createImageBitmap` for images, a `<video>`'s `loadedmetadata`
  for video, then `change`.
- A file whose metadata can't be read is delivered without the size fields.
  It is not an error.

### D4 — The bytes go to `app:/tmp/picked/`, and the app decides what's next

**Native hosts** copy each picked file into `app:/tmp/picked/` before
`change` fires. The copy is required: PHPicker's `loadFileRepresentation` URL
is deleted when its callback returns, and `NSOpenPanel`'s URL is
security-scoped. A path the app holds must outlive both.

What the app does next is its own logic, through grants it already declares
(LLP 1027.001, LLP 1069.008):

- read it: `fs.read app:/tmp`;
- keep it: `fs.write app:/data`, then `rename`;
- upload it: `net.fetch <origin>`, with `readFile`'s bytes as the body.

The picker needs no grant. The user's selection is the consent, as on the
web and for PHPicker, which needs no photo-library permission and no usage
string. LLP 1069.008 D7's reach table lists "picks files (`accept`)",
derived from the tag's presence in the plan.

`app:/tmp/picked/` is emptied at launch.

*Known cost:* uploading a large video puts it all in the source's memory
(`readFile`). A streamed request body from a path belongs to LLP 1016.000's
streaming work.

### D5 — On the web the `File` backs the entry; nothing is copied

The web's `app:/tmp` lives in IndexedDB (`host/web/storage-fs.js`). Copying
a 300 MB video into it before `change` would stall the pick and double the
storage. The glue registers each `File` as a blob-backed entry at its
`app:/tmp/picked/…` path:

- `stat` answers from `File.size`;
- `readFile` answers `await file.arrayBuffer()`;
- `rename` into `app:/data` is where a real copy is written.

A `File` is structured-cloneable, so the storage worker holds it the same
way. The entries last as long as the page.

### D6 — The host delivers a type `accept` names, converting when it must

This follows iOS Safari, on every host (ruled). Given `accept="image/jpeg"`,
Safari hands a HEIC photo over as a JPEG; given `image/*`, the original.

| accept | the photo is HEIC | the video is HEVC/ProRes |
|---|---|---|
| `image/*`, `video/*` | HEIC, as is | `preferredAssetRepresentationMode = .current` |
| `image/jpeg,image/png` (no HEIC) | JPEG, quality 0.9, orientation applied, location metadata stripped | `.compatible` (H.264) |

- **macOS.** `NSOpenPanel` returns the file on disk; the same rule converts
  with ImageIO and `AVAssetExportSession`.
- **Web.** The browser has already chosen what it hands over.
- **Non-media types** (`file_handlers`) are never converted.
- **No other transforms** at pick: no resizing, compression, cropping or
  size limit. A cap is the app's decision, made with `size`. Image editing
  stays out (LLP 1045 §5). *Reopened 2026-10-08 for one step the app asks
  for after the pick:* `storage.fs.compressImage` (§Amendment A1).

### D7 — `image` and `video` take `app:/` sources

A compose screen shows the picked image before it is uploaded:

- **Apple:** the owned directory's file URL.
- **Linux:** the path.
- **Web:** a blob URL for the storage entry, revoked when the node leaves.

The read is the host's. A source outside `app:/tmp`, `app:/cache` and
`app:/data` is refused, and so is `..`.

### D8 — Per host

| host | presents | notes |
|---|---|---|
| iOS | media: `PHPickerViewController`, filter from `accept`, `selectionLimit` 1 or 0 for `multiple`; other types: `UIDocumentPickerViewController(forOpeningContentTypes:asCopy: true)` | no permission prompt, no usage string; presented from the session's view controller (LLP 1035.001) |
| macOS | `NSOpenPanel` with `allowedContentTypes` from `accept` (`UTType(mimeType:)`, `.image`, `.movie`), `allowsMultipleSelection` from `multiple` | a sheet on the window; separate from `DocumentsMac`'s `open-file` route, which stays the manifest's |
| web | the element's own `showPicker()` | Safari, Chrome and Firefox support it on file inputs |
| Linux | refused: `showPicker` journals `picker: refused: unavailable` and fires `cancel` | an XDG portal `FileChooser` when a desktop Linux host exists (ruled). The substitute (D9) still answers |

### D9 — Substitute

LLP 1069.007 D7's paragraph for this capability:

1. **Shape:** a request, command-shaped: the answer arrives as `change` (or
   `cancel`) on the input.
2. **Pending:** `showPicker` under the agent presents nothing. `state.pending`
   lists `{ticket, device: {capability: "pick", args: {id: "attach",
   accept: ["image/*", "video/*"], multiple: true}}}` (LLP 1069.007 D3).
   **Answer:** `type @t <path>…`, each a file on the driver's machine,
   copied in through D4/D5's path; the host then reads the metadata (D3),
   converts (D6) and fires `change`, so a HEIC fixture tests the JPEG
   conversion. `tap @t cancel` fires `cancel`. **Fixture:**
   `--answer pick=<path>[,<path>…]`. The answer's `delivery` is
   `substituted`.
3. **Web override:** CDP's `Page.setInterceptFileChooserDialog`, then
   `DOM.setFileInputFiles` on `Page.fileChooserOpened` (`delivery:
   "platform"`).

Every host takes it, Linux included, so a smoke drives a compose flow
headlessly. The repo carries one HEIC image and one short H.264 video at
`scripts/fixtures/picker/`.

## Verification

- A fixture app, `apps/picker-fixture`: picks one image, many images and a
  video; previews them over `app:/tmp/picked/`; moves one into `app:/data`;
  restarts to show `tmp` emptied and `data` kept.
- Driven by `smoke.mjs` on web, macOS, iOS and Linux through D9.
- On iOS, one manual pass on a phone with a real HEIC and a Cinematic
  video, against D6's table.
- On the web, a `showPicker` from a timer is refused by the browser and
  journaled (D2); on macOS the same action opens the panel.

## Not in this RFC

- A camera and `capture` ("No camera anything").
- Any `accept` beyond media and `file_handlers` types.
- Directory picking, save panels, handles to documents edited in place
  (LLP 1069.010 D1–D2).
- Drag and drop of files onto the app; receiving shares.
- Image editing; resizing beyond §Amendment A1's `compressImage`; upload progress (the app's state).
- A streamed request body from a path (LLP 1016.000).
- The photo library as a data source (`expo-media-library`).

## Decided

1. The element plus `showPicker(id)`; LLP 1045 D10's `upload` is replaced
   (D1, D2).
2. Native hosts don't enforce user activation; the web's rule is the
   browser's and is documented (D2).
3. iOS Safari's conversion rule on every host (D6).
4. Linux refuses; only the substitute answers there (D8).
5. `accept` widens to `file_handlers` types, per `rules/DEFERRED.md`'s
   2026-09-27 widening; this element is LLP 1069.010's import (D1).
