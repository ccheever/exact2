# LLP 1069.002: The media picker — `<input type=file accept="image/*,video/*">`

**Type:** RFC
**Status:** Draft; Charlie's rulings recorded 2026-09-27 (§Rulings, which overrides the text below where they differ)
**Systems:** Contract (`input type=file`, `accept`, `multiple`; the `showPicker` command; `change` carrying a file list); Kernel (no new node type; three props); Runner (the command, a `picked` value, a pending picker in `state`); Apple host (PHPicker on iOS, `NSOpenPanel` on macOS); Web host (the element itself, blob-backed `app:/tmp` entries); Linux host (refused, with an agent substitute); `image`/`video` (`app:/` sources); Agent API (`type` answers a picker)
**Author:** Claude (Opus 5.5) for Charlie Cheever

## Rulings (Charlie, 2026-09-27)

- **Q1: the element plus `showPicker(id)`,** not LLP 1045 D10's `upload`.
- **Q2: native hosts do not enforce user activation** (Charlie: "don't enforce it ourselves. let's just trust developers"). **This overrides D2's refusal.** A native host opens the picker from any action. On the web the browser's own rule still applies, so a picker opened outside a press fails there. That difference is documented for authors, not enforced.
- **Q3: iOS Safari's conversion rule on every host.**
- **Q4: Linux refuses** and only the agent substitute answers, until a desktop Linux host exists.

## Summary

The picker was admitted on 2026-09-21 (LLP 1045 D10) and never built. A
search for `upload(`, `PHPicker`, `fileinput` and `accept` over `host/`,
`contract/lower/src`, `runner/src` and `js/src` finds nothing. The only
picker today is the macOS document panel (`DocumentsMac.swift`), and it
serves `file_handlers`, not media.

This RFC finishes the picker, using the web's spelling:

```
input type="file" accept="image/*,video/*" multiple testId="attach"
    change=attach display="none"
button press=choose aria-label="Add photo"
  image "symbol:photo"

action choose
  showPicker("attach")

action attach(files: list Picked) writes drafts
  ...
```

- **D1–D2, the tag and the command.** `input type=file` is the tag. The
  command `showPicker(id)` is `HTMLInputElement.showPicker()`, which opens
  it from any press. D10's `upload(id, "image")` becomes these two: the kind
  of media moves into `accept`.
- **D3, the value.** The picked files reach the app as `change`'s value. It
  is a list of records: an `app:/tmp/picked/…` path, the name, the MIME
  type, the size and, where the host knows them cheaply, the pixel size and
  the duration.
- **D4–D5, the bytes.** The host copies them into the app's temporary
  directory before `change` fires. On the web they are not copied; the
  browser's `File` backs the entry. The app keeps a file by renaming it into
  `app:/data`, or uploads it with `fetch`. The runner never sees bytes, as
  D10 required.
- **D6, the formats.** The host delivers a type the `accept` list names,
  converting when it must: HEIC to JPEG, and a compatible video
  representation. That is iOS Safari's rule, and Safari is the oracle.
- **D7, previews.** `image` and `video` accept an `app:/` source, so a
  compose screen can show what was picked before it is uploaded.
- **D9, the agent.** A pending picker appears in `state`. `type <id>
  <fixture>` answers it on every host, including Linux, where there is no
  system picker (LLP 1069.007).

The DEFERRED limit holds and the compiler enforces it. `accept` must be
`image/*`, `video/*`, or image and video MIME types. `capture` is refused,
so there is no camera. There is no generic file input.

## Motivation

Two admitted consumers want this now:

- **Interview (LLP 1045).** Captioned figures in posts. D10 already
  describes the flow: pick, store or upload, then `format(id, figure(url))`
  inserts `![](url)` with the caret in the caption.
- **Bluesky** (`bluesky-exact2`, admitted 2026-09-27). Compose attaches up
  to four images or one video. Bluesky's `app.bsky.embed.images` wants each
  image's `aspectRatio` beside its blob. If the picker doesn't report the
  pixel size, the app has to decode the file itself just to post it. D3
  therefore reports the size.

The survey (LLP 1069 §2.2) found `expo-image-picker` among the most used
Expo packages. Nothing in exact2 fills that role.

## Design

### D1 — The tag is HTML's: `input type=file` with `accept` and `multiple`

The kernel's input node gains `type=file` and two props, `accept` (the MIME
list as HTML writes it) and `multiple` (a boolean). No new node type.

A visible file input presents as the platform's own button:

- the browser's "Choose File" control on the web;
- a system button titled by `aria-label` on Apple.

Almost every real app hides the input and opens it from its own button
(D2), which is also how the web is written. The default is kept only so
that a bare input does what a bare `<input type=file>` does.

**The compiler refuses:**

- an `accept` that is not a literal;
- an `accept` naming anything but `image/*`, `video/*`, `image/<subtype>` or
  `video/<subtype>` (no extensions, no other types);
- a missing `accept`;
- `capture`.

Each refusal cites `rules/DEFERRED.md`'s sentence. This is how "no generic
file input" is kept: widening it is a compiler change and a DEFERRED line,
never an attribute value.

*Alternative, D10 as written:* `upload(id, "image" | "video")` as a
capability command, with no element. It is one line shorter for the author,
but it has no web name. Its value also has no node to arrive on:
`change` needs an element, and a command can't carry an answer back
(`Outcome.commands` is fire-and-forget). It would need a new
"command with a reply" path that nothing else uses. The element gives the
value a home, gives the agent an address (D9), and matches what a web
author already writes. **Recommended: the element.** D10's text is amended
to point here.

### D2 — `showPicker(id)` opens it from any press

`showPicker` joins `focus`, `selectText` and `blur`: a command naming an
element by id, issued from an action. Its name is
`HTMLInputElement.showPicker()`. On the web the glue calls exactly that.

Browsers allow `showPicker()` only during user activation. The runner
issues commands inside the batch that answers the press, so the web host
calls it inside the event's own task. A `showPicker` issued outside a press
(a timer, an answer) is refused by name on every host, not only the web,
so a flow that works natively cannot fail only in the browser. This is
the web's rule, applied everywhere, the same way LLP 1017 P1 treats the
web's other limits.

A second `showPicker` while one is open does nothing and journals it.
Cancelling fires HTML's `cancel` event on the input (a new `EventKind`),
so a compose screen can clear its "choosing…" state.

### D3 — `change` carries a list of `Picked` records

The value `change` passes to its action is `list Picked`:

| field | type | always | notes |
|---|---|---|---|
| `path` | string | yes | `app:/tmp/picked/<id>.<ext>`; `<id>` from the launch seed and a counter (LLP 1027.000), never the user's file name |
| `name` | string | yes | the original name, for display (`IMG_0412.HEIC`) |
| `type` | string | yes | the MIME type of what is at `path` (after D6), not of the original |
| `size` | number | yes | bytes at `path` |
| `width`, `height` | number | images and video | pixels, orientation applied (EXIF on images, the track transform on video) |
| `duration` | number | video | seconds |

`Picked` is a shape the compiler supplies, the way `exactViewport`'s shape
is supplied, so `action attach(files: list Picked)` type-checks. Without
`multiple`, the list has one element. The order is the order the user
selected in.

**Where the fields come from:**

- **Apple.** The pixel size comes from the ImageIO header (no decode) or
  `AVAsset`'s track. Reading it costs microseconds.
- **Web.** The browser has no header read, so the glue decodes once with
  `createImageBitmap` for images and reads a `<video>`'s `loadedmetadata`
  for video, then fires `change`.

A file whose metadata cannot be read is still delivered, with no size
fields. It is not an error; the app decides what to do.

### D4 — The bytes go to `app:/tmp/picked/`, and the app decides what's next

**Native hosts** copy each picked file into `app:/tmp/picked/` before
`change` fires. The copy is required:

- PHPicker's `loadFileRepresentation` URL is deleted when its callback
  returns.
- `NSOpenPanel`'s URL is security-scoped.

A path the app holds must outlive both.

**What the app does next** is its own logic, through the grants it already
declares (LLP 1027.001, LLP 1069.008):

- read it: `fs.read app:/tmp`;
- keep it: `fs.write app:/data`, then `rename`;
- upload it: `net.fetch <origin>`, with `readFile`'s bytes as the body.

The picker itself needs no grant. The user's selection is the consent, as
it is on the web and for PHPicker, which needs no photo-library permission
and no usage string. LLP 1069.008 still lists "picks images and video" on
the app's capability page, derived from the tag's presence in the plan.

`app:/tmp/picked/` is emptied at launch. A file the app did not move is
gone by the next launch, the way `tmp` behaves everywhere.

*Known cost:* uploading a large video means `readFile` puts it all in the
source's memory. A streamed request body from a path would avoid that. It
belongs to LLP 1016.000's streaming work, not here.

### D5 — On the web the `File` backs the entry; nothing is copied

The web's `app:/tmp` lives in IndexedDB (`host/web/storage-fs.js`). Copying
a 300 MB video into it before `change` would stall the pick for seconds and
double the storage.

Instead, the glue registers each `File` as a blob-backed entry at its
`app:/tmp/picked/…` path:

- `stat` answers from `File.size`.
- `readFile` answers `await file.arrayBuffer()`.
- `rename` into `app:/data` is the point where a real copy is written.

A `File` is structured-cloneable, so the storage worker holds it the same
way. The entries last as long as the page, which is what `tmp` means on the
web.

### D6 — The host delivers a type `accept` names, converting when it must

This follows iOS Safari. Given `accept="image/jpeg"`, Safari hands a HEIC
photo over as a JPEG, and given `image/*` it hands over the original. Every
Apple host does the same:

| accept | the photo is HEIC | the video is HEVC/ProRes |
|---|---|---|
| `image/*`, `video/*` | HEIC, as is | `PHPickerConfiguration.preferredAssetRepresentationMode = .current` |
| `image/jpeg,image/png` (no HEIC) | JPEG, quality 0.9, EXIF orientation applied, location metadata stripped | `.compatible` (H.264) |

The app that uploads to a server that rejects HEIC (Bluesky's accepts JPEG,
PNG and WebP) says so in `accept`. The one that keeps originals says
`image/*`.

- **macOS.** `NSOpenPanel` returns the file as it is on disk, so the same
  rule converts with ImageIO and `AVAssetExportSession`.
- **Web.** The browser has already chosen what it hands over.
- **No other transforms.** There is no resizing, compression, cropping or
  size limit. A cap is an app decision, and it has `size` to make it with.
  Image editing stays out (LLP 1045 §5).

### D7 — `image` and `video` take `app:/` sources

A compose screen shows the picked image before it is uploaded, so both tags
accept an `app:/…` source on every host:

- **Apple:** the owned directory's file URL.
- **Linux:** the path.
- **Web:** a blob URL for the storage entry. The glue revokes it when the
  node leaves.

The read is still the host's, not the app's. A source outside `app:/tmp`,
`app:/cache` and `app:/data` is refused, and so is `..`.

### D8 — Per host

| host | presents | notes |
|---|---|---|
| iOS | `PHPickerViewController`, filter from `accept` (`.images`, `.videos`, `.any(of:)`), `selectionLimit` 1 or 0 for `multiple` | no permission prompt, no usage string; presented from the session's view controller (LLP 1035.001's presenter owns presentation) |
| macOS | `NSOpenPanel` with `allowedContentTypes` from `accept` (`UTType(mimeType:)`, `.image`, `.movie`), `allowsMultipleSelection` from `multiple` | a sheet on the window, not modal to the app; separate from `DocumentsMac`'s `open-file` route, which stays the manifest's |
| web | the element's own `showPicker()` | Safari, Chrome and Firefox all support `showPicker()` on file inputs |
| Linux | refused: `showPicker` journals `picker unavailable on this host` and fires `cancel` | the DRM/KMS and headless hosts have no picker; an XDG portal `FileChooser` is the route when a desktop Linux host exists. The agent substitute (D9) still works here |

### D9 — The agent answers a picker with `type`

A picker opens without a system UI when an agent drives the session. It is
also open whenever a real one is showing.

- **`state` shows it:**
  `pending.picker: { id: "attach", accept: "image/*,video/*", multiple: true }`.
- **`type attach <path>…` answers it.** Each path is a file on the
  driver's machine, and the driver copies each one in through the same D4
  and D5 path the host uses. The host then reads the metadata (D3), runs
  the conversion (D6) and fires `change`. So a HEIC fixture tests the JPEG
  conversion.
- **`type attach ""` cancels it.**

A picker is an input, so answering it is a form of `type`, and there is no
new operation (`rules/DEFERRED.md` §Agent API). This is the concrete case of
LLP 1069.007's rule. Every host takes it, Linux included, so a smoke can
drive a compose flow headlessly. The repo carries one image and one short
video fixture, a HEIC and an H.264 file, at `scripts/fixtures/picker/`.

## Consumers, as written

**Interview's figure** (LLP 1045 D10 unchanged but for the verb):

```
input type="file" accept="image/*" testId="figure-file" display="none" change=figurePicked
button press=chooseFigure aria-label="Insert image"
  image "symbol:photo"

action chooseFigure
  showPicker("figure-file")
action figurePicked(files: list Picked) writes uploading
  uploading = first(files).path     // the app's source uploads it and answers a URL
```

**Bluesky compose.** Four images, or one video. The app's TypeScript
uploads each file to `com.atproto.repo.uploadBlob` and builds the embed
with `aspectRatio: { width, height }` from the record:

```
input type="file" accept="image/jpeg,image/png,image/webp" multiple
    testId="compose-images" display="none" change=attach
```

## Verification

- A fixture app, `apps/picker-fixture`. It picks one image, many images and
  a video; previews them with `image`/`video` over `app:/tmp/picked/`;
  moves one into `app:/data`; and restarts to show `tmp` emptied and `data`
  kept.
- Driven by `smoke.mjs` on web, macOS, iOS and Linux through D9's `type`.
- On iOS, one manual pass on a phone with a real HEIC and a Cinematic
  video, against D6's table.
- Web against Chrome and Safari's own `showPicker()` for the activation
  rule (D2).

## Not in this RFC

- A camera and `capture` (DEFERRED: "No camera anything").
- Any `accept` beyond images and video.
- Directory picking.
- Drag and drop of files onto the app.
- Receiving shares from other apps.
- Image editing or resizing.
- Progress for an upload. That is the app's state, as D10 said.
- A streamed request body from a path (LLP 1016.000).
- Save panels, and open/save for documents (LLP 1069.010).
- The photo library as a data source (`expo-media-library`).

## Open, for Charlie

1. **The spelling.** Should it be the element plus `showPicker` (D1, D2,
   recommended), or D10's `upload` command? Choosing the element amends
   D10's text and adds the `cancel` event and one command.
2. **Activation everywhere (D2).** Should a picker opened outside a press be
   refused natively too, to match the web? The alternative lets native
   hosts open it from anywhere. That's easier, but a flow can then work on
   iOS and fail in the browser.
3. **Conversion (D6).** Adopt iOS Safari's rule (convert only when `accept`
   excludes the original) as the cross-host rule?
4. **Linux (D8).** Is "refused, agent substitute only" right until a desktop
   Linux host exists?
