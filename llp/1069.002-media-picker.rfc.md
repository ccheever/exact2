## Amendment A1 (2026-10-08): `storage.fs.compressImage`

**Status:** approved by Charlie 2026-10-08, via the lead. This is a design; §As built
records what lands.

### Why

Bluesky's composer shrinks every picked image before upload
(`social-app/src/lib/media/image/compress.ts`). The lexicon's blob limit is
2 MB (`app.bsky.embed.images`: "May be up to 2 MB, formerly limited to 1
MB"). A phone photo is 3–12 MB, so the clone has to refuse most photos
outright. Under D6 a module could do this only by decoding and encoding
JPEG in JavaScript, with every byte passing through `readFile`. The
platforms already have the codecs.

### A1.1 The call

```ts
interface FileSystem {
  // … the existing members …
  /** Decode `from`, scale it to fit `maxDimension`, and encode it as a JPEG
   * of at most `maxBytes` at `to`. Orientation is applied; no metadata is
   * written. */
  compressImage(from: string, to: string, options: CompressImageOptions): Promise<CompressedImage>;
}
export interface CompressImageOptions {
  readonly maxDimension: number; // integer, 1..8192: the longer side's limit, in pixels
  readonly maxBytes: number;     // integer, 1..67108864: the encoded file's limit
}
export interface CompressedImage {
  readonly path: string;         // `to`
  readonly type: "image/jpeg";
  readonly size: number;         // bytes at `path`, <= maxBytes
  readonly width: number;        // pixels, orientation applied
  readonly height: number;
}
```

```ts
// Bluesky's post limits; avatars and banners pass 2000 and 1_000_000.
const out = await storage.fs.compressImage(pick.path, `app:/tmp/upload/${n}.jpg`,
  { maxDimension: 4000, maxBytes: 2_000_000 });
const body = await storage.fs.readFile(out.path);   // then uploadBlob
```

- **It is an `fs` member,** like `copyFile`: two paths, read on the first and write on
  the second. It joins the module's one storage queue (LLP 1097 D3), so it
  runs in order after the operations issued before it. It
  is refused where storage is: at bake, and in a drive with no scratch
  store. Its refusals carry the same `{kind: "Unavailable", code}` as
  every other storage call. It takes no new grant. The app must hold `fs.read` on `from` and
  `fs.write` on `to`; Bluesky's are `fs.read app:/tmp` and `fs.write
  app:/tmp`.
- **The caller names `to`,** as with `copyFile` and `rename`. The host
  mints no name. Under LLP 1027.000 a name is
  the app's to derive from its seed. Writing to a known path also lets the app replace or
  remove the file. `to` is replaced atomically; `from === to` is allowed
  (the source is read in full before anything is written). Both paths must
  be `app:/` paths. A `doc:/` path or a native disk path is refused
  (`failed`), as `copyFile` is for documents.
- **The result has `Picked`'s fields** (`path`, `type`, `size`, `width`,
  `height`), so a compressed image can stand in for the pick.
- **The app chooses the numbers.** Nothing in exact2 knows Bluesky's 4000
  and 2 MB.
- **It always re-encodes,** even when the source already fits. That is
  what strips a JPEG's GPS block. An app that wants to skip the call compares
  `size`, `width` and `height` with its limits first, as Bluesky's
  `compressIfNeeded` does.
- **A Rust source** asks for it with `exact_data::storage::request(
  "fs.compressImage", {"path", "destination", "maxDimension", "maxBytes"})`.
  The reply is the same record as JSON.

### A1.2 The algorithm: Bluesky's, run in the host

The search is `compressImage` in `compress.ts`, as it is today. Here it is restated over the
**oriented** source size `W × H`:

```
dim = maxDimension; lo = 0; hi = 101; shrinks = 0; best = none
while hi - lo > 1:
  if shrinks >= 4: break
  (w, h) = (W, H) if W <= dim and H <= dim
           else scale s = dim / max(W, H); (floor(W*s), floor(H*s))
  q = round((lo + hi) / 2)               // JS Math.round: halves go up
  if q <= 13:                            // 51, 26, 13: give up on this size
    lo = 0; hi = 101; shrinks += 1; dim = floor(dim * 0.8); continue
  bytes = jpeg(resize(source, w, h), quality q / 100)
  if len(bytes) <= maxBytes: lo = q; best = bytes (w, h)
  else: hi = q
return best, or fail `unfit`
```

The fidelity details follow `compress.ts` exactly:

- The fourth shrink ends the loop before its size is tried. The sizes
  tried are therefore `maxDimension × 0.8^k` for k = 0..3: 4000, 3200, 2560 and
  2048, never the ~1638 its comment mentions.
- A size whose 51 and 26 both miss gives up on that size and shrinks. Once a quality fits, `lo` is at
  least 26, so the search never shrinks again and climbs to the best quality that fits
  (about seven encodes).
- Size is the encoded byte length. Bluesky estimates it from the base64
  length (`round(len × 3 / 4)`), which can overstate it by up to two bytes. Our check is the
  exact one.
- Quality is the platform's own scale. On iOS, `expo-image-manipulator`'s
  `compress` is ImageIO's `kCGImageDestinationLossyCompressionQuality`. On
  the web it is `toBlob`'s quality. Each of our hosts passes `q / 100` to
  the same parameter.

**The search runs in the host, in one call.** The alternative was a module-side
loop over a single-quality primitive. The host is better because:

- No image bytes cross into JavaScript. A trial is only a length, and the
  module never holds a 2 MB buffer just to measure it.
- The source is decoded once per size, not once per trial. Natively that
  is one ImageIO thumbnail decode, and the seven quality trials encode the
  same bitmap.
- One storage operation keeps the queue's order and the answer's pending
  state simple. Fifteen round trips, each a queued storage step, would hold
  the queue as long and cost an executor turn each.
- The same algorithm on every host is a spec this section fixes. A test
  checks it against a recorded trial sequence (A1.7).

The cost is that an app cannot pick a different search. That is a later
option (`quality` alone), not something this needs.

### A1.3 Per host

| host | where it runs | how |
|---|---|---|
| iOS, macOS (TypeScript) | Ibex's storage worker, off the JS thread | The prelude's `fs.compressImage` reaches Ibex as a new async fs op (opcode 121, Exact patch 8). Ibex admits both paths, reads the source through its app-directory handles, calls the codec the embedder installed (`Context::set_image_codec`), and writes the result with its atomic write. exact-js installs `exact_data::image::compress`. |
| iOS, macOS (Rust source) | the host worker that runs storage continuations | `exact-data-host`'s native adapter takes `fs.compressImage` and calls the same Ibex function with the same codec |
| the codec on Apple | — | Rust FFI to ImageIO and Core Graphics, no Swift: `CGImageSourceCreateWithData`; the header's size and orientation from `CGImageSourceCopyPropertiesAtIndex`; per size, `CGImageSourceCreateThumbnailAtIndex` (`…FromImageAlways`, `…WithTransform` for orientation, `…ThumbnailMaxPixelSize` = the long side), drawn into an opaque 8-bit RGB `CGBitmapContext` of exactly `w × h`, filled white first, with high-quality interpolation; each trial `CGImageDestinationCreateWithData` (`public.jpeg`) + `AddImage` with only `kCGImageDestinationLossyCompressionQuality`. No property dictionary is copied, so there is no EXIF, GPS, TIFF or orientation tag. The colour profile of the drawn image (sRGB or Display P3) is kept. It decodes what ImageIO decodes: JPEG, PNG, HEIC/HEIF, WebP, GIF (the first frame), TIFF. |
| web, all three paths | the page, or the module's worker when it is placed there | `storage-fs.js` `compressImage`, used by the wasm host's realm (`storage.js`), the JS target (`ts-data.js`) and Rust storage requests (`storage-request.js`). It reads the entry as a `Blob` (a picked entry is already the `File`, D5) and lazily imports `storage-image.js`, so nothing loads before first pixel. Then `createImageBitmap(blob, {imageOrientation: "from-image"})` (retried without the option where a browser refuses that enum value; every current engine applies EXIF orientation by default), an `OffscreenCanvas(w, h)` with `{alpha: false}`, filled white, `imageSmoothingQuality = "high"`, `drawImage`, then `convertToBlob({type: "image/jpeg", quality: q / 100})`. In a window without `OffscreenCanvas` it uses a `<canvas>` and `toBlob`. A blob whose type is not `image/jpeg` (a browser that cannot encode JPEG) is `unsupported`. The result is stored as bytes (`atomicWriteOwnedFile`), not as a `Blob` entry, so `appendFile` and `copyFile` treat it as any file. Canvas output carries no metadata. |
| Linux, Windows, Android | — | **Refused:** `compressImage: unsupported: no JPEG encoder on this host`. The workspace has no JPEG encoder outside Apple and the browser. The `image` crate appears only in manifests outside the workspace (`game/bake`, `bench/…`), not in `Cargo.lock`, and the Linux host decodes only PNG itself (`host/linux/src/image/jpeg.rs`: other formats refuse off Android). Android could use `AImageDecoder` with `AndroidBitmap_compress`, which is deferred. An app treats `unsupported` as "upload the original if it fits, else say no", which is the clone's current behaviour. |

**Transparency** becomes white on every host, an explicit choice. The
canvas standard composites onto black when the format has no alpha, and so
does a bare ImageIO JPEG encode. A transparent PNG logo turning black is
the familiar bug, and white is what a person expects.

### A1.4 Failures

| code | when | message (native) |
|---|---|---|
| `TypeError` (rejected, nothing queued) | `from` or `to` is not a string; `options` is missing, or a limit is not an integer in range | `storage.fs.compressImage(): maxDimension must be an integer from 1 to 8192` |
| `denied` | no `fs.read` on `from`, or no `fs.write` on `to`. Both are checked before anything is read. | `denied: fs.write` |
| `ENOENT`, `EISDIR`, `ENOTDIR` | the source is missing or not a file; `to`'s folder is missing | the filesystem's |
| `failed` | a path is not `app:/` | `compressImage: needs app:/ paths` |
| `too-large` | the source is over 64 MiB, or its header says more than 64 Mi pixels (`exact_raster::MAX_ENCODED_BYTES`, `MAX_SOURCE_PIXELS`) | `compressImage: too-large: 9000×9000 pixels is over 67108864` |
| `undecodable` | not an image the platform decodes, or corrupt | `compressImage: undecodable: …` |
| `unfit` | no trial fits `maxBytes` within the search | `compressImage: unfit: no JPEG of app:/tmp/… fits 1000 bytes` |
| `timeout` | the search ran past 20 s. This is checked before each trial; a trial in progress finishes. | `compressImage: timeout: …` |
| `unsupported` | the host has no codec (A1.3), or the browser encodes no JPEG | `compressImage: unsupported: no JPEG encoder on this host` |

Natively the code is read from the message (`compressImage: <code>: `),
as the prelude reads `denied: ` today. The web sets `code` directly. A
Rust source gets the message. On any failure `to` is left as it was.

### A1.5 Limits

- **Input:** 64 MiB and 64 Mi source pixels, checked against the file
  size and the header before decoding.
- **Decode memory:** natively, the subsampled thumbnail and the
  `w × h` context, at most 2 × 4 × w × h bytes (w, h ≤ 8192). This does
  not grow with the source: ImageIO subsamples JPEG and HEIC while
  decoding. Add the source bytes and one encoded trial. On the web the
  browser decodes the full bitmap (64 Mi pixels at most, by the check
  above, after `createImageBitmap` reports the size), and the bitmap is
  closed in a `finally`.
- **Time:** 20 s from the start of the codec, checked before each trial.
  A storage continuation's own deadline is 30 s (`js/src/storage.rs`).
- **One at a time per module:** storage's queue serializes it. Four images
  are four calls.

### A1.6 Agent and fixtures

This is computation on the module's own files, not a device capability.
Nothing is held and there is no substitute. Under `--storage <name>` a
drive runs the real codec on macOS, iOS and the web, and gets
`unsupported` on Linux. Without a scratch store it is refused as all
storage is (`agent`). The fixture is
`scripts/fixtures/picker/oriented-gps.jpg`: a small JPEG stored 64×48
with EXIF orientation 6 (rotate 90°) and a GPS block. A correct result is
48×64 with no EXIF orientation and no GPS. A poorly compressing image
(noise) that exercises the shrinks is generated by each test, not
committed.

### A1.7 Tests

- **Ibex (patch 8):** `compress_image` with a stand-in codec. Read and
  write denial are reported before the codec runs. A source over the limit
  is `too-large`. A failing codec leaves `to` untouched. Non-`app:/` paths
  are refused, and so is a missing codec (`unsupported`). The opcode table
  includes 121.
- **`exact-data` (every platform):** the search is a pure function over an
  `encode(w, h, q) -> len` closure. It is checked against recorded trial
  sequences: fits at 51 then climbs; 51 and 26 miss and the size shrinks;
  four shrinks give `unfit`; an already-small source is not upscaled.
  The same table is checked in Bun against `storage-image.js`'s search.
- **`exact-data` (macOS, and the iOS simulator through `simctl spawn`):**
  the fixture comes back 48×64, JPEG, without orientation or GPS
  properties. Noise shrinks to fit a small budget. A transparent pixel
  becomes white. Non-image bytes are `undecodable`.
- **exact-js (macOS):** a TypeScript module calls
  `storage.fs.compressImage` on the fixture in `app:/tmp` (Hermes, the
  prelude, opcode 121, the codec) and gets the record. A missing
  `fs.write` grant gives `denied`, and a bad option a `TypeError`.
- **exact-data-host:** a Rust source's `fs.compressImage` request. On
  macOS it gets the record; elsewhere `unsupported`.
- **Web (Chrome, `js/web/tests/browser.rs`):** `createFileSystem`'s
  `compressImage` on the fixture's bytes: 48×64, `image/jpeg`, within
  budget; noise shrinks; `undecodable`; `denied`; a result `readFile`
  returns as bytes. `storage-request.js` answers the Rust request.
- **iOS:** the codec is Rust, so there is no XCTest. The macOS test
  binaries are built for `aarch64-apple-ios-sim` and run on the simulator,
  so iOS's ImageIO answers too.

### A1.8 Not in this amendment

Crop, rotate or any edit; PNG or WebP output; keeping HDR gain maps (the
picker keeps them, `Picker.swift`, and this drops them, as Bluesky's
re-encode does); video; a progress callback; cancelling a running call;
codecs on Linux, Windows and Android.

## As built (2026-09-27)

Built on web, macOS, iOS and Linux, on LLP 1069.007's holds. Where the
build departs from the design below, this section is right.

- **The tag** (D1). `input type="file"` is the kernel's `Control`
  (as a checkbox is, LLP 1069.001) with `type` `file` and two new props,
  `accept` and `multiple` (`kernel/tables/schema.json`); `multiple` is
  written bare, as HTML's boolean attribute, or `multiple=true`. Lowering
  refuses a missing or bound `accept`, `*/*`, a non-media wildcard and
  `capture` (`lower-picker-accept`, `lower-picker-capture`), and `accept`,
  `multiple`, `capture` on any other element; the bake refuses a type that
  is neither media nor in the manifest's `file_handlers`
  (`bake-picker-accept`, `contract/cli/src/picker.rs`, where `app.json`
  is read). Each refusal quotes `rules/DEFERRED.md`. A plan compiled
  without an app admits media alone.
- **The command and events** (D2). `showPicker` joins `HOST_COMMANDS`;
  `cancel` is a new `EventKind` and handler. A node without `cancel=`
  takes a cancel as nothing.
- **The value** (D3). `Picked` is a compiler-supplied shape beside
  `MarkdownSelection`: `path`, `name`, `type`, `size`, and `width`,
  `height`, `duration` as **`option<number>`** (`none` when unread), so
  a record has one shape. Write it `list<Picked>`. Hosts report kind 26,
  one tab-separated line per file (`exact_runner::Picked::payload`); the
  runner refuses a path outside `app:/tmp/picked/` and a file list on
  anything but a file input. Names are `app:/tmp/picked/<seed>-<n>.<ext>`
  from the runner (`pickedPath`), the extension the original's (or `jpg`
  after D6).
- **The bytes** (D4, D5). Native hosts copy into the `temporary` root
  storage configures, emptied when storage is configured (after first
  pixel); a scripted drive without `--storage` copies into a directory of
  the process's own. The web stores each `File` itself as the IndexedDB
  entry's contents (`storage-fs.js` `putBlob`; `readFile` and `stat`
  answer from it) when the page has a store, and keeps it in memory for
  previews either way; `app:/tmp/picked/` is emptied at the page's first
  pick, not at load, so that nothing loads before first pixel. The
  browser stores a `File` put into IndexedDB as a blob of its own: the
  pick is never read into memory, but it is copied by the browser.
- **Formats** (D6). Safari's rule is `delivered_type` in the runner and
  `Picker.swift` on Apple: a HEIC/HEIF photo under an `accept` that names
  images but not HEIC becomes a JPEG (ImageIO, quality 0.9, orientation
  applied, no metadata copied). iOS asks PHPicker for `.compatible` video
  unless `accept` has `video/*`; an explicit HEVC-to-H.264 export on macOS
  and for the agent's files is **not built**. Linux has no HEIC decoder
  and refuses (`picker: refused: image/heic to JPEG is unavailable on
  Linux`, then `cancel`).
- **Previews** (D7): `image` only. Apple resolves `app:/` through the
  roots the library names at boot (`appRoots`) and with each picked path
  (`AppFiles`, `RasterInput.open`); Linux through the roots, known at boot
  (`host/linux/src/picker.rs`); both web hosts through an object URL for a
  file this page picked or, else, the file store's entry (`picker-glue.js`
  `appURL`; on the JS target symbols.js sets it, a literal source arriving
  as `data-app-src`). So a pick kept in `app:/data` shows after a relaunch on
  every host (2026-10-04, recipes F9/F18). The store a pick fills is the one
  the data module opens: both are keyed by the page's launch URL, not the
  route's (`storage-environment.js` `launchHref`). `video` does not take an
  `app:/` source yet.
- **Per host** (D8). iOS: `PHPickerViewController` (no permission) for
  media, `UIDocumentPickerViewController(asCopy:)` otherwise, from the
  window's top view controller. macOS: `NSOpenPanel` as a sheet,
  `allowedContentTypes` from `accept`. Web: `HTMLInputElement.showPicker()`
  inside the dispatch; a refusal is journalled `picker: refused: <name>`
  and fires `cancel`; the element's own `change`/`cancel` report. Linux:
  `picker: refused: unavailable`, then `cancel`. No native host enforces
  activation (Q2). A visible file input presents only on the web; native
  hosts draw nothing (every consumer hides it), and a press on one on
  Linux opens its picker.
- **The substitute** (D9). Under the agent, `showPicker` holds a `pick`
  (`Runner::hold_picker`); `state.pending` shows `{id, accept,
  multiple}`; `clock settle` returns `reason: "device"` with the ticket.
  `type @N <path>…` is checked against the input before the hold is
  spent (count, and each type after D6, so a wrong answer can be
  corrected); `scripts/agent.mjs` makes the paths absolute and, on the
  web, sends the bytes, which the page turns into `File`s. The answer
  reply names the node; each host then copies, describes and fires
  `change` (or `cancel` for `tap @N cancel`). The journal says `device
  pick 7 answered: 2 items`, never a path. `--answer pick=` fixtures and
  the CDP override are not built.
- **Consumer.** Fieldnotes' Backups screen has **Import backup file…**:
  `accept="application/json"`, declared in its manifest's `file_handlers`
  (so macOS also lists it for `.json` files); the chosen file is
  confirmed, then `importNotes` reads it under a new `fs.read
  app:/tmp/picked` grant. Fixtures: `scripts/fixtures/picker/` (a HEIC,
  a PNG, a backup); the video is `apps/video-player/assets/motion.mp4`.
- **Verified by driving** a scratch plan and Fieldnotes: web, macOS, iOS
  simulator and Linux each hold on `showPicker`, return `reason: "device"`
  from `clock settle`, take `type @N` (a PNG and an MP4: sizes, 160 px
  width, the video's 10 s on the web and macOS) and `tap @N cancel` (fires
  `cancel`); a HEIC under `accept="image/jpeg,image/png"` arrives as
  `image/jpeg`, 320 px wide, on macOS and iOS; Fieldnotes imports a
  backup file on the web and macOS. The preview shows on the web and iOS;
  on macOS and Linux an `image` mounted after boot does not load under
  the agent at all (QUEUE). Not verified: a real PHPicker, document
  picker or NSOpenPanel pick, a physical phone, the web's
  `NotAllowedError` path.

## Summary

The picker was admitted on 2026-09-21 (LLP 1045 D10) and never built. The
only picker today is the macOS document panel (`DocumentsMac.swift`), which
serves `file_handlers`. A search over `host/`, `contract/lower/src`,
`runner/src` and `js/src` for `upload(`, `PHPicker`, `fileinput` and
`accept` finds no picker: the hits are a GPU texture `upload`
(`host/linux/src/gpu/images.rs:45`) and a socket `accept`
(`AgentIOS.swift:83`).

This RFC builds it with the web's spelling:

```
input type="file" accept="image/*,video/*" multiple testId="attach"
    change=attach display="none"
button press=choose aria-label="Add photo"
  image "symbol:photo"

action choose
  showPicker("attach")

action attach(files: list Picked) writes drafts
  ...
```

- **D1–D2, the tag and the command.** `input type=file` is the tag;
  `showPicker(id)` is `HTMLInputElement.showPicker()`. D10's
  `upload(id, "image")` becomes these two: the kind moves into `accept`.
- **D3, the value.** `change` carries a list of records: an
  `app:/tmp/picked/…` path, the name, the MIME type, the size and, for
  media, the pixel size and duration.
- **D4–D5, the bytes.** Native hosts copy them into `app:/tmp/picked/`
  before `change` fires; on the web the browser's `File` backs the entry.
  The runner never sees bytes.
- **D6, the formats.** iOS Safari's rule: HEIC becomes JPEG only when
  `accept` excludes it.
- **D7, previews.** `image` and `video` take an `app:/` source.
- **D9, the substitute.** A held picker is answered with `type @t <path>…`
  on every host, Linux included.

`accept` is bounded by the compiler: media types, or the types the
manifest's `file_handlers` declares (D1). `capture` is refused, so there is
no camera, and no picker takes "any file".

## Motivation

Three admitted consumers:

- **Interview (LLP 1045).** Captioned figures: pick, store or upload, then
  `format(id, figure(url))` inserts `![](url)` with the caret in the
  caption.
- **Bluesky** (`bluesky-exact2`, admitted 2026-09-27). Compose attaches up
  to four images or one video. `app.bsky.embed.images` wants each image's
  `aspectRatio` beside its blob, so D3 reports the pixel size and the app
  never decodes a file just to post it.
- **Fieldnotes' import** (LLP 1069.010 D3). A backup `.json` chosen by the
  person, copied into `app:/tmp`: the same element with `accept` from
  `file_handlers`.

`expo-image-picker` is among the most used Expo packages (LLP 1069 §2.2).

## Design

### D1 — The tag is HTML's: `input type=file` with `accept` and `multiple`

The kernel's input node gains `type=file` and two props, `accept` (the MIME
list as HTML writes it) and `multiple`. No new node type.

A visible file input presents as the platform's own button: the browser's
"Choose File" control on the web, a system button titled by `aria-label` on
Apple. Almost every app hides it and opens it from its own button (D2), as
on the web.

**`accept` may name:**

- `image/*`, `video/*`, `image/<subtype>`, `video/<subtype>`;
- a MIME type or extension that a `file_handlers` entry in `app.json`
  declares (`rules/DEFERRED.md`, widened 2026-09-27 with LLP 1069.010).

**The bake refuses**, each citing `rules/DEFERRED.md`'s sentence:

- an `accept` that is not a literal, or is missing;
- any other type, `*/*`, or an extension no `file_handlers` entry names;
- `capture`.

Widening further is a DEFERRED line and a bake change, never an attribute
value.

*Rejected:* D10's `upload(id, "image" | "video")` with no element. Its
value has no node to arrive on (`Outcome.commands` is fire-and-forget), so
it would need a "command with a reply" path nothing else uses. The element
gives the value a home and the agent a target, and matches what a web
author writes. D10's text points here.

### D2 — `showPicker(id)` opens it

`showPicker` joins `focus`, `selectText` and `blur` in `HOST_COMMANDS`
(`contract/types/src/checks.rs:682`): a command naming an element by id,
issued from an action. On the web the glue calls
`HTMLInputElement.showPicker()`.

**User activation.** Browsers allow `showPicker()` only under transient user
activation. The glue runs commands inside the input dispatch, so a
`showPicker` in a pressed action works on the web. Native hosts don't
enforce activation: a picker opens from any action, a timer or an answer
included (ruled). On the web the same `showPicker` outside a press is
refused by the browser (`NotAllowedError`), journaled as `picker: refused:
NotAllowedError`, and fires `cancel`. The authoring guide says so; nothing
in the compiler or the hosts enforces it.

A second `showPicker` while one is open does nothing and journals it.
Cancelling fires HTML's `cancel` event on the input (a new `EventKind`), so
a compose screen can clear its "choosing…" state.

### D3 — `change` carries a list of `Picked` records

| field | type | always | notes |
|---|---|---|---|
| `path` | string | yes | `app:/tmp/picked/<id>.<ext>`; `<id>` from the launch seed and a counter (LLP 1027.000), never the user's file name |
| `name` | string | yes | the original name, for display (`IMG_0412.HEIC`) |
| `type` | string | yes | the MIME type of what is at `path` (after D6) |
| `size` | number | yes | bytes at `path` |
| `width`, `height` | number | images and video | pixels, orientation applied (EXIF, or the track transform) |
| `duration` | number | video | seconds |

`Picked` is a shape the compiler supplies, as `exactViewport`'s is, so
`action attach(files: list Picked)` type-checks. Without `multiple` the list
has one element, in the order the user selected.

- **Apple.** Pixel size from the ImageIO header (no decode) or `AVAsset`'s
  track: microseconds.
- **Web.** `createImageBitmap` for images, a `<video>`'s `loadedmetadata`
  for video, then `change`.
- A file whose metadata can't be read is delivered without the size fields.
  It is not an error.

### D4 — The bytes go to `app:/tmp/picked/`, and the app decides what's next

**Native hosts** copy each picked file into `app:/tmp/picked/` before
`change` fires. The copy is required: PHPicker's `loadFileRepresentation` URL
is deleted when its callback returns, and `NSOpenPanel`'s URL is
security-scoped. A path the app holds must outlive both.

What the app does next is its own logic, through grants it already declares
(LLP 1027.001, LLP 1069.008):

- read it: `fs.read app:/tmp`;
- keep it: `fs.write app:/data`, then `rename`;
- upload it: `net.fetch <origin>`, with `readFile`'s bytes as the body.

The picker needs no grant. The user's selection is the consent, as on the
web and for PHPicker, which needs no photo-library permission and no usage
string. LLP 1069.008 D7's reach table lists "picks files (`accept`)",
derived from the tag's presence in the plan.

`app:/tmp/picked/` is emptied at launch.

*Known cost:* uploading a large video puts it all in the source's memory
(`readFile`). A streamed request body from a path belongs to LLP 1016.000's
streaming work.

### D5 — On the web the `File` backs the entry; nothing is copied

The web's `app:/tmp` lives in IndexedDB (`host/web/storage-fs.js`). Copying
a 300 MB video into it before `change` would stall the pick and double the
storage. The glue registers each `File` as a blob-backed entry at its
`app:/tmp/picked/…` path:

- `stat` answers from `File.size`;
- `readFile` answers `await file.arrayBuffer()`;
- `rename` into `app:/data` is where a real copy is written.

A `File` is structured-cloneable, so the storage worker holds it the same
way. The entries last as long as the page.

### D6 — The host delivers a type `accept` names, converting when it must

This follows iOS Safari, on every host (ruled). Given `accept="image/jpeg"`,
Safari hands a HEIC photo over as a JPEG; given `image/*`, the original.

| accept | the photo is HEIC | the video is HEVC/ProRes |
|---|---|---|
| `image/*`, `video/*` | HEIC, as is | `preferredAssetRepresentationMode = .current` |
| `image/jpeg,image/png` (no HEIC) | JPEG, quality 0.9, orientation applied, location metadata stripped | `.compatible` (H.264) |

- **macOS.** `NSOpenPanel` returns the file on disk; the same rule converts
  with ImageIO and `AVAssetExportSession`.
- **Web.** The browser has already chosen what it hands over.
- **Non-media types** (`file_handlers`) are never converted.
- **No other transforms** at pick: no resizing, compression, cropping or
  size limit. A cap is the app's decision, made with `size`. Image editing
  stays out (LLP 1045 §5). *Reopened 2026-10-08 for one step the app asks
  for after the pick:* `storage.fs.compressImage` (§Amendment A1).

### D7 — `image` and `video` take `app:/` sources

A compose screen shows the picked image before it is uploaded:

- **Apple:** the owned directory's file URL.
- **Linux:** the path.
- **Web:** a blob URL for the storage entry, revoked when the node leaves.

The read is the host's. A source outside `app:/tmp`, `app:/cache` and
`app:/data` is refused, and so is `..`.

### D8 — Per host

| host | presents | notes |
|---|---|---|
| iOS | media: `PHPickerViewController`, filter from `accept`, `selectionLimit` 1 or 0 for `multiple`; other types: `UIDocumentPickerViewController(forOpeningContentTypes:asCopy: true)` | no permission prompt, no usage string; presented from the session's view controller (LLP 1035.001) |
| macOS | `NSOpenPanel` with `allowedContentTypes` from `accept` (`UTType(mimeType:)`, `.image`, `.movie`), `allowsMultipleSelection` from `multiple` | a sheet on the window; separate from `DocumentsMac`'s `open-file` route, which stays the manifest's |
| web | the element's own `showPicker()` | Safari, Chrome and Firefox support it on file inputs |
| Linux | refused: `showPicker` journals `picker: refused: unavailable` and fires `cancel` | an XDG portal `FileChooser` when a desktop Linux host exists (ruled). The substitute (D9) still answers |

### D9 — Substitute

LLP 1069.007 D7's paragraph for this capability:

1. **Shape:** a request, command-shaped: the answer arrives as `change` (or
   `cancel`) on the input.
2. **Pending:** `showPicker` under the agent presents nothing. `state.pending`
   lists `{ticket, device: {capability: "pick", args: {id: "attach",
   accept: ["image/*", "video/*"], multiple: true}}}` (LLP 1069.007 D3).
   **Answer:** `type @t <path>…`, each a file on the driver's machine,
   copied in through D4/D5's path; the host then reads the metadata (D3),
   converts (D6) and fires `change`, so a HEIC fixture tests the JPEG
   conversion. `tap @t cancel` fires `cancel`. **Fixture:**
   `--answer pick=<path>[,<path>…]`. The answer's `delivery` is
   `substituted`.
3. **Web override:** CDP's `Page.setInterceptFileChooserDialog`, then
   `DOM.setFileInputFiles` on `Page.fileChooserOpened` (`delivery:
   "platform"`).

Every host takes it, Linux included, so a smoke drives a compose flow
headlessly. The repo carries one HEIC image and one short H.264 video at
`scripts/fixtures/picker/`.

## Consumers, as written

**Interview's figure** (LLP 1045 D10 unchanged but for the verb):

```
input type="file" accept="image/*" testId="figure-file" display="none" change=figurePicked
button press=chooseFigure aria-label="Insert image"
  image "symbol:photo"

action chooseFigure
  showPicker("figure-file")
action figurePicked(files: list Picked) writes uploading
  uploading = first(files).path     // the app's source uploads it and answers a URL
```

**Bluesky compose.** Four images, or one video. The app's TypeScript
uploads each file to `com.atproto.repo.uploadBlob` and builds the embed
with `aspectRatio: { width, height }` from the record:

```
input type="file" accept="image/jpeg,image/png,image/webp" multiple
    testId="compose-images" display="none" change=attach
```

**Fieldnotes' import** (LLP 1069.010 D3), with `file_handlers` declaring
`application/json`:

```
input type="file" accept="application/json" testId="import-file" display="none" change=importBackup
```

## Verification

- A fixture app, `apps/picker-fixture`: picks one image, many images and a
  video; previews them over `app:/tmp/picked/`; moves one into `app:/data`;
  restarts to show `tmp` emptied and `data` kept.
- Driven by `smoke.mjs` on web, macOS, iOS and Linux through D9.
- On iOS, one manual pass on a phone with a real HEIC and a Cinematic
  video, against D6's table.
- On the web, a `showPicker` from a timer is refused by the browser and
  journaled (D2); on macOS the same action opens the panel.

## Not in this RFC

- A camera and `capture` ("No camera anything").
- Any `accept` beyond media and `file_handlers` types.
- Directory picking, save panels, handles to documents edited in place
  (LLP 1069.010 D1–D2).
- Drag and drop of files onto the app; receiving shares.
- Image editing; resizing beyond §Amendment A1's `compressImage`; upload progress (the app's state).
- A streamed request body from a path (LLP 1016.000).
- The photo library as a data source (`expo-media-library`).

## Decided

1. The element plus `showPicker(id)`; LLP 1045 D10's `upload` is replaced
   (D1, D2).
2. Native hosts don't enforce user activation; the web's rule is the
   browser's and is documented (D2).
3. iOS Safari's conversion rule on every host (D6).
4. Linux refuses; only the substitute answers there (D8).
5. `accept` widens to `file_handlers` types, per `rules/DEFERRED.md`'s
   2026-09-27 widening; this element is LLP 1069.010's import (D1).
