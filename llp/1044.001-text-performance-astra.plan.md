## 1. Decision proposed to Charlie

Keep the repairs to ordinary macOS scrolling. Spend the next substantial implementation on making **cold visible work bounded**, including a single enormous paragraph. A limit on offscreen row count cannot accomplish that. Prepare expensive text away from input handling, publish a bounded visible result, and retain one coherent accepted result while the next is prepared. Remove the native view per inline run. Extend the same ownership and scheduling rules to iOS and Linux; preserve browser text semantics on the web.

This is broader than tuning the Markdown reader's pump, and narrower than moving the entire kernel to a background thread. The kernel, application state and ordered effects keep their existing owners. Text preparation is the expensive independent work. Layout publication must stop traversing unrelated live application subtrees before this architecture can serve large applications reliably.

LLP 1044 §8 is right to withdraw the claim that ordinary current macOS scrolling is generally slow. Its historical timings are not today's measurements. Its remaining concerns are real, but incomplete: fresh experiments found expensive first paint of giant paragraphs, severe inline-view expansion, browser-native reflow cliffs, app-size-dependent layout, and quadratic malformed-inline parsing. The parser remains absent from steady scrolling; it emphatically matters to opening and switching documents.

This is Charlie's requested independent draft, not an accepted implementation specification. It assigns no implementation date before he chooses a direction. The work below is ordered, names the files and acceptance experiments, and identifies the limited instrumentation approval needed. Nothing in this plan authorizes a new benchmark application, worker pool, blocking check or general scheduler.

## 4. Fresh worst cases, ranked by what the user feels

| Priority | User-visible failure | Why this order |
|---|---|---|
| 1 | Dense or giant text freezes opening/reflow; browser giant reflow also stalls. | Hundreds of milliseconds to seconds, including in quieter engine controls; changing scroll scheduling alone cannot fix it. |
| 2 | A malformed small file monopolizes parsing and delays the next file. | A 64 KiB source takes about half a second even in the quieter repeat; growth is quadratic. |
| 3 | Text updates get slower as the live application grows. | The quieter 50,000-node layout takes about 52 ms with one measurement; interaction impact depends on the actual app's layout dependencies. |
| 4 | Cold jumps and rapid coverage changes produce isolated native bursts. | Ordinary corpus landings reach 20 ms here; a dense/giant landing inherits priority 1. |
| Control | Warm ordinary reading. | Fresh in-process steps are mostly small; real delivered-frame superiority remains a separate comparison. |

### 4.1 Ordinary reading is the control, not the largest remaining defect

In `reader-corpus.out`, forward steps had median/p95/max **0.118/1.485/2.148 ms**; reverse steps **0.135/1.188/1.643 ms**. These include move, one pump and paint/flush, with 240 samples each. They support the repaired-path diagnosis. The loop runs as fast as possible; it does not reproduce display scheduling, asynchronous overscan slack or a physical trackpad.

Ten distant jumps cost **12.67 ms median, 20.33 ms maximum** for synchronous move plus paint. The nine window resizes cost **9.07/16.33 ms median/maximum**. These are new results for this fixture at load 59, not replacements for every old 30–55 ms jump. More importantly, the mechanism remains: `.now`, uncovered geometry and visible raster preparation can bypass the ration ([`PresenterMac.swift:474`](../host/apple/Sources/ExactKit/Mac/PresenterMac.swift#L474), [`:647`](../host/apple/Sources/ExactKit/Mac/PresenterMac.swift#L647)). A small typical landing does not bound the next one.

### 4.2 Highest priority: one visible paragraph can monopolize the UI

The reader window inside the native probe was actually resized nine times per file, after opening and exercising scroll/reversal/jump paths. These are single-process exploratory observations under rising load, from `reader-sizes.out`:

|---|---:|---:|---:|
| Giant paragraph, 256 KiB budget | 349.8 | 105.9 / 122.4 | 119 |
| Giant paragraph, 1 MiB | 496.1 | 492.5 / 551.5 | 119 |
| Giant paragraph, 4 MiB | 2,220.1 | 1,887.2 / 2,141.9 | 119 |
| Code block, 1 MiB | 988.0 | 422.9 / 462.2 | 120 |
| Code block, 4 MiB | 1,619.1 | 1,437.5 / 1,722.0 | 120 |

Virtualizing blocks cannot help when one block is the document. A cheap subsequent jump within its already-laid-out lines does not mean it opened or reflowed cheaply. A row-count budget admits this entire cost as “one row.” The code profile also disproves treating preformatted text as automatically inexpensive.

The isolated engine experiment explains part of the cost without any runner or native view tree. The table uses the later repeat at one-minute load 8.18→8.09 (`engine-quiet.out`, same counts/protocol); the first, busier series remains in `apple-engine.out`:

| Source budget | Cold paragraph median, ms (3) | First viewport paint median, ms (3) | Color-only paragraph median, ms (3) | New-width median, ms (18) | Warm viewport paint median, ms (30) |
|---|---:|---:|---:|---:|---:|
| 16 KiB | 1.06 | 1.56 | 0.82 | 0.39 | 0.145 |

Each engine made two `TextShape` objects and eight `layout` calls: black, colored, then six widths. Reusing line ranges is useful but does not mean “shaped and painted once.” Dirty paint calls `inkBounds()` ([`Text.swift:778`](../host/apple/Sources/ExactKit/Text.swift#L778)); its first index construction covers the paragraph. The warm viewport result is excellent and is the operation to preserve. The separate ordinary raster path excludes text taller than 4,096 points ([`TextRasterMac.swift:34`](../host/apple/Sources/ExactKit/Mac/TextRasterMac.swift#L34)), then leaves it to strips; this avoids a giant bitmap, not complete first layout/index construction.

The 4 MiB engine's residency diagnostics report estimated cold admission of **384,042,000 bytes (366 MiB)** despite the 64 MiB cold-cache target. That is **accounting, not measured RSS**. The cold counter itself exceeds the soft target; accepted/live owners and scratch also need separate accounting. The 512-entry measured-break cache also stores variable-length arrays ([`Text.swift:470`](../host/apple/Sources/ExactKit/Text.swift#L470)). Counting entries cannot establish a byte bound for giant paragraphs.

### 4.3 Equally urgent: rich inline text defeats view virtualization

Each dense fixture is one paragraph made from repetitions of bold, plain, italic, code and linked text. The parser produces eight inline runs per repetition. Native mounting follows those runs even though the paragraph is one Taffy text leaf ([`app.contract:191`](../apps/markdown/app.contract#L191), unconditional native creation at [`PresenterMac.swift:812`](../host/apple/Sources/ExactKit/Mac/PresenterMac.swift#L812) and [`PresenterIOS.swift:514`](../host/apple/Sources/ExactKit/IOS/PresenterIOS.swift#L514)). From `reader-density.out`:

| Repetitions | Native views after open | Open/display, ms (one) | Resize median / maximum, ms (nine) |
|---|---:|---:|---:|
| 16 | 245 | 57.1 | 15.7 / 16.9 |
| 64 | 629 | 53.3 | 16.6 / 35.9 |

### 4.4 The browser has a giant-text cliff of its own

The corrected web stress run retained bounded window nodes for many small blocks and tables, but a 1 MiB paragraph's width-control acknowledgment reached a **1,348 ms median** (six samples). This includes agent overhead. Direct forced-layout trials at 600/1,160-point paragraph widths took roughly **1.4/0.84 seconds** at 1 MiB; `web-layout.out` records twelve alternating widths and exact text length.

A control copied the paragraph's computed font/whitespace styles into a **single bare DOM div**, removed the application, and used the same source. Its six 1 MiB width changes still took roughly **1.39/0.79 seconds** (`web-bare.out`). This control ran at much higher load, so it is not a precise paired ratio. It nevertheless rules out blaming all the large cost on Exact's list feedback: browser text layout alone can reproduce the scale of the stall.

Both 4 MiB browser attempts exceeded the carrier's 15-second command deadline before a valid completed reflow sample. They are recorded failures, **not 15-second measured layout times**. Browser-native scrolling can continue independently of JS in some circumstances; that does not make a giant synchronous reflow, input dispatch or first content free. Moving Markdown parsing to a worker is necessary but cannot solve this case by itself.

### 4.5 Large applications and many small blocks expose different costs

A root with 100, 1,000, 10,000 and 50,000 live text siblings was laid out, then its first text changed twenty times. Exactly **one host measure callback** occurred per mutation, and the returned geometry-change list was empty. Full layout medians were **0.156, 1.765, 38.583 and 194.338 ms** (`kernel.out`; repetition retained in `kernel-repeat.out`). The experiment measures Taffy plus kernel publication, not the proportion attributable to either. It is a counterexample to “the memo hit makes app-size irrelevant.” These siblings are ordinary block flow, not already-isolated layout boundaries. A third run at load 8.55→8.18 still cost **0.102/0.940/11.263/51.660 ms** (`kernel-quiet.out`, twenty each, still one callback). Contention magnifies the cost; it does not create the app-size dependency.

The reader behaves better with many small blocks: fixtures with 100, 1,000, 10,000 and 50,000 heading/paragraph pairs all mounted **191 views**. Opening the latter two took **198/640 ms**, versus **81/36 ms** for the smaller two (`reader-sizes.out`, one each, not a monotonic quiet benchmark). The viewport stays bounded; complete parsing, Value construction, keys and initial height/index ownership still grow with the document. The existing parser tool separates parse from full Value conversion in `parse.out`.

On width change the legacy window allocates a fresh N-element estimated-height array ([`window.rs:215`](../runner/src/instance/window.rs#L215)). Replacing data builds a `BTreeMap` of every key ([`:272`](../runner/src/instance/window.rs#L272)), so this portion is O(N log N), followed by O(N) height/anchor work. These operations do not become O(visible rows) merely because the host mounts few views. Native document settlement also calls `siblings(path)` after the worker returns, scanning and sorting directory entries before taking 500 ([`data/src/lib.rs:58`](../apps/markdown/data/src/lib.rs#L58), [`:112`](../apps/markdown/data/src/lib.rs#L112)); that path deserves relocation, not a claim that all I/O is already off the UI thread.

### 4.6 A small malformed document can delay the whole file-opening lane

The actual inline parser, compiled unmodified into an optimized probe, preserved every input byte for the malformed cases. At 4/8/16/32/64 KiB, median plain-text times were **0.038/0.066/0.133/0.268/0.529 ms**. Repeated unmatched `[x` took **6.62/26.41/198.30/768.95/3,572.04 ms**; repeated `x<` took **2.47/9.85/40.31/166.18/734.98 ms**, three samples each (`inline.out`). The second run reproduced the growth (`inline-repeat.out`). At load 8.55 the third run still took **1.55/6.09/28.47/111.82/447.60 ms** for unmatched brackets and **1.58/6.14/27.03/107.87/465.96 ms** for unmatched autolinks (`inline-quiet.out`, three each). Do not extrapolate an unmeasured 4 MiB duration from these numbers.

The cause is explicit: each unmatched opener searches the remaining suffix ([`inline.rs:219`](../apps/markdown/parse/src/inline.rs#L219), [`:241`](../apps/markdown/parse/src/inline.rs#L241), [`:353`](../apps/markdown/parse/src/inline.rs#L353)). The earlier UTF-8/plain-rest repair did not remove these O(N²) cases. Parsing on a worker protects immediate scrolling, but a stale parse still occupies the lane and delays the latest requested document. Cancellation and linear scanning are different requirements; both are needed.

A disposable indexed-delimiter prototype was also tried, only in `target/textperf-astra/inline-variant.rs`. It preserved the baseline runs on **10,000 seeded 128-character ASCII cases, 4,000 corpus lines and three 64 KiB literal cases** ([comparison record](../target/textperf-astra/inline-variant-check.txt)). It precomputes matching delimiter positions and next-`>` lookup rather than repeating suffix searches. It is not a finished parser fix: its matched-pair sorting is O(P log P), recursive emphasis/backtick behavior is unchanged, and these samples do not prove all grammar cases. At load 8.5, its 64 KiB unmatched-bracket/autolink medians were **0.417/0.259 ms**, three samples each ([inline-variant.out](../target/textperf-astra/inline-variant.out)). Plain 64 KiB text took **0.593 ms**, versus 0.162 ms in the earlier quiet baseline; this was not a paired trial and the extra unconditional indexing needs attention. The final implementation must meet slice A's linear-work requirement without paying for unused delimiter indexes on plain text, rather than copy this prototype wholesale.

The simulator held 60–151 nodes across its tested profiles; both sizes of each profile had the same count. Type echoes succeeded, but one mixed-case acknowledgment exceeded two seconds amid load above 500. That is a reason to retain the outlier, not evidence of a two-second physical-iPhone typing defect. Its shared-collection path also does not clear the legacy UIKit scheduler issue found in source.

Real scrollbar dragging was also tried. The first two driver versions selected text or failed to move the scrollbar; their apparent durations are excluded. No uninterrupted visible-coverage movie, physical trackpad gesture, IME composition over a large page, VoiceOver traversal, actual Linux display, or physical iPhone result is claimed here. Whole-source editor replacement, table extremes beyond the tested 256 columns, cancellation during a malformed parse, and all retained-state memory owners need the acceptance work below. The plan does not substitute a fast scroll-offset acknowledgment for correct text reaching the display.

## 5. The desired architecture

### 5.1 A paragraph is prepared content, not a subtree of drawing widgets

Keep the Contract and CSS model. A text node still has styled inline descendants, exact source ranges, links, selectable text and accessibility semantics. On native hosts those descendants become paragraph metadata rather than individual `NSView`/`UIView` objects. One paragraph presenter owns the visible text surface and exposes virtual accessibility elements where needed. Interactive embedded controls remain actual controls; this optimization must not erase focus, pointer targeting or authored inline box behavior.

Use a stable source/metric identity containing content revision, metric-affecting styles, font-catalog incarnation, locale/direction and whitespace/wrapping policy. Width and exclusions identify a layout result, not the source. Color, underline and link destination belong to paint/interaction revisions unless they genuinely change metrics. Pixel scale identifies raster output. A reused numeric node ID or a hash collision is never sufficient identity.

Resolve source encoding and run boundaries once per immutable source revision. Keep the existing payload-free `ParagraphStamp` fast path; a warm measurement must not flatten runs, decode strings, hash all bytes or rebuild attributed text. Preserve min-content, max-content and baseline semantics rather than routing every offer through a definite-width paragraph. Font changes invalidate the appropriate namespace.

Native measurement and paint consume the same prepared metric geometry. A color-only change must not repeat line breaking or full glyph shaping. CoreText objects stay confined to their owning executor; the UI receives immutable line ranges, extents, source/caret mappings and ready viewport pixels. If CoreText cannot supply color-independent reusable glyph output for a case, measure and name the remaining paint-only work instead of claiming “one shape.” Linux already separates shaped source from width-specific layout ([`text.rs:535`](../host/linux/src/text.rs#L535)); retain that useful separation.

### 5.2 Ownership and scheduling

| Owner | Work it owns | Work it must never inherit accidentally |
|---|---|---|
| Platform scroll/input system | Gesture recognition, scrolling existing content, native editing/IME, focus and accessibility dispatch. | Waiting for a new paragraph's full source to shape merely because its row just became visible. |
| UI executor | Application commits, serial kernel layout, small measured publications, placement of prepared surfaces, coherent hit/selection metadata. | Full giant-paragraph shaping, full glyph-bound indexing, directory enumeration, or unbounded row mounting in a scroll callback. |
| Existing bounded native text service | Source preparation, expensive width results, visible glyph/caret/ink extraction and raster work, with cancellation checkpoints. | A second application-state graph, arbitrary app callbacks, mutable CoreText shared with the UI, or an accumulating resize backlog. |
| Data worker | File I/O, parsing, source indexing and document answer preparation. | UI-owned mount/selection state; stale work consuming an unlimited queue. |
| Browser | Ordinary DOM/CSS text layout, selection and painting; compositor scroll where available. | An assumption that ordinary DOM APIs make arbitrary giant paragraphs bounded. |

Start from the existing region machinery, not a fresh scheduler. [`RegionService.swift:1`](../host/apple/Sources/ExactKit/RegionService.swift#L1) already has one active job, one replaceable latest request and one completion; its ownership and abandonment rules are valuable. The separate ordinary rasterizer currently permits two jobs with no backlog ([`TextRasterMac.swift:51`](../host/apple/Sources/ExactKit/Mac/TextRasterMac.swift#L51)). Converge their text ownership and byte accounting; do not add another pool beside them.

The existing region path is not the answer already shipped: its source capture happens through a registered native owner, its macOS surface is separate, and flowed text explicitly falls back to ordinary synchronous layout ([`content_region/host.rs:117`](../host/apple/src/content_region/host.rs#L117)). Its worker metrics still scan every authored run for each glyph run ([`RegionWorkerLayout.swift:111`](../host/apple/Sources/ExactKit/RegionWorkerLayout.swift#L111)). Extending it needs rich-inline parity and indexed run lookup, not simply turning its switch on.

A large new source or width becomes a candidate identified by document, source, font, width, appearance and request generations. Accept geometry, pixels and hit metadata together. On reversal, navigation or resize, replace obsolete pending presentation work; do not drop ordered application effects or keystrokes. Cancellation releases bytes when the old worker actually stops, not when its request becomes unwanted. One active plus latest is an outstanding-work bound, not a latency guarantee; checkpoint spacing and the largest uncancellable platform call must also be measured.

### 5.3 Bound the unit of visible work

Use the platform's scroll position as demand. Schedule the currently visible interval first, then a directional overscan band, then retirement. An admission limit counts estimated work and bytes as well as rows. Measure actual elapsed time between small operations, but do not mistake a timer around one giant synchronous operation for preemption. No visible-row exemption may invoke unbounded shaping, mounting or paint.

For ordinary warmed rows, preserve today's immediate coverage. For a cold distant jump, publish a lightweight landing region and prepare its visible text before overscan. Keep the logical scroll extent and anchor identity while measured heights refine it. A pending region must be explicit: do not display old text under a new file title, stretch old pixels to a new width, or permit clicks using mismatched hit geometry. The desired ordinary-use bar permits no visible placeholder; the overload bar permits a clearly pending landing interval with a strict time-to-correct-content bound (§6).

A giant paragraph needs a viewport-sized presentation unit even when its semantic paragraph is indivisible. Full Unicode/bidi/source preparation may remain O(bytes); line-offset metadata may remain O(lines). Materialized glyph runs, ink bounds, caret detail and pixels should cover the viewport plus bounded overscan, rather than the complete paragraph before first paint. Very long logical lines require horizontal viewport culling too. Full-document copy reads source/ranges, not mounted views.

Keep one accepted width and one candidate per active paragraph/region; do not retain every width traversed during a drag. Compact scalar summaries can have a separately charged small cache. Charge measured-break arrays, attributed source copies, active worker scratch, queued completion, GPU surfaces and deferred destruction to named owners. Retire cold history before reducing useful visible coverage. Keep all source bytes needed for correctness; never silently truncate a file to satisfy a memory graph.

### 5.4 Make layout and collection publication local

The synchronous `TextMeasurer` seam currently returns complete metrics. It must not silently return guessed “exact” metrics when an expensive artifact is missing. In collections, the existing provisional row-height protocol can represent a pending row; replace it with accepted geometry only when the text result arrives. This is the first implementation scope because it already has a legitimate estimate/anchor contract.

For ordinary non-collection text, add an explicit pending text result only with a serial, resumable layout/publication boundary. The kernel remains UI-owned. A pending leaf blocks the dependent ancestor geometry from publication; already-independent fixed-box controls can still echo input. Keep accepted host frames and their revision until a complete replacement is ready. Do not copy the entire application tree, publish half a dependent layout, or move arbitrary Taffy computation to a worker. If the boundary cannot prove independence, keep it coarse and expose pending state rather than fabricating correct geometry. This extension is a prerequisite to claiming the solution serves every app, not an implicit property of the existing callback.

Introduce serial dirty-subtree publication and narrowly proven layout boundaries for definite, contained geometry. Cache hits in Taffy are not enough while the kernel and native emitter still walk every live descendant. Ancestor baselines, intrinsic sizing, overflow, percentages and shape exclusions can cross a proposed boundary; those cases require propagation. A whole-document width change can still invalidate every paragraph, but only the visible presentation must settle synchronously.

Use width-generation invalidation for measured heights so a drag does not zero N entries each sample. Preserve an anchor by stable key and inset, with explicit deletion fallback. Within a giant paragraph, anchor by source offset plus baseline inset, then map that source position into the accepted new-width lines; retaining the old pixel offset alone does not retain the same words. Initial key/index construction and truly arbitrary reorders still scan the input. Converge the reader and shared collection implementation only after selection, full copy, focus pins and nested scrolling pass; then delete the old protocol. There should be one way to ration a viewport, not a third text-specific list engine.

### 5.5 The web work is a correctness gate, not a promised free speedup

Keep normal text in DOM/CSS. Batch geometry reads separately from writes and coalesce collection feedback; the legacy path currently reads row rectangles then dispatches a mutating list answer in a microtask ([`glue.js:209`](../host/web/glue.js#L209)). That is worthwhile cleanup, but the bare-div control shows it cannot remove the giant-paragraph cliff.

The proposed large-paragraph path is source-backed, visible line fragments with a complete paragraph preparation context and explicit source-range mapping, extending the existing textflow/fragment machinery. Shape with the host's font system; preserve bidi paragraph context, ligatures, combining marks, fallback, whitespace, break opportunities and overhang. Never split raw text every K bytes and call the fragments equivalent paragraphs. Browser selection, find, copy, accessibility and link hit testing are part of the product, not optional polish.

There is a real unresolved implementation question here: browser APIs may not provide reusable shaping/line geometry that both matches DOM/CSS and avoids an unbounded full-paragraph layout. [`textflow/src/walker.rs:98`](../textflow/src/walker.rs#L98) documents its approximate additive advances at emergency cuts; the Pretext-style speed result is not proof of general browser shaping equivalence. The bounded web experiment in slice D must answer this before a general replacement is selected. If it fails, retain CSS correctness, report the remaining web pathological case, and ask Charlie to choose the narrower guarantee or a specifically justified rendering scope expansion. Debouncing reflow alone does not meet the stated goal.

### 6.2 Proposed numerical budgets and their trade

These are **targets for approval/implementation**, not measurements achieved here. Native main-thread work gets only part of a refresh interval; platform input, compositing and other app work need the rest. Existing repository cold-start/dev-loop budgets remain binding. Work rejected from this interval becomes bounded pending work, not invisible debt.

| Operation | Completion bar | Instrument and validity guard |
|---|---|---|
| Warm ordinary scroll/reversal | p99 text/list UI work ≤2 ms, no individual owned span >4 ms; ≤1 hitch ms/s over a 60-second valid run; no stall >2 refresh intervals. | Existing presenter signposts plus Animation Hitches, paired with actual presented-frame cadence ≥98% of requested display cadence during motion. |
| Input echo while document work is pending | p99 input-to-first-correct-visible echo ≤2 refresh intervals: 33.3 ms at 60 Hz, 16.7 ms at 120 Hz. | Window-server frame timestamps on Mac; device presentation tooling on phone/web. Agent acknowledgment alone cannot pass. |
| Ordinary cold jump/file switch | Correct target viewport p95 ≤100 ms; no event-handling span >4 ms. | Input timestamp to revision-identified correct viewport pixels, with source/anchor and blank-band checks. |
| Admitted 4 MiB giant text or dense/table overload | Pending feedback within one refresh; first correct viewport p95 ≤500 ms, stable-width complete geometry ≤2 s; other controls continue meeting the input bar. | Separate first-content and full-layout intervals; record cancellation and largest atomic UI span. No pretending a pending surface is content. |
| Resize | Shell follows every delivered size within two refreshes; ordinary final correct text ≤100 ms after last size, overload ≤500 ms; no old-width hit regions. | Real border drag plus deterministic width sequence, presentation/revision record and input during resize. |
| Large application | Fixed-box input/update p95 ≤2 ms at 100, 1,000, 10,000 and 50,000 unrelated live nodes; no more than 25% increase from 1,000 to 50,000 after constant overhead. | Existing kernel/host timings, visited-node/host-measure counts, and presented input echo. Coupled whole-flow changes are reported separately. |
| Inline presentation | Mount O(visible paragraph surfaces + real controls), zero native view per purely textual inline run; no shape/rebreak on color-only changes. | Deterministic view counts, source/metric identities, shape/break counters and existing selection/link tests. |
| Memory | One active/latest/completion bound; one accepted/candidate width; viewport glyph/pixel ownership independent of document length; no retained growth after ten identical passes beyond 5% or 8 MiB, whichever is larger. | Explicit owned-byte counters plus `vmmap` physical footprint/native device tools; settled and peak reported separately. |

Use the existing 64 MiB cold text-cache target as the initial eviction budget, charging break arrays and all cold text owners to it. It is not the process-RSS limit. Propose a separate **128 MiB per-session text working-set admission budget**, including in-flight geometry, viewport pixels and scratch estimates, beyond immutable source/index ownership; report those O(N) bytes separately. Oversized full glyph arrays must become viewport artifacts, not exemptions. If a platform's unavoidable scratch exceeds this budget, measure it and bring the explicit trade to Charlie before raising the budget. Spend less on cold width history and overscan first, not on correctness or input responsiveness.

### 6.3 What remains O(N), intentionally

Reading and retaining N source bytes, complete parsing, Unicode/bidi preparation, building an initial source/key index, whole-document search/copy, and a genuine replacement of all source remain O(N). Initial sorted key/directory work is currently O(N log N); move it off input handling and reduce needless sorting, but name it until removed. Full width-dependent paragraph geometry may remain O(N) in a worker. A semantically coupled whole-flow layout can affect all following siblings. None of those facts permits O(N) work on every scroll tick, scalar-cache hit, isolated input echo, color update, or intermediate width publication.

The absence of pathologies means no accidental superlinear parser/run-lookup behavior, no unbounded queue/history, and no source-sized indivisible UI operation within the admitted input domain. It does not mean opening an arbitrarily large file takes constant time. The reader's current 4 MiB admission remains explicit; general text applications need the same pending/backpressure behavior rather than borrowing that app-specific cap as a framework guarantee.
