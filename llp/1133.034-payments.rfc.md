## Summary

`@exact/payments` takes a payment for physical goods and services with
the device's wallet: Apple Pay on iOS and macOS, Google Pay on Android,
and whichever of the two the browser offers on the web. Tier 1 is the
W3C Payment Request API's: its method data, details and options, its
events, `show()`, `complete()` and `retry()`:

```
use showPaymentRequest, paymentRequestStatus, PaymentResult, PaymentRequestStatus
  from "@exact/payments"

resource checkout = printCheckout(size) as shape Checkout else empty()
resource wallet = paymentRequestStatus(methodData=checkout.methodData)
  as shape PaymentRequestStatus else empty()
mutation ordered as shape PaymentResult then confirmed

action orderPrint
  send ordered = showPaymentRequest(methodData=checkout.methodData,
    details=checkout.details, options=checkout.options,
    onmerchantvalidation="validateMerchant", onshippingaddresschange="quoteShipping",
    onshippingoptionchange="quoteShipping", onpaymentauthorized="placeOrder")

// in the view, shown while wallet.canMakePayment:
exact-payment-button type="order" checkout=checkout press=orderPrint testId="order-print"
```

```ts
// app.ts: the app's own data code, which the sheet calls back. The
// checkout's `details.id` is the server's checkout, made with its prices.
const post = async (path: string, body: unknown) =>
  (await fetch(`${api}${path}`, { method: "POST", body: JSON.stringify(body) })).json();

export const tools = {
  async validateMerchant(e: MerchantValidationEvent) {     // Safari's Apple Pay
    return post(`/apple-pay/session`, { url: e.validationURL });
  },
  async quoteShipping(e: PaymentRequestUpdateEvent) {      // a PaymentDetailsUpdate
    return post(`/checkouts/${e.requestId}/quote`,
      { address: e.shippingAddress, option: e.shippingOption });
  },
  async placeOrder(response: PaymentResponse) {
    const res = await fetch(`${api}/checkouts/${response.requestId}/pay`, { method: "POST",
      body: JSON.stringify({ method: response.methodName, payment: response.details,
        ship: response.shippingAddress, option: response.shippingOption,
        email: response.payerEmail }) });
    if (res.status === 422) return { retry: (await res.json()).errors };  // retry()
    if (!res.ok) return { result: "fail" };                              // complete("fail")
    const checkout = await res.json();          // paid, declined or indeterminate (D6)
    if (checkout.state === "indeterminate") return { result: "unknown" }; // complete("unknown")
    if (checkout.state !== "paid") return { result: "fail" };
    return { result: "success", data: { orderId: checkout.orderId } };
  },
};
```

Five decisions carry the module:

- **The sheet asks the app while it is up.** A shipping address chosen
  in the sheet needs the app's price for it, and an authorized payment
  needs the app's server to charge it, both before the sheet closes.
  Each is a handler the app names, a function in its data module's
  `tools`, which the module calls through the runner's `invoke` and
  answers the sheet with (D5).
- **The payment token reaches data code alone.** The token is what the
  merchant's server charges, so it never enters Contract state, the
  journal, `pending` or `state.extensions`: only the `onpaymentauthorized`
  handler receives it, as only data code receives a passkey response
  (D7).
- **Authorization is the point of no return.** Until the person
  authorizes, the request lives as its call does; once the handler that
  charges has been called, it runs to its answer and the sheet shows that
  answer, whatever happens to the call. The app's server captures at
  most one payment per checkout, whose id every handler receives, and is
  the record of what was paid (D6).
- **The method data is the platform's own words.** Payment Request
  already gives each payment method its own dictionaries: Apple's
  `ApplePayRequest` and `ApplePayModifier`, and Google's
  `PaymentDataRequest`. Each target pays with the method it has, and
  those dictionaries are tier 2 (D10).
- **What may be sold this way is the stores' rule.** Apple and Google
  require their in-app purchase systems for digital goods and require
  something else, such as Apple Pay or Google Pay, for physical goods
  and services. Digital goods are `@exact/purchases` (LLP 1133.015) (D12).

Tier 2 also reaches Wallet passes: adding a signed pass to Apple Wallet
and saving one to Google Wallet. Tier 3 hands the app's Swift the
`PKPaymentRequest` before it is presented, and its Kotlin the
`PaymentDataRequest`'s JSON before `loadPaymentData`.

The consumer is the photo editor (§10): Order a Print sends the edited
photo to a print lab, a physical good, through a fixture print server
that records orders and never charges a card.

## 0. What is new here

The modules before this one either answer a value the device has, or
show a sheet whose answer the module returns (a passkey, a store
purchase). A payment sheet differs in three ways, and four more things
follow from what is being sold:

1. **A sheet that needs the app's answers while it is up.** Apple's
   delegate is asked for a new total when the person picks an address or
   a shipping method, and for the authorization's result after they
   authorize; it "automatically waits for its delegate to finish
   responding to one method before it calls other delegate methods"
   ([`PKPaymentAuthorizationControllerDelegate`](https://developer.apple.com/documentation/passkit/pkpaymentauthorizationcontrollerdelegate)).
   Google calls a service in the app, which "must call
   `onCompleteListener.complete(...)` within 30 seconds"
   ([client reference](https://developers.google.com/pay/api/android/reference/client)).
   The web fires `shippingaddresschange` and asks for `updateWith()`.
   No module so far is called back while its own call is pending (D5).
2. **A credential with a few minutes' life.** The token is encrypted for
   the merchant, and the merchant's server can charge it once; Apple
   tells the server to treat a token whose signing time is more than five
   minutes from the transaction as a possible replay
   ([token format](https://developer.apple.com/documentation/passkit/payment-token-format-reference)).
   It belongs below the data seam (LLP 1018 D5), as a passkey response
   and an ID token do (D7).
3. **A call that must outlive its caller.** Once the server may have
   charged, cancelling the call would leave the person's money taken and
   the sheet saying it failed (D6).
4. **The web needs the press.** Browsers reject `show()` without
   transient activation ([§`show()`](https://www.w3.org/TR/payment-request/),
   a MAY that Chromium and WebKit apply), where passkeys needed none
   (LLP 1133.011 D9). So the payment button shows the sheet in its own
   click handler, as sign-in's button opens its window (LLP 1133.014 D5),
   and the call adopts it (D8).
5. **What may be sold is decided by the stores** (D12), and nothing on
   the device can tell a print from a subscription.
6. **Two wallets, one tier 1.** No platform has both Apple Pay and Google
   Pay natively; the web has whichever its browser has. Payment Request's
   method data names both, and each target takes its own (D1, D10).
7. **Real money in the agent's hands.** A drive must never charge a card.
   Under the agent no wallet is reached; Google Pay runs in its `TEST`
   environment in every build that is not a production bake, and nothing
   the app writes changes that; Apple Pay is driven only with Apple's
   sandbox; and the fixture server never sends a token to a processor
   (§9).

## 2. Tier 1

### D1 — Payment Request's names

The W3C API is one object: `new PaymentRequest(methodData, details,
options)`, then `show()`, which answers a `PaymentResponse` that the
page finishes with `complete(result)` or sends back with
`retry(errors)`; while the sheet is up, `shippingaddresschange`,
`shippingoptionchange` and `paymentmethodchange` fire, each answered by
`updateWith(detailsUpdate)`; `canMakePayment()` says whether the page
may offer it ([Payment Request](https://www.w3.org/TR/payment-request/)).
`@exact/payments` declares:

| Name | Kind | Meaning | Contract | Data code |
|---|---|---|---|---|
| `showPaymentRequest(methodData, details, options, on…)` | send; a request (the wallet's sheet) | the constructor's arguments and `show()` in one call, with the app's handlers for the sheet's events (D5) | `send p = showPaymentRequest(…)` | `await showPaymentRequest({ … })` |
| `paymentRequestStatus(methodData)` | live source; a fact; `sync` | `"PaymentRequest" in window` and `canMakePayment()` for these methods on this target, and which method it would use | `resource s = paymentRequestStatus(…)` | `await paymentRequestStatus({ methodData })` |
| `exact-payment-button` | view | the wallet's own button; its `press` is an event the app's action answers by calling `showPaymentRequest`; its `checkout` (`{methodData, details, options}`) is what the web shows at the press (D8) | `exact-payment-button type="buy" checkout=c press=pay` | — |

**The handlers** are keyword arguments naming functions in the app's data
module's `tools` (D5). Each is called with the request's `requestId`,
`details.id`, so a handler knows which checkout it answers for:

| Handler | The web's event | Called with | Answers |
|---|---|---|---|
| `onshippingaddresschange` | `shippingaddresschange` | `{requestId, shippingAddress, shippingOption, methodName}`, the address redacted (D2) | a `PaymentDetailsUpdate` |
| `onshippingoptionchange` | `shippingoptionchange` | the same, with the chosen option's `id` | a `PaymentDetailsUpdate` |
| `onpaymentmethodchange` | `paymentmethodchange` | `{requestId, methodName, methodDetails}` (Apple's card type, or a coupon code, D10) | a `PaymentDetailsUpdate` |
| `onmerchantvalidation` | `merchantvalidation` (WebKit's) | `{requestId, methodName, validationURL}` | `{merchantSession}`, the opaque object Apple's server returned (D8) |
| `onpaymentauthorized` (required) | none: Apple Pay JS's `onpaymentauthorized` and Google Pay's `onPaymentAuthorized` | the `PaymentResponse`, with `details` | `{result, data}` for `complete(result)`, or `{retry: PaymentValidationErrors}` for `retry(errors)` |

**Values,** by the W3C's dictionaries, every amount a
`PaymentCurrencyAmount` (`currency`, an ISO 4217 code, and `value`, a
decimal string; never a float):

| Shape | Fields |
|---|---|
| `PaymentMethodData` | `supportedMethods` (`https://apple.com/apple-pay` or `https://google.com/pay`); `data`, `json`: the method's own request (D10) |
| `PaymentDetailsInit` | `id` (the request's id: the app's checkout id, else one the module makes); `total` (`PaymentItem`: `label`, `amount`, `pending`); `displayItems`; `shippingOptions` (`id`, `label`, `amount`, `selected`); `modifiers` (`supportedMethods`, `total`, `additionalDisplayItems`, `data`: the method's modifier, D10) |
| `PaymentDetailsUpdate` | as `PaymentDetailsInit` without `id`, with `error`, `shippingAddressErrors`, `payerErrors`, `paymentMethodErrors` |
| `PaymentOptions` | `requestPayerName`, `requestPayerEmail`, `requestPayerPhone`, `requestShipping`, `requestBillingAddress`; `shippingType` (`shipping`, `delivery`, `pickup`) |
| `ContactAddress` | `country`, `addressLine`, `region`, `city`, `dependentLocality`, `postalCode`, `sortingCode`, `organization`, `recipient`, `phone` |
| `PaymentResponse` (handler only) | `requestId`, `methodName`, `details` (`json`, the method's payment, D7), `shippingAddress`, `shippingOption`, `payerName`, `payerEmail`, `payerPhone` |
| `PaymentResult` (the send's answer) | `PaymentResponse`'s fields without `details`; `result` (`success`, `fail`, `unknown`: the last `PaymentComplete` the handler chose); `message` (`option<string>`: `authorize-timeout`, D6); `data` (`option<json>`, what the handler gave for the screen); `apple`, `android` (D10) |
| `PaymentRequestStatus` | `available`; `canMakePayment`; `hasEnrolledInstrument` (`option<bool>`); `methodName` (`option<string>`, the method this target would use) |

**Errors.** In Contract, `failure(…).code`; in TypeScript and Rust a
rejection `{code, message}` (LLP 1133.002 D1). The W3C's names, with the
platforms' cases:

| Code | When | Apple | Android |
|---|---|---|---|
| `AbortError` | the person closed the sheet before any result (D6) | `paymentAuthorizationControllerDidFinish` with no authorization | `CommonStatusCodes.CANCELED` |
| `NotSupportedError` | no method in `methodData` that this target has; the target has no implementation; `available` false | `canMakePayments()` false | `isReadyToPay` false; Play services missing |
| `NotAllowedError` | a tool, wake or headless origin (`person-required`, D14); the app in the background; no window of the session on screen or in front (D15); on the web, no request shown by this press to adopt (`activation`) or another sheet up (`busy`), D8 | the same | the same |
| `SecurityError` | an Apple Pay `merchantIdentifier` no `payment.apple-pay` line grants (D13); the web's own refusals | — | — |
| `TypeError`, `RangeError` | a malformed amount, currency or method, checked at admission as the W3C constructor checks them | — | — |
| `OperationError` | the wallet failed; the platform's code in `apple.code`, `android.code` | `present` answered false | `loadPaymentData` failed, with its `statusCode` |

A declined card is not an error: the handler answers `{result: "fail"}`,
the sheet shows the failure, and the send answers `PaymentResult` with
`result` `fail`, which the app's screen reads.

### D2 — What the sheet gives, and when

The person's address and contact reach the app in two steps, by the
W3C's rule and both platforms' alike:

- **While the sheet is up,** a shipping address is redacted: the W3C
  removes `organization`, `phone`, `recipient` and `addressLine` before
  `shippingaddresschange`; Apple gives "only the card type and a redacted
  shipping address" before authorization ([HIG](https://developer.apple.com/design/human-interface-guidelines/apple-pay));
  Google's `IntermediatePaymentData` carries the address's country,
  postal code, administrative area and locality. The handler receives
  what its platform gives, in `ContactAddress`'s fields, and absent
  fields are `none`.
- **At authorization,** the full shipping address, the payer's name,
  email and phone that the options requested, and the payment.

So a handler that quotes shipping works from a region and a postal code,
and only `onpaymentauthorized` sees a street.

### D3 — Declared deviations

Each because the web's form does not fit a module call that answers:

- **No `PaymentRequest` object.** `showPaymentRequest` takes the
  constructor's three arguments and shows the sheet; the name says both,
  since a bare `show` would collide with an app's own action names (the
  photo editor has one). The request's `id` is in `details` as the W3C's.
  On the web the button constructs and shows the request at the press,
  from its `checkout`, and the call adopts it (D8).
- **Events are named handlers, not listeners.** A Contract value cannot
  be a function, and a call into data code needs a name the runner can
  admit (D5). The handler keywords take the W3C's `on…` attribute names.
- **`onpaymentauthorized` replaces `complete()` and `retry()` on the
  response.** The W3C resolves `show()` and lets the page finish the
  response later. Here the handler that receives the response answers
  how to finish it: `{result}` is `complete(result)`, with `data`, the
  W3C's `PaymentCompleteDetails.data`; `{retry}` is `retry(errors)`, and
  the handler is called again when the person authorizes again. Three
  reasons: the token stays in data code while the sheet may be started
  from Contract (D7, D8); Google gives the authorization's outcome only
  through `onPaymentAuthorized` and Apple only through its delegate's
  completion; and a send answers once. The name is the one Apple Pay JS
  (`ApplePaySession.onpaymentauthorized`) and Google Pay's web API
  (`paymentDataCallbacks.onPaymentAuthorized`) share.
- **`onmerchantvalidation` is WebKit's.** The W3C removed
  `MerchantValidationEvent`; MDN marks it deprecated and non-standard;
  Safari still fires it and Apple Pay on the web needs it (D8). It is
  read only on the web, and only for Apple Pay.
- **No `abort()`.** The request lives as its call does (LLP 1133 D6
  rule 2), up to authorization (D6).
- **`hasEnrolledInstrument` is a shared word.** Chromium shipped it and
  the W3C dropped it; Apple's `canMakePayments(usingNetworks:capabilities:)`
  and Google's `isReadyToPay` with `existingPaymentMethodRequired` have
  it. `canMakePayment` keeps the W3C's meaning: "A true result … does not
  imply that the user has a provisioned instrument", which is Apple's
  `canMakePayments()`.
- **TypeScript gets Promise form**, and a handler is an `async` function
  in the data module's `tools` (D5).

app writes changes it (§9).

## 3. The sheet

### D5 — The sheet asks the app: handlers through `invoke`

A handler is a function in the app's data module's `tools` export, the
record `invoke` already calls (`js/src/prelude.js`), named by a string
literal in the call (`onpaymentauthorized="placeOrder"`). The bake checks
that `tools` has it (`payment-handler-missing`). The handler runs as
`invoke` runs a language model's tool (LLP 1133.016 D9 and D15 item 1): an
answer of its own, admitted at the call's origin or `tool`, whichever is
lower, so a handler can fetch and read the app's storage but cannot open
another sheet, prompt or pay (D14). Its journal line and `state.pending`
entry name the extension, the handler and the request id.

**Where each platform calls it:**

| Event | Apple ([delegate](https://developer.apple.com/documentation/passkit/pkpaymentauthorizationcontrollerdelegate)) | Android ([`BasePaymentDataCallbacks`](https://developers.google.com/pay/api/android/reference/client)) | Web |
|---|---|---|---|
| shipping address | `didSelectShippingContact`, answered with `PKPaymentRequestShippingContactUpdate` | `onPaymentDataChanged`, intent `SHIPPING_ADDRESS`, answered with `PaymentDataRequestUpdate` | `shippingaddresschange`, `updateWith(promise)` |
| shipping option | `didSelectShippingMethod`, `PKPaymentRequestShippingMethodUpdate` | `onPaymentDataChanged`, `SHIPPING_OPTION` | `shippingoptionchange` |
| payment method | `didSelectPaymentMethod`, `didChangeCouponCode` | `onPaymentDataChanged`, `PAYMENT_METHOD` (a card) and `OFFER` (a promotion code) | `paymentmethodchange` |
| merchant validation | — (the entitlement is the merchant's identity) | — | WebKit's `merchantvalidation`, `complete(promise)` |
| authorization | `didAuthorizePayment`, answered with `PKPaymentAuthorizationResult` | `onPaymentAuthorized`, intent `PAYMENT_AUTHORIZATION`, answered with `PaymentAuthorizationResult` | `show()` resolves; the module calls `complete()` or `retry()` |

The module asks a platform only for the events whose handlers the call
names: Apple's delegate answers the others with the request's own
values; Google's `callbackIntents` lists only those; the web listens to
those alone. `onpaymentauthorized` is always named, so Google's
`PAYMENT_AUTHORIZATION` intent is always on, and the Android sheet stays
up until the handler answers, as Apple's and the web's do.

**The seam's change: a pending call as `invoke`'s anchor.** Today
`invoke` is anchored on a handle a reply has already delivered, and the
runner records the handler names when that reply lands
(`handler_grant` in `invoke.rs`). A sheet's handlers are called before
its call has answered. So the runner records the call's handler names
and origin at admission, keyed by the pending call, and admits `invoke`
against that record until the sheet is closed (D6, D16 item 1).

**The budget and the platforms' deadline.** Every platform dismisses a
sheet whose handler is late: Google's callbacks "must call
`onCompleteListener.complete(...)` within 30 seconds"
([client reference](https://developers.google.com/pay/api/android/reference/client));
for Apple Pay "each event handler has a thirty (30) second timeout. If
the related completion method is not invoked within 30 seconds from the
start of the event, the payment sheet will dismiss with an error",
`shippingaddresschange` in Payment Request included ([TN3174](https://developer.apple.com/documentation/technotes/tn3174-diagnosing-issues-with-the-apple-pay-payment-sheet-on-your-website)).
PassKit's native delegate states no limit; the module treats it as Apple
Pay's. So the module gives each handler a budget of 25 seconds, which
leaves the module time to answer inside the platform's 30. Past the
budget an update is answered with the sheet's values as they were and
the platform's update error (Apple and the web, the update's `error`,
"unavailable"; Android, `PaymentDataRequestUpdate` with an error), and an
authorization is completed as D6 says. The budget runs on the session
clock, so under the agent the agent's clock decides. A handler that
throws is answered as one past its budget, at once. A platform that
dismisses the sheet itself (a slow module, a platform's shorter limit)
ends the call as the person's cancel would, or, after authorization, as
D6's timeout.

**Android's handlers live in a service.** Google calls an app's
`BasePaymentDataCallbacksService`, declared in its manifest with
`com.google.android.gms.permission.BIND_PAYMENTS_CALLBACK_SERVICE` and the
action `com.google.android.gms.wallet.callback.PAYMENT_DATA_CALLBACKS`,
in the app's own process (no `android:process`). The Android
implementation declares the service in its `exact.json`, and the service
hands each callback to the process's one open sheet, whose session it
recorded when the sheet opened; a callback that finds no open sheet
answers an error. `invoke` on Android is a seam addition (D16 item 2).

### D6 — The sheet's phases

A request moves through four phases, and what may end it differs in
each:

1. **Editing,** from the sheet's showing until the person authorizes,
   and again after a `retry`, or after a `fail` or `unknown` on Android,
   whose error result keeps the sheet up. While the call is live, the
   person edits, cancels or authorizes.
2. **Authorizing,** from the call of `onpaymentauthorized` until it
   answers or its budget ends. The handler may already have charged the
   card, so nothing but the session's end stops it: the runner does not
   cancel the send when its call is let go (an exception to LLP 1133.016
   D15 item 2, D16 item 1), and the sheet shows the handler's answer. A
   let-go that comes during this phase is held and takes effect when it
   ends, so the request then becomes abandoned rather than returning to
   editing.
3. **Abandoned,** when the call is let go (a superseded mutation, the
   screen leaving) while the sheet is up and not authorizing. The module
   closes the sheet where the platform lets it: `dismiss` on Apple;
   `abort()` on the web, except during a `retry`, when the W3C's `abort()`
   and `complete()` both reject until the person acts
   ([`abort()`](https://www.w3.org/TR/payment-request/#abort-method)).
   Where it cannot (that web retry; Android, whose Google Pay activity no
   app can withdraw), the request stays the module's, holding its place
   in the queue of decisions until the platform reports the sheet
   closed, and any authorization that arrives is answered as failed at
   once (`complete("fail")` after the web's retry resolves; Google's
   error result) without calling the app, so no payment reaches a
   server. Any update handler running is let go.
4. **Closed,** once the platform reports the sheet gone: after a result
   it shows, the person's cancel, or its own dismissal.

**The handler's answer:**

| Answer | Apple | Android | Web |
|---|---|---|---|
| `{result: "success"}` | `PKPaymentAuthorizationResult(status: .success)`; the sheet closes | `PaymentAuthorizationResult` success; the sheet closes | `complete("success")` |
| `{result: "fail"}` | `.failure` with no errors: the sheet shows the failure, then `paymentAuthorizationControllerDidFinish` is sent ("after the PKPaymentAuthorizationStatus … has been shown to the user", `PKPaymentAuthorizationController.h`) and the module dismisses it | an error result: Google's sheet shows it and stays, so the person may try another card (back to editing) or close it | `complete("fail")`, which closes it |
| `{result: "unknown"}` | `.failure`, as `fail`: PassKit and Google have no third state, and a success mark for a charge the merchant cannot confirm would mislead the person (App Review 4.9: "use Apple Pay branding and user interface elements correctly") | an error result, as `fail` | `complete("unknown")`, which shows neither and closes it |
| `{retry: errors}` | `.failure` with the errors, which "will be displayed to the user to correct" (`PKPaymentAuthorizationResult.errors`; `PKPaymentRequest.paymentShippingAddressInvalidError(withKey:localizedDescription:)` and the rest); back to editing | `PaymentAuthorizationResult` with the error's intent; back to editing | `retry(errors)`; back to editing |

A second authorization after a `retry`, or after a `fail` or `unknown`
on Android, calls the handler again, for the same checkout (below). On
Apple and the web a `fail` closes the sheet, and another try is a new
press on the same open checkout.

**The send answers when the sheet closes:** `PaymentResult` with the
last result the handler gave, or `AbortError` if the person closed it
with none. A call let go answers nothing: the journal says `payment:
closed after its call ended`, with the request id and the last result.

**The session's end** stops the handler (its runtime ends with the
session), so the module completes the sheet as failed where it can, and
the journal names the request.

**The authorization's budget** is D5's. Past it the module answers the
authorization as failed, the result is `fail` with the message
`authorize-timeout`, and the request ends for the app: on Apple and the
web the sheet closes, and on Android, whose error result keeps it up,
the request is abandoned (phase 3), so no later authorization calls the
app while the first attempt's outcome is unknown. The late handler runs
on, holding nothing; its answer is journaled and dropped.

**The app's server is the record of what was paid,** because a failed
sheet does not prove a card was not charged (a late answer, the
session's end, `unknown`). So the recipe's server, and the fixture's:

- makes the checkout, which is the order, before the sheet, with its
  items and prices fixed, and gives its id as `details.id`; every
  handler receives it as `requestId`, and the module makes no id of its
  own when the app gives one;
- treats each authorization as an attempt with its own idempotency key
  at the processor (the payment's transaction id, or an attempt id the
  server makes for that `/pay`), so a repeated submission of one payment
  charges once;
- captures at most one attempt per checkout: `/pay` on a paid checkout,
  or on one with an attempt not yet settled, answers that outcome and
  charges nothing; a declined or voided attempt leaves the checkout open,
  so a new payment may pay it;
- aims to answer within 20 seconds, inside D5's budget, and keeps an
  attempt whose processor outcome it does not know (a processor timeout,
  a lost processor answer) as `indeterminate`, then reconciles it with
  the processor, which sets the checkout `paid` or back to `open`;
- fulfils a paid checkout whatever the sheet showed: the server never
  sees the sheet, a fast answer can still be lost on its way to the
  device, and the sheet's failure is not a refund. A paid checkout that
  the person did not mean to pay is refunded through the app's own
  support, as a hand-built app's would be;
- answers `/pay` so the handler can tell the three apart: paid
  (`success`), declined (`fail`), and indeterminate (`unknown`, which
  D6's table shows as failure natively and as neither on the web);
- keeps a checkout's state (open, paid, indeterminate, needs action),
  which the confirmation screen reads, never only the send's answer.

**After the wallet,** a processor may still need the person: Google
documents that a card payment can require 3-D Secure authentication
after the sheet ([strong customer authentication](https://developers.google.com/pay/api/android/guides/resources/sca)).
The handler then answers `success` with `data` saying so
(`{needsAction: url}` in the recipe), the screen shows the checkout as
not yet paid, and the person continues from an app-origin action (an
`openURL` or the processor's own page); the server's state says when it
is paid. A wallet's success mark means the wallet's part is done, not
that the order is paid.

### D7 — The token reaches data code alone

`PaymentResponse.details` is the payment the merchant charges: Apple's
`ApplePayPayment` (`token.paymentData`, the encrypted payment, with
`paymentMethod` and `transactionIdentifier`), or Google's `PaymentData`
(`paymentMethodData.tokenizationData.token`). It is in the
`onpaymentauthorized` handler's argument and nowhere else exact2
publishes or keeps:

- the send's answer, `PaymentResult`, has no `details` (`withhold`, LLP
  1133.011 D10);
- the runner holds the handler's argument only while the handler runs
  (`Running.args` in `invoke.rs`, which a turn that awaits reuses), and
  never publishes, persists or records it: it is not in `pending`,
  `state.extensions`, the journal, a checkpoint or a trace;
- the hatches see the request before it is shown, never the payment
  (D11).

**One shape per method, wherever it came from.** The Apple
implementation serialises a `PKPayment` to the `ApplePayPayment` JSON
that Safari gives `PaymentResponse.details`, and the Android one passes
Google's `PaymentData` JSON as the web's Google Pay gives it. So an app's
server parses one shape for Apple Pay and one for Google Pay, whether the
payment came from a browser or a phone, and charges it with the
processor's own Apple Pay or Google Pay call. The substitute's payment
has the same shape (§9).

The rule binds exact2, not the app: a handler that returns the token in
its `data` puts it in Contract state, as data code that returns a
password does (LLP 1133.010 D2). The fixture's test checks that no
answer, state, journal line or trace carries the substitute token's
marker (§10, drive 1).

### D8 — The web: the press, merchant validation, and the browser's methods

**The press.** Chromium and WebKit reject `show()` without transient
activation, and a successful `show()` consumes it (the W3C's step:
"consume user activation"). WebKit measures a gesture by its call stack,
and a package view's event reaches the app after a microtask and
`exact.ready` (`host/web/native-glue.js`), so neither the press's action
nor a send from it runs where Safari still has the press. So the web
does as sign-in's button does (LLP 1133.014 D5):

1. **At the press,** in its own click handler and before it delivers
   `press`, `exact-payment-button` admits its `checkout` as the call
   would be admitted, synchronously, from what the web build gives the
   implementation: each Apple Pay `merchantIdentifier` against the app's
   `payment.apple-pay` lines (D13), the method dictionaries against
   their schemas (D10), and the one-sheet rule. A checkout refused there
   shows nothing, and the press's call fails with the refusal's code.
   The press is a person's, in the foreground, by construction.
2. **Then, in the same click,** it constructs a `PaymentRequest` from the
   checkout, attaches its listeners, and calls `show()`. Each listener
   answers its event before it returns, as the W3C requires
   (`updateWith(promise)`, and Safari's `complete(promise)` for
   `merchantvalidation`), with a promise that waits for the request's
   adoption and then for the handler. D5's budget for that handler runs
   from the event, not from the handler's start, since the platform's 30
   seconds do.
3. **The press's action** calls `showPaymentRequest` as its first
   operation, with nothing awaited before it: a Contract send, or data
   code whose first call it is. The call reaches the web implementation
   through promises (`host/web-js/modules.js`), passes the runner's own
   admission, and adopts the request this press showed, when its
   `methodData`, `details` and `options` equal the button's `checkout`;
   the handlers it names then answer the promises already given.
4. **A request no call adopts** is aborted when the press's action
   settles without having dispatched `showPaymentRequest`, the moment
   sign-in's button closes an unclaimed window (LLP 1133.014 D5); a
   dispatched call adopts it when it arrives, or aborts it if the runner
   refuses the call. So a press whose action does not pay leaves nothing
   up.

A call that finds no request to adopt, or one whose arguments differ
from the button's, fails `NotAllowedError`, message `activation`, and
aborts what was shown. So on the web a payment starts only from
`exact-payment-button`, which the HIG asks for anyway ("Use Apple Pay
buttons only to initiate payment"). The recipe computes the checkout
before the button is shown. Natively the button shows nothing itself,
and the call presents the sheet.

**One sheet on the web cannot wait.** Waiting in the queue of decisions
spends the activation, so a press that finds another sheet up shows
nothing, and its call fails `NotAllowedError`, message `busy`.

**Merchant validation.** Apple Pay on the web proves the merchant for
each payment: Safari gives a validation URL; the app's server posts to it
with its merchant identity certificate, over mutual TLS, and receives
"an opaque merchant session object" that "expires five minutes after it
is created" ([Providing merchant validation](https://developer.apple.com/documentation/applepayontheweb/providing-merchant-validation)).
Apple says: "Ensure that your server accesses only the validation URLs
provided by Apple … and fails for other URLs. It's a best practice to use
a strict allow list for the validation URLs. You must send the payment
session request from your server; never request the session from the
client" ([Requesting an Apple Pay payment session](https://developer.apple.com/documentation/applepayontheweb/requesting-an-apple-pay-payment-session)).
So an Apple Pay method needs `onmerchantvalidation` on the web, a
handler that posts the URL to the app's server and answers its session;
the recipe's server and the fixture allow only Apple's listed gateway
hosts, over HTTPS and without following redirects. The bake refuses a
call with an Apple Pay method and no `onmerchantvalidation` in an app
that builds for the web (`payment-merchant-validation`), since Safari
would otherwise fail every payment after showing the sheet; natively the
handler is inert. The domain must be registered and verified with Apple,
which serves `/.well-known/apple-developer-merchantid-domain-association`:
the app places the file Apple gives it in its web root, and the web build
warns when an app with a `payment.apple-pay` line has none.

**Which browsers.** Safari answers Apple Pay through Payment Request
(since 11.1); Chrome answers Google Pay through it ("Chrome is currently
the only web browser supporting the Payment Request API" for Google Pay,
[Google](https://developers.google.com/pay/api/web/guides/paymentrequest/tutorial));
Firefox ships Payment Request only behind a preference
(`dom.payments.request.enabled`, [compatibility data](https://github.com/mdn/browser-compat-data/blob/main/api/PaymentRequest.json)),
so there `available` is false. The web implementation reaches no
provider's script: Payment Request is the browser's own API, and the
Google button is drawn from Google's published assets, which the package
carries, as sign-in's is (LLP 1133.014 D5).

### D10 — The platforms' words

**The method data is tier 2.** Payment Request gives each method its own
dictionaries, in `PaymentMethodData.data` and in each
`PaymentDetailsModifier.data`, and each is the platform's own:

- **Apple Pay,** `supportedMethods: "https://apple.com/apple-pay"`.
  The method data is
  [`ApplePayRequest`](https://developer.apple.com/documentation/applepayontheweb/applepayrequest)'s
  keys, as Safari takes them: `version`, `merchantIdentifier`,
  `merchantCapabilities`, `supportedNetworks`, `countryCode`,
  `requiredBillingContactFields`, `requiredShippingContactFields`,
  `billingContact`, `shippingContact`, `supportedCountries`,
  `supportsCouponCode`, `couponCode`, `shippingContactEditingMode`,
  `applicationData`, `applePayLaterAvailability`. A modifier's data is
  [`ApplePayModifier`](https://developer.apple.com/documentation/applepayontheweb/applepaymodifier)'s:
  `paymentMethodType` (`credit`, `debit`, `prepaid`, `store`; absent,
  every type), `total`, `additionalLineItems`,
  `additionalShippingMethods`, and the `recurringPaymentRequest`,
  `automaticReloadPaymentRequest`, `deferredPaymentRequest` and
  `multiTokenContexts` that ask for those kinds of payment. Natively the
  Apple implementation builds a `PKPaymentRequest` from the same keys
  (`supportedNetworks` to `PKPaymentNetwork`s, a modifier's
  `recurringPaymentRequest` to `PKRecurringPaymentRequest`, …), applies a
  modifier with no `paymentMethodType` to the `PKPaymentRequest` before
  it is presented, and applies one with a type at
  `didSelectPaymentMethod`, whose `PKPaymentMethod.type` names the
  card's, as Safari's sheet applies it: its summary items and shipping
  methods, and a replacement for a recurring, automatic reload, deferred
  or multi-token request through the `PKPaymentRequestUpdate` it answers
  ([`PKPaymentRequestUpdate`](https://developer.apple.com/documentation/passkit/pkpaymentrequestupdate)).
  PassKit's headers set three limits, which the bake and admission
  check: the four requests are exclusive of one another on both classes,
  so a request with more than one is refused; an update's "billing
  agreement cannot be changed", so a typed modifier may replace one of
  them only when the request already has it from an untyped modifier;
  and the recurring, automatic reload and multi-token requests are iOS
  16 and macOS 13, the deferred one iOS 16.4 and macOS 13.3, below which
  each is refused `NotSupportedError`. So the same dictionaries serve
  Safari, iOS and macOS. `version` is read only on the web.
- **Google Pay,** `supportedMethods: "https://google.com/pay"`: Google's
  `PaymentDataRequest` JSON (`apiVersion`, `allowedPaymentMethods` with
  their `tokenizationSpecification`, `merchantInfo`,
  `shippingAddressParameters`, `offerInfo`), as Chrome takes it.
  Natively the Android implementation passes it to
  `PaymentDataRequest.fromJson` after filling what Payment Request's own
  arguments say, as Chrome does: `transactionInfo` from `details`,
  `shippingAddressRequired`, `emailRequired`, `shippingOptionRequired`
  from `options` and `callbackIntents` from the handlers named (D5). The
  environment is not in that JSON on Android: it is
  `Wallet.WalletOptions.setEnvironment`, given when the `PaymentsClient`
  is made, and the implementation makes the client with the bake's value
  (§9). On the web it is the method data's `environment`, which the web
  implementation writes from the bake.

The bake checks each dictionary's keys against the declaration's schema
for that method and place (method data or modifier) and refuses an
unknown key by name, as it refuses a dotted platform word (LLP 1133.002
D13); an authored Google `environment` is refused
(`payment-environment`), so no dictionary carries one. A target uses
only its own method's
dictionaries; the other is inert there.

**Words on the answers.**

| Word | On | Apple | Android |
|---|---|---|---|
| `orderDetails` | the authorize handler's answer, `apple.orderDetails` | `PKPaymentOrderDetails` (`orderTypeIdentifier`, `orderIdentifier`, `webServiceURL`, `authenticationToken`; iOS 16, macOS 13), on `PKPaymentAuthorizationResult`; on the web `ApplePayPaymentCompleteDetails.orderDetails` | — |
| `paymentMethod` | `PaymentResult`, `apple.paymentMethod` | `displayName` (such as "Visa 1234"), `network`, `type` | — |
| `paymentMethodDescription`, `cardNetwork` | `PaymentResult`, `android.…` | — | `paymentMethodData.description`, `info.cardNetwork` |
| `code` | errors | the PassKit error code | the `CommonStatusCodes` or `WalletConstants` code |

The HIG asks the confirmation to name the card as "1234 (Apple Pay)";
these words are what the screen shows, and they are no credential.

**Wallet passes,** imported from the platform's path (LLP 1133.001 D2):

| Name | From | Kind | Platform API |
|---|---|---|---|
| `addPasses(paths)` | `@exact/payments/apple` | send; a request (Wallet's sheet) | [`PKPassLibrary.addPasses(_:)`](https://developer.apple.com/documentation/passkit/pkpasslibrary) (iOS 7, macOS 10.12) on `PKPass(data:)`s read from `app:` paths; answers `PKPassLibraryAddPassesStatus` (`didAddPasses`, `shouldReviewPasses`, `didCancelAddPasses`) |
| `passLibraryStatus()` | `@exact/payments/apple` | live source; a fact | `PKPassLibrary.isPassLibraryAvailable()`, `PKAddPassesViewController.canAddPasses()` (iOS; false on macOS, which has no add-passes controller) |

A pass is signed by its issuer (an Apple Pass Type ID certificate; a

it to the wallet. On the web a pass is a link: a `.pkpass` URL that
Safari opens, or Google's `https://pay.google.com/gp/v/save/<jwt>`, which
`openURL` and `href` reach today, so the web has no pass words. Each pass
send is `"origin": "app"` and `"foreground": true` (D14), since it
shows a sheet.

## 5. What may be sold

### D12 — Physical goods and services; digital goods are purchases

The stores decide which goods an app may sell through a wallet, and
their rules are the module's boundary:

- **Apple.** "If you want to unlock features or functionality within
  your app … you must use in-app purchase" (3.1.1). "If your app enables
  people to purchase physical goods or services that will be consumed
  outside of the app, you must use purchase methods other than in-app
  purchase to collect those payments, such as Apple Pay or traditional
  credit card entry" (3.1.3(e)). "Physical gift cards that are sold
  within an app and then mailed to customers may use payment methods
  other than in-app purchase" (3.1.1). "Approved nonprofits may fundraise
  directly within their own apps or third-party apps, provided those
  fundraising campaigns … offer Apple Pay support" (3.2.1(vi)); other
  apps may not collect charitable funds in the app (3.2.2(iv)). "Apps
  using Apple Pay must provide all material purchase information to the
  user prior to sale … and must use Apple Pay branding and user interface
  elements correctly", and an app offering recurring payments must
  disclose the term, what each period provides, the charges and how to
  cancel (4.9) ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)).
- **Google Play.** Apps must use Play's billing for digital goods "unless
  Section 3, 8, or 9 applies", and must not use it "for the purchase or
  rental of physical goods", "for the purchase of physical services", for
  a credit card or utility bill, or for "peer-to-peer payments, online
  auctions, and tax exempt donations"; "In some markets, we offer Google
  Pay for apps selling physical goods and/or services"
  ([Payments policy](https://support.google.com/googleplay/android-developer/answer/9858738)).

**exact2 checks none of it.** Nothing on the device can tell a print
from a premium feature, and the rules are the stores', applied in review.
The package's README and the recipe state the line and send digital
goods to `@exact/purchases`; `contract vocab showPaymentRequest` says so
in its first line. The web has no store, and an app may sell what it
likes there; an app that ships the same screen natively is held to the
stores' rules on those targets, which is the app's to keep, as a
hand-built app's is.

## 6. Permission and origin

### D13 — No permission; the grant lines name the merchant

No platform asks a runtime permission for a wallet: the sheet, confirmed
with Face ID, Touch ID or the device's lock, is the consent each time. So
the module declares no `permission`. It does need the merchant named at
build:

| Line | Derives | Admission |
|---|---|---|
| `payment.apple-pay <merchant id>` (`merchant.com.example.app`; one line per merchant ID) | iOS and macOS: the `com.apple.developer.in-app-payments` entitlement listing every granted ID ([entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.in-app-payments)); web: the association-file warning (D8) | an Apple Pay method's `merchantIdentifier` must be a granted ID, else `SecurityError` before the sheet, as passkeys match `rp.id` (LLP 1133.011 D6) |
| `payment.google-pay` | Android: `<meta-data android:name="com.google.android.gms.wallet.api.enabled" android:value="true"/>`, the callbacks service (D5) | a Google Pay method needs the line, else `NotSupportedError` |

A binding call or a Contract use with neither line refuses at bake
(`grant-missing`). The entitlement needs a profile for an explicit App ID
with the Apple Pay capability, on iOS and on macOS, where Apple Pay is a
Developer ID capability as well as a Mac App Store one
([supported capabilities](https://developer.apple.com/help/account/reference/supported-capabilities-macos));
exact2's Mac releases are Developer ID, and a Mac build with a profile is
LLP 1133.010 D7's open step. A Mac bake without one marks the module
unavailable and the journal says why.

### D14 — Who may pay, and spending is not delegable

| Origin | `showPaymentRequest`, `addPasses`, `savePasses` | `paymentRequestStatus`, the pass facts |
|---|---|---|
| a person's input; the app's own foreground code | the wallet's sheet (D15) | answer |
| a tool invocation (LLP 1111) | fails `NotAllowedError`, `person-required`, before the wallet is reached | answer |
| a background wake; a headless session | fails `person-required` | answer |
| the app in the background | fails `NotAllowedError` (`"foreground": true`) | answer |
| a handler called by `invoke` | `person-required` (its origin is at most `tool`, D5) | answer |
| the development agent | §9 | §9 |

**Spending is not delegable,** as LLP 1133.015 D14 rules for a store
purchase: a payment spends the person's money with a card in their
wallet, confirmed by them in the wallet's sheet. No delegation record
lets a tool start one, as no record satisfies a presence check (LLP
1133.010 D12). An agent that wants the person to buy something asks
through the app's own UI, from whose button the person pays.

### D15 — One sheet at a time, over the session's window

`showPaymentRequest` and the pass sends join LLP 1133.002 D9's queue of
decisions natively, each held until the platform reports its sheet
closed, and are never shared: two queued payments show two sheets. The
web cannot wait (D8).

The sheet is presented over the session's window. On Apple the
controller's delegate answers
[`presentationWindow(for:)`](https://developer.apple.com/documentation/passkit/pkpaymentauthorizationcontrollerdelegate/presentationwindow(for:))
(iOS 14, macOS 11: a `UIWindow` on iOS, an `NSWindow` on macOS) with the
window of the package context's `presentation` (LLP 1133.027 D17 item
3): on iOS its view's window, on macOS its `NSWindow`. `presentation` is
set while the session's view is on screen, key or not; this module adds
its own check, since a payment sheet over a window the person is not
using is the wrong window: a call while `presentation` is nil, while the
iOS scene is not `foregroundActive`, or while the Mac window is not key,
fails `NotAllowedError` at once.

On Android `loadPaymentData` answers a `Task<PaymentData>` whose
resolution starts Google's activity. `ExactActivity` is a plain
`Activity` (`ExactActivity.kt`), so Google's
`TaskResultContracts.GetPaymentDataResult`, which needs a
`ComponentActivity`'s `registerForActivityResult`, is not available;
`AutoResolveHelper.resolveTask(task, activity, requestCode)`, deprecated
but documented, starts it for a request code whose result reaches
`onActivityResult`, which the host already routes to extensions
(`Extensions.activityResult`). The extension context gains that request
code (D16 item 6). With `PAYMENT_AUTHORIZATION` on, the authorize
handler is called from the callbacks service, never from the activity
result, which only ends the request.

## 7. Packaging and callers

### D16 — Seam additions

Each is general, each is apparatus under `rules/RULES.md` that lands
with this ruling, and each is proved by the out-of-tree fixture before
this package uses it (LLP 1133.001 D8):

1. **`invoke` anchored on a pending call, and a final callback.** A
   send's declared `callbacks` are recorded with its origin when the
   runner admits it, keyed by the pending call, and `invoke` is admitted
   against that record until the implementation reports the sheet
   closed. A callback marked `"final": true` (here `onpaymentauthorized`)
   holds the call: once it is invoked, `cancel_let_go` sends no `cancel`
   for that call until the callback answers or its budget ends, and a
   let-go during that span is delivered when it ends, which amends LLP
   1133.016 D15 item 2 for that span alone. Before it, `cancel` dismisses the
   sheet as today. Any sheet that consults the app while it is up would
   use the anchor: Apple's coupon codes, a map's search completer, App
   Intents' parameter resolution.
2. **`invoke` on Android:** `ExtensionContext.invoke(handler, args,
   reply)`, which the language model's Android tools also need (LLP
   1133.020 §4 row 7).
3. **A ceremony that asks the app** (§9): a ceremony declares `asks`,
   each a typed field or a choice the agent gives (`type @t
   {"shippingAddress": …}`, `tap @t authorize`) that calls a named
   handler and lays its answer over the ticket's `args`, so the agent
   sees what the person would see after the app answered. Today a
   ceremony's ticket is answered once.
4. **A `json` option checked by a schema per discriminant:** `data` is
   checked against the dictionary its sibling `supportedMethods` names,
   at bake for literals and at admission for computed values (D10).
5. **The grant family `payment.*`** and its derivations (D13), beside
   `auth.passkey` in `bake/src/reach.rs`.
6. **An activity request code for an extension on Android:**
   `ExtensionContext.resultCode(done)`, a code from the host's range
   whose `onActivityResult` reaches `done`, with the activity in front,
   for a platform helper that starts its own activity
   (`AutoResolveHelper.resolveTask`; Play's `startIntentSenderForResult`
   flows).
7. **A package view that acts in its own click on the web,** for a call
   from that press to adopt, as sign-in's button does (LLP 1133.014 D5):
   the view holds what it started under the press's dispatch; a call
   the press's action dispatches claims it when it arrives, and it is
   undone when the action settles having dispatched none, or when the
   runner refuses the call (D8). If sign-in's button lands first, this is its
   mechanism, generalized; if this does, sign-in uses it.

Inherited, built or accepted, and built by whichever module comes first:
the session's `presentation` (LLP 1133.027 D17 item 3), the locked Gradle
graph (LLP 1133.008 D8 item 5) and the merged-manifest check (LLP
1133.015 D16 item 6). Inherited as built: package views and their click
on Android, `withhold`, `destroy`, the foreground, the session clock,
handles provisional until delivered, activity results. `"gesture": true`
is not used: no send from a package view's press reaches the browser
inside the press (D8).

There is no `prefer` that pays: each payment in a drive is a tap, so the
transcript shows every place a person would be asked to pay. An app's
handlers run unchanged against the substitute's payment and a real one,
since the shapes are the same; the fixture server takes a substitute
token only when started with `--agent`, and a production server is told
by the recipe to refuse `exactSubstitute` outright.

**Never a real card.** Four rules, each a decision, not a default:

1. **Under the agent no wallet is reached** (above).
2. **Google's environment is the bake's.** Every bake that is not a
   production delivery bake (LLP 1030) makes the Android client with
   `WalletConstants.ENVIRONMENT_TEST`, and has the web implementation
   write `environment: "TEST"`, in which "the API doesn't return card
   data capable of a transaction"; only a production bake gives
   `ENVIRONMENT_PRODUCTION` and `PRODUCTION`. The implementation never
   relies on the client's default, which is production. An authored
   `environment` is refused at bake (`payment-environment`, D10), and no
   hatch reaches it (D11). Nothing an app writes outside a production
   bake reaches Google's production environment.
3. **Apple's environment is the account's.** Apple Pay has no
   environment switch: a device signed in to a Sandbox Apple Account
   offers Apple's test cards, and "Real cards must be used in the
   production environment. Test cards will not work"
   ([sandbox](https://developer.apple.com/apple-pay/sandbox-testing/)).
   So `--bind payments` runs under the agent only on the iOS simulator,
   which has no card; on a device or a Mac it runs only through the
   checklist, whose first step checks that a Sandbox Apple Account is the
   one signed in, and a device with a personal account is never used.
4. **The fixture server charges nothing.** It records the checkout and
   the token's length and never sends a token to a processor, so no card
   is charged whatever is in the wallet.

**Disclosure:** `state.extensions` lists `payments`, its binding per
target, each ceremony's request id, method, total, origin and outcome,
and each handler's name, duration and answer kind; never an address
line, a payer's details or a token.

**Production:** none of it.

## 10. The consumer: Order a Print

The photo editor edits a photo and saves it to the library (LLP 1133.019
§11). A print of the edit is the most ordinary physical good an editing
app sells, and the clearest case of App Review's 3.1.3(e): the print is
made and mailed outside the app, so in-app purchase may not be used. The
editor gains:

- **Order a Print,** a row under Save to Photos, shown while

  with `transformImage` (LLP 1133.019), uploads it, and makes a checkout
  on the print server with the size and price fixed; it answers the

## 11. What this amends, and what stays out

  checked by a discriminant's schema (D16 item 4).

  goods" moves to this module's record (§13 question 9).

- Card entry without a wallet, and any processor's SDK.

1. **Handlers through `invoke`, with the token in the authorize
   handler's argument alone (D5, D7),** rather than Payment Request's
   two-phase `show()` then `complete()` in data code. *Recommended: yes
   (75%).* The two-phase form keeps the W3C's shape for data code, but
   on the web data code cannot reach `show()` inside the press (D8), and
   on Android the authorization's outcome is only a callback. The cost is
   a declared deviation and D16 items 1 and 2.
2. **A final handler holds its call (D6):** once the authorize handler
   is called, a let-go call sends no `cancel` until it answers or its
   budget ends, and a request whose call is gone calls the app no more,
   kept by the module where the platform cannot close it. *Recommended: yes
   (80%).* The alternative, cancelling with the call, can leave a card
   charged and the sheet saying it failed.
3. **`unknown` shown as failure natively (D6).** *Recommended: yes
   (70%).* PassKit and Google have no third state; a success mark for a
   charge the merchant cannot confirm misleads, and the server's
   checkout says what happened. The alternative, success, is what a
   person who was in fact charged would rather see.

   implementations stay pure platform code.
