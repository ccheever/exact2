## Summary

`@exact/payments` takes a payment for physical goods and services with
the device's wallet: Apple Pay on iOS and macOS, Google Pay on Android,
and whichever of the two the browser offers on the web. Tier 1 is the
W3C Payment Request API's: its method data, details and options, its
events, `show()`, `complete()` and `retry()`:

```
use showPaymentRequest, paymentRequestStatus, PaymentResult, PaymentRequestStatus
  from "@exact/payments"

resource checkout = printCheckout(size) as shape Checkout else empty()
resource wallet = paymentRequestStatus(methodData=checkout.methodData)
  as shape PaymentRequestStatus else empty()
mutation ordered as shape PaymentResult then confirmed

action orderPrint
  send ordered = showPaymentRequest(methodData=checkout.methodData,
    details=checkout.details, options=checkout.options,
    onshippingaddresschange="quoteShipping", onpaymentauthorized="placeOrder")

// in the view, shown while wallet.canMakePayment:
exact-payment-button type="order" press=orderPrint testId="order-print"
```

```ts
// app.ts: the app's own data code, called by the sheet.
export async function quoteShipping(e: PaymentRequestUpdateEvent) {
  return await (await fetch(`${api}/quote`, { method: "POST",
    body: JSON.stringify(e.shippingAddress) })).json();   // a PaymentDetailsUpdate
}

export async function placeOrder(response: PaymentResponse) {
  const res = await fetch(`${api}/orders`, { method: "POST", body: JSON.stringify({
    method: response.methodName, token: response.details, ship: response.shippingAddress,
    print: currentPrint() }) });
  if (res.status === 422) return { retry: (await res.json()).errors };  // retry()
  if (!res.ok) return { result: "fail" };                              // complete("fail")
  return { result: "success", data: { orderId: (await res.json()).id } };
}
```

Five decisions carry the module:

- **The sheet asks the app while it is up.** A shipping address chosen
  in the sheet needs the app's price for it, and an authorized payment
  needs the app's server to charge it, both before the sheet closes.
  Each is a handler the app names, a function its data code exports,
  which the module calls through the runner's `invoke` and answers the
  sheet with (D5).
- **The payment token reaches data code alone.** The token is what the
  merchant's server charges, so it never enters Contract state, the
  journal, `pending` or `state.extensions`: only the `onpaymentauthorized`
  handler receives it, as only data code receives a passkey response
  (D7).
- **Authorization is the point of no return.** Until the person
  authorizes, the request lives as its call does; once the handler that
  charges has been called, it runs to its answer and the sheet shows that
  answer, whatever happens to the call (D6).
- **The method data is the platform's own words.** Payment Request
  already gives each payment method its own dictionary: Apple's
  `ApplePayRequest` and Google's `PaymentDataRequest`. Each target pays
  with the method it has, and that dictionary is tier 2 (D10).
- **What may be sold this way is the stores' rule.** Apple and Google
  require their in-app purchase systems for digital goods and require
  something else, such as Apple Pay or Google Pay, for physical goods
  and services. Digital goods are `@exact/purchases` (LLP 1133.015) (D12).

Tier 2 also reaches Wallet passes: adding a signed pass to Apple Wallet
and saving one to Google Wallet. Tier 3 hands the app's Swift the
`PKPaymentRequest` before it is presented, and its Kotlin the
`PaymentDataRequest`'s JSON before `loadPaymentData`.

The consumer is the photo editor (§10): Order a Print sends the edited
photo to a print lab, a physical good, through a fixture print server
that records orders and never charges a card.

## 0. What is new here

The modules before this one either answer a value the device has, or
show a sheet whose answer the module returns (a passkey, a store
purchase). A payment sheet differs in three ways, and four more things
follow from what is being sold:

1. **A sheet that needs the app's answers while it is up.** Apple's
   delegate is asked for a new total when the person picks an address or
   a shipping method, and for the authorization's result after they
   authorize; it "automatically waits for its delegate to finish
   responding to one method before it calls other delegate methods"
   ([`PKPaymentAuthorizationControllerDelegate`](https://developer.apple.com/documentation/passkit/pkpaymentauthorizationcontrollerdelegate)).
   Google calls a service in the app, which "must call
   `onCompleteListener.complete(...)` within 30 seconds"
   ([client reference](https://developers.google.com/pay/api/android/reference/client)).
   The web fires `shippingaddresschange` and asks for `updateWith()`.
   No module so far is called back while its own call is pending (D5).
2. **A credential with a few minutes' life.** The token is encrypted for
   the merchant, and the merchant's server can charge it once; Apple
   tells the server to treat a token whose signing time is more than five
   minutes from the transaction as a possible replay
   ([token format](https://developer.apple.com/documentation/passkit/payment-token-format-reference)).
   It belongs below the data seam (LLP 1018 D5), as a passkey response
   and an ID token do (D7).
3. **A call that must outlive its caller.** Once the server may have
   charged, cancelling the call would leave the person's money taken and
   the sheet saying it failed (D6).
4. **The web needs the press.** Browsers reject `show()` without
   transient activation ([§`show()`](https://www.w3.org/TR/payment-request/),
   a MAY that Chromium and WebKit apply), where passkeys needed none
   (LLP 1133.011 D9). So the sheet is shown by a Contract send in the
   press's dispatch, and the token goes to data code by the handler (D8).
5. **What may be sold is decided by the stores** (D12), and nothing on
   the device can tell a print from a subscription.
6. **Two wallets, one tier 1.** No platform has both Apple Pay and Google
   Pay natively; the web has whichever its browser has. Payment Request's
   method data names both, and each target takes its own (D1, D10).
7. **Real money in the agent's hands.** A drive must never charge a card.
   Under the agent no wallet is reached; Google Pay runs in its `TEST`
   environment in every build that is not a production bake; Apple Pay is
   driven only with Apple's sandbox; and the fixture server never sends a
   token to a processor (§9).

## 2. Tier 1

### D1 — Payment Request's names

The W3C API is one object: `new PaymentRequest(methodData, details,
options)`, then `show()`, which answers a `PaymentResponse` that the
page finishes with `complete(result)` or sends back with
`retry(errors)`; while the sheet is up, `shippingaddresschange`,
`shippingoptionchange` and `paymentmethodchange` fire, each answered by
`updateWith(detailsUpdate)`; `canMakePayment()` says whether the page
may offer it ([Payment Request](https://www.w3.org/TR/payment-request/)).
`@exact/payments` declares:

| Name | Kind | Meaning | Contract | Data code |
|---|---|---|---|---|
| `showPaymentRequest(methodData, details, options, on…)` | send; a request (the wallet's sheet) | the constructor's arguments and `show()` in one call, with the app's handlers for the sheet's events (D5) | `send p = showPaymentRequest(…)` | `await showPaymentRequest({ … })` |
| `paymentRequestStatus(methodData)` | live source; a fact; `sync` | `"PaymentRequest" in window` and `canMakePayment()` for these methods on this target, and which method it would use | `resource s = paymentRequestStatus(…)` | `await paymentRequestStatus({ methodData })` |
| `exact-payment-button` | view | the wallet's own button; its `press` is an event the app's action answers by sending `showPaymentRequest` | `exact-payment-button type="buy" press=pay` | — |

**The handlers** are keyword arguments naming functions the app's data
module exports (D5):

| Handler | The web's event | Called with | Answers |
|---|---|---|---|
| `onshippingaddresschange` | `shippingaddresschange` | `{shippingAddress, shippingOption, methodName}`, the address redacted (D2) | a `PaymentDetailsUpdate` |
| `onshippingoptionchange` | `shippingoptionchange` | the same, with the chosen option's `id` | a `PaymentDetailsUpdate` |
| `onpaymentmethodchange` | `paymentmethodchange` | `{methodName, methodDetails}` (Apple's card type, or a coupon code, D10) | a `PaymentDetailsUpdate` |
| `onmerchantvalidation` | `merchantvalidation` (WebKit's) | `{methodName, validationURL}` | `{merchantSession}`, the opaque object Apple's server returned (D8) |
| `onpaymentauthorized` (required) | none: Apple Pay JS's `onpaymentauthorized` and Google Pay's `onPaymentAuthorized` | the `PaymentResponse`, with `details` | `{result, data}` for `complete(result)`, or `{retry: PaymentValidationErrors}` for `retry(errors)` |

**Values,** by the W3C's dictionaries, every amount a
`PaymentCurrencyAmount` (`currency`, an ISO 4217 code, and `value`, a
decimal string; never a float):

| Shape | Fields |
|---|---|
| `PaymentMethodData` | `supportedMethods` (`https://apple.com/apple-pay` or `https://google.com/pay`); `data`, `json`: the method's own request (D10) |
| `PaymentDetailsInit` | `total` (`PaymentItem`: `label`, `amount`, `pending`); `displayItems`; `shippingOptions` (`id`, `label`, `amount`, `selected`); `modifiers` (`supportedMethods`, `total`, `additionalDisplayItems`, `data`) |
| `PaymentDetailsUpdate` | as `PaymentDetailsInit` without `id`, with `error`, `shippingAddressErrors`, `payerErrors`, `paymentMethodErrors` |
| `PaymentOptions` | `requestPayerName`, `requestPayerEmail`, `requestPayerPhone`, `requestShipping`, `requestBillingAddress`; `shippingType` (`shipping`, `delivery`, `pickup`) |
| `ContactAddress` | `country`, `addressLine`, `region`, `city`, `dependentLocality`, `postalCode`, `sortingCode`, `organization`, `recipient`, `phone` |
| `PaymentResponse` (handler only) | `requestId`, `methodName`, `details` (`json`, the method's payment, D7), `shippingAddress`, `shippingOption`, `payerName`, `payerEmail`, `payerPhone` |
| `PaymentResult` (the send's answer) | `PaymentResponse`'s fields without `details`; `result` (`success`, `fail`, `unknown`: the `PaymentComplete` the handler chose); `data` (`option<json>`, what the handler gave for the screen); `apple`, `android` (D10) |
| `PaymentRequestStatus` | `available`; `canMakePayment`; `hasEnrolledInstrument` (`option<bool>`); `methodName` (`option<string>`, the method this target would use) |

**Errors.** In Contract, `failure(…).code`; in TypeScript and Rust a
rejection `{code, message}` (LLP 1133.002 D1). The W3C's names, with the
platforms' cases:

| Code | When | Apple | Android |
|---|---|---|---|
| `AbortError` | the person closed the sheet before authorizing; the call was let go before authorization (D6) | `paymentAuthorizationControllerDidFinish` with no authorization | `CommonStatusCodes.CANCELED` |
| `NotSupportedError` | no method in `methodData` that this target has; the target has no implementation; `available` false | `canMakePayments()` false | `isReadyToPay` false; Play services missing |
| `NotAllowedError` | a tool, wake or headless origin (`person-required`, D14); the app in the background; no window of the session on screen (D15); on the web, the press's activation spent (`activation`) or another sheet up (`busy`), D8 | the same | the same |
| `SecurityError` | an Apple Pay `merchantIdentifier` no `payment.apple-pay` line grants (D13); the web's own refusals | — | — |
| `TypeError`, `RangeError` | a malformed amount, currency or method, checked at admission as the W3C constructor checks them | — | — |
| `OperationError` | the wallet failed; a handler did not answer within its bound (D5); the platform's code in `apple.code`, `android.code` | `present` answered false | `loadPaymentData` failed, with its `statusCode` |

A declined card is not an error: the handler answers `{result: "fail"}`,
the sheet shows the failure, and the send answers `PaymentResult` with
`result` `fail`, which the app's screen reads.

### D2 — What the sheet gives, and when

The person's address and contact reach the app in two steps, by the
W3C's rule and both platforms' alike:

- **While the sheet is up,** a shipping address is redacted: the W3C
  removes `organization`, `phone`, `recipient` and `addressLine` before
  `shippingaddresschange`; Apple gives "only the card type and a redacted
  shipping address" before authorization ([HIG](https://developer.apple.com/design/human-interface-guidelines/apple-pay));
  Google's `IntermediatePaymentData` carries the address's country,
  postal code, administrative area and locality. The handler receives
  what its platform gives, in `ContactAddress`'s fields, and absent
  fields are `none`.
- **At authorization,** the full shipping address, the payer's name,
  email and phone that the options requested, and the payment.

So a handler that quotes shipping works from a region and a postal code,
and only `onpaymentauthorized` sees a street.

### D3 — Declared deviations

Each because the web's form does not fit a module call that answers:

- **No `PaymentRequest` object.** `showPaymentRequest` takes the
  constructor's three arguments and shows the sheet; the name says both,
  since a bare `show` would collide with an app's own action names (the
  photo editor has one). The request's `id` is in `details` as the W3C's.
- **Events are named handlers, not listeners.** A Contract value cannot
  be a function, and a call into data code needs a name the runner can
  admit (D5). The handler keywords take the W3C's `on…` attribute names.
- **`onpaymentauthorized` replaces `complete()` and `retry()` on the
  response.** The W3C resolves `show()` and lets the page finish the
  response later. Here the handler that receives the response answers
  how to finish it: `{result}` is `complete(result)`, with `data`, the
  W3C's `PaymentCompleteDetails.data`; `{retry}` is `retry(errors)`, and
  the handler is called again when the person authorizes again. Three
  reasons: the token stays in data code while the sheet may be started
  from Contract (D7, D8); Google gives the authorization's outcome only
  through `onPaymentAuthorized` and Apple only through its delegate's
  completion; and a send answers once. The name is the one Apple Pay JS
  (`ApplePaySession.onpaymentauthorized`) and Google Pay's web API
  (`paymentDataCallbacks.onPaymentAuthorized`) share.
- **`onmerchantvalidation` is WebKit's.** The W3C removed
  `MerchantValidationEvent`; MDN marks it deprecated and non-standard;
  Safari still fires it and Apple Pay on the web needs it (D8). It is
  read only on the web, and only for Apple Pay.
- **No `abort()`.** The request lives as its call does (LLP 1133 D6
  rule 2), up to authorization (D6).
- **`hasEnrolledInstrument` is a shared word.** Chromium shipped it and
  the W3C dropped it; Apple's `canMakePayments(usingNetworks:capabilities:)`
  and Google's `isReadyToPay` with `existingPaymentMethodRequired` have
  it. `canMakePayment` keeps the W3C's meaning: "A true result … does not
  imply that the user has a provisioned instrument", which is Apple's
  `canMakePayments()`.
- **TypeScript gets Promise form**, and a handler is an exported
  `async` function (D5).

## 3. The sheet

### D5 — The sheet asks the app: handlers through `invoke`

A handler is a function the app's data module exports, named by a string
literal in the call (`onpaymentauthorized="placeOrder"`). The bake checks
that the data module exports it (`payment-handler-missing`). The handler
runs as `invoke` runs a language model's tool (LLP 1133.016 D9 item 1):
an answer of its own, admitted at the call's origin or `tool`, whichever
is lower, with the cause `payment`, so a handler can fetch and read the
app's storage but cannot open another sheet, prompt or pay.

**Where each platform calls it:**

| Event | Apple ([delegate](https://developer.apple.com/documentation/passkit/pkpaymentauthorizationcontrollerdelegate)) | Android ([`BasePaymentDataCallbacks`](https://developers.google.com/pay/api/android/reference/client)) | Web |
|---|---|---|---|
| shipping address | `didSelectShippingContact`, answered with `PKPaymentRequestShippingContactUpdate` | `onPaymentDataChanged`, intent `SHIPPING_ADDRESS`, answered with `PaymentDataRequestUpdate` | `shippingaddresschange`, `updateWith(promise)` |
| shipping option | `didSelectShippingMethod`, `PKPaymentRequestShippingMethodUpdate` | `onPaymentDataChanged`, `SHIPPING_OPTION` | `shippingoptionchange` |
| payment method | `didSelectPaymentMethod`, `didChangeCouponCode` | `onPaymentDataChanged`, `OFFER` | `paymentmethodchange` |
| merchant validation | — (the entitlement is the merchant's identity) | — | WebKit's `merchantvalidation`, `complete(promise)` |
| authorization | `didAuthorizePayment`, answered with `PKPaymentAuthorizationResult` | `onPaymentAuthorized`, intent `PAYMENT_AUTHORIZATION`, answered with `PaymentAuthorizationResult` | `show()` resolves; the module calls `complete()` or `retry()` |

The module asks a platform only for the events whose handlers the call
names: Apple's delegate answers the others with the request's own
values; Google's `callbackIntents` lists only those; the web listens to
those alone. `onpaymentauthorized` is always named, so Google's
`PAYMENT_AUTHORIZATION` intent is always on, and the Android sheet stays
up until the handler answers, as Apple's and the web's do.

**The seam's change: a pending call as `invoke`'s anchor.** Today
`invoke` is anchored on a handle a reply has already delivered, and the
runner records the handler names when that reply lands. A sheet's
handlers are called before its call has answered. So the runner records
the call's handler names and origin at admission, keyed by the pending
call, and admits `invoke` against that record until the call answers or
D6's rule ends it (D16 item 1).

**The bound.** Each handler answers within 30 seconds, Google's limit,
which the module applies on every target so that a handler behaves the
same everywhere: past it, an update leaves the sheet as it was with the
platform's own error (Android shows `CALLBACK_TIMED_OUT` itself; Apple
and the web get the update's `error`, "unavailable"), and an
authorization completes with D6's timeout. The bound runs on the session
clock, so under the agent the agent's clock decides. A handler that
throws is answered as one that timed out, at once.

**Android's handlers live in a service.** Google calls an app's
`BasePaymentDataCallbacksService`, declared in its manifest with
`com.google.android.gms.permission.BIND_PAYMENTS_CALLBACK_SERVICE` and the
action `com.google.android.gms.wallet.callback.PAYMENT_DATA_CALLBACKS`.
The Android implementation declares the service in its `exact.json`, and
the service hands each callback to the process's one open sheet, whose
session it recorded when the sheet opened; a callback that finds no open
sheet answers an error. `invoke` on Android is a seam addition (D16 item
2).

### D6 — Before and after authorization

**Before the person authorizes,** the request lives as its call does: a
superseded mutation, the screen leaving or the session's end (LLP
1133.009 D10 item 1) closes the sheet, `dismiss` on Apple, `abort()` on
the web, and the call fails `AbortError`. Android cannot withdraw Google
Pay's activity; the implementation records the call as let go, and an
authorization that then arrives is completed `ERROR` at once and calls no
handler, so the token reaches no server. A handler running for an update
when its call is let go is let go too (`invoke`'s own rule).

**Once `onpaymentauthorized` has been called,** the request is the
handler's until it answers, whatever happens to the call:

- the handler is not let go when its call is, because it may already
  have charged the card;
- the sheet shows the handler's answer: `success` and `fail` as the
  platform's success and failure; `retry` as the errors, with the sheet
  left up; `unknown` as success on Apple and Android, which have no third
  state, and as `complete("unknown")` on the web;
- the send answers `PaymentResult`, or, if its call was let go, the
  answer is dropped and the journal says `payment: completed after its
  call ended`, with the request id and the result.

The session's end is the exception: the handler's runtime ends with the
session (LLP 1133.009 D10 item 1), so the module completes the sheet as
failed and the journal names the request. The app's server is the record
of what was charged: a confirmation screen reads the server's orders,
never only the send's answer, and the recipe's server keys each charge
by the token's transaction id, which Apple's step 5 asks of it ("Confirm
that you haven't already credited this payment"), so a repeated
authorization charges once.

**The authorization's bound** is D5's 30 seconds. Past it the module
completes the sheet as failed, the send fails `OperationError`, message
`authorize-timeout`, and a later answer from the handler is journaled and
dropped. A card the server charged after the bound shows as failed in
the sheet; the recipe's server answers within 20 seconds or voids.

### D7 — The token reaches data code alone

`PaymentResponse.details` is the payment the merchant charges: Apple's
`ApplePayPayment` (`token.paymentData`, the encrypted payment, with
`paymentMethod` and `transactionIdentifier`), or Google's `PaymentData`
(`paymentMethodData.tokenizationData.token`). It is in the
`onpaymentauthorized` handler's argument and nowhere else:

- the send's answer, `PaymentResult`, has no `details` (`withhold`, LLP
  1133.011 D10);
- the runner carries the handler's argument to the data runtime and
  keeps no copy: it is not in `pending`, `state.extensions`, the journal
  or a checkpoint; `invoke`'s journal line names the handler and the
  request, never the argument;
- the hatches see the request before it is shown, never the payment
  (D11).

**One shape per method, wherever it came from.** The Apple
implementation serialises a `PKPayment` to the `ApplePayPayment` JSON
that Safari gives `PaymentResponse.details`, and the Android one passes
Google's `PaymentData` JSON as the web's Google Pay gives it. So an app's
server parses one shape for Apple Pay and one for Google Pay, whether the
payment came from a browser or a phone, and charges it with the
processor's own Apple Pay or Google Pay call.

The rule binds exact2, not the app: a handler that returns the token in
its `data` puts it in Contract state, as data code that returns a
password does (LLP 1133.010 D2). The fixture's test checks that no
answer, state or journal line carries the token's marker (§10, drive 1).

### D8 — The web: the press, merchant validation, and the browser's methods

**The press.** Chromium and WebKit reject `show()` without transient
activation, and a successful `show()` consumes it (the W3C's step:
"consume user activation"). Data code reaches a page module through a
promise even when the module is loaded (LLP 1133.014 D5), so a
data-code call reaches the browser after the press's dispatch, where
Safari's activation may already be gone. So `showPaymentRequest` is
declared `"gesture": true`: a Contract send from a press reaches the web
implementation in that press's dispatch (LLP 1133.016 D9 item 5), which
constructs the request and calls `show()` there. The recipe sends it from
`exact-payment-button`'s press with nothing awaited first, and computes
the checkout (its method data, prices and options) before the button is
shown. A data-code call on the web, or one whose press is spent, fails
`NotAllowedError`, message `activation`. Natively nothing needs the
press, and data code may call it.

**One sheet on the web cannot wait.** Waiting in the queue of decisions
spends the activation, so a press that finds another sheet up fails
`NotAllowedError`, message `busy`, as sign-in's does (LLP 1133.014 D5).

**Merchant validation.** Apple Pay on the web proves the merchant for
each payment: Safari gives a validation URL; the app's server posts to it
with its merchant identity certificate, over mutual TLS, and receives
"an opaque merchant session object" that "expires five minutes after it
is created" ([Providing merchant validation](https://developer.apple.com/documentation/applepayontheweb/providing-merchant-validation));
"never request the session from the client". So an Apple Pay method on
the web needs `onmerchantvalidation`, which posts the URL to the app's
server and answers its session; admission refuses a web call with an
Apple Pay method and no such handler (`payment-merchant-validation`),
since Safari would otherwise fail every payment after showing the sheet.
The domain must be registered and verified with Apple, which serves
`/.well-known/apple-developer-merchantid-domain-association`: the app
places the file Apple gives it in its web root, and the web build warns
when an app with a `payment.apple-pay` line has none.

**Which browsers.** Safari answers Apple Pay through Payment Request
(since 11.1); Chrome answers Google Pay through it ("Chrome is currently
the only web browser supporting the Payment Request API" for Google Pay,
[Google](https://developers.google.com/pay/api/web/guides/paymentrequest/tutorial));
Firefox ships Payment Request only behind a preference
(`dom.payments.request.enabled`, [compatibility data](https://github.com/mdn/browser-compat-data/blob/main/api/PaymentRequest.json)),
so there `available` is false. The web implementation reaches no
provider's script: Payment Request is the browser's own API, and the
Google button is drawn from Google's published assets, which the package
carries, as sign-in's is (LLP 1133.014 D5).

### D10 — The platforms' words

**The method data is tier 2.** Payment Request gives each method its own
dictionary in `PaymentMethodData.data`, and each is the platform's own:

- **Apple Pay,** `supportedMethods: "https://apple.com/apple-pay"`:
  [`ApplePayRequest`](https://developer.apple.com/documentation/applepayontheweb/applepayrequest)'s
  keys, as Safari takes them: `version`, `merchantIdentifier`,
  `merchantCapabilities`, `supportedNetworks`, `countryCode`,
  `requiredBillingContactFields`, `requiredShippingContactFields`,
  `supportedCountries`, `supportsCouponCode`, `couponCode`,
  `shippingContactEditingMode`, `applicationData`, and the recurring,
  automatic reload and deferred payment requests. Natively the Apple
  implementation builds a `PKPaymentRequest` from the same keys
  (`merchantIdentifier` to `merchantIdentifier`, `supportedNetworks` to
  `PKPaymentNetwork`s, `recurringPaymentRequest` to
  `PKRecurringPaymentRequest`, …), so one dictionary serves Safari, iOS
  and macOS. `version` is read only on the web.
- **Google Pay,** `supportedMethods: "https://google.com/pay"`: Google's
  `PaymentDataRequest` JSON (`apiVersion`, `allowedPaymentMethods` with
  their `tokenizationSpecification`, `merchantInfo`,
  `shippingAddressParameters`, `offerInfo`), as Chrome takes it.
  Natively the Android implementation passes it to
  `PaymentDataRequest.fromJson` after filling what Payment Request's own
  arguments say, as Chrome does: `transactionInfo` from `details`,
  `shippingAddressRequired`, `emailRequired`, `shippingOptionRequired`
  from `options`, `callbackIntents` from the handlers named (D5), and
  `environment` (D4).

The bake checks each dictionary's keys against the declaration's schema
for that method and refuses an unknown key by name, as it refuses a
dotted platform word (LLP 1133.002 D13). A target uses only its own
method's dictionary; the other is inert there.

## 5. What may be sold

### D12 — Physical goods and services; digital goods are purchases

The stores decide which goods an app may sell through a wallet, and
their rules are the module's boundary:

- **Apple.** "If you want to unlock features or functionality within
  your app … you must use in-app purchase" (3.1.1). "If your app enables
  people to purchase physical goods or services that will be consumed
  outside of the app, you must use purchase methods other than in-app
  purchase to collect those payments, such as Apple Pay or traditional
  credit card entry" (3.1.3(e)). "Physical gift cards that are sold
  within an app and then mailed to customers may use payment methods
  other than in-app purchase" (3.1.1). "Approved nonprofits may fundraise
  directly within their own apps or third-party apps, provided those
  fundraising campaigns … offer Apple Pay support" (3.2.1(vi)); other
  apps may not collect charitable funds in the app (3.2.2(iv)). "Apps
  using Apple Pay must provide all material purchase information to the
  user prior to sale … and must use Apple Pay branding and user interface
  elements correctly", and an app offering recurring payments must
  disclose the term, what each period provides, the charges and how to
  cancel (4.9) ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)).
- **Google Play.** Apps must use Play's billing for digital goods "unless
  Section 3, 8, or 9 applies", and must not use it "for the purchase or
  rental of physical goods", "for the purchase of physical services", for
  a credit card or utility bill, or for "peer-to-peer payments, online
  auctions, and tax exempt donations"; "In some markets, we offer Google
  Pay for apps selling physical goods and/or services"
  ([Payments policy](https://support.google.com/googleplay/android-developer/answer/9858738)).

**exact2 checks none of it.** Nothing on the device can tell a print
from a premium feature, and the rules are the stores', applied in review.
The package's README and the recipe state the line and send digital
goods to `@exact/purchases`; `contract vocab showPaymentRequest` says so
in its first line. The web has no store, and an app may sell what it
likes there; an app that ships the same screen natively is held to the
stores' rules on those targets, which is the app's to keep, as a
hand-built app's is.

## 6. Permission and origin

### D13 — No permission; the grant lines name the merchant

No platform asks a runtime permission for a wallet: the sheet, confirmed
with Face ID, Touch ID or the device's lock, is the consent each time. So
the module declares no `permission`. It does need the merchant named at
build:

| Line | Derives | Admission |
|---|---|---|
| `payment.apple-pay <merchant id>` (`merchant.com.example.app`; one line per merchant ID) | iOS and macOS: the `com.apple.developer.in-app-payments` entitlement listing every granted ID ([entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.in-app-payments)); web: the association-file warning (D8) | an Apple Pay method's `merchantIdentifier` must be a granted ID, else `SecurityError` before the sheet, as passkeys match `rp.id` (LLP 1133.011 D6) |
| `payment.google-pay` | Android: `<meta-data android:name="com.google.android.gms.wallet.api.enabled" android:value="true"/>`, the callbacks service (D5) | a Google Pay method needs the line, else `NotSupportedError` |

A binding call or a Contract use with neither line refuses at bake
(`grant-missing`). The entitlement needs a profile for an explicit App ID
with the Apple Pay capability, on iOS and on macOS, where Apple Pay is a
Developer ID capability as well as a Mac App Store one
([supported capabilities](https://developer.apple.com/help/account/reference/supported-capabilities-macos));
exact2's Mac releases are Developer ID, and a Mac build with a profile is
LLP 1133.010 D7's open step. A Mac bake without one marks the module
unavailable and the journal says why.

### D14 — Who may pay, and spending is not delegable

| Origin | `showPaymentRequest`, `addPasses`, `savePasses` | `paymentRequestStatus`, the pass facts |
|---|---|---|
| a person's input; the app's own foreground code | the wallet's sheet (D15) | answer |
| a tool invocation (LLP 1111) | fails `NotAllowedError`, `person-required`, before the wallet is reached | answer |
| a background wake; a headless session | fails `person-required` | answer |
| the app in the background | fails `NotAllowedError` (`"foreground": true`) | answer |
| a handler called by `invoke` | `person-required` (its origin is at most `tool`, D5) | answer |
| the development agent | §9 | §9 |

**Spending is not delegable,** as LLP 1133.015 D14 rules for a store
purchase: a payment spends the person's money with a card in their
wallet, confirmed by them in the wallet's sheet. No delegation record
lets a tool start one, as no record satisfies a presence check (LLP
1133.010 D12). An agent that wants the person to buy something asks
through the app's own UI, from whose button the person pays.

### D15 — One sheet at a time, over the session's window

`showPaymentRequest` and the pass sends join LLP 1133.002 D9's queue of
decisions natively, each held until the platform reports its sheet
closed, and are never shared: two queued payments show two sheets. The
web cannot wait (D8).

The sheet is presented over the session's window: on Apple the
controller's delegate answers
[`presentationWindow(for:)`](https://developer.apple.com/documentation/passkit/pkpaymentauthorizationcontrollerdelegate/presentationwindow(for:))
with the window of the package context's `presentation` (LLP 1133.027
D17 item 3), and a call while it is nil, or while the session's scene is
not active or its window not key, fails `NotAllowedError` at once (LLP
1133.027's reading of LLP 1133.015 D15); on Android `loadPaymentData`'s
result is delivered through the session's activity
(`ExtensionContext.startActivityForResult`, LLP 1133.018 D13), since
`ExactActivity` is a plain `Activity` and Google's
`TaskResultContracts.GetPaymentDataResult` is an Activity Result
contract (its predecessor `AutoResolveHelper.resolveTask` is
deprecated); stage 3 settles which of the two drives the activity there.

`NotSupportedError`, so the photo editor shows no Order a Print row. An
app that sells there takes card details through its processor's own
form, which is not this module.

### D21 — What each wallet requires before anything works

| | Development and test | Production |
|---|---|---|
| iOS | a merchant ID and an explicit App ID with Apple Pay; a development profile; Apple's sandbox: a Sandbox Apple Account from App Store Connect signed in on a test device, with Apple's test cards in Wallet ([sandbox](https://developer.apple.com/apple-pay/sandbox-testing/)); the simulator, where "Running in Simulator doesn't require a card" ([sample](https://developer.apple.com/documentation/passkit/offering-apple-pay-in-your-app)) | an App Store build; a payment processing certificate, whose key the app's processor holds |

| Android, Chrome | `TEST`, with a Google account on the device that has joined the test card suite group, so the sheet offers Google's test cards and "the API doesn't return card data capable of a transaction" with the `example` gateway; no registration | the Google Pay & Wallet Console's production access; until then "An `Unrecognized App` error appears on the Google Pay payment sheet" |

So the module builds and is driven under the agent with no account
(§9), and every real drive needs accounts Charlie creates (§13 question
7). Production waits for the app's processor, which is the app's.

### D22 — Cost

An app that does not import the package links nothing of it: no PassKit,
no Play services wallet, no merged service or meta-data, no web chunk
(LLP 1047.001). One that does loads the implementation with the app's
module after first pixel; nothing runs before it. PassKit is a system
framework the module dylib links, never the executable. Stage 3 records
the APK size the wallet and pay libraries add after R8 and the artifacts
the graph gains; stage 1 the dylib's size; stage 2 the web chunk's,
including Google's button assets.

## 9. The substitute, and the wallets' test environments

| | What runs | What it proves | Who uses it |
|---|---|---|---|
| **the substitute** | the runner's ceremony, the app's real handlers and its fixture server, no wallet | the app's flows: quoting, errors, retry, cancel, supersession, timeouts, origins, the token kept out of state | every drive (§10) |
| **the platform's local sheet** | iOS simulator with `--bind payments`: the real controller and sheet with no card | the Apple implementation's PassKit code and its delegate | stage 1 |
| **the wallet's test environment** | Apple's sandbox on a device and in Safari; Google Pay `TEST` on an emulator with Play services and on a phone, and in Chrome | the whole path, a token reaching the fixture server | by hand, Charlie or Daehyeon (§10 drive 12) |

**A declared substitute, in the runner.** The sheet is held as a
`payment` ceremony (LLP 1133.011 §9) on every target, so one
implementation of the synthetic sheet serves the web, Apple, Android and
the Linux host, and the drive's handlers are the app's own data code
through the runner's `invoke`. The implementations make no request,
present nothing and call no hatch under the agent.

**The ticket's `args`:** the target's method (by D4's rule over the
preferred status), the total and display items as the sheet would show
them, the shipping options with the selected one, the requested contact
fields, any `error` and field errors the last handler gave, the session
and the origin. Never a token.

| Event | Result |
|---|---|
| `showPaymentRequest` from a foreground app origin, admitted | a `payment` ticket; on the web with an Apple Pay method, `onmerchantvalidation` is first called with a fixture validation URL, and an empty answer fails the call `OperationError` as Safari would |
| `type @t {"shippingAddress": {…}}` | the address, redacted by D2's rule, to `onshippingaddresschange`; its update over the ticket's `args`; an `error` or field errors shown there |
| `type @t {"shippingOption": "express"}` | `onshippingoptionchange` likewise |
| `type @t {"paymentMethod": {…}}` | `onpaymentmethodchange` likewise (an Apple card type or coupon code) |
| `tap @t authorize` | a synthetic payment: `details` `{"exactSubstitute": true, "transactionId": n}` (a counter the session's seed fixes), the last address in full, a fixture payer; `onpaymentauthorized` is called with it; `success`, `fail` and `unknown` retire the ticket and answer the send; `retry` keeps it with the errors |
| `tap @t cancel` | `AbortError`, before authorization only |
| the call let go before `authorize` | the ticket retires; `AbortError`; no handler is called |
| the call let go after `authorize` | the handler runs on; its answer is journaled and dropped (D6) |
| `clock +30000` with a handler outstanding | D5's bound: an update leaves the ticket as it was with `error` "unavailable"; an authorization fails `authorize-timeout` |
| `prefer extension payments.paymentRequestStatus={"available":false}` | every send `NotSupportedError`; the button draws nothing |
| a tool-origin or wake-origin call | as production: `person-required`, no ticket |
| a second call while a ticket is held | natively, held behind it; on the web, `busy` |

There is no `prefer` that pays: each payment in a drive is a tap, so the
transcript shows every place a person would be asked to pay. The
fixture server takes a substitute token only when started with
`--agent`, and a production server is told by the recipe to refuse
`exactSubstitute` outright.

**Never a real card.** A drive under the agent reaches no wallet.
`--bind payments` is allowed on the iOS simulator, which has no card, and
on Android, where every bake that is not production writes Google's
`TEST` environment, which returns only test tokens; on a device it runs
only through the checklist, which starts by checking that a Sandbox Apple
Account or a test-suite Google account is the one signed in. And the
fixture print server never sends a token to a processor: it records the
order and the token's length, so no card is charged whatever is in the
wallet.

**Disclosure:** `state.extensions` lists `payments`, its binding per
target, each ceremony's request id, method, total, origin and outcome,
and each handler's name, duration and answer kind; never an address
line, a payer's details or a token.

**Production:** none of it.

## 10. The consumer: Order a Print

The photo editor edits a photo and saves it to the library (LLP 1133.019
§11). A print of the edit is the most ordinary physical good an editing
app sells, and the clearest case of App Review's 3.1.3(e): the print is
made and mailed outside the app, so in-app purchase may not be used. The
editor gains:

- **Order a Print,** a row under Save to Photos, shown while
  `wallet.canMakePayment`: a sheet with the sizes (4×6, 5×7, 8×10), their
  prices, and `exact-payment-button type="order"`;
- **`printCheckout(size)`,** a data-code resource that fetches the price
  from the print server and answers the method data (Apple Pay for
  `merchant.com.exact.photoeditor`; Google Pay with the `example` gateway),
  the details and `requestShipping`, `requestPayerEmail`;
- **`quoteShipping`,** which posts the redacted address to the server and
  answers its shipping options (Standard everywhere it ships, Express in
  the United States) and total, or a `country` error where it does not
  ship;
- **`placeOrder`,** which renders the edit with `transformImage` (LLP
  1133.019), posts it with the token, the full address and the email to
  `/orders`, and answers `success` with the order id, `fail` on a
  decline, or `retry` with the server's field errors;
- **Orders,** a list read from the server's `/orders`, which is what the
  confirmation shows, so a payment completed after its screen went away
  is still there;
- **`apps/photo-editor/fixture/prints.ts`,** a Bun server: `/quote`,
  `/orders` (it validates the shape of the method's `details`, records
  the order and never forwards the token), `/apple-pay/session` (merchant
  validation, which posts to Apple's sandbox gateway when given the
  merchant identity certificate's path, and answers 503 otherwise), and
  fault switches for drives (`--decline`, `--reject-postal`, `--slow`).

The grants: `payment.apple-pay merchant.com.exact.photoeditor` and
`payment.google-pay`, in `app.ts` beside its others.

The photo editor has no Android port: `rules/DEFERRED.md`'s camera record
took it as the camera's take. So Android's drives run the package's
conformance fixture, a one-screen checkout of a print against the same
server, with an Android crate (as the camera's fixture does).

**Acceptance drives,** under the agent on the web, macOS and the iOS
simulator with the photo editor, on the Android emulator with the
fixture app, and on Linux headless (ticket ids are read from
`state.pending`; `@t` stands for each):

1. `tap order-print`; `tap size-8x10`; `tap pay`; `type @t
   {"shippingAddress":{"country":"US","region":"CA","city":"Palo Alto","postalCode":"94301"}}`:
   the ticket's total gains Standard shipping; `type @t
   {"shippingOption":"express"}`: Express's total; `tap @t authorize`;
   `clock settle`: the confirmation with the order id, the server's
   `/orders` listing it with the full address, and no state, journal line
   or `state.extensions` entry containing `exactSubstitute`.
2. An address in a country the server does not ship to: the ticket shows
   the `country` error and no options; a US address then clears it.
3. `--reject-postal`: `authorize` answers `retry`; the ticket stays with
   the `postalCode` error; a corrected address and `authorize` again: one
   order.
4. `--decline`: `authorize` answers `fail`; the screen says the payment
   did not go through; no order.
5. `tap @t cancel`: `AbortError`; back to the size sheet; no order.
6. Leave the sheet's screen before `authorize`: the ticket retires and no
   handler runs. With `--slow`, leave it after `authorize`: the order
   completes on the server, the journal says `completed after its call
   ended`, and Orders lists it.
7. `--slow` past the bound: `clock +30000` fails `authorize-timeout`;
   Orders shows what the server did.
8. A tool-origin call (a runner test through `Runner::act_from` until a
   door makes one): `person-required`, no ticket.
9. On the web with the Apple Pay method first: `onmerchantvalidation` is
   called before the ticket's first update; a call with no such handler
   refuses `payment-merchant-validation` at admission.
10. `prefer extension payments.paymentRequestStatus={"available":false}`:
    no Order a Print row; on Linux headless (the photo editor's Linux
    crate, the module optional) the same with no `prefer`.
11. On the Android emulator, the fixture app: drives 1, 3, 5 and 7.
12. By hand, with the platforms' test environments only (§13 question
    7): on an iPhone signed in to a Sandbox Apple Account, with Apple's
    test Visa in Wallet, an 8×10 print paid with Face ID, the sheet's
    shipping update, and the token reaching the fixture server; the same
    on the iOS simulator with `--bind payments`; on a Mac with Touch ID
    and a provisioned build; on an Android phone signed in to a test
    account that has joined the test card suite, with Google's test card,
    and the token reaching the server; in Chrome with Google Pay `TEST`
    on `localhost`; in Safari on the public origin with the sandbox
    gateway, once that origin exists.

Drives 1–11 run the substitute; the conformance suite runs the real
implementations (§12).

## 11. What this amends, and what stays out

**Amends:**

- **LLP 1133.011 §9:** a ceremony may ask the app while it is held
  (`asks`, D16 item 3).
- **LLP 1133.016 D9 item 1:** `invoke` anchored on a pending call, a
  final handler that outlives its call, the cause `payment`, and `invoke`
  on Android (D16 items 1 and 2).
- **LLP 1069.008 D2:** the grant family `payment.*` (D13).
- **LLP 1133.001 D1:** the declaration types `handler` and a `json`
  checked by a discriminant's schema (D16 item 4).
- **LLP 1133.000 §3.7:** payments' row: tier 1 adds the shared words of
  D3; its wave is done at Charlie's request; its tvOS, Windows and Linux
  cells are `absent`.
- **`rules/DEFERRED.md`:** the purchases record's "payments for physical
  goods" moves to this module's record (§13 question 9).

**Stays out,** each until a consumer asks:

- Card entry without a wallet, and any processor's SDK.
- A payment server of exact2's, decrypting tokens or talking to a
  processor: the app's server talks to its processor, as LLP 1133.015 D8
  has the app's server talk to its store.
- Apple Pay's in-app provisioning, Tap to Pay on iPhone, disbursements,
  identity verification with Wallet, and Apple Pay Later's merchandising
  views.
- Secure Payment Confirmation and the web's payment handlers.
- Native merchant session updates
  (`didRequestMerchantSessionUpdate`), which Apple documents with no case
  an in-app merchant needs.
- An "Add to Apple Wallet" button view (`PKAddPassButton`), until an app
  adds passes from its own screen.
- The watchOS and visionOS cells.

## 13. Questions for Charlie

1. **Handlers through `invoke`, with the token in the authorize
   handler's argument alone (D5, D7),** rather than Payment Request's
   two-phase `show()` then `complete()` in data code. *Recommended: yes
   (75%).* The two-phase form keeps the W3C's shape for data code, but
   on the web data code cannot reach `show()` inside the press (D8), and
   on Android the authorization's outcome is only a callback. The cost is
   a declared deviation and D16 items 1 and 2.
2. **A final handler outlives its call (D6).** *Recommended: yes (80%).*
   The alternative, cancelling the handler with its call, can leave a
   card charged and the sheet saying it failed.
3. **The 30-second bound everywhere (D5),** Google's limit, rather than
   each platform's own (Apple and the web state none). *Recommended: yes
   (65%).* One behaviour on every target; a handler slower than that
   fails on Android anyway.
4. **The substitute in the runner, as a ceremony that asks (§9),**
   rather than each implementation as its own substitute.
   *Recommended: yes (70%).* One synthetic sheet serves every target,
   Linux included, and the handlers it calls are the app's own; the
   implementations stay pure platform code.
5. **Photo Editor's Order a Print as the consumer (§10),** with the
   package's fixture app for Android. *Recommended: yes (70%).* No app
   sells a physical good today; a print is the plainest 3.1.3(e) case
   and the editor already renders the edit. The alternative, Shelf's
   "buy this book", runs on Android but makes the app a bookshop's.
6. **Wallet passes (D10): build stage 4 now, or when an app adds a
   pass.** No app needs a pass today, and both platforms need an issuer
   account to sign one. *Recommended: design now, build when a consumer
   asks (60%),* keeping §12's stage 4 as written for then.
7. **Accounts** (never a real card; the checklist names each). For the
   real drives, Charlie creates or approves:
   - **Apple:** a merchant ID `merchant.com.exact.photoeditor` on the
     team, with a payment processing certificate (kept by Charlie, not
     committed; the fixture needs it only to try decryption) and a
     merchant identity certificate for Safari's merchant validation (its
     key given privately); the Apple Pay capability on the explicit App
     IDs `com.exact.photoeditor` and the conformance fixture's; a Sandbox
     Apple Account (App Store Connect, Users and Access, Sandbox), signed
     in on a test iPhone and a Touch ID Mac, with Apple's sandbox test
     cards; for Safari, the public origin registered and verified as a
     merchant domain (LLP 1133.020 §3.1); for stage 4, a Pass Type ID and
     its certificate.
   - **Google:** a Google test account (LLP 1133.020 §3.2's) that has
     joined the Google Pay test card suite group, signed in on the
     Android test phone, the emulator's Play image and a Chrome profile.
     `TEST` needs no Google Pay & Wallet Console registration. For stage
     4, a Google Wallet issuer account in demo mode and a service account
     to sign pass JWTs, in the testing Cloud project, its key given
     privately.
   *Recommended: yes, the Apple merchant ID and the Google test account
   first (they unblock stages 1 and 3's real drives); the Safari pieces
   with the public origin.*
8. **Google's environment chosen by the build (D4, §9):** `TEST` in
   every bake but production, an authored `environment` refused.
   *Recommended: yes (85%).* exact2 cannot otherwise promise that a
   drive never charges a card.
9. **`DEFERRED.md`.** The purchases record keeps "payments for physical
   goods" out until a consumer asks. Proposed: an "Expanded" record
   admitting payment for physical goods and services by Payment
   Request's names through Apple Pay and Google Pay (`@exact/payments`),
   on the web, iOS, macOS and Android, with tier 2's Wallet passes;
   consumer Photo Editor's Order a Print; §11's stays-out list as its
   "Still out"; and that item removed from the purchases record. *Take:
   none offered;* a waiver, as purchases' and the language model's
   records had, or Charlie names one.
10. **D16's five seam additions** as apparatus admitted with this
    ruling. *Recommended: yes.*
