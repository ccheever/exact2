# LLP 1091.002: A component's members across files

**Type:** RFC
**Status:** Accepted by Charlie (2026-10-25: "yes seems like a good idea", on the panel's recommendation), stage 1 built the same day
**Systems:** Contract syntax (`contract/syntax/src/{parser,parser/component.rs,members.rs,scope.rs,spans.rs,fmt.rs}`), the loader (`contract/cli/src/sources.rs`, `sources/members.rs`), the duplicate-member refusal (`contract/types/src/component.rs`), `docs/contract-grammar.md`
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-10-25
**Amends:** LLP 1091 (Contract modules): a second way a file is loaded, besides `use`
**Answers:** `issues/20261025-a-large-root-component-cannot-meet-the-line-cap.md` (#1013), ask 1
**Related:** LLP 1017.002 (only the root owns requests and timers); `rules/RULES.md` (1,500 lines per source file). Reviews: the panel on the issue, `llp/reviews/issue-2026-10-25-1013.{astra,grok,fable}.md`

## Summary

A component may write some of its members in other files. A `members "./composer.contract"`
line in the component's body stands for the members that file declares under `members T3Code`,
as if they were written at that line. Nothing after the loader sees a difference: the program,
and so the plan, is the one-file program. Each file counts against the line cap on its own.

## Motivation

The T3 Code clone's root, `examples/t3-code/app.contract`, is 2,998 lines: 307 actions, 269
states, 104 tasks, 85 resources, 44 mutations and a one-line view. Its view already lives in
child components, and three rules keep the rest in the root: only the root owns resources,
mutations and tasks (`docs/contract-grammar.md:310`); a task's schedule names a parameterless
action of the same component (`:291-292`); and `send` names a mutation of the same component.
Moving members into children moves the same closure to whichever ancestor still sees every name
it reads (the root's `resource data` and `derive transportAnswering` read every feature), so the
file stays above the cap. The issue measured the floor at about 1,800 lines.

The rule that keeps requests in the root exists so that a row component cannot silently open N
requests (LLP 1017.002). A file boundary has nothing to do with that, so the fix is to let one
component's source span files, and leave ownership as it is.

## Design

**D1. The line.** In a component's body, `members STRING` names a `.contract` file whose
members join this component. The path follows a relative `use` path's rules: `./` or `../`,
inside the app or the package the file belongs to (`contract-use-path`). A component may have
any number of `members` lines, each naming a different file.

**D2. The file.** A members file holds one `members IDENT` block, indented like a component's
body, whose name is the component that lists it (`contract-members-owner`). Beside it the file
may have `use` lines and any declaration a file may have (`shape`, `fn`, `style`, a
`component`); those are its own, scoped as any file's (LLP 1091 D1). A file is listed by one
`members` line in the program (`contract-members-twice`), and a file with a `members` block
that no `members` line lists is refused (`contract-members-unlisted`).

**D3. What a block may hold.** `state`, `derive`, `resource`, `mutation`, `action`, `task` and
`sequence`. The sections a component has once (`props`, `inject`, `provide`, `slot`, `view`,
`params`, `parts`) are written in the component's own body, and so is every `members` line: a
members file lists none (`syntax-members-section`).

**D4. Meaning.** A `members` line is replaced by its block's members, in the order the block
writes them, at the line's place among the component's own. The program is the one a single
file with those members written at that line compiles to, and the plan is byte-identical to it
(the test `component_members_across_files_compile_to_the_one_file_plan`). Order matters only
where it does in one file: a state's initializer reads the states before it.

**D5. Names.** A component's members are one namespace across its files. Every file of the
component sees all of them, and the component's props and injects, as its own body does. A
name declared in two of its files is refused naming both (`contract-members-duplicate`); two in
one file stay `type-duplicate-name`. A file's other
names (the shapes, `fn`s, styles and components it calls) resolve through that file's own `use`
lines, so a members file `use`s what it needs as any file does, and `contract fmt --uses` fixes
each file's lines separately.

**D6. Everything else is the component's.** Identity (`{home}#{name}`, LLP 1121 D15),
`persist`, dev reload carry and the root-only rules (`type-child-resource`, LLP 1017.002) apply
to the assembled component: a members file of a child component may not declare a resource,
just as the child's own body may not. Every refusal points at the file and line the member is
written in, since each token's span keeps its file. `contract sources` lists members files, so
the dev loop and `build.rs` rebuild when one changes, and navigation reports a member where it
is written.

**D7. The line cap.** Each file counts on its own (`rules/RULES.md`). No exemption is added.

## Not chosen

- **Resources, mutations and tasks in a child that stays mounted (the issue's ask 2).** It
  changes when requests open and close, and needs instance-owned timers and requests in the
  expander, the runner and the Lean semantics. It also would not shrink this root: most of its
  tasks and resources are app-wide. Instance-owned requests remain worth designing for screens
  on `stack(nav)` (LLP 1035.005.000 D5); this RFC neither needs nor blocks that.
- **A named exemption (ask 3).** `rules/RULES.md` says a limit gets exceptions and a trade does
  not, and `caps.mjs` can only allow an unnamed count of oversize files.
- **A nameless `use "./x.contract"` that loads a file's `extend` blocks.** It works, but it gives
  `use` a second meaning and lists the parts at the top of the file, away from the component
  they extend and from the place they join it.

## Stages

1. The syntax, the loader, the refusals, the formatter, the grammar page and tests: the split
   app compiles to the one-file plan; refusals name the right file; members are visible across
   files; a child's members file cannot own a resource.
2. The T3 Code clone's root split by feature (composer, stream, transport, cite, pull requests,
   settings), each file under the cap, on the clone's branch.
