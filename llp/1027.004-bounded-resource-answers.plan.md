## 1. Priority and scope

Charlie directed us to keep and ship the small value-transfer fixes and write up
bounded answers on 2026-09-18. The priority is to make large-history interaction
cost depend on the requested window and changed data, starting with Messages.
This document records that priority and proposes the implementation sequence;
it does not claim pagination, deltas or a new resource protocol have shipped.

First return a bounded, ordinary immutable value through the existing data seam.
Keep the small conversion fixes underneath it. Shared views, typed buffers and a
mutable shared heap remain research; none is required for the first slice.

**Trade:** move further shared-representation optimization and generic arrival-time
structural reconciliation behind proving bounded answers in Messages. Use the
existing app and Messages stress consumer, agent operations and five checks. No
new benchmark app, scheduler, shared state graph or permanent feature matrix.
This plan takes the working-set slot previously used by language parity; the
completed transfer research stays in the corpus. Both remain linked context.

## 2. Why this comes first

The actual Messages stress runner comparison in LLP 1027.003 §9 found:

- Whole-resource answers cause N rows to be keyed after an edit, even when
  unchanged subtrees reuse their previous allocations.
- Reusing an equal root avoids that keying only when the entire answer is unchanged.
- The existing 100-row paged source keys 100 rows at 1,000, 10,000 and 100,000
  total messages. That is a manually selected page, not automatic viewport paging.

The observed 100,000-row edit medians were roughly 0.3 ms for a page versus
78 ms for a fresh whole answer. Shared-machine timing is diagnostic; work counts
establish the scaling result. These runs exclude TS crossing and host painting.
The B/C/D experiments exposed representation costs and a retained-data benefit,
but did not remove whole-resource publication or settlement work.

LLP 1010's current windowing bounds mounted rows and views. It explicitly allows
O(N) input records and metadata. This plan addresses the input/query/answer cost
as a separate layer; a small DOM is not evidence that the data path is bounded.

## 3. First slice: bounded immutable pages

### D1 — Bound work at the producer

Use Messages' existing ordered message identity and storage query facilities to
request a page around an anchor. Do not build, sort, decorate or serialize all N
messages and then slice the answer. Where an initial index is needed, measure its
construction separately and update it incrementally; never hide rebuilding it in
a page request. Identify the actual storage API against the then-current Snapback
version before implementing: the concurrent client migration is not assumed here.

A first candidate uses 100 rows per page and at most three resident pages,
including visible rows and overscan. Add a one-MiB encoded-answer budget per page
and an aggregate admitted in-flight/cache byte budget; these are starting design
values to validate, not implemented runtime defaults. Count scalar/string bytes
and envelope overhead as well as rows. A single oversized body must use an
explicit bounded preview/detail request or a clear refusal; never silently lose
stored text or run an unbounded decode before checking admission.

If storage cannot fetch a range without scanning or materializing the history,
report that producer cost and fix the query/index first. Returning fewer bytes
alone is a useful partial improvement, not completion of this slice.

### D2 — Make page identity and invalidation explicit

A page result carries its conversation identity, ordering anchor, continuation
information and source revision with the rows. The exact Contract shape is chosen
with the implementation; this document does not add syntax or an ABI.

Prefer stable key/order cursors over mutable numeric offsets. Define behavior
when an anchor is deleted or reordered: retain the nearest surviving keyed anchor
and its visual offset, or use a declared end-of-history fallback. A prepend must
not jump a reader to the newest message. A reader already following the tail may
continue following it; a reader in old history sees the new-message affordance.

A mutation refreshes affected resident pages and necessary small metadata. It
must not download every historical page. A global revision can detect staleness,
but must not become an instruction to rebuild the entire history. A cheap source
revision or retained immutable page can avoid answering again when nothing relevant
changed; no generic whole-value deep comparison is introduced for that purpose.

Keep drafts, sync state and conversation summary separate from bulk row answers
where their lifetimes differ. Reply counts, unread counts and quoted-message
lookups cannot secretly scan the full history on every visible-row edit. Maintain
or query the needed aggregates and request off-window details by identity.

### D3 — Preserve the runner's transaction and ownership rules

Values remain immutable. Source owners compute answers; the runner validates and
commits them. Existing Store ordering, grants, errors and rollback semantics from
LLP 1027.002 D3 remain unchanged. A page is not a live mutable object shared with
Contract, and a loading placeholder must not erase a committed page.

Bind each asynchronous answer to its conversation, request and module incarnation.
Late results for an old window or conversation cannot replace current content.
Bound outstanding requests and retired-result ownership, deduplicate overlapping
requests, and preserve existing cancellation semantics: cancellation does not undo
an external effect that already happened. Rapid scrolling/replacement must not
accumulate a hidden cache of every visited page.

Use stable row keys across page boundaries. Preserve draft text, focus, selection,
replies, pending sends, deletion/recovery and viewport anchors. Any rows pinned for
interaction count against an explicit bounded budget; they are not an unlimited
exception. Keep the durable store authoritative when a page is evicted.

### D4 — State exactly which memory is bounded

Account separately for queried records, decorated answers, conversion scratch,
queued replies, retained pages, runner input, mounted rows and host objects.
Existing database state and any initial O(N) index are separate retained costs.
If the app still loads all durable records into its TS model at startup, say so;
a bounded result does not make total process memory O(window).

Measure transition peaks while old and new pages coexist, repeated traversals,
held selections and leaving/reopening a conversation. Cache limits apply to the
session total, not independently to every page or previously visited conversation.

## 4. Implementation order and acceptance

| Slice | Work | Evidence required before proceeding |
|---|---|---|
| 0 | Land the selected conversion/kept-answer/Messages fixes | Clean integrated checks and real native/browser execution; retain the old cost attribution |
| 1 | Implement a bounded Messages query and explicit paging with ordinary values | Exact page contents/order, count and byte admission, producer work counters, no lost edits; visibly label manual paging if that is what exists |
| 2 | Connect bounded requests to the actual scrollport and retain keyed anchors | Top/middle/tail scrolling, prepend/delete, width change, focus/selection and async replacement pass on browser and native |
| 3 | Retain unchanged pages and invalidate only relevant resident data | Unrelated edits avoid re-query/settlement; affected edits publish correct bounded pages with bounded retained ownership |
| Conditional | Consider keyed deltas within a page | Only if measured page publication/settlement still materially harms the interaction budget |

Run the existing Messages and Messages stress consumers at 25 / 1,000 / 25,000
rows, with a 100,000-row scaling check where practical. Use identical viewport,
seeds and action sequences. Cover an unchanged refresh, one visible edit, an
off-window edit, prepend, deletion of the anchor, recovery, send refusal, rapid
scroll, conversation switch, module replacement and offline/reconnect behavior.
Include a huge single string, many small rows and actual reply/selection cases.

Record producer records visited, rows decorated, answer bytes, allocation/live
and peak ownership, rows keyed and mounted, and host work. Time acquisition,
producer computation, crossing, settlement and visible update separately. Keep
raw samples and source/binary identities. A byte reduction or microbenchmark is
not a frame-rate claim; physical iPhone claims require physical measurements.

For fixed row/byte budgets and a fixed viewport, steady-state page edits and
scroll steps must not acquire an N-sized answer, decorate N rows or key N rows.
A storage index lookup may be O(log N); initial index construction and whole-model
sync costs must remain visible rather than being mislabeled O(1). Report both
absolute interaction latency and how counted work changes with N. The first slice
is complete only when both the data path and the existing UI semantics pass.

## 5. Deferred choices and return triggers

Keyed deltas require a base revision, insert/update/delete ordering, duplicate-key
rules, atomic application and resynchronization on mismatch. They may reduce
O(window) publication to O(changed), but are a separate design only after paging
shows a remaining bottleneck. They must not expose partial application to Contract.

Reconsider an immutable view or retained Rust representation when a real app
repeatedly reads a small part of Rust-owned data after bounded queries and the
small fixes. Reconsider a buffer only with complete ingestion, decoding,
publication and lifetime accounting. The heap also owes safe alias lifetime,
transaction/reload semantics and a comparison against the improved conversion
path. None is selected merely because a handle operation is cheap.

The first implementation must resolve the storage cursor/index API, page and
aggregate byte limits, exact oversized-message presentation, and anchor fallback
under deletion/reorder. These are bounded product decisions for Messages, not
permission to create a general cache, scheduler or second application-state graph.
