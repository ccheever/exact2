## 1. Decision

Opening, editing and scrolling a long conversation should cost in proportion to
the rows a reader can reach in one gesture. The length of the history should not
matter. Charlie set this priority on 2026-09-18, after LLP 1027.003 §9.

The mechanism combines three small pieces with what already exists:

1. **The window is the resource.** A conversation resource's arguments include a
   cursor, and its answer is at most K rows plus the cursors next to them. The
   runner already keeps one request per resource, drops stale answers, and keeps
   the committed value while a new one is pending (LLP 1016 D3, D5). This plan
   adds no page cache, page bookkeeping, delta protocol or in-flight budget.
2. **The virtualized list reports its edges.** `list virtualized=true` gets two
   events, `reachstart` and `reachend`. The runner dispatches one when the
   realized window reaches the first or last supplied row. The Contract responds
   by moving the cursor, and the collection's existing key anchor keeps the
   reader's place while the rows change underneath (LLP 1010 §6.2, §6.5).
3. **Each answer costs the producer O(log N + K).** Each consumer maintains the
   ordering index and the aggregates its rows display, so answering a window
   never walks the history.

**Trade:** further shared-representation tuning and generic arrival-time
structural reconciliation wait until bounded answers are proven in Messages
(`rules/NOT-DOING.md`, 2026-09-18). The only new Contract surface is the two
event names. They are the one plan-format change (two `EventKind` entries in the
format table). There is no Value, data-seam or host wire change, and no
benchmark app, scheduler, shared state graph or feature matrix.

## 2. Evidence, and what it does not show

LLP 1027.003 §9 ran the actual Messages stress Contract and runner. A 100-row
page keyed 100 rows at 1,000, 10,000 and 100,000 messages. A whole-history
answer keyed N rows after every edit, even when subtrees were reused, and
equal-root reuse helped only when the whole answer was unchanged. At 100,000
rows the edit medians were about 0.3 ms for a page and 78 ms for a fresh whole
answer. Those times came from a shared machine; the work counters, not the
times, establish the scaling. The runs excluded TS crossing and host painting.

LLP 1010 §6 bounds mounted rows, kernel nodes and host views, but it explicitly
allows O(N) input records and key metadata. After a membership change the
collection validates every supplied key. A small mounted tree therefore says
nothing about the data path. This plan bounds the input.

Slice 0 has landed: the conversion, kept-answer and Messages read-path fixes are
on `origin/main` at `7e77aaf`, with the five checks and Messages web/Linux drives
(LLP 1027.003 §10).

## 3. Design

### D1: The window is the resource

A windowed resource takes a `cursor` argument. Its answer is an ordinary
immutable record:

- `rows`: at most K rows
- `earlier` and `later`: cursors
- `hasEarlier` and `hasLater`: booleans

The window holds K rows centered on the cursor's position, clamped to the history.
An empty cursor `""` means the latest K rows. `earlier` is the cursor of the
current first row and `later` the cursor of the current last row. Moving to
either one recenters the window on that row, so after a shift the reader sits
K/2 rows from both new edges. K is a constant for each consumer, starting at 200.

A resource holds at most one committed answer and, for an async source, one
request in flight; LLP 1016 D5 already drops an answer for superseded
arguments. Leaving a conversation and coming back resets to the tail. No cache
of visited windows exists anywhere. When `revision` changes, the window is
answered again at O(K) cost. Reusing unchanged windows is deferred (§5).

### D2: Cursors name positions in the order, never offsets

The source builds a cursor as an opaque string from its ordering key: the
synthetic index for Messages stress, and `order` for Messages. The Contract
stores cursors it received and passes them back; it never computes one.

To resolve a cursor, the source binary-searches for the first surviving row at or
after that position, or takes the last row if the position is past the end. If
the anchor row was deleted, the window lands on its nearest neighbor, so a
cursor never silently turns into the tail. A malformed cursor is refused as bad
arguments.

An empty cursor follows the tail: new rows append, as they do today. A reader
holding a non-empty cursor is never moved by arrivals. Opening a conversation,
sending, and an explicit "latest" control reset the cursor to `""`.

### D3: `reachstart` and `reachend` on a virtualized list

The geometric window is the set of rows that intersect the scrollport plus the
collection's existing one-viewport overscan. Rows kept alive only by a focus or
interaction pin don't count. After the host has reported real geometry, the
runner dispatches `reachstart` when the geometric window contains the first
supplied row, and `reachend` when it contains the last. A list that declares
neither handler dispatches nothing, so every existing virtualized list behaves
exactly as before.

- **Edge-triggered.** Each edge starts armed and disarms when it fires. It re-arms
  when its row leaves the geometric window or when the first (or last) supplied
  key changes. Each collection dispatches at most one edge event per feedback
  call, so a list filled with tiny rows loads at the host's feedback rate rather
  than in a synchronous loop. A viewport resting at an edge with nothing left to
  load never dispatches again.
- **No per-host edge logic.** The runner dispatches the handler as an ordinary
  action after the feedback commit, inside the host's existing feedback call.
  That action can be refused after the feedback has already committed, so the
  feedback call returns the committed receipts together with an optional action
  error, the same shape `advance_timed` already returns. The Rust wrappers for web,
  Apple and Linux consume both, and hosts that match `EventKind` exhaustively
  get a no-op arm for the two runner-only kinds. The wire formats are unchanged.
  Feedback that only moves the offset and reaches no edge still runs no query and
  evaluates no key.
- **Spelling.** The names follow the existing lowercase events (`swiperight`,
  `contextmenu`) and the web's `scrollend`. CSS has no equivalent; the nearest
  web pattern is an IntersectionObserver sentinel, which the runner implements
  once for every host. LLP 1010 §6.5 records the events when they land.
- **Handlers.** A handler moves the cursor: on `reachstart`, if
  `hasEarlier`, set the cursor to `earlier`; `reachend` mirrors it with `later`.
  The list keeps its anchor key and offset across the change in membership.

### D4: Producer bounds for each consumer

**Messages stress (Rust).** The synthetic rows are O(1) by index, so a window is
a direct slice. The existing manual-page, eager and full-history virtualized modes
stay as controls. The new bounded mode proves the runner, Contract and
collection path at 1,000, 10,000 and 100,000 rows.

**Messages (TypeScript).** The conversation answer must not visit rows outside
the window. Each thread maintains:

- its rows sorted by `order`, so cursors resolve by binary search
- an id-to-row map, for selection and reply parents
- a reply count per root, and each root's rows for the reply sheet
- its last outgoing row, for the delivery label

The same helpers that insert and remove rows update these, and `restore`
rebuilds them. The window is decorated together with its two neighbors outside
it, so day labels, bubble tails and sender names at the edges match what
decorating the whole thread produces. Selection count and text come from the
map, in `order`. Every fixture thread has 10 rows or fewer, well under K, so
its answer matches today's except for the new cursor fields, and every existing
drive must pass unchanged.

### D5: What stays O(N), stated rather than hidden

- **Messages durable writes.** Messages loads every durable record into its TS
  model at startup and after each received sync page (`restore`). Every mutation
  also JSON-clones the whole model (`snapshot()`) and diffs it against the held
  copy (`persist`). After this plan, a write therefore still costs O(total
  records). The Snapback migration in progress in main's working tree is
  replacing that layer, so this plan does not touch `snapback-client.ts` and
  records the cost in `QUEUE.md`.
- **The 512-record cap.** Snapback refuses any edit that changes more than 512
  records, so deleting or recovering a conversation with more than 512 messages
  is refused today. It has the same owner and gets its own `QUEUE.md` line.
- **The eager Messages transcript.** Messages' transcript is an eager `scroll`,
  not a virtualized list, because its horizontal timestamp-reveal wrapper is a
  shape the collection doesn't support (LLP 1010 §6.5). Until LLP 1010's
  consumer sweep virtualizes it, Messages uses windows through labeled "Show
  earlier messages" and "Show later messages" rows, which appear only once a
  thread exceeds K rows. Mounted rows are bounded by K rather than by the
  viewport, and the eager transcript does not keep its scroll position across
  an explicit shift. Once the transcript is virtualized, `reachstart` and
  `reachend` replace those rows with no change to the source.
- **Other Messages mutation walks.** `advanceReplies` marks every outgoing row
  Read, and deleting or recovering rows in the middle of a thread splices the
  sorted array. Both are O(thread) mutations, cheaper than the snapshot above.
  Inserting through `sendMessage` resolves its reply parent through the
  maintained maps, not a thread scan.
- **The reply sheet.** `replies` is bounded by the size of the reply thread, not
  by K.
- **Key validation.** A change in membership validates every supplied key, which
  now means O(K).
- **The scrollbar.** The scrollbar spans the resident window rather than the whole
  history, as it does in iMessage. This is a declared deviation.

### D6: Not built

This plan does not build:

- keyed deltas, or reuse of unchanged windows
- page caches, or byte budgets beyond the existing kept-answer bound
- preview/detail requests for oversized bodies (Snapback's payload limit already
  bounds a stored message)
- sparse whole-history extents
- shared views, typed buffers or a shared heap (LLP 1027.003)

| Slice | Work | Done when |

**S1** covers cargo tests on the actual Contract and runner, plus drives:

1. At N = 1,000, 10,000 and 100,000 with K = 200, the supplied list never exceeds
   K rows plus the local echo. `last_instance_work().rows_keyed` stays at or below
   K + 1 for a stream tick at the tail and for a window shift. Feedback that only
   moves the offset and reaches no edge causes zero source queries and zero key
   evaluations.
2. A traversal from the tail to the first message and back, driven only by
   collection feedback:
   - Each edge crossing dispatches exactly one event.
   - The reader's anchor key keeps its offset across every shift, within the
     collection's existing tolerance.
   - At the first row, `hasEarlier` is false and nothing more is dispatched.
   - Resetting the cursor resumes following the tail.
3. A cursor past the end of the history (after the history size shrinks) resolves
   to the nearest surviving row. A malformed cursor is refused.
4. Agent drives on web and headless Linux at 100,000 rows, plus macOS if its build
   fits the loop:
   - scroll to the first message and back to the latest
   - type during streaming and check the exact echo
   - check that mounted rows stay bounded

   The drives report counts, not frame rates.

**S2** covers the TypeScript producer and the Messages app:

1. Rust tests run the shipped Messages bytecode without storage. Each seeds one
   thread with 25, 1,000 and 25,000 messages, including replies, reactions, group
   senders and a day boundary. Each conversation answer has at most K messages.
   A row's decorated fields must be identical in every window that contains it.
   At N ≤ K, the answer is the whole thread. No test proves that the answer
   skips rows outside the window. The TS rows are internal, and `exact_js::Module`
   exposes no deterministic work counter: a deliberately reintroduced
   whole-thread decoration passed with every observable count unchanged. Wall
   time can't serve as a guard either, because the debug-mode crossing dominates
   a 200-row answer. The walk bound therefore rests on review by both families,
   plus the flat answer size and time diagnostic in item 4.
2. Cursors round-trip:
   - Moving earlier reaches the first message, and moving later returns to the tail.
   - A deleted anchor resolves to its neighbor.
   - Sending while reading history returns to the tail with the sent row visible.
   - Selection count and text are correct with selected rows on both sides of the
     window.
3. Existing Messages tests pass, and so do the web and Linux Messages drives.
4. Diagnostic only: answer time and bytes at 1,000 versus 25,000 rows in one
   process, which should be flat. This is not a gate and not a frame-rate claim.

For every slice, the five checks pass on the integrated commit. Astra and Grok
review that same commit, blind to each other. A finding that only one family
raises is a hypothesis to check, not a defect to fix. Fix loops stop after three
rounds.

## 5. Deferred, with the trigger that brings each back

- **Keyed deltas or reuse of unchanged windows:** only if a measured O(K) answer
  still breaks an interaction budget. Deltas also need a base revision, ordered
  insert/update/delete, duplicate-key rules, atomic application and resync on
  mismatch, and Contract must never see a partly applied delta.
- **A sparse whole-history extent:** when a consumer needs a scrollbar that spans
  the history, or jump-to-date.
- **Virtualizing the Messages transcript:** LLP 1010's consumer sweep, tracked in
  `QUEUE.md`. It reuses these cursors and events unchanged.
- **O(total) durable writes and the 512-record cap in Messages:** the Snapback
  migration, tracked in `QUEUE.md`.
- **Immutable views, typed buffers or the heap:** the triggers in LLP 1027.003 §9.
  A real consumer has to keep reading a small part of Rust-owned data after
  bounded answers are in place.

## 6. What r2 changed from r1

- **The scroll-to-request mechanism.** r1 left it open ("the exact Contract shape
  is chosen with the implementation"), and it was the design's one real decision.
  r2 chooses a runner-side edge event plus a cursor argument, which needs no host
  changes.
- **Page residency, in-flight budgets and late-result binding.** r1's D3 specified
  these. r2 uses LLP 1016 D3/D5 instead, because a window that is the resource's
  arguments already has those semantics.
- **Slice 0 and slice 3.** r2 records slice 0 as landed. r1's slice 3 (retain
  unchanged pages, precise invalidation) moves behind a trigger, because a K-row
  answer is already O(window).
- **Byte budgets and oversized-body previews.** r1 proposed per-page and aggregate
  byte budgets and an oversized-body preview/detail request. r2 drops them: the
  kept-answer bound and Snapback's payload limit already bound them.
- **Where Messages is still O(N).** r2 names the costs outside the answer that r1
  left implicit: whole-thread decoration, reply counts, selection lookups, durable
  snapshots, the 512-record cap and the eager transcript. Each is assigned to this
  plan or to a named owner.
- **Acceptance.** Acceptance is now a short list per slice, with counted work
  instead of an open-ended scenario matrix.
