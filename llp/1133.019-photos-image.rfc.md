## Summary

Two modules of LLP 1133.000's wave 3, written as one RFC because one
consumer needs both and each is half of the same path: a photo is taken,
edited, and saved to the person's library.

**`@exact/photos`** reads the person's photo library and adds to it, on
iOS, macOS and Android, with the web a visible absence (the web has no
library API). Its tier 1 is a declared deviation in the web's style:

```
use photoLibraryStatus, photoAssets, copyPhotoAsset, addToPhotoLibrary,
  managePhotoSelection, PhotoAsset, PhotoCopy from "@exact/photos"

resource library = photoLibraryStatus()
resource recents = photoAssets(limit=24) as shape PhotoAsset[] else empty()
mutation opened as shape PhotoCopy then edit

action open(id: string)
  send opened = copyPhotoAsset(asset=id)

view
  for a in recents key=a.id
    button press=open(a.id) aria-label="Edit this photo"
      img src=a.picture width=72 height=72 object-fit="cover"
```

**Image** is the storage image call that exists (`compressImage`, LLP
1069.002 A1) widened to crop, rotate, flip and encode, as a second call
over the same codec for an edit, which keeps what the camera made:

```ts
import { addToPhotoLibrary } from "@exact/photos";

const out = await storage.fs.transformImage(photo, "app:/tmp/edits/1",
  { rotate: 90, crop: { x: 0, y: 412, width: 3024, height: 3024 } });
await addToPhotoLibrary({ path: out.path });
```

Tier 2 reaches PhotoKit's and MediaStore's own fields, iCloud's
downloads and Android's WebP lossless; tier 3 hands the app's Swift
PhotoKit's fetch, request and creation options, and its Kotlin the query
and insert values.

Four things this RFC decides, each for later modules too (§0):

- **Large media crosses by reference, picture and file, never by value.**
  A library item is an id the app may keep, a picture the host draws at
  the size of its box, or a copy in `app:/tmp`; no bytes enter Contract,
  data code or a module request.
- **Adding and reading are two permissions,** with two grant lines, two
  states and two prompts, because the platforms ask them apart.
- **Limited access is a fact beside the state,** and nothing the module
  keeps outlives it.
- **Image stays a data capability,** with the codec each host already
  has, and the purpose of a call sets what it keeps: an upload strips, an
  edit keeps.

The consumer is the photo editor: after the camera (LLP 1133.008), it
saves its edit to Photos, and opens a recent photo from a strip under
limited access (§11).

## 0. What is new here

1. **Media by reference.** Every module before this one names a session
   object by a handle that ends with the session (LLP 1133.009 D10 item
   10). A library item is not the session's: it outlives the app, other
   apps change it, and the person can withdraw it. It reaches the app as
   three things, each with one job (D2), and the module invents no fourth.
2. **A picture needs no file.** A grid of the person's photos must not be
   written into the app's files: it costs an encode per cell, and the copies
   outlive the person's choice. So a package may serve an `img` source
   scheme, which the host's raster loader asks at the size it will draw
   (D2, D11 item 1). This is a seam other modules will use: a contact's
   photo, a map snapshot, a document's thumbnail.
3. **Two permissions in one module.** Apple has an add-only access level
   and a read-write one, with separate usage strings and prompts; Android
   asks nothing to add on API 29 and later and asks a runtime permission to
   read. Geolocation's two lines narrowed one permission (LLP 1133.002 D7);
   these are two (D4).
4. **Limited as a fact, and no copy outlives it** (D6). The selection
   changes outside the app, and on Android expires by itself; what the app
   was shown must not survive in its kept answers, its cache or its files
   when the person takes it back.
5. **The purpose of an image call sets its unsaid defaults** (D15). The
   built `compressImage` flattens to sRGB, drops HDR and strips all
   metadata, which is right for an upload and a tell for an edit saved to
   Photos: the copy would lose its colour, its HDR and its date and place.

## 1. What exists

- **The picker** (LLP 1069.002) is HTML's `input type=file`, PHPicker on
  iOS and `NSOpenPanel` on macOS, with no permission: "the user's
  selection is the consent". A picked file lands in `app:/tmp/picked/` as a
  `Picked` record (`path`, `name`, `type`, `size`, `width`, `height`,
  `duration`). Android has no arm (LLP 1133.000 §2). Its "Not in this RFC"
  lists "the photo library as a data source (`expo-media-library`)".
- **`storage.fs.compressImage(from, to, {maxDimension, maxBytes, type})`**
  (LLP 1069.002 A1 and A1.11): Bluesky's search, run in the host, one decode
  and up to seven encodes, off the JS thread on Ibex's pool worker
  (opcode 121), on the module's one storage queue, with capped reads and an
  atomic write that a timeout cannot half-finish (A1.5). The output is
  sRGB, SDR, white under transparency for JPEG, and carries none of the
  source's metadata (A1.3). Codecs: Apple's ImageIO through Rust FFI, the
  web's canvas; Linux, Windows and Android refuse `unsupported` (A1.3).
  LLP 1133.006 D1 amends it for the clipboard (keep the size, a pixel bound,
  SVG input).
- **LLP 1114.003** (Draft, unruled) adds a `crop` rectangle to
  `compressImage`, in the upright image's pixels, and keeps the crop UI in
  Contract. Its question 2 left rotation for a consumer.
- **The camera** (LLP 1133.008, accepted) writes a photo to
  `app:/tmp/camera/<n>.<ext>` and opens a camera screen over the photo
  editor, which then loads an `app:/` path.
- **The photo editor** (`apps/photo-editor`, LLP 1024) edits one photo in
  its own module, `<photo-editor>`: zoom, free rotation, quarter turns,
  pan and a crop rectangle, in UIKit, AppKit and Pointer Events. It reports
  the edit as a string in its canvas's terms and writes no image
  (`modules/apple/PhotoEditor.swift`, `PhotoEdit.summary`). Its Rust data
  crate answers nothing.
- **The grant `device.photos-add`** is a row of `runner/src/device.rs`
  with `NSPhotoLibraryAddUsageDescription` on iOS and macOS and the
  hardened-runtime entitlement `com.apple.security.personal-information.photos-library`
  on macOS. No module uses it. LLP 1069.008 D2: "Reading the whole library
  would be a `device.photos` row, and nothing asks for it."
- **`keeps_no_answers`** is a column of the grant table (LLP 1069.008.000
  D7): an app granting such a row keeps no answers across launches.
- **`rules/DEFERRED.md`** names neither the library nor image editing.
  LLP 1069.002 D6 does: "Image editing stays out", reopened on 2026-10-08
  for `compressImage` alone.

## 2. Tier 1

### D1 — The names, a declared deviation

The web has no photo library API: a page reaches the person's photos only
through the file input the picker already is. So tier 1 is the shared words
of PhotoKit and MediaStore, named in the web's style, each a declared
deviation (LLP 1133 D1):

| Name | Kind | Meaning | Contract | Data code |
|---|---|---|---|---|
| `photoLibraryStatus()` | live source; a fact; `sync` | `available`, `state`, `access`, `addState` (D5) | `resource s = photoLibraryStatus()` | `await photoLibraryStatus()` |
| `photoAssets(limit=)` | live source; a fact; its read while `state` is `prompt` asks (`"request": "when-prompt"`) | the library's photos the app may see, newest first | `resource r = photoAssets(limit=24)` | `await photoAssets({limit})` |
| `copyPhotoAsset(asset=, version=, path=)` | send; asks while `prompt` | a copy of one photo's file in `app:/` | `send c = copyPhotoAsset(asset=id)` | `await copyPhotoAsset({asset})` |
| `addToPhotoLibrary(path=)` | send; a request (D6) | a new photo in the library from an `app:/` file | `send x = addToPhotoLibrary(path=p)` | `await addToPhotoLibrary({path})` |
| `managePhotoSelection()` | send; a request | under limited access, the platform's sheet to change the selection | `send s = managePhotoSelection()` | `await managePhotoSelection()` |
| `PhotoAsset.picture` | an `img` source (D2) | the photo drawn at the box's size | `img src=a.picture` | — |

**Values.**

| Shape | Fields |
|---|---|
| `PhotoAsset` | `id` (D2); `mediaType` (`image`); `width`, `height` (pixels of the version Photos shows, orientation applied); `creationDate: option<number>` (ms since the epoch); `favorite` (bool); `picture` (string, D2); `apple: option<ApplePhotoAsset>`, `android: option<AndroidPhotoAsset>` (D8) |
| `PhotoLibraryStatus` | `available`; `state` (`granted`, `prompt`, `denied`, `unknown`), the read permission; `access` (`full`, `limited`, `none`); `addState` (the same four), the add permission; `apple`, `android` (D8) |
| `PhotoCopy` | `Picked`'s fields (`path`, `name`, `type`, `size`, `width`, `height`, `duration`), so an action that takes a pick takes a copy |
| `PhotoAdded` | `asset: option<string>`: the new photo's id where the app may read it (D6), else `none` |

`photoAssets` takes `limit` (1 to 500, default 60) and answers the newest
that many. It does not page: a creation date cannot be a cursor, since
many photos share one (Android's `DATE_ADDED` is in seconds), and a grid
that pages past `limit` takes an opaque cursor when a consumer asks (§9).
Videos are not listed (§9).

**Errors** are `DOMException` names, as the media modules give them (LLP
1133.009 D1): `NotAllowedError` (denied, or a caller the origin rule
refuses, with `message` `person-required`, D7); `NotFoundError` (an id the
library does not have, or one outside a limited selection, which the
platform does not tell apart); `NetworkError` (a photo held only in iCloud
that could not be downloaded, or that `apple.isNetworkAccessAllowed=false`
refused to download); `DataError` (a file `addToPhotoLibrary` cannot add:
not an image the library takes); `AbortError` (the call's mutation or
session ended first); `NotSupportedError` (a target without the module:
the web); `UnknownError` (the platform failed).

**Declared deviations,** with reasons:

- **No web name.** The nearest web forms are the picker, which this
  module does not replace, and a download, which is not a library.
- **A photo is a reference, a picture or a file** (D2), never bytes.
- **The selection is a fact, not a list of grants.** The platforms hand
  the app a view of the library that already holds only the selection
  (D6); the module adds no per-asset permission of its own.

### D2 — Three forms of a library item

A photo in the library is megabytes, may live only in iCloud, belongs to
another app's database, and may be withdrawn by the person. The module
gives it to the app in three forms and no other:

1. **A reference: `id`.** The platform's own: PhotoKit's
   `localIdentifier`, Android's MediaStore content URI. It is durable: the
   app may keep it in its state, its key-value store or its database and
   use it in a later launch. It is not a session handle (LLP 1133.009 D10
   item 10): nothing disposes of it, and holding it grants nothing. Each
   use resolves it again, and one that no longer resolves (the photo
   deleted, hidden, or left out of a limited selection) fails
   `NotFoundError`. It is a reference on this device: PhotoKit's identifier
   differs on the person's other devices, and Android asks an app to check
   `MediaStore.getVersion()` at startup, since its media may have been
   rescanned ([media](https://developer.android.com/training/data-storage/shared/media));
   the status carries that version as `android.generation`, so an app can
   drop the ids it stored when it changes.
2. **A picture: `picture`.** A string, `photos:<id>`, that an `img` takes
   as a source. Drawing it is a read of the module, admitted like any
   other (LLP 1133.002 D14) and never a request: the host's raster loader
   hands the runner the source, the pixel size and the fit of the box it
   will draw (`object-fit`'s `cover` or `contain`); the runner checks the
   grant and that `state` is `granted` (or, for the app's own photo on
   Android, D6's rule), and only then asks the bound
   implementation, on the main thread, as every module entry is (LLP
   1067.000 D4). The implementation answers later, once or twice (a quick
   picture, then the final one), with a decoded image, which the loader
   takes on its own queue as it takes a download
   (`RasterInput.fetch`, `host/apple/Sources/ExactKit/RasterInput.swift`)
   and holds in its decoded-image budget (LLP 1010 §6), its colour space
   classified as LLP 1100 says. While `state` is `prompt` or `denied`, the
   picture fails and the platform's library is not entered (save the app's
   own photo on Android, D6), so a draw never prompts, whoever caused it. On Apple the implementation asks
   `PHCachingImageManager`, which "can prepare asset images in the
   background … for example … to populate a collection view … with
   thumbnails" ([PHCachingImageManager](https://developer.apple.com/documentation/photos/phcachingimagemanager));
   on Android, `ContentResolver.loadThumbnail(uri, size, signal)`, which
   "efficiently loads a visual thumbnail" (API 29,
   [loadThumbnail](https://developer.android.com/reference/android/content/ContentResolver#loadThumbnail(android.net.Uri,%20android.util.Size,%20android.os.CancellationSignal))).
   A picture is never a file in the app's store, never bytes in data code,
   and never a value in Contract.
   **Withdrawing a picture is not replacing it.** An `img` keeps its last
   raster while a new source loads, and a failed load leaves it
   (`NodeViewIOS.swift`), which is right for an ordinary image and wrong
   for a photo the person took back. So when the implementation learns
   that a photo left what the app may read (D6), it revokes its pictures:
   the host clears every displayed raster and cache entry of those URLs,
   cancels their loads and drops any later reply to them, and the `img`
   shows its empty box and fires `error`.
3. **A copy: `copyPhotoAsset`.** The photo's file, written to
   `app:/tmp/photos/<n>.<ext>` (or a `path` the app names, admitted
   against its `fs.write`), answered as `PhotoCopy`. This is what an app
   uploads, edits or shares. The directory is emptied at launch, as
   `app:/tmp/picked/` is (LLP 1069.002 D4); an app that keeps a copy moves
   it into `app:/data` itself.

*Rejected:* thumbnails as files (`requestThumbnail` writing
`app:/cache/photos/<id>-<w>x<h>.jpg`). It needs no new seam, but each cell
costs an encode, a write, a runner commit and a decode; the app must choose
pixel sizes it cannot see; and every photo a person shows the app is then
a copy in its cache after they take it back (D6). *Rejected:* a package
view per photo (`exact-photo asset=`), the camera's viewfinder shape. It
reaches the platform's cache too, but makes every cell of a grid a hosted
native view, with none of `img`'s CSS (`border-radius`, `object-fit`,
`aspect-ratio`) unless each is reimplemented.

## 3. Permission

### D4 — Two grant lines, two permissions

| | `device.photos-add <purpose>` (exists) | `device.photos <purpose>` (new) |
|---|---|---|
| What it allows | add | read, and add |
| iOS | `NSPhotoLibraryAddUsageDescription` | `NSPhotoLibraryUsageDescription`; `PHPhotoLibraryPreventAutomaticLimitedAccessAlert` true (D6) |
| macOS | `NSPhotoLibraryUsageDescription` and the entitlement (below) | `NSPhotoLibraryUsageDescription` and `com.apple.security.personal-information.photos-library` |
| Android (the host builds API 29 and later) | nothing: "as of Android 10 (API level 29), apps no longer need storage permissions to add files to shared storage" ([Selected Photos Access](https://developer.android.com/about/versions/14/changes/partial-photo-video-access)) | `READ_MEDIA_IMAGES` (API 33), `READ_MEDIA_VISUAL_USER_SELECTED` (API 34), `READ_EXTERNAL_STORAGE` with `maxSdkVersion="32"`, and `ACCESS_MEDIA_LOCATION` (below) |
| web | none | none |

Apple's access levels are `addOnly` ("may only add") and `readWrite` ("can
read from and write to"), on iOS 14 and macOS 11
([PHAccessLevel](https://developer.apple.com/documentation/photos/phaccesslevel)),
each asked by its own prompt with its own string. Apple lists
`NSPhotoLibraryAddUsageDescription` for iOS, iPadOS and visionOS only, and
`NSPhotoLibraryUsageDescription` for macOS too
([add](https://developer.apple.com/documentation/bundleresources/information-property-list/nsphotolibraryaddusagedescription),
[read](https://developer.apple.com/documentation/bundleresources/information-property-list/nsphotolibraryusagedescription)),
so the existing row's macOS column, which writes the add key alone, is
amended to write the read key with it; stage 2 records which text the Mac's
prompt shows. On macOS the two lines then write one key: with both, the
key takes `device.photos`'s purpose, the broader prompt's, and the bake
says so rather than write whichever line came last (`bake/src/reach.rs`
inserts a key once). The entitlement is the hardened runtime's ([entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.personal-information.photos-library)).

An app may write either line or both: they are two permissions, not one
narrowed (`narrows` stays empty). By LLP 1133.009 D10 item 9, a name lists
the lines that satisfy it: `addToPhotoLibrary` is satisfied by either;
`photoAssets` by `device.photos` alone; a picture or a copy of a photo
the app added itself by either, where the platform lets the app read it
back (D6), and of any other by `device.photos`. **A request asks the narrowest permission
the app declares that satisfies it:** with both lines, an add asks
add-only, as Apple says to ("if your app only adds photos to the library,
instead, request add-only access"); with `device.photos` alone it asks
read-write, which is what the app said it needs.

On Android, Google Play restricts `READ_MEDIA_IMAGES` to the uses its
policy names and recommends the photo picker instead
([media](https://developer.android.com/training/data-storage/shared/media));
the recipe says so, and meeting the policy is the author's. The read
permissions differ by API level (`READ_EXTERNAL_STORAGE` to 32,
`READ_MEDIA_IMAGES` from 33, `READ_MEDIA_VISUAL_USER_SELECTED` from 34), so
the Android column holds an API range per permission, the manifest writes
`maxSdkVersion` where the range ends, and the request names only the ones
the device's level has, one dialog on each.

**Location on Android.** Android redacts a photo's location from the bytes
an app reads unless the app holds `ACCESS_MEDIA_LOCATION` ("allows an
application to access any geographic locations persisted in the user's
shared collection", API 29, a runtime permission) and opens the file with
`MediaStore.setRequireOriginal`, "without any Exif redaction"
([Manifest.permission](https://developer.android.com/reference/android/Manifest.permission#ACCESS_MEDIA_LOCATION),
[setRequireOriginal](https://developer.android.com/reference/android/provider/MediaStore#setRequireOriginal(android.net.Uri)),
[media](https://developer.android.com/training/data-storage/shared/media#media-location-permission)).
`device.photos` derives it and asks it in the same request as the read
permission. The app's own photos are not redacted: MediaProvider exempts
the owner ([AOSP](https://android.googlesource.com/platform/packages/providers/MediaProvider/+/69a25763cdb46c8f23fe9eb976132acbe2af82d6%5E!/)).
So `PhotoCopy`'s `android.locationRedacted` describes the export made, not
the permission held: true when the copy of another app's photo was opened
without `setRequireOriginal`, and an edit of such a copy has no location to
keep (D15). Stage 3 records whether the platform shows the permission as a
dialog of its own.

### D5 — Read: the state, the access, the add state

`photoLibraryStatus()` answers, with one meaning on every target (LLP
1133.002 D8):

| Platform | `state` | `access` | `addState` |
|---|---|---|---|
| Apple `authorizationStatus(for: .readWrite)` `notDetermined` | `prompt` | `none` | — |
| Apple `authorized` | `granted` | `full` | `granted` |
| Apple `limited` | `granted` | `limited` | `granted` |
| Apple `denied`, `restricted` | `denied` | `none` | — |
| Apple `authorizationStatus(for: .addOnly)`, when read-write is not granted | — | — | `notDetermined` `prompt`, `authorized` `granted`, `denied` and `restricted` `denied` |
| Android `READ_MEDIA_IMAGES` (API 33+) or `READ_EXTERNAL_STORAGE` (29–32) | `granted` | `full` | `granted` |
| Android `READ_MEDIA_VISUAL_USER_SELECTED` alone (API 34+) | `granted` | `limited` | `granted` |
| Android neither | by the host's history (LLP 1133.008 D8 item 7) | `none` | `granted` |
| web, and any target without the module | `unknown`, `available` false | `none` | `unknown` |

Apple's older `authorizationStatus()` "return[s] `authorized` when the user
authorizes your app for limited access only", so the implementation reads
the per-level form only (the privacy guide above). Android's mapping is the
guide's own detection code (Selected Photos Access, above). A read-write
grant includes adding, so `addState` folds it in. Apple's `restricted`
(parental controls) is `apple.authorizationStatus`.

### D6 — Limited access is a fact, and nothing outlives it

Limited access is `access: "limited"` while `state` is `granted`, as
geolocation's approximate accuracy is a field beside its state (LLP
1133.002 D8). It is not a fourth state, because every read proceeds under
it; what changes is what the reads see.

**What the app sees is the platform's.** Under limited access "your app can
only access these assets", the person's selection, and "the system
automatically adds assets that your app creates with a
`PHAssetCreationRequest` to the user's limited library selection" (Apple's
privacy guide). Android attributes to an app the media it created, which
it reads without permission ([media](https://developer.android.com/training/data-storage/shared/media)),
and on Android 16 shows the app's own photos pre-selected when the person
limits it (Selected Photos Access). So `photoAssets` answers the selection
and what the app added, and `addToPhotoLibrary` answers the new id where
the app may then read it: under read-write access (full or limited) on
Apple, and on Android whatever its read permission; under Apple's add-only
access, `none`.

**Android's own photos are read under the add line.** Whether a photo is
the app's own is known only to MediaStore, when the id is opened, and
opening the app's own photo asks nothing. So on Android, while `addState`
is `granted`, admission lets a picture or a `copyPhotoAsset` through with
no dialog whatever `state` reads (the declaration's `"owned":
"device.photos-add"`), and the implementation opens the id as the app's
own media. If MediaStore refuses it (another app's photo), the copy
enters admission again as an ordinary read under `device.photos`, with
its own origin and D7's row for it: while `state` is `granted` it
proceeds, a tool's and a wake's too; while `prompt`, a person's call or the
app's own foreground code holds the permission ticket and asks, and a
tool's or a wake's fails `NotAllowedError`, `person-required`; while
`denied`, it fails `NotAllowedError`; an app without the line fails
`NotFoundError`, since the add line reaches only its own photos. A picture never asks and fails
as an unresolved image. Every other read, and every read on Apple, keeps D2's
rule: the library is not entered while `state` is not `granted`. Android's
attribution does not survive a reinstall ("you must request
`READ_EXTERNAL_STORAGE` to access the files that your app originally
created"), so after one an id fails under the add line alone.

**It changes outside the app,** and the module reads it again:

- On Apple the person changes the selection in Settings or in the
  system's sheet; "any changes the user applies to the limited library
  selection trigger a `PHPhotoLibraryChangeObserver` update"
  ([presentLimitedLibraryPicker](https://developer.apple.com/documentation/photos/phphotolibrary/presentlimitedlibrarypicker(from:completionhandler:))).
  The implementation registers one observer and announces
  `photoLibraryStatus` and `photoAssets` on each change, so their readers
  are asked again.
- On Android "the permission grant can be changed between the `onStart`
  and `onResume` app lifecycle callbacks", and a partial grant's "access
  to the selected photos and videos expires eventually"; Android says
  "don't store the permission state in a permanent way" and to "refresh
  the results when your app goes through the `onResume`"
  (Selected Photos Access). The implementation reads both permissions at
  each resume (`resumed()`, LLP 1133.002 §10 stage 4) and announces a
  change.

**Nothing the module gives outlives the fact.** When the person narrows or
withdraws access, nothing the app was shown may survive in a form the app
did not choose to keep:

- **No kept answers.** A relaunch after a revocation must not draw the
  last launch's list before the module answers. A module source's answer
  is never kept: only a resource that reads the store is (`keep_answer`,
  `runner/src/runner/kept.rs`). But library data reaches store-reading
  answers by more paths than a rule on the call can follow: answer B may
  await a promise answer A made (LLP 1133.002 D14), read what an earlier
  answer left in module memory, or take `photoAssets`' answer as an
  argument or a `with` input from Contract, and a kept entry records its
  arguments as well as its value. So `device.photos` is a
  `keeps_no_answers` row (LLP 1069.008.000 D7), as HealthKit's rows are:
  an app that reads the library keeps no answers across launches, and its
  first frame shows placeholders. The cost is the app's every kept
  answer, not only those that touched a photo; a finer rule, which would
  have to follow library values through Contract inputs and every data
  runtime, waits for an app whose first frame needs it (§13 question 6).
  `device.photos-add` keeps answers: the app reads back only its own
  photos.
- **Pictures are never files** (D2), so a withdrawn photo's picture fails
  at its next draw.
- **Copies are temporary** (`app:/tmp/photos/`, emptied at launch). A copy
  the app moves into `app:/data` is the app's decision, as with a picked
  file.
- **References re-resolve.** A kept `id` that left the selection fails
  `NotFoundError`, like a deleted one.

**Asking to change it.** `managePhotoSelection()` shows the platform's own
sheet and answers the new status:

- iOS and iPadOS 15: `presentLimitedLibraryPicker(from:completionHandler:)`;
  "if the user hasn't enabled limited library access mode for your app,
  calling this method does nothing", so while `access` is `full` the call
  answers the status at once. It is not on macOS (the method lists iOS,
  iPadOS, Mac Catalyst and visionOS), where the call fails
  `NotSupportedError` and the person changes access in System Settings.
- Android 14: the permission request again, `READ_MEDIA_IMAGES` with
  `READ_MEDIA_VISUAL_USER_SELECTED`, which shows the selection dialog
  (Selected Photos Access's own example).

**The automatic alert.** "By default, the system automatically prompts the
user to update their limited-library selection once per app life cycle.
This automatic presentation isn't the preferred user experience for most
apps." Its suppression is `PHPhotoLibraryPreventAutomaticLimitedAccessAlert`
set to `true` in `Info.plist` ([limited](https://developer.apple.com/documentation/photos/phauthorizationstatus/limited)).
`device.photos` always writes it (the grant table's `ios_flags`, as
`NSLocationDefaultAccuracyReduced` is written, LLP 1133.002 D7), for two
reasons. The alert is system UI that PhotoKit opens at a fetch, so with it
a tool's or a wake's granted read could open a sheet, which LLP 1133 D6
rule 3 refuses. And Apple names the suppressed alert as the better
experience. So the only way the selection sheet opens is
`managePhotoSelection`, a request admitted by its origin, and the recipe
tells an app under limited access to show a Manage button.

### D7 — Ask, explain, and who may call

**Ask.** The first read of `photoAssets`, a `copyPhotoAsset` or an
`addToPhotoLibrary` while its permission reads `prompt` asks, through
`requestAuthorization(for:handler:)` with the access level of D4 on Apple
and `Activity.requestPermissions` on Android, in LLP 1133.002 D9's queue.
"The first time your app performs an operation that requires
authorization, the system automatically and asynchronously prompts the
user for it" (Apple's guide); the implementation asks first, so a request
never waits on a prompt PhotoKit opens by itself. Explaining is the app's
own UI and recovering is `openURL("app-settings:")` (LLP 1133.002 D11).
Apple's guidance and the recipe agree: an app that only lets a person
choose a photo uses the picker, which asks nothing.

**Who may call** (LLP 1133.002 D12):

| Origin | `photoAssets`, `copyPhotoAsset` | `addToPhotoLibrary` | `managePhotoSelection` | `photoLibraryStatus`, pictures |
|---|---|---|---|---|
| a person's input; the app's own code in a foreground session | proceeds; asks while `prompt` | proceeds; asks while `prompt` | shows the sheet | answers; a picture only while `granted`, or of the app's own photo on Android (D6) |
| a tool invocation (LLP 1111) | proceeds under the app's grant; while `prompt`, `person-required` | `NotAllowedError`, `person-required`, in every state | `person-required` | the same |
| a background wake; a headless session | proceeds where granted; while `prompt`, `person-required` | `person-required` | `person-required` | the same |

A tool may read what the app may read, as a tool may read a granted
position (LLP 1133.002 D12; the delegation direction there may narrow it).
**Adding is the app's** (`"origin": "app"`, LLP 1133.009 D10 item 8): a
new photo in the person's library is an effect outside the app, which
syncs to their other devices, so an agent acting through the app's tools
may not make one without the person, as it may not replace their
clipboard (LLP 1133.006 D6). A picture needs no origin rule of its own:
it never prompts, it enters the library only for a granted read or the
app's own photo on Android (D2, D6), and the platform's selection alert,
the one other sheet a read could open, is suppressed (D6).

### D11 — Seam additions

What the package uses as it is: writes to `app:/tmp/<extension>/` with no
grant (LLP 1133.008 D8 item 4), a path to read (LLP 1133.006 D8 item 3) and
to write (LLP 1133.009 D10 item 4), grants per name (LLP 1133.009 D10 item
9), the origin rule (item 8), preferred values reaching an implementation
that is its own substitute (LLP 1133.008 D8 item 9), the host's permission
history (LLP 1133.008 D8 item 7) and `resumed()`. What it needs beyond
them, each general and each proved by the out-of-tree fixture first (LLP
1133.001 D8):

1. **A package serves an `img` source scheme, through admission.** An
   interface declares `"images": {"scheme": …, "grants": […]}`; the bake
   refuses a scheme two packages declare (`bake-scheme-twice`) or one the
   hosts own (`app`, `doc`, `symbol`, `data`, `http`, `https`). The source
   is a raw prefix, as `app:/` is: a PhotoKit identifier holds slashes and
   an Android one is a `content:` URI, which a URL parser would split. A
   host's raster loader, given such a source, does not open it as a file:
   it makes an asynchronous, cancellable read, which the runner admits as
   D2 says (grant, `state`, target; never a request) before the bound
   implementation is asked on the main thread with the pixel size and fit.
   The implementation answers through a completion, once or more, with a
   decoded image; the loader takes it on its own queue, as it takes a
   download, and the main thread never waits for it. Apple: beside
   `RasterInput.fetch`, a decoded input the raster cache holds under its
   URL and size, charged to LLP 1010 §6's budget. Android: the reader's
   Rust image loader (`host/linux/src/image`), which has no door for a
   source outside the asset root today, gains this one, with a `Bitmap`
   from the Kotlin implementation. The web runtime: a `Blob` URL. Under the
   agent the runner admits first and the implementation answers its
   fixtures, so a screenshot shows them. A source with no bound
   implementation, no grant or no granted read fails as an unresolved
   image (`error`), never a network fetch. An implementation **announces**
   a changed picture by its URL, and the host loads it again; it
   **revokes** a URL, and the host clears its displayed rasters and cache
   entries, cancels its loads and drops later replies (D2).
2. **More than one permission in one interface.** `permission` becomes a
   list, each entry naming its grant line, status source and field, so
   `prefer permission.photos …`, `prefer permission.photos-add …`,
   `--permission photos=…` and their tickets work as geolocation's do; a
   name says which permission it asks, or `narrowest` (D4).
3. **A ticket choice beyond allow and deny.** A permission entry's
   `choices` names further answers and what each sets, so `tap @t limited`
   grants with `access` `limited` (§10). A `selection` ticket, held by
   `managePhotoSelection`, takes `type @t <ids>`.
4. **A read of the app's own item under another line.** A name's
   `"owned"` names, per target, a grant line under which admission lets a
   read through without a dialog, leaving it to the implementation to open
   the item as the app's own. A refusal re-enters admission under the
   call's origin as a request for the name's own permission (D6).

Each is apparatus under `rules/RULES.md` and lands with this ruling.

## Part II — Image

## 6. Where image lives, and what it does

### D13 — Image stays a data capability

Image is computation on the app's own files: it needs no device, asks no
permission and shows nothing (LLP 1069.002 A1.6). What it needs is
storage's, which `compressImage` already has: `fs.read` on the source and
`fs.write` on the destination, the module's one storage queue, a read
capped before decoding, a write published atomically that a timeout cannot
half-finish (A1.5), and a worker off the JS thread. So it stays a data
capability (LLP 1133 D5's exception), widened as the roster's row says,
for three reasons:

1. **One codec per host.** Every image call on a host goes through the
   codec that host installs (`Context::set_image_codec`): Apple's ImageIO
   through Rust, the web's canvas, and, new here, Android's (D16). A
   package would bring a second pipeline (Swift ImageIO beside the Rust
   one), and the same file decoded two ways is the bug class LLP 1100
   closed for colour and HDR.
2. **No bytes in a module request.** A package's call runs on the main
   thread (LLP 1067.000 D4) and its request is bounded at 4 MiB (LLP
   1133.006 D1); it would hop to a queue and pass paths, rebuilding A1.5
   without its tests.
3. **Its caller is data code already.** An edit is rendered when the
   person saves, to be uploaded or added, which LLP 1133 D6 says is data
   code's ("when the value is an input to a request or a computation").

What it costs: Contract does not call it (the photo editor gains a data
source, §11), and a third party cannot add a platform's codec without
exact2. *Rejected:* `@exact/image`, a package with Swift, Kotlin and
JavaScript implementations, for the reasons above; it would be right if a
consumer needed image work from Contract, or a platform exact2 does not
maintain.

### D14 — `transformImage`, by the web's names

```ts
interface FileSystem {
  transformImage(from: string, to: string, options?: TransformImageOptions): Promise<TransformedImage>;
}
interface TransformImageOptions {
  readonly rotate?: number;                       // degrees clockwise
  readonly flip?: "horizontal" | "vertical";
  readonly crop?: { readonly x: number; readonly y: number;
                    readonly width: number; readonly height: number };
  readonly resizeWidth?: number;                  // ImageBitmapOptions' names
  readonly resizeHeight?: number;
  readonly resizeQuality?: "pixelated" | "low" | "medium" | "high";
  readonly type?: string;                         // ImageEncodeOptions' names
  readonly quality?: number;                      // 0 to 1
  readonly metadata?: "keep" | "no-location" | "none";
}
interface TransformedImage {
  readonly path: string; readonly type: string; readonly size: number;
  readonly width: number; readonly height: number;
  readonly colorSpace: "srgb" | "display-p3" | "other";
  readonly hdr: boolean;
  readonly metadata: "keep" | "no-location" | "none";
}
```

The names are the web's where it has them: the crop is a `DOMRect`'s
`{x, y, width, height}`, as LLP 1114.003 D1 chose; the size is
`createImageBitmap`'s `resizeWidth`, `resizeHeight` and `resizeQuality`;
the encoding is `convertToBlob`'s `type` and `quality`, a number from 0 to
1 ([convertToBlob](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas/convertToBlob)).
`rotate` is degrees clockwise, as CSS's `rotate` property turns; `flip`
and `metadata` have no web name.

**One order, one decode, one encode.** The source upright (its orientation
applied, as `Picked`'s size is), then `rotate` about its centre, then
`flip` in the turned frame (so `horizontal` mirrors what the person sees),
then `crop` in that frame's pixels, then the size, then the encoding. A
quarter turn resamples nothing. Any other angle turns the picture into its
bounding box, and pixels the picture does not cover are transparent where
`type` keeps alpha and white otherwise (A1.3's rule). The photo editor's
straighten-and-crop is then one call: the angle, and the crop inside it.

- **Crop** is checked, clipped and rounded as LLP 1114.003 D2 says; one
  that misses the picture fails `outside`.
- **Size:** one of `resizeWidth` and `resizeHeight` keeps the aspect, both
  set the size, as `createImageBitmap` does; neither keeps the crop's.
  The output is bounded as the source is (64 Mi pixels, A1.5).
- **`type`** omitted is the source's where the host encodes it, else
  `image/jpeg`; written, a type the host does not encode fails
  `unsupported`, never silently another (`convertToBlob` falls back to PNG,
  so the web checks the blob's type, as A1.3 does). A `to` without an
  extension gains the type's, as a camera photo's does (LLP 1133.008 D1).
- **`quality`** omitted is 0.9, the picker's conversion (LLP 1069.002 D6).

### D15 — An edit keeps what the camera made; an upload strips

The two calls share every step but the search, and differ in what they
keep when the author says nothing, because their purposes do:

| Unsaid | `compressImage` (an upload) | `transformImage` (an edit) |
|---|---|---|
| colour | sRGB | the source's profile (Display P3 stays P3) |
| HDR | tone-mapped to SDR | a gain map kept where the type and host carry it, else SDR by LLP 1100 D13's ladder |
| metadata | none | `keep`: the source's EXIF, TIFF, GPS, IPTC and XMP, with the orientation reset and the size rewritten |
| size | Bluesky's search to `maxBytes` | as asked, no search |

An edit saved to Photos that came back flat, undated and placeless would be
noticed by anyone who knows the platform: Photos' own Duplicate keeps all
three. An upload that kept the person's location would leak it; A1's
choice stands.

`metadata: "no-location"` cannot be ImageIO's GPS switch: "this flag
doesn't filter any proprietary location data in the manufacturer's EXIF
MakerNote or in custom XMP properties"
([kCGImageMetadataShouldExcludeGPS](https://developer.apple.com/documentation/imageio/kcgimagemetadatashouldexcludegps)).
So it writes a conservative set rather than subtracting from the source's:
the standard EXIF and TIFF tags that describe the capture (dates, camera,
lens, exposure, the colour space), the IPTC rights fields, and nothing
else, with no GPS dictionary, no MakerNote and no XMP. `keep` keeps what
the source has, MakerNote and XMP included, since the photo goes back to
the person's own library. The result's
`colorSpace`, `hdr` and `metadata` say what was written, so a host that
cannot keep something (the web, below) is visible, never silent.

`compressImage` gains `rotate`, `flip` and `crop` with D14's meanings and
its own defaults, so an avatar cropped from a turned photo is one upload
call. This takes LLP 1114.003's Amendment A2: with no `rotate` or
`flip`, its rectangle in the upright image's pixels is unchanged; with
them, D14's order puts the rectangle in the turned frame.

*Rejected:* one call with a mode (`purpose: "upload" | "edit"`). It is one
name whose unsaid behaviour depends on a word an author may forget, and
the cost of forgetting is a leaked location or a flattened photo; two
names make each default the right one for what the call is.

### D16 — Per host

| Host | How |
|---|---|
| iOS, macOS | the A1 codec widened (`data/src/image/apple.rs`): the oriented decode, a `CGAffineTransform` for turn and flip into a context of the output's size, ImageIO's encode. To keep HDR it decodes with `kCGImageSourceDecodeToHDR`, draws into an extended-range context and encodes with `kCGImageDestinationEncodeToISOGainmap` (iOS 18, macOS 15, [the key](https://developer.apple.com/documentation/imageio/kcgimagedestinationencodetoisogainmap)), with LLP 1100 D13's SDR retry and Core Image tone-map fallback; metadata through the source's properties into the destination's. Encodes JPEG, PNG and HEIC |
| web | `storage-image.js` widened: the oriented `ImageBitmap`, the context's `rotate` and `scale(-1, 1)`, `drawImage` with the crop as its source rectangle, `convertToBlob`. Writes no metadata (a canvas has none), sRGB, SDR: the result says so. HEIC and AVIF stay `undecodable` (A1.5). Encodes PNG always, and JPEG and WebP where the browser does |
| Android | **new:** a codec installed into the data executor as Apple's is, in two paths. **API 34 and later:** Java's `ImageDecoder` (through JNI from Ibex's pool worker, which attaches to the JVM) gives an upright `Bitmap` (the decoder applies EXIF orientation, as the reader's output already is) that carries the source's gain map; turn and flip are one `Matrix` applied to the whole bitmap with `Bitmap.createBitmap`; the crop, in the turned frame, is a second `createBitmap` of a subset, since one call would take its rectangle in the source's frame, which for a free angle is not D14's crop; and the size is a third, scaling the cropped bitmap, so the crop is never taken from resized pixels. Both are `Bitmap` transforms, which "make the appropriate changes to the gain map" for rotate, crop and scale ([Ultra HDR editing](https://developer.android.com/media/grow/ultra-hdr/edit)); then `Bitmap.compress` (JPEG, PNG, and from API 30 `WEBP_LOSSY` and `WEBP_LOSSLESS`, [CompressFormat](https://developer.android.com/reference/android/graphics/Bitmap.CompressFormat)) and `android.media.ExifInterface` for metadata. "Android supports ISO 21496-1 encoding from and decoding to Bitmap for JPEG starting on Android 15" ([Ultra HDR](https://developer.android.com/media/platform/hdr-image-format)); where a drive shows the gain map lost (a free angle, API 34), the result's `hdr` is false. **Below 34:** SDR, decoded with `AImageDecoder` (API 30) and `ImageDecoder` below it, through the same three steps, at the size the decoder's own header reports (`AImageDecoderHeaderInfo_getWidth`, `getHeight`), not the start-of-frame size the reader passes to `setTargetSize` (`host/linux/src/image/jpeg.rs`), and with neither `setCrop`, which crops "the (possibly) scaled image" ([ImageDecoder](https://developer.android.com/reference/android/graphics/ImageDecoder)), nor `setTargetSize` unless there is no turn, flip, crop or size. Whether these decoders apply EXIF orientation is disputed by the evidence (AOSP's decoder respects it; the reader's wrapper reads only the stored size), so the codec compares the decoded size with the stored size and the EXIF tag, and applies the orientation in the first matrix only where the decoder did not. Stage 3 checks an orientation-6 source with no edit, with a crop, and with a crop and a size, on API 29, 33 and 34. Encodes JPEG, PNG and WebP, not HEIC. The same codec gives `compressImage` its Android arm, which A1.3 refuses today |
| Windows | later: WIC's `BitmapEncoder` with a `BitmapTransform`, whose order is "1. Scale 2. Flip 3. Rotation 4. Crop" ([BitmapTransform](https://learn.microsoft.com/uwp/api/windows.graphics.imaging.bitmaptransform)), so the codec composes D14's order from it |
| Linux | later: the workspace has no image codec (A1.3) |
| terminal | absent |

The encode is the platform's Java API rather than the NDK's
`AndroidBitmap_compress` (API 30): the gain map and EXIF are reachable only
from Java, and the host's minimum is API 29.

### D17 — Failures, limits, words

Failures are A1.4's (`TypeError` before anything is queued for a bad
option; `denied`; the filesystem's codes; `too-large`; `undecodable`;
`timeout`; `unsupported`), with LLP 1114.003's `outside`. `unfit` is
`compressImage`'s alone. Limits, cancellation and publication are A1.5's,
unchanged. A Rust source asks with `exact_data::storage::request(
"fs.transformImage", …)` and the same record. On the wire to Ibex the
options travel as one JSON value rather than more positional numbers
(opcode 121 already carries five; LLP 1114.003 D3 would have made it nine).

**Tier 2:** `android.compressFormat: "webpLossless"`, since `image/webp`
does not say which (`Bitmap.CompressFormat.WEBP_LOSSLESS`, API 30). No
other word until a consumer asks. **Tier 3:** none. The codec holds
nothing between calls, and an app's own Swift or Kotlin can run ImageIO or
`ImageDecoder` on an `app:/` file itself, as LLP 1133.006 D6 reasons for
the clipboard.

### D19 — Cost

An app that does not import `@exact/photos` links none of it, derives no

## 10. The substitute

**`@exact/photos` is its own substitute,** in LLP 1133.008 D8 item 9's
split: under the agent the runner admits each call and holds the permission
tickets, and each implementation runs, told so, asks PhotoKit and
MediaStore for nothing and calls no hatch. Under the agent, on Apple and
Android (the web's implementation answers absence under the agent too, as
in production):

- **The library** is `packages/photos/fixture/`: six JPEGs, `agent-1` to
  `agent-6`, with fixed creation dates, one with EXIF orientation 6 and
  one in Display P3. Pictures are drawn from them at the size
  asked; a copy is the fixture's file, byte for byte.
- **Tickets.** A read while `photos` reads `prompt` holds a `permission`
  ticket: `tap @t allow` grants `full`; `tap @t limited` grants `limited`
  with the selection `agent-1` to `agent-3`; `deny` and `cancel` as
  geolocation's. An add while `photos-add` reads `prompt` holds its own.
  `managePhotoSelection` under limited access holds a `selection` ticket:
  `type @t agent-2,agent-5` sets the selection; `cancel` leaves it. On
  macOS it fails `NotSupportedError` under the agent too, as the target's
  restriction (LLP 1133.002 D14 step 2).
- **Preferred values.** `prefer extension photos.photoLibraryStatus={"access":"limited"}`
  and `prefer extension photos.selection=["agent-4"]`, which reach the
  implementation when set (LLP 1133.008 D8 item 9); the change announces
  the readers, as the platform's would.
- **Adds** go into the agent's library in the private store: they appear
  in `photoAssets` (under limited access too, by D6's rule), and
  `state.extensions` lists each with its SHA-256. Leaving the selection
  revokes the photo's pictures as the platform's change would (D2).

**Image has no substitute** (A1.6): the codec runs for real under
`--storage` on macOS, iOS, the web and, after stage 3, Android, and is
`unsupported` on Linux.

**Disclosure:** `state.extensions` lists the status, the selection, each
picture asked (its id, size and whether it was answered), each copy's
path, each add, and each answer's origin. **Production:** none of it.
