## Summary

An app decodes compressed video in its TypeScript data code with
WebCodecs' names, and shows the frames in a `video` element or samples
them in a GPU surface. Frames never pass through Contract, and on native
hosts they never return to data code:

```ts
import { VideoDecoder, EncodedVideoChunk, VideoTrackGenerator } from "@exact/webcodecs";

const screen = new VideoTrackGenerator();
const decoder = new VideoDecoder({ output: screen.writable, error: (e) => fail(e) });
decoder.configure({ codec: "avc1.640033", description: avcC, optimizeForLatency: true });
decoder.decode(new EncodedVideoChunk({ type: "key", timestamp: 0, data: nalUnits }));
return { trackId: screen.track.id };
```

```
video srcObject=device.trackId autoplay muted playsinline width="100%" height="100%"
canvas surface=phone(device.trackId, hinge) width="100%" height="100%"
```

The decode is the platform's: WebCodecs in the browser, VideoToolbox on
Apple; MediaCodec on Android and Media Foundation on Windows later.
Linux answers `NotSupportedError`. A GPU surface reads the track's
current frame as a `wgpu::TextureView` for the frame it renders, which is
WebGPU's `importExternalTexture` contract carried to wgpu (D5).

The consumer is the T3 Code clone's device streams: an iOS simulator's
H.264 over HTTP and an Android emulator's over a WebSocket. The clone
does this today in 4,295 lines of app-owned Swift: VideoToolbox, the
streams and their input, and SceneKit for the 3D viewers. With this
module the parsing moves to TypeScript, the 3D viewers to the app's GPU
crate, and the Swift goes (§12).

§3 records what was measured on 2026-10-21, including the alternative of
running the reference's own viewer in a bundled page (§11).

## 1. The consumer

The reference, T3 Code at `74541bab17`, decodes in the page
(`packages/client-runtime/src/device/stream.ts`, 1,405 lines):

- **One codec, H.264,** "High 5.1 without frame reordering"
  (`docs/internals/devices.md:108`). The codec string is `avc1.` and SPS
  bytes 1–3 (`stream.ts:193-197`). No HEVC, VP9 or AV1 in the device code.
- **Two framings.** serve-sim (iOS simulators) answers
  `GET …/helper/<id>/stream.avcc`, an HTTP body of envelopes: `u32` big-
  endian length, a tag byte (1 description, 2 key frame, 3 delta, 4 a
  JPEG seed), the payload (`stream.ts:256-302`). serve-emu (Android
  emulators) sends WebSocket binary messages with a 16-byte header (magic
  `SEMU`, a key flag, a `u64` presentation time) over Annex-B, decoded
  with no `description` (`stream.ts:199-249`, `:1194`).
- **The decoder:** `configure({codec, description, optimizeForLatency:
  true})` after `isConfigSupported` (`stream.ts:613-633`); chunks with
  `type`, `timestamp` and `data` (`:653-659`); deltas dropped until a key
  frame (`:637-640`); `decodeQueueSize > 8` resubscribes (iOS) or resets
  and asks for a key frame (Android, `:641-650`); an error falls back to
  MJPEG (iOS) or resets (Android, `:600-608`).
- **The sink:** each `VideoFrame` is drawn with Canvas 2D `drawImage`
  (`frame.ts:6-23`), then closed. The 3D viewers wrap that canvas in a
  three.js `CanvasTexture` (`phoneViewer.ts:74-81`; two for the Duo,
  `duoViewer.ts:62-79`), with `needsUpdate` set per frame.
- **Fallbacks:** MJPEG in an `<img>`, and WebRTC for a locked iOS stream
  (`stream.ts:711-718`, `:886-994`). The mobile app runs the same client
  in a `react-native-webview`, and prefers MJPEG for iOS devices
  (`apps/mobile/src/features/devices/device-stream.browser.ts:134`).

The clone (`examples/t3-code/modules/apple`, `3e0c90e7b5`) does the same in
Swift. `T3DeviceVideo.swift:156-239` is a `VTDecompressionSession`
(BGRA, IOSurface, `RealTime`), whose output becomes a `CGImage` on the
main queue (`:217-221`), set as a `CALayer`'s contents for the flat view
and as a SceneKit material's for the 3D ones (`T3DevicePhone.swift:478-485`).

## 4. Tier 1: WebCodecs

### D1 — WebCodecs' names, with one deviation

The decoder is [WebCodecs](https://www.w3.org/TR/webcodecs/)'
`VideoDecoder`: `configure(VideoDecoderConfig)`, `decode(EncodedVideoChunk)`,
`flush()`, `reset()`, `close()`, `state`, `decodeQueueSize`, the
`dequeue` event and `VideoDecoder.isConfigSupported(config)`. The config's
fields are WebCodecs': `codec`, `description`, `codedWidth`,
`codedHeight`, `displayAspectWidth`, `displayAspectHeight`,
`colorSpace`, `hardwareAcceleration`, `optimizeForLatency`. A chunk is
`new EncodedVideoChunk({type, timestamp, duration, data})`. Errors are
the specification's `DOMException`s: `NotSupportedError` for a config the
host cannot decode, `EncodingError` for bad data, `InvalidStateError`
for a call in the wrong state, `DataError` for a delta before a key
frame, and a `TypeError` for an invalid config.

The codec string is the registry's
([WebCodecs Codec Registry](https://www.w3.org/TR/webcodecs-codec-registry/)):
`avc1.*` with an `avcC` `description` or Annex-B without one, `hvc1.*`
and `hev1.*`, `vp09.*`, `av01.*`. Which of them a host decodes is the
host's answer to `isConfigSupported`, never a promise by Exact; H.264 is
the one every implemented target must decode.

**The deviation: `output` is a track's writable, not a callback.** In a
browser, `output` is a function called with each `VideoFrame`. Here it is
the `writable` of a `VideoTrackGenerator`, the standard sink of
[MediaStreamTrack Insertable Media Processing](https://w3c.github.io/mediacapture-transform/#video-track-generator),
and the decoder writes each frame there without calling data code. On the
web the implementation wires `output: (f) => writer.write(f)` itself. A
function `output` throws `TypeError` on every host, the web included, so
that a decoder written once runs everywhere. Reason: on a native host a
callback would carry every frame up into Hermes and its handle back down,
a crossing per frame for nothing data code needs. What data code needs
about frames (the first one, the size, counts) it gets as low-rate track
events (D3).

*Rejected for now:* both, a function `output` beside the writable, with
frames to data code as `VideoFrame` handles without pixels. The writable
would stay the fast path and the callback would keep the web's shape for
code ported as it is. It is not proposed because nothing the consumer does
needs a frame in data code, the crossing's cost is unmeasured, and a
frame handle without `copyTo` or drawing is a frame data code can do
nothing with. It returns with the first consumer that holds frames (§13);
§16 question 2 ruled (a).

### D2 — A track is a `video` element's source

`new VideoTrackGenerator()` makes a host-owned track; `generator.track`
is a `MediaStreamTrack` with the web's `id` (a string), `kind` `"video"`,
`readyState` and `stop()`. A track belongs to the data code that made it
and, like a socket handle (LLP 1016.000 D7), to that resource's
incarnation: forgetting the resource stops the track and closes its
decoders.

Contract names a track by its `id`, because a Contract value cannot hold
an object:

```
video srcObject=device.trackId autoplay muted playsinline
```

`srcObject` is the media element's DOM property
([HTML](https://html.spec.whatwg.org/multipage/media.html#dom-media-srcobject)),
spelled as LLP 1042 spells DOM properties (`currentTime`, `paused`). Its
value in Contract is a track id: a **declared deviation**, since the web's
value is a `MediaStream`. A video with `srcObject` ignores `src`, as HTML
does. An id no live track has shows the element's empty box and reports
`error("src-not-supported")`, HTML's code for a source that cannot play.

A live track plays as a `MediaStream` does in Chrome: no duration
(`durationchange` reports none), `currentTime` advancing while playing,
`loadedmetadata` at the first frame, and one event the element gains for
every source, HTML's `resize`, when `videoWidth` or `videoHeight`
changes. `state.media` reports them as it does today. Seeking, `loop`,
`playbackRate` and `fastSeek` do nothing on a live track, as in a
browser. The kernel still owns only the box; the frame's size reaches
layout through the intrinsic-size seam as a file's does (LLP 1042 §2).

### D3 — The decoder lives in data code, its frames below it

A decoder is made, configured and fed in data code, typically in a
WebSocket mapper (LLP 1016.000 D7), which receives each binary message:

- **What crosses.** On native hosts, `decode` copies the chunk's bytes
  once into the host and returns.
- **`decodeQueueSize`** counts decode requests not yet accepted by the
  codec, as WebCodecs' control queue does: up by one at `decode`, down when
  the host hands the chunk to the platform decoder
  (`VTDecompressionSessionDecodeFrame` returns), reported at the next
  turn with a `dequeue` event. It does not wait for the frame to come out:
  a codec that holds or drops output does not move the count. WebCodecs
  updates it from queued tasks too, so a read between turns is the web's.
- **When it runs: at once, a declared exception to commit staging.**
  `configure`, `decode`, `flush`, `reset` and `close` act when called, in
  any turn of the data code that owns the decoder: a resource's answer, an
  answer's continuation, a mapper, a mutation. They are not staged until a
  commit stands, as a socket's send is (LLP 1016.000 D7,
  `host/web-js/ts-stream.js:103-121`). So `state`, `decodeQueueSize`, a key
  frame's requirement and the host's decoder always agree; there is
  nothing to roll back. What a refused commit cannot undo is the picture:
  a frame decoded in a turn whose snapshot was refused still shows. That
  is the failure the exception accepts, and the journal names it
  (`decoder ran in a refused turn`). Reason: the decoder's effect is a
  picture, which no other party, store or server sees, and staging it
  would make a decoder's state differ from the facade's whenever a turn
  is refused. Staging, with a rollback of the facade's state, was §16
  question 7's alternative, not chosen.
- **Promises.** `flush()` and `isConfigSupported()` return promises that
  are host work, registered as storage's are (`js/src/prelude.js:207-215`),
  so an answer may `await` them on every host: `decode(…); await
  decoder.flush(); return snapshot` resolves once the host reports the
  outputs, with no commit in between. A mapper, which cannot await
  (`js/src/prelude.js:1404`), calls them without awaiting. `reset()` and
  `close()` reject a pending `flush()` with `AbortError`, as WebCodecs
  does; forgetting the owning resource closes the decoder.
- **Errors** reach `error` in a later turn, as in a browser, and close
  the decoder. The journal records configure, reset, close and each
  error, never a chunk.
- **Track events.** The track's frames go to `video` and canvases without
  data code. Data code hears of them at low rate: the stream that owns
  the track (the resource whose incarnation made it, D2) receives a
  `track` event through its mapper at the first frame, at each size
  change and when the track ends: `{type: "track", trackId, width,
  height, stats}`, where `stats` is
  [`MediaStreamTrackVideoStats`](https://w3c.github.io/mediacapture-extensions/#the-mediastreamtrackvideostats-interface)'
  `deliveredFrames`, `discardedFrames` and `totalFrames`. This is a
  declared deviation (the web's track has no such event); it is what the
  consumer's first-frame timeout and size need when only a canvas shows
  the track. A stream that goes silent after one frame sends no more
  events; the app's timeout is a Contract `task … after` over the
  snapshot the first event settled. `track.stats` and `getSettings()`
  (`width`, `height`, `frameRate`) are also readable in any turn.

### D4 — Presenting a track

A track keeps the latest frame only, as a live stream does: a frame
replaces the last one undisplayed, so a slow presenter drops frames and
never queues them. Every reader (each `video`, each canvas) presents the
latest frame at its next display tick.

### D4.1 — The web's fan-out, frame by frame

Specified 2026-10-23 before stage 1 builds the track doors, as §15
requires (Sol r3 #5); not reviewed. On the web the decoder's output is a
`VideoFrame` the page must close, and a track has up to three kinds of
reader: its `video` elements through the engine's track door (§3), a
WebKit worker that owns the standard `VideoTrackGenerator`, and each GPU
artifact's canvases (D5, stage 3). Each reference has one owner, who
closes it:

| Reference | Made | Owner | Closed |
|---|---|---|---|
| `current` | the decoder's output frame itself | the track | when the next frame replaces it, or the track ends |
| Chrome's write | `current.clone()`, one per write | the `MediaStreamTrackGenerator`'s writable once `write` is called | by the writable; by the track if `write` rejects |
| WebKit's transfer | `current.clone()`, transferred with `postMessage(frame, [frame])` | the worker | by the worker after its generator's `write`, or when that rejects |
| Firefox's draw | nothing: `drawImage(current)` into the hidden canvas whose `captureStream()` the `video` plays | — | — |
| a GPU artifact's | `current.clone()`, pulled when one of its canvases begins a render and the generation changed | that artifact's glue | as `copyExternalImageToTexture` returns |

Replacement keeps D4's rule, the latest frame and no queue, at every door:

- **The writer** has at most one `write` in flight. A frame that arrives
  while one is pending only replaces `current`; when the write settles,
  the door writes a clone of `current` if its generation is newer than
  the last written. A slow sink sees fewer frames, never older ones.
- **The WebKit worker** has at most one frame in flight: the window
  transfers the next clone when the worker acknowledges the last, and
  only if `current` is newer. The worker made the generator once, at the
  track's creation, and transferred its track to the window, where each
  `video`'s `MediaStream` holds it.
- **Firefox's canvas** draws `current` once per animation frame when the
  generation changed; nothing is cloned.
- **A GPU artifact** pulls, so nothing waits in it: the render that
  begins reads `current`, which D5 already makes the frame of that
  render.

A failed write is cleaned up by whoever made the reference: a rejected
`write` closes its clone (closing a closed frame does nothing), and the
door stops writing until the track is replaced; a `postMessage` that
throws (`DataCloneError`, a frame closed meanwhile) closes the clone and
the next frame is sent as usual. When the track ends (its `stop()`, or
its resource forgotten, D2), the track closes `current`, closes the
writer, posts the worker its end (the worker closes what it holds and
ends its generator), and stops the canvas stream's track; a frame the
decoder outputs after that is closed at once. Several `video` elements
on one track share the door's one `MediaStreamTrack`: no frame is cloned
per element.

### D5 — A track in a GPU surface

A canvas surface takes the track id as an argument and reads the
track's current frame while it renders:

```rust
fn render(&mut self, frame: &Frame, device: &wgpu::Device, queue: &wgpu::Queue,
          encoder: &mut wgpu::CommandEncoder, target: &wgpu::TextureView,
          format: wgpu::TextureFormat) -> bool {
    if let Some(screen) = frame.video(&self.track) {
        // screen.view: &wgpu::TextureView, Rgba8UnormSrgb; screen.width, screen.height;
        // screen.generation changes with each new frame.
    }
    …
}
```

The contract is WebGPU's
[`importExternalTexture`](https://www.w3.org/TR/webgpu/#dom-gpudevice-importexternaltexture):
the texture is the frame current when this render began, valid for that
render only, and re-read on the next one. A new frame on a bound track
asks every canvas bound to it for a render (LLP 1009 D4: something to
render). Colour is converted to sRGB with the frame's own matrix,
primaries, transfer and range, as the reference's `CanvasTexture` with
`SRGBColorSpace` shows it.

**The hand-over.** The host keeps one current frame per track: on the
web a `VideoFrame`, on Apple a retained `CVPixelBuffer`. A GPU artifact
has its own device (LLP 1009 D6; `host/web/gpu-modules.js:7`), so the
host hands each artifact with a canvas that reads the track its own
reference: a `VideoFrame.clone()` on the web, the same IOSurface,
retained for that artifact, on Apple. It hands one at each new frame, and
the current frame again when such a canvas mounts and when an artifact's
device is recovered, so a still picture is not lost. The host releases a
frame when it has been replaced and every artifact has released its
reference. Each reference carries a descriptor:

| Field | Meaning |
|---|---|
| `track`, `generation` | the track's id and a count that rises with each frame |
| `format` | Apple only: `nv12` or `bgra8`, which the host asks VideoToolbox for; a 10-bit or 4:4:4 stream is refused by name there and the canvas keeps the last frame. The web's `VideoFrame` is copied as the browser holds it (I420, NV12 and BGRX were seen, §3), with no format rule |
| `coded`, `visible`, `display` | the coded size, the visible rectangle within it, the display size |
| `matrix`, `primaries`, `transfer`, `fullRange` | WebCodecs' `VideoColorSpace` fields, from the `VideoFrame` on the web and the pixel buffer's attachments (`kCVImageBufferYCbCrMatrixKey` and its siblings) on Apple |
| the pixels | the `VideoFrame` on the web; the `IOSurfaceRef` on Apple |

Ownership and order:

- **Web.** The host's glue hands the module's glue its clone; the
  module calls `Queue::copy_external_image_to_texture`
  (`ExternalImageSource::VideoFrame`) into its texture for the track and
  closes the clone when the call returns, since WebGPU reads the source
  when the copy is issued.
- **Apple.** The host retains the `CVPixelBuffer` and hands the module
  its IOSurface through a new export, `gpu_video_frame(descriptor)`, as
  `gpu_texture_metal` hands an `MTLTexture` (`gpu/src/lib.rs:1225-1294`:
  retained, reused when unchanged). The module makes a texture of each
  plane on its own device and records the conversion into the track's
  texture in the tick's encoder before the tick's first surface
  `render`, so every draw of that tick samples one pinned generation
  (surfaces record into that encoder before `flush` submits it,
  `gpu/src/frame.rs:219`, `:349`, `:385`). It
  holds the buffer until the command buffer that read it completes
  (`Queue::on_submitted_work_done`), then releases it; a newer frame
  arriving first replaces the pending one, which is released unread.
- **Readers.** Every canvas of one artifact reading a track samples that
  artifact's one converted texture of the current generation, so several
  readers cost one conversion per artifact; the texture is made again
  after its device is recovered. `reset` keeps the last frame; the track's end makes
  `frame.video` answer `None` from the next render.

**Why a `TextureView`, not wgpu's `ExternalTexture`.** WGSL's
`texture_external` would sample the planes without the conversion pass.
But wgpu 30 has it on Metal and DX12 only, not on Vulkan, and not on its
WebGPU backend (§2), so a surface written for it would not run on the
web, Linux or Android. One `texture_2d<f32>` binding runs on every
host. The pass costs one full-screen draw per new frame per track,
measured at stage 3; `ExternalTexture` becomes a tier 2 word on Apple and
Windows if that measurement says so.

## 5. Tier 2 and tier 3

### D6 — The platforms' words

Options on `configure`, under the platform's key (LLP 1133 D2):

| Word | Platform name | Beats |
|---|---|---|
| `apple.realTime` (bool) | [`kVTDecompressionPropertyKey_RealTime`](https://developer.apple.com/documentation/videotoolbox/kvtdecompressionpropertykey_realtime) | `optimizeForLatency`; VideoToolbox's own default is true (`VTDecompressionProperties.h`) |
| `apple.requireHardware` (bool) | [`kVTVideoDecoderSpecification_RequireHardwareAcceleratedVideoDecoder`](https://developer.apple.com/documentation/videotoolbox/kvtvideodecoderspecification_requirehardwareacceleratedvideodecoder) | `hardwareAcceleration="prefer-hardware"`, a preference |
| `apple.maximizePowerEfficiency` (bool) | [`kVTDecompressionPropertyKey_MaximizePowerEfficiency`](https://developer.apple.com/documentation/videotoolbox/kvtdecompressionpropertykey_maximizepowerefficiency) | nothing in tier 1; true sets `RealTime` false, since Apple calls the two together undefined (`VTDecompressionProperties.h`) |
| `android.lowLatency` (bool, later) | [`MediaFormat.KEY_LOW_LATENCY`](https://developer.android.com/reference/android/media/MediaFormat#KEY_LOW_LATENCY) | `optimizeForLatency` |

`apple.maximizePowerEfficiency=true` beside `apple.realTime=true` or
`optimizeForLatency=true` is an invalid config: `configure` throws and
`isConfigSupported` rejects, both with `TypeError`, as WebCodecs does for
an invalid config. The consumer needs none of these words;
`optimizeForLatency` is its word.

### D7 — Access hatches

On Apple the module hands the app's Swift its `VTDecompressionSession`
after creating it and before the first decode, and owns its output
callback, its `RealTime` property and its invalidation. An app may set
other properties. No hatch on the web, where the browser holds the
decoder. The consumer uses none.

Common uses of VideoToolbox and MediaCodec, and the tier that reaches each:

| Use | Tier |

## 7. Unsaid defaults

- `hardwareAcceleration` unsaid is `"no-preference"`: the platform
  chooses, which on Apple is VideoToolbox's default (hardware where the
  chip has it).
- `optimizeForLatency` unsaid is false, as in WebCodecs, and sets
  nothing on Apple, where VideoToolbox's default is already real time;
  true sets `RealTime` explicitly.
- A `video` with `srcObject` and no `controls` draws no controls, as
  Chrome's does for a stream; `object-fit` is `contain`, the video UA
  default (LLP 1042 §2).
- A live track's `video` pauses off screen by LLP 1042 §7 B's rule only
  when `autoplay` started it and `paused` is unbound, as for a file.

## 8. Packaging and callers

### D8 — exact2's vocabulary, with its names imported

LLP 1133 D5 makes an extension the default and asks a reason for
vocabulary. The decoder is vocabulary, a data capability beside `fetch`
and `crypto`, for three reasons:

1. **Its input is bytes, which never enter Contract,** like a fetch body.
   An extension's sends and sources are Contract's (LLP 1133.002 D13).
2. **Its output goes where only the host is:** the `video` element's
   presenter and the GPU module. No package seam reaches either.
3. **Its rate.** LLP 1133 D6 rule 1 gives every module call the runner's
   admission, a journal line and a `state.extensions` count. A decode is
   called 60 times a second.

The names are still imported (LLP 1133 §0 ruling 2): data code imports
`VideoDecoder`, `EncodedVideoChunk` and `VideoTrackGenerator` from
`@exact/webcodecs`, and the bake refuses the bare globals, as it refuses
`navigator`. `packages/webcodecs` holds the interface's TypeScript types,
the support table and the conformance suite; the implementations are in
the runtimes and hosts. A third party cannot replace them until the
track seam is public (§13).

### D9 — Callers, and the bytes that feed them

- **Contract** reads none of the module's names; it reads a track id
  from a resource's answer and binds it to `video srcObject=` or a
  canvas surface's arguments.
- **TypeScript** calls every name. None is a request (nothing prompts);
  none is `sync` in LLP 1133 D6 rule 4's sense. `isConfigSupported`
  returns a promise, as on the web.
- **Rust** data code: later. Its typed request is the same shape as the
  prelude's door ops, once a Rust consumer asks.

**The bytes.** The Android stream is a WebSocket, which data code already
reads (LLP 1016.000 D7). The iOS stream is an HTTP body of binary
envelopes, and no streamed answer carries one: SSE is text, a WebSocket
is not HTTP. This RFC asks LLP 1016.000 for a **byte stream**:
`fetch(url, { exactStream })` on a response that is not
`text/event-stream` gives the mapper a `message` whose `data` is an
`ArrayBuffer` of the bytes read since its last turn, at arbitrary
boundaries: several transport reads join into one message, so the number
of turns follows the mapper's pace, not the transport's chunking, and no
byte is dropped or reordered. D7's 1 MiB queue bound holds; overflow ends
the stream with a visible error, as for a socket. That is an amendment of its own,
reviewed and ruled with this one (§16 question 3).

**The throughput gate.** Each incoming message is mapped, then its
snapshot settles (LLP 1016.000 D7). A WebSocket stream sends a message
per frame, 60 a second; an HTTP body's messages follow its byte
boundaries, so one frame may take several, and no rate is assumed. A Duo
has three streams. Before the API is fixed, stage 0 measures it on macOS
and the web.

- **Input:** recorded streams, replayed by a local server at their
  recorded timing and chunking: a serve-sim `stream.avcc` body and a
  serve-emu WebSocket, each 60 fps H.264 at the simulator's screen size,
  including key-frame bursts; one stream and three at once; and the HTTP
  body again with its chunks deliberately split small.
- **Path:** the real mapper parsing the framing and calling `decode`,
  answering an unchanged snapshot. On the web the browser's decoder; on
  macOS the door op that copies the bytes into the host and drops them,
  since the platform decoder's own cost is not what is being decided.
- **Timing:** four stamps per chunk, taken in a development build and
  read by `perf` (LLP 1079): transport receipt, mapper entry, the
  decode call reaching the host, and the commit standing; and the
  measured message and commit rates per stream.
- **Pass, as ruled (§16 question 8):** with three streams for 60 s, no
  queue overflow and no frame dropped by the path; receipt to decode p95
  under 8 ms (half a frame) and p99 under 16 ms; the data executor's busy
  time under 25% of one core; the main thread's frame time unchanged
  within the noise of a run without streams.

If it fails, the alternative is that the host demuxes a declared framing
(`avcC` envelopes, `SEMU` over Annex-B) straight into the decoder, and data
code handles only control. That is a narrower API; it is the fallback,
not the proposal.

## 10. Grant, substitute and cost

**Grant: none.** Decoding asks for no permission on any platform and
has no Info.plist key, entitlement or `Permissions-Policy` feature. The
bytes come through `net.websocket` or `net` as before.

**Substitute (LLP 1069.007 D7).** The module has no request and no
ticket: the agent's drive runs the real decoder on every host that has
one. `state.media` gains `decoders` (codec, state, `decodeQueueSize`,
decoded, dropped, errors) and `tracks` (id, frames, size, readers).
`prefer webcodecs=absent` makes a host answer as Linux does, so a drive
tests the app's fallback (the consumer's MJPEG). Whether the agent's
macOS and iOS screenshots include an `AVSampleBufferDisplayLayer`'s
picture is unmeasured; stage 2 checks it, and if not, the screenshot
draws the track's latest frame into the video's box.

**Cost.** A binary that does not import `@exact/webcodecs` carries none of
it: the TypeScript binding is a prelude chunk the bake includes on
import, VideoToolbox is linked by the video artifact, and the GPU export
is in the module of an app whose surface reads a track. The video
artifact loads at the first video creation (LLP 1042 §2) or the first
decoder's `configure`, whichever comes first, never before first pixel,
so a canvas-only viewer loads it too. Until it has loaded, the host
queues the decoder's operations in order and `decodeQueueSize` counts
them. Nothing runs before first pixel. The
sizes are measured by LLP 1047's probe at stage 2.

## 11. The alternative: the reference's viewer as a bundled page

LLP 1020.001 serves an app's bundled pages in an iframe at
`exact-app://app` on Apple, and the reference's mobile app runs its
device client in a web view. The clone could bundle that client and
three.js, open it in an iframe per device, and send it the server origin
and ticket with `postMessage(text, iframeId)`.

Measured (§3): in a WKWebView on macOS at that origin, top level and in an
iframe, WebCodecs decodes H.264, a guest WebSocket to the loopback reads
binary messages, and `importExternalTexture` takes a decoded frame. iOS
was measured in the simulator's Mobile Safari, not in a WKWebView inside
an app.

Not measured, and each a precondition:

- **CORS for `stream.avcc`.** The page's `fetch` to the T3 server is
  cross-origin from `exact-app://app`; the server must answer with
  `Access-Control-Allow-Origin` for it. A WebSocket has no CORS, but a
  server may check its `Origin`.
- **Guest pointer input** as a verified row (LLP 1020 §5's "guest
  focus/keyboard as a verified row"), which drag-to-touch and keys need.
  The agent's `tap` and `type` reach a guest's DOM already, as untrusted
  script-dispatched events (LLP 1020 D4, `host/apple/Sources/ExactKit/WebModule.swift:379-461`); a
  person's drag and keys in a native window are not verified.
- **A web view per panel:** memory and first-frame time for a Duo's three.

The agent is not blind in the page: its `tree` shows a guest's DOM
outline and its `screenshot` composes the guest's pixels (LLP 1020
D4). The device's screen is pixels without structure either way; what
the module adds is `state.media`'s decoder and track counts.

So the page is a bridge, not an end state. It ships the reference's own
behaviour sooner, but gives no other app a decoder, adds a web view's
tells to a native window (LLP 1115), keeps the 3D viewers in three.js
rather than the app's GPU crate, and has two unmeasured preconditions
(CORS, a person's input). §16 question 5 ruled against building it first.

## 16. Rulings (Daehyeon Mun, 2026-10-23)

Each question below was ruled as proposed.

1. **Vocabulary or extension** (D8)? Proposed: vocabulary, names
   imported from `@exact/webcodecs`. **Ruled:** vocabulary. Its input is
   bytes, its sinks exist only in the host (`video`, the GPU module), and
   it is called 60 times a second.
2. **`output`** (D1): (a) a track's writable only, a function refused on
   every host (proposed); (b) both, the writable as the fast path and a
   function receiving pixel-less `VideoFrame` handles, a crossing per
   frame on native hosts; (c) the web's callback only. **Ruled:** (a).
   Nothing the consumer does needs a frame in data code; (b) returns with
   the first consumer that holds frames.
3. **The byte stream** (D9): amend LLP 1016.000 with this RFC, or
   separately first? The iOS stream needs it. **Ruled:** with this RFC,
   built first as stage 0 in its own PR, and recorded in the same
   `rules/DEFERRED.md` entry. It is the throughput gate's input.
4. **`TextureView` now, `ExternalTexture` later** (D5)? **Ruled:** as
   proposed. wgpu 30 has no `ExternalTexture` on Vulkan or its WebGPU
   backend, and one `texture_2d` runs on every host.
5. **The bundled page** (§11): build it first as a bridge, or go straight
   to the module? Proposed: straight to the module; the page's CORS and
   a person's input in it are unmeasured. **Ruled:** straight to the
   module. The bridge gives no other app a decoder, keeps three.js and
   adds a web view's tells.
6. **Targets:** web, macOS and iOS first; Android, Windows and tvOS
   later; Linux later, answering `NotSupportedError` until its host has
   a media stack; the terminal absent (§9)? **Ruled:** as proposed.
7. **When decoder operations run** (D3): at once, a declared exception
   (proposed), or staged until the commit stands, as socket sends are,
   with the facade's state rolled back when a turn is refused? At once,
   a refused turn's effects stay: a picture it decoded shows, a `reset`
   it made discarded the decoder's queued work and its next chunk must be
   a key frame, and a `close` it made closed the decoder and rejected its
   pending `flush` with `AbortError`; recovery is the app's, by making and
   configuring a new decoder, as after an error. Staged, none of those
   happen, but the facade must keep a second copy of the decoder's state
   to roll back, which r2 found incoherent when written. **Ruled:** at
   once, as a declared exception, with the effects above. This resolves
   Sol r3 #1.
8. **The gate's budgets** (D9): the numbers proposed there, or others.
   **Ruled:** the proposed numbers (stage 0). If the gate fails, the
   host-demux fallback is used.

**Trade** (`rules/DEFERRED.md`): `QUEUE.md`'s "Re-measure VideoArm's
position read with many autoplaying videos" moves to Later: a video-lane
measurement with no consumer, whose attention moves to the decoder.
