## Summary

Screen capture is three things an app asks for, and the web names all
three with one call, [`getDisplayMedia`](https://w3c.github.io/mediacapture-screen-share/):

1. **What the person chooses to share,** a screen or a window, picked in
   the platform's own picker every time (W3C: "the user agent MUST let the
   end-user choose which display surface to share out of all available
   choices every time").
2. **The app's own pixels,** the current tab in the web's words
   (`preferCurrentTab`), narrowed to one element by Element Capture's
   [`restrictTo`](https://screen-share.github.io/element-capture/).
3. **A window named by the app, with no picker,** which the web does not
   have and macOS does (ScreenCaptureKit with the Screen Recording
   permission). This is tier 2.

```
use getDisplayMedia from "@exact/screen-capture"
use stopTrack, MediaStream from "@exact/media-capture"
use startMediaRecorder, stopMediaRecorder, MediaRecorderInfo from "@exact/recording"

action recordScreen
  send screen = getDisplayMedia(video=true)
  then send take = startMediaRecorder(stream=screen.id, mimeType="video/mp4",
                                      path="app:/data/takes/screen-3.mp4")
```

The answer is a `MediaStream` whose video track joins the session's track
table that `@exact/media-capture` keeps (LLP 1133.009 §3), beside the
microphone's and the camera's tracks; `stopTrack` and `mediaStreamTrack`
work on it unchanged. The one consumer of its frames in this RFC is the
recorder: `startMediaRecorder` records a display track to an H.264 MP4
(D6). Frames never reach data code (LLP 1133.003 D4).

Five decisions carry it:

- **The person's choice is the platform's picker, and nothing else
  answers it** (D2). `SCContentSharingPicker` on macOS and on iOS 27,
  MediaProjection's consent on Android, the browser's picker on the web.
  A tool invocation or a wake never starts a capture.
- **The app's own pixels are the host's own rendering, with no prompt**
  (D3), as the browser shell's picture of a frame needs no grant (LLP
  1020.002 D7): it reaches nothing the app does not already have. `restrictTo(track=, element=)` narrows them to one
  element, which is how the T3 Code clone records its browser panel.
- **A picker's track never idles** (D4). Unlike a camera, it cannot be
  reopened without asking the person again, so it is live from the
  picker's answer until `stopTrack`, the person's stop in the platform's
  own control, or the session's end. Self capture asks nothing, so it
  idles as a camera does (D3).
- **A display track is a frame source in the shared track table** (D5),
  where a camera is a capture graph: the platform hands the host frames,
  and the host hands them to each consumer.
- **Android's capture runs in a foreground service the host owns** (D11
  item 3), since MediaProjection requires one from API 29. It is the first
  client of a seam the roster's `foreground-service` module and
  recording's Android background (LLP 1133.009 D7) also need.

The consumers: the T3 Code clone's browser recording (LLP 1020.002 D8,
which calls this B10) and SnapShot shortcut (LLP 1133.025 §12.1), both on
macOS, which set the shape; and a small real feature on main, the
recorder's "Record screen", which drives the person's choice on the web,
macOS, iOS and Android (§9). Every drive captures a fixture: a synthetic
picture under the agent, the fixture's own window, or an emulator's own
screen. No drive captures this Mac's screen or a phone's (§9.4).

## 0. What is new here

1. **A device whose consent cannot be kept.** A camera grant is asked
   once; a screen share is chosen each time, on every platform. The web
   forbids keeping it ("The user agent MUST NOT store a "granted"
   permission entry"), Android 14 requires consent "before each capture
   session"
   ([behavior changes](https://developer.android.com/about/versions/14/behavior-changes-14)),
   and macOS grants a picker's choice "for the duration of the screen
   capture session"
   ([WWDC23 10053](https://developer.apple.com/videos/play/wwdc2023/10053/)).
   So the permission fact is `prompt` while capture is possible (D9), and
   a track that stops is gone (D4).
2. **A video producer that is not a capture graph.** The camera's preview
   and photo are outputs of AVFoundation's and CameraX's graphs (LLP
   1133.008 D3). Screen capture hands the app finished frames
   (`CMSampleBuffer` from `SCStream`, an `Image` from a `VirtualDisplay`),
   so the track table needs a second kind of video entry (D5).
3. **The app's own pixels as a source.** No module has captured the host's
   own rendering continuously. The agent's screenshot and the browser
   shell's frame snapshot do it once (LLP 1020.002 D7); D3 does it at a
   frame rate.
4. **A capture that outlives the foreground on purpose.** Sharing another
   app's window is the point of screen capture, so the app is often in
   the background while it runs. That is allowed on macOS, needs a
   foreground service on Android and a background mode on iOS (D9).

## 1. What exists

**On the web,** `navigator.mediaDevices.getDisplayMedia(options)` answers a
`MediaStream` after the browser's picker: Chrome 72, Edge 79, Firefox 66,
Safari 13 on the desktop; Safari on iOS 27; not Chrome on Android, where
it "was exposed, but always failed with NotAllowedError" until it was
removed ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia)).
The specification is a Working Draft
([W3C Screen Capture, 2026-08-27](https://www.w3.org/TR/2026/WD-screen-capture-20260827/)).
Element Capture is Chrome 132 on the desktop, "only enabled for
self-capture for now"
([Chrome](https://developer.chrome.com/docs/web-platform/element-capture)).
`MediaRecorder` writes H.264 in MP4 in Chrome 126 and Safari 14.1, not in
Firefox ([Chrome Platform Status](https://chromestatus.com/feature/5163469011943424),
[WebKit](https://webkit.org/blog/11353/mediarecorder-api/),
[Mozilla bug 1631143](https://bugzilla.mozilla.org/show_bug.cgi?id=1631143)).

**On Apple,** ScreenCaptureKit is the capture API on macOS 12.3 and later,
and on iOS, iPadOS and tvOS 27, where it "replaces ReplayKit for screen
streaming and mirroring. A broadcast extension is no longer necessary"
([ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit)).
ReplayKit's `startCapture` is deprecated in 27.0: "Use ScreenCaptureKit
SCStream with SCStreamOutput instead"
([RPScreenRecorder](https://developer.apple.com/documentation/replaykit/rpscreenrecorder/startcapture(handler:completionhandler:))).
The system picker, [`SCContentSharingPicker`](https://developer.apple.com/documentation/screencapturekit/sccontentsharingpicker),
is macOS 14 and iOS 27.

**On Android,** [MediaProjection](https://developer.android.com/media/grow/media-projection)
from API 21, with a foreground service of type `mediaProjection` required
from API 29 and consent per session from API 34.

**On Windows,** [`Windows.Graphics.Capture`](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/screen-capture)
from Windows 10 1803, with `GraphicsCapturePicker`.

**On Linux,** a desktop session's capture is the
[ScreenCast portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html)
over PipeWire. exact2's Linux host is not a desktop client: it owns the
display through DRM/KMS, or runs headless (`host/linux/src/display.rs`).

**In exact2:**

- `@exact/media-capture` opens the microphone and the camera, keeps a
  per-session track table (`ExactTrackEntry`, `ExactTrackOwner`,
  `ExactTrackConsumer` in `host/apple/modules/ExactPackage.swift`), and
  names `stopTrack`, `mediaStreamTrack` and `setTrackEnabled`.
- `@exact/recording`'s `startMediaRecorder` records audio only: the web
  implementation filters the stream to `kind === 'audio'`, and the Apple
  one answers `NotSupportedError` without an audio track.
- The host draws its own window for the agent's screenshot
  (`PaintCapture.swift`'s paint-order copy, each web view's
  `takeSnapshot`), and the browser shell writes a frame's picture to a
  file with no grant (LLP 1020.002 D7).
- LLP 1133.003 makes a track a host-owned object named by id, with
  `video srcObject=` and latest-frame-only delivery (D4), and keeps frames
  out of data code on native.
- `rules/DEFERRED.md` lists `getDisplayMedia` among recording's "still out,
  each until a consumer asks" (LLP 1133.009 §13), and video recording
  among the camera's (LLP 1133.008 §12).

**In the T3 Code clone** (`examples/t3-code` on `daehyeon/t3-code-main`),
two features capture today without a module:

- **Browser recording** (`T3BrowserRecorder.swift`, 725 lines;
  `browser-recording.ts`, 561): records the browser panel's guest frame to
  an MP4. It polls `WKWebView.takeSnapshot` at the frame rate with at most
  two in flight, writes H.264 through `AVAssetWriter` at a variable frame
  rate, draws the cursor with a page script, and draws key and click
  badges with a native compositor (`T3RecordingDecorations`). The data
  code calls `getDisplayMedia(tabId, {audio: false, video: {frameRate:
  {ideal, max}}})` through a host seam, then `MediaRecorder`.
- **SnapShot** (`T3SnapShot.swift`, 541): a global shortcut captures the
  frontmost other app's window by running `/usr/sbin/screencapture -l
  <windowId>`, after `CGPreflightScreenCaptureAccess` finds the Screen
  Recording permission.

## 2. Tier 1

### D1 — `getDisplayMedia`, in the web's names

```
getDisplayMedia(video=, audio=, preferCurrentTab=, selfBrowserSurface=,
                surfaceSwitching=, monitorTypeSurfaces=, systemAudio=,
                windowAudio=) -> MediaStream
restrictTo(track=, element=) -> MediaStreamTrack
displayCaptureStatus() -> DisplayCaptureStatus      // a live fact
```

`getDisplayMedia` takes [`DisplayMediaStreamOptions`](https://w3c.github.io/mediacapture-screen-share/#dom-displaymediastreamoptions)
as keyword arguments, and answers media-capture's `MediaStream` shape, as
`getUserMedia` does (LLP 1133.009 D1). Each option:

| Option | Meaning | Native |
|---|---|---|
| `video` | `true`, or constraints: `width`, `height`, `frameRate`, and `displaySurface` as the picker's suggested pane. `false` is the web's `TypeError` | width, height and frame rate configure the stream (`SCStreamConfiguration`, the `VirtualDisplay`'s size); `displaySurface` picks the picker's style (`SCShareableContentStyle` `.window` or `.display`) |
| `audio` | ask for the surface's audio | accepted; no audio track in this RFC (§4) |
| `preferCurrentTab` | offer the current tab | the app's own pixels, D3 |
| `selfBrowserSurface` | `include` or `exclude` the capturing document from the picker | macOS: `exclude` sets the picker configuration's `excludedBundleIDs` to the app's own |
| `surfaceSwitching` | let the person change the shared surface mid-capture | macOS: `allowsChangingSelectedContent` |
| `monitorTypeSurfaces` | offer whole screens or not | macOS: `exclude` removes the display modes from `allowedPickerModes`; Android: none before API 37 |
| `systemAudio`, `windowAudio` | which audio may be offered | accepted, no effect (§4) |

`preferCurrentTab` is Chrome's, outside the specification (MDN's
compatibility data marks it non-standard; Chrome 94). It is the name the
T3 clone's web oracle uses for the case D3 serves, so it is the tier 1
name. `controller` (`CaptureController`, focus behaviour) is out: it
decides which window is focused after a browser tab is chosen, which has
no native counterpart (§11).

**Errors,** the specification's: `NotAllowedError` when the person
cancels the picker, the platform refuses (a policy, an MDM profile), or
the call lacks the person's origin; `NotSupportedError` where the target
has no cell or the option has no meaning there; `NotReadableError` when
the platform fails to start the capture; `AbortError` when the session
ends while the picker is up; `TypeError` for `video=false`. A web
`InvalidStateError` for a call outside transient activation is reported
as `NotAllowedError`, the code admission gives a call without a person's
origin, so the app sees one name for one cause (a declared deviation).

**Settings.** `mediaStreamTrack(track=)` answers the track as for any
track, with the display surface's settings beside `width`, `height` and
`frameRate`:

```
shape DisplaySettings                      // in MediaStreamTrack.settings
  displaySurface: enum<monitor|window|browser>
  logicalSurface: bool
  cursor: enum<never|always|motion>
```

`displaySurface` is `browser` for the app's own pixels (D3): the web's
word for the capturing document's own surface. `logicalSurface` is true
for a window, which is captured whole even where covered.

**`displayCaptureStatus()`** is a fact source (LLP 1133.002 D5) a view
reads before it shows a "Record screen" button:

```
shape DisplayCaptureStatus
  available: bool                          // getDisplayMedia can ask here
  state: enum<granted|prompt|denied|unknown>
  surfaces: enum<monitor|window|browser>[] // what the picker can offer
  selfCapture: bool                        // preferCurrentTab gives D3's capture
  restrictTo: bool                         // restrictTo works here
```

### D2 — The person's choice is the platform's picker

Without `preferCurrentTab`, `getDisplayMedia` shows the platform's picker
or consent, and only its answer starts a capture:

| Target | What the person sees | What may be chosen |
|---|---|---|
| web | the browser's picker | a screen, a window, a tab, as the browser offers |
| macOS 14 and later | `SCContentSharingPicker`, presented with the style `video.displaySurface` suggests | a display, a window, an application's windows |
| iOS, iPadOS 27 and later | `SCContentSharingPicker`, `present(using: .display)` or `.window` | the display or this app; `SCShareableContent` and `SCContentFilter`'s initializers are unavailable on iOS, so the filter comes only from the picker |
| Android 10 (API 29) and later | MediaProjection's consent, from `createScreenCaptureIntent()` | the whole screen, or from Android 14 QPR2 a single app ([media projection](https://developer.android.com/media/grow/media-projection)) |

**Why the picker and not an exact2 sheet.** The picker is the consent on
every platform. macOS lets an app capture what its picker returned
without the Screen Recording permission: "your app is permitted to record
selected content for the duration of the screen capture session. This
means your app is not required to obtain separate permission"
([WWDC23 10053](https://developer.apple.com/videos/play/wwdc2023/10053/)).
macOS 15 tells developers to move to it, warning that older capture paths
"can trigger system alerts"
([macOS 15 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-15-release-notes)).
An exact2-drawn list of windows would need that permission and would be a
tell.

**Per platform, the start:**

- **macOS and iOS.** The implementation activates the shared picker with
  its configuration, observes `contentSharingPicker(_:didUpdateWith:for:)`,
  and starts an `SCStream` with that filter and an `SCStreamConfiguration`
  from the constraints. The picker's cancel answers `NotAllowedError`. On
  macOS, a person's change of content through the system's menu bar item
  arrives as a new filter, which the implementation applies with
  `updateContentFilter`; the track keeps its id and announces new
  settings. The picker's [`maximumStreamCount`](https://developer.apple.com/documentation/screencapturekit/sccontentsharingpicker)
  is left at the system's.
- **Android.** The implementation starts
  `createScreenCaptureIntent()` with the package context's activity
  result seam (LLP 1133.018), passing `createConfigForDefaultDisplay()`
  on API 34 and later when `monitorTypeSurfaces` is not `exclude` and the
  app asked for `displaySurface: "monitor"`, else the default config. On a
  result of `RESULT_OK` it claims the host's foreground service with type
  `mediaProjection` (D11 item 3) and keeps the result's `Intent`; only in
  the claim's `started`, after the service has called `startForeground`,
  does it call `getMediaProjection`, in the order Android 14 requires:
  "the app must have started the foreground service with that type
  before calling this API here, or else it'll receive a
  SecurityException"
  ([MediaProjectionManager](https://developer.android.com/reference/android/media/projection/MediaProjectionManager)).
  It registers the `MediaProjection.Callback` before
  `createVirtualDisplay`, which "throws an IllegalStateException" without
  one, and makes the one virtual display the projection allows. The send
  answers then. With the single-app choice, the chosen app is in front by
  that time and the recorder's activity is stopped; D6 lets a
  display-only take start so.
- **Web.** The implementation calls the browser's `getDisplayMedia` with
  the options as given, inside the press's dispatch (D9).

**One capture per call.** A display capture is not a device that sessions
share: each call is the person's choice and gets its own platform
capture, so media-capture's leases and "one capture per device for the
process" (LLP 1133.009 D3) do not apply. Where the platform runs one at a
time, a second ends the first: Android's `onStop` fires on "another
MediaProjection session starting", and the first track ends (D4).

### D3 — The app's own pixels: `preferCurrentTab` and `restrictTo`

```
send shot = getDisplayMedia(preferCurrentTab=true, video={frameRate: {ideal: 30, max: 30}})
then send restricted = restrictTo(track=shot.videoTracks[0], element="tab-3")
```

On the web, `preferCurrentTab` offers the current tab in Chrome's dialog
and Element Capture's two steps narrow the track to an element:
`RestrictionTarget.fromElement(element)` makes an opaque token, and the
track's `restrictTo(target)` applies it. The element "must form its own
stacking context", and frames are "an independent rendering of that
stacking context", so "any occluding and occluded content are removed"
([Element Capture](https://screen-share.github.io/element-capture/);
[Chrome](https://developer.chrome.com/docs/web-platform/element-capture)).
`restrictTo(element=null)` lifts the restriction.

On native, the app's own pixels come from **the host's own rendering**,
not the platform's capture:

- **No prompt and no indicator.** An app draws its own window on every
  platform without asking, and the browser shell's picture of a frame
  already takes no grant because "the pixels are the app's window's" (LLP
  1020.002 D7). So any of the app's foreground code may start a self
  capture, as `getUserMedia` may be started (LLP 1133.009 D9), and it
  shows nothing on screen. That gives the app no power it lacks: its
  nodes are its own state, and a guest frame's pixels are already its own
  by D7, with no grant, at any time. What it must not reach is what
  another app shows, and it cannot: content another process draws into
  the window (a system picker's remote view, AutoFill's) is not the app's
  and does not appear, since the host draws only what it renders. A
  deviation from the web, which asks even for the current tab; declared in
  `state.extensions` and put to Charlie (§12 question 3).
- **The rendering Element Capture describes.** The host draws the
  element's subtree alone, in paint order, at the element's size: the
  "independent rendering" of the web's definition. So `restrictTo` is
  native's natural case, and the whole tab is `restrictTo` of the
  session's root. A guest frame (the browser shell's `iframe`) is drawn by
  `WKWebView.takeSnapshot`, polled at the frame rate with at most two in
  flight, the clone's way and LLP 1020.002 D8's.
- **The calling session's view only.** Self capture covers the session's
  root and its subtree, never another session's in the same process (LLP
  1031's sample host) or the embedder's own views.
- **It idles.** Self capture spends no consent, so it follows LLP
  1133.008 D3's rule as a camera does: the host draws only while the
  track has a consumer, stops when the last consumer goes, and draws
  again, with no prompt, when one attaches. The track stays `live`
  meanwhile and reads `muted`, `muteReason` `idle`. A consumer attaching
  is admitted with its own origin, as any capture start is (D9).
- **When frames come.** While the element is painted: displayed by
  `wakelock`'s function (`runner/src/wakelock.rs`, `displayed`), or a
  guest frame the browser shell keeps painting while parked (LLP 1020.002
  D8: "A hidden frame that records keeps painting"). Otherwise no frames
  come and the track stays `live`, as Element Capture says: "Invalidity
  will suppress additional frames until validity is restored." A frame is
  drawn only when its subtree changed since the last, up to the frame
  rate; the recorder holds the last frame between (D6).
- **The element is named by its `id`**, resolved in the calling session,
  as the browser shell's frames are (`captureScreenshot("tab-3", …)`, LLP
  1020.002 D7). One call stands for the web's two steps: Contract has no
  value for an opaque token, and nothing else takes one (a declared
  deviation). An id that names nothing fails `NotFoundError`; an element
  of another track's tab, `NotSupportedError`, the web's.

`restrictTo` works on a track from `preferCurrentTab` (on the web, Chrome's
rule: "Element Capture is only enabled for self-capture"). On a track
from the picker it fails `NotSupportedError` on every target.

**Where the web differs, and where it lacks.** Safari and Firefox ignore
`preferCurrentTab` and show their picker; neither has `restrictTo`, which
fails `NotSupportedError` there, and `displayCaptureStatus()` says so
(`restrictTo: false`). On the web a self capture contains whatever the
browser renders for the tab, the platform's answer.

### D4 — The display track: in the shared table, live until it is stopped

A display track is an entry in the calling session's track table, owned
by the screen-capture package (`ExactTrackOwner`), with `kind` `video`.
media-capture's names act on it: `stopTrack` ends it; `mediaStreamTrack`
reads it; `setTrackEnabled(enabled=false)` replaces its frames with black
until `true`, as Media Capture requires of a disabled video track
("black frames", [Media Capture and Streams](https://www.w3.org/TR/mediacapture-streams/#life-cycle-and-media-flow)),
so a recorder records black over the interval on every target, as
MediaStream Recording's does on the web. Today those names act only on
tracks media-capture opened (`MediaCapture.swift` consults its own map and
otherwise answers `NotFoundError`), so the owner gains `stop`, `enabled`
and `state`, and media-capture forwards a name for a track it did not open
to the owner the table names (D11 item 6).

**A picker's track never idles.** The camera's track releases its camera when its last
consumer goes and reopens it when a viewfinder shows it again (LLP
1133.008 D3's rule: "a consumer that shows the capture" reopens). A
display capture cannot reopen: the picker's answer is spent (Android 14:
"each MediaProjection instance must be used only once"; the web's stopped
track "never exits" `ended`). So the reopen rule does not apply, and a
track from the picker (or tier 2's) keeps its platform capture from the
picker's answer until it ends. A self capture's track idles (D3). Consumers come and go meanwhile: a track with none delivers
frames to nobody and drops them.

**It ends** at `stopTrack`; when the person stops sharing in the
platform's own control (macOS's and iOS's `stream(_:didStopWithError:)`
with `userStopped`, "the user took an intentional action to cancel the
stream",
[SCStreamDelegate](https://developer.apple.com/documentation/screencapturekit/scstreamdelegate/stream(_:didstopwitherror:));
Android's `onStop`, fired on "a user stopping the session via UI
affordances in system-level UI, or the screen being locked",
[MediaProjection.Callback](https://developer.android.com/reference/android/media/projection/MediaProjection.Callback);
the browser's own stop); when the captured window closes (W3C: "the user
agent MUST queue a task … that ends the corresponding media track"); when
a platform stops it (iOS without the background mode, D9; a second
projection on Android); and at the session's end, whose `destroy` stops
each platform capture and releases its foreground service claim. Each end
announces `mediaStreamTrack` with `readyState` `ended`, and a recorder of
the track stops with `reason` `track-ended` (LLP 1133.009's reasons).

**Mute.** A display track is `muted` only while the platform says the
captured content is unavailable: macOS's and iOS's frames whose
`SCFrameStatus` is `blank` or `suspended`, Android's
`onCapturedContentVisibilityChanged(false)` (API 34). Its `muteReason` is
`interrupted`; media-capture's enum gains no word. A captured window that
merely does not change sends no frame and is not muted.

**Origins.** The start is a capture start, admitted with the commit's
origin, refused to a tool and a wake (D9). Consumers attaching later carry
their own admission: `startMediaRecorder` keeps `"origin": "app"`, and its
`"foreground": true` holds for a stream with a microphone or camera track,
not for a display-only stream (D6).

### D5 — A frame source in the track table

The camera's video entry is a capture graph the consumer configures
(`ExactVideoSource`: `configure`, run on the session queue, adding outputs;
LLP 1133.008 D3). A display capture has no graph to add an output to: the
platform delivers finished frames. So a track entry gains a second video
form, a **frame source**, which the camera does not use:

- **Apple:** each frame is a `CVPixelBuffer` with a presentation time on
  the session clock, from `SCStreamOutput`'s `.screen` sample buffers, or
  from the host's own rendering (D3). A consumer subscribes with a queue
  and receives the latest frame when it is ready for one: a consumer that
  is busy gets the newest frame when it frees, never a backlog, as LLP
  1133.003 D4 delivers decoded video.
- **Android:** the projection's one `VirtualDisplay` renders into the
  host's `ImageReader` surface, and each consumer receives the latest
  `Image`'s `HardwareBuffer` and timestamp the same way. The one surface
  is the platform's: a virtual display has one, and on API 34 a second
  `createVirtualDisplay` needs a second consent. Self capture renders into
  an `ImageReader` surface of its own (D11 item 2), so both reach
  consumers in one form.
- **Web:** the browser's `MediaStreamTrack` is the source; a consumer
  takes the track itself.

The pixel format is the platform's capture format (`'BGRA'` from
`SCStream`, `RGBA_8888` from `ImageReader`), so a frame reaches the
encoder without conversion where the encoder accepts it. Frame sources
are host objects reached through the table (LLP 1133.009 D3's rule), so a
session's end does not take another session's track.

### D6 — Recording a display track (an amendment to LLP 1133.009)

`startMediaRecorder(stream=)` records a stream whose video track is a
display track, by MediaStream Recording's names, to an MP4:

| Target | Encoder | Container |
|---|---|---|
| web | the browser's `MediaRecorder` with `mimeType` `video/mp4;codecs=avc1` where `isTypeSupported` says yes, else `video/webm` | as the browser writes it; `RecordedMedia.mimeType` says which |
| iOS, macOS | `AVAssetWriter` with an H.264 `AVAssetWriterInput` and a pixel buffer adaptor, frames appended at their presentation times | MP4 |
| Android | `MediaCodec` H.264, fed from the frame source, beside the recorder's existing `MediaMuxer` | MP4 |

- **Options:** `mimeType` (`video/mp4` is the native default; the web's
  default is the browser's) and the web's `videoBitsPerSecond`. The
  others of `MediaRecorderOptions` wait for a consumer.
- **Variable frame rate.** Frames are written at their presentation
  times; a source that sends nothing (an unchanged window, a hidden
  element) leaves the last frame showing, which is what the clone's
  recorder does and what an MP4 with variable frame rate plays.
- **Audio.** A stream with a display track and no audio track writes a
  video-only file. Recording a display track and a microphone track
  together needs one stream holding both, which nothing makes yet (§11).
- **Admission follows the stream.** Recording's names and interface take
  `device.microphone` or `device.display-capture`, so an app that records
  only the screen writes no microphone line. But admission's permission
  check picks a permission by the arguments given (`permission_of` in
  `runner/src/runner/modules/admit.rs`), and `stream` is given to every
  recording: the recorder, which grants both, would be asked the
  microphone's permission for a screen-only take. So the runner keeps,
  for each stream handle it delivers, the sources of its tracks
  (`microphone`, `camera`, `display`), read from the answer that
  delivered it, and a name taking a stream handle declares its grants,
  permission and `foreground` per source (D11 item 7). A screen-only
  take asks nothing; a take with a microphone track checks the
  microphone's permission, as today.
- **A display-only take starts in the background.** Android's single-app
  choice launches the chosen app before the consent returns (AOSP's
  `MediaProjectionAppSelectorActivity`), so the recorder's activity is
  stopped when `getDisplayMedia` answers, and a `"foreground": true`
  start would be refused. Recording a stream whose tracks are all
  display tracks opens no device the person has not already chosen to
  share, so its `foreground` is false; its origin stays `"app"`, refused
  to a tool and a wake. A stream with a microphone or camera track keeps
  `"foreground": true` (LLP 1133.009 D9).
- **The level and the waveform** stay audio's: `audioLevel` of a display
  track fails `NotSupportedError`.

Recording the camera's video stays out (LLP 1133.008 §12): the camera's
track is a capture graph, and recording it is an `AVCaptureMovieFileOutput`
or a CameraX `VideoCapture`, a different consumer this RFC does not need.

## 3. Tier 2 and tier 3

### D7 — The platforms' words

Tier 2 is what a consumer here needs and the web cannot say: macOS's
programmatic capture of a named window, for SnapShot.

```
apple.shareableContent() -> ShareableContent           // a send
apple.captureImage(window=, display=, path=, showsCursor=, scale=) -> CapturedImage
apple.requestScreenRecording() -> ScreenRecordingStatus
apple.screenRecordingStatus() -> ScreenRecordingStatus  // a live fact
```

- **`apple.shareableContent()`** answers
  [`SCShareableContent`](https://developer.apple.com/documentation/screencapturekit/scshareablecontent)'s
  windows and displays: each window's `windowID`, `title`,
  `owningApplication` (`bundleIdentifier`, `applicationName`,
  `processID`), `frame`, `windowLayer`, `isOnScreen` and `isActive`, front
  to back as `CGWindowListCopyWindowInfo` orders them, and the frontmost
  application's process id (`NSWorkspace.frontmostApplication`). It is a
  send, not a live source: window lists change constantly and a reader
  would poll them. It needs the Screen Recording permission. Reading
  `SCShareableContent` without it makes the system show its prompt
  ([forum 765103](https://developer.apple.com/forums/thread/765103)), so
  the implementation reads `CGPreflightScreenCaptureAccess` first and,
  when it is false, fails `NotAllowedError` without touching
  ScreenCaptureKit: only `apple.requestScreenRecording` asks.
- **`apple.captureImage`** captures one window or display as a PNG with
  [`SCScreenshotManager.captureImage(contentFilter:configuration:)`](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager/captureimage(contentfilter:configuration:completionhandler:)),
  macOS 14, through an `SCContentFilter(desktopIndependentWindow:)` or a
  display filter, written to `path` (an `app:/` path under the app's
  `fs.write` lines, LLP 1133.009 D10 item 4), answering `{path, width,
  height}`. `scale` defaults to the display's backing scale; `showsCursor`
  to false. Without the permission it fails as `apple.shareableContent`
  does.
- **`apple.requestScreenRecording()`** calls
  `CGRequestScreenCaptureAccess`, which prompts "if it has not yet been
  determined"; "a previously denied process is not re-prompted; the user
  must enable access in System Settings"
  ([CGWindow.h](https://developer.apple.com/documentation/coregraphics/cgrequestscreencaptureaccess())).
- **`apple.screenRecordingStatus()`** is the fact (D9).

Every other platform word waits for a consumer: `SCStreamConfiguration`'s
`showsCursor`, `capturesAudio`, `captureMicrophone`, `pixelFormat` and
`queueDepth` as `apple.` arguments to `getDisplayMedia`; a stream of a
named window (`getDisplayMedia(apple.window=)`); Android's
`MediaProjectionConfig` sources of API 37; Windows' `IsBorderRequired`.
Each fits as a dotted keyword when one asks.

### D8 — Access hatches

**A frame transform.** An app's Swift (LLP 1075.003.000.001) may register
a transform on a display track's frame source: a function from a
`CVPixelBuffer` and its time to a `CVPixelBuffer`, run on the source's
queue before the frame reaches any consumer. It is how the clone keeps
`T3RecordingDecorations`, which draws key and click badges into the
recording and not on screen. The transform owns its timing: the source
does not wait for it beyond one frame, and a transform still running when
the next frame arrives is skipped for that frame (latest frame only). On
Android the same hatch takes a `HardwareBuffer`; on the web the app's
script owns the stream already.

This amends LLP 1020.002 D8, which put the key badges in "a compositor in
data code". Data code never receives frames on native (LLP 1133.003 D4),
so the badges are the app's Swift through this hatch, or Contract nodes
inside the restricted element, which the self capture draws and the
person also sees.

**Broadcast extensions are out.** iOS's `RPBroadcastSampleHandler` is a
separate process and is deprecated in 27.0 for ScreenCaptureKit, which
reaches the same content from the app (D2). Nothing here needs one.

## 5. Permission

### D9 — LLP 1133.002 §4, for a consent that is not kept

**The grant lines.** Two rows in `runner/src/device.rs`:

| Row | Line | Web | iOS | macOS | Android |
|---|---|---|---|---|---|
| `display-capture` | `device.display-capture <key>` | `Permissions-Policy: display-capture=(self)`, the specification's feature, "default allowlist is "self"" | `NSScreenCaptureUsageDescription`; `screen-capture` in `host.ios.backgroundModes` when the app captures in the background (below) | `NSScreenCaptureUsageDescription` | `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_MEDIA_PROJECTION`, normal permissions, and the host's service's `mediaProjection` type (D11 item 3) |
| `screen-recording` | `device.screen-recording <key>` (tier 2, macOS) | — | — | `NSScreenCaptureUsageDescription` | — |

ScreenCaptureKit's overview tells an app to "add a
NSScreenCaptureUsageDescription key with a description of why your app
requires screen recording access"
([ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit)),
and an app that touches a protected API without its usage key may be
terminated rather than asked. The key has no Information Property List
reference page, and Apple's iOS sample declares none, so whether the
picker reads it is unknown: both rows write it, and stage 2 records what
the picker does in a bundled app without it.

`display-capture` is the web's name. `screen-recording` is a declared
deviation in macOS's own words (System Settings' Screen Recording), since
the web has no standing capture permission. An app grants either or both;
they do not narrow each other.

**The fact, `displayCaptureStatus().state`:**

| Platform | Reading | `state` |
|---|---|---|
| web | `permissions.query({name: "display-capture"})` where the browser names it; else `prompt` where `document.featurePolicy` allows the feature | its word; `denied` when the policy disallows |
| macOS, iOS 27 | the picker asks each time | `prompt`; `unknown` below the floor (`available: false`) |
| Android | consent each session; `DevicePolicyManager.getScreenCaptureDisabled` | `prompt`, `denied` when an admin disabled capture |
| Linux, Windows, tvOS | no cell (D12) | `unknown`, `available: false` |

`granted` is never read: no platform keeps the consent. `apple.screenRecordingStatus()`
reads `CGPreflightScreenCaptureAccess`, a boolean that "never prompts":
`true` is `granted`; `false` is `prompt` until the module has called
`CGRequestScreenCaptureAccess` once for this install, and `denied` after,
by the history LLP 1133.002 D8 keeps for Android's permissions. macOS
applies a granted change to a running process only after a relaunch in
some releases; stage 3 measures it and records it.

**Who may start, by name** (LLP 1133.002 D12; LLP 1133.009 D9):

| Name | `origin` | `foreground` | Why |
|---|---|---|---|
| `getDisplayMedia` | `"app"`, `"gesture": true`, `"request": true` | true | a tool or a wake never starts a capture (LLP 1133.009 D9). Without `preferCurrentTab` a person chooses in the platform's picker, whatever code raised it; with it, any foreground code of the app may start it (D3). On the web the browser also requires transient activation ("If the relevant global object … does not have transient activation, return a promise rejected"), which `"gesture": true` keeps by running the call in the press's dispatch (LLP 1133.013 D11 item 5); Safari enforces it, Chrome does not yet ([Chrome Platform Status](https://chromestatus.com/feature/5090735022407680)) |
| `restrictTo` | `"app"` | false | it changes what a live capture contains |
| `apple.shareableContent`, `apple.captureImage` | `"app"` | false | another app's windows and titles: never a tool's or a wake's. Not foreground: SnapShot's global shortcut fires while another app is frontmost, and its event carries the `app` origin of a person's input (LLP 1133.025 D11 item 3). Neither asks: without the permission each fails at once (D7) |
| `apple.requestScreenRecording` | `"app"`, `"request": true` | true | the system prompt, from the app in front |
| `displayCaptureStatus`, `apple.screenRecordingStatus` | any | false | facts |

`"app"` refuses a tool invocation and a wake in every state, before
anything is asked, with `NotAllowedError` and the message
`person-required` (`admit.rs`), and holds no ticket. `"person"` would
refuse the same callers with `PERMISSION_DENIED`, local authentication's
code (LLP 1133.010 D12); it admits no fewer callers, and the web's name
is `NotAllowedError`.

**In the background.** A capture started in the foreground continues in
the background where the platform allows, because sharing another app is
the purpose:

| Target | The platform capture in the background | Self capture in the background |
|---|---|---|
| macOS | continues | frames while the host paints (a hidden window's web view still snapshots, LLP 1020.002 D8) |
| iOS 27 | continues with `screen-capture` in `UIBackgroundModes`; without it the system stops the stream (`missingBackgroundMode`) and the track ends | no frames until the app returns |
| Android | continues: the foreground service keeps the process | no frames until the app returns |
| web | the browser's | the browser's |

A recorder of the track continues with it (LLP 1133.009 D7's "a Mac app
keeps its input in the background" holds for this input on every row
above where the capture continues).

**Indicators are the platform's.** macOS shows its screen-sharing menu bar
item for every stream, with controls to change or end it ([WWDC23
10136](https://developer.apple.com/videos/play/wwdc2023/10136/)); Android
15 QPR1 shows a status bar chip and stops projection at the lock screen
([Android 15 features](https://developer.android.com/about/versions/15/features));
the browser shows its own. exact2 adds none. What iOS 27 shows during an
`SCStream` is not documented; stage 2 records it.

## 6. Packaging and callers

### D10 — A package over media-capture

`@exact/screen-capture` (`packages/screen-capture`) is a new package that
uses `@exact/media-capture`, pinned exactly, and declares
`getDisplayMedia`, `restrictTo`, `displayCaptureStatus` and the `apple.`
names. It registers its tracks in media-capture's table; `stopTrack`,
`mediaStreamTrack`, `setTrackEnabled` and the `MediaStream` shapes are
imported from media-capture, never re-exported.

Why not a name inside media-capture: media-capture opens inputs that share
one device and the audio session (LLP 1133.009 D3); a display capture
shares neither (D2, "one capture per call"). A separate package keeps
ScreenCaptureKit, MediaProjection and the foreground service out of every
app that only records its microphone, and its grant out of their
manifests. media-capture's rule, that it is "the only package that opens
an input", is amended to say: the only package that opens a microphone or
a camera.

**Callers** (LLP 1133 D6): Contract sources and sends; generated
TypeScript and Rust bindings from the declaration; one route through
admission for each. The clone's `browser-recording.ts` calls
`getDisplayMedia({preferCurrentTab: true, video})` and
`restrictTo({track, element})` from data code; the recorder's Contract
calls them as sends.

### D11 — What the seam gains

1. **A frame source in the track table** (D5): `ExactTrackEntry.frames`,
   an `ExactFrameSource` with `subscribe(queue:, frame:)` delivering the
   latest `CVPixelBuffer` and time, `transform` for D8's hatch, and the
   entry's existing `subscribe` for `muted`, `unmuted` and `ended`. The
   Android context gains the same with `HardwareBuffer`. The camera's
   `ExactVideoSource` is unchanged.
2. **The host's rendering of a node as frames** (D3): the package context
   gains `surfaces.frames(session:, id:, rate:) -> ExactFrameSource?`,
   which resolves the id in that session, draws the node's subtree when it
   changed, at most at `rate`, by the paint-order copy the agent's
   screenshot uses, with each web view's `takeSnapshot`, and reports
   `nil` for an id that names nothing. The Android host records the
   subtree into a `RenderNode` (replaying its op stream, and drawing each
   platform view of the subtree with `View.draw`) and renders it with a
   [`HardwareRenderer`](https://developer.android.com/reference/android/graphics/HardwareRenderer)
   onto an `ImageReader` surface, both API 29, exact2's floor; a canvas
   cannot draw into a `HardwareBuffer` directly, and `PixelCopy` of the
   window would include what covers the element. It reports the node's
   displayed state with the origin that changed it, as package views'
   `displayed` does, and starts and stops drawing as the track gains and
   loses consumers (D3, "It idles").
3. **A foreground service the host owns** (Android). The host's manifest
   declares one service, `dev.exact.canvas.ExactForegroundService`, whose
   `android:foregroundServiceType` is the union of the types the app's
   granted rows name (`mediaProjection` for `device.display-capture`),
   derived as `-Ppermissions` derives `<uses-permission>`
   (`host/android/app/build.gradle.kts`), in every variant a drive
   installs. The context gains `foregroundService.claim(type:, title:,
   started:) -> Claim` and `Claim.release()`. The host runs the service
   while any claim lives, with one notification naming the claims, and
   calls `startForeground` with the union of the live claims' types; a
   claim's `started` runs on the main thread after that call has returned
   in the service's `onStartCommand`, never inside `claim`, since
   `startForegroundService` returns before the service starts and the
   main thread must not wait for it. A release calls `startForeground`
   again with the remaining types, and the last stops the service, as the
   Apple host keeps one audio session for every claim on it (LLP 1096 D8).
   MediaProjection's start is therefore: the consent's result, a claim,
   and in `started`, `getMediaProjection`, the callback, then
   `createVirtualDisplay` (D2). Starting
   the service from a person's press in the foreground is within Android's
   rules; Android 15 forbids starting a `mediaProjection` service from
   `BOOT_COMPLETED`
   ([service types](https://developer.android.com/develop/background-work/services/fgs/service-types#media-projection)),
   which no claim does. The roster's `foreground-service` module, being
   written in this wave, and recording's Android background (LLP 1133.009
   D7, "a foreground service of type `microphone`") are the next clients;
   this RFC builds the claim and nothing a later client needs.
4. **A grant row's Android service type.** `Device` gains
   `android_service: Option<&str>` and `android_normal: &[&str]`
   (permissions declared, never asked), which item 3's derivation reads.
5. **The recorder's video path** (D6), inside `@exact/recording`.
6. **Control of another package's track.** `ExactTrackOwner` (and its
   Android and web counterparts) gains `stop(id)`, `setEnabled(id, _:)`
   and `state(id)`, and media-capture's `stopTrack`, `setTrackEnabled`
   and `mediaStreamTrack` forward to the owner `ExactTracks.lookup` names
   when the track is not one media-capture opened (D4).
7. **A stream handle's sources in admission.** The runner keeps, for each
   delivered `handle<stream>`, the sources of its tracks, read from the
   answer that delivered it (media-capture's tracks are `microphone` or
   `camera`; screen-capture's `display`), and the declaration lets a name
   that takes a stream handle condition its grants, its permission and
   its `foreground` on them (D6). The form of the condition is the
   declaration's, beside `when` and `permissionBy`
   (`contract/cli/src/declaration.rs`).

Nothing else is new: the activity result seam (LLP 1133.018), the
package context's `destroy`, session clock and foreground fact,
`release(name, args)`, handles provisional until delivered (LLP 1133.009
D10), and the agent's tickets and preferred values are used as they are.

### D13 — Cost

An app that does not use the module links none of it. One that does links
ScreenCaptureKit (weak where its floor is above exact2's) and, on Android,
nothing beyond the platform: MediaProjection, `ImageReader` and
`MediaCodec` are in the framework, so the locked Gradle graph (LLP
1133.008 D8 item 5) gains no library. The foreground service is a few
dozen lines of host Kotlin, present only in apps whose grants name a
service type. Nothing loads before first pixel: the implementation loads
at its first call or status read. Stage 1 measures the Apple module's

## 8. The substitute

**The implementation is its own substitute** (`"substitute":
"implementation"`, LLP 1133.006 D8), as media-capture's and recording's
are: under the agent the runner admits each call and holds its tickets;
the bound implementation runs told it is substituting, shows no picker,
asks the platform for nothing and **captures no screen**. It makes
frames instead:

- **The picker is a ticket.** `getDisplayMedia` without
  `preferCurrentTab` holds a `display-capture` ticket (a `choose` ticket,
  as `selectContacts`' is, LLP 1133.018 D13 item 4), whose `args` name the
  options, the target's `surfaces` and the call's origin. The drive
  answers `tap @t monitor`, `tap @t window` or `tap @t browser`, or `tap @t
  cancel` for `NotAllowedError`. A choice the target cannot offer is
  refused, so a drive sees each platform's picker.
- **The frames are a fixture picture.** The implementation draws a test
  card: colour bars, the chosen surface's word, a frame counter and the
  session clock's time, at `video`'s size (1280 by 720 when unsaid) and
  frame rate, on the agent's clock, so `clock +1000` makes a second of
  frames. On Apple it fills `CVPixelBuffer`s, on Android `HardwareBuffer`s,
  on the web a canvas's `captureStream()`. `prefer extension
  screen-capture.surface={"width":1920,"height":1080,"displaySurface":"window"}`
  sets it. The recorder records these frames for real, so a drive gets a
  playable MP4 of the test card.
- **Self capture runs as in production on native.** `preferCurrentTab`
  and `restrictTo` draw the app's own nodes by the host's rendering, which
  can reach nothing but the app's own pixels (D3). **On the web it does
  not:** a browser asked for the current tab may show its full picker
  (Safari and Firefox ignore `preferCurrentTab`, and Chrome treats it as
  a suggestion), so the substituting web implementation never calls
  `getDisplayMedia`; it answers the test card with `displaySurface`
  `browser`. The browser's own capture of the tab runs only bound, in
  drive 5, whose Chromium is started with `--auto-accept-this-tab-capture`
  (§9.5).
- **The person's stop** is `prefer extension
  media-capture.mediaStreamTrack={"readyState":"ended"}` for the track, as
  the camera's substitute ends a track (LLP 1133.008 §9).
- **Tier 2.** `apple.shareableContent` answers a fixture list of three
  windows of two invented applications and the fixture's own window;
  `apple.captureImage` writes the test card at the named window's size.
  `apple.screenRecordingStatus` overlays (`"overlays": "implementation"`):
  `prefer extension screen-capture.screenRecording="denied"` sets it, and
  `apple.requestScreenRecording` holds a `permission` ticket while it reads
  `prompt`.
- **Failures.** `prefer extension screen-capture.fail="NotReadableError"`
  fails the next start with that name, an agent word the substitute
  declares (`"agent": {"fail": "string", "surface": "object",
  "screenRecording": "string"}`).

`--bind screen-capture` binds the real implementation under the agent;
§9.4 says which bound drives are allowed, and no drive binds it where a
real picker could offer a real screen. On a target with no
implementation the declared defaults answer (`available: false`) and every
call fails `NotSupportedError`.

**Disclosure.** `state.extensions` lists each display track: its source
(`picker`, `self`, `substitute`), `displaySurface`, the element it is
restricted to, its consumers, its frame count, its foreground service
claim on Android, and each call's origin and outcome. Never a window
title, an application name or a pixel.

## 9. The consumers

### 9.1 The T3 Code clone: browser recording (macOS)

The clone records its browser panel's guest frame. With this module:

```ts
// grants: 'device.display-capture', 'fs.write app:/data/recordings'
const stream = await getDisplayMedia({ preferCurrentTab: true,
  video: { frameRate: { ideal: 30, max: 30 } } });
await restrictTo({ track: stream.videoTracks[0], element: tabId });
const rec = await startMediaRecorder({ stream: stream.id, mimeType: "video/mp4", path });
```

`T3BrowserRecorder.swift`'s snapshot loop and writer become the module's
self capture and the recorder's video path; its page script for the
cursor stays (LLP 1020.002 D9); `T3RecordingDecorations` becomes a frame
transform (D8). LLP 1020.002 §12 deletes `T3BrowserRecorder.swift` (712
lines as counted there), `T3BrowserAutomationRecording.swift` (102) and
the parking parts of `T3BrowserCapture.swift` when B10 lands; stage 2's
acceptance is that deletion with the clone's recording drive passing.

### 9.2 The T3 Code clone: SnapShot (macOS, tier 2)

The SnapShot shortcut (LLP 1133.025 §12.1) captures the frontmost other
app's window. With this module, `/usr/sbin/screencapture` and the
clone's own permission check go:

```ts
// grants: 'device.screen-recording snapshot.purpose', 'fs.write app:/data/shots'
// In settings, from a press while the app is in front:
if ((await apple.screenRecordingStatus()).state === "prompt") await apple.requestScreenRecording();

// At the shortcut, with another app in front:
if ((await apple.screenRecordingStatus()).state !== "granted") return showSettingsHint();
const content = await apple.shareableContent();
const front = content.windows.find(w => w.owningApplication.processID === content.frontmostProcessID
                                     && w.isOnScreen && w.windowLayer === 0);
if (front) await apple.captureImage({ window: front.windowID, path });
```

The shortcut's event carries the `app` origin of a person's input (LLP
1133.025 D11 item 3), which both capture names require; neither prompts,
so the system's prompt comes only from the settings press. The app's text
read through Accessibility is not screen capture and stays the clone's.

### 9.3 The recorder: "Record screen" (web, macOS, iOS, Android)

The T3 consumers are on a branch and macOS only. The in-tree consumer is
the recorder (`apps/recorder`), which records the microphone today: it
gains a "Record screen" button, shown where `displayCaptureStatus()`
reads `available` with a `surfaces` entry other than `browser`. A press
calls `getDisplayMedia(video=true)` and records the track to
`app:/data/takes/<n>.mp4`; the take appears in the list with its length
and plays in a `video` element (LLP 1133.003); the track's end, from the
recorder's stop button or the platform's own control, stops the take. It
is a real feature, a small screen recorder of the kind every platform
ships one of, and it exercises the picker, the background rule and the
recording amendment on every target with a cell. On iOS the app declares
`screen-capture` in `host.ios.backgroundModes`, as it declares `audio` for
a microphone take.

### 9.4 The drives

the frames are the test card (§8). A bound drive captures the fixture
app's own window, its own element, or a simulator's or emulator's own
screen showing the fixture. No drive captures this Mac's screen or a
phone's; no drive runs on a physical phone. Where a real picker would
need a person to choose, the drive answers it only on an emulator; on a
Mac, the picker is a hand step of the checklist, done on a test Mac with
the fixture's window the only thing chosen.

### 9.5 Answering a picker without a person, on a fixture

Each target's way, measured or read in its source on 2026-10-25, and the
ways a drive must never use because they capture a real screen:

- **Chrome.** `--auto-accept-this-tab-capture` answers a
  `preferCurrentTab` request with the page's own tab ("It should only be
  used for tests", [switch list](https://peter.sh/experiments/chromium-command-line-switches/));
  probed in Playwright's Chromium 156 in new headless, the capture was the
  page's own pixels. `--auto-select-tab-capture-source-by-title=<title>`
  picks a tab by title, and selects the page's own tab only with
  `selfBrowserSurface: "include"`. `--use-fake-ui-for-media-stream`
  together with `--use-fake-device-for-media-stream` answers the picker
  with a synthetic screen (a test pattern). **Never**
  `--use-fake-ui-for-media-stream` alone, which without a fake device
  shares the real screen (`DisplayMediaDevicesFromFakeDeviceConfig` in
  `media_stream_manager.cc` "Returns a video device with default
  DesktopMediaID otherwise"), nor `--auto-select-desktop-capture-source`
  or `--auto-select-screen-capture-source`. Drive 5 uses the first switch,
  and a bound web picker drive the fake device pair.
- **Firefox.** Its permission preference shares the whole screen ("this
  gives us full screen sharing by default",
  [MediaDevices.cpp](https://searchfox.org/mozilla-central/source/dom/media/MediaDevices.cpp)),
  and no preference picks a window or tab for `getDisplayMedia`. So
  Firefox runs only the agent's drives.
- **WebKit.** Playwright's WebKit build answers `getDisplayMedia` with
  "Mock screen device 1", grey frames, and no prompt (probed; WebKit's
  mock capture, undocumented). It may run bound.
- **Android emulator.** The drive answers SystemUI's consent dialog with
  UiAutomator on the emulator, the path a person takes, so the result
  arrives through the activity result seam as in production; the
  projection is the emulator's own screen, which shows only the fixture
  or the app 7b chooses. A shortcut exists, `adb shell appops set
  <package> PROJECT_MEDIA allow`, which SystemUI's consent activity
  checks before showing its dialog (`MediaProjectionPermissionActivity`
  and `MediaProjectionManagerService.hasProjectionPermission` in AOSP;
  Appium's settings app relies on it); whether it still skips the dialog
  for an ordinary package on API 34 and later, where consent is per
  session, is unconfirmed, and stage 4 records it before any drive leans
  on it. Whether frames flow on the emulator's images is also stage 4's
  to record.
- **iOS simulator.** ScreenCaptureKit is absent from the simulator SDKs,
  and ReplayKit's `startCapture` there reported success and delivered no
  frames in 20 seconds (probed on an iOS 26.5 simulator). So iOS's bound
  drives are self capture alone.
- **macOS.** No profile or command grants Screen Recording ("A profile
  can't grant access to the contents; it can only deny it",
  [PPPC services](https://developer.apple.com/documentation/devicemanagement/privacypreferencespolicycontrol/services-data.dictionary)),
  and no documented way answers `SCContentSharingPicker` without a
  person. So drive 6 builds its filter from the fixture's own window, and
  the picker is a checklist step.
- **Windows,** when its cell is built: `IGraphicsCaptureItemInterop::CreateForWindow`
  on the drive's own window makes a capture item with no picker
  ([CreateForWindow](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow),
  Windows 10 1903).

## 11. What this amends, and what stays out

**Amends:**

- **LLP 1133.009** (recording): `startMediaRecorder` records a display
  track's video (D6), with `videoBitsPerSecond`; recording's names take
  `device.display-capture` as an alternative to `device.microphone`, with
  grants, permission and `foreground` following the stream's sources (a
  display-only take may start in the background);
  §3's "the only package that opens an input" becomes "a microphone or a
  camera" (D10); §13's `getDisplayMedia` leaves the out list.
- **LLP 1133.008** (camera): the track table's video entry gains a second
  form, the frame source (D5); the camera's is unchanged. D3's reopen rule
  holds for self capture and not for a picker's track, whose consent is
  spent (D4).
- **`@exact/media-capture`**: its track names forward to the owning
  package for a track it did not open (D11 item 6).
- **Module admission and the declaration**: a stream handle's sources
  condition a name's grants, permission and `foreground` (D11 item 7).
- **LLP 1020.002 D8**: the key badges are a frame transform in the app's
  Swift, or Contract nodes inside the restricted element, not a compositor
  in data code (D8).
- **LLP 1133.025 §12.1**: SnapShot's capture moves onto tier 2 (§9.2).
- **`rules/DEFERRED.md`**: §12 question 1 proposes the entry.

**Stays out,** each until a consumer asks: the surface's audio
(`systemAudio`, `windowAudio` and the `audio` track); a stream combining a
display track and a microphone track; `ImageCapture.grabFrame` on a
display track; a preview in `video srcObject=`; `CaptureController`; a
stream of a named window and the other `apple.` configuration words;
Android's app-content projection of API 37; broadcast extensions; WebRTC;
frames in data code; and the Windows, Linux, tvOS, visionOS and watchOS
cells (D12).
