# LLP 1047.000: Staged loading by capability

**Type:** RFC
**Status:** Draft
**Systems:** Build (`host/web/build.mjs`, the capability map); Web host (`glue.js`, loading modules that share one memory); Runner (a readiness gate per loaded capability); Render server (a page's preloads)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-25
**Related:** LLP 1047 (the parent: three tiers, D1; the core diet, §6; §10's landings and sizings); LLP 1048 and 1048.000 (served pages, adoption, the capture script); LLP 1050 (the list engine being rewritten); `~/projects/realworld-react/bench/README.md` ("Server-rendered React")

## Summary

This records a question and its measured answer.

> Charlie, 2026-09-25: *"is chipping away at the wasm download likely to be
> something we could achieve?"* … *"intuitively to me, it seems like
> splitting things up (tree shaking sort of) so that we don't download
> unnecessary stuff in apps that don't need it, and then maybe breaking it
> up into stages. wdyt"*

The answer is yes, in that order, with one refinement: stages should follow
capabilities (what a page uses), not a recorded profile. The two parts:
- **Tree shaking:** code an app never uses is unlinked at build. This is LLP
  1047's linking by use, mostly built.
- **Stages:** code only some pages or users need becomes a secondary module
  of the same wasm, sharing its memory. The page loads it with the core when
  the page uses it, or when the capability is first used.

Measured on RealWorld, this takes the first download from 250 KB to about
205 KB (brotli), −15–18%, with no recording step and no synchronous
fallback.

The remaining ~205 KB is the core itself: runner, Rust std, kernel, web host,
plan loading and data. Capability staging can't reach React's ~110 KB; only
a smaller core or a split of the core can. §6 says which to decide, and when.

## 1. Why the wasm matters less than it did

Served pages arrive as HTML (LLP 1048), so what the user sees first no longer
waits for the wasm.

| Mobile profile, ms (bench, 2026-09-25) | exact2 served | React SSR, CSS inlined | React SPA |
|---|---|---|---|
| Content painted, `/` | 204 | 216 | 1,105 |
| Tag tapped at `load` → feed | 209 | 211 | 200 |
| Runtime up / hydrated | ~1,890 | ~950 | with content |
| A press that needs the runtime, at `load` | ~1,100 | dropped (not hydrated) | ~50 |

A tap before the runtime is up is a link to a rendered page, or a press the
capture script replays. So the wasm's size now governs two things:
- **How soon the runtime is up.** That matters for presses that need it (a
  signed-in ♥, a form) in the first seconds of a first visit.
- **How many bytes a first visit costs.** Repeat visits have it cached.

On the bench's 1.6 Mbps link each KB is ~5 ms. On ordinary networks the whole
download is ~100–200 ms.

## 2. Where RealWorld's bytes go

`app.wasm` on the web toolchain (121d629e) is 780,997 B raw and 250,059 B
brotli-11:
- code: 217.9 KB brotli;
- data: 29.6 KB (57.8 KB raw of it is the plan, ~10 KB brotli);
- other sections: 2.1 KB.

Attribution uses a names build (`EXACT_WEB_NAMES=1`). A function goes to the
first exact2 module its demangled name mentions, and each group is
brotli-compressed alone. That overcounts by about 10% in sum, so the rows are
shares, not a ledger.

## 3. What has been done

- **Linking by use (LLP 1047 stages 2–3):** 390,646 → about 263,500 B
  (§10).
- **The core diet (§10):** std's float reader and printer, `serde_json`,
  small maps and hash tables, and `core::fmt` off the boot path were
  replaced or removed.
- **The web toolchain (121d629e):** a pinned nightly builds std for size and
  drops panic text, 267,921 → 250,059 B. The Markdown editor and text flow
  wasm each shrank by about a third.

## 4. Sized and not taken

- **Errors as codes:** ~5–8 KB, touching every error site (9bb9ca88).
- **A DOM-only web kernel:** the kernel is ~31 KB on the web. A host that
  only patches the DOM still needs ids, the tree, transactions and
  style-to-CSS, so ~10–15 KB, behind a runner–kernel boundary that doesn't
  exist (9bb9ca88).
- **Compiling the runner once instead of per data type:** zero here. The web
  artifact has one instantiation, `Runner<exact_js_web::Module>`, and
  monomorphization bloat overall is ~9 KB of drop glue and ~20 KB of sort
  variants, raw.
- **Non-generic maps:** declined by the diet lane (§10). The yield is 2–3 KB,
  and the compact id map it resembles cost the commit path 55–70%.

## 5. Two ways to stage

### A split by recorded profile

`wasm-split --profile` puts the functions that boot, adoption and a press ran
in the primary module (1,355 of 2,926 at 629bb030) and defers the rest.
- **Yield:** the primary would be ~150–160 KB on the web toolchain (§10's
  table, less the flags that have landed).
- **The profile must come from the same build,** because function indices
  change with every build. That means one of:
  - **(A)** recording it in production web builds by driving the app in
    headless Chrome (~30 s, and Chrome at build);
  - **(B)** committing a recorded list of function names per app and warning
    on drift, which bends "generated files are never committed";
  - **(C)** driving the wasm's exports under Bun. It has one import,
    `exact_js.call`, but the data-module protocol must be emulated, and the
    coverage is synthetic.
- **A call into deferred code before it arrives** needs a synchronous
  fallback that stalls the page, since placeholders can't await.
- **Coverage can decay silently:** taps get slower, and nothing fails.

### A split by capability

The capability map `metrics.mjs` already uses assigns functions to modules
by name. `wasm-split --multi-split` takes that as a manifest.
`--no-placeholders` makes a call into a module that hasn't loaded trap rather
than stall. So loading is explicit and a mistake is loud.

Measured on RealWorld's names build at 121d629e, names stripped after the
split:

| Module | Raw | Brotli-11 |
|---|---|---|
| Unsplit (shipped) | 780,997 | 250,059 |
| Core (primary) | 670,916 | 211,757 |
| Markdown | 30,432 | 13,132 |
| Lists | 51,491 | 20,372 |
| Inspection | 15,369 | 6,632 |
| Unused here (transition and shape parsers, text flow, content region) | 21,606 | 8,910 |

The modules sum to 260.8 KB. Splitting costs ~10 KB: import and export tables
between modules, and compression that no longer spans them. Hence the rule:
- **What an app never uses is unlinked, not split.** Lists and the unused
  parsers leave RealWorld's artifact entirely.
- **What some pages or users need is a stage.** Markdown and inspection.
- **Nothing under a few KB is its own stage.** Its overhead would be most of
  it.

## 6. Proposal

*Revised after review: §9's order supersedes this one where they differ.*

1. **Finish tree shaking.** For RealWorld that means ~29 KB:
   - the list engine behind its seam (§10's deferred design), coordinated
     with the LLP 1050 lane that is rewriting it;
   - the transition and shape parsers the seam unblocks;
   - text flow's shaper;
   - the content region on the web, which only Apple and Linux call.
2. **Stage by capability.**
   - The build splits the app's artifact by the capability map into a core
     and a module per staged capability (`--multi-split --no-placeholders`).
   - The glue instantiates each with the core's memory, table and exports.
   - The runner and host ask whether a capability is ready before calling
     it. A premature call is a trap, and a bug.
   - First candidates:
     - **Markdown:** loaded with the core on pages that render it.
     - **Inspection:** loaded when an agent attaches. The smoked bytes stay
       the shipped bytes; they just arrive later.
3. **Pages preload their stages.** The render server knows which
   capabilities a page uses, so the served document preloads those modules
   beside the core. An article fetches Markdown in parallel, and adoption
   waits for both. A client-side navigation to such a page loads the module
   with its data.
4. **Measure on the bench:** time until the runtime is up and a runtime
   press at `load`, against React SSR.
5. **Then decide the core.** With 1–4 in, RealWorld's first download is
   ~205 KB. The next step is one of:
   - a profile split of the core (§5, ~50 KB more, with its costs);
   - a smaller core. The runner core (~50 KB) is the place to look, not the
     kernel.

   Or neither, if time-to-interactive has stopped mattering by then.

## 7. Costs and risks

- **Loading:** a loader for several modules sharing one memory, and a
  readiness gate in the runner. Estimated at a day or two.
- **Overhead:** ~10 KB of split overhead, spread across modules.
- **Tool maturity:** binaryen's `--multi-split` is newer than its two-way
  split. Its outputs must pass the smoke on every host that ships a web
  artifact.
- **Build:** a names build plus the split per production web build. The
  names are stripped before shipping.

## 8. Open questions

1. **Separate artifacts.** Should the Markdown editor and text flow, now
   separate wasm with their own std, become stages of the app's module? They
   would share its std and allocator. The editor is 45 KB and text flow
   38 KB brotli, alone.
2. **A capability before its module arrives on a client navigation.** A
   Markdown node needs its module only once its text has arrived, so waiting
   with the data is natural. Does every staged capability have such a point?
3. **Per-route use-sets.** The render server would need each route's
   capabilities, not just the app's. The plan's use-set (LLP 1047 D2) is
   app-wide today.
4. **The minimum size worth its own stage,** given ~10 KB of overhead across
   the modules.

### Measured since the draft, at `121d629e`

- **The mechanism works.** A names build was split four ways and loaded
  with every stage instantiated before boot. It behaved identically to the
  unsplit artifact: home, the tag press in place, an article's Markdown
  (19 pieces), and agent `tree` and `state`, byte for byte. So
  `--multi-split` modules sharing one memory and table run this app in
  Chrome. Staged, withheld loading is untested.
- **Stages by call graph** (`wasm-opt --print-call-graph`). The roots are the
  exports, the address-taken functions and the start function, less the seam
  entries:

  | Stage | Seam entry | Functions | Brotli-11 |
  |---|---|---|---|
  | Markdown | `exact_web_capabilities::markdown::pieces` | 109 | 15.0 KB |
  | Inspection | `exact_runner::agent::handle` | 79 | 11.2 KB |
  | Core (the rest) | — | — | 229.8 KB (unsplit 250.1) |

  The stages are larger than the attribution map's 13.1 and 6.6 KB: they
  take the generic helpers only they use, and leave what the core shares.
  `exact_runner::compare`, which the map files under inspection, is on
  every commit's path (`instance.rs`, `vm.rs`) and stays in the core.
- **What tree shaking can reach.**
  - **The list engine:** entered from `instance::realize`,
    `Tree::collections`, `RegionInst::update` and reorder, as the reviews
    said. Its seam runs through `instance.rs`, which LLP 1050 is rewriting,
    so it is coordinated with that lane, not done beside it.
  - **Motion's transition parser and text flow:** reached from the kernel's
    generated `StyleProps` (its drop, clone, copy and set) as well as from
    the list engine, because `StyleProps` stores those rows' types. Only the
    parsers go with the list seam; the rest needs a style-storage change.
  - **The content region:** entered only from `Kernel::apply`. That is a
    hook in the kernel's commit path, ~1.8 KB.

### As built: the inspection pilot, 2026-09-26 (`c247b1d3`)

**What was built:**
- `host/web/stages.mjs` plans each stage on binaryen's call graph (seam
  entry `exact_runner::agent::handle`). The build fails if the core calls
  the seam directly.
- It splits with `--multi-split --no-placeholders`, binaryen 132 pinned,
  names the stage `stages/inspection.<digest>.wasm`, and records it in the
  core's `exact.stages` section.
- The glue loads the stage before an agent call or a replacement boot, and
  `ask` refuses in JS before the stage has loaded. Calling the raw export
  anyway traps (`RuntimeError: null function`), the assertion.
- The dev loop, the names build and a machine without the pinned binaryen
  stay unsplit, and the build report says why.
- `/stages/` is public, so deploys publish it, and `metrics.mjs` reports
  stage bytes beside the core.

**Checks:**
- The web smoke asserts the page boots with the stage unloaded and that the
  first agent call loads it.
- A normal page (boot, a tag press, navigation) never fetches the stage.
  Agent `tree` and `state` are byte-identical to the unsplit build.
- Fieldnotes, Messages and Exact Live split cleanly too.

**Measured.** RealWorld at `c247b1d3`, served by its render server with the
fixture API. Staged against unsplit from the same commit (the unsplit one
through the build's own fallback). Nine runs each, alternating, loads 14–21.
"Ready" is navigation to the data module's readiness, observed without

### As built: the list-engine seam, 2026-09-26 (`ad07dc2f`)

**The design.** `ListLinks` (`runner/src/instance.rs`) holds the list
engines' heavy entries:
- create a collection;
- a windowed list's children, and its preparation on update;
- a collection's data update;
- a windowed region's update, moved from `RegionInst::update` to
  `window::update_region`;
- typography invalidation;
- the collections JSON.

**How it is wired:**
- The core reaches the table only through `Env::lists`, which the runner
  fills from `RunnerLinks::lists`.
- `LISTS` is named only by `RunnerLinks::ALL` (native hosts, tests) and the
  web's collections capability. `Linked::collections` now carries the table.
- A list engine in use without the table is a named `InstanceError`.
  Admission (D6) refuses such a plan first.
- The windowed list was not deleted, and LLP 1050's parity work is
  untouched; when LLP 1050 deletes it, its entries in the table go too.

**What stays direct:** lookup, row text, drop glue and the reorder bindings
a commit reconciles. By the call graph, that leaves 8.7 KB raw of
list-engine code reachable from the core, against 74 KB before.

**Measured:**
- RealWorld's core went from 754,813 to 698,518 B raw, and from 242,028 to
  233,819 B brotli-11.
- The five checks pass (1,468 tests).
- The web smoke passes for Caltrain, and for Messages (`--app-only`), which
  windows lists.

**A correction to §2 and §5.** A group compressed alone overstates what
removing it saves inside the whole file:

| Group | Alone | Marginal, measured on the core |
|---|---|---|
| List engines | 26 KB | 8.2 KB |
| Inspection | 11.1 KB | 8.1 KB |
| Markdown | 15.0 KB | ~12 KB (the call-graph split) |

The list engines are generic code much like the core's own, so brotli finds
them almost free in context. §2's "about 50 KB RealWorld doesn't need on
most pages" is therefore closer to 25 KB at the margin. Future sizing
should measure a removal against the whole file, as this does.

**The order now:**
1. The transition and shape parsers, which the list engine's style rows
   also reached. Most of their code sits in `StyleProps`'s storage, so it
   needs a storage change.
2. Markdown, after per-route use-sets.
3. The core decision. RealWorld's first download is now 233.8 KB, against
   250.1 at 1047.000's draft and 267.9 before the web toolchain.

### As built: `app.wasm` across deploys, 2026-09-26 (`6e0b8874`)

The review's lead (Opus, in the table above): a returning reader downloaded
all of `app.wasm` after every deploy, since the plan and every app change
with it are inside it. Taken next (Charlie, 2026-09-26: "wire this into
the render server, then test and measure it").

**The constraint.** Chrome keeps a response as a compression dictionary only
while the response is fresh or inside `stale-while-revalidate`. A probe on
Chrome 153:
- `no-cache`, how `app.wasm` went out, is never kept;
- `max-age=0, stale-while-revalidate=…` is kept, but the returning fetch gets
  the old build: an old wasm under new glue;
- `must-revalidate` or `no-cache` beside it is never kept;
- a URL that names its content, cached `immutable`, is kept, and
  `match="/app.wasm"` covers its query.

So `app.wasm`'s URL names its build. That lifts LLP 1048.000 D10's deferral of
content-addressed assets for this one file.

**What was built:**
- `build.mjs` names the build in the shell's preload: `./app.wasm?v=` and the
  first 16 hex digits of its SHA-256. The file keeps its name, so every script
  that reads `dist/app.wasm` is unchanged.
- The capture script and the glue fetch what the page preloads. An
  interaction page, which drops the preload, names the build in its
  checkpoint (`data-wasm`) for `document-glue.js`. The glue stays the same
  across builds. A first version stamped the URL into the glue too, and a
  returning reader then re-downloaded about 20 KB of glue after every deploy:
  80 ms on the mobile profile, twice the delta itself.
- The render server sends a URL that names the build it has as `public,
  max-age=31536000, immutable`, with `Use-As-Dictionary: match="/app.wasm"`.
  Any other `app.wasm` URL (the dev loop's, or a build the server no longer
  has) goes `no-cache` as before.
- `--generations <dir>` keeps each build the server has served under its
  SHA-256, the newest four. At bind it makes the served build's delta against
  each earlier one, at brotli 11 on a thread of its own; brotli's window
  (`lgwin` 22) takes a build and its dictionary up to 4 MB together. Until a
  delta is made, the build goes as brotli.
- A request naming a kept build in `Available-Dictionary` gets `dcb`, with its
  own ETag and `Vary: Accept-Encoding, Available-Dictionary`. A CDN's request
  gets neither the header nor a delta, as for pages (LLP 1048.000 D11).

**Measured.** RealWorld's `/`, served, on the mobile profile. A first visit on
one build, the server restarted on the next, then the revisit timed in the
same browser context. Medians of five, all arms interleaved in one session
(load 2.6):

| Revisit | `app.wasm` | Runtime ready |
|---|---|---|
| After a deploy, with `--generations` | 9.5 KB as `dcb` | **912 ms** |
| After a deploy, before this change | 238.6 KB brotli | 1,608 ms |
| After a deploy, without `--generations` | 238.6 KB brotli | 1,613 ms |
| No deploy (now; before) | 0 B, from cache; a 141 B 304 | 863; 869 ms |
| First visit (now; before) | 238.6 KB brotli | 1,751; 1,757 ms |

- The deploy is a one-string `app.contract` edit.
- The runtime-ready spread is under 20 ms in every arm.
- A revisit without a deploy was already about 865 ms: its 304 overlapped
  other work, so the immutable URL saves a request, not time.
- First visits don't change.

Across runtime changes the deltas are larger:

| From → to | Delta, of 238.6 KB brotli |
|---|---|
| `56f3516a` → `ad07dc2f` (the list-engine seam) | 38.6 KB |
| `56f3516a` → `6e0b8874` (14 commits under the runtime's crates, the seam among them) | 48.5 KB |

Chrome decodes every delta measured to the build's SHA-256.

**Checks:**
- The five checks pass (1,500 tests).
- The render server's tests cover:
  - a named build, its delta, and the delta's 304;
  - a URL that names no build;
  - a CDN's request, and a dictionary the server doesn't keep;
  - keeping the newest four builds.
- Caltrain's document tests (9) and the web smoke pass.
- `agent.test.mjs` fails the same eight as origin/main (QUEUE).
- The capture script's pin in `boot.mjs` moved with it.

**Not yet:**
- Who passes `--generations`: hosting. The bench passes it by hand.
- A page left open across a deploy still loads the new build, and can skew
  against its checkpoint (D10's "kept for pages still open"). The server now
  keeps the earlier builds, so serving each at its own URL would close that.
- The stage files are named by their content but still go `no-cache`;
  `immutable` would drop their revalidation.
