# LLP 1057.000: Composable gestures: a closed table, a shared engine, or native primitives with a shared algebra

**Type:** RFC
**Status:** Draft
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-26
**Systems:** Contract (a `gesture` declaration, `touch-action`), Plan (a compiled gesture graph), Runner (dispatch, the use-set), Motion (holds, springs, `VelocityTracker`), Web host (`glue.js`, `input-glue.js`, `motion-glue.js`), Apple host (UIKit recognizers and delegates, AppKit events), Linux host (evdev contact), Agent API (forms of `tap`)
**Related:** LLP 1057 (the parent research; §10 is design A), LLP 1002 D4/D5/D6 (the platform recognizes; the arena deleted; the trade), LLP 1035.001 §2, §6 (native interaction ownership; no Exact arena), LLP 1035.003 D1/D5 (contact phases; two clocks), LLP 1012 §1 (eight operations; delivery classes), LLP 1043.000 D8 (`pan` commits per frame), LLP 1047 D1/D2/D6 and stage 3 (motion and drag linked by use), `rules/NOT-DOING.md` §Motion (:64-71, :258-263, :275-276, :291), §Agent API (:295-302), §Moving something off (:348-351), `AGENTS.md` "The web is the standard"

## Summary

Charlie asked: can exact2 have SwiftUI's unlimited gesture composition, behave
the same on every host, and keep each platform's feel?

**Yes, with a narrower claim than "the same".** "The same" has to mean the
same outcome: which gesture wins, and the order of its phases. It can't mean
the same timing. With that definition, design C gets all three, but only on
Apple. On the web and Linux, C is design B, because those hosts have no
native recognizers. On Android, if exact2 ever has an Android host, C is
mostly B too.

| | A: the table (LLP 1057 §10) | B: one shared engine | C: native primitives + shared algebra |
|---|---|---|---|
| Author composition | none | unlimited (three combinators) | unlimited (three combinators) |
| Recognition | native per host; glue on the web | Rust on every host | native on Apple; Rust on web and Linux |
| Arbitration | a fixed table, written four ways | the Rust engine | UIKit's graph, which asks the compiled Rust graph through its delegates |
| Feel on iOS | native | constants imitate UIKit | native |
| Cross-host outcome | intended, not tested | identical by construction | identical where the delegate model can express it (§6) |
| Seekable under the virtual clock | web and Linux only | every host | web and Linux; Apple at the primitive level |
| NOT-DOING trade | none for phases 0-1 | arena + compositions + claims | compositions (not an arena, §11) |
| Cost | lowest | high | highest: B's engine plus Apple adapters |

The Contract surface of B and C is **identical**. They differ only in how each
host realizes it, so the choice between them can be made per host and
reversed later.

**Recommendation (§12):**

1. Do A's phases 0 and 1 now: pinch on the photo binding, and the written
   precedence table. They need no trade.
2. Then adopt the algebra with C's realization:
   - the engine on web and Linux;
   - native primitives and delegate queries on UIKit;
   - a hybrid on AppKit: system trackpad events for magnify and rotate, the
     engine for the mouse.
3. Gate step 2 on a UIKit spike that passes a shared conformance suite for
   this RFC's three examples.
4. Pay the NOT-DOING trade by deleting the four hand-written arbitration
   orders and the per-host recognition code of `swiperight` and the three drag
   bindings. The compiled graph replaces them.

## 1. What binds

- **The platform recognizes; the engine follows** (llp/1002:102-106). The
  arena was deleted (llp/1002:189-194). NOT-DOING refuses "a gesture arena,

  (NOT-DOING.md:258-261). It keeps "a generic gesture arena" out of the

- **The web is the standard** (AGENTS.md; RULES.md Scope). The web has no

- **Pay for what you use** (llp/1047 D1/D2/D6). A new capability is linked only
  when the plan's bytes say so.
- **Moving an item off NOT-DOING** takes one line naming what it unblocks, plus
  something taken off the doing-list in the same PR (NOT-DOING.md:348-351).

## 3. The three designs

### A: the table

This is LLP 1057 §10, unchanged:

- Closed recognizers as handler events, each lowered to the host's native
  recognizer.
- `touch-action` completed to CSS's vocabulary.
- One fixed precedence table (llp/1057 §10.2).
- One built-in simultaneous pair: pan with pinch on a transform binding.
- No author composition.

### B: one shared engine

- A declarative algebra in Contract, compiled to a static recognizer graph in
  the plan.
- One deterministic Rust engine on every host, fed normalized pointer streams.
- Up-front claims decide native versus app at pointer down.
- Outputs drive holds (follow) and actions (at phase boundaries).

### C: native primitives + a shared algebra

- The same algebra and plan graph as B.
- Where the platform has a recognizer for a primitive, the platform recognizes
  it. Composition is answered by the compiled graph, which the host consults
  in-process from its native arbitration hooks.
- Where there is no recognizer (the web, Linux, the mouse on AppKit), the B
  engine recognizes.

## 4. The Contract surface

### 4.1 A

No new syntax beyond LLP 1057 §10.1. The examples use today's attributes plus
§10's additions: pinch on `transformDragFor`, and `panrelease`.

```
-- photo: pan + pinch + double-tap zoom
box id="viewer-transform" translate=`${panX}px ${panY}px` scale=zoom transition="translate spring(300, 30, 1), scale spring(300, 30, 1)"
  image viewer.photo.asset object-fit="contain" width="100%" height="100%"
  box transformDragFor="viewer-transform" transformgeometry=photoGeometry transformrelease=releasePhoto dblclick=toggleZoom touch-action="none"

-- long press, then drag, to reorder: the binding picks long press or pan per host (ReorderIOS.swift:9-34)
box reorderFor="arrange-list" reorderdrop=moveItem touch-action="none"

-- swipeable card with a fling: needs §10's phase-2 panrelease; pan commits per frame (LLP 1043.000 D8)
box pan=dragCard panrelease=releaseCard touch-action="pan-y" translate=`${cardX}px 0px` transition="translate spring(260, 26, 1)"
```

What A can't say:

- a double tap that waits for nothing, versus one that suppresses the single
  tap;
- rotate with pinch, unless it's the built-in pair;
- a long press that starts a drag anywhere other than a reorder handle;
- a card that follows the finger without a runner transaction per frame.
  `pan` is a commit by design, and swipe covers only rightward.

### 4.2 B and C (shared)

This is a proposal, sized to Contract's existing shapes: `derive` lines,
curried actions, and mini-languages in values such as `transition`.

```
gesture <name> = <expr>
<expr>      := <primitive> <clause>*
             | simultaneously(<expr>, <expr>, …)   -- all may recognize
             | sequenced(<expr>, <expr>)           -- the second may begin only after the first
             | exclusively(<expr>, <expr>, …)      -- the earlier wins; a later one only if the earlier fail
<primitive> := tap(count: n) | longPress([duration: ms]) | drag([axis: x|y|both] [, minDistance: pt])
             | magnify() | rotate()
<clause>    := follows <row> [of "<id>"]           -- presentation hold: no runner, no app code per frame
             | on begin <action> | on end <action> | on cancel <action>
             | label "<text>"                      -- names the derived accessibility action (§10.4)
```

- **The node attribute:** `gesture=<name>`.
- **Payloads appended at `end`:**
  - `drag`: `dx, dy, vx, vy`;
  - `magnify`: `scale, vscale`;
  - `rotate`: `radians, vradians`;
  - `tap` and `longPress`: none.

  Units follow LLP 1057 §10.3: logical px, px/s, scale units/s.
- **No `on change`.** Per-frame values reach presentation only through
  `follows`, which is a hold (llp/1002:108-122). `follows` is `@GestureState`:
  - it resets to the authored target when the gesture ends or cancels;
  - an `on end` action that writes the target makes the spring start from the
    finger with its release velocity.

  That is how a fling works without a decay driver (NOT-DOING.md:275-276).
- **Omitted `duration` and `minDistance` take the host's constant** (the feel).
  Stated values bind on every host (consistency).
- **Claims are derived, not written.** The graph compiles to the node's
  `touch-action`:
  - `drag(axis: x)` → `pan-y`;
  - any `magnify` → the absence of `pinch-zoom`;
  - `drag()` → `none`.

  An authored `touch-action` intersects with the derived one. The web gets it
  as CSS. UIKit's scroll view already reads it (NodeViewIOS.swift:41-58).

```
-- photo: pan + pinch + double-tap zoom
derive target = "viewer-transform"
gesture photo = exclusively(
    tap(count: 2) on end toggleZoom label "Toggle zoom",
    simultaneously(
      drag() follows translate of target on end releasePan,
      magnify() follows scale of target on end releaseZoom label "Zoom"))
…
box id="viewer-transform" translate=`${panX}px ${panY}px` scale=zoom transition="translate spring(300, 30, 1), scale spring(300, 30, 1)"
  image viewer.photo.asset object-fit="contain" width="100%" height="100%"
  box gesture=photo testId="viewer-handle"              -- derived touch-action: none

-- long press, then drag, to reorder: the reorder binding consumes the drag's output
gesture lift = sequenced(longPress(), drag(axis: y)) label "Move"
box reorderFor="arrange-list" reorderdrop=moveItem gesture=lift

-- swipeable card with a velocity fling
action releaseCard(dx: number, dy: number, vx: number, vy: number) writes cards, cardX
  if abs(vx) > 800 or abs(dx) > 120
    cardX = dx > 0 ? 600 : -600        -- the spring starts at the finger with vx
    cards = dropFirst(cards)
  else
    cardX = 0
gesture fling = drag(axis: x) follows translate on end releaseCard label "Dismiss"
box gesture=fling translate=`${cardX}px 0px` transition="translate spring(260, 26, 1)"   -- derived: pan-y
```

**The existing bindings become sugar.** Each would be a named gesture over the
same holds:

| Today | As a gesture |
|---|---|
| `swiperight` | `drag(axis: x)` with the knee |
| `transformDragFor` | photo's `simultaneously` |
| `heightDragFor` | `drag(axis: y)` |
| `reorderFor` | `sequenced(longPress(), drag(axis: y))`, or `drag(axis: y)` under `touch-action` |

## 6. UIKit: where the delegate model can and can't express each combinator

**The mechanism in C.** Each primitive is a stock UIKit recognizer. When UIKit
asks a relationship question, the delegate calls into the in-process runner
with `(graph node a, graph node b, native states of the graph's recognizers
on this node path)` and returns the answer. The query is a pure function, as
`NavigationRules.panMayBegin` is (NavigationRules.swift:77-80). The host
passes current `state`s rather than keeping a mirror, so there is no drift.
The Apple runner is linked in-process behind a synchronous C ABI
(Bridge.swift:123-158), so a delegate answer costs one FFI call, not a hop.

The delegate hooks. I'm confident of these semantics unless marked:

| Hook | When UIKit asks | Use in C |
|---|---|---|
| `gestureRecognizerShouldBegin(_:)` | leaving `.possible` | the `sequenced` gate; axis and claims (already used, NodeViewIOS.swift:177-196) |
| `shouldRecognizeSimultaneouslyWith` | when one recognizing would block the other; YES from either side's delegate wins | `simultaneously` |
| `require(toFail:)` / `shouldRequireFailureOf` / `shouldBeRequiredToFailBy` | the static call is fixed; the delegate forms are asked lazily, I believe once per recognition attempt (unsure of the exact cadence) | `exclusively` where the earlier primitive is discrete |
| `shouldReceive(_ touch:)` | before a touch reaches a recognizer | editor and canvas exclusion (already used, NodeViewIOS.swift:219-230) |
| `canPrevent` / `canBePrevented` (subclass) | default exclusion | observers (already used, CollectionIOS.swift:8-9) |

Per combinator:

| Combinator | UIKit realization | Holds | Breaks or risky |
|---|---|---|---|
| `simultaneously(A, B)` | YES for pairs within the group | fully. Pinch with rotate, and pan with pinch, are the canonical uses | Today's pans set `maximumNumberOfTouches = 1` (TransformDragIOS.swift:18). With pinch they need 2 and a centroid, or the pan cancels or ignores the second finger. I'm unsure which. The group's composite phase (begins with the first, ends with the last) is synthesized by the graph, not UIKit. |
| `exclusively(A, B)` with A discrete (tap, long press) | `B.require(toFail: A)` | expressible. It is SwiftUI's priority semantics | **Latency.** B waits for A to fail. A single tap waits out the double-tap interval, the classic case (DevMenuIOS.swift:53 does exactly this). That contradicts the web's `dblclick` rule (llp/1057 §4). The graph must say which one the author gets. A `delay` also goes through UIKit's delayed-touch queue, which crashed on a phone (DevMenuIOS.swift:47-49). |
| `exclusively(A, B)` with A continuous (drag, magnify, rotate) | **not** `require(toFail:)`. A pinch with one finger down may stay `.possible` until lift (unsure), stalling B. Instead: UIKit's default exclusion, plus `shouldBegin(B) = A is not began/changed` | as a *race with priority on ties* | A deviation from SwiftUI's strict "B only if A fails". The algebra defines `exclusively` this way for continuous leaders on every host, so the engine matches UIKit. It does not match SwiftUI. |
| `sequenced(longPress, drag)` | **one** `UILongPressGestureRecognizer`: its `.changed` after the press is the drag (ReorderIOS.swift:35-50) | fully, and it is UIKit's own idiom | Doing it with two recognizers breaks. If the pan crosses its hysteresis before the press duration, `shouldBegin(pan)` is asked, the gate says no, and **a failed recognizer stays failed until every touch ends**. The drag never starts. The compiler must pick the one-recognizer realization. The drag's `minDistance` becomes the long press's `allowableMovement` before the lift, and is unbounded after. |
| `sequenced(tap, drag)` (tap then drag, as in Maps' one-finger zoom) | gate `shouldBegin(drag)` on "the tap recognized within the platform's multi-tap interval" | across touch sequences, since recognizers reset between them | Where the drag's touch-down starts matters. UIKit gives no public multi-tap interval, so the window is a host constant (unsure of UIKit's value). |
| `sequenced(A, B)` with A continuous and B another primitive | gate + `simultaneously(A, B)` while A is live | mostly | The same fail-and-stay-failed hazard if B's threshold comes first. Restrict v1 to the two sequenced shapes above. The compiler refuses the rest by name. |

**Races and edge cases**:

1. **Query order.** Two recognizers can change state within one touch event,
   and UIKit's internal order isn't documented. So `simultaneously` and
   `exclusively` must compile to an order-free pairwise table.
   `sequenced`'s gate is the only query that depends on state.
2. **Nested nodes.** A child `tap` and a parent `drag` on different views. The
   delegate hooks work across views, and the compiled graph includes ancestor
   gestures on the hit path. The precedence table's "innermost wins"
   (llp/1057 §10.2 item 3) is the default edge where the author wrote none.
3. **The scroll view.** Its pan is not in the author's graph. It stays outside,
   decided by derived `touch-action` (NodeViewIOS.swift:41-58). Scroll still
   wins every axis the claims leave to it.
4. **System gestures** (interactive pop, the screen edges) stay outside the
   graph, arbitrated as today (NavigationIOS.swift:347-371).
5. **Cancellation.** `.cancelled` from UIKit (an incoming call, the view being
   removed, a scroll steal) ends every hold. The graph's phase order records
   `cancel`, not `end`.
6. **Stale callbacks.** A recognizer outliving its node is already guarded by
   identity checks (LayoutPan.swift:105-108). C keeps that per primitive.
7. **`press` isn't a recognizer.** It's `touchesEnded`, and a pan cancels it
   (NodeViewIOS.swift:1371-1376). A `tap(count: 1)` in a graph would be a
   `UITapGestureRecognizer`. Mixing the two on one node is refused.

**Verdict.** UIKit can express all three combinators if the compiler picks the
realization and the algebra's `exclusively` is defined as the table above says.
The residue it can't express is:

- strict fail-first priority over a continuous leader;
- `sequenced` with an arbitrary continuous predecessor.

Both are refused at compile time, on every host.

## 7. AppKit

- **What AppKit has.** `NSGestureRecognizer` (10.10+) has the same delegate
  shape: `gestureRecognizerShouldBegin`, `shouldRecognizeSimultaneouslyWith`,
  `shouldRequireFailureOf`, `shouldBeRequiredToFailBy`, and
  `shouldAttemptToRecognizeWith event`. Its subclasses are Click (with
  `numberOfClicksRequired`), Press, Pan, Magnification and Rotation. I'm
  confident of the classes. I'm less sure that every delegate method behaves
  exactly like UIKit's.
- **What exact2 uses.** None of them. Mouse input is a responder-chain chain
  (NodeViewMac.swift:1360-1443).
- **The trackpad is already OS-recognized.** `magnify(with:)`, `rotate(with:)`
  and `smartMagnify(with:)` (two-finger double tap) arrive as phased
  `NSEvent`s. They are the most native primitives on the platform, so C takes
  them as-is. `NSMagnificationGestureRecognizer` wraps the same stream.
- **The mouse** has no feel to preserve beyond:
  - `clickCount`, which follows the user's double-click setting;
  - the platform drag threshold.

  So C on AppKit feeds mouse events to the engine, with `clickCount` as the
  host's tap-count constant. It doesn't adopt `NSClickGestureRecognizer`. This
  is B for the mouse and C for the trackpad. The resulting arbitration is the
  graph's, replacing the chain.
- **Device split.** `simultaneously(drag, magnify)` means two devices on a Mac:
  a mouse or trackpad-click drag, and a trackpad pinch. In practice it is
  "either". A **two-finger trackpad scroll over a zoomed photo** should pan it,
  as Preview does. That is scroll input driving a `drag` primitive, and the
  algebra doesn't say that yet (open question 4).
- **Double click.** macOS today drops the second `press` (§2). The algebra's
  `tap(count: 2)` semantics decide this on every host (open question 2).

## 8. Linux, the web, Android

- **Linux (evdev).** It has no recognizers, one contact, and no multitouch
  slots (input.rs:1-4, :108-111). So under both B and C, the engine recognizes
  everything, and `magnify`/`rotate` are declared unavailable.
  - The graph degrades by rule: an unavailable primitive fails at once, so
    `simultaneously(drag, magnify)` is `drag`.
  - Tracking `ABS_MT_SLOT` is a separate Linux lane.
  - The engine replaces the candidate chain (contact.rs:236-241) and keeps
    `VelocityTracker`.
- **The web.** It has no recognizers, so under both B and C the engine
  recognizes from Pointer Events in wasm, called from glue. It replaces:
  - the swipe, transform and height recognizers in `motion-glue.js`;
  - `input-glue.js`'s pan;
  - the JS velocity estimators (motion-glue.js:482, :578).

  Derived `touch-action` goes out as CSS, so the browser still decides scroll
  and zoom on the compositor at pointer down. For trackpad pinch, Safari's
  `gesture*` events and Chromium's `wheel` + `ctrlKey` are normalized into
  `magnify` (llp/1057 §4). The same Rust code that runs Linux runs here. The
  web is the oracle for the engine hosts, and Apple is held to the engine by
  outcome.
- **Android** (no host today). `GestureDetector` and `ScaleGestureDetector`
  are helpers with no arbitration, and arbitration is per-container intercept
  (llp/1057 §3). So an Android host under C would use the detectors' constants
  (`ViewConfiguration` slop and timeouts) and run the engine for composition.
  That is B with native constants, which is also what RNGH ended up building
  (llp/1057 §6). Compose detectors matter only if the host renders with
  Compose.

## 9. How SwiftUI maps its combinators onto UIKit

This section is partly memory, and I've marked it that way.

- **Before iOS 18** (fairly confident): SwiftUI ran its **own gesture engine**
  in-process. Gesture values composed into a tree that SwiftUI evaluated
  against touches from its hosting view. SwiftUI gestures weren't
  `UIGestureRecognizer`s, which is why bridging a UIKit recognizer took a
  representable. It's also why a `DragGesture` inside a `ScrollView` was a
  known conflict. `DragGesture`'s default `minimumDistance` of 10 was a
  constant chosen to feel like UIKit. That is design B, shipped by Apple, and
  it felt native.
- **iOS 18** (moderately confident about the API, unsure about internals):
  - UIKit and SwiftUI gestures were unified;
  - `UIGestureRecognizerRepresentable` was added;
  - failure requirements between UIKit recognizers and SwiftUI gestures became
    possible across frameworks.

  That implies each SwiftUI gesture now participates in UIKit's recognizer
  graph. If so, `simultaneously` likely lowers to simultaneous recognition,
  and `exclusively` to a failure requirement. I don't know how `sequenced` is
  realized, or whether primitives became stock UIKit recognizers or remained
  SwiftUI recognizers registered with UIKit's graph.
- **What this means for exact2.** Apple moved from B toward C. It kept one
  composition algebra and handed arbitration to the platform graph so it could
  interoperate with UIKit. exact2 has the same need: its scroll views, back
  swipe, sheets and swipe actions are UIKit's (llp/1035.001 §2).

## 10. Comparison

### 10.1 Feel

| | A | B | C |
|---|---|---|---|
| iOS thresholds (pan hysteresis, long-press duration, multi-tap interval) | UIKit's | host constants that imitate UIKit; UIKit's are undocumented, so measured | UIKit's |
| iOS velocity | UIKit's | `VelocityTracker` (a 100 ms window, velocity.rs:13) | UIKit's |
| iOS system settings affecting recognition (Touch Accommodations hold duration and similar) | honored | unsure: I believe these act before app touches, so they would still apply | honored |
| Coexisting with UIKit's own recognizers (scroll, back swipe, text, sheets) | native | claims at down only; no mid-gesture relationship | native relationships |
| macOS | trackpad magnify native; mouse chain | mouse and trackpad through the engine | trackpad native; mouse through the engine |
| Web, Linux | glue / host code | engine | engine |

### 10.2 Cross-host consistency

| | A | B | C |
|---|---|---|---|
| Which gesture wins | the table, implemented four times (§2: the macOS and Linux orders differ from each other already) | one engine | one graph; UIKit's realization is checked by the conformance suite |
| Phase order | per host | identical | identical within §6's expressible set |
| Timing | differs | identical where constants are shared; host constants differ by design | differs by design |
| Web as oracle | only for `touch-action` | the engine is the web's recognizer | same as B |

**Equivalence is defined over outcomes.** A conformance case is:

- a starting fixture;
- a script of primitive events (`down`, `move`, `recognize magnify 1.4`,
  `end`);
- the expected `(winner set, phase sequence, actions dispatched with payload
  shapes)`.

The same cases run:

- against the Rust graph in `cargo test`, on the seconds loop;
- on web and Linux through the engine;
- on Apple through a primitive-injection carrier (§10.3).

### 10.3 Determinism and agent testability

| | A | B | C |
|---|---|---|---|
| Seekable under `clock` | web and Linux recognizers only; UIKit's timers aren't seekable (llp/1035.003 D5) | every host: timestamps come from the stream | graph: every host. Primitives: web and Linux |
| Agent drive | `tap` phases (one contact); `recognized` on iOS | multi-contact `tap` phases (`tap down #2 at …`). Amends llp/1035.003 D1, which excluded a second contact | `tap <target> magnify 1.4 [over 300]`, `tap <target> longpress`, beside the existing phases |
| Delivery (llp/1012:224) | as today | `recognized` on Apple (the stream skips UIKit touch delivery); `platform` on web via CDP multi-touch | `platform` on web; `recognized` on Apple and Linux |
| Tests UIKit's real arbitration? | no | n/a (UIKit doesn't arbitrate) | **possibly** (see below) |
| New agent operation | none | none | none |

**Driving the real UIKit graph (unsure).** In agent mode, C's primitives could
be thin subclasses of the stock recognizers, and the driver would set `state`
through the subclass interface. Would UIKit then run its real relationship
resolution, calling the delegate and failing the dependents? If it would, the
iOS carrier tests the actual arbitration and not a model of it. I believe
subclass state changes do trigger that machinery, but I haven't verified it.
This is phase 2's feasibility gate.

| Web | none: ARIA has no custom actions. WCAG 2.5.1/2.5.7 need authored alternatives, like the photo's Fit/2× buttons (apps/interaction-gallery/app.contract:304-309) | same. The compiler can warn when a path or multipoint leaf has no authored alternative |

### 10.6 Bundle size under LLP 1047

- **A** stays inside today's Motion and Drag capabilities (uses.rs:19-37;
  llp/1047 §4 roster: motion about 72 KiB wasm and 37 KiB JS; drag 11 KiB JS).
- **B and C** add one linked capability, `Gestures`, selected by a `gesture`
  row in the plan. Plans without one pay zero (llp/1047 D2/D6).
  - **Estimate, not measured:** the engine for five primitives and three
    combinators is 1.5-3K lines of Rust. That's about 25-50 KiB raw wasm and
    10-20 KiB brotli. For comparison, exact1's arena was 11K lines
    (llp/1002:58-62).
  - It deletes most of the recognition code in `motion-glue.js` and
    `input-glue.js`.
  - On Apple under C, the Rust part is only the graph query (small). The
    adapters are Swift.

## 11. The trade

B and C both need a line off NOT-DOING. Proposed wording, for Charlie:

> **Moved off (Charlie, date):** author-declared gesture composition
> (`simultaneously`, `sequenced`, `exclusively`), compiled to a static graph in
> the plan. On Apple it is realized by UIKit's own recognizer relationships.
> On hosts without recognizers it is realized by one Rust engine. Unblocks:
> photo pinch-and-rotate, long press to drag outside reorder, and flings in
> any direction, with the same outcome on every host.
>
> **Take:**
>
> 1. the four hand-written arbitration orders (NodeViewIOS.swift:177-196,
>    NodeViewMac.swift:1363-1430, contact.rs:236-241, the web's independent
>    listeners);
> 2. the per-host recognition code of `swiperight` and the three drag
>    bindings, which become graph instances;
> 3. the two JS velocity estimators.
>
> Still refused: custom recognizers in Contract, `on change` callbacks,
> runtime graph admission, decay drivers, and a Rust arena on Apple.

Is that a real take? It removes apparatus, and it retires the unwritten
four-way arbitration that LLP 1057 §9.2 called the worst weakness. But
NOT-DOING asks for something taken off the *doing-list*. Charlie may want a
feature taken instead (open question 1).

## 12. Recommendation

1. **Now, no trade:** LLP 1057 §10.6 phases 0 and 1.
   - Write the precedence table.
   - Align the AppKit and Linux orders to it, and fix macOS's second `press`
     to follow whatever Charlie picks for open question 2.
   - Add `pinch-zoom`.
   - Use one velocity estimator and one threshold table.
   - Add pinch on `transformDragFor` for iOS, macOS and web.

   Phase 1 is written as the first compiled graph (the photo's
   `simultaneously`), hard-coded, so nothing is thrown away.
2. **Then C, behind a gate.**
   - The Contract algebra (§4.2).
   - The plan graph.
   - The engine on web and Linux.
   - UIKit primitives with delegate queries.
   - AppKit's hybrid.

   **Gate:** a UIKit spike passes the conformance suite for the three examples,
   including §6's sequenced realization and the subclass carrier. If the gate
   fails for a shape, that shape runs on the engine on Apple (B for that
   gesture only), and the compiler records it.
3. **Not B everywhere.** B is simpler and fully seekable, but on iOS it gives
   up two things: native relationships with UIKit's scroll views, back swipe,
   sheets and text, which exact2 deliberately hands to UIKit
   (llp/1035.001 §2); and UIKit's thresholds and velocity. SwiftUI's own move
   toward UIKit's graph (§9) points the same way.
4. **Not A forever.** A is right as long as nobody has the §10.7 trigger
   (llp/1057:817-828). This RFC's three examples are that trigger in small.
   Whether they're wanted is Charlie's call.

## 14. Open questions for Charlie

1. **The trade.** Is §11's take (deleting four arbitration orders and the
   binding recognizers) enough? Or should a feature come off the doing-list?
2. **Double tap.** Should the web rule (`press`, `press`, `dblclick`, no delay)
   bind on every host, including macOS, which drops the second `press` today?
   Or should `exclusively(tap(2), tap(1))` be allowed to buy UIKit's delayed
   single tap where the author asks for it?
3. **`exclusively` over continuous leaders.** Is the race-with-tie-priority
   meaning (§6) acceptable, given that it differs from SwiftUI's strict
   fail-first?
4. **Trackpad pan on macOS.** Should two-finger scroll over a `drag` +
   `magnify` node drive `drag`, as Preview does, or stay scroll?
5. **Accessibility payloads.** For a `drag` with a `label`, is a synthesized
   terminal payload acceptable, such as "Dismiss" dispatching
   `releaseCard(±∞-ish dx, 0, 0, 0)`? Or must authors name a separate action?
6. **Scope.** Are the three examples wanted as product (a named consumer), or
   is this readiness? NOT-DOING admits consumers, not capability.

## 15. What I'm unsure of

- Whether iOS's two-tap recognizer cancels the second `press` today
  (NodeViewIOS.swift:244-249). I read the default `cancelsTouchesInView` as
  yes, but didn't run it.
- Whether a `UIPinchGestureRecognizer` with one finger down stays `.possible`
  until lift. §6 designs around it either way.
- What a `maximumNumberOfTouches = 1` pan does when a second finger lands:
  cancel, or ignore.
- The cadence of the `shouldRequireFailureOf` / `shouldBeRequiredToFailBy`
  queries (once per attempt is my belief).
- UIKit's undocumented values: pan hysteresis, multi-tap interval, and
  `delaysContentTouches` delay.
- Whether setting `state` from a recognizer subclass runs UIKit's real
  relationship resolution (the §10.3 carrier). This is the gate's crux.
- How far iOS 18's UIKit and SwiftUI unification goes internally, and how
  SwiftUI realizes `sequenced` (§9).
- Whether iOS Touch Accommodations affect a raw-touch engine (B).
- That AppKit's gesture delegate methods match UIKit's exactly.
- The engine's size: 1.5-3K lines and 10-20 KiB brotli is an estimate.
- Whether Charlie reads C on Apple as "not an arena". The graph decides
  relationships while UIKit runs the state machines. Some will call that an
  arena by another name.
