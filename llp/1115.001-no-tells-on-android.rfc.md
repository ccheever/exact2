## 0. Summary

Android was admitted as a host on 2026-10-07, two days before LLP 1115 made "no tells" the
top rule, and LLP 1115 never named it. The second audit (LLP 1115.000) read the Android host
and found 51 things, 18 of them visible to most people in most apps. They come to three
facts:

1. **Nothing is Material.** Everything a person sees is the Linux painter's look, which is
   part Chrome (a 13 × 13 checkbox, `#0075ff`) and part iOS (the switch, the spinner, Apple's
   colours and type ramp).
2. **No setting of the device reaches the app** except its size and density: not dark theme,
   font scale, locale, layout direction, insets as they change, or the keyboard.
3. **Nothing leaves the app but pixels.** Links, share, the clipboard, haptics, notifications
   and pickers are refused or logged. Dialogs, menus and popovers are never painted. System
   Back presses a control whose `id` is `back`, and otherwise the activity finishes.

A separate read of the Kotlin side, which the audit could not see, found it is a benchmark
harness: a finger cannot scroll, text arrives one key at a time, and it has no upcalls at all.
It also found that **every copy of it is on one shared build box, in git repositories with no
remote** (§1).

The reference for Android is an app built by hand with Material 3 on the same Android
version (D1 names the library). This document proposes how Exact gets there: fifteen
decisions (§2) and an order (§3). One needs Charlie's word before anything else: bringing
the reader into the repository (D2). §5 lists the other questions that are his.

## 1. What is there today

**Two hosts, both in `host/linux`.** The *Canvas host* (`canvas.rs`, `canvas/jni.rs`) records
the presenter's paint as an op stream that a Kotlin `View` replays onto Android's own Canvas;
it attaches GPU canvases too. The *swapchain host* (`android.rs`) paints with vello into an
`ANativeWindow`; its whole input is scroll, touch, repaint and stop.

**The reader** (the Kotlin side of the Canvas host) is not in the repository:

- It is on the build box `expo-build-1000`, newest in `~/bench/lists/exact-v11/android/canvas`
  (`c30c683`, 2026-10-11). `~/bench/lists/` holds about 26 copies, none with a remote.
- It is a Views-only Gradle project: an `ExactActivity`, an `ExactView`, about 4,100 lines
  of Kotlin; minSdk 31, targetSdk 36; no Compose, AppCompat or Material library.
- It replays ops onto HWUI's Canvas with a `RenderNode` per row, scroller and layer, and
  hardware bitmaps for pictures. Text is `drawGlyphs` from a font file; the shaping is Rust's.
- It is built for the list benchmark. A bench driver scrolls; a finger does not. Touch is one
  pointer. The soft keyboard is a `BaseInputConnection`, so text is key events. Insets pad the
  view once. `start(width, height, density, …)` is all it tells Rust. It makes no upcall.
- The Views it hosts (a WebView, video) are drawn by hand into nodes and receive no input.
- It handles no lifecycle: a rotation is a resize, and nothing is saved or restored.
- The swapchain host's shell is a 90-line `SurfaceView` activity on the same box.

**By area**, from the audit (IDs in Appendix A):

| Area | Today | A hand-built Material 3 app |
|---|---|---|
| Colour | Apple's fallback hex for every role; always light | the device's dynamic scheme, light and dark |
| Type | 16; Apple's ramp; font scale never read | sp at the person's font scale; Material's type scale |
| Controls | Chrome's checkbox, radio and slider; an iOS switch; grey boxes for buttons and fields | Material 3 components, 48 dp targets |
| Touch feedback | none unless authored; a tapped button keeps a blue focus ring | ripple; no focus in touch mode |
| Text input | one key at a time; caret to the end on tap | IME composition, autofill, handles, the floating toolbar |
| Scrolling | one vertical feed, driven by the bench | the scroller under the finger, fling, stretch overscroll |
| Back | a control with `id="back"`, else leave | pops; predictive back |
| Bars, tabs, lists, sheets | bare boxes; no transitions | top app bar, navigation bar, list items, bottom sheet |
| Dialogs, menus | refused, never painted | alert dialog, dropdown menu |
| System bars, insets | once at launch or never; no keyboard inset | edge to edge, kept current |
| Out of the app | refused | Intents, Sharesheet, clipboard, haptics, notifications |
| Accessibility | nothing leaves the process | a TalkBack node tree |
| Lifecycle | none | state survives rotation, backgrounding and process death |

## 2. Decisions

### D1 — What "the platform's" means on Android

On iOS the system's controls are the system's views, so Exact uses them. On Android most
"system controls" are a library's drawings: Compose's Material 3 paints its checkbox on a
Canvas, as Exact would. So painting a Material control is not by itself a tell. A person who
knows Android notices the control's shape, colour, ripple and motion, and they notice the
things that are the operating system's own:

- text input (the IME, composition, autofill, selection handles, the floating toolbar),
- scrolling (fling, overscroll stretch, nested scrolling),
- system bars, insets and cutouts,
- Back, and its predictive preview,
- haptics, accessibility, the system font and its scale,
- the system's own dialogs and pickers, and the app's lifecycle.

**Proposed.**

1. **The reference** is the current stable Compose Material 3 library's components, on the
   device's dynamic colour, on the same Android version. Each stage that builds a component
   names the library version it matched.
2. **Exact uses everything in the list above and never imitates it.**
3. **Painting a Material component is permitted, not required.** A component is painted
   when that is the cheaper way to match the reference without giving up cold start, and it
   is a framework or library view when that is cheaper (a date picker is the first case, D9).
   The choice is made per component and recorded where it is built.

LLP 1104 D7 ("Linux has no platform controls", so the painted hosts have a look of their own)
holds for desktop Linux and is amended for Android, which has a platform.

### D2 — The Canvas host ships; the reader comes into the repository (Charlie's word)

1. **The Canvas host is the app host**, for games too: it already attaches GPU canvases, it
   draws through Android's own Canvas, the system's overscroll effect and accessibility
   provider attach to its view, and it is the host the benchmarks measured ahead of Views and
   Compose on cold start. **The swapchain host stays experimental** and gets nothing in this
   document, so two shells do not each collect the platform's obligations. It earns work when
   a consumer shows what it does better.
2. **The reader moves into this repository** as `host/android/` (Kotlin and its Gradle
   build), under a general class name in place of `dev.exact.bench.exactcanvas`, with the
   bench driver left behind as a consumer. This adds a directory and a build system, which is
   apparatus, so it needs Charlie to say so. Until it moves, its only copies are on one box.
3. `scripts/agent.mjs android` gains the `--reader` carrier LLP 1107 D1 foresaw, driving the
   APK; `apps/shelf` gets the `linux/` crate it lacks, so the recipe app builds for Android.

Rust-side work below can be built and driven headless before the move. Every Kotlin half
waits for it.

### D3 — The device's settings reach the app, before its first layout

1. **One call carries the configuration** before the first layout and again, whole, on every
   change: night mode, font scale, locales and layout direction, the 12/24-hour preference,
   "remove animations", bold text and contrast. The presenter has some receiving ends
   (`set_system_scheme`, `set_root_font_size`, `set_preferences`); nothing calls them on
   Android.
2. **The presenter alone owns insets.** The reader passes the raw system-bar, cutout and IME
   insets whenever they change and pads nothing itself, so no inset is applied twice. The
   presenter resizes the viewport, answers `env(safe-area-inset-*)`, and keeps the focused
   field above the keyboard. That last part does not exist: the presenter reports a keyboard
   inset of zero today, so it is built here, not switched on.
3. **The device's direction applies only where the author left `direction` unsaid.**
4. **The window's background before the first frame is `surface`**, the colour the first
   frame will have, and an unset page background is `surface` too. Never white.

### D4 — Colours and type are reported by the host, not tabled

The role table has an iOS column and a macOS column because those values are named constants.
Android's are computed per device (dynamic colour) and per setting (font scale is non-linear
above 100% since Android 14). So the Kotlin side resolves them and reports them, through the
door Apple already uses for colours (`roles::set_reported`) and a matching one for type. The
names an author writes do not change.

**Type is reported whole, as layout input.** For each text style the host reports size,
weight, line height and tracking, and the kernel resolves them before it measures, so layout
agrees on every host given the same resolved inputs. Two things in lowering stand in the way
today and change with LLP 1115.000 D12.2: a heading is lowered to a literal weight, and the
`font` shorthand writes a literal weight and `line-height: normal`. Both name the style
instead, and an authored `font-weight` or `line-height` stays distinct from the style's own.
Authored `px` and CSS's relative units mean what they mean now.

### D5 — One channel out

Every Android call today goes from Kotlin into Rust. Haptics, opening a URL, share, the
clipboard, notifications, pickers, showing the keyboard, saying whether Back has somewhere to
go, and accessibility events all need the other direction. **One mechanism:** the presenter
queues host requests and wakes the reader, which takes them on the UI thread. It does not
wait for a paint, since a haptic or a clipboard write changes no pixel and a frame may carry
no stream. A request that has an answer (a picker, a permission) completes or is cancelled
later, by its id. No capability gets a channel of its own.

With it, what the author wrote works: a link opens (a Custom Tab, the dialer, mail), `share`
is the Sharesheet, `copyText` the clipboard, `haptic` and `-exact-press-haptic` are
`performHapticFeedback`, `showPicker` the Photo Picker or the document picker.

[AND-16, -26]

### D6 — Back, in order

System Back goes to the first of these that takes it:

1. the soft keyboard, which the system closes itself;
2. the top layer: an open menu, dialog or sheet closes (D10);
3. the route: the authored Back control if there is one; else the navigation root's
   `navigate` handler; else, and only for a root with no handler, the runner's `host_back`
   (which is what `host_back` is for; calling it first would bypass what the author wrote).

The reader's back callback is enabled only while one of these would take it (told through
D5), so Back at the root leaves the app with the system's own animation. Predictive back's
progress is presentation only: nothing commits until the gesture does, and a cancel puts the
screen back (D12).

[AND-5]

### D7 — Scrolling and touch are the system's

1. **The reader owns the scroll gesture and its physics:** `OverScroller`'s fling, the
   stretch `EdgeEffect`, fading scroll indicators, nested hand-off. Nothing scrolls by finger
   now, so this is new work, not a port.
2. **The boundary is stated before it is built.** The presenter tells the reader, per
   scroller: its id, its axes, its bounds and its current offset. The reader is the authority
   on the offset while a gesture or fling runs and reports it; a programmatic scroll from the
   app goes the other way and ends any fling. When a scroll wins a touch, the presenter's own
   press and pan recognition for that touch is cancelled. Today's entry is one vertical
   delta, which is none of this.
3. **A finger is a finger:** pointer type `touch`, no hover left behind after it lifts,
   multi-touch as the gestures need it. Slop, long-press and fling thresholds are read from
   `ViewConfiguration`, not replaced by another constant.
4. **No focus ring in touch mode.** A focused control shows a ring only when the focus came
   from a keyboard or D-pad, as `:focus-visible` rules on the web. A hardware keyboard moves
   focus between controls outside a text field: Tab, the arrows, Enter and Escape reach the
   presenter, which today hears only characters, Enter and Backspace.

[AND-12, -17, -18, -25; the hardware-keyboard half of AND-11]

### D8 — A text field is a real `EditText`

Each visible `input` and `textarea` hosts the framework's own `EditText`, with no background
of its own, over the container D9 gives it. The IME, composition, autofill, the selection
handles, the magnifier, the floating toolbar and spell checking come with it, and `type`,
`inputmode`, `enterkeyhint`, `autocomplete` and `autocapitalize` map to its input type and
IME options. A field is real whether or not it is focused, so nothing shifts on focus.

The hosted Views the reader has today are drawn by hand and take no input, so hosting a live
one is new. Decided here, before it is built:

- **Geometry.** The kernel lays the field out; the `EditText`'s own measurement (its line
  height and insets at the reported type) feeds the kernel through the control-measurement
  seam the other hosts use. The view is placed, clipped and transformed by its node's box,
  and stacks in tree order with painted content.
- **Value and composition.** The `EditText` owns the text while it has a composition. An
  app commit that sets the same value leaves the composition and selection alone; one that
  sets a different value replaces the text and ends the composition.
- **Identity.** A field keeps its view, its selection and its undo while its node lives,
  through app commits and through its row scrolling out and back. A recycled row gets a
  recycled view only with that state reset.
- **Touch.** A touch inside the field's box goes to the `EditText`; the presenter hears of
  the focus, not the touch.

Re-implementing text input over an `InputConnection` is the alternative. It is the part of
Android that painted toolkits get wrong longest, and LLP 1076 §7 question 4 asked which
controls should stay native. This one.

[AND-11]

### D9 — The Material look, measured and painted

The Linux presenter gains a look for Android beside desktop Linux's, chosen at build time.
Desktop Linux and Windows keep theirs, and the five tests that pin it stay as they are.

- **Metrics enter measurement, not only paint.** A control's Material size reaches the
  kernel through the same control-measurement seam, so layout knows it. Its **touch target**
  is separate from its drawn size: a 40 dp button and a 20 dp checkbox each answer a 48 dp
  target. An authored size, padding or radius wins, and `appearance="none"` is the author's
  box, as on every host.
- **Buttons** by `buttonStyle`, keeping the order of emphasis: `filled` and the prominent
  styles are Material's filled button, `tinted` its tonal, `bordered` and `gray` its
  outlined, `plain` its text button.
- **Checkbox, radio, switch, slider, linear and circular progress** in Material's metrics
  and motion. The indeterminate indicators turn.
- **A field's container** is Material's filled text field around D8's `EditText`. A `select`
  is an exposed dropdown that opens D10's menu.
- **Press** is the ripple and state layer, bounded by the control's or the row's shape, for
  native controls and for every undeclared pressable (LLP 1115.000 D6's Android row).
- **Date and time** are the first components that are not painted (D1.3): the framework's
  `DatePickerDialog` and `TimePickerDialog`, opened through D5, with the value shown in the
  locale's format. For these two the reference is the system's dialog, which is what a
  Views app shows; this is a stated exception to D1.1's library.
- An inherited `color` does not tint a spinner or a field (LLP 1115 D4).

### D10 — A top layer

The presenter presents dialogs, menus, sheets and snackbars in a layer above the page. On
Android: an `alertdialog` is Material's alert dialog, a menu popover its dropdown menu, a
chooser and a `modal` route its bottom sheet with a scrim and a drag handle. `showModal` and
`close` stop being unknown commands, which makes LLP 1115 D6 true here.

Its behaviour is part of the decision, not left to the look: what dismisses each surface
(a tap outside, Back, Escape, a drag), that the page beneath is inert to touch, keys and
TalkBack, that focus moves in and returns to the invoker, and that a hosted View (D8's
`EditText`, a WebView) stacks under a surface opened over it.

The mechanism will serve desktop Linux too, which has no top layer either. Finishing the
desktop's presentation of it is not part of this document.

[AND-6]

### D11 — Structure is projected

A route's `header` is a top app bar (its heading, the Back arrow, its buttons), a root
`tablist` is a navigation bar, a segmented `tablist` is Material's segmented buttons, and
`list appearance="auto"` rows are list items with Material's dividers. What counts as
header-shaped, a root tab bar or a grouped row is recognised by the rules iOS uses, in shared
code. What each becomes on Android is Android's decision and is not copied from UIKit: a top
app bar's title placement and collapse, a navigation bar's labels, a list item's leading and
trailing slots follow Material.

Until this lands, an app written as LLP 1115 D7 asks (structure, nothing else) is unstyled
rows on Android. That is the largest gap and the largest piece of work.

[AND-14]

### D12 — Motion and gestures

A push, a pop and a tab switch use the platform's transitions, and predictive back previews
the pop. What the author declared and Android has a form for is presented: swipe actions,
pull-to-refresh, sheet detents, keyboard dismissal on scroll, long-press context menus.

[AND-24, -28]

### D13 — Accessibility is built with the rest, and gates release

The reader's view answers TalkBack through an `AccessibilityNodeProvider`, fed by the
presenter from the kernel's tree: role, name, state, bounds, actions and live regions. Android
is not called supported for shipped apps before this works.

It is not built last. Virtual-node identity, actions, traversal order and modal filtering
are settled with scrolling (D7), the text field (D8) and the top layer (D10), because each
of those decides what a node is. A real `EditText` reports itself, and the painted node for
the same field is not reported twice. `tree --ax` on Android reads what Android exposes, not
the presenter's own idea of it.

[AND-19]

### D14 — Symbols have Material's shapes

A symbol role gains an Android glyph beside its SF name and its web path: `back` is an arrow
and not a chevron, `share` is Android's share mark, `more` is three vertical dots. The glyphs
come from Material Symbols. Directional ones mirror in a right-to-left layout. An image the
author supplied is never replaced.

[AND-29]

### D15 — The app survives what Android does to it

An Android app is recreated on a configuration change it does not handle, stopped in the
background, and killed and restored by the system. A person notices an app that loses its
place. Proposed:

1. **Configuration changes are handled, not survived by restart:** rotation, a resize, night
   mode and font scale reach the running host through D3. The activity is not recreated for
   them.
2. **Background and resume:** the host stops its frame work when the activity stops and
   resumes it on start.
3. **Process death:** the route stack, each scroller's offset, focus and a field's draft come
   back. What an app's own state needs to survive is LLP 1018's subject; what the host must
   save beside it (offsets, focus, an uncommitted draft) goes in the activity's saved state.

[not in the audit; found by the review, from `android-reader.md`]

## 3. Order of work

**S0 (Charlie's word): the reader moves in** (D2), with the `--reader` carrier, and Shelf
builds for Android.

**S1: one screen through every layer.** A vertical slice on `apps/shelf`: its library (a
list, a search field, a row's menu) and its add-a-book form (text fields, a number field,
a button):

- D3 whole: settings before first layout, insets, the keyboard inset;
- D5's transport, carrying only what the slice needs (Back's state, the keyboard, a haptic);
- D6: Back through its order;
- D7: a finger scrolls the list, with the boundary of D7.2;
- D8: one real `EditText`;
- D10: the top layer's behaviour, with one menu, since a `select` needs it;
- D13: TalkBack reads that screen;
- D4's colours, so it is in the device's palette, light and dark.

Not in the first slice: notifications and the wider set of D5's requests, the full symbol
set, route transitions, and anything for desktop Linux. Cold start and the edit loop are
measured with the existing tools before and after, since the reader gains work.

**Then, in this order:** S2, the Material look and D4's type (D9, D14); S3, structure (D11);
S4, motion and gestures (D12); S5, the rest of D5 and lifecycle's process death (D15.3).
D15.1 and D15.2 land with S1, since a slice that restarts on rotation proves nothing.

Rust halves that need no Kotlin (the JNI entry points onto existing setters, the pointer
type, the focus rule, the Material painting and measuring) can land ahead of S0 and be
driven headless (`agent android`, `agent linux`). Each stage ends with a drive of
`apps/shelf` on a Pixel, light and dark, at the default and the largest font scale.

The comments and tests the audit found on this host change with their stage: the stale
reasons ("Linux's pointer is a mouse", "This host reads no system setting", "No haptic engine
here") with S1.

## 4. Not in this document

- A Kotlin native module, and a `view` for a node that is an Android `View`: their own RFC,
  as `QUEUE.md` already says.
- Hatches on Android beyond what LLP 1075.003.000.001's stage 6 built.
- Tablets, foldables beyond LLP 1078, Wear, TV and Auto.
- Widgets, the look of notifications, the app icon and the splash screen's own design.
- Which text engine shapes on Android (LLP 1085.000).
- A per-app language picker and per-app theme.

## 5. Questions that are Charlie's

1. Is the reader's move into the repository, with its Gradle build, approved (D2)?
2. Which app defines the first supported release? This document assumes `apps/shelf`.
3. Who owns Material fidelity after the first slice: matching a moving library is ongoing
   work, not a one-time port.
4. May a stage use a Material-library component where that is cheaper than painting (D1.3)?
   The reader has no Material or AppCompat dependency today, and adding one costs APK size
   and possibly cold start, which is why D1.3 says "without giving up cold start".
