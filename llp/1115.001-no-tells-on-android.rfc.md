## 0. Summary

Android was admitted as a host on 2026-10-07, two days before LLP 1115 made "no tells" the
top rule, and LLP 1115 never named it. The second audit (LLP 1115.000) read the Android host
and found 51 things, 18 of them visible to most people in most apps. They come to three
facts:

1. **Nothing is Material.** Everything a person sees is the Linux painter's look, which is
   part Chrome (a 13 × 13 checkbox, `#0075ff`) and part iOS (the switch, the spinner, Apple's
   colours and type ramp).
2. **No setting of the device reaches the app** except its size and density: not dark theme,
   font scale, locale, layout direction, insets as they change, or the keyboard.
3. **Nothing leaves the app but pixels.** Links, share, the clipboard, haptics, notifications
   and pickers are refused or logged. Dialogs, menus and popovers are never painted. System
   Back presses a control whose `id` is `back`, and otherwise the activity finishes.

A separate read of the Kotlin side, which the audit could not see, found it is a benchmark
harness: a finger cannot scroll, text arrives one key at a time, and it has no upcalls at all.
It also found that **every copy of it is on one shared build box, in git repositories with no
remote** (§1).

The reference for Android is an app built by hand with Jetpack Compose or Views using
Material 3 on the same Android version. This document proposes how Exact gets there: twelve
decisions (§2) and an order (§3). Two need Charlie's word before anything else: which host
ships, and bringing the reader into the repository (D2).

## 1. What is there today

**Two hosts, both in `host/linux`.** The *Canvas host* (`canvas.rs`, `canvas/jni.rs`) records
the presenter's paint as an op stream that a Kotlin `View` replays onto Android's own Canvas.
The *swapchain host* (`android.rs`) paints with vello into an `ANativeWindow`; its whole input
is scroll, touch, repaint and stop.

**The reader** (the Kotlin side of the Canvas host) is not in the repository:

- It is on the build box `expo-build-1000`, newest in `~/bench/lists/exact-v11/android/canvas`
  (`c30c683`, 2026-10-11). `~/bench/lists/` holds about 26 copies, none with a remote.
- It is a Views-only Gradle project: an `ExactActivity`, an `ExactView`, about 4,100 lines
  of Kotlin; minSdk 31, targetSdk 36; no Compose, AppCompat or Material library.
- It replays ops onto HWUI's Canvas with a `RenderNode` per row, scroller and layer, and
  hardware bitmaps for pictures. Text is `drawGlyphs` from a font file; the shaping is Rust's.
- It is built for the list benchmark. A bench driver scrolls; a finger does not. Touch is one
  pointer. The soft keyboard is a `BaseInputConnection`, so text is key events. Insets pad the
  view once. `start(width, height, density, …)` is all it tells Rust. It makes no upcall.
- The swapchain host's shell is a 90-line `SurfaceView` activity on the same box.

**By area**, from the audit (IDs in Appendix A):

| Area | Today | A hand-built Material 3 app |
|---|---|---|
| Colour | Apple's fallback hex for every role; always light | the device's dynamic scheme, light and dark |
| Type | 16; Apple's ramp; font scale never read | sp at the person's font scale; Material's type scale |
| Controls | Chrome's checkbox, radio and slider; an iOS switch; grey boxes for buttons and fields | Material 3 components, 48 dp targets |
| Touch feedback | none unless authored; a tapped button keeps a blue focus ring | ripple; no focus in touch mode |
| Text input | one key at a time; caret to the end on tap | IME composition, autofill, handles, the floating toolbar |
| Scrolling | one vertical feed, driven by the bench | the scroller under the finger, fling, stretch overscroll |
| Back | a control with `id="back"`, else leave | pops; predictive back |
| Bars, tabs, lists, sheets | bare boxes; no transitions | top app bar, navigation bar, list items, bottom sheet |
| Dialogs, menus | refused, never painted | AlertDialog, DropdownMenu |
| System bars, insets | once at launch or never; no keyboard inset | edge to edge, kept current |
| Out of the app | refused | Intents, Sharesheet, clipboard, haptics, notifications |
| Accessibility | nothing leaves the process | a TalkBack node tree |

## 2. Decisions

### D1 — What "the platform's" means on Android

On iOS the system's controls are the system's views, so Exact uses them. On Android most
"system controls" are a library's drawings: Compose's Material 3 paints its checkbox on a
Canvas, as Exact would. So painting a Material control is not by itself a tell. A person who
knows Android notices the control's shape, colour, ripple and motion, and they notice the
things that are the operating system's own:

- text input (the IME, composition, autofill, selection handles, the floating toolbar),
- scrolling (fling, overscroll stretch, nested scrolling),
- system bars, insets and cutouts,
- Back, and its predictive preview,
- haptics, accessibility, the system font and its scale,
- the system's own dialogs and pickers.

**Proposed:** Exact paints Material 3 as the Material library draws it, on the device's
palette, and it *uses* everything in that list and never imitates it. LLP 1104 D7 ("Linux has
no platform controls", so the painted hosts have a look of their own) holds for desktop Linux
and is amended for Android, which has a platform.

### D2 — The Canvas host ships apps; the reader comes into the repository (Charlie's word)

1. **The Canvas host is the app host.** It draws through Android's own Canvas, so real Views
   (a text field, a WebView, video) sit in one hierarchy with painted content, the system's
   overscroll effect and accessibility provider attach to its view, and it is the host the
   benchmarks measured ahead of Views and Compose on cold start. The swapchain host is the
   game host, as the wasm target is on the web (LLP 1071 §8); it gets Back, insets and
   configuration and nothing else here.
2. **The reader moves into this repository** as `host/android/` (Kotlin and its Gradle
   build), under a general class name in place of `dev.exact.bench.exactcanvas`, with the
   bench driver left behind as a consumer. This adds a directory and a build system, which is
   apparatus, so it needs Charlie to say so. Until it moves, its only copies are on one box.
3. `scripts/agent.mjs android` gains the `--reader` carrier LLP 1107 D1 foresaw, driving the
   APK; `apps/shelf` gets the `linux/` crate it lacks, so the recipe app builds for Android.

Everything Rust-side below can be built and driven headless before the move. Every Kotlin
half waits for it.

### D3 — The device's settings reach the app

One call at start and on every configuration change carries: night mode, font scale, locales
and layout direction, the 12/24-hour preference, "remove animations", bold text and contrast.
A second carries insets (system bars, cutout, IME) whenever they change. The presenter
already has the receiving ends (`set_system_scheme`, `set_root_font_size`, `set_safe_area`,
`set_preferences`); nothing calls them on Android.

With that: the app is edge to edge; an unset background is `surface`, never white; the
focused field stays above the keyboard; a right-to-left language mirrors.

### D4 — Colours and type are reported by the host, not tabled

The role table has an iOS column and a macOS column because those values are named constants.
Android's are computed per device (dynamic colour) and per setting (font scale is non-linear
above 100% since Android 14). So the Kotlin side resolves them and reports them, through the
door Apple already uses for colours (`roles::set_reported`) and a matching one for the type
ramp. The names an author writes do not change.

| Role | Material 3 |
|---|---|
| `Canvas`, `-exact-background` | `surface` |
| `CanvasText`, `-exact-label` | `onSurface` |
| `-exact-secondary-label`, `-exact-placeholder` | `onSurfaceVariant` |
| `-exact-tertiary-label`, `GrayText` | `onSurface` at 38% (Material's disabled content) |
| `-exact-separator` | `outlineVariant` |
| `AccentColor`, `LinkText`, `-exact-link`, `ButtonText` | `primary` |
| `AccentColorText` | `onPrimary` |
| `Field`, `-exact-fill` and its kin | `surfaceContainerHighest` |
| `ButtonFace` | `secondaryContainer` |
| `-exact-secondary-background`, `-exact-grouped-background` | `surfaceContainerLow` |
| `-exact-secondary-grouped-background`, `-exact-tertiary-background` | `surfaceContainer` |
| `Highlight` | `primary` at 40% |
| `-exact-system-red` | `error` |
| the other system hues | the table's own pair (they are hues, not roles) |

| Text style | Material 3 (size/line, weight) |
|---|---|
| `large-title` | `displaySmall` 36/44 |
| `title1` | `headlineMedium` 28/36 |

The root font size is 16 sp at the person's scale. The system font is the device's default
family, not a literal "Roboto". One accent: the painter's `#0075ff` goes.

### D5 — One channel out

Every Android call today goes from Kotlin into Rust. Haptics, opening a URL, share, the
clipboard, notifications, pickers, showing the keyboard, saying whether Back has somewhere to
go, and accessibility events all need the other direction. **One mechanism:** the presenter
queues host requests and the reader drains them after each frame it takes. No capability
gets its own.

With it, what the author wrote works: a link opens (a Custom Tab, the dialer, mail), `share`
is the Sharesheet, `copyText` the clipboard, `haptic` and `-exact-press-haptic` are
`performHapticFeedback`, `showPicker` the Photo Picker or the document picker.

[AND-16, -26]

### D6 — Back

System Back pops a pushed route or closes a sheet through the runner's `host_back`, whether or
not the author declared a control (LLP 1115 D5); an authored control is still what it presses.
The reader's back callback is enabled only while there is somewhere to go (told through D5),
so Back at the root leaves the app with the system's own animation. Predictive back's
progress drives the route's transition once routes have one (D10).

[AND-5]

### D7 — Scrolling and touch are the system's

1. **The reader owns the scroll gesture and its physics:** the scroller under the finger, on
   either axis, with the system's slop, `OverScroller`'s fling, the stretch `EdgeEffect`,
   fading scroll indicators, and nested hand-off between scrollers. The presenter is told
   offsets, as it is today by the bench driver. Nothing scrolls by finger now, so this is new
   work, not a port.
2. **A finger is a finger:** pointer type `touch`, no hover left behind after it lifts, the
   system's 8 dp slop in place of 4, multi-touch as the gestures need it.
3. **No focus ring in touch mode.** A focused control shows a ring only when the focus came
   from a keyboard or D-pad, as `:focus-visible` rules on the web.

[AND-12, -17, -18, -25]

### D8 — A text field is a real `EditText`

Each visible `input` and `textarea` hosts the framework's own `EditText`, with no background
of its own, over the container the painter draws (D9). The IME, composition, autofill, the
selection handles, the magnifier, the floating toolbar and spell checking come with it, and
`type`, `inputmode`, `enterkeyhint`, `autocomplete` and `autocapitalize` map to its input type
and IME options. The same holds on iOS, where a field is a `UITextField`. A field is real
whether or not it is focused, so nothing shifts when it takes the focus.

Re-implementing text input over an `InputConnection` is the alternative. It is the part of
Android that painted toolkits get wrong longest, and LLP 1076 §7 question 4 asked which
controls should stay native. This one.

[AND-11]

### D9 — The Material look is painted

The Linux presenter gains a look for Android beside desktop Linux's, chosen at build time.
Desktop Linux and Windows keep theirs, and the five tests that pin it stay as they are.

- **Buttons** by `buttonStyle`, keeping the order of emphasis: `filled` and the prominent
  styles are Material's filled button, `tinted` its tonal, `bordered` and `gray` its
  outlined, `plain` its text button; 40 dp tall, fully rounded, `labelLarge`.
- **Checkbox, radio, switch, slider, linear and circular progress** in Material's metrics
  and motion, each with a 48 dp target. The indeterminate indicators turn.
- **A field's container** is Material's filled text field around D8's `EditText`. A `select`
  is an exposed dropdown that opens D10's menu.
- **Press** is the ripple and state layer, bounded by the control's or the row's shape, for
  native controls and for every undeclared pressable (LLP 1115.000 D6's Android row).
- **Date and time** open the framework's `DatePickerDialog` and `TimePickerDialog` through
  D5, and show the value in the locale's format. They are the system's dialogs, so nothing
  is imitated.
- An inherited `color` does not tint a spinner or a field (LLP 1115 D4).

[AND-4, -7 to -10, -22, -23, -27, -30, -33]

### D10 — A top layer, and structure

1. **The presenter gets a top layer** for dialogs, menus, sheets and snackbars. Desktop Linux
   needs the same mechanism and gets it with its own look. On Android: an `alertdialog` is
   Material's alert dialog, a menu popover its dropdown menu, a chooser and a `modal` route its
   bottom sheet with a scrim and a drag handle. `showModal` and `close` stop being unknown
   commands, which makes LLP 1115 D6 true here.
2. **Structure is projected, as on iOS:** a route's `header` is a top app bar (its heading,
   the Back arrow, its buttons), a root `tablist` is a navigation bar, a segmented `tablist`
   is Material's segmented buttons, and `list appearance="auto"` rows are list items with
   Material's dividers. The rules that decide what is header-shaped are the ones iOS uses.
3. **Routes move:** a push, a pop and a tab switch use the platform's transitions, and
   predictive back previews the pop (D6).
4. What the author declared and Android has a form for is presented: swipe actions,
   pull-to-refresh, sheet detents, keyboard dismissal on scroll, long-press context menus.

Until this stage lands, an app written as LLP 1115 D7 asks (structure, nothing else) is
unstyled rows on Android. That is the largest gap and the largest piece of work.

[AND-6, -14, -24, -28]

### D11 — Accessibility is a gate

The reader's view answers TalkBack through an `AccessibilityNodeProvider`, fed by the
presenter from the kernel's tree: role, name, state, bounds, actions and live regions, the
same facts `tree --ax` reads. Android is not called supported for shipped apps before this
works; it can be built last.

[AND-19]

### D12 — Symbols have Material's shapes

A symbol role gains an Android glyph beside its SF name and its web path: `back` is an arrow
and not a chevron, `share` is Android's share mark, `more` is three vertical dots. The glyphs
come from Material Symbols.

[AND-29]

## 3. Order of work

| Stage | What | Needs the reader in the repository |
|---|---|---|
| S0 | D2: the reader moves in; `--reader` carrier; Shelf builds for Android | it is the move |
| S1 | D3 settings and insets; D6 Back through `host_back`; D7.2 and D7.3; D4 colours | the Kotlin halves |
| S2 | D5 the channel out, and what rides it | yes |
| S3 | D7.1 scrolling | yes |
| S4 | D8 text input | yes |
| S5 | D9 the Material look, D4's type ramp, D12 | the reported ramp only |
| S6 | D10 the top layer, structure, transitions | no, but for predictive back |
| S7 | D11 accessibility | yes |

The Rust halves of S1 (JNI entry points onto the presenter's existing setters, `host_back`,
the pointer type, the slop, the focus rule) and all of S5's painting and S6's top layer can
land first and be driven headless (`agent android`, `agent linux`). Each stage ends with a
drive of `apps/shelf` on a Pixel, light and dark, at the default and the largest font scale.

The comments and tests the audit found on this host change with their stage: the stale
reasons ("Linux's pointer is a mouse", "This host reads no system setting", "No haptic engine
here") with S1 and S2; LLP 1076's "Android remains deferred" gets a note now.

## 4. Not in this document

- A Kotlin native module, and a `view` for a node that is an Android `View`: their own RFC,
  as `QUEUE.md` already says.
- Hatches on Android beyond what LLP 1075.003.000.001's stage 6 built.
- Tablets, foldables beyond LLP 1078, Wear, TV and Auto.
- Widgets, the look of notifications, the app icon and the splash screen.
- Which text engine shapes on Android (LLP 1085.000).
- A per-app language picker and per-app theme.
