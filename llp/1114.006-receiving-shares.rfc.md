## 1. Summary

"Share to Bluesky" from Photos, Safari or another app should open the clone's
composer with the shared text, link or images. The web already has a standard
for this: the Web App Manifest's `share_target`, which makes a share a
navigation to the app's `action` URL with the shared members as query
parameters. This RFC adopts it as written. On every host a received share ends
as one location — `/compose?text=…&url=…` — delivered the way LLP 1038 D8
already delivers a URL: the launch location when cold, one `navigate` event
when running. The router, `searchParam` and the app's `navigate` action do the
rest; no new event kind, no new shape.

Files are the one deviation. The web posts their bytes as `multipart/form-data`;
exact2 delivers each file's `app:/tmp/shared/…` path as the parameter's value,
the way the file picker delivers `app:/tmp/picked/…` paths. Only a share the
host itself claimed may carry those parameters.

The cost is on Apple. iOS and macOS show an app in other apps' share sheets
only through a **share extension**: a second bundle, a second executable, a
second signature and profile, and, for files, an App Group both processes can
write to. This is the first extension target exact2's build would make.

## 2. What Bluesky does

`modules/Share-with-Bluesky/ShareViewController.swift` in `bluesky-social/social-app`
(read 2026-10-08):

- **No UI.** In `viewDidAppear` it reads the first attachment, writes what it
  must to the App Group `group.app.bsky`, opens the main app and calls
  `completeRequest`.
- **Text and URLs** open `bluesky://intent/compose?text=<encoded>`. A URL
  whose type is an image or a movie goes to the image or video path instead.
- **Images** (`MAX_IMAGES = 10`) are re-encoded as JPEG into the group
  container and passed as `imageUris=<url>|<width>|<height>,…`.
- **Video**: the first item only, copied into the container, `videoUri=…`.
- **Opening the app** walks the responder chain to a `UIApplication` and calls
  `open(url)`. Apple doesn't document this for share extensions; it works and
  ships.
- **Activation rule** (`Info.plist`): text, one web URL, up to 10 images, one
  movie.

The main app handles `intent/compose` in `src/lib/hooks/useIntentHandler.ts`.
The web client answers the same path, `https://bsky.app/intent/compose?text=…`.

**Corrections to `source.md`.** It calls the deferral "LLP 1069.003 §267";
it's the "Not in this RFC" list at `llp/1069.003-share.rfc.md:267`, and that
entry already says where it belongs ("an incoming share as a `navigate`
event", LLP 1038). The payload needs an App Group only for files; text and
URLs fit in the URL the extension opens. And it's not only build work: the
web half is a manifest key and, for files, a service worker.

## 3. What exact2 has today

- **An incoming URL is already a location.** iOS reads
  `connectionOptions.urlContexts` before boot and `scene(_:openURLContexts:)`
  after (`host/apple/Sources/ExactIOS/main.swift:212-218`, `:256-263`); macOS
  takes a non-file URL in `application(_:open:)`
  (`host/apple/Sources/ExactMac/main.swift:449-466`). Both call
  `Session.openURL`, which makes it the launch location before boot and a
  `navigate` after (`host/apple/Sources/ExactKit/Session.swift:1404-1409`).
  Linux takes the first argument, and the agent passes a non-http `--url` as
  `EXACT_LAUNCH_URL` (`scripts/agent.mjs:872-878`).
- **Custom schemes** come from `host.<platform>.urlSchemes`
  (`host/apple/build.mjs:296-299`, `scripts/app.schema.json:339`).
- **Query parameters** are readable: `searchParam`
  (`route/src/location.rs:165`).
- **The clone has the route.** `compose "/compose"` and
  `navigate=followLink` on its navigation root
  (`bluesky-exact2/app.contract:29`, `:503`).
- **The manifest's web keys are an allowlist** that doesn't include
  `share_target` (`host/web/build.mjs:294`, `host/web-js/build.mjs:77`), and
  the schema doesn't know it.
- **No service worker** in either web build.
- **The Apple bundle is assembled by hand.** `Package.swift:62-67` declares
  four executables and no extension. `build.mjs` copies one executable into
  `<Name>.app` and writes its `Info.plist` (`:1320-1330`), copies the
  frameworks, then signs each bundle with one profile and one entitlements
  file (`:1350-1366`). There is no `PlugIns/` directory, no `.appex`, no
  nested signing, and no App Group: `entitlements()` writes only `true`-valued
  grant entitlements (`:311-330`), while
  `com.apple.security.application-groups` is an array.
- **Profiles** are chosen per bundle id, wildcard or exact, and a required
  entitlement narrows the choice to an exact App ID with a named error
  (`host/apple/devices.mjs:188-213`).
- **`host/apple/build.mjs` is 1,499 lines**, one under the cap. Extension
  assembly can't be added to it without moving something out.

Nothing receives a share today on any host.

## 4. What the web does

The [Web Share Target](https://w3c.github.io/web-share-target/) extension to
the [Web App Manifest](https://www.w3.org/TR/appmanifest/):

```json
"share_target": {
  "action": "/compose",
  "method": "GET",
  "params": { "title": "title", "text": "text", "url": "url" }
}
```

- `action` and `params` are required. `method` is `GET` (the default) or
  `POST`; `enctype` is `application/x-www-form-urlencoded` (the default) or
  `multipart/form-data`.
- A `GET` share is a navigation to `action?title=…&text=…&url=…`, the names
  being `params`' values. A member that wasn't shared is left out.
- Files need `POST` and `multipart/form-data`, and
  `params.files: [{ name, accept }]`, where `accept` lists MIME types and
  extensions. The page (in practice its service worker) receives the form.
- Only an installed app is a target. Chromium ships it (Android, ChromeOS,
  and installed apps on desktop); Safari and Firefox don't. Chrome on Android
  often puts a shared link in `text`, not `url`, so a receiver reads both.

Chrome's WebAPK turns `share_target` into an Android `ACTION_SEND` intent
filter. That one declaration maps onto a native share mechanism is the
precedent for doing the same on Apple.

## 5. Design

### D1 — The declaration is the manifest's `share_target`, as the web writes it

Options: (a) the web's key, verbatim; (b) a `host.ios.shareExtension` block in
exact2's own words. **(a).** It sits beside `file_handlers` and
`launch_handler`, which exact2 already takes from the same manifest (LLP 1033
D1, LLP 1069.010 D4); a browser reads it unchanged; and the bake derives every
native artifact from it, as it derives `CFBundleDocumentTypes` from
`file_handlers`.

The bake checks it:

- `action` is a path that matches one of the app's routes (the route crate's
  `match`, as the compiler validates route literals); otherwise the build fails.
- `files` requires `POST` and `multipart/form-data`, as the spec does.
- Each `accept` MIME type maps to a UTI (`DOCUMENT_UTIS`, `scripts/app.mjs`,
  plus `image/*` and `video/*`), or the build fails, as `file_handlers` does.

### D2 — A share is one location: `action` plus the shared members as query parameters

Options: (a) the location, through LLP 1038 D8; (b) a new `share` event on the
navigation root carrying a `Shared { title, text, url, files: list Picked }`;
(c) a reserved source (`exactShare()`) the app reads after launch.

**(a).** It is what the web does for `GET`, so a web share and a native share
reach the app identically. It needs nothing new in Contract, the plan or the
ABI: the app matches the route and reads `searchParam(e, "text")`. Cold, it is
the launch location (D5), so the first frame is the composer. It is what LLP
1069.003 said this would be. (b) adds an event kind and a payload shape the web
doesn't have. (c) adds a fact with a lifetime (when is a share "used up"?) for
nothing (a) can't carry.

The cost of (a) is that `Picked`'s metadata (name, type, size, width, height)
doesn't ride along. The app gets it from the path: `storage.fs.stat` for the
size, the extension for the type, and `compressImage`'s answer for the
dimensions the embed needs.

### D3 — Files arrive at `app:/tmp/shared/`, and their parameters are the paths

The host that claims a share (D6) copies each file into
`app:/tmp/shared/<id>.<ext>` before it delivers the location, with `<id>` from
the launch seed and a counter, as `app:/tmp/picked/` names are (LLP 1069.002
D3–D4). The `files` parameter repeats once per file:
`/compose?text=hi&photos=app:/tmp/shared/s1-0.jpg&photos=app:/tmp/shared/s1-1.jpg`.
The picker's conversion rule applies (LLP 1069.002 D6): a HEIC photo shared to
a target whose `accept` lacks `image/heic` is converted to JPEG on the main
app's side, never in the extension (D8). `app:/tmp/shared/` is emptied at
launch, except the files of a share being delivered by that launch.

**Only a claimed share carries file parameters.** A path is a capability: a
deep link `/compose?photos=app:/data/session.db` would otherwise get the app
to attach and upload its own data. The runner strips every `files` parameter
`share_target` names from any incoming location (`navigate` from a URL entry
point, the launch location) that the host didn't compose from a claimed share,
and journals `share: stripped photos from an incoming location`. A host
composes a share's location through its own runner call (`deliver_share`, a
recorded input under LLP 1069.009 D1), not through `openURL`.

Reading the files needs `fs.read app:/tmp`, the grant the picker flow already
needs. Receiving needs no grant: the person's choice of the app in the share
sheet is the consent, as picking is. LLP 1069.008 D7's reach table gains
"receives shares (`share_target`)", derived from the manifest.

### D4 — Per host

| host | how a share arrives | |
|---|---|---|
| **web** | the browser navigates to `action?…` (`GET`); with files, a fixed service worker takes the `POST`, writes each `File` into the page's `app:/tmp` store as a blob entry at `app:/tmp/shared/…` (the IndexedDB `exact-storage:<id>` that `host/web/storage-fs.js` keeps), and answers `303` to the composed `GET` location | Chromium, installed apps only. The worker is emitted only when `share_target` has `files`; it is a separate artifact, not loaded before first pixel |
| **iOS** | a share extension (D7) opens the main app by URL; the host claims it (D6) | iPhone and iPad |
| **macOS** | the same extension kind in `Contents/PlugIns/`, in every app's Share menu; the app is usually already running, so the share is a `navigate` into the front window (`launch_handler`'s mode) | App extensions on macOS must be sandboxed, though the app isn't |
| **tvOS** | refused: tvOS has no share sheet. The bake ignores `share_target` for `--tvos` and says so | |

### D5 — Cold and warm are LLP 1038's

Cold, the composed location is the launch location (LLP 1038 D5), so the app
boots into the composer. Warm, it is one `navigate`; the app's action chooses
`push` or `open`, as it does for a notification tap. On macOS,
`launch_handler`'s `client_mode` decides which window gets it (LLP 1069.010
D4). Nothing new.

### D6 — Apple: the extension hands over by URL, the app claims from the App Group

The extension is generic host code, the same for every app; the bake
parameterizes it through its `Info.plist`.

1. It reads the `NSExtensionItem`s: `public.url` (http/https only) → url,
   `public.plain-text` → text, the item's `attributedTitle` → title, and each
   attachment conforming to an accepted UTI → a file.
2. **Text and URL only:** it opens
   `<app id>://exact-share?title=…&text=…&url=…` and completes. No App Group.
3. **With files:** it streams each file with
   `loadFileRepresentation(forTypeIdentifier:)` into
   `<group>/shares/<token>/`, writes `share.json` (title, text, url, file
   names and types), opens `<app id>://exact-share?token=<token>`, and
   completes.
4. The main app's URL handler sees the `exact-share` host before
   `ExactDevelopmentLink` and `openURL`. It moves the token's files into
   `app:/tmp/shared/`, converts if D3 says to, composes the location from the
   baked `share_target`, deletes the token's directory, and delivers through
   `deliver_share`.
5. If opening the app fails (the responder-chain call returns false), the
   share stays in the group. The app claims every pending token when it next
   becomes active, oldest first. The person's share is never lost because the
   handoff was.

The scheme is the app's bundle id, which the bake adds to `CFBundleURLTypes`
when `share_target` is declared. Another app can claim the same scheme or call
it. What it can send is a token that names nothing in a group it can't read,
or text and a URL. That is the same exposure as the web's `GET` target, which
any page can link to. File paths can't be injected (D3).

### D7 — The build: an `.appex` beside the app, signed inside out

- **Target.** `Package.swift` gains `ExactShare`, an executable target with
  no dependency on `ExactKit` or the app's Rust archive. Its linker settings:
  `-e _NSExtensionMain` and `-application_extension`. Built per destination,
  like the other products, only when the manifest declares `share_target`.
  About 200 lines of Swift: UIKit and AppKit halves under `#if os(...)`.
- **Bundle.** `<Name>.app/PlugIns/Share.appex` (iOS) or
  `Contents/PlugIns/Share.appex` (macOS), with its own `Info.plist`:
  - `CFBundlePackageType` `XPC!` and bundle id `<app id>.share`;
  - `NSExtensionPointIdentifier` `com.apple.share-services`;
  - an `NSExtensionActivationRule` predicate (a `SUBQUERY` over
    `registeredTypeIdentifiers`) built from `params` and each `accept` UTI,
    with no count cap (the web has none);
  - `ExactShareGroup` and `ExactShareScheme`.
- **Signing.** The extension is signed first, then the app. On a device each
  needs its own profile: two explicit App IDs (`<id>` and `<id>.share`), both
  with the App Groups capability and the group `group.<app id>` registered.
  A team wildcard profile can't carry App Groups, so a files-taking target
  can't use the wildcard `profile()` falls back to today. A text-only target
  can. `entitlements()` learns array-valued entitlements
  (`com.apple.security.application-groups`). macOS adds
  `com.apple.security.app-sandbox` to the extension only. A simulator build
  embeds entitlements in `__TEXT,__entitlements`, as the app's are
  (`build.mjs:1143-1149`).
- **Where the code goes.** `build.mjs` is at 1,499 lines. Extension assembly
  (its plist, the activation predicate, nested signing, its profile) moves to
  a module `host/apple/extension.mjs` beside `assets.mjs` and `devices.mjs`
  (Q3).
- **The receipt** (LLP 1030 D2) records the extension's identity, profile and
  entitlements beside the app's, and LLP 1030 D1 gains its rows ("rows in D1
  when an app has one", LLP 1030 §"Not in this RFC").
- **The external control plane.** Registering the second App ID and the group
  is the developer's, in the portal (LLP 1030). `devices.mjs`' missing-profile
  error names both ids and the group.

### D8 — The extension stays small: no runner, no Contract, no decode

iOS kills a share extension that exceeds its memory limit. Apple doesn't
publish the figure; it is commonly measured at about 120 MB. Embedding the
session (Hermes, the kernel, the presenter) would spend much of that before
the first file. So the extension:

- shows no UI of its own (as Bluesky's doesn't);
- streams files to disk without decoding them (Bluesky decodes each image to
  re-encode it as JPEG; ten 48 MP photos is where that hurts);
- converts nothing (D3: the main app converts).

A composer inside the share sheet, authored in Contract, is out of scope (§9).

### D9 — The agent's view

The shape is **an incoming location**, the row LLP 1069.007 D6 already has for
a notification tap.

- **Text and URL, warm:** `type <root> "/compose?text=hi&url=https://x.test"`
  (LLP 1038 D11), built.
- **Cold:** `--url "/compose?text=hi"`, built (`scripts/agent.mjs:878`).
- **Files:** a share is a URL in the `share:` scheme, which only the driver
  speaks: `type <root> "share:?text=hi&photos=scripts/fixtures/picker/photo.heic"`,
  or `--url "share:?…"` cold. The driver hands it to the host's claim path
  (D6 step 4), so the copy into `app:/tmp/shared/`, the conversion, the
  composed location and the stripping rule are the code a real share runs.
  A host never accepts `share:` from outside the agent.
- **Disclosure:** the journal says `share: received` with the members present
  and the files' types and sizes, never the text. A stripped parameter is
  journaled by name.
- **Lifetime:** none to retire. A share is delivered once; `app:/tmp/shared/`
  is emptied at the next launch.
- **The real surface** (LLP 1069.007 D8): an XCTest drives `ExactShare`'s
  controller with a stub `NSExtensionContext` (one test per kind) and asserts
  the group's `share.json` and the URL it opened. `xcrun simctl openurl` drives
  the main app's claim on a simulator. Sharing from Photos by hand, once per
  release, is the step nothing automates.

## 6. Questions for Charlie

1. **Admit receiving shares, and with it exact2's first extension target?**
   LLP 1030 lists extensions as separate signed targets for "when an app has
   one", and Bluesky's admission (`rules/DEFERRED.md`, 2026-09-27) covers its
   asks "each still held to its own review". *Recommended:* yes, iOS first,
   macOS after; record it under the Bluesky admission.
2. **Open the containing app through the responder chain?** It isn't
   documented for share extensions. Bluesky and many others ship it, and D6's
   pending-share fallback covers its failure. The alternative is a share that
   waits until the person opens the app. *Recommended:* yes, with the fallback.
3. **Move extension assembly into a new `host/apple/extension.mjs`?**
   `build.mjs` has one line left under the cap, and RULES asks for your
   approval before an agent adds a script. *Recommended:* yes. It's a module
   `build.mjs` imports, not a new verb.
4. **Files as `app:/tmp/shared/…` paths in the location**, where the web
   posts the bytes (D3)? *Recommended:* yes. It's the picker's model, and the
   stripping rule makes the path unforgeable.

## 7. What the clone does after

- **Manifest:** `"share_target": { "action": "/compose", "method": "POST",
  "enctype": "multipart/form-data", "params": { "title": "title", "text":
  "text", "url": "url", "files": [{ "name": "photos", "accept": ["image/*",
  "video/*"] }] } }`.
- **The composer**, on entering `/compose`, reads `text`, `url` and `title`
  into the draft (a link in `text` too, D4's Android note) and each `photos`
  path into attachments. It caps them at four images or one video, as the
  composer already does for picked files, and drops the rest with a note.
- **Device:** register `com.ccheever.bluesky.share` and
  `group.com.ccheever.bluesky` in the portal.
- **Verified by:**
  - `agent.mjs ios --url "share:?text=hi&photos=…/a.jpg" tree state "screenshot …"`
    shows the composer with the text and one image;
  - `type bluesky "/compose?photos=app:/data/x"` shows no attachment and the
    journal's `stripped` line;
  - a share from Photos on a simulator by hand;
  - on the web, Chrome on Android with the installed app.

## 8. Effort and complexity

**exact2: L**, in four slices that each ship alone.

1. **Manifest, web `GET`, stripping, agent (S, about a day).** The schema key,
   the two web allowlists, the bake checks, `deliver_share` and the stripping
   rule in the runner, and the `share:` driver form. Text and URL shares then
   work on the web (Chromium) and through the agent everywhere.
2. **iOS extension, text and URL (M, 2–3 days).** The `ExactShare` target, the
   `.appex` assembly and nested signing, the `exact-share` claim, and the
   XCTest. No App Group, so wildcard profiles still work.
3. **Files (M, 2–3 days).** The App Group: array entitlements, the
   two-explicit-profile path and its error, the claim and conversion, and the
   web's service worker. This slice is where the hard part is: provisioning is
   per developer and can't be tested from this machine without a second
   registered App ID.
4. **macOS (M, 1–2 days).** The sandboxed extension in `Contents/PlugIns/`.
   One unmeasured risk: whether an ad-hoc-signed development build's extension
   registers with `pluginkit` at all. If not, development needs an Apple
   Development identity on the Mac.

**Easy:** everything after the location exists. The router, `searchParam`,
LLP 1038's cold and warm paths and the clone's `/compose` route are built.
**Hard:** signing two bundles with two profiles and a group, and the 1,500-line
cap on `build.mjs`.

**Clone: S**, about half a day: the manifest key, reading the parameters into
the draft, and the portal registrations.

## 9. Not in scope

- **A composer inside the share sheet** (an extension that runs a Contract
  session). The memory limit (D8) and a second session's cold start argue
  against it; Bluesky doesn't do it either.
- **macOS Services** (`NSServices`: "New Post with Selection"). It needs no
  extension and no sandbox, and could come later as a cheap Mac-only route to
  the same location.
- **Other extension kinds**: widgets, notification content, action
  extensions, Quick Look (LLP 1035.006 11.10). Each is its own decision; this
  one shows how a second bundle is built, not that the next is admitted.
- **Sending shares with files** (LLP 1069.003 D7), the other direction.
- **An Android package and a Windows MSIX package**, which D4 waits on.
