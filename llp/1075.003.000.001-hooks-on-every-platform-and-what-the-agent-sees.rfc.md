## Summary

Charlie, 2026-10-06: "Can we write up an RFC for adding hooks to every
platform. They might make sense on Mac and Android and Linux and web too. We
also might want to be able to add stuff into your hooks code that gives agents
visibility into what's going on in them."

Access hatches (hooks, until the ruling above; "hatch" in code and below)
already reach further than one platform. iOS has the container hatches and
`element`; macOS has `element` and the window toolbar; the web's JS target has
`element` and the container hatches (§1). Several things are still missing:
hatches above the node (the app and its windows), a frame clock a hatch shares
with the agent, Linux and Windows, an Android shape, and any way for hatch
code to say what it is doing. The Signal clone runs into each gap (§1.3).

- **D1. One model, four scopes.** A hatch attaches to the **app** (`app`:
  lifecycle and appearance), a **window** (`window`, `windowEnded`), a
  **container** (as built) or a **node** (`element`, by `hatch="word"`, as
  built). The names are the same in Swift, Kotlin, Rust and JavaScript. The
  module stays one per session (LLP 1067.000), and so does each handle.
- **D2. Two kinds of host, one handle.** On an *object host* (Apple, the web)
  a handle carries the platform object. On a *painting host* (Linux, Windows)
  it carries the node's box, an overlay the hatch replaces whole, and the input
  that lands there, to observe only. Android's shape stays provisional until
  its renderer is chosen.
- **D3. Hatches share the session's clock.** `context.frames` ticks at the
  instants LLP 1073's frame tasks fire: presented frames on the wall, and the
  virtual 60 Hz display under the agent. `context.after` waits on the session
  clock. Under the agent a seek stops at each hatch instant, so a callback sees
  that instant's state, and `clock +1000` equals ten `clock +100`. Both are
  logical time, for behaviour. Measured time stays LLP 1079's, and under the
  agent `perf frames` stays `virtual`.
- **D4. Into Contract only through what a person could do.** A hatch reads
  only declared `data-*` words. It writes only by acting on authored nodes:
  `click`, `focus`, `blur`, and a new `input(text)`, which replaces a field's
  value through a named editing primitive per host. Topics stay the data path.
  There is no `dispatch`, and no state read or write. Every act is journaled
  without its value. Acts go through a bounded queue, count as in flight, and
  land between batches. `clock settle` waits for them on every host.
- **D5. The app works without its hatches.** No hatch runs before first pixel.
  `EXACT_HATCHES=off` turns hatches off in a development build and leaves the
  module's views and calls alone. With hatches off, the app's Contract state is
  reachable through authored acts. A hatch-only surface that changes no
  Contract state (a dev-menu shortcut, a frame meter) is allowed if it is
  declared.
- **D6. Hatch code can make itself observable.** `context.diagnostics`
  (`log`, `count`, `measure`, `begin`/`end`, `publish`) is bounded and
  development-only, like `perf`. Exact also times every hatch call itself.
  Reads are cumulative and change nothing. Results show in `logs`,
  `state.hatches`, a `perf hatches` form, a person's late frames (on wall time
  only), and Save Trace.
- **D7. The agent is told what it cannot see.** A hatch binds an owned region
  to a platform object it made (`owns(view:…)`). The host observes the
  object's frame and life, and `tree` shows both the declaration and what the
  host observed. 1080.001's opaque interiors name their owner. A hatch may
  also declare **parts** bound to a view. They show in `tree` and join
  `tree --ax`. Whether `tap` may reach them is §10 Q1, and the
  recommendation is real platform input only, never a closure.
- **D8. Safety.** Element teardown stays synchronous inside the batch, and
  container hatches stay where they make construction decisions, both as
  built. Element built and changed run after the batch. Callbacks carry the
  session's incarnation, and stale ones are dropped. A crash leaves a
  breadcrumb, persisted per process. A Kotlin or JavaScript throw is caught,
  and that instance still gets its teardown. Hatches hold no grant the app
  lacks. A delivered plan that needs a hatch the installed binary's module
  lacks, on a platform whose current module handles it, publishes no bundle
  to that stream (1030 D3).
- **D9. Build and scaffold.** `modules/<platform>/` per platform. `app.json`
  may name which platforms handle each word. Windows gets its own adapter.
  The web stays `index.js`. `exact.mjs hatch <word>` writes one stub for each
  target the app builds. Android is named here and built with its host,
  which `DEFERRED.md` still holds.

Charlie ruled the six questions of §10 as recommended (§Rulings).

- `tree` prints `hatch="word"` on the node on every host
  (`scripts/agent-inspect.mjs:138`, `:163`).

  journaled (`ElementHatches.swift:120-123`, `hatches.js:44`).

## 2. The model

### 2.1 Scopes and moments (D1)

The module is one instance per session (LLP 1067.000). Each handle below
belongs to that session.

| Scope | Hatch | Moments | Handle carries |
|---|---|---|---|
| App | `app(_:)`, `appEnded(_:)` | **built** when the module connects; **changed** when a fact below changes, or a root `data-*` word; **ended** at the session's end and before a plan reload (§4.3) | `ExactApp`: the platform application object (process owner only, §2.1.1), the facts, root `data` |
| Window | `window(_:)`, `windowEnded(_:)` | **built** for each surface the session presents into (replayed at connect); **changed** on a size or safe-area change; **ended** before the session leaves the surface, including a move to another window (then `window` for the new one) | `ExactWindow`: the `UIWindowScene` and `UIWindow`, the `NSWindow`, the document, or the painting host's surface; its `frame`; `exclusive` (§2.1.1) |
| Container | `navigation`, `route`, `routeEnded`, `tabs`, `tabContainer`, `toolbar` | as built (1075.003 §3.2, 1075.003.000 §3.7) | as built |
| Node | `element`, `elementEnded` | built, changed (`data-*`), ended, as built | `ExactElement`, as built, plus §2.2 |

**The app's facts, by source.** From `exactPage()` (LLP 1069.000 D2):
`visibilityState` and `onLine`. A change to either is a `changed` moment.
`canShare` is fixed for a session and is not a moment. From the viewport
preferences that `prefer` sets (`runner/src/viewport.rs:11-17`):
`prefersColorScheme`, `prefersContrast`, `prefersReducedMotion` and
`prefersReducedTransparency` (the last two from LLP 1061). A change to any of
them is a moment.

**When each moment runs.** This keeps each scope's order as built, and adds
the new scopes:
- **Element ended runs synchronously, inside the batch or reset that removes
  the node**, before its view goes (`ElementHatches.swift:86-92`, 1075.003.000
  §7.6–7.7). That is how `reusable` works, and how a hatch removes a
  recognizer before its view is reused. `routeEnded` and `windowEnded` run
  the same way, before their controller or surface goes. Acts asked for in an
  ended moment are queued like any other (§2.5).
- **Container hatches keep their construction moments.** `navigation` runs when
  Exact builds the controller, before any child is laid out, so its
  `showsBar` decides the first layout (`NavigationBarIOS.swift:384`).
  `tabContainer` returns the container Exact installs
  (`NavigationTabsIOS.swift:114`). Both run inside the installing batch when
  the module is connected (`PresenterIOS.swift:783`), and at connect for
  objects built earlier. `route` runs before the frame that shows it
  (1075.003 §3.2). Nothing here changes them. They run synchronously, and
  what they ask of elements is queued.
- **Element built and changed run after the batch** (1075.003.000 §3.2), in
  the order the batch built the nodes.
- **App and window built run at connect, and their changed moments run after
  the batch or the fact change that caused them**, never inside a batch.
- **No hatch runs before first pixel.** The module is prepared and connected
  the turn after first draw. So the first frame is the hatch-less app on every
  host (D5). A first frame's colour comes from the manifest: the web page's
  first paint and the iOS launch screen use `background_color` and
  `background_color_dark` (`scripts/app.schema.json:138-146`). `theme_color`
  is the browser's chrome only (`:135`).
- **Under the agent, hatches run.** They are journaled, and their effects are
  governed by §2.4 and §4.6.

#### 2.1.1 Who owns the window

A session rarely knows whether it owns its window. An embedded Exact view
(LLP 1031) shares the window with the embedder's native UI. The macOS sample
host puts two sessions and its own table in one window
(`ExactHostMac/main.swift:38-61`). `ExactMac` runs one session per document
window (`ExactMac/main.swift:132`, `:161`). So there are two grants, and
neither is inferred:
- **`window.exclusive`** is true only when the embedder says so. `ExactMac`
  passes it to each document session for its own window. `ExactIOS` and the
  Linux and Windows entries pass it to their one session. An embedder passes
  it through ExactKit when it creates a session (`hatchWindow: .exclusive`).
  Otherwise it is false.
- **A non-exclusive window** gives its hatch `frame`, the moments and `owns`,
  and nothing it could restyle: `window` is nil on the handle. The
  development check journals a write to the window's chrome from a
  non-exclusive session's hatch.
- **`app.processOwner`** is a separate grant for process-wide state
  (`UIAppearance` proxies, `NSApp.appearance`, the platform application
  object on `ExactApp`). At most one session in a process holds it. `ExactIOS`
  and the Linux and Windows entries give it to their one session. `ExactMac`
  gives it to no document session, because several share the process, so a
  Mac app styles per window. An embedder may give it to one session. A
  session without it gets a nil application object, and the development
  check journals a write to the appearance proxies from its hatch. When the
  owner's session ends, its `appEnded` is the place to undo what it set, and
  the grant is not passed on.

#### 2.1.2 Ownership of what a hatch registers

Everything a hatch registers belongs to a scope and carries that scope's
**incarnation** (the session's plan generation):
- `context.frames`, `context.after` and the module's diagnostics belong to
  the session. They end at the session's end and at a plan reload.
- `element.owns`, `element.parts` and an element's diagnostics belong to the
  node. They end at `elementEnded`. A reused view's (§1.1, `reusable`) are
  cleared by the host before the next node's `element`.
- `window.owns` belongs to the window and ends at `windowEnded`.
- A callback registered under an earlier incarnation is dropped and
  journaled once (`hatch frames: a ticket from before the reload was dropped`).
  A handle cannot outlive its object in a way that reaches the next object.

There is no node-scoped frame ticket. LLP 1073 admits frame tasks at the
root only (`DEFERRED.md`, "one root task form"), and the session scope keeps
hatches inside that line.

### 2.2 Two kinds of host, one handle (D2)

Every node and window handle has:
- `frame`: in window coordinates, the box Exact laid out, read-only, current

- `data`, `hatch`, `id`, `isNew`, `isLive`;
- `click()`, `focus()`, `blur()`, `input(_:)` (§2.5);
- `owns(…)` and `parts` (§3.4, §3.5).

| | Object host: Apple, web | Painting host: Linux, Windows |
|---|---|---|
| `view`, `platform` | the node's view and the kind's object, as built | nil |
| `overlay` | nil: the hatch adds subviews or sublayers to `view` | §2.2.1 |
| Input | the platform's own gestures and events on `view`, under LLP 1057's precedence | `observe(input:)`: the pointer and key events that land in the box, after Exact has handled them, read-only (§2.2.2) |
| `window` | `UIWindow`, `NSWindow`, the document | the host's surface |

- **Linux and Windows get hatches they can use:** the overlay, observed
  input, the app and window hatches, the frame clock and diagnostics. They
  still have no native objects, and the journal says so once, as today.
- **Android stays provisional** (§10 Q4). LLP 1076 includes hybrids, where
  some nodes are Views and the rest are painted, so a host-wide split may not
  fit. If it fits neither column, the per-node answer is: a node that is a
  View gets `view`, and a painted node gets `overlay`. The scope names and
  moments are fixed; the handle's members are revised in the Android host's
  RFC.
- **The web's wasm target stays without hatches.** It builds games, whose
  render hooks are LLP 1046.006.000's, and conformance.

#### 2.2.1 The overlay on a painting host

The overlay is a protocol, not a canvas:
- **A recording replaces the last one whole.** `overlay.draw { list in … }`
  records a fresh Canvas 2D list (LLP 1056's ops, its list format) against
  the box's current size, and publishes it. It has no persistent pixels, no
  carried state, and no incremental append. Nothing blends twice, and
  nothing depends on an earlier recording. `overlay.clear()` publishes the
  empty list.
- **Size.** A recording carries the box size it was recorded at. When the
  box's size changes, the host drops the recording, and the hatch hears
  `changed` with the new `frame` and records again. A stale size is never
  stretched.
- **Clip and order.** Clipped to the node's border box, painted after the
  node's own paint and its descendants, and below the next sibling. The
  overlay is the node's top-most content, and it never paints outside the
  node.
- **Resources.** Images in a recording are named by the app's asset URLs and
  resolved through the host's image cache. A recording owns nothing that
  outlives it.
- **Threads and handoff.** On Linux and Windows the hatch runs on the host
  loop's thread, between turns. A publish swaps a pointer that the painter
  reads at the start of its next paint. One recording is pending at a time,
  and the latest wins. The paint walk never calls hatch code, and a hatch never
  sees a half-painted frame.
- **Repaint.** A publish (or `clear`) marks the node's box dirty and asks the
  host for a frame, which wakes an idle presenter as a Contract change would.
  An image in a recording that is still loading is drawn as nothing. When it
  resolves, the host dirties the box and asks for a frame again. A hatch's
  visual update never waits for unrelated activity.
- **Bounds.** A recording is at most 4,096 ops and 256 KB. A larger one is
  refused by name, and the last good one stays.

#### 2.2.2 Input on a painting host: observe only

Exact is the hit-tester on Linux and Windows. A hatch that could claim an
event would make Exact's dispatch a negotiation, which is the gesture arena
`DEFERRED.md` refuses. So a hatch only observes, after Exact's dispatch, with
`handled` saying whether an authored handler or a scroll took the event:
- **Pointer events** go to the observers whose boxes contain the point,
  innermost first along the hit chain Exact computed. A pointer that went
  down in a box stays with that box's observers until up or cancel, even
  after it leaves the box (capture, as the web's pointer capture).
- **Key events** go to the observers on the focused node and its ancestors,
  innermost first. A node with no focus inside it hears no keys.
- **Order** among observers on one node is registration order.

To act, a hatch uses §2.5's acts. Claiming input on a painting host is out of
scope here, and would need its own LLP and a ruling on the arena.

### 2.4 The frame clock: logical time (D3)

```swift
// Swift
let ticket = context.frames { frame in … }     // frame.now: session clock, ms; frame.seq: the commit it follows
ticket.stop()
context.after(800) { … }                        // the session clock
```

```js
// the page module
const stop = exact.frames(frame => { … });
exact.after(800, () => { … });
```

`frames` and `after` are logical time. They are for behaviour that must keep
step with the app, such as a hatch-drawn indicator that follows an animation.
They are not for measuring the display, which §3 covers.

- **The same instants as LLP 1073's frame tasks.** While a ticket is live the
  host registers a frame interest with the runner, as a root frame task does.
  The source then runs (1073 D2), and a ticket fires at each frame after that
  frame's tasks and timers, in registration order, with `frame.now` the
  frame's time.
- **On the wall** that is each presented frame.
- **Under the agent** it is 1073 D3's virtual display: `clock +1000` passes
  sixty instants on every host, at `base + k·1000/60`, bit for bit.
- **A seek stops at every hatch instant.** The host gives the runner its next
  hatch instant (the earliest live ticket's next frame or due `after`). The
  runner's seek advances to the earlier of that instant and the target,
  firing timers and frame tasks due at or before it, in 1073 D3's order. The
  host then, at that instant:
  1. applies that instant's commits;
  2. calls each due tick in registration order, then each due `after` in
     due order (ties by registration), with `context.now()` and `frame.now`
     at the instant, and the state as of that instant;
  3. drains the acts those callbacks queued, synchronously, at that instant:
     snapshot after snapshot (§2.5), each act a commit at the instant, until
     the FIFO is empty. Acts queued by moments those commits cause (a
     `changed` that clicks) are drained in the same loop. An `after(0)`
     registered here fires at the same instant, after the current round of
     callbacks, and its acts drain in the same loop;
  4. resumes the seek.

  This runs inside `clock +ms` itself on every host, on both of its return
  paths (settling and not: `Agent.swift:531-538`,
  `host/linux/src/agent.rs:840-857`). The next-turn, microtask and
  `MessageChannel` drains of §2.5 are the wall path only. So a callback sees
  the state of its own instant. An `after` registered inside a callback for a
  later time fires later in the same seek, and one stopped inside a callback
  never fires.
- **Limits, per command.** Ticks and `after` callbacks are not commits. They
  count against a cap of 4,096 per agent command, across all of its stops,
  and drained acts count against a cap of 4,096 per command too. Past either
  the command stops with `error: "HatchFireLimit"` or `"HatchActLimit"`, as it
  stops at `TimerFireLimit`. Acts are commits, but they count only against
  their own cap, so `TimerFireLimit` keeps 1073's meaning. A host's frame
  interest is not a plan `every(frame)` task. It commits nothing and adds
  nothing to `TimerFireLimit`.
- **Partitioning.** `clock +1000` and ten `clock +100` give the same
  callbacks, states, commits and journal when neither hits a cap. A command
  that hits a cap says so, and the equality is not claimed for it.
- **`frame.seq`** is the commit sequence the instant's state ends at, after
  step 1 and before step 3.
- **On the wall** the same order runs at each presented frame and each due
  `after`, without the seek.
- **`perf frames` stays as LLP 1079 built it:** wall-clock observations, and
  `{"virtual": true}` under the agent (1079 D4). A ticket does not keep the
  frame sampler running (1079 D3).
- **`context.now()` is unchanged**: the session clock
  (`ExactNativeModule.swift:98`).

A hatch's own `CADisplayLink`, `requestAnimationFrame` loop or wall timer is
the wall. The agent cannot step it, and §4.6 says what that costs.

### 2.5 Talking to the Contract app (D4)

**Into a hatch:**
- **`data-*` words**, declared in `app.json` `data`, on a hatched node, a
  route or (new) the root. A root word reaches `app` as `app.data`, and its
  change is a `changed` moment on `app`. This is how a hatch reads state: the
  Contract projects what the hatch should know into a word.
- **Facts** the host already tracks (§2.1).
- Nothing else. No hatch reads the runner's state, a resource, or another
  node's props.

**Out of a hatch:**
- **Acts on authored nodes**, as a person would: `click()`, `focus()`,
  `blur()`, and new, `input(text)`. `input` **replaces the whole value** of
  an authored editable field, as LLP 1012's `type` does, without moving
  focus. So a native search controller can feed an authored field while it
  keeps the keyboard. It applies to single-line and multi-line text fields
  (`input` of a text-like type, `textarea`). Each host names its primitive:
  - **iOS:** `TextInputLimit.prefix` cuts the text to the field's limits.
    The host assigns it as `writeValue` does (`FieldEditingIOS.swift:11-18`),
    then reports it with `presenter.typed`, the call `fieldChanged` makes
    for a keystroke (`:36`), so Contract hears an input. Character acceptance
    stays `TextInputLimit`'s (`NodeViewIOS.swift:397-403`). `inputmode` sets
    only the keyboard (`:1101-1108`) and filters nothing.
    `becomeFirstResponder` is not called.
  - **macOS:** the same limit, then the field's `stringValue` when it is not
    being edited. When it is, the field editor's `replaceCharacters(in:with:)`
    over the whole range. Then the same `typed` report. Focus does not move:
    unlike the agent's `type` (`AgentMac.swift:835`), it never makes the
    field first responder to get an editor.
  - **The web:** for `input` types that support it (`text`, `search`, `url`,
    `tel`, `password`) and `textarea`, `el.setRangeText(text, 0,
    el.value.length, "end")`. For `email` and `number`, where the HTML
    standard has `setRangeText` throw, the host assigns `el.value`. Either way
    it then dispatches `InputEvent("input", { inputType:
    "insertReplacementText" })`. The JS host truncates to `maxlength` first.
    That is new work, since `host/web-js` has no `maxlength` handling today.
  - **Linux and Windows:** a new whole-value replace by node id in the
    presenter's field model, applying the same limits. The focused-field key
    path (`host/linux/src/presenter/field.rs:343-367`) edits a selection, so
    it is not used.
  - **Refused by name:** a field that is composing (iOS `markedTextRange !=
    nil`, an active IME elsewhere); a disabled or `readonly` field; a
    contenteditable editor, such as the Markdown editor's `div`
    (`host/web/markup-editor.js:101`); text longer than 64 KB; and any node
    that is not an editable field.

  The agent's `type` keeps its own delivery (CDP `Input.insertText` on the
  web, `scripts/agent.mjs:491`; focus, select all and insert on Apple,
  `AgentIOS.swift:847-851`). Both apply the field's limits and report an
  input, but only `type` moves focus, and on the web only `type` goes
  through the browser's editing host.
- **Topics**, unchanged: `context.changed(topic)` re-asks every
  `native.watch(topic)`, and the source asks back with `native.call` or
  `native.later` (LLP 1016.002, 1067.000).
- **No `dispatch(action)`, no state write, no event that bypasses an authored
  handler.** That is 1075.003 §3.4's rule, kept.

**Every act is queued, counted and journaled:**
- **One bounded FIFO per session**, owned by the host: at most 256 acts and
  1 MB of queued `input` text. Past either, an act is refused by name and
  counted (`state.hatches.refused`).
  Apple's acts move from `DispatchQueue.main.async` (`ElementHatches.swift:225`)
  into it. Linux and Windows have the same FIFO. The web keeps a JavaScript
  array.
- **A drain runs a snapshot.** It runs the acts that were queued when it
  started, at most 64. Acts queued during the drain (a `changed` moment that
  clicks again) go to a later snapshot. **On the wall** the later snapshot is
  a later turn: the main queue's next turn on Apple, the loop's next turn on
  Linux and Windows, and on the web a microtask for the first drain and a
  `MessageChannel` task after that, so a hatch that keeps queueing cannot
  starve the page. **Inside an agent command** the snapshots run back to back
  at the same instant, under the per-command act cap (§2.4).
- **In flight.** The FIFO's length, plus due `after` callbacks, plus (on the
  web) the page module's load, is the host's `hatchInFlight` count. An act
  counts from the moment it is queued until it has run. Today the web drops
  its in-flight count on a `setTimeout` after the module loads
  (`hatches.js:74`); that changes to the act's own completion.
- **`clock settle`** waits for `hatchInFlight` to reach zero on every host,
  bounded like requests: 16 drains, then `settled: false, reason: "hatches"` (a
  new reason beside `"requests"`, `Agent.swift:542`). Each host drains in its
  own settle loop rather than waiting on a queue it is blocking:
  - **Apple:** the settle loop runs on the main thread
    (`Agent.swift:526-556`), so it drains in its pump step (`settlePump`).
  - **Linux and Windows:** `clock_within` (`host/linux/src/agent.rs:788-866`)
    blocks the loop. It drains the FIFO before it decides it has settled.
  - **The web:** the agent's settle waits on `hatchInFlight` beside its
    requests.
- **The journal** gets `hatch element search #q: input (5 chars, delivery:
  hatch)`. It records the length, never the text, and nothing at all for a
  `type=password` field beyond `input (protected)` (1080.002's protected
  values).
- **An act from an ended handle** does nothing and is journaled, as built.

### 2.6 The app works without hatches, and parity (D5)

- **The first frame is hatch-less** on every host (§2.1).
- **`EXACT_HATCHES=off`** (development builds only) connects no hatches. The
  production strip, which today drops `EXACT_AGENT` and `EXACT_AGENT_*`
  (`Session.swift:49-52`), gains the name `EXACT_HATCHES`, and the Linux,
  Windows and web strips gain it too. The module still loads, and its
  views and calls work. It is a different state from **a module that failed
  to load**. There the views are unavailable boxes and the calls fail
  (LLP 1024 D2, `state.native`), and the author's obligations are 1024's,
  unchanged. This RFC promises nothing about an app whose module is
  missing.
- **What "works" means.** With hatches off, every Contract state the hatched app
  reaches is reached by authored acts (`tap`, `type`), as the smoke drives
  them. The test is the fixture's (§9), not a promise about every app.
- **Looks may differ, behaviour may not.** A hatch may change how a platform
  looks and feels. Anything that changes Contract state goes through an
  authored node (§2.5).
- **A hatch-only surface is allowed when it changes no Contract state and is
  declared.** A dev-menu shortcut, a frame meter or a haptic is declared with
  `owns` (§3.4), and needs no authored stand-in. `state.hatches` lists these
  surfaces, so the agent knows they exist.
- **Parity is per platform** (Charlie, 2026-09-27: allow what a platform
  supports). A hatch on one platform needs no twin on the others. `app.json`
  says which platforms handle each word (§5). The journal and `state.hatches`
  name the current host's words, and a host makes no claim about another
  platform's module.

### 2.7 Refused

- **Native property names in Contract** (`DEFERRED.md`; 1035.006 12.08).
- **A hatch that runs before first pixel**, or anywhere on the boot path
  (`RULES.md`).
- **A hatch that writes Contract state**, dispatches an action, or reads the
  runner's state.
- **An element built or changed moment inside a batch** (container
  construction moments stay as built, §2.1), and any hatch inside the
  painter's walk.
- **Claiming input on a painting host** (the gesture arena).
- **A node-scoped frame ticket** (LLP 1073's root-only rule).
- **A tap that runs hatch code by name** (§3.5; LLP 1012).
- **JavaScript above the data seam on native** (`DEFERRED.md` §Authoring
  models). Native hatches are Swift, Kotlin or Rust. 1075.003 §3.10's
  TypeScript experiment is unchanged and adopts nothing.
- **A hatch on the wasm target**, and a per-frame journal line.
- **An eleventh agent operation.** Everything in §3 is a form of `tree`,
  `state`, `logs` or `perf`, and §3.5's driving, if ruled, is a form of
  `tap`.
- **Platform-suffixed route overrides.** A hatch configures what Exact built.
  It never replaces a route's authored tree.

## 3. What the agent sees (D6, D7)

### 3.1 What Exact measures by itself

All of this is collected only while measuring is on: development trust,
under LLP 1079 D1's switch. In production it is not collected.
- **Every hatch call is timed** on the main (or loop) thread: calls, total
  ms and the worst call. For nodes the key is **plan site and moment**, kept
  across node retirement as `perf`'s site totals are (1079 D1). `perf hatches`
  sums sites into words, and `perf <target>` reads the sites under its
  target. For the other scopes the key is the hatch. Times are exclusive: a
  hatch call nested inside another (a `changed` caused by an act drained in
  settle) is charged to itself, not to its outer call. The counters are
  cumulative, as `perf`'s are.
- **A person's late frames name the hatches that ran in them.** On wall time
  (a development session, Save Trace, `perf frames live`), a late frame's
  record gains `hatches: [{ hatch: "element avatar", calls: 12, ms: 9.8 }]`: the
  hatch calls that overlapped its window, each charged its overlap. The window
  is the sample's own observation interval on the sampler's clock: `(t −
  interval, t]`, where `t` is the callback timestamp and `interval` the gap
  to the previous callback (`FrameSampler.swift:163-178`; on the web, the rAF
  callback gap, `host/web/frames.js:37`). A call that began before the
  frame's target and crossed it, which is what an overrun is
  (`FrameSampler.swift:145`), overlaps the window and is counted. The host
  keeps the last 1,024 hatch calls (start, end, key) per session for the join,
  and a record says `coverage: partial` when its window reaches past the
  oldest. The join is by window with stated coverage, as frame records join commits by `seq` (1079 D3). It
  is not a causal trace. Under the agent there are no late frames
  (`virtual`), and hatch time is read from `perf hatches` instead.
- **Frame tickets** count their live tickets and ms per tick.

### 3.2 What hatch code adds: `context.diagnostics`

```swift
let d = context.diagnostics                       // element.diagnostics is scoped to its word
d.log("swipe began at \(x)")                      // a journal line
d.count("swipes")                                 // a counter, +1
d.count("frames.over20", by: n)
let span = d.begin("swipe")  …  span.end()        // a span on the session clock
d.measure("swipe.worst", ms: worst)               // one sample of a named, measured timing
d.publish("lastswipe", ["worst": worst, "over20": n])   // a snapshot, JSON
```

```js
exact.diagnostics.count("swipes");   // e.diagnostics for a node
```

```rust
ctx.diagnostics().count("swipes", 1);   // Linux, Windows
```

- **Development only, like `perf`** (LLP 1079 D1). In production every call
  is an early return on one flag, with no storage and no platform log. The
  crash breadcrumb (§4.4) is separate and always on. §10 Q5 asks whether
  Charlie wants more than that in production.
- **Names** follow `data-*`'s rule: lowercase letters, digits and `-`, with
  `.` to group, at most 64 bytes. A bad name increments one `rejected`
  counter per module. The first 8 distinct bad names are journaled, and the
  rest are only counted.
- **Bounds, per module, all fixed at connect:**

| Kind | Bound | Over the bound |
|---|---|---|
| Counter | 64 names, `u64` cumulative | `rejected` +1 |
| Timing (`measure`, spans) | 64 names; per name a cumulative count, sum and max, plus a ring of the last 256 samples | the ring overwrites, and its `dropped` counts what it lost |
| Open spans | 32 at once | `begin` returns an inert span, `rejected` +1 |
| A span still open when its scope ends | closed as `abandoned` and counted, not timed | — |
| Snapshot (`publish`) | 16 names, 4 KB of JSON each, the latest kept | refused, `rejected` +1 |
| `log` | 256 bytes a line; 20 lines per second of **session clock** per bucket, then one `… N more`. A bucket is a node word (shared by every node with it) or a non-node hatch | truncated with `…`; counted |
| Cross-thread records (`log`, `count`, `measure`, spans) | a 1,024-entry ring of fixed 320-byte slots (a name and a 256-byte payload), 320 KB per module, drained by the owning thread each turn | overwritten, `dropped` +1; a `log` line past 256 bytes is cut with `…` (a log line is text, so a cut is safe) |
| `publish` from another thread | the whole snapshot is copied into its own 4 KB slot, swapped in on the owning thread; never through the ring | a snapshot that does not fit is refused whole, `rejected` +1, never truncated |
| Regions (`owns`, §3.4) | 32 per scope instance, 1,024 per session; a sentence of at most 120 bytes; `appearance` regions keyed, at most 16 per session, a second with the same key replacing the first | refused by name, `rejected` +1 |
| Parts (§3.5) | 32 per node; `id` at most 64 bytes, unique within its node; `label` at most 120 bytes | the registration is refused whole, by name |
| The undeclared-recognizer walk (§3.4) | 8 levels below a hatched view or window, 2,000 views a check | stops, and journals `truncated` once |
| `state.hatches`, `perf hatches` replies | 64 KB each | the longest lists are cut first, with `truncated` |
| `saveTrace()` | at most once a second of wall time | coalesced into the pending one |

- **Repeatable under the agent.** Counters, spans on the session clock and
  `log`'s rate limit all use the session clock, so two identical drives give
  identical `logs`, counts and spans. `measure` samples are the hatch's own
  measurements, which may be wall time, and are marked `measured`. Whether
  `saveTrace()` wrote a file depends on wall time, so it is not repeatable
  (§4.6).
- **Namespaced.** Every line and name is prefixed with its scope (`hatch
  element avatar: …`, `hatch module: …`).
- **Cost.** A `count` is a bounds check and an add into a fixed table. §9 sets
  a measured threshold.

| Read | What it gains |

**Reads change nothing** (1079 D2). Every count is cumulative from the
incarnation's start. A difference is two reads that the driver subtracts,
and it refuses to subtract across a changed incarnation or plan digest, as
`perf <target> during` already does. A reader, Save Trace, or a second agent
leaves the next read unchanged. A reload starts a new incarnation and resets
the counters, and the reply says so.

### 3.4 Hatch-owned regions

A region is a declaration bound to an object the hatch made. The host then
observes that object:

```swift
let title = TitleView(…); route.controller.navigationItem.titleView = title
route.owns(view: title, "title view: avatar, name, verified seal")
element.owns(recognizer: longPress, "long press: reaction picker")
window.owns(recognizer: threeFinger, "three fingers held 0.8 s: dev menu", surface: true)
app.owns(appearance: "tab bar tint: label")
```

- **Bindings are weak.** A region names a view or layer, a gesture
  recognizer, or (for `appearance`) nothing. It ends when its object
  deallocates, leaves the hierarchy, or its scope ends. `surface: true` marks
  a hatch-only surface (§2.6).
- **`tree` shows both halves**, distinguished: `owns: [{ by: "route
  conversation", kind: "view", what: "…", observed: { live: true, frame,
  class: "TitleView" } }]`. `what` is the hatch's sentence. `observed` is
  what the host saw, with `frame` converted to window coordinates by the
  same conversion 1012 §1's geometry uses (scroll and presentation transforms
  included), at read time. A region whose object is gone is retired by
  the host, not by a read: it stays as a tombstone, `observed: { live:
  false, ended: <session time> }`, for 5 s of session clock, with at most 16
  tombstones per session (the oldest goes first). Every reader in that time
  sees the same tombstone, and Save Trace changes nothing.
- **On a painting host**, `owns(overlay:)` binds the node's overlay, and
  `observed.frame` is the node's box.
- **LLP 1080.001** attributes an `opaque` interior by object identity, not by
  sentence. A non-node subview under a region's bound view counts as that
  region's:
  `opaque: 85 (hatch "title view" 12, module 40, platform 33)`. When bound
  views nest, the innermost bound ancestor of a subview wins. An unbound
  subview stays plainly `opaque`. This amends 1080.001 D3, which counts each
  such subview as `opaque` without saying whose it is.
- **Undeclared gestures, as new work.** The development check walks a hatched
  node's view and an exclusive window, and counts recognizers that are neither
  Exact's nor bound by a region. It journals once: `hatch element avatar added
  a UILongPressGestureRecognizer it did not declare`. Today's check compares
  only the scroll, field and text properties Exact recorded
  (`ElementHatches.swift:191-204`). The walk is added in stage 3.
- **Screenshots are unchanged.** `observed.frame` tells the agent which
  pixels belong to which hatch.

### 3.5 Hatch parts: what a hatch drew, named

A part is a control a hatch drew, bound to a view. Parts exist only on object
hosts. A painting host has no view to bind, so it has no parts.

```swift
element.parts = [ExactPart(id: "seal", view: sealButton, role: "button", label: "Verified")]
```

- **`tree`** lists parts under their node, as `part`, with `id` (unique
  within the node), `role`, `label` and the observed, converted `frame`, at
  most 32 per node (§3.2). They are not plan nodes, and `layout` refuses them
  by name.
- **`tree --ax`** joins a part through its bound view's own accessibility
  element, which is ownership, not a string match (1080.002). A part whose
  view exposes no element is reported `ax: "not exposed"` in the join's
  coverage. It is not one of 1080.002's four findings, which judge only
  exposed elements, and this RFC adds no finding.
- **There is no closure.** A part does nothing when the agent names it. What
  the bound control does when touched is the hatch's own code, which must act
  on an authored node (§2.5).

**Driving a part** is §10 Q1. Recommended: `tap <node>/<part>` only as real
platform input, with no activation fallback. On the wire it is `{"op":
"tap", "id": V, "part": "seal"}`, where `id` is the node's target as 1012
addresses it (a test id or a view id). The CLI form is `tap dot/seal`.
- **The aim.** The host resolves the part to its bound view, then runs the
  same side-effect-free aim 1080.000 runs for a node: the session and
  incarnation match, the view is live and in the window, the converted
  frame's centre hit-tests to the bound view or a descendant (not covered),
  and nothing is mid-transition. A failed aim is refused by name (`part seal:
  covered by UIDimmingView`). A stale part is refused.
- **A binding token.** The aim records a token: the part's id, the bound
  view's object identity, and the incarnation. Delivery is checked against
  it. A part replaced, or a view swapped, between aim and delivery fails the
  check, so two parts of one class under one node cannot be confused.
- **Delivery.** iOS uses 1080.000's real-touch carrier (`delivery:
  platform`). macOS and the web dispatch a synthesized pointer event at the
  aimed point through the platform's own hit-testing, as 1012 §1's `tap`
  does there. Where no real carrier exists (a phone without 1080.000's
  runner, a painting host), the reply is `unsupported`. It never falls back.
- **Evidence.** The reply carries what the platform reported, checked
  against the token. On iOS, 1080.000's landing record (`TouchLog.landing`,
  `IOS/TouchIOS.swift:54`) gains the hit view's object identity, and the host
  answers `landed: "part"` only when that view is the bound view or its
  descendant. Otherwise the answer is `landed: "elsewhere"`, with the class and
  node it reached. On macOS and the web, the host's own hit test at dispatch
  gives the same identity check. Whether a recognizer began is reported only
  for recognizers bound by a region (§3.4). The host observes their state as
  new instrumentation, because `TouchLog` does not observe recognizer
  outcomes (`TouchIOS.swift:5`). Other recognizers are reported as not
  observed.
- **No action by name.** Every path is a touch at a place, which 1012
  already allows. So this does not amend 1012's sentence. 1075.003 §3.4's
  "named action" placeholder is closed by refusal.

### 3.6 With LLP 1079 and LLP 1080

- **1079.** `perf hatches` is a form of `perf`, not an operation, and its reads
  change nothing. Save Trace gains a section, not a format. Times stay
  observations with their proxy named (1079 D6). `perf frames` keeps
  `virtual` under the agent. Collection stays development-only.
- **1080.000.** Real touches reach hatch gestures and, if Q1 rules it,
  parts, through the existing aim.
- **1080.001.** Regions attribute `opaque` by identity. A hatch's own subviews
  stay unjudged, because Exact does not own that subview list.
- **1080.002.** Parts join `tree --ax` by ownership. Hatch UI the platform
  exposes is already read.
- **1080's constraints hold.** No new operation. Every list is bounded and
  says `truncated`. A painting host has no parts (§3.5), so `tap` with a
  `part` there is `unsupported`.

## 4. Safety (D8)

### 4.1 Threads

- **Every hatch runs on the main thread** on Apple (and the UI thread on
  Android). On the web it runs on the page's thread, and on Linux and Windows
  on the host loop's thread, between turns.
- **Ended runs inside the batch or reset that removes the object**,
  synchronously (§2.1). **Container construction moments run inside the
  installing batch**, as built: `navigation`'s `showsBar` decides the first
  layout (`NavigationBarIOS.swift:384-387`), and `tabContainer`'s return value
  is what the batch installs (`NavigationTabsIOS.swift:114`, `:148-153`;
  `PresenterIOS.swift:783`). **Element built and changed run after the
  batch.** No hatch applies a batch: acts are queued (§2.5).
- **Never on the owner thread** (LLP 1072). A hatch cannot reach a runtime,
  so it cannot reenter the owner.
- **The painter never calls hatch code** (§2.2.1).
- **Two things may be called from any thread:** `context.changed(topic)`,
  as today (`ExactNativeModule.swift:100`), and `diagnostics`, through the
  cross-thread ring and the snapshot slots (§3.2). A handle's other members are
  main-thread only. The guard that returns silently today
  (`NativeHatches.swift:61`) becomes, in development builds, a journal line
  naming the member and the thread, and still returns.

### 4.2 Lifetime

- **A handle lives while its object does.** After its ended moment, `view`,
  `platform` and `overlay` are nil, and acts do nothing and are journaled (as
  built for nodes, 1075.003.000 §7.7).
- **Registrations carry their scope's incarnation** (§2.1.2). A ticket, an
  `after`, a region or a part from an earlier incarnation is dropped, and the
  drop is journaled once.
- **A reused view** (iOS `reusable`) has its regions and parts cleared by the
  host before the next node's `element`. Its next hatch decides again.

### 4.3 Reload and delivered updates

**A plan reload, per host:**
- **Apple, Linux, Windows:** every hatched node, route and container ends and
  is built again (LLP 1024 D6). The platform window survives the reload, but
  its hatches do not carry across it: `appEnded` and `windowEnded` run first,
  inside the reset, so a hatch removes the recognizers and views it added to
  a surviving window. Then `app` and `window` run again as **built**, with
  new handles. Only then are the old incarnation's registrations dropped. A
  window recognizer is never installed twice, and none is left behind
  undeclared.
- **The web:** the dev loop reloads the page. Everything is built again,
  `app` included.

**A hatch edit** is a native change: a rebuild and restart on Apple, Linux and
Windows, and a page reload on the web (1024 D6, LLP 1030).

**A delivered plan that marks a word the installed module does not handle**
is a real gap today:
- A word is not a plan requirement (`bake/src/receipt.rs:450-480`), and the
  hatch words are not in the compatibility inputs (`bake/src/compat.rs:330-332`,
  which is `null` for an empty roster even when an app has hatches).
- On Apple the host builds `ExactHatchKey(word)` from the plan's string
  (`ExactNativeModule.swift:892`; `data-keys.mjs:15` accepts any string), so
  the module is called with a key its code never compiled.

The proposal works per platform, because a word need not be handled
everywhere (§2.6):
- **Who handles what is declared statically.** `app.json` `hatches` may give
  a word its platforms, `"hatches": { "avatar": ["ios", "macos", "web"] }`. A
  plain list still means every platform the app builds. The bake reads it
  directly, so nothing is scanned or run, and cross-compiling changes nothing
  (§5).
- **The plan's requirement, per target platform P:** the words the plan
  marks that `app.json` says P handles. A word P does not handle is no
  requirement on P. That is an intended fallback, and its nodes are shown
  and never called there.
- **The cohort's capability:** the words its binary's module was built to
  handle on P, written into the build receipt from the same declaration. An
  empty view roster still records them. A cohort built before this change
  has no capability, which reads as "handles nothing".
- **`classifyArtifacts` (`scripts/app.mjs:1328-1345`)** gets an explicit
  subset branch beside `surfaceCalls` and `gpuSurfaces`: each required word
  must be in the cohort's set. Without that branch the new key would fall
  through to the catch-all equality (`app.mjs:1351`). A missing word adds
  `app.plan: hatches.avatar (handled by this platform's module, not by the
  installed one)` to `missing` (the classifier prefixes the artifact's name,
  `app.mjs:1338`). So no bundle is published to that stream, and
  the snapshot is whole or absent (1030 D3, `classifyArtifacts`'s `bundle`).
  Whether a new binary is needed stays the classifier's separate answer.
- **The compatibility inputs gain the declaration.** The id is a digest of
  every input (`bake/src/compat.rs:307`), so adding this input moves it once
  when this lands, and afterwards a change to a platform's handled words
  moves it, as any other input's change does. The first plan with a
  non-empty requirement needs one new binary per stream.
- **At run time the plan decides, and the module can only narrow.** The bake
  writes each platform's handled words into the plan itself, as a row the
  plan's signature covers. A host calls a word only if the plan's row for
  its platform has it **and** its installed module was built to handle it.
  So removing iOS from `avatar` reaches an old iOS cohort with the next
  bundle, and stops the calls there, even though the old module still
  handles the word. Adding a word to a platform is the classifier's case
  above. Either kind of skipped word is journaled once and listed in
  `state.hatches.unhandled`, with the reason (`plan` or `module`). This also
  covers a development build whose module lags its plan.
- **A change to a hatch's body with the same words moves nothing here.** It is
  a binary change because the module changed, which the binary's digest
  already covers.

### 4.4 Crashes in hatch code

**Swift and Objective-C cannot be caught, and neither can Rust.** A Swift
trap or an Objective-C exception ends the process. Rust panics abort in every
shipped profile: `[profile.release]` sets `panic = "abort"`
(`Cargo.toml:50`), `host-dev` inherits it (`Cargo.toml:110-111`), and
`logic-dev`/`gpu-dev` set it (`Cargo.toml:129`, `:137`). No `catch_unwind`
is claimed. For all three, the host leaves a breadcrumb:
- **Persisted per process, where the OS keeps it.** The file is
  `hatch-breadcrumb-<pid>` in the app's Application Support directory under
  `exact/` (not the temporary directory, which iOS may purge between a crash
  and the next launch, and which sessions share outside the agent,
  `NativeModule.swift:468-470`).
  The process creates it once and `mmap`s it shared, so a write reaches the
  page cache with no syscall, and the kernel keeps the page if the process
  dies. Under the agent it goes in the agent's scratch tree.
- **Slots per session.** The file has 8 session slots of 512 bytes each.
  A session takes a free slot at start, and clears and frees only its own
  slot at its end, so ending one session never touches another's record.
  A ninth concurrent session runs without a breadcrumb, and the journal says
  so once.
- **Written around each call.** Each slot is a stack of up to 8 records
  (hatch scope and word, moment, session id, incarnation, a call sequence),
  with a depth word and a checksum per record. A push writes the record, then
  publishes the new depth with a release store. A pop lowers the depth. A
  nested call past 8 only increments an overflow count, and the line says
  `(+N nested)`. A reader trusts a record only below the published depth and
  only with a valid checksum, so termination in the middle of a push leaves
  the last whole record.
- **Read at the next launch.** The host reads every `hatch-breadcrumb-*` whose
  process is gone, then deletes it. A clean process exit deletes its own
  file. A non-empty stack means that run ended (crash, kill or jetsam) while
  those calls were open. The journal's first line says `the last run ended
  while inside hatch element avatar (built, call 4127); if it repeats, launch
  with EXACT_HATCHES=off`, and `state.native.lastEnd` carries it. The wording
  is "ended while inside", not "crashed in": another thread may have been the
  cause.
- **Cost.** About 40 bytes stored into a mapped page, plus one release store,
  per push and per pop, with no syscall. §9 measures it with the rest.
- **The same on Linux and Windows**, in the XDG data directory and
  `%LOCALAPPDATA%` respectively.

**Kotlin and JavaScript can be caught.** Android's Kotlin hatches (when they
exist) are called inside `try`/`catch`, and the web already catches a throw
and journals it (`hatches.js`, `call`). After a throw:
- the throw is journaled with the hatch's name;
- **that instance's** built and changed moments are not called again this
  session. Other nodes with the same word, and other rows, keep running;
- **its ended moment still is**, so a hatch that installed a recognizer or
  a reusable-view addition before throwing still gets to remove it. A throw
  in an ended moment is journaled, and teardown of the next object goes on.

**No automatic disable across launches.** A crash loop in a development build
is broken with `EXACT_HATCHES=off`, which the breadcrumb line names.

### 4.5 Privacy and capabilities

- **Hatches hold no grant the app lacks.** The context gives a hatch no token,
  keychain item, resource, fetch, or other session's data. Its directories
  are the module's own (`ExactModuleContext.data`, `cache`, `temporary`), and
  a scratch tree under the agent.
- **Native hatches are declared, not enforced** (LLP 1069.008 D3). In-process
  native code can call any platform API, and it bypasses the first-party
  runtime check. What enforces anything then depends on the platform:
  - **Apple (and Android):** the OS, through its prompts and the usage keys
    and entitlements the app's `device.*` grants put in the binary. A hatch
    that uses the camera without the grant fails at the OS.
  - **Linux and Windows:** nothing. Linux has no prompt and no usage-string
    mechanism (1069.008 D8), so a Rust hatch reaches whatever the process can.
    The grant is a declaration, and the reach table lists it.

  The documentation says this per platform. Exact makes no claim to sandbox
  native code.
- **On the web, policies hold where they are served.** A page-module hatch is
  held to the CSP and `Permissions-Policy` that Exact's render server derives
  from the grants (LLP 1048 D11, 1069.008 D6), like any page script. A static
  dist gets no `Permissions-Policy` and says so in its reach table (1069.008
  D6, D7). There a hatch is held to nothing more than the page is.
- **Under the agent a hatch substitutes, as modules do.** `context.agent` is
  true. A hatch that reaches a device answers from a substitute, never the OS
  (LLP 1069.007), and never prompts.
- **Typed text is not journaled** (§2.5). Diagnostics are development-only
  (§3.2) and never uploaded. The breadcrumb holds names and numbers only.

### 4.6 Determinism under the agent clock

- **Repeatable:** the moments (ordered by batches), acts (FIFO, settled),
  `context.now`, `frames` and `after` (the virtual display), counters, spans,
  and `log` with its session-clock limit.
- **Not repeatable, and named in the documentation:** a hatch's own display
  link, wall timers, `Date()`, `CACurrentMediaTime()`, its own threads,
  `measure` samples taken from them, whether `saveTrace()` wrote, and **UIKit
  or Core Animation a hatch starts**. Agent timing freezes only Exact's own
  animation, at the call sites that read `agentFreezes`
  (`Session.swift:65-73`; `PresenterIOS.swift:292`, `NavigationIOS.swift:350`,
  `NodeViewIOS.swift:963`, `:1004`). There is no global freeze, so a hatch's
  `UIView.animate` runs on the wall, and screenshots of it do not repeat. A
  hatch that wants a repeatable animation drives it from `frames`.
- **`clock settle`** waits for acts and due `after` callbacks (§2.5). It does
  not wait for a hatch's own timers, which it cannot see. `perf hatches`
  promises a mark only for a `frames` ticket, never for a display link the
  host did not issue.

| Web | `modules/web/index.js`, the page module | `host/web-js/build.mjs` | the page module, and `hatches.js` only where linked by use (as built; the byte-identical cores check it, §9) | after first paint (as built) |
| Linux | `modules/linux/*.rs`, one type that implements `exact_linux::Hatches` (every method has a default that does nothing), named once: `pub type ExactHatches = App;` | the app's own Linux crate: the generated `entry.rs` `include!`s the files | the app's binary, statically: no `dlopen`, no C table, no cargo feature on a core crate | the host constructs the value with `ExactHatches::default()` after first present, then calls `app` |
| Windows | the same `modules/linux/*.rs` (the trait is the presenter's) | `exact-windows` gains an adapter. Its own entry (`src/lib.rs`) takes the hatches value. | Android | `modules/android/*.kt`, one `ExactModule` subclass, the same names | the Android host's build, when it exists | the APK | after first frame |

- **No hatch code runs before first present on any host.** On Linux and
  Windows nothing in `modules/linux` is constructed before then. The generated
  entry holds only the type, and the host makes the value.
- **Which platforms handle each word is declared in `app.json`**, not in
  code: `"hatches": ["avatar"]` (every platform the app builds) or `"hatches": {
  "avatar": ["ios", "macos", "web"] }`. It is a static literal, so the bake
  reads it for every target with nothing scanned or run, even when building
  iOS on a Mac. A computed `class var` cannot be read that way, and an export
  scan sees names, not values (`build.mjs:92`), so neither is used. The
  declaration feeds the requirement and the capability (§4.3) and
  `state.hatches.platform`.
- **Typed keys follow the declaration per platform.** `ExactHatchKey` (Swift,
  Kotlin) and `HatchKey` (Rust) are generated with only the words that
  platform handles. `data-keys.mjs` maps `app.manifest.hatches ?? []` as a word
  list today (`:15`), so it learns to flatten the object form for the target
  it is building before it emits keys. Module code that names a word its platform does not
  handle fails to compile, so the declaration and the code cannot disagree on
  natively compiled platforms. On the web, the page module reads plain
  strings, and a word the web does not handle is never called.
- **The web stays `index.js`.** The export scan reads only that file
  (`build.mjs:86-91`), and the build copies the module directory unchanged
  (`build.mjs:508`). A TypeScript page module would be separate work, not
  part of this RFC.
- **The ABI grows by size.** New module-table entries: `app`, `window`,
  `windowEnded`. New host-table entries the module calls: `frames`, `after`,
  `diagnostics` (one pointer to a call table), `owns`, `parts`, `input`. That
  is three module entries and six host entries past 184 and 48. The
  breadcrumb is written by the host around each call and has no table entry. An older module's shorter table still
  loads with none of them (1075.003 §3.9). The overlay has no Apple entry.
- **`bun scripts/exact.mjs hatch <word> [--app | --window]`** (new apparatus,
  approved by Charlie 2026-10-06) adds the word to `app.json` `hatches` (for a node),
  with the platforms it writes stubs for.
  It writes one stub for each target the app actually builds: `apple/` and
  `modules/apple` for Apple, the web build for the web, a `linux/` crate for
  Linux and Windows. It does not use `host`, which is per-platform bake
  metadata and may name a platform the app does not build. Each stub has
  the hatch's moments, its ended moment undoing what built added, a region, and one
  `d.log`. Each stub says what the hatch gives up on that platform
  (1075.003.000 §3.5). An app with no module gets each platform's
  boilerplate. The files it writes are the app's.
- **The template's `AGENTS.md`** (LLP 1086) gains a short section on hatches:
  the verb, §2.5's rule, `EXACT_HATCHES=off`, `perf hatches`, `owns`.

## 6. Alternatives

- **Hatches in TypeScript on every platform.** This is 1075.003 §3.10's
  experiment. It is refused here because it runs JavaScript in the tree on
  native, and its thread and lifetime questions are open. Nothing in this
  design forecloses it.
- **An event bus from hatches into Contract** (`dispatch(action, payload)`).
  Simpler for authors, and wrong for parity: the web, the agent and the
  hatch-less app could not reach what a hatch dispatched.
- **Agent visibility by scraping** the platform's view and accessibility
  trees. 1080.001 and 1080.002 already do the platform's part, but they
  cannot say *whose* a view is or *why* it is there.
- **The platform's own tracing** (`os_signpost`, `console.time`, Perfetto)
  instead of `diagnostics`. A hatch may still use it. It does not reach
  `perf`, `state` or the trace file on every host.
- **A logical frame clock driven by the display link even under the agent.**
  Rejected: under the agent there is no display, and 1073 D3 already defines
  the virtual one.
- **Activation delivery for parts through a closure.** Rejected (§3.5). It
  exercises different code from a finger and is an action by name.
- **Claiming input on painting hosts.** Rejected for now (§2.2.2): it is the
  gesture arena.
- **Linux through a C ABI and `dlopen`.** That only matters if hatches ship
  apart from the binary, and a native change never does.
- **No painting-host hatches.** That is honest, but it leaves Linux and Windows
  with no escape hatch at all. The overlay is bounded: it replaces a whole
  recording in a format the painter already replays.

## 7. Risks

- **The escape hatch becomes the road** (1075.003.000 §5). The hatch-less smoke
  (§9), the journal, `perf hatches` and `owns` make a heavy hatch visible.
- **Diagnostics become telemetry.** They are development-only, capped, never
  uploaded, and refused past their bounds.
- **Regions and parts can be wrong.** They are bound to objects, and the
  host reports what it observes beside what was declared. A part that is
  covered fails the aim, by name.
- **The overlay drifts into a canvas API.** It is limited to whole-recording
  replacement, clipped to the box, with fixed bounds. Anything more is a
  `canvas` node.
- **The settle pump grows.** Draining hatch acts inside settle on Apple adds a
  path through which app code runs during an agent read. It is the same code
  that would run on the next turn, in the same order.
- **The ABI grows by nine entries.** Each lands with its fixture case, or
  is not added.
- **Windows needs real adapter work**, not just a re-export. Stage 4 sizes it
  and tests a running Windows binary.
- **Android's shape is provisional.** Its host's RFC may revise the handle.

## 8. Stages

Each stage lands with its fixture cases in `apps/native-fixture`, its tests in
existing binaries, and an amendment to this document's as-built section.

1. **Diagnostics, timing, the breadcrumb, the delivery gap** (Apple, web JS).
   Exact times every call; `context.diagnostics` with §3.2's bounds;
   `state.hatches`'s new fields; `perf hatches`; Save Trace's `hatches` section and
   `saveTrace()`; the late-frame `hatches` on wall time; the breadcrumb; the web's
   throw rule with teardown kept, per instance; the per-platform `hatches`
   declaration and keys; §4.3's requirement, capability and classifier
   branch.
   *Acceptance, under the agent:* `smoke.mjs <ios|macos|web> --app
   native-fixture` reads a `d.log` line, a counter, a span and the fixture
   hatch's call time in `perf hatches`, and two drives agree on every count. The
   classifier refuses a bundle whose plan needs an Apple-handled word against
   an Apple cohort built without it, and publishes the same plan to a Linux
   cohort whose platform does not handle the word.
   *Acceptance, on the wall* (a development session, no agent clock): a

   late frame from a missed callback and one from an overrun alone both name

   *Acceptance, the breadcrumb:* an XCTest launches a fixture build whose hatch

   other's hatch, and the relaunch names the right session.

### 13.2 Stage 1 on the web's JS target: timing and diagnostics

Landed in `host/web-js/hatches.js`, with `agent.js`, `perf.js` and the driver
(`scripts/agent-inspect.mjs`):
- **Every call is timed** (§3.1), a node's by plan site and moment and a
  container's by its hatch, exclusive of calls nested in it. The last 1,024

- **`diagnostics`** (§3.2) is `e.diagnostics` on a node's handle, scoped
  `element <word>`, and `globalThis.exact.diagnostics`, scoped `module`. Every
  bound in §3.2's table that applies to one thread is enforced (the
  cross-thread ring is Apple's). The bounds are per page module, so a node's
  counters and the module's share the 64 names.

  plan's digest (`exact.plan`), the same mark `perf` uses. A production page

- **`state.hatches` is reshaped**, on Apple too: `{ words, scopes, measuring,

  reply's own fields must not be taken for one. A word's entry gains

  containers' calls. §3.3's "as today, plus" is amended by this.
- **`perf hatches`** answers `{ hatches, calls, tickets, counters, timings,
  rejected, abandoned, limited }` with `perf`'s tags (`seq`, `plan`,
  `incarnation`). `hatches` is each hatch's calls, total and worst ms;
  `calls` is the same by site and moment. `perf hatches during "<op>" …`
  subtracts two reads and refuses across a changed plan or incarnation.
  `perf <target>`'s reply carries `hatch: { calls, ms }` on a hatched site's
  row. The Linux host is refused by name until stage 4.

  node's `element` is not called again; its `elementEnded` still is.

### 13.3 Stage 1 on Apple: timing, diagnostics, Save Trace's section

Landed in `HatchDiagnostics.swift` (the session's store), `NativeHatches.swift`
(the table and the timed calls) and `ExactNativeModule.swift` (the module's
side), on iOS, tvOS and macOS:
- **The host table is 56 bytes.** Offset 48 is `diagnostics`, a pointer to a
  call table `{ u32 size 16; 8 record(host, kind, node, scope, name, value,
  text) → u64 }`, and nil in a production bake. A module reads it only from a
  table of 56 or more, so an older host or module still loads (§5).
- **`ExactDiagnostics`** is `context.diagnostics` (scope `module`) and
  `element.diagnostics` (scope `element <word>`): `log`, `count(_:by:)`,
  `measure(_:ms:)`, `begin(_:)` returning an `ExactSpan`, `publish(_:_:)` and
  `saveTrace()`. With no entry to call, each returns at once. The module's
  records nothing before the hatches connect.
- **Any thread may call.** Off the main thread a count joins a pending sum
  and a snapshot replaces a pending one, both under a lock, so counts from
  several threads sum exactly; every other record goes through a ring of
  1,024 that overwrites its oldest and counts `dropped`. The main thread
  drains them, in order, on its next turn and before each read. This is
  §3.2's ring with a lock in place of fixed 320-byte slots; the bounds are
  the table's.
- **A span from another thread** is timed from the turn that drains it, on
  the session clock, which only the main thread reads.
- **Every call is timed by hatch and moment, not by plan site.** The Swift
  host does not know a node's site (the runner does), so `perf hatches` on
  Apple has no `site` on a node's rows, and `perf <target>`'s rows carry no
  hatch time there. Owed: the site, from the runner, by node.
- **`state.hatches`** is the web's shape (§13.2), plus `dropped`.
  `perf hatches` takes its tags from the runner's own `perf` read.
- **A new module is a new incarnation:** the store is emptied when the
  hatches connect.
- **Save Trace** carries `hatches: { state, perf }`, read in the turn that
  reads the journal, the frames and `perf`; the web's does too, and
  `agent.mjs trace <file>` prints it. `diagnostics.saveTrace()` asks for one,
  at most one a second of wall time. On the web under the agent's clock no
  frame is sampled, so there is nothing to save.

Tests: `HatchDiagnosticsTests` (every bound, a nested call's time, four
threads' counts, the ring's overwrite), `FrameSamplerTests` (the trace's
section); the fixture's Swift module records as its web module does, and
`smoke.mjs <macos|ios> --app native-fixture` reads it back.

### 13.4 Stage 1: the per-platform declaration and the delivery check

- **`app.json` `hatches` has two forms** (§5): a list, every platform the app
  builds, or `{ "word": ["ios", "web"] }`. The names are `ios`, `tvos`,
  `macos`, `web`, `linux`, `windows` and `android`. The bake knows four
  platforms (`ios`, `macos`, `linux`, `web`), and tvOS bakes as `ios`, so a
  tvOS build handles what `ios` names; `tvos` and `windows` are accepted and
  match nothing until a bake is theirs. One rule, read three ways: the bake's
  `contract::native::hatches_on`, the scripts' `hatchWords` (`scripts/app.mjs`),
  and the schema's `oneOf`.
- **Typed keys follow the platform.** `ExactHatchKey` has only the words the
  build's platform handles, so Swift that names another platform's word does
  not compile there.
- **The cohort's capability** is the compatibility input `hatches`: the words
  its platform's module handles, `null` for none. The key is new, so every
  compatibility id moved once with this change.
- **The plan's requirement** is `requires.hatches` on `app.plan`: the words
  the plan marks that the platform handles. A plan that marks none has no
  such key, so a cohort from before the capability still takes its bundles.
- **`classifyArtifacts`** checks the subset beside `executors`: a missing word
  adds `app.plan: hatches.<word> (handled by this platform's module, not by
  the installed one)` and no bundle is published to that stream.
- **A host calls only what its module handles.** On Apple the module's table
  names its words (under `hatches` in the roster text, a key no tag can take),
  and the host skips any other word: its nodes are shown, the journal says so
  once, and `state.hatches.unhandled` lists it with reason `module`. On the
  web the build writes the web's words into the page when the manifest gives
  words their platforms, and `hatches.js` does the same with reason `plan`.
  `state.hatches.platform` is the list.
- **Not built: the plan's own per-platform row.** §4.3 has the bake write
  each platform's words into the plan, under its signature, so that removing
  a platform from a word reaches an installed cohort with the next bundle.

### 13.6 Stage 1 on Apple: the crash breadcrumb, and `EXACT_HATCHES=off`

Landed in `HatchBreadcrumb.swift`, on in production as well:
- **The file is §4.4's**: `hatch-breadcrumb-<pid>`, one page mapped shared, 8
  session slots of 512 bytes, each a stack of 8 checksummed records under a
  published depth, with an overflow count. A record holds the hatch as the
  journal names it (46 bytes), its moment, the incarnation and the session's
  call number; the slot holds the session's label.
- **Whose process is gone is decided by a lock, not the pid.** A process
  holds `flock` on its file while it lives, and a launch reads and deletes
  each file it can lock. A pid can be reused, and on iOS another app's
  process cannot be probed.
- **Where:** `~/Library/Application Support/exact/<bundle id>/`. Under the
  agent, a directory in the temporary directory keyed by the bundle id, so
  the next agent launch finds it; the agent's per-process scratch tree would
  not survive the death.
- **When it is read:** as the first session's hatches connect, after first
  pixel, never on the boot path. That session's journal gets the line, so it
  is not the journal's first line. An app with no module makes no file and
  reads none.
- **Where it shows:** `logs`, and `state.hatches.lastEnd` (§4.4 said
  `state.native.lastEnd`; the native state is the runner's, and this is the
  host's).
- **The depth is published by a call the optimizer cannot see through**, in
  place of an atomic store: the deployment targets predate Swift's atomics.
- **`EXACT_HATCHES=off`** (§2.6) is built on Apple: a development build
  connects no hatch and says so once; the module still loads and its views
  and calls work. The production strip drops the name with `EXACT_AGENT`.
  The web's, Linux's and Windows' switches come with stage 2 and stage 4.

Tests: `HatchBreadcrumbTests` (a death inside a call, a clean run, nesting
past 8, each session's slot and a ninth session, a torn record, a live
process's file). `smoke.mjs macos --app native-fixture` kills the fixture
inside the badge's hatch (`EXACT_FIXTURE_DIE`, the fixture's own switch),

### 13.7 Stage 2, first part: the act queue, `input`, and settle

On the web's JS target and on Apple (§2.5):
- **One bounded FIFO a session** for what a hatch asks of an authored node:
  256 acts and 1 MB of `input` text, an act past either refused by name and
  counted in `state.hatches.refused`. A drain runs the acts queued when it
  starts, at most 64. On Apple the drains are main-queue turns
  (`ElementHatches.later`, which replaced a dispatch per act). On the web the
  first is a microtask and each later one a `MessageChannel` task, until a
  task finds the queue empty.
- **Every act is journaled** when it runs: `hatch element presser #130: click
  (delivery: hatch)`.
- **In flight.** On the web an act counts in the page's `inflight` from its
  asking until it has run, which is what settle waits on.
  `state.hatches.inFlight` is the queue's length on both hosts. Apple's
  settle loop drains the queue itself, on the main thread it holds.
- **`clock settle`** answers `settled: false, reason: "hatches"` after 16
  drains that left acts queued. The reason is `hatches`, not §2.5's `hooks`.
- **`input(text)`** is `ExactElement.input(_:)` and `e.input(text)`, host
  table offset 56 (the table is 64 bytes). The primitives are §2.5's: on iOS
  the field's or text view's `text`, on macOS the field editor's
  `replaceCharacters` over the whole range while the field is edited and
  `stringValue` otherwise, each cut by `TextInputLimit` and reported with
  `typed`; on the web `setRangeText`, or `value` for `email` and `number`,
  cut to `maxLength`, then an `InputEvent` of `insertReplacementText`. Focus
  does not move. Refused by name: a node that is not a text field, a
  contenteditable editor (the web), a disabled or readonly field, a composing
  one, and text over 64 KB. The journal has the length, `protected` for a
  password, and never the text.
- **Not built yet:** the drain inside a seek at a hatch instant (§2.4 step
  3), which comes with the frame clock; `HatchActLimit`; the web's
  page-module load in `hatchInFlight` as its own count (it is in `inflight`
  as before).

The fixture's detail route has a field a hatch feeds and a button a hatch
presses, once when armed and on every change while looping. Its smoke, on the
web, macOS and iOS: the fed value reaches Contract and the journal holds only
its length; `clock settle` returns after the queued click committed; the
looping hatch is named by settle and, stopped, settles. `js-hatches.test.mjs`
covers the refusals and the queue's bounds. Stage 2's other `input` cases (a
search controller that keeps first responder, macOS search forwarding,
composition) are not driven yet.

### 13.8 Stage 2: the app and window scopes

On Apple (`ScopeHatches.swift`, the module table at 200 bytes) and the web's
JS target (§2.1, §2.1.1):
- **The module's methods are §2.1's**: `app`, `appEnded`, `window`,
  `windowEnded`, with `ExactApp` and `ExactWindow`. The table has two
  entries, each taking an event (built, changed, ended), at 184 and 192, where
  §5 counted three.
- **`app`** is built as the hatches connect, after first pixel, and changed
  when a fact moves: `visibilityState`, `onLine`, `prefersColorScheme`,
  `prefersContrast`, `prefersReducedMotion`, `prefersReducedTransparency`.
  One call however many moved, on the turn after, never inside a batch.
- **`window`** is built for the surface the session presents into, changed
  on a new size or safe area, and ended as the session leaves the window
  (`willMove(toWindow:)`, `viewWillMove(toWindow:)`), while it is still
  there. `frame` is the session's surface in the window's coordinates.
- **The grants are the embedder's**, two properties on the session set
  before its first frame, in place of a creation parameter:
  `hatchesOwnWindow` and `hatchesOwnProcess`. `ExactMac` gives each document
  session its window and no session the process; `ExactIOS` gives its one
  session both; the sample host gives neither. Without the first,
  `window.window` and the scene are nil; without the second,
  `app.application` is nil.
- **A reload** ends `window` then `app` inside the reset and builds both
  again on the next turn, with new handles. The session's end ends both
  before the module goes.
- **On the web** the page is the app's own, so `processOwner` and
  `exclusive` are true; `window` is the page's window with `frame` its inner
  size, changed on `resize`; both end at `pagehide`. A page module that
  exports `window` shadows the global of that name in its own file and
  reaches it as `globalThis`.
- **Not built:** root `data-*` words as `app.data` and their change as a
  moment; the development check for writes to a non-exclusive window's
  chrome or to the appearance proxies without the process; `owns` on either
  scope (stage 3).

The fixture's modules count and publish each moment and tint a window that
is theirs. Its smoke, in a session of its own on the web, macOS and iOS: both
are built and journaled; the grants decide what is handed over (macOS: the
window and no application); `prefer prefers-color-scheme dark` is one
`changed`; a resize is told to `window` (the web and macOS). Stage 2's
two-session sample-host case and the two-document `ExactMac` case are not
driven.

### 13.9 Stage 2: the frame clock, and the web's switch

On Apple (`HatchClock.swift`) and the web's JS target (§2.4):
- **The API.** Swift: `context.frames { frame in … }` and
  `context.after(ms) { … }`, each returning an `ExactTicket` with `stop()`;
  `ExactFrame` is `now` and `seq`. On the web: `exact.hatches.frames(f)` and
  `exact.hatches.after(ms, f)`, each returning its stop, with
  `exact.hatches.now()` and `exact.hatches.diagnostics`. §2.4 wrote
  `exact.frames` and `exact.after`; `exact.frames` is the development frame
  sampler's name (LLP 1079 D3), so the page module's functions sit under
  `exact.hatches`. `exact.diagnostics` stays as it was.
- **The instants are a ticket's own virtual frames**, `base + k·1000/60`
  with the product first, from the session clock's time when the first
  ticket began. A plan frame task armed at the same time has the same
  instants, and a ticket ticks after it.
- **The seek's stops are the host's, not the runner's.** On Apple the agent's
  advance (`advanceStepped`) brings the runner to each hatch instant in turn
  and applies its batch, then calls the ticks and due `after`s and drains
  what they asked, before going on. The runner's seek to `t` then to `t′` is
  its seek to `t′`, which its own partition test holds, so the runner needed
  no change; LLP 1073 D3 is amended in what a host does, not in the runner.
  On the web the runtime's clock holds two entries of the hatches', the
  ticks' and the afters', which its `advance` fires in their turn: after any
  timer or frame task due at the same time, and not counted as commits.
- **At an instant** (§2.4 steps 1–4): the ticks in registration order, the
  due `after`s in due order, then the acts they asked, snapshot after
  snapshot, with the `changed` moments those commits cause, and any `after`
  now due, until nothing is queued. On the web a `changed` moment is told in
  a microtask on the wall and there and then inside a seek.
- **Caps a command:** 4,096 ticks and `after`s (`HatchFireLimit`) and 4,096
  drained acts (`HatchActLimit`), counted across the command's stops and
  answered as `clock`'s error, as `TimerFireLimit` is. The names are
  `Hatch…`, not §2.4's `Hook…`. On Apple each stop's runner seek keeps its
  own `TimerFireLimit`.
- **On the wall** a ticket ticks at each presented frame, after the frame's
  tasks: Apple's frame source runs while one is live, and the web's frame
  loop does not park. An `after` is a timer on the session clock.
- **`frame.seq`** on Apple is the last applied batch's sequence, which a
  development build's trailer carries; a production build reports 0.
- **A reload** drops what was registered, with one journal line.
- **`perf hatches`** reports `tickets` on the web; Apple's reply still says
  0, and a tick's time is under the `frames` and `after` hatches on both.
- **The web's `EXACT_HATCHES=off`** is `?hatches=off` on a development page,
  which the driver sets from the environment variable.

The fixture's `clock` hatch holds a ticket while its node says to run. Its
smoke, a session a drive, on the web, macOS and iOS: 60 ticks for `clock
+1000`; tick *k* reads the count a frame task made at the same instant, 60
times of 60; an `after(0)` chained in the first tick and its `after(20)`
fire inside the seek and a stopped one never; the third tick's 65 clicks and
the one their `changed` asks land at one instant (66 journal lines with one
time); and `clock +1000` equals ten `clock +100`, counters and lines.
`js-hatches.test.mjs` adds the order, the same-instant drain and
`HatchFireLimit`. Not driven: `HatchActLimit`, and the wall path under a
real display.

### 13.10 Stage 3: regions and parts

On Apple (`HatchRegions.swift`, `AgentParts.swift`; host table offsets 80
and 88, 96 bytes) and the web's JS target (§3.4, §3.5):
- **`owns`** is on each scope's handle: `element.owns(view:_:)` and
  `owns(recognizer:_:)`, the same on `ExactRoute` and `ExactWindow`, and
  `app.owns(appearance:)`, each with `surface:`. On the web:
  `e.owns(element, "what", { surface })`, the same on a route and the
  window, and `a.owns("what")` on the app. The web binds elements and
  appearances; it has no recognizer objects to bind.
- **`tree`** shows a node's regions under it as `owns`, the declaration (`by`,
  `kind`, `what`, `surface`) beside `observed` (`live`, the frame the host
  reads from the bound object, its class), and its `parts` with their
  observed frames. `state.hatches` gains `owns` (every region, whatever its
  scope), `surfaces` (the hatch-only ones) and `parts`.
- **Tombstones.** A region whose object has gone or left its window is
  retired as a batch begins and before a read: `observed: { live: false,
  ended }` for 5 s of session clock, at most 16 a session. A second read with
  nothing changed between sees the same tombstone. A node's end, a route's,
  the window's and the app's take what they registered, without a tombstone.
- **The bounds are §3.2's**, each refusal by name and whole: 32 regions a
  scope and 1,024 a session, a sentence of 120 bytes, 16 appearances keyed by
  their sentence, 32 parts a node, an id of 64 bytes unique in its node, a
  label of 120.
- **1080.001's opaque interiors** are attributed by identity: a non-node
  subview under a region's bound view counts toward
  `coverage.stray.opaqueBy.hatch["<its sentence>"]`, the innermost bound
  ancestor winning. The module and platform split §3.4's example shows is not
  built: the walk does not tell those two apart today.
- **Undeclared recognizers** (a development build): a recognizer a node's
  `element` call left on the node's own view, neither there before the call
  nor bound by a region, is journaled once a hatch and class. The check
  compares the view's recognizers across the call; the walk of an exclusive
  window's recognizers is not built.
- **`tap <node>/<part>`** (Q1 (a)). The host's side is two forms of `tap`:
  `{"op":"tap","id":V,"part":"seal","aim":true}` answers the part's middle
  from its node's corner and a token, or refuses by name (no such live part,
  not in the window, `covered by <class>`); the driver then delivers one real
  click at that point (`clicks 1 at x y`, the form that takes a point on any
  node; a touch on the simulator under `--touch platform`); and
  `{"…","landed":token}` answers `landed: "part"` or `"elsewhere"` with the
  class and node reached. The token binds the node, the part, the bound
  view's identity and the incarnation: a part replaced or a view swapped
  between the two is refused as stale. On macOS the evidence is the click's
  own hit view, recorded by the delivery; on the web, the target of the
  pointer event the page heard after the aim. No path activates by name.
  `unsupported`, never a fallback: the simulator's agent taps (not real
  touches), Linux, Windows.
- **`tree --ax`** on Apple joins a part by ownership: an element whose view
  is the bound view or inside it carries `part: "<node>/<id>"`, and
  `coverage.parts` lists every part as `exposed` or `not exposed`. No finding
  is added. The web's Chrome tree is not joined to parts yet.
- **Not built:** recognizer outcomes for bound recognizers in the tap's
  reply; the aim's "nothing is mid-transition" test; the simulator's
  real-touch landing identity (`TouchLog`), so a part tap there has not been
  driven; `layout`'s refusal of a part by its own name (an unknown target is
  refused as any is).

The fixture's badge draws a seal with a click recognizer of its own and
declares both. Its smoke, on the web, macOS and iOS: `tree` shows the
region's two halves and the part; `tap hatched-badge/seal` lands on the part
and the hatch counts the press (the web and macOS; `unsupported` on the
simulator); an absent part is refused by name; with the seal gone its regions
are tombstones, the same at each read. `HatchRegionsTests` and
`js-hatches.test.mjs` hold the bounds.

### 13.12 Stage 1: the plan's own per-platform row

§13.4 left this owed; it is built for Apple.
- **The plan has a `hatches` table**: each word `app.json` declares, with a
  mask of the platforms that handle it (bit 0 `ios`, 1 `tvos`, 2 `macos`, 3
  `web`, 4 `linux`, 5 `windows`, 6 `android`; a plain list is every bit). The

  give the platform its bit reaches Swift as `hatchOff` in place of `hatch`:
  the node is an ordinary one there, on the fast path, no hatch is called, the
  journal says so once, and `state.hatches.unhandled` lists it with reason
  `plan`. A plan with no rows leaves every word to the module, which narrows
  by its own list (reason `module`, §13.4). So a platform taken off a word
  stops being called with the next bundle, whatever the installed module was
  built to handle. tvOS reads the `ios` bit, as it bakes as `ios`.
- **`tree` still shows the word** on such a node: it is the runner's.
- The web needs no row at run time: its page build and its plan are one
  artifact, and the build writes the web's words into the page (§13.4). Linux

### 13.13 Stage 4: Linux and Windows

Built by a second lane and merged here. Hatches run on the Linux host end to
end. The Windows adapter is written and type-checked on a Mac with its `cfg`
gates lifted; it has not been compiled for Windows or run there.
- **The trait and the entry** (§5). `exact_linux::Hatches` has `app`,
  `app_ended`, `window`, `window_ended`, `element`, `element_ended`, each
  defaulting to nothing, implemented by one type in `modules/linux/*.rs`
  named once (`pub type ExactHatches = App;`). The entry is
  `run_with_hatches::<Data, H>(PLAN, COMPAT, HatchKey::WORDS)`, on
  `exact_linux`, `exact_linux_update` and `exact_windows`; it holds only the
  type, and the presenter makes the value with `Default` after its first
  frame is presented. `contract::native::rust_hatches` writes the typed
  `HatchKey` (the platform's words) and the module that includes the files;
  an app's Linux `build.rs` calls it. Only the fixture's does so far.
- **The handle** (§2.2): `hatch()`, `id()`, `node()`, `frame()`, `data(word)`,
  `is_new()`, `is_live()`, the four acts, `overlay()`, `diagnostics()`.
  `frame()` is the laid-out box in document coordinates, without scroll or
  transforms; observed pointer input carries the point local to the painted
  box.
- **The overlay** (§2.2.1): `overlay().draw(|c, w, h| …)` records a Canvas 2D
  list that replaces the last one whole; `clear()` publishes the empty one. It
  is refused past 4,096 ops or 256 KB, clipped to the border box with its
  rounded corners, painted after the node and its descendants, dropped at a
  new size with a `changed` moment, and a publish dirties the picture and
  wakes an idle loop. Images and text in a recording draw nothing yet.
- **Observed input** (§2.2.2): `context.observe(&element, |me, input, cx| …)`,
  after Exact's dispatch, with `handled`, innermost first, a pointer captured
  from down to up, keys to the focus and its ancestors. `observe`, `frames`
  and `after` are on the context, not the handle: the closure needs the
  module's type. `handled` means a commit landed or a scroller moved during
  Exact's dispatch. The wheel is not observed.
- **When moments run.** Between turns: each agent command, each loop turn,
  each hatch instant. `ended` runs after the commit that removed the node,
  with the handle keeping its last box and words, where Apple runs it inside
  the batch. `changed` also fires on a size change alone, so hatch code that
  acts on words compares them (the fixture does).
- **The rest is the shared design**: the act queue and `input` (§13.7), the
  app and window scopes with both grants true (§13.8), the frame clock with
  the seek stopping at each hatch instant under `HatchFireLimit` and
  `HatchActLimit` (§13.9), diagnostics and timing with `state.hatches` and
  `perf hatches` in the shared shape, `clock settle` naming `hatches`, the
  crash breadcrumb in `$XDG_DATA_HOME/exact/<app id>` or
  `%LOCALAPPDATA%\exact\<app id>` (under the agent, a directory of its own
  kind, so a painting host and Apple's never read each other's), and
  `EXACT_HATCHES=off`. Diagnostics are the loop thread's only: the handles
  are not `Send`, and there is no cross-thread ring. `publish` takes JSON
  text.
- **Per-platform words**: the host calls a word only where the plan's row
  gives it to `linux` (or `windows`, `android`) and the module's
  `HatchKey::WORDS` has it, with reason `plan` or `module` (§13.12).
- **Extra reply fields**: `words.<w>.overlay { shown, published, dropped }`,
  `overlaysRefused`, and `lastEnd`.
- **The `hatch` verb** writes `modules/linux/hatches.rs` for an app with a
  `linux/` crate, a word an arm and its two functions, and says what the
  crate's `build.rs` owes.
- **Not built:** images and text in an overlay; the late-frame join and
  `save_trace()` outside the Linux display loop; root `data-*`; `owns` and
  parts (parts are an object host's); a Windows crate for the fixture, so
  nothing has run on Windows; the KMS display loop's edits
  (`host/linux/src/display.rs`) are not compiled on a Mac.

Tests: `cargo test -p exact-linux --lib --tests` (overlay replacement, the
resize drop, clipping, both bounds, observed input after dispatch, ticks at
virtual instants, the act queue's bounds, the diagnostics' bounds, the
breadcrumb file, the entry generator); `smoke.mjs linux --app native-fixture`
(38 checks: the dot's overlay in a screenshot and redrawn at a new size on the
detail list, the observed press with `handled`, counters and `perf hatches`,

and the swapchain host over the same presenter. So Android is a painting
host here, and its hatches are stage 4's:
- **The same trait and files.** An Android build of an app's Linux crate
  includes `modules/linux/*.rs`, or `modules/android/*.rs` when the app has
  that directory, as `exact_linux::Hatches`: the node's box, an overlay,
  observed input, the app and window scopes, the frame clock, the act queue,
  diagnostics, the breadcrumb, `EXACT_HATCHES=off`.
- **The word is `android`.** The build writes `HatchKey` from the words
  `app.json` gives `android`, and the host reads the plan row's `android`
  bit. The bake still computes the cohort's capability as `linux`'s, since an
  Android build bakes as `linux`; nothing is delivered to Android yet.
- **The crash breadcrumb** takes its lock with `flock`: the standard
  library's file lock is not supported on Android, where it left a file
  nobody held or read. Linux uses the same call now.
- **Q4 stands for the rest.** The scope names and moments are the ones fixed.
  A Kotlin `ExactModule`, a `view` on the handle for a node that is a View,
  and `modules/android/*.kt` wait for the Canvas reader, whose Kotlin view
  lives outside this repository (LLP 1076 §3.3, LLP 1107 §2); that side
  still owes its own RFC. `exact hatch` writes no Android stub and adds no
  `android` to a word: an app that builds for Android adds it to the words
  its Linux hatches handle.

Driven on two phones, a Pixel 10 Pro XL and a Pixel 10a, both on Android 16,
over `adb` from the Linux box they are attached to (the fixture built there
with NDK r27c): the 38 checks of stage 4's smoke pass on each (the dot's
overlay in a screenshot and redrawn at a new size, the observed press, the
counters and `perf hatches`, a draw then a clear with the app idle, settle
after a queued act, the frame clock, the launch after a death inside a hatch
naming it). `smoke.mjs` has no `android` host, so the checks were run by
calling its painting-host function against the `android` carrier by hand;
admitting `android` to the smoke is LLP 1107's to do. Not driven: the GPU
painter on a phone (the carrier's default is the CPU painter), the swapchain
host on a screen, and touch through Android's own input system.

### 13.16 Stage 1: Apple times a node's calls by its plan site

An element hatch's calls on Apple are timed by site and moment, as the web's
and the painting hosts' are: `perf hatches`' `calls` rows carry `site`, and
`perf <target>`'s row for a hatched site carries `hatch: {calls, ms}`. The
host asks the runner for a node's site once (the `node` operation), in a
development build only, and keeps it until the node's `ended`, whose call the
runner could no longer place. `perf hatches`' `tickets` is the live frame
tickets, where it had been a constant 0. The shared fixture smoke reads both
on the web, macOS and iOS.

### 13.17 Stage 4 on a real Linux box

Stage 4 was built on a Mac, where the Linux host runs headless and its KMS
code is not compiled. On an x86_64 Linux box (2026-10-07): `cargo build -p
exact-linux --all-targets` and `cargo clippy -p exact-linux -p exact-windows
--all-targets -- -D warnings` pass, and the fixture's Linux smoke passes with
its 38 hatch checks. `cargo test -p exact-linux` passes one test thread at a
time (623 library tests, 76 pinned, 88 integration); in parallel the library
and pinned binaries segfault inside the Vulkan loader as many GPU painters
start at once, the same at the commit before stage 4 (QUEUE).

Windows is still uncompiled: `cargo check -p exact-windows --target
x86_64-pc-windows-msvc` (and `-gnu`) from Linux stops in `ring`'s build
script, which needs a Windows C toolchain.
