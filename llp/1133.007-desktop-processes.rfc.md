## Summary

A desktop app built with exact2 cannot start a program. The T3 Code clone
starts six, all from its own Swift: the `t3` server, which it keeps alive
and restarts; `t3 --version`; `tar`, to unpack the server's runtime; the
login shell, to learn the person's `PATH` (three times, for three
callers); `tailscale status --json`; and `ssh`, for configuration, a
remote launch and tunnels. With them come reads and writes under `~/.t3`
and `~/.ssh`, which no grant can name, and an SSH password field whose
value must reach `ssh` without passing through the app's state. That is
3,882 lines of Swift (§13), and the reference app does the same from
Node's `child_process` in Electron's main process.

This RFC proposes one module, `@exact/child-process`, for macOS, Linux and
Windows, with one Rust implementation in the data executor:

- **A child process is a stream resource** (D2). Data code returns
  `spawn(command, args, options)` as a resource's answer, as it returns
  `fetch(url, { exactStream })` for a WebSocket today. Its mapper receives
  `spawn`, ordered `stdout` and `stderr` chunks, `exit`, and `close` once
  the pipes have drained. It writes stdin through the handle of that
  incarnation, under LLP 1016.000 D7's rules for a socket's `send`, with
  Node's `drain` for flow control. Letting the resource go sends `SIGTERM`
  to the child's process group, then `SIGKILL` after a grace period. The
  names are Node's, since the web has none (D1).
- **A one-shot run** (D3): `await execFile(file, args, options)` answers
  `{ stdout, stderr, code, signal }`, with a timeout the host keeps.
- **A kept service** (D4): `spawn`'s `exactRestart` and `exactReady`
  options restart the child with backoff while the resource is held and
  report readiness by polling a URL, so restart and readiness need no
  timers in data code.
- **The login shell's environment** (D5): `loginShellEnvironment()`
  answers the variables the app's grants name, captured once per launch.
- **Which programs** (D7): `process.spawn` grant lines name each program:
  a bundled helper, an absolute path, a home or app path, or a name looked
  up on a `PATH`.

Beside it, pieces other apps can use:

- **Home and bundle paths** (D6): `home:/.t3/userdata` and
  `bundle:/Resources/t3-runtime` are paths that grants and `storage.fs`
  take, beside `app:/` and `doc:/`, with the file operations the consumer's
  install and probe need added to `storage.fs` (D6a).
- **A secret field** (D8): `input type="password" secret="ssh.password"`
  keeps what the person types in a volatile secret store that no event,
  state, snapshot or journal sees. Data code reads it with `store.get`.

iOS, tvOS, Android and the web answer every name of the module, and every
`home:` path, with `NotSupportedError`, and `processStatus().available` is
false there (§8; Android's cell is `later`, the others `absent`). The secret field is not desktop-only: it lands on
every host that has a password field.

## 0. What the ruling decided

§12 records the nine rulings (Daehyeon Mun, 2026-10-23), each as
proposed. The five that change the design: the module is exact2's
vocabulary, imported from `@exact/child-process` (Q1); a grant may name
bundled helpers, absolute paths, `home:` and `app:` paths and names on a
`PATH`, one line per program (Q2); supervision is `spawn` options, not an
`app.json` list (Q3); the secret field is `input type="password"
secret=` (Q5); and a tool, wake or headless origin may neither start nor
drive a program (Q8).

## 1. What exists, and what the consumer needs

### 1.1 In exact2

- **Nothing starts a program for an app.** Shipped host code launches a
  process in two places only: the Mac host relaunching its own executable
  (`host/apple/Sources/ExactKit/Relaunch.swift:33-38`) and the terminal
  host's `open` or `xdg-open` for `openURL`
  (`host/terminal/src/term/unix.rs:296-308`). `host.macos.resources`
  copies a helper tree into the bundle (`host/apple/assets.mjs:461-516`)
  and LLP 1069.008 D9 signs a helper with a hardened-runtime exception
  (`runtime.allow-jit Helpers/node/bin/node`), but "nothing launches or
  supervises it. A native module can"
  (`issues/20261015-chosen-documents-outlast-the-launch.md:43`), and data
  code cannot even find it: "Find `Resources/server` through
  `Bundle.main.resourceURL` from a native module" (`docs/reference.md:722-723`).
- **A bidirectional stream exists.** LLP 1016.000 D7 gives TypeScript
  sources a WebSocket whose mapper receives ordered frames and whose handle
  sends, staged with the commit that made them, bounded per call, per
  answer and by the transport's buffer, refused after release, and listed
  in `state.streams`. It is built on the web JS target and in native
  TypeScript on Apple and Linux, over `ibex2`'s transports. A request is
  one struct with optional kinds (`runner/src/request.rs:120-160`: HTTP,
  `storage`, `surface`, `stream`, `socket`); a socket's staged operations
  are addressed by stream ticket (`SocketSend`, `:562-573`).
- **One executor on three desktops.** `ibex2` runs fetch, WebSocket,
  `fs` and `env` for Apple, Linux and Windows; the executor core is shared
  by Apple and Linux (`host/linux/src/executor.rs:8` compiles
  `host/apple/src/executor_core.rs`), and the Windows host builds on the
  Linux one (`host/windows/Cargo.toml:10`). The executor refuses a stream
  that is not independent HTTP (`executor_core.rs:1099-1106`).
- **Path grants** are `app:/…`, `doc:/…` or an absolute path fixed at bake
  (`PathPrefix::new`, `grants/src/lib.rs:69-93`, mirrored in `ibex2`'s
  `grant.rs`). `~` has no spelling, and a home directory differs per
  person, so `~/.t3` cannot be named. The executor's `fs` was written with
  that case in mind ("the package that cannot read `~/.ssh`",
  `vendor/ibex/crates/ibex2/src/stdlib/fs.rs:9-12`). Its `stat` has no mode
  (`fs.rs:324-333`), and the web's `storage.fs` refuses every path but
  `app:/` (`host/web/storage-fs.js:21-23`). `env.read <NAME>` parses and
  `ibex2` reads it (`vendor/ibex/crates/ibex2/src/host.rs:633-658`), but no
  data executor exposes it to TypeScript.
- **A password field's text reaches the app.** It is never agent output
  (`tree` shows `•••`), but the field is bound to state like any text field
  (`apps/unsaid/app.contract:252`; `runner/src/agent.rs:393-396`: "The
  app's own state still holds the value"), and its events carry the text:
  `InputEvent`'s `value` and `data` (`contract/types/src/selection.rs:173-183`),
  `beforeinput` with the replacement and the prior value
  (`host/apple/Sources/ExactKit/FieldInput.swift:69-81`;
  `host/web-js/rt.js:926`), and key events (`rt.js:931`). The secret store
  is durable: `Store::set` records a write (`runner/src/store.rs:386-399`),
  a reload carries its snapshot (`:464-470`), and the web keeps it in
  `localStorage`. LLP 1133 §7 refuses "a secret, key or token as a Contract
  value", and LLP 1018 D5 keeps a token below the data seam; neither has a
  field that types into that place.
- **`rules/DEFERRED.md`** has no entry for processes, spawning, shells or
  the home directory: nothing refuses them by name, and nothing admits
  them. Its nearest entries keep ambient WebSocket globals refused
  (`:475-483`) and durable capability grants refused (`:504-511`); this
  RFC adds neither. LLP 1133.000 lists no such module; it mentions
  "desktop-process work" once, as where reveal-in-Finder waits
  (`llp/1133.000-the-roster.rfc.md:110-114`).

## 2. Tier 1

### D1 — The web has no process: Node's `child_process` names, a declared deviation

No browser can start a program, and none will. Following LLP 1133 D1, the
module takes the name its platforms share most widely and says so: Node's
`child_process`, which a TypeScript author who has written a CLI or an
Electron main process already knows. The names are `spawn`, `execFile`,
and the options `cwd`, `env`, `stdio`, `encoding`, `timeout`, `maxBuffer`
and `killSignal`; the events are `spawn`, `exit`, `close`, `drain` and
`error`; the child's methods are `write` (Node's `child.stdin.write`),
`end` (`child.stdin.end`) and `kill(signal)`; its fields are `pid`,
`exitCode`, `signalCode` and `writableLength` (`child.stdin.writableLength`).

The shape is Exact's, as a WebSocket's is: a child is a resource's answer
and its events reach a mapper, not an `EventEmitter`, because a resource's
value is what the mapper returns (LLP 1016.000 D1) and a data module has
no timers or listeners that outlive an answer. These are the deviations,
each declared:

| Node | Here | Why |
|---|---|---|
| `child.stdout.on('data', f)`, `child.on('exit', f)` | one mapper, `exactStream(event, child)` | a child is a stream resource (D2) |
| `spawn` returns the child at once | the child arrives with the `spawn` event | the runner does no I/O; the host spawns after the answer commits |
| one `ChildProcess` for the child's life | one handle per incarnation | D4 restarts a child; a handle never addresses its successor |
| `exec(command)` and `shell: true` | refused | a shell line runs any program, which no grant could bound (D7) |
| `fork`, an `ipc` channel, extra `stdio` slots, `detached`, `unref()`, `uid`, `gid` | refused | §5 |
| `stdio` entries other than `"pipe"` and `"ignore"` | refused, except a stdin file (`exactStdinFrom`) | an app has no terminal to inherit, and its own descriptors are the executor's |
| `util.promisify(execFile)` | `execFile` returns a promise, cancelled by Node's `signal` option | LLP 1133 D6: TypeScript gets the Promise form |
| a `.bat` or `.cmd` file on Windows | refused: `path:` finds only `.exe` and `.com`, and a batch file is run by naming `cmd.exe` itself | `CreateProcessW` runs no batch file without `cmd.exe`, which runs any command line ([Node](https://nodejs.org/api/child_process.html#spawning-bat-and-cmd-files-on-windows)) |
| `child.kill()` on Windows | the same, said: `SIGTERM`, `SIGINT`, `SIGQUIT` and `SIGKILL` terminate; others are `NotSupportedError` | Windows has no signals ([Node](https://nodejs.org/api/child_process.html#subprocesskillsignal)) |

### D2 — A child process is a stream resource

```ts
import { spawn } from "@exact/child-process";

let tail = "";   // the server's last output, for a failure report

export function answer(source: string, args: unknown[], store: Store, storage: Storage) {
  if (source === "server") {
    const [runtime, port] = args as [string, number];
    return spawn(runtime, ["--bootstrap-fd", "0"], {
      env: serverEnvironment(),
      encoding: "utf8",
      exactStream(event, child) {
        // the envelope holds the bootstrap secret: built here, never a resource argument
        if (event.type === "spawn") { child.write(envelope(port, store) + "\n"); child.end(); }
        if (event.type === "stdout" || event.type === "stderr") tail = (tail + event.data).slice(-65536);
        return { phase: event.type, pid: child.pid, exitCode: child.exitCode };
      },
    });
  }
}
```

- **Lifetime is the resource's.** The host spawns when the answer commits
  and the child lives while the resource is held. New arguments,
  `refresh`, or the resource leaving the plan release it (LLP 1016.000
  D2). A child the app keeps for its whole run is a resource the root
  view reads.
- **Events,** each mapped in order, none coalesced, as a socket's frames
  are (LLP 1016.000 D7):
  - `{type: "spawn", pid, restarts}`: once per incarnation, with that
    incarnation's handle;
  - `{type: "stdout" | "stderr", data}`: a chunk as the pipe gave it, at
    most 64 KiB, a string under `encoding: "utf8"` (decoded across chunk
    boundaries), otherwise an `ArrayBuffer`. Chunks are not lines; a
    mapper that needs lines keeps the remainder. The two pipes' chunks
    arrive in the order the host read them, which is all a reader of two
    pipes can know;
  - `{type: "exit", code, signal}`: the child has exited; one of the two
    is `null`, as Node's `exit` gives them. Output may still follow, from
    the pipes' buffers or from descendants that hold them;
  - `{type: "close", code, signal, drained}`: both pipes have reached end
    of file, or `exactDrainTimeout` milliseconds (default 5000, the
    clone's) passed after `exit` and the host closed them (`drained:
    false`). The utf8 decoders are flushed into a last chunk before it.
    The incarnation ends here: the stream ends, or D4 restarts;
  - `{type: "drain"}`: stdin's queue, which had passed its high-water
    mark, has been written out (below);
  - `{type: "error", kind, message}`: the program could not be started
    (`NotFound` for `ENOENT`, `Refused` outside the grants or for the
    caller's origin, `Unsupported` where the module is absent), or the
    stream failed. It ends the stream.
- **Writing stdin.** `child.write(string | ArrayBuffer | ArrayBufferView)`
  and `child.end()` follow `socket.send` and `socket.close`: the mapper may
  write while it answers any event before `close`; a mutation, and an
  answer in flight of the same module, may write on a kept handle; bytes
  are copied at the call, staged with the commit, and sent only if it
  stands; D7's bounds hold per mapper call, per mutation and per answer
  over all its turns (256 operations, 1 MiB), and `QuotaExceededError`
  past them; `InvalidStateError` after `end`, after `close`, after
  release, or on a handle whose incarnation has ended. A child spawned
  with `stdio[0]: "ignore"` has no stdin and its `write` refuses. Each
  write, end and kill carries the origin of the turn that made it, and is
  admitted by D13's rule as a spawn is.
- **Flow control.** The host keeps a queue of at most 1 MiB per child for
  stdin. `child.writableLength` is that queue's length as the turn began
  plus what this turn has staged, as D7's `bufferedAmount` is. `write`
  returns `false` when the queue is past 64 KiB, Node's signal to wait
  ([`writable.write`](https://nodejs.org/api/stream.html#writablewritechunk-encoding-callback)),
  and a `drain` event follows when the host has written it out; a write
  that would pass 1 MiB throws `QuotaExceededError`. A mapper feeds a
  child megabytes by writing on each `drain`; a file as stdin is
  `exactStdinFrom: "app:/…"` (or `home:`), read by the host under
  `fs.read`, as `fetch`'s `exactBodyFrom` is.
- **Reading has backpressure.** Unlike a server's frames, a pipe can wait:
  when the stream's receive queue holds 256 chunks or 1 MiB, the host stops
  reading the child's pipes, and the child blocks on its next write until
  the runner catches up. Nothing is dropped and the stream does not fail.
- **Release** (the resource let go, or app quit): the host sends
  `killSignal` (default `SIGTERM`) to the child's process group, then
  `SIGKILL` to it after `exactForceKillAfter` milliseconds (default 5000,
  the reference's and the clone's grace; 0 sends `SIGKILL` at once). The
  escalation belongs to the group, not to the leader: it goes ahead after
  the leader has exited, while any member remains, which POSIX makes safe
  because a process group's ID is not reused while the group exists
  ([`setpgid`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/setpgid.html)).
  At app quit every group is signalled at once and escalated at its grace
  or 5 s, whichever is shorter, so a quit waits at most 5 s. A released
  child's later output is dropped and its mapper is not called again, as a
  forgotten ticket's messages are dropped (`runner/src/runner/commit.rs`).
  A group still alive when its incarnation closes (the leader exited,
  members kept the pipes past the drain) is released the same way before a
  restart or the stream's end.
- **Signalling is not release.** `child.kill(signal)` sends one signal to
  the incarnation's process group and nothing else: no escalation, and the
  resource is still held, so the mapper sees `exit` and `close` if the
  signal ends it. It takes `SIGTERM`, `SIGINT`, `SIGHUP`, `SIGQUIT`,
  `SIGUSR1`, `SIGUSR2`, `SIGSTOP`, `SIGCONT` and `SIGKILL`. A kill is staged
  with the commit like a write, addressed to its incarnation, and refused
  on an ended one.
- **The options:** `cwd` (a `home:`, `app:` or absolute path; default
  `home:/`; D6), `env` (the child's whole environment, as Node's replaces
  it; omitted, the app's own environment), `stdio` (each of the three
  `"pipe"` or `"ignore"`; default all `"pipe"`), `exactStdinFrom`,
  `encoding` (`"utf8"` or `"buffer"`, the default), `killSignal`,
  `exactForceKillAfter`, `exactDrainTimeout`, and D4's two.
- **State and journal.** `state.streams` lists each child as it lists a
  socket, with `kind: "process"`, the grant line that admitted it, the
  program as its line names it, its pid and incarnation, bytes each way,
  restarts, its exit and whether it drained. The journal records spawn,
  exit, close, kill and release, never arguments or environment values,
  which may carry tokens.

### D3 — A one-shot run: `execFile`

```ts
import { execFile } from "@exact/child-process";
const { stdout } = await execFile("path:tailscale", ["status", "--json"], { timeout: 1500, encoding: "utf8" });
```

`execFile(file, args, {cwd, env, input, exactStdinFrom, timeout,
maxBuffer, encoding, killSignal, signal})` answers `{stdout, stderr, code,
signal}` once the child has closed (D2's `close`). It is a step of an
answer, as a `fetch` is, so a resource or a mutation may await it and keep
its context (LLP 1133.002 D14).

- **Node's rules:** a non-zero exit, a signal, a timeout or output past
  `maxBuffer` (default 1 MiB, Node's) rejects with an error that carries
  `code`, `signal`, `stdout` and `stderr`; a timeout kills the group with
  `killSignal`, then `SIGKILL` after 5 s.
- **`input`** (a string or bytes, at most 16 MiB) is written to stdin,
  which is then closed: `execFileSync`'s option, added to the asynchronous
  form, since the clone's remote launch writes a script to `ssh`'s stdin.
  Without it or `exactStdinFrom`, stdin is empty.
- **The timeout is the host's,** as `fetch`'s `exactTimeout` is: data code
  has no timers (`AbortSignal.timeout()` refuses).
- **Cancelling.** `signal` takes an `AbortSignal`, as Node's does: aborting
  releases the child as D2 does and rejects with `AbortError`. An answer
  the runner lets go aborts its own `execFile` calls the same way.

### D4 — A kept service: restart and readiness as `spawn` options

```ts
return spawn(runtime, ["--bootstrap-fd", "0"], {
  env: serverEnvironment(),
  exactRestart: { when: "always", delay: 500, maxDelay: 10000, preventExitStatus: [78] },
  exactReady: { url: `http://127.0.0.1:${port}/.well-known/t3/environment`, interval: 100, timeout: 60000 },
  exactStream(event, child) { … },
});
```

- **`exactRestart`** starts a new incarnation after `close`, while the
  resource is held: `when` is `"on-failure"` (a non-zero code, or a signal
  the app did not send with `kill`) or `"always"`; the n-th consecutive
  restart waits min(`delay` × 2ⁿ, `maxDelay`) milliseconds; an exit code in
  `preventExitStatus` ends the stream instead. The names follow systemd's
  `Restart=`, `RestartSec=`, `RestartMaxDelaySec=` and
  `RestartPreventExitStatus=`, in milliseconds; the doubling is the
  clone's and the reference's, where systemd interpolates over
  `RestartSteps=`. Release never restarts. The clone restarts every
  unexpected exit, a zero exit included, except 78, so it takes
  `"always"`.
- **Each incarnation** begins with its own `spawn` event and its own
  handle, so the mapper writes the bootstrap envelope again. The host
  addresses every staged write, end and kill to its incarnation (the
  ticket and the incarnation's number), and refuses one whose incarnation
  has ended; a new incarnation's stdin starts open and empty. Readiness
  probes and the release's escalation belong to the incarnation that
  started them and stop with it.
- **`exactReady`** polls `GET url` every `interval` milliseconds, each
  probe with a 1 s limit, until an answer whose status `accept` admits
  (default `[200, 299]`; the tunnel's is `[100, 499]`), then emits
  `{type: "ready"}` and resets n. If `timeout` passes first, `onTimeout`
  says what happens: `"retry"` (the default) emits `{type:
  "ready-timeout"}` and starts another round, as the clone's server does;
  `"fail"` emits it, releases the incarnation as D2 does and ends the
  stream with `error` of kind `Timeout`, as the clone's tunnel does. The
  URL is admitted by the app's `net.fetch` grants, like any fetch; a
  loopback URL needs `net.fetch http://127.0.0.1` or `net.fetch http:`.
- **No timers in data code.** The clone's two loops become two options.
  Choosing the port and writing the envelope stay the app's.

A service lives as long as the resource that answers it, so it needs no
second lifetime: LLP 1016.000 D2 rejected explicit `open` and `close` for
the same reason.

### D5 — The login shell's environment

A GUI app on macOS starts with launchd's short `PATH`
(`/usr/bin:/bin:/usr/sbin:/sbin`), not the one the person's shell builds,
so `tailscale`, `node` or Homebrew's tools are not found. Electron apps read
the login shell's environment for this, as T3 Code does.

```ts
import { loginShellEnvironment, appEnvironment } from "@exact/child-process";
const login = await loginShellEnvironment();   // { PATH: "/opt/homebrew/bin:…", SSH_AUTH_SOCK: "…" }
```

- **What it answers:** the variables the app's grants name with
  `env.read login:<NAME>`, one line per name, from the login shell. An
  unnamed variable is absent, even if the shell sets it: a login
  environment carries the person's tokens as often as their `PATH`.
  `env.read <NAME>` keeps its meaning, the app's own environment, which
  `appEnvironment()` answers the same way, so the app can merge the two as
  the clone does.
- **How the host captures it,** once per launch, after first pixel, on the
  first call from a foreground origin (D13): `$SHELL -ilc` with a start and
  an end marker around each named variable (`printenv` between them, or
  Nushell's own form when the shell is `nu`), stdin `/dev/null`, a new
  session so that the shell has no controlling terminal, and a 5 s limit;
  then `/bin/zsh` on macOS, or `/bin/sh -l` on Linux, if `$SHELL` gave no
  `PATH`; on macOS then `launchctl getenv PATH` with 2 s; failing all,
  the app's own `PATH`. This is the clone's algorithm
  (`T3LocalShellEnvironment.swift:36-130`) moved into the host, so the
  clone's three captures become one.
- **The login shell needs no `process.spawn` line.** The host runs the
  person's own shell with a fixed command line; the app chooses neither.
- **Windows** has no login shell: a process started from Explorer already
  has the person's environment. It answers the named variables from the
  app's own environment.

### D6 — Home paths: `home:/`, and bundle paths: `bundle:/`

`home:/` names the person's home directory, as `app:/` names the app's
storage: `fs.read home:/.ssh`, `fs.write home:/.t3/userdata`,
`process.spawn home:/.t3/runtime/versions`. `storage.fs` takes `home:`
paths wherever it takes `app:` paths, and `spawn` takes them for `cwd`,
the program and `exactStdinFrom`.

- **The home directory** is `getpwuid(getuid())->pw_dir` on macOS and
  Linux (not `$HOME`, which a launcher may set) and the profile known
  folder (`FOLDERID_Profile`) on Windows.
- **Coverage is by whole names after realization,** as for any path grant
  (`GrantSet::realized_fs`): a symlink under a granted prefix that leads
  outside it is outside it. `fs.read home:/.ssh` covers
  `home:/.ssh/config` and not `home:/.ssh2`.
- **`home:/` alone is refused** (`home-grant-whole`). LLP 1069.010
  rejected "absolute paths and grants widened to `/`" because "the grant
  would stop meaning anything"; a line naming the whole home directory is
  that grant for the person's files. A line names a subtree:
  `home:/.ssh`, `home:/.t3`, `home:/Applications`.
- **Why `home:` and not that rejection's other half.** LLP 1069.010 also
  noted that such grants work "unsandboxed on the Mac and nowhere else".
  That is this module's target set: `home:` is declared on macOS, Linux and
  Windows and absent everywhere else, and a chosen document stays a `doc:`
  handle on every target.
- **`cwd` needs no line.** A child's working directory is any `home:`,
  `app:` or absolute path: the grant bounds the data code's own reads and
  writes, and a child reads what its program reads.
- **A child needs a native path.** Programs take paths as arguments
  (`ssh -F <file>`, `tar -C <dir>`), so `storage.fs.realpath` of a granted
  `home:`, `app:` or `bundle:` path answers its native absolute path, under
  the same `fs.read` line.
- **`bundle:/`** names the app's installed bundle, read only: on macOS the
  bundle's `Contents/` (`bundle:/Resources/t3-runtime`, a tree
  `host.macos.resources` copied), admitted by `fs.read bundle:/Resources/…`.
  Linux and Windows bundle no resource trees today, so a `bundle:` line is
  refused at bake there until they do.
- **Absent:** iOS, tvOS, Android and the web have no home directory an app
  may read. A grant line with `home:` builds there and its operations
  refuse with `NotSupportedError`. A sandboxed macOS build (none today
  but widgets, `host/apple/widgets.mjs`) refuses the line at bake: the
  sandbox's container is not the person's home.

### D6a — What `storage.fs` gains, by Node's names

The consumer's install, launcher and probe need operations `storage.fs`
lacks, each under the existing `fs.read` or `fs.write` line, on every
native executor (the web's `storage.fs` keeps its `app:/` records, which
have none of these):

| Operation | Name's source | Use |
|---|---|---|
| `stat(path).mode`, `lstat(path)` | Node's `Stats.mode`, `fs.lstat` | permission bits, and an entry's own metadata without following a link: the install's check of each unpacked entry. On Windows `mode` is `0o444` or `0o666` |
| `readlink(path)` | Node's `fs.readlink` | a link's target, which the install checks stays inside the runtime |
| `access(path, mode)` | Node's `fs.access` with `constants.X_OK` | whether this user may execute it, by `faccessat(…, AT_EACCESS)`, which counts ownership, ACLs and `noexec` mounts as mode bits cannot: the editor probe |
| `chmod(path, mode)` | Node's `fs.chmod` | the askpass helper's `0o700`, the launcher's `0o755`; on Windows only the read-only bit |
| `symlink(target, path)` | Node's `fs.symlink` | the launcher's link into a granted directory such as `/usr/local/bin` |
| `flock(path)` | POSIX `flock(2)`, a declared deviation (Node has none) | an exclusive advisory lock on a file, created if absent and left on disk, held until `unlock()` or the end of the answer that took it, with a `timeout`: the same lock the clone and T3 Code take on `.install.lock`, so they still exclude each other; on Windows `LockFileEx` |
| `digest(path, algorithm)` | a declared deviation (Node streams a file through `crypto.createHash`) | SHA-256, -384 or -512 of a file of any size, read by the host in bounded memory: the 81 MB archive, past `readFile`'s limit (`vendor/ibex/crates/ibex2/src/stdlib/fs.rs:30`) |

### D7 — Which programs: `process.spawn` lines

Every program data code starts is named by a grant line, `process.spawn
<target>`, one target per line. The target is one of:

| Target | Example | Resolves to |
|---|---|---|
| a bundled helper | `bundle:/Helpers/t3/bin/t3` | that file under the bundle's `Contents/` on macOS; refused at bake where the host bundles no helpers |
| an absolute path | `/usr/bin/ssh`, `/usr/bin/tar` | that file |
| a home or app path, a file or a directory | `home:/.t3/runtime/versions` | any executable at or under it, by whole names, after realization |
| a name on a `PATH` | `path:ssh`, `path:tailscale` | the first executable of that name on the child's `env.PATH` when `env` is given, as Node resolves `spawn("ssh")`, else on D5's login `PATH`; on Windows the name with `.exe` or `.com` only (D1) |

- **The program in a call** is written as its line's target is
  (`spawn("path:ssh", …)`, `spawn("home:/.t3/runtime/versions/1.2.0/t3",
  …)`), so the call and the grant read alike. `execPath(target)` answers
  the native path a spawn of that target would run, or `null`, under the
  same line: the editor probe's question, asked without listing every
  `PATH` directory.
- **Arguments are free.** A grant names a program, not what it is told.
  A line naming a shell or an interpreter (`path:sh`, `path:node`,
  `/bin/zsh`) therefore admits any program, and the reach table says so,
  as it says a scheme-wide `net.fetch`. So does a program that runs
  commands it is given: `ssh -o ProxyCommand=…` runs a local command
  ([`ssh_config`](https://man.openbsd.org/ssh_config#ProxyCommand)). The
  refusal of `exec` and `shell: true` is therefore an API's shape, keeping
  the program a call starts visible in the call; it is not a boundary on
  what a granted program can be made to run.
- **Programs a child starts are the child's.** `ssh` runs the askpass
  helper it is pointed at; the T3 server starts its own workers. No line
  names them, and nothing in the module bounds them: a granted program is
  trusted as the app's own code is.
- **Why system binaries are allowed** (Q2). The consumer's programs are a
  server it unpacks into `~/.t3`, the system's `ssh` and `tar`, and
  `tailscale` wherever the person installed it. With bundled helpers only,
  the module would not serve its consumer, and an app that wants `ssh`
  would bundle its own copy, which is worse for the person: it is not the
  `ssh` their configuration and agent are written for. A desktop app
  outside the Mac App Store may already run any program from native code
  (LLP 1069.008 D3: native modules are "declared, not enforced"); the grant
  makes the data code's programs declared, enforced and visible.
- **What the line derives:** nothing in a manifest on macOS, Linux or
  Windows; a hardened-runtime child needs no entitlement to be spawned.
  A sandboxed macOS build refuses every `process.spawn` line, since a
  sandboxed app's child inherits its sandbox and could not read `~/.ssh`.
  A `process.spawn`, `home:` or `bundle:` line changes the grant ceiling,
  so the deploy classifier calls for a binary release, as a `runtime.*`
  line does.

### D8 — A secret field: `input type="password" secret=`

```
input type="password" secret="ssh.password" autocomplete="current-password" submit=answer("submit")
```

- **Where the text lives.** Each edit goes to the held secret
  `ssh.password`, which the app's grants name with `secret.hold
  ssh.password`. A held secret is volatile: the runner keeps it apart from
  the store's durable values, so it is never a `StoreWrite`, never in
  `snapshot` or a reload's carry, never in `localStorage` on the web, the
  journal, the agent's `state`, or a crash report; it is gone when the app
  exits. A name is either kept or held: both lines for one name are
  refused at bake (`secret-name-twice`). A source's grant scope narrows
  held names as it narrows kept ones.
- **What Contract sees.** No event or read carries the field's text:

  | Channel | In a secret field |
  |---|---|
  | `input`, `change`, `select` (`InputEvent`) | `value` is `""` and `data` is `none`; a new field, `length`, is the text's length in UTF-16 units; the selection's offsets stay |
  | `selectionchange` | offsets only; the text it carries today (`host/web-js/rt.js:958`, `host/apple/Sources/ExactKit/FieldSelections.swift:347`) is `""` |
  | `beforeinput` | `data` is `none` and the prior value `""`; it may still be cancelled |
  | IME composition | the same as `beforeinput`; marked text stays in the platform's field |
  | `paste`, `copy`, `cut` | the clipboard's text is not read into the event; copy and cut do nothing, as a platform's secure field does |
  | `keydown`, `keyup`, `keycapture`, on the field or any ancestor | a printable key arrives as `key: "Unidentified"` with its `code` withheld; Enter, Escape, Tab, arrows, Backspace, Delete and modifiers arrive as themselves |
  | `bind=`, `value=` | refused beside `secret=` (`secret-field-bound`): there is no Contract value |
  | `setRangeText` on the field | refused (`secret-field-written`): only the person writes it |
  | the agent's `tree`, `layout`, `type` reply | `•••`, as for any password field |

- **How data code receives it.** Main-thread native TypeScript reads the
  store through its door (`js/src/door.rs:32`). The other callers receive
  a source's secrets in a snapshot built per call (the module ABI,
  `logic/abi/src/lib.rs:115-125`; the web's wasm and worker dispatch,
  `js/web/src/lib.rs:671`); held secrets travel there in a separate
  volatile field of the call, only the names the source's grant scope
  holds, and the executor drops them when the call returns. They are never
  written into the durable snapshot that a reload carries.
- **What data code does.** A mutation the submit runs reads
  `store.get("ssh.password")` and passes it on (to the child's environment
  for `SSH_ASKPASS`, to stdin, to a `fetch` body) and calls
  `store.forget("ssh.password")`; when that commit stands, the host empties
  the field. `store.set` on a held name is refused: only the person writes
  it.
- **The agent** types into it as into any password field (`type
  ssh-password-field "…"`); `state.secrets` shows `ssh.password: held, 9
  characters`, never the text.
- **Every host with a password field implements it:** web, macOS, iOS,
  Linux, and Android and Windows as their text fields arrive. On the web
  the page's glue holds the text in memory, outside the module realm, and
  the data module's `store.get` reads it from there.
- **Askpass, fully below data code,** is left out (§11): a host-supplied
  `SSH_ASKPASS` helper that reads a held secret over a pipe would keep the
  password out of the child's environment too. The reference and the clone
  both pass it in the environment, which other processes of the same user
  can read (`ps -E` on macOS, `/proc/<pid>/environ` on Linux); D8 keeps
  the clone's behaviour and moves the field out of app Swift.

### D9 — Unsaid defaults are the platform's

How the child starts, per platform. Rust's `std::process::Command` does
not give all of these (it neither closes descriptors other libraries left
inheritable nor resets every signal's disposition), so the transport
spawns through the platform's call directly.

| Default | macOS | Linux | Windows | Why |
|---|---|---|---|---|
| The call | `posix_spawn` | `fork` and `execve`, with the steps below between them | `CreateProcessW` | |
| Process group | `POSIX_SPAWN_SETPGROUP`, its own group; D5's shell `POSIX_SPAWN_SETSID` | `setpgid(0, 0)`; D5's shell `setsid` | a job object per child | a signal to the group reaches what the child starts |
| Descriptors | only 0, 1, 2 (`POSIX_SPAWN_CLOEXEC_DEFAULT`) | `close_range(3, ~0U, 0)`, falling back to closing each of `/proc/self/fd` | an explicit list, `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` | some libraries open descriptors without close-on-exec; the app's sockets and files stay its own |
| Signals | `POSIX_SPAWN_SETSIGDEF` for every signal, `POSIX_SPAWN_SETSIGMASK` empty | every disposition `SIG_DFL`, mask empty | — | an ignored signal survives `exec`; the app's choices do not leak |
| Console | — | — | `CREATE_NO_WINDOW` | a GUI app's child flashes no console |
| `cwd` | `home:/` | `home:/` | `home:/` | a Terminal starts there; the bundle is read-only |
| At app quit | every child released as in D2, the quit waiting at most 5 s (the clone waits 5.5 s) | the same | the same, the job closed | |
| After a crash | the host records each child's process group, the leader's start time and the boot's identity (`kern.boottime`) in app storage; at the next launch, in the same boot, it signals the group's members (`proc_listpgrppids`) whose start time is not before the leader's (the clone's pid file, moved and widened to the group) | the same record (boot from `/proc/sys/kernel/random/boot_id`, members from `/proc`), plus `PR_SET_PDEATHSIG(SIGKILL)` in the child, which then checks that `getppid()` is still the spawner and exits if not; spawning happens on one long-lived executor thread, since the signal follows the thread that forked | `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, which ends every process in the job | |

**The cleanup boundary.** Release and crash cleanup reach the child and
what is in its process group, or on Windows its job, whether or not the
leader is still alive. A descendant that starts its own session or group
(a daemonizing program) has left it on purpose and is not reached. Linux's
death signal reaches the child only, so after a crash the rest of the
group waits for the next launch's check on Linux, as on macOS; a group
whose members all started before its recorded leader, or in another boot,
is not the app's and is left alone.

## 4. Packaging and callers

### D12 — exact2's vocabulary, imported from `@exact/child-process`

LLP 1133 D5's default is a host extension. This module is exact2's
vocabulary, a data capability like `fetch`, for two reasons:

1. **The stream is the executor's.** A child's ordered output with stdin
   writes staged per commit is LLP 1016.000 D7's machinery, which lives in
   the runner and the executor. An extension answers through the native
   slot, which has no ordered events (LLP 1124 §5 refuses value streams;
   LLP 1133 D6 rule 7), and the executor refuses a native stream
   (`executor_core.rs:1099-1106`).
2. **One Rust implementation for three hosts.** `ibex2` is already the
   executor on macOS, Linux and Windows, with grants parsed and checked in
   one place. Linux and Windows have no module slot an extension could load
   into (LLP 1124 D6's `Extension` trait is not built).

**The route,** one per call, from every caller:

- **The declaration.** `packages/child-process/exact.json` is an interface
  (`kind: "interface"`) whose names are `spawn` (a stream), `execFile`,
  `execPath`, `loginShellEnvironment`, `appEnvironment` and the
  `processStatus` fact, with their option and event shapes and their grants,
  and whose implementation on `macos`, `linux` and `windows` is
  `"executor"` rather than a package; none elsewhere. The bake's binding
  table names implementations for Apple, Android and the web only
  (`js/bake/src/typescript.mjs:968-1002`); stage 0 adds the executor kind.
- **The binding.** For an executor implementation, the generated module
  re-exports the prelude's own functions, as `fetch` is the prelude's; it
  does not serialize a call into a native body. On a target with no
  implementation every function rejects `NotSupportedError` and
  `processStatus().available` is false.
- **The request.** `spawn` and `execFile` build a process request, a new
  optional kind of `Request` beside `storage` and `surface`: the program as
  written, its arguments, environment, cwd, stdio, encoding, the kill,
  drain, restart and readiness options, and whether it is a stream. A
  `spawn` is returned as the answer (`Answer::stream`); an `execFile` is a
  step the answer awaits. Staged writes, ends and kills ride `SocketSend`'s
  path with a process operation addressed by (ticket, incarnation).
- **Admission,** in the executor before anything starts, as it admits a
  fetch: the program against the `process.spawn` lines of the source's
  grant scope (`Request::grants`, which may only narrow the app's), paths
  against `fs.*`, the readiness URL against `net.fetch`; then the origin
  rule (D13); then, under the agent, the substitute (§7). A refusal is a
  failed answer naming the line it needed.
- **Release** is the forget path a stream already has: a forgotten ticket
  is released at the host, which runs D2's sequence.

So the bake finds module use the way it finds geolocation's, refuses a call
without its grant (`grant-missing`), types the binding, links the process
transport only into apps that import it (LLP 1047.001), and binds the
absent answer on every other target. A Contract app reaches a child only
through the resource its data code answers; the module has no Contract
names, as `fetch` has none.

### D13 — Callers and origins

| Name | Caller | Request (LLP 1069.007 D1)? | `sync`? |
|---|---|---|---|
| `spawn` | a resource's answer (a stream) | no | no |
| `execFile`, `execPath` | any answer's step | no | no |
| `loginShellEnvironment`, `appEnvironment` | any answer's step | no | no |
| `processStatus` | a fact, on every target: `{available, state}` | no | yes, where the host has `call` |
| `secret=` | a Contract attribute | no | — |

**Origins.** Starting a program opens no system UI itself, but what the
program does may: it may touch a location the system guards (§6) or open a
window of its own, with arguments the grant does not bound. LLP 1133 D6
rule 3 lets no tool invocation (LLP 1111), wake or headless session open
system UI, and the module cannot tell in advance what a child will do, so
it holds the line wherever the app's code directs a child: `spawn`,
`execFile`, a first capture of the login environment, and every write,
end and kill on a running child from a tool, wake or headless origin fail
`person-required` (Q8). A mapper's turn has the origin of the turn that
spawned the child, and an answer in flight keeps its own (LLP 1133.002
D14). A child already running keeps running whatever origin later reads
its resource, and `execPath`, `appEnvironment` and an already captured
login environment answer any origin. Every call and operation carries its
origin to the journal.

**Rust sources** get `execFile`, `execPath` and the environment reads as
typed requests in `exact_data`, as `fetch` has them, and `spawn` as a
receive-only stream until Rust sources get D7's send path, a gap shared
with WebSockets (`docs/reference.md`, "Remaining host gap").

## 5. The ceiling test

Common uses of a child process in desktop apps, by Node's API and the
platforms' (`Process`, `posix_spawn`, `CreateProcessW`), and the tier that
reaches each:

| Use | Tier |
|---|---|
| start a program with arguments, environment, cwd | 1 (`spawn`, `execFile`) |
| stream its output; know when output is complete | 1 (`stdout`, `stderr`, `close`) |

## 6. Permission and grant

There is no platform prompt to start a program on any desktop: the grant
is the whole permission (LLP 1069.008 D8, Linux's rule, holds on all
three). The module's permission fact, `processStatus()`, is LLP 1133 D7's
in its shape and says so: `state` is `granted` where the module is
available and the app has at least one `process.spawn` line, `denied`
where it is available and has none, and `unknown` where it is absent;
there is never a `prompt`, since nothing asks. An ungranted call fails
`Refused` naming the line it needed. Grant lines:

| Line | Admits |
|---|---|
| `process.spawn <target>` | starting that program, and `execPath` of it (D7) |
| `fs.read home:/…`, `fs.write home:/…` | `storage.fs` under that home path, never the whole home directory (D6) |
| `fs.read bundle:/…` | reading under the app's bundle (D6) |
| `env.read login:<NAME>` | one variable of the login shell's environment (D5) |
| `secret.hold <name>` | a field's held secret, and `store.get` and `forget` of it (D8) |

The reach table lists every line; a production build's `exact release`
prints the `process.spawn` targets beside the hardened-runtime ones.

What a child does is still subject to the platform's own permissions, and
they are the app's: macOS attributes a child's access to a protected
location (Desktop, Documents, a removable volume) to the app that started
it, its responsible process, so the system's prompt names the app and the
grant the person gives is the app's. The module adds nothing to that
prompt and answers none of it (LLP 1133.002 D12); D13's origin rule is
what keeps a tool from causing it.

## 7. The substitute

- **Nothing runs unless the drive says so.** Under the agent a spawn or
  `execFile` fails `Refused`, naming the launch flag below, until the
  drive says what its target is. A real child cannot be isolated from the
  person's files by anything the framework remaps: OpenSSH finds `~/.ssh`
  from the password database, not from `HOME`
  ([`ssh.c`](https://github.com/openssh/openssh-portable/blob/master/ssh.c)),
  and a program the app owns may start such a program itself (D7). So the
  drive's flag is the only thing that lets a real program run, and the
  drive that gives it accepts what that program touches. LLP 1069.007 D6
  answers a socket with "a local server the smoke starts"; a child is
  answered the same way, by the drive.
- **Launch flags,** no new agent operation (LLP 1133 §7):
  - `--process <target>=<file>` runs that executable instead, with the same
    arguments, environment and pipes (the clone's `T3_SSH_COMMAND` double);
  - `--process <target>=script:<file.json>` answers from a script with no
    process at all: chunks on `stdout` and `stderr`, reads of stdin, an
    exit code or signal, a pipe left open after exit, at times on the
    agent's clock. Stage 0 drives with it before the transport exists;
  - `--process <target>=real` runs the program itself, and `--process
    all=real` every target.
  `state.streams` names what ran for each child.
- **The clock.** Under the agent, D4's restart delays, readiness intervals
  and timeouts, D2's drain and kill escalation, and `execFile`'s timeout
  run on the agent's clock: `clock +500` advances them and `clock settle`
  runs them to rest. A readiness probe against a scripted child answers
  from the script; against a real one, it is a real `fetch`. `clock
  settle` does not wait on a child after its `spawn` event, as it does not
  wait on an open stream after its first message (LLP 1016.000 D5).
- **`loginShellEnvironment`** answers the drive's `--login-env
  NAME=value` lines, or the app's own environment for the named variables
  when none is given, so a drive never runs the person's shell.
- **`home:`** is a scratch directory the drive names (`--home <dir>`),
  empty by default, for the data code's own reads and writes (the clone's
  `T3_SSH_HOME` and `T3_LOCAL_HOME`). It does not isolate a real child.
- **A production bake** reaches none of it.

## 9. Security

- **What a grant bounds:** which programs data code starts, and which home
  and bundle paths it reads and writes. It does not bound arguments (D7)
  or what the program does: a granted `ssh` connects anywhere the person's
  configuration lets it, and runs a local command if told to
  (`ProxyCommand`). A `process.spawn` line is trust in a program, as a
  native module is trust in code.
- **Who can call:** only the app's own data code, and only from a
  foreground origin, for a spawn and for every operation on a child
  (D13). A reply from a server (a `fetch` answer, a
  socket frame) reaches `spawn` only through the app's code, which chooses
  the program from its granted lines.
- **What never leaves the executor:** environment values and arguments are
  not journalled (D2); a held secret is in no event, state, snapshot or
  storage (D8).
- **Distribution:** a Mac App Store build is sandboxed and refuses every
  line of this module at bake (D6, D7). Developer ID builds, the only kind
  exact2 ships for macOS today, are not sandboxed.

## 12. Rulings (Daehyeon Mun, 2026-10-23)

Each question below was ruled as proposed.

1. **Packaging** (D12). (a) exact2's vocabulary, a process request in the
   executor, with names imported from `@exact/child-process`
   (recommended). (b) A host extension with a Rust implementation: data
   code can already send it request bytes (`native.later`,
   `js/src/prelude.js:1257-1263`), but it would need ordered events with
   staged writes, which the extension seam does not have, and a module
   slot on Linux and Windows. (c) The names imported from
   `node:child_process`: more familiar, but it promises Node's
   `EventEmitter` and streams, which an author would write and the bake
   would have to refuse.
   **Ruled: (a).** The module needs ordered events and staged writes,
   which the extension seam lacks, and (c) promises Node's streams, which
   the bake would have to refuse.
2. **Which programs** (D7). (a) Bundled helpers only: the consumer cannot
   use it (its server lives in `~/.t3`, and it needs the system's `ssh`).
   (b) Helpers and absolute paths. (c) (b) plus `home:` and `app:` paths
   and names on a `PATH`, one line per program (recommended): what the
   consumer runs, each line in the reach table. Under each option a
   granted program can run others (a shell, `ssh`'s `ProxyCommand`), so the
   choice is which programs the app is trusted to name, not a sandbox.
   **Ruled: (c).** The consumer runs `~/.t3`'s server and the system's
   `ssh`; a grant is trust in a program, not a sandbox.
3. **Supervision** (D4). (a) `spawn` options, the service living with its
   resource (recommended). (b) An `app.json` `services` list: the program,
   restart and readiness in the manifest, started when the app's code asks
   with the arguments it chooses. It reads well for a fixed service, but
   splits one child's description between the manifest and the code, and
   still needs a lifetime, which a resource already has.
   **Ruled: (a).** One child is described in one place, and the resource
   gives it a lifetime.
4. **The login environment** (D5). (a) Named variables only, `env.read
   login:<NAME>` (recommended). (b) The whole environment under one line.
   **Ruled: (a),** least privilege; the clone names 20 variables.
5. **The secret field** (D8). (a) `input type="password" secret=<name>`
   with a volatile `secret.hold` and the redaction table (recommended).
   (b) The field's text travels with its `submit` event to a mutation as a
   redacted argument: no new store tier, but a value class Contract does
   not have, and the other channels need the same redaction. (c) No field:
   the text stays in state, as the reference keeps it in React state.
   **Ruled: (a).** LLP 1018 D5 keeps credentials out of the plan, which
   (c) breaks, and nobody using the app sees the difference. The field
   lands on every host with a password field. Stage 2's drive proves r2 #4
   (§10).
6. **Scope of this ruling:** stages 0 to 2 on macOS and Linux, and the
   field also on the web and iOS; Windows in stage 3 when it can be
   driven. Recommended: yes. **Ruled: yes.** Linux is provisional with no
   consumer (Q9).
7. **The `rules/DEFERRED.md` record.** Nothing refuses processes by name,
   so this admits a capability rather than reversing a refusal. No take is
   offered; this asks for a waiver (`rules/RULES.md`, Scope). Proposed
   text: "**Admitted** (<ruler>, <date>, waived; LLP 1133.007): desktop
   processes (`spawn`, `execFile`, supervision, the login environment) and
   `home:` and `bundle:` paths on macOS, Linux and Windows, absent
   elsewhere; a password field's held secret on every host with the field.
   Consumer: the T3 Code clone's local server and SSH environments. Still
   refused: a pseudo-terminal, shell command lines, daemons that outlive
   the app, and processes on iOS, Android and the web." **Ruled: the
   take is waived** (Daehyeon Mun, 2026-10-23): nothing refuses processes
   by name, no doing-list item is in this area, and the change retires app
   Swift. `rules/DEFERRED.md` records the admission in the proposed text,
   under "Features carried over as no".
8. **Origins** (D13). (a) A tool, wake or headless origin may neither
   start a program nor write to, end or signal a running one
   (recommended): it keeps LLP 1133 D6 rule 3 without the module having to
   know what a child will show. (b) Allow it, amending rule 3 for indirect
   effects: an agent driving the app as a tool could then start the server
   itself or send a running shell a command, at the cost of a tool being
   able to cause a system prompt through a child.
   **Ruled: (a).** It keeps LLP 1133 D6 rule 3 intact. Stage 1's drive
   proves the origin is checked on every write, end and kill (r2 #2, §10).
9. **Acceptance per target** (LLP 1133 D9 item 11). macOS is accepted on
   the T3 Code clone's drive; Linux, which no consumer builds, is built

## 14. Cost

An app that does not import the module links none of it: the process
transport is a module of `ibex2` reached only from the binding (LLP
1047.001), and no grant line derives anything. An app that does adds the
transport's code and nothing before first pixel: the login shell is
captured on the first call, after first pixel. The size is pending
measurement: an estimate before stage 1 is 1,000 to 1,500 lines of Rust
shared by three hosts and 100 to 200 per host for quit and crash handling;
stage 1 measures the binary cost with LLP 1047's probe and records it here
before acceptance (LLP 1133 D9 item 10).
