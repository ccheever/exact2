## 0. Summary

Compose Material 3 is the reference 1115.001 D1 names, and an Android app's "native widgets" are a library's either
way: the operating system ships no Material 3 control. So the components that are expensive to paint well are
shown by that library, as islands over the painted page, and the rest stay painted. A date or time control is the
first: its press opens Material 3's `DatePickerDialog` or `TimePickerDialog`, and its answer is the control's value.
Compose is linked only into an app whose plan has such a control, so an app without one pays nothing.

Access hatches run on the Canvas host for the first time: the app's Rust ones (`modules/linux`, stage 6's), and
Kotlin ones beside them (`modules/android`), which hear the same moments, act on nodes by number, reach a node's
platform view where it has one (a text field's `EditText`), and set what a date or time control's picker offers, or
replace it.

## 1. What was measured

runs `verify` (no profile); a store install runs about as `speed-profile` with the library's baseline profile.

**Which library** (Caltrain, an island opened 1.5 s after launch, timed to the frame after its first draw; 15 cold
starts interleaved, five launches of three shows each):

| | none | Compose Material 3 (BOM 2026.09.00) | Material Components 1.14 (Views) |
|---|---|---|---|
| cold start (`am start -W` median) | 184–186 ms | 179–182 ms | 179–180 ms |
| APK, resources shrunk | 23.08 MB | 25.31 MB | 25.16 MB |
| PSS, no island shown | 68–70 MB | 72–77 MB | 73–74 MB |
| PSS after a first date dialog | 75 MB (framework's) | 84 MB | 91 MB |
| date dialog, verify (first, repeats) | 51, 57–62 ms (framework's) | 140, 111 ms | 110, 102–118 ms |
| date dialog, speed-profile (first, repeats) | 48, 58–66 ms (framework's) | 74, 79–83 ms | 103, 103–109 ms |
| an inline bar, speed-profile (first, repeats) | | 34, 19 ms | 39, 20–22 ms |

Material Components needs AppCompat's view inflater: its picker's layouts declare `<Button>` and `TextView` and are
right only as `MaterialButton` and `MaterialTextView`. In a plain `Activity` its colours resolve to
`ColorStateList`'s magenta fallback and its header overlaps its title, until a delegate's view factory is installed
(`AppCompatDelegate.create(…).installViewFactory()`). It is no cheaper, its picker is slower in both compile states
(inflation, not code: its baseline profile is 1.6 KB), and it asks for AppCompat. Compose asks for a lifecycle owner.

**On the path built here** (the fixture's Detail screen; a real touch, timed from the touch to the frame after the
picker's first draw, `x_log_requests=1`; five launches, each showing the date picker three times, then the time
picker; 15 cold starts interleaved; medians, with the range of five):

| | Compose Material 3 | the framework's dialogs |
|---|---|---|
| APK | 26.03 MB (dex 2.34 MB) | 23.47 MB (dex 0.33 MB) |
| cold start, verify | 181 ms (quartiles 171–189) | 178 ms (174–182) |
| cold start, speed-profile | 187 ms (172–189) | 176 ms (171–179) |
| date picker, verify: first, second, third | 138 (134–162), 109, 88 ms | 89 (76–136), 59, 56 ms |
| date picker, speed-profile: first, second, third | 94 (72–122), 79, 88 ms | 93 (76–105), 68, 62 ms |
| time picker after the dates, verify / speed-profile | 66 / 88 ms | 115 / 126 ms |
| PSS on Detail, then after the four pickers (speed-profile) | 73.3, then 93.2 MB | 66.4, then 83.2 MB |

With its profile, Material 3's first date picker shows as soon as the framework's does, after a touch, and its later
ones within about 20 ms of it; its time picker is faster than the framework's. Unprofiled, its first is about 50 ms
slower. The cold starts' quartiles overlap. The touch reaches the reader's request in about 11 ms.

## 2. Decisions

### D1 — A date or time control opens the platform's picker (amends 1115.001 D9)

A press on an `input type="date"`, `"time"` or `"datetime-local"` that is not disabled asks the reader for its
picker through 1115.001 D5's channel: request kind 9, with the node, its kind, what it shows now (the person's
choice while the bound value is the one it was made at, else the bound value), and its `min`, `max` and `step`, each
as HTML writes it. The reader's answer is the value chosen, in HTML's form (`2026-10-23`, `09:30`,
`2026-10-23T09:30`; seconds only where `step` asks for them), and it lands as a select's row does: `input`, then
`change`. A dismissal changes nothing and is journaled (`picker: dismissed for <node>`). `datetime-local` asks for
the day, then the time, as Android apps do.

The picker is Compose Material 3's (D2), themed by the device's dynamic colours: the reference D1 names. 1115.001 D9
chose the framework's `DatePickerDialog` as "a stated exception to D1.1's library", for its cost; the cost is now
measured (§1) and is small and off the launch path, so the exception is withdrawn. The framework's dialogs remain the
fallback where Compose is not linked.

A host with no shell (desktop Linux, the headless carrier) is unchanged: the agent's `type` sets a date field.

### D2 — Compose is linked by use

`dates` joins the use set (LLP 1047 D2): a plan with a control whose `type` can be one of the three. The Android
crate's build writes the plan's uses beside it (`contract::native::android_entry`, `uses.txt`);
`agent-android.mjs` reads them from Cargo's build-script output and passes `-Pcompose=1` to the shell's Gradle,
which then applies the Compose compiler, links `androidx.compose.material3` (BOM 2026.09.00, Material 3 1.4.0) and
compiles `app/src/compose` in place of `app/src/nocompose`. Every other host links nothing for it: the web's are the
browser's, Apple's are UIKit's.

The reader's activity stays a plain `Activity`; the picker brings the lifecycle and saved-state owners Compose
looks for. Compose never runs before a press, so 1115.001 §5 Q3's rule (never on the launch path) holds by
construction.

### D3 — A picker is a hatch's to shape

A date or time control marked `hatch="word"` (a word `app.json` gives `android`) has its Kotlin hatch asked as its
picker opens: `ExactHatches.picker(element, picker)`. The hatch may set the title, open on typing rather than the
calendar or the clock (`input`), hide the mode toggle, refuse days beyond `min` and `max` (`selectable`), choose a
24-hour clock, or replace the picker with its own (`show`, called with what to answer). This is Android's form of
what an iOS hatch does to a `UIDatePicker`; the library's own object is not handed over, since a composable has no
object to hand, and the members are the ones Material's pickers take.

### D4 — Kotlin hatches beside the Rust ones (answers 1075.003.000.001 §10 Q4 for the Canvas host)

An app's `modules/android` may hold Kotlin: one `class exact.app.Hatches : ExactHatches()`, compiled into the APK,
made by name the first time a moment is told (after first pixel), and called on the main thread. It hears the
moments a Rust hatch hears, for the same words (`app.json`'s for `android`): `app` (built, and changed when a root
`data-*` word changes), `element` (built, and changed when its `data-*` words or its box's size change),
`elementEnded`. Exact sends them as request kind 10 after each turn, from a module beside the app's Rust one
(`hatches::reader`), so the moments, their order and `EXACT_HATCHES=off` are the presenter's, unchanged.

The handle (`ExactElement`) is a painting host's with what the reader has besides:

- `hatch`, `id`, `node`, `frame` (the document's points), `words` and `data(word)`, `isNew`, `isLive`;
- `click()`, `focus()`, `blur()`, `input(text)`: each crosses to exact2's thread by the node's number and is queued
  and run as a Rust hatch's act is (§2.5 there);
- `view`: the node's platform view where it is one. Today that is a text field's `EditText` (1115.001 D8). Every
  other node is painted and has none.

A Rust file in `modules/android` still overrides `modules/linux` for the Rust side; a directory of Kotlin alone no
longer does.

**Not given to Kotlin yet:** the overlay (a Rust hatch's), observed input, the frame clock and `after`,
diagnostics, and a view of its own at a node's box (`owns`).

### D5 — The Rust hatches run on the Canvas host

`exact_linux::canvas_jni!(Data, hatches = crate::exact_hatches())` hands the host the app's install, which
`android_entry` writes: the app's Rust hatches with the reader's told beside them, the reader's alone, or none.
They connect as the reader takes its requests after the first displayed frame (until now only a pending data module
did, so an app without one never connected them), run between turns (`hatch_turn` in the frame), and an overlay is
painted as the Canvas host paints a canvas: a picture.

## 4. Not done

- **The field is not Material's yet.** A date control is the painted field with its value in HTML's form
  (`2026-10-23T12:01`), where D9 asks for Material's filled field showing the locale's format.
- **An authored `accent-color` does not reach the picker.** The dialog takes the device's dynamic colours whatever
  the control's `accent-color` says, where LLP 1115 gives the author's word precedence. Material 3 1.4.0 has no
  public way to derive a scheme from one colour; setting only `primary` would be a partial answer.
- **The agent cannot answer a picker.** Under the agent a `tap` opens the real dialog, which the driver neither sees
  nor closes (`type` still sets the value). A held picker the agent answers, as a file input's is (LLP 1069.002
  D9), is owed.
- **D4's handle is partial** (above), and `exact.mjs hatch` writes no Kotlin stub.
- **One phone.** A Pixel, and a cold start of an app whose first screen has a date control, were not measured.
- **TalkBack in the dialog** is Compose's own and was not heard.
