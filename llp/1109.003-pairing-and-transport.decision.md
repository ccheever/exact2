## Context

[confirmed] The supplied handoff requires a mobile client of a real upstream server and reuse of Daehyeon's client. Protocol 2 is present at mobile pin `365aa87982`. Protocol agreement alone does not establish payload or lifecycle parity; the seeded server is the integration oracle.

[observed] The shared client already owns snapshot validation, subscriptions, retained-event acknowledgements, fleet routing, commands and preferences. Its native transport supplies HTTP, WebSocket RPC, route walking and Keychain. The shared module entry imports AppKit. The mobile app cannot compile that entry unchanged.

## Decision

[inferred] Keep one shared `T3Client` instance in the mobile data module, and project mobile view data from it. Do not add a second mobile reducer or credentials to Contract resource results. The root Contract owns resources and mutations. Every command refreshes the snapshot when it settles; connection status alone does not load the shell.

[observed] Gap 001 prevents parent TypeScript imports during bake. The required closure is 296 TypeScript files at adopted base `887b2491b182f851b11253655f6aa84fe2a26708`. It includes desktop presentation helpers because the client's command groups import them. Preserve every copied body with two provenance lines, and compare bodies with the adopted parent in tests. Do not trim imports inside a pinned copy. Restore direct imports when the framework can capture them.

[inferred] The app owns one native module, with transport calls and subsequent native views under the existing `ExactModule` interface. Keep the nine Foundation transport files as app-local source copies, preserving source identity and marking each mobile adaptation. This is the selected app-module layout and mobile policy adaptation, not a separate reproduction of the TypeScript-only Gap 001. The UIKit activity reporter and extracted pure pull-request error helper are additional files. Keep the remaining desktop module out of the iOS compilation. The build first queries the native view roster on macOS: guard UIKit implementations with `#if os(iOS)` and provide the same refusal-only macOS roster as the existing calendar app. The refusal roster is build discovery, not a macOS client. The UIKit module owns lifecycle observers and destroys its transports, fleet workers and activity reporter at session teardown.

## Mobile adaptations

[observed] Upstream mobile differs from the desktop clone in these concrete places:

| Concern | Mobile rule |
| --- | --- |
| Pairing input | Preserve shared hosted-link parsing, unwrap mobile QR/deep links, accept host-only input, and preserve the mobile bare-IP URL rule. |
| OAuth scopes | Request pinned mobile AuthStandardClientScopes (13 granular permissions) for credential exchange; saved-token reconnects retain their existing grant. |
| OAuth metadata | Label T3 Code Mobile; device type mobile on phone, tablet on iPad; OS iOS. |

| Writes | Mobile-created messages and threads send creationSource mobile through the adapter, without editing the shared TypeScript body. |
| SSH | Mobile presents no SSH provisioning or tunnel controls. |

[inferred] Keep these differences in narrow mobile wrappers and app-local Swift adaptations. Shared desktop behavior remains unchanged. Do not claim plain HTTP LAN pairing works: the shared endpoint policy currently rejects non-loopback plaintext routes. The simulator seed uses loopback; physical-device parity needs its own finding and verification.

## Credential and storage ownership

[observed] The native credential store has two modes: persistent Keychain in ordinary launches, in-memory credentials for agent sessions. The shared `nativeFiles` adapter admits only its designated preferences file. Preserve those boundaries. A saved environment row exposes identity, display address and status, not its access/refresh tokens. Logs and screenshots must not publish pairing secrets.

[observed] The pinned server rejects one-use pairing on its required Node version because its SQLite call binds a boolean. Supported development authentication works against the same three seeded databases. Label that oracle evidence accurately. Ordinary pairing against the later official nightly is separately verified below; this does not resolve the pinned server's failure. The two apps share server data, not credential storage. Prove reconnect and remove independently: removing a saved environment must also drop its credential and stream ownership.

[observed] Targeted Add route uses the existing shared environment-route-add operation, including its expectedEnvironmentId check before token exchange. A background environment's Retry uses its own fleet transport; the shared focused reconnect operation would retry the wrong server. Saved-entry validation refuses unknown and switched-off rows. The command ownership tests cover this distinction.

[observed] Pinned mobile auth prioritizes explicit session.permissions (including an empty array) over legacy scopes. The shared snapshot retains only scopes. The environment-detail adapter reads the selected transport's session and rechecks its permission immediately before provider/server actions, preserving the shared client and reducer. Public release checks use a native20-second deadline carried opaquely between pages; data sources do not read a wall clock. Native confirmation precedes route removal and server update. These paths have helper/typecheck evidence; live maintenance and credential persistence remain unproved.

## Granular grant compatibility correction

[observed] During the native Moonbase drive, pairing, Home and transcript loading worked while Files displayed its filesystem-read denial. Source comparison found the unchanged desktop `shared/remote-scopes.ts` requests five legacy scopes, while pinned mobile365aa87982 `packages/contracts/src/auth.ts` defines thirteen standard granular scopes. The pinned server's `EnvironmentAuth.exchangeBootstrapForAccessToken` intersects requested scopes with the bootstrap grant; it does not expand legacy parent permissions. This request mismatch is consistent with the observed limited access. The actual app session's raw permissions were not exposed by the existing driver snapshot, so the runtime grant contents are not asserted here.

[decision] [mobile-grants.ts](../examples/t3-code/mobile/mobile-grants.ts) names the pinned mobile standard scopes. The existing mobile native adapter replaces the scope only for credential-bearing `connect`, `pairEnvironment` and `fleetOutdatedPair` operations. This covers the shared pairing paths without changing their reducers or copied source. Credential-free reconnect retains its issued token; obtaining a broader eligible grant requires a new pairing exchange. No server permission, bootstrap grant, or persisted bearer is modified by this adapter.

[observed] The same leaf helper now implements all nine pinned `legacyParents` entries in `sessionGrantsScope`. Explicit `permissions`, including an empty array or a grant missing the requested child permission, remain authoritative. Parent fallback applies only when permissions are absent and the server lacks `auth.serverUpdateScope`. The former helper covered only provider/environment maintenance fallback; old-server filesystem, diagnostics, settings, preview, source-control and terminal-read compatibility is now included. Invalid non-array permission data refuses access.

[observed] Focused tests execute the actual `mobileNative` request boundary for all three exchange operations, preserve saved-token/unrelated requests, verify all nine compatibility mappings and prove constrained server grants remain denied. Grant, environment-detail, client and review suites pass44 tests/1141 assertions; the generated app Answer typecheck passes. The full native build launches. A fresh UI pairing then loads two real diff sections with two changed files, and the Files route lists the seeded workspace. App Cargo build and Clippy pass; the aggregate mobile suite passes544 tests/3156 assertions. Independent same-family review passes14 tests/108 assertions with no actionable finding. These observations establish read access, not full route or pixel acceptance. Test credentials are synthetic; no token or secret is recorded in the logs or this document.

## App links

[observed] The mobile manifest registers the production `t3code` scheme. The authored route table nests destinations beneath Home so the existing router builds Home beneath a directly opened thread. A source-body executable using the actual `exact-route` library and the extracted production table verifies cold thread/terminal ancestry and Back. The native app now builds and launches; external URL delivery remains a separate native validation target.

[decision] `navigation-links.ts` accepts the public paths in pinned Stack.tsx and maps implemented settings, review-comment and file paths to the app's internal locations. Tap-time internal routes are not public links. The boot action captures its original visit and location; it resolves that location once and cannot reinterpret a later in-app visit. Warm actions capture their requesting visit too. The app uses the existing shared thread-selection action; a late failure now checks its captured visit before displaying an alert. Public environment IDs resolve only to a unique real catalog source, while internal actions retain exact route keys.

[observed] Existing X5/#104 still applies. The host removes the scheme and fragment before delivering a location; the actual route library maps `t3code://` to `/` and `t3code:///` to `//`. Warm slash-only locations therefore preserve the current stack. This also prevents an explicit external Home link from resetting navigation. Expo launcher/share wake paths are ignored warm and resolve Home cold. No raw callback or fragment is reconstructed, and no framework source is changed.

[unknown] The prepared public new-task flow still needs installed-app URL-delivery validation. Configured cloud callbacks and pairing links with missing raw information remain open. Cold filtering currently occurs after the first resource answer, not before the first rendered frame. Root Contract and native builds pass under the user's resumed validation authorization. Source checks do not establish native URL-delivery or visual parity.

## Alternatives

A new mobile protocol client duplicates reducers and breaks the handoff's reuse requirement. Compiling the whole desktop native module imports AppKit and desktop controls. Editing shared auth constants would change the desktop client. An additive shared metadata API could reduce copied Swift later, but requires its own shared commit and review; it is not necessary for this app-local implementation.

## Reconnect launch ownership correction, 2026-10-07

[observed] An ordinary installed app launch retained an enabled saved environment but showed Environment unavailable. Re-pairing recovered it; terminating and launching the same installed app reproduced the symptom without reinstalling. The native environment metadata survived. This does not identify a Keychain failure or prove which launch read was cancelled.

[observed] The actual imported `mobileSnapshot` reproduces a permanent reconnect omission when the first saved-environment catalog read is aborted. The desktop-pinned `shared/r8-pointer-reconnect.ts` marked the client as attempted before awaiting that read. Three subsequent healthy snapshots performed zero connects. The fleet also excluded the remembered origin, leaving neither a focused nor background connection. The same fixture with a healthy first read issues one focused connect.

[decision] The mobile copy explicitly adapts launch attempt ownership while retaining immutable desktop pin `887b2491b182f851b11253655f6aa84fe2a26708`. An eligible disconnected focus commits its once-only decision only after a successful catalog read. The newest concurrent read owns that decision. A failed or superseded read remains retryable from a fresh answer. Connected, connecting, error and already identified focus decisions remain terminal, as does a successful catalog without an enabled target. Once connect is submitted, rejected completion does not release the marker or pending focus: a cancelled answer can still have dispatched the native operation. Existing transport status settles that ownership. No desktop or framework source changed.

## Complete transfer decoding, 2026-10-10

[observed] Actual laptop transcript loading exhausted the clone's Hermes heap
inside JSON parse and stringify. Chunking bounds individual native replies,
while assembling a complete value still needs its whole JSON text and object.
The app-native owner already checks its creation-age 120-second expiry every
second while connected, as well as during preparation. Reset removes every
transfer when its transport retires. Expiry is not confined to preparation.

[decision] The mobile-only [protocol copy](../examples/t3-code/mobile/shared/protocol.ts)
retains every fragment until complete assembly, then drops the fragment-array
references and attempts the existing releaseChunk operation before JSON parse.
Reads remain replayable until that explicit release. Cleanup keeps the captured
ID, generation and owned native ticket, and remains best effort. The desktop
body, native store, wire operations, quotas and timeouts are unchanged. The
immutable source pin is retained; the copy audit permits only this exact mobile
transformation and still compares all 297 copied bodies.

[observed] Round 1 passes 31 client tests and 1,614 assertions, including the copy
audit and seven transfer regressions. The unchanged baseline fails the two
release-before-parse assertions; its other five transfer cases pass. A lossless
12 MiB reply with Unicode and nested fields is parsed only after native release.
Interrupted ordinary reads, malformed JSON, cleanup rejection, overlapping
reply IDs, chunk replay and changed generations preserve their tested outcomes.
Strict protocol TypeScript passes. A Foundation executable using the actual
unchanged native source confirms Unicode reassembly, non-consuming repeated
reads, independent releases, idempotence, reset and retained-byte quota behavior.
These are controlled helper checks, not device or Hermes heap measurements.

[unknown] ExactReply does not expose cancellation or whether a descriptor was
accepted. A superseded ownedNative can hide it, and an Exact-aborted letGoAware
refuses the finally cleanup. The cancellation regression still observes zero
native releases and a retained transfer pending existing expiry/reset. This
partial allocation-order change does not fix prompt abandonment, establish a
64 MiB working-set bound or prove that the live transcript crash is resolved.
A complete fix needs app ownership that can observe abandonment without writes
through a retired answer; a guessed shorter timeout could discard a valid
paused or replayed read and is not added here.
