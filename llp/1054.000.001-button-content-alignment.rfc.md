# LLP 1054.000.001: Where a button's content sits

**Type:** RFC
**Status:** Superseded (Charlie, 2026-10-04, delegated: a `button` follows Chrome's `<button>` — option E with C's `text-align: center` — built as recorded in LLP 1001 §1). Was: Accepted (Charlie, 2026-09-27: option B, "ok seems reasonable"); never implemented
**Systems:** Contract lowering (`tags.rs`, `button`'s fixed rows), kernel style vocabulary (`justify-content`), web host (`<button>`), every app's buttons
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-26
**Related:** LLP 1054 L3 (the finding); LLP 1054.000 C1; LLP 1006 §3 and LLP 1007 §1 (Charlie, 2026-09-23: "One native button, flex column"); `CLAUDE.md` "The web is the standard"; commit `01d4f08b`

## Summary

*Superseded 2026-10-04.* Three app diaries (kanban F16, onboarding F3,
recipes F5) hit the column default again, and the decision went to the
browser's button outright: a block whose content the kernel centres with
block `align-content: safe center` — no anonymous box, since Taffy's block
layout aligns its content as one subject — plus the UA sheet's `text-align:
center`; flex and grid buttons are ordinary containers (LLP 1001 §1). The
measurements below still hold.

Contract's `button` is a pressable flex column with no alignment of its own,
so its content starts at the top-left. A browser's `<button>` centres its
content vertically. The Bluesky port set `justify-content="center"` on
fixed-height buttons over and over (LLP 1054 L3). This document measures
what the browser actually does, sets out five options with the strongest
case for and against each, and recommends one.

**Recommendation: option B.** A `button` whose author does not choose its
layout centres its content on the block axis, as a browser's block
`<button>` does. It uses `justify-content: safe center`, added to the
kernel's vocabulary. Horizontal stretch stays, and `text-align` stays
`start`. When an author sets `display`, `flex-direction` or
`justify-content`, the centring is gone, as it is for a `display: flex`
`<button>` in Chrome.

## What the browser does (measured)

Chrome 154.0.8037.58, headless, `getBoundingClientRect`, a 200×100 button
(the probes are at the end):

| Case | Child box (x, y, w, h) |
|---|---|
| UA `<button>`, text "Save" | 85, 43, 30, 15: centred both ways (`text-align: center`) |
| UA block `<button>`, block child 20 tall | 8, 40, 184, 20: centred vertically, **stretched** horizontally (8 = UA padding) |
| UA block `<button>`, block child 50 wide | 8, 40, 50, 20: **not** centred horizontally |
| `all: unset; display: block`, block child | 0, 40, 200, 20: still centred vertically |
| `all: unset; display: block`, two 20-tall children | first at y 30: the group is centred |
| `all: unset; display: block`, child 150 tall | 0, 0: overflow starts at the top (*safe* centring) |
| `all: unset; display: block`, auto height | 0, 0: nothing to centre |
| `all: unset; display: flex` (a row) | 0, 0: **no** centring |
| exact2 today (`display: flex; flex-direction: column`) | 0, 0: top |

So the browser's behaviour is specific. A *block* button centres its
content as a group on the vertical axis. It does so safely: content that
overflows starts at the top. Children keep their normal horizontal
behaviour (stretch, or start when sized). The only thing centred
horizontally is inline text, and that comes from the UA stylesheet's
`text-align: center`, which `all: unset` removes. A flex button does
none of this.

## Today, in numbers

Across the 18 in-repo apps and the Bluesky port, 337 `button` lines (a
line-based count, so a lower bound):

- 87 set `justify-content="center"`, 90 set `align-items="center"`, and 55
  set both. The Bluesky port alone accounts for 24 and 40.
- 215 set neither. Most size to their content, and centring changes nothing
  for them.
- At least 20 have a fixed height and no `justify-content`. Most of those
  set `flex-direction="row"` (Messages' Reply button, Bluesky's search
  pill), which option B leaves alone.

## The options

### A. Keep it: a button is a column (today)

**For.**
- It is your decision of 2026-09-23, and it is two days old.
- One rule: `button` is exactly a pressable `column`, so there is nothing
  special to learn and nothing hidden.
- Authors state alignment the same way on every container.
- The kernel and the web already agree (LLP 1007 §1's deviation was
  deleted by this).
- Nothing moves in 18 apps.
- Buttons that are whole rows or cards (Messages' conversation rows)
  behave like the columns they are.

**Against.**
- A fixed-size button whose label sits at the top is the one thing a web
  developer, or a model trained on the web, never expects. "The web is the
  standard" is the rule this repo holds hardest.
- 87 attributes exist only to undo the default, and the port hit it on
  every pill.
- The default is defensible as "a column", but no platform's button looks
  like that.

### B. Centre on the block axis, like a block `<button>` (recommended)

`button`'s fixed rows gain `justify-content: safe center`, but only when
the author sets none of `display`, `flex-direction` and `justify-content`.
In a column, that is vertical centring of the content as a group.

**For.**
- It is exactly what Chrome does, on every measured case: vertical, as a
  group, safe on overflow, horizontal stretch kept, and no centring once
  the button is laid out as flex.
- Content-sized buttons, the large majority, don't move at all.
- Buttons that set `flex-direction="row"` don't move either. They are
  Chrome's "flex button", and they get no centring there too.
- It removes most of the 87 `justify-content="center"` attributes.
- It keeps your 09-23 point: one native button, and a flex column as far
  as authors can see.

**Against.**
- It's a conditional default: the rows depend on which other rows the
  author wrote. Nothing else in Contract works that way, and it has to be
  explained. (The browser's rule is conditional in the same way, which is
  the justification.)
- It needs `safe center` in the kernel's `JustifyContent` vocabulary. It's
  CSS, and vendored Taffy has `safe`, but it's a schema change. Plain
  `center` would overflow upward, where Chrome does not.
- A tall card-like `button` with a fixed height and top-aligned content
  moves down. Messages has a few, and each needs
  `justify-content="flex-start"` or an audit.
- It changes a decision you made this week.

### C. B, plus the UA's `text-align: center`

**For.**
- Fuller fidelity to a bare `<button>`: a text label is also centred
  horizontally, with no attribute.

**Against.**
- exact2 already strips the UA button's chrome (padding, border,
  background, font); its web emits `all: unset`-like rows, and there
  `text-align` is `start`.
- `text-align` inherits. Every paragraph inside a row-like button (a
  conversation's name and preview) would centre, which is the reset every
  web app writes. The repo's rule is to follow CSS defaults, not the UA
  stylesheet's per-element chrome.
- It moves many more buttons than B.

### D. Centre both axes (`align-items` and `justify-content: center`)

**For.**
- It's what React Native, SwiftUI and most design tools do, and it's
  simple to say.

**Against.**
- It isn't the web. `align-items: center` shrinks a block child to its
  content width and centres it; Chrome stretches it. Every full-width row
  inside a button would collapse.
- It moves the most buttons, in the most visible way.

### E. Make `button` a block, and centre in the kernel as the browser's anonymous box does

**For.**
- Fidelity by construction: the kernel lays out a block button as Chrome
  does, including inline content.

**Against.**
- Taffy has no anonymous boxes. It would be a kernel special case for one
  node type.
- It undoes the 09-23 decision, which moved the web to flex precisely to
  avoid this mismatch.
- B gets the same visible result with a vocabulary value.

## Recommendation

B. It is the only option that matches what the browser does on every
measured case. It moves only the buttons that are laid out as fixed-size
block buttons and aren't centred today. It removes the attribute the port
wrote most. The conditional default is the cost, and the browser has the
same condition.

If you prefer the rule to stay unconditional, A is the honest second choice,
with a lint suggesting `justify-content="center"` on a fixed-height `button`.
C and D contradict the measurements. E is B at a much higher price.

## If B is chosen

- `kernel/tables/schema.json`: `JustifyContent` gains `safe center` (Taffy's
  `AlignContent::Center` with `Safe` overflow); the web emits
  `justify-content: safe center`.
- `contract/lower/src/tags.rs`: `button` gains the row when the author's
  attributes include none of `display`, `flex-direction`,
  `justify-content`.
- Tests: the Chrome cases above as `kernel/tests/it/browser_cases.rs`
  entries; a corpus test for each condition.
- Audit the 20+ fixed-size buttons; delete redundant
  `justify-content="center"` in the same change.
- LLP 1006 §3 and LLP 1007 §1 record the rule and the measurements.

## The probes

Each row of the table is one `<button style="…">` with the given CSS
(`width: 200px; height: 100px` unless noted) in a `16px/18px` body. The
child's rect is measured relative to the button's with
`getBoundingClientRect`, using `Google Chrome --headless=new --dump-dom`
on 2026-09-26. The session's two probe pages were scratch files; the cases
move into `browser_cases.rs` if B is chosen.
