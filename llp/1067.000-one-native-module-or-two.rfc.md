## Summary

An app's native code is **one module**: it declares its views and its long
calls together, the host makes **one instance per session**, and every entry
into it runs on the **main thread**. A view receives the instance, so a
camera preview and "take a photo", or a waveform and "stop recording", share
one object by ordinary reference. It is the web's shape (one page module,
`modules/web/index.js`, already held both halves) and Expo's.

On Apple it is LLP 1024's artifact, `libexact_modules.dylib`, loaded on
demand, with its function table at `major` 2. The static Swift bridge LLP
1067 D6 added (`swift_native`, `swift_native_module!`) is deleted.

`apps/recorder`, a microphone recorder with a live waveform, is the consumer
that worked this out. It runs on the web, macOS and the iOS simulator, and
its smoke holds the page module and the Swift module to the same takes.

## Motivation

Until this change an app's Swift reached exact2 through two seams, built a
day apart:

| | View modules (LLP 1024) | Long calls (LLP 1067 D6) |
|---|---|---|
| Built by | `host/apple/build.mjs` → `libexact_modules.dylib` | Cargo `build.rs` → a static archive in the binary |
| Loaded | `dlopen` after first paint | at launch |
| Interface | one size- and version-checked table | fixed C symbols, renamed per app |
| Instances | one per view; nothing per session | one per activation |

What went wrong with two:
1. **A view and a function couldn't share an object.** Two Swift images
   have two sets of globals and two copies of any shared type. Most native
   capabilities are one object with a view and functions around it: a
   camera, a map, a player, a recorder. The only bridge was a round trip
   through Contract state, too slow for a preview and wrong for a handle.
   The web never had the problem, so it was a parity break by construction.
2. **Two interfaces to version, two lifecycles, two dev loops,** and
   functions mapped at launch whether or not an app called them.
3. **Android copies whatever Apple does.** Expo's Kotlin API is one module
   class, as its Swift API is.

## Design

### D1 — One module per app, views and long calls together

An app's module has a roster of view tags and a `later` handler, and
announces device topics. On every host it is one object per session:
- **Web:** the page module, `modules/web/index.js`. One page is one session,
  so its top level is the instance.
- **Apple:** a subclass of `ExactModule` in `modules/apple/*.swift`, named
  once:

```swift
final class Recorder: ExactModule {
    override class var views: [String: ExactNativeFactory] {
        ["waveform-view": ExactNativeFactory(for: Recorder.self, snapshot: true) { recorder, props, events in
            WaveformView(recorder: recorder, events: events) }]
    }
    override func later(_ request: [String: Any], reply: ExactReply) { … }  // reply once, any thread
    override func destroy() { … }
}
let exactModule: ExactModule.Type = Recorder.self
```

`views` is read once per process: it is the roster the build checks. A
factory made with `for:` receives the instance typed, and another type is
refused by name. A view-only app returns no `later`.

### D2 — The Apple artifact: LLP 1024's dylib, table `major` 2

| Offset | Entry |
|---|---|
| 0 | `u32 major` = 2, `u32 size` ≥ 104 |
| 8 | roster JSON |
| 16 | `create(module, tag, …)`: a view, given the session's instance |
| 24–48 | `platform_view`, `set_props`, `snapshot`, `destroy` (unchanged) |
| 56, 64 | reserved: `set_bounds`, `agent_input` |
| 72 | `module_create(context json, host, changed, now)` → instance |
| 80 | `module_destroy(instance)` |
| 88 | `module_later(instance, body, reply, answer)` |
| 96 | reserved: `call` (Q8) |

The host refuses any other major by name ("module ABI 1, host ABI 2"), so an
artifact built against the view-only table fails loudly, not at a call. It
is built by `build.mjs` and never closed (1024 D5).

### D3 — One instance per session

- **Made at first need:** the first view node after the paint gate, or the
  first long call, whichever comes first.
- **Outlives activations.** A TypeScript dev reload reconnects to the same
  instance, so a recording carries across an edit. A Swift edit is a restart
  (1024 D6).
- **Destroyed with the session,** after its views and its runtime.
- Two sessions in one process have two instances; neither sees the other's.

### D4 — Every entry on the main thread

View create, props and destroy; `module_create`; the start of each `later`;
`module_destroy`. The executor's I/O worker that takes a long call
dispatches it to main asynchronously and returns at once. Long work goes on
the module's own queues, and a reply may be sent from any thread, once:
only the first answers, and a reply dropped unanswered fails the call.

Why main:
- The web's page module is single-threaded, and the web is the standard.
- `main` is the default placement, so most sources already run there.
- AVFoundation, MapKit and every view want main anyway.
- No instance lock. The lock the PR #47 review added could hold the main
  thread behind a `later` running on an I/O worker.

### D5 — How a long call reaches the module

A long call is a request to `exact-native:` (LLP 1067 D1), and the runner
hands it to the handler in a native slot:
- **The host installs the app module in the slot** (`Native::host`). It
  outlives activations: unloading a source clears only the source's own
  handler. A source's own handler, when it has one, wins.
- **Which slot:** a TypeScript module's own (shared with a worker-built
  instance, so worker placement works unchanged), or, for a source with none
  (a Rust source), the runner's (`Runner::native_slot`). A Rust source asks
  with `Request::native(body)` and watches a topic with
  `Store::observe_topic`, as the TypeScript prelude does.
- **`native.available`** is true for a hosted module, including in agent
  mode (D6). Apple installs the module only when the app ships an artifact,
  which is a file check, not a load.
- **Apple's seam:** `exact_set_app_module(rt, later, ctx)`,
  `exact_app_changed(rt, topic)` and `exact_app_reply(reply, status, body)`
  (`include/exact.h`). A reply is HTTP-shaped: 200 carries the JSON answer,
  any other status a refusal that rejects the promise.
- **Web:** unchanged. The glue sends `exact-native:` to the page module's
  `later`, whatever the source's language.

`exact_js` knows nothing about Swift.

### D6 — Agent mode: substitute before the OS, on the session's clock

The instance exists under the agent, and its context says so:
- **Web:** `connect({ changed, agent, now })`.
- **Apple:** `ExactModuleContext.agent`, `now()`, and the data, cache and
  temporary directories (a scratch tree under the agent).

A module substitutes its device input before the OS is asked (LLP 1069.007).
It is driven by `now()`, the agent's clock under the agent, so a screenshot
after `clock +N` is the same every run and on every host, and no permission
prompt blocks a drive.

The iOS capture redraws module views before it composes. `drawHierarchy`
reuses a clean layer without calling `draw`, and a view that draws from
`now()` may not have drawn since the clock moved.

### D7 — The web's context is `connect`

`connect` already receives the session's `changed`; it now receives `agent`
and `now` too. A separate `create(context)` would rename it, not add to it
(Q3: no).

### D8 — Loading

Apple loads the artifact at the first view node after the paint gate, or at
the first long call, whichever comes first. By LLP 1067 D4 no first-frame
answer depends on `native`, so nothing moves before first pixel (Q2: at
first call). The recorder's artifact loaded 5.7 ms (macOS) and 9.8 ms (iOS
simulator) after first pixel.

### D9 — `call` (open: Q8)

Provisionally, an app module answers only `later`: `native.call` refuses
with "the app's module answers native.later, not native.call", and slot 96
is reserved. A Rust `NativeModule` (Messages' Snapback) keeps `call`. Q8
below explains the choice.

## Evidence (2026-09-27)

Driven through the agent's operations:
- **`bun scripts/smoke.mjs <web|macos|ios> --app recorder`: 7 of 7 on
  each.** The module is available and idle. Three seconds of recording draw
  the waveform from the object while the source is asked for status twice
  in all. The takes read "Take 1 · 3.0 s · level 52%" and "Take 2 · 1.5 s ·
  level 51%" on every host: the level is the take's average, so the page
  module and the Swift module can't drift apart.
- **`bun scripts/smoke.mjs host --app recorder`:** two sample-host sessions
  each keep their own recorder on their own clock, and one keeps recording
  after the other is destroyed.
- **`native-fixture` on macOS: 33 of 33,** including the refusal of a
  `major` 1 artifact by name.
- **Worker placement** (`EXACT_TYPESCRIPT_PLACEMENT=worker`, confirmed in
  the bake's compatibility record): the recorder smoke, 7 of 7.
- **A TypeScript dev reload mid-recording** (`host/web/dev.mjs` and
  `EXACT_DEV_PLAN` on macOS): the edit shows, the recording carries on, and
  the take is 3.0 s from before the edit.
- **Web, outside the agent:** headless Chrome with a fake audio device
  records a live waveform and writes `recorder/take-1.webm` to the origin
  private file system.
- **Tests:** `runner/tests/it/app_module.rs` (a Rust source's call and an
  announced re-ask), `host/apple/src/app_module.rs` (the one-shot reply),
  `host/web/native-glue.test.mjs` (`connect`'s context). The five checks
  pass: 1,759 tests, none failing.

Not yet driven: the real microphone on Apple, which needs a person to answer
the OS prompt (`EXACT_APP_DIR=apps/recorder bun host/apple/build.mjs --run`).

## Moving an app to this shape

- **A view-only app** (photo-editor, map-demo, native-fixture): wrap the
  roster in an `ExactModule` subclass's `views` and name it
  `let exactModule`. Their factories are unchanged.
- **An app with a static Swift bridge** (grnl), in five steps:
  1. Move its Swift into `modules/apple/`.
  2. Make its `ExactNativeModule` class a subclass of `ExactModule`: `later`
     takes an `ExactReply`, and `configure(data:cache:temporary:)` becomes
     reading `context.data` and its siblings.
  3. Move `call` handlers to `later`, or wait for Q8.
  4. Replace `ExactNative.changed(topic)` with `context.changed(topic)`.
  5. Delete `swift_native` from its `build.rs` and `swift_native_module!()`
     with `with_native(native_module)` from its crate; the app module needs
     no Rust.

## Alternatives considered

| | Shares state | Web parity | Before first pixel | Per session | Dev loop | Interface | Accepted decisions |
|---|---|---|---|---|---|---|---|
| **A** one module, dylib (chosen) | yes | yes | nothing | yes | dylib + restart | one table | extends 1024 |
| B two artifacts, one contract | untyped registry only | no | data at launch | yes | two | two | leaves 1067 D7 |
| C keep as is | no | no | data at launch | data only | two | two | leaves D7 open |
| D one module, statically linked | yes | yes | mapped at launch | yes | relinks the app | symbols | reverses 1024 D3 |
| E both in one dylib, unrelated | no | no | nothing | partly | dylib | two | — |

- **D** traded a load-time check for link errors, at the cost of reversing
  1024 D3 and a slower dev loop.
- **B** needed a session registry of objects passed between two images. A
  Swift type in two images is two types, so only ObjC classes from a third
  framework could cross.
- **C** meant every adopter moved later, as a hard cut.

## Open questions for Charlie

- **Q8. Does an app module answer `native.call`?** `native.call` answers
  inside the TypeScript answer, synchronously, within its 100 ms budget.
  `native.later` answers whenever the module replies, like a `fetch`.
  - **Against `call`** (the provisional choice):
    - The web can't answer a synchronous call, so an app that uses it isn't
      portable.
    - Under D4, `call` from a worker-placed source would have to hop to the
      main thread and wait for it, the one place the host would block on
      main.
    - The recorder needed only `later`.
  - **For `call`:**
    - A cheap query (is the microphone available, what's the battery level)
      costs a request round trip through `later`: a ticket, a pending
      answer, a settle.
    - Messages' Rust module uses `call` for its synchronous database.
  - **Recommendation: no `call` on app modules (65%).** Keep Rust
    `NativeModule::call` for Rust-side work like Snapback, and revisit when an
    app module needs a synchronous answer that `later` makes visibly worse.

## Not in this RFC

- Linux view modules (still refused in v1). A Linux app module would be a
  Rust `NativeModule`, which already works.
- Android, which should copy this shape.
- Live-swapping native code in a running process (1024 D6; `dlclose` stays
  forbidden).
- Streams of partial results (LLP 1016.000's question).
