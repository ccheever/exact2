### What the web step showed (2026-09-27)

`apps/recorder` runs on the web: one page module, `modules/web/index.js`,
whose top-level recorder object both `<waveform-view>` and `later` use.
Driven through the agent: record, `clock +3000`, stop gives "Take 1 · 3.0 s",
and two runs' screenshots are identical, byte for byte. Outside the agent,
headless Chrome with a fake audio device records a live waveform and writes
the take to the origin private file system (`recorder/take-1.webm`, 32 KB).

Findings:
- **High-rate data never reaches the source.** Levels arrive 20 times a
  second and the view draws them every frame, but the source sees only
  coarse state: recording or not, and the list of takes. A `level` topic
  would have re-asked an answer 20 times a second for nothing. That is K1's
  whole case: the view needs the object, not a value copied through Contract.
- **`native.call` went unused.** The web can't answer a synchronous call
  (module realms throw), so a portable app uses `later` for everything. In
  (A), `call` could be an Apple and Linux fast path, or dropped from the
  shared protocol. This is new: Q8.
- **The context already has a home on the web.** The page module's
  `connect` now receives `{ changed, agent, now }`: the agent flag, and the
  page's clock, which is the agent's under the agent (`host/web/glue.js`,
  `native-glue.js`). `connect` is the per-session context, so Q3's
  `create(context)` would rename it rather than add anything.
- **The agent needs the clock as well as the flag.** A synthetic input that
  follows wall time can't be screenshot twice the same. Apple's
  `ExactModuleContext` needs the session's clock too.

### Q5. Threads: the module runs on the main thread, with no instance lock

Every entry into an app's module runs on the main thread:
- view create, props and destroy (as today);
- `call`;
- the start of `later`, which the host dispatches to main asynchronously,
  so the I/O worker that took the request returns at once;
- `destroy`.

Long work runs on the module's own queues, and `done` may be called from any
thread, once.

Why:
- `native.call` already runs on main for most apps: `main` is the default
  placement (`contract/cli/src/manifest.rs:75-100`), and a main-placed
  source runs inline.
- The web's page module is single-threaded. One thread is the web's model,
  and the web is the standard.
- AVFoundation, MapKit and every view already want main.
- It deletes the instance lock added on 2026-09-27. That lock holds the
  main thread while a `later` runs `call` on an I/O worker (the issue above).

A worker-placed source's `call` hops to main synchronously. That is safe
only while the main thread never waits on a source's owner thread. Nothing
in the host does today. The agent's settle spins the main run loop, and that
spin still services the main queue. The hop costs the call a main-thread
turn inside its 100 ms budget.

### Q6. Ownership: one instance per session, not per activation

Today the Rust `NativeModule` factory runs per activation, so each
TypeScript dev reload makes a new one (`js/src/lib.rs:585-608`). Under (A),
views hold the instance too, so it belongs to the session:
- it is created at first need, which is the first view node after the paint
  gate or the first activation that asks for `native`;
- each activation reconnects to it, and its `watch` listener is re-registered;
- it is destroyed at session teardown, after the views.

A TypeScript edit therefore doesn't stop a recording. A Swift edit is a
restart (1024 D6).

### Q7. Agent mode: the instance exists and substitutes its input

Today the data factory doesn't run in agent mode without
`EXACT_AGENT_STORAGE`, but views load. Under (A), the instance always exists,
and its context says `agent: true`. A module then substitutes its device
input before the OS asks for anything (LLP 1069.007's "substitute before the
OS"). The recorder uses a synthetic signal, so its screenshots are
deterministic and no permission prompt blocks an agent run. Until 1069.007's
D4 is built, an agent can't answer an `exact-native:` request itself.

## Summary

An app's own Swift reaches exact2 through two seams that were built a day
apart and never met:

- **View modules (LLP 1024)** give a hyphenated tag (`<photo-editor>`) a
  platform view. The Swift in `modules/apple/` is built by `build.mjs` into
  `libexact_modules.dylib`, loaded with `dlopen` after first paint, and
  reached through one size- and version-checked function table.
- **Data modules (LLP 1067)** give a TypeScript source functions:
  `native.call`, `native.later` and `native.watch`. The Swift is compiled by
  the data crate's `build.rs` (`exact_js_bake::swift_native`), statically
  linked into the app's binary, and reached through fixed C symbols.

On the web the two are already one artifact, `modules/web/index.js`, which
both defines the custom elements and exports `later`/`connect` (LLP 1067
D5). On Apple they are two artifacts with two ABIs, two build paths and two
load times, and **they cannot share Swift state**. A camera preview (a view)
and "take a photo" (a function) get two different camera objects.

This document lays out five shapes, judges them against eleven criteria,
and recommends one: **(A) one module artifact per app, which declares its
functions and its views together, is instantiated once per session, and is
loaded on demand.** It is the Expo Modules API's shape, the web's shape, and
the extension of the view-module artifact Charlie already accepted. This is
a proposal; nothing is decided until Charlie rules.

## Motivation

### What exists (2026-09-27)

| | View modules (LLP 1024 §9) | Data modules (LLP 1067 D6–D7) |
|---|---|---|
| **Authored in** | `apps/<app>/modules/apple/*.swift` | any Swift files the data crate's `build.rs` lists |
| **Built by** | `host/apple/build.mjs`, with the host's `ExactNativeModule.swift` | Cargo, via `exact_js_bake::swift_native` (`swiftc` → static archive) |
| **Artifact** | `Frameworks/libexact_modules.dylib` | inside the app binary (linked into the data crate) |
| **Loaded** | `dlopen` at the first module-node create after the paint gate; never closed | with the binary, at launch |
| **ABI** | `exact_native_abi()` → one table: `major` 1, `size` 72, roster JSON, `create`/`platform_view`/`set_props`/`snapshot`/`destroy`, two reserved slots (`set_bounds`, `agent_input`) | fixed C symbols: `create`/`destroy`/`configure`/`call`/`later`/`listen`/`unlisten`/`free`, per-app names since 2026-09-27 |
| **Instances** | one per node; the table is per process | one per activation (per session), since the 2026-09-27 fix |
| **Threads** | main thread (views) | the source's thread, or the executor's worker for `later` (LLP 1027.002) |
| **Skew** | checked once at load; a mismatch is a per-node `unavailable` | a link error |
| **On the web** | `modules/web/index.js` defines the custom elements | the same file exports `later` and `connect` |
| **On Linux** | not supported in v1 (the empty box) | a Rust `NativeModule` in the data crate (`Module::with_native`) |
| **Consumers** | `apps/photo-editor`, `apps/map-demo`, `apps/native-fixture` | grnl (outside the repo) |

### What goes wrong with two

1. **A view and a function can't share an object.** Most native
   capabilities are one object with a view and functions around it:
   - a camera preview and capture;
   - a map and geocoding or pin state;
   - a recorder and its live waveform (grnl);
   - a player view and play/pause/seek;
   - a document scanner and its results.

   In two Swift images, each has its own globals and its own copy of any
   shared type. The only bridge is a round trip through a TypeScript source
   and Contract state, which is too slow for a preview and wrong for a
   handle (an `AVCaptureSession` can't be serialized). The web doesn't have
   the problem, because both halves live in one JavaScript module, so the
   two seams are a parity break by construction.
2. **Load-on-demand is broken for functions.** `AGENTS.md` says optional
   capability is "a separate artifact loaded on demand". Strictly, that rule
   is about exact2's optional capabilities, not app code. Still, the view
   half follows it and the function half doesn't: statically linked Swift
   is mapped at every launch whether or not the app calls it.
3. **Two ABIs to version.** 1024's table is built to evolve: size-checked,
   with a major version and reserved slots. 1067's symbols are not. Before
   the 2026-09-27 fix they collided if two apps' modules were linked into
   one binary. The fix added a third naming scheme (per-app symbols).
4. **Two lifecycles.** After the fix, data-module instances are per session
   (LLP 1031 requires it). View-module state has no per-session owner: a
   factory is process-global, and each node's instance is alone.
5. **Two dev loops.** Editing a view module's Swift rebuilds the dylib and
   restarts (1024 D6). Editing a data module's Swift re-runs `swiftc` inside
   Cargo's build script and relinks the app's data crate and binary.
6. **Android is next.** Whatever Apple does, Android copies: a Kotlin module
   with views and functions. Expo's Kotlin API is one module class, as its
   Swift API is.

### Precedent: the Expo Modules API

Expo's native module is one class whose `definition()` declares everything
together:
- `Name`;
- `Function` and `AsyncFunction` (our `call`, `later`);
- `Events` (our `changed`/`native.watch`);
- `View(...)`, with `Prop` setters and `Events`;
- lifecycle hooks (`OnCreate`, `OnDestroy`).

The module is instantiated once per app context (per React Native host), and
its views receive that instance, so a view and a function share state by
ordinary Swift references. Expo links modules statically (autolinking via
CocoaPods). The instance-per-context and views-plus-functions-in-one-class
shape is the part worth copying; the static linking is a separate question
(options A and D below).

## Criteria

Each option is judged on these, in rough order of weight:

| # | Criterion | Why it matters here |
|---|---|---|
| K1 | **A view and a function share state** | The main functional gap (Motivation 1) |
| K2 | **Parity with the web and the future Android** | Web is one artifact; Android will copy Apple |
| K3 | **Nothing before first pixel** | `RULES.md` budgets: cold start to first frame 100 ms p50; 1024 D3 puts module loading after the paint gate |
| K4 | **Per-session ownership and teardown** | LLP 1031: a session owns its state and is destroyed whole |
| K5 | **Dev-loop cost** | Edit Swift → see it; LLP 1024 D6's restart shape |
| K6 | **Failure modes** | Link error vs. load-time refusal vs. run-time `unavailable` |
| K7 | **ABI surface to version** | One table vs. several symbol sets |
| K8 | **Consistency with accepted decisions** | 1024 (accepted 2026-09-26), 1009's on-demand dylib |
| K9 | **Embedding (LLP 1031)** | What an embedder ships and links |
| K10 | **Build and toolchain** | `swiftc` inside Cargo vs. `build.mjs`; caching (the 2026-09-27 fingerprint fix) |
| K11 | **Migration cost** | Three in-repo view-module apps; one outside data-module app (grnl) |

Delivery (LLP 1030) doesn't separate the options. A native change is a
binary change in every shape: iOS can't take native code over the air, and
the module roster is already in the compatibility id. Grants (LLP 1069.008)
don't separate them either: whatever instance exists receives the session's
effective grants.

## Options

### (A) One module per app, as a dylib, loaded on demand — Expo's shape, 1024's artifact

The app writes one Swift module in `modules/apple/`. It declares its
functions and its views together, and the host instantiates it once per
session:

```swift
final class Recorder: ExactModule {
  required init(context: ExactModuleContext) { … }        // grants, directories, changed(topic)
  func call(_ request: [String: Any]) throws -> [String: Any] { … }
  func later(_ request: [String: Any], done: ExactReply) { … }   // one-shot, aborts if dropped
  var views: [String: ExactViewFactory] {
    ["waveform-view": { props, events in WaveformView(recorder: self, props, events) }]
  }
  func destroy() { … }                                      // session teardown
}
```

- **Artifact.** `libexact_modules.dylib`, as today. 1024's table goes to
  `major` 2 and gains the module entries:
  - `module_create(grants, directories) → instance`, `module_destroy`;
  - `call`, `later` (with `done`/`discard`, the one-shot contract built on
    2026-09-27);
  - `listen`/`unlisten`.

  The view entries gain the session's instance: `create(instance, tag,
  props, …)`. Tag creation's reserved slots (`set_bounds`, `agent_input`)
  stay reserved.
- **Loading.** The first of two events loads the dylib:
  - **the first module-node create after the paint gate**, which is 1024
    D3 unchanged;
  - **the first `native` use from a source**, on the executor's thread.
    `dlopen` is thread-safe, and ObjC/Swift image registration off the main
    thread is supported; views are still only created on the main thread.

  By LLP 1067 D4 no first-frame answer depends on `native` (a bake has no
  module, so a branch on `native` is never baked), so loading at the first
  call puts nothing before first pixel. A source that calls `native` during
  its first activation waits for the load on its own thread, not the main
  thread. Measured precedent: the GPU dylib's `dlopen` plus device is
  23–36 ms warm, dominated by the device, not the load (LLP 1009).
- **Rust side.** `js/src/swift.rs` reads the table through the host's loader
  instead of linking symbols. `swift_native_module!`,
  `exact_js_bake::swift_native` and `js/native/ExactNative.swift` are
  deleted, and their protocol and one-shot reply move into the host's
  `ExactNativeModule.swift`. A Rust native module on Linux (and on Apple, if
  an app writes one in Rust) is unchanged: Rust is the data crate's own
  language.
- **Web.** `modules/web/index.js` already holds both halves. For parity it
  would export a `create(context)` returning `{ call, later, views }`. One
  page is one session, so this is naming, not behaviour.

| K1 | K2 | K3 | K4 | K5 | K6 | K7 | K8 | K9 | K10 | K11 |
|---|---|---|---|---|---|---|---|---|---|---|
| yes | yes | yes (after paint, or off-main at first call) | yes | fast (dylib + restart) | load-time skew check; a missing entry is `unavailable`, not a link error | one table | extends 1024 | the embedder ships the dylib in `Frameworks/` | `build.mjs` only | grnl moves its Swift; the three view apps adapt to `major` 2 |

**Costs and risks.**
- Rust no longer gets link-time proof that the Swift exists; the table's
  size and major checks replace it.
- The first native call pays the load (a few ms, off the main thread).
- `dlclose` stays forbidden (1029.000: Swift/ObjC images can't be safely
  unloaded), so a dev restart, not a reload, picks up new Swift. That is
  1024 D6 already.

### (B) Two artifacts, one contract

Keep both artifacts. Give them one lifecycle contract: a per-session
instance, grants and teardown for each. A view that wants a function's
state goes through a session-scoped registry the host provides (for
example, `context.shared["camera"]`), holding opaque references passed
between the two images.

| K1 | K2 | K3 | K4 | K5 | K6 | K7 | K8 | K9 | K10 | K11 |
|---|---|---|---|---|---|---|---|---|---|---|
| only through an untyped registry; two images' types don't match, so shared objects must be ObjC-visible | no (Apple differs from the web) | data half at launch | yes | two loops | both | two | leaves 1067 D7 as is | both | both | small |

**Costs and risks.** The registry is the "second value graph" `DEFERRED.md`
refuses in spirit, and it's fragile. A Swift type defined in both images is
two different types, so only ObjC classes or protocols from a third shared
framework could cross. That shared framework is then a third artifact.

### (C) Keep as is

Revisit when a consumer needs a view and a function that share state.

| K1 | K2 | K3 | K4 | K5 | K6 | K7 | K8 | K9 | K10 | K11 |
|---|---|---|---|---|---|---|---|---|---|---|
| no | no | data half at launch | data yes (2026-09-27), views no | two loops | both | two | leaves D7 open | both | both | none now; grows with every adopter |

**Costs and risks.** Every app that adopts either seam before the change
has to move later, and "delete; don't deprecate" makes that a hard cut.
grnl's recorder and waveform may already be the consumer (Q4).

### (D) One module per app, statically linked

Option A's single module and per-session instance, but compiled into the
app binary, as Expo and CocoaPods do, instead of a dylib. The view half
moves from `build.mjs` into the data crate's `build.rs` (or into the
binary's link step), and `dlopen` goes away.

| K1 | K2 | K3 | K4 | K5 | K6 | K7 | K8 | K9 | K10 | K11 |
|---|---|---|---|---|---|---|---|---|---|---|
| yes | yes | mapped at launch; nothing *runs* until first use | yes | slower: relinks the app | **link errors**, the strongest | a symbol set, or a table linked statically | reverses 1024 D3 (accepted) | the embedder links it with the app's archive | `swiftc` inside Cargo | view apps move their build |

**Costs and risks.**
- Charlie accepted 1024 D3's on-demand dylib the day before this document,
  and D reverses it.
- The dev loop gets slower for view modules.
- Launch maps code an app may not use. The cost is small (ObjC classes are
  realized lazily; Swift metadata is registered at image load), but not
  zero, and it grows with modules that link large frameworks
  (`AVFoundation`, `MapKit`), whose load commands then move to launch.

### (E) Functions ride in the view dylib, but stay a separate module

The same dylib carries both, but as two unrelated modules with two
protocols and no shared instance. Two ABIs in one file.

It solves K3, K5 and K10 without K1, and K1 is the main reason to change.
It's listed so it isn't reinvented; it's not recommended.

## Recommendation

**(A), about 70% confident.** It is the only option that closes K1 and K2
without reversing an accepted decision:
- the web's shape, and Expo's, on Apple;
- one ABI table to version, already built to evolve;
- functions loaded on demand like everything else native;
- a per-session instance that views and functions share.

**The runner-up is (D), about 20%.** It trades A's load-time skew check for
link-time errors and a simpler loader, at the cost of reversing 1024 D3 and
a slower dev loop. If Charlie weighs "a missing symbol is a build error"
above "nothing extra at launch", D is the better choice.

**B and C together, about 10%.** C is right only if no app needs a shared
view-and-function object in the next months, and grnl probably already does
(Q4).

**Why now:** each seam has few adopters today (three in-repo view apps, one
outside data app). The 2026-09-27 fixes already moved the data seam to
per-session instances and one-shot replies, which are the hard parts of A's
contract. Every month adds adopters to a shape "delete; don't deprecate"
would then have to break.

## If (A) is chosen: the work

1. **ABI `major` 2.**
   - Add the module entries and the instance parameter to 1024's table.
     View-only apps keep working by returning a module with no functions.
   - The table's size check refuses a `major` 1 artifact by name.
2. **Swift authoring.**
   - One `ExactModule` protocol in `host/apple/modules/ExactNativeModule.swift`
     (functions, views, `destroy`), with an `ExactModuleContext` (grants,
     directories, `changed(topic)`) and `ExactReply` (one-shot, aborts on
     drop), carried over from the 2026-09-27 bridge.
   - The per-tag factory table becomes the module's `views`.
3. **Host loading.**
   - `Sources/ExactKit/NativeModule.swift` loads at the first module node
     after the paint gate, or at the first executor call, whichever comes
     first, once per process.
   - Instances are created per session at activation and destroyed at
     session teardown, after views.
4. **Executor.**
   - `js/src/swift.rs` becomes a `NativeModule` over the loaded table.
   - `swift_native_module!`, `exact_js_bake::swift_native`,
     `js/native/ExactNative.swift` and `js/bake/src/swift.rs` are deleted.
5. **Web.** `modules/web/index.js` gains `create(context)` for parity, and
   `later`/`connect` move under it.
6. **Held by:**
   - `apps/native-fixture` gains a function and a view that share one
     object: a counter the view shows and a function increments, checked on
     macOS, iOS and the web through the agent;
   - two sessions in the `--host` fixture each see their own counter;
   - a `major` 1 artifact is refused by name.
7. **Consumers.**
   - `apps/photo-editor`, `apps/map-demo` and `apps/native-fixture` adapt in
     the same change.
   - grnl moves its Swift into `modules/apple/`, declares its roster, and
     drops `swift_native` from its `build.rs`. The exact edit list goes to
     Seth.

Estimated size: one change of a few hundred lines on each side of the
seam, plus the fixture. The one-shot reply, per-session instances and grants
already exist, from the 2026-09-27 fix.

## Open questions for Charlie

- **Q1. A, D, B or C?** The recommendation is A.
- **Q2. When do functions load?** At the first native call (A as written),
  or eagerly on the executor thread once the paint gate passes, which keeps
  a first call from waiting but loads apps that never call `native`?
  Recommendation: first call (80%).
- **Q3. Does the web adopt `create(context)`?** One page is one session, so
  it's naming only. Recommendation: yes, so an app author sees one shape on
  every host (70%).
- **Q8. Does the shared protocol keep `call`?** The web can't answer it,
  and the recorder didn't need it. Keep it as an Apple and Linux fast path,
  or leave it out of (A)'s protocol so that every app is portable by
  construction? Recommendation: leave it out of the shared protocol, and keep
  Rust `NativeModule::call` (60%).
- **Q4. (Answered 2026-09-27: `apps/recorder`, §Working direction.)** Does grnl need a shared view and function today? Its recorder and
  waveform suggest so. Seth would know, and his answer changes how urgent
  this is, not which option is right.

## Not in this RFC

- Linux view modules (still refused in v1).
- Android (it should copy whichever shape is chosen, and nothing here
  presumes its build).
- Live-swapping native code in a running process (1024 D6's cut; `dlclose`
  stays forbidden).
- Rust native modules (unchanged).
