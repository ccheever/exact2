## Summary

`@exact/language-model` lets an app prompt the device's own language
model: Apple's Foundation Models on iOS and macOS, Gemini Nano through
ML Kit's GenAI Prompt API on Android, and the browser's model through the
Prompt API on the web, with every other target of LLP 1133 D8 a visible
`later` or `absent`. Its tier 1 is the Prompt API's: `LanguageModel.availability`,
`LanguageModel.create`, a session's `prompt` and `promptStreaming`,
`responseConstraint` for structured output, `append`, `clone` and
`destroy`.

```
use languageModelAvailability, createLanguageModel, promptStreaming,
  languageModelResponse, abortLanguageModelResponse, LanguageModelMessage,
  LanguageModelAvailability, LanguageModelInfo, LanguageModelResponseInfo,
  LanguageModelResponse from "@exact/language-model"

state sessionId = ""
state responseId = ""
resource model = languageModelAvailability() as shape LanguageModelAvailability else empty()
mutation created as shape LanguageModelInfo then ready
mutation asked as shape LanguageModelResponseInfo then streaming
resource reply = languageModelResponse(response=responseId, interval=100)
  as shape LanguageModelResponse else empty()

action start
  send created = createLanguageModel(
    initialPrompts=[LanguageModelMessage(role="system", content="Answer in two sentences.")])
action ready
  match created
    case some(s)
      sessionId = s.id
    case none
      sessionId = ""
action ask(question: string)
  send asked = promptStreaming(session=sessionId, input=question)
action streaming
  match asked
    case some(r)
      responseId = r.id
    case none
      responseId = ""
action stop
  abortLanguageModelResponse(response=responseId)
```

```ts
import { createLanguageModel, prompt } from "@exact/language-model";

const s = await createLanguageModel({});
const json = await prompt({ session: s.id, input: `A title for: ${firstMessage}`,
  responseConstraint: { type: "object", properties: { title: { type: "string" } },
    required: ["title"] } });
return JSON.parse(json.text).title;
```

Tier 2 reaches Apple's use cases, guardrails, sampling, response-token
limit and tool-calling mode, and ML Kit's model preference, sampling and
output limit. Tier 3 hands the app's Swift the `SystemLanguageModel`
before each session is built, and its Kotlin the `ModelConfig` and each
`GenerateContentRequest` builder.

What the parent RFCs did not settle, and this one decides (§0): how
availability is a fact when the model may be downloading, unsupported or
turned off; how streamed text reaches Contract and data code without a
commit per token; how the model calls the app's tools, which is the first
time a module calls the app back; which callers may start the model and
what a tool the model calls may do; and what the agent sees in place of a
model, which must answer the same way every run.

The consumer is Agents (`apps/agents`), the messenger for talking to
models: an "On this device" model beside the OpenRouter ones, which works
with no service and no network, names its conversations by structured
output, and finds earlier conversations through a tool (§10).

## 0. What is new here

1. **Availability is four states and a reason, and it moves by itself.**
   The web's `availability()` answers `unavailable`, `downloadable`,
   `downloading` or `available`, per the options asked; Apple's answers
   `available` or `unavailable` with one of three reasons, one of which
   (`appleIntelligenceNotEnabled`) is the person's choice; Android's
   `checkStatus()` answers the web's four. Each changes without the app:
   a download finishes, the person turns Apple Intelligence off, Chrome
   removes its model when the disk fills. So availability is a live fact
   with a shared `reason` (D5), and **starting a download is a person's
   act** (D5, D10): the web requires transient activation for it, and it
   costs gigabytes.
2. **Streamed text is a value, polled, never a commit per token.** A
   response is a handle whose state is a polled live source answering the
   whole text so far (D7). Text needs no batch and no cursor, unlike
   motion's samples (LLP 1133.013 D5): a response is bounded by the
   model's context window, and each answer contains every earlier one, so
   two answers that coalesce lose nothing. A poll ends when its answer is
   final, which polled sources cannot say today (D15 item 3).
3. **The model calls the app back.** A tool the model chooses to call runs
   the app's own data code, named by the call that created the session,
   and the generation waits for its answer (D9). Until now every call has
   gone from the app to a module (`later`, `call`); this is the first
   module that needs the other direction, and the seam gains it for every
   package (D15 item 1).
4. **The model is an agent inside the app.** Its tool calls are not a
   person's act, and the text it read may be adversarial (a note, a web
   page, a message). So everything a model's tool call causes carries the
   prompt's origin narrowed to `tool` (a wake's stays `wake`): it never
   opens system UI, starts a capture, satisfies presence or starts a
   download (D10). A prompt itself shows no UI, so any caller may make
   one, a tool invocation (LLP 1111) included.
5. **The transcript is the module's; the platform's session is a cache.**
   Android's API has no session at all, Apple's session stops at its
   context limit, and the web evicts old turns. The implementation keeps
   each session's transcript and rebuilds the platform's object from it
   whenever it must (D6): on overflow, on memory pressure, after a
   platform session is lost. This is what makes the web's eviction rule
   tier 1 on every target.
6. **Structured output and tools differ in kind on Android.** Apple and
   the web take a schema at run time; ML Kit takes structured output and
   tools only from Kotlin classes its KSP compiler generates at build
   time, which is a Gradle plugin LLP 1133.001 D9 refuses. So on Android
   a constraint is validated rather than enforced, and tools are `later`
   (D8, D9; §14 question 4).
7. **The substitute is a scripted model.** Under the agent no model runs:
   the implementation answers from a script the drive sets, else a fixed
   reply, streamed at a fixed rate on the session clock, with token
   counts by a fixed rule, so a screenshot after `clock +N` is the same on
   every host and every run (§9). A model's quality is outside what a
   drive or the conformance suite can test, and the module claims nothing
   about it (D3).

## 1. What exists

**Models today are a service's.** Agents and Messages each run a Bun
service on loopback (`apps/agents/service.ts`, `apps/messages/service.ts`)
that holds an OpenRouter key and streams a model's reply; the app's data
code starts a turn with `fetch`, and its Contract polls a cumulative
snapshot while the reply streams (Agents: `task stream when streaming`,
`every(120, poll)`, `apps/agents/app.contract`; Messages every 250 ms).
That is the shape this module takes for the device's own model (D7),
without the service, the key or the network. The coding harness
(`apps/harness`) reaches remote models the same way.

**The package seam** as geolocation built it and the wave 1 RFCs grew it
(`host/apple/modules/ExactPackage.swift`): an implementation answers
`later` and `call`, is told `release(name)`, `release(name, args)`,
`preferred`, `dispose(ids)`, `foreground` and `destroy`, and reaches the
runner only through `changed(topic)` and `log`. Admission records each
commit's origin (`CallOrigin`: `app`, `tool`, `wake`,
`runner/src/runner/modules/admit.rs`), and polled live sources run outside
the timer wheel (`poll.rs`). Nothing lets an implementation run the app's
code, and a request let go before it replies is dropped by the host's
executor without the implementation hearing of it (LLP 1133.009 §14's
as-built note on item 10; a data-code call's handles are not tracked,
`QUEUE.md`).

**The roster** (LLP 1133.000 §3.5) names this module's tier 1 the Prompt
API, its platforms Foundation Models, Gemini Nano through ML Kit GenAI
and Phi Silica, and what tier 2 must reach: guided generation, tool
calling, adapters. `rules/DEFERRED.md` has no entry for it; under its bar
a capability no consumer needs does not exist, so this module needs an
"Expanded" record (§14 question 9).

## 2. Tier 1

### D1 — The Prompt API's names

| Name | Kind | Web | Contract | Data code |
|---|---|---|---|---|
| `languageModelAvailability(expectedInputs=, expectedOutputs=)` | live source; a fact; `sync` on Apple | `LanguageModel.availability(options)` | `resource m = languageModelAvailability()` | `await languageModelAvailability({})` |
| `createLanguageModel(initialPrompts=, expectedInputs=, expectedOutputs=, tools=)` | send; may start a download (D5) | `LanguageModel.create(options)` | `send s = createLanguageModel(…)` | `await createLanguageModel({…})` |
| `prompt(session=, input=, responseConstraint=, omitResponseConstraintInput=)` | send | `session.prompt(input, options)` | `send r = prompt(…)` | `await prompt({…})` |
| `promptStreaming(session=, input=, responseConstraint=, omitResponseConstraintInput=)` | send; answers a response's id at once | `session.promptStreaming(input, options)` | `send r = promptStreaming(…)` | `await promptStreaming({…})` |
| `languageModelResponse(response=, interval=)` | live source; a fact; polled while generating (D7) | the stream's chunks, its end and errors, and the session's `contextoverflow` | `resource r = languageModelResponse(response=id, interval=100)` | `await languageModelResponse({response})` |
| `abortLanguageModelResponse(response=)` | send, answers nothing | `abort()` on the call's `AbortSignal` | statement | `await abortLanguageModelResponse({response})` |
| `appendLanguageModel(session=, input=)` | send | `session.append(input)` | `send x = appendLanguageModel(…)` | `await appendLanguageModel({…})` |
| `measureContextUsage(session=, input=, responseConstraint=)` | source | `session.measureContextUsage(input, options)` | `resource u = measureContextUsage(…)` | `await measureContextUsage({…})` |
| `languageModelSession(session=)` | live source; a fact | `contextUsage`, `contextWindow` | `resource s = languageModelSession(session=id)` | `await languageModelSession({session})` |
| `cloneLanguageModel(session=)` | send | `session.clone()` | `send c = cloneLanguageModel(session=id)` | `await cloneLanguageModel({session})` |
| `destroyLanguageModel(session=)` | send, answers nothing | `session.destroy()` | statement | `await destroyLanguageModel({session})` |
| `prewarmLanguageModel(session=)` | send, answers nothing; a shared word | none | statement | `await prewarmLanguageModel({session})` |

A message is `LanguageModelMessage(role=, content=)`, `role` one of the
specification's `system`, `user` and `assistant`, `content` text. `input`
is a string (a user message, as the web reads one) or a list of messages.
`initialPrompts` may begin with one `system` message (the web throws a
`TypeError` for one anywhere else, and so does admission). A tool is
`LanguageModelTool(name=, description=, inputSchema=)` (D9).
`expectedInputs` and `expectedOutputs` are lists of
`LanguageModelExpected(type=, languages=)`, `type` `text` here; image and
audio inputs, which the web and ML Kit take, stay out (§12).

`prewarmLanguageModel` is a shared word: Apple's
[`prewarm(promptPrefix:)`](https://developer.apple.com/documentation/foundationmodels/languagemodelsession/prewarm(promptprefix:))
and ML Kit's `warmup()` load the model before the first prompt. The web
has no such call (creating a session loads it), so there it answers at
once and does nothing.

### D2 — Values and errors

One representation on every target:

| Shape | Fields |
|---|---|
| `LanguageModelAvailability` | `availability` (`unavailable`, `downloadable`, `downloading`, `available`), `reason: option<enum<device-not-eligible|not-enabled|model-not-ready|unsupported-options|os|policy|disk|not-supported>>`, `progress: option<number>` (0 to 1, while `downloading`, where the platform reports it), `contextWindow: option<number>`, `leavesDevice` (D3), `structuredOutput` (`enforced`, `validated`, `none`; D8), `tools` (bool; D9), `apple`, `android` |
| `LanguageModelInfo` | `id` (a session handle, D6), `contextUsage: option<number>`, `contextWindow`, `tools: string[]`, `overflowed` |
| `LanguageModelResult` | `text`, `contextUsage: option<number>`, `overflowed` (bool: earlier turns were evicted to make room, D6) |
| `LanguageModelResponseInfo` | `id` (a response handle), `session` |
| `LanguageModelResponse` | `id`, `session`, `state` (`generating`, `calling-tool`, `complete`, `aborted`, `failed`), `text` (the whole response so far), `toolCalls: LanguageModelToolCall[]`, `overflowed`, `contextUsage: option<number>`, `error: option<string>`, `reason: option<string>`, `message: option<string>`, `apple`, `android` |
| `LanguageModelToolCall` | `id`, `name`, `arguments` (JSON text), `state` (`running`, `done`, `failed`), `result: option<string>` (JSON text, as the model received it), `truncated` (bool; D9) |
| `LanguageModelSessionInfo` | `id`, `contextUsage: option<number>`, `contextWindow`, `responding` (bool) |

`contextUsage` and `contextWindow` are in tokens, as the platform counts
them: the web's attributes, Apple's
[`contextSize`](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel/contextsize)
and `tokenCount(for:)`, ML Kit's `countTokens`. `contextUsage` is absent
where the platform cannot count: Apple's `tokenCount(for:)` begins at iOS
and macOS 26.4, while `contextSize` is back-deployed to 26.0 ([Foundation
Models updates](https://developer.apple.com/documentation/updates/foundationmodels)),
so on 26.0 to 26.3 `contextUsage` is `none` and `measureContextUsage`
fails `NotSupportedError`.

**Errors** are the specification's `DOMException` names, answered as LLP
1133.006 D8 item 2 answers them (`{error, message}`, a `DOMException` in
TypeScript, `failure(…).code` in Contract), with `reason`, a shared word,
where the name alone does not say what happened:

| Name | When | Platforms' cause |
|---|---|---|
| `NotSupportedError` | a target with no implementation; languages or types the model does not take; a schema outside D8's subset; tools where `tools` is false | web as specified; Apple `unsupportedLanguageOrLocale`, `unsupportedGuide` |
| `NotAllowedError` | the model is turned off (`not-enabled`, `policy`); a download a caller may not start (`person-required`, D10; `activation`, the web's rule, D5); a generation where the platform forbids it (`background`, D10) | web as specified; Apple `appleIntelligenceNotEnabled` at a call; ML Kit `BACKGROUND_USE_BLOCKED` |
| `QuotaExceededError` | an input that does not fit even after eviction, with `requested` (absent where the platform cannot count, D6) and `contextWindow` | web as specified; Apple `exceededContextWindowSize` after D6's eviction |
| `NotReadableError` | output the platform filtered or the model refused (`guardrail`, `refusal`) | web as specified; Apple `guardrailViolation`, `refusal` |
| `SyntaxError` | a response that does not satisfy `responseConstraint` | web as specified; Apple `decodingFailure`; Android's validation (D8) |
| `OperationError` | the platform is busy or over its quota (`rate-limited`, `quota`); the model could not load (`model-not-ready`) | Apple `rateLimited`, `assetsUnavailable`; ML Kit `BUSY`, `PER_APP_BATTERY_USE_QUOTA_EXCEEDED`, AICore binding failures |
| `AbortError` | an aborted response, a destroyed session, a call let go (D6) | as specified |
| `InvalidStateError` | a handle the session does not hold, or a destroyed one; a tool handler prompting the session that called it (D9) | — |

`rate-limited` and `quota` under `OperationError` are a declared
deviation: the specification has no name for a platform's rate limit, and
`QuotaExceededError` already means the context window there.

### D3 — Declared deviations, and what tier 1 does not promise

- **Objects are ids.** A session and a response are handles the
  implementation holds for the app's session (LLP 1133.009 D10 item 10),
  named by `id`, as a track and a recorder are. `promptStreaming` answers
  the response's id at once rather than a `ReadableStream`;
  `languageModelResponse` is the stream, read as a value (D7).
- **Events are fields.** The stream's chunks are `text`; its end is
  `state`; `contextoverflow` is the response's `overflowed`, sticky for
  that response; `downloadprogress` is the availability's `progress`. A
  response that ends stays readable in its final state while anything
  reads it, so an end cannot be lost to coalescing (LLP 1133 D6 rule 7);
  how long an ended one is kept beyond that is D6's.
- **Cancellation is a send or a lifetime.** The web's per-call
  `AbortSignal` is `abortLanguageModelResponse` for a streamed response,
  and for everything else the call's own lifetime: a superseded mutation
  or a replaced answer lets its call go, and the implementation aborts it
  (D6, D15 item 2).
- **A tool runs the app's data code** (D9), named by the tool. The
  specification's tools are an open loop: `prompt` answers `tool-call`
  items and the page answers with a `tool-response` message. Apple's are a
  closed loop: the framework calls `Tool.call(arguments:)` and continues.
  Tier 1 takes the closed loop, because Contract cannot hold a function
  and data code's answers end when they return; the web implementation
  runs the open loop inside itself.
- **`temperature` and `topK` are not tier 1.** The specification marks
  them deprecated for web pages (an extension's alone) and its
  `samplingMode` is an origin trial (Chrome's Prompt API page). Apple's and
  Android's sampling are tier 2 (D11).
- **Text only.** Image and audio inputs wait for a consumer (§12).

**What tier 1 does not promise: the same answer.** Every target has a
different model (Apple's, Gemini Nano in two packagings, and whatever a
browser ships), and a prompt tuned to one reads differently on another.
This is Mozilla's objection to the Prompt API itself
([position](https://github.com/mozilla/standards-positions/issues/1213)),
and it holds here: the module makes the names, shapes, errors, lifetimes
and availability the same, never the text. Apple's own documentation says
the model changes with OS updates and lists three versions so far
([SystemLanguageModel](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel)),
and ML Kit's says different Gemini Nano versions answer the same prompt
differently ([ML Kit GenAI](https://developers.google.com/ml-kit/genai),
`getBaseModelName()`). So an app reads `apple.modelVersion` and
`android.baseModelName` (D11) if it keys prompts by model, and its tests
check structure, not wording; the recipe says so.

**Where prompts go.** Every endorsed implementation runs on the device:
Foundation Models' `SystemLanguageModel`, AICore's Gemini Nano, the
browser's on-device model. `leavesDevice` is false for each. A third
party's implementation over a server model (Apple's iOS 27 `LanguageModel`
protocol makes one easy,
[LanguageModel](https://developer.apple.com/documentation/foundationmodels/languagemodel))
is welcome under LLP 1133.001 and must answer `leavesDevice` true; the
conformance suite checks that the field is declared, not where the bytes
went.

### D4 — Unsaid options are the platform's

LLP 1133 D4: what the author omits is the platform's default.

| Option | Web | Apple | Android |
|---|---|---|---|
| sampling, temperature | the browser's | `GenerationOptions` with each property `nil`: "the framework defers to the underlying model" | the request builder's defaults |
| response length | the browser's | no `maximumResponseTokens` (Apple advises against one except to stop runaway output) | no `maxOutputTokens` |
| guardrails | the browser's | `SystemLanguageModel.Guardrails.default` | AICore's |
| use case | — | `.general` | — |
| `omitResponseConstraintInput` omitted | false: the schema is in the context | `includeSchemaInPrompt: true` | the schema is in the prompt (D8) |
| `expectedInputs`, `expectedOutputs` omitted | the browser's default (text, any language it supports) | the device's languages (`supportedLanguages`) | Gemini Nano's |

**What the module adds to the screen: nothing.** Apple's guidelines ask an
app to "clearly identify when and where you use AI" and to give feedback
during generation ([Generative AI](https://developer.apple.com/design/human-interface-guidelines/generative-ai));
how is the app's design, and exact2 draws no badge, disclaimer or
progress of its own, which would be a tell. Windows' AI text APIs add an
invisible watermark to their output from October 2026
([Phi Silica](https://learn.microsoft.com/windows/ai/apis/phi-silica));
that is the platform's, when the cell is built.

## 3. Availability

### D5 — Availability is a fact, and a download is a person's act

`languageModelAvailability(options)` answers for the model the options
select (the web's rule: `availability()` takes `create()`'s options), so
an app that will create with `expectedInputs=[…languages=["ja"]]` reads
availability with the same options, as speech's status does (LLP 1133.012
D7). Each platform maps:

| Platform | `availability` | `reason` |
|---|---|---|
| web `availability()` | the same word | `unavailable` with no reason the browser gives: `not-supported` |
| Apple `.available`, with `supportsLocale` true for each requested language | `available` | — |
| Apple `.unavailable(.deviceNotEligible)` | `unavailable` | `device-not-eligible` |
| Apple `.unavailable(.appleIntelligenceNotEnabled)` | `unavailable` | `not-enabled` |
| Apple `.unavailable(.modelNotReady)` | `unavailable` | `model-not-ready` |
| Apple, a requested language the model does not support | `unavailable` | `unsupported-options` |
| Apple, an OS below 26 (D14) | `unavailable` | `os` |
| ML Kit `checkStatus()` `AVAILABLE`, `DOWNLOADABLE`, `DOWNLOADING`, `UNAVAILABLE` | the same word | `UNAVAILABLE`: `device-not-eligible`; a bootloader-unlocked device: the same (ML Kit does not run there) |
| a target with no implementation | `unavailable` | `not-supported` |

Apple's `modelNotReady` is "the models aren't available on the user's
device" ([UnavailableReason](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel/availability-swift.enum/unavailablereason)),
and Apple's own example says the cause may be a download "or other
system reasons" ([SystemLanguageModel](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel)).
So it is `unavailable` with `model-not-ready`, not `downloading`: the
module does not claim a download it cannot see. It is the one reason
that is transient by nature, which the system resolves without the app,
and the recipe says to show "not ready yet" for it rather than "not
supported". Apple has no `downloadable` and no `downloading`: the system,
not the app, fetches its model.

**It changes by itself, and the implementation watches.** The person
turns Apple Intelligence on or off in Settings; a download ends; Chrome
deletes its model when free space falls below 10 GB and fetches it again
later (Chrome's Prompt API page). So:

- Apple: `SystemLanguageModel.default.availability` is read again at each
  return to the foreground (the context's `foreground`, LLP 1133.009 D10
  item 3), at each create, and while `model-not-ready` every 10 s
  of the session clock; a change announces the source.
- Android: `checkStatus()` at each return to the foreground and at each
  create; the `download()` flow's events while one runs.
- Web: `availability()` at `visibilitychange` to visible, at each create,
  and from the `monitor`'s `downloadprogress` while one runs.

`available` is a promise about now, not about the next call: a create or
prompt that finds the model gone fails with D2's error and announces the
source.

**A download is started only by `createLanguageModel` while
`downloadable`,** as on the web, where `create()` starts it and its
`monitor` reports progress. Starting one is a person's act:

- On the web the Writing Assistance APIs' shared creation requires
  transient activation when the availability is `downloadable`, and
  rejects with `NotAllowedError` otherwise (§5.2, "create an AI model
  object"). So the web implementation calls `create()` inside the input's
  activation (D15 item 5), as the pickers are (LLP 1069.010 D2), and a
  call whose activation has lapsed fails `NotAllowedError`, `activation`.
- On every target, admission refuses a download start to a tool
  invocation, a model's tool call and a wake (`NotAllowedError`,
  `person-required`, D10), and to an app in the background. A download
  costs the person's disk and data (Chrome asks for 22 GB free and an
  unmetered connection; Microsoft advises asking consent before its
  several-gigabyte download), so it is theirs to start. Any of the app's
  own foreground code may start one (LLP 1133 §0); the recipe recommends
  a button that says what will be downloaded, as Microsoft's guidance does.
- Android's `download()` needs no activation; admission's rule is the
  only one there.
- While `downloading`, `createLanguageModel` waits for the download (the
  web's rule) and answers when the model is available, bounded by the
  call's lifetime; the availability's `progress` reads the platform's
  (`loaded` on the web, `totalBytesDownloaded` over the size where ML Kit
  gives one; Apple never reads `downloading`). A create while Apple reads
  `model-not-ready` fails `OperationError`, `model-not-ready`, at once.

There is **no permission**: no platform asks the person before an app
uses its model, so the module has no permission state, no ticket and no
grant line (§14 question 8). `not-enabled` is the nearest thing, and it
is the person's setting, which the app must not try to change: Apple
gives no URL to the Apple Intelligence settings, and `openURL("app-settings:")`
opens the app's own page. The recipe follows Apple's guidance: offer the
feature where the model is available and the app's other path where it is
not ("ensure a great experience even when generative features aren't
available").

## 4. Sessions and responses

### D6 — Sessions and responses are handles; the transcript is the module's

- **A session** is made by `createLanguageModel` or `cloneLanguageModel`
  and lives until `destroyLanguageModel` or the end of the app's session.
  Its id is a handle (LLP 1133.009 D10 item 10): provisional until its
  reply is delivered, disposed of if the runner drops the reply. A
  session belongs to the app's session, not to the answer that made it,
  so data code may keep its id across answers, as Agents keeps one per
  conversation (§10).
- **A response** is made by `prompt` or `promptStreaming`. `prompt`'s
  generation belongs to its call: a call let go (a superseded mutation, a
  replaced or cancelled answer) is cancelled at the implementation (D15
  item 2), which aborts the generation. `promptStreaming`'s response is a
  handle once delivered and runs to its end, an abort, or its session's
  destruction.
- **An ended response is retired.** Its state is kept while a reader
  reads it, and after that until its session has ended eight newer
  responses; then the implementation forgets it and its id answers
  `InvalidStateError`. A destroyed session's responses go with it. So a
  session kept for a long conversation holds at most eight ended states,
  each bounded (D9's tool records), beside its transcript, which the
  context window bounds. A mutation that reads a response once, as
  Agents' pulse does, reads it while it is kept; an app that needs a
  reply longer keeps the text, as Agents does.
- **One generation per session at a time.** A prompt, append or clone on
  a session that is responding waits behind it in order, as the
  specification's prompt queue does; Apple's `concurrentRequests` never
  reaches the app. On Android, which answers `BUSY` to an app that asks
  too much at once, the implementation also runs one generation per
  process.
- **The transcript is the module's.** The implementation keeps each
  session's messages, its instructions, its tools and each turn's tool
  calls and results, in the platform-neutral form of D1. The platform's
  object is a cache built from it: a web `LanguageModel` (created with the
  transcript as `initialPrompts`), Apple's `LanguageModelSession(model:tools:transcript:)`,
  and on Android nothing at all, since ML Kit's `GenerateContentRequest`
  is one request whose `Content` turns the implementation sends each
  time. The implementation rebuilds the cache when it has none (a clone,
  a memory warning that dropped it, an Apple session that stopped at its
  limit).
- **A turn is the unit.** A session's transcript is its system message
  and then turns: one turn is the input of one prompt (or one append),
  the tool calls and results it caused, and the assistant's text. A
  prompt's `input` is only what is new; the app never sends the history
  again (Agents creates each session from history once, then sends each
  new message). Every end commits the turn before the session's next
  call is admitted: `complete`; `aborted` and `failed` with the text so
  far, so the next prompt is answered by a model that has seen what the
  person sees. A turn that ends with no text still commits its input,
  since the app shows the question it asked (Agents keeps every message
  it sent). The platform caches hold the same turns: the web and Apple
  implementations rebuild after an abort, since neither platform keeps a
  cancelled reply in its own session.
- **Every rebuild replays turns.** A create, a clone and every rebuild of
  a platform session replay the module's turns, tool exchanges included:
  the web cache as messages whose content is the specification's
  `tool-call` and `tool-response` types beside text, Apple's as a
  `Transcript` whose entries carry the tool calls and their output.
  `initialPrompts` from the app are messages (D1); the app's own history
  holds no tool exchanges, so a restored conversation has none.
- **The context window is the web's rule on every target.** When an input
  would not fit, the oldest turns after the system message are evicted,
  each whole with its tool exchanges, until it does, the response reads
  `overflowed`, and if eviction cannot make room the call fails `QuotaExceededError` with `requested` and
  `contextWindow` (the specification's `contextoverflow` steps; Chrome's
  page). Apple's session instead stops with `exceededContextWindowSize`
  and recommends a new session from a trimmed transcript ([Managing the
  context window](https://developer.apple.com/documentation/foundationmodels/managing-the-context-window));
  the Apple implementation measures with `tokenCount(for:)` before it
  prompts and rebuilds from the trimmed transcript, so the error reaches
  the app only when even that fails. On 26.0 to 26.3, where it cannot
  count, it prompts and, when Apple throws `exceededContextWindowSize`
  before the response's first output (a token of text or a tool call, so
  no retry runs a handler twice), evicts the oldest turn, rebuilds and
  retries, until the input fits or only the system message and the new
  input are left (then `QuotaExceededError`, `requested` absent). An
  overflow after the first output, which no target can evict its way out
  of, ends the response `failed`, `QuotaExceededError`, with its text so
  far kept as the turn (above). Android's input limit (under 4,000
  tokens, `countTokens`) is enforced the same way by the implementation.
- **A create evicts as a prompt does.** `initialPrompts` that would not
  fit are trimmed by the same rule, oldest turns first (a user message and
  the assistant messages after it being one turn), and `LanguageModelInfo`
  reads `overflowed`; a create fails `QuotaExceededError` only when the
  system message and the newest turn do not fit. So a long conversation
  restored from the app's history always opens. On Apple 26.0 to 26.3,
  where nothing counts, the trimming happens at the first prompt, by the
  retry above.
- **Threads.** Every entry into the package is on the main thread (LLP
  1067.000 D4); generation runs on the platform's own executor, and its
  text reaches the main thread at most once per poll (D7).
- **The end of the app's session** (`destroy`, LLP 1133.009 D10 item 1)
  aborts every response and drops every session; nothing needs finishing.

### D7 — Streaming: a polled value of the whole text, never a commit per token

`languageModelResponse(response=, interval=)` is a polled live source (LLP
1133.009 D10 item 7): while a reader reads it and the response is
`generating` or `calling-tool`, the runner asks again each `interval` of
the session clock (default 100 ms, at least 50 ms, LLP 1133.013 D5's
floor), outside the timer wheel, with at most one ask in flight. Each
answer is the whole response so far. An omitted `interval` is the
default; a data-code mutation that wants only the end reads the response
once when its own poll or action runs, as Agents' pulse does.

- **The implementation never announces a token.** Platform output lands
  in a cell on the platform's thread: Apple's `ResponseStream` yields
  snapshots of the whole content so far
  ([ResponseStream](https://developer.apple.com/documentation/foundationmodels/languagemodelsession/responsestream)),
  which the cell takes as they come; the web's stream yields successive
  pieces ([MDN](https://developer.mozilla.org/docs/Web/API/LanguageModel/promptStreaming)),
  and ML Kit's `generateContentStream` a chunk's candidate text, which the
  implementation appends. An answer reads the cell. The implementation
  announces the source (`changed`) only when `state` changes, so the final
  text lands at once rather than at the next poll.
- **The poll ends with the response.** A declaration gains `"while"` on
  its poll (D15 item 3): the runner polls only while the last delivered
  answer's `state` is one of the listed values. A complete response is
  never asked again by the clock.
- **Why the whole text, and no cursor.** Motion's batch and cursor (LLP
  1133.013 D5) exist because samples are unbounded and each is distinct.
  A response is bounded by its session's context window (4,096 tokens on
  Apple's model, "under 4,000" input on ML Kit's, the browser's
  `contextWindow`), so the whole text is tens of kilobytes at most,
  and each answer contains every earlier one, so answers that coalesce
  lose nothing. Contract replaces a value; it has no append. A cursor and
  deltas would force every reader to rebuild the text the runner already
  has.
- **What it costs.** At 100 ms a streaming response is ten commits a
  second while it is read, each relaying the text and laying it out. LLP
  1133.009 D13's budget applies: 2 ms of main-thread time per update on an
  iPhone 17 Pro's simulator on the live clock, measured in stage 0 with a
  4,000-token reply in a Contract `p` and in Agents' Markdown (§13). If it
  fails, the floor rises to what passes, as LLP 1133.013 D5 says of its
  own.
- **Data code** reads a response as any live source: a resource's answer
  that reads `languageModelResponse` is asked again each poll, and a
  mutation's answer reads it once (LLP 1133.002 D5). Agents' pulse, a
  mutation sent every 120 ms while a reply streams, reads it once per
  pulse (§10). An answer must not start the generation it reads: a
  resource's answer that calls `promptStreaming` and reads its response
  would start a new one at each poll, so the bake refuses a data source
  that does both with one handle where it can see it
  (`language-model-self-read`), and admission refuses at run time a
  `promptStreaming` from an answer that is a poll's re-ask of itself.
  Starting belongs to an action or a mutation.
- **Tool calls** appear in `toolCalls` as they start and finish, and
  `state` reads `calling-tool` while one runs (D9), so an app can say
  what is happening, as Apple's guidance asks.

### D8 — Structured output

`responseConstraint` is a JSON Schema, as the specification takes it.
The module accepts one subset on every target, the one each platform can
carry, and refuses the rest by name (`NotSupportedError`, at bake for a
literal and at admission for a computed one):

| JSON Schema | Apple's `DynamicGenerationSchema` |
|---|---|
| `type: "object"` with `properties` and `required` | `init(name:description:properties:)`, a property optional when not required |
| `type: "string"`, with `enum` | a string schema; `anyOf` of the choices |
| `type: "string"`, with `pattern` | a regex guide, where Apple's guides accept it (else `NotSupportedError`, as `unsupportedGuide`) |
| `type: "number"` or `"integer"`, with `minimum`, `maximum` | a numeric schema with range guides |
| `type: "boolean"` | a boolean schema |
| `type: "array"`, with `items`, `minItems`, `maxItems` | `init(arrayOf:minimumElements:maximumElements:)` |
| `description` | the schema's or property's description |
| `$ref` to `$defs` | `init(referenceTo:)` |

Anything else (`oneOf`, `allOf`, `not`, `if`, formats, a regular
expression as the whole constraint) is outside it. The web takes the
schema as it is; Apple builds a `GenerationSchema` from the dynamic
schemas and calls `respond(to:schema:includeSchemaInPrompt:options:)`
([DynamicGenerationSchema](https://developer.apple.com/documentation/foundationmodels/dynamicgenerationschema)).
Both constrain decoding, so a response always conforms; the text answered
is the JSON.

**Android validates.** ML Kit's structured output (alpha) takes its
schema only from Kotlin `@Generable` classes that its KSP compiler,
`com.google.mlkit:genai-schema-compiler`, turns into code at build time
([structured output](https://developers.google.com/ml-kit/genai/prompt/android/structured-output));
its reference documents no run-time schema type. A KSP compiler is a
Gradle plugin, which an implementation may not add (LLP 1133.001 D9; LLP
1133.008 D8 item 5). So the Android implementation puts the schema in the
prompt (unless `omitResponseConstraintInput`), parses and validates the
answer, asks once more on a mismatch with the error appended, and fails
`SyntaxError` on a second. `structuredOutput` reads `validated` there and
`enforced` on Apple and the web, so an app knows. Generating `@Generable`
classes from the app's literal schemas at bake, and admitting the KSP
plugin, is the alternative (§14 question 4).

**In Contract,** a schema is written as the name of one of the app's
shapes, `responseConstraint="TitleSuggestion"`: a new declaration type,
`shape-name`, a literal the bake checks names a shape and converts to D8's
subset (D15 item 4). A Contract `prompt` with a constraint answers the
constrained value itself, typed as that shape, so its mutation reads
`as shape TitleSuggestion`; its declaration says so (`"answers":
{"shape": "responseConstraint", "else": "LanguageModelResult"}`, D15 item
4). `promptStreaming` in Contract answers `text`, the JSON so far, and
the parsed value is data code's to make. In data code
`responseConstraint` is a JSON Schema object and `prompt` answers the
JSON as `text`, as the web does.

## 5. Tools

### D9 — A tool is the app's data code, which the model calls back

```
use createLanguageModel, LanguageModelTool, LanguageModelInfo from "@exact/language-model"

shape ConversationQuery
  query: string

action open
  send created = createLanguageModel(tools=[LanguageModelTool(name="findConversations",
    description="Finds the person's earlier conversations about a topic",
    inputSchema="ConversationQuery")])
```

```ts
// app.ts: the handler is the data source the tool names.
const sources: Sources = {
  findConversations: async ([{ query }], _store, storage) => {
    await load(storage);
    return matches(query).slice(0, 5).map((c) => ({ title: c.title, excerpt: c.excerpt }));
  },
  // …
};
```

**The handler.** A tool's `name` names a data source the app's data
module answers, its **handler**: a TypeScript `sources` entry or a Rust
source, as a resource's or a mutation's source is. The bake finds each
tool's name in a literal `tools=` (Contract or data code; a computed list
is refused, since the handler must exist at bake), checks the data module
answers it, and adds it to the generated `Sources` type with the tool's
input shape as its one argument and a JSON value as its answer
(`language-model-tool-handler`). The handler's grants are the data
module's own, as every source's are.

**The call.** When the model calls a tool, the implementation asks the
runner to run that handler with the model's arguments (D15 item 1). The
runner:

1. checks the name is one this session's creating call listed, and the
   arguments against the input schema (a mismatch answers the model an
   error without running anything);
2. commits the response's `calling-tool` answer with the call in
   `toolCalls`, and starts the handler when every live reader of the
   response has been delivered that answer or one poll period has
   passed, whichever is first (at once with no reader); a reader whose
   answer is still waiting on other work may miss `calling-tool`, and
   every reader, a mutation that reads once included, sees the call in
   `toolCalls`, which keeps it; then it admits the run with the origin
   `CallOrigin::min(the prompt's origin, tool)` and the cause `model`
   (D10), where the prompt's origin is the one the runner stored on the
   response's handle when it admitted the `prompt` or `promptStreaming`
   that made it, kept for the response's life, after that call has
   answered: a wake's prompt stays `wake`, never widened to `tool`, even
   on a session the person created;
3. asks the handler as it asks a mutation's source, a fresh answer that
   subscribes to nothing and fills no Contract slot, under the runner's
   ordinary data-code lifetime;
4. hands the answer, as JSON text, to the implementation, which returns
   it to the model; a failure or a refusal is returned as the tool's
   error, and the generation continues;
5. bounds the run by `toolTimeout` (default 30 s of the session clock): a
   handler that has not answered by then is let go and the model is told
   it failed;
6. lets the run go when the response is aborted, its session destroyed or
   the app's session ends;
7. counts the response's tool calls: past 16 in one response, the
   response ends `failed`, `OperationError`, `tool-limit`, with its text
   so far committed as its turn (D6). On the web, where each call is
   another round of prompting, the count bounds the rounds too.

**What a response keeps of a call.** `toolCalls` records each call's
`arguments` and `result` as the model saw them, each cut to its first 4
KB in the response's state (marked by `truncated`), so a response's state
is bounded whatever the tools return: 16 calls of at most 8 KB beside a
text the context window bounds. The transcript keeps what the model
received; eviction removes it with its turn.

The response shows each call in `toolCalls` (D7), and the journal and
`state.extensions` record the handler, its arguments, its answer's size,
its origin and its time.

**Each platform's loop.**

- **Apple** is closed: the implementation gives the session one `Tool`
  per declared tool, whose `Arguments` is `GeneratedContent`, whose
  `parameters` is the `GenerationSchema` built from the input schema
  (D8), and whose `call(arguments:)` awaits the runner's answer
  ([Tool](https://developer.apple.com/documentation/foundationmodels/tool)).
  The framework places the tools in the prompt, calls them and continues.
  The protocol admits this: `Tool`'s `Arguments` need only conform to
  `ConvertibleFromGeneratedContent`, and `GeneratedContent` conforms to it
  (and to `Generable`), while `parameters` is the tool's own
  `GenerationSchema` property. Stage 2 proves it first on a device. If the
  framework refuses a tool whose schema is not its `Arguments`' own, the
  bake writes, for each literal tool, a `@Generable` struct from its input
  schema and a `Tool` over it into the implementation's generated adapter,
  Swift the app's build already compiles (LLP 1133.001 D9 forbids a module
  resolving packages, not generated Swift); the tier stays 1.
- **The web** is open: a session created with tools takes
  `expectedOutputs` including `tool-call`; a `prompt` that answers
  `tool-call` items makes the implementation run each through the runner
  and send a `tool-response` message with `LanguageModelToolSuccess` or
  `LanguageModelToolError`, then prompt again, until the model answers
  text ([explainer](https://github.com/webmachinelearning/prompt-api)).
  A browser without tool use answers `availability` with
  `expectedOutputs=[tool-call]` as `unavailable`, and `tools` reads false.
- **Android:** ML Kit's tools, like its schemas, are generated by KSP from
  annotated Kotlin (`com.google.mlkit.genai.schema.tools`, "runtime
  discovery of generated tool details"), so tools are `later` there for
  D8's reason; `tools` reads false, and a session created with tools fails
  `NotSupportedError`. Prompting for a JSON tool call and validating it
  would work as D8's validation does, but a 4,000-token model choosing
  among tools by prompt alone is not a tool loop an app can rely on.

**Reentry.** A handler runs in the data runtime like any answer and may
call the module: a handler that prompts another session works; one that
prompts the session whose response called it fails `InvalidStateError`
at once, since that session's queue is waiting on the handler. A
model's tool call made inside a handler's own prompt is admitted with the
same origin, and the chain is bounded at two models deep
(`InvalidStateError` beyond it).

*Rejected:* the specification's open loop as tier 1. Each tool call would
end the response with `tool-call` items, and the app would answer them
from an action or a data answer and prompt again. Contract would hold
glue for every tool, Apple's framework would hold a `Tool.call` open on
the app's next action for as long as the person took, and the result
would be what the runner does here, written by every app.

*Rejected for now:* LLP 1111's `tool` lines as the model's tools. They
are the app's tools for a person's agent, with schemas from the plan, a
consequence class and consent, and the on-device model is one more agent
that could use them. LLP 1111 is parked and unbuilt, so a handler is a
data source now; when its `tool` lines exist, letting a session name them
is the obvious next step (§14 question 7).

### D10 — Who may call, and what the model's tools may do

Every call carries its origin (LLP 1133.002 D12). This module shows no
system UI, so its rules are about cost and about the model as a caller:

| Origin | availability, session state | create, prompt, append, clone (model available) | start a download | what a model's tool call runs |
|---|---|---|---|---|
| a person's input; the app's own code in the foreground | answers | proceeds | proceeds (the web: inside the input's activation) | `tool`, cause `model` |
| a tool invocation (LLP 1111) | answers | proceeds under the app's grants | `NotAllowedError`, `person-required` | `tool`, cause `model` |
| a model's tool call (D9) | answers | proceeds | `NotAllowedError`, `person-required` | `tool` (or `wake`, if its own prompt's was), cause `model` |
| a background wake (LLP 1114.001) or the app in the background | answers | Android: `NotAllowedError`, `background`; Apple: proceeds, and the platform may answer `rate-limited`; web: the browser's | `NotAllowedError`, `person-required` | `wake`, cause `model` |
| the development agent | §9 | §9 | §9 | §9 |

**A model's tool call is never more than `tool`.** The handler and
everything it causes are admitted with `CallOrigin::min(the prompt's
origin, tool)`, the prompt's origin being the one the runner recorded for
the call that started the response, never one the implementation passes
back (LLP 1133.008 D8 item 2's rule): a person's or the app's prompt gives
`tool`, a wake's stays `wake`. So: no permission prompt, no capture
start (LLP 1133.009 D9), no presence check (LLP 1133.010 D12), no
download, no `openURL("app-settings:")`. A person's tap that sends a
prompt is the person asking the model, not the person approving what the
model then chooses; the model reads text the person did not write (a
message, a note, a page), and that text can instruct it. Apple's
guidelines say the same of the app's own design: "avoid automating
destructive actions … ask for confirmation before performing a
significant action on someone's behalf" ([Generative AI](https://developer.apple.com/design/human-interface-guidelines/generative-ai)).
So a handler that would change something the person cares about answers
the model with what it would do, and the app shows that and lets the
person do it from their own input; the recipe gives the pattern. A
session a wake may prompt can run its handlers with no one present, so
its handlers must be safe to run unattended; the recipe says so. The
journal records the origin and the cause (`<origin>:model:<response>`,
such as `tool:model:r3` or `wake:model:r7`), so a drive and
`state.extensions` show which work the model caused.

**Prompting is open to a tool invocation.** An agent calling the app
through LLP 1111 may cause a prompt: it opens no UI and uses nothing the
app's grants do not allow. What the model then calls is still `tool`.
When agents come to delegate authority to agents (LLP 1133.002 D12's
direction), the model is the least of them: it holds what the call that
prompted it held, narrowed to `tool`, and never presence (LLP 1133.010
D12).

**In the background.** ML Kit permits inference only while the app is the
top foreground application, and answers `BACKGROUND_USE_BLOCKED`
otherwise, from a foreground service too ([ML Kit GenAI](https://developers.google.com/ml-kit/genai));
admission refuses it first, as a target restriction (LLP 1133.002 D14
step 2), and a response running when the app leaves the foreground on
Android ends `failed`, `NotAllowedError`, `background`, with its text so
far. Apple rate-limits only an app in the background
([`rateLimited`](https://developer.apple.com/documentation/foundationmodels/languagemodelsession/generationerror/ratelimited(_:))),
so a wake's prompt proceeds there and may fail `rate-limited`; the
module takes no background task of its own, and a response still running
when iOS suspends the process resumes or fails as the framework decides.

### D12 — Access hatches

## 7. Cost, and every target

### D13 — Memory, heat, quotas and size

**The model is the system's.** Apple ships its model with the OS, AICore
holds one Gemini Nano for every app ("apps share the on-device Gemini
Nano model"), and a browser downloads one for every origin. So the app's
binary carries no weights, and two apps using the model do not hold two.
What an app holds is its sessions: transcripts (bounded by the context
window, kilobytes each) and the platform's per-session state, which the
module treats as a cache (D6). On a memory warning
(`UIApplication.didReceiveMemoryWarningNotification`, Android's
`onTrimMemory`) the implementation drops the platform objects of
sessions that are not responding, and rebuilds them on their next use.

**Heat, battery and quotas are the platform's to enforce.** The platforms
throttle generation themselves and say so only through errors: AICore's
per-app quota answers `BUSY` and a long-term `PER_APP_BATTERY_USE_QUOTA_EXCEEDED`;
Apple's rate limit applies in the background. The module surfaces them
(`OperationError`, D2) and adds no governor of its own, which would differ
from what a hand-built app sees. What exact2 controls is how much work an
app's code can start without meaning to:

- one generation per session at a time, and on Android per process (D6);
- a generation's lifetime is its caller's, so a resource asked again
  lets its last prompt go rather than stacking another (D6);
- a streamed response costs commits at the poll's rate, not the model's
  (D7);
- a development build journals a data source whose answers start more
  than ten generations a minute (`language-model-reprompt`): detection,
  not enforcement.

The device's thermal state is the `device` module's fact (LLP 1133.000
§3.3), read beside this one by an app that wants to defer optional work.

**Size and boot.** An app that does not import the module links none of
it (LLP 1047.001). One that does loads it with the app's module after
first pixel; nothing runs before first pixel, and no model loads until a
session is created or prewarmed. Apple's implementation links
FoundationModels, weak-linked below iOS and macOS 26 (D15 item 6).
Android's adds ML Kit's `com.google.mlkit:genai-prompt` (beta) and AICore
binding through the locked Gradle graph (LLP 1133.008 D8 item 5). The web
loads a chunk of page code. Stages 2 and 4 measure each with LLP 1047's
probe and record it here.

**The seam additions,** each general, each proved by the out-of-tree
fixture before this package uses it (LLP 1133.001 D8):

1. **A module calls the app back.** The package context gains
   `invoke(handle, handler, args, reply)` on every host
   (`ExactPackageContext`, Android's `ExtensionContext`, the web
   implementation's context), `handle` being the work the call serves (a
   response here). The runner stores, on each handle a reply delivers,
   the origin it admitted the handle's call with, and keeps it for the
   handle's life, so it is there after the call has answered. It accepts
   only a handler that a literal the bake resolved named for that handle
   (here: listed by the creating call of the response's session), admits
   it with `CallOrigin::min` of the handle's stored origin and `tool`,
   with the cause the implementation states (`model`), runs the data
   source as D9 says, and replies on the main thread. It records the run
   against the handle, so `dispose`, an abort or the session's end lets
   it go. Any
   package whose platform calls back into an app (a map's tile provider,
   App Intents' perform) would use it with its own cause.
2. **A request let go is cancelled.** When the call that made a pending
   request is let go (a superseded mutation, a replaced or cancelled
   answer, data code's included), the runner tells the implementation
   `cancel(request)`, so long work stops rather than running to a reply
   nobody reads. Today the host's executor drops the reply silently
   (LLP 1133.009 §14, item 10's note), and a data-code call's handles are
   not tracked (`QUEUE.md`); both are closed here, since Agents calls the
   module from data code.
3. **A poll that ends with its answer:** `"poll"` gains `"while"`, a field
   and the values for which the runner keeps polling; a delivered answer
   outside them stops the clock's asks until a change announces the
   source again. `mediaRecorderState` (LLP 1133.009 D1) may use it.
4. **Shapes as schemas.** A declaration type `shape-name`, a string
   literal naming one of the app's shapes, which the bake converts to the
   JSON Schema subset the interface declares (D8) and sends as JSON; and
   an answer typed by such an argument, `"answers": {"shape": "<option>",
   "else": "<Shape>"}`, so the mutation's `as shape` is checked against
   the named shape (`contract-module-answers`).
5. **A send inside the person's activation, on the web.** A send admitted
   from a person's input reaches the web implementation in that input's
   dispatch where its chunk is loaded, as the pickers' commands are (LLP
   1069.010 D2), and the web implementation's chunk loads at the app's
   first read of any of its names, so a later press finds it loaded. A
   send from data code reaches it within the activation's lifetime or
   not at all, and the browser decides.
6. **A framework newer than the app's floor is weak-linked.** An Apple
   implementation declares `"frameworks": {"FoundationModels": {"ios":
   "26.0", "macos": "26.0"}}`; the build weak-links it where the app's
   `minimumOS` is lower (Agents' iOS floor is 17.0) and the implementation
   checks `#available` before touching it.

Each is apparatus under `rules/RULES.md` and lands with this ruling. The
rest is inherited unchanged: handles and their disposal, `release(name,
args)`, `destroy`, `now()`, the foreground, preferred values reaching the
implementation, and the camera's split under the agent (LLP 1133.008 D8
item 9).

## 9. The substitute: the agent model

**The implementation is its own substitute,** in LLP 1133.008 D8 item
9's split: under the agent the runner admits each call (origins, the
foreground, downloads), and each implementation then runs, told so, loads
no model, asks the platform for nothing and calls no hatch. The **agent
model** is specified once, in the interface's conformance suite, and each
implementation carries it; the suite holds the three equal by driving one
fixture on each host and comparing state and screenshots, as recording's
synthetic signal is held (LLP 1133.009 §10).

- **Availability** is `available`, `contextWindow` 4096, `structuredOutput`
  `enforced`, `tools` true, with each target's restrictions applied (the
  Android implementation's agent model answers `structuredOutput`
  `validated` and `tools` false, so a drive sees Android's limits). `prefer
  extension language-model.languageModelAvailability={…}` overlays it (LLP
  1133.009 D10 item 11): `{"availability":"unavailable","reason":"not-enabled"}`,
  `{"availability":"downloadable"}`, `{"availability":"downloading","progress":0.4}`.
  A `createLanguageModel` while `downloadable` from an admitted origin
  sets `downloading` with `progress` 0 and waits; the drive completes it
  with `{"availability":"available"}`.
- **A reply** comes from the script, `prefer extension
  language-model.responses=[…]`, a list each `prompt` and `promptStreaming`
  of the app's session takes the next entry of, in admission order. An
  entry is `{"text": "…"}`; `{"value": {…}}` (the canonical JSON of the
  value is the text); `{"toolCalls": [{"name": "…", "arguments": {…}}],
  "text": "…"}` (the calls run first, through D9's path, then the text);
  `{"error": "NotReadableError", "reason": "refusal"}`; or `{"text": "…",
  "hold": true}`, which stops before its last token until aborted. With the
  script empty, the reply is `Agent model reply N.`, N counting the
  session's responses from 1; under a constraint it is the schema's first
  instance: each required property in order, a string's first `enum`
  value or `""` (or a `pattern`'s shortest match, refused at bake where
  the suite has none), a number's `minimum` or 0, `false`, and an array of
  `minItems` first instances.
- **A scripted reply is checked as the platform checks.** An entry that
  does not satisfy the response's constraint fails the response
  `SyntaxError` on targets whose `structuredOutput` is `validated`, and on
  the others fails the drive's `prefer` with the schema's complaint named,
  since a constrained platform cannot produce it. A tool call whose name
  the session did not list, or whose arguments fail its input schema, is
  refused the same way.
- **Streaming** runs on the session clock: the text is cut into tokens at
  the end of each run of whitespace, and one token lands each 25 ms from
  the moment the generation starts (after any tool calls), so `clock +100`
  shows four. `prefer extension language-model.rate=0` lands each reply
  whole. A poll after `clock +N` answers everything N revealed (LLP
  1133.009 D1's rule for elapsed time); `clock settle` lands nothing the
  clock has not reached. `prompt`, which answers once, answers whole at
  once.
- **Tokens** are counted by one rule on every host: a message costs 4
  plus ⌈its UTF-8 bytes ÷ 4⌉; a schema costs ⌈its JSON's bytes ÷ 4⌉ unless
  omitted. `prefer extension language-model.contextWindow=256` shrinks the
  window, so a drive reaches D6's eviction in three turns.
- **Tool calls under the agent** run the app's real handler through the
  same runner path as production, admitted as D9 step 2 says, so a drive
  tests the app's own tool code.

On a target with no implementation (tvOS, Linux, Windows today) the
interface's declared part answers under the agent:
`languageModelAvailability` is `unavailable`, `not-supported`, and every
other name fails `NotSupportedError`, as in production.

The script, the rate and the window are agent-only sources of the
interface (`"source": "responses", "agent": true`, and likewise `rate`
and `contextWindow`), the form `camera.picture` takes (LLP 1133.008 D7):
the runner accepts a `prefer` only of a declared source, and pushes each
to the bound implementation when it is set (LLP 1133.008 D8 item 9).

**Disclosure:** `state.extensions` lists the session's model sessions
(their transcripts' sizes, `contextUsage`, tools), each response's state,
text length and tool calls with their origins, the script's remaining
entries, and each answer's origin.

**Production:** none of it.

## 10. The consumer: Agents

Agents is a messenger for talking to models, each conversation one model
at one thinking effort, through a loopback service holding an OpenRouter
key (`apps/agents/README.md`). It needs the device's model now for the
reasons Apple's guidance gives for one: no key, no service to run, no
network, and nothing leaves the device. It gains:

- **"On this device"** in the model menu, beside the featured models,
  shown while `languageModelAvailability()` is anything but `unavailable`
  with `device-not-eligible` or `not-supported`. While `not-enabled` it
  reads "Turn on Apple Intelligence in Settings to use this model" (on
  Apple) and is disabled; while `downloadable`, choosing it shows a
  Download button that says what it will fetch, whose press creates the
  session (D5); while `downloading`, the progress; while `model-not-ready`,
  "The on-device model isn't ready yet"; while `available`, it
  opens like any model. Thinking effort does not apply and is hidden.
- **A conversation on it** is a session made by `createLanguageModel`
  from the conversation's history as `initialPrompts` (so a relaunch, a
  dev reload or a lost session restores it), kept in the conversation
  object of `app.ts` with the session's id. Sending a message calls
  `promptStreaming` with that message alone as `input` (D6's turn) from
  `command`'s mutation answer and keeps the
  response id as `job`; `pulse`, already sent every 120 ms while a reply
  streams, reads `languageModelResponse` once and copies `text` into the
  reply, as it copies the service's cumulative snapshot today. Stop calls
  `abortLanguageModelResponse`; the reply keeps what it had. When a
  create (restoring a long conversation) or a response reads
  `overflowed`, the conversation shows the line "Earlier messages no
  longer fit in the on-device model's memory" above the newest reply
  from then on.
- **Titles by structured output.** `name()` asks a fresh session `prompt`
  with `responseConstraint` `{title: string}` (D8) instead of the
  service's `/title`, and destroys the session.
- **A tool: earlier conversations.** Where the availability reads
  `tools` true (Apple, and a browser with tool use), the on-device session
  is created with `findConversations` (D9's example); where it reads
  false (Android, other browsers), without it, and the rest of the
  feature is unchanged. Its handler searches the
  conversations `app.ts` already keeps and answers up to five titles with
  excerpts, so the on-device model, whose window holds a few pages, can
  answer "what did I ask Claude about lifetimes last week?". It is the
  smallest real use of tool calling in the repository: the data is the
  app's and local, and the model cannot hold it. The reply shows
  "Searched your conversations for “lifetimes”" above its text from
  `toolCalls`, which keep every call, so the line does not depend on a
  pulse landing while the handler runs. It reads only;
  nothing the model calls changes a conversation.
- **An Android crate** (Agents has none), as geolocation's slice gave
  Weatherlight one.

## 14. Rulings (Charlie, 2026-10-23: "Accept all (Recommended)")

   or the app's foreground code, refused to tools, a model's tools and
   wakes; on the web inside the input's activation. *Proposed: yes (80%).*

   D9),** until a Gradle plugin is admitted for ML Kit's KSP schema
   compiler, with the bake generating `@Generable` classes from the app's
   literal schemas. *Proposed: yes (70%); admitting the plugin is the
   alternative, at the cost of LLP 1133.001 D9's rule and a compiler step
   in every Android build that uses the module.*
