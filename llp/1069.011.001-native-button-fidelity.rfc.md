## Summary

`button appearance="auto"` draws UIKit's own `UIButton` (LLP 1069.011). An app that moved nine real buttons onto it found five differences from the same screens built by hand:
- no space between symbol and title
- no size or capsule
- no title font
- no wrapping
- `gray` ignoring the tint

So it kept its custom buttons. This RFC closes those gaps by four rules:

1. **Absent means the platform's own answer, asked at runtime.** When an author writes nothing, the host either leaves UIKit's field alone or, where UIKit names a standard through an API, asks that API on the running OS:
   - the gap comes from UIKit's system spacing
   - the symbol's size comes from the title font

   No number measured on one OS version is written into a table or the code.
2. **Where CSS has a name, it is the name.** These mean on a native button what they mean on a browser's `<button>`:
   - `gap`
   - `flex-direction`
   - `font-size` and `font-weight`
   - `white-space` and `line-clamp`
   - `text-align`
   - `color`
   - `aria-busy`

   Where CSS has no name (the platform's control sizes and corner styles), the row is `-exact-` prefixed (LLP 1081).
3. **The face is semantic.** A native button's children are UIKit's semantic fields, never laid-out views. They become `title`, `subtitle`, `image` and `imagePlacement`, and a busy button shows `showsActivityIndicator`. UIKit lays them out, as it does in its own apps.
4. **UIKit draws all the chrome, glass included.** Every row here sets a content field of `UIButton.Configuration` that all twelve styles honour. Background, border, padding, shadow and material stay refused on every style (LLP 1069.011 D6). No style needs the author to draw any part of it.

## 1. Why, and what came before

Our fork met the same need on 2026-10-01 with the vendor row `-exact-apple-button-style` (`7b1a37e8b`). `main` had no native buttons then. Lexy needed UIKit's touch handling (highlight, drag-off, scroll cancel) and the system styles. The row:
- turned every `button` into a `UIButton`
- drew a configuration from the one text and one symbol
- read the button's `border-radius`, the text's `font-size`/`font-weight` and the laid-out boxes' spacing

Lexy's buttons look right with it, and they are the target here. Its shape is the problem, not its look:
- it reads box rows that LLP 1069.011 D6 refuses on a native button
- it has no meaning on the web, macOS or Linux (the report's §3, LLP 1081 §1)

This RFC gives the same look through rows every host understands. §5 moves Lexy and deletes the vendor row.

**Native button or the author's boxes** is CSS's own switch: `appearance="auto"` or `none` (LLP 1069.011 D1), settable in a class. Nothing here changes it.

## 2. Measured (iOS 27 simulator, 2026-10-06)

These are evidence for the design, not values anything uses. Probes: `UIButton.Configuration` factories and UIKit layout in a bare process.

| | Result |
|---|---|
| `imagePadding` default | 0 on every factory and size: the symbol and title touch (3.7 pt of ink gap, side bearings only) |
| UIKit's system spacing after an image (`constraint(equalToSystemSpacingAfter:)`, `UIStackView.spacingUseSystem`) | 8 at body, subheadline and footnote |
| SwiftUI `Label` in a button (for comparison only) | the same gap as `imagePadding` 8: UIKit's system spacing is the platform's standard |
| `UIListContentConfiguration.imageToTextPadding` | 16 (cell), 10 (sidebar): a list row's own spacing, not a button's |
| Symbol size | the configuration's default symbol is larger than its title; `UIImage.SymbolConfiguration(font:)` matches it to the title font |
| Wrapping | `.byWordWrapping` with 0 lines: UIKit wraps (LLP 1069.011's one line is Exact's) |
| Semantic fields | `subtitle`, `imagePlacement` (`.leading`, `.trailing`, `.top`, `.bottom`), `titlePadding` (1), `showsActivityIndicator` (keeps the size), `indicator` (`.automatic`; `.popup` for a menu) |
| Glass | `glass` and `prominent-glass` honour `imagePadding`, a title font, `buttonSize` and `baseForegroundColor` exactly as `gray` does |
| Threads | `UIButton.Configuration` is usable off the main thread; `UIButton` is main-actor |

## 3. Design

**D1. Absent is the platform's own answer.** For each row below, when the author has not written it:
- If UIKit's field is a real default (wrapping, the font for the size, corners, placement), the host does not write it, so a future OS's default shows through.
- If UIKit leaves a field at zero and names the standard through a separate API, the host asks that API on the running OS. This applies to two fields:
  - the gap (D3, UIKit's system spacing)
  - the symbol's size (D4, `SymbolConfiguration(font:)` of the title's font)
- It never writes a number we chose or measured.

The agent's `layout` reports, per row, whether it was authored and what was drawn.

**D2. Only what is on the button applies.** A browser's UA sheet resets `font`, `color`, `white-space` and `text-align` on `<button>`, so an ancestor's typography does not reach it. Exact's native button does the same: these rows count only when written on the button or its class. `accent-color` stays inherited (LLP 1069.011 D7), as in CSS.

**D3. The face is UIKit's semantic fields.** LLP 1069.011 D5 allowed one text and one symbol. This allows what `UIButton.Configuration` names:

| Children (in order) | iOS | web |
|---|---|---|
| a `text` | `title` | the text |
| a second `text` | `subtitle` (smaller, secondary, as UIKit draws it) | a second line (`flex-direction` and font as the UA rule lays it) |
| an `image` with a `symbol:` | `image` | the `img` |
| image before the texts / after | `imagePlacement` `.leading` / `.trailing` in a row, `.top` / `.bottom` with `flex-direction: column` | the CSS itself |

- **`flex-direction`** (`row` or `column`, the face's only layout row, now admitted) chooses the axis. The children's order chooses the side. Lexy's control tiles, an icon over a label, are `flex-direction=column` with the image first. That is `imagePlacement = .top`, as Apple's own icon-over-label buttons are drawn.
- **`gap`** (or `column-gap`/`row-gap` on that axis) is `imagePadding`.
  - Absent: UIKit's system spacing between an image and the title's font, asked at runtime (D1). On iOS 27 that is 8, SwiftUI's spacing too.
  - Authored: the length.
- **The title-to-subtitle spacing** is UIKit's `titlePadding`, never authored.
- **`aria-busy="true"`** is `showsActivityIndicator`: UIKit puts its spinner where the image is and keeps the size. On the web, `aria-busy` is the attribute itself, and the UA rule shows a spinner in place of the `img`. Lexy's header refresh button is this.
- **A menu invoker's** `indicator` is `.popup`, once native invokers land (LLP 1069.011.000 §5).

The web lays the same children out with its own CSS and has no "system spacing". So absent `gap` on the web draws the face inline, with a space between image and text. That is the gap a browser gives `<button><img> Sign In</button>`: the font's own space, a declared approximation of UIKit's 8. macOS: `NSButton` has `imagePosition` (all four sides) and no padding or subtitle. Authored `gap` and a subtitle are declared stand-ins there, reported by the agent. Linux: its look.

**D4. `font-size` and `font-weight` set the title's font; the symbol follows the font.**
- iOS: `titleTextAttributesTransformer`, the system font at that size and weight, scaled for Dynamic Type as Exact's text is. Either row alone changes only that axis of the platform's default title font.
- In every case, authored or not, `preferredSymbolConfigurationForImage` is `UIImage.SymbolConfiguration(font:)` of the title's font. The symbol matches the text as it does in UIKit's own labelled buttons.
- macOS: `NSButton.font`.
- The web: the CSS; the symbol is `1em` of it.
- `font-family` stays refused.

**D5. Wrapping is `white-space` and `line-clamp`.**
- Absent: UIKit's default (wraps), and a browser's `<button>` wraps too.
- `white-space: nowrap`: one line, truncated at its end.
- `line-clamp: N`: at most N lines, the last truncated.

This lifts LLP 1069.011 D6's one line. macOS push buttons are single-line, a declared stand-in.

**D6. `text-align` places the face.**
- Absent: centred, the platform's default and the UA sheet's.
- `start`, `end`, `left`, `right`:
  - iOS: `contentHorizontalAlignment` for where the face sits in the box, `titleAlignment` for a wrapped title's lines.
  - macOS: `NSButton.alignment`.
  - The web: the CSS, which the UA rule maps onto its flex row's `justify-content`.

Lexy's "Check for update" is `text-align=start` on a full-width button.

**D7. `color` is the label's colour; `accent-color` stays the tint.** UIKit has two fields:
- `tintColor`: the platform decides what it colours. On `gray`, that is nothing.
- `baseForegroundColor`: the title and symbol.

CSS has the same two: `accent-color` and `color`.
- `color` is `baseForegroundColor` on every style, glass included (§2). On macOS it is `contentTintColor`.
- An inherited root accent does not repaint every gray button: UIKit's gray draws its label in the label colour.
- A gray action that reads as an action is `buttonStyle="gray" color=accent()`.

**D8. `-exact-control-size`.** CSS has no control-size vocabulary, so this is an `-exact-` style row (LLP 1081):

| Value | iOS | macOS | Web | Linux |
|---|---|---|---|---|
| `mini` | `.mini` | `.mini` | `x-small` | its look |
| `small` | `.small` | `.small` | `small` | its look |
| `medium` | `.medium` | `.regular` | `medium` | its look |
| `large` | `.large` | `.large` | `large` | its look |

On iOS the value is `buttonSize`; on macOS, `controlSize`. On the web it is CSS's own absolute `font-size` keyword, so the browser's button scales its padding with it: a declared approximation, and no number of ours. Absent: the platform's default (`medium` on iOS 27). The row is styleable like any row, so a class can carry it. A full-width primary action is `-exact-control-size=large` plus `width=100%`; the box rules of LLP 1069.011 D6 are unchanged.

**D9. `-exact-corner-style`.** This is `UIButton.Configuration.CornerStyle`'s vocabulary (`dynamic`, `small`, `medium`, `large`, `capsule`) as an `-exact-` row.
- Absent: the style's own corners (`dynamic`; a capsule for glass).
- iOS: `cornerStyle`.
- macOS 26 design: `capsule` is the push bezel's default shape, and the others are declared stand-ins.
- The web:
  - `capsule` is `border-radius: calc(infinity * 1px)`, CSS's fully rounded end.
  - The sized ones keep the browser's own radius, a declared approximation.

`border-radius` stays refused on a native button, as in LLP 1069.011 D6.

**D10. Which rows apply to which style.** All of D3–D9 apply to all twelve `buttonStyles`: each is a content field of `UIButton.Configuration` every factory honours (§2 measured glass beside gray). What each style owns is its chrome, and it stays refused on every style:
- background, border, padding, shadow
- `backdrop-filter`, `filter`
- `backgroundMaterial`

Glass owns its chrome exactly as `filled` does, and the author's rows reach only its content.

**D11. The first layout is right, and asked of the OS.** Today a native button lays out at 64 × 34 until the host reports UIKit's size after the batch (LLP 1069.011 D3/D6). Every row above would show as a jump on frame two, and with wrapping a single size is not enough. Instead:
- The kernel measures a native button as it measures text, through a host hook and height-for-width: `ControlMeasurer::measure(face, rows, style, offer)`, beside `TextMeasurer` in the same `Hooks`.
- `UIButton` is main-actor and the kernel lays out on the executor thread, so the Apple presenter answers from a cache of real `UIButton.systemLayoutSizeFitting` results. The cache is keyed by the face, the rows, the style, the offered width, the content size category, the legibility weight and the scale.
- On a miss, the presenter measures on the main thread with the real configured button before it presents that batch, then asks for a relayout. A screen that adds no new face pays nothing; one that does pays one extra layout before the frame, never a visible jump.
- macOS does the same with `NSButton.fittingSize`.
- The web lays out natively.
- Linux's painter is Exact's own and synchronous.

**D12. Refusals** (`lower-button-style-attr`, each naming the custom `button` as the alternative):
- background, border, `border-radius`, padding, shadow, `filter`, `backdrop-filter`
- `font-family` and the other typography rows
- inner layout other than `flex-direction` and `gap`
- `direction`, `pointer-events`, `press-scale`
- more than two texts or one image

## 4. Fixture and tests

`scripts/fixtures/native-buttons.contract` gains two sets of rows.

**Lexy's buttons**, the target look:
- the defrost pair (symbol and title, `tinted`/`gray`)
- a control tile (`flex-direction=column`, icon over label)
- Check for update (`text-align=start`)
- the busy header refresh (`aria-busy`)

**The report's nine:**
- Sign In: `filled`, `-exact-control-size=large`, `-exact-corner-style=capsule`, semibold
- Resend Code: `gray`, `color=AccentColor`
- the method choices: `tinted`, symbol and title, no `gap` written
- the links: `plain`, small semibold, wrapping, one symbol-only
- each also in `glass`

Each row is drawn three ways:
- the native button
- a `UIButton.Configuration` (and an `NSButton`) configured by hand in Swift for the same intent
- the web

The checks:
- A pixel diff between the native button and the hand-configured one, on iOS and macOS.
- Lexy's rows compared against its current `-exact-apple-button-style` screenshots.
- A filmed `screenshot … over 300 every 16` from launch asserts that no frame moves after the first.
- XCTests:
  - absent rows write nothing except D1's two runtime answers
  - each mapping
  - `aria-busy`
  - the cache's traits
  - a Dynamic Type change remeasures
- Contract: each admitted row and each refusal.

## 5. Build order and migration

1. Contract and kernel: the allowlist, the two `-exact-` rows, the face's subtitle and placement, and the measure hook with a host that answers "unknown" (no behaviour change).
2. iOS: the mappings and D11's cache, against the fixture's hand-configured column.
3. Web and Linux.
4. macOS.
5. Lexy moves from `-exact-apple-button-style` to `appearance="auto"` with these rows. Then the vendor row, its style bit 193 and its `index.html` approximation are deleted from our integration branch.

The disabled transition (`transition: -exact-enabled …`) is not part of this branch.
