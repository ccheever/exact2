# LLP 1069.011.001: Native buttons that look like the platform's own

**Type:** RFC
**Status:** Draft r1, for review. Nothing here is built.
**Author:** Claude (Opus 5.5) for James Ide
**Date:** 2026-10-06
**Systems:** Contract (`contract/lower/src/controls.rs`: the native button's allowlist), Kernel (`schema.json`: `buttonSize` and the `buttonSizes` table; `ButtonFace` gains the authored rows; a control measure hook beside `TextMeasurer`), Apple (`NativeButtonsIOS.swift`, `NativeButtonsMac.swift`, the measure hook), web (`index.html`'s `button[data-button-style]` rules), Linux (`paint/control.rs`, `presenter/control.rs`), the fixture (`scripts/fixtures/native-buttons.contract`)
**Related:** LLP 1069.011 (native buttons; this revises its D6 and D7), LLP 1069.011.000 (one face per button), LLP 1069.001 (form controls; `appearance`), LLP 1081 (names Exact invents), `issues/20261002-native-button-limitations.md` (the request this answers), `CLAUDE.md` ("the web is the standard")

## Summary

`button appearance="auto"` draws the platform's own button (LLP 1069.011). An app that moved nine real buttons onto it found five differences from the same screens built with `UIButton.Configuration` by hand. There was no space between symbol and title, no size or capsule, no title font, no wrapping, and `gray` ignored the tint. So it kept its custom buttons. This RFC closes those gaps by three rules:

1. **Nothing authored means the platform's default, exactly.** Every row below is an override. When it is absent, the host leaves the platform's own field alone, so a new OS version's defaults show up without a change here. Nothing measured on one OS version is written into a table.
2. **Where CSS has a name, it is the name.** `gap`, `font-size`, `font-weight`, `white-space`, `line-clamp`, `color` and `border-radius` mean on a native button what they mean on a browser's `<button>`. Size is the one choice CSS has no name for, so it is a table, as `buttonStyle` is.
3. **The platform draws all the chrome, glass included.** Every row admitted here sets a *content* field of the platform's button (spacing, font, wrapping, foreground, size, corner style), and each one is honoured by all twelve styles. Background, border, padding, shadow and material stay refused on every style, as LLP 1069.011 D6 says. So no style needs the author to draw any part of it.

## 1. Why, and what came before

Our fork answered the same need on 2026-10-01 with the vendor property `-exact-apple-button-style` (`7b1a37e8b`). At that point `main` had no native buttons. The app being ported needed UIKit's touch handling (highlight, drag-off, scroll cancel) and the system styles, and an Apple-only vendor row was the shortest path:

- It turned every `button` into a `UIButton`.
- It drew the configuration from the button's one text and one symbol.
- It read the author's `border-radius` for a capsule, the text child's `font-size`/`font-weight` for the font, and the laid-out boxes for the padding.

It worked for one app on one platform. On 2026-10-02 `main` shipped the general design (LLP 1069.011: `appearance="auto"` plus `buttonStyle`). The limitations report and LLP 1081 §1 both rejected the vendor row as the fix. The objection was not its name. It was that it reads box styles D6 refuses on a native button, and that it means nothing on the web, macOS or Linux. Lexy still uses it through our integration branch. §5 retires it.

**Native button or the author's boxes.** The choice is already CSS's own switch. `appearance="auto"` gives the platform's button, and `appearance="none"`, a plain `button`'s fixed default, gives the author's box. The switch can be set in a class like any row (LLP 1069.011 D1, D12). Nothing here changes it. What changes is how close `auto` gets to a hand-configured platform button.

## 2. Measured (iOS 27 simulator, 2026-10-06)

These numbers are evidence for the design, not values anything uses. Probes: `UIButton.Configuration` factories in a bare process (`/tmp/nbprobe`). The ink gap is the distance between the symbol's ink and the title's ink, rendered at 3×.

| | Result |
|---|---|
| `imagePadding` default | 0 on every factory and every `buttonSize` |
| Ink gap at `imagePadding` 0 | 3.7 pt (side bearings only, so it reads as touching) |
| SwiftUI `Button { Label(…, systemImage:) }` | 11.3 pt ink gap, the same as `imagePadding` ≈ 8 |
| Title wrapping default | `titleLineBreakMode` `.byWordWrapping`, `numberOfLines` 0: UIKit wraps. LLP 1069.011 D6's one line is our choice, not UIKit's. |
| Title font default | 15 pt at `mini`/`small`, 17 pt at `medium`/`large`, regular weight, every style |
| Natural height | 28 (`mini`, `small`), 34.33 (`medium`), 50.33 (`large`). `mini` is the same as `small` on iOS 27. A 13 pt title keeps the size's height. |
| `cornerStyle` default | `dynamic`; `capsule` on the four glass factories |
| Glass and the content fields | `glass` and `prominent-glass` honour `imagePadding`, a title font, `buttonSize` and `baseForegroundColor` as `gray` does (same sizes, same colour) |
| Threads | `UIButton.Configuration` is a value type usable off the main thread; `UIButton` and its `intrinsicContentSize` are main-actor |

The gap result is the one real tension. UIKit's configuration default is 0. The platform's own buttons (SwiftUI's `Label`, which Apple's apps use) space the two at about 8. D3 takes this up.

## 3. Design

**D1. Absent is the platform's default.** For each row below, a native button on which the row is not authored leaves the platform's field untouched: the host does not write it at all. That is the only rule, so a host never writes a measured number (a 17 pt font, an 8 pt gap) as a "default". A future OS's defaults show up without a change here. The agent's `layout` reports per row whether it was authored, and the drawn value the platform chose.

**D2. Only what is authored on the button applies.** A browser's UA sheet resets `font`, `color` and `white-space` on `<button>`, so an ancestor's typography does not reach it. Exact's native button does the same: its fixed rows reset the inherited typography (as D6 already does on the web), so these rows count only when written on the button or its class. `accent-color` is the exception. It stays inherited (LLP 1069.011 D7), as it is in CSS.

**D3. `gap` is the space between symbol and title.** `gap` or `column-gap` (a length) on a native button with both a symbol and a title. The mappings:
- iOS: `imagePadding`.
- macOS: none; AppKit has no symbol-to-title spacing on `NSButton`. Declared there as a stand-in: the agent reports it, and the draft's open question 3 asks whether to refuse it instead.
- web: the CSS itself.
- Linux: its look's spacing.

Absent, D1 says the platform's default, which on iOS is 0, the "touching" case the report complained about. Two options:
- (a) Keep D1 strictly, and the fixture shows authors `gap=8` for the SwiftUI look.
- (b) Write a gap only when the platform has an API that names its own spacing. UIKit has none, and SwiftUI's `Label` spacing is not public, so (b) collapses to (a) on iOS today.

Recommended: (a). The report's ask was "the platform's spacing, not 0", and on iOS the platform's API spacing *is* 0. A number we chose would be the hardcoding D1 forbids. Open question 1.

**D4. `font-size` and `font-weight` are the title's font.** iOS: `titleTextAttributesTransformer` setting the system font at that size and weight, scaled for Dynamic Type as Exact's text is (the same `UIFontMetrics` path). macOS: `NSButton.font`. The web: the CSS. Linux: its measurer's font. Either alone keeps the other at the platform's default: a bare `font-weight=600` asks the platform for its default title font and changes only its weight. `font-family` and the rest of the typography stay refused.

**D5. Wrapping is `white-space` and `line-clamp`.** The mappings:
- Absent: the platform's default. UIKit wraps; a browser's `<button>` wraps.
- `white-space: nowrap`: one line, truncated at its end (`numberOfLines` 1, `.byTruncatingTail`).
- `line-clamp: N`: at most N lines, the last truncated.

This lifts LLP 1069.011 D6's "the title is one line, truncated at its end, everywhere". That one line was Exact's choice, not the platform's (§2). macOS push buttons are single-line in AppKit, so wrapping there is a declared stand-in: one line, truncated, reported by the agent.

**D6. `color` is the title's and symbol's colour; `accent-color` stays the tint.** The report asked for `accent-color` to tint `gray`'s title. The platform's own model has two fields:
- `tintColor`: the platform decides what it colours. On `gray` that is nothing.
- `baseForegroundColor`: the label.

CSS has the same two: `accent-color` and `color`. So:
- `color` on a native button: iOS `baseForegroundColor`, honoured by every style, glass included (§2). macOS `contentTintColor`. The web: the CSS.
- `accent-color`: unchanged (D7 of LLP 1069.011).

A gray secondary action that reads as an action is `buttonStyle="gray" color=accent()`, or `color=AccentColor` where the system accent is wanted. An inherited root accent does not repaint every gray button: that would break D1, since UIKit's gray draws its label in the label colour. Open question 2.

**D7. `buttonSize` and the `buttonSizes` table.** CSS has no control-size vocabulary, so this is a host-policy prop like `buttonStyle`: styleable, a name in one schema table, absent meaning the platform's default.

| name | iOS | macOS | SwiftUI (reference) | web and Linux |
|---|---|---|---|---|
| `mini` | `.mini` | `.mini` | `.mini` | the `small` look |
| `small` | `.small` | `.small` | `.small` | `small` |
| `medium` | `.medium` | `.regular` | `.regular` | `medium` |
| `large` | `.large` | `.large` | `.large` | `large` |

Names are one-to-one with UIKit's enum, as `buttonStyles`' are with its factories. The web and Linux have no platform sizes, so their column names a look: three declared approximations in `index.html` and the Linux painter (padding and font), marked `~` in the table as `buttonStyles` marks stand-ins. Absent, the web keeps the browser's own button size. A full-width primary action is `buttonSize="large"` plus `width=100%` or `align-self=stretch`; the box rules of LLP 1069.011 D6 are unchanged.

**D8. Corners: `border-radius` as a capsule, or nothing.** Absent: the style's own corners (UIKit's `dynamic`, a capsule for glass). Authored, only a fully rounded end is admitted, mapped to iOS `cornerStyle = .capsule`, macOS the push bezel's capsule (the default in the macOS 26 design), and the web the CSS itself. Every other radius is refused, `lower-button-style-attr`, naming the capsule spelling.

How to spell "fully rounded" is open question 4. The report suggested `50%`, but on a box wider than it is tall CSS draws `50%` as an ellipse, not a capsule, so the web would disagree with iOS. CSS's own capsule idiom is a length at least half the height: `border-radius: 9999px`, or `calc(infinity * 1px)` (CSS Values 4). Recommended: admit only those, and refuse `50%` with a message saying why.

**D9. Which rows apply to which style.** All of D3–D8 apply to all twelve `buttonStyles`, because each is a content field that every UIKit factory honours (§2 measured glass and gray side by side). The rows each style owns, and which stay refused on every style as LLP 1069.011 D6 says, are its chrome: background, border, padding, shadow, `backdrop-filter`, `backgroundMaterial`, `glassGroup` membership rules (D9 there), `filter`. So the answer to "does glass need to do all its own styling" is no: glass owns its chrome, as every style does, and the author's rows reach only its content. One exception: `border-radius` on a glass style is accepted and is a no-op, since glass is already a capsule.

**D10. The first layout is right, and nothing is measured ahead of time.** Today a native button lays out at 64 × 34 until the host reports UIKit's size after the batch (LLP 1069.011 D3/D6), so every change in D3–D8 would show as a jump on frame two. With wrapping (D5), the size depends on the width offered, so a single reported size is no longer enough either. Instead:
- The kernel measures a native button the way it measures text: through a host hook, height-for-width. `ControlMeasurer::measure(face, rows, style, size, offer)` sits beside `TextMeasurer`, passed at boot in the same `Hooks`.
- On Apple the hook cannot touch `UIButton` (main-actor; the kernel lays out on the executor thread). So the presenter answers from a cache of real `UIButton.systemLayoutSizeFitting` results, keyed by everything the size depends on: face, rows, style, size, offered width, content size category, legibility weight and scale.
- On a miss, the kernel lays out with the hook's "unknown". The presenter measures the misses on the main thread with a real configured `UIButton`, before it presents that batch, and asks for a relayout. The batch the user sees is the second one. A screen with no new button faces pays nothing; one that adds some pays one extra layout, before the frame, never a visible jump.
- macOS does the same with `NSButton.fittingSize` under its alignment rect.
- The web lays out natively.
- Linux's painter is Exact's own, so its measurer is synchronous.

Every number comes from the running OS at the moment it is needed. Nothing is copied into a table.

**D11. `text-align` places the face.** On a browser's `<button>` the UA sheet sets `text-align: center`, and `start`/`end`/`left`/`right` move the content to that side and align a wrapped title's lines. The same holds here: absent, the platform's default (centred).
- iOS: `contentHorizontalAlignment` (`.leading`, `.trailing`, `.left`, `.right`, `.center`) for where the face sits in the box, and `titleAlignment` for a wrapped title's lines.
- macOS: `NSButton.alignment`.
- The web: the CSS. The native button's UA rule lays the face out as a flex row, which `text-align` alone does not move, so the rule maps `text-align` onto `justify-content` (`start` → `flex-start`, …).
- Linux: its look's placement.

Lexy's leading-aligned "Check for update" is `text-align=start` on a full-width button.

**D12. Refusals.** Still refused on every native button, `lower-button-style-attr`, each naming the alternative (a custom `button` with `appearance` absent):
- background, border, padding, shadow, `filter`, `backdrop-filter`
- `font-family` and the other typography rows
- `direction`, `pointer-events`, `press-scale`
- any `border-radius` that is not a capsule (D8)

## 4. Fixture and tests

`scripts/fixtures/native-buttons.contract` gains the report's nine buttons as rows:
- Sign In: `filled`, `large`, capsule, semibold.
- Resend Code: `gray`, `color=AccentColor`.
- The two method choices: `tinted`, symbol and title, `gap=8`.
- The links: `plain`, small semibold, wrapping, one symbol-only.
- Each in `glass` too.

Each row is drawn three ways:
- the native button
- a `UIButton.Configuration` (and an `NSButton`) configured by hand in Swift with the same intent, inside the fixture's host module
- the web render

The comparison is a pixel diff per row between the first two on iOS and macOS (tolerance for anti-aliasing), plus the web screenshot beside them for review. A filmed `screenshot … over 300 every 16` from launch asserts no row's frame changes after the first presented frame. XCTests: absent rows write nothing (each configuration field equal to a bare factory's); each row's mapping; the cache key's traits; a Dynamic Type change remeasures. Contract: each admitted row, each refusal, `50%` refused with its message.

## 5. Build order and migration

1. Contract and kernel: the allowlist (D3–D8), `buttonSize`, the measure hook with a host that answers "unknown" (no behaviour change).
2. iOS: the mappings and the D10 cache, against the fixture's hand-configured column.
3. Web and Linux.
4. macOS.
5. Lexy moves from `-exact-apple-button-style` to `appearance="auto"` with these rows (defrost, Check for update, the header refresh). Then the vendor property, its style bit 193 and its `index.html` approximation are deleted from our integration branch.

The disabled transition (`transition: -exact-enabled …`) is not part of this branch.

## 6. Open questions for review

1. **Default gap.** D3 (a): the platform's API default (0 on iOS), and authors write `gap`. Or pick a number, which breaks D1?
2. **`color` vs `accent-color` on gray.** D6 makes `color` the foreground and leaves the inherited accent as UIKit's tint, so system defaults hold. The report asked for `accent-color` to do it.
3. **What macOS cannot do** (gap, wrapping): a declared stand-in reported by the agent, or a Contract refusal when the app targets macOS?
4. **The capsule spelling.** Admit `9999px`/`calc(infinity * 1px)` and refuse `50%` (it is an ellipse on the web), or admit `50%` as the report suggested and declare the web's deviation?
