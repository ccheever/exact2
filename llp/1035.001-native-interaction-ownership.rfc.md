## Summary

The app says which route is selected, which sheet is requested, where a
draft lives, and whether dismissal is permitted. It never calculates a
keyboard height, transfers a UIKit controller parent, or guesses whether an
interrupted swipe committed navigation. UIKit owns the motion, the
recognition and the arbitration; Exact declares intent and receives
outcomes; the driver reports what it saw.

This RFC collects the ownership rules, the cases that verify them, and the
remaining implementation work. Slice 1 and subsequent Messages repairs are in
the working tree; their evidence appears beside the relevant decisions. Native
title projection and its CSS geometry mapping remain under D9; the initial
controller handoff is now implemented. The
motivation below records the original code survey; the decisions distinguish
that baseline from the current implementation.

## 1. Motivation — what Messages exercised, and what the code does

**Navigation** (`NavigationIOS.swift`). The first root's `navigationBack`
turns its children carrying `navigationKey` into routes (`:54-68`); the
root's key selects one and the preceding routes are the stack (`:69-75`);
one `RouteController` per route node, the bar hidden, contained by the
nearest owning controller found through the responder chain (`:77-96`).
Push/pop rewrite the stack with `setViewControllers`, animated only outside
agent mode and outside a modal (`:111-114`). The interactive pop begins only
with depth > 1, no transition in flight, no modal, a resolvable Back
control, no context preview anywhere in the session, and — for a pan
starting past 20 window points — no `swiperight` node under the start
point and a horizontal velocity (`:149-168`). While a transition is in
flight `sync` remounts nodes but does not rewrite UIKit's stack (`:100-102`).
Completion presses the Back control **once** because `didShow` compares
the shown route's key to the root's current key (`:174-181`): a cancelled
swipe shows the same key and dispatches nothing; a programmatic Back has
already changed the key and dispatches nothing more. The Back control is
re-resolved by `id` with a `press` handler and not `disabled` on every
use (`:142-147`), which is why the forwarding sheet disabling Back stops
both recognizers before they start.

**Sheets** (`ModalIOS.swift`). `navigationPresentation="modal"` on the
selected route presents a page sheet at one large detent (`:12-15`) from
the navigation controller's owner, refused if that owner already presents
(`:124-126`). The session viewport moves into the sheet (`:141`); the
source route's controller is re-parented under the presenting controller
with its **live** view left in the `ExactView` at its saved frame, inert to
input and accessibility (`:130-136`), its frame/content ops deferred per
node and replayed on close, frames before contents in id order
(`:83-90`, `:100-111`). `closedby="none"` is `isModalInPresentation`,
re-evaluated each batch (`:120-123`, `:139`); the app expresses "an empty
draft may be dismissed, a populated one springs back" as
`closedby=(newDraft == "" ? "closerequest" : "none")`
(`apps/messages/app.contract:680`). A user dismissal presses Back through
the same resolver (`:195-207`); a kernel-driven close finishes and
dismisses (`:114-119`); a route destroyed under the sheet freezes its
pixels (`:35-40`); a reload finishes without refitting until the new
runtime's first batch is mounted (`:209-214`).

**Keyboard** (`ExactViewIOS.swift`, `PresenterIOS.swift`). A zero-size
probe pinned to the keyboard layout guide forces a layout on every guide
move, because frame notifications omit interactive frames (`:30-40`); the
sheet has its own probe (`ModalIOS.swift:20-29`). `fit()` reads bounds,
safe area and the guide from the modal's view when one is up, else the
`ExactView` (`:77`); during an interactive drag or a modal it uses the
guide's local edge, else the presenter's window-converted keyboard top
(`:82-97`). A keyboard change arriving while a batch is applying waits for
the batch to end (`PresenterIOS.swift:113-120`, `:291-298`); zero-duration
bursts wait 80 ms; animated changes apply inside the keyboard's own
animation; agent mode applies at once (`:84-99`, `:133-138`). The viewport
freeze (`preservesKeyboardViewport`) applies only to an initially
interactive navigation transition outside a modal
(`NavigationIOS.swift:138-140`, `ExactViewIOS.swift:71-76`).

**Focus** (`PresenterIOS.swift:216-230`, `ModalIOS.swift:157-172`). The
`focus("id")` command is delivered after the batch; the target must be in
a window, enabled, non-zero and under no hidden or `inert` ancestor; every
refusal is a silent `return`. The only queue is the modal's single
`pendingFocus`, kept only while `presenting` is true and overwritten by a
later command; elsewhere an early focus is dropped. There is no focus
restoration path after a sheet or a pop: the app re-issues `focus`.
`retainFocus` suppresses the blur a tap would cause and nothing else
(`PresenterIOS.swift:398-408`). Editor traits: `spellcheck` inherits in the
kernel (`host.rs:934-939`); `autocapitalize` and `autocorrect` are read
from the node's own props (`TextAreaIOS.swift:32-56`), which is HTML's rule
(those two consult the element, then its form owner, never an ancestor).

**Two sessions** (`ExactHostIOS/main.swift`). Each pane has its own
`UINavigationController` so a native push covers one pane (`:73-93`), and
each session has its own presenter, keyboard probe and `editing`. But both
presenters observe the same global keyboard notifications guarded only by
"my viewport has a window" (`PresenterIOS.swift:69`), and a blur is
`window.endEditing(true)` — window-wide (`NodeViewIOS.swift:70,1054`,
`AgentIOS.swift:204`). Closing a sheet in session a can therefore end
session b's editing. No fixture checks it.

**What the record left open**, each with its owner in §3: a back swipe over the
horizontal timestamp scroller goes to the scroller — D1; the 62-point
large-title travel versus 36.67 — D9; an initially selected modal route at
launch is unverified — D8; the outside-dismiss miss at (390, 170) in
normal mode — 1035.003's instrument first.
The earlier 160-point reading-position jump on contact-details Back was
subsequently reproduced through native inspection and repaired by Codex;
D7 records the owner and verification without marking this RFC implemented.

## 2. Ownership

| Owner | Owns | Does not infer |
|---|---|---|
| Application state | route selection, draft contents, send/cancel intent, whether dismissal is allowed (`closedby`) | controller geometry, transition progress, keyboard height |
| Kernel/runner | logical identity, committed state, authored layout, event dispatch, the `focus` command's target | UIKit containment, OS transition timing, first-responder state |
| Native host | controller containment, editor mounting, keyboard guides, transition callbacks, the pending-focus queue, refusals with reasons | whether closing should discard a draft, which route "should" be selected |
| Driver (1035.003) | the input sequence and the observations of its outcome | that an activation proved a gesture |

CSS and HTML concepts keep their meaning (`inert`, `disabled`, `id`, focus
and blur as events); native presentation adds declared host behaviour
around them and never a second state model.

### D1 — The route vocabulary is the one that landed; consolidation means writing its rules down, not adding flags

The five props and their rules, as the contract (today they are scattered
across LLP 1001 §1 and 1008 §9):

- `navigationKey` on the first root selects; on a direct child names a
  route. Routes are the children with a key, in tree order; the stack is
  the prefix through the selected one. A root whose key matches no child
  leaves the stack alone (a refusal to journal, D6).
- `navigationBack` names the HTML `id` of a `press` control in the active
  route. It must exist, be enabled and be in the active route for any
  interactive pop or sheet dismissal to *begin*; completion presses it
  once. An app that wants to block dismissal disables that control (the
  forwarding sheet) or sets `closedby="none"`.
- `navigationPresentation="modal"` on the *selected* route presents it as
  a sheet over the preceding route, which stays mounted, live and inert.
  Any other value, or the prop on an unselected route, is ignored (D6
  journals it).
- `closedby` on a modal route: `closerequest` (default) permits the
  platform's dismissal gesture and Escape; `none` refuses both; explicit
  Close (the app's own control) works in either. The web maps Escape the
  same way (LLP 1007 §4).
- `retainFocus` on a node keeps the current editing session through a tap
  on it or its descendants. It never focuses.

LLP 1038 D6 (landed 2026-09-14) makes iOS controller replacement a swap
unless one whole controller list is a prefix of the other. macOS and Linux
project each `navigationBack` container's direct keyed routes as the web does:
only the selected route is visible and interactive, with its immediate modal
underlay visible but inert; every other route is hidden and inert. An unmatched
key preserves the projection and journals once per key.

Arbitration is the platform's: a back swipe beginning over a `swiperight`
node yields to it; one beginning over a horizontal scroll container's
content is that scroll view's (UIKit's own rule, which native Messages
also exhibits over its timestamp strip). The 20-point edge stays
navigation's. No flag is added per Messages symptom; a new prop needs a
second consumer and a CSS/HTML name where one exists.

**Back belongs to the selected route (Codex, 2026-09-10):** the native lookup
previously searched every live node, including retained inactive routes. A
physical fixture naming an inactive route's control lets UIKit pop while the
logical route stays selected; its sheet dismissal subsequently crashes with a
controller-parent inconsistency. The lookup now requires containment in the
selected route. Sheets also require that enabled control before dismissal,
both when applying intent and in UIKit's permission callback; a refused attempt
is journaled. Browser Escape resolves the control within the selected route.
Five physical permission cases and seven Messages Back/sheet cases pass:
foreign controls cannot authorize a pop, foreign/disabled controls make a sheet
resist while retaining its editor, and valid controls dispatch once. D2's
subsequent completion repair covers a valid Back handler keeping its route selected.
Fixture failures, baseline crash and rebuilt evidence:
`/tmp/messages-back-owner/verification.json`.

### D2 — An interactive dismissal has three outcomes, and completion dispatches exactly once

Outcomes: **in progress** (UIKit owns the motion; the kernel's stack is not
rewritten; `state.navigation.transition.phase = "in-progress"` in
1035.002), **cancelled** (route, draft, editor selection and intended focus
are untouched; nothing dispatches; the viewport refits), **completed** (the
Back control is pressed once, provided the route and session still exist).

**Completion repair (Codex, 2026-09-10):** comparing only the shown and current
keys incorrectly dispatched a new route's Cancel when a programmatic Back
finished after Compose was selected. The navigation delegate now captures the
source node and key only for an initially interactive transition. Completion
dispatches only if that node still exists, its key remains selected, and UIKit
shows a different key. The enabled Back control is still resolved by `id` at
use; replacing the source route cannot transfer a completion to its successor.
Callbacks from a retired navigation controller or a shown controller that is no
longer its top are ignored. The interactive source is consumed once; reset clears
it. Intent deferred during a transition is projected at completion. A production
UIKit fixture reproduces the old programmatic dispatch and stale-owner mutation;
the fresh Messages drive passes rapid Back → Compose twice with keyboard/focus,
saved drafts, and physical Back cancellation/completion
(`/tmp/messages-navigation-completion/`).

**Completed sheet ownership (Codex, 2026-09-10):** a valid Back handler that
keeps its route selected also reproduces the controller-parent crash. Deferring
the interactive-dismiss callback's work alone still crashes: the surviving
modal-navigation slot skips preparation of the primary stack as a background
when the sheet is presented again. The second candidate restores the viewport
and releases that slot after UIKit's callback returns, before dispatching the
original route's Back. The source must still be the same live, selected node;
a successor cannot inherit its completion. Reset recognizes an already completed
native dismissal, and cleanup preserves a newer pending focus command.

The retained route, ordinary close, replacement sheet, permission revocation
during measured movement, replacement requested during movement, and the new
sheet's own dismissal pass six physical cases. Replacement focus arrives, Back
counts advance once, and the resulting editors remain usable. Revocation after
UIKit has committed dismissal leaves the route selected and re-presents it with
the keyboard closed; this is not cancellation with continuous editing. Browser
Escape verifies retained/replaced route intent and independent close counts.
An actual two-session sheet drag requests reload after measured movement;
the host accepts it in both sessions, the replacement Compose stays open, and
both sessions remain editable after the old completion. Seven Messages gesture
cases and 22 contact captures also pass on the rebuilt host.
`/tmp/messages-dismissal-owner/verification.json` preserves both failed native
variants and the second candidate's rebuilt evidence.

**Unmounted native ownership (Codex, 2026-09-10):** removing ExactView during
a measured sheet drag previously let the old completion close retained Compose.
Unmount now retires the session's sheet and navigation controllers without Back,
restores surviving route nodes to their logical parent, and prevents offscreen
batches from creating native presentations. Remount projects the current tree.
The physical unmount/remount and destruction cases preserve the surviving
session; Compose and its recipient survive unmount and remain editable on return.

An offscreen timer also replaces the selected route and requests focus on its
new editor. The first two candidates restored that route but lost its focus:
fresh-owner reset cleared the command, and child window callbacks could consume
it before controller installation. The third candidate preserves the queued
command and defers its delivery from `willMove(toWindow:)` through owner
installation. The replacement sheet opens focused and closes exactly once.
Evidence: `/tmp/messages-unmounted-owner/` verifies remount in the same pane.

**Different native parent (Codex, 2026-09-11):** the current host also passes
moving a live ExactView to another UIKit controller in the same window and back.
The old parent releases its navigation child; the new parent acquires it.
Messages retains Compose and its recipient, and the other session stays usable.
A transfer after 77.67 points of measured physical sheet movement also preserves
Compose through the old gesture completion. Separately, an offscreen route
replacement queues focus and delivers it to the replacement editor after mounting
under the new parent; Close dispatches once. Unmount ends the existing first
responder, so these checks establish explicit queued focus, not continuous editing
through removal. The temporary adapter links unchanged production ExactKit;

### D3 — A pending focus is a queued command with an identity, a reason, and a refusal

Today: one presenter-owned slot during navigation, sheet presentation or native window mounting, bound
to the actual target node and exposed with its wait reason; replacing an existing
owner clears it, while mounting a fresh owner preserves commands issued offscreen.
Delivery waits for both controller installation and sheet presentation to
finish. A new modal navigation controller can call `didShow` before entering the
sheet; consuming focus there loses the editor during its subsequent move. The
production Back → Compose drive reproduced that loss and passes with the wait
(`/tmp/messages-modal-owners/production-results.json`). The completion repair above proves the Messages recipient handoff. The wider
rule remains proposed: a `focus(id)` command not deliverable *now* — not
mounted, zero-size, inside a presentation still animating — is queued
with its target `id`, the batch epoch that issued it, and the reason. It
is delivered once, at the end of the batch or presentation that makes it
deliverable. A later `focus` replaces it. If the target is destroyed or
its route leaves the stack first, it is refused with a journal line
(`focus #to refused: destroyed before mount`), never delivered to a
successor with the same `id`. Refusals that are final today — hidden
ancestor, `inert` ancestor, disabled, no window — become journal lines
too. 1035.002's `state.focus.pending` shows `{target, reason, since}`.

**Authored inertness (Codex, 2026-09-11):** the former compiler rejection is
repaired: `inert` lowers to existing boolean prop 20, and the browser receives
the real attribute instead of `data-inert`. A validated native plan supplying
that prop below the compiler reproduced continued editing and child activation
while inert, despite the later explicit-focus refusal. iOS now ends editing in
that subtree, excludes it from input/accessibility and checks ancestors before
activation or renewed editing. Ten-step iOS/browser input drives preserve the
draft, identities and all twenty compared region/control frame observations per
host; clearing inertness restores input. The iOS accessibility tree removes and
restores the measured descendants. Browser route projection preserves authored
inertness when deciding which route is active.

A native modal confirmation now escapes inert ancestors and remains valid when
its invoker becomes inert after opening; both cases pass on iOS and the browser.
The third/final candidate also gives browser focus, gestures, shortcuts and
inspection one ancestor lookup that stops at an open modal dialog. The rebuilt
browser passes explicit focus into that dialog, reports its control as interactive,
and confirms once. Ten-step basic and active-route input drives pass on the final
candidate, with forty unchanged identity/frame observations. Four rebuilt Messages
selection/deletion/forwarding cases pass per host (native candidate two, browser
candidate three). Initial browser startup failures remain in the evidence; the
successful diagnostic spent 124 seconds in build validation, with the filesystem
helper sampled at macOS's loader entry point, then served every runtime request
successfully.
AppKit/Linux subtree enforcement, full VoiceOver/IME and active-drag coverage,
and comprehensive reporting of the browser’s implicit modal inertness remain

spacing/material loops. Evidence: `/tmp/messages-inert-ownership/verification.json`.

### D4 — Preserve the presenting native owner throughout a sheet's lifetime

The presenting navigation controller retains its parent, stack, bar and content
scroll relationship. A separate navigation controller owns the modal route and
moves into the sheet with the session viewport. The presenting controller's whole
view stays in the owning `ExactView`; closing restores its view to its original
container and retires only the modal navigation controller. Retaining source
content alone is insufficient: transferring its navigation owner removes the bar
and changes the source scroll insets.

When declared selection leaves the sheet for a different primary destination,
install that destination underneath the sheet before dismissing it. Dismissal
must not reveal the former route and then start another push to catch up with
already-committed application state.

The source remains live (dynamic colours, materials, text), inert to input and
hidden from accessibility. Geometry and scroll writes wait until its viewport
returns, then replay in the existing frame-before-content order. These rules are
implemented in the working tree (Codex, 2026-09-10).

Verification: the native-title prototype retains the same presenting controller,
route controller and bar through Compose, both expanded at inset 168/offset -168
and compact at inset 116/offset -36. The production Messages drive passes rapid
Back → Compose twice, recipient/composer focus, local Send and retained drafts.
The production two-session host passes sheet open/close in a while b retains its
search, then destruction of a with a filled sheet open while b remains mounted
and editable (`/tmp/messages-modal-owners/`). A valid-plan reload with the filled
sheet open preserves its draft and modal state, accepts subsequent editor input,
and keeps b's search; destroying a afterward still leaves b editable. The wheel-return-to-top probe stayed compact; D9's later real-touch check
returns the title to expanded. Neither establishes complete native title behavior.

### D6 — Refusals are journal lines, not silence

Every host-side refusal of a declared intent — a focus that cannot be
delivered, a route key that matches no child, a modal presentation refused
because the owner already presents, a Back gesture refused because the
control is missing or disabled — is one line in the runner's journal
(`Runner::log`, LLP 1012 §3: "hosts may append; none does today"). The
line names the node, the intent and the reason. This is how the driver and
a reader learn that an intent was refused without reproducing it in LLDB.

### D7 — Draft lifetime is application state; the host guarantees selection and composition on a retained view and nothing on a destroyed one

A draft lives in a slot (Messages: per-conversation drafts, saved on leave).
A retained editor — a route behind a sheet, a route below a pushed one —
keeps its text, selection and an in-progress IME composition, because
UIKit keeps the view. A destroyed editor keeps nothing the app did not
save; the host does not promise to restore a composition across
destruction. Focus restoration after a sheet or a pop is the app's
`focus` command (as today) with one host rule added: **revealing a
focused editor moves only the scroll containers that contain it, each the
minimum, and never a sibling scroll container** — so restoring the
composer's focus cannot scroll the transcript.

**Subsequent repair (Codex, 2026-09-09):** `layout <node>` showed the same
transcript surviving while its viewport grew from 313 to 636 points and its

### D10 — Router breadth is a semantic contract; the first implementation stays narrow

LLP 1039 limits tablist projection on both Apple hosts to absent or `horizontal` `aria-orientation`. A `vertical` tablist remains the authored column and buttons, with the same committed selection and synchronous `press` ownership.

Exact2 Router does not begin as a package that owns fetching, authentication,
caches, SSR, or application drafts. Its durable core is the small algebra already
present here: stable route keys, an ordered stack, a selected tab, modal
presentation, and completed/cancelled native outcomes. Application state in the
Rust runner owns those values. Hosts project them and never become a second
router state machine.

The projection shapes (Charlie, 2026-09-27; LLP 1059):

| Every tab's content | iOS | macOS |
| --- | --- | --- |
| One image or text alone | `UISegmentedControl`; native height returned to layout | `NSSegmentedControl` |
| Exactly one symbol image plus one text label | `UITabBar`; measured height returned to layout | Authored views |
| Any other shape (including a badge) | Authored views with the tab-bar trait | Authored views |

The first Interview slice is intentionally bounded:

- ordinary `role="tablist"` with direct, pressable `role="tab"` children and
  one `aria-selected=true` child is the tab declaration; Apple hosts project
  that semantic pattern according to the table above;
- an iOS tab with one direct image child projects that image at its authored
  size, preserving its accessible name without a visible title. The host caches
  the raster and avoids resetting unchanged geometry/selection while UIKit
  owns tracking. Hidden or inert ancestors refuse activation. Interview's
  five-tab simulator sweep and system screenshots verify selection, route
  changes, and scroll hide/reveal (2026-09-12); a hierarchy capture can omit
  the selected icon's glass rendering. A real held simulator contact mapped
  through its AX device-screen bounds tracks the enlarged lens from Home to
  Messages and commits Messages on release; system screenshots capture both
  states. The hover-based driver calibration was unavailable on this simulator;
- the projection replaces only presentation, according to the whole tablist's
  shape (LLP 1059). A horizontal tablist with at least two direct pressable tabs
  uses this table; a vertical list stays authored. The host journals its choice
  and reason (`tablist #N: …`), once per change;
- the native control dispatches the selected authored tab's `press` action
  synchronously. Its visual selection is refreshed from committed Contract
  state, so UIKit/AppKit never invents selection;
- iOS receives its current Liquid Glass appearance from the projected system
  control. The browser keeps the authored HTML/ARIA/CSS and macOS uses the
  system control appropriate to that platform;
- the existing `navigationKey` prefix remains the stack declaration. UIKit's
  navigation controller continues to own edge-pop recognition, progress and
  cancellation, with only a completed pop invoking `navigationBack`;
- per-tab retained stacks and browser URL/history restoration are part of the
  router model, decided by LLP 1038 D3–D7; its slice 1 supplies the explicit
  state and host projection, with browser history mirroring remaining slice 2.

This is the Exact1 lesson applied narrowly: content identity is separate from
presentation, tab switching is not a push, and stable route identity matters;
the router does not absorb every lifecycle adjacent to navigation. In particular,
this decision does not reopen `rules/DEFERRED.md`'s exclusion of an
engine-owned gesture arena or interactive-navigation model.

The Profile account-switcher consumer adds two native projections (Charlie,
2026-09-12). A tab's `contextmenu` handler receives a UIKit long press on its
segment; recognition cancels the pending tap, preserves authored selection, and
leaves moving-finger tab tracking with UIKit. A modal route may request
`navigationDetent` as a positive point height (serialized as a string), excluding
the bottom safe area. UIKit supplies a single custom detent clamped to its
maximum available height; changed values animate to fit changed content.
The app supplies its own handle, and upward dragging does not expand to a
second height. Missing or invalid values retain the default large sheet.
For `closedby="any"`, a tap outside the presented sheet invokes the same enabled
Back control as dismissal; it does not deliver a press into the background.
Interview's held-contact simulator drive verifies long press without navigation,
background dismissal, pull-down dismissal, and account selection.
