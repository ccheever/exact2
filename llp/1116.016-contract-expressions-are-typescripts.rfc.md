## 0. Summary

LLP 1116.015 D2 made the roster's web functions methods (`s.trim()`, `xs.filter(f)`, `xs.length`). Measured, it
changed nothing for tokens or quality, and it changed what builders reach for: with free functions a builder
knew the roster was its own small library; with methods Contract looks like JavaScript, and builders write
JavaScript's other methods. On the guess corpus `.sort(…)` went from 1 screen of 80 to 8 (5 GPT, 3 Muse).

Charlie's direction (2026-10-15) is to finish that rather than undo it. The end state: **an expression
Contract accepts means what the same TypeScript means, apart from a short, declared list of deviations that
Exact's guarantees need; what it does not accept is refused with the TypeScript that works; and the guide
teaches only the deviations and Exact's own library.** r1 stated the rule without the list, and the reviews
found that today's Contract already breaks it in five places and that two of r1's own additions would have
broken it again. r2 writes the list down, fixes the one break that is a bug, and keeps only the additions
that meet the rule:

| | What changes | Kind |
|---|---|---|
| D1 | The rule, its declared deviations (§D1's table), and the roster's admission standard | standard |
| D2 | A method call always means the built-in: a file that declares a `fn`, shape or action of a method's name and calls that method is refused | bug fix |
| D3 | `xs.some(f)` and `xs.every(f)` | sugar onto `filter` |
| D4 | `xs.toSorted(cmp)`, with one stable algorithm on every executor | roster row with a callback |
| D5 | TypeScript forms refused with an edit that means the same thing | messages |
| D6 | start-here and the card teach the deviations, not the methods | docs |

Stage 2, options as TypeScript spells absence (`T | undefined`, `??`, `?.`, narrowing), is the next RFC (§6);
`find` and `xs[i]` wait for it, because their result is an option either way.

**What it buys.** Expressions and functions are about 3% of a GPT build's direct token exposure and 2% of
Muse's (LLP 1116.015 §3); that is an estimate of what the topic's docs cost, not a causal ceiling, and the stage
is not judged on total tokens. The case is the language's: a builder writing TypeScript gets a program that
means what they wrote or a refusal naming what does, and the guide stops describing a dialect.

## 1. The evidence

**Real builds** (469 Exact2 builds, rounds 1–15 and the A/Bs; every refusal id in each build's log, its name counted
once per build). `.length` 24 (now accepted), `empty` 9, `sum` 2, `flatMap` 2, spread → `concat` 2, `reduce` 1,
`clamp` 1, `flatten` 1; no `sort`, `find`, `some` or `Math`. All of these builds wrote the free-function spelling
as taught.

**The guess corpus after D2** (one screen from start-here alone, 40 features, GPT and Muse; `~/bakeoff/guesses/post15`).
Missing methods: `sort` 8 screens (seven `(a, b) => a.field - b.field`, one string `.sort()`), `some` 1; `xs[i]` in
the trivia screens of every arm. Before D2 (`pre15`): `sort` 1.

**Unguided sketches** (`priors1`, `priors2`: 112 contracts from a 1 KB guide). Methods outside the roster: `find`
16, `sort` 2, `reduce`, `every`, `some`, `toUpperCase`, `Math.max` 1 each; `null` or `undefined` in 29 of 80
features, `??` or `?.` in 10.

So `toSorted` has the strongest evidence in Contract (and is what method syntax invites next); `some` and
`every` are cheap and complete the predicates; `find` is real but belongs with stage 2.

## 2. The tests every change must pass

LLP 1116.015 §4's T1 to T6 hold. Two bind hardest.

- **T4: no spelling that compiles with another meaning.** An accepted form means what TypeScript means for the
  values Contract has, or its difference is in D1's table. Where an edit is offered, the edit itself must mean
  what the refused form meant, or say what differs.
- **T2: sugar is a rewrite into the program the semantics already has**, with expected-behaviour tests of its
  own, since difftest cannot see a wrong rewrite: the program in each spelling, the expected value against
  JavaScript for edge inputs, and a diagnostic that names the form the author wrote.

## D1. The rule, its deviations, and admission

**The rule.** An expression Contract accepts evaluates as the same TypeScript expression does, for every value
Contract can hold, except as declared below. Every refused TypeScript form is refused with an edit that means
the same thing, or with a message that says what Contract lacks.

**The declared deviations.** Each is kept because a guarantee needs it (T1) or a representation cannot hold
TypeScript's value; each is one line in start-here (D6).

| Deviation | Why |
|---|---|
| No truthiness: a condition is a `bool` | T1; `if (name)` is refused with the comparison |
| Nothing is an option (`none`, `some(x)`, `match`), not `undefined` or `null` | T1, until stage 2 respells it |
| Values do not change: no `push`, `sort`, assignment into a list or record; `concat`, `toSorted`, a record copy | T1; one transaction per action |
| Lists and records compare by value (`[1] == [1]`) | values have no identity in Contract |
| A string is well-formed: a lone surrogate becomes U+FFFD (`slice`, and any string builder) | LLP 1088 D2; the runner holds scalar values |
| `min`/`max` drop a `NaN` operand | today's roster (LLP 1102); changed with the `Math` renames (§5) |
| Names may hold hyphens, so subtraction takes spaces (`a - b`) | CSS's names (`font-size`) |
| List work is bounded (`MAX_LIST_STEPS`), and a bound is a refusal where TypeScript would run on; `some`, `every` and `filter` pass the whole list | LLP 1017.003 D3; determinism of the budget |
| Where ECMA-262 leaves a result to the implementation (a sort's comparisons, an inconsistent comparator), Contract fixes one and says so | the runner, the web runtime and Lean must agree |

**Admission.** An operation joins the roster when TypeScript has it as a pure, total operation on strings,
numbers or lists (or total through an option); its TypeScript meaning can be Contract's, or its difference fits
the table; and Contract sources show builders writing it: real builds, or guess-corpus walls in both model
families. Data-module code does not count: it already runs as TypeScript. It keeps TypeScript's name, argument
order and method form, and its implementation cost is weighed with its evidence (a callback is a proof; a string
function is a row). Mutation, `this`, classes, exceptions, `Date` and `Math.random` stay out by T1.

## D2. A method call means the built-in

LLP 1116.015 D2's parser rewrites `x.trim()` to the call `trim(x)`, so an app that declares `fn trim` captures it,
which TypeScript never does (`String.prototype.trim` is not replaced by a function named `trim`). A file that
declares a `fn`, shape or action named like a method (`METHODS` in `contract_syntax::idioms`) and calls that
method is refused: "`.trim()` is the built-in; rename your `fn trim`". A file that declares `fn trim` and calls it
`trim(x)` keeps working. Test: the probe above refused, the shadowing tests in `contract/cli/tests/it` updated.

## D3. `some` and `every`

| Written | Rewritten to |
|---|---|
| `xs.some(x => c)` | `xs.filter(x => c).length > 0` |
| `xs.every(x => c)` | `xs.filter(x => not (c)).length == 0` |

The value is TypeScript's for every list, `[]` included (`some` false, `every` true). The work is not: both pass the
whole list and build the filtered one (D1's table). A callback with an index (`(x, i) =>`) keeps it. Tests: same
plan as the expansion; values against JavaScript for `[]`, one item, all true, all false, an index predicate; a
non-`bool` body whose diagnostic says `.some(…)`; the list bound reached with a match at the front.

## D4. `toSorted`

`xs.toSorted((a, b) => n)` is ES2023's `Array.prototype.toSorted`: a new list, ordered by the comparator's number,
stable. `xs.toSorted()` on a `string[]` orders by UTF-16 code units, as TypeScript's default does; on any other
list it is refused with `(a, b) => a - b` (a number list) or a field comparison, since TypeScript's default would
compare numbers as text (`[10, 9, 1]` sorts to `[1, 10, 9]`) — a guardrail, declared.

- **One algorithm.** A bottom-up merge sort over the indices, written out the same way in the runner
  (`machine.rs`, beside `Map` and `Filter`), the web runtime (`roster.js`, metered through `budget.js`), and Lean.
  Never the engine's `Array.prototype.sort`. For a consistent comparator the result is the stable order ECMA-262
  requires; for an inconsistent one it is this algorithm's, identical everywhere (D1's table).
- **SortCompare.** A `NaN` result reads as `+0`, and `-0` as `0` (ECMA-262 SortCompare).
- **Bound.** Each item placed charges one list step, as `map` does, plus `⌈log₂ n⌉` passes: a list of n items costs
  n·⌈log₂ n⌉ steps, so 5,000 rows cost 65,000 and fit. A comparator's own list work charges as nested work does.
- **The semantics.** A new instruction beside `Map` and `Filter`, whose callback binds two parameters. The Lean
  side defines the same merge sort as a function, proves the result is a permutation of the input and, for a
  comparator that is a total preorder, sorted and stable; lowering correctness extends `LowerCorrect` with a
  `SortR` relation as `each_sem` covers `MapR`/`FilterR`. difftest's generator emits comparators, including
  inconsistent and `NaN`-returning ones, and a corpus program pins ties, `NaN`, `-0`, astral strings against
  code-unit order, and the bound.
- **The refusals.** `.sort(cmp)` leads with `.toSorted(cmp)` (the list is not changed in place); `.sort()` with the
  default above.

This is the expensive part of the stage. It lands after D2, D3 and D5, as its own commits, and is judged on its own.

## D5. TypeScript refused with an edit that means the same thing

| Written | The message leads with |
|---|---|
| `xs.sort(cmp)` | `xs.toSorted(cmp)`: a list is not changed in place |
| `xs.push(x)`, `[...xs, x]` | `xs = xs.concat([x])`; on a `Router`, `push(nav, location)` |
| `xs.reverse()` | refused; reverse in the data source (no evidence yet for `toReversed`) |
| `xs[i]`, `s[0]` | `xs.at(i)`, an option (`none` past the end; a negative index counts from the end, unlike `xs[i]`) |
| `xs.find(f)` | `xs.filter(f).at(0)`, an option; stage 2 gives `find` itself |
| `a.localeCompare(b)` | Contract has no locale order (results would differ by device); `<` compares by code unit, as TypeScript's `<` does |
| `a === b`, `a !== b` | `==`, `!=` (which compare lists and records by value) |
| `Date.now()` | `performanceNow()` for elapsed time; the clock's date is `exactTime` in the data module |
| `Number(s)`, `parseFloat(s)` | `parseNumber(s)`, an option: `Number("")` is `0` and `Number("12px")` is `NaN` |
| `String(x)` | `x.toString()` |
| `Math.floor(n)`, `Math.max(a, b)`, … | `floor(n)`, `max(a, b)`; `max` drops a `NaN` (D1) |
| `xs.reduce`, `xs.flatMap` | today's: compute it in the data source |

## D6. Teach the deviations

start-here's **Expressions** bullet becomes the rule and D1's table in a line each. The card keeps Exact's own
functions (formatting, routes, `parseNumber`, `calendarDiff`, the platform's), the signatures whose result is an
option (`at`, `first`), and its "Not in Contract" line, which names what a TypeScript writer would try; the methods
that mean what TypeScript means are named in one line. The as-built note records the net bytes and, from the
judging run, the `contract vocab` lookups.

## 5. Not in this stage, with the trigger

- **`Math.floor`, `Math.ceil`, `Math.round`, `Math.min`, `Math.max`.** The five are renamed together or not at
  all, and `min`/`max` first become JavaScript's (`NaN` in, `NaN` out; signed zeros as now; arguments evaluated
  once, in order) across the runner, `roster.js`, `Number.lean` and the `arith` difftest, after a search for apps
  that rely on the dropped `NaN`. Trigger: a guess-corpus or real-build wall on `Math.` in both models.
- **`find`, `findIndex`, `xs[i]` as `at`**: stage 2.
- **`reduce`, `flatMap`** (real builds: 1 and 2; `sum` 2): a fold is a callback with an accumulator and its own
  proof. Trigger: as often as `sort`.
- **`padStart`, `padEnd`, `toUpperCase`, `toReversed`, `trimStart`, `repeat`, `lastIndexOf`**: no Contract evidence.
  When `padStart` comes, LLP 1088's note binds (StringPad's order, the byte bound after the early returns) and a
  fill split mid-surrogate is D1's well-formed deviation.
- **`localeCompare`** with a fixed collation: the same tables on every host, matched to the byte.

## 6. Stage 2: absence as TypeScript spells it

Unguided, models write `null` or `undefined` in 29 of 80 features and `??` or `?.` in 10; guided, every build
learns `match` (46 of 80 post-D2 screens). TypeScript with `strictNullChecks` keeps Contract's guarantee that a
value whose type does not include absence is never absent, so absence could be spelled `T | undefined` with
`??`, `?.` and narrowing. The next RFC designs it, and must decide:

- `undefined` (what `find`, `at` and `?.` produce in TypeScript) as the one absent value, `null` refused with the edit, or both;
- nested options: today `some(none)` differs from `none`, and `T | undefined` cannot say so; flatten them (the
  web already erases `some`, and `contract/types/src/bounds.rs` refuses directly nested options) or keep a
  spelling for the nested case;
- `??` and `?.` lowered to `match`, so the right side of `??` runs only when the left is absent;
- narrowing by `x != undefined`, through `&&`, `||` and ternaries, ended by an assignment; `if (x)` stays refused;
- the data boundary (`contract/cli/src/typescript.rs` already emits `T | null`), generated `.d.ts`, and what
  becomes of `some`, `none` and `match` under the one-spelling rule.

Then `find` returns `T | undefined` and `xs[i]` can be weighed again.

## 7. How it is judged

- **T2 and T4 first.** D2's refusal; D3's same-plan and JavaScript-value tests; D4's difftest agreement, Lean
  proofs and cross-executor corpus, including inconsistent comparators.
- **The guess corpus**, per model, every error by diagnostic id, on the 40 features and on 40 held-out features
  (`guess.py --n 80`, screens 41 to 80), against `post15` and a held-out baseline run before the change. The
  `sort` and `some` walls fall once start-here names `toSorted`; refused TypeScript (`D5`'s rows, truthiness,
  `null`) does not rise in either model beyond the run-to-run spread, which the baseline runs twice to measure.
- **D6's net bytes** and lookups. No graded A/B: the stage's direct exposure is below its resolution
  (LLP 1116.013).
- **T6.** Charlie and James read one option-heavy and one list-heavy app before D4 lands.

## 8. Cost and migration

D2, D3 and D5 are the parser, the checker and `idioms.rs`, with their tests; nothing is renamed, so no source
migrates. D4 is the cost: an instruction in the runner and the web runtime, the Lean definition and proofs,
difftest's generator, a corpus program. D6 is docs.
