## 0. Summary

LLP 1116.015 D2 made the roster's web functions methods (`s.trim()`, `xs.filter(f)`, `xs.length`). Measured, it
changed nothing for tokens or quality, and it changed what builders reach for: with free functions a builder
knew the roster was its own small library; with methods Contract looks like JavaScript, and builders write
JavaScript's other methods. On the guess corpus `.sort(…)` went from 1 screen of 80 to 8 (5 GPT, 3 Muse).

Charlie's direction (2026-10-15) is to finish that rather than undo it, without letting Contract become a
programming language. The end state: **an expression Contract accepts means what the same TypeScript means,
apart from a short, closed list of deviations that Exact's guarantees need; what it does not accept is refused
with the TypeScript, or the data-module move, that works; Contract computes only what a view should compute,
synchronously, boundedly and identically on every executor; and the guide teaches only the deviations and
Exact's own library.**

| | What changes | Kind |
|---|---|---|
| D0 | What Contract never becomes: no effects on change, no statements in expressions, no recursion, no unbounded work; an operation's cost is visible | standard |
| D1 | The rule, its closed table of deviations, the debts on it, and the roster's admission standard | standard |
| D2 | A method call always means the built-in (built, `d4a80fa50`) | bug fix |
| D3 | An audit of every accepted form against JavaScript | test |
| D4 | Per-row list work over another list warns, if §7's probe shows the cost is real | warning |
| D5 | TypeScript forms refused with an edit that means the same thing | messages |
| D6 | start-here and the card teach the deviations, not the methods | docs |

Out of this stage (§5): `some`/`every` (they wait for one search that stops at the first match, shared with
`find`), `toSorted` (its own RFC, on a trigger; a key sort, `sortBy`, was admitted on 2026-10-17), and the
`Math.*` renames. Stage 2, absence spelled
`T | undefined`, is the next RFC, written now and built only past its own gates (§6).

**What it buys.** Expressions and functions are about 3% of a GPT build's direct token exposure and 2% of
Muse's (LLP 1116.015 §3). The stage is not judged on total tokens. The case is the language's: a builder
writing TypeScript gets a program that means what they wrote or a refusal naming what does. The program's
larger levers remain the data protocol (0.49 MB-steps a GPT build) and tooling (0.60); this stage is
time-boxed against them.

## 2. The tests every change must pass

LLP 1116.015 §4's T1 to T6 hold. Two bind hardest.

- **T4: no spelling that compiles with another meaning.** An accepted form means what TypeScript means for the
  values Contract has, or its difference is a row of D1's table. Where an edit is offered, the edit itself must
  mean what the refused form meant, or say what differs.
- **T2: sugar is a rewrite into the program the semantics already has**, with expected-behaviour tests of its
  own, since difftest cannot see a wrong rewrite.

## D0. What Contract never becomes

Contract is the view's language. TypeScript's spelling is the goal for its expressions; TypeScript's statements
and React's hooks are not. These stay out, whatever a builder writes or a census shows:

| Never | What holds instead |
|---|---|
| Code that runs because a value changed (`useEffect`, a watcher, an `onChange` of state) | An action runs on an event; a gated task arms or drops a timer and runs nothing when its gate changes (LLP 1092); a derive is recomputed when what it reads changes and has no effects |
| Statements, loops, mutation or early return in an expression | Expressions, `let`, `if` and `match` values; an action is one transaction over the snapshot it began with |
| Recursion, and functions as stored values | A `fn` is a nonrecursive expression; a callback is written at its use (`map`, `filter`) |
| Async, the clock's date or randomness in an expression | The data module (`exactTime`, a seeded shuffle); `performanceNow()` for elapsed time |
| Unbounded work | `MAX_LIST_STEPS` per evaluation (LLP 1017.003 D3); the value bounds |

**An operation's cost is visible.** An admitted operation's work is linear in its operands or its cost is stated
(a sort's n·⌈log₂ n⌉), it charges the list bound, and `agent.mjs perf` names it by plan site. A convenience
whose cost a reader cannot see from the call does not join, however familiar its name.

The refusals that guard D0 lead with the Contract form: "do Y when X changes" with the action that changes X, or
a gated task when Y is a timer.

## D1. The rule, its deviations, and admission

**The rule.** An expression Contract accepts evaluates as the same TypeScript expression does, for every value
Contract can hold, except as declared below. Every refused TypeScript form is refused with an edit that means
the same thing, or with a message that says what Contract lacks.

**The declared deviations.** The table is closed: a new row is a language change, accepted as one. Each row is
one line in start-here (D6).

| Deviation | Why |
|---|---|
| No truthiness: a condition is a `bool` | T1; `if (name)` is refused with the comparison |
| Absence is an option (`none`, `some(x)`, `match`), not `undefined` or `null` | T1, until a stage 2 respells it |
| Values do not change: no `push`, `sort`, assignment into a list or record; `concat`, a record copy | T1; one transaction per action |
| Lists and records compare by value (`[1] == [1]`) | values have no identity in Contract |
| A string is well-formed: a lone surrogate becomes U+FFFD (`slice`, and any string builder) | LLP 1088 D2; the runner holds scalar values |
| Names may hold hyphens, so subtraction takes spaces (`a - b`) | CSS's names (`font-size`) |
| List work is bounded (`MAX_LIST_STEPS`), and a bound is a refusal where TypeScript would run on | LLP 1017.003 D3; determinism of the budget |
| A formatting function prints `""` for a non-finite number (`toFixed(Infinity)`, where JavaScript prints `"Infinity"`) | LLP 1054.000.003 D7 |
| A stored number is finite: `NaN` and `±Infinity` live inside an evaluation, and a commit that would put one in a state or derive is refused, so the write that caused it does not land (`total / count` with `count` 0) | state holds what every host can carry (`semantics/corpus/numbers/refuse-derive.contract`, `refuse-nonfinite.contract`) |
| Where ECMA-262 leaves a result to the implementation, Contract fixes one and says so | the runner, the web runtime and Lean must agree |

**Debts.** A difference no guarantee needs is a debt, listed with its fix, never a row:

- Whatever D3's audit finds.

The first debt, `min`/`max` dropping a `NaN` operand, is paid (As built).

Two rows can produce a wrong app rather than a refusal, because they parse and run: structural `==` and hyphenated
names. If a measurement (§7) shows agents following either into a wrong screen, the colliding form is refused,
not explained.

**Admission.** An operation joins the roster when all of these hold:

- TypeScript has it as a pure, total operation on strings, numbers or lists (or total through an option), and its
  meaning is Contract's or its difference is already a row.
- A view needs it: it computes over values the view already holds, synchronously, boundedly, identically on
  every executor (D0). Effects, failure, device-specific behaviour, locale order, randomness and the data's
  canonical form stay in the data module.
- Contract sources show builders writing it: real builds, or guess-and-repair walls in both model families. A
  callback-taking operation needs real-build evidence; a one-shot guess alone never admits one. Data-module code
  does not count.
- Its cost is named and weighed with its evidence (a string function is a row; a callback is an instruction and a
  proof; a change to absence is a type system).

It keeps TypeScript's name, argument order and method form.

## D2. A method call means the built-in

Built (`d4a80fa50`). LLP 1116.015 D2's parser rewrites `x.trim()` to the call `trim(x)`, so an app that declared
`fn trim` captured it, which TypeScript never does. A file that declares a `fn`, shape or action named like a
method and calls that method is refused (`syntax-method-shadowed`), with the rename. A file that declares
`fn trim` and calls it `trim(x)` keeps working. None of the 461 tracked `.contract` files hits it.

## D3. The audit

An executable table of every accepted operator and roster row, each evaluated by the runner and the web runtime
and compared with Bun's JavaScript on edge values: `NaN`, `±Infinity`, `-0`, integers past 2⁵³, empty and
one-item lists, astral and lone-surrogate strings, negative and fractional indices and arguments, omitted
optional arguments, and argument evaluation order. Each case is classified as matching, restricted (Contract
refuses), a row of D1's table, or a debt. A debt is fixed or listed before D6 teaches the table. The expected
values come from JavaScript, not from Contract's own rewrite, so a wrong rewrite cannot agree with itself.

## D4. The per-row lookup

The list bound is per evaluation of one binding, so `for row in rows` with `users.filter(u => u.id == row.userId)`
in the row stays under the bound in each row while the screen does rows × users work. If §7's probe shows that
cost is user-visible at sizes an app holds, a warning flags it, with the edit: join in the data module. A
`derive` of the join is no edit: Contract has no keyed lookup, so it is the same rows × users steps in one
evaluation, past the bound at 1,000 × 1,000.

## D5. TypeScript refused with an edit that means the same thing

| Written | The message leads with |
|---|---|
| `xs.sort(cmp)`, `xs.toSorted(cmp)` | `sortBy(xs, x => key)`, a stable sort by one key (since 2026-10-17, §5); a locale, stored or unloaded order in the data source; a list is never changed in place |
| `xs.push(x)`, `[...xs, x]` | `xs = xs.concat([x])`; on a `Router`, `push(nav, location)` |
| `xs.reverse()` | reverse in the data source |
| `xs[i]`, `s[0]` | `xs.at(i)`, an option (`none` past the end; a negative index counts from the end, unlike `xs[i]`) |
| `xs.find(f)` | `first(xs.filter(f))`, an option |
| `xs.some(f)`, `xs.every(f)` | today's composition (`xs.filter(f).length > 0`) |
| `a.localeCompare(b)` | Contract has no locale order (results would differ by device); `<` compares by code unit, as TypeScript's `<` does |
| `a === b`, `a !== b` | `==`, `!=` (which compare lists and records by value) |
| `Date.now()` | `performanceNow()` for elapsed time; the clock's date is `exactTime` in the data module |
| `Number(s)`, `parseFloat(s)` | `parseNumber(s)`, an option: `Number("")` is `0` and `Number("12px")` is `NaN` |
| `String(x)` | `x.toString()` |
| `Math.floor(n)`, `Math.max(a, b)`, … | `floor(n)`, `max(a, b)` |
| `xs.reduce`, `xs.flatMap` | compute it in the data source; since `flat` (§5), `flatMap` names `xs.map(f).flat()`, or `xs.map(f)` for a callback that returns one value |
| `useEffect`, a watch, "on change" of state | the action that changes the value, or a gated task for a timer (D0) |
| `"Total: " + n` (a string and a number) | `` `Total: ${n}` `` |
| `s.at(i)` on a string | `s.slice(i, i + 1)`, `""` past the end |

Each row has a fixture whose suggested edit typechecks. Where the edit differs (structural `==`, negative `at`,
code-unit `<`, router `push`), the message says so.

## D6. Teach the deviations

start-here's **Expressions** bullet becomes the rule, D0's line, and D1's table in a line each. The card keeps
Exact's own functions (formatting, routes, `parseNumber`, `calendarDiff`, the platform's), the signatures whose
result is an option (`at`, `first`), and its "Not in Contract" line, `sort` included; the methods that mean what
TypeScript means are named in one line. Success is lookups that do not rise, not bytes that fall (LLP 1116.013:
a shorter first read moved knowledge into lookups).

## 5. Not in this stage, with the trigger

- **`toSorted`.** Its own RFC. Trigger: guess-and-repair or post-D5 real builds still spending repair steps on
  sort after D5's message points at the data source, with the repaired app worse for it; or a real app whose
  derive is a presentation order of rows it already holds, chosen by view state, which Charlie and James read as
  clearer in the view. r2's design carries over: one bottom-up stable merge sort written out in the runner, the
  web runtime and Lean; SortCompare's `NaN` as `+0`; items charged, not comparisons; permutation, sortedness and
  stability proved; no default sort except on `string[]`. It must also fit a filter followed by a sort of 5,000
  rows under the bound. **Admitted as `sortBy` (Charlie, 2026-10-17; As built), not `toSorted`:** a key sort is
  Exact's own function, since TypeScript's comparator semantics (an inconsistent comparator's result is the
  engine's) are not one written-out algorithm.
- **`some`, `every`, `find`, `findIndex`.** One search instruction that stops at the first match, so the work is
  TypeScript's; `find` returns an option, so it is weighed with stage 2. Trigger: a guess-and-repair wall in both
  models after D5.
- **`Math.floor`, `Math.ceil`, `Math.round`, `Math.min`, `Math.max`.** Renamed together or not at all; the
  `min`/`max` debt that blocked them is paid. Trigger: a wall on `Math.` in both models.
- **`reduce`, `flatMap`** (real builds: 1 and 2): a fold is a callback with an accumulator and its own proof.
  Trigger: as often as `sort`. (`flatMap` is a composition since `flat`, below: `xs.map(f).flat()`, or `xs.map(f)` for one value.)
- **`padStart`, `padEnd`, `toReversed`, `trimStart`, `repeat`, `lastIndexOf`**: no Contract evidence.
- **`localeCompare`** with a fixed collation: the same tables on every host, matched to the byte.

**Admitted by Charlie's ruling (2026-10-17)**, past §7's stop rule, from the euxy port's source:

- `toUpperCase`, beside `toLowerCase`, for a string handed elsewhere; text on screen keeps `text-transform`
  (LLP 1088 §10).
- `range(n)`, Exact's own and not a deviation from TypeScript, which has no such function: 0 to n - 1, a step an
  item before it builds; a count that is not a whole number at least 0 is refused as a literal and traps when
  computed (LLP 1017.003 §Refused).
- `xs.flat()`, TypeScript's at its default depth and no other: a list of lists' items, one level, a step an outer
  item and one an item kept; `flat(2)` is refused naming `xs.flat().flat()`, and `flatMap`'s refusal names
  `xs.map(f).flat()`, or `xs.map(f)` when the callback returns one value (LLP 1017.003 §Refused).

## 6. Stage 2: absence as TypeScript spells it

Unguided, models write `null` or `undefined` in 29 of 80 features and `??` or `?.` in 10; guided, builders learn
`match` (46 of 80 post-D2 screens, `null` in none). TypeScript with `strictNullChecks` keeps Contract's guarantee
that a value whose type does not include absence is never absent, so absence could be spelled `T | undefined`.
The next RFC is written now and decides, free to conclude that options stay:

- one absent value (`undefined`, which `find`, `at` and `?.` produce in TypeScript; the data boundary emits
  `T | null` today, `contract/cli/src/typescript.rs`), the other refused with the edit;
- nested options flattened (`contract/types/src/bounds.rs` already refuses direct nesting; the web erases `some`);
- `??` and `?.` lowered to `match`, receivers evaluated once and the right side only when the left is absent;
- narrowing by `x != undefined` through `&&`, `||` and ternaries, ended by an assignment; `if (x)` stays refused;
- indexing that returns a possibly absent value, as `noUncheckedIndexedAccess` has it, and whether `xs[i]` can
  ever mean `at(i)`, since `at` counts a negative index from the end and `xs[-1]` is `undefined`;
- what becomes of `some`, `none` and `match` under the one-spelling rule, and the migration's size.

**Its hardest part is the snapshot.** An action reads the state it began with. TypeScript's narrowing follows an
assignment; narrowing that did so here would typecheck the read-after-assign programs the guide now suppresses
(24 of 80 unguided) and mean the old value. The RFC's central example is that action, as a test.

**Its gates to build,** independent of stage 1's result: the snapshot example's diagnostic says in one line that
the read sees the old value; and Charlie and James read one option-heavy app faster in the `T | undefined`
spelling than in `match`. A guess corpus full of `??` alone is a reason to improve the `match` message.

## As built

**D3, the audit (2026-10-16).** `semantics/corpus/typescript/` holds 197 accepted TypeScript-named forms
(operators, printing, `toString`, `toFixed`, rounding, `min`/`max`, string and list methods, `at` against `?? …`)
on edge values, each expecting what the same TypeScript evaluates to under Bun. 191 match; 4 are D1 rows (`toFixed`
of a non-finite number; a lone surrogate from `slice`); 2 were the `min`/`max` debt, and match since it was paid
(below). The web runtime agrees with the runner on all 197 and Lean on the 192 it models (it has no `toLowerCase`).
22 more TypeScript forms are refused, which T4 allows: a string `+` a number, `\u` escapes, `**`, `.join()` without
a separator, `at` on a string, `includes`/`indexOf` of a list in a list, a list in a template. The audit added one
row the table lacked, the finite stored number, and two D5 messages. A table entry checked by a test that only
compares Contract with itself would have passed the surrogate cases: their expected values are written as
JavaScript gives them.

**The `min`/`max` debt (2026-10-16).** `min(a, b)` and `max(a, b)` are JavaScript's two-argument `Math.min` and
`Math.max` (ECMA-262 §21.3.2.24–25): `NaN` when either operand is `NaN`, `-0` below `+0`. The runner's
`stdlib::js_min`/`js_max`, `roster.js`'s `Math.min`/`Math.max` and `Number.lean`'s `jsMin`/`jsMax` replace Rust's
`f64::min`/`max` and the copies of it; the `arith` difftest compares the runner's with Lean's. A stored number is
finite, so a `NaN` reaching a state or derive through `min`/`max` now refuses the commit where it used to store the
other operand. Of the `min`/`max` calls in the repo's `.contract` files, three could take a `NaN`: the dashboard

**`sortBy` (Charlie, 2026-10-17).** §5's trigger met: the euxy port's Patterns screen orders patterns it already
holds by a sort its menu chooses (name, BPM, creation date), and did it as a resource round trip to its data
module, `sortPatterns(patterns, by)`. The review panel (Astra, Grok, Fable) was unanimous for a key sort as
Exact's own function rather than `toSorted`. `sortBy(xs, x => key)` and `sortBy(xs, x => key, "desc")`:

- The key is one expression, a `map` callback (the item and its index), typed `number` or `string`; the direction
  a literal `"asc"` (the default) or `"desc"`. A free function, as `sum` is: TypeScript has no `sortBy` method, so
  `xs.sortBy(…)` is refused with the call.
- Numbers by `<` with `NaN` as `+0`, so `NaN`, `-0` and `+0` tie; strings by UTF-16 code units, as `<` compares
  them (LLP 1088 D1). Stable in both directions: descending orders the keys the other way, and equal keys keep
  their input order either way, so a secondary key is an earlier `sortBy`.
- A rewrite into what the VM runs (T2): the list bound as a local, a `Map` of the key callback over it, then the
  roster call `sortBy(list, keys, descending)`, which orders without running code. Each key is evaluated once,
  on the `Map`'s list step; the call takes none. So the budget charges one step an item, not a comparison, and a
  filter of 5,000 rows followed by their sort is 10,000 of the 65,536 steps. The comparisons are the cost D0
  states: at most n·⌈log₂ n⌉ (about 450,000 for 30,000 rows), every evaluation that reads it.
- One bottom-up merge sort over the items' positions, a run's head taken from the right only when its key orders
  strictly before the left's, written out alike in the runner (`runner/src/lists.rs`, `sort_by`) and the JS
  target (`host/web-js/budget.js`, `x_sortBy`), never `Array.prototype.sort`. The order is total on (key,
  position), so the result is the one stable order. Lean defines it with core's `List.mergeSort` on (item, key)
  pairs and proves it a permutation, sorted by key, and stable (`semantics/Contract/Sort.lean`,
  `SortFacts.lean`).
- `sort` and `toSorted` stay refused, their message naming `sortBy` and what stays in the data module: a locale's
  collation, a stored or canonical order, and rows the view has not loaded.
