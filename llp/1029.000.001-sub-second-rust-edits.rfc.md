# LLP 1029.000.001: Sub-second Rust edits without hot-patching

**Type:** RFC
**Status:** Draft
**Systems:** Development loop (`host/web-js/dev.mjs`, `host/web-js/build.mjs`, `host/web-js/module.mjs`, `host/web-js/rust-data.js`), Rust producers (`scripts/rust.mjs`), Runner data seam (module identity and re-ask, LLP 1007 §6)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-10-05
**Implementer:** Claude (Opus 5.5), starting on Charlie's acceptance (proposed 2026-10-05)
**Related:** [LLP 1029.000](1029.000-rust-development-reload.rfc.md) (parent: whole-module Rust replacement with carry; its §6 sets the 0.5–1 s target and the measurement protocol); [LLP 1029.000.000](1029.000.000-hot-patching-rust-measured.research.md) (the measurements and the Subsecond comparison this RFC acts on, §1, §3, §5); [LLP 1007](1007-web-host-v1.spec.md) §6 (restart with carry; answers reused only while the data module's identity matches); [LLP 1071](1071-exact2-web-target.rfc.md) §7 (the JS target's dev loop).

## Summary

On today's main, saving a one-line edit to an app's Rust data crate takes:
- **2.3 s** on Caltrain's web loop;
- **3.2 s** on the web loop for an outside app (the heavy list);
- **1.6–2.0 s** with live replacement on macOS and the iOS simulator.

LLP 1029.000 §6 aims for **0.5–1 s**. LLP 1029.000.000 measured where the time goes:
- **Compiling the edited crate is a small share:** 0.13–0.55 s.
- **The rest is three avoidable costs:**
  - The JS target's dev loop links its module with the release profile. For the outside app that is fat LTO and `opt-level = "z"`, and the link alone takes 1.2–1.4 s.
  - A Rust-only edit reruns the whole JS build and reloads the page.
  - The native producer builds its Wasm and native variants one after the other, about 0.35–0.45 s each, whether or not a client runs both.

This RFC removes those three costs. It also records why a Subsecond-style function patcher is not the way to the target:
- the data module is already the separately linked unit that Subsecond's mechanism creates;
- a patcher would save only another 0.1–0.3 s;
- it would bring Subsecond's limits and several thousand lines of object-file code (LLP 1029.000.000 §3).

## Motivation

The JS target made Contract edits feel instant (about 0.1 s). A Rust edit is ten to thirty times slower, and that slowness is mostly overhead, not compilation, so the gap can be closed.

Dioxus's `dx serve --hotpatch` sets the expectation from other Rust UI stacks: about 130 ms on an idle M4, by its author's figure.

## Design

### D1. The JS target's dev loop builds its module in `logic-dev`

**What changes.**
- `host/web-js/module.mjs` gets a profile argument. A development build (`build.mjs --dev`, which the dev loop runs) compiles the data module with `--profile logic-dev`. That is the profile the native producers already use for the same crate: `opt-level = 1`, incremental, no LTO, `panic = "abort"`, defined by `scripts/app.mjs`'s `--config` set.
- `--production` and `deploy.mjs` keep `--release` with the web toolchain's size settings. Production bytes don't change.
- The development build keeps the web toolchain only for what it has to have. Std is built for size (`-Zbuild-std`) only in release; a `logic-dev` module links the prebuilt `wasm32` std. The output path follows the profile directory, `wasm32-unknown-unknown/logic-dev/`.
- An app that declares its own `rust.module` package gets the same treatment, and so does the generated crate `module.mjs` writes for an app that doesn't.

**What it needs to be true.**
- `rust-data.js` must accept the larger, unoptimized module, and nothing in the page may assume release-sized bytes.
- The module stays importless. A `logic-dev` build that pulls in an import (for example from std's panic machinery without build-std) is refused by name.

**Expected:** 0.6–1.5 s off every Rust edit on the web (LLP 1029.000.000 §1.2 and §5).

**Acceptance.** Over 20 edits each (LLP 1029.000 §6's protocol), Caltrain's and the outside app's web edit-to-new-text p50 and p95 fall by at least the release-link time measured today. Production `app.module.wasm` is byte-identical before and after.

### D2. A Rust-only edit swaps the module in the page

**Today.** Every `.rs` save reruns `host/web-js/build.mjs --dev`: Contract → JS, grants, Rolldown, the module. Then every open page checkpoints its slots and reloads. With the logic revision changed, carried answers are dropped, which is correct.

**What changes.**
- **In `dev.mjs`:** sort each save by what it touched. A change only to the Rust module's inputs (its closure from `scripts/rust.mjs`'s `rustClosure`) rebuilds only the module (D1's build). The server then pushes `{ logic: <revision>, module: <url> }` instead of `{ reload }`. Any other change, a Contract edit included, reloads as today.
- **In `rust-data.js`:** a `replace(bytes)` path does the following.
  1. Instantiate the new module.
  2. Run its metadata check. Grants must match the admitted build; a module whose grants changed is a reload, never a swap.
  3. Bind and activate it, with the same calls `install` makes.
  4. Only then switch the page's executor to it.
  5. Forget every answer the old module gave (LLP 1007 §6: an answer is reused only while the module's identity matches), and re-ask every live resource.
- **What survives a swap:** slots, the Store and the clock stay, because they never belonged to the module.
- **In-flight work:** a reply to a mutation or request in flight from the old module is discarded, as the runner already discards a superseded answer (LLP 1016 D5).
- **Failure:** a module that fails to instantiate, bind or activate leaves the old one running and shows the build-error overlay.

**Why the dev build allows this.** A development JS build compiles the Contract unbaked, so `app.js` carries no compiled values from the data source that could go stale. A Rust edit therefore changes nothing in the page but the module.

**What it does not do.**
- **The module's private heap is not carried.** A source that keeps state outside the Store rebuilds it in `activate`, as on native today.
- **A heap checkpoint, if one is ever needed, is a separate decision.** It would be explicit and typed, carried through the ABI next to slot carry, and refused on a shape change (LLP 1029.000.000 §3.4). No consumer needs one today.

**Expected:** this removes the reload, the checkpoint round trip, and rerunning the unchanged JS build, about 0.3–0.5 s. The wasm loop's in-place plan restart takes about 20 ms, the closest precedent.

**Acceptance:**
- **The Caltrain edit:** a station-name edit in `caltrain-data` swaps without reloading. The page's selected station and scroll offset are unchanged after the swap, and the new name shows.
- **A failure test:** a module that panics in `activate` keeps the old module and shows the overlay.
- **A grants test:** a grants edit reloads.
- **The heavy list:** its reaction counts reset, which is expected because they live in the module's heap. Record this in the pitfalls doc if it surprises anyone.
- **Timing:** p50 and p95 per D1's protocol.

### D3. Producers build the variants their clients run, in parallel

**Today.** `scripts/rust.mjs` `compileModules` builds the Wasm variant, then the native one, for every save, whatever is connected.

**What changes.**
- The resident producer keeps the set of variants its connected clients have asked for in this session. Each client's update request already names its target and executor mode (`wasm`, `native`, `tiered`). A save builds only that set.
- A web-only session builds no dylib, and a Mac-only session builds no Wasm unless its mode is `tiered`.
- With nothing connected, the producer builds Wasm, which is what the web page and the iOS simulator use. A newly connecting client's first request builds what it lacks.
- When two variants are needed, they build concurrently in separate target directories (`target/rust-wasm/`, `target/rust-<triple>/`), because Cargo serializes builds that share one. The first build in each directory is cold once.
- The bake and publication don't change: the plan is still baked once, after the variants exist.

**Expected:** 0.35–0.45 s off each native save when one variant is enough, and about the same when both are needed and run in parallel.

**Acceptance:**
- A Mac-only session's save runs one Cargo build, and a web-plus-Mac session runs two concurrently.
- The LLP 1029.000 §7 producer tests still pass.
- p50 and p95 per surface, as in D1.

### What this deliberately does not build

**A function-level patcher (Subsecond's mechanism).** LLP 1029.000.000 §3.2 weighed it against today's `logic-dev` rebuild:

| | |
|---|---|
| Saves | 0.1–0.3 s more: Cargo's start, the cdylib link |
| Costs | per-platform Mach-O, ELF and Wasm object-file code; a relocatable Wasm base that contradicts the importless module the web and Wasmi share; no iOS device; crashes on a struct-layout change |
| Cannot do | skip the re-ask (a patched function's old answers are stale anyway, LLP 1007 §6) |

Revisit only if, after D1–D3, the measured remainder is the rustc work on the changed crate itself, and a consumer needs sub-200 ms Rust edits.

## Plan

1. **D1:** profile plumbing in `module.mjs` and `build.mjs`. Verify importlessness, production bytes, and `rust-data.js` acceptance; measure.
2. **D2:** classify saves in `dev.mjs`, add `replace` in `rust-data.js` and a runtime hook to forget and re-ask answers by module identity, then the tests above. Measure.
3. **D3:** the variant set and parallel builds in `scripts/rust.mjs`; measure on macOS and the iOS simulator.
4. **Report:** p50 and p95 over 20 edits per surface, including the first edit after readiness, on an idle machine, in this LLP's §As built. Each step lands on its own after the five checks.

## Open questions

1. **D1:** should a `logic-dev` web module keep panic messages (`panic = "abort"` with the location kept) so a development panic names its line? It costs bytes only in development.
2. **D2:** should a swap also carry the old module's answers for resources whose source function the edit didn't touch? That needs the identity of a function, not just the module: Subsecond's granularity, which this RFC declines. The proposed answer is no.
3. **D3:** a second target directory per app costs one cold build and its disk (several GB for a large crate graph). Should it be opt-in, or the default?
