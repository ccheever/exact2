# LLP 1017.003: `map`, `filter` and `join` in Contract expressions

**Type:** Spec
**Status:** Accepted (Charlie, 2026-09-27); r2 folds Astra's review of r1
**Systems:** Contract (syntax, types, lowering), Plan (`format.json`: two opcodes, three roster rows), Runner (VM, dependency table)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-09-27
**Implementer:** Claude (Opus 5.5), 2026-09-27, `feat/contract-listmap`
**Amends:** LLP 1017 §5 P5 ("no lists built by iteration") and LLP 1017.000 §P5, for pure, bounded list transforms only
**Related:** LLP 1006 §3 (`fn`); LLP 1005 §4 (the VM), §5 (the roster), §8 (the dependency table); LLP 1004 D4/D6 (the roster grows by fixture); `QUEUE.md`, "Holding the crypto list's data once needs a Contract ruling" (perf/crypto-mem2); review and dispositions `llp/reviews/1017.003-map-filter-join.astra.md`

## The ruling

The question put (QUEUE, perf/crypto-mem2, option (a)): "Add the web's
map/join to Contract expressions, limited to pure map/filter/join over lists
with a size cap." Charlie, 2026-09-27: **"rec ((a)) seems fine".**

LLP 1017 P5 bounded `fn` hard: "one expression, no loops, no recursion, no
lists built by iteration; … the first `fn` that wants a loop is evidence for
the data crate". This relaxes that bound for three list operations and
nothing else. Everything else P5 refused stays refused (§Refused).

## Why

The crypto-list benchmark's 5,000 rows each draw a 48-point sparkline.
SwiftUI keeps `series: [Double]` and computes the polyline in the view; Expo
keeps `number[]` and maps it in a `useMemo`. exact2's port cannot: a view has
no way to turn a list into a string. So its data source keeps a parsed
`Vec<f64>` per coin for the ticks to edit, and every row also carries a
formatted `points` string: 5,000 of them in the baked first answer, and
about 80 rows rebuilt per 100 ms tick, each formatting its string whether
the row is shown or not. With `map` and `join` a row holds its numbers once,
the data source keeps no second copy, and the view formats the string for
the rows that are mounted.

## Decisions

### D1 — Functions, with the web's names and callback shape

```
join(map(c.series, (p, i) => `${x(i)},${y(p)}`), " ")
filter(items, (item) => item.visible)
```

- `map(list, callback)`, `filter(list, callback)` and `join(list,
  separator)` are roster functions, spelled like every other roster entry.
  The roster has always turned the web's methods into functions:
  `contains(s, t)` is `s.includes(t)`, `length(x)` is `x.length`, `first(xs)`
  is `xs[0]`. `.` in Contract reads a record's field and nothing else, so a
  method form would be the language's first method and would collide with a
  shape that has a field named `map`.
- The callback is an arrow function, as on the web: `x => e`, `(x) => e`,
  `(x, i) => e` or `() => e`. The second parameter is the item's index, a
  `number`, as `Array.prototype.map` passes it. The web's third argument (the
  array) is not passed: the list is already in scope.
- An arrow function is only ever the second argument of `map` or `filter`.
  Anywhere else it is `type-arrow-position` (and outside any call's
  arguments it does not parse). It is not a value: it has no type and cannot
  be a `derive`, a state, a prop, an argument to a `fn` or another roster
  entry, or a result. So nothing escapes the call it is written in, and
  there are no closures to keep.
- Its body is one expression. It reads its parameters and whatever the
  enclosing expression can read: a view's props, items, states and derives;
  a `fn`'s parameters. A parameter shadows an outer name, as a `match`
  binding does. Two parameters may not share a name, and there are at most
  two (`type-arrow-parameters`).
- The parameters are binders everywhere the compiler rewrites expressions:
  capture-avoiding substitution renames them apart when a component's prop
  or a derive mentions the same name, derive resolution freshens them, and
  the `fn` call graph walks callback bodies, so a `fn` that reaches itself
  through a callback is `type-fn-recursive`.

### D2 — Pure by construction

A Contract expression has no effects: assignments, commands, `send` and
`refresh` are statements, and an arrow's body is an expression. So the body
cannot write state, run an action or ask a source, and nothing needs
checking beyond what every expression already gets. It may call the roster,
`fn`s, and `map`/`filter`/`join` again.

A callback body runs once per item, perhaps never. The rewrites that bind
repeated work once treat it as a branch: a `fn` call or derive read that
only a callback makes is bound inside the callback (once per run), never
hoisted ahead of a list that may be empty.

### D3 — Bounded: 65,536 list steps per evaluation

- One evaluation of one code body (a binding, a derive, an action) takes at
  most **65,536 list steps** (`MAX_LIST_STEPS`): each run of a callback body
  is a step, nested runs each counted, and each item `join` prints is a
  step. The next step is the trap `IterationLimit`, named by the pc of the
  `Map`, `Filter` or `join` that took it.
- Why steps and not a list length: nested calls multiply (a length cap alone
  would allow 65,536² runs), and a `join` inside a callback would otherwise
  print a whole list per run for free. A callback body is straight-line
  code with forward jumps, so the bound caps the instructions an evaluation
  runs at 65,536 times the code's length. What an instruction costs is what
  it costs today: a `==` over two lists or a `contains` walks its operands,
  within the existing value bounds, so an evaluation's work is at most
  65,536 times its body's.
- Why 65,536: the one consumer takes 96 steps per row (48 runs, 48 joined
  items). It leaves room to map a 5,000-item answer once in a `derive`, or
  255 × 256 nested.
- The value bounds that already hold keep holding, checked as the list is
  built: a `map` result is a list the VM builds (`MAX_VALUE_NODES`,
  `MAX_VALUE_BYTES`, depth), and `join` makes a string (`StringTooLong`, a
  typed trap, not a type mismatch).
- **At compile time** nothing is known about lengths: lists come from data.
- **At bake** the first frame is evaluated against baked answers; a trap
  there fails the bake with the trap and its pc, as any trap does today.
- **At run time** a trap while the tree updates poisons the runner, as every
  binding trap already does (`StringTooLong`, `ValueTooLarge`,
  `TypeMismatch`): the journal says `… poisoned the runner:
  Instance(Trap(IterationLimit { pc }))` and later commits are refused. A
  trap in a derive or an action's own body refuses that commit. Making tree
  traps recoverable is transaction work for every trap, not this one, and is
  not proposed here.

### D4 — Types

| call | parameters | result |
|---|---|---|
| `map(xs, f)` | `xs: list<T>`, `f: (T, number) => U` | `list<U>` |
| `filter(xs, f)` | `xs: list<T>`, `f: (T, number) => bool` | `list<T>` |
| `join(xs, sep)` | `xs: list<T>` with `T` a `string`, `number` or `bool`; `sep: string` | `string` |

- The callback's parameters take their types from the list; nothing is
  annotated. A body whose type is not `bool` in `filter` is
  `type-argument`.
- `join` prints each item as `toString` does (the web's `Number` to
  `String`, so `join(xs, ",")` is `xs.join(",")` for these types). An empty
  list joins to `""`. A list of options or records is `type-argument`: the
  web would print `[object Object]`, which no view wants.
- The roster table gets three rows. `map` and `filter` take `any, any` and
  return `any` there, as `first` does, with the types above in the checker,
  which types them before any argument is inferred as a value. Their rows
  exist so the names are reserved (a `fn` named `map` is
  `contract-fn-shadows-roster`) and listed. They are never lowered to
  `Call`: a plan that calls them that way traps with a type mismatch.
- No list literal and no `slice` are added. `length(xs)` already works on
  lists.

### D5 — Lowering: two opcodes with an inline body

`Map u32` and `Filter u32`. The list is on the stack; the callback body
follows the opcode inline; the operand is the offset just past the body.

```
<list>            ; the list
Map end
  <body>          ; reads LoadLocal k (item) and LoadLocal k+1 (index)
end:
```

- The VM pops the list; for each item it binds the item and its index as
  the next two locals and runs the body to `end` on an operand stack of its
  own (the caller's is set aside), then takes the one value the body left.
  `Map` collects the values; `Filter` keeps the item when the value is
  `true` (anything else is a type mismatch). An empty list skips to `end`
  with an empty result; a filter that kept every item is the same list.
- The VM keeps an explicit stack of callbacks in progress (absolute pcs,
  one step counter for the evaluation), and at every instruction boundary
  first finishes any callback whose `end` it has reached, innermost first,
  so nested callbacks that share an `end` unwind in order. It traps
  (`Malformed`) when a body leaves other than one value, drops a local it
  did not bind, or reaches `Return`; a body cannot read or drop what its
  caller left on the stack (`StackUnderflow`).
- The plan checker treats `end` like a jump target (after the opcode, on an
  instruction boundary) and adds three rules: no jump inside a body goes
  past its `end`; no jump from outside lands strictly inside it (landing on
  `end` is a branch around it, which a trailing ternary produces); and
  bodies nest, since an inner `Map` is a jump inside its outer body. The VM
  checks the first again at run time. So the only backward transfer is the
  VM's own return to the body's start, once per item, and a checked body
  still terminates.
- Locals: the compiler already counts the locals in force (`fn` expansion,
  inline `match`, shared lets), so the callback's two locals are the next
  two indices. Inside a `fn` this is the same: a `fn` is expanded where it
  is called, and a `fn` expanded inside a callback continues from there.
- Why opcodes and not roster calls: a `Call` takes values, and a callback
  is code. Why not compile-time unrolling: lengths are not known until run
  time.
- The plan format changes (two opcodes, three roster rows), so
  `FORMAT_DIGEST` changes and every app re-bakes; there is no compatibility
  path (`rules/RULES.md`: delete, don't deprecate).

### D6 — Recomputed only when what it reads changes

A binding is re-evaluated when an input it reads has changed (LLP 1005 §8).
For a row, the row's item was one input: any change to the item re-ran
every binding in the row that read any field of it. So a crypto row's
`points`, which reads `c.series`, would be formatted again on the tick after
its price moved, when only its flash went off.

The dependency table now also records **which fields of the innermost
frame's value** a body reads: the `LoadItem 0` or `LoadBound 0` → `Field k`
pattern sets bit `k` (63 and past share bit 63), and any other read of that
value sets every bit. When a kept row's item (or a kept arm's bound value)
changes, the runner compares the old and new records field by field with
`equivalent`, as it compared whole items (so signed zero still counts), and
enters the scope with the mask of fields that changed; a value that is not
a record of the same length marks every field.

The mask refines one term only: "the innermost frame changed". A body is
stale, as before, when a root input it reads changed, when an outer frame
it reads changed, when a row slot it reads was written, when it is opaque,
or when `full` evaluation is on; and it is stale through the innermost
frame only if a field it reads changed. Conservative rules at scope edges:

- A subtree's reads are folded into its parent's with frame depths shifted
  (LLP 1005 §8). A read made from a deeper scope that lands on the parent's
  frame 0 after the shift (`c.name` inside a `when` or a nested `each`
  within row `c`) marks every field: which field is not kept that far out.
  An inner frame's field numbers are never read as the outer frame's.
- Keys and a region seen from outside (a shift of 1) are not refined.
- Leaving a scope restores the enclosing scope's mask with its dirty
  frames.

It applies wherever a kept row or arm is entered: a keyed `each`, a
`windowed` list, a virtualized list's mounted rows (`reposition`) and a
`match` arm. So `points` is formatted when the row appears and when
`series`, `lo` or `hi` change, and at no other time. Nothing is memoized and
nothing is stored beyond one 64-bit mask per dependency entry and per
update scope; the kernel still only gets a `SetProp` when the new string
differs. The incremental-equals-full test covers it (a map/filter/join in
its synthetic app's plain and virtualized rows).

This is general, not specific to `map`: any binding in a keyed row now
skips when the fields it reads did not change. It could land on its own;
it lands here because the consumer needs it.

### D7 — Hosts and data modules

- Every host runs the runner; the web runs it in `app.wasm`. There is no
  host code to change and no second evaluator to keep in step.
- TypeScript and Rust data modules are unaffected: Contract expressions
  never run below the data seam.
- A retained action binding (`binding_projection`, LLP 1035.001) accepts a
  fixed grammar of loads and fields; a handler argument that uses `map` is
  outside it and is refused `Unsupported`, as a ternary is. Ordinary
  dispatch evaluates it as any expression.

### D8 — `rules/DEFERRED.md`

Iteration in views is not listed there, so nothing moves on or off the
doing-list. The bound this relaxes is LLP 1017 P5's, amended here.

## Refused, with the trigger

- `reduce`/fold, `find`, `some`, `every`, `sort`, `indexOf`, `includes` on
  lists, `flatMap`, `concat`, `slice`, spread (`Math.min(...xs)`), list
  literals, and callbacks with a block body. The trigger for each is a
  view-only need demonstrated in source. The crypto port needs its series'
  minimum and maximum; a fold would compute them, so the data source keeps
  `lo` and `hi` in the row beside the series (two numbers the tick updates).
- A number-to-fixed-decimals formatter (`toFixed`). LLP 1054.000.003 D5
  proposes `formatNumber`; the port rounds with `floor(v * 100 + 0.5) / 100`,
  which `toString` prints as the same two-decimal value.
- Method syntax (D1).
- Memoizing a derived value across evaluations, and recoverable tree traps
  (D3).

## Diagnostics

What an agent or a web developer predictably writes first is refused with
the spelling that works or what to do instead (`contract_syntax::idioms`),
each with a test in `contract/cli/tests/it/lists.rs` and a reject fixture:

| written | id | the message says |
|---|---|---|
| `xs.map(f)`, `xs.filter(f)`, `xs.join(",")`, any `x.name(…)` | `syntax-method-call` | write `map(xs, f)`; the roster spells the web's methods as functions (`contains(s, t)` is `s.includes(t)`) |
| `xs.length` (and `xs.map` without a call) | `type-not-a-record` | write `length(xs)` |
| `reduce`, `find`, `every`, `sort`, `slice`, `flatMap`, `concat`, `indexOf`, … as a function or a method; `some(xs, f)` | `type-refused-idiom`, `syntax-method-call`, `syntax-refused-idiom` | refused by this LLP; compute it in the data source, as the crypto port keeps `lo` and `hi` |
| `Math.min(...xs)`, `Math.max(...xs)` | `syntax-method-call` | `min(a, b)` takes two numbers; over a list, the data source |
| `toFixed`, `toPrecision` | `type-refused-idiom`, `syntax-method-call` | round with `floor(v * 100 + 0.5) / 100`, or `formatNumber` once LLP 1054.000.003 lands |
| a view line `map(xs, x => text x)` | `syntax-map-view` | repeat children with `each x in xs key=x.id` |
| a callback whose body is a node (`x => text x`, `x => Row(…)`) | `syntax-callback-view`, `type-callback-view` | the same |
| `filter(xs, x => x.name)` | `type-argument` | Contract has no truthiness: `x.name != ""` (a number `!= 0`, an option `!= none`, a list `length(…) > 0`) |

## Tests

- Types and syntax (`contract/cli/tests/it/lists.rs`): every arrow form; an
  arrow outside `map`/`filter` (`type-arrow-position`), including as a `fn`
  argument; duplicate or three parameters; `filter` with a non-`bool` body;
  `join` of records and with a non-string separator; nested `map`; a
  callback reading an outer name, a shadowing parameter, and a `fn`
  parameter; a prop that mentions a callback's parameter name; recursion
  through a callback; a repeated call bound inside the callback; a `fn`
  named `map`.
- A corpus fixture (`contract/corpus/lists.contract`, the crypto chart in
  miniature) proven on the runner; map/filter/join in the incremental test's
  synthetic app.
- VM: 65,536 runs across nesting pass and one more traps; a `join` of
  65,536 items passes and of 65,537 traps; empty lists; a filter body that
  is not a bool; a `Return` in a body; a body that pops its caller's operand
  or drops its item; `join`'s printing and its typed overflow.
- Plan checker: a jump leaving a body, one entering it, a branch landing on
  its end, and crossed bodies.
- Runner: a keyed row's `points` binding is evaluated when the row appears
  and when its series changes, and not when its flash or tags change, in a
  plain `each` and in a virtualized list (`bindings_evaluated`); `full`
  evaluation agrees.
- Bake and boot: a nested map past the bound fails the bake and the boot
  with `IterationLimit`.

## The value's text (Charlie, 2026-09-28)

This spec's saving rests on the 16-byte `Value` (perf/value16, `9f70cda1`:
text and items behind one thin pointer). Its text is now two variants with
one meaning, ruled on 2026-09-28 ("the new safe variant"):

- `Value::InlineStr` holds text of up to 14 bytes in the value itself (a
  length byte and the bytes; safe Rust, read with `str::from_utf8`), and
  `Value::HeapStr` the rest, shared by count. `Value` stays 16 bytes,
  asserted at compile time and in a test.
- Construction picks: `Value::str`, `From<&str>`, `From<String>` and
  `From<Str>` hold text of 14 bytes or less inline; decoding does the same.
  Nothing outside `exact-plan` can make shared short text (its payload is
  opaque; only a doc-hidden constructor for consumers' tests does).
- Every read goes through one accessor, `Value::as_str` (and `text`,
  `is_str`, `to_shared_str`, `same_str`, `str_identity`,
  `str_strong_count`). Both payloads are opaque, so no caller can read text
  from a variant; a caller matches text as `v @ exact_plan::str_value!()`,
  a pattern for both variants together, and never names one alone.
- Equality, the canonical encoding, `Debug`, the runner's `same`,
  `equivalent` and `equal`, the decode pool's keys, and the JSON bridges
  (`exact-js-value`, the web and Apple batches, the agent's JSON) treat the
  two forms of one text as one text; tests in `exact-plan`, the runner,
  `exact-js-value` and `exact-web` pin it. `same` is identity: one
  allocation, or equal inline bytes (inline text has no allocation, and
  equal text is indistinguishable, the reason the decode pool may share it).
- Every wildcard arm over `Value` in the workspace was audited; since no
  arm outside `exact-plan` names one text variant alone, a wildcard sends
  both forms of text where it sent text before.

Why 14 bytes: most of an app's text is short. The Extra Heavy feed holds
68,527 distinct strings, 80% of them 14 bytes or less, each a 32-byte
allocation (arcstr's 16-byte header, rounded) where Swift keeps up to 15
bytes inline.
