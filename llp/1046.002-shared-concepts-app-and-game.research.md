# LLP 1046.002: What the app engine and a game engine can share — and what they should not

**Type:** Research
**Status:** Draft (findings from reading the tree and the corpus on 2026-09-17; it proposes nothing on its own authority, and is not linked into `llp/current/`)
**Systems:** GPU module (`gpu/`), Runner (clock, events, the data seam), Motion (`exact-motion`), Agent API, Delivery, the dev loop, the hosts' input paths, Linux host; the proposed engine add-on (LLP 1046 §5)
**Author:** Claude (Fable 5.1) for Charlie Cheever
**Date:** 2026-09-17
**Related:** LLP 1046 (the analysis), LLP 1046.000 (the consumer), LLP 1046.001 (the agent interface); LLP 1002 / 1003 (motion; one representation, two executors), LLP 1005 §6–§7 (events, the clock, the data seam), LLP 1007 §6 (what a reload carries), LLP 1009 (D2 the module, D4 the frame, D5 shaders, the `Custom(u16)` extension point), LLP 1012, LLP 1014 (children; D5 placements), LLP 1015 §7, LLP 1016, LLP 1018, LLP 1020 (D2 messages are strings; D4 the guest joins the eight), LLP 1027 (storage), LLP 1027.000, LLP 1027.002, LLP 1029.000 §3–§4, LLP 1030 D8 and LLP 1030.000 §4 (the asset row), LLP 1038; `rules/NOT-DOING.md`; `CLAUDE.md` (optional capability)

## Summary

Charlie asked whether concepts can be elegantly reused across the app engine
and a game engine — without forcing anything that does not naturally fit.
Twenty candidates were read against the tree. **Nine are reused as they
are** — the clock, the explicit-input rule, the module artifact and the
loop inside it, `bind`, canvas children as game UI, the spring, delivery,
the agent's eight operations, and two habits (the parity oracle; one
declaration authority). **Three need a
new seam in the core**, each small and each with a consumer that is not a
game. **Three are already decided in the corpus and unbuilt**, waiting for a
consumer a game would be. **Five should not be unified**, and the reasons
are the more useful half of this document.

The finding that does the most work is F3: **the display-rate loop a game
needs already exists, and it is the GPU module's.** A game is not a new
kind of app. It is a guest in a `canvas`, as a web page is a guest in an
`iframe` (LLP 1020) — and most of what follows is that one sentence applied.

## 1. Method

Each candidate gets one verdict: **reuse** (works as it is, or as a library),
**seam** (the core changes; §3 says how little), **owed** (decided
elsewhere, unbuilt), or **keep apart** (tempting, and wrong). "Fits" means
the game wants the same *semantics*, not a similar-looking API.

## 2. Findings

### Reuse

**F1. The clock.** One clock already reaches everything that moves: the
runner's timers, `exact-motion`, and the GPU module through
`Frame::now_ms` — "the host's presentable clock — deterministic under the
agent's `clock`; a surface that samples wall time is not" (LLP 1009 D2). In
agent mode the module "never reschedules itself; `clock` asks it for a
frame" (LLP 1012 §2). A fixed-timestep world keyed to that value —
`tick = floor(now_ms × hz / 1000)` — inherits the seek (LLP 1005 §6: sixty
advances of a second equal one of a minute) with no new clock and no new
agent operation. *Reuse, unchanged.*

**F2. Explicit time and randomness.** LLP 1027.000 D1: a time-dependent
source takes its time as an argument, a randomized one takes a seed;
"Rust providers follow the same explicit-input contract". A world's seed is
a `canvas` argument — `canvas surface=world(level, seed, paused)` — and its
time is F1. The rule is reused; what it cannot do for native Rust (it can
still call OS APIs) a world hash would catch (LLP 1046.001 D5). *Reuse.*

**F3. The module artifact, and the loop inside it — one module, one
memory.** Nothing per-frame reaches app code through the runner: every host
advances it on a **250 ms** interval (`host/web/glue.js:1375`,
`Session.swift`, `host/linux/src/display.rs`); the display link and
`requestAnimationFrame` drive only motion and the GPU module. So the 60 Hz
loop exists, and it is `Surface::render`, returning `true` to ask for the
next frame — `aurora` and `glass` do exactly that today.

LLP 1046 F6 asked how a simulation reaches a renderer at 60 Hz across the
plan. The natural answer is that it never crosses it: **the simulation
lives in the same module as the renderer** and steps inside `render`, off
`Frame::now_ms`. One artifact (`dlopen`ed dylib, or a second wasm), one
address space on every host including the web, loaded after first pixel,
absent from apps that have no world (LLP 1009 D2). The channel problem is
removed rather than solved. What it costs: the world pauses when its
canvas is off screen (the host renders "when the host judges it on
screen", LLP 1009 D4) — for a game on a phone that is the right default —
and the module's name outgrows "GPU". *Reuse; rename someday.*

**F4. Runner → world is `bind`.** Pause, volume, the chosen level, a
restart counter: plan values, arriving as `bind(inputs)` whenever they
change, "the newest arguments win" (LLP 1016 D5). A one-shot command is a
counter slot. *Reuse, unchanged.*

**F5. Canvas children are the game's UI toolkit.** LLP 1014: a `canvas`
holds Contract children, laid out by the kernel, composited over the
surface everywhere, handed through it as textures where the host can; D5
gives each direct child its own texture, and the surface answers
`placement(index)` with a homography and a depth that the host inverts to
hit-test and reports to accessibility. That is a HUD, a pause menu, a
dialogue box, a name-plate over a character and a readable, tappable
signpost in the world — with real text shaping, fonts (LLP 1019), focus and
accessibility — for no engine code at all. `stack` already places cards in
3D this way. A game engine's weakest subsystem is the app engine, finished.
*Reuse, unchanged.* One limit to respect: D5 placements are per *direct
child*, captured per child; forty name-plates is forty captures. Measure
before leaning on it for crowds.

**F6. The spring and the transition, as a library.** `exact-motion`
depends on nothing and is closed-form: `SpringConfig::sample(displacement,
velocity, elapsed)`, `settle_time(…)`, `Engine::advance(now)` — "one seek
gives the bits sixty would" (LLP 1002 D3). A lantern's intensity, a
camera's ease, a UI-like flourish in the world are that function, called by
the add-on as any crate calls another. And there is a finding in the tree:
`apps/caltrain/gpu/src/stack.rs` steps its **own** critically damped
springs from `now_ms` deltas (`:403-410` — sub-steps with a remainder, the
delta clamped to two seconds), so where a card lands depends on how the
clock was advanced; the closed-form spring does not. A world would want
the second kind for the same reason the agent does. *Reuse as a library.* (Skeletal
animation is F17 — a different thing.)

**F7. Delivery.** A world's level, tuning tables and shaders are files in
the app's conventional trees; bake digests each; native hosts fetch by
digest; a dev shader edit is one `{seq}` that the running module swaps in
when its interface digest still matches the binary's (LLP 1030 D8,
LLP 1030.000 §4 — driven on web and macOS). A level edit reaching an
installed game without a host rebuild is that mechanism with a different
file extension. *Reuse*; the bytes-to-the-module half is F13.

**F8. The agent's eight operations, by the iframe's precedent.** LLP 1020
D4 already ruled on a second world inside a node: "the guest joins the
eight operations. No ninth op, no controller" — a guest outline in `tree`,
`tap`/`type` addressed into it, `screenshot` composing its pixels, and an
agent export on its module (`exact_web_agent_eval`). LLP 1046.001 is that
ruling applied to a `canvas`. *Reuse the ruling; the pass-through is S3.*

**F9. Two habits, not code.** *The parity oracle* (LLP 1002, 1009 D1): one
representation, two executors, a fixture between them — as built, each
host's canvas is held to a recorded picture at ≤ 1 % of pixels beyond
±8/255 (`scripts/smoke.mjs`, `scripts/png.mjs`). A renderer held to a
reference path tracer, and a simulation held to a cross-host hash, are the
same habit. *One declaration authority* (`kernel/tables/schema.json`,
`plan/tables/format.json` → generated code): a world's **component table**
should be one too — generating the save format, the hash order, the agent's
JSON and the level checker from one file, so none can drift from the
others. Neither habit shares a line of code with the add-on; both are why
it would feel like this repository.

### Seams — the core would change, a little (§3)

**F10. Continuous input reaches a world.** Today: thirteen event kinds
(`plan/tables/format.json` `EventKind`); `key` is key-down only, the name
as the web spells it, no key-up, no repeat, no modifiers; "not events:
pointer coordinates and moves (a drag), `keyup`" (LLP 1005 §6). A canvas
*can* carry the ordinary handlers (`press`, `key`, `hover` — only `load`
and `message` are tag-restricted), but nothing it could receive describes a
held key or a moving pointer. Routing those
through the runner would be wrong anyway: they are not state, they are
device samples, and the runner ticks at 4 Hz. *Seam S1.*

**F11. World → runner.** Values flow runner → surface only. A HUD needs
"7 / 12" to come back. The iframe already solved this shape: the guest
posts a **string**, the host dispatches `message` on the node, an action
takes it from there (LLP 1020 D2 — "messages are strings"). A world posting
a message on its canvas when a *published* value changes — a score, a
flag, never a per-tick sample — reuses the event kind, the handler, its
string payload and the agent's view of it. The lowering refuses `message`
on any tag but `iframe` today (`contract/lower/src/lib.rs:1315`); the seam
lifts that for `canvas`. *Seam S2 — a method on `Surface`, one dispatch in
each presenter, one tag admitted.*

**F12. The agent's reads reach a world.** `runner/src/agent.rs` emits a
fixed key set and has no registration hook — and should not grow one: the
host already merges its own `state` sections outside the runner. *Seam S3 —
one export on the module's ABI; LLP 1046.001 §2.*

### Owed — decided already, waiting for a consumer

**F13. Asset bytes to a module.** LLP 1030 D8 names "textures, meshes,
lookup tables" as assets beside WGSL; only shaders are wired
(`gpu/src/shaders.rs`: `set_shader(name, text, expected)`). No decoded
image reaches a surface as a texture today except inside the children
texture; hosts decode images, apps do not (LLP 1011). A world needs named
bytes — glTF, KTX2, audio — the same road shaders travel. *Owed by 1030.*

**F14. The Linux host loading the module.** "The GPU module this host does
not load yet" (LLP 1015 Related; §7). Headless worlds on the fleet —
LLP 1046.001 D7 — wait on it; a module whose simulation runs without a
device is the smaller half. *Owed by 1015.*

**F15. `Property::Custom(u16)`.** LLP 1009 decided the extension point for
display-rate values reaching `bind` from `exact-motion`; `motion/src/
property.rs` still has four properties and no `Custom`. With F6 as a
library a world does not need it; an app that wants a Contract
`transition` to drive a shader uniform does. *Owed by 1009; not on a
world's path.*

### Keep apart

**F16. The kernel tree and the scene graph.** Both are trees of nodes with
transforms, and that is where it ends. The kernel tree is CSS layout —
boxes sized by content and constraint, the web as its oracle. A scene graph
is rigid transforms, authored positions, thousands of instances, no
measurement. Making either the other would cost the kernel its oracle or
the world its speed. They meet at exactly one point, and it is already
built: a placement (F5).

**F17. Skeletal animation and `exact-motion`.** `exact-motion` is CSS's
`transition` model over four properties of a box. A skeleton is sampled
clips blended by weight through a state machine, forty joints at a time. The
shared idea — a pose is a pure function of the clock — is F1, not a shared
type. The add-on should use a spring *from* `exact-motion` (F6) and keep its
animation runtime its own.

**F18. Contract and the level format.** Tempting: Contract already has a
parser, types, a roster check and a build-time error with a line number.
But Contract is a reactive UI tree with bindings to slots and resources; a
level is static data validated against a component table (F9), and the
behaviour is Rust. Bending Contract to describe entities would add a second
language inside the first. Share the habit — refuse at build, by name, with
a position — not the grammar. The border stays clean at one attribute:
`canvas surface=world(level, seed, …)`.

**F19. The Router and scene management.** The Router (LLP 1038) owns a
location, a stack per tab, six verbs, the address bar. A game's title,
settings, level select and "you made it" *are* routes and should simply be
routes; the world is one canvas on one of them. Inside the world, loading a
level is the simulation's business, and giving it a URL is an app-level
choice (`/play/island-2`), made with the Router as it is. Nothing to unify;
something to use.

**F20. Gestures, scrolling and game input.** `NOT-DOING.md` §Motion: no
gesture arena; "the platform recognizes; the engine follows"; scroll always
wins. A world wants the opposite — raw contacts, unrecognized, its own.
These coexist only if they never mix: S1 delivers raw input **to a canvas
that asked for it, inside its box, and nowhere else**, the way `touch-action:
none` and pointer capture scope it on the web. The app engine's gesture
rules are untouched outside that box, and the add-on never gets a say in
them.

*And one with nothing to unify with:* **audio.** There is none in the tree
(no hit for `audio`, `AVAudio`, `AudioContext`, `cpal`, `kira`, `rodio`).
The add-on would own its audio device as it owns wgpu's — WebAudio through
the bindings the module already has, `cpal`-class natively — so it needs
**no core seam**, with one likely exception: iOS's audio session (silent
switch, interruptions) is the host app's to configure. Under the agent the
device is never opened; the journal is the output (LLP 1046.001 D2). If
apps later want interface sounds, the add-on's crate is where to look —
reuse flowing the other way.

## 3. The seams, stated as small as they are

Each is justified by a consumer that is not a game, or it should be refused.

- **S1 — raw input to a canvas that asks.** `Surface::wants_input() -> bool`
  (default `false`) and `Surface::input(&mut self, event)`: key down/up by
  the web's names, pointer phases with coordinates in the canvas's points,
  wheel, a stick. Delivered by the presenter straight to the module, stamped
  with the host clock, never through the runner; scoped as F20 says. The
  agent's carrier work is done — LLP 1035.003's phases are already real
  platform events on the web and macOS. *Non-game consumer:* Caltrain's line
  map — pan, pinch, scrub to a station — cannot be built today.
- **S2 — a surface posts a message.** `Surface::messages(&mut self) ->
  Vec<String>` drained after `render`; the host dispatches `message` on the
  canvas's node. *Non-game consumer:* the same map telling the app which
  station was tapped; any chart with a selection.
- **S3 — an agent export on the module.** `gpu_agent(len)` beside
  `gpu_render`, mirroring `exact_agent` and `exact_web_agent_eval`.
  *Non-game consumer:* any surface an agent must verify without reading
  pixels — "which station does the map think is selected".
- Also read for a seam and **not proposed**: carrying a surface's private
  state across a dev reload. Surfaces are re-created on a plan reload
  (LLP 1009 D2), `Surface` has no save hook, LLP 1029.000 defers
  "GPU/surface replacement, arbitrary native object migration", and
  `NOT-DOING.md` refuses generic executor-private state migration. A world
  already has the honest version: its save file, reloaded
  (LLP 1046.001 D6). Slower than a slot carry; no new machinery.

## 4. Later, if measured

**Worker placement.** LLP 1027.002 places a data module on a worker;
`NOT-DOING.md` holds "Rust on a web Worker … behind a consumer that needs
it". WebGPU works in a dedicated worker with an `OffscreenCanvas`, so the
whole world — simulation and renderer, still one memory — could leave the
main thread and the DOM's UI would never drop a frame to it. It is the
natural second step of F3 and the wrong first one: nothing has been
measured, and the children-texture path (F5) would have to cross the
boundary.

## 5. Open questions

1. F3's cost — a world that stops when its canvas is off screen. Right for
   a phone; is it right for a simulation someone wants running behind a
   menu? (A route that keeps the canvas mounted answers it without a seam.)
2. S1's scoping on iOS, where there is no `touch-action`: which recognizers
   must fail inside the canvas's box for raw contacts to arrive, and does
   that disturb the dev menu's four-finger tap?
3. S2's rate. "Published values only" is a convention; should the host
   enforce a ceiling per frame?
4. Whether the module's name and the `gpu_` prefix change when it carries a
   simulation, or whether that is a rename for after a consumer exists.
5. F9's component table — a JSON table like `schema.json`, or Rust derives?
   The first matches the house; the second matches the ecosystem.

## Confidence

High on what exists — every "today" sentence above was read from the tree
or a spec on 2026-09-17, by this author or by two read-only survey agents
whose citations were spot-checked (`glue.js:1375`, `WebModule.swift:56`,
`stack.rs`, LLP 1015, LLP 1027 on agent-mode storage). One survey claim
failed its check and is corrected above: `message` is not accepted on any
tag, only on `iframe`. Others may be wrong the same way; the code is the
authority. Medium on the verdicts: F3 and
S1–S3 are designs on paper, and LLP 1046.000's S0 slice is the experiment
that would confirm or sink them in days. Low on F5's cost at crowd scale and
on §4 — neither measured.
