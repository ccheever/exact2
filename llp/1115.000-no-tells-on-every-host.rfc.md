## 0. Summary

LLP 1115 changed the top rule on 2026-10-09 from "the web is the standard" to "write the web,
ship the platform": what the author writes is CSS and wins; what the author leaves unsaid is
the platform's for anything a person can see or feel; layout defaults and names stay CSS. Its
two waves and the four bake-off rounds since built most of that on iOS and on the web.

On 2026-10-11 Charlie asked for a second audit: where does the code, or anything else, still
follow the old rule? Six read-only passes (iOS, macOS, Android, the web, the kernel and
compiler, the words) read main at `ccc9afd52` and returned 242 findings, with overlap between
passes. LLP 1116.003 landed the same day; a seventh pass re-read the findings it touched at
`ccd3d3be7`. It had fixed four and part of two. Nothing was built or run by any pass: every
finding is from reading. Appendix A lists them by ID.

This document sorts them three ways:

- **Wave 0** (§3): the words, and fixes with one possible answer under rulings already made.
  It lands now.
- **Sixteen decisions** (§2), each with a proposed answer. They are for review before any of
  it is built. §5 lists the questions that are still Charlie's.
- **What waits for its own document** (§4): the Mac's structure, Android, the painted hosts.

## 1. What the audit found

1. **LLP 1115 landed on iOS and the web, and reads as landed everywhere.** System Back
   without an authored control (D5 there) is called only from the iOS presenter on Apple, so a
   pushed route on the Mac has no way back. Press feedback for an undeclared pressable is under
   `#if os(iOS)`. LLP 1115 §6 says "`showModal`/`close` on every host"; the Linux host refuses
   both. Its "Still open" list names three things that have since landed.
2. **Author > platform has two holes in its mechanism** (D2). A host cannot tell what the
   author wrote, so it guesses, and the guess drops authored platform colours on iOS controls
   and cannot separate the compiler's implied rows from the author's.
3. **The compiler writes iOS's look onto every host** (D3). The grouped-list sheet is nine
   literal iOS hex pairs and iOS point sizes, so `list appearance="auto"` on the Mac is an
   iPhone Settings list at 17 points. The web's stylesheet repeats about fifteen of the role
   table's colours as hex, and two have drifted from it.
4. **Native behaviour that was made to match the browser on purpose is now a tell.** On the
   Mac: a click on a button takes the focus, Tab reaches every button whatever the system
   setting, inner scrollers never rubber-band. On iOS: scrolling never dismisses the keyboard,
   a plain Return leaves it up, nested scrollers chain. Each was a ruling under the old rule
   (LLP 1104 D6, LLP 1010 §3), and seventeen tests pin them (D14); five more pin the Linux
   painter's look and are LLP 1115.001's.
5. **The web's designed look has gaps a web developer notices** (D4): a popover is the
   browser's bordered box in the middle of the viewport, custom pressables and links give no
   hover or press response, checkbox and radio are the browser's 13 px ones beside 36 px
   designed fields, a modal route has no surface.
6. **Ten items of the 2026-10-09 audit are in neither of LLP 1115's lists**, done or open:
   keyboard dismissal on scroll, the large title's collapse, nested-scroll chaining, the iPad
   focus halo, `scroll-behavior`, control margins, SVG `fill`, `hr`'s margins, the Mac's route
   header, and Tab under Keyboard Navigation. Each has a decision below or a line in §4.
7. **The words.** `README.md`'s third principle, the root explainer (LLP 1000) and the kernel
   spec's §1 rule (LLP 1001) still say "the web is the standard". About twelve rulings in older
   LLPs decide presentation by that rule and carry no note. Three `QUEUE.md` entries now point
   the wrong way.

### D2 — "Written" is a fact each row carries

Author > platform needs each host to know what the author wrote on a node. Today hosts guess:

- iOS's `ownColor` counts a colour as written only when it is not a platform colour and
  differs from the parent's. So `color="-exact-system-red"` on a bar button, a spinner, an
  alert's action or a segment's symbol is dropped, and naming a role is what the docs teach
  (IOS-06). A written colour equal to the parent's is dropped as well.
- A row the compiler implies (a tag's fixed rows, a heading's size and weight, a link run's
  colour, the whole grouped sheet) is an ordinary style row. A host cannot tell the sheet's
  `color` from the author's (KRN-07).
- So LLP 1116.003 D7 taught the kernel a third guess: `kernel/src/grouped.rs` keeps a copy
  of the sheet's colours and sizes (`SHEET_COLORS`) and calls a grouped row's text authored
  when its value differs from them. That fixed the footer, and it means the sheet now lives
  in two places that must change together (D3.1).

**Proposed.** One bit per style row: *the author wrote this on this node*.

1. **Each row carries its provenance from the moment it is made, through every rewrite.**
   Lowering's `Origin` cannot simply be copied: it is computed by position (`index <
   sheet.len()` is a tag row), only when sites are on, and the grouped sheet's rows are
   spliced in after those boundaries are drawn, so copying it would mark compiler rows as
   the author's. So the bit is set where a row is emitted and never worked out afterwards.
   An attribute the author wrote, or a row of a `style` class the author wrote, is authored;
   a tag's fixed row, a heading's style, a link run's colour, a row a compiler sheet adds
   and a row derived from another (a checkbox's accessibility state) are not. A written
   value that equals its parent's is still written.
2. **Where two rows set the same property, the plan carries the winner's bit.**
3. The bit travels in the plan, the kernel keeps it beside the row, and the batch carries it
   to the presenter. Hosts read it wherever they apply LLP 1115 §2's rule, in place of
   `isSystemColor`, the equal-to-parent test and `SHEET_COLORS`. LLP 1115 §2 then reads
   "written means the bit is set", which is also true of an inherited value (the bit is not
   set on the child).

The first consumer, built alone and first, is iOS's `ownColor`. The plan format and the
compatibility id move once (LLP 1030 D3a).

### D3 — One palette, named by role; text sizes named by text style

1. **No sheet the compiler or a host writes holds a hex colour.** The grouped sheet
   (`contract/lower/src/grouped.rs`, and the kernel's copy of it until D2 retires that) and
   the web's stylesheet (`host/web/index.html`) name roles. Wave 0 did the grouped sheet's
   label colours and its tint (`07c60e572`): a row's symbol and checkmark are `AccentColor`,
   so an authored accent and Increase Contrast reach them, and the Mac draws its own label
   colours. Two parts wait. The separator and the red stay literal pairs until item 2. The
   three surfaces were built and held (`held/1115.000-grouped-surfaces-as-roles`): on macOS
   27 `windowBackgroundColor` and `controlBackgroundColor` are the same colour, so a
   section's card vanishes; they wait for the Mac's own list (§4) or a Mac answer for a card.
2. **The role table gets a neutral column, and Apple's pairs are re-measured** (wave 2). The
   neutral column is what the web resolves a role to under D4's neutral look, and what a
   painted host shows (D17). The pairs that are Apple's stay what an Apple host falls back
   to before it reports its own; where the grouped sheet's measured value and the table's
   disagree (separator, accent, red), the newer measurement goes into the table. A
   probe of an iOS 27 simulator in wave 0 read `separator` `#3c3c431f / #54545880`,
   `systemRed` `#ff383c / #ff4245` and `systemBlue` `#0088ff / #0091ff`, the sheet's values;
   the same pairs are written twice more in `host/web/index.html`, and the table feeds the
   schema's digest, so this is one change with a compatibility move.
3. **The grouped sheet's text sizes are text styles** (`-exact-body`, `-exact-footnote`,
   `-exact-subheadline`), so its text follows the root font size: 13 on the Mac, the reader's
   setting on the web. **Its row metrics stay as they are** (52-point rows, 26-point
   corners): they are iOS's shape, scaling them by `em` would not make them the Mac's, and
   the Mac's own list is §4's work.
4. **An authored `accent-color` reaches every `AccentColor`** on macOS as it does on iOS and
   the web: symbols and rows, not only controls.
5. **A block `link` of text is the tint on native hosts too**, as LLP 1116.000 D4 made it on
   the web. One blue for links on the web: `LinkText`'s web resolution is the accent.
6. Three rows of the role table are corrected. An unset page background is `-exact-background`
   (`windowBackgroundColor` on the Mac), and LLP 1115 §3 says so in place of "`Canvas`";
   `Canvas` stays the document white. `ButtonText` on iOS is the tint, so an authored accent
   reaches it. `-exact-link` and `LinkText` resolve alike on iOS.
7. **Roles are added only as a decision here needs them:** `SelectedItem` and
   `SelectedItemText` (CSS's own names) for a selected row, and a scrim. Shadow colour, metric
   and motion roles are not proposed.
8. **An unsaid SVG `fill` is `currentcolor`, on every host**, the web's sheet included.
   r1 kept SVG's black and added a warning; that leaves an unfilled icon black on a dark
   page, and LLP 1115 §3 says a presentation colour default is never a literal. Black is
   what an author writes when they mean it. The 2026-10-09 audit asked for this too. The
   paint servers' own initial colours (`stop-color`, `flood-color`) stay SVG's.

9. **An unsaid symbol on the Mac is a label colour, not the accent** (ruled, Charlie,
   2026-10-11), as AppKit draws a template image; on iOS it stays the tint, as UIKit draws
   one. The default becomes a role with a column for each. *Measured 2026-10-11 on macOS
   27.0.1:* an untinted template symbol in an `NSImageView` draws black at 50% in a light
   window and white at 55% in a dark one. That is `secondaryLabelColor`, not `labelColor`
   and not the accent, so the Mac's column is the secondary label colour. (The probe is
   kept with the audit's records, `appkit-symbol-probe.swift`.)

### D4 — The web is one look, finished

**Ruled (Charlie, 2026-10-11): "one look", and asked whose, "neutral web look please".**
The web's designed default is the same in every browser and on every operating system, and
it is no platform's: not Apple's, which is what LLP 1116 D1 built and what the audit found
to be the tell on Windows and on Android's Chrome (WEB-01).

So part B below is a redesign and not a finishing. The neutral look keeps what is already
the browser's (the system font, the reader's text size, the browser's accent unless the
author names one, its focus ring) and replaces what imitates iOS: the bar's material and
large title, the tab bar, the alert's shape, the switch and the segmented control's
metrics, and the palette (D3.2's neutral column). It is a matter of taste as much as rule,
so **the new sheet is shown to Charlie first** (every default control and each piece of
chrome, light and dark, in Chrome, Safari and Firefox) and replaces the default when he
has seen it. Part A does not depend on the look and is built first.

**A. Routes are pages (behaviour and accessibility).**

1. **The title follows the route.** `document.title` is the authored `head` title when
   there is one, else the route header's heading, else the app's name. Only the middle step
   is new.
2. **Focus follows the route.** On a push, focus moves to the new route's heading, or to
   the route's own container when it has no heading; on Back it returns to the row that was
   pressed. A focus that an action set explicitly is left alone.
3. **The browser's Forward, and a same-origin link to a declared route, work with no
   `navigate` handler**, as Back does since LLP 1116.003.
4. **A row that only navigates is a link.** The recipes and patterns write `link href=…` for
   it, so ⌘-click, middle click and "Open in New Tab" work. Nothing is inferred in lowering.
5. **A modal route is a dialog to assistive technology:** `role="dialog"`, `aria-modal`,
   focus moved in and returned on close. A tablist and a menu move by arrow keys.
6. A rendered page keeps the manifest's `lang`.

**B. The look.**

7. **Menus and popovers** get a surface (rounded, shadowed, rows that highlight on hover) and
   open anchored to their invoker, or at the pointer for a context menu.
8. **A modal route is a sheet:** the `Canvas` surface, a card over a backdrop on a wide
   window and full-bleed on a narrow one.
9. **Checkbox, radio, range and file** are drawn in the look at the size of the other
   controls, in the accent.
10. **A surface the host paints carries its own ink.** Fields, selects and the app bar take
    `FieldText` or `CanvasText` unless the node's own `color` is written (D2's bit). The
    indeterminate spinner is the secondary label colour, not `currentColor`. This is LLP 1115
    D4 on the web, and it replaces LLP 1104 D4's inherited ink for these surfaces.
11. **A material the host paints honours the person's settings.** The default header's blur
    goes opaque under `prefers-reduced-transparency`; under forced colours the drawn controls
    revert to the browser's own. An effect the author wrote is the author's and is not
    touched.
12. **The shell carries the resets a careful web app ships:** `text-size-adjust: 100%`,
    `touch-action: manipulation` on controls, and `overscroll-behavior: contain` on a shell
    that scrolls inside itself (so a list's top does not pull the page to refresh).
13. **A route `header`'s default padding, minimum height and stickiness have one source
    that every host painting a header shares**, where today only the web's stylesheet has
    them. A host that projects the header (iOS) takes its box out of layout, as now. They
    are a painted header's defaults, written as implied rows (D2), and an author's own win.
14. Small ones, each with one answer: inline links underline on hover and focus; a keyboard
    press shows the pressed state; the Back button matches the other controls and its label
    is localisable; a segmented track is the width of its segments; hairlines are borders
    (D10.3), not half-pixel shadows; symbols and images in pressables are not draggable; the
    select's chevron and the switch's thumb use logical sides; a plain `dialog` has no
    padding the kernel does not know.

### D5 — Back is always there, on every host

LLP 1115 D5 landed on iOS and the web, and not all of it on iOS.

1. **macOS.** A pushed route gets the Mac's ways back, each calling the same `hostBack` iOS
   calls: **Go ▸ Back, ⌘[**; the **two-finger swipe**; and a **navigational toolbar item**
   (a back chevron) while a route is pushed. An authored Back control is still what they
   press. The reviews differ on the chevron: Grok would leave it to §4's structural work
   with the rest of the toolbar. It stays here, because a way back that is only a menu item
   and a gesture cannot be seen, and it is one item, not the header's projection.
2. **iOS, a pushed route with no bar.** LLP 1116.003 D2.2 wrote the rule down as it stands,
   with a warning (`lower-header-no-bar`): with no single heading a route has no bar, no
   title and no Back button, only the edge swipe. LLP 1115 D5 says a pushed route "still
   gets the system back button". **Ruled (Charlie, 2026-10-11: "its ok to break things
   right now, let's do the right long term thing"), and a change to D2.2:** every pushed
   route with no bar of its own gets a bar that holds the system Back alone. That includes
   a route whose `header` is not bar-shaped, where the compiler's warning already tells the
   author what to fix; an app that relied on having no bar changes, and that is accepted.

   **No bar is something the author says, not something inferred.** r2 let an authored Back
   control suppress the bar. But LLP 1115 D5 makes that control the thing the system's
   button presses, and a photo viewer with no header and no control is exactly the screen
   that wants no bar. So a route asks for a full-bleed screen in so many words
   (`navigationBar="none"`; the spelling is the implementer's to settle), and the compiler
   warns when a route draws its own Back control without it, since the bar's Back would be
   a second one.
3. **iOS, the bar per route.** A stack whose first route has no header still shows the bar
   for a later route that has one.
4. **Linux desktop** calls `host_back` for its Back key, in the same wave; it has no caller
   today.

Android's half is LLP 1115.001 D6.

### D6 — Something pressable responds, on every host

An undeclared pressable (a card, a `plain` button, a link) shows the platform's response.
A row of a `list` is not dimmed by this decision: its press is the cell's highlight, which
is D16, and a dim built now would be replaced by it.

| Host | Unsaid press | Unsaid hover |
|---|---|---|
| iOS | dims (landed) | none |
| macOS | dims while the mouse is down, as a borderless `NSButton` does | none |
| Web | dims on `:active` | a fill in `-exact-quaternary-fill` (`hover: hover` only) |
| Android | LLP 1115.001 D9 | |

**A default yields only to the author's version of the same state.** Authored press feedback
(`-exact-press-scale`, a pressed style) replaces the default press; an authored hover style
replaces the default hover. A `hover` handler that only observes is not a style and replaces
nothing. A native control keeps its own feedback, and no dim is laid over it.

A disabled custom pressable dims on every host, as a disabled control does. The web keeps the
tap highlight off, since the press state replaces it. On iOS a press keeps tracking in
UIKit's margin around the control before it cancels.

### D7 — On the Mac, the Mac's rules for focus, keys and text

LLP 1104 D6 made focus "follow the web". Safari on the Mac does not: it does not focus a
clicked button, and the web conformance run already admits that as a known difference
("Safari's macOS convention", `host/web-js/conformance/known-webkit.json`), with its Tab
order. So the Mac's rule is not a departure from the web a Mac user knows.

Two things the author does always win, in every item below: a key the app prevented
(`preventDefault()`) does nothing more, and a focus an action set is kept.

1. **A click on a button, or on empty ground, leaves the first responder where it is.**
   `retainFocus` becomes the Mac's default, not an opt-in.
2. **Tab honours Keyboard Navigation** (`NSApp.isFullKeyboardAccessEnabled`): off, it moves
   between text fields and lists; on, it reaches every control. `tabindex` written by the
   author still wins.
3. **Space presses the focused control. Return presses the default button, when there is
   exactly one.** A dialog with exactly one `filled`, non-destructive button has a default,
   drawn so by AppKit. A dialog with none, or with several, has no default, and Return does
   only what the focused control does with it: emphasis alone never picks among actions.
   When a field is the first responder, a single-line field with a `submit` handler takes
   Return itself; one without passes it to the default button, as AppKit does.
4. **Return in a single-line field sends `submit` and ends editing**, as `NSTextField` does.
   In a `textarea` it is a new line.
5. **A new window puts the caret in its first key view**, unless the author wrote `autofocus`
   elsewhere. A canvas that takes text input keeps today's rule.
6. **A confirmation in the alert shape is `NSAlert`** as a sheet on its window (LLP 1115
   D6's Mac half: text, one cancel, at most three buttons), with Cancel on Escape and the
   default button on Return. A chooser stays the `NSMenu` it is until §4's structural work;
   LLP 1115 D6's split by shape holds.
7. **Unsaid `autocorrect` and `spellcheck` are the person's settings.** The host writes only
   what the author wrote.
8. **A release build has no Develop menu.** It follows the development trust the build bakes.

### D8 — Scrolling feels like the platform

What scrolls, and how far, is layout and stays CSS. How it feels is the platform's:

1. **An unsaid `overscroll-behavior` is the platform's edge behaviour.** On iOS and macOS
   an inner scroller rubber-bands at its end; it does not hand the gesture to the scroller
   around it mid-drag, though a gesture that begins at the edge still goes to the scroller
   around it. `contain` and `none` mean what CSS says. **A written `auto` is CSS's
   chaining**: it is how an author asks for it, and it is what D2's bit is for.
2. **A `scroll` node on the Mac is scrolled by AppKit:** its momentum, its wheel step, its
   elasticity. The hand-rolled 40-point tick goes. This part can land alone.
3. **Scrollers follow the system's style, and the kernel's gutter lands in the same
   change.** A legacy scroller takes room, as it does in Chrome on a Mac. Letting one show
   before layout knows its width would bring back the mismatch that made
   `ChainingScrollView` force overlay scrollers, so the two are one change or neither. Until
   then inner scrollers stay overlay.
4. **`scroll-behavior: auto` animates a reveal and nothing else.** Bringing a focused field
   or a `scrollIntoView` target into view animates on native hosts, unless the person has
   Reduce Motion on; a written `scrollTop` still jumps, since restoring a position must not
   animate.
5. Arrow, Space and Page keys scroll the focused scroller on macOS, by AppKit's own actions.

### D9 — The iOS keyboard goes away as it does in an iOS app

1. **Unsaid `keyboardDismissMode` is `interactive`** on a vertical scroller: the keyboard
   follows a drag that reaches it. An authored value wins. (`on-drag` is what SwiftUI's lists
   do; `interactive` is proposed because it never takes the keyboard from someone who was only
   scrolling a form.)
2. **A plain Return resigns a single-line field.** When the field has a `submit` handler
   the action runs first, and the field keeps the keyboard only if the action focused it
   again, so an "add another" field does not flicker. In a `textarea` Return is a new line.
3. **Return's label is the system's** unless `enterkeyhint` says otherwise; a `submit` handler
   no longer makes it "Go".
4. A tap on blank ground still ends editing. The stated reason becomes that hand-built iOS
   apps do it, not that a page does.

### D10 — A control's spacing and size, the same on every host

r1 proposed dropping Chrome's control margins natively and leaving them on the web. That
makes the same plan lay out differently per host, which LLP 1115 keeps CSS's job to prevent.
So:

1. **Chrome's margins on checkbox, radio and range go on every host.** Lowering stops
   writing them and the web's sheet resets them (the reset path of LLP 1104 D4: preflight
   zeroes them too). A native control's alignment inset stays inside its presentation and is
   not layout.
2. **`range` and a determinate `progress` are full width by an ordinary row.** Their default
   rows gain `width: 100%`, written by lowering as an implied row on every host (D2's bit
   unset), so an authored `width` or flex row wins by the normal rules and nothing is "filled"
   by a host. Their intrinsic size (129 for a range; `10em` × `1em` for a progress) is what
   they fall back to and their flex basis.
3. **`hr` has no margin of its own**, on every host, and is one hairline. **The hairline is
   a shared input**: a width, `-exact-hairline`, that the kernel resolves to one device pixel
   from the display's scale, which is a layout input as the root font size is. Authors may
   write it in place of `0.5`.
4. `audio controls` keeps its 300 × 54 box.

### D11 — iOS bars, lists and rows

1. **The route's scroller is the bar's scroller with nothing written.** The large title
   collapses and content runs under the bar without `navigationScroll`. When a route has
   several scrollers the host picks the one it already picks for the status-bar tap, by one
   rule for both; `navigationScroll` stays as the way to name a different one.
2. **Header search takes UIKit's placement** and hides on scroll as UIKit does.
3. **A tapped grouped row stays selected through the push** and fades on return. Re-tapping
   the selected tab at its root scrolls to the top. `refresh` on a grouped list is on the list
   that shows.
4. **In a grouped row, a field and a textarea are borderless.**
5. **A `dialog` that is not alert-shaped is a sheet** on iOS, where today it presents
   nothing. The alert shape stays the alert (LLP 1115 D6); this is the other half of the
   same split by shape, and it is its own piece of work.
6. Small ones: a `link` is a link to VoiceOver; key commands carry titles, so holding ⌘ lists
   them; `user-select="text"` is honoured; a segmented title takes its own width.

### D12 — Type is the platform's, all the way

1. **An authored absolute `font-size` is the author's number on every node.** A native
   button's title stops scaling it. `rem` and text styles are what follow Dynamic Type, and
   the docs and `no-tells` already steer authors to them.
2. **A text style carries its weight and its leading**, per platform (the Mac's `headline`
   is bold), when `font-weight` and `line-height` are unsaid. The kernel resolves both before
   it measures, so layout and paint agree. Lowering names the style for a heading and for the
   `font` shorthand, where today it writes a literal weight and `line-height: normal`.
3. **Increase Contrast moves roles, and Dynamic Type moves `rem` and text styles**, as they
   do now. **Bold Text weights the system font, an authored weight included** (ruled,
   Charlie, 2026-10-11). The setting is the person's, not the platform's default, so the
   order is: the person's accessibility settings, then the author, then the platform, then
   CSS's default. It reaches only what it reaches in a hand-built app: the system font. A
   font file the author ships is left alone. How much heavier each weight becomes is
   measured on a device, not guessed.
4. **Unsaid font metrics are the platform's.** `line-height: normal` and `ui-monospace` on an
   Apple host are CoreText's. The two `QUEUE.md` entries that ask to match Chrome there are
   closed, and cross-host layout fixtures pin a face and a line height (D14).
5. **`aria-level` without `role="heading"` is not a heading.** r1 gave it the heading's
   style; that makes a title VoiceOver does not announce. The compiler warns and names
   `role="heading"`, and iOS stops reading a bare `aria-level` as a heading for the bar, so
   every host agrees.

Withdrawn from r1: an ellipsis by default on a clipped line. A box the author clipped is
layout the author wrote; `text-overflow` stays `clip` unless written. [KRN-13 is left.]

### D13 — States the platform's control does not have

1. **An empty date** shows the author's `placeholder` in the platform's pill, and with none
   it shows no words at all. Chrome's English `mm/dd/yyyy` goes, and so would a localised
   pattern in its place: either is a browser's empty field drawn on a control that has none.
2. **A radio on iOS** is the SF Symbols pair at body size with a 44-point target, as the
   checkbox is; in a grouped row it is the row's checkmark accessory.
3. **Accessibility values are the platform's:** a checkbox reads as a toggle with UIKit's
   own value, spoken in the person's language. `tree --ax` joins on what the author wrote
   (D14).
4. **An alert has no outside.** Lowering implies `closedby="any"` for every `alertdialog`,
   so on the web and the Mac a tap outside dismisses a dialog that iOS presents as an alert
   with none. The implied value for an alert-shaped dialog becomes `closerequest`: Escape and
   Back cancel, a tap outside does nothing. An author who writes `closedby="any"` gets the
   platform's dismissible form (an action sheet or popover on iOS, a light-dismiss dialog on
   the web). The diagnostic stops saying a native confirmation "is dismissed by a tap
   outside it".

### D14 — The oracles move with the rule

1. **A test that pins a retired default is rewritten in the commit that changes the default.**

2. **Cross-host layout comparisons pin their inputs.** LLP 1115 §4 promised a pinned root
