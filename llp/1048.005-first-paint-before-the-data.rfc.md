## Summary

A served page today sends its head at once and nothing of its body until the page has settled, so a reader sees nothing until the slowest answer is in. React's RealWorld server sends the page's frame — navigation, banner, "Loading articles…", footer — about 1 ms after the request and the articles when the API answers.

A route may now declare `paint=boot`. Its server sends the **boot document** — the page as the runner boots it, every answer still to come, its placeholders showing — right after the early head, with the head's fields (title, metas, fonts) in the head. Then, when the page settles, it sends the **settled document**, exactly as today, preceded by a style that hides the boot document and followed by one inline script, admitted by its hash, that removes it before the runtime adopts the settled one. A reader without JavaScript ends with the settled document shown and the boot document hidden. Presses and edits made on the boot document are moved to the settled elements at the same place and replayed as LLP 1048.001 D5 replays any early press.

## 1. The decisions

**D1 — Opt-in per route: `paint=settled|boot`.** A route's policy field beside `render=` and `activate=` (LLP 1048.003 D5); undeclared is `settled`, today's page. The plan carries it in the routes table (`paint`, enum `PaintPolicy`). `paint=boot` goes only with `render=cached` or `request`: a page made at build, or on the client, waits on nothing a reader sees, so `lower-route-field` refuses it elsewhere. It is an author's choice and not a default because it trades bytes and a head computed before the data (D3) for first paint, which is worth it only when the route's answers are slow (§3).

**D2 — The boot document is the runner's boot, projected.** After `Runner::boot_at` and before the first answer, the render host projects the runner's instance tree (`document_tree`, the same fold and projection as the settled page, LLP 1048.004 stage 1) in the runtime's form, and sends it in `<div id="exact-root" data-boot="">`. It shares the root's id so the shell's scoped classes (`#exact-root#exact-root{.cN{}}`) style it. A page with nothing pending at boot settles as it boots, so it gets no boot document. This adds no second renderer: the boot document is what the client runtime would itself draw before its answers.

**D3 — The head is the boot document's.** The head's fields go with the boot document, before it, so they are in `<head>` (the parser closes the head at the boot document's first element). Nothing of the head is repeated after it: there is one `<title>`, one viewport meta. A field that reads an answer (RealWorld's article title, `${post.title} — Conduit`) has its answer-less value in the served head; the runtime writes the settled value when it adopts (`rt.js` `hd`, which sets `document.title` and the description from state). So a reader with JavaScript has the right head once the runtime is up; **a reader without JavaScript (a social card's scraper) sees the boot head.** A route whose head depends on its data and must be right for such readers should not declare `paint=boot`. Two head-related parts may follow the boot document, in the body: `@keyframes` the settled document names beyond the boot document's (a `<style>`), and the document-scroll script when only the settled document asks for it.

**D4 — The swap.** The settled part opens with `<style>#exact-root[data-boot]{display:none}</style>`, so the boot document disappears as the settled root begins to arrive, script or none. Right after the settled root's `</div>`, before the checkpoint and the module script, an inline script (`exact_render::boot_swap_js`):
- maps each press or edit the capture script queued on a boot element (`exact.q`) to the settled element at the same child-index path from the root, copying an edited control's `value` and `checked`;
- moves focus the same way;
- removes the boot document.

The runtime then finds one `#exact-root`, the settled one, and adopts it as today; the capture script's queue is replayed as today. The CSP admits the script by its sha256 like the capture script (`serve.rs` `csp`). The capture script loads the runtime only once the checkpoint is in the page, so a press on the boot document queues and waits for the settled page.

**D5 — What is kept.** A page a server keeps (`render=cached` with a lifetime) is kept as the settled page alone, with the settled head: no boot document, no hiding style, no swap script. A later reader gets it whole, as any kept page.

**D6 — LLP 1048.000 D6 still holds for the settled document.** The settled document is the settled checkpoint's projection, byte for byte what it would be without `paint=boot` (`--compare` is unchanged). The boot document is outside that rule: it is not adopted, it is never kept, and it is gone before the runtime starts.

## 2. What it costs

- **Bytes.** The boot document repeats the page's frame. RealWorld's home is +0.3 KB compressed (7.4 → 7.7 KB); a page whose boot document is large pays for it twice.
- **Server CPU.** One extra projection of the boot tree per render, and nothing when nothing is pending. Measured in §3.
- **The head (D3).** A field that reads an answer is right for a reader with JavaScript, wrong for one without.

## 3. Measurements

The shipped build (e72a8e81) against the same commit with every route settled, react-ssr and solid-ssr, measured side by side on the mobile profile with real network shaping (4× CPU, 150 ms RTT, 1.6 Mbps), 9 runs, medians, every build interleaved run by run (2026-10-01). An early press is pressed sooner on the boot document (the harness presses at first paint), so its time from press to answer is longer, while the answer lands at the same moment (RealWorld's page-2 press answered at 1192 vs 1188 ms at 20 ms, 1322 vs 1332 at 150 ms).

Server CPU per page (both servers driven at once, a navigation's headers, RealWorld `/`): 3.00 → 3.05 ms at concurrency 8 (+1.8%), 2.77 → 2.75 at 64 (p95 191 → 190 ms); `/tag/javascript` +2.4%; the feed's timeline 4.63 → 4.67 (+0.7%). Within the machine's noise.

What a reader sees (a filmstrip at 150 ms): the boot frame — navigation, banner, the feed's tab, "Loading articles…", "Loading tags…", the footer — then, about 120 ms later, the settled page in one step. The navigation, banner and tab do not move; only the placeholders become the content. There is no blank frame between them and no layout shift (CLS 0: the settled content is new elements, not moved ones).

## 4. Alternatives considered

- **Every route, always.** Rejected: at a fast API the gain is about 20–50 ms and the head of a data-dependent route is the boot head (D3).
- **Out-of-order slots (React's `$RC`): stream the boot document and patch each region as its answer lands.** More first-content wins on pages with several independent answers, but the document is then many scripts' work rather than one projection, and adoption would have to start from a document no projection produced. Not now.
- **The head after the boot document.** The experiment's form: the title still worked, but the metas and fonts landed in `<body>`, where crawlers and the preload scanner ignore them. D3 replaces it.
