# LLP 1114.008: Accessibility actions on an element, as ARIA's `aria-actions`

**Type:** RFC
**Status:** Draft, 2026-10-08. Not reviewed.
**Systems:** Contract (`aria-actions`: `contract/lower/src/tags.rs`, `contract/lower/src/lint.rs`); the kernel table (one `str` prop: `kernel/tables/schema.json`); the web hosts (`host/web/src/element.rs`, which the JS target shares); the Apple host (`host/apple/Sources/ExactKit/Accessibility.swift`, `IOS/NodeViewIOS.swift`, `Mac/NodeViewMac.swift`, `IOS/ContextMenusIOS.swift`, `Mac/MenusMac.swift`); the agent's `tree --ax` (`host/apple/Sources/ExactKit/AgentAccessibility.swift`, `scripts/agent-ax.mjs`)
**Author:** Claude (Opus 5.5) for Charlie Cheever
**Date:** 2026-10-08
**Implementer:** unassigned until ruled
**Related:** LLP 1114 (the parent: what the Bluesky clone asks of Exact2); LLP 1080.002 (`tree --ax`, its four findings, and "driving VoiceOver" refused, §4); LLP 1057.000 §10.4 (custom actions derived from gestures, Draft); LLP 1094 (the reorder grip's four custom actions, built); LLP 1021 §5.1 (`contextPopover`) and its deferred keyboard route (`llp/1021-menus.rfc.md:886`); LLP 1015 (Linux: "accessibility of any kind" deferred, `llp/1015-linux-host-v1.spec.md:655`); WAI-ARIA 1.3's proposed [`aria-actions`](https://github.com/w3c/aria/pull/1805) and its Core-AAM mappings (same PR), from [w3c/aria#1440](https://github.com/w3c/aria/issues/1440)

## 1. Summary

An element takes `aria-actions`: the ids of other elements that act on it. For
example, a post names its Reply, Repost and Like buttons. Assistive technology
offers those as the element's actions. VoiceOver lists them in its Actions
rotor. Choosing one presses the button it names. This is ARIA's proposed
attribute, as Firefox and Chrome 151 already ship it. Each action is named by
the referenced element's accessible name, so there is no second list of labels
to keep in step. The web passes the attribute through. iOS, tvOS and macOS map
it to `accessibilityCustomActions`. Linux, Windows and the terminal have no
accessibility tree yet, so it does nothing there. Separately, an element with
a context menu gets the platform's show-menu action, which is Bluesky's
actual use on its chat messages.

## 2. What Bluesky does

`source.md` says "VoiceOver actions on a post (like, repost, reply)". **That
is not what Bluesky does.** The facts below are from `social-app` at
`35fd4fbad`, 2026-10-08. Its feed posts expose their buttons as separate
elements and have no custom actions. Its custom actions are:

- **A chat message.** The message is one element with one action, "Open
  message options", which opens its context menu
  (`src/components/dms/ActionsWrapper.tsx:38-43`).
- **A conversation in the chat list.** Magic tap and long press open
  "conversation options" (`src/screens/Messages/components/ChatListItem.tsx:500-511`).
- **A notification.** The notification is one element. Its actions are
  "Expand/Collapse list of users", or "View <name>'s profile"
  (`src/view/com/notifications/NotificationFeedItem.tsx:586-612`).

So the clone needs two things:
- named actions that do what an inner control does (the notification);
- an action that opens an element's context menu (the message).

Putting Reply, Repost and Like on a post would go beyond Bluesky. It is the
same feature, and the clone may do it.

## 3. What exact2 has today

- **ARIA in Contract, without actions.**
  - Contract carries ARIA names and maps them to `accessibility*` props
    (`contract/lower/src/tags.rs:548-556`, `:633-652`).
  - That includes three ID-reference attributes: `aria-labelledby`,
    `aria-describedby` and `aria-controls`.
  - `lint.rs` knows WAI-ARIA 1.2's names (`contract/lower/src/lint.rs:35-90`).
    `aria-actions` is not among them, so the compiler refuses it as not
    ARIA's.
- **No accessibility tree in the kernel or runner.** Each host builds the
  platform's tree from its own views (LLP 1080.002, Systems). The only action
  that comes back is a press:
  - iOS: `accessibilityActivate`, `IOS/PointerIOS.swift:229`;
  - macOS: `accessibilityPerformPress`, `Mac/NodeViewMac.swift:1341`.
- **Custom actions exist in two fixed places, both Apple:**
  - The reorder grip's four ("Move earlier", …), at
    `IOS/ReorderPartsIOS.swift:147-155` and `Mac/ReorderPartsMac.swift:141-146`
    (LLP 1094).
  - Swipe rows on iOS. While VoiceOver or Switch Control runs, each row
    stays a `UITableViewCell` that is one accessibility element, so UIKit
    offers its swipe actions (`IOS/SwipeActionsIOS.swift:13-30`, `:312-318`).
  - Neither is something an app declares.
- **ID references already resolve on Apple.** `aria-labelledby` finds its
  views through `presenter.chrome.named`
  (`host/apple/Sources/ExactKit/Accessibility.swift:29-39`). The web writes
  an authored `id` as the DOM `id` (`host/web/src/element.rs:944`).
- **Context menus are invisible to assistive technology.**
  - iOS uses a `UIContextMenuInteraction` (`IOS/ContextMenusIOS.swift:114-116`),
    and the repo neither builds on nor tests what VoiceOver does with it.
  - macOS opens an `NSMenu` on right-click (`Mac/MouseEventsMac.swift:68,87`).
    It has no `accessibilityPerformShowMenu`.
  - The web's keyboard route is deferred (`llp/1021-menus.rfc.md:886`,
    `QUEUE.md:400`).
- **The agent can read actions on iOS only.** `tree --ax` reports iOS
  custom actions (`AgentAccessibility.swift:401`). macOS's `AxFacts` does not
  read them (`:287-300`). The web reads Chrome's computed tree. No host can
  invoke an action: driving VoiceOver is refused (`rules/DEFERRED.md:773`).
- **Elsewhere:**
  - Linux has no accessibility of any kind (LLP 1015). `tree --ax` answers
    "no AT-SPI tree" (`host/linux/src/agent.rs:711-714`).
  - Windows and the terminal have none.
  - AccessKit is not in `Cargo.lock`.
- **No prior decision.** LLP 1069's survey does not cover this. LLP
  1057.000 §10.4 says "ARIA has no custom actions" (`:489`), which was true
  of ARIA 1.2 and is no longer the whole story.

## 4. What the web does

- **ARIA 1.2 has no custom actions.** The Accessibility Object Model's
  custom actions (Phase 2, 2017) were never specified. WebKit closed its
  implementation bug as superseded.
- **The successor is `aria-actions`.** It started as Sarah Higley's
  proposal ([w3c/aria#1440](https://github.com/w3c/aria/issues/1440)). The
  spec text is [w3c/aria#1805](https://github.com/w3c/aria/pull/1805), which
  was still open on 2026-10-08 and is proposed for ARIA 1.3. The proposal
  says:
  - **The value** is an ID reference list. It "identifies a related element
    or elements whose primary activation (click event) will trigger a
    behavior or operation relevant to the referencing user interface object,
    such as the close button for a tab, or the reply button for a message."
  - **The referenced elements** may be anywhere in the document. Authors
    MUST give each one an accessible name. Each MUST respond to `click`.
    Each MUST be keyboard-reachable, or have a shortcut while the
    referencing element has focus.
  - **Action names:** user agents SHOULD use the referenced elements'
    accessible names as the actions' names.
- **Platform mappings (Core-AAM, same PR):**

  | API | Mapping |
  |---|---|
  | AX API (macOS; iOS by the same model) | "Implement as a custom action" |
  | ATK/AT-SPI | `AtkAction`: one action per referenced node, named `custom_<id>`, localized name the target's accessible name, `do_action` activates the target; `has-actions:true` |
  | IAccessible2 | `IAccessibleAction`, the same scheme |
  | UIA | the custom property `AccessibleActions` (an element array); `AriaProperties.hasactions` |

- **Shipping:**
  - Firefox has shipped it.
  - Chrome 151 ships it on Windows, macOS and Linux desktop
    ([Intent to Ship](https://groups.google.com/a/chromium.org/g/blink-dev/c/DNE6dB1AS0Y)),
    but not on Android or ChromeOS.
  - Safari has it behind a flag.
  - Microsoft's Fluent UI plans to adopt it.

The platforms' native APIs are
[`UIAccessibilityCustomAction`](https://developer.apple.com/documentation/uikit/uiaccessibilitycustomaction)
(iOS and tvOS),
[`NSAccessibilityCustomAction`](https://developer.apple.com/documentation/appkit/nsaccessibilitycustomaction)
(macOS), `AtkAction` on AT-SPI, and UIA's custom properties or patterns.
Context menus have standard actions of their own: macOS's `AXShowMenu`
(`accessibilityPerformShowMenu`), and the keyboard's ContextMenu key or
Shift+F10 on the web.

## 5. Design

### D1. The shape: `aria-actions`, references to real controls

- **(a) `aria-actions`.** An ID list naming elements that already have a
  `press`. It is the web's own proposal, two engines ship it, and every
  action is a real control the person can also reach without assistive
  technology.
- **(b) React Native's shape.** `accessibilityActions=[{name, label}]` plus
  an `accessibilityaction` event that carries the name. It is not the web,
  and it lets an app offer an action no visible control has, which WCAG 2.5.1
  needs authors to avoid anyway.
- **(c) Only actions derived from gestures** (LLP 1057.000 §10.4). This
  covers swipes and context menus, but not "expand the list of users".

**Recommendation: (a), plus D4 for context menus.** (c) stays 1057.000's to
decide for gestures.

```text
column press=open(post.path) aria-actions=`reply-${post.id} repost-${post.id} like-${post.id}` aria-label=post.summary …
  …
  button id=`reply-${post.id}` press=reply(…) aria-label="Reply" …
```

### D2. Contract

- **The prop.** `aria-actions` lowers to a new `str` prop,
  `accessibilityActions`. It is space-separated ids, as `aria-labelledby` is
  (`schema.json`, `accessibilityLabelledBy`).
- **`lint.rs`.** `aria-actions` joins its list, which grows from 1.2's
  names to 1.2's plus `aria-actions`. The comment there names the PR it
  follows.
- **A literal id is checked at compile time.** It must name an element in
  the same component that has a `press` (or is a `link`) and an accessible
  name. Otherwise the build fails, because the proposal's MUSTs are what make
  the action work.
- **A computed id is checked when the host resolves it.** One that names
  nothing is dropped, as browsers drop it, and is reported once in `logs`.

### D3. Per host

| Host | What it does |
|---|---|
| Web (wasm and JS target) | Writes `aria-actions` as is; ids are the app's own (`element.rs:944`). The browser does the rest. Chrome desktop and Firefox expose it; Safari does not yet, and Chrome on Android does not. |
| iOS, tvOS | `accessibilityCustomActions` on the element's view. There is one `UIAccessibilityCustomAction` per id that resolves (through `presenter.chrome.named`, as `labelledBy` does). Its name is the target's `accessibleName`, read when VoiceOver asks, so "Like" becomes "Unlike" without a commit. Its handler presses the target through the same dispatch as the target's own `accessibilityActivate`. The element becomes one accessibility element, named by accname (its `aria-label` or `aria-labelledby`, else its text, `Accessibility.swift:17-40`). |
| macOS | `accessibilityCustomActions()` returns `NSAccessibilityCustomAction(name:handler:)`, and the handler calls the target's `accessibilityPerformPress()`. The element's children stay in the tree, as Chrome's mapping leaves them. |
| Linux, Windows | Ignored. There is no accessibility tree (LLP 1015). When AT-SPI arrives, Core-AAM's `AtkAction` mapping above is the one to build; UIA's `AccessibleActions` on Windows. |
| Terminal | Ignored. There is no screen-reader surface. |

Merging and order:

- The actions follow the attribute's order.
- On a reorder grip they come after the grip's four actions.
- On a swipe row (iOS) they come after the row's swipe actions.

**Why iOS makes the element one accessibility element.** VoiceOver offers
the actions of the element it has focused. A plain `column` with children is not
an element (buttons and labelled images are made elements at
`IOS/NodeViewIOS.swift:1140-1153`), so its actions would never be offered.
UIKit's own list cells work the same way: the cell is the element, and its
swipe actions are its actions (`SwipeActionsIOS.swift:316`). It is also what
Bluesky does: `accessible={true}` on the message and on the notification.

**The cost.** Under VoiceOver on iOS, the element's descendants are reached
only through its actions. That includes inline links in a post's text. An app
lists every control that matters. That is the trade every native list cell
with actions makes, and Q2 asks Charlie to accept it.

### D4. A context menu is an action

An element with `contextPopover` gets the platform's standard way to open it:

- **macOS:** `accessibilityPerformShowMenu()` opens the same `NSMenu` a
  right-click does (`Mac/MenusMac.swift:207`). That is `AXShowMenu`, which
  VoiceOver offers as VO-Shift-M.
- **iOS and tvOS:** first verify on a device what VoiceOver offers for a
  view with a `UIContextMenuInteraction`. If it offers nothing, add one
  custom action that presents the interaction. It is named by the popover's
  `aria-label`, which the compiler then requires on a context popover.
  Bluesky's own label for this is "Open message options".
- **Web:** unchanged here. The keyboard route (Shift+F10, the ContextMenu
  key) is LLP 1021's deferred item.

### D5. The grant, the clock, the agent

- **Grant:** none.
- **Data modules:** untouched.
- **`tree --ax`** reports each element's `actions` (names, in order) on
  every host that has a tree:
  - iOS already does (`AgentAccessibility.swift:401`).
  - macOS reads `accessibilityCustomActions()` into `AxFacts`, plus a
    `showMenu` flag.
  - The web reads the names from Chrome's computed tree if CDP serves them,
    or else from the attribute, resolved to the targets' computed names.
- **LLP 1080.002's parity finding** ("a role or name disagreeing with the
  web") extends to the action list for `testId`-joined fixtures. That is a
  wider comparison inside an existing finding, not a fifth finding.
- **Invoking:** no new operation. An action is its target's press, so
  `tap like-<id>` already drives it. Driving VoiceOver stays refused.

## 6. Questions for Charlie

1. **Take `aria-actions` from an ARIA PR that has not merged?** Firefox and
   Chrome ship it, and it is the only web-shaped proposal. If the name or
   meaning changes before ARIA 1.3, exact2 follows, and per the rules there
   is no compat shim. **Recommended:** yes.
2. **On iOS, does an element with actions become one accessibility element
   (D3)?** **Recommended:** yes. It is the only way VoiceOver can offer the
   actions, and it is UIKit's and Bluesky's own shape. The cost is named
   above.
3. **D4 (context menus) in this RFC, or its own?** **Recommended:** in
   this RFC. Bluesky's one post-like use (the chat message) is exactly this,
   and the macOS half is a few lines.

## 7. What the clone does after

- **Notifications.** A grouped notification becomes one element
  (`aria-label` summarising it) with
  `aria-actions="expand-<id> profile-<id>"` over its existing toggle and
  avatar link.
- **Chat messages.** Messages with `contextPopover` get the show-menu
  action with no code (D4), and the popover gets `aria-label="Message
  options"`.
- **Posts, optionally.** Each post's `column` takes
  `aria-actions` over its Reply, Repost, Like and More buttons. Their `id`s
  become per post, and `aria-label` summarises the post.
- **Verified by:**
  - `bun scripts/agent.mjs ios tree --ax` shows the notification's and the
    post's `actions` in order, and the parity finding is clean against the
    web;
  - `tap like-<id>` followed by `tree --ax`, which shows the action renamed
    "Unlike";
  - by hand, VoiceOver on an iPhone and on macOS: swipe up or down on the
    Actions rotor, choose "Like", and the heart fills.

## 8. Effort and complexity

**exact2: S–M.**
- **Easy:**
  - the Contract attribute and lint entry, and the schema prop;
  - the web, which is one attribute mapping;
  - macOS, whose custom actions and show-menu are a getter and an override;
  - the agent's macOS facts.
- **Harder:**
  - iOS's collapse: an element with actions must stop exposing its children
    without breaking `tree --ax`'s walk or the swipe-row cells that already
    collapse;
  - the iOS context-menu half of D4, which needs a device check first.
- **The compile check for literal ids** is a small pass over one component.

**Clone: S.** It adds attributes and per-post ids to existing elements.

## 9. Not in scope

- Actions an app offers with no visible control (option (b)).
- Standard VoiceOver gestures: magic tap, escape, and increment or decrement
  on a non-control.
- Android's TalkBack (exact2 has no Android host).
- An AT-SPI tree on Linux or UIA on Windows (LLP 1015's deferral stands).
- Driving VoiceOver from the agent (`rules/DEFERRED.md:773`).
- Actions derived from gestures, which are LLP 1057.000's.
