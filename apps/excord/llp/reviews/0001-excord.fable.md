Review of LLP 1141 (Excord). I read the RFC in full and checked its claims against LLP 1016.000, LLP 1010, the reference, the rules, and the two Messages apps. Five fundamental points, most serious first, then the two requested verdicts.

**1. The gateway's READY frame will end the stream for a real account, and the plan cannot see it until stage 3.** A D7 socket takes a 1 MiB per-message ceiling by default (`runner/src/request.rs:44`), and a frame over it ends the stream with a visible refusal (`docs/reference.md:1237`). Discord's user-account READY carries every guild's channels, roles and emoji; past roughly ten active servers it is several megabytes uncompressed. The RFC treats compression as a cellular nicety for later, and runs stage 2 on a fresh second account with few servers, which is exactly the account that keeps READY small. The first connect from Charlie's real account, in stage 3, is where the gateway dies. This is fundamental because it shapes §4.2 (the mapper parses the whole READY on the data thread, once per failed RESUME) and decides whether an Exact ask exists. What instead: the escape hatch is already in Exact. The gateway's fetch should set `exactIndependentHttp.maxResponseBytes` high from the first line (`docs/reference.md:913`, up to 64 MiB, counted twice). Add to stage 1's gate one read-only connect on a many-server account that records READY's compressed and uncompressed size and its parse time on an iPhone 12. Decide `zlib-stream` from that number, knowing Hermes has no `DecompressionStream`, so inflate is pure TypeScript.

**2. §2's rules protect the second account, not the main one.** Three gaps. First, acks and typing indicators are writes a reader emits passively, so an agent's "read-only" drive that opens channels will write unless the app suppresses them in agent mode. Second, stage 3's writes are "by hand" but the RFC does not say on which account, and the exit criterion for the second account is a week of clean reads, which does not test the behaviour that gets accounts flagged. Third, pinning one desktop client identity everywhere puts Chromium properties on top of URLSession's TLS fingerprint on iOS, a mismatch the official iOS client never shows. What instead: name acks and typing as writes under rule one and suppress them in agent drives. Keep stage 3 on the second account too, and move the main account only after the app has been boring in daily human use. Identify as the official client of the host you are on, as the web stage already does. Also age the second account in the official app before pointing Excord at it. Confidence the rules keep a second account alive: 85%. Confidence they are enough as written to protect Charlie's main account: 60%.

**3. §4.2: build (b), and skip the measurement.** A 5,000-message snapshot crossing the Hermes door and conformed per dispatch will not measure under a millisecond on an iPhone 12, so the threshold is a formality. (b) is right for a structural reason the RFC does not name: the gateway stream's arguments must be constant, since changed arguments end the socket (D2), so the stream's snapshot cannot depend on which channel is open. (b) as written is incomplete in one way. Mutations cannot move a version that lives in the stream's snapshot, so history loads and optimistic sends must use Contract's `refreshes` on the window resource; the version argument then covers only gateway-driven change. Make the window resource answer one contiguous run around the anchor, not the channel's history. That also removes §6's third ask: the list never needs discontiguous windows, and a jump is a fresh key set restored with the `scrollIntoView` offset form of `llp/1010-scrolling-v1.spec.md:1240`. Check that before filing it. Confidence in (b): 85%.

**4. Messages is the wrong tiebreaker for a Discord-shaped transcript.** LLP 1115's oracle is a hand-built screen of the same kind on the same OS. A full-width, author-grouped transcript with hover actions is not Messages, and §3 already needed one exception for swipe direction. The platform should still win on controls, motion, keyboard, menus and haptics. For transcript structure and behaviours (grouping, dividers, the jump pill, reply gestures), the reference is Discord's own iOS app, and Messages only where the two are identical in kind, such as composer growth and keyboard interaction. Seventeen acceptance properties hang on this. Confidence it matters: 70%.

**5. Stages 6 and 7 assume a socket the reference does not grant them.** The RFC calls Windows and Android "the same app" with gaps filed against §3, but TypeScript sources receive the bidirectional socket only on the web JS target, macOS, iOS and Linux (`docs/reference.md:1121`), and Windows TypeScript still awaits its qualification (`docs/reference.md:40`). Android may inherit the Linux executor's path. Add a one-line `wss:` echo on each host to stage 1 so those stages are gated on a known D7 port rather than discovered at the end.

No other fundamental concerns. The fixture-first plan, the TypeScript choice, the stage order through macOS, and the process in §8 hold up against the rules and the existing transcript work.
