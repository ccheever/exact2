**A Mac canvas draws some of its native text upside down since cc60cf219** (2026-10-04; found driving Caltrain after a build-speed change, bisected on the M4 over 157 commits with a capture compared by pixels). Caltrain's header card (the name, "Change station", "Web deck", the theme row, the train), the search field's text and "Back" are each flipped top to bottom in place, on screen and in the agent's screenshot; plain text rows beside them ("Matches", "Palo Alto") are upright, and two dividers are gone. `cc60cf219` ("compose macOS canvas uploads in current paint order") is the first commit that shows it: `Capture.bitmap` stopped using `cacheDisplay` and renders a copied layer tree with `CALayer.render(in:)` (`paintOrderBitmap`), which does not draw an AppKit view's flipped contents the way AppKit does. `bun scripts/agent.mjs macos "tap change-station" "type station-search Palo" "clock settle" "screenshot out.png"` shows it. This belongs with the entry below: whichever capture is kept has to draw those views upright. It is also the macOS smoke's one failure on a 1x Mac: the sky fixture's "Zoom" and "Label" are upside down (1.58% of pixels beyond the band against `canvas-sky.macos.420x120.png`, which shows them upright). Ruled out (fix/health6, 2026-10-04, four tries reverted): `contentsAreFlipped()` does not tell the turned layers from the upright ones — Caltrain's header texts and its result rows are both `NSViewBackingLayer`s with `NSViewBackingLayerContents`, `contentsAreFlipped() == true` under the one geometry-flipped layer above the overlay's root, identity `contentsTransform`, the same gravity, rect and format, yet the copy draws the header turned and the rows upright. Turning every copied layer whose count of flipped ancestors differs fixes the header and turns the rows; redrawing every view before the copy changes nothing; holding the copy under a geometry-flipped layer mirrors the whole picture with the same split. What the window knows about each backing store that the copy loses is still to be found; the likeliest is an orientation `NSViewBackingLayerContents` carries from when it was drawn (the split differed between runs, the train image upright in one and turned in another), which the window server honours and `render(in:)` does not. The candidate fix is to give the copy each drawing view's own picture as a `CGImage` (its `draw(_:)` into a bitmap, as `cacheDisplay` did before cc60cf219) in place of its backing store; a single NSView fixture captured both ways would confirm it first.
