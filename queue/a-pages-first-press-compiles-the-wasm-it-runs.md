**A page's first press compiles the wasm it runs** (2026-09-25, a trace of RealWorld's post-read tap at ce3a4d68; LLP 1047 §10). V8 compiles each wasm function on the main thread at its first call, and the boot never runs the press path: the route change, the source call and its fetch, the list rebuild, the batch. On the bench's mobile profile (4× CPU), the `python` tag after a 3-second read spent about 14 ms compiling wasm and 5 ms compiling JavaScript before its request left, and about 5 ms more compiling wasm once the answer came. A warmed press compiles nothing: 7 ms from click to request and 5 ms from answer to DOM, against React's 11 and 4 (nine runs each, a raw `page.mouse.click`, loads 9–35). Lazy compilation is already most of the boot's cost (LLP 1047 §10), and compile hints still need a Chrome flag. The press path could be compiled while the page idles after activation, for instance by running it once on throwaway input. **Not taken for now** (2026-09-26, the third step of the load sequence Charlie approved; bailed as its goal allowed). The prize is about 24 ms on the first press on a 4× CPU (about 6 on a real phone), where exact2's first press already beats React's (192 against 212 ms from `pointerdown`). The clean lever, a build-time `metadata.code.compilation_priority` section for the press path's functions, did nothing in Chrome 153: a traced probe still compiled the hinted function lazily at its call. The same probe under `--experimental-wasm-compilation-hints` did too, so the probe shows no working hint in any configuration, not only the shipping one. What is left is new apparatus for 24 ms once per page: running a handler speculatively (side effects on the live page), or a second instance in a worker that shares the compiled module and runs the press path on throwaway input. Worth reopening when compile hints ship. The 5 ms of JavaScript could be tried alone with V8's `//# allFunctionsCalledOnLoad` on the minified glue (untested; it compiles every glue function at load, off the main thread).
